## Goal

Nostr is **a deep, first-class integration, not a thin account-link bridge** (decided 2026-06-08): the user's Fauna nest is their **personal Nostr home** — a NIP-01 relay + bidirectional outbox sync, a `you@<nest-domain>` NIP-05 identity (nests already have domains), and an optional NIP-46 self-signer ("your sovereign Nostr identity, hosted on your own box"). This is the most Fauna-aligned bridge (Nostr's decentralization fits the nest-as-home-server model far better than the more-centralized Bluesky/ActivityPub). Target: the deep surface — account/relays/follows, DMs, and Nostr-native content (reactions, reposts, long-form, communities, live, classifieds, zaps, badges) — exposed uniformly across all 7 apps. Today: full on all 7, with DMs as bridged rooms on unified Conversations rather than on this page — windows closed the last page gap 2026-07-29 and the last *Connected apps* NIP-46 gap 2026-07-30, so every settings surface this doc tracks is now on all 7 (§ Implementation status today).

## Architecture (ratified 2026-06-08)

**This integration is already deep in code** — the work is largely *exposing + ratifying* it, not building from scratch:
- **Shared Rust:** `libs/fauna-bridge-nostr` implements ~20 NIPs (01 relay, 02 contacts, 04/17/44 DMs, 05 identity, 10 threads, 11 relay-info, 18 reposts, 19 bech32, 23 long-form, 25 reactions, 42 auth, 46 remote-signing, 53 live, 57 zaps, 58 badges, 65 relay-lists, 72 communities, 99 classifieds) with a bidirectional `translate.rs` mapping Fauna's content model ↔ Nostr event kinds. **All Nostr logic (relay clients, event composition, signing, encryption, translation) lives here — never per-app** (priority #2). The only acceptable app glue is the NIP-07 browser-extension boundary call.
- **Server-side relay:** `bins/fauna-nest/src/nostr/relay_endpoint.rs` — `wss://<domain>/nostr` (NIP-01) + `/nostr/info` (NIP-11), NIP-42 auth, serving the user's opt-in "exposed" content as Nostr events. **External-relay sync:** `nostr/sync_worker.rs` — outbound crossposting to the user's relays + inbound follow-and-ingest, NIP-65 relay-list publishing. The inbound sweep also carries the followed authors' kind-0 metadata into the cross-bridge `bridge_authors` projection — owner [`../behavior/bridges.md`](../behavior/bridges.md) § Unified feed ingestion → *Bridged authors*.
- **Key custody:** the user's `nsec` is stored **encrypted-at-rest with the nest identity key** (`nostr/key_crypto.rs`); the nest decrypts it server-side to sign/relay on the user's behalf. A **NIP-46 bunker** (`signing_mode` / `nip46_bunker_url`) is the non-custodial alternative for users who keep their key external.

### The bridging gate is the central constraint — phased rollout

Server-side bridging acts as the user's Nostr **agent** — it signs and relays with the user's key, translates the user's exposed content, and unwraps NIP-17 gift-wrap DMs in flight. So bridging is gated on the user actually trusting the box with their key, in two phases:

- **Phase 1 — gated on the deposited `nsec` (built 2026-07-12, Phase-4 S8.9).** Nostr bridging runs in-process for exactly the users who deposited an `nsec` on the box (`nostr_accounts.encrypted_privkey` — the explicit per-user trust act; box-level predicate `nostr::db::any_nsec_deposited`, per-user enforcement structural: signing, gift-wrap unwrap, and DM send each require that account's own deposited key, and the inbound subscription sweep selects depositor accounts only). A box with no depositor — fresh or legacy — has the Nostr surface **cleanly unavailable / degraded** (gated + surfaced in UI — the mail-`msek`-gating pattern), never half-working. NIP-07/NIP-46 accounts deposit nothing, so their boxes do not bridge in-process (Phase 2 is their story). The deposit licenses the **in-flight** agent acts, not plaintext at rest: inbound gift-wrap DM content is sealed at ingest through the D2 resolver (`get_recipient_seal_key` → `seal_recipient_blob`) to the owner's MSEK-derived recipient key before storage, and an outbound DM's Sent copy arrives already sealed to that key by the sending app — the nest holds no opening key, and the bridged-conversation family's `inbox.fetch` serves the sealed envelope for the client to open (the wire carries only `sealed_content`; no plaintext field exists). Sealed is the **only** at-rest DM shape: pre-S8.9 plaintext rows were **deleted** at migration, not converted (user ruling 2026-07-12 — `../architecture/nest/storage-modes.md` § Legacy artifacts; the gift wraps remain fetchable from the relays). *(Superseded 2026-07-12: the interim S8.4b gate on the legacy `nest_mode` row — the row is now inert for Nostr.)*
- **Phase 2 — a box with no bridging authority delegates to a paired proxy** (implementation spec ratified 2026-07-22, tracked internally; built 2026-07-23 — § Implementation status today). Reuses the **shipped** home-with-public-relay seam (`docs/goal/architecture/nest/deployment-home-with-public-relay.md`): the keyless public box is the user's *serving* relay face; the paired head (the user's trusted box holding the deposited `nsec`) runs every agent act — materialization/signing, gift-wrap unwrap, DM sealing, the NIP-46 signer. **Mechanism (resolved by the spec, superseding the earlier refutable sketch):** a new **`nostr_push` pairing capability** (`fauna_protocol::pair::capability`, in `default_self_sync()`; gates both legs, as `mail_pull` gates `mail_ack`) over **two head-originated channel kinds `fauna.federation.sync.nostr_push` + `.nostr_pull`** — push carries the head's rows public-ward with the RPC reply as the ack; pull fetches externally-deposited rows head-ward, cursor-parameterized (`(stored_at, id)` compound, head-persisted) and **non-destructive** (the public box keeps serving what it relays — no purge, hence no ack kind; this replaces the pre-spec `nostr_{push,ack}` sketch). `post_forward` is **not** reused (the head already holds the canonical fauna content; the public box never needs it). Both legs move signed wire JSON through the shared ingest (`verify → scope → store_event`), so every store invariant carries by construction; an `origin` provenance column (`ingest`/`federation`) stops echo — federation legs never re-export federation-arrived rows. The public box's account row is **auto-provisioned by the push leg** (`signing_mode='proxied'`, keyless — no client action, no `PostLinkHook`); serving availability becomes **`nostr_serving_available` = any nsec deposited ∨ any non-expired `nostr_push` pairing** (per-request derived, so revocation degrades the box immediately and crash-safely), while `nostr_bridging_available` (agency) stays nsec-only — *serving ≠ agency*, extending the NIP-05 "identity ≠ agency" split. NIP-46 bunker traffic (ephemeral kind-24133, never stored) rides no federation batch: **the head subscribes to the public box's own relay as a plain Nostr client** (`kinds:[24133], #p:[signer pubkeys]`, peer URL from its `nest_pairings.nest_url`) and publishes signed responses back as plain ephemeral EVENTs; invite `relay=` hints and NIP-65/10050 self-advertisement name the `nostr_push` peer's public URL when one exists. Compat notes: `pair.add` is full-row replace, so a pre-Phase-2 pairing gains the cap only via an idempotent `LinkBoth` re-run; `'proxied'` is an additive `signing_mode` value all apps must degrade gracefully on.

### The relay event store — the nest is a real relay (ratified 2026-07-13)

The `/nostr` endpoint graduates from a translate-on-read outbox view to a **real NIP-01 relay with a persistent, owner-scoped event store**. Ratified with the user 2026-07-13; built (§ Implementation status today).

- **Owner-only scope (the ratified default).** The store accepts exactly two categories: **(1) events authored by local-account pubkeys** (the owner and any other users on the box — the personal-home model), and **(2) events addressed to a local pubkey** — NIP-59 gift wraps (kind 1059) with a local depositor in the `p` tag, plus reactions/mentions/zap receipts targeting local users' events. Everything else is rejected with `OK false` / `restricted:`. ⚠ **Of category (2) the kind-1059 gift-wrap and kind-9735 zap-receipt halves are built; reactions/mentions are not** (the zap half landed 2026-07-31 — a receipt is accepted only when the `p`-tagged payee designated its signer, [`../behavior/monetization.md`](../behavior/monetization.md) § Zap receipts — the trust model). See § Implementation status today. This bounds disk to what the owner controls and structurally removes the open-relay abuse surface (no operator exists to moderate one — the one-configuration-surface invariant). A wider posture was ruled OUT 2026-07-15 — the relay stays owner-only; see the *Wider posture* bullet below for the rationale and the revisit trigger.
- **Store semantics.** Events persist as signed wire JSON plus indexed columns (id, pubkey, kind, created_at, tag index for `e`/`p`/`d`). Standard NIP-01 lifecycles: regular kinds stored; replaceable kinds (0, 3, 10000–19999) replaced per `(pubkey, kind)`; parameterized-replaceable (30000–39999) per `(pubkey, kind, d)`; ephemeral (20000–29999) broadcast, never stored; duplicates `OK true` with `duplicate:`. REQ serves the store with real filter SQL (ids/authors/kinds/since/until/limit + tag filters), then EOSE, then live events.
- **Fauna-content translations are materialized, not re-signed per read.** Exposed Fauna posts are translated + signed **once** (at publish/expose, riding the existing outbound-sync signing position) and stored like any other event, deduped via `nostr_event_map`. The relay **never emits an unsigned event** — the current empty-`sig` fallback is deleted, not gated. Toggling `expose_content` off deletes the derived translated events (recreatable — re-derived from the Fauna posts on re-expose).
- **Read/write policy.** Reads are public — anyone may REQ the owner's public events; that is the point of an outbox relay (NIP-65 model). Writes require NIP-42 auth by a local-account pubkey (unchanged), with one exception: **inbox delivery** — unauthenticated senders may EVENT a kind-1059 gift wrap addressed to a local depositor (rate-limited; Phase B below). Gift-wrap reads are recipient-gated: kind-1059 events are served only to the NIP-42-authed `p`-tag recipient (NIP-17). `/nostr/info` (NIP-11) must advertise truthfully: reads open, writes restricted, real limits — never claims the code doesn't honor.
- **Inbox role (NIP-17).** Accepting gift wraps directly makes the nest the user's DM inbox relay — no dependency on external relays for delivery. An accepted wrap is stored verbatim in the event store (to serve back to Nostr clients) **and** feeds the existing S8.9 pipeline: unwrap in flight (licensed by the deposit) → seal through the D2 resolver → `nostr_dms`, plaintext discarded. The user's published NIP-65 relay list (and kind-10050 DM-inbox list) advertises `wss://<domain>/nostr` as their write + DM-inbox relay.
- **At rest.** Public Nostr events are signed, world-readable by construction — the plaintext-by-design readable class, same as public posts; gift wraps are ciphertext by construction, stored opaque; owner-readable DM plaintext never rests (the sealed `nostr_dms` rail is unchanged). Conformance row: [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Per-content-kind conformance.
- **No new configuration surface.** Retention caps, per-event size limits, inbox rate limits are hard-coded Rust constants advertised via NIP-11. The user-facing choices remain exactly the existing page toggles (`nostr-expose-content` etc.); the whole relay stays behind the nsec-deposit bridging gate (§ above).
- **NIP-50 search — placement ratified 2026-07-15: a relay-internal FTS table owned by the event store, deliberately NEITHER of the two existing search backends** ([`../behavior/content-index.md`](../behavior/content-index.md) § Two search backends today). A REQ/COUNT filter's `search` field is served from a dedicated SQLite FTS5 table beside `nostr_events`, maintained in lockstep with the store by schema triggers on `nostr_events` itself — so every current and future store write/delete path (NIP-01 replacement, NIP-09 deletion, NIP-40 sweep, expose-toggle-off, anything later) keeps the index consistent structurally, the same permanent-discipline shape as the kind-1059 recipient gate. Nobody "runs an indexer": the store is the indexer, by construction.
  - **Why neither backend.** The per-user tantivy index (backend 2) is structurally unavailable — the nest holds no index key and must never gain a way to read or query that index (a ratified security boundary, not a preference). `content_fts` (backend 1) is the Fauna Search page's corpus with different keying (`blake3(content_type:natural_id)`), different lifecycle (no NIP-09/40/replacement deletes), and a different consumer (`fauna.search.query`); sharing the table would double-index materialized Fauna-post translations into the Search page (their bodies are already in `content_fts` as public posts) and surface native Nostr events in Fauna search — an unratified product change. The relay search shares backend 1's *mechanism* precedent (SQLite FTS5; the `content_fts` shape) but never its table. Whether Nostr events surface on the Fauna Search page was deliberately left unruled when NIP-50 was built; **ruled in direction 2026-07-22 (user) and RATIFIED the same day:** bridges get a *uniform* per-bridge search policy — no Nostr special case — with a "show in search" toggle and a numeric "limit posts in search" cap per bridge. **Owner: [`../behavior/content-index.md`](../behavior/content-index.md) § Bridge content in the Search corpus** (public-class content indexes into `content_fts` at the bridge's nest-transit point in lockstep; the relay-internal NIP-50 table stays untouched); this doc keeps only this pointer.
  - **Corpus & exposure.** Only the `content` of stored non-gift-wrap events is indexed — kind-1059 rows are excluded at index time (structurally, ahead of the serving gates, which still apply unchanged: `matches_any` + `gift_wrap_visible_to` on every serving verb). The indexed text is world-readable class-1 by construction (owner-only store; slice A's public predicate keeps sealed/gated payloads out entirely), so the FTS table adds no new at-rest exposure class. The sealed `nostr_dms` rail is untouchable by search by construction.
  - **Semantics.** `search` combines AND-wise with the other filter dimensions. On the store-read path (REQ replay, COUNT) the FTS5 verdict is authoritative for the search dimension — the query is sanitized (free-text tokens individually quoted; NIP-50 `word:value` extension tokens stripped-and-ignored, per the NIP's own SHOULD for unsupported extensions). `Filter::matches` carries a documented case-folded token-containment approximation of the same verdict so the live-broadcast path — including ephemeral events, which never reach the store — search-matches too; any divergence between the two matchers is a completeness miss (an event not delivered), never a leak. The relay FTS tokenizer is plain `unicode61` (no porter stemming — unlike `content_fts`, deliberately: stemming is right for product search, wrong for a protocol-literal text match the live path must approximate). Results stay newest-first (NIP-50's relevance ordering is a SHOULD; on a personal outbox corpus recency is the honest order). Limits are the existing hard constants; NIP-11 `supported_nips` gains 50 in the same change that builds it — never before. The `search` string itself is hard-capped (bytes + token count, `fauna_bridge_nostr::nip50`): over-cap searches are refused loudly (NIP-01 `CLOSED`) before any store query, and the shared tokenizer truncates structurally so no serving path — present or future — can be driven to unbounded FTS work by a hostile search string (it arrives on an unauthenticated REQ/COUNT).

- **Wider posture — ruled 2026-07-15 (session-ratified from the existing invariants): the relay STAYS owner-only, and no width change is planned.** Three parts:
  - **Family/multi-user width is already satisfied — no design needed.** "Owner-only" has always meant *all local accounts*: category (1) accepts events authored by any local-account pubkey and category (2) accepts gift wraps to any local depositor, so a household box is every member's outbox + DM inbox today. There is no gap for a "family width" pass to close.
  - **"Followed accounts" width (storing third-party authors' events so the nest doubles as a read/aggregator relay) is REJECTED as target state, not merely deferred.** (a) No driving use case: Fauna apps already receive followed content through the sync worker's inbound ingest (`nostr-inbound-to-feed`) — NIP-01 re-serving would benefit only external Nostr clients using the nest as their read relay, which is not the personal-outbox posture (NIP-65's model needs the owner's relay only as their write/outbox + DM-inbox relay, which is built). (b) It reopens exactly the open-relay abuse surface owner-only exists to remove (unbounded third-party disk keyed to no owned resource; a moderation burden with no operator to carry it). (c) It would be speculative capacity — the `/context` lesson (build per live surface, never speculatively). **Revisit trigger:** a user-named need ("point my everyday Nostr client at my nest as its main read relay") — a product decision for the user to raise, never a session's inference.
  - **Phase-2 proxy interplay: the constraint set is fixed here; the mechanism belongs to the Phase-2 implementation spec** (§ The bridging gate already declares channel-kind/mechanism specifics refutable, and `deployment-home-with-public-relay.md` § Architectural rules owns the seam — home box = bridge head, `nostr_push` pairing capability, the mail-relay pairing + federation channel + `PostLinkHook` auto-provision patterns). The constraints any Phase-2 shape must satisfy: **(i)** the `nsec` never reaches the keyless public box — signing (translation materialization), gift-wrap unwrap, and DM sealing happen only on the head box holding the deposit; **(ii)** the public box may hold and serve only what every relay-store box holds today — class-1 signed public events and opaque kind-1059 wraps — and every serving-box invariant carries unchanged (recipient-gated 1059 serving, the caps, the NIP-50 index-time exclusion); **(iii)** the store schema is location-independent (signed wire JSON + filter columns), so the same `nostr_events` shape serves on both ends with federation legs moving rows, not a second store design; **(iv)** the availability predicate on a keyless *serving* box (today `any_nsec_deposited`, which would 503 it) becomes pairing-derived — "a paired head vouches for this box's serving role" — now specified: `nostr_serving_available` = nsec-deposited ∨ non-expired `nostr_push` pairing, per-request derived (§ The bridging gate → Phase 2; spec ratified 2026-07-22).

*Rollout: A — event store + REQ/EVENT on it + the honesty fixes (stale gate message, empty-sig deletion, NIP-11 truth) — BUILT; B — inbox (gift-wrap acceptance + recipient-gated serving + NIP-65/10050 self-advertisement) — BUILT; C — protocol completeness (NIP-09 deletion, NIP-40 expiration, NIP-45 COUNT, enforced limits) — BUILT; D — NIP-50 search (placement ratified 2026-07-15, bullet above) — BUILT 2026-07-15. Wider posture: ruled 2026-07-15 — stays owner-only (bullet above); no further relay-store slice is planned. Slices tracked internally.*

### The nest as the user's NIP-46 signer (bunker) — ratified 2026-07-19

The § Goal headline's "optional NIP-46 self-signer" leg: the nest **is** the user's bunker. Third-party Nostr apps (Damus, Amethyst, noStrudel, …) sign via the user's own box over NIP-46 (kind-24133 RPC); the deposited nsec never leaves the nest. This is the inverse of the existing `signing_mode=remote` client role (`fauna_bridge_nostr::nip46` — the nest asking an *external* bunker to sign); both roles coexist. The bunker role requires a **deposited** key (custodial modes `generated`/`imported`): a `remote`/`nip07` account has no key on the box to sign with, so those modes never offer it.

- **Connection model (per-app authorization).** Authorizing an app is a user act in the app UI, following the mail-credentials interaction shape ([`../behavior/mail-credentials.md`](../behavior/mail-credentials.md) — the external-third-party-app-authorized-by-a-one-time-revealed-revocable-secret precedent): the user taps *Connect an app* → the nest mints a **pending connection** with a one-time secret (hard-coded TTL, single-use) → the app shows `bunker://<signer-pubkey>?relay=wss://<domain>/nostr&secret=<secret>` as text + copy + QR (the QR is what a phone app scans off a desktop screen) → the app's NIP-46 `connect` presents the secret; the nest consumes it and activates the connection, pinned to the app's client pubkey. Each connection row carries a user-editable label (the bunker flow transports no app name), created / last-used / use-count, expiry, and a revoke control. **Revocation is immediate** — evaluated per request, no cached authority — and unlinking the Nostr account revokes every connection (the key-less cascade). A connection is per-scope in the operative sense — "this app may request signing as this account"; per-method/per-kind narrowing is a declared future refinement, not v1.
- **Why a nest-enforced roster, not `capability_grants` blobs.** The capability-grant primitive ([`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Capability tiering) delivers HPKE-wrapped *content keys* to a holder, sealed so the nest can't read them — enforcement is cryptographic. A bunker connection is the opposite: the app receives **no key material ever**, and the *nest* is the enforcement point (it decides per request whether to sign), so the authorization must be nest-readable — the mail-credentials/devices roster class, not the sealed-grant class. The client-authoritative signed grant log is likewise not load-bearing here: it audits content-read grants against a dishonest box, but a box holding the deposited nsec could sign regardless — the governing trust act is the nsec deposit itself (§ The bridging gate), and this surface inherits it. Audit is the roster's last-used/use-count, served to the owner's client.
- **Signer identity.** A dedicated per-account **bunker signer keypair** (minted on first invite; encrypted at rest via `key_crypto` under its own BLAKE3 context string) — deliberately not the user's pubkey. NIP-46 allows signer-pubkey ≠ user-pubkey (`get_public_key` returns the user pubkey); the dedicated key keeps the connect string from leaking the user's identity and keys request routing + rate limiting.
- **Transport — the nest relay carries its own bunker traffic.** kind 24133 is ephemeral (20000–29999): broadcast, never stored (§ The relay event store lifecycle) — no new at-rest class. Inbound requests arrive as a **second unauthenticated-write carve-out** beside the kind-1059 inbox, same shape and same privacy ordering ([`../architecture/nest/network-exposure.md`](../architecture/nest/network-exposure.md) § Rulings F4): signature-verify first, then membership (the `p` tag names a registered bunker signer pubkey), then a per-signer rate limiter (a hard constant beside the gift-wrap limiter); a request at a non-registered pubkey falls through to the generic auth-required/restricted rejections, indistinguishable from any other non-local event. The request is handled in-process (no external-relay listening — the bunker URL names our own relay) and per ephemeral semantics also broadcast; the response (kind 24133, signed by the signer key, encrypted to the app) rides the live broadcast — the app holds its REQ subscription open, standard NIP-46 operation.
- **Protocol surface (shared Rust).** `fauna_bridge_nostr::nip46` grows the signer side beside the existing client role: request parse / response build, NIP-44 encryption with NIP-04 fallback (answer in the scheme the request used — both already in the crate). Methods v1: `connect`, `get_public_key`, `ping`, `sign_event`, `nip44_encrypt`, `nip44_decrypt`, `nip04_encrypt`, `nip04_decrypt`. No `auth_url` flow — approval is the app UI, never a browser round-trip.
- **Expiry (time-bounded, hard constants, no config surface).** A connection expires after 90 days unused (sliding on last-use — an active app never breaks; an abandoned one lapses); plus a per-account connection cap and the invite-secret TTL, all hard-coded Rust constants.
- **Control plane.** New User-class, caller-scoped WS-RPC kinds `fauna.nostr.bunker.{create_invite,list,revoke,set_label}` (the `fauna.nostr.*` namespace, per live surface — § WS-RPC migration contract), consumed by the Nostr page's new *Connected apps* section on all 7 apps. Deliberately not `fauna.bridges.set_settings` — this is a roster with mint/revoke verbs, not a settings blob.
- **Non-overlap.** Phase-2 `nostr_push` (proxy delegation, `pair::capability`) is a different axis — a *paired box* bridging on the user's behalf; a bunker connection is an *external app* requesting signatures. Neither reuses the other's rows.
- **A principal as a bunker client (TP11, ratified 2026-10-02; nest side built 2026-10-02 — § Implementation status today).** A third-party principal holding `fauna:identity:op:nostr.*` ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Scope grammar → *The second arm*) needs no invite secret: over its principal session it calls **`fauna.nostr.bunker.bind`** with its NIP-46 client pubkey and gets back `bunker://<signer-pubkey>?relay=…` with no `secret` — the bind IS the pinning (one client key per principal; a re-bind re-points), and a real client's `connect` is answered as the ack an already-pinned app gets. The bound client is a row of its own, keyed by principal (`nostr_oracle_clients` — not a `nostr_bunker_apps` row, so the connected-apps roster shows the principal once, under its own row and its own revoke verb), and **every request is authorized against the live `identity.op` grant, re-resolved per request**: the principal row must exist, the grant row for `(owner, the principal's attested holder key)` must be live and name the method's class (`Nip46Method::oracle_class` — `connect`/`ping`/`get_public_key` need none; the legacy NIP-04 pair is never served to a principal), a `sign_event`'s kind must be admitted (`ORACLE_SIGN_EVENT_DENIED_KINDS`: NIP-41 key migration and NIP-46 itself), and the hard-constant ceiling (`fauna_core::identity_op::RateWindow`, two integers on the client row) must admit — so `fauna.capabilities.revoke` or `fauna.principals.revoke` severs at the very next call, with no cached authority anywhere. Each served operation lands as a per-operation audit row on the client (class, detail, time; bounded) beside last-used/use-count — the custodian-held record [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Audience: deployment infrastructure → *The oracle* rules (the audit split), served to the owner's app with the principal's row. The invite-minted roster above keeps working beside it until the connected-apps migration makes every bunker app a principal; unlink, succession leg 2 and the principal's revoke all delete the bound rows.

Data shape: new tables `nostr_bunker_signers` (actor, signer pubkey, encrypted signer privkey, created) and `nostr_bunker_apps` (actor, app pubkey, label, secret hash while pending, status pending/active/revoked, created / last-used / use-count, expiry) — additive, no existing-table change. User-facing vocabulary: "Nostr Connect" / "Connected apps" / "Disconnect" — never "capability"/"grant" (the [`nests.md`](nests.md) vocabulary rule, generalized).

### Key succession and rotation (ratified 2026-08-11)

The whitepaper calls the deposited Nostr key "the honest exception twice over" — in Nostr's model the key *is* the identity, and rotation means a new one. This section owns what that costs at identity succession and what the remedies actually reach. The summary row lives in [`../behavior/succession-aftermath.md`](../behavior/succession-aftermath.md) § Re-key scope; the mechanism is here.

**The custody fact that shapes everything: a seed thief gains *use*, never *possession*.** The deposited nsec rests encrypted under the **nest identity key** (`nostr/key_crypto.rs`) — not under anything seed-derived — and it crosses no wire outbound: the deposit is write-only, no RPC returns it, and NIP-46 signing hands out signatures, not the key. So the seed thief the succession ceremony answers could *act* as the npub during the compromise window (publish through the bridging gate, mint bunker connections for their own apps) but could not *take* the key. That is the exact inverse of the MSEK — which the thief could read raw from the account's mail custody (`fauna.state.mail`), forcing burn-by-construction — and it is why **succession preserves the npub**: nothing the thief did made the key theirs.

**At succession, three legs** (all in or driven from the succession transaction; identity-succession.md's table row summarizes):

1. **The `nostr_accounts` row re-points** to the successor (future-authority class, the standard classification). The relay's event store needs nothing: events are keyed by pubkey, the pubkey is unchanged, and signed history stays attributed as everywhere else.
2. **Every bunker connection is revoked**, wholesale — the MSEK-credential asymmetry verbatim: re-authorizing an app is bounded and visible; a thief-minted connection signs as the user's npub silently, forever. Uniform for theft and loss, no reason carried (a self-declared reason could not be trusted exactly where it matters). The bunker *signer keypair* persists — it never left the box, it identifies the signer rather than the user, and every outstanding connect string dies with its connection anyway.
3. **The aftermath's only adjudication here is the npub check.** The theft-window residue is *visible, not silent*: thief-published events sit in the user's own outbox (removable by the ordinary delete, which emits the kind-5 retraction), and profile/relay-list rewrites re-publish over. The one thing worth a deliberate look is the account row's pubkey — a thief who ran unlink + re-link left a *different* npub linked (their own), and a `generated`-mode original destroyed that way is unrecoverable. The successor confirms the page shows their npub; a wrong or missing one routes into the new-key path below.

**The new-npub path — when the key itself is lost or hostile.** Three ways in: a thief's unlink destroyed a `generated` key; an `imported` key's outside copy (its life before deposit) is believed exposed; an external-signer account (`nip07`/`remote`) was compromised where Fauna never held the key. The remedy is the existing page machinery — link a fresh key (generate or import) — and **NIP-05 rebinding is the continuity Fauna actually controls**: `you@<domain>` re-resolves to the new npub immediately, on the nest's own serving. The honesty that must accompany it: NIP-05 is a hint most clients display, not a binding; followers follow the old *npub*, and no migration statement can help against a hostile-held key — the thief can sign a competing one, so nothing signed by the old key distinguishes owner from thief. Re-follow happens socially, at the price the whitepaper names. This asymmetry — same-npub succession above, new-npub loss here — is exactly why the deposit-custody model (use, never possession) is the load-bearing design choice, and why "don't export the nsec" must stay true: an export affordance would collapse the succession story from *re-point and revoke* to *burn and start over*.

**Leg 2's companion — a designated zap signer is revoked with the bunker connections (ratified 2026-08-11, built in the same commit).** The same sentence that justifies leg 2 decides this one: a zap-signer designation is *standing third-party authority*, and its consequence is not cosmetic — this nest **believes** receipts that signer produces for the user's pubkey, and a believed receipt meeting a tier's asking price *buys* the post ([`../behavior/monetization.md`](../behavior/monetization.md) § Per-post pay-to-unlock). A thief-planted designation would therefore keep minting believed payments after the ceremony, exactly as a thief-minted bunker connection would keep signing — so it dies with them. Designations are rows rather than a status, so revoking is deleting them, and re-designating is the same bounded, visible act re-authorizing an app is. The enumeration is deliberate: everything else actor-keyed (the account, its follows, DMs, federation cursors, the bunker *signer keypair*) is the user's own data or the box's own, and travels with the account rather than dying with the thief's authority.

**Implementation status:** **legs 1 and 2 are BUILT (2026-08-11), including the zap-signer companion above** — `record_succession` re-points `nostr_accounts` and every actor-keyed satellite, and revokes every bunker connection (the rows re-point *and* revoke, so the successor's Connected-apps page shows which apps held standing authority instead of leaving invisible residue on the refused identity). Pinned tier_3 in `bins/fauna-nest/tests/conformance_succession_nostr.rs`, including the beside-control that a nest whose Nostr bridge never ran still performs a succession at all. **Leg 3 — the aftermath npub check — landed on tui 2026-08-17** (the lead app), **then linux, android, and web 2026-08-18, then macOS+iOS 2026-08-25** (windows remains, the usual batched trickle-down): the confirmation stamp — since 2026-09-30 the account-plane kind `fauna.state.nostr-confirmation` (`fauna_core::nostr_confirmation::NostrConfirmation`, one row at `self`, merges as `max`; [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § Implementation status today owns the kind's entry), until then `UserConfig.nostr_npub_confirmed_at` — compared against `fauna.recovery.succession.status`'s `succeeded_at` by the pure `fauna_client_config::nostr_npub_confirm::npub_confirmation_owed` predicate; `npub_confirmation_owed_for` runs the check at Nostr page load over the stamp each host reads through its account-store handle (`AccountStoreHandle::npub_confirmed_at`; no runtime yet reads as not owed), and `AccountStoreHandle::confirm_nostr_npub` records the "yes, that's my npub" write. ### Replying to and quoting a nostr note — the unified interact shape (ratified 2026-09-26, design pass; built 2026-09-28 — § Implementation status today)

**The shape.** A reply to, or a quote of, a nostr note swept into the feed is **an ordinary signed post of the replier** — the same `Reference::Reply`/`Reference::Quote` post every native reply is ([`feed.md`](feed.md) § Interaction bar → *Reply and quote on a bridged post* owns the app-side rule and the one-reply-shape rule; [`../behavior/activitypub.md`](../behavior/activitypub.md) § Reply and quote is the fediverse twin and records why the nest-mint alternative was rejected) — composed by the app, created through `fauna.posts.create`, and **derived** into a nostr event by the nest at create time. Posture 2's own rule, applied: the nest is the user's personal outbox, and the reply is one more post it signs onto the network.

**The door.** `fauna.posts.interact` `{action: reply | quote}` on a post whose source is `nostr` answers the native arm's ack verbatim — `{action, target_post_id, source}`, `counts` read from `content_meta` (the swept note is a local row) — when the caller may publish, else refuses with a `400` naming the remedy: no linked account (existing), no custodial key — the `remote`/`nip07` signing modes cannot sign on the nest (existing, `decrypt_keypair`'s refusal), an explicitly empty relay list (existing — § Errors & edge cases' never-default rule), and, for a `reply`, `publish_replies` switched off (new — the toggle's shipped meaning). `body` is ignored on this door; an older nest's `fauna.posts.unsupported` is the affordance's inline failure and composes nothing.

**The derived event — a reply.** Kind 1, NIP-10 **marked** tags via `nip10::build_reply_tags`: the parent's own root (parsed from the stored parent event's tags — every mapped event rests in the relay store beside its `nostr_event_map` row, the `interact.rs::fetch_stored_event` invariant) as `["e", <root>, "", "root"]` plus `["e", <parent>, "", "reply"]`, or the parent alone as root when it has none; `p` tags for the parent's author and the parent's own `p` tags (NIP-10's thread participants). **A quote:** kind 1 with `nip18::build_quote_tags` (`q` + the quoted author's `p`) and a NIP-21 `nostr:nevent1…` reference (`nip19`) appended to the content — the form every client renders as an embedded note. Content is `Post::body_text()` as for any materialized post; media rides the same URL form.

**Reference resolution — the rule both translators must obey.** The shared translator (`fauna-bridge-nostr::translate`) is DB-free; the nest resolves every reference through `nostr_event_map` and hands the translator resolved ids: outbound, a `Reference` target's local post id → `(nostr_event_id, nostr_pubkey)`; inbound, a swept event's `e`/`q` target → the local post id the map holds (the blake3 of the swept parent's canonical bytes — `inbound_lifecycle::ingest_translated_event`'s id). **An unresolved reference emits no tag and threads nothing — never a synthetic id.** Until 2026-09-28 the translator did the opposite in both directions — outbound the Fauna digest as the `e`/`q` id (no relay has ever seen that id), inbound a `synthetic_cid` from the event id that no local row carries — so no thread crossed the bridge either way; both directions obey the rule since 2026-09-28 (§ Implementation status today).

**When the nest publishes (the create-side arm, and the two toggles given their meaning).** The create-side bridge fan-out (`routes::spawn_post_bridge_fanout` — the hook the AP push and the bluesky write-through already ride) gains a nostr arm for an author with a deposited nsec: a new post is translated, signed once at the deposited-key position, stored as a **derived** event with an outbound `nostr_event_map` row (`materialize_account`'s convention, so the sweep dedupes), and pushed to the account's publish relays (`resolve_relay_urls`, through the sync worker's outbound channel) when **either** the post references a nostr-origin note — the reference is the intent, exactly as a fediverse reply is delivered to its addressee regardless of the follower fan-out — **or** `auto_publish` is on (its shipped label: *Automatically publish Fauna posts to Nostr relays*; read by nothing until this lands). A post carrying `Reference::Reply` is pushed only when `publish_replies` is on (its shipped label: *Publish replies*; likewise unread today). An explicitly empty relay list publishes nowhere — the kind-5 precedent, never the defaults; for a reply/quote the door has already refused, so the arm never meets it. `expose_content` is untouched: it keeps governing the bulk materialization sweep of the account's posts onto the nest's own relay (§ The relay event store), and its toggle-off deletion of derived rows applies to a reply's derived event like any other (external relays keep what was pushed; `fauna.posts.delete` is the retraction, via the kind-5 leg).

**Mirror, thread, delete.** The reply is a local signed post with source `fauna`; it threads under the swept note by the note's local id (`is_reply`, `content_links`), moves that note's `reply_count` through `record_reference_engagements`, and is retracted by `propagate_post_delete`'s kind-5 on `fauna.posts.delete` — all existing.

**Security.** No new inbound surface, no configuration beyond the page's own toggles; signing at the established custodial position; the relay set is the user's; every `e`/`p`/`q` id comes from the map, never from client-supplied hex.

**Pins the build owes**: translator — marked root+reply tags when the parent has a root, root-only when it is the root, the `p` set, the quote's `q` + `p` + `nostr:` content, unresolved → plain, inbound resolved → `Reference::Reply` with the local id; the door's refusals; the create-side arm over a fake outbound channel (reference → sent; `publish_replies` off → not sent; `auto_publish` → sent; neither → not sent; empty relays → not sent); `inbound_lifecycle` — a swept reply to a swept parent threads; and the real-client leg in `bins/fauna-nest/tests/nostr_relay_interop.rs` — rust-nostr reads the derived reply back from the nest's relay and its own parser sees the marked tags.

## Where logic lives

**Resolved 2026-06-08:** all of it is **already shared Rust in `libs/fauna-bridge-nostr`** (see § Architecture) + the nest bridge worker (`bins/fauna-nest/src/nostr/`). The only app glue is the NIP-07 browser-extension boundary call.

- **Key generation, NIP-07 integration, import / unlink.** `fauna-bridge-nostr::signing` + `nostr/key_crypto.rs`; NIP-07 boundary is the lone app-glue call.
- **Relay connections** (WebSocket clients to relay set). `fauna-bridge-nostr::relay_client` + `nostr/sync_worker.rs`.

## Persistence

**Resolved 2026-06-08.** The `nsec` lives **server-side, encrypted-at-rest with the nest identity key** (`nostr/key_crypto.rs::encrypt_nostr_privkey`) — the nest is the custodial signer (decrypts to sign/relay). The **non-custodial alternative** is a **NIP-46 bunker** (`signing_mode`/`nip46_bunker_url`): the key stays in the user's external signer and the nest never holds it. A client only holds `nsec` material when the user pastes one to import (the import path), and in that transient case it must use the platform secure store (Apple Keychain / Linux libsecret / Windows ISecretStore / Web identity slot / Android CredentialStore) per the `onboarding.md` identity-store contract — but the steady-state home is the nest (custodial) or the bunker (external), not per-app storage.

## Errors & edge cases

- `error-message` page-level.
- nsec import format error, NIP-07 not available, relay connection failure, follow not resolvable — surfaced via the bridge error wire in `error-message`; per-variant copy is open (resolved by each surface's lead-app slice).
- **An explicitly-emptied relay list (`nostr-remove-relay` down to zero) is respected, not silently defaulted (ratified 2026-08-11); unreadable/corrupt storage joins it, not the never-configured case (ratified 2026-08-12).** `resolve_relay_urls` (`bins/fauna-nest/src/nostr/relays.rs`) distinguishes three states of the stored **publish** list (`nostr_accounts.relay_list`): `relay_list: null` — never configured — falls back to the 3 built-in default relays; a parseable value, `[]` included, is taken verbatim (the user removed every relay — publish nowhere); and **unparseable/corrupt JSON now also resolves to empty, never to the defaults** — the row was authored, and its unreadable content may have been exactly the `[]` (or pruned list) the user chose, so folding it to the defaults would risk republishing to relays the user deliberately removed (`../architecture/nest/common.md` § Unreadable stored values — the authored-choice direction, cited there as this rule's own exemplar). A publish attempted with zero relays is refused loudly (`fauna.nostr.no_relays_configured` on `nostr.events.publish_signed` and on `fauna.bridges.conversation.send` in a Nostr-leg room, before the Sent row or the outbox item is written; a `400` on the unified interact endpoint's like/repost), never silently routed to the defaults the user just removed — user control over where their content flows, not configuration-file theatre standing in for it. The **read/subscribe** side is a separate resolver: `resolve_relay_hints`, over the follow-scoped `nostr_follows.relay_hints` (which relays to subscribe from for a follow, sourced from the network's own NIP-65 advertisements, not authored on this box) — `null` **and** unparseable both fall back to the defaults there, because hints widen where the nest fetches from, never where the user's own data is published; an empty fold on that side would silently kill the follow's inbound subscription instead.

- **One pubkey, one account (2026-09-27).** A Nostr pubkey is linked to at most one account on a nest, and the account that holds it keeps it: a link in any mode (`generate`/`import`/`remote`/`nip07`) naming a pubkey another account holds is refused `fauna.bridges.identity_in_use`, and the `fauna.federation.sync.nostr_push` auto-provision refuses it `fauna.federation.forbidden` — the holder's row, its deposited nsec included (for a `generated` key, the only copy), is never replaced. The single writer `nostr::db::link_account` enforces it (a plain insert; the table's UNIQUE pubkey conflict is the typed refusal `LinkAccountError::PubkeyHeld`), so every caller is covered at once. What the writer cannot know is whether the caller *holds* the key it names — that is the next bullet.
- **Proof of possession (2026-09-28).** A pubkey held OUTSIDE the nest — the `nip07` and `remote` modes, whose key never rests here — is linked only once its holder has signed this nest's challenge: a NIP-42 kind-22242 AUTH event over a nest-minted nonce, bound to this nest's own relay URL (`fauna_bridge_nostr::nip42::auth_event_template` / `verify_link_proof`; a proof minted for one nest is dead at every other, as NIP-42 intends). The two modes differ only in who signs. **`nip07`:** the app calls `fauna.bridges.link_challenge {bridge_id:"nostr", mode:"nip07"}` (the wire is [`../behavior/bridges.md`](../behavior/bridges.md) § Bluesky bridge → *Link flow*, step 2), hands the reply's `payload` — the unsigned event — to `window.nostr.signEvent`, and sends `fauna.bridges.link {mode:"nip07", params:{pubkey, proof_json}}`, the signed event as NIP-01 JSON (the `nostr.events.publish_signed` carriage); the nest takes the actor's single outstanding challenge (one per actor, the newest superseding, dead after five minutes, spent on first use whether or not the proof verifies) and verifies kind, relay, nonce, signature, and that the signing key is the `pubkey` claimed. **`remote`:** inside the one `link` call the nest completes the NIP-46 handshake against the bunker the user pasted — `connect` with the invite secret, `get_public_key`, then `sign_event` over the same template (`fauna_bridge_nostr::nip46::NostrConnectClient`) — and verifies the answer the same way; the row is written with the pubkey the **signature** proves (the bunker's *user* key, never the signer pubkey the `bunker://` URL spells — signer ≠ user by NIP-46 design), and the stored bunker URL has lost its one-time secret. **Refusals are typed and surfaced:** a `nip07` link with no `proof_json` (an app older than the challenge), a proof over a stale, spent or foreign challenge, a bad signature, or a bunker that refuses `connect`/`get_public_key`/`sign_event` is `fauna.bridges.proof_required` (`error-message`), never a silent link; a relay the nest cannot reach at all is `fauna.bridges.provider_error` (the "relay connection failure" above). Every row written from this date on is therefore proven at the writer's door, so NIP-05 keeps serving every *linked* row unchanged (identity ≠ agency, § The bridging gate); the `nip07`/`remote` rows that could predate this — none exist outside a three-day staging window, the 2026-09-24 baseline reset having ruled no earlier installation existed — are grandfathered rather than migrated or dropped (no column, no data loss). The remaining unproven writer is the federation `nostr_push` auto-provision, a peer-trust question owned by [`../architecture/federation.md`](../architecture/federation.md), not a user link.

- **A private-network relay is refused when the user adds it (2026-09-29).** The store-time half of the outbound relay guard (the rule itself: [`../architecture/nest/network-exposure.md`](../architecture/nest/network-exposure.md) § Rulings F7): a relay URL whose text alone shows no dial may reach it — an IP-literal host that is not globally routable, a `localhost` / `*.localhost` name, or no `ws`/`wss` scheme and host — is refused in the app before any RPC (`fauna_protocol::nostr_relay::relay_url_error`, message `nostr.relays.private_address` shown in `error-message`, no row added), and the nest refuses it again on every user-supplied source — the relay list (`update_settings`), a follow's `extra.relay_hints` (`add_follow`) and a pasted bunker string's `relay=` parameters (the `remote` link, before any dial) — with `invalid_params` naming the rule, storing nothing. A DNS name is never looked up at store time; its addresses stay the dial's to judge.
- **A reply or quote of a swept nostr note is refused at the door, never half-published (design 2026-09-26, § Replying to and quoting a nostr note):** `fauna.posts.interact` `{action: reply | quote}` on a `nostr`-source post answers `400` for no linked account, no custodial key, an explicitly empty relay list, or (a reply) `publish_replies` off — each message naming the Nostr-page remedy — and the app composes nothing; an older nest's `fauna.posts.unsupported` renders the same way. On the ack the app composes the signed post and the nest derives and pushes the event.

## Architectural rules

1. Feature parity across all 7 apps. Web's lead is not the end state.
2. Observer-driven rendering once shared snapshot exists.
3. Indexed list IDs (`nostr-relay-item[i]`, `nostr-remove-relay[i]`, `nostr-follow-item[i]`, `nostr-remove-follow[i]`).
4. NIP-07 boundary call is the only acceptable app-glue branch on this page; everything else is shared Rust.
5. Every relay URL this page collects — the relay list, a pasted bunker string, a follow's relay hints — is dialed under the nest's outbound relay guard; which targets it refuses (private networks included) is ruled in [`../architecture/nest/network-exposure.md`](../architecture/nest/network-exposure.md) § Rulings F7.

## Don't do these

- Don't store nsec in plaintext or in non-secure storage.
- Don't implement relay clients per-app.
- Don't compose published event payloads per-app.
- Don't ship Linux's partial state as the long-term shape; close the gap.
