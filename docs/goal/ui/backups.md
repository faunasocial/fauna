## Goal

The Backups page lets the user pick a folder, see its snapshot history, and create / delete / prune / check snapshots. Folders whose nest place keeps snapshots accumulate point-in-time snapshots with retention rules; the page surfaces those snapshots with their integrity-check status.

## Layout & flow

- Folder selector at top (`backup-folder-selector`) — picks which folder's snapshots are shown.
- Last-backed-up timestamp display.
- Snapshot list (`snapshot-list` + `snapshot-item` indexed) — each row shows snapshot ID, time, status.
- Action row: create snapshot, prune (apply retention), check integrity.
- Per-row: delete (`snapshot-delete-button` indexed, the 30-day soft delete) + immediate-delete (`snapshot-immediate-delete-button` indexed, opens the `immediate-delete-confirm-modal` — never a one-click action; see § User actions).
- Snapshot detail (`snapshot-detail-files`) — file list inside a snapshot when one is selected.
- Per file row: a download button (`snapshot-file-download-button` indexed) — retrieves that one file's bytes from the snapshot (single-file restore, `../behavior/backup-restore.md` § 3: "retrieve an accidentally deleted or overwritten file") and saves them via the platform-native save mechanism: a file-save dialog on desktop (windows/macos/linux), the browser download on web, the system save/share sheet on mobile (ios/android). The user picks the destination — no fixed downloads directory.

## Restore from backup destination

These controls restore a **snapshot the nest holds**, and they keep that meaning (user answer 2026-09-25, option b). The restore after *losing* the nest is a different act with its own gesture, because a rebuilt nest holds no snapshots and the copy lives on the destination: § Restore after losing the nest, below. The flow:

- `restore-source-select` (button/select) — pick which configured backup destination holds the chunks. Disabled when zero destinations are configured.
- `restore-snapshot-select` (button/select) — once a source is chosen, lists `snapshots` rows pulled from that destination, grouped by close-in-time (mail snapshot at T₀ + calendar snapshot within ±60s of T₀ render as one selectable pair). Selecting a row picks both kinds' snapshots.
- `restore-kinds-checkboxes` (component, two checkboxes: `mail`, `calendar`) — defaults to both checked when both have a snapshot; user may uncheck one. The checkbox set is wired to `data.backups.restore_kinds` (a doc-internal binding name — § Element IDs note). ⚠ *Reality check (corrected 2026-07-22 — the 2026-07-10 note below was stale): snapshot **create** and **restore** now cover `mail`/`post`/`conv`/`calendar`/`card` uniformly (`bins/fauna-nest/src/filesync_handlers.rs`; S6.9 replaced the `calendar_not_implemented` stub and added the `card` twin, 2026-07-10, tier_3-proven by S6.11 the next day) — the mail+calendar pairing prose here is no longer backend-gated. Whether to widen this checkbox set to include `card` is a ui.yaml change to make deliberately (rule A), with approval — not made here.*
- `restore-confirm-input` (text_input) — user re-types the snapshot id(s) shown above, comma-separated when restoring both kinds. Same friction bar as the immediate-delete modal: `restore-confirm-button` enables only when the typed text matches.
- `restore-confirm-button` — on click, dispatches one `fauna.filesync.snapshot.restore_message_kind` WS-RPC per kind, sequentially. Disabled when `restore-confirm-input` mismatches OR a restore is already in flight.
- `restore-progress` (text/view) — shows the current step ("waiting for mail chunks", "replaying mail manifest", "waiting for calendar chunks", "replaying calendar manifest", "done — restart the bridge"). Wired to `data.backups.restore_in_progress` + `data.backups.restore_progress_step`.
- `restore-warning` (text; ratified 2026-09-25, rule-A id user-approved) — the completed-with-caveat advisory beside `restore-progress`. The `restore_message_kind` reply carries `config_present`; `false` means the restore **proceeded** but the nest holds no wrapped-MLS blob bundle for the owner's bridge (`bridge_wrapped_mls_blobs`), so the bridge cannot AUTH after restart until that bundle is restored too. When a restore's reply says `false`, the page paints this element with the shared string `backups.restore_warning_config_absent` in the same state change that reaches DONE; when it says `true`, and on any page arrival before a restore, the element is **absent**. The reply is the advisory's only carrier (no read reproduces it), so an app that drops it has destroyed the only copy. The text is the i18n string keyed off the typed bool — **never** the reply's `note`, which is a nest-side diagnostic sentence, not user copy — and it is **never** routed to `error-message` (a completed restore is not a failure; § Errors & edge cases).

The endpoint pulls nothing from a destination: it replays a snapshot whose segments this nest already holds. The progress text reflects whether the local segment chain is complete (`segment_records` mirror rebuilt from on-disk segments) or still being filled in.

**Conversation (`conv`) snapshots are a third message-snapshot kind** alongside `mail` and `calendar`. The shared snapshot-create / snapshot-restore plumbing handles conv generically: `fauna.filesync.snapshot.create_message_kind` and `restore_message_kind` accept `kind = "conv"`, scoped to a `channel_id` (the MLS group) under channel-membership authorization, with no placement layer (`docs/goal/behavior/backup-restore.md` §§ 5–6). However, the *cross-location destination-restore picker above* (`restore-source-select` → `restore-snapshot-select` → the `restore-kind-checkbox` set, currently enumerating `mail` / `calendar`) is the disaster-recovery flow that pulls from a backup destination; conv's cross-location backup + its `__conv/<channel>` backup destination capability **landed** in the conversations-segment rollout's Plan 9 (`../architecture/message-segment-store.md` § Layout — Plan 9's four-gate pure-backup capability + round-trip). (Conv compaction + conv snapshot create/restore against locally-available segments landed in that rollout's Plan 8.) Plan 9 landing is no longer what's blocking `conv` from the checkbox set — conv is backend-ready; widening the checkbox set to include it is a ui.yaml change to make deliberately (rule A), with approval, and that change has simply not been made here yet.

When the nest is lost and rebuilt, the owner's content comes back from the copy a backup destination holds, through the **re-seed ceremony**. [`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § Third destination kind → *Re-seed* owns the ceremony, where it runs, and its post-ceremony duty. ## Restore history

Below the create / prune / check action row, a `restore-history-section` collapsible (default open when ≥1 row exists, collapsed when empty) shows the `restore_history` table for this nest:

- `restore-history-list` (view, indexed by `restore-history-item[i]`) — each row shows completed-at timestamp, kinds restored (`mail` / `calendar` / `mail+calendar` / `conv`), source destination (or "local snapshot" if `source_member_id IS NULL`). A conv restore writes a `restore_history` row under the restoring member (the bearer) just like mail/calendar; it has no divergence banner (no MUA / placement layer).
- `restore-divergence-banner` (text/view, indexed per-row) — only renders on rows where ≥1 `bridge_restore_divergence` row exists for that `snapshot_id`. Banner text: "N MUAs reconnected with newer state". Clicking opens the divergence-details modal.
- `restore-divergence-details-modal` (modal) — lists per-collection × per-MUA divergence entries. Each row: collection name (mailbox or calendar UID-hex slice), MUA id (advisory; `(unknown)` when `mua_id IS NULL`), client modseq, server modseq, "~N writes lost" (= `lost_event_count`). Footer reads "Lost writes cannot be recovered — they died with the source nest. This list is forensic." No action buttons; cancel-only.

Retention follows the snapshot's recovery window (32 days from restore, per `backup-restore.md` § 5 — matches the soft-delete window). Rows older than that age out via the same GC pass that prunes expired `snapshots` rows.

## Restore divergence

The `bridge_restore_divergence` table is written at two seams: (1) at IMAP `SELECT` when a MUA supplies QRESYNC `(last_uid_validity, last_modseq)` and the modseq exceeds the server's `bridge_imap_mailbox_state.highestmodseq` for the target mailbox; (2) at CalDAV `sync-collection REPORT` when the supplied `sync-token` (= modseq) exceeds the calendar's `highestmodseq`. The (γ) detection is forensic — the server's state wins (RFC 7162 §3.2.5.2 / RFC 6578 §3.8 stale-sync-token fallback applies); the row exists so the user can see what they lost.

MUA-id is captured advisory: IMAP from the RFC 2971 `ID` command (today upstream-blocked in go-imap — `mua_id` is `NULL` until that lands); CalDAV from the HTTP `User-Agent` request header. Both are best-effort; the row keeps whatever the protocol offered.

`lost_event_count` is the modseq delta (`client_modseq - server_modseq`), labeled as "~N writes" in the UI. Precise lost-write count is not promised — a single `STORE +FLAGS (\Seen)` on a 50-UID set is one modseq bump but 50 user-visible flag changes (spec § D10).

### Audit-alert surface (ratified 2026-07-24 — IDs user-approved; **first shell landed on linux 2026-07-29**)

The client-side audit loop (`../behavior/backup-restore.md` § Background Tasks owns the loop + the ratified constants `AUDIT_SAMPLE_K` / `AUDIT_MIN_INTERVAL` / `FRESHNESS_SLACK` / `AUDIT_OVERDUE`) verifies each configured destination **directly, trusting neither the source nest nor the destination's self-report**: freshness (the destination's backed-up high-water vs. the client's own locally-synced high-water) and inclusion sampling (K records sampled and opened under the client's seed-derived `NestBackupKey`). The destination set iterated is the client's own pinned destination list (`fauna.state.backup`). Its UI surface here is two elements:

- **`backup-destination-last-audit-time`** — per-status-row sibling of `backup-destination-last-upload-time`: when this destination last **passed** an audit ("never" until the first pass). A healthy page thereby shows positive evidence the audit runs — the no-device-awake case is visible before it becomes overdue.
- **`backup-audit-alert`** — the loud banner at the top of the page, one per failing destination, rendered only while a failure exists (the `restore-divergence-banner` idiom). Failing states: **freshness failure** (high-water lag > `FRESHNESS_SLACK`), **inclusion failure** (a sampled record missing or unopenable, a path the set's own ledger names gone, or a ledger served below the generation this device verified — the loop's owner doc names each), **audit overdue** (> `AUDIT_OVERDUE` since the last successful audit). The banner text is self-describing (destination + reason).

**The client-device arm — what these two elements mean on a custodian row (ratified 2026-08-20, tui leading; refutable downstream).** The loop above audits a destination *directly*, which a **client-device custodian** offers no way to do: it carries no address at all, and inclusion-sampling a sleeping device is structurally impossible ([`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § Custodian contract, question 4 — the owner doc, which ratifies that the custodian self-audits and its check-in feeds the nest projection). A custodian row therefore reads its audit answer from the **status row** (`audit_state` + `last_audit_passed_at`, carried by `fauna.backup.status`) rather than from this client's own pass, and the two elements behave as follows:

- **`backup-destination-last-audit-time`** carries the custodian's own last **passed** self-audit, worded so the provenance is visible ("Self-checked: …" against the owner-side row's "Last checked: …"), via the separate shared door `fauna_core::format::backup_self_audit_label`. Two failures this wording exists to refuse: rendering a self-report in the owner-side words lets it wear the authority of an independent verification, and rendering the owner-side loop's *structural* silence about a custodian ("Last checked: never") reports a device that self-checks every pass as unchecked. Both fail quietly, in the reassuring direction. **A custodian that has never self-audited renders absence** ("Self-checked: not yet") — never a verdict, the same refusal the nest makes when it declines to invent one for a row that has not reported.
- **`backup-audit-alert`** gains a fourth reason, `BackupAuditAlertReason::SelfReported`, raised when the custodian reports `AUDIT_STATE_FAILED`. It is loud because a reported failure is the *only* failure signal that exists for a kind the owner cannot sample, and because withholding it silences the row — and silence here reads as the ordinary sleeping-device case, i.e. the wrong alarm thirty days late. Which reported states are loud stays single-sourced in `fauna_core::format::backup_self_audit_is_alerting`: **absence is quiet** (every custodian shipped before the carrier landed reports nothing, and a fleet-wide false data-loss alarm is the loudest possible way to get this wrong) and **an unrecognised value a newer client wrote is quiet too** (this client cannot know whether it names a failure).
- **`backup-audit-alert`** gains a fifth reason, `BackupAuditAlertReason::SourceRegressed { left_secs }` (ratified 2026-09-29; **built on tui 2026-09-29, on linux, web and android 2026-10-01 (the shared `alert_reasons` projection on the ffi and wasm audit rows) and on macos and ios 2026-10-08 (FaunaKit's one flat `auditAlerts` list takes every entry of each row's `alertReasons`); NOT BUILT on windows**), raised while an accepted source regression's recovery window is open: the owner's own nest went backwards (restored from an older copy of its data directory) and this destination still holds what it lost, for `left_secs` more (rendered as whole days like its siblings). The loop's owner doc names the moment, the record and the window ([`../behavior/backup-restore.md`](../behavior/backup-restore.md) § Background Tasks → *Implementation status (audit loop)*, the accepted-regression bullet); this page owns only the render: **one banner per destination** (its earliest open window, however many ledgers regressed together), on the same indexed element in the same flat pass a shell already makes over `DestinationAuditRecord` — the shell reads `alert_reasons(now)` in place of `alert_reason()` and paints every reason it yields, so which reasons are loud stays the shared answer. It needs no new element: it is **self-expiring** rather than dismissable — it renders while the copy still holds something the nest lacks and stops by itself when nothing is left to recover (the standing rule and its first, fixed-window form are the loop's owner doc's; `left_secs` is absent when no deadline exists, and the label says *until recovered* then — its own string, `backups.backup_audit_alert_source_regressed_until_recovered`, built 2026-10-03) — which is why the notice itself adds no rule-A question. It carries no gesture yet: restoring the copy into a lived-in nest is designed — by record, never by path ([`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Client-device custodian (pull) → *Restore* → *Recovery into the lived-in nest that regressed*; NOT BUILT) — and its gesture's placement, on this banner beside the fifth reason's text or on the destination's `backup-destination-status-row`, with the confirm and result in the re-seed gesture's shape (§ Restore after losing the nest), is the rule-A question asked with its build. Text: `backups.backup_audit_alert_source_regressed`.

⚠ **`state_path` is the shell's own to resolve, and must be actor-scoped** wherever an account switch happens in-process (the same requirement the paragraph below states for the store key): two accounts sharing one path would let one account's observation high-water suppress the other's freshness failures, which fails *quietly*, in the safe-looking direction.

**tui's one structural deviation, and why it is not a divergence to resolve.** linux fires the pass as a *second, independent* round trip so a slow destination never delays the status rows; tui folds it into the **same awaited op** as the page read, because its actuation contract is one awaited op per nav edge or gesture (`apps/tui.md` § The page-module contract) and the agent path awaits that op to completion before its next read — a backgrounded pass would be exactly the fire-and-forget shape that contract exists to prevent, and the driver's next banner read could legitimately see the pre-pass frame. The user-visible behaviour is identical (the 24 h `AUDIT_MIN_INTERVAL` debounce means a repeat visit costs one store read and no round trip); tui bounds the folded pass with a named budget so an unreachable destination cannot hold the nav edge open. A shell choosing either shape is conforming — what is *not* optional is the merge, the observation feed, and which verdicts are loud.

Five things the remaining five shells inherit rather than re-derive:

- **One call.** `fauna_client_backup::audit::run_audit_pass(connector, inclusion, store, destinations, now)` loads the client-local state, audits everything due, merges over what was known, persists, and hands back the full per-destination picture. A shell renders that vector; it implements no merge, no debounce, and no verdict logic.
- **The inclusion arm is shared too, and needs no platform absence.** A shell supplies only `BackupInclusionSource` — a `BlobFetcher` for the destination's public content-addressed routes plus the owner's `FileDownloadKeys` — and shared Rust does the sampling, fetching, opening and verdict. Both fetcher legs already exist (`ForeignPublicChunkFetcher` natively, `WasmPublicChunkFetcher` on web), so **web was reachable and is now built**: the walk is `fauna_core::file_download::download_file_bytes_by_manifest`, which is wasm-clean and already used by web's per-file snapshot download — *not* the native-only `SyncEngine` binding over it. Native apps call `fauna_client_pair::native_backup_inclusion_source(owner_secret)`; web calls its twin `wasm_backup_inclusion_source(owner_secret)` in the same module, differing in exactly one line (the fetcher). **One link in web's chain that is easy to miss and is already in place:** the browser fetches those two routes on a *destination* origin, i.e. cross-origin, so it needs CORS — and both `/api/v1/{chunks,manifests}/{hash}` already carry a route-scoped `Access-Control-Allow-Origin: *` (GET/HEAD, no credentials; `bins/fauna-nest/src/lib.rs`, the S6 cross-nest-member decision), granted for exactly this "a web app on a foreign nest's app origin" case. Nothing about the audit needed a new nest-side allowance.
- **The merge is not optional.** `audit_all` returns only the destinations that *ran*, so a shell rendering a pass's raw outcomes would blank a debounced destination's standing alert on most passes — precisely for the destination that is broken. `merge_outcomes` also drops a removed destination's record, so its banner clears.
- **Which verdicts are loud is shared.** `DestinationAuditRecord::alert_reason()` is the single map (and `AuditVerdict::is_alerting` is defined through it), so no app can drift into alerting on a transient `Unreachable` — the laptop-on-a-plane case the loop keeps quiet by design.
- **The label mapping is written** (`fauna_core::format::backup_last_audit_label` / `backup_audit_alert_label` / `BackupAuditAlertReason`, beside `backup_last_upload_label`) — see `../behavior/value-formatting.md` § Backup destination status labels.

**The freshness comparison needs a client-local observation, and each shell must feed it.** `AuditStateSnapshot::observed_high_water` is the newest message-kind record the client has *seen with its own eyes*, persisted by the same store; the audit compares the destination against **that**, never against a live read of the source nest — a source that answers "nothing new" would otherwise make freshness unfailable forever. A client that never observes anything cannot fail freshness (the documented `None` contract), so a shell that renders the elements but feeds no observation ships a permanently-passing audit. All three built shells feed it from the conversation list's render — the one place the app shows the user what it knows about the nest-originated kinds (`apps/fauna-linux/src/backup_audit.rs`, `apps/fauna-tui/src/backup_audit.rs`, `libs/fauna-wasm/src/backup_audit.rs` driven from web's `routes/conversations/+page.svelte`); each remaining shell picks its own equivalent choke point. Two costs the feed's placement implies, both settled on tui and both binding on web: a paint that is rebuilt per automation read (not only per repaint) needs an in-memory high-water cache or it pays a store read per frame, and that cache must be **keyed by actor** wherever an account switch happens in-process, or one account's observation silently suppresses another's. Web is where the second matters most — it switches accounts with no restart, so the store key itself is actor-scoped too (`fauna_backup_audit_<actor_hex>`).

**⚠ The two audit e2es above do NOT cover the feed, on any shell — that gap has its own test, now on linux, tui and web.** Neither named test can reach a *freshness* verdict (the reason is in both docstrings: `evaluate_freshness` floors the destination's high-water at `added_at`, so a seconds-old enrollment is correctly never stale and shifting `now` moves both sides), and freshness is the only verdict that reads the observation — so a green audit page is not evidence the feed works. All three are mutation-verified (removing the shell's `observe_thread_activity`/observe call leaves the store unwritten and the test fails for exactly that reason). The shared half above the store (`observe_local_record`'s monotonicity) is already tier_1-covered for all of them; macos/ios landed their audit surface 2026-08-01 but still owe this dedicated feed-proof test (their store path is `AccountStateDir.backupAuditStatePath` / `<Application Support>/Fauna/<actor-hex>/backup-audit-state.json`, read directly off disk like linux/tui); **windows landed both 2026-08-02** (store path `AccountStateDir.BackupAuditStatePath` / `<data_dir>\<actor-hex>\backup-audit-state.json`, same read-directly-off-disk shape).

### Snapshot-list shape (RATIFIED 2026-08-05 — the snapshot-shape design pass)

This section owns the snapshot half's page state, data sources, and UI semantics. The protocol it consumes is owned by `../behavior/backup-restore.md` — § 2 (browsing + the additive row lifecycle fields), § 7 (deletion safety), § 8 (retention + the net-new `fauna.filesync.snapshot.prune_set_policy` kind) — and is not restated here. **The protocol half of that is built and served, and so is the client shape below — the shared machine, both boundary faces, tui's lead page, the linux, web and android reconciliation legs (all 2026-08-05), apple's (2026-08-09), and windows' (2026-08-11, the last of the seven)** (§ Implementation status today owns the build ledger; the *Reconciliation ledger* at the end of this section has the per-app detail).

**The shared home is a page machine, `fauna-backups-machine`** — the established page-machine idiom (`fauna-devices-machine` / `fauna-folders-machine` / `fauna-onboarding-machine`: `machine.rs` + `state.rs` + observer + a `nest_api/` seam with a tier_1 fake + renderable snapshot records). tui and linux consume the crate directly; windows/apple/android over one UniFFI face; web through a `fauna-wasm-backups` twin (the `fauna-wasm-folders` shape). It wraps the **custody-wired** `SnapshotsClient` (label custody is a construction input, so the sealed-plane pins carry over — a keyless machine renders sealed rows per the path-sealing consumer-wiring rule, it never bypasses it) plus one owner-scoped `fauna.folders.list` read. Architectural rule 1 binds from the machine's landing: an app renders `backups_snapshot()` and dispatches gestures; it holds no page logic. A deliberate consequence: the per-call boundary-face gaps that accumulated (the FFI dropping `tags`/`structured_errors`/`manifest_hash`+`mtime`, wasm hard-coding `dry_run=false` on prune and `verify_content=false` on check, no `undelete` face on either boundary) stop being load-bearing — the machine crosses each boundary as one face and owns its calls internally.

**The renderable record:**

```rust
backups_snapshot() -> BackupsSnapshot {
    folders: Vec<BackupFolderRow>,    // owner-scoped fauna.folders.list; reserved (__) names excluded; name-ordered
    selected_folder: Option<String>,
    snapshots: Vec<SnapshotRow>,         // the selected set's rows, wire order (newest-first)
    last_backed_up: Option<i64>,         // newest snapshot created_at of the SELECTED set; None renders "never"
    in_progress_op: Option<BackupOp>,    // Create | Delete | ImmediateDelete | Undelete | Prune | Check | Detail | Refresh — single-flight
    check_result: Option<CheckOutcome>,  // session-local, from the last check reply (is_ok + counts + implicated rows)
    prune_preview: Option<PrunePreview>, // dry-run result awaiting execute/cancel (counts, candidates, policy_state)
    detail: Option<SnapshotDetail>,      // opened snapshot's file list; scoped to the selected set (§ User actions → Detail)
    error: Option<LocalizedText>,        // the error-message element; never carries a success (rule 6)
}
BackupFolderRow { name, mode, snapshot_count, last_snapshot_at }   // FolderSummary's cached_* columns
SnapshotRow {
    id, created_at, file_count, total_bytes, device_id, tags,
    state: SnapshotState,     // Active | DeletionPending { execute_after } | SoftDeleted { purge_after }
    integrity: RowIntegrity,  // Unknown | CheckedOk | Implicated — derived from check_result, never nest state
}
```

Per-concern rulings (each reconciles a measured divergence — the 2026-08-05 six-app survey):

- **Selector source is `fauna.folders.list`, owner-scoped, non-reserved sets of every mode.** The richest shipped pattern (apple's) wins over the 4-app `fauna.sync.backup_status` read: `FolderSummary` carries `mode`, `cached_snapshot_count`, and `cached_last_snapshot_at`, which the selector rows render; `backup_status`'s `last_change_at` is the last *file change*, not the last snapshot — the source of web's live wrong-value bug (below). No `mode == "backup"` filter: snapshot create refuses only the reserved destination class, so sync/backup/web sets all belong here. Shared-with-me sets are excluded (`include_shared_with_me` unset — every snapshot verb is owner-scoped).
- **Selection is machine state, page-lifetime, deterministic default.** Default = the first row of the name-ordered list once loaded; selection resets on page mount (5 of 6 apps already behave so; linux's build-once-persist widget and its hard-coded `"default"` fallback are retired). A selected set that disappears falls back to the default. Selection is never persisted at rest. **A pick is the user's gesture, not an op, so the single-flight gate never refuses it:** a pick made while another op is in flight is recorded at once (the picker never snaps back) and loaded when that op ends, and a load never commits the outgoing set's rows under a newer pick. **A refresh asked for while an op is in flight is not dropped either** (ruled 2026-10-06): it is recorded and re-read when that op ends, keeping that op's own verdicts (a re-read stays on the same set, unlike a pick). The op holding the slot may have read the folder list before the change the refresh was asked to pick up, so dropping it left a set added meanwhile out of the picker until the next visit.
- **`last-backed-up` is ONE non-indexed element = the selected set's newest snapshot `created_at`, "never" when it has none.** Derived in the machine from the list reply (the unselected sets' `cached_last_snapshot_at` feeds their selector rows instead). This retires web's `last_change_at` source, windows' hardcoded `"Last: "` + stale-after-mutation refresh, macOS's per-set *indexed* rendering (a ui.yaml scope deviation — the id is non-indexed), and linux's stale-on-empty-set carryover. Label via the shared value-formatting idiom.
- **Row content contract.** A `snapshot-item` visibly renders at least: formatted `created_at`, `file_count`, formatted `total_bytes` — never a raw record dump (windows renders the C# record `ToString()` today, raw epoch + raw bytes, no i18n). A non-`Active` state renders on the row (i18n: deletion-pending with its `execute_after`; soft-deleted with its recoverable-until `purge_after`). Every row exposes its snapshot id to the automation layer (the per-platform attr/value mechanism already pinned by the immediate-delete e2e) — that is a cross-app contract, not a test nicety. Order is the wire's newest-first; apps do not re-sort.
- **Create** (`snapshot-create-button`) → `SnapshotsClient::create_folder(selected, tags: [], device_id)`. **Manual creates are untagged — ratified.** A tag is a retention shield (`keep_tags` + the tagged-never-auto-pruned guarantee), so auto-tagging manual snapshots silently exempts them from retention forever — windows' `["manual"]` tag is the live instance and is dropped. `device_id` = the shell's stable sync device id when it has one (row provenance), else `None`. Single-flight: every mutating control is disabled while `in_progress_op` is `Some` (today: six ad-hoc partial busy flags, linux none at all).
- **Delete** (`snapshot-delete-button[i]`) → confirm (app glue — windows and iOS ship no confirm today and gain one; the other four keep theirs) → `SnapshotsClient::delete`, which queues the 48 h pending action; the row then renders `DeletionPending`. The *cancel* affordance is the pending-actions surface on the Settings page ([`settings.md`](settings.md) § Pending actions — built on all seven apps by 2026-09-07, snapshot delete among the verbs it lists and cancels); this page only shows the state.
- **Soft-deleted rows render their state and their undelete affordance (id user-approved 2026-08-14).** With the lifecycle fields landed, `SoftDeleted` rows are visible (recoverable-until text). `snapshot-undelete-button[i]` renders ONLY on a `SoftDeleted` row and dispatches the machine's undelete gesture (`SnapshotsClient::undelete` over `fauna.filesync.snapshot.undelete`), returning the row to `Active` before its `purge_after`; it is a mutating control, so the single-flight rule disables it while `in_progress_op` is `Some`. The verb's dark-verb declaration is retired: tui leads the render, and the six remaining app legs are ordinary render work over the shared gesture.
- **History — pinned pairs (2026-09-10 → 2026-09-24).** From 2026-09-10 this page named the snapshot that kept a *pinned pair* — two encryptions of one piece of the set's content under one key, left by the pre-2026-09-03 raw writers and readable together without that key — with a per-row marker (`snapshot-pinned-pairs-count[i]`) and a page warning (`backup-pinned-pairs-warning`) whose text followed what the owner could do under the § 7 Layer-1 floor, off the owner's pair audit (`fauna.sync.chunk_pairs.list`). Built on all seven apps by 2026-09-14, it was retired on 2026-09-24 with the audit itself by the compat-remnant sweep: after the baseline reset no such pair rests anywhere, so both elements, their texts and the shared derivation are gone ([`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § Per-chunk file-sync key owns the history). The one shared statement of the floor it introduced, `fauna_protocol::filesync::snapshot_delete_allowed` over `SNAPSHOT_HARD_FLOOR`, stays — the nest's delete path reads it.
- **Prune** (`snapshot-prune-button`) = *apply this set's own resting retention policy* — preview, then execute, both over the new set-policy kind (`backup-restore.md` § 8 owns it). The dry-run preview renders would-prune/remaining counts + the candidate list; execute is offered only from a preview (apple's preview-first flow, blessed as the uniform shape — the one app that had it right). **Observables (IDs user-approved 2026-08-13 — item 14, confirmed live with the user):** the standing preview renders as `snapshot-prune-preview` (present only while one stands), with `snapshot-prune-execute-button` / `snapshot-prune-cancel-button` — tagging the surfaces every app had painted as chrome, so the round trip is e2e-assertable. `policy_state: not_set` renders "no retention policy configured for this set" (the folders page's nest-place editor is where one is set — the folder wizard lost its retention inputs 2026-08-16); `unparseable` surfaces loudly. This retires all four per-app client-supplied policies **and apple's `RetentionEditorSheet`** — retention policy is edited on the folders page's per-folder nest-place editor (the per-set 2-field bounds; the folder wizard until 2026-08-16), never on this page; apple's hand-encoded `keep_*` JSON writer was deleted 2026-08-01, and the rows it left behind are deliberately not migrated (`backup-restore.md` § 8 → *The off-shape at-rest residual*).
- **Check** (`snapshot-check-button`) → `SnapshotsClient::check(selected, verify_content: false)`; **clicking the tagged button runs the check** (apple's sheet requiring a second, untagged "Start check" click violates the actuation contract and is reconciled). The verdict is the shared `is_ok()` predicate — `SnapshotCheckReply::is_ok()` / `FfiSnapshotCheckReply.is_ok` / `SnapshotCheckJs.is_ok`; adopting apps **call** it, never re-code `status == "ok"` (ratified 2026-06-01; apple's `IntegrityCheckSheet` re-derives from error counts today because its `APIClient` drops the field — both reconciled). The machine additionally derives per-row `integrity` from the reply's `structured_errors` (`snapshot_id` implication): `Unknown` until a check runs this session, then `CheckedOk` / `Implicated`. **A completed check with errors is a result, not an error** — it renders in the check-result surface (`snapshot-check-result`, ID user-approved 2026-08-13 — same item-14 confirmation as the prune observables), never in `error-message` (rule 6 below).
- **Detail** (`snapshot-item[i]` click → `snapshot-detail-files`) → `SnapshotsClient::get` (the custody-wired sealed-plane read, § User actions); per-file rows render path + formatted size + `snapshot-file-download-button[i]` (ratified 2026-07-12, unchanged).
- **Two draft fields deliberately dropped.** The draft `SnapshotSummary` sketched per-row *"integrity status"* and *"retention class"* as if they were nest state — neither exists on the wire, and neither should: integrity is a per-set check whose reply implicates rows (derived above), and retention candidacy is only honest as a nest-evaluated dry-run result (the preview), never a standing row column an app would have to re-derive the policy to fill.

## Manage backup destinations

The destination-management surface lives on the Backups page, beneath the per-destination status rows (§ Element IDs). It is the *cross-location* destination list — distinct from the folder wizard's `wizard-mode-backup` (which marks a *local* folder as backup-mode for point-in-time snapshots). A destination is a nest the owner administers, a friend's nest that admitted the owner as a storage-only `backup`-tier user (held-for-friends — ratified 2026-06-14, nest enablement + quota enforcement landed 2026-06-16; it enrolls through this same add dialog and mints no ids of its own, [`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § Held-for-friends enrollment), or this device (the client-device kind, § Kind below).

This section owns the **page surface**; the protocol behind every control below — enroll, edit, remove, the destination kinds and their custodian contract — is owned by [`../behavior/backup-destinations.md`](../behavior/backup-destinations.md), and the `§ State & data shape → …` pointers in these bullets resolve there.

- **Add.** `backup-destination-add-button` opens `backup-destination-add-modal`: the user enters `backup-destination-url-input` (the destination nest's URL) and optionally `backup-destination-name-input` (a friendly label; blank ⇒ the destination's domain). `backup-destination-add-confirm-button` runs the enroll flow (§ State & data shape → Create): resolve identity, verify reachability, record the destination. Errors (unreachable nest, identity refusal) surface in the page `error-message` and the destination is not recorded.
- **Kind (ratified 2026-08-02; IDs user-approved 2026-08-02).** The add dialog branches on `backup-destination-kind-select`: **Another nest** (the URL flow above) or **This device** (the client-custodian flow — no URL; the name defaults to the device name; `backup-destination-capacity-input` takes the user-set cap). A client-device destination can only be added **on the device itself** (§ State & data shape → Third destination kind → Enrollment). Status rows gain a per-row `backup-destination-kind-badge`; client-device rows additionally render `backup-destination-usage` (held bytes vs cap); and the page shows `backup-sole-client-destination-warning` when every configured destination is a client device. The S3 kind joins the same select in its own pass.
- **Status rows.** Once ≥1 destination is configured, each renders a `backup-destination-status-row` with its `display_name`, `backup-destination-last-upload-time`, and `backup-destination-backlog-count`, plus `backup-destination-edit-button` and `backup-destination-remove-button`.
- **Edit.** `backup-destination-edit-button` reopens the dialog to change the display name or URL (§ State & data shape → Edit).
- **Remove.** `backup-destination-remove-button` opens `backup-destination-remove-confirm-modal`, which warns that removing a destination causes its offsite copy to be reclaimed (the coordinator deregisters the manifests). `backup-destination-remove-confirm-button` drops the destination; `backup-destination-remove-cancel-button` closes without effect. Removal is a plain config edit — the coordinator reconciles the deregistration (§ State & data shape → Remove), so it is crash-recoverable. For a **client-device** destination, removal deliberately does NOT delete the local sealed store (3c-ii — it is the owner's only offline copy); the remove dialog additionally offers `backup-destination-remove-reclaim-checkbox` (opt-in: also reclaim this device's copy now — the moment the intent forms).
- **Reclaim this device's copy (IDs user-approved 2026-08-13 — item 14, confirmed live with the user; BUILT on tui + linux 2026-08-21, android + macos + ios 2026-08-22, and windows 2026-08-24 — every app that can hold a custodian store; the one remaining leg is web's declared absence, which hosts no custodian and so can hold no orphaned store; build ledger in [`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § Implementation status today).** After a client-device destination is removed without the opt-in, the device holds a full sealed store with no destination row left to hang a gesture off — so reclaim hangs on `backup-orphaned-store-row` (renders whenever this device holds a sealed store with **no** matching destination row), carrying `backup-destination-reclaim-button` → `backup-reclaim-confirm-modal` (plain confirm, no re-type: reclaiming destroys this device's standalone-restore property — the reason for the modal — but the store is re-buildable from a fresh pull whenever the device re-enrolls) → `backup-reclaim-confirm-button` / `backup-reclaim-cancel-button`. The orphaned row is what keeps reclaim reachable for a store whose destination was already removed — without it the disk space is unrecoverable from the app.

## Where logic lives

- **Snapshot creation, deletion, pruning, integrity check.** Shared Rust, two layers (ratified 2026-08-05): the typed call surface is `libs/fauna-client-snapshots`' `SnapshotsClient` (one method per `fauna.filesync.snapshot.*` kind — already built), and the page orchestration (single-flight, refresh-after-mutation, result projection) is `fauna-backups-machine` (§ Snapshot-list shape — built 2026-08-05 and adopted by all seven apps by 2026-08-11, § Implementation status today). The nest-side halves (creation §§ 1/5, deletion safety § 7, prune § 8, check) are owned by `../behavior/backup-restore.md`.
- **Retention policy evaluation.** **Nest-side, never client-side** (ratified 2026-08-05, grounded in the 2026-08-01 § 8 arming): the per-set 2-field policy the folders page's nest-place editor records (`folders.retention_policy`, written via the shared `fauna-folders-machine` seam) is evaluated only by the nest — automatically on the armed path, and on demand by the set-policy prune kind this page's `snapshot-prune-button` drives (`backup-restore.md` § 8). No app ever computes retention; the preview is the nest's dry-run reply.

## Persistence

Snapshot metadata lives nest-side: `snapshots` (per-snapshot id / parent-snapshot DAG link / `file_count` / `total_bytes` / `max_change_seq` / `created_at`) + `snapshot_files` (per-file-in-snapshot `path` / `manifest_hash` / `size_bytes` / `mtime` / `mode` / `file_type`). Snapshot bodies — manifests and chunks — live in the same content-addressed blob store every fauna-sync folder uses (`blobs/{hash[0:2]}/{hash[2:4]}/{hash}` — `nest/common.md` § Blob Store). The shared-Rust authority for snapshot creation / browse / restore / prune / integrity-check is `libs/fauna-sync-engine` (the client-side restore walk) + `bins/fauna-nest/src/backup/` + `bins/fauna-nest/src/snapshot_routes.rs`; apps surface the snapshot list and the action set via the existing `snapshots` REST surface (`docs/goal/behavior/backup-restore.md` § Technical Flow). Retention policy lives on the per-set policy, the `folders.retention_policy` column (`docs/goal/behavior/backup-restore.md` § Retention Policy), evaluated by the same shared-Rust path on every storage location holding the folder. The cross-location replication shape (own data on other locations vs held-for-friends) is owned by the next section.

**Encryption at rest:** see § Encryption at rest below for the per-blob seal, the per-configuration property (own data on other locations vs held-for-friends), the source-of-seal behavior, and the precise plaintext floor a backup contributes.

## Encryption at rest

A backup is the bytes of a fauna-sync reserved folder replicated to a destination location with the data owner's authorization. The at-rest property is invariant across the content kinds a backup may carry — today: `__drafts`, library-media-attached blobs (per `docs/goal/ui/media.md` § Encryption at rest), the search-index `__index/` (per `docs/goal/behavior/content-index.md`); and the message-segment-store kinds (`__mail` / `__conv` / `__calendar` / `__card` / `__post` — the authoritative kind table with per-kind status is `docs/goal/architecture/message-segment-store.md` § Layout; `conv`'s scope is the `channel_id`, its cross-location backup lands Plan 9). Whichever content kind contributes the bytes, the *backup* seal is the same.

**Seal.** *(Split ratified 2026-07-23, target: nest-originated message-kind segment backups seal under `NestBackupKey` — `owner-key-material.md` § Path A-sibling-0 — by the source nest's coordinator; the rest of this section's `BackupKey` statement covers client-originated kinds, and describes the shipped reality for all kinds until the flip.)* Every backup chunk and manifest is sealed under the **data owner's `BackupKey`** — Path A in `docs/goal/architecture/owner-key-material.md` § Audience: owner only Path A, which owns the seal shape: BLAKE3-derived from the owner's Ed25519 identity seed (deterministic, no rotation, every device of the owner re-derives it independently); backup chunks seal through the **convergent** `chunk_crypto` primitive under the domain-separated `BackupKey::convergent_chunk_root()` and are store-keyed by the **ciphertext** hash (so the destination's F9 chunk route verifies them — FS-BIND FOLLOW-ON A, user-ratified 2026-07-07, incl. the owner-equality-visible-to-destination property recorded there); optional zstd compression layer (prefix-byte signalled). Full pipeline mechanics: `docs/goal/behavior/backup-restore.md` § Blob Storage Pipeline.

This page covers two distinct backup configurations the same mechanism serves — one row each in `docs/goal/architecture/encryption-at-rest.md` § Per-content-kind conformance:

- **Own data on the owner's other locations.** A user with one or more additional storage locations (a second nest, a VPS, a friend's nest the owner trusts as an active replica) replicates their reserved folders to those locations via fauna-sync. The destination is added as a member of each folder; chunks ride the transport sealed under the owner's `BackupKey`. The destination's blob store keeps the encoded bytes opaque on disk unconditionally — `decode_blob` in `bins/fauna-nest/src/backup/mod.rs` runs only on the read path, and only when the local `BackupKey` is configured (it isn't, on a nest, today: `bins/fauna-nest/src/main.rs:736-738` hardcodes `encryption_key = None`). The two destination roles are operational: an *active-replica* destination would reconstitute content locally and serve it; a *pure-backup destination* (an offsite cold-store node) keeps encrypted chunks indefinitely without reconstituting, queried only at restore time. Today every destination behaves as the pure-backup variant — restore is the data owner's client pulling chunks back and decoding locally with its `BackupKey`. The active-replica variant requires an explicit owner-provisioned read capability (sketched internally as a client-driven backup protocol); until that lands, no nest reconstitutes user content from sealed chunks server-side. The cryptographic property — chunks sealed under `BackupKey`, opaque on disk — is uniform.
- **Other user's data this user holds ("held-for-friends").** A user's nest can host another user's reserved-folder data as a backup destination — the *holding* nest is added as a member of the *data owner's* folder. Chunks arrive sealed under the data owner's `BackupKey`, which the holding nest never holds. The holding nest's blob store keeps the encrypted bytes opaque on disk — there is no decrypt path. The holding nest can size-account against the data owner's quota, run blob-store retention, and evict tombstoned chunks per the data owner's retention policy (per `docs/goal/behavior/backup-restore.md` § Retention Policy and § Garbage Collection), but cannot read, modify, compact, or restore the data without the data owner's `BackupKey` (only held on the data owner's devices). Restoring from a held-for-friends backup is the data owner pulling chunks back to one of their own locations and decoding locally. The **enrollment** (how the friend authorizes the data owner to consume their nest's space) is ratified in [`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § State & data shape → *Held-for-friends enrollment*: the holding nest's admin admits the data owner as a storage-only `backup`-tier user via the existing admission lifecycle — no new authorization primitive.
- **Own data on the owner's own device (client custodian — ratified 2026-08-02, unbuilt).** A client-device destination ([`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § State & data shape → Third destination kind) stores the same sealed chunks + manifest mirror a nest destination holds — sealed under the same seed-derived keys, byte-identical by the convergent seal. The floor/ceiling split collapses by design: the custodian is an owner device holding the seed, so the at-rest protection is the platform's device encryption + secure-store unlock gating, and the sealed store is excluded from platform cloud backups. Conformance row: `docs/goal/architecture/encryption-at-rest.md` § Per-content-kind conformance → *Backups (own data on the owner's own device)*.

**Source-of-seal is uniform.** The chunk-encrypt step at the *source* runs on the data owner's **client**, unconditionally — the client is the only `BackupKey` holder (`BackupKey::derive(&ed25519_seed)` from the identity seed, `libs/fauna-core/src/crypto.rs:28-118`). For `__drafts` and library media this is what `libs/fauna-sync-engine/src/engine_lifecycle.rs:209` (`owner_backup_key` derives the key from the identity seed) + `libs/fauna-sync-engine/src/engine.rs:1484` (`upload_file`) already does — derive `BackupKey` client-side, chunk + encrypt, upload ciphertext to the source nest, which stores it opaque (`bins/fauna-nest/src/chunk_routes.rs:103-113` calls `encode_blob` with `encryption_key = None`). For the message-segment-store kinds (when that track lands), the source nest will serve the folder's local plaintext-framed segment bytes (records inside still sealed by the kind's inner seal — MLS read key for mail, `derive_blob_key` for conversations, `derive_post_key` for posts, etc.) over a new endpoint, and the data owner's client will chunk them with its `BackupKey` and upload the chunks. The endpoint shape (`GET /api/v1/segments/{kind}/{actor}/{segment_id}`, returning sealed segment bytes for the client to re-chunk) and the control-plane WS-RPC kinds (`fauna.segments.list`, `fauna.segments.changed`) are specified in the internal design (tracked internally) and ratified in `docs/goal/architecture/segment-backup-protocol.md` § Cross-location backup protocol.

**Plaintext floor (per backup).** BLAKE3 content hash of every chunk and manifest (the routing identifier — `blob_metadata.hash`); ciphertext size (rounded; the standard per-blob floor any fauna-sync upload contributes); per-snapshot summary metadata in `snapshots`; per-file-in-snapshot metadata in `snapshot_files` (the columns enumerated in § Persistence above). The reserved-folder name (e.g., `__drafts`, `__index`, the segment-store `__mail` / `__conv`, and the forthcoming `__calendar` / `__post`) is the floor's authoritative routing pointer for *which* folder this backup belongs to. In the held-for-friends case the data owner's `actor_id` is part of the floor on the holding nest (whose backup is this — for quota accounting, retention policy enforcement, and restore-back-to-owner routing). Manifest *contents* (per-file paths / mtimes / hashes inside the manifest blob) are part of the floor on the data owner's own locations because the owner's nest manages restore over them, but on a held-for-friends destination the manifest blob rides the same chunk pipeline as the chunks it references — the floor stops at the manifest blob's BLAKE3 hash.

**Cross-flow.** `docs/goal/architecture/encryption-at-rest.md` § Cross-flow behavior row 5 ("Backup of any nest's data on any other nest") states the property at the cross-flow level: backups always travel as ciphertext sealed under the data owner's backup key, and the destination nest stores opaque bytes unconditionally. That row applies; this section adds the per-configuration detail (own-other-locations vs held-for-friends) and the source-of-seal detail.

Authority for this section: `docs/goal/architecture/encryption-at-rest.md` § Per-content-kind conformance rows `Backups (own data on the user's other locations)` and `Backups (other user's data this user holds)` + `docs/goal/behavior/backup-restore.md` (snapshot UX, retention policy, deletion safety windows, GC, the blob-storage pipeline) + `docs/goal/architecture/owner-key-material.md` § Audience: owner only Path A (the `BackupKey` derivation + AEAD framing).

## Errors & edge cases

- `error-message` page-level — transport/RPC failures only, **never a success or a completed-with-findings result** (Architectural rule 6; web and android route prune/check successes through it today — reconciliation legs).
- **Snapshot creation while one is in progress** (ratified 2026-08-05): two guards, neither an error. Client-side, the machine is single-flight — `snapshot-create-button` (and every mutating control) is disabled while `in_progress_op` is `Some`. Nest-side, creation is idempotent within a one-second window (`backup-restore.md` § 1) — a race that slips past the disable folds to the existing row. No "already in progress" error state is representable, by design.
- **Integrity-check failure** (ratified 2026-08-05): a completed check reporting `"errors"` is a *result* — rendered in the check-result surface (glue off `check_result`: verdict via the shared `is_ok()`, the counts, and per-row `Implicated` marks), never in `error-message`. Only a check that could not run (transport failure, `backup_unavailable`) is an error.
- **Prune with no candidates** (ratified 2026-08-05): the preview renders "nothing to prune" (zero candidates, `remaining` = the active count) and offers no execute; distinct from `policy_state: not_set` ("no retention policy configured for this set" — set one on the folders page's per-folder nest-place editor, § Element IDs' ⚠ Superseded note above; the shipped `backups.prune_policy_not_set` copy still says "the folder wizard" and is owed the same correction) and from `unparseable` (loud error naming the set). All three states come typed off the set-policy kind's reply; no app infers them.
- **Restore completed without the account's configuration** (ratified 2026-09-25): `config_present == false` on the `restore_message_kind` reply is a *caveat on a success*, rendered in `restore-warning` (§ Restore from backup destination), never in `error-message`. A dedicated id rather than a reuse of `error-message`: the page's one `error-message` is already shared by the destination and snapshot failure paths, and a test could not tell the three apart.

## Architectural rules

1. Observer-driven rendering once shared snapshot exists.
2. Indexed list IDs (`snapshot-item[i]`, `snapshot-delete-button[i]`) — scoped queries only.
3. Retention policy evaluation is shared Rust, not per-app — and since 2026-08-05, **nest-side only** (§ Where logic lives): no app computes retention, and the page never supplies a policy.
4. The immediate-delete modal **never** renders a one-click "Delete immediately" affordance. Both `immediate-delete-confirm-input` and `immediate-delete-acknowledge-input` must contain exact-match text before `immediate-delete-confirm-button` is enabled (`data.backups.immediate_delete_button_enabled`). This is a behavioural invariant, not styling; the shared Rust snapshot computes the enabled flag.
5. **The prune button never carries a client-chosen policy** (ratified 2026-08-05). It applies the set's resting `folders.retention_policy` via the set-policy kind; inventing a `keep_*` policy app-side (the pre-ratification state on all six apps; linux left it 2026-08-05) silently re-maps the bounds family onto the union family, which `backup-restore.md` § 8 forbids.
6. **`error-message` never carries a success** (ratified 2026-08-05). A completed prune/check reports through its own result surface; the error element means something failed. (An e2e that reads `error_text()` as a failure witness depends on this.)

## Don't do these

- Don't compute retention per-app.
- Don't expose snapshot manipulation that bypasses fauna-sync's safety checks.
- Don't expose the immediate-delete API surface without the modal — direct `DELETE …?immediate=true` from a long-press or context menu without typed confirmation defeats the override's safety bar.
