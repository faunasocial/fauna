# Events — target state

Owns: events
Status: ratified — calendar + scheduling model 2026-06-01, implemented across all six apps 2026-06-13 (the encrypted `bridge_caldav_*` backend); week/day contract 2026-06-23; RSVP-for-everyone 2026-06-29. Remaining follow-ons are listed in § Implementation status today.
Authority: ui.yaml (`events` page) owns element IDs + per-page element scope; this doc owns the Events-page UX (views, day-cell interaction, attendee-row presentation, reminders, import/export) and the page's view of the calendar data; defers the wire/store/scheduling protocol (VEVENT + sidecar, sealing, iTIP/iMIP, sync) to [`../behavior/caldav-server.md`](../behavior/caldav-server.md), drafts at-rest to [`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § Drafts Sync + [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md), and shared date/label primitives to their `fauna_core` homes (`caltime`, `ical`).

## Goal

The Events page is a calendar surface: users browse events across one or more named calendars, create calendars and events, RSVP, invite attendees (cross-nest mailbox-less-Fauna delivery resolves automatically from the typed CAL-ADDRESS, no manual nest URL — see § Scheduling / invitations), and switch between agenda / month / week / day views. Server backend is CalDAV-compatible.

## Layout & flow

- Sidebar / top: calendar list (`calendar-item` indexed), `new-calendar-btn`, view-mode controls (component `calendar-view-controls`), prev/next navigation, calendar visibility toggles (`calendar-visibility`).
- Main area: month grid (component `month-grid-view`), week grid (component `week-grid-view`), day timeline (component `day-timeline-view`), or agenda list — per active view mode (week/day contract in **§ Week & day timeline views** below). The month grid follows **Microsoft Outlook's** day-cell interaction (Outlook is the calendar UX reference): each day cell is `events-day-cell-{YYYY-MM-DD}` (indexed) — **single-click** a day → switch to **Day view** for that date (the month→day drill-in); **double-click** an empty day → open **new-event** compose prefilled with that date. Event cards inside a cell keep their own click → `event_detail` (a click on an `event-card` is not a day-cell click).
- Event cards (component `event-card`) clickable → `event_detail`.
- Sub-pages:
  - `create_calendar` — `calendar-name` + `create-calendar`. Creating a calendar **targets it** for the next authoring action, so an event can be added immediately with no extra "pick a calendar" step — but it does **not** force a selection: the no-selection union of all owned calendars stays visible (§ Implementation status today's no-selection union). All apps behave this way: web/windows/apple/android target the just-created / first available calendar when none is explicitly selected (web previously force-*selected* the new calendar, a divergence that existed only because its events list was gated on a selected calendar; the union lift removed that gate, 2026-07-18).
  - `create_event` — `event-summary` + `create-event` + datetime pickers (components `event-form-start-datetime`, `event-form-end-datetime`) + description + location.
  - `event_detail` — view event with same datetime components, plus the
    Reminders affordance (below). The `.ics` import/export controls are NOT
    here: they are calendar-level, beside the calendar list (§ Import / Export).
- RSVP component `rsvp-button-group` — going / interested / decline. **Shown to every viewer, the organizer included** — an organizer MAY RSVP to their own event (ratified 2026-06-29, user decision; matches all 7 apps). The author-only affordances (invite, delete) are separately gated on `organized_by_me` and are NOT part of this visibility rule.

### Week & day timeline views

Week and day views are **Microsoft Outlook-style time grids** (Outlook is the calendar UX reference, as for the month grid). The layout is identical to the richest existing implementation, linux `views/events/week_grid.rs` + `day_grid.rs`:

- **Week (`week-grid-view`, container `calendar-week-grid`)** — 7 day-columns for the week containing the selected date; **week-start follows the app locale** (each app via its platform mechanism — windows `CultureInfo.CurrentCulture.DateTimeFormat.FirstDayOfWeek`, apple `Calendar.current.firstWeekday`, android `WeekFields`, web `Intl`; the two Rust apps share `caltime::locale_week_start` — see § Where logic lives — and every consumer feeds the answer to the `caltime::week_start_date` / `month_grid` / `visible_days` `week_start` param). **The week's range label reads the same value as the grid beside it**, never its own: a label that probes independently can name a different week than the columns underneath it show, which is exactly the bug linux shipped (fixed 2026-08-01). A left **hour gutter** (00:00–23:00); a 24-hour vertical grid at **half-hour** row granularity; a separate **all-day band** (`calendar-allday-band`) above the timed grid carrying per-day all-day-event chips; **timed events as positioned blocks** (top = start, height = duration) with **side-by-side column-packing for overlaps**; a **current-time line** (`calendar-current-time`) on today's column; auto-scroll to **~08:00** on first render.
- **Day (`day-timeline-view`, container `calendar-day-timeline`)** — the *same* day-column renderer, a single full-width column for the selected date.
- **Timed event blocks** carry the indexed id `calendar-event-block` (by event id) and are clickable → `event_detail`. Clicking an **empty time slot** opens the new-event compose prefilled at that date/time (the same Outlook drill-in as the month grid's empty-day double-click).
- **The column's event layout is shared Rust end-to-end** — `fauna_core::caltime::day_column_layout` (all-day/timed classification + timed minute geometry + `find_overlaps` union-find packing, one call per day column; § Where logic lives), so identical events lay out identically across apps: a 22:00→02:00 event renders 22:00 → midnight everywhere (end clamped to 1440, 30-minute floor), never a collapsed or grid-overflowing block. What stays per-app is the rendering shell over the platform's own date library: the date filter (which events fall on this day), the gutter, columns, pixel positioning. Block top/height come from the placement's start/end minutes; left/width from its column index/count.
- **Drag-to-move / drag-edge-resize editing is a deliberate later, fleet-wide slice — not part of these views' first cut** (it is not functional on any app today: linux's drag gesture is wired but its drop handler only logs; web has none).

### Attendee list presentation

On `event_detail`, the `attendee-list` renders **one row per attendee** (the indexed `attendee-item`), **not** a wrapping badge/capsule layout (user decision 2026-06-23). Each row, leading → trailing:

- a **monogram avatar** — the uppercased initial of the display name. Attendees carry no avatar URL (a CalDAV ATTENDEE is just `CN` + email + `PARTSTAT`), so the monogram is generated, never fetched;
- the **display name** (`CN`, falling back to the bare email when the VEVENT carried no `CN`);
- the **email** beneath the name (omitted when the name *is* the email — i.e. no `CN`);
- a **colored RSVP-status indicator** trailing, using the one shared status→color mapping: going = green, interested = yellow, declined = red, waitlisted = orange, invited / unknown = secondary. The status **label text** is single-sourced in shared Rust — `fauna_core::ical::rsvp_status_label(status)` returns a localized `events.rsvp.*` `LocalizedText` each app resolves through its own i18n pipeline (so the label can't drift per-app) — while the **color** is rendered idiomatically per app (a tinted capsule, colored text, a status dot, a CSS class). The color is deliberately *not* lifted: apps already mirror the spec'd vocabulary→color assignment without drift, and a faithful shared tone token would need one variant per color (green/yellow/orange/red/secondary) ≈ re-encoding the status string, so it earns no sharing.

Rationale: the prior shape diverged 2-vs-4 across apps (web + macOS drew wrapping capsule chips; linux / windows / android / iOS drew plain rows, and linux even omitted inline RSVP) with neither a strict superset and this doc silent on it. Rows were chosen because they scale to a long roster (chips wrap into a dense block) and the enriched row is a **strict superset** of every prior app — so unifying onto it loses nothing and gains linux's missing inline RSVP. Apps render the colored RSVP indicator idiomatically (a tinted capsule, colored text, or a colored status dot) — the **status text and color are required**; the monogram + name + email row layout is the shared shape across the 6 GUI apps. tui (no images, and its own idiom treats color as having no terminal equivalent — same reasoning as § Implementation status today) compresses the row to `<name-or-email> (<status>)` on one line — no monogram, no separate email line even when the `CN` differs from the address (`apps/fauna-tui/src/events/detail.rs`); this is a narrower rendering than the row shape above, not an alternative superset of it.

### Reminders

Each event carries at most one reminder. The reminder is expressed as an
offset relative to the event start (e.g. "15 min before", "1 hour before",
"1 day before"). Setting / clearing the reminder lives on the `event_detail`
sub-page.

The control (the shared `event-reminder` component) has two states. With **no
reminder set**: a preset `<select>` (`event-detail-reminder-select`) plus an
explicit **Set** button (`event-detail-reminder-set`) — the chosen preset is
applied *on Set*, never auto-applied on selection, so the cross-app driver
contract is `select(id, "PT1H")` **then** `click(event-detail-reminder-set)`.
With a **reminder set**: the current-offset label
(`event-detail-reminder-current`) plus a **Remove** button
(`event-detail-reminder-remove`). The explicit-Set interaction is uniform across
all apps (an earlier iOS auto-apply-on-`onChange` variant was a deviation,
resolved 2026-06-24).

The three canonical presets the `<DropDown>` offers — `PT15M` / `PT1H` / `P1D`
(the ISO-8601 *values* are the cross-app `select(id, "PT1H")` contract) — map
to their human label in **shared Rust** (`fauna_core::ical::reminder_label`),
returning a `LocalizedText` each app resolves through its own i18n pipeline
(`events.reminder.{min_15,hour_1,day_1}`); a non-preset offset renders verbatim.
The **catalog itself** — the value list in picker order, paired with those
labels — is also shared (`fauna_core::ical::reminder_presets`, 2026-07-16;
FFI `reminder_presets`, wasm `reminderPresets`): every app's picker renders
this one list, never a hand-rolled value array (linux's picker showed users the
raw ISO strings; windows hard-coded English item labels on an otherwise
localized page). Both keep the preset → value/label contract uniform across
apps (the offset→label map was previously hand-rolled per app and had
drifted — see § Implementation status today).

### Refused scheduling changes

Someone who may not change an event on this user's calendar tried to — a `CANCEL` or rewriting `REQUEST` from a co-attendee, a `REPLY` speaking for someone else, a creating `REQUEST` with a spoofed `ORGANIZER` — and the client refused it. The authority for *what* is refused, and for the record itself, is [`../behavior/inbound-scheduling-authority.md`](../behavior/inbound-scheduling-authority.md) § Who may mutate an existing event over the inbound rail → *Surfacing*; this section is only how the Events page presents it.

**Where it sits and when.** A list on the page's main surface (above the calendar content), painted **only when at least one open row exists** — so the page every user sees every day is unchanged by this feature. Each row reads as one sentence: what was tried and to which event (`refused-change-title`), who tried it (`refused-change-author`), why it was refused (`refused-change-reason`), and when it last happened (`refused-change-time`).

**The row's wording is shared Rust, not per-app prose** — `fauna_client_caldav::refused_change_view` composes every line as a `LocalizedText`, because the phrasing of a security notice is precisely the thing that must not drift between apps. An app supplies exactly two things it alone has: a **candidate** handle for the sender where **its own device** can resolve one (`ConversationsManager::handle_for_person`, re-derived at paint, never cached into the record — the same rule the member-review surface follows), and the platform's date formatting. Whether the candidate may name the row is the shared view's decision, never the app's (below). Where no handle names it, the row names a short actor id; where the home nest attested no author at all, it says so.

**Who it names.** The attested sender, never a name read out of the message. A co-attendee's forged `CANCEL` carries the real organizer's `ORGANIZER` line verbatim — that is the attack the rule exists to stop — so a row built from the `.ics` would accuse the victim. **And the sender is named by the pair, not the bare actor id**: a hostile nest can attest any actor id for a channel homed on itself, including the id of a colleague this user really talks to, so a device-known handle names a row attested by a *foreign* nest only when that handle's domain is the attesting nest's host. Otherwise the row reads as that nest's claim: a short actor id *and* the attesting nest's host. The recipient's own nest (blank `author_home_nest_url`) lends any handle. This is a deliberate, fail-closed **approximation** of the rule's `(actor, home nest)` equality: the device holds no home nest per person, only the handle's domain, so a nest served on a host other than its handle domain names even a genuine sender by short id and nest, and never the reverse. **A refusal off the mail rail** holds no actor id at all: it names the email address the delivery door authenticated (the row's `sender_address`, printed as it is — no handle lookup, no nest), and when the copy carried no such stamp it says the sender could not be identified ([`../behavior/inbound-scheduling-authority.md`](../behavior/inbound-scheduling-authority.md) § Who may mutate an existing event over the inbound rail → *The mail rail*).

**Dismiss is the only control.** The ruling gives the list no *apply anyway*: a user cannot adjudicate an authority question the client could not. `refused-change-dismiss` records that the owner has seen the attempts counted so far, so a **later** attempt re-opens the row rather than landing silently on a closed one. Repeat attempts on one event never stack up as rows — they collapse onto one row's count, which is what keeps a flood from becoming the page.

### Import / Export (`.ics`)

The selected calendar exposes calendar-level import/export of RFC 5545 `.ics`. The three controls sit **beside the calendar list** (not on `event_detail`) and are shown **while a calendar is selected** — both act on that calendar (placement user-confirmed 2026-09-25 with the ids):

- **`calendar-import-file`** — the path of the `.ics` file to import: a text input that a native picker beside it fills on every app that has one (web: an `<input type=file accept=".ics">`); tui types the path, a terminal having no picker. The `file-upload` shape Media uses.
- **`calendar-import-button`** — imports the chosen file's events into the selected calendar and **says how many it imported and skipped** (the shared `IcsImportOutcome` counts; a partial import is an expected outcome, not an error). Pressed with **no file chosen it says so on `error-message`** — never a silent no-op (`events.ics_file_required`, or `events.ics_path_required` on tui, the media `file_required`/`file_path_required` split).
- **`calendar-export-button`** — writes the selected calendar as **one `.ics` file into the platform's downloads location** (the `snapshot-file-download-button` precedent — a browser download on web, the downloads directory on a terminal) and **names the file it wrote** (`events.calendar_exported`). A second export never overwrites the first.

Both run through the CalDAV-compatible nest backend; parsing/serialisation of `.ics` is shared Rust (RFC 5545): import is `fauna_client_caldav::CalDavClient::import_ical_events` (parse + seal + PUT each VEVENT; a UID-less VEVENT gets a caller-minted UID), export is `CalDavClient::export_calendar_ics` (read every stored event, re-serialize through `generate_ical_multi` with its roster; a row that will not unseal or parse is left out rather than failing the whole file; an empty calendar exports an empty VCALENDAR). Both are WASM-safe, so all 7 apps call the same two functions (web via `fauna-wasm`, the UniFFI apps via `FfiCaldavClient`). v1 import writes event fields only — rosters on imported events are a follow-up.

Per-app notes (from ui.yaml):
- iOS: `new-calendar-btn` is a standalone toolbar button; all 4 view modes implemented as individual buttons.
- macOS: the left calendar pane (mini-calendar DatePicker + calendar-management controls + calendar list) is an eager `ScrollView`, not a sidebar `List` — the in-process automation driver only registers an element on its `.onAppear`, and a lazy `List` never `.onAppear`s rows below the fold (the management cluster sat below the 280pt DatePicker in a pane shared ~50/50 with the event list). A plain ScrollView renders all children eagerly so every id registers; the cost is the calendar rows lose List inset styling.
- macOS: the **agenda list** below it is an eager `ScrollView { VStack }` for the same reason (2026-07-30) — it was the last lazy `List` in the Events cluster. An appended event could go unrendered indefinitely: measured after a successful create, the agenda listed only the earlier event for a full 30 s while the view model held both, with exactly one `event-card` slot registered and room on screen for a second. Both apple apps now render the agenda eagerly (iOS `CalendarListView` converted 2026-07-16), so a row count on this page is a measure of the data again on both. Same styling cost as the pane above.

## State & data shape

The Events page is a **CalDAV calendar surface** over the encrypted `bridge_caldav_*` store, reached via the `fauna.bridges.*` calendar RPCs (WS-RPC) — the *same* store and RPCs the mail-bridge MDA serves to Apple Calendar, so an appointment created in the Fauna app and one created in Apple Calendar are the same data (Decision B, 2026-06-01). The wire shapes, sealing, the canonical-VEVENT-plus-Fauna-sidecar model, and the scheduling protocol are owned by [`../behavior/caldav-server.md`](../behavior/caldav-server.md); this section is the page's view of that data.

Snapshot:
- `events_snapshot()` → `EventsSnapshot { calendars: Vec<CalendarSummary>, visible_range: DateRange, view_mode: AgendaMonthWeekDay, events: Vec<EventSummary>, selected_event: Option<EventId>, compose: EventComposeState }`.
- `CalendarSummary` — `calendar_id` (the 32-byte client-assigned id; `Personal` is the deterministic `blake3("personal")[:32]`), display name, color, visibility (a client-side display toggle, not stored in the event store).
- `EventSummary` carries id, `calendar_id`, summary, start, end, `rsvp: RsvpState`, attendees (the roster), and **author** (= the iCalendar `ORGANIZER`; the actor id of the creator, used to gate author-only actions — delete / manage attendees).
- `RsvpState` = `Going | Interested | Tentative | Declined | Invited | Waitlisted` (**built 2026-09-01** — `fauna_core::rsvp`, one `uniffi`-derivable enum shared by every app and by `ical`'s `PARTSTAT` projection). **`Interested` is Fauna-native** and projects to `PARTSTAT=TENTATIVE` on the wire; the asymmetric render rule (an attendee shows as *Interested* only when the Fauna sidecar marks them so, else the verbatim `PARTSTAT`) is defined in `caldav-server.md` § Scheduling & invitations → RSVP semantics. ⚠ **This list said `NeedsAction` and omitted `Waitlisted` until the type was actually built.** `Waitlisted` is Fauna-native and real — emitted and parsed as the `X-FAUNA-STATUS=waitlisted` attendee param, which is what distinguishes it from `Invited` given both project to `PARTSTAT=NEEDS-ACTION`. And the variant is `Invited`, not `NeedsAction`, because `invited` is the Fauna status string every app already compares against and the enum's serde repr: a variant named for the iCalendar spelling of the `PARTSTAT` it *projects to*, whose `as_str()` returned something else, would be a permanent trap.
- **What a user may submit is a strictly smaller set** — `RsvpResponse` = `Going | Interested | Declined`, the three answers the RSVP trio offers (`caldav-server.md` § RSVP semantics: tentative and needs-action are **inbound**). It is a separate type rather than a runtime check, so submitting an inbound-only state is unrepresentable at every native call site. This closed a live hole: four call surfaces (`fauna-ffi`, `fauna-wasm`, and two windows sites) documented `tentative` as an accepted RSVP value while `partstat_from_fauna` had no `tentative` arm at all, so submitting it fell through to `NEEDS-ACTION` — the user's answer silently became *hasn't answered*, and the call reported success. The shared `apply_rsvp` now refuses an unrecognized response instead of folding it, which is the one gate every leg passes through (linux and tui call it directly, the native apps over UniFFI, web over wasm). **The FFI signature itself is typed as of android's leg (2026-09-01):** `FfiCaldavClient::rsvp_event`'s `response` parameter is `RsvpResponse`, not a `String` — the one shared export apple, windows and android all call, so the change lands once and android's Kotlin call sites are the first to consume it. Apple and windows own the same signature now too. Apple's Swift call sites are migrated as of its own leg (2026-09-01); windows' C# call sites are migrated as of its own leg (2026-09-01) — `NestRpcClient.CaldavRsvpEventAsync` takes the typed `RsvpResponse`, and both RSVP view models (`EventsViewModel`/`EventDetailViewModel`) parse the button's case-name string into it via `Enum.Parse`, so a wrong value is a compile error, not a hand-rolled string switch.

**The event's two halves:** standard fields (summary/time/location/description/reminder/recurrence/organizer/attendees) live in the canonical sealed **VEVENT**; Fauna-only data (the `interested` refinement, cross-nest attendee nest-url hints) lives in the sealed **`encrypted_fauna_ext` sidecar**. Apps read both; a CalDAV MUA sees only the VEVENT.

## Where logic lives

All of the below is **shared Rust** (a calendar/scheduling crate consuming the `fauna.bridges.*` calendar RPCs, mirroring `fauna-client-conversations`); the per-app shell is just rendering + the native datetime picker.

- **iCalendar serialize/parse (RFC 5545).** The app reads/writes the canonical VEVENT. The **writer** (struct → VEVENT `.ics`) is the existing WASM-safe `fauna_core::ical::generate_ical` (`libs/fauna-core/src/ical.rs`) — **reused, not net-new** (it already emits RFC 5545 TEXT-escaped, 75-octet-folded, CRLF output and carries the `interested↔TENTATIVE` PARTSTAT projection). It must stay WASM-safe so web shares one writer with the native apps (web links `fauna-core`, not `fauna-mail`'s non-WASM `icalendar` feature). The crate-backed **parser** + `expand_recurrence` live in `libs/fauna-mail` (the MDA path); the writer's output is contract-tested against that parser in `libs/fauna-mail/tests/ical_writer_parser_contract.rs`. Remaining net-new: a UniFFI export of the writer so the Go MDA auto-schedule gateway can serialise iMIP (the MDA today only has `mailfauna.ParseICalendar`/`ExpandRecurrence`).
- **Sealing / unsealing.** The client seals the VEVENT (and sidecar) with the actor's `credential_id="default"` capability — the *same* key+AAD scheme the MDA uses, so MDA-written and client-written events are mutually readable (`caldav-server.md` § Authentication). Sealing is shared Rust, not RPC glue.
- **Which calendars the page is scoped to.** The selection rule is shared Rust — `fauna_client_caldav::resolve_calendar_selection` (2026-07-30): a live `calendar-item` selection narrows the page to that one calendar, no selection is the union (§ Layout & flow), and a selection whose calendar has since **vanished** — deleted here, or by a CalDAV MUA against the same `bridge_caldav_*` store — reverts to the union rather than scoping the page to nothing, which would otherwise strand the user on a permanently blank list. Consumed by linux + tui directly, and android via a UniFFI face (`libs/fauna-ffi/src/resolve.rs::resolve_calendar_selection`, 2026-07-30 — `EventsVM.kt:376`'s `scopedEventItems` now resolves the live-vs-vanished check through it before falling back to the union, pinned by `EventsScopeTest.vanishedSelection_fallsBackToUnion`). **windows closed the same way 2026-08-02** — `EventsViewModel.QueryEventItemsAsync` resolves `SelectedCalendar?.Id` against the current `Calendars` ids through the same UniFFI face before branching (the earlier "recovers only incidentally via `ListView` clearing `SelectedItem`" note no longer applies — the resolution is explicit, at read time, and never mutates `SelectedCalendar` itself), pinned by `Load_SelectionNamingDeletedCalendar_FallsBackToUnion` (mutation-verified: fails empty without the resolve call, passes with it). **web closed 2026-08-02** — a new standalone wasm face, `resolveCalendarSelection` (`libs/fauna-wasm/src/rpc.rs`, no `&self`/RPC — mirrors the android UniFFI face's shape, not `WsRpcClient`'s async methods), wrapped by `$lib/wasm.ts` and consumed in `+page.svelte`'s `queryEventItems`: resolves `selectedCalendar?.id` against the current `calendars` list before branching single-vs-union, never mutating `selectedCalendar` itself. **apple (macos + ios) closed 2026-08-02** — one shared FaunaKit edit covers both targets: `EventsVM.swift`'s `queryEventItems()` resolves `selectedCalendar?.id` against the current `calendars` ids through the same UniFFI face before branching single-vs-union, never mutating `selectedCalendar` itself; pinned by `EventsVMPublishOrderingTests.staleSelectionFallsBackToUnion` (mutation-verified against the pre-fix single-query code path, which the pin's `queriedCalendarIds` assertion catches). **No app remains** — all 7 now resolve at read time. Any *additional* per-app display filter composes onto the no-selection arm, never onto a live selection.
- **Which calendars display — the `calendar-visibility` per-calendar show/hide filter (ratified 2026-08-02 as the id's ONE meaning, all 7 apps).** A per-row toggle beside each `calendar-item`: unchecking a calendar drops it from the *displayed* no-selection union; an empty visible-set means "no filter" (the full union), so a fresh page shows everything. It composes onto the no-selection arm only (the rule above) and is client-side display state — never persisted server-side, never a privacy/sharing control (calendar sharing is a separate deferred workstream, `../behavior/caldav-server.md` § Out of scope / follow-on tasks). The predicate lives in shared Rust — `fauna_client_caldav::calendar_is_displayed`, beside `resolve_calendar_selection` (landed 2026-08-02, generalizing linux's proven `CalendarViewState::shows_calendar`: the whole composition — staleness resolve, selection-wins, empty-set-is-union — in one call, with UniFFI + wasm faces; per-app consumption tracked in § Implementation status today).
- **Recurring event expansion (RFC 5545 RRULE).** Shared Rust (`expand_recurrence`); apps render expanded instances only — never per-app recurrence math.
- **View mode + visible range.** The active view (`calendar-view-agenda|month|week|day`) and the dates it shows are shared Rust — `fauna_core::caltime::{CalendarViewMode, pan_step, pan, visible_days}` (2026-07-31). Three parts, and the split between them is deliberate:
  - **The vocabulary.** `CalendarViewMode::as_wire()` (`"agenda"|"month"|"week"|"day"`) is the one spelling every app's toggle, automation surface and persisted view state uses. web's SPA called the agenda view `'list'`; `from_wire` rejects that rather than silently selecting nothing.
  - **The pan policy.** `events-prev-month`/`events-next-month` move **one visible range** per click (§ User actions) — `pan_step` answers `Months(1)` / `Days(7)` / `Days(1)` for month/week/day, and `None` for agenda, whose list is date-unfiltered and so has no range to pan. This is *policy, not Gregorian date math*: a native reads the unit + magnitude from `pan_step` and applies it with its own platform date library (the carve-out below is untouched), while Rust/wasm consumers call `pan` for the whole walk. A month step clamps the day onto a shorter month (Jan 31 → Feb 28), deliberately lossily — the alternative is state a pan control should not carry.
  - **The visible days.** `visible_days` returns the month grid's 42 cells / the week's 7 day-columns / the single day / nothing for agenda, taking the app's locale `week_start` rather than deriving it (§ Week & day timeline views keeps week-start a platform lookup).
- **Date range computation per view mode** (which events fall in this week / month / day) — shared Rust over the expanded instances, via `visible_days` above.
- **CalDAV sync.** Shared Rust: `sync_calendar_since` (RFC 6578) poll + a calendar-change push, against the `fauna.bridges.*` RPCs.
- **Scheduling / invitations (iTIP/iMIP).** Shared Rust constructs the `REQUEST`/`REPLY`/`CANCEL`, routes per attendee (iMIP email via the bridge MTA for email-reachable invitees; the WS-RPC sealed rail for mailbox-less Fauna users, resolved automatically from the CAL-ADDRESS alone — no manual nest URL), and merges inbound replies. Full design (incl. the server-side auto-schedule gateway that lifts this same module into the MDA) in `caldav-server.md` § Scheduling & invitations.
- **RSVP submission + the `interested↔TENTATIVE` projection.** Shared Rust.
- **The refused-change list** (§ Refused scheduling changes). Shared Rust end to end: the record is written by the two `SchedulingSink`s from `SchedulingApplyOutcome::refused_change_record`, rests on the account plane's `fauna.state.refused-scheduling-changes` row (the sinks record into the conversations manager's inbox, which holds what arrives before the account store is up), is read back through `fauna_account_seams::refused_changes::load_open` (which owns the dismissed-row filter, and reads empty until the store is up) and phrased by `fauna_client_caldav::refused_change_view`, which also decides whether the nest that attested the author may lend it a device-known name (§ Refused scheduling changes → *Who it names*). The app contributes the candidate handle its own device can resolve and its date formatting — nothing else.
- **Datetime parsing / formatting.** Shared Rust returns ISO 8601 + LocalizedText display strings; app glue only renders the platform-native picker. Per ui.yaml + `feedback_use_uiyaml_components` memory, datetime pickers are a per-platform component.
- **Pure calendar/date primitives.** The portable Gregorian date math (month-grid generation, day-of-week via Sakamoto, week-start, add-days, days-in-month, prev/next-month), ISO-8601/epoch-millis timestamp parsing, all-day detection, and week/day overlap-layout live in **`fauna_core::caltime`** (WASM-safe, unit-tested; its civil-from-days pair is merge-gated as single-owner, alongside the RFC-5322 **wire** month/weekday vocabulary in `fauna_core::imf_date` — which is deliberately NOT this bullet's localized display vocabulary: a localized `Date:` header is a malformed header. [`../architecture/merge-gates.md`](../architecture/merge-gates.md) § Local-merge gates) — lifted from linux's `views/events/time_utils.rs` 2026-06-19 (priority #2), which now re-exports them. Per-app glue keeps the system clock (`today()`, `now_hm()`) and the localized month/weekday *name* strings (i18n belongs to the client, not `fauna_core`) — those names come from the **i18n catalog**, which carries all 38 of them (`i18n/strings/en.yaml` § `time`, referenced directly by app code rather than through a `LocalizedText` key). **The two Rust apps share one lookup** — `fauna_i18n::time::{month_name, month_name_short, weekday_name, weekday_short}` (2026-08-19): linux's `views/events/time_utils.rs` and tui's `crate::format` had held byte-for-byte identical tables over the *same* constants, so they were one function duplicated rather than per-app glue (priority #4); both now re-export the shared set under their existing call-site paths, unchanged. The **label formatters** that consume those names (`format_month_label`/`format_week_label`/`format_day_label`) deliberately stay app-side: they need `fauna_core::caltime`, and `fauna-i18n` is a dependency-free leaf that much of the workspace links, so hosting them there would push `fauna-core` under `fauna-protocol`/`fauna-client`/`fauna-conversations`. The five non-Rust apps keep resolving names through their own platform catalog as before. **A platform date library's own name formatting is not a substitute** (2026-08-17): it renders a language from inside the binary, where no catalog can localize it, so the app silently stays English when every sibling translates. tui shipped exactly that split for months — its month-grid weekday *header* read the catalog while the three date labels beside it and the two day-column headers under them went through chrono `%B`/`%b`/`%A`/`%a` — and it is now closed and guarded: `apps/fauna-tui/src/format.rs`'s `no_painted_text_takes_a_month_or_weekday_name_from_chrono` walks the whole tui source tree and reds on any chrono name specifier inside a `.format("…")`, while leaving numeric ones (`%Y-%m-%d`) alone. **The locale week-start probe is per-*platform*, not per-app** (amended 2026-08-01): the five apps with a locale-aware platform calendar library read it from there (§ Week & day timeline views lists them), while **linux and tui share `fauna_core::caltime::locale_week_start`** — Rust ships no such library, so "per-app over the platform library" would have meant two copies of the same hand-rolled heuristic, which is priority #4's resolve-don't-match case. It is feature-gated behind `local-clock` (native-only, both apps already opt in) and reads `LC_ALL`/`LC_TIME`/`LANG` in POSIX precedence; the classification it feeds, `caltime::week_start_for_locale`, is pure and stays on the WASM-safe default surface so it is unit-testable without process-global env. That table is a **curated subset of CLDR `weekData/firstDay`**, defaulting to Monday for any unlisted or unparseable region — deliberately an approximation, because the platform libraries the other five use carry the full data and the two Rust apps do not need bit-identical parity with them, only the right answer in the locales we ship to. Widening it is a table row plus a test row. **Exposure is additive and asymmetric by app (decided 2026-06-19 after auditing every app's calendar view):**
  - **Web → WASM (yes).** `fauna-wasm` exposes `monthGrid` / `prevMonth` / `nextMonth` / `weekStartDate` / `addDays` (`libs/fauna-wasm/src/caltime.rs`, 2026-06-19). The SPA hand-rolled the 42-cell month-grid assembly and the week-start snap over the quirky JS `Date` (silent month overflow, mutable, no good platform calendar library), so consuming the shared tested math is a genuine improvement, not just parity. The WASM API uses `caltime`'s 1-based-month + `0 = Mon` conventions; the `$lib/caltime` adapter converts at the seam (`jsMonth + 1` in, `new Date(year, month - 1, day)` out). **Consumed 2026-06-20:** `MiniCalendar.svelte` (month-grid + prev/next-month nav) and the week/day `TimeGrid.svelte` (Monday-start week range via `weekStart`+`addDays`) now ride these — no `new Date(...).getDay()` / `new Date(year, month + 1, 0)` grid math left in either. **`findOverlaps` exposed 2026-06-24** (`libs/fauna-wasm/src/caltime.rs` → `$lib/caltime`), consumed by `TimeGrid.svelte` for the week/day timeline's overlap column-packing — the first web surface to need it, exactly the "until a web surface needs them" revisit anticipated here. **The parity-bearing set joined 2026-07-16** (the same amendment as the natives bullet below): `dayColumnLayout` / `isAllDay` / `normalizeEventDatetimeInput` are exposed via `libs/fauna-wasm/src/caltime.rs` (+ `reminderPresets` beside `reminderLabel`) — the SPA's local `minutesOfDay` end-derivation was one of the drifted interval copies (it dropped the end's date, collapsing midnight-crossing events to 30-minute blocks), so `TimeGrid.svelte` consumes `dayColumnLayout` instead. **The view-mode + visible-range pair joined 2026-08-01**: `pan` and `visibleDays` (same file), minted with their first web consumer per this bullet's own additive rule — the SPA's pan control now moves one anchor by one visible range instead of a month-only second anchor its week/day views never read. `panStep` is deliberately **not** exposed: the § *View mode + visible range* split gives `pan_step` to the natives and `pan` to wasm callers, so a web `panStep` would only invite the walk back into JS `Date` arithmetic. The remaining pure-math primitives (`dayOfWeek` / `daysInMonth` / `isLeap` / `parseDate` / `parseTime`) stay un-exposed until a web surface needs them. (`EventSummary.is_all_day` stays the wire pre-flag; the grid's classification rides the richer shared union rule — see the natives bullet.)
  - **Natives → UniFFI (platform date libraries for Gregorian date math; the parity-bearing set shared).** Apple, Windows, and Android delegate calendar **date math** to mature, locale/timezone-aware platform libraries — Swift `Calendar`/`DateComponents`, .NET `DateTime`, Kotlin `java.time` (`YearMonth`/`TemporalAdjusters`) — never hand-rolled Gregorian arithmetic; forcing them onto a Rust twin of *that* would be net-negative drift (the duplication is conceptual layout, not algorithmic). **That rule is scoped to *date math*; it does not cover classification, geometry derivation, catalogs, or input normalization** — the amendment ratified 2026-07-16, after the original "only `find_overlaps` is shared" phrasing was stretched over exactly those and every one of them drifted per-app into real rendering bugs (a 22:00→02:00 event rendered as a 30-minute block on three apps and a grid-overflowing 1560-minute block on a fourth; a multi-day all-day event crushed android's day column as a 24-hour timed block; the drift sat precisely in the *inputs* to the shared `find_overlaps`, voiding the bit-identical parity that sharing it was for — the revisit clause this bullet always carried, fired). **The shared parity-bearing set, all UniFFI free functions in `libs/fauna-ffi` (`caltime.rs` — self-contained records, no feature gate):**
    - `find_overlaps` (`find_event_overlaps`) — the week/day sub-column overlap packing (shared since 2026-06-23; unchanged).
    - `day_column_layout` — the complete all-day/timed layout for one day column from the events' raw `(dtstart, dtend)` strings: `is_all_day` classification, timed minute geometry (start-minutes; end = minutes from the **start-day** midnight, clamped into `[start + 30, 1440]`, so midnight-crossing events render start → 24:00), and `find_overlaps` packing in one call. An unparseable start degrades to the all-day band (visible), never a silent drop. Which events belong to the day (the date filter) stays on the platform date library.
    - `is_all_day` (`event_is_all_day`) — the one all-day classification rule (union, ratified 2026-07-16): no end, a date-only DTSTART (RFC 5545 `VALUE=DATE` semantics — the DTSTART type governs), or a midnight-to-midnight span of ≥ 1 whole day. `fauna_core::ical::parse_ical`'s `EventSummary.is_all_day` wire flag keeps its narrower `VALUE=DATE`-only derivation (a parser fact, not a layout decision); grid classification uses this richer rule.
    - `normalize_event_datetime_input` — the combined `event-dtstart`/`event-dtend` text-field rule (see § Layout & flow's A2 history): pad a bare `…THH:MM` to `…THH:MM:00`, unify a space-separated date+time to `T`; seconds-bearing / zoned / date-only / unrecognizable input passes through (rejection stays nest-side).
    - `calendar_pan_step` + `calendar_view_mode_wire` + `calendar_view_modes` (**minted 2026-08-22, with android as first consumer** per this bullet's additive rule) — the view-mode vocabulary and the pan *policy* of § *View mode + visible range*. `calendar_pan_step` answers the magnitude only (`Months{1}` / `Days{7}` / `Days{1}` / `None`); the **sign and the walk are the native's**, applied with its own date library, which is exactly the date-math carve-out above. `pan()` is deliberately NOT exposed here — it is the wasm/Rust seam, and a native calling it would move the Gregorian walk off the platform library this bullet exists to keep it on. `CalendarViewMode::from_wire` is likewise unexposed, and — **now that both natives whose view mode was a bare string have landed (apple 2026-08-23, windows 2026-08-24) — it turned out no native needs it at all.** The earlier reading of this sentence was that their legs would mint it; both found instead that nothing on a native ever *parses* a string into a mode. Every write is a literal and every read an equality compare, so adopting the enum **deletes** the strings rather than needing a parser, and the rare string→mode direction (a persisted view, a test fixture) is already covered by `calendar_view_modes()` + `calendar_view_mode_wire()`. Mint `from_wire` only if a consumer appears that genuinely parses untrusted wire input — which is the case `from_wire`'s refusal of web's legacy `"list"` exists for, and which no native has.
    - `reminder_presets` — § Reminders' catalog (value-format-gated FFI, like `reminder_label`).

    Still per-app on the platform date library: the 7 week dates, the week-start *lookup* (per-platform — see the amendment above; the two Rust apps share one probe), month grids, "today"/now, locale names — Gregorian date math proper. Revisit again only if a further native consumer outgrows the platform libraries or needs bit-identical parity.

## Persistence

Calendar definitions and events live nest-side in the **encrypted `bridge_caldav_*` store** (ciphertext-only — nest never holds plaintext), written/read over the `fauna.bridges.*` calendar RPCs (`provision_calendar`, `put_event_ciphertext`, `query_events`, `sync_calendar_since`, `delete_event`). This is the same store the mail-bridge MDA serves to CalDAV MUAs; shape + sealing in [`../behavior/caldav-server.md`](../behavior/caldav-server.md). The legacy plaintext path — the `content` table via the `fauna.events.*` WS-RPC + `/api/events`/`/api/calendars` REST — is **retired** (Decision B); on an encrypted nest it was a disjoint store invisible to CalDAV clients. Client cache: the events snapshot is derived from the synced calendar; durable cross-session caching follows the client's standard snapshot store.

`EventComposeState` (the in-progress event being composed in `event-form` before submission) is a draft and follows the unified draft authority: event-compose drafts rest in the `__drafts` reserved folder per [`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § Drafts Sync — that section is the at-rest authority — at the ratified rail `path = "events"`, sealed under the owner's `BackupKey` (the owner-only key defined in [`../architecture/owner-key-material.md`](../architecture/owner-key-material.md) § Audience: owner only Path A), regardless of nest mode. **The serialised shape is settled** (2026-08-17; it was previously deferred here to "the shared-Rust events crate's design", which now exists as `fauna_client_caldav::drafts::EventDrafts`), on four rules — the first three carried over verbatim in intent from the posts rail ([`feed.md`](feed.md) § Persistence), the fourth this rail's own:

- **One slot, no draft ids.** The composer is a single modal surface (the `event-form` component), so the rail's blob is one record — unlike the conversations rail, which carries a per-thread map plus a new-thread slot. Nothing assigns or needs a draft id.
- **Only user-authored input rests, enumerated not embedded.** The five `event-form` inputs survive: `summary`, `dtstart`, `dtend`, `description`, `location`. The at-rest record *enumerates* its fields rather than embedding a compose struct, so a field added to some app's event form later cannot silently become at-rest data — the author has to choose.
- **The calendar is NOT at rest.** `ui.yaml`'s `event-form` carries no calendar picker: the target calendar is resolved at submit from the page's selected calendar (first-calendar fallback when none is selected). A page's selected calendar is per-device view state, exactly as [`feed.md`](feed.md) § Persistence rules for the selected feed — and a persisted calendar id could name a calendar the restoring device does not have.
- **Datetimes rest raw as typed.** `dtstart`/`dtend` persist the composer's text as the user left it, mid-edit and possibly not yet well-formed; normalization to the wire's `…THH:MM:SS` shape stays at submit (§ Where logic lives, the A2 rule). A rail that normalized on save would rewrite half-typed input under the cursor.

The blob is byte-stable for equal logical state, which is what lets `DraftsSync` skip re-uploading an unchanged draft to the user's other devices.

**Opening the compose resumes the draft; a day-cell gesture starts fresh.** The event compose is *modal*, unlike the always-present feed composer, so the rail is only meaningful if the openers agree on which one resumes. The New Event opener **restores** the persisted draft into the form — that is what draft persistence is for, and an opener that cleared it would leave the rail inert. The month/week day-cell double-click **starts a new event** at the clicked date, per § Layout & flow's `create_event` bullet, which defines that gesture as *"start a new event here"*; it therefore clears the buffers and applies its date prefill. A successful create, or an explicit discard, clears the rail.

## Errors & edge cases

- `error-message` page-level.
- Empty calendars / empty range → empty-state snapshot variants (not errors).
- **RSVP / invite delivery failure.** RSVP and invitations are best-effort transport (iMIP email or WS-RPC): a dispatch failure surfaces on `error-message` but does not block the local write — the event/roster persists and the invite is retried (the shared scheduling crate owns retry, reusing the mail send path's retry semantics). An invitee whose typed CAL-ADDRESS resolves to neither a Fauna nest nor a deliverable address is a per-attendee failure shown against that attendee, not a whole-event error.
- **Stale sync token** → shared Rust full-resyncs transparently (`caldav-server.md` § Stale sync-token handling); no user-visible error.

## Architectural rules

1. Observer-driven rendering.
2. Recurrence expansion is shared Rust; apps render expanded instances only.
3. Datetime pickers are the only per-platform component on this page; logic and validation are still shared. ui.yaml's `event-form-start-datetime` / `end-datetime` components document the per-app variants — do not flatten their child IDs into the page.
4. Indexed list IDs (`calendar-item[i]`, `event-card[i]`).
5. CalDAV is the wire format; the client never invents its own event encoding.

## Don't do these

- Don't expand recurrences per-app.
- Don't add platform-specific datetime ID variants outside the component.
