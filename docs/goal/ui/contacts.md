## Goal

The Contacts page lists the user's accepted contacts, surfaces pending knocks (incoming contact requests), and lets the user search for new contacts by handle and add them. Confirming an accepted contact and accepting/blocking a knock are first-class actions on this page.

## Relationship to Profile

Contacts is the **list** half of a list→detail pair; the **detail** half is the per-user **Profile** (`profile.md`, the canonical per-user surface). A contact row renders via the shared **`user-header`** component and **links into** that user's Profile, where the per-user actions (DM, request-contact, follow/subscribe, block) and identity detail live. This page **owns the contact-edge lifecycle** — knocks, accept / block / dismiss, confirm, the `ContactStatus` edge persisted nest-side — and the Profile *calls* that same shared logic to surface those actions on its detail view (it does not fork the edge model). Subscription / follow is **not** a contacts concern (it is an asymmetric per-user action on the Profile); contacts may show a subscription-status badge as a convenience cross-link only. See `profile.md` § Relationship to Contacts and `monetization.md` § Why profile, not contacts.

## Layout & flow

Three regions:

1. **Knock list** (`knock-card` indexed) — pending incoming knocks. Per-row: sender ID, dismiss, accept (`contacts-accept-button`), block (`contacts-block-button`).
2. **Contacts list** (component `contact-list-item`) — accepted contacts. Per-row: name, status badge, confirm action for accepted ones (**conditional render, ratified by the user IN-PERSON 2026-08-15**: `contact-confirm` appears only on a `status='accepted'` row — the one the transition applies to; confirmed/blocked rows carry no confirm affordance. "Pending" in this doc's earlier wording meant the not-yet-confirmed *accepted* edge, not `ContactStatus::Pending`, which is a knock — § Persistence), plus `contact-unattested-mark` when that contact is also a person carrying an open post-succession review item — a **badge only**, with no verdict affordance, because the Keep/Remove decision lives on the group member chip where removal already exists ([`../behavior/succession-propagation.md`](../behavior/succession-propagation.md) § Propagation → *MLS groups* owns the ruling and the reason a contacts-only flag would hide the population the surface exists for). A **roster filter** (`contacts-search-field`) above the list narrows the *already-loaded* accepted contacts as the user types — a purely local, case-insensitive substring filter, **not** a nest query (see § Where logic lives → Contact roster filter). It hides non-matching `contact-row`s in place; it does not produce a `contact-actor-id-result`.
3. **Add-contact panel** (component `add-contact-form`) — look up a *new* contact by `64-hex actor-id | user@domain` via `contact-actor-id-field` → `contact-actor-id-lookup`, result in `contact-actor-id-result`, add to contacts (`contacts-add-button`), error display (`contact-find-error`). This is the **federated discovery** path (§ Where logic lives → Contact lookup by handle), distinct from region 2's local roster filter. **Button copy ratified (user decision, 2026-08-25):** `contact-actor-id-lookup` reads **"Find"** and `contacts-add-button` reads **"Knock"** on all 7 apps — before this, the resolve step split "Find" (android/ios/macos/web) vs "Look Up" (linux/windows/tui) and the send step split "Add" (windows/android/ios/macos/web) vs "Knock" (linux/tui); "Knock" won over "Add" specifically because it is the term the rest of the product already uses for this action (the `fauna.inbox.send` wire sentinel, `KnockItem`, the recipient's own knock-list section) — a sender who clicked "Add" had no signal that what they'd just sent would land the recipient in a screen literally titled Knocks.

> **ID note:** `contacts-search-field` is the **roster filter** (region 2), *not* the add-contact search — the field name is misleading. The federated lookup's input is `contact-actor-id-field` (in `add-contact-form`); its result is `contact-actor-id-result`. That result used to also carry a second id, `contacts-search-result` (web bound the outer wrapper to it; several apps had it on the result container while `contact-actor-id-result` sat on the actor-id text leaf) — **consolidated into the single `contact-actor-id-result` id 2026-07-12** (user-approved 2026-07-10), landed on the leaf holding the actor-id value across all 6 apps so `contact-actor-id-result`'s existing exact-text assertion (`test_contacts_knock_send_web.py`) keeps working unchanged. `contacts-search-result` no longer exists anywhere in ui.yaml or client code.

**Address Book segment (slice 4b — data layer + bindings + UI DONE on ALL SEVEN apps; tui landed 2026-07-29, the last one, with its tier_3 e2e green).** Per a **2026-07-07 user nav decision** (`carddav-server.md` § Independent enablement), the Contacts page carries a top-level **segment toggle** (`Contacts | Address Book`): the **Contacts** view is the three regions above (the social contact-edge graph); the **Address Book** view lists the user's CardDAV address books + vCards (`FN` / `TEL` / `EMAIL` / `ADR` / `ORG` / …), a **separate store** from the social graph (§ Persistence; `carddav-server.md` § What a CardDAV address book *is*), decrypted locally (zero-access). It mirrors the Events page's master-detail: an address-book picker (mirror `calendar-item`) + a card list (mirror `event-card`) + a card-detail pane (mirror `event_detail`). Data layer is shared-Rust `libs/fauna-client-carddav` (`CardDavClient::{list_addressbooks_decoded, query_cards_decoded}` + the WASM-safe `vcard` reader + `unseal_card_body`); the `ui.yaml` element design is landed (§ Implementation status today; tracked internally).

## State & data shape

The **client snapshot shape** is still proposed (resolve before building the client viewmodel); the
**nest-side enrichment** of each contact row is **implemented** (2026-06-25, see below).

Target shape (proposed):
- `contacts_snapshot()` → `ContactsSnapshot { contacts: Vec<ContactSummary>, knocks: Vec<KnockSummary>, search: SearchState, find_error: Option<LocalizedText> }`.
- `ContactSummary` carries actor_id, **handle, domain**, status (pending/accepted/confirmed/blocked — the full edge-status set, § Persistence).
- `SearchState` carries query, in-flight flag, results.

**`ContactSummary` must carry `handle` + `domain`** for the roster filter (§ Where logic lives → Contact roster filter) to match them uniformly. As of 2026-06-25 this **is true at the source**: `fauna.contacts.list` returns `ContactItem { peer_id, status, accepted_at, created_at, handle, domain }` (`bins/fauna-nest/src/contacts_handlers.rs` `contacts_list_handler`). `handle`/`domain` are joined **nest-side** from the peer's `Profile`: `handle` from the local `users` table via a `LEFT JOIN` in `CacheDb::list_contacts_full` (the nest's `contacts` edge table holds none — § Persistence), and `domain` from this nest's handle domain (`AppState::handle_domain()`, `bins/fauna-nest/src/state.rs:413` — the live `identity_domain` set at claim, falling back to `registration.handle_domain` pre-claim and then the node config domain; the same source `resolve_handle_core` reports for a handle, so a domainless-then-claimed box labels a local peer with the claimed domain, not a stale pre-claim seed). They are populated for **local** peers (a registered user with a handle set); a **federated** peer gets `None` for both, because the nest holds **no cached federated Profile** and a per-row federated fetch is the wrong default on this read (the knock/DM-arrival hot path also reads the contacts table — § Persistence). Both fields are **additive** (`#[serde(default, skip_serializing_if = "Option::is_none")]`, absorbed by `extra` on older peers — `architecture/version-compatibility.md`), so no client breaks within the major version. **web**, **linux**, and **tui** receive them automatically (web via the wasm `to_js(&reply.contacts)`; linux and tui via direct `ContactItem` decode — tui imports `fauna_protocol::contacts::ContactItem` straight, `apps/fauna-tui/src/contacts.rs`); **android / apple / windows** receive them too, since the `FfiContactItem` UniFFI mirror was extended with the two fields (2026-06-25/26 — § Implementation status today). All seven apps' contact rows now carry handle + domain.

## Where logic lives

- **Contact lookup by handle.** Shared Rust — `fauna_core::resolve::classify_recipient` (parse `64-hex actor-id | user@domain`) then the anonymous `fauna.nest.resolve` / `fauna.actor.by_handle` discovery kinds, consumed by native apps via the `libs/fauna-ffi/src/resolve.rs` UniFFI seam (`classify_recipient` / `resolve_nest` / `resolve_handle`); the same resolution DM-compose recipient entry uses. The deprecated `/api/v1/{resolve-node,actor/by-handle}` HTTP twins are deleted (`api-layers.md` discovery row). Native consumers: android `core/ResolveService.kt`, apple `APIClient.resolveRecipient`, **windows `ContactsViewModel.LookUpRecipientAsync`** (2026-07-02); linux and tui read `fauna_core::resolve` directly (tui: `apps/fauna-tui/src/contacts.rs` `Action::Lookup` → `classify_recipient`, same-nest handle resolve over `fauna.actor.by_handle`). **All seven apps now have the federated-discovery path.** Windows was the lone app without it until 2026-07-02: its `contact-actor-id-field` used to accept only a 64-hex actor-id (`ContactsPage.AddContactButton_Click` gated on `length == 64` then sent a knock, with no `user@domain` handle resolve). It now classifies via `FaunaFfiMethods.ClassifyRecipient` and, on the handle branch, resolves through `FaunaFfiMethods.ResolveNest(HomeUrl, domain)` → `ResolveHandle(nodeUrl, user)` — the home nest URL being `NestRpcClient.HomeUrl` (the same own-home-nest URL android's `ApiClient.nodeUrl` / linux's `FaunaClient::node_url` feed `resolve_nest`) — then adds the RESOLVED actor id. The multi-domain **display** follow-on (echoing the typed secondary domain) is **built (2026-07-02, tracked internally)**: `LookUpRecipientAsync` threads the classified `@domain` into `FaunaFfiMethods.ResolveHandle(nodeUrl, user, domain)`, so a typed `bob@domain2` resolves with the secondary domain echoed and windows displays `bob@domain2` (parity with web/linux/android; `mail-multidomain.md` § Multi-domain handles, § Implementation status today).
- **Knock accept / block / dismiss.** Shared Rust — `fauna.knocks.{accept,block,dismiss}` (the `fauna-client-contacts::ContactsClient` knocks methods).
- **Knock sender display** (`knock-sender`). Shared Rust — the element reads `fauna_core::format::short_id(sender)` ([`../behavior/value-formatting.md`](../behavior/value-formatting.md) § Short id), and the knock's `summary` is a line of its own beside it, never this element's text. A knock row carries no handle (wire shape: [`../architecture/core-client-kind-catalog.md`](../architecture/core-client-kind-catalog.md) § Contacts & Knocks), so the sender's actor id is the row's only identity and the short id is its display; the full id rides only on the row's accept / block / dismiss actions. Consumed through the wasm `shortId` (web), the UniFFI `short_id` (windows `KnockInfo.SenderLabel`, android, apple), and `fauna_core::format` directly (linux, tui) — **all seven apps as of 2026-09-14**, when tui (which showed the full hex) and linux (which showed the summary) converged. A knock with an empty summary shows linux's fixed "wants to connect" line in its place. Cross-app witness: `test_knock_sender_display.py`.
- **Contact confirm.** Shared Rust — `fauna.contacts.confirm` promotes an `accepted` edge to `confirmed` (the `contact-confirm` button, a deliberate user action). The **same promotion also happens automatically** on a live inbox arrival: `deliver_to_inbox`'s `promote_contact` flag (`bins/fauna-nest/src/routes.rs:1303-1307`) calls the identical `promote_to_confirmed` (idempotent, guarded on `status = 'accepted'` same as the button) whenever a message actually reaches the recipient's inbox from that sender — "a message was exchanged" is the other route to `confirmed`, matching the `ContactStatus::Confirmed` doc comment (`libs/fauna-core/src/data.rs`). It is deliberately **not** applied when a knock's held payload is later released (`deliver_held_knock_payload`), since that arrival predates acceptance and would confirm every accepted knock on the spot, defeating the accepted-contact TTL below.
- **Unblock.** Shared Rust — `fauna.knocks.unblock(peer_id)` **clears the contact edge** (`ContactStatus` → `None`). A block is a *hard reset* of the relationship, so unblock returns the edge to the no-relationship state, **not** any pre-block status: the edge stores no prior status (`block_contact` overwrites `status` to `blocked` with no history — § Persistence), so there is nothing to revert to, and re-establishing contact afterward goes through a fresh knock (knock-send: tracked internally). The nest write is **guarded** to act only on a `blocked` edge (a no-op when `accepted`/`confirmed`/`pending`/absent), so a stale client snapshot can never clear a live relationship. Semantics decided 2026-06-22 — option (a) *clear-the-edge*, the no-new-state default (tracked internally); option (b) *revert-to-prior* was rejected because it would require new at-rest state the edge does not carry. Surfaced as the `profile-block-button` Block⇄Unblock toggle (`profile.md`), not a Contacts-page element. The toggle's **viewmodel** (its `contact_status`-driven state + label, distinct from the edge transition above) is likewise Shared Rust as of 2026-06-25: `fauna_core::format::contact_row_blocks_actor(peer_id, status, target_actor_id) -> bool` (a `blocked` row whose `peer_id` matches the target — case-insensitive hex — that apps fold over `fauna.contacts.list` with `.any`/`.some` to derive `is_blocked`) and `fauna_core::format::contact_toggle_block_label(is_blocked) -> LocalizedText` (`is_blocked` → `profile.unblock`/`profile.block`), consumed by natives via the `libs/fauna-ffi` `value_format` UniFFI face and by web via `libs/fauna-wasm` `contactRowBlocksActor`/`contactToggleBlockLabel` twins — the same recipe as `contact_status_label`. The predicate resolves the lone divergence (windows compared the actor-id case-insensitively, the other four case-sensitively); the button **style** (linux's `destructive-action` on "Block") stays an idiomatic per-app render. Consumed by **web + linux (2026-06-25)** + **windows + android + apple (2026-06-26)** (windows: `ProfileViewModel.RefreshBlockStateAsync` → `ContactRowBlocksActor`, `ProfilePage.ApplyBlockLabel` → `ContactToggleBlockLabel`; android: `ProfileVM.refreshBlockState` → `contactRowBlocksActor`, `ProfileSecondaryActionsRow` label → `contactToggleBlockLabel` injected FFI-free; apple: shared FaunaKit `ProfileView` label → `contactToggleBlockLabel(isBlocked:)`, state → `contactRowBlocksActor(rowPeerId:rowStatus:targetActorId:)` folded over the roster; tui reads `fauna_core::format` directly — `fetch_block_state` at `apps/fauna-tui/src/profile/mod.rs:1471-1476` (`contact_row_blocks_actor`) and `block_label` at `profile/mod.rs:1634-1635` (`contact_toggle_block_label`)) — **all seven apps now consume the shared predicate + label**.
- **Contact roster filter** (`contacts-search-field`). Shared Rust predicate — a case-insensitive substring test of the trimmed query against a contact's searchable fields, **handle + domain + actor-id** (the richest existing per-app shape; an empty/whitespace query matches all). The canonical home is `fauna_core::format` (alongside `short_id` / `url_host` / `backup_destination_label`), consumed by natives via a `libs/fauna-ffi` UniFFI face and by web via a `libs/fauna-wasm` twin, exactly like `short_id`. **Precondition: the contact rows must carry handle + domain** (§ State & data shape — **satisfied at the nest as of 2026-06-25**: `fauna.contacts.list` now supplies handle/domain; web/linux/tui receive them automatically, android/apple/windows via the extended `FfiContactItem` — § State & data shape has the full per-app breakdown). The lift is therefore **now ready** — the matching mechanism alone is trivial native logic not worth an FFI boundary, but the uniform shared predicate is the value. The filter is **local-only**: it never issues a nest query (contrast Contact lookup by handle, which is the federated discovery path). Once the snapshot carries handle/domain, all seven apps filter through this one predicate (resolving today's field-drift: web matches actor-id only, android matches handle+domain+actor-id, linux/windows match handle+actor-id, iOS/macOS have no filter).
- **Search debouncing.** Settled: N/A — neither search surface needs one. The roster filter (`contacts-search-field`) is a synchronous local substring match over already-loaded rows with no network cost (§ Layout & flow region 2; Contact roster filter above); the federated lookup (`contact-actor-id-lookup`) fires only on an explicit button press, not live-as-you-type (ui.yaml `contacts:` block; e.g. `apps/fauna-tui/src/contacts.rs` `Action::Lookup`, `apps/fauna-web/src/routes/contacts/+page.svelte:239` `handleFind` on click). No app debounces either path today, and none needs to given this shape.
- **Status badge text** (pending/accepted/confirmed/blocked label). Shared Rust — `fauna_core::format::contact_status_label(status) -> LocalizedText` (`pending`/`accepted`/`confirmed`/`blocked` → `common.*`; unknown → capitalized verbatim; `""` → empty), consumed by natives via the `libs/fauna-ffi` `value_format` UniFFI face and by web via a `libs/fauna-wasm` `contactStatusLabel` twin — the same recipe as `fauna_core::ical::rsvp_status_label`. The status **icon/color** stays an idiomatic per-app render (not part of the lift). Implemented for web + linux + apple + **android (2026-06-25)** + **windows (2026-06-25)** (`ContactInfo.StatusLabel` get-only, which also restored the previously-missing `confirmed` case its `_ => Unknown` map dropped — and added a `Confirmed` enum member so the status no longer collapses into `accepted` at the RPC boundary) + **tui** (built 2026-07-14 already wired to it — `contact_status_label` call at `apps/fauna-tui/src/contacts.rs:1046`) — **all seven apps now consume the shared formatter.**

## The private overlay — your own nickname, notes and labels on a person

**Ratified 2026-09-19 (design pass; the substrate ruling below and the element-ID package were approved by the user 2026-09-25). Built in shared Rust (the succession fold included) and on tui 2026-09-26, on linux 2026-10-01, on android, macos and ios 2026-10-03 over the UniFFI face — windows and web not yet (§ Implementation status today).** The overlay is what *you* attach to another person and nobody else ever sees: a **nickname** (your own name for them), free-form **notes**, and **labels**. This section owns the record, its merge, its identity-succession rule, where the nickname paints, and how labels reach the roster filter. It defers: the kind's audience rung and sealing epoch to [`../architecture/account-data-taxonomy.md`](../architecture/account-data-taxonomy.md) § The audience ladder → *The contact-overlay rung*; the plane mechanics (entry form, merge-policy seam, feeds) to [`../architecture/account-sync-plane.md`](../architecture/account-sync-plane.md); the formatter's canonical form to [`../behavior/value-formatting.md`](../behavior/value-formatting.md) § Peer display label; and the edit surface to [`profile.md`](profile.md) § The private section, because the Profile is the home of every per-user action (§ Relationship to Profile).

**It is keyed by actor id and is NOT gated on a contact edge.** The logical key is the other person's actor id (lowercase 64-hex). An overlay may exist for anyone whose Profile you can open — an accepted contact, a knock sender, a blocked stranger, a creator you follow — and it **outlives the edge**: unblock clears the edge and the 30-day accepted-TTL sweep deletes one (§ Persistence), and neither may take user-authored notes with it (`principles.md` § No user-data loss). Labelling someone you blocked is a first-class use. "Contact overlay" is the concept's name, not a membership test.

**Substrate: an account-state plane kind, `fauna.state.contact-overlay` — not a `__contacts` blob folder.** One class-2 item per person (the same one-row-per-logical-key shape the custody rows use), merge policy **CRDT per-field**, fleet-only rung, tip-sealed (the taxonomy owns those two columns and their argument). Why the plane and not a new reserved rail: the overlay has **no legacy data**, the rails' ratified direction is to dissolve onto the plane ([`../architecture/account-sync-plane.md`](../architecture/account-sync-plane.md) § Substrate settlements), and a new rail would need its own get/put wire pair, closed path set, size bound and history collapse (what `__drafts` had to grow — [`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § Drafts Sync) only to be bridged and migrated off later under the no-data-loss rule. A rail is also load-on-launch and whole-blob; the plane gives per-person items, live cross-device pickup and removed-device severance. **Web reaches this kind like every other app.** When this was ruled the plane engine was native-only, which ordered web's leg behind its store backend; web has hosted the account runtime since 2026-09-29 ([`../architecture/account-client-lifecycle.md`](../architecture/account-client-lifecycle.md) § Implementation status today, *web hosts the runtime*) and registers this kind's seam with it, so web's leg is the same lift as the natives' — never a declared absence, and no `ui.yaml` platform-scope flag is taken. A tab that hosts no runtime (a second tab of the same account) cannot write the kind, so its Save is refused under that doc's absent-runtime bound (§ The client-side lifecycle → *The account port*, *Bounds, stated*); the gesture works in the hosting tab. `__contacts` is consequently never minted ([`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § Contacts Sync).

**The record.** Canonical dag-cbor, additive like every wire type (`#[serde(default)]` fields + a trailing `extra` catch-all so an older binary re-seals what it does not know). Home: `fauna_core::contact_overlay` (wasm-safe, so web's later leg reuses it unchanged).

```
ContactOverlay {
  nickname: Register<Option<String>>,                // None = cleared
  notes:    Register<Option<String>>,
  labels:   BTreeMap<FoldedLabel, Register<Option<String>>>,  // value = the label's display spelling; None = removed
  extra
}
Register<T> { stamp: LwwStamp, value: T }            // LwwStamp = the plane's (at_ms, writer) total order
```

- **Merge — per-field last-writer, labels per-label.** Each register resolves independently on its `LwwStamp` (an exact stamp tie resolves on the values' canonical bytes, never on which replica is merging — the `merge_user_configs` join rule). So a nickname set on one device and notes edited on another **both survive**; whole-record latest-wins was rejected precisely because it would silently drop one of them, and notes are irrecoverable user-authored text. Labels are a map of per-label presence registers rather than a union set, so a **removal propagates** instead of being resurrected by a stale replica; a removed label's marker is retained (`value: None`). The merge must be a **join in bytes** — commutative, associative, idempotent, asserted over a pair differing in every register — the same bar `format_user_config.rs` holds. **Accepted residual:** two devices editing the *same* register concurrently (the same person's notes, both offline) resolve last-writer and the loser's text is gone; three-way text merge has no wired resolver on the plane (`MergePolicy::ThreeWay`), and a per-person note is short-lived-edit territory. Revisit only with evidence.
- **Clearing is a write, not a tombstone.** CRDT-per-field kinds admit no tombstone ([`../architecture/account-sync-plane.md`](../architecture/account-sync-plane.md) § Merge-policy seam). "Remove everything I wrote about this person" sets every register to `None` under fresh stamps; the emptied item stays (a few dozen bytes). An all-`None` overlay reads everywhere as *no overlay*.
- **Bounds, enforced in the shared validator before the writer door** (each refusal a `LocalizedText`): nickname ≤ 64 characters after trimming (whitespace-only = cleared); notes ≤ 16 KiB; a label ≤ 48 bytes after trimming and whitespace-collapse, its map key the Unicode-lowercased form (so "Family" and "family" are one label, displayed as last written); ≤ 32 live labels per person and ≤ 128 map keys including removal markers — at the cap the writer **refuses the new label** rather than pruning a marker, because pruning is what lets a stale replica resurrect. All comfortably inside the plane's 64 KiB entry cap (`fauna_protocol::account_state::MAX_STATE_ENTRY_BYTES`).
- **The label vocabulary is derived.** The set offered for completion when labelling someone is the union of live labels across all overlay items — class 4, recomputed, never its own kind. A global rename is N item writes and is not a v1 affordance.
- **The in-memory projection is `fauna_conversations::ContactsCache`** — the long-standing empty struct becomes `actor id → ContactOverlay`, fed from the account store handle's `states_of_kind` read and its change nudges, and is what snapshot builders consult. It never touches the engine crate itself (the app's session hands it the entries), which keeps `fauna-conversations` engine-free.

**When a person's identity succeeds, the overlay folds forward — a statement-consumer action.** The nest re-points contact *edges* inside the succession transaction but cannot open a client-sealed overlay, so the client does it, on the same trigger and contract as the peer-contact row ([`../behavior/succession-propagation.md`](../behavior/succession-propagation.md) § Propagation → *Contacts*): the witness-verified statement that re-points a thread participant row also folds the predecessor's overlay into the successor's — `successor := join(successor, predecessor)` using the ordinary per-register merge (so where both carry a nickname the newer stamp wins, and labels union), then the predecessor's item is cleared; terminal hop on a twice-succeeded person, per `resolve_successor`'s contract. The fold is a **reconcile, not a one-shot**: it runs at statement consume *and* whenever the projection loads a non-empty item whose key has a witness-verified successor — which is what absorbs a straggler device that edited the old identity's notes after the fold. Two devices folding concurrently write the same join and converge. An unverified or merely claimed succession folds nothing. **What is carried, and how the old item is emptied:** only the predecessor's *live* registers are joined — a `None` there is a removal or the fold's own earlier clear, and carrying the clear would let a second fold wipe what the first one moved (so a label removed on the old identity is not removed from the successor) — and each carried register is cleared **one millisecond past its own stamp**, never at a wall-clock stamp. The fold is therefore a pure function of the two items (two devices write identical bytes), the clear outranks exactly what was carried, and a straggler's later edit outranks the clear and survives the plane join, for the next fold to carry instead of losing it. **The verdicts the reconcile consumes** are the witness-verified re-points this session made, held in memory for the session and retired with the account at an identity change; after a relaunch the reconcile waits for the next verified verdict for that identity — the same remedy the harvest wait's no-roster ruling names ([`../behavior/identity-succession.md`](../behavior/identity-succession.md) § The succession statement → *the harvest wait*).

**Where the nickname paints: everywhere the app names that person — through one shared resolver, at snapshot build.** A nickname that showed on the roster but not above their messages would be a toy. The resolver is `fauna_core::format::peer_display_label` ([`../behavior/value-formatting.md`](../behavior/value-formatting.md) § Peer display label owns its form: nickname, else the public name chain). Snapshot builders in shared Rust call it with the projection's nickname, so apps receive a finished string and never resolve names themselves — consistent with `conversations.md`'s rule that display names live on the snapshot, never on the address (`TypedAddress::display` stays overlay-free). v1 surfaces, all of which today hand-roll one of three different fallbacks (raw 64-hex, `short_id`, full hex) and converge here: the roster row (`contact-name`), the knock sender (`knock-sender` — a nickname if you have given that sender one, else `short_id` exactly as today), the conversation message sender (this *is* the "contact-name resolution" `MessageSnapshot.sender_display` has waited on — `conversations.md` § Implementation status), group member chips and the reply-quote author, the feed post author, the subscription author label, and the Profile header. **Two guards.** (1) *The public identity is never hidden*: wherever a nickname is the primary line on a list or detail surface (roster row, Profile header), the public name it replaced renders as a secondary line; compact surfaces (message sender, chips) show the primary only, and the Profile is one tap away. (2) *A nickname never leaves your devices in anything another person can read*: it paints, it is never authored — not into a mention, a reply quote's wire form, a group or thread name sent to others, an exported vCard, an invitation. Authored content naming a person keeps their public handle.

**The paint gate — a nickname paints only on a proven identity (ruled 2026-09-27).** An overlay is a fact about an actor id — *the holder of this key is "Mum"* — so a surface may paint it only where the id it holds was bound to that key by cryptography, never where the id is a peer's bare claim. On the conversations snapshot the two binds of [`../behavior/conversations-at-rest.md`](../behavior/conversations-at-rest.md) § Encryption at rest are the only proofs: a **member chip** paints the nickname only once the participant's actor id is a verified leaf of the thread's bound MLS group (the *Leaf-credential binding*, read off the rail's authoritative roster — `RailBackend::authoritative_roster`, the same source the eviction driver trusts and never `ThreadDetail::participants`); a **message bubble**'s sender is the leaf MLS authenticated at decrypt (the *authenticated leaf is the sender* rule) or a room message's signature-verified author, and is proven by the rail that ingested it. Why the seat needs a gate the bubble does not: a cross-nest participant's actor id arrives from the dialed nest's `by_handle` answer, which the dial rule ([`../architecture/foreign-handle-resolution.md`](../architecture/foreign-handle-resolution.md) § Peer-auth model → *What a peer's answer may and may not claim*) leaves unbound — a nest serving `attacker.test` may answer `bob` with the actor id of someone the viewer has nicknamed, and the KeyPackage the group then fetches from that nest may be for a key of the attacker's own — so before the group bootstraps, and whenever the admitted leaf is not that key, the chip keeps the public label (`bob@attacker.test`), which is exactly what the viewer typed. The honest cost is bounded and accepted: a 1:1 or group the viewer starts shows the public label until its first send bootstraps the group, and a group joined from a Welcome is proven from the start. The gate is read-time in shared Rust (`ConversationsManager::project_participant_nicknames`), so every app inherits it with no snapshot-shape change. **The same rule governs the device-local handle backfill** (`ConversationsManager::handle_for_person`, which names a nameless seat from any thread carrying the same actor id): a seat lends its handle only from a thread whose bound group has proven that id, so the forged `(handle, id)` pair can never put the dialed handle on that person's genuinely nameless seat elsewhere. Surfaces keyed on the id the overlay is *about* rather than on a `(handle, id)` claim — the roster row, the knock sender, the Profile header, the feed and subscription author — have no second party asserting the id and stay ungated. The residual this leaves is the KeyPackage-substitution residual federation.md ratifies: the substituted leaf is admitted as its own key, never as the nicknamed person, and paints as such.

**Labels and the roster filter.** `contact_matches_filter` (§ Where logic lives → Contact roster filter) gains the nickname and the live labels as searchable fields beside handle + domain + actor-id — typing a label narrows the roster to the people carrying it. **Notes are deliberately not matched**: a row that matches for a reason the row does not show is a confusing filter. The roster row shows the person's labels as one text line (`contact-labels`). A dedicated tap-a-label filter control is not v1.

## Persistence

Contact-relationship state (per-edge `(actor_id, peer_id, status, accepted_at, created_at)` with `status` in `{pending, accepted, confirmed, blocked}`) lives nest-side in the plaintext routing floor — `bins/fauna-nest/src/db/contacts.rs`'s `contacts` SQLite table — and is mutated by the user-facing WS-RPC kinds (`fauna.contacts.confirm`, `fauna.knocks.{accept,block,dismiss,unblock}`) plus the auto-`pending` `upsert_contact(..., "pending")` write inside `store_knock` (`bins/fauna-nest/src/routes.rs`), fired from a real knock arrival over `fauna.inbox.send` (same-nest) or the federation `inbox.deliver` channel kind — **not** real inbound email, which carries no `ContactStatus`/`InboxMode` gating today (`reach_floor` keys on `ContactStatus` **between actors** only; email's own reach control is the separate, unrelated `unknown_sender_mail` guardian gate — `family-safety.md` § Guardian policy pillar 1). `fauna.knocks.unblock` is the lone **user-triggered edge-deleting** transition reachable from the relationship surface (guarded on `status = 'blocked'`); it returns the relationship to no-edge (§ Where logic lives → Unblock). A second, time-driven path also deletes an edge: an hourly background sweep (`bins/fauna-nest/src/main.rs`, `ACCEPTED_CONTACT_TTL_SECS = 30 days`) calls `expire_accepted_contacts`, which deletes any `accepted` edge whose `accepted_at` is older than 30 days — the same no-edge outcome as unblock, but reached by inaction rather than a click; an edge already `confirmed` (or `pending`/`blocked`) is untouched, so only an accepted-but-never-confirmed contact can silently lapse. A third, also time-driven (2026-09-24): the same sweep's `expire_old_knocks` deletes the `pending` edge of every knock it expires, together with the knock's notification row (`../behavior/notifications.md` § Retention rule 3) — before that an expired knock left its `pending` edge behind, which refused the sender's every later knock as still pending while the recipient had no knock left to act on. Re-establishing contact after any of these paths goes through a fresh knock. The `deliver_inbox_payload_core` hot path (`routes.rs`) reads this table on every knock/DM arrival.

User-private contact-record contents — your own nickname, notes and labels on a person, keyed by their actor id — are the **private overlay**, owned by § The private overlay: one account-state plane item per person (`fauna.state.contact-overlay`), sealed client-side, never readable by any nest. (Until 2026-09-19 this paragraph routed them to a reserved `__contacts` fauna-sync folder; that folder was never built and the ruling there retires it.)

The standard **address book** — full vCards for arbitrary contacts (grandma, the plumber, a school — overwhelmingly *not* Fauna actors), including the cross-rail address-book mappings that unify one logical person across `actor_id` + mail address + XMPP JID — is a **separate** store: the CardDAV bridge store `bridge_carddav_*` (`docs/goal/behavior/carddav-server.md` § Storage model), MLS-sealed and served to generic CardDAV clients (DAVx5 / Apple Contacts / Thunderbird). This **superseded the `__contacts`-for-address-books** half of the original contacts-at-rest design (tracked internally); the other half, the private overlay, moved to the account-state plane on 2026-09-19 (§ The private overlay), so nothing remains for a `__contacts` folder to carry. A vCard MAY link back to a social contact via an optional `X-FAUNA-ACTOR-ID` field (post-v1).

Knocks (pending incoming contact requests) live nest-side in the `knocks` SQLite table. The knock's plaintext fields are routing-floor artifacts — sender identity and timestamps are floor items, and `summary` is a plain client-authored `ContactRequest.summary` text field (`libs/fauna-core/src/data.rs`) with no mail-subject derivation (the legacy in-core SMTP path's mail-subject-derived summary was removed with `fauna-bridge-smtp`, 2026-05-26); it falls under this Contacts row, not the `Mail subject` conformance row (`encryption-at-rest.md`). The same hourly sweep that expires stale-accepted contacts (above) also runs `expire_old_knocks` (`bins/fauna-nest/src/main.rs`, `PENDING_KNOCK_TTL_SECS = 90 days`), deleting any knock row older than 90 days regardless of whether it was ever acted on. **A knock is bounded at the door, because every byte of it is written by someone the recipient has not accepted** (built 2026-09-24, `store_knock` in `bins/fauna-nest/src/routes.rs`, so every arrival that lands on the knock path is covered — local or federated, the `allow_knock` mode arm or the guardian-forced one): the knocker-written columns have hard-coded caps — `summary` 500 bytes (`MAX_KNOCK_SUMMARY_BYTES`; the shared senders trim it to 80, and it is the one field copied onward, into the permanent notification row's `summary` and `body_args`), `sender_node` 2 KiB — and an over-cap knock is **refused whole** with a malformed-class error, never truncated, since a silently trimmed sentence is a change the sender cannot see; the held arrival stays capped at 16 KiB and is dropped past it, as before; and a recipient holds at most 1 000 knocks (`MAX_PENDING_KNOCKS_PER_RECIPIENT`), past which a new knock is refused with the transient `fauna.protocol.rate_limited` until the recipient acts on the queue or old knocks expire. The count cap is what survives a distributed flood — the per-(recipient, sender) dedup falls to a fresh keypair per knock and the federation throttle to many sources — and it is per recipient rather than nest-wide so a flood aimed at one account fills only that account's queue. **Metering knocks against the recipient's tier quota was considered and not taken:** knock rows are not counted in the account's usage, so a `check_quota` call would refuse knocks only to an account already full for other reasons, and it would do nothing at all where tier quotas are off (the desktop nest) — the hard caps hold on every deployment. **How long a knock's notification row lives is `../behavior/notifications.md` § Retention's ruling (2026-09-24):** the doorbell goes with the knock on dismiss, block and expiry, stays on accept, and a re-knock supersedes it.

Device-local P2P state (per-peer last-known endpoints, success rate, backoff level, plus a vestigial WireGuard public-key column the 2026-08-23 deletion left in place under the additive-wire rule — `libs/fauna-peer::PeerContact`) is operational state of each device's P2P engine and is not synced between the user's locations.

## Encryption at rest

Contacts split across two at-rest representations, by operational role:

- **Contact-relationship state (plaintext routing floor).** The per-edge row `(actor_id, peer_id, status, accepted_at, created_at)` in the nest's `contacts` SQLite table. Authoritative for routing: status changes flow through the WS-RPC kinds named in § Persistence to this table, and the `deliver_inbox_payload_core` hot path (`bins/fauna-nest/src/routes.rs`, the shared core behind `fauna.inbox.send` and the federation `inbox.deliver` channel kind) reads it on every knock/DM arrival (e.g., `contacts_only` inbox-mode filtering; `allow_knock`-mode knock dedup + auto-`pending` write on arrival from a not-yet-contact sender). This is Fauna actor-to-actor traffic only — real inbound email carries no `ContactStatus`/`InboxMode` gating (the legacy in-core SMTP reader that once also drove this for literal email, `fauna-bridge-smtp`, was excised at the I6 cutover with no successor there; email's own unknown-sender reach control is the separate `unknown_sender_mail` guardian gate, `family-safety.md` § Guardian policy pillar 1, which composes its own primitive rather than routing through `reach_floor` — the function above, which keys on a `ContactStatus` between actors). The nest must be able to mutate this table without `BackupKey`; it is not a derived mirror of a sealed source, it is the authoritative representation of the routing-state subset by construction.

- **User-private contact-record contents (the private overlay — sealed account-state plane items).** Your nickname, notes and labels on a person, keyed by their actor id (§ The private overlay). Each item is a class-2 plane entry sealed on the owner's client under the kind's fleet-only, generation-tip key ([`../architecture/account-data-taxonomy.md`](../architecture/account-data-taxonomy.md) § The audience ladder → *The contact-overlay rung*; entry form and its cleartext floor — scope, writer, sequence, blinded item key, size, timing — [`../architecture/account-sync-plane.md`](../architecture/account-sync-plane.md) § The class-2 entry form). Every replica, the nest included, relays ciphertext it cannot open; the item key is blinded, so a custodian cannot even tell *which person* an entry is about. (The standard **address book** — full vCards for arbitrary contacts + the cross-rail mappings — lives in the **separate** MLS-sealed CardDAV store `bridge_carddav_*`; see `docs/goal/behavior/carddav-server.md` § Storage model.)

The peer's *public* fields the Contacts page surfaces — display name, handle, avatar — are read from that peer's federated public `Profile` record (signed plaintext, per the `Profile` conformance row in `docs/goal/architecture/encryption-at-rest.md`). They are not stored locally as user-private contact content; the user's optional local *override* of the name (a private nickname) is what the overlay carries.

Authority for this section: § The private overlay + `docs/goal/architecture/account-data-taxonomy.md` § The audience ladder for the overlay, `docs/goal/behavior/reserved-folders.md` § Contacts Sync for the floor / contents split, and `docs/goal/architecture/encryption-at-rest.md` § Per-content-kind conformance row "Contacts" (rationale tracked internally). The **address-book vCard** store is a *separate* at-rest authority — `docs/goal/behavior/carddav-server.md` § Storage model (`bridge_carddav_*`, MLS-sealed per session), which supersedes the `__contacts`-for-address-books portion of that rationale.

## Architectural rules

1. Observer-driven rendering.
2. Indexed list IDs (`knock-card[i]`, `contact-row[i]`, `contact-status[i]`, `contact-confirm[i]`, `contact-unattested-mark[i]`) — scoped queries only.
3. Localized strings via i18n table.

## Don't do these

- Don't render contact status text per-app. The shared `fauna_core::format::contact_status_label` supplies the localized label (§ Where logic lives → Status badge text); call it on the raw `status` rather than hand-rolling a status→label map. (When the deferred `ContactsSnapshot` lands it carries that same label; until then apps call the shared face directly.)
- Don't block-list per-app. Block state is server-side; the snapshot reflects it.
