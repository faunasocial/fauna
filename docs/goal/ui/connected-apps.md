## Goal

One page shows the user everything that acts for them from outside the seven apps — a website they signed into, a device app, a plugin their admin installed, a mail client's app password, a Nostr signer client — with what each may reach, in words, and one **Revoke** per row. It is also where a user *starts* two of the consent flows: typing the code a device app showed them, and answering a quiet request an already-approved app pushed.

## Layout & flow

A Settings sub-page (rail slot after *Task delegation* — [`settings.md`](settings.md) § Navigation model), four regions top to bottom:

1. **Requests** — the quiet-push tray: one card per live request (client identity verbatim, scopes in words, the binding code, Approve / Decline, and *Never show requests from this app*). Renders only while a request is live, exactly as the consent card does today — no permanent empty row, because a standing "no requests" line trains the user to ignore the one place the anti-phishing check happens.
2. **Connect an app** — one entry: a code field and a submit; a valid code opens the same consent card the browser start shows. This is the RFC 8628 user-code half; the code's alphabet and length are the issuer's.
3. **The roster** — one row per principal, grouped by execution form (remote, device, plugin, app password, signer client) or flat with a badge — the tui build decides; per row: name + publisher domain, the scopes in words (the same describe path the consent card uses — never a second renderer), *lasts-until*, last used, **Revoke** with an inline confirm. A plugin's row additionally links to its settings card (the `settings_schema` render the Bridges page already owns, [`../behavior/bridges.md`](../behavior/bridges.md) § Bridge settings). A **mail app password's** row additionally carries what a user needs to set a mail app up: the password's kind (Password / Bearer token), the exact login a mail app uses with a copy control, and the secret — hidden until revealed, with reveal and copy — read on demand and never part of the snapshot. What those mean, and the burned state a row shows after an identity succession, are the mail-settings page's ([`mail-settings.md`](mail-settings.md) § Credentials list); this page owns only where they render. A **principal that attested a holder key** additionally carries, on an app that reads the owner's grant log, its **trust facet and history lens** — the per-row Now / History lens the Nests page renders, over the keys the app holds (§ The trust facet and history lens).
4. **Blocked apps** — one row per client the user chose *Never show requests from this app* for: the client identity verbatim, when it was blocked, and **Unblock**. Renders only while something is blocked, for the reason the tray has no empty row.

## The trust facet and history lens (ratified 2026-10-03)

A third-party principal is a participant ([`../behavior/participants.md`](../behavior/participants.md) § The participant model → *Third-party principal*: "the trust facet renders its grants, the history lens its audit log … and revoke is the same control"), so its roster row carries the participant model's facet in the shape the Nests page already renders — a **per-row Now / History lens** ([`nests.md`](nests.md) § Layout item 2, § Trust facet — grants, § Trust facet — History lens) over the shared folds `fauna_client_capabilities::view_model::{principal_trust_facet, principal_history}` (the owner's signed grant log keyed by the principal's attested holder key, the principal's grants only — the predicate [`../architecture/third-party.md`](../architecture/third-party.md) § The principal model rule 4 owns). The richest existing pattern, reused rather than a second shape (priorities #3 and #4); it is a *row expansion*, not a detail view, because the Nests facet is one and a user who learned one page has learned both.

- **Which rows.** The facet renders on a row whose principal attested a holder key, on an app whose machine reads the owner's grant log (the consent-grant seams — tui, linux, macOS and iOS today; android and web are parity-in-flight, not a declared absence: [`../architecture/third-party-kinds.md`](../architecture/third-party-kinds.md) § Implementation status today). Every other row — a principal that attested no key, an ATProto app-password session, a signer client, a mail app password, and every principal row on an app without the seams — renders **no facet and no lens toggle: absent, never an empty state.** "Holds no keys" is a claim only a read of the log may make, and the row's scopes-in-words line already says what the app may reach by its sign-in.
- **The Now lens.** One row per live third-party grant to the holder (the Nests rule: an expired grant stays listed as Expired, a revoked one leaves), soonest-expiring first; each row shows **the scope in words**, ***lasts-until***, **the liveness** — Active / Expiring soon / Expired, never Auto-renewing: a principal is never a blessed box and nothing renews its trust in the background — and **the required honest-bound copy** ([`nests.md`](nests.md) § Honest bound, the standing-keyed wording in the principal's voice: disconnecting stops this app getting keys again on an honest nest; it cannot un-see what the app already read, and does not yet block records sealed after that). A principal with a holder key and no live grant shows an explicit empty state, *This app holds no keys to your records* — true even for an app with wide sign-in scopes, because the facet speaks only of keys and the scopes line above speaks of sign-in reach.
- **No per-grant Renew and no per-grant Revoke in v1.** The page's rule is one Revoke per row (§ Architectural rules), and that Revoke *is* the participant's revoke control — it records each grant's `Revoke` in the owner's log (built 2026-10-03, [`../architecture/third-party.md`](../architecture/third-party.md) § Implementation status today). Renewal of a principal's trust is the app asking again: the consent card is the only mint for a principal ([`../architecture/third-party.md`](../architecture/third-party.md) § The principal model — an untrusted holder, never a trusted mint), so an Expired row's status says so (*Expired — the app will ask again if it needs them*) where the Nests row says *renew to resume*; one shared status door chooses by whether the row can renew. Both controls are refutable at a later build if a journey needs them; neither mints an ID now.
- **The words rule for `ext.*` kinds.** A manifest declares a kind's string, class and merge policy and no display name ([`../architecture/third-party-kinds.md`](../architecture/third-party-kinds.md) § The manifest), so a kind is named the way the consent card named it when the user approved it: its **publisher** and its **name label verbatim, in quotes** — *Keys to your records published by example.com: "notes", "reading-list" — read and write* (or *— read only*) — composed once in shared Rust from the grant's tuples (one grant covers one publisher's kinds; a kind carrying a `content.write` tuple is read-and-write, else read-only; a grant whose kinds differ marks each kind, though none mints today), through the same door the Nests facet's scope line uses (`fauna_client_pair::scope_label`'s family), never a raw `ext.example.com.notes` token (§ Don't do these). A name label is lowercase `a–z 0–9 _ -` and is shown verbatim, never prettified — no title-casing, no `-` to space — because the user matches it against the app's own documentation and against the card they approved.
- **The History lens.** The principal's third-party grant events, most-recent-first — Minted / Revoked (Renewed cannot occur for a principal today) — each self-describing through the shared history line (`fauna_client_pair::history_line_text` over the same scope words as the Now row), a Revoke naming the scope its grant last carried (the shared fold's rule, [`nests.md`](nests.md) § Trust facet — History lens). **Two consequences, accepted:** the lens is keyed by the row's *current* holder key, so the `Revoke`s of a key the app replaced ([`../architecture/third-party.md`](../architecture/third-party.md) § The principal model → *Key replacement*) and the whole record of a disconnected app leave this page with the row — the signed log keeps them, and a page-level audit view is deliberately not minted here; an app that re-connects under the same key shows its earlier Minted and Revoked entries under the new row.
- **Lens state** is per row, held in the shared machine (`set_lens(key, lens)`, the Nests machine's `SetLens` twin), Now by default, and reset on a fresh visit with the page's other drafts (§ Persistence). Nothing leaves the device.

## State & data shape

One shared-Rust snapshot, `ConnectedAppsSnapshot { loaded: bool, requests: Vec<ConsentRequestRow>, principals: Vec<PrincipalRow>, blocked: Vec<BlockedAppRow>, error }`, composed by one shared machine over the principal roster read plus the pending-consent read the ATProto settings machine already performs (`AtprotoSettingsSnapshot.consents`) — the machine generalizes, it is not duplicated. `PrincipalRow` is the roster model's row ([`../architecture/third-party.md`](../architecture/third-party.md) § The roster model) with the scopes already rendered to words; a mail app password's row additionally carries its login (only `{handle}` left for the renderer), its kind label and whether the succession burn killed it. No secret is ever in the snapshot. A principal's row additionally carries `trust: Option<PrincipalTrust { lens, grants, history }>` — the Nests row's `TrustGrantRow` / `TrustHistoryRow` projections over `principal_trust_facet` / `principal_history`, filled on the same read that derives *lasts-until*; `None` means no facet (§ The trust facet and history lens → *Which rows*), never an empty one. A request row carrying a bare folder-plane scope additionally carries `folder_picker: Option<FolderPicker { options, chosen, none_eligible }>` — the account's eligible folders by name and row id, composed by the machine from the owner's folder custody, with the reason when none is eligible (ruled 2026-10-05, [`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Consent → *The card chooses the folder*). The exact type names are the build's; the field set is not.

## Where logic lives

- **Shared Rust:** the snapshot and every derivation in it (scope words, *lasts-until*, the grouping key, the revoke → which verb), the code-field validation, the consent-card composition (the built one, reused), and the same-device handoff's open — `ConnectedAppsMachine::open_handoff(request_uri)` calls `fauna.oauth.consent.open_handoff` and places the row it answers in the requests tray, the `submit_code` shape, a miss being the page's one error ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Consent → *How the same-device handoff is built*); the trust facet's folds, the `ext.*` words, the liveness and the per-row lens state (§ The trust facet and history lens); the consent card's folder picker — which owned folders are eligible for the card's verbs, and the chosen id carried into the twin's mint and the resolve ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Consent → *The card chooses the folder*). Priority #2: a row that means the same thing on seven apps is composed once.
- **App glue, with reason:** navigation into the page; painting; the `fauna://consent/<request_uri>` route's intake (platform URL registration is per-OS by definition; tui's is a launch argument, [`../architecture/apps/tui.md`](../architecture/apps/tui.md) § System integration → *In-app routes*), which hands the parsed route to the shared open above and lands on the same consent card.

## User actions

- **Type a code → submit** → the shared machine calls the device-authorization lookup; a live code opens the consent card; an unknown or expired code shows the page's `error-message` ("that code has expired — ask the app for a new one"), never a distinguishable "unknown vs expired" pair.
- **Approve / Decline a request** → `resolve_consent`, the built verb; a decline is recorded, not dismissed locally. An approve whose attested holder or writer key differs from the roster's for the same client also ends the old key's third-party grants and records their `Revoke`s, and the card says so — the model is [`../architecture/third-party.md`](../architecture/third-party.md) § The principal model → *Key replacement*.
- **Choose the folder on a request card** (a card carrying a bare folder-plane scope) → the shared machine records the choice; Approve then mints the arm's twin over that folder and sends it with `resolve_consent`; with no eligible folder the card says why and Approve is disabled ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Consent → *The card chooses the folder*).
- **Never show requests from this app** → the per-client block (nest state); the row disappears from the tray and no future request from that client renders.
- **Unblock a blocked app** → lifts the per-client block (nest state); the row leaves the section and that client's next request renders again.
- **Reveal / copy a mail app password's secret, copy its login** → the machine's on-demand secret read (reveal paints it for this visit only; copy puts it on the clipboard without painting it); the login copy is local. A failed read shows `error-message`.
- **Now / History on a principal's row** → flips that row's lens in the shared machine; a local view change, no nest call (§ The trust facet and history lens).
- **Revoke a row** → one verb per credential class, chosen by the machine: the OAuth grant's `revoke_session` cascade, the mail app password's `RevokeCredential` (what it ends: [`../behavior/mail-credentials.md`](../behavior/mail-credentials.md) § Soft revoke), the bunker app's `fauna.nostr.bunker.revoke`, a principal row's delete. The app never picks the verb.

## Persistence

Nothing app-local. Rows are nest state read on every open (non-optimistic: a revoke re-reads before painting, the Nostr page's rule); the per-client block is nest state. A revealed secret lives only on the page for the visit that asked for it.

## Errors & edge cases

Three-state list (`loaded`), and every visit starts unread: the page drops the previous visit's rows and paints neither rows nor the empty state until this visit's own read has returned. A refused principal-roster read is an ordinary page error (`error-message`), while a feature-excised surface (the nostr signer roster on a nest built without it) contributes no rows and no error. A revoke that fails leaves the row and shows `error-message`. A request whose code expired mid-read renders nothing (the built collapse in the nest's consent read-back, `read_consent_state`). A grant log the seams could not load leaves every principal row without a facet for that visit — absent, never an empty lens claiming the app holds nothing (§ The trust facet and history lens → *Which rows*).

## Architectural rules

- **One roster, one describe path, one revoke per row.** No per-page copies of the three rosters survive the lift.
- **The consent card here is the built card**, composed in the shared machine — the page adds a start, never a second card.
- **Quiet means quiet**: a never-approved client's request produces no notification from this page or any other surface.

## Don't do these

- **Don't render a permanent "no requests" row.**
- **Don't show a scope as a token string.** Words only, through the shared describe path.
- **Don't let an app choose the revoke verb** or paint a row twice during the migration.
