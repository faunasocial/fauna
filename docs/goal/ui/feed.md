## Goal

The Feed page lists posts from feeds the user follows (own posts, contact posts, bridge feeds — Bluesky/ActivityPub, etc.), and lets the user compose a new post. Feeds are a user-defined filter over post sources; the user can create new feeds with rule sets (`create_feed` sub-page) and view a single post in detail (`post_detail` sub-page).

## Layout & flow

Three regions stacked top-to-bottom (desktop sidebar variant) or front-and-back via tab + drill-in (mobile):

1. **Feed selector** (component `feed-selector`) — list of feeds the user has defined; current selection drives the post list. Also hosts the built-in **Trending** virtual-feed pseudo-entry (`feed-trending-item`, `FeedSnapshot.trending_selected`) above the user's own feeds — owned by [`../behavior/trending.md`](../behavior/trending.md) § The Trending feed, not restated here.
2. **Search bar** (component `feed-search-bar`) — filters the visible post list by free text.
3. **Post list** — `post-card` (component) per row; click opens `post_detail`.
4. **Composer** (component `feed-compose-bar`) — text + tags + file picker; submit creates a new post against the currently selected feed scope (or the user's primary feed if no scope is selected).
5. **Bridge subscribe form** — inline form with `bridge-form-*` elements for subscribing to a Bluesky/ActivityPub URI as a synthesised feed.

### Interaction bar (like / reply / repost / quote) — ratified 2026-06-27

Every `post-card` carries the four interaction buttons `feed-like-button`,
`feed-reply-button`, `feed-repost-button`, `feed-quote-button` (the ui.yaml
`interaction-bar` component), **identical on all seven apps**. Two
presentation rules were ratified by the user on 2026-06-27, resolving a
priority-#1 divergence (web had text labels + Quote; windows/apple icon+count
without Quote; linux text without Quote; android icon-only without Quote):

- **Quote is universal.** `feed-quote-button` (already a shared `elements`
  entry in ui.yaml) renders on **all seven** apps — web is the reference;
  linux / windows / apple / android / tui add it. A quote is a repost *with*
  commentary (`Reference::Quote`); **today** the button fires a direct
  quote-repost with empty commentary. The mechanism is
  `FeedManager::quote(post_id, body)`, which **composes a post carrying
  `Reference::Quote`** — corrected 2026-08-10, having previously read
  "`oninteract(post_id, 'quote')` → `fauna.posts.interact` action `quote`,
  exactly as web does". That named a call which, on a native post, discards its
  input and creates nothing; every app made it and nothing happened (§
  Implementation status today). Capturing the *commentary* (a composer
  pre-targeted at the quoted post) is a **fleet-wide follow-on**, not a per-app
  add — it changes the action on all seven apps together, so it is deferred
  until that cross-app decision lands. It is now a genuinely small one: the
  composed post already carries a `body`, so the follow-on is UI only.
- **Reply and quote on a bridged post (ratified 2026-09-26, design pass; build state in § Implementation status today).** The same signed referencing post as on a native post, for **every bridged source** — `activitypub`, `nostr` and `bluesky` — after **one eligibility ack** from `fauna.posts.interact` `{action: reply | quote}` with no body: the native arm's `{action, target_post_id, source}` ack (with `counts` from the local row where the nest holds the counters) means compose; the bridge's refusal — no linked account, no relays, replies switched off — is the affordance's inline failure and nothing is composed; an older nest's `fauna.posts.unsupported` renders the same way, never a crash. The nest's create-side bridge fan-out then derives the origin protocol's reply or quote — mechanics owned by [`../behavior/activitypub.md`](../behavior/activitypub.md) § Reply and quote, [`nostr.md`](nostr.md) § Replying to and quoting a nostr note and [`../behavior/bridges.md`](../behavior/bridges.md) § Interactions + § Cross-posting → *A post that references a Bluesky record*. **One reply shape on every arm:** the native ack, so `PostInteractReply.result` reads the same for a `fauna`, `activitypub`, `nostr` or `bluesky` target of these two verbs, and no new wire field exists; a `bluesky` ack carries `counts: None` (its counters live at the origin) and the client's existing `None` handling leaves the rendered numbers alone. Bluesky joined this shape on 2026-09-26 — its nest-mint arm, which built the reply at the PDS from the interact `body` with no local post, was retired the same day, no older-client path kept ([`../behavior/bridges.md`](../behavior/bridges.md) § Interactions). `FeedManager::compose_referencing_post_as` routes every non-native source through ack → compose; the interact-with-body path no longer exists. Every app calls `FeedManager::reply`/`quote`, so the routing lives once in `libs/fauna-feed` and no app has a leg of its own.
- **Display is icon + interaction count, uniform.** Each button shows a
  recognizable icon plus its interaction count — **no word labels** — and the
  **count is hidden when 0** (a clean icon-only button until the post has
  activity). web/linux drop their word labels; android adds the counts;
  windows/apple already render icon+count and only bind the now-real values.

The counts are read from the shared snapshot, **not** computed per app —
including right after the user's own tap, which is the case that used to be
wrong. `fauna.posts.interact` returns the target's four counters as the nest
holds them after the act (`PostInteractReply.counts`, additive 2026-08-10) and
`FeedManager::interact` folds them into the loaded window, so the tapped number
moves without a feed re-query. A client-side optimistic `+1` is **not** an
allowed substitute: the nest's like counter is idempotent per (actor, post), so a
repeat tap moves nothing, and a local guess would be right once and wrong every
time after. An absent `counts` (older nest, bridged source, `unrepost`) leaves
the rendered counts untouched.

**Repost is a toggle, and a repost is a post (ratified 2026-08-10).** The at-rest
truth was settled in the original 2026-03 app-design data model and has held since:
a repost is a `Post` — author = the reposter, **empty body**, `Reference::Repost {
target }` — content-addressed, signed, created through the ordinary
`fauna.posts.create` door and chronologically placed at repost time, so it appears
in the reposter's author feeds by construction and the bridge translators produce
the same shape inbound (nostr kind-6, AP Announce). What was never designed until
2026-08-10 is the *client-visible* half, three pieces ratified together because
they are one wire decision:

- **The carrier.** `query_feed` projects the repost target exactly as it projects
  the quote target: `write_post_index` writes a `content_links link_type='repost'`
  row (source = the repost post, target = the original, **actor = the reposter** —
  the actor column is what makes the viewer-state read below one indexed lookup),
  and the additive `FeedPostItem.reposted_post_id` / `PostSummary.reposted_post_id`
  carries it. The shared `Post::reposted_post_id()` accessor (twin of
  `quoted_post_id()`) feeds both the nest indexer and the client's decode paths, so
  the two ends cannot drift (§ The read model's no-drift rule).
- **The render.** A repost row renders as **attribution + the shipped `quoted-post`
  embed of the original** — the component ui.yaml has described as
  "quoted/**reposted** post display" since it landed. The body area is empty by
  construction; apps paint the i18n `feed.post.reposted_marker` attribution in the
  author header row and the original folds in through the same
  `RenderBlock::QuotedPost` embed-fold (`resolve_quoted_post`, which resolves
  either embed field — no new render machinery, no new walker variant). A repost
  row shows **no interaction bar and no own counters** (its own counters are
  structurally dark — nothing ever renders them), and **activating the card opens
  the ORIGINAL's `post_detail`**, never the empty repost's, where the full live
  interaction bar is one tap away. The own-post ⋯ actions menu stays (a repost is
  the reposter's own post; deleting it through the ordinary delete path reverses
  the counter identically to `unrepost`). The feed does **not** suppress an
  original that shares a window with its repost (the client never re-sorts or
  re-filters — § Anti-patterns); collapsing that duplicate is a future nest-side
  want, not a client job.
- **The viewer-state carrier.** Two additive per-viewer fields, projected per row
  for the connection actor (the feed handlers already authenticate one):
  `viewer_repost_id: Option<String>` — the id of the viewer's own live repost post
  naming this row's post (presence = "reposted by me"; the value is **exactly
  `unrepost`'s argument**, which is what makes `unrepost` reachable at all — the
  nest shipped it 2026-07-15 and no client could ever name the id it takes) — and
  `viewer_liked: bool` (the like/unlike arms already maintain a clean per-(actor,
  target) toggle row in `engagement_events`; the projection is a primary-key hit
  on `compute_toggle_event_id`). Both default-off, so an older nest renders as
  today. Bridged rows generally project neither (their interactions live in the
  origin protocol, the same reason their `counts` don't ride
  `PostInteractReply`). The like *button* becoming a toggle off `viewer_liked` is
  a per-app follow-on; the carrier is ratified here so it lands once, not twice.
  That follow-on's shared half landed 2026-08-11 as `FeedManager::like` — one
  verb, same door and same post id in both directions, since a like is
  *recorded* rather than composed (§ Implementation status today).

The verb is `FeedManager::repost(post_id)` — **one verb, toggle semantics** (the
shape ui.yaml's ios note always assumed and no wire could express):
`viewer_repost_id` absent → compose via `build_referencing_post(…,
ReferenceKind::Repost)` (empty body) and fold the created post's id into
`viewer_repost_id` locally (the create reply already returns it — no wire
change); present → `interact(viewer_repost_id, "unrepost")`, then read the
original's post-act counters back through the interact door (the native
non-toggle arm is a pure read that returns `counts`) and clear the field.
**No confirmation dialog**: a repost is cheap and instantly reversible by the
same toggle — confirm ceremonies are for destructive verbs. Two devices racing
the toggle converge (each repost post is individually unrepostable; the
projection serves the latest). Bridged sources keep the shipped
`interact(post_id, "repost"/"unrepost")` verbatim — the manager's existing
source routing decides, and no app leg knows.

The count fields are
`PostSummary.{like_count, reply_count, repost_count, quote_count}` (below),
which the nest projects from `content_meta` (§ The read model). See § *User
actions* for the increment path and § *Implementation status today* for the
rollout state — the counter columns **and** the live increment path both
landed 2026-06-27 (tier_3-proven by
`tests/e2e-unified/tests/api/test_engagement_counts.py`), so the counts are real;
per-app rendering (icon+count + the universal Quote button) has landed on
linux / android / apple / web / windows. A client talking to an **older** nest
that doesn't project the counts still shows 0 (additive + wire-default),
identical to a post with no activity.

Shows `feed-post-detail-dialog`, author, body, tags, attached image, quoted post.

- `create_feed` — opens on `click feed-create-feed-button`. Form with name, rule list (type + value + threshold + required toggle), add-rule, combination (all/any), create/cancel.

The two `TextAndNumber` types (Label Below / Label Above) are the only ones taking **two** inputs — `feed-rule-value-input` carries the category, `feed-rule-threshold-input` the 0–10 confidence — and `feed-add-rule-button` is gated on a **parseable threshold** for them, so the field is load-bearing, not cosmetic: without it the add button can never enable and those two rule types are uncreatable. That was the real state of every app until 2026-08-04 — the field rendered on six apps but carried **no test id anywhere**, and tui did not render it at all (a user had to know to hand-type `"spam:5"` into the category field). The id was user-approved and registered on all 7 apps 2026-08-04, and tui's field built in the same change. It survived unnoticed for the same reason as the gating bug below — the apple harness actuated the disabled button directly, so `test_create_feed_label_below_rule` passed for months while verifying a rule no user could create; see [`../architecture/apps/apple-e2e-automation.md`](../architecture/apps/apple-e2e-automation.md) § The actuation gate. The threshold prefills to the shared `fauna_client_feed::DEFAULT_RULE_THRESHOLD` ("5", the scale midpoint) rather than empty, so picking a label rule never presents an already-disabled add button.
  - *`feed-add-rule-button`'s full validity gate:* `fauna_client_feed::can_add_rule(input_kind, value, threshold)` — non-blank for `Text`, a parseable integer for `Number`, always-addable for `Toggle`, and BOTH a non-blank category and the parseable threshold above for `TextAndNumber`. Until 2026-08-13 apple was the *only* app enforcing this (its own `FeedCreateForm.canAddRule`); the other six let a user stage an empty/unparseable rule, which `build_filter_rule` then silently papered over rather than refusing — a blank category defaulted to `"spam"`, an unparseable count/threshold defaulted to `1`/the midpoint — so a junk Add staged a real, wrong rule instead of doing nothing. Lifted into shared Rust and consumed by tui / linux / android / web; windows and apple's own de-duplication onto the shared fn are entrusted.
  - *Create gating:* the `create-feed` submit requires **only a non-blank name** (plus the app's own in-flight guard). Rules and factor weights are independent, optional inputs of the same `create_feed` call — a **factor-only** feed (ranking with no filter rules) and a rule-only feed are both valid, so neither may gate submit. Apple additionally required ≥1 staged rule until 2026-08-03, which made a factor-only feed impossible to create there while web and linux allowed it; fixed onto this uniform shape (priorities #1/#4). It survived unnoticed because the apple e2e harness could actuate the disabled button directly — the find is the case study in [`../architecture/apps/apple-e2e-automation.md`](../architecture/apps/apple-e2e-automation.md) § The actuation gate.

## State & data shape

**Status: ratified 2026-06-14** (the feed-shape design pass). The Feed page renders from a single shared-Rust snapshot; no app open-codes post-list state (priorities #1/#2/#3).

### Where the snapshot lives

The feed snapshot + its mutating logic live in **`libs/fauna-feed`** as a `FeedManager`, the direct analogue of `fauna_conversations::ConversationsManager` (`libs/fauna-conversations/src/manager.rs:17`) — the established stateful-snapshot template the Conversations page already uses (ui.yaml `conversations.state_fields` are "derived from fauna-conversations' ConversationsManager snapshot"). It mirrors that shape exactly:

- `FeedManager::snapshot() -> FeedSnapshot` (the `ConversationsManager::snapshot()` analogue, `manager.rs:47`) — a cheap clone of current state.
- `FeedManager::add_observer(Arc<dyn SnapshotObserver>)` / `clear_observers()` — the same `SnapshotObserver` reactivity trait (`libs/fauna-conversations/src/observer.rs:7`); the manager `notify()`s after every state mutation and the view re-reads via `snapshot()`. No client-side caching of post lists (§ Architectural rules).
- One async method per user action (§ User actions), each driving the WS-RPC call, then mutating state + notifying.

`FeedManager` is constructed over the already-shipped transport client `fauna_client_feed::FeedClient<R: RpcRequester>` (`libs/fauna-client-feed/src/lib.rs:44` — the thin, WASM+UniFFI-safe `fauna.feed.*` call surface), so the manager owns *state + projection logic* and the client owns *transport*. The manager is exposed to native apps via a `#[uniffi::export]` façade in `libs/fauna-ffi` and to web via `fauna-wasm`, exactly as `ConversationsManager` is. `libs/fauna-feed` keeps its existing badge logic (`classify_sources` / `SourceKind`); the snapshot is the second thing it grows — the home `lib.rs:13-18` already reserves it.

### The read model — where the visible list is computed, and where post bytes are read

Two layers, both Rust, neither in app glue:

1. **Nest-side selection / filter / sort / FTS / pagination.** The visible post list is computed on the nest by `query_feed` / `query_feed_scored` / `query_feed_for_authors` (`bins/fauna-nest/src/db/feeds.rs`), reached via `fauna.feed.posts` (a custom feed) and `fauna.feed.local.posts` (this nest's local feed) (`bins/fauna-nest/src/feed_handlers.rs`; shared `*_core` fns in `feed_routes.rs`). The nest translates the feed's shared `fauna_core::scoring::FilterRule` set into the index query — **rule evaluation is the nest's SQL** ("shared Rust" is satisfied because the rule *type* and *encoding* are shared and the single evaluator is the nest; no client re-filters), applies the chronological (`created_at` micros) or score (`order=score`, micro-units) ordering — where a feed carrying a **composition** (frame § Composition, landed 2026-07-08) orders by the composed key `Σ (weight_permille · factor_value) / 1000` over the `content_scores` bus (JOIN by `content_id` alone; a factor with no row — including any sealed tier-1 factor the nest cannot read — contributes 0, the nest-side seam) with `"engagement"` = `content_meta.score` expressed per-mille, and a feed without one orders by the legacy single nest-computed score, folds the optional `search` term in as a `BodyContains` filter (**search is a re-query, never a client-side filter over the loaded list**), and paginates by cursor. A `discovery`-scoped feed additionally aggregates contributor nests via `fauna.federation.feed.query` + `peer_query.rs`, merged nest-side; the home nest hands the client one ordered stream.

   **`created_at` is bounded only going forward — at every door that writes a remote-asserted one.** `content.created_at` is the column this read model sorts on, and the local feed serves it to every local user, so a value dated ahead of the nest's own clock would pin its post atop the chronological feed until real time caught up. Every door that writes an author's, a peer's or a bridged server's `created_at` into it therefore refuses one too far ahead (`bins/fauna-nest/src/storage/mod.rs`) — **one comparison, two cushions (ruled 2026-09-15):**

   - **A Fauna-native post — ~2 minutes** (`reject_future_created_at`): a post a Fauna author's client signed, whether it arrives at the local `fauna.posts.create` door, on the federation forward leg, through the trend-exchange fetch, or as the discovery poller's index stub (whose `created_at` is the peer's own unsigned claim).
   - **A bridged foreign-protocol plane — ~1 hour** (`reject_future_bridged_created_at`): the ActivityPub inbox's `Create` and `Update{Note}` (a Note's `published`) and the Nostr sweep (every kind but the NIP-59 gift wrap, whose timestamp is randomized by design — [`nostr.md`](nostr.md) § Implementation status today). There the value is a remote server's or client's clock and a refusal is silent to its author, so the cushion is the drift this nest already allows a remote clock (the ActivityPub inbox's signed-`Date` window, [`../behavior/activitypub.md`](../behavior/activitypub.md) § Security posture): a tight one would silently drop an honest peer whose clock drifts, and an hour still ends the pin.

   Both **refuse, never clamp**: rewriting a translated post's date changes the hashed post every replay re-derives, and clamping only the column leaves each re-derivation from the body (a restore, nest-link replication) to reopen the pin. The comparison is made in the timestamp's own unsigned domain, so a value past `i64::MAX` is refused rather than wrapped negative. **The doors are enrolled mechanically, not listed:** the census test `every_content_created_at_writer_is_partitioned` walks every production writer of the column and requires each to be classified — a bounded door (its bound call held to the code), a relay whose own callers are walked in turn, the SQL itself, or a writer no remote value reaches (the nest's own clock, another plane's row, replication inside one deployment) — so a new door fails there until someone decides which it is. **The owner's own backup restore is the one door that never refuses:** a future-dated own post is the user's data. The past stays unbounded: backdating and an archive import's original, long-past `created_at` ([`../behavior/archive-import.md`](../behavior/archive-import.md) § What each category becomes) sort exactly where they say. **The bound is a DOOR rule, and no boot pass may re-litigate it at rest:** a stored value that passed its door is final, so any at-rest pass that would rewrite `content.created_at` by magnitude — the one such pass that ever existed, the reconcile of the three units three writers disagreed on until 2026-08-03, ran one-shot behind its own marker row and retired with the 2026-09-24 genesis of the nest schema — must be **one-shot behind its own marker row**, because a repeating one cannot tell a legacy seconds value from a legal 1970-1973 microsecond instant and would lift the latter centuries into the future, past every door's bound and atop the chronological feed for good.

   **The score-order cursor is a compound keyset cursor** (`(score_cursor, score_cursor_created_at)`, both echoed from the previous reply; ratified + landed 2026-07-11). The scored sort is `ORDER BY key DESC, created_at DESC`, so the cursor must carry **both** the boundary row's ordering key *and* that row's `created_at`: resume on `key < k OR (key = k AND created_at < ts)`. A key-only cursor is not a position in a compound sort — it silently **skips every row tied on the boundary key**, and it fails to advance *at all* when the key is flat. Flat keys are not exotic: a composition of only **sealed** tier-1 factors (the canonical trained-topic feed — [`../behavior/topic-factors.md`](../behavior/topic-factors.md) § Scoring) has every nest-side term 0 by the zero-term seam, so a key-only cursor dead-ends such a feed after one page. With the tiebreak the flat-key case degenerates to plain chronological keyset pagination, which is the correct order for a flat key. `score_cursor_created_at` is additive on `fauna.feed.posts` (request + reply): an older nest ignores it, and a client that sends the key alone still advances on the legacy strict predicate (re-inheriting its tie-skipping). Pinned by `bins/fauna-nest/tests/composed_feed.rs` (`composed_cursor_does_not_drop_posts_sharing_the_boundary_key`, `a_sealed_only_composition_paginates_to_completion`) + `scored_feed.rs` (`a_key_only_cursor_still_paginates_for_a_pre_keyset_client`).

2. **Client-side snapshot assembly.** `FeedManager` calls the kind for `selected_feed`, maps each `FeedPostItem` → `PostSummary` (micros→millis on `timestamp`; `classify_sources(source)` drives badges; `quoted_post_id` drives the embed; `media_hash` starts `None`, resolved lazily per `has_media` post by `resolve_media` — the blob hash lives in the post *body*, which the feed-index projection deliberately never reads, so it costs one `fauna.posts.get` + decode, the same per-post augmentation as the quoted-post fallback), appends each paginated page onto `posts` **deduplicating by `post_id`** (the only dedup the client does — guarding the cursor-boundary repeat case), **preserves the nest-supplied order** (never re-sorts — § Anti-patterns), sets `has_more` from the returned cursor, and `notify()`s. The embedded quoted-post card is projected by a shared `libs/fauna-feed` helper from the already-loaded post set (falling back to a batched `fauna.posts.get` for a quote outside the loaded page) — the single shared quoted-post projection that retires the per-app divergence.

**A REFRESH keeps the posts on screen until the new page lands; only a SWITCH clears them up front (ratified 2026-08-28).** `reload` claims a generation, then re-queries — and what it does to `posts` *before* the fetch depends on whether the query changed. A **switch** (a different `selected_feed`, Trending, a changed `search_query`) clears the list immediately: feed A's posts under feed B's header is a lie, and the reader must never see one. A **refresh of the query already on screen** (the reconnect re-hydrate, the post-submit refresh, a manual pull) must NOT clear: those posts are still true, and the landed page replaces the list wholesale anyway, so the list still converges — a post deleted server-side does not linger. The manager decides this itself, by comparing the query it is about to run against the one the current posts were committed for (`loaded_query` = `(selection, search_query)`, written on the Ok arm only), rather than each caller passing a flag it could pass wrongly. **Why it is a rule and not a preference:** clearing up front means any refresh whose fetch never lands strands the reader on an EMPTY feed with `status = Loading`, no `error` to explain it, and nothing that recovers — an app suppresses a second re-hydrate while the first is still running, so the blank persists until the user navigates away. That is a real state on a flapping connection (a nest flip, a bearer re-mint), it costs the user their whole timeline, and it is invisible to any test that only asserts the *end* of a healthy reload. Pinned at tier_1 by `manager.rs::a_same_feed_refresh_keeps_its_posts_while_the_fetch_is_in_flight` and its twin `a_switch_clears_its_posts_while_the_fetch_is_in_flight`, which park the fetch at the mock's reload-race gate and read the list; and end to end on tui, web, linux, macos, ios and windows by `test_feed.py::test_a_refresh_keeps_the_posts_on_screen_and_only_a_switch_clears_them`, which parks the real reload at the manager's test-only one-shot hold (`FeedManager::hold_next_reload_for_test` — the reload publishes the list it kept or cleared, then waits for `release_held_reload_for_test` before fetching) and reads the page while a Feed-tab re-entry and a typed search are each in flight. While a hold is armed, an app's e2e agent starts a feed op without awaiting it: a held reload cannot land until it is released, so an awaited trigger would park the agent with it. That is why this is a client-side hold and not the nest's reply hold (`helpers/rpc_hold.py`, `bins/fauna-nest/src/rpc_hold_test_hook.rs`, which serves the pre-fetch windows): an agent that awaits the reload cannot tell a held reply from a slow nest, so it would park on it; a hold the manager owns is one the agent can read (`reload_hold_armed_for_test`) before it decides to await.

**Where post *bytes* are read from — the load-bearing decision for the posts at-rest segment-store rollout.** `query_feed` and its siblings read **only the feed-index projection** — the floor columns (`content.{id,author,created_at,source}` + `content_meta.{has_media,is_reply,score,reply_count,repost_count,quarantined,suppressed}`), the tags (`content_links`), the list-card preview (`content_meta.preview` — *The list-card preview* below; until 2026-09-29 the FTS body doubled as the preview store, which no bridged post has), the SQLite-FTS body index (`content_fts`), and the classifier scores (`content_labels`). **They never read `content.payload` (the post body bytes)** — verified against `feeds.rs::query_feed`'s `SELECT`. The full body is read by several single-post paths — `fauna.posts.get`/`get_post_core`, post-reference resolution, the ActivityPub outbox, video manifests, export, moderation, federation-get, and web-content rendering — but **never by `query_feed`**. (Pre-cutover, production stored post bodies inline in `content.payload` for ≤64 KiB and spilled larger bodies to the blob store via `payload_store`; the cutover retires both for posts.) Therefore the posts segment-store rollout (`docs/goal/architecture/message-segment-store.md` § Implementation status today) moves **only the body bytes** (`content.payload` → opaque records in `__post/<actor_hex>`) and **retains the nest-maintained feed-index projection** (the `content` floor columns + `content_meta` + `content_fts` + `content_links` + `content_labels`, rebuildable from segments on recovery exactly like `segment_records`) as the read model `query_feed` scans **unchanged**. Single-post detail reads the body from the segment by CID instead of `content.payload`. This is the **mail template applied to posts**: mail bodies live opaque in `__mail` segments while the `segment_records` mirror + IMAP placement serve the hot reads; for posts the hot read is the cross-actor feed query, which runs off the projection, not the body. The cutover (write + read flip landed 2026-06-15, `segments::post::{store_post,load_post_body}`; tier_3 `segment_post_cutover.rs`) moved the body-byte authority into the `__post` segments while **retaining** the `content` projection row with an empty `payload` — unlike the conv cutover (which dropped its legacy `content` rows entirely), posts keep the row because `query_feed`'s read model lives there. A reader resolves a body **segment-first**, falling back to `content.payload` for the one shape that rests inline: a body `store_post` cannot decode has no author, so no segment scope. Every other post rests in its author's `__post` segment and is segment-backup-eligible. (The 2026-06-16 boot back-fill that moved pre-cutover inline bodies into segments retired 2026-09-25 with the nest schema's genesis (`compat-remnant-sweep.md` § Program 4) — no pre-cutover post rests anywhere.) The projection stays capability-appropriate by construction — `content_fts` indexes only plaintext-readable bodies (public bodies + restricted previews everywhere; full restricted bodies only where the nest holds the relevant keys, built by a reception-time transient-decrypt with the body itself resting sealed — **target; today the restricted *preview* only, § Encryption at rest → Implementation status**), and the cross-actor projection over *public* post floor is **not** a "cross-user index" violation (that rule, `content-index.md`, governs the per-user Tantivy index — a different mechanism from this SQLite-FTS feed index; the feed is a public social read by design).

**The list-card preview is a column of the feed-index projection, never a lookup into the Search corpus (ruled 2026-09-29; built the same day — § Implementation status today).** Until this ruling `query_feed` and its two siblings (`query_feed_scored`, `query_feed_for_authors`) filled `body` by a correlated subquery into `content_fts` keyed by the post id — the FTS row `insert_and_index` writes for a native post doubled as the preview store — and every bridge-ingested post reached every app with an EMPTY list card: ActivityPub, nostr and Bluesky all store through `segments::post::store_post` with a `source`, whose projection writer (`put_post_with_source_index_only`) writes no FTS row, and the bridge Search corpus keys its rows by `blake3(content_type:natural_id)`, never the post id. The coupling was accidental, so the rule is: **`content_meta.preview`** — a nullable additive `TEXT` column (`../architecture/nest/common.md` § Upgrade safety lands it on a long-lived `/data` without a hand `ALTER`) holding the first 500 characters of `Post::body_text()`, **exactly the string the native FTS row indexes today**, so the projection holds no plaintext it did not hold before (a gated post's preview is still its public preview; bridged text is foreign public content, readable class 1 of `../architecture/encryption-at-rest.md` § Readable classes, so sealing constrains nothing here) — carried on `PostMetadata` and written by `write_post_index`, the one funnel every feed-visible post passes (native, all three bridges, the segment restore), so a writer can no more mint a card without its text than without its `content_meta` row; a census test enrolls every production `content_meta` writer the way `every_content_created_at_writer_is_partitioned` enrolls the `created_at` doors. The three feed reads take `COALESCE(cm.preview, '')` and the FTS subquery goes; the one-shot backfill for rows written before the column (a version-guarded `run_migrations` step, the shape its retirements already take) copies each `post/%` FTS body into the NULL previews, so the read never falls back to the corpus and a media-only post's `''` is distinguishable from a pre-column row's NULL. **Why not the two alternatives:** FTS-indexing bridged posts under `post/%` by post id would put every bridged post into `content_fts` outside the per-bridge show-in-search control and its newest-N cap — the cap exists precisely so a firehose-grade bridge cannot balloon the FTS table ([`../behavior/content-index.md`](../behavior/content-index.md) § Bridge content in the Search corpus), and a query-time source filter would turn a structural control into a filter; and an app-side `fauna.posts.get` for each empty-bodied card is a per-card round trip on all 7 apps against this section's founding rule (list cards never read bodies). **Corollary — the feed's text filters over bridged posts read the Search corpus, because it is the only text index of bridged content there is.** `BodyContains` / `BodyExcludes` rules — and the page's search, which `feed_routes::search_to_filter` folds into a mandatory `BodyContains` — matched only `content_fts` rows of a `post/%` schema by post id, which a bridged post never has, so until this corollary no keyword feed and no feed search ever showed one. A second, unbounded text index of bridged posts is exactly what the cap forbids, so those filters reach a bridged post through its corpus row: `bridge_index_map` gains the post's `content.id` beside the blake3 key (nullable — the nostr relay-store plane indexes events that hold no post row), and the filter's `IN` admits a `bridge.%` row through it. The consequence is by construction, not a preference: with show-in-search OFF for a bridge, or past its cap, its posts match no text filter; the preview column above is untouched by either control — the card always shows its text.

**Opening a post the timeline never loaded — the deep-link resolve (ratified + landed 2026-08-10).** `post_detail` was designed against a `post-card` click, where the post is in `posts` by construction. A **search result row** is the first caller that can name a post the feed query never returned (`../ui/search.md` § Where logic lives → *Result navigation (deep link)*): older content, an account the viewer doesn't follow closely, anything past the loaded page. A detail surface reading `snapshot.posts` alone then paints a blank dialog. So the manager owns a single-post resolve — `FeedManager::resolve_post(post_id)` — with these ratified properties:

- **Where the post lives: one `deep_linked_post` slot beside the list, never inside it.** Pushing a deep-linked post into `posts` would corrupt the load-more cursoring, surface a post the user never scrolled to *in their feed list*, and lose it again on the next `reload` (which replaces the list wholesale). **Exactly one slot** — a detail surface shows one post at a time — so there is no cache to grow and **no eviction policy to get wrong**; re-opening the same post is free, alternating between two costs one fetch each, and the slot is cleared whenever the timeline already covers the post. This is deliberately *not* the `resolved_quotes`/`resolved_previews` unbounded-map shape: those fold into many list rows, this renders one surface.
- **The read is `fauna.posts.get` + decode**, the same single-post door `resolve_quoted_post`'s out-of-page fallback uses. Because it decodes the **raw signed envelope** it knows more than a list card does — the full body (not the 500-char FTS preview), a real `Verified`/`Failed`, and the media hash without `resolve_media`'s second fetch. It cannot know what only the feed-index projection holds: interaction counters, content labels, the web-publish slug, the protocol source, or the per-viewer pair (`viewer_repost_id`/`viewer_liked` — same class, deliberately not carried by the deep-link door). None of those are in ui.yaml's `feed.sub_pages.post_detail` element scope; a surface that grows to need one needs the wire to carry it, never a guess client-side.
- **The projection must not drift from the nest's indexer.** `has_media` / `is_reply` / tags / `quoted_post_id` are shared `fauna_core::data::Post` accessors (`has_media()`, `is_reply()`, `indexed_tags()` — lowercased, the spelling `content_links` holds — and `quoted_post_id()`), used by **both** the nest's `extract_post_metadata` and the client's `map_fetched_post`, so the same post reads identically whichever door opened it (priority #2/#4).
- **The rendered set is timeline + slot, everywhere.** `FeedSnapshot::rendered_posts()` / `find_post()` are the one definition of that union: every per-post lazy resolve (media, quote fold, link preview, unlock offer, muted-keyword collapse) and every unseal writes through it, so a deep-linked post gets the same treatment as a listed one. *Ranking* paths deliberately do not — the scored window, exemplar picking and re-rank read `posts`, because a deep-linked post holds no position in the ordered list.
- **A legally-taken-down post resolves to `PostResolution::TakenDown { reference }`, and the slot takes a tombstone `PostSummary`** (refinement built 2026-08-10). The nest withholds its body from every viewer, so there is no *post* to project — but there is something to render, and it belongs where the post would have been. `resolve_post` therefore parks `PostSummary::taken_down(post_id, reference)` in the slot (id + `legal_takedown_ref`, everything else `Default`: no body, no author, no timestamp, `verification` `Unchecked` because nothing was withheld-then-verified), so `find_post` answers for the requested id and each app branches on `legal_takedown_ref` to paint `fauna_core::obligation::legal_takedown_tombstone(reference)` **in the body area, in place of the post** — the third surface of the one concept, beside the quoted-post embed and the DM bubble (`../behavior/moderation.md` § Legal takedown owns that surface list). The page error surface no longer stands in for a body. The outcome is still returned, because a caller may need to skip work a live post would have earned (tui skips the gated-unseal leg on it). *Replacing* the slot is what protects the property the earlier clear-the-slot shape existed for — no earlier post may sit on screen under a different post's takedown notice — and protects it strictly better than emptying it did.
- **A gated deep-linked post unseals exactly as an on-screen one does.** The resolve and the unseal are ordered legs of one detail-open door, because a post outside the timeline has no snapshot row to ask "is this gated?" of until the fetch lands.

### Feed-rule types

User-defined feeds are filter rules over the post stream, with a top-level
combination mode (`All` — every rule must match — or `Any` — at least one).
The supported rule types are:

| Rule type | Input shape | Example display |
|-----------|-------------|-----------------|
| Has Hashtag | comma-separated tags | `#rust, #fauna` |
| Protocol Source | comma-separated protocols | `source: fauna, bluesky` |
| Has Media | required yes/no | `media: yes` |
| Is Reply | required yes/no | `reply: no` |
| Min Replies | number | `replies >= 5` |
| Min Reposts | number | `reposts >= 3` |
| Created After (hours) | number (hours) | `age < 24h` |
| Body Contains | comma-separated terms | `contains: fauna, mls` |
| Body Excludes | comma-separated terms | `excludes: spam` |
| Label Below | category + threshold (0-10) | exclude posts above a confidence threshold for a label category (e.g. spam) |
| Label Above | category + threshold (0-10) | show only posts above a confidence threshold for a label category |

Rule evaluation is shared Rust per the architectural rules — same semantics
on every app. Rule *encoding* (form input → wire JSON) is shared too — see
*Where logic lives*.

### Post creation — own-write (ruled and built 2026-09-22)

`fauna.posts.create` creates only the caller's OWN post: the envelope signature verifies against `post.author` (or a delegated authoring sub-key's `Capability::Post` cert chained to it, `atproto-pds-full.md` D10), **and** `post.author` **is** the connection actor. Another account's validly signed post is refused as `fauna.posts.ingest_failed` with reason `post_uploader_not_author`, and nothing is stored. This is the profile door's own-write rule and the create twin of *Post deletion*'s second author check below. Everything the create keys on the caller inherits it: the private-mode forward queue's author stamp (which that author's account deletion purges by — `account-data-plane.md` § Nest-side requirements item 1), the bridge fan-out, and the interaction counters' engagement rows. User-class only (`bridge_method_allowlist`). A bridged post enters through its bridge's own kind, which builds the post under the bridged account's own id and runs the same ingest. A post arriving from a paired nest on the federation forward leg is not a create and does not pass through this door.

### Post deletion (ratified 2026-07-15)

Self-service "delete my own post" — the author-only destruction verb. This subsection owns the wire shape, authz, and removal semantics; the Nostr kind-5 derivation is owned by [`nostr.md`](nostr.md) § The relay event store (NIP-09), and moderation removal / legal takedown are owned by [`moderation.md`](../behavior/moderation.md) (different verbs — they gate serving; this one destroys).

- **The verb is DELETE, not hide.** The author's post is destroyed on their nest: the body bytes are tombstoned in the `__post` segment (reclaimed by compaction — the sanctioned removal mechanics) and the feed-index projection rows (`content` + `content_meta` + `content_fts` + `content_links` + `content_labels`) are removed, so the post vanishes from every feed query and `fauna.posts.get` returns `not_found`. This is the *user always controls their data* invariant's delete affordance — user-initiated destruction of the user's own content is the one sanctioned "data loss". A "hide my post from some audience" wish is an *audience* change (gated tiers), never this verb; the moderation flags (quarantine/suppress) and `LegalTakedownMarker` likewise gate serving without destroying — three verbs, three owners, no overlap.
- **Wire:** `fauna.posts.delete` carries the embed-as-bytes wire of a signed `fauna_core::data::Tombstone { author, post_id, created_at }` (sign-over-CID envelope, the same discipline as `Post`/`Profile` — `serialization.md`; signed-only, no bare fallback on this new surface). Reply `{ post_id, deleted }` — `deleted:false` is the idempotent already-gone success, never an error. Replay-safe (the end state is idempotent); User-class only (`bridge_method_allowlist`).
- **Authz — three author checks, all required:** the envelope signature verifies against `tombstone.author`; the connection actor **is** `tombstone.author`; the stored post's author (segment-record scope, or the decoded body's `author` for a legacy non-segment row) **is** `tombstone.author`. A mismatch is `permission_denied`; only the author self-serves deletion.
- **Removal order (crash-safe):** the projection rows go first (the serving gate — after this, `get`/feeds are correctly dark), then the segment-record tombstone (`segments::post::tombstone_by_cid`), then the interaction-counter reversal: for each `Reference::{Reply,Repost,Quote}` the deleted post carried, the *target's* counter decrements via the `engagement_events` dedup log (the exact mirror of `record_reference_engagements`; idempotent). A crash between steps leaves only an unreachable-but-live segment record (reclaimed on a delete retry; never a servable half-state). Trending: the removed `content_meta` row withdraws the signal at the trend sweep's next re-probe (≤15 min); an immediate-withdraw hook is a named follow-on.
- **References TO the deleted post dangle by design** (replies/quotes by others survive; their embedded target renders as the existing not-found state client-side) — deleting must never destroy other authors' content. **The not-found embed is one shared fold (built 2026-09-21):** the quoted-post resolve folds a `RenderBlock::QuotedPost` carrying `not_found: true` (empty author and body) for a target the nest answers `fauna.posts.not_found`, caches it like any resolved quote, and an app paints `feed.post.post_not_found` in the embed's place — never a blank embed, and never nothing, which would read as a quote of no post. A transport failure folds nothing (the next notify retries). On the deleting device the delete itself does the same, before any refetch: `FeedManager::delete_post`, once the nest confirms, replaces the resolved embed of the deleted post in every loaded card that quotes or reposts it, because that device resolved the embed from its own loaded page and would otherwise keep painting the words it just deleted.
- **Propagation (target): a deleted post must not outlive its derivations.** Every surface a post creation fans out to needs the matching delete leg: the paired public-nest replica (`spawn_replicate_post`'s tombstone twin), the forwarded-post outbox (`maybe_enqueue_outbox` twin), the Nostr relay materialization (native kind-5 — **BUILT 2026-07-15**, `nostr::propagate_post_delete`, `nostr.md` § The relay event store, NIP-09), the Bluesky write-through record, the ActivityPub `Delete` activity, and — for a still-web-published post — its rendered static page (`../behavior/web-content-hosting.md` § Routing, render, serving: a re-render fired from `delete_post_core` right after the projection delete, gated on the post having a live `web_published` link so an unpublished post's delete renders nothing). A leg that fails must not strand the derivation: every outward leg (steps 3b–7 of `delete_post_core`) runs again on a retry that finds the post already gone, gated on the post-delete `tombstone/post` witness naming the retrying actor, and the two legs whose first attempt can give up for good — the Bluesky write-through delete and the paired-replica twin — are re-driven with no retry at all by `post_delete_redrive`: an hourly pass (the first at boot) over the write-through mappings and `worker_replication` post markers whose post is gone, plus a replica replay at every worker connect. An author whose delete answered `Deleted` has no reason to retry, so the retry alone is not enough. Per-leg build status lives in § Implementation status today — unbuilt legs are gaps to close, not accepted behavior.
- **A deleted post is never re-ingested by replay (ruled 2026-09-29).** The post's signed bytes outlive the delete wherever anyone kept them: they were public, and under the default `open` submission policy any peer may relay a validly-authored post ([`../architecture/nest/private-mode.md`](../architecture/nest/private-mode.md) § Post Forwarding step 2). So every door through which a *peer* hands this nest a post's bytes checks one shared predicate first — **this nest has seen the post deleted** — and a post it has seen deleted is not stored, indexed or fanned out again: `fauna.federation.post.forward` answers `Ok` and does nothing (the peer learns nothing and stops retrying), and the trending exchange's import-triggered fetch ([`../behavior/trending.md`](../behavior/trending.md) § Import-triggered public-post fetch) neither fetches nor ingests it. The predicate is **the `tombstone/post` witness row present AND no `content` row at the post id** (`CacheDb::post_was_deleted`): step 1 of the removal order writes the witness in the same transaction that removes the projection, so it is the one durable per-post trace a delete leaves. The `content` half is load-bearing: a legal takedown writes the same witness over a still-live post ([`../behavior/moderation.md`](../behavior/moderation.md) § Legal takedown), and a taken-down post is withheld, not deleted — its replay finds the post still stored and is the ordinary idempotent no-op. Takedown then author delete leaves the witness and no post, so it reads as deleted. The local `fauna.posts.create` door is **not** gated: it is own-write (§ Post creation), so no stranger can replay through it, and an author uploading their own signed post again is the author's own act.
- **Client:** the delete *call* is shared (`PostsClient::posts_delete`; the caller builds the signed tombstone bytes with `sign_and_pack`, exactly as compose builds signed-post bytes); the confirmation *affordance* is app glue. **IDs user-approved 2026-07-16** — `feed-post-delete-button` (indexed, inside `feed-post-actions-menu`, gated `is_own`) + `feed-post-delete-confirm-button` (destructive confirm step), mirroring the shipped `dm-message-delete-button`/`dm-message-delete-confirm-button` conversations pattern verbatim (ui.yaml `feed-post-actions-menu` component). `feed-post-actions-menu`/`feed-post-actions-button` themselves are still target-state for the *unrelated* trained-topic-factor training verbs (topic-factors.md § Authoring surface) — delete's rollout is independent and does not wait on that.

- **Feed rule evaluation** (which posts match a user-defined feed). **Shared Rust — the single evaluator is the nest** (`bins/fauna-nest/src/db/feeds.rs::query_feed`, translating the shared `fauna_core::scoring::FilterRule` into the index query). ## Persistence

**Status: ratified 2026-06-14.** Two distinct things persist, at two different layers:

- **Feed definitions** (name, rule set, combination, scope, contributor seeds) persist **nest-side**, owner-keyed, in the `feeds` table (`bins/fauna-nest/src/db/feeds.rs` — `create_feed` / `update_feed` / `delete_feed` / `list_feeds_by_owner`, all scoped on `owner`), mutated only through the `fauna.feed.{create,update,delete}` kinds. They are server-state, not client-local: every one of the user's devices reads the same feed list via `fauna.feed.list`. This is the correct home (not the sealed account-state plane) — a feed definition is shared user state, and the nest must read the rules to evaluate `query_feed`. Discovery-feed contributors persist in `feed_contributors` (same module), mutated via `fauna.feed.contributors.*`.
- **The user's selected feed** is **per-device view state**, not synced configuration. `FeedSnapshot.selected_feed` defaults to `None` (the nest's local feed) on launch; an app MAY persist the last selection locally as a UI convenience, exactly as the Conversations page treats its selected thread. It is deliberately *not* written to nest state / the account-state plane — it is not "nest configuration set from apps" (the product invariant), it is a view preference like which tab is open. No genuine tradeoff here; the uniform answer matches the other pages' per-device view state.

Compose drafts (the in-progress `FeedComposeState` for an unsent post) rest in the `__drafts` reserved folder per [`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § Drafts Sync — that section is the at-rest authority — at the ratified rail `path = "posts"`, sealed under the owner's `BackupKey` (the owner-only key defined in [`../architecture/owner-key-material.md`](../architecture/owner-key-material.md) § Audience: owner only Path A). **The serialised shape is now settled** (2026-08-15; it was previously deferred here to "the future `libs/fauna-feed` crate's design", which now exists as `fauna_feed::drafts::PostDrafts`), on three rules:

- **One slot, no draft ids.** The composer is a single surface (`FeedSnapshot.compose`), so the rail's blob is one record — unlike the conversations rail, which carries a per-thread map plus a new-thread slot. Nothing assigns or needs a draft id.
- **Only user-authored input rests.** `text`, `tags`, `attached_file`, `gate_tier`, `gate_preview`, `sell` and `gate_room` survive (`gate_room` omitted from the bytes when absent, so a draft with no room is byte-identical to one written before the field existed); `error` and `submitting` do **not**. The latter two describe one app run's attempt to post, not what the user wrote, and persisting `submitting` would restore a composer that is disabled with no gesture that clears it. The at-rest record therefore *enumerates* its fields rather than embedding `FeedComposeState`, so a field added to the composer later cannot silently become at-rest data. ⚠ This rule now holds on **both** rails: the conversations rail embedded its whole `ComposeState` including the transient `SendState::Sending` — a defect of the same class, **fixed 2026-08-16**. Because that rail's blob had already shipped it could not adopt a separate enumerated record (dropping a key would blind un-updated apps); it enforces the same property through a normalising constructor instead. [`../behavior/conversation-drafts.md`](../behavior/conversation-drafts.md) § Persistence owns that rail's shape.
- **Attachments by content address — and a restored draft's attachment is a handle, not a file: its submit refuses rather than posting without it (ruled 2026-09-14, the one concept both rails share).** A draft carries `AttachedFile`'s `{name, size, blob_hash, media_type}` — never bytes (`libs/fauna-feed/src/compose.rs::AttachedFile`). On this rail the blob is uploaded only by the submit itself ([`media.md`](media.md) § Encryption at rest → *Submit-time upload*), so a resting draft's file is almost always `blob_hash: None`, and its bytes live only on the device that picked them: a draft restored after a relaunch, or synced to the user's other device, names a file that device does not hold, with no coordinates to fetch it from. **Every submit path refuses such a handle** — `submit_post`, the tier and room arms of `prepare_gated_blob`, and `prepare_sell_post` each test `attached_file` itself (`Some` with no `blob_hash`) before staging, sealing or minting anything, stamp `feed.compose_attachment_missing` naming the file on `compose-error`, and keep the draft, so the author attaches the file again (or another) and submits; the text is never published alone, and a sale never mints a tier for it (`FeedManager::refuse_unresolved_attachment`; pinned by the four `*_refuses_a_restored_attachment_*` tests in `libs/fauna-feed/src/manager.rs`). This retires the text fallback `submit_post` used to take for an unresolved hash: a post going out without the file the author picked, with no word to them, is exactly the harm [`../behavior/conversation-drafts.md`](../behavior/conversation-drafts.md) § Persistence's refusal exists to prevent, and a `Some` without a hash now errs in `media_item_from_staged` too, should a future caller skip the refusal. **The app duties that make the refusal reachable:** an app stages a pick on the manager the moment it is made, as its hash-less handle (`{name, size}` — no bytes, no upload), so a draft saved before the submit carries the file at all: a pick the app keeps to itself until the submit is lost on relaunch with nothing left to refuse. It carries the manager's own `attached_file` through every `update_compose` it makes while holding no bytes of its own — at a keystroke and at submit alike — and stages `None` only as the user's remove gesture; a fresh pick replaces the handle, and the submit's upload resolves its hash. Staging `None` "because this device holds no file" *is* the silent drop. **The compose bar shows the handle and lets the author drop it:** `compose-file-ready` renders off the snapshot's `attached_file`, never only off the app's own pick, naming the file and its size (the shared `fauna_core::format::byte_size` — the shape of conversations' `dm-compose-attachment-chip`), and `compose-file-remove` beside it stages `None`; so the refusal never names a file the bar does not show, and dropping a restored file never takes attaching another. Which apps do which is § Implementation status today. The conversations rail's `AttachmentDraft` differs only in mechanism (its bytes wait in an in-memory store; here the app holds the pick), and [`../behavior/conversation-drafts.md`](../behavior/conversation-drafts.md) § Persistence owns that rail's refusal.

The blob is byte-stable for equal logical state, which is what lets `DraftsSync` skip re-uploading an unchanged draft to the user's other devices.

## Errors & edge cases

- Every page exposes `error-message`; tests read it via `app.error_text()` / `app.has_error()`.
- Composer-specific errors render into `compose-error`; staged-file confirmation renders into `compose-file-ready`.
- Empty states (no feeds, no posts in selected feed, no search results) are **snapshot-derived, not per-app checks**: `FeedSnapshot.status == Loaded && posts.is_empty()` is the empty state, and the shared `FeedSnapshot::empty_state()` (`libs/fauna-feed/src/snapshot.rs`) is the one place that decides it and picks the variant — apps render the copy off its answer, never re-derive it. **Two elements, at most one present at a time (user-approved 2026-09-25):** `feed-empty-state` (copy `feed.list.no_posts`, "No posts yet.") when no search is active, and `feed-no-results` (copy `feed.list.no_matching_posts`, "No matching posts.") when a `search_query` is active. Both are **absent** while a read is in flight (`status != Loaded`) and whenever posts are on screen, so a test tells loading, empty and populated apart off element presence alone, never a timer. Built on tui, macOS, iOS, windows and android; the copy strings render as unlabelled chrome on web and linux (§ Implementation status today).
- Loading states are `FeedSnapshot.status == Loading` (initial fetch) and `has_more` + an in-flight paginated fetch (the manager exposes a `loading_more` flag if a spinner-at-bottom is wanted); no per-app loading bookkeeping.
- Network failures during a feed query / post submission / bridge subscription set `FeedSnapshot.error` (page-level) or `FeedComposeState.error` / `BridgeFormState.error` (form-scoped) to a `LocalizedText`. **Retries are manual** (the user re-triggers the action) — automatic retry is not introduced here; the snapshot surfaces the failure and the affordance to retry, consistent with the other pages.

## Architectural rules

1. **Observer-driven rendering.** Once `feed_snapshot()` exists, the app subscribes to the feed object's observer and re-renders on every notification. No client-side caching of post lists.
2. **No per-stage view-model.** A thin proxy over the shared snapshot is the only state the view layer holds.
3. **Rule evaluation never happens client-side.** All filtering for a user-defined feed runs in shared Rust.
4. **Localized strings come from the i18n table.** `compose-error` and `error-message` text is `LocalizedText { key, args }` from the snapshot, not English literals.
5. **Indexed list IDs from ui.yaml.** Tests use `post-card[i]` and `feed-item[i]` scoped queries — never global `count()` + slice.

## Don't do these

- Don't filter posts client-side based on a feed's rule set. The shared Rust filter is the only correct implementation.
- Don't paginate / sort posts client-side. The snapshot supplies the visible list.
- Don't introduce a per-app `FeedViewModel` that owns post state. The shared snapshot owns it.
- Don't add platform-specific element IDs for composer affordances — every app uses the same `compose-*` IDs.
- Don't skip tests for an app that hasn't implemented composer file uploads. Implement the action layer and let the test fail until support lands.
