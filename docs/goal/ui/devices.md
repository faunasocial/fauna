## Goal

The Settings → Devices page lists the user's enrolled devices, lets the user copy *this* app's own actor ID (for pairing a new device — § Layout & flow), and remove an enrolled device. It is the roster only; folder creation, configuration, and conflict resolution live in Settings → Folders ([`folders.md`](folders.md)).

## Layout & flow

Reached via the Settings shell (`{"view":"settings","id":"devices"}`, `settings.md` § Navigation model). One region:

1. **Device list** — `device-card` (indexed) with `device-name`, `device-status`, `device-remove-button`.
2. **Own-identity copy** — `peer-actor-id-copy-btn`, `indexed: false` in ui.yaml's registry: a single button (not one per `device-card`) that copies *this* app's own actor ID, for handing to a new device being paired — not a per-row action on a listed device. It had a sibling, `peer-wg-key-copy-btn`, until 2026-08-23; that element was deleted with the WireGuard stack (see § Where logic lives). `error-message` is the page-level error surface.
3. **Members without a matching entry** — below the roster, a separately-labelled group (title *Signed-in devices without a matching entry*), `device-member-note` and one `device-member-card` (indexed) per listed member; renders nothing when the list is empty (§ Members without a matching entry).

## Members without a matching entry (ratified 2026-09-19; IDs user-approved 2026-09-25; built on tui, macOS and iOS — § Implementation status today)

**Owner of the rule:** [`../architecture/account-data-taxonomy.md`](../architecture/account-data-taxonomy.md) § The generation machinery → *Fleet-scope reclamation*, clause (4), *A disagreement is the user's to settle* — who is listed, why the door takes no nest input and reads no row statement, what it refuses, and its bounds. This section owns only the **page**: where the group sits, what a card shows, the gesture, and the copy.

- **Who appears.** Every verified fleet member — a device holding this account's keys — other than this device that **no roster row accounts for** (`fauna_core::fleet_removal::unaccounted_members`): a device whose nest row was deleted with no fleet leg run (a client that ran none — no app's own row gesture does this since web's fleet leg landed, the last bullet below), a device whose own record names a row that is not its roster row (a fabricated one, a sibling's, this device's own — and then *both* devices stating one row are listed), a non-stating device whose claim the nest stripped or re-aimed, and a device signed in but not yet registered with the server, until it does. A settled honest fleet — every device registered, none re-minted — lists nobody, and then the group paints nothing at all — no title, no note (an honest fleet can still list a device mid-registration, and a re-minted machine's two principals, below).
- **What a card shows, stated plainly because it is thin.** Such a member has **no name** — the label lives on the nest row, which is exactly what cannot be trusted for it. The card carries the member's **key fingerprint** (`device-member-fingerprint`, `devices.member_fingerprint`: *Device 3f9a1b2c…c21e9d8f* — [`../behavior/value-formatting.md`](../behavior/value-formatting.md) § Fleet fingerprint owns the width and the elision) and the **sign-in time the device itself claims** (`device-member-enrolled-at`, `devices.member_enrolled_at`: *Says it signed in 2026-08-02 14:10* — the member's own self-signed enrollment instant, a hint and never proof, formatted locally through the shared absolute-timestamp door).
- **How the user tells them apart: by elimination.** Every device still in hand shows its own fingerprint on its own roster row — `device-own-fingerprint` (`devices.own_fingerprint`: *Key 3f9a1b2c…c21e9d8f*), a single element beside `device-this-mark-badge`, absent until the account runtime has answered — and the member to remove is the card matching none of them. The two surfaces are two halves of ONE comparison, so both render through the one shared formatter and nothing else (pinned in `fauna-devices-machine`); the honest re-minted machine (two principals stating one row) yields two cards, one of which matches its own fingerprint, and the copy expects that rather than treating two cards as an attack.
- **The gesture is two steps** (the user's choice, 2026-09-25, over a single click like the roster's): `device-member-remove-button` arms the card — its confirm/cancel pair (`device-member-remove-confirm-button` / `device-member-remove-cancel-button`) paints on that card and no other, and a fresh visit disarms — and the confirm removes **the member the armed card showed, by its key**: the key the card carries travels from the arm to the confirm, never a position in a list a refresh may have reshaped between the two (`DevicesMachine::remove_member_by_id(device_id)` → `FleetRemoval::remove_member` → `AccountStoreHandle::remove_fleet_member`): one leg, the fleet's absorbing `Removed` record on this device's own replica, published by the pump; no nest row is chosen, so no nest deletion and nothing staged. The member's nest row, if it still has one, then comes off by the ordinary row gesture, whose claim now names a removed id and needs no fleet write. On success the page refreshes and the card is gone (the member is no wrap target); a refusal (this device, an id the fleet view no longer verifies, the runtime not up) or a failed write paints `error-message` with the same refusal copy the row gesture uses, and the card stays to re-arm.
- **The note carries three warnings, in the group's own text** (`device-member-note`, `devices.member_note`, single): removing one is **permanent** — no undo, the device must sign in again from scratch; a listed device is **not necessarily a problem** — one that has signed in but not yet registered with the server appears here until it does; and **compare the fingerprint with the devices you still have before removing** — if two cards appear where you expected one, one of them is a device you hold.
- **The row-mismatch refusal points here.** `devices.error_remove_row_mismatch` ends with the pointer: *If the device is not one you hold, remove it by its key from the signed-in devices without a matching entry, below the list.* — the refusal has exactly one way through, and it is on this page.
- **Web paints the same group and removes the same way.** Web hosts the account runtime since 2026-09-29, and its Devices machine reaches the runtime's door through the account port (`architecture/account-client-lifecycle.md` § The client-side lifecycle → *The account port*). So on web the row gesture stages the fleet leg as on every other app, and the group paints off `DevicesSnapshot::members` with the ids above, the confirm carrying the member's key.

## Custody facet (ratified 2026-08-15; W8 — built on tui, § Implementation status today)

The device-shaped half of the participant custody facet ([`../behavior/participants.md`](../behavior/participants.md) § The participant model → Custody facet; mechanism + grant: [`../architecture/account-replica-posture.md`](../architecture/account-replica-posture.md) § Replica posture → *The custody grant + ceremony*). Three pieces, all additive to the roster (the roster's own scope and "Don't do these" stand):

1. **Keyless-posture marker on own roster rows.** An own device enrolled relay-only (a kiosk, an old laptop) is an ordinary `device-card` row wearing a *"relay only — holds no keys"* marker. The marker renders the **derived** posture (bundle key reach) — posture is never stored or asked, so there is no toggle here, only the fact.
2. **Custodian-device rows (owner side — "who holds my data").** One row per **cross-account custodian device** — a friend's device holding sealed copies under a custody grant. Identity = the counterpart account + the device-principal key pinned at the ceremony; these are *not* enrolled devices and render as a distinctly-labeled group, never intermixed with the roster. Row content mirrors the Nests custody rows (`nests.md` § Trust facet — custody rows, the copy + three-state receipt-honesty rules stated once there): grant-event-log fold (Now/History, `lasts-until`, renew/revoke) + latest-receipt freshness and held-bytes, with stale receipts rendering as degraded redundancy the owner sees.
3. **Held-for-others rows + the consent surface (host side — "what I hold for others").** One row per custody this account's devices hold for *other* accounts: the owner (contact), a scope summary, metered held-bytes against the per-custody budget (`retained_bytes_cap`, chosen at accept, adjustable here), and a stop-holding control (the host may always stop; the owner sees coverage die via receipts). An **incoming custody offer** surfaces here as an actionable consent card whose copy MUST state the custody floor — what this device would see (how much, when it changes — the shape, never content) — before accept; accepting binds *this* device and picks the budget — or, under an offer that advertises it and with a pinned nest identity in hand, binds the host's NEST instead (the nest-custodian identity fact, [`../architecture/account-replica-posture.md`](../architecture/account-replica-posture.md) § Replica posture → The custody grant + ceremony; the target select `custody-offer-target-select`, ID user-approved 2026-08-17, renders ONLY under an advertising offer with a reachable owner nest URL and a pinned nest identity in hand — absent otherwise, never disabled; shipped 2026-08-17 with the custodian-nest runtime, tui the lead app). Custodian devices **refuse materialization grants in v1** — whether a friend's device may hold readable views is a future two-sided consent question that will land on this surface when opened (charter § Replica posture).

## State & data shape

The roster comes from the page-level shared-Rust machine **`DevicesMachine`** (`libs/fauna-devices-machine`, `#[uniffi::Object]`). It owns the whole `DevicesSnapshot`; this page reads only the roster slice:

```
DeviceSummary { … }                          // one per device-card
DevicesSnapshot.devices: Vec<DeviceSummary>
DevicesSnapshot.error:   Option<LocalizedText>   // page-level error-message
```

(The full `DevicesSnapshot` — `folders`, `conflicts`, `wizard` — is documented in [`folders.md`](folders.md) § State & data shape, the page that renders those slices.)

`DevicesMachine` mirrors `FolderWizardMachine`'s observer + snapshot + injected-requester pattern: apps register a `DevicesObserver`, build it with `build_devices_machine(nest, observer)` (native `fauna-ffi` / wasm `fauna-wasm-folders`), and re-render off `snapshot()` on every tick. Its `DevicesNestApi` seam consumes **only** WS-RPC kinds — `fauna.sync.devices.{list,delete}` — through the shared `fauna-client-sync` adapter (no HTTP impl). A read or write failure surfaces in `error`; a subsequent successful gesture clears it.

Beside the machine's snapshot, the page reads one fact off the **account runtime** on every hydrate (the same read door as the This-device marker's `enrolled_device_row`): the nest's **standing refusal of this machine's enrollment** — `AccountStoreHandle::enrollment_refusal() -> Option<EnrollmentRefusal>` (`fauna_sync_engine::account_runtime`; UniFFI face `FfiNestClient::account_enrollment_notice() -> Option<String>`, the sentence already resolved). Today the one refusal is `DeviceLimitExceeded`, the tier device cap ([`../behavior/devices.md`](../behavior/devices.md) § Step 4 owns the refusal; [`../behavior/admin.md`](../behavior/admin.md) § 2 Users owns the quota). It is not machine state and not a gesture error: the enrollment pass that meets it runs in whichever process holds the pump — on a desktop usually the co-located sync agent — and records it in the per-actor credential slot, which every process reads fresh, so an app that runs no pass of its own still renders it. `EnrollmentRefusal::notice` is the sentence, the same string `RpcError::localized` renders for the wire code.

Projecting per boundary instead would be two copies of one fold, free to drift on which receipt state reads which way; the shape mirrors `libs/fauna-client-pair/src/trust.rs` and `fauna-core`'s own `LocalizedText`. `[u8; 32]` and `Option<CustodyScopeSet>` do not cross either boundary, so ids cross as `Vec<u8>` and the scope set gets its own `CustodyScopesView`. Each row arrives with both label decisions below already folded (`LocalizedText` + epoch seconds), so no leg re-assembles strings. ⚠ `view_model`'s own fold types stay derive-free — the boundary layer is separate and explicit, which is the property the "keep the computation types pure" rule protects. Faces: `custody_facet_load` (UniFFI, `libs/fauna-ffi/src/custody.rs`) and `DevicesMachine.custodyFacetLoad` (wasm, `libs/fauna-wasm-folders`); the fauna-ffi one is gated behind its default-on `custody` feature, which keeps the Go mail-bridge's `--no-default-features` build off `fauna-sync-engine/account-runtime`.
- **The custody facet's five gestures (accept / decline / set-budget / stop / revoke) + offer initiation.** ✅ **Shared Rust** — `fauna-client-custody` owns the assembly: `run_custody_act` (the five acts + the mint, each re-folding the facet afterwards and returning an error string that must reach the page's `error-message` — never a silent drop, e2e convention 11), `load_custody_facet` (the custody and ledger kind reads + fold + native registry overlay), and `spawn_drive` (one `drive_ceremonies` pass, fired on session start, account-store-ready, and every ceremony-moved edge). ⚠ **Why a separate crate from the folds:** the acts need BOTH `fauna-sync-engine` (the R14 registry door) and `fauna-client-conversations` (the ceremony poster), which are native-only *and* mutually independent siblings — so no existing crate can host them without inventing an edge between the two, and `fauna-client-capabilities` cannot because it must stay wasm-clean. Two orderings inside are load-bearing and are documented at the shared definition rather than left to each leg: the **accept binds the T10 writer key** (the peer-plane NodeId), never the roster's `device.db` id — a custody bound to that id could neither pull nor attest (the wiring bug the two-account journey caught 2026-08-17) — and **revoke calls the nest before recording the signed event**, since a recorded revoke the nest never saw would leave the capability live. What stays per-app is only the app's own bindings: the ceremony observer onto its event loop, and the budget-input draft resolution against its string table. Lifted out of tui 2026-08-17. ⚠ **The web leg's act path is NOT an open design question — measured 2026-08-17.** Revoke, piece 2's one gesture, needs nothing native: it is `CapabilitiesClient::revoke` (this crate, generic over `RpcRequester`) then `grant_log::record_revoke` (pure) through a `ConfigClient` CAS then, the ledger store (`SuccessionLedgerStore`) since the `__config` rail retired (wasm-clean, and already driven in the browser by `libs/fauna-wasm`). So the revoke assembly — **including the nest-before-record order** — lives in `fauna_client_capabilities::custody_acts::revoke_custody`, wasm-clean and compiled for wasm32, and `fauna-client-custody`'s native `Revoke` arm **calls it** rather than keeping a second copy. What genuinely stays native-only is accept (binds the T10 writer key), the mint (needs a conversations session to post on) and set-budget/stop (write the R14 registry row): gated on capabilities web lacks, not on where code lives. **Faces (2026-08-17, mint added 2026-08-18):** `custody_revoke` + `custody_drive` + `custody_mint_candidates` + `custody_mint` (UniFFI, `libs/fauna-ffi/src/custody.rs`) and `DevicesMachine.custodyRevoke` (wasm, `libs/fauna-wasm-folders`) — **corrected 2026-08-31: the UniFFI face now reads the account store through `crate::account_runtime::handle()` rather than hardcoding `store: None`** (`custody.rs:124,165,235,270`; the wasm face has no such runtime to read, and is unaffected). **The held-side gestures cross together (2026-09-28):** `custody_accept`, `custody_decline`, `custody_set_budget`, `custody_stop` and `custody_remove` landed as one surface, because piece 3's card is *defined* by its budget, stop and remove controls (§ Custody facet) and a leg must be able to paint it with every control live; the accept, like the mint, requires the session its drive posts over. A leg still renders the `held`/`offers` rows only with those controls wired — never a card with dead controls. **The mint is exported and needs no store** — it writes a ceremony record through the config CAS, and the host's registry row is the *host's* side of the ceremony; what it needs is a conversations session to post the offer on, which is **required** at the face rather than optional (an offer recorded with no session would never be sent and never reported — a silent drop, e2e convention 11; `run_custody_act` refuses it too). That session requirement is also why the mint is the one export with **no wasm twin**. So the exported face was **piece 2 plus the drive pass plus offer initiation** until 2026-09-28 — originally scoped "until the W3 store reaches a UniFFI app", **but corrected 2026-08-29: a UniFFI app (fauna-ffi, for windows/macOS/iOS) has hosted the W3 store since 2026-08-19** (`account-client-lifecycle.md` § The client-side lifecycle; `fauna-ffi/src/account_runtime.rs`), and `custody.rs` is now rewired (corrected 2026-08-31) to call `crate::account_runtime::handle()` the way `offline_share.rs`/`nest_client.rs` already do, at all four store-consuming call sites (`custody_facet_load`, `custody_revoke`, `custody_mint`, `custody_drive`) — so the store was never the gate on `SetBudget`/`Stop`/`Accept`, which were simply not yet exported (they are as of 2026-09-28); the drive pass is what makes the owner-side receipt freshness real (it ingests the receipts custodian nests deposited) and what posts a fresh offer. ## Persistence

Device state lives nest-side; the page is a `DevicesMachine` read-through with **no local cache** (the machine re-reads `fauna.sync.devices.list` on refresh — the shipped answer; see § State & data shape). The one exception is this device's own peer participation, which is device-local by ruling and only *reported* to the nest ([`../behavior/p2p.md`](../behavior/p2p.md) § Per-device participation).

**Registration timing (when a device joins the roster).** A device appears here once it has *registered* with the nest — which happens when it first acts, not on login alone: a sync client registers on a location binding, and a Media write self-registers an otherwise-unregistered device write-capable. The authoritative model (including the self-healing media-write path and the `fauna.sync.device_unregistered` signal) lives in [`../behavior/file-sync.md`](../behavior/file-sync.md) § Device Registration.

## Errors & edge cases

- `error-message` page-level — a roster read/remove failure surfaces here; a subsequent successful gesture clears it.
- **A refused removal is one of those, and deletes nothing.** `device-remove-button` on the row of the device in hand, or on a row whose fleet member the app cannot verify from its own replica, leaves the row in place and paints the reason (`devices.error_remove_own_device` — sign out on this device instead; `devices.error_remove_unverified_device` — try again shortly; `devices.error_remove_row_mismatch` — the row and the device's own record disagree, and the copy never says to try again because no retry clears it; and, on an app that hosts the account runtime, `devices.error_remove_device` while that runtime is not running — it cannot check anything yet). Shared Rust (`DevicesMachine::remove_device`), so every app that wires the fleet-removal port behaves alike; owner of the rule: [`../behavior/devices.md`](../behavior/devices.md) § Removing a Device. The row-mismatch copy ends with the pointer to the member group (§ Members without a matching entry), where that device is removed by its key.
- **A refused member removal keeps the card.** `device-member-remove-confirm-button` on a card the runtime answers `OwnDevice` / `NotAMember` / `Unavailable` for — or whose `Removed` write failed — paints the same refusal copy (`devices.error_remove_own_device`, `devices.error_remove_unverified_device`, `devices.error_remove_device`) and the card stays to re-arm; nothing was written. Shared Rust (`DevicesMachine::remove_member`).
- **The tier device-cap refusal is a standing notice on the same `error-message`** (ratified + built 2026-09-15; § State & data shape names the read). While the account runtime's slot records `EnrollmentRefusal::DeviceLimitExceeded`, the page paints its `notice` — one sentence naming the cap and both remedies: remove a device here, or ask the admin for a bigger tier (`error.sync.device_limit_exceeded`). A gesture's own error wins while it stands; a gesture's snapshot repaint does **not** clear the standing notice — only the slot no longer recording it does, which happens on the first pump pass that registers the machine after a slot frees (the next accepted register clears it), or at sign-out (swept with the bundle). Every app that hosts the account runtime renders it — a fact read off shared Rust, never a per-app parse of the wire error — web included since 2026-09-29.

## Architectural rules

1. Observer-driven rendering off `DevicesMachine` (no per-app roster logic).
2. Heading is "Devices" on every app that renders the page (all 7, tui via the same shared `fauna_i18n::strings::devices` title key) — no per-app heading divergence (the former linux "Peers" is dropped with the Settings move); identifiers stay canonical.
3. Indexed IDs throughout (`device-card[i]`, `device-name[i]`, `device-status[i]`, `device-remove-button[i]`; `device-member-card[i]` and its children).
4. The member group and the custody families render **below** the roster as distinctly-labelled groups, never intermixed with `device-card` rows, and an empty group paints nothing.

## Don't do these

- Don't run roster logic per-app. Shared Rust `DevicesMachine`.

- Don't reintroduce a top-level "Peers" nav item or a "Peers" heading.
