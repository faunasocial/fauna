## Goal

> **Concept big picture:** for *what a folder is* and how this page relates to Media / Backups / Web hosting, see [`../behavior/folders.md`](../behavior/folders.md) (the map). This page owns the **control-plane UI** only.

The Settings → Folders page is the control plane for the user's folders: create a set (name, device places), edit its config in place, bind a location on this device (desktop only), and resolve sync conflicts — all per set. The files *inside* sets are browsed on the separate **Media** page (the content plane, [`media.md`](media.md)); this page never browses file contents.

## Layout & flow

Reached via the Settings shell (`{"view":"settings","id":"folders"}`, `settings.md` § Navigation model). Regions, per folder:

1. **Folder list** — `folder-row` (indexed) with `folder-add-button` (opens the create wizard) and, per row, `folder-delete-button` (→ `folder-delete-confirm` dialog) and in-place config (below).
2. **In-place per-set config** — selective-sync paths (`folder-include-paths` / `folder-exclude-paths` / `folder-save-paths`), the conflict policy (`folder-conflict-policy-select`, § Conflicts), and the nest place's snapshot policy (`folder-nest-*`). There is no per-set scan-frequency editor: the reconcile cadence is a hard-coded constant (§ Scan frequency).
3. **Location binding (desktop only)** — nested under each folder: `folder-location-list` / `folder-location-row` / `folder-location-path` / `folder-location-add-button` / `folder-location-path-input` / `folder-location-browse-button` / `folder-location-remove-button` (+ `folder-location-mode-toggle` on windows, and on tui wherever its agent has a placeholder surface — a windows host today), and — only while the row's set is holding — `folder-location-deletes-held` / `folder-location-apply-deletes-button`, the mass-delete floor's *"this folder looks empty"* line and its explicit propagate verb (ids user-approved 2026-08-15; behavior owner [`../behavior/delete-propagation.md`](../behavior/delete-propagation.md) § A wholesale-vanished folder is infrastructure failure) — and, only while part of the row's set could not be read, `folder-location-unreadable`, a status line with the count and **no** action (id user-approved 2026-09-25; behavior owner [`../behavior/delete-propagation.md`](../behavior/delete-propagation.md) § Unreadable is not absent). Absent on web / iOS / android (no user-bindable location tree). On **macOS + iOS** every owner row — and every row of a folder shared *with* the account (user-approved 2026-09-30) — additionally carries `folder-on-demand-toggle`, the set-level "Show in Finder" / "Show in Files" on-demand affordance (§ Binding; ratified 2026-07-18).
4. **Conflict surface (per set)** — `conflict-type-badge` (indexed), `conflict-file-info` (indexed), `conflict-resolve-button` (indexed), shown when a set has conflicts. Under the 2026-07-10 auto-resolve target this becomes a **review list** over already-auto-resolved conflicts (§ Conflicts).

**Create wizard** — three steps driven by the shared `FolderWizardMachine` (`FolderWizardStep`: `Name → Devices → Review → Done`), opened by `folder-add-button`. **A folder has no type** (folders re-model phase 2 slice e; the mode contraction, 2026-09-28) — step 1 has no mode picker and step 2 is place-flag checkboxes on all 7 apps (windows last, built 2026-08-21, verified + closed 2026-09-09, § Implementation status today):

- Step 1 — **Name**: name (`wizard-name-input`) entered once. `wizard-next-button` enabled once the name is non-empty.
- Step 2 — **Devices**, rendered as **device places**: per-device enrollment (`wizard-device-check` indexed) + the three place-flag checkboxes `wizard-device-originates` / `-accepts` / `-applies-deletes` (indexed — § Element IDs). Applies to every folder (a "source device + backup targets" split is expressed as flags). **Optional — `continue_enabled` is always true; enrolling zero devices is a valid, advanceable state** (this step configures local-folder-sync/backup-fan-out participation only; it gates nothing about basic Media upload/browse, which only needs the caller to own the set — `../ui/media.md` § Upload). The step header `devices.wizard.select_devices_roles` states the zero-devices-is-fine rule explicitly (a 2026-08-05 live-user field report — "a completely incomprehensible list of things" — found nothing on screen said so), and each checkbox carries its own one-line explainer (`devices.wizard.place_*_desc`), the pattern the retired role picker used per role.
- Step 3 — **Review**: read-only summary (name + enrolled devices; no mode, retention, or cadence line); `wizard-create-button` commits via the machine's async `submit()`. *(The scan-frequency step that used to sit here retired with folders re-model phase 5, 2026-08-20 — § Scan frequency; the retention inputs it carried on windows left with it, in favor of the nest place's per-folder snapshot policy, editable on **any** existing folder after create, `folder-nest-*` § Element IDs.)*
- `Done` is terminal: a successful `submit()` lands here; the app closes the wizard and refreshes the folder list.
- Navigation: `wizard-next-button`, `wizard-back-button`, `wizard-create-button`.

Per-app notes (from ui.yaml):

Each bound row carries the windows `folder-location-mode-toggle`, backed by the agent's FUSE root (`../behavior/on-demand-files.md` § Linux FUSE binding, which owns the behavior and carries its build status; ui.yaml scope approved by the user 2026-09-26): a fresh binding starts always-resident, the switch renders insensitive with the reason where the agent cannot mount, and a row whose mount was refused says so beside the switch.

- tui: location binding as linux, through the same per-user agent; `folder-location-mode-toggle` renders on the bound row wherever that agent has a placeholder surface — a windows host (cfapi) or a linux host (the agent's FUSE root) — and nowhere else (the user's Rule A ruling 2026-09-26, `../behavior/on-demand-files.md` § On-Demand Files).

## Audience and website serving

*Ratified 2026-08-19 (element IDs rule-A approved the same day); tui is the lead app. Behavior authority [`../behavior/folders.md`](../behavior/folders.md) § Target re-model — this section is the UI over it.*

**The audience select offers what the nest accepts, and nothing else.** The option set is built per row by the shared `fauna_folders_machine::audience_options(bound, current)` — `current` is the normalized audience, so the picker knows which state it is offering exits *from* — and every app builds the same picker:

| Folder | Options offered | Why |
|---|---|---|
| Unbound | `private`, `public` | Both are real transitions. |
| Group-bound, not public | `shared` (current state, **not** selectable), `public` | Bound-ness is entered through the share flow and nowhere else, so `shared` is a state to render, never a destination. `private` is withheld because the nest refuses it while bound — the honest repair is to remove the sharing first. |
| Group-bound, currently `public` | `shared` (**selectable** — the flip-back), `public` (current state) | The one legal exit from a bound folder's public window (2026-08-20): the nest accepts `→shared` exactly while bound, and the pick is what re-seals the corpus for its members. Without it the picker offered exactly one selectable option and it was the irreversible one — a client-caused state no client could leave. |

Offering an option the nest would refuse is the anti-pattern here: it produces a control that fails on click, and the failure text has to re-explain a rule the picker could simply have honoured. The hint beside the select rides the same `(bound, current)` inputs (`audience_hint`), so the copy and the option set can never disagree — the bound-public state explains its one exit rather than claiming `shared` is unreachable.

**The rendered value is normalized, never the raw column** (`normalize_audience`). A nest predating the audience column sends nothing at all, and `FolderSummary` defaults it to the empty string — so a select painting the raw value would show a value outside its own option set. The normalization is **fail-closed in the one direction that matters: nothing unparseable ever resolves to `public`.** A binary that cannot read the column must not tell the user their folder is world-readable, nor invite them to publish into one it cannot vouch for.

**Picking `public` does not commit.** It arms `folder-audience-public-confirm`, and the flip happens only when that is answered. This is a product invariant, not a courtesy: a public folder rests **unsealed**, content and names/paths alike ([`../principles.md`](../principles.md) § The user always controls their data owns that single exception to sealed-at-rest). Two consequences are stated in the dialog copy, because each surprised readers on its own:

1. **Names and paths go public too** — they become the address of each file.
2. **Flipping back re-seals only *future* content.** Anything published while the folder was public should be treated as public for good.

While the confirm is armed the select keeps painting the folder's **current** audience. The nest has not moved, and showing `public` before the answer would report an audience the folder does not have — the same rule that keeps the WebDAV toggle non-optimistic. Expanding a different row drops the arm, exactly as it drops an armed delete confirm.

**Re-confirming a public folder this seat cannot verify (ratified with the owner-attested declassification; IDs rule-A user-approved 2026-09-25; tui led 2026-09-27).** An owner row the nest reports `public` whose served attestation does not verify under this seat's own actor id paints `folder-audience-unattested` — the folder stays public on the nest, but its content rests sealed on every upgraded seat until the owner confirms again — beside `folder-audience-reconfirm-button`. The button **arms the same declassify dialog** the select does (it commits nothing; the two consequence lines state the same stakes), and answering `folder-audience-public-confirm` re-sends `public` through the shared `set_audience`, which re-mints the attestation. A dedicated button, because re-picking `public` on a select already at `public` fires no change. The paint condition is one shared predicate, `FolderSummary::is_public_unverified_for(own)` (`fauna-protocol`, delegated from the `fauna-devices-machine` snapshot), built on the nest's unsealed *claim* — so the nest-refused (public + WebDAV-served) fail-safe state, which claims nothing unsealed, never paints it. Which folders reach this state, and why nothing auto-mints: [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Readable classes → *The declassification is owner-ATTESTED*.

**The website toggle publishes the head; the audience decides who may read it.** The two are orthogonal, so the toggle stays **enabled** on a folder that is neither `public` nor paywalled — the setting is real, merely inert, and it hints rather than disabling. Disabling it there would imply the setting is unavailable, and would strand the user with no way to prepare a site before publishing it. This control is what **restores website-folder creation**, which has been impossible since phase 2 slice e retired the wizard's mode step (an accepted gap at the time, recorded in [`../behavior/folders.md`](../behavior/folders.md) § Implementation status today, and explicitly not to be patched by re-adding a mode control).

**The hint is a TRI-state on the live serving picture** (shared decision: `fauna_folders_machine::website_serve_hint`; tui renders it as of 2026-08-19, the other apps inherit it with the phase-4 trickle-down). Publishing a site takes switches in TWO places — this page's audience + website toggle, and the actor's own web-address opt-in (`web-settings-subdomain-toggle`, default OFF) — and a user who flipped only the folder half was told nothing while the nest served its info page in their site's place (measured, phase 4 slice 4e). So the folders page reads the address flag with its refresh (`DevicesSnapshot.website_address_enabled`, best-effort — `fauna.web.get_subdomain_enabled`) and the hint says the true thing: no readable audience → the audience wording; address known ON → the site is served, plainly; address known OFF → the pointed nobody-can-reach-it wording naming Settings → Web; address unknown (an old nest, a failed read) → the combined hedge — the degrade direction is deliberate, unknown must never claim the site is live.

**Cross-toggle refusals are nest-side and about audience, never about the website flag** — WebDAV-serve ⊕ `public` (DAV serving is M2-sealed; a plaintext folder has no key to convey) and paywall ⊕ `public` (a world-readable paywall is no paywall). Each pair is refused whichever side moves second, and the refusal text names the repair. The audience's pair with the nest place's residency is surfaced the same way and adds no element; [`../behavior/file-sync.md`](../behavior/file-sync.md) § Content residency owns it (*v1 scope cuts*, the `public` pair — ruled 2026-10-01, unbuilt).

**Where the logic lives.** `fauna_client_folders::FoldersClient::{set_audience, set_website_enabled}` — **keyless, for every direction the picker offers**, the bound `→shared` flip-back included: all are plain `fauna.folders.update` writes needing no MLS engine and no content key, because the back-catalogue is moved by each device's own engine at its next catch-up **or rescan tick** off the projected audience (`SyncEngine::converge_corpus_to_audience`, which dispatches the sealed direction on bound-ness), not by the caller — and the projection reaches every member's engine, which a per-actor custody sentinel never could (the former sentinel-staging `FoldersAuthor::set_audience` is deleted).

**Third-party deposit and read (ratified 2026-09-05, the third-party integration chain; unbuilt, IDs deferred to rule A).** A folder row gains a **facet, not a control**: which third-party principals hold `deposit` (write-only, keyless) or `read` (the content-key twin) over it, rendered from the same trust-facet fold the Nests page uses ([`../behavior/participants.md`](../behavior/participants.md) § The participant model). Consent is granted and revoked on the connected-apps page ([`connected-apps.md`](connected-apps.md)) — never from this row, which only *shows*; a deposited-but-not-yet-adopted item is invisible here until a seat's next sync adopts it ([`../behavior/file-sync.md`](../behavior/file-sync.md) § Third-party deposit ingress). The deposit/read refusal pairs are nest-side, like the audience ones above: `deposit` ⊕ metadata-only residency (nothing to park), `read` ⊕ not served over WebDAV — judged by the owner's custody at the card (ruled 2026-10-05), which covers `public` and metadata-only, never servable ([`../behavior/webdav-server.md`](../behavior/webdav-server.md) § Key model → *A principal's read*). Mechanism owners: file-sync (deposit + adoption), [`../behavior/webdav-server.md`](../behavior/webdav-server.md) (the bearer door + read twin).

## Exclusive editing (design ratified 2026-09-21; IDs rule-A approved 2026-09-25; built on tui, the other six owed)

Some folders hold files that cannot safely be merged — a SQLite database, a video project, a large binary asset. For those the owner can ask that **only one device at a time may write to the folder**. Mechanism owner: [`../behavior/file-sync.md`](../behavior/file-sync.md) § Exclusive editing (the lease, when a seat acquires it, and what an offline seat does); this section owns only what the page shows.

**Two surfaces, both per folder.** A **toggle** on the folder row turns exclusive editing on or off — the owner's choice, off by default. And when the folder is lease-governed, a **status line** says whether it is writable right now: free, held by this device, or held by another device — naming that device by its label, never by a raw id, because the user picked those labels and a 64-character hex string is not an answer to *"why can't I edit this?"*.

**The status is read, never probed.** It comes off the folder read projection the page already polls, so a reader member sees it too. The page must never call the lease acquire kind to find out — asking takes the lease (`file-sync.md` § Exclusive editing says why), and a page that answered *"is this free?"* by taking it would lock the folder every time the user looked at it.

**A read-only folder still accepts edits on disk; it just does not upload them.** Whatever the page renders for *held by another device*, it may not read as *your changes were rejected* — the user's local edits are safe and waiting, and the copy has to say so. This is the one thing here that is easy to get wrong in a way that costs a user their trust rather than a click.

**Element IDs — rule-A user-approved 2026-09-25.** Two indexed per-folder elements, following the shape `folder-webdav-toggle` and `folder-nest-residency-select` already set on this page:

- `folder-exclusive-editing-toggle` (indexed) — the owner's per-folder on/off.
- `folder-lease-status` (indexed) — the writable-right-now line; present only while exclusive editing is on.

Both are in `ui.yaml`. The status line rides the row **header**, not the expanded body — a reader member has no body to expand, and it is the seat that most needs to see the lock. Its three readings (free / this device / held by ‹label›, with *another device* when this reader's roster cannot name the holder) are resolved once, in shared Rust (`fauna_devices_machine::folder_lease_status`), so no app re-derives the expiry rule or the never-the-hex rule. Build order is the standing one — tui leads, the other six follow in a batched trickle-down.

## Binding (local-folder, desktop only)

It is sanctioned **device-local config** (the per-device "where on disk"); the folder itself is nest-authoritative and the binding only records which already-existing set a location serves. ## Sharing a folder (cross-user)

Sharing turns a folder into a **cross-user shared set** — bound to one MLS group whose members are *other users* (distinct from the device roster, which is the owner's own devices). The crypto (a per-set content key the group distributes + **rotates on member removal** for forward secrecy) is **done + proven**; this section is the UI over it. Key-model authority: [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2; share/rotate orchestration: `libs/fauna-client-folders::FoldersAuthor`. Present on **all 7 apps** since 2026-07-30 (control-plane, like folder create/config — not location binding). UI target-state **user-approved 2026-06-30**.

**Owner side — inline "Shared with" section.** Each expanded `folder-row` gains a *Shared with* section, alongside the device roster + path config:

- `folder-share-button` (indexed) — "Share…" opens the **existing** shared `recipient-picker` (`recipient-picker-input` / `-chip` / `-suggestion` / `recipient-resolve-status`, reused verbatim from conversations add-participant — priority #2, **no new picker IDs**) to pick a person by handle / actor-id.
- `folder-share-confirm` (`optional_elements`) — commit the picked recipient (present only while the picker is open).
- `folder-member-item` (indexed) — one person the set is shared with; carries `folder-member-handle` (indexed), `folder-member-status` (indexed — "Pending" until their Welcome lands, then "Active"), `folder-member-role-select` (indexed — the member's access, Reader | Writer, owner-editable in place; ratified 2026-07-18), `folder-member-cap-input` (indexed, `optional_elements` — per-member byte cap, blank = uncapped), and `folder-member-remove-button` (indexed). The share flow itself carries `folder-share-role-select` (`optional_elements` — access for the recipient being picked, default Reader). *(The access controls — both role selects and the cap input — render on linux, windows, android, web and tui; macOS and iOS render the member row without them, a declared absence of the whole grant surface recorded in § Implementation status today.)*
- `folder-shared-badge` (indexed) — marks a row as a shared set (a set's bound flag = `mls_group_id IS NOT NULL`); renders "Shared · N" for the owner, "Shared by ‹…›" for a recipient. The recipient label is the pre-computed `FolderSummary.owner_display` (handle else the owner's `short_id` — never a bare ellipsis or a client-side truncation; the account-display-label rule, owned by [`../behavior/value-formatting.md`](../behavior/value-formatting.md) § Account display label).

Sharing is **owner-only** — a member cannot re-share (the nest's first-binder channel claim + the claimant gate on `members.evict` / `content_key.put` enforce it). **Each member has an `access` of `reader` (default) or `writer`, chosen at share time and owner-editable per member row (ratified 2026-07-18; design tracked internally).** A **reader** browses + downloads/decrypts via Media (no location binding — a bound location whose edits cannot upload would breach `file-sync.md`'s iron rule that a tracked file's modification MUST be uploaded). A **writer** additionally binds locations and syncs read-write: the nest admits writers at exactly `fauna.sync.changes.record`, the upload leases, and `fauna.sync.conflicts.report` (the `writable_folder` gate — owner OR `access == 'writer'`); everything else (share, evict, rotate, supersede, schedule/retention/mode/delete, serve, paywall) stays owner-only. Access is persisted per (channel, actor) in the home nest's `folder_member_access` table (absent row = reader; the wire field is `access` — never overload the member-list `role`, which means owner/member), written via the owner+claimant-gated `fauna.folders.members.set_access`. **Quota is owner-pays, uniformly**: a writer's recorded bytes charge the **owner's** quota with an optional per-member byte cap enforced by the home nest (metering mechanics owner: `../behavior/file-sync.md` § Multi-writer shared sets). Because an uncapped writer can therefore consume the owner's entire remaining quota (their other sets included), the share flow / member row shows a **warning when `writer` is granted with no cap** ("this member can use your entire storage quota" — one i18n string, all apps); blank-cap-means-uncapped itself stays as ratified — a silent server-side default cap would be an arbitrary constant wrong for the common trusted-person share, and the nest has no UI of its own to warn from (advisory disposition, 2026-07-19; refutable downstream). Writer→reader is a plain access edit (**no rotation** — they stay a reader); reader→writer likewise (they already hold the keys). Removing a member (`folder-member-remove-button`) **rotates the content key** so the removed member cannot decrypt post-removal content (§ key-material-hierarchy M2 *Rotate-on-removal*).

**A writer grant on a folder whose content is readable BEYOND its members warns too (ratified 2026-08-27; element ID `folder-writer-published-warning` user-approved 2026-09-25 — § Implementation status today).** The `writer` grant is described to the owner as permission to *change files in this folder*. On a folder that has been published, it is more than that: the same grant lets that person change what people **outside the set** read — and on a website-serving folder those changes land on the **owner's** site, because the `web_files` rail is keyed to the site owner whoever recorded the change, not to the recorder. That is a materially larger grant than the word *Writer* conveys, and nothing in the UI said so.

- **The condition is REACH, not the website toggle.** Content is readable beyond the member set exactly when `audience == "public"` (the corpus rests unsealed and world-readable, § Audience and website serving) **or** the folder is paywalled (served to subscribers). This is deliberately the same test `website_serve_hint` already applies when it calls the website toggle inert — *neither `public` nor paywalled ⇒ nothing serves to anyone* — so the two decisions cannot drift apart, the way `audience_hint` shares its inputs with `audience_options`. `website_enabled` on its own is **not** the condition: a website-enabled folder that is neither public nor paywalled serves nobody, and a `public` folder is world-readable through the follow flow (§ Following a public folder) whether or not it is served as a site.
- **It rides the SAME surface as the uncapped warning — the share flow and the member row — and for the decisive reason that this surface is STATE-based, not event-based.** The warning renders whenever `access == writer` **and** the folder reaches beyond its members, so it is correct under **both** orderings: granting Writer on an already-published folder, and publishing a folder that already has writers. A line in the declassify confirm (`folder-audience-public-confirm`) would be event-based and would cover only the second, so **that dialog deliberately does NOT gain one** — its two ratified consequences stand unchanged, and a future session should not add a third there.
- **Two sentences, not one, because the two reaches are different facts** — the shared decision returns which one applies, exactly as `audience_hint` and `website_serve_hint` return one key of several, so no app re-derives it (priority #2): public ⇒ *"This folder is public, so this member can change what anyone can see."*; paywalled ⇒ *"This folder is sold to subscribers, so this member can change what they see."* Advisory only — it never blocks the grant, never disables the picker (the same disposition as the uncapped warning; refutable downstream). The two warnings **stack** on a folder that is both published and uncapped: they name different consequences of one grant, and suppressing either would be the UI choosing which risk the owner is allowed to know about.
- **Why this was surfaced rather than dropped.** The premise that it had gone a month without a report was wrong: the owner-side grant UI reached its fifth app only on 2026-08-26 (windows), and the audience/website controls landed on tui 2026-08-19 and on linux/web with the phase-4 trickle-down — so the two conditions had barely co-existed in any shipped build. Absence of reports was absence of exposure. Weighed against that, the sibling advisory from the same review — the uncapped-quota warning above — was ratified and shipped on every app that has the surface, and this is the same class of non-obvious consequence attached to the same gesture; surfacing one and not the other would have been an inconsistency in the same paragraph.

> ✅ **BUILT 2026-07-23 — sharing an already-shared set ADDS the new person to the set's existing group.** This block previously declared the opposite as a confirmed bug: `FoldersAuthor::share_set` unconditionally called `FolderGroupCrypto::create_group`, so **every** share minted a *fresh* MLS group and `fauna.folders.share` re-bound the set's `mls_group_id` to it — silently dropping every earlier member from both the roster (`members.list_actors`) and the read gate (`folder_authz`), which project over the set's **current** derived `ChannelId`. Their client went dark on a set nobody revoked, with no rotation, no audit entry and no UI saying so: a **`docs/goal/principles.md` § *User always controls their data* breach**. The fix is the *Adding the 2nd..Nth member* paragraph below (mechanism owner: [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 *Admitting a member*); design ratified and built 2026-07-23. **Proof:** `conformance_shared_folders.rs::sharing_with_a_second_member_keeps_the_first_on_the_roster_real_nest` — formerly `#[ignore]`d RED, now green — after two shares the set is still on one group, both members are rostered, **each opens the content-key envelope through their own engine at their own epoch**, and the first member still reads after the second is evicted. **The data question this block used to leave open is ANSWERED and pinned:** content uploaded *before* a second share stays readable afterwards, for the owner **and** for the newly-admitted member — admitting never changes the set's channel and never rotates, so generation 1 keeps the key that sealed it (`content_uploaded_before_a_second_share_stays_readable_after_it_real_nest`). **No migration is owed for the pre-fix behavior:** a set shared with a 2nd person on a build before the fix would have had its pre-re-bind content stranded (sealed under the orphaned channel's generation 1 — recoverable, since custody only ever appends channel entries, but not resolvable by the normal read path). **User ruling 2026-07-23: no set had ever been shared, so nothing is stranded and no backwards-compatibility or data-recovery capability is to be built for it.**

**Adding the 2nd..Nth member (ratified + BUILT 2026-07-23; mechanism owner: [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 *Admitting a member*).** Sharing an already-shared set admits the new person into the set's **existing** MLS group — an MLS Add staged and distributed exactly like a conversation add-participant (priority #3) — never a fresh group, never a re-bind; **no rotation on admit** (history-on-join). The behavior rules the UI relies on:

- **The share gesture is idempotent and self-healing.** Re-sharing with a person already on the roster only refreshes their access row (equivalent to `members.set_access`) — their staged or accepted membership is untouched. Re-sharing with a person a crashed earlier share left half-admitted (in the group but never on the roster — a Welcome that never landed) **heals automatically**: the ghost leaf is evicted through the ordinary rotate-on-removal machine, then the person is admitted fresh with a new KeyPackage and a new Welcome.
- **"Shared with" tells the truth.** A member appears on the owner's roster exactly when their Welcome was delivered (same-nest `actor_channels` at `welcome.deliver`; cross-nest `channel_foreign_members` at the federation relay) — so a share interrupted before delivery leaves the list unchanged, and the re-share gesture *is* the recovery. There is deliberately **no launch-time resume machinery for adds** (unlike removals): an add stages no irrecoverable key material, and the failure state is visible and gesture-recoverable (rationale: KMH § M2 *Admitting a member*).
- **Declining an invitation removes you from the roster** (ratified + BUILT 2026-07-23). The recipient's decline is an ack **plus** the existing self-scoped leave (`fauna.folders.leave`, relayed cross-nest like a voluntary leave) — so the owner's list never shows a decliner as shared forever, and a later re-share is a genuine re-invite (fresh Welcome). The leave runs **before** the ack: the un-acked row is the only handle on a roster row still to be removed, so a crash between them re-lists the share and re-declining converges. A **suppressed** (Blocked-sharer) knock drops the roster row the same way: to the sharer a block is indistinguishable from a decline — one deliberate bit, accepted (refutable downstream); the alternative (a suppressed recipient rostered forever) would both lie in the owner's list and make the person un-re-invitable after an unblock. **Proof:** `conformance_shared_folders.rs::declining_a_share_drops_the_roster_row_and_a_re_share_re_invites_real_nest` — B is rostered by the share, declines through the shared client recipe, drops off the roster *and* out of the content-key read gate, and the re-share then mints a genuinely new Welcome via the ghost-heal arm (B was still an MLS leaf, since declining never joins).
- **The newcomer's access row still lands before their Welcome** (D5): the add path reuses `fauna.folders.share` unchanged — with the existing group id it is an idempotent claimant re-bind whose real work is recording the access row.
- **An older client's share of an already-shared set fails visibly instead of silently revoking** (2026-07-24). Because a client older than 2026-07-23 still mints a fresh group for every share — and stays wire-compatible for the whole major version — the nest now refuses a share naming a group other than the set's own, so that gesture surfaces as an ordinary share error the user can see and retry from an updated client, rather than quietly emptying their "Shared with" list. Nothing an up-to-date client does can trip it. Server-side mechanism + rationale: [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 *Admitting a member*.
- **Recipient-side arrival is identical for the first and the Nth member** (auto for contacts, knock for strangers, always-knock cross-nest — below).

**A removal the owner's local sync agent has not yet caught up with surfaces in the app — ruled 2026-09-25 (refutable downstream; built 2026-09-27, § Implementation status today; the mechanism under it moved to the agent 2026-09-27).** The owner's removal gesture makes two promises: the nest stops serving the removed person (`members.evict` + `folder_authz`, effective the moment the gesture returns), and everything the owner adds afterwards is sealed under a generation that person never held. The second depends on the owner's running sync engine picking up the rotated generation, which the desktop sync agent does by re-reading custody at its own edges, and until it holds that generation it holds new writes to the set rather than seal them under the one the removed member holds (mechanism owner [`../behavior/on-demand-files.md`](../behavior/on-demand-files.md) § Shared sets on a capability host → *One mechanism*). **The ruling: that state is shown, not logged.** *Why surfaced over silent:* nobody in a deployment reads a log ([`../principles.md`](../principles.md) § One configuration surface — there is no operator), so a log-only state is one nobody can know about; the gesture promised a revocation, and a list that *tells the truth* about who is shared with (above) must not let the revocation's second half wait in silence; and every comparable background state the apps already hold — agent health, the transfer window, the peer-share listener's `share-serve-status`, a VPS host's maintenance state — was chosen surfaced over invisible. *Where — an existing element, no new ID:* the state is **not** per member (the member row is gone by then — eviction precedes the re-key), **not** per set (the agent's reading covers every bound set at once), and not a gesture error (`error-message`'s lifetime is the next gesture's; this state's is the agent's). It is a state of the owner's **local sync agent**, so it lives on the global `sync-agent-status` element as a fourth value, **Keys pending**, whose derivation, threshold, lifetime and precedence [`../architecture/apps/sync-agent.md`](../architecture/apps/sync-agent.md) § Local agent health owns. It reaches exactly the apps that run a bound engine — tui, linux, windows and macOS — and no other: web, iOS and android seal nothing under a stale generation. It also covers a rotation made from another of the owner's devices while this app was closed, and a set the user is a member of. *What the owner can do with it:* the state names a device whose additions to a set are waiting to be sealed away from the removed person, so the owner can check that device's connection, or open an app of this account on it, until it clears; the nest gate keeps the removed member out throughout. Deliberately not a modal, not a banner on the removal itself, and no attempt budget that would turn the state into a permanent error: the agent's edges never give up, so the state reads as *pending*, never *failed*.

**Recipient side — auto for contacts, knock for strangers.** Arrival is gated by your **existing relationship** to the sharer (the contacts model, [`contacts.md`](contacts.md) — `contact-status` ∈ Confirmed / Accepted / Pending / Blocked):

- **Sharer is a Confirmed/Accepted contact → auto-share.** The set auto-appears in your `folders` list, **read-only**, with a `folder-shared-badge` ("Shared by ‹handle›") and a `folder-leave-button` (indexed) to remove yourself.
- **Sharer is not a contact (or Blocked) → knock.** The share lands as a `folder-pending-share` (indexed) in a "Shared with you" pending area; you `folder-share-accept-button` (indexed) or `folder-share-decline-button` (indexed). The MLS Welcome is **staged unprocessed** until accept, so declining never joins the group (a Blocked sharer's knock is suppressed). Declining (and suppression) also drops your roster row — § *Adding the 2nd..Nth member* above (ratified + built 2026-07-23).

This reuses the contacts relationship as the spam boundary: known people are frictionless; a stranger cannot force a set into your list.

The fix removes the dependency instead of retrying it (convention 14): `flaui-bridge/Actions.cs::CommitEditable` commits by shifting UIA focus to the field's nearest keyboard-focusable neighbour, firing the app's own `LostFocus` handler — generic by tree walk rather than by naming a sibling, safe because FaunaApp declares zero `GotFocus`/`GettingFocus`/`LosingFocus` handlers, and with the physical Enter kept as a fallback. ⚠ The disconnected-session state itself is NOT fixed and still blocks any windows e2e gesture that genuinely needs `SendInput`; (2) android's binding-gate half is N/A by construction, RULED 2026-08-15 — android has the owner-side roster/access adoption, and that is the whole of its leg: android renders **no location binding at all**, for an owned set or a shared one (§ Element scope above; `folder-location-*` is desktop `platform_elements` in ui.yaml), so a `writer` member row has **no affordance to differ on** from a reader's — the same disposition, for the same reason, as iOS above. Nothing is gated or deferred. ⚠ The one surface that looks like a candidate is **not** one: android's `core/WatchedDirectoryManager.kt` binds SAF `content://` trees to a folder name, but it is a **manual one-shot scan with no watcher** (`../behavior/file-sync.md` § How a file syncs, step 1) whose screen is unreachable (route `media/watched`, unlinked from Media since the 2026-07-01 explorer rework, zero test IDs, outside ui.yaml) and parked pending the Settings → Folders re-home decision. Offering it as a writer-bind would promise read-write sync the android ingress cannot honour — the same fail-closed reasoning that refuses a *reader's* bind. Growing a bespoke android write affordance is therefore a **new per-app deviation** (priority #1) needing explicit user approval, and it belongs to that re-home decision, not to this fan-out; **web adopted the owner-side access-grant UI 2026-07-21** — the `member_access_options()` catalog + the enriched member row via `foldersActorMembers`/`foldersMemberSetAccess` — but has **no location-binding at all** (no browser filesystem), so the binding-gate half is N/A for web by construction); (3) the CROSS-NEST writer app leg on the six apps other than linux — **linux's landed 2026-07-22** (discovery: seed + refresh wire + the `foreign_rows` mapper, so every app's foreign row splits on the real grant; then the bind: the eager `write_token.get` verify + the agent's foreign-routed engine; then the revoked-park surface, which is same-nest AND cross-nest in one shape), leaving only the linux Media resolver — the two-nest end-to-end pin LANDED 2026-07-22. **A client adopting the writer-binding row must keep withholding it for a row carrying a `home_nest_url` until it has the foreign engine legs** — offering a bind the engine cannot honour seals the user's edits under their own `BackupKey`; see the cross-nest members bullet above; design RATIFIED 2026-07-20; the build contract also carries the linux app→agent content-key push closing the agent-path caveat on the linux binding leg — mechanics: `../behavior/file-sync.md` § Multi-writer shared sets → *Implementation status today*). Phased plan: the 2026-07-18 read-write/cross-nest design § Phases (tracked internally) + the app leg's own task breakdown.

## Following a public folder (ratified 2026-08-18; **BUILT on tui 2026-08-19**, then web, linux, macos, ios and windows — element IDs granted 2026-08-19; android owes the last leg)

Behavior owner: [`../behavior/folders.md`](../behavior/folders.md) § Publicly-synced follow; the
kinds: [`../architecture/federation.md`](../architecture/federation.md) § The public folder read
plane. This section owns the UX. **The IDs are in ui.yaml and six apps render them** (rule-A granted
2026-08-19, alongside the phase-4 audience ask); android is the last leg (§ Implementation status today).

**The gesture.** A *Follow public folder…* affordance on the Folders page opens a small flow:
pick the owner by handle via the **existing shared `recipient-picker`** (reused verbatim, as the
share flow does — priority #2, no new picker IDs), name the folder (plaintext — public names are
world-readable), confirm. The app resolves the handle — a bare `alice` on the user's own nest,
or `alice@domain` for an owner homed on another nest, whose nest the handle's domain discovers
(the address rules, cross-nest included, are the behavior owner's:
[`../behavior/folders.md`](../behavior/folders.md) § Publicly-synced follow) — runs the first
public fetch, and pins the stable `folder_id`. Failure (no such public folder — absent, private,
or misspelled are deliberately indistinguishable) surfaces on the page's `error-message`.

**The followed row.** A followed folder appears in the folders list as a read-only row — no
device roster, no location binding, no share section, no toggles: name + owner handle + a
*Public* provenance badge + status. Its content browses in **Media** on demand like a shared
set a reader holds (plaintext decode — no keys): tapping the followed row opens Media scoped to
that follow, and the follow also appears in Media's own `media-folder-filter` options — both
doors drive the same followed browse scope, owned by [`media.md`](media.md) § Followed public
folders. When the home nest stops serving it (audience
flipped back, folder deleted), the row flips to a loud *no longer available* state and stays
until the user removes it; a re-flip resumes it. **A network fault is never that state**: a
read that could not reach the nest leaves every followed row, and its last verdict, standing
until a read succeeds — neither *no longer available* nor gone from the list.

**The owner handle is the handle the user followed them by, shown only while it still names
them.** The public plane names no owner in its reply (a stranger addressing folders by id must
not learn whose each one is), and no kind maps an actor id back to a handle — so the follow
remembers the handle it was addressed by, and the reader re-checks it against the pinned owner
id beside each availability probe, under the same staleness budget. A handle that no longer
resolves, or now names someone else, is dropped; a follow made by bare actor id has none. The
row then names the owner by the id's canonical short form. Every app paints one precomputed
string (`FollowedFolderSummary.owner_display`, *By ‹owner›*) on the row's own text, so the one
read every app offers — `folder-followed-item[k]` — carries it, and Media's filter option
appends the same string (`media.md` § Followed public folders). **A follow homed on another nest
shows the handle it was followed by and is never re-checked** (re-ratified 2026-09-22; the earlier
sentence — *not checkable from the follower's nest* — rested on a capability gap the cross-nest
gesture closed): the follow gesture verified that `handle@domain` against the owner's nest
through the anonymous hop, and that verdict stands until the user unfollows — the same
*last verdict stands* rule a same-nest check that faults gets. It is not re-checked on purpose,
not for want of a mechanism: the availability probe is relayed by the follower's own nest, so
the follower's app never dials the owner's nest on a timer, and a per-probe anonymous re-check
would add exactly that — a recurring connection from the follower's address to the owner's
nest with no user action behind it, against a lookup the peer rate-limits for anonymous
callers. The follow is pinned to the actor id regardless, so a handle that later moves on the
peer mislabels the row at worst, never re-points it.

**Unfollow** removes the record locally — nothing to revoke anywhere (the home nest never knew).

**Element IDs (granted 2026-08-19; in ui.yaml):** `folder-follow-button` (opens the flow),
`folder-follow-name-input`, `folder-follow-confirm` (`optional_elements` — present while the flow
is open; the handle half reuses `recipient-picker-*`), `folder-followed-item` (indexed row),
`folder-followed-status` (indexed — Following / No longer available), and
`folder-unfollow-button` (indexed).

**Three shapes the trickle-down must keep.** (1) **The section is always offered**, even with no
follows — the button is how a user gets their first one, so gating it on a non-empty list makes
it unreachable. (2) **A followed folder is a row in its own list, never a `folder-row`** — it has
no roster, no binding and no seat, so a `folder-row` would open an expander full of controls that
cannot apply to it. (3) **The handle half reuses `recipient-picker-input`** — no second picker,
exactly as the share flow does (priority #2). The owner is accepted as a handle *or* a bare
64-hex actor id, the same superset `share_set` takes.

**Where the logic lives.** `fauna_client_folders::follow_ops::{follow_public_folder,
unfollow_public_folder}` — **the one composition every app calls** (lifted 2026-08-20; before that
tui, the wasm face and the web SPA each held their own copy of the same address rules — and web
kept its own until 2026-09-22, when the wasm `followPublicFolder` face was routed through the
recipe: the SPA had resolved the handle itself and passed an always-empty home url, so web could
only ever follow on its own nest). It owns what sits between the two halves either side of it:
classify the owner address (bare 64-hex actor id, else a Fauna handle — bare, or `handle@domain`;
the same-nest `fauna.actor.by_handle` probe, the shared same-nest-vs-cross-nest verdict and the
anonymous hop to a foreign owner's nest, exactly the recipient picker's chain — the same superset
`share_set` takes), run `public_follow::resolve_public_folder` (which pins the stable `folder_id`;
relayed by the follower's own nest for a cross-nest home), then persist via
`fauna_client_config::save_follow` / `save_unfollow`. **`FollowOpError` carries ONE not-found arm
on purpose**, so no app can re-widen the three folded causes apart; the *wording* stays the app's
half, from the shared catalog. An app leg is therefore a render plus a two-arm error match, never a
re-derivation. The rows come from `DevicesSnapshot.followed`, filled by the
`set_followed_folders_source` seam — which tui wires as of this slice, and which was the reason
that list had always been empty. Availability rides the staleness budget + bounded fan-out
described in [`../behavior/folders.md`](../behavior/folders.md) § Publicly-synced follow, so
rendering the rows does not put a cross-nest round trip per follow on every page refresh.

## Photo backup (apple + android)

The photo library is an ordinary folder ("Photo Library"; the preset's shape is ruled in the next paragraph) whose platform ingress feeds the set — **PhotoKit on apple, MediaStore on android** (identical UX per the 2026-07-10 ruling). It is a *normal* folder created via the standard wizard (in practice a one-tap preset), never a hardcoded magic set. Its config lives **here**, as the `photo-backup-controls` component: `photo-backup-enable-toggle`, `photo-backup-wifi-only-toggle`, `photo-backup-sync-progress`, `photo-backup-sync-now-button`, `photo-backup-last-sync-text`. The unified **Media** explorer shows the files inside that set alongside every other set ([`media.md`](media.md) § Photo-backup reframe). Desktop/web have no device photo library; they create a folder over a normal directory whose device place keeps everything (`applies_deletes` off — the archive point).

Photos are one-way, continuous ingress rather than two-way sync because the OS owns the photo library — two-way sync would imply deleting from or writing into the camera roll on nest-side changes; cross-device viewing is the Media explorer reading the set. **The preset's shape without a mode (ruled 2026-09-28, the folders mode contraction design pass; built 2026-09-28 — `PHOTO_LIBRARY_RETENTION`):** `fauna_folders_machine::photo_library` enrols every device it lists at the **archive point** `{originates: true, accepts: true, applies_deletes: false}` — exactly the point the retired Backup role named, so the contraction changed no seat's behavior; the ingress device is deliberately NOT refined to `accepts: false` (its receiving side is moot — an ingress has no directory to deliver into — and flipping the flag would move its upload accounting, `../behavior/file-sync.md` § 4's both-flags projection). And it stamps the nest place's snapshot policy — 7 snapshots / 30 days, the former Backup default — **explicitly** on create, through the same `retention_policy` any folder's create may carry. A plain wizard create stamps no retention: the nest place's policy rests *unset* (the scheduler's default) until the owner edits `folder-nest-*`.

**Status:** the apple reframe is **complete** (controls 2026-06-30; the set model 2026-07-13 — B3). **Android's reframe is now fully complete too** — the set model landed 2026-07-16 and the UI-restructuring (retiring the standalone `settings/photo-backup` route) landed 2026-07-19 (detail in § Target set model below) — both platforms resolve the target set through the shared `fauna_folders_machine::photo_library` resolver: it reuses an existing "Photo Library" set, else creates the wizard-preset **"Photo Library"** folder through the ordinary `FolderWizardMachine` (the adoption of an existing `"photos"` set was retired 2026-09-24 by the compat-remnant sweep ([`compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md) § Program 4)).

> **⚠ The hardcoded set never existed, so photo backup never worked** (found while landing B3, 2026-07-13). `fauna.sync.changes.record` requires an existing control-plane `folders` row (`owned_folder` ⇒ `not_found`), and **nothing in production ever created a `"photos"` set** on any app. Every photo ingest therefore uploaded its chunks and then had its change record rejected: the file never appeared in Media, and the per-item `catch` on both apps swallowed the failure into a banner. So B3 is not a migration of a real back-catalogue — it is the fix that makes photo backup work at all; the legacy-adoption rule below covered the narrow case where a user had hand-created a set literally named `photos`, until the compat-remnant sweep ([`compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md) § Program 4) retired it. **Android carried the identical bug** (`PhotoBackupEngine.kt` recorded into `"photos"`) until its 2026-07-16 adoption of the shared resolver — a bug fix, not a refactor.

Also note the rendered `photo-backup-wifi-only-toggle` is currently hardcoded on + disabled — the real gate is `NetworkMonitor.shouldSyncPhotos()`.

**`photo-backup-sync-progress` names a POSITION, not merely that something is happening** — "Syncing 3 of 5" (the catalog's `photo_backup.syncing`), driven by a per-pass countdown the engine writes as each asset leaves the loop. The user-facing promise it serves is *while a backup pass runs, the phone shows how far it has got*, and a spinner does not serve it.

> **⚠ Two silent no-ops on apple, both fixed 2026-09-20, both the shape android shipped twice.** This feature's failure mode is never an error — it is a green toggle over an inert path — and apple carried its own pair for months behind exactly that. **(1)** `PhotoBackupEngine.pendingCount` was declared and never written, so the "{n} remaining" row could not render and a running pass showed only an indeterminate spinner (android has always written its twin, so this was drift toward the poorer surface). **(2)** `startObserving()` registered a `PhotoLibraryObserver` built inline at the call site, and `PHPhotoLibrary.register(_:)` keeps only a WEAK reference to its observer — so it was deallocated as the method returned and `photoLibraryDidChange` never fired again: the foreground trigger above was dead, and "new photos go up by themselves" was false whenever the app was open. Both were found by writing the witnesses the outcomes lacked, which is the standing argument for writing them: a missing witness very often hides a missing implementation.

**What drives the ingress — the constant cadence, not a per-app timer (android leg landed 2026-07-22; the per-set choice retired with phase 5, 2026-08-20).** "Continuous ingress" above is a *trigger* claim: the ingress period is the same hard-coded reconcile constant every seat ticks at (authority: [`../behavior/file-sync.md`](../behavior/file-sync.md) § Config, the phase-5 block) — no app invents an interval, and no row supplies one. Per-platform trigger, mirroring the same split `backup-restore.md` § Background Tasks draws for mail-segment backup:

- **iOS** — two triggers, and both are load-bearing. **Backgrounded:** the `social.fauna.sync.upload` `BGProcessingTask` (`BackgroundScheduler.swift`), which calls `syncNewPhotos()` (photo backup is that task's only leg — the mail-segment leg is retired; task table in `apps/ios.md` § BackgroundScheduler). iOS grants no period control, so the OS schedules — and since `BGProcessingTask` has no public initializer either, the handler's body is a named method (`runScheduledUploadPass`) so the e2e can drive the *production* path rather than a shortcut around it. **In the foreground:** PhotoKit's own change notification, registered by `PhotoBackupEngine.startObserving()` on enable — this is what makes a photo taken while the app is open go up immediately rather than at the next OS slice.
- **Android** — a `WorkManager` periodic worker (`PhotoBackupWorker`), enqueued at app start on WorkManager's 15-minute periodic floor, which absorbs the 300 s constant — a platform limit, not a client-chosen cadence; `NetworkType.UNMETERED` is the scheduling-time twin of the `shouldSyncPhotos()` per-file gate. (Before phase 5 the worker re-periodized itself from the row on each pass; the floor already swallowed every value a user could pick, so the de-knob changed no android behavior.) **Before this landed, `photo-backup-enable-toggle` persisted an `autoPhotoBackup` flag that nothing automatic ever read**: the one-shot `SyncService` behind `photo-backup-sync-now-button` was the *only* caller of `syncNewPhotos()`, so android photo backup was manual-only despite the toggle's wording. **A second, independent silent-no-op survived until 2026-08-06**: nothing under the app had ever minted `SecureStorage.deviceId`, so on every production install it was null and `syncNewPhotos()`'s `secureStorage.deviceId ?: return 0` early-out fired on both the scheduled and the manual-tap path — every pass uploaded nothing, whether or not the toggle and the worker themselves fired correctly. `SecureStorage.deviceId`'s get-or-create fixed it fleet-wide — a random mint then, the derived per-account id since 2026-09-22 (self-healing for every already-installed device; no re-onboarding path exists, so a mint-only-at-onboarding fix would have stranded them).
- **macOS** — the always-running app watches the library directly; no scheduler.

Native apps take the constant (`fauna_client_folders::cadence::DEFAULT_RESCAN_INTERVAL`) directly; the row-resolving FFI faces (`FfiFoldersClient::rescan_interval_secs_for`, `FfiFileProviderHost::rescan_interval_secs`) are deleted.

**Target set model (ratified 2026-07-12 with the apple sync-engine convergence design — `../behavior/sync-engine-deployments.md` § Apple apps — convergence design owns the engine/seal mechanics; this section owns the set model):** on first enable the app creates the **wizard-created "Photo Library" folder** as a one-tap preset (the ordinary `FolderWizardMachine` create — never a client-invented magic name), and a device-local binding records which set the platform ingress (PhotoKit / MediaStore) feeds. **Legacy adoption rule — retired 2026-09-24:** a device that already uploaded into the hardcoded `"photos"` set used to bind ingress to that existing set; the compat-remnant sweep ([`compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md) § Program 4) removed the rule (no pre-sweep installation exists), so a `"photos"` set is now an ordinary user folder and every install creates or reuses the preset set. Ingress itself is the shared engine's sealed per-file ingest (export → ingest → delete the temp; no staged duplicate of the photo library on disk). **Android's set-model half landed 2026-07-16**, including the (since retired) adoption rule: its hardcoded `"photos"` set retired in favor of the wizard-created Photo-Library set, resolved via the shared resolver on every backup pass. **The UI-restructuring half landed 2026-07-19**: the bespoke standalone `settings/photo-backup` route (`PhotoBackupScreen.kt`) is retired — `photo-backup-controls` now renders as a `PhotoBackupSection` injected into `FoldersContent` on this page, identical in shape/placement to apple's `PhotoBackupControlsView`. Android's reframe is now fully complete, matching apple.

## State & data shape

The page reads the page-level **`DevicesSnapshot`** owned by **`DevicesMachine`** (`libs/fauna-devices-machine`, `#[uniffi::Object]`) — the same machine the roster ([`devices.md`](devices.md)) reads; this page renders the folder / conflict / wizard slices:

```
DevicesSnapshot {
    devices:   Vec<DeviceSummary>,              // → devices.md (roster)
    folders: Vec<FolderSummary>,             // folder-row list
    followed: Vec<FollowedFolderSummary>,    // followed public folders — § Following a public folder
    conflicts: Vec<ConflictSummary>,            // path, type, Vec<ConflictCandidateSummary>
    wizard:    Option<FolderWizardSnapshot>,   // Some while the create wizard is open
    error:     Option<LocalizedText>,           // page-level error-message
}
```

`ConflictSummary`'s candidate versions are `Vec<ConflictCandidateSummary>` (`{manifest_hash, device_id, size_bytes, created_at}`), transcribed from the protocol `ConflictCandidate` returned by `fauna.sync.conflicts.list`.

The create wizard is a shared-Rust state machine, **`FolderWizardMachine`** (`libs/fauna-folders-machine`), mirroring `OnboardingMachine`. Its renderable form is the serializable **`FolderWizardSnapshot`** (`uniffi::Record`, serde) — `step: FolderWizardStep` (`Name | Devices | Review | Done`); `name: NameSnapshot { name, continue_enabled }`; `device_places: DevicePlacesSnapshot { devices, continue_enabled }` (step 2 as the place-flag checkboxes render it); `review: ReviewSnapshot { name, retention, enrolled, create_enabled, phase, created, failed_members, error }`. (The `FrequencySnapshot` step record and `ReviewSnapshot.frequency_secs` left with phase 5; the mode field, the role-picker snapshot and its option list left with the mode and `role` contractions, 2026-09-28/29.)

Value types: `SubmitPhase { Idle, Submitting, Done, Failed }`, `RetentionPolicy { max_snapshots, max_age_days }`, and `fauna_protocol::folders::PlaceFlags` (the place a device holds). `LocalizedText` is the shared `fauna_core::localized::LocalizedText`.

Defaults: a plain create stamps no retention and the Photo Library preset stamps 7 / 30 (§ Photo backup); devices are initially unselected, and an enrolled device's default point is `{originates, accepts, applies_deletes}` all true.

## Where logic lives

- **Folder create wizard.** ✅ **Shared Rust** — `FolderWizardMachine` (`libs/fauna-folders-machine`), built via `build_folder_wizard_machine(nest, …)` (UniFFI + WASM). Derived from the three `ConflictSummary` fields apps already hold — a pure client-side computation, no wire/at-rest change. Adopts web's richer shape as canonical (priority #4): it localizes the two known conflict types (`binary_copy` → `type_binary`, `merge_markers` → `type_merge`) that the natives leaked raw, and applies the resolution arms uniformly (android previously rendered the raw wire type even on a *resolved* row). UniFFI face: `folders`-gated `fauna-ffi` free fn `conflict_badge_label`; wasm twin `conflictBadgeLabel`. - **Conflict review-row derivations (`conflict-file-info` text + `conflict-resolve-button` gating).** ✅ **Shared Rust** — computed once at the snapshot transcribe (`fauna-devices-machine`, `From<SyncConflict> for ConflictSummary` — the `owner_display` pattern): `ConflictSummary.file_info` is the display-ready `"{set}: {path} → {winner8}"` line (bare `"{set}: {path}"` while unresolved), and `ConflictSummary.has_other_version` gates the one-tap re-point (a resolved row must retain a candidate ≠ the winning head; always `false` unresolved — § Conflicts above). Apps read the two fields verbatim; no app re-derives the winner/candidate comparison or hand-shortens the hash. Replaces four identical hand-rolled copies and the android drift (an **ungated** resolve button driving the legacy `resolve_conflict(id, first-candidate)` instead of the gated `use_other_version` re-point, plus a winner-less `"{set} · {path}"` info line) — the android swap is a behavior fix. No wire change (snapshot-side computed fields). Landed 2026-07-16 (linux consumes both; apple read-swapped same day — local `hasOtherVersion`/`infoText` deleted; windows swapped same day; web/android swaps tracked per app).
- **Selective-sync path-field parse/format (`folder-include-paths` / `folder-exclude-paths` field text ↔ list).** ✅ **Shared Rust** — `parse_paths_field(text) -> Vec<String>` (comma-split, trimmed, empties dropped) + `join_paths_field(paths) -> String` (comma+space-joined; absent/empty → `""`) in `fauna_folders_machine::state`, beside the conflict-policy helpers. Canonical semantics: **an emptied field parses to `[]`, never an absent field** — the `fauna.folders.update` wire treats an absent path field as *leave unchanged* and `[]` as *clear the filter* (an empty include list disables the whitelist, so the engine syncs everything). Replaces five hand-rolled per-app copies; android's had diverged into sending `null` for an emptied field, making "clear all paths and save" a silent no-op — its swap is a user-facing bug fix, not just a de-dup. ## Persistence

Folder definitions, members, schedule, retention, and conflicts are **nest-authoritative** via fauna-sync (created once via the wizard). Location bindings are **device-local config** (a location map / `LocationConfig`, per `on-demand-files.md` § On-Demand Files). Local caching of the snapshot is unspecified per-app glue (resolved by the first app that needs one; no contract today).

## Errors & edge cases

- `error-message` page-level — read/write failures surface here; a subsequent successful gesture clears it.
- Wizard validation errors (empty name, no mode chosen), selective-sync regex error — unspecified beyond "surface as snapshot variants" (resolved by the wizard-machine error-variant pass when an app needs richer copy).
- **Conflict resolution failure** — a `winning_manifest_hash` not among the conflict's recorded candidates returns `fauna.sync.internal`-namespaced `not_found` (`bad_candidate`); an already-resolved / missing conflict returns `not_found`. Both surface in `error-message`.
- **Delete cascades** — deleting a set with snapshots removes those snapshots in the same nest transaction (the non-cascading refusal, which returned `fauna.folders.internal`, was retired 2026-05-30); a refused delete (a reserved rail, or `conflict` while another destructive op holds the folder's lock) surfaces in `error-message`.
- **A removal the local sync agent has not yet caught up with** — not an error here: it is the `sync-agent-status` state *Keys pending* (§ Sharing a folder, the 2026-09-25 ruling); `error-message` never carries it, because its lifetime is the agent's, not a gesture's.

## Architectural rules

1. Observer-driven rendering off the shared snapshot / wizard machine.
2. A folder is created **once** via the wizard (name entered once); location binding references an existing set — no free-text set name.
3. The wizard is three steps (name → devices → review) on all seven apps; no step asks for a cadence.
4. Scan frequency is **not a control**: the reconcile backstop is a hard-coded constant (`file-sync.md` § Config, the phase-5 block); the nest place's snapshot policy is the one user-facing time control.
5. Conflicts are resolved per set on this page; no standalone conflicts page / `conflicts-tab`.
6. Indexed IDs throughout (`folder-row[i]`, `folder-conflict-policy-select[i]`, `conflict-*[i]`, `wizard-device-check[i]`, `wizard-device-role[i]`, `folder-location-row[i]`).

## Don't do these

- Don't run wizard logic per-app. Shared Rust state machine.
- Don't reintroduce `folder-location-fileset-input` (free-text set name) or `folder-location-fileset` (per-row set-name display) — the set is contextual (D3 / O-1).
- Don't add a standalone conflicts page or a windows `conflicts-tab` — conflicts are per-set here.
- Don't skip retention controls in non-Backup wizard mode by deleting them — gate visibility on the wizard state.
- Don't add a 7th folder/Media paradigm; Media is the folders *content* view ([`media.md`](media.md)), this page is the control plane.
