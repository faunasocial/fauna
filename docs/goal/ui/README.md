Shared contract for all 7 Fauna apps: web, iOS, macOS, Android, Windows, Linux, tui. Each page doc describes what the user sees, what data is displayed, and what actions are available. Apps may adapt layout and interaction patterns to their platform, but the information architecture and user flows must match.

**Reading ui.yaml: use `just ui-show`, never a whole-file read.** This doc and the ones beside it route many claims to `tests/e2e-unified/ui.yaml` — element IDs, per-page element scope, nav membership. That file is **867,925 bytes, 3.31× the 262,144-byte Read-tool ceiling**, so opening it whole is not possible: the tool refuses the read outright and returns none of the file. What makes that a trap rather than a dead end is the tool's own remedy — *"use offset and limit"* — which is the wrong advice for a structured spec, because a blind byte range is not a node and leaves you with no table of contents. `just ui-show` addresses it one node at a time and returns the file's own bytes with their line range, so `ui.yaml:NNN` citations still resolve: `just ui-show` for the table of contents, `just ui-show pages.feed` (or the bare `feed`) for one page, `just ui-show elements.error-message` for one element, `just ui-show --find <substring>` to locate a key. A node over the output cap renders as an index of its children rather than truncating, so every part of the spec is reachable. The reader is tooling, not a claim about the product; its contract lives with the script (`scripts/ui-show.py`) and is pinned by `tests/scripts/test_ui_show.py`. A PreToolUse hook enforces the "never a whole-file read" half: it blocks an argument-free `Read` of the file — not because that call would otherwise succeed, but so the refusal names the reader instead of sending the session at a blind byte range — while leaving a bounded `Read` (explicit `offset`/`limit` — what editing a specific range needs) and hand-editing the file (rule A) alone.

## Navigation model

**Membership is ui.yaml's domain.** Which primary-nav destinations exist, which are gated (`admin-tab`, `family-tab`), and which apps legitimately lack one live in ui.yaml `navigation.{tabs,gated_tabs,nav_exceptions}` — read the tab set there; this doc never carries a second copy. Every destination uses the shared `{page}-tab` ID convention (ui.yaml owns the IDs).

**Per-form-factor patterns:**

- **Desktop (web, windows, macos, linux, tui):** a persistent sidebar/rail carrying the primary tabs. Web renders the sidebar on desktop widths and a bottom tab bar on mobile widths. tui — a desktop form-factor app despite being a terminal UI — renders the same sidebar in its left pane, same placement as linux's GTK sidebar (`architecture/apps/tui.md` § Form factor and navigation).
- **Mobile (ios, android):** a compact primary surface plus an overflow hub. iOS is the reference shape: a bottom tab bar with Conversations / Feed / Contacts / **More**, where the More hub carries the remaining destinations. Android uses a navigation drawer over the same `{page}-tab` IDs. E2E drivers branch on `driver.is_mobile()` — never on app names (`architecture/e2e-conventions.md` § Cross-app e2e conventions, point 3).

**Sub-page navigation (the two-element convention).** Shell pages (Settings, Admin) address their sub-pages with a two-element nav path: `{"view":"<shell>"}` opens the shell, `{"view":"<shell>","id":"<page>"}` opens a sub-page (e.g. `{"view":"settings","id":"account"}`; the Mail & Calendar sub-page's own `id` is the shorter `mail`, not `mail-settings` — the `id` is the sub-page's nav slug, which need not match its ui.yaml page key or doc filename). The Settings shell's internals are owned by [settings.md](settings.md) § Navigation model; the admin shell by [admin.md](../behavior/admin.md).

**Reaching a sub-page by clicks — the rail-row IDs (user-approved under rule A 2026-10-04).** The two-element nav is the automation path; a human reaches the same sub-page by the shell's entry tab and then a row of its rail, and so must a test bound to gestures alone (`../architecture/e2e-conventions.md` convention 8). So every shell rail row carries one indexed ID keyed by the sub-page it opens — `admin-nav-row[<page>]` on the admin rail, `settings-nav-row[<page>]` on the Settings rail, in the `dns-provider-row[<id>]` idiom; the key, the rows that keep an older ID, and the mobile placement are ui.yaml `navigation.sub_page_nav_rows`' (its domain). Built on tui (2026-10-04, the lead app; `tests/e2e-unified/tests/test_subpage_rail_click_nav.py`); the other six apps follow in trickle-down rows.

**Entering a shell lands on its canonical entry (ratified 2026-08-13).** Crossing the boundary *into* a shell — Settings, Admin, or any shell added later — always lands on that shell's **canonical entry sub-page** (Settings → Status; Admin → Dashboard), never on the sub-page a previous visit happened to leave open. Sub-page position is **shell state, not session state**: it does not survive leaving the shell. Four qualifications make the rule precise, and all four are load-bearing:

1. **The reset fires on the nav *edge* only** — the transition from outside the shell to inside it. Re-selecting a sub-page *within* a visit is never clobbered, and navigating to the shell you are **already in** is a *reload*, which must not throw the user out of the sub-page they are on. An implementation that resets on every nav actuation rather than on the edge is wrong in a way this rule does not license.
2. **The two-element nav composes with it, and the deep link wins.** `{"view":"<shell>"}` (no id) lands on the canonical entry, which is the rule above stated in nav-path terms; `{"view":"<shell>","id":"<page>"}` routes to `<page>` *after* the edge reset, so a programmatic deep-link — and any in-app affordance that jumps straight to a sub-page — still lands where it aims. The reset is the floor for an id-less entry, not a filter over id-bearing ones.
3. **It binds shells, not pages.** An ordinary page that keeps its scroll position or its selection across a visit is outside this rule; what resets is a shell's *sub-page*, the surface the shell's own rail switches.
4. **The reset lives on the path a *human* takes, not only on the automation path — and an e2e test alone cannot grade this rule.** The canonical-entry behavior reached three apps' *nav-path* code long before it was written down here: macOS resolves a bare admin nav id to the Dashboard (`AdminPage.swift`, `case "dashboard", nil`), Windows lands an absent/unrecognized id there too (`AdminNavigation.cs` — "so an admin nav never resolves to 'nowhere'"), and linux matched them **in its test agent** (`main.rs`'s nav patch). On linux that left the sidebar-clicking user still landing on the stale sub-page while every e2e assertion passed — because the agent's own nav reset the very state the test was about to read. A conformance check for this rule must therefore drive the app's **real** entry affordance (linux does it in-process through the actual sidebar, `walk.rs` sweep 4; tui through its own walk), and an app that satisfies the rule only through its state-protocol nav has **not** conformed.

**A nav to a page shows that page's own primary surface (push-stack pages; ratified 2026-08-28).** Qualification 3 leaves an ordinary page free to keep its selection across a visit, and on every two-pane app that is free: the list pane never leaves the screen, so a remembered selection cannot hide the page. A **single-pane mobile push stack is the one shape where keeping the selection also *covers* the page** — iOS pushes the thread/event detail over its list root — so a nav aimed at that page would otherwise land on whatever detail the last visit left open. So on a push-stack page, a nav patch *targeting that page* returns the page's **own** push stack to its root. This is not the shell reset and does not overlap it: no sub-page state is cleared, no other page's stack is touched, and a nav aimed elsewhere leaves an open detail alone. Qualification 3 still holds for what it says — the *selection* may persist wherever persisting it does not cost the user the page they asked for.

iOS and android have the shape today. iOS implements it with the `reloadToken` idiom — the page takes `appState.navGeneration` as a parameter and pops its own detail on change, scoped to `appState.selectedTab`/`moreSelectedView` naming that page: `Fauna-iOS/Views/Events/CalendarListView.swift` (events, 2026-07) and `Fauna-iOS/Views/Conversations/Unified/ConversationsListView.swift` (conversations, 2026-08-28). The conversations gap is what made a covered list root read as a *render* failure: the automation registry deliberately keeps a covered element visible (a pop fires no balancing `.onAppear`), so the root's toolbar items still answered `is_visible` while every `conversation-item` slot was voted definitively hidden — an e2e opener saw state that already listed the new thread and a row count of zero. **android was MEASURED 2026-09-27 and conformed on the same day.** Its `conversations` list and `conversation/{threadId}` detail are a flat sibling pair in the shipped `NavHost` graph, the detail plain-`navigate()`d from the list, so the drawer's multi-stack `popUpTo(start) { saveState } + restoreState` idiom (the same mechanism `DrawerShellReEntryTest` measured for the shell rule) restored a covered detail exactly as it restores a shell's stale sub-page — driven headlessly and confirmed red first, then fixed: `FaunaNavHost.kt::navigateToDrawerRoute` withholds the restore for a `PUSH_STACK_PAGES` target the same way it withholds it for a shell entry, on every nav that targets the page (no reload exception — a push-stack page carries no sub-page the user is entitled to keep). Pinned by `ConversationsPushStackReEntryTest`, the same no-emulator shape as `DrawerShellReEntryTest`.

**Why this and not "resume where I was".** Both shapes are defensible in the abstract, and the apps split 4–2 on them (measured across all seven, 2026-08-13). What settles it is that the split is not symmetric. On the canonical-entry side the behavior is **chosen**: tui resets on the nav edge because a live user got stuck on a stale sub-page ([`../architecture/apps/tui.md`](../architecture/apps/tui.md) § Rendering; one of the three bugs motivating [`../architecture/e2e-conventions.md`](../architecture/e2e-conventions.md) convention 17), and iOS resets with a comment saying exactly why. On the resume side it is **emergent**: a GTK `Stack` and a SwiftUI `@State` simply keep their last value, and no app defends the behavior anywhere. Decisively, the canonical entry was **already the de-facto cross-app rule on the nav path** — macOS, Windows and linux's agent all resolve an id-less shell nav to the shell's first page, and linux's own code comment calls the alternative "a per-app divergence (priority #1)" and records it making a crash-recovery journey red on linux while green on macOS. Ratifying the canonical entry writes down what three apps had already converged on; ratifying "resume" would have broken them. A stale sub-page is the worse failure mode besides: the user who wanted their last page loses one click, while the user who did not know a shell remembers is left facing a surface they never asked for, with no affordance naming the way out. Priority #4 — resolve drift, pick the principled pattern rather than the incidental one — therefore rules for the canonical entry.

**Conformance today (2026-08-14).** **4 of the 7 apps already conformed before this ruling** — **tui** (`apps/fauna-tui/src/app.rs::set_page`, nav-edge reset for Settings + Admin, pinned by `walk.rs::returning_to_settings_via_the_sidebar_always_lands_on_the_rail_root`), **ios** (`Fauna-iOS/App/ContentView.swift`, `selectedSettingsPage = nil` on the More-hub entry and on leaving the sub-view), **web** (the `settings-tab` href is the id-less `/app/settings`, so entry is canonical by construction), **windows** (`MainPage.xaml.cs` navigates a fresh `SettingsShellPage`/`AdminShellPage`, whose `Page_Loaded` selects Status/Dashboard). **linux conforms as of 2026-08-13** (`apps/fauna-linux/src/app.rs`, the content-stack `visible-child-name` notify that already swaps the rail now also seats the shell's sub-stack on its root; pinned by `walk.rs` sweep 4). **android was MEASURED 2026-08-14 and conforms as of the same day.** It had been the one app whose landing was unreadable from source — its drawer navigated with `popUpTo(saveState = true)` + `restoreState = true` over a *flat* graph, where the answer belongs to Navigation-Compose's saved-back-stack machinery rather than to anything we wrote. Driven headlessly (`DrawerShellReEntryTest`, a real `NavHost` over the shipped route shape, no emulator — the observable is a `NavController` destination, not a pixel), the flat graph turned out to restore exactly as the multi-stack idiom advertises: leaving Settings from `settings/account` and re-entering through the drawer landed back on `settings/account`, and a deeper visit restored `settings/admin-users`. **So android resumed, and now does not:** `FaunaNavHost.kt::navigateToDrawerRoute` withholds the restore on the shell entry edge alone (`restoreState = !enteringShell`), leaving ordinary pages' own stacks — qualification 3 — untouched. Its canonical entry is the **Settings hub** (`composable("settings")`), the mobile idiom iOS's More-hub also lands on, not the desktop rail's Status. Qualification 1 already held before the change and is pinned by the same test so the fix cannot silently take it away. Two notes on the strength of that pin: the drawer and the test agent now cross **one** shared edge (`TestAgent.kt::applyNavPatch` calls the same function), which is what makes qualification 4's linux failure mode — an agent that resets while the real affordance does not — unrepresentable here rather than merely untested; but no test yet *taps the drawer widget itself* on a device, so the last inch stays owed to the host emulator. **macos conforms as of 2026-08-24** — the last gap, closed. `MacAppState.selectedSidebar`'s `didSet` (`Fauna-macOS/App/AppState.swift`) is the one edge every writer of the property passes through — the rail's `List(selection:)` binding, `.automationActivate` closures, keyboard shortcuts, the quick switcher, and the state-protocol nav patch alike — so none of them need their own reset: crossing into `.admin`/`.settings` (`oldValue != selectedSidebar`, qualification 1's reload guard) resets `selectedAdminPage`/`selectedSettingsPage` to `.dashboard`/`.status`. Pinned by driving the real `admin-tab`/`settings-tab` sidebar rows through the automation registry — never a nav patch, which macOS's own `applyNavPatch` already resolves correctly regardless of edge-vs-reload and would read conformant either way (qualification 4's trap) — in `tests/e2e-unified/tests/test_macos_shell_canonical_entry.py`.

**A shell sub-page must paint a real, visible heading — title metadata a container never renders does not satisfy `page-heading` (ratified 2026-08-13).** ui.yaml's `global.elements` already requires `page-heading` (or a page's own designated landmark/heading id, where its own `elements:` block names one in its place — today `muted-words`, `settings-logs`) on **every** authenticated page, sub-pages of a shell included; this is not a new rule. The gap a walk found on linux (`apps/fauna-linux/src/walk.rs`, pinned today by `check_surface_has_a_heading`/`every_settings_sub_page_upholds_the_invariants`) is one of *implementation*, not spec: a title can be set as inert metadata a shell's specific container never paints, so the id genuinely reaches nobody's screen — the same failure class the canonical-entry rule above exists to catch on the navigation side. Measured across all 7 apps on the 8 Settings sub-pages sharing linux's rail — Account, Privacy, Muted words, General, Encryption, P2P, Web, Logs (2026-08-13; full per-app table in [settings.md](settings.md) § Implementation status today):

- **linux was the one shell comprehensively broken on this rule** — all 8 sub-pages showed no heading of any kind: each is an `adw::PreferencesPage` with a `.title(...)` that paints only inside an `adw::PreferencesWindow`, and the sidebar-swap shell hosts them in a plain `gtk::Stack`, which ignores it entirely. **Fixed 2026-08-14** — every sub-page now paints a real, visible label per page (not a metadata change); full per-page table in [settings.md](settings.md) § Implementation status today.
- **iOS's Logs sub-page has the identical defect, independently, for an unrelated reason.** macOS's shell wraps every sub-page in one shared `.pageTitle()` call outside its switch (`SettingsShellView.swift:123`), so an individual sub-page needs no title of its own; iOS instead pushes each sub-page raw via `NavigationStack` with no such umbrella, and `LogsView` itself never calls `.navigationTitle`/`.pageTitle`. Owed to `apple`/ios — tracked internally.
- **web, windows, macos and tui already conform** for every sub-page they build — web via one shared `<h1 data-testid="page-heading">` mounted outside its `{#if}` sub-page switch, windows and tui via a real per-page label, macos via the shared `.pageTitle()` wrap. This is the richest existing pattern, which is why the ruling is "paint the missing heading", not "relax the requirement" — the alternative the finding first raised (amend § global so a shell's rail-row selection alone counts as the heading) is **rejected**: it would weaken an already-shipped, working contract on 5 of 7 apps to excuse 2 apps' bugs. **General and Encryption landed on tui 2026-08-14** (`apps/fauna-tui/src/settings/{general,encryption}.rs`, both painting `page-heading` first in their element list) — the standing tui-parity gap this measurement's 2026-08-13 snapshot found is closed; tui now conforms on all 8 sub-pages.
- **android and iOS both carry a narrower, second-order gap** on several already-visible titles: a real title paints and a sighted user sees it, but the element carries no `page-heading`/`*-heading` id, so it is invisible to automated and accessibility tooling. android: Account, Privacy, Muted words, Encryption. iOS: Account, Privacy, General, Encryption. Same rule, cheaper fix (tag what already renders) — tracked internally.
- **P2P is a Settings sub-page only on linux and tui**; the other five surface it differently or not at all (windows: a top-level nav page, not inside Settings; web: a redirect stub; android/macos/ios: no page). That per-app shape split is not itself a question this rule settles — see [`../behavior/p2p.md`](../behavior/p2p.md) § Implementation status today.

## Copy comprehensibility

**Ratified 2026-08-03** (the systematic comprehensibility audit; triggered by live-user reports of technically-correct-but-useless UI text). Nearly all user-facing copy is shared (`i18n/strings/en.yaml`), so this standard binds **all 7 apps at once** — a string that fails it fails everywhere, and a fix lands everywhere. A page author or reviewer self-checks every user-visible string against the four questions:

1. **Does it say *what happened*** — not just that something didn't work? ("Failed to load posts: {message}" passes; a bare "Error" does not.)
2. **If it's a refusal or error, does it say *why* — or point at what to check?** The canonical failure: `media.error_no_set` was "Select a folder to upload into first.", technically correct while every one of the user's sets failed the (unstated) upload-target rule — correct copy that leaves the user stuck is a UX bug even when every test passes. Two *different* conditions deserve two *different* messages (the `error_no_set` / `error_no_sync_set` split, `media.md` § Errors & edge cases).
3. **Does it use a term the user has any way of knowing?** A mode name, a technical concept, or a scheme the UI never explained fails here unless the screen carries its one-line explainer (rule 5).
4. **Would a first-time user, with zero context, know what to do next?** Refusals name the action and the place ("Create a folder under Settings → Folders"), not just the state.

Two structural corollaries:

5. **One line of context per consequential choice; zero lines of lore.** Every choice with consequences (a mode, a policy, a retention rule) carries one short explainer for the *selected* option — the `devices.wizard.{sync,backup,web}_desc` family is the shape — and every **disabled** control the user can see has an on-screen reason within eyeshot ("Enter a name to continue.", "create a tier first", `restore-progress`'s "Select a snapshot and re-type its id to restore."). Bounded on both sides: "you have to know it all already" minimalism fails a first-time user (user directive, 2026-08-03), and walls of tutorial prose fail everyone.
6. **State legibility is copy's twin.** A message can only be judged against what the screen shows: a one-of-N group must display *which* option is current, a picker must display its current *value*, a required field must be distinguishable from an optional one. Per-platform vocabulary is each app's (tui's: `../architecture/apps/tui.md` § Rendering → *Control vocabulary*); the requirement is cross-app.

**Enforcement split (what's mechanical vs judgment).** Questions 1–4 are judgment — re-audited cheaply via each app's corpus reader where one exists (tui: `walk.rs::dump_screen_text_corpus`, one command for every screen's painted text). Rules 5–6 harden into per-app invariants where expressible (tui's walk I3: no input may prompt with its raw element id). Shared state machines pin condition→key splits in their own tests (the two-key media pin in `fauna-media-machine`).

**Known non-conforming clusters: none.** The last two fragment strings closed 2026-08-03 — `onboarding.oob_error` (with its row-sibling `oob_invalid`) and `task_delegation.error_device_id` — joining the two flat-failure *families* (`devices.*` author gestures and `admin.*` page errors, both 2026-08-03; `conversations.recipient_resolve_error` was the first single fix). The precedent the families set is below; the fragments added one of their own:

**Precedent — a fragment's copy is decided by which conditions can actually reach it.** Both fragments were unwritable until their producer was traced, and in both cases the reachable set was *narrower* than the string implied. `oob_error` reads as one generic failure, but `InviteCodeError::Malformed` has no construction site anywhere (only a declaration, a comment saying the generic `ApiError` conversion never produces it, and a consuming match arm), so the only condition that reaches it is `Transient` — the nest was never reached and the code was therefore **not judged**. First-run copy that let that read as a rejection would be actively wrong, which is why the pair now splits the two meanings explicitly rather than sharing a shape. Conversely `task_delegation.error_device_id` names a condition no app should ever reach; **copy is not the fix where the state itself is a defect** — write the string for the residual "genuinely could not read the local store" case, and raise the defect separately rather than letting good copy make a broken state look intended.

**Precedent — how a flat-failure cluster is closed.** The keys were *prefix-only by convention*: each app was expected to append `": <detail>"` itself. Nothing enforced that, so the same failure read "no actor for handle 'bob'" on linux and "Failed to share folder" on tui. **The fix makes the placeholder the contract, not the convention:** every key in the family carries `{message}`, and no app concatenates — each resolves through the parametric form its platform already generates (`devices::error_share_set(&detail)`, `t.devices.error_share_set({message})`, `S.Format("devices/error_share_set", detail)`, `getString(…).replace("{message}", …)`). Sweep the whole family across every app that implements it, in one change — a per-app fix re-creates the convention. Three defect classes surface only once a family is swept that way, and are worth looking for in the next one:

- an app pairing the key with a **generic** error renderer that drops which gesture failed;
- an app rendering the raw exception **instead of** the string, so the banner says *why* but never *what* (web's whole `admin.*` surface did this: `e instanceof Error ? e.message : t.admin.…load_tiers_error`);
- an app pairing the detail with a **label** string instead of the error key — android rendered "Serve over WebDAV: …", which never says anything failed at all.

**Precedent — rule 5 binds the PRE-FETCH window, and a hand-rolled pre-fetch state is how it breaks (ratified 2026-08-14).** A page whose disabled controls carry their reason *after* its first read can still paint them bare *before* it, because the pre-fetch state is a different object — and where the shared machine's own `Default` is unreachable across the FFI/wasm seams, every app invents that object separately. Measured on the Bluesky/atproto page: `AtprotoSettingsSnapshot::default()` is the ratified pre-fetch state (gate CLOSED, carrying `gate_reason_pending`), but UniFFI generates no constructor for a `Record`'s `Default` and the wasm face exported none, so **four** apps hand-rolled a stand-in — android's full record literal drifted from the Rust default **twice** (`hostedGateReason`, then `showDidMethodRadio`), apple and web kept one-key fallbacks that covered the gate reason and nothing else, and windows had none at all and shipped a pre-fetch page whose gate rendered **open** — the inverse of the contract. Every one was invisible to tests, because a per-app stand-in is only ever checked against itself.

**The rule this sets: a shared machine's default is part of its contract, so export it wherever it is not the type's own zero value.** That is the mechanical test — `Default` that merely zeroes every field cannot drift meaningfully, but one with *deliberate* non-zero fields (here five: `level: "off"`, `hosted_gate_reason: Some(pending)`, `did_method: "plc"`, `show_did_method_radio: true`, `external_apps_enabled: true`) encodes decisions an app cannot re-derive and must not restate. Export it as an explicit free function on **both** seams (`atproto_settings_prefetch_snapshot` / `atprotoSettingsPrefetchSnapshot`), have each app seed its pre-fetch state from it, and delete the stand-ins rather than re-syncing them — a second source of truth is the defect, not the drift. Corollary for reviewers: an app-side literal that a comment describes as "mirrors the Rust default" is that defect already, whatever its current values say.

**A local refusal is not a threading case.** Where the app declines client-side and no request is ever built, there is no detail to thread: answer Q2/Q4 in the string itself — name the rule that was broken and the control that fixes it, by its visible label (`admin.settings_page.save_tier_error_invalid_cap`, `…save_membership_tier_error_no_tier`). Reusing the network key's flat prefix for a validation refusal is the anti-pattern; it tells the user an operation failed while withholding the one thing they can act on.

## List pages: loading is not empty

**Ratified 2026-08-05** (generalized from the Media page's three-state fix the day it landed, after the identical defect was found unfixed on the community-labelers catalog). A page whose content is a list read over the wire has **three** renderable states, not two, and the row list alone can only distinguish two of them — it is empty **both** before the first read returns **and** after one that found nothing. Every empty-state element therefore takes a **second painting condition**: the page's own *has the read resolved* bit.

| loaded | rows | render |
|---|---|---|
| `false` | (any) | still loading — no rows, and **no** empty state |
| `true` | empty | the genuine empty state |
| `true` | non-empty | the rows |

Four rules, all cross-app:

1. **The bit lives in shared Rust, on the page's own snapshot**, set in the one place the rows are assigned and named `loaded` (priority #2: one field, seven apps, no per-app re-derivation). An app-side `snapshot != nil` is **not** a substitute — it answers "did a read return *or fail*", and a failed first read must stay unloaded.
2. **Monotonic.** Set on the first read that *returns successfully*, never cleared. A first-read failure keeps the page unloaded, so `error-message` does the talking rather than a false "nothing here" beside it; a later failure keeps prior rows on screen, so the loading state is never re-armed under content the user can still see.
3. **The loading state paints no ID of its own.** The **absence** of the empty-state element alongside zero rows is what identifies it — three states off one ID, and no wall-clock inference for a driver to make (`../architecture/e2e-latency-independent-assertions.md` convention 14). Minting a `*-loading` ID is the exception, not the default, and needs the same rule-A approval as any new element.
4. **A page whose list is derived, not read, is outside this rule** — a per-row facet arriving with its parent row, or a client-side filter over an already-loaded list, has no read of its own to wait on. The filtered facet inherits its *source's* bit rather than inventing one (the Personalization home's subscribed-labelers facet reads the catalog's).

Shipped instances, each owning its own field and element names: the Media page ([media.md](media.md) § Default view); the community-labelers catalog + the Personalization home's subscribed facet (`LabelerCatalogSnapshot.loaded`, one machine feeding both, per [content-moderation-and-ranking.md](../architecture/content-moderation-and-ranking.md) § Tier-3); and the Muted-words sub-page (`MutedWordsSnapshot.loaded`, same doc's § Implementation status today leg 4 — which also records the ruling that **rule 1 does not require a state machine**: the bit rides a shared page *record* minted by the shared read, which is what a machine-less account-state-backed page needs). Two more pages were already correct before the rule was written and are the precedent it generalizes: Web settings' published-posts section (gated on its `view` hydrate signal) and the trained-factor publish sheet's exemplar list (gated on `scored`).

## A cancellation is not an error

**Ratified 2026-09-21.** A request the app itself stopped caring about must **never**
paint an error surface. A cancellation is not a failure: it means a view went away (a
tab switch, a navigation, a launch verdict seeding the wizard, a session teardown
replacing the shell) and the work it had asked for is no longer wanted. Nothing went
wrong, and the user asked no question that went unanswered — so a red
"HTTP error: cancelled" states a problem that does not exist.

Two properties make it worse than a merely redundant line, and both are why this is a
rule rather than a nicety:

1. **The error channel is global** (`../architecture/e2e-conventions.md` convention 2 —
   an app's `messages.error` is "an error is being shown", not "*this page* has an
   error"). A banner raised by a view that has already gone follows the user onto
   whatever page they land on next, where it is not just noise but a false statement
   about *that* page.
2. **Cancellation is the normal end of an in-flight read**, not a rare fault, so the
   line appears during ordinary use — most visibly right after launch, when the shell
   the app first rendered is replaced by the one it settles on.

Three rules, all cross-app:

1. **The mapping from a thrown error to display text is ONE shared function per app
   family**, not a decision each catch block makes. It returns *no text* for a
   cancellation, which is what every "no error" field already means. Sixty FaunaKit
   call sites spelled the mapping inline before this rule, so one of them getting
   cancellation right would have left fifty-nine wrong.
2. **It recognises every spelling the platform throws** — on apple, Swift concurrency's
   `CancellationError`, `URLSession`'s `URLError.cancelled` (whose
   `localizedDescription` is the bare word "cancelled"), and the same condition already
   bridged to `NSError`.
3. **Suppression is at the display boundary, never at the source.** A cancelled request
   is still worth a log line and still leaves the page unloaded (§ *List pages: loading
   is not empty*, rule 2 — a first read that did not return successfully keeps the page
   in its loading state). What the rule removes is the *red sentence*, not the fact.

## Auth model

All pages except Login/Onboarding require an identity (secret key in the platform credential store — owner: [common.md](../architecture/apps/common.md) § Credential storage). The identity consists of:

- **Secret key** — Ed25519 seed (32 bytes, hex-encoded)
- **Actor ID** — derived public key (hex-encoded)
- **Handle** — user-chosen name (e.g. `alice`)
- **Domain** — nest domain (e.g. `nest.fauna.social`)
- **Tier** — account tier (e.g. `free`)
- **Registered** — whether the user has completed registration

Admin pages are additionally gated on the nest-admin check — the WS-RPC kind `fauna.account.am_i_admin` (gate mechanics + the admin shell: [admin.md](../behavior/admin.md)). ui.yaml `navigation.gated_tabs` records the gated tabs.

This file remains the ui-directory index for ui-specific conventions; its routing content defers to the top-level registry ([../README.md](../README.md) § Registry).
