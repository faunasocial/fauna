## Goal

The Media page lets the user upload, browse, and manage their media (images, videos, files). **Resolved paradigm (2026-06-28):** **folders are the substrate, and Media is the media-optimized *view* of them** — a Windows-Explorer-style browser over the files inside the user's folders. It defaults to a unified **all-media** view aggregating files across every readable folder, with a per-set filter to scope to one.

This collapses the three paradigms that previously coexisted into one:

- **generic upload** (web / Linux) → "upload into a folder" (upload targets the selected set).
- **folders** (Windows / macOS / Android) → the substrate itself; Media is its viewer.
- **photo backup** (Apple, iOS + macOS — the shared FaunaKit `PhotoBackupControlsView` over `PhotoBackupEngine`, PhotoKit-only) → an **ordinary folder over the photo library** ("Photo Library"); its PhotoKit ingress feeds the set, the photo-backup *controls* become that set's configuration under **Settings → Folders** (not on the Media page), and Media shows the unified explorer — including the Photo Library set — instead of a bespoke `PhotoBackupView`. See § Photo-backup reframe.

So **Media (content plane) browses the files; Settings → Folders (control plane) configures the sets.** Folder creation, device places, retention, roster, selective-sync paths, location binding, and conflict resolution all live in `docs/goal/ui/folders.md` — Media only *reads* the sets and never configures them. (`folders.md` is the authority for that control plane; do not duplicate its prose here.)

## Layout & flow

Media is a **Windows-Explorer-style file browser** over the media inside the user's folders:

- **List ↔ thumbnail (grid) toggle** (`media-view-toggle`) — switch between a detail-list view (name / size / date columns) and a thumbnail-grid view.
- **Sortable** by name / size / date (`media-sort-select`). A single select, uniform across form factors; desktop *may* render it as clickable column headers, mobile/web as a dropdown — same ID either way.
- **Sort direction** (`media-sort-direction`) — a select over the stable values `ascending` (the **default**) / `descending`, applied to whatever `media-sort-select` key is active. Uniform across form factors like the key select; a desktop column-header rendering *may* express it as the header's second click, but the ID and its two option values are the same everywhere. The ordering itself runs in shared Rust (`MediaSnapshot::view`'s `descending` — § O-4's "re-sorts/filters … in shared Rust"), so no app re-derives it. **A direction is a select, not a toggle, deliberately:** a toggle's result depends on the current state, so a caller that needs a *known* order must read state first and can still race it, whereas setting a direction is idempotent. (User-approved 2026-07-30.)

  **Why direction is load-bearing, not just a preference.** Apps are free to render the list lazily (the macOS grid is a `LazyVGrid`), and a row that never materializes registers neither its cell nor its name — so an off-screen item is indistinguishable from an absent one to any reader, in-app or automated. Under a name-ascending sort, date-prefixed files sort to the **tail** of a growing set, which is exactly where a lazy list stops registering. Ordering newest-first puts the rows that matter at the **head**, which every app registers, converting an unenforceable *completeness* requirement into a one-action *ordering* one.
- **Per-set filter** (`media-folder-filter`) — scopes the browse to one folder, or (the **default**) the unified **all-media** view aggregating files across every readable folder.
- **Upload** (`file-upload` — the path input, which a **native picker beside it fills** on every app that has one — + `upload-button`) — uploads the chosen file(s) **into the selected folder**. ⚠ The phrasing here read "text-input *acting as* a file picker" until 2026-08-06, which is ambiguous in the one way that matters: it can be read as "the input stands in for a picker, so no picker is needed", and linux shipped for two months with no picker at all on that reading. The shape is **both** — the input is the drivable source of truth (see § Where logic lives) and the picker is a convenience that writes into it — with **tui the sole exception** (no OS picker exists in a terminal; matrix row below). (When the all-media view is active with no single set selected, the app prompts for / defaults the target set; the upload always lands in exactly one set.)

  **Where the offerable sets come from — the control plane, not the items (ratified 2026-08-03).** The `media-folder-filter` options and the upload target are derived from the caller's **folder list** (`fauna.folders.list`), never from the sets *present in the media aggregate*. The distinction is the whole difference between a set being reachable and not: a set created in Settings → Folders holds nothing yet, so an item-derived list omits it — leaving it unselectable in the filter *and* skipped by the upload default, so the one action that would give it media is the action it blocks. **Two lists, deliberately different scopes:**
  - **Browse options** = **every** user folder of the caller's (the same scope § O-4 gives the aggregate — only reserved `__*` sets are never Media), whether or not it currently holds media. The former web-type exclusion is **retired** (folders re-model phase 4, 2026-08-17, executing open call #4 ratified 2026-08-13): a website-published folder appears in Media like any other — the website is a serving toggle over the same substrate, not a separate content plane.
  - **Upload targets** = **every folder in the caller's own list.** A folder has no type ([`../behavior/folders.md`](../behavior/folders.md) § Target re-model), so the former sync-type-only rule retires (ruled 2026-09-28, the folders mode contraction design pass; built 2026-09-28). What stays excluded is structural, not a type: reserved `__*` sets (never in the list) and followed public folders (§ Followed public folders — never in `known_folders`). A Media upload records a head row like any writer; which devices then receive it is each device's place (`accepts`), so uploading into the Photo Library folder is legitimate — the phone's ingress feeds it and its other seats receive it, exactly as for a file dropped into any folder. *(History: the original projection-mismatch rationale — Backup sets read from `backup_custody`, invisible to a `sync_changes` upload — retired with the 2026-08-17 head unification; the model reason that replaced it — "a Backup folder's content is what its source device backs up" — retires with the type itself.)*

  Sets shared *with* the caller keep reaching Media exactly as they always have — through `fauna.media.list`'s own readable-set scope, once they hold media. The client's own list is read **owner-scoped** (`include_shared_with_me` unset) on purpose: the member-visible projection returns rows that are only *rostered* nest-side, so rendering it requires the client-side MLS join-filter (`folders.md` § Sharing; the anti-abuse control behind `fauna_devices_machine::MlsQuery`), and Media has no need to widen that surface to fix an option list. Losing the control-plane read (an older nest, a transient failure) degrades to the item-derived options rather than erroring the page — media is the read that matters. [Shared Rust: `MediaSnapshot::folders` / `upload_targets` in `libs/fauna-client-media`.]
- **Per-item rows/tiles** are the `media-item` component (indexed), each carrying name (`media-item-name`), size (`media-item-size`), date (`media-item-date`), thumbnail (`media-thumbnail`), and a **source online/offline status** dot (`media-source-status`).

### Default view: cross-set all-media

Media **opens on the aggregated all-media view** — every readable folder's media in one browse, sorted by the active `media-sort-select` key. `media-folder-filter` narrows to a single set when the user wants it.

**Three renderable states, and the empty one is `media-empty-state`** (approved 2026-08-05). This page obeys the cross-page rule in [`README.md`](README.md) § *List pages: loading is not empty* — which owns the three-state table, the monotonicity of the `loaded` bit, and why the loading state paints no ID of its own. This page's own two names for it: the bit is **`MediaPageSnapshot.loaded`** (set when a `refresh()` first returns successfully) and the element it gates is **`media-empty-state`** ("No media yet"), so `loaded && items.is_empty()` is the empty state and the *absence* of `media-empty-state` beside zero `media-item` rows is the loading one.

That absence is also the harness's read: it lets an empty listing settle immediately instead of polling to a deadline, and makes a page that never loads fail loudly (`e2e-latency-independent-assertions.md` convention 14; `tests/e2e-unified/helpers/multiseat_config.py::settle_listing`).

### Source status vs. sync state — two distinct signals

`media-source-status` is the **folder's** content-reachability dot — green when the folder's files can be fetched right now, red when no holder of them is reachable; when red, some files may be unavailable to fetch. **What "reachable" means — which holders count (the nest place when it holds the content, otherwise the seats the relay read path would ask), why it is not any device's liveness and not one designated source seat's, and the copy's vocabulary — is owned by `../behavior/file-sync.md` § Content reachability (ratified 2026-09-22); reference it, never restate it.** This is **distinct from** the per-file `sync-state-badge`, which is **this file's own** presence. Both ride the `media-item` row and answer different questions: source-status is the *folder's* reachability, the badge is the *file's* state.

### Thumbnails

Each `media-thumbnail` renders the item's thumbnail blob. Thumbnails ride the existing wire: the uploader's `UploadSidecar.thumbnail_hash` (`libs/fauna-media/src/sidecar.rs:26`) points at a separate thumbnail blob sealed under the same audience as its parent — no new thumbnail wire is introduced, Media consumes what upload already produces. The cross-set explorer fetches it through the **shared-Rust `MediaMachine::fetch_thumbnail`** (FFI + wasm): `MediaItem.thumbnail_hash` → `GET /api/v1/blob/<hash>` **direct-by-hash** (**not** `?thumb=1` — a Media-library / device-synced item has no `/api/v1/blob` primary with `blob_metadata` for `?thumb=1` to resolve) → **verify the content address** (`blake3(fetched sealed bytes) == thumbnail_hash`, rejecting a substituted blob — the backup-chunk AEAD frame carries no AAD, so its tag proves only *owner-sealed*, not *this* blob; security review) → decrypt under the owner `BackupKey` → decoded bytes the client paints (`bins/fauna-nest/src/blob_routes.rs` by-hash GET). (The `?thumb=1` routing is the **feed**-attachment render path, where the client holds only the primary blob's hash — § Implementation status.) Images carry C2PA provenance where present (§ C2PA provenance).

## Followed public folders — the followed browse scope (design ratified 2026-08-19; BUILT the same day — shared Rust + tui, the other six trickle down)

Behavior owner of the follow itself: [`../behavior/folders.md`](../behavior/folders.md)
§ Publicly-synced follow (address, floor, strip, zero nest-side state, keyless read); the
follow *gesture* and the followed row on the Folders page: [`folders.md`](folders.md)
§ Following a public folder. **This section owns how a followed folder browses in Media** —
the promise those two sections make ("browses in **Media** on demand like a shared set a
reader holds").

**A followed folder is a browse SCOPE, not a set in the aggregate.** Its rows live on its
*home* nest behind `fauna.folders.public.fetch`; the follower's own nest keeps no copy, so
`fauna.media.list` structurally cannot serve them and the **all-media default view never
includes followed content** — deliberately, not just structurally: eager aggregation would put
one relayed cross-nest fetch per follow on every Media refresh, the exact fan-out the
availability-probe design bounded (`behavior/folders.md` § Publicly-synced follow), against a
plane whose throttles exist because serving it is metered by nobody. Selecting the scope is
what fetches, once, on demand — the same browse-on-demand boundary the follow's v1 non-goals
draw.

**Identity lives on the scope, never on the item.** The scope is addressed
`(home_nest_url, folder_id)` — the follow record's pinned identity. Items inside it render as
ordinary `media-item` rows off the **unchanged `MediaItemSummary`** (`folder` carries the
follow's display name for rendering; nothing routes on it). The machine holds the active scope
and is the single source of the address, so an app can never pair the wrong identity with a
row; when a followed scope is active the machine fills the snapshot's `items` with the
followed listing, so the per-app list render is byte-identical to the ordinary browse.

**The read model, all shared Rust** (`public_follow` owns the mechanisms; the machine wires
them):

- **Listing** = `fetch_followed_changes` + a pure client-side **head fold** (latest change per
  path wins; a path whose latest change is a delete is not listed) — the public plane serves
  raw change rows above the floor, and no fold helper exists yet; it belongs beside the other
  pure functions in `public_follow`, tested without a nest.
- **A browse fetch is availability evidence.** Its success/refusal feeds the same cached
  verdict the probe writes (`CachedAvailability`) — one mechanism, never a second parallel
  probe racing the first. A refused fetch (the plane's own `not_found`) surfaces the folded
  wording on the page-level `error-message` and flips the cached verdict; a transport fault
  stays a transport error, never the revoke — the same rule `availability_from_probe` pins.
- **Downloads** = `public_follow::download_followed_file` through a fetcher bound to the
  scope's `home_nest_url` from the **already-injected `ForeignBlobFetcherFactory`** (the seam
  cross-nest shared sets use; an empty `home_nest_url` — a same-nest follow — uses the
  machine's own fetcher, mirroring `download_file`'s two arms). **The dial to another nest is
  verified against the identity the public-fetch reply stamped** — the scope carries the
  record's `home_nest_actor_id` to the factory, and the native fetcher graduates the home's
  SPKI pin against exactly that root before the first byte
  ([`../architecture/security.md`](../architecture/security.md) § Transport trust, the
  federation-granted row: the follower holds no account there, so this is the byte plane's only
  trust root; a self-signed home works, a WebPKI home is unchanged; the browser, which cannot
  pin, keeps WebPKI). **Never `download_file`, never
  `folder_keys_for`, never `LabelCustody`** — the keylessness is structural (the shared op's
  own ⚠ paragraph owns why), and a followed read touching the name-keyed custody resolver is a
  bug even when it appears to work.
- **Filter options are shared-Rust-owned.** The followed scopes ride the snapshot as their own
  option list beside `folders` — each option a machine-minted **opaque stable value** plus a
  display label (`<display name>` + the same owner string the `folder-followed-item` row
  shows, which is what disambiguates a name collision with an owned set at the label level).
  Apps append them to the existing `media-folder-filter` select and hand the chosen value back
  to one shared gesture; the value↔scope mapping lives in shared Rust, and values are
  guaranteed disjoint from set names (priority #2 — no app re-derives any of it).

**The scope is read-only, structurally.** Never an upload target (`upload_targets()` derives
from `known_folders`, which a follow never enters); no delete, no restore, and **no version
history** — the public plane is head-only by the follow's v1 non-goals, so the item detail
for a followed item offers download alone. Availability rendering follows the Folders row's
contract: unavailable keeps the scope listed (the revoke is loud, not silent), and the
three-state loading rule (`README.md` § List pages: loading is not empty) applies to the
followed listing exactly as to the aggregate.

**Thumbnails: ESTABLISHED 2026-08-19 — a public folder's thumbnail blobs rest SEALED, never
plaintext, so a followed row renders no thumbnail and that is the permanent v1 answer, not a
gap.** The question this paragraph used to leave open is closed by two facts in the engine,
and no leg should re-open it. **(1) The seal is unconditional and audience-independent**:
`maybe_upload_thumbnail` / `_from_path` (`libs/fauna-sync-engine/src/engine.rs`) seal every
thumbnail under `fauna_media::audience::Audience::Library { backup_key }` — the **owner's raw
`BackupKey`** — and deliberately stay on the raw key rather than the bound-set-aware
`effective_backup_key` (the reasoning is written at that function). Nothing in either producer
consults the folder's audience. **(2) The audience converge never touches them**:
`declassify_owner_corpus` walks `Synced` *file entries* and re-seals *content* through
`reseal_path_under_current`; a thumbnail is a **separate blob**, addressed by its own content
hash recorded on the folder member, and no declassify path re-records it. So both reachable
states of a public folder rest sealed — a file uploaded while already public still seals its
thumbnail under the owner key, and one uploaded before the flip keeps the sealed blob the
converge left alone.

A follower holds no key, structurally, so it can decrypt neither. **A followed row therefore
paints the placeholder degrade this page already has** — never an error, and never a key hunt:
reaching for `folder_keys_for` or the custody resolver here is the architectural-rule-6
violation that "appears to work" only when it is finding an owned set's key. Making followed
thumbnails possible at all is a *producer* change (a plaintext thumbnail audience for public
folders), which is its own slice with its own privacy question — a thumbnail is a legible
downscale of the content, so publishing one is a real disclosure decision, not a rendering
detail — and it is explicitly out of scope for v1.

**No new element IDs in v1.** The scope rides `media-folder-filter` (options are data),
`media-item`, `error-message`, and the empty/loading chrome. A followed provenance marker on
the browse header, if ever wanted, is its own rule-A ask — do not smuggle one in.

**Two refuted alternatives, recorded so nobody re-derives them** (the full weighing:
`behavior/folders.md` § Publicly-synced follow): (i) **widening `MediaItemSummary` / the
custody resolver to an identity address** — refused for this slice: a follow never consults
custody, so the widening would not serve it, and it would re-open the deliberately-deferred
channel-keyed custody direction (the owned-shadows-foreign precedence and its
"menu (c)" future) as a rider on a UI slice, at the cost of a 7-app data-shape trickle-down
with zero follow-side benefit; (ii) **eager aggregation into all-media** — refused above. The
pre-existing name-key latency for foreign *shared* sets is explicitly **not this scope's to
fix** — it stays owned by the shadowing rule at
`libs/fauna-client-folders/src/custody_ingest.rs::resolve_custody_from`.

## State & data shape

**Backing shared surface: the cross-set `media_snapshot()` (the `fauna.media.list` RPC).** Media reads a single shared-Rust snapshot that **aggregates media items across every readable folder**. Per item it carries (the **settled O-4 wire shape**, `libs/fauna-protocol/src/media.rs` `MediaItem`):

```
{ folder, path, size_bytes, updated_at, thumbnail_hash: Option<hex>, source_online: bool }
```

plus the active view state (list/grid toggle, sort key, folder filter) and upload progress (client-held view state, not part of the RPC), plus **`loaded`** — client-held, not on the wire: whether a `refresh()` has ever returned successfully. It is the `media-empty-state` element's second painting condition (`README.md` § List pages: loading is not empty owns the three-state rule); the machine sets it in the one place `raw` is assigned and never clears it.

**Staying live while the page is open.** A file can land in a set from outside this page at any moment — the device's own sync engine picking up a watched folder, a second device, or a collaborator. While Media is on screen the page **re-reads the aggregate when that happens**, with no navigation and no manual reload; the arrival is not deferred to the user's next visit. The signal is the existing remote-change nudge — `PushEvent::SyncChanged` / `fauna.sync.changed`, whose fan-out, delivery guarantees and correctness backstop are owned by [`../behavior/file-sync.md`](../behavior/file-sync.md) § Remote-change nudge — so Media grows no wire, no poll, and no mechanism of its own; it becomes one more consumer of a rail every app already handles. **Scoped to the page being on screen, deliberately:** entering Media already re-reads the aggregate, so an arrival while the user is elsewhere is covered by the visit itself, and this is a cross-*set* read that an initial folder sync would otherwise re-run once per recorded file. Push is the latency path; per that owner section the periodic reconcile remains the correctness path, so a dropped nudge costs freshness, never data. **The behavior is what is ratified, not the mechanism** — where an app has no push arm on this surface a poll delivers the same guarantee more coarsely (web does exactly that today, § Implementation status today), which is the same push-primary/poll-backstop split [`events.md`](events.md) § Implementation status today already carries for the identical staleness.

**Per-item version history** (the `media-item-detail` surface) reads `fauna.files.versions.list` scoped to the item's `(folder, path)`; the projection semantics, `version_num` identity, and restore mechanics are owned by [`../behavior/file-versions.md`](../behavior/file-versions.md) § File Versions — Media only renders the list and drives the restore helper.

## Persistence

Media items live in the nest's blob store as content-addressed blobs — a folder's file as chunks behind a `ChunkManifest`, the one shape every producer writes (§ Encryption at rest → *One at-rest shape*, ruled 2026-10-06), its thumbnail as one blob of its own; their folder membership lives in the folder rows the substrate owns (`docs/goal/behavior/file-sync.md` § Content-Addressed Storage). Apps may keep the images they paint (thumbnails, post images) in an in-memory per-content-hash cache while they render — a hash names immutable bytes, so an entry never goes stale — and may cache upload progress locally; none of it is part of the persisted contract. Where an app's image path runs in Rust (tui, linux) the cache's load-state bookkeeping (loading / loaded / hopeless, per key) is shared, `fauna_core::load_cache`; the fetch, the decoded payload and how a loaded image reaches its widget are per-app glue. The same cache holds a revealed third-party remote image keyed by **url**, apart from the by-hash entries (a url names bytes that can change). **Hopeless is a property of the bytes, not of one attempt:** a fetch that failed because the nest was unreachable, timed out or overloaded (`fauna_nest_http::ApiError::is_transient` — transport, `408`, `429`, `5xx`) is forgotten rather than recorded, so the page's next rebuild asks again; an absent, refused, unopenable or undecodable blob stays hopeless for the session, and so does every failed third-party remote image (its shared fetch cannot tell a transient failure apart, and a host must not be able to make the reader call it again by failing). On linux the cached surfaces are every image a rebuilt card paints from a fetch — the feed's `post-image` and `c2pa-badge` verdict, and on both the feed (list card and `feed.post_detail`) and conversations pages the link-preview og:image and the revealed remote image (`media_loads`); the DM attachment image is not cached, since it fetches nothing and is decoded only when its message changes.

**Encryption at rest:** see § Encryption at rest below for the per-blob-keying-by-audience rule and the per-mode property.

## Encryption at rest

The user's media items — photos, videos, voice memos, generic files — exist as content-addressed blobs. The at-rest property is **per-blob keying by audience**: each blob is sealed under the audience that controls the surrounding content it is attached to. This rule is **independent of the folder substrate and the explorer view** (§ Goal / § Layout & flow): a blob's seal is determined by what content it is *attached to*, not by which folder the Media explorer browses it under. Every media blob falls into one of the audience classes below and inherits its seal.

**Library media (owner-only).** The user's personal media items not attached to any audience-broader content (an item just uploaded to the library; an item the user never shares). Sealed under the owner's `BackupKey` (the owner-only symmetric key defined in `docs/goal/architecture/owner-key-material.md` § Audience: owner only Path A) via the standard fauna-sync `encode_blob` pipeline (`docs/goal/behavior/file-sync.md` § Content-Addressed Storage). Identical seal-shape to `__drafts` (and to the `__config` blob before its rail retired). No nest ever holds `BackupKey` — the data owner's client derives it from the identity seed (`BackupKey::derive`) and seals before upload (`libs/fauna-sync-engine/src/engine.rs:1469` `SyncEngine::upload_file`; the engine lived at `bins/fauna-sync/src/engine.rs` before the 2026-06-01 `fauna-sync-engine` crate extraction); nests treat library blobs as opaque uniformly.

**Public-audience folders — the one exception, and Media is a producer for it.** A folder whose owner declassified it rests **unsealed**; the rule, its confirm and its one-way warning are owned by [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Readable classes → *Owner-flipped public-audience folders* (full statement: `principles.md` § The user always controls their data). It reaches this page because website-published folders are in Media's browse **and upload** scope (§ Layout & flow → *Where the offerable sets come from*; the web-type exclusion was retired 2026-08-17), so an upload here lands in such a folder exactly as the sync engine's own writes do — and therefore rests the same way: plaintext bytes, plaintext path, no sealed label. The producer asks `FolderSummary::rests_unsealed()` at the control-plane seam and carries the verdict on the set row; it never re-derives the rule, and anything it cannot classify seals (over-sealing a public folder costs a re-record, under-sealing a private one is irrecoverable). This does not qualify the per-blob-keying rule above: that rule asks what content a blob is *attached to*, and this asks what the owner did to the folder it rests in.

**Content-keyed sets — WebDAV-served or shared (ruled 2026-09-26; BUILT the same day, shared Rust, all 7 apps at once).** A set served over WebDAV, or bound to a sharing group, rests under its M2 content key ([`../behavior/webdav-server.md`](../behavior/webdav-server.md) § Key model, the *app-side seams* bullet — the owner of the ruling; [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2), and Media is a producer for it exactly as the sync engine is: an upload into such a set seals the file through the engine's own whole-file pipeline (`fauna_core::blob_seal::seal_blob` under the set's current generation — chunks under their ciphertext hashes, a canonical `ChunkManifest`, the change recorded stamped with the generation, the path sealed under the same root) — **never a Library blob primary**, which only this page could ever open. The custody comes from the one shared resolver the page already renders and downloads under (`folder_keys_for` → `NestFolderKeyResolver`), so the seal root cannot diverge from the roots the readers hold; keys not yet on this device refuse the upload with a page error (fail closed), never an owner-key seal, and a set homed on another nest is refused likewise. Such an item carries no thumbnail — the engine records none for a content-keyed set either (§ Implementation status today). Reads are the same custody: the page lists the rows the mount wrote into a served set, and after the owner stops serving, the served-era rows keep rendering under the retired generations the owner's custody kept. The per-blob-keying rule above is not qualified but applied: the content such a blob is attached to is the set, and a content-keyed set's audience is its content key.

**One at-rest shape for a folder's file — the chunk manifest, whatever produced it (ruled 2026-10-06; the producer BUILT the same day — § Implementation status today).** Every file this page records into a folder rests as the engine's shape: FastCDC chunks behind a canonical `ChunkManifest`, sealed through the one whole-file pipeline `fauna_core::blob_seal::seal_blob` under the root the folder's custody names — the set's current content key for a WebDAV-served or shared set (the paragraph above), the owner's convergent chunk root (`BackupKey::convergent_chunk_root`, recorded unstamped) for an owner-only set, and no root at all (plaintext chunks, `stored_hashes = None`) for a `public`-audience folder. **The blob-store primary is retired as the shape of a folder's file.** Until this ruling `MediaMachine::do_upload` sealed an owner-only or public upload as ONE blob under the bare `BackupKey` (`fauna_media::process_and_seal`, `Audience::Library` / `Audience::PublicFolder`) — a shape no other producer writes and every reader had to be taught twice: the page's own download and restore arms and the sync engine's hydrate and re-seal arms each carry a second arm for it, and the two readers that were never taught it fail exactly where a user looks — the web serve walk answers 404 for a Media upload into a website folder (so a phone or web user could not put a file on their own site), and a private link cannot be minted for a Media upload into an owner-only folder ([`../behavior/share-links.md`](../behavior/share-links.md) § Which files can be linked: the control was offered and the create failed). Three candidates were weighed. **(1) Move the uploads onto the chunk pipeline — chosen.** **(2) Per-file eligibility** (carry the shape on the listing so the link control hides on a blob primary) was refused: it writes the divergence into the wire and the UI and leaves the website case unsolved. **(3) A blob-primary arm on the nest's serve and share routes** was refused on a key fact: a Library blob is sealed under the raw `BackupKey` with a random nonce (`encrypt_backup_chunk`), so the only key a link's envelope could hand out is the owner's master owner-only key, which no design may ever share — and the blob has neither the convergent dedup nor the byte identity the chunk scheme gives; a plaintext-only serve arm would still have been a second shape on the public serve path, for the public case alone. What the chunk shape gives every Media upload with no nest change: the private link (`mint_private_link` unseals the manifest's hashes under the owner root and hands out per-chunk keys), the public serve and the public link (a plaintext manifest is what `file_bytes::read_file_by_manifest` reads), hydration onto a synced desktop, the audience-flip re-seal passes, and per-owner convergent dedup. What stays: `process_media` still runs first (metadata strip, MIME sniff, thumbnail, C2PA flag), and **the thumbnail stays a blob-store blob** sealed under the folder's audience exactly as today (`seal_thumbnail` — a derived view only this page reads, never linked or served), its hash recorded on the change record (`record_member`'s `thumbnail_hash`, which `fauna.media.list` surfaces and `fetch_thumbnail` fetches by its own hash; the primary sidecar's pointer and `?thumb=1` were never on this page's path); a content-keyed set still records no thumbnail. `fauna_media::process_and_seal` and the `Audience::Library` / `PublicFolder` blob seal remain the attachment plane's (a post's or a message's media, sealed per content — § *Conversation-attached media* and the rows below), which is not a folder file and is untouched. **The read arms for the retired shape go too, provided the build lands before the open-source flip** ([`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 2, the fourth exception: no installation or data exists before the flip, so there will be no blob primary left to read) — `download_file`'s arm 1, the restore re-seal's arm 1, the engine's two; a build that lands after the flip keeps them as read-compat and mints a client-driven re-seal pass (the `converge_corpus_*` shape) instead. Link eligibility stays per **folder** (`share_link_eligible` over the folder's facts) — exact again once every file the page records is a manifest.

**Conversation-attached media.** Sealed under the conversation group's `derive_blob_key(epoch_secret)` — the same primitive conversation **attachments** (`engine.rs::seal_conversation_blob`) and group-shared MLS-attached blob content already use (see `mls-group-key-material.md` § Audience: an MLS group at a specific epoch) — on the **end-to-end** class; on the **community** class, which has no MLS group, under the room's attachment content kind off the naming message's generation (`docs/goal/behavior/community-rooms.md` § The three classes → *Community* → *Attachments — the second content kind*, ratified 2026-09-10, which owns that key; same blob store, same sidecar class, same `attachment_refs` pin). *(The message **body** itself uses the MLS application-message layer, not `derive_blob_key` — see that doc's `derive_blob_key` entry.)* No new key, no new derivation. When the user shares a previously-uploaded library item into a conversation, the client decrypts under `BackupKey` and re-seals under the conversation's `derive_blob_key`; the resulting blob has a different hash and ciphertext than the library copy (dedup is lost across audiences by construction — that is the audience-rule's correct behavior). What keeps the sealed blob alive on the nest is the plaintext `attachment_refs` the send lists beside the sealed envelope (`../behavior/conversations-at-rest.md` § Encryption at rest → *Attachment reachability*, built 2026-09-09) — the nest cannot read the message that names it.

**Restricted-post-attached media.** Sealed under **the post body's own per-post key** — the group's epoch secret for group-restricted posts, the tier's period key (which reaches subscribers via the post's `KeyBlob`) for audience-restricted ones, in both cases with the per-post derive input `../behavior/restricted-posts.md` § Encryption at rest ratifies and owns; that section is where the derivation is stated, not here. One per-post key seals the post body and all attachments together with random nonces per blob; recipients who can decrypt the body can decrypt the attachments by construction. **That construction has a reader as of 2026-09-07:** `FeedManager::unlock_gated_post` registers each opened body's items under the key that opened it and `open_media_bytes` opens the bytes an app fetched by hash — the write side alone had shipped until then, so a gated photo post rendered its caption over a blank card (`docs/goal/behavior/archive-import.md` § Implementation status today).

**The seal is resolved BEFORE the attachment is uploaded, never after — this is a rule, not an implementation detail.** A blob's audience decides its seal, so a compose that POSTs the bytes at *pick* time and asks about the audience at *submit* time has already published a readable copy of a restricted post's photo: blob `GET` is unauthenticated by design and the nest exposes **no blob DELETE**, so "no plaintext copy is fetchable" is achievable only by never uploading one. Every app therefore resolves the composer's audience first and seals-or-passes-through once, at submit. The seal itself is **shared Rust reached by id** — `FeedManager::seal_compose_attachment`, which mints the post's `seal_id`, seals under `derive_post_key(period_key, seal_id)`, and hands the app ciphertext plus the real plaintext MIME (the sealed sidecar's is pinned `application/octet-stream`, so the `MediaItem`'s type can come from nowhere else). The period key never crosses the FFI/wasm boundary, per the audience-subset rule in § Today's reality below.

**Submit-time upload is the rule for the public (pass-through) class too, for a reason the seal argument does not reach: the nest's blob GC (ratified 2026-09-08).** A blob is pinned only once a stored post names it; before that, the only thing between an upload and the sweep is the 30-minute creation grace, which a re-upload of the same bytes does not renew — both owned by [`../behavior/backup-restore.md`](../behavior/backup-restore.md) § 9 (step 2f's live-signed-records arm and step 5's grace). A composer that POSTed at pick time would lose the photo of any post written for longer than the grace, silently and unrecoverably: the nest holds no other copy, and the publish itself succeeds, so there is no error to retry from. So every app holds the picked bytes locally — the preview renders from the local file — and uploads at submit, immediately before the post that names the hash is stored; all 7 composers do as of 2026-09-08 (android and apple were the last two, having uploaded at pick). The nest side is pinned by `gc_sweeps_a_pick_time_upload_before_its_post_exists` (`bins/fauna-nest/src/backup/gc.rs`), which ages a pick-time upload past grace before its post is ingested and asserts it is swept — the ruling's chosen outcome, so a future composer cannot expect the grace to cover it. **A video is the one upload a submit cannot make near-instant:** its segments go up one `POST /api/v1/video/segments` at a time — a sweep door since 2026-09-22, each segment carrying its `blob_metadata` row — all before the post that names them is stored, so a segment upload longer than the grace leaves its earliest segments exposed to a sweep that lands before the post. No app composes a video post yet (the only builder is the e2e FFI twin); the first composer owes either an upload that completes inside the grace or a reference that pins the uploaded segments until the post is stored — the shape the web render uses for its own in-flight bodies ([`../behavior/backup-restore.md`](../behavior/backup-restore.md) § 9 step 2h).

**Rendering a sealed attachment takes one of two shapes, decided by whether the app's image path holds the bytes.** The seal is one mechanism, but the apps divide on a platform fact, so this is a declared two-shape rule rather than drift to resolve (priority #1): **(1) the apps whose post-image path fetches bytes itself** — tui, linux, windows, android — pass **every** hash through `open_media_bytes` before decoding, unconditionally. There is no is-this-post-restricted branch anywhere in them: an unregistered hash (public media, an avatar, a link preview, a still-sealed post's item) comes back untouched, so one call serves both classes. **(2) the apps whose post image is a URL the platform fetches and decodes natively** — web's `<img src>` and apple's `AsyncImage(url:)` — never see the bytes in app code, so they must ask **`FeedManager::is_sealed_media(hash)`** *before* rendering: `false` (the overwhelmingly common answer) keeps the plain blob URL, including the `?thumb=1` smaller blob; `true` means fetch the bytes, hand them to `open_media_bytes`, and render the result as a local object URL / in-memory image — a sealed item has no server-openable thumbnail, because the nest cannot read it. **In both shapes the branch, where one exists, lives in the page or view model and never in the post card**, which paints whatever image source it is handed; and in both, a `None`/`null` answer paints the placeholder the app already shows for undecodable bytes, never the ciphertext. **The badge correction adds a cost to shape 2, and it is accepted (2026-09-20).** A shape-1 app already holds the bytes, so re-deriving the provenance verdict over them is free. A shape-2 app — apple's `AsyncImage(url:)`, web's `<img src>` — does not, and a **public** post's image is exactly the case it renders as a plain blob URL, which is also exactly the case where `has_c2pa` is forgeable (a sealed class is refused `has_c2pa = true` at ingest). So correcting the badge there means one extra full-image fetch **solely for the badge**, and only for the posts whose `x-c2pa` pre-filter already said `true`. That is the price of not painting a provenance claim on an uploader's say-so, and it is the right trade: the alternative is a badge that lies. It does **not** reopen the two-shape rule — the *image* still renders from the URL; the badge check is a second, independent read on the same hash, the shape tui and linux have always had (`FetchImage` and `FetchC2pa` are separate ops resolving on their own schedules). Web already pays it through `readProvenanceFromUrl`.

**Public-post-attached media.** Signed plaintext, no key. The post's signature attests to the blob hash; the bytes are public; deduplicated naturally across all public attachments. (Avatar / banner blobs referenced from the federated public `Profile` record follow the same shape — see the `Profile` conformance row in `encryption-at-rest.md`.)

**What's in the floor (per blob).** BLAKE3 content hash (the routing identifier; `blob_metadata.hash`); ciphertext size (rounded); upload timestamp; uploader-supplied MIME (the `Content-Type` to serve on download); uploader-supplied thumbnail-blob hash (the `?thumb=1` routing pointer; the thumbnail is a separate blob sealed under the same audience as its parent); uploader-asserted `has_c2pa` flag (the `x-c2pa` response header — see § C2PA provenance below). The attachment-relationship floor (which post / conversation / event references which blob) lives in the *referencing content's* metadata (the post's attachments-by-hash list — for a restricted post that list is the plaintext `GatedInfo.attachment_refs`, ratified 2026-09-08 exactly so the nest can pin what the sealed body hides from it (`../architecture/encryption-at-rest.md` § Plaintext floor → Posts row); for a conversation message the plaintext `attachment_refs` the sender lists beside the sealed envelope, ratified 2026-09-08 for the same reason — `../behavior/conversations-at-rest.md` § Encryption at rest → *Attachment reachability*; etc.) and is owned by those rows, not duplicated here. **The relationship is what keeps a blob alive:** the nest's blob GC deletes every blob no live record names ([`../behavior/backup-restore.md`](../behavior/backup-restore.md) § 9 step 2), so a writer that uploads through `/api/v1/blob` and records no reference — the shape every feed-compose door and the avatar upload had until 2026-09-08 — is a writer whose bytes are swept ~30 minutes later. The per-item `path` / `folder` fields `fauna.media.list` returns are likewise not part of this per-blob floor — they come from the folder substrate's `sync_changes` rows, whose plaintext-path at-rest exposure is owned by the Folder files conformance rows in `../architecture/encryption-at-rest.md` (+ its § Carve-outs — the 2026-07-29 paths-are-content sealing ruling).

**C2PA provenance** — sealed alongside the pixels, not as a separate plaintext attestation. The C2PA manifest is a JUMBF segment inside the JPEG/PNG bytes by construction; sealing it alongside the pixels keeps the nest out of the provenance pipeline (it sees neither pixels nor signer identity — it can never read sealed content, § Architectural rules corollary of `content-scoring.md`), avoids extending the plaintext floor with sensitive provenance metadata, and is free for the viewing client (which needs the bytes anyway to render). **The badge is the VIEWER's verdict over the bytes, never the uploader's word.** The `has_c2pa` flag in `blob_metadata` is always uploader-asserted — the nest never inspects the bytes to verify it, and its `PublicPost` ingest arm checks only length and MIME shape (`bins/fauna-nest/src/storage/sealed.rs`; the `has_c2pa` refusal alongside it belongs to the sealed classes, whose flag rides inside the ciphertext) — so the `x-c2pa: true|false` response header is a UI hint and NOT a security boundary: anyone posting through a modified client or a raw multipart request can claim provenance for an image that carries none. Every viewing app therefore **re-derives the verdict from the unsealed bytes it already holds** and paints `c2pa-badge` only on its own `true`. One shared function is that verdict — `fauna_media::process::detect_c2pa_in_bytes` (`libs/fauna-media/src/process.rs:168`), which sniffs the container off the bytes (an uploader-asserted MIME is as forgeable as the flag) and delegates to the same `detect_c2pa` the upload path runs, so a viewer recomputes precisely the `has_c2pa` an honest uploader would have stamped. The apps whose image path holds the bytes in Rust (tui, linux) call it directly; android, windows and apple hold them in platform code and reach the same function through the single UniFFI export `detect_media_c2pa` (`libs/fauna-ffi/src/media_upload.rs:161`); web re-parses with the JS `@contentauth/c2pa-web` SDK the page already loads (§ *Upload-side `has_c2pa` population on web*). **The header survives as a PRE-FILTER only**: `false` ends the check without fetching anything — the answer for essentially every post — and `true` is what buys a byte-level parse, which is what keeps the correction from costing a blob read per card. **What the badge certifies (ratified 2026-09-20): a parseable C2PA manifest is PRESENT in these bytes — not that it validates, and not who signed it.** The shared detector is `Reader::with_stream(..).is_ok()` (`libs/fauna-media/src/process.rs`): it accepts any stream the reader can parse and performs no trust-list, signer or signature check. The copy matches that and must keep matching it — the shared badge's label is the bare `C2PA` (`i18n/strings/en.yaml` `c2pa.badge_label`), never "verified" or "valid"; a future session "improving" it to a verification claim would make the UI assert something no app computes. Web's detail panel is the one declared superset: its SDK does report a validation status, so `C2paImage.svelte` additionally shows `c2pa.valid` / `c2pa.validation_issue` and titles the panel `c2pa.verified_title` — a richer statement backed by a richer check, not a different rule. This section is the c2pa registry row's home (badge UX + hint semantics + the badge-correction rule + what the badge certifies); the per-app render glue lives at web `apps/fauna-web/src/lib/c2pa.ts`, linux `apps/fauna-linux/src/c2pa.rs`, windows `FaunaApp.Core` `Helpers/PostMediaOpen.cs` (the verdict; called from `FaunaApp` `Helpers/BlobImageLoader.cs`), apple (macos+ios) `FaunaKit` `ViewModels/FeedVM.swift::hasC2pa(_:)`, with `Core/APIClient.swift::hasC2paAssertion(hash:)` as its pre-filter (one-line notes in their app docs); sealing mechanics stay with `architecture/encryption-at-rest.md`.

**Upload-side `has_c2pa` population on web — RESOLVED + BUILT 2026-07-30 (refutable advisory, no live deployment affected).** The 2026-07-17 root-cause framed a binary — a wasm `c2pa-detect` build vs. nest-side re-verification at ingest — and **both are rejected**; the resolution is a third path the binary missed. **(1) Nest-side re-verification is rejected on this section's own ratified trust model:** `has_c2pa` is *uploader-asserted* and the nest *never inspects the bytes* — that rule is what keeps the nest out of the provenance pipeline (and off sealed content, where re-verification is structurally impossible anyway); ingest-time inspection would be a trust-model change this doc deliberately forbids, partial by construction, and a new nest-side content-processing surface against `content-scoring.md`'s placement rule. **(2) A Rust wasm `c2pa-detect` build is rejected as redundant:** the bundle-size argument that excluded it is *sunk* — web already ships a lazy-loaded C2PA WASM detector for the viewer path (`@contentauth/c2pa-web`, `$lib/c2pa.ts`), and compiling `fauna-media`'s `c2pa` tree into `fauna_wasm` would ship a **second** detection engine to the same app. **(3) The resolution: web computes `has_c2pa` at upload in the browser, via the SDK it already ships** (`readProvenanceFromBytes` over the file's bytes, gated to `image/*`), and passes it into the seal exactly the way the browser `File.type` already patches `mime` — per-platform *detection* (the browser facility web has; native's is `fauna-media`'s `c2pa-detect`), shared *data shape* (`UploadSidecar.has_c2pa`). The uploader-asserted + viewer-corrected trust model above is **unchanged** — this makes web's assertion *honest*, not authoritative; a lying uploader can still only suppress their own badge (declaring `false` hides their own provenance) or trigger the viewer's real check (declaring `true` makes viewers parse the manifest, which fails → no badge). **Built 2026-07-30**: `libs/fauna-wasm/src/lib.rs::process_and_seal_public_post` gained the `has_c2pa: bool` param, both web call sites (`routes/feed/+page.svelte`, `routes/profile/[[actorId]]/+page.svelte`) wire it from `readProvenanceFromBytes`. **The closing proof now HOLDS — verified green 2026-08-02; see the web bullet below.**

**Today's reality.** `POST /api/v1/blob` accepts **only** the `multipart/form-data` shape — exactly two parts named `sidecar` (DAG-CBOR-encoded `UploadSidecar` carrying `{class: AudienceClass, mime, has_c2pa, thumbnail_hash: Option<[u8;32]>}`) and `bytes` (sealed bytes); any non-multipart Content-Type → 400 (the legacy `application/octet-stream` body retired with the blob strict flip). An absent sidecar or any per-class rule violation returns `Err(StorageUnavailable::ingest_rejected(IngestRejectReason::Blob*))` → HTTP 400 `{"error":"ingest rejected: <reason>"}`; on accept the sidecar fields populate `BlobIngestOutcome` (the served `Content-Type`, the `x-c2pa` response header, the `?thumb=1` routing pointer). The remaining row-resolution work is uploader-side: the rust-side audience-keyed seal pipeline already shipped (`libs/fauna-media`'s `process_and_seal`); per-app wire-up follows in the six per-app upload-sidecar tracks spawned by this slice (tracked internally). - **No upload target is TWO conditions with two messages (2026-08-03, shared Rust — `MediaMachine::set_error_no_upload_target`):** the caller has *no folders at all* → `media.error_no_set` ("create one first"), vs. the caller *has sets, none sync-type* → `media.error_no_sync_set` (named the sync-type-only rule — the actionable half a flat "select a set" hid from a live user with only backup-type sets). Don't collapse them back into one string. **Ruled 2026-09-28: the second condition becomes unreachable once every own folder is an upload target (§ Layout & flow), so `media.error_no_sync_set` retires with the contraction slice and only `media.error_no_set` remains** — the two-message rule stays the precedent for a refusal that genuinely has two causes.
- Folder content unreachable — `media-source-status` shows red; affected items may be unfetchable (their thumbnails / bytes unavailable until a holder is reachable again — `../behavior/file-sync.md` § Content reachability).

## Architectural rules

1. One unified concept across all 7 apps: **folders are the substrate, Media is their media-optimized view.** Photo-backup-only and folders-only-as-a-separate-page are not acceptable end states — folders is the substrate, photo-backup is a guided ingress into one folder, and Media is the unified explorer over all sets.
2. Observer-driven rendering off the shared `media_snapshot()` cross-set snapshot.
3. Indexed list IDs for `media-item` (already indexed in ui.yaml).
4. Media is the **content plane only** — it reads folders, it never configures them. All folder creation / place-flag / retention / roster / binding / conflict UI lives in Settings → Folders (`docs/goal/ui/folders.md`); do not add control-plane affordances to the Media page.
5. **Folder scope** — Media aggregates the **media library**: every user folder, website-published ones included (the web-type exclusion is RETIRED — 2026-08-17, § State & data shape → *Folder scope*). Reserved `__*` sets stay out. Don't surface a `__*` set in the Media explorer.
6. **A followed public folder is identity-addressed and keyless, end to end** (§ Followed public folders). Never route one through the name-keyed custody resolver, the owner-key download path, or the all-media aggregate — its scope carries `(home_nest_url, folder_id)`, its reads are `public_follow`'s, and a followed read that touches key material is a bug even when it appears to work.

## Don't do these

- Don't ship a per-app Media paradigm (photo backup OR folders-as-its-own-page OR flat generic upload) — render the unified cross-set explorer on all 7.
- Don't implement the upload pipeline or cross-set aggregation per-app. Shared Rust (`media_snapshot()` / `process_and_seal`).
- Don't add `file-upload` substitutes per-platform without raising a ui.yaml change.
- Don't put folder configuration (place flags, retention, roster, binding, photo-backup ingress controls, conflicts) on the Media page — those belong in Settings → Folders.
- Don't route a followed public folder through the name-keyed custody pipeline (`download_file` / `folder_keys_for` / `LabelCustody`), offer it as an upload target, or aggregate its rows into all-media — § Followed public folders and architectural rule 6 own the boundary.
