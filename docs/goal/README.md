> **Visitors: these are internal design specs, not user documentation.** The
> `docs/goal/` tree is the project's working design specification — target
> state, implementation status, and open questions, written by and for the
> people building Fauna and published for transparency. Expect target-state
> prose ahead of the code, implementer vocabulary, and unresolved TBDs. If you
> want to *use* Fauna, start at the [documentation front door](../README.md)
> and the [user guides](../guides/) instead.

## The hierarchy

- **Level 0 — this map**: routing + conventions. No behavioral claims.
- **Level 1 — principles/invariants**: [`principles.md`](principles.md) owns the
  never-violate product rules and the engineering principles; per-domain
  invariant sections (where a cluster needs one) own domain principles. Not
  summaries of Level 2 — nothing to sync.
- **Level 2 — the corpus** (`architecture/`, `behavior/`, `ui/`): owns every
  specific fact. Exactly one owner per claim (§ Writing protocol).
- ui.yaml split is unchanged: `tests/e2e-unified/ui.yaml` owns element IDs and
  per-page element scope; goal docs own behavior. On conflict in the other's
  domain, raise it.

## Reading protocol (start here, every time)

1. Find your concept in the § Registry below; open the **owner** doc.
2. Read the owner doc's `## Implementation status today` FIRST — target-state
   prose ahead of code is declared there, not discoverable from the prose.
3. Check the front-matter `Status:` — `draft`/`partially-specified` in your
   sections is a hard stop: don't build against them; raise the gap first.
4. A claim about the concept found in any *other* doc is a reference, not
   authority — follow its pointer; if it carries a mechanism and disagrees with
   the owner, the owner wins and the restatement is a bug (fix or file it).

## Writing protocol

> **Iron-clad: one owner per claim; reference, don't restate.** Every
> load-bearing claim — invariant, default, data/wire/storage shape, flow — lives
> in exactly one goal doc: the one whose `Owns:` lists the claim's concept
> (registry below). Every other doc refers to it with at most a one-line *scope
> description* plus a pointer ("DKIM provisioning is nest-side, automatic —
> owner: `behavior/mail-bridge-lifecycle.md` § DKIM provisioning"), never a
> paraphrase of the mechanism. The test, before writing a sentence about another
> doc's concept: **if the owner doc changed its mechanism tomorrow, would this
> sentence become false?** Yes → it is a restatement; replace it with a
> reference. Goal docs still MUST NEVER contradict — minimized overlap is *how*
> that is guaranteed, instead of by re-reconciling N copies on every edit.

- Adding a claim = pick the owner concept (or coin one), write it in the owner
  doc, update the registry if ownership is new. Never add the mechanism to a
  second doc "for convenience."
- Moving a claim = one commit that moves the text, updates both docs' `Owns:`,
  and updates the registry row.
- When you change an owned mechanism, grep for referencing one-liners and fix
  any whose scope description is now wrong (cheap — they carry no mechanism).
- New claim → owner doc per the registry; new concept → add a registry row in
  the same commit.
- Goal-doc edits precede or accompany implementation, never lag it.
- **Reading the labels.** Two short letter-series labels recur through shipped
  code comments and docs, each a pointer into `account-data-plane.md`'s own
  design-pass registers — the FIRST use of either in a shipped file cites its
  defining section: **`W<n>`** (`W0`–`W8`, plus decimal
  sub-phases like `W2.5`) names a workstream — [`account-data-plane.md`](architecture/account-data-plane.md) § Workstreams;
  **`R<n>`** names a ratified decision — the same doc,
  § The ratified decisions (each decision is also individually anchored —
  `§ R11` — since they are bulleted, not tabled). A third series joined
  2026-09-05: **`TP<n>`** (`TP1`–`TP12`) names one of the third-party
  integration chain's twelve rulings — [`architecture/third-party.md`](architecture/third-party.md)
  § The rulings — index, which routes each to its owner; the letters are
  deliberately not `R`, because the chain's rulings cite and coexist with
  `account-data-plane.md`'s `R<n>` decisions inside the same owner docs.
  Other short numeric-suffix
  labels exist locally within individual docs (a rollout-slice `S<n>`, a
  resolved-question `T<n>`) but are each their own doc's vocabulary, reused
  independently enough (`content-index.md`'s rollout ledger, `path-sealing.md`'s
  own `S1`–`S9`, the mail-scanning family's decimal `T1.4`, and a real
  collision with the literal string "S3" naming an AWS-compatible object
  store) that no single defining doc could be cited for them without being
  wrong some of the time — do not assume `S`/`T` follow this same convention.
- **State mechanisms, never law.** A legal characterisation in the project's own
  voice — what a court, the police or an authority must do, whose legal duty
  something is, the organisation's own regulatory status, what a regulation will
  or might require, a compliance verdict — does not ship in the spec, however
  likely it is to be right: no session and no machine review can verify a legal
  claim, and the spec's authority is engineering. Say what the mechanism does
  ("the box owner holds only ciphertext", "blocking has no reporting path") and
  leave the legal reading to the reader. Legal background worth keeping for the
  next designer rides inside `` like any other provenance (next bullet);
  the sentences the 2026-08-30 legal sweep took out of the shipped spec stay
  out under this rule — the organisation's own decision, never a wait on
  anyone. Review by a lawyer is never a gate
  ([`architecture/public-texts.md`](architecture/public-texts.md) § Rulings, 20).
- Run `goal-lint` before committing goal-doc changes (front-matter,
  registry bijection, link resolution, and that a registry row for a doc
  shipping as a public stand-in keeps only a one-line "public summary" outside
  its excision span — live since 2026-07-07: gated in CI
  (`ui-lint` job) and at merge time; `--verbose` lists the docs
  still pending their cluster review).

## Front-matter schema

Every doc under `docs/goal/` (except `ui/_template.md`) begins with the H1 title
followed immediately by:

```markdown
Owns: <comma-separated concept slugs from the § Registry>   (— if none)
Status: ratified | draft | partially-specified               (non-ratified adds: — resolved by <who/what>)
Authority: <optional one line — domain splits with other docs or ui.yaml>
```

plus a `## Implementation status today` section wherever target-state prose is
ahead of code (one line stating "fully implemented" otherwise).

**Conversion complete (2026-07-10):** every doc in the corpus carries
front-matter and has been through its Phase 2 cluster review (design + reports
tracked internally). Missing front-matter is now always
a violation (`goal-lint` enforces it).

**Standing maintenance practice (ratified at Phase-2 close-out, 2026-07-10):**
`goal-lint` catches structure rot mechanically; content rot has one place to go
stale per claim. For the judgment-class defects lint cannot see (infeasibility,
bad ideas, ambiguity, code-drifted status sections), run a lightweight
re-review **after each major feature wave, or
~quarterly** — per-cluster review with code verification → severity-ranked
report → maintainer triage → fix pass, the same machinery as the
Phase 2 reviews. Watch especially for the two failure classes Phase 2 found
everywhere: *inverted status* (draft/TBD/pending prose over built surfaces —
a stop-before-building signal pointed the wrong way) and *changelog disease* (status
sections accreting correction archaeology instead of a current-state matrix).
Since 2026-07-12 the practice also runs **continuously** via a consistency
ledger (tracked internally) that prioritizes concepts by code churn under each
concept's paths since its last verification, so a big semantic shift's
referencing tail converges between the periodic reviews.
Every cleanup or maintenance pass — mechanical or judged — also **names the
generator**: it states which convention or authoring pattern produced the rot
it removed (append-in-place histories and single-line changelogs are the
recurring ones) and either fixes that convention in the same change or leaves
a tracked work item pointing at it. Cleaning the instance while leaving the
generator running returns the same rot compounded (ratified 2026-07-20; the
646KB single-line snapshot-header comment is the type specimen).

## Registry

One row per concept, all owners ratified (Phase 2 complete 2026-07-10 — zero
⚠ rows remain; new concepts minted since add rows here in the same commit).
The Phase 0 draft index (a frozen historical artifact, tracked internally)
lists every other doc touching each concept.

**A row's Notes cell is a one-line scope plus routing arrows, at most 400 bytes.** It says what the concept covers, so a reader can tell whether their question belongs to this owner, and sends each adjacent question to its own owner (`<aspect> → <doc> § <section>`). It does not record history (when a concept was minted, ratified, split or narrowed, and by whom), list the owner doc's mechanisms, or give build status — those live in the owner doc's front-matter, body and `## Implementation status today`, and in version control. A Notes cell that grows a history is the *append-in-place history* generator named in § Front-matter schema, and the registry is the one file every session reads, so it pays that cost first. `goal-lint` counts the cells over budget and fails when the count rises; lower its ratchet in the commit that shortens one.
