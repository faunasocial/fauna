## Goal

ActivityPub is a **thin account-link bridge, not a deep integration** — the deliberate contrast is Nostr ([`../ui/nostr.md`](../ui/nostr.md) § Goal, which ranks the two: Nostr's decentralization fits the nest-as-home-server model; ActivityPub/Mastodon is the more-centralized network Fauna interoperates with rather than inhabits). The shape: the user's nest doubles as their **Mastodon-compatible fediverse server**. Enabling federation on the Bridges page mints an AP actor `@<username>@<nest-domain>`; remote fediverse users can WebFinger-discover, follow, and receive the user's public posts in their home timelines (built 2026-07-16 — § The produce direction below); the user can follow remote fediverse actors, ingest their public notes into the unified feed, and bridge likes/boosts outbound. All user choice lives in the app Bridges UI (enable/disable, auto-accept follows, default visibility, backfill) persisted in nest state — there is no other configuration surface; the AP domain is the nest's deployment-derived domain, not a knob.

## Architecture (current, shipped)

**Code split (priority #2):** protocol logic — JSON-LD types, Fauna↔AP translation, HTTP signatures (draft-cavage), WebFinger, RSA identity, table DDL — lives in the shared crate `libs/fauna-bridge-activitypub`; nest glue — routes, handlers, the delivery worker, DB helpers, key custody — in `bins/fauna-nest/src/activitypub/`. Everything is `#[cfg(feature = "activitypub")]`-gated. Zero per-app code exists: the app surface is the provider-agnostic unified Bridges page ([`bridges.md`](bridges.md)).

- **Identity & keys.** Per-account RSA keypair minted at enable; the private key rests **encrypted with the nest identity key** (`activitypub/key_crypto.rs` — the same custody pattern as Nostr's `nsec` deposit) and is decrypted transiently to sign outbound HTTP requests. The actor URL is `https://<domain>/ap/users/<username>`.
- **The instance actor** (built 2026-07-22, closing phase 2 of gap 4). One nest-level `Application` actor at `https://<domain>/ap/instance`, WebFinger-resolvable as `acct:<domain>@<domain>` — Mastodon's own instance-actor shape, so a peer that WebFingers a fetched actor back to confirm it agrees with the `keyId` it was handed resolves rather than 404s. It exists for exactly one reason: **the outbound remote-actor fetch has no per-user actor to sign as.** That fetch runs on *arrival* of an activity, before anything is verified, precisely to obtain the key verification needs — so we do not yet know which local user (if any) it concerns, and a shared-inbox delivery may concern several. A peer in secure mode (`AUTHORIZED_FETCH`) refuses unsigned `GET`s of its objects, which turns the missing signature into a federation break rather than a stylistic gap: no key, no verified `Follow`, no `Accept`, so the follow never completes. Key custody is the per-account rule verbatim (§ Security posture); the key is minted once (single-row table, `INSERT OR IGNORE` + read-back, so racing minters converge and a remote never sees two keys) and **never re-minted**, since remotes cache it against the actor URL. **One instance key signs every outbound AP `GET`**, including the call sites that *do* have user context — uniform (priority #1), and it keeps a fetch from leaking which local user is looking a remote actor up. The actor is a signing identity, not a profile: no follower collections, no profile fields, an outbox that is always an empty `OrderedCollection` (served, because a document must not advertise a link the nest does not route — the six-week `/.well-known/nodeinfo` dangle is what that costs). Deliberately **not** derived from the nest seed: an RSA key regenerated from a seed would silently change if the `rsa` crate ever altered its keygen walk, invalidating every peer's cached copy. **Corollary — the factory-reset rotation hazard (ratified 2026-07-22):** a factory reset wipes `ap_instance_actor` and the next boot re-mints it, which silently invalidates the cached key of **every real peer that ever federated with the box** — off-box state no reset or teardown can reach; affected peers refuse our signed fetches (and strict peers refuse everything) until their caches expire or re-fetch. This is an operational property of factory reset on any nest that has federated, not a test-harness note — it is why live AP tests never factory-reset (`testing.md` § shared-box rule, non-destructive carve-out), and a deployed box that has real remote followers should treat factory reset as a federation-visible event.
- **Every outbound AP request carries a `User-Agent`** (`activitypub/outbound.rs::AP_USER_AGENT`, built 2026-07-22). Not a courtesy header: **GoToSocial refuses a UA-less request with `418 I'm a teapot`**, and since the first thing an arriving activity makes us do is fetch the sending actor's document for its key, a UA-less nest completes *no* exchange with a GoToSocial instance — no key, no verified `Follow`, no `Accept`. Our client sent none from the feature's inception; Mastodon never minded, so the defect survived until a second implementation was put in front of it (§ Implementation status today, gap 4 — the interop harness's whole thesis, confirmed on its first GoToSocial run). Set on the client in the **single AP dialer** so it cannot be forgotten at a future sink, exactly as the SSRF guard is. Deliberately **static** (`fauna-nest/<version> (+<project url>)`), carrying no instance domain: the conventional fediverse form appends the instance URL, but a signed GET already names us in its `keyId` and a delivery names us in its actor, so threading the domain would add a parameter to the single dialer and tell a remote nothing it was not already told. The nest's *other* outbound fetchers (media proxy, link preview) deliberately stay **unattributed** — a UA there would tell every fetched origin which deployment is looking — so the shared `ssrf_safe_https_client` takes the UA as an option rather than defaulting it.
- **Username derivation (user-ratified 2026-07-16).** The username mints at enablement from the user's **Fauna handle, verbatim** — the handle charset (3–63 lowercase alphanumeric + hyphens, no edge hyphens; owner: [`../architecture/nest/public-mode.md`](../architecture/nest/public-mode.md) § User Registration) is already a valid WebFinger local-part and inside Mastodon's remote-username grammar. Three rules (`bridge_provider::derive_username`; unit pins `derive_username_tests`, e2e pin `test_enable_derives_username_from_handle`):
  1. **Frozen at enablement.** A later Fauna handle change never renames the AP actor — the username is baked into the UNIQUE `actor_url`, every pushed note id, and every remote server's cache + follow edge, and there is no AP rename/`Move` support (a future `Move`/`alsoKnownAs` story is a separate feature, deliberately out of scope). The Bridges page displays the stored (frozen) identity.
  2. **Collision → lowest free numeric suffix** (`alice-2`, `alice-3`, …). The real collision class is a released-and-reclaimed handle: A froze `alice`, changed handle (72 h cooldown passed), B registered `alice` and enables AP. The bare name belongs to whoever froze it first.
  3. **Handle-less accounts fall back to the legacy first-16-hex-of-actor-id derivation** (admin-created accounts may carry no handle), same suffix rule. Existing rows keep their minted usernames — frozen-at-mint applies uniformly; AP shipped to production 2026-07-16 ([`../architecture/installers/docker.md`](../architecture/installers/docker.md) § Feature flags) with zero enabled accounts at ship time, so there was no migration to perform.
- **Actor serving** (`actor_routes.rs`): `/.well-known/webfinger`, `/.well-known/nodeinfo` (**discovery only** — its href must name `/nodeinfo/2.1`, the document route on this same nest; the two derive from one `NODEINFO_SCHEMA_VERSION` constant precisely because they silently drifted apart once: the href pointed at the `/api/v1/node-info` HTTP twin that the 2026-06-05 discovery rip deleted, so from then until 2026-07-16 every peer following our own advertised link got the SPA's HTML fallback), the NodeInfo 2.1 document itself (`/nodeinfo/2.1` — fingerprint-lean by construction: `software.version` coarsened to `major.minor` like the anonymous `fauna.nest.info` reply, `usage.users.total` counting **AP-enabled accounts only** rather than nest population, empty `metadata`; `protocols` carries only NodeInfo's own vocabulary — `["activitypub"]` — never the nest's internal `fauna`/`nostr`/`bluesky` tokens, which are absent from the schema enum and would fail a strict peer validator), the actor document (rendered from the user's real signed `Profile` row via the shared signed-only `decode_profile` — contract owned by [`../ui/profile.md`](../ui/profile.md); falls back to a minimal Person), `followers`/`following` collections (**count-only** — no member items are exposed, deliberately), and the **pull outbox**: paged `Create{Note}` activities translated on read from the author's stored posts, gated on the account's `backfill` setting (off → an empty collection); and the **single-note dereference** `GET /ap/users/{username}/notes/{post_id_hex}` (§ The produce direction — the note id every produce sink mints must resolve).
- **Inbound pipeline** (`inbox_routes.rs`): per-user (`/ap/users/{u}/inbox`) + shared (`/ap/inbox`) inboxes run the same pipeline — content-type check → 1 MB body cap → HTTP-Signature parse → Digest verify → per-remote-domain rate limit → remote-actor fetch/24h-cache (`ap_remote_actors`) → signature verify against the cached key → dispatch. Handled activities: `Create{Note}` (authorship-gated — the signer must be the Note's `attributedTo`, on the note id's host; translate → BARE-encode → content-addressed `store_post` with source `activitypub` + an `ap_post_map` row), `Update` (Person → refresh actor cache; Note → tombstone-old + store-new) — **both arms object-ownership-gated (audit 2026-07-22); `Update{Note}` also clears the same audience + relationship gates as `Create`** (§ Security posture → Object ownership), `Follow` (record inbound follow; auto-`Accept` if configured), `Undo` (Follow/Like/Announce), `Like`/`Announce` (synthetic upvote/repost posts by a `synthetic_actor_id`, behind the reaction gate below), `Delete` (tombstone the `ap_post_map` row), `Accept` (mark our outbound follow accepted). Unknown types are acknowledged and ignored.
- **Inbound AS2 multi-valued properties parse in BOTH spellings** (`fauna-bridge-activitypub::types::one_or_many`, built 2026-07-22). JSON-LD compaction drops the array wrapper around a property holding exactly one value, so `"tag": {…}` and `"tag": [{…}]` — and `"to": "…#Public"` and `"to": ["…#Public"]` — are the *same* document; a peer chooses freely and both must yield the same parsed value. This is a conformance requirement, not tolerance: because serde fails the **whole** struct on one mis-shaped field, a single compacted property rejects the entire activity. Real GoToSocial 0.22.1 compacts the `tag` of a reply mentioning one account, so **every inbound reply from that peer was refused** with `400` + `invalid type: map, expected a sequence` — invisible against Mastodon, which always emits arrays (§ Implementation status today, gap 4). Applied to every `Vec`-valued AS2 field on `ApNote`/`ApActivity`/`ApPerson`, so a new one cannot be added in only the strict spelling; pinned by `types::tests` (both spellings parse to an equal value, a compacted `to` still reads as publicly addressed, absent/null stays empty) and end-to-end by `TestActivityPubInboundIngest` in `tests/api/test_activitypub_federation.py`.
- **Inbound AS2 required-field strictness matches AS2's actual optionality** (audit 2026-07-22 — the `one_or_many` generalization). serde fails the *whole* struct on one field, so any single required-but-AS2-optional field silently drops an entire legal Note class from some peer — the compacted-`tag` failure mode, one field over. A flow-trace fixes the surface first: **`ApNote` (with its nested `ApMediaAttachment`/`ApTag`) is the ONLY AS2 type this crate deserializes from remote input.** Remote *actors* are read field-by-field from a raw `serde_json::Value` (`fetch_remote_actor`/`parse_remote_actor`, and the `Update{Person}` arm), and the top-level inbox activity is a raw `Value` — so `ApPerson` and `ApActivity` are **serialize-only**, and their required fields cannot cause an inbound drop (correcting two suspects — `ApPerson.name`, `ApActivity.id` — that assumed an inbound-parse path this crate does not have). On `ApNote`, only `id` (the `ap_post_map` identity key — nothing to ingest without it) and `type` (dispatch already guaranteed `"Note"`) stay required. Relaxed: `content` and `published` (AS2-optional; an absent `published` takes an ingest-time fallback, a *malformed* one still errors as non-conformant), `attributedTo` (now accepts the IRI-string, `{id}`-object, and array shapes AS2 permits — kept non-empty because it mints the stored author; **trust is unaffected**, since the relationship/reaction gates key on the signature-verified top-level `actor`, never this self-claimed field), and every field of `ApMediaAttachment`/`ApTag` (a url-less attachment is skipped, not fatal to the Note; tags are unconsumed on ingest). Documented residuals, unfixed because no target peer emits them: a `url` spelled as a Link object/array (Pleroma multi-resolution), and a non-object bare-string tag element. Pinned field-by-field in `types::tests`.
- **The inbound audience gate** (security review): only a **publicly addressed** Note (AS `Public` in the Note's or activity's `to`/`cc`; Public-in-`cc` = Mastodon "unlisted" counts) may enter the public `post/*` projection, because `store_post` rows are full-body, ungated, and searchable by every authenticated user. `is_publicly_addressed` lives in the shared crate; pinned by `inbox_routes` tests. **A non-public `Create{Note}` goes to the direct-message leg instead, which delivers it or drops it (built 2026-10-03):** a Note is *direct* when its audience (`to` ∪ `cc`, the Note's and the activity's) holds neither `Public` nor a followers collection (`is_directly_addressed`, shared crate), and a direct Note is delivered to every **enabled local actor its `to` names** — as a sealed row in that account's bridged room with the sender ([`../ui/conversations.md`](../ui/conversations.md) § Where logic lives → *The `Bridged` adapter*, ruling 3), never as a post. Everything else non-public is ACCEPTED-and-dropped as before: a followers-only Note (with or without a mention — a mention rides `cc`, and the inbox it arrived at is not address), and a direct Note naming no enabled local actor. The room and the family bridge-DM gate key on the canonical top-level `actor` the HTTP signature verified; the Note must be that actor's own (`attributedTo` equal to it, `id` on its host — the object-ownership rule of § Security posture) or it is dropped ([`family-safety.md`](family-safety.md) § The bridge-DM gate → *Enforcement points*). Outbound, a message the user sends in such a room leaves as a `Create{Note}` addressed to that actor alone, with a `Mention` tag, on the signed delivery queue. Pinned by `activitypub::dm_leg` tests. Not built: an inbound `Update` or `Delete` of a direct Note changes nothing.
- **The inbound relationship gate** (ruling 2026-07-19): the audience gate bounds *what kind* of note may enter the public projection; this gate bounds *whose*. A publicly addressed inbound `Create{Note}` is stored only when a local account **opted in**: the signature-verified sending actor is followed by an enabled local account (an outbound `ap_follows` row, any state — the local user's Follow request is itself the opt-in), or the note is addressed to an enabled local account (the per-user inbox target, or a shared-inbox `to`/`cc` resolution). Anything else — including a validly-signed public Note POSTed to a zero-enabled-account nest — is ACCEPTED-and-dropped (no retry, and no oracle distinguishing "no such user" from "not opted in"). This mirrors the Nostr relay store's owner-only scope ([`../ui/nostr.md`](../ui/nostr.md) § The relay event store) — same abuse class, same shape (priority #3). A Note that clears both gates is still ACCEPTED-and-dropped when its `published` sits past the bridged planes' future bound — `Create` and `Update{Note}` alike, before any store or map row moves ([`../ui/feed.md`](../ui/feed.md) § The read model owns the bound and its cushion; pinned by `a_create_note_published_past_the_bridged_cushion_is_not_stored` and its `Update` twin). Keyed on the top-level verified `actor`, never the Note's self-claimed `attributedTo`. Mechanism: `db_helpers::any_enabled_account_follows` + the `handle_create` gate; pinned by the `unsolicited_public_inbound_note_is_dropped` / followed / addressed / disabled-account `inbox_routes` tests.
- **The reaction gate + retraction** (ruling 2026-07-19): an inbound `Like`/`Announce` mints its synthetic upvote/repost only under the `Create` gate's opt-in shape adapted to reactions — the signature-verified reacting actor is **followed** by an enabled local account (a followed actor's likes/boosts are subscribed timeline content), or the reacted-to object is an enabled local account's **own post** (engagement on your own federated posts is what enabling federation subscribes you to — Mastodon-parity: any verified remote actor may favorite/boost a local account's public post; the residual sock-puppet-engagement exposure is accepted, as on every AP server, bounded by signature verification, the per-domain rate limit, and the idempotency below). Everything else — a stranger reacting to an ingested remote object — is ACCEPTED-and-dropped. **Replay idempotency:** one synthetic reaction per (actor, verb, object) — the stable map key (`like:`/`announce:` prefix + acting actor + object URL, deliberately never the activity id, which a replayer mints fresh at will) dedupes before any store side-effect; a tombstoned row is not a duplicate, so un-react → re-react mints again. The same key is `Undo`'s lookup: `Undo{Like}`/`Undo{Announce}` retract the synthetic reaction, actor-scoped by construction since the key embeds the acting actor. (Pre-ruling, `Undo{Like}` hashed the key into a `fauna_post_id` that matched nothing — un-likes never retracted — and `Undo{Announce}`, Mastodon's unboost, was unhandled; pre-ruling Announce rows keyed on the activity id persist at rest, undeduped and harmless.) **Retraction withdraws the whole synthetic post, not just its map row** (ruling 2026-07-20): because a tombstoned map row is deliberately not a duplicate (un-react → re-react mints again), an `Undo` that tombstoned only the map row would orphan the synthetic `content`/`content_meta`/segment rows the mint created — one per react→unreact cycle, driveable by any opted-in remote actor on any local public post, bounded only by the per-domain inbox rate limit. So `retract_reaction` tears down all three (map-row tombstone + `delete_post_projection` + segment `tombstone_by_cid`), mirroring `delete_post_core`'s teardown minus the counter reversal (the AP mint never calls `record_reference_engagements`, so no counter was ever bumped) and the propagation legs (a synthetic reaction post is never itself pushed or replicated). This bounds the synthetic corpus to at-most-one post per (actor, verb, object) at any instant — the same invariant the dedupe key enforces on the map. Mechanism: `mint_synthetic_reaction`/`retract_reaction` (one path for both verbs, so gate/key/retraction cannot drift) + `db_helpers::enabled_account_owns_ap_url`; pinned by the reaction-gate/replay/undo `inbox_routes` tests (including `undo_withdraws_the_synthetic_content_projection`) + the `db_helpers` ownership unit.
- **Outbound delivery** (`sync_worker.rs` + `ap_delivery_queue`) — **enqueue-then-nudge, one path for every producer:** an activity is written to `ap_delivery_queue` per target inbox (durable — it survives a nest restart), then the producer wakes the worker via the `delivery_nudge` (`tokio::sync::Notify` on `ActivityPubState`) so it drains the queue *now*. The worker delivers with an HTTP-signed POST (per-account RSA key, `Digest` + `Signature` + `Date` headers), 3 attempts with exponential backoff, dead-inbox tracking (>7 days failing → skip + hourly cleanup of stale follows to dead inboxes). Its 30 s poll is the **backstop, not the delivery mechanism**: a missed nudge costs latency, never the activity. Durability and immediacy are therefore independent — which is why the nudge is a signal rather than a channel carrying the activity (a channel send can drop or block, and would lose a `Create` on a nest crash). Nudges coalesce (`notify_one` leaves a permit when the worker is mid-drain), so a burst enqueues once and drains once.
- **Outbound interactions** (`interact.rs`, dispatched from the unified `fauna.posts.interact` by post source `activitypub`): `like` → `Like`, `repost` → `Announce`, enqueued to the object owner's inbox — resolved from `ap_remote_actors` via the map row's `remote_actor_uri` (URL-shape heuristic only as the legacy-row fallback); `reply`/`quote` are the **eligibility + target-info door** of § Reply and quote (design ratified 2026-09-26, built 2026-09-28): the reply itself is the replier's own signed post, and the `Create`-push derives its fediverse form.
- **Control plane — the `fauna.bridges.*` wire, and nothing else:** the `ActivityPubProvider` (`bridge_provider.rs`) — link mode `enable` (no fields), settings `auto_accept_follows` / `default_visibility` (public | unlisted | followers_only) / `backfill`, follow add/remove. Page UX and wire owned by [`bridges.md`](bridges.md). The duplicate `/api/v1/activitypub/*` bearer-auth HTTP routes (`account_routes.rs`) were **ripped 2026-07-16** following the Nostr control-plane precedent ([`../architecture/api-layers.md`](../architecture/api-layers.md) § ActivityPub); no app had ever called them. **The duplicate had drifted into an authz bypass** — the textbook cost of two control planes for one capability: `fauna.bridges.link` gates on `require_permission` **and** the guardian `feed_sources` check, while the HTTP `enable` carried only `BearerAuth` ([`family-safety.md`](family-safety.md) § Guardian policy — that gate's whole subject is `fauna.bridges.{link,add_follow,feeds.create}`). The second surface never gained the gate the first one grew. Ripping it closed the bypass: the `fauna.bridges.*` wire is the only control plane for the capability, so its gates cannot be routed around.

## Data shape (nest-side, `libs/fauna-bridge-activitypub/src/db.rs` + `activitypub::init_db`)

| Table | Holds |
|---|---|
| `ap_accounts` | per-actor AP identity: username, actor URL, encrypted RSA privkey, public PEM, `enabled`, `backfill`, `auto_accept_follows`, `default_visibility` |
| `ap_remote_actors` | 24h cache of fetched remote actors: inbox, shared inbox, public key, profile fields; every write also projects the actor's face into the cross-bridge `bridge_authors` row — owner [`bridges.md`](bridges.md) § Unified feed ingestion → *Bridged authors* |
| `ap_follows` | follow edges, `direction` = inbound (they follow us) / outbound (we follow them), `state` = pending/accepted |
| `ap_post_map` | `fauna_post_id ↔ ap_url` mapping (+ owning actor, `tombstoned` flag, and — since 2026-07-16, additive — `remote_actor_uri` for real-inbox resolution on interactions); written by inbound ingest AND the local `Create`-push |
| `ap_delivery_queue` | pending outbound activities: JSON + target inbox + attempts/backoff/status |
| `ap_dead_inboxes` | delivery-failure tracking driving the dead-inbox skip |

All evolution is additive (`CREATE TABLE IF NOT EXISTS` + additive migrations); follows/settings are user-recreatable but never dropped on upgrade (alpha invariant).

## The produce direction — `Create`-push to followers (ratified + built 2026-07-16)

Before this direction, local posts were only **pulled** (the backfill-gated outbox); no `Create` was ever delivered to a follower's inbox, so accepting followers was misleading — they received nothing. The produce direction closes that: **a local post actively fans out to the author's accepted fediverse followers**, the same delivery model every AP server implements. Mechanism (`bins/fauna-nest/src/activitypub/push.rs`):

- **Hook:** the shared create-side bridge fan-out `routes::spawn_post_bridge_fanout` (this push beside the Bluesky write-through, both `cfg`-gated), called wherever a post enters the store as a **new** row — `ingest_post_core` and the forwarded-post receive alike (paired-deployments bullet below). Fire-and-forget + non-fatal (a push hiccup must never fail the store), a clean no-op when the author has no enabled AP account or no accepted followers.
- **Gate:** the account's existence + `enabled` — enabling federation *is* the opt-in (unlike Bluesky's `write_through` mode, which cross-posts to an *external* identity and therefore wants its own knob, an AP follower explicitly subscribed to this actor; delivering is the contract of accepting the Follow). No new setting.
- **Addressing consumes `default_visibility`** (today stored but unread): `public` → `to=[Public], cc=[followers]`; `unlisted` → `to=[followers], cc=[Public]`; `followers_only` → `to=[followers]`. `fauna_post_to_ap_note`'s fixed public addressing gains a visibility parameter (shared-crate change). The pushed body is exactly what the pull outbox serves for the same post — public-by-construction content, because **a gated post is not federated at all** (next bullet).
- **A gated (monetized) post is never federated** — not pushed, not served by the pull outbox, and not counted in the outbox's `totalItems`. This is the *world-broadcast* stance nostr states categorically (`public_post_from_payload`: *"a gated post is never world-broadcast, even though its preview body decodes"*) and the trending plane hard-refuses; AP now matches rather than deviating (priority #4). **Not a confidentiality measure** — a gated post's stored body *is* its public preview and the public web paywall renders that same teaser to anonymous callers by design ([`restricted-posts.md`](restricted-posts.md) § Encryption at rest); the full content is ciphertext at `gated.encrypted_ref` and never reaches this path. It is a **monetization-integrity** one: federating the teaser as an ordinary free `Note` strips the paywall/unlock affordance the web render carries, so the post arrives on a remote server indistinguishable from free content. Mechanism, and why it must be explicit: a gated post lives in the public `post/*` projection like any other (`db::post_body_schema` derives `schema` from the body variant alone and never reads `Post::gated`), so exclusion is **read-side and per-consumer**, keyed on `content_meta.gated_tier` — the preview body decodes fine, and nothing upstream stops it. The outbox's share of that contract is single-owned in `db_helpers::public_outbox_{count,page}`; the push leg refuses in `create_push_inner`. Pinned by `create_push_skips_gated_posts` + `public_outbox_reads_exclude_gated_posts`.
- **Object identity is push/pull-symmetric:** note id `<actor>/notes/<post_id_hex>`, activity id `<actor>/activities/<post_id_hex>` — identical to the outbox translation, so a pushed and a pulled copy of the same post are the same AP object.
- **The note id is dereferenceable (built 2026-07-19):** `GET /ap/users/{username}/notes/{post_id_hex}` serves the same `ApNote` (with `@context`) that the push delivers and the outbox embeds. Real-peer propagation depends on it: a third-party server receiving an `Announce` (boost) of our note fetches the object by id before rendering it, and mainstream search-by-URL resolves the same way — our in-test fediverse server never dereferences, which is how the missing route stayed green (remaining-gap 4's lesson: real-peer conformance is a mechanism, not pixels). Servability mirrors the outbox filter, single-owned in `db_helpers::public_note_exists` (right author, `post/%` row, not gated) plus the public-addressing check on the translated note; every other case — gated, author mismatch, disabled account, followers-only visibility, unknown user, malformed hex — is an indistinguishable 404. **Deliberately NOT gated on `backfill`:** that flag governs bulk history *enumeration* (the outbox), while a pushed note's id must stay fetchable or boosts of a no-backfill account's posts break on every third-party server. Pinned by `note_url_serves_public_note` + `note_url_404s_every_non_public_case` + `public_note_exists_applies_outbox_filter`.
- **Fan-out:** accepted **inbound** follows → resolve each via `ap_remote_actors` → prefer `shared_inbox` over `inbox` → dedupe inbox URLs → enqueue (one queue job per inbox, same activity JSON) via the delivery worker; retries/dead-inbox handling ride the existing queue semantics unchanged.
- **The push writes an `ap_post_map` row for the local post** (`fauna_post_id`, the local note URL, the author). This is what makes the produce direction *round-trip coherent*: inbound `Like`/`Announce`/`Delete`/replies targeting our pushed note URL resolve through the same `get_post_id_for_ap_url` lookup as any remote object, and the `Delete` leg (below) gets its pushed-witness. Local rows cannot misroute the unified interact dispatch — it keys on the post's `source`, and a local post's source is `fauna`.
- **Paired private→public deployments (ratified 2026-07-16): the forwarded-post receive runs the same create-side fan-out.** A post authored on a private nest reaches its paired public nest as `fauna.federation.post.forward`; the receive (`post_forward_handler`) stores it and — iff it was **newly** stored — calls `spawn_post_bridge_fanout`, so the author's fediverse followers receive the post exactly as if it had been created locally. The mandate model: **fan-out authority is the author's own per-actor bridge enablement on the publishing nest, never the post's arrival path.** Three grounds, all already ratified elsewhere: the author registered on the public nest and enabled AP *there* (bridges run on the public nest only — [`../architecture/nest/private-mode.md`](../architecture/nest/private-mode.md) § What a private nest does NOT do), the pull outbox already serves forwarded posts under the author's actor with no origin distinction (push/pull symmetry — a pushed copy adds no authority the pull doesn't exercise), and the `Delete` leg already chases forwarded tombstones through the shared `delete_post_core` (a nest that chases deletes of posts it refused to publish would be incoherent). The newly-stored gate is the idempotency guard: a private outbox retries until acked, and `store_post` is itself an idempotent upsert — so the receive checks the `content` projection for the post id *before* storing (`CacheDb::post_exists`), and a re-delivered forward fans out nothing; a forward of a post this nest has seen deleted is neither stored nor fanned out ([`../ui/feed.md`](../ui/feed.md) § State & data shape → *Post deletion*). Structural non-risks: exactly one nest can hold the author's AP account (bridges are public-nest-only), and a public nest never re-forwards (`maybe_enqueue_outbox` is private-mode-only) — no double-push, no loop. (Private-mode nests expose no AP endpoints at all.)

## Reply and quote — the produce direction extended to referenced remote objects (ratified 2026-09-26, design pass; built 2026-09-28 — § Implementation status today gap 1)

**The shape.** A reply to, or a quote of, a fediverse post is **an ordinary signed post of the replier** — the same `Reference::Reply`/`Reference::Quote` post every native reply is ([`../ui/feed.md`](../ui/feed.md) § Interaction bar → *Reply and quote on a bridged post* owns the app-side rule and the one-reply-shape rule) — composed by the app and created through `fauna.posts.create`; the nest never mints a post on the user's behalf (it holds no key that could sign one, and `fauna.posts.create` refuses an unsigned body). The bridge then **derives** the ActivityPub form inside the create-side fan-out it already runs for every new post (§ The produce direction): this section is that direction extended to a post that *references* a remote object, not a new arm. **Rejected alternative — the nest-mint shape:** building the reply from the interact request's `body` and posting it remotely (what the bluesky arm shipped until 2026-09-26, when it joined this shape — [`bridges.md`](bridges.md) § Interactions). A reply that is not in the user's own store cannot be deleted through `fauna.posts.delete`, exported, threaded under its target in the feed, or chased by the `Delete` leg — and on this bridge it would not even appear in the replier's own feed, since nothing pulls our outbound notes back. Every other outbound path here (the `Create`-push, the `Delete` leg, the pull outbox, nostr's materialization, bluesky's write-through) already goes *local signed post → derived remote form*; the reply follows it.

**The door.** `fauna.posts.interact` `{action: reply | quote}` on a post whose source is `activitypub` answers the native arm's ack verbatim — `{action, target_post_id, source}` — when the caller may federate a reply, or refuses — **typed, one code per remedy (ratified 2026-10-08):** `fauna.activitypub.not_linked` (no ActivityPub record for the account — enable it on the Bridges page) and `fauna.activitypub.switched_off` (the record exists, federation is off — turn it back on there), each a `400` at the door that the posts mapper carries through as its code with the reason in `details`, and each rendered app-side by `RpcError::localized()`'s exact-code arm naming the Bridges page (`i18n` `error.activitypub.*`; [`../ui/feed.md`](../ui/feed.md) § Interaction bar → *Reply and quote on a bridged post* owns the app-side rule and the older-app fallback). The app composes only on the ack; a `body` on this door is ignored (the words travel in the signed post). An older nest answers `fauna.posts.unsupported` (its `not_implemented`), which the app renders as the affordance's inline failure and composes nothing — additive in both directions, no new wire field. The ack's `counts` are `Some`, read from `content_meta` exactly as the native arm reads them: the target is a local row (the ingested note), so its counters are what the card shows — unlike a bluesky target, whose counters live at the origin and stay `None`.

**The derived `Create{Note}` — a reply.** In `create_push_inner`, a post whose `Reference::Reply{post_id}` resolves through `ap_post_map` (`get_ap_target_for_post` — an ingested remote note, or one of our own pushed notes; same table, so a self-thread works) is pushed with `inReplyTo` = the target's `ap_url`, a `Mention` tag for the target's author (`href` = the map row's `remote_actor_uri`, `name` = `@preferredUsername@host` from the cached actor — `ap_remote_actors`), the author's actor URI added to `to`, and the author's inbox — `resolve_delivery_inbox`, lifted out of `interact.rs` so the push and the interaction arms share one copy — added to the delivery set beside the follower fan-out. Addressing otherwise follows `default_visibility` exactly as a top-level post. Everything else is the plain push, unchanged: note id and activity id, the `ap_post_map` row for the local note (so the remote author's `Like`, reply or `Delete` on our reply resolves), enqueue-then-nudge, the gated-post exclusion, the `Delete` leg on `fauna.posts.delete`. A reference that resolves to no map row (a native target, a bluesky or nostr one) pushes a plain top-level note — the reply threads on Fauna only, which is correct: the target was never a fediverse object.

**The derived `Create{Note}` — a quote.** AS2 has no quote verb. **Ruling:** a `Reference::Quote` whose target resolves through `ap_post_map` is pushed as a `Create{Note}` carrying the quote in every spelling a mainstream server reads today, all additive on one object: the FEP-e232 object link — `tag: [{type: Link, mediaType: 'application/ld+json; profile="https://www.w3.org/ns/activitystreams"', href: <ap_url>, name: 'RE: <ap_url>'}]`; the FEP-044f `quote` property (Mastodon ≥ 4.4's own reading) together with its legacy twins `quoteUri` and `_misskey_quote` (the Misskey family) — all three emitted; and the line `RE: <ap_url>` appended to the note's `content`, which is what a server that understands none of them renders. The pinned F-matrix Mastodon (`v4.3.15`) predates quote support entirely, so that content line is the real-peer observable there. **Deferred, named:** the FEP-044f `QuoteRequest`/`QuoteAuthorization` handshake by which Mastodon ≥ 4.4 marks a quote *verified*; without it a 4.4+ server shows the quote in its fallback form and never drops the post. It becomes a build the moment a 4.4+ pin shows the fallback unacceptable — the F-matrix leg mints it. The quoted author's inbox joins the delivery set exactly as a reply's does (a quote is a mention of its author in every fediverse UI).

**The inbound half of the same thread.** `ap_note_to_fauna_post` writes `references: []` for every ingested note, so a remote reply to our note (F5) rests unthreaded — mapped and stored, but with no `Reference::Reply`, hence `is_reply = false`, no `content_links` row and no `reply_count` on our note. The design closes it in the same build: `handle_create` and the `Update{Note}` unseen-post arm resolve `inReplyTo` through `get_post_id_for_ap_url` and pass a `Reference::Reply` into the translation (the shared translator gains the input and stays DB-free), so the ingested reply threads under our note like a native one. An `inReplyTo` this nest never mapped resolves to nothing and the note stays top-level — never a synthetic id ([`../ui/nostr.md`](../ui/nostr.md) § Replying to and quoting a nostr note records why that shape threads nothing).

**Media, mirror, thread, delete.** All the top-level post's rules, unchanged: the signed post's `TextWithMedia` items translate to AP `Document` attachments through `media_item_to_attachment`; the reply is a local row with source `fauna`, threads under the ingested note by its local id, moves that note's `reply_count` through `record_reference_engagements`, and is chased by the `Delete` leg like any pushed note.

**Security.** No new inbound surface and no configuration: one added delivery target, resolved from the cached actor the inbound ingest recorded — never from anything the client supplies (§ Security posture → Outbound).

**Pins the build owes**: `push::tests` — a reply resolves `inReplyTo` + Mention + the author-inbox job, a quote carries the three spellings + the Link tag + the `RE:` line, an unmapped reference pushes today's plain note, a reply to our own pushed note resolves; `inbox_routes::tests` — an inbound `inReplyTo` naming our note threads, an unknown one stays top-level; the tier_3 in-test server (`TestActivityPubFollowerDelivery`) — a `fauna.posts.create` reply to an ingested `FakeFollower` note lands a signed `Create` on the follower's inbox with `inReplyTo` = its note id and the follower's actor in `to`; the F-matrix — **F10**, our reply to a peer status appears in that status's context on the peer (`GET /api/v1/statuses/{id}/context` descendants), and **F11**, our quote arrives with the `RE:` link in its content — both against Mastodon *and* GoToSocial (the AP arc's lesson: one lenient peer is a weak oracle).

## Post deletion — the AP `Delete` leg (Leg D of the propagation set; ratified + built 2026-07-16)

The delete verb, wire, authz, and the "a deleted post must not outlive its derivations" invariant are owned by [`../ui/feed.md`](../ui/feed.md) § Post deletion; this section owns only the AP leg's mechanics.

- **Symmetry rule (load-bearing): push a `Delete` iff a `Create` was pushed.** The `ap_post_map` row the push wrote is the witness. Without the produce direction the leg is incoherent — there is no pushed derivation to chase (which is why it was deferred until the produce ratification).
- **Hook:** `routes::delete_post_core` step 7, a further non-fatal step after the paired-replica twin — `#[cfg(feature = "activitypub")] activitypub::push::spawn_delete_push(state, actor, digest)`, fire-and-forget, never fails the local delete. It runs after a delete's own steps and again on a retry that finds the post already gone (`AlreadyGone`), when the post-delete witness names the retrying actor — so a retry chases a `Delete` a first attempt failed to enqueue (`push::tests::a_retried_delete_of_a_gone_post_still_pushes_the_delete`); the tombstoned `ap_post_map` row still resolves for it.
- **Mechanics:** look up the author's `ap_post_map` row for this post (**including tombstoned rows** — retry idempotency; `db_helpers::get_local_note_url`), no row or no account → clean no-op (deliberately not gated on `enabled` — a `Create` pushed before the user disabled federation must still be chased); build `build_delete_activity(actor_url, activity_id, note_url)`; fan out to accepted followers exactly as the create push; tombstone the map row (the local delete already stands regardless of delivery outcome — best-effort eventual consistency, like every other leg).
- **Inbound hardening (landed with the leg):** inbound `Delete` used to tombstone whatever `ap_post_map` row the object URL resolved to, **without checking the signing actor owns the object** — any authenticated remote could hide any mapped post (including, once the push landed, our own local notes). `handle_delete` now enforces the standard same-origin check: a `Delete` whose object URL's host differs from the signing actor's host is dropped (ACCEPTED, no retry). (`Undo`'s arms never needed it — all are actor-scoped by construction: the Undo-Follow deletes only that actor's own follow edge, and the Undo-Like/Undo-Announce retraction key embeds the acting actor — § Architecture → The reaction gate.)
- **Inbound `Delete` withdraws the translated post (2026-08-02).** Tombstoning the map row was never enough, and the sibling path already said so: `retract_reaction`'s own doc notes that "tombstoning only the map row would orphan the synthetic `content`/`content_meta`/segment rows", which is why `Undo` tears all three down. `handle_delete` did not — and **nothing in serving reads `ap_post_map.tombstoned`** (its only readers are the push/interact URL lookups, `WHERE tombstoned = 0`), so a note its author deleted upstream stayed in the Fauna feed indefinitely. Both paths now share `withdraw_translated_post` (projection + segment teardown; best-effort and non-fatal, since the map tombstone has already hidden the object).
- **…for INGESTED notes only — the destructive verb does not rest on the same-origin gate alone.** A local account's own pushed note also has an `ap_post_map` row, and § Security posture *knowingly accepts* that a signature-verified sibling on a shared instance may `Delete` a same-host actor's object. That residual may cost a hidden map row; it must not cost a user their post. The withdrawal is therefore gated on `db_helpers::is_local_account_post` — deliberately **not** the reaction gate's `enabled_account_owns_ap_url`, whose `enabled = 1` clause would stop protecting a user's posts the moment they switched federation off and whose `tombstoned = 0` clause would stop protecting them on a delete retry. `fauna.posts.delete`, with its three author checks, remains the only verb that may destroy a local post.

## Follow requests — approving or refusing a held-back follow (designed 2026-10-01; nest and shared Rust built 2026-10-04, app surface pending — § Implementation status today gap 5)

**The gap this closes.** With *accept follows by itself* off, `handle_follow` records the inbound `ap_follows` row as `pending` and stops: until this section was built nothing in the nest, on the wire or in any app could move it, so the switch as first shipped could only make followers wait for ever — the requester's server shows a request nobody answers, and the user is never shown that one exists. A choice the app offers must have both of its positions usable from the app (§ Goal: all user choice lives in the Bridges UI), so the off position gets its surface rather than being removed: `followers_only` default visibility means something only when the account decides who its followers are, and the pair is the fediverse's ordinary locked-account shape. **Rejected alternative — retiring the switch** (always accept): it would leave `followers_only` addressing readable by anyone who asks, and remove a ratified user choice to spare a list.

**A request is the pending row — no new table.** The inbound `ap_follows` row in state `pending` *is* the follow request: it already holds the remote actor and the `Follow` activity id the answer must name. Listing requests reads those rows joined to `ap_remote_actors` for the requester's `@user@host` address and display name. The app surface and its two wire kinds are owned by [`bridges.md`](bridges.md) § Follow requests; this section owns what each answer does.

**Approve** runs exactly what the auto-accept arm runs — build `Accept{Follow}`, enqueue-then-nudge to the requester's inbox, mark the row `accepted` — through **one function both callers share** (`inbox_routes::accept_inbound_follow`; `handle_follow`'s auto arm runs it, so the two paths cannot drift). The function reads only what the stored row keeps — the requester and the `Follow` activity id — so the `Accept` embeds a `Follow` rebuilt from those (`translate::follow_object_for_answer`: `id`, `actor`, `object`) rather than the inbound activity's own JSON: an answer sent at the door and one sent days later are the same object, its id is derived from the `Follow`'s id, and nothing the requester wrote is echoed back beyond that id. From then on the follower is in the `Create`-push fan-out (§ The produce direction); posts made while the request waited are not replayed to it.

**Refuse** sends `Reject{Follow}` (the shared crate gains `build_reject_activity`, the `Accept` builder's twin) through the same queue and **deletes the row** (`inbox_routes::reject_inbound_follow`). An answer acts on a *pending* row only (`inbox_routes::resolve_follow_request`): a refusal that arrives after the follower was accepted — a stale card on another device — deletes nothing and sends nothing. A refused requester may ask again, and a later `Follow` is a new request. Refusing is not blocking: keeping an actor out for good is a separate feature and is not designed here.

**A withdrawn request leaves by itself.** `Undo{Follow}` already deletes that actor's inbound edge whatever its state, so a requester who cancels drops off the list with no user action.

**Turning the switch back on answers everything waiting.** A `set_settings` that moves `auto_accept_follows` from off to on approves every pending inbound row through the same function; otherwise the requests that arrived while it was off would stay stranded behind a switch that says follows are accepted. As built (`ActivityPubProvider::update_settings` → `inbox_routes::accept_all_pending_follows`) the setting is written first, so a `Follow` arriving meanwhile is accepted at the door, and the sweep runs on every write that leaves the switch on rather than on the off→on edge alone — a sweep cut short is finished by saving the setting again, and with nothing waiting it sends nothing.

**The actor document says which mode the account is in.** `manuallyApprovesFollowers` is served as the negation of `auto_accept_follows`, on both shapes of the document — the profile-backed one and the no-profile `minimal_person` fallback — because the caller hands the flag to the shared builders (`fauna_profile_to_ap_person`, `ap_person_skeleton`). Until 2026-10-04 it was derived from the profile's conversation inbox mode (`AllowKnock | ContactsOnly | Closed`), which answers a different question — who may message the account — so an account could advertise manual approval and then accept at once, or the reverse, and a no-profile account always advertised open follows. Peers render the lock and their "request sent" state from this field, so it must describe the follow path.

**Telling the user — deferred, named.** An inbound follow raises no notification today, accepted or pending, and this design does not add one: the Bridges card shows the waiting requests and their count. A notification for a new follower or a new request is a new notification kind and belongs to [`notifications.md`](notifications.md); until it exists, a user who turns the switch off finds requests by opening the card.

**Security.** No new inbound surface: both answers act only on a row the verified inbound `Follow` created, name the requester by the stored actor URI (never a client-supplied URL), and ride the existing signer, queue, retry and dead-inbox posture. Both kinds are self-scoped — an account answers its own requests only.

**Pins (written and green 2026-10-04, save the last):** `inbox_routes::tests` — `auto_accept_and_approval_produce_the_same_accept_and_row_state`, `refusing_a_follow_enqueues_reject_deletes_the_row_and_a_second_follow_is_pending_again`, `a_late_refusal_never_removes_an_accepted_follower`, `turning_auto_accept_on_approves_every_pending_follow` (through the provider, so it also pins the list read and its `handle`), `a_withdrawn_request_leaves_the_list_by_itself`; the actor-document tests — `actor_routes::tests::actor_document_manual_approval_follows_the_setting_and_ignores_the_inbox_mode` (both document shapes) and the shared crate's `manually_approves_followers_is_the_callers_and_ignores_the_inbox_mode` and `reject_is_the_accept_builders_twin`; the tier_3 in-test server (`TestActivityPubFollowerDelivery`) — `test_a_held_back_follow_is_listed_as_a_request`, `test_approving_a_request_sends_accept_and_later_posts_reach_it`, `test_refusing_a_request_sends_reject_and_later_posts_do_not_reach_it` (the negative half read from the delivery queue once the fan-out's other delivery has arrived, never by waiting out a clock), `test_turning_auto_accept_back_on_accepts_the_waiting_requests`, plus `TestActivityPubFederation::test_actor_document_says_whether_followers_are_approved_by_hand`. Still owed: the lead app's journey through the Bridges card ([`bridges.md`](bridges.md) § Follow requests).

## Security posture

- **Inbound:** HTTP-Signature verification against the fetched-and-cached remote key on every inbox POST; 1 MB body cap; per-remote-domain rate limiting (30/s, `governor`). The audience gate keeps non-public remote content out of the public projection entirely; the relationship and reaction gates (§ Architecture) bound whose content and engagement enter at all. **Signature coverage is enforced, not merely a signer courtesy (closed 2026-08-15):** `verify_signature` checks only the headers the signer's own `headers=` list names, so nothing outside that list is bound to anything. `(request-target)` is now required unconditionally (every signer in this codebase always includes it, so this costs nothing legitimate), and the inbox route now requires the `Digest` header to be present *and* named in the signed-header list — a Digest header that merely matches the body (the pre-existing check) proves the body is self-consistent, not that anyone signed for it. Every delivery this nest sends already covers both (`sync_worker::deliver`), so the fix asks nothing of a peer we don't already hold ourselves to. **The floor covers all four headers the signer emits (closed 2026-08-16).** The digest floor above bound the BODY; `date` binds the request to a *moment*, and both were left to signer discretion when the first floor landed. **`host` binds this nest's authority in BOTH halves — coverage AND value (completed 2026-08-17).** Requiring `host` in the signed set is what makes the signing string nest-specific at all (below); the value check is what makes the covered `host` name *this* nest — `verify_signature` reconstructs the signing string by reading each covered header back out of the request *as sent*, so coverage alone would not distinguish a delivery signed for another nest's authority from one signed for ours. **The accepted-authority set (ratified 2026-08-17, row 152 item 1)** is exactly the nest's identity authority: the request `Host` and `handle_domain_if_set()` compare as `host[:port]` authorities (`inbox_routes::host_authority`) — host part case-insensitive with a trailing FQDN dot trimmed, an absent port defaulting to 443 (AP rides https, so `example.com` ≡ `example.com:443`) — and deliberately **not** port-blind: a dev/e2e identity domain is an `ip:port` netloc and two nests may share a hostname differing only in port, so the port is part of the authority. Per-user *web* subdomains are not AP authorities — every actor URI this nest advertises rides the identity domain, so nothing legitimate is refused. **A domainless box refuses all inbound deliveries outright** (404, the same not-configured posture the discovery routes hold): no authority exists to bind, WebFinger refuses discovery, and the actor URIs such a box would advertise are placeholders, so no peer can legitimately hold a URL of ours to deliver to. The follow-edge question is settled independently of signature coverage by **`handle_follow` route/body agreement (2026-08-17):** whichever way the target username is determined, the signed `object` must name that same local actor on this nest's authority, so a route-supplied username can never outvote the target the follower actually signed for (`inbox_routes::tests::follow_drops_a_route_username_the_signed_object_did_not_name`). **`host`, the coverage half:** `(request-target)` covers `method path` and nothing else, and the shared-inbox path is the same constant on every fauna nest, so without `host` in the signed set a delivery's signing string would say nothing about *which* nest it was for; coverage closes that half, the value check above the other. **`date` + a freshness window:** the two are one remedy, because requiring coverage without a window leaves the signature valid forever and enforcing a window on an *unsigned* Date lets the replayer rewrite it. Both are needed because `handle_follow`/`handle_undo{Follow}` carry no per-activity replay suppression of their own. The window is `AP_INBOX_DATE_SKEW_SECS`, one hour, symmetric, a hard-coded constant like the rest of this surface; it bounds replay rather than eliminating it (per-activity suppression would be the mechanism for that, and the reaction handlers already have their own — § Architecture → The reaction gate). Exposure was bounded by who can hold the signed bytes — TLS protects transit, so the replayer is a terminating proxy, a forwarding relay, log/backup exposure, or a receiving nest replaying to a *different* nest. It cost no legitimate peer anything by this posture's own standard: this nest's signer already covers all four, and Mastodon/GoToSocial sign `(request-target) host date digest`. Pinned by `http_signatures::tests::verify_rejects_a_signature_not_covering_request_target`, `inbox_routes::tests::{inbox_rejects_a_signature_that_does_not_cover_digest,inbox_accepts_a_signature_that_covers_digest}`, the two replay-window probes `{probe_373_a_a_years_stale_signed_date_must_not_be_accepted,probe_373_b_a_signature_omitting_host_must_not_verify_at_another_nest}` — both red-verified against the pre-fix code before the fix landed — the host-value probe `probe_374_a_a_delivery_signed_for_another_nest_must_not_verify_here` (shipped `#[ignore]`d and red against pre-fix code; un-ignored by the value-check commit), and the authority-bound pins `{a_domainless_box_refuses_deliveries_as_not_configured,a_default_port_spelling_of_our_authority_is_accepted,a_delivery_for_our_host_on_another_port_is_refused}` plus the `host_authority` normalization table test. **The accepted-authority set governs every inbound actor-URL door, not only `Host` (closed 2026-08-17):** shared-inbox `to`/`cc` username resolution, `handle_follow`'s signed-object check, `handle_undo{Follow}` and `handle_accept` all decide "is this our actor URL" through the one predicate `inbox_routes::local_actor_username` (https + `/ap/users/<username>`, authority compared via `host_authority`) — before it, those four doors raw-prefix-matched exactly one spelling of the authority (fail-closed — stricter, refusal never forgery — but drift-prone, with no test watching a loosening). Pinned by the four `*_agrees_with_the_host_door_on_spelling` door-agreement tests, each asserting its door's accept/refuse matches `host_authority` equality across a spelling table (the general invariant, not hand-picked cases), plus the `local_actor_username` table test. ⚠ The AP module is behind the non-default `activitypub` feature, so a bare `cargo test -p fauna-nest --lib` reports these as *filtered out* and exits 0; the gate that runs them is `just nest-lib-test-check`'s second arm.
- **Key custody:** per-account RSA private keys **and the instance actor's** rest encrypted under the nest identity key, decrypted only transiently to sign; compromise of the DB alone does not yield signing capability. One custody rule for both key classes, deliberately — a second scheme for a second class is what makes a posture unauditable.
- **The remote-actor fetch trusts nothing about the response.** It is dialed at an attacker-supplied URI before any verification, so: non-2xx is an error (never a document), and a body missing an `inbox` or a `publicKeyPem` is refused rather than cached. Both were absent until 2026-07-22 and the pair was actively harmful: every field was read with `unwrap_or("")`, so a peer's *error body* — which is JSON, and parses — became a `RemoteActor` with an empty key, was cached for 24 h, and made every subsequent activity from that actor fail signature verification with a PEM parse error that pointed the reader at crypto rather than at the refused fetch. A cached row with an empty key is now also treated as stale, so rows already at rest heal on the next activity instead of on a timer. **Nor its size (closed 2026-09-28):** the guarded dialer bounds the target and the time (10 s), not the bytes, and the fetch runs pre-signature on a URI the unverified activity named — so an uncapped read was an unauthenticated memory lever. The actor document is read through `crate::ssrf::read_capped` at 1 MiB (`outbound::AP_ACTOR_DOCUMENT_MAX_BYTES`, the inbox POST's own cap) and parsed from the bytes; an error body, here and on a failed delivery (`sync_worker::delivery_outcome`, whose inbox a remote named), keeps a 4 KiB prefix (`outbound::error_body_snippet`) and never pulls the rest off the socket. Pinned by the `inbox_routes::tests::an_*_cap*` set and `sync_worker::tests::an_endless_delivery_error_body_is_cut_at_the_cap`, all red against the uncapped reads.
- **At rest:** ingested AP notes are public-by-construction (the audience gate admits only publicly addressed content) — the plaintext-by-design readable class, same as public posts.
- **Outbound:** the mirror of the inbound audience gate — only content Fauna itself treats as world-broadcast leaves via AP. Today that means **gated posts are excluded** from both the push and the pull outbox (§ The produce direction). The `post/*` projection is *not* self-filtering: it holds gated posts too, and every public-broadcast consumer carries its own `content_meta.gated_tier` exclusion. **A new AP surface that reads `post/*` inherits that obligation** — the filter is emergent and per-consumer, not central. A reply or quote of a remote object (§ Reply and quote) adds exactly one delivery target — the referenced object's author's inbox, resolved from the cached remote actor the inbound ingest recorded, never from a client-supplied URL (the client names only a local post id) — and rides the same queue, signer, retry and dead-inbox posture as every other push.
- **Object ownership — two tiers, deliberately asymmetric (ruling 2026-07-22):** the gate strength follows what the verb *semantically claims*. **Object verbs (`Delete`, `Update{Note}`) enforce actor↔object same-origin** — host equality — because an instance legitimately manages its own objects (a moderator tombstoning a departed user's post is a normal `Delete`); the residual this accepts, and accepts knowingly, is that a signature-verified sibling on a *shared honest instance* can Delete/Update another same-host actor's mapped object — instance-internal authority is the instance's to police, not ours (`Delete`: § Post deletion, last bullet, landed 2026-07-16; `Update{Note}`: audit 2026-07-22). **The actor verb (`Update{Person\|Service\|Group\|Organization\|Application}`) requires exact self-identity** (`same_actor_identity`: normalized URL equality of the signed actor and `object.id`) — an actor update is *always* self-authored, so host scope was looser than the verb's own semantics. The rule that now holds: **only an actor itself may replace its own cached public key**, same-host siblings included — that cached key is what verifies every later activity from the actor. **`Create{Note}` claims authorship, so it takes both checks at once (2026-09-28):** the signed actor must BE the Note's `attributedTo` (`same_actor_identity`) and the Note's `id` must sit on the signer's host (`same_origin`); anything else is ACCEPTED-and-dropped with a spoof-attempt warning. The `Update{Note}` arm's unseen-post branch stores like a `Create`, so it takes the same `attributedTo` rule; a seen-post `Update{Note}` stays the object verb above. Without it any signing remote could plant a post under any actor's synthetic author (listed, indexed and interaction-routed as theirs), or claim another server's note URL first and capture the Likes, replies and Updates that later resolve through `ap_post_map`. The relationship gate being keyed on the signer is not enough: it decides *whether* to store, not *whose*. Redistributing another actor's note travels as `Announce`, so nothing legitimate is lost. `Undo`'s arms are actor-scoped by construction. **The original `Update` audit (2026-07-22) closed two gaps reachable by any signature-verified remote:** the cross-origin `Update{Person}` key-poison (now closed for same-host siblings too, above) and `Update{Note}` overwriting/tombstoning any mapped post, **including a local user's own pushed note**. Additionally, `Update{Note}` clears the identical audience + relationship gates as `Create` — factored into the shared `note_passes_ingest_gates` so the two paths can never drift; ungated, `Update` was a backdoor around both (the "unseen post" branch stores like a `Create`). Pinned by `update_note_cross_origin_is_dropped`, `update_note_unsolicited_is_dropped`, `update_note_same_origin_from_followed_actor_is_applied`, `update_person_cross_origin_does_not_poison_cache`, `update_person_same_host_sibling_does_not_poison_cache`, `update_person_self_identity_is_applied`, `create_note_attributed_to_another_actor_is_dropped`, `create_note_with_cross_origin_id_is_dropped`, and `update_note_unseen_attributed_to_another_actor_is_dropped`.
- **No configuration surface beyond the app:** hard-coded constants (body cap, rate limit, retry policy, dead-inbox threshold) + the deployment-derived domain; the user's choices are exactly the Bridges-page settings.

## Naming: the Fediverse rail

**Ruled 2026-09-27 — the Fediverse rail is `ActivityPub`, by [`atproto-pds-bridge.md`](atproto-pds-bridge.md) § Naming's rule: *name the layer the code speaks*.** The conversations rail and the feed classification are one network seen from two pages, and only one of them was named for it: `fauna_feed::SourceKind::ActivityPub` named the protocol while `fauna_conversations::Rail::Mastodon` / `TypedAddress::Mastodon` named one app. What the rail speaks is ActivityPub, not a Mastodon API: its address is a WebFinger `acct` (`user@host`), which every Fediverse server resolves; a direct message on it is an AS2 `Note` addressed to actors rather than to `Public` — plain ActivityStreams, no app-specific layer — and the only transport the nest can lend it is this doc's AP module (today the rail is a transport-less skeleton, `libs/fauna-conversations/src/backends/activitypub.rs`, and until 2026-10-03 a remote DM stopped at § Architecture's audience gate; the ingest that replaced the stub is [`../ui/conversations.md`](../ui/conversations.md) § Where logic lives → *The `Bridged` adapter*, ruling 3).    The lesson generalizes to every remaining item here: real-peer conformance is a **mechanism**, not pixels. A mainstream server's *rendering* needs a human eye; whether our JSON-LD parses, our links resolve, and our documents validate does not. Prefer a headless flow assertion — follow the link, parse the document, assert the schema — over deferring to the live check.
