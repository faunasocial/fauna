## Goal

A member makes a link to one of their files that a person **without Fauna** opens in an ordinary browser, sees every link they have made, and can kill any of them from their app. The link is time-limited, revocable, and needs no account on the receiving end.

## What a link is

A link points at **one file's bytes as they were when the link was made** — the manifest of the file's current version at mint time, never the path. Editing, renaming or moving the file afterwards does not change what the link serves. The link stops working when it expires, when its author revokes it, or when that version's bytes are no longer on the nest (retention is [`file-versions.md`](file-versions.md)'s; the first build adds **no** pin that keeps a version alive because a link names it — see § Non-goals).

Every link is a `public: true` token — anyone holding the link may open it. The restricted (`public: false`) variant stays refused end to end until a real audience design exists; no app surface sets or shows the flag. Owner of that ruling: the kind catalog's § Share. A link to a sealed file is still `public: true`; what differs is *how* it opens, the additive `key_in_fragment` field of § The private-file extension.

## Which files can be linked

**The rule: an app offers "Share a link" exactly where the nest will serve the result, and nowhere else.** Offering a control the nest refuses is the anti-pattern [`../ui/folders.md`](../ui/folders.md) § Audience already rules out for the audience picker; this page adopts the same rule.

**What the nest serves plaintext is a file in a `public`-audience folder, and only that.** The public route holds no content key, so a content-key-sealed manifest is refused at serve time (`403`, the authoritative gate — never relocated or weakened) and refused again at registration (`fauna.share.unsupported_encrypted_set`). Every file outside a `public`-audience folder rests sealed. So the first build's eligibility is one shared predicate over the file's folder — `audience == public` — and the affordance is simply absent on every other file. The two nest refusals stay the authority: an app that offers the control wrongly gets a refusal it renders in `error-message`, never a dead link. A sealed file becomes linkable only through the fragment-keyed design below, which widens the predicate to owner-only folders and never the `403`.

### The private-file extension — a fragment-keyed link; the nest stays blind (ratified 2026-09-25)

The feature most people will expect — "send someone a link to one of my private files" — **cannot be served plaintext on the plane as it stands**: the serve-side `403` on a sealed manifest stays, and the nest never holds a user's content key. The design pass of 2026-09-19 put one candidate to the user, a **per-link unsealed copy** resting on the nest behind an explicit confirm until the link dies, and **the user refused it (2026-09-25)**: it would be a new exception to the sealed-at-rest invariant, and there is to be none beyond the `public`-audience folder. What the user asked for instead, and what this section ratifies, is a link that keeps the nest blind: the file's bytes rest and travel sealed, and the **key rides the link's URL fragment**, which a browser never sends to any server. The shape was set aside once in the path-sealing design record ([`path-sealing.md`](path-sealing.md) § Sealed names & paths) and reopened by the user the same day; the ruling below is the answer. Until its build lands, the first build's eligibility (§ Where logic lives) stays `audience == public`.

**The link.** `https://<nest>/share/<token>#<key>`. The token is the same client-minted, signed, self-verifying `ShareToken` as a public link (the kind catalog's § Share) with one **additive** field, `key_in_fragment: true`, that tells the nest *how* this link opens — the existing `public` flag keeps saying *who* may open it (anyone holding the link). `<key>` is a fresh 32-byte random per-link secret, base64url, generated by the owner's client at create time and never sent anywhere: it exists in the URL the author copies and nowhere else. A fragment-keyed token carries an **empty** `filename` — the plaintext name would otherwise ride the URL path the nest sees in every request log; the name travels inside the envelope below.

**What the nest stores, and why revoking one link exposes nothing else.** Every sealed chunk is already encrypted under a per-chunk key derived from the folder's root and the chunk's own plaintext hash (`fauna_core::chunk_crypto`; the primitive is owned by [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 *At-rest blob keying* and [`../architecture/owner-key-material.md`](../architecture/owner-key-material.md) § Path A). A link therefore needs no re-upload and no second ciphertext: the owner's client derives **the per-chunk keys of exactly the chunks the link's manifest names**, packs them with the plaintext chunk hashes, the whole file's plaintext hash and the filename into a **key envelope**, seals the envelope under the link key (AEAD; the link key is used for nothing else), and registers the envelope with the link (`fauna.share.create` gains an additive `key_envelope` field; the `share_tokens` row an additive column). Per-chunk keys are a one-way derivation from the root, so an envelope reveals nothing about the root, nothing about any chunk it does not name, and nothing about a sibling link — and the nest, which never sees the link key, holds ciphertext chunks it already held plus an opaque blob. The one thing a chunk key does reveal is that same chunk wherever the folder's convergent scheme deduplicated it (a byte-identical chunk in another file of the same folder), which is the bytes the holder already has. The link names a version's manifest like every link (§ What a link is), so it pins nothing and dies with the version's bytes under [`file-versions.md`](file-versions.md)'s retention; the manifest's own hashes are sealed ([`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 *Sealed manifest hashes*), so the envelope carries the plaintext chunk hashes the viewer needs and the viewer never reads them off the manifest.

**What the nest serves — three things, never plaintext.** For a token whose signed content says `key_in_fragment`, `GET /share/<token>` answers a **viewer page** on a navigation request, and the viewer's own fetches get the manifest with the envelope and the ciphertext chunks by index — each an unauthenticated read gated exactly as the public arm is (signature, expiry, the registry's `410`, the succession gate, the legal-takedown `451`), and each served as content-addressed bytes the nest never opens. The **authoritative serve-side `403` on a sealed manifest is untouched**: the new arm is a separate branch taken only on a signed token that declares the fragment key, it never hands the sealed walk a key, and a sealed token without the declaration, or a declared token over a plaintext manifest, is still refused. The mint-side `unsupported_encrypted_set` refusal gains the mirror exemption: a declared token over a sealed manifest registers; a declared token over a plaintext manifest is refused (there is nothing to key). Owner: the kind catalog's § Share for the route and the refusals; this section for the arm's contract.

**The viewer is a browser page and needs no account.** It reads the fragment, fetches the manifest and envelope, opens the envelope with the link key, decrypts each chunk with its per-chunk key, verifies every chunk against its plaintext hash and the whole against the manifest's file hash (the integrity chain is the token's signature → the manifest hash → the manifest → the hashes; the envelope's AEAD tag is the link author's), and then offers the file. It is **part of the web SPA's build** (the same shared Rust decrypt, compiled to wasm; no second implementation), served by the nest under the same reserved-path rule and security headers as `/app/` ([`web-content-hosting.md`](web-content-hosting.md) § Same-origin security model → *The nest-served `/app/` and the central origin*: bundled by default; when the admin's web-app-origin choice is central, the same `302` — the browser carries a fragment across a redirect whose target names none, so the key survives the hop and still reaches no server). Four rules the viewer obeys, each load-bearing: **(1)** it makes no request that could carry the URL — no external resource, `Referrer-Policy: no-referrer`, a CSP that admits nothing but its own origin — so the fragment leaves the browser only if the person pastes it somewhere; **(2)** it **never renders the decrypted file as a document on the app origin** — that is the exact attack § Same-origin security model exists to rule out — so it offers a download of the reassembled bytes, plus an inline preview only for the media types a browser renders without executing anything (an image, audio or video via an object URL; plain text in a text element); an HTML, SVG-as-document or any other file is download-only; **(3)** it touches no identity slot and no account state — a signed-in owner opening their own link is treated exactly like a stranger; **(4)** it leaves the URL alone (no rewrite that would strip the key from the bar) — the link the author copied is the only key there is, and the person opening it may need to keep it. What an unfurler or a chat app that pre-fetches the URL gets is the viewer page with no fragment: a generic "a file shared with Fauna" title and nothing about the file, since the name is sealed in the envelope.

**The honest limits, stated to the author at create time.** Anyone holding the link opens the file until it expires or is revoked; a copy already downloaded stays with them (true of a public link too); a person who fetched the ciphertext and the envelope before a revoke can still open them afterwards, because revocation is the nest refusing to *serve*, never the key changing; and the link *is* the key — pasting it into a chat, a mail or a bug report hands the file to that channel's readers, and the person's browser history keeps it. The create surface says the first and the last of these plainly, in the one added element below; the shape of every other surface, gesture and ID is identical to a public link.

**Eligibility, and what stays out.** A fragment-keyed link can be made for a file whose chunk keys the app can derive: a **`public`-audience folder needs none** (the public arm serves it), and an **owner-only folder** the seat holds the root of is the private-link case. A **bound (`shared`-audience) folder's file is not linkable in the first private build**: the owner chose an audience of named members, a member re-sharing outward is the folder's audience question, not the link plane's, and a co-authored scope must not be opened by one member's gesture ([`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Readable classes, the own-actor-scopes rule) — widening this is a follow-on ruling for [`../ui/folders.md`](../ui/folders.md)'s audience model, not a predicate tweak. So the shared predicate becomes `share_link_eligible(folder) = audience == public || (unbound && the seat holds the owner root)`, and `mint_link` picks the arm off the same folder facts. The predicate is per **folder** because the file's at-rest shape is per folder too: every file the Media page records is a chunk manifest, whatever produced it ([`../ui/media.md`](../ui/media.md) § Encryption at rest → *One at-rest shape*, ruled 2026-10-06 — a per-file shape bit on the listing was weighed there and refused), so a folder's eligibility is every one of its files' eligibility.

## Flows

### Create

1. The user opens a file's detail surface on the Media page. When the file is eligible, the surface shows **Share a link**.
2. Activating it opens the create surface: the file's name, the expiry choice (§ Expiry), **Create link**, **Cancel**.
3. **Create link** runs the shared author function (§ Where logic lives): read the file's current version → mint and sign the token → seal the filename → register with `fauna.share.create`.
4. **The URL is revealed only after registration succeeds.** A token serves statelessly for a live author whether or not it is registered, and only a registered token can be revoked — so a URL shown before registration would be a link its author can never kill, which breaks the user-control invariant ([`../principles.md`](../principles.md) § The user always controls their data). On a failed registration the minted token is discarded, never displayed, never logged; the surface shows the error and stays open for a retry.
5. On success the surface shows the URL and a **Copy** control, and the link appears in the list.

Create and revoke need a reachable nest. They are **online-only** under the offline-mutation contract — not queued to the outbox, because a queued create would have to hold an unrevealed, unregistered token across restarts for no user benefit. The per-kind classification row lands with the build, in the contract's owner doc ([`../architecture/account-offline-mutation.md`](../architecture/account-offline-mutation.md)).

### List

A page-level **Shared links** control on the Media page opens the list of the caller's registered links, newest first (`fauna.share.list`). Each row shows the file name (unsealed client-side), when the link expires, and its state — **Active**, **Expired**, or **Revoked** — derived in shared Rust from `expires_at`, `revoked` and the clock. Expired and revoked rows stay listed (they are the user's record of what they handed out); the first build has no delete-from-list gesture. The list follows the cross-page three-state rule for wire-read lists ([`../ui/README.md`](../ui/README.md) § List pages: loading is not empty): loading, empty, populated off one `loaded` bit.

**Copy from the list re-derives the URL; it is never stored.** The nest keeps a link's token *id*, not the token. The token is a deterministic function of its fields (canonical encoding, Ed25519 signature), all of which the list row returns, so the shared function re-mints it and **verifies that its id equals the row's `token_id` before handing it out**; on any mismatch (a token minted by a future client with fields this one does not know) the row's Copy control is absent rather than producing a wrong link. Active rows only.

### Revoke

Each Active row carries **Revoke**, behind a single confirm (the file-delete confirm on the same page is the precedent; a revoke destroys nothing but the link). `fauna.share.revoke` flips the row; the link answers `410 Gone` from then on. There is no un-revoke — a new link is one gesture away.

## Expiry

The expiry is the link author's choice, made per link at create time: **1 day, 7 days (default), 30 days, 1 year.** The option list and the default are shared-Rust constants (the default is `fauna_core::share::DEFAULT_EXPIRY_SECS`). There is deliberately **no "never"**: a registry row is the only thing that makes a link revocable, so a link whose row is lost (a nest restored from an older backup) is bounded only by its expiry — an unbounded one would be permanent and unkillable.

## The filename rests sealed

The file's name is content (the paths-are-content ruling). The first production caller of `fauna.share.create` lands it **born sealed**, against the spec [`path-sealing.md`](path-sealing.md) § Sealed names & paths already ratified for this plane (salt = the token id, the author's root, a random nonce) — this page adds nothing to that spec. What the build owes it: an **additive** sealed-filename field on `ShareCreateRequest` and on `ShareRecord` in `libs/fauna-protocol/src/share.rs` (older peers ignore it; an older nest simply stores none), the nest writing it to `share_tokens.filename_sealed` and never resting the plaintext, and the list rendering seal-first through the shared label-render seam. **As built since 2026-10-01 the seal is required, not additive:** every registration carries it (fragment-keyed links included — the author's list has no other name to show), the nest refuses one without, and neither the record nor the table holds a plaintext name, so the list renders from the seal alone and omits a row this reader cannot open. The recipient-serving path is unchanged and out of scope: the name a browser receives comes from the URL-presented signed token, transiently, at serve time.

## Where logic lives

Shared Rust, all of it; apps render state and forward gestures (priority #2).

- **Author seam — a new `libs/fauna-client-share` crate** (UniFFI + wasm, like its `fauna-client-*` siblings; not `fauna-client-share-host`, which is the unrelated peer-to-peer share plane). `mint_link` (mint + sign + seal the name, the URL released only by `MintedLink::reveal` against the registration's reply), `link_rows`, `link_url(record) -> Option<String>` (the verified re-derivation above), and `ShareClient` over the three kinds. It signs with the account key the app session already holds; **no per-app code ever touches `ShareToken`.**
- **Eligibility** — one predicate, `share_link_eligible(folder)`, in the same crate, consumed by the Media machine so the control's presence is state, not per-app logic. First build: `audience == public`. The private-link build widens it to `|| (unbound && the seat holds the owner root)` (§ The private-file extension) and `mint_link` picks the public or the fragment-keyed arm off the same facts — the per-chunk-key derivation and the envelope seal live in `fauna-core` beside `chunk_crypto` (one new entry point exposing the derived per-chunk key, and its decrypt twin), so the viewer's wasm and the author's crate share them.
- **Machine** — the create surface's step state, the list's `loaded` bit and row states, and error mapping live in the Media page's shared machine alongside the detail surface it already drives.
- **Nest** — no new behavior beyond storing the sealed filename.

## Windows Explorer's Share leaf

**The leaf hands off to the app; the sync agent never mints a link.** A token must be signed by the account key, and the per-user agent is a seedless process by design ([`../architecture/apps/sync-agent-credentials.md`](../architecture/apps/sync-agent-credentials.md)) — it holds a device-scoped renewal credential, not the identity. So "the agent calls the shared author function" is not available, and giving the agent the account key to make it available would be the wrong trade. Instead:

- **On a file:** the leaf is present only when the file is eligible (the agent knows the folder's audience from the nest folder row it already syncs). Activating it brings the Fauna app forward on that file's detail surface with the create surface open — the same flow, the same expiry choice, as inside the app.
- **On a tracked folder:** a share link names one file, so it has no meaning here. The leaf stays, per the 2026-07-16 user decision that Share on a folder means sharing *the folder*: it brings the app forward on the Folders page with that folder's member-share picker open ([`../ui/folders.md`](../ui/folders.md) § Sharing). **"The folder" is a bound folder's own root** (2026-09-30, the build): a sub-folder inside it offers no Share, because it is not a unit the member-share picker can share, and opening its containing folder's picker instead would silently widen what the user right-clicked.

The hand-off mechanism — how the shell extension's request becomes an app activation targeting a surface — is [`../architecture/apps/windows.md`](../architecture/apps/windows.md) § Shell Extension → *The Share hand-off*.

## Build order

Shared Rust + wire field + nest writer first, then **tui** (the lead app) with the e2e journey — create a link on a `public`-folder file, fetch it over plain HTTP as an unauthenticated client, revoke it, observe `410` — then the other six in the batched trickle-down, Windows carrying the Explorer hand-off. The first implementation also lands the user guide page and the feature's catalog page. **The private-link build follows**, in the same order: the shared-Rust key entry points, the token field, the envelope on the wire and in the registry, and the nest's fragment-keyed arm first (one nest-area row); then the **viewer page in the web SPA** (a browser page, so the web area leads it — the carve-out for a journey tui cannot host); then tui's create surface gains the sealed arm and the key notice, and the other six inherit both through the same trickle-down. Its e2e journey: create a link on an owner-only sealed file, fetch `GET /share/<token>` unauthenticated and assert the body is the viewer page and that no plaintext byte of the file is in any response, open the viewer with the fragment in a real browser and assert the download equals the file, revoke, observe `410` on every arm.

## Non-goals (first build)

Restricted links (an audience on the token); links to folders or to several files; a link that follows the file's newest version; pinning a version against retention because a link names it (if links to superseded versions dying early proves to bite, the pin is a nest-side retention rule to design with [`file-versions.md`](file-versions.md)'s owner, not an app feature); deleting rows from the list; download counts or access logs. For the private-link build additionally: a link to a file in a bound (`shared`-audience) folder (§ The private-file extension, *Eligibility*); a viewer that renders documents inline; password-protected or otherwise second-factor links (the fragment is the whole secret); and a viewer served from anywhere other than the nest's own reserved path or the central origin's.
