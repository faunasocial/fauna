## Goal

A user has one canonical address (`bob@<our-domain>` → their actor) and an unbounded number of alternative addresses that route to the same mailbox: shop-by-shop disposable addresses (`bob-amazon-AbCdEf@…`), purpose-tagged wildcards (`bob-newsletter@…`, `bob-receipts@…` matching `bob-*@…`), `+suffix` filter aliases (`bob+work@…`). The deployment may also have one admin-designated catch-all (`*@<our-domain>`) for typo recovery on small deployments. Each alias has its own controls — spam-threshold override, disable-without-delete, rate-cap, label — so the user can shut off the "Amazon" alias for one offender without losing the address, or set a higher spam threshold on a `+newsletter` alias that hits aggressive classifiers.

**Bar: parity with Fastmail's "Masked Email" + Gmail's `+suffix` + Apple "Hide My Email" + cPanel-style catch-all** — all in one UX, all per-account-controlled (catch-all admin-controlled), all backed by a single resolver running at RCPT TO time before mail enters the policy stack.

**Symmetric design with mail-forwarding.** Both are per-account address-and-routing UXes living on the mail-settings page family (sibling `mail-*` sub-pages). The user understands "this is where I configure where mail comes in (aliases) and where it goes out (forwarding)." Same UX shape: section header, indexed list, add / edit / revoke / delete buttons, per-row controls.

## Alias kinds

| Kind | Pattern | Tier | Default state |
|---|---|---|---|
| **Exact** | `bob@<our-domain>` | user (Tier 3) | the canonical address each user gets at signup |
| **+suffix sub-addressing** | `bob+<anything>@<our-domain>` matches `bob@`'s actor | user (Tier 3); admin-toggleable deployment-wide | on by default (`mail.inbound.subaddressing_enabled = true`) |
| **Wildcard prefix** | `bob-<anything>@<our-domain>` matches `bob@`'s actor (one wildcard pattern per actor, the user picks the prefix) | user (Tier 3); admin-toggleable | on by default (`mail.inbound.wildcard_prefix_enabled = true`) |
| **Catch-all** | `*@<our-domain>` routes to a designated actor | admin (Tier 2) | off by default (per-domain `mail_domains.catch_all_actor_id` NULL — `mail-multidomain.md` § Per-domain catch-all) |
| **Disposable** | `bob-temp-AbCdEf@<our-domain>` — `AbCdEf` is a 6-character base32 random token; one-or-N uses, time-bounded | user (Tier 3) | none generated by default; user mints on demand |
| **List** | `<list-name>@<our-domain>` — the user's chosen list address; outbound-only (inbound to this address rejects); see `mail-mass-mailing.md` § List as an alias kind | user (Tier 3) | none created by default; user creates lists explicitly |
| **Forwarder** | `info@<our-domain>` → an **external** address; no local mailbox (forward-only) | admin (Tier 2) | none by default; admin creates explicitly; see § Kind 7 + `mail-forwarding.md` § Admin external forwarders |

### Kind 1 — Exact

The canonical address — **the user's registration handle is their email address**, with no separate alias step. It is created when the user **enables mail** (the nest, in `fauna.bridges.provision_recipient_mls_pubkey`, idempotently writes the `<handle-localpart>@<domain>` exact alias mapping to the enabling actor). The address domain is the handle's own domain when the nest serves mail for it, otherwise the primary mail domain (the canonical `<our-domain>`). Enable-time rather than literally signup-time because the mail domain must exist first — on a fresh nest the admin registers the mail domain before any user enables mail; the enable path is the first moment both the handle and a servable domain are known. The creation never clobbers a `(local_domain, pattern)` another actor already owns. The **admin** (box claimer) never travels `provision_recipient_mls_pubkey` — it claims via `claim_admin` (which only sets the bare handle) and toggles mail with `set_mail_enabled` — so the nest writes the admin's own canonical alias from the mail-enable / boot safety net (`ensure_admin_recipient_aliases`, the companion to the primary-mail-domain net `ensure_primary_mail_domain`) once a servable domain exists; same row and idempotency as the per-user path, so the admin's `<handle>@<domain>` resolves for AUTH login (`validate_recipient`, the exact-only "a login must resolve an exact canonical identity" resolver below) exactly like a regular user's. The user can add additional exact aliases (`bob.smith@`, `bob.s@`, `b.smith@`) up to a per-account cap (`mail.account.exact_aliases_max`, Tier 2, default 20 — caps abuse of the namespace by a single user). Two users **cannot** claim the same exact alias on the same local domain (uniqueness constraint on `(local_domain, pattern)` where `kind = exact`).

Exact aliases have no resolution-time stamping — the message routes to the actor with no special headers added. From the user's perspective, all their exact aliases are interchangeable; from a downstream sender's perspective, they see the alias they sent to.

### Kind 2 — +suffix sub-addressing (RFC 5233)

`bob+anything@<our-domain>` matches `bob@`'s actor (or any of `bob`'s exact aliases — `bob.smith+receipts@` matches if `bob.smith@` is one of bob's exact aliases). On match, the suffix is **preserved in delivery metadata** via two mechanisms:

- An `X-Fauna-Address-Suffix: anything` header stamped by the **MTA at delivery** (onto the sealed local copy + the recipient's filter-rule context) before the message hits the user's filter rules.
- The full original `RCPT TO` address is preserved in the message envelope as delivered (the IMAP `\Recent` and the per-message envelope metadata).

The suffix lets the user filter incoming mail by purpose without registering each address (`my filter rules treat anything with +newsletters as low-priority`). This is the lowest-friction alias — no pre-registration, infinite suffix space, just type the address with the suffix and it works.

The character class for `<anything>` is RFC 5233-permissive but Fauna-restricted: `[A-Za-z0-9._-]+`, length 1–64. Suffixes with characters outside this set get rejected at RCPT TO with `550 5.1.1 Invalid sub-address` (the strict floor protects against pathological suffixes that some MUA / search-index pairs interpret strangely).

Admin can disable sub-addressing deployment-wide via `mail.inbound.subaddressing_enabled = false` (Tier 2); above-the-knob mail to `bob+x@` falls through to "no match" (eventually catch-all or 550). The long-term question ratifies keeping the default at `true` — sub-addressing is a Gmail-since-2004 expectation, off would surprise.

### Kind 3 — Wildcard prefix

The user picks a wildcard pattern on their `mail-aliases` page — default `<handle>-*@<our-domain>`, customizable to anything matching `^<one-or-more-chars>-\*@<our-domain>$`. One pattern per actor (multiple patterns would invite name-space-grabbing fights between users). Any inbound mail to an address matching the pattern routes to the actor; the matched suffix is stamped as `X-Fauna-Address-Wildcard-Suffix: <matched-portion>`.

Example: bob's pattern is `bob-*@`. Mail to `bob-amazon@` routes to bob with `X-Fauna-Address-Wildcard-Suffix: amazon`; mail to `bob-newsletter@` routes with suffix `newsletter`; mail to `bob-stripe-receipts@` routes with suffix `stripe-receipts`.

**Conflict resolution at creation time:** when bob tries to claim `bob-*`, nest validates the prefix against:

- **Existing exact aliases** owned by another user — if alice has `bob-foo@` as an exact alias, bob's `bob-*` cannot proceed (`409 conflicts_with_existing_alias`). Exact wins over wildcard at resolution time; the conflict check at creation time enforces this invariant.
- **Existing wildcard prefixes** owned by another user — if alice has `bob-*` already, bob's `bob-*` cannot proceed.
- **Reserved local-parts** — `bob-*` would match `bob-postmaster@`, which is reserved; the conflict check at creation time refuses (`409 reserved_local_part_in_wildcard`).

On match at RCPT TO time, the match is logged in the alias_hits audit log (per § Storage) — `alias_id` (the wildcard alias's UUID) + `matched_address` (`bob-amazon@example.com`) + `sender_domain` + `received_at`. The hit log lets the user see "which addresses am I receiving on?" in their training-history-like UI.

Admin can disable wildcard prefix deployment-wide via `mail.inbound.wildcard_prefix_enabled = false`; default `true`.

### Kind 4 — Catch-all

`*@<our-domain>` routes every inbound address that doesn't match a more-specific kind to a designated actor. **Admin-tier only**, because it routes every other user's typos and any address not claimed by anyone:

- The designation is the **per-domain `mail_domains.catch_all_actor_id` column** — storage + designation are owned by `mail-multidomain.md` § Per-domain catch-all (set at `add_local_domain` time, or later via the Admin-class `fauna.bridges.set_catch_all_actor`). NULL (the default) means no catch-all for that domain; unmatched addresses reject `550 5.1.1 User unknown`.
- Admin can designate themselves or any other actor (the designated actor's consent is implicit — the admin can already see their mail, so this is not an additional privacy violation; the consent UX is the admin asking them in-person before they toggle).
- One catch-all per local domain max — structural, since the designation is a single column on the domain row.

On match at RCPT TO, the message is stamped with `X-Fauna-Address-Catchall: true` plus `X-Fauna-Address-Catchall-Domain: <domain>` (the shared `HEADER_CATCHALL` / `HEADER_CATCHALL_DOMAIN` consts, `fauna_mail::aliases`), and the full original `RCPT TO` is preserved in the message envelope.

**User-tier catch-all is forbidden.** A user cannot claim `*@`. The product invariant + the cross-user-mail-trapping concern combine — the deployment-wide catch-all is an admin choice, not a user choice. The admin designates a domain's catch-all actor from the **`admin-dns` per-domain row** (`admin-dns-domain-catch-all-select` — `mail-multidomain.md` § Per-domain catch-all / `dns-management.md` § Detail page), per-domain, because it is a 1-per-domain setting alongside the domain's other per-domain knobs (not a section on `admin-aliases`, which hosts the N-per-domain external forwarders — `admin.md` § 4); it is not an option in the user `mail-aliases` add-sheet kind-picker.

### Kind 5 — Disposable

The user mints a disposable alias on demand: in their client they click `mail-aliases-generate-disposable-button` → client calls `fauna.bridges.generate_disposable_alias(ttl_days, uses_remaining, label?)` → nest generates a 6-character base32 token (case-insensitive; collision-checked against existing disposable aliases), constructs the address `<handle>-temp-<token>@<our-domain>`, returns it → client copies it to the clipboard with a toast "Disposable address copied: `bob-temp-AbCdEf@<our-domain>` (expires in 30 days, 1 use)".

Defaults:

| Knob | Default | Notes |
|---|---|---|
| TTL | 30 d | `mail.account.disposable_default_ttl_days` (Tier 3, per-user) |
| Uses | 1 | `mail.account.disposable_default_uses` (Tier 3, per-user) — "1" means first inbound message routes, subsequent reject; the mint param "0" means unlimited until TTL, **stored as a `NULL` `uses_remaining`** (see § Storage), never a literal `0` |
| Per-day generation cap | 50 | `mail.account.disposable_generate_per_day` (Tier 3, per-user; admin ceiling `mail.outbound.disposable_generate_max_per_day`, Tier 2, default 200) |

The TTL is the **outer bound**: a disposable alias expires when `(now - created_at) > ttl_days` OR `uses_remaining == 0`, whichever comes first. Post-expiry mail to the address rejects `550 5.1.1 Address expired` (sender sees a clean error; user is not notified — they minted it disposable).

The token is **opaque** in the address: it doesn't leak the user's identity (`bob-temp-AbCdEf@` reveals `bob` and `temp`, but not the user's underlying handle if the user's handle is different from their wildcard prefix — by default they're the same, but the user can customize). The `temp-` literal in the local-part is a tag for downstream filtering (lets the recipient's MUA spot disposables at a glance).

On match at RCPT TO:

1. Resolver decodes the token via `base32 decode` against the disposable-alias table.
2. Verifies the alias is alive: `now - created_at <= ttl_days` **AND** (`uses_remaining IS NULL` (unlimited) **OR** `uses_remaining > 0`). The unlimited sentinel is `NULL`, never `0` — a finite alias decrements toward `0`, and `0` is exhausted/dead. (This is the canonical reading of the "0 = unlimited" mint param: it stores `NULL`.)
3. Decrements `uses_remaining` (atomic at the DB level) — only for finite aliases (`uses_remaining` non-`NULL`); an unlimited alias is a no-op decrement.
4. Routes to the actor; stamps `X-Fauna-Address-Disposable: AbCdEf` header.
5. Logs the hit in `alias_hits`.

The token is **not** stamped on the message body (no message-body trace of the disposable address) — stamping it would leak the disposable to body-scanning recipients and defeat the "address is disposable, don't tell the sender what other addresses I have" property.

### Kind 7 — Forwarder (external alias)

An **admin-configured** address on a local domain that has **no local mailbox** and instead forwards every inbound message to an **external** address — the cPanel "forwarders" / "external alias" shape (`info@<our-domain>` → `yourname@example.com`). This is the home for `mail-forwarding.md` § Admin external forwarders; that doc owns the forward *dispatch* (SRS / loop / rate-cap / NDR), this doc owns the *resolution* (it is, mechanically, an alias whose target is external rather than a local actor).

- **Tier** — admin (Tier 2). Created/listed/deleted via Admin-class RPCs (§ Wire shapes), **not** the user alias CRUD. The admin manages forwarders from the **`admin-aliases` page** (`admin.md` § 4 — the admin-tier alias surface). Forwarder rows are **excluded from `list_account_aliases`** (which is owner-scoped to a user's personal aliases) so an admin's forwarders never surface as the admin's personal aliases — the same separation concern that keeps the catch-all out of the user surface (§ Storage), resolved here by surface (Admin RPCs + list filter) rather than by a separate table, so the **single** RCPT-TO resolver still handles all address resolution.
- **Storage** — an `account_aliases` row with `kind = 'forwarder'`, `pattern` = the local-part, and the new `forward_target` column = the external destination (NULL for every non-forwarder kind). `actor_id` is the **managing admin's** actor — the accountable principal for the forward (SRS attribution, the forward rate-cap, and the bounce recipient per `mail-forwarding.md` § NDR routing), not a delivery target.
- **No local delivery** — a forwarder match yields a *forward*, not a mailbox write; it is `redirect`-shaped (no local copy is kept). Resolution returns the external destination + the managing admin actor; the MTA hands it to the forward dispatch.
- **Validation at create time** — `forward_target` is checked with the shared `fauna_mail::validate_forward_target` (RFC 5321 syntactic + **must not be a domain we host**, `mail-forwarding.md:244` — a forwarder to a local domain is a same-deployment alias, not a forward). `pattern` must be on a `local_domain`, must not be a reserved local-part (§ Reserved local-parts), and must not collide with an existing exact alias or forwarder on `(local_domain, pattern)`.
- **Plaintext at rest, uniformly** — like every `account_aliases` row, a forwarder is envelope/routing metadata, not user content (§ Storage; `encryption-at-rest.md`). The `forward_target` is admin/deployment routing config (the same class as the catch-all designation), and rests at the same plaintext routing-metadata floor as a *user's* `forward_all_to` — which is likewise plaintext today, not yet sealed; sealing user forward config (wrapped to the MTA bridge service-user pubkey, for separate-bridge deployments) is a deferred, additive upgrade (`mail-forwarding.md` § Where the forward config lives at rest, tracked internally as N1b).

## Resolution order at RCPT TO time

At the MTA's RCPT TO stage (before the policy stack — connection rate, DNSBL, etc.), the resolver runs in fixed order:

1. **Exact match** in `account_aliases(kind=exact)` where `pattern == LOWER(rcpt_to)` and `local_domain == LOWER(rcpt_domain)` → route to actor, no header stamping.
2. **Forwarder match** in `account_aliases(kind=forwarder)` on the same `(local_domain, pattern)` exact key → **forward** (no local delivery) to the row's `forward_target`, attributed to the row's managing-admin `actor_id`; the MTA hands `{forward_target, forwarder_actor_id}` to the forward dispatch (`mail-forwarding.md`). No `X-Fauna-Address-*` stamp (there is no local recipient whose filter rules would read it). A given `(local_domain, pattern)` is either an exact mailbox or a forwarder, never both (the `(local_domain, pattern, kind)` uniqueness + the create-time collision check enforce it). The same exact key then carries the **list match**: a `kind=list` row (checked when exact and forwarder both missed) → reject `550 5.1.1 List submissions not accepted at this address`, because a list only sends (`mail-mass-mailing.md` § Pattern) — so no later step (a wildcard, the role-address route, catch-all) may deliver list-address mail to a mailbox.
3. **+suffix strip + exact match** on stripped local-part (`LOWER(rcpt_to)` split on `+`, retry exact match on the prefix) → route to actor, stamp `X-Fauna-Address-Suffix: <stripped-suffix>`. Only fires if `mail.inbound.subaddressing_enabled = true`.
4. **Disposable-alias match** — if the local-part matches `^<handle>-temp-<6-base32-chars>$`, decode the token, look up in `account_aliases(kind=disposable)` → if alive (not expired, uses_remaining > 0), decrement, route, stamp `X-Fauna-Address-Disposable: <token>`. If decoded but expired/exhausted, reject `550 5.1.1 Address expired`.
5. **Wildcard prefix match** in `account_aliases(kind=wildcard_prefix)` ordered by pattern length (longer prefix wins — `bob-newsletter-*` would win over `bob-*` if both existed for the same user, though we enforce one wildcard per actor) → route to actor, stamp `X-Fauna-Address-Wildcard-Suffix: <matched-portion>`. Only fires if `mail.inbound.wildcard_prefix_enabled = true`.
6. **Role-address route** — if the local-part is a reserved role name (`classify_role_address`) and nothing above matched, route to the role-address **target**; which actor that is (per-domain override vs the deployment admin; the always-processor `tlsrpt`/`dmarc-report` special case) is owned by `smtp-server.md` § abuse@/postmaster@ routing + `mail-multidomain.md` § Per-domain role-address routing. The **never-reject** route: a malformed/absent override degrades to admin, and a reserved name with no admin claimed `451`s (RPC error), never a hard `550`. No `X-Fauna-Address-*` stamp, no `alias_hits` row (there is no stored alias — the route is the RFC default); the resolve carries `is_role_address = true` so the MTA bypasses per-mailbox quota + greylisting on delivery. (Steps 1–5 above can't actually match a reserved name: user-tier exact/wildcard/disposable creation refuses reserved local-parts — § Reserved local-parts — so this step fires for *every* reserved-name RCPT in practice, ahead of catch-all.)
7. **Catch-all** — if the RCPT domain's `mail_domains.catch_all_actor_id` is set (`mail-multidomain.md` § Per-domain catch-all), route to the designated actor, stamp `X-Fauna-Address-Catchall: true` + `X-Fauna-Address-Catchall-Domain: <domain>`.
8. **No match** → reject `550 5.1.1 User unknown`. Standard per `smtp-server.md`.

The order is **fixed** — no admin override. Reordering would break user expectations:

- Exact wins over wildcard so a deliberately registered address takes precedence over a pattern match. (A user who registered `bob-corp@` as an exact alias expects it to land with no wildcard-suffix-stamp.)
- Exact, forwarder and list share the exact-key tier (a registered local mailbox is checked first, then the admin forwarder table, then the list table); they are mutually exclusive on one address, so the within-tier order is moot in practice.
- +suffix wins over disposable so `bob+work@` doesn't accidentally pattern-match the disposable shape.
- Wildcard wins over catch-all so a user's claimed pattern takes precedence over the deployment-wide catch-all.
- **Role-address wins over catch-all** so role-address mail (`postmaster@`/`abuse@`) reaches the admin, not a non-admin catch-all actor — the never-reject + quota/greylist-bypass guarantees of `smtp-server.md` § abuse@/postmaster@ routing would be defeated if catch-all swallowed it first.

> **Role-address routing lives *inside* this single resolver (step 6), on alias-miss — not as a separate pre-resolver stage.** Both the AUTH-time `validate_recipient` and its RCPT-TO superset `resolve_recipient` classify the reserved local-part after the alias lookups miss, carrying `is_role_address`; target selection differs between them and is owned by `smtp-server.md` § abuse@/postmaster@ routing (with `mail-multidomain.md` § Per-domain role-address routing owning the override storage). Earlier prose in this doc that framed role routing as a "step 0 implicit" stage *before* the resolver was drift — corrected here and in §§ Reserved local-parts / Don't-do-these.

The resolver's per-RCPT-TO cost is bounded: exact lookup is one index hit; +suffix is one substring split + one index hit; disposable is one regex match + one index hit; wildcard is one prefix scan (per-user, so at most one row to check); catch-all is a column read on the already-loaded `mail_domains` row. Total per-RCPT-TO < 1 ms with the indexes per § Storage.

## Per-alias controls

Every kind except exact carries the four controls (exact aliases inherit the actor's defaults; their config is at the actor level via `mail.account.*`):

### Spam-threshold override

`spam_threshold_override` (nullable) — per-alias override of the per-account `mail.account.spam_threshold_override` (which itself overrides `mail.inbound.max_score_before_spam_folder`). A `+newsletter` alias may set a higher threshold (more lenient — newsletters trip aggressive classifiers); a `+banking` alias may set lower (more aggressive — phishing impersonating banks is a real threat). Resolution at delivery time: per-alias override > per-account override > admin-tier default.

**Where the three tiers collapse into one number: at DELIVERY, nest-side, and the resolved value then rides WITH the message (ruled 2026-08-17).** "At delivery time" above is load-bearing and decides the whole shape, because the disposition is *applied* somewhere else entirely: the routing decision is taken at **MDA SELECT-time scoring** (`mail-spam.md` § Routing decision), per session, long after the RCPT that alone knew which alias the message arrived through. Two readings were on the table when this was ruled; only one survives the sentence above:

- **RULED — nest folds alias > account > default at ingest into a single per-message threshold, stamped into the message as an `X-Fauna-*` delivery-stamp header** alongside the `X-Fauna-Address-*` stamps the same resolve already emits. It needs no new plane: the resolver already returns both the headers to stamp and the per-alias `control_overrides` from one RCPT-time call, the stamps are prepended **before** the message is sealed (so they are inside the sealed body and reach the authenticated agent that unwraps it), and sender-forged `X-Fauna-*` headers are already stripped before the genuine ones are prepended — so the channel is spoof-safe by construction rather than by a new check. A consequence to accept deliberately: the number is **frozen at delivery**, so changing an override does not re-file mail already delivered. That is what "at delivery time" *means*, and it is the desirable reading — a threshold change that silently re-sorted old mail would be the surprising one.
- **REJECTED — the MDA re-resolving the chain per message.** It contradicts "at delivery time"; it would require shipping alias rows (and the per-account tier) to an IMAP session that has no other reason to hold them, widening what that session knows about the user's alias taxonomy; and it re-derives per SELECT what one RCPT already knew.

⚠ **The scorer's session-level early exit is wrong under per-message thresholds — DELETED 2026-08-18.** `internal/mda/imap/spam_score.go`'s `if policy.SpamFolderThreshold == 0 { return }` skipped the whole INBOX when the *session* threshold was disabled, which under per-message thresholds silently skips exactly the messages an override was set for. The rule it encodes stands and is now implemented: the per-message value is the one consulted, with the session policy as fallback — never an extra branch beside it — and a resolved `0` means "not Junk-routable" for **that message**, decided per message. Pinned by `TestScoreSelectedInboxSpamFolderDisabledHonoursAPerMessageStamp` (§ Implementation status today).

### Disable

`disabled` (bool) — set true to reject mail to the alias with `550 5.1.1 Address disabled` while preserving the alias row + audit log. Useful for "shut off this alias for one offender without losing the address" — the user can re-enable later (via `enable_account_alias`, the reverse of `revoke`; **both `revoke` and `enable` must exist** — disable without re-enable is a client-causable unrecoverable state, `principles.md` § Client-recoverable nest state), the alias_hits audit shows what came in before. Distinct from delete (which removes the row entirely; deleted addresses 550 with `User unknown` instead of `Address disabled`).

**The canonical alias is protected.** The `<handle>@<domain>` exact alias written at mail-enable (§ Kind 1) is the user's primary mailbox **and** their AUTH-login identity (`validate_recipient`) **and** the dependency for disposable mints (`:565`). It must always be alive **and keep its address**: `revoke_account_alias` and `delete_account_alias` **reject it** with `fauna.bridges.canonical_alias_protected`, and `update_account_alias` **rejects a pattern (localpart) change** to it with the same code — renaming the canonical would strand AUTH login, the same unrecoverable class as disabling it (editing its label / spam-threshold / rate-cap stays allowed; only the localpart is frozen). `list_account_aliases` flags the canonical row `is_canonical = true` (computed from the runtime mail domain — the same resolution the guards use — never stored), so apps render the canonical row **read-only** (no disable / edit / revoke / delete; marked as the primary address) — § Aliases UX — making the protection visible, not just an error on attempt. (This closes the live-found disable-trap where disabling `<handle>@<domain>` stranded all inbound mail with no client-side recovery.)

### Per-alias rate-cap

`rate_limit_per_hour` (nullable integer) — over-quota mail rejects with `451 4.7.0 Rate limit exceeded` (tempfail; legitimate senders retry; if the cap is genuinely permanent, the user disables instead). Default null = unlimited.

`rate_limit_per_day` (nullable integer) — same semantics over 24 h window.

Disposable aliases have a hard default `rate_limit_per_day = 100` (independent of the per-hour cap) — protects against a sender enumeration / spam-blast on a disposable address discovered in the wild.

**The cap is enforced nest-side, inside `resolve_recipient` (2026-08-17).** The count is a windowed read of the alias's own `alias_hits` rows (`received_at` within the trailing hour / 24 h, over `idx_alias_hits_alias_time`), taken during the RCPT-time resolve the MTA already round-trips for every recipient; over quota answers `Reject { 451 }`, which the bridge's existing resolver-reject mapping renders as `451 4.7.0 Rate limit exceeded`. Three consequences worth stating, because they are why this beats the bridge-local bucket this line specified before it: the count is **durable** (a bridge restart cannot reset a user's cap, where an in-process bucket would); **all three RCPT call sites** — inbound MX and both submission paths — resolve through that one function, so there is no second place to keep in step; and it costs **no extra round trip and no new wire field** (`control_overrides` still rides to the bridge for the spam-threshold half, whose consumer is a different stage — § Implementation status today). An alias with neither cap set pays no query at all.

**The gate runs ahead of the disposable decrement and ahead of the hit log**, so a tempfailed message consumes no `uses_remaining` and writes no `alias_hits` row. The second half is load-bearing: `alias_hits` counts *accepted deliveries*, so a sender retrying a tempfail cannot re-arm the window that is refusing them — were the rejected attempt logged, a capped alias could never drain.

A `0` cap therefore blocks every message. That is deliberate and reachable (the doors accept `0`, refusing only a negative): it is the **tempfail pause** — senders retry and get through once the user raises it — as against `disabled`'s permanent `550 5.1.1 Address disabled`.

*Second consumer, deliberately left uniform:* the same resolver serves the **in-domain partition** of both first-party doors — `submit_outbound` (`bridge_routing_handlers.rs`) and `fauna.email.send` (`email_handlers.rs`), a local client sending to a local address — where **any** resolver `Reject` drops the recipient out of local delivery and onto the outbound queue, i.e. the message MX-relays to our own perimeter and meets the same verdict there, and the sender gets the standard DSN the MTA already generates rather than a bare RPC error code. That is the pre-existing shape for `disabled`/expired, not something the rate cap introduced, and the cap is honoured either way (never delivered while over quota; a retry lands once the window drains). Making that seam short-circuit locally is a separate change that must move **every** reject reason together and both doors with them.

**"Any reject" means all five, the non-existent address included (ruled 2026-08-23).** The reasons are `451` rate-capped, `550 Address disabled`, `550 Address expired`, `550 Invalid sub-address`, and `550 User unknown` — that last one being an address this deployment simply has no alias for. An earlier wording of the paragraph above enumerated only the first three, which read as though a *non-existent* local address were an unruled case; it is not, and it is not a distinct one either. The objection it invites — that queuing `nobody@our-own-domain` for remote delivery hands a message for our own domain to the outside — applies **identically** to `disabled`/expired/capped, all of which were accepted here on the same reasoning: the MX the message is relayed to is the deployment's own perimeter, which re-decides with this very resolver; the submitting client is authenticated and already under the per-hour/per-day submission ceiling, so the arm opens no relay and no enumeration oracle; and the bounce a real MTA emits is more use to the sender than a counter. A future change may still make the seam short-circuit locally — the argument for it is latency and one fewer network hop for the plaintext, not correctness — but it moves all five reasons at both doors, per the paragraph above.

**The doors refuse a negative cap (2026-08-17).** `fauna.bridges.aliases.create` and `.update` answer `fauna.protocol.malformed` on a negative `rate_limit_per_hour` / `rate_limit_per_day` — a negative is meaningless under the semantics above (`None` is how "unlimited" is expressed), and the client-side parse below is not what makes the check unnecessary: an app older than that parser is a supported peer (`../architecture/version-compatibility.md`). One `validate_alias_controls` over the shared `AliasControls` bundle serves both doors so they cannot drift. `0` stays valid — the refusal is `< 0`, never `< 1`, the same `0`-is-meaningful boundary `value-formatting.md` § Tier cap validation keeps. This landed **ahead of** the enforcement gate on purpose (hours ahead, the same day), so the gate above never has to defend against a negative already sitting in the column — which is why `rate_cap_exceeded` compares against the stored value directly and treats no cap value as untrusted.

**Where the override-input parse lives (shared Rust).** The add-sheet's two optional numeric overrides are parsed through the shared validator family — `fauna_core::format::parse_count` for `spam_threshold_override` (`u32`) and `fauna_core::format::parse_count_i64` for `rate_limit_per_hour` (the signed-`i64` column, parsed as a non-negative cap) — one source of truth, no per-app hand-rolling. An empty/invalid entry parses to `None` = "no override" (it does **not** fall back to a prior value, unlike the admin-mail knobs). See `value-formatting.md` § Mail-knob validation.

### Label

`label` (free text, max 64 chars, UTF-8) — UI tag rendered in the client's mail-detail "Delivered to: `bob-amazon-AbCdEf@…` [`Amazon - Kindle order receipts`]" surface. Lets the user filter by alias-purpose without exposing the alias-system internals to message-body scanners.

Empty label is fine; the UI falls back to the alias-kind + pattern.

## Bulk import (`fauna.bridges.import_account_aliases`, User)

Bulk-creates **exact** aliases from a list of full addresses (one per `lines`
entry). This is the **recipient-whitelist import path** — a user migrating a
unique-address-per-service allowlist (postfix/dovecot/sieve) pastes their ~100
approved addresses in one shot instead of adding them one dialog at a time
(design ratified 2026-07-01; tracked internally).

Best-effort per line — each line yields an `ImportAliasOutcome`
(`created` / `skipped_duplicate` / `invalid` + `reason`); a malformed,
over-cap, or duplicate line is *reported*, never aborting the batch, so one
typo can't block the other 99. **Idempotent:** re-importing an existing
address is `skipped_duplicate` (safe to re-paste). Blank lines are trimmed and
produce no outcome.

**App UI (all 7 apps).** An "Import addresses" button
(`mail-aliases-import-button`) on the `mail-aliases` page opens a paste sheet
(`mail-aliases-import-sheet`): a one-address-per-line textarea
(`mail-aliases-import-textarea`) → submit (`mail-aliases-import-submit-button`)
→ a per-line result summary (`mail-aliases-import-result`, rendered as
`N created · M already existed · K invalid`, with the reason for each invalid
line). Driven by the shared `MailAliasesMachine` `Import` action (no per-app
logic); mirrors the existing `mail-list-members-import` sheet.

**Validation per line** (mirrors single `create_account_alias`, plus a
domain-ownership check `create` omits): well-formed `local-part@domain`;
`domain` must be one the nest owns (`mail_domains`, active) — an address on a
domain the nest does not host is `invalid` (reason `"domain not local"`), so a
single paste may span **several owned domains**; `local-part` passes the
exact-alias validator (strict ASCII, not reserved); the per-actor exact-alias
cap (`alias_policy.exact_aliases_max`, counted across all domains) applies
**across the batch**. Each valid line inserts an exact alias
(`kind='exact'`, default controls, no label); the UNIQUE `(local_domain,
pattern, kind)` index makes a same-address collision `skipped_duplicate`.
An address an admin forwarder or a list already holds is `skipped_duplicate`
with reason `"conflicts with existing alias"` — the exact-key tier's
one-holder rule (§ Resolution order), which binds every door that writes an
exact, forwarder or list row, import and rename included.

### Whitelist semantics — drop = delete (not disable)

In the recipient-whitelist model the whitelist *is* the user's exact-alias set.
**Dropping a leaked address = deleting that alias** (`delete_account_alias`):
the row is gone, the address becomes unknown, and inbound to it **falls through
the resolver to the catch-all** (§ Resolution order) — delivered to the user
with an `X-Fauna-Address-Catchall` stamp so the unlisted-recipient penalty
(`mail-spam.md` § Unlisted-recipient penalty) can file it to Junk, while the
message's own `To:` header still identifies *which* address leaked. This is
distinct from **`disable`/`revoke`**, which keeps the row and hard-rejects
inbound `550 Address disabled` (§ Disable) — no catch-all fall-through, no
delivery. Delete is the default "drop"; disable is the opt-in hard-bounce for
one address.

## Storage

```
account_aliases(
    alias_id          UUID,
    actor_id          UUID,
    local_domain      TEXT,
    kind              TEXT,    -- 'exact' / 'wildcard_prefix' / 'disposable' / 'forwarder' / 'list' (list-kind semantics: `mail-mass-mailing.md`; catch-all is NOT a row — see below)
    pattern           TEXT,    -- the localpart pattern (no domain); for disposable, the base32 token
    forward_target    TEXT,    -- forwarder only: the external destination address; NULL for every other kind
    label             TEXT,
    disabled          BOOLEAN,
    spam_threshold_override  NUMERIC(4,1),
    rate_limit_per_hour      INTEGER,
    rate_limit_per_day       INTEGER,
    uses_remaining           INTEGER,  -- disposable only; NULL = unlimited (the `uses = 0` mint) OR a non-disposable kind; N > 0 = finite uses (decremented per route); 0 = exhausted/dead
    expires_at        TIMESTAMP,       -- disposable only; NULL = no expiry (other kinds)
    created_at        TIMESTAMP,
    last_hit_at       TIMESTAMP,       -- updated on each route
    hit_count         BIGINT,
    PRIMARY KEY (alias_id),
    UNIQUE (local_domain, pattern, kind)  -- two aliases of the same kind on the same domain can't share a pattern
)

alias_hits(
    hit_id            UUID,
    alias_id          UUID REFERENCES account_aliases(alias_id) ON DELETE CASCADE,
    matched_address   TEXT,            -- the full RCPT TO that hit; useful for wildcard / catchall audit
    sender_domain     TEXT,
    received_at       TIMESTAMP
)
```

Indexed on:

- `(local_domain, pattern)` where `kind = 'exact'` for the exact-lookup hot path.
- `(local_domain, pattern)` where `kind = 'disposable'` for disposable-token lookup.
- `(actor_id, kind)` for per-user enumeration on the `mail-aliases` page.
- `alias_hits(alias_id, received_at)` for the per-alias audit / "last hit" query.

`account_aliases.uses_remaining` is decremented atomically at RCPT TO time for disposable aliases.

The catch-all is **not** in this table — it is the per-domain **`mail_domains.catch_all_actor_id` column** (`mail-multidomain.md` § Per-domain catch-all owns the storage + the designation UX; the resolver reads it at step 7, `aliases/mod.rs` sources it from the domain row). At most one designation exists per domain — a column on the domain row, structurally. Treating it as a special row in `account_aliases` would invite "the admin's catch-all is a per-account alias?" confusion; keeping it on `mail_domains` reinforces that it's a per-domain admin setting, not a user alias.

## Cross-actor isolation + reserved local-parts

A user manages their **own** aliases only. **An admin neither sees nor edits another member's alias list (ruled 2026-10-03).** A member's aliases are the member's own data — disposable and per-service aliases say where a person has signed up — and the admin role holds no oversight of a member's own settings ([`family-safety.md`](family-safety.md) § App surface; [`../principles.md`](../principles.md) § The user always controls their data). What an admin legitimately needs is met without a look: a forwarder or role route that collides with a member's alias is refused with a message, abuse is answered by suspension, and an address the deployment hands out (a role or shared address) is the admin's own routing surface (§ Kind 4 and the role routes of `mail-multidomain.md`), never a write into a member's list. The read-only "User detail" panel this paragraph promised until 2026-10-03 is struck; the Admin-class write that contradicted it is removed (§ Implementation status today).

### Reserved local-parts (uncircumventable)

User-tier creation cannot claim a pattern that overlaps with the deployment-wide reserved local-parts (per `smtp-server.md` § abuse@ / postmaster@ role-address routing). Reservation is **applied per `local_domain` independently** per `mail-multidomain.md` § Per-domain role-address routing — `postmaster@domain1` and `postmaster@domain2` are separately reserved; the admin may delegate one to themselves and the other to a community moderator via `mail.inbound.role_addresses_per_domain`. **Two mechanically distinct sets:**

1. **The role-routed set** (`fauna_mail::aliases::DEFAULT_RESERVED_LOCAL_PARTS` — the fixed six `classify_role_address` consults at resolver step 6 for the never-reject / admin-fallback / quota+greylist-bypass routing): `postmaster`, `abuse`, `noc`, `security`, `dmarc-report` (per `dmarc-reporting.md`), `tlsrpt` (per `smtp-server.md` § TLSRPT). The Tier 2 knob `mail.inbound.reserved_local_parts` (`mail-policy-config.md` — "uncircumventable **user-tier reservation**") is admin-writable and widens *this* enumeration only for the **creation-blocking** checks below (`validate_exact_local_part` / `validate_wildcard_prefix` / `create_forwarder`'s reserved check all read the effective, admin-tunable value) — an admin-added name becomes unclaimable by users the same way. It does **not** widen what the three RCPT-TO/AUTH-time call sites (`validate_recipient_handler`, `check_greylist_handler`, `resolve_local_recipient_unstamped`) pass to `classify_role_address`: those are hardcoded to `DEFAULT_RESERVED_LOCAL_PARTS` regardless of the admin override, so an admin-added reserved name is unclaimable but is **not** role-routed — it falls through to catch-all or `550`, never to the admin mailbox with the never-reject / quota / greylist exemptions. Only these six get the full role-routing treatment today.
2. **The creation-only set** (`fauna_mail::aliases::is_creation_reserved_local_part` — uncircumventable, **not** admin-tunable, and **never role-routed**): `unsubscribe` / `unsubscribe-*`. Deliberately *not* in set 1 — role-routing it would send inbound `unsubscribe+<token>@` to the admin mailbox instead of the list-unsubscribe mailto handler, which intercepts it **before** role classification (`mail-mass-mailing.md` § The mailto handler; `smtp-server.md` § abuse@/postmaster@ routing, the unsubscribe@ carve-out).

The validation at creation time:

1. Exact aliases — pattern must not be in either reserved set (role-routed or creation-only).
2. Wildcard prefixes — pattern must not match (when expanded as a glob) any reserved name. Example: `bob-*` doesn't match `postmaster` (`postmaster` doesn't start with `bob-`), so it's allowed; `*-master` would match `post-master`, so it's refused.
3. Disposable aliases — the auto-generated address `<handle>-temp-<token>@` is structurally distinct from any reserved name (the `-temp-` middle segment is the disambiguator); no validation needed.
4. Catch-all — admin-tier; the catch-all designated-actor never receives mail to reserved local-parts, because the role-address route (§ Resolution order **step 6**) fires *ahead of* catch-all (step 7) and sends reserved names to the admin. (Role routing is **step 6 inside this single resolver**, on alias-miss — not a separate pre-resolver stage; see § Resolution order.)

A user trying to claim a reserved local-part gets `400 reserved_local_part` at the `create_account_alias` RPC; the UI surfaces a tooltip explaining the reservation.

**The six are a floor: the admin's list adds to them and never replaces them (ruled 2026-10-01).** "Widens" in set 1 above is meant literally. The role route is an alias-*miss* fallback (§ Resolution order at RCPT TO time, step 6), so it holds only while nobody can own one of the six as an address: a member holding `postmaster@` would take the domain's postmaster mail, and one holding `dmarc-report@` or `tlsrpt@` the reports meant for the nest. An admin who wants a role address to reach someone else has the per-domain role override for exactly that (`mail-multidomain.md` § Per-domain role-address routing), so freeing a role name serves nobody. Therefore: the effective reserved set is the six **plus** the admin's list; an empty list clears the admin's additions only; and the reservation covers every way a member comes to own an address — an alias they create, and the canonical address their **handle** gives them, so a handle equal to one of the six is refused like any reserved handle. ⚠ **Not what the nest does today** — § Implementation status today, *The role-name floor*.

### Cross-user uniqueness

Uniqueness is **per local_domain** (`(local_domain, pattern, kind)`), not deployment-wide — `bob@domain1` and `bob@domain2` are independent rows; per `mail-multidomain.md` § Per-domain alias namespace, each `local_domains` entry is a separate alias namespace.

- Two users **cannot** share an exact alias on the same local domain. The uniqueness constraint enforces this.
- Two users **can** have wildcard prefixes that don't overlap (`alice-*` and `bob-*` coexist).
- One user's wildcard prefix **cannot** shadow another user's exact alias **on the same local domain** — the validator at wildcard-creation time refuses (`409 conflicts_with_existing_alias`).
- One user's exact alias **cannot** be claimed if another user's wildcard prefix is a longer-specific match? **No** — exact wins over wildcard at resolution time, so the exact claim is fine; the wildcard owner just doesn't receive at that one address.
- The per-domain catch-all (`mail_domains.catch_all_actor_id`, `mail-multidomain.md` § Per-domain catch-all) does not conflict with any user-tier alias; it's the resolver-step-7 fallback.
- One actor can claim addresses on multiple domains — they show up as separate rows in `account_aliases` with different `local_domain` values; the per-account exact-alias cap (`mail.account.exact_aliases_max`) is **across all domains for that actor** (storage abuse cap, not per-domain).

## Architectural rules

- **Fixed resolution order.** Exact > Forwarder > +suffix > Disposable > Wildcard > Role-address > Catch-all > 550. The order is a contract, not a knob. (Forwarder shares the exact-key tier and yields a *forward*, not a local route — § Kind 7.)
- **Per-alias controls additive to per-account defaults.** Spam-threshold-override / rate-limit / label / disable live per-alias; missing values fall back to per-account; per-account falls back to admin-tier.
- **Reserved local-parts are uncircumventable from user-tier creation.** `postmaster`, `abuse`, `noc`, `security`, `dmarc-report`, `tlsrpt` + admin-added entries. Validation at create time refuses overlap.
- **Catch-all is admin-tier only.** Users cannot claim `*@`. The product invariant forbids cross-user mail trapping by a non-admin.
- **Disposable aliases auto-expire and rate-limit.** TTL + uses-remaining are hard bounds; per-day rate-limit defaults 100 (overrides at user level).
- **Rate-limit-exceeded is tempfail not permfail.** `451 4.7.0 Rate limit exceeded`. Legitimate senders retry; permanent caps require disable.
- **Deletion is irreversible; revoke is the soft intermediate.** The user revokes to shut off without forgetting; deletes only when committed.
- **Pattern uniqueness on (local_domain, pattern, kind).** Same kind on same domain shares no pattern.
- **The disposable-alias token is opaque on the message body.** Stamped on header only; body bytes don't carry the token. Defeats body-scanning recipients harvesting the disposable.
- **User-tier exposes their own aliases only.** No admin surface shows a member's alias list and no admin-side write to it exists (§ Cross-actor isolation, ruled 2026-10-03).
- **Audit log is per-alias, 30-day retention.** Same retention as verdict logs.
- **Pattern character class is strict.** ASCII subset (`[A-Za-z0-9._-]+`); rejects pathological characters that some MUA / search-index pairs misinterpret.

## Don't do these

- **Don't allow user-tier creation of patterns colliding with reserved local-parts.** `postmaster`, `abuse`, etc. — the reservation is uncircumventable.
- **Don't let a wildcard prefix shadow another user's exact alias.** Validated at create time. Resolution-time precedence (exact wins over wildcard) would route correctly but the conflict-at-create check makes the conflict visible to the wildcard-creating user.
- **Don't generate disposable aliases without rate-limiting the generator.** Compromised client could enumerate a deployment by minting infinite disposables; `mail.account.disposable_generate_per_day` defaults to 50.
- **Don't allow `*@` at user-tier.** Admin-tier only; user-tier is rejected with `400 catchall_not_user_tier`.
- **Don't auto-create catch-all on first claim.** Admin opts in explicitly; the unset default is "reject unmatched."
- **Don't preserve the original recipient address in delivery metadata for disposable aliases as a body-stamp.** Stamped in headers only; body-stamping would leak the disposable to a body-scanning recipient.
- **Don't hard-bounce a deleted exact alias when the domain's catch-all is set — the fall-through is the designed drop semantics.** Deleting an alias makes the address unknown: with no catch-all it rejects `550 User unknown`; with a catch-all it falls through and delivers stamped `X-Fauna-Address-Catchall`, so the unlisted-recipient penalty (`mail-spam.md` § Unlisted-recipient penalty) files it to Junk while the message's own `To:` still shows which address leaked (§ Whitelist semantics — drop = delete). A user who wants a hard bounce for one address uses `disable`/`revoke` (row kept, `550 Address disabled`), not delete.
- **Don't stamp `X-Fauna-Address-*` headers if their values are user-controlled-but-sensitive.** Wildcard suffix and +suffix are user-controlled but not sensitive (the sender already sent to that address); disposable token is the disposable token itself which is **public** (it's in the address the sender used); catch-all is a boolean signal. None are sensitive.
- **Don't allow wildcard patterns shorter than two characters.** `b-*` is too greedy; minimum prefix length is `<two-or-more-chars>-`. Enforced at creation time.
- **Don't add a separate pre-resolver role-address stage.** Role-address routing is **step 6 of this single resolver**, on alias-miss (§ Resolution order; `smtp-server.md` § abuse@/postmaster@ routing `:31`): a reserved local-part (`postmaster@`, etc.) that no alias above matched routes to the admin ahead of catch-all, carrying `is_role_address`. One resolver, one order — splitting role routing into an envelope-time pre-stage would duplicate the reserved-name classification and risk drift from the alias order.
- **Don't merge `account_aliases` rows across local domains.** A deployment with multiple `local_domains` has separate alias namespaces per domain; bob's `bob@domain1` is distinct from `bob@domain2` (which may be unowned or owned by another user).
- **Don't store the disposable token in a guessable form.** 6 base32 chars = 32^6 ≈ 1 G possibilities; per-deployment generation cap protects against enumeration; collision-check at mint time avoids re-use of an active token.
- **Don't auto-expire disposable aliases without telling the user.** The expiry is visible on the row's `expires_at` column in the audit / list UI; the user can extend (edit) before expiry.
- **Don't let sub-addressing mask a role address.** `dmarc-report+x@<our-domain>` is nonsense: `classify_role_address` keys on the **raw** local-part, so `dmarc-report+x` is *not* reserved (the `+x` makes it non-reserved) and falls through the normal +suffix/alias path — while bare `dmarc-report@` hits the role route at step 6. Reserved-name recognition is exact, not prefix, by design.
- **Don't expose the disposable address auto-naming pattern (`<handle>-temp-<token>`) to a user-customizable shape** ("can I have `bob-throwaway-<token>` instead of `bob-temp-<token>`?"). The `-temp-` segment is a deployment-wide recognizable tag for downstream filtering; making it user-customizable would defeat the recognizability without much user-side gain.

  per § Storage (so future *additive* expansions land via the boot-time
  `reconcile_added_columns` backstop with no hand-migration —
  `../architecture/version-compatibility.md` § Dimension 1; the table is
  **never dropped to evolve**, alpha onward), plus the indexes named there. (The
  `forward_target` column + the forwarder partial index landed with the
  § AF admin-forwarder slice below.)
- `alias_hits` is also created up-front, with no production writer at I4
  (superseded: `resolve_recipient` populates it since § A2.4 below).
- `db::mail_aliases::put_exact_alias` + `lookup_exact_alias` are the
  only writer/reader; `fauna.bridges.validate_recipient` resolves
  through `lookup_exact_alias`.
- The standalone `recipient_routes` table is **dropped** (no
  production writer existed; the e2e fixture's SQLite hand-poke moves
  to the admin RPC — tracked internally, § E.3.3).

**Landed (tracked internally, § A2.1)** (the user-tier exact-alias
CRUD slice; nest WS-RPC + shared `MailAccountClient` wrapper):

- The five **exact-kind** user RPCs `fauna.bridges.{list,create,update,
  revoke,delete}_account_alias` (`User`-class — the owning actor is the
  authenticated caller, owner-scoped writes; wire shapes in
  `libs/fauna-protocol/src/bridge_routing.rs`, handlers in
  `bins/fauna-nest/src/bridge_routing_handlers.rs`). (A2.2 extended
  `create` to also accept `wildcard_prefix` — see below.)
- Per-alias controls **read + written for exact**: `label`, `disabled`
  (via `revoke`), `spam_threshold_override` (whole spam-points on the
  wire — DAG-CBOR forbids floats), `rate_limit_per_hour`,
  `rate_limit_per_day`. (`uses_remaining` / `expires_at` / `last_hit_at`
  / `hit_count` had no production writer at A2.1 — superseded: § A2.3 and
  § A2.4 below now write them.)
- Reserved-local-part validation (the six defaults `postmaster`,
  `abuse`, `noc`, `security`, `dmarc-report`, `tlsrpt`) + the strict
  ASCII char-class + the per-account exact cap (`mail.account
  .exact_aliases_max`, default 20) — all four alias-policy knobs
  (`exact_aliases_max`, `reserved_local_parts`, `subaddressing_enabled`,
  `wildcard_prefix_enabled`) are **admin-tunable** via
  `fauna.bridges.put_alias_policy`/`get_alias_policy`
  (`AliasPolicyOverrides::effective`, `db/mail_policy.rs` — landed, incl.
  the `admin-mail-alias-*` client controls), not hardcoded; the shared
  `fauna_mail::aliases` module holds the pure validators plus the const
  defaults an unset override falls back to. Cross-user
  uniqueness enforced by the `(local_domain, pattern, kind)` UNIQUE
  constraint (`conflicts_with_existing_alias`).

**Landed (tracked internally, § A2.2)** (the fixed-order resolver +
the shared matcher + wildcard/`+suffix`):

- The fixed-order RCPT-TO resolver `fauna.bridges.resolve_recipient`
  (`BridgeMta \| BridgeMda`-class — the MDA's server-side auto-schedule
  classifier also calls it, § Wire shapes below) — exact > +suffix > disposable > wildcard >
  catch-all > 550, per § Resolution order. Returns `{actor_id,
  headers_to_stamp, control_overrides}`; honors `disabled` (`550 Address
  disabled`) and rejects an invalid sub-address (`550 Invalid
  sub-address`). The richer **superset** of `validate_recipient`
  (exact-only) — it has **superseded** `validate_recipient` at the RCPT-TO
  call on **both** the Go MTA paths (inbound MX + submission, the cutover is
  complete). `validate_recipient` is **retained** as the exact-only
  **AUTH-time** resolver (the submission/IMAP/CalDAV login `resolveActor`
  paths): a login must resolve an exact canonical identity, never an alias /
  wildcard / catch-all / forwarder, so the two RPCs are not interchangeable
  there and `validate_recipient` is not deleted. The order + the matching
  predicates (`split_subaddress`,
  `match_wildcard`, `validate_wildcard_prefix`) are a pure, wasm-safe
  unit in `libs/fauna-mail/src/aliases/`; the handler does the I/O.
- **Wildcard-prefix create** — `create_account_alias(kind="wildcard_prefix")`
  with the create-time conflict checks (§ Cross-user uniqueness): vs
  another user's matching exact alias → `conflicts_with_existing_alias`;
  same prefix as another user's wildcard → `conflicts_with_existing_alias`
  (UNIQUE); reserved-glob → `reserved_local_part_in_wildcard`; min
  `<2-chars>-` prefix; one wildcard per actor → `actor_already_has_wildcard`.
  The wire `pattern` is the literal prefix incl. the trailing `-` (e.g.
  `bob-`).
- `+suffix` sub-addressing is **resolver-only** (no stored row): the
  resolver splits on the first `+`, re-matches the base exact alias, and
  stamps `X-Fauna-Address-Suffix`. Gated by `subaddressing_enabled`
  (admin-tunable via `put_alias_policy`/`AliasPolicyOverrides`, default
  `true`; same treatment for `wildcard_prefix_enabled`). Catch-all is
  sourced from the per-domain `mail_domains.catch_all_actor_id`.

**Landed (tracked internally, § A2.3)** (the disposable mint +
resolution + the per-day generate cap):

- The **disposable** kind + the user mint RPC
  `fauna.bridges.generate_disposable_alias` (`User`-class): the nest derives
  the `<handle>` + hosting `<domain>` from the actor's canonical (oldest)
  exact alias, enforces the per-day generate cap
  (`disposable_generate_per_day` = 50, hardcoded — A3 Bucket C),
  collision-checks a 6-char base32 token, inserts a `kind='disposable'`
  row writing `uses_remaining` + `expires_at` (their first production
  writer) + the hard `rate_limit_per_day = 100`, and returns
  `{alias_id, full_address, token}`.
- The **disposable resolution step** (resolver step 4, between +suffix and
  wildcard): `<handle>-temp-<token>` decodes the token, looks up the row,
  checks aliveness, **atomically decrements** `uses_remaining` (the one
  resolver step with a side effect — the pure matcher signals the consume,
  the handler does the guarded `UPDATE … WHERE uses_remaining > 0`, so a
  last-use race rejects exactly the loser), stamps `X-Fauna-Address-Disposable`
  (**header-only**), and rejects a decoded-but-dead address `550 Address
  expired`. A non-existent token falls through to wildcard / catch-all.
- The decode/aliveness predicates (`split_disposable`, `is_base32_token`,
  `disposable_alive`, `disposable_local_part` + the token alphabet/length
  consts) are pure, wasm-safe additions to `libs/fauna-mail/src/aliases/`.
- **`uses_remaining` semantics resolved** (a goal-doc contradiction this
  slice fixed): `NULL` = unlimited (the `uses = 0` mint), `N > 0` = finite
  (decrement per route), `0` = exhausted/dead. The unlimited sentinel is
  `NULL`, never `0` (§ Kind 5, § Storage now state this).
- **Dependency:** the mint needs the actor's canonical exact alias to exist
  (else `fauna.bridges.no_canonical_address`). That canonical row is now
  auto-created at mail-enable time (`ensure_canonical_handle_alias`, § Kind 1),
  so an enabled user has one before minting (this gap note is superseded).

**Landed (tracked internally, § A2.4)** (the alias-hit audit — this
**closes the A2 alias program** on the nest side):

- **`alias_hits` population at resolve time.** `resolve_recipient` logs one
  `alias_hits` row (`hit_id`, `alias_id`, `matched_address`, `sender_domain`,
  `received_at`) + bumps the matched alias's `last_hit_at` / `hit_count` on
  every match attributable to a **stored row** (exact, +suffix→base exact,
  wildcard, disposable); **catch-all has no row → no hit**. Like the
  disposable decrement, this is a handler-side side effect the pure matcher
  *signals* (`RecipientResolution::Resolved.matched: Option<MatchedAlias>`),
  not performs. For a disposable the hit is logged only **after** a successful
  `uses_remaining` decrement (a lost last-use race rejects + logs nothing).
- **`fauna.bridges.list_account_alias_hits` (`User`-class)** — the paginated
  per-alias audit reader. Owner-scoped (the handler joins `alias_hits.alias_id
  → account_aliases.actor_id == caller`, else `not_found` — never leaks another
  user's hits). Newest-first; `before_hit_id` is the keyset cursor (resolved to
  its `received_at` then paged on the composite `(received_at, hit_id)` since
  `hit_id` is a random UUID). Page size capped at 500.
- **`sender_domain` on the wire.** `ResolveRecipientRequest` grew an optional
  `sender_domain` (`#[serde(default)]`) so the Go MTA passes MAIL FROM at the
  cutover; the audit is complete from day one (empty until the cutover).
- **30-day retention GC.** A periodic sweeper deletes `alias_hits` older than
  `ALIAS_HITS_RETENTION_DAYS` = 30 (hardcoded — A3 Bucket C, until the
  observability policy write-path lands `mail.observability.verdict_retention_days`),
  mirroring the `bridge_audit` retention sweeper. `ON DELETE CASCADE` already
  drops an alias's hits when the alias is deleted.

**Landed (tracked internally, § AF)** (the admin external-forwarder
alias-half — Kind 7; gated on the forwarding-dispatch SRS rewrite (tracked
internally, § N3) having landed, which it has):

- The **forwarder** kind + the `forward_target TEXT` column (NULL for every
  other kind) + the `idx_account_aliases_forwarder` partial index on
  `(local_domain, pattern)`. Plaintext at rest, uniformly (routing
  metadata, § Kind 7 `:115`).
- The three **Admin-class** RPCs `fauna.bridges.{create,list,delete}_forwarder`
  (wire shapes in `bridge_routing.rs`, handlers in `bridge_routing_handlers.rs`,
  `MailAdminClient::{create,list,delete}_forwarder` wrapper). `create` validates
  the `forward_target` (shared `fauna_mail::validate_forward_target` — RFC-5321
  syntactic + **must not be a hosted domain**), requires `local_domain` to be a
  hosted domain, validates `pattern` against the **admin-tunable**
  `reserved_local_parts` (the `put_alias_policy` effective value, not a const),
  and refuses an exact↔forwarder collision on the key (`conflicts_with_existing_
  alias`). The exact-create path gained the symmetric forwarder-collision check,
  so a `(local_domain, pattern)` is an exact mailbox **or** a forwarder, never
  both (§ Resolution order `:124`,`:134`). `delete` is admin-scoped (any admin).
- **Forwarders are excluded from the owner-scoped `list_account_aliases`** so an
  admin's forwarders never surface as their personal aliases (§ Kind 7 `:111`);
  they list only via `list_forwarders`.
- The **`Forward` resolver outcome** (resolver step 2, on the exact key, after
  exact): the pure matcher (`fauna_mail::aliases`) gained a `ForwarderCandidate`
  + a `RecipientResolution::Forward { forward_target, forwarder_actor_id }`
  variant; `resolve_recipient` returns the wire `ResolveRecipientReply::Forward`
  — no local delivery, no header stamp, attributed to the managing admin. No
  `alias_hits` row this slice (there is no admin forwarder-hit-list RPC yet).
- **Forward *dispatch* is out of scope here** — it is the same SRS / loop /
  rate-cap / NDR pipeline the forwarding track owns (tracked internally, N3–N5, landed);
  the resolver hands `{forward_target, forwarder_actor_id}` to it. The Go MTA
  consumes the `Forward` outcome only once the RCPT-TO cutover lands (below).
