## Implementation status today

- **✅ Built — federation propagation (slice 4), both legs; peer-side verification anchored 2026-07-29 (the unanchored-verify hardening), and the anchor made unplantable + identity-proven 2026-07-29.** A succession no longer stops at its home nest. **Push:** landing a statement fans it out (detached, best-effort) to every peer holding cross-nest residue about the identity — the home nest resolves those peers from `channel_foreign_members` (which gained an additive nullable `nest_url` because a `home_nest_id` authorizes an inbound call but cannot *originate* one), mapped through the nest-wide `nest_addresses` directory to each target identity's known addresses, proven-first and **per-identity-fair capped**: the directory retains at most a small constant of addresses per identity (first-N-wins at the write — every row is dial-backed, so this caps only an identity's own mint), and the fan-out bound consumes every identity's best-ranked address before any identity's second, so one identity holding many early proven addresses (each costs only a dial) cannot evict a later-seen honest peer from the push set — evicting a peer outright requires as many *distinct dial-proven identities* as the whole bound, with the hourly pull the declared backstop past it. **Pull:** an hourly (and at-boot) reconcile asks the home nest of every remote identity this nest holds residue about whether it was superseded, which is what makes an unreachable peer a delay rather than a permanent hole. **One verification path, anchored in what the peer already knows — a push is a hint, never evidence.** The plane's adversary holds the identity seed, and a seed holder mints a registration chain every signature of which is genuine — so "the delivered chain verifies" proves seed possession, not RecoveryKey legitimacy, and the push carries no chain at all (the payload's never-verified `chain` field, kept for pre-hardening receivers, left the wire with the 2026-09-24 compat-remnant sweep). A receiving peer takes only *which identity to check* from a push, then runs the same path the hourly pull runs. Its **anchor** is a nest *identity*, not a URL: the `home_nest_id` of the **oldest residue row overall** at first contact, and the **persisted `foreign_recovery_heads.anchor_nest_id` pin** once the identity has ever been verified (write-once, so a later re-invite that rewrites the oldest binding cannot move a proven anchor). Dialable URLs are resolved for *that* identity from the nest-wide **`nest_addresses` id→URL directory** — **every** address recorded for it, dial-proven ones first and then oldest sighting first, capped — and — the load-bearing step — **the dial then proves the identity** (`fauna.auth.nest_handshake` signs a fresh nonce as the expected nest key; `AnonymousNestClient::verify_nest_identity`) before a byte is trusted, so a URL resolved from an attacker-influenceable binding fails closed. **The walk over those candidates is what keeps a failed dial a delay rather than a hole**: residue is nest-wide and any User-class caller can add a binding, so resolving a *single* address let one planted row — for any actor, naming the honest identity at a box that cannot sign as it — deny that identity's succession on every future pass. Identity-proof-fail-closed makes a wrong candidate cost exactly one refused dial, so trying the rest is free of security consequence; each attempt spends the same per-pass dial budget, and a hint's whole walk stays inside the one hint ceiling. **A walk is only as good as the list it walks, and the first version of that list could be emptied**: the address lived on the membership row, whose write is an upsert keyed `(channel_id, actor_id)`, so a re-pointed binding *overwrote* the honest address in place rather than joining it — and for an identity known through a single cross-nest row (the ordinary 1:1 DM or folder share) the walk was left with nothing honest to reach, restoring the very denial it was built to close. Addresses therefore live in their own nest-wide directory, where a differing address is a **new row**: erasure is unrepresentable rather than guarded, a genuine address migration resolves because both addresses stay candidates, and `proven_at` — stamped only where the proof happens, on a completed federation handshake — orders a dial-proven address ahead of one a caller merely asserted. The same directory feeds the **push** leg, which previously read that single overwritable column with no walk at all, so a rewrite silently redirected an entire push; its fan-out is capped for the same attacker-extendability reason the pull walk is. Only then does it fetch `fauna.recovery.registration.chain` and `succession.lookup` and verify with `fauna_core::recovery::verify_succession_against_chain`, passing the **persisted known head** (`foreign_recovery_heads`, one row per remote identity, monotonic): a served chain must *visit* that head, so it cannot be *rewritten or truncated*. **The known head bounds a hostile chain-server but not the seed thief** — a seed holder can extend the genuine chain with a seed-alone link that visits the head (the legitimate honest-loss arm), so the head alone does not refuse a takeover; the anchor-**identity** proof is what does, by refusing a box that cannot sign as the pinned home. Quiet pulls persist heads and pin the anchor opportunistically, shrinking first-contact TOFU to the window before a peer's first pass. An identity with **no addressable anchor is refused**, never TOFU'd from pushed bytes — that is the un-addressable-peer residual the re-key scope table already declares. Hint-triggered verifies are throttled (per-identity cooldown, concurrent-dial cap, bounded dial) so a push cannot be a dial-on-demand lever. On acceptance the peer writes the **same** `actor_successions` row the home nest does (`db/successions.rs::record_peer_succession`), which is what makes the rest structural rather than re-implemented: the supersession consult at `deliver_inbox_payload_core` starts refusing the superseded key's *new* relayed content, and the peer's own `succession.lookup` serves the link onward. Residue re-points in the same transaction — `channel_foreign_members` and contact edges (keeping their trust flags), collision-safe where the successor already holds the row; multi-hop paths land one anchored hop per pass, the re-pointed residue carrying the anchor to the next hop. A statement naming a **locally-homed** identity is refused: only `succession.submit` may supersede a local account, because only it re-points the account too. Nest-side cached KeyPackages are deliberately not in scope — `key_packages` holds only *local* actors' packages and a cross-nest fetch is destructive, so that residue lives in the client's MLS state. Handler `bins/fauna-nest/src/federation_handlers.rs`, originator `federation_pool::originate_succession_push`, anchor + pull + hint worker `bins/fauna-nest/src/succession_pull.rs`, verification `libs/fauna-core/src/recovery.rs`.
- **✅ Built — the per-group MLS ceremony mechanics (2026-08-02), and the transport question they answer.** MLS has no identity-change path (`self_update` keeps the credential by design), so § Propagation's two-commit pair is the only shape; `fauna_mls::succession` now composes it — `commit_add_successor` (authored by the old leaf, which is the only member that *can* author it) and `commit_remove_old` (authored by the successor, because MLS forbids committing one's own removal, refused **by name** rather than as an opaque OpenMLS error so a mis-ordered ceremony does not read as a broken group). Both guardrails are pinned, as is resumability (a second add over a group already carrying the successor is refused rather than growing a duplicate leaf). **The property the ceremony exists for is pinned end-to-end** by `libs/fauna-mls/tests/succession_ceremony.rs`, over three engines rather than two — a two-engine test cannot tell "the group survived" from "the group became a DM": an unrelated third member keeps reading across both commits while the removed old leaf — *the thief's copy* — fails to decrypt the first post-removal message. **The transport question is settled and is why this is runnable at all:** after the statement lands the old identity is refused at every authenticated surface, so it cannot upload its own commit — the module therefore *authors* bytes and never publishes them, and the **successor's** session uploads both halves through `fauna.conversations.channel.send`, one of the three raw roster auto-register paths, so MLS carries membership and the nest only ever sees a member-shaped upload. **Declared out of reach on this path:** a **claimed folder channel**, whose roster is owner-managed (only the claimant may drive an auto-register), so a succeeded claimant's folder channels need their own answer.
- **✅ Built — the per-group sweep driver (2026-08-02).** `fauna_client_recovery::group_sweep::sweep_groups` enumerates the succeeded identity's groups off its own MLS engine and runs the pair over each, so a real user's groups are actually re-pointed. It lives beside `succeed_identity` rather than in `fauna-mls` because it needs a nest connection and that module's whole contract is having none. **Two engines, one process** — add-successor can only be authored by the old leaf and remove-old only by the successor — and the driver is deliberately indifferent to how the old engine was provisioned: on-disk MLS store (theft) or `ProviderReplica::restore_into` under the restored seed (loss-with-escrow, which is what makes § Propagation's *"identical — the restored seed drives it"* true in code). Because both engines are co-resident the **Welcome never hits the wire**; what is published, over the successor's session, is the two commits with the in-group statement between them (bullet below). **Position is reconstructed from membership facts, not a stored cursor**, and the add commit is published *before* the successor joins locally — so "the successor holds this group" implies the members were told, and a re-run of a finished sweep posts nothing rather than growing a duplicate leaf. One crash window is *reported* rather than hidden (`NeedsMemberReAdd`: the add was authored but never published and the Welcome is gone — § Propagation's member-side re-add is the declared remedy), and a group that refuses the post never denies the others their re-key. **The degraded arms' user-facing copy named only that remedy from 2026-08-05 until the retry gesture landed 2026-08-16; they now name the button first and keep the member-side remedy as the fallback it still is:** they previously advised a re-run when no re-run affordance existed or was buildable as advised — at the time `sweep_groups` had one caller, the ceremony fold, reachable only between the ceremony and the account switch, and add-successor can only be authored by the old leaf, whose *live* engine is gone post-switch; the only control the sentence could be read against is *My Identity Was Stolen*, which as the successor runs a second irreversible succession that evicts nothing. - **✅ Built — the sweep's first app call site, on tui (2026-08-02); with it, the affordance exists for a user.** `Op::RecoveryStolen` now runs `sweep_groups` immediately after `succeed_with_held_kit` returns and **before** the account switch, so clicking *My Identity Was Stolen* re-points the user's groups as part of the one ceremony. Two rulings that shape it, both with user-irrecoverable data behind them: **(1) the sweep reuses the LIVE conversations engine, never a second one opened over the same store.** `MlsEngine::new` holds a real SQLite handle for the engine's life, the conversations backend already holds one over the signed-in account's `mls_state.db` for the whole session, and the sweep *mutates* the old engine (it authors add-successor and ratchets epochs) — so a second engine on that file would put two divergent OpenMLS states on one store, corrupting group membership and message keys. This is the same answer, for the same reason, that `ConversationsSession::engine()` already exists to give the folder author path. It is also **why the sweep runs pre-switch**: that is the only moment both engines exist at once, since the switch drops the conversations session and rebuilds it over the successor's own scope. Pinned by `settings::tests::the_succession_op_reuses_the_live_engine_rather_than_a_db_path`. **(2) The ceremony's outcome outlives the switch that ends the ceremony.** `drop_authenticated_state` drops every per-identity field so one identity's state cannot paint under the next; the sweep report is the deliberate and only exception, because it describes the *outgoing* identity's departure and the switch is the ceremony's own closing act — dropping it would delete the result at the moment of completion. Pinned by `app::tests::the_succession_sweep_outlives_the_switch_but_not_a_reset`. **(3) The successor seed is made durable BEFORE the sweep runs, inside the same op.** The nest commits the succession before it replies, so from that commit until the seed is written there is exactly one copy of the key the account now belongs to, in memory; the sweep makes network calls over every group, so sweeping first would stretch that window across an arbitrary number of round trips, and a crash inside it locks the user out of their own account permanently (§ Product invariants → *No user-data loss*, client-only-resident key material). ## Propagation

- **Own device fleet:** each device's next connect gets the `superseded` refusal → the client surfaces "this identity was succeeded — import the new identity" and the user imports the new seed (QR / paste — the same distribution as adding a second device; `devices.md`). Device registrations and sync-agent renewal grants are re-created under the new identity, not migrated. **The device that ran the ceremony, when it takes the account back at RELAUNCH, owes the group sweep — ruled 2026-09-26.** The undecidable arm of a lost submit reply persists the successor without activating it, and the next launch adopts it once the chain proves it ([`identity-succession.md`](identity-succession.md) § Implementation status today, the lost-reply bullet's relaunch adoption); that adoption cannot run the ceremony's own sweep, which needs the retired identity's live engine, and a refused launch never opens one. Member-side re-pointing is **not** a substitute: the roster-pair gate (*MLS groups* below) means a member re-points only once the successor is seated here and the predecessor's leaf is gone, and only this device's sweep produces that pair — until it runs, the succeeded credential keeps its seat in every group, which is the one alert-shaped succession condition. So the adoption **owes the sweep exactly as it owes the kit**: a flag set beside the kit-owed one in the adoption, surviving the account switch and cleared only by a factory reset, discharged by the successor's post-auth hook as an unbidden press of `recovery-kit-sweep-retry-button` — the shared `retry_sweep_as_successor`, which already resolves the retired identity's seed and conversation store off this device's registry (the device that ran the ceremony is, by construction, the device that holds them) and never opens a second engine over a store conversations already has open. Its `Swept` report is parked as the ceremony's own sweep report would have been, so the two lines and the ephemeral review pass render as after any ceremony; every other answer parks the owing arm, so the retry button renders and its sentence says why — the existing floor, never a silent drop. The sweep discharge precedes the kit's in the same hook (the ceremony's own order), and a hook with no nest yet leaves the flag set, as the kit's does.
- **MLS groups (per group):** the successor must join as a **new member** (the credential *is* the actor_id; there is deliberately no in-place credential swap). In the theft case the owner still holds the old seed, so the ceremony uses the old leaf constructively one last time: the old leaf commits **add-successor** (Welcome to the successor client), then the **new leaf commits remove-old** (MLS forbids committing one's own removal). The statement rides in-group alongside the add so members render continuity instead of "someone added a stranger", and member clients that hold the statement treat the pair as one logical operation. **What makes that one operation binding, and not merely how a member is asked to read it — the roster-pair gate (ratified 2026-09-20).** Verifying a statement proves the succession *happened*; it never proves it happened **in this group**. A true statement is public — it rides the chain — and the transport sender is deliberately unbound, so any member may carry one into any group, a seed thief still holding the old leaf in a group the sweep never reached included: a member that re-points on the verification alone renders *that* group as continuity while the thief's leaf stays live, which is precisely the "the ceremony did not finish" condition [`critical-alerts.md`](critical-alerts.md) § Feeders calls the one alert-shaped succession condition — painted as its opposite, the one rendering that hides it. **A member therefore re-points a participant row only where this group's own roster carries the pair: the successor seated here and the predecessor's leaf gone.** The roster is read from the **MLS engine**, never from the chat snapshot, for the reason rule (1) of *Removing a flagged member* gives below — a foreign-authored membership Commit is the adversarial case, and it is the case the snapshot cannot see. The gate's two refusals are deliberately not the same, because the honest ceremony passes through one of them: the statement rides *alongside the add*, so the predecessor is still seated when it arrives and **every** honest succession meets the gate mid-flight — that verdict **holds** the statement rather than degrading it, and the inbound remove-old commit re-drives what is held (a consumed MLS application message cannot be re-decrypted, so that single delivery is the only copy the session will ever hold, and a gate that dropped it would mean no member ever renders continuity again). A statement whose successor holds no leaf here at all is **dropped** instead: the ceremony never ran in this group, and when it does reach it the sweep posts the statement again beside its own add. Loss-with-escrow: identical (the restored seed drives it). Loss-without-escrow: another member (DM peer, any group member) re-adds the successor after verifying the statement; a sole-member group with no escrow is lost — declared. Ratcheting after remove-old restores per-group forward secrecy **against the succeeded credential** from that epoch — every leaf bearing it, which the ceremony evicts in one commit; group propagation is therefore part of the **urgent** phase. **That is narrower than "against the thief", deliberately.** The attacker held the seed, therefore the old leaf's authority to author `add_member`, so they may have seated a leaf under a *second identity they control* at any point in the pre-succession window; such a leaf survives this ceremony untouched, and the client cannot distinguish it from a member added honestly in the same window — the compromise has no announced start, and a leaf carries no join date. The sweep therefore **reports** every surviving member it did not itself add or remove, rather than guessing (§ Re-key scope → MLS groups). No client-side rule closes this: "remove every leaf the ceremony did not add" would empty every group of every honest correspondent on every run, since the ceremony adds exactly one leaf. The party who can classify the residual is the user, and the surface's job is to show them the roster. **Which surface, ratified 2026-08-02 and refined 2026-08-03:** the roster renders as the **outcome of the ceremony the user just ran**, in the flow that ran it — not as a standing banner. That ceremony-flow pass is **ephemeral, shown once per recovery**, and offers per-person **Keep** / **Remove** plus *defer the rest*; a **permanent review view** then holds **only what was still unhandled when it was closed or deferred**, which is what makes that view empty before any recovery and empty again once the backlog is worked through (2026-08-03 — it is a page, so the not-a-banner and not-an-alert rulings above are untouched). Both surfaces render **one flag stored on the person**, keyed **`(person, raising event)` — never a permanent per-person boolean**: a *Keep* is a verdict about the compromise window that raised it and cannot vouch for that person across a later one, so a second succession legitimately re-raises them. The item carries a **`reason`** field from the start though it has one value today, because the witness's unverifiable arm (§ Implementation status → the ✅ witness bullet) is a second producer already in sight. **An adjudicated item is KEPT at rest carrying the owner's verdict, never deleted (ratified 2026-08-06)** — the reflex shape, where presence means "open" and *Keep* removes the row, makes an answered item indistinguishable from one never raised, so any **re-run** of the raising sweep (a resume, or the *"finish moving your groups"* retry) silently re-raises everyone the user already worked through; the re-run is a real flow, so the idempotence belongs in the data rather than in a rule every future caller must remember. Carrying the verdict is also what lets two of the user's devices work the same backlog without either erasing the other: the items merge as a **per-key union in which a decided verdict beats a still-`Open` one** — richer than the grant marks' whole-field latest-wins beside them, which would drop one device's adjudications wholesale, and safe against the bare union that would resurrect what the peer just closed. **When the item is written down (ratified 2026-08-06):** by the successor's **aftermath**, in the same pass that re-keyed `__config` when ratified (since the ledger kind's cut, the post-store-ready pass that writes the ledger's rows; leg 1 retired with the rail on 2026-10-02 — [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)), not by the sweep that produced the roster — the sweep runs pre-switch as the predecessor, when the account's record is sealed to a key whose bearers the succession has already revoked, so no identity exists that could store it then. The raise is attributed to the **retired identity as a parameter**, never to whichever predecessor key happened to open the blob, because a chain with two retired identities can be re-keyed from either and only one of them raised this roster. The roster itself is the ceremony's own report, never a later re-derivation from the successor's engine: it is a fact about the membership *across the compromise window*, and a re-derivation would flag people who joined afterwards. The roster is not staged at rest in between — the raise is idempotent per `(person, raising event, reason)`, so a re-run of the sweep is what recovers a ceremony whose app died before the aftermath ran. The flag is deliberately **not** a contacts-list flag: an unattested member is a *group* member and often not a contact — the entry that matters most, an identity a thief seated in a group, is precisely the one that never was — so it renders in **group member lists** (where removal already lives, so no second removal mechanism is minted), in contacts where applicable, and in the permanent view. Per-app build status gated for per-app rollout. It is deliberately **not** a critical-alerts feeder ([`critical-alerts.md`](critical-alerts.md) § Feeders owns that ruling and the two shapes it kills): a healthy group has unattested members by construction, so a banner would announce the user's own correspondents as a permanent alarm after every *successful* succession. The one succession condition that is alert-shaped is the opposite accessor — groups where the ceremony did not finish, so the succeeded credential still has reach — which is re-derivable, self-clearing, and owned by that same section. **A claimed folder channel obliges one more consumer of the statement (ratified 2026-09-22):** its roster is owner-managed under a durable owner marker every member seat holds, and that marker is also the anchor a member's seat verifies the owner-attested declassification against — so the statement must re-point it, at the ceremony's midpoint, or the successor's remove-old is refused and the retired key keeps both powers. The rule and its build ledger are [`../architecture/federation.md`](../architecture/federation.md) § Cross-nest shared folders + channel append → *The marker follows the owner's verified succession*; the sweep's transport half on such a channel — the nest's claim re-point — is [`succession-aftermath.md`](succession-aftermath.md) § Re-key scope's MLS-groups row.
- **Federation peers:** the home nest pushes the statement to every peer it has residue with (a new federation kind), and peers can pull the chain from the old identity's home. The push is a **wake-up hint**: a receiving peer resolves the identity's **anchor** — the nest identity of the oldest residue binding it learned *first*, or the write-once pin it persisted at first verification — **proves that anchor identity by a signed-nonce challenge before trusting a byte**, and only then verifies against the chain it fetches from that anchor (plus the chain head it has persisted). It refuses an identity it holds no addressable anchor for, and refuses a box that cannot sign as the pinned anchor — never trusting the pushed bytes, per the verification rule above. Addresses are held in a nest-wide id→URL directory in which a newly-seen address **joins** an identity's candidate set and never replaces what is already there, so no caller can make an identity un-addressable by re-pointing a binding; candidates a federation handshake has actually proven are dialed first. The directory retains a bounded per-identity address set (first-N-wins; every row is dial-backed, so the cap constrains only an identity's own mint), and the push fan-out consumes addresses per-identity-fairly — every identity's best address before any identity's second — so a crowded identity cannot evict an honest peer from the push set. The membership row's `home_nest_id` itself remains caller-writable on purpose (a genuine member migration must stay expressible): a re-pointed row costs the push leg at most one pull interval of delay, because the peer's own pull reads its *own* residue and its *own* pinned anchor — an **accepted** window, not a gap; a first-write-wins pin would need a re-invite hatch that reopens the very displacement it closes. The persisted head stops a *rewritten* chain; the identity proof stops a *seed thief* who extends the genuine chain with a seed-alone link (which the head alone accepts, since that is also the honest-loss shape). A peer that verifies it: persists its own succession row, re-points its remote-identity residue (foreign channel membership, contact edges, cached KeyPackages invalidated), and refuses *new* content signed by the superseded key. Historical content keeps verifying and stays attributed to the old id — correct, since it was genuinely authored by that key; clients that hold the statement render the old id as "now `new_actor_id`" for continuity. **A nest that holds an account for the identity is not a peer in this sense.** It is another nest the succession must be applied at, by its own chain and the whole transaction, and the successor's devices carry the statement there; the federation arm keeps refusing a statement that names a local identity. Owner: [`identity-succession.md`](identity-succession.md) § Enforcement on the home nest → *Every nest the identity is linked to*.
- **Removing a flagged member (ratified 2026-08-10).** Two of the three renderings route their *Remove* to the affordance the row already has; the two surfaces that render a person **outside any one group** — the ephemeral kit-side pass and the permanent review view — have none to route to, so their *Remove* means **evict this person from every group of mine they are currently in**. That driver is `ConversationsManager::evict_person_everywhere` (`libs/fauna-conversations/src/eviction.rs`), and it sits with conversations rather than beside the ceremony because it is a statement about group membership with no succession in its story — the manager already owns both the roster and the per-thread removal, and the second producer of review items already in sight (the witness's unverifiable arm) is not a succession either. Four rules, each of which had a plausible wrong answer: **(1) Which groups — the ones the person is in *now*, re-derived**, since the item deliberately stores no group list. That is right for removing and would be **wrong for raising**: a raise is a fact about membership *across the compromise window*, so re-deriving it would flag people who joined afterwards. Two operations, two questions, and neither may borrow the other's answer. ***Re-derived from what* is the security-bearing half of this rule, added 2026-08-10:** membership comes from the **MLS engine roster** — the same source the flag was raised off (`SweepReport::unattested_members` → `MlsEngine::group_members`) — and never from the chat snapshot (`ThreadDetail::participants`), which is a local view written at join and by the owner's own gestures that **no inbound Commit reconciles**. A foreign-authored membership Commit therefore seats someone in the engine and not in the snapshot, and that is the adversarial case rather than a corner: a thief's planted second identity (Residual 1, [`succession-aftermath.md`](succession-aftermath.md) § Adjudicating what the aftermath carries across → *MLS groups*) is added by the *thief's* commit. Deciding membership from the snapshot does not fail loudly — it skips the group, records no failure, and so earns `Removed` under rule (4) while the person is still seated, which is rule (3)'s harm reached through the enumeration door. Two sources for one question is the defect; the driver and every surface built on it read the flag's source, and a surface must likewise never render *who remains* from the snapshot. The same rule binds the removal itself: a roster edit is keyed on the participant's **actor id**, never on the rendered handle (an MLS roster's handles are empty by construction and attacker-chosen by threat model, so a handle-keyed removal takes same-handle bystanders with it). **(2) Groups, not 1:1 threads** — a DM is not a group, and "removing" the only other person from one would leave the owner alone in a thread the ordinary delete already handles, minting the second removal mechanism this section refuses. (The gate is the thread *flavor*; the `supports_membership_change` capability cannot express it, because a Fauna-addressed participant only appears on FaunaMls threads and every FaunaMls flavor is membership-capable.) **(3) A partial eviction records NO verdict and the item stays `Open`.** Removing someone from 3 of their 5 groups is the ordinary outcome of a flaky link, and `Removed` means the person *was* removed — writing it there makes the surface go quiet, since an adjudicated item is kept at rest and no longer rendered, while the person is still seated in the two that failed. Nothing is lost by waiting and nothing is asked twice: the successful removals are durable and the group list is re-derived, so the next press targets exactly the remainder and converges with no resume cursor, no per-group verdict, and no state this design refused to keep. **(4) An eviction that frees nobody still earns `Removed`** — the common case on the permanent view, which by construction holds a postponed backlog the flagged person may have left every group of in the meantime; "removed from every group they were in" is vacuously true of zero groups, and refusing the verdict would strand an item nobody could ever close. The verdict is **derived from the outcome, never chosen by the caller** (`CrossGroupEviction::earned_verdict`), so no app can reconstruct rule (3) wrongly on its own. **(5) What "every group of mine" spans — the channel classes (ratified 2026-08-10).** The *raise's* span is every MLS group the owner's engine holds, deliberately class-unfiltered (Residual 1, [`succession-aftermath.md`](succession-aftermath.md) § Adjudicating what the aftermath carries across → *MLS groups*: a thief's seat is a foreign add, and narrowing the raise is the direction that hides one); *Remove*'s reach is decided per class, and a raised seat *Remove* cannot clear **blocks the verdict as a typed, rendered fact** (`CrossGroupEviction::unreachable`) — it never escapes silently and never earns `Removed` while it stands, which is rule (3)'s principle applied at the class level. Per class: a **chat-group thread** is a group of mine — evicted directly under rules (1)–(4). A **1:1 thread** is not a group and its one honest peer — the participant the snapshot lists — is never *Remove*'s business (rule (2) stands); but **any engine seat beyond the snapshot-listed peer is evicted exactly like a group seat**: the chat poll applies membership Commits with no flavor gate, so a thief's Commit can seat a third identity in a DM channel, and rule (2)'s rationale (don't strand the owner alone in a thread the ordinary delete already handles) says nothing about a third seat. A **chat channel with no bound thread on this device** (the thread↔channel binding is rebuilt at restore from history slices) is still a group of mine but not removable-from here until its thread is: the seat blocks the verdict, typed as such, and its closure is the restore completing on this device or the *Remove* running from a device that holds the thread. A **folder channel** is in the raise's span but governed on the folder plane: removal there is the set owner's key-rotating `FoldersAuthor::remove_member` in the folder's own sharing surface, and a member of someone else's set removes nobody but can leave the set — so the seat blocks the verdict, typed as such, and either remedy converges, since a removed member or a left set is out of the raised span at the next press. (An unbound channel carrying no class marker classifies as folder by the same derivation the folder poll uses — over-approximate on legacy unmarked chat channels, accepted here for the same reason it is accepted there.) A **scheduling channel** is not a group at all: a one-off iMIP delivery envelope whose roster no applied Commit can ever change — `poll_inbound_scheduling` skips Commits by design, so a seat there cannot be planted in the owner's own copy, cannot be evicted, and never blocks; its one-off lifecycle is its own closure. The enumeration follows the same source rule as the roster (rule (1)): the driver asks the rail for the engine's unbound seats (`RailBackend::unbound_seats_of`) rather than deriving the span from the thread list, which cannot see an unbound channel by construction.
- **Contacts (scoped 2026-08-16 — the clause used to read as an aftermath leg every app owed; it is not):** the **social contact graph is nest-side-complete** — `fauna.contacts.list` renders rows `record_succession` / `record_peer_succession` re-point inside the succession transaction, both directions, so no app holds a social-contact *edge* row to re-point and **no tui leg exists for the edge** (tui keeps no at-rest contact store; the CardDAV Address Book is a different, MSEK-sealed plane with its own MSEK-leg ruling). **One client-held thing keyed by a peer's actor id does need re-pointing, and it is not the edge (scoped 2026-09-19): the private contact overlay** — the owner's own nickname, notes and labels on a person, client-sealed on the account-state plane where no nest can open it, so the succession transaction cannot reach it. It **folds forward as a statement-consumer action**, the same contract as the peer-contact row below: the witness-verified statement folds the predecessor's overlay into the successor's by the overlay's own per-field join and clears the predecessor's item, as a reconcile that re-runs whenever a non-empty item is found under a succeeded identity ([`../ui/contacts.md`](../ui/contacts.md) § The private overlay owns the rule). Built in shared Rust 2026-09-26, beside the participant re-point it rides (`ConversationsManager::apply_inbound_succession`) and over the one account-runtime seam every native app wires, so no app owes a leg of its own. **Collision rule (ruled 2026-08-31): where the collapse gives the same holder an edge to both identities, the surviving edge keeps the higher-trust-impact status — `blocked` absorbs everything; among the rest `confirmed` > `accepted` > `pending`.** A succession re-points who an edge names and never widens what its holder reaches (the membership arm's own axis), so in particular it can never silently dissolve a block in either direction: the holder blocked one of the two identities knowing what they knew, and the collapse is the first moment the link between them is even visible — a wrongly-surviving block is visible in the app and one-tap reversible (Unblock), a silently-dropped one is invisible and irrecoverable. The one at-rest client contact store this clause governs is `fauna-peer`'s `PeerDb.peer_contacts` (linux p2p + the FFI peer surface), and its re-point is a **statement-consumer** action, not a ceremony leg: the same witness-verified statement that re-points a thread participant row re-points the peer-contact row in place (preserving the trust flags; terminal hop on a twice-succeeded peer — `resolve_successor`'s contract) rather than minting a stranger entry. It lands with each app's witness-registration trickle-down leg and is declared client residue until then.
- **Subscriptions:** author succession re-points tiers on the home nest and future KeyBlobs are signed by the successor (subscribers accept via the statement); subscriber succession takes effect at the author's next period rotation, which wraps to the successor's pubkey.
