## The declared re-point axis

> **A column the walk reads by NAME cannot rule what a column CONTAINS — the blob-held actor ids, declared 2026-09-21.** The completeness walk [`succession-repoint-axis.md`](succession-repoint-axis.md) § The declared re-point axis owns finds unaccounted columns by searching for words in column names, which makes it exactly as complete as its vocabulary — the circularity `the_walks_vocabulary_can_name_every_registered_column` was written to break. One level out, the same circularity was still live in a form no widening of the word list could reach: `room_policy_versions` holds an owner id, an admin set and a signer id, all inside `policy_blob`, and has **no actor-shaped column at all** — so the walk never looked at the table, and it landed (schema 68) with no ruling on either axis without reddening anything. No vocabulary reaches it, because there is nothing in a name to read. So the shape is declared instead of searched for: every blob-ish column in the live schema must say whether its CONTENTS name actors — `ACTOR_BEARING_BLOB_COLUMNS` with its ruling, or `NON_ACTOR_BLOB_COLUMNS` with why not (a third list, `BLOB_PROPERTY_COLUMNS`, holds the columns that are a digest, size, path or id *of* a blob and so have no contents to ask about) — and an undeclared one reds in the commit that adds it. **The first four bearers are all room-plane signed acts, and all four Stay:** a member judges a floor delete record against the policy *of the version the record names*, so a retained version naming a since-deleted admin is the verification history that keeps that delete a delete; dropping it would un-tombstone on the next fresh session, and rewriting it would break the author's signature over it. Succession needs no rewrite either — the floor resolves a name through the chain at judgment time (`floor_designee`). **What this does NOT claim:** that the declared bearers are the true count. It claims that another cannot arrive silently in a column the schema calls a blob, which is the only property a declaration can actually carry.
>
> **The other fifteen blob columns, ruled the same day — nine more bearers, six non-bearers, backlog 15 → 0 — and the rule that ran through all of them is that a blob ruling FOLLOWS the row ruling its table already has; it never re-derives one.** The walk landed naming fifteen columns as owed rather than guessing them, because a guessed verdict in a security registry reads as coverage. Reading each writer turned that into two questions per carrier: *which ids do the bytes name*, and *does the row's existing verdict leave those ids in a state anything can observe*. **Four name nobody** and need only their code-side reason: the three columns of deployment key material keyed by bridge, domain or selector (`bridge_dkim_blobs.blob` — its table retired 2026-10-04 at nest schema 123, `mail-bridge-lifecycle.md` § DKIM provisioning (automatic) — `bridge_tls_cert_blobs.blob`, `atproto_session_secret_blobs.blob`), whose index and sealed bundle were both read and carry no actor; and `personalization_models.sealed_blob`, sealed client-side in a container with no index and no associated data at all, so ownership is the row's registered `actor_id` and nothing else. **Six follow their row out of existence**, so the id inside never outlives the row that carries it: the four MUA-plane blobs [`succession-repoint-axis.md`](succession-repoint-axis.md)'s MUA-facing bridge-plane blockquote already burns (`bridge_wrapped_mls_blobs`, `bridge_wrapped_submission_tokens`, `bridge_mls_snapshot_blobs`, `bridge_webdav_keys_blobs` — each carries a plaintext, AEAD-bound index naming the row's own actor, which the nest never decodes; `Move`, ruled dangerous for the row, is also *impossible* for the bytes, since the bridge opens with the actor it resolved and the nest holds no key to re-seal), `capability_grants.blob` (the index names the **owner**, the one inner id the nest verifies at deposit; `holder` is a service-user key and the scope tuples name no person; burned, then re-minted by the successor's client under its own id — [`succession-aftermath.md`](succession-aftermath.md) § Implementation status today, the capability-grant re-mint), and `recovery_escrow.blob` (its index names the owner and, on a successor's blob, a sealed section names every predecessor — neither readable by the nest; burned in the ceremony's transaction per [`succession-aftermath.md`](succession-aftermath.md) § Re-key scope). All six purge on deletion. **Two stay as signed**, for the room plane's reason: `labelers.metadata_blob` names only `algorithm_id`, the artifact's self-signed key, exactly as its `publisher_actor` column was already ruled; and `current_key_blobs.blob_data` — the one bearer that names people *other than* the row's owner — is a tier's signed `KeyBlob` naming the author, the signing device and every wrapped subscriber. Its **row moves** with the tier family while its **bytes stay**: the author id sits under a signature verified against the author's own delegation, so a moved historical version names the predecessor as author for ever, which is true, and is superseded wholesale by the next approval, revocation or rotation rather than edited. A deleted or succeeded subscriber's id rides until that next version as a wrap to a key nobody holds — it confers nothing, because readability is gated on the `subscribers` row that the purge walk and the paying-reader leg do rule. **And one where the row moves and the bytes CANNOT follow — `atproto_identity_key_blobs.blob`, the pass's one real finding, ✅ closed the same day (2026-09-21).** The nest mints these keys, seals them to the bridge and discards the plaintext, so after a ceremony the row is the successor's while the actor id inside — twice: the AEAD-bound plaintext index and the sealed bundle — names the predecessor for the life of the DID; across a chain it names the *first* holder, since the reconcile carries the family straight to the terminal. As found, that was safe only through an omission that was also a gap: the blob opened with associated data taken from **its own index** and no consumer compared anything, so a moved blob opened — *and* so did one identity's whole blob served as another's, which the index binding (it detects an edited index) never sees. The two were coupled — a consumer comparing actor ids would have had to resolve the requested actor through the succession chain or strand the DID of every account that ever succeeded — and the closure **cuts the coupling instead of resolving it**: the bridge binds the blob to the identity's *published keys*, which sit on the `atproto_identities` row that moves (or parks) all-or-nothing with the blob, so the binding holds across any number of hops with no chain lookup, and the ids inside stay what they always were — mint-time provenance, never compared. The mechanism, what it does and does not defend against (a misrouted or substituted row — not a hostile nest, which sources the expectation and minted the keys), and the alternatives declined are owned by [`atproto-pds-bridge.md`](atproto-pds-bridge.md) § State & data shape; the succession half is pinned by the two-ceremony, two-hop-reconcile and parking tests beside the ceremony's own in `successions.rs`. **The fragment-list residual is re-affirmed, with its measurement:** widening `BLOB_SHAPED_COLUMN_FRAGMENTS` to `payload` / `record` / `body` was weighed and declined — the opaque carriers outside the word `blob` are on the order of a hundred columns with no shared vocabulary, so three more words would catch a handful and read as coverage of the rest. The complete notion is the column's declared *type*, a walk of its own with a backlog of its own — the next blockquote.

> **The declared-TYPE walk — every `BLOB` column the two name walks do not claim, landed 2026-09-21 with a named backlog of 277 columns over 148 tables (none today — the last two columns were ruled on 2026-09-21 and the list was deleted at zero; 14 over 8 after the day's three drains, below, three of the held carriers ruled since, and then the conversation and curation drain's nine with their three tables — the bridge planes took it to 208 over 115, the conversation and curation planes to 152 over 88, the sync, backup, custody, recovery and nest planes the rest) — and what it delivered on landing is the arrival property, not the rulings.** `every_blob_typed_column_outside_the_name_walks_declares_what_it_holds` (its own module beside the registry, `db/actor_tables/tests/opaque_carriers.rs`, because the registry file is already several times the whole-file read ceiling and these are its longest lists) reads the type `PRAGMA table_info` reports, subtracts the two populations that already have an owner — a column whose *name* reads as a person is the census walk's, registered or excluded there; a column whose name carries a blob fragment is the blob walk's, the fragment list now shared between the two so one column can be owed to neither or both — and requires everything left to be declared actor-bearing with its ruling or non-actor with why. **No vocabulary is involved**, which is the point: `record`, `statement`, `envelope`, `payload`, `witness`, `receipt`, `evidence` and the `*_sealed` / `encrypted_*` families share no word, and they share a type. **The backlog was `UNEXAMINED_OPAQUE_COLUMNS`, pinned by an exact `==` count until it reached zero and was deleted (2026-09-21), and it was a different population from the blob walk's deleted one** — columns no walk had ever looked at, not a re-opening of "owed" for a blob-named column. By the shape of their names **at landing** (the figures are the harvest's and are not maintained as the list drains), and *only* as a map for whoever drains it: about 118 read as non-person ids, 38 as digests, 27 as sealed or encrypted content, 24 as key or secret material, 17 as public keys, 5 as signatures or nonces, and 48 as structured or unclassifiable (`statement`, `record`, `envelope`, `witness`, `receipt`, `evidence`, `reply`, `payload`, `raw_message`, `auth_grant`, …). ⚠ **That sort is deliberately NOT in the code.** A fixed-width id the census vocabulary failed to recognise as a person is exactly what this walk exists to surface — the landing harvest already lists `contacts.peer_id`, `content_labels.classifier_id` / `scanner_id` and `access_grants.algorithm_id` beside the hashes — and a name rule that waved the "obvious" ones through would be the matcher excusing itself, the circularity one level further out. Entries leave by being **read**, plane by plane. **The first drain — the bridge, mail, atproto and spam planes, 69 columns over 33 tables, 2026-09-21 — and the definition it had to settle.** *Names an actor* means the bytes **structurally** carry an identifier an account can be found by — an actor id, a per-account public key, a DID, a mail address — in the clear or under a seal; free text a user typed (a calendar's display name, a mail subject) is not that, while a word model trained over whole messages is, because the address headers are always in the training text. **Fifty-four name nobody:** every `*_id` of the mail-routing plane is a `Uuid::new_v4()` minted at its one insert site or a foreign-key copy of one; the atproto session, grant and consent ids are CSPRNG output; the DAV ids and the audit idempotency hashes are one-way digests whose only actor input already sits in the row's own `actor_id` column; the three `bridge_service_users` keys are a bridge *process's* own (the same 32-byte principal namespace as an actor id, and never a `users` row); `delivery_receipts` holds nest ids and has no production writer. Two of those digests are declared for what they are rather than waved through: `uid_hash` (both DAV rails) and `import_sessions.source_hash` are **unkeyed** blake3 over a client-chosen or low-entropy preimage — no id inside, but a confirmation oracle for whoever can guess the preimage, the first pinned unsalted on purpose because the Go MDA applies a bare blake3 to the same key. **Fifteen bear, and twelve of them simply follow their row:** the identity-signed authoring cert and its per-account sub-key (`atproto_authoring_keys`, Purge / Burn — the cert authorizes the key against the *predecessor's* identity, so Burn is right for the bytes too); the six sealed DAV bodies, index hints and sidecars, each an envelope the owner's own client seals to the owner's own key with a header that names nobody, so the ids inside are reachable by no nest-side walk by construction; `import_sessions.source_sealed`; the owner's spam model and its per-event deltas, whose plaintext shape is word n-grams over whole RFC 5322 text and so carries a correspondent's address as the n-gram of its parts; and `spam_model_holder_copies.sealed_copy`, whose **plaintext** AEAD-bound index is the contributor's actor id a second time (Purge / Burn; the nest stores it without comparing it to the row). **Three are more than "follows its row".** *(1)* `atproto_native_records.record` and `atproto_preferences.preferences` are plaintext and name **other** accounts — a follow's subject DID, a labeler's — possibly ones this nest hosts. The row moves and the bytes stay: the row's `cid` is the address those bytes were published under, and what is named is a DID, which the named account's succession carries unchanged, so there is nothing to re-point; a deleted subject leaves a follow of a DID that no longer resolves, as on every PDS. *(2)* ⚠ `bridge_caldav_events.encrypted_fauna_ext` is the one DAV carrier holding a Fauna **actor id** rather than an address — the organizer binding a later inbound `CANCEL` or updating `REQUEST` must come from — and it names *another* person under the owner's seal. The client compares it to the attested author by plain equality, with no resolution through the succession chain, so **a succeeded organizer's cancel or update is refused on every invitee's calendar for good**. That is the safe direction (`last_commit_sender`'s shape: a comparand that can only match a dead identity admits no one) and a stranded event rather than a hole; the fix is client-side chain resolution, never a rewrite. **The rule is now ruled and built** — [`inbound-scheduling-authority.md`](inbound-scheduling-authority.md) § Who may mutate an existing event over the inbound rail → *A succeeded organizer* owns it: a verified walk fetched from the *bound* nest, only after the local comparison misses, admitting only where the account ended up, and re-binding an admitted update — **and both shipped resolvers, native and web, now perform that walk**, so a succeeded organizer's cancel is honoured on all 7 apps (that doc's § Implementation status today). *(3)* `spam_baseline.model_json` bears in the spam model's weak sense and sits on a singleton table keyed by no actor, so it has no registry row and cannot take one — and **its ruling, left open at the drain, was made the same day and is owned by [`mail-spam.md`](mail-spam.md) § Cold start, Path 2 → *A contributor's departure withdraws the baseline***: a summed contributor's deletion, opt-out, model reset or grant revoke withdraws the published sum at once (the purge walk withdraws before it deletes the row that says the actor was summed), and a succession is not a departure. The entry carries that ruling and cites the owner. **No person-shaped fixed-width id surfaced in this slice** — the landing harvest's four are all in later ones. **The ordering rule the blob walk never had to state:** a carrier's ruling follows the row ruling its table already has, so a carrier on a table with **no** `ACTOR_TABLES` entry — the `room_policy_versions` shape, a table the census never opens — needs its *row* ruled first; an entry that invents a row verdict in passing is a ruling made in the wrong registry. **The rule binds only a carrier whose bytes name an actor** — a digest, a row id or a deployment key on an unregistered table needs no row verdict invented for it, `bridge_tls_cert_blobs.blob`'s precedent. **And a fixed-width id found to be a person does not leave this walk by being registered:** the walk subtracts only what `actor_shaped` or a blob fragment claims by *name*, so registering the column or declaring it a vocabulary blind spot hides it from nothing here (`segment_records.scope_id` is registered, a declared blind spot, and still seen) — it is either claimed by widening `ACTOR_SHAPED_ROOTS`, after checking what the substring pulls in across the schema, or it stays declared in `ACTOR_BEARING_OPAQUE_COLUMNS` pointing at its census entry. **What this walk still cannot see, declared:** a carrier that is not `BLOB`-typed at all. Structured data in a `TEXT` column (`results_json`, `origins_json`, the `overrides_json` family) is the same blindness in another affinity, and `TEXT` is not walked because there it is the *norm* rather than the exception — names, labels and URLs by the hundred — so a type walk over it would be a backlog with no arrival property worth its size. It stays a named residual until a narrower notion than "is TEXT" exists.

> **The conversation and curation planes, drained the same day beside the bridge planes: 56 columns read — so the backlog stood at 152 columns over 88 tables after both — and the walk's premise confirmed on its first outing.** Fifty-three name nobody, and almost all of them reduce to four derived ids stated once in the code: a **room id** (a salted hash over the founder's actor id, its salt resting beside it, so the row is a *checkable statement about* `rooms.owner_id` rather than a second place the owner is named), a **channel id** (a hash over a randomly minted group id — never over a channel's members), a **roster entry id** (a slot derived from the member's id and the seating stamp, never equal to it) and a **content id**. Three bear actors and follow their rows (five since the 2026-09-22 re-rule, the last blockquote): `content.payload` (signed posts, inbox envelopes and takedown witnesses — the row moves, the bytes stay as signed, `current_key_blobs.blob_data`'s reason) and the labeler key on `labelers` and `labeler_subscriptions` (`algorithm_id`, by its own column's ruling never an enrolled account). ⚠ **Four things are declared rather than ruled away, each inside its entry:** `engagement_events.event_id` and the bridge/profile content ids are *unsalted* hashes over an actor id, so they are recomputable by anyone holding the inputs — a linkability oracle, not an identity; `room_members.reception_pubkey` is one key per account reused across rooms, a stable cross-room correlator; `content_links.metadata` and the FTS shadow index hold bridged mail addresses and display names in the clear, which are not actor ids and are not nothing; and the dormant `DeviceSyncChannel::expected_channel_id` is an unsalted hash of a single actor id, so the session that wakes it re-rules every `channel_id` here. ⚠ **And the finding the walk was built for: `room_invites.invitee_id` / `inviter_id` and `content_labels.classifier_id` / `scanner_id` are PERSON ids under words the census vocabulary lacks**, on tables that appear nowhere in the registry — so account deletion never reaches them *by the person*: no statement outside `db/rooms.rs` touches `room_invites` at all, and `content_labels` rows leave only with the content they label, so a label an account hand-attached to somebody else's post keeps that account's id after the account is gone (as an invite does, twice more inside the signed act). They were deliberately **not** ruled in passing: per the ordering rule above their *rows* are ruled first, in the registry proper, and until then they stay on the backlog by name. ✅ **`room_invites` ruled, 2026-09-21 — the first of the three, and both exits from this walk used at once.** The row is the invitee's: *Purge* (`room_members.principal_id`'s reason), a plain *Move*, exported to the invitee. The premise the finding above was filed under had already gone stale: since 2026-09-11 the attach door admits only the content's own author or a holder of that author's `content.label-write` grant ([`moderation.md`](moderation.md) § Per-row badge data path), and a grant holder is a bridge service user, never a `users` row — so *a label an account attached to somebody else's post* is no longer writable, and no account deletion names its writer. **Deletion therefore takes no verdict of its own, and a `Purge` would be wrong as well as redundant:** an author's labels leave with their posts through the federation-aware retraction; where that retraction leaves a post standing the post still names its author, so the label discloses nothing more, and a self-label is a safety property of content still being served — it lives exactly as long as the content. Declared residue: rows the old class-only door wrote, unattributed and inert to every binding read, leave only with their content. **Succession is where the defect was.** A label has no detach door; its writer revises it by attaching again, and the upsert keys on `classifier_id`. Nothing is signed, so nothing is contradicted. > **The third drain, 2026-09-21 — the sync, backup, custody, recovery and nest planes and the remainder: 143 read, 138 ruled, and what the reading found is mostly that the schema's column names are a poor guide in BOTH directions.** Twenty-nine bearers and 109 non-bearers, every one from its writer (31 and 107 since the 2026-09-22 re-rule, the last blockquote); the per-column text lives in the two lists, and what follows is only what is more than *follows its row*. **Names that promise a person and hold none:** `device_authorizations.device_key` is *this nest's* signing key (the door refuses anything else); `nest_rotation_log.statement` spells its fields `*_nest_actor_id` and holds two generations of the nest's own key; `groups.group_id` is a post digest and `guardian_mail_holds.message_id` a content hash. A **nest identity is never a person** though it has an actor id's exact shape and sometimes its type name — every deployment seed is a fresh random draw (first boot, provisioning, rotation), none derives from an account key — and a **device id or device key names a machine seat, not an account**: a sync device id is keyed by an install secret that never leaves the machine, so the bytes resolve to nobody, and what links one to a person is the registered `sync_devices` row beside it. The one exception is ruled as a bearer: the WebDAV **pseudo-device id is a pure function of the actor id** (`label_custody::webdav_pseudo_device_id`), so `sync_changes.device_id` and `sync_devices.device_id` can be confirmed against a candidate id by anyone; it follows its row, and on a moved `sync_changes` row it goes on deriving from the predecessor — true attribution of a past write, compared to nothing. **Names that hide a person — the walk's best findings, as predicted:** `contacts.peer_id` is a plain counterparty actor id whose ruling already exists in the row's own `Move(Bespoke)` (both sides collapse; an edge *to* a deleted account rides in the holder's list, it being the holder's address book) — it was declared in the bearing list until the `peer` root joined the census vocabulary (2026-09-21), and is now a `SUCCESSION_REFERENCES` entry carrying that same verdict; > **The five carriers the third drain held — all five ruled the same day.** Each was read, names an actor, and sat on a table with no registry entry, so nothing deleted or re-pointed it. ✅ **`feature_policies.subject_id` — Purge / `Move(Plain)`.** The account a *self-imposed* feature policy binds (empty for the nest-wide tiers, so every actor-keyed statement is tier-selective by construction). It **moves**: a self-exclusion is the person's choice about themselves, and a key rotation that erased it would hand a self-excluded person their feature back for having recovered their account. `Move` is safe out of a *compromise* too, which is the usual argument against one — the self tier can only tighten, so a thief-authored row widens nothing, and the owner removes any limit with no cooling-off ([`dynamic-features.md`](../architecture/dynamic-features.md) § Authoring surfaces, the de-escalation ruling): a tier that cannot trap its author cannot trap their successor. ✅ **`membership_tiers.admin_id` — Retain / `Move(Plain)`, its parent's verdicts.** The designation that makes one of the admin's own subscription tiers mean membership of this nest addresses `subscription_tiers` by value, with no foreign key, so it takes that row's rulings or it dangles: purged from under a retained tier it would silently stop admitting the members who paid. It left the type walk rather than joining the bearing list, because its root — `admin`, a role noun like `owner` — is now in the census vocabulary (three false positives excluded by name: two legacy `admins`-table rowids and a quota-tier name). ✅ **`worker_replication.payload_key` — Purge / Stay.** Polymorphic: the inbox **recipient's raw actor id** on `inbox` rows, a post content id on the rest. The registry has no row filter, so the `inbox` narrowing is not expressible and the safety of an actor-keyed statement rests entirely on id-space disjointness (`segment_records.scope_id`'s argument). Purge, because the one reader is a dashboard count a deleted account's markers would over-count for ever; **Stay**, because the marker truthfully records a replica stored on the paired worker *under the retired id* — moving it would claim the worker holds the successor's copy. ⚠ The replica itself is the worker's to delete and no leg here reaches it. ✅ **`namespace_entries.namespace` — Purge / Burn.** The publishing actor's id (the LAN-certificate publish binds the caller; the sync worker calls it *the actor's self-namespace (= the actor pubkey)*; the federation rail parses it as a 32-byte id) — the census had excluded the table as having *no actor-identifying column at all*, which its writers refute. The row is a **mailbox, not what the box serves**: a TLS bundle sealed to one nest and parked for a paired nest to pull, while an installed bundle lives in the nest's certificate directory — so purging it takes no working certificate with the account, only a blob nothing can reach once the actor's pairing (also *Purge*) is gone. It **burns** because it is a signed *instruction to install a TLS key*: the signature verifies only under the retired key, so it cannot move, and it must not stay — the sync worker's pull watermarks are in memory, so every restart of a paired nest re-pulls from zero and re-runs the install for whatever still verifies, over a certificate the successor has since published. Withheld from the export as sealed key material. It left the type walk rather than joining the bearing list: `namespace` is now a census root, with no false positive (it is the only column in the schema containing the word). The namespace is no longer only the publish door's convention: since 2026-09-21 both sync doors refuse a namespace that is not the paired actor's, so the ruling's *reachable only through the actor's pairing* is enforced. The door does not check `actor_sig`, by ruling — each consumer verifies its own entry kind ([`private-mode.md`](../architecture/nest/private-mode.md) § Namespace Sync). ✅ **`outbox` — `Policy::Partial` / `Move(Plain)`, on a new `author_id` stamp; `outbox.payload` a bearer that follows the row.** The signed post or tombstone awaiting forward names its author on a table that had **no person column at all**, so neither registry could find an account's rows. The additive `outbox.author_id` (schema v74) is stamped by all three producers — the post create and the two delete doors (`routes.rs::maybe_enqueue_outbox` / `maybe_enqueue_delete_outbox`) — each with the verified author in hand; the create's hand is the caller, which is the author only because post ingest is own-write ([`../ui/feed.md`](../ui/feed.md) § Post creation). **No row is unstamped:** the boot backfill that once stamped a row an older binary wrote was ruled a standing backfill rather than *let them drain* — **a refused entry may never drain**: it retries until sent, however long the refusal lasts — and was deleted with the 2026-09-24 genesis collapse, which keeps no backfill for a database predating it ([`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 2) ([`../architecture/nest/private-mode.md`](../architecture/nest/private-mode.md) § Post Forwarding owns the retry rule). Deletion cannot be a plain purge, because the two entry types want opposite things and the registry has no row filter: a queued *post* must not be published after its author is gone, while a queued *deletion* is the message that removes a copy already published on the paired nest. So the deletion axis gained its third verdict, **`Partial`** — the twin of the succession axis's, for the same reason: the purge walk runs one hand-written predicated leg, a dedicated test owns the row rule, and the two registry-driven sweeps (*every `Purge` row goes*, *every `Retain` row stays*) deliberately assert nothing about the table, since each would be wrong. Everything the deleted author queued goes **except a tombstone that can still be sent**, which leaves when sent — or at the retry ceiling, since an entry whose author has no account on the nest keeps only the retries it has left. A tombstone already at the ceiling when its author is deleted goes with the rest. On succession the stamp **moves** with `content.author`, the post it forwards: it is a finder, read only by that deletion leg, and the account continues under the successor — while the payload **stays as written**, signed under the retired key, so the two deliberately disagree afterwards. The queue is live only on a private-mode nest with post auto-forwarding on, which bounds who is affected.
