## Goal

A nest admin sees **one place** in their Fauna app that answers "is my deployment's DNS correct, and what do I do about it?" — for every domain the nest hosts and every record that domain needs (mail and the nest host itself).

- **If the admin's client holds the domain's DNS-provider credentials** (the API token captured during onboarding, kept by the client), the admin flips a single switch — "Fauna controls DNS" — and the **client** publishes every required record and keeps it correct as keys rotate, domains are added, or policies change. Zero manual DNS work. The nest never sees the token; it only reports the *expected* record matrix and *verifies* public DNS (see § Where the credential lives and § Live verification).
- **If no admin client holds credentials** (the admin runs DNS elsewhere, or declined to share the token), the same surface lists every record — name, type, exact value to paste — and shows a **live red/green indicator** per record: green when public DNS already serves the expected value, red when it's missing or wrong. The admin pastes records into their own DNS provider and watches them go green.

Both modes cover **all** DNS a deployment needs in one consolidated surface, not just DKIM: the nest host's `A`/`AAAA`, mail `MX`, `SPF`, `DKIM` (every selector × algorithm), `DMARC`, `MTA-STS`, `TLSRPT`, optional `DANE`, and a `PTR`/rDNS advisory (see § Records covered for why PTR is special).

This is the post-onboarding complement to `onboarding.md`'s first-domain DNS step: onboarding does the **initial** publish (or hands the admin the records to paste); this surface is where DNS lives **for the rest of the deployment's life**.

## The two modes (per domain)

Mode is **per `mail_domains` entry**, not deployment-wide: a deployment may host `example.com` at Hetzner (Fauna-managed) and `example.org` at a registrar with no supported API (manual). A deployment-level convenience ("manage all domains") sets every domain's mode at once, but the stored state is per-domain.

**Mode is client-side state, not nest state** (decided 2026-05-25). The "this domain is Fauna-managed" opt-in lives in the admin's DNS record (a per-domain managed set, alongside the credential — § Where the credential lives), **not** a nest-side flag. Rationale: managed mode is only actionable on a client that *holds the credential* — on a two-admin deployment where only one admin has the provider API key, a nest-shared flag would falsely imply the keyless admin could auto-publish. So mode co-locates with the credential that makes it actionable. **Effective mode is a client-side projection**, computed by the shared `DnsManagementMachine`: a domain renders Fauna-managed iff it is in the admin's managed set **and** some held credential's `verify()` reports a zone covering it; otherwise it renders manual. The nest's `fauna.dns.list_records` `mode` field is informational ("manual" today) — the client overlays the effective mode onto the snapshot; the nest neither stores the mode nor acts on it (it never publishes — § Where logic lives).

### Fauna-managed

Enabled only when an admin client holds DNS-provider credentials whose `verify()` reports a zone covering this domain (§ Where the credential lives). When on:

- **Publish.** The **client** writes every record in § Records covered via the held provider credentials, reusing the `libs/fauna-provisioning` `DnsProvider` dispatch — the same code path *and the same execution context (the client)* that onboarding's orchestrator already uses. Idempotent: `find_records` pre-flights each write; an already-correct record is skipped. The client sources the *expected* values from the nest's `fauna.dns.list_records` read, so client and nest agree on the matrix byte-for-byte.
- **Reconcile.** The client re-publishes on every event that changes a record body — DKIM rotation, SPF/DMARC/MTA-STS policy edit, domain add/remove — and whenever the DNS page is open or a client background poll detects drift via `fauna.dns.verify_records`. Rate-limited per `mail-multidomain.md` § Per-domain DNS records ("at most one rewrite per entry per minute"). DNS does **not** require sub-hour self-healing while every admin device is offline, so reconcile is client-driven, not a nest daemon — a record that drifts while no client is connected simply shows red until a client next checks, exactly as in manual mode.
- **Withdraw-aware convergence — DKIM re-mint + rotation cleanup; ATProto handle rename (tracked internally (E), resolved 2026-06-23; generalized to a second slot 2026-07-24).** The generic Publish above is **create-only** (`fauna-client-dns::DnsManagementMachine::publish` — `find_records` pre-flight then create-if-absent), so it cannot retire a record whose **value changed at a stable name**. Two DKIM cases need exactly that: **(1) re-mint** — a missing `mail_dkim_keys` row makes the nest mint, at boot, a *fresh* key under the **same** selector (`mail-bridge-lifecycle.md` § DKIM provisioning), so `<selector>._domainkey.<domain>` must flip to the new `p=` **and** the stale `p=` be withdrawn (the 2026-06-21 example.com incident: stale `p=` → external `dkim=fail`); **(2) rotation cleanup** — after a `<YYYYMM>` selector flip the **old** selector's TXT must be unpublished (`mail-multidomain.md` § Rotation, "the old TXT is later unpublished"). Both are handled by a **dedicated, best-effort, per-selector-slot converge pass** (`reconcile_dkim_txt`), mirroring the cert-coupled `reconcile_floor_mx_tlsa` (§ Records covered): for each `<selector>._domainkey.<domain>` name in the nest's `list_records` matrix, **create** the desired `public_dns_value` if absent and **withdraw** any published `p=` value at that name absent from the desired set. The withdraw is **scoped to the Fauna-exclusive `_domainkey` names** — never a blanket "delete anything not in the matrix," which would clobber unrelated apex TXT; this is the same single-slot scoping that keeps the TLSA pass safe, and it is the reason a withdraw-aware converge is a *dedicated pass per exclusively-owned slot*, not a generic matrix-wide diff. During a rotation's 24 h overlap **both** selectors are in `list_dkim_selectors` (so both are "desired"), so the pass never withdraws the old selector mid-overlap; it only cleans up once the nest revokes it and it drops from the projection. **Mechanism completion (built 2026-07-17):** a revoked selector's name has *left* the matrix, so a purely matrix-name-scoped visit could never reach it — the pass therefore visits **desired ∪ remembered** names, where `DnsConfig.dkim_published_names` (per domain, `#[serde(default)]`, sole writer = the machine's managed publish) remembers the names this client previously managed; after each converge the memory is rewritten to the still-desired names plus any name whose withdraw could not be verified (so failures retry on the next publish). Only Fauna-once-desired names are ever visited — the memory is what makes revoked-selector cleanup possible *without* a zone-wide `_domainkey` sweep (which would clobber a third-party mailer's DKIM TXT at the same domain, e.g. an ESP selector) and *without* nest-side revoked-selector tombstones (rejected as a heavier nest+wire change contradicting the client-held custody framing; `delete_dkim_selector` keeps deleting the row outright). The memory lives beside the credential that did the publishing — same custody, same sync story. Only values carrying `p=` are withdrawn, and value comparison is quote-insensitive but case-sensitive (base64 `p=` bodies). **Custody + mode scope:** this runs **client-side** (the nest never holds the DNS-provider credential — § Where the credential lives — so a *nest* reconcile loop like the rejected `dns_provider_credentials` design is infeasible) and only for **managed-mode** domains (a covering credential exists). For **manual-mode** domains — **every domain today, including example.com** (`mode` is `"manual"` for all, § Implementation status today) — there is no credential, so **no client automation is possible**; the floor is **deploy-verify gate 6** (a dedicated dev-fleet checker / `build-system.md` § Verifying a deploy), which detects a stale published `p=` at every deploy. (A later generalization may extend the converge-withdraw to other body-edited records — SPF/DMARC — but only with the same exclusive-name slot scoping; a whole-matrix withdraw is rejected.) **Second slot — the ATProto handle TXT (built 2026-07-24).** That anticipated generalization landed for `_atproto.<handle>.<primary>` (§ Records covered): the mechanism is now one pass parameterized by a **slot descriptor** (`fauna-client-dns::reconcile_exclusive_txt_slot` over `TxtSlot { label, marker }`), with `reconcile_dkim_txt` (marker `p=`) and `reconcile_atproto_txt` (marker `did=`) as its two callers and a sibling memory `DnsConfig.atproto_published_names` — one implementation of the desired-∪-remembered rule rather than two copies of it. The withdraw case here is a **rename** rather than a value edit: the ATProto handle is derived at read time, so a rename re-derives the row under a new name and the old name leaves the matrix, which is precisely the shape the remembered set exists to reach. Leaving it published is not merely untidy — it fails *closed* for the renamed user (the DID document's updated `alsoKnownAs` no longer claims the old handle, so the bidirectional check fails), but when a later user claims the freed Fauna handle the create-only publish adds a **second** `did=` at that same name, and an ambiguous handle never resolves, stranding the new user's repo behind the bridge's first-emit gate. Withdrawal is scoped exactly as DKIM's is — Fauna-known names only, and within them only values carrying the slot marker — so a foreign verification token parked at the same name survives. The pass is **not** primary-gated despite the rows only appearing on the primary today: a secondary's desired ∪ remembered is empty (zero provider calls), while a domain that ever stops being primary still converges its remembered names to removal. **Manual-mode residual:** as with DKIM this is client-side + managed-mode only, so for today's all-manual domains no automation is possible and a stale `_atproto` TXT persists until the admin removes it by hand; unlike DKIM there is **no deploy-verify gate** covering it yet (gate 6 checks `p=` only). **Third slot — the `_fauna` identity root (built 2026-08-12).** `reconcile_fauna_self_txt` (marker `self=`, memory `DnsConfig.fauna_self_published_names`) is the third caller of the same pass, and its withdraw case is the third distinct shape: neither a value edit under a stable name (DKIM) nor a name that moves (ATProto), but a **deployment-seed rotation** — the nest derives `self=` from its live deployment key at every matrix read, so after a rotation the value differs at a name that never moved. The create-only loop asks only whether the name exists, finds that it does, and would leave the **superseded** identity published beside the successor — where a fresh app resolving the zone is free to pin a dead identity, defeating the record's whole purpose (`../architecture/nest/tls-certificates.md` § E). Here the remembered set is **not** what makes the withdraw reachable (the name is in the matrix throughout); it carries the slot for a domain that stops being primary, and for retrying a withdraw that failed. ⚠ **One thing differs materially from the other two slots and must not be "simplified" away:** `_fauna.<domain>` is **not** a Fauna-exclusive *name* — it is the deployment's shared Fauna TXT node, whose grammar also carries `subhandles=` and `cache=` (`fauna_core::resolve::resolve_handle`). The marker scoping is therefore the *only* thing preventing this pass from deleting a sibling Fauna key; a name-scoped sweep here would be a data-loss bug, not merely an over-reach. Same manual-mode residual as the other two slots, with no deploy-verify gate.
- **The page** shows each record with a managed/green status; the admin does nothing. A publish failure (revoked token, provider 5xx, zone not found) surfaces as a per-record error with a "re-enter credentials" affordance — it does **not** silently fall back to manual.

### Manual + live verification

The default when no admin client holds usable credentials for the domain. When on:

- **Render every record** — name, type, value, TTL — from the same shared builders the managed path publishes (§ Records covered). The value shown is byte-identical to what Fauna would publish.
- **Live red/green per record.** Nest resolves the record against **public** DNS (a recursive resolver, not the provider API) and compares the observed value to the expected one, yielding `ok` (green) / `missing` / `mismatch` (red) / `checking`. The check runs on page load, on demand ("re-check"), and on a slow background cadence. Resolution happens **nest-side** (the client may sit behind split-horizon/LAN DNS that would lie). See § Live verification.
- The admin copies records into their own provider; rows flip green as DNS propagates. No record is a hard gate — the admin is never blocked from proceeding by a not-yet-green row (DNS propagation can lag hours); green is informational truth, not a lock.

## Where the credential lives (client-held, never on the nest)

**The credential is persisted client-side — built 2026-05-25, resting on the account-state plane since 2026-10-02 (§ Storage below; this paragraph said "captured during onboarding and then discarded" until 2026-10-02, which had been true only before the build).** Onboarding still captures the credentials into the wizard-only `DnsConfigState.creds` (`onboarding.md` § DNS configuration) and never writes a store itself; the onboarding machine hands the verified credential to the launched client (`OnboardingMachine::captured_dns_credential()`), and the client seals it through the DNS machine's own `PutCredentials` path (`fauna_client_dns::dispatch_seal_captured_dns_credential`) on its first authenticated run — every app shell drives that hand-off, and `tests/e2e-unified/tests/test_admin_dns_managed.py` proves the persisted credential end to end. So `mail-multidomain.md` § Adding a new local domain's reuse of "the deployment's existing DNS-provider credentials", unsatisfiable while nothing persisted, is satisfiable: any of the admin's clients can act on the credential for the deployment's lifetime. A bundled provider's credential (`../architecture/provisioning/bundled-provider-api.md`) is the same shape — its `base-url` and hosted-auth token are two ordinary provider fields — persisted, re-verified and revoked exactly like every other provider's; nothing in this doc is bundled-specific.

**The nest never holds, receives, or can decrypt the DNS/VPS-provider API key in plaintext.** This is a deliberate invariant, not an implementation convenience:

- **The client already does everything onboarding needs with these keys, and keeps doing it afterward.** `libs/fauna-provisioning`'s `DnsProvider`/`Registrar` run client-side (UniFFI on native, WASM on web — `fauna-onboarding-machine`), and the *initial* publish happens from the admin's client at onboarding, before the nest even exists. Anything doable from the client at onboarding stays doable from the client afterward; the nest coming into existence must not relocate the credential or the publish operation onto the nest.
- **The running nest has no autonomous DNS-write need.** A nest acquires its trusted cert either by **HTTP-01** ACME, which it serves itself on its own public port and which writes no DNS at all (`bins/fauna-nest/src/acme_http01.rs`), or by a **client-published DNS-01** challenge — the admin's client publishes `_acme-challenge` and the issued cert is sealed back to the nest ([`../architecture/nest/tls-certificates.md`](../architecture/nest/tls-certificates.md) § B owns the tiering, including which nests can use which). Either way **the nest is out of the DNS-write path** (the client-driven DNS-01 order cores are built, native + wasm — owner: `tls-certificates.md` § B / § Implementation status). There is **no hand-run DNS bootstrap** — the VPS is cloud-inited to start the container automatically (no human runs a CLI), and **all** DNS is published by the admin's client (which holds the keys); the deploy-time Go `fauna-dns` bootstrap binary was **removed**. There is therefore nothing the nest must do with the registrar key unattended — the earlier "the nest must use it autonomously to publish/reconcile" rationale was false.
- **Storage: the account's DNS record — one account-plane row, `fauna.state.dns` — not a new folder.** The credential lives in the admin's DNS record (`DnsConfig`, `libs/fauna-core/src/data.rs`): a `Vec` of credential records (provider id + the provider's token/key fields + the cached `verify()` zones + a label) plus a per-domain managed-mode set (see § The two modes) and the rest of this doc's client-held DNS state (delegations, the auto-renew opt-outs, the remembered published names, the persisted ACME account and an interrupted manual issuance). It is one row per account on the fleet-only rung, sealed under the account's generation tip (`../architecture/account-data-taxonomy.md` § The audience ladder places it; `../architecture/config-dissolution.md` owns the kind's registration and its move off the `__config` blob, where it was born as `UserConfig.dns`), so it is **nest-opaque**: the nest stores and relays sealed bytes it cannot read, and the DNS-credential invariant above holds with no new nest handler and no reserved folder. Every one of the admin's apps (laptop, phone, web) reads the same record through its account runtime (`AccountStoreHandle::{dns, write_dns}`), synced across the account's devices by the account plane. **One store, one writer:** the `DnsManagementMachine` is the sole writer, through its `DnsStore` seam (`fauna_client_dns::AccountDnsStore` over the seat's account-store handle). The record is one whole-record latest-wins row, so a write replaces what is stored: every write re-reads the record immediately before it writes, never writing back a copy read before a provider round-trip or an ACME order. Onboarding does **not** write it directly — it has no account runtime at the DNS step and, in the fresh-provision path, no live nest; instead the onboarding machine *captures* the verified credential and exposes it (`OnboardingMachine::captured_dns_credential()`), and the **launched client** seals it via the machine's `PutCredentials` path on first authenticated run, the store waiting for the account runtime that sign-in starts (`onboarding.md` § 4). So the credential still *originates* from the onboarding DNS-step capture, but the write is the machine's, not a second seal path in onboarding (priority #2).
- **Never returned in a client *read* either.** The nest's DNS read surface (`fauna.dns.list_records`) never carries the token; the page shows "credentials present for provider X / zone Y" from local client state. The token is decrypted only inside the client that publishes.
- **Scope.** One credential record per (provider, set of zones the token covers). A domain is Fauna-manageable iff some held credential's `verify()` (run client-side) reports a zone covering it. This is exactly the check `mail-multidomain.md` § Adding a new local domain step 2 ("DNS provider check") needs — now backed by real client-persisted state. Clearing credentials flips affected domains back to manual.

## Records covered

The unified surface enumerates, **per domain**, every record the deployment needs. The **bodies are defined elsewhere and referenced, never re-defined here**:

- **Mail records** — `MX`, `SPF`, `DKIM` (per selector × algorithm), `DMARC`, `MTA-STS` TXT, `TLSRPT`: bodies + publication lifecycle per `mail-multidomain.md` § Per-domain DNS records (the `dns::per_domain::build_{mx,spf,dkim_txt,dmarc_txt,mta_sts_txt,tlsrpt}_record` builders). The DKIM TXT specifically is the unsealed `public_dns_value` from `mail-bridge-lifecycle.md` § DKIM provisioning UX (served via `fauna.bridges.list_dkim_selectors`). The deployment also publishes one **automatic, cert-coupled `DANE`/TLSA** at `_25._tcp.mail.<primary>` while the MX is on the self-signed floor (host-level builder `dns::host::build_mail_tlsa_record`, withdrawn once a trusted cert covers the MX — `mail-multidomain.md` § Per-domain DNS records + `../architecture/nest/tls-certificates.md` § D); it is **not** an admin opt-in. In **managed** mode the floor-MX TLSA is auto-published **and withdrawn** by a dedicated, primary-only, best-effort converge pass (`fauna-client-dns::reconcile_floor_mx_tlsa`) — kept out of the generic create-only loop because it needs withdrawal, Cloudflare needs a structured `data` body, and a provider without TLSA (Namecheap) would otherwise abort the publish (`tls-certificates.md` § Implementation status today, the "Self-signed-MX DANE/TLSA" row). The **withdraw also fires immediately** when the primary's served cert is observed to flip **floor→trusted** (the `fauna.tls.cert_status` / `RefreshCertStatus` observation drives `reconcile_floor_mx_tlsa` via `withdraw_floor_mx_tlsa_on_trust`, not gated on the managed opt-in since the TLSA is automatic+cert-coupled — same row), so a stale floor-key pin can't keep DANE-hard-failing senders until the next managed re-publish. **PTR** alone is *shown/verified* but never zone-published (it is set at the IP owner via `vps.set_ptr`).
- **CalDAV autodiscovery** — `_caldavs._tcp.<domain>` `SRV` → `0 1 443 mail.<primary>.` (RFC 6764 § 4), one row per local domain, so a stock CalDAV client (macOS Calendar.app *automatic* setup) given only the bare domain finds the CalDAV host without the apex cross-host-redirect dance macOS declines. The target is the deployment's single CalDAV/mail host `mail.<primary>` (= the `MX` target — every domain's CalDAV is served there via SNI). Body + rationale per `caldav-server.md` § Network exposure — SRV autodiscovery (the `dns::per_domain::build_caldavs_srv_record` builder).
- **CardDAV autodiscovery** — `_carddavs._tcp.<domain>` `SRV` → `0 1 443 mail.<primary>.` (RFC 6764 § 4), a per-domain sibling of the CalDAV SRV, so a stock CardDAV client (macOS Contacts.app / DAVx5 *automatic* setup) given only the bare domain finds the address-book host. Byte-identical to the CalDAV record save the service label — the same MDA serves CardDAV (`/carddav/{user}/`) on the same `mail.<primary>:443` (`caldav-server.md` § Network exposure — the 2026-07-06 CardDAV-served flip; the `dns::per_domain::build_carddavs_srv_record` builder). TLS-only (`_carddavs`, no plaintext `_carddav`). A standing matrix row exactly like `_caldavs`, **now emitted** by `build_domain_dns_records` (Slice 3) — the per-deployment `carddav_enabled` toggle gates the live service + the apex `/.well-known/carddav`, not the offered DNS row.
- **Nest-host records** — `A`/`AAAA` for the apex `<primary-domain>` (the nest / WS-RPC-web endpoint) **and** `mail.<primary-domain>` (the `MX` target), per `onboarding.md` § Nest provisioning (the orchestrator already creates the apex `A` at provisioning). Surfaced here for verification even on the manual path. **The two names may resolve to different addresses** — the mail server (`mail.<primary>`) can be a separate box from the nest, so the host address is persisted as **two** addresses (nest / mail), not one (memory `mail-host-ip-distinct-from-nest-ip`). The address is **public, not a secret** (unlike the DNS-provider credential, which stays client-held), so it lives nest-side as plaintext state, persisted via the `fauna.dns.set_host_address` onboarding hand-off (§ Implementation status today); record *names* are derived from the primary mail domain, only the IPs are persisted.
- **`PTR`/rDNS — advisory only.** Reverse DNS is set at the **IP host / VPS provider** (the address's owner), **not** in the domain's DNS zone, so it is generally **not auto-publishable** through a zone-API credential and not all VPS providers expose an API for it. The page shows the expected `PTR` value and verifies it (forward-confirmed rDNS matters for inbound acceptance — `smtp-server.md` § FCrDNS), but treats it as an admin-action advisory with a "set this at your VPS provider" note, never as a Fauna-managed record. (If the VPS provider's API does support rDNS and its credentials are stored, a later phase may manage it; out of scope for v1.)
- **`relay.<primary-domain>` `A`/`AAAA` — the P2P relay sidecar's host record, gated on the `iroh_relay` service.** When the nest runs its self-hosted iroh P2P relay (`services.json iroh_relay` — the image's own runtime gate for the sidecar `bins/fauna-iroh-relay`, set by the artifact and by no person: [`p2p.md`](p2p.md) § The relay, which also records that nothing sets it yet), `relay.<primary>` `A` (and `AAAA` when an IPv6 is set) points at the **nest** address (the same `nest_*` IP as the apex, **not** `mail.<primary>`), because the relay's HTTPS listener is SNI-routed through `fauna-sni-router` on the nest's :443 (`../architecture/transport.md` § Future directions). Built by the host-address builder (`fauna_mail::dns::host`, gated on the flag the nest passes via `dns_handlers::append_host_records`), surfaced here so the admin of a nest that runs the relay sees the `A` record they must publish. **Load-bearing coupling:** the matching `relay.<apex>` SAN on the apex managed cert is added to the ACME order **only once this record resolves** (`acme_http01::relay_san_included`) — an ACME order is all-or-nothing, so adding an unresolvable name would fail the *whole* apex order and take apex HTTPS down (`../architecture/nest/tls-certificates.md` § HTTP-01). Surfacing the record here is what tells the admin to make it resolve; until then the relay serves on the self-signed floor cert (which carries `relay.<apex>` unconditionally — `../architecture/nest/tls-certificates.md` § A), so LAN/floor serving never waits on the `A` record. **The nest never publishes it** — the client does, like every other record.
- **`pds.<primary-domain>` `A`/`AAAA` — the ATProto PDS bridge's host record, gated on an approved `atproto.pds` bridge.** The second instance of the *same shape* as `relay.<primary>` above, and it obeys every clause of it: the record points at the **nest** address (the bridge's XRPC listener is SNI-routed through `fauna-sni-router` on the nest's :443, `pds.*` → the bridge's loopback port), it is built by the same host-address builder (`fauna_mail::dns::host`, gated on the signal the nest passes via `dns_handlers::append_host_records`), the nest never publishes it, and the matching `pds.<apex>` SAN joins the apex ACME order **only once this record resolves** (`acme_http01::pds_san_included` — the relay SAN coupling applies verbatim; until then the PDS serves the self-signed floor cert, which carries `pds.<apex>` unconditionally). The gate is *an approved `atproto.pds` bridge service user exists* — the role is never auto-approved, so an approved row means an admin deliberately stood the bridge up. Scope + rationale for the PDS hostname: `atproto-pds-full.md` § Wire & process topology.
- **`_atproto.<handle>.<primary-domain>` TXT — the ATProto handle-verification record, one per ACTIVE hosted identity.** Name + value (`did=<did>`) are owned by [`atproto-pds-bridge.md`](atproto-pds-bridge.md) § Handle (built by `fauna_protocol::atproto::handle_verification_txt`); the nest appends the rows to the **primary** domain's matrix only, deriving each handle **at read time** from the user's current Fauna handle. In managed mode the generic create-only publish covers the create side with zero client change, but the withdraw side needs the dedicated converge pass below: because the handle is derived rather than stored, a **rename** moves the row to a new name and the old name leaves the matrix entirely, stranding the TXT it already published. A pending mint (no DID yet) and a non-public primary emit no row at all.
- **Wildcard `*.<primary-domain>` `A`/`AAAA` — the per-user subdomain web-hosting record.** When the deployment offers per-user subdomain sites (`<handle>.<primary>`, opt-in — `web-content-hosting.md` § Routing + Architectural rule 8), **one** wildcard `*.<primary>` `A` (and `AAAA` when an IPv6 is set) points every user subdomain at the nest. It resolves to the **nest** address (the same `nest_*` IP as the apex, not the `mail.<primary>` IP), since subdomain web content is served by the nest, and is what lets the nest answer the per-subdomain HTTP-01 ACME challenge at `http://<handle>.<primary>/.well-known/acme-challenge/...`. It is a **steady-state** row (unlike `_acme-challenge`): published once, kept correct. Published by the admin's client like every other record — **the nest never writes it** (the nest-never-writes-DNS invariant); a per-subdomain *wildcard cert* is explicitly **not** used (that would need forbidden DNS-01) — each subdomain gets its own per-name HTTP-01 cert via the existing `MultiDomainCertResolver` lifecycle (`web-content-hosting.md` § Custom domains and TLS). Surfaced here for verification on both modes; bodies/derivation are the host-address builder's (`fauna_mail::dns::host`) nest IP, the same source the apex `A` uses.
- **`_fauna.<domain>` TXT `self=<nest_actor_id>` — the public-domain identity root.** The record a *fresh* app resolves to learn which nest identity to expect **before** it has anything pinned; `../architecture/security.md` § Transport trust, Axis 2 owns its place in the trust model, and the read side is `fauna_core::resolve::lookup_fauna_txt` / `fauna-anon-client`'s `resolve_dns_self_root`. Emitted on **every public active local domain's** matrix — primary *and* secondary — and **skipped per domain when that domain is non-public**: the reader classifies loopback / IP-literal / `.local` as having no DNS authority and returns `None` there, so the row would be unconsultable (the gate is evaluated per domain, never inherited from the primary). ⚠ **Per-domain, deliberately unlike `_atproto` and the wildcard** (ruled 2026-08-13, reconciling this bullet with `../architecture/nest/tls-certificates.md` § E, which had always read "per domain"): those two are primary-only because their *names* derive from something that exists only on the primary — handles are minted there, and per-user subdomain sites are served there — whereas this row's value is the **deployment's** identity, the same answer at every domain of one box. A secondary is a client entry point *by construction* (it gets its apex `A`/`AAAA` → nest for exactly that reason, and that apex joins the ACME order under the same heading, both above), so scoping the row to the primary made a user's trust posture depend on which of the box's domains their handle happened to sit on, with no principled basis. Widening is a **name-set change, not a semantics change** — the value is byte-identical on every domain — and it needed no client change: the managed converge pass already resolves the covering credential and zone *per domain*, so a secondary publishes into its own zone. **Scope boundary: "local domain" means an active local *mail* domain, never a user's custom web domain** (`web-content-hosting.md`) — those are user-owned names that are not this nest's identity apex, and `_fauna-verify.<domain>` is their separate ownership-proof record. The value is derived from the **live** deployment key at every matrix read, never stored, which is what makes a deployment-seed rotation move it with no migration. Two consumers depend on it: the self-signed floor's fresh-client acceptance on a public domain (`../architecture/nest/tls-certificates.md` § E) and the rotation ceremony's post-flip re-publish (`../architecture/nest/box-recovery.md` § Deployment-seed rotation → *DNS row and the propagation window*). In **managed** mode it is published by a **dedicated withdraw-aware converge pass** (`fauna-client-dns::reconcile_fauna_self_txt`, remembered in `DnsConfig.fauna_self_published_names`), *not* the generic create-only loop: a rotation changes the value at a name that never moves — the create-only loop asks only "does this name exist?", sees that it does, and would leave the **superseded** identity resolvable beside the successor, free for a fresh app to pin. ⚠ **The withdrawal is scoped to values carrying `self=`, and that scoping is load-bearing in a way DKIM's and `_atproto`'s is not:** `_fauna.<domain>` is a **shared** Fauna TXT node whose grammar also carries `subhandles=` and `cache=` (`fauna_core::resolve::resolve_handle`), so a name-scoped withdraw would destroy a sibling key. Never widen it to a namespace sweep. **Ruled with the per-domain widening (2026-08-13):** that same `resolve_handle` bare-domain arm treats `self=` at a name as *the actor id for that domain*, so publishing on a secondary makes `@secondary.example` resolve to this nest's actor. That is **correct, not a corruption** — a secondary local mail domain is a nest-owned apex, so "which actor is this domain" genuinely answers "this nest", exactly as it already did on the primary. (The arm has no production callers today; the ruling is recorded so lighting it later needs no re-derivation.) **Two adjacent facts a maintainer must not miss:** `_fauna-verify.<domain>` is a *different* record (custom-domain ownership proof — `web-content-hosting.md`), and **tui and web dispatch `DnsAction::Publish` from nowhere at all** (only linux/windows/android/macos/ios do, off the managed-mode flip), so on those two apps this row — like every other managed row — is published only once that gap closes.
- **`_acme-challenge.<domain>` TXT — transient, published only during a DNS-01 cert order.** When a nest behind NAT (or a no-API-registrar public domain) cannot use HTTP-01, a publicly-trusted cert is obtained via a **client-published DNS-01 challenge**: the admin's client (which holds the provider key) publishes the `_acme-challenge.<domain>` TXT carrying the order's key-authorization digest through this same managed/manual path, the CA validates, and the record is torn down. It is therefore **not** a steady-state row the red/green check nags about — its absence between renewals is correct, not drift. In managed mode the `DnsManagementMachine` publishes it automatically; in manual mode the page shows it to paste, or a **one-time CNAME delegation** (`_acme-challenge.<domain>` CNAME → a zone the managed credential controls) automates recurring renewals after the single manual step. The delegation target follows the **re-homing convention** `_acme-challenge.<domain>.<controlled-zone>` (the challenge name re-rooted under the controlled zone — the renewal TXT is published there and the CA follows the CNAME); it is persisted in `DnsConfig.delegations` (a `CnameDelegation` per delegated domain, written by the machine's `DelegateRenewal` / `RemoveDelegation` actions — the same single-writer pattern as the credential store) and surfaced for the admin via `DnsSnapshot.delegations`. The full cert-acquisition tiers + lifecycle (including the convention rationale) are owned by [`../architecture/nest/tls-certificates.md`](../architecture/nest/tls-certificates.md) § B; this surface only enumerates the record. **The nest never publishes it** — the nest-never-writes-DNS invariant holds (the client publishes; the issued cert ships back to a private nest over namespace-sync).

The exhaustive per-record-type list, expected-value derivation, and the `MTA-STS` HTTPS policy-file caveat (which is an HTTPS endpoint, not a DNS record, but is part of "MTA-STS works") live in the design doc's record-matrix section.

## Live verification (revises "nest doesn't poll DNS")

Nest **does** resolve public DNS to produce the per-record red/green truth. (An earlier `mail-multidomain.md` had the admin confirm DNS by hand and the nest believe it; that text is gone, and this section is the model.)

- **Verification is the displayed truth, not a gate.** Nest resolves and reports `ok`/`missing`/`mismatch`/`checking`; the admin sees real status instead of a blind "I did it" button. But the admin is **never blocked** from proceeding (adding a domain, finishing onboarding) by a not-yet-green record — propagation lag must not strand the admin. **There is no manual-confirm control (ruled 2026-10-01):** live status replaced the "I've set these" button rather than joining it — nothing is gated on DNS, so a confirmation would release nothing, and nothing nags, so there is nothing for it to silence (`mail-multidomain.md` § Wizard steps, step 2). Until then this bullet kept the button "alongside live status"; no app, element id or stored flag ever carried it.
- **Resolution is nest-side, public-recursive.** A recursive resolver (not the provider API, not the client's stub resolver) so the answer reflects what peer MTAs and the public Internet actually see. The web-content domain-verification check (`bins/fauna-nest/.../web_content/domain.rs::check_dns_txt`) is now backed by this same shared `DnsVerifier` (the always-`false` placeholder is gone); see `docs/goal/behavior/web-content-hosting.md` § Registration and DNS verification.
- **What "correct" means per record** is exact-match for the value Fauna would publish, with type-appropriate normalization (TXT segment joining, trailing-dot/case for names, MX priority+target). Defined precisely in the design doc.
- **One deliberate exception to "public-recursive": the DNS-01 propagation probe.** `fauna.dns.probe_txt_visible` (Admin) resolves **authoritative-direct and non-recursive**, because a recursive resolver negative-caches a miss for up to the zone's SOA minimum and so cannot decide whether a *freshly published* ACME challenge TXT is live yet. It exists for the web app, which has no raw DNS in the browser and would otherwise validate blind. Different question, therefore a different resolver — the record-matrix verdicts above stay recursive. Owned by `../architecture/nest/tls-certificates.md` § The browser's arm of the propagation gate.

## Where logic lives

Per priority #2, shared Rust by default; per-app shells render + dispatch only.

- **Shared Rust (`libs/fauna-*`)** — a `DnsManagementMachine` (snapshot + dispatch, mirroring `DeliverabilityMachine`/`MailSettingsMachine`): renders the per-domain record matrix + statuses + mode; reads `fauna.dns.{list_records,verify_records}` from the nest; and **runs the credential store + publish/reconcile client-side** — it seals/loads the provider credential in the admin's synced `BackupKey`-sealed store and drives `libs/fauna-provisioning`'s `DnsProvider` to publish. The *expected* record values come from `libs/fauna-mail` builders via the nest read; the provider *publish* runs here, on the client.
- **Nest** — **read/verify only:** the record-matrix assembler (`fauna.dns.list_records`) and the public-recursive-resolver verify surface (`fauna.dns.verify_records`), both Admin-only WS-RPC. The nest **never** stores or sees a provider credential and **never** publishes — there is no nest credential table and no nest reconcile loop (retired; see § Where the credential lives).
- **Per-app** — render the snapshot, dispatch actions; no DNS logic in any shell.
