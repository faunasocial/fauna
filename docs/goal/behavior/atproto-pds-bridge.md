## Goal

The nest can host an **ATProto PDS** for its users: mint a DID, hold the user's ATProto repo, sign repo commits, serve the `com.atproto.sync.*` / `com.atproto.repo.*` read surface, and emit a `subscribeRepos` firehose — so the user's *public* Fauna posts appear natively on the Bluesky network and the user is followable from any Bluesky client. The pitch: **Fauna isn't "an app that logs into your Bluesky account" — Fauna *is* your Bluesky home server.**

This is "Approach B (Run a PDS)" from the 2026-03-17 ATProto integration review and "Phase 5: ATProto bridge" from the interop-strategy review (both tracked internally). The 2026-03-17 review *deferred* it in favor of write-through; this doc revisits that with mitigations (Go + indigo, the projection model, did:web reusing mail's DNS, out-of-process) that materially lower the cost the review assumed.

## Relationship to the consume-side Bluesky bridge (`bridges.md`)

`docs/goal/behavior/bridges.md` (§ "Bluesky bridge — current behavior") documents the **consume** direction: the user OAuth-links their *existing external* Bluesky account, reads feeds/DMs, and optionally cross-posts (`write_through`) by calling `com.atproto.repo.createRecord` **on the user's external DID repo** (`bridges.md` § Interactions / § Cross-posting).

This doc is the **host** direction. The two are **alternative identity backings** for one Fauna user's ATProto presence, and must not be confused:

| | Consume (bridges.md) | Host (this doc) |
|---|---|---|
| ATProto identity | the user's **external** DID, hosted on bsky.social's (or another) PDS | a **Fauna-hosted** DID, repo on the nest |
| How it's set up | OAuth link of an existing account | mint a DID at enable-time |
| Writes (`createRecord`) | XRPC call to the external PDS | **local** repo append on the nest |
| Cross-posting | the explicit `write_through` path | subsumed — public posts *are* the repo (see § Projection) |

**Non-contradiction anchor:** `bridges.md`'s interaction/cross-post semantics still hold; only the *write target* differs (external XRPC vs. local repo append). The PDS-host model **subsumes** `write_through` — there is no separate "cross-post" step, because a user who hosts a PDS has their public posts projected into their own repo directly. A Fauna user picks **one** backing; the read/interact surfaces (feeds, DMs, notifications) are shared plumbing regardless of which backing supplies the identity.

## Architecture

- **Out-of-process Go bridge, on the mail-bridge model** — *not* the current in-nest `bluesky` cargo feature (`bins/fauna-nest/src/bluesky/`, compiled into the nest binary). A PDS that holds repos + signing keys + a firehose must be a separate supervised process so it never contends with the core nest. Role name `atproto.pds` (the architecture docs already anticipate `atproto.federation` / `atproto.firehose` — `mail-bridge-lifecycle.md:91`, `:263`; `apps/bridges.md:30`).
- **Built on [`indigo`](https://github.com/bluesky-social/indigo) Go primitives** — `atproto/repo/mst` (Merkle Search Tree), `atproto/repo`, `atproto/atcrypto`, `atproto/identity`, generated `com.atproto.*`/`app.bsky.*` lexicon types, `atproto/lexicon` validation. These are Bluesky's own production libraries; the bridge does **not** hand-roll MST/CBOR/signing. The genuinely-new build is CAR export + carstore + `subscribeRepos` emission + the XRPC read server (indigo's relay code is prior art, not a drop-in library).
- **Go-vs-Rust re-surveyed 2026-07-19 — decision stands (Go + indigo; user-confirmed same day); revisit trigger below.** The original premise ("no production-grade Rust stack covers PDS hosting") is now only partly true: a modular crates.io library family (`atproto-repo`/`-dasl`/`-identity`/`-plc`/`-lexicon`, coordinated 0.14.5 release 2026-04-02) covers MST + signed commits, CARv1 + exact-CID dag-cbor, did:plc operations (both curves, rotation keys), and lexicon validation in embeddable form, and production Rust PDSs exist (Tranquil — AGPL, application-shaped, not embeddable; Blacksky's rsky — pre-1.0, application-shaped). Still true: **no reusable Rust library serves the `com.atproto.sync.*`/`repo.*` surface or emits a server-side `subscribeRepos` firehose** (hand-roll on either path), the `atproto-*` family is 0.x / single-maintainer / not production-proven, and indigo remains actively maintained and battle-tested at network scale — so Go+indigo stays the lower-risk choice, with the protocol *translation* logic in shared Rust regardless (§ Where logic lives). **Revisit trigger:** re-survey before starting S3, or earlier if the `atproto-*` family reaches 1.0 or ships a production PDS — at that point an all-Rust bridge (those crates + an in-house sync/firehose serving layer) becomes a genuine alternative worth a fresh decision.
- **Fauna-authoritative, one-way derived projection.** Fauna stays the source of truth. A new public Fauna post → translate → append to the MST repo → sign the commit → emit firehose. **No bidirectional sync.** Inbound interactions (a Bluesky user replies/likes) bridge in as "via Bluesky" content (the existing DM/feed plumbing), **never** as authoritative writes to the repo. This eliminates the review's "dual store + bidirectional sync" cost (the 2026-03-17 review; tracked internally); the residual is storage duplication (cheap) + blob re-hashing (BLAKE3/FastCDC → sha256-CID) + tombstone translation.
- **Enrollment + lifecycle = the mail-bridge contract verbatim** (see § below). The PDS bridge is just another `fauna.bridges.*` peer.

## Identity: DIDs and handles

### DID method — did:plc default, did:web opt-in

A Fauna user's hosted ATProto identity is one DID, of one method (the methods are **mutually exclusive** — the method is encoded in the DID string; you cannot have both, and migrating between them is a new identity, not a swap).

- **`did:plc` (default, recommended).** Portable across PDSs; has **rotation keys + an auditable log**, so a leaked signing key is *recoverable* and takeover is *detectable*. PBC operates the PLC directory, but that is an **availability** dependency, **not custody** — with your rotation keys held, PBC can neither seize nor forge your identity.
- **`did:web` (opt-in).** Fully self-contained in the domain, **no third-party directory in the resolution path** — but tied to the domain forever, with **no recovery primitive** (domain compromise = permanent identity loss). Also heavier to host: requires serving `/.well-known/did.json` over HTTPS at the user's subdomain (per-user cert / wildcard).

The default is did:plc because the lighter handle infra (one TXT record, below) and the recovery story both point the same way. did:web is for the "nothing from PBC in the path, ever" user who accepts the no-recovery trade.

### Handle — derived from the Fauna handle

The ATProto handle is **auto-derived** from the Fauna handle: `alice@example.com` → `alice.example.com` (`@`→`.`). Same identity, same domain — no synthetic handle. The opaque DID string is never shown; users see the handle.

Verification reuses the mail-stack DNS automation (the client holds the DNS-provider keys and publishes records, per [`dns-management.md`](dns-management.md)):

- **did:plc handle** verifies via a single `_atproto.alice.example.com` **TXT record** → the DID. No HTTPS serving, no per-user cert.
- **did:web** additionally needs `/.well-known/did.json` over HTTPS at the subdomain (wildcard cert + per-Host serving).

Edges to handle: (1) **reserve infra subdomains** — handle localparts share the subdomain namespace with per-user web hosting, so derivation reuses the same consumption gate (`fauna_core::web::RESERVED_SUBDOMAIN_LABELS` — `mail`, `mta-sts`, `app`, `www`, `relay`, `pds`; `_atproto`/`_`-prefixed names are charset-impossible as handles, and the apex is not a localpart case); (2) localparts with dots / plus-addressing / underscores / unicode are **structurally impossible** for stored handles (`fauna_protocol::handle::validate_handle` constrains every registrable handle to `[a-z0-9-]{3,63}`, no edge hyphens — every storable Fauna handle is already a valid ATProto handle label), so derivation rejects only raw/claim-era input defensively; (3) **deferred niceties:** apex-as-handle for single-user nests (`example.com` itself), and custom external-domain handles (requires the user control that domain's DNS — breaks out-of-box).

**Handle changes follow the Fauna handle.** The ATProto handle is *derived at read time* from the current Fauna handle — never frozen at mint. A Fauna handle or domain change re-derives, republishes the `_atproto` TXT **and withdraws the one at the old name** (the withdraw is a managed-mode client converge pass, since only the client holds the DNS credential — mechanism owned by [`dns-management.md`](dns-management.md) § Fauna-managed → *Withdraw-aware convergence*), updates the DID document's `alsoKnownAs`, and emits an `#identity` firehose event so the network re-resolves. did:plc absorbs this natively (one more reason it is the default); did:web is domain-bound and cannot follow a domain change — surface that limit in the did:web opt-in copy.

## Disable & revocation

Three revocation layers, all now specified (layer 2 ratified 2026-07-22; layer 3 restated for the full PDS 2026-07-23):

1. **Bridge-level (specified — inherited).** The admin revokes the bridge service user exactly as for mail: the lifecycle contract's revocation teardown applies verbatim (bearer revoked, socket force-closed, `whoami` denied at the capability gate, graceful drain — `mail-bridge-lifecycle.md` § revocation). A revoked bridge also loses its sealed key blobs: the per-user DID signing/rotation keys are sealed to *its* attested x25519, so revocation severs key custody at the same stroke.
2. **Per-user (RATIFIED 2026-07-22, user).** Stepping down from a hosted level (the [`../ui/atproto.md`](../ui/atproto.md) depth selector's downward transitions) = **reversible deactivation**: projection stops immediately (per the product invariant that user-facing data shapes are user-revocable from the user's own app), the repo is no longer served, an `#account` (deactivated) firehose event is emitted, and — wording per C8, covering future surfaces — the account's **entire ATProto presence is suspended**: live app sessions are killed and OAuth grants suspended (rows kept, listed, individually revocable), never only projection. The DID and sealed key blobs are **retained**; re-enabling restores the same identity with no data loss. Destruction is a **separate, stronger action — "Delete my Bluesky presence"**: a full `deleteRecord` sweep of the projected records (still reversible in identity terms), inside which did:plc users get an explicit opt-in "also permanently retire this identity" (PLC tombstone — terminal, unrecoverable), never performed implicitly. Deactivation semantics landed in S4-D (2026-07-23 — bridge unserve + `#account`, see § Implementation status); the sweep landed in S5 slice 5 (2026-07-29, below); the selector UX that invokes them is owned by [`../ui/atproto.md`](../ui/atproto.md).

**The sweep's shape (S5 slice 5).** The user's confirm records a durable **tombstone in nest** (`atproto_identities.status = 'deleted'`), tears down the account-side halves (sessions revoked, the D10 authoring credential destroyed) and drops the integration level to `off` — a selector left parked on a hosted rung would offer to restore a presence that no longer exists. The **bridge converges on that status**, exactly as the rename hook converges on a handle rather than consuming an event, which is why there is no intermediate "deleting" state and no completion call back to nest. Its order is **sweep first, unserve last**: every record is deleted through real signed commits *while the repo is still served*, then one `#account(active=false, status="deleted")` is announced, then the repo — records, blocks, blobs, the PostId↔AT-URI map, the projection watermark and the head row — is purged. The tempting inverse (stop serving, then destroy) is wrong on its own terms: a sweep is a **sequence of valid commits**, so a half-swept repo is a coherent repo with fewer records, indistinguishable from a user deleting records one at a time — whereas unserving first would make every intermediate state incoherent and would suppress the delete tombstones, which are the only part of a deletion that propagates to relays and AppViews. Retained on purpose: the **DID and its sealed key blobs** (this is what "reversible in identity terms" means — re-entering a hosted level restores the *same* DID and rebuilds the repo from Fauna state, since the repo is derived), the **projection floor** (the consent record a later re-enable is measured against), and the **firehose outbox**, whose frames are the network's record that the deletion happened.

**The tombstone's shape (S5 slice 5b; destruction boundary RE-STATED 2026-08-02 — the old "a sub-flow this box cannot perform" wording did not follow from the deployed key custody).** Destroying the *identity* is the PLC tombstone. The **product's** tombstone path is client-side, signed with the user's client-held senior rotation key — but "cannot perform" was too strong: a PLC tombstone may be signed by *any* rotation key **listed** on the op it chains to, and the bridge's junior key is listed for the identity's whole life ([`atproto-identity-custody.md`](atproto-identity-custody.md) § Key custody and per-identity seniority), so a **compromised bridge could sign a tombstone the directory would accept**. What the custody split delivers against that is stated honestly in [`atproto-identity-custody.md`](atproto-identity-custody.md) § Key custody and per-identity seniority: the user's senior **contest position** inside PLC's 72 h recovery window, plus client-side **attribution** — a tombstone the user's own keyring did not sign raises the custody alarm instead of reading as the user's retirement. Four properties bind the product flow:

- **It runs strictly after the sweep, and the reason is the network's, not our bookkeeping.** A tombstoned DID stops resolving, and a relay or AppView that cannot resolve a DID cannot verify that DID's commits — so retiring first would silently strand the delete tombstones, leaving our repo gone and every network copy standing, the precise failure the delete flow exists to prevent. (It is *not* that the sweep would break: the bridge signs those commits with a key it already holds and never resolves the DID.) This is the sweep's own sweep-first-unserve-last rule one level up — do destructive work *through* the protocol while the protocol can still hear you, and change the terminal state last.
- **The opt-in is durable in nest AND consented in the client — the act runs only on their agreement (consent half ratified 2026-08-02).** The tick records two things, client-side consent **first**: `tombstone_consents` in the `fauna.state.atproto-identity` rows gains the DID (client-authored, fleet-only and sealed under the generation tip, union-joined like the rotation keyring — a record the nest cannot author), and then the nest records the *intent* (`atproto_identities.tombstone_requested`). The client signs and submits on a later converge pass, once the sweep has finished — **and only when the nest's intent and the client's own consent record agree**; intent alone is nest-authored wire testimony, and a terminal, irreversible act must never run on nest testimony alone. The intent cannot live *only* in the client, because the act spans a crash and a sibling device may finish it; the consent cannot live in nest, because nest is the party the check binds. Consent-before-intent ordering is what a crash leaves safe: consent-without-intent is inert (re-tick), intent-without-consent would wedge — and when the converge pass meets intent without consent it refuses loudly, since that is either the attack shape or a not-yet-synced config that resolves itself. The outcome reports back as a fifth status, `'tombstoned'`. Nest itself records *testimony* — it holds no rotation key and makes no connection to the directory, so it has no independent view of the outcome and does not claim one (the *bridge's* listed junior key is the paragraph above's concern, not nest's).
- **It is unreachable outside the delete ceremony, enforced on the wire — and the consent record is what makes that hold against the box itself.** The opt-in kind refuses any identity that is not already recorded deleted, so [`../ui/atproto.md`](../ui/atproto.md) § Don't do these ("never a step-down, never implicit") holds by construction rather than by each of the seven apps honouring it. That wire guard binds *clients*; a box writing its own DB rows never calls the RPC — which is exactly why the converge pass demands the client-side consent record above. did:web is refused for a different reason: it has no operation log to tombstone, its custody *being* domain custody.
- **A retired identity is never restored — re-entry mints a fresh one, with a fresh senior rotation key.** The DID no longer resolves, so restoring it would park the user on a hosted rung backing a repo no relay can verify. But a retirement ends an *identity*, not the user's ability to have one: entering a hosted level afterwards is an ordinary mint, exactly as if they had never enabled — and it publishes a **fresh** user rotation key, never the retired identity's ([`atproto-identity-custody.md`](atproto-identity-custody.md) § Key custody and per-identity seniority's fresh-key-per-mint rule): the retired DID's log carries its key forever, so reuse would let anyone reading both logs link the new identity to the one the user destroyed. The retired identity moves into an **append-only archive** (`atproto_retired_identities`) rather than being overwritten or deleted. That archive is the point rather than bookkeeping — a DID that no longer resolves anywhere leaves this row as the last thing anyone can say about it, it is not re-derivable from anything, and a second retirement appends beside the first rather than forgetting it. § State & data shape's "the DID is data, not an assumption" is what makes this shape the natural one: the destroyed DID stays a stored fact with provenance, it merely stops being *this actor's live identity*. The retired identity's sealed key blob goes with it (those keys sign for a dead DID and can authorize nothing); its public halves stay in the record.
3. **Sensitive-custody (RESTATED 2026-07-23, F3 — the full PDS now touches private data; D5 of [`atproto-pds-full.md`](atproto-pds-full.md) § Problem 3).** For the *content-mirror* alone this was "there is nothing to revoke": the bridge held **no read capability over sealed content** — only *public* posts project (§ Firm boundaries), plaintext-floor data every nest serves uniformly (`../architecture/nest/storage-modes.md`; the floor is owned by `../architecture/encryption-at-rest.md`), and no user-minted content grant existed to revoke. The **full PDS** widens this to an **enumerated capability set**: the bridge holds (a) the sealed DID signing/rotation-key blobs (unchanged — layer 1), (b) a preferences read/write capability (`app.bsky.actor.{get,put}Preferences` served from nest state — live since F3 phase 4), and (c) session/grant registry access (the F1 session registry; OAuth grants join it at F4). No private content is ever **bridge-resident**: preferences and sessions rest in nest state, and DM traffic (once hosted-backing DM proxying lands) passes through bridge memory transit-only (D4 custody). Bridge-level revocation (layer 1) therefore additionally tears down all live sessions, every OAuth grant's usability (DPoP-bound tokens die with the AS keys), service-auth minting, and the in-memory caches — teardown includes a supervisor-driven process restart, so no plaintext outlives revocation.

**Honest caveat (all layers):** revocation stops *future* publishing and deletes/deactivates what *we* serve; it cannot recall records the public network already copied (relay/AppView caches and third-party mirrors persist). This is inherent to publishing on a public network, and it is why enable is a default-OFF explicit consent and history backfill a second explicit opt-in.

## Projection & backfill

One **watermark-driven loop** unifies live projection, initial backfill, and downtime catch-up:

| Trigger | Watermark start | Emit path |
|---|---|---|
| First-enable, **forward-only (default)** | enable timestamp | nothing historical; live `#commit` forward |
| First-enable, **history opt-in** | genesis | build repo offline → `getRepo` snapshot **before** `requestCrawl` |
| Downtime catch-up | last projected mark | replay gap as `#commit`; collapse huge gaps to one `#sync` + relay re-`getRepo` |

- **Default forward-only.** History backfill is an explicit opt-in checkbox in the enable panel ("Also publish my N existing public posts"), because publishing years of already-public posts to a *searchable, cache-persistent* external network is irreversible enough to warrant deliberate consent.
- **The pre-crawl snapshot advantage Bridgy Fed lacks.** At first-enable the repo is **un-crawled and has zero ATProto followers**, so a history backfill is built offline and ingested by the relay as a single `com.atproto.sync.getRepo` snapshot — **no firehose flood, no follower spam.** Bridgy Fed is forced forward-only precisely because it bridges *already-crawled* accounts; Fauna isn't.
- **Honest caveat:** Bluesky's AppView largely indexes by `indexedAt` (= now), not the self-asserted `createdAt`, so backfilled history may **clump as recent activity** on bsky.app rather than lay out as a timeline. Set `createdAt`/TID rkey honestly anyway (correct for the repo, for verifiability, and for AppViews that honor it); accept bsky's presentation. The only proof is observation.
- **Scope: posts + profile.** The `app.bsky.actor.profile` record (display name, avatar blob, bio) projects from the Fauna profile and follows profile edits — a handle with posts but no profile record reads as broken/bot-like on bsky.app, so profile is in the core projection scope, not a nicety. Defer follow/like/repost *graph* backfill — Fauna follows are mostly Fauna identities with no DID, so `app.bsky.graph.follow` records would dangle. Wait for identity-attestation (interop Phase 1) to map contacts → DIDs.
- **Self-labels.** Where a Fauna content label has a defined ATProto equivalent (adult-content categories foremost), the translate layer emits it as `com.atproto.label.defs#selfLabels` on the projected record — good-citizen behavior on the target network, and cheap only if built into the translation from the start. *(Dated note, 2026-07-20, S3 translator landing: the mechanism is wired — the translator takes a self-labels parameter — but the v1 mapping is deliberately EMPTY. No author-asserted structured category exists on `Post` today (only free-text `content_warning`, category-unguessable), and publishing classifier verdicts as self-labels was rejected: a false positive would publicly mark a user's post on an external network without their assertion — contra user-controls-their-data. A future structured author-asserted label slots into the existing parameter.)*
- **Deterministic rkeys — the repo is derived state.** Record keys (TIDs) are derived deterministically from the Fauna post's creation instant plus a stable disambiguator — never minted from wall-clock at projection time — so a from-scratch re-projection reproduces byte-identical AT-URIs and the entire repo/carstore is **re-derivable**, not user-irrecoverable data. This is the crash/backup story: only the DID key material (and the user-held rotation key) is precious; the carstore can always be rebuilt from Fauna state without breaking external references.
- **Idempotency / crash-safety:** per-user `last_projected` watermark + the existing `bluesky_posts` PostId↔AT-URI map (`libs/fauna-bridge-atproto/src/db.rs`); a PostId already mapped is skipped, so mid-batch crashes never double-emit. (With deterministic rkeys the map is itself re-derivable — it is an index, not a source of truth.)
- **Media blobs — fetch, re-hash, store, THEN reference.** A public post's image attachments project as `app.bsky.embed.images` (a post that also quotes takes the lexicon's own answer for a single `embed` field, `app.bsky.embed.recordWithMedia`). The bridge pulls the bytes from the nest over the sanctioned CID-addressed byte route (`GET /api/v1/blob/{cid_b32}` — [`../architecture/api-layers.md`](../architecture/api-layers.md) § The four API protocols owns that surface), re-hashes them to the ATProto blob CID (CIDv1/raw/sha2-256 — the "blob re-hashing" residual § Goal already accepts), and **stores them before committing the record that references them**, so `com.atproto.sync.getBlob` can serve every ref the instant a `#commit` reaches a relay; the inverse order would publish a dangling ref. Reading those bytes never crosses § Firm boundaries: a public post's attachments are the one audience class Fauna does not seal. An attachment that **cannot** be published — the nest does not hold the bytes, they exceed the per-blob ceiling, or the fetch failed — is **dropped, and the post publishes without it**, the same reading as the translation-edge row below: withholding content the user consented to publish is the worse failure. The blob store is derived and re-derivable like the rest of the repo, and the `#commit` frame's `blobs` field announces the set. **Profile avatar/banner is the same mechanism and is BUILT (2026-07-29).** `Profile.avatar`/`banner` project as the record's `avatar`/`banner` blob refs through the identical fetch → re-hash → store → reference path, so `com.atproto.sync.getBlob` serves them the instant the `#commit` lands. Two translation edges are particular to a profile picture. **(a) The media type is determined from the bytes, not declared:** a profile stores a bare `ContentHash` — no MIME, size or dimensions — and the CID-addressed byte route answers `application/octet-stream`, so the bridge sniffs the type magic-byte-wise and **drops bytes that are not an image** rather than publishing them under an invented type. **(b) Each field is independent and its absence is the drop unit:** an unpublishable avatar removes the *field*, never the profile (a handle whose profile record failed to project reads as the broken/bot-like account § Projection scope exists to prevent), and never the banner. Clearing a picture is the same mechanism read forwards — the record is re-derived from the profile each pass and replaces the stored one wholesale, so a cleared field simply stops being referenced. **Video projects as `app.bsky.embed.video` by assembling one rendition (ratified 2026-07-29).** A Fauna video is an HLS manifest plus per-resolution segments while the lexicon wants a single mp4 blob, so the mapping is an *assembly*, not a lookup — but it is a lossless one, and calling it unmodellable was the failure it looked like a limit. The segments of one resolution are h264+aac in MPEG-TS, produced by one ffmpeg run and therefore concatenable end-to-end with continuous timestamps; concatenating them and **remuxing to mp4 with stream copy** (no re-encode) yields exactly the blob the lexicon asks for. The split is § Where logic lives' usual one: shared Rust reads `PostBody::Video` and describes the **renditions** — each resolution's segment CIDs *in order*, with the declared byte total — plus the `aspectRatio` the record needs; the bridge picks the **highest resolution whose declared total fits the video ceiling**, fetches those segments over the same CID-addressed byte route, assembles, re-hashes, stores, and only then references, the identical ordering the image path obeys. Publishing the best rendition the ceiling admits is the point: a lower one is a worse copy of the same video, so quality is chosen by what can be served, never by what is cheapest. Three edges are particular to video. **(a) The ceiling is video's own, not the image one** — a video that fits in an image's budget does not exist, and the lexicon admits far more, so a separate constant governs it (still a hard-coded constant, never configuration). **(b) Dedup keys on the *manifest* hash**, the one stable per-video identity in the post: the assembled mp4 has no Fauna CID of its own — it is bytes this bridge computed, not bytes the nest stores — so without a per-video key, re-projection would re-fetch and re-assemble every segment to discover it had already published the result. **(c) The video's thumbnail is deliberately unused.** `app.bsky.embed.video` has no thumbnail field; the AppView derives its own, and publishing the still as an *image* embed instead would tell the network a video post is a photo post.
- **A post with neither text nor embed is not projected at all.** The drop rules above are per-attachment by design — the post publishes with fewer images — but their limit is the record that would carry *nothing*: `PostBody::Media` and `PostBody::Video` have no text of their own, so a media post whose every attachment was dropped, or a video whose renditions all exceed the ceiling, would otherwise commit a valid-but-blank `app.bsky.feed.post`. A blank record is the broken/bot-like account § Projection scope exists to prevent, published one post at a time, and it is strictly worse than silence: it asserts the user said nothing, where absence asserts nothing at all. Such a post is therefore **skipped**, and skipping is safe here for the reason it was *not* safe for an unbridged reply parent — the translation-edge row's cascade argument turns on a skipped post being absent from the PostId↔AT-URI map, which by that same row's ruling makes its replies project *standalone* rather than skip. The watermark advances past a skipped post like any other, so it is not retried forever; a post that later becomes publishable (a raised ceiling) is picked up by re-derivation, not by the live pass.
- **What "public" means is not this doc's to define (2026-07-29).** The stream serves only rows passing the nest's single off-box servability predicate (`db::public_servability::PUBLIC_POST_SERVABLE`), which withholds gated posts *and* everything the moderation flags withhold. The rule and its rationale are owned by [`moderation.md`](moderation.md) § Legal takedown — read it there; this stream is one of its three enumerated off-box consumers, alongside the ActivityPub outbox and note dereference. What binds *here* is § Firm boundaries' "only *public* posts project": a post the nest is withholding is not a public post, so it never enters the projection. A takedown of an **already-projected** post additionally writes the `tombstone/post` witness that drives this stream's built retraction path, so the record is deleted from the repo rather than left standing; an overturn deliberately does **not** re-publish. Both rules — and why the second is a ruling rather than a limit — are [`moderation.md`](moderation.md) § Legal takedown's to state.
- **Translation edges:** reply/quote whose parent isn't bridged → **project as standalone, dropping the ref** (*resolved 2026-07-24, S5 slice 3 — this section previously left "standalone or skip" open*); already-tombstoned/expired → skip; future `expires_at` → project + schedule a `deleteRecord` at expiry. **Why standalone and not skip:** a skipped reply is itself absent from the PostId↔AT-URI map, so every reply *beneath* it would skip too — one unbridged parent would silently withhold a whole subtree of posts the user did consent to publish, and a forward-only user (the default) replying inside a thread that predates their enable instant is exactly the common case. Consent here is **time-scoped** (the projection floor), and skipping would add a second, invisible withholding axis nobody chose. The reply's `root` follows the ATProto rule — the parent's own root, or the parent itself when the parent starts the thread — and resolution is **cross-repo**, since replying to another bridged actor is the ordinary case. Either way the invariant is the same: never a ref to a record no repo serves.

## Firm boundaries

Carried from the 2026-03-17 review (`:458-470`) and the interop strategy; never relaxed:

- **Never bridge encrypted content.** MLS channels, gated/subscription posts, and device-sync are Fauna-only by design. Only *public* posts project.
- **Never `putRecord`-update — binds the *post path* (ratified 2026-07-20 with the S3 translator, per `atproto-pds-full.md` C2; decided wording adopted verbatim-in-meaning).** Fauna posts are immutable + content-addressed → posts are only ever `createRecord` / `deleteRecord` (matching the network: Bluesky posts aren't editable either); a Fauna tombstone maps to `deleteRecord`. The boundary does **not** bind mutable-singleton lexicons: `app.bsky.actor.profile` (rkey `self`) is one, and its sanctioned update path is a repo `update` op — driven by the projection loop for Fauna-side profile edits (and, once the full PDS lands external writes, by round-trip-through-Fauna for external `putRecord`s). Nothing external ever touches the MST directly; every mutation funnels through the single per-user repo writer (C1).
- **Never auto-merge cross-protocol identities.** Surface hints; let the user choose.

## Where logic lives

- **Shared Rust** (`libs/fauna-bridge-atproto`, the existing crate) — Fauna `Post` → `app.bsky.feed.post` translation (facet mapping is already near-1:1), media descriptor prep, tombstone→delete mapping. Priority #2: this is protocol logic, it belongs in Rust, not Go.
- **Go bridge** (new, `bins/fauna-*` or alongside the mail bridge) — indigo-backed repo/MST/commit-signing, CAR/carstore, `subscribeRepos` firehose emission, XRPC read server, DID lifecycle (PLC ops / did:web doc serving), `requestCrawl`. No Fauna-side equivalent exists for any of this, so Go-via-indigo is the right home.
- **Nest** — a few *additive* `fauna.bridges.*` kinds: fetch a user's public posts + an `outbound_ready`-style push when a new public post lands (the reactive nudge the mail outbound path already uses). Small, additive surface — no deep entanglement.

## State & data shape

Reuse the existing `libs/fauna-bridge-atproto/src/db.rs` tables where they fit (`bluesky_accounts`, `bluesky_posts` as the PostId↔AT-URI map). New state the host direction needs: per-user DID + signing-key material — realized in S2 as nest's `atproto_identities` + `atproto_identity_key_blobs` (sealed to the bridge's attested x25519, like the mail TLS blobs) — plus the repo/carstore and the per-user `last_projected` watermark (S3/S5). Signing keys are held by the **bridge process**, sealed by nest to the bridge's attested x25519 pubkey — never readable from nest disk in encrypted mode (same handling as mail TLS key blobs, `mail-bridge-lifecycle.md:85-88`). **What the bridge binds a blob to when it opens one (ratified + built 2026-09-21): the identity's PUBLISHED keys, never an actor id.** `fetch_identity_key_blob` serves the identity row's `signing_pub` + `bridge_rotation_pub` beside the blob, and the one shared unseal (`fauna-mls::wrapped_blob::unseal_atproto_identity`, which every bridge consumer — the mint, the rotation-key path, the repo signer — reaches through a single fetch-and-open helper) refuses a blob whose sealed keys are not exactly that pair, an empty pair included. The blob's own AEAD-bound actor index detects an *edited* index and nothing more; it is the key binding that refuses one identity's **whole** blob served where another's was asked for. It binds to keys because the blob outlives its actor: the identity row and the blob move together at a succession while the sealed bytes cannot be re-sealed (the nest discards the plaintext at mint), so the two actor ids inside are mint-time provenance that names an ancestor for the life of the DID — an actor comparison would strand every succeeded account — whereas the published pair rides the identity row across any number of hops and is untouched by parking ([`succession-repoint-axis.md`](succession-repoint-axis.md) § The declared re-point axis owns the move). **Scope, stated honestly:** this closes a misrouted or row-level-substituted blob — a routing bug, a swapped `atproto_identity_key_blobs` row. It is **not** a defence against a hostile nest: the expected pair is nest-sourced at every consumer, a nest that lies consistently already controls the roster, the handles and the projected content, and the nest *minted* these keys. It matters most at genesis, the one place a wrong blob does lasting harm, because its keys are published into a new DID document; after mint a wrong key's signatures simply verify nowhere (commits bind the DID, service JWTs the issuer, PLC operations their predecessor). The scalar is tied to the same pair bridge-side: each consumer re-derives the public half of the key it is about to sign with and refuses on drift. **Weighed and declined:** resolving the requested actor through the succession chain (a new bridge-facing chain surface with multi-hop and parking semantics, under the same nest-sourced trust, for a binding the published pair gives by construction); the nest naming the expected predecessor in the reply (vacuous — it restates the blob, not the request); and checking against the public PLC directory (independent of the nest, but a network round-trip on every signer open, nothing for did:web, and nothing at genesis where no document exists yet — and after mint the directory already is the verifier). **Provision is one transaction:** the blob and its published pair are written together, since a blob beside a row that records no keys is unopenable under the binding. A row torn that way before this landed is re-provisioned on the next fetch **only while no DID is minted** — nothing is published, so nothing is orphaned; a *minted* identity found in that state is refused loudly and left untouched, the declared residual (its remedy, should one ever be observed, is backfilling the pair from the DID's own published document).

**Key custody, the custody audit feeders and the 72 h recovery-fork contest moved to [`atproto-identity-custody.md`](atproto-identity-custody.md) on 2026-08-03** — the did:plc key-custody split and per-identity seniority, the client-held rotation keyring and its fresh-key-per-mint rule, feeder #1's genesis-seniority verification, feeder #3's published-handle binding, the audit floor with the departed-DID clear rule, and the ten ratified decisions of the recovery fork. A citation of *this* section for any of those claims resolves there; what stays here is the nest-side state above and the DID-as-data rule below.

**The DID is data, not an assumption.** Store each user's DID as an opaque value with provenance (minted-here did:plc, minted-here did:web, or — future — *imported*), and key every downstream path off the stored value. Nothing may assume "the DID was freshly minted at enable time": inbound account migration (§ Design horizon) will one day bring an existing did:plc from another PDS into the nest, and that lands additively only if the identity model already treats minted and imported DIDs uniformly.

## Bridge lifecycle (inherits the mail-bridge contract)

Identical to `mail-bridge-lifecycle.md` cold-boot steps 1–6, role `atproto.pds`:

1. Read/generate the Ed25519 keypair file.
2. Anonymous WS → `fauna.bridges.request_enrollment(pubkey, role_hint="atproto.pds", bridge_id)` — **loopback-gated**; remote IP refused (`fauna.bridges.remote_enrollment_unsupported`).
3. Poll on 1/2/4/8/16/30 s backoff until `approved` (admin approves via `fauna.bridges.approve_pending_bridge`).
4. Challenge-response auth → bearer token → authenticated `/api/v1/ws/{actor_id}`.
5. `fauna.bridges.whoami()` → `status=approved`, role `atproto.pds`.
6. `fauna.bridges.register_service_user(ed25519, x25519, role, bridge_id)` to attest x25519 (so nest can seal DID signing-key blobs to it), then `fetch_config` + subscribe to `config_changed` for hot-reload.

Default-off-on-first-claim: the bridge is s6-supervised but blocks on a flag file until the first user enables (the `/data/imap-enabled` analog), then nest writes the flag + `up`s it via `/run/fauna-supervisor.sock`.

## Discovery risk & the MVP gate (S0)

Of every con, exactly **one is outside Fauna's control:** will Bluesky's Relay + AppView actually crawl and index a small niche self-hosted PDS? `requestCrawl` to `bsky.network` is self-service today (no allowlist), but rate-limits, future PDS requirements, and indexing behavior are PBC policy (`interop-strategy.md:555` — "Bridged content appears in the Bluesky app only if the Relay indexes the bridge's PDS"). The only proof is **observation on a live network**.

Therefore the build is **risk-ordered: S0 probes this first, cheapest, before any production machinery.** S0 stands up a **standalone throwaway `did:web` PDS** (one user, one text post) on the dogfood VPS, `requestCrawl`s, and a human confirms the post appears on bsky.app. S0 deliberately uses did:web (not the product default did:plc) to isolate the discovery risk from the PLC-ops subsystem, and proves *nothing else* — it's a kill-risk probe, not a foundation. If S0 fails or the network won't crawl niche PDSs, this whole design is refuted and write-through (Approach A) remains the path. **S0 is a live human-proof, not a CI tier** — the same category as the mail milestone's live-Gmail proof (S0 scope + slice roadmap tracked internally).

**Gate disposition (2026-07-19): WAIVED — ratified.** The build proceeds on the working assumption that the Relay/AppView will crawl and index a self-hosted PDS; S0's live human-proof is no longer a prerequisite for S1+. The assumption stays **refutable**: the first live deployment must record the actual crawl/index observation in § Implementation status today, and if the network demonstrably refuses to index, the write-through recommendation (Approach A) is back on the table before further investment. The throwaway probe (`tools/atproto-s0-probe/`) remains available for an optional early signal but is no longer required to run.

Three shape decisions: the cursor is a **keyset** (the last DID / last rkey), never an offset, so a repo or record appearing or vanishing mid-walk cannot make the following page skip or repeat an entry; a malformed, zero or negative `limit` is **clamped to the default rather than refused**, because the ceiling is the actual protection and refusing would only hand an anonymous caller a way to make the endpoint error; and the paginated query is a *separate* store method from the complete one, because two internal callers — the firehose's `#sync` degrade and the boot self-check — must see **every** repo and would be silently truncated by a paginated listing (asserted in the same test that walks the pages). Serving fewer records than a caller asked for is conformant; the cursor carries the rest. **`com.atproto.sync.getRecord` became a real proof CAR 2026-07-29 (S5 slice 7), closing the last item that pagination could not reach.** It had served the *whole repo* CAR since S3 — correct, since a repo trivially contains any record's proof path, and recorded honestly as a scope note rather than hidden, but the same amplification the page ceilings closed in the one place a ceiling is no help: the caller is already asking for exactly one record, so the fix has to be a smaller payload rather than a smaller page. The response now carries the signed commit, the MST nodes on the path from the repo root down to the record's key, and the record block — measured on a 40-record repo, 7 blocks / 1725 bytes against 218 blocks / 43542 bytes for the full-repo answer, a ratio that widens with every post a user projects (the full CAR also carries every orphaned MST node earlier incremental commits left behind, which no proof needs). Three shape decisions are load-bearing. **(a) The walk is lazy — one block read per MST level, never a whole-tree load.** Loading the tree and selecting the path afterwards would have shrunk the response while leaving each request's *work* proportional to the repo, which moves the amplification from the wire to the disk rather than removing it; depth is logarithmic in the record count (3 nodes at 60 records), so the served proof and the work to build it are both bounded by something the PDS chose. **(b) Node decoding goes through indigo's own `mst.NodeDataFromCBOR`/`NodeData.Node`** (§ Architecture: the bridge does not hand-roll MST/CBOR/signing) — indigo's `repo` package explicitly does not implement the host side, so no proof helper existed to call, but what had to be written is only the *descent* (which child subtree covers the key) and the CAR framing, never the wire format. **(c) Existence is decided by the walk itself**, not by a lookup preceding it: the previous handler proved the record existed with one read and then answered from a different one, and collapsing them means a miss can only be reported by the same pass that failed to find it. Verification is deliberately not an assertion about our own bytes — indigo's `repo.LoadRepoFromCAR` (what a relay runs) must accept each partial CAR, verify the commit signature, and resolve the record out of it, asserted for **every** record in a multi-level repo rather than a sampled one, plus absent keys before, among and after the set. Two residuals recorded honestly: a miss answers the lexicon's `RecordNotFound` rather than the alternative it also permits — a CAR *proving* non-existence — which is a purely additive change should any consumer want it, since the exclusion path is already walked to detect the miss; and the descent's bound on spurious sub-walks is a **work** bound, not a correctness one (a spurious descent cannot yield a wrong record, because MST subtrees partition the keyspace, so it still ends in a miss — which is why that bound is pinned by a unit test on the descent function, the cost being invisible from the served CAR). **`com.atproto.sync.getRepo` serves the repo's CURRENT state — RATIFIED + LANDED 2026-07-29, closing slice 7's recorded follow-on.** Slice 7 had measured `ExportRepo` serving every block ever persisted for the DID (append-only, C6): a converged ~4× blocks / ~8× bytes overhead for append-only workloads, and genuinely unbounded for **update- and delete-heavy** repos, where each rewrite adds a commit block, a record block and a fresh MST path while the live set stays the same size — the profile record's exact shape (`app.bsky.actor.profile`, rkey `self`, rewritten in place by the projection loop). The question it left open — is that surplus *history a consumer is entitled to?* — is answered by the spec, not by preference. The atproto sync spec defines the getRepo payload as "all repo records, MST nodes, and the current signed commit object, all in a single CAR file"; the repository spec defines a full export as "the full repo structure … for the indicated commit"; and network-side chain validation is inductive (`prevData` on `#commit` frames — repo-v3 `prev` "must exist in the CBOR object, but is virtually always `null`"), so no consumer dereferences the head commit's `prev` out of a getRepo response. Superseded blocks are therefore on-box history, never payload. `ExportRepo` is accordingly a lazy reachable-set walk from the head commit — indigo's own node decoding, one block read per reachable block, work proportional to the live repo rather than the persisted table (the slice-7 rule: narrowing the wire must not move the amplification to the disk) — which also makes the boot self-check validate exactly the bytes the wire will serve. The `since` param stays accepted-and-ignored, now as a recorded ruling rather than an omission: the lexicon makes the diff optional ("Optionally only a 'diff' since a previous revision"), a current-state export is a conformant superset of any diff (consumers "should … ignore any unnecessary or unlinked blocks"), and a correct diff — head-reachable blocks new since a given rev — contains no superseded block by construction, so the narrowing forecloses nothing if `since` is ever honored. Pinned by a Go test that derives the live set independently of the code under test (the union of every live record's proof CAR — each MST node lies on some root-to-key path, so the union is exactly commit + live MST + records) and asserts CAR-block set equality in both directions, indigo load + signature verification, block-count **invariance** under further rewrites of the same record, and the all-deleted repo exporting exactly the head commit plus the empty MST root; the update-heavy fixture measured 17 blocks / 2.7 KB narrowed against 116 blocks / 20.8 KB before. Three residuals, recorded honestly: the funnel still writes a **non-null `prev`** into commits (spec-tolerated — the field is nullable in exactly the sense that non-null remains valid — but the v3 norm is null; a wire-visible cosmetic to confirm or flip when live interop (F5) first observes real consumers); **at-rest storage stays append-only**, so superseded blocks now cost disk only, growing with the box's own commit cadence — reclaiming them is the already-recorded `rebuild(sources)` follow-on (C3), with its own crash-safety analysis, deliberately not bundled into a serving change; and the history opt-in's future emit path (slice 2b, "one `getRepo` snapshot before `requestCrawl`") consumes exactly this narrowed export, so 2b inherits current-state semantics by construction. **`com.atproto.sync.getRepo` is bounded by COST, not by response size — RATIFIED + LANDED 2026-07-30, closing the read-surface review's last open item.** The two hardenings above both narrowed *what a caller receives*; getRepo is the one route where neither move exists — the lexicon gives it no `limit`/`cursor`, and its answer *is* the caller's whole live repo — so what gets bounded instead is how the payload is **produced** and how long it may be **held**. Produced: the CAR now streams block by block (`Store.ExportRepoTo`, one CAR-framing owner shared with the buffered form), replacing a materialise-twice-before-the-first-byte shape — an in-memory blockstore plus a full buffer copy — that let one anonymous IP pin ~2× live-repo bytes of resident memory per in-flight call, 60 calls a minute under `ClassPublicRead`. Held: every reply on the table runs under a **response-stall deadline** (30 s, the firehose's own per-frame write-timeout value and rationale), armed by the XRPC frame for every route that is not `Route.LongLived` and **re-armed per bounded chunk by the frame's own response writer** (since the 2026-07-30 fix every non-stream handler writes through a chunking wrapper, so no route opts in — a handler that hands its whole payload to one `Write` is chunked underneath; getRepo's handler additionally writes through `xrpc.ProgressWriter`, whose byte count is what its teardown decision reads) — deliberately a *stall* bound rather than a request budget, because any fixed total budget for a whole-repo payload would have to be generous enough for the largest legitimate repo over the slowest legitimate link, and would therefore bound nothing. Around it, the listener gained `ReadHeaderTimeout` (15 s) and an explicit `IdleTimeout` (2 min), the phases no route can bound from inside; `ReadTimeout`/`WriteTimeout` stay **zero as a correctness requirement, not an omission** — `subscribeRepos` is a WebSocket on this same `http.Server`, held open for hours and legitimately silent throughout, so a server-wide deadline would evict exactly the healthy relays the firehose exists to feed, which is precisely why the per-request bound lives one layer in, where it can tell a stream from a reply. Three rulings worth not re-deriving: **`since` is not the answer to this** — a parameter only a cooperative caller sets can narrow a response but can never bound an anonymous surface, since an attacker simply omits it (so honouring `since` later remains the additive conformance improvement it always was, and closes nothing here); **streaming's cost is the error contract, and it is paid deliberately** — the head commit is loaded and decoded before the first byte, so "this repo cannot be served at all" still answers cleanly, while a failure after bytes are out **tears the response down** (`http.ErrAbortHandler`) rather than ending normally, because Go would otherwise close a well-formed chunked body and hand the consumer a CAR that parses fine while silently missing records; and **an export failure on an already-admitted repo is ours, not the caller's** — it now logs and answers `InternalServerError` instead of the swallowed, unlogged `RepoNotFound` that made a corrupt tree indistinguishable from a mistyped DID. The walk also stopped trusting its own node entries: an entry naming neither a child nor a value, or naming one with no CID, now **fails** the export as a corrupt tree, where before a malformed child was silently skipped (dropping a whole subtree into a short-but-well-formed CAR) and the value branch dereferenced with no guard. Pinned by five tests, two of them mutation-checked: streamed sections counted one-per-block and a writer that refuses mid-CAR stopping the walk (both collapse under a materialise-then-return implementation), teardown-not-truncation on a corrupted record block (a plain `return` serves a complete-looking 200), corrupt-head answering 500 rather than `RepoNotFound`, the frame arming the deadline on an ordinary route and **not** on a `LongLived` one, and the listener's two bounds plus its two deliberate zeroes. One residual, accepted and unchanged: per-call **DB reads** still scale with the live repo under nothing but `ClassPublicRead`'s 60/min per IP — the same posture already recorded for `getBlob` just below. A per-route concurrency cap was considered and **declined**: with per-call resident cost now one block and stalls dying in 30 s, it would refuse legitimate relay backfill for no remaining exposure. One thing the mechanism reaches beyond the read surface, recorded here because the frame owns it: the stall deadline is armed — and per-chunk re-armed by the frame's chunking writer — for **every** non-`LongLived` route, F3's service-proxy fallback included; its upstream relay also writes through the same `xrpc.ProgressWriter` (for the `Written()` teardown decision, since a proxied body may run to safefetch's 5 MiB cap) — and it gained the same truncation fix, because a proxy whose *upstream* dies mid-body reaches its error path with a perfectly healthy downstream connection, where returning normally let Go finish the response and even synthesise a `Content-Length` the upstream never sent. Its own comment already said to cut the transfer short; now it does.

**S5 slice 1a — post media blobs — LANDED 2026-07-29**, closing the biggest remaining product gap in the projection: a Fauna media post had been projecting as a valid record with **empty text and no embed**, because the translator mapped `PostBody::Media`/`Video` to `("", no facets)` and set `embed` only for a quote, and the bridge emitted `Blobs: []` on every `#commit`. A public post's images now project as `app.bsky.embed.images` (or `app.bsky.embed.recordWithMedia` when the post also quotes), the bytes are served by new `com.atproto.sync.getBlob` / `listBlobs` routes on the existing read surface, and the `#commit` frame announces the blob CIDs it references. Four shape decisions are load-bearing. **(a) The slice is atomic and could not be split.** § Projection & backfill's "never a ref to a record no repo serves" binds the three halves: a blob store with no serve route is dead code, a record blob-ref with no stored blob is the dangling ref the section forbids, and a serve route with no blobs serves nothing — so store, embed and `getBlob` had to land together. The ordering follows from the same rule: blobs are written **before** the commit that references them, and a crash between the two leaves an orphan blob row, which is harmless and re-derivable, whereas the inverse order publishes a ref to bytes no repo serves. **(b) The split is descriptor-in-Rust, bytes-in-Go** (§ Where logic lives, "media descriptor prep"), the S5-slice-3 shape reused verbatim: `outbound::extract_projection_media` says which bytes matter and what they are (already filtered to `image/*`, capped at the lexicon's four, video-free), Go fetches/re-hashes/stores, and hands `ResolvedImage`s back to the same translator — so the bridge still never decodes a Fauna post, and **no new nest wire kind was needed**: the attachments are already inside the `fetch_public_posts` payload, and the bytes ride the pre-existing CID-addressed HTTP carve-out. **(c) The blob row remembers its Fauna CID.** The two content-address spaces do not map onto each other — BLAKE3 → sha256 is only computable by *holding* the bytes — so without that provenance column, answering "have I already published this attachment?" would itself cost the fetch it was meant to avoid; with it, a re-projection and a second post reusing the same image are both free. **(d) An unpublishable attachment drops the image, not the post**, for the reason the translation-edge row already ratified for an unbridged reply parent. Reading the bytes at all is legal under § Firm boundaries because a public post's attachments are `AudienceClass::PublicPost`, the one class Fauna does not AEAD-seal, so no encrypted content is ever bridged. Pinned by Rust unit tests over the extraction and both embed shapes, eight Go tests over the real store, projector and funnel (blob CID pinned against an independently-derived vector; store round-trip + per-DID isolation; keyset pagination; blob-stored-before-referenced; fetched-once-on-reuse; all three drop causes; the `#commit`'s `blobs` parsed back through **indigo's own event decoder**), read-surface tests including the deactivation matrix (`getBlob` on a deactivated repo refuses `RepoDeactivated` for a CID it does not hold — proving deactivation is checked before existence, so a stepped-down repo cannot be probed for which media it holds), and tier_3 `test_atproto_firehose_post.py`. **Residuals, recorded honestly:** avatar/banner was in scope per § Projection scope but blocked upstream on the apps-area profile image-upload increment — **that block lifted and the residual CLOSED 2026-07-29**, see the profile-picture entry below; video is deferred as a genuinely different mapping; an over-ceiling image is dropped rather than downscaled or served as its thumbnail, which would need the media pipeline; a *transiently* failed fetch is dropped for good rather than retried, because the post then lands in `post_map` and per-attachment retry state does not exist; and `listBlobs` accepts but ignores the lexicon's `since` (blobs are keyed by CID here, not by the commit that introduced them — the full set is a conformant superset of any `since` answer, whereas honouring it wrongly would silently withhold blobs). One posture note rather than a residual: `getBlob` serves up to the per-blob ceiling per request on an unauthenticated surface, which is the *same* amplification profile `getRepo` already has (a whole repo CAR per request) under the same `ClassPublicRead` per-IP limit — so it adds no new exposure class. The ceiling bounds the *bytes* one request can ask for; how long the response may take is bounded identically for both (and for every non-stream route): the frame's chunked response writer re-arms the 30 s stall deadline per chunk, so a slow-but-reading consumer is never cut off and only a stalled peer is torn down. (The 2026-07-30 fix — between the commit that introduced the deadline and it, the deadline was a *total* transfer budget on any route not writing through `ProgressWriter`, which cut `getBlob` off mid-body below ~14 Mbit/s at the video ceiling.)

**S5 video — the video mapping + the blank-record rule — LANDED 2026-07-29**, closing slice 1's last media gap and, with it, a defect the mapping's absence had been quietly producing. A Fauna video had been recorded as "deferred: `app.bsky.embed.video`'s single blob does not model an HLS manifest plus segments" — but the consequence of deferring was not that video posts stayed on Fauna. `PostBody::Video` carries **no text**, so the translator's text-less arm plus an empty media extraction committed a valid `app.bsky.feed.post` with empty `text` and no `embed`: **a blank post on the network, once per video the user posted.** The same hole was reachable without video — a media post whose every attachment was dropped produced the identical record. Four shape decisions are load-bearing. **(a) "Does not model" was a convenient limit, not a true one.** The segments of one rendition come from a single ffmpeg HLS run, so they are h264 + aac in MPEG-TS with continuous timestamps: concatenating them and remuxing to mp4 with **stream copy** is lossless, costs roughly a disk copy, and needs no packaging change because ffmpeg already ships in the runtime image for the nest's own transcode path. What looked like a missing capability was a missing assembly step. **(b) The split is the established one, and the ceiling decided where the choice lives.** Shared Rust (`outbound::extract_projection_video`) describes the *renditions* — each resolution's segment CIDs in playback order, with a declared byte total — and the bridge picks the **highest resolution that fits**, fetches, assembles, re-hashes, stores, then references. Rendition choice is a byte-ceiling decision, and byte ceilings live with whoever does the fetching (the same reason `MAX_EMBED_IMAGES` is in Rust and `MaxBlobBytes` in Go); the declared total is an *upper* bound on the mp4, since the remux strips MPEG-TS packet headers, so choosing on it can reject a rendition that would just fit but never accept one that would not. **(c) Dedup keys on the manifest hash, because the published bytes have no Fauna CID.** Unlike an image blob — a Fauna blob republished verbatim — the mp4 is computed by the bridge and exists nowhere in Fauna, so the image path's fauna-CID provenance column has nothing to store; the video's manifest hash is the one stable per-video identity, and without it "have I already published this?" would cost re-fetching and re-assembling every segment. **(d) A missing segment fails the whole video, which inverts the image path's reading on purpose.** A dropped attachment is content a viewer simply does not see; a gap mid-stream is not a shorter video but a corrupt one. **The blank-record rule that falls out is stated separately in § Projection & backfill because it is not video-specific:** a post that would carry neither text nor embed is now **skipped**, not committed — and skipping is safe precisely because slice 3 ruled that an unmapped parent makes a reply project *standalone*, so the anchor a blank record was once justified by was never what kept replies publishable. Pinned by Rust unit tests over the extractor and both embeds (rendition grouping/order/best-first, the skip arm for video and for all-images-dropped, quote-plus-video nesting as `recordWithMedia`), eight Go tests driving **real ffmpeg over real segments** and handing the result to **ffprobe** — a container that merely starts with `ftyp` can still be undecodable, so "playable" is asserted by a decoder opening it and reporting both tracks copied through — plus rendition choice, the missing-segment arm, dedup across a re-projection, and the `#commit` `blobs` announcement; and end-to-end by tier_3 `test_atproto_firehose_post.py` step 6d-bis, where alice uploads genuine MPEG-TS segments, posts a real `PostBody::Video`, and `com.atproto.sync.getBlob` serves back a faststart mp4 whose CID matches none of the CIDs the post named. Four mutations were checked by name; a fifth is recorded honestly below because it did **not** fire. **Residuals, recorded honestly:** the `-bsf:a aac_adtstoasc` flag is stated explicitly but is **not test-pinned** — removing it leaves the assembly test green, because current ffmpeg inserts the filter itself for TS→mp4 stream copy, so the flag is insurance against a future version that stops inferring it rather than a behaviour the suite can distinguish (verified by planting exactly that mutation); the ceiling is a flat 50 MB byte count rather than a duration- or cost-aware choice, and a video over it at *every* rendition skips the post entirely rather than falling back to a lower-quality re-encode, which would need a transcode the bridge deliberately does not do; captions and `alt` are absent because Fauna's video body carries neither, and the thumbnail is unused because the lexicon has no field for one; and a transiently failed segment fetch skips the post for that pass — unlike a dropped image it *is* retried, since a skipped post never enters `post_map`, but the retry waits for the next pass that offers it.

**S5 slice 5 — the "Delete my Bluesky presence" sweep — LANDED 2026-07-29**, making § Disable & revocation's "separate, stronger action" real for the first time: the `atproto-delete-presence` button had rendered on linux, apple, tui and web since S4-B with no handler behind it, by design, waiting for this. The user-facing kind is `fauna.bridges.atproto.delete_presence` (User-class, self-scoped, idempotent, no parameters), filling the slot [`../ui/atproto.md`](../ui/atproto.md) § User actions had reserved as "S5-scope kind, named at build time". Nest records the decision — sessions revoked, the D10 authoring credential destroyed, `atproto_identities.status = 'deleted'` (a second data-preserving CHECK widen on the S4-A pattern), level dropped to `off` — and the **bridge converges on that status** rather than consuming an event, the rename hook's shape, which is why there is no `deleting` intermediate state and no completion call back into nest. Four shape decisions are load-bearing. **(a) The order is sweep-first, unserve-last, and the NEXT's own guess was the wrong way round.** Every record is deleted through real signed commits *while the repo is still served*, then one `#account(active=false, status="deleted")` is announced, then the repo is purged. The intuition that a destructive pass should stop serving first "so a crash never serves a half-destroyed repo" does not survive contact with what a sweep actually is: a **sequence of valid commits**, so every intermediate state is a coherent repo with fewer records, indistinguishable from a user deleting records one at a time. Unserving first is what would create incoherence — announcing `#commit`s for a repo just declared unserved — and, far worse, would suppress the delete tombstones, which are the only part of a deletion that propagates removal to relays and AppViews; a crash would then leave records present-but-unreachable with the network never told. **(b) The tombstone is nest-side, never bridge-side.** The bridge's store is explicitly derived and re-derivable, so an intent recorded only there would evaporate on a wipe and the swept presence would quietly re-project itself — the same argument that put the projection floor in nest at slice 2a. **(c) `projection_state` is purged with the rest, deliberately.** A surviving watermark would make a later re-enable project only posts *newer* than the sweep, leaving the rebuilt repo permanently missing history that sits inside the user's own consent floor — a silent withholding of posts the user did consent to publish, the failure mode slices 2a and 3 each argued against, and a contradiction of re-derivability. **(d) The identity survives, so the sweep is genuinely not user-data loss.** The DID, its sealed key blobs and the projection floor are all retained; re-entering a hosted level restores the *same* DID and rebuilds the repo from Fauna state (deterministic rkeys make it byte-identical). No relay-visible state is left claiming otherwise: the `repo_heads` row goes with the repo, so every subsequent read answers `RepoNotFound` and `listRepos` omits the DID — the spec-conformant answer, since the sync lexicons define no `RepoDeleted` error and `#account`'s `status: deleted` *is* the announcement. Pinned by Go store tests (the enumerator spans collections; the purge erases records/blocks/post_map/blobs/watermark/head and **spares the outbox**, whose frames are the network's record of the deletion; an unknown DID purges silently; an incoherent `active`/`status` pair is refused) plus six loop tests over the real store and funnel with every frame decoded through **indigo's own decoders** (the final commit carries delete ops for the posts *and* the profile singleton; exactly one `#account(deleted)`; never a `deactivated` frame first; convergence after a crash between the sweep and the announcement; silence for a never-projected identity; projection stops), nest-side by `conformance_atproto_integration_level.rs`, and end-to-end by tier_3 `test_atproto_firehose_post.py` **step 10 (green, 52.6 s)** — a real `delete_presence` over the wire, the bridge's own sweep, `#account(status="deleted")` on a live `subscribeRepos` subscriber, and the repo answering `RepoNotFound` and dropping out of `listRepos`, which is the cross-binary half the Go tests cannot reach because they drive a fake nest. Two mutation checks fired: removing the delete pre-emption made the pass announce `deactivated` first and leave the repo standing, and dropping the blob/watermark purges tripped exactly the assertions written for them. **Residuals, recorded honestly:** the sweep deletes in chunks of a hard-coded 200 ops per commit, which is a count rather than a wire-cost comparison (the same calibration gap slice 4 recorded); and § Disable & revocation's honest caveat is undiminished — the sweep deletes what *we* serve and tells the network, but cannot recall what relays, AppViews and third-party mirrors already copied. **The headline residual — "the app confirm ceremony is not wired" — CLOSED 2026-08-21, and complete on all 7 apps as of 2026-09-06**: the ceremony landed in the shared settings machine and on tui, the lead app, so the kind has a caller for the first time; linux, web, android, macOS and iOS landed the trickle-down leg 2026-08-28; windows landed last (2026-09-06), closing the ladder end-to-end. Its shape and the two per-app rendering rules it settled are owned by [`../ui/atproto.md`](../ui/atproto.md) § Implementation status today; what binds *here* is that the card states this section's caveat verbatim and frames the sweep as reversible in identity terms, which is what keeps the consent it collects matched to what actually runs.

**S5 profile pictures — avatar/banner projection — LANDED 2026-07-29**, closing slice 1a's largest residual. **An unchanged profile no longer re-commits — FIXED 2026-07-29**, a pre-existing defect found while tracing the profile path for the picture slice above and fixed ahead of it. The projection loop re-projects the profile singleton on **every** pass whether or not it changed, and the funnel's create/update arm never compared the incoming record against the stored one — so a byte-identical profile minted a fresh rev and broadcast a `#commit` to the whole network on every pass, indefinitely. The fix is an opt-in `SkipUnchangedRecords` batch option the projection passes and external writes do not: a re-derivation knows that "identical" means "nothing happened", whereas `com.atproto.repo.putRecord` must still return a commit and rev for identical bytes because the lexicon promises one. The comparison runs inside the batch under the per-DID lock, never as a read-then-write in the caller. Worth carrying: the existing profile test re-projected only *changed* bytes, so the defect sat under a green test — the missing case was "call it twice with the same input", which is the cheapest possible test of anything that runs on a loop.

Two independent holes, both closed: the three moderation flags were never consulted, and the `LEFT JOIN` made a **missing** `content_meta` row read as public-and-unflagged (so a *gated* post whose best-effort index write failed projected as public). The fix is a single named predicate, `db::public_servability::PUBLIC_POST_SERVABLE`, now applied by all three off-box serve paths — this stream plus the ActivityPub outbox and note dereference, which carried the identical defect and which this module's own doc comment had named as the filter it followed. Two shape notes worth carrying. **(a) The tombstone arm must bypass the predicate, and that is not an oversight.** A `tombstone/post` journal row carries no `content_meta` row by construction, so asserting the row's existence across the whole filter — or switching to an `INNER` join — would silently drop every retraction: the failure is invisible in the happy path and permanent on the network, so it has its own regression pin. **(b) Requiring the meta row strands no history.** The prior ActivityPub test asserted the opposite, reasoning that an inner join "would silently empty every outbox whose posts predate their meta row"; that era never existed (`content_meta` is base schema, not a later migration), while the genuinely reachable source is the swallowed `write_post_index` error — and since the feed read already inner-joins the table, the outbox had been *more permissive than the author's own feed*. Pinned by four red-first tests, each verified non-vacuous by reverting the predicate. **The retraction leg closed 2026-07-29, and the residual with it.** The predicate stopped only *future* publication; the takedown transaction now also writes the `tombstone/post` witness that drives the built `deleteRecord` path, so a post projected **before** its takedown is withdrawn from the repo too. Three things worth carrying. **(a) The Go side needed no change, and that was verified rather than assumed** — the projector already returns a clean no-op for a tombstone naming a post it never projected (the whole point of resolving through the record map first), and a test already pinned it; the new witness simply makes a case that could not previously arise reachable. **(b) The witness id is derived from the post digest, not from the caller-supplied content id** — that string arrives off the wire, so deriving from it would let an uppercase-hex request mint a second witness for the same post and break the at-most-one-retraction invariant this row shares with the delete path. Because the id is shared, a later user delete of the same post rewrites the row at the later instant, which can only move it *forward* in the stream and so can never drop it behind a watermark that already consumed it. **(c) The overturn direction is now ruled, not silent:** an overturn re-serves on Fauna and deliberately does not re-publish off-box — `moderation.md` § Legal takedown owns the ruling and, importantly, states it as a choice rather than an inherent limit, since the deterministic record key means a restore witness *could* return the record to its original address.

**S5 slice 5b — the terminal PLC tombstone — LANDED 2026-07-29**, closing slice 5's headline residual and making § Disable & revocation layer 2's "explicit opt-in to also permanently retire this identity" real for the first time. It is the only act in the subsystem that destroys rather than deactivates, and the only one this box structurally cannot perform: the operation must be signed by a rotation key listed on the previous one, and the ratified custody split puts the senior key in the user's client and nowhere else. So the op builder is shared Rust, in `libs/fauna-client-atproto` beside the key it signs with — build the did:plc v0.1 `plc_tombstone` (`{type, prev}` and nothing else), canonical-dag-cbor encode it, sign with the user's P-256 senior key, read the directory's standing head for the `prev` to chain to, and POST the signed op over the client's own HTTPS connection, the same no-nest-in-the-middle property S4-C's seniority check relies on. Nest gains a fifth `atproto_identities.status` (`'tombstoned'`, a third data-preserving CHECK widen on the S4-A pattern), an additive `tombstone_requested` intent column, and two USER-class self-scoped kinds — `fauna.bridges.atproto.request_tombstone` and `.record_tombstone` — neither of them bridge-callable, since the bridge holds only the *junior* rotation key and no box-held key may end an identity.

Five decisions are load-bearing, and the first two are the ones a future slice is most likely to get wrong. **(a) The ordering rationale is the network's, not ours**, and the NEXT's own guess ("the sweep's commits need the identity to still resolve") was the wrong reason for the right answer: the bridge signs those commits with a key it already holds and never resolves the DID, so the sweep would not break. What breaks is *verification* — a tombstoned DID stops resolving, and a relay that cannot resolve a DID cannot verify its commits, so retiring first would leave our repo gone and every network copy standing, with the delete tombstones unverifiable and ignored. **(b) The intent is durable nest-side because the act spans a crash.** The tick and the submission cannot be one gesture: the submission has to wait for the sweep, so a client that died in between would leave the user believing an identity was retired when nothing was published — the same argument that put the delete tombstone in nest rather than the bridge at slice 5a, applied one level up to the *identity*. What nest stores is testimony, not verification; it has no key and no connection to the directory, and pretending otherwise would be the more dangerous shape. **(c) The precondition is the wire-level form of a UI rule.** `request_tombstone` refuses any identity not already recorded deleted, so [`../ui/atproto.md`](../ui/atproto.md) § Don't do these ("never a step-down, never implicit") is unreachable to violate rather than a rule seven separate app implementations are each trusted to keep — and the same clause encodes (a)'s ordering. **(d) Both halves are idempotent, including "already retired" — but idempotent is not the same as permissive.** The client re-reads the head before submitting and treats an already-tombstoned log as success, and both kinds report "changed nothing" rather than erroring, so a crash between submitting and reporting converges instead of showing the user a failure for an act the network has already seen. What `record_tombstone` must *not* do is answer the same way for a report it never authorized: "already retired" and "no opt-in stands here" both change no row, yet the second means a client believes it destroyed a DID whose row is still `'deleted'` — and a `'deleted'` row still reactivates, so accepting it would re-park the user on a hosted rung backing a dead DID, with § Disable & revocation's re-entry refusal never firing because the terminal status was never written. Reachable whenever the opt-in write was lost, a crash landed between the two calls, or a client skipped the tick; it is therefore refused loudly, and the read that distinguishes the two runs under the same lock as the write so a concurrent re-entry cannot overtake it. *(Caught while the client leg was still unwritten, and fixed before it was written.)* **(e) Low-S normalization is explicit and load-bearing**: ATProto requires it of both blessed curves, and RustCrypto's P-256 signer does not normalize on its own (unlike its secp256k1 signer), so an unnormalized signature would verify locally and be rejected by the directory about half the time. Pinned by a self-proving test that also samples unnormalized signatures and asserts some come out high-S — without that half it would pass even if the normalization vanished. The signing input itself is byte-pinned for the same class of reason: it is what the directory validates against, so a silent change to it would change what every published signature means and no round-trip test could catch it.

Proof: 11 new Rust unit tests over the op, the signature and the head lookup; four nest db tests (the opt-in is unreachable from active *or* deactivated; did:web and unminted are refused; the terminal status is written only for a requested deletion; a retired identity never reactivates); a migration test rebuilding the slice-5 on-disk shape and asserting every row survives with its DID, provenance and projection floor intact; four conformance tests through the real router (class/allowlist, the refusal outside the ceremony, the full delete → opt-in → report flow with both idempotency directions, and the refused re-entry); and a Go loop test asserting a retired identity is inert to the bridge — no frame, no poll — checked against a repo that still exists, so the negative assertion is made where the bridge *could* have acted wrongly.

**The client's converge pass LANDED 2026-07-29**, giving slice 5b its first caller: the settings machine now finishes the act the opt-in recorded, on the same status convergence that already runs the S4-C seniority check. It is a **converge pass rather than a gesture** for the reason property (b) gives — the act spans a crash, so the tick that records the intent cannot also submit — and the same shape is what lets a *second* device complete a retirement a first one started, or the same device finish one after a restart. Three decisions are load-bearing. **(a) The sweep-completion observable is the DID's own PDS answering `RepoNotFound`, asked client-direct.** The endpoint is read out of the DID's published PLC operation (`services.atproto_pds.endpoint`), never taken from a nest reply, so **the box is never in the middle of a question about its own conduct** — the property S4-C chose deliberately. `RepoNotFound` is also the answer for a never-projected identity, which is the correct reading here: either way nothing is left to delete. **(b) It is a politeness ordering, not a security boundary, and the code says so rather than overselling it.** A hostile or broken box could equally just not sweep, or answer `RepoNotFound` while still serving; the probe proves nothing. What protects the user is the tombstone itself, which lands regardless. The probe's narrower job is still worth doing: retiring before the deletes are published would strand them, per property (a). **(c) Three answers, never two.** "Gone", "still there" and "could not tell" are distinct, and an unanswerable probe — an unreachable PDS, a standing op declaring no PDS service, an unrecognised error body — is a quiet retry, never a licence to retire early; the answer is keyed on the lexicon's error *name*, not the HTTP status, because `getRepoStatus` returns 400 for a malformed request too. A published tombstone that nest failed to record is likewise a *reporting* gap and not a lost retirement — the directory is the durable record, the intent still stands nest-side, and the next convergence re-reads an already-tombstoned log and reports again. **That recovery sentence was FALSE at code level until 2026-07-29**: the pass asked its two questions — *has the sweep finished?* and *is it already retired?* — as two independent calls, and for an already-published tombstone they are contradictory when asked separately, because the head that means "already retired" is a `plc_tombstone`, which declares **no services**, so the sweep probe routed through it answered "cannot tell" forever. The already-retired report was unreachable in production, and one ordinary transient (the report failing after a successful submit) wedged the row at the *restorable* `'deleted'` status permanently — re-entry would then re-serve a repo behind a DID that resolves nowhere, a client-causable unrecoverable state. The fix makes the step **one function reading the directory's log once**: an already-tombstoned head reports success *before* any probe (there is nothing to probe and nothing left to wait for), a live head is probed at its published PDS, and only a finished sweep signs and submits — which also halves the directory reads and makes the contradictory pair unrepresentable in the test seam, whose fake now models one log state that a successful submit itself flips to tombstoned (a fake holding the two answers as independent knobs could script a state the real directory cannot produce, which is exactly how the defect sat under green tests). Pinned by a pure decision test on the raw wire shape (a service-less tombstone head decides "already retired", never the probe), a two-convergence machine test over the coupled fake (pass 1 submits with the report failing; pass 2 *must* report and land the terminal status), and the standing matrix (an unfinished or unanswerable sweep submits nothing and retries; nothing is attempted for an active, deactivated, un-opted-in, already-retired or did:web identity; a `'tombstoned'` identity stages a **mint**, never a reactivation) plus shared-Rust tests over the endpoint read and the error-name reading.

**Re-entry after a retirement now mints a FRESH identity, LANDED 2026-07-29**, closing slice 5b's other residual and the last thing standing between a retirement and an honest product story: it had been *refused*, which beat the silent lie the reactivation path would otherwise have produced but left a retirement as a permanent lockout. What blocked it was only the schema — `atproto_identities` is one row per actor — so the fix gives the old row somewhere to go. Three decisions are load-bearing. **(a) The archive is a separate append-only table, not two columns on the live row.** Columns would remember only the *most recent* retirement, so a user's second retirement would silently erase the record of their first — a DID they really did publish. A table also keeps `atproto_identities` meaning "the live identity" (its unique-DID index stays a statement about live DIDs), keeps the retired row out of the bridge's roster, and makes the fresh mint the *existing* insert path rather than a second one. **(b) The whole change is one bit in the shared transition plan.** `LevelContext.has_identity` means a **restorable** identity — active, deactivated or presence-deleted, all of which retain the DID — and a retired one is not restorable. The plan then says *mint* rather than *reactivate* on its own, which is what makes the client's confirmation card describe a new identity and send the mint parameters for one; nest and the card cannot disagree, because they read the same plan. **(c) Archive-then-delete is one transaction.** A crash between them would either lose the record of a published DID or leave a retired row blocking every future mint, and neither is recoverable from the client (§ Client-state recoverability). Pinned by db tests (the archive round-trip and fresh re-mint; only a retired row ever moves, with active/deactivated/deleted each asserted to stay put; a second retirement keeping the first), a migration test (the archive arrives additively and no identity row is touched), and conformance tests through the real router (re-entry mints a *new* pending identity while the destroyed DID survives in the archive and stays out of the roster — plus its neighbour, that a presence delete still restores the *same* DID). The `identity_retired` refusal is gone with the limitation it described.
