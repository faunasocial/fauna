## Goal

The S1–S5 **content-mirror** PDS makes a Fauna user *visible* to the ATProto network: the network can read, follow, and interact, but only Fauna apps drive the account. The **full PDS** adds the login half of the protocol, so `alice.example.com` works as a login in bsky.app and any third-party ATProto app, with all writes landing on the nest:

- session + app-credential auth (`com.atproto.server.*`),
- the ATProto **OAuth authorization-server** surface,
- the authed XRPC **write** surface (`com.atproto.repo.*`),
- **service proxying** to the AppView and chat service (`atproto-proxy` + service JWTs),
- **preference storage** (`app.bsky.actor.{get,put}Preferences`).

Definition of success (unchanged from the decision record): a user with a nest-hosted DID logs into the official Bluesky app and at least one third-party ATProto app with their `alice.example.com` handle, posts from it, and that post (a) lands in the nest-held repo, (b) appears in Fauna apps as a normal Fauna post, and (c) reaches the network via our firehose — with connected apps visible and revocable from all 7 Fauna apps, and every touched invariant re-ratified rather than silently bent. This completes the pitch: **"Fauna *is* your Bluesky home server" becomes literally true for any app in the ecosystem.**

Decision provenance: § Design horizon item 1 of [`atproto-pds-bridge.md`](atproto-pds-bridge.md) — **DECIDED 2026-07-19: build it.** The original "sequenced strictly after S1–S5" rider was **overridden by user directive 2026-07-20**: the full-PDS chain runs in parallel with the mirror chain, under § Parallel execution's per-slice gates.

## Problem 1 — the two-writer problem: external writes into a one-way-derived repo

**The ratified claims at stake** (`atproto-pds-bridge.md` § Projection + § Firm boundaries): Fauna is the source of truth; the projection is one-way; deterministic rkeys make the repo byte-identically **re-derivable** ("the repo is derived state"); the translator only ever `createRecord`/`deleteRecord`, never `putRecord`. A full PDS lets bsky.app `createRecord`/`putRecord`/`applyWrites` into that same repo. The design must keep Fauna authoritative without making external apps second-class.

### D1 (decided) — round-trip through Fauna, plus a nest-held native-records journal

**Round-trip (mappable lexicons).** Every external write whose lexicon maps to a Fauna concept is reverse-translated **into Fauna first**, then projected back into the repo by the normal one-way loop — external apps become just another client of Fauna state:

- `app.bsky.feed.post` → a Fauna post (origin-tagged "via Bluesky app", the consume-side ingestion pattern) → the projection loop appends it to the repo exactly as if composed in a Fauna app.
- `app.bsky.actor.profile` (`putRecord`) → a Fauna profile update → the projection re-emits the profile record.

**D2 (decided) — per-lexicon membership policy + starting table.** The *policy* is ratified: **round-trip iff a Fauna concept already exists for the record's meaning — never invent a hollow Fauna concept just to round-trip; everything else journals; refuse only what the § Problem 4 table refuses.** The starting membership under that policy (F2 verifies each round-trip row against the consume-side interaction vocabulary *as built* before implementing it — a row whose Fauna concept turns out not to exist falls back to the journal, which is always safe):

| Lexicon / write | Path | Notes |
|---|---|---|
| `app.bsky.feed.post` (incl. replies, quotes, embeds) | round-trip → Fauna post | blobs via `uploadBlob` → Fauna media path; origin "via Bluesky app" |
| `app.bsky.actor.profile` (`putRecord` on rkey `self`) | round-trip → Fauna profile update | the C2 sanctioned-update path |
| ~~`app.bsky.feed.like` / `repost`, `app.bsky.graph.follow` **on subjects the consume side already represents**~~ | ~~round-trip~~ → **journal** | **Verification RAN 2026-07-24 (F2.1) and moved this row — see below.** |
| like/repost/follow/block/mute (**all** subjects); `app.bsky.graph.list*`/`listitem`; threadgates/postgates; starter packs; labeler service decls | **journal** | lexicon-validated where the lexicon is known |
| Unknown/custom collections (third-party lexicons) | **journal** | ATProto repos are open-world and real PDSs accept arbitrary structurally-valid records; we do the same — structural (CBOR/size) validation only, no schema gate on unknown NSIDs |

**Verification outcome (2026-07-24, F2.1) — the interaction row journals; the policy did the work it was written to do.** The starting table made like/repost/follow conditional on "subjects the consume side already represents", and the code recon this row demanded found the consume side does *not* represent them in any writable way: `viewer_like`/`viewer_repost`/`viewer_following` are read-only AppView view-state AT-URIs (`libs/fauna-bridge-atproto/src/types.rs`), the Bluesky kind registry holds exactly one kind — `bluesky.feed.thread`, a read (`libs/fauna-protocol/src/kind.rs::register_bluesky_kinds`) — and the Bluesky bridge provider *hard-refuses* follows (`bins/fauna-nest/src/bluesky/bridge_provider.rs`, "Bluesky does not support bridge follows"). Round-tripping would therefore have required inventing exactly the hollow Fauna concept the policy forbids. Nothing is lost: a journaled interaction still lands in the repo, still federates on the firehose, and still reads back via `getRecord`. If Fauna later grows a real interaction vocabulary, the row moves back with a test rather than a redesign. Implemented as the pure `fauna_bridge_atproto::membership` classifier.

**Two refinements the same slice settled**, both inside D2's existing policy rather than changing it:

- **The disposition is a function of (collection, *action*), not collection alone.** § F2 detail already makes `putRecord` on a post refused while `createRecord` round-trips, so the collection cannot answer by itself. `putRecord` is classified `Update` even when the rkey does not yet exist, so the same call never flips verdict on repo state.
- **`deleteRecord` on `app.bsky.actor.profile` is refused *fauna-surface*** (the D6 per-endpoint residue this slice finalized, per § Problem 4's mandate that each F-slice settle its own residue). The projection owns that collection, so a journal tombstone for it would collide with the record the projection keeps emitting and the repo would stop being re-derivable from Fauna state — breaking D1. The refusal names the Fauna app, where clearing a profile actually lives.

**Synchronous write path (read-your-writes).** XRPC clients expect `createRecord` to return the final AT-URI/CID and to read the record back immediately. The request path is therefore synchronous end-to-end: validate → reverse-translate → commit to Fauna → project → repo append → sign → firehose emit → respond. This works *because* rkeys are deterministic from the Fauna post's creation instant — the AT-URI is knowable the moment the Fauna post exists. The repo append rides the same single per-user repo-writer funnel as the projection loop (§ Constraints, C1) — there is exactly **one** writer to the MST, fed by two sources.

**Native-records journal (unmappable lexicons).** Records with no Fauna equivalent (threadgates/postgates, `app.bsky.graph.list*`, starter packs, labeler-service records, …) land in an append-only **native-records journal keyed per user, held in nest state** — *not* bridge-local storage. The bridge materializes the MST from (Fauna projection) ∪ (native journal). Consequences this preserves:

- **"The repo is derived state" survives with a scoped restatement:** the repo/carstore is re-derivable from *nest-held* state — now two nest-held sources instead of one. Nothing precious ever lives only on the bridge (`atproto-identity-custody.md` § Key custody and per-identity seniority keeps its "only key material is precious" property, with the journal joining Fauna state on the nest side of the line).
- Deletion/tombstones: external `deleteRecord` on a round-tripped record = the corresponding Fauna tombstone; on a journal record = a journal tombstone entry. Both re-derive.
- Rejected alternative — **bridge-local native store**: makes the bridge's storage precious (new backup surface, new loss mode, breaks the mirror's crash story). Rejected alternative — **repo-authoritative external writes** (write MST first, ingest into Fauna async): reintroduces the bidirectional-sync cost the 2026-03-17 review rejected and breaks re-derivability outright.

**Refusals are explicit.** A write we do not accept (refused lexicon, refused endpoint, immutable-record `putRecord`) returns a proper XRPC error (`InvalidRequest` with a message naming the policy) — **never a silent drop, never a silent accept-and-ignore** (the e2e point-11 lesson applied to a protocol surface).

**Firm-boundary restatement (decided wording — lands in `atproto-pds-bridge.md` § Firm boundaries when the S3 translator makes it live, per C2; that doc owns the claim):** "never `putRecord`" binds the ***post path*** (Fauna posts are immutable → create/delete only — which matches the network: Bluesky posts aren't editable either). It does **not** bind mutable-singleton lexicons (profile), whose sanctioned update path is a repo `update` op — driven by the projection loop for Fauna-side edits, and by round-trip-through-Fauna for external `putRecord`s. External apps' writes never touch the MST directly in either case; everything funnels through § Constraints C1's single per-user repo writer.

### D10 (direction decided 2026-07-23; mechanism RATIFIED 2026-07-23) — external-app posts are authored by a delegated per-account signing sub-key

**The problem the F0 sketch left unspecified (surfaced 2026-07-23 by a two-pass code recon).** D1 says an external `app.bsky.feed.post` write "becomes a Fauna post … the consume-side ingestion pattern … as if composed in a Fauna app." On contact with the code this is underspecified and its two phrasings conflict:

- A Fauna `Post` is content-addressed and **signed by its `author`'s `ActorKeypair`**; the signer *must equal* the author (`libs/fauna-core/src/encoding.rs`, `signer_public_key()` returns `&self.author.0`). `ingest_post_core` (`bins/fauna-nest/src/routes.rs`) → `classify_encrypted_post` (`storage/sealed.rs`) **verifies that Ed25519 envelope** (`PostSignatureMismatch` otherwise), and the **federation receive path** (`federation_handlers.rs`) *independently* re-verifies it against `post.author`. So a first-class, federating Fauna post **requires an identity signature**.
- At external-write time **no Fauna identity key is present server-side** — the user is in bsky.app, not a Fauna app; the identity key is client-custody only. The one keyless-authoring precedent (ActivityPub inbound: `synthetic_actor_id` + **bare/unsigned** `Post` + `store_post(Some("activitypub"))` + a `content.source` tag) attributes to a **synthetic stranger identity** and its bare posts **cannot federate** (they fail `verify_envelope`) — the wrong shape for the hosted user's *own* posts. There is **no delegated/device signing key model** in `fauna-core` today (`ActorKeypair` is the sole authoring key; task-delegation and capability-grants exist but neither authorizes authoring a `Post`).

**Decision (user-ratified direction, 2026-07-23).** External-app-authored posts are signed by a **delegated per-account authoring sub-key**, distinct from the identity key:

- The user's client authorizes a dedicated **authoring sub-key** via an **identity-signed delegation** ("sub-key `K` may author `Post`s for actor `A`, until revoked"). The identity key itself **stays client-only — never server-held** (the login.md invariant holds literally: what the server gains is a *delegated, revocable, non-identity* authoring credential, not the identity key).
- The sub-key is **server-held** (sealed, home-nest/bridge custody — the same custody class as the repo signing key the hosted account already trusts the bridge with). Posts it signs are **genuinely verifiable**: any nest accepts a `Post` whose signer is `K` when a valid delegation `A→K` accompanies (or is resolvable for) it. This preserves end-to-end unforgeability against *relaying/forwarding* nests — only the account's own home nest holds `K`, exactly the trust already inherent to hosting a full PDS (the bridge already signs the ATProto repo commits on the user's behalf).
- **Rejected alternatives** (recon 2026-07-23): (a) *home-nest-vouched, unsigned real-ActorId post* — least code but a compromised relaying nest could forge posts attributed to the user (today it provably cannot); (b) *synthetic keyless identity* — not the user's own post; (c) *ATProto-only, non-federating* — a Fauna follower would see bsky.app posts only through ATProto, an asymmetry. All three bend a different guarantee; the delegated sub-key is the only option that keeps the user's real identity, preserves third-party unforgeability, and federates unchanged.

**Mechanism (ratified 2026-07-23 — grounded in a code recon; each piece's owner doc named inline per the one-owner rule).** The load-bearing discovery: **the delegation chain D10 needs already ships.** `DeviceAuthorization` (`libs/fauna-core/src/data.rs` — identity-signed, `{actor_id, device_key, capabilities, created_at, expires_at}`, with `Capability::Post`/`UpdateProfile` in its vocabulary since inception) is the cert, and the broadcast-KeyBlob mint already verifies the full author/signer/cert/capability chain (`fauna_core::subscription::crypto::verify_key_blob_signature`, cert traveling with the payload in `EncryptedKeyBlobUpload.signer_auth`). D10 is that existing model applied to authoring kinds — no new cert type, no new chain shape:

- **Cert.** A `DeviceAuthorization` `{actor_id: A, device_key: K_pub, capabilities: [Post, UpdateProfile], created_at, expires_at: None}`, signed by A's identity key (sign-over-CID, embed-as-bytes). Owner of the cert model: [`devices.md`](devices.md) § DeviceAuthorization — this surface joins as its third consumer, the *server-held authoring sub-key*. `Capability::Post` authorizes signing `Post` **and** post-`Tombstone` envelopes (the create/delete repo-write pair); `UpdateProfile` authorizes `Profile` envelopes (consumed at F2.3 — minted up front so F2.3 needs no re-ceremony). Provisioning refuses a cert for this surface carrying anything outside that enumerated set (no `All`/`ManageSubscribers`/`RenewBearer` — scope minimalism).
- **`K` custody: home-nest-held, per-account** (the direction's "home-nest/bridge" disjunction settled to home-nest). Two grounds: the ratified one-nest-round-trip F2 write path signs where reverse-translation happens — nest-side — and bridge-sealed custody adds no real protection against the nest, which roots bridge attestation anyway. Prior art, not a new custody class: the nest already holds per-user signing keys and signs protocol events on users' behalf — the Nostr per-user keypair and the NIP-46 bunker signer, at rest under the **nest-internal key-encryption key** with per-purpose domain-separated contexts ([`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Nest-internal key-encryption key; K's taxonomy entry lands there in this commit). K is an Ed25519 keypair minted nest-side on first fetch (provision-on-read, first-write-wins — the session-secret discipline), secret at rest KEK-wrapped in a new `atproto_authoring_keys` table (`actor_id` PK — one authoring sub-key per account; row also carries `K_pub` + the uploaded cert), `SecretBytes` in memory, never leaving the nest process. `K_pub` is public.
- **The cert travels WITH the post** (settled against resolve-from-the-author's-nest: verify-on-receipt stays self-contained — no availability coupling on federation, and re-serve/re-federate/backup/export all keep working from stored bytes alone). Carrier: the embed-as-bytes wire gains an optional third field `signer_auth` (the cert's own embed-as-bytes), `#[serde(default, skip_serializing_if)]` — additive; a wire without it is byte-identical to today's. Owner: [`../architecture/serialization.md`](../architecture/serialization.md) § Embed-as-bytes + the delegated recipe under § Sign-over-CID. `fauna.federation.post.forward`/`post.delete` grow a matching optional field (additive; an old peer drops it and fail-closed-refuses the forward — acceptable skew: existing traffic is untouched, old peers simply don't accept delegated posts until upgraded).
- **The verification relaxation is uniform and fail-closed.** `Signed for Post`/`Tombstone` **keep returning the author key** — so every un-upgraded `verify_envelope` site *rejects* a delegated post rather than accepting an unverified one (deny, never forge; this is what makes the rollout safe). The chain verify is one new `fauna-core` helper beside `verify_envelope` (recipe owned by `serialization.md`): (1) the value's envelope verifies under the **author** key → accept as direct (an attached cert is ignored); else (2) cert present and its envelope verifies under `cert.actor_id`; (3) `cert.actor_id == value.author`; (4) the kind's required capability (or `All`) ∈ `cert.capabilities`; (5) `expires_at`, when present, ≥ the value's `created_at` (signer-asserted — revocation bullet carries the caveat); (6) the value's envelope verifies under `cert.device_key`. F2.2 upgrades exactly four sites: `classify_encrypted_post` (`bins/fauna-nest/src/storage/sealed.rs` — the `fauna.posts.create`/ingest gate), the federation `post.forward` + `post.delete` receive verifies (`federation_handlers.rs`), the shared client read `fauna_client_core::post::decode_post` (the single face wasm + FFI expose to all 7 apps), and `decode_tombstone`. Intended general consequence: any `DeviceAuthorization` granting `Post` makes its `device_key` a valid delegated author — the capability-restricted-secondary-device model of `devices.md` working as designed, not an atproto special case.
- **Mint ceremony (client-side; rides the hosted-enable flow).** Enabling the full-PDS level fetches `K_pub` (`fauna.bridges.atproto.fetch_authoring_key`, User class — mints K on first call), builds + identity-signs the cert, uploads via `fauna.bridges.atproto.provision_authoring_delegation` (nest verifies: caller is A, envelope valid, `device_key == K_pub`, capabilities ⊆ the enumerated authoring set, `expires_at` absent-or-future). Until a delegation exists, F2's round-trip post arm refuses with the D6 **fauna-surface** sub-type (the error names the Fauna-app authorization step). The atproto page's hosted level shows the delegation (authorized date, revoke); concrete element IDs are proposed with the F2.2 app leg (net-new IDs need user approval, § App surface).
- **Revocation (decided): revoke destroys the sub-key; already-published posts stay valid.** Client-driven `revoke_authoring_delegation` deletes the `atproto_authoring_keys` row — cert + K secret die (recreatable state: re-enabling mints a fresh K + cert; the deletion comment cites this). Un-host / account deactivation cascade the same delete; the kill-switch OFF suspends use non-destructively (external writes only arrive through sessions it already refuses). Already-federated/stored posts stay verifiable forever — the cert is embedded, and a post authorized at creation stays authorized, the same immutability stance as identity-signed history; the user's removal tool is the normal tombstone path (which K may also sign, under `Post`). Residual, accepted: a *compromised* K could sign back-dated posts (no revocation registry at verify time) — reaching K requires home-nest compromise, the position that already forges the account's entire ATProto side via the repo signing key; what D10 newly adds there is Fauna-side forgery scoped to the enumerated capabilities, user-chosen, revocable, and auditable from the signed bytes themselves (the Audit bullet below owns that mechanism; its surface landed 2026-07-31 — § Implementation status today). **At identity succession the delegation dies with the old identity** (future-authority class); the successor re-mints at re-enable; delegated posts stay attributed like all signed history. ⚠ **That sentence was ratified when the delegation shipped and had NO implementation until 2026-08-12** — it cited a table row in [`succession-aftermath.md`](succession-aftermath.md) § Re-key scope that the same section's registry conversion later deleted, so the ruling pointed at nothing while `record_succession` did nothing with the row. It is now carried where a ruling can be *executed and tested* rather than only stated: `atproto_authoring_keys` declares `Succession::Burn` in `bins/fauna-nest/src/db/actor_tables.rs`, and both the ceremony and the boot reconcile execute every declared burn — this row included — through the shared registry-driven `execute_burn_legs` loop (`bins/fauna-nest/src/db/successions.rs`; the earlier per-domain `burn_the_atproto_authority_plane` function was folded into this generic mechanism 2026-08-15), and the registry's data-driven gate fails if the row survives either path. The whole hosted-PDS plane was ruled in that pass (the authority half burns, the identity half moves) — [`succession-repoint-axis.md`](succession-repoint-axis.md) § Implementation status today owns the reasoning.

- **Expiry binds at THREE points, which ask three different questions (ratified 2026-07-29, closing security finding).** `expires_at` is optional on the cert, but where a user sets one it must actually bind — [`../principles.md`](../principles.md) (`:64`) requires capability grants be **time-bounded**. (a) **Provision time** — `provision_authoring_delegation` refuses a cert already past its expiry (the absent-or-future check in § Mint ceremony above). (b) **Authoring time** — every path that signs with `K` first compares `expires_at` against the **wall clock**, and a lapsed cert is treated exactly as no delegation at all: the D6 *fauna-surface* refusal, which is also the right remedy, since re-provisioning is precisely what the user must do. (c) **Verify time** — the chain verify's step (5) above compares `expires_at` against *the value's own* `created_at`, deliberately **not** the wall clock, so an already-published post stays verifiable forever (the immutability stance the Revocation bullet takes). **(b) cannot be folded into (c):** the round-trip write arm adopts the record's `created_at` verbatim from the external app (§ F2 detail), so a `created_at`-relative comparison would be measured against a value the constrained party itself chooses, and the expiry would bind on nothing — a failure mode distinct from the compromised-K residual the Revocation bullet accepts. ⚠ `Timestamp` is **microseconds**; a millisecond clock reads ~1000x small, puts every real expiry in its own "future", and disables (a) and (b) silently. **Accepted residual:** back-dating by an app whose delegation is *live* stays possible and is in-scope for the grant — bounding record-vs-now skew generally is a separate product call, deliberately not bundled here, because it would change the ratified `createdAt`-adoption behavior for legitimate old-content import too.

- **Audit (ratified 2026-07-29; the surface LANDED 2026-07-31 — § Implementation status today).** [`../principles.md`](../principles.md) (`:63-69`) requires a grant be **audited from the user's own client**, and for D10 the audit surface is **the delegated content itself, verified client-side** — never a nest-read log. Ground: `verify_authoring_envelope` already computes `AuthoringOrigin::{Direct, Delegated{device_key}}` on every read, and the origin bit is **tamper-evident in the only direction that matters**: `signer_auth` rides *outside* the signed bytes, so stripping it from a delegated value makes verification FAIL rather than read as direct (masquerading as direct would need the identity key), while attaching a cert to a direct value changes nothing (chain step 1 verifies direct first, cert ignored). Rendering the computed origin is therefore client-authoritative audit in exactly the [`../ui/nests.md`](../ui/nests.md) § "never a nest read" sense — the signed bytes *are* the log, preserved at rest (`ingest_post_core` and `ingest_profile_core` both store the full `signer_auth`-carrying wire) and across federation, with no new column and no wire change. **Ratified shape:** (a) the shared read faces — `fauna_client_core::post::decode_post` and `fauna_core::encoding::decode_profile` — return the `AuthoringOrigin`, and it reaches a **user-visible surface** (the `delegated-origin-badge` on the post card; IDs user-approved 2026-07-31, tui lead) — an exported-but-unrendered origin would be the dark-capability class again; (b) complementary and **advisory only**: `last_used_at` on the delegation row (the `atproto_oauth_grants` shape its sibling table already carries) — nest-maintained and therefore *not* forensics, the same honest-bound framing the nests.md grant row uses. **The OAuth half of (b) is BUILT as of F4 slice 8a:** the nest stamps `atproto_oauth_grants.last_used_at` inside the rotation transaction, which is the one moment it observes a grant in use — access-token calls verify bridge-side and never reach the nest — so a recent value proves use and an old one proves nothing, which is exactly why the column is advisory. Rendering it on the connected-apps row is slice 8b's. **Honest bound:** this audits what the client *sees*; a compromised nest can still withhold content from the owner's own feed (generic compromised-nest behavior, not D10-specific) — but any delegated value any client is ever served is identifiable as delegated, after the fact, from bytes alone.

Until F2.2 lands these pieces, F2's **round-trip for posts remains blocked in code** (the journal path, membership classifier, and reverse-translate parsing are signing-independent and proceed — F2.1).

## Problem 2 — auth without passwords

**The invariant** ([`login.md`](login.md): "A single Ed25519-keypair-based auth model. No passwords") is not negotiable, and this design does not bend it: **Fauna identity auth stays key-based; nothing here adds a user-chosen, memorized secret anywhere.** What the full PDS adds is machine-generated **capability credentials** for an external protocol surface — a class Fauna already ships: mail's auto-generated bridge password and preferred OAUTHBEARER token ([`mail-credentials.md`](mail-credentials.md) § KDF choice / § Auto-generated bridge password — generated ≥128-bit-entropy secrets, minted/revealed/rotated/revoked from the client, nest never holding a recoverable copy). The ATProto surface gets the same treatment.

### D3 (decided) — the ladder: both rungs, app credentials first

Both rungs are required — neither alone suffices (the 2026-07-19 § Ecosystem reality snapshot: the official client still logs in via `createSession` with no announced sunset, while a growing third-party segment is OAuth-only; re-verify at § Reconciliation). Rung 1 ships in F1, rung 2 in F4.

**Rung 1 — app credentials (F1; the pragmatic v1).** ATProto "app passwords" reframed as what they actually are here: *minted capability credentials*.

- **Minted, listed, revoked exclusively from Fauna apps** (bridge settings, all 7 apps — the only configuration surface). Never mintable from the XRPC side (`com.atproto.server.createAppPassword` is refused — § Problem 4): an external session must not be able to escalate into more credentials.
- **Generated** in the ecosystem's `xxxx-xxxx-xxxx-xxxx` shape (login-box compatibility) from OS CSPRNG entropy; the user never chooses it. The no-passwords argument, made explicitly (decided): the invariant ([`login.md`](login.md) § Goal — "A single Ed25519-keypair-based auth model. No passwords") bans user-chosen memorized secrets as *Fauna identity auth*; it has never banned minted machine credentials for external-protocol compatibility — mail's generated PLAIN bridge password and OAUTHBEARER token ([`mail-credentials.md`](mail-credentials.md) § Auto-generated bridge password) are the standing precedent, ratified and shipped. Manual entry of a user-chosen secret is **not offered at all** on this surface (stricter than mail, which allows it behind a warning): no ATProto client needs a memorable secret, so there is no reason to permit a weak one.
- **Custody — client side mirrors mail; nest side deliberately diverges from it.** The minting user's client keeps the recoverable copy for re-reveal on the account plane — `fauna.state.atproto`, one sealed row per credential, synced across the account's own devices ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) owns the kind) — (the mail token-reveal pattern, `mail-credentials.md` § OAUTHBEARER token issuer — that half is verbatim prior art). Nest-side, mail stores **no verifier at all** — its model is KDF-to-unwrap (the credential unwraps a nest-held sealed capability blob, `bridge_wrapped_mls_blobs`/`bridge_wrapped_submission_tokens`, and the nest can open neither). This surface has **no sealed capability for the credential to wrap** — posts are plaintext-floor public data and preferences are served under the bridge's role capability, not per-credential — so a wrapped-blob shape would mean inventing a blob for shape's sake. Instead nest state holds a **verifier** (Argon2id, client-computed, PHC-serialized so parameters travel with the hash and the nest never sees the secret even at mint) + metadata (label, created, last-used, DM flag). Deliberate divergence, recorded 2026-07-19 after a code recon confirmed mail's actual shape; detail in § Detailed design → F1. The bridge verifies at `createSession` against fetched verifier records; it never stores credentials.
- **Scoped:** per-credential DM-access flag at minimum (the ecosystem's app-password precedent); app-credential sessions are refused account-mutation endpoints regardless (§ Problem 4).
- This one rung already makes bsky.app login work: bsky.app resolves the handle → our PDS → `createSession(identifier, secret)`; it cannot distinguish an app credential from a "main password", and a Fauna-hosted account simply *has no* main password — every login is a revocable, per-app credential. Arguably a *better* posture than the ecosystem default.

**Rung 2 — ATProto OAuth provider (F4; the target).** The spec-mandated surface (PAR, PKCE, DPoP-bound tokens, AS + protected-resource metadata, client-metadata resolution — exact requirements re-verified at § Reconciliation; § Ecosystem reality). The genuinely novel Fauna piece is the **consent ceremony with no password to type — decided:**

- **The ceremony is approve-in-Fauna-app (device-authorization pattern):** the authorization page (served by the PDS surface) displays a short code + pushes a consent request; the user confirms in any logged-in Fauna app (which authenticates the approval with their Ed25519 identity over normal WS-RPC). The browser session never holds a Fauna secret; the Fauna app is the root of trust, exactly as it is for every other grant. Deep-link/QR handoff into an installed Fauna app is a mobile nicety layered on the same ceremony, not load-bearing.
- **Contingency, not shipped by default — app-credential entry on the consent page** (authenticate the grant with a rung-1 credential). Weaker (a phishable page) and a second ceremony to maintain; build it only if live F4/F5 testing proves the primary infeasible for some client class, and record why here if so.

## Problem 3 — private data reaches the bridge: the revocation story changes

**The ratified claim at stake** (`atproto-pds-bridge.md` § Disable & revocation, layer 3): *"the PDS bridge holds no read capability over sealed content … there is nothing to revoke."* True for the mirror; **false for the full PDS**, and the claim must be *updated with new scope, not silently broken*. New non-public data classes the bridge touches:

**D4 (decided) — custody table.** All non-transient private data lives in **nest state**; the bridge holds nothing precious (C6) and caches in memory only:

| Data | Custody (decided) | Notes |
|---|---|---|
| ATProto preferences (`putPreferences` — saved feeds, muted words, labeler subscriptions: **private**) | **Nest state** (source of truth), served to the bridge over a `fauna.bridges.*` kind under a declared capability; bridge caches in memory only | Never bridge-local; joins normal nest backup |
| App-credential verifiers | Nest state (hash only — § Problem 2) | Bridge verifies via nest kind |
| Sessions (access/refresh JWTs the bridge mints/verifies) | Bridge-held signing use of nest-sealed key material; session **registry** in nest state so Fauna apps can list/revoke | Re-derivable/expirable — not precious |
| OAuth grants + DPoP key bindings | Nest state (the grant registry **is** product data — it feeds the connected-apps UI) | |
| DM traffic (chat.bsky proxying) | **Transit only** — request/response pass through bridge memory; nothing persisted | Bluesky DMs are not E2EE; this is inherent to hosting the account, surface it honestly in the enable copy |

**D5 (decided; LANDED 2026-07-23 with F3 phase 4 preferences) — layer-3 restatement** (the wording below now lives in `atproto-pds-bridge.md` § Disable & revocation, landed in the preferences commit — the first bridge private-data handling): from "nothing to revoke" to an **enumerated capability set**: the bridge holds (a) sealed DID signing-key blobs (unchanged, layer 1), (b) a preferences-read/write capability, (c) session/grant registry access. Bridge revocation (layer 1) then additionally tears down: all live sessions, all OAuth grants' usability (DPoP-bound tokens die with the AS keys), service-auth minting, and the in-memory caches (teardown includes process restart via the supervisor, so no plaintext outlives revocation).

**Grants join the audit surface.** Every OAuth grant and app credential is a row in a **connected-apps surface in all 7 apps**: app name/client-id, scopes, created, last-used, revoke. This is the product-invariant grant vocabulary applied unchanged (`principles.md`: per-scope, time-bounded, revocable, audited from the user's client; prior art: the capability audit/revoke surface holders already appear in, e.g. the mail MDA's — `monetization.md` § Holder identity). Per-user disable (layer 2) must also tear down that user's sessions + grants, not only stop projection (§ Constraints C8).

## Problem 4 — scope of the served lexicon surface

**D6 (decided) — three explicit buckets**, with refusals sub-typed. Membership below is the design; each F-slice finalizes only the *per-endpoint residue* (new endpoints the ecosystem adds, exact error strings) against the then-current lexicon set. Refusals come in three flavors, and the distinction is load-bearing: **policy-refused** (permanent — the operation contradicts a Fauna invariant), **fauna-surface** (the capability exists but only in Fauna apps — the error message says where to go), and **deferred** (planned but unbuilt — the error says "not yet", and the classification here prevents a later session reading a refusal as permanent policy):

| Bucket | Surface | Notes |
|---|---|---|
| **Served locally** | `com.atproto.server.{createSession,refreshSession,deleteSession,getSession,describeServer}`; `com.atproto.repo.{createRecord,putRecord,deleteRecord,applyWrites,uploadBlob,getRecord,listRecords,describeRepo}`; `com.atproto.sync.*` (mirror scope, already public); `com.atproto.identity.{resolveHandle,…}` restricted read subset; `app.bsky.actor.{getPreferences,putPreferences}` | Writes go through § Problem 1's funnel; `uploadBlob` ingests into the Fauna media path (BLAKE3/FastCDC store) with the sha256-CID mapping the mirror already does in reverse |
| **Proxied** | `app.bsky.*` reads → AppView; `chat.bsky.*` → chat service; (video/other services as the ecosystem defines) | Via `atproto-proxy` header + `com.atproto.server.getServiceAuth` service JWTs signed with the user's repo signing key (bridge-held — no custody widening; `atproto-identity-custody.md` § Key custody and per-identity seniority). For **hosted** accounts this *replaces* the consume-side's OAuth-based DM poller — the switch is D7 below |
| **Refused** (explicit XRPC error, documented, sub-typed) | *Policy-refused:* `com.atproto.server.createAccount` (accounts exist only via Fauna onboarding); `com.atproto.identity.updateHandle` (the Fauna handle is authoritative; handle changes flow Fauna→ATProto, derived at read); email/password account-management endpoints (no such account model). *Fauna-surface:* `createAppPassword`/`listAppPasswords`/`revokeAppPassword` (credentials mint only in Fauna apps — no session escalation); `deleteAccount` (destructive account ops live in Fauna apps). *Deferred:* account-**migration** endpoints (`activateAccount`/`deactivateAccount`, migration-oriented `getServiceAuth`) | Migration endpoints are **deferred, never policy-refused** (decided): outbound migration is a *guarantee* per `atproto-pds-bridge.md` § Design horizon 3, and repo export (`sync.getRepo`) is already public — the "not yet" error names the planned outbound-migration path so no session hardens the refusal into policy |

**D7 (decided) — the DM-path switch is the identity backing itself.** The mirror doc already makes the two backings mutually exclusive per user (consume-side external DID *or* nest-hosted DID — its § Relationship table). That existing choice is the switch: an account whose ATProto backing is nest-hosted reads DMs via service-auth chat proxying, and the consume-side OAuth DM poller **never runs** for that account; no new toggle, no per-feature flag, no state in which both paths poll. F3 implements the gate where the poller schedules itself (keyed off the stored backing, which the "DID is data" rule already persists).

**D8 (decided) — one authorization decision point, two credential planes.** The granular OAuth scope grammar gates service proxying by `lxm`+`aud` (`rpc:` scopes — § Ecosystem reality), so OAuth-scope enforcement and proxy enforcement are one decision, not two. Therefore: build a **single per-request authorization module** — input (credential plane, session, endpoint/`lxm`, target `aud`), output allow/deny — in **F3**, with app-credential sessions as its first caller (an app-credential session carries the ecosystem's app-password-equivalent grant: full repo + rpc, minus account-mutation endpoints, DM access per the credential's flag); the F4 OAuth plane (granular scopes + permission-set expansion) becomes its second caller. This is C1's funnel philosophy applied to authorization — F4 adds a *caller*, not a second enforcement path. It also means F3 and F4 stay separate slices deliberately: the coupling the ecosystem snapshot flagged lives inside this one module, not across the slice boundary.

## Detailed design (third pass, 2026-07-19 — same best-guess status as D1–D9; re-verified wholesale at § Reconciliation)

Everything below is the implementation-ready layer under D1–D9: what the F-slices build, named concretely so they inherit specs, not just decisions. Prior-art anchors were verified against code 2026-07-19 (file:line cited inline); the mirror chain will move some of them — § Reconciliation step 1 re-pins every cited anchor. Two framing rules apply to every knob named here, per the product invariants: **every tunable is either a hard-coded Rust/Go constant or a user/admin choice surfaced in all 7 apps — no config file, env var, or flag anywhere in this design**; and every new data shape defaults to user-revocable from the client.

### Wire & process topology

- **The XRPC/OAuth surface terminates in the `fauna-atproto-bridge` process** (the S1 bridge grows it; role `atproto.pds`), never in the nest — the same isolation rationale as the mirror. Public HTTPS reaches it the way it reaches every other public Fauna surface: the SNI router routes the PDS hostname(s) to the bridge's loopback listener with **PROXY protocol v2** carrying the client IP (the nest's anonymous surfaces already key rate limits on exactly this — `bins/fauna-nest/src/anonymous_rate_limit.rs`). TLS custody and the loopback port split are packaging wiring (artifact-set IPC, decided at the F1 packaging step on the mail-bridge precedent — cert blobs sealed to the bridge's attested x25519).
  **F1 packaging resolution (2026-07-20).** The SNI router is pure L4 pass-through (backends terminate their own TLS — `bins/fauna-sni-router/src/main.rs` module doc), so two things follow. (1) **The PDS hostname is the dedicated subdomain `pds.<primary-domain>`** — the apex SNI is nest's `--default` route and an L4 router cannot split one hostname by path, while XRPC must never terminate in nest (above). The `mail.*` wildcard-route precedent applies verbatim: `pds.*` → the bridge's loopback XRPC port, listed in `--send-proxy-to`. (2) **The bridge terminates `pds.<domain>` TLS itself** via the sealed TLS-cert blob fetch (the MDA's `internal/tls.Provider` fetch→unseal→cache pattern; `fauna.bridges.fetch_tls_cert_blob` needs its allowlist widened to `BridgeAtprotoPds`), which requires `pds.<domain>` to join the ACME domain set and the deployment DNS matrix (beside `mail.<domain>`/`relay.<domain>`). Consequence: **S2's `pds_endpoint = https://<apex>` derivation (`bridge_blob_handlers.rs`, `fetch_atproto_identities`) flips to `https://pds.<domain>` in the same commit as this wiring** — no earlier (an endpoint nothing serves), no later (the first-impression identity trap binds S3's first firehose emit, and any identity minted against the apex needs a PLC `services.atproto_pds` update op at the flip; pre-flip mints are all placeholder/test-scoped). The listener-side PROXY-v2 wrap landed 2026-07-20 (`proxyproto.New` under `http.Serve`, headerless dials untouched); since 2026-08-14 that wrap also verifies the router-auth TLV before honouring a conveyed source, because the XRPC bind is loopback and its per-IP rate limits key on the peel — mechanism owned by `../architecture/security.md` § Co-resident process trust boundary.
- **Auth classes are route-table declarations** (C5's slots filled): every route registers as `public` (the whole mirror read surface), `app_session`, `oauth_session`, or `session` (either plane). The middleware chain per route: source-IP rate limit → auth-class check (token verify) → D8 authorization → handler.
- **Rate limiting is two-layer.** Bridge-side: per-IP × per-endpoint-class sliding windows (the `anonymous_rate_limit.rs` model; the reusable primitive is `bridge_rate_limit::Limiter`). Nest-side: the PDS-facing kinds get per-caller windows like every other bridge kind. Starting constants (hard-coded; F1/F2 tune before ship, ecosystem-aligned): `createSession` 10/5 min per IP **plus** per-identifier exponential backoff on failures; PAR + token endpoints 30/5 min per IP; authed writes per-actor aligned with the ecosystem's points-per-hour model; public reads at the anonymous-surface default (60/60 s per IP × kind).

### F1 detail — app credentials, `createSession`, tokens

- **Generation (shared Rust, the `password_gen` pattern):** `generate_app_credential()` → `xxxx-xxxx-xxxx-xxxx`, 16 symbols from a 32-symbol lowercase alphabet ≈ 80 bits, OS CSPRNG, rejection-sampled. 80 bits is not the mail token's 128, but it rides Argon2id + the rate-limit stack, and offline attack of a *random* 80-bit secret is already infeasible; the shape is fixed by ecosystem login boxes. Client computes the Argon2id verifier at mint (mail's PLAIN parameters, `mail-credentials.md` § KDF choice; PHC-serialized so old credentials verify under their own params forever), calls `provision_app_credential`, then persists the secret as the account plane's `fauna.state.atproto` row at its `credential_id` (an `AtprotoAppCredential` — a `MailCredential`-shaped struct: `SecretByteBuf` secret, kebab-derived `credential_id`, `libs/fauna-core/src/data.rs`). Re-reveal reads that row back, on any of the account's devices; the page machine reaches the plane only through its injected credential seam (`fauna_atproto_settings_machine::AtprotoCredentialStore` — web's ATProto chunk through the account port, [`../architecture/account-client-lifecycle.md`](../architecture/account-client-lifecycle.md) § *The account port*); a persist that seam refuses hands the secret back once, flagged as not re-revealable. The settings state machine lands beside the existing shared bridge-settings core — the placement question this line left open was **resolved at F1 (2026-07-22)**: the typed `fauna.bridges.atproto.*` call surface joined `fauna-client-bridges` (which already owned the namespace and the credential primitives) and the machine became its own `fauna-atproto-settings-machine` crate, the thin-client ↔ machine two-layer split every page machine uses (§ Implementation status today).
- **Provisioning is insert-only — a duplicate `credential_id` is refused, never upserted** (security-review finding, fixed). `credential_id` is kebab-derived from the label, and a device's collision-avoid can only see credentials it has already refreshed; two devices minting the same label therefore race on `(actor_id, credential_id)`. An upsert would replace the first device's verifier — retiring a working app password with no signal on either side — so the nest refuses with `fauna.bridges.atproto.credential_exists`. Safe because the settings machine calls the nest **before** persisting the secret locally and surfaces provision errors: the race degrades to a visible retry rather than a silent loss.
- **`createSession`:** resolve identifier (handle or DID) → fetch verifier rows → Argon2id-verify **bridge-side** (keeps the secret out of the nest and the CPU cost off it) → `record_session` → mint tokens. Failures are uniform (`AuthenticationRequired`) with no user-enumeration signal, and count into the per-identifier backoff.
- **Token model:** access JWT — HS256 under a bridge-scoped sealed secret (verified only by the bridge; no cross-service key distribution problem), claims `sub` = user DID, `aud` = the PDS service DID, `scope` = `com.atproto.appPass` (or the ecosystem's DM-privileged variant when `dm_allowed`), 60 min, plus the private `fauna_actor` claim (hex actor id) described next.
- **The Fauna actor id is its own claim, and `sub` is the account's real DID (decided 2026-07-29, F2.2 slice 4d).** Every nest-facing call the bridge makes — `record_session`, `refresh_session`, `end_session`, `ingest_external_write`, D8's input — needs the 32-byte actor id, and the bridge holds no session state to look it up from. F1 encoded it *into* `sub` as a `did:fauna:<hex>` placeholder, which made `sub` non-conforming and, because the projection loop always committed under the real `did:plc:`, left the two halves of the bridge maintaining **two repos for one account** (§ Implementation status today, the 4c bullet). The convergence puts each value where it belongs: `sub` carries the real DID, resolved nest-side and handed over as `login_did`, and the actor id rides `fauna_actor`. This changes no trust property — the token is minted *and* verified by the same bridge under the sealed secret, so the actor id was already a claim, merely smuggled inside the DID string — and it keeps the auth hot path free of a DID→actor lookup, which would need a cache that refuses valid tokens for any account minted since its last refresh. A token without a well-formed `fauna_actor` is refused rather than defaulted, which is also what retires every pre-4d token.
- **`createSession` requires an ACTIVE hosted identity (decided 2026-07-29, F2.2 slice 4d).** `fetch_app_credential_verifiers` answers `login_did` — the DID this account may open a session as — filled **only** for an `active` identity row with a minted DID, and `None` otherwise (no row, `pending`, `deactivated`, `deleted`). `None` joins the existing uniform-failure set (unknown identifier / kill-switch OFF / no credentials), so no enumeration signal leaves the box. The rule lives nest-side because identity status is *interpretation*, which stays out of Go for the same reason D8's planes do. Beyond the obvious (no DID → no repo to serve, nothing for `getSession` to name, no `iss` for service auth), this is what makes the ratified step-down suspension real: [`atproto-pds-bridge.md`](atproto-pds-bridge.md) § Disable & revocation suspends the account's **entire** ATProto presence including live app sessions, and revoking those sessions accomplished nothing while the next `createSession` re-issued one — the login path never consulted identity status, and a step-down deliberately does not touch the user's own kill-switch (persisting `false` there would clobber a user-owned toggle and leave it OFF after stepping back up). A DID-form login identifier resolves against the same stored `did` column, so an app can log back in with the `sub` it was handed. Refresh JWT — `jti` = `session_id`, 90 days, **rotate-on-use with reuse detection** (a replayed old refresh token kills the whole session family — the registry makes this a one-row check in `refresh_session`). ⚠ **A re-issued `refresh_session` RPC is a retry, not a reuse (decided 2026-08-02, the atproto `fetch`-pocket replay audit).** The kind is `forbid_replay = false`, which asserts the handler is naturally idempotent ([`../architecture/transport.md`](../architecture/transport.md) § Idempotency and reconnect-with-resume) — and it was not: the idempotency cache is per-connection and `request_auto_retry` re-issues on a fresh one, so a connection dropping mid-refresh re-sent the identical `(presented_jti, new_jti)` pair, whose presented jti the first call had already rotated away. That took the reuse branch, so **a network blip logged the user out of a connected app and wrote a token-theft signal for an event that never happened** — the one signal this table exists to make legible. `refresh_atproto_session` now recognizes its own already-applied rotation (`current == new_jti`) and answers `Rotated` without writing. The reuse rule is otherwise untouched, and deliberately so: the discriminator is the caller's own minted value, and the bridge mints a fresh `new_jti` for every refresh it attempts, so a stolen refresh token always presents a `new_jti` that is not current and still kills the family. Chosen over flipping the kind to `forbid_replay = true` because refusing the retry *is* the logout, and the dedup key was already reachable — the fix-vs-flip rule's *non-idempotent by omission* case. `deleteSession` → `end_session`. Revocation latency for a live access token is bounded by its 60-min lifetime; client-driven revoke also nudges the bridge (`sessions_changed`) to drop its in-memory session cache immediately.
- **`describeServer`:** static — no invite codes, no email verification, `availableUserDomains: []` (accounts exist only via Fauna onboarding; the D6 refusal table is the matching write-side statement).
- **Per-account external-apps kill-switch (user-added 2026-07-20).** A per-account `external_apps_enabled` flag in nest state, **default ON**, surfaced as a toggle on the same settings page. The login surface is already inert-by-construction for an account with no credentials/grants; this is deliberate defense-in-depth against implementation bugs in the auth path, plus a legible off-state for security-conscious users. Semantics: **OFF suspends the account's entire external-app plane** — `createSession` and consent requests are refused (uniformly, no enumeration signal: the same `AuthenticationRequired` as a wrong secret), `refresh_session` is refused nest-side, and the bridge rejects even currently-valid access tokens per-request (it checks its cached flag, refreshed by the `sessions_changed` nudge, so a flip takes effect immediately — not after token expiry). Credential/grant/session **rows are kept**, visible in the app UI, individually revocable; flipping back ON restores usability. Non-destructive and reversible by design — the destructive path is per-row revoke, not the switch. When F3's D8 module lands, this flag becomes one of its inputs (one decision point); until then the F1 middleware enforces it directly. **The switch binds the account's third-party principals too (ruled 2026-10-02).** A principal ([`../architecture/third-party.md`](../architecture/third-party.md) § The principal model) is an external app by every measure the switch names — minted by the same consent card, redeemed at the same `/oauth/token`, listed on the same connected-apps page — so "the entire external-app plane" includes it, Fauna-family scopes and all, and OFF is never "off except for the app that talks to the nest directly". Three legs, one flag. **(1) Minting:** every start's redemption passes `record_oauth_grant`, whose OFF answer (`invalid_grant`, nothing recorded) comes before the transaction that writes the grant and its principal row, so no new principal is born while OFF; the consent card itself is not withheld — it is the user's own surface on their own apps, and the one owner of the refusal is the redemption, where the row would be written. **(2) Refresh:** `rotate_session`'s `disabled` answer, shared by the nest's refresh grant, so a principal's token family is not renewed. **(3) The live session:** the principal session's upgrade gate and its per-RPC dispatch gate read the flag beside the row and the account's authority ([`../architecture/transport-connection.md`](../architecture/transport-connection.md) § Connection lifecycle → *The principal session*; [`../architecture/apps/bridges.md`](../architecture/apps/bridges.md) § Capability-allowlist enforcement → *How the class meets the connection*, rule (a)), refusing with the same uniform shapes a revoked row gets — `401 invalid_token` at the upgrade, the every-kind refusal per call — so OFF is not distinguishable from revoked from outside; and the flip to OFF sweeps the account's live principal sessions `4401` after its write, as the roster revoke sweeps its principal's, because a refused socket left open is still a Push recipient once the event door exists. This is the nest-side analogue of the bridge's per-request check on its cached flag: immediate, never at token expiry. Non-destructive as everywhere here: the principal row, its grants and its sessions are kept and listed, and ON restores them with nothing to redo — the destructive verb stays `fauna.principals.revoke` (third-party.md rule 4). **Page home unchanged:** the toggle stays `atproto-external-apps-enable` within the full-PDS level; an account below that level holds the flag at its default ON and has the principal's revoke as its only off-switch. Re-homing the toggle to the connected-apps page, where every external app is now listed, is a ui.yaml page-scope change that waits on user approval; the roster rendering a paused principal as paused, and the toggle's copy saying it pauses connected apps, are app work the tui queue carries.

### F2 detail — the synchronous write path, journal, blobs

- **One nest round-trip per write batch.** `createRecord`/`putRecord`/`deleteRecord`/`applyWrites` → bridge structurally validates (indigo lexicon + CBOR/size caps) → **one** `ingest_external_write` call carrying the whole batch → nest processes it transactionally: round-trip rows translate into Fauna mutations **via the delegated-sub-key authoring path of D10** (the reverse-translate module lands in `libs/fauna-bridge-atproto` — new module beside the existing inbound `translate.rs`, which maps the *other* direction and is not it — and produces the intermediate post/profile shape that the D10 sub-key then signs — the F0 "normal post/profile creation paths" phrasing is superseded by D10); journal rows insert into `atproto_native_records`; refusals return the D6 sub-typed error. **The signed post is then ingested through `ingest_post_core` — the same path a Fauna app's own post takes** (clarified 2026-07-24 at build: an earlier phrasing here excluded that path as "the identity-signed" one, which stopped being true when F2.2 slice 2a upgraded its `classify_encrypted_post` gate to run the D10 chain verify. Sharing the path is the point — the gate re-verifies the delegated envelope on the real bytes, so the arm cannot emit a post the gate would reject, and the result federates, projects and decodes with no special case. Bypassing it would have created a second, unverified ingest door). **CID source (refined 2026-07-23):** the reply carries per-write `{rkey, at_uri}` — deterministic from the Fauna-side creation instant (D1) and computable before any append — while the **`cid` is filled bridge-side from the C1 funnel's own record-CID computation** (`funnel.go` already computes `dagCBOR.Sum(record)` and the AT-URI internally); there is **no second Rust dag-cbor/CID encoder kept byte-identical to indigo** (the same single-encoder principle already ratified for service-auth signing). The bridge then drives the C1 funnel (apply → sign → persist → emit), reads back the per-op CID, and answers the XRPC call with `{uri, cid}`. `applyWrites` = one funnel commit. The projection loop will also see the new Fauna post via its normal push — the `bluesky_posts` map (with C4's `origin` column) makes that a no-op, which **is** the idempotency story.
- **This funnel is the oracle's `atproto.commit` door (ruled 2026-10-02).** An external write is a third party having the account's repo signing key used on its behalf, and the owner of that class — [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Audience: deployment infrastructure → *The oracle* → *The ATProto classes ride the protocol's own door* — rules that it is carried here, by the ATProto family's own `repo:` scopes, never by a Fauna kind; the three oracle properties the funnel still owes (the per-write live session check on the `ingest_external_write` round trip, the per-session ceiling, the per-operation record) are that section's, and it names the row.
- **A write batch is ALL OR NOTHING (decided 2026-07-29, F2.3 piece 2 — SUPERSEDES the F2.1 "a refusal mid-batch does not roll back the rows around it" ruling).** One refused row means the nest applies *none* of the batch. Per-write refusal **data** is unchanged and still positionally aligned — that half of the F2.1 bullet stands, and is exactly what lets the bridge name the offending row — but the *application* is now transactional. **Why the earlier ruling could not survive:** it was decided while only single-write verbs were served, a world in which "partial" could never arise. `com.atproto.repo.applyWrites`' reply is a results array **or** an error, with no shape for "3 of your 5 writes happened", so applying the good rows and failing the call would leave real Fauna posts — federated, projected, visible on all 7 apps — behind for a write the caller was told did not occur. That is the same "the answer names something that did not happen" failure the first-emit ruling rejects *answer-now-commit-later* for. **Every refusal is decided before the first row is applied, in THREE passes** (the second added 2026-07-29, closing a security finding that proved by execution that one pass was not enough — the original text here claimed the dispositions were the whole enumeration, and they are not). **Pass 1, the dispositions:** every refusal derivable from `(collection, action)` plus the account row — the D2/D6 classifier verdict, the no-delegation account state, the narrower-delegation capability miss. **Pass 2, the pre-flight:** the refusals only the record's own bytes or stored state can reveal — an unparseable post, an unparseable profile, and a delete of a post this actor does not own. Those three used to be raised *inside* the apply arms, which is precisely where all-or-nothing breaks: rows `0..i` are already applied, nothing rolls them back, and the bridge then fails the whole call while **the projection loop carries the applied rows onto the firehose anyway** (no `post_map` row was written, and "already mapped" is exactly its idempotency test). The delete arm was the worst case — a user's post destroyed *and* withdrawn from the network on a call answered as failed. **No adversary is required:** an ordinary app's malformed row reached it, not a crafted one. Parsing is pure, so the arms re-run it and cannot reach a different verdict; the delete authorization has **one owner** (`routes::check_post_delete_authorization`) that the arm still runs as its guarantee. **Pass 3, the input shape (added 2026-07-29, closing a further security finding):** every requirement that is a *pure function of the row* — an over-cap record, an absent record, an absent or blank rkey, an absent or blank cid — decided for the whole batch, **journal rows included** (passes 1 and 2 both return early on a non-round-trip disposition, and the journal arm's four shape errors were the largest part of the gap). These raise an `RpcError` rather than a refusal, and the finding's load-bearing insight is that **the distinction does no work for this rule**: what the ruling forbids is an *outcome* — rows applied, call answered as failed, projection carrying them onto the network — and any mid-loop `Err` produces it just as well as a `refused(…)`. The exposure was latent rather than live, because the Go bridge caps the record at the identical constant and always supplies an rkey and CID before the single `ingest_external_write`, and the kind is bridge-class — but that made the guarantee rest on **a different process having validated first**, an unstated precondition, which is the same false-premise class that produced the previous finding. A guarantee that holds because someone else checked is not one this code can state. Each check has one owner (`require_record` / `require_rkey` / `require_cid`) that the up-front pass and the apply arm both call, so the two cannot drift into disagreeing verdicts. Pinned by `a_whole_call_error_from_a_later_row_still_rolls_back_the_batch`, whose row 0 is a **round-trip post create** — the least reversible thing a batch can do, so a journal-only version would pass against a much weaker fix — mutation-checked by neutering the pass and watching row 0's post survive a failed call. Rows that did not themselves refuse are told the batch was abandoned rather than answered empty, so no result is ambiguous. Pinned by three tests that are only sufficient together: `a_refused_row_rolls_back_the_whole_batch` (a pass-1 refusal), **`a_refusal_only_the_record_can_reveal_still_rolls_back_the_batch`** (a pass-2 refusal — the pass-1 test stayed green through the whole of that earlier gap, so a pin whose refusing row is classifier-decided proves nothing about this), and the clean-batch control, without which an implementation that never applied a batch at all would pass.
- **The round-tripped post adopts the record's own `createdAt` (decided 2026-07-24, F2.2 slice 3).** The external record's `createdAt` is client-asserted and reaches the nest untrusted; the ruling is that the Fauna post takes it verbatim rather than being stamped with the nest's clock. Three grounds. (1) *Native parity* — a Fauna app already asserts its own creation instant (`fauna_client_core::post::build_post` stamps `Timestamp::now()` **client-side**) and no ingest-side skew check exists, so nest-stamping only this surface would be a per-app deviation that closes nothing an ordinary client cannot already do. (2) *Round-trip fidelity* — the projection emits `post.created_at` verbatim back into the record's `createdAt`, so discarding the submitted value would hand the caller back a materially different record than it wrote, against D1's never-silently-alter stance. (3) *No new exposure* — D10 already names back-dating by a compromised `K` as an accepted residual. **Consequence, and why the two halves are pinned by one test:** the projected rkey is `deterministic_tid(created_at, post_id)`, so adopting the record's instant is exactly what makes the `{rkey, at_uri}` answered synchronously the one the record actually lands at — read-your-writes by construction rather than by timing. Should Fauna ever want a creation-skew policy, it belongs at the shared ingest gate for **every** post, never invented per-surface here.
- **Reply, quote, and post-delete round-trips need bridge-supplied target ids (surfaced 2026-07-24, F2.2 slice 3; BUILT 2026-07-29, slice 4b).** A reply/quote names its target by AT-URI and a `deleteRecord` names an existing record by rkey, but a Fauna `Reference` (and a tombstone) needs the target's **Fauna post id**, and nothing resolves AT-URI/rkey → post id nest-side: the rkey derivation is one-way, and the reverse index is the bridge's own `post_map` (`internal/atprotorepo/funnel.go`). The bridge therefore resolves the targets and sends them alongside the record — the same class of bridge-side work as filling the record CID — with the wire field landing together with its producer.
  - **The wire shape is a map, not named per-kind fields (decided 2026-07-29).** `ExternalWrite.resolved_targets` is `AT-URI → Fauna post id` (the earlier phrasing here, "the resolved Fauna post id", was singular and therefore wrong: a post can be a reply **and** a quote at once). A map also keeps reference *kinds* off the wire entirely, which is what lets the bridge stay a pure **resolver** — it answers "what Fauna post, if any, sits at this URI" and never learns which URI meant what. The nest parses the record anyway and is the only side that needs the meaning, so a future third reference kind touches neither the bridge nor the wire. Bounded by `record_refs::MAX_RECORD_REFS`, re-checked nest-side.
  - **The extraction is shared Rust in the always-on pure core (decided 2026-07-29).** Something must read the referenced AT-URIs out of the record so the bridge knows what to resolve, and `fauna_bridge_atproto::record_refs` — walking raw dag-cbor with the *same decoder* `reverse_translate` uses — is that one place, exported over FFI as `atproto_extract_record_refs` and reached through the `RepoWriter` seam (so `internal/atprotopds` stays cgo-free). **Not Go:** a quote reaches a record through two embed shapes, `app.bsky.embed.record` and the one-level-deeper `app.bsky.embed.recordWithMedia`, and a hand-rolled Go walker that learned only the first would silently stop resolving quote-with-media posts — journaling writes that should have round-tripped, with nothing failing loudly. **Not `reverse_translate` itself:** that module stays `client`-gated with no FFI export (the F2.1 decision is *not* reopened), because exporting it would drag `atrium-api`'s 184-crate subtree — tokio, regex, http — into the FFI cdylib that `default-features = false` exists to keep lean. The residual risk is the two modules drifting on *paths* rather than bytes, which a shared fixture corpus pins (`record_refs::extraction_agrees_with_reverse_translate`).
  - **A target that resolves to nothing is not an error** — the write journals, per the ruling below. That is why the extraction is infallible: an unreadable embed must degrade to "no references", never fail a user's write.
- **A reply or quote whose target is not a Fauna post JOURNALS — it neither refuses nor flattens (decided 2026-07-24, F2.2 slice 4; this closes the open question the slice was handed).** Most of the ATProto network is not Fauna, so replying to a non-Fauna post is the *ordinary* case, not an edge one. **Refusing** would make the account's PDS reject the network's most common operation — and because the record only reaches the repo after the nest answers, the user's reply would exist nowhere at all, which no third-party client could present as anything but the PDS being broken. **Round-tripping it standalone** would strip the conversation and publish the user's words to their Fauna followers as an independent statement — the same harm that keeps a reply from being flattened above, and a silent content alteration against D1. **Journaling is D2's own answer** applied literally ("round-trip iff a Fauna concept already exists; else journal"): the Fauna concept *reply-to-a-post-Fauna-does-not-have* genuinely does not exist. The record lands verbatim in `atproto_native_records`, the bridge commits it to the repo and the firehose, so the reply appears in its thread on the network exactly as written, and no misleading Fauna post is manufactured. It is also the **reversible** choice — refusing destroys the write and flattening publishes something the user cannot recall from followers' feeds, while a journaled record is re-derivable and can be back-filled should Fauna ever grow cross-network references. Quotes take the same rule rather than a second one: a quote missing its target is materially altered too, and one uniform rule beats two. **Direction-symmetric with the mirror:** outbound, a Fauna reply whose parent was never projected drops the reference and projects standalone (`atproto-pds-bridge.md` § Projection & backfill) — each direction keeps the write on the network the user aimed it at, and neither invents context that is not there.
- **Repo writes are their own endpoint class (decided 2026-07-24, F2.2 slice 4).** `com.atproto.repo.{createRecord,putRecord,deleteRecord,applyWrites}` register as `write`, not as the `authed` class that carries authenticated reads and proxying: a write costs a nest round-trip plus a signed funnel commit, and `authed`'s own contract is *non-write* calls. The class name is a **two-sided constant** — `xrpc.EndpointClass`'s `String()` on the Go side and D8's accepted set (`authz::ENDPOINT_CLASS_WRITE`) on the Rust side — and the two must land together, because D8's closed world *denies* a class it has not been taught, uniformly: a Go-only addition would make every external write fail as though the token were bad. **`com.atproto.repo.uploadBlob` is a fifth class, `blob`, not a member of this one** — added 2026-07-29 under the same two-sided rule; the reasoning is in § F2 detail's `uploadBlob` bullet. The per-IP window is the bridge-side layer; the per-**account** bound is the nest-side layer on `ingest_external_write`, since only the nest knows the authenticated actor behind a shared egress IP (§ Wire & process topology's two layers, made concrete).
- **The write reply carries the Fauna post id (decided 2026-07-24, F2.2 slice 4).** A round-tripped write answers `{rkey, at_uri, fauna_post_id}`; a journaled record answers without the last, having no Fauna identity. The bridge needs it to write its `post_map` row, and that row is what makes the write path and the projection loop idempotent *with each other*: the loop skips a post already mapped to an AT-URI, so without the mapping it would re-project this very post and overwrite the caller's own record bytes with the translator's rendering of them — handing the caller back a different record than it wrote (against D1) and emitting a spurious `#commit`. The rkey is likewise the **nest's** to choose and the bridge's to honour: it derives from the Fauna post's creation instant and content id, so committing at a bridge-chosen key would put the record where the projection would never look.
- **A write REFUSES while the account's identity is still first-emit gated (decided 2026-07-29, F2.2 slice 4e).** § Ecosystem reality's first-impression trap requires a DID + handle to resolve *before* the account's first firehose event; the projection loop has always enforced that (`projection.go`, `state.FirstEmitGated`), but the write path committed straight through the funnel, so an external app writing during the window could put the account's first `#commit` on the network unresolvable — permanently 404ing it on the AppView, since later events only UPDATE an actor row that was never created. **The ruling: this PDS serves no repo write for an account whose identity has not been announced** — one rule for `createRecord` and `deleteRecord` alike — refusing `InvalidRequest` with a message naming the DNS step the account owner finishes in their Fauna app. **The refusal is decided bridge-side, BEFORE `ingest_external_write`**, which is the load-bearing half: refusing after it would leave a real Fauna post that all 7 apps show while the network never sees it. **The alternative — answer `{uri, cid}` and let the projection loop commit once the gate opens — was rejected on three grounds.** (1) The answered **`cid` would name bytes that never land**: the projection loop commits its own *translated* record, not the caller's (mentions drop, media embeds are ignored — § F2.1), so honouring the promise would need a durable replay queue for the caller's exact bytes, with its own crash-recovery and never-opens-garbage stories. (2) It **breaks read-your-writes**, the property the synchronous answer exists to provide — `com.atproto.repo.getRecord` serves from the repo, so the just-answered URI would 404. (3) The write path already gives the *same person* the *same class* of answer for the sibling condition — no D10 delegation → `fauna_surface`, naming the Fauna-app step (D10 § Mint ceremony) — and one uniform "finish setup, then write" refusal beats two mechanisms. Recoverable by an ordinary user action, so it creates no unrecoverable state. **Considered and deferred to F5, not rejected outright:** committing the caller's exact bytes with `DeferFrameToSync` and announcing via `#sync` once the gate opens would answer a true `{uri, cid}` *and* keep read-your-writes — but it makes the account's **first** network appearance a `#sync` rather than a `#commit`, and whether a consumer creates an actor row from one is precisely the unverified ecosystem behavior the first-impression trap is about; F5's live interop proof is what could settle it. **Enforcement is two-site:** the handler pre-check above is the good error message, and `atprotorepo.ErrFirstEmitGated` on the funnel's four outbox producers (`ApplyBatch`, `EmitIdentity`, `EmitSync`, `EmitAccount`) is the guarantee — so no future emitter can bypass the gate by being written before its author reads this. A `DeferFrameToSync` batch is the one deliberate carve-out: it appends no outbox row, so it carries nothing onto the network.
- **Lexicon-schema validation is SERVED, against a vendored catalog (recorded 2026-07-24 as deferred; DESIGNED + BUILT 2026-08-02).** The bridge validates a record against the ATProto Lexicon schema for its collection whenever it holds one, on top of the structural checks that need no catalog (JSON object, `$type` matching the collection, dag-cbor encodability, size caps). Owner: `bins/fauna-bridges/internal/atprotolex`.
  - **The catalog is VENDORED, not resolved at write time — and this supersedes the 2026-07-24 recording, which named runtime Lexicon resolution as "what closes it".** That closure clause was wrong, and D2's own table (§ Problem 1) is why: unknown/third-party NSIDs get **no schema gate** — "real PDSs accept arbitrary structurally-valid records; we do the same". A PDS that never gates a stranger's lexicon has nothing to resolve a stranger's lexicon *for*, so resolution would buy the write path nothing while adding an attacker-directed DNS+HTTP plane and making a record's validity change under the caller over time. What the catalog closes is the other half of the same table: records whose lexicon **is** known are "lexicon-validated", and only those may answer `"valid"`. **Lexicon resolution is still owed — to F4's permission sets** (`include:<NSID>?aud=…`, § Ecosystem reality), which genuinely require it; it is not a write-path dependency and the two tracks no longer share one.
  - **The three answers.** `validate: false` → no check, `"unknown"` (the caller's explicit opt-out; the honest status for a validation nobody ran). Collection **not** in the catalog → the write proceeds unvalidated and answers `"unknown"`, per D2's no-gate rule — *unless* the caller passed `validate: true`, which is refused `InvalidRequest`, because answering 200 to a demand for a check nobody ran is the failure the old deferred arm existed to prevent. Collection **in** the catalog → validated, and only here may the reply say `"valid"`; a record that fails is refused `InvalidRequest`. **`InvalidRequest`, not `MethodNotImplemented`:** the method is served and succeeds for any collection in the catalog, so an unknown lexicon is a property of the *request*, not an unbuilt endpoint. The D6 `deferred` sub-type no longer applies to this path.
  - **Behavior change, deliberate:** a malformed record in a KNOWN collection that wrote before 2026-08-02 is refused now. Such a record fails at every consumer that reads it anyway, `validate: false` remains the escape hatch, and the alternative — knowing a record violates its schema and committing it to the repo and the firehose regardless — is what D2's "lexicon-validated where the lexicon is known" rules out. It landed already having caught real cases: four of this path's own test fixtures were records (`app.bsky.graph.list` with no `purpose`, a bare `app.bsky.feed.threadgate`) that no PDS on the network would have accepted.
  - **Strictness is three rulings, each pinned by a test** (`internal/atprotolex`, `validateFlags`): lenient datetimes are ACCEPTED (the network is full of them; refusing would diverge from every other PDS on records we had no reason to reject); legacy blob refs are REFUSED (they predate the ref shape the blob walk reads, so one would commit a reference nothing walks — the dangling ref *store-then-reference* forbids); and validation does NOT recurse strictly into union members, because atproto unions are open and a record carrying an embed the catalog never heard of is legitimate — recursing would re-impose the schema gate on unknown NSIDs that D2 rules out.
  - **It validates the CALLER'S record, which is what `validationStatus` is a statement about — not necessarily the committed one.** For a round-tripped collection the nest answers a `record_override` and the repo commits the projection's rendering instead. That the *projection's own* renderings satisfy their schemas is a separate guarantee, and it cannot live on the request path — a refusal there would arrive after the Fauna post exists, with nowhere to go. It belongs in tests over the real translator's output, and **that test is BUILT (2026-08-03)**: `cmd/fauna-atproto-bridge/projection_lexicon_ffi_test.go` renders posts and profiles through the real FFI translator, encodes them with the projector's own `JSONRecordToDagCBOR`, and validates the result against this same catalog. Its inputs come from the production builders the 7 apps compose with (`build_post*` / `build_edited_profile*`), never from fixture literals — findings 48/49. **It found a live bug on its first run** (§ Implementation status today): the projection capped `text` / `displayName` / `description` by **grapheme count only**, while a lexicon string cap is a *pair* — `maxGraphemes` **and** a UTF-8 `maxLength` — so 300 family-emoji clusters rendered 7500 bytes of `text` inside the 300-grapheme cap and 2.5× outside the 3000-byte one. Fixed in `outbound::truncate_for_lexicon`, which now honours both axes and never splits a cluster.
  - **Refresh:** a dedicated dev-fleet sync tool, pinned by `internal/atprotolex/LEXICONS_COMMIT`. The tree is a verbatim copy of upstream `lexicons/` (no per-subtree filter — a filter is policy that drifts), embedded rather than fetched at boot because it is needed at runtime in the shipped binary. The `git diff` of a refresh is the catalog's supply-chain review surface.
- **CAS semantics:** `swapCommit`/`swapRecord` compare against the MST head the bridge owns — checked bridge-side before the nest call; mismatch → `InvalidSwap`, nothing ingested. Silently dropping a CAS would break exactly the concurrency guarantee the caller asked for. **BUILT 2026-07-29 (F2.3 piece 3);** the earlier "refused deferred until it lands" arm is gone from all three sites.
  - **The wire name is `InvalidSwap`, no `Error` suffix** (this bullet said "InvalidSwapError" as prose until 2026-07-29). It is the lexicon's own error name on all four write verbs, and third-party clients branch on that exact string to decide whether to re-read and retry — the same reason `InvalidRequest` and `MethodNotImplemented` are spelled as the lexicon spells them.
  - **Enforcement is two-site (decided 2026-07-29, F2.3 piece 3).** The bridge-side pre-check before `ingest_external_write` is what this bullet's "nothing ingested" demands — a write whose precondition has already failed must not create a Fauna post the repo then refuses to carry — but it **cannot be the guarantee**, because that read is not atomic with the commit that follows: a concurrent writer for the same account can land in between. So the expectations ride into the funnel as batch options and `ApplyBatch` repeats the identical comparison **under its per-DID lock, against the very head the commit chains onto** (`atprotorepo.ErrSwapMismatch`). One owner for the comparison itself (`CheckCommitSwap`/`CheckRecordSwap`), two callers, so the pre-check and the guarantee can never drift into disagreeing verdicts. **The alternative — holding the funnel's per-DID lock across the nest round-trip — was rejected:** it would block the projection loop for that account behind a network RPC. **Residual, deliberately accepted:** when the funnel-side check is the one that fires (a genuine race), the Fauna-side write has already happened, so the caller gets `InvalidSwap` while the post exists in Fauna and reaches the repo on the projection loop's next pass — the same reconciliation the existing post-ingest commit failure already relies on.
  - **The reconciler race's NO-CAS direction is BENIGN, proven by flow trace rather than merely accepted (recon 2026-07-30).** The write path is nest-ingest-THEN-commit: `ingest_external_write` creates the Fauna post and answers synchronously, but the bridge's own funnel commit for it runs strictly after that round trip returns, and nothing holds the per-DID lock in between. A projection pass (30 s cadence) can therefore land inside that window, see the same unmapped Fauna post, and commit it FIRST — at the identical deterministic rkey the write path's own commit will target next, with the same Fauna post id. Left unexamined this reads as the answer-fidelity failure the first-emit ruling above rejects *answer-and-defer* for (a synchronously-answered `cid` naming bytes a later pass overwrites) — but the trace shows the opposite: the write path's own commit runs anyway, finds the path occupied, relabels the firehose op `create`→`update` (funnel.go's reality-not-caller's-label rule), and **replaces the record with the caller's exact bytes**, while `post_map` is an upsert (`ON CONFLICT(did,fauna_post_id) DO UPDATE`) rather than a bare insert, so the second write converges instead of colliding. Net: the answered `cid` names bytes that really land, `getRecord` agrees, `post_map` is correct, nothing errors — the same answer-fidelity property the CAS residual above accepts losing, holding here without a retry. **Two DESIGNED properties are load-bearing and must not be "simplified":** the deterministic rkey (so both writers target one path, never a duplicate record at a second key) and the upsert (so the second `post_map` write converges). A change toward a non-deterministic rkey, or toward a bare `INSERT`, would turn this benign race into the failure this paragraph starts by describing. **Residual, cosmetic only:** the projection's rendering can differ materially from the caller's own bytes (a media post — § F2 detail's media arm), so a consumer briefly sees the projection's rendering before the caller's replaces it — one extra `#commit`, eventual consistency, not data loss. For a **profile** write the two renderings are byte-identical since slice 3 (both sides render through `RenderProfileRecord`), so the write path's own commit now passes `atprotorepo.SkipUnchangedRecords()` **(fixed 2026-07-30)** — the redundant frame there is now a `NoChange` no-op rather than a second broadcast of bytes a consumer already has; for a post the two renderings can legitimately differ, so the option only ever short-circuits the byte-identical case and never masks a real content change. Pinned by `TestASecondCommitAtAnOccupiedDeterministicRkeyConvergesRatherThanCollides` (mutation-checked: a bare `post_map` INSERT turns it red) and `TestASecondCommitOfByteIdenticalBytesEmitsNoRedundantFrameWithSkipUnchanged`, both in `funnel_test.go` — sequencing the two `ApplyBatch` calls in this order reproduces the race deterministically, since the funnel has no notion of which caller ran first, only of what is already at a path when a commit lands.
  - **The CAS keeps the path the CALLER named**, even where the nest chose a different rkey to commit at: `swapRecord` is a precondition about the record the caller pinned, not about the write's target, so re-keying it onto the committed path would quietly assert something else.
  - **`putRecord`'s `swapRecord` is NULLABLE, and an explicit `null` is itself a CAS assertion (recorded 2026-07-29, F2.3)** — it asserts *the record does not already exist*. It must therefore be decoded as a raw/optional value, never as a plain string: a string decode flattens `null` into "no CAS requested" and serves a write the caller asked us to guard, which is the silent-drop this bullet exists to forbid. `deleteRecord`'s `swapRecord` is by contrast plain and non-nullable — there is no "must not exist" assertion to make about a record you are deleting. Pinned by `TestPutRecordHonoursTheNullableSwapRecord`, whose three arms (absent / `null` / a CID) are only meaningful **together**: a decode that collapses any two of the three still passes the other two.
- **`putRecord`** routes by lexicon class: mutable singletons (profile) → the C2 sanctioned update path; posts → refused (immutable, matching the network); journal collections → journal update (new CID, tombstone-and-replace semantics in the journal, one funnel `update` op).
  - **The profile round-trip MERGES; it never replaces (decided 2026-07-29, F2.3).** An `app.bsky.actor.profile` record can express a display name, a description and two blob refs; a Fauna `Profile` also carries `nests`, `links`, `admin_nests`, inbox mode and the recovery-key mirror. So the write is a read-modify-write over the account's current profile, and the line is drawn at the record's *translatable scope*: `display_name` and `bio` are taken from the record and are **authoritative, absence included** (clearing a display name in bsky.app clears it in Fauna — otherwise a user could never remove one from the app they set it in), while every field outside that scope is **preserved untouched**. Treating the record as a whole profile would destroy the account's `nests` — how peers find it at all — because someone edited their bio in another app. **Avatar/banner sit outside the scope today** and are therefore preserved: their blob refs need F2.4's `uploadBlob` ingest to become Fauna `ContentHash`es, and dropping them meanwhile would be silent data loss.
  - **`updated_at` is nest-stamped, unlike a post's adopted `createdAt` (decided 2026-07-29, F2.3).** The profile lexicon carries no creation instant to adopt, and nothing derives an rkey from this one (the singleton's key is the constant `self`), so the two grounds that made adoption right for posts do not apply. It also closes the same shape of gap by construction on this path: the chain verify's step-5 expiry comparison runs against an instant the external app does not choose.
  - **What the repo carries is the PROJECTION's rendering, not the caller's record (decided 2026-07-29, F2.3; the renderer settled 2026-07-30, F2.4 slice 3).** For this one collection the projection is the owner and re-derives the record, so the caller's bytes are an *input* to a Fauna update rather than the record that results. Two things follow, and both are the point: the synchronously answered `cid` names bytes that really landed (`getRecord` agrees with the write's own answer), and the next projection pass is a **no-op by construction** — same profile → same record → same CID — which is why a profile round-trip needs no `post_map`-style idempotency row. Committing the caller's bytes instead would have the next pass overwrite them, the same "answer names bytes that never land" failure the first-emit ruling rejects *answer-now-commit-later* for.
    - **The nest asserts the property; the BRIDGE renders the record (decided 2026-07-30, F2.4 slice 3 — this replaces F2.3's `record_override`).** F2.3 had the nest render the record JSON and ship it in a `record_override` field. That could never be right for an account **with a profile picture**, which is the gap slice 3 was opened to close: a projected `avatar`/`banner` blob ref carries the picture's **ATProto** CID, MIME and size out of the *bridge's* blob store — indexed by the picture's **Fauna** CID, the direction `atproto_blobs` does not answer, and with no row at all for a picture a Fauna app set — and whether a picture publishes at all is **sniffed from its bytes**, with per-field drop, under a rule [`atproto-pds-bridge.md`](atproto-pds-bridge.md) § Projection & backfill owns and the nest cannot evaluate (the bytes never reach it). A nest-side rendering was therefore a **second implementation** of the projection's rendering, obliged to stay byte-identical across four axes — which CID, which MIME string, which size, publishable-at-all — three of them silent; the same objection that forbids a second dag-cbor encoder (§ *CID source*), a Go sidecar encoder and a Go `media_ref` spelling. So the reply field became **`reproject_record: bool`** — "the record the repo must carry is the projection's own rendering of the state this write changed" — and the bridge answers it through the *same* function a projection pass calls (`atprotorepo.Projector.RenderProfileRecord`, which `ProjectProfile` also calls). **Override-equality stops being a property two implementations maintain and becomes identity.** A render failure fails the write rather than falling back to the caller's bytes: the fall-back would restore the very drift the signal prevents, invisibly. The field stays deliberately general — it states a property of *projection-owned collections*, not of profiles — and a record-carrying field can return additively if a projection-owned collection ever appears that the nest genuinely can render. **Residual, stated rather than overstated:** a picture whose bytes fail to fetch during the write's own render is dropped from that record and restored by a later pass — one spurious `#commit`, self-healing, and strictly narrower than the pre-slice-3 behaviour, where *every* pictured account's write was rewritten by the next pass, always.
  - **A live delegation narrower than the write refuses `fauna_surface`, never errors (decided 2026-07-29, F2.3 landing review).** Provisioning accepts any subset of the enumerated authoring set, so a Post-only cert (a non-Fauna client minting its own) is a legitimate stored state — and a profile write under it must be told the remedy (*re-authorize in a Fauna app*; re-provisioning overwrites the cert in one gesture and the Fauna ceremony mints the full set), not handed an opaque internal error. Enforcement is two-site: the dispatch pre-check (`atproto_authoring_key::delegation_grants`, per-write, per-disposition-capability) is the good message, and the chain verify's step 4 inside each arm remains the guarantee. Found live: the tier_3 suite's own Post-only mint surfaced as a 500 before this. Pinned by `a_profile_update_under_a_post_only_cert_refuses_fauna_surface_not_an_error` + its post-side twin + tier_3 leg 6a.
  - **`Profile`'s verify sites are TWO, not four (verified 2026-07-29, F2.3).** Where `Post` needed four, a profile has one shared read face — `fauna_core::encoding::decode_profile`, which `fauna-client-profile` on all 7 apps, the ActivityPub actor serve and the projection's `translate_profile_bytes_for_projection` all go through — plus the strict ingest gate. The gate is now `profile_handlers::ingest_profile_core`, the **single profile write door** that `fauna.profile.set` and the round-trip arm share: sharing it is the proof, exactly as `ingest_post_core` is for posts — it re-runs the chain on the real bytes, so the arm cannot produce a profile the ordinary publish path would reject. The required capability is **`UpdateProfile`, never `Post`**, so a cert minted for posting alone cannot rewrite the account's profile.
- **`uploadBlob`:** bytes stream bridge→nest over the existing bulk-binary HTTP carve-out (the one sanctioned non-WS-RPC internal surface), land in the Fauna media path (BLAKE3/FastCDC), and get an `atproto_blobs` row keyed by sha256-CID. A blob unreferenced by any record past the reference window is GC'd. **BUILT 2026-07-29 (F2.4 slice 1) — the ingest leg; the media arm followed 2026-07-30 (slice 2):** a record referencing an uploaded blob now round-trips as a real Fauna media post, `referenced_at` is stamped, and the `#commit` frame announces the record's blobs.
  - **The media arm (decided 2026-07-30, F2.4 slice 2): a record's image embed becomes real Fauna post media, and a blob ref that resolves to nothing REFUSES the write.** `reverse_translate` parses `app.bsky.embed.images` and the media half of `app.bsky.embed.recordWithMedia` (the same two-shape rule as the quote extraction); the nest resolves each ref through `atproto_blobs` → `blob_metadata` and builds `PostBody::Media` (empty text; the FIRST image's `alt` becomes the set-level `alt_text` — the exact inverse of the outbound alt-on-first-image rule) or `PostBody::TextWithMedia` (non-empty text; per-image alts drop, symmetric with outbound emitting none there). The `MediaItem`'s type and size are the nest's own STORED values — for these bytes, what the upload leg *sniffed* — never the record's declared `mimeType`/`size` (the sniffed-not-declared ruling, third application); the declared `aspectRatio` does cross as dimensions, because nothing stored knows it and a native app declares its own. More than the lexicon's four images refuses (the ceiling is two-sided with outbound's cap). **The resolves-to-nothing ruling, and why neither sibling precedent transfers whole:** the deciding axis is *who serves the referenced thing*. A reply/quote target lives on the open network — journaling keeps the thread intact because the network serves it — but a blob ref is **repo-scoped**: only this PDS can ever serve it, so journaling would commit a record whose media 404s from every consumer forever (exactly the dangling ref *store-then-reference* forbids), and round-tripping without the image would silently alter the post while its record still claims the media (outbound may drop because outbound's record is *derived*; inbound the record is the caller's bytes, committed verbatim). Refusing is the `uploadBlob` asymmetry applied again — nothing published yet, the app learns immediately, the remedy is literally the upload it skipped (re-upload converges by CID) — and it is reference-PDS parity. The resulting taxonomy, for the next media-shaped arm: **journal what Fauna has no concept for; refuse a reference only this PDS could serve and cannot; translate-minus-part only where the part is severable and the record still serves whole network-side** (mentions, link-card presentation — their blobs still gate and stamp; only the Fauna rendering drops them).
  - **The blob-existence rule covers every row that commits a caller-authored record — journal rows included — and EXEMPTS profile rows; enforcement is the all-or-nothing pre-flight (decided 2026-07-30).** A journaled record commits to the repo just like a post's, so its dangling ref would 404 identically; the check is a fourth up-front concern (the pass-3 pattern — decided before anything applies, one resolver owning the verdict, the arm asking the same owner for the values). Profile rows are outside the rule on both counts, deliberately: what a profile round-trip commits is the projection's rendering, not the caller's record, and an *unchanged* picture's blob ref is **projection-stored** — no `atproto_blobs` row exists or should — so covering profiles would refuse every "change display name, keep avatar" write from a pictured account. **Slice 3 KEPT the exemption and strengthened its reason rather than evolving it as this bullet expected (2026-07-30):** since the bridge renders the committed record, a profile write commits blob refs the nest never chose, and those refs are servable by construction — the projection's own *store-then-reference* discipline stored each picture before referencing it. There is nothing for a nest-side existence check to add and nothing for the stamp to key on: the refs belong to the bridge's blob store, not this ledger. The row set moves only if a picture ever comes *from* the caller's record, which is the separate inbound change the next bullet scopes.
  - **A picture crosses INBOUND by resolution, never by trust (design RATIFIED 2026-07-30; BUILT 2026-07-30 — § Implementation status today).** Avatar/banner join the merge's translatable scope, **authoritative, absence included** — the `display_name` rule exactly: an app that omits or clears the field clears the user's picture, because otherwise a picture set anywhere is unremovable from bsky.app; the cleared ref is re-settable from any Fauna app and destroys no bytes. What makes authority safe is that every inbound ref must RESOLVE to bytes this PDS already serves, through exactly two resolvers, each asked about the store it owns. **(1) A fresh upload resolves nest-side:** the `atproto_blobs` row (the same `resolve_uploaded_blob` owner the media arm uses) maps the ref to its `media_ref` `ContentHash`, and is STAMPED pre-apply — so the profile row set finally enters the blob pre-flight, and the `commits_caller_record` exemption **narrows to what its name says** (record-bytes commitment only): a profile write still commits the projection's rendering, but it now gates and stamps the caller-authored refs it carries. **(2) The echoed current picture resolves bridge-side** (the unchanged case — a caller handing back the ref our own projection emitted): the bridge's blob store is the ONE Fauna-CID↔ATProto-CID index (the slice-3 renderer ruling), so the bridge walks the record's refs before `ingest_external_write` and attaches a `resolved_media` map (additive wire field; producer and consumer land in one commit). Content-addressing makes this case convergent with no special "unchanged" arm: the echo resolves to the `ContentHash` the profile already holds and the merge is a no-op on that field. **(3) Resolves-to-nothing REFUSES the whole batch** — a ref whose bytes this PDS does not serve would commit a dangling ref, which *store-then-reference* forbids; the caller's echo is never trusted. **Rejected:** a second `atproto_blobs` row class for projection-published blobs — it would duplicate the bridge-store index nest-side (the two-implementations drift class the slice-3 renderer ruling exists to prevent) and add a projection-hot-path write for a fact one owner already knows. After the merge applies, the bridge renders and commits exactly as slice 3 built — the committed record remains the projection's rendering.
  - **`referenced_at` stamps from a GENERIC blob-shape walk, before the apply loop (decided 2026-07-30).** The walk (`record_refs::external_record_blob_refs`, beside the refs extraction, same decoder) recognizes the `blob` shape anywhere in the record — embed images, a link card's `thumb`, a video blob, any journal-collection lexicon — because a stamp keyed on the embeds the media arm happens to map would leave every other referenced blob reading as unreferenced to the GC: deleted user media, not a cosmetic miss. Stamping precedes application in the fail-safe direction — an over-stamp on a batch an internal fault then kills costs one blob's collectability, while stamp-after-apply would let a crash in between turn media a committed record references into GC bait (the no-data-loss direction). First reference wins; a re-upload never clears the mark. The stamped row set and the existence-checked row set are ONE predicate (`carries_caller_blob_refs`, named `commits_caller_record` until the inbound-picture slice widened it to profile rows), so refusal coverage and stamp coverage cannot drift.
    - **⚠ The walk must know the link shape the WIRE carries, not the one fixtures build (found 2026-07-30, the inbound-picture slice; the second sighting of the finding-42 class).** The bridge encodes a caller's record with indigo's `atdata` codec, which stores a blob's `ref` as the literal map `{"$link": "<cid>"}` — **not** as a dag-cbor tag-42 link. The walk understood only tag-42, so from slice 2 until this fix it returned **nothing** for every record an external app ever wrote: no `referenced_at` stamp ever landed, every externally uploaded image was swept after the 7-day window and its bytes reclaimed by the box GC, and the `#commit` frame's `blobs` field was always empty. Nothing failed — both sides' unit tests were green throughout, because every fixture built tag-42 links, a shape production never produces. The walk now accepts both spellings, and the agreement is pinned **cross-binary** (`TestTheRustBlobWalkSeesTheRefsTheGoEncoderReallyWrites`: encode with the real Go encoder, ask the real Rust walk) rather than by each side matching its own fixture literal — the F2.2 slice-4d rule, which exists for exactly this.
  - **The `#commit` frame's `blobs` field is filled from the same walk, on the committed bytes (decided 2026-07-30).** The write path used to commit media records announcing an empty blob set — the "small lie about the commit" the funnel's own `frameBlobLinks` docs call out; only the projection loop filled `RepoOp.BlobCIDs`. The same Rust walker now crosses the FFI (`atproto_extract_blob_refs`, the `atproto_extract_record_refs` precedent) and the bridge fills the op at construction, from the bytes that actually land — override included — so what the frame announces and what the nest guards against GC cannot disagree about which blobs a record names.
  - **The reference window is SEVEN DAYS, and it governs the ROW — never the bytes (decided 2026-07-30, F2.4 slice 4).** A hard-coded Rust constant (`atproto_blob_sweeper::ATPROTO_BLOB_REFERENCE_WINDOW_MILLIS`; § Product invariants — no human chooses it), sized by an asymmetry rather than by measurement: over-retention costs disk the next sweep past the window reclaims anyway, while under-retention destroys an upload a record was about to name, committing a ref only this PDS can serve and no longer can — the dangling ref *store-then-reference* forbids. The legitimate upload→reference gap is **seconds** (an app uploads each image as the user attaches it, then posts), so seven days clears the real case by four orders of magnitude. It is deliberately **not** the defence against an upload flood — the `blob` endpoint class's rate limit and the per-blob ceiling are — so shortening it buys nothing. The sweep is hourly, cross-actor, and does its filtering in SQL (`referenced_at IS NULL AND created_at < cutoff`); `list_atproto_blobs` never could have fed it, being per-actor, and its doc comment claiming otherwise was corrected with this slice.
  - **Collection is TWO STAGES with two owners: the sweep deletes the ROW, and the box-wide GC reclaims the BYTES (decided 2026-07-30, F2.4 slice 4).** `atproto_blobs` rows are now a top-level reference class in the nest's single reachability oracle (`backup::gc::collect_reachable_hashes`), pinned by **row existence alone** — no window arithmetic on that side. Dropping the row is therefore the *whole* act of collection: the bytes stop being reachable as a consequence and the ordinary GC cycle reclaims them. Three reasons this split is the design and not an implementation detail. **(1) One oracle.** That walk's own contract is that a second, hand-rolled reachability answer is a data-loss bug waiting to happen (it already cost the `__index` purge a chunk-level miss); a sweep deleting media bytes on its own authority would be exactly that second answer. **(2) Content addresses are shared.** `atproto_blobs` is keyed `(actor_id, cid)`, so two accounts uploading identical bytes hold two rows over **one** content address — and a Fauna app's own post media can share it too. One account's expired upload is another's live post, and only the box-wide walk can see all of it. **(3) Crash-safety becomes structural.** The sweep performs a single write and the reclaim it enables is a separate idempotent pass, so there is no order to get right and no half-state to reason about — the "orphaned media object without its row" this bullet might otherwise have to forbid is instead the *already-documented* resting state of the upload leg's bytes-only partial (see the write-order bullet below), reclaimed by the same pass.
  - **⚠ The oracle gap this closed was live data loss, not a missing feature (found 2026-07-30, F2.4 slice 4).** Until this slice the reachability walk drew top-level references from live snapshots, `sync_changes` and backup custody only — and the `uploadBlob` leg records **none** of those. A Fauna app's media is pinned by the media library's own `changes.record`; an external app has no such leg, so every byte uploaded through `com.atproto.repo.uploadBlob` was reachable from nothing and was deleted by the first GC cycle past the 30-minute creation grace (the scheduler runs six-hourly in production). The repo record still named it and `com.atproto.sync.getBlob` still had to serve it. So the slice that was scoped to *collect* unreferenced uploads had first to stop the box from collecting **referenced** ones. Pinned by `gc_keeps_an_atproto_uploaded_blob_a_record_references`, red before the fix, and by the staged `gc_reclaims_an_atproto_blob_only_after_its_row_is_swept`. **The general lesson for any future non-`sync_changes` writer into the blob store:** `blob_routes` says it plainly — the metadata row is a blob's only durable trace *until a reference row lands* — so a new write path that stores bytes without recording a reference the oracle walks has silently scheduled their deletion.
  - **The stamp is the row's immunity token, so it is acquired BEFORE the verdict that depends on the row surviving (decided 2026-07-30, F2.4 slice 4).** Slice 2 left a constraint for this slice: the sweep must not take a row an in-flight write has already resolved, or the apply arm's re-ask errors mid-batch — the mid-batch-error shape. It is answered by ordering rather than by locking or by excluding rows from the sweep. `preflight_blob_refs` now stamps each ref **immediately before** resolving it, and the sweep evaluates `referenced_at IS NULL` inside its own `DELETE`, so the two serialize on the one connection and a stamped row is unsweepable from that instant: every later reader — the pre-flight's own verdict, the apply arm's re-ask — is asking about a row the sweep provably cannot take. Resolve-then-stamp left a real (if narrow) window in which the verdict said *resolvable* and the arm then failed. The cost is that a batch which later refuses has stamped its resolvable refs; that is the same fail-safe direction slice 2 ratified for the apply loop, and it is bounded to the caller's **own** uploads (a row exists only where this account uploaded those bytes), which posting them would pin anyway. It also merged the two loops that walked the same refs over the same row set: agreement between the stamped set and the checked set is now identity rather than parallel maintenance.
  - **The media type is SNIFFED from the bytes, and bytes we cannot name are REFUSED — where the outbound projection DROPS (decided 2026-07-29, F2.4).** Both directions share one sniffer (`atprotorepo.SniffImageMIME`, owned by the media rule in `atproto-pds-bridge.md` § Projection & backfill) and differ only in what they do with a non-image verdict. **The asymmetry is the ruling.** Outbound, refusing would withhold content the user already consented to publish, and the post can publish without that attachment — the drop is the lesser failure, and § Projection & backfill ratified it. Inbound, **nothing has been published yet**: the app learns immediately, nothing is half-done, and it can retry with a format we can name — while accepting bytes whose type we had to invent means the nest serves them under a guess forever. **The caller's declared `Content-Type` is never trusted**, because that value becomes the `Content-Type` the nest answers on download, so honouring it would let a caller decide what its own bytes are later claimed to be.
  - **The bytes land under `AudienceClass::PublicPost` (recorded 2026-07-29).** It is the one class Fauna does not AEAD-seal, which is what makes the leg possible at all — the bridge holds no user key material and could seal for no other class — and it is also correct by *content*: a blob an `app.bsky.*` record references is public by construction, the same audience the outbound path already reads. Consequence worth carrying: for a sealed class the true MIME rides *inside* the ciphertext and the verifier demands the `application/octet-stream` placeholder, whereas `PublicPost` carries the real sniffed type in the sidecar. **The sidecar bytes are encoded by shared Rust and exported over the FFI** (`atproto_public_post_upload_sidecar`), never hand-rolled in Go: the nest strict-decodes them and then cross-checks them against the body, so a Go copy drifting on canonical map ordering, the class spelling, or an absent `thumbnail_hash` would fail with an opaque 400 — the same one-owner reasoning as `appview_service_did()`.
  - **The account attribution is its own WS-RPC leg, never inferred from the byte upload (decided 2026-07-29).** `POST /api/v1/blob` authenticates as the **bridge's** service user and keeps its `uploader` for audit only, so the byte route cannot know which account uploaded; the authenticated actor exists only on the session-token side. `fauna.bridges.atproto.record_blob` carries it. That kind also **answers the `media_ref` spelled as a canonical Fauna content CID**, because the bridge's blob store records that string as provenance and the projection loop's "have I already published these bytes?" lookup matches it against `ContentHash::to_base32` — a Go-side spelling one character off would re-fetch and re-hash every image forever with nothing failing. Deriving it nest-side makes that drift unrepresentable; pinned by a test comparing the answered string against the outbound spelling of the same bytes.
  - **The write order is nest bytes → `atproto_blobs` row → bridge blob store → answer (decided 2026-07-29).** The inbound reading of § Projection & backfill's *store, THEN reference*: the caller receives a ref it will put in a record moments later, so `com.atproto.sync.getBlob` must serve it from the instant the ref exists, and answering first would hand out a ref that 404s. Every partial state converges and none hands out an unresolvable ref — bytes-only leaves an orphan in the Fauna media store (the GC's business; the retry re-derives the identical CID from the identical bytes), and bytes+row returns an error the caller retries idempotently at every step. **Bridge-store-first was rejected:** it leaves bytes `getBlob` serves with no Fauna media backing, so a record could reference bytes the round-trip cannot resolve.
  - **`uploadBlob` is its own endpoint class `blob`, not `write` (decided 2026-07-29).** A record write's cost is a funnel commit plus a nest round-trip over a few KB; a blob body runs to the ceiling, so sharing `write`'s window would let one IP push ceiling×window bytes a minute — a bandwidth-and-storage cost a record write cannot express. Second ground: an image post is `uploadBlob` **then** `createRecord`, so one shared bucket would silently halve the effective post rate for exactly the callers who upload media. Starting constant 20/60 s. Lands **two-sided** per this section's endpoint-class rule.
  - **The inbound ceiling sits strictly below the nest's multipart cap (recorded 2026-07-29).** The bytes travel as one part of a multipart body whose *whole* size the nest caps at 10 MiB, so a blob at exactly the outbound per-blob ceiling could not fit beside its own sidecar and would 413 after the caller had streamed every byte. `MaxUploadBlobBytes` therefore reserves explicit headroom, pinned by a test rather than left to a comment; the nest's 413 stays the authority — the bridge pre-check is the good error message, the same two-site shape the CAS and first-emit gates use.

### F3 detail — the D8 module, service proxying, preferences, DM switch

- **The D8 authorization module is shared Rust** (`libs/fauna-bridge-atproto`, new `authz` module), exported to the Go bridge over the **tracked** fauna-ffi Go binding (same regen discipline as the mail bridge's). API shape: input `{plane: AppCredential{dm_allowed} | OAuth{parsed_scopes}, external_apps_enabled, lxm, aud?, endpoint_class}` → `Allow | Deny{xrpc_error, message}` (the kill-switch flag folds in here as a plain input once D8 exists — F1's direct middleware check retires then). Scope-grammar parsing, permission-set expansion, and the app-credential implicit-grant matrix (full repo + rpc, minus account-mutation endpoints, DM per flag) all live inside it; Go supplies inputs and enforces verdicts. This is what makes F4 a *caller*, not a second enforcement path. **Ratified contract (2026-07-22 — anchors verified against the code as landed; the F3 session builds to this):**
  - **Seat and retirement.** The Go seat is the existing `xrpc.AuthzHook` slot (`internal/xrpc/xrpc.go` — run post-authentication, pre-handler; its doc comment already names it D8's seat). F3 replaces the F1 kill-switch hook (`internal/atprotopds/server.go` `Server.AuthzHook`, the `flagCache` check) with a hook that assembles the module's input and enforces its verdict; the flag becomes the `external_apps_enabled` input. The uniform-refusal property survives the move: a Deny caused by the kill-switch (or any input the module treats as account-disabling) maps to the same `AuthenticationRequired` as a bad token — no enumeration signal; other denies carry the XRPC error name + message the verdict states.
  - **Inputs, pinned to what the frame already carries.** `plane` from `Caller.Plane` (`app_credential` | `oauth`); for the app plane, `dm_allowed` derives from the token scope — `com.atproto.appPass` vs `com.atproto.appPassPrivileged` (the ecosystem's real privileged-scope name, re-verified 2026-07-22; F1's `token.go` already mints exactly these); `lxm` = the route NSID (and, on `getServiceAuth`, the requested `lxm` parameter — both are checked); `aud` = the resolved proxy-target service DID, present only on proxied calls and `getServiceAuth`; `endpoint_class` mirrors the route's declared `EndpointClass`. Nothing in the input set requires new plumbing — every field exists in `Route`/`Caller` or the proxy resolution today.
  - **Verdict + default-deny.** `Allow | Deny{xrpc_error, message}`. The matrix is closed-world: an input combination the module doesn't recognize (unknown plane, unparseable scope, unclassified lxm on a guarded surface) **denies** — Go never interprets, never falls through to allow. The module is a **pure function of its inputs** (no I/O, wasm-clean like the rest of the crate) so the matrix is table-driven-testable in Rust; the Go side keeps only assembly + enforcement.
  - **App-credential implicit grant** (the ecosystem's app-password semantics, re-verified 2026-07-22): full repo read/write, blob upload, and service-proxy `rpc` — **minus** the account-mutation/destructive class. Most of that class is already route-level refused by D6 (`createAppPassword`, `deleteAccount`, `updateHandle`, …); D8 additionally polices the *residue reachable through generic machinery*: `getServiceAuth` minting for migration/account-management `lxm`s stays deferred-refused (the D6 mechanism), and proxied account-management calls are denied by `lxm` class. The **DM class** — `aud` = the chat service DID, or `lxm` under `chat.bsky.*` — requires the privileged scope, i.e. the credential's `dm_allowed` flag at mint time.
  - **OAuth plane arm — defined now, consumed by F4** (what makes F4 additive): parsed granular scopes (`repo:`, `rpc:` with `aud=`/`lxm=`, `blob:`, `account:`, `identity:`) evaluated against the same `lxm`/`aud` inputs; **permission-set expansion is module-owned logic over caller-supplied data** — resolving an `include:<NSID>` set's Lexicon document is a network fetch, so Go performs it (same SSRF-guarded fetch class as client-metadata, cached) and hands the resolved set in as input, keeping the module pure *(sharpened 2026-08-03 by the permission-set ruling: the **fetch** is Go's; the parse/validate/expand over the fetched document is the module's own pure logic, and what D8 receives is the expansion's output of ordinary granular scopes — § F4 detail's *Permission sets* bullet owns the full split)*; transition scopes map onto the app-plane matrix (`transition:generic` ≈ the app-credential grant minus DM; `transition:chat.bsky` adds the DM class; `transition:email` has no Fauna meaning — no email account model — and grants nothing).
  - **Go-binding discipline.** A bridge-consumed Rust module changes the tracked Go binding — `libs/fauna-mail-go` regen rides the same commit (the standing gotcha).
- **Service proxying:** `atproto-proxy: did#fragment` → resolve the target DID's service endpoint (indigo identity) → guard (HTTPS only, public DNS name only, no loopback/private ranges, response size + time caps) → mint the service JWT (`iss` = user DID, `aud` = target service DID, `lxm` = the invoked method, `jti` unique, `exp` ≤ 60 s, signed with the user's **repo signing key** — the § Ecosystem reality-confirmed shape, no custody widening) → forward, stream back. Headerless `app.bsky.*` reads default to the AppView — reference-PDS convention, not spec (attribution corrected 2026-07-22, § Ecosystem reality); the constant is hard-coded and an explicit header always wins. `getServiceAuth` mints the same JWTs for clients, gated by D8 (its `lxm`/`aud` rules are how migration-oriented minting stays deferred per D6).
- **Preferences:** `app.bsky.actor.{get,put}Preferences` ↔ `fetch_preferences`/`store_preferences` ↔ `atproto_preferences`. Opaque array passthrough with a hard size cap; no Fauna concept invented (D2's policy applied to preferences).
- **DM switch (D7):** the gate lands where the consume-side poller schedules itself (the nest's `bluesky::dm_worker`), keyed off the stored identity backing — a hosted-backing account never polls; its `chat.bsky.*` traffic rides the proxy path, transit-only (D4).

- **A delegation is time-bounded by construction, and there is NO user-facing expiry chooser.** Minting sets `expires_at` to a hard-coded window (`fauna_client_bridges::atproto_delegation::DELEGATION_WINDOW_SECS`, ~90 days) with no configuration surface — the shipped capability-grant shape ([`../ui/nests.md`](../ui/nests.md) § Expiry / renewal, whose default window is the same 90 days for the same reason). - **Re-authorizing is the renewal gesture** — provisioning overwrites the stored cert with a freshly dated one, so a lapsed delegation recovers without revoking first. The row renders a liveness state (`active` / `expiring_soon` / `expired` / `never_expires`, warning ~14 days ahead) so a lapse reads as "re-authorize here", **never as silent feature loss** — the bar `nests.md` § Expiry / renewal sets for grant rows. Revoke stays the separate, destructive action (§ Revocation: it destroys `K`; already-published posts stay verifiable forever).

The read returns the stored cert **verbatim** plus `k_pub`, both optional; `k_pub`-present-with-`cert`-absent is a real interrupted-ceremony state that authorizes nothing and renders as *not authorized*.
- **The client verifies the cert it is shown.** The cert crosses as raw bytes and the client re-runs the envelope verify under its **own** identity key before rendering (`atproto_delegation::parse_delegation_cert`), so a nest serving a cert the account never signed is detectable client-side and is surfaced as a mismatch rather than rendered as a grant. The nest stays a non-interpreter of a structure it only stores.

### Security posture summary

Default-closed per account: the login plane is inert until the user mints a credential or approves a grant, and the per-account external-apps kill-switch (F1) hard-refuses the whole plane regardless — defense-in-depth against auth-path implementation bugs. Brute force: generated-only secrets (≥80-bit) × Argon2id × per-IP windows × per-identifier backoff — no user-chosen secret exists to be weak. Token theft: DPoP binding (OAuth plane), 60-min access lifetime + registry-checked rotate-on-use refresh (app plane), reuse detection kills session families. Consent phishing: approval happens only in an authed Fauna app with the binding code check; the browser never holds a Fauna secret; the contingency page-entry ceremony stays unbuilt unless F5 proves it necessary (D3). SSRF: client-metadata fetch and proxy resolution share one guard (HTTPS, public DNS, private-range deny, caps) — stricter than the accepted consume-side postures because these fetches are attacker-*directed*, not user-directed. Enumeration: uniform auth errors, rate-limited resolve surface. The F5 security-review hand-off (roadmap) covers this whole section.

## Constraints on the mirror build (S1–S5) — ADVISORY, the reason this doc exists now

Each constraint is cheap or free if honored while S1–S5 are being built, and expensive to retrofit. The mirror chain **ratifies or refutes each** when it reaches the relevant slice (refutations get a dated note here). None of them changes mirror-visible behavior.

- **C1 (S3/S5, the big one) — one repo-writer funnel, projection as its first caller.** Build repo mutation as a per-user serialized funnel — *apply ops → sign commit → persist → emit firehose* — that the projection loop **calls**, not **is**. If the projection loop *is* the writer (owns the MST exclusively, assumes all records come from Fauna), adding the authed write surface later means rewriting S3/S5's core. The funnel's second caller (external writes) arrives in F2; its first caller is the projection loop today.
- **C2 (S3) — restate "never `putRecord`" precisely *now*, because the mirror itself needs it.** § Projection says the profile record "follows profile edits", but `app.bsky.actor.profile` is a mutable singleton at rkey `self` — an edit is an **update** op in ATProto commit semantics, which the literal "only ever `createRecord`/`deleteRecord`" wording forbids. S3 will hit this on the first profile edit regardless of the full PDS. Recommended wording: the boundary binds **posts** (immutable → create/delete only); profile-record updates are the sanctioned update path. Ratify in `atproto-pds-bridge.md` § Firm boundaries when S3 lands the translator.
- **C3 (S5) — structure re-derivation as `rebuild(sources)`, not `wipe-and-reproject-from-Fauna`.** Today sources = {Fauna projection}; the full PDS adds {native-records journal} (§ Problem 1). A rebuild path hard-coded to "the projection is the only source of records" gets rewritten; a rebuild that folds an ordered set of record sources gets a second source added.
- **C4 (S5) — the `bluesky_posts` PostId↔AT-URI map should record origin/direction.** With external writes, mappings arise from both directions (projected vs round-tripped). One additive column (`origin`) when S5 touches that schema is free now; a migration plus backfill later is not.
- **C5 (S1) — every XRPC route declares its auth class explicitly from day one.** The S1 route table should register each endpoint with a declared auth requirement (`public` for the entire mirror surface), with middleware slots for auth + rate limiting existing (empty) in the stack. This is the concrete form of the already-ratified "authed routes are additive" obligation — additive means *a new declaration value*, not *a new routing architecture*.
- **C6 (S1/S3) — keep the bridge storage non-precious.** Nothing user-irrecoverable in bridge-local storage, ever (the mirror already promises this; the full PDS depends on it — § Problem 3 puts all private data in nest state). If a slice is tempted to stash state bridge-side, the question is "would the full PDS have to migrate this into nest state?" — if yes, start it in nest state.
- **C7 (S2) — no narrowing of signing-key use.** F3/F4 sign service JWTs and session tokens with bridge-held key material under the same custody split (user rotation key senior). S2 shouldn't build key handling that assumes "the signing key only ever signs repo commits" (e.g. a sealed-blob format or capability description hard-scoped to commit signing).
- **C8 (S4/S5) — word the layer-2 disable ratification to cover future surfaces.** When S4/S5 ratify what per-user OFF means (`atproto-pds-bridge.md` § Disable & revocation layer 2), phrase it as "OFF suspends the account's ATProto presence" (projection stops, `#account` deactivation, **and any future authed surface: sessions killed, grants suspended**) — not "OFF stops projection", which would need re-ratification the day sessions exist.
- **C9 (S3/S5) — external rkeys will coexist.** Deterministic TIDs for projected records must not *assume the whole rkey space is theirs*: external `createRecord`/`applyWrites` may carry client-chosen rkeys into the same collections later. No mirror code change needed — just don't build validation/dedup that treats a non-deterministic rkey in the repo as corruption.

**Permission-set mechanics researched 2026-08-03 (the scope-model residual design pass; sources: atproto.com/specs/permission, atproto.com/specs/lexicon, atproto.com/guides/permission-sets, the bluesky-social/proposals 0011 auth-scopes proposal — docs pages only, no third-party source read):**

1. **A set is a published Lexicon document** with `title` and `details` fields "displayed as part of the OAuth flow" (i18n supported); its members are permission objects (the spec's examples show `repo` and `rpc` member types). **No nesting is defined** — a set holds permissions, not other sets, so resolution depth is 1 per include.
2. **The same-NSID-hierarchy constraint is explicit:** "Permission sets are limited to expressing permissions that reference resources under the same NSID namespace as the set itself" — same group and children "recursively deep", never "sibling groups" or parents.
3. **`inheritAud` semantics:** an `rpc` member with `inheritAud: true` inherits the `aud` from the `include:` invocation's `?aud=` parameter; a member declaring both `inheritAud` and its own `aud` "is invalid (and should be ignored)" — the spec's own invalid-member-→-ignore precedent.
4. **Resolution timing:** "At the start of a session, if a permission set can not be resolved (and is not already in a local cache), the auth request will fail." Refresh-time re-expansion is a **MAY** ("the computed permissions for the session may be updated to reflect changes to sets"). Cache guidance: **24-hour stale / 90-day expiration** lifetimes, with stale-on-failure explicitly allowed.
5. **The resolution chain is the Lexicon publication system:** DNS TXT at `_lexicon.<reversed-authority-domain>` → `did=<DID>` → the record at `at://<did>/com.atproto.lexicon.schema/<full-NSID>`. The lexicon spec cautions against caching DNS results "for long time periods" and specifies **no record authentication** (§ F4 detail's authenticated-fetch ruling is deliberately stricter).
6. **No size or member-count limits are specified** ("dozens or even hundreds of individual permissions" is the motivating scale); no AS-metadata signaling mechanism for permission-set support was found in the pages read (§ F4 detail's advertisement pin).

**D9 (decided) — the F4 OAuth provider and mail's anticipated OAUTHBEARER issuer stay separate.** `mail-credentials.md` § OAUTHBEARER token issuer anticipates a future nest OAuth issuer for MUAs; the F4 ATProto authorization server does **not** share infrastructure with it. The specs diverge where it matters (DPoP-bound tokens, PAR, client-id-as-URL metadata resolution, ATProto scope grammar + permission-set expansion vs. a plain bearer-token mint for SASL), the token audiences never overlap, and a shared "OAuth core" would be an abstraction serving two callers badly.
