## Goal

A single CalDAV entry point per nest deployment, **served by the mail-bridge MDA role** (`bins/fauna-bridges/`; role discovered from nest by the enrolled service-user keypair — no `--mode=...` flag, per `../principles.md` § One configuration surface), implementing RFC 4791 (CalDAV baseline), RFC 6578 (sync-collection), RFC 4918 (WebDAV foundation), RFC 5545 (iCalendar parsing — server-side validation on PUT), and the CalDAV / IMAP shared-quota model from `imap-server.md` § QUOTA / GETQUOTAROOT. All calendar and event state is nest-side (`bridge_caldav_calendars`, `bridge_caldav_events`, `bridge_caldav_expunged` per the I2b absorption); the MDA process is a stateless protocol terminator that holds only the per-session unwrapped MLS-decryption capability and an in-memory cache of decrypted collection metadata for the AUTH'd session lifetime.

**Bar: parity-or-better with Radicale.** Any extension a hardened Radicale install gives MUAs out of the box (sync-collection, ETag conditional updates, multistatus PROPFIND, calendar-query with time-range filters, calendar-multiget, PROPPATCH on collection metadata, RFC 6638 scheduling — in v1 scope per § Scheduling & invitations; its build state is in § Implementation status today) must be present here. Beyond Radicale, every event write is sealed-to-recipient at the MDA before reaching nest — nest never sees plaintext iCalendar bodies, recurrence rules, attendee lists, or descriptions.

**When in doubt, choose the stricter option.** Mirrors `imap-server.md` § Goal: a non-conforming MUA that violates RFC 4791 in a way a strict reading would reject loses the request rather than producing ambiguous calendar state. Permissive carve-outs need explicit user approval and a counter.

## Process topology

| Port / path | Role | Process | TLS | AUTH |
|---|---|---|---|---|
| `/caldav/{user}/` | CalDAV (REST + REPORT + PROPFIND + PROPPATCH + PUT + DELETE) | mail-bridge MDA role | served at `mail.<domain>:443` via **SNI passthrough** (§ Network exposure); same `internal/tls.CertProvider` cert as IMAP — `mail.<domain>` is already the IMAP host + a cert SAN (`mail-credentials.md` § IMAP host, `nest/common.md` § cert SAN set); TLS posture per `smtp-server.md` § TLS posture per port (1.2 floor, 1.3 preferred) | HTTP Basic Auth → AEAD-unwrap-as-auth (same wrapped-blob flow as IMAP per `imap-server.md` § Authentication) |
| `/.well-known/caldav` | RFC 6764 service discovery | mail-bridge MDA role | same | redirect to `/caldav/{user}/` post-auth |
| `/api/v1/ws/{actor_id}` | MDA ↔ nest RPC | WS-RPC + DAG-CBOR | TLS to nest's HTTPS listener | challenge-response over WS subprotocol, signed by the MDA's enrolled service-user Ed25519 keypair |

There is one MDA-role instance per nest deployment in the target shape; horizontal scaling is by enrolling additional MDA service-user keypairs and load-balancing the CalDAV HTTPS path alongside IMAP. **The same MDA process serves IMAP and every DAV protocol** — CalDAV, CardDAV (`carddav-server.md`, served), and WebDAV files (`webdav-server.md`, ratified 2026-07-06; server surface + app UI built — see that doc's own Implementation status) — one TLS termination, one WS connection to nest, one per-session decryption capability covers them all. Per-session state (the unwrapped MLS capability, the decrypted-metadata cache, the CalDAV Basic-auth credential identifier) lives in the MDA process only; persistent calendar / event state lives in nest's SQLite (`bridge_caldav_calendars`, `bridge_caldav_events`, `bridge_caldav_expunged`).

## Network exposure — single-`443`, SNI passthrough, short address

CalDAV is addressed at the **bridge hostname `mail.<domain>`** (derived from the primary mail domain by the shared `MuaInstructions::for_node_url` — `mail-credentials.md` § IMAP host; there is no hostname knob; the same host that serves IMAP on `:993`), on **port `443`** — never a non-standard port, so a MUA needs only a hostname, no `:port`. The *typed* address stays as short as the apex: a client pointed at the bare apex `<domain>` reaches nest's `GET/PROPFIND /.well-known/caldav` (the service-discovery route already in nest's surface — `nest/public-mode.md` § routes), which **`301`-redirects to `https://mail.<domain>/.well-known/caldav`** unconditionally — the apex is storage-mode-independent (below) — per RFC 6764 *cross-host* bootstrapping: the unauthenticated apex can't know `{user}`, so it hands off to the bridge host's own discovery, which post-auth redirects on to `/caldav/{user}/`. The user types `<domain>`; the client follows the two redirects to the right per-user collection on the bridge host. (A client pointed straight at `mail.<domain>` hits the MDA's `/.well-known/caldav` directly, skipping the apex hop.) The apex `301` returns `503` until mail is enabled (no primary domain → no MDA host to point at), and when CalDAV is explicitly disabled (`set_caldav_enabled(false)`; an *unset* toggle inherits `mail_enabled` — § Independent enablement — so a mail-enabled box answers without an explicit opt-in, and the apex never `503`s while the MDA serves). The apex is **storage-mode-independent**: the MDA is the only CalDAV server in *both* modes (§ Independent enablement), so it `301`s in both — exactly as the CardDAV and WebDAV apexes do. (It once served a `207 Multi-Status` discovery collection in plaintext mode, advertising the in-core store; that store was retired in the Decision-B § 4c cleanup, leaving the `207` naming a collection the nest does not serve — a MUA pointed at the bare apex of a plaintext box dead-ended there instead of reaching `mail.<domain>`.)

**SRV autodiscovery (RFC 6764 § 4) — the *other* half of "type just the domain".** The apex `/.well-known/caldav` cross-host `301` is one RFC 6764 discovery path; the **SRV** path is the other, and it is the one macOS Calendar.app's *automatic* account setup actually uses — given only `user@<domain>` it queries `_caldavs._tcp.<domain>` and connects to the host:port the record names, **without** following an apex cross-host redirect (which macOS declines during account setup — a hand-proof finding). So each local domain publishes a `_caldavs._tcp.<domain> SRV 0 1 443 mail.<domain>.` record (priority 0, weight 1, port 443, target the deployment's single CalDAV/mail host — every domain's CalDAV is served at `mail.<primary>` via SNI, so the SRV target equals the MX target). This is a **per-domain row in the unified DNS matrix** (`dns-management.md` § Records covered), built by the shared `fauna_mail::dns::per_domain::build_caldavs_srv_record` and surfaced + verified by `fauna.dns.{list,verify}_records` like every other record; the admin publishes it manually or in managed mode alongside MX/SPF/DKIM. After the SRV hop the client uses the MDA's already-served `/.well-known/caldav`, so the optional RFC 6764 § 6 `path=` TXT companion is redundant and omitted. **Only the TLS variant `_caldavs` is published** (CalDAV is HTTPS-only — no plaintext `_caldav`), and a **`_carddavs._tcp` companion is published alongside it**: the same mail-bridge MDA now also serves a CardDAV / address-book surface (`/carddav/{user}/` on the same `mail.<domain>:443`, sibling to this CalDAV surface — served since 2026-07-05, slices 1–2d), so its SRV points Contacts.app's *automatic* account setup at a real service rather than a missing one. The `_carddavs._tcp.<domain> SRV 0 1 443 mail.<domain>.` record mirrors `_caldavs` exactly (same host, same port, same SNI target) — built by the shared `fauna_mail::dns::per_domain::build_carddavs_srv_record` (sibling to `build_caldavs_srv_record`) and surfaced/verified via `fauna.dns.{list,verify}_records` like every other record. (The record's build+wiring is Slice 3 — see § Implementation status today.) (Advanced mode — the user typing `mail.<domain>` directly — works with or without the SRV record; the SRV exists to make the bare-domain *automatic* path work too.)

**nest never terminates CalDAV TLS.** On a single-IP deployment where `<domain>` and `mail.<domain>` share one address, `:443` is fronted by an **SNI-passthrough (L4) router** that terminates nothing and forwards the raw TLS stream by SNI hostname: `<domain>` → nest, `mail.<domain>` → the MDA's CalDAV listener. (IMAP/SMTP keep their own dedicated ports — 993/143/25/465/587 — with no nest conflict, so the router fronts only `:443`.) Because the router does not decrypt, **no single process ever sees the union of nest traffic and CalDAV plaintext** — nest sees only its own TLS, the MDA sees only CalDAV. A TLS-*terminating* reverse proxy is explicitly rejected: to route by path it would have to decrypt, becoming an omniscient plaintext point that buys no privacy over nest doing it (it would *widen* exposure, not narrow it).

**Client-IP propagation (PROXY protocol v2).** Because the router splices at L4, a naïve forward makes the backend see the *router's* loopback address as the peer for every internet client. That silently defeats nest's per-source rate limiting and its loopback-only `fauna.bridges.request_enrollment` trust gate — the in-container mail bridge also dials nest's loopback, so without the real client IP nest cannot tell an external client from the local bridge (security review). So the router prepends a **PROXY-protocol-v2 header** (`fauna-proxy-protocol`, `--send-proxy-to`) carrying the real client address to the **nest** backend; nest's `serve_tls` parses it (trusted only from the loopback router) and uses the conveyed address as the connection source. A headerless direct loopback dial (the bridge) keeps its genuine loopback address, so the enrollment gate still recognises it. The MDA CalDAV backend now parses PROXY v2 too: the Go `internal/proxyproto` package peels the header **below** `tls.NewListener` (and below the `internal/connlimit` wrap) on the same rules as nest — loopback-trust, signature-peek, **and the router-auth TLV check** (`../architecture/security.md` § Co-resident process trust boundary owns it) — and the router lists the MDA's loopback port in `--send-proxy-to` (`127.0.0.1:8444`). So CalDAV's AUTH lockout + `report_auth_event` key on the **real** client IP — full cross-account per-real-IP keying + a meaningful per-IP audit — with no change to the `clientIP(r)`/`r.RemoteAddr` handler seam. A direct headerless dial keeps its genuine peer. **Loopback-trust alone is deliberately not enough here**, and the reason is specific to this listener: `127.0.0.1:8444` is reachable by every co-resident UID, so a compromised sibling process (canonically the hostile-MIME-parsing MTA) could otherwise forge a header and choose the IP this section's lockout and audit key on. Verifying the router's TLV is what makes "the real client IP" a true statement rather than a claimed one; on a box with no secret provisioned the peel falls back to legacy loopback-trust, and the lockout's IP dimension is then only as trustworthy as the co-resident set. IMAP (993/143) and submission (465/587) are published directly, so their lockout + audit already key on the real IP without a header.

**Connection cap.** The CalDAV listener is wrapped in the shared `internal/connlimit` global connection cap — the same semaphore the SMTP MX / submission / IMAP listeners use (`smtp-server.md` § Connection-time limits) — an OOM/FD backstop against a connection flood. The ceiling is a compile-time `maxMDAConns` (4096), matching the IMAP surface. Because CalDAV is implicit-TLS, the cap wraps the raw socket **below** `tls.NewListener` so `http.Server` still type-asserts `*tls.Conn` and populates `r.TLS`. Saturation is observable on `mda_connections_total{listener="dav-443",result}` (`accepted`/`capped`/`per_ip_shed`) — the label is `dav-443`, not `caldav-443`, since the listener was unified as the shared CalDAV+CardDAV 443 DAV surface. This is the global backstop; the **per-IP concurrent-connection cap** (`AuthPolicy.max_conn_per_ip`, default 256, `0` = disabled) is layered below it via `internal/connlimit`'s `PerIPListener` (landed 2026-06-04, § B(b.2) — tracked internally), shed-on-cap (`per_ip_shed`), loopback-exempt, hot-reloaded on `config_changed`. CalDAV is the one MDA listener fronted by the SNI router, so its `PerIPListener` wraps **above** `internal/proxyproto` — its accept-time `RemoteAddr()` resolves the PROXY-v2-conveyed real client IP (not the router's loopback), the same seam the AUTH lockout keys on (above) — and **below** the global cap, mirroring the nest TLS loop's global-then-per-IP order.

**Request timeouts.** The CalDAV `http.Server` time-bounds the *whole* request, not just the header read: `ReadHeaderTimeout` (30 s) + `ReadTimeout` (5 min, the full body) + `WriteTimeout` (5 min) + `IdleTimeout` (2 min). Without the latter three a slow-body PUT/REPORT (size-bounded at the 16 MiB `maxRequestBytes`, but otherwise not *time*-bounded) or an idle keep-alive could hold a goroutine + buffer indefinitely (§ B6). The read budget is generous so a genuinely slow but legitimate MUA uploading a near-16-MiB calendar still completes, while a slow-loris drip is cut off.

This is what keeps the bridge a **relocatable** node. On a multi-IP / split-server deployment the SNI router disappears: `mail.<domain>` gets its own A/AAAA record (published via the client's DNS management — `dns-management.md`) pointing at a separate bridge box that terminates its own `:443`. The address the user typed never changes. See `../architecture/nest/deployment-home-with-public-relay.md` for the home-LAN instance of relocating the MDA off public infrastructure (IMAP/CalDAV LAN-bound, never tunneled through the public nest).

**Desktop / IP deployment — direct admin-set port, no SNI router (no `mail.<domain>` required).** A **desktop-native nest** (the residential box of `../architecture/nest/deployment-home-with-public-relay.md`, run on Windows/macOS via the desktop installers) *is* that "separate bridge box terminating its own port", and often has **no domain at all** — it is reached by IP/LAN address, where `mail.<IP>` is nonsense that breaks SNI host routing (`../architecture/nest/domains-and-tls-bootstrap.md` § the local-target carve-out). So on a desktop box the SNI router is **absent** and the MDA's CalDAV listener is pointed at a **routable interface on the admin-set CalDAV port** (default **8443**; IMAP keeps its own direct 993/143), reached directly at `https://<host-or-ip>:<caldav-port>/`. Discovery: a *domain* deployment's `_caldavs._tcp.<domain>` SRV record already carries the port, so RFC 6764 autodiscovery is unchanged; an *IP* deployment shows the address and port to **each member on their own mail settings page** (`mail-settings-mua-caldav-host` / `mail-settings-mua-caldav-port`, composed by `MuaInstructions::for_node_url` with the admin-set port), which is where a person setting up a calendar app looks; the admin's Calendar page sets the port and shows no address (corrected 2026-10-01: this sentence said "in the admin UI"; IP boxes cannot autodiscover regardless). **The CalDAV port is an admin choice, not deployment topology.** Per the iron-clad config-surface invariant (`../principles.md` § One configuration surface; `../architecture/nest/common.md`), a port a human *picks* is exposed as app UI in all 7 apps and persisted in **nest state** — never a config file/env. So the admin sets it from any app via `fauna.bridges.set_caldav_port` (Admin-class), nest stores it as the `caldav_port` singleton (default `DEFAULT_CALDAV_PORT` = 8443), projects it on `FetchConfigReply.caldav_port`, and the MDA binds it directly — rebinding (exit 0 → supervisor restart) on the `caldav_port` `config_changed` since an in-process listener can't be re-bound live. The legacy `caldav_listen_https` topology hatch survives **only as IPC** — the loopback port a domain box's SNI router targets, or a desktop supervisor's `<iface>:<port>` — and when present it **wins** over the admin port (the admin port drives only the no-hatch direct listener), so a router/desktop box is unaffected. Full design + the cross-platform MDA-supervision split: the desktop-native CalDAV/IMAP design (ratified 2026-06-18; tracked internally).

> **Asymmetric twin — the client-facing API serving port.** The nest's own **client-facing HTTPS API port** (the WS-RPC transport + SPA, default `443`) is the same *kind* of admin choice — the `serving_port` singleton (`fauna.admin.set_serving_port`, Admin-class), default 443 — but unlike this CalDAV port it does **not** realize on a cloud/domain box: Decision D (user, 2026-06-23) keeps a custom `serving_port` a **direct-listener feature only** (desktop / self-hosted / bare-IP); a Docker/cloud nest always serves `443` via the always-up `fauna-sni-router`, and `fauna.admin.set_serving_port` is **rejected** on a router-fronted nest rather than persisting an inert value. Owned by `../architecture/nest/common.md` § Serving ports (substrate wired + all-7-app UI landed); this CalDAV section's admin-set port applies uniformly on every deployment shape, which the serving port deliberately does not.

**Any-locator serving — the cert is name-independent, no registered domain required.** On *any* of the no-public-domain shapes above (desktop-native, or a single-IP Docker box reached by a bare IP — the single-IP home case in the any-locator design (ratified 2026-06-18; tracked internally)), the MDA serves the nest's self-signed **floor cert** (CN `fauna-nest`, SANs `localhost`/`127.0.0.1`/[the bind IP]) — there is **no `mail.<domain>` cert and no registered mail-domain**. nest's `fetch_tls_cert_blob` seals whatever floor cert is on the acme dir to the MDA regardless of the requested domain, and the MDA builds its TLS provider even when the deployment has no primary domain (fetching under a floor sentinel). Fauna apps key-bind whatever cert is served (`../architecture/security.md` § Transport trust — Axis 1, address/CA-independent); third-party MUAs TOFU-accept the self-signed floor (the SSH `known_hosts` posture sanctioned for the LAN-IP row of the trust table). On the **single-IP Docker box reached by bare IP** (the home2 / home-relay shape), `:443` stays the SNI router's (default backend = nest/SPA, the verified `https://<ip>/` path), so CalDAV is served **directly on the LAN interface at the admin-set CalDAV port** (default 8443), router-bypassing. The deployment names the interface — and *only* the interface — via the **`caldav_bind_host` topology hatch** (the entrypoint writes `caldav_bind_host = <LAN-IP>` from `FAUNA_LAN_BIND_IP`); the **port stays nest state** (the `caldav_port` admin singleton), so the MDA binds `<LAN-IP>:<admin-port>` and the admin can still change the port from any app (the rebind path stays live — *no* full `caldav_listen_https` pin, which would freeze the port). This is the exact CalDAV analogue of the IMAP LAN bind (`<LAN-IP>:993/143`), and it is **driven by the LAN topology, independent of any registered domain** — a domainless home-relay box reached by a LAN hostname/IP still serves CalDAV by bare IP, because the bind keys on `FAUNA_LAN_BIND_IP`, not on whether a domain has been claimed (`FAUNA_DOMAIN` is retired anyway; `../architecture/nest/domains-and-tls-bootstrap.md` § Env contract). Under host networking (the `docker-compose.home.yml` bundle) the LAN IP is the host's real interface, so no port-publish indirection is needed. A bare-IP box has no SRV autodiscovery anyway, so the MUA is in advanced (hand-config) mode where a `:port` is expected. (Port-number hygiene — **the nest's internal port is `3000`, NOT 8443** (`FAUNA_PORT`, the entrypoint/HEALTHCHECK/SNI-router/bridge default), so the MDA's `<LAN-IP>:8443` CalDAV bind never collides with the nest's `0.0.0.0:3000`. The earlier reasoning here assumed nest bound loopback `:8443`, but the entrypoint binds it `0.0.0.0:${PORT}` (all interfaces) — so 8443 was shared between nest and CalDAV and the MDA `EADDRINUSE`-crash-looped; **fixed 2026-06-20** by moving the nest off 8443 to 3000 (`8443` now means CalDAV only). See § Implementation status today.)

## Threat model — where calendar plaintext can exist

Server-side CalDAV is **not zero-access, and cannot be** — a generic MUA (Apple Calendar, Thunderbird) cannot decrypt Fauna's sealing, so the MDA must decrypt server-side to answer a REPORT or serve an event. It holds that capability per session (AEAD-unwrap of the password-derived blob; § Authentication). This is the deliberate convenience tier — the same reason ProtonMail's Bridge runs on the user's own device rather than their servers. Fauna-*native* apps keep zero-access (they decrypt locally); the CalDAV/IMAP surface is the opt-in "let the box decrypt while it serves me."

What the design **does** preserve:

- **Storage is ciphertext-only.** The MDA seals every event to the actor's MLS pubkey before the `put_event_ciphertext` RPC, so nest's persistent store (`bridge_caldav_*`) never holds plaintext iCalendar, RRULEs, attendee lists, or descriptions — even though the MDA decrypts transiently to serve reads. Since S6.12 (2026-07-10) the nest also *enforces* this at the RPC edge: `put_event_ciphertext` rejects an `encrypted_body` or `encrypted_index_hint` that is not a sealed recipient envelope with `fauna.protocol.malformed` (mechanism + rationale owned by `../architecture/encryption-at-rest.md` § Implementation status).
- **nest never sees CalDAV plaintext, even in transit** (§ Network exposure — SNI passthrough). The only process that ever holds a decrypted calendar is the MDA, and only for the AUTH'd session.
- **Calendar *storage/sync* has no ingest boundary; *invitations* do — and only when email is enabled.** Calendar events are written by authenticated clients (a native app that seals locally, or a CalDAV PUT the MDA seals) and, create-only, by the placement of an emailed invitation (§ Server-side auto-schedule — sealed where the mail is sealed, so it adds no plaintext point beyond the mail ingest window below), so the storage/sync surface has no plaintext ingest from the outside world of its own — the only calendar-specific plaintext point is the relocatable MDA. Cross-system **invitations**, however, interoperate via iTIP/iMIP email (§ Scheduling & invitations) so a Fauna user can exchange meeting requests with Apple/Outlook/Gmail users. Inbound invites/replies *from external (email-based) calendar systems* arrive at the **mail MTA** in cleartext and are sealed-to-recipient there — the same irreducible ingest window mail has (the one ProtonMail and every interoperating service has). Crucially this window exists **only when the user has enabled email**: by independent enablement (§ Independent enablement), a **calendar-only deployment (email off) runs no MTA, receives no inbound iMIP, and therefore has no *plaintext* calendar ingest boundary at all** — its invitations are Fauna-native (WS-RPC, sealed end-to-end between nests) only. That sealed scheduling rail is nonetheless an **ingest boundary of *effect***: it is stranger-reachable by design, and an outside party's `.ics` drives the recipient's own authenticated client to write its calendar — so what such a message may *do* is ruled separately (§ Scheduling & invitations → *Who may mutate an existing event over the inbound rail*). "No ingest boundary" is a statement about where plaintext can exist, never about who can cause a write.

Consequence for deployment: a **calendar-only** MDA (email disabled) can be moved onto user-controlled hardware the public internet cannot reach (`../architecture/nest/deployment-home-with-public-relay.md`), and then **no public box ever holds calendar plaintext at all** — its sole plaintext point is the LAN MDA, and with no MTA there is no public ingest window. A deployment that *also* runs email accepts mail's forced-public MTA window, and its calendar *invitations* ride that same window (calendar *storage* stays MDA-only-ciphertext regardless). So the privacy-maximal configuration is **calendar-only**; enabling email trades the no-ingest property for seamless email-world interop — a conscious per-deployment choice the enable-email / enable-CalDAV toggles expose. Mail can never reach the zero-public-plaintext ideal (its MTA window is forced-public); calendar-only can. See `../architecture/encryption-at-rest.md` for the storage-mode trust axis, and `imap-server.md` for the MTA-side plaintext window this contrasts with.

## Authentication

HTTP Basic Auth over TLS only. The credential is the same `(actor_id, credential_id)` pair the user provisions via their Fauna app for IMAP — **no separate CalDAV credential** (one PLAIN bridge password, auto-generated by default, serves IMAP + SMTP + CalDAV per `mail-credentials.md` § Auto-generated bridge password). **Enablement, however, is independent:** email (SMTP/IMAP) and CalDAV gate separately (§ Independent enablement) — both ride the one MDA bridge and share the one credential, but a user can run calendar without email or email without calendar. The AUTH flow:

1. MUA opens HTTPS to the MDA's CalDAV path, sends `Authorization: Basic base64(user@domain:password-or-token)` — **or, for a bare-username client (see below), `base64(user:password-or-token)`**.
2. MDA fetches `fauna.bridges.fetch_wrapped_mls_blob(actor_id, credential_id)` from nest.
3. MDA AEAD-unwraps via `libs/fauna-mls/src/wrapped_blob/` (UniFFI to Go). **AEAD-success = AUTH-success.** Same as IMAP.
4. MDA reports the outcome via `fauna.bridges.report_auth_event(result=success|fail, source_ip, reason)` — `source_ip` is the request's TCP peer address and **must be non-empty** (nest rejects an empty one). On failure: HTTP `401 Unauthorized`.
5. On LOGOUT-equivalent (the MUA's HTTP connection closes; CalDAV is connection-less so there's no explicit logout — the MDA zeroizes on inactivity timeout configured as `mail.imap.idle_timeout_seconds` reused).

**Online-guessing / KDF-exhaustion brake.** Before step 2's `validate_recipient` round-trip and step 3's Argon2id AEAD-unwrap, the MDA checks a per-`(principal, credential_id, source-IP)` failure lockout — the **same** fixed-window counter the SMTP submission and IMAP paths use (`mail.auth.max_auth_failures_per_minute`, catalog default, 1-minute window; `0` disables), implemented in the shared `internal/authlock` package and hot-reloaded on `config_changed`. The `principal` is the **canonical** `base@domain` the presented username resolves to (`auth.PrincipalKey` — the credential suffix stripped, domain lower-cased), so every form that resolves to one credential (`alice`, `alice+`, `alice+default`, bare `alice` vs `alice@<primary>`) shares a single bucket instead of each opening a fresh per-credential allowance (§ B7). The `(limit+1)`-th failure within the window returns `401` **before** any nest call or KDF, denying the attacker the bridge's per-attempt KDF cost and an AEAD-timing oracle; the counter resets on every successful AUTH. Because the SNI router now prepends a PROXY-v2 header that the MDA CalDAV listener peels — and verifies came from the router (§ Network exposure — Client-IP propagation) — the `source-IP` dimension is the **real** client address, so the lockout keys cross-account per-real-IP (in addition to per-`(principal)`) and the `report_auth_event` audit is per-real-IP — both achieved with no code change to this path (the header is stripped below `tls.NewListener`, so `r.RemoteAddr` is already the real IP). The TLV check is what keeps that dimension *sound*: an unauthenticated peel would let a co-resident process pick the key, poisoning the coarse `(source_ip)` tier against a victim's egress IP (a cross-user lockout) and evading the spray brake by rotating forged addresses. Like the submission/IMAP paths, the locked branch skips `report_auth_event` (don't inflate the audit log during a brute-force).

**Stateless re-auth and the per-`(actor, credential)` auth-material cache.** CalDAV is connection-less HTTP Basic auth, so every request (PROPFIND/REPORT/PUT/multiget) re-runs the AUTH flow above. Steps 2 and the snapshot fetch hit nest's `fetch_wrapped_mls_blob` / `fetch_mls_snapshot_blob`, which are gated by the per-`(bridge, actor, credential)` `bridge_rate_limit` (`bins/fauna-nest/src/bridge_rate_limit.rs`, 30 events / 60 s). A naïve re-fetch-per-request blows past that on any sync burst — two MUAs plus the IMAP poller all share the actor's `default` credential bucket — so nest returns rate-limited and the MDA 401s a *legitimate* request (a "works out of the box" break for a real macOS Calendar.app + Mail.app on one account). The MDA therefore caches the **password-independent** fetched material — actor id, wrapped MLS blob (ciphertext), MLS + index pubkeys, encrypted MLS-snapshot blob — per `(actor, credential)` for a short TTL (`authMaterialTTL`, `internal/mda/davauth/auth_material_cache.go` — lifted into the shared DAV-HTTP auth package alongside CardDAV/WebDAV), collapsing a request burst to a single nest fetch. The cache stores **only** ciphertext + public keys, never the unwrapped capability or the password, so the per-request Argon2id AEAD-unwrap of the presented password (step 3) **still runs on every request** — a cache hit does not weaken "AEAD-success = AUTH-success", and a wrong password still 401s (off the cached blob, without re-loading nest). The TTL is deliberately short so a credential rotation propagates within the window. This realizes the § Goal "in-memory cache … for the AUTH'd session lifetime" for the stateless-HTTP case. The lockout brake above is checked *before* the cache, so a brute-forcer is still capped per `(username, credential, source-IP)`.

**No legacy bearer-token CalDAV surface.** The transitional `bins/fauna-bridge-imap/internal/caldav/` had its own bearer-auth path; the binary was retired (tracked internally) ahead of I5, and I5 stands the unified PLAIN/OAUTHBEARER + AEAD-unwrap model up against the new MDA path.

**Bare-username clients default the domain to `PrimaryDomain` (macOS Calendar.app interop).** macOS Calendar parses a configured `user@domain` account, uses the **domain** for server discovery, and sends **only the bare local part** (`user`, no `@domain`) as the CalDAV Basic-auth username. A strict `user@domain` requirement therefore `401`s a *correctly configured* Apple Calendar with "malformed username" *before* discovery starts, which the client retry-loops into a "Connecting…" hang (Apple **Mail**/IMAP is unaffected because it sends the full address; the symptom is CalDAV-only). So when the Basic-auth username carries no domain, the bridge resolves it under the box's `PrimaryDomain` (the single-domain TLS/DKIM/EHLO anchor; `mail-multidomain.md` § The primary domain) — matching how every mainstream CalDAV server (Nextcloud / SOGo / Radicale / Baïkal) accepts a bare username. This is the **shared `auth.SplitEmailDefault`** helper, applied **uniformly across all three bridge AUTH surfaces** (CalDAV Basic, IMAP PLAIN/OAUTHBEARER, SMTP submission) so a bare username behaves identically everywhere. On a multi-domain box a bare username resolves only on the primary domain; secondary-domain users present the full address. Sub-addressing still applies to the local part (`user+credential` → credential selection).

**Any-locator local login — resolve by handle when the domain isn't a registered mail-domain (Change A).** A box reached at a bare IP / `localhost` / `.local` name has **no registered mail-domain at all** (the local-target claim skips mail-domain registration — `mail.<IP>` is nonsense; `../architecture/nest/domains-and-tls-bootstrap.md` § the local-target carve-out), so there is no `PrimaryDomain` to default a bare username to and no exact-alias to resolve `user@<locator>` against. Such a box does **not** fall back to a strict `user@domain` reject (the old behavior): on the **AUTH-login path only** (`validate_recipient`), when the address domain is not a registered mail-domain, the bridge resolves the local-part against the **unique handle→actor store** (`fauna.account` handle index), so `test`, `test@192.168.1.57`, and `test@<any-name-that-reached-me>` all authenticate to the single actor whose *handle* is `test`. This is **hijack-proof and unambiguous**: handles are unique per nest, and aliases are an Admin-only, separate namespace that never participates in the bare-handle path (an alias resolves only via its explicit `@<registered-domain>` form). **Delivery (`resolve_recipient` / `partition_recipients`) is untouched** — it stays domain/alias-strict; only local login gains the handle fallback. This is what lets a third-party MUA (Apple Calendar, Thunderbird) reach a domainless home/LAN nest by IP with just `handle` + bridge password. Authority: the any-locator design § 3, Change A (ratified 2026-06-18; tracked internally); identity model: `../architecture/security.md` § Transport trust (the keypair, not the address, is identity).

**Discovery walk (RFC 6764 / RFC 5397) — the principal is served at a single-segment path.** A real CalDAV client (macOS Calendar.app) doesn't PROPFIND the calendar home directly; after the `/.well-known/caldav` hop it walks **current-user-principal → calendar-home-set → list calendars**: PROPFIND `/` for `current-user-principal` (→ the principal href), PROPFIND the principal for `calendar-home-set` (→ `/caldav/{user}/`), then PROPFIND that home (Depth 1) for the calendar collections. (The `/.well-known/caldav` `301`/`308` lands the client on the principal, *not* straight on `/caldav/{user}/`; the § Process topology / § Network exposure "redirect to `/caldav/{user}/`" describes the eventual destination — the principal is the standard intermediate hop.) The MDA serves CalDAV via **emersion/go-webdav**, whose handler routes a request to its resource type purely by **path-segment depth** (`caldav.backend.resourceTypeAtPath`: depth-1 → user-principal, depth-2 → calendar-home-set, depth-3 → calendar, depth-4 → calendar object). Consequently the **principal is served at a single-segment path `/{user@domain}/`** (`internal/mda/caldav/backend.go::CurrentUserPrincipal`), *not* a `/principals/{user@domain}/` two-segment path: a 2-segment principal lands at the same depth as the calendar-home-set (`/caldav/{user@domain}/`) and emersion misroutes a PROPFIND of it into the home-set branch, whose path-equality guard then fails and it serves an **empty multistatus** — the exact macOS Calendar "Connecting…" stall (Gap 1c). At a single segment emersion's own `propFindUserPrincipal` fires and returns `calendar-home-set`, so the walk completes. The principal path is an opaque account-config value; only the `/caldav/{user}/…` tree is otherwise referenced (owner, collections, events).

**No anonymous CalDAV.** Service discovery (`/.well-known/caldav`) requires auth too — the redirect (to the principal, then on to `/caldav/{user}/`) happens post-auth so the path doesn't leak whether a user exists.

## Independent enablement

Email (SMTP/IMAP) and CalDAV are **separately enableable**, even though one MDA bridge serves both and one credential authenticates both. The reason is infrastructure prerequisites: **email** needs MX + DKIM + SPF/DMARC + port-25 reachability + a deliverability reputation; **CalDAV** needs only the HTTPS surface (a publicly-trusted cert for `mail.<domain>` + the SNI-router, § Network exposure). So a deployment that can't (or won't) run real email can still offer calendar sync, and a user who only wants mail needn't expose a calendar surface.

- **Two intent flags, machine-derived at claim, and set directly from the admin shell:** `fauna.bridges.set_mail_enabled`, `fauna.bridges.set_caldav_enabled`. Each defaults to the machine-derived § 3b rule — `onboarding.md` § 3b owns it: handle locality AND the NAT axis (OFF for `user@localhost` / `user@IP`, and OFF on a private-axis box, whose serving is provisioned by the relay-link path instead) — with no onboarding checkbox to toggle it; the former `onboarding-enable-email-checkbox` / `onboarding-enable-caldav-checkbox` retired with the `encryption_mode_choice` page and were **not relocated** (no-modes, ratified 2026-07-12). Nest-side, an **unset** `caldav_enabled` singleton falls back to the mail toggle — `fetch_config` projects `get_caldav_enabled().unwrap_or(mail_enabled)` (`bins/fauna-nest/src/bridge_routing_handlers.rs`) — so a mail-enabled box serves calendar out of the box until the admin explicitly toggles CalDAV off. This is a **default, not a force-disable**: the user can still toggle CalDAV on, and on a domainless / bare-IP nest **CalDAV works when enabled** — the MDA serves nest's self-signed **floor cert** (no `mail.<domain>` cert needed) and login resolves by handle (§ Authentication — any-locator local login; the any-locator design, tracked internally). **Email** is the genuinely domain-gated subsystem (it needs MX + DKIM + SPF/DMARC + a deliverability reputation a LAN box can't get), so the email default stays strict for the local case. Both flags are deployment-wide singletons, so an admin also flips them directly: `mail.enabled` from `admin-mail`'s `admin-mail-enabled-toggle` (`admin.md` § 6 Mail) and `caldav.enabled` from `admin-calendar`'s `admin-calendar-enabled-toggle` (`admin.md` § Calendar) — the admin shell is the change surface alongside the claim-time launch glue and the user mail-settings page. The MDA runs iff `mail_enabled || caldav_enabled`, so the one bridge is "enabled if either toggle is on", whichever surface set it.
- **One bridge, per-protocol gating.** The MDA process serves IMAP (993/143) and CalDAV (443 → `:8444` behind the SNI-router) from one TLS termination + one WS connection. Each protocol's listener is gated by its own enable flag: with email off + CalDAV on, the MDA serves CalDAV but not IMAP, and the SMTP submission/MX (MTA role) stay down.
- **Shared credential regardless.** Whichever subset is enabled, the actor's single PLAIN bridge password (auto-generated; `mail-credentials.md` § Auto-generated bridge password) is what the MUA presents; the MDA AEAD-unwraps the same `(actor_id, "default")` wrapped blob for either protocol.
- **Credential management reachable for a CalDAV-only deployment.** Because the credential is shared, a CalDAV-only user obtains + rotates the one bridge password on the same mail-settings page; the render predicate and section scope are owned by `docs/goal/ui/mail-settings.md` § CalDAV-only mailbox (the independent-enablement UX gap closed (tracked internally)).

## Calendar collection model

### Per-actor calendars

Every actor owns zero or more calendar collections at `/caldav/{user@domain}/{segment}/`. The on-the-wire `calendar_id` is a 32-byte blob (per `libs/fauna-protocol/src/bridge_routing.rs::ProvisionCalendarRequest.calendar_id`); the URL `{segment}` maps to it via `resolveCalendarSegment` (`internal/mda/caldav/backend.go`): a **64-hex** segment decodes directly (the shape a Fauna app and the lazy "Personal" calendar use, where the segment *is* `hex(calendar_id)`), and any **other** non-empty segment — the opaque slug a stock CalDAV client (macOS Calendar.app) picks for a `MKCALENDAR` it issues — maps deterministically to `calendar_id = blake3(segment)[:32]`. The mapping is one source of truth, shared by every path parser (PROPFIND/PUT/REPORT/DELETE/PROPPATCH/sync), so a client-chosen URL resolves to the same id on every request. Calendars are owned by exactly one `actor_id`; sharing is out of scope for v1 (§ Out of scope / follow-on tasks; RFC 4791's scheduling extension RFC 6638 is in v1 scope — § Scheduling & invitations).

### Lazy "Personal" calendar

A freshly-AUTH'd actor with zero provisioned calendars sees a lazy-created `Personal` calendar on first PROPFIND of `/caldav/{user}/`. The MDA calls `provision_calendar(actor_id, calendar_id=blake3("personal")[:32], encrypted_metadata=seal({displayname: "Personal", color: "#3273dc"}))`; subsequent PROPFINDs return the persisted row. Rationale: works-out-of-the-box (`../principles.md` § Works out-of-the-box) — a fresh deployment + a fresh user + Apple Calendar pointed at `/caldav/{user}/` sees a working calendar without the user's Fauna app being open.

User-created calendars (named "Work", "Family", etc.) come from the user's Fauna app via the existing `provision_calendar` RPC (also allowed to `User`-class callers per `bridge_method_allowlist.rs`), OR from a CalDAV MUA on `/caldav/{user}/{segment}/` via **either** verb:

- **`MKCALENDAR`** (RFC 4791 §5.3.1) — the dedicated calendar-create verb **macOS Calendar.app** (and most stock clients) send when a user adds a calendar. emersion/go-webdav routes only `MKCOL`, so the MDA handles `MKCALENDAR` in `newMkcalendarInterceptor` (`internal/mda/caldav/mkcalendar.go`), parsing the optional `<C:mkcalendar><D:set><D:prop>…` body for `displayname`/`calendar-color`/`calendar-description` (defaults applied when absent). Without this interceptor `MKCALENDAR` falls through to emersion's `405` and Calendar.app shows "This is not a location that supports this request."
- **`MKCOL`** (extended-MKCOL with a `<C:mkcalendar>`-flavored resourcetype body) — routed by emersion through `Backend.CreateCalendar`.

Both translate to a `provision_calendar(update_metadata=false)` insert at the `{segment}`-derived `calendar_id` (§ above). Re-creating an existing `calendar_id` returns `405 Method Not Allowed` per RFC 4918 §9.3.

### Standard properties

Each calendar collection has the following DAV / CalDAV properties, sourced from the decrypted `encrypted_metadata` blob:

| Property | Source | PROPPATCH allowed |
|---|---|---|
| `displayname` | metadata | yes (Tier-3 user) |
| `calendar-color` | metadata | yes (Tier-3 user) |
| `calendar-description` | metadata | yes (Tier-3 user) |
| `getctag` (RFC 6578) | `bridge_caldav_calendars.highestmodseq` (decimal string) | no |
| `getetag` (per event) | `bridge_caldav_events.etag` | no |
| `resourcetype` | constant `<collection/><calendar/>` | no |
| `supported-calendar-component-set` | constant `VEVENT, VTODO` | no |
| `max-resource-size` | constant 16 MiB | no |
| `current-user-privilege-set` | constant `<all/>` for the owning actor | no |
| `owner` | constant `/caldav/{user}/` of the AUTH'd actor | no |

`supported-calendar-component-set` is constant `VEVENT, VTODO`; `VJOURNAL` is out of scope (no UX surface; the events.md page is event-only).

**Metadata-blob canonicality contract.** The `encrypted_metadata` plaintext (a `{displayname, color, description}` CBOR map, sealed-to-recipient) **must be canonical DAG-CBOR (length-first key sort)** regardless of which side wrote it. A native Fauna app reads the *same* blob the MDA seals (a calendar the MDA lazy-creates on PROPFIND, then the client lists) and decodes it with a *strict* canonical decoder — so an MDA that emitted struct-field-order CBOR (bare `cbor.Marshal`) is rejected and renders as **0 calendars** on every native Events page, even though CalDAV MUAs read it fine (the MDA's own permissive decoder hid the asymmetry). Both producers therefore seal canonically: the MDA via `internal/dagcbor.Marshal`, the client via `fauna_core` canonical encoding. Regression-pinned by `TestSealCollectionMetadataIsCanonicalDagCbor`.

**The other way this blob fails to open — a key the MDA does not hold.** The metadata is sealed to the actor's published recipient key, so the MDA can open it only while the matching secret is in the MLS snapshot it loaded at AUTH. The two halves of the post-quantum (X-Wing) recipient keypair travel to the box by different RPCs, and the rule binding them — every client path that publishes the encapsulation key rewrites the snapshot in the same transaction — is owned by [`../architecture/security/post-quantum.md`](../architecture/security/post-quantum.md) § Post-quantum key publication and derivation. Read that section before diagnosing a `caldav: skipping calendar with undecryptable metadata` WARN: it is the failure the rule prevents, and the read path answers it by dropping the collection from the home set (below), so the user sees a calendar disappear rather than an error. The WARN is deduped to once per collection id (`internal/mda/dav.UndecryptableWarnDedup`, shared with the CardDAV twin) because it otherwise repeats on every PROPFIND.

### Event resources

Events live at `/caldav/{user}/{calendar-id}/{event-uid-hash}.ics`. The path component is the blake3 hash of the event's plaintext `UID` (hex-encoded, 32 bytes), not the UID itself — the plaintext UID stays inside the sealed body (Decision 7 in the I2b D.5 plan: "leaking which would let a caller probe whether a calendar exists" — extends here to per-event probing).

**Canonical body + Fauna sidecar.** Each event row carries **two** sealed payloads:

- `encrypted_body` — the canonical RFC 5545 **VEVENT** (`.ics`). This is the *only* thing the MDA serves to a CalDAV MUA, so a generic client (Apple Calendar) sees a clean, portable, standard `.ics`. Everything iCalendar can express lives here: `SUMMARY` / `DTSTART`+`DTEND` / `DESCRIPTION` / `LOCATION` / `RRULE` / `VALARM` (the single reminder) / `ORGANIZER` (= the Fauna event author) / `ATTENDEE;PARTSTAT=…` (the roster).
- `encrypted_fauna_ext` — an **optional** sealed Fauna-extension sidecar, fetched only by Fauna apps via the read RPCs and **never** sent to a MUA. It holds the data with no faithful iCalendar home: the true RSVP state where it refines the wire value (the `interested` state — § Independent enablement of RSVP semantics below), per-attendee nest-url resolution hints (for the WS-RPC delivery path), and any future Fauna-social metadata.

**Sidecar invariants:** (1) the VEVENT is the lowest-common-denominator truth; the sidecar is a Fauna-only *refinement* layer authoritative *only where it speaks*. (2) A MUA write (`PUT` carries no sidecar) must **preserve** the existing `encrypted_fauna_ext` (the MDA passes `encrypted_fauna_ext = None` ⇒ keep prior); only a Fauna-app write replaces both halves. A MUA edit still bumps `etag`/`highestmodseq`, so Fauna apps re-read and keep the sidecar attached. This is a nullable `encrypted_fauna_ext` column on `bridge_caldav_events` + an `Option<encrypted_fauna_ext>` field on `PutEventCiphertextRequest`.

## Read surface (brief)

Read RPCs are already cataloged in `../architecture/apps/bridges.md` § Phase D — the MDA invokes them verbatim and does not redefine the shape:

`list_calendars`, `query_events` (calendar-query / calendar-multiget translation), `sync_calendar_since` (RFC 6578 sync-collection). The MDA fetches calendar metadata + event ciphertext bytes via these RPCs, decrypts in-session via the per-session MLS capability, derives DAV properties locally, and returns the WebDAV multistatus response.

Time-range filtering (the `<C:time-range>` element on `calendar-query`) is **MDA-local**: nest stores opaque sealed bodies, so it cannot filter on recurrence-rule expansion; the MDA fetches the calendar's events (or the resume-paginated subset since the last sync token), decrypts them, expands recurrence rules via `mailfauna.ExpandRecurrence`, and filters on the window. The full-calendar fetch (`fetchAllEvents`) is **bounded pagination**: it pulls `query_events` in `reportPageSize` (1000) chunks — each well under the bridge's 16 MiB WS read cap — accumulating up to a `maxReportEvents` hard cap of **~10k events per calendar**. Within that envelope the result is complete; a calendar beyond it is **truncated + logged** (§ B6, 2026-06-24 email-component-compromise review) pending the future "encrypted index on DTSTART buckets" follow-up (listed in § Out of scope / follow-on tasks) that would let the MDA fetch only the DTSTART-window events without decrypting the whole calendar.

### Atomicity rule

Every single-RPC write (PUT / DELETE / single-collection PROPPATCH) is one nest SQLite transaction. The MDA reports success to the MUA only after the RPC's commit returns.

MOVE / COPY span two RPCs (delete_event + put_event_ciphertext) because nest doesn't yet expose an atomic cross-calendar move RPC. The MDA pattern: put_event_ciphertext at destination first → on success, delete_event at source → on success, return `201`. A destination-PUT failure leaves the source intact (MOVE never started). A source-DELETE failure after a destination-PUT success leaves a copy at destination + the original at source — return `202 Accepted` with a body `<error><multistatus>...</multistatus></error>` describing the inconsistency; the MUA is expected to retry the source-DELETE on its next sync. **This is the only multi-RPC write the MDA performs;** every other write is one RPC.

### Create-then-rename race (collection PROPPATCH visibility retry)

A stock client that creates **and names** a calendar in one user action — macOS Calendar.app's "add a calendar", then type a name *before tabbing away* — fires `MKCALENDAR` and the rename `PROPPATCH` back-to-back on **separate** connections. Every CalDAV request shares the one MDA→nest WS-RPC caller and the nest serializes calendar state on a single SQLite connection, so the `PROPPATCH`'s `list_calendars` read can win the conn lock microseconds *before* the concurrent `MKCALENDAR` insert commits → an empty list → a spurious `404` that makes the client roll the name back to its local "Untitled" placeholder (the user-reported symptom, 2026-06-08). Note the diagnostic asymmetry: a *post-create* rename (a standalone later `PROPPATCH`) always succeeds because the calendar is fully committed — only the **create-time** rename races, which is the signature of a visibility race rather than a structural URL/body/parser bug.

The collection-`PROPPATCH` handler therefore **re-reads `list_calendars` under a short bounded back-off** (`createVisibilityRetrySchedule`, `internal/mda/caldav/props.go`) before returning `404`, so the in-flight insert lands and the rename applies in **either** arrival order. The common path — calendar already present on the first read (the standalone post-create rename) — never sleeps. A genuine `PROPPATCH` against a calendar the actor doesn't own walks the whole schedule once, then `404`s. The fix is server-side and ordering-independent and does **not** weaken `MKCALENDAR`'s "existing collection → `405`" contract: the create still inserts-or-`405`s, and the rename only ever *updates* (an upsert-on-`PROPPATCH` would instead let a `PROPPATCH`-arrives-first ordering create the row, then `405` the trailing `MKCALENDAR` — strictly worse). Pinned by `internal/mda/caldav/props_test.go::TestPropPatchAbsorbsCreateThenRenameRace` (deterministic via the `list_calendars` reply queue: empty → populated).

## Sync model (RFC 6578)

`sync-collection` REPORT against a calendar collection returns the events changed (and tombstones written) since the supplied `sync-token`. The wire shape:

- The MUA's first sync uses `sync-token` = `<sync-token>0</sync-token>` (RFC 6578 §3.1; we follow nest's `SyncCalendarSinceRequest.sync_token` convention where `"0"` = full sync).
- Subsequent syncs use the `new_sync_token` from the prior response.
- Reply is a multistatus with one `<response>` per changed event (with the decrypted iCalendar body) and one per tombstone (with `404 Not Found` and the resource path; per RFC 6578 §3.6).
- `new_sync_token` is the calendar's current `highestmodseq` as a decimal string (passed through `SyncCalendarSinceReply.new_sync_token`).

### Stale sync-token handling

If the supplied `sync-token` predates the calendar's tombstone retention window (configurable; defaults to 30 days per `mail.imap.tombstone_retention_days` — the IMAP and CalDAV tombstone retention share the same admin knob), the right reply is **not** `SyncCalendarSinceReply::CalendarNotFound` (which means the *calendar* is gone, not the token). Instead, nest returns the existing `SyncCalendarSinceReply::Ok` shape with a dedicated stale-token signal so the MDA can distinguish it from the steady-state "no changes since last sync" reply (which has the same `more: false` + empty `expunged` shape). The MDA emits the `<DAV:valid-sync-token>` precondition failure response (RFC 6578 §3.8) when the supplied token is stale past retention; the MUA falls back to a full PROPFIND + per-event GET.

**See also.** Tombstones are also persisted to the `__calendar-placement` reserved folder (per `reserved-folders.md` § __calendar-placement Sync). Snapshot rows pin the placement manifest alongside the content manifest so DR restore preserves the sync-token continuity property.

**Restore divergence.** When the supplied `sync-token` (= modseq, base-10) exceeds the calendar's current `highestmodseq` — the post-restore "MUA ahead" case — the nest writes one row into `bridge_restore_divergence` (`protocol = 'caldav'`, `collection = <calendar_id hex>`, `client_modseq = sync_token`, `server_modseq = highestmodseq`, `lost_event_count = sync_token - highestmodseq`, `mua_id` from the HTTP `User-Agent` request header or `NULL`) and returns `SyncCalendarSinceReply::Stale { server_modseq }`. The MDA translates `Stale` to the standard `DAV:valid-sync-token` precondition-failure response per RFC 6578 §3.8, which causes the client to fall through to a full PROPFIND + per-event GET on that calendar.

Server-side state wins; the divergence row is forensic so the Backups page can render "N writes lost" — see `docs/goal/ui/backups.md` § Restore divergence.

**Etag generation.** `bridge_caldav_events.etag = format!("{:016x}", modseq)` — hex-encoded per-event modseq. This is byte-stable across restore (the placement manifest preserves modseq verbatim), so MUA `If-Match` conditional updates continue to work after a DR restore for events whose modseq the MUA had observed at backup time. Picked from the two options in the restore design (ratified 2026-05-14; tracked internally) — modseq form is naturally preserved by the placement journal and matches existing test invariants (`bins/fauna-nest/src/bridge_caldav_handlers.rs` `etag_format_is_hex_modseq`-style assertions verify this in CI).

## Scheduling & invitations (iTIP / iMIP, server-side auto-schedule)

CalDAV stores/syncs *one user's* calendar; **invitations between people ride iTIP/iMIP email**, delivered through the existing mail bridge. These are separate layers, which is what makes interop broad and the build tractable. `ORGANIZER` = the event author; `ATTENDEE;PARTSTAT=…:mailto:<handle>` = the roster — both live in the canonical VEVENT (§ Event resources), so every standard client renders the roster natively. Because in production a Fauna **handle domain == the mail domain**, `mailto:alice@example.com` is simultaneously a valid iCalendar `CAL-ADDRESS`, a deliverable email address, and a Fauna identity — so the same `ATTENDEE` line works for Fauna and non-Fauna invitees alike.

### Server-side auto-schedule (the MDA advertises `calendar-auto-schedule`)

The MDA advertises RFC 6638 auto-scheduling + per-principal scheduling Inbox/Outbox, so **any** client — including a stock Apple Calendar with no Fauna app present — can *organize*: add attendees and have invites fan out, receive invites, and respond. Almost all of RFC 6638 maps onto operations the bridge does **without any standing decryption capability** (preserving the threat model):

- **Organizer fan-out** (an organizer PUTs/updates an event with attendees): happens *inside the organizer's AUTH session*, so the MDA already holds their per-session capability. It decrypts the VEVENT, generates the iTIP `REQUEST` / `CANCEL`, and routes per recipient:
  - **email-reachable** (external Apple/Outlook/Gmail, or a mail-enabled Fauna handle) → an **iMIP email via the bridge MTA** (the real outbound mail path — DKIM/SPF/DMARC-authenticated, so invites aren't spam-filtered). Mechanically the MDA enqueues this through the **same `fauna.bridges.enqueue_outbound_mail` RPC the MTA submission path uses**, but **caller-scoped**: the RPC is `BridgeMta | BridgeMda`, and for a `BridgeMda` caller nest requires an `on_behalf_of_actor` and rejects the call unless `original_sender` resolves (exact alias, the same path AUTH uses) to that actor — so the MDA may enqueue *only* as the one organizer whose encrypted PUT session it is inside, never an arbitrary or external From (the same `target == actor` shape `require_caller_scope` enforces for the calendar storage RPCs; the MDA's grant is strictly narrower than the MTA's sender-unconstrained submission grant). **In-domain short-circuit (nest-side partition):** an attendee on *this* deployment's own mail domain (a mail-enabled Fauna handle on the box, including a `+suffix` sub-address that resolves back to a local mailbox) is **not** relayed out to MX — that would self-loop back through the box's own inbound listener and, on a containerized deploy, `554`-bounce at the inbound HELO-identity check (the loopback source is the docker bridge IP, not loopback). Instead `enqueue_outbound_mail` partitions recipients — the same split `fauna.email.send` and the Go MTA submission path (`partitionRecipientsByLocalDomains`) make — and any in-domain recipient that resolves to a local mailbox (via the full alias resolver: exact / `+suffix` / wildcard / catch-all / disposable / RFC 2142 role-address) is **sealed to that recipient's MSEK-derived pubkey and delivered locally** through the shared sealed-ingest path (`__mail/<actor>` segment + `bridge_imap_messages` INBOX), exactly like inbound mail; only genuinely off-box recipients ride the MX-relay queue. So an organizer inviting an in-domain attendee lands the invite in that attendee's mailbox with no self-loop. (An in-domain address that resolves to an admin external-forwarder, or that fails to resolve, falls through to the outbound queue — the inbound MX leg resolves the forwarder, or an unknown local part bounces there.)
  - **mailbox-less Fauna user** (CalDAV enabled, email disabled — independent enablement) → **WS-RPC sealed delivery** to their nest (resolved automatically from the typed CAL-ADDRESS via `resolve_attendee_transport` — no manual nest-URL entry), sealed end-to-end. **Mechanism (ratified 2026-06-05; the Fauna-app rail LANDED same- + cross-nest — see Implementation status today):** the iMIP rides the **existing cross-nest MLS transport** — delivered as a conversation/welcome over `fauna.conversations.keypackage.fetch` + `…welcome.deliver` / `fauna.federation.welcome.deliver` (key packages are *designed* to be cross-nest fetchable), so there is **no new standing-key surface** and the mail threat model is not weakened; the recipient client extracts the iMIP exactly like the inbound-`REPLY` merge. The one-off welcome is tagged **`WelcomeKind::Scheduling`** (the `"scheduling"` channel-type) so the recipient's receive loop routes that channel's application messages to the calendar-apply path, **not** the conversation UI — a scheduling delivery never surfaces as a chat thread. (The rejected alternative — exposing the recipient's mail HPKE pubkey to User-class + cross-nest and adding a new sealed-scheduling-delivery RPC — is a net-new key-exposure surface.) Needs a client-side scheduling-inbox drain loop (a mailbox-less user runs no mail poll today). **Status (see Implementation status today):** the Fauna-app rail (a Fauna app acting as organizer) is wired + tier_3-proven **both same-nest and cross-nest** — the cross-nest case (an attendee on a different, *unpaired* nest) landed via the membership-gated `fauna.federation.channel.fetch` relay (the federation track): the recipient's `poll_inbound_scheduling` carries the channel's home-nest URL learned from the `Scheduling` Welcome envelope and fetches through its own nest, so the rail works cross-nest unchanged. Design + flow: `direct-messages.md` § Technical Flow — Cross-Nest (step 3) + `federation.md` § Federation residue surface. The **MDA gateway** routing a mailbox-less recipient over this same rail — an *external* organizer's server-side auto-schedule fan-out (the "Organizer fan-out" path above, run inside the organizer's AUTH session) — is now **fully wired, same-nest AND cross-nest** (`internal/mda/caldav/autoschedule.go`): the same-nest leg landed C4/C5 2026-06-15 + the email-disabled-nest classifier fix 2026-06-16, and the **cross-nest leg LANDED 2026-06-16** (tracked internally; § Implementation status today). **Server-side classification rule:** the MDA gateway routes a **local-domain** attendee onto the sealed rail when the **deployment is email-disabled** (`MailEnabled=false`), *not* when `resolve_recipient` Rejects — because enabling CalDAV mints the canonical `<handle>@<domain>` alias for AUTH (`ensure_canonical_handle_alias`), so a CalDAV-only actor *does* Resolve. This is the same-nest mirror of the cross-nest decision; an **off-box-domain** attendee is classified by the *same* shared resolver `resolve_attendee_transport` (reached over the `mailfauna.ClassifyAttendeeTransport` UniFFI export), which anon-discovers the peer nest directly and keys on **that nest's** `email_enabled` — so a mailbox-less Fauna attendee on a different, email-disabled nest rides the sealed rail (`peer_domain` = the foreign domain), one source of truth for "email vs sealed" across the native send path and the MDA gateway (§ Implementation status today). (Per-recipient email-disabled on an email-enabled nest is out of scope: the design is deployment-level — a CalDAV-only deployment.) (Per-recipient email-disabled on an email-enabled nest is out of scope: the design is deployment-level — a CalDAV-only deployment). **Signing-identity resolution (ratified 2026-06-15, the gap this design was silent on):** the MDA never holds the organizer's Ed25519 secret (CalDAV auth is password→capability), so it cannot create the one-off MLS group *as* the organizer. It mints a fresh **ephemeral** MLS identity per delivery, so on this rail the MLS creator credential identifies nobody and the recipient ignores it (the tier_3 `ephemeral_mls_sender_scheduling_delivery_is_received_and_applied` test pins that an ephemeral-signed delivery is still received and applied). **Amended 2026-09-20:** the earlier wording here — that this is sound "because the apply path authenticates the invite by the iMIP `ORGANIZER`" — is **withdrawn**: an `ORGANIZER` line is attacker-written text and authenticates nothing. What identifies the deliverer on *both* rails is the **home-nest-attested record author** — the nest posts the gateway's record *as the organizer* (`deliver_scheduling_as_organizer`, the `on_behalf_of_actor`-scoped caller), exactly as it posts a Fauna app's record as its authenticated caller — and the authorization rule built on it is § *Who may mutate an existing event over the inbound rail* below. The MDA seals the welcome+message **itself** (the nest only ever sees ciphertext — the encryption invariant; the chosen design over the simpler nest-side variant that would expose the iMIP plaintext to the nest), via `mailfauna.BuildSchedulingDelivery` (`fauna_mail::scheduling`, ephemeral-signer over the single-sourced `fauna_mls::engine::build_scheduling_delivery` the Fauna app rail also uses), then ships the opaque bytes over a **narrow caller-scoped** `fauna.bridges.deliver_sealed_scheduling` RPC (BridgeMda, `on_behalf_of_actor`-scoped to the organizer — mirroring `enqueue_outbound_mail`) plus a `keypackage.fetch` widening to fetch the recipient's key package — keeping the MDA's new perimeter to one delivery RPC + one public read rather than blanket-widening the conversation RPCs (§ Implementation status today).
- **Inbound invite** (an external organizer invites a Fauna user): the MTA receives the iMIP `REQUEST` in cleartext and **seals it to the recipient** (`EncryptToRecipient` — the same encrypt-only primitive inbound mail uses; the bridge never decrypts the recipient's store) and drops it on their calendar. Their Apple Calendar then shows the invite (decrypted in *their* session). **Rules of the placement (ratified 2026-09-24 with the build):** (1) **one reading of an invitation** — the shared-Rust `fauna_mail::icalendar::invite_from_mail` decides whether a message is a `REQUEST` carrying a `UID`, a `DTSTART` and an `ORGANIZER`, and renders the stored body through `fauna_core::ical::render_stored_event`, the same renderer a Fauna app's own PUT uses, so a stranger's bytes never reach a calendar collection unparsed; (2) **two delivery paths, one placement** — mail from another server crosses the Go MTA, which seals the event exactly as the MDA seals a PUT and hands nest ciphertext over the MTA-only kind `fauna.bridges.place_inbound_invite`, while mail from a sender on the nest's own domain never crosses the MTA (the in-domain partition), so the nest reads and seals it itself at the same moment it seals the mail; both land in `place_sealed_invite`, which lazily provisions `Personal` exactly as a first PROPFIND would; (3) **the invitation goes where its mail went** — placed only after the mail copy is delivered, never when the recipient's guardian mail gate holds the sender (recomputed nest-side from the envelope sender, the `Withheld` reply) and never from a copy filed as spam; (4) **create-only** — an event already carrying the `UID` on any of the recipient's calendars is left byte-for-byte untouched, because email proves nothing about who sent it (the *Who may mutate* ruling below applies the same reasoning to the sealed rail); an organizer's update or cancellation by email stays in the inbox for the user's Fauna app or calendar app to act on. Placement is best-effort after delivery: a failure costs the calendar entry, never the mail.
- **Responding** (a Fauna user RSVPs in any client): set in their session → the MDA emits the iMIP `REPLY` to the organizer — in-session, capability present. A stock calendar app answers by re-storing the event with its own `PARTSTAT` changed, so the MDA reads the prior stored body on any PUT of an event with an `ORGANIZER` and sends a `REPLY` exactly when the signed-in attendee's answer (`ACCEPTED` / `DECLINED` / `TENTATIVE`) differs from the stored one — an app re-storing an unchanged answer on every sync sends nothing, and the organizer's own PUT is the organizer fan-out's, never a reply. The decision and the message are the shared-Rust `fauna_core::ical::build_attendee_reply_imip` (reached by the Go MDA as `mailfauna.BuildAttendeeReplyFromICS`), built by the same `build_event_imip` a Fauna app's RSVP reply uses, and the reply rides the same rails as the organizer's fan-out.

So *organize / get-invited / respond* all work for an Apple-only user with **zero** standing access for the bridge — the encryption invariant (bridge sees plaintext only transiently, in-session) holds.

**Advertisement contract (RFC 6638 §2; LANDED 2026-06-05, `internal/mda/caldav/schedule.go`).** For a stock client to actually *defer* to this server-side scheduling — rather than ALSO sending its own client-side iMIP, producing **duplicate invites** — the MDA must advertise the capability, and the advertisement must be self-consistent:

- **OPTIONS** on every scheduling-capable resource returns `calendar-auto-schedule` in the `DAV:` response header (alongside `calendar-access`).
- **The principal** (`/{u}@{d}/`) serves three properties (namespace `urn:ietf:params:xml:ns:caldav`) beside the discovery props (`calendar-home-set`, `current-user-principal`, `resourcetype`): `calendar-user-address-set` — a `mailto:{u}@{d}` href (the value the client matches against the VEVENT `ORGANIZER`/`ATTENDEE` to recognise "me", RFC 6638 §3.1) plus the principal href — and `schedule-inbox-URL` + `schedule-outbox-URL`.
- **The schedule Inbox and Outbox are real collections** reporting `DAV:collection` + `CALDAV:schedule-inbox` / `schedule-outbox` in their `resourcetype` on PROPFIND (RFC 6638 §2.1/§2.2 MUST). They are **empty and not browsable** — incoming invites are sealed-to-recipient onto the calendar directly (above) and replies merge client-side (below), so no scheduling message is ever surfaced there, and the Outbox needs no iTIP `POST` (organizer fan-out is *implicit*: the server fans out on the PUT, never on an Outbox POST). But they MUST exist and be correctly typed — a half-advertised surface (token present, URLs 404) is the worst case, since a client may suppress its own iMIP against a server it then can't schedule through.

Implemented as the MDA scheduling interceptor, wired ahead of emersion/go-webdav's handler (which hardcodes a `calendar-access`-only OPTIONS header and a fixed principal prop set, neither reachable through its Backend interface). Pinned by the in-process Go twins (`internal/mda/caldav/server_test.go::TestServer{AdvertisesCalendarAutoScheduleInOptions,PrincipalAdvertisesSchedulingProps,ScheduleInboxOutboxReportResourceType}`) + the tier_3 real-binary `tests/e2e-unified/tests/test_caldav_discovery_sequence.py` Hop 4. The live macOS Calendar.app connect is the end-to-end hand-proof; the advertisement must be **redeployed to the box before the gateway is relied on in production**.

### The one operation with a cost: applying a `REPLY` to the organizer's stored event

Flipping an attendee's `PARTSTAT` on the *organizer's* stored copy (so the organizer's Apple Calendar shows "Carol ✓") mutates an existing sealed-to-organizer object from input that arrives when the organizer may be offline. **v1 design (privacy-preserving):** the server delivers the `REPLY` encrypt-only into the organizer's scheduling Inbox; **the organizer's Fauna app merges it** on next sync and re-PUTs the updated event — Apple reflects it shortly after. No standing capability; the cost is a small lag and that a Fauna app must *eventually* sync (every Fauna user has one — the Fauna app is primary, CalDAV is the additional surface).

**Deferred enhancement (`roster-split`, has a privacy cost — opt-in, not v1):** to make a reply reflect *instantly* for an "Apple-only, no Fauna app anywhere" user, the bridge would hold a **standing capability**. Bound it by splitting each event into **content** (time/title/description/location — sealed to the user only; bridge sees it only in-session) and a **roster object** (attendees + `PARTSTAT` — bridge holds a standing capability *to this only*); the bridge applies replies to the roster async without ever holding standing access to event content, and the served `.ics` is content ⊕ roster merged in-session. This persists a (RSVP-scoped) decryption capability on the bridge — a real weakening of encrypted mode — so it is documented-but-deferred, enabled only if that narrow case proves to matter.

### Where logic lives

iMIP `REQUEST`/`REPLY`/`CANCEL` construction (on the shared-Rust iCalendar **writer**, which is the existing WASM-safe `fauna_core::ical::generate_ical` — reused, *not* net-new; see § iCalendar parsing rules), reply-merge, the attendee-roster sidecar, the `interested↔TENTATIVE` projection, and dispatch routing (email vs WS-RPC) all live in **shared Rust**, reusing the mail send path + mailbox poll + `parse_icalendar`. v1 invokes it **client-driven**; the server-side auto-schedule gateway **lifts the same module into the MDA** so it runs for any client (the bridge MTA is its iMIP gateway). Same code, two call sites — which is why the writer must stay WASM-safe (web shares it) yet be UniFFI-reachable by the Go MDA (a thin export over `generate_ical`, landed as `mailfauna.GenerateICal`).

### Interop matrix

CalDAV serves the Apple-and-open ecosystem; **email-based invites are the universal layer that reaches everyone** (Outlook and Google are *not* general CalDAV clients but are first-class iMIP implementations):

| Client ecosystem | Mount a Fauna calendar (CalDAV) | Exchange invites (iMIP email) |
|---|---|---|
| Apple (Calendar.app, iOS) | ✅ full read/write sync | ✅ |
| Thunderbird / Evolution / DAVx5 (Android) / Fastmail | ✅ CalDAV-native | ✅ |
| **Microsoft Outlook / Exchange** | ❌ no general CalDAV account support | ✅ excellent (Exchange's meeting model *is* iMIP) |
| **Gmail / Google Calendar** | ❌ no external read/write CalDAV (OAuth API is for Google's own calendars) | ✅ excellent (inline RSVP, adds to Google Calendar) |

(iMIP-with-Exchange has known rough edges — timezone rewriting, TNEF/`winmail.dat` on Rich-Text senders, `SEQUENCE` quirks — but it is the universal mechanism every system uses.)

### RSVP semantics: `interested` projects to `TENTATIVE` (asymmetric, by necessity)

Fauna's RSVP is **going / interested / decline** (+ standard tentative / needs-action inbound). `interested` has no standard `PARTSTAT` value and is a *subtype* of `TENTATIVE` (a social "soft yes"), so the projection is **lossy** and the mapping is asymmetric:

> A Fauna app renders an attendee as **"Interested"** *iff the sidecar explicitly marks that attendee interested*; otherwise it renders the VEVENT `PARTSTAT` verbatim (Going=`ACCEPTED` / **Tentative**=`TENTATIVE` / Declined=`DECLINED`).

- Fauna user picks **Interested** → sidecar=`interested`, VEVENT `PARTSTAT=TENTATIVE`. Apple/Outlook/Gmail show **Tentative**; Fauna shows **Interested**.
- A stock client picks **Tentative** → `PARTSTAT=TENTATIVE`, no sidecar marker → Fauna shows **Tentative** (not Interested).

(Optional belt-and-suspenders: also emit `X-FAUNA-PARTSTAT=INTERESTED` beside `PARTSTAT=TENTATIVE` so a Fauna app reading a raw `.ics` without the sidecar can recover it — best-effort, since a MUA may strip X-params on round-trip; the sidecar stays authoritative.)

## iCalendar parsing rules

**Writer vs parser — two homes, one contract.** Serialisation (struct → VEVENT `.ics`) is `fauna_core::ical::generate_ical` (`libs/fauna-core/src/ical.rs`) — hand-rolled and **WASM-safe** so web and the native apps share one writer. Parsing + recurrence expansion are the crate-backed `fauna_mail::icalendar::{parse_icalendar, expand_recurrence}` (the `icalendar`/`rrule` crates are *not* WASM-safe, so this surface is native/MDA-only). **The gate is on that crate-backed tree, never on reading `.ics` at all** — and the distinction is load-bearing, because reading the gate as “web cannot parse iCalendar” has twice sent a session looking for a web parser that already exists. Beside the writer there is a hand-rolled, WASM-safe **flat reader**, `fauna_core::ical::parse_ical` with `parse_ical_attendees` / `parse_ical_organizer`: it yields flat `EventFields` + a roster rather than a component tree, and it is the **web parse story**. `fauna_client_caldav::decode_event_entry_flat` reads the Events page through it on every target, and so does the whole inbound iTIP apply chain (`apply_inbound_scheduling_from_message` → `REQUEST` / `CANCEL` / `REPLY`), which needs a stored row's `uid_hash` and verbatim `.ics` and nothing more. That chain is therefore **shared, not native-only**, and the per-calendar search it drives goes through the flat decoder on both targets rather than building a crate-backed tree it would discard. Only a consumer that genuinely needs the tree or RRULE expansion — `query_events_decoded`, the MDA — is native/MDA-only. The two are independent implementations; `libs/fauna-mail/tests/ical_writer_parser_contract.rs` pins the contract that the writer's output round-trips through the MDA parser (incl. RRULE expansion + TEXT escaping). The writer is reused as-is; its UniFFI export — `fauna_mail::icalendar::generate_ical` (a thin wrapper calling the single-sourced `fauna_core::ical::generate_ical`, with mirror input records in the `fauna_mail` namespace to avoid the cross-namespace `fauna_core` Go-binding footgun) — is landed, so the Go MDA's auto-schedule gateway can build iMIP via `mailfauna.GenerateICal`, alongside the existing `mailfauna.ParseICalendar`/`ExpandRecurrence`.

Every PUT body parses via `mailfauna.ParseICalendar` (UniFFI to `libs/fauna-mail/src/icalendar.rs`). The MDA enforces:

- **Mandatory fields per VEVENT:** `UID`, `DTSTAMP`, `DTSTART`. Missing any → `400 Bad Request` with `<error><valid-calendar-object-resource/></error>`.
- **Single component family:** one `BEGIN:VCALENDAR` wrapper, one or more `VEVENT` / `VTODO` inside; mixed event-and-todo bodies are accepted; nested `VTIMEZONE` is accepted. `VJOURNAL` is rejected (out of scope per § Calendar collection model).
- **UID uniqueness per calendar:** the `uid_hash` is the dedup key on nest. Re-PUTting the same `UID` to the same calendar updates the row; re-PUTting to a *different* calendar collides on `uid_hash` only if blake3 matches — across calendars the row keying includes `calendar_id`, so the same `UID` in two different calendars is two distinct rows (this is a tolerated divergence from RFC 4791 §4.1, which suggests UIDs be globally unique per server-wide; MUAs treat per-calendar UID isolation as acceptable in practice).
- **Recurrence rules:** stored opaquely in the sealed body. Nest never sees the RRULE. The MDA expands ephemerally during AUTH'd sessions for `time-range` REPORT filtering only — never persisted.
- **VTIMEZONE:** validated for structural correctness on PUT; the MDA's `expand_recurrence` consumes VTIMEZONE for timezone-aware DTSTART expansion (per spec § Components § iCalendar — VTIMEZONE arithmetic in Rust core).

### Size cap

PUT bodies cap at 16 MiB (the `max-resource-size` property's declared value, enforced at the HTTP layer per the W1 (account-data-plane.md § Workstreams) mitigations in spec § Library inventory). Bodies above the cap → `413 Payload Too Large`. Calendar collections themselves have no aggregate size cap beyond the shared IMAP+CalDAV per-actor quota (§ QUOTA below).

## QUOTA — shared with IMAP

Per-actor quota covers ciphertext bytes across `bridge_imap_messages` + `bridge_caldav_events` + `bridge_carddav_cards` (one quota root per actor named `user/<handle>`, matching `imap-server.md` § QUOTA / GETQUOTAROOT § Quota root model). A user's storage budget is one number across mail + calendar + contacts; sending 1 GB of mail eats into the same budget as creating 1 GB of calendar attachments. Each event or card counts its live content record's block length, sized through its own kind's CARv2 index exactly as a mail placement is (never a SQL byte column); the `MESSAGE` resource stays the mail placement count — an event is not a mailbox message. The one usage figure is what `fauna.bridges.get_quota` reports and what every enforcement point — mail-side and the DAV writes below — checks, so a full calendar blocks an APPEND the same as a full mailbox, and a full mailbox blocks a new event. RFC 9208's CalDAV-side equivalent (`DAV:quota-available-bytes` / `DAV:quota-used-bytes` on the principal collection) reports the same shared budget.

### Enforcement points

- `PUT` on a new event — pre-check; over-quota returns `507 Insufficient Storage` with `<error><quota-not-exceeded/></error>` (the negative phrasing is RFC 4918 §15).
- `PUT` updating an existing event — pre-check on (new_ciphertext_size − old_ciphertext_size); a shrinking or same-size write is never checked at all, so it passes even for an account already over a lowered ceiling.
- The same two rules bind every other write that stores an event or a card: a card `PUT` (`carddav-server.md` § Quota), the destination leg of a `MOVE`/`COPY` (§ Write surface — `507`, the source untouched), and an app's own `put_event_ciphertext`/`put_card_ciphertext`. The nest refuses with the typed `fauna.bridges.over_quota` before the body reaches the segment store, so a refusal writes nothing; the MDA maps it to the `507` above and the apps render it as a storage-full refusal.
- An emailed invitation (§ Server-side auto-schedule, "Inbound invite") for an account with no room is **not placed**: the placement answers the `over_quota` outcome, which the MTA logs. It is never a failed delivery — the mail copy is already delivered, and the invitation stays in the inbox.
- `MKCOL` — no quota check (metadata bodies are bounded and tiny).
- `PROPPATCH` — no quota check (metadata mutation, bounded size).
- `DELETE` — reduces usage; never blocked.

## MDA ↔ nest WS-RPC contract

The RPCs split into two caller-class groups (per `../architecture/apps/bridges.md` § Per-role method allowlist):

- **MDA-only** (the AUTH/session plane — the bridge proves it AUTH'd a MUA): `fauna.bridges.fetch_wrapped_mls_blob`, `fauna.bridges.report_auth_event`, `fauna.bridges.report_session_close`.
- **`BridgeMda | User`** (the calendar storage/sync plane): `fauna.bridges.list_calendars`, `fauna.bridges.provision_calendar` (with `update_metadata` flag for PROPPATCH path), `fauna.bridges.put_event_ciphertext`, `fauna.bridges.delete_event`, `fauna.bridges.query_events`, `fauna.bridges.sync_calendar_since`. The MDA calls these on behalf of a served MUA; **per events.md Decision B (2026-06-01) a Fauna app calls the same RPCs directly against its OWN calendars** (sealing client-side, replacing the retired legacy plaintext `fauna.{calendars,events}.*` / `content`-table path). Every non-MDA caller is **caller-scoped**: nest rejects (`fauna.bridges.permission_denied`) any request whose `actor_id` ≠ the connection actor, so a user/admin reaches exactly its own data and nest still never sees plaintext (§ Threat model). `Admin ⊇ User`, also caller-scoped. Enforced in `bridge_caldav_handlers.rs::require_caller_scope`; allowlist in `bridge_method_allowlist.rs`.

Wire-level shapes are pinned by `libs/fauna-protocol/src/bridge_routing.rs` round-trip tests and `bins/fauna-nest/src/bridge_caldav_handlers.rs` integration tests; this doc names the contract by RPC, not the byte-level encoding. **When adding a new CalDAV RPC, the order is:** catalogue entry (the internal bridge↔nest WS-RPC API catalogue) → nest handler + round-trip test → MDA wrapper in `bins/fauna-bridges/internal/wsrpc/methods.go` → MDA-role allowlist entry → CalDAV wire wiring → goal-doc update here. Without the allowlist entry the bridge cannot reach the new method.

## Architectural rules

- **One MDA-role process per nest deployment in the target shape.** Same process serves IMAP + CalDAV; one TLS termination; one WS connection to nest.
- **All calendar / event state is nest-side.** The MDA holds no per-user persistent state on disk. SQLite writes happen only via RPC; `bridge_caldav_calendars` / `bridge_caldav_events` / `bridge_caldav_expunged` are the only CalDAV state surfaces.
- **Every PUT / DELETE / single-collection PROPPATCH is one SQLite transaction at the nest boundary.** MOVE / COPY are two RPCs (one transaction each) because nest doesn't yet expose an atomic cross-calendar move; the MDA's two-RPC pattern preserves source-on-destination-failure (per § Atomicity rule).
- **Every state-changing RPC appends a placement event to `__calendar-placement/<actor>/` atomically with the SQLite transaction.** Same shape as the IMAP-side rule in `imap-server.md` § Architectural rules. The placement journal exists so that disaster-recovery restore from a backup destination reconstitutes `bridge_caldav_*` tables with RFC 6578 sync-collection continuity (restore design ratified 2026-05-14; tracked internally).
- **Recurrence expansion is per-session, never persisted.** RRULE bytes live inside the sealed body; nest never sees them; the MDA expands ephemerally during AUTH'd sessions for time-range REPORT filtering only.
- **PROPPATCH on event resources is rejected.** Events are atomic re-PUTs; per-event property mutation is rarely-used and adds API surface for no product value.
- **One quota root per actor (`user/<handle>`) covers IMAP + CalDAV.** Per-mailbox or per-calendar sub-quotas are not implemented. Per-tier limits come from `tiers.storage_bytes`.
- **PROPPATCH on calendar metadata is one RPC.** `provision_calendar(update_metadata=true)` is the idempotent update path; reading the existing blob + mutating + re-sealing happens on the MDA so nest only sees ciphertext.
- **`getctag` reads from `bridge_caldav_calendars.highestmodseq`.** The same column `query_events` reads as `HighestModSeq`. The two surfaces agree by construction.
- **AEAD-success = AUTH-success.** Same flow as IMAP; the same wrapped MLS blob serves both protocols.
- **No caller reaches another actor's calendars.** For a direct Fauna app (the `BridgeMda | User` storage/sync RPCs, Decision B), nest enforces `request.actor_id == connection actor` for every non-MDA caller (`require_dav_caller_scope`, `bridge_routing_handlers.rs`) — a user/admin can read or write only its own calendars. **For the MDA** (`CallerClass::BridgeMda`), `require_dav_caller_scope` deliberately lets `target` name any actor — that's what lets one bridge process serve every user on the box — so on this path isolation rests entirely on the `WHERE actor_id = ?1` predicate in the four DB-layer scope queries (`query_caldav_events`, `query_caldav_changes_since`, and their CardDAV twins), since `calendar_id` on the wire is a fleet-wide constant for the lazy "Personal" calendar (§ above) and any two clients naming a collection the same slug collide too. Cross-actor isolation on this predicate is covered by `bridge_caldav.rs::query_caldav_events_is_isolated_per_actor_on_shared_collection_id` and its `query_caldav_changes_since` twin.
- **No anonymous CalDAV.** Service discovery (`/.well-known/caldav`) requires auth too.

## Don't do these

- Don't add server-side calendar state in the MDA process. SQLite writes flow through nest RPCs; the MDA is a stateless protocol terminator.
- Don't synthesize sync-collection responses past the tombstone retention window. The MUA falls back to full PROPFIND + per-event GET when its `sync-token` is stale — that's the correct CalDAV-side behavior per RFC 6578 §3.8.
- Don't allow PROPPATCH on event resources. Event property mutation is atomic re-PUT.
- Don't reintroduce the legacy bearer-token CalDAV flow that lived in `bins/fauna-bridge-imap/internal/caldav/` (retired; tracked internally). The I5 MDA path replaces it.
- Don't write CalDAV state to the MDA's local filesystem. The MDA's `--data-dir` is for logs + the keypair file only.
- Don't split a single-RPC write into multiple transactions. PUT / DELETE / single-collection PROPPATCH are one nest RPC each; the atomicity rule is at the nest transaction boundary.
- Don't share quota across users on the same nest. Per-actor quota roots are independent; one user filling their quota doesn't affect a sibling user.
- Don't allow Basic Auth over cleartext HTTP. The CalDAV path is HTTPS-only; the `Authorization` header is rejected pre-TLS.
- Don't conflate per-actor CalDAV quota with per-actor mail quota in any UI surface or error message. They're a *shared* quota root — the user sees one number on their account page covering both; surfacing "you're out of calendar storage" without mentioning "this is your shared mail + calendar quota" misleads.
- Don't add per-event ACLs. V1 is single-user per calendar; RFC 3744 ACL is not advertised, `GETACL` / `SETACL` are not implemented.
- Don't reject CalDAV PUTs containing future `DTSTART` dates. CalDAV calendars routinely hold events many years out; date-range validation belongs in the client UX, not the protocol terminator.

## Out of scope / follow-on tasks

- **~~RFC 6638 scheduling~~ — now IN scope (v1, encrypt-only).** Server-side auto-schedule (implicit scheduling: organizer fan-out, inbound seal-to-recipient, response) is part of v1 per § Scheduling & invitations, delivered over iMIP email through the bridge MTA (+ WS-RPC for mailbox-less Fauna users). The one deferred piece is **instant** reply-reflection for an Apple-only / no-Fauna-app user — v1 merges replies client-side (a Fauna-app sync applies them); the `roster-split` standing-capability design (§ Scheduling & invitations) is documented-but-deferred, enabled only if that narrow case matters.
- **`VFREEBUSY` REPORT.** Time-availability queries against a calendar. Out of scope for v1; clients fall back to full event lists.
- **Encrypted index on DTSTART buckets.** For calendars with > ~10k events, the MDA-local time-range filter becomes the bottleneck. A future encrypted-index pass would let the MDA fetch only the events in a DTSTART window without decrypting the full calendar.
- **`Apple-style "calendar-color" RGB-A.** The `calendar-color` property is a hex-RGB string in our model; CalDAV ACE (Apple Calendar Extension) extends to RGB-A with alpha. Out of scope; v1 calendar-color is opaque 6-digit hex.
- **Full calendar *sharing* (WebDAV ACLs, RFC 3744).** Giving another actor read/write to a *whole calendar* (vs. per-event invitations, which v1 covers via § Scheduling & invitations) is out of scope for v1. Direction when built: a shared calendar *is an MLS group* — its metadata + events seal to the group key (not a single actor), so members decrypt with the group key, reusing the same `FaunaMls` machinery as conversations. `provision_calendar` would take a group audience; membership management + revocation follow the MLS group lifecycle. A genuine workstream, not a v1 bolt-on.
- **Browsable, message-bearing Scheduling Inbox/Outbox collections.** The schedule Inbox/Outbox *are* advertised and exist as minimal, correctly-typed collections (§ Server-side auto-schedule — Advertisement contract; RFC 6638 §2.1/§2.2 MUST). What stays out of scope is exposing them as *browsable* collections that surface scheduling messages to MUAs: incoming invites land on the calendar directly and replies merge client-side, so the collections stay empty, and the Outbox needs no iTIP `POST` (organizer fan-out is implicit on PUT).
- **`Sieve-equivalent for calendar rules.** Filter rules on incoming events (auto-decline conflicting events, etc.). Out of scope.

- **GAP 2 — a client-written calendar event was invisible to a CalDAV MUA — FIXED 2026-06-05.** Root cause (NOT the actor-id divergence first hypothesised — actor-id, calendar-id `blake3("personal")`, and the body-seal crypto were all confirmed byte-consistent): the shared client iCalendar writer `fauna_core::ical::generate_ical` **omitted the RFC-5545-mandatory `DTSTAMP`** (the very property § iCalendar parsing rules lists as mandatory per VEVENT). go-ical's *decoder* accepts a DTSTAMP-less VEVENT, but its *encoder* — which the MDA runs to serialize each event into the CalDAV REPORT/GET `<calendar-data>` — requires exactly one `DTSTAMP`, so it errored **mid-stream**, after emersion had already committed the response status (a "superfluous WriteHeader"), truncating the multistatus so *every* event vanished from the MUA's view (not just the bad one — which is why it read as an "empty collection" with no per-event WARN). The sealed client-write path (`fauna.bridges.put_event_ciphertext`) bypasses the MDA's MUA-PUT DTSTAMP validation (§ iCalendar parsing rules → 400), so nothing caught the omission; a MUA PUT worked only because its raw `.ics` carries DTSTAMP. **Why it passed every prior test:** the cross-language **client-Rust-seal → Go-MDA-serve-to-MUA** path was untested — `conformance_caldav_client.rs` reads back via the Rust crate; `tests/api/test_caldav.py` was MUA-PUT→MUA-read; the live test's Case 1 was the first exercise of it.
