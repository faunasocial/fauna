**The container streams, and `ExportFormat` has one definition (2026-09-21) — the first half of the client leg.** Three shared-Rust pieces the drive loop needs, landed ahead of the loop itself. **(1) `libs/fauna-mail/src/export/stream.rs`** builds the container incrementally: a forward-only pseudo-`Seek` sink feeds the zip writer, whose drained bytes go into **one** long-lived zstd encoder, and the caller pulls fixed-size slices off the compressed tail — those slices are the uploadable chunks, which is exactly what § Container shape means by "a byte SLICE of the single stream". Peak memory is **one message**, not one export, which is what § Quota composition's 10 GiB ceiling demands (the sink drains only on `flush()`, driven by `set_flush_on_finish_file(true)`, because the zip writer patches each file's local header *after* writing its body — draining mid-body is the bug that once broke restore for every file over 64 KB in the nest's own `ChannelWriter`). `build_blob` is now a thin wrapper over this rather than a second implementation: a one-shot `zstd::encode_all` records the total input size in its frame header and a streaming encoder does not, so two implementations would have meant the determinism contract holding of each path separately while the two disagreed with each other. ## Goal

A user can pull their entire mail-area state out of Fauna in one of three standard MUA-portable formats, without leaving the Fauna app, without admin intervention, and without the admin — or the box owner — being able to read the bytes mid-transit. The export sits in a sealed blob on nest's disk just long enough for the user to download it, then it's GC'd; the blob is sealed under a per-session key only the user's clients can unwrap, because the whole-mailbox snapshot is the user's secret during the download window, never the box owner's (every nest stores user content sealed at rest — `architecture/encryption-at-rest.md`; the per-session seal is *additional*, see § Sealed-blob delivery).

**Bar: parity with Thunderbird's "ImportExportTools NG" and Apple Mail's "Export Mailbox" plus data-portability properties.** The export is mountable by any standards-compliant MUA after download + format-decompression. The user re-imports into Gmail / Apple Mail / Thunderbird without translation. The bytes-leaving-Fauna are deterministic for the same input (same source mailbox, same format, same scope → byte-identical output up to embedded timestamps), so the user can self-verify.

**Symmetric to mailbox-migration.** Every shape mailbox-migration.md defines on import (the wizard layout, the session row model, the state machine, the push-event names, the 30-day GC, the resume-on-restart pattern) is reused on export. A user who has done one understands the other.

## UX shape

The export wizard is the `mail-export` page — a sub-page of `mail-settings` reached via the Mail sub-nav, exactly like `mail-aliases` / `mail-lists` and symmetric with the (future) `mail-import` wizard. There is no separate entry-button element (the sub-nav is the entry, per the mail-UX design pass — the same shape aliases/lists use). The wizard's five steps share one element set on the page, shown conditionally by step (same pattern as `mail-add-credential`); the durable-commit CTA is `mail-export-start-button`. Element IDs use the `mail-export-*` prefix (folded from the draft's `account-detail-mail-export-button` + `mailbox-export-wizard-*`).

### Wizard steps

1. **Format picker** — radio choice of:
   - **`mbox`** (RFC 4155) — one text file per mailbox, messages concatenated with `From ` lines (the venerable Unix-mailbox format). One large file per mailbox where the other two give one file per message — a property of the files inside, not of the download: all three formats ride the same container (§ Container shape) and their archives come out about the same size. Broadest MUA support (Thunderbird, Apple Mail, Mutt, Pine, every Unix tool). Default selection.
   - **`Maildir++`** — one file per message in a `cur/` / `new/` / `tmp/` tree per mailbox; IMAP flags encoded in the filename suffix per the Courier-Maildir extension (https://www.courier-mta.org/maildir.html — no IETF RFC, but Dovecot-canonical). Dovecot / Cyrus / Courier import path; preserves IMAP-flag state explicitly.
   - **`EML zip`** — one `.eml` file per message in a flat zip, with a manifest `mailboxes.json` recording each message's source mailbox + flags + IMAP UID + INTERNALDATE. Lowest-common-denominator: every MUA imports an `.eml`. Best for archive purposes.

2. **Scope picker** — defaults:
   - Mailboxes: **all** (user can deselect — `Trash` / `Junk` pre-deselected; `INBOX` / `Sent` / `Archive` / `Drafts` pre-selected; custom mailboxes pre-selected).
   - Date range: **all messages** (user can set "since" / "until" dates). **The rule (ratified 2026-09-21):** each field is a bare date written `YYYY-MM-DD`, and a bare date names a **whole UTC day** — there is no time zone, no time of day and no locale, because the field is a coarse filter over the mailbox's own timestamps, not a moment. **Both ends are inclusive of their whole day:** "since" admits from that day's first second and "until" through that day's last, so `2023-11-14` … `2023-11-14` is exactly that one day. The instant compared is the message's **INTERNALDATE** — the mailbox's own record of when the message arrived, the same value the archive's entry times and the mbox `From ` line carry — never the `Date:` header, which the sender wrote and can say anything. Either field may be empty (unbounded on that side). **A date that is not this shape, is not a real calendar day, or a "since" after the "until" refuses `Start` before any session exists** — never "no range": quietly exporting the whole mailbox in place of a range nobody could read is the same under-delivering control the header-strip list below exists to prevent. **A message outside the range is outside the export's scope**: it is not serialized, not opened (so one this device could not open is no reason to fail an export that never asked for it — § An unopenable record fails the session governs the messages the export *wants*), and **not counted in `skipped_count`**, which is for messages the export wanted and could not take. The range is part of the scope for § Goal's byte-identical bar — same source, same format, same mailboxes, same range → same archive — and needs nothing new to hold: mailbox-level entries take the earliest INTERNALDATE of the messages actually **exported** (the serializers' running minimum sees only those), and a mailbox the range leaves empty contributes no entry, exactly as an empty mailbox does.
   - Header-strip toggle: **off** (preserve all headers, transit trail included). Advanced users may opt to strip the transit headers for privacy when sharing the export externally; the UI surfaces a tooltip explaining the tradeoff (strip = no transit-path metadata leaks; preserve = full forensic fidelity). **What "strip" removes (ratified 2026-09-20): every header a relaying or receiving host stamps onto the message to record the path it took or the hosts and IP addresses that handled it — and nothing the originator wrote.** The set is a closed list of exact field names, matched whole-name and case-insensitively, folded continuation lines included, in the header section only (a body line that merely looks like one is untouched), identically in all three formats. **Strip set:** `Received`, `X-Received`, `Received-SPF`, `Authentication-Results`, `ARC-Seal`, `ARC-Message-Signature`, `ARC-Authentication-Results`, `X-Originating-IP`, `X-Originating-Client-IP`, `X-Sender-IP`, `X-Forwarded-For`, `X-Real-IP`, `X-Client-IP`, `X-Forefront-Antispam-Report`, `X-Forefront-Antispam-Report-Untrusted`, `X-ClientProxiedBy`, `X-MS-Exchange-Organization-OriginalClientIPAddress`, `X-MS-Exchange-Organization-OriginalServerIPAddress`, `X-MS-Exchange-Organization-ConnectingIP`, `X-MS-Exchange-Organization-AuthSource`, `X-MS-Exchange-CrossTenant-AuthSource`, `X-MS-Exchange-Transport-CrossTenantHeadersStamped`, `X-SES-Outgoing`, `X-Mailgun-Sending-Ip`, `X-Ovh-Remote`, `X-Barracuda-Connect`, `X-Barracuda-Apparent-Source-IP`, `X-Scanned-By`, `X-Greylist`, `X-Virus-Scanned`, `X-Spam-Checker-Version`, `X-AntiAbuse`, `X-Authenticated-Sender`, `X-Get-Message-Sender-Via`. **Why each family is in (widened 2026-09-23 — the 2026-09-20 list stopped at four generic `X-*-IP` names and omitted the provider families that meet the definition word for word):** the first eleven are the trace, authentication-result and generic client-IP headers of the original list; `X-Real-IP` / `X-Client-IP` are the proxy and webmail client-IP stamps; the `X-Forefront-*` / `X-ClientProxiedBy` / `X-MS-Exchange-*` family is Exchange and Exchange Online's record of the connecting IP (`CIP:` and `H:` inside the Forefront report), the original client and server IPs, and the hostnames that authenticated, proxied or stamped the message; `X-SES-Outgoing` / `X-Mailgun-Sending-Ip` / `X-Ovh-Remote` are a sending or receiving service's own record of the IP it sent from or accepted from; the Barracuda pair, `X-Scanned-By`, `X-Greylist`, `X-Virus-Scanned` and `X-Spam-Checker-Version` name, by design, the appliance or scanner host (often by IP) that handled the message; and the cPanel/Exim trio (`X-AntiAbuse`, `X-Authenticated-Sender`, `X-Get-Message-Sender-Via`) records the originating host and the identity that authenticated to it. **Deliberately out of scope, and why (ruled 2026-09-23):** verdict stamps that carry no host by design (`X-Spam-Status`, `X-Spam-Score`, `X-Spam-Level`, `X-Spam-Flag`, `X-Spam-Report`, `X-Proofpoint-*`, `X-Mimecast-*`, `X-Microsoft-Antispam`) — the definition is about the path, not the filtering outcome, and a hostname that merely appears inside a free-text report is not a record of it; opaque provider message tokens (`X-Google-Smtp-Source`, `X-Gm-Message-State`, `X-SG-EID`, `X-Mailgun-Sid`, `X-MS-Exchange-Organization-Network-Message-Id`) — they identify the message to its provider, not a host; envelope records (`Delivered-To`, `X-Original-To`, `X-Envelope-To`, `X-Envelope-From`) — addresses, not hosts, by the same reasoning as `Return-Path` below; cPanel's `X-Source` / `X-Source-Args` / `X-Source-Dir` — the sending script's path, not a host; and Fauna's own `X-Fauna-*` delivery stamps — the filing nest's policy record (alias match, spam threshold), never a host or IP, which every nest door strips from bytes it did not write itself before filing them (`smtp-server.md` § Architectural rules → *The `X-Fauna-*` namespace*), so an archive re-imported anywhere carries nothing a nest would trust. A header outside both lists is added to one of them *here* first. **This list is the authority and the Rust constant mirrors it** (`libs/fauna-mail/src/export/mod.rs::TRANSIT_STRIP_HEADERS`, pinned equal to this line by a test that reads this file) — a newly-seen transit header is added *here*, and the promise above is only as wide as this list: the toggle had shipped removing `Received` alone while this bullet already promised "no transit-path metadata leaks", leaving `Received-SPF`, `Authentication-Results` and the `X-*-IP` family — literal sender and client IPs, the receiving nest's hostname — in archives the user believed scrubbed. **Kept deliberately, strip on or off:** `DKIM-Signature` — originator-written content authentication, not a transit record; removing it would cost the recipient of a shared archive the one check that the messages are unaltered, and the kept signature still verifies, because RFC 6376 §5.4.1 tells signers not to cover headers that are added or rewritten in transit — which is this whole set. `Return-Path` — it names the envelope sender (an address the `From` header almost always already shows), not the path, and the mbox `From ` separator line is derived from it (§ Format choices → `mbox`); stripping it would silently rewrite every separator. Should it ever join the list, the separator must be derived *before* the strip runs. The strip changes the serialized bytes, so the § Goal byte-identical bar holds per toggle position: same input + same toggle → same archive. A stored message's header lines may end in bare LF (a migration keeps its source's bytes unmodified), so the strip frames lines as the mail parser does — a line ends at LF with or without CR, the section ends at the first empty line — and a message the strip would leave with no bytes at all is refused (the export fails closed), never written as an empty entry in an archive reported complete.
   - *(A fourth scope row — "include encrypted-mode metadata," display-conditional on a storage-mode probe — was retired 2026-07-23 with the storage-mode axis; see `## Implementation status today` for the cleanup ledger. Flags/UIDs/mailbox metadata are always preserved by the format serializers themselves — the EML manifest, mbox `X-Status`, Maildir++ filename flags — so there is no residual "metadata yes/no" choice to offer.)*

3. **Confirmation** — total messages + estimated bytes + estimated wall-clock time summarized; the user clicks "Start export." This is the durable commit point — nest opens an `export_sessions` row at this step.

4. **Progress** — full-screen progress UI mirroring the import progress shape:
   - Overall: `X of Y messages exported / Z skipped / W errored`, progress bar, elapsed + ETA.
   - Per-mailbox: list with per-mailbox progress.
   - Per-message error log: scrollable list (oversize-skip, parse fail on read, etc.) with reasons.
   - Buttons: **Pause**, **Resume**, **Cancel**. Pause persists; Resume continues the stream in the app that paused it and restarts it from the first message anywhere else (§ Resume). Cancel asks for confirmation; on confirm the export is aborted and the partial blob is unlinked.
   - The screen survives app restart — same pattern as the import progress per `mailbox-migration.md` § Resume protocol. The user closes the laptop, opens it later, returns to the same Fauna app surface and sees the progress UI resumed (the client re-subscribes to the export session's push events).

5. **Done** — summary card (X exported, time elapsed, blob size); buttons for **"Download export"** (triggers the sealed-blob download via the user's authenticated session) and **"Discard now"** (immediate blob unlink before the 30-day GC). The download URL is shown as a copyable secret link in case the user wants to download from a different device — the URL is bound to the user's actor (the recipient client AUTHs the same way the originating client did; not a public link).

## Format choices

The three format choices land as three serializers in `libs/fauna-mail/src/export/`:

### `mbox` (default)

Per RFC 4155 plus the de facto `mboxo` / `mboxrd` extensions:

- One file per source mailbox: `INBOX.mbox`, `Sent.mbox`, `Custom-Project-A.mbox`, ... (the name → path rule is § Mailbox names in archive paths).
- Messages concatenated, each preceded by a `From <envelope-sender> <ctime>\n` line (RFC 4155 separator).
- Lines beginning `From ` inside message bodies are `>From `-escaped (mboxo/mboxrd canon).
- IMAP-flag preservation in non-X-mboxrd headers (`X-Status: O` for seen+old, `X-Mozilla-Status` for cross-MUA compat — Thunderbird's de facto convention).
- INTERNALDATE preserved in the leading `From ` line's ctime.
- Inside the export zip, the mbox files share one root directory `<actor>-mbox/`.

### `Maildir++`

Per the Courier extension (https://www.courier-mta.org/maildir.html — no RFC; the canonical Maildir++ spec; widely supported by Dovecot, Cyrus, Courier, MailMate, and most modern IMAP servers):

- One directory tree per source mailbox: `INBOX/cur/`, `INBOX/new/`, `INBOX/tmp/`. **Every exported message is written to `cur/` with its `:2,` flag suffix; `new/` and `tmp/` are created empty** (pinned 2026-09-20). A message in `new/` carries no `:2,` suffix by construction, so routing unseen mail there would silently drop every flag it holds — losing `\Flagged` on an unread message is a data loss the format need not take, and `cur/`-for-everything is what `doveadm` and ImportExportTools NG already emit.
- One file per message, named `<unix-time>.<unique>.<host>:2,<flags>` (Maildir++ filename convention; `<flags>` are the colon-2 form encoding IMAP `\Seen` → `S`, `\Answered` → `R`, `\Flagged` → `F`, `\Deleted` → `T`, `\Draft` → `D`). **The three components are pinned deterministic (2026-09-20), because the live Maildir convention mints them from pid + wall-clock + hostname and the byte-identical bar (§ Goal) forbids all three:** `<unix-time>` is the message's INTERNALDATE in epoch seconds; `<unique>` is the first 16 lowercase hex characters of BLAKE3 over the message's raw RFC 5322 bytes, suffixed `-<n>` (n from 2) only to break a genuine within-mailbox collision in first-emission order; `<host>` is the fixed literal `fauna.invalid` — a constant, never the nest's hostname, which would both leak the deployment into the user's archive and make the output machine-dependent (RFC 2606 reserves `.invalid` for exactly this "not a resolvable name" use). **`<flags>` are concatenated with no separator and sorted ASCII-ascending** (`DFRST` order — the Courier colon-2 form; the `,` in `:2,` is the marker's own separator, not a flag separator).
- INTERNALDATE preserved in the file's mtime + the unix-time component of the filename.
- Subscribed-mailbox state preserved in a `subscriptions` file at the export root, one mailbox directory per line (§ Mailbox names in archive paths owns the directory names).
- Inside the export zip, the maildir tree shares one root directory `<actor>-maildir/`.

### `EML zip`

The lowest-common-denominator:

- One `<message-id-or-uuid>.eml` per message in a flat directory `<actor>-eml/`.
- Each `.eml` is the raw RFC 5322 message bytes (the same byte sequence that would land in a fresh APPEND to a fresh mailbox).
- A manifest `<actor>-eml/manifest.json` lists per-message: `source_mailbox`, `imap_uid`, `imap_uidvalidity`, `imap_flags` (list), `internal_date` (RFC 3339), `message_id` (header), `filename` (in the zip).
- The manifest is the only place where per-message metadata lives — `.eml` files are pristine. Tools that ignore the manifest just see one `.eml` per message; tools that read it (a future Fauna re-import) get flag/mailbox-restoration fidelity.

### Mailbox names in archive paths — one injective encoding (pinned 2026-09-21)

**A mailbox name becomes an archive path through one injective encoding, shared by the mbox file (`<name>.mbox`), the Maildir++ directory (`<name>/cur/`) and the Maildir++ `subscriptions` index — two distinct mailboxes never share a path.** The rule it replaced was a many-to-one fold (separators to `.`, reserved characters to `_`, control bytes dropped, trailing dots and spaces stripped) that nothing downstream reconciled, so `Reports` beside `Reports ` — or `A:B` beside `A_B`, `A.B` beside `A/B`, `Reports` beside `Reports` plus a control byte — put two entries on one path, the container refused the duplicate, and the whole export failed on every retry, mid-stream, naming neither mailbox. **The encoding, per character:** the IMAP hierarchy delimiter `/` folds to `.` — the Maildir++ nesting convention, kept deliberately (`Work/Reports` → `Work.Reports.mbox`, `Work.Reports/cur/`) — except as the name's first or last character or right after another `/`, where it is `%2F`; the escape character `%`, a literal `.` (which would otherwise read as a folded `/`), `\`, the reserved `:` `*` `?` `"` `<` `>` `|`, and every ASCII control byte become `%XX`, the byte in uppercase hex; every non-ASCII character whose compatibility decomposition (NFKD) holds `/` or one of those characters — the fullwidth twins (`／` `％` `．` `＼` `：` `＊` `？` `＂` `＜` `＞` `｜`), the small forms (`﹒` `﹨` `﹕` `﹪` …), the dot leaders (`․` `‥` `…`) — becomes `%XX` per UTF-8 byte, as do the separator look-alikes no decomposition names (`¥` `₩` `∕` `⁄` `∖` `⧵`); a space as the last character becomes `%20`; everything else, non-ASCII included, is kept verbatim; the empty name is a lone `%`. **Why escape the colliding characters rather than suffix a collision (`-2`):** a suffix depends on which mailbox arrived first and silently renames one of the user's folders in their own archive, while an escape round-trips — `.` decodes to `/`, `%XX` to its byte, so every name is recovered exactly, which is what makes the map injective — and leaves every ordinary name, and every valid handle in the `<actor>-<format>/` root, untouched. The same rules make every component safe with no separate step: never empty, never `.` or `..`, no separator, and no trailing dot or space for Windows to drop on extraction. **Why the fullwidth twins, on every rung:** an extractor that narrows a UTF-16 path to a Windows ANSI code page with best-fit mapping turns U+FF01–U+FF5E into the ASCII it looks like, so a kept `／` or `．` would make one safe component several on the user's disk (`a／．．／b` extracting as `a/../b`, outside its directory), a kept `：` would name a stream, and a kept `％` would forge an escape. Escaping them makes "no separator" true for every extractor without measuring which ones narrow; the rest of the fullwidth block (letters, digits, brackets) narrows only to characters that are safe where they land, so a CJK name keeps them verbatim — it pays nine bytes only for a fullwidth `／` it uses as a date separator. **Why the separator look-alikes outside the block, too:** best-fit narrowing does not stop at the fullwidth block — `¥` is byte 0x5C, `\`, in code page 932 (Japanese), `₩` is in 949 (Korean), and the slash and backslash operators `∕` `⁄` `∖` `⧵` look like the separator they may become — so kept, `a¥b` would extract under a Japanese locale as two nested directories `a\b`. Inside the root, but no longer the archive's shape; the same bet as the fullwidth twins (escape on sight, without measuring which code page narrows which) makes "no separator" hold for them as well, at the accepted cost that a Japanese or Korean name spelling a currency sign pays six bytes for it. **Why the whole compatibility class, not a list of its instances:** a list closes only the look-alikes someone thought of — the fullwidth `．` was escaped while the small-form `﹒` beside the escaped `﹨` was not, so a mailbox named `﹒﹒` narrowed to `..`, one level above the archive root. Best-fit tables narrow a character to what its compatibility decomposition spells, so escaping every non-ASCII character whose decomposition holds `/` or an always-escaped character closes the class, and only a mapping no decomposition names (the currency signs and operators above) needs listing; the accepted cost is that a rare name spelling `…` or `⒈` pays its bytes too. **Why a doubled `/` escapes its second:** a `.` in the encoding is only ever one folded interior `/`, and no character kept verbatim decomposes to a `.`, so no component holds `..` — as encoded, nor once an extractor narrows it by compatibility decomposition or the listed best-fit mappings — a guard of the encoder's own, where it used to rest on the nest refusing `//` in a mailbox name (`a//b` was `a..b`, and `x¥//¥y` would have narrowed to `x\..\y`). **Not claimed:** that the listed look-alikes are every character some code page narrows, outside its compatibility decomposition, to `/`, `\` or `.` — an unlisted separator look-alike could still re-nest a name inside the root, and an unlisted dot look-alike is the one way a `..` could still form, so the no-`..` guarantee holds for every narrowing a decomposition or the list names, not for a code page's private mapping; and that two names stay two files under best-fit narrowing — `Ｗork` and `Work` narrow to one path, as any lossy extractor merges names; the rule keeps every component below its own directory and free of streams, not distinct under every lossy mapping. **Maildir++ only:** a mailbox that would encode as `subscriptions` (in any case) has its first character escaped (`%73ubscriptions`), because the index file of that name sits beside the mailbox directories — no longer a rule of its own but the second rung of § Archive paths on the extracting filesystem's ladder, with the index's name held as taken; it stays injective because decoding is context-free on every rung, whichever characters a rung escapes. **The `subscriptions` index lists the mailbox directories exactly as the archive names them, one per line** — never the raw mailbox names, which disagreed with the tree beside them. The EML zip layout never carries a mailbox in a path (one flat directory; `manifest.json`'s `source_mailbox` records the raw name), so it needs no rule here. **This rule settles what happens inside the archive only** — what the extracting filesystem does to two distinct paths is the next section's.

### Archive paths on the extracting filesystem — the escape ladder (pinned 2026-09-21)

**Two paths that are distinct inside the zip must still be two files after the user extracts it — on any filesystem, since the user, not Fauna, chooses where.** The container accepts `Work.mbox` beside `work.mbox`; default APFS, HFS+, NTFS and FAT then write the second over the first, and a whole mailbox is gone from an export the wizard reported complete. Four classes, one mechanism. **The mechanism is per-run, not per-name:** the serializer remembers the *extraction key* of every mailbox component it has handed out — the component canonically decomposed, uppercased then lowercased, decomposed again; deliberately coarser than any one filesystem, because too coarse costs a rare name one avoidable escape and too fine loses a mailbox (canonical equivalence only: no filesystem this archive is extracted onto folds a fullwidth `％` to `%` — a best-fit *extractor* does, which is why the encoding escapes `％` itself — and a key that did would let a name forge an escape) — and walks each mailbox up an **escape ladder** until its key is free: (1) the plain encoding of § Mailbox names in archive paths; (2) the same with its first verbatim character escaped too (`work` → `%77ork` — still readable); (3) every character escaped except ASCII digits, the interior `/` still folding to `.`. A non-ASCII character escapes as `%XX` per UTF-8 byte. **Which mailbox of a colliding pair keeps its plain name is decided by § Container shape's total order, never by timing** — the first in raw-byte order, so `Work` stays and `work` becomes `%77ork` — and the byte-identical bar holds unchanged: same source, scope and format → same bytes.

**Why a ladder rather than a context-free rule, and what it costs.** Of `Work` and `work` at most one can be its own path in *every* archive, so a rule that decides without seeing the other mailbox must mangle one of them always — and the only such rules (escape every uppercase letter; append a case mask) rewrite `INBOX`, `Sent` and `Archive` in every user's archive, and in the folder list of every MUA it is imported into, to defend against a pair almost no user has. The ladder leaves every archive without a collision exactly as it was. **The cost, accepted:** a mailbox's path depends on what it was exported beside — `work` alone is `work.mbox`, beside `Work` it is `%77ork.mbox`. **What it does not cost is the round-trip:** the rungs only ever escape *more* characters and decoding never looks at context (`.` is `/`, `%XX` is that byte), so every mailbox name is still recovered exactly from its path — which is the whole of the case against a `-2` suffix, and it still stands.

**Windows device names.** A component Windows would open as a device — `CON`, `PRN`, `AUX`, `NUL`, `COM0`–`COM9`, `LPT0`–`LPT9` (the superscript digits `¹²³` included), `CONIN$`, `CONOUT$`, in any case — is never acceptable on any rung, so it climbs to the second whatever else is exported (`Aux` → `%41ux.mbox`, `%41ux/cur/`). The test reads **the part of the component before its first `.`**, trailing spaces ignored, because Windows reserves these names with any extension: that covers the `.mbox` the serializer appends, the Maildir++ directory that has no extension at all, and the `/` fold, which turns `Aux/Reports` into `Aux.Reports`. Unlike a case collision this is a property of the name alone, so such a mailbox has the same path in every archive.

**Component length.** A mailbox component is at most **240 UTF-8 bytes** — most filesystems cap a component at 255 bytes (NTFS at 255 UTF-16 units, never more), and the margin is for `.mbox` and for the sidecar suffixes MUAs write beside an imported file. The nest caps a mailbox name at 255 bytes, a hierarchy folds into *one* component, and escapes triple a byte, so the cap is reachable. A longer component, on whichever rung, is cut to the longest prefix that splits neither a character nor an escape, then `%~` and the first 32 hex characters of BLAKE3 over the **raw** name — the digest keeps two names with a long common prefix apart, and it is 128 bits rather than the 64 of a message's `<unique>` because the names can be chosen by an adversary (a migration auto-creates the source server's mailbox names, and 64 bits yield a chosen colliding pair at a birthday cost of about 2^32 hashes), and `%` followed by a non-hex character occurs nowhere else in the encoding, so a cut name is never mistaken for a whole one. **This is the one step that does not decode:** a mailbox with a name that long keeps every message and loses the tail of its own spelling in mbox and Maildir++ (the EML manifest still records it raw). Total *path* length (Windows `MAX_PATH`) is deliberately not budgeted: it depends on the directory the user extracts into, which no rule here can know.

**EML zip filenames follow the same key, not the same ladder.** The flat directory never carries a mailbox, but its `<message-id>.eml` stems are case-sensitive ASCII and the run-wide filename set compared them exactly — `<ABC@x>` beside `<abc@x>` was two zip entries, one extracted file, and two manifest rows pointing at it. The set now holds extraction keys, so the second message takes the existing `-<n>` suffix (`abc@x-2.eml`); and a stem that is a device name (`<CON>`, `<aux.17@host>`) declines to the message digest, as an unusable `Message-ID` always has. No ladder, because this stem was never decodable — the manifest's `message_id` is the record, the filename only a convenience. Stem length was already capped (96 characters).

**What the ladder also repairs in Maildir++.** Message filenames restart their `<unique>` set per directory, so a byte-identical message filed in both `Work` and `work` has the *same* filename in each; two directories merged by the filesystem would keep one copy. Keeping the directories apart is what keeps both. Within one directory no two filenames differ only by case (`<unique>` is lowercase hex, the flag letters a fixed uppercase alphabet). **Not addressed, by the format's own definition:** the `:` of the `:2,` flag marker cannot exist in a Windows filename, so a Maildir++ tree extracts faithfully only onto a filesystem that allows it — the spec requires that character, and an archive rewritten to avoid it would no longer be the Maildir++ a standards-compliant MUA mounts (§ Goal). mbox and EML zip are the formats for a Windows extraction.

**The unreachable refusal.** If no rung yields a free key the export fails naming the mailbox, rather than letting one mailbox be extracted over another. The last rung keeps nothing verbatim that a fold could change, so this takes a 128-bit digest collision between two over-long names — about 2^64 hashes even for a source server that chooses its mailbox names on purpose. Were it ever reached it fails closed: the export refuses and nothing is written over anything.

### Compression wrapper

All three formats are wrapped as a `.zst` (zstd) blob at level 9 (the default for this kind of cold-storage compression — fast decompress, reasonable compress). The wrapper is applied uniformly: `<format>.zst` is the on-disk shape; the client decompresses post-download. (We do **not** use `.gz` despite its broader tool support — zstd compresses mail bodies about 30% smaller at comparable wall-clock, and every modern MUA either has built-in zstd decode or the user runs `zstd -d` once.)

The blob's filename inside the user's download is `fauna-export-<actor-handle>-<format>-<iso-date>.zip.zst` — self-documenting, sortable, doesn't leak the session-id.

### Container shape — zip inside zstd (pinned 2026-09-20)

All three formats are **multi-file trees**, so a container sits between the serializer and the zstd wrapper; this section had named it "the export zip" twice while § Compression wrapper named only `.zst`, and the ambiguity is resolved here rather than in each implementing track. **The container is a zip whose entries are all `Stored` (uncompressed), and one zstd stream at level 9 wraps the finished zip.** So `<format>.zst` and "inside the export zip" are both literally true, and the file resting on nest disk is `<session-id>.zip.zst.sealed` — the `.sealed` suffix is not optional, because what rests there is the framed ciphertext of § Blob shape on disk, and only the user's own client ever holds a plain `.zip.zst`. Three reasons this beats the alternatives: the user's *other* data export already hands back a zip (`GET /api/v1/export`), so priority #3 keeps one archive concept across both egress paths; a single solid zstd window over the whole archive compresses a mail corpus far better than zip's per-entry deflate, which is the ratio § Compression wrapper is buying; and after one `zstd -d` the user holds a plain `.zip` that Windows Explorer and Finder open natively, which a `.tar.zst` does not. Per-entry deflate is therefore **not** used — it would compress every message twice for a worse ratio.

**Determinism contract (the § Goal byte-identical bar).** The archive is byte-identical for the same input because: entries are emitted in one total order (mailbox name ascending by raw bytes, then, within a mailbox, IMAP UID ascending); every entry's stored modification time is the message's own INTERNALDATE (the mailbox-level entries take the mailbox's earliest), never the wall clock; no entry carries a host, uid/gid, or external-attributes field derived from the running machine; and the zstd level is the fixed constant above. Nothing in the container reads the clock, the hostname, or a random source.

**Consequence for the chunk-relay pipeline (§ Export pipeline).** Because the artifact is one zip inside one zstd stream, a chunk is a **byte slice of that single stream**, not an independently-compressed unit: the client holds one streaming zip writer feeding one streaming zstd encoder, and `upload_export_chunk` carries the next slice of encoder output, sealed. The nest still only appends opaque bytes in `chunk_idx` order, exactly as § Export pipeline describes — what is pinned here is that it may never reorder, re-compress, or independently decode a chunk.

**ZIP64 is emitted without being asked (measured 2026-09-21).** A classic zip counts entries in 16 bits and addresses offsets in 32, and an export under § Quota composition's 10 GiB ceiling, one entry per message, can pass either limit. Nothing in the container selects ZIP64 for the archive (only a per-entry large-file flag for a single entry over 4 GiB), so whether the `zip` dependency promotes on its own was settled by measurement on the forward-only streaming writer the drive loop uploads from — never by reading the dependency's source: an archive of 66 535 entries and one of 4.125 GiB (the last entries past the 4 GiB offset) both carry the ZIP64 end records and read back entry-for-entry, CRC-checked, and the first also opens cleanly in Info-ZIP `unzip`/`zipinfo` and Python's `zipfile`. Pinned in `libs/fauna-mail/src/export/tests.rs` (the entry-count case runs every time; the 4 GiB case is an ignored test, about forty seconds, run deliberately). A `zip` version bump that stops promoting would red the first.

**INTERNALDATE left the total order on 2026-09-21 (with the client drive loop), and the determinism bar is unchanged.** The order had read *mailbox, then INTERNALDATE, then UID*. It is not streamable: the down-leg's only cursor is `fetch_export_chunk_ciphertext`'s `after_uid` (§ Export pipeline), and an **imported** message carries its source's original INTERNALDATE on a freshly-minted, higher UID — so a UID walk of any mailbox a user has ever imported into feeds the serializer a descending date, and the serializer refuses the run rather than silently reordering. Honouring the old order would have meant buffering a whole mailbox's *bodies* to sort them, which § Quota composition's 10 GiB ceiling forbids outright, or a composite `(date, uid)` cursor the message store has no index for. UID is already unique, stable and total within a mailbox, so "same source, same scope, same format → byte-identical archive" holds exactly as before; what changes is only *which* faithful order the archive is in, and UID order is the order the mailbox actually rests in. The mailbox-level entries still take the mailbox's **earliest** INTERNALDATE, which is now a running minimum rather than the first message's date (under the old order those were the same value).

### Compile-time decisions (NOT configurable)

- The three format choices themselves — adding a fourth (e.g., PST, Outlook OST) would mean adding a serializer; not a knob.
- The Maildir++ flag-encoding character set — interoperability floor.
- The zstd compression level — a balance, not a tunable.
- The manifest schema for the EML format — adding fields requires a code change so consumers know what to expect.
- The container (zip, `Stored` entries) and the entry ordering + timestamp rules of § Container shape — they are what makes the output byte-identical, not a preference.
- The Maildir++ `<unique>` derivation and the `fauna.invalid` `<host>` literal — same reason: a knob here would reintroduce machine-dependent output.
- The chunk size and the maximum frame length derived from it (§ Blob shape on disk) — a wire/at-rest format bound and a memory-safety floor, not a preference; the two move together or an opener rejects a conforming writer's own chunk.
- The header-strip toggle's strip set (§ UX shape step 2) — the user chooses *whether* to strip, never *which* headers: a per-header picker would hand the user a privacy control whose correct setting they cannot know, and a partial strip is exactly the under-delivering control the closed list exists to prevent. Growing the list is a doc + code change.

## Session row model

Per `mailbox-migration.md` § Progress lives nest-side, with the same column shape and state machine, only renamed `import_sessions` → `export_sessions`:

| Column | Notes |
|---|---|
| `session_id` | uuid; primary key |
| `actor_id` | the exporter (the user's own actor) |
| `format` | `mbox` / `maildir` / `eml-zip` |
| `scope_descriptor` | DAG-CBOR blob recording mailbox selection, date range, header-strip flag |
| `state` | `running` / `paused` / `errored` / `completed` / `cancelled` |
| `started_at` | wall-clock start |
| `last_progress_at` | wall-clock of the most recent message-exported event |
| `total_count` | estimated; revised as the client enumerates the actor's mailboxes. The start estimate is the listing's whole-mailbox sum, which a date range (§ UX shape step 2) overstates — so under a range the client tightens it as each mailbox finishes (exported so far + the unwalked mailboxes' counts) and sets it to the exact exported figure with the last frames, and at completion nothing overstates. `list_own_mailboxes` is deliberately **not** given a ranged count: it is the general caller's-own-mailboxes kind (§ Wire shapes), and the nest learns a message's INTERNALDATE only by reading its record |
| `exported_count` | committed to the export blob |
| `skipped_count` | per-message skip (parse-fail on read, oversize) |
| `errored_count` | per-message error |
| `last_processed_message_id` | resume cursor (the per-mailbox cursor is a sub-field — same as `last_processed_source_uid_per_mailbox` on the import side) |
| `blob_path` | nest-relative path to the on-disk blob of the **current stream generation** — `exports/<session-id>.zip.zst.sealed` for generation 0, verbatim (§ Blob shape on disk pins the name per generation; § Reclaim is what turns this string into an unlink) |
| `stream_generation` | 0 at start; + 1 per `restart_export_session` (§ Resume). Every driver call carries the generation it drives, and a stale one is refused — the nest's only notion of "which driver" |
| `blob_bytes` | finalized size; populated at completion |
| `blob_decryption_key_wrapped_for_actor` | the user's wrapped key for the blob (see § Sealed-blob delivery) |
| `download_url` | **derived, not stored** — it is `/api/v1/export/<session-id>` for every session, so a stored copy would be a second truth a route rename desynchronizes silently. The nest renders it into the wire reply (and into `BridgeExportComplete`) only once the session is `completed`, and the route re-checks that itself; valid only while the session is alive |
| `expires_at` | 30 days after `last_progress_at`; nest GC-removes the row and unlinks the blob after that (§ Expiry). Only a session still in flight moves it — progress on a finished one does not re-arm its window |

**State machine** identical to imports: `running` ↔ `paused`, `running` / `paused` → `errored` on session-fatal error (`fail_export_session`, § Resume — it unlinks the partial blob too), `running` → `completed` on finish, `running` / `paused` → `cancelled` on explicit cancel — plus the one transition the import twin has no use for, `running` / `paused` → `running` under a new stream generation (`restart_export_session`, § Resume). **Push events** mirror imports: `BridgeExportProgress { session_id, exported_count, skipped_count, errored_count }` after each batch; `BridgeExportError { session_id, reason }` on session-fatal; `BridgeExportComplete { session_id, download_url, blob_bytes }` at end.

### Resume — warm continues the stream, cold restarts it (ratified 2026-09-21)

**A paused export *continues* only in the app session that was driving it; anywhere else, Resume *restarts* the stream on the same session.** § Container shape pins the blob as byte slices of *one* zstd stream, and a zstd stream cannot be picked up from the middle: an app that restarted holds no encoder state, and the frames already on the nest are a prefix only that lost encoder could extend. So there are two resumes. **Warm:** a Pause keeps the live stream in the running app and a Resume there continues it — `resume_export_session`, `paused` → `running`, nothing re-uploaded. **Cold:** a session the app finds at page load that it did not start itself (the app was closed mid-export, or it is a *second* device of the same user) has nothing to continue, so its Resume calls **`restart_export_session`**, and the export runs again from the first message *on the same session* — same row, same concurrency slot, same Progress screen, counters back to zero. It costs the work already uploaded and nothing else, because nothing about the export lives in the abandoned stream: the scope rides the row (`scope_descriptor`), the mailbox order and the UID cursors re-derive from the listing, and the archive is deterministic (§ Container shape), so the restarted stream is the archive the abandoned one would have been.

**A restart opens a new *stream generation* — a fresh blob file and a fresh key — it never truncates in place.** The row carries a `stream_generation` counter (0 at `start_export_session`). `restart_export_session(session_id, wrapped_session_key, total_count)` does one atomic row update — state → `running`, `stream_generation` + 1, `blob_path` → the new generation's file name (§ Blob shape on disk), `next_chunk_idx` / `blob_bytes` / the three counters / `last_processed_message_id` → zero, the wrapped key replaced by the one the restarting client just minted — and only then unlinks the previous generation's file. Truncating the old file in place was the first shape considered and is **rejected**: an upload reserves its slot on the row and appends to the file afterwards, outside any lock the row update shares, so an upload already past its reservation would append its stale frame *after* the truncate, ahead of the new frame 0; and a crash between a row reset and a truncate leaves old bytes under a row that reads `next_chunk_idx = 0`. With a file per generation both holes close by construction, on § Reclaim's existing rules and no new lock: the upload's reservation returns the `blob_path` it read **under the same lock as its generation check**, so a stale in-flight append can only ever land in the *old* file; the new file does not exist until the new stream's frame 0 creates it (rule 1 — the row named it first); and the old file, which no row names from the instant of the update, is garbage whether the unlink ran, failed, or never happened because the nest crashed (rule 3). There is no half-done state to observe — the row switch is one statement. For the same reason an append creates the file only for frame 0: a later frame that finds no file is an upload into a generation that is gone (or a crash that lost frame 0), and must fail there rather than seed a blob that starts mid-stream.

**The nest cannot see "the driver is gone", so it does not try: a restart is always honoured from `running` or `paused`, and the generation is what shuts the previous driver out.** A session found after the app was closed mid-export is normally still `running` — nobody was left to pause it — so `paused`-only would make the feature unreachable in its main case. And no signal separates a dead driver from a live one on another device: the frames carry no device identity, and a last-progress age is a wall-clock guess. So the user's Resume on a cold session is taken at its word, and correctness never depends on the old driver really being gone. **Every call a driver makes carries the generation it drives** — `upload_export_chunk` always, and the loop's own `pause` / `resume` / `finalize` / failure-`fail` as an only-if-I-am-still-the-driver condition — and the nest answers a stale one with the typed `fauna.bridges.export_stream_superseded`, checked *before* the chunk index so a stale driver is never told to "resume from chunk n". A superseded driver **drops its run and touches nothing**: in particular it does not run its failure path, whose disposal would otherwise kill the restarted session out from under the device now driving it. The user's own Cancel (and a Pause or Resume pressed where no run is held) carries no generation and applies unconditionally — disposing of an export from any device stays the user's right. Pause is the one control a cold view must not send at all while the session is `running`: the nest refuses uploads to a paused session, so it would cost whichever device *is* driving the whole export; the shared machine refuses it with that reason.

**Each generation is sealed under its own key.** The restarting client mints and wraps a fresh per-session key exactly as `start_export_session`'s caller does (§ Key material), and the restart replaces the row's wrapped key with it. The previous key would have *worked* — any client of the owner can unwrap it — but reusing it would leave two streams' frames valid under one key at the same `(session_id, format, chunk_idx)`, which is precisely the associated data § Blob shape on disk authenticates: a nest that kept the old file could splice generations into a blob every frame of which passes AEAD. A fresh key makes cross-generation frames fail to open by construction, leaves the frame format, the associated data and the opener untouched, and spares the cold path an unwrap it does not otherwise need. Terminal sessions do not restart: `completed` has nothing to redo, and `cancelled` / `errored` have released their concurrency slot (§ Quota composition), so reviving one would be a second way past the cap — the user runs the wizard again.

**Version skew.** A nest that does not register `restart_export_session` answers `fauna.protocol.unknown_kind`, which the client surfaces as an ordinary error — the client-side fallback to the pre-restart behaviour left with the 2026-09-24 compat-remnant sweep (`../architecture/version-compatibility.md` § Dimension 2). A client older than this section never drives an export at all (no released app spawned the drive loop before the generation landed), so a generation-less upload is always generation 0 from a driver that was never restarted over; the field is additive and absent-means-zero.

**While driving, the client owns the pause transition.** The nest refuses `upload_export_chunk` on any session that is not `running`, so a pause sent while a page is half-uploaded would make the next upload fail and — under § An unopenable record fails the session's no-silent-loss rule — cost the user the whole export. `Pause` therefore asks the client's loop to stop, and the loop finishes the page it holds, pauses the session itself, and parks the stream. Cancel needs no such handoff: it disposes of the session at once, and a fetch or upload that then fails is the cancel's own consequence, not an error to report.

**A client-detected session-fatal failure is reported with `fail_export_session`, which disposes of the session AND records why (ratified 2026-09-22).** The partial blob has no terminator and could never be opened, so the disposal is not in question — the unlink and the freed concurrency slot are the same ones a cancel performs. What the kind adds is the **record**: the row moves `running`/`paused` → `errored` carrying the client's `reason` in `error_reason`, and `BridgeExportError` reaches the user's other connected clients, so a second device — and this one after a restart — reads an export that *failed*, and why, instead of one that merely reads `cancelled` with the reason resting on whichever device happened to see it. The client owns the conversion, so the client owns the classification: the nest records the string it is handed and judges none of it, refusing only an empty one (the import twin's rule — a reason that says nothing leaves exactly the record-free row the kind exists to improve on). **It carries the driver's `stream_generation` like every other driver call**, because a failure is always *a driver's* and may be this device's alone: a dropped fetch that lands after another device restarted the export is answered `fauna.bridges.export_stream_superseded` and disposes of nothing (the superseded driver then drops its run, as everywhere else in this section). (The client's fallback to `cancel_export_session` for a nest predating the kind left with the 2026-09-24 compat-remnant sweep.) Because reaching `errored` now unlinks the blob, an errored session holds **no** per-user footprint, exactly as a cancelled one does not (§ Quota composition).

## Sealed-blob delivery

The export blob is **encrypted at rest on nest disk**, under a per-session key the user's clients hold. The box owner cannot read the export blob.

### Why a per-session seal on top of at-rest sealing

The at-rest mailbox is already sealed — per message, to the recipient's MSEK-derived key (`architecture/encryption-at-rest.md`). The export blob still gets its **own** seal, for two reasons. First, artifact class: it concatenates an entire mailbox into a single artifact with a finite download window — the user's whole mail history in one exfiltratable shot — so it carries its own key rather than inheriting the per-message key structure. Second, mechanics: the blob is *assembled from client-converted plaintext* (§ Export pipeline) — the per-message at-rest seals are removed by the client during conversion, so without the session seal the uploaded chunks would land readable on nest disk. The per-session key, generated and wrapped client-side, is what keeps the assembled artifact exactly as opaque to the box as the messages it was built from.

The cost (one AEAD frame per uploaded chunk, plus the terminator frame finalize adds — § Blob shape on disk) is trivial; the benefit (the whole-mailbox snapshot stays opaque to the box owner end-to-end) is the invariant.

### Key material

- Per-export-session 256-bit key, generated client-side at session-start time — and again, fresh, by the client that restarts the stream (§ Resume: one key per stream generation; the restart replaces the stored wrapped key).
- Wrapped under the user's actor key (the same wrapping shape sealed mail uses per the mail-bridge rearchitecture design (ratified 2026-05-07; tracked internally) § MDA fetches per-credential wrapped MLS-key blobs).
- The wrapped key is sent to nest via the `start_export_session` RPC and stored in `export_sessions.blob_decryption_key_wrapped_for_actor`. **The nest never sees the unwrapped key** — the client seals every chunk itself (§ Export pipeline); the stored wrapped blob exists solely so *any* of the user's clients (not just the one that started the session) can fetch it, unwrap under the actor key, and decrypt the download.
- At download time, the client fetches the wrapped key from the session row + decrypts the downloaded blob client-side.

**The wrap shape, pinned 2026-09-21 (with the client key-custody seam).** "The user's actor key" resolves to the account's **MSEK-derived recipient key material** — the same key structure at-rest mail is sealed to, which is what makes "the same wrapping shape sealed mail uses" concrete. The wrapped key is a `fauna_mls::wrapped_blob::ExportSessionKeyBlob`: its own `kind` tag and an AAD bound to the exporting actor id, sealed under the post-quantum **X-Wing** suite with no classical degrade arm. Three consequences worth stating because each closes a path the obvious implementation leaves open. **(a) Its own kind, not `seal_to_recipient`'s** — the session key and an at-rest mail record are sealed to the *same* recipient material, so only a distinct AAD kind stops one opening as the other. **(b) The AAD binds the actor, not the session** — the nest mints the session id in the reply to the very call that carries the wrapped key, so there is no session id to bind at seal time; the gap is closed one layer up, because every frame of the blob authenticates its own `session_id` (§ Blob shape on disk), so a wrapped key moved onto another of the same user's sessions produces a download whose first frame fails AEAD. **(c) It opens against the account's complete *standing* key set** — current generation plus the grace generations of a rotation, the same set and trial order the receive path uses (`mail-app-surface.md` § Inbound client receive) — never a single generation: the wizard may have run before a key rotation and the archive may be opened after one, and a single-generation opener would hand that client a session it can see, a blob it can download, and no way to read it.

### Blob shape on disk — a framed per-chunk AEAD (pinned 2026-09-20)

`<data-dir>/exports/<session-id>.zip.zst.sealed` (§ Container shape). **That whole suffix is the file's name and `blob_path` records it verbatim** — the bytes on nest disk are framed ciphertext, never a mountable `.zip.zst`, so the shorter `e.g.` § Session row model carried was a drafting inconsistency and is corrected to this one. The user's *download* keeps the plain `fauna-export-…zip.zst` name of § Compression wrapper, because by then the client has opened the frames. **A restarted stream gets its own file** (§ Resume): generation *n* ≥ 1 rests at `exports/<session-id>.<n>.zip.zst.sealed`, generation 0 keeps the name above, and `blob_path` always names the current generation's — which is why every use site reads the recorded path and none rebuilds it from the id.

The file is a preamble followed by **one AEAD frame per uploaded chunk**, in `chunk_idx` order:

```
[6-byte preamble: b"FXPT" || format-version u16 BE]   once, as plaintext preceding frame 0's header
then repeated, one per chunk:
[ciphertext length u32 BE] [24-byte XChaCha20-Poly1305 nonce] [ciphertext]
```

Each frame's plaintext is the next byte slice of the single zstd stream (§ Container shape — never an independently-compressed unit) and each nonce is drawn fresh, so no counter discipline has to survive a resume. The MAC is still over the frame's ciphertext plus **a 32-byte associated-data field**, now `BLAKE3(preamble || session_id || 0x00 || format || 0x00 || chunk_idx u64 BE || is_final u8)`: it prevents the format substitution the original field was for, and additionally binds the version, the frame's position, and whether the frame terminates the blob — so a reordered, duplicated, dropped, truncated or re-versioned blob fails AEAD rather than opening to something plausible. The preamble is authenticated by every frame, which is why nothing on disk is left unauthenticated despite sitting outside the ciphertext.

**The declared frame length is bounded, and the bound is checked before any arithmetic on it (pinned 2026-09-22).** The length prefix is the one field an opener must trust *before* the AEAD can check anything — it is what says where the ciphertext ends — and the bytes come from the nest, the party this seal exists to distrust. So the format pins a **maximum frame length as a compile-time constant** (§ Compile-time decisions — no user or admin would ever choose it), derived as *the chunk size plus the AEAD tag*, because that is exactly the largest frame a conforming writer emits: a full chunk's declared length is the plaintext slice **plus 16 bytes of Poly1305 tag**, so a bound set naively to the chunk size alone would reject the writer's own output. An opener **refuses a frame whose declared length exceeds the bound, before it buffers toward that length, allocates on it, or adds the header size to it** — the last clause is not pedantry: on a 32-bit target (the web app) `header + declared` wraps for a declared length near `u32::MAX`, turning the refusal into a panic. Without the bound the codec's advertised streaming property is not true against a hostile nest: a single oversized header would make a streaming opener accumulate toward 4 GiB before it could authenticate one byte, which is the whole-blob-in-memory opener § Quota composition's 10 GiB ceiling rules out. This mirrors `libs/fauna-ipc`'s `MAX_FRAME_SIZE` / `checked_frame_len`, whose doc calls the length-prefix policy a project decision kept in one place (priority #3).

**Why framed, and not one pass over the whole blob.** The single-pass shape this section carried until now — *"seal in-memory by the worker; chunked-AEAD would only matter for blobs > 1 GiB"* — cannot survive two later ratifications in this same doc. § Export pipeline (2026-07-23) moved conversion to the **client** unconditionally, so there is no worker holding the blob in memory to seal; and § Quota composition's ceiling is **10 GiB**, not 1 GiB, so a single pass would make the client buffer the entire archive before one byte could be uploaded, on a phone as readily as a desktop. The per-chunk layer was never optional either way: § Why a per-session seal requires it independently, because an unsealed chunk lands **readable on nest disk the moment it arrives**. So this is not a second layer being added — it is the layer that was always there, and the section stops describing a whole-blob pass on top of it.

**What `finalize_export_session` contributes.** The client uploads a **terminator frame**: an empty-plaintext frame whose AAD sets `is_final = 1` and whose `chunk_idx` is the count of body frames. It is the blob's commitment to its own length, and it is what keeps § Architectural rules' no-partial-download property true without a second pass: an opener that reaches end-of-file without a terminator refuses the archive. The nest appends those bytes exactly as it appends any other chunk — it cannot tell a terminator from a body frame, parses neither, and still holds no key.

### Download flow

1. Client receives `BridgeExportComplete { session_id, download_url, blob_bytes }`.
2. Client GETs `download_url` (authenticated by the user's actor session; nest verifies the requesting actor matches `export_sessions.actor_id`).
3. Nest streams the sealed blob.
4. Client unwraps the per-session key using its actor key, then opens the blob's frames in `chunk_idx` order under it (§ Blob shape on disk) — **refusing a frame whose declared length exceeds the maximum frame length** (before buffering or arithmetic on it), and **refusing an archive whose last frame is not the terminator**, which is how a truncated or still-running export is caught rather than half-restored. What the frames concatenate to is the `.zip.zst` of § Container shape.
5. Client saves **those recovered bytes verbatim**, under § Compression wrapper's `fauna-export-<actor-handle>-<format>-<iso-date>.zip.zst` name (the client's standard "download to disk" path). **On web the destination is the browser's own download — its save dialog or its downloads folder, whichever the user's browser is set to — reached through a temporary file, never a `Blob` and never the save-file picker** (settled 2026-10-03 with the web leg): the opened frames are written one at a time into an origin-private temporary file the user cannot see, and only after step 4's terminator check does the page hand that disk-backed file to the browser as an ordinary download under the archive's name; a refused archive's temporary file is deleted and no download starts. A `Blob` assembled from the frames would hold the archive in memory, which § Quota composition's 10 GiB ceiling forbids. The save-file picker exists in one browser family only, must be opened before the asynchronous unwrap spends the click that asked for it, and creates the user-visible file before the first frame has been checked. The costs are accepted: the archive is on disk twice while the browser copies it out, and the page is never told when that copy ends — so a finished archive's temporary file is removed by a later sweep (once it is an hour old, on the next visit to the export page or the next download) rather than at once. On a native app the shared sink writes into a directory; where the platform's user-facing destination is a dialog, a share sheet or a content URI, the app passes an app-owned directory and hands the finished file on from there — never a partially written one, so the refusal in step 4 still leaves nothing that reads as a mailbox. **The client does not decompress**: § Container shape (2026-09-20) made the artifact one zip inside one zstd stream, and the user runs `zstd -d` once to hold a plain `.zip` their file manager opens natively — which is also why § Blob shape on disk says the download "keeps the plain `fauna-export-…zip.zst` name … because by then the client has opened the frames". This step and step 4 had read *"decompresses … saves the decompressed `<format>` file/directory tree"*, prose that predates the container: back then a format **was** a directory tree and the client would have had to expand one. The later ratification governs; corrected 2026-09-22 with the download leg. A client that expanded the zip here would also have to re-decide, per platform, where a whole tree lands and what happens when part of it collides — for no gain over the one archive file every desktop already understands.

**Standing and the owner's notice — ruled 2026-09-24.** A sealed blob is not a harmless one: it is a whole mailbox leaving the nest, a harvest-now-decrypt-later copy for whoever holds a bearer, and a bearer outlives the moment it was minted — the 30-day window of § Expiry is ample time for one to outlive a standing change. So the download door carries the account archive's use-time duties (`GET /api/v1/export`, `architecture/core-client-kind-catalog.md`) in the byte plane's shape: **(1) standing is asked at use** — the door authenticates through the nest's one bearer validator, which refuses a suspended or locked-out actor's surviving bearer (a locked-out *admin* keeps the door, the dispatch gate's own ruling), and refuses it `401` like every session-only byte door; the account route's `403` is particular to its eviction-token fall-through, which this door does not have; **(2) every successful download rings the owner** — a `MailboxExportDownloaded` security notice (its own event, not the account archive's, so the row names what left: the format and the peer address), fired after every gate passes and off the response path, and rendered as the ordinary security-notice row (`notifications.md` § Security notices); **(3) supersession needs no gate here** — succession burns the retired identity's export sessions and its bearers (§ Reclaim), so unlike the account route, whose deliberate supersession exception is `identity-succession.md`'s, there is no sanctioned post-succession download on this door to strand.

### Expiry

The session row + blob are GC'd 30 days after `last_progress_at` (the same 30-day window as the import session). The user can also explicitly discard via the "Discard now" button on the completion screen.

**From the instant `expires_at` passes, the session is gone from its owner's view** — out of `list_export_sessions`, the concurrency cap and the per-user footprint (§ Quota composition) — **but only the nest's periodic expiry job removes it**, across every actor, on the nest's existing expiry cadence: it unlinks the blob and then deletes the row (§ Reclaim rule 2), so an expired blob outlives its window by at most one pass. No per-actor path deletes an expired row itself: a row is the only record of where its blob is, and a path that drops it without unlinking orphans the file. The window counts from real progress only — a finished (`completed`/`cancelled`/`errored`) session's window is never re-armed.

A blob that's been GC'd but the user references via a stale URL gets a `404 Not Found` from nest — there's no zombie-blob recovery shape.

### Reclaim — the row is the authority, the file follows

An export session is a row **and** a file, and only the row can be deleted transactionally. Three rules keep the file from outliving it. **(1) Row before file, on the way in:** the session row — which carries `blob_path` — is committed before the blob file is created, so a file on disk always has (or once had) a row naming it. **(2) File before row, on the way out:** every path that discards a session — discard, expiry, account deletion — unlinks the blob while the row still names it, and deletes the row only after, and only while it still names the file that was unlinked (a restart may repoint it in between); an unlink that fails leaves the row standing, so the discard can be retried instead of orphaning a whole-mailbox snapshot nothing can find. **(3) A file under `<data-dir>/exports/` that no row names is garbage**, reclaimed by listing the directory (the listing is taken *before* the rows are read — rule 1 makes that order race-free against a session being created concurrently); it runs at boot, after every succession and on every pass of the periodic expiry job (§ Expiry), and it is what makes a crash between the two halves of rule 2, or a path that cannot honour rule 2 at all, recoverable rather than a permanent leak. `blob_path` is the nest-relative path of the file itself, verbatim, and only the minted shape `exports/<one file name>` is ever turned into an unlink. **A restart (§ Resume) is these three rules and nothing more:** the row is repointed at the new generation's file name before that file exists (rule 1), and the previous generation's file is unlinked after the row stopped naming it — deliberately *not* rule 2's file-before-row, because here the row survives: unlinking first would leave a `running` row naming a missing file if the update then failed, whereas updating first leaves at worst an unnamed file, which rule 3 collects.

**Account deletion** unlinks every blob the account's sessions name and then purges the rows (rule 2): a blob that will not unlink fails that deletion pass, which the pending-action executor retries. **Identity succession burns the sessions — they neither move to the successor nor stay with the retired identity.** The blob is sealed under a per-session key wrapped for the *retired* actor (§ Key material), so a moved session is an archive the successor cannot open and the old key's holder can; and a session left behind is never expired by its owner's own lazy sweeps, because a retired identity never calls again. The burn runs inside the succession transaction and cannot touch the disk, so its files are collected by rule 3 immediately after the commit. The user re-exports under the new identity. The per-table verdicts (deletion, succession, and what "export my data" carries of this table — everything but the wrapped key and the internal path) are declared on the `export_sessions` entry of the nest's actor-table registry (`account-data-plane.md` § Nest-side requirements item 1 owns that registry's rules).

## Cross-actor isolation

**A user exports their own mailboxes only.** The admin cannot trigger an export of another user's mail. The user-controls-their-data invariant (`principles.md` § Product invariants) forbids it.

Specifically:

- The `start_export_session` RPC takes no `target_actor_id` parameter — it implicitly exports the calling actor's mailboxes.
- An admin's only export-adjacent capability is the backup path — a separate feature, **not** in scope for this doc, and explicitly *not* a user-data export: backups never yield admin-readable user mail (backup mechanics + key custody are owned by `docs/goal/behavior/backup-restore.md` and `docs/goal/architecture/key-material-hierarchy.md`; this doc takes only that property, not the mechanism).

## Export pipeline — client-side conversion, unconditionally

On every nest, the per-message bytes rest as ciphertext sealed to the recipient (`architecture/encryption-at-rest.md`; the MTA seals at the perimeter per the mail-bridge rearchitecture design, ratified 2026-05-07). A nest holds no read key at all — Phase 3 dropped the last plaintext custody path (`actor_plaintext_msek`, migration 11) — so format conversion, which must read every message's plaintext, runs at the one position where plaintext and the user's unwrap capability coexist: **the user's client**. This is the same placement rule that governs scoring and search (`architecture/content-scoring.md` § The placement matrix; `mail-spam.md` § Scoring placement is the scoring instance, this section is the export instance). There is exactly one pipeline; a "conversion locus" question no longer exists.

### The chunk-relay pipeline

```
nest (worker)                     client (user's MUA)
─────────────                     ──────────────────
list scope                                     ←─ start_export_session(scope_descriptor, format, wrapped_session_key)
                                  client batches:
                                    fetch_export_chunk_ciphertext(session_id, mailbox_cursor)
                                      ↓
                                    returns N ciphertext messages + their wrapped MLS-key blobs
                                  client unwraps, plaintext-decodes,
                                  per-format-serializes (mbox / maildir / eml)
                                    into the ONE running zstd stream,
                                  cuts the next byte slice off that stream,
                                  seals that slice with the session key,
                                  uploads:
                                    upload_export_chunk(session_id, chunk_idx, sealed_chunk)
nest appends to blob_path,
nest emits BridgeExportProgress
                                  client repeats until all mailboxes enumerated,
                                  signals:
                                    finalize_export_session(session_id)
nest seals the blob, emits
BridgeExportComplete                 ←
                                  client downloads + decrypts (per § Sealed-blob delivery)
```

The conversion happens on the client because the **client** owns the unwrap keys. Nest is a chunk-relay: it streams ciphertext to the client, accepts sealed chunks back, appends them to the on-disk blob. Nest never sees plaintext mail bytes during the export. The per-session XChaCha20-Poly1305 layer is added by the **client**, chunk by chunk as each one is produced, and never by nest — because nest doesn't hold the session key, and because a chunk arriving unsealed would rest readable on nest disk. Finalize adds the terminator frame that commits to the blob's length, not a second pass over it (§ Blob shape on disk).

**The diagram's compression step is per-stream, not per-batch** (corrected 2026-09-21, with the client drive loop): it read "zstd-compresses the format batch", which predates § Container shape's 2026-09-20 pin that the archive is **one** zstd stream and an uploaded chunk is a byte SLICE of it, never an independently-compressed unit. A per-batch compressor would produce a concatenation of zstd frames that no single `zstd -d` opens, and would make the archive's bytes depend on where the chunk boundaries happened to fall — which the determinism contract forbids. The later ratification governs; the diagram now says so.

**The date range is applied by the client, in this loop (ratified 2026-09-21).** Each down-leg record carries its INTERNALDATE, and the loop drops an out-of-range one before opening it. A nest-side `since`/`until` on `fetch_export_chunk_ciphertext` was considered and is **deferred as a pure transfer optimization**, not rejected: INTERNALDATE is plaintext metadata the nest already serves, so no sealing property would be touched — but the nest reads it off the record's floor, i.e. only by reading the sealed body it would then not send, so the saving is wire bytes between a user and their own nest, not nest work; and an older nest would ignore the additive fields, so the client filter is the mechanism either way and the archive can never depend on the nest having filtered. **Reconsideration trigger:** a measured ranged export over a large mailbox on a slow link. It would land as additive request fields (absent = unbounded) plus this doc's § Wire shapes row and `bridges.md` Phase H.

**A record is opened by its seal instant, never its date (ratified 2026-09-25).** Each down-leg record also carries the nest's seal instant (`stored_at`, additive; `0` from a nest that reports none), and the client's record opener picks the epoch keys it trials by that instant — the classification basis `../architecture/encryption-at-rest.md` § Capability tiering (content-sealing epochs) names for every opener of stored mail. INTERNALDATE decides only the date range and the archive's dates; it is the opener's fallback only when the nest reports no seal instant. Taking the epoch from INTERNALDATE fails any record sealed in a later epoch than its date names — all imported mail, and ordinary mail delivered after a weekly epoch boundary its `Date:` precedes — because the epoch chain scans only backward from its target; on this path that is an export that fails (§ An unopenable record fails the session).

The "client repeats until all mailboxes enumerated" loop is rate-limited (default 8 concurrent chunk fetches, 16 MiB chunks; same shape as the IMAP MDA's sealed-record fetch). The wire cost — each message crosses down as ciphertext and back up inside a sealed chunk — is the floor for this operation, not overhead: any scheme that avoids the round-trip requires handing the nest an unwrap capability it deliberately does not have. Output is deterministic where it is checkable: same source mailboxes, same scope and same format → a byte-identical **plaintext** archive (the self-verifiability bar in § Goal, and what § Container shape's determinism contract pins). The sealed file is not byte-identical across runs and must not be asserted to be — every frame draws a fresh nonce (§ Blob shape on disk), which is the property that lets a resumed session keep uploading without replaying a counter.

### An unopenable record fails the session (ratified 2026-09-21)

A record the client cannot open — a rotation past the grace window, a mailbox torn down and re-enabled under a fresh MSEK, a tampered envelope — **fails the whole export session**, with the mailbox and UID in `error_reason`. It is never skipped, never counted into `skipped_count`, and never logged into the error log while the run carries on.

**This is the opposite of the receive path's rule, deliberately.** `mail-app-surface.md` § Inbound client receive ratified *skip-and-record* for exactly the same condition, because there the alternative is one bad record stopping a mailbox from receiving anything after it — a contained fault made uncontained. An export has no such asymmetry: the run produces one artifact whose whole promise is that it is the user's mail, and § Goal's self-verifiability bar is what a user checks it against. An archive quietly missing messages is worse than no archive, because the user cannot tell — they delete the account, or the source, against a file that looked complete. Skipping is the receive path's *containment*; on an egress path it is silent data loss.

The same rule governs the two other ways a message can go missing on the down-leg, so there is one answer rather than three: a `body_ref` the client cannot resolve off the bulk-byte plane fails the session (it is a fetch failure, transient by construction — retry, then fail; never drop), and so does a serializer refusal. The client's cursor is durable, so a failed session is re-runnable once the cause is fixed, which is the recovery path a skip would have denied by producing a plausible archive instead.

### The rejected alternative — nest-side conversion under a session-scoped capability (recorded 2026-07-23)

A server-side conversion path could in principle be rebuilt the way the AUTH'd MDA session reads mail: the export session carries a time-boxed, user-minted unwrap capability, and a nest worker converts in-process. **Rejected.** It would mint a *whole-mailbox* read capability to the box for a job the user's client is by definition present for (the wizard's steps 1–3 are interactive; there is no headless initiator), re-creating exactly the exposure the placement matrix exists to prevent, for no capability gain — only a wire saving. It would also make the export blob's "opaque to the box owner" property (§ Sealed-blob delivery) depend on worker-memory hygiene instead of holding by construction. **Reconsideration trigger:** a genuine zero-client export need (e.g. a future scheduled/unattended export feature). Such a feature would ride the capability-grant plane (`architecture/encryption-at-rest.md` § Capability tiering — the content-processor holder pattern), with its own design round; it must never come back as a deployment-posture probe (`nest/storage-modes.md` § The transition contract rule 3: conditionals key on observable data, never a mode flag — and `fauna.bridges.storage_mode`, the probe RPC the client machine stubbed, is retired with this section).

## Quota composition

**Exports don't count toward the user's per-mailbox quota.** The user is reading their own data, not writing new. Imports consumed mailbox quota (per `mailbox-migration.md` § Quota composition); exports don't.

**Per-export-session disk ceiling.** Default 10 GiB per export session, admin-tunable (`mail.export.max_blob_bytes` — tier/binding/surface per the `mail-policy-config.md` catalog). A session that would exceed the ceiling errors with `session_blob_oversize` and the user must narrow the scope or split into multiple smaller exports. The ceiling exists because the blob sits on nest disk for up to 30 days; without a per-session cap, a user with a 500 GiB mailbox would tie up 500 GiB of nest disk on a single export.

**Concurrent-export cap.** Default 3 concurrent in-flight exports per user (`mail.export.max_concurrent_per_user` — same catalog). Above the cap, the wizard refuses to start a new export until one finishes / errors / cancels. (A user with 3 paused exports can have 4th-attempt rejected.) The cap bounds how many exports a user drives at once — it does **not** bound disk on its own: a finished export frees its slot but keeps its blob for the whole § Expiry window, so under the cap alone one user could hold 10 GiB × every export finished in 30 days.

**Per-user footprint.** The disk bound is its own check: **the blob bytes of all of a user's live sessions together may not exceed `max_blob_bytes × max_concurrent_per_user`** — 3 × 10 GiB = 30 GiB per user by default, following either ceiling when the admin tunes it. It is **derived, not a third knob** — nobody would choose it independently of the two it multiplies (`mail-policy-config.md` § Export). "Live" means every session still holding a blob — `running`, `paused` and `completed` — and not one of the two **disposed** states, `cancelled` and `errored`, each of which unlinks its blob while the row stays for the wizard to list (§ Resume: `fail_export_session` disposes of a partial blob that can never be opened, exactly as cancel does), nor an expired one (gone from the owner's view, § Expiry). It is checked beside the per-session ceiling, against the same running totals: a start is refused while the user's live sessions already hold the whole footprint, and a chunk is refused if it would cross it, without writing a byte — both with `export_footprint_exceeded`, whose remedy is to download and discard a finished export (narrowing the scope, `session_blob_oversize`'s remedy, does not help when finished exports hold the disk). It is a nest-disk bound on export blobs only, never the mailbox storage quota (§ Don't do these).

## Architectural rules

- **User-owned, user-controlled.** The user is the only principal who can initiate, pause, resume, cancel, or download an export of their mailbox. The admin's only role is the policy cap (max blob bytes, max concurrent). The admin cannot read the export blob.
- **Sealed at rest, always.** Every export blob is XChaCha20-Poly1305-sealed under a per-session key wrapped for the user — the export is a different artifact-class than the at-rest mailbox and carries its own key (§ Sealed-blob delivery), and the sealing cost is trivial.
- **Symmetric session row with imports.** `export_sessions` has the same column shape as `import_sessions`, the same state machine, the same 30-day GC, the same push-event naming pattern. A future "snapshot" feature unifying both is forecasted-compatible.
- **Three format choices, no more, no less in v1.** mbox, Maildir++, EML zip. Each has a real MUA-interoperability story; adding a fourth (PST, Outlook OST, custom Fauna shape) without a real consumer is the scope-creep we don't take.
- **Client-side conversion, unconditionally.** The nest is a ciphertext chunk-relay; it holds no read key and never sees plaintext mail bytes during an export (§ Export pipeline). There is no server-side conversion arm and no mode/posture probe deciding a locus.
- **Per-session disk + concurrency caps, and the per-user footprint they imply.** A 10 GiB ceiling per session + 3 concurrent per user is the default, and together they bound a user's live export blobs at 30 GiB (§ Quota composition) — fits the project's early "no users yet" current state without setting a tone that says "the box owner hosts unlimited free archives." The two ceilings are admin-tunable; the footprint follows them.
- **Exports are GET-not-POST-able by external tools.** The download URL is bound to the user's actor session; an external tool with the URL but not the cookie can't download. We don't generate "public link" exports — the user wanting a shareable export downloads, then shares the file via their own channel.
- **No partial-blob download.** A user mid-export cannot usefully download a partial blob: the frames already on disk open, but the archive has no terminator frame, so the client's opener refuses it rather than handing back a truncated mailbox (§ Blob shape on disk). What guarantees this is the terminator, not the absence of chunked AEAD — the frames *are* chunked AEAD, and have to be, since an unsealed chunk would rest readable on nest disk. A future "stream-on-read" mode for very-large exports is therefore a UX decision about partial archives, not a crypto-shape change.
- **An unopenable record fails the session, never skipped.** The one rule that differs from the receive path's, and it differs because an export is egress: a silently short archive is worse than a failed one (§ An unopenable record fails the session).
- **The session_id is visible, and nothing rests on it being secret.** It names the blob path and rides inside the download address (`/api/v1/export/<session-id>`, § Session row model), which the Done step shows as a copyable link so the user can fetch the export from another of their devices (§ Wizard steps step 5). What protects the export is never the address: the route re-checks the caller's actor session, so the address in anyone else's hands opens nothing (§ Cross-actor isolation), and behind that stands the per-session seal. The UI shows the address as a link and never offers the bare id as a handle of its own. (Corrected 2026-10-01: this rule had said the UI never exposes the id, while step 5 shows the address that carries it.)
- **30-day GC on export, same as import.** Long-lived sealed blobs are an obligation we don't take on; if the user wants their export forever, they download it. Re-running the wizard is cheap.
- **Reading-from-own-mailbox doesn't consume quota.** Exports don't bill against per-mailbox storage quota, per the user-controls-their-data invariant — gating data egress on storage quota would be a different product.

## Don't do these

- Don't store export blobs in plaintext on nest disk, ever. The blob is a different artifact class than the message store and carries its own per-session seal (§ Sealed-blob delivery).
- Don't let the admin export another user's mailbox. The product invariant forbids it; an "admin override" path would be a backdoor by another name.
- Don't generate "public link" exports. The download URL is actor-bound; we don't issue tokens that bypass the actor session. (A user wanting to share their export shares the file, not the link.)
- Don't bundle multiple users' exports into a single box-owner-readable archive. Backup is a separate feature with its own custody design (owner: `backup-restore.md` + `key-material-hierarchy.md`); export is per-user, per-session, single-user-readable.
- Don't unwrap the per-session key on nest, ever. There is no code path that needs it (the client seals every chunk and the finalize layer itself — § Export pipeline); a nest-side unwrap appearing in any implementation is a design violation, not an optimization.
- Don't expose the blob's raw filesystem path in any user-facing surface. The user sees `<format>` and the size; the path (`exports/<session-id>.zip.zst.sealed`) is an internal handle.
- Don't ship a "merge mailboxes into one file" export option. The format choices preserve mailbox boundaries (mbox = one file per mailbox; maildir = one tree per mailbox; eml zip = manifest records per-message mailbox). Flattening is the user's downstream choice if they want it; preserving structure is the right floor.
- Don't auto-trigger an export on account-deletion. The user explicitly opts in via the wizard; an auto-export on delete would tie up disk and key-management complexity for no gain (the user about to delete their account should run the export *first* and then delete — the delete confirmation reminds them to: its surface is owned by [`../ui/settings.md`](../ui/settings.md) § Layout & flow, item 14, and is unbuilt).
- Don't let the export blob outlive `expires_at`. The 30-day GC is hard; an "I forgot to download" recovery path doesn't exist. The user re-runs the wizard.
- Don't tie quota composition to the export blob's disk footprint as a backdoor "storage quota for exports." The per-session ceiling is the right shape; counting export disk against the mailbox storage quota would be an indirect rationing that the user's mental model doesn't accommodate.
- Don't bypass `fauna.bridges.fetch_export_chunk_ciphertext` for "performance." The chunk-relay shape exists because nest holds no unwrap keys; a "let nest unwrap for the export" shortcut is the rejected alternative in § Export pipeline and would puncture the at-rest sealing property (`architecture/encryption-at-rest.md`).
