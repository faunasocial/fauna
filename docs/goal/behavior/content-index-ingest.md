## Ingest triggers, v1

**Ingest triggers, v1 (ratified 2026-08-02, S0(d)).** How the client builder learns there is content to index — two arms, both in shared Rust:

- **The receive hook — an observer seam, not a hard dependency. BUILT 2026-08-02 (S3).** The shared client receive paths gain an index-sink observer trait (registered by app glue, the `observe_local_detection` / `FolderCustodyObserver` precedent): `MessageIndexObserver` / `IndexableMessage` in `libs/fauna-conversations/src/index_sink.rs`. `fauna-conversations` stays tantivy-free — it hands the sink already-decrypted, already-parsed text and identifiers; the sink implementation lives in the builder crate below. **Both chokepoints fire the one seam**, one frame inside the entry points named at ratification: `ConversationsManager::ingest_inbound` (the mail rail — `backends::smtp::ingest_inbound_record` funnels straight into it) and `ingest_inbound_to_thread` (conversations, kind wired but ignored by the mail-slice sink until S4), each beside the existing post-decrypt hook. That frame rather than `ingest_inbound_record` itself, for two reasons found in the build: it is **past the message-id dedup**, so a re-delivered message the manager drops is never indexed, and it is where the **thread id exists**, so every emitted doc carries the real navigation target `ui/search.md` § State & data shape requires of a local row. Flow-pinned end to end by `libs/fauna-client-index/tests/receive_hook_flow.rs`.
- **The backfill — a one-shot per-kind paged pass at builder start**, for any kind whose client keeps a local store and therefore sees only *new* content on the receive path. **For mail this reduces to the receive walk's own first pass — there is no second walk (CORRECTED 2026-08-03 at code level; the ratified wording assumed a premise the code refutes).** The ratification reasoned "there is no local mail store to scan, so the backfill is a UID-cursor walk over `fauna.email.{inbox,sent}.fetch`" — but the *absence* of a local store is exactly why no separate walk is needed: the receive loop's paging cursors are per-session and in-memory (`Session::mail_cursors` is a `Mutex<(u32, u32)>` initialised `(0, 0)`; the detached loop seeds its own `mail_inbox_uid`/`mail_sent_uid` at `0` on every start, and no app or FFI layer persists a mail UID anywhere), and the manager's thread store is empty after a restart — so **every launch already re-pages the entire mailbox from UID 0**, every record clears the message-id dedup, and the seam fires for all of it. A separate backfill pass would re-fetch and re-decrypt the identical records for no added coverage, and it could not reproduce the frame the seam is deliberately placed at (past the dedup, thread id in hand) without duplicating the manager's bucketing — which is the very thing that placement exists to avoid.
- **What mail owes instead is a stage-time guard, not a walk. BUILT 2026-08-03.** Because the full walk repeats every launch, a builder wired naively would re-stage the whole mailbox into a fresh segment chain at every start — unbounded growth on the user's at-rest store, and the ruled compactor (§ Where the index is built) is not built yet. So a **resumed** builder must not re-index content its own published segments already hold. The mechanism is a **stage-time content-id guard**: `Index::content_ids` reports the live ids in an opened index, `resume_mail_builder` seeds the builder from the segments it opened at resume, and `MailIndexBuilder::stage` drops a doc whose content id is already known (membership test and insert under one lock, so two receive passes racing on one message cannot both stage it). Exact, no seam change, no wire change, and it reuses the `(kind, content_id)` key the design already dedups on. **The rejected alternative** — plumbing a mailbox UID onto `IndexableMessage` so the advisory cursor gates staging — fails on the cursor's own shape: `ingest_cursors` holds one `u64` per `ContentKind`, while INBOX and Sent are independent UID spaces, so the max-merge is wrong for two feeds. The cursor therefore stays advisory and idempotence stays structural, per the bullet below. **Kind-scoped on purpose:** skip-if-present is safe for mail because a mail content id is the immutable RFC `Message-ID`; it would be **wrong** for a mutable kind (drafts), so S4's master-key builder owes its own answer rather than copying this one. ⚠ **That premise was FALSIFIED on 2026-09-15 and the guard re-ruled 2026-09-16 — read the sub-bullet below before relying on the sentence you just read:** a mail content id is a stable *identity*, but the content under it is replaceable, so the guard now keys on the nest record id beside the content id. **The S5 MDA leg inherits the question directly** — it builds the *same* mail/calendar slice under the *same* MSEK-derived key, from a source that likewise re-presents the whole mailbox each session, so it needs the same guard seeded the same way (or an explicit reason it does not).
  - **A mail content id is a stable IDENTITY, not immutable CONTENT — the guard keys on the nest record id too (RULED + BUILT 2026-09-16).** The bullet above rests skip-if-present on "a mail content id is the immutable RFC `Message-ID`". The Message-ID collision rule ([`conversations-at-rest.md`](conversations-at-rest.md) § Receiving into the conversations view, ratified 2026-09-15) falsified the content half of that: when an `INBOX` copy **squats** on a Message-ID this account also sent under, the account's `Sent` copy *displaces* it — the squat leaves its thread and the `Sent` copy ingests afresh — so the content under a Message-ID this device already indexed is **replaced**. Keyed on identity alone the guard dropped the genuine copy's observe for ever, and two things were wrong at once for the user: the account's own body was **never tokenized** (nothing found the message locally — a false negative on the user's own mail), and the squat's words **kept matching** from a segment sealed before the displacement, a hit that resolves through the live thread store and therefore renders the *genuine* message, showing a result that does not contain the word searched for. The fix is not a weaker guard — the guard's job is the every-launch mailbox re-page and that has not changed — but a **more precise key plus a tie-break**, and a supersession needs **both**. **(1) A different nest segment-record id.** A doc counts as already indexed only when it arrives under the **same** record id (`IndexableMessage::nest_message_id`, already carried for the MDA's `SEARCH` coverage and already stored as the doc's `secondary_id`, so no wire change and no format bump); a different one means the nest filed a *different record* under this id, which is what a displacement is. **(2) The arriving copy is the account's OWN** — `IndexableMessage::is_own`, the one field the seam had to grow, which for mail means the `Sent` mailbox served it and is therefore the only proof of authorship the collision rule recognises. **Condition (2) is not belt-and-braces; without it the guard oscillates.** The squat re-pages from `INBOX` every launch and the thread store starts empty every launch, so on *every* launch the squat reaches the seam **before** the `Sent` copy: keyed on content change alone the squat would take the id back, the `Sent` copy would take it again, and each launch would rewrite a segment twice, for ever. Ownership breaks the tie, and it breaks it in the direction [`../ui/conversations.md`](../ui/conversations.md) already chose — *an `INBOX` record never displaces a held copy*. The same asymmetry closes the forgery direction: a squat arriving **after** the account's own copy is indexed is dropped, so a forger cannot replace the account's own indexed body with their text and make the real message unfindable. The index must never be the softer target than the view. `None == None` on the record id matches, so every rail that carries no nest record (MLS conversations, the drafts corpus, attach-time walks) keeps its pre-2026-09-16 behaviour exactly, and so does the non-message door `stage_doc`, which never supersedes — a future kind whose content id can be re-pointed states that itself rather than inheriting mail's answer. **Why a *state* comparison and not a displacement EVENT on the seam** — an `observe_displaced(content_id)` fired where the view evicts the squat looks like the obvious shape and is the wrong one, because the displacement is **not a one-off**: it re-fires on every launch (the store is empty, the squat re-pages, the `Sent` copy displaces it again), so an event-driven rewrite republishes a segment blob per launch for as long as the forged record sits in the mailbox. Comparing *what is indexed* against *what arrived* is idempotent instead — once the rewrite has landed, the `Sent` copy matches the doc under its id and the next launch does nothing. **Why the nest's record id is the thing compared:** it is the one discriminator here a forger does not control — the nest assigns record ids, while the Message-ID and every header are the attacker's to choose, and the delivery timestamp (the other candidate) is attacker-influenced and can collide. **Retiring the stale copy is a separate obligation** and cannot be met by re-staging: `Index::add_doc`'s upsert stops at the boundary of one sealed segment, so the superseded doc survives in the segment that already holds it and survives compaction too — the retirement affordance and its bounds are [`content-index.md`](content-index.md) § Where the index is built → *Retiring a superseded doc*, which owns that half. **The test for a future kind gains a third question** beside *can its content change in place* and *can it vanish*: **can a stable content id be re-pointed at different content** — for mail by the collision rule, and for any kind whose id is producer-owned rather than content-derived. An append kind may answer yes and stay append-shaped, provided its producer hands over an identity that changes when the content does.
- **If the receive cursor ever becomes restart-persistent, a real mail backfill becomes necessary again** — that is the condition to re-check before concluding this bullet still holds.
- **The Conversation kind's catch-up: two idempotent legs (RULED 2026-08-04; BUILT 2026-08-05).** The kind's re-presentation shape mirrors mail's with one structural leak: the thread store is in-memory, rebuilt every launch from two sources — the `__mls` history-slice restore (`restore_and_wire`, `devices.md` § Cross-device MLS group-state sync slice 5), which appends via `ThreadStore::restore_channel_slice` and **bypasses the seam**, and the log refold + live ingest through `ingest_inbound_to_thread`, which fires it. So restored history — cross-device history, the owner's own sent plaintext — reached no builder before this landed. The ruling is **both** of the obvious halves: **(1)** the manager's restore path offers each restored message to the same seam the ingest chokepoints fire (an absent observer drops it, as everywhere else); **(2)** the builder walks the thread store through the seam when it attaches (the store is enumerable — `list_summaries` + `get`). Whichever leg runs second completes the corpus, and overlap is harmless under the stage-time `(kind, content_id)` guard. **The skip-if-present guard transfers to Conversation** because message content is immutable post-ingest — the store dedups by message id, a restore keeps local copies, and no edit path exists (subject lines are set only at ingest bucketing) — and explicitly does **not** transfer to drafts (mutable), whose arm still owes its own answer per the mail bullet above. **Both legs are pass-shaped** — the store re-presents every launch — so the lease gates them as catch-up staging (§ Where the index is built), and the live trickle stays ungated. The boundary rule generalizes from mail's clean-sweep rule: only a restore + initial refold that completed **without error** closes the Conversation catch-up boundary — an errored refold leaves the walk unfinished, and closing on it would reclassify the un-walked remainder as trickle (which the lease never gates), the exact failure mode the mail rule exists to prevent. **A message the user SENDS reaches the builder when it is sent (RULED + BUILT 2026-09-22).** The receive poll never re-presents a sender's own record on the device that sent it, so until this ruling the launch walk was a sent message's only path, and it stayed unsearchable from the moment it was sent until the app restarted. `ConversationsManager::send` now offers the own copy to the seam as its rail's kind — `Conversation` for FaunaMls and the bridged DM rails, one mapping shared with the inbound chokepoint (`index_kind_for_rail`) — exactly as the launch walk would offer it (no subject, no record id), so the next launch's re-offer is dropped by the stage-time guard. **Mail is the exception, by identity:** a mail doc's secondary identity is the nest record id, which the local echo lacks — offered at send, the next launch's re-page of the same `Sent` record would take the builder's replace-and-rewrite arm, one wasted segment rewrite per sent mail — so the send offers nothing for mail, and the server `Sent` copy, which the manager drops against the held own echo (`SentCopyOutcome::AlreadyOwn`), is offered in its place, record id and all, in the session it arrives. **The bridged rails are in by decision, not by accident:** a received bridge DM was already indexed as `Conversation`, the launch walk skips non-native threads, so without the send-time offer a bridged message the user wrote was never searchable at all. The offer is a live arrival and meets the lease like every other: while its kind's catch-up window is still open it counts as backlog, so a seat that has stood down withholds it and the lease holder indexes the same record off its own receive (`index_builder.rs` — `a_stood_down_seat_skips_the_catch_up_backlog`, `a_stood_down_seat_still_stages_a_live_arrival`). It reaches the apps that build an index — tui, linux, macOS, windows; iOS and Android never build one (`libs/fauna-ffi/src/index_launch.rs` `CLIENT_BUILDS_INDEX`), and the web app has no local search (`content-index.md` § Where queries run — per app). Pinned by `manager_integration_tests.rs` (`a_message_sent_in_a_fauna_native_group_is_offered_to_the_index_at_send_time`, `a_message_sent_on_a_bridged_rail_is_offered_to_the_index_at_send_time`) and `smtp_backend_tests.rs` (`a_sent_mail_reaches_the_index_through_its_sent_copy_in_the_same_session`).
  - ⚠ **The ruling's stated *reason* for two legs was REFUTED by the build (2026-08-05), and the ruling itself stands on a better one.** The 2026-08-04 wording justified both legs by claiming restore-vs-attach ordering is "genuinely unordered", since `restore_and_wire_with_retry` re-attempts transient failures with backoff. That is not what the code does: the retry is **awaited**, so every seat completes (or permanently abandons) the restore *before* an index observer exists — tui and the FFI seat because `start_receive_loop`'s prologue awaits `mls_sync_launcher.launch()` two statements above the index launch, linux because it awaits its own `wire_mls_state_sync` before calling `start_receive_loop` at all — and there is exactly **one** production restore call site, reached only from launch. So the ordering is deterministic, leg 2 is what indexes restored history today, and **leg 1 offers into an empty observer slot every time.** Both legs are still built and still ruled, for the reason that survives: the pair is *order-independent by construction*, so the day the restore moves after attach — one `tokio::spawn` away, and tempting, since it currently blocks the whole receive loop on an indefinite backoff — restored history keeps reaching the index instead of silently becoming unsearchable. A leg with no live caller is exactly what a later refactor deletes as dead, so it carries its own tier_1 pin.
  - **The restore half of the boundary rule is discharged structurally, not dynamically** — a consequence of the same ordering. Because the restore has always ended by the time the observer exists, the loop checks only the refold half (`poll_bound` now answers whether every bound channel folded cleanly, and a per-fold-site `conv_sweep!` closes the boundary on the first clean one, mirroring `mail_sweep!`). `index_launch_ordering_tests.rs` pins the ordering that makes this sound; if it ever changes, the restore's completion has to become a condition rather than a precondition.
  - **A community room waiting for its key-in folds FOR NOW — and its key-in REOPENS the window (RULED + BUILT 2026-09-12).** A newcomer's walk stops before the first `RoomSealed` record it holds no key for, and reports that stop as `stalled` ([`community-rooms.md`](community-rooms.md) § Implementation status today → *A newcomer's walk waits for its key-in*). Under the clean-sweep rule above that counted as an unfinished fold, so **one** unkeyed room held the whole **account's** Conversation boundary open: `poll_bound` answered incomplete on every sweep and `observe_catch_up_complete(Conversation)` never fired — for as long as the wait lasted, which has no bound, no timeout and no end but an owner's or admin's device happening to poll. A seat that had stood down from the index lease therefore withheld **every other channel's** backlog for the rest of the session, over a room it could do nothing about. So an `awaiting_key` fold counts as **folded for now**: the boundary closes on the room's siblings, and nothing of the room's own is thereby reclassified, because its cursor still sits before the record it is owed. **What withholds the ROOM's backlog is the reopen, not the stall.** Everything sealed between acceptance and the key-in — for a `Full` history policy, the room's whole past — becomes walkable in one step, normally long after the boundary closed. So the walk stops **once more**, before the first record its new key opens (`ConvPollOutcome::keyed_in`, a one-shot per wait), the receive loop fires `MessageIndexObserver::observe_catch_up_reopened(Conversation)`, and only then re-walks that room: the held-back history arrives inside a window, in the same reopen → backlog → boundary order the late-arm bullet below gives a mid-session arm. Two costs, stated rather than discovered: the window is open across that re-walk, so a **concurrent app-driven sweep's** live trickle can be counted as backlog (withheld on a stood-down seat until the next boundary — never lost), which is why the re-walk covers only the rooms that just keyed in and runs after the sweep's own loop; and an app-driven sweep that **wins the race to the first key** walks straight past the stop (`poll_inbound_conv_past_key_in` — it has no window to reopen), leaving that room's backlog staged as trickle, which is what every room's backlog did before this ruling and costs a re-stage the `(kind, content_id)` guard drops.
  - **The boundary signal is per kind.** `MessageIndexObserver::observe_catch_up_complete` carries an `IndexableKind` and each builder takes only its own, exactly as `observe_indexable_message` already did. This was **one rule the build had to add, because the ratified wording did not reach it**: the launcher fans one seam callback out to every arm, so a single kind-less signal would close the *Conversation* window on the *mail* sweep — mid-refold, reclassifying the rest of that backlog as trickle — while a mail-enabled actor whose feed errored every sweep would never close the Conversation window at all. Same failure pair the mail clean-sweep rule exists to prevent, arriving from an unrelated rail.
- **An arm attaches when its precondition arrives — the launch is not one-shot (BUILT 2026-08-05).** `launch()` runs once, in the receive loop's prologue, but an arm's precondition can arrive mid-session: **mail enabled after login** leaves the MSEK absent from the mail custody at that instant, and before this the mail arm then never existed for the rest of the process's life — the mail arrived, rendered in Conversations, and was silently never staged for search until an app restart. (A transient rail failure at launch stranded an arm identically.) The receive path never had this problem because it re-derives lazily on every poll (`MailKeyCache::get`); indexing now does the same. The seam is `IndexBuilderLauncher::ensure_arm(kind) -> bool` — attach that kind's arm if it is missing and buildable now — asked by the loop **on every sweep of that kind, before the poll**. Before, never after: within a session the mail cursors advance, so an arm attached after the fetch misses that sweep's mail and nothing re-presents it until the next launch. Two rules the build had to add:
  - **Attaching mutates the registered container; it never mints a new one.** The seam holds exactly one observer slot, so the naive fix — re-run `launch()` on the transition — would replace the registered observer and discard the already-running arms' live state: their seeded `(kind, content_id)` re-index guard and anything staged but not yet flushed. Neither is visible in a search result, so nothing downstream would notice the loss. `FanOutObserver` is therefore created with the launcher and grows in place, and a claim/release guard keeps a class from ever getting two builders (two would each rewrite the same manifest wholesale and clobber the other's segment chain). Consequently `launch()` returns that container **unconditionally** — `None` would promise the loop that no observer can ever appear, which is the one-shot behaviour being removed.
  - **The QUERY side is one-shot too, and closing only the build half fixes nothing a user can see.** Registering the Search page's local arm needs the same MSEK, and app glue registers at login — so a user who enabled mail afterwards had the mail indexed correctly and *still* saw no local hits, because the page had no arm to ask. Found by the e2e, which stayed red after the build half landed. So glue registers a **resolver** (`LocalIndexResolver`, implemented once for every native seat as `fauna_client_conversations::LauncherLocalIndex`) rather than an arm, and `SearchManager` mints on the first query that finds no arm, caching the first **complete** arm — registration is synchronous and always possible, where minting is not. **A partial arm is not final (fixed 2026-09-26):** the master reader needs only the identity seed, so a login mints a real master-only arm before mail is enabled, and that arm carries neither the mail reader nor the `Contact` claim (both ride the MSEK); caching it as the first `Some` left contact and mail hits invisible until the app restarted, whenever the arm happened to be minted before the user enabled mail. The glue marks such an arm `awaits_precondition` (`CompositeLocalSearch::awaiting_precondition`), and the manager re-asks its resolver on every query while it holds one, keeping the partial arm if the resolve yields nothing — found by the phone twin of the Contact search leg, whose mail is enabled through the app after login. `None` stays a normal answer meaning *no local rows*, never a page error. The web SPA registers neither, structurally (§ Where queries run).
  - **A late arm gets a fresh catch-up window, never the one that closed without it.** With mail disabled a sweep is a graceful no-op that answers *complete*, so the mail boundary normally closes on **sweep 1 — before mail is even enabled**. Replaying that closure to a late arm would reclassify the whole mailbox re-walk as trickle, which the lease never gates (the N× republish the boundary exists to prevent); leaving the window shut would make a stood-down seat withhold that arm's backlog for the rest of the session. So the loop reopens that kind's window on attach — per kind, for the same reason the boundary itself is — and Mail additionally re-pages from UID 0 (free in the enablement case, and the one re-page that gets this session's earlier mail to an arm stranded by a rail failure) while Conversation re-runs the attach-time walk that carries its corpus. Pinned by `libs/fauna-conversations/tests/index_catch_up_boundary_tests.rs` (attach + index that session's mail; the attach→backlog→boundary order; the running arm attached exactly once across a late attach), each mutation-verified.
- **Drafts are a SNAPSHOT KIND — the builder republishes the corpus and retires what came before (RULED + BUILT 2026-08-05).** The mail bullet above says a mutable kind owes its own dedup answer rather than copying skip-if-present. Drafts' answer is not a different *guard*; it is a different **build shape**, because the premise both candidate guards rested on is false. **The refuted premise, pinned before anything was built:** `Index::add_doc` upserts by content id, so re-staging an edited draft looked like it would supersede the old version — but that upsert is scoped to **one writer**. Once a segment is sealed and published, no later `delete_term` can reach into it: `open_multi_segment` copies each input in as-is, so the superseded text stays queryable from its old segment, and `merge_segments` does not collapse it either (neither input carries a delete for the other). Both facts are pinned by `libs/fauna-index/tests/cross_segment_supersession.rs`. So *no* stage-time guard — exempting the kind, keying by `(kind, id)`, or hashing the body — can make a user's deleted text stop matching, and a second failure has no append-side expression at all: a **discarded** draft would linger in the index forever. The shape that answers both: the producer hands the seam the **entire draft corpus** on every change (`MessageIndexObserver::observe_draft_corpus`, fired from `DraftStore` itself — the compose mutators are too many to be a chokepoint), and the flush publishes one segment holding it while **tombstoning every previously live segment of that kind** (`IndexBuilder::stage_snapshot` + the supersede arm of `plan_flush`). Consequences worth stating: the re-index guard is deliberately **not** consulted or populated for a snapshot kind (an entry there would pin each draft's first version forever), and what bounds at-rest growth is the rewrite rather than the guard — to **one copy of the corpus**, which is strictly tighter than the append kinds' "one copy per content id ever seen". Retirement stays **tombstone-only**, exactly as compaction's is. An **empty** corpus is a real event, not a quiet flush: it is how "the user discarded their last draft" reaches the index, so it writes a manifest with no segment. A corpus too large to seal under the one-blob ceiling declines to supersede and appends instead — stale copies stay queryable until a later flush carries the whole corpus, which is the pre-existing non-destructive failure mode rather than a partial corpus replacing a complete one. **The test for a future kind is not "is it small" but "can its content change after it is indexed" — refined 2026-08-05 by the posts ruling to distinguish its two halves.** *Change-in-place* forces the snapshot shape: stale text keeps matching and only a corpus rewrite can retire it. *Vanish-only* stays **append-shaped**: a deleted item's hit is dropped at resolve time (the class resolver reads the live corpus — § Where queries run), its at-rest posting residue is purged by the next versioned re-index, and a whole-corpus rewrite per delete would be pathological at post-history scale. So (`is_snapshot_kind`, total over `ContentKind` so a new kind must answer): drafts change and vanish → snapshot; contacts change in place → snapshot (ruled below); posts vanish only → append. **The per-segment doc accounting the 25 % tombstoned threshold reads is therefore NOT owed by this arm** (§ Where the index is built → *Thresholds* said S4 owed it): a snapshot kind never has more than one live segment, so neither compaction criterion can be what governs it. It becomes owed by the first *append* kind whose docs are superseded — which, on the shape ruled here, no currently planned kind is. **The corpus offer is never lease-gated (2026-09-25):** nothing re-presents it — the store offers it once per change and once at observer registration — so `Draft` has no catch-up window for a stand-down to bind; the ruling, the race it closes and the pin are [`content-index.md`](content-index.md) § Where the index is built → *The builder and the advisory task lease* (the stream-shaped sub-bullet).

- **Cursors are advisory; idempotence is structural.** Per-kind ingest cursors ride the owning manifest as an additive field (max-merge across builders); correctness never rests on them — `Index::add_doc` is an upsert by `content_id` within a builder, and the shared query seam dedups by `(kind, content_id)` across independently built segments. A lost cursor advance means re-ingest, never duplication in results.
