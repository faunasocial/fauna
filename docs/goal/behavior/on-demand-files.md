## On-Demand Files (Placeholders)

A folder can be marked **always-resident** (every file kept on disk) or **on-demand**. In on-demand mode a synced file appears in the platform file browser as a **placeholder**: it shows the right name, size, and modification time but occupies no local space until it is opened or the user picks "always keep on this device". Opening a placeholder **hydrates** it — the engine fetches that single file's chunks on demand and materializes its bytes — and the user can later **dehydrate** ("free up space") to reclaim disk while keeping the placeholder. Directory listings populate lazily, so browsing a folder never forces a full download.

**The choice is the user's, per folder, per device — and it is remembered.** That is the one promise every platform with a placeholder surface makes, whatever control carries it: on **windows** the per-binding `folder-location-mode-toggle` on the bound row flips *that location* between always-resident and cfapi placeholders (the mode is a field of the binding, `LocationConfig.mode`, persisted by the sync agent in its device-local `config.toml` — never nest state); on **macOS/iOS** the per-set `folder-on-demand-toggle` picks the set's one local presence (§ *Apple File Provider binding* — set-level by platform fact, default ON, yielding to a bound location; persisted in the device-local `FileProviderDomainPrefs`). The switch reads the same after the user leaves the page and returns, and across a relaunch, because the page re-reads the sync host's record rather than holding the choice in view state. **The default a fresh binding takes is platform-scoped, decided in the agent (user ruling 2026-09-26): a fresh windows binding starts on-demand — uniform with apple's default-ON and with the Files-On-Demand default a windows user already knows — while a bound location on every other agent-backed platform starts always-resident.** The one bind verb, the agent's `AddLocation`, gives a NEW path `LocationMode::fresh_binding_default()` (`bins/fauna-sync-agent/src/config.rs`): `on-demand` on windows, `always` elsewhere — on macOS a bound location is always-resident by design (§ *Apple File Provider binding*: the binding outranks the FP domain), and a fresh linux binding starts always-resident although its FUSE root can serve an on-demand one (§ *Linux FUSE binding*, the flips rule). So on windows the bound directory becomes a cfapi sync root the moment the folder-bind reconcile serves it (Explorer shows cloud-status marks on the user's own directory from the first moment; a big set costs metadata until opened; files already in the directory are uploaded and kept, never dehydrated by the bind), and always-resident is the deliberate second step via `folder-location-mode-toggle`. The default is for NEW binds only: a persisted binding keeps its recorded `mode` (the serde read fallback for a row lacking the field stays `always`, so nothing existing migrates). The app's e2e location channel (`InMemoryLocationControlChannel.FreshBindingMode`) mirrors the agent so the windows witness reads the same start. **The default is the agent's, whichever app binds:** a **tui** running on windows binds through the same agent and so gets an on-demand root — and flips it back from tui itself: tui renders the same per-binding `folder-location-mode-toggle` wherever its agent has a placeholder surface (the user's Rule A ruling, YES for tui, 2026-09-26), built on windows hosts, where the switch sends the agent's `SetLocationSyncMode` and reads the row's mode back off the agent's `ListLocations` (mirrored onto the shared `LocationBindingsModel` row, `BindingRow::mode`). The availability rule is shared Rust — `LocationBindingsModel::mode_toggle` (`libs/fauna-client-sync`), fed by the agent's status reply — and the linux app and tui both read it (tui folds the status reply on its `sync-agent-status` poll), so tui renders the switch on a windows or a linux host and none on macOS. **linux** takes the windows location-level shape — the same `folder-location-mode-toggle` on the bound row, the same `LocationConfig.mode` record — over its FUSE root (§ *Linux FUSE binding* carries the status; the toggle's ui.yaml scope grew to linux on the user's Rule A approval of 2026-09-26, built 2026-10-04); tui on a linux host renders no switch until its own arm lands. **android** takes apple's set-level shape — the same `folder-on-demand-toggle` — once its SAF binding lands (§ *Android SAF DocumentsProvider binding*, designed 2026-09-26, unbuilt; the toggle's ui.yaml scope growing to android is likewise a Rule A change asked of the user); until then android renders neither switch.

#### Sync direction: on-demand is a *storage* choice, never a *direction* choice (USER-ratified 2026-07-14)

**Always-resident vs on-demand decides how much of the set lives on this disk — nothing else. Both are two-way by default.** The placeholder vocabulary above is deliberately OneDrive's (hydrate on open, "always keep on this device", "free up space"), and it carries OneDrive's promise with it: a user who puts a folder under Fauna expects edits made there to reach their other devices.

- **Iron-clad — a change to a *tracked* file MUST be uploaded.** If a file is in the folder (it has a sync-state row; it carries a Fauna badge in the file browser), then a local modification to it **must** be uploaded. **No mode, folder setting, or platform host may suppress this**, and no such setting may be offered. A client that badges a file as synced and then silently discards the user's edit has told the user their data is safe while dropping it — a direct breach of *User always controls their data* (`../principles.md`). Where the host cannot observe local writes, that is a **bug in the host**, not a licence to drop the edit: the host must acquire the capability (on Windows, the cfapi `NOTIFY_*` callbacks it does not currently register; see *Implementation status today*).
- **New files are adopted.** A new file placed in a synced folder joins the folder and uploads. There is **no mode, and no badge, for "don't upload new files"** — a *"synced folder that doesn't sync some of your files"* is a surface a user has to hold in their head, and it earns its complexity only if a real need appears (USER-decided 2026-07-14: dropped, deliberately, in favour of making two-way work).
- **Mixed folders — an open future question, with nothing reserved for it.** A folder holding a mix of synced and non-synced files is a coherent thing to want, and if it is ever built it will need its own design (including how a user *sees* which files are excluded). It is **not** a deferred half-built feature: no setting, no badge state, and no overlay-handler budget is being held back for it today.
- **This supersedes the "download-only" clause** that appeared as a parenthetical in `file-versions.md` § Restore ordering rule 3. That clause was never a designed product decision: it was asserted in passing inside an *ordering* rule about a different concern, given no rationale anywhere, and contradicted by the two-way placeholder UX this section describes. It documented what the Windows cfapi host happened to do — it registered only the OS→provider *read* callbacks and so could not see local writes — and that implementation fact was then cited back as intent. The tell is the promise the code itself makes at the invalidation gate ("a later reconcile pass resolves the conflict"): someone knew local edits would happen and would need resolving. Direction is now decided here, in the section that owns it.

#### A placeholder is *present-but-unreadable* — never hash it, never take it for absent (measured 2026-07-14)

A cloud-only placeholder is a file the engine can **see but not read**, and every scan/upload path must hold both halves of that at once. Getting either half wrong breaks the root, in opposite directions — both measured against a live cfapi sync root, not inferred:

- **Never read one.** A cloud provider fires **no fetch callback for I/O originating in the provider's own process** — and the sync host *is* the provider. So the host's own read of its own placeholder is answered by nobody: it blocks for the platform's full recall timeout (**60 s** on cfapi) and then fails (`ERROR_CLOUD_FILE_REQUEST_TIMEOUT`). It does **not** read as empty — `metadata.len()` is the file's *real* size — so there is no "upload emptiness over the nest's copy" hazard. The hazard is **liveness**: those 60 s burn on the single driving thread that also *serves* hydration, so an N-placeholder set spends N × 60 s unable to hydrate anything while still logging "reconciliation complete". A hash-and-upload pass over an on-demand root therefore does not corrupt the nest; it silently **kills the root**.
- **Never mistake one for absent.** A placeholder is *present*. A scan that simply omits them makes the reconcile's delete-detection see a `Synced` row with no file behind it and record a **delete on the nest**, propagating the deletion to every other device — and the user reaches exactly that state through Explorer's ordinary *"Free up space"*. **Freeing disk space must never mean erasing the file.** This is the real data-loss path, and it is *created* by the naive remedy for the stall above. Which rows the mass-delete floor counts on a root of placeholders, and why the lazy population makes that restriction load-bearing, is [`delete-propagation.md`](delete-propagation.md) § *A wholesale-vanished folder* → *The floor on an on-demand root*.

So the scan **reports** placeholders and **flags** them: skipped by the hash/upload path, counted by the delete path — and which placeholder rows the delete path may count, live or across a downtime, is [`delete-propagation.md`](delete-propagation.md) § *A wholesale-vanished folder* → *The floor on an on-demand root* (rule (2) and *An offline placeholder delete propagates*). The client detects them from ordinary OS file attributes (on Windows `FILE_ATTRIBUTE_OFFLINE` / `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`), which a hydrated file no longer carries — so the guard cannot suppress the very uploads two-way sync exists to deliver.

**The empty-file special case — a 0-byte placeholder is present-and-empty, and badges `Synced` (measured 2026-07-15; implemented).** A 0-byte file has no bytes to fetch, so on an on-demand root the platform fires **no** fetch callback when it is opened — on cfapi, opening a 0-byte placeholder *clears* its `OFFLINE`/`RECALL` bits (the file is genuinely present-and-empty on disk) but delivers **no** `FETCH_DATA`, so the mark-hydrated step that flips a normal file to `Synced` never runs. The row therefore can never leave `Placeholder` via the fetch path. It is **not** promoted to `Synced` at population either: a `Synced`-while-not-yet-materialized row would be erased by reconcile's delete-detection (which scans `Synced` rows for on-disk absence) — a data-loss trap. So the engine row **stays `Placeholder`** (carrying the empty-content identity, so a later reconcile that finds the file present-and-empty leaves it stable rather than re-uploading it), and every **badge** reads it as `Synced` through the shared size-aware mapping `SyncState::effective_for_size(size_bytes)` — a 0-byte placeholder is present-and-empty, not cloud-only. A folder whose only tracked descendants are 0-byte files therefore reads `Synced`, not `CloudOnly` (the folder-badge fold applies the same mapping). Keeping the rule in shared Rust — not in a per-platform fetch callback — means a macOS File Provider inherits the identical empty-file case (priority #2).

The placeholder *surface* is platform-specific (Windows Cloud Files API, macOS File Provider, a Linux FUSE/overlay), but the **hydration primitive is shared**: `fauna_sync_engine::SyncEngine::download_file_bytes(relative_path)` resolves the file's recorded manifest from the state DB and returns its reassembled, decrypted bytes — the platform's fetch callback hands those to the OS. See `docs/goal/architecture/apps/windows.md` § Shell Extension for the Windows cfapi binding.

**The three surfaces are all built, not equally far — the Linux FUSE root is the youngest (direction decided 2026-09-26; the agent's root built 2026-10-01/02, the linux app's switch 2026-10-04).** Windows' cfapi provider and Apple's File Provider are live (see the status paragraphs under § *Apple File Provider binding*); the **Linux FUSE mount is a ratified design built through its lifecycle** (2026-10-02: it mounts, lists, hydrates on open, passes every other operation through, frees space, keeps pins, flips both ways and is unmounted by a crash guard after a crash; the linux app renders its switch, tui not yet) — § *Linux FUSE binding* below is its owner and carries the status. So a Linux location binding starts always-resident and goes on-demand by the bound row's switch: `tests/e2e-unified/ui.yaml` § `folders` scopes `folder-location-mode-toggle` to windows, linux and tui-on-a-windows-host, and `folder-on-demand-toggle` to macos+ios. What the linux root does not do yet is named in § *Linux FUSE binding*'s status paragraph. The direction question that stood here until 2026-09-26 — build a real placeholder provider, or declare linux always-resident *by design* — was answered by the user: **build it**, with the `fuser` crate and the distro `fusermount3`.

**Who runs the hydration host, and the keys it holds.** The fetch callback must *decrypt* the file's chunks, so whatever process serves hydration must hold a decryption key — and the placeholder surfaces (Windows cfapi, macOS File Provider) run in **separate, out-of-app processes** from the identity-holding UI. Per the key-hierarchy doctrine that keeps the identity seed on user-trusted full clients only (`docs/goal/architecture/key-material-hierarchy.md` § Roots + rule #6) and hands content-serving helpers a *minted, least-privilege capability* rather than the root (rule #7 — the blast-radius invariant, realized for mail by the MDA bridge's MSEK), the hydration host is **never given the identity seed**. It runs in the user's logon session — so it shares the identity-holding app's trust boundary (handing a same-session helper a derived key adds no attack surface the seed-holding app in that session doesn't already present) — and the app provisions it with the narrowest capability that suffices:

- **Phase 1 (today's at-rest shape).** Ordinary file chunks are sealed under the owner's `BackupKey` (§ Content-Addressed Storage; `owner-key-material.md` § Audience: owner only Path A), the *only* key that opens them — so the app hands the host the `BackupKey` plus a renewable nest bearer. `BackupKey` is broad (it opens *all* of the user's owner-only content) and un-revocable short of seed rotation; that breadth is acceptable **only** because the host shares the app's user-session trust boundary. It must never be handed to a more-exposed context (a LocalSystem service, another machine).
- **Phase 2 (target).** When per-folder keys land (the `chunk_crypto` / MLS-`epoch_secret` path, `mls-group-key-material.md` § Audience: an MLS group; forward-looking today), the host is handed only the on-demand folder's key — a narrow, revocable capability, doctrinally identical to the MDA bridge's MSEK. This is the end state; Phase 1 is the expedient the same-session boundary makes safe. How a Phase 1 host comes by a *shared* set's keys, and the one constraint that already binds Phase 2's delivery, are § *Shared sets on a capability host*.

This is the **uniform cross-platform shape** for on-demand file providers: the identity-holding app holds the seed and full authority; the out-of-app hydration host (Windows cfapi helper, macOS File Provider extension) is a same-user, session-scoped delegate holding only a minted decryption capability — the same "app provisions a capability to a helper" pattern fauna already uses for the mail bridge, not a per-platform invention.

**Hosting multiple on-demand folders (multi-root).** A user may mark more than one folder on-demand, and **each on-demand folder is its own folder** (§ Selecting Folders to Sync — one folder ↔ one named folder). The on-demand host therefore serves **N folders concurrently — one provider root per folder** (a Windows cfapi sync root, a macOS File Provider domain, a Linux FUSE mount), each backed by **one bearer-only `SyncEngine` keyed by folder**, each scoped to that folder's changes (the engine is built `folder = Some(name)`, so it folds *only* that set's `changes.list` into placeholders — never the actor's whole change history under one root), with a **per-folder state DB** (`fsid-<ref>.db`, keyed by the set's identity — the next paragraph) and a **single shared device id** (`device.db`) so the nest sees one device, not N. All engines share **one** least-privilege capability — in Phase 1 the owner `BackupKey`, which decrypts every folder's chunks, so multi-root needs **no** additional keys; Phase 2's per-folder key narrows this to one capability per engine.

**A location binding identifies its set by a `FolderRef`, not by name (BUILT 2026-07-29).** Folder names are unique only **per owner** (the nest enforces `UNIQUE(name, actor_id)`), so a user who owns "docs" *and* is a member of someone else's "docs" cannot say by name which of the two a location is bound to. Every seam that must tell one running engine from another therefore keys on `fauna_core::folder_keys::FolderRef` — the engine registry, the pushed engine-key blob entry, and the per-set state DB — and it has two structurally disjoint arms: **`Local(<nest folders.id>)`** for any set with a row on this holder's own nest (owner-only, owner-shared, served, *and* same-nest member rows), and **`Foreign(<derived ChannelId>)`** for a cross-nest set, which has no row here at all. The rule is chosen by *where the set lives*, never by the caller's role in it, and is resolved in one shared place (`fauna_client_folders::engine_binding::folder_ref_for_row`) so the apps cannot drift on it. The same one-resolver discipline holds on the agent's own IPC surface: the absolute-path router (`path_map::resolve_to_folder_rel`) carries the binding's ref, so the overlay-status, folder-badge, dehydrate-record and restore-re-point reads all open the identity-keyed state DB the engine actually writes — never a re-derived name-keyed path (the four readers' name-keyed drift was fixed 2026-07-29). The ref is **stable across the set's lifecycle** — becoming shared, or having the WebDAV serve flag flipped, does not change it — which is what lets an existing binding survive those transitions.

**The ref is the binding's only key; the name is a label.** There is one bind verb — `SetLocationFolder { path, folder, folder_id }` on the app↔agent IPC, with `folder_id` required and refused unless it parses — and every seam downstream of it resolves by the ref alone: the agent's `config.toml` row is read as bound only when it carries a label **and** a parseable ref (`LocationConfig::binding`), a `FolderEngineKeys` blob entry must carry the ref (an entry without one is refused at decode), and a blob with no entry for the bound ref answers **unbound (fail closed)** — the only same-named candidate would be a different set, precisely the wrong answer the ref exists to refuse. A row `folder_ref_for_row` yields no ref for (a cross-nest row with a malformed group id) is **refused** at the bind gesture, on the page's error surface, never bound by name. Per-set state DBs live in their own `fsid-<ref>.db` filename namespace. The verbs that still address a set by name (`PullFolderNow`, `ApplyHeldDeletes`) are only a lookup into this device's bindings — one binding wearing the name resolves to its ref, several are refused as ambiguous, none is "not served" — never a name used as a key. The seat's per-tick policy read (`fauna_sync_engine::config::resolve_device_mode_from_nest`, which carries the audience, residency, website, selective-sync and exclusive-editing facts off one `fauna.folders.list` read) resolves its row by the same key (`binding_edge::SeatRowKey`): an engine by its binding's ref, and one holding no ref reads no row — every field's sealed / fail-closed direction; the headless daemon, whose wiring named only the set, read a row only while exactly one listed row carried that name, and read none — sealed — when the user owned a set of the name *and* was a member of another (until its removal, 2026-10-02). A member seat on a shared "docs" therefore never adopts its user's own public "docs" and arms the plaintext upload arm on the shared set. The name-keyed binding a pre-identity peer used (the ref-less verb, the name fallback in every resolver, the `fs-<name>.db` adoption rename, the `location-map.json` migration seeds) was retired in place 2026-09-24 by the compat-remnant sweep ([`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 2, the fourth exception). **Status:** built on the shared seam, the agent, linux, tui, windows and macOS (every app's bind gesture resolves the ref through the shared `folder_ref_for_row` — `FaunaFfiMethods.FolderRefForRow` on windows, `FolderSummary.folderRef` on macOS — and calls `bind_location(path, folder, folder_id)`); iOS has no location-binding surface of this kind (its File Provider domain binding is a separate mechanism, unaffected); android has no location-binding surface. The in-app `FfiSyncEngineHost` binds no location either: its resident half (`start_engine` over a `location-map.json` whose `folder_id` was optional) was retired 2026-09-25, since nothing called it. **The in-process hosts are ref-keyed too (built 2026-09-25):** that host's construct-run-drop calls — the library-ingress `ingest_file`, the `file_states`/`transfer_backlog` reads, the `sync_file_states` steward read, the `sync_set_unrecorded_rels` removal gate — and the File Provider host's constructor take the set's `FolderRef` wire string (`folder_id`, refused unless it parses; `fauna_ffi::sync_engine_host::parse_folder_id`); `engine_lifecycle::build_engine` opens `fsid-<ref>.db` (`FolderRef::state_db_path`, the one join every writer and cross-process reader shares) and resolves the set's row by identity (`summary_for_ref` over this nest's own list — a cross-nest ref, or a ref the list does not carry, refuses), taking the set's name from that row; the photo-library resolver (`photo_library_set`) returns the set's identity beside its name and binds the device by identity, so a renamed photo set stays the target; the Media page snapshot carries each filter option's identity (`folder_options`) so a badge read keys on it. No app hands a name to these seams: android's watched-directory row stores the ref of the set the user picked from their own folders (`ownFolderChoices`, each row's ref through the shared `folder_ref_for_row`), so a rename of that set keeps the directory feeding it; the ref is required at rest (`watched_directories.folderId` is `NOT NULL` since Room schema 9), and the one-time resolution of a ref-less row from its name label was retired 2026-10-01 as a compat remnant ([`../architecture/compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md), the early audit pass's reading (1)).

The host multiplexes its N engines exactly the way the Linux in-process client already does (`apps/linux.md` § File Sync): a **single driving thread with a current-thread runtime polls every engine future inline** (the engine is `Send` but `!Sync`), keyed by folder, with **live start/stop** so marking a folder on-demand (or back to always / removing it) adds or drops one provider root without restarting the others. This multiplexer is the **shared `fauna_sync_engine` multi-engine driver**, generic over the per-engine loop and a per-engine teardown: Linux supplies an always-resident watcher loop (teardown = drop the `FsWatcher`/inotify); the on-demand host supplies a hydration-command loop and registers an OS provider root per engine (teardown = unregister the provider root + drop its callback-routing entry). The platform's fetch/enumerate callbacks route to the right engine by the provider root's identity — **on Windows the cfapi `CF_CONNECTION_KEY`**, on macOS the File Provider domain identifier. The uniform shape is thus: **one shared multi-engine driver + the shared `download_file_bytes` primitive**, with each platform contributing only its OS provider-root binding (cfapi / File Provider / FUSE) and the per-root callback routing — never a per-app driver. One carve-out, ratified with the Apple binding (2026-07-18): a **control-inverted** provider surface has no driving loop for the shared driver to drive — `fileproviderd` itself instantiates one extension object per domain and routes callbacks by domain identifier, so the Apple extension holds one independent request/response host per domain (§ Apple File Provider binding, *the extension hosts the engines*) and the shared multi-engine driver applies to the *self-driving* hosts (the Windows cfapi service, Linux, a future FUSE root).

#### Apple File Provider binding (ratified 2026-07-18 — design record tracked internally; M0 packaging skeleton built 2026-07-18, engine-backed binding M1–M5)

macOS and iOS realize the on-demand surface as **one shared `NSFileProviderReplicatedExtension`** serving a **Fauna location** in the Finder sidebar and the Files app — **one File Provider domain per folder this device accepts** (domain identifier = the set's **actor-scoped** `FolderRef`, `<ref-component>@<actor-id-hex>` — `local%3A1@…`, the callback-routing identity named above, scoped to the account since 2026-09-25 and its ref half percent-encoded since 2026-09-29 (*the actor-scoped device identity*, below); the set name is only the display name — the `fauna.sync.changed` nudge, which carries the set's own name or its name hash, is matched to a held set through the shared rule (`sync_changed_names_set`, against `PresenceSet.set_name`) and signals that set's domain by its identifier, never by the display name, which for a shared set carries its owner), each domain backed by a `folder`-scoped engine over the same shared `EngineHost` driver. The OS supplies placeholders, hydrate-on-open, *Download Now* / *Remove Download*, badges, and progress natively. Eight binding-specific rules:

- **Control inversion — the replicated FP calls the provider; there is no watcher and no disk scan on this surface.** The OS owns the on-disk tree (under the system-managed `~/Library/CloudStorage/` location) and calls the extension: enumerations serve the engine's row fold (the same batch-latest-per-path fold placeholder population uses; item `contentVersion` = `recorded_content_hash`), `fetchContents` = `download_file_bytes` + `mark_hydrated`, local user changes arrive as `createItem`/`modifyItem`/`deleteItem` and drive the **sealed per-file ingest** (the photo-ingress path) + `changes.record` / tombstone, observed eviction drives `mark_placeholder`, and a pulled remote change signals the enumerator. The placeholder-vs-absent and never-read-a-placeholder hazards structurally cannot arise here.
- **The recorded-head gate manifests as the upload ack.** The extension acknowledges a local change to the OS **only on `UploadOutcome::recorded`**; the OS never discards a local copy whose upload is un-acked. Same key (`recorded_content_hash`), same invariant as `is_dehydration_safe` — an un-recorded edit is un-evictable by construction.
- **The extension hosts the engines.** `fileproviderd` launches it with the app dead and iOS has no daemons, so the extension runs the per-set engines in-process via FaunaFFI, with state (`fsid-<ref>.db`, shared `device.db`) in the app group container — **state unification (ratified 2026-07-19; re-ratified per CONSENT DOMAIN 2026-08-25): ONE apple state dir per consent domain, `<domain root>/sync/<actor-id-hex>` (per-actor since the Multi-account consequence-3 landing below), and each set's engine state lives in its HOST's domain root.** iOS has one domain (the sandboxed app and its extension share the app-group container). macOS has **two**, because macOS 15+ puts `~/Library/Group Containers` under `kTCCServiceSystemPolicyAppData` and a launchd-spawned background process is prompted there on every instance with no user decision ever binding the next one (measured: `../architecture/installers/macos.md` § Identifier domain, record item 5): the **user domain** (`~/Library/Application Support/Fauna/sync` — the platform state base of `../architecture/account-data-plane.md` § The account store, the root of the external `fauna-sync-agent`, fauna-tui, and the unsandboxed app) and the **container domain** (`<app-group>/sync` — the root of the sandboxed File Provider extension, which can reach nothing else). The rule that makes two roots one law: **a process never opens a root outside its own domain** (the agent never touches the container; the extension cannot touch the user domain), and **no set's state is ever needed across the two** — the one-local-presence arbitration below gives every set exactly one local host, and a host switch (FP domain ↔ bound folder) re-derives the replica from the nest for a *different* local root rather than carrying the old `fsid-<ref>.db` (the FP domain's replica paths mean nothing to a bound folder, and vice versa); `device.db` is not a coupling point either, since on macOS both hosts take the device id from their provisioned credentials. The one process that spans both domains is the unsandboxed **app**, which is the container's *steward*: it writes `domain-owners.json` and the extension's pin replica there and reads the FP-bound sets' `file_states` there, while everything of its own — its one-shot engine host (restore and state reads on macOS; the photo set's ingest on iOS, where the container is the app's only domain), its `location-map.json`, its deployment-seed `config-replica` — and its reads of the agent-hosted sets' `file_states` (or `GetFileStatus` over IPC) live in its own domain, the user domain. A Media-badge fold spans both roots (**built 2026-08-25**: `SyncStatesStore` routes each set by the registered FP domains — a set with a domain is read from the container, every other set from the host's root — and the shared read `sync_file_states` is pure, never minting an `fsid-<ref>.db` for a set the device hosts nowhere; `SyncStateDir.Domain` is the Swift home of the two roots, the user-domain base taken from shared Rust's `platform_state_base()`). Pre-unification state is adopted **copy-never-destroy** via the shared `migrate_state_dir` (SQLite-backup snapshots, first-writer-wins, sources never touched — each process adopts the legacy dirs its domain can reach; the 2026-07-19..2026-08-25 container-resident *agent* state reached no user machine — no signed artifact shipped it — and is left untouched on the dev boxes that hold it). One writer per set = the hosting process (guaranteed by the one-local-presence arbitration below); the app reads `file_states` cross-process for Media badges (WAL + busy-timeout make the cross-process reads safe). It is exactly the out-of-app hydration host of *Who runs the hydration host* above: provisioned `BackupKey` + a renewable bearer via the shared app-group Keychain, never the identity seed; a shared set's content keys are not provisioned beside them — the host loads them from custody itself (§ *Shared sets on a capability host*, decision 1). The OS is the multiplexer on this surface: `fileproviderd` instantiates one extension object per domain, so the extension holds one independent `FfiFileProviderHost` (engine + current-thread runtime + bearer connection) per domain — the shared `EngineHost` driver is deliberately not used here, since it exists to drive self-driving loops and a control-inverted host has none (carve-out recorded in § *Hosting multiple on-demand folders*). N such folders ⇒ N per-domain hosts in the one extension process, matching the windows N-engines-per-service resource shape (per-set engine + per-set connection).
- **Apple's on-demand is set-level, not location-level (platform fact, sanctioned deviation from the windows folder-mode shape).** An FP domain cannot take over an arbitrary user directory, so per set per device there is exactly **one local presence**: none (RemoteOnly), a bound always-resident location (the location map, unchanged), or the Finder/Files domain — never two (two engines writing one set from one device id would fight). The UI affordance is the per-set `folder-on-demand-toggle` (`ui/folders.md` § Binding), not `folder-location-mode-toggle`. **Arbitration precedence (ratified 2026-07-19): a bound location outranks the on-demand toggle.** The binding is an explicit user act with a chosen on-disk location, the toggle is the ambient zero-config default — so a bound set never gets an FP domain (the domain yields *before* the binding's resident engine starts), and unbinding lets the toggle decide again (the domain reappears, default ON). Enforced in the shared `FileProviderCoordinator.reconcile` (`desiredDomains` = own folders this device accepts in ∩ toggle-enabled ∖ bound — the next bullet's rule) — the decision itself now has its shared-Rust home, `fauna_folders_machine::on_demand_presence` (§ Android SAF DocumentsProvider binding), which the coordinator migrates onto; iOS has no binding surface, so there the rule reduces to FP-domain-or-RemoteOnly.

A place with `accepts: false` gets no domain either — delivery is switched off for that seat ([`file-sync.md`](file-sync.md) § 4), so a domain would show a tree that never updates. - **Multi-account × File Provider (ratified 2026-07-19): the FP surface is serialized single-account — the active account only.** The account model everywhere is a serialized switcher (one active identity per running client; switch = teardown + relaunch — owned by `../architecture/long-term-store.md` § Multi-account evolution), and every out-of-app sync host already follows it: the external sync agent is unprovisioned on **every** session-teardown path and re-provisioned by the incoming session's launch. ⚠ **Read "is unprovisioned" as *is asked to unprovision, and made to reconcile if the asking fails*.** The teardown is enforced by exactly **one best-effort local RPC per teardown path**, and what it revokes is built to outlive it — the capability persists in the secure store, the bearer self-renews app-dead off a renewal grant that deliberately carries **no expiry**, and both resume across reboots. So a lost message (a *wedged*, not dead, agent at the teardown instant; a connect timeout under load) leaves the signed-out account's engines serving. That case is no longer unbounded: the app records the sign-out durably **before** sending the message, and the agent revokes itself against that record — `../architecture/apps/sync-agent-credentials.md` § Credential model → *The signed-out reconcile* owns the mechanism, its ordering rule, and its limits. The File Provider surface follows the same shape, not a per-account one: per-set domains exist for the **active** account's own accepted folders only, and the shared-Keychain capability store is deliberately **single-slot** (the active account's `BackupKey` + renewable bearer; `provision` is delete-then-add). Per-account credential slots are rejected on purpose — they would keep app-dead engines serving a switched-away identity with no live session to renew its bearer, drive its arbitration inputs, or answer for it in the UI, a concurrency no other app surface offers (priority #3). Three load-bearing consequences: **(1) a switch tears the FP presence down before the new session starts** — `tearDownSessionForSwitch` runs the same `FileProviderCoordinator.signOut()` teardown as sign-out (every domain removed, capability revoked), exactly as it unprovisions the sync agent, then the incoming account's launch reconcile re-provisions and re-adds *its* domains (a switch-back re-populates placeholders from the nest — metadata-cheap by design); without this the outgoing account's domains keep serving while the single slot is re-provisioned under the incoming identity mid-flight. **(2) Domain removal preserves dirty data on every path — on macOS** — the one shared `FileProviderDomains.remove` uses `.preserveDirtyUserData` there, so an un-uploaded local edit under a removed domain (toggle-off, bind-time yield, sign-out, switch) is moved aside by the OS, never destroyed: the removal-shaped hole in *the OS never discards a local copy whose upload is un-acked* is closed at the single choke point every caller inherits. **iOS platform limitation (discovered at build, 2026-07-19): the iOS SDK marks BOTH `DomainRemovalMode` preserve cases unavailable** (the doc pages claim iOS 16+; the headers refuse — the compiler is the authority), so iOS removal is necessarily plain; the iOS-side guard is an **upload-drain gate before removal** (refuse/drain while un-recorded rows exist — the reviewer's alternative fix shape) — **BUILT 2026-07-19**: `FileProviderDomains.remove` on iOS throws `FileProviderRemovalRefused` while the set's state DB holds un-recorded local edits (engine seam `db::set_unrecorded_rels` — mid-flight states plus the record-failed `Synced`-without-proof shape, tier-1-pinned, fail-closed on an unreadable DB), leaving the domain registered so the OS's own pending-change retry drains them; sign-out holds the capability while any refusal is pending (revoking would strand the drain behind a fails-closed extension) and retries on the next reconcile. The companion **domain-owner record** (`domain-owners.json` at the flat state base — written by the app when it adds a domain, **backfilled at every reconcile only where no owner is on record**, cleared on successful removal, read by the extension at host build) keeps a dirty domain lingering across an account switch from ever being served — or its queued edits ingested — under the incoming account's single-slot credentials: the extension fails closed (`foreignDomainOwner`) and the drain resumes when the owning account signs back in; the removal gate likewise consults the *owner's* scoped state, not the currently-provisioned account's (the owner read from the identifier itself since 2026-09-25). **Foreign-owner rule (ratified 2026-09-25): a desired set whose domain identifier is registered under a DIFFERENT account on record is neither adopted nor re-recorded.** The incoming account's reconcile leaves that domain and its owner record alone, logs the hold, and adds its own domain on the first reconcile after the owner's drain has completed and the domain is removed (the owner's next sign-in drains it; its sign-out or switch then removes it) — the incoming set waits without a domain, which is the fail-closed direction. The collision was ordinary, not exotic, while the domain identifier was the bare `FolderRef` wire string — a `local:<id>` ref is unique per *nest*, not per device, so two accounts on two nests routinely both want `local:1` — and the record, not the identifier, was what told them apart; since 2026-09-25 the identifier carries the account (*the actor-scoped device identity*, below), the collision cannot arise for own-nest refs, and the rule stands as defense in depth over the record. Residual exposure, accepted: an edit still pending in the OS's replicated queue that never reached the extension at all (no DB row — e.g. the extension never ran while offline) is invisible to the gate and is discarded by a removal. **(3) Per-account sync-state scoping — BUILT 2026-07-19**: per-actor subdirs `<app-group>/sync/<actor-id-hex>/`, derived identically by all three processes through the one shared Rust rule (`db::actor_state_dir` — the app's `SyncStateDir.resolveShared(actorIdHex:)` from the session's actor, the extension from its provisioned credentials, the agent by scoping `SyncPaths::base_dir` — its binding-store `config.toml` included — from its provisioned capability at restore/provision time, unscoping at unprovision), so two accounts can never share a `fsid-<ref>.db`, `device.db`, a location map, or agent binding store. Nothing is adopted into a subdir from the flat base: a state file sitting flat there records no owner and is no account's (the first-adopter adoption that once copied the pre-scoping layout into the active account's subdir, stamped by a `state-owner` marker, was retired by the compat-remnant sweep — [`../architecture/compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md) § Program 4, tranche B1). Activation is apple + windows + **linux (LANDED 2026-07-22)**, on **every layout — the production base and a `--data-dir` override alike (ratified 2026-09-26)**: the override only relocates the flat base and the scope nests under it, so an e2e agent runs the real code path on every platform. The earlier carve-out that kept `--data-dir` layouts flat (so harnesses kept a fixed layout, e2e-launch-isolation.md § point 10) is RETIRED: windows is the one e2e layout that passes `--data-dir` (the agent's default root is the machine-global `%LOCALAPPDATA%`, so the app- and tui-spawned agents are pinned to a per-launch dir), and the flat agent there shared one binding store and one `fsid-local-N.db` across every account a test module signed in — a `local:<id>` is unique per nest, two fresh nests both mint `local:N`, so a later account inherited the earlier one's per-folder pull anchor and skipped its own nest's first changes. The e2e readers never depended on flatness (`helpers/sync_agent_config.py` globs flat then per-actor); only the process-level dirs stay at the flat base (the log dir, a `--data-dir` trust store). linux has no `--data-dir` test mode at all (`account-scoping.md`'s gap-ledger row has the full account). **Windows (LANDED 2026-07-21) conforms to the consequence-1 uniform shape "every out-of-app sync host is unprovisioned on every session-teardown path": it now sends `UnprovisionCapability` (the unit-variant teardown signal added to its C# IPC encoder) on BOTH teardown paths — `SignOutHandler` (after stopping the convergence loop, so its next tick can't re-provision from the still-loaded crypto) and `SwitchAccountHandler`'s step-4 teardown (awaited before step-5 re-provisions under the incoming identity — macOS's `switchAccount await FileProviderCoordinator.signOut()` ordering) — so the agent drops the capability, clears its per-actor scope, and stops engines, and never keeps serving a signed-out / switched-away account. - **The actor-scoped device identity (ratified 2026-09-25; the ref half percent-encoded 2026-09-29): every per-set registry a DEVICE keeps for this binding is keyed by the set's ref scoped to the account — `<ref-component>@<actor-id-hex>`, `local%3A1@<hex>` — never by the bare `FolderRef`.** A `FolderRef` is unique per *nest*, not per device (`local:<id>` is that nest's `folders.id`), so two accounts on two nests routinely both own `local:1`, and a device-wide registry keyed by the bare ref hands one account's presence to the other. Three registries collided this way and all three take the scoped key, and a fourth follows it: **(1) the domain identifier** — `FileProviderDomains.add/remove/list` register, remove and list scoped identifiers, the reconcile's plan matches desired sets against them, and the extension recovers both halves from the domain it was built for; **(2) the staging root** — `<group>/FileProvider/roots/<actor-id-hex>/<ref-component>`: the identifier's `@` boundary IS the directory boundary, account outermost (the same per-account nesting as `<group>/sync/<actor-id-hex>/`), and the identifier's ref half IS the directory's name — the ref as one percent-encoded component (`local%3A1`: shared Rust's `FolderRef::path_component`, the one encoder android's owned-tree roots key by too); **(3) the on-demand-toggle preference** — the shared-Rust `OnDemandPrefs` store (`FileProviderDomainPrefs` its wrapper), keyed by the scoped identifier, so it is per set per *account* per device, which was always the intent; **(4) the domain-owner record** (`domain-owners.json`, consequence 2 above) — keyed by the identifier and cleared on every successful removal, so it follows the identifier through the removal path with no step of its own. The grammar has exactly one home, shared Rust's `fauna_core::folder_keys::ActorScopedFolderRef` (`to_wire`/`parse`; FFI `actor_scoped_folder_ref` / `actor_scoped_folder_ref_parse`, which hand back the identifier, both halves and the ref component together), and FaunaKit's `FileProviderDomainIdentity` is its only wrapper — no Swift spells the separator or the ref's encoding. **The ref half is percent-encoded (ruled 2026-09-29): iOS refuses a File Provider domain identifier carrying `/` or `:` — measured 2026-09-27 on the iOS 26.5 simulator, `NSFileProviderManager.add` on `local:1@…` answers `NSPOSIXErrorDomain` 22, "Domain identifier … may not contain any of the characters '/:'" — so the bare wire's `:` cannot appear in it; the staging root's one-component encoding was chosen over a fresh `-` spelling because it makes identifier and directory one spelling and moves no root on any platform, and the encoder's alphabet (alphanumerics and `-_. ` pass, every other byte `%XX`) means the identifier is alphanumerics, `%` and the one `@`.** `@` was chosen because neither half carries it and it is path-safe everywhere: an OS registry may key a directory by the identifier, so `/` — which would have read naturally as the staging-root nesting — was rejected; the ref leads so a log line shows the set before the 64-char account. `parse` accepts exactly what `to_wire` emits: the pre-2026-09-29 spelling `local:1@…` and any escape the encoder would not write are refused like a bare ref, so a domain macOS registered under the old spelling (iOS never could) takes the un-gated unscoped-removal path below, its staging root byte-identical before and after (the roots always encoded the ref), and a `disabled` entry the toggle store holds in the old spelling is an **inert orphan** — never matched, never re-keyed, never swept; the choice is one tap to make again, and no dev box held a domain or a prefs file when the spelling changed. **Seam rule:** the apps feed the coordinator BARE refs (own-nest `FolderResponse.folderRef`, the same key the binding surfaces use — `FileProviderSyncSet.folderId` stays bare), the coordinator scopes each one exactly once (`desiredDomains`), and the Rust host constructor and the drain seam keep taking the bare ref recovered from the identifier. **Gate rule:** the iOS upload-drain gate parses the identifier to its halves and consults *that* account's scoped state for *that* set — never the raw identifier's validity as a `FolderRef`, which a scoped identifier fails — so a scoped domain with un-uploaded edits still refuses removal, and the gate no longer reads the owner record (the account is in the identifier). An identifier that scopes no set to any account — a bare ref or a set name from before actor scoping, or the pre-2026-09-29 spelling with the bare `:` in the ref half — is never served by the extension (`unscopedDomainIdentifier`, fail closed) and is removed by the next reconcile as undesired, *un-gated*: nothing under it can drain, so gating it would only wedge it and the sign-out capability hold behind it; no adoption, under the 2026-09-24 baseline reset. **Consequence for the foreign-owner rule above:** the identifier collision it worked around cannot arise for own-nest refs — two accounts' `local:1` are two identifiers, one added and the other left to the gated removal — and the domain-owner record is demoted to defense in depth: the extension's structural guard compares the identifier's account with the provisioned one *before* reading the record, and the plan's foreign-hold arm is reachable only through a corrupt or hand-edited map, and stays. **BUILT 2026-09-25; the ref half re-spelled 2026-09-29**; headless pins: `FileProviderDomainIdentityTests` (the shape — carrying neither `/` nor `:` — distinct per account, the staging roots spelled as the identifier's ref half, the per-account toggle, the drain gate's decision, the old spelling refused and un-gated), `FileProviderReconcilePlanTests` (two accounts' `local:1` never collide; a pre-scoping or pre-encoding identifier is removed, not adopted), `SyncStatesStoreTests` (the Media-badge fold routes only the active account's domains to the container), android's `FaunaDocumentsProviderTest` (the document-id grammar over the live spelling) and the shared-Rust `folder_keys` pins (the alphabet, the one encoder, the old spelling refused). Before the re-spelling **no iOS domain for a real set had ever registered** — the reconcile logged the refusal and continued — so iOS had nothing to migrate. #### Linux FUSE binding (ratified 2026-09-26; S1–S4 — mount, hydrate on open + pass-through I/O, dehydrate + pins, flips + the crash guard — BUILT 2026-10-01/02, the app toggle (S5) BUILT 2026-10-04)

Linux realizes the on-demand surface as a **FUSE filesystem the per-user `fauna-sync-agent` mounts over the bound location** — the windows *location-level* shape (`folder-location-mode-toggle` on the bound row, `LocationConfig.mode` in the agent's `config.toml`, the one `SetLocationSyncMode` verb), chosen because a FUSE mount, unlike a File Provider domain, *can* take over an arbitrary user directory; apple's set-level toggle exists only because FP cannot, so linux does not adopt it. The user's direction ruling (2026-09-26): build it, with the `fuser` crate (crates.io under `cargo vet`, `default-features = false` — the pure-Rust `/dev/fuse` protocol, no libfuse link) plus the distro `fuse3` package's setuid `fusermount3` for unprivileged mounts, since the agent never runs as root (`../architecture/apps/sync-agent.md` § Packaging + lifecycle). Eight binding-specific rules:

- **The same host, a different OS binding.** The root runs the shared `run_hydration_loop` exactly as the windows cfapi root does — the folder-scoped `SyncEngine` as its `HydrationHost`, the `LocalWrites` watcher + `converge` as its write half (one uploader, never a second), `serve_populate` for listings, a `PlaceholderInvalidator` for dehydrate and pins — and the FUSE session thread contributes only what `cfapi_host.rs` contributes on windows: translating kernel requests into `HydrationCommand`s and completing them. A FUSE `PlaceholderInvalidator` replaces the cfapi one. `provider_face` (the control-inverted apple face) is deliberately **not** this surface's seam: a FUSE root is self-driving — it owns a watcher and the loop — so it belongs with the cfapi service under the shared multi-engine driver (§ *Hosting multiple on-demand folders*), and the headless FFI-seam proof it inherits from apple is the vehicle, not the host shape.
- **Mount-over: the bound directory IS the backing store, and the mount is a view of it.** The agent opens the bound directory before mounting and keeps that descriptor; every read and write of the *underlying* directory goes through it (the `/proc/self/fd/<fd>` reach, which is also the engine's `watch_dir`), and the FUSE view presents the union of the underlying entries (hydrated files, the user's own new files) and the state DB's `Placeholder` rows (`serve_populate` over `immediate_children` — names, sizes, mtimes, no bytes). The consequences are the point: nothing is ever moved or copied on a mode flip, an unbind, a sign-out or a crash, and once the mount is gone the directory is an ordinary directory holding exactly the hydrated files (a clean stop unmounts; a crash leaves a dead mount until the boot sweep — the lifecycle rule below) — the user's bytes are always at the user's path (`../principles.md` § The user always controls their data). There is no separate cache root; disk accounting is the user's own filesystem's (the view's `statfs` answers with the underlying filesystem's). **A request from the agent's own process is answered from the underlying directory alone** — no placeholder listing, no hydration: resolving a path under the reach (a `canonicalize`) looks names up through the view, and a lookup that waited on the root's driving loop from inside that loop would never be answered.
- **Hydrate on open; write through.** Opening a placeholder hydrates it: the FUSE thread hands the request to the loop, which streams the file into the underlying directory (`download_file_to_path`, temp-then-rename), records the served identity (`mark_hydrated` — the closed hydration→upload feedback loop in § *Implementation status today*), pushes `FileStatusChanged{Synced}`, and only then completes the open. Hydrations run off the FUSE dispatch thread so a slow fetch never stalls a listing, and several may run at once. Every other operation on a materialized file passes through to the underlying file, so a user write lands where inotify sees it and the shared watch→`upload_file` loop uploads it. A placeholder is *present*: `unlink` of one records the delete through `handle_delete` (a loop arm, never the FUSE thread), `rename` of one hydrates first (apple's rule), directories pass through (`rmdir` over remaining placeholder rows refuses `ENOTEMPTY`; a `rename` of a directory still holding placeholder rows answers `EXDEV`, so `mv` copies it — hydrating as it reads — rather than leaving its rows behind), and symlinks and hard links are refused in v1. A hydration downloads into a dot-named temp file beside its target and lands by rename, so the watcher and the scans never see a half-written file, and a file the user wrote at that name meanwhile wins.
- **Dehydrate ("free up space") removes the underlying bytes — and that removal is NEVER a delete.** `FreeSpace` and the pin reaction gate on `is_dehydration_safe`, flip the row to `Placeholder`, and only then unlink the underlying file. **Iron-clad: a FUSE root's `Placeholder` rows are outside the delete universe on both rails — the scan and the watcher — and this root never writes the seen mark (amended 2026-10-01; the 2026-09-26 wording predated the mark).** This is linux's form of *never mistake one for absent*: on cfapi a placeholder is a file on the disk, so once the engine has *seen* it there its absence is a delete ([`delete-propagation.md`](delete-propagation.md) § *An offline placeholder delete propagates*, decision (a)); here a placeholder is never on the underlying disk — the row is the file's only presence — so a seen mark on this root would make every browsed or freed file read as a user delete at the next sweep and record it on the nest. Four obligations follow, each one the binding's own and none a change to the cfapi rule: **(1)** the listing sink reports **nothing placed** — `serve_populate` marks exactly the set its sink vouches for, and a FUSE listing puts nothing on the disk; **(2)** the dehydrate records the row through an off-disk form that leaves it unseen, never through the mark that cfapi's in-place free earns; **(3)** the root boots as a **fresh registration**, so a mark that arrived with an inherited state DB is cleared before the boot sweep; **(4)** a watcher `Remove` for a path whose row is `Placeholder` is the provider's own unlink, never a user delete, and the write half drops it before it reaches `handle_delete` — the dehydrate additionally registers the rel with the recent-removal suppression before unlinking. `handle_delete` itself is unchanged and stays the ONE way a placeholder is deleted here: the explicit `unlink` through the mount (the rule above), handed to the loop by the FUSE thread. The order is row first, unlink second, because that is the crash-safe one: a crash in between leaves a `Placeholder` row over a file still on disk, repaired toward the bytes (back to `Synced` when the disk hashes to the recorded head, an ordinary local edit otherwise), where the reverse order would leave a `Synced` row with no file — a delete to the next sweep. Pins live in the row (`SyncEntry.pinned` gains its setter; cfapi kept them in the OS): a pinned placeholder hydrates eagerly, a pinned file refuses dehydrate. No automatic pressure-driven eviction in v1 — a policy a user might want to choose is an app-UI + nest-state decision, never a constant hidden in the agent.
- **Placeholder detection needs no OS attribute.** The underlying directory holds only genuinely local bytes, so `is_cloud_placeholder` answering `false` on linux is correct, not a gap: the present-but-unreadable hazards cannot arise because nothing unreadable is ever on disk, and reconcile's delete detection — over the rows with evidence, the `Synced` rows and the *seen* placeholders — never counts one here, since this root marks none seen (the dehydrate rule above). Two windows-isms in shared code are fixed with this binding: `path_map::overlay_abs_path` joins with `\`, and `normalized_path_to_rel` matches case-insensitively.
- **The mount lifecycle: a clean stop unmounts, a crash guard unmounts after a crash, and the boot sweeps what the guard could not (amended 2026-10-01 — measured, replacing "crash-safe by construction"; guard 2026-10-02).** Options: `fsname=fauna-sync-agent`, `subtype=fauna`, `default_permissions`, never `allow_other`. **`auto_unmount` is not available to this binding**, and that is a measurement, not a preference: the `fuser` crate refuses the option on an owner-only mount (it demands `allow_other` or `allow_root`, each of which needs `user_allow_other` in `/etc/fuse.conf` — off on a stock distro, and a widening this binding never takes), and the same option handed raw to `fusermount3` mounts but leaves the mount in place ten seconds after a `kill -9`. So a crashed agent leaves a **dead mount**: the directory answers every access with `ENOTCONN` until something unmounts it — the hydrated bytes are intact underneath, and unreachable at their path for that window. Boot reconcile, before any engine starts, lazily unmounts (`fusermount3 -uz`) every leftover `fuse.fauna` mount at a configured on-demand location — the linux twin of the windows ghost-registration sweep — for a ghost nothing else cleared. **The window closes without a restart, by the agent's own means, never by `allow_other`:** at every mount the agent re-executes itself as a **crash guard** — a child in a process group of its own holding the read end of a pipe whose write end only the agent holds; however the agent goes, the guard reads EOF and lazily unmounts the mount it was given, but only while that mount is still in the table under its mount id AND answers `ENOTCONN` (dead) — a successor's live mount at the same path, recycled id or not, is never touched. So with the agent dead the directory is an ordinary directory again within moments; a guard killed with the agent (a whole-cgroup stop) leaves its ghost to the boot sweep. Mounting needs an openable `/dev/fuse` and a `fusermount3` on PATH; the agent probes both at boot and reports the result as the additive `on_demand_available` field of its status reply (with `on_demand_unavailable_reason`, a stable code), which the apps read to render the toggle disabled with the reason ("needs the fuse3 package") — the offline-aware-controls shape, never a silent no-op. **One refusal the probe cannot see is per location:** Ubuntu confines `fusermount3` with an AppArmor profile that admits a mount point only under the user's home, `/mnt`, `/media`, `/run/user/<uid>` or `/tmp` (measured 2026-10-01: *mount failed: Permission denied* anywhere else). A root whose mount fails runs unmounted — its hydrated files sync two-way and no placeholder is listed — and the agent says so per location: `LocationInfo::on_demand_mount_error` carries a stable code — `mount-refused` for the helper's permission refusal, `mount-failed` for anything else — for exactly as long as that root runs unmounted, the shared binding model mirrors it onto the row (`BindingRow::mount_error`, on the reconcile and on the status-tick watch), and the app renders its line beside the row's switch, which stays live so the user can turn on-demand off. The linux row renders that line as untagged text like its other captions, so it took no element of its own.
- **Mode flips and unbinds are mount/unmount, nothing else.** always→on-demand: stop the resident engine, mount over the directory — every file already there is simply a hydrated file. on-demand→always: unmount, start the resident engine, which materializes every `Placeholder` row (a `Placeholder` row on a resident root is a pending download, never a delete; the windows flip is checked against the same rule at build time). Unbind, unprovision, sign-out and account switch: stopping the engine unmounts (the mounted session is a drop guard, like `CfApiConnection`), and the directory is left holding its hydrated files. A fresh linux binding starts always-resident (the agent's platform-scoped `fresh_binding_default`, § On-Demand Files → *The choice is the user's*); whether linux follows windows to an on-demand default once its FUSE root can serve one is decided with that root, not before.
- **Install channels.** deb and `install.sh` declare/check the `fuse3` package (`../architecture/installers/linux-desktop.md` § Installation Files); AppImage boxes already run FUSE. Flatpak and Snap cannot mount from inside their sandboxes (no setuid `fusermount3`, no `/dev/fuse`), so there the probe reports unavailable and the toggle renders disabled with that reason — a stated limitation, not a per-channel design.

**Headless proof.** `bins/fauna-sync-agent/src/fuse_live_integration.rs`, the linux twin of `cfapi_live_integration.rs`: the agent's own host over a real mount in a temp dir, every assertion from **another process** (`ls`, `cat`, a write by a subprocess), opt-in behind a `fuse-live` cargo feature (it needs `/dev/fuse`) so the merge-gate check runs it on the linux dev machine. Same test names as the cfapi file wherever the rule is shared (populate, open-hydrates-and-flips-`Synced`, a cloud-only placeholder is never uploaded, a dehydrated file is never recorded as a delete, a local edit by another process is uploaded, zero-byte). The cross-app witness for `files-on-demand` outcome 1 is `test_folder_location_mode_toggle.py`'s linux arm over the real agent, plus a tier_3 read-path test (`test_folder_on_demand_read_path_linux.py`: bind → flip → the kernel's mount table, `ls`/`cat` and a write from subprocesses, the engine's own upload record → flip back) — both built with S5.

#### The free-up-space gesture where the OS offers none (designed 2026-10-04; advisory until the user's Rule A ruling on its ids; UNBUILT)

Windows gets *Free up space* and *Always keep on this device* from Explorer, apple from Finder and Files, android from the system's cache reclaim. A linux desktop has no such verb for a FUSE root, and a terminal has none anywhere, so there the gesture has to be the app's: without it a file once opened stays on the disk for good and an on-demand folder only ever grows. This section is that gesture's owner. Nothing in it is built; the ids it proposes are **asked of the user and unanswered**, and a NO from the user turns the section into the decision that linux keeps no such gesture.

- **The surface is the bound row and the unit is the location.** Each bound row whose binding is on-demand, and whose placeholder surface stands (no `on_demand_mount_error`), carries one verb: **Free up space**. It frees every file under that location that is on this device, not kept, and provably recorded — exactly what Explorer's verb does on a folder — and leaves every other file where it is. Why the row: it is the one surface in every app that is keyed by a local binding and already speaks to the agent, and it is the same control on tui and the desktop apps. Why not the Media page: Media lists a set's content from the nest, a set may be bound here twice or not at all, and no app reads a per-file presence from the agent — a per-file action there would be a second file browser beside the user's own. Why not a file-manager extension: it is one integration per desktop (Nautilus, Dolphin, Nemo, Thunar), third-party code on its own install channel, and it gives tui nothing; it stays a separate question for the user, never a silent follow-on.
- **Every app that renders the switch renders the verb (priority #1).** The rule is the row's, not the host's: `folder-location-mode-toggle` present and on → the verb is present. So tui (the lead app), linux and windows carry it; on windows it duplicates Explorer's verb on the folder, which costs nothing and keeps one rule and one witness. macOS renders neither (a bound location is always-resident there).
- **What the row says.** Beside the verb the row states how much of the location is on this device (bytes on this device of the set's bytes), so the user can see what a press would reclaim and that it did. After a press the row states the outcome of the latest sweep: how many files and bytes were freed, and how many were kept because they hold a change the nest has not recorded yet — the user-visible form of *a change that has not reached the nest cannot have its space freed*. The verb is never optimistic: both lines are the agent's reading, re-read off `ListLocations`, as the switch's is.
- **Keep on this device is the switch.** At the location's grain "always keep" already exists: turning the row's on-demand switch off downloads everything and keeps it. A finer keep (one file, one sub-folder) needs a per-file surface, which the app deliberately does not have (first bullet), so `PinFile`/`UnpinFile` keep no app caller on linux and that is a decision, not a gap: they stay the agent's verbs, pinned by `fuse_live_integration`, and are what a later per-file surface — the file-manager question above — would call. The sweep honours a pin regardless: a kept file is never freed.
- **The seam is shared Rust plus one agent verb.** Agent: a new request `FreeLocationSpace { path }` (the bound location's root; additive — an agent that predates it answers an error, which the row shows). It refuses a location that is not a mounted on-demand root, answers once the sweep is accepted, and the root's own loop does the work: every row with bytes on this device goes down the ONE existing road (`free_space` → the pin refusal → `free_local_bytes` → `is_dehydration_safe`), so there is no second gate and no second order of row-then-unlink. On windows the sweep walks the same rows through `handle_free_space`'s per-file body. **A sweep never outranks an open:** it yields between files, so a hydrate-on-open waits for at most one file's proof. **An own record in a metadata-only folder is the same refusal:** the gate keeps it (the paragraph *In a metadata-only folder a seat's own record is not a dehydration proof*, below), the sweep counts it in `kept_unsynced` with the unrecorded changes — one count, one line, no id of its own — and the line's string therefore says *kept because this device may hold the only copy*, since in such a folder waiting does not drain the count. The reading rides `LocationInfo`, additive: `on_device_bytes` (the recorded sizes of the rows that are not `Placeholder`) and `free_space` — the latest sweep of this agent's lifetime (`running`, `freed_files`, `freed_bytes`, `kept_unsynced`, `kept_pinned`), derived and never stored, with the lifetime rule `deletes_held` has. Client: `fauna-client-sync`'s agent control gains `free_location_space(path)` beside `set_location_sync_mode`; `BindingRow` mirrors the two readings on every reconcile; and `LocationBindingsModel::free_space_verb(&row)` answers what an app paints (absent / idle / running, the two lines' numbers), each line named in the shared string table (`devices.sync_locations.free_space_*`). An app adds a button, two texts and one call.
- **No automatic eviction — restated, not reopened.** The sweep runs when the user presses it and at no other time; a pressure- or age-driven policy stays what § *Linux FUSE binding* already rules it: a choice a user might want, so app UI + nest state if ever, never a constant in the agent.
- **The witness is one seat, and it closes two outcomes.** `tests/e2e-unified/tests/test_folder_location_free_space.py` (tier_3; tui and linux on Linux, tui and windows on Windows), every assertion another process's view or the agent's own record. *Outcome 4:* bind, drop a file, wait for its upload, flip on-demand, press the verb → the row reports one file freed and nothing on this device, the engine logged the dehydrate, `ls` through the mount still lists the name with its size, the Media page still lists the file, and `cat` returns the original bytes — which this device no longer held, so the nest still does. That last step is also the first app-level hydrate of a cloud-only file a single seat can make. *Outcome 5:* with the nest stopped through the bridge, change the file through the mount, press the verb → the row reports one file kept, and `cat` returns the changed bytes while the nest is down (they can only be local); start the nest, wait for the upload, press again → freed.
- **Proposed ids (Rule A — asked 2026-10-04, unanswered).** On `pages.folders` `platform_elements` for linux, windows and tui, each indexed and scoped under `folder-location-row`: `folder-location-free-space-button` (button; `state` attr `idle|running`), `folder-location-on-device` (text — the standing reading), `folder-location-free-space-result` (text — the latest sweep's outcome; absent until one has run).

#### Android SAF DocumentsProvider binding (designed 2026-09-26; direction user-ruled, the rules below advisory until built; shared-Rust cores and presence plan BUILT, the provider's read and write paths BUILT 2026-09-28, its device run and toggle UNBUILT)

Android realizes the on-demand surface as **a SAF `DocumentsProvider` over a replica the app owns** — apple's *set-level* shape (the per-set `folder-on-demand-toggle`, "Show in Files", own accepted folders, default ON), for apple's reason: a provider cannot take over a user-picked tree (a `content://` tree exposes no path — [`sync-engine-deployments.md`](sync-engine-deployments.md) § Implementation status today (android byte-sync)), but it can serve a tree the app itself owns. The direction is the user's ruling of 2026-09-26 ([`p2p.md`](p2p.md) § Cross-user shared-set transfer → Implementation status today: phones are peers, and android's peer-transfer leg is owed behind this replica); the rules below are this design's, refutable until a build slice proves or breaks them. It is the fourth binding and the only one where **the provider itself owns the tree** — there is no OS-managed location (apple) and no user directory (windows, linux) — which decides most of what follows. Ten binding-specific rules:

- **Control inversion, in the app's own process.** The OS — the system file browser, any other app's picker — calls the provider; there is no watcher and no disk scan on this surface, so the shared `provider_face` cores serve it exactly as they serve apple's extension: `queryChildDocuments` / `queryDocument` = `serve_enumerate` / `serve_item` (every live row, placeholder and materialized alike), `openDocument` = `serve_fetch_to_path` + `mark_hydrated`, a closed write = `serve_ingest_with_base`, `deleteDocument` = `serve_delete`, `renameDocument` / `moveDocument` = `serve_rename`. The provider is manifest-registered with no `android:process`, so it runs **in the app's process**: the hydration host is in-app, and *Who runs the hydration host* above has no process seam to cross here — no credential rendezvous, no second lifecycle, no app↔extension byte seam.
- **One construction path: the capability constructor.** Each set's host is built through the capability construction apple's extension uses (the owner `BackupKey` plus a bearer source plus a change-signer source, **never the identity seed**) — its owned-tree twin `FfiFileProviderHost::app_dead_owned_tree`, which derives the two roots below — fed from the app's own secure storage: the provider mints its own bearers and holds its own nest connection for the set list, since the process may be running for another app's picker with no app session. The change signer is the machine principal every capability host signs with ([`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, *The capability host* — owner of the ruling and of its android arm); here the host reads it out of the app's own principal slot itself (`machine_change_signer`, the shared-Rust slot reader) because there is no process boundary to copy it across. In-process it is not forced by a trust boundary; it is chosen because a provider the OS starts for another app's picker has no live app session to borrow, and because one construction path for every control-inverted host is the uniform shape (priority #3). One host per set — per-set `fsid-<ref>.db`, the shared `device.db`, in the account's sync state dir — built lazily by the first call that names the set and dropped at teardown; the multi-root rule above holds unchanged.
- **The provider owns the tree, so the owned-tree logic is shared Rust.** On apple the OS keeps the replica, re-drives an un-acked change and evicts under pressure; here nothing does it for us. What the OS does for apple is therefore written **once, in shared Rust, beside the cores** — body lookup, hydrate-for-open, prepare-for-write, close → ingest, the start sweep, eviction observation — and surfaced through `FfiFileProviderHost`. The Kotlin provider translates `DocumentsContract` calls into host calls and builds cursors; it holds no sync state and makes no sync decision (priority #2).
- **Two roots per set — a kept root and a cache root.** The **kept root**, `<filesDir>/on-demand/<actor-id-hex>/<ref-component>/` (the engine's `root_dir`), holds exactly the bodies this device must not lose: a local edit the nest has not recorded yet. The **cache root**, `<cacheDir>/on-demand/<actor-id-hex>/<ref-component>/`, holds recorded bodies, which the nest can always serve again. Account outermost, the ref one percent-encoded component (`local%3A1` — shared Rust's `FolderRef::path_component`, the identifier's own ref half: apple's staging-root grammar, from the same shared `ActorScopedFolderRef`). A lookup reads the kept root first, then the cache root; a body in neither is a placeholder — and a cache-root body counts only while its row is hydrated: once a refresh re-points the row at a moved head, the cached bytes are the superseded version and the next open fetches the head. The host derives both roots itself from the platform's files and cache directories (`OwnedTree::for_set`), so no app code spells the grammar.
- **Hydrate on open — and never a stand-in body.** Opening a document whose body is in neither root fetches it into the cache root (temp-then-rename), marks the row hydrated and only then returns the descriptor; the call blocks the caller's binder thread, as every cloud provider's does, and honours the `CancellationSignal`. A body that cannot be fetched (offline, signed out, a refused capability) fails the open with the platform's not-found error: a placeholder is *present-but-unreadable*, and the provider never answers with bytes that are not the file's. The first build advertises no thumbnail support, so browsing a folder never hydrates; the 0-byte case is the shared size-aware mapping above.
- **Freeing space is the OS's cache reclaim — and it is never a delete.** Android already has this platform's *free up space*: the system trims an app's cache under storage pressure, and the user's own "Clear cache" does it on demand. Recorded bodies live in the cache root precisely so that reclaim is the OS's, with no eviction policy and no constant of ours (a policy a user might want to choose would be app UI + nest state, as the linux binding records). Eviction is **observed**, as on apple: at open, at host start and on the refresh tick, a hydrated row whose body is in neither root is handed to `serve_evict` (`mark_placeholder`). No scan runs delete-detection on this surface, so a reclaimed body can never read as a deletion; and because an un-recorded edit is never in the cache root, *a change that has not reached the nest cannot have its space freed* holds by construction, not by a gate. "Always keep on this device" is the kept root's second use (a pinned body lives there); its control is not in the first build and is a Rule A item when it is proposed.
- **Two-way, with the body's presence as the write intent.** Opening for write promotes the body into the kept root (hydrating it first), and the descriptor carries a close listener; the close runs `serve_ingest_with_base` with the version the open saw, and on a *recorded* ack the body is demoted to the cache root (a conflicted ingest that moved the row to another head drops the local body, so the next open fetches the winner — the shared conflict arm). `createDocument` creates in the kept root; `deleteDocument`, rename and move are record-first and are **refused to the caller when they cannot be recorded**, never applied locally and lost. **A body found in the kept root IS the write intent:** the start sweep ingests every body there (the recorded-head-proof skip makes it idempotent) and demotes on ack, so a process death between a close and its upload loses nothing and needs no journal. *One exception (2026-10-01):* a body the share plane landed from a peer for a row the nest has not confirmed rests in the kept root too — the nest cannot serve it again either — but it was never this device's authorship, so the sweep and an unchanged close never ingest it; the nest's own row for the path confirms it (demoted like any recorded body) or supersedes it (dropped), and a body the user has since written over is an ordinary write intent again ([`p2p-shared-set-build.md`](p2p-shared-set-build.md) § *Phone peers — design* owns the landing policy and that reconcile). The sweep runs after the set is populated, and a kept-root body over a row that is a *placeholder* — the nest's head moved while the edit waited — takes the shared conflict auto-resolve rather than a plain upload, so the missing journal never costs a last-writer-wins clobber. A body leaves the kept root only on the engine's own dehydration proof (the row `Synced`, the disk hashing to the recorded head), and never while another descriptor still holds it open for write. **A directory is only its files' paths — it has no row — so it is deleted, renamed and moved file by file** (apple's appex walks a folder the same way): each file record-first, in path order, stopping at the first file that cannot be recorded with an error to the caller. The walk is not atomic, and it does not need to be: every file is either recorded at its new state or untouched, never lost, and repeating the gesture finishes the rest. An empty directory cannot be created (nothing would record it, and a directory the provider could not list again would be a lie); creating or renaming to an ignored name is refused, as is moving a directory into itself or a document across sets. What is advertised follows: a document supports write, delete, rename and move; a directory inside a set supports create, delete, rename and move; a set itself supports create only — it is never renamed or deleted from the provider.
- **Identity: the actor-scoped ref, never the set name.** A document id is `<ref-component>@<actor-id-hex>/<rel>` (`local%3A1@…/<rel>`) — the scoped identifier of apple's domains, whose percent-encoded ref half never carries the `/` the id splits on, followed by the folder-relative path — and the set's name is only the display name. One SAF root per **active** account, titled Fauna, whose children are that account's desired sets. Persisted URI grants key on the id, so it must not change when a set is renamed; a rename of a document returns its new id, as the contract allows.
- **Set-level, one local presence per set per device, serialized single-account — and the plan is shared Rust.** Desired sets = the folders this device holds an accepting place in (the apple bullet *Auto-appear default-ON* above owns the mode-free plan and its enrol gesture) ∩ toggle-enabled ∖ sets this device feeds through an ingress (the watched-directory ingress, the photo library): the explicit act outranks the ambient default, apple's precedence, so no set has two engines writing it from one device id. The toggle is device-local, keyed by the scoped identifier. **The plan and the preference store are shared Rust** — `fauna_folders_machine::on_demand_presence` (`desired_presences` + `plan`, the `OnDemandPrefs` store; FFI `on_demand_presence_plan` + `FfiOnDemandPrefsStore`) — so android consumes what apple does instead of growing a Kotlin twin, and apple's coordinator keeps only its OS calls. The plan takes every set the account holds with its role and seat — one shared mapping, `held_sets`, builds that list from the member-visible folder list and custody, so no app maps a row itself (§ *Shared sets on a capability host*, decision 3) — the stronger-presence refs, the toggle store, the registered identifiers, and an optional owner record; it answers add / keep / backfill / foreign-held / remove, each removal carrying the account and set its identifier scopes — none for an identifier that scopes no set, whose removal is un-gated. **The owner record is apple's alone:** the domain-owner map (defense in depth over a registry shared by every account on the device) stays persisted in apple's OS layer and enters the plan as data; android keys its roots by the scoped identifier alone and passes none. Sign-out, account switch and toggle-off **hide** the set at once (hosts dropped, the roots change notified) and delete the cache root, but never the kept root: its bodies are drained by the owning account's next session. iOS must refuse a removal while edits are un-recorded because the OS would destroy them; android owns the tree, so it hides and keeps. The plan's shared-with-me arm and a reader's read-only host are § *Shared sets on a capability host*, decision 3.
- **Nothing of ours runs resident.** A remote change reaches the tree by `refresh()` — on a tick while the process lives, and on the file browser's own refresh — followed by a change notification on the affected children (the `signalEnumerator` twin); with the process dead the tree is simply as fresh as its last refresh, and the next call refreshes it. Doze and process death need no handling beyond the two roots' rules: a half-fetched temp file is discarded at the next start, a half-uploaded edit is still in the kept root. The provider is not direct-boot aware (credential-encrypted storage is closed before first unlock), and it resolves its dependencies at the first call, never in `onCreate`, which the platform runs before the application's own.

**The seam the peer-transfer plane consumes.** A phone's share plane serves from and ingests into this replica ([`p2p.md`](p2p.md) § Cross-user shared-set transfer), through three host-side operations and nothing else: **look up a body by path** (kept root, then cache root, else none — the serve half's honest `Ok(None)` for a placeholder); **land a body into a named root** (the kept root when the nest may not hold it yet, the cache root when it does); **record a row as a placeholder**. Which pulled bodies are landed and where is the phone-peer design's policy, owned by p2p-shared-set-build.md (§ Cross-user shared-set transfer → *Phone peers — design*, decided 2026-09-26); this binding only guarantees the two roots' invariants hold whoever lands the body. *Built 2026-10-01:* the plane's ingest door is one host operation over these (`OwnedTree::share_ingest`, surfaced as `FfiFileProviderHost::share_ingest`), and its serve half runs the lookup's own rule over the two roots and the set's state DB.

**Headless proof.** The owned-tree cores are tier-1 tested against the faked `ProviderEngine` the existing cores use, and proven against a real nest in the `conformance_file_provider_client.rs` vehicle (*Headless-first testing* above) — open-hydrates, a reclaimed body is observed and never recorded as a delete, a closed write uploads, a body left in the kept root by a killed process is uploaded by the start sweep, a delete that cannot be recorded is refused. The provider contract itself (`DocumentsContract` queries and opens through a `ContentResolver`) is an instrumented test on the emulator — the provider's `MANAGE_DOCUMENTS` guard admits the app's own uid, so the test needs no system role. The cross-app witnesses are android arms of `test_folder_on_demand_toggle.py` (the `files-on-demand` page's first outcome) and a read-path journey reading a document through the resolver, both gated on the ui.yaml scope ruling.

#### Shared sets on a capability host (decided 2026-09-26; decisions 1 and 2 BUILT 2026-09-27; decision 2′ — the unreachable nest — ruled 2026-10-01, BUILT 2026-10-02; 4 built, not enabled; 3 answered 2026-09-30 and BUILT 2026-10-01 in shared Rust and on android, 2026-10-03 on apple; the agent's convergence BUILT 2026-09-27, the one builder and its cross-nest arm 2026-09-28; decision 1′ — the plane read — ruled 2026-09-30, BUILT and wired 2026-09-30 but for the apple credential store's item)

**What this rules.** A **capability host** is any on-demand host built through the capability constructor — the owner `BackupKey` plus a bearer, never the identity seed: apple's extension today, android's provider when it lands. Until this section such a host could serve owner-only sets alone. A set bound to an MLS group — a shared set, [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 content-key mechanism — failed closed at the engine build, so an owner's set stopped opening in Files the day it was shared, and a set shared *with* the user had no on-demand presence at all. The four decisions below close that for every capability host alike; none of them has a per-platform variant. The cross-user transfer plane's phone legs stand on the result ([`p2p-shared-set-build.md`](p2p-shared-set-build.md) § Cross-user shared-set transfer → *Phone peers — design*, the first of its three gates).

**1. The host loads custody itself — nothing is provisioned beside the `BackupKey`.** The content keys of a bound or WebDAV-served set rest in their holder's custody (the M2 *Custody* rule) — the plane kind `fauna.state.folder-keys` since the dissolution cut the field (2026-09-30), which a capability host reads as decision 1′ below rules; before the cut, the `__config` blob, sealed under that holder's `BackupKey` (the rail itself retired 2026-10-02 — [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)). That at-rest blob carried no signature envelope, so the `BackupKey` alone opened it — the seed was never load-bearing for those bytes, which is what already let the seedless sync agent host the account store. A capability host therefore resolves a set's keys as a seed-holding host does: from the same custody, over its own bearer connection, held in memory for the life of the engine and never written to disk. The app provisions **no per-set key** — not in the shared Keychain, not in android's secure storage, not as a constructor argument. *Why not provision them today:* while the host holds the `BackupKey`, a provisioned key narrows nothing (the `BackupKey` already opens the custody that holds every generation), and it would add a second channel that can go stale, a push on every custody change in two shells, and a rotation that cannot reach a host whose app is not running (decision 2). *Blast radius:* unchanged. The capability is still the `BackupKey` and a bearer; what is new is only that the host uses a breadth Phase 1 had already accepted. The seed stays out of the host (rule #6), and so does every piece of MLS state (rule #7): a capability host is never a group member, opens no envelope and ingests no custody. A generation reaches custody only through an identity-holding app of the same user — the owner's rotating device, or a member's custody-ingest leg — and the host reads what that app wrote. *What a removed member's host keeps:* nothing at rest. The generations that member held stay in their own custody, as on every device of theirs (content they could already read — M2 *Rotate-on-removal*); the set's row leaves their folder list, so their host's next build refuses and the plan drops the set; and content sealed after the removal is stamped with a generation their custody never receives, which fails closed. *One later addition to what the app provisions (ruled 2026-09-27, unbuilt):* the machine principal's writer key and its `DeviceAuthorization`, beside the bearer and over the same channel, so the host signs what it records — the design, the why (a device key is neither the seed nor MLS state) and the macOS/iOS split are [`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, ruling (1).

**This is Phase 1's mechanism, and Phase 2 supersedes it.** *Who runs the hydration host* above names the end state, a host that holds only its folder's key. The two statements are phases of one design, not alternatives: custody load is how a host that holds the `BackupKey` comes by a shared set's keys; the day owner-only content moves to per-folder keys and the `BackupKey` leaves the host, custody is no longer the host's to open, and each set's keys are delivered to it as a capability. One constraint on that delivery is recorded now, because this pass measured it: it must reach a host whose app is not running, from any of the user's identity-holding devices, through the nest — so a device-local hand-off from the app (a Keychain write, an in-process call) cannot be the whole of it.

**1′. On the plane, the host loads custody as the enrolled device it is — a throwaway fleet-scope replica keyed by the machine principal's wraps (ruled 2026-09-30; the shared-Rust half and the engine cut BUILT 2026-09-30, the apple store's item UNBUILT — *Implementation status* below; the build rows are at the end of this paragraph).** The dissolution moved shared-set custody off the `__config` blob onto `fauna.state.folder-keys`, a fleet-only kind sealed under the account's generation tip ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md), the kinds table), and the `BackupKey` deliberately does not reach a random generation — removed devices keep it ([`../architecture/owner-key-material.md`](../architecture/owner-key-material.md) § Path A-sibling-2, the generation axis). So decision 1's read stops working the day the cut lands, and no goal doc said how a host that hosts no account store reads a plane-only kind: the apple extension can reach no store root but its own container (§ Apple File Provider binding, *state unification*), and android's provider builds its hosts with no runtime running (§ Android SAF DocumentsProvider binding — a provider the OS starts for another app's picker has no app session). The ruling: **a capability host is a process of an enrolled device, and it reads a fleet-only kind exactly as an enrolled device does — from the wraps the plane addresses to the machine's device key.** The machine principal's writer secret is already in every capability host (the signer ruling, [`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, ruling (1), *The capability host*), and that secret derives the device's X-Wing KEM keypair — the target of the inline member wrap on every mint and of every top-up row the fleet writes for the device — so nothing new is provisioned for the read. The mechanism is the box-recovery cold read's ([`../architecture/nest/box-recovery.md`](../architecture/nest/box-recovery.md) § The plane-era recovery floor, *(b)*; `fauna_account_plane::deployment_seed_recovery::cold_read_deployment_seeds`), generalized to a second key source: a **throwaway replica** — an `AccountStore` on the in-memory backend under an ephemeral writer key that is never published, a **pull-only** fleet plane over the host's own bearer connection (no walker mark, no publish path: the nest records nothing for the walk and the host authors nothing on the plane) — walks the `state-fleet` scope, keys every walked mint through the device arm (this device's inline wrap or top-up row, opened with the KEM secret against the mint's key commitment) or through the custody it holds, reconciles, and folds `fauna.state.folder-keys` through the plane's own door (`read_folder_keys` → `FoldersConfig::fold`). Everything the replica applies runs the plane's own code — the same writer-signature check, the same trial open, the same join — so a row the host folds is a row every replica folds; the plane's trust (prior tips, escrow holders) gates only sealing, and the host seals nothing on the plane. The replica is **one per (process, account)**, shared by every per-set host in the process and held for the process's life: decision 2's edges become one incremental walk each (the plane's stored frontier), and a process the OS kills starts from a full walk of the fleet scope — the account's fleet-only state, one scope, never the delegable `state` scope and never a content scope. **Retained keys — the host's custody is the credential store it already reads its signer from.** A generation this device obtained without a wrap on the plane — recovered from escrow at a seed-holding sign-in, or a top-up the reclaim pass has since retired because the app consumed it — is in the machine slot's `generation-keys` carriage and nowhere on the plane (the top-up pass never self-wraps: a self-wrap is noise to a store that persists its keys), so the host needs that custody beside the wraps: on **android** the host reads the machine slot itself, as it reads its signer (`SlotChangeSigner`), the slot's `RetainedKeyCustody` is its custody, and its own unwraps are recorded there exactly as the runtime's are; on **apple** the app-group credential store (`FileProviderCredentialStore`, the single-slot store that already carries the `BackupKey`, the bearer, the writer secret and the `DeviceAuthorization`) gains a `generation-keys` item, the **app** mirrors the machine slot's carriage into it on every slot write (the signer watch that already re-provisions the signer, the same trim as the slot's), and the **extension** records into it every generation it unwraps itself — so an app-dead mint reaches the extension by its wrap, an escrow-recovered generation by the mirror, and a generation the extension opened once needs neither again; both are the same custody class as the `BackupKey` beside them. *Blast radius — stated, not softened:* a capability host holds the whole device bundle, the `BackupKey` and the machine principal's secret, and so opens every fleet-only kind the machine's own apps open, not the one kind it needs. That is no more than the blob rail allowed (the `BackupKey` opened the whole `__config` blob, every field, until the rail retired), no more than the app process whose trust boundary it shares, and it brings the generation axis's removal severance with it, which a `BackupKey`-only custody never had: a removed device's host stops keying new generations because nothing wraps to it, and its bearer dies with the device row. What the dissolution would otherwise have narrowed for the host, it does not — that narrowing is Phase 2's, and Phase 2 now has two things to take out of the host, the `BackupKey` and the machine principal's secret: a Phase 2 host signs under a per-host key the device certifies and receives its folder's key as a capability, recorded here, not designed. *Rejected:* mounting the machine's account store (the sandboxed extension cannot reach the user domain — the two-domain law; on android it would tie a provider the OS starts for another app's picker to a runtime only a sign-in assembles; a store the iOS extension shares with the app through the container forks the mechanism per OS); the app provisioning per-set keys (decision 1's own argument — the rotation that must reach a dead app cannot); a copy of the slot's carriage alone, with no wrap read (the same hole: a mint made from another device while the app is dead never reaches it); pulling Phase 2 forward (a per-folder owner key for owner-only content and a per-host delivery kind are a design of their own, and the cut needs neither); a second reader outside the plane's code (one verifier — a row's admission is decided in `apply`, once); a blob mirror kept for these hosts (an E3 kind is born plane-only, `config-dissolution.md` P5). **A host whose machine has no principal yet reads no custody** (it has no device to read as): a bound set builds keyless, and an own set whose records are signed lists nothing — no row verifies without the set nonce custody holds — while every write is held with the reason; it rebuilds, over the custody it can now read, at the first refresh or seal that finds a principal provisioned. The replica is one per (process, account, nest), rebuilt when the principal is re-minted or the `BackupKey` it is handed differs, and it brings its own bearer connection up — no host's build connects it. The desktop sync agent is not this case: it hosts the machine's store (the seedless host) and reads the kind through its own handle; where that store cannot mount — a slot with no app-enrolled `BackupKey` — custody is unreadable and every bound set builds keyless until the machine signs in once, the refusal's own recovery.

**2. Rotation: the host re-reads custody at its own edges, and enforces the generation floor itself.** A set's keys are final at engine build, and an app-dead host has no app to rebuild it, so the host re-resolves on its own evidence at three edges: at **every build**; at **every refresh**, when the set's binding, the caller's access, or the set's content-key floor (the owner-stamped current version the nest keeps beside the set's envelope, which the set's row carries — [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 → *Multi-writer*) differs from what the engine was built on, or when that floor is still ahead of the generation the engine holds (custody arriving is not visible on the row, so a host behind the floor re-reads at every refresh until the generation is there); and **before a seal** — every write, a delete included, since a recorded path seals under the same generation — when that floor is ahead of the generation the engine holds (a row that cannot be read is decision 2′'s case: the seal stands on the last floor read, and nothing it produced is published to a nest until the row reads). Re-resolving is a custody re-read and an engine rebuild over the same state DB — never a domain removal, never a re-population. A set whose row is gone (deleted, or the caller removed from it) rebuilds into a refusal. A host that still lacks the generation after the re-read **fails closed per operation and keeps serving the rest**: a body stamped with that generation does not open (the fetch fails with the platform's error, never a stand-in body; the file's path rests sealed under the same generation — [`file-sync.md`](file-sync.md) § Sealed names & paths — so it does not list either), and a write is **neither sealed under the older generation nor acknowledged** — the edit stays where an un-recorded edit stays (the OS's pending queue on apple, the kept root on android) and is sealed when the generation arrives. The host holds an **owner's** sets to the floor exactly as it holds a member's. The nest's own floor exempts owner devices, because an owner's resident engine is re-keyed by the app that rotated; a capability host has no such trigger, and without its own check an owner's phone would go on sealing new files under the generation a removed member still holds. *The limit:* if none of the user's identity-holding apps has run since the rotation, the generation is not in custody and the host waits, failing closed, until one does. That is the price of keeping MLS state out of the host, and it is paid in availability, never in confidentiality (the one bound on that sentence is a rotation an unreachable host cannot learn of, on the peer plane alone — decision 2′). **A fourth edge, for a host that holds a live nest connection (added 2026-09-27; the nudge moved to the plane 2026-09-30).** Every `fauna.account.state.put` fans a `SyncChanged` nudge tagged with the written scope out to the writer's own connected devices ([`../architecture/account-data-plane.md`](../architecture/account-data-plane.md) § Nudges and backstops; the emit is the nest's `sync_handlers`), and every custody change — a rotation, a share, a serve or paywall flip, a member's ingest — is a write to the fleet scope (`state-fleet`), since custody is the fleet-only `fauna.state.folder-keys` kind. A host whose bearer connection carries pushes re-resolves on that nudge once the account store it reads through has walked the rows in, whatever the row says; the three edges above stay the correctness backstop, because the nudge is best-effort by construction. A host that reads custody through an account store it mounts reads that store's local rows, which only a walk brings in — so an edge whose re-read still leaves a bound set behind its floor or keyless has the store run a pass and reads once more: a lost nudge is healed by the edge that noticed it, not left to the store's own backstop. The desktop sync agent is the first such host (*One mechanism* below); a control-inverted extension, woken by the OS per request, has no standing connection and keeps to the three.

**2′. The nest unreachable: the floor gates what is published to a nest, and a seal stands on the last floor the engine read (ruled 2026-10-01; refutable — the cost named below is put to the user; BUILT 2026-10-02 — *Implementation status* below).** Decision 2 as first written held every write whose pre-seal row read failed, and [`p2p.md`](p2p.md) § Cross-user shared-set transfer has a file authored with no nest in reach arrive on another member's device peer-to-peer. The own-pending row that plane serves is minted from the write's seal ([`p2p-shared-set-build.md`](p2p-shared-set-build.md) § *Build design — the row half*, the own-pending bullet), so on a resident host the hold removed the feature: the two could not both stand. The rule is one rule — for every host, for every writer (an owner's device and a writer member's seal through the same code and under the same generation, [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 → *Multi-writer*) and for both arms. **(a) A floor the host has read binds it whether or not the nest is in reach.** A generation behind the last floor read is never sealed under, and a row the last successful read found gone holds every write — decision 2 unchanged, offline as online. **(b) A seal stands on the last floor the engine read.** Every engine is built on one — a same-nest set's row, a cross-nest set's custody record — so when the pre-seal read fails, the engine seals under the generation it holds, that generation having met the last floor it read, and mints the write's own-pending row; the peer plane serves it as it serves any row. **(c) Nothing reaches a nest without a floor check made against a nest in reach.** A pass whose pre-seal read failed publishes nothing it sealed — no chunk, no manifest, no record — and the write stays un-acknowledged where an un-recorded edit stays. The control plane the read rides and the byte plane are separate connections, so this is a gate the engine enforces, never a side effect of being offline. The first pass that reads the row again decides: the floor still met, it publishes what it sealed (the seal is convergent, so the bytes are the ones peers already hold); the floor ahead, (a) holds until custody brings the generation, the write is re-sealed under it, the re-mint replaces the pending row, and what was queued under the older generation is completed unpublished (the drain's never-publish-prior-generation rule, [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 → *Multi-writer*). **(d) An own-pending row stamped below a floor the host has since read is withdrawn from the peer door** — the host now knows that seal is behind. *The two arms differ only in who makes (c)'s check.* A cross-nest set has no row here: its floor rides the custody record (*One mechanism* below, question 2), its engine has sealed on the last recorded floor since 2026-09-28 — which is (b) — and its publication check is the home nest's `stale_content_key` refusal, which never exempts the caller, always a member there. A same-nest host makes the check itself, because the nest's floor exempts an owner's devices. *A control-inverted host* (the File Provider extension, android's provider) acknowledges only what is recorded, so its write stays un-acked through an outage exactly as before; it serves no peer plane today, and its phone-peer leg inherits (b) when it lands ([`p2p-shared-set-build.md`](p2p-shared-set-build.md) § *Phone peers — design*). **What it costs, stated, not softened.** A person removed after the host's last floor read, whom the host still admits at the peer door — admission reads the MLS roster the device holds, and a removal reaches that roster through the nest too — can open what that host authors until it next reaches a nest, taken from that host or from another member's device that relays the row and has not learned of the removal either. Never from a nest: that is (c). So decision 2's *never in confidentiality* holds for everything published to a nest and for every rotation a host has read, and is bounded, on the peer plane alone, by what an unreachable host can know — the bound that plane already carries for its writer roster ([`p2p.md`](p2p.md) § Peer-served change-row provenance: the last roster stands offline and honors a recently demoted writer until reconnect). No staleness limit is set on (b): the roster and brake caches beside it carry none, the scenario the peer plane exists for runs for days, and a limit would be a number no user chose. *Rejected:* keeping the hold and re-stating the peer plane's promise as *a file recorded before the outage* — it deletes offline authorship, the own-pending leg's whole purpose, to close a window that needs a removal the host has not seen, the removed person within peer reach, and an outage, all at once; exempting the owner's resident engine — the trigger that exemption rested on was retired 2026-09-27 (the agent re-keys itself, [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § Implementation status today), and it would leave a writer member's identical seal held; a time limit on (b) — above.

**3. The presence plan: every folder this device is a delivery seat for, the account's own or shared with it (the user's answer, 2026-09-30: yes and yes).** Desired sets = (the account's own folders ∪ the folders shared with it) where this device is a delivery seat ∩ toggle-enabled ∖ the sets this device presents another way (apple: a bound location; android: an ingress). An owner's set does not leave the plan when it is shared: being bound to a group changes its keys, not its ownership. **The user's answer (2026-09-30):** a folder shared *with* the user appears in Files (iOS, android) and Finder (macOS) by default, as the user's own folders do, and `folder-on-demand-toggle` renders on a member's row as well as an owner's, so a member can hide it ([`../ui/folders.md`](../ui/folders.md) § Element IDs) — so the arm is ON, and nothing below is gated on a question any more. **What makes a device a delivery seat differs by role, and the difference is forced by where the device roster lives.** For an own folder it is the mode-free rule (*Auto-appear default-ON* above): this device's place has `accepts: true`. For a folder shared with the account it is **the membership itself**: the device roster is the *owner's* — a member's device holds no row in it and has no door to write one (the roster kinds resolve a folder by name among the caller's own) — and the engine already reads a member's absent seat as accepting (`fauna_sync_engine::config::accepts_from_seat`). Accepting the share is the member's yes, the toggle is how one device says no, and the toggle on a member's row is hide-only: it never writes a place. A member's seat is therefore never read through the roster — which is also what keeps a by-name roster read from answering for an own folder that wears the same name. **A shared folder joins once it is accepted, never when it is merely offered.** The nest lists a member row as soon as the owner rosters the account, before the member has joined the group, so the plan admits a shared folder only once the account's custody holds its content keys — the evidence the member's custody-ingest ran — and a folder from another nest once its custody record exists (written at accept; a record with no set name is not bindable and stays out). A stranger cannot put a folder into the user's file browser, and a folder whose keys custody does not hold could not list a single path anyway (decision 2). A shared-with-me set joins under the same per-set toggle, keyed by the same actor-scoped identifier, with the same default (ON — a placeholder tree costs metadata only); its display name carries its owner — `docs (alice)`, the owner's account display label ([`value-formatting.md`](value-formatting.md) § Account display label) — because a member can hold a set that wears the name of one of their own; a cross-nest set carries its owner's canonical `handle@domain`, as its home nest stamped it and the member's own nest verified it ([`../architecture/federation.md`](../architecture/federation.md) § Cross-nest shared folders + channel append → *The cross-nest owner label* owns the stamp, its trust rule and the record's join rule), and its home nest's host until that pair lands. **One mapping, in shared Rust:** `fauna_folders_machine::on_demand_presence::held_sets` turns the member-visible folder list and custody into the plan's input — role, seat, display name, and whether the account only reads the set — so no app maps a row itself. **A reader's host is read-only by construction, not by refusal:** it is built with no write half, the provider advertises no write, create, delete or rename capability on its items, and so the OS never hands it an edit. That is why the rule that a reader runs no engine ([`file-sync.md`](file-sync.md) § Multi-writer shared sets) does not reach it: the rule guards hosts over a directory the user can write behind the engine's back, where an edit that cannot upload would break *a change to a tracked file MUST be uploaded*, and a control-inverted host has no such directory. The host learns which it is from the set's own row at every build and edge, never from its caller: a reader granted `writer` rebuilds two-way at its next refresh, a writer demoted to reader rebuilds read-only at its next write's row read, and a write that reaches a reader's host anyway is refused with a typed refusal before anything is sealed, recorded or moved on disk — its sweep ingests nothing and it drives no re-seal. A writer's host is the ordinary two-way host. A cross-nest set's grant is the home nest's advisory stamp on the custody record (absent ⇒ reader); the home nest's write-token mint stays the enforcement. The binding's reader flag also picks the byte plane's bearer: a reader's engine takes the read token ([`../architecture/federation.md`](../architecture/federation.md) § Cross-nest shared folders + channel append → *Relay serving across nests*), never the write mint, which refuses a reader and would park it as a demoted writer; a writer's takes the write token. **What the two legs this once waited on still owe: nothing.** Member custody-ingest and the `writable_folder` gate family are built ([`../ui/folders.md`](../ui/folders.md) § Sharing → *Member custody-ingest read leg*; [`file-sync.md`](file-sync.md) § Multi-writer shared sets, same-nest).

**Two-way on-demand folders — LANDED 2026-07-14 (USER-ratified the same day; § On-Demand Files → *Sync direction*).** The Windows on-demand host uploads local edits, so a tracked file's change reaches the nest from an on-demand folder exactly as it does from an always-resident one. No new user-facing setting was needed: two-way is simply what a synced folder does.

*What it was.* The host was **one-directional**, in breach of the iron rule. Measured live 2026-07-14: a user edited a tracked placeholder; two subsequent rescans logged `placeholders=0`, the `transfer_queue` stayed empty, the sync-state row stayed `placeholder`, and the badge went on claiming `CloudOnly` — the edit was neither uploaded nor surfaced as a conflict. The root cause was a **missing capability wearing a policy's clothes**: `run_on_demand_root` constructed no file watcher, so Windows had no way to *learn* a local write had happened, and the code's own promised remedy (*"a later reconcile pass resolves the conflict"*, at the invalidation gate) was never built — `run_hydration_loop` had only cancel / rescan / reconnect / fetch arms. It had been written up as "download-only by design"; it was a bug.

*How it works.* The on-demand root drives the **shared** `fauna_sync_engine::always_resident` watch→`upload_file` loop — **one uploader, not a second implementation** (priorities #2/#4). `run_hydration_loop` now runs `LocalWrites` (watcher + debouncer + `is_user_write`) as one cancel-safe `select!` arm alongside the cfapi read callbacks, plus `LocalWriteHost::converge` (drain → reconcile → `upload_pending`) at startup and on the rescan tick as the backstop for edits made while the service was down. **The rule is enforced by the type system, not by a comment:** the write half is the shared `LocalWriteHost` trait, and the host's `HydrationHost` **requires it as a supertrait** — so a download-only on-demand host no longer compiles. (`libs/fauna-cfapi` registers no `NOTIFY_*` callbacks *for the upload path*, and does not need to: the shared `notify` watcher — `ReadDirectoryChangesW` under the hood — observes the write, and the placeholder guard is what makes that safe on a cfapi root. It *does* register `NOTIFY_DEHYDRATE_COMPLETION`, but only to keep the sync-status **row** honest when the OS frees a file's space — a read-only observation, entirely outside the write path; see § Per-file sync-status display → *Windows OS shell-overlay carve-out*.)

*Two consequences worth naming.* (1) **`EngineRole` is gone.** It existed to hand the on-demand root an *empty* `IgnoreMatcher` ("a download-only host makes no local writes to ignore") — which became a bug the moment the root uploaded, since an ignored file would be uploaded the first time the watcher saw it. Both roots now load `.faunaignore`, the role had no other effect, and it was deleted. (2) **Backup + on-demand is fixed by construction.** A `Backup`-mode set bound to an on-demand folder used to be inert in *both* directions — and because no change was ever *recorded*, the snapshot scheduler never ran either, so there was **no point-in-time recovery at all** (`backup-restore.md` § Snapshot scheduling). Backup has no separate change detector: it *is* this shared watch→upload loop. Since the folders re-model's phase 3 head unification (2026-08-17), an ordinary folder — a backup one included — records to `sync_changes` exactly like any other; only a **reserved** (`__*`) custody-copy cross-location backup-destination set routes to `backup_custody` (`is_reserved_custody_copy`, `bins/fauna-nest/src/db/snapshots.rs`).

*Pinned by* `cfapi_live_integration.rs` — headless, against a **real cfapi sync root**, with the **real `SyncEngine::upload_file`** (the harness host delegates its write half to a production engine; only the three nest-facing calls are faked, and the byte plane is a wiremock nest so an upload has somewhere to land): `a_local_edit_by_another_process_is_detected_and_uploaded` (which *also* pins that hydration must **not** echo straight back up — the watcher sees our own hydration write, and only `mark_hydrated`'s recorded content identity stops the re-upload) and `a_backup_mode_set_on_an_on_demand_folder_uploads` (a new file is adopted and uploaded, **while the cloud-only placeholder beside it is never touched** — our own `CfExecute(TRANSFER_PLACEHOLDERS)` materializes files the OS reports as ordinary `Created` events, so telling them apart is the watcher's job).

**The placeholder-safety guard is LANDED (2026-07-14)** — the prerequisite, and the half that was actively dangerous. `fauna_sync_engine::placeholder` now recognizes a cloud-only placeholder from OS file attributes; `ScannedFile::is_placeholder` carries it; `reconcile` skips them (without dropping them from the delete-detection set); and `upload_file` refuses one outright, so the failure is unrepresentable whichever caller reaches for it. Pinned by three live-cfapi tests (`a_cloud_only_placeholder_is_never_uploaded`, `a_dehydrated_file_is_never_recorded_as_a_delete`, plus the unit predicate), both **sabotage-verified**: removing the reconcile skip makes a 3-placeholder pass take **362 s**; dropping placeholders from the scan makes a merely-dehydrated file record a **delete** on the nest. See § On-Demand Files → *A placeholder is present-but-unreadable*.

**The hydration→upload feedback loop is CLOSED (2026-07-14), and the recorded diagnosis of it was wrong.** It was written up as a watcher problem — "a naive watcher cannot tell the provider's own writes from the user's" — but its root cause was a **dishonest row**, and it fired through `reconcile` just as surely as through any watcher. `SyncEngine::mark_hydrated` recorded *only* `state = Synced`: no `local_hash`. Both upload paths decide "did this change locally?" by comparing exactly that field (`upload_file`'s *already synced, skipping* short-circuit and `reconcile`'s re-hash branch both test `entry.local_hash == Some(file_hash)`), so a freshly-hydrated file — `Synced`, `local_hash: None` — read as **locally modified** to both, and a two-way root would have re-uploaded every file it just downloaded, bumping a nest version per hydration. `mark_hydrated` now records the served content's identity (hash + size + mtime), which closes both paths with one change; a watcher-level suppression (`was_recent_download`) closes neither, being consume-on-check and not surviving a rescan. A **partial** hydration (cfapi may fetch only the range a reader asked for) deliberately records no identity — the placeholder guard keeps the file out of the upload path until it is genuinely local.

⚠ **The recorded identity is NECESSARY but NOT SUFFICIENT, and reading it as sufficient cost three sessions (corrected 2026-08-04).** Since the ack-honesty pass the skip also requires the row's **hydration anchor**: `if let Some(recorded_manifest) = entry.manifest_hash && entry.recorded_content_hash == Some(file_hash)` — it must return that manifest as the recorded head, and a proof-less `Synced` row deliberately re-drives upload + record instead (a failed record must stay retryable). So a row with a correct `local_hash` but **no `manifest_hash`** still re-uploads. That shape is unreachable in production — `record_placeholders_from_changes` writes `Some(manifest_hash)` on every placeholder row it records (0-byte included; `download_file_bytes` resolves the fetch manifest from that very field, so a `None` could not hydrate at all), and `update_recorded_head` sets it after every successful upload — but it *was* reachable in the `cfapi_live_integration` harness, whose seed wrote `manifest_hash: None` while faking `download_file_bytes`. That single unfaithful seed is what failed `a_local_edit_by_another_process_is_detected_and_uploaded` (`left: 1, right: 0`) from that change onward. It was reported and hoisted as an **engine regression in `mark_hydrated`**, chased as one across sessions, and left standing as a known-red that four sessions routed around; the engine was innocent throughout. Fixed 2026-08-04 by making the seed faithful, with the row's local identity now asserted separately from the upload count so a future red names which half broke.

⚠ **The remaining hazard for the wiring itself: the provider's own placeholder *creation* looks like a user's file creation.** `CfExecute(TRANSFER_PLACEHOLDERS)` materializes files in the root, and a `notify` watcher reports each as an ordinary `Created` event that `was_recent_download` does **not** cover. The placeholder guard above is what makes a shared watcher safe on a cfapi root; `LocalWrites::is_user_write` applies it at the source. **`is_user_write` also drops directory events outright (fixed 2026-07-17):** a directory is never uploadable content — a folder carries directories only implicitly via child paths — and every write *inside* a folder also raises a `Modified` event on the folder itself, so before this fix each child edit re-queued the parent directory and `upload_file`'s read of it logged a fresh error.

**In a metadata-only folder a seat's own record is not a dehydration proof (ruled 2026-10-01; BUILT 2026-10-04 in the shared gate).** The nest took no bytes, so the head cannot be fetched back from it. The rule, its reach — *free up space*, OS eviction, the cache-root demotion — and what is built and still unarmed are owned by [`file-sync.md`](file-sync.md) § Relay serving → *A holder keeps what it wrote* and that section's status paragraph. Here it means `is_dehydration_safe` answers *not safe* for such a body, so every road in this doc that takes the gate refuses it the way it refuses an unrecorded edit, with the same refusal shown to the user; the in-sync assertion of the next paragraph takes the gate too, so such a file is not vouched in-sync. A stale hydrated copy that is such a body is not freed and re-pointed like the others: its seat fetches the new head over it first — same owner, *A superseded own-record body is replaced, never freed* (ruled 2026-10-04).

**A recorded upload flips the file to the platform's in-sync state — LANDED 2026-07-17.** Until this landed, nothing ever told Explorer (or the sync-state row) that a two-way upload had actually finished — the Status column kept its sync-pending arrows on a file that had synced perfectly (measured live: `stale_hydrated=2`, only the dirty-file dehydrate refusal protected the bytes). The windows hydration loop now follows `apply_local_write`'s `LocalWriteApplied::recorded` — the rels whose `fauna.sync.changes.record` reached the nest, carried out of `SyncEngine::upload_file`'s new `UploadOutcome { recorded }` — with `flip_recorded_in_sync`: a still-cloud placeholder gets the in-sync assertion alone; an ordinary file (locally created, or an editor's replace-save destroyed the placeholder's reparse point) is first re-anchored as a **hydrated, not-in-sync** placeholder (`fauna_cfapi::convert_to_placeholder_anchored` — `CfConvertToPlaceholder` with no flags, the folder-relative path as its `FileIdentity`) and then takes the same assertion — bytes stay local either way. The flip keys on **recorded**, never on upload alone: bytes that reached the nest without a successful change record are unreachable for later hydration, so marking them in-sync would license a data-destroying dehydrate. It runs before the pin-reaction arm in the same tick, so an edit-then-unpin inside one debounce window sees the file already in-sync when its dehydrate is attempted.

**Recorded is necessary, not sufficient: the flip vouches only for the recorded content, atomically (2026-09-28).** The upload read the file before its record landed, so a save landing in between (an autosaving editor, a large file) is on disk when the flip runs — and that save has already tripped `CF_INSYNC_POLICY_TRACK_ALL`'s not-in-sync bit, the one refusal every dehydrate caller relies on (the pin reaction's bare dehydrate, a remote change's stale-hydrated invalidation, the shell's *Free up space*). An unconditional flip cleared it, and the next dehydrate freed the only copy of the newer edit. So every in-sync assertion on a FILE — this flip and the pin reaction's stale-refusal repair alike — goes through one road, `bridge::assert_recorded_in_sync`: (1) anchor an ordinary file not-in-sync (vouching for nothing, so safe unproven); (2) read the file's USN (`fauna_cfapi::file_usn`); (3) prove the disk is the recorded content (`SyncEngine::is_dehydration_safe`: row `Synced`, disk hash == `recorded_content_hash`); (4) assert in-sync only if the USN has not moved — `fauna_cfapi::set_in_sync(path, usn)` opens the file with a share mode that shuts out every other writer, deleter and renamer, re-reads the USN through that handle, and calls `CfSetInSyncState` on the same handle. A write landing any time after step 2 refuses the assertion, and none can land between the re-read and the call, so the bytes step 3 hashed are the bytes vouched for, or nothing is. A file another process holds open for writing refuses too (the next recorded upload retries), a volume with no USN journal (USN 0) never flips (honestly pending), and **no file is ever marked in-sync by a convert** — `CfConvertToPlaceholder` takes no USN condition, so the former `MARK_IN_SYNC` file convert and the pin repair's one-op `MARK_IN_SYNC | DEHYDRATE` convert are retired (`convert_to_placeholder_in_sync` now refuses a file; it serves the directory flip below). Why not cfapi's own condition: `CfSetInSyncState`'s `InSyncUsn` was measured on Windows 11 ARM64 to refuse `0x80070179` for every value, including the exact USN read through its own handle, so it cannot express "not written since" and is never sent. The shell's *Free up space* verb additionally gates on `is_dehydration_safe` itself (`pipe_server::handle_free_space`, via `SyncEngine::is_dehydration_safe_in` over the folder's state DB), so it does not depend on every in-sync assertion ever made being right. Pinned by `the_flip_never_vouches_for_a_save_newer_than_the_recorded_content`, `a_save_landing_during_the_proof_refuses_the_in_sync_assertion`, `the_free_space_gate_frees_only_the_recorded_content` (unit, any machine), live against a real root by `a_save_during_an_upload_survives_the_in_sync_flip_and_a_free_up_space` and `a_save_between_the_proof_and_the_in_sync_assertion_is_refused` (`cfapi_live_integration.rs`), and the OS fact itself by `live_population::set_in_sync_refuses_a_write_newer_than_its_usn`.

A second, coupled cause made the same symptom worse: the upload path deliberately left the row's `manifest_hash` at the pre-upload merge base (a record in flight may still fail), but the fold's stale-hydrated-row comparison (`file-versions.md` § Implementation status today → *Stale hydrated copies invalidated at service start*) reads that same column as the local head's identity — so once a record **succeeded**, the row still looked stale against the device's own echoed record, and the next fold queued the user's own fresh edit for dehydration as if it were a superseded remote copy. `SyncEngine::commit_recorded_head` now stamps the row (manifest + size + content-key generation) in both upload paths' record-success arms; a failed record still keeps the base, so a genuinely-failed upload is not falsely declared current.

**A folder whose known subtree is fully synced flips too — LANDED 2026-07-17.** The file-level flip above left every containing folder showing sync-pending arrows forever — directories were never flipped at all. The new shared predicate `SyncEngine::subtree_fully_synced(dir)` reports whether at least one live row exists under `dir/` with none in-flight or diverged (a cloud-only `Placeholder` child counts as synced, a `Deleted` tombstone is neutral, and **no rows at all is `false`** — a folder carries directories only implicitly via child paths, so an empty directory exists on no other device and must keep its honest pending state rather than claim a sync the fleet will never perform). After each file-level flip, `flip_clean_ancestor_dirs` walks every distinct ancestor of the batch's recorded rels, deepest-first, and flips each whose subtree is clean — `set_in_sync` for an already-cloud directory, else `convert_to_placeholder_in_sync` (which now opens with `FILE_FLAG_BACKUP_SEMANTICS` so a directory handle works at all). Never byte-freeing, same as the file-level flip.

Both flips are unit- and live-cfapi-tested (`a_recorded_upload_head_is_not_stale_on_the_next_fold`, `a_genuinely_moved_nest_head_still_classifies_stale`, `flip_recorded_in_sync_picks_the_repair_by_cloud_file_ness`, `subtree_fully_synced_requires_a_live_clean_subtree`, `clean_ancestor_dirs_flip_after_their_files`) and live-verified on a real box the same day (files flip to ✅, the next fold logs `stale_hydrated=0`, folders flip too). **Remaining leg** (tracked internally): the new directory `convert_to_placeholder_in_sync` path lacks its own live-cfapi test. The other two gaps this paragraph once named are closed, both fixed 2026-07-18: the *converge* backstop (rescan catch-up, offline edits, the startup-converge race) flips ✅ exactly like the live watch-loop arm, and `is_dehydration_safe` now also requires `recorded_content_hash` to match the disk hash, so an uploaded-but-record-failed edit fails the gate and is never dehydrated.
