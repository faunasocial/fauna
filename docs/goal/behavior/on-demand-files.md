## On-Demand Files (Placeholders)

A folder can be marked **always-resident** (every file kept on disk) or **on-demand**. In on-demand mode a synced file appears in the platform file browser as a **placeholder**: it shows the right name, size, and modification time but occupies no local space until it is opened or the user picks "always keep on this device". Opening a placeholder **hydrates** it — the engine fetches that single file's chunks on demand and materializes its bytes — and the user can later **dehydrate** ("free up space") to reclaim disk while keeping the placeholder. Directory listings populate lazily, so browsing a folder never forces a full download.

**The choice is the user's, per folder, per device — and it is remembered.** That is the one promise every platform with a placeholder surface makes, whatever control carries it: on **windows** the per-binding `folder-location-mode-toggle` on the bound row flips *that location* between always-resident and cfapi placeholders (the mode is a field of the binding, `LocationConfig.mode`, persisted by the sync agent in its device-local `config.toml` — never nest state); on **macOS/iOS** the per-set `folder-on-demand-toggle` picks the set's one local presence ([`on-demand-files-apple.md`](on-demand-files-apple.md) § *Apple File Provider binding* — set-level by platform fact, default ON, yielding to a bound location; persisted in the device-local `FileProviderDomainPrefs`); on **android** the same per-set toggle ("Show in Files") shows or hides the set under the provider's Fauna root ([`on-demand-files-android.md`](on-demand-files-android.md) § *Android SAF DocumentsProvider binding* — default ON, yielding to a watched-directory ingress; persisted in the same shared preference store). The switch reads the same after the user leaves the page and returns, and across a relaunch, because the page re-reads the sync host's record rather than holding the choice in view state. **The default a fresh binding takes is platform-scoped, decided in the agent (user ruling 2026-09-26): a fresh windows binding starts on-demand — uniform with apple's default-ON and with the Files-On-Demand default a windows user already knows — while a bound location on every other agent-backed platform starts always-resident.** The one bind verb, the agent's `AddLocation`, gives a NEW path `LocationMode::fresh_binding_default()` (`bins/fauna-sync-agent/src/config.rs`): `on-demand` on windows, `always` elsewhere — on macOS a bound location is always-resident by design ([`on-demand-files-apple.md`](on-demand-files-apple.md) § *Apple File Provider binding*: the binding outranks the FP domain), and a fresh linux binding starts always-resident although its FUSE root can serve an on-demand one ([`on-demand-files-linux.md`](on-demand-files-linux.md) § *Linux FUSE binding*, the flips rule). So on windows the bound directory becomes a cfapi sync root the moment the folder-bind reconcile serves it (Explorer shows cloud-status marks on the user's own directory from the first moment; a big set costs metadata until opened; files already in the directory are uploaded and kept, never dehydrated by the bind), and always-resident is the deliberate second step via `folder-location-mode-toggle`. The default is for NEW binds only: a persisted binding keeps its recorded `mode` (the serde read fallback for a row lacking the field stays `always`, so nothing existing migrates). The app's e2e location channel (`InMemoryLocationControlChannel.FreshBindingMode`) mirrors the agent so the windows witness reads the same start. **The default is the agent's, whichever app binds:** a **tui** running on windows binds through the same agent and so gets an on-demand root — and flips it back from tui itself: tui renders the same per-binding `folder-location-mode-toggle` wherever its agent has a placeholder surface (the user's Rule A ruling, YES for tui, 2026-09-26), built on windows hosts, where the switch sends the agent's `SetLocationSyncMode` and reads the row's mode back off the agent's `ListLocations` (mirrored onto the shared `LocationBindingsModel` row, `BindingRow::mode`). The availability rule is shared Rust — `LocationBindingsModel::mode_toggle` (`libs/fauna-client-sync`), fed by the agent's status reply — and the linux app and tui both read it (tui folds the status reply on its `sync-agent-status` poll), so tui renders the switch on a windows or a linux host and none on macOS. **linux** takes the windows location-level shape — the same `folder-location-mode-toggle` on the bound row, the same `LocationConfig.mode` record — over its FUSE root ([`on-demand-files-linux.md`](on-demand-files-linux.md) § *Linux FUSE binding* carries the status; the toggle's ui.yaml scope grew to linux on the user's Rule A approval of 2026-09-26, built 2026-10-04); tui on a linux host renders no switch until its own arm lands. **android** takes apple's set-level shape — the same `folder-on-demand-toggle` — once its SAF binding lands ([`on-demand-files-android.md`](on-demand-files-android.md) § *Android SAF DocumentsProvider binding*, designed 2026-09-26, unbuilt; the toggle's ui.yaml scope growing to android is likewise a Rule A change asked of the user); until then android renders neither switch.

#### Sync direction: on-demand is a *storage* choice, never a *direction* choice (USER-ratified 2026-07-14)

**Always-resident vs on-demand decides how much of the set lives on this disk — nothing else. Both are two-way by default.** The placeholder vocabulary above is deliberately OneDrive's (hydrate on open, "always keep on this device", "free up space"), and it carries OneDrive's promise with it: a user who puts a folder under Fauna expects edits made there to reach their other devices.

- **Iron-clad — a change to a *tracked* file MUST be uploaded.** If a file is in the folder (it has a sync-state row; it carries a Fauna badge in the file browser), then a local modification to it **must** be uploaded. **No mode, folder setting, or platform host may suppress this**, and no such setting may be offered. A client that badges a file as synced and then silently discards the user's edit has told the user their data is safe while dropping it — a direct breach of *User always controls their data* (`../principles.md`). Where the host cannot observe local writes, that is a **bug in the host**, not a licence to drop the edit: the host must acquire the capability (on Windows, the cfapi `NOTIFY_*` callbacks it does not currently register; see *Implementation status today*). A restore's stale cache is not a change: its bytes are the version the restore replaced ([`file-versions.md`](file-versions.md) § Restore, ordering 2).
- **Remote changes arrive the same way — deletes included.** Another device's create, edit or delete reaches an on-demand folder's disk as it reaches an always-resident one's; how a remote delete is applied there, and what it may never destroy, is [`delete-propagation.md`](delete-propagation.md) § *How a delete travels* (the on-demand bullet).
- **New files are adopted.** A new file placed in a synced folder joins the folder and uploads. There is **no mode, and no badge, for "don't upload new files"** — a *"synced folder that doesn't sync some of your files"* is a surface a user has to hold in their head, and it earns its complexity only if a real need appears (USER-decided 2026-07-14: dropped, deliberately, in favour of making two-way work).
- **Mixed folders — an open future question, with nothing reserved for it.** A folder holding a mix of synced and non-synced files is a coherent thing to want, and if it is ever built it will need its own design (including how a user *sees* which files are excluded). It is **not** a deferred half-built feature: no setting, no badge state, and no overlay-handler budget is being held back for it today.
- **This supersedes the "download-only" clause** that appeared as a parenthetical in `file-versions.md` § Restore ordering rule 3. That clause was never a designed product decision: it was asserted in passing inside an *ordering* rule about a different concern, given no rationale anywhere, and contradicted by the two-way placeholder UX this section describes. It documented what the Windows cfapi host happened to do — it registered only the OS→provider *read* callbacks and so could not see local writes — and that implementation fact was then cited back as intent. The tell is the promise the code itself makes at the invalidation gate ("a later reconcile pass resolves the conflict"): someone knew local edits would happen and would need resolving. Direction is now decided here, in the section that owns it.

#### A placeholder is *present-but-unreadable* — never hash it, never take it for absent (measured 2026-07-14)

A cloud-only placeholder is a file the engine can **see but not read**, and every scan/upload path must hold both halves of that at once. Getting either half wrong breaks the root, in opposite directions — both measured against a live cfapi sync root, not inferred:

- **Never read one.** A cloud provider fires **no fetch callback for I/O originating in the provider's own process** — and the sync host *is* the provider. So the host's own read of its own placeholder is answered by nobody: it blocks for the platform's full recall timeout (**60 s** on cfapi) and then fails (`ERROR_CLOUD_FILE_REQUEST_TIMEOUT`). It does **not** read as empty — `metadata.len()` is the file's *real* size — so there is no "upload emptiness over the nest's copy" hazard. The hazard is **liveness**: those 60 s burn on the single driving thread that also *serves* hydration, so an N-placeholder set spends N × 60 s unable to hydrate anything while still logging "reconciliation complete". A hash-and-upload pass over an on-demand root therefore does not corrupt the nest; it silently **kills the root**.
- **Never mistake one for absent.** A placeholder is *present*. A scan that simply omits them makes the reconcile's delete-detection see a `Synced` row with no file behind it and record a **delete on the nest**, propagating the deletion to every other device — and the user reaches exactly that state through Explorer's ordinary *"Free up space"*. **Freeing disk space must never mean erasing the file.** This is the real data-loss path, and it is *created* by the naive remedy for the stall above. Which rows the mass-delete floor counts on a root of placeholders, and why the lazy population makes that restriction load-bearing, is [`delete-propagation.md`](delete-propagation.md) § *A wholesale-vanished folder* → *The floor on an on-demand root*.

So the scan **reports** placeholders and **flags** them: skipped by the hash/upload path, counted by the delete path — and which placeholder rows the delete path may count, live or across a downtime, is [`delete-propagation.md`](delete-propagation.md) § *A wholesale-vanished folder* → *The floor on an on-demand root* (rule (2) and *An offline placeholder delete propagates*). The client detects them from ordinary OS file attributes (on Windows `FILE_ATTRIBUTE_OFFLINE` / `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`), which a hydrated file no longer carries — so the guard cannot suppress the very uploads two-way sync exists to deliver.

**The empty-file special case — a 0-byte placeholder is present-and-empty, and badges `Synced` (measured 2026-07-15; implemented).** A 0-byte file has no bytes to fetch, so on an on-demand root the platform fires **no** fetch callback when it is opened — on cfapi, opening a 0-byte placeholder *clears* its `OFFLINE`/`RECALL` bits (the file is genuinely present-and-empty on disk) but delivers **no** `FETCH_DATA`, so the mark-hydrated step that flips a normal file to `Synced` never runs. The row therefore can never leave `Placeholder` via the fetch path. It is **not** promoted to `Synced` at population either: a `Synced`-while-not-yet-materialized row would be erased by reconcile's delete-detection (which scans `Synced` rows for on-disk absence) — a data-loss trap. So the engine row **stays `Placeholder`** (carrying the empty-content identity, so a later reconcile that finds the file present-and-empty leaves it stable rather than re-uploading it), and every **badge** reads it as `Synced` through the shared size-aware mapping `SyncState::effective_for_size(size_bytes)` — a 0-byte placeholder is present-and-empty, not cloud-only. A folder whose only tracked descendants are 0-byte files therefore reads `Synced`, not `CloudOnly` (the folder-badge fold applies the same mapping). Keeping the rule in shared Rust — not in a per-platform fetch callback — means a macOS File Provider inherits the identical empty-file case (priority #2).

The placeholder *surface* is platform-specific (Windows Cloud Files API, macOS File Provider, a Linux FUSE/overlay), but the **hydration primitive is shared**: `fauna_sync_engine::SyncEngine::download_file_bytes(relative_path)` resolves the file's recorded manifest from the state DB and returns its reassembled, decrypted bytes — the platform's fetch callback hands those to the OS. See `docs/goal/architecture/apps/windows.md` § Shell Extension for the Windows cfapi binding.

**A placeholder describes the version its row resolves — and an open that finds it does not is refused, never served (measured 2026-10-08).** cfapi asks the provider for exactly `[0, the placeholder's size)`, and the size lives in the placeholder on the disk, not in the row. So whenever a remote edit or a restore moves a row to a version of another size, the binding moves the placeholder with it — size and mtime, the bytes freed, in one `CfUpdatePlaceholder` that is refused unless the file is in sync (`fauna_cfapi::supersede_placeholder`; the orderings are `file-versions.md` § Restore's). A bare dehydrate keeps the old size: the 2026-10-08 native seat pair's peer was served a 248-byte edit's first 6 bytes, recorded them, read them back as its own edit and uploaded them over the real one. As defence in depth the fetch compares the size the OS holds for the placeholder (the callback's `FileSize`) with the version's length and FAILS the transfer on a mismatch (`bridge::serve_fetch_chunked`), so no path that leaves a placeholder behind its row can land a truncated file. **A placeholder found behind its row heals from the row (2026-10-09).** The refused open owes the placeholder a re-describe to its row's size and mtime (`bridge::owed_redescribe`, the same superseding update, so a file carrying a local edit is still refused and untouched), and so does the OS's notice of its own eviction. The serve loop tries it a second later, then less often while a program holds the file open (`bridge::PendingRedescribes`), never at the refusal itself: the platform retries a refused read at once, and the update waits for that fetch. Run on the loop at the refusal, the update held the root for cfapi's 60 s timeout (measured 2026-10-09). **No update the serve loop makes can hold up the root (2026-10-10).** Every cfapi call that changes a cloud file waits for any outstanding fetch of that file: the superseding update, with or without its free; a bare dehydrate; the in-sync assertion; a pin or an unpin; and the pinned file's replacing rename. Only the root's own serve loop answers a fetch (measured, `cfapi_live_integration::diag_calls_that_wait_on_an_outstanding_fetch`). So the loop makes each of those calls on a thread of its own and goes on answering the platform's fetches and listings until it is back (`bridge::PlatformCall`, `bridge::PlatformRequests::answer_while`). That covers the fold's re-describe and its free of a superseded copy, a restore's apply, the pin reactions, the in-sync flips and the owed re-describe alike. A program opening a file as another device's edit lands therefore waits on nothing but its own answer, and every other open on the root is served meanwhile. A fetch answered while an update of its file is out can record the file hydrated just before the update frees it, so a re-described file is recorded freed afterwards. The calls that wait on no fetch stay in place: an unlink (refused at once while a program holds the file), a new placeholder, and the anchor of an ordinary file or directory. This provider's own free of a file whose row moved past its bytes leaves it describing the row's version. So whatever left the placeholder behind — a re-describe or a restore's free refused, a bare eviction since — the user's retried open is served. The refusal fails the open at once: it names the range the platform asked for (`fauna_cfapi::transfer_failed`). Until 2026-10-09 it named none, and the opening program waited out cfapi's 60 s request timeout. The FUSE and File Provider bindings read size and mtime from the rows, and have no copy on the disk to go stale. **Nothing the serve loop waits on holds up the root (ruled 2026-10-10).** The loop answers the platform's fetches, listings and hydrations across every wait it makes — a platform call, as above, and equally an upload of a local write, a sweep's converge and corpus passes, a re-pull of the nest, and an engine command's answer — never only between its arms. Otherwise an open of any cloud-only file waits for whichever arm is out: a large upload on a slow uplink, or a re-pull against a nest that is down, holds every open on the root past cfapi's 60 s request timeout and the opening program fails, and on linux a listing of the root waits with it. The engine permits the interleaving: it is driven on one thread and makes every state change in one synchronous call between its waits, so an interleaving never tears one; a fetch's own engine work is one row read before its download and, in the same poll as its last transferred byte, the row's hydration mark, which re-reads the row and so keeps whatever version it moved to meanwhile (the recorded-freed-afterwards rule above covers the one such move); a listing is a synchronous read and a seen mark; and the write half already interleaves its uploads with each other (`SyncEngine::upload_pending`). What an arm holds across a wait is its own file's state, and a file is never a fetch's and an upload's at once — an upload needs the bytes on this disk, a fetch their absence, and a file carrying an edit is never dehydrated. Two things stay true for this: a hydration marks its row with no wait between its last byte and the mark, so no scan meets local bytes under an unmarked row (a scan would re-hash it and the write half re-upload it); and the requests the loop does not answer meanwhile — a notice, an unlink — still wait for the arm, in the order they came. **A file kept on this device — pinned, Explorer's *Always keep on this device* — is replaced, never freed (decided 2026-10-09).** cfapi refuses that update, and a bare dehydrate, on a pinned file (`0x80070188`), and freeing it would break the keep anyway. So the new version is fetched into a dot-named sibling and swapped in by one rename of a placeholder that already carries the pin (`fauna_cfapi::replace_placeholder`). The swap is refused unless the file is in sync, under a handle that shuts out every other writer: the same dirty-file refusal the update makes, so an unsynced local edit survives whole. Only then does the row move, and the new bytes are vouched in sync. The device holds one whole version, and the pin, at every instant. A pin the agent set on a body it keeps is the same OS pin; while the holder-keeps gate still keeps that body, the body takes its own replace road (the next paragraphs).

**The three surfaces are all built, not equally far — the Linux FUSE root is the youngest (direction decided 2026-09-26; the agent's root built 2026-10-01/02, the linux app's switch 2026-10-04).** Windows' cfapi provider and Apple's File Provider are live (see the status paragraphs under [`on-demand-files-apple.md`](on-demand-files-apple.md) § *Apple File Provider binding*); the **Linux FUSE mount is a ratified design built through its lifecycle** (2026-10-02: it mounts, lists, hydrates on open, passes every other operation through, frees space, keeps pins, flips both ways and is unmounted by a crash guard after a crash; the linux app renders its switch, tui not yet) — [`on-demand-files-linux.md`](on-demand-files-linux.md) § *Linux FUSE binding* is its owner and carries the status. So a Linux location binding starts always-resident and goes on-demand by the bound row's switch: `tests/e2e-unified/ui.yaml` § `folders` scopes `folder-location-mode-toggle` to windows, linux and tui-on-a-windows-host, and `folder-on-demand-toggle` to macos+ios. What the linux root does not do yet is named in [`on-demand-files-linux.md`](on-demand-files-linux.md) § *Linux FUSE binding*'s status paragraph. The direction question that stood here until 2026-09-26 — build a real placeholder provider, or declare linux always-resident *by design* — was answered by the user: **build it**, with the `fuser` crate and the distro `fusermount3`.

**Who runs the hydration host, and the keys it holds.** The fetch callback must *decrypt* the file's chunks, so whatever process serves hydration must hold a decryption key — and the placeholder surfaces (Windows cfapi, macOS File Provider) run in **separate, out-of-app processes** from the identity-holding UI. Per the key-hierarchy doctrine that keeps the identity seed on user-trusted full clients only (`docs/goal/architecture/key-material-hierarchy.md` § Roots + rule #6) and hands content-serving helpers a *minted, least-privilege capability* rather than the root (rule #7 — the blast-radius invariant, realized for mail by the MDA bridge's MSEK), the hydration host is **never given the identity seed**. It runs in the user's logon session — so it shares the identity-holding app's trust boundary (handing a same-session helper a derived key adds no attack surface the seed-holding app in that session doesn't already present) — and the app provisions it with the narrowest capability that suffices:

- **Phase 1 (today's at-rest shape).** Ordinary file chunks are sealed under the owner's `BackupKey` (§ Content-Addressed Storage; `owner-key-material.md` § Audience: owner only Path A), the *only* key that opens them — so the app hands the host the `BackupKey` plus a renewable nest bearer. `BackupKey` is broad (it opens *all* of the user's owner-only content) and un-revocable short of seed rotation; that breadth is acceptable **only** because the host shares the app's user-session trust boundary. It must never be handed to a more-exposed context (a LocalSystem service, another machine).
- **Phase 2 (target).** When per-folder keys land (the `chunk_crypto` / MLS-`epoch_secret` path, `mls-group-key-material.md` § Audience: an MLS group; forward-looking today), the host is handed only the on-demand folder's key — a narrow, revocable capability, doctrinally identical to the MDA bridge's MSEK. This is the end state; Phase 1 is the expedient the same-session boundary makes safe. How a Phase 1 host comes by a *shared* set's keys, and the one constraint that already binds Phase 2's delivery, are [`on-demand-files-shared-sets.md`](on-demand-files-shared-sets.md) § *Shared sets on a capability host*.

This is the **uniform cross-platform shape** for on-demand file providers: the identity-holding app holds the seed and full authority; the out-of-app hydration host (Windows cfapi helper, macOS File Provider extension) is a same-user, session-scoped delegate holding only a minted decryption capability — the same "app provisions a capability to a helper" pattern fauna already uses for the mail bridge, not a per-platform invention.

**Hosting multiple on-demand folders (multi-root).** A user may mark more than one folder on-demand, and **each on-demand folder is its own folder** (§ Selecting Folders to Sync — one folder ↔ one named folder). The on-demand host therefore serves **N folders concurrently — one provider root per folder** (a Windows cfapi sync root, a macOS File Provider domain, a Linux FUSE mount), each backed by **one bearer-only `SyncEngine` keyed by folder**, each scoped to that folder's changes (the engine is built `folder = Some(name)`, so it folds *only* that set's `changes.list` into placeholders — never the actor's whole change history under one root), with a **per-folder state DB** (`fsid-<ref>.db`, keyed by the set's identity — the next paragraph) and a **single shared device id** (`device.db`) so the nest sees one device, not N. All engines share **one** least-privilege capability — in Phase 1 the owner `BackupKey`, which decrypts every folder's chunks, so multi-root needs **no** additional keys; Phase 2's per-folder key narrows this to one capability per engine.

**A location binding identifies its set by a `FolderRef`, not by name (BUILT 2026-07-29).** Folder names are unique only **per owner** (the nest enforces `UNIQUE(name, actor_id)`), so a user who owns "docs" *and* is a member of someone else's "docs" cannot say by name which of the two a location is bound to. Every seam that must tell one running engine from another therefore keys on `fauna_core::folder_keys::FolderRef` — the engine registry, the pushed engine-key blob entry, and the per-set state DB — and it has two structurally disjoint arms: **`Local(<nest folders.id>)`** for any set with a row on this holder's own nest (owner-only, owner-shared, served, *and* same-nest member rows), and **`Foreign(<derived ChannelId>)`** for a cross-nest set, which has no row here at all. The rule is chosen by *where the set lives*, never by the caller's role in it, and is resolved in one shared place (`fauna_client_folders::engine_binding::folder_ref_for_row`) so the apps cannot drift on it; the wire plane keys on the same ref — a sender holding the row stamps it on every per-set request ([`set-addressing.md`](set-addressing.md) § The row form). The same one-resolver discipline holds on the agent's own IPC surface: the absolute-path router (`path_map::resolve_to_folder_rel`) carries the binding's ref, so the overlay-status, folder-badge, dehydrate-record and restore-re-point reads all open the identity-keyed state DB the engine actually writes — never a re-derived name-keyed path (the four readers' name-keyed drift was fixed 2026-07-29). The ref is **stable across the set's lifecycle** — becoming shared, or having the WebDAV serve flag flipped, does not change it — which is what lets an existing binding survive those transitions.

**The ref is the binding's only key; the name is a label.** There is one bind verb — `SetLocationFolder { path, folder, folder_id }` on the app↔agent IPC, with `folder_id` required and refused unless it parses — and every seam downstream of it resolves by the ref alone: the agent's `config.toml` row is read as bound only when it carries a label **and** a parseable ref (`LocationConfig::binding`), a `FolderEngineKeys` blob entry must carry the ref (an entry without one is refused at decode), and a blob with no entry for the bound ref answers **unbound (fail closed)** — the only same-named candidate would be a different set, precisely the wrong answer the ref exists to refuse. A row `folder_ref_for_row` yields no ref for (a cross-nest row with a malformed group id) is **refused** at the bind gesture, on the page's error surface, never bound by name. Per-set state DBs live in their own `fsid-<ref>.db` filename namespace. The verbs that still address a set by name (`PullFolderNow`, `ApplyHeldDeletes`) are only a lookup into this device's bindings — one binding wearing the name resolves to its ref, several are refused as ambiguous, none is "not served" — never a name used as a key. The seat's per-tick policy read (`fauna_sync_engine::config::resolve_device_mode_from_nest`, which carries the audience, residency, website, selective-sync and exclusive-editing facts off one `fauna.folders.list` read) resolves its row by the same key (`binding_edge::SeatRowKey`): an engine by its binding's ref, and one holding no ref reads no row — every field's sealed / fail-closed direction; the headless daemon, whose wiring named only the set, read a row only while exactly one listed row carried that name, and read none — sealed — when the user owned a set of the name *and* was a member of another (until its removal, 2026-10-02). A member seat on a shared "docs" therefore never adopts its user's own public "docs" and arms the plaintext upload arm on the shared set. The name-keyed binding a pre-identity peer used (the ref-less verb, the name fallback in every resolver, the `fs-<name>.db` adoption rename, the `location-map.json` migration seeds) was retired in place 2026-09-24 by the compat-remnant sweep ([`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 2, the fourth exception). **Status:** built on the shared seam, the agent, linux, tui, windows and macOS (every app's bind gesture resolves the ref through the shared `folder_ref_for_row` — `FaunaFfiMethods.FolderRefForRow` on windows, `FolderSummary.folderRef` on macOS — and calls `bind_location(path, folder, folder_id)`); iOS has no location-binding surface of this kind (its File Provider domain binding is a separate mechanism, unaffected); android has no location-binding surface. The in-app `FfiSyncEngineHost` binds no location either: its resident half (`start_engine` over a `location-map.json` whose `folder_id` was optional) was retired 2026-09-25, since nothing called it. **The in-process hosts are ref-keyed too (built 2026-09-25):** that host's construct-run-drop calls — the library-ingress `ingest_file`, the `file_states`/`transfer_backlog` reads, the `sync_file_states` steward read, the `sync_set_unrecorded_rels` removal gate — and the File Provider host's constructor take the set's `FolderRef` wire string (`folder_id`, refused unless it parses; `fauna_ffi::sync_engine_host::parse_folder_id`); `engine_lifecycle::build_engine` opens `fsid-<ref>.db` (`FolderRef::state_db_path`, the one join every writer and cross-process reader shares) and resolves the set's row by identity (`summary_for_ref` over this nest's own list — a cross-nest ref, or a ref the list does not carry, refuses), taking the set's name from that row; the photo-library resolver (`photo_library_set`) returns the set's identity beside its name and binds the device by identity, so a renamed photo set stays the target; the Media page snapshot carries each filter option's identity (`folder_options`) so a badge read keys on it. No app hands a name to these seams: android's watched-directory row stores the ref of the set the user picked from their own folders (`ownFolderChoices`, each row's ref through the shared `folder_ref_for_row`), so a rename of that set keeps the directory feeding it; the ref is required at rest (`watched_directories.folderId` is `NOT NULL` since Room schema 9), and the one-time resolution of a ref-less row from its name label was retired 2026-10-01 as a compat remnant ([`../architecture/compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md), the early audit pass's reading (1)).

The host multiplexes its N engines exactly the way the Linux in-process client already does (`apps/linux.md` § File Sync): a **single driving thread with a current-thread runtime polls every engine future inline** (the engine is `Send` but `!Sync`), keyed by folder, with **live start/stop** so marking a folder on-demand (or back to always / removing it) adds or drops one provider root without restarting the others. This multiplexer is the **shared `fauna_sync_engine` multi-engine driver**, generic over the per-engine loop and a per-engine teardown: Linux supplies an always-resident watcher loop (teardown = drop the `FsWatcher`/inotify); the on-demand host supplies a hydration-command loop and registers an OS provider root per engine (teardown = unregister the provider root + drop its callback-routing entry). The platform's fetch/enumerate callbacks route to the right engine by the provider root's identity — **on Windows the cfapi `CF_CONNECTION_KEY`**, on macOS the File Provider domain identifier. The uniform shape is thus: **one shared multi-engine driver + the shared `download_file_bytes` primitive**, with each platform contributing only its OS provider-root binding (cfapi / File Provider / FUSE) and the per-root callback routing — never a per-app driver. One carve-out, ratified with the Apple binding (2026-07-18): a **control-inverted** provider surface has no driving loop for the shared driver to drive — `fileproviderd` itself instantiates one extension object per domain and routes callbacks by domain identifier, so the Apple extension holds one independent request/response host per domain ([`on-demand-files-apple.md`](on-demand-files-apple.md) § Apple File Provider binding, *the extension hosts the engines*) and the shared multi-engine driver applies to the *self-driving* hosts (the Windows cfapi service, Linux, a future FUSE root).

#### The free-up-space gesture where the OS offers none (designed 2026-10-04; advisory until the user's Rule A ruling on its ids; UNBUILT)

Windows gets *Free up space* and *Always keep on this device* from Explorer, apple from Finder and Files, android from the system's cache reclaim. A linux desktop has no such verb for a FUSE root, and a terminal has none anywhere, so there the gesture has to be the app's: without it a file once opened stays on the disk for good and an on-demand folder only ever grows. This section is that gesture's owner. Nothing in it is built; the ids it proposes are **asked of the user and unanswered**, and a NO from the user turns the section into the decision that linux keeps no such gesture.

- **The surface is the bound row and the unit is the location.** Each bound row whose binding is on-demand, and whose placeholder surface stands (no `on_demand_mount_error`), carries one verb: **Free up space**. It frees every file under that location that is on this device, not kept, and provably recorded — exactly what Explorer's verb does on a folder — and leaves every other file where it is. Why the row: it is the one surface in every app that is keyed by a local binding and already speaks to the agent, and it is the same control on tui and the desktop apps. Why not the Media page: Media lists a set's content from the nest, a set may be bound here twice or not at all, and no app reads a per-file presence from the agent — a per-file action there would be a second file browser beside the user's own. Why not a file-manager extension: it is one integration per desktop (Nautilus, Dolphin, Nemo, Thunar), third-party code on its own install channel, and it gives tui nothing; it stays a separate question for the user, never a silent follow-on.
- **Every app that renders the switch renders the verb (priority #1).** The rule is the row's, not the host's: `folder-location-mode-toggle` present and on → the verb is present. So tui (the lead app), linux and windows carry it; on windows it duplicates Explorer's verb on the folder, which costs nothing and keeps one rule and one witness. macOS renders neither (a bound location is always-resident there).
- **What the row says.** Beside the verb the row states how much of the location is on this device (bytes on this device of the set's bytes), so the user can see what a press would reclaim and that it did. After a press the row states the outcome of the latest sweep: how many files and bytes were freed, and how many were kept because they hold a change the nest has not recorded yet — the user-visible form of *a change that has not reached the nest cannot have its space freed*. The verb is never optimistic: both lines are the agent's reading, re-read off `ListLocations`, as the switch's is.
- **Keep on this device is the switch.** At the location's grain "always keep" already exists: turning the row's on-demand switch off downloads everything and keeps it. A finer keep (one file, one sub-folder) needs a per-file surface, which the app deliberately does not have (first bullet), so `PinFile`/`UnpinFile` keep no app caller on linux and that is a decision, not a gap: they stay the agent's verbs, pinned by `fuse_live_integration`, and are what a later per-file surface — the file-manager question above — would call. The sweep honours a pin regardless: a kept file is never freed.
- **The seam is shared Rust plus one agent verb.** Agent: a new request `FreeLocationSpace { path }` (the bound location's root; additive — an agent that predates it answers an error, which the row shows). It refuses a location that is not a mounted on-demand root, answers once the sweep is accepted, and the root's own loop does the work: every row with bytes on this device goes down the ONE existing road (`free_space` → the pin refusal → `free_local_bytes` → `is_dehydration_safe`), so there is no second gate and no second order of row-then-unlink. On windows the sweep walks the same rows through `handle_free_space`'s per-file body. **A sweep never outranks an open:** it yields between files, so a hydrate-on-open waits for at most one file's proof. **An own record in a metadata-only folder is the same refusal:** the gate keeps it (the paragraph *In a metadata-only folder a seat's own record is not a dehydration proof*, below), the sweep counts it in `kept_unsynced` with the unrecorded changes — one count, one line, no id of its own — and the line's string therefore says *kept because this device may hold the only copy*, since in such a folder waiting does not drain the count. The reading rides `LocationInfo`, additive: `on_device_bytes` (the recorded sizes of the rows that are not `Placeholder`) and `free_space` — the latest sweep of this agent's lifetime (`running`, `freed_files`, `freed_bytes`, `kept_unsynced`, `kept_pinned`), derived and never stored, with the lifetime rule `deletes_held` has. Client: `fauna-client-sync`'s agent control gains `free_location_space(path)` beside `set_location_sync_mode`; `BindingRow` mirrors the two readings on every reconcile; and `LocationBindingsModel::free_space_verb(&row)` answers what an app paints (absent / idle / running, the two lines' numbers), each line named in the shared string table (`devices.sync_locations.free_space_*`). An app adds a button, two texts and one call.
- **No automatic eviction — restated, not reopened.** The sweep runs when the user presses it and at no other time; a pressure- or age-driven policy stays what [`on-demand-files-linux.md`](on-demand-files-linux.md) § *Linux FUSE binding* already rules it: a choice a user might want, so app UI + nest state if ever, never a constant in the agent.
- **The witness is one seat, and it closes two outcomes.** `tests/e2e-unified/tests/test_folder_location_free_space.py` (tier_3; tui and linux on Linux, tui and windows on Windows), every assertion another process's view or the agent's own record. *Outcome 4:* bind, drop a file, wait for its upload, flip on-demand, press the verb → the row reports one file freed and nothing on this device, the engine logged the dehydrate, `ls` through the mount still lists the name with its size, the Media page still lists the file, and `cat` returns the original bytes — which this device no longer held, so the nest still does. That last step is also the first app-level hydrate of a cloud-only file a single seat can make. *Outcome 5:* with the nest stopped through the bridge, change the file through the mount, press the verb → the row reports one file kept, and `cat` returns the changed bytes while the nest is down (they can only be local); start the nest, wait for the upload, press again → freed.
- **Proposed ids (Rule A — asked 2026-10-04, unanswered).** On `pages.folders` `platform_elements` for linux, windows and tui, each indexed and scoped under `folder-location-row`: `folder-location-free-space-button` (button; `state` attr `idle|running`), `folder-location-on-device` (text — the standing reading), `folder-location-free-space-result` (text — the latest sweep's outcome; absent until one has run).
