## Goal

A single page in the Fauna app where the admin and the user (each within their own tier) configure every mail-subsystem knob. **No mail policy lives in a CLI flag, an env var, a TOML file, or a flag file** — those surfaces are reserved for OS-deployment topology the deployment artifact sets (keypair file location, nest endpoint URL, data dir, log destination). Every behavior the SMTP / IMAP servers can be tuned for is either:

- A nest-side row read by `fauna.bridges.fetch_config` and rendered in the Fauna app UI, **or**
- A compile-time decision (the cipher list, the strictness floor, the wire-format invariants) that is **not** configurable.

The discriminator is policy-stable: anything that varies by deployment, by admin preference, or by user choice belongs in this catalog. Anything that's a security invariant across all 7 apps + nest belongs as a compile-time decision (so a misconfiguration cannot reduce security).

## Three configuration tiers

This doc owns the three-tier model (it originated in a retired track, tracked internally; this section is the authoritative statement — sibling docs cite it as § Three configuration tiers):

| Tier | Decision-maker | Surface | Examples |
|---|---|---|---|
| **1. OS-deployment topology** | The deployment artifact (installer / compose / entrypoint — whoever runs `docker-compose up` merely launches it; nothing in this tier is a human preference) | `docker run` env vars, persistent-volume mount, host port mapping, image variant; the bridge process inherits its argv from s6's service script | `FAUNA_PORT` / `FAUNA_LAN_BIND_IP`, host port 25 mapping, the bridge's `--keypair-file` / `--nest-endpoint` / `--log-level` / `--data-dir` argv. (The box's **domain** is *not* a deployment env var — `FAUNA_DOMAIN` is retired; the domain comes from the admin's claim handle, `../architecture/nest/domains-and-tls-bootstrap.md` § Env contract.) **None of these are mail policy** — they are deployment plumbing. (No DNS-provider credential is a deployment env var: the nest never receives it — DNS is published client-side, `dns-management.md` § Where the credential lives.) |
| **2. Box-wide policy** | Admin (one per box, the `/data/claim-code` claimant) | Admin pane in their Fauna app → nest state, served via `fauna.bridges.fetch_config` | Whether mail runs at all; DKIM keys; DNSBL lists; rate-limit caps; MTA-STS / DANE posture; STARTTLS mode; greylist windows; ACME endpoint; per-deployment spam thresholds. |
| **3. Per-account policy** | Each user (zero-to-many per box) | Their own Fauna app → nest state | Their handles / aliases / addresses; submission credentials; per-account spam preference; per-account auto-respond opt-in; per-account filter rules / Sieve rules; per-account quota visibility. |

The bridge process sees Tiers 2+3 as a flat config snapshot via `fauna.bridges.fetch_config`; it doesn't distinguish — it just applies. Nest enforces the tier authorization (admin RPC vs. user RPC) when the *write* happens.

**Default-off on first claim:** a freshly-claimed nest has mail **off** until the admin explicitly enables it in their Fauna app. The mail-bridge binary may be present in the image but the supervisor doesn't start it; nest writes the `/data/imap-enabled` flag file + sends an "up" command via the supervisor sidekick socket when the admin toggles `mail.enabled` in their UI. Full lifecycle prose — startup, keypair generation, enrollment dance, default-off handshake, re-keying, reconnect, shutdown — lives in `docs/goal/behavior/mail-bridge-lifecycle.md`; this doc owns the configuration catalog the lifecycle reads from.

## Policy catalog

Every knob below has a `tier` (who sets it), a `default` (what ships), and a `binding` (the nest-state key name). The fourth column is `surface` — but see the reconciliation banner immediately below: the `bridges-detail-mail-*` / `account-detail-mail-*` ids it lists throughout are the **superseded draft-rendering premise**, not live ui.yaml ids.

> **⚠ UX-surface reconciliation (ratified 2026-06-01 by the mail-UX design pass, tracked internally).** The `Surface` column below was authored against a `bridges-detail` admin page (rendering the mail bridge as a metadata-driven `BridgeProvider`) and an `account-detail` mail page. **Neither page exists in ui.yaml, and the mail bridge is deliberately NOT surfaced on the `bridges` page** (`bridges.md` line 14 § Scope; the `bridges` page is user-facing feed bridges — Bluesky / ActivityPub). The entire `bridges-detail-mail-*` / `account-detail-mail-*` `Surface` column is therefore **superseded en masse**; the flat homes are:
>
> - **Automatic concerns — NO manual admin UI at all** (2026-05-24 user directive): DKIM, TLS/STARTTLS, MTA-STS/DANE, ACME, TLSRPT, DMARC-record publishing, content-scanning, deliverability/warmup, observability. *(One exception, the user's own, 2026-10-03: a per-domain DMARC policy select on `admin-dns` — owner `dmarc-reporting.md` § Multi-domain deployments.)* These are auto-provisioned with correct defaults; their `bridges-detail-mail-*` ids are **dropped**. DKIM/MX/SPF/DMARC records render read-only on `admin-dns`; scanner/deliverability/bridge health badges have **no current home** — their former `admin-services` page was removed 2026-06-04 (admin.md § Admin IA redesign), so the readout is deferred (can resurface on `admin-nest`/`admin-dns` later).
> - **Genuine admin *policy* knobs that have a real write-path** (today: the five `put_{spam,auth,submission,imap,outbound}_policy` sub-structs + `put_alias_policy` + `mail.enabled` — § Implementation status today) → the flat **`admin-mail`** page. Their per-knob `admin-mail-*` ids are **allocated with the consuming nest+app track, not pre-invented here** (most of the catalog is "Bucket C — neither projected nor admin-writable" today, so pre-inventing ids would be inventing UI for inert defaults).
> - **Domains + per-domain records** → `admin-dns` (CRUD already shipped); **bridge approval** → `admin-bridges-pending`; **mail enable/disable** → `admin-mail-enabled-toggle` on `admin-mail` (the old `admin-services` `bridge` toggle was vestigial and dropped with that page 2026-06-04 — admin.md § Admin IA redesign).
> - **Tier-3 per-account knobs** → the **`mail-settings` page family** (all reached via the Mail sub-nav): Aliases → the ratified **`mail-aliases`** page; Lists → **`mail-lists`**; spam reset / contribute-baseline / training-history → **`mail-spam`**; export wizard → **`mail-export`**; the simple per-account toggles (receive/send/autorespond/forward/filter-rules/Sieve/disposable defaults/scan-result-visible) → **sections on `mail-settings`** (or the relevant sub-page), ids allocated with the consuming per-app track. Per-message rows (scan-result, warmup-deferred) live on the **general mail message-detail surface**, not this family.
>
> So the rule "adding a knob requires a ui.yaml entry in the same commit" now reads: **a knob gets a ui.yaml id only when it is a genuine user/admin *choice* with a write-path AND a consuming app track is building its surface** — automatic/inert knobs carry no ui.yaml id. The per-row `Surface` strings below are retained only as a semantic hint (which knob is which); treat them as dropped/folded per this banner.

| Knob | Default | Binding | Surface |
|---|---|---|---|

| Auto-enable mail for new users | `true` (works-out-of-box, extended to every user) | `mail.auto_enable_for_new_users` (settable-both-ways `mail_auto_enable_new_users` DB singleton; unset ⇒ ON) | `admin-mail-auto-enable-new-users-toggle` on `admin-mail` (allocated + rendered linux + web + windows + macos + ios 2026-06-12, tui 2026-07-18; android lift pending) — a sibling of the `admin-mail-enabled-toggle`, but read back from `fauna.setup.status` (not `get_mail_config` — the bridge never reads this knob) |

| Multi-domain mail hosting | (per-domain rows in `mail_domains`) | `mail.domains` — the `mail_domains` table binding per `mail-multidomain.md` § Storage | `bridges-detail-mail-domains-section` |

> **`mail.auto_enable_for_new_users` is a *client-read* deployment default, not a bridge knob.** When ON (the default), a freshly-registered user's client auto-provisions its own mailbox on first authenticated setup — so a new user gets a working `<handle>@<domain>` mailbox with **no** admin provisioning and **no** manual user toggle (the works-out-of-box invariant, extended to every user — `mail-credentials.md` § Auto-enable for new users). The nest **cannot** mint the mailbox itself (the MSEK is client-held — `mail-credentials.md` § MSEK lifecycle), so the knob never reaches the bridge via `fetch_config`; it is surfaced to clients on `fauna.setup.status` (`SetupStatusReply.auto_enable_mail_for_new_users`), and the client gates its first-setup auto-mint on it **together with** `mail.enabled` (`email_enabled`). It is the admin's deployment-wide override of the default-on behavior (`fauna.bridges.set_auto_enable_mail_for_new_users`, Admin-class) — **not** a per-user control: the admin never sets mail for an individual user (mail is user-controlled — `admin.md` § Don't do these); a user who doesn't want mail opts out from their own app (the per-actor `actor_mail_serving` toggle / disabling their mailbox), exactly as today.

DKIM private-key bytes are **never** in this catalog — they rest sealed in nest state (`mail_dkim_keys`, one row per (domain, selector) — `mail-multidomain.md` § Storage) and are opened only by the nest, to sign (`mail-bridge-lifecycle.md` § DKIM provisioning (automatic)). > **Spam-score action defaults are permissive (auto-Junk only).** The two
> spam-score tiers above, **Junk and reject**, are the **combined-score** tiers
> (`max(rspamd_scaled, weighted_bayesian)`, 0–15 points; see `mail-spam.md`
> § Combined-score formula). There is no hold between them: a hold only an
> admin can review is an admin reading members' mail, and a hold the member
> reviews is the Junk folder. Out of the box only `spam_folder` is enabled
> (5 → Junk); `reject` defaults to `0` (**disabled**). The bridge **scores +
> tags every message and never 550-rejects on the content score by
> default** — the destructive action is opt-in, either by an admin setting a
> non-zero reject tier here or by a per-user filter rule acting on the score
> (`email-filters.md` § Email filter rules). This preserves *user-controls-their-
> data* (no silently bounced/hidden mail on a score the user can't override)
> while keeping *works-out-of-box* (spam still lands in Junk). When both tiers
> are non-zero, `spam_folder < reject` must hold (a `0` tier is skipped). The
> perimeter hard-gates (auth, DNSBL reject-class, ClamAV malware, greylist,
> rate-limits) reject independently of these tiers.

### Compile-time decisions (NOT in this catalog)

These are intentionally not configurable; changing them would require a code change + a deliberate security review:

- TLS cipher list (the pinned AEAD-only set in `smtp-server.md` § TLS posture per port). Admin **cannot** add CBC ciphers.
- TLS minimum version (1.2 floor, 1.3 ceiling). Admin **cannot** lower it.
- Header section caps (256 lines / 1 MiB). Admin **cannot** raise them — the cap is parser-bomb defense.
- Connection-time constants (`smtp-server.md` § Connection-time limits): the global concurrent-connection caps (100 on port 25; 4096 on the authenticated submission/IMAP/CalDAV surfaces), the port-25 per-IP **concurrent** cap (`maxInboundConnsPerIP` = 50 — unauthenticated MX has no `AuthPolicy` to feed it, unlike the admin-set `mail.auth.per_ip_max_concurrent_conn` on the authenticated surfaces), the escalating error tarpit (250 ms × n, capped 5 s), and `MaxLineLength` (1000 octets). All compile-time by design.
- The envelope sender-domain MX/A check (`smtp-server.md` § Sender-domain). A sender domain with neither MX nor A/AAAA is rejected `550 5.7.1` at MAIL FROM; this is always-on (no knob). Loopback peers and the null sender `<>` are exempt; resolver errors fail open with a counter.
- Per-method bridge↔nest RPC allowlist (per `apps/bridges.md` § Per-role method allowlist). Adding an MDA-class method to the MTA allowlist requires a code change.
- The submission-quota independence-from-IMAP-quota rule (per `imap-server.md` § Composition with submission quota).
- The product-invariant rule itself: that mail policy is set from Fauna apps, not env vars. **This catalog can grow; the rule cannot be opted out of.**

## Wire: `fauna.bridges.fetch_config`

The mail-bridge process calls `fauna.bridges.fetch_config(role)` over WS-RPC at startup and subscribes to `fauna.bridges.config_changed` push events. The response carries every Tier-2 + Tier-3 knob the bridge needs for its role:

- **MTA role:** the Tier-2 (admin-set) projections its perimeter + outbound engine consume (`local_domains`/`primary_domain`/`dkim_selectors`, the spam/auth/submission/outbound policy sub-structs). Per-recipient Tier-3 state does **not** ride `fetch_config` — the MTA fetches it per-delivery over dedicated kinds: filter rules via `fauna.bridges.fetch_recipient_filters` (evaluated at the MTA perimeter, incl. the AutoReply action — `email-filters.md` § Email filter rules), forward config via `fauna.bridges.fetch_recipient_forward_config`, and recipient resolution (aliases/receive-gating) via `fauna.bridges.resolve_recipient`.
- **MDA role:** the Tier-2 projections its serving surfaces consume (IMAP policy, auth policy, `local_domains`). Per-actor Tier-3 state is read during AUTH'd sessions over the MDA-class kinds (mailbox ops, quota via the IMAP QUOTA surface), not via `fetch_config`.

Wire-level shape, error modes, and the subscribe-and-hot-reload semantics are pinned by `bins/fauna-nest/src/bridge_routing_handlers.rs` round-trip tests; this doc owns **which knobs are in the payload**, not the byte-level encoding. New knobs land in: this catalog → nest-state schema → fetch_config payload → bridge consumer → ui.yaml surface → per-app UI rendering, in that order, with the goal-doc + nest-state schema changes landing in the same commit.

## Architectural rules

- **Every mail-policy knob is in this catalog.** A code path that branches on a config value not listed here is a bug: either land the knob (with `tier`, `default`, `binding`, `surface` columns + a ui.yaml entry in the same commit) or hardcode the value as a compile-time decision.
- **No env var, no CLI flag, no TOML file for any value in this catalog.** Tier-1 OS-deployment topology fields (the four bridge argv slots, the docker env vars driving image build) are the **only** non-nest-state surface. If a session catches itself reaching for `FAUNA_BRIDGE_*` to add a new knob, the answer is "fetch_config payload + UI", not "another env var."
- **`fauna.bridges.fetch_config` is the single source.** The bridge process does not read TOML / env / argv for any catalog entry; it pulls from nest at startup and reapplies on push. Subscribe-and-hot-reload is mandatory — the bridge MUST apply changes at the next request boundary without a restart.
- **Default-off on first claim.** The mail subsystem is **off** on a freshly-claimed nest. The admin opts in by toggling `mail.enabled` in their UI; nest writes the s6 flag file + sends the supervisor sidekick "up" command; s6 brings the bridge up. Full lifecycle handshake in `mail-bridge-lifecycle.md`.
- **Validator in shared Rust.** Both nest (write-side) and apps (form-side) use the same `libs/fauna-mail/src/policy.rs` validator. New knobs land alongside the validator entry.
- **An enumerated knob's value set has ONE owner — no app, and no other binary, re-derives it.** A knob whose catalog `Default` column names a closed set (`off / score_signal / enforce`, `forbidden / allowed`) is not just a picker's contents: it is a *wire value the bridge switches on*, a *stored admin choice*, a *render order* two apps address by position, and an *unknown-token fallback* — and that fallback is a safety decision, not a rendering detail. All four live together in one table in shared Rust, today `fauna_client_mail_settings::admin_policy::{FcrdnsMode, ImapDeleteNonempty}` (`ORDER` / `as_str` / `label_key` / `from_wire_or_default` / the `*_options()` catalogs). tui and linux read the enum directly; web, android, apple, and (since 2026-08-30) windows read it through the UniFFI/wasm doors (`fcrdnsModeOptions`, `imapDeleteNonemptyOptions`, exported directly from `fauna_client_mail_settings`'s own UniFFI namespace — no `fauna-ffi` facade, no Go-binding involvement), the same shape `family-safety.md` § Where logic lives uses for `content_floor_options`. No app hand-writes either value list anymore (§ Implementation status today). The Go MTA's own const family is pinned against the same tokens by `libs/fauna-client-mail-settings/tests/go_wire_policy_contract.rs` + `bins/fauna-bridges/internal/wsrpc/go_wire_outcome_contract_test.go`, so a rename cannot silently revert an admin's `enforce` to `score_signal` on the far side of a binary boundary. The wire field stays `String`-typed for forward-compat (`bridge_routing.rs`) — that is what makes a shared *reader* with a ruled fallback necessary rather than optional. Priority #1/#2/#4.
- **Admin can disable mail for an account.** Tier-3 entries are user-set in the normal flow, but the admin retains a kill-switch at the user-management level (suspend / evict the user) per existing `docs/goal/architecture/nest/common.md` § `users` table semantics.
- **No knob lowers a compile-time security floor.** Cipher suites, TLS version, header caps, the per-method allowlist — these are not configurable. Admin requests to weaken them are a code-change conversation, not a UI control.
- **Knob removal is forbidden between releases without a transition path.** A future deployment may have a value set against a knob this catalog ships with; removing the knob silently drops the admin's choice. Renames + deprecations land alongside a `fauna.bridges.migrate_config` step. (In the current pre-production era this is mostly aspirational — we have no users yet — but the rule lands now so future work inherits it.)

## What `0` means on an unsigned knob

Every integer knob in this catalog rides the wire as `Option<u32>` / `Option<u64>`, so a negative
is *unrepresentable* rather than merely rejected (the best shape sweep named), and the apps
save each field as `parse_count(text).unwrap_or(prev)` — an unparseable edit keeps the persisted
value (`value-formatting.md` § Mail-knob validation). **So a `0` reaching a door is always a
deliberate keystroke, never a parse artifact**, and every knob owes an answer to "what does `0`
mean here?". Swept knob-by-knob against the consumer (sweep, 2026-08-18).

The answer splits on what kind of knob it is, and the two families take **opposite** sentinels:

- **A protection threshold** — a knob that arms a defence (connection-rate caps, the AUTH-failure
  lockout, the spam-score tiers, the unlisted-recipient penalty). `0` = **the protection is off**.
- **An allowance** — a quantity a user consumes (submissions per day, mailbox bytes/messages,
  aliases). `0` = **no allowance**, which is a legitimate admin choice even though its effect is to
  refuse everything. This is the ratified `0`-is-meaningful boundary the admin tier caps and the GC
  grace period already keep: `api-layers.md` § Admin doors refuses a *negative* and deliberately
  leaves `0` valid, "so the floor is `0`, never `1`".

Neither family's `0` is refused at the door. **Do not "harden" an allowance knob by rejecting
`0`** — that contradicts the tier-cap ruling and takes away an admin's legitimate "this account
gets nothing".

| Knob | `0` means | Made true by |
|---|---|---|
| `max_score_before_spam_folder` / `_reject` | tier disabled (skipped in the ordering check) | `bridge_routing_handlers.rs::put_spam_policy_handler` |
| `max_conn_per_min` | connection-rate gate disabled, admit all | `internal/mta`'s `RateLimiter.Allow` |
| `max_conn_per_ip` | per-IP concurrency gate disabled, admit all | `internal/connlimit`'s `PerIPLimiter.tryAcquire` |
| `max_auth_failures_per_minute` | AUTH-failure lockout disabled | `internal/authlock`'s `Lockout.IsLockedFor` |
| `unlisted_recipient_penalty` | penalty off (the default) | the MTA delivery loop |
| `bayesian_weight_milli` | the per-user Bayesian term contributes nothing | the SELECT-time scorer |
| `bayesian_min_samples` | the per-user term applies from the first sample | the confidence ramp |
| `bayesian_full_confidence_samples` | **refused** — must exceed `bayesian_min_samples` | `put_spam_policy_handler` |
| `max_message_bytes` | **not uncapped** — falls back to the shipped default | `fauna_mail::transport_limits::effective_max_raw_message_bytes` |
| `greylist_delay_secs` | no hold-down, greylist tracking retained | the MTA greylist gate |
| `idle_timeout_secs` | unset — falls back to the 29-minute RFC 2177 default | `internal/mda/imap`'s `Session.idle` + `IdleTimeout()` |
| `tombstone_retention_days` | **floored to 7 days** | `bridge_imap_handlers.rs` EXPUNGE prune |
| `training_history_retention_days` | keep nothing — prunes every row before the sweep instant | `run_spam_training_history_gc` |
| `bodystructure_cache_max` | BODYSTRUCTURE cache disabled (pure perf cost) | `internal/mda/imap`'s LRU |
| `exact_aliases_max` | no user-added aliases beyond the signup canonical | the alias CRUD cap |
| `max_per_day` | no allowance — every submission is over quota | `try_consume_submission_quota` |
| `storage_bytes_default` / `message_count_default` | no allowance — every delivery/APPEND is over quota | `imap_quota_overage` |
| `retry_schedule_seconds` | `Some([])` = no retries after attempt 1, a deliberate clear — as `dnsbl_servers: Some([])` already reads | `OutboundPolicyOverrides::effective`, `retry_policy_from_outbound` |
| `permanent_failure_timeout_hours` | **unset → the catalog default.** A literal `0` would permanently fail every message on its first attempt, so `effective()` floors it | `OutboundPolicyOverrides::effective` |
| `delay_warning_at_hours` | delay warning on the first failure — benign | `retry_policy_from_outbound` |
| `ndr_rate_limit_days` | `0` → no rate-limiting beyond a same-instant duplicate — a legitimate admin allowance choice, no floor (unlike `permanent_failure_timeout_hours`) | `OutboundPolicyOverrides::effective`, `generate_permfail_bounce` |
| `max_recipients_per_message` | no allowance — the same boundary `max_per_day` keeps | `check_submission_quota_handler` |

## Don't do these

- Don't add a `FAUNA_BRIDGE_*` env var for any value in this catalog. The product invariant explicitly forbids it. (The legacy bridge's env-var configuration surface was deleted at the I6 cutover; see `smtp-server.md` § Configuration is nest-side — new env vars are not allowed.)
- Don't introduce a per-app mail-config UI variant. Same catalog, same shared `MailPolicyMachine`, same fields, all 7 apps. Per-app UI work is the platform-shell that *hosts* the shared machine's rendering, not per-knob logic.
- Don't let the admin lower TLS to 1.0/1.1 / re-enable CBC / shrink header caps. These are compile-time decisions, not knobs.
- Don't add an admin-only "auto-CC all bounces to postmaster@" toggle. Per `smtp-server.md` § Postmaster CC, this is an amplification vector; the per-account opt-in is the only correct shape and it's off in v1.
- Don't store DKIM private-key bytes in this catalog. They rest sealed in the nest's own key store (`mail-bridge-lifecycle.md` § DKIM provisioning (automatic)); the admin sets the *policy* (selector, rotation, algorithms), nest generates the keys and seals them.
- Don't render an admin-only knob on a user's `mail-settings` surface (and vice versa — no admin knob on the user's mail pages, no Tier-3 knob in the admin pane). Tier-2 vs. Tier-3 separation is load-bearing for the security model — `policy.rs` validates each write against the caller's tier.
- Don't hand-edit `/data/imap-enabled` (or any sibling flag file) on a running production deployment. The flag is **nest's output**, not the admin's input — the admin's input is the `mail.enabled` toggle in their UI, which nest then materializes as the flag. Hand-editing breaks the lifecycle model and can drive s6 + nest into disagreement.
- Don't bypass `fauna.bridges.fetch_config` for any "performance" reason. A SIGHUP-based local-file reload is the **wrong shape** under the product invariant; the only correct reload path is "config_changed push event triggers in-memory snapshot update."
