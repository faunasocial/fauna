## Goal

A user who has an export archive from another social network — Facebook or Instagram first; X, Mastodon, TikTok and Google Takeout later through the same wizard — imports it into Fauna **from the Fauna app**, on any of the 7 apps, and afterwards:

1. **Their own content is theirs again, at its original dates and with its original audience.** Posts, album photos and videos, and events appear in their feed and calendar exactly where they happened, badged with the platform they came from.
2. **Nothing is lost, ever.** The untouched archive plus a normalized model of it rest sealed in a folder on the user's nest, so later phases keep mining it without another export, and a parser mistake never destroys anything.
3. **Other people's content is kept for the owner alone and never republished** — until the person it belongs to is a Fauna user who has linked with the owner, at which point it becomes *that person's* own signed content (§ Linking and merging). No shadow profile of a non-user is ever created.
4. **A family, friend group or community that all import can piece their shared activity back together, given consent** — one standing per-pair consent, after which comments and reactions merge automatically in both directions.

**Bar: better than Pixelfed's Instagram import and every Bluesky Twitter-archive importer** — all of which take a zip and re-post it. Fauna keeps the archive, preserves dates and audiences, keeps other people's content private, and adds the cross-user merge nobody else has built.

**Why an archive and not an API.** As of 2026-09 there is no pull API for Facebook or Instagram (Meta only *pushes* to a vetted destination with a fixed public endpoint, which a self-hosted nest is not), and every other gatekeeper's API is EEA-only and requires a verified corporate identity. The user's own export archive is the one mechanism that works today, worldwide, for every source, with no gatekeeper relationship. The API paths are a later, organisation-level phase; the design record carries the research.

## The archive model

A new shared-Rust crate, **`libs/fauna-archive`**, owns one strict, platform-neutral model and every parser that fills it. The vocabulary follows ActivityStreams, which the ActivityPub integration already speaks: actor, post, comment, reaction, media, album, event, group, friendship, thread, message, profile. Nothing platform-specific leaks past a parser.

**External identity is the pivot.** Every entity carries

- `ExternalId { platform, kind, id }` — `platform` is a closed enum (`Facebook`, `Instagram` now; additive), `kind` the entity kind, `id` the platform's own identifier or permalink when the export carries one, else `h:<blake3-hex>` over the canonical CBOR of (platform, kind, `created_at`, normalized text, sorted media creation instants). The derivation is frozen by golden tests: the same archive yields the same IDs forever, because re-imports, dedup and cross-user matching all key on them. Per kind, only inputs a re-export cannot legitimately change enter the hash: posts and messages hash their text and the creation instants of their media — never the media bytes, because the platforms re-encode media per export (Facebook at the requester's chosen quality), so a byte hash would re-import every photo post as a duplicate (user ruling 2026-09-08, re-pinned before any real import existed); comments their text; events their title; groups their name; albums their name and earliest-photo date — the album's last-modified stamp only when no photo or video is dated — with no media (the media set is mutable across exports); reactions their kind token — never the platform's localized, name-bearing prose title.
- `ExternalActorRef { platform, id: Option<String>, display_name, name_key }` — the platform's user ID when present; `name_key` is the normalized display name, the matching key when IDs are absent (Facebook comment authors are names only).
- the original `created_at` and an `ArchiveAudience` ∈ { `Public`, `Friends`, `Custom`, `OnlyMe`, `Unknown` }.

Entities: `ArchiveProfile`, `ArchivePost` (text, media refs, links, tagged actors, album, original URL), `ArchiveAlbum`, `ArchiveComment` (parent external ID, author), `ArchiveReaction` (target external ID or URL, author, kind), `ArchiveMediaRef` (path inside the zip, BLAKE3 once read, MIME, taken-at, caption), `ArchiveEvent` (title, start/end, place, own RSVP; attendees kept as actor refs), `ArchiveGroup`, `ArchiveFriendship`, `ArchiveThread` + `ArchiveMessage` (participants as actor refs, per-message sender, text, media, reactions). Every entity serializes as canonical DAG-CBOR (architecture/serialization.md owns the encoder).

`ArchiveSummary` is the index a parser produces from the zip's central directory plus the small profile file, before anything is uploaded: platform, the owner's own `ExternalActorRef`, date range, per-category counts, total media bytes.

## Storage — the archive folder

The archive lives in an **ordinary private folder**, one per import, created by the wizard at Start — and *recognized* by nothing but its marker: `list_archive_folders` walks every owned folder and keeps the ones whose `fauna-archive.cbor` decodes (ruled 2026-09-28, built the same day; a folder has no type, [`folders.md`](folders.md) § Target re-model). It is sealed under the folder's content key, quota-metered, backed up like any folder, and listed in Folders so the user can see, browse and delete it. The nest place holds the content; no device place is bound, so no device mirrors it. Layout:

```
fauna-archive.cbor          # marker: platform, owner ExternalActorRef, import id, parser version
raw/<original filename>     # the untouched export zip — ground truth, kept forever
model/summary.cbor
model/profile.cbor
model/posts.cbor  model/albums.cbor  model/comments.cbor  model/reactions.cbor
model/events.cbor  model/groups.cbor  model/friends.cbor  model/threads.cbor
state/import.cbor           # wizard progress, ExternalId → Fauna id map, skip log, dedup keys
state/links.cbor            # phase two: per-pair links, received origin indices, claim ledger
```

The app writes into it as **chunked, owner-sealed files** — the sync engine's sink-agnostic seal (`fauna_sync_engine::seal::seal_blob` under the owner's `BackupKey` root) → the chunk store (`check_chunks`, `POST /api/v1/chunks`, `POST /api/v1/manifests`) → one `fauna.sync.changes.record` row per path — the shape a synced folder's files already have and the walk every reader already runs (`fauna_core::file_download`); this is a deliberate departure from the Media page's *upload* gesture (ui/media.md § the Upload gesture), which posts one sealed blob under the tier's `max_blob_size`, a cap the raw zip cannot live under. It reads them back by manifest + chunks — whole for the model files (megabytes), and by **byte range** for the raw zip (`fauna_core::file_download::download_file_range_by_manifest`, slice 3, over the existing per-chunk primitives, bound by `SyncEngine::download_file_range`; each opened chunk is verified against the manifest's plaintext hash, since a range has no whole-file address to check) — so a later device fetches the model it needs and reads one zip member at a time, never the gigabytes of zip.

**Two deliberate departures from mailbox migration, with reasons.** (1) Not a reserved rail: rails are bounded by construction at 1 MiB per path and an archive is the unbounded, metered class (behavior/reserved-folders.md § Drafts Sync). (2) Not a nest-side session table: the nest cannot read the archive, so a plaintext session row would only add import progress to the plaintext floor; state inside the sealed folder is strictly more private and yields cross-device restart-resume for free.

**Re-imports are continuous through dedup.** A newer export of the same platform lands in a new folder; the wizard lists existing archive folders of that platform (by marker) and consults their `state/import.cbor` maps, so an entity already imported is skipped and the new archive only adds what is new. Deleting an archive folder deletes the archive, never the posts it produced — those are ordinary posts, deleted like any post.

**A state a newer build wrote.** Every enum in `state/import.cbor`, the marker and the model files carries its unknown arm ([`../architecture/transport.md`](../architecture/transport.md) § Rule 3 in full; the per-enum answers are the enum ledger), and `ImportState` / `ImportScope` keep keys they do not name in an `extra` catch-all, so a newer build's state still decodes and **still feeds dedup** — an older build never re-imports what a newer one imported. Such a state, or a marker naming a platform this build lacks, is **not resumable by this build and never rewritten**: hydrate passes over it, and the run and every checkpoint refuse it (`DispatchError::NewerImport`) before writing anything, so its bytes stay as they are for a build that can read them. An unknown audience mode maps as only-me, never the original audience. An entity a model file holds that this build cannot name is counted as skipped, never fails the file.

## What each category becomes

Guiding rule: **the owner's own authored content is imported at its original date with its original audience; other people's content is kept for the owner alone, sealed, never republished; what cannot be attributed or matched is not imported but survives in the folder.**

| Archive category | Becomes | Audience |
|---|---|---|
| Own posts (text, links, photos, videos) | one `Post` each, `created_at` = original, `origin` set, `source` = platform token; media re-uploaded through the media pipeline sealed for the post's audience | § Audience mapping |
| Album media not attached to a post | one `Post` per album carrying its media, dated at the album's creation | the album's audience |
| Other people's comments on own posts | stay in `model/comments.cbor`; the feed manager reads them for the owner's own imported posts and renders them collapsed under the post as owner-only context | owner only, sealed; never published |
| Own reactions and comments on other people's content | not imported now — the target is not here; phase two resolves them against linked contacts' imported posts | — |
| Message threads | read-only records under the **`Archive` rail** (`Rail::Archive`, glyph `SourceGlyph::Archive`, a box), projected into the conversations list by the manager from `model/threads.cbor`; never written to `__conv` | owner only, sealed |
| Friends, followers, following | not imported as contacts; kept in `model/friends.cbor` for phase two's matching and a later opt-in friend finder | — |
| Own events | calendar events with title, time, place and own RSVP; attendee lists stay in the model | owner only |
| Profile (name, bio, links, picture) | offered as a one-tap prefill at Done, never applied silently | as the profile is |
| Ad interests, logins, saved items, liked pages | not imported | — |
| The raw zip | `raw/` in the archive folder | owner only |

**Audience mapping** — onto the three classes ui/feed.md owns, nothing new: `Public` → public post; `Friends` → gated to the always-present free **followers** tier (Fauna's own "people who follow me"; a new user with no followers is effectively private until followed, which preserves the friends-only meaning); `Custom`, `OnlyMe`, `Unknown` → gated to a **reserved owner-only tier**: minted once by the machine on first need at the reserved name and top rank, hidden from every offer surface — `fauna_core::subscription::{OWNER_ONLY_TIER, OWNER_ONLY_TIER_RANK}` and the `hidden` flag, both owned by behavior/monetization.md § The unifying model → *A tier may be hidden*. The author decrypts own gated posts with their own period key already (`libs/fauna-feed/src/manager.rs:2603`), so no new key material exists. The wizard's **audience mode** switch overrides the whole mapping to owner-only.

**Gating needs a live tier — the machine provisions both tiers before the first non-public post, and never silently downgrades an audience.** A gated post seals under the tier's period key (Pillar-1 custody, the `fauna.state.subscriptions` rows) and names the tier's live `KeyBlob` (`fauna.subscriptions.key_blob.get`), exactly as the compose leg does. The owner-only tier is minted through the ordinary `SubscriptionsAuthor::stage_tier` → `commit_tier` shape with `hidden: true`, `auto_approve: false`, rank `OWNER_ONLY_TIER_RANK` (found first by `OWNER_ONLY_TIER` on the author's own `tiers.list`, so the mint is idempotent). The followers tier has no such path today: the nest provisions its row on the first follow and the author's client mints its key at the first approval, so an account nobody follows yet — the typical importer — holds neither. Slice 3 therefore lets `tiers.create` accept the reserved name at exactly rank 0 as the idempotent client-side twin of `ensure_followers_tier`, birth `KeyBlob` included (`monetization.md` § The unifying model owns the relaxation). Both provisions are gated on the nest advertising `hidden-tiers`; against a nest that does not, the wizard imports the public categories and lists every non-public record in the skip log with the one reason ("this nest predates hidden tiers — update it"), so a re-import after the update picks them up (dedup keys on external ID, and a skipped record is not in the map). A `Friends` post is never re-authored owner-only because followers were unavailable: a signed post cannot be re-gated later, and "at its original audience" is the promise. A gated import's public preview is the neutral placeholder "<Platform> import" — never any of the text: the compose leg's teaser is an author's deliberate choice, and an import cannot make it for them. Events import regardless of `hidden-tiers` — they ride the sealed calendar, not a tier.

**The post origin field.** `Post` gains `origin: Option<PostOrigin { platform: String, url: Option<String> }>` — `#[serde(default)]`, additive exactly like `gated` and `content_warning` (`libs/fauna-core/src/data.rs`, the `Post` struct); and `skip_serializing_if`, so a post without an origin encodes byte-identically to one from before the field (its CID and signatures unchanged); plain strings; an older peer tolerates the unknown key on decode and stores and forwards the content-addressed bytes verbatim, so nothing is lost. It is a field of the signed `Post` envelope — **plaintext on every post, gated or not**, exactly like `gated` and `content_warning` (a gated post seals only its `PostBody`), which is what lets the nest index `source` from it for a gated import too. **Ruled 2026-09-06 (slice 3, ruling 2 — refutable advisory): the envelope carries the platform and nothing that identifies the post on the other network.** `external_id` is *not* a field of `PostOrigin` (slice 2 minted one; it was removed before any release carried it — the production pin predates slice 2): nothing reads it from the envelope — dedup, the phase-two origin index and the collapsed-comment join all key on the sealed folder's `state/import.cbor` map, and the index travels inside the sealed channel — while an `h:<blake3>` id on a gated post would be a content-confirmation oracle over the sealed body (its inputs beyond `created_at` and `platform`, both already plaintext, are exactly the text and media creation instants), the same reasoning that made `GatedInfo.seal_id` random rather than a body hash; and a platform-native id names an object under the user's account on another network, which belongs in the sealed model. `url` stays an optional field and **phase one authors `url: None` on every post**: a permalink names the user's Facebook or Instagram handle on every card, a stronger identity link than the platform badge, so linking to originals is a per-import choice the wizard does not yet offer (phase-three direction: a "link to originals" scope option, public posts only). `platform` alone sits on the plaintext floor — the badge and the `source` index need it, and it says only what the badge says. The badge is the existing `protocol-badge` with the platform's canonical label. Both platforms resolve to the single `SourceGlyph::Archive` concept (a box) — the label, not the glyph, names the platform (render-model.md § D5). The nest indexes `source` through `Post::source_token`, which normalizes the platform token (`fauna_core::source::normalize`: one lowercase word, ≤ 32 bytes) and indexes the platform token only when it names an archive platform this nest knows (`fauna_core::source::ARCHIVE_PLATFORMS`), and falls back to `fauna` for anything else — an unknown or bridge token can never be indexed from a client-authored origin; and `SourceKind::is_native` / `fauna_core::source::is_native` count the archive platforms as native, so likes, reposts and replies on an imported post are signed posts on both the client and the nest's interact door.

## The wizard and its machine

**Page `archive-import`**, a Settings rail entry **"Import from other services"** directly after Mail import (ui/settings.md § Navigation model owns the rail; this doc owns the page). One shared-Rust state machine, **`libs/fauna-archive-import-machine`**, mirrors `MailImportMachine`'s shape exactly — Snapshot / Action / Machine / dispatch / hydrate, client-side steps first, durable commit at Start — with two trait seams: `ArchiveSource` (the zip: `len()` + `read_at(offset, len)`, backed by a path on native and a browser `File` on web) and `ArchiveNest` (folders, posts, media, calendar, tiers). tui and linux link it directly; the other five reach it through `fauna-ffi` / `fauna-wasm` faces (architecture/apps/native-async-execution.md's `Box::pin` rule applies to its leaf futures).

Steps, `ArchiveImportStep`:

1. **Source** — Facebook or Instagram (more later); the panel explains how to request the export on that platform, in JSON format, and deep-links there, because the user must do that first and the download link expires after four days.
2. **Archive** — path entry on tui, a real file input on web, native pickers elsewhere (the tui absence rule). The machine reads the central directory and the profile file only, and shows the `ArchiveSummary`: platform, account, date range, size, per-category counts. A zip whose platform is not detected, or an HTML-format export, is refused here with the message naming what to request instead.
3. **Scope** — category checkboxes with counts; the **audience mode** (keep original audiences / only me); an optional date range. The range follows the mailbox export's date rule ([`mail-export.md`](mail-export.md) § UX shape step 2 owns it): a bare `YYYY-MM-DD` names a whole UTC day, both ends include their whole day, either may be empty, and a malformed date or a "since" after the "until" refuses **Next** here (and `Start`) — never "no range". The instant compared is the archive's own timestamp for the record.
4. **Confirm** — totals and estimated bytes; **Start** is the durable commit: the folder is created and the raw upload begins.
5. **Progress** — per-category rows, overall bar, elapsed + ETA, pause / resume / cancel (cancel keeps what landed), and the skip log. Order inside a run: raw zip, then model files, then media + posts oldest-first, then events, then threads. Between batches the machine checkpoints `state/import.cbor` into the folder, so a real restart resumes from the folder — cross-device, not same-process.
6. **Done** — counts; "View imported" (feed filtered by source); "Review skipped"; the profile prefill offer; the archive folder's name as a link into Folders.

There is no global jobs surface in any app (none exists for mail import either); progress lives on this page. That shared gap is a later cross-feature track, not this doc's.

## Linking and merging (phase two)

Built on the identities phase one recorded. **No new nest surface**: every signal travels inside the existing end-to-end sealed MLS direct-message channel between two accepted contacts, which already crosses nests, as one additive `ChannelMessageBody::Archive(bytes)` variant carrying a canonical-CBOR `ArchiveSignal` — the opaque-bytes pattern `Scheduling` / `Custody` / `ShareEndpoints` already use (`libs/fauna-mls/src/types.rs`). Apps never render these as chat.

- **Scope of matching:** accepted contacts, and members of a shared Fauna room once room UI exists (behavior/conversation-rooms.md). There is no nest-wide or federated directory of platform identities; nobody can be looked up by an outsider.
- **Discovery.** After an import, the app sends each accepted contact `Announce { platform, fingerprint }` — a hash of (platform, user ID) when the export has IDs, else of (platform, `name_key`). The receiving app compares the fingerprint against its own `model/friends.cbor`. On a hit it asks its user **once**: "Is your contact B the 'B' from your Facebook friends?" Yes sends `LinkOffer` carrying the asker's own `ExternalActorRef`, so the other app can ask the mirror question; the second yes sends `LinkConfirm`. Both store the link in `state/links.cbor`, keyed by (contact, platform). One standing consent per pair; nothing per item.
- **The origin index.** On linking, each side sends `OriginIndex { platform, entries: [(external_id, post_id, audience_class)] }` for its own imported posts the other may read, refreshed after a re-import. This is what lets B's `ArchiveReaction` "liked post 12345" find A's post — no nest lookup, nothing on the plaintext floor.
- **Merges — automatic once linked, oldest first, each authored by the person whose content it is.** B's comments on A's posts live in A's archive: A's app sends `ClaimOffer` items (text, date, media, target post ID, external IDs); B's app signs backdated **reply posts** (`Reference::Reply`, `origin` set) and returns `ClaimResult` with their IDs; A's app records them and stops rendering those comments as owner-only context. B's reactions on A's posts live in B's archive: B's app resolves them through the origin index and signs backdated **reaction posts** (`Reference::React { emoji }` with the platform's reaction kinds mapped to emoji, `Upvote` for a plain like). A re-import on either side re-runs the offers; dedup by external ID makes it idempotent.
- **Unlink** (`Unlink` signal, either side, from the contact's row in Contacts) stops future merges. Claimed content stays: it is genuinely the claimant's own signed content, deleted like any post.
- **Held for phase three, with the reason recorded:** photo tags (a signed post cannot be amended, so tag → mention needs an edit mechanism or a sidecar — a design question of its own); message threads (both archives hold the same conversation and MLS cannot backdate history, so linking only cross-references the two copies); events and groups (behavior/groups.md's UI gap first); the friend finder for non-contacts.

## Parser contract

Every parser implements one trait: `detect(&ZipDirectory) -> Option<Detected>`, `index(&mut ArchiveReader) -> Result<ArchiveSummary>`, `stream(&mut ArchiveReader, Category) -> Box<dyn Iterator<Item = Result<Entity, EntityError>>>` — `ArchiveReader::open(&dyn ArchiveSource)` is the seam that turns a source into the central directory plus one-member-at-a-time reads every parser drives. Rules:

1. **Never fail the whole import on one bad record** — a per-entity error lands in the skip log with the reason.
2. **Ignore unknown files**; a newer export layout degrades to "fewer categories", never to a refusal.
3. **Count before writing** — `index` runs from the central directory, the profile file and the category JSON members (megabytes at most); media is sized from the directory and never read before Start.
4. **Determinism** — the same zip yields the same external IDs on every run and every parser version; golden tests pin them.
5. **JSON only in version one**; the HTML variant is refused at the Archive step with the message naming the format to request.
6. **Facebook's byte-wise UTF-8 mojibake** (each UTF-8 byte escaped as its own `\u00XX`) is repaired by one named pure function with a golden test; every string field passes through it. A media `uri` is the one exception in timing, not in rule: it is repaired at resolution time — the raw name is tried first because the archive's own member names are the truth, the repaired name second — and the name the archive holds is what the model keeps.
7. **Fixtures are generated, never real.** `tests/e2e-unified/fakes/fake_facebook_archive.py` produces a valid Facebook-shaped zip (mojibake included) for tier_3; `libs/fauna-archive/tests/fixtures/` holds small hand-written JSON files for tier_1. No real export ever enters the repo.
8. **Streaming.** A parser reads members by offset through `ArchiveSource`; it never needs the whole zip in memory.
9. **Bounded in aggregate, not only per member (2026-09-09).** `MAX_MEMBER_BYTES` (256 MiB) bounds **one** member and nothing else — its comment used to read like an answer to the zip-bomb question in general, which is precisely why every aggregation above it went unbounded. What a *record* makes the importer hold at once is chosen by the archive, so it carries its own ceilings: **`facebook::posts::MAX_RECORD_MEDIA_REFS`** (512) caps the media refs one record may name, and **`run::MAX_RECORD_MEDIA_BYTES`** (64 MiB) caps the bytes one record's media may occupy together — without them a single crafted record reached N × 256 MiB, N attacker-chosen. The byte budget is checked on each member's *declared* size before the member is read (`ArchiveReader::member_size`; the reader never returns more than that), so the member that would cross it is never materialized and the constant is the true peak, not the budget plus one whole member. Both refuse the way rule 1 demands: the oversized record is skipped with its reason, and a truncated media list emits its own skip-log line naming how many were dropped, because a silent trim is data loss the user never learns about. A third ceiling, **`facebook::json::MAX_IDENTITY_BYTES`** (1 KiB), bounds what the parser *copies* rather than holds: a thread's ID goes into every one of its messages, and the owner's ID and display name into every comment, reaction and message the owner wrote or is the target of — so without it one identity's length was multiplied by a record count, two numbers the archive picks, and the model outgrew the JSON it came from. A thread whose ID outgrows the ceiling is refused whole (one skip, on both thread streams, before any of its messages is built); a profile whose owner ID or name does is refused, and the export is read with the nameless owner an export without a profile gets. Real ones are tens of bytes. Three aggregations are deliberately **un**capped and bounded by construction instead — capping any of them would refuse large *legitimate* archives, which is the failure this rule is not for: `collect_category` holds one category's entities because that is exactly what writing `model/*.cbor` requires (with their CBOR encoding beside them while the file is written, and the model file's bytes beside its decoded entities wherever a run reads one back — about twice the entities); a member's parse burst is bounded by `MAX_MEMBER_BYTES` × its expansion; and a **message thread** — a directory whose number of `message_<n>.json` files the archive chooses — is read one file at a time, each file's JSON dropped once its messages are taken, so a thread holds one member's parse burst plus its own messages, which are a slice of what `collect_category` holds for the Messages category anyway (the Threads stream keeps only their count and date range). The thread is the one that went unnoticed, and the largest: holding a directory's files together multiplied a member's burst by a file count the archive picks — `libs/fauna-archive/tests/thread_aggregate_bound.rs` fails if a thread's hold grows with its file count. Layout derivation is linear in entries (the thread grouping is a map, not a scan) since `locate` re-runs on every `detect`/`index`/`stream`.

## Compatibility

All changes are additive within the major (architecture/version-compatibility.md § I4): `Post.origin` (serde default; strings), `SourceKind::{Facebook, Instagram}` (old clients fall to `Other { raw }`), `Rail::Archive` (a client-local projection, never on the wire), the tier `hidden` flag, the nest's `source`-from-`origin` derivation (an older nest indexes `"fauna"`), and the interact door's native arm widened to every native token (an older client, whose `source == "fauna"` native test now fails for such a post, sends its like to the interact door, whose native arm serves it instead of the 501 an unknown token got). **Named gap for a pre-slice-2 client against a new nest (zero exposure until slice 3 authors the first origin post):** such a client can never `unlike` an imported post, and its `reply`/`repost`/`quote` reach the door's catch-all sub-arm, which acks target info and creates nothing — the typed body is silently dropped. Slice 3 closes this before the first import (ruling 3 below).

**Slice-3 rulings (2026-09-06, refutable advisory — each is the answer the goal docs and priorities already imply; a later session may refute one by naming the doc it contradicts):**

1. **Never re-broadcast an import.** `PUBLIC_POST_SERVABLE` refuses every archive-platform `source`, so an imported public post is served on Fauna (the feed read is untouched — the exclusion is off-box only) and never federated, projected to Bluesky or materialized onto the relay. A backdated flood into other networks' home timelines is the one irreversible outcome, under-publishing is the safe failure direction (`moderation.md` § Legal takedown's own ground), and re-publication to a searchable external network is elsewhere a deliberate author act, never a side effect. The exclusion lives in the one predicate, keyed on `fauna_core::source::ARCHIVE_PLATFORMS`, so every present and future off-box *pull* consumer inherits it — and in its create-time twin, `publishable_off_box_at_create`, kept beside the SQL, for the two *push* legs (the ActivityPub `Create`-push and the Bluesky write-through) that fire on the decoded post before any row exists and so cannot apply a SQL predicate; `moderation.md` § Legal takedown owns both halves. Publishing an import outward later is a phase-three direction with the same posture as Nostr-advertise: a per-import author act, never automatic.
2. **The envelope identifies the platform, not the post** — § What each category becomes → *The post origin field*.
3. **The older client fails loudly, and the older nest imports only what it can hold.** The interact door's native arm answers `reply`/`repost`/`quote` on an archive-platform post with `bad_request` naming the cause (a reply, repost or quote of an imported post is composed as a signed post by the app; an app that sent it here predates archive imports and must be updated), while the `fauna` token keeps its legacy target-info answer; `like`/`unlike` stay served on every native token. A nest that does not advertise `hidden-tiers` (below) never receives a gated import: the wizard imports the public categories and skip-logs the rest with the nest-update reason (§ Audience mapping), rather than minting a reserved tier that nest would offer to strangers.
4. **Hidden means not offered and not subscribable** — `monetization.md` § The unifying model → *A tier may be hidden* owns the ruling; the mint passes `auto_approve: false`.

Two additive mechanisms carry the rulings: the `hidden-tiers` capability token (`fauna_protocol::discovery::capability::HIDDEN_TIERS`), advertised by a nest that refuses `subscribe` to a hidden tier and accepts the reserved-name `tiers.create`; and that relaxation itself — `tiers.create` with `name == followers` at exactly rank 0, idempotent, birth blob stored when the row has none (`monetization.md` § The unifying model). An older nest answers the relaxation with its `rank must be >= 1` refusal, which the machine never reaches because it checks the token first. The `PostOrigin` shape correction (ruling 2) is not a wire break: the production pin (`tests/e2e-unified/pinned-previous-build.toml`, 2026-08-27) predates slice 2, so no released peer ever encoded or decoded the field. **Phase two's precondition:** `ChannelMessageBody` has no unknown-variant catch-all today (§ Implementation status today), so before any `Archive` variant ships, the decode path's behavior on an unknown variant is verified and, if it fails the fetch rather than skipping the one message, an `Unknown` catch-all lands first, alone, and is released before the variant exists — an old client must ignore what it does not know, never fail its thread. (Verified 2026-09-06 by reading `libs/fauna-conversations/src/backends/fauna_mls.rs:3037-3056` and `libs/fauna-mls/src/types.rs:145-149`: an undecodable envelope is skipped, not fatal — so the "verify FIRST" commit is a test pinning that behavior; the `Unknown` catch-all lands only if the test disproves it.) **Ruled 2026-10-01:** `ChannelMessageBody` is a record-level-skip enum (`../architecture/transport.md` § Schema and forward-compat discipline → *Rule 3 in full*, answer 3), and the pinning test on the body itself — today's pin covers a nested `GroupMetaMessage` variant only — lands before the 2026-10 baseline, which is what "released before the variant exists" needs.

## Architectural rules

- **The app parses; the nest stores sealed.** Never a nest-side parse, never delegated authoring for imports, never a materialization grant for this — the archive is client-originated data.
- **Signed by its owner.** Every post, reply and reaction produced by an import or a merge is signed by the app of the person whose content it is. Nothing is ever attributed to someone who did not sign it.
- **No shadow graph.** No contact, actor or profile is created for a person who is not a linked Fauna user; unmatched names live only inside the owner's sealed folder.
- **One model, N parsers.** Platform knowledge stops at the parser boundary; the machine, the mapping, the wizard and the merge protocol are platform-agnostic.
- **Uniform across the 7 apps** (priorities #1–#3): one machine, one page, one ID set; per-app code is the file-choosing shell and the rendering glue, nothing else.
- **Everything in the folder is user-visible and user-deletable** (principles.md § The user always controls their data).
- **The parser crate is a reusable library (user ruling 2026-09-07).** `libs/fauna-archive` — the model, the frozen ID derivation, the mojibake repair, the zip seam, the parsers — depends on crates.io only, never on a `fauna-*` crate: it carries its own epoch-micros `Timestamp` (byte-identical on the wire to `fauna_core::data::Timestamp`), its own platform token constants (pinned equal to `fauna_core::source`'s vocabulary by a test in the machine crate, the one crate that knows both sides), and calls `serde_ipld_dagcbor` directly for the derivation (the codec `fauna-cbor` wraps, so the goldens did not move). Everything Fauna-specific — what a record becomes, where it rests, under which audience — is the machine's. Chosen as the cheapest of four shapes (git dependency as-is; decouple in place; a neutral name plus a written derivation spec; a crates.io publish); the last two are deferred until the Instagram parser has shaped the API, because a published crate freezes its API and its ID derivation.

## Don't do these

- Don't import friend lists as contacts, or hash them into any nest-side index — the matching key stays inside the sealed folders and the sealed DM channel.
- Don't publish other people's comments or messages under the archive owner's identity, not even "as a quote".
- Don't backdate by rewriting `created_at` after the fact; a post is created with its original date once.
- Don't add a per-item consent step to merges; the per-pair link is the consent (user directive 2026-09-05). Unlink is the off switch.
- Don't add a nest-side `import_sessions` twin for archives; the folder's `state/` is the session.
- Don't add a platform-specific field to `Post` or to any wire type; provenance is `origin`, and everything else is inside the archive model.
- Don't accept the HTML export "as a convenience" — one format per platform per parser, until a second is scoped and tested.
