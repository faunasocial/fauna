## The deposit

*The third-party integration chain's folder half — the owner of the **deposit** and its adoption. The bearer door on the DAV server and the read grant twin are [`webdav-server.md`](webdav-server.md) § Independent enablement → *Third-party read + deposit*; the page facet [`../ui/folders.md`](../ui/folders.md) § Audience and website serving → *Third-party deposit and read*; the keyless `deposit` class [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Capability tiering → *Third-party holders*.*

**Deposit is write-only and carries no key.** A third-party principal holding `fauna:folder:deposit:<id>` posts a file to `/api/v1/folders/{id}/deposit` (remote servers — classified as HTTP residue by [`../architecture/api-layers.md`](../architecture/api-layers.md); a hosted principal deposits over WS-RPC without the HTTP door). The nest seals it **on the user's behalf** to the user's registered recipient key through the one resolver the mail ingest sites already share (the D2 seal-key resolver, [`smtp-server.md`](smtp-server.md) § Inbound pipeline; [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § The sealed posture) and parks it in the folder's **inbox segment** — a per-folder holding area that is not yet a folder entry. The principal holds no key, sees no folder content, and learns nothing but "accepted".

**The door, as built (2026-10-03).** Both forms carry one file — a name, a declared media type, at most `MAX_DEPOSIT_BYTES` (1 MiB, under the WS-RPC message cap so the two doors accept the same deposits; `fauna_protocol::folders`) in the single-message form, more in the staged form (§ Deposits larger than one message) — and run one gate (`bins/fauna-nest/src/folder_deposit.rs`): the HTTP form admits the DPoP-bound token exactly as the principal session's upgrade does and dispatches the same kinds, `fauna.folders.deposit` for a body that fits one message. After the `ThirdParty` ceiling and the arm-wide scope check, the handler requires, in order: a name that is one plain file-name component every seat's platform lands as an ordinary visible file (`is_deposit_name`, shared with adoption — no separator or control character; no leading `.`, so no dotfile, which the scanner would never upload and which is a stage's shape; and none of the shapes Windows will not create, so a Windows seat never leaves an item parked for ever: a `:` such as a drive prefix `C:x`, the characters `<>"|?*`, a reserved device name with any extension such as `CON` or `nul.txt`, a trailing `.` or space — the device-name check is `fauna_core::windows_names`, which the mail export's namer shares, 2026-11-05); one of the session's scopes naming **this** folder; a LIVE keyless `deposit` grant over this folder, owned by the account and held by the key the principal attested — the audit + revocation record, re-resolved at every deposit, so revoking the grant ends deposits as revoking the principal does; a folder the account owns; and a residency that is not metadata-only. Every refusal but the last answers the same `fauna.folders.permission_denied`, so a depositor never learns whether a folder it does not hold exists; the metadata-only refusal names its reason (`ui/folders.md` § Audience and website serving → *Third-party deposit and read* owns the refusal pairs — a `public` folder is **not** one of them for deposit). The sealed payload is a `DepositEnvelope` (name, media type, bytes — all content, so all inside the seal), sealed through the recipient-blob seal the nest's other seal sites use, and the inbox segment is the `folder_deposit_inbox` table: per item the folder, the depositor's principal id (kept past a revoke — an accepted item is the user's), the sealed blob, its size and the arrival time. A deleted folder takes its unadopted items with it, as it takes its files. The reply is `{accepted: true}` (HTTP `202`) and nothing else.

**Adoption is the user's next client sync.** An owner's seat of the folder opens the parked item with the owner's recipient key, re-seals it under the folder's own convergent scheme ([`file-sync.md`](file-sync.md) § Content-Addressed Storage — `BackupKey`-rooted for an unbound folder, the M2 content key for a bound one), and records it as an ordinary change row through the same remotely-authored-change door every other ingest uses — guard, then rename, never a direct write (the invariant [`file-sync.md`](file-sync.md) § Content-Addressed Storage's last paragraph states). From then on it is a file like any other: versioned, synced, served. This is the mail pattern applied to files: sealed at the perimeter to the user, adopted by the user's own device.

**Adoption, as built (2026-10-05).** Two owner-only kinds beside the door, `fauna.folders.deposits.list` (a page of the folder's parked items, sealed as they rest, oldest first) and `fauna.folders.deposits.retire` (drop one by its id; `false` when already gone), both refusing a folder the caller does not own as not found. The engine pass is `SyncEngine::adopt_deposits` (`libs/fauna-sync-engine/src/deposit_adoption.rs`), armed at build only on a set the account owns on its own nest (never a member's, a reader's or a cross-nest set's engine: only the owner's recipient secret opens the item), and run after the pull by every root, one shared pass (`always_resident::adopt_parked_deposits`): the always-resident root on entry, on every rescan tick and on the sync nudge the door sends the owner's devices alone; the on-demand root (cfapi, FUSE) after its startup fold and every re-pull, flipping each retired file in-sync like any recorded upload. A cloud placeholder holding a candidate name is never opened (only that root's own loop answers its fetch): its row says whether it holds the item's bytes, else the name is taken. Per item: open it with the recipient secret derived from every MSEK the mail custody holds (`fauna.state.mail`, current then the retained priors), through the X-Wing opener, which opens the classical degrade too; land it under its own name, or under `<stem> (deposit <id>)<ext>` when another file holds that name, so every seat derives the same target; write it through `contained_apply_target` and `atomic_write_file`; record it with the ordinary own-change upload, which seals it under the folder's scheme; retire it once the path's recorded head is exactly the item's bytes. A seat that finds the target already holding those bytes (another seat adopted it, or a crash fell before the retire) writes nothing and only records if owed, then retires, so adoption is idempotent on the deposit id. A host whose custody source holds no mail custody (a capability host's cold replica) adopts nothing; another of the owner's seats does. An item larger than one message carries no body in its envelope, only its part count: the pass fetches each part (`fauna.folders.deposits.part`, owner-only like the other two), opens it with the same key, refuses the item — leaving it parked — when the index sealed inside a part is not its place, and streams the parts in order into a stage: a dotfile temp beside the target (the scanner never uploads a dotfile), hashed as it is written and fsynced, so at most one part is held in memory and the landed check compares length and a streamed hash rather than reading the target whole; the stage lands by the same guard, then rename, and a refused or already-landed item's stage is removed. **A capability host — the apple File Provider face, android's provider — has no pull loop and runs the same pass in its host's refresh, its MSEK read through the host's fleet replica: [`on-demand-files-apple.md`](on-demand-files-apple.md) § Apple File Provider binding → *Third-party deposit adoption on a capability host* owns that ruling (2026-10-10; unbuilt).**

## Deposits larger than one message

*Built 2026-10-10.* A file over `MAX_DEPOSIT_BYTES` is deposited in **parts behind an atomic commit** — the shape of mail's continuation parts (`fauna_mail::transport_limits`), never a larger WebSocket frame: the bearer WS-RPC connection keeps its 2 MiB bound. On the principal session three kinds carry it, each running the whole gate above again, so revoking the grant or the principal ends an upload mid-way: `fauna.folders.deposit.begin` (the folder; answers a random 16-byte upload token, never a row id), `fauna.folders.deposit.part` (the token, an index from `0`, at most `MAX_DEPOSIT_PART_BYTES` = one message's worth; re-sending an index replaces that part, so a part whose reply was lost is retried as it was) and `fauna.folders.deposit.commit` (the token, the file's name and media type, the part count). Each part is sealed to the owner's recipient key **on arrival** as a `DepositPart` (its index inside the seal), so no plaintext rests while the upload is open; the commit seals the header — a `DepositEnvelope` with an empty body and the part count — and flips the item adoptable in one write, refusing unless exactly the indices `0..parts` are staged. Until then the item is a **staged upload** that no list shows and no part read serves: a crash, a dropped principal or a refused commit leaves either a staged upload or a whole item, never a half-adoptable one ([`../architecture/nest/common.md`](../architecture/nest/common.md) § Client-state recoverability). A staged upload idle for an hour expires with its parts, swept where uploads begin and where the owner's seats list (every rescan tick), so no timer of its own, through a partial index over the staged rows alone. A begun upload parks no byte the quota counts until its first part, so the open uploads are **counted** (2026-11-05): a principal holds at most `MAX_STAGED_DEPOSIT_UPLOADS_PER_PRINCIPAL` (16) staged uploads across every folder, and a folder at most `MAX_STAGED_DEPOSIT_UPLOADS_PER_FOLDER` (64) across every principal (bucket 1, `bins/fauna-nest/src/folder_deposit.rs`), counted under the same connection as the begin's insert; a begin past either is refused with `fauna.folders.too_many_uploads` (HTTP `429`), and a commit, a refused name or the idle expiry gives the place back. A commit refused for its name drops the upload at once; a repeated commit of a committed upload answers `accepted` again. A deposit has at most `MAX_DEPOSIT_PARTS` (1024) parts — `MAX_DEPOSIT_TOTAL_BYTES`, 1 GiB, equal to the inbox's hard ceiling (§ The inbox quota), which no single deposit could rest past anyway: adoption streams, so no smaller per-deposit bound is needed to keep a seat's memory finite (the nest pins the equality at compile time). **The HTTP door streams instead:** a remote server posts the whole body to the one `POST /api/v1/folders/{id}/deposit`; a body that fits one message dispatches `fauna.folders.deposit`, a larger one is cut into parts as it arrives and dispatches begin, each part and the commit through the same principal dispatch — so the door holds at most two parts of plaintext, and the item is adoptable only once the whole body arrived. That route alone is mounted outside the router's blanket 10 MB body limit, the handler bounding the body at `MAX_DEPOSIT_TOTAL_BYTES` (`413` past it). At rest a larger item is its `folder_deposit_inbox` row (the sealed header; `committed`, `upload_token`) plus one `folder_deposit_parts` row per sealed part, which go with the item's retire and its folder's deletion.

## The inbox quota

*Built 2026-10-10.* An unbounded inbox would be a disk-fill door for any principal holding the scope, so the sealed bytes parked for one account — every item's header, every part, staged uploads included, across all its folders — are bounded, checked under the same connection as the write so two deposits cannot both squeeze under it: **the tier's `max_inbox_bytes` where tier quotas are enforced** (the tier *is* the quota, [`admin.md`](admin.md) § 2 Users; `0`, the storage-only `backup` tier, admits no deposit), and always a hard-coded ceiling of 1 GiB (`DEPOSIT_INBOX_CEILING_BYTES`, bucket 1 — the bound on a nest that enforces no tier quota, the single-user desktop nest). The deposit budget is measured from the inbox tables themselves, not charged to the delivery inbox's `users.inbox_bytes_used` counter, so a principal's deposits never block the user's mail and messages, and an adopted item's retire gives its room back at once. The commit's sealed header counts like a part — it carries the name and the media type the principal chose, the type bounded at `MAX_DEPOSIT_CONTENT_TYPE_BYTES` (255) on both kinds and refused as `invalid_params` past it, so no header parks bytes the quota did not count. A single-message deposit, a part or a commit past the quota is refused with `fauna.folders.inbox_full` (HTTP `507`) and parks nothing (a refused commit leaves its upload staged); the principal learns only that the owner's inbox is full until their apps adopt what is parked.

## The depositor signs, the owner's device verifies

*Ruled 2026-11-05; the nest's half, the adopter's check and ruling 3 built 2026-11-05 — § Implementation status today names what is still to run. Refutable until the first signed deposit is adopted.*

**The defect this closes.** The nest seals a deposit to the owner's recipient key, which is public, and the owner's seat adopted whatever opened under it: a nest could park an item of its own making in any owned folder, and the seat would land it and record it as the owner's own change — signed by the owner's device, sealed under the folder key — so the members of a shared folder received it as owner-authored. Before deposits the nest could author no folder content ([`participants.md`](participants.md) § Mechanism asymmetry: the client is the trusted mint, the nest an untrusted holder). A keyless door is only as narrow as the adopter's check, and the adopter checked nothing but the seal.

**Ruling 1 — a deposit carries its depositor's signature, and the owner's device admits an item only on a signature it can tie to a grant the owner signed.** The principal signs every deposit with its attested Ed25519 writer key (`fauna_writer_ed25519`, the key a `content.write` grant already confines a principal's rows to — [`../architecture/third-party-kinds.md`](../architecture/third-party-kinds.md) § Principal write authority; a principal that attested none cannot deposit, below). The statement it signs is a fixed byte layout, so a remote server in any language needs only BLAKE3 and Ed25519: the domain tag `fauna.folder-deposit.v1\0` (the self-delimiting convention of `fauna_core::account_entry_crypto`'s in-seal signature), the folder's row id as 8 big-endian bytes (two's complement), the body's length as 8 big-endian bytes, the BLAKE3 of the whole body (the folder plane's content hash, which adoption computes anyway), the BLAKE3 of the name's UTF-8 bytes and the BLAKE3 of the declared media type's UTF-8 bytes — hashed, so no field needs a length prefix. The signature rides the request: a `sig` field on `fauna.folders.deposit` and on `fauna.folders.deposit.commit` (the parts carry none — the commit binds them, carrying the whole body's hash beside the signature since the nest cannot hash sealed parts, the nest summing the staged parts' length), and on the HTTP door a `Fauna-Deposit-Signature` header (unpadded base64url), the statement's name and media type being the `?name=` and `Content-Type` the request sent. The nest verifies the signature under the caller's own attested writer key — never a key the request names — before it seals, refusing a missing or failing one as `invalid_params`, and checks the statement's hash and length against the body wherever it holds the whole plaintext: the single-message form, and the HTTP door, which hashes the body as it streams. The staged WS-RPC form's parts may arrive out of order or be re-sent, so there the nest verifies authorship alone and the body binding is the adopter's (a principal lying about its own hash loses only its own deposit). The nest writes the writer key and the signature into the `DepositEnvelope` it seals (`writer`, `sig`, additive) — the nest is what saw the caller's attested key, so a principal cannot name another's.

**The adopter's check.** The owner's seat, having opened an item, rebuilds the statement from what it holds (the folder id it is armed with, the envelope's name and media type, the body's length and the hash it streams anyway), verifies `sig` over it under the envelope's `writer`, and admits the item only when **the owner's own signed grant log authorizes that writer for this folder**: a `Mint` or `Renew` event in the succession ledger's chain-signed fold ([`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Capability tiering → *Third-party holders*) carrying a `deposit` tuple over this folder confined to that writer. This is position (2) of `content.write` applied to the deposit class — `fauna_account_plane::ext_writers` over `fauna_core::grant_event::content_write_authorizations` — with a fold `deposit_authorizations` beside it, read by the engine through its custody source: a `FolderKeyReader::deposit_writers(folder_id)` beside `recipient_mseks`, answered from the same replica (the seat's account runtime, the capability host's cold replica), a source holding no log answering empty, which licenses nothing. An item that fails either check — no signature, one that does not verify, a writer the log never authorized for this folder — is **left parked**, exactly as an item the seat cannot open is today: never landed, never recorded, never retired, counted as deferred and logged at warn as a detection signal (an honest nest's door refuses such an item before it is parked, so one found parked was parked by something that is not that door). Not retired, because an item may arrive before its `Mint` reaches this replica — the log lags the nest by one pump — and the first pass after the event lands admits it, the re-presentation `ext_writers` keeps. The seal is unchanged: it still keeps the nest and every other reader out of the content; the signature is what keeps the nest out of the authorship.

**Ruling 2 — adoption is armed by the grant log, and that is the same read.** The finding asked whether adoption should be armed only for folders the owner's log shows opened to deposit; under ruling 1 the set of writers the log authorizes for the folder *is* that arming: a folder with no `deposit` `Mint` in the log has an empty writer set, so nothing verifies and nothing is adopted. The engine keeps `set_deposit_inbox` on every owned set on its own nest (the list is a cheap owner-only read, and every custody read waits for a parked item) and reads the writer set only once an item is parked, as it reads the MSEK — no separate arming flag, so a consent given after the engine was built reaches the next pass without a rebuild, the posture `recipient_mseks` already has.

**Ever minted, revoked or not.** The adopter admits a writer that any `Mint` or `Renew` in the log ever named for the folder, as `content_write_authorizations` does and for the same reasons: an accepted item is the user's (§ The deposit — the inbox row keeps the depositor past a revoke), a parked item carries no trusted time a revocation window could be checked against (`received_at` is the nest's word), and what ends a principal's depositing is the nest's door closing with its grant. The bound is the honest-box revocation bound every keyless class rests on ([`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Capability tiering → *Third-party holders*): a revoked principal that keeps its writer key deposits again only through a nest that disobeys its own door, and then only items it signs itself, recorded as its (ruling 3) — never as the owner's.

**The tuple names its writer, and the log twin names the folder.** `ScopeTuple::folder_deposit` gains the holder's attested writer key as its `factor` (`writer:<hex>`, `fauna_core::grant_event::writer_factor` — the `content.write` tuple's own shape; the class stays keyless, a factor is not a key), so the nest's door admits a grant only when its `deposit` tuple over the folder names the caller's attested writer — as the `records` put admits only the row's writer — and the writer-replacement rule ends it: a later ceremony attesting a different writer key ends, nest-side at `/oauth/token` and in the owner's log at the approve, every third-party grant whose `content.write` **or `deposit`** tuple names the old writer ([`../architecture/third-party-kinds.md`](../architecture/third-party-kinds.md) § Principal write authority owns the rule; [`../architecture/third-party.md`](../architecture/third-party.md) § The principal model → *Key replacement* the owner's record of it). The log's `GrantEventScope` is frozen and carries no `set`, so today a deposit `Mint` records the class and no folder; the twin folds the folder into the `kind` slot as `folder:<id>` with the writer factor after it (`kind: "folder:17 writer:<hex>"` — `base_kind` the folder token, `factor` the writer; the precedent for a non-kind token in that slot is the kind-less `labeler:<hex>`), `deposit_authorizations` reads both back, and the succession re-mint rebuilds the tuple's `set` from the same token. The consent side refuses a `folder:deposit` arm from a client that attested no writer key — at PAR as `invalid_request` (the nest's half, where a malformed key is refused today) and in the planner as `ExtConsentError::NoWriterKey` beside `NoHolderKey` (the app's half, fail-closed) — so a deposit scope is never minted blind of its writer.

**Ruling 3 — the adopted change records its depositor.** The change row the seat records carries `deposited_by`, the depositor's writer key (hex; additive on `SyncChange` and the record request), inside the writer-signed statement ([`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md)): the owner's device's signed word to every member, not a nest stamp — the nest learns nothing by it (its inbox row named the depositor already) and a member learns it. The version row's author (`file-version-author`, [`../ui/media.md`](../ui/media.md) § Element IDs; the recorder's attribution is owned by [`file-sync.md`](file-sync.md) § Multi-writer shared sets) reads the depositor beside the recorder: the owner's app resolves the writer key through its connected-apps roster (`PrincipalInfo.writer_ed25519`) to the app's label — "<app> via <owner>" — and a member's app, holding no roster of the owner's, "a connected app via <owner>"; a strings change in `i18n/`, no new element. The depositor's own signature is not carried into the change row: a member holds no copy of the owner's log to verify it against, and the owner's device vouched when it adopted. tui leads, the other six follow in their trickle-down batches ([`../architecture/testing.md`](../architecture/testing.md) § Default app and nest mode).

**Residuals, stated.** The folder is named by its nest row id on the scope string, the tuple and the statement alike, as the consent card named it to the user; a nest that renumbers an account's sets is outside this ruling and every other folder-id door. The signature binds a deposit to its depositor and its content, not to a time: `received_at` stays the nest's word. The staged form's body binding rests on the adopter alone (ruling 1). The HTTP door's signing contract is not yet a public text; the day it is documented for third parties it goes through [`../architecture/public-texts.md`](../architecture/public-texts.md), the layout above being its source.
