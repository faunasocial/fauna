## The deposit

*The third-party integration chain's folder half — the owner of the **deposit** and its adoption. The bearer door on the DAV server and the read grant twin are [`webdav-server.md`](webdav-server.md) § Independent enablement → *Third-party read + deposit*; the page facet [`../ui/folders.md`](../ui/folders.md) § Audience and website serving → *Third-party deposit and read*; the keyless `deposit` class [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Capability tiering → *Third-party holders*.*

**Deposit is write-only and carries no key.** A third-party principal holding `fauna:folder:deposit:<id>` posts a file to `/api/v1/folders/{id}/deposit` (remote servers — classified as HTTP residue by [`../architecture/api-layers.md`](../architecture/api-layers.md); a hosted principal deposits over WS-RPC without the HTTP door). The nest seals it **on the user's behalf** to the user's registered recipient key through the one resolver the mail ingest sites already share (the D2 seal-key resolver, [`smtp-server.md`](smtp-server.md) § Inbound pipeline; [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § The sealed posture) and parks it in the folder's **inbox segment** — a per-folder holding area that is not yet a folder entry. The principal holds no key, sees no folder content, and learns nothing but "accepted".

**The door, as built (2026-10-03).** Both forms carry one file — a name, a declared media type, at most `MAX_DEPOSIT_BYTES` (1 MiB, under the WS-RPC message cap so the two doors accept the same deposits; `fauna_protocol::folders`) in the single-message form, more in the staged form (§ Deposits larger than one message) — and run one gate (`bins/fauna-nest/src/folder_deposit.rs`): the HTTP form admits the DPoP-bound token exactly as the principal session's upgrade does and dispatches the same kinds, `fauna.folders.deposit` for a body that fits one message. After the `ThirdParty` ceiling and the arm-wide scope check, the handler requires, in order: a name that is one plain file-name component (`is_deposit_name`, shared with adoption); one of the session's scopes naming **this** folder; a LIVE keyless `deposit` grant over this folder, owned by the account and held by the key the principal attested — the audit + revocation record, re-resolved at every deposit, so revoking the grant ends deposits as revoking the principal does; a folder the account owns; and a residency that is not metadata-only. Every refusal but the last answers the same `fauna.folders.permission_denied`, so a depositor never learns whether a folder it does not hold exists; the metadata-only refusal names its reason (`ui/folders.md` § Audience and website serving → *Third-party deposit and read* owns the refusal pairs — a `public` folder is **not** one of them for deposit). The sealed payload is a `DepositEnvelope` (name, media type, bytes — all content, so all inside the seal), sealed through the recipient-blob seal the nest's other seal sites use, and the inbox segment is the `folder_deposit_inbox` table: per item the folder, the depositor's principal id (kept past a revoke — an accepted item is the user's), the sealed blob, its size and the arrival time. A deleted folder takes its unadopted items with it, as it takes its files. The reply is `{accepted: true}` (HTTP `202`) and nothing else.

**Adoption is the user's next client sync.** An owner's seat of the folder opens the parked item with the owner's recipient key, re-seals it under the folder's own convergent scheme ([`file-sync.md`](file-sync.md) § Content-Addressed Storage — `BackupKey`-rooted for an unbound folder, the M2 content key for a bound one), and records it as an ordinary change row through the same remotely-authored-change door every other ingest uses — guard, then rename, never a direct write (the invariant [`file-sync.md`](file-sync.md) § Content-Addressed Storage's last paragraph states). From then on it is a file like any other: versioned, synced, served. This is the mail pattern applied to files: sealed at the perimeter to the user, adopted by the user's own device.

**Adoption, as built (2026-10-05).** Two owner-only kinds beside the door, `fauna.folders.deposits.list` (a page of the folder's parked items, sealed as they rest, oldest first) and `fauna.folders.deposits.retire` (drop one by its id; `false` when already gone), both refusing a folder the caller does not own as not found. The engine pass is `SyncEngine::adopt_deposits` (`libs/fauna-sync-engine/src/deposit_adoption.rs`), armed at build only on a set the account owns on its own nest (never a member's, a reader's or a cross-nest set's engine: only the owner's recipient secret opens the item), and run after the pull by every root, one shared pass (`always_resident::adopt_parked_deposits`): the always-resident root on entry, on every rescan tick and on the sync nudge the door sends the owner's devices alone; the on-demand root (cfapi, FUSE) after its startup fold and every re-pull, flipping each retired file in-sync like any recorded upload. A cloud placeholder holding a candidate name is never opened (only that root's own loop answers its fetch): its row says whether it holds the item's bytes, else the name is taken. Per item: open it with the recipient secret derived from every MSEK the mail custody holds (`fauna.state.mail`, current then the retained priors), through the X-Wing opener, which opens the classical degrade too; land it under its own name, or under `<stem> (deposit <id>)<ext>` when another file holds that name, so every seat derives the same target; write it through `contained_apply_target` and `atomic_write_file`; record it with the ordinary own-change upload, which seals it under the folder's scheme; retire it once the path's recorded head is exactly the item's bytes. A seat that finds the target already holding those bytes (another seat adopted it, or a crash fell before the retire) writes nothing and only records if owed, then retires, so adoption is idempotent on the deposit id. A host whose custody source holds no mail custody (a capability host's cold replica) adopts nothing; another of the owner's seats does. An item larger than one message carries no body in its envelope, only its part count: the pass fetches each part (`fauna.folders.deposits.part`, owner-only like the other two), opens it with the same key, refuses the item — leaving it parked — when the index sealed inside a part is not its place, and streams the parts in order into a stage: a dotfile temp beside the target (the scanner never uploads a dotfile), hashed as it is written and fsynced, so at most one part is held in memory and the landed check compares length and a streamed hash rather than reading the target whole; the stage lands by the same guard, then rename, and a refused or already-landed item's stage is removed. **A capability host — the apple File Provider face, android's provider — has no pull loop and runs the same pass in its host's refresh, its MSEK read through the host's fleet replica: [`on-demand-files-apple.md`](on-demand-files-apple.md) § Apple File Provider binding → *Third-party deposit adoption on a capability host* owns that ruling (2026-10-10; unbuilt).**

## Deposits larger than one message

*Built 2026-10-10.* A file over `MAX_DEPOSIT_BYTES` is deposited in **parts behind an atomic commit** — the shape of mail's continuation parts (`fauna_mail::transport_limits`), never a larger WebSocket frame: the bearer WS-RPC connection keeps its 2 MiB bound. On the principal session three kinds carry it, each running the whole gate above again, so revoking the grant or the principal ends an upload mid-way: `fauna.folders.deposit.begin` (the folder; answers a random 16-byte upload token, never a row id), `fauna.folders.deposit.part` (the token, an index from `0`, at most `MAX_DEPOSIT_PART_BYTES` = one message's worth; re-sending an index replaces that part, so a part whose reply was lost is retried as it was) and `fauna.folders.deposit.commit` (the token, the file's name and media type, the part count). Each part is sealed to the owner's recipient key **on arrival** as a `DepositPart` (its index inside the seal), so no plaintext rests while the upload is open; the commit seals the header — a `DepositEnvelope` with an empty body and the part count — and flips the item adoptable in one write, refusing unless exactly the indices `0..parts` are staged. Until then the item is a **staged upload** that no list shows and no part read serves: a crash, a dropped principal or a refused commit leaves either a staged upload or a whole item, never a half-adoptable one ([`../architecture/nest/common.md`](../architecture/nest/common.md) § Client-state recoverability). A staged upload idle for an hour expires with its parts, swept where uploads begin and where the owner's seats list (every rescan tick), so no timer of its own; a commit refused for its name drops the upload at once; a repeated commit of a committed upload answers `accepted` again. A deposit has at most `MAX_DEPOSIT_PARTS` (1024) parts — `MAX_DEPOSIT_TOTAL_BYTES`, 1 GiB, equal to the inbox's hard ceiling (§ The inbox quota), which no single deposit could rest past anyway: adoption streams, so no smaller per-deposit bound is needed to keep a seat's memory finite (the nest pins the equality at compile time). **The HTTP door streams instead:** a remote server posts the whole body to the one `POST /api/v1/folders/{id}/deposit`; a body that fits one message dispatches `fauna.folders.deposit`, a larger one is cut into parts as it arrives and dispatches begin, each part and the commit through the same principal dispatch — so the door holds at most two parts of plaintext, and the item is adoptable only once the whole body arrived. That route alone is mounted outside the router's blanket 10 MB body limit, the handler bounding the body at `MAX_DEPOSIT_TOTAL_BYTES` (`413` past it). At rest a larger item is its `folder_deposit_inbox` row (the sealed header; `committed`, `upload_token`) plus one `folder_deposit_parts` row per sealed part, which go with the item's retire and its folder's deletion.

## The inbox quota

*Built 2026-10-10.* An unbounded inbox would be a disk-fill door for any principal holding the scope, so the sealed bytes parked for one account — every item's header, every part, staged uploads included, across all its folders — are bounded, checked under the same connection as the write so two deposits cannot both squeeze under it: **the tier's `max_inbox_bytes` where tier quotas are enforced** (the tier *is* the quota, [`admin.md`](admin.md) § 2 Users; `0`, the storage-only `backup` tier, admits no deposit), and always a hard-coded ceiling of 1 GiB (`DEPOSIT_INBOX_CEILING_BYTES`, bucket 1 — the bound on a nest that enforces no tier quota, the single-user desktop nest). The deposit budget is measured from the inbox tables themselves, not charged to the delivery inbox's `users.inbox_bytes_used` counter, so a principal's deposits never block the user's mail and messages, and an adopted item's retire gives its room back at once. A single-message deposit or a part past the quota is refused with `fauna.folders.inbox_full` (HTTP `507`) and parks nothing; the principal learns only that the owner's inbox is full until their apps adopt what is parked.
