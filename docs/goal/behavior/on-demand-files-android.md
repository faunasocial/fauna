#### Android SAF DocumentsProvider binding (designed 2026-09-26; direction user-ruled, the rules below advisory until built; shared-Rust cores and presence plan BUILT, the provider's read and write paths BUILT 2026-09-28, the toggle BUILT 2026-10-08, its device run UNBUILT)

Android realizes the on-demand surface as **a SAF `DocumentsProvider` over a replica the app owns** — apple's *set-level* shape (the per-set `folder-on-demand-toggle`, "Show in Files", own accepted folders, default ON), for apple's reason: a provider cannot take over a user-picked tree (a `content://` tree exposes no path — [`sync-engine-deployments.md`](sync-engine-deployments.md) § Implementation status today (android byte-sync)), but it can serve a tree the app itself owns. The direction is the user's ruling of 2026-09-26 ([`p2p.md`](p2p.md) § Cross-user shared-set transfer → Implementation status today: phones are peers, and android's peer-transfer leg is owed behind this replica); the rules below are this design's, refutable until a build slice proves or breaks them. It is the fourth binding and the only one where **the provider itself owns the tree** — there is no OS-managed location (apple) and no user directory (windows, linux) — which decides most of what follows. Ten binding-specific rules:

- **Control inversion, in the app's own process.** The OS — the system file browser, any other app's picker — calls the provider; there is no watcher and no disk scan on this surface, so the shared `provider_face` cores serve it exactly as they serve apple's extension: `queryChildDocuments` / `queryDocument` = `serve_enumerate` / `serve_item` (every live row, placeholder and materialized alike), `openDocument` = `serve_fetch_to_path` + `mark_hydrated`, a closed write = `serve_ingest_with_base`, `deleteDocument` = `serve_delete`, `renameDocument` / `moveDocument` = `serve_rename`. The provider is manifest-registered with no `android:process`, so it runs **in the app's process**: the hydration host is in-app, and *Who runs the hydration host* above has no process seam to cross here — no credential rendezvous, no second lifecycle, no app↔extension byte seam.
- **One construction path: the capability constructor.** Each set's host is built through the capability construction apple's extension uses (the owner `BackupKey` plus a bearer source plus a change-signer source, **never the identity seed**) — its owned-tree twin `FfiFileProviderHost::app_dead_owned_tree`, which derives the two roots below — fed from the app's own secure storage: the provider mints its own bearers and holds its own nest connection for the set list, since the process may be running for another app's picker with no app session. The change signer is the machine principal every capability host signs with ([`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, *The capability host* — owner of the ruling and of its android arm); here the host reads it out of the app's own principal slot itself (`machine_change_signer`, the shared-Rust slot reader) because there is no process boundary to copy it across. In-process it is not forced by a trust boundary; it is chosen because a provider the OS starts for another app's picker has no live app session to borrow, and because one construction path for every control-inverted host is the uniform shape (priority #3). One host per set — per-set `fsid-<ref>.db`, the shared `device.db`, in the account's sync state dir — built lazily by the first call that names the set and dropped at teardown; the multi-root rule above holds unchanged.
- **The provider owns the tree, so the owned-tree logic is shared Rust.** On apple the OS keeps the replica, re-drives an un-acked change and evicts under pressure; here nothing does it for us. What the OS does for apple is therefore written **once, in shared Rust, beside the cores** — body lookup, hydrate-for-open, prepare-for-write, close → ingest, the start sweep, eviction observation — and surfaced through `FfiFileProviderHost`. The Kotlin provider translates `DocumentsContract` calls into host calls and builds cursors; it holds no sync state and makes no sync decision (priority #2).
- **Two roots per set — a kept root and a cache root.** The **kept root**, `<filesDir>/on-demand/<actor-id-hex>/<ref-component>/` (the engine's `root_dir`), holds exactly the bodies this device must not lose: a local edit the nest has not recorded yet. The **cache root**, `<cacheDir>/on-demand/<actor-id-hex>/<ref-component>/`, holds recorded bodies, which the nest can always serve again. Account outermost, the ref one percent-encoded component (`local%3A1` — shared Rust's `FolderRef::path_component`, the identifier's own ref half: apple's staging-root grammar, from the same shared `ActorScopedFolderRef`). A lookup reads the kept root first, then the cache root; a body in neither is a placeholder — and a cache-root body counts only while its row is hydrated: once a refresh re-points the row at a moved head, the cached bytes are the superseded version and the next open fetches the head. The host derives both roots itself from the platform's files and cache directories (`OwnedTree::for_set`), so no app code spells the grammar.
- **Hydrate on open — and never a stand-in body.** Opening a document whose body is in neither root fetches it into the cache root (temp-then-rename), marks the row hydrated and only then returns the descriptor; the call blocks the caller's binder thread, as every cloud provider's does, and honours the `CancellationSignal`. A body that cannot be fetched (offline, signed out, a refused capability) fails the open with the platform's not-found error: a placeholder is *present-but-unreadable*, and the provider never answers with bytes that are not the file's. The first build advertises no thumbnail support, so browsing a folder never hydrates; the 0-byte case is the shared size-aware mapping above.
- **Freeing space is the OS's cache reclaim — and it is never a delete.** Android already has this platform's *free up space*: the system trims an app's cache under storage pressure, and the user's own "Clear cache" does it on demand. Recorded bodies live in the cache root precisely so that reclaim is the OS's, with no eviction policy and no constant of ours (a policy a user might want to choose would be app UI + nest state, as the linux binding records). Eviction is **observed**, as on apple: at open, at host start and on the refresh tick, a hydrated row whose body is in neither root is handed to `serve_evict` (`mark_placeholder`). No scan runs delete-detection on this surface, so a reclaimed body can never read as a deletion; and because an un-recorded edit is never in the cache root, *a change that has not reached the nest cannot have its space freed* holds by construction, not by a gate. "Always keep on this device" is the kept root's second use (a pinned body lives there); its control is not in the first build and is a Rule A item when it is proposed.
- **Two-way, with the body's presence as the write intent.** Opening for write promotes the body into the kept root (hydrating it first), and the descriptor carries a close listener; the close runs `serve_ingest_with_base` with the version the open saw, and on a *recorded* ack the body is demoted to the cache root (a conflicted ingest that moved the row to another head drops the local body, so the next open fetches the winner — the shared conflict arm). `createDocument` creates in the kept root; `deleteDocument`, rename and move are record-first and are **refused to the caller when they cannot be recorded**, never applied locally and lost. **A body found in the kept root IS the write intent:** the start sweep ingests every body there (the recorded-head-proof skip makes it idempotent) and demotes on ack, so a process death between a close and its upload loses nothing and needs no journal. *One exception (2026-10-01):* a body the share plane landed from a peer for a row the nest has not confirmed rests in the kept root too — the nest cannot serve it again either — but it was never this device's authorship, so the sweep and an unchanged close never ingest it; the nest's own row for the path confirms it (demoted like any recorded body) or supersedes it (dropped), and a body the user has since written over is an ordinary write intent again ([`p2p-shared-set-build.md`](p2p-shared-set-build.md) § *Phone peers — design* owns the landing policy and that reconcile). The sweep runs after the set is populated, and a kept-root body over a row that is a *placeholder* — the nest's head moved while the edit waited — takes the shared conflict auto-resolve rather than a plain upload, so the missing journal never costs a last-writer-wins clobber. A body leaves the kept root only on the engine's own dehydration proof (the row `Synced`, the disk hashing to the recorded head), and never while another descriptor still holds it open for write. **A directory is only its files' paths — it has no row — so it is deleted, renamed and moved file by file** (apple's appex walks a folder the same way): each file record-first, in path order, stopping at the first file that cannot be recorded with an error to the caller. The walk is not atomic, and it does not need to be: every file is either recorded at its new state or untouched, never lost, and repeating the gesture finishes the rest. An empty directory cannot be created (nothing would record it, and a directory the provider could not list again would be a lie); creating or renaming to an ignored name is refused, as is moving a directory into itself or a document across sets. What is advertised follows: a document supports write, delete, rename and move; a directory inside a set supports create, delete, rename and move; a set itself supports create only — it is never renamed or deleted from the provider.
- **Identity: the actor-scoped ref, never the set name.** A document id is `<ref-component>@<actor-id-hex>/<rel>` (`local%3A1@…/<rel>`) — the scoped identifier of apple's domains, whose percent-encoded ref half never carries the `/` the id splits on, followed by the folder-relative path — and the set's name is only the display name. One SAF root per **active** account, titled Fauna, whose children are that account's desired sets. Persisted URI grants key on the id, so it must not change when a set is renamed; a rename of a document returns its new id, as the contract allows.
- **Set-level, one local presence per set per device, serialized single-account — and the plan is shared Rust.** Desired sets = the folders this device holds an accepting place in (the apple bullet *Auto-appear default-ON* above owns the mode-free plan and its enrol gesture) ∩ toggle-enabled ∖ sets this device feeds through an ingress (the watched-directory ingress, the photo library): the explicit act outranks the ambient default, apple's precedence, so no set has two engines writing it from one device id. The toggle is device-local, keyed by the scoped identifier. **The plan and the preference store are shared Rust** — `fauna_folders_machine::on_demand_presence` (`desired_presences` + `plan`, the `OnDemandPrefs` store; FFI `on_demand_presence_plan` + `FfiOnDemandPrefsStore`) — so android consumes what apple does instead of growing a Kotlin twin, and apple's coordinator keeps only its OS calls. The plan takes every set the account holds with its role and seat — one shared mapping, `held_sets`, builds that list from the member-visible folder list and custody, so no app maps a row itself ([`on-demand-files-shared-sets.md`](on-demand-files-shared-sets.md) § *Shared sets on a capability host*, decision 3) — the stronger-presence refs, the toggle store, the registered identifiers, and an optional owner record; it answers add / keep / backfill / foreign-held / remove, each removal carrying the account and set its identifier scopes — none for an identifier that scopes no set, whose removal is un-gated. **The owner record is apple's alone:** the domain-owner map (defense in depth over a registry shared by every account on the device) stays persisted in apple's OS layer and enters the plan as data; android keys its roots by the scoped identifier alone and passes none. Sign-out, account switch and toggle-off **hide** the set at once (hosts dropped, the roots change notified) and delete the cache root, but never the kept root: its bodies are drained by the owning account's next session. iOS must refuse a removal while edits are un-recorded because the OS would destroy them; android owns the tree, so it hides and keeps. The plan's shared-with-me arm and a reader's read-only host are [`on-demand-files-shared-sets.md`](on-demand-files-shared-sets.md) § *Shared sets on a capability host*, decision 3.
- **Nothing of ours runs resident.** A remote change reaches the tree by `refresh()` — on a tick while the process lives, and on the file browser's own refresh — followed by a change notification on the affected children (the `signalEnumerator` twin); with the process dead the tree is simply as fresh as its last refresh, and the next call refreshes it. Doze and process death need no handling beyond the two roots' rules: a half-fetched temp file is discarded at the next start, a half-uploaded edit is still in the kept root. The provider is not direct-boot aware (credential-encrypted storage is closed before first unlock), and it resolves its dependencies at the first call, never in `onCreate`, which the platform runs before the application's own.

**The seam the peer-transfer plane consumes.** A phone's share plane serves from and ingests into this replica ([`p2p.md`](p2p.md) § Cross-user shared-set transfer), through three host-side operations and nothing else: **look up a body by path** (kept root, then cache root, else none — the serve half's honest `Ok(None)` for a placeholder); **land a body into a named root** (the kept root when the nest may not hold it yet, the cache root when it does); **record a row as a placeholder**. Which pulled bodies are landed and where is the phone-peer design's policy, owned by p2p-shared-set-build.md (§ Cross-user shared-set transfer → *Phone peers — design*, decided 2026-09-26); this binding only guarantees the two roots' invariants hold whoever lands the body. *Built 2026-10-01:* the plane's ingest door is one host operation over these (`OwnedTree::share_ingest`, surfaced as `FfiFileProviderHost::share_ingest`), and its serve half runs the lookup's own rule over the two roots and the set's state DB.

**Headless proof.** The owned-tree cores are tier-1 tested against the faked `ProviderEngine` the existing cores use, and proven against a real nest in the `conformance_file_provider_client.rs` vehicle (*Headless-first testing* above) — open-hydrates, a reclaimed body is observed and never recorded as a delete, a closed write uploads, a body left in the kept root by a killed process is uploaded by the start sweep, a delete that cannot be recorded is refused. The provider contract itself (`DocumentsContract` queries and opens through a `ContentResolver`) is an instrumented test on the emulator — the provider's `MANAGE_DOCUMENTS` guard admits the app's own uid, so the test needs no system role. The cross-app witnesses are android arms of `test_folder_on_demand_toggle.py` (the `files-on-demand` page's first outcome) and a read-path journey reading a document through the resolver, the read-path journey gated, like the toggle's arms, on an android device venue.

**Implementation status (2026-10-08): the owned-tree cores and their FFI surface are BUILT, so is the shared presence plan, so are the provider's read path, its write half and the toggle; the device run is not.** Built: `provider_face::owned_tree` (`libs/fauna-sync-engine`) — the two roots, hydrate-on-open, prepare-for-write, close → ingest → demote, create, record-first delete and rename, the start sweep, eviction observation and the three seam operations — tier-1 tested against a faked engine, surfaced additively on `FfiFileProviderHost` through a second capability constructor, `app_dead_owned_tree` (the host runs the start sweep itself once the set is populated; apple's `app_dead` surface is unchanged), and proven against a real nest in `conformance_file_provider_client.rs` (open-hydrates, a reclaimed body observed and never a delete, a closed write uploads, a killed writer's edit uploaded by the next host's sweep, a write closed offline uploaded by the sweep after reconnect, a conflicted close ending with the winner's bytes on the next open, a directory renamed and deleted file by file, an offline delete refused). A directory is deleted or renamed file by file inside `OwnedTree::delete` / `rename`, so the Kotlin provider walks nothing itself. The read path (BUILT 2026-09-28): `apps/fauna-android/.../provider/FaunaDocumentsProvider.kt` serves one root for the active account (none signed out) whose children are the plan's desired sets (default ON — before the toggle every folder this device holds an accepting place in that no watched-directory ingress feeds, and since 2026-10-01 every accepted folder shared with the account, a reader's advertising no write — [`on-demand-files-shared-sets.md`](on-demand-files-shared-sets.md) § *Shared sets on a capability host*, decision 3), ids `<ref-component>@<actor-id-hex>/<rel>`, rows from the host's `enumerate` / `item`, and opens for read through `open_for_read`; `FfiOnDemandSource` builds one `app_dead_owned_tree` host per set lazily from the account's secure storage, and the provider refreshes on the shared rescan cadence and on a browser re-query, notifying its cursors on a change; sign-out and switch drop the hosts, delete the account's cache root, keep the kept root and re-announce the roots. The write half (BUILT 2026-09-28): the flags above are advertised (no thumbnail); a write-mode open goes through `open_for_write` and hands out a descriptor whose close listener calls `closed_write` exactly once — an error close included, and a descriptor that fails to open is closed at once — on a background scope, so a write the nest does not record stays in the kept root; `createDocument` (SAF's `name (n).ext` collision rule), `deleteDocument`, `renameDocument` and `moveDocument` (within one set, through `rename_document`) go through the host and throw to the caller when it cannot record them; and every pull — the tick and the browser's re-query — re-drives the kept-root sweep after its refresh (the start sweep itself runs inside the host at build), so a write closed offline uploads at the next pull after reconnect. A close the host holds at its pre-seal edge (offline, no signer) still ends its writer (`OwnedTree::release_writer`), so the sweep can re-drive the body — a held close that kept its writer would have been skipped by every sweep. **The signer (BUILT 2026-09-29):** the host signs each record with the machine principal the shared account runtime enrolls at every sign-in — android's app already runs that ceremony — read out of the app's own principal slot by the host itself (`FfiOnDemandSource` passes `machine_change_signer`, the shared-Rust `SlotChangeSigner`; the android arm of [`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, *The capability host*), proven against a real nest in `conformance_file_provider_client.rs` (a host built over an empty slot holds no principal, so it reads no plane custody — decision 1′ below — and serves an empty tree for a nonce'd set, refusing a create and recording nothing; the ceremony enrolls the machine into the slot and the account's device set; with nothing handed to the host, its next refresh rebuilds over the custody it can now read, the set lists, and a write and a create record at once, signed by the slot's writer key and verified from the list's side table). On a machine the ceremony has not enrolled yet a closed write stays in the kept root, is never recorded unsigned, and uploads at the first sweep after it is; a create, delete, rename or move there is refused to the caller like any write that cannot be recorded — the pre-seal edge stops it before the tree, and nothing changes. The text stub it used to serve as a file's bytes and its enumeration of the ingress's Room rows are deleted, so `file-provider-host` now rides every android FFI flavor. Its proof today is the Kotlin translation layer headlessly (`FaunaDocumentsProviderTest`, Robolectric, a faked host: roots, children, id grammar, the real body on open, an unfetchable open failing with `FileNotFoundException`, a re-hydrate after the cache body is deleted; the advertised flags, one `closed_write` per written descriptor with the open's base on a clean and an error close, create with the collision rule, an empty directory and an ignored name refused, an unrecordable delete or rename refused with the document still listed, rename and move returning the new id, a re-query re-driving the sweep) beside the host's real-nest conformance test above; **the emulator instrumented test through a `ContentResolver` against a real nest is owed** — no android device venue runs on the dev machines yet. The build order is rust-first: the owned-tree cores and their FFI surface; the presence plan and preference store lifted out of Swift (BUILT 2026-09-28: `fauna_folders_machine::on_demand_presence`, the Swift pins ported as its tests; apple's coordinator runs on it, its Swift pins thinned to the wrapper); the android read path (the provider rewritten over the host, the stub and the Room enumeration deleted — BUILT 2026-09-28); the write half (BUILT 2026-09-28); then the toggle, its e2e arms and the guide. **The toggle (BUILT 2026-10-08; ui.yaml scope approved by the user 2026-09-30):** `folder-on-demand-toggle` ("Show in Files") renders on every owner row and on every row of a folder shared with the account (`FoldersScreen.kt`), reading and writing the shared preference store the plan reads, keyed by the row's actor-scoped identifier (`FfiOnDemandSource`, the page's `OnDemandToggle` seam); a flip re-plans and notifies the roots, so the set appears in or leaves the file browser at once. On an owner row ON is the enrol gesture — the shared `ensure_place`, before the re-plan, apple's order; a member's row is hide-only and writes no place (decision 3). A set a watched-directory ingress feeds shows the bound-location caption in place of the toggle — the stronger presence.
