## Goal

A user who wants "a feed of cats" creates a trained topic ("Cats"), marks a handful of posts *more like this* (and the occasional false positive *less like this*), and composes a feed dominated by that factor. The model trains instantly on-device at each tap (tier-1 self-servicing — no background job, no nest involvement beyond storing the sealed blob), syncs to her other devices through the nest as an opaque blob, and re-ranks her feed pages client-side. The nest never learns what "Cats" means, what the model contains, or which posts matched — it sees only an opaque `topic:<hex>` key inside her feed compositions (the same visibility class as the muted-keywords factor key).

## The model — a generalized Bernoulli n-gram Naive Bayes (v1)

The v1 trainable primitive is the **spam classifier's exact structure, generalized away from mail** (the frame Q2: "the exact tier-1 machinery as the spam model"):

- **Lift, don't copy (priority #2/#4).** `SpamModel` + the shared tokenizer (`libs/fauna-mail/src/spam/classifier.rs:93`, `libs/fauna-mail/src/tokenizer.rs`) move to a mail-independent shared crate, **`libs/fauna-text-model`**; `fauna-mail` re-exports them so the spam surface and its **serialized layout stay byte-identical** (the sealed spam-model blob at rest is a compat surface — the version-tagged serde_json field names must not change).
- **`TopicModel`** is that structure with topic semantics: per-n-gram `{more, less}` message counts, two document counters, the same NFKC/UAX#29 tokenizer and 1/2/3-gram windows, the same **reversible forward/inverse deltas** (`apply_forward_delta_ngrams`/`apply_inverse_delta_ngrams` — a training event is exactly undoable), the same count-based eviction (`cap_to_bytes`, self-cap `TOPIC_MODEL_MAX_BYTES = 256 KiB`).
- **Score:** `P(topic | text)` as integer per-mille `[0, 1000]`, `tier = TIER_USER` (the bus convention; dag-cbor forbids floats). Promote-vs-demote direction comes from the composition *weight*, not the score. Cold-model damping: `score = 500 + damp · (raw − 500)` with `damp = min(1, samples / TOPIC_FULL_CONFIDENCE_SAMPLES)` (constant `30`) — a constant 500 shifts every item equally, so an untrained model has **zero ordering effect** and the feed gracefully falls back to its other factors (the spam confidence-ramp idea, restated for sort).
- **Factor key:** `topic:<16-byte-random-hex>`, minted at factor creation — namespaced like `labeler:<hex>`, so it can never collide with bare built-in keys; the display name lives only in the sealed registry (§ Wire & registry), never on the nest.
- **Example markers, in-blob:** `examples: BTreeMap<content_id_hex, ExampleLabel{MoreLikeThis | LessLikeThis}>`, capped `TOPIC_EXAMPLE_MARKERS_MAX = 4096` (oldest evicted). Markers render the per-post toggle state across sessions, guard against double-training (spam's `DuplicateSignal` equivalent), and back a future "examples list" view. Markers are ids only — no deltas, no text.
- **Not an embedding model — deliberately.** The frame Q1 portfolio principle means a future embedding-based topic scorer is a *new factor kind added beside this one*, not a v2 of it. Today the workspace has no neural inference runtime, no client-side training path and no embedding infra; the Bernoulli NB is the only trainable shared-Rust primitive, it is proven for spam, and its per-event reversibility is what makes the toggle gesture honest. All model constants are hard-coded Rust (bucket 1 — no human chooses them).

## Training signals

**v1 — explicit examples only.** The per-post **"more like this" / "less like this"** gesture (mirroring spam's Mark-as-spam):

1. The client fetches the post's **full text** at gesture time (`fauna.posts.get`; decrypting a restricted body it is entitled to read) — the feed card's 500-char preview is too lossy to train on. Trained text = title + body + tags.
2. Tokenize → forward delta → increment the class counter → insert the example marker → re-seal → put (§ Wire). Tapping the *other* verb on an already-marked post applies the inverse of the old delta then the forward of the new; un-marking applies the inverse alone.
3. **Undo limitation (declared):** the inverse delta is recomputed from the content at undo time, so un-marking a post whose body is no longer fetchable removes the marker but leaves its statistical ghost in the counts — harmless in a personal statistical model. If this ever bites, the escalation path is spam's sealed-delta history mechanism (`mail-spam.md` § Undo), which v1 deliberately omits (topic training is single-position and toggle-shaped; spam's history exists for its multi-position audit trail).

**v2 — implicit engagement (ratified target, frame Q2; not in the first build).** A like (later: follow-weighted authorship, reply, save) trains a **weak positive** example into each trained factor whose `learn_from_engagement` flag is on (**default off**, per-factor, set in the registry); unlike applies the inverse where the body is still fetchable. **Implicit cues join the same v2 mechanism (frame D6/D9, 2026-07-12):** the derived per-item verdicts `watch-complete` (weak positive) / `skip` (weak negative) — vocabulary, derivation, and the sealed cue rollup owned by [`engagement-cues.md`](engagement-cues.md); this doc owns only the weighting shape they train through. No per-event markers (volume — the like itself is the nest-side record; `compute_toggle_event_id` semantics dedup the toggle). The frame's *explicit-signals-only-across-users* rule stands untouched: engagement feeds only the user's own sealed model, never any shared artifact.

**The weak-weighting shape — RATIFIED 2026-07-15 (decided at this v2 build): separate additive integer engagement counters, scaled at score time — *not* fractional-weight fold-in.** The `TopicModel` grows four additive, zero-defaulted fields, serialized `#[serde(default, skip_serializing_if = "<is-zero>")]` so a model that has never been engagement-trained (and every existing sealed blob) serializes **byte-for-byte as before** — the `golden_bytes_pin_at_rest_field_names` test is the guard, and this is what keeps a *published* factor able to strip the private half trivially (frame: engagement never leaves the user's own model):

- On `TopicNgramCount` (beside `more`/`less`): `more_engagement`, `less_engagement` — in how many distinct engagement-*positive* / engagement-*negative* documents the n-gram appeared.
- On `TopicModel` (beside `more_examples`/`less_examples`): `more_engagement_examples`, `less_engagement_examples` — the engagement document counters.

**Training** is transition-driven — the sealed **cue rollup** ([`engagement-cues.md`](engagement-cues.md) § At rest) owns per-item verdict state (capped 4096), so the model holds only the *aggregate* engagement counts and keeps **no** per-item engagement markers: `TopicModel::train_engagement(text, old: Option<ExampleLabel>, new: Option<ExampleLabel>)` applies the exact inverse of the old verdict's delta (where recomputable from `text`) then the forward of the new, on the `_engagement` counters only (mirroring the explicit `apply_forward`/`apply_inverse`). `watch-complete` maps to `MoreLikeThis`, `skip` to `LessLikeThis`; `old == new` is a no-op (a re-watch does not double-count — the last-wins rule). The `FeedManager` drives it from each observed verdict transition, for every composed factor with `learn_from_engagement` on, using the item's text **from the loaded feed window** (a `posts.get` per scrolled item is too costly — an item no longer in the window is skipped, the "text still fetchable" clause), then re-seals + puts the touched model.

**Scoring** folds the engagement counters in at score time at a hard-coded weak weight `CUE_ENGAGEMENT_WEIGHT_PM` (bucket-1 constant in `fauna_core::scoring::cues`, default 200 ‰ = 0.2 documents per engagement event): the Bernoulli posterior reads *effective* counts `explicit + engagement · weight` for both the document priors and each n-gram likelihood. **Invariant (test-guarded):** a model with zero engagement counts scores **bit-identically** to today (effective == explicit), so no existing user's feed shifts until they actually opt a factor into engagement. Integer counters keep the reversal on a verdict flip exact and the serialization deterministic; the fold-in arithmetic (f64 effective counts vs. integer-rounded) is an implementation choice bounded by this invariant, not an at-rest concern.

## Placement — where train / undo run

Per `../architecture/content-scoring.md` § Input classes (content + per-user secret → **the client, post-decrypt**): every mutation runs on the user's client. Unlike spam there is **no AUTH'd-MDA leg** (topic factors score posts, not mail) and **no server-side train path at all — the nest never holds a plaintext topic model at any point in the lifecycle**, and the model is sealed from birth, as spam's has been since its server-side writers retired (`mail-spam.md` § Implementation status item 4b). Cross-device sync is fetch-on-demand (a device fetches the sealed blob at session start / personalization-page open, puts after each train); a concurrent two-device train is last-put-wins losing at most one gesture, with the advisory `sample_count` available for an adopt-if-larger reconcile (the spam `ModelWriteOp::ModelSync` shape) if it proves needed.

## At rest — seal + home

- **Seal: the delegable unit for the reserved kind `fauna.personalization.model`** (`fauna_protocol::personalization::MODEL_SEAL_KIND`) — the pair `fauna_core::crypto::DelegableSchedule::derive(&backup_key).for_kind(MODEL_SEAL_KIND)` derives, the derivation the account plane's delegable kinds already use, rooted in the **BackupKey** (32 bytes, deterministically derived from the Ed25519 identity seed), so every device derives it (`fauna_client_personalization::model_seal_keys`). Pipeline: canonical bytes → zstd → `encrypt_kind_chunk` (ChaCha20-Poly1305 under the pair's entry key, AAD = form byte ∥ kind; `fauna_core::crypto`), the form `[0x02][nonce][ct+tag]` — the BackupKey chunk's layout under its own leading form byte (`KIND_CHUNK_FORM`), so an opener tells the two apart from the bytes alone. **Deliberate divergence from spam's MSEK-derived recipient seal:** the MSEK exists only when mail is enabled, and a personalization feature must work on a mail-less actor; the delegable schedule needs no MSEK. (Hybrid/PQ upgrade of the chunk AEAD is the post-quantum work's axis.) **Re-keyed for the third-party plane (ruled 2026-10-02; built 2026-10-05):** the seal moved off the bare BackupKey to that per-kind unit because the fifth Fauna-family arm `fauna:personalization:rw` ([`authorization-server.md`](authorization-server.md) § Scope grammar → *The planes ruled 2026-10-02*) needs a grant twin and a grant may never wrap the BackupKey (it also seals backups, drafts, library media and single-user folder chunks — [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Don't do these); the per-kind pair is then the ordinary `content.read` tuple, the one grant unit the plane has: a grantee rebuilds it (`AccountStateKindKeys::from_grant`) and opens the blobs through the same shared functions the owner's apps call. The move was an **in-place cutover**, not an expand→contract: it landed before the 2026-10 baseline, at which no installation and no blob survives ([`../architecture/compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md), the 2026-10-04 rulings), so the shared byte pipeline (`seal_model_bytes`/`unseal_model_bytes`, which the cue rollup rides too) writes and opens the new form only and refuses a BackupKey-form blob; the nest, which stores the blob opaque, changed nothing.
- **Home: a dedicated nest table** `personalization_models (actor_id BLOB, factor TEXT, sealed_blob BLOB, sample_count INTEGER, updated_at INTEGER, PRIMARY KEY (actor_id, factor))` — `spam_models` generalized by factor key, blob stored verbatim-opaque. **Not** inside account state (a plane entry's size cap and the registry's merge both fit a small preference record, not a growing model blob — the rule was first stated against the whole-record `UserConfig` and its 1 MiB cap, which retired with the `__config` rail), and **not** a `__<kind>` segment store (that pattern is append-only content; this is one mutable record per factor).
- **Caps (hard-coded):** sealed blob > `512 KiB` rejected at put; > `TRAINED_FACTORS_MAX = 32` factors per actor rejected at create (compositions already cap at 64 entries).
- **No re-score obligation:** a sealed factor writes no `content_scores` rows, so it stays out of `model_versions` / `builtin_factor_versions()` — the muted-keywords precedent, verbatim. Deleting the nest row is allowed UI-driven destruction of user-revocable data (the user's own delete affordance), never a migration.

## Wire & registry

- **Model wire (User-class, dag-cbor, additive-everywhere):**
  - `fauna.personalization.model.fetch { factor }` → `{ sealed_blob: Option<bytes>, sample_count, updated_at }`
  - `fauna.personalization.model.put { factor, sealed_blob, sample_count }` → ack (validates the `topic:` prefix, the blob cap, the per-actor factor cap)
  - `fauna.personalization.model.delete { factor }` → ack
- **Trained-factor registry — sealed, in account state:** the delegable `fauna.state.personalization` kind's value (the E1 preference cluster — [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The kinds*), `PersonalizationConfig { trained_factors: Vec<TrainedFactorMeta { id: [u8;16], name: String, learn_from_engagement: bool /* default false */, created_at }> }`, sealed + synced + offline-replicated by the account-state plane. Merge: whole-record latest-wins on `updated_at` (matching `moderation` — the registry is a recreatable preference; a concurrent two-device create can drop one registry row while its model blob survives, healed by re-adding the name). The **name never reaches the nest**; the nest sees only the opaque key inside compositions.
- **Delete semantics:** registry remove + `model.delete`; compositions still referencing the key stay valid — the zero-term seam makes an orphan key inert, and the feed-edit UI simply no longer offers it.

## Scoring — the client-side sealed-factor compose seam (feed)

The frame's sealed-factor rule (`../ui/feed.md` § The read model + § Frame reconciliation): a sealed tier-1 factor has no bus rows, its nest term is `COALESCE(…, 0) = 0` (pinned by `bins/fauna-nest/tests/composed_feed.rs`), and the client composes `final = FeedPostItem.score + Σ sealed contributions`. This doc owns that seam's mechanism, **for the feed surface**:

- **Home: shared Rust, inside `libs/fauna-feed::FeedManager`** — a sealed-compose step that runs when pages are appended: for each sealed factor in the feed's effective composition (own composition + the global factor set), compute its contribution and re-rank the **loaded window** by the adjusted key. App shells keep rendering snapshot order unchanged — `feed.md`'s "apps must not sort the post list themselves" is preserved because the *manager* owns the adjustment and the snapshot still supplies the visible order (reconciling edit landed in `feed.md` § Where logic lives).
- **The contribution formula, and the invariant that fixes it.** Three scales meet: a factor *value* is per-mille (`1000` = 1.0), a composition *weight* is per-mille (`1000` = 1.0×), and `FeedPostItem.score` is **micro-units** (the nest ships `(ordering_key · 1e6).round()`, `feed_handlers.rs::score_to_micro`). The nest's SQL term for a bus factor is `weight_permille · (content_scores.score / 1000.0)` (`db/feeds.rs::query_feed_scored`), so a sealed factor composed client-side contributes, **in micro-units**:

  ```text
  round( w · (v / 1000.0) · 1e6 )  ==  w · v · 1000      (exact, in integers)
  ```

  The governing invariant is **nest-equivalence**: a sealed factor contributes *exactly* what the nest would have contributed had it been able to read that factor's bus row — the seal is a privacy boundary, not a scoring change. Implementation + the test that pins it against an independent `f64` recomputation of the nest's term: `libs/fauna-feed/src/sealed_compose.rs` (`sealed_contribution_equals_the_nest_term_it_replaces`). *(An earlier revision of this section wrote the contribution as `weight_permille · factor_value / 1000`, which is 1e6× too small against a micro-unit base and would have made every sealed factor inert; corrected 2026-07-10 when S5 traced the units end-to-end.)*
- **Scored text (v1):** the item's preview body + tags already present in `PostSummary` — no extra fetch on the hot path (training uses full text; scoring 50 list items must stay cheap). A lazy full-body upgrade can follow the `resolve_media` pattern if preview-scoring proves too coarse.
- **Two sealed scorers ride the seam from day one:** `topic:*` models (this doc) and the **muted-keywords penalty** (`fauna_core::scoring::muted_keywords_penalty_entry`, the matching keyword's weight, default −1000; the feed seam is its first production caller, while its conversation collapse stays with the local-moderation-flags work). Sub-threshold items get the collapse-to-placeholder render treatment (the frame's ratified verb).
- **The muted-keywords penalty composes IMPLICITLY, at unit weight (1.0×)** — ratified 2026-07-11 with the seam. A user mutes *words*, never a composition entry, and the frame requires the penalty to apply globally ("a global muted keyword mutes it everywhere"), so the client adds the term to every score-ordered window whenever the muted list is non-empty, with **no nest-side global-factor row**. Two reasons it must be implicit rather than a stored entry: the factor is sealed, so its nest term is `0` regardless — a row would buy *nothing* functionally while telling the nest that this user mutes something (the scorer's whole contract is that "the nest never sees the list, the body match, or the resulting entry"); and a mute that depends on a row having been written is a mute that can silently be **missing** after a failed or unsynced write. Nothing to write means nothing to fail. An explicit entry, should one ever exist, takes precedence over the implicit weight (and two of them sum, exactly as the nest sums any doubly-listed factor).
- **A mute sinks only where there is an order to sink in; it collapses everywhere.** Sinking is an ordering effect and needs a base key, which exists only for a feed fetched `order=score`. A **chronological** feed — the local feed, or any feed with no composition — is deliberately **not** promoted to score order just because the user muted a word: that would silently re-sort their chronological timeline by engagement, a far larger change than they asked for. There the mute surfaces purely as the collapse-to-placeholder treatment (`FeedManager::is_muted`), which is client-side and universal. This is the honest reading of "mutes it everywhere": the *filter* is everywhere, the *re-ranking* is where ranking happens.
- **Page-boundary honesty (accepted limit):** the nest paginates on the transparent key, so sealed contributions re-rank only within the loaded window; exact cross-page ordering would require handing the factor to the nest, which the tier-1 seal forbids. A strong negative (mute) therefore sinks-and-collapses within the window rather than pre-filtering pages — the same privacy-over-exactness trade the conversation collapse already made.
- **The pages must at least *arrive*, which the sealed case makes non-obvious.** A feed dominated by a trained topic typically carries **only sealed factors** in its composition, so by the zero-term seam **every** nest-side key is 0 — a flat key. Scored pagination therefore has to be a **compound keyset cursor** over `(key, created_at)`, not the key alone, or such a feed dead-ends after its first page (and any feed with tied keys silently loses the tied posts). Owner of the cursor shape: [`../ui/feed.md`](../ui/feed.md) § The read model (`score_cursor` + `score_cursor_created_at`, landed 2026-07-11 as the first consumer of `order=score`). The seam depends on it: `rerank_loaded_window` can only reorder posts the nest actually delivered.

## Publishing a trained factor (tier-1 → tier-3; frame D8, ratified 2026-07-12 — built end-to-end on linux 2026-07-16; web/android/apple followed 2026-07-17; windows landed 2026-07-18)

A user may **voluntarily** share what a trained factor has learned ("I generally like small orange cats") as a subscribable tier-3 artifact. Publishing is always an explicit, reviewed act — a sealed tier-1 model never leaks by default, and `learn_from_engagement` training makes the published artifact a *derivative of private behavior*, which is exactly why the shapes below are gated the way they are:

- **v1 — publish as a List (the built artifact kind).** The client scores the user's loaded/known public-post corpus with the factor, presents the top-N exemplars for review (the user prunes anything they'd rather not endorse), and publishes the pruned `content_id → score` map via the existing `fauna.labelers.publish` as a `list` artifact. Nothing of the model crosses — subscribers see exactly the ids the publisher chose to show, the strongest inspect-before-subscribe of any kind. Zero new wire, zero new sandbox; the factor's display name is publisher-chosen at publish (the sealed registry name stays private). Limitation (accepted, stated in the UI copy): a List scores only content the publisher saw — it does not generalize to unseen posts.
- **v2 — the `text-model` artifact kind (privacy-scrub pass RATIFIED 2026-08-13 — pulled forward by explicit user direction, the demand gate's own condition; no organic "List proved too limited" signal had been recorded, stated for honesty). Build state: § Implementation status today** (which owns it — this bullet ratifies the *mechanism*, not what is built). Publishing a model generalizes to unseen content — the one thing a List cannot do — but raw n-gram counts leak training text, so the charter was the scrub. The ratified design strengthens the charter's field-stripping framing into a **rebuild, not a redaction**:
  - **The artifact is derived at publish time from the factor's *public, still-fetchable explicit examples* only — the private model state is never serialized outward, even scrubbed.** The client walks the factor's example markers, fetches each marked post (`fauna.posts.get`), drops everything restricted, deleted, or fetch-failed, re-tokenizes the same `model_text` training used, and builds a fresh `{more, less}` count table over that corpus. Four leak classes die **by construction** rather than by stripping diligence: example markers (ids never enter the artifact), engagement counts (the rebuild never reads them — the frame's "engagement never leaves the user's own model" holds structurally, so a `learn_from_engagement` factor publishes only what its explicit examples teach), restricted-content text (never fetched into the corpus), and the private model's statistical ghosts (residue of unfetchable posts never enters). The structural pin the build must carry: a model trained with engagement *and* restricted examples publishes **byte-identically** to its explicit-public-only twin.
  - **Minimum-count prune — `TEXT_MODEL_PUBLISH_MIN_DOCS = 3` (bucket-1 constant):** an n-gram survives only if it appears in ≥ 3 *distinct* included example posts, counting both classes together — the prune is an anti-quote privacy floor, not a signal filter, and class-blind counting is the privacy-relevant quantity. Nothing unique to one or two marked posts survives, which kills both single-document text reconstruction and single-post identification of the user's sealed judgment. The value matches the k-anonymity floor the spam-baseline aggregate already ships (a different axis — distinct documents of one publisher vs. distinct contributors — but the same judgment that below 3 an aggregate is a quote). A corpus of fewer than 3 public examples yields an empty vocabulary, and an empty vocabulary refuses to publish (the v1 empty-set refusal, with copy saying the factor needs more public examples). The floor is **structural, not merely publisher-side**: because the artifact's two per-class counts *are* the distinct-document counts, `validate_text_model_artifact` checks `more + less ≥ 3` — so the nest publish gate refuses a below-floor n-gram no matter which client built it. That guarantee covers the counts an artifact *asserts*, not the n-gram *shape*: at any version this build's tokenizer contract covers, the same gate also refuses an entry whose n-gram is not 1/2/3 non-empty tokens joined by single spaces — else an out-of-contract n-gram (e.g. a full sentence) could carry a passing count and still be pure disclosure, since it can never match a subscriber's tokenizer (§ Implementation status today, slice 1).
  - **Vocabulary bound — `TEXT_MODEL_PUBLISH_MAX_NGRAMS = 512` (bucket-1):** survivors ranked by the NB's own informativeness (|log-odds| under the scorer's smoothing; ties lexicographic, so the scrub is deterministic), truncated at 512. The cap is deliberately double-duty: it is the size bound *and* the review bound — unlike the List's `REVIEW_TOP_N` (which bounds endorsement of already-public ids), the vocabulary **is** the disclosure, so everything that crosses must be humanly reviewable, and the cap is what keeps "review the whole artifact" honest. `TEXT_MODEL_ARTIFACT_MAX_BYTES = 64 KiB` at the nest publish gate (beside the 1 MiB wasm cap) bounds the worst-case bytes.
  - **Review-before-publish:** the existing publish sheet gains a kind choice (List | Model). The Model review lists **every** surviving n-gram — text, class direction, distinct-doc count, default-checked include checkbox (the exemplar rows' prune semantics) — above the same blank-by-default public name input, plus a corpus-size line ("built from N public examples of your M marked posts"). Mandated copy, all three ratified (absence is a bug): the model generalizes to unseen content; it discloses word patterns shared by ≥ 3 of the publisher's marked public posts — *including* patterns from less-like-this examples, the dislike half being part of the disclosure the direction column makes visible; and publishing is pseudonymous and reflects explicit examples only, never activity.
  - **Artifact shape (dag-cbor, canonical, additive):** `TextModelArtifact { version: 1, name: Option<String> (the List's name rules verbatim), more_docs, less_docs, ngrams: [{ngram, more, less}] }` — entries strictly ascending by n-gram with no duplicates (equal artifacts have equal bytes, so the `wasm_hash` metadata binding is meaningful, exactly as for the List), each per-class count ≤ its class doc-counter, each entry non-zero in at least one class. `version` carries the tokenizer contract (NFKC/UAX#29, 1/2/3-grams): a subscriber meeting an unknown version treats the factor as **inert and says so** — never a silent mis-score. Validation (`validate_text_model_artifact`) lives beside the List's in `fauna_core::scoring`; the tokenizer-dependent scrub + subscriber scorer live in `fauna-text-model`.
  - **Identity and versioning:** the **same** per-factor derived keypair signs every publish of the factor regardless of kind — `artifact_kind` is per-version (the frame's additive axis), so a factor upgrades its published form List → Model as an ordinary version bump; subscribers keep their subscription and their client follows the kind it fetches. No new key-material surface. The nest-side consequence (List-row withdrawal on a kind change) is the frame's clause, not this doc's.
  - **Evaluation at the subscriber is client-side — the kind's contract is owned by [`../architecture/content-moderation-and-ranking.md`](../architecture/content-moderation-and-ranking.md) § Tier-3 artifact kinds** (placement forbids nest-side content evaluation; the MDA drain is mail-scoped; the subscriber's client is the one position where post plaintext meets the artifact). Mechanically it rides this doc's compose seam (§ Scoring): the artifact's counts feed the same Bernoulli posterior and the same cold-model damp (`TOPIC_FULL_CONFIDENCE_SAMPLES` over `more_docs + less_docs`, so a thin published model has bounded ordering effect), scored text is the same preview-body-plus-tags, the nest term is 0 by the zero-term seam, and page-boundary honesty applies verbatim. `content_kind: "post"` only at v1 — `mail` rejected at publish (the List's rule); an MDA-drain mail leg is a possible follow-on, deliberately not designed here.
  - **Accepted residual (stated, not hidden):** statistical membership inference — correlating the published vocabulary against a heavily-represented public post — remains partially possible above the prune floor. It is strictly weaker disclosure than the v1 List (which publishes chosen exemplar ids *exactly*), it is bounded by the full-vocabulary review, and it is the voluntary act's disclosed cost, carried by the mandated copy.
- Subscribe/compose/revoke are the unchanged tier-3 mechanics (frame § Tier-3); the published artifact is a fork-at-publish snapshot — later training never mutates it (re-publish is a new version).
- **The display name rides *inside* the List artifact** (`LabelerListArtifact.name`), not on the wire — which is what lets "zero new wire" and a publisher-chosen name both hold (ratified 2026-07-16 with the shared-Rust build). The signed `AlgorithmLabeler` carries no name, its shape is frozen, and its signature is checked by **re-encoding** the metadata, so a name field there would make every older nest reject every named labeler. Inside the artifact the name is instead bound for free by `wasm_hash`, which hashes the raw artifact bytes with no re-encode, and an older nest ignores the unknown field and materializes the entries as before. An unnamed list stays byte-identical to the pre-name shape. Consequence: the name reaches a subscriber at **inspect** (which returns the raw artifact), not on the metadata-only catalog browse.
- **Publishing is pseudonymous: each factor's artifact is signed by its own per-factor keypair, derived from the actor secret** (`blake3::derive_key` under a dated, domain-separated context, over `actor_secret ‖ factor_id`; the `BackupKey::derive` precedent) — **user-ratified 2026-07-16**. Forced by labeler identity being public-key-is-identity: the nest sets `labeler_id = algorithm_id = publisher_actor`, so signing with the user's own actor key would cap them at **one** published list forever *and* conflate labeler identity with actor identity. Deriving per factor yields many mutually unlinkable lists, needs no new persisted state, and makes re-publish re-derive the same key so the nest's monotonic version bump resolves (the client reads its current version off the catalog and publishes at +1). A published list therefore carries **no author attribution** — the publisher-chosen name is the only author-facing signal, and the sheet says so. Optional attribution (a signed author claim) is deliberately unbuilt, gated on observed demand like v2 below.

UI: a **Publish…** action on the Trained-topics facet rows. The name input **starts blank on every open**, never prefilled from the registry: the sealed name is private, and prefilling would leak the user's own label into a public artifact by default — the one thing the two-names split exists to prevent.
