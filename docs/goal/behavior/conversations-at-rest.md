## Encryption at rest

Fauna-native MLS conversations split across three at-rest representations, by operational role. Per-rail bridge conversations (SMTP / Bluesky / Nostr / ActivityPub) are carved out below.

- **Conversation message envelopes (sealed client-side, unconditionally; MLS-application-layer for every class but one).** Each application message **body** is sealed *client-side* by the **MLS application-message layer** — `MlsGroup::create_message` produces an opaque `ChannelEnvelope::Application(ciphertext)` (`libs/fauna-mls/src/engine.rs:851-869` `encrypt`, `:1804-1812` `encrypt_to_envelope` — citation refreshed 2026-07-23; 18 intervening commits since the 2026-07-03 original had shifted both functions) whose AEAD key comes from the **per-sender message ratchet** at that epoch (RFC 9420 § 9), opened only by `process_message` on a full group-member. This is **not** `derive_blob_key(epoch_secret)` — that BLAKE3-`derive_key("fauna.blob.v1", epoch_secret)` → ChaCha20-Poly1305 seal (`libs/fauna-mls::blob_crypto`) is used for conversation **attachments** (`engine.rs::seal_conversation_blob`), *not* the message body; the earlier claim that message bodies use `derive_blob_key` was a doc-vs-code error corrected 2026-07-03. The nest stores the resulting envelope bytes opaque in the per-channel `__conv/<channel_id_hex>` segment store, ordered by a per-channel monotonic `seq` mirrored in `segment_records` (`bins/fauna-nest/src/segments/conv.rs::append`; mechanism + scope in [`../architecture/message-segment-store.md`](../architecture/message-segment-store.md) § Layout / § `segment_records` SQLite mirror). **The nest never holds the opening key; no live nest path calls into the MLS decode, and none is planned** — every nest keeps the sealed envelope, because conversations have no read-requiring server-side purpose (Fauna apps decrypt them; conversation FTS is a *client* capability) and the nest cannot open an MLS application message without a full member view anyway (it holds no identity signing key — rule #7 / MLS-2). **The declared exception, and the only one (BUILT 2026-09-09): a community room's own home nest** ([`../behavior/community-rooms.md`](../behavior/community-rooms.md) § The three classes → *Community*, which owns the rule). Both halves of the sentence above survive it literally rather than by exemption: that envelope is a third `ChannelEnvelope` variant sealed under the **room's generation key**, not by the MLS application layer, so no nest path calls into the MLS decode and no nest holds an MLS opening key — and the nest's key is not one it minted or was configured with but a wrap the room's members made to its `room_read_pubkey` and can rotate out, which deletes the derived views in the same act. The invariant that actually moves is narrower than "the nest cannot read": it is that **whether a nest reads is the members' standing choice, visible on the roster**. Every other class, and every room this nest merely relays for, is unchanged. See [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Readable classes (the read-position purpose test, formerly named "the plaintext-at-rest purpose test") + the Conversation-messages conformance row, and the internally-tracked design (2026-07-03) Phase 3 case ii (retired; client-push is the mechanism *if* a purpose ever emerges). Per-message MLS framing (sender's KeyPackageRef, the per-message `epoch`, `generation`, `content_type` fields openMLS embeds) lives *inside* the sealed envelope. Sender identity is **not** stored alongside the segment record by construction — the segment store carries only the opaque envelope + the per-channel `seq` + `received_at` floor; `(sender, recipient)` lives only in the anti-spam `sender_behavior` table (see the anti-spam carve-out below).

- **Attachment reachability (plaintext floor — ratified 2026-09-08, BUILT 2026-09-09).** A conversation attachment is a separate blob: sealed client-side — on the end-to-end class under the channel's `derive_blob_key(epoch_secret)` (`engine.rs::seal_conversation_blob`); on the community class under the room's attachment content kind off the message's generation ([`../behavior/community-rooms.md`](../behavior/community-rooms.md) § The three classes → *Community* → *Attachments — the second content kind*, which owns that key and the home nest's relation to the bytes) — uploaded through `POST /api/v1/blob` (`ConversationsRpc::blob_put`, sidecar class `Conversation`), and named only by the `ChannelAttachment::sealed_cid` inside the sealed application message above. The nest's blob GC deletes every blob no live record names ([`../behavior/backup-restore.md`](../behavior/backup-restore.md) § 9 step 2), and it cannot read the message — so until 2026-09-09 every conversation attachment was swept ~30 minutes after upload and 404ed forever for every member (found 2026-09-08 while closing the identical finding for posts). **The ruling:** the sender lists the sealed blobs' content addresses in plaintext beside the envelope — `ChannelSendRequest::attachment_refs` (and `channel.send_remote` → `fauna.federation.channel.append` for a foreign-homed channel) — filled by `FaunaMlsBackend::encode_body` from the very cids it just uploaded, one shared-Rust writer for all 7 apps; the nest records them beside the record's mirror row (`conv_attachment_refs`, written in the same transaction by `segments::conv::append_with_refs`) and pins them for as long as the record is live. This is the floor addition the Posts row made for `GatedInfo.attachment_refs`, one kind over, and it reveals the same class of thing: that a record carries attachments, how many, and which already-stored blobs it links — never the sender (the record still records none), never the bytes, MIME, filenames or captions; the nest never serves or relays the list. **Reclaim follows the record, not a delete leg:** a reference pins nothing once its `(channel, seq)` has no live `segment_records` row — a paired nest's relay-ack purge, or compaction — so the bytes reclaim with the record after grace. A cooperative `dm-message-delete-button` `Delete` is a sealed message and never a store tombstone, so it keeps the attachment bytes exactly as it keeps the envelope (§ Reactions & message delete → *At rest*); there is deliberately no reclaim on delete, because delete-for-everyone is cooperative and No-user-data-loss already keeps the envelope. Weighed and rejected: an upload-side reference the sender records against a reserved rail (the device-sync wire refuses reserved sets by design — [`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § Drafts Sync — and release-on-delete would need a second floor addition), and pinning every blob of every channel member (unbounded, and `blob_metadata` records no uploader). Additive both ways (`skip_serializing_if` empty; a pre-field nest drops the list into `extra`), so a pre-field app's attachment messages stay unpinned exactly as before — status quo, not a regression. Pinned by `gc_keeps_a_live_conversation_attachment_and_still_reclaims_orphans` + `gc_reclaims_a_conversation_attachment_once_its_record_is_tombstoned` (`backup/gc.rs`), `append_with_refs_records_them_beside_the_mirror_row_and_a_replay_keeps_them` (`segments/conv.rs`), `attachment_round_trips_outbound_to_inbound_faunamls` (the shared-Rust send lists the cid it uploaded) and the tier_3 `test_real_faunamls_conversation_attachment_survives_a_blob_gc_sweep` (web/linux/tui, one body) with its `test_windows_`/`test_macos_`/`test_ios_` launch-gated twins. **Where the bytes rest is the room's home nest — for a foreign-homed channel too (ratified + BUILT 2026-09-09, closing the first of this paragraph's two residuals):** [`../behavior/conversation-rooms.md`](../behavior/conversation-rooms.md) § The home nest → *Attachment bytes* owns the residency and the two cross-nest byte legs (a write token relayed from the home nest for a direct `POST /api/v1/blob`; a direct public `GET` by content address), so the pin above works unchanged — refs and bytes on one nest. Until then `blob_put`/`blob_get` read the member's *own* nest whatever the channel's home, so a cross-nest attachment was pinned nowhere and fetchable by nobody. **The last residual closed the same day:** a legal-takedown withhold blanked the record's body while its sealed attachment stayed fetchable by hash — the blob-serve door now consults the flag, over the very refs this ruling added, and answers 451 while every live record naming the blob is withheld ([`../behavior/moderation.md`](../behavior/moderation.md) § Legal takedown, which owns that rule).

- **MLS-channel routing roster (plaintext floor).** `actor_channels(actor_id, channel_id, created_at)` on the nest (primary key `(actor_id, channel_id)`, indexed on `actor_id`; `bins/fauna-nest/src/db/migrations.rs` `MIGRATIONS_ACTOR_CHANNELS`). The nest reads it on every fan-out (`db/channels.rs::list_channel_actors`, consumed by the `fauna.conversations.channel.send` handler in `conversations_handlers.rs` — the WS-RPC surface that replaced the deleted `channel_routes.rs`) and on every per-actor sync (`list_actor_channels` → `segments::conv::read_for_scopes_after_seq`, the `mls_pull` read path that replaced the removed `get_channel_messages_for_actor` db method at the Plan 7 reads cutover). Auto-populated on first channel post by a member (the channel-send handler's idempotent `INSERT OR IGNORE`) and on Welcome delivery for the recipient (the `welcome.deliver` handler). This is the floor's *authoritative routing-state representation* — not a derived mirror of a sealed source — same pattern as the relationship-state subset of the
  [`../ui/contacts.md`](../ui/contacts.md)
  Contacts row: the nest must be able to mutate this without holding any MLS key, because fan-out happens on every channel post regardless of which clients are online.

- **MLS-cryptographic group state (owner-only Fauna-app audience — Path A).** The ratchet tree, member leaf indices, the per-epoch key schedule, group secrets, current `epoch_secret`, and recent past `epoch_secret`s for grace decrypt — all belong to the owner-only **Fauna-app** audience: held in each member's MLS read-side state on their own clients, reached from the identity seed (Path A in
  [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md)
  § Roots → MLS group state). **Not** sealed under MSEK, **not** reachable from a MUA (IMAP/CalDAV) credential, and **not** held on the MDA bridge — per that doc's rule #7 (blast-radius invariant): a leaked IMAP/CalDAV credential reaches mail + calendar only, never conversations. The MSEK-sealed `MlsSnapshotBlob` of Path B carries only the user's mail/calendar read material, not this group/epoch state. Opaque on the nest; unsealed only on the user's primary clients. The nest holds no opening key — this material never rests in the open on any nest. (At-rest persistence + cross-device sync of this state ride the owner's identity-seed-path key — the `BackupKey`-class Path A audience, not MSEK. **Mechanism (design ratified 2026-07-05): a state-replica synced under `BackupKey` through the `__mls` reserved folder via `fauna.mls.{get,put}`, mirroring Drafts Sync** — two sealed path families: `provider` (the openMLS provider snapshot, `libs/fauna-mls/src/engine.rs::export_provider_storage`/`restore_from_provider_storage`) and `history/<channel_hex>` (the per-channel thread-store slice **including own message plaintext** + the ingest watermark — required because a sender cannot MLS-decrypt its own application messages, so log replay alone cannot rebuild own history on a second device). Multi-device write safety = the device-owned-epoch invariant + commit CAS/rebase; protocol-shape authority: [`../behavior/devices.md`](../behavior/devices.md) § Cross-device MLS group-state sync; at-rest/reserved-set shape: [`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § MLS state replica; design ratified 2026-07-05 (tracked internally). **Build state is owned by [`../behavior/devices.md`](../behavior/devices.md) § Implementation status today** — read its `Cross-device MLS group-state sync` bullets for what is wired, leg by leg. The multi-leaf re-invitation alternative (`recovery.rs::prepare_reinvitations`) was deleted 2026-07-12 — superseded, and a Rule-1 hazard; see [`../behavior/devices.md`](../behavior/devices.md) § Implementation status today. A retired earlier design (Phase 3 case ii) once proposed a plaintext-nest path that would have ridden this same foundation; superseded, per the corrected § Conversation message envelopes bullet above.) MLS membership-change commits (Add / Remove / Update / Commit proposals) flow as opaque `ChannelEnvelope::Commit` MLS messages on the same channel as application messages — MLS-layer-sealed and, at the segment-store level, byte-indistinguishable opaque bytes to the nest (**not** `derive_blob_key`-sealed); the corresponding routing-roster mutation is a parallel nest-side write the client drives, like contacts.

**Receiving into the conversations view (per-rail).** Inbound for every rail reaches the UI the same way: a per-rail source decrypts a message client-side and hands the plaintext to `ConversationsManager::ingest_inbound` (`libs/fauna-conversations`). The *source* differs by whether the rail is backed up on nest:

- **Nest-backed kinds — fauna-native MLS (`conv`) and mail (`mail`).** Both rest sealed in the nest's per-channel/per-actor segment store (the backup-of-record; the nest holds no opening key). The client reads them with a **message-kind read feed** — `fauna.conversations.channel.fetch` for `conv`, and for `mail` **both** `fauna.email.inbox.fetch` (received) **and** `fauna.email.sent.fetch` (the actor's own `Sent` mailbox, so mail sent from another MUA/device surfaces as an outbound message) (`../behavior/mail-app-surface.md` § Inbound client receive) — and decrypts each sealed record locally (`open_mail_record` for mail; `decrypt_blob` for conv). The same sealed records restore on a new device (`fauna.filesync.snapshot.restore_message_kind`). **What is backed up on nest is exactly what flows through a nest read feed.** **Ownership (`MessageSnapshot.is_own`) for mail is derived from which mailbox served the record, never the `From:` header** — the nest only ever files a record into `Sent` via a submission this account authenticated, so `Sent` is proof of authorship and `INBOX` never is, regardless of what `From:` claims (`SmtpBackend::bucket_inbound`); a same-Message-ID `Sent` copy of a message already held from `INBOX` (the self-addressed-mail case) *upgrades* the held copy to own rather than being deduped away silently (`ConversationsManager::ingest_inbound_identified`) — **when the Sent copy parses to the same message as the held one in every field the parse fills: sender, recipients (`To:`), subject, reply reference (`In-Reply-To:`), body text, body format (plain text, or HTML converted to markdown), and each attachment block — its content handle, filename, type and size, in order** (`ThreadStore::mark_message_own`). Headers the parse never reads may differ, the bridge's `Received:` stamp on the `INBOX` copy among them, so both copies of an honest self-send still match. Of the compared fields, the sender, body and attachments render on the message itself; the subject renders as the message's subject divider when it changes its thread's subject, or as the label of a thread the message starts; the recipients render only as the participants of a thread the message starts; the reply reference never renders, but routes the message into its parent's thread. **A Message-ID collision is settled by one rule (ratified 2026-09-15): a device holds one message per Message-ID, and when a `Sent` copy of it is in hand, the `Sent` copy is that message — content, ownership and delivery time.** So a matching held copy upgrades in place — it keeps its position in its thread but shows the `Sent` copy's delivery timestamp, and its thread's activity time follows (never the `INBOX` copy's time: whoever delivers a later identical copy would otherwise set when the account's own message shows) — while a held copy that *differs* from the `Sent` copy in any compared field is a squat on the account's Message-ID, never merged and never upgraded: the `Sent` copy **displaces** it (`ThreadStore::evict_message`, then the ordinary ingest), so the squat leaves its thread — and the thread leaves the view when that empties it and nothing else is bound to it — and the account's genuine message threads by its own participants, subject and reply reference, own, with its own content and time. The reverse order needs no rule: an `INBOX` record never displaces a held copy, so a squat arriving after the `Sent` copy is dropped by the dedup like any duplicate. Either way the device ends up showing the `Sent` copy and never the squat: a forged `INBOX` record that reuses a genuine Sent Message-ID therefore never inherits ownership of content this account didn't send, and never hides the message the account did send — the `Sent` copy reloading on every replaying device is the durability promise of `../behavior/mail-app-surface.md` § Inbound client receive. The per-user content index follows the displacement too, as of 2026-09-16: its re-index guard keys on the nest record id beside the content id, so the `Sent` copy re-stages and the segment holding the squat's text is rewritten — the index's own mechanism, ruled in `../behavior/content-index-ingest.md` § Ingest triggers, v1 and `../behavior/content-index.md` § Where the index is built.
- **A mail record whose header carries other than exactly one `From:` field renders like any other — no flag, and the sealed corpus is not rewritten.** Its displayed sender is `parse_message`'s, which is `mail-parser`'s choice: the **last** From field, the same one `sender_domain` indexes. New ones stop arriving — the SMTP inbound and sending doors refuse them (`../behavior/smtp-server.md` § Architectural rules → *Exactly one From field*) — so what remains is inbound mail delivered before that refusal landed and mail the account filed itself through IMAP APPEND, which does not refuse. That set never grows from outside, so a per-message warning would add a new cross-app surface for a closed legacy set.
- **Federation rails — Bluesky / ActivityPub.** Sourced **client-direct** from their networks (credentials on the synced account-state plane, which replaced the `__config` blob retired 2026-10-02 — [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The kinds*), **not** stored or backed up on nest. There is no nest read feed for them; their history lives in the source network and is re-fetched. A future producer that re-seals federation messages into a nest message-kind store *could* join the read-feed model, but that is out of scope today (the carve-out above stands).
- **Nostr — nest-backed, NOT client-direct (reclassified 2026-06-08; wire shape ratified 2026-06-13 by the nostr-dm-rail track).** This bullet originally lumped Nostr with Bluesky/Mastodon as "client-direct," but that classification (2026-05-25) **predates** the user-ratified **posture-2 Nostr decision** (2026-06-08; [`../ui/nostr.md`](../ui/nostr.md) § Architecture): the nest is the **custodial Nostr signer** — it holds the user's deposited `nsec` encrypted-at-rest, unwraps NIP-17/44 DMs server-side in flight, and stores the body sealed to the owner's MSEK-derived key (the steady-state key home is the nest or a NIP-46 bunker, **not** per-app — `nostr.md` § Persistence; gate + at-rest contract `nostr.md` § The bridging gate). A custodial-nsec rail is therefore **nest-mediated**, so the steady-state client cannot re-fetch+decrypt DMs from relays with a key it does not hold. Nostr DMs are consumed over a **nest read-feed / WS-RPC kind** — exactly the "future producer re-seals into a nest message-kind store" path named above for Bluesky/Mastodon, except for Nostr it is in scope. **Ratified wire shape (the nostr-dm-rail track, 2026-06-13):** three User-class, caller-scoped Nostr DM kinds (`list` / `messages` / `send`; the nest-backed-feed family, `fauna.` prefix like `fauna.conversations.*` / `fauna.email.*` — **not** the prefix-less `nostr.<area>.<verb>` form reserved for the step-4 protocol-content kinds). The `/api/v1/nostr/dms/*` HTTP rip (the ws-rpc-everywhere track's step 3, tracked internally) landed with the kind. **Since 2026-10-03 a Nostr DM thread is a bridged room, read and sent through `fauna.bridges.conversation.*`** — the three kinds and the per-rail `NostrBackend` designed to consume them are deleted. See [`../ui/nostr.md`](../ui/nostr.md) § Implementation status today → DMs.

This is why the receive mechanism generalizes over **message-kinds** (the nest-backed storage concept), not over rails: adding a future fauna-native message-kind reuses the same read-feed shape; adding a federation rail stays client-direct.

**Community rooms (superseded "community / user groups" framing corrected 2026-09-08).** A community room — a room whose member set includes its home nest — is owned by [`../behavior/community-rooms.md`](../behavior/community-rooms.md) § The three classes → *Community*: its log rests in the same `conv` scope as an end-to-end room's, sealed under the recipient-set scheme with the home nest as one wrap recipient, so the fauna-native bullets above cover it too — what differs is only which key the reader holds. Its floor roster and owner-signed policy (name, roles, join rule, history policy) are plaintext-floor on the home nest by design (moderation, search and unbounded fan-out need them), the same footing as the routing roster above. The `groups` + `group_members` tables were the dormant group plane's ([`../behavior/groups.md`](../behavior/groups.md)), retired 2026-09-26 under [`../behavior/conversation-rooms.md`](../behavior/conversation-rooms.md) § The group plane's fate; `tier_mls_groups` was a subscriptions-plane table, unrelated to rooms, retired with the tier-MLS plane (schema 91 —
[`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md)
§ Per-content-kind conformance). The earlier reading of those three tables as one separate "community/user groups" concept is superseded.

**Anti-spam metadata carve-out.** Every channel post records a behavioral event `(sender_actor_id, target_actor_id, "dm_sent", micros)` (the channel-send handler in `conversations_handlers.rs` → `db/sender_behavior.rs`) where the target is resolved by `list_channel_actors(channel_id)` filtered against the sender — recorded with a `target_actor` only when exactly one other member is on the roster; a group-forked thread and a not-yet-seated recipient both record a target-less event instead (scope + rationale: [`../behavior/direct-messages.md`](../behavior/direct-messages.md) § Anti-Spam, which owns this behavior). When the anomaly scorer triggers (score ≥ 0.3), a `spam/behavioral` content label is applied to the channel (same handler). Both are plaintext — the scorer must compute social-graph distance + fanout rate on every send, so sealing the `(sender, recipient)` pair would defeat the anti-spam point. This is a known floor item, analogous to envelope-FROM SPF audit on the mail side; the corresponding plaintext-floor-tightening (hashing / removing the resolved `target_actor` on `sender_behavior` events) is parallel to the mail-side "hash envelope FROM on inbound" tightening listed in
[`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md)
§ Carve-outs and known plaintext-floor items to tighten.

**MLS Welcome at-rest.** Welcome bytes delivered at channel bootstrap (over `fauna.conversations.welcome.deliver`; cross-nest via the `fauna.federation.*` legs — the HTTP welcome route is deleted) are HPKE-sealed by the sender to the recipient's MLS init_key — the seal is inherent in MLS Welcome, not added by this row's at-rest layer. The nest stores the Welcome opaque in the recipient's inbox via `push_inbox` and pushes it over WS for the recipient client to process. Welcomes do **not** live in the `__conv` segment store (which holds only application/Commit channel envelopes); they live in the recipient's inbox-item store with the floor's per-inbox-item metadata (recipient routing, timestamp, sealed bytes).
