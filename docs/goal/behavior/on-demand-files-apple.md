#### Apple File Provider binding (ratified 2026-07-18 — design record tracked internally; M0 packaging skeleton built 2026-07-18, engine-backed binding M1–M5)

macOS and iOS realize the on-demand surface as **one shared `NSFileProviderReplicatedExtension`** serving a **Fauna location** in the Finder sidebar and the Files app — **one File Provider domain per folder this device accepts** (domain identifier = the set's **actor-scoped** `FolderRef`, `<ref-component>@<actor-id-hex>` — `local%3A1@…`, the callback-routing identity named above, scoped to the account since 2026-09-25 and its ref half percent-encoded since 2026-09-29 (*the actor-scoped device identity*, below); the set name is only the display name — the `fauna.sync.changed` nudge, which carries the set's own name or its name hash, is matched to a held set through the shared rule (`sync_changed_names_set`, against `PresenceSet.set_name`) and signals that set's domain by its identifier, never by the display name, which for a shared set carries its owner), each domain backed by a `folder`-scoped engine over the same shared `EngineHost` driver. The OS supplies placeholders, hydrate-on-open, *Download Now* / *Remove Download*, badges, and progress natively. Nine binding-specific rules:

- **Control inversion — the replicated FP calls the provider; there is no watcher and no disk scan on this surface.** The OS owns the on-disk tree (under the system-managed `~/Library/CloudStorage/` location) and calls the extension: enumerations serve the engine's row fold (the same batch-latest-per-path fold placeholder population uses; item `contentVersion` = `recorded_content_hash`), `fetchContents` = `download_file_bytes` + `mark_hydrated`, local user changes arrive as `createItem`/`modifyItem`/`deleteItem` and drive the **sealed per-file ingest** (the photo-ingress path) + `changes.record` / tombstone, observed eviction drives `mark_placeholder`, and a pulled remote change signals the enumerator. The placeholder-vs-absent and never-read-a-placeholder hazards structurally cannot arise here.
- **The recorded-head gate manifests as the upload ack.** The extension acknowledges a local change to the OS **only on `UploadOutcome::recorded`**; the OS never discards a local copy whose upload is un-acked. Same key (`recorded_content_hash`), same invariant as `is_dehydration_safe` — an un-recorded edit is un-evictable by construction.
- **The extension hosts the engines.** `fileproviderd` launches it with the app dead and iOS has no daemons, so the extension runs the per-set engines in-process via FaunaFFI, with state (`fsid-<ref>.db`, shared `device.db`) in the app group container — **state unification (ratified 2026-07-19; re-ratified per CONSENT DOMAIN 2026-08-25): ONE apple state dir per consent domain, `<domain root>/sync/<actor-id-hex>` (per-actor since the Multi-account consequence-3 landing below), and each set's engine state lives in its HOST's domain root.** iOS has one domain (the sandboxed app and its extension share the app-group container). macOS has **two**, because macOS 15+ puts `~/Library/Group Containers` under `kTCCServiceSystemPolicyAppData` and a launchd-spawned background process is prompted there on every instance with no user decision ever binding the next one (measured: `../architecture/installers/macos.md` § Identifier domain, record item 5): the **user domain** (`~/Library/Application Support/Fauna/sync` — the platform state base of `../architecture/account-data-plane.md` § The account store, the root of the external `fauna-sync-agent`, fauna-tui, and the unsandboxed app) and the **container domain** (`<app-group>/sync` — the root of the sandboxed File Provider extension, which can reach nothing else). The rule that makes two roots one law: **a process never opens a root outside its own domain** (the agent never touches the container; the extension cannot touch the user domain), and **no set's state is ever needed across the two** — the one-local-presence arbitration below gives every set exactly one local host, and a host switch (FP domain ↔ bound folder) re-derives the replica from the nest for a *different* local root rather than carrying the old `fsid-<ref>.db` (the FP domain's replica paths mean nothing to a bound folder, and vice versa); `device.db` is not a coupling point either, since on macOS both hosts take the device id from their provisioned credentials. The one process that spans both domains is the unsandboxed **app**, which is the container's *steward*: it writes `domain-owners.json` and the extension's pin replica there and reads the FP-bound sets' `file_states` there, while everything of its own — its one-shot engine host (restore and state reads on macOS; the photo set's ingest on iOS, where the container is the app's only domain), its `location-map.json`, its deployment-seed `config-replica` — and its reads of the agent-hosted sets' `file_states` (or `GetFileStatus` over IPC) live in its own domain, the user domain. A Media-badge fold spans both roots (**built 2026-08-25**: `SyncStatesStore` routes each set by the registered FP domains — a set with a domain is read from the container, every other set from the host's root — and the shared read `sync_file_states` is pure, never minting an `fsid-<ref>.db` for a set the device hosts nowhere; `SyncStateDir.Domain` is the Swift home of the two roots, the user-domain base taken from shared Rust's `platform_state_base()`). Pre-unification state is adopted **copy-never-destroy** via the shared `migrate_state_dir` (SQLite-backup snapshots, first-writer-wins, sources never touched — each process adopts the legacy dirs its domain can reach; the 2026-07-19..2026-08-25 container-resident *agent* state reached no user machine — no signed artifact shipped it — and is left untouched on the dev boxes that hold it). One writer per set = the hosting process (guaranteed by the one-local-presence arbitration below); the app reads `file_states` cross-process for Media badges (WAL + busy-timeout make the cross-process reads safe). It is exactly the out-of-app hydration host of *Who runs the hydration host* above: provisioned `BackupKey` + a renewable bearer via the shared app-group Keychain, never the identity seed; a shared set's content keys are not provisioned beside them — the host loads them from custody itself ([`on-demand-files-shared-sets.md`](on-demand-files-shared-sets.md) § *Shared sets on a capability host*, decision 1). The OS is the multiplexer on this surface: `fileproviderd` instantiates one extension object per domain, so the extension holds one independent `FfiFileProviderHost` (engine + current-thread runtime + bearer connection) per domain — the shared `EngineHost` driver is deliberately not used here, since it exists to drive self-driving loops and a control-inverted host has none (carve-out recorded in [`on-demand-files.md`](on-demand-files.md) § *Hosting multiple on-demand folders*). N such folders ⇒ N per-domain hosts in the one extension process, matching the windows N-engines-per-service resource shape (per-set engine + per-set connection).
- **Apple's on-demand is set-level, not location-level (platform fact, sanctioned deviation from the windows folder-mode shape).** An FP domain cannot take over an arbitrary user directory, so per set per device there is exactly **one local presence**: none (RemoteOnly), a bound always-resident location (the location map, unchanged), or the Finder/Files domain — never two (two engines writing one set from one device id would fight). The UI affordance is the per-set `folder-on-demand-toggle` (`ui/folders.md` § Binding), not `folder-location-mode-toggle`. **Arbitration precedence (ratified 2026-07-19): a bound location outranks the on-demand toggle.** The binding is an explicit user act with a chosen on-disk location, the toggle is the ambient zero-config default — so a bound set never gets an FP domain (the domain yields *before* the binding's resident engine starts), and unbinding lets the toggle decide again (the domain reappears, default ON). Enforced in the shared `FileProviderCoordinator.reconcile` (`desiredDomains` = own folders this device accepts in ∩ toggle-enabled ∖ bound — the next bullet's rule) — the decision itself now has its shared-Rust home, `fauna_folders_machine::on_demand_presence` ([`on-demand-files-android.md`](on-demand-files-android.md) § Android SAF DocumentsProvider binding), which the coordinator migrates onto; iOS has no binding surface, so there the rule reduces to FP-domain-or-RemoteOnly.
- **Auto-appear default-ON (user decision 2026-07-18) — for every folder this device holds an ACCEPTING place in (the mode-free rule, ruled 2026-09-28 in the folders mode contraction design pass; the shared plan built 2026-09-28 — `PresenceSet.this_device_accepts` replaced its mode input — apple feeds it this device's place since 2026-09-29 — read since 2026-10-03 inside the shared lister (`FfiFoldersClient::presence_sets`), each owner row's `accepts` through the shared seat rule `fauna_protocol::folders::SeatRead::delivers_presence` — a failed roster read skipping the reconcile rather than removing domains; android's SAF plan reads each row's `accepts` the same way since 2026-09-29).** A folder has no type ([`folders.md`](folders.md) § Target re-model); what a device does with one is its **place**, and a File Provider domain is a *delivery seat* — it pulls the head and hydrates on open — so the presence plan — the shared `fauna_folders_machine::on_demand_presence::desired_presences`, which apple's coordinator runs on and android consumes ([`on-demand-files-android.md`](on-demand-files-android.md) § Android SAF DocumentsProvider binding) — keys on THIS device's place, the re-key landing once in that shared function: **desired = folders where this device's place has `accepts: true` ∩ toggle-enabled ∖ sets this device presents another way** (a bound location; an ingress such as the photo library). A folder where this device holds no place gets no domain — the wizard's unchecked device box means what it says, which the retired mode-keyed plan silently overrode (a domain appeared for every own sync-type set, member or not); the toggle is still *offered* on such a row, and turning it on is the **enrol gesture**: it writes this device's place at the default point (`{originates, accepts, applies_deletes}` all true) through `fauna.folders.places.set`, after which the domain follows ([`file-sync.md`](file-sync.md) § 4, *A local presence writes the place it needs*). A place with `accepts: false` gets no domain either — delivery is switched off for that seat ([`file-sync.md`](file-sync.md) § 4), so a domain would show a tree that never updates. The toggle hides the domain per set per device, as before. A folder shared with the account joins the same plan — readers read-only, writers read-write, a cross-nest set included — by [`on-demand-files-shared-sets.md`](on-demand-files-shared-sets.md) § *Shared sets on a capability host*, decision 3 (the user's answer 2026-09-30; built in the shared plan and on android 2026-10-01, on apple 2026-10-03).
- **Multi-account × File Provider (ratified 2026-07-19): the FP surface is serialized single-account — the active account only.** The account model everywhere is a serialized switcher (one active identity per running client; switch = teardown + relaunch — owned by `../architecture/long-term-store.md` § Multi-account evolution), and every out-of-app sync host already follows it: the external sync agent is unprovisioned on **every** session-teardown path and re-provisioned by the incoming session's launch. ⚠ **Read "is unprovisioned" as *is asked to unprovision, and made to reconcile if the asking fails*.** The teardown is enforced by exactly **one best-effort local RPC per teardown path**, and what it revokes is built to outlive it — the capability persists in the secure store, the bearer self-renews app-dead off a renewal grant that deliberately carries **no expiry**, and both resume across reboots. So a lost message (a *wedged*, not dead, agent at the teardown instant; a connect timeout under load) leaves the signed-out account's engines serving. That case is no longer unbounded: the app records the sign-out durably **before** sending the message, and the agent revokes itself against that record — `../architecture/apps/sync-agent-credentials.md` § Credential model → *The signed-out reconcile* owns the mechanism, its ordering rule, and its limits. The File Provider surface follows the same shape, not a per-account one: per-set domains exist for the **active** account's own accepted folders only, and the shared-Keychain capability store is deliberately **single-slot** (the active account's `BackupKey` + renewable bearer; `provision` is delete-then-add). Per-account credential slots are rejected on purpose — they would keep app-dead engines serving a switched-away identity with no live session to renew its bearer, drive its arbitration inputs, or answer for it in the UI, a concurrency no other app surface offers (priority #3). Three load-bearing consequences: **(1) a switch tears the FP presence down before the new session starts** — `tearDownSessionForSwitch` runs the same `FileProviderCoordinator.signOut()` teardown as sign-out (every domain removed, capability revoked), exactly as it unprovisions the sync agent, then the incoming account's launch reconcile re-provisions and re-adds *its* domains (a switch-back re-populates placeholders from the nest — metadata-cheap by design); without this the outgoing account's domains keep serving while the single slot is re-provisioned under the incoming identity mid-flight. **(2) Domain removal preserves dirty data on every path — on macOS** — the one shared `FileProviderDomains.remove` uses `.preserveDirtyUserData` there, so an un-uploaded local edit under a removed domain (toggle-off, bind-time yield, sign-out, switch) is moved aside by the OS, never destroyed: the removal-shaped hole in *the OS never discards a local copy whose upload is un-acked* is closed at the single choke point every caller inherits. **iOS platform limitation (discovered at build, 2026-07-19): the iOS SDK marks BOTH `DomainRemovalMode` preserve cases unavailable** (the doc pages claim iOS 16+; the headers refuse — the compiler is the authority), so iOS removal is necessarily plain; the iOS-side guard is an **upload-drain gate before removal** (refuse/drain while un-recorded rows exist — the reviewer's alternative fix shape) — **BUILT 2026-07-19**: `FileProviderDomains.remove` on iOS throws `FileProviderRemovalRefused` while the set's state DB holds un-recorded local edits (engine seam `db::set_unrecorded_rels` — mid-flight states plus the record-failed `Synced`-without-proof shape, tier-1-pinned, fail-closed on an unreadable DB), leaving the domain registered so the OS's own pending-change retry drains them; sign-out holds the capability while any refusal is pending (revoking would strand the drain behind a fails-closed extension) and retries on the next reconcile. The companion **domain-owner record** (`domain-owners.json` at the flat state base — written by the app when it adds a domain, **backfilled at every reconcile only where no owner is on record**, cleared on successful removal, read by the extension at host build) keeps a dirty domain lingering across an account switch from ever being served — or its queued edits ingested — under the incoming account's single-slot credentials: the extension fails closed (`foreignDomainOwner`) and the drain resumes when the owning account signs back in; the removal gate likewise consults the *owner's* scoped state, not the currently-provisioned account's (the owner read from the identifier itself since 2026-09-25). **Foreign-owner rule (ratified 2026-09-25): a desired set whose domain identifier is registered under a DIFFERENT account on record is neither adopted nor re-recorded.** The incoming account's reconcile leaves that domain and its owner record alone, logs the hold, and adds its own domain on the first reconcile after the owner's drain has completed and the domain is removed (the owner's next sign-in drains it; its sign-out or switch then removes it) — the incoming set waits without a domain, which is the fail-closed direction. The collision was ordinary, not exotic, while the domain identifier was the bare `FolderRef` wire string — a `local:<id>` ref is unique per *nest*, not per device, so two accounts on two nests routinely both want `local:1` — and the record, not the identifier, was what told them apart; since 2026-09-25 the identifier carries the account (*the actor-scoped device identity*, below), the collision cannot arise for own-nest refs, and the rule stands as defense in depth over the record. Residual exposure, accepted: an edit still pending in the OS's replicated queue that never reached the extension at all (no DB row — e.g. the extension never ran while offline) is invisible to the gate and is discarded by a removal. **(3) Per-account sync-state scoping — BUILT 2026-07-19**: per-actor subdirs `<app-group>/sync/<actor-id-hex>/`, derived identically by all three processes through the one shared Rust rule (`db::actor_state_dir` — the app's `SyncStateDir.resolveShared(actorIdHex:)` from the session's actor, the extension from its provisioned credentials, the agent by scoping `SyncPaths::base_dir` — its binding-store `config.toml` included — from its provisioned capability at restore/provision time, unscoping at unprovision), so two accounts can never share a `fsid-<ref>.db`, `device.db`, a location map, or agent binding store. Nothing is adopted into a subdir from the flat base: a state file sitting flat there records no owner and is no account's (the first-adopter adoption that once copied the pre-scoping layout into the active account's subdir, stamped by a `state-owner` marker, was retired by the compat-remnant sweep — [`../architecture/compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md) § Program 4, tranche B1). Activation is apple + windows + **linux (LANDED 2026-07-22)**, on **every layout — the production base and a `--data-dir` override alike (ratified 2026-09-26)**: the override only relocates the flat base and the scope nests under it, so an e2e agent runs the real code path on every platform. The earlier carve-out that kept `--data-dir` layouts flat (so harnesses kept a fixed layout, e2e-launch-isolation.md § point 10) is RETIRED: windows is the one e2e layout that passes `--data-dir` (the agent's default root is the machine-global `%LOCALAPPDATA%`, so the app- and tui-spawned agents are pinned to a per-launch dir), and the flat agent there shared one binding store and one `fsid-local-N.db` across every account a test module signed in — a `local:<id>` is unique per nest, two fresh nests both mint `local:N`, so a later account inherited the earlier one's per-folder pull anchor and skipped its own nest's first changes. The e2e readers never depended on flatness (`helpers/sync_agent_config.py` globs flat then per-actor); only the process-level dirs stay at the flat base (the log dir, a `--data-dir` trust store). linux has no `--data-dir` test mode at all (`account-scoping.md`'s gap-ledger row has the full account). **Windows (LANDED 2026-07-21) conforms to the consequence-1 uniform shape "every out-of-app sync host is unprovisioned on every session-teardown path": it now sends `UnprovisionCapability` (the unit-variant teardown signal added to its C# IPC encoder) on BOTH teardown paths — `SignOutHandler` (after stopping the convergence loop, so its next tick can't re-provision from the still-loaded crypto) and `SwitchAccountHandler`'s step-4 teardown (awaited before step-5 re-provisions under the incoming identity — macOS's `switchAccount await FileProviderCoordinator.signOut()` ordering) — so the agent drops the capability, clears its per-actor scope, and stops engines, and never keeps serving a signed-out / switched-away account. Windows STILL re-scopes on the *provision* path for the incoming account (a switch's engine rebuild rides `reconcile_engines`), and the scope-aware engine stamp (`bins/fauna-sync-agent` `EngineStamp` carries the actor scope, so an owner-only set sharing a name + folder across two accounts rebuilds instead of leaking the outgoing engine's open `fsid-<ref>.db` handle) remains the belt-and-braces backstop. Both teardown paths are **e2e-proven end-to-end 2026-07-22** against a real `fauna-sync-agent.exe` over a real named pipe (`tests/e2e-unified/tests/test_sync_agent_unprovision_windows.py`, tier_3): a switch un-provisions the outgoing capability and re-provisions under the incoming identity, and a sign-out clears it durably with no re-provision after — previously the glue was compile-verified only. ⚠ Sending the teardown was necessary but not sufficient, and the gap took until 2026-08-06 to close: a teardown landing during the session INSTALL (~10 s of nest round-trips at login) unprovisioned nothing, because the app published its session handle only after that chain returned — so the sign-out found no session, reported success, and the install then provisioned seconds later, leaving the signed-out account served. Fixed by ordering the install *publish-before-provision* (`../architecture/apps/sync-agent.md` § Control plane split, which owns the rule and its two failure modes); windows now holds it through the unit-tested `SyncAgentSessionHost`, matching linux's synchronous `install()`. The e2e's own sign-out assertion was a `time.sleep(5.0)` settle window, which is why the defect survived a green run — it is now anchored to the `data.sync.agent_install_in_flight` causal barrier (e2e-latency-independent-assertions.md § point 14).** **One move between two scopes exists (ruled 2026-10-22): an identity succession carries the predecessor's agent scope — bindings and engine DBs, never `account-store/` or `device.db` — into the successor's, by the agent, from an attested predecessor only; owner [`../architecture/apps/sync-agent.md`](../architecture/apps/sync-agent.md) § The per-actor scope follows the account across a succession.**
- **The actor-scoped device identity (ratified 2026-09-25; the ref half percent-encoded 2026-09-29): every per-set registry a DEVICE keeps for this binding is keyed by the set's ref scoped to the account — `<ref-component>@<actor-id-hex>`, `local%3A1@<hex>` — never by the bare `FolderRef`.** A `FolderRef` is unique per *nest*, not per device (`local:<id>` is that nest's `folders.id`), so two accounts on two nests routinely both own `local:1`, and a device-wide registry keyed by the bare ref hands one account's presence to the other. Three registries collided this way and all three take the scoped key, and a fourth follows it: **(1) the domain identifier** — `FileProviderDomains.add/remove/list` register, remove and list scoped identifiers, the reconcile's plan matches desired sets against them, and the extension recovers both halves from the domain it was built for; **(2) the staging root** — `<group>/FileProvider/roots/<actor-id-hex>/<ref-component>`: the identifier's `@` boundary IS the directory boundary, account outermost (the same per-account nesting as `<group>/sync/<actor-id-hex>/`), and the identifier's ref half IS the directory's name — the ref as one percent-encoded component (`local%3A1`: shared Rust's `FolderRef::path_component`, the one encoder android's owned-tree roots key by too); **(3) the on-demand-toggle preference** — the shared-Rust `OnDemandPrefs` store (`FileProviderDomainPrefs` its wrapper), keyed by the scoped identifier, so it is per set per *account* per device, which was always the intent; **(4) the domain-owner record** (`domain-owners.json`, consequence 2 above) — keyed by the identifier and cleared on every successful removal, so it follows the identifier through the removal path with no step of its own. The grammar has exactly one home, shared Rust's `fauna_core::folder_keys::ActorScopedFolderRef` (`to_wire`/`parse`; FFI `actor_scoped_folder_ref` / `actor_scoped_folder_ref_parse`, which hand back the identifier, both halves and the ref component together), and FaunaKit's `FileProviderDomainIdentity` is its only wrapper — no Swift spells the separator or the ref's encoding. **The ref half is percent-encoded (ruled 2026-09-29): iOS refuses a File Provider domain identifier carrying `/` or `:` — measured 2026-09-27 on the iOS 26.5 simulator, `NSFileProviderManager.add` on `local:1@…` answers `NSPOSIXErrorDomain` 22, "Domain identifier … may not contain any of the characters '/:'" — so the bare wire's `:` cannot appear in it; the staging root's one-component encoding was chosen over a fresh `-` spelling because it makes identifier and directory one spelling and moves no root on any platform, and the encoder's alphabet (alphanumerics and `-_. ` pass, every other byte `%XX`) means the identifier is alphanumerics, `%` and the one `@`.** `@` was chosen because neither half carries it and it is path-safe everywhere: an OS registry may key a directory by the identifier, so `/` — which would have read naturally as the staging-root nesting — was rejected; the ref leads so a log line shows the set before the 64-char account. `parse` accepts exactly what `to_wire` emits: the pre-2026-09-29 spelling `local:1@…` and any escape the encoder would not write are refused like a bare ref, so a domain macOS registered under the old spelling (iOS never could) takes the un-gated unscoped-removal path below, its staging root byte-identical before and after (the roots always encoded the ref), and a `disabled` entry the toggle store holds in the old spelling is an **inert orphan** — never matched, never re-keyed, never swept; the choice is one tap to make again, and no dev box held a domain or a prefs file when the spelling changed. **Seam rule:** the apps feed the coordinator BARE refs (own-nest `FolderResponse.folderRef`, the same key the binding surfaces use — `FileProviderSyncSet.folderId` stays bare), the coordinator scopes each one exactly once (`desiredDomains`), and the Rust host constructor and the drain seam keep taking the bare ref recovered from the identifier. **Gate rule:** the iOS upload-drain gate parses the identifier to its halves and consults *that* account's scoped state for *that* set — never the raw identifier's validity as a `FolderRef`, which a scoped identifier fails — so a scoped domain with un-uploaded edits still refuses removal, and the gate no longer reads the owner record (the account is in the identifier). An identifier that scopes no set to any account — a bare ref or a set name from before actor scoping, or the pre-2026-09-29 spelling with the bare `:` in the ref half — is never served by the extension (`unscopedDomainIdentifier`, fail closed) and is removed by the next reconcile as undesired, *un-gated*: nothing under it can drain, so gating it would only wedge it and the sign-out capability hold behind it; no adoption, under the 2026-09-24 baseline reset. **Consequence for the foreign-owner rule above:** the identifier collision it worked around cannot arise for own-nest refs — two accounts' `local:1` are two identifiers, one added and the other left to the gated removal — and the domain-owner record is demoted to defense in depth: the extension's structural guard compares the identifier's account with the provisioned one *before* reading the record, and the plan's foreign-hold arm is reachable only through a corrupt or hand-edited map, and stays. **BUILT 2026-09-25; the ref half re-spelled 2026-09-29**; headless pins: `FileProviderDomainIdentityTests` (the shape — carrying neither `/` nor `:` — distinct per account, the staging roots spelled as the identifier's ref half, the per-account toggle, the drain gate's decision, the old spelling refused and un-gated), `FileProviderReconcilePlanTests` (two accounts' `local:1` never collide; a pre-scoping or pre-encoding identifier is removed, not adopted), `SyncStatesStoreTests` (the Media-badge fold routes only the active account's domains to the container), android's `FaunaDocumentsProviderTest` (the document-id grammar over the live spelling) and the shared-Rust `folder_keys` pins (the alphabet, the one encoder, the old spelling refused). Before the re-spelling **no iOS domain for a real set had ever registered** — the reconcile logged the refusal and continued — so iOS had nothing to migrate. Measured 2026-09-29 on the iOS 26.5 simulator against the real `fileproviderd`, the two spellings side by side through the DEBUG CLI's raw-identifier path: `local:1@<hex>` still answers `NSPOSIXErrorDomain` 22 "may not contain any of the characters '/:'", while `local%3A1@<hex>` passes that check — the identifier is accepted as spelled. A spawned process is refused by `fileproviderd` for not being a launched app, one step after the identifier check, so the registration itself needed a real launch. **Measured 2026-10-17 through a real `simctl launch` of the Debug app on the iOS 26.5 simulator (a throwaway device that booted with no new SpringBoard or backboardd crash report):** after `provision` answered `provision OK`, `register local:1 ProbeSet` answered `register OK: local%3A1@<hex>` and `list` showed that identifier registered — the production identifier is accepted by `fileproviderd` from a launched app. Two facts the witness needs: the launched build must be ad-hoc signed (`CODE_SIGN_IDENTITY=- CODE_SIGNING_ALLOWED=YES CODE_SIGNING_REQUIRED=NO`; the unsigned build answers `provision` `-34018` even from a real launch, because the app-group entitlement is absent), and the extension's init line is **not yet witnessed** — `fileproviderd` adds the domain `(disabled,replicated,…)`, answers `signalEnumerator` with "signalled … without active enumerators, not launching it", and answers an opened enumerator (listing the domain's user-visible root) with `NSFileProviderErrorDomain` -2011 "Sync is not enabled", so the extension process never launched and its app-group log directory was never created. What enables a freshly added iOS domain without a person at the Files app is the open question, and until it is answered the init line cannot be read from a headless launch. macOS stays unmeasured, its appex tier being signing-gated; the one macOS dev box held no domain and no prefs file at the change.
