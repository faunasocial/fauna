## Pillar 1 — Fauna-app subscriptions (built)

The end-to-end-encrypted paywall for Fauna-native readers. **Server, protocol, and shared FFI are complete; the ratified profile-centric UX is live on all 7 apps** — tui, last to arrive, built the subscriber offers/follow leg (M5 slice 2, 2026-07-15), closed the SELF author-management sections 2026-08-01 and the consumer `subscription-settings` page 2026-08-02, so all three UX surfaces below are now built everywhere (per-app state: § Implementation status today).

- **What it is.** A creator gates a post to a tier (`Post.gated = Some(GatedInfo { key_access: Broadcast { key_blob_ref }, tier, tier_rank, .. })`, `restricted-posts.md` § Encryption at rest). The body is sealed; the `KeyBlob` at `key_blob_ref` carries the period key individually X25519-wrapped to each current subscriber. Only an approved subscriber's client can decrypt.
- **Tier-key mint moves to the creator's client.** The nest never mints, holds or wraps a subscription period key, so KeyBlob minting/rotation happens on the creator's client (`mint_key_blob` in `libs/fauna-core::subscription::crypto`). Subscribe/unsubscribe **enqueue** intents; the creator's client picks them up, mints a roster-covering KeyBlob, and uploads it. Client-minted tiers are **broadcast-only** (no MLS group, no server-side period key). The nest-held period-key plane that once served pre-Phase-4 tiers was removed by the compat-remnant sweep on 2026-09-27 ([`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 2, the fourth ratified exception).
- **Wire.** Subscription management rides the `fauna.subscriptions.*` WS-RPC kind family (registry: `register_subscription_handlers` — a counted list re-rots; the registration block is authoritative) (`libs/fauna-protocol/src/subscriptions.rs`; handlers `bins/fauna-nest/src/subscription_handlers.rs`). Three carry an `encrypted_upload: { key_blob, signer_auth }` envelope (`tiers.create`, `requests.approve`, `subscribers.remove`); two always enqueue intents for the author's client (`subscribe`, `unsubscribe` — whatever the tier's `auto_approve`). `requests.approve` and `subscribers.remove` refuse a call without the envelope (`fauna.subscriptions.missing_upload`). The nest verifies a four-step auth chain + three state checks before storing the blob (design ratified 2026-05-15; tracked internally). The mutating HTTP twins were **removed** in the WS-RPC-everywhere cutover; only public, **unauthenticated** reads (`GET /api/v1/subscriptions/tiers/{author_id}`, `nest/info`, `delegate/{author_id}`) stay HTTP — i.e. the per-author tiers HTTP read serves only genuinely-unauthenticated / external (web-paywall, federation) consumers; **every authenticated Fauna app reads over WS-RPC** (the ws-rpc-everywhere directive — see `api-layers.md`). `tiers.list` (added 2026-06-18) is the **authenticated own-read** of the caller's tier definitions — the SELF "My tiers" source; its reply additionally carries `auto_approve` so the edit form round-trips it. `offers.list` (added 2026-06-19) is the **authenticated another-author read** — the target author's public tier offerings (request-supplied `author_id`, reusing the `TiersListReply` shape), the WS-RPC successor to the public HTTP read for the in-app subscriber-browse on someone else's profile (`profile.md` § Layout & flow → *Another's profile*; powers `subscription-offers-section`). `mine.list` (added 2026-06-18) is the **caller-scoped consumer enumeration** — the caller's subscriptions across *all* creators (active subscriber rows + pending subscribe requests, deduped), each carrying the creator's nest-resolved handle (or `None` → the app renders the hex actor id); it powers the `subscription-settings` page (distinct from the per-creator `status.get`). **`tiers.create` REQUIRES the birth envelope.** `TierCreateRequest.encrypted_upload` is a required field: a create without it fails to decode, and the nest verifies the envelope — the same four-step auth chain, plus the tier-name match and the empty-roster check — **before** it inserts the tier row, so a refused envelope leaves no tier behind — except on the reserved `followers` slot (rank 0), whose row is the nest's own shape: the nest provisions it (`ensure_followers_tier`, the same call a first follow makes) *before* checking the envelope, so a refused birth blob there leaves the nest-provisioned keyless followers row that a first follow would have created anyway, never a client-shaped tier. The envelope-less create that alpha clients sent before the field existed (2026-07-13), once accepted under a 2026-08-02 wire-compat ruling, was removed by the compat-remnant sweep ([`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 2, the fourth ratified exception), which supersedes that ruling. **Every upload door refuses a tier with no stored `KeyBlob`** (`fauna.subscriptions.key_blob_not_found`) — with ONE exception, `requests.approve` on the lazily provisioned `followers` tier: a first follow of an author who never created that tier provisions the row alone (`ensure_followers_tier` — the nest cannot mint), so the tier's first blob rides the first follow approval and is stored at version 1, minted under the followers period key the author's client generates on demand. Every other tier gets its birth blob at version 1 from `tiers.create`, so its first approve lands at version 2. The general no-prior-blob arm that served tiers stored without a birth blob was removed with the nest-held period-key plane ([`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 2, the fourth ratified exception). A required envelope still cannot make a keyless "orphan" tier unrepresentable — the period key is client-custodied and invisible to the nest, and a birth blob's empty roster wraps no key, so a raw protocol client that mints a blob under a key it then discards still creates a tier no client can later mint for. That state stays recoverable, not a brick: `tiers.delete` and `requests.reject` take no key material (`nest/common.md` § Client-state recoverability is satisfied). Orphan *prevention* lives client-side, where the custody fact is visible: the shared orchestration persists the period key before it mints the birth blob, and the raw e2e seeding helper (`tests/e2e-unified/actions/api_actor.py::subscription_create_tier`, whose envelope comes from the same shared mint via `fauna_ffi.build_tier_birth_upload`) documents the orphan hazard in its docstring — that render-only seeding shape stays sanctioned. Pinned by `tiers_create_refuses_a_create_without_the_birth_envelope` and `tiers_create_refuses_a_foreign_envelope_before_inserting_the_tier`; `tiers_create_never_mints_a_period_key_or_mls_group` pins that even an enveloped create mints no nest key. **A third-party principal follows and unfollows through the sixth Fauna-family arm, `fauna:follow:write` (ruled 2026-10-02 — [`authorization-server.md`](authorization-server.md) § Scope grammar → *The planes ruled 2026-10-02*, which owns the arm):** principal twins of `subscribe`, `unsubscribe` and `status.get` for the `followers` tier only, the subscriber's ML-KEM key read from the per-account registry entry that arm's build adds, a missing entry refusing the follow.
- **Every tier is backed by the broadcast `KeyBlob`.** No writer creates an MLS-backed subscription tier any more: the nest-side MLS tier path went with the nest-held period-key plane, so the `KeyAccess::Mls` arm is authored only for room-restricted posts (`restricted-posts.md` § Encryption at rest; `key-material-hierarchy.md`); the `epoch_secret.get` / `archival_blob.get` read kinds and the `mls_in_encrypted_mode` refusal were retired with that plane on 2026-09-27 (`feed.md` room ruling 8, lifted), and the writer-less `tier_mls_groups` table left the schema with the plane's retire step (schema 91).
- **A follow across nests (ruled 2026-10-16; built in the nest and shared Rust 2026-10-17, in the apps on tui, android and linux, the other four following — § Implementation status today).** Following *is* subscribing to the free followers tier, and the owner ruled that this relationship **reaches across nests**: a subscriber homed on nest A subscribes to an author homed on nest B through a signed federation twin of `fauna.subscriptions.subscribe` that A originates and B enqueues as it enqueues a local intent; the author's client drains it as any other and wraps the followers-tier period key to the remote subscriber's pubkey exactly as to a local one — the `KeyBlob` stays author-minted, nest-blind and roster-covering, and no nest holds key material (the tier-key rule above). Paid tiers take the same twin once the payment leg can name a remote buyer — the claim redeem does since 2026-11-08 ([`monetization.md`](monetization.md) § Pillar 3 → *Buyer↔actor binding (Q4)* → *Which nest an in-app redeem binds on*; the twin's admission [`federated-follow.md`](federated-follow.md) § Decision 2 → *The redeem twin*); the signed-in checkout does since the same day's Q13 ruling — the buyer's relayed intent and the provider's webhook complete one request row at the author's nest, in either order ([`monetization.md`](monetization.md) § Pillar 3 → *Buyer↔actor binding (Q4)* → *A checkout-bound buyer homed on another nest*). What a follow then *delivers* — the author's post envelopes to the follower's nest, for its own index — is [`../architecture/feed-read-model.md`](../architecture/feed-read-model.md) § The read model → *Posts of authors you follow on other nests*; the kinds are [`../architecture/federation.md`](../architecture/federation.md) § Federation residue surface, the *Federated follow* row. Decided 2026-10-16 and owned by [`federated-follow.md`](federated-follow.md): the subscriber's own signed `FollowIntent` under `Capability::Follow`, carried verbatim by their nest and bound to it by the home (§ Decision 2 there); the `KeyBlob` rests where it rests today — `current_key_blobs` behind `key_blob.get`'s roster gate, never on a public route, since it names every subscriber — and a remote follower reads it through their own nest's `key_blob.get`, which relays to the home (§ Decision 3); the re-points on either side's succession and the unsubscribe and delete legs (§ Decision 5). A subscribe naming no home stays same-nest: `subscribe_core` provisions the followers tier only for an author this nest hosts (`tier_not_found` otherwise).
- **The offers browse across nests (ruled 2026-11-11, design pass; BUILT in the nest and shared Rust 2026-11-11, on tui the same day, the other six following — § Implementation status today; refutable at build time by the rows it names).** The OTHER Tiers tab of a creator homed on another nest lists that creator's offered tiers, read from their home **through the viewer's own nest**: `fauna.subscriptions.offers.list` answers from the caller's nest alone, which holds no tier of an author it does not host, so until the apps call the relay the tab paints nothing there while the follow, the subscribe, the checkout and the redeem already reach the home. Eight parts:
  - **The carrier is the relay, `fauna.profile.get_remote`'s twin — never the app dialing the home's public `GET /api/v1/subscriptions/tiers/{author_id}`.** The app asks its own nest with a distinct kind, `fauna.subscriptions.offers.list_remote { author_id, nest_url }` (`User` class, `OnlineOnly`, the 30 s peer deadline, never pre-identity, a replay-safe pure read — the `_remote` family's shape, [`../architecture/federation.md`](../architecture/federation.md) § Federation residue surface, the *Offers browse across nests* row), and the nest answers it in `subscribe_core_from`'s arm order: an author it hosts is answered locally, exactly as `offers.list` would; any other author is read from the named home by originating `fauna.federation.follow.offers.list { author_id }` over the nest-signed channel, the peer resolved from `nest_url` as the subscribe twin resolves it, the reply forwarded unstored. **A distinct kind and not an additive `home_nest_url` on `offers.list`** (where the subscribe twin did add fields): a subscribe an old own nest cannot route fails loudly (`tier_not_found`), but a read that ignored the field would answer the local empty list — the silent wrong answer this ruling exists to remove — so an own nest that predates the kind must refuse it as unknown. **Why not the public HTTP read**, though the data is as public there: every app browses over its one WS-RPC connection with no per-app HTTP glue ([`../ui/profile.md`](../ui/profile.md) § Where logic lives → *Tiers tab*, priority #2); an app's direct dial of a foreign home is ruled only for content-addressed bytes, where the hash checks what arrives and the pin is graduated against the identity the app's own nest dial-proved — a tier list is not content-addressed, so a direct read would need a trust anchor the app does not hold for a self-signed home, while the channel already has one; the home gets attribution and the per-nest throttle; and the web app is spared a cross-origin read. The public route stays what it was kept for, genuinely unauthenticated consumers outside the apps.
  - **The home answers what its own `offers.list` answers.** `fauna.federation.follow.offers.list` is nest-signature and serves the same `TiersListReply` through ONE function shared with the local handler, so the three withholdings cannot drift between the doors: no per-post pay-to-unlock tier, no hidden tier, and `asking_price` never carried ([`monetization.md`](monetization.md) § The unifying model and § Per-post pay-to-unlock own the three). An author the home does not host answers the empty list, as the local kind answers for any author with no tier — no `not_found` arm, so the read is no hosting oracle beyond what `fauna.actor.by_handle` already says, and the page needs no second empty state.
  - **No reach gate — the read departs from `fauna.profile.get_remote` here, deliberately.** The profile relay is served only on the actor's signed `audience = Everyone` because the profile record carries `recovery_head` and `nests` and its anonymous read was declined on 2026-08-17 ([`../ui/profile.md`](../ui/profile.md) § Where logic lives → *The remote read*). None of that holds for an offer: the home already serves these exact fields to anyone, unauthenticated, on its public route, so a gate on the channel would withhold nothing; an offered tier is by its nature the creator's word to people who are not yet subscribers, and the owner ruled 2026-10-16 that follows and paid subscriptions reach across nests with no opt-in — the subscribe twin, the redeem twin and the checkout carry none; and the tab must work for a creator whose profile is `ThisNest`, whose header falls to the id while the follow button beside it already works. What a creator does not want browsed is not offered: the `hidden` flag is the per-tier control, and it holds on every door.
  - **The reply is the home's word, bound to the nest that gave it.** Tier definitions are not author-signed, on the local door either; the viewer's nest forwards what the home it dialed answered and adds nothing. The home is the page's `actor_home` slot ([`../ui/profile.md`](../ui/profile.md) § Where logic lives → *The actor's home*): the actor's own signed profile when the header read verified one, else the hint the open carried — exactly the home the follow, the subscribe and the redeem on the same page already trust, so the browse opens no exposure they have not (a home that lies about an author it does not host can offer a tier whose subscribe it then answers itself; it cannot reach the real author's roster or keys).
  - **The viewer's status needs nothing new.** The badge and the button state stay `fauna_core::format::offer_status` over `status_get(actor_id)` on the viewer's OWN nest, which already answers a remote author from `remote_follows` (`subscription_handlers::remote_status`: the approved paid tier if one, else the approved `followers` tier, and `follow_pending`) — so a tier bought by a redeemed code or a checkout paints `active` on its relayed row with no further read, and the home is never asked about the viewer. The per-row Subscribe calls `subscribe_across_nests` with the same slot, as the follow button does.
  - **The old-peer answer and the failures.** A home that predates the kind refuses it at its allowlist, which the relay maps to `fauna.federation.peer_nest_outdated` (`rpc_errors::map_peer_relay_error`); an unreachable home is the relay's ordinary peer error. Either paints where a failed local `offers.list` paints today, with its own localized message, and leaves the rest of the page working — the header, the follow button and the redeem row do not wait on the browse.
  - **No cache, on either nest.** The viewer's nest stores nothing ([`../ui/profile.md`](../ui/profile.md)'s *Federation receive-write is deferred* stands), and tier definitions change at the author's will — a stale price hint or payment link is worse than a round trip. The app re-reads at the Tiers-tab re-read doors § Implementation status today already rules, nothing more.
  - **The app side is one shared method.** `SubscriptionsClient::offers_list_across_nests(author_id, home)` beside `subscribe_across_nests`: no home → `offers.list`; a home → `offers.list_remote`, with UniFFI and wasm faces. Every app's Tiers-tab load passes the page's `actor_home` slot and re-spells nothing; tui leads.
### Pillar 1 — UX (ratified 2026-06-14; IA approved, lead app = linux)

**IA: profile-centric.** Subscription is an *asymmetric* creator↔audience relationship, so it lives on the creator's identity surface (the **profile**), not on contacts (§ Why profile, not contacts). ui.yaml owns the IDs (`profile` page + `subscription-settings` page + 6 components); `profile.md` owns the profile-shell layout. Three surfaces:

1. **Author management — profile Tiers tab, own profile** (`is_self`):
   - **§1 My tiers** (`subscription-tiers-section`, component `subscription-tier-list`, form `subscription-tier-form`) — create/edit/delete tiers. Mirrors the admin quota-tier list shape (priority #3); distinct from `admin-settings-tier-*` quota tiers.
   - **§2 Pending requests** (`subscription-requests-section`, component `subscription-request-list`) — approve/reject pending **subscribe** requests, with a `subscription-request-kind` badge. Mirrors `admin-invite-requests-list`. **Unsubscribe rows are transient, not judgment calls** (ratified 2026-08-01): the pump commits them without author action (§ Flows → Unsubscribe), so they appear here only between ticks; an approve on one refuses (`wrong_request_kind`).
   - **§3 Subscribers** (`subscription-subscribers-section` + `subscription-subscribers-tier-select`, component `subscription-subscriber-list`) — the selected tier's roster, with per-row remove.
2. **Subscriber browse — profile Tiers tab, another's profile** (`subscription-offers-section`, component `subscription-offer-list`) — offered tiers + per-row Subscribe + price hint + external payment link + this viewer's status. The free "followers" tier uses `profile-follow-button` (follow = subscribe to the free tier).
3. **Consumer side — `subscription-settings` page** (Settings ▸ Subscriptions, sibling of mail-settings/web-settings; component `subscription-mine-list`) — what this user subscribes to across all creators, with unsubscribe.

**Flows.**
- **Subscribe:** `subscription-offer-subscribe-button` → `fauna.subscriptions.subscribe`; this always returns `Queued` for a caller not yet subscribed → `subscription-offer-status` flips to "pending" (an `auto_approve` tier included: its author's client grants it on the next tick). The per-tier `subscription-offer-status` badge is derived in shared Rust — `fauna_core::format::offer_status(tier_name, status_tier, pending) -> OfferStatus` (precedence Active>Pending>None) + `offer_status_label` (`subscriptions.offer_status_*`); `pending` is the transient post-`Queued` overlay (`status.get` carries no pending discriminant). Natives consume the `OfferStatus` enum (badge + Subscribe-button state); web the composite label. See `profile.md` § Where logic lives → Tiers tab (the canonical statement).
- **Approve / Remove — the transparent crypto:** `subscription-request-approve-button` (or `subscription-subscriber-remove-button`) → the client orchestrates *list post-mutation roster → `mint_key_blob` → `requests.approve` / `subscribers.remove` with the `encrypted_upload` envelope*; `subscription-request-busy` shows during the mint; nest errors (`roster_mismatch`, `stale_rotation`, `missing_upload`) surface to `error-message`.
- **Tier CRUD:** `subscription-tier-create-button` → `subscription-tier-form` → `fauna.subscriptions.tiers.create` (the nest never mints a period key or MLS group for a new tier — client-minted by design).
- **Unsubscribe:** `subscription-mine-unsubscribe-button` → `fauna.subscriptions.unsubscribe` naming the row's tier (what a leave covers, the unfollow included: § The free followers tier — follow and unfollow); this returns `Queued` (the subscriber stays until the author's client commits the removal). **The commit is automatic — a leave is not the author's to refuse (ratified 2026-08-01):** the author pump's drain routes every `kind='unsubscribe'` row into the removal rotation (`remove_subscriber` + queue-row clear), unconditionally and before any same-pass approve-mint; the consumer row of a same-nest subscription honestly persists until that commit — a cross-nest one's row is the follower's nest's own record, marked `removed` once the home answers the leave (§ The free followers tier — follow and unfollow, rule 2), while the commit at the home still waits on the author's client — (an app that optimistically drops it renders a leave as done while the KeyBlob still covers the leaver). Approve-minting an unsubscribe row is refused at both the shared seam (`AuthorError::WrongRequestKind`) and the wire (`fauna.subscriptions.wrong_request_kind`) — the approve upload's KeyBlob covers the roster *including* the leaver, so accepting it would silently cancel the leave (which is exactly what every app's §2 Approve button did until 2026-08-01).

**Where the logic lives — the load-bearing shared-Rust requirement (priority #2).** The approve/remove **mint+upload orchestration** (read the post-mutation roster → `mint_key_blob` → build `EncryptedKeyBlobUpload` → call the kind → retry on a nest `roster_mismatch`/`stale_rotation` if the roster changed under it; a `stale_rotation` re-reads the period key first — [`succession-aftermath.md`](succession-aftermath.md) § Re-key scope's period-keys row owns why) MUST live in **shared Rust** (a client subscriptions client/state machine), exposed via UniFFI + WASM, so all 7 apps dispatch a single high-level "approve subscriber" / "remove subscriber" call and render a snapshot — never re-implement the crypto dance per app. Today `FfiSubscriptionsClient.requests_approve` / `subscribers_remove` take a **pre-built** `encrypted_upload` envelope (the caller must mint), so the lead-app track's **first deliverable is adding that orchestration to the shared client crate** (the standing shared-Rust cleanup job — clean up the consumption surface). Tier CRUD / subscribe / unsubscribe / list reads are thin pass-throughs to the existing kinds. Snapshot shape (proposed): a `SubscriptionsSnapshot` carrying the author's tiers, pending requests (with `kind`), the selected tier's roster, an in-flight/busy flag for the mint, and `LocalizedText` errors; the subscriber views carry offered tiers + status, and the consumer view carries this user's subscriptions. Observer-driven rendering, no client-side caching (same rules as `feed.md` § Architectural rules). The thin per-kind wrappers exist in `libs/fauna-client-subscriptions` (`SubscriptionsClient<R>` — every kind, incl. the authenticated `tiers_list` + `mine_list` own-reads; `requests_approve`/`subscribers_remove` take a **pre-built** `encrypted_upload`), and the high-level orchestration that mints that envelope **landed 2026-06-15** as `SubscriptionsAuthor` in the same crate (`orchestration` module) — it bundled the thin client with a `ConfigClient` (period-key custody + the crash-staged removal sentinel + the identity keypair the mint signs with); since the rail retired 2026-10-02 it holds the `ActorKeypair` and the custody rests in the account-state plane kind `fauna.state.subscriptions` ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The kinds*). The remaining per-app work is exposing it over UniFFI (Apple/Android/Windows) + WASM (web); linux consumes the Rust crate directly.

**The author pump's *cadence and tick body* are shared policy too (added 2026-08-01).** Each app owns only the *scheduler* — a tokio task, a Swift `Task`, a C# `Task.Delay` loop, a Kotlin coroutine, a JS `setTimeout` — because that is genuinely platform-specific. Everything else is `fauna-client-subscriptions`: **`SubscriptionsAuthor::reconcile_once()`** is the whole tick (resume crash-staged removals, *then* drain auto-approvals; each half best-effort, reported in a `ReconcilePass`, neither able to abort the other), and **`author_poll_interval()`** is the backstop cadence (the 30 s constant plus the `FAUNA_SUBS_POLL_SECS` e2e override; native-only env probe, so a browser gets the constant and supplies its own e2e cadence). Natives reach both over UniFFI as `subscriptions_reconcile_once` / `subscriptions_author_poll_secs`. **An app MUST NOT re-derive either.** Two properties are load-bearing and were being re-asserted in six independent hand-written loops until this landed: (1) **resume runs before drain** — a staged-but-uncommitted removal must be driven out before the drain mints over the roster, or the fresh `KeyBlob` re-covers the very subscriber being removed, leaving them read access for a full period; (2) **both halves run on every tick** — hoisting resume to once-per-connection looks equivalent and is not, because a removal staged *during* a session (a transient upload failure, or a peer device's staging arriving via config sync) then heals only at the next connect. Calling `reconcile_once` makes both mistakes unrepresentable; that is the point of the seam. The tick also carries a third half that runs **once per connection** rather than per tick — the stale-keyed-blob pass (`republish_stale_keyed_blobs`); what it heals and when it is owed is owned by `succession-aftermath.md` § Re-key scope (the period-keys row), and its latch rides the connection object the natives and the SPA already hold, so no app wires it.

**The headless-author corollary + the canonical e2e seeding shape (ratified 2026-08-01).** An inline `approved` on subscribe is reachable only for a caller who is already an active subscriber of the tier (the idempotent re-subscribe); for anyone else — on every tier, `auto_approve` or not — `subscribe` answers `Queued`, and the grant materializes only when the author's **client** next runs a reconcile tick. `auto_approve` removes creator *judgment* (no manual approve click), never creator *presence* (the KeyBlob mint needs the tier's period key, which only the author's client holds). So a headless author can never produce an `approved` subscription, and a test or fixture that needs "an author-granted subscription exists" seeds it as: **the author's client creates the tier** (a raw WS-RPC `tiers.create` whose birth envelope is minted under a throwaway key — the e2e seeding helper's shape — mints an **orphan tier**: its period key lands in no custody, so no client can ever mint a later KeyBlob for it; `approve_subscriber` deliberately auto-heals a missing key only for the reserved `followers` tier — § Pillar 1 Wire bullet) → subscribe (assert `Queued`) → the author's client grants — either its reconcile tick drains an `auto_approve`/`payment_entitled` request (the connect-time drain reliably beats a manual UI approve — the 2026-08-01 `test_sell_post_buyer_redeems_claim_and_unseals` finding), or the author drives the UI approve for a judgment tier — → deadline-poll the subscriber's `status.get` until active (a named generous budget, never a settle-sleep — `../architecture/e2e-latency-independent-assertions.md` § point 14) → proceed as the subscriber. **The mirror holds for leaving:** a queued unsubscribe is committed only by the author's client (the pump's unsubscribe-commit leg, § Flows → Unsubscribe), so its canonical e2e shape is unsubscribe (assert `Queued`, row persists) → author's client online → deadline-poll `status.get` until the tier is gone. **No instant-grant nest test-hook exists, deliberately:** such a hook would either fabricate a nest-minted period key — a state a post-Phase-4 nest cannot produce (the nest never mints one) — or mint an `approved` row with no KeyBlob behind it, which no production path produces either; both would run every downstream assertion against an unreachable state. Template: `tests/e2e-unified/tests/test_subscriptions.py` — `test_follow_auto_grants_in_encrypted_mode` proves the drain mechanism itself; `test_subscription_settings_lists_active_subscription_and_unsubscribes` consumes the shape as precondition seeding. **The API-tier form (no app, 2026-10-09):** a witness that keeps the period key it created the tier under *is* that author's client — `ApiActor.subscription_create_tier_with_key` keeps the key, and `ApiActor.subscription_grant_pending` mints the approve upload over the current roster through the same shared `mint_self_delegated_upload` every app's drain rides (the e2e cdylib's `fauna_subscriptions_build_roster_upload`), so a `[nest]` outcome about a granted subscription is witnessed through the real approve door with no app launched (`tests/e2e-unified/tests/api/test_payments_webhook.py`). It is still the author's mint, never a nest test-hook.

**Resolved dependency — client-minted period-key custody.** `mint_key_blob` takes the tier's **period key** as input, but the nest mints and holds none for a tier created since the storage-mode axis retired (`tiers.create` never mints one, by design), so the **author's client** generates it at tier-create and retains it as owner-private key material. **Custody home:** the account plane's `fauna.state.subscriptions` rows, fleet-only and generation-tip-sealed (plane-only since 2026-09-30) — per tier the `current` period key plus the full uncapped `prior` history (archival backfill needs every period). Generate-at-tier-create / retrieve-at-mint / rotate-on-removal live in `libs/fauna-client-subscriptions` (the standing shared-Rust home, mirroring `fauna-client-mail-settings`'s MSEK lifecycle). Full design + the storage-shape rationale: `key-material-hierarchy.md` § Audience: an opaque set of subscriber pubkeys → *Client-minted at-rest custody (author's client)*. This was the one piece of new *crypto-adjacent* client state the feature needs; everything else is glue over existing primitives. **Second client-state piece the mint needs:** a self-signed `DeviceAuthorization` granting `ManageSubscribers` (the single-device delegation the auth chain checks — 2026-05-15 spec § Auth chain step 3) — **built**, `fauna_core::subscription::crypto::build_manage_subscribers_self_delegation`, called from the `SubscriptionsAuthor` mint orchestration above (`libs/fauna-client-subscriptions/src/orchestration.rs`).

**Implementation slicing (lead = linux).** Slice A (author-first, the novel/hard part): the shared-Rust mint orchestration + the profile Tiers-tab SELF sections (tiers CRUD, pending-approve-with-mint, roster-remove-with-mint). Slice B: the subscriber side (offers + subscribe + status) and the `subscription-settings` consumer page. Then lift to the other 5 apps (the existing per-app `TODO-{client}-subscriptions-ws-rpc-1.md`, re-scoped from "migration" to "lift"). i18n strings (`S.subscriptions.*`, tier/request/status labels) are added to `en.yaml` by the lead at implementation.

## The free followers tier — follow and unfollow (ruled 2026-11-07, design pass; refutable at build time by the rows § Implementation status today names)

**The gap this rules.** Following *is* subscribing to the free rank-0 `followers` tier (§ Pillar 1; [`monetization.md`](monetization.md) § The unifying model), and three docs promised the reverse — [`../ui/profile.md`](../ui/profile.md) named `SubscriptionsClient::unsubscribe` as the unfollow, [`federated-follow.md`](federated-follow.md) § Decision 5 had a leave stop delivery, and [`authorization-server.md`](authorization-server.md)'s follow arm unfollows as the account — while no door served it: `fauna.subscriptions.unsubscribe` leaves paid tiers only (`subscription_handlers::unsubscribe_core`, the rank ≥ 1 scope note), so a user's leave of the free tier was refused `not_subscribed` on one nest and at the home across two (measured on two real nests 2026-11-07); the apps' `profile-follow-button` only ever subscribes, and its label flipping to *Following* was a state with no gesture behind it. The principal arm alone enqueued a followers-tier leave (`subscription_handlers/principal.rs::unsubscribe_handler`), which is the one place the mechanism already existed.

**1. An unfollow is a subscriber leave of the followers tier on the one unsubscribe door — no unfollow kind.** `UnsubscribeRequest` gains an additive `tier: Option<String>` naming the tier the subscriber leaves (the federated leave already names it: `FollowIntent.tier`, and `SubscriptionsClient::unsubscribe_across_nests` takes it). **A leave is at-or-above the named tier's rank**: `Some(name)` ends `name` and every tier the subscriber holds at a higher rank, `None` keeps today's meaning — floor rank 1, every paid tier, the follow kept — so `Some("followers")` is the unfollow and ends everything the subscriber holds with the author, paid subscriptions included. That is the one leave set the rank cascade leaves stable: a subscriber off the followers roster who still holds a paid tier is re-enrolled by the cascade's boot-time and edit-time reconcile (`db/migrations.rs::reconcile_unlock_fanout_requests`, the standing self-heal of [`monetization.md`](monetization.md) § Per-post pay-to-unlock rule (c)), and a leave of one paid tier below a higher one held is re-enrolled the same way, which is why the retired plaintext arm already leaved by a rank floor (`remove_subscriber_from_tiers_at_or_above`). **A designated (`unlocks_post`) tier is never in a leave set:** a purchase is a good, not a relationship ([`monetization.md`](monetization.md) § The unifying model → *One model, many mechanisms, two targets*), so it survives an unfollow and a paid-tier cancel alike — a correction of today's door, which drops every held tier of rank ≥ 1, a bought post's among them. The reply stays `Queued`; the subscriber stays on each roster until the author's client commits the leave (§ Pillar 1 → Flows → *Unsubscribe*). **A request still pending is withdrawn, not left (amended 2026-11-08):** the subscriber's own `kind='subscribe'` rows for undesignated tiers at or above the floor are deleted at once — no roster holds them and no key was wrapped to them, so no rotation is owed — and a floor the subscriber has only asked for is a floor like a held one; a leave that withdrew and queued nothing answers `Removed`.

**2. Across nests the same leave rides the existing twin.** `unsubscribe_across_nests` sends the signed `kind = unsubscribe` intent naming the tier; the home's `fauna.federation.follow.unsubscribe` handler passes the intent's tier to `unsubscribe_core` as the floor (today it passes none, so a followers intent is refused there); the follower's nest marks its own `remote_follows` rows by name — every row of the author for `followers`, the named row for a paid tier, every row but `followers` for none; an `approved` or a `pending` row alike — once the home has answered the leave or could not be reached, never when the home refuses it (amended 2026-11-08: a refused leave leaves no half-state on the follower's nest) — and the home's `follow_state removed` pushes land the rest of the at-or-above set as the author's client commits each tier. Delivery to that home then stops by [`federated-follow.md`](federated-follow.md) § Decision 1's discard, and the purge removes the envelopes once no local reader follows the author (§ Decision 5 there owns the legs; this section owns only what the leave *is*).

**3. The author's client commits a followers leave as it commits every leave: the removal rotation.** `SubscriptionsAuthor::commit_unsubscribe` → `remove_subscriber(followers, leaver)`: rotate the followers tier's period key, mint the roster-covering `KeyBlob` without the leaver, upload through `subscribers.remove` (whose handler enqueues the state leg for a homed subscriber), clear the queue row. **No shortcut for a "public-only" follower:** the tier is the entitlement, the author's client cannot know which follower never reads a followers-gated post, and a leaver must not read one sealed after the leave; one rotation per leave is the price an author's removal already pays. The followers tier's period key is in the author's custody like any tier's (the approve path records a missing one at the first approval, and the leave path takes the same heal, since a nest-provisioned tier whose author's client never minted may hold followers whose leave arrives first). Batching the leaves of one pass into one rotation per tier is an optimisation this ruling leaves open, not a requirement.

**4. The app gesture: `profile-follow-button` is a toggle, like `profile-block-button`.** *Follow* subscribes (as today); *Following* pressed unfollows, `tier = followers`, at the author's home when the profile carries one (the same slot the follow uses, [`../ui/profile.md`](../ui/profile.md) § Where logic lives → *Follow / unfollow / follow-status*). **When the viewer holds a paid tier at that author the press is confirm-gated** — two presses, the first relabelling the button with the cost ("Unfollow and end your paid subscription"), the shape `admin-mail-list-unsubscribe-secret-rotate-button` already has — because by rule 1 the unfollow ends the paid subscription too, and ending a paid relationship on one tap is not a toggle's to do. The `is_following` derivation moves to shared Rust beside the label (`fauna_core::format::follow_toggle_label`): **following ⇔ `status.get` names a tier, or reports `follow_pending`** — every paid subscriber holds `followers` by the cascade, and the status pick already skips designated tiers, so a pure buyer reads *Follow*; *Following* pressed while the follow is only pending withdraws the request (rule 1's withdrawal), so the toggle holds in that window too; this retires the 2026-07-08 decision that kept the derivation per app, which had web reading *Follow* for a paid subscriber (its test was `tier == followers`, false once a paid tier outranks it for display). The consumer page's `subscription-mine-unsubscribe-button` leaves at its row's tier, which every app already passes — on a `followers` row it is the same unfollow (today that press is refused `not_subscribed`).

**5. The principal arm is unchanged in scope and gains the shared path.** [`authorization-server.md`](authorization-server.md)'s follow arm unfollows the free tier only and refuses while a paid tier is held (a paid tier is the user's own act to end); its handler's enqueue becomes a call of the same `unsubscribe_core` floor the user door takes, so one implementation serves both.

**6. A purchase no longer makes a follower (the cascade's designated edge, re-ruled 2026-11-07 — owner [`monetization.md`](monetization.md) § Per-post pay-to-unlock, rule (a)).** Until now a designated grant fanned out to every undesignated tier at or below its rank, "so a buyer of a sold post becomes a follower" — which made every buyer's unfollow unstable (rule 1's reconcile re-followed them at the next boot) and, read against the grant-time SQL, over-granted: a pure pay-per-view tier is minted *above* the author's highest regular tier, so its buyer sat at a rank every paid tier is at or below, and `enqueue_unlock_fanout` enqueued them for each — a one-post purchase buying every paid subscription, perpetually (found by reading; the fixtures only ever sold at rank 1, below the paid tier). Ruled: **a designated grant fans out to nothing**; the undesignated direction stands (a rank-R subscriber is enrolled in every tier ≤ R, designated included — subscribers get the post free). A buyer who wants the author's posts follows, free, in one tap.

**What this does not change.** Which posts a same-nest reader's feed lists is [`../architecture/feed-read-model.md`](../architecture/feed-read-model.md)'s; a local leave changes the roster and what unseals (no followers-gated post sealed after it), not the on-box listing. Cancelling a paid tier keeps the follow, as ruled when the mode axis retired (the `None` floor). The reserved tier's name, rank and auto-provisioning ([`monetization.md`](monetization.md) § The unifying model) are untouched.

  **The poll backstop got its first e2e pressure 2026-08-12** — until then the arm was code-wired everywhere and asserted nowhere, and `FAUNA_SUBS_POLL_SECS` (declared above as the e2e's fast-drain override) was set by **no test at all**, so every suite that touched the pump ran it at the 30 s constant. `test_subscriptions.py::test_the_author_pumps_poll_backstop_grants_a_ui_subscribe_with_no_author_action` (tier_3, tui lead + linux) closes that: two GUI apps, the author's already established — and so its *connect* pass already spent against an empty queue — when the subscriber's UI subscribe arrives, leaving a later poll tick the only thing that can grant it. Its sibling `test_follow_auto_grants_in_encrypted_mode` covers the connect arm (it logs the author in *after* the queue is non-empty), and the two are genuinely discriminating: a connect-only pump passes that one and reds this one, verified by mutation. The subscriber-side render is the assertion surface, and making it green surfaced a divergence worth declaring here: there is **no push kind for a subscribe grant**, so a subscriber sitting on another actor's offers section never re-renders on its own — and the apps do not agree on what *does* re-read it. tui re-reads on entering the Tiers tab; linux re-reads only when the profile **page** becomes visible, its tab click being inert; the other five are unsurveyed. So a granted subscribe can read "Pending approval" indefinitely depending on which app you run and which widget you touch. That is drift to resolve, not a design — **the ruling landed 2026-08-12 and is the next paragraph.**

  **The Tiers-tab re-read door — ruled 2026-08-12.** The full seven-app survey found **four** distinct doors, not two: **tui** re-reads on every `profile-tiers-tab` activation (`Action::ShowTiers` → `Op::LoadOffers`, unconditional — a re-click while already on the tab re-reads); **android** re-reads only when the tab branch re-composes (`LaunchedEffect(targetActorIdHex)` inside `ProfileOffersTab`), so leaving to Posts and back re-reads but a re-click does not; **linux**, **web**, **windows** and **apple** re-read at *page* granularity only (linux `app.rs`'s `connect_visible_child_name_notify` → `ProfileHandles::refresh_tiers`; web an `$effect` keyed on the viewed actor; windows `Page_Loaded` → `HydrateAsync`; apple `.task(id: viewedActorId)` on `ProfileView`) — and on all four the tab click is **inert**, switching a stack/visibility/`activeTab` and touching no loader. **Ruling: activating `profile-tiers-tab` re-reads that tab's data on all 7 apps** — the OTHER branch's offers + viewer status, and symmetrically the SELF branch's §§1–5 — which is tui's shape and, per priority #4's *richest existing pattern* rule, a strict superset of the other three doors (the offers section is only visible while the tab is active, so a tab-activation read subsumes every page-level read for this surface). Page-level loads stay as the first load; the new door is additive. **The poll pattern was considered and rejected here**: `onboarding.md` § The pending-invite surface ratifies "poll is the channel, **structurally**" for a waiter with no push channel at all, but that justification does not transfer — a subscriber is a bearer-proven actor holding a live push connection, so polling would paper over a missing producer rather than answer a structural absence (`transport.md` § Pre-identity → No actor state is what makes the invite case different). **The push kind is the ratified end-state and is deliberately NOT this ruling**: a `fauna.subscriptions.*`-shaped member of the `*.changed` push family (the nest knows the exact grant moment — `drain_auto_approvals` and the author approve path) is what removes the user action entirely, and it is a nest producer + wire addition + seven consumers, tracked separately. The tab door is owed regardless and is not throwaway work: every `*.changed` consumer in this codebase pairs its push with a load-on-open path, because a push can be missed across a reconnect, an offline window, or a nest too old to emit the kind. **Per-app status: ALL SEVEN CONFORMANT.** tui was already conformant (reference); linux + web + android landed 2026-08-12; windows landed 2026-08-13 (`TiersTab_Click` now awaits `HydrateAsync()`); apple (macOS+iOS, one shared `ProfileView`) landed 2026-08-23 (a `tiersReloadToken` bumped on every Tiers-tab tap). The e2e helper `ActionLayer.wait_for_offer_status_after_external_grant` re-opens only the tab, not the whole profile, and the per-app `require_tiers_tab_reread_door` skip gate is deleted.

  Dated one-liners: UX ratified 2026-06-14 (Q5, profile-centric); profile shell + `fauna.profile.{get,set}` landed 2026-06-17/18; `tiers.list`/`mine.list` 2026-06-18, `offers.list` 2026-06-19; followers auto-provision (`ensure_followers_tier`, rank-0 reserved, status.get fallback rule) + encrypted-mode lazy followers period-key 2026-07-01; auto-approve pump core + linux/windows/web/android run-wiring landed through 2026-07-08 (the per-app `FOLLOWERS_TIER` literals deliberately stay compile-time constants — an immutable reserved wire name; decided 2026-07-08. **Narrowed 2026-08-22:** that ruling is bought by FFI/WASM call overhead, so it covers only the five apps that reach `fauna-core` across a door; the two **Rust-native** shells `use` the shared constant directly and keep the same compile-time semantics — tui always did, linux was corrected to match); macos/ios run-wiring followed 2026-07-12 (`SubscriptionsAuthorCadence`, shared FaunaKit, wired into both app lifecycles — see table above), closing the pump run-wiring leg on all 6 pre-parity-flip apps. tier_3: `conformance_subscription_followers.rs` (4 tests) + `conformance_subscription_tiers_list.rs` + the orchestration unit suite. **tui (the 7th app) built the Slice B OTHER-profile offers/follow leg** (M5 slice 2, 2026-07-15) and **closed the SELF author-management sections §§1–5 plus the auto-approve pump run-wiring on 2026-08-01** (`apps/fauna-tui/src/profile/tiers.rs`, `subscriptions_author.rs`), which closes the pump run-wiring leg on all 7 apps; only the consumer `subscription-settings` page stays a declared future slice there, not drift (`ui-actual-tui.yaml`).
