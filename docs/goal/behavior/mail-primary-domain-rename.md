## Goal

The admin can rename the deployment's primary domain — atomic from the admin's perspective, but with a **peer-MTA cache-flush grace window** in between an "anchor flip" and a "decommission" so the deployment never silently drops mail or breaks RFC 8058 unsubscribes during the cache transition. Bar:

1. **Existing user aliases are not migrated.** A user with `bob@old-primary` keeps `bob@old-primary` after the rename; the handle (`bob`) stays the user's deployment-wide identifier, but no automatic `bob@new-primary` alias is created. The user opts in to a `@new-primary` alias via the standard add-address flow. Per the handle-uniqueness rule of `mail-multidomain.md` § Architectural rules, no other user can claim handle `bob`, so `bob@new-primary` is reserved-for-bob-if-he-wants-it.
2. **No mail dropped during peer-cache transition.** Every peer-MTA caching surface (MX records, MTA-STS policy + TXT, TLSRPT TXT, DMARC TXT, the cert chain) gets a dual-binding window long enough for the worst-case cache TTL plus a safety margin. The default grace is 7 days; per-rename override via the `grace_days` request param (range [1, 30]). (A Tier-2 deployment-default knob `mail.primary_rename.grace_days` is **proposed, not built** — it lands with the consuming track.)
3. **No silent security regression.** The new primary already has its own DKIM/DMARC/MTA-STS published (as a regular additional domain pre-rename); the rename only re-targets the **anchor responsibilities** (MX, processor inboxes, list-unsubscribe origin, cert SAN graph). The new primary's TLS posture matches or exceeds the old primary's (validated at `start_primary_domain_rename`); rename refuses if the new primary is in `mta_sts_mode = none` while the old primary is in `enforce`.
4. **Old primary stays alive as an additional after the rename.** Demote-not-delete is the default — preserves every existing user's address, keeps RFC 8058 one-click unsubscribe working for in-flight mass-mail, lets the admin take a separate considered action on the old domain later (keep, soft-delete, or repurpose). The rename completion never auto-removes the old primary.
5. **Idempotent + abort-able.** Each RPC is retriable on network blips. The rename can be aborted up to the moment of completion; abort during grace is expensive (re-flip anchors + rewrite every TXT) but valid.

**Default-strict.** The new primary's pre-rename DKIM rotation pattern, DMARC `p=` mode, MTA-STS `mode`, and cert mode all carry over into the new primary's role — the rename is **anchor-responsibility transfer**, not a fresh policy provisioning. If the admin wants `p=none` on the new primary during a warmup window, they configure that on the new primary as an additional **before** starting the rename, not as part of it.

**Two-step admin action.** Rename is intentionally two RPCs (first `add_local_domain(<new>)` per `mail-multidomain.md`, then `start_primary_domain_rename(<new>)`). This forces the admin to verify the new domain's DKIM/DMARC/MTA-STS/cert health as an additional before committing it as primary. A one-shot "rename" RPC that did both steps would mask a half-broken new-domain provisioning behind the rename anchor flip and is forbidden.

## Lifecycle

The rename is a state machine on a single `mail_domain_renames` row. States transition under nest's control; the admin RPCs are entry points (`start`, `complete`, `abort`) and the periodic grace-window watcher promotes `grace` → `ready_to_complete` based on wall-clock.

| State | Reached by | Effect | Reversible? |
|---|---|---|---|
| `requested` | admin calls `start_primary_domain_rename(<new>)`; nest validates preconditions; inserts row | no DNS / cert / binding mutations yet; nest acks the admin | yes, `abort` is a no-op database delete |
| `cert_issuance` | nest enters at row insert; the deployment's **single managed cert** (in-process ACME HTTP-01, not certbot — see § Behavior — cert chain re-issue ordering) is widened to add the `mail.<new>` SAN, **gated on `mail.<new>` resolving to the nest** (the assembler advertises `mail.<new> A → nest` during a rename; the client publishes it; the SAN is resolve-gated exactly like a secondary apex, so an unpublished/unpropagated `mail.<new>` can never fail the all-or-nothing order and take the primary's cert down) | the managed cert gains the `mail.<new>` SAN; the MTA/HTTPS listeners keep **only the old SAN graph bound** (`mail.<new>` is dormant until anchor flip in slice 3). No second cert — one managed cert whose SAN set grew by one | yes, `abort` just narrows the desired-SAN set back (the widened cert stays valid; nothing remote to undo) |
| `cert_ready` | the cert-lifecycle loop observes the managed cert now covers `mail.<new>` (`cert_covers_sans`) | the rename row carries `new_cert_fingerprint` + `cert_acquired_at`; nest is one transaction away from the anchor flip | yes, same shape as `cert_issuance` abort |
| `anchor_flip` | the cert-lifecycle loop (SLICE 3) advances a `cert_ready` row directly to `grace` — the flip is atomic, so `anchor_flip` is the transition *name*, not a persisted resting state (§ Crash recovery) | ONE atomic transaction: flip `is_primary = false` on the old row **then** `is_primary = true` on the new row (demote-first for the exactly-one-primary partial unique index) + set rename `state = grace`, `flipped_at`/`grace_started_at = NOW()`, `grace_ends_at = NOW() + grace_days × 1 day`. After commit, runtime side effects: swap the in-memory identity projection to the new primary (`apply_primary_identity` — else `handle_domain()` stays stale and the cert loop re-orders around the old apex), and fire a `config_changed`/`local_domains` push so bridges re-fetch config + the admin client re-fetches + re-publishes the re-targeted DNS. Every per-domain record re-targets automatically because the assembler reads `is_primary` (§ Data — Mutations to per-domain DNS records); the listeners already serve both `mail.<old>`/`mail.<new>` by cert coverage (SLICE 2); the processor inboxes + `/list/unsubscribe` are deployment-wide / host-incidental no-ops (§ Behavior — TLSRPT and DMARC / RFC 8058) | yes — `abort` from grace re-runs the inverse re-flip (SLICE 4, built): one atomic transaction demotes the new row + re-promotes the old + marks `aborted`, then the identity projection swaps back and the cert narrows on its next renewal (recompute-driven, once the rename is terminal). |
| `grace` | nest enters at flip commit | dual-binding live; both old and new anchor addresses accept mail / serve HTTPS; both cert chains valid; peer caches converge on the new TXT records per their TTLs | yes — abort possible until `complete` |
| `ready_to_complete` | grace watcher detects `NOW() > grace_ends_at` | nest awaits the admin's `complete` call (no auto-decommission — the admin signs off on the cache-flush completion) | yes — abort still possible; admin may also `extend_primary_domain_rename_grace(<n>)` to push `grace_ends_at` further out |
| `completed` | admin calls `complete_primary_domain_rename()` | the rename becomes terminal and the grace keep-alives stop **by recomputation**: the DNS assembler drops the `mail.<old>` A row and the cert loop stops holding the `mail.<old>` SAN (dropped at the next natural renewal — § Behavior — cert chain re-issue ordering). `tlsrpt@<old>` / `dmarc-report@<old>` need no teardown — the standard role-address routing keeps sending them to the deployment-wide processor (§ Behavior — TLSRPT and DMARC inbound flow re-routing); the `/list/unsubscribe` endpoint stays served on the old hostname **permanently** as long as the old domain is in `local_domains` (§ Behavior — RFC 8058 unsubscribe endpoint continuation); set `completed_at = NOW()`; the rename row becomes audit-only | no — `completed` is terminal |
| `aborted` | admin calls `abort_primary_domain_rename()` from any non-terminal state | nest re-flips `is_primary` back if it was flipped (the SLICE-4 one-transaction inverse); every per-domain record re-targets back **by recomputation** (the client re-fetches + re-publishes on the `config_changed` push — the nest writes no DNS); the widened cert narrows on its next renewal; sets `aborted_at = NOW()`; the new domain stays in `mail_domains` as a regular additional (it was already an additional pre-rename) | no — `aborted` is terminal; a fresh rename starts a new row |

### Concurrency

At most one row in `(requested, cert_issuance, cert_ready, anchor_flip, grace, ready_to_complete)` at a time. The `mail_domain_renames` table enforces this with a partial unique index on `WHERE completed_at IS NULL AND aborted_at IS NULL`. A second `start_primary_domain_rename` call while one is in flight refuses with `409 rename_already_in_progress`.

### Crash recovery

Each state transition is committed to `mail_domain_renames` before/atomically-with the side effects. Recovery is **not** a persisted-failure state (there is no `provisioning_failed` column anywhere in the nest — that spec framing predates the implementation); it is **idempotent re-derivation from DB state on every cert-lifecycle tick**, the exact pattern `cert_lifecycle_loop` already uses for mail domains (it re-reads `list_active_mail_domains()` + re-derives the desired SAN set each iteration and re-issues iff the on-disk cert doesn't cover it). The rename driver rides the same loop: each tick reads `get_active_rename()` and re-enters the row's idempotent action — a row in `cert_issuance` re-asserts the `mail.<new>` SAN in the desired set + re-checks coverage (issuing only if not yet covered); a `cert_ready` row runs the **atomic anchor-flip transaction** (`is_primary` flip on both rows + `state = grace` + stamps in ONE transaction — so there is no persisted `anchor_flip` resting state; the row is either `cert_ready`, not-yet-flipped, or `grace`, flipped: a single atomic decision point); and — **on every tick, not only during a rename** — the loop **reconciles the runtime identity projection unconditionally** against the DB primary (if the in-memory `identity_domain` cache doesn't match `lookup_primary_mail_domain()`, re-apply `apply_primary_identity` + re-push `config_changed`; gated on the primary existing and being non-local, so an IP/domainless box is left untouched and the `!=` guard makes the steady state a no-op). This self-heals the projection against *any* divergence source — the flip, an abort re-flip, or a raced stale re-apply that left the cache on a since-aborted domain — so it can never stay wrong until restart. A `grace`/`ready_to_complete` row then waits for `grace_ends_at`. **Every state transition's UPDATE is state-conditional (a CAS on the expected from-state, `rows == 1` asserted, a 0-row result refused with `rename_wrong_state` — never a silent clobber):** so an admin RPC racing the lifecycle loop (a pre-flip abort racing the flip; the watcher racing an abort) loses the race cleanly with a 409 instead of stranding a half-terminal or resurrected row — the single-atomic-decision-point guarantee holds against concurrent writers, not just crashes. The one race where a CAS 0-row result is *not* a genuine wrong-state is `start`'s **own** `requested → cert_issuance` auto-advance losing to a coincident loop tick driving the *identical* transition: the rename was created and is correctly in `cert_issuance`, so `start` re-reads the row and returns it as the idempotent success it is (mirroring the loop's own tolerance — it swallows the error and re-derives next tick) rather than surfacing a spurious `409 rename_wrong_state`; any re-read state other than `cert_issuance` (e.g. a concurrent abort of the just-inserted row) still propagates the refusal, so a genuinely divergent race is never masked. A nest restart is free — the DB flip persisted, so boot's `resolve_identity_domain` re-derives the identity from the (now-new) primary row, and the loop resumes re-deriving from the persisted rename row; the grace-window `mail.<old>` keep-alive + the widened cert SAN are both re-derived each tick.

### Renaming away from a dead domain (ratified 2026-08-11)

The machine above was designed for the voluntary case — both zones live, peer caches to flush. It is also the **only** re-home path when the old primary is lapsed or seized ([`../architecture/nest/domains-and-tls-bootstrap.md`](../architecture/nest/domains-and-tls-bootstrap.md) § Domain loss owns that story), and against a dead old zone its behavior deltas are these:

- **Preconditions are unaffected, deliberately.** `start` validates the *new* domain and compares *stored* policy modes; it consults the old zone's liveness nowhere, and must never grow such a gate — a liveness precondition would wedge exactly the rename that matters most.
- **The dead-apex ACME deadlock, and its remedy (BUILT 2026-08-11).** The deployment's ACME order is all-or-nothing, and outside a rename it includes the primary apex **un-gated** (only secondaries and infra SANs carry a resolve gate). While the dead old domain is still primary, every order therefore fails — *including the `cert_issuance` order that must add the `mail.<new>` SAN* — so the rename could never reach `cert_ready` and the anchor flip never ran: a deadlock in which the machinery built to leave the dead zone was held hostage by it. The remedy is surgical: **while a rename is pre-flip, the old primary's apex and `mail.<old>` SANs are resolve-gated like secondaries** — a live old zone keeps both SANs (the voluntary case's dual-binding is untouched), a dead one drops out of the order, the widened cert issues for what actually resolves, and the flip proceeds. No new state, no new RPC; a pre-flip rename row is the license, and it is also the whole scope: post-flip the old domain is an ordinary secondary already carrying the secondary gate, and the apex is by then the *new* domain, which is never gated. **The fail direction inverts versus secondaries: DROP on uncertainty, never keep.** A secondary that cannot be strongly checked (no persisted `nest_host_address`) falls back to a weak "has any `A`/`AAAA` record" test, because a false negative there merely defers a secondary; here a false *positive* is the harm — a name that merely looks alive would stay in the all-or-nothing order and re-arm the very deadlock the gate exists to kill, with no escape left, because the rename *is* the escape. So an unknown host address drops both SANs rather than guessing; that case is already anomalous, since a rename is admin-initiated from an app whose post-auth hook persists the host address (§ Implementation status today — host-address acquisition). The gate is shared with the cert-at-risk nudge, so the nudge never flags a SAN the issuer has declined to order; the DNS-01 client path (`fauna.tls.cert_status`'s `desired_sans`) deliberately keeps reporting the un-gated set, because DNS-01 validates by publishing into the zone and the client's own credential coverage is the gate that binds there. **Abort is recompute-driven like every other narrowing:** the gate stops firing the moment the row goes terminal, so the old apex returns to the desired set and is re-covered by the next successful order — which, for a zone that is still dead, is the same "no order can succeed for this name" the box was already living with, so nothing recoverable is lost. Outside a rename nothing changes at all: a dead primary with no rename in flight keeps failing every renewal and coasting on its current cert (`../architecture/nest/domains-and-tls-bootstrap.md` § Domain loss) — starting the rename is precisely what makes an order possible again.
- **The same fail direction binds the two rename MAIL-HOST gates (ratified 2026-08-13).** The bullet above rules the old primary's *apex* SANs; the deployment gates two further names through `rename_mail_host_reachable` — the pre-flip `mail.<new>` widening and the grace `mail.<old>` keep-alive — and both now **DROP on uncertainty** rather than falling back to the weak "has any `A`/`AAAA` record" test. The reason is structural rather than an analogy to the apex: the **sole publisher** of both names, the DNS assembler's `append_rename_mail_host`, reads the *same* `nest_host_address` the gate does and is a no-op without it. So where the address was **never persisted** — the only arm a pre-flip rename can actually reach, since without `mail_ipv4` the assembler cannot publish `mail.<new>` at all and HTTP-01 could never have validated it — the deployment has published **nothing** at that name, and whatever a resolver answers there is by construction someone else's: a zone wildcard, a stale row, a squatter. There the weak test cannot produce a true positive at all; it can only produce a false one, which is why both gates drop: an unvalidatable name never enters the all-or-nothing order, because the escapes from a failing order cost the very thing in flight — abort the rename, or force-complete the grace early and surrender the peer-cache convergence grace exists to buy. **The one arm where the weak test could have been right, and why it drops anyway:** a *transient* `get_host_address` **error** during grace, where a correct `mail.<old>` record published earlier (by the ordinary apex path, back when the old domain was primary) may still be live. Dropping there costs effectively nothing — narrowing the desired set forces no re-issue, since `need_issue` keys on self-signedness, coverage and freshness and the installed cert still covers the superset, so the name returns on the next readable tick — while *keeping* on an unreadable address would leave the two gates disagreeing on the very same tick, `apex_sans_for_cycle` having already dropped the apex on that identical error. Uniform DROP is the cheaper and more legible half of that trade. Dropping is bounded and self-healing by comparison — pre-flip the rename simply waits in `cert_issuance` while every validatable SAN keeps renewing (it advances the moment the host address is persisted, which any admin connect from any of the 7 apps does); during grace, peers still on a cached `<domain> MX → mail.<old>` fail TLS to that host and **defer**, mail retrying rather than bouncing, until their cache turns over — and against the dead or seized zone this ruling guards, `mail.<old>` no longer points here at all, so no peer reaches it and the drop costs nothing. **The secondary-apex gate keeps its weak fallback and is deliberately NOT swept in:** its false positive is an admin-visible, self-inflicted misconfiguration (a secondary was added whose apex does not point here) with a proportionate escape — remove or deactivate that one domain — where both rename gates' escapes cost the rename or the grace itself. That residual stays owned by [`../architecture/nest/domains-and-tls-bootstrap.md`](../architecture/nest/domains-and-tls-bootstrap.md) § Host-address acquisition.
- **The grace window protects nothing — take the minimum.** Grace exists for peer caches to converge on records Fauna controls; a lapsed zone's records belong to the next registrant. `grace_days=1` (the range floor) is the right call, and the keep-alives aimed at the old zone (the `mail.<old>` A row, the TXT rewrites) fail at the client's DNS publish — the credential no longer controls the zone — which is noise, not harm: the assembler's desired state is simply unpublishable there, and nothing downstream gates on it.
- **Post-completion disposition differs by cause.** A *lapsed* domain may keep the demote-not-delete default (bar 4) — the rows are inert history. A *seized* domain warrants the considered soft-delete instead: the zone is hostile, so keeping `@old` addresses presented as live invites misdirected mail and false continuity claims. Either way outbound `From: @old` is already dead in practice — DKIM for a zone the deployment no longer controls cannot be published, so receivers refuse it; users move to `@new` via the standard add-address flow, their handles reserved by handle-uniqueness (bar 1).

## Behavior — peer-MTA cache invalidation

The rename's grace window is dimensioned by the longest peer-MTA cache lifetime across the surfaces below. Default grace = 7 days. The admin sees the grace duration at `start` time + can override via `start_primary_domain_rename(... grace_days=<n>)` for `n` in [1, 30]. A watcher-computed **recommended** grace (from the per-domain TXT TTLs + MTA-STS `max_age` values + the cert renewal interval, with nest warning-but-accepting a lower admin value) is **proposed, not built** — today nest accepts any in-range `grace_days` without a recommendation.

### MX invalidation

Every `<domain> MX 10 mail.<primary>` record across all `local_domains` re-targets at anchor flip: `mail.<old-primary>` → `mail.<new-primary>`. Each per-domain MX TTL is the dominant cache budget for that domain.

- **Default TTL:** 3600 s (1 hour, matching the per-domain TXT TTL convention from `mail-multidomain.md` § Per-domain DNS records).
- **Peer behavior:** an MTA caching `<domain> MX → mail.<old-primary>` keeps using the old target until its TTL expires. During grace, `mail.<old-primary>` is **still bound** to the deployment's MTA (dual-binding on the MTA listener); inbound delivery to `mail.<old-primary>:25` keeps succeeding.
- **Dual-binding mechanism (reconciled with the code, 2026-07-06):** there is **no listener hostname allowlist** — neither the Go `fauna-mail-bridge` MTA/MDA listeners nor the nest's `:443` inspect the SNI hostname. The bridge's `GetCertificate` ignores the ClientHello entirely and serves the single managed cert; the nest's `MultiDomainCertResolver` serves the apex/default managed cert for any SNI it lacks a per-web-domain cert for. So a listener accepts `mail.<x>` SNI **iff the served managed cert covers `mail.<x>`** — nothing else. SLICE 2 already widened that cert with the `mail.<new-primary>` SAN and fired a `config_changed`/`tls` push, so the bridges (which swap the cert atomically on the live listener via `TriggerRefresh`) already serve **both** `mail.<old-primary>` and `mail.<new-primary>` from `cert_ready` — before the flip. The "dual-binding" is thus a property of cert coverage, established in SLICE 2; the flip adds nothing to it. At `complete` (SLICE 4) the cert narrows to drop `mail.<old-primary>`, and only then does a peer connecting to `mail.<old-primary>:25` see a cert mismatch.
- **Cache-flush completion criterion:** after 1 × TTL (3600 s), 99.9% of peer caches have expired; after 7 × TTL (~7 hours), effectively all peers have re-resolved. The 7-day default grace gives a generous margin even for peers with bug-quirky DNS resolvers.

### DKIM invalidation (no-op)

The user-named concern in `mail-multidomain.md` § The `mail_domains` model is that "every peer MTA's cached MX / DKIM / DMARC / MTA-STS material would need to expire" during a primary rename. **This is a misconception that the rename surfaces cleanly: DKIM TXT records are per-domain, keyed by the `d=` tag (RFC 6376 §3.6), and the rename does NOT touch any domain's DKIM TXT records.** Every domain (including the old primary post-demotion + the new primary pre-promotion) keeps its own `default._domainkey.<domain>` TXT records pointing at its own keypair. Outbound messages signed by the nest during the grace window pick the DKIM key by matching the From: header domain (per `mail-multidomain.md` § Signing-key selection at outbound time); the From: domain is independent of which `mail_domains` row carries `is_primary = true`.

The rename's `cert_issuance` phase explicitly does NOT trigger DKIM rotation on any domain. A DKIM rotation during a primary rename would compound peer-cache invalidations (each domain's `default._domainkey.<domain>` cache + the per-domain MTA-STS cache + the deployment-wide MX cache all flushing on the same wall-clock window) and is forbidden — if an admin wants to rotate DKIM keys at the same time as a primary rename, they do those as two sequential, separately-grace-windowed actions.

This section is named **explicitly** so a future implementer reading `mail-multidomain.md` doesn't worry about flushing DKIM caches during a rename. There is no DKIM cache to flush.

### DMARC invalidation

Every domain's `_dmarc.<domain>` TXT record has `rua=mailto:dmarc-report@<primary>` (and possibly `ruf=mailto:dmarc-report@<primary>`, the same address unless the admin overrode `ruf_destination` — `dmarc-reporting.md` § Record shape) — these point at the **primary's** processor inbox. At anchor flip, every row's `_dmarc.<domain>` TXT is rewritten: `dmarc-report@<old-primary>` → `dmarc-report@<new-primary>` (same for `ruf=`). Peer caches per TXT TTL (default 3600 s, same as MX).

- **During grace:** peer MTAs caching the old `rua=dmarc-report@<old-primary>` keep sending DMARC aggregate reports to the old address. The MTA's RCPT TO handler routes `dmarc-report@<old-primary>` to the same deployment-wide DMARC processor as `dmarc-report@<new-primary>` (the dual-binding routing rule lives in `mail-multidomain.md` § Per-domain role-address routing — `dmarc-report@` always routes to the deployment-wide processor regardless of which domain it's addressed to, so the rename's "dual-binding" here is actually no-op already; the rename just needs to confirm the routing rule continues to fire for the old primary post-demotion).
- **Post-grace:** peer caches have refreshed; new reports go to `dmarc-report@<new-primary>`. The routing rule still accepts `dmarc-report@<old-primary>` (since the old primary remains a local domain, and the role-address rule applies to all local_domains uniformly) — so even after grace, late-cached reports keep working.
- **Cross-link:** `dmarc-reporting.md` § Multi-domain deployments — the per-domain `rua=` assembly pipeline this rewrite invokes.

### MTA-STS invalidation

Each domain's `_mta-sts.<domain>` TXT carries `id=<policy-version-hash>` (RFC 8461 §3.2). The `id=` rotates whenever the policy file at `https://mta-sts.<domain>/.well-known/mta-sts.txt` changes. At anchor flip, every domain's policy file changes (`mx: mail.<old-primary>` → `mx: mail.<new-primary>`) — so every domain's TXT `id=` rotates simultaneously.

- **Peer behavior:** an MTA caching `_mta-sts.<domain>` TXT with the old `id=` re-fetches the policy file when it next consults MTA-STS for that domain (typically each delivery attempt, with a short TXT TTL allowing rapid id-change detection). On re-fetch, the new policy file has `mx: mail.<new-primary>` — the peer learns the new MX target. Peers that don't re-check between the TXT-cache expiry and a delivery attempt fall back to MX-record resolution (which is itself dual-targeted during grace per § MX invalidation above).
- **Policy `max_age` interaction:** the policy file's `max_age` field (default 86400 s = 1 day per `mail-multidomain.md` § Per-domain MTA-STS) governs how long an MTA caches the policy *content*. A peer caching an `enforce`-mode policy with `mx: mail.<old-primary>` for `max_age` seconds will refuse to deliver to anything other than `mail.<old-primary>` during that window. During grace, the deployment's MTA listener binds **both** `mail.<old-primary>` and `mail.<new-primary>` — so STARTTLS connections to either target succeed against the dual-cert chain.
- **The grace window dimensioning:** `grace_ends_at` ≥ NOW() + `max(mta_sts_max_age_seconds over all local_domains)` + safety margin. Default 7 days against a default 86400 s policy max_age is 7 ×; a deployment with a 7-day MTA-STS policy max_age needs `grace_days ≥ 14` (the watcher's recommendation surfaces this).
- **Policy-file server during grace:** the HTTPS dispatcher (per `mail-multidomain.md` § Policy-file server) handles `https://mta-sts.<each-domain>/.well-known/mta-sts.txt` requests. During a rename, the assembled policy file's `mx:` line is taken from the **new primary** for any domain (the flip already committed). **Caveat — the managed cert carries NO `mta-sts.<each>` SANs today** (§ Behavior — cert chain re-issue ordering; the `mta-sts.` host SANs ride the deferred cert-mode dispatcher, a cluster-#4 / tls-certificates.md follow-up), so TLS on the `mta-sts.<domain>` hosts is the dispatcher's concern, not the rename's. Once those SANs exist, the cert covers both `mta-sts.<old-primary>` and `mta-sts.<new-primary>` and a peer fetching via the old `_mta-sts.<old-primary>` TXT id succeeds and reads the policy listing `mail.<new-primary>` (also the peer's current MX target if their MX cache has updated, or covered by the MTA-listener's dual-binding if not).
- **Cross-link:** `mail-multidomain.md` § Per-domain MTA-STS — the per-domain policy file shape this rewrite preserves on each domain.

### TLSRPT TXT invalidation

Each domain's `_smtp._tls.<domain>` TXT carries `rua=mailto:tlsrpt@<primary>` per RFC 8460 §3. At anchor flip, every row is rewritten: `tlsrpt@<old-primary>` → `tlsrpt@<new-primary>`. Peer caches per TXT TTL.

- **During grace:** peer-generated TLSRPT reports addressed to `tlsrpt@<old-primary>` route to the deployment-wide processor (same rule as DMARC above — the role-address `tlsrpt@` resolves to the processor regardless of which local_domain hosts it). Reports addressed to `tlsrpt@<new-primary>` go to the same processor.
- **Post-grace:** the old primary stays in `local_domains` (the rename doesn't remove it), so `tlsrpt@<old-primary>` continues to route to the processor indefinitely. Late-cached reports keep working.

### Cache budget summary

| Surface | Cache lifetime (peer-side) | Re-fetch trigger | Dual-binding during grace |
|---|---|---|---|
| MX records | per-domain MX TTL (default 3600 s) | DNS resolver expiry | Yes — MTA listener binds both `mail.<old>` and `mail.<new>` |
| DKIM TXT | per-domain TXT TTL (default 3600 s) | DNS resolver expiry | N/A — no DKIM record changes during a rename |
| DMARC TXT | per-domain TXT TTL (default 3600 s) | DNS resolver expiry | Routing rule pre-existing — `dmarc-report@<any-local-domain>` always routes to processor |
| MTA-STS TXT | per-domain TXT TTL (default 3600 s) | DNS resolver expiry | N/A — TXT carries id-hash; policy file content is the dual-binding |
| MTA-STS policy | per-policy `max_age` (default 86400 s) | id-hash change in TXT | Policy content re-targets at flip (assembled-on-read); `mta-sts.<domain>` HTTPS serving awaits the deferred cert-mode dispatcher (no `mta-sts.*` SANs on the managed cert today) |
| TLSRPT TXT | per-domain TXT TTL (default 3600 s) | DNS resolver expiry | Routing rule pre-existing — `tlsrpt@<any-local-domain>` always routes to processor |
| ACME cert chain | cert validity (default 90 days for Let's Encrypt) | renewal cycle | Dual-binding — both `mail.<old>` and `mail.<new>` SANs in the cert |

The grace window default of 7 days covers the dominant cache budget (MTA-STS `max_age`) at default settings with a comfortable margin. Admins running non-default MTA-STS `max_age` see a recommended `grace_days` that scales with their longest cache.

## Behavior — cert chain re-issue ordering

> **Mechanism (reconciled with the code, 2026-07-05).** The nest has **no certbot subprocess and no DNS-01 path** (DNS-01 was removed with the nest-never-writes-DNS decision, 2026-05-25). TLS is served by **one** deployment-managed cert (`fullchain.pem` under `acme_dir`) issued by the **in-process ACME HTTP-01 lifecycle loop** (`bins/fauna-nest/src/acme_http01.rs` `cert_lifecycle_task`), whose SAN set is `desired_san_domains(apex, reachable_mail_domains(...), include_relay_san)` re-derived from DB state every ~5-min tick. (Earlier drafts used "certbot" as shorthand for this loop; the term survives only in historical notes — there is no second cert and no shell invocation.) Two consequences the certbot framing hid: **(a)** `mail.<new-primary>` currently has **no DNS record** (a secondary publishes only its apex `A → nest`; `desired_san_domains` deliberately never emits `mail.<secondary>`, and the assembler builds no `mail.<secondary>` A row — `dns_handlers.rs`/`libs/fauna-mail/src/dns/host.rs`), and HTTP-01 needs `mail.<new-primary>` to resolve to the nest to answer the challenge; and **(b)** the ACME order is **all-or-nothing** — an unresolvable SAN fails the whole order and would take the *primary's* cert down. So SLICE 2 must (1) advertise `mail.<new-primary>` `A → nest` in the assembled record set **during a rename** so the client publishes it, and (2) **resolve-gate** that SAN into the order (defer until it resolves to the nest), exactly as `reachable_mail_domains` already gates secondary apexes. The `mta-sts.<each>` SANs the prose below assumes are **not built today** — the real cert carries `apex + mail.<apex> + each reachable secondary apex + optional relay.<apex>` only.

The deployment's managed cert covers (pre-rename): the apex `<old-primary>` + `mail.<old-primary>` (the single MX host) + each reachable secondary apex `<additional>`. The new primary, as an additional pre-rename, already contributes its own apex `<new-primary>` SAN; the rename adds exactly **one** new SAN: `mail.<new-primary>` (the new MX host). The re-issue is staged across the lifecycle:

### Pre-flip (states `cert_issuance` → `cert_ready`)

On entering `cert_issuance`, the lifecycle loop widens the single managed cert's desired-SAN set to include `mail.<new-primary>`, i.e. the desired set becomes the current set **plus** that one name:

```
desired SAN set during cert_issuance/cert_ready =
  <old-primary>                (apex, unchanged)
  mail.<old-primary>           (current MX host, unchanged)
  <each reachable secondary>   (unchanged, incl. <new-primary>'s apex)
  mail.<new-primary>           (NEW — the only addition)
```

- The loop replaces the managed cert **in place** (`issue()` obtains-then-writes, no delete-first) with one carrying the union; the old SAN graph stays valid throughout. **Prerequisite — `mail.<new-primary>` must resolve to the nest first:** during a rename the assembler emits a `mail.<new-primary>` `A/AAAA → nest` row (mirroring how the primary's `mail.<primary>` row is built by `append_host_records`), the client reconciles it, and the SAN is **resolve-gated** (a new `mail.<x>`-host gate reusing the `reachable_mail_domains` / `secondary_apex_resolves_to_nest` shape — a strong match against `nest_host_address.mail_ipv4`, and **strong-check-or-DROP** with no weak fallback when that address is unpersisted, per § Renaming away from a dead domain; see § Implementation status today for the host-address dependency). Until `mail.<new-primary>` resolves, the SAN is **deferred** (the row stays in `cert_issuance`) and the primary's cert is untouched — the rename simply waits.
- **The new primary's mail server is not the MX target until anchor flip — but this is a *DNS-targeting* fact, not a listener-binding one** (reconciled 2026-07-06). Every domain's `MX` still points at `mail.<old-primary>` until the flip (the assembler keys the MX target on `is_primary`), so no peer connects to `mail.<new-primary>:25` pre-flip. There is **no** SNI hostname allowlist gating it: the managed cert already covers `mail.<new-primary>` at `cert_ready`, and the listeners serve any SNI the cert covers (§ Behavior — peer-MTA cache invalidation, Dual-binding mechanism), so a STARTTLS handshake *to* `mail.<new-primary>` would in fact succeed — there is simply no reason for a peer to attempt one until the MX flips. The flip re-targets the MX (via the `is_primary` recompute), which is what makes the new primary "live" as a mail destination.
- **SAN-cap check (aspirational today).** `start_primary_domain_rename` refuses with `409 cert_san_limit_exceeded` when the post-rename SAN graph would exceed Let's Encrypt's 100-SAN cap. The slice-1 check computes `2 + 2 × N` (N = active local domains), a formula that assumes `mta-sts.<each>` SANs which **are not built** (`desired_san_domains` emits none) — so the real cert carries far fewer SANs and the check is **conservative** (refuses earlier than strictly necessary), harmlessly forward-compatible for when `mta-sts.<each>` SANs do land. It is not a description of today's cert.

### At-flip (state `anchor_flip`)

The flip itself is the atomic `is_primary` transaction (no TXT rewrites — those are assembled-on-read; § Data). The listener side is **already handled by cert coverage from SLICE 2** — there is no per-flip listener-binding step:

1. The nest's `:443` (`MultiDomainCertResolver`) and the Go bridge's MTA/MDA listeners both serve **any** SNI the single managed cert covers, with no hostname allowlist. That cert has covered both `mail.<old-primary>` and `mail.<new-primary>` since `cert_ready` (SLICE 2 widened it + pushed `config_changed`/`tls`, and the bridge swapped it atomically on the live listener).
2. So STARTTLS/TLS handshakes to either `mail.<old-primary>` or `mail.<new-primary>` already succeed at flip time; the flip does not touch the listeners. To be safe against a cert renewal narrowing the SAN set during a long grace, the loop **keeps `mail.<old-primary>` in the desired SAN set** while the rename is post-flip non-terminal (§ During grace).
3. The in-process ACME lifecycle loop continues to renew the superset cert on its normal cadence.

The transaction commits → the row is in `grace`; the flip driver then swaps the identity projection + pushes `config_changed`/`local_domains`.

### During grace (state `grace` → `ready_to_complete`)

Both anchor hostnames remain served by cert coverage. The managed cert stays a **superset** (both `mail.<old-primary>` and `mail.<new-primary>` SANs) throughout grace because the cert-lifecycle loop, while the rename is post-flip non-terminal, **adds `mail.<old-primary>` to the desired SAN set** — mirroring how SLICE 2 adds `mail.<new-primary>` pre-flip. Without this, the post-flip desired set (apex = new primary, `mail.<new>`, old primary as a secondary apex) would omit `mail.<old>`, and the next renewal would narrow it away mid-grace. The loop does NOT reduce the SAN graph during grace; the narrow to drop `mail.<old-primary>` happens only at `complete` (SLICE 4).

### Post-complete (state `completed`)

> **Mechanism (reconciled with the code, 2026-07-06, SLICE 4).** There is no certbot and no forced re-issue at `complete`. `complete_primary_domain_rename` simply makes the rename **terminal** (`state = completed`); this is what narrows the graph, by **recomputation**: once terminal, `get_active_rename()` returns None, so the grace-window keeps stop — the DNS assembler drops the `mail.<old-primary>` A row (a `config_changed`/`local_domains` push prompts the client to re-fetch + reconcile) and the cert-lifecycle loop no longer adds `mail.<old-primary>` to the desired SAN set, so the **next natural renewal** issues a cert without it. The nest does **not** force an ACME issuance at `complete` — keeping `mail.<old-primary>` as an extra SAN until the renewal is harmless (the old domain stays a local domain), and a forced narrow would burn an issuance against Let's Encrypt's success-side limits for no functional gain.

The post-complete desired-set delta, relative to grace:

- **Dropped:** `mail.<old-primary>` (the grace keep-alive ends at terminal state).
- **Kept:** the new apex `<new-primary>` + `mail.<new-primary>` (now the primary pair); `<old-primary>` (still a reachable secondary apex — the old domain remains a local domain by default); each other reachable secondary apex; the optional relay SAN. (No `mta-sts.<each>` SANs exist today — deferred cert-mode dispatcher, § pre-flip mechanism note.)

The HTTPS dispatcher keeps serving on the old apex (its SAN remains, so the assembled MTA-STS policy — now listing `mx: mail.<new-primary>` — stays fetchable where the dispatcher serves it). A peer attempting STARTTLS to `mail.<old-primary>:25` after the renewal-driven narrow sees a cert mismatch (or nothing resolvable, once the client withdraws the `mail.<old>` A record). The reduced desired set is the **post-rename steady state** the deployment carries forward; future `add_local_domain` calls run against this baseline.

### Cert mode interaction

The doc above assumes the deployment's default `expand_primary` cert mode. Deployments using `wildcard` or `per_host` cert modes on some domains have a slightly different invocation but the same staging:

- **`wildcard` domain unchanged by rename:** a domain on a wildcard cert (`*.<that-domain>` covering its `mta-sts.<that-domain>`) is unaffected by the primary rename. Its wildcard cert is a separate cert lineage and doesn't enter the rename's SAN-graph rewrite. (Cert-mode topologies other than `expand_primary` ride the deferred cert-mode dispatcher — `mail-multidomain.md` § The `mail_domains` model.)
- **`per_host` domain unchanged by rename:** same — a domain with its own single-SAN cert is unaffected.
- **The new primary must be `expand_primary` cert mode.** If the admin added the new primary as `wildcard` or `per_host`, the rename refuses at `start_primary_domain_rename` with `409 new_primary_cert_mode_must_be_expand_primary` — the primary anchors the managed cert that the additionals' apex SANs piggyback on (and the deferred `mta-sts.<each>` SANs would). The admin must `update_local_domain_config(<new-primary>, cert_mode = expand_primary)` first.

### Cert mode for the demoted old primary

After `complete`, the old primary remains an additional. Its apex `<old-primary>` SAN stays on the managed cert (a reachable secondary apex); its `mail.<old-primary>` SAN is gone after the next renewal. The old primary's cert mode silently transitions to `expand_primary` (it's now an additional, and the cert covers it via the superset). If the admin later wants to put the old primary on its own `wildcard` or `per_host` cert, they call `update_local_domain_config(<old-primary>, cert_mode = ...)` post-completion — that's an additional-domain admin action, not part of the rename.

## Behavior — TLSRPT and DMARC inbound flow re-routing

The processor inboxes for inbound TLSRPT aggregate reports + inbound DMARC aggregate reports (and forensic reports if enabled) are deployment-wide singletons per `mail-multidomain.md` § Per-domain TLSRPT and § Per-domain DMARC. Pre-rename, peers send reports to `tlsrpt@<old-primary>` / `dmarc-report@<old-primary>` per the `_smtp._tls.<each-domain>` / `_dmarc.<each-domain>` TXT `rua=`/`ruf=` fields, which all point at the old primary.

### The routing rule that handles this for free

The rule's mechanics are owned by `mail-multidomain.md` § Per-domain role-address routing (`tlsrpt@`/`dmarc-report@` always route to the deployment-wide processor for any local domain, per-domain overrides ignored). **The rename-boundary claim this doc owns:** as long as the old primary remains in `local_domains` (the default — `complete` doesn't remove it), that rule keeps routing `tlsrpt@<old-primary>` / `dmarc-report@<old-primary>` to the processor — **forever**, not just during grace. Peer caches of the old `rua=` value keep delivering successfully.

### What changes at anchor flip

At anchor flip every domain's `rua=` re-targets (recomputed on read, § Data — Mutations to per-domain DNS records) from `<old-primary>` to `<new-primary>`. Peers that re-fetch the TXT see the new `rua=`; peers caching the old `rua=` keep delivering to the old address. Both work because of the routing rule above.

The processor inbox doesn't get a "dual-binding" in the dispatcher's sense — it's already the destination for `tlsrpt@<any-local-domain>`. The rewrite is purely a DNS-side update so new peer queries advertise the new primary as the canonical destination.

### What happens at `complete`

Nothing special for these flows — the routing rule keeps firing. The processor inbox accepts mail addressed to `tlsrpt@<old-primary>` and `tlsrpt@<new-primary>` alike. If the admin later soft-deletes the old primary via `remove_local_domain(<old-primary>)`, that's the moment the MTA stops accepting mail to the old address (per `mail-multidomain.md` § Removing a local domain) — and at that point, late-cached peer TLSRPT/DMARC reports addressed to the old primary start bouncing. The admin owns the tradeoff: keeping the old primary as an additional preserves report-receipt forever; removing it loses late-cached reports after the 30-day soft-delete window.

### Cross-doc consistency

The rename does NOT change the role-address routing rule itself. `mail-multidomain.md` § Per-domain role-address routing is the authority for that rule and stays unchanged. This doc just confirms the routing rule's behavior across the rename boundary so a future implementer doesn't reinvent dual-binding for these flows.

## Behavior — RFC 8058 unsubscribe endpoint continuation

`mail-mass-mailing.md` § RFC 8058 one-click unsubscribe specifies the HTTPS endpoint at `https://<primary-domain>/list/unsubscribe?t=<token>`. The token is HMAC-derived + globally unique (192 bits per `mail-mass-mailing.md` § Token format) and identifies the `(list_id, member_id)` pair via nest's token store — the **hostname is incidental** to the token validation. The endpoint serves the same handler regardless of which hostname the request arrived on.

### During grace

The HTTPS dispatcher binds `<old-primary>` and `<new-primary>` simultaneously (both routes covered by the superset cert per § Behavior — cert chain re-issue ordering). A peer's MUA POSTing to `https://<old-primary>/list/unsubscribe?t=<token>` succeeds; same for the new primary. Mass-mail in flight pre-rename emitted headers with the old primary URL — those keep working.

### Mass-mail emitted during grace

The mass-mailing pipeline reads `mail_domains WHERE is_primary = true` to build the unsubscribe URL header. During grace (post-flip), it emits headers with `<new-primary>` — outbound messages from this point have the new URL. Some recipients of pre-flip mass-mail may receive AND attempt to unsubscribe from post-flip mass-mail at different addresses for the same list; both succeed (tokens are globally unique, hostname-independent).

### Post-complete: permanent binding on the old hostname

`complete_primary_domain_rename` does **NOT** un-bind the `/list/unsubscribe` endpoint on the old hostname. As long as the old primary remains in `local_domains` (the default — rename doesn't remove it), the HTTPS dispatcher continues to serve `/list/unsubscribe` requests on `<old-primary>`. This is the post-grace continuation rule:

- **Why:** in-flight mass-mail emitted with the old primary URL may sit in recipient inboxes for weeks or months before they click unsubscribe. Breaking RFC 8058 one-click for already-sent mail is a permanent regression that violates the deployment's outbound-deliverability contract.
- **Cost:** zero functional — the same handler runs regardless of hostname. The endpoint binding on the old hostname is a single line in the HTTPS dispatcher's hostname-allowlist that stays present as long as the domain row exists.
- **When the continuation ends:** if the admin later soft-deletes the old primary via `remove_local_domain`, the old hostname's HTTPS routes are dropped per `mail-multidomain.md` § Removing a local domain. The admin accepts the late-arriving-unsubscribe regression as the cost of removing the domain.

### Cross-doc note

`mail-mass-mailing.md` says the unsubscribe URL is "one HTTPS endpoint regardless of how many local domains the deployment has" — this remains accurate post-rename: the deployment has ONE `<primary-domain>` for new mass-mail, and the post-rename endpoint at `<old-primary>` is a continuation binding (not a parallel endpoint emitted in fresh headers). The two facts compose; this doc adds the continuation rule, mass-mailing keeps the emission rule.

## Behavior — handle uniqueness preservation

The handle-uniqueness rule from `mail-multidomain.md` § Architectural rules ("a user's handle is unique across the deployment's user table") is **deployment-wide and unaffected by the rename**. A user with handle `bob` and signup-alias `bob@<old-primary>` retains the handle through the rename + retains the existing alias row. No alias migration is performed.

### What the user sees post-rename

- Their primary alias is still `bob@<old-primary>`. Sending mail with `MAIL FROM: bob@<old-primary>` continues to work (the old primary is now an additional with its own DKIM/DMARC/MTA-STS, all unchanged from pre-rename).
- The deployment's onboarding domain for new signups is now `<new-primary>`. New users signup as `<handle>@<new-primary>`.
- The user can claim `bob@<new-primary>` via the standard add-address flow (creating an `account_aliases` row with `kind = exact, pattern = bob, local_domain = <new-primary>`). The handle-uniqueness rule reserves the handle for the user across all local_domains, so the add is unconflicted — but it's an opt-in, not automatic.

### Why not auto-migrate

Auto-migration would:
- Create surprise — the user's "primary" address would change without their consent.
- Break peer-cached delivery — peers caching the user's address (e.g., in correspondents' contact lists) would keep sending to `bob@<old-primary>`, which still works because the old primary stays a local domain; if we auto-migrated and the admin later removed the old primary, peers' caches would break delivery.
- Conflate two orthogonal concerns: "this deployment renamed its public face" (the rename) vs. "this user wants their address to follow" (a separate, per-user decision).

The long-term-defensible answer is to keep these two concerns separate: the rename moves anchor responsibilities; user-level address migration is a per-user opt-in via existing mechanisms.

### Reserved-but-empty: the `<handle>@<new-primary>` slot

Per the handle-uniqueness rule, the new-primary slot for an existing user's handle is **reserved-for-that-user**. A different user attempting to claim `bob@<new-primary>` (assuming handle `bob` exists somewhere in the deployment) gets a `409 handle_reserved` error — same shape as the existing rule. The rename doesn't relax this — `bob` is `bob`'s handle across both primary hostnames.

### Display-handle interaction

User-facing strings that render a user's handle as `<handle>@<primary-domain>` (e.g., the profile-display short form per the existing convention in onboarding) read the **current** primary at render time. So pre-rename, bob's profile shows `bob@<old-primary>`; post-rename, it shows `bob@<new-primary>` — even though bob hasn't added a `<new-primary>` alias. This is the **display convention** following the primary, not a per-user address change. If bob hasn't claimed `bob@<new-primary>`, mail to that address bounces (no resolver hit) — the display is aspirational, not addressable.

The Tier 2 knob `ui.profile_display_handle_uses_signup_domain` (a new knob this doc names, default `false`) lets a deployment opt for "show the signup domain, not the current primary" — useful for deployments where rename is a one-off transition and the existing users prefer their signup-domain identity to be visible. Adding this knob is the consuming-track's commit, not this doc.

## Data — the `mail_domain_renames` model

A new table tracking in-flight + completed primary-rename actions.

### Row shape

| Column | Type | Notes |
|---|---|---|
| `rename_id` | UUID | primary key |
| `old_primary_domain_id` | UUID | FK → `mail_domains(domain_id)`. Set at row insert; the `is_primary = true` row at start time. Immutable after insert. |
| `new_primary_domain_id` | UUID | FK → `mail_domains(domain_id)`. Set at row insert; must be a current additional (`removed_at IS NULL AND is_primary = false`) with cert mode `expand_primary` and TLS posture ≥ old primary's at start time. Immutable after insert. |
| `state` | TEXT | enum: `requested`, `cert_issuance`, `cert_ready`, `anchor_flip`, `grace`, `ready_to_complete`, `completed`, `aborted`. Constraints: only one row in non-terminal state at a time (partial unique index). |
| `started_at` | TIMESTAMP | NOT NULL, set at row insert |
| `grace_days` | INTEGER | NOT NULL, value at start time; carried for audit; range [1, 30] |
| `cert_acquired_at` | TIMESTAMP | nullable; set when state transitions to `cert_ready` |
| `new_cert_fingerprint` | TEXT | nullable; SHA-256 of the new cert at acquisition; carried for audit + crash recovery (so a restart can recognize the already-acquired cert) |
| `flipped_at` | TIMESTAMP | nullable; set when state transitions to `grace` |
| `grace_started_at` | TIMESTAMP | nullable; equal to `flipped_at` in the steady case; tracked separately to allow `extend_primary_domain_rename_grace` to mutate `grace_ends_at` without losing the original flip-time |
| `grace_ends_at` | TIMESTAMP | nullable; set at flip; equals `grace_started_at + grace_days × 1 day`; can be pushed out by `extend_primary_domain_rename_grace` |
| `ready_to_complete_at` | TIMESTAMP | nullable; set when state transitions to `ready_to_complete` (typically equal to `grace_ends_at`) |
| `completed_at` | TIMESTAMP | nullable; set at `complete` |
| `aborted_at` | TIMESTAMP | nullable; set at `abort` |
| `abort_reason` | TEXT | nullable; admin-provided string at `abort` for audit |
| `initiated_by_actor_id` | UUID | NOT NULL; the admin who started the rename; carried for audit |

Constraints:

- `(state)` partial unique on `WHERE state NOT IN ('completed', 'aborted')` — at most one in-flight rename at a time.
- `(old_primary_domain_id != new_primary_domain_id)` CHECK.
- `(completed_at IS NULL OR aborted_at IS NULL)` CHECK — completed and aborted are mutually exclusive terminal states.
- `(state = 'completed' → completed_at IS NOT NULL)` and `(state = 'aborted' → aborted_at IS NOT NULL)` enforced by the state-machine validator at update time.

Indexes:

- `(state) WHERE state NOT IN ('completed', 'aborted')` — the grace watcher's hot path (find the active rename to advance).
- `(grace_ends_at) WHERE state = 'grace'` — the watcher's wakeup query.
- `(initiated_by_actor_id, started_at DESC)` — admin audit page enumeration.

### Mutations to `mail_domains`

The rename mutates `mail_domains` exactly twice:

1. **At anchor flip (state → `anchor_flip` → `grace`):** atomic update of two rows:
   - `UPDATE mail_domains SET is_primary = false WHERE domain_id = <old>` (demote-first)
   - `UPDATE mail_domains SET is_primary = true WHERE domain_id = <new>`
   
   The two updates are in one transaction with the `mail_domain_renames` state update (→ `grace` + the flip/grace stamps). Order matters: the old row is demoted **before** the new row is promoted, so the `mail_domains` exactly-one-primary partial unique index (`WHERE removed_at IS NULL AND is_primary = 1`) never sees two primaries mid-transaction. Atomicity is the underlying database's transaction guarantee. There is **no** per-domain TXT rewrite or listener-binding step inside the transaction — those are not nest-written (see § Data — Mutations to per-domain DNS records + § Behavior — peer-MTA cache invalidation). **Runtime projection:** the deployment's identity domain is an in-memory projection of the primary row (`identity_domain_core::apply_primary_identity`; `handle_domain()` reads a lock-free cache), so immediately after the transaction commits the flip driver calls `apply_primary_identity(<new-primary>)` to swap that cache — otherwise the cert-lifecycle loop keeps ordering the cert around the old apex while DNS points at the new primary.

2. **At abort from `grace` or `ready_to_complete`:** the inverse — ONE atomic transaction demotes the new row + re-promotes the old (demote-first, the mirror of the flip) + sets `state = 'aborted'` (`abort_rename_from_grace`). After commit: the identity projection swaps back (`apply_primary_identity(<old>)`) and a `config_changed`/`local_domains` push prompts the client to re-fetch + re-publish — every per-domain record re-targets back **by recomputation**, and the cert narrows on its next renewal. No TXT writes, no listener step (neither exists — § Data — Mutations to per-domain DNS records + § Behavior — peer-MTA cache invalidation); costly only in that the peer-cache flush runs twice.

No other mutations to `mail_domains` happen during a rename. The DKIM blob references, the per-domain config rows, the alias rows — all untouched.

### Mutations to per-domain DNS records

> **Mechanism (reconciled with the code, 2026-07-06).** The nest **never writes DNS** (`dns-management.md`; nest-never-writes-DNS): there is no "DNS provider write path" and no per-row rewrite rate-limit in this codebase. The per-domain records are **assembled on read** by `dns_handlers::assemble_domain_views` → `build_domain_view`, which sources every primary-anchored value — the `<domain> MX 10 mail.<primary>` target, the MTA-STS policy `mx:` line (and thus its TXT `id=` hash), the TLSRPT `rua=tlsrpt@<primary>`, the DMARC `rua=`/`ruf=@<primary>` — from `lookup_primary_mail_domain()` (the `is_primary = true` row). The **client** fetches `fauna.dns.list_records` and reconciles the zone. So the anchor flip does **not** "rewrite" any record: flipping `is_primary` on the two `mail_domains` rows makes the assembler recompute every domain's records against the **new** primary automatically, and a `config_changed` push (reason `local_domains`) prompts the admin client to re-fetch + re-publish. The four record types below are therefore **re-targeted by the flip, not written by the nest**.

At anchor flip, every domain's records re-target from the old to the new primary — computed, not written:

- `<domain> MX 10 mail.<primary>` — the priority-10 MX target recomputes to `mail.<new-primary>`.
- `_mta-sts.<domain> TXT "v=STSv1; id=<hash>"` — the policy file's `mx:` line changes, so the assembled `id=` hash rotates.
- `_smtp._tls.<domain> TXT "v=TLSRPTv1; rua=mailto:tlsrpt@<primary>"` — the `rua=` recomputes to the new primary.
- `_dmarc.<domain> TXT "<assembled-record>"` — re-assembled per `dmarc-reporting.md`'s pipeline; `rua=`/`ruf=` recompute to the new primary.

**Grace-window `mail.<old>` keep-alive.** Post-flip the old primary becomes a secondary, whose assembled record set drops its `mail.<old-primary>` A row (a secondary emits only its apex `A → nest`). But peers holding a cached `<domain> MX → mail.<old-primary>` must still resolve `mail.<old-primary>` during grace. So while a rename is post-flip non-terminal, the assembler **keeps emitting** `mail.<old-primary>` `A/AAAA → mail-host` for the old-primary domain (symmetric to the pre-flip `mail.<new>` emission), so the client keeps it published until `complete` narrows it away. This is the DNS half of the grace-window dual-binding; the cert half keeps `mail.<old>` as a SAN (§ Behavior — cert chain re-issue ordering).

No new DNS credentials or providers are involved — there are none; the nest only assembles the desired-state record set the client reconciles.

### Cross-table cascade

The `mail_domain_renames` row references both old + new `mail_domains` rows by `domain_id`. If a future `remove_local_domain` against either domain is attempted while a rename references the row in a non-terminal state, `remove_local_domain` refuses with `409 domain_in_rename_flight` (built). The **target** FK shape is `ON DELETE SET NULL` (preserving the rename row in audit form, with the referenced `domain_id` columns nulled) — **deferred, not built**: today the rename stores plain BLOB ids with no FK, and a post-terminal dangling audit id is tolerated (`lookup_mail_domain_by_id` handles a missing domain; § Implementation status today). The long-term-defensible call either way: never lose the audit row; lose the back-link instead.

## Architectural rules

- **The new primary must exist as an additional before rename starts.** No one-shot "add + promote" RPC; the admin runs `add_local_domain(<new>)` first, verifies the new domain's health as an additional, then runs `start_primary_domain_rename(<new>)`. Two-step is forced to make the verification mandatory.
- **At most one rename in flight at a time.** Enforced by the partial unique index on `mail_domain_renames.state`. Sequential renames are valid (each must reach a terminal state before the next starts); parallel renames are forbidden.
- **The old primary stays in `local_domains` after `complete` by default.** The rename is anchor-responsibility transfer, not domain removal. The admin separately decides whether to keep, soft-delete, or repurpose the old primary post-completion.
- **DKIM keys are not rotated as part of the rename.** Per-domain DKIM rotation is orthogonal; bundling them is forbidden (it compounds peer-cache flushes on the same wall-clock window). An admin wanting both does them sequentially.
- **Cert SAN-graph stays a superset throughout grace.** The cert covers both `mail.<old>` and `mail.<new>` SANs — alongside the apex + reachable-secondary-apex set (no `mta-sts.<each>` SANs exist today; deferred cert-mode dispatcher) — until `complete`. Post-completion, the SAN graph shrinks to drop `mail.<old>` only.
- **Per-domain DNS records re-target at flip by recomputation, not a write.** The nest never writes DNS: flipping `is_primary` makes `assemble_domain_views` recompute every domain's records against the new primary, which the client re-fetches (`config_changed`/`local_domains`) and reconciles. There is no per-row rewrite and thus no rewrite rate limit to bypass (the earlier "rate-limit lifted during the flip transaction" prose described a provider-write model this codebase does not have).
- **TLSRPT and DMARC processor-inbox routing is unchanged by rename.** Both flows are deployment-wide singletons accessible at `<role>@<any-local-domain>` per the existing role-address routing rule. The rename rewrites TXT `rua=` fields to point at the new primary; the routing rule itself is not touched.
- **The `/list/unsubscribe` HTTPS endpoint binds on the old primary hostname permanently after rename completion** (as long as the old primary remains in `local_domains`). Late-arriving one-click unsubscribes from pre-rename mass-mail keep working.
- **Handle uniqueness is preserved across the rename.** A user's handle is deployment-wide; the rename does not migrate aliases. The user's existing addresses on the old primary continue to work indefinitely (as long as the old primary remains in `local_domains`).
- **The grace-window watcher is the source-of-truth for state advancement past `grace`.** No admin action is required to transition `grace → ready_to_complete`; the watcher polls on `grace_ends_at` and promotes the state. The admin's `complete` call is required to transition `ready_to_complete → completed` — the admin signs off on the cache-flush completion.
- **Cert renewals during grace continue to use the superset SAN graph.** The lifecycle loop re-derives the desired SAN set from DB state on every tick — the post-flip keep-alive adds `mail.<old>` while the rename is non-terminal — so a mid-grace renewal re-issues the superset. It never reads the current cert's SAN list as the source of truth; no special-case is needed for renewals during grace.
- **The rename row is preserved for audit forever.** Completed and aborted rows stay in `mail_domain_renames` indefinitely. The admin can query the deployment's rename history via `list_primary_domain_renames` for compliance / debugging. Domain rows referenced by the rename can be removed independently; the target FK shape is `ON DELETE SET NULL` to preserve the audit row (deferred — plain ids + tolerant lookup today, § Implementation status today).
- **Abort from a post-flip state is expensive but always valid.** The one-transaction inverse re-flip; records re-target back by recomputation and the client re-publishes. Costly because it doubles the peer-cache flush; valid because the alternative — being stuck in a partially-renamed state because abort wasn't possible — is worse for the admin.

## Don't do these

- **Don't auto-migrate user aliases.** Each user's existing `account_aliases` row on the old primary stays put. The deployment-wide handle-uniqueness rule reserves the new-primary slot for the same user, but the user must opt-in via the standard add-address flow. Auto-migration would surprise users and break peer-cached delivery.
- **Don't combine the rename with DKIM rotation.** Two independent peer-cache flushes on the same wall-clock window compound into a single longer grace window that's hard to dimension. Run sequentially or refuse the bundle.
- **Don't auto-soft-delete the old primary at `complete`.** The old primary remains a regular additional with its addresses intact. The admin separately decides removal; the rename completion never removes domains.
- **Don't allow `add_local_domain + start_primary_domain_rename` in one RPC.** The two-step is intentional — the admin must verify the new domain's health as an additional before promoting it. A one-shot RPC would mask half-broken new-domain provisioning behind the anchor flip.
- **Don't shrink the cert SAN graph during grace.** The superset cert (old + new SANs) is the dual-binding mechanism for peer-cached MTA-STS policies that still list `mail.<old-primary>`. Shrinking before peer caches expire would cause STARTTLS failures.
- **Don't allow the rename to violate the TLS-posture-monotonicity rule.** If the old primary's stored `mta_sts_mode` is `enforce`, the new primary's must be `enforce` too. No human sets the mode, so the one way this refuses is a target the nest has not advanced yet — added or restored less than 7 days ago, or on a nest whose mail name is not yet trusted; the admin waits for the nest's advance (`mail-multidomain.md` § Per-domain MTA-STS → *The advance*) and starts the rename then. (An `accept_tls_regression` **request field** on `start_primary_domain_rename`, surfaced as a wizard confirm-dialog option, was proposed as an override and is not built; there is no CLI flag surface.) The default refuses regressions.
- **Don't bypass the grace window via `force` lightly.** `complete_primary_domain_rename(force=true)` exists for emergencies (e.g., a confirmed cert compromise of the old `mail.<old-primary>` SAN forces immediate decommissioning of the old cert). The confirm dialog names the peer-cache-flush risk.
- **Don't allow concurrent renames.** The partial unique index on `mail_domain_renames.state` enforces serialization. A second `start_primary_domain_rename` call while one is in flight refuses; the admin must complete or abort the first.
- **Don't migrate the DMARC processor inbox to a per-domain shape during the rename.** The processor stays a deployment-wide singleton (per `mail-multidomain.md`'s rule); the rename just rewrites which address peers send to. A per-domain processor shape is out-of-scope and would conflict with the existing per-domain role-address routing rule.
- **Don't tie the grace window to a fixed wall-clock value.** The default 7 days suits default cache TTLs (3600 s for MX/TXT, 86400 s for MTA-STS `max_age`). Deployments with longer caches need longer grace; the grace_days knob + the watcher's recommendation surface this.
- **Don't assume the rename can publish DNS itself.** The nest never writes DNS (client-publish model, `dns-management.md`). In managed mode the wizard checks that the client-held credential covers the new primary's zone; otherwise it surfaces the manual-DNS-instructions screen (same shape as `mail-multidomain.md` § Adding a new local domain step 2). Usually near-moot — the new primary is already an additional with published records — but the rename adds the `mail.<new-primary>` A row pre-flip, which must actually get published (managed reconcile or by hand) for the resolve-gated SAN to proceed.
- **Don't fire DKIM TXT cache-invalidation warnings during the rename.** The long-term-defensible answer is in § Behavior — DKIM invalidation (no-op): no DKIM TXT records change, no peer DKIM cache flushes. A future implementer reading `mail-multidomain.md` § The `mail_domains` model's "cached … DKIM … material would need to expire" should be redirected to this doc's explicit no-op explanation rather than over-engineering DKIM-flush logic.

**Built (SLICE 2 — `cert_issuance` / `cert_ready`, the cert SAN widening):**
- The cert-lifecycle loop (`bins/fauna-nest/src/acme_http01.rs` `cert_lifecycle_loop`) drives the pre-flip rename each ~5-min tick: it reads `get_active_rename()`, advances a `requested` row to `cert_issuance` (`advance_rename_to_cert_issuance`, idempotent), widens the **single in-process ACME HTTP-01 managed cert**'s desired-SAN set with the **one** new SAN `mail.<new-primary>`, and — once the (re-)issued cert covers it (`cert_covers_sans`) — stamps `new_cert_fingerprint` (hex `spki_sha256_of_cert_der` of the leaf) + `cert_acquired_at` and advances `cert_issuance → cert_ready` (`mark_rename_cert_ready`). No second cert; the old SAN graph stays valid throughout (`issue()` obtains-then-writes).
- The `mail.<new>` SAN is **resolve-gated** by `mail_host_resolves_to_mail_ip` — a gate keyed on the **mail-host** address `nest_host_address.mail_ipv4` (NOT `nest_ipv4`; the `mail.<new>` A record points at the MX host, which may differ from the apex). It shares the strong-verify core (`name_resolves_to`) with the secondary-apex gate but **not** its weak fallback: an unpersisted host address (or a `get_host_address` error) **DROPS** the SAN — § Renaming away from a dead domain owns that ruling (extended to this gate 2026-08-13; the earlier weak "any record" inheritance is RETIRED, and with it this paragraph's former claim that a mis-pointed `mail.<new>` could never reach the order — under the weak fallback it could, and did). An unresolved / mis-pointed / unverifiable `mail.<new>` is **deferred** (the row waits in `cert_issuance`), never dropped into the all-or-nothing order, so it can never take the primary's cert down.
- The DNS-record assembler (`bins/fauna-nest/src/dns_handlers.rs` `assemble_domain_views`) emits a `mail.<new-primary>` `A/AAAA → mail-host` row (`fauna_mail::dns::host::build_mail_host_records`, `mail_ipv4`/`mail_ipv6`) for the new-primary domain **while an active rename is pre-flip** (keyed on `get_active_rename()`'s `RenameState::is_pre_flip()`), so the client publishes it and HTTP-01 can resolve `mail.<new>`. (The design prose's "→ nest" was imprecise — the MX-host row points at the **mail** address, exactly as `mail.<primary>` does.) At anchor flip the domain becomes primary and its `mail.` row flows from the normal apex path (`append_host_records`) instead.
- `start_primary_domain_rename` auto-advances the inserted `requested` row to `cert_issuance` and wakes the loop (`acme_retry_notify.notify_one()`), so issuance fires promptly rather than on the next steady poll. `abort` is valid from any pre-flip state with **nothing remote to unwind** — the widened SAN + advertised DNS row simply stop being re-derived once the row is terminal (the widened cert stays valid until its next renewal narrows it back).
- Storage: `advance_rename_to_cert_issuance` (idempotent `requested → cert_issuance`) + `mark_rename_cert_ready(rename_id, fingerprint, acquired_at)` (strict `cert_issuance → cert_ready`, so a re-observe never overwrites the original acquisition stamp). The `cert_acquired_at` / `new_cert_fingerprint` columns already existed.
- Crash recovery is **re-derivation** (no `provisioning_failed` state anywhere): a restart resumes the loop, which re-reads the persisted row and re-asserts the SAN + re-checks coverage; a `requested` row stranded by a crash between insert and the handler's advance is advanced by the loop; a `cert_issuance` row whose on-disk cert already covers `mail.<new>` is stamped `cert_ready` next tick without re-issuing.

**Built (SLICE 3 — `anchor_flip` → `grace`, the atomic `is_primary` flip):**
- The atomic anchor flip (`bins/fauna-nest/src/db/mail_domain_renames.rs` `advance_rename_to_grace`): ONE transaction demotes the old `mail_domains` row (`is_primary = 0`) **then** promotes the new (`is_primary = 1` — demote-first so the exactly-one-primary partial unique index never sees two primaries) and sets the rename `state = grace`, `flipped_at`/`grace_started_at = now`, `grace_ends_at = now + grace_days × 1 day`. Strict `cert_ready → grace`; a missing participant `mail_domains` row rolls the whole thing back (no half-flip). There is **no** persisted `anchor_flip` resting state — the flip is atomic, so a crash lands the row at `cert_ready` (not flipped) or `grace` (flipped): a single atomic decision point.
- The cert-lifecycle loop (`acme_http01.rs` `cert_lifecycle_loop`) drives it: a rename that was `cert_ready` at the **start** of a tick flips on that tick (one tick after `cert_ready`, keeping `cert_ready` observable). After the DB flip it swaps the runtime identity projection — `identity_domain_core::apply_primary_identity(<new-primary>)` (else `handle_domain()` stays stale and the loop keeps ordering the cert around the old apex; the deployment's identity IS a projection of the primary row) — and pushes `config_changed`/`local_domains` so bridges re-fetch config + the admin client re-fetches + re-publishes the re-targeted DNS. The `handle_domain() != new` guard fires the swap + push exactly once per flip and self-heals a crash that left a `grace` row with a stale projection.
- **DNS re-targeting is by recomputation, not a write** (§ Data — Mutations to per-domain DNS records): every per-domain record (MX target, MTA-STS `mx:`/`id`, TLSRPT/DMARC `rua`) is assembled-on-read from `lookup_primary_mail_domain()`, so the `is_primary` flip re-targets them all; the client reconciles `fauna.dns.list_records`. The assembler (`dns_handlers.rs` `assemble_domain_views`) also keeps `mail.<old-primary>` `A → mail-host` alive for the demoted old primary while post-flip non-terminal (`rename_extra_mail_host_id`), so peers with a cached `<domain> MX → mail.<old>` keep resolving it; and the loop keeps `mail.<old>` in the desired SAN set (resolve-gated, **strong-check-or-DROP** — § Renaming away from a dead domain) so a renewal can't narrow the superset mid-grace.
- **Listener dual-binding is inherited from SLICE 2, not re-done** (§ Behavior — peer-MTA cache invalidation): the Go bridge MTA/MDA listeners (`GetCertificate` ignores SNI) and the nest `:443` (`MultiDomainCertResolver`) serve any SNI the managed cert covers — no hostname allowlist — so `mail.<old>`/`mail.<new>` are both served from `cert_ready`. The `tlsrpt@`/`dmarc-report@` processor inboxes (deployment-wide role-address routing) and the `/list/unsubscribe` endpoint (token-based, host-incidental on nest `:443`) are verified no-ops.
- **Abort guard (SLICE 3, superseded by SLICE 4):** SLICE 3 **refused** a post-flip (`grace`/`ready_to_complete`) abort (`rename_abort_after_flip_unsupported`) so a client couldn't strand `is_primary` flipped with no active rename via a bare state-only abort — a placeholder until the inverse landed. **SLICE 4 replaced that refusal with the real inverse re-flip** (see Built (SLICE 4)). The shared classifier `RenameState::is_post_flip_active()` (`libs/fauna-mail/src/domain_rename.rs`) keys the assembler keep-alive, the cert SAN keep, and the abort routing.

**Host-address acquisition — ratified and built; residual narrower than at SLICE 2 time.** The *strong* `mail.<new>` resolve-gate needs `nest_host_address` (`mail_ipv4`) persisted. `set_host_address` now **does** have automatic callers: the shared `fauna_client_dns::host_address::report_host_address` decision tree is wired at the universal post-auth admin-gated hook on all 7 apps (`../architecture/nest/domains-and-tls-bootstrap.md` § Host-address acquisition — `tui` landed the call site last, 2026-07-29), so a box administered from any app converges onto the strong gate on the next admin connect/reconnect — no separate onboarding hand-off needed. The residual as it stands after the 2026-08-13 ruling: the two **rename** mail-host gates no longer have a weak arm at all — an unpersisted address DROPS the SAN and the rename waits (§ Renaming away from a dead domain), which on a pure-LAN box costs nothing real, since without `mail_ipv4` the assembler cannot publish `mail.<new>` and HTTP-01 could never have validated it anyway. What survives is the **secondary-apex** gate's weak fallback for a pure-LAN box (active WAN-discovery is a standing deferral) — the open weak-fallback residual, owned in full by `../architecture/nest/domains-and-tls-bootstrap.md` § Host-address acquisition (the former "admin exclusively uses `tui`" arm of it is closed).

**Built (SLICE 4 — grace watcher + `complete` + `extend` + abort-from-post-flip inverse + remove guard):**
- The grace watcher rides the cert-lifecycle loop (`bins/fauna-nest/src/acme_http01.rs`): each tick, after the SLICE-3 identity reconcile, a `grace` row whose wall-clock window has elapsed (`NOW() > grace_ends_at`) is promoted to `ready_to_complete` (`advance_rename_to_ready_to_complete`). No cert/DNS/identity side effect — `ready_to_complete` is functionally identical to `grace` for the keep-alives (both `is_post_flip_active`). Idempotent + crash-safe (re-derived each tick).
- `complete_primary_domain_rename` (Admin RPC): valid from `ready_to_complete` (no force) or `grace` with `force = true` (else `grace_period_not_expired`); `complete_rename` stamps the terminal `completed` state, then a `config_changed`/`local_domains` push prompts the admin client to re-fetch `list_records`. **The narrow is recompute-driven, not a forced re-issue:** once terminal, `get_active_rename()` returns None, so the DNS assembler's `mail.<old>` keep-alive (`dns_handlers.rs`) and the cert-loop SAN keep (`active_rename_old_mail_host`) both stop — DNS drops `mail.<old> A` on the next reconcile and the cert narrows to drop the `mail.<old>` SAN on its **next natural renewal**. No ACME issuance is forced at `complete` (keeping `mail.<old>` as an extra SAN until renewal is harmless — the old domain stays a local domain — and a forced narrow would burn an issuance against Let's Encrypt's success-side limits for no functional gain). `is_primary` is untouched (already the new domain from SLICE 3).
- `extend_primary_domain_rename_grace` (Admin RPC): `grace_ends_at += additional_days × 1 day` (`additional_days ∈ [1,30]` per call), valid from `grace` / `ready_to_complete`; a `ready_to_complete` row **reverts to `grace`** (its deadline is future again) and the watcher re-promotes when the new deadline passes. No `config_changed` push (only the watched deadline moves).
- The **abort-from-post-flip inverse** (`abort_rename_from_grace`, `db/mail_domain_renames.rs`): ONE transaction demotes the new `mail_domains` row **then** re-promotes the old (demote-first, the exact mirror of `advance_rename_to_grace`) + sets `state = aborted` — a single atomic decision point, rolling back (no half-reflip) if a participant vanished. The `abort_primary_domain_rename` handler routes a post-flip row here, then swaps the runtime identity projection back (`apply_primary_identity(<old>)`, a sync call with no await-gap after the txn) + pushes `config_changed`/`local_domains`; a pre-flip / not-found / terminal row still takes the state-generic `mark_rename_aborted`. **This replaces the SLICE-3 `rename_abort_after_flip_unsupported` refusal.**
- The `domain_in_rename_flight` refusal on `remove_local_domain`: the handler refuses removing either participant (old or new primary) of a non-terminal rename (`get_active_rename()` + name→id lookup).

**Built (the dead-old-apex resolve gate, 2026-08-11 — § Renaming away from a dead domain owns the ruling):**
- `acme_http01::ApexSans` (`apex` / `mail_host`, one named field per gated SAN, mirroring `InfraSans` — and deliberately **no `Default`**, because the two types' safe sides are opposites: omit an unresolvable infra SAN, *keep* the apex) is now a parameter of `desired_san_domains`, which skips `<apex>`, `mail.<apex>`, and the apex's own row in `mail_domain_names` when gated out (that last skip is load-bearing — `list_active_mail_domains` carries the primary, so the per-domain loop would otherwise re-admit the name the gate just dropped).
- `acme_http01::apex_sans_for_cycle` computes the verdict: `INCLUDED` unless a **pre-flip** rename row exists whose old-primary domain name *is* the apex (a mid-reconcile disagreement between the in-memory projection and the DB gates nothing), then the strong check `name_resolves_to` per SAN — apex against `nest_ipv4`/`nest_ipv6`, `mail.<old>` against `mail_ipv4`/`mail_ipv6` — with **no weak fallback**: an unknown host address or a `get_host_address` error returns `DROPPED`.
- Wired at both order-computing call sites — the issuer (`cert_lifecycle_loop`) and the at-risk nudge (`cert_nudge`), which must compute the identical set or it would nudge forever about a SAN the issuer declines to order. `tls_handlers::desired_listener_sans` (the DNS-01 client path) passes `ApexSans::INCLUDED` by design.
- Pinned end-to-end by an **all-or-nothing fake issuer** (an order holding any name that does not point at this nest fails wholesale and writes no cert — the assumption a dead zone breaks, and one `cert_writing_issuer` could not express): a seized old apex parked at a squatter IP still drives `requested → cert_ready` with its SANs absent from the order, and the beside-control proves a live old zone keeps both SANs. Plus per-verdict unit tests, including the no-persisted-host-address DROP that the weak fallback would have kept.

**Built (hardening — security review of slices 2/3/4):**
- **State-conditional (CAS) transitions** (`db/mail_domain_renames.rs`): every rename state-transition UPDATE is now conditional on its expected from-state (`AND state = '…'` / `IN (…)`, `rows == 1` asserted; the pre-flip `mark_rename_aborted` CASes on the pre-flip set `requested`/`cert_issuance`/`cert_ready`, so a flip that raced the abort refuses instead of clobbering `grace → aborted`). A lost race maps to `409 rename_wrong_state`, never a silent clobber — closing the admin-RPC ↔ cert-lifecycle-loop races (pre-flip abort racing the flip; the watcher racing an abort). Refusals are a typed `RenameTransitionError` (`NotFound`/`AlreadyInProgress`/`AlreadyTerminal`/`WrongState`), so `map_rename_err` downcasts instead of string-matching — which also fixes wrong-state `complete`/`extend`/`abort` mapping to `500 internal` (now `409 rename_wrong_state`).
- **Unconditional identity-projection reconcile** (`acme_http01.rs` cert-lifecycle loop): the loop now reconciles `handle_domain()` against `lookup_primary_mail_domain()` on **every tick** (gated on a non-local primary existing), not only while a rename is post-flip-active — self-healing the in-memory `identity_domain` cache against any divergence source (the flip, an abort re-flip, a raced stale re-apply that left the cache on a since-aborted domain, or the abort handler's own skip-on-lookup-failure), so a diverged projection can never persist until restart.
- **`start` auto-advance idempotent against a racing loop tick** (`bridge_routing_handlers.rs`): `start`'s own `requested → cert_issuance` CAS could lose to a coincident cert-loop tick driving the identical transition and surface a spurious `409 rename_wrong_state` for a rename that was created and *is* in `cert_issuance` (the admin's retry then returned `rename_already_in_progress`). The handler now re-reads on a refused advance via the pure `reconcile_concurrent_cert_issuance_advance` helper and returns the row iff it is now exactly `cert_issuance`; any other re-read state (e.g. a concurrent abort of the just-inserted row) propagates the refusal, so a genuinely divergent race is never masked. Mirrors the loop's own tolerance (§ Crash recovery). Trusted-writers-only, no data loss — this only tidied the RPC surface.
