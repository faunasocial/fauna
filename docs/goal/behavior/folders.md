## Target re-model — folders (ratified 2026-08-13)

Design authority: the 2026-08-13 folders re-model design (RATIFIED — full decision record, migration, phasing, rename inventory; tracked internally). The target-state claims, at concept level:

- **The former "file sets" are "folders", renamed full-depth** — wire (`fauna.folders.*`), at-rest tables, code, crates, IDs, i18n, docs. No compat shim (user updates all consumers). Four opaque KDF/exporter `.v1` constants keep their spelling (renaming would strand sealed data); the local-binding "folder" vocabulary renames to **location** first (a bound local directory is the folder's *location on this device*). **"No compat shim" is scoped to consumers the user re-rolls** — apps, bridges, the nest — and never to bytes already at rest on a user's disk, which no user can re-roll: those get an in-place read-fallback, exactly as the nest half does at boot. Owner of that boundary: [`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 1.
- **A folder has NO type.** The former sync/backup/web modes dissolve. Behavior lives per **place** — device places with flags (`originates` / `accepts` / `applies_deletes`, replacing the Source/Sync/Backup/Mirror role enum), the nest place (live head + optional snapshots + content residency), destination places (blind sealed custody, today's backup destinations — the per-folder attachment design is ratified: [`backup-destinations.md`](backup-destinations.md) § Ordinary-folder coverage). Serving is per-folder **toggles**: website (+ paywall tier), WebDAV.
- **One write plane; derived planes.** Devices record only to the live head; snapshots are quiet-period manifest-level cuts per snapshot-keeping place's policy (cadence + retention); the website is a toggle-driven fan-out of the head. `backup_custody` recording for ordinary sets retires — with **no data migration**: the planned head re-seed was deleted by user ruling 2026-08-17 (§ Implementation status today records the scope); reserved destination custody is untouched.
- **Audience ∈ private / shared / public.** `private` = owner-key sealed; `shared` = MLS group + M2 content keys (unchanged); `public` = world-readable by design, rests unsealed incl. names/paths, behind an explicit owner confirm (`principles.md` § The user always controls their data owns the invariant exception) — and a seat unseals only on the owner's **signed attestation** of that confirm, never on the nest's report of the audience (mechanism owner: [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Readable classes → *The declassification is owner-ATTESTED*). **Paywalled web content is `shared`-audience machinery** — sealed under the per-folder content key, decrypted at serve time via the web-serve holder's scoped revocable grant; it never needs (and never gets) `public`.
- **The per-folder scan-frequency knob retires** — the reconcile backstop becomes a hard-coded constant; the user-facing time control is snapshot policy. Website-published folders appear in Media like any other folder. Former web-mode sets got **no migration** (user ruling 2026-08-13: no current users) — any existing row maps to a plain private folder, website off.

## What a folder is

A **folder** is a named collection of files an actor keeps as a unit, owned by that actor and able to span multiple devices. It is **nest-authoritative**: the set (its name, device roster + places, snapshot policy, selective-sync paths) lives in a nest folder row, created once via the folder wizard; a device's local-folder *binding* only references an already-existing set.

Folders are the **substrate** for the user's stored files. Several app surfaces are *views* over that one substrate (§ The surfaces over a folder) — they never duplicate the set; they read or configure it.

**Scan frequency** is a RETIRED control (phase 5's de-knob — the reconcile backstop is a hard-coded constant; the non-UI half and the rule-A-granted UI retirement both landed 2026-08-20, so no app renders a picker and new seats ignore the stored value). Behavior + compat contract: [`file-sync.md`](file-sync.md) § Config (the ⚠ phase-5 block).

## The surfaces over a folder

The substrate is one thing; these surfaces are distinct views, each with its own authority:

| Surface | Plane | What it does | Authority |
|---|---|---|---|
| **Settings → Folders** | control | Create / configure a set (device places, selective-sync paths, conflict policy, the nest place's snapshot policy), bind a location (desktop), resolve conflicts. | [`../ui/folders.md`](../ui/folders.md) |
| **Media** | content | A Windows-Explorer-style *media library* view over the files **inside** the user's folders (cross-folder all-media browse; never configures a folder). **Excludes reserved `__*` sets only.** | [`../ui/media.md`](../ui/media.md) |
| **Backups** | content | Snapshots + retention editing (the nest place's policy, any folder). | [`../ui/backups.md`](../ui/backups.md), [`backup-restore.md`](backup-restore.md) |
| **Web hosting** | content | Authoring/serving a website-enabled folder as a published website (web-settings / admin-web UI). | [`web-content-hosting.md`](web-content-hosting.md) |
| **WebDAV serving** *(ratified 2026-07-06; status → [`webdav-server.md`](webdav-server.md) § Implementation status today)* | content | Serving explicitly-flagged folders to generic WebDAV clients (read + write) via the mail-bridge MDA; the per-set `folder-webdav-toggle` lives on the Settings → Folders control plane. | [`webdav-server.md`](webdav-server.md) |

Two rules keep the planes clean: **the content plane reads, the control plane configures** (Media never configures a set; web-settings never browses media), and a website-enabled folder is browsable in Media like any other — the site is the head's fan-out, not a separate plane.

## How files get sealed at rest

A folder's chunk bytes are sealed per the set's audience: an owner-only set seals under the owner's `BackupKey`; a cross-user **shared** set seals under the group's content key (MLS); a **WebDAV-served** set (ratified 2026-07-06; status → [`webdav-server.md`](webdav-server.md) § Implementation status today) also seals under an M2 content key, additionally conveyed to the MDA bridge per DAV session ([`webdav-server.md`](webdav-server.md) § Key model). Authority: [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) (the audience taxonomy) + [`file-sync.md`](file-sync.md) § Content-Addressed Storage. ## Publicly-synced follow (ratified 2026-08-18; the NEST HALF is BUILT — 2026-08-18, slice 4f-i)

**What it is.** Any Fauna user, on any nest, may **follow** a `public`-audience folder and
browse/download its content from their own app — the "publicly synced" read path the re-model's
audience bullet promises. A follow is **the reader experience over a public folder**: like a
shared-folder *reader* (see [`../ui/folders.md`](../ui/folders.md) § Sharing — readers get no
location binding, by the `file-sync.md` iron rule that a tracked file's modification must
upload), a follower browses + downloads via Media, on demand. On-disk read-only mirroring is
**not** v1 — it rides the future read-only device places design (`originates=false` places,
expressible in the flag space, deliberately no UI in v1) and lands for shared readers and public
followers **uniformly** when it lands at all.

**The behavior contract:**

- **Address = owner + name, pinned to `folder_id`.** The follow gesture takes a handle (resolved
  to an actor id by the existing discovery kinds) + the folder's plaintext name; the first
  successful read pins the home nest's stable `folder_id`, which subsequent reads address — so a
  later rename never breaks an established follow (a rename before pinning is just a failed
  follow). Public folder names are world-readable by the ratified exception, so name-addressed
  resolution of a *public* folder is not an oracle problem; **everything else stays folded**: a
  non-public or absent target answers the same `not_found`, indistinguishably (ST-RES-1 held).
  **The home nest is discovered from the handle, never typed** (ratified 2026-09-22): the
  handle's `@domain` is the address's nest half, and the follow runs the SAME chain the
  conversations recipient picker runs — a same-nest `fauna.actor.by_handle` probe, then the one
  shared same-nest-vs-cross-nest verdict (`fauna_core::resolve::is_foreign_handle_domain`). A
  bare handle, or a domain the follower's own nest serves, is the **same-nest** follow (empty
  `home_nest_url`; the follower's nest serves the folder itself). A **foreign** domain is
  resolved directly against that peer through the anonymous discovery hop (the picker's
  `actor_by_handle_remote`; [`../architecture/federation.md`](../architecture/federation.md)
  § Peer-auth model), and the record's `home_nest_url` is the peer's base URL from the one
  domain→URL derivation every cross-nest caller shares (`fauna_provisioning::probe::peer_nest_url`),
  so every read after the first is relayed there by the follower's own nest. A bare actor id
  names no nest and is always same-nest. A handle no nest knows, and a peer's definite refusal,
  fold into the same `not_found` as an absent folder; a transport fault stays a fault.
- **The public floor — nothing recorded before the most recent flip-to-public is ever served on
  the public plane.** Each →`public` transition stamps the folder's current head seq as
  `folders.public_floor_seq` (additive column; a born-public folder's floor is 0), and the public
  read serves only rows strictly above it. What the owner declassified is the folder *from the
  flip forward*: the confirm dialog names content + names/paths, and the 4b declassify pass
  re-records the live back-catalogue above the floor — but the **private era's metadata** (edit
  timing, sizes, counts, sealed labels) was never declassified and never crosses this plane. The
  floor makes that boundary structural rather than per-row-filtered.
- **Stripped projection.** Public-plane change rows ride the same `SyncChange` wire shape with
  the identity/key metadata fields **absent**: `device_id`, `author_actor_id`, `path_sealed`,
  `content_key_version`. A follower needs paths, manifest refs, sizes, types, timestamps and the
  causal watermark — never the owner's device fleet or authorship map.
- **Zero nest-side follower state.** A follow writes **no row on the home nest** — no roster, no
  registration, no per-follower anything. Follow state lives solely in the follower's own
  account store — one `fauna.state.follows` row per followed folder
  ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) owns the
  kind; a `FollowedFolder` record: home nest URL + `nest_actor_id` stamp, owner actor id,
  the owner handle the follow was addressed by when it was one — a display input, re-checked
  before it is shown (`../ui/folders.md` § Following a public folder) — pinned `folder_id`,
  display name). Consequences: followers are not enumerable, a follower flood
  cannot grow nest state, and unfollow is a purely local delete.
- **Flip-back closes the plane immediately and loudly.** The gate reads the folder's *current*
  audience per request, so a `public`→`private`/`shared` flip makes the next read answer
  `not_found` (indistinguishable from absent — that *is* the revoke semantics). The follower's
  app marks the follow "no longer available" (kept visible until the user removes it); a re-flip
  resumes it (the `folder_id` is stable). Plaintext chunks already fetched or still awaiting
  GC after the flip-back's re-seal were world-readable while public — secrecy already forfeit,
  per the ratified one-way warning.
- **Trust envelope: nest-asserted, website parity.** A follower trusts the home nest for content
  authenticity exactly as a website reader does — content addressing gives integrity (blake3
  chunk/manifest hashes), the nest asserts *which* manifest is the head. MLS is not involved (no
  group, no keys). Named future hardening, not owed: owner-signed manifest roots.
- **Reads ride existing planes end-to-end.** The change-log/meta read is one new WS-RPC kind pair
  (client + federation twin — [`../architecture/federation.md`](../architecture/federation.md)
  § The public folder read plane owns the kinds, gates and throttles); manifests + chunks ride
  the existing open by-hash bulk GETs (plaintext for a public folder — the self-describing
  `stored_hashes = None` shape every reader already passes through), with the established
  SPKI-pin/WebPKI trust root for a cross-nest follower's direct byte-plane dial. What that
  means for a folder whose bytes do not rest on the nest: [`file-sync.md`](file-sync.md)
  § Content residency, *v1 scope cuts* (the `public` pair, ruled 2026-10-01).

**Implementation status.** The **nest half is BUILT (slice 4f-i, 2026-08-18** — `git log
--grep 'phase 4 slice 4f-i'`): `folders.public_floor_seq` at rest (schema **v44**, additive,
`MIN_READER` stays 42 — `INTEGER NOT NULL DEFAULT 0`, a constant that is correct per-row
because a born-public folder's floor IS 0 and a never-declassified row never reads it),
stamped in the ONE audience writer (`CacheDb::update_folder_for_user`) **inside the same
UPDATE as the flip** — a read-then-write pair would let a change recorded in between land
below the floor and be served — and guarded on the pre-update value, so a re-assert of
`public` never re-stamps and silently un-serves the public window. The read core is its own
module (`bins/fauna-nest/src/folder_public.rs`): address resolve → audience-only gate → floor
filter (`max(since, public_floor_seq)`, applied at the query so a floored row is never

and its federation twin. `FolderReadGrant` gained the `Public` variant, which
`can_read_folder` never returns — the public core authorizes independently, and the variant's
one load-bearing use is routing the `path_sealed` decision through the same
`is_label_audience` predicate every other read surface uses. **One wire precision the design
prose did not anticipate:** "stripped" means **no value**, not **no key** —
`author_actor_id`, `path_sealed` and `content_key_version` carry `skip_serializing_if` and
lose their keys, but `SyncChange.device_id` has neither that attribute nor `#[serde(default)]`,
so it rides as an explicit `null`; adding the attribute would break decode on every peer and
client without the matching default, a compat break inside a major. A `null` discloses nothing
about the owner's device fleet. Pins: `conformance_folder_public_fetch.rs` (all four oracles
— the gate's indistinguishability across absent/private/reserved/wrong-owner, the floor and
its per-flip re-stamp, the strip against a control row that demonstrably carries the fields,
flip-back-as-revoke — plus "a public read writes nothing"). **4f-ii's SHARED-RUST CORE landed 2026-08-18** (same day; `git log --grep 'phase 4 slice
4f-ii'`): `UserConfig::follows` — a `FollowedFolder` list at rest (**config payload version 8**,
additive, `min_reader` stays 1) holding the *whole* of a follow, since the home nest keeps none;
follow/unfollow/list as **deltas** applied inside the config CAS (never list-replacement — the apps'
lesson, so a concurrent follow from another device survives a retry), through the
shared chokepoint `fauna_client_config::{save_follow, save_unfollow, load_followed_folders}`
built in `sync_prefs.rs`'s shape; and the two read ops
`fauna_client_folders::public_follow::{resolve_public_folder, fetch_followed_changes}` — first
contact by `(owner, name)`, every later read by the pinned `folder_id`.

**The merge arm is latest-wins per followed folder, and that is load-bearing rather than
incidental.** Latest-wins is the arm under which **unfollow propagates**: a tombstone-less union
CRDT would resurrect a removed follow from any device still listing it — the user unfollows on
their phone and watches the row return from their laptop. The record qualifies for that arm on
the existing rule this file's siblings already state (`moderation`/`sync_prefs`/`personalization`):
a follow is a *recreatable* preference, not irrecoverable key material. Since 2026-09-30 the
follow rests as one `fauna.state.follows` row per folder, each latest-wins on its own stamp and
an unfollow a stamped tombstone — the blob's whole-record arm narrowed to the folder, so unfollow
still propagates and the blob arm's declared cost (two devices following *different* folders
concurrently could drop one) is gone. The `UserConfig.follows` blob field retired with the `__config`
rail on 2026-10-02; `config-dissolution.md` § Implementation status today records the cut and the
retirement.

**Also pinned client-side: the refusal must stay uninformative.** `FollowError` carries exactly
one domain arm (`Unavailable`), matched on the wire **code** — the nest folds absent / private /
reserved / wrong-owner into one answer on purpose, so a client that tried to tell them apart for
a friendlier message would rebuild the existence oracle the fold prevents. A *transport* fault
deliberately does NOT fold into it: "the network is down" and "this folder is no longer public"
must never render the same, or a follower sees a revoke every time their wifi drops.

**4f-ii is COMPLETE as of 2026-08-18** — its four surfaces landed over two sessions and all
three client boundaries now carry the follow. The **folders-list projection** is
`DevicesSnapshot.followed: Vec<FollowedFolderSummary>`, a list *separate* from `folders`
(a followed folder has no group, no roster, no binding, and a status those rows cannot hold),
filled from the optional `DevicesMachine::set_followed_folders_source` seam — unwired it is
simply empty, which is the correct render for an app that has not built the surface. The
**availability verdict belongs to the source, not the machine**: deciding "still served" means
running the public fetch and telling the plane's own refusal apart from a transport fault, and
the machine is deliberately transport-free — so `StoreFollowedFoldersSource` (both arms) owns
the round trip while the *rule* lives in the pure, tested
`public_follow::availability_from_probe`. `available == false` keeps the row visible: it **is**
the revoke, and a re-flip resumes it.

**The probe's fan-out was decided 2026-08-19, ahead of the UI that would have felt it.** The
source's first shape probed **serially — one relayed cross-nest round trip per followed folder,
on every devices refresh** — which nobody had felt because no app rendered the rows. Wiring
4f-iii is exactly what makes it felt, so it was settled first. The resolution is a **staleness
budget plus bounded concurrency**, both in the tested crate
(`public_follow::{AVAILABILITY_TTL_MS, AVAILABILITY_PROBE_CONCURRENCY, needs_probe,
resolve_availability}`), with the glue reduced to a cache read, one call, and a write-back:

- **Why a budget, not just concurrency.** Availability changes when an owner flips a folder's
  audience back or deletes it — about once ever per follow, not a live signal — while the
  devices page refreshes on every nav edge and push. Probing per refresh spends N relayed round
  trips to re-learn a value that almost never moves. **The budget introduces no *kind* of
  staleness the contract did not already accept**: a transport fault already keeps a row
  available indefinitely, deliberately, because a dropped connection must not read as a revoke.
  One minute, so a revoke surfaces on the next refresh past it.
- **Why bounded, not `join_all`.** Each probe is relayed by the follower's own nest out to a home
  nest, so N concurrent probes become N concurrent relays into the per-source-IP and per-nest
  throttles the public plane rides by design ([`../architecture/federation.md`](../architecture/federation.md)
  § The public folder read plane, *Zero state, zero metering*). Serial was throttle-safe and
  unusably slow; an unbounded fan-out is fast and trips the very throttles that keep the plane
  cheap to serve. Four keeps a cold render to `ceil(N/4)` round trips.
- **Not an async-update shape.** The ratified row has two states (Following / no longer
  available) and no "checking" — [`../ui/folders.md`](../ui/folders.md) § Following a public
  folder — so resolving in the background would need a third state or would briefly paint a
  wrong one.
- ⚠ **A future-stamped cache entry re-probes.** The obvious `now.saturating_sub(probed_at)`
  saturates to `0` under a backwards clock (a laptop waking, an NTP correction), i.e. "probed
  this instant", freezing the row for as long as the skew lasts. Its own test caught that
  against the saturating form. The **native façade** is four UniFFI exports
(`folders_follow_public` / `folders_unfollow_public` / `folders_followed_list` /
`wire_devices_followed_folders`); the **browser façade** is their `fauna-wasm-folders` twins
(`followPublicFolder` / `unfollowPublicFolder` / `followedFolders` /
`setFollowedFoldersSource`), which is what promoted `StoreFollowedFoldersSource` from
native-only to both targets. The **Media plaintext read** needed no new decode arm — the walk
selects `Plaintext` on `stored_hashes.is_none()` *before* consulting key material, so a
keyless reader already passes through — but the follower's own shape (keyless **over
plaintext**) had never been pinned, sitting untested between the keyed-over-plaintext and
keyless-over-*sealed* cases; it is now
(`file_download::tests::keyless_follower_reads_a_plaintext_manifest`). The shared read op
`public_follow::download_followed_file` makes the keylessness structural: a plaintext manifest
opens under *any* key state, so a caller that passed its own `BackupKey` would succeed in every
happy path and only diverge where it matters — a sealed manifest on the public plane must fail
closed, not be attempted against the follower's root.

**4f-iv landed 2026-08-18 — the follow proven end to end, and the RELAY arm exercised for the
first time.** Every earlier proof of this plane took the *same-nest* branch (owner and reader
on one deployment, request carrying no `nest_url`), so the arm a real follow takes — the
follower's own nest relaying to the folder's home nest — had never run. It now does, in two
places whose split is deliberate. The **wire and the bytes**:
`tests/e2e-unified/tests/api/test_public_folder_follow_cross_nest.py` (tier_3, two real nest
**binaries**) walks a stranger on nest F through the relay to a folder on nest H — private
answers exactly what absence answers *through the hop*, the strip survives the relay's
re-encode into a fresh reply, the `home_nest_actor_id` stamp is **H's** `nest.info` identity
and demonstrably not F's (a relay that stamped its own would aim every follower's byte dial at
the wrong deployment, and no single-nest test can see the difference), F's own local arm knows
nothing about the address (so it really was the relay that served), the file's bytes come back
byte-exact off H's open by-hash plane **with no credential and no key**, and flip-back →
re-flip revokes and resumes under the pinned `folder_id` with the floor re-stamped. The
**client half**: `bins/fauna-nest/tests/conformance_public_follow_client.rs` stands two
in-process nests up and drives the follower's own stack — first contact over the relay,
`save_follow` (then into the follower's `__config`; since 2026-09-30 into its account store's
follows, a store double there — the production door is proven in
`libs/fauna-sync-engine/tests/peer_leg_convergence.rs`), and
`StoreFollowedFoldersSource` emitting the row a followed-folders list renders, its
`available` verdict coming from a live relayed probe (and going false, without dropping the
row, when the owner re-seals). That source is built over a concrete `NestClient` and so had
been reachable only by stub; a conformance seat reaches it without waiting for 4f-iii's UI.

**The Media browse routing is DESIGNED AND BUILT (both 2026-08-19 — shared Rust + tui; web and
linux landed their legs 2026-08-20, the remaining four apps trickle down, and `ui/media.md`
§ Implementation status today records exactly what landed and what is owed).** The gap it closed: Media's
item list is built from the user's *own* nest aggregate, and its custody resolver is keyed by
folder *name*, while a follow is addressed `(home_nest_url, folder_id)`. **The ruling: a
followed folder browses as a parallel, identity-addressed, keyless SCOPE on the Media page —
the name-keyed pipeline is not widened.** [`../ui/media.md`](../ui/media.md) § Followed public
folders owns the explorer UX and read model; what this section owns is the routing boundary: the
scope (never the item) carries the follow's identity, listing is `fetch_followed_changes` on
demand plus a pure head fold, downloads are `download_followed_file` through a home-nest-bound
fetcher off the `ForeignBlobFetcherFactory` seam cross-nest shared sets already use, and a
followed read **never touches the name-keyed custody resolver or any key material** — the
keylessness is structural. Two refutations of record, so nobody re-derives them: (i) **widening
`MediaItemSummary`/the resolver to an identity address was REFUSED for this slice** — a follow
never consults custody, so the widening would not serve it; it would re-open the
deliberately-deferred channel-keyed custody direction (the owned-shadows-foreign
precedence and its "menu (c)" future, recorded at
`libs/fauna-client-folders/src/custody_ingest.rs::resolve_custody_from`) as a rider on a UI
slice; and it is a 7-app data-shape trickle-down bought for zero follow-side benefit. The
pre-existing name-key latency for foreign *shared* sets stays owned by that shadowing rule —
not by this slice. (ii) **Eager aggregation of followed rows into all-media was refused** — the
follower's nest holds no copy, so aggregation means one relayed cross-nest fetch per follow on
every Media refresh, the exact fan-out the probe design above bounded. A followed/owned name
collision ("photos" following "photos") is a *label* problem only under this design — routing
never keys on names — and the Media filter labels disambiguate by owner.

**Note for the routing's implementer:** the design's stated
reason for pinning `folder_id` — "a later rename never breaks an established follow" — is
currently **unassertable**, because the product has no folder-rename path at all (no
`fauna.folders.rename` kind, no rename DAO). The pinned form is built and tested for
addressing and precedence; its rename-survival oracle belongs with whatever slice first lands
a rename.

**Deliberate v1 non-goals (each named, none accidental):** no public-folder *discovery/listing*
kind (follow is by exact address; an enumeration surface is a separate decision); no anonymous
direct-dial WS read (the follower's own nest relays, as every cross-nest client read does — the
core is exposure-ready if a future pass deliberately opens the anonymous plane, which then needs
its own throttle class); no snapshots on the public plane (head only); no push/nudge to followers
(browse-on-demand; the cross-nest nudge stays the named deferred candidate it already was); no
on-disk read-only sync (above).
