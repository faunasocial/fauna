## Goal

A bridge process — the mail-bridge and the ATProto PDS bridge today, a future standalone Nostr relay bridge tomorrow — starts, enrolls, discovers its role, fetches its config, opens its protocol-specific listeners, reacts to admin-initiated state changes (enable / disable / rotate / revoke), survives nest restarts, and shuts down gracefully — **all without any hand-edited configuration beyond the four artifact-set deployment-topology argv slots** (`--keypair-file`, `--nest-endpoint`, `--log-level`, optional `--data-dir` — set by the supervisor/run-script, never typed by a human). Everything else — which role this binary serves, what config knobs apply, when to start listening, how to rotate keys — comes from nest, set by an admin in their Fauna app.

**Bar: a fresh nest + a fresh container + a fresh admin app → working mail subsystem with one click in the admin UI.** No CLI invocations, no hand-edited TOML files, no `touch /data/imap-enabled`, no `docker exec` to seed a keypair. Each step that needs human input surfaces in the admin's Fauna app and is one click; everything between clicks is automatic.

**Universal contract for future bridges.** A future standalone Nostr relay bridge / future-protocol bridges (like the now-landed ATProto PDS bridge) inherit the lifecycle shape spelled out here — ActivityPub does not, since it shipped in-process rather than as a bridge-as-client (`architecture/apps/bridges.md` § Future bridges). Their per-bridge specs (in `docs/goal/architecture/apps/<bridge>.md` and `docs/goal/behavior/<bridge>.md`) add only their protocol-specific listener configuration; the startup → enrollment → fetch-config → listen → reconnect → shutdown flow is shared.

- **Zero-touch self-enrollment (`fauna.bridges.request_enrollment`)** — **shipped (nest side, tracked internally).** A bridge that has generated a fresh keypair self-announces over the **anonymous pre-identity WS** (`GET /api/v1/ws`, no token) to create a `pending` enrollment row — so it surfaces in `list_pending_bridges` for the admin to approve **from their Fauna app**, replacing the out-of-band `POST /api/admin/bridges/pending` pre-register interim (Stage-5 deploy Gap B). ## Lifecycle phases

The bridge process moves through five phases over its lifetime. Each phase has a clear entry condition, a clear exit condition, and a state row in nest's `bridge_service_users` table the admin pane can read.

| Phase | Entry | Exit | Nest `status` |
|---|---|---|---|
| **Cold boot** | Supervisor exec's the bridge binary | Keypair loaded; anonymous WS open; `request_enrollment` returns `pending` | no row → `pending` on first `request_enrollment` |
| **Pending approval** | Bridge self-enrolls (`request_enrollment`) with a never-seen pubkey | Admin clicks "Approve" in the Fauna app | `pending` → `approved` |
| **Running** | `whoami` returns `status=approved` | SIGTERM / revoke / internal fatal error (a WS drop → Reconnecting, not exit — reconnect is indefinite) | `approved` |
| **Reconnecting** | WS connection drops | WS reconnects + `whoami` returns `approved` | `approved` (unchanged — connectivity is not a status field) |
| **Shutting down** | SIGTERM received OR `whoami` returns `status=revoked` | Last in-flight transaction drained or grace-timeout | `approved` (graceful) or `revoked` (forced) |

### Cold boot

The process supervisor (s6 in the docker image, systemd on bare-metal Linux, equivalents elsewhere) launches the bridge binary with the four deployment-topology argv slots:

```
fauna-mail-bridge \
    --keypair-file /data/keys/<role>.key \
    --nest-endpoint wss://<nest-host> \
    --log-level info \
    --data-dir /data/mail-bridge
```

`--nest-endpoint` is the nest **base URL only** — the bridge derives the WS
endpoint itself, swapping the scheme to `ws`/`wss` and appending
`/api/v1/ws/<actor_id_hex>` (`internal/wsrpc/client.go` `buildWSURL`; the actor
id is the bridge's Ed25519 pubkey hex). Passing a full `…/api/v1/ws` path would
double it. In-container deployments pass the **loopback** `https://127.0.0.1:<port>`
 — the nest serves **TLS** on its main listen port (a real ACME
cert; or, for a localhost/LAN/bare-IP deploy with ACME off, a **self-signed
bootstrap cert** the nest synthesizes at boot — `nest::main`'s self-hosted-TLS
bootstrap via `self_signed_cert::write_self_signed_bootstrap`, see § TLS
provisioning), so there is no plaintext listener for the bridge to dial. The
bridge skips cert verification for a **loopback** endpoint only
(`nestHTTPClient`/`isLoopbackHost`): the connection never leaves the host, and a
self-signed/LAN cert cannot chain a loopback hostname — the same posture as a
client pinning a self-hosted nest's Ed25519 identity. Non-loopback endpoints keep
full verification. See `installers/docker.md` for the realized s6 run-scripts.

The binary's startup steps, in order:

1. **Read keypair file at `--keypair-file`.** If the file exists, parse it as a DAG-CBOR-encoded `ServiceUserKeyfile` (Ed25519 signing seed + X25519 HPKE-decrypt secret, workspace-standard shape per `libs/fauna-mls/src/wrapped_blob/service_user.rs`, mirrored Go-side by `bins/fauna-bridges/internal/keypair/keyfile.go`); on parse failure, exit with status 65 (`EX_DATAERR`) and a structured-log line naming the file and parse error.
2. **Generate keypair if absent.** If the file does not exist, generate a fresh Ed25519 + X25519 keypair via the workspace standard, write it to the file with mode 0600 (owner read/write only — sensitive secret), and emit a structured-log line at INFO `bridge_keypair_generated keypair_file=<path> pubkey_hex=<hex>`. This is the first-run case; it is never hand-seeded.
3. **Self-enroll over the anonymous WS.** Open the **anonymous (pre-identity) WebSocket** to `--nest-endpoint` (`GET /api/v1/ws`, no bearer) and call `fauna.bridges.request_enrollment(ed25519_pubkey, role_hint, bridge_id, x25519_pubkey, enrollment_sig)`. `role_hint` is derived from the keyfile basename (`/data/keys/mta.key` → `"mta"`); `bridge_id` may be the keyfile's (or empty — nest synthesizes `<role>-<pubkey-prefix>`). The request carries the bridge's **x25519 pubkey plus an Ed25519 proof-of-possession signature** over `enrollment_signed_message(role, ed25519_pubkey, x25519_pubkey)` (Go `wsrpc.EnrollmentSignedMessage`, `internal/wsrpc/enroll.go` — always sent by the image bridge), which also binds the x25519 **set-once** at enrollment. nest creates a `pending` enrollment row and returns the current status. **Two authorization tiers, both loopback-gated** (a remote source IP is refused with `fauna.bridges.remote_enrollment_unsupported`; cross-IP/multi-host enrollment is deliberately deferred): (a) **strict mode** — when the deployment artifact provisions a per-role blessed pubkey (a root-owned registry file; nest re-reads it live per enrollment via the `FAUNA_BLESSED_KEYS_DIR` IPC env — artifact wiring, not operator config; the legacy `FAUNA_BLESSED_{MTA,MDA}_PUBKEY` value envs are the non-image fallback), nest requires the presented pubkey to *be* the blessed key **and** the proof-of-possession signature to verify (`bridge_blob_handlers.rs::blessed_bridge_pubkey` + `check_enrollment_authorization`), so a stray same-host process cannot enroll; (b) **lenient fallback** — with no blessed key provisioned (dev / binary-e2e), a loopback peer is accepted as inside the deployment trust boundary. The crypto contract is owned by `architecture/security.md` § Enrollment proof-of-possession contract. The bridge↔nest hop is the in-container loopback (`http://127.0.0.1:<port>`), so the gate holds for the supported deployment. ⚠ **Forward-watch for whoever lands the systemd/bare-metal mail-bridge analog (§ above records it as still a TODO): that installer must provision the blessed registry too.** The strict tier is reached only when the *artifact* provisions `FAUNA_BLESSED_KEYS_DIR`, which today only the Docker image's run-script does — so a bare-binary/systemd box structurally lands on tier (b). It does so **silently**: the `request_enrollment is UNAUTHENTICATED … any loopback peer can enroll` warning (`bridge_blob_handlers.rs::request_enrollment_handler`) is guarded on `is_fronted_by_router()`, an IPC env only that same Docker run-script sets, so it can effectively fire only on a *misprovisioned Docker* box and never on the deployment shapes that have no registry at all. That guard is coherent with tier (b)'s stated dev/binary-e2e scope and is **not** a defect today — it becomes one the moment systemd/bare-metal is a shipped mail-serving shape, because then a production box runs loopback-only enrollment with no signal. Graded and refuted as a live finding, recorded here so the installer session inherits it instead of re-deriving it. This **replaces** the old "open the authed WS and hold it open for an unknown pubkey" idea: the standard challenge-response auth path is unchanged (it still rejects an unenrolled pubkey — that 404 is the *user* onboarding signal), and the bridge does not run it until after approval (step 5).
4. **Poll `request_enrollment` until approved.** While the reply is `pending`, re-call `request_enrollment` on a 1 / 2 / 4 / 8 / 16 / 30 s exponential-backoff schedule (it is idempotent — returns the row's current status without re-creating it). On `approved`, proceed to step 5; on `revoked`, enter the shutting-down phase (§ Shutting down). The bridge must **not** crash-loop on the pre-approval state — it waits in-process on the anonymous WS.
5. **Authenticate and open the running connection.** Once approved, run the standard challenge-response auth flow (per `docs/goal/architecture/transport.md`) — the bridge signs the nest-provided challenge with its Ed25519 secret key and nest mints a bearer token (approval inserted the audit `users` row, so auth now succeeds) — open the authenticated `/api/v1/ws/{actor_id}` connection, and call `fauna.bridges.whoami()`; it returns `status=approved` with the role nest assigned (the bridge's authoritative operating role).
6. **Attest the x25519 pubkey via `fauna.bridges.register_service_user(ed25519_pubkey, x25519_pubkey, role, bridge_id)`** before fetching config and opening listeners. nest seals every per-bridge wrapped blob — the TLS cert (`store_acme_material` fan-out) and the DKIM key — to this attested x25519 pubkey (storage-modes.md § Architectural rules rule 6). Without the attestation `bridge_service_users.x25519_pubkey` stays NULL, the cert + DKIM fan-out skip the bridge (`bridges_skipped_no_x25519`), and 465/993 never get a cert while DKIM signing has no key. The upsert is idempotent and the row is persisted, so the bridge attests **once at cold boot** — a reconnect (which re-runs `whoami` + `fetch_config`) does not need to re-attest. Attestation failure is fatal at cold boot (the supervisor restart retries), consistent with the other bootstrap RPCs. The call has since grown two additive, optional fields this doc doesn't own: a post-quantum `mlkem_ek` encapsulation key (`../architecture/security/post-quantum.md`) and a self-reported `confinement` diagnostic ([`../architecture/security.md`](../architecture/security.md) § Confinement self-probe).

### Pending approval

After the first `request_enrollment` (cold-boot step 3) creates the `pending` row, the bridge enters a **polling loop**: it re-calls `request_enrollment` on the anonymous WS on a 1 / 2 / 4 / 8 / 16 / 30 s exponential-backoff schedule (max 30 s between polls, no decay) until the returned `status` changes (`pending` → `approved` / `revoked`). Each poll re-uses the same anonymous WS connection (no reconnect, no token). `request_enrollment` is the pre-approval poll surface; `whoami` (authenticated, approved-only) is only reached *after* approval (cold-boot step 5).

While the bridge is polling, **the admin's Fauna app surfaces an approval card.** The admin's app reads `fauna.bridges.list_pending_bridges()` (a polled read; a dedicated pending-approval push event is a possible future refinement, not built); the `admin-bridges-pending` page — there is no separate bridges-detail page, § Service-user re-keying — renders one `admin-bridges-pending-card` per pending bridge with:

- The pubkey hex (truncated to first 16 + last 4 chars; full hex on hover/expand for verification against the bridge's log line from step 2 of cold boot).
- The role-hint the bridge declared in its `request_enrollment` call (`role_hint`, derived bridge-side from the keyfile basename — `mta` / `mda`; future bridges: `atproto.federation`, etc.), persisted as the pending row's role. The admin confirms it at approval (`approve_pending_bridge` validates the supplied role against this row's role).
- The connecting IP / hostname (for sanity checking against the deployment topology — for the supported single-container deployment this is always loopback, since `request_enrollment` is loopback-gated).
- The first-seen-at timestamp.
- An **Approve** button (`admin-bridges-pending-approve-button`) and a **Reject** button (`admin-bridges-pending-reject-button`).

Approval flow: admin clicks **Approve** → admin's app calls `fauna.bridges.approve_pending_bridge(pubkey_hex, role)` → nest flips the row to `approved`, records the approver, and inserts the audit `users` row (so the bridge's challenge-response auth now succeeds); the bridge's next `request_enrollment` poll returns `approved`, and the bridge authenticates + `whoami`s into the running phase (cold-boot steps 5–6). (The role is fixed at enrollment from the bridge's `role_hint`; `approve_pending_bridge` validates rather than re-assigns it.)

Rejection flow: admin clicks **Reject** → confirmation dialog ("Reject this bridge? It will not be able to connect again until an admin re-approves a fresh keypair.") → `fauna.bridges.reject_pending_bridge(pubkey_hex)` → nest moves the pubkey to the rejection list; the bridge's next `request_enrollment` poll returns `status=revoked`; bridge enters the shutting-down phase. Note: rejection is not "delete the pubkey row"; the row stays with `status=revoked` so subsequent connects from the same pubkey reject immediately without re-pending.

#### The retired pre-registration path

The pre-registration path described in `2026-05-07-mail-bridge-rearchitecture-design.md` § I2 slice 1 ("admin POSTs the bridge's pubkey to `/api/admin/bridges/pending` before the bridge ever connects") was a transitional bridge for the window before the admin-pane approval card existed. Its retirement condition — the card on all 7 apps — is met, so the routes (`GET|POST /api/admin/bridges/pending`, `POST /api/admin/bridges/{pubkey}/approve`, `POST /api/admin/bridges/{pubkey}/revoke`) are **removed**. Enrollment has exactly one surface: the bridge's own `request_enrollment` (§ Cold boot), then the admin's `approve_pending_bridge` / `reject_pending_bridge`, or `revoke_service_user` for an approved bridge. A fixture that needs a bridge approved before its process starts makes those same calls on the bridge's behalf.

### Default-off on first claim

A freshly-claimed nest (one where the admin has just completed `/data/claim-code` acceptance) has `mail.enabled = false`. The s6 service for `fauna-mail-bridge` is **supervised** (s6 knows about it, its run-script exists) but does not `exec` the binary — the run-script blocks on the `/data/imap-enabled` flag file's absence.

The supervisor pattern: each `fauna-mail-bridge-{mta,mda}` service is **down-by-default** (a `down` file) and its run-script re-downs a spurious up while `/data/imap-enabled` is absent; the supervisor never polls the filesystem — nest signals the `fauna-supervisor` sidekick service (which owns the socket → `s6-svc` dispatch) when it writes the flag. One process + one keypair **per role** — `mta.key` and `mda.key` (§ Multi-role multi-process). `--nest-endpoint` is the **loopback base URL** (the bridge appends `/api/v1/ws/<actor_id>` itself; § Cold boot). The realized run-scripts are owned by `installers/docker.md` § s6-overlay Services (`docker/s6/fauna-mail-bridge-{mta,mda}/run`) — this doc owns the semantics, not the script text.

The admin flow:

1. **Admin turns mail on in the Fauna app → admin's app calls `fauna.bridges.set_mail_enabled(true)`.** Realized (design A) by the admin **enabling mail on the `mail-settings` page**: `MailSettingsMachine::enable_mail` (shared Rust, `libs/fauna-client-mail-settings`) — which the admin runs anyway to mint their own mailbox — fires `set_mail_enabled(true)` as its final step. The call is **Admin-class on the nest, which is the scoping**: the admin (the first user) flips the deployment subsystem on; a non-admin enabling their own mailbox is rejected server-side (a no-op), so the machine swallows that `Rejected` and surfaces only a `Transient` (connectivity) failure. Beyond mail-settings there is **one earlier enable trigger, now machine-derived at claim**: `email_enable_requested()` (`onboarding.md` § 3b), **default ON for a real-domain handle** (OFF for `localhost` / IP) — no onboarding checkbox to toggle it (the former `onboarding-enable-email-checkbox` retired with `encryption_mode_choice`, not relocated; no-modes, ratified 2026-07-12). It **auto-completes** the box's mail setup — the authed launch glue mints the admin's mailbox with a generated password and the box's own bridges are auto-approved (§ Onboarding auto-approval); because onboarding is pre-identity and `set_mail_enabled` is Admin-class, the machine records the derived intent and the authed launch glue runs the full mail-enable (mailbox mint + `set_mail_enabled(true)`). The two paths are **idempotent** — enabling at claim and again on mail-settings do not conflict. Apart from these, there is **no separate "mail on/off" admin toggle element** — enabling the admin's mailbox *is* turning the deployment on. (Before any app dispatched `set_mail_enabled`, a real Docker/systemd deploy never wrote the flag and the bridge never booted even though every binary e2e was green — the gap the tier_4 `test_mail_client_ui_enable_docker` regression pins.)
2. **Nest writes `/data/imap-enabled`** synchronously (touch-create with mode 0600, owner the `fauna` user), then sends an `up` command for **each** mail-bridge role service (`fauna-mail-bridge-mta`, `fauna-mail-bridge-mda` — one process per role, § Multi-role multi-process) via the nest→supervisor sidekick socket (a Unix-domain socket the s6 entrypoint creates at `/run/fauna-supervisor.sock`; nest writes one line-framed JSON command per service, supervisor maps each to `s6-svc -u`). (The persisted `mail_enabled` DB toggle — now the authoritative enable-state that `fetch_config` reads and the boot-plus-60 s reconcile re-asserts the flag from — landed in Phase E; see § Implementation status today.)
3. **s6 receives the up command**, the run-script's `s6-svwait` returns, the run-script proceeds to `exec` the bridge binary.
4. **Bridge binary's cold-boot dance** begins (keypair generation if first run, then enrollment dance).
5. **The box's own bridges are auto-approved** — the admin's enable in step 1 *is* the approval (§ Onboarding auto-approval); no card to click. (A bridge enrolled out-of-band — mail disabled, or a future non-mail role — still surfaces a pending-approval card for a manual click.)
6. Bridge enters running phase → mail is live.

**Mail-domain safety net (enable- and boot-time).** Step 2 has a precondition the bridge cold-boot depends on: at least one `mail_domains` row must exist, because the bridge's `local_domains` projection and the ACME cert SAN set are both derived from `list_active_mail_domains()` — an **empty** table means the MTA/MDA bind nothing and mail never serves (and DKIM provision-on-read never fires, since it gates on an active local mail domain — see § DKIM provisioning). The primary mail domain is normally written at claim time (`mail-multidomain.md` § The primary domain), but a re-claim that carries no `mail_domain` (e.g. re-claiming a factory-reset box, whose DB — including `mail_domains` — was wiped) leaves the table empty, and there is no post-claim app `add_local_domain` affordance yet (§ Implementation status). So an idempotent safety net (`mail_enable::ensure_primary_mail_domain`) fires from **two triggers**, each one **before** the relevant bridge cold-boot: when `mail_domains` is empty it auto-registers the nest's own domain (`AppState::handle_domain`) as the primary — **gated to a real domain** by the same loopback/IP predicate `email_enable_requested()`'s machine-derived default uses (`resolve_handle_domain(d).is_public_dns_name`; a `localhost`/IP/`.local` nest is skipped, since mail needs real DNS + public TLS). The two triggers:

- **enable transition** — `set_mail_enabled(true)` calls it before the supervisor brings the services up, so a normal claim→enable flow provisions the domain.
- **nest boot** — `lib.rs` startup calls it (when `mail_enabled` is already true) *before the WS server accepts bridge connections*, so a box that booted enabled-but-domainless self-heals on its next restart. Provisioning at nest boot (the bridge runs in the same container, cold-booting after nest) guarantees a non-empty `local_domains` on the bridge's first fetch — a belt to the braces of § *An idling bridge stays subscribed*, which is what now brings an already-idling MTA live when a domain is added under it. (Until 2026-08-21 there were no braces: an idling bridge observed no config change at all, so this trigger was the *only* thing standing between an enabled-but-domainless box and a mail subsystem that never served.)

It shares `ensure_mail_domain_registered` with the claim path and **composes** with it (fires only when nothing is registered, so a user who chose a different mail domain at claim is never overridden). Net effect: on a real-domain box, mail enablement always leaves a working primary mail domain regardless of how the box was (re-)claimed.

Reverse flow (admin toggles `mail.enabled` OFF):

1. **Admin toggles `mail.enabled` OFF** → `fauna.bridges.set_mail_enabled(false)`.
2. **Nest sends a `down` command for each role service** (`fauna-mail-bridge-mta`, `fauna-mail-bridge-mda`) via the sidekick socket (supervisor maps each to `s6-svc -d`).
3. **s6 sends SIGTERM** to the bridge process.
4. **Bridge enters shutting-down phase** (drains in-flight transactions for up to `mail.bridge.shutdown_grace_seconds` seconds, default 30, Tier-2; on grace expiry, hard-exit).
5. **Nest unlinks `/data/imap-enabled`** after the supervisor confirms the service is down (the sidekick socket returns the s6 ack).
6. **The s6 supervisor stays supervising** but the run-script blocks on the flag's absence again — the cycle is restartable with a re-toggle.

The flag file is **nest's output, never anyone's input.** Nobody hand-edits it — a deployment has no operator (`../principles.md` § One configuration surface) — so a flag that disagrees with the stored toggle is a torn write or a fault, and nest's flag-vs-state reconciliation (a pass at boot, then every 60 s) **repairs it**: it rewrites the flag from the toggle and logs `bridge_flag_file_diverged_from_state`. That log line is the whole surface, by ruling (2026-10-01): a divergence the nest has already repaired leaves the admin nothing to do, so no app shows it. (Until then this paragraph promised a warning in the admin pane; none was ever built, and the sentence's "hand-editing" described a person the product does not have.)

#### Why the supervisor sidekick socket, not filesystem polling

Filesystem polling on `/data/imap-enabled` would mean s6 wakes up every N seconds to `stat` the file — adds latency to the toggle (up to N s) and adds idle CPU. The sidekick-socket approach is event-driven: nest writes the flag + sends one command + the bridge is up in milliseconds. The socket is a Unix-domain socket at a well-known path inside the container; only nest (running as the `fauna` user) can write to it; supervisor receives `up <service-name>` / `down <service-name>` commands and dispatches via `s6-svc`. The same pattern applies on systemd-deployed bare-metal nest (the sidekick is a small helper systemd service holding the socket; nest writes commands, helper dispatches via `systemctl`).

### Onboarding auto-approval (the box's own bridges)

The default-off → approve flow above (steps 5–6) is the **general** lifecycle, where an admin reviews each pending bridge and clicks approve. For the **deployment's own co-located mail bridges on the admin's enable**, that click is **automatic**: when an admin enables the mail subsystem (`set_mail_enabled(true)`, Admin-class), the box's own MTA/MDA enrollments are approved with no manual click. This is the "works out-of-the-box" path — the machine-derived enable-email intent firing at claim (no onboarding checkbox to check; `onboarding.md` § 3b) or enabling on `mail-settings` yields a serving mailbox with no further admin step beyond publishing DNS (`onboarding.md` § Enable-email at claim).

**Why this is not the forbidden "auto-approve on first connect" (§ Architectural rules / § Don't do these).** Two facts bound it to the box's own bridges:

1. **Loopback origin + blessed-key proof-of-possession.** `request_enrollment` is loopback-gated (§ *Self-enrollment is loopback-gated*) — a remote / network-path peer is **refused** and never creates a `pending` row. So every pending bridge is necessarily a **same-host** process inside the deployment trust boundary; the "attacker who reached the nest endpoint via a compromised network path" the general rule guards against cannot enroll at all. On an image deploy the **strict mode** narrows this further: enrollment requires the artifact-provisioned blessed pubkey plus a verifying Ed25519 proof-of-possession signature (§ Cold boot step 3; `architecture/security.md` § Enrollment proof-of-possession contract), so even a malicious same-host process that cannot read the UID-isolated key file cannot enroll.
2. **Admin-class enable.** The auto-approval window is opened only by `set_mail_enabled(true)`, an **Admin-class** call — the admin's enable *is* the admin completing approval for the box's own bridges. A non-admin cannot open it.

So the trust anchor is **(loopback origin) + (the Admin-class enable toggle)**, not "any bridge that connects." The residual exposure is a malicious *same-host* process racing the real bridge to enroll — which already requires same-host code execution (inside the trust boundary), the same exposure the manual pubkey-eyeball does not actually defend against (an admin cannot distinguish a legitimate from a forged 32-byte pubkey by sight).

**Mechanism (nest-side).** Auto-approval lives in the nest's `request_enrollment` handler, with a **per-role enablement condition** (the `auto_approve` match, `bridge_blob_handlers.rs:904-920`): a loopback (and, in strict mode, blessed-key-verified) enrollment lands `approved` (recorded with a `None` / system approver) instead of `pending` — for **MTA** iff the `mail_enabled` DB toggle is `true`; for **MDA** iff `mail_enabled || caldav_enabled || carddav_enabled || webdav_enabled` (a DAV-only box — calendar/contacts/files enabled, mail off — must still boot its MDA, which serves those surfaces); the other two roles, **`content-processor` (`BridgeRole::ContentProcessor`) and `atproto.pds` (`BridgeRole::AtprotoPds`), never auto-approve** — both always take the manual approval card. Because the enabling toggle is persisted before the supervisor brings the bridge up (§ Default-off step 2 precedes step 3), the bridge's first enrollment already sees its condition true and lands approved; a bridge that enrolled `pending` *before* the admin flipped the toggle self-heals to `approved` on its next poll. The bridge still **self-generates its own keypair** (§ Architectural rules — *Keypair generation is bridge-side*); only the approval *trigger* changes, so the nest never touches the bridge's private keys.

**Scope (narrow, uniform).**

- **Mail/DAV roles only, per the conditions above.** A future non-mail bridge role (ATProto, Nostr, …) is **not** auto-approved by these toggles, and `content-processor` never is; both fall back to the manual approval card.
- **Disabled stays manual.** With the role's enabling toggle(s) off/unset (mail for the MTA; mail + the DAV axes for the MDA), enrollment lands `pending` for an explicit admin approval (the general flow).
- **Revoked stays revoked.** Auto-approval only flips `pending` → `approved`; an admin's reject (§ Pending approval — rejection flow) is durable and never resurrected by a re-poll.
- **Uniform across the lifecycle.** The same rule covers onboarding, factory-reset → re-claim → re-enable (§ Factory reset), reconnect, and re-keying — there is no first-only special case, because the manual pubkey-eyeball adds no security the loopback gate does not already provide.

**Implementation status.** The nest-side auto-approval (this section's mechanism) is **landed** (`request_enrollment_handler`, `bins/fauna-nest/src/bridge_blob_handlers.rs`). The *mailbox* auto-mint half — the post-claim launch glue calling the shared `enable_mail_with_generated_password` helper (`fauna-client-mail-settings`) instead of bare `set_mail_enabled` (`onboarding.md` § Enable-email at claim) — is **built on all seven apps** (corrected here — this bullet had stale-marked five of them "remaining" long after they shipped): linux (lead), web/windows/android (2026-06-12), macos/ios (2026-06-16, shared FaunaKit `MailEnableGlue`), tui (2026-07-19, ported alongside the onboarding wizard).

### Running

The bridge holds the WS connection open, listens on its protocol-specific ports, processes traffic, fires verdict logs (see `mail-observability.md`), and applies config changes received via `fauna.bridges.config_changed` push events without restart. `subscribe-and-hot-reload is mandatory` per `mail-policy-config.md` § Architectural rules — every config knob applies at the next request boundary, no SIGHUP, no in-place file reload.

Health is implicit in the WS connection liveness — a bridge that can hold the WS open is alive. There is no separate bridges-detail page (§ Service-user re-keying) and no per-bridge heartbeat/last-activity tracking today — `BridgeServiceUser` (`bins/fauna-nest/src/db/bridge_service_users.rs`) carries no `last_seen_at`/`last_heartbeat_at` column, and the `admin-bridges-pending` page's Approved-bridges roster surfaces only `admin-bridges-approved-approved-at`, not a live last-activity readout (corrected here — an earlier draft of this doc described unbuilt heartbeat tracking as shipped).

#### An idling bridge stays subscribed

A role decides its listener set **once**, from the snapshot it cold-boots with, and a role whose gates are all shut binds nothing and **idles**: the MTA when mail is disabled or no `mail_domains` row exists; the MDA when mail, CalDAV, CardDAV and WebDAV are all off. Idling is not a lesser state of the lifecycle — the "subscribe-and-hot-reload is mandatory" rule above holds there too. **An idling bridge holds its WS open, stays subscribed to `fauna.bridges.config_changed`, and re-fetches on every push and every reconnect, exactly as a serving one does.**

What it does with the re-fetched snapshot is the one thing that differs: it re-evaluates its own startup gates, and when they open it **exits 0 for the supervisor to restart it bound** — the same exit-for-rebind a *serving* MDA performs when its gating tuple flips (§ *Independent enablement* in `caldav-server.md`). An in-process listener set cannot be re-bound live, so a fresh process is the simplest correct rebind; the supervisor (s6 in the image, the sidekick helper on systemd) is what performs it, which is why the gate-open path returns cleanly rather than binding in place. Each role reads one predicate for both directions (`mta.Bindable`, `mda.Bindable`), so it can never idle on a snapshot it would also wake for — a restart loop — nor wake for one it would then idle on.

Implementation: `bins/fauna-bridges/internal/wsrpc/idle_gate_watch.go`, called from each role's idle branch.

One thing the idling role does that a serving one must not: **a re-fetch that fails retries.** Dropping a failed fetch and keeping last-good config is right for a serving role — its listeners have a config to keep — but an idling role has no last-good serving state, so losing the single fetch that an admin's enable provokes would leave it idling until an unrelated second config change or a restart. The idle path therefore re-arms its own reload trigger after a fixed 3 s; the retry drains through the ordinary reload loop and applier, so there is no second code path, and the serving path's drop-and-keep-last-good is untouched.

The fixed, non-escalating cadence is safe because neither failure mode it can meet costs the nest anything. A **busy** nest makes the fetch *slow*, and the 30 s `fetch_config` timeout puts the real cadence at ~33 s — slower than the 30 s reconnect cap below — so the case where retrying would hurt most self-throttles. A **disconnected** nest makes the call fail without any I/O at all, so those retries never reach it; in that window the retry is redundant with the reconnect re-fetch (next section), which is what actually recovers the gate. Neither mode amplifies load on a nest that is already struggling.

**Before 2026-08-21 this was not true**, and the gap was invisible precisely because the deployment normally hides it: under s6 a bridge whose subsystem is off is not *running* at all (§ Default-off on first claim), so "an idling bridge misses config changes" almost never has an observable victim in production. The idle branches blocked on `<-ctx.Done()`, which returns before the role builds its `ConfigReloader` — so an idling bridge had no subscription whatsoever, and an admin's enable reached it only if something else restarted the process. Any deployment or harness that starts a bridge *before* its subsystem is enabled sat squarely in that hole; the e2e `dedicated_mail_nest` fixture, which spawns both bridges and then enables mail through the app UI, is how it was finally caught.

### Reconnecting

When the WS connection drops — nest restart, network blip, NAT timeout, idle close — the bridge enters reconnect-backoff: 1 / 2 / 4 / 8 / 16 / 30 s (max 30 s, no decay). Each reconnect attempt:

1. Re-runs the WS handshake with its cached bearer, re-minting it once over challenge-response when the nest refuses it at the upgrade — the HTTP `401` a nest restart gives every bearer it forgot (`architecture/transport-connection.md` § Connection lifecycle → *Upgrade-time auth rejection*).
2. Calls `whoami` (because the admin may have revoked the service user while the bridge was disconnected — the bridge must re-verify status). A revoked bridge is *denied* whoami outright (`fauna.bridges.permission_denied` — the capability gate refuses its identity before the handler runs), so the client classifies the outcome via `wsrpc.WhoamiIndicatesRevoked`: an identity-level denial means revoked → graceful shutdown; any other error is transient → retry.
3. Calls `fauna.bridges.fetch_config(role)` (because the admin may have changed config while nest was down — the bridge must re-fetch).
4. Re-subscribes to `fauna.bridges.config_changed` push events.

**Listeners stay up across reconnect attempts.** The SMTP / IMAP / CalDAV listeners themselves don't depend on nest for connection-time policy — they're armed with the last-known config snapshot; verdict-needing RPCs (DKIM verification, spam scoring, delivery routing) queue against the WS connection and tempfail with `451 4.7.1 Temporary system failure, retry later` if the reconnect takes longer than 30 s (the next per-recipient retry from the sending MTA will succeed once nest is back).

The reconnect-backoff cap (30 s) is **not configurable** — too short and a bridge that flaps overwhelms nest with reconnect storms; too long and a real outage takes too many minutes to recover from. 30 s is a compromise that the long-term question ratifies.

### Shutting down

Shutdown is triggered by one of three events:

1. **SIGTERM** from the supervisor (admin toggled `mail.enabled = false`, or the container was stopped).
2. **Nest refuses the bridge's identity** during the running or reconnecting phase (admin clicked "Revoke service user" in the admin pane, or "Reject" on a pending bridge whose run-script raced ahead). Detected as an identity-level `permission_denied` — via the standing probe on a live connection, or the reconnect-time whoami after nest's revocation teardown force-closes the socket (4401); a revoked bridge never receives a `status=revoked` whoami *reply*, only the pre-approval `request_enrollment` poll reports that status explicitly.
3. **Internal fatal error** the bridge can't recover from (keypair file became unreadable, structured panic from the listener code, etc.).

The shutdown sequence:

1. **Stop accepting new connections** on all protocol listeners (the OS-level accept loop closes the listening sockets; in-flight connections keep going).
2. **Send `421 4.3.2 Service shutting down`** on any new MAIL-FROM (SMTP) or `BYE` (IMAP) on any new EXAMINE/SELECT (IMAP) — protocol-specific graceful-rejection.
3. **Drain in-flight transactions** for up to `mail.bridge.shutdown_grace_seconds` seconds (default 30, Tier-2; target: admin-tunable 0–300 — today fixed at the 30 s catalog default, the `put_bridge_policy` write-path is still pending per § Implementation status).
4. **On grace expiry**, force-close all in-flight connections, emit a structured-log line `bridge_shutdown_force_close pending_count=<N>`, exit.
5. **Close the WS connection** to nest with a clean close-frame (status code 1000).
6. **Exit** with status 0 (clean shutdown) or 1 (forced).

The supervisor sees the exit code and either leaves the service down (admin-initiated shutdown via the flag-file unlink) or restarts it (unexpected exit — the bridge crashed, and the supervisor starts it again). **A helper that cannot stay up is shown to the admin by the mail health readout, not by an alert of its own (ruled 2026-10-01):** while mail is on and an approved MTA or MDA bridge has no live connection, `fauna.bridges.mail_health` folds to `bridge_down`, and the Mail page and the dashboard's Mail card say the mail service is not connected (`mail-deliverability.md` § Admin-pane Deliverability surface → *The mail health readout*). Until then this sentence promised a `bridge_supervisor_restart_loop` alert after "the s6 default 3-times-in-30s threshold"; neither existed — no supervisor in the tree counts restarts, the image's s6 services carry no such threshold, nothing in the nest or any app knows the name — and a helper being down is below the critical-alert bar by that doc's own rule (`critical-alerts.md`). A restart counter would tell the admin nothing the not-connected state does not.

## Service-user re-keying

The service-user keypair on disk is the bridge's identity to nest. Rotating it is an admin-initiated operation:

1. **Admin clicks "Rotate service-user key"** on the bridge's card in the **Approved bridges** roster of the `admin-bridges-pending` page (`admin-bridges-approved-rotate-button`). There is no separate bridges-detail page — the approval-card page carries both the pending cards and the approved roster (`admin.md` § Bridge display naming; ui.yaml `admin-bridges-pending`). The roster is fed by `fauna.bridges.list_service_users(status="approved")`; the button's `bridge_actor_id` is the card's Ed25519 pubkey.
2. **Confirmation dialog** (`admin-bridges-rotate-confirm`) explains: the bridge will be marked `revoked`, the running bridge will exit, the supervisor will restart it, the new keypair will need re-approval (automatic on a mail-enabled box). The dialog shows **no DKIM warning for any role**: a re-key touches no DKIM key and no published record (the DKIM-consequence note below).
3. **Admin confirms** → `fauna.bridges.revoke_service_user(bridge_actor_id)` → nest sets `bridge_service_users.status = revoked`.
4. **The running bridge notices immediately and enters the shutting-down phase.** The revoke tears down the bridge's live authority at the source (transport.md § Revocation teardown, wired 2026-07-12): nest revokes its bearer, **force-closes its WebSocket with 4401**, and purges its mailbox-state push subscriptions (`BridgePushRegistry::remove_mda` — the entries would otherwise resume streaming per-user mailbox metadata to a socket the leaked key re-opens, since a Push consults no capability gate and the mint gate never reads `bridge_service_users`). The 4401 drives the bridge's `ReconnectingClient` into a reconnect whose `whoami` nest denies (`fauna.bridges.permission_denied` — a revoked bridge never sees a `status=revoked` *reply*); the client maps that identity-level denial to `ErrBridgeRevoked` (`wsrpc.WhoamiIndicatesRevoked`) → graceful shutdown. Belt-and-braces, the **standing probe** (`internal/wsrpc/reconnect.go::probeStanding`) still covers a denial arriving on a connection that somehow outlived the teardown: any `permission_denied` reply triggers one `whoami` on that same connection — `whoami` is allowlisted for every approved bridge, so it too being denied proves the denial is identity-level, not kind-level, and finishes with the same `ErrBridgeRevoked`. A kind-level authz miss (whoami still healthy) passes through untouched.
5. **Supervisor restarts the bridge** (after the s6 restart cooldown, ~1 s).
6. **Bridge re-runs cold boot and detects the revocation at the enrollment poll.** The keypair file exists but its pubkey's row is `revoked`, so the cold-boot `request_enrollment` call (§ Cold boot step 3 — the pre-approval status surface; `whoami` is authed + approved-only and never reachable here) returns `status=revoked`.
7. **Bridge auto-regenerates:** it archives the old keypair at `<keypair>.revoked.<unix-time>` (mode 0400, read-only — preserved for forensic / audit purposes), **generates a fresh keypair**, writes it to the original path, and re-runs cold boot from step 3 — the fresh pubkey has no row, so `request_enrollment` creates a new `pending` enrollment → pending-approval phase. (Go: `keypair.ArchiveAndRegenerate` + the enrollment retry loop in `cmd/fauna-mail-bridge/main.go`; at most one regenerate per process run — a second `revoked` is a deliberate admin rejection and the bridge exits cleanly instead of minting keys in a loop.) **Strict-enrollment composition (the image path):** the fresh key is not yet the artifact-blessed key, so its first `request_enrollment` is rejected `permission_denied`; the bridge exits 0, the supervisor restarts it, and the role's s6 run-script — root, before the privilege drop — re-derives the blessed pubkey from the keyfile at the UID-isolated path and republishes the root-owned registry entry (`docker/rebless-bridge-key.sh`, called by both bridge run-scripts; a no-op on a normal start). nest reads the registry **live per enrollment** via the `FAUNA_BLESSED_KEYS_DIR` IPC env (a path, not a boot-time value snapshot — `bridge_blob_handlers::blessed_pubkey_from_dir`), so the re-bless reaches the running nest with no nest restart. The trust anchor is unchanged in strength: "the key at the root-verified, UID-isolated `/data/keys/<role>/<role>.key`" — a co-resident non-role UID still cannot write that path (0700 subdir) so it cannot get a rogue key blessed, and the role UID itself already holds the role's private key, so re-deriving from its keyfile grants it nothing it lacks (`security.md` § Enrollment proof-of-possession contract).
8. **Admin sees the new approval card** in the admin pane → clicks Approve → bridge enters running phase with the new key. (On a mail-enabled box the box's own bridge auto-approves per § Onboarding auto-approval — the admin's revoke was the security decision; the re-key completes hands-free.)

> **Implementation status (built 2026-07-09; ratified 2026-07-08, cluster-#3 review L1): steps 6–7's auto-regenerate is BUILT, both modes.** Lenient (dev/binary) mode completes fully in-process; strict (image) mode adds one supervisor restart for the root-mediated re-bless, per step 7's composition note — the bridge process alone deliberately cannot complete a strict-mode re-key (the registry stays bridge-UID-unwritable). The earlier draft of this flow keyed detection on `whoami` at cold boot — refuted: `whoami` denies non-approved callers; `request_enrollment` is the pre-approval surface.

**DKIM consequence of an MTA re-key — none.** The DKIM key is the nest's (§ DKIM provisioning (automatic) → *Custody moves to the nest*), so `fauna.bridges.revoke_service_user` on an MTA-role bridge is the plain `CacheDb::revoke_bridge_service_user` — one row write that touches no DKIM key and no published record — and the successor bridge relays mail the nest signs under the same selector. An MDA revoke is the same write. Pinned by `bins/fauna-nest/tests/mail_dkim_oracle.rs::revoking_the_mta_refuses_its_hand_out_and_leaves_the_key_alone` and, across a nest kill mid-revoke, by `test_crash_recovery_journeys.py::test_kill_nest_mid_mta_revoke_leaves_dkim_key_untouched` (`../architecture/nest/common.md` § Client-state recoverability). TLS is unaffected too — `fetch_tls_cert_blob` is seal-on-read, so the re-keyed bridge gets the current cert on its first fetch.

The whole rotation is bounded by: time-to-confirm + supervisor restart cooldown (~1 s) + new keypair generation (~10 ms) + the approval (automatic for the box's own bridges; the admin's reaction time otherwise). With an attentive admin, ~30 s end-to-end; with the admin away, the bridge stays in pending-approval until they return — which is the right shape because rotation is a security-sensitive change, and "rotation completes without the admin's awareness" would be the wrong default.

**What `mode 0400` guarantees, and how Windows spells it (ruled 2026-09-11).** The
archive's mode is there for **read-only preservation** — the revoked key is audit
evidence and must not be altered or auto-deleted — and `0400` is how a POSIX
filesystem spells that. **Windows has no such spelling and does not need one:** NTFS
security is ACL-based, its file attributes carry a single read-only flag, and Go's
`os.Chmod(path, 0400)` sets exactly that flag, which `stat` then reports as `0444`.
Access control proper is the ACL of the bridge's data directory (per-user
`%LOCALAPPDATA%`, or the service account's directory under the installed
`FaunaBridge` service — `../architecture/installers/windows.md`). This is the **same
rule the LIVE keyfile already follows**: `keypair.LoadOrCreate` skips its `0o077`-clean
gate on Windows because a mode check there is "both meaningless and unsatisfiable",
and names those ACLs as the protection instead. The live key holds the same two
long-lived secrets as the archive, so hardening the dead copy past what guards the
live one would be incoherent — the archive follows the live key's rule rather than a
second one of its own. Tests therefore assert *no write bits* on Windows and the exact
`0400` on POSIX, not the POSIX triad everywhere.

**The archived old keypair file** at `<keypair>.revoked.<unix-time>` is kept indefinitely on the bridge's local disk. Disk pressure is non-issue (a keypair file is < 1 KiB; even with quarterly rotation, 100-year history fits in 400 KiB). The archive serves audit / forensics: if a private key was suspected of compromise, the archive lets the investigator confirm "yes, that key was active from T1 to T2, here's the file." Deletion is the user's prerogative, not automatic.

**DKIM key rotation is separate.** DKIM private keys are the nest's own, sealed at rest and opened only to sign at the outbound hand-out; rotation is **nest-side and scheduled** — a fresh key under a new `<YYYYMM>` selector (the per-domain cadence lever `fauna.bridges.set_dkim_rotation_days`, the immediate `fauna.bridges.force_rotate_dkim`, and selector retirement via `fauna.bridges.revoke_dkim_blob`), detailed in § DKIM provisioning (automatic) → Rotation above and `mail-multidomain.md` § Rotation — not the service-user-key flow described here. The two rotation paths are orthogonal: the service-user key is the bridge's identity to nest; the DKIM key is the deployment's identity to peer MTAs.

## DKIM provisioning (automatic)

DKIM signing keys are provisioned **automatically** — like TLS/ACME, with **no manual admin UI** (decided 2026-05-24, `dkim-tls-automatic-no-manual-ui`). The DKIM-only `admin-mail-deliverability` page that earlier drafts described here is **dropped entirely**. This section owns the **key half** (the nest-held signing key + the unsealed `public_dns_value` it yields); the DKIM DNS **record** — displaying it, verifying it red/green, publishing it when Fauna controls the domain's DNS — is one record among all the deployment's DNS on the unified surface of `docs/goal/behavior/dns-management.md`, rendered from `fauna.bridges.list_dkim_selectors`.

**Mechanism — the nest holds the key and mints it at a deliberate door** (built 2026-10-03). Keygen runs **nest-side**: DKIM is freshly-minted signing material like the ACME-minted TLS key, so the `client-holds-provider-keys-not-nest` directive — which governs *user-owned* provider API tokens (DNS/VPS), not auto-generated keys — does not push it client-side, and no client ever holds it. The private half rests sealed under the nest's own key-encryption key and is opened only to sign. One keygen: `fauna_provisioning::dkim::mint_signing_key`.

**Custody moves to the nest (RULED 2026-10-03; BUILT 2026-10-03).** One store, one signer: the nest keeps every (domain, selector) DKIM private key itself (`mail_dkim_keys`) and signs outbound mail as it hands the mail to the MTA. No bridge holds, fetches, unseals or signs with a DKIM key; the MTA relays the bytes it is handed verbatim. The key's own entry — seal, context string, audience, threat model — and the reason the class is no Fauna-family oracle class are [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Audience: deployment infrastructure → *The oracle* → *The DKIM class is the outbound spool's own door*; this section owns the custody decision and the mechanism.

- **Why the key is the nest's and not the MTA's.** Sealing the key to the MTA (the 2026-06-01 shape, removed 2026-10-04) buys little: the nest mints the key and names the public half the admin publishes, so a compromised nest can already sign as the domain with a key of its own making. It costs three things. (1) An MTA re-key would destroy every DKIM key and leave the published record stale, coupling the bridge's identity to the deployment's identity to peer MTAs where § Architectural rules calls them orthogonal. (2) A second MTA could not sign. (3) The key would live in the process that faces the internet on port 25, while mail the nest composes itself — an app send through `fauna.email.send`, a bounce — would leave with no DKIM signature at all, the nest having no key to sign it with.
- **When the key mints — never by a read.** At boot, for every active mail domain whose active selector has no key — the fresh box and the upgrading box alike (`mail_dkim_key::mint_for_keyless_domains`, a member of the boot step `nest_kek::mint_at_boot`); in the door that activates a mail domain (`CacheDb::add_mail_domain` and `restore_mail_domain`, on the connection that writes the row); and in the scheduled rotation mint (`mail-multidomain.md` § Rotation). Every door seals under the deployment seed read on the connection it inserts on; the rule and its reason are `key-material-hierarchy.md` § Room-read keypair → *When it mints*. No approved MTA is needed first, so the DNS record exists the moment the domain does. A door whose (domain, selector) has a key a factory reset carried adopts that key in place of minting (`../architecture/nest/common.md` § Factory reset → *The DKIM keys are carried*).
- **Where it signs — one site.** Every outbound message, from every door, rests in the nest's `outbound_mail_queue` and leaves through `fauna.bridges.fetch_outbound_due` (`smtp-server.md` § Outbound delivery). That hand-out is the sign site (`mail_dkim_key::OutboundSigner`, loaded once per batch — a lookup, never a mint). A unit that carries exactly one From field naming exactly one mailbox, whose domain selects a local signing domain (`mail-multidomain.md` § Signing-key selection at outbound time, against the nest's own `mail_domains` rows and never anything the caller says), and for whose active selector the nest holds the key, leaves with the signature prepended. Every other unit leaves as it rests. The row itself rests unsigned and is signed afresh at each hand-out, before the staging decision (a staged body is the signed bytes), so a retry after a selector flip carries the new selector. A missing key, a key that will not open or a sign failure ships the unit unsigned and counts it (`mail_dkim_key::unsigned_handouts`); it never holds the queue. The signature exists only on what leaves through the hand-out: local (Fauna-to-Fauna) copies, the Sent copy and the bytes the bridge enqueues are unsigned.
- **No signing kind, no signing wire field, no failure of its own.** The MTA can deliver nothing without `fetch_outbound_due`, so a nest it cannot reach stops delivery with or without signing, and signing adds no outage of its own. Submission mail, auto-replies, list-send copies (`mail-mass-mailing.md`), app-composed mail and bounces are all signed at this one site.
- **What follows.** `revoke_service_user` on an MTA touches no DKIM key and no DNS record; a second MTA needs nothing to sign; the DNS page shows a selector whether or not a bridge is enrolled.
- **The sealed-blob path is removed (2026-10-04).** The MTA-sealed store (`bridge_dkim_blobs`), the kinds `fauna.bridges.fetch_dkim_blob` and `fauna.bridges.provision_dkim_blob`, the wire field `OutboundUnit.needs_dkim_signing` and the bridge's unwrap-and-sign code do not exist (`libs/fauna-protocol/schemas/ratified-breaks.txt`, the 2026-10-04 block). **Timing ruling:** no holder of the sealed form can exist once the public repository is minted — the bridge ships inside the nest image at the nest's own version, so there is no older bridge build to serve, and under the 2026-09-24 baseline reset no installation or data predates the baseline — so the path was removed outright rather than by expand→migrate→contract (`../architecture/version-compatibility.md` § Dimension 2, the fourth ratified exception). **No upgrade path remains:** the one-shot step that dropped the store from an existing database (nest schema 123) left with the second genesis collapse on 2026-10-04 (`../architecture/version-compatibility.md` § 2.2), and a database that held a sealed blob is one the genesis refuses at open. The blob was deployment-infrastructure material the nest could not open, never user data.
- **What the move does not yet buy.** The nest signs what the bridge enqueued. From-header *ownership* at the SMTP submission door (`mail-multidomain.md` § From: header ownership) is still checked bridge-side only, so a compromised MTA cannot take the key but can still have a message signed. The nest-side check at `fauna.bridges.enqueue_outbound_mail` is owed.
- **As built.** The table and its doors: `bins/fauna-nest/src/mail_dkim_key.rs` (`mail_dkim_keys`, nest schema 122, a `nest_kek::SATELLITES` member; schema 124 adds the factory-reset carry stamp). The sign site: `bridge_routing_handlers.rs::fetch_outbound_due_handler`. The selector reads — `fauna.bridges.list_dkim_selectors`, `fauna.setup.status` `dkim_records`, `force_rotate_dkim`, the auto-flip, the rotation mint's gate — all read that one table (`CacheDb::list_dkim_selectors`), and `fauna.bridges.revoke_dkim_blob` retires a selector's key from it (`CacheDb::delete_dkim_selector`). The Go bridge reads `fetch_config`'s `dkim_selectors` for one thing only — the From-header ownership check at submission (`550 5.7.7 From: domain not local`), which keys on the configured selector set.

**Prerequisite — none.** The key is the nest's own, so it needs no approved bridge: a selector and its DNS record exist from the moment the mail domain does.

**Automatic flow.** Adding (or restoring) a mail domain mints an Ed25519 DKIM keypair for the domain's active selector on the connection that writes the row; boot does the same for any active domain found without one. The sealed private half and the unsealed `public_dns_value` persist in `mail_dkim_keys`, so the published DNS public key is **stable** — nothing re-mints an existing selector. No admin clicks, no form. The selector is the domain's `fetch_config` `dkim_selectors` entry (defaults `"default"`; tracked internally). **Any number of MTAs:** none of them holds the key, so a second approved MTA delivers signed mail exactly as the first does.

**Deployment-level coverage.** Two tier_4 tests pin the automatic mechanism on the real deploy image (`tests/e2e-unified/tests/platform/docker/test_mail_deploy_dkim_auto_enable.py`): `test_nest_auto_provisions_dkim_signed_outbound` proves the nest auto-provisions + signs (a `d=`-aligned `DKIM-Signature` on the relayed message), and `test_nest_dkim_signature_verifies_against_published_record` **cryptographically verifies** that relayed signature against the nest's stored `public_dns_value` (the `b=` ed25519 check) — proving the key the deployment signs with and the public half the nest reports for publication are a **matched pair end-to-end**. The latter catches a **store / publish-vs-key divergence** that the matched-pair unit round-trip (`libs/fauna-mail/tests/dkim_tests.rs`, one keypair by construction) structurally cannot, and is the deployment-level complement to gate 6's live DNS-vs-stored check (tracked internally (C), 2026-06-23).

**No DNS auto-reconcile in manual mode — the manual-mode publish is one-shot and can go stale.** Unlike the floor-MX TLSA record (which a `reconcile_floor_mx_tlsa` loop keeps in sync), a **manual-mode** DKIM TXT is published **once, by hand**, from the selector's `public_dns_value` (the admin-DNS page). Nothing re-publishes it, so a key re-mint — a selector's key lost and minted afresh at boot, or the schema-123 upgrade replacing a sealed blob (*The sealed-blob path is removed*, above) — silently orphans the already-published TXT: external mail then arrives `dkim=fail signature verification failed` while SPF/DMARC still pass (so it still delivers and looks fine). This is the 2026-06-21 example.com incident; the signer code is sound, the published record was simply stale. The deploy-time safety net is **deploy-verify gate 6** (a dedicated dev-fleet checker / `build-system.md` § Verifying a deploy), which reads the nest's current records off the anonymous `fauna.setup.status` (`dkim_records`) and asserts the published `p=` matches. **Whether DKIM should additionally auto-reconcile is now resolved** (tracked internally (E), 2026-06-23; authority `dns-management.md` § Reconcile → Withdraw-aware convergence): **yes — but client-side and managed-mode only.** A dedicated per-selector-slot `reconcile_dkim_txt` converge pass (mirroring `reconcile_floor_mx_tlsa`) creates the desired `public_dns_value` and **withdraws** a stale `p=` at the Fauna-exclusive `<selector>._domainkey` name, so a re-mint (and a rotation's old-selector cleanup) self-heals. It **cannot** run nest-side (the nest never holds the DNS-provider credential — `client-holds-provider-keys-not-nest`), so a **manual-mode** domain (every domain today, including example.com — no covering credential) has **no** auto-reconcile and gate 6 above stays its floor. **The pass is built** (`reconcile_dkim_txt`, `libs/fauna-client-dns/src/lib.rs`, wired into the machine's managed `Publish`; landed 2026-07-17 — corrected here 2026-07-20, this doc had stale-marked it "designed but unbuilt" after `dns-management.md` § Fauna-managed → Withdraw-aware convergence, the mechanism's authority, was already updated to BUILT). Inert for today's all-manual deployments (incl. example.com) — the manual-mode floor stays deploy-verify gate 6. Memory `dkim-publish-goes-stale-silently` (its "no auto-reconcile" framing is now manual-mode-only; still accurate for example.com itself).

**The DKIM record (display + verify).** The unsealed `DkimSelectorInfo { domain, selector, created_at, public_dns_value }` is read via `fauna.bridges.list_dkim_selectors` (Admin-only) and rendered as a DKIM `admin-dns-record` on the `admin-dns` page (`dns-management.md`) with the live red/green verify. The same public `{domain, selector, public_dns_value}` triple is also surfaced anonymously on `fauna.setup.status` (`dkim_records`) for the credential-less deploy-verify gate 6 above (no key material — the value is meant to live in public DNS). The private half never leaves the nest's seal, and no client and no bridge holds it, so the public metadata is the only form a client ever sees (listing it never exposes key material). **Before enrollment the MDA's capability holder is a no-op, and that is a live state (ruled kept 2026-09-24, compat-remnant sweep — `../architecture/version-compatibility.md` § Dimension 2, the fourth exception):** it holds nothing while the bridge's X25519 secret is absent or short (a bridge before its enrollment completes, or the localhost / e2e shape), and the post-enrollment restart wires it — a reading of an absent value a current deployment produces on every cold boot, not an accept path for an older bridge. (The MTA has no such DKIM state: it holds no DKIM key at any point.)

**Rotation.** Automatic, **nest-side and scheduled**: a background job mints a fresh nest-held `<YYYYMM>` key for each rotation-due domain, both selectors stay valid until DNS propagation settles, then the nest flips the active selector onto the new one after a 24 h cache-warmup and the old one is retired via `fauna.bridges.revoke_dkim_blob` (Admin-only; deletes the selector's key and its public metadata; idempotent). The full mechanism + the per-domain rotation lever (`set_dkim_rotation_days`) live in `mail-multidomain.md` § Rotation (the authority for the rotation cadence + selector model).

**TLS provisioning (three paths).** Triggered by bridge approval; the path chosen is admin-controlled. All three converge on the same bridge-side wire shape: an HPKE-sealed `TlsCertBlob` per `(bridge_role, bridge_id, domain)` tuple per `wrapped-blob-crypto-design.md` § Per-domain TLS cert blob, sitting in `bridge_tls_cert_blobs`; bridges fetch on startup and on cert-renewal timer via `fauna.bridges.fetch_tls_cert_blob` then HPKE-Open with the bridge's X25519 secret. The bridge-side unwrap path is identical regardless of which provisioning path produced the blob. **The fetch handler is seal-on-read** (`Storage::seal_current_tls_cert_for_bridge`): it seals the cert *currently on disk* to the requesting bridge fresh on each fetch, keyed by the requester's own `domain` + attested x25519, falling back to the stored blob only when no cert is on disk yet. So the bridge always gets the latest cert regardless of *when* it attested relative to issuance and regardless of whether its `PrimaryDomain` differs from the apex `node.domain` — the stored blob is a cache, not the source of truth.

| Path | Trigger | Used by |
|---|---|---|
| **ACME-managed** | The nest's HTTP-01 pipeline issues and renews automatically — issuance conditions, SAN set, rate budget, and self-heal are owned by [`../architecture/nest/tls-certificates.md`](../architecture/nest/tls-certificates.md) § B / § Keeping the cert alive (ACME settings are TOML/env today, a recorded invariant violation whose app-UI migration target is that doc's § ACME settings — the app-UI target). On each issuance it calls `Storage::store_acme_material(...)` — which writes the on-disk PEM AND seals+fans out to each approved bridge with an x25519 pubkey. | Deployments with port-80 reachable (HTTP-01). DNS-01 is **client-driven and built** — owner: tls-certificates.md § B tier 2. |
| **Admin-uploaded** | Admin pastes (or uploads) cert chain + private key (admin-UI home **pending** — formerly the dropped `admin-mail-deliverability` page; the WS-RPC path is unchanged). Admin's client wraps via `seal_tls_cert_blob` (UniFFI export from `libs/fauna-ffi/src/mail.rs`) and calls `fauna.bridges.provision_tls_cert_blob` (Admin caller class) directly with the pre-sealed bytes. Renewal is manual re-upload before expiry. | Deployments using a CA outside nest's reach (corp PKI, prior-purchased cert, separately-run ACME client); also the path the I4-Phase-E e2e fixture exercises for the MTA's submission listener cert. |
| **Admin-synthesized (self-signed)** | Admin's app calls `fauna.bridges.provision_self_signed_cert` (Admin caller class; request `{domain, additional_dns_sans: [...]}`). Nest synthesizes the cert via `rcgen`, hands the (cert, key) pair to `Storage::store_acme_material(...)` which seals + fans out + writes the on-disk PEM — same code path as the ACME finish. Renewal: re-call before the 90-day sealed-bundle expiry; nest does not auto-renew the synthesized cert (admin-driven by design — the admin chooses when an internal cert rolls over). Reply names which bridges were sealed-to and which were skipped (no x25519 yet) for admin visibility — but the admin **no longer needs to re-call** after a skipped bridge attests: seal-on-read (`fetch_tls_cert_blob`) hands it the on-disk cert on its next fetch. (The transitional admin HTTP twin `POST /api/admin/local_domains/{domain}/self_signed_cert` was retired once its consumers migrated to this kind — no-HTTP directive; the synthesis logic lives in the neutral `crate::self_signed_cert::synthesize_and_seal_self_signed_cert`.) | Dev / internal / air-gapped / behind-NAT deployments where neither ACME nor an externally-issued cert is appropriate. Also the path the I5 MDA E2E fixture exercises (the MDA listener's `TLSProvider != nil` gate fires before any application traffic, so a self-signed cert is the minimal-friction way to clear it). |

Per-deployment, the admin chooses one path at TLS setup; switching paths later is supported (revoke the old TLS blob, provision under the new path). All three paths are first-class production paths — the storage trait's seal+fan-out side-effects are mode-agnostic (Plaintext + Encrypted both fan out identically after the storage-trait parity port in `bins/fauna-nest/src/storage/plaintext.rs::store_acme_material`), and the WS-RPC `fetch_tls_cert_blob` surface the bridge calls doesn't distinguish between them.

**Nest TLS is a bridge-enrollment prerequisite (why the floor matters here).** The in-container mail bridge dials the nest over **https on loopback** (§ Cold boot) and cannot enroll against a plaintext listener — so a nest must serve TLS from its first listen or **mail never serves** (the regression: the bridge moved to https-loopback while a localhost nest still served plain HTTP; guarded by the tier_4 `test_mail_deploy_lifecycle` / `test_mail_security_relay` deploy-image tests). The always-live self-signed **floor** guarantees this on every nest, domainless included — mechanism owner: [`../architecture/nest/tls-certificates.md`](../architecture/nest/tls-certificates.md) § A (plain HTTP survives only behind the test-only `FAUNA_INSECURE_DISABLE_TLS` escape).

**Self-heal, rate budget, switch-back — owner pointer.** A self-signed cert auto-upgrades to a real one whenever ACME can issue, paced by a persisted rate budget, with wake accelerators and a preserved-cert instant switch-back (`fauna.bridges.restore_real_tls_cert`, Admin, non-destructive) — the whole keep-alive mechanism is owned by [`../architecture/nest/tls-certificates.md`](../architecture/nest/tls-certificates.md) § Keeping the cert alive. The bridge-facing half lives here: **prompt bridge re-serve** — when a real cert lands, `cert_lifecycle_loop` fires a `config_changed`/`"tls"` push so every running bridge re-runs `fetch_tls_cert_blob` and swaps the served leaf without waiting out its 12 h TLS timer (§ *`fauna.bridges.config_changed` push*). (A client-facing "switch back / retry now" button + a warning when switching *to* self-signed remain follow-up UI work.)

Note that this *provisioning-path* axis is orthogonal to the `mail_domains.mta_sts_cert_mode` column (`expand_primary` / `wildcard` / `per_host` per `mail-multidomain.md` § The `mail_domains` model), which controls *cert topology* (whether one cert covers the primary + secondaries, a wildcard SAN, or one cert per host). The self-signed admin endpoint is callable regardless of `mta_sts_cert_mode` — one-off provisioning during an ACME outage, or a per-domain dev cert, are both legitimate uses.

Failure surfaces (admin pane — the cert-health readout's home is the **`admin-dns` cert-status row** (`admin-dns-cert-status`), rendered on all 7 apps from `fauna.tls.cert_status` — owner: [`../architecture/nest/tls-certificates.md`](../architecture/nest/tls-certificates.md) § C.4; the former `admin-services` page and the `admin-mail-deliverability-tls-cert-status` element are both retired):
- **No TLS source configured**: yellow indicator "Configure TLS"; submission listeners (465/587) cannot bind, port 25 runs without STARTTLS advertised (degraded). Now that the self-signed floor is unconditional (tls-certificates.md § A), this state is reachable only behind the test-only `FAUNA_INSECURE_DISABLE_TLS` escape — the no-domain dev/binary-e2e nest; a real deploy always serves at least the floor and never lands here.
- **ACME challenge fails** (DNS provider misconfigured, port-80 unreachable, account-key issue): red indicator with the structured ACME error. Admin-uploaded path remains available as a fallback.
- **Cert nearing expiry without renewal**: the badge's `Expiring` state fires a single **30-day** lead (the shared `CERT_RENEWAL_LEAD_SECS`, same threshold the ACME renewal task itself acts on — tls-certificates.md § C.4), not a two-tier yellow/red day-count; the badge colour is an idiomatic per-app render of that one state (`value-formatting.md` § Cert status badge). An automated email to the admin nearing expiry is target-state (ships with a future admin-notification-mail feature — unbuilt, no owner track yet; the badge is the current signal). Renewal trigger is path-dependent: ACME re-runs automatically on its schedule; admin-uploaded requires a manual re-paste, and the expiry warning is the admin's primary signal.
- **No bridge approved yet**: the cert-status row says nothing about it — its three states are the nest's own certificate's ([`../architecture/nest/tls-certificates.md`](../architecture/nest/tls-certificates.md) § C.4), and none is about a helper. A helper waiting for approval is a card on `admin-bridges-pending`, and with mail on and no approved helper connected the mail health readout reads `bridge_down` (`mail-deliverability.md` § Admin-pane Deliverability surface → *The mail health readout*). (Corrected 2026-10-01: this bullet promised a "Pending bridge approval" indicator with a link. It was never built, and the state it described has since all but closed: the box's own helpers are approved by the enable itself — § Onboarding auto-approval — and the cert fetch seals on read, so only a helper the admin rejected, or one of another kind, waits.)

The user-side credential surface — Mail-settings page, `WrappedMsekBlob` / `MlsSnapshotBlob` / `WrappedSubmissionTokenBlob` provisioning — is owned by `docs/goal/behavior/mail-credentials.md`. It is independent of DKIM / TLS provisioning (different blob shapes, different audiences, different RPC slots in the `fauna.bridges.*` allowlist); the two flows cross-reference but never block each other.

## Multi-role multi-process

One mail-bridge binary, two roles per the spec: `mail.mta` (SMTP) and `mail.mda` (IMAP + CalDAV). Each role runs as a **distinct process** with a **distinct service-user keypair** and a **distinct enrollment**:

```
fauna-mail-bridge --keypair-file /data/keys/mta.key  # MTA role
fauna-mail-bridge --keypair-file /data/keys/mda.key  # MDA role
```

The supervisor (s6 in docker, systemd on bare-metal) runs the binary twice, with the two keypair files. Each instance calls `whoami` after auth and gets a different role + config from nest; the MTA instance opens ports 25/465/587; the MDA instance opens 993/143 + the CalDAV HTTP path. The processes don't share state — they're independent peers of nest.

Because the two roles run as separate processes on the **same host**, their localhost-only `/metrics` listeners must bind distinct ports. The bind address is **role-derived** — MTA defaults to `127.0.0.1:9090`, MDA to `127.0.0.1:9091` — computed from the `whoami` role rather than diverging the two supervisor run-scripts (an topology hatch `metrics_bind_addr` still overrides it). A `/metrics` bind/serve failure is **non-fatal**: it is observability-only and must never strand mail serving, so the role logs and continues.

**Approval is per-role.** The admin approves the MTA service user and the MDA service user independently. The admin pane card shows the requested-role hint so the admin can distinguish which approval is which. On the deployment's **own enable path** both approvals are **automatic** (§ Onboarding auto-approval) — the admin's `set_mail_enabled(true)` approves the box's own loopback MTA+MDA with no click. The per-role one-click-each flow is the **general** case, for bridges enrolled out-of-band (mail disabled, or a future non-mail role).

**Future bridges with multi-role binaries (ATProto federation + ATProto firehose, hypothetically) inherit the same pattern:** one binary, one process per role, one keypair per role, one enrollment per role. The lifecycle doc names this as the universal contract; per-bridge specs add only the role names.

## Factory reset

`fauna.admin.factory_reset` (Admin-class WS-RPC) returns the nest to **fresh / unclaimed** via a restart-wipe: it stages a marker carrying the next claim code, replies, and exits; the supervisor restarts the process, and the pre-DB-open startup hook wipes all deployment state (the SQLite DB — including every `bridge_service_users` enrollment row — the blob dir, the mail-enable flag, the claim code) before regenerating the claim code from the marker. It **preserves** the nest host identity keypair, the on-disk ACME cert, and the bridge keypairs under `/data/keys/`, and it **carries** each mail domain's DKIM key across the wipe, so the published DKIM record stays valid once the domain is registered again (owner: `../architecture/nest/common.md` § Factory reset → *The DKIM keys are carried*). (`bins/fauna-nest/src/factory_reset.rs` is the authoritative wipe-vs-preserve catalogue; the post-reset box returns to fresh/unclaimed — content-ready sealed from first boot, no mode-resolve step: `storage-modes.md` § Boot story.)

**The running mail-bridge services are brought down as part of the reset.** The `fauna-mail-bridge-{mta,mda}` s6 services are long-lived — they survive the nest restart — but the wipe deletes their enrollment rows. Because a bridge only calls `request_enrollment` at **cold boot** (§ Cold boot step 3), a *still-running* bridge would never re-enroll against the fresh nest: every reconnect would hit `fauna.auth.verify → fauna.auth.not_registered` (the deleted row) and the reconnect-backoff loop (§ Reconnecting) would retry that indefinitely without re-enrolling, so no pending bridge ever surfaces for the admin to approve. To avoid that stranded state, the `factory_reset` handler signals the supervisor sidekick socket to **`s6-svc -d` both role services before it exits** — the same down-signal `set_mail_enabled(false)` uses, both routing through the shared `mail_enable::reconcile_supervisor(node_mode, false, false, false, false)` (all four service axes forced off; renamed and widened from the single-service `notify_supervisor` when the four supervisor-reconciling call sites were unified onto one function, § Implementation status today). s6 SIGTERM-drains each bridge (graceful shutdown, § Shutting down) and holds it down across the restart.

The freshly-claimed nest therefore starts **mail-off** (consistent with § Default-off on first claim — no enrollment rows, the mail-enable flag unlinked, the `mail_enabled` toggle unset). When the admin next turns mail on (§ Default-off on first claim — `set_mail_enabled(true)`), the supervisor `s6-svc -u`'s the down services into a fresh **cold boot**: each generates/loads its keypair, calls `request_enrollment` against the fresh nest, creates a new `pending` row, and the admin approves it. The bridge keypairs on disk are preserved, so the same pubkey re-pends (a wiped nest has no prior row to clash with) — re-keying is *not* required, only re-approval. This makes factory-reset → re-claim → re-enable a clean, repeatable cycle (the believable live-mail e2e relies on it).

**App affordance.** Factory reset is initiated from the app, never a CLI/SSH command (product invariant: nest config is set from apps). The admin triggers it from a destructive "Factory reset this nest" control on the admin-settings page (`admin-factory-reset-button`, behind a confirm dialog), Admin-class-gated like every `fauna.admin.*` call — v1 has no extra cooldown gate (`fauna_protocol::admin::FactoryResetRequest` doc). Because the handler replies with the new claim code and then exits + restarts, the app **never sees** that code on screen; the affordance therefore tears down the authenticated session (keeping the local identity — the box was wiped, not the app) and re-seeds onboarding at the claim-code step with the returned code **pre-filled** (`OnboardingMachine::navigate_to_claim_code_for_known_nest_with_code`; `onboarding.md` §3a). The client tolerates the ~1-2 s WS drop across the restart via the claim-code page's existing transient-error retry, then re-claims as the same identity (the post-reset box is content-ready sealed — nothing to re-pick; the re-claim now routes straight to `nat_mode_choice` on all 7 apps — `onboarding.md` § 3b-bis — since the client-half demolition landed, no-modes ratified 2026-07-12, Phase-4 S8.7; `storage-modes.md` § Implementation status today). The call wrapper is the shared `AdminClient::factory_reset` (`libs/fauna-client-admin`), so all seven apps render the same flow; linux is the lead implementation.

**Implementation status — re-claim handle sourcing.** The nest stores **bare** localparts and auto-registers the primary mail domain from the handle's `@domain` at claim, so the re-claim ideally carries the re-qualified `localpart@domain`. **Convergence target:** every app (1) sources the handle **authoritatively** from the still-live admin session (`fauna.account.get`) before the wipe, falling back to the cache, and (2) re-qualifies via the **shared** `fauna_onboarding_machine::qualify_reclaim_handle(handle, domain, nest_url)` (UniFFI + wasm twins `qualifyReclaimHandle`). Status matrix (refreshed 2026-08-16 — linux's hand-rolled copy was migrated onto the shared fn, and macos/ios gained its first call site, both this pass):

## Shared lifecycle for future bridges

Every future bridge — the now-landed ATProto PDS bridge, a future standalone Nostr relay bridge, future-protocol — inherits this lifecycle without modification. ActivityPub does not: it shipped entirely in-process, not as a bridge-as-client (`architecture/apps/bridges.md` § Future bridges).

1. Supervisor exec's the bridge binary with `--keypair-file` and `--nest-endpoint`.
2. Bridge generates keypair if absent.
3. Bridge self-enrolls over the anonymous (pre-identity) WS via `request_enrollment` (loopback-gated) → creates a `pending` row.
4. Bridge polls `request_enrollment` until `approved` (it does not run the authenticated auth flow until then).
5. Admin approves in the Fauna app.
6. Bridge authenticates, calls `whoami`, fetches config, opens listeners, runs.
7. Reconnects on nest restart, re-fetches config.
8. Rotates keys via the same admin-initiated revoke + auto-regenerate flow.
9. Shuts down on SIGTERM with the grace timeout.

Per-bridge specs (in `docs/goal/architecture/apps/<bridge>.md` and `docs/goal/behavior/<bridge>.md`) add only the protocol-specific listener configuration (which ports? which transport? which auth?) and the protocol-specific RPCs the bridge needs from nest. The lifecycle prose is **not** re-specified per bridge; new bridges link here for "see mail-bridge-lifecycle.md § Lifecycle phases."

## Architectural rules

- **Keypair generation is bridge-side, on first run, automatic.** A keypair file is never hand-seeded. Generation is bounded by file-mode 0600 + structured-log audit-trail.
- **Status comes from nest, never argv.** A bridge with `--mode=...` is forbidden; the role is in `whoami`'s reply, set by the admin at approval time. Per `principles.md` § Product invariants.
- **Default-off on first claim, materialized via flag file + supervisor sidekick.** Admin toggles in app UI → nest writes flag + sends sidekick command → s6 brings up service. No filesystem polling.
- **Hot-reload mandatory.** Config changes apply at the next request boundary; no SIGHUP, no restart-to-pickup-config. The bridge subscribes to `config_changed` push events.
- **Listeners stay up across nest disconnect.** Connection-time policy is applied from the last-known config snapshot; verdict-needing RPCs tempfail with 451 if reconnect exceeds 30 s. The sending MTA's next retry catches up.
- **Per-role process model.** One process per role; one keypair per role; one enrollment per role. The supervisor runs the binary multiple times with different keypair files.
- **Shared lifecycle across all bridge types.** ATProto / a future standalone Nostr relay / future bridges inherit this shape; per-bridge specs add only listener config. ActivityPub is not a bridge-as-client — it shipped in-process (`architecture/apps/bridges.md` § Future bridges).
- **Approval is admin-initiated.** A bridge can *ask* to be approved (by self-enrolling via `request_enrollment`, which creates a `pending` row and surfaces the approval card); only an admin can complete approval. No "auto-approve on first connect" — that would defeat the security model. **One carve-out:** the deployment's own co-located mail bridges are auto-approved on the admin's `set_mail_enabled(true)` — an Admin-class action that *is* the admin completing approval, bounded to same-host processes by the loopback gate (§ Onboarding auto-approval). This is still admin-initiated (the admin's enable opens the window); it is not "any bridge that connects."
- **Self-enrollment is loopback-gated with blessed-key proof-of-possession; cross-IP is deferred.** `request_enrollment` runs on the anonymous pre-identity WS and is accepted only from a **loopback (same-host) peer**; on an image deploy the **strict mode** additionally requires the artifact-blessed per-role pubkey plus a verifying Ed25519 proof-of-possession signature over `enrollment_signed_message` (binding the x25519 set-once) — loopback-without-signature survives only as the lenient dev/binary-e2e fallback (§ Cold boot step 3; crypto contract: `architecture/security.md` § Enrollment proof-of-possession contract). A remote source IP is refused (`fauna.bridges.remote_enrollment_unsupported`); enrolling a bridge on a *different host* than nest needs a real cross-host auth mechanism that is intentionally **not yet designed** — add it when a multi-host deployment first needs it, don't pre-build it. The peer address is available only on nest's plain-HTTP listener (the in-container bridge↔nest hop); the public TLS listener has no `ConnectInfo`, so a loopback-only kind is unreachable there by construction.
- **Re-keying preserves history.** The old keypair is archived (`<keypair>.revoked.<unix-time>`) for audit / forensics. Disk pressure is negligible; manual deletion remains possible but is never required.
- **Reconnect-backoff cap is fixed at 30 s.** Not configurable — flap-protection floor, recovery ceiling.
- **The flag file is nest's output, nobody's input.** A divergence is repaired on the next reconcile pass and logged; no app shows it (§ Default-off on first claim).
- **DKIM rotation is orthogonal.** The service-user key rotation flow described here does not rotate, delete or otherwise touch DKIM keys; those are the nest's own and follow its scheduled rotation (§ DKIM provisioning (automatic) → Rotation).

## Don't do these

- **Don't ship a `--mode={mta,mda}` argv flag** on any bridge binary. Role comes from `whoami`. See `principles.md` § Product invariants ("a bridge process discovers its role from its nest service-user enrollment, not from `--mode=...`").
- **Don't require hand-seeding the keypair file.** First-run generation handles it. A "please copy this PEM into /data/keys/mta.key before starting the container" step is the anti-pattern this doc replaces.
- **Don't poll the filesystem from s6 / systemd for flag-file changes.** Use the supervisor sidekick socket. Polling adds idle CPU + toggle latency.
- **Don't auto-approve a pending bridge — as a general rule.** The approval card is admin-gated; auto-approve would let an attacker who reached the nest endpoint (e.g. via a compromised network path) self-enroll a bridge. **The one sanctioned exception** is the deployment's own loopback-enrolled mail bridges on the admin's `set_mail_enabled(true)` (§ Onboarding auto-approval) — the network-path attacker this guards against cannot enroll (loopback gate), and the window is opened only by an Admin-class enable. Don't broaden it: no auto-approve for non-loopback peers (refused anyway), non-mail roles, or while mail is disabled/unset.
- **Don't restart the bridge for a config change.** Hot-reload via push event is mandatory. A restart drops in-flight connections; hot-reload doesn't.
- **Don't tear down listeners across nest disconnects.** Listeners armed with the last-known config snapshot keep working; verdict-needing RPCs tempfail. Tearing down listeners means in-progress senders see connection drops instead of the protocol's `451` retry signal.
- **Don't share keypairs across roles.** One process per role, one keypair per role. Sharing breaks the per-role allowlist's security boundary — the same keypair calling MTA + MDA methods would defeat the spec's deliberate separation.
- **Don't delete the archived `.revoked.<unix-time>` keypair files automatically.** Audit / forensics value; trivial disk cost. They can be deleted manually if desired.
- **Don't rotate the service-user key without admin confirmation.** Rotation is a security-sensitive change; the confirmation dialog protects against accidental click-throughs.
- **Don't ship a CLI tool for keypair generation / rotation on the deployment box.** The bridge binary handles generation; the admin handles rotation in the app UI. An out-of-band CLI is a fourth surface that the product invariant forbids.
- **Don't store the supervisor sidekick socket on a network filesystem.** Unix-domain only, in `/run/` (tmpfs); permissions enforce single-user access.
- **Don't let a bridge in pending-approval consume mail.** Until status flips to `approved`, the bridge's listeners are not opened — `fetch_config` is gated on `status == approved`. A pending bridge holds its WS connection and polls; nothing else.
- **Don't ship a "bypass approval" deploy mode.** Pre-production temptation to skip the click for testing produces a security regression that gets shipped. The long-term question says: real approval click in dev too; testing flows produce a real second admin actor that auto-approves their own bridge instance, not a bypass. (The § Onboarding auto-approval path is **not** such a bypass: it is a real, Admin-class-gated, loopback-scoped approval of the box's *own* bridges — not a switch that skips the gate for arbitrary bridges, and not configurable.)
