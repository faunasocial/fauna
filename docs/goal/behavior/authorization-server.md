## Goal

Every third party — an ATProto client signing into a hosted PDS, a mail client with no browser, a website offering "sign in with Fauna", a device app, a plugin the nest hosts — obtains its transport authority from **one** authorization server on the nest's own domain, up whenever the nest is up, independent of every optional bridge. It resolves the client's self-authenticating metadata document, gates every request at PAR, binds every token to a DPoP key, shows the user **one consent card** reached by four starts, and mints short-lived access tokens under **one** ES256 key that also signs OIDC ID tokens. A token opens no sealed byte: where a scope names sealed data, its grant twin is minted by the user's app to the principal's key ([`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Capability tiering).

## The issuer (TP5)

The authorization server becomes a **nest-native surface on the nest's own domain**: discovery at `/.well-known/oauth-authorization-server` and `/.well-known/openid-configuration`, `/oauth/{par,authorize,token,revoke,jwks,userinfo}`, plus the two consent-start endpoints of § Consent (`/oauth/device_authorization`, `/oauth/bc-authorize`). It is up whenever the nest is up. Three consumers:

| Consumer | What it needs | How the one issuer serves it |
|---|---|---|
| ATProto clients (built today against `pds.<domain>`) | the ATProto scope grammar, permission sets, DPoP, the PDS as resource server | the PDS's `/.well-known/oauth-protected-resource` names the nest-domain AS (RFC 9728 permits any AS); the ATProto grammar is one scope family among several (§ Scope grammar) |
| Mail clients (the retired sketch) | RFC 8628 device grant; nest-side token validation | the typed-code start *is* the device grant; the nest validates its own tokens (§ Mail clients) |
| Fauna third-party apps | identity assertion + scoped transport authority | § OIDC + the Fauna scope family |

**Cross-origin access — the plane is open to every origin, with no credentials (ratified 2026-10-02).** Every surface the issuer serves — the two discovery documents, `/oauth/jwks`, and every request-taking endpoint of the list above — answers a browser on **any** origin: `Access-Control-Allow-Origin: *`, methods `GET` and `POST`, the request headers `Content-Type`, `Authorization` and `DPoP`, the response headers `DPoP-Nonce` and `WWW-Authenticate` exposed, and **never** `Access-Control-Allow-Credentials`. Three reasons, each sufficient. **(1) A browser client's origin is unknowable ahead of time:** a website offering "sign in with Fauna" is identified by its client metadata document, resolved at PAR — an origin allowlist for the issuer would be a second registration of the same fact, and a knob no admin should hold ([`../principles.md`](../principles.md) § One configuration surface); the nest's credentialed allowlist is for the nest's **own** app origins and is untouched for every other route. **(2) Nothing on the plane is authenticated by an ambient credential:** no cookie, no nest bearer — every request is self-authenticating (a DPoP proof, a PKCE verifier, a `private_key_jwt` assertion, an access token in `Authorization`), so a foreign page can do nothing here that a non-browser client cannot already do, which is exactly the reasoning that opened the content-addressed byte routes ([`../architecture/federation.md`](../architecture/federation.md) § Cross-nest shared folders). **(3) The plane's own headers must cross the origin boundary:** `DPoP` is a request header a browser may send only after a preflight allowed it, and the nonce and challenge are response headers a page reads only when exposed — the nonce is what a browser client dials its principal session with ([`../architecture/transport-connection.md`](../architecture/transport-connection.md) § Connection lifecycle → *The principal session*). The ATProto OAuth profile presumes the same: its browser-based clients reach the server metadata, PAR and the token endpoint directly from their own origin. **The resource server's half follows the rule:** the PDS bridge's `/.well-known/oauth-protected-resource`, which a browser client reads first to find this issuer, carries the same open header. **Built as one router under one layer** (`bins/fauna-nest/src/oauth_issuer_routes.rs::routes`), merged into the nest's router *after* the credentialed layer so no response ever carries two `Access-Control-Allow-Origin` values; a surface added to the issuer joins that router, never the main one. What stays closed: `/api/v1/principal/ws` is a WebSocket upgrade, which CORS does not govern — the browser's WebSocket API opens it from any origin and the DPoP-bound token is the gate.

**Custody.** The ES256 signing key moves from bridge-held to **nest-held**. It is a *service* key — the class the nest already holds for its own identity and for the delegated-authoring sub-key — not user key material; the bridge doc's "no direct access to user MLS keys" rule is untouched. The custody entry, the domain-separated context, the rule-#8 statement for one key signing two JWT classes, and the threat model are owned by [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Audience: deployment infrastructure → *Issuer signing key*. What moves with the key: the DPoP nonce secret, the PAR store, the replay sets, the two signers — all bridge memory today, nest memory tomorrow, semantics unchanged. **The move affects no users, and no transition window is owed.** The always-on first-party issuer *process* on the sidecar channel was the recorded fallback should the hierarchy have refused nest custody; it did not (the nest already holds keys that sign on behalf of users), so the fallback is not taken.

**What the move re-decides** (each a declared gap, § Implementation status today): the PDS's protected-resource metadata names a *different* host; AS-key rotation adds a key to a nest-held set instead of a second sealed blob beside the first; `get_as_key_status` may report a `kid` once the nest can read the key; and the admin rotate control is placed where a nest-held deployment key's controls belong — beside `rotate_srs_secret` and `force_rotate_dkim` in the admin shell — rather than on a bridge's approved card, which was forced only by the key being reachable through that bridge. Neither of those two kinds has an app control of its own, so the concrete home is the `admin-nest` page, directly after the deployment identity rotation ([`admin.md`](admin.md) § N Nest).

**The kids are reported by a NEW nest kind, not by widening `get_as_key_status` (ratified 2026-09-09).** The clause above is permissive — "*may* report a `kid`" — and it was written when the only key set in the system was a bridge's. `get_as_key_status` is **per approved bridge**: it answers "the AS key *this bridge* reaches". The nest's issuer key set is deployment-wide and exists with no bridge enrolled at all, so hanging the deployment-wide fact off a per-bridge reply would make it unreadable in exactly the configuration nest custody exists to serve. So the admin surface is its own **`fauna.oauth.*`** pair, Admin-only and ungated like the rest of the issuer:

| Kind | Reports / does |
|---|---|
| `fauna.oauth.issuer_key_status` | the served key set (`kid` each, `retired_at` on the outgoing one), which key signs, and the retirement horizon in seconds — so an admin reads "the old key stops being served in N minutes" rather than deriving it |
| `fauna.oauth.rotate_issuer_key` | mints a new signer, retires the outgoing key in one transaction, returns the new `kid` and the rotation instant; the outgoing key stays **served** for the retirement horizon |
| `fauna.oauth.force_rotate_issuer_key` | mints a new signer and **drops every other key** in the same transaction — the active one and any retired key still inside its horizon — returning the new `kid`, the instant, and the dropped `kid`s; the very next JWKS read carries the new signer and nothing else, and every live principal session is closed with the drop (*Two rotation arms*, below) |
| `fauna.oauth.force_rotate_session_secret` | re-mints the issuer's **second signer** — the HS256 secret every OAuth refresh token **this** AS mints is MACed under — in one statement, **and ends the grant rows whose refresh families that re-mint killed**, closing every live principal session with them (*Two rotation arms*, below), returning the instant, the replaced generation's mint instant and `grants_ended`. Every outstanding nest-minted OAuth refresh token is refused on the very next `/oauth/token` read and its client re-authorizes; the bridge AS's tokens are MACed under a secret of its own and are untouched (*Two rotation arms*, below, owns why the ending is part of the act rather than a follow-up). The forced issuer arm's sibling, with no ordinary arm (*Two rotation arms*, below); custody in [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Audience: deployment infrastructure → *OAuth refresh-token signing secret* |

The namespace is `fauna.oauth.*`, not `fauna.bridges.*`, for the same reason the control moves out of the bridge card: the key is the nest's own. `get_as_key_status` is left exactly as it is — it keeps describing the bridge-held key it was written for, and is retired with the endpoints, not widened on the way there.

**Two rotation arms — the compromise window is the retirement horizon, not the token lifetime (ratified 2026-09-09).** § As built → *AS-key rotation* calls rotation "a deliberate compromise response" and gives the two-signers interlock as the reason a rotation is cheap: only ≤15-minute access tokens are ES256-signed, so the outgoing key is retired minutes later. **That argument bounds honest tokens only.** It answers the *availability* question — how long must a retired key stay verifiable so tokens minted just before the rotation survive — and the horizon (`issuer_key_retirement_horizon_secs`, 15 min + 5 min pickup grace) is its answer. It says nothing about a *forged* token: a thief holding the leaked scalar chooses `exp` themselves, so the lifetime constrains nothing they mint, and the only thing that does is whether the token's `kid` is still in the served JWKS. Under the ordinary arm that is the full horizon **after** the admin has already responded, plus each verifier's own JWKS-cache pickup. The two questions have opposite safe directions — a longer horizon is safer for availability and worse for compromise — so one knob cannot serve both, and shortening the horizon is the wrong fix (it re-opens the outage the key *set* exists to prevent). Hence **two arms, and the admin chooses**, per the config-surface invariant: `rotate_issuer_key` for a precautionary rotation (a suspected exposure, a departed operator — nothing breaks), `force_rotate_issuer_key` for a known leak (the leaked `kid` leaves the served set on the next read; every honest token signed by a dropped key stops verifying at once, and the app control states that cost before dispatch). The forced arm drops **every** key that existed, not a named one, because a leak takes every key that existed at the moment of the leak — the admin is never asked to guess which one the thief holds. It is a **kind, not a flag** on the ordinary arm: an older nest would carry an unknown flag in `extra`, rotate softly, and answer success, leaving the admin believing a leaked key was gone while it stayed served — a kind an older nest never registered fails loudly instead, which is the only honest answer a compromise response can give when the nest cannot perform it. **The leak shape the forced arm answers, stated precisely (amended 2026-09-09):** an **exposed unsealed scalar** — a core dump, a cleartext backup, a log line, an operator's copy, a signing-path bug — or a **seed-bearing** read of the store. A read of the store *without* the deployment seed exposes neither signer (both rest sealed under it, [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Audience: deployment infrastructure), so there the arm answers nothing and nothing needs answering; a seed-bearing read exposes **both** signers at once, and that is why the arm has a sibling: **`force_rotate_session_secret`** re-mints the HS256 secret every refresh token **this** AS mints is MACed under, killing every outstanding nest-minted refresh token on the next `/oauth/token` read — and, like the forced issuer arm, closing every live principal session with it (the socket half of both arms: [`../architecture/transport-connection.md`](../architecture/transport-connection.md) § Connection lifecycle → *The principal session*, door (c)). Without it the response is half done — a forged refresh token redeems, through the ordinary refresh path, for an access token signed by the **new** issuer key. ⚠ **That path is not signature-and-claims only, and this paragraph used to say it was (corrected 2026-09-11):** `refresh_token_grant` rotates the family row and refuses anything whose status is not `ROTATED` — the reuse family-kill — so a forger needs a live `(sid, current jti)` pair, not merely a well-formed token. The arm is still needed for exactly the leak shape above: a seed-bearing store read hands over that pair along with the secret. The overstatement mattered because it made the arm look like the answer to a weaker attacker than the one it actually answers. The sibling has no ordinary arm, because the secret is a single row no stranger verifies: there is no outgoing generation to keep served, so its only rotation is the forced one, and its cost — every connected app re-consents — is what the app control states before dispatch, beside the forced issuer arm. **What the forced arm does not bound:** a verifier that caches the JWKS keeps trusting a dropped `kid` until its own pickup — so the resource server that verifies against this issuer must re-read the set on an unknown-`kid` miss *and* on a nudge, never on a fixed long TTL alone; that pickup rule is built into the resource server's feed (*The teaching is one WS-RPC feed carrying both halves*, below). **The bridge-held key set had the identical 20-minute shape and was left as it was:** its surface was about to retire with the endpoints, so a second forced arm there would have been work on a dying surface. That window was accepted for the rest of the set's life, and closed when the set retired with the bridge AS (2026-09-26).

**The retirement horizon has one owner, and it is shared Rust (ratified 2026-09-09).** § As built ruled the horizon "DERIVED BRIDGE-side … because the lifetime constant lives bridge-side and nest must not duplicate it" — correct then, and its *reason* (never two copies of the number) is what survives nest custody. Nest custody gives the number a second consumer, so it moved **up** rather than across: `fauna_provisioning::oauth_issuer` owns the access-token lifetime, the JWKS pickup grace, and the horizon derived from them, the nest reads it directly, and the Go bridge reads it through `fauna_ffi`. The nest applies it **lazily on the key-set read** — `/oauth/jwks` and the status kind share one door — never on a timer, which is the same "against the injected clock, no timers" shape the bridge already used and for the same reason: a timer needs a scheduler, fires on a nest nobody is asking, and would still have to be re-derived on read for a nest that was asleep when it should have fired.

**The forced session-secret arm ENDS the grants it kills, and counts them (ratified 2026-09-12).** Re-minting the secret kills every nest-minted refresh family on the next `/oauth/token` read, and until this ruling it stopped there — which left, row for row, the state *Grants recorded while the flow is unhonoured are ended at the re-point* condemns, reached through a second door: connected-apps kept listing each dead connection with its real scopes, and `last_used_at` — whose contract is that a rotation is the one moment the nest observes a grant in use — kept reporting use for a credential that cannot be used, until an `expires_at` up to 180 days out. The honest re-consent the client then performs adds a second row beside the dead one. So the arm **ends** those grants in the same act, through the same `end_oauth_session` owner revocation uses, and the reply carries the **count** — the blast radius the confirm warned about, come back as a number the app control states rather than a sentence the admin has to trust. Five rulings fix the shape.

  - **It finds its rows by the grant registry's ISSUER MARK, and what it does with a NULL row is not ruled here.** A forced session-secret rotation kills exactly the families the *nest* MACed, so the ending selects **positively** on the nest's mark. The mark itself (what writes it, that it is written going forward only, and the bounded residue that leaves) and how each ending resolves a NULL row are owned by *Grants recorded while the flow is unhonoured are ended at the re-point* → *Which rows those are, and the residue in finding them*, below. This arm reads that rule rather than restating it.

  - **Rotate FIRST, end second.** The secret is read from the store on every mint and verify, never cached, so a refresh arriving between the two acts dies on the MAC. Ending first would leave the inverse window — a still-live secret minting a fresh family *behind* the sweep, producing exactly the live-looking row the ending exists to remove.

  - **The ending is ONE transaction, and the count means what the connected-apps surface shows.** Scoped to the live view `list_grants` serves — not revoked, not past `expires_at` — because the number the admin reads is *how many connected-apps rows disappeared*; a grant already ended is not this response's to claim, and an expired one is already invisible, so counting either would inflate the count in the one direction that makes a compromise response sound bigger than it was. Atomic rather than a loop of per-grant endings, because a half-finished sweep would leave the admin's count and the surface disagreeing with nothing saying where the boundary fell. And **one nudge per affected actor rather than one per grant**: the nudge names an actor, so a user with four connected apps would otherwise get four identical frames carrying no extra information.

  - **A failed ending is reported, never swallowed — and never as a failed rotation.** The secret is already gone when the sweep runs, so the call must not answer a clean success over an unfinished response; it answers an error that **says the secret was replaced** and that the grants were not, and re-running finishes it (both halves are idempotent, and the second run counts only what it ended itself). Because the sweep is atomic, that error is exact: nothing was ended. The reply's count is correspondingly an **absent** value, not a zero, wherever a nest cannot stand behind one — a nest older than this ruling omits the field, and reading that absence as "none were connected" would be a false statement in the surface that must not make any.

  - **`/oauth/revoke` is untouched by all of this.** A client presenting a now-dead refresh token there still gets the uniform empty `200` every token outcome gets (§ Don't do these — a distinguishable answer makes the endpoint a validity oracle), and an unexpired *access* token can still revoke, since this arm leaves the ES256 issuer key alone. What the ending changes is the *effect* behind that uniform answer, never the answer.

**Two HS256 secrets, not one — and the plane claim is kept anyway (ratified 2026-09-09).** § As built records "one HS256 secret now signs two planes' refresh tokens", which was a *consequence* of one process minting for both planes, never a requirement. Nest custody removes the premise: that secret is a nest-held blob **sealed to the bridge**, unreadable to the nest, and it also signs the app-credential plane's `refreshSession` tokens, which stay on the bridge. So the nest mints its **own** OAuth-plane HS256 secret ([`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Audience: deployment infrastructure → *OAuth refresh-token signing secret* owns the custody entry), and the ⚠ two-signers ruling is untouched — this splits the *refresh* signer per plane, it does not move refresh tokens onto the AS key, which is the thing that ruling forbids. **The plane claim stays**, because separate secrets do not cover the case it was written for: an OAuth refresh token minted by the *bridge* under the shared secret is still presentable at `com.atproto.server.refreshSession`, which verifies under that same secret. An interlock that held only while two secrets stayed unmerged would be a promise about the future rather than a property of the token.

**`iss` and `aud` follow the artifact's real reader, so the two token classes differ (ratified 2026-09-09).** The bridge minted both under one identity because one host was AS and resource server at once; on the nest they part.

| Token | `iss` | `aud` | Why |
|---|---|---|---|
| Access (ES256) | the **nest** issuer — the AS that minted it | the **set of its readers** — the PDS service DID (`did:web:pds.<apex>`), the nest issuer, or both (*The audience is the set of readers*, below) | a public artifact a resource server verifies; RFC 9068 makes `aud` the resource server, and the grant's scope families decide which resource servers there are |
| Refresh (HS256) | — | the **nest** issuer | presented back to this nest's own token and revoke endpoints and to nothing else, so the honest audience is this AS; it also means an app-plane token can never verify here even were the secrets ever merged — a second, structural interlock beside the plane claim |

**This is the gap that makes the resource server the retirement slice's first job**, and it is one gap with two halves, not two: the PDS bridge pins *both* `iss` (to its own issuer URL) and the signing key (from the bridge-held key set) when it verifies an OAuth access token, so a nest-minted token is refused there until the bridge is taught the nest's issuer identifier **and** fed the nest's public JWKs. Neither half is a regression while it stands — nothing points a client at the nest's AS until the PDS's protected-resource metadata is re-pointed, which is the same slice's work — but the re-point must not land before both halves do, or every authenticated OAuth call breaks at once. That last sentence was true of one document and false of the other for as long as it stood in prose alone; *The staging rule covers both documents* below is what makes it true.

**The audience is the set of readers, decided by the grant's scope families (ratified and built 2026-10-01).** The table's access row first named the PDS service DID alone, written when the PDS was the only resource server. The nest is one too: `/oauth/userinfo` since OIDC, and now the principal session ([`../architecture/transport-connection.md`](../architecture/transport-connection.md) § Connection lifecycle → *The principal session*). *`aud` names the artifact's real reader* has to hold for a token the PDS never sees — and under that rule an OIDC-only grant on a nest with no PDS bridge named a service that does not exist there. So `aud` lists each resource server the grant's scopes can be exercised at: the **PDS service DID** when the grant holds an ATProto-family scope, the **nest issuer identifier** when it holds an OIDC or Fauna-family scope. One reader is a string, so an ATProto-only token is byte for byte what it was under the PDS-only rule; two readers are the two-member array RFC 7519 allows. Each resource server requires **its own identifier to be a member** and ignores the rest — the PDS verifier, `/oauth/userinfo`, and the principal session's upgrade. One shared-Rust function derives the set from the scope list, beside the family predicates, and only the mint calls it. `/oauth/revoke` is not a resource server and is not addressed by `aud`: it is the issuer identifying its own artifact, so it accepts an access token naming either reader — a token this issuer minted stays revocable whatever its families. **No transition window is owed:** the token is opaque to its client and at most 15 minutes old, so one minted under the old rule is refused once at a reader that now wants its own name (`401 invalid_token`), and the refresh that answer already provokes mints the new shape; the PDS bridge ships in the nest's own image, so the verifier and the mint change together. ⚠ **`aud` is not the reach check.** A token naming the nest opens a principal session only with a Fauna-family scope, and reaches only what the chokepoint's scope check allows; the audience keeps a token consented for one server from being *presented* at another, and DPoP already keeps it from being *replayed* there.

**The teaching is one WS-RPC feed carrying both halves, and it lands ahead of the re-point without changing anything (ratified 2026-09-10).** The paragraph above says *what* the resource server is owed; this says how it is fed, and the shape follows from the two halves being one gap. `fauna.bridges.atproto.fetch_issuer_jwks` answers every approved PDS bridge with the nest's **served** public key set *and* the issuer identifier to pin, in one reply — so the two facts cannot arrive apart, which teaching them through two doors would allow. It rides the WS-RPC channel the bridge is already enrolled on rather than an HTTP read of `/oauth/jwks`: the bytes are identical and public either way, and the channel that already authenticates the bridge to the nest is the one that needs no second trust decision about who answered. **The served set REPLACES what the verifier held, never merges** — the nest applies the retirement horizon on this read exactly as it does for `/oauth/jwks`, so absence from the set is what stops a key verifying, and a merge would leave a force-rotated `kid` alive at the one place the forced arm exists to reach. **Pickup is push, miss, ticker, in that order of urgency:** `fauna.bridges.atproto.issuer_key_rotated` after either rotation arm (this is the arm's actual reach, and the reason it is a separate kind from `as_key_rotated`, which names a different set with different custody and retires with the bridge's own AS), a damped re-read when a presented token names an unknown `kid`, and a slow ticker behind both — which is what *Two rotation arms* means by "on an unknown-`kid` miss *and* on a nudge, never on a fixed long TTL alone". ⚠ The two fast paths answer opposite questions and are easy to swap: a *force-dropped* `kid` is one the verifier still holds, so it produces no miss at all and only the push removes it; a miss is the *honest* client arriving with a token from a key minted since the last read. **And `issuer` was withheld until the deployment honoured nest-minted tokens** (since the re-point it is always carried, `None` only on a domainless nest) — the same pin *The staging rule covers both documents* gates discovery on, read once nest-side and answered here, so the re-point flips the two documents *and* the resource server's acceptance in one edit. That is what lets this leg land first and change nothing: a bridge holding keys but no issuer verifies no nest-minted token, so no grant recorded before the flip goes live ahead of it (*Grants recorded while the flow is unhonoured are ended at the re-point*), and the next paragraph's *ONE change* still holds in the sense its reasoning needs — every window it names is a window of *behaviour*, and the teaching's mechanism landing first opens none of them, because its effect is gated on the very pin the re-point flips: the resource server's acceptance, the advertised flow and the retirement still take effect in one edit.

**The re-point, the teaching, and the bridge AS's retirement are ONE change — three legs, not two (ratified 2026-09-09).** The paragraph above binds two of them: the PDS is taught the nest's issuer and fed its JWKs *before* the protected-resource metadata re-points. The third belongs in that same change — **the bridge's own `/oauth/*` request-taking routes come down with it**. Leaving them up while the resource server names the nest is what turns a sign-out into a lie: a client that re-discovers through the re-pointed document now believes the nest is its authorization server and presents *bridge*-minted artifacts at the nest's `/oauth/revoke`, which cannot identify them — the access token's `kid` names a key in the bridge's set, and the refresh token's MAC is under a secret the nest has never held — and which therefore answers the uniform empty `200` of § As built and does nothing. **Cross-recognition is not the remedy and must not be built:** the nest holds the bridge's ES256 key only as ciphertext sealed to the bridge and its HS256 secret not at all (§ As built → *AS-key rotation*, and *Two HS256 secrets, not one* above), so identifying a bridge artifact would mean unsealing a bridge secret or fetching an optional bridge's JWKS at revoke time — the second a runtime dependency on a bridge that § Goal and rule #1 refuse, bought for a window § Custody has already ruled no user is owed. Moving the three together instead makes a bridge-minted artifact **inert rather than unrevocable** at that instant: the bridge's `/oauth/token` is gone, the nest's refresh MAC refuses it, and `com.atproto.server.refreshSession` refuses it on the plane claim (*Two HS256 secrets, not one*) — a dead credential, which is what the user asked for, rather than a live one their sign-out silently missed. **What the endpoint answers does not change**: the one-writer `revoked()` and the `bound_jkt` filter ahead of it stay exactly as they are, because an answer that distinguished "this token was not mine" would trade this bug for the validity oracle that shape exists to prevent. The grant *rows* those artifacts point at are a separate question — what becomes of a grant recorded before the flip — answered once, beside the advertisement-staging rule, never twice.

**A nest with no claimed domain has no issuer, and says so (ratified 2026-09-09).** The issuer identifier *is* the nest's own apex domain, so a box that has not claimed one has no identity to advertise — and it may not invent one: `iss` is client-pinned, so minting under a guess (an IP, `localhost`) would produce tokens that stop verifying the moment a real domain is claimed, with nothing to re-point them to. All three S1 surfaces therefore answer **`503` until a domain is claimed**, the same shape `/.well-known/carddav` already uses for "the surface is real, its prerequisite is not here yet". This costs nothing in recoverability: a post-boot claim re-points the live apex (`identity_domain_core::apply_primary_identity`), so the surfaces begin answering with no restart. It is the one narrowing of "up whenever the nest is up" above, and the only one — every *other* precondition (a bridge being enrolled, a feature being compiled) is exactly what nest custody exists to remove.

**The staging rule covers both documents, and one pin enforces it (ratified 2026-09-09).** *"Nothing points a client at the nest's AS until the re-point"* was written about the PDS's protected-resource document, which is the document that redirects an **ATProto** client. It was never true of the nest's **own** AS metadata: `/.well-known/oauth-authorization-server` and `/.well-known/openid-configuration` are discoverable at the apex by any OAuth client that knows the nest's domain, independently of any PDS, and once all four endpoints answered they advertised a complete, correct-looking OAuth 2.1 server whose tokens the resource server refuses twice over. The rule that governed the port — *only advertise what the nest serves*, because a client reading `token_endpoint` and getting a `404` cannot tell a broken deployment from an unfinished one — was enforced by a guard that can only ask **whether a route answers**. Answering is necessary and not sufficient: a client that follows this document all the way through a *successful* ceremony and is then refused at the resource server is in exactly the epistemic position that rule exists to prevent, arriving one step later and having spent a real user consent on the way. **So "serves" means the token is honoured**, and the nest's discovery document advertises the flow — the four endpoint members and every member describing what happens behind them — **only when the deployment's protected-resource metadata names the nest's issuer**, which is the same event the re-point is. Until then it carries what S1 carried: an issuer identity and its `jwks_uri`, which is the true and complete statement about a nest whose tokens nothing accepts yet (the JWKS stays because it is served, and because it is how the resource server is fed the nest's public keys when the re-point is prepared). **The two documents therefore flip in ONE edit**: both read `fauna_bridge_atproto::oauth_metadata::protected_resource_authorization_servers`, so the slice that re-points the resource server turns the nest's flow on in the same commit, and cannot land half of it. ⚠ The gate is a **static derivation over shared code** — a pure function of the apex domain — not a runtime look at bridge or deployment state: *A nest with no claimed domain has no issuer* above stays the one narrowing of "up whenever the nest is up", and this adds no second one. It **retired with the re-point** (S2d, 2026-09-26): that change deleted the predicate and the branch together, and the pin is now ordinary — the nest serves the shared `oauth_authorization_server_document` over its apex, and the PDS's protected-resource document names that issuer.

**Grants recorded while the flow is unhonoured are ended at the re-point, never silently upgraded (ratified 2026-09-09).** The gate above closes the *discovery* path; the four routes still answer, so a client holding hardcoded URLs can complete a ceremony whose tokens are inert. Two things are wrong with letting such a grant survive the flip. It is a **live-looking connection today**: connected-apps lists it with real scopes, and `last_used_at` — whose contract is that a refresh rotation is "the one moment the nest observes a grant in use" — reports use for a credential that cannot be used, honest for a bridge-minted grant and false for this one. And it is a **capability change with no user-visible event tomorrow**: public sessions run 14 days and confidential ones are unbounded behind 180-day refresh tokens, so every grant still inside its window on re-point day would go live at once, on a consent given when the token was inert. Refusing to *record* it instead is worse and is rejected: the tokens are minted either way at that point, so a grant with no row is a credential the connected-apps surface can neither show nor revoke — the exact inversion the record-before-answer ordering exists to prevent (§ As built). So the re-point slice **ends** every grant the nest-hosted AS recorded before the flip, writing the same two rows revocation writes (the grant and its session family, the pair `end_oauth_session`'s storage door writes), so the refresh family dies with it. The client re-runs the ceremony; one consent card is the honest price of a consent spent on a credential that could not be used.

**Which rows those are, and the residue in finding them (2026-09-11).** Both this ending and the forced session-secret rotation's — the second door that reaches the same state, *Two rotation arms* above — need to name *the nest AS's own grants*, and until 2026-09-11 nothing in `atproto_oauth_grants` could: bridge-minted and nest-minted rows sat in one table with the same shape. They are now distinguished by an additive nullable **`issuer`** column, `'nest'` from `oauth_as_routes`' record path and NULL from the bridge's relayed kind, written at record time on the one writer both share. ⚠ **The mark is written going forward only, so a row recorded before it existed also reads NULL and is indistinguishable from a bridge-minted one.** That residue is bounded rather than sound: it can only contain grants recorded between the nest token endpoint going live and the column landing, and only from a client holding hardcoded URLs, since nothing advertised the flow in that window (*The staging rule covers both documents*). **The two endings resolve NULL oppositely, because their circumstances differ (re-ruled 2026-09-26, S2d).** The **forced session-secret rotation** selects positively on the mark and leaves NULL alone: a bridge-minted family MACs under a secret it never touches and keeps working, so ending it would sign the user out of a live connection. A pre-column nest grant's refresh token still dies on the MAC at the next `/oauth/token` read, and what's missed is only its row's ending, which the user can do by hand. The **re-point ends every live grant, marked or NULL**, and both of those premises fail there. The bridge AS retires in the same change, so a bridge-minted grant loses its token endpoint and its signing key, and its row is a live-looking dead connection, the state this paragraph's parent condemns. The re-point also re-mints nothing, so a pre-column nest grant's MAC survives and its credential would go live at the flip, which is exactly what the ending exists to prevent. It ran once, as the database step of the release that carried the re-point (schema 82), before the nest served; the step left with the 2026-10-04 genesis collapse, since no database predating the re-point exists. From then on nothing writes a NULL mark, since the bridge's relayed record kind retired with its AS. The genesis declares the column `NOT NULL`, and the grant recorder requires an issuer, so the forced arm's positive selection equals every live grant.

## OIDC (TP6)

Additive on the existing token endpoint: an `id_token` when `openid` was consented, `nonce` carried from PAR, `aud` = the client's document URL, `sub` = the actor ID (stable across handle and domain changes), `preferred_username` = the handle, `iss` = the nest domain; `/oauth/userinfo` behind a DPoP-bound access token; the discovery document advertises `id_token_signing_alg_values_supported: ["ES256"]` and `subject_types_supported: ["public"]`. `profile` and `email` are separate scopes rendered as separate card rows. **The consequence to carry:** to a standard relying party `(iss, sub)` is the identity, so a domain move reads as a new account; a Fauna-aware relying party keys on `sub`, and the identity-succession proofs ([`identity-succession.md`](identity-succession.md)) can later link old and new pairs — additive, not now.

**As built — the rules the build decided (2026-09-26).**

- **The `atproto` base scope is the ATProto family's entry rule, not the server's.** A request (and a client's declared `scope`, fetched or loopback) naming only the OIDC family needs no `atproto`; one naming any other scope still does. One predicate decides it at all three places (`authz::lacks_atproto_base`).
- **`profile` and `email` are granted only together with `openid`.** Every surface that releases their claims exists only under `openid`, so without it they would be card rows nothing honours — PAR refuses them `invalid_scope`, the same honesty rule `scope_grants_something` applies to the ATProto family. The OIDC family answers that predicate by membership (it grants at the issuer's surfaces, never at the PDS), and it is advertised only in the issuer's document — the PDS's protected-resource document keeps the ATProto family alone.
- **What each scope releases.** `openid` → `sub`, the hex actor id. `profile` → `preferred_username`, the handle. `email` → the account's canonical mailbox (the `<handle>@<mail domain>` row mail-enable writes, [`mail-aliases.md`](mail-aliases.md) § Kind 1 — Exact) with `email_verified: true`, **only while that exact alias exists and names this account** — otherwise the claim is omitted, never invented. The ID token and `/oauth/userinfo` render from one resolved value, so they cannot release different facts about one grant.
- **An OIDC-only grant needs no ATProto identity.** The access and refresh tokens' `sub` is the account's DID when the grant carries any ATProto-family scope (the PDS reads `sub` as the repo) and the hex actor id otherwise — so "Sign in with Fauna" completes for an account that never enabled Bluesky, and an ATProto grant for such an account is still refused post-consent as before.
- **The ID token is minted on the authorization-code grant only** (OIDC Core §12.2 lets a refresh reply omit it). Its `aud` is the client's `client_id`, its `nonce` the PAR's verbatim (1–256 characters; a present-but-empty `nonce` is refused, not treated as absent), and its lifetime the **access token's** — load-bearing, because the rotation horizon keeps a retired key verifiable for exactly the longest-lived token it signed.
- **`/oauth/userinfo` is the nest's one resource-plane route** (GET and POST). It verifies the access token's `iss` and pinned `typ: at+jwt` — so an ID token is refused there by its header — and requires **this issuer's identifier to be a member of `aud`**, so a token addressed to the PDS alone (an ATProto-only grant's) is refused `401 invalid_token` — then the DPoP proof with a required `ath` over the presented token and the proving key equal to `cnf.jkt`. A `Bearer` presentation is refused. Refusals are `401 invalid_token` (every token failure collapsed), `401 use_dpop_nonce` only after a verified token, and `403 insufficient_scope` for a grant without `openid`, each with a `WWW-Authenticate: DPoP` challenge and a fresh `DPoP-Nonce`. Like the PDS it does not consult the grant registry per call (§ As built — the 15-minute access lifetime is the bound). Its request budget is `ClassPublicRead`'s numbers, not the authorization endpoints'.

## Consent — one card, four starts (TP9)

One consent **card** — the built ceremony: nest-minted binding code, pending row in nest state, fan-out to the user's own authenticated apps, `resolve_consent` signed under the identity root, the read-back rule that a grant is never wider than the card (§ As built → *Consent ceremony wire flow*) — reached by four **starts**, all ending in the same `/oauth/token` exchange — PKCE + DPoP for the two starts that begin with PAR (the browser start's code travels through a redirect; the same-device handoff polls with its `request_uri`), and for the two polled-start endpoints a DPoP-bound handle that never leaves the client (*How the two polled starts are built* and *How the same-device handoff is built*, below):

| Start | Who | Mechanism | Standard | New surface |
|---|---|---|---|---|
| **Browser** | websites | PAR → authorize page long-polls → card → code released to the browser | OAuth 2.1 + PAR | none (built) |
| **Same-device handoff** (TP9 default) | device apps | PAR → the app opens `fauna://consent/<request_uri>` → the user's Fauna app on the same device opens the row (`fauna.oauth.consent.open_handoff`) and shows the card → approve → the app polls `/oauth/token` with `urn:fauna:params:grant-type:handoff` | RFC 9126 PAR with the Fauna app in the browser's seat and a DPoP-bound poll in the redirect's (RFC 8252's native-app shape without its interceptable redirect) | the `fauna://consent` route in all 7 apps, the user kind, the grant type |
| **Typed code** (TP9 default) | device apps, cross-device, mail clients | `/oauth/device_authorization` → `user_code` shown by the app → the user opens Fauna → *Connect an app* → types it → card → approve → the app polls with `urn:ietf:params:oauth:grant-type:device_code` | RFC 8628 (server half; all 7 apps already implement the client half for provisioning) | the endpoint, the grant type, the *Connect an app* entry on the connected-apps page |
| **Push by handle** (TP9, quiet) | device apps that know the handle | `/oauth/bc-authorize` with `login_hint` → card fanned out → the app polls with `urn:openid:params:grant-type:ciba` | CIBA poll mode | the endpoint, the grant type, the quiet-tray rule |

**Why push is bounded, and the three rules that close the rest.** The push endpoint inherits PAR's posture verbatim: a DPoP nonce round trip and possession proof before anything is stored or fetched, the per-IP `ClassAuth` limit before the body is read, the domain-anchored client identity shown verbatim on the card, per-bucket pending ceilings with nearest-to-expiry eviction and a ten-minute life, and a reply that never reveals whether the hint resolved (all § As built). TP9 adds: **(a)** a request from a client this user has never approved raises no notification and lands in the requests tray only — the user started the flow seconds ago and knows to look, and an unsolicited request has no way to get in front of them; a client with a prior approval may notify; **(b)** one live request per (client, user) — a repeat replaces; **(c)** a per-client "never show requests from this app" block set from the card, stored in nest state, honored silently with the same uniform reply.

**How the two polled starts are built (ratified 2026-09-26).** Both open their consent row through the ONE owner every start shares (`bridge_atproto_handlers::open_consent_request`, which names the start), so the three push rules are decided in one place and neither endpoint holds a second opinion about resolving a `login_hint`. **The typed code.** The row is opened unassigned and its code is the RFC 8628 `user_code` — 8 characters in two groups (40 bits), longer than the glance-read binding code because this one is typed and compared, and a guess that lands claims someone's device. It is **listed to nobody** until the account that types it claims it with `fauna.oauth.consent.lookup_code` (User-class; hyphens, spaces and case insignificant; any miss is one empty answer), after which it is an ordinary pending row of that account, answered by `resolve_consent`; an unclaimed typed-code row cannot be resolved by id either, so knowing a consent id is never a way around typing the code. Unclaimed typed-code rows are their own pool with a wider ceiling (64) than the unassigned browser pool (8), because nothing renders them. `verification_uri` is the issuer's origin and no `verification_uri_complete` is offered — a link carrying the code is RFC 8628 §5.4's remote-phishing aid. A `login_hint` sent here is refused rather than ignored. **The quiet push.** `login_hint` is required; `binding_message` (`invalid_binding_message` — the card shows the nest-minted code, never client-authored text), `user_code`, `id_token_hint` and `login_hint_token` are refused, since a client that sends one believes it took effect. An **unresolved hint and a blocked client (rule (c)) both open nothing** and are answered exactly as a real request is — an `auth_req_id` built from constants and a fresh handle only, which polls `authorization_pending` until it expires — so the endpoint is neither a handle oracle nor a block oracle. **Rule (a)'s "approved" means approved as what the request PROVED:** a client that authenticated (`private_key_jwt`) proved its `client_id`, so any prior grant to that client counts; a **public** client proved only its DPoP key, so only a prior grant bound to that same key counts. Without that narrowing, anyone could name a public client the user once approved, put a notification in front of them, and — since no redirect pins where the answer goes — collect the tokens by polling; a public client that re-keys per session is simply quiet, and still reaches the user through the pending list. Any grant row counts as a prior approval, revoked or expired included. Rule (b) is scoped to push rows: a repeat deletes the same client's live, unanswered push to the same account before the new row lands, and the replaced request's poll reads expired. Every bucket is (account-or-unassigned, start), so a flood through one start cannot evict another start's rows. Rule (c)'s block is nest state (`oauth_client_blocks`), set and lifted with `fauna.oauth.consent.block_client` and read back with `fauna.oauth.consent.list_blocked_clients` (both User-class) so the user can see and undo it from their own app; it governs the quiet push only — a typed code is the user's own deliberate act, and a browser row is on a page they opened. Both starts take the holder-key attestation PAR takes (`fauna_holder_x25519`), carried on the polled flow to the principal the approval mints ([`../architecture/third-party.md`](../architecture/third-party.md) owns the attestation). **The poll.** Both grants share one path at `/oauth/token`: the handle is looked up without being consumed, the client is held to the one it was issued to and authenticated, and the DPoP key is checked against the key the start was proved under — all before the consent is read or the poll is paced, so a stolen handle without its key learns nothing and cannot push the honest client into `slow_down`. The interval is 5 seconds; `slow_down` (widening it by 5 for good) is answered only while the request is still pending, since there is nothing pending left to pace once the user has answered. Only an approval consumes the handle, and only one poll can: one approval, one set of tokens, recorded through the same grant owner the code grant uses — so § OIDC holds for these grants unchanged: an `openid` grant's reply carries an ID token (with no `nonce`, since neither start carries one), and an OIDC-only grant needs no ATProto identity. Polling is what re-decided `/oauth/token`'s request budget ([`atproto-oauth-provider.md`](atproto-oauth-provider.md) owns the `ClassAuth` question).

**How the same-device handoff is built (ratified 2026-10-02).** **One PAR, two doors.** The handoff pushes exactly the request the browser start pushes — `/oauth/par` is unchanged and no parameter says which door will consume the handle — and the door is decided by who consumes the single-use `request_uri`: `/oauth/authorize` for a browser, or the user's own Fauna app for the handoff. Whichever door consumes it first spends it and the other finds it unusable, so a client whose open of `fauna://` finds no handler falls back to the browser door with the same handle. PAR's lifetime (90 s) is the window in which the user's app must open it: the handoff is same-device and immediate, and a client whose handle expired first — the Fauna app was not running, or not signed in — reads `expired_token` from its poll and starts again at the cost of one PAR. **Opening the row.** `fauna.oauth.consent.open_handoff` (User-class, self-scoped, online-only, beside `lookup_code`) takes the `request_uri` the route carried, consumes the PAR handle with the same single-use lookup `/oauth/authorize` uses, and opens the row through the one shared opener, naming a fourth start (`ConsentStart::Handoff`): the row is opened **assigned to the calling account**, never unassigned — the user who opened the route is the user who answers, and no hint is resolved to find them — with the binding code minted as every start's is; from then on it is an ordinary pending row of that account, listed by `list_pending_consents`, answered by `resolve_consent`, and pushed to the account's own apps as a browser row whose hint resolved is (the user asked for this card). A `login_hint` the pushed request carried must resolve to the calling account or the open misses: across both doors the hint has one meaning, the account this request is for. **Every miss is one empty answer** — no such handle, expired, spent by either door, a malformed handle, a hint naming another account — the `lookup_code` rule: the reply says nothing about handles the caller does not hold, and an authenticated user probing handles can at worst spend one, which is all a 256-bit handle costs anyone who learns it without the key. The reply is the row the card renders, or none. **Bucket and rules.** The row's bucket is (account, handoff) under the standard per-bucket ceiling, its own so a flood through the route evicts none of the account's browser or push rows (`consent_start` value `handoff`). TP9's three rules do not apply, each for its own reason: (a) governs an unsolicited push, and the user opened this route themselves, so it notifies; (b) a repeat is a row the user opened again, not a client's replay, so nothing is replaced; (c) the block governs the quiet push only, exactly as for a browser row on a page the user opened. The handoff takes the holder-key attestation PAR takes (`fauna_holder_x25519`), carried from the stored request to the grant. **The poll's grant.** The device app polls `/oauth/token` with `grant_type=urn:fauna:params:grant-type:handoff`, its `request_uri`, `client_id`, `code_verifier`, the DPoP proof under the key the PAR was proved under, and its client authentication when confidential. The `request_uri` is the DPoP-bound polled handle — the third grant on the path the two polled starts share: the handle looked up without being consumed, the client held to the pushed request's and authenticated, the key checked against the PAR's `dpop_jkt` — plus PKCE: the `code_challenge` PAR demanded is honoured by the poll (`code_verifier`, S256), so every parameter the client was required to push took effect; `redirect_uri` alone has no role in this door — validated as every pushed request's is, used by the browser door only — and a client that reads the grant in discovery knows that. Answers: while the handle is a live PAR nobody has opened → `authorization_pending` (the user has not reached their app yet; unpaced, since the window is PAR's own and the endpoint's budget bounds it — the one non-consuming PAR look-up, and the poll's alone); while the row is pending → `authorization_pending`, `slow_down` on the 5-second interval; declined → `access_denied` and the handle is consumed; the row expired, or the PAR expired before anyone opened it → `expired_token` once, then unknown; unknown, spent by the browser door, or already redeemed → `invalid_grant`. Only an approval consumes the handle and only one poll can. **Why a poll and not RFC 8252's redirect back to the app:** a redirect needs the Fauna app to launch another app's URI — impossible for tui over SSH, and meaningless when the user answers from another of their devices, which the row allows since it is the account's and listed on every one of its apps — and a private-use-scheme redirect on a shared device is interceptable (RFC 8252 §8.1), while a DPoP-bound handle intercepted on a shared device is useless without the key. **Why not the typed code's `user_code` in the URI:** that code is a 40-bit bearer secret and a link carrying it is RFC 8628 §5.4's phishing aid, which the typed-code start refuses; the PAR handle is bound to the client's key and is a secret to no one. **Phishing stays what it is for the browser start:** a `fauna://consent/…` URI an attacker sends to a victim is the same exposure as an authorize link — the card shows the domain-anchored client identity and the scopes, and approving is the victim's deliberate act on their own app; nothing in the URI is a secret the user must guard. The binding code has no counterpart surface in this start (no page shows it to the device app); what binds this request to this client is the handle's single use and its key. **The app half.** Every app opens the route through the shared machine (`ConnectedAppsMachine::open_handoff(request_uri)` → the kind → the card in the requests tray, the `submit_code` shape — [`../ui/connected-apps.md`](../ui/connected-apps.md) § Where logic lives); the URI's intake is per-platform glue, tui's a launch argument ([`../architecture/apps/tui.md`](../architecture/apps/tui.md) § System integration → *In-app routes*), and web's is none — a browser tab is launched by no OS link, so web's intake is this paragraph's own fallback, the browser door ([`../architecture/apps/web.md`](../architecture/apps/web.md) § Implementation status today declares the absence and the mechanisms it refused). The route stays navigation (`fauna_core::app_route`): applying it opens the pending request the card shows, as the browser's `GET` does, and the approval stays the user's act on the card. A route arriving before the session is signed in is held and applied once it is; when the PAR has expired by then, the miss paints as the page's one error and the user starts again from the device app.

**The install-approval leg** (hosted code) shows the same card with an install section and is the admin's act; it mints a principal and no grant — owned by [`../architecture/third-party.md`](../architecture/third-party.md) § The runner contract.

**The card chooses the folder (ruled 2026-10-05; the nest half built, the picker unbuilt — § Implementation status today).** A consent row carrying a **bare** folder-plane scope (§ Scope grammar → *The folder plane's qualifier is the user's*) renders **one folder picker** on the card — one per card, however many bare folder verbs it carries — over the account's own folders that every such verb can take: for deposit a residency that is not metadata-only, for read a set the owner's custody marks served ([`webdav-server.md`](webdav-server.md) § Key model → *A principal's read*, rule (2)); the options come from the approving app's shared machine — the owner's folder custody, by name, keyed by row id — never from the request, and when no folder is eligible the card says why and cannot be approved. The approve sends the chosen folder with `resolve_consent`, after the approving app has minted the arm's twin over it (the deposit arm's keyless tuple, the read arm's keyed one) — mint before resolve, as for every twin — and the nest qualifies the row's bare scopes with it before recording the approval, so what the grant records is the card's rows plus the user's own choice. A qualified folder scope on a card renders as today — the folder named when the approving app can resolve the id, the approve refused when it is not one of the account's — and shows no picker. The picker is the Connected apps page's element ([`../ui/connected-apps.md`](../ui/connected-apps.md) § Element IDs — a rule-A approval pending).

## Scope grammar — three families

One advertised grammar, three families, one predicate — "every advertised scope must be one the matrix can grant something under" (`authz::scope_grants_something`, [`atproto-oauth-provider.md`](atproto-oauth-provider.md) § F4 detail → *Scope model*):

| Family | Shape | Examples | Owner |
|---|---|---|---|
| **OIDC** | fixed | `openid`, `profile`, `email` | this doc § OIDC |
| **ATProto** | as built | `atproto`, `repo:*`, `blob:*/*`, `rpc:*?aud=*`, `include:<NSID>` | [`atproto-oauth-provider.md`](atproto-oauth-provider.md) — unchanged; `no_granular_scope_reaches` keeps the box's own account plane unreachable |
| **Fauna** | `fauna:<plane>:<verb>[:<qualifier>]` | `fauna:records:rw:ext.dating.example.*`, `fauna:folder:deposit:<folder-id>`, `fauna:folder:read:<folder-id>`, `fauna:feed:read`, `fauna:feed:read:account`, `fauna:personalization:rw`, `fauna:events:subscribe`, `fauna:follow:write`, `fauna:conversations:bridge`, `fauna:identity:op:<class>` (posting is the class `post.author` — *The planes ruled 2026-10-02*, below; `fauna:post:write` is retired) | this doc; the qualifier is an `ext.*` kind or its publisher's wildcard, a folder id (the user's, chosen on the card — *The folder plane's qualifier is the user's*), an operation class, or the fixed word `account` (the account's own reading of a plane whose bare verb is public); a wildcard covers exactly one publisher's kinds ([`../architecture/third-party-kinds.md`](../architecture/third-party-kinds.md) § The grammar) |

Rules carried over unchanged from § As built: a PAR is held to the document's own declared `scope` by exact membership; expansion is frozen at the ceremony, never re-resolved; the card renders every scope through one shared describe path in the shared machine, control characters stripped where the row is composed. **A Fauna scope that names sealed data has a grant twin** ([`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Capability tiering → *Third-party holders*): the card row says both what the token permits and what keys will be wrapped, in words; a scope with no grant twin (`fauna:feed:read` over public content) says so, and so does a keyless twin — the record minted, no key wrapped (`fauna:identity:op:<class>`, `fauna:folder:deposit:<id>`). **No `fauna.*` kind is ever grantable to a principal by name** — first-party kinds are reached only through the family's *plane* verbs.

**The Fauna family, exactly (ratified 2026-10-01; built 2026-10-01 — § Implementation status today).** The table row above gives the shape and the planes the rulings name; these six rules are what a build follows.

- **The string.** `fauna:<plane>:<verb>[:<qualifier>]`. Plane and verb are lowercase ASCII letters. The qualifier is everything after the third colon, drawn from `a–z 0–9 . _ -`, plus — for `records` alone — one trailing `.*`. Scopes are compared as whole strings, never by prefix: `fauna:folder:read:abc` neither grants nor is granted by `fauna:folder:read:abcd`.
- **A closed table, one arm per built plane.** The family lives in shared Rust as a module beside the ATProto grammar (`fauna_bridge_atproto::fauna_scope`; the crate's name is residue — it has been the issuer's whole decision layer since the issuer moved to the nest — and `describe_scope` and `scope_grants_something` stay the single doors every caller already uses). Each arm fixes a plane and verb, whether a qualifier is required and its form, its card row, and whether it has a grant twin. **A string matching no arm is `invalid_scope` at PAR — including a plane the table above lists and no slice has yet built.** That is the family's predicate made structural: an arm exists only while a kind in the `ThirdParty` ceiling names it, and a nest-side sweep test holds the two sets equal — every arm reaches at least one kind, every scoped ceiling kind names a live arm ([`../architecture/apps/bridges.md`](../architecture/apps/bridges.md) § Capability-allowlist enforcement → *`ThirdParty`* owns the ceiling). **Amended 2026-10-05 for the first bridge-doored arm:** an arm has exactly one door — the nest's dispatch, or a bridge's resource server — and the predicate reads per door: a nest-doored arm exists while a ceiling kind names it; a bridge-doored arm (*The read arm*, below) while the BridgeMda relay kind that admits its token exists; the same sweep holds both sets, and no arm is doored twice. Discovery advertises the arms that exist, in the issuer's document only.
- **A scope string's reach never widens.** Once an arm ships, the set of kinds it covers is fixed. A grant is frozen at its ceremony and nothing asks the user again, so mapping a new kind onto an existing string would enlarge every outstanding grant with no consent event. New reach is a new verb or a new qualifier, with a card row of its own. Narrowing — retiring a kind from an arm — is always allowed.
- **Wildcards.** Only `records`, only trailing, and only the principal's own publisher: `ext.<publisher>.*` covers exactly the kinds whose parsed publisher **equals** `<publisher>` — one name label, matched structurally after parsing the kind, never by string prefix — and at PAR `<publisher>` must equal the client document's host ([`../architecture/third-party-kinds.md`](../architecture/third-party-kinds.md) § The grammar owns the parse; re-ruled 2026-10-02 from "inside the domain prefix", which a dot-separated domain made ambiguous).
- **Session kinds need no scope.** A small set of kinds is covered by holding a principal session at all — which itself takes at least one Fauna-family scope. The first is `fauna.capabilities.fetch`, self-scoped to the principal's own holder key, so a principal that attested no key reads an empty list. They are still arms of the compiled ceiling, reviewed like any other.
- **The first arm: `fauna:feed:read`.** No qualifier, no grant twin. ## Tokens authorize transport

Every third-party call carries a DPoP-bound access token (≤15 min — the honest cap given no per-call revocation, § As built → *Lifetimes*) naming its scopes; the resource-server plane's scheme dispatch and per-plane replay set ([`atproto-oauth-provider.md`](atproto-oauth-provider.md) § F4 detail → *The resource-server plane*) apply unchanged to the nest's own routes. **A token opens no sealed byte.** It is what the nest checks at the central dispatch chokepoint ([`../architecture/apps/bridges.md`](../architecture/apps/bridges.md) § Capability-allowlist enforcement → *`ThirdParty`*) and what rate limits and audit key on. On WS-RPC the token is presented once, at the upgrade of a connection of the principal's own, and its `exp` ends that connection ([`../architecture/transport-connection.md`](../architecture/transport-connection.md) § Connection lifecycle → *The principal session*).

## As built — the bridge-hosted authorization server (moved verbatim from `atproto-oauth-provider.md` § F4 detail, 2026-09-05)

The bullets below are the record of what shipped. Read them with § The issuer: bullets premised on *bridge* custody or on the PDS host (the first bullet's mounts and key custody; § *AS-key rotation*'s beside-not-inside blob and no-`kid` status) are superseded in their premise only — every posture ruling (refuse before storing, one freshness constant, Rust decides / Go verifies, the code consumed before validated, the two signers, the uniform revocation answer) carries to the nest-hosted issuer unchanged.

- **Endpoints on the PDS host:** `/.well-known/oauth-protected-resource` (points at the AS = same host), `/.well-known/oauth-authorization-server` (PAR required, PKCE S256 required, DPoP required, the granular scope grammar advertised), `/oauth/par`, `/oauth/authorize` (the consent page), `/oauth/token`, `/oauth/revoke`, `/oauth/jwks`. AS signing key: ES256, bridge-held, sealed like the rest (§ Key material). DPoP: server-issued nonces from a rotating bridge-memory secret (≤5 min windows, per spec); access tokens carry `cnf.jkt`, ≤30 min; refresh lifetimes follow the ecosystem's public/confidential split. PAR requests and auth codes are **bridge-memory with TTLs** — transient by design (C6): a bridge crash mid-flow fails that flow cleanly and the user retries. The pending **consent row is nest state** (§ Nest state schema's `atproto_consent_requests` — the apps read and answer it, and a WS-RPC kind is how they reach anything); only the browser-flow bookkeeping around it is bridge memory. *(This sentence originally listed consent state as bridge-memory; slice 6a's ratified ceremony rulings settled the split, and § Nest state schema owns it.)*
- **Client metadata resolution:** `client_id` is a URL → fetched with the same SSRF guard as proxying (HTTPS, public DNS, size/time caps) + the spec's loopback-client dev carve-out, cached with TTL. The consent page displays the *resolved* client name/logo alongside the requesting origin — never the client's self-asserted string alone.
  - **The URL is parsed exactly once, by the component that dials it.** Shared Rust *classifies* a `client_id` (loopback dev client / https fetch plan / refuse) and Go parses, resolves, guards and GETs — the same split, for the same parser-differential reason, that § F3 detail phase 3 fixed for the proxy dial. What Rust adds on top of the guard are identity tightenings the guard has no opinion about, expressed as substring facts so they cannot disagree with a parse: **no fragment, no userinfo, no port**. A document is this client's only if its own `client_id` member **string-equals** the URL it was served at; that equality is what makes the URL a self-authenticating identity.
  - **The loopback dev carve-out's boundary is the redirect host, not the client_id.** `http://localhost` (no port, empty path — an IP-literal host is *not* the loopback client_id) resolves with **no fetch at all**, from a document synthesized out of its own query string; unknown query parameters refuse rather than being ignored, because for this client the `client_id` *is* the document, so an unread parameter is a configuration the client wrongly believes it made. Since that identity is one nobody owns and anybody may claim, **every declared `redirect_uri` must be `http` on `127.0.0.1` or `[::1]`** — otherwise an attacker would hold a consent-screen identity that redirects the response to a host they control. Port is ignored in redirect matching (a dev server binds whatever ephemeral port it gets); **path is not**. The displayed name is chosen by this server ("Development client"), which is the "never the client's self-asserted string" rule holding for free.
  - **The cache is never authoritative, and it caches refusals too.** Positive TTL 15 min (short enough that a fixed or withdrawn document takes effect promptly, long enough that an authorization burst costs one fetch); **negative TTL 1 min**, deliberately far shorter — without negative caching a hostile `client_id` costs one outbound fetch per request, which is the amplification an unauthenticated endpoint must not offer, and with it a transient outage at a good client's host pins that client as broken. Size-bounded, evicting nearest-to-expiry; every eviction costs only a re-fetch, which is what licenses so crude a policy. A fetch failure's **reason is logged, never echoed** — it describes our outbound network, and returning it would make the endpoint an SSRF oracle.
  - **What is authoritative for the consent page is the whole resolved client**, stored beside the pushed request rather than flattened into it, so there is one owner of what gets rendered. `logo_uri` is stored and **deliberately not fetched by the nest or bridge**; whether the approving app loads it is the consent slice's decision, because loading an attacker-named URL inside the user's app discloses the user's address to whoever published the document.
- **PAR (`/oauth/par`) — the pre-consent gate.** Every refusal returns **before** anything is stored: the endpoint is an unauthenticated write surface, so a request that will be rejected must never occupy a slot in it, and keeping the decision a pure function is what makes that structural rather than a rule the handler has to remember. Accepted requests get an RFC 9126 `urn:ietf:params:oauth:request_uri:` handle (256 bits of entropy), answered `201` with `expires_in`, held in bridge memory under a **90 s** TTL and a size ceiling that evicts nearest-to-expiry — overflow costs that flow a retry, which is exactly C6's transient-by-design contract, and is also why this whole transition has no client-state-recoverability surface: it writes no durable state at all. Redemption is **single-use and lives with the store** (the lookup consumes), so a redemption path cannot forget a rule its only lookup enforces. A client-supplied `request_uri` is refused — the handle is issued by this server, never named by the caller. **The endpoint refuses (`temporarily_unavailable`) when this bridge has no AS signing identity**: accepting a request whose token exchange could never be signed would redirect the user into a ceremony that cannot complete, so F4 is uniformly inert without its key plane.
  - ~~**Still deferred: confidential-client authentication (`private_key_jwt`)**~~ — **CLOSED 2026-07-31 (slice 5), and with it all three of the checks the mounting gate was holding.** See the *Confidential clients* bullet below; `TestPDSMuxDoesNotMountOAuthDiscovery` now guards only the one thing its name says — the two `.well-known` documents stay unmounted until `/oauth/token` exists — so the slice that deletes it has *less* to check, not more.
    - ⚠ **The mount is safe because it is BOUNDED, not because it is unlisted** (correction, 2026-07-31, refuting slice 3's recorded ground). `/oauth/par` is a **spec-conventional path**: an attacker needs no discovery document to find it, so "a client learns the endpoint exists only from the AS document" was never the protection and must not be recorded as one — a later session deleting the per-IP limiter on the strength of "it's undiscoverable anyway" would be reasoning from a false premise. What actually bounds the endpoint is the machinery in the code: the per-IP `ClassAuth` limit applied before the body is read, the shared `fetch_guard` on the only outbound call it makes, the size/TTL ceilings on both stores — and, since slice 4, **a DPoP proof and a live server-issued nonce required before client resolution runs at all**, which is what removed the anonymous-caller-triggers-an-outbound-fetch primitive entirely. Discovery staying unmounted is a defence-in-depth *reduction in traffic*, not the boundary.
- **DPoP at PAR — possession before anything else the endpoint does.** Every request carries a proof JWT the client signed with its own key; the key's RFC-7638 thumbprint is stored beside the pushed request as `dpop_jkt`, which is what the token slice binds into `cnf.jkt`. Seven rulings fix the shape.
  - **The nonce is a keyed MAC over a window index, not a token in a set** — `HMAC(secret, domain ‖ window)`, truncated. The alternative (mint a random nonce, remember it) would put a *third* unauthenticated write surface on an anonymous endpoint, and its overflow policy would have to choose between refusing to issue nonces and issuing ones it cannot recognise. A MAC has no set to overflow, and no amount of traffic can make a nonce live longer than the window named inside it.
  - **One freshness constant, not two.** A proof's `iat` window and a nonce's lifetime are the same number — two accepted windows of 2 minutes, so **4 minutes**, under the spec's 5-minute ceiling (§ Ecosystem reality item 3) with headroom, so widening the accepted-window count later cannot silently cross it. Two separate freshness rules on one path would be two things to keep in step, and a proof cannot outlive the nonce it must carry anyway.
  - **The secret rotates hourly with a one-generation overlap** (§ Key material inventory's *DPoP nonce secret* row). Freshness is bounded by the window index, never by rotation; the overlap exists only so a client whose proof was minted moments before the rotation instant is not refused for something it could not have known.
  - **Rust decides, Go verifies — and the compact JWT is decomposed exactly once, in Rust.** Every policy question (`typ`, `alg`, the embedded JWK's shape, `htm`/`htu`, `iat`, `ath`) is `fauna_bridge_atproto::dpop`; the signature check, the nonce's provenance and the `jti` store are Go's, per the same ruling that put signing there. The module hands back the exact `signing_input` bytes and key coordinates, so **Go never re-splits the token**: this is the *Client metadata resolution* bullet's "parsed exactly once, by the component that dials it" applied to a JWT, and for the sharper reason — two splitters would have the part that *decides* and the part that *verifies* judging different headers.
  - **`htu` is compared exactly, against the URL this server's own AS document advertises.** One builder (`oauth_metadata::oauth_par_endpoint_url`) renders both, because a conformant client builds `htu` from the endpoint URL it read out of our document — so exact equality is what a correct client produces, and a second spelling would refuse every one of them with nothing visibly wrong on either side. A `htu` that kept its query or fragment is refused by name.
  - **The order is the security property, in three places.** (i) The gate runs **before client resolution**, which dials a host the caller names — so an anonymous caller cannot make this server fetch anything until it has completed a nonce round trip and proved possession of a key. (ii) The nonce is checked **before** the signature: it is the cheap check, it is the one every correct client fails on its very first request, and answering it early costs an attacker nothing, since this server hands a fresh nonce out with every response anyway. ⚠ **That last clause is a standing DUTY on every plane that requires a nonce, not an observation about these three endpoints** (corrected 2026-08-03 — it was found false the moment slice 7 added a second such plane; see the *resource-server plane* bullet's nonce ruling in § F4 detail). A plane may not require a nonce it does not issue: a nonce lives one freshness window and a token lives far longer, so requiring without issuing strands every client whose harvested nonce ages out. **Any future nonce-requiring surface inherits the duty with the requirement** — it is what licenses this ordering, so a surface that skips it invalidates the argument above rather than merely being inconvenient. (iii) The `jti` is recorded **strictly after** the signature verifies — recording it earlier would let anyone send unsigned proofs carrying an honest client's future identifiers and lock that client out, turning the defence into the attack.
  - **A JWK carrying private key material is refused, not ignored.** The thumbprint ignores `d`, so nothing else would notice; a client shipping its private key is one whose key must be treated as compromised, and quietly accepting it means holding a secret we were never meant to see. **`ath` is likewise refused** rather than checked: it binds a proof to an access token, and an authorization-server endpoint takes none — a proof carrying one was minted for a different request context.
  - **The replay set's overflow evicts nearest-to-expiry and logs it, and that direction is THIS endpoint's, not a general one.** Evicting a pushed request costs one flow a retry; evicting a `jti` lets one proof be replayed. It is the right trade here because a replayed PAR proof buys an attacker nothing of value — the eventual token is bound to the proof's own key, which a replayer does not hold, and the `request_uri` redirects only where the client declared — and because failing closed would hand any flood an off switch for the endpoint. **`/oauth/token` must re-decide it:** a proof there is bound to a token being *used*, so the calculus is not the same one. ⚠ **That obligation binds EVERY caller of the shared type, not just the one named here** — slice 7 added a third (the resource-server plane) and inherited this policy without either decision being taken. A new caller re-decides two things, and the second is the one that was missed: the eviction *direction*, and whether it may share an *instance* — sharing pools two populations into one budget, so the plane reachable at the lower privilege level can spend the other's. Both are settled for the resource server in § F4 detail's *resource-server plane* bullet.
- **Confidential clients — `private_key_jwt`, and the key set resolved before it is needed.** A client whose document declares `token_endpoint_auth_method: private_key_jwt` signs a short-lived JWT with a key that same document publishes; there is no shared secret anywhere in this design, so **the client's metadata document is its credential store** and the `client_id` URL it is served at is what makes the identity self-authenticating. Five rulings fix the shape.
  - **The key set is resolved EAGERLY, with the client — never lazily at assertion time.** A `jwks_uri` is followed as part of resolving the client, so the cached `ResolvedClient` always carries usable keys and **authenticating an assertion performs no network I/O at all**: no failure mode, no timing signal, no ordering question on the one path whose whole job is establishing who is calling. The rejected alternative also had to answer *"an assertion names a `kid` we have not seen — do we re-fetch?"*, and both answers are bad (yes makes an attacker-chosen `kid` a fetch amplifier; no makes rotation silently unsupported). Eager resolution never asks it. The cost — a rotated key takes effect only when the 15-minute client-cache entry expires — is exactly what a key *set* with `kid`s absorbs: a client rotating correctly publishes old and new together. The `jwks_uri` fetch is a **second call site of the one guarded fetcher**, never a second fetch path (the § *Client metadata resolution* rule, unchanged).
  - **A confidential client with no usable key is refused at RESOLUTION**, and a document declaring both `jwks` and `jwks_uri` likewise. A document that says "I authenticate with a key" and then names none describes a client that could never authenticate; refusing there means the client author sees a configuration error (cached negatively, so one fetch rather than one per request) instead of an assertion failure that reads as the assertion's fault. Two key sets is not a merge problem — it is two answers to "which keys sign my assertions", and picking one would be this server deciding which of the client's own statements to believe. Within a set, keys this server cannot verify with (RSA, another curve, `use: enc`) are **skipped**, because a real key set holds keys for several purposes; a set with *nothing* usable, a **duplicate `kid`** (selection must not depend on document order), or a malformed *usable-looking* key refuses the whole set — skipping that last one would leave the client authenticating under whichever other key happened to parse, a silent downgrade of what it published.
  - **Both directions refuse, and `token_endpoint_auth_method` is the single owner of which direction applies.** A confidential client that sends no assertion is refused — that is the fact `ResolvedClient.confidential` existed to enable since slice 3, and until now it had no consumer, so anyone could push requests in a confidential client's name. A **public** client that sends one is *also* refused rather than having it ignored, the same posture as the loopback client's unknown query parameters: a caller that sends credentials to an endpoint which silently discards them believes it authenticated. The presence of a key set never implies confidentiality — inferring an auth method from key material is how a client gets held to a contract its document never made.
  - **Authenticate, then authorize.** The gate runs after client resolution and **before** the PAR request is validated. A confidential client that has not proved it is itself must not reach the scope and redirect refusals: those are diagnostics about *that client's* configuration, and handing them to a caller who has not shown it is that client makes the endpoint a probe for someone else's setup.
  - **`aud` is the claim that carries the security, and the replay entry's life comes from the artifact.** The assertion must name **this AS's issuer**, from the same builder that prints `issuer` in the AS document — one owner, so a correct client's spelling and ours cannot diverge — which is what stops an assertion minted for another authorization server being replayed here. A `jti` is required and remembered until the assertion's own `exp`, **capped at 5 minutes**: deriving the entry's life from the artifact rather than a store-wide constant is what makes the set's size a function of that cap. ⚠ That ceiling is deliberately **not** the DPoP proof's window, and this is the one place F4 declines to follow the *one freshness constant, not two* ruling — those two are the same rule stated twice (a proof cannot outlive the nonce it carries), while these are two different rules on two different artifacts: the proof's freshness is a window *this server* mints, the assertion's is a claim *the client* makes. Sharing the number would mean a future widening of the DPoP window silently widened how long an assertion stays replayable. The replay store is now **one implementation with two policies** (`replaySet`, per-entry expiry supplied by the caller) — the shape is shared so the eviction loop cannot diverge; the policy is re-decided per credential, which is exactly what the DPoP slice's own finding demands and must not be read as having been shared along with the type.
- **Consent ceremony wire flow (D3 rung 2):** authorize page renders client + scopes + a short **binding code** and long-polls the bridge; bridge → `create_consent_request` → nest stores pending consent + fans out `fauna.atproto.consent_requested` to the user's apps (identified via the PAR `login_hint`; no hint → the page says "open Fauna and approve" and the pending consent is visible in-app). The client's approval card shows the same client identity, the scope list (human-readable, from the D8 parser), and the binding code; the user checks the code matches the browser and approves — `resolve_consent` over normal authed WS-RPC, Ed25519-rooted. Nest nudges the bridge (`consent_resolved`, poll-fallback `fetch_consent`); bridge releases the auth code to the browser; token exchange completes with PKCE + DPoP. The code-match is what binds *this* browser tab to *this* approval — a phished consent push without the matching code is visibly wrong on the card. <!-- gitleaks:allow -->
  - **The NEST mints the binding code; the bridge renders what it was handed.** One origin for the value both surfaces show, so the bridge structurally cannot display a code the pending row does not hold, and per-flow uniqueness is guaranteed by the party that also authenticates the approver. The rejected alternative — the bridge mints and the nest stores an opaque string it did not generate — leaves the nest unable to say anything about a value it fans out. **Uniqueness is among every LIVE row, not per account:** an unassigned request is rendered on the same card list as an account's own, so a shared code is precisely the confusion the mechanism exists to prevent; minting re-rolls on collision and fails loudly rather than ever emitting a duplicate.
  - **The code's length is chosen for glance-comparison, and the argument is not entropy.** Six characters over the ambiguity-free 32-symbol alphabet (30 bits, `ABC-DEF`). It is never typed and never compared programmatically — a human reads it off their browser and matches it against their card — and what it defends against is a *phished consent push*, which fails because this server mints the code and refuses to reuse a live one, not because the code is hard to guess. Guessing is bounded anyway by a minutes-long lifetime, the PAR endpoint's per-IP limit and the per-bucket ceiling. ⚠ This is deliberately **not** the admin claim code's length constant, which is a user decision tied to the *claim throttle*: the two share only `fauna_core::human_code`'s alphabet, and sharing the generator but not the length is the whole point of that module.
  - **`client_name` is stripped of control characters where the card row is COMPOSED, in the shared machine — never in a per-app painter (fixed 2026-08-01).** The nest applies only `non_empty` to a client's published name, and every app paints the card as one structured multi-line body that is later split on newlines — so without the strip, characters in a client-published name and the card's own row structure are the same bytes by paint time. The invariant: the card's rows are the card's own, because the name is stripped where the row is composed. Three things this fixes and one it does not. **(i)** Composition is the fence because it holds for all seven apps at once (priority #2) — six have yet to paint this card. **(ii)** A per-app *structural* fix (a dedicated element for the name) would **not** be sufficient: a name carrying fifty newlines still paints fifty rows. **(iii)** The scope descriptions are stripped in the same pass — not needed today, since no scope token can carry a newline, but that safety is a property of a splitter two crates away and `describe_scope` echoes raw text on its unknown-scope fallthrough. **What it is not:** the tui sink-side control-character gate is *correct where it is* and must not be moved here — it runs after the split that has already consumed newlines as row structure, so the property is gone by the time it sees the text. ⚠ **The browser half never had this defect** (`html/template` contextual escaping plus a separate DOM element per field), which is the sharper half of the lesson: the premise that the two surfaces say the same thing held only one way, and the forgeable one was the app the user approves in.
  - **`logo_uri` does NOT cross to the approving app at all** (this is the decision § *Client metadata resolution* deferred to this slice). Loading an attacker-named URL inside the user's app discloses their address to whoever published the document, and the consent card is exactly where an attacker controls that URL — while a value that crosses but must never be rendered is the dark-capability class D10's `device_key` disposition already names. The card renders the **resolved** `client_name` plus the `client_id` **verbatim**; nothing derives an origin from it, because that string is parsed exactly once, by the component that dials it. A future logo needs its own ruling on *who fetches it* (the bridge, through the one guarded fetcher, re-serving bytes) and is additive.
  - **⚠ The reply to `create_consent_request` must not reveal whether the `login_hint` resolved.** The authorize page is anonymous and attacker-reachable, so a distinguishable answer would make the OAuth flow a **handle-enumeration oracle** — the exact posture § Security posture summary forbids where the answer is free. An unresolvable hint therefore takes the same path as no hint at all: an unassigned row, and one page text either way. The difference lives where it belongs — in *who can see the request*, not in what the browser is told.
  - **An unhinted request is stored unassigned and claimed by whoever answers it.** The approver's own identity is the answer to "which account is this grant for", so `resolve_consent` binds the caller — for a decline as much as an approval, so the row records who answered. Two consequences to hold: it is listed to every account on the nest (the honest cost of a flow that named none), and the flood bound is therefore **per bucket** — an account's own rows and the unassigned pool are counted separately, so neither can evict the other.
  - **Overflow evicts nearest-to-expiry, and expiry is its own constant.** With one shared TTL, nearest-to-expiry is the oldest, which is the right direction because a flood's victim is mid-flow in the *newest* request; refusing instead would let an attacker deny a user the ability to consent at all. The window bounds a **human** — unlocking a phone, finding the app, comparing the code — which is why it is ten minutes and deliberately **not** a reuse of any F4 freshness number (the DPoP window, the assertion cap, the PAR TTL). Those bound cryptographic artifacts; this bounds a person, and sharing one would mean a change to either silently moved the other.
  - **`fetch_consent` collapses "unknown id" into `expired`, and reports a resolution past expiry.** A swept row, an evicted row and an id this nest never issued are one answer to the only caller — *this flow is dead, start again* — and two statuses meaning the same thing to their only consumer is how they drift apart. Conversely a **resolved** request reports its resolution even past `expires_at`: the user really did answer, and what may still be minted from that answer is the bridge's own freshness rule, not one to lose by silence. The approved reply carries the account, its `login_did` (present only while the ATProto identity is ACTIVE — the same two-rules-in-one-field treatment `fetch_app_credential_verifiers` holds, so a layer-2 step-down cannot be undone by approving a fresh grant), and **the scope set read back from the row the user was shown**, which is what stops a recorded grant ever being wider than the card.
  - **The two halves are class-separated in both directions.** `create_consent_request`/`fetch_consent` are bridge-only — a user who could *open* a consent request could push an approval card naming any client they liked, which is the phishing shape the binding code exists to make visible — and `resolve_consent`/`list_pending_consents` are user-only, since the approval arriving over the caller's own authed connection *is* the ceremony's Ed25519 root. Authorization for an answer is the storage layer's `WHERE` clause rather than a pre-check: a row belonging to another account, an already-answered row and an expired one are all simply unmatched, so there is no read-then-write window and an approval cannot be replayed into a second grant.
- **`/oauth/token` — the two grants, and the two signers (F4 slice 7).** `authorization_code` redeems the released code; `refresh_token` rotates the pair. Ordering is PAR's, one endpoint over: per-IP limit before the body, a fresh nonce on every response, the DPoP gate before anything is looked up, every refusal before state is written. Six rulings fix the shape.
  - **The code is consumed BEFORE it is validated, and the grant is recorded BEFORE the tokens are answered.** `authCodes.Take` deletes on lookup, so a redemption that then fails PKCE or the key binding has still spent the code — a guessed or stolen code is worth exactly one attempt, and the honest client's retry failing too is correct (a client that must retry starts a new flow; the same rule holds at the authorize endpoint, one step later). The write order is the reverse trade: a crash between the grant row and the answer costs one failed exchange, while answering first would hand out credentials the connected-apps surface cannot see or revoke — a capability with no audit row, which [`../principles.md`](../principles.md) forbids outright.
  - **Two signers, and the split is what makes AS-key rotation possible at all.** An access token is **ES256 under the AS key** because it is a public artifact any resource server may verify against `/oauth/jwks`. A refresh token is **HS256 under the session secret** because it is not: it is presented back to this bridge and to nothing else, so a public signature would buy nothing — and would cost the rotation horizon, since the outgoing key would have to stay verifiable for the refresh lifetime (up to 180 days). With only ≤15-minute access tokens ES256-signed, a rotation retires the old key in **minutes**. ⚠ Do not "unify" the two onto the AS key for symmetry; that is the ruling directly below made unbuildable.
  - **Lifetimes, from § Ecosystem reality item 2's corrected constants.** Access **15 min**, not <30: the AS cannot revoke an individual access token, so the stricter cap is the honest one. Slice 7 shipped the grant row without a per-call check or `/oauth/revoke`; slice 8a shipped the revocation endpoint and **still declines to widen**, because revoking a *family* is not revoking an *access token* — see the ⚠ ruling below, which now owns this question. Widening stays **additive for the slice that builds the per-call consultation, and must not precede it.** Individual refresh tokens ≤ **180 days** (confidential); a **public** client's grant additionally carries an absolute **14-day** session deadline as a `sexp` claim carried across every rotation, so refreshing cannot extend a session — a public client holds no credential of its own, so PKCE and DPoP are all that bind it.
  - **One HS256 secret now signs two planes' refresh tokens, so every token names its plane.** Without the claim each would verify at the other's endpoint: an OAuth refresh token rotating through `com.atproto.server.refreshSession` would mint an app-plane access token — laundering a DPoP-bound credential into an unbound one — and an app-password refresh token redeemed at `/oauth/token` would buy a grant nobody consented to. Both directions refuse. An absent claim reads as the app plane, which is what every token minted before this slice is.
  - **Rotation rides the NEST's registry** (`plane: "oauth"`, `record_grant` writing the grant row and its session family in one transaction), so rotate-on-use and the reuse family-kill apply to OAuth refresh tokens with **no second implementation** — a replayed OAuth refresh token kills its family exactly as a replayed app-password one does. The grant id *is* the session family id *is* the initial refresh `jti`: one identifier joining the connected-apps row to its rotations, which is what lets the revoke slice cascade with no join table.
  - **The replay-set eviction direction, re-decided here as the DPoP bullet requires** (and it lands on the same answer as PAR, for different reasons — the point of re-deciding). Evict nearest-to-expiry and log. Every artifact a token-endpoint proof accompanies is *already* single-use at its own store (the code at `Take`, the refresh token at the nest's rotate-on-use), so an evicted `jti` re-opens replay only of a proof whose companions are spent — exploiting it needs an independent credential theft. Failing closed, by contrast, would hand a flood an off switch for **every sign-in and every refresh** on the box, with live sessions dying inside the access lifetime: strictly worse than at PAR, where a refusal only delays a new login. The assertion set is shared with PAR and its corrected sizing is unchanged by the second recorder.
- **Grant registry:** token issuance writes `record_grant`; the grant row (client, scopes, `dpop_jkt`, timestamps) is the connected-apps row, read by the user-class `list_grants` (F4 slice 8a). Revoke from any app → the grant row and its refresh family die in one transaction, immediately and authoritatively nest-side; an already-issued access token dies within its own ≤15-minute lifetime at the PDS (the *Lifetimes* ruling above, and the reason that cap stays where it is), while a principal session opened under the family is closed by the ending itself ([`../architecture/transport-connection.md`](../architecture/transport-connection.md) § Connection lifecycle → *The principal session*, door (c)). The same transaction finds-or-creates the account's third-party principal for the client, recording the holder key the PAR attested; that row, its attestation parameter and its one-verb revoke are owned by [`../architecture/third-party.md`](../architecture/third-party.md) § The principal model (built status: its § Implementation status today).
  - **The registry write is idempotent on `(actor_id, grant_id)`, and the arm that makes it so writes nothing (ruled 2026-09-09).** `grant_id` is fresh per exchange, so a second call carrying one is the same exchange asked twice — the reply lost between the commit and the caller. It reports the success the first call already earned; a call whose *authorization* fields differ under a colliding id still errors, because that is a bug rather than a replay. **The replay must not re-land the rows**: an OAuth session's `current_refresh_jti` is unset only until its first rotation and reads as *“the initial jti (= the grant id) is current”*, so re-landing it after a rotation would return a spent refresh token to validity and disarm the reuse family-kill — the same reason revocation survives a replay. This is what the kind's `forbid_replay = false` asserts ([`../architecture/transport.md`](../architecture/transport.md) § Idempotency and reconnect-with-resume owns that flag's meaning); until this ruling the claim was false and a replay was a primary-key violation.
  - **There is deliberately NO `revoke_grant` kind, and that is a design ruling rather than an omission.** `grant_id` *is* the session-family id, so revoking a grant is `revoke_session` over that id, whose storage function cascades to the grant row. One operation with one spelling: the user's app, the bridge behind `/oauth/revoke`, and the reuse family-kill all reach the same function, so the three cannot come to disagree about what revocation means. The cascade runs in the *reuse-detection* path too — reuse is exactly when a row must stop reading as live.
- **`/oauth/revoke` (RFC 7009) — the whole grant, and a uniform answer (F4 slice 8a).** Ordering is `/oauth/token`'s: per-IP limit before the body, a fresh nonce on every response, the DPoP gate before anything is looked up. Four rulings fix the shape.
  - **Revocation destroys the GRANT, never one artifact.** RFC 7009 §2.1 permits either and recommends the cascade; here it is the only honest option, because an access token is a self-contained JWT nothing consults per call — "revoke just this access token" is a request this AS could answer 200 to and do nothing about. Either artifact therefore identifies one family and kills it. `token_type_hint` is read as a hint that orders the two verifiers and never as a constraint that limits them, so a client mislabelling its own token still gets it revoked.
  - **Every token outcome answers an identical empty 200 — revoked, unknown, expired, other-plane, or bound to a different key.** RFC 7009 §2.2 already requires 200 for an invalid token, and the reason generalises: a distinguishable answer makes the endpoint a **validity oracle** on token bytes, letting a thief who holds a stolen token but not its DPoP key learn the token is live, and learn when the honest client's rotation retires it. The client's remedy is identical in every case. Non-200 answers are all about the *request* — wrong method, no `token`, a failed DPoP gate, a confidential client that did not authenticate, and the one genuine failure (the nest call erroring), which must not answer 200 because the client would believe it had signed out.
  - **A DPoP proof is required, though RFC 7009 does not ask for one.** Without it, anyone holding stolen token bytes could sign the honest user's app out — a denial-of-service reachable with a credential that is otherwise useless. With it, revoking needs the key the grant was bound to, which is the same thing *using* the token needs. A client that genuinely lost its key has a dead session anyway and its user revokes from their own Fauna app. `ath` is refused, not required: this is an authorization-server endpoint and the token travels as a form parameter, not as this request's credential.
  - **`revocation_endpoint_auth_methods_supported` must be rendered, not omitted.** RFC 8414 §2 defaults the member to `client_secret_basic` — a credential class this AS does not implement — so silence advertises a method every request using it would be refused for. It mirrors `token_endpoint_auth_methods_supported` because revocation holds a client to the same identity requirement the token endpoint does.
- **⚠ The grant registry does NOT qualify as access-token revocation, and the 15-minute cap stays (decided 2026-08-01, F4 slice 8a — closing the question § Ecosystem reality item 2 left to build time).** That item sets the bar precisely: the registry qualifies only if *the D8 authz slot consults the grant row on every call, killing access at the resource server regardless of token lifetime*. Both ways to reach it are refused deliberately. **(1) A nest round-trip inside `AuthzHook`** would tax every authenticated XRPC call with an extra RPC *so that tokens may live fifteen minutes longer* — more traffic than the widening saves, and it makes D8's pure decision function I/O-bearing, with a new "nest unreachable" arm on the one path whose job is deciding who is calling. **(2) A nudge-fed bridge-side revocation cache** carries exactly the hole the kill-switch `flagCache` documents on itself — after a bridge restart a stale token passes again until it expires — which is not "regardless of token lifetime" and would be a guarantee the design does not keep. So revocation is authoritative at the family, nest-side, and an outstanding access token dies inside ≤15 min. **Widening to <30 min remains additive and still must not precede the per-call consultation**; a future slice that wants it builds that first, and re-decides this bullet in the same change. **The nest's own principal session is not this question (ruled 2026-10-02):** there the gate consults the canonical rows on every RPC by construction, at neither cost above, so a family's ending closes the sessions its tokens opened — [`../architecture/transport-connection.md`](../architecture/transport-connection.md) § Connection lifecycle → *The principal session* → *Revocation — three doors*, door (c), owns it. That widens nothing here: the cap is set by the plane that cannot consult, and the PDS resource server still cannot.
- **AS-key rotation — ratified 2026-08-01 (F4 slice 7's deadline).** The bridge's ES256 AS key is first-write-wins with no rotation path, which was correct while nothing verified it and stops being correct the moment tokens exist: an external verifier caches our JWKS, so re-minting orphans every cached copy. Four rulings, of which the first two are BUILT because they ossify at first token and the rest are additive.
  - **Every token carries `kid`, and verification is a key-SET lookup** (`asKeyForKID`), from the first token ever minted. A verifier that has always been handed a `kid` can be pointed at a set the day rotation lands; one that learned to expect a single implicit key cannot be, and every token in flight would have to break to teach it. Today the set holds one key, and an unknown `kid` resolves to **no key** rather than falling back to the current one.
  - **Rotation ADDS a key; it never replaces one in place** — the insert-only `put_atproto_as_key_blob_if_absent` is untouched and stays the provisioning path. **The outgoing generation rides BESIDE the current one, never inside its bundle** (mechanism corrected 2026-08-02, slice 8c — the ratifying sketch had it as an additive `AtprotoAsKeyBundle` CBOR field, which is unbuildable: nest holds only the HPKE ciphertext sealed to the bridge's attested x25519 and forgot the plaintext at mint, so it cannot re-seal a generation it cannot read; § Key material inventory's custody is the constraint that wins). Concretely: `atproto_as_key_blobs` keeps both sealed blobs — the rotation write path moves `blob` → `previous_blob` + stamps `previous_rotated_at` (unix seconds, the FACT) in one statement, exactly two generations by construction — and the `fetch_as_key_blob` reply serves the pair additively (`previous_blob`/`previous_rotated_at` absent = never rotated, so every pre-rotation nest and bridge stays wire-compatible). Each generation stays in today's per-generation sealed format; the bundle's additive-field seam remains free for genuinely in-bundle futures (an explicit `alg`). The JWKS renders the set (its document type is already a list), old key retired after the access-token horizon — the horizon is DERIVED BRIDGE-side (`previous_rotated_at` + access-token lifetime + a pickup grace, lazily against the injected clock, no timers) because the lifetime constant lives bridge-side and nest must not duplicate it. Pickup is the house nudge+fallback: an `as_key_rotated` push, a reconnect refetch, and a slow ticker backstop.
  - **No scheduled rotation.** ES256 keys do not wear out, and every rotation risks JWKS-cache skew at exactly the clients we least want to break. Rotation is a deliberate **compromise response**, so it is an admin action with a UI in the apps (the config-surface invariant — never a config file or a flag), landing with the connected-apps surface. **The control shipped 2026-08-02 (slice 8d) on the `admin-bridges-pending` approved-bridge card, not on the user-facing `atproto` page** — four user-approved IDs (`bluesky-as-key-status`, `bluesky-as-key-rotate`, `bluesky-as-key-rotate-confirm`, `bluesky-as-key-rotate-cancel`), rendered on the `atproto.pds` row only. The placement is forced by reachability: the `atproto` page's full-PDS panel renders only at the *signed-in admin's own* `integration_level = hosted_full`, so putting a deployment-wide compromise response there would hide it from an admin who never enabled Bluesky for themselves, while the bridge card exists exactly when the key can. Interaction detail (the disabled-when-unprovisioned rule, the inline confirm) is owned by [`admin.md`](admin.md) § Approved-bridges roster. Its read half is the Admin-class `get_as_key_status` (§ WS-RPC kind surface), which reports `provisioned` + `previous_rotated_at` and deliberately **no `kid`** — nest forgot the plaintext at mint and cannot derive a thumbprint for a key it cannot read, the same custody constraint that put the outgoing generation beside the current one rather than inside its bundle.
  - **The refresh-token signer is the interlock** (the two-signers ruling above): because only ≤15-minute access tokens are ES256-signed, an outgoing key is retired minutes after a rotation rather than after the refresh lifetime. Any future change that signs a long-lived artifact with the AS key re-opens this and must re-decide it. **This interlock bounds honest tokens only** — it is the availability argument, and it says nothing about a token a thief mints under a leaked scalar; the compromise window is the retirement horizon itself, and the nest-hosted issuer answers it with a second, forced arm (§ The issuer → *Two rotation arms*).

## Architectural rules

1. **One issuer per nest, on the nest domain, always on.** A bridge may be a *resource server* against it; no bridge is ever an issuer.
2. **Every refusal returns before anything is stored; every nonce-requiring plane issues one on every response; every shared replay set is re-decided per caller** — the three posture rules of § As built bind the nest-hosted issuer verbatim.
3. **The consent card is one card.** A new start adds a start row to § Consent; it never adds a second card, a second binding-code origin, or a second read-back path.
4. **A scope that names sealed data has a grant twin, stated in words on the card.** A card that promises reach a token cannot deliver — or delivers keys the card did not name — is the lie the scope predicate exists to prevent.
5. **Push is quiet until first approval.** Rules (a)–(c) of § Consent are the boundary; a "richer" push that notifies an unapproved client re-opens the phishing surface the binding code closed.
6. **The issuer plane is open to every origin and credential-less** (§ The issuer → *Cross-origin access*). A browser client's origin is a fact its metadata document carries, never one an admin registers; a surface that needs the nest's app-origin allowlist is not an issuer surface.

## Don't do these

- **Don't mount the issuer on a bridge host or seal its key to a bridge** once TP5 lands; the built shape is the record, not the template.
- **Don't add a second issuer for any consumer** (mail, sign-in, plugins). The typed-code start is the device grant.
- **Don't advertise a scope the matrix grants nothing under**, in any family.
- **Don't widen the 15-minute access cap ahead of a per-call consultation** (§ As built → the ⚠ revocation ruling).
- **Don't let a push start notify a never-approved client**, and don't drop the per-client block.
- **Don't mount an issuer surface under the nest's credentialed CORS allowlist, and don't add an origin knob for third-party clients** — an issuer route joins the issuer router (§ The issuer → *Cross-origin access*); a browser client shut out by the allowlist is a bug there, never a setting to add.
