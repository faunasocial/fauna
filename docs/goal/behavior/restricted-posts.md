## Encryption at rest

`docs/goal/architecture/encryption-at-rest.md` owns the at-rest *property* (the plaintext routing floor, the readable-classes ceiling, cross-flow, the trust property under compromise); this section owns the posts-specific mechanics. On conflict in that doc's domain, that doc wins. Posts do not introduce a new sealing primitive — a restricted post is *born* with its body sealed, using the protocol's existing gated-content machinery (`Post.gated: Option<GatedInfo>`, `KeyAccess`, `KeyBlob` in `libs/fauna-core::subscription`; `derive_post_key` / `encrypt_content` in `libs/fauna-core::subscription::crypto`).

**Three audience classes.** A post's audience is one of three; the class is surfaced as a plaintext attribute on the stored post (the nest reads it for fan-out routing and read ACL):

| Class | Protocol shape | What's sealed at rest |
|---|---|---|
| **Public** | `gated: None`; `body` *is* the content. | Nothing — the signed `Post` is plaintext, byte-identical everywhere. |
| **Audience-restricted** (subscriber tiers; the always-present default tier is the user's *followers*) | `gated: Some(GatedInfo { encrypted_ref, key_access: Broadcast { key_blob_ref }, tier, tier_rank, seal_id })`; `body` is a public preview/teaser; the full `PostBody` (canonical dag-cbor, `canonical_encode`) is in the `encrypted_ref` blob, sealed via `encrypt_content(derive_post_key(period_key, seal_id), …)`. **`seal_id` (ratified 2026-07-12 with the web-paywall render path; a required field since 2026-09-30)** is a creator-minted random 32-byte per-post derive input carried on the record: the record's own CID cannot be the derive input (the record contains `encrypted_ref`, whose ciphertext depends on the derived key — circular at creation), and a plaintext-body hash would be a content-confirmation oracle; `None` decodes only pre-field records (no authoring flow shipped before the field — readers treat `None` as undecryptable). The `KeyBlob` at `key_blob_ref` carries that period key individually X25519-wrapped to each *current* subscriber's pubkey (`create_key_blob_entry`); the period key rotates on a membership change; older periods stay readable from the author's client's retained `prior` period history (the account-state plane kind `fauna.state.subscriptions` — [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The kinds*; [`../behavior/monetization.md`](../behavior/monetization.md) § Pillar 1, *client-minted period-key custody*): a retained subscriber keeps the keys it held, and a later subscriber's back-catalogue wrap is minted from that history by the author's client — the nest serves no archival key material (its HTTP route and the `archival_blob.get` kind are retired, room ruling 8 below). | The `encrypted_ref` blob + the `KeyBlob` (opaque to anyone without a subscriber keypair — each entry is wrapped to a distinct pubkey). The `Post` envelope and the preview `body` are plaintext. |
| **Room-restricted** (the row formerly named *Group-restricted*; re-ruled 2026-09-10 under the room model — the paragraph *Room-restricted — the ruling* below) | `gated: Some(GatedInfo { encrypted_ref, key_access: Mls { group_id, epoch, generation? }, tier: "room", tier_rank: 0, seal_id, … })` — the wire tag stays `Mls`; the arm names a **room** by its channel id (`group_id`), and the base key is the room's class's own: an **end-to-end** room's MLS epoch secret at `epoch` (the arm as first designed), or — with the additive `generation` field naming a room generation id — a **community** room's generation key, domain-separated for posts (`group_content_key(gen_key, ROOM_POST_CONTENT_KIND)`). The full `PostBody` is in `encrypted_ref` sealed via `encrypt_content(derive_post_key(base, seal_id), …)` (same `seal_id` convention as the audience-restricted row); readers are the room's floor members holding that epoch / generation ([`../behavior/conversation-rooms.md`](../behavior/conversation-rooms.md) § The three classes). | The `encrypted_ref` blob; the `Post` envelope is plaintext — including the room's channel id. |

**Room-restricted — the ruling (2026-09-10, the room-model design pass; refutable until the first build).** Under the room model a *group* is a **room** ([`../behavior/conversation-rooms.md`](../behavior/conversation-rooms.md) § The three classes), so the class this row names is *a post whose readers are a room's floor members*, in either of the room's two member-keyed classes: an **end-to-end** room's MLS epoch secret (the arm as first designed) or a **community** room's generation key. Eight rulings, each owned here unless pointed elsewhere:

1. **A room-addressed post is an ordinary post of its author** — author's `__post` plane, follower fan-out, profile and feed — never a room message: it never enters the room's log, never rides `channel.send`, and no post travels to the room's home nest for any purpose (bulk bytes never ride federation — `conversation-rooms.md` § The home nest). A member who does not follow the author does not receive it; whether a room *surfaces* its posts is a client-plane question the room family's trickle-down answers, not this ruling.
2. **The wire grows by an additive field, never a new `KeyAccess` variant.** `KeyAccess` is an externally tagged enum with no `Unknown` fallthrough ([`../architecture/transport.md`](../architecture/transport.md) § Schema and forward-compat discipline, rule 3 — unmet here) sitting inside `Post.gated`, and the envelope reaches every follower's app whatever its version — so a new variant would fail whole-`Post` decode on every shipped app, a break within the major ([`../architecture/version-compatibility.md`](../architecture/version-compatibility.md)). The `Mls` arm grows `generation: Option<[u8; 32]>` (`#[serde(default, skip_serializing_if)]`): `group_id` carries the room's channel id, `generation` a community room's generation id, absent for an end-to-end room. An older app decodes the arm it already could not open and renders its ordinary gated card. The wire tag `Mls` is frozen; the Rust variant may be renamed to say *room*. The rule-3 `Unknown` arm is added in the same build for future arms — it cannot protect apps already shipped, which is exactly why this feature does not depend on it.
3. **`tier` is the hard-coded constant `room`, `tier_rank` 0** — never a tier the author owns. `content_meta.gated_tier` is then non-NULL, which keeps the post out of the public and trending feeds and off-box publish with no new code; an older app's card names a tier it cannot subscribe to — the honest degrade.
4. **The seal is the Posts row's own** (`conversation-rooms.md` § The group plane's fate): per-post key `derive_post_key(base, seal_id)` + `encrypt_content`, with `base` = the MLS epoch secret (end-to-end) or `group_content_key(gen_key, ROOM_POST_CONTENT_KIND)` (community — a post kind constant beside the message kind in `libs/fauna-core::group_content`, so a room's posts and messages never share a key). Attachments seal as `RestrictedPostAudience::Group` with that base → `AudienceClass::GroupRestrictedPost`; no new sidecar class; `attachment_refs` pin as today.
5. **Every floor member may post; nobody is gated by the nest.** Send is every role (`conversation-rooms.md` § Roles and authorization); the author's nest may not home the room, and the key is the gate — as for every gated post, the envelope is served to every follower and only a holder opens the body. No new read ACL. **The residue this leaves, ruled accepted 2026-09-13:** *the key is the gate* cuts both ways, so **a removed member of an end-to-end room can still author a room-addressed post its remaining members open** — from a device that has not yet processed the commit removing it, which seals with the exporter secret of the group it still holds, at the epoch it was removed at; or from a modified client replaying the per-epoch secret every member's device keeps (*Built* detail (i)). The remaining members open it because they keep that epoch's secret too, for as long as they keep the group, and the open path has no freshness check — so the residue is **not** bounded by the group's next commit, only by the ex-member's device holding the old epoch. It is stated rather than closed because nothing can close it on this ruling's terms: a device that never saw its removal has no signal to act on, a modified client honours no client-side check, and a nest-side gate is exactly what this ruling refuses. What bounds it is ruling 1 — the post is an ordinary post of its real author, to the author's own followers, never the room's log, signed and painted as that author — and the app half does what composer honesty can (*The rooms offered*: a device that **has** processed its removal is not offered the room, and could not seal for it anyway — its exporter refuses an evicted group).
6. **History and rotation fall out of the scheme:** a post sealed under generation G opens for whoever holds G's wrap; a newcomer under `history_policy: none` cannot read pre-tip posts; a rotated-out member keeps what it held — **amended 2026-09-13 by class.** For the **end-to-end** class "keeps what it held" is exact and unbounded: the per-epoch secret (*Built* detail (i)) rests on every member's device, the removed one included, and nothing ever clears it. For the **community** class it holds only **for the rest of the session**: a room's generation keys are an in-memory cache, and the re-read a relaunch needs (`room_generation_key`'s miss path) is refused to a removed member by the room's home nest (*not a member of this room*) — so a removed community member loses the read at its next launch. Stronger than the sentence promised, in the safe direction, and not a guarantee either way: the retention is the cache's, not a policy.
7. **The reception-time pass, room arm** (`community-rooms.md` § The three classes → *What the home nest does with its read*, purpose 3, owns *what for*; this item owns *how*): the room's home nest opens a room-addressed post **it stores** — the author or a follower homed there — under the tip's wrap in the act that ingests it, indexes the body into the room's per-room FTS class keyed by post id, serves hits through `fauna.conversations.room.search` with an additive kind discriminator — positions/ids and ranks, never text — and purges them with the room's other views on rotate-out. Labels ride the community-room label mechanism. A post a moderation flag withholds yields no hit and no verdict while the flag stands (the views stay for the overturn) — owner [`../behavior/moderation.md`](../behavior/moderation.md) § Legal takedown → *The blob-serve door* → *What the withhold binds on owner- and admin-scoped routes*, path 4. The general subscriber-tier reception pass (the *Reception-time processing* paragraph below) stays target state and is not this arm.
8. **Nothing is retired** — *as ruled 2026-09-10; LIFTED 2026-09-27 by the compat-remnant sweep.* The ruling kept `tier_mls_groups`, the `mls_in_encrypted_mode` refusal and the arm's never-authored subscriber-tier reading under I1's never-dropped rule; the sweep's universal scope ([`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 2, the fourth ratified exception) overrides it for a pre-sweep at-rest remnant, and this plane is one: its nest-side path left with the nest-held period-key plane, no writer creates an MLS-backed tier, and no shipped app ever authored the arm's subscriber-tier reading — nothing predating the sweep exists to serve, and no use the room reading does not cover is known. **Retired end to end:** the `epoch_secret.get` / `archival_blob.get` kinds on every surface (nest, kind catalog, offline class, bridge allowlist, `fauna-client-subscriptions`, FFI, Go binding), the refusal, and the nest's caller-less tier-MLS accessors. **The `Mls` arm has exactly one reading, the room reading (rulings 2–4).** The four writer-less tables (`period_keys`, `tier_mls_groups`, `tier_epoch_secrets`, `tier_transitions`) and `actor_successions.period_keys_rotated_at` — all empty on every nest — left the schema the same day through schema 91's one-shot retire step, under the user's deletion approval.

**Built 2026-09-10 — the ruling survives its first build, and the refutable window closes here.** All eight rulings held as written. The build settled four details they left open, each owned here: **(i) the end-to-end base** is the MLS exporter secret under its own label `fauna.room.post.v1` — never the blob, chunk or subscription export of the same epoch — and every member's device keeps each epoch's secret just before any merge that advances its group, its own commit or a peer's, so history survives a membership change the way ruling 6 says (a member keeps what it held; a member who joined later never held the earlier epoch; the web app keeps no per-epoch secrets, the limit the blob key already carries there). **(ii) The reception pass indexes into the room's per-room *post* class**, a sibling of its message class, so a search that asks for messages only returns exactly the page it always did. **(iii) Post hits on `fauna.conversations.room.search` are opt-in** (`include_posts`): a post hit carries `kind: post` and the post id and no `seq`, and an app built before post hits requires a `seq` on every hit — so it is never sent one. **(iv) `room` is a reserved tier name** — `tiers.create` refuses it — so ruling 3's "never a tier the author owns" is enforced rather than assumed. The wire pin is a decode test against the shipped derived shape of `KeyAccess`; no CDDL schema names that type. **(v) Labels, later the same day — where ruling 7's "ride the mechanism" needed one decision of its own: the serving surface.** The pass runs the room's named labelers after the index, the same set and the same shared scorers as the message pass (`conversations_handlers::run_room_labelers`, one home), and the rows land under a `room_post` kind keyed `(room, post)` — kept out of the List plane's withdrawals, the owner-scoped re-score worklists and `fauna.moderation.stats` exactly as the `room_message` kind is, and purged with the room's views on revoke and with the post on delete. A message's verdicts ride `channel.fetch` beside the envelope; a post's cannot ride any envelope read, because a room post is its author's ordinary post and reaches every follower — through `fauna.posts.get`, the feed pages and the deep-link door — with none of those reads floor-gated, the bytes being sealed, while a verdict was derived from the plaintext. So the verdicts take a **post-scoped, floor-gated read of their own, `fauna.posts.room_labels`** (a batch of post ids; the nest finds each post's room from its own reception-pass map and answers for a post only where the caller is a live member of that floor — `is_live_floor_member`, the `channel.fetch` gate, one home so the two reads can never drift), and no envelope read carries one, on any door, to anyone. The shared feed manager asks it in the act that unseals a room post and merges the answer into the card's own labels by the message rule (`merge_server_labels`), so the badge every app already paints shows them with no app change — once an app can open a room post at all, which is the seam remainder below. **That read relays, added 2026-09-11 — the one detail (v) got wrong on the day, and the last community-room read without a twin.** A door that resolves a post's room from *the serving nest's own* reception-pass map can only ever be answered by the nest that wrote it, and `room_post_view::index_room_post` runs on the nest that **stores** the post and homes the room — so a member homed elsewhere was answered empty, which this door deliberately makes indistinguishable from “nobody labelled it”, and its card lost the badge with nothing said. It now takes the distinct client kind `fauna.posts.room_labels_remote { room_id, post_ids, nest_url }` to the home's `fauna.federation.conversation.room_labels.fetch`, exactly as the room's three other reads do ([`../architecture/federation.md`](../architecture/federation.md) § Federation residue surface owns the twin, its gate — the foreign-member binding **and** the floor — and why the request names the room where the same-nest one does not). The kind pick is the shared manager's, from the room's recorded home over the `RoomPostKeys::room_home_nest_url` seam, so “with no app change” holds for a foreign member too. Pinned in `bins/fauna-nest/tests/conformance_conversation_rooms.rs` (the room-restricted post label cases: a member's read carries both planes with no plaintext in its bytes; a follower off the floor reads the post and none of its verdicts, a removed member likewise; the revoke and the delete leave the count at zero), `bins/fauna-nest/tests/conformance_cross_nest_conversations_client.rs` (`a_foreign_members_room_post_verdicts_ride_their_own_relay` — the relayed read carries both planes for a seated foreign member and nothing for a bound one with no seat, and the relaying nest keeps no room record, no map row and no verdict row) and `libs/fauna-feed` (`a_room_posts_served_verdicts_merge_into_the_cards_own_labels`, `a_foreign_homed_rooms_verdict_read_goes_to_the_rooms_home`).

**Room-restricted — the app half (2026-09-10; tui first).** Owned here, each detail one the rulings left to the build:

- **The seam is the conversations session.** `ConversationsSession` implements `RoomPostKeys` — its key answers are the MLS backend's own, both directions, and `room_post_rooms` reads the conversations manager — because it is the one place that meets both owners a room post needs. The app installs it with `FeedManager::set_room_post_keys` where the two sessions meet; without it every room post stays locked and no room is offered, the honest state for a device with no conversations plane. The answers live on `fauna_conversations::RoomPostSeam` (over the manager and its FaunaMls backend), which the session's impl delegates to — so web, which has no session, installs the same seam built from its conversations manager (`WasmFeedManager.setRoomPostKeys`).
- **The rooms offered** (`FeedSnapshot::own_rooms`): every group thread bound to a channel whose room the rail's own `room_state` calls end-to-end or community — a 1:1 is not a group (`../behavior/conversation-rooms.md` § The room) and a transport-only room has no member key — labelled as the user's conversation list reads it, **and on which this device still holds a seat as far as the rail can tell (2026-09-13)**: an end-to-end room whose group this device has processed its own removal from is not offered (`RailBackend::seated_on_room`, the FaunaMls rail's answer being `MlsEngine::is_group_active`) — the seal would be refused at send, so the option was dead; a community room is offered while its class says so, whether this device holds the tip's wrap being decided at the seal against the nest's answer, never guessed from a cache. This is composer honesty, not a gate: it reaches no device that never saw its removal (ruling 5's residue, stated there). The list is a projection of the conversations plane, so it is re-read by `refresh_feeds` and on that plane's own change tick; the manager notifies only when it changed.
- **The composer's fourth answer.** `compose-gate-tier-select` gains one option per room, "Room: ‹label›" (no new element id), mutually exclusive with a tier and a sale (§ State & data shape); the teaser is staged alone (`update_compose_preview`), so writing it never flips the answer.
- **One post, one key.** `prepare_gated_blob`'s room arm asks the seam for the room's key *now* (`room_post_seal_key`) and builds through `build_room_post_at`. A photo sealed first stashes its seal id **and** the seal its base was resolved under, and the body re-derives that same base (`room_post_base_key`) rather than asking "now" a second time — so an epoch advance or a rotation between the two calls cannot split one post's keys. A photo sealed for another audience is refused as stale, as the tier arm refuses one.
- **The body blob declares `GroupRestrictedPost`** — ruling 4's class for the post's photos, applied to its body so one post names one audience, and no new class. The staged post names it (`FeedManager::gated_upload_sidecar`) and `fauna_client::upload_sealed_post_blob` carries it; an app that uploads through its own HTTP code takes the same sidecar as encoded bytes from the FFI/wasm face (`gated_upload_sidecar`), for a tier's, a sale's and a room's body alike; no app picks a class.
- **The room answer rests in the posts-rail draft** (§ Persistence).
- **The card — BUILT 2026-09-13 on tui, linux and web; the other four take it with their room legs.** A room post's card names the room — its label as the reader's own conversation list reads it, in the composer's own "Room: ‹label›" string — rather than the reserved tier, and offers a member "open" where a tier's card offers subscribing; a reader not in the room sees the reserved tier `room`. Three details the build settled, owned here. **(a) Where the card learns the room:** the nest projects the arm's channel id into the feed index beside the tier — `content_meta.gated_room` → `FeedPostItem.gated_room`, additive at rest and on the wire, the same plaintext floor as `gated_tier` (*Plaintext floor for a stored post* below) read through the shared `room_post_of` — so the list knows every room post's room on arrival, with no per-post decode and no per-app resolve trigger; the deep-link door derives the same field from its own decode. A post indexed before the column, or served by an older nest, carries none and keeps the reserved-tier badge: ruling 3's degrade is now the fallback, not the rule. **(b) The member test and the label are the reader's own:** `FeedManager::snapshot` derives `PostSummary::room_label` on every read from `own_rooms` (*The rooms offered* above) — `Some(label)` exactly when the post's room is one this device still holds a seat on — never stored and never taken from anything the author sent, so a lost seat drops the card back to the tier on the next read, with no second bookkeeping path. **(c) "Open" is the card's own detail-open.** No new element id: a member's "open" is the unchanged detail-open unseal — the act "subscribing" buys a tier reader — and the badge text is the only thing that differs: `gated-post-badge` reads the room label for a member and the tier for everyone else (ui.yaml's element note says so). A reader off the floor who still holds the epoch (ruling 5's residue) sees the tier badge and still opens — honest both ways: the badge speaks for the seat, the key for the open.
- **Room search reaches no app yet.** The nest answers post hits (detail (iii)), but no app has a room-search surface: [`../ui/conversations.md`](../ui/conversations.md) § Where logic lives keeps its list filter local and names a nest-backed body search as a separate feature not yet specified — so the app half has nothing to render post hits in until one is.

**A reply, quote or repost of a restricted post — the ruling (2026-09-19; ruling 5's sealed arm built 2026-09-19, its public-by-confirmation arm built 2026-09-25 — the ruling survives both builds as written).** A reply, a quote and a repost are each *an ordinary post of the person who makes them* (§ Interaction bar), fanned out to **their** followers — so when the target is audience-restricted or room-restricted, the act crosses from the target's readers to the replier's. Until this ruling nothing said what audience that post gets, and the composer built it public: a member answering in a room's context published their words to every follower, with nothing said. Six rulings, owned here:

1. **What is protected is the user's words.** A restricted target's id, author, class, room channel id and teaser are already on the plaintext floor (below), served to every follower of its author; naming them again discloses nothing. The words a user types in that post's context are what no build may publish wider than the user was told.
2. **Never silently public.** No referencing post whose body carries words is composed public under a restricted target unless the user was told, in the act, that it is public. This binds every composer of a reference: reply, a quote with commentary (the deferred commentary composer of § Interaction bar inherits it the day it lands), and any later verb.
3. **A wordless reference stays public.** A repost, and today's commentary-less quote, carry an empty body: they publish nothing of the user's and render as the target's own gated card, teaser and badge. The 2026-03-15 paywalled-content design (§ 8.4, *Reposts* — "reposting a gated post shares the preview") is **kept**, and extends to a room post unchanged. Whitespace is not words.
4. **That design's *Threads and replies* is kept as a limit and overruled as a default.** Its position — replies quoting decrypted material "are public — this is an inherent limitation, identical to screenshotting. The protocol does not attempt to prevent this" — stands as to what the protocol can *prevent*: a reader can always publish what they read, and nothing here pretends otherwise. It is overruled as the behaviour of the reply button: a limit on what can be stopped is not a licence for the app to do it on the user's behalf, unasked. Its "anyone can reply to a gated post's preview" returns with ruling 5's confirmation, not before.
5. **Target state — the reply carries the target's arm where the replier can author under it, and is public only by an explicit answer.** A reply to or quote of a room post, by a member whose device still holds a seat on that room (the *rooms offered* test above), seals to the same room through the shared room arm; a reply to a tier post by that tier's owner seals to the same tier. Anyone else — a tier's subscriber, a reader off the room's floor — cannot author under the arm: a subscriber holds a period key, but a post of theirs gated to *another author's* tier is no shape the protocol has. Their only path is public, behind a per-reply confirmation that names the audience change. How `feed-reply-dialog` states the audience is an element-scope question ui.yaml owns: `feed-reply-audience` (the manager's answer, painted) and `feed-reply-public-confirm` (the explicit answer, unchecked at every open), approved 2026-09-25.
6. **Until ruling 5 is built, words under a restricted post are refused, with the reason** (§ Implementation status today). The accepted cost is that a reader outside the audience cannot reply to a teaser in the meantime. The rule has one home in shared Rust: `build_referencing_post` takes the target's audience as an argument (`ReferencedAudience`) — never a default, so no composer can reference a post without saying what it references — and refuses words under a restricted one with the stable `REFERENCE_REFUSED_RESTRICTED`, before anything is created. The shared manager states the class from the row's own `gated_tier` / `gated_room` (either alone marks it restricted); a target the loaded window cannot answer for composes nothing at all (the interact fallback of § Layout & flow), the safe direction. An app paints the refusal as `feed.reference_restricted`, recognized through the shared `fauna_feed::refusal_i18n_key`. **The refusal does not retire when ruling 5 is built** — it stays the answer to words nobody confirmed, so the constant and its string outlive the interim.

**Ruling 5's build — the shape (design pass 2026-09-19; (a)–(d) — the sealed arm — BUILT 2026-09-19 in shared Rust and on tui; (e) — the confirmation — BUILT 2026-09-25 in shared Rust and on tui; none of it refutable any longer).** Five details ruling 5 left open, owned here:

- **(a) The sealed reply's public `body` is empty.** A sealed post's envelope carries a plaintext preview, and a reply has nothing to announce: any text there would be the replier's words in the clear (ruling 1), and a fixed sentence would be a language baked into signed bytes. Empty is what a repost already carries. The card needs nothing more — the badge names the audience and the envelope's `references` name what it answers. The composer's *a gated post needs a teaser* rule is the composer's own (it lives in the prepare step, never in the builders or on the nest) and is untouched: a top-level post announces itself, a reply does not.
- **(b) The reference rides the plaintext envelope, beside the sealed body.** `references` is already on the plaintext floor (below), so a sealed reply discloses what it answers and nothing of what it says. The shared sealer under `build_gated_post_at` / `build_room_post_at` takes the envelope's `references` (empty for every composer post, as today); `build_referencing_post` stays the **public** builder and never learns to seal — its audience argument grows one value, *restricted, public confirmed*, the only way words pass it under a restricted target.
- **(c) The upload leg is the composer's own, reused — not a manager-owned upload.** Every app already uploads a staged sealed body through its own HTTP shell (`gated_upload_sidecar` → upload → `submit_gated_post`); blob transport is per-app across the whole product, and moving it into the manager is a product-wide change this ruling does not make. So the sealed reply mirrors the composer's fall-through exactly: a new prepare verb on the shared manager answers the sealed body when the target is restricted **and** this device can author under its arm (staging the post in the same single slot, marked as a reference so the submit refreshes the target's counters instead of reloading the feed and clears no composer), and answers *nothing to upload* otherwise — the app then calls `reply` / `quote` as today. An app leg is: prepare, and if it answers bytes, the upload it already has.
- **(d) Who can author under the arm is the manager's answer, derived at every snapshot read like `room_label`** — never an app's: a room post whose room is in `own_rooms` (the *rooms offered* test, seat included) → sealed to that room, keyed through the room-post seam *now*; a tier post whose author is this actor and whose tier is in `own_tiers` → sealed to that tier under the current period key; anything else restricted → public only by confirmation. The snapshot carries that three-way answer per post so the reply dialog states it without deciding it.
- **(e) The confirmation is an answer given in the reply dialog, per reply, never remembered.** The confirmed-public reply is its own manager verb (additive on the FFI and wasm faces — `reply`'s signature does not change, so an app built before it keeps refusing, the safe direction). What the dialog shows and the ids it shows them under are ui.yaml's, approved 2026-09-25: `feed-reply-audience` states the manager's per-post answer ((d)) in one of three sentences — sealed to the room by the reader's own label, sealed to the reader's own tier, or *a reply from you would be public* — and `feed-reply-public-confirm`, present only where the answer is *public by confirmation* and unchecked at every open, is the explicit answer; the submit sends `reply_public_confirmed` only while it is checked and the ordinary `reply` otherwise, which meets ruling 6's refusal. The verb's gate is the manager's own, on the same `reply_audience` the dialog painted: a target this device could seal is refused (`REPLY_SEALS_INSTEAD`) rather than sent past an arm no dialog offered to bypass, and a public target composes as `reply` would — so words leave the device public under a restricted target only where the reader was told, in the act, that they would. A quote with commentary inherits the same door the day its composer lands (ruling 2).

**Plaintext floor for a stored post (every nest).** The `Post` envelope minus the gated body: post ID (BLAKE3 routing pointer), author actor ID, `created_at`, audience class (public / audience-restricted / room-restricted — the last in the clear down to the room's channel id, `KeyAccess::Mls.group_id`), `references`, `content_warning`, `expires_at`; for restricted posts also the public preview `body`, the existence of a `key_blob_ref` pointer, and — **ratified 2026-09-08** — `GatedInfo.attachment_refs`, the content addresses of the media sealed alongside the body under the same per-post key (the ruling and its bound: [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Plaintext floor → Posts row; the consumer: [`../behavior/backup-restore.md`](../behavior/backup-restore.md) § 9 step 2). Nothing else joins the floor.

**A restricted post never has a plaintext-full-body wire form, on any nest.** The protocol federates the `Post` envelope + the `encrypted_ref` ciphertext blob (+ the `KeyBlob` for broadcast tiers). Sealing happens at publish time on the **author's client**; unsealing at render time on the **reader's client** (group epoch secret for `Mls`; `decrypt_key_blob_entry` with the reader's own keypair, then `derive_post_key`, for `Broadcast`). So a nest — author's *or* recipient's — stores the `Post` envelope + `encrypted_ref` blob + `KeyBlob` as ordinary bytes and holds no key that opens any of it — **with the one exception the room model makes by design:** a **community** room's home nest holds that room's generation wrap ([`community-rooms.md`](community-rooms.md) § The three classes → *What the home nest does with its read*) and so opens a room-addressed post **it stores**, for the purposes ruling 7 above names and no others; an audience-restricted post, and a post addressed to an **end-to-end** room, no nest can open. The federation/wire surface carries no mode signal.

Broadcast-`KeyBlob` *management* (minting `KeyBlobEntry`s for new subscribers, rotating the period key on a removal, minting per-subscriber archival key material) lives on the **author's client** for every tier — the nest holds no period key, and the author's client holds `ManageSubscribers` to itself per the `verify_key_blob_signature` delegation chain; client-minted tiers are the unconditional default (`behavior/monetization.md` § Pillar 1). (The nest-held period-key plane that served pre-Phase-4 tiers was removed by the compat-remnant sweep — `../architecture/version-compatibility.md` § Dimension 2, the fourth ratified exception.) Consequence: **new-subscriber backfill of historical restricted posts is best-effort** — posts under the current period key are readable immediately from the live `KeyBlob`; older periods only once the author's client is online to mint the archival material.

### Encryption at rest — broadcast tiers

Subscription management rides the `fauna.subscriptions.*` WS-RPC kinds
(`libs/fauna-protocol/src/subscriptions.rs`). Three kinds carry an
`encrypted_upload: { key_blob, signer_auth }` envelope for a client-minted
tier's roster mutations: `tiers.create` (never mints a period key or MLS
group, by design); `requests.approve` (author commits client-minted
KeyBlob); `subscribers.remove` (same) — both refuse a call without the
envelope (`missing_upload`). Two kinds always enqueue intents: `subscribe`
and `unsubscribe` write to the `subscribe_requests` table with
`kind='subscribe' | 'unsubscribe'`; the author's client picks them up via
`requests.list` and commits via the approve/remove kinds. The upload
rules — every door refuses a tier with no stored blob, save the
`followers` tier's blob-less first approval — are owned by
`behavior/monetization.md` § Pillar 1.

The author's client mints the KeyBlob via `mint_key_blob` in
`libs/fauna-core::subscription::crypto`. The nest verifies the four-step
auth chain (canonical-dag-cbor decode → signature self-verifies → bearer ∈
{author, signer.device_key} → key_blob.author == operation scope) and three
state checks (tier exists + matches; `rotated_at` strictly monotonic; entries
set matches post-mutation roster), then stores `blob_data` as canonical
dag-cbor bytes.

The subscriptions HTTP twins are **deleted** (the WS-RPC rip-out + the
2026-06-19 key-material follow-on); tier mutations ride the
`fauna.subscriptions.*` kinds only. The three surviving HTTP routes
(`list_tiers`, `nest_info`, `get_delegation`) are deliberate
public/federation-bootstrap residue, not deprecated twins. The remaining
per-app adoption TODOs are `TODO-{android,ios,macos}-subscriptions-ws-rpc-1.md`
(the linux/web/windows ones closed + archived). Client-minted
tiers are broadcast-only by construction (no MLS); the
`mls_in_encrypted_mode` refusal that once guarded a legacy MLS tier's
roster went with the tier-MLS plane (room ruling 8 above, lifted 2026-09-27).

**Reception-time processing (target; not built today — see Implementation status below).** The nest stores the `Post` envelope + `encrypted_ref` blob + `KeyBlob` as above. The **body byte-shape is uniform** — the `encrypted_ref` blob rests **sealed always** (retiring the earlier design-(a)/(b) "plaintext nest decrypt-and-*store* the body" target). Being a device of its users, a nest holding the relevant keys — for its own users' restricted posts, and for a received restricted post the user is entitled to (it holds `period_key`/`epoch_secret`) — *may* **transient-decrypt the full `PostBody` at reception** to run server-side FTS / classifiers over it just as it does over public ones, **keeping only the derived index + labels and discarding the plaintext body.** *What* gets indexed is owned by `docs/goal/behavior/content-index.md`; the at-rest property (sealed-always; reception-time / capability-driven processing, never plaintext-body-at-rest) is `docs/goal/architecture/encryption-at-rest.md` § purpose test + Posts row and the internally-tracked design (ratified 2026-07-04). **Implementation status:** this reception-time restricted-body index/score pass is **not built today** — the nest currently indexes only the public preview into `content_fts` (zero restricted-body decode call sites under `bins/fauna-nest/`); the sealed-at-rest posture already holds by construction (the nest never stored a decrypted body).

**Where the crypto lives.** All shared Rust, no per-app divergence: `libs/fauna-core::data` (`Post`, `PostBody`), `libs/fauna-core::subscription::{types,crypto}` (`GatedInfo`, `KeyAccess`, `KeyBlob`, `derive_post_key`, `encrypt_content`/`decrypt_content`, `create_key_blob_entry`/`decrypt_key_blob_entry`, `mint_key_blob` (the author-client KeyBlob mint — the only one: the nest mints no KeyBlob since the nest-held period-key plane was removed, 2026-09-27), `verify_key_blob_signature`), `libs/fauna-mls` (MLS group epoch secrets — the root key for `KeyAccess::Mls`). The future `libs/fauna-feed` crate owns the feed snapshot and rendering, not the crypto. Nest-side: byte storage handles the `Post` envelope + `encrypted_ref` blob + `KeyBlob` (the `content` table / blob store) — **sealed always**. The `Storage` trait has a single live implementation (`SealedStorage`; the retired `PlaintextStorage` impl is fully deleted, no mode-aware surface remains — `bins/fauna-nest/src/storage/sealed.rs`). The reception-time **transient-decrypt-at-reception → index/score** pass (target; not built today, above) would live in the post-ingest / index-registry path, **not** the `Storage` trait, and keeps only the derived artifacts (never a plaintext body at rest). The one trait-level post hook is the ingest-time seal-verification pass on `SealedStorage::ingest_post` (strict: Ed25519 signature against `post.author`, and — if gated — `encrypted_ref` non-zero + `key_access` consistency; rejection returns `Err(StorageUnavailable::ingest_rejected(IngestRejectReason::Post*))` → HTTP 400, and the verdict drives `nest_post_ingest_total{verdict ∈ accepted|rejected, reason}` per `docs/goal/architecture/encryption-at-rest.md` § Trust-the-uploader interim).
