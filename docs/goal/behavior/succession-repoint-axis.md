- **✅ Fixed (rust) — the rotation's owed-predicate now witnesses the KEY, not the publisher, 2026-09-22, the same day the leg below shipped.** The leg landed deriving owed-ness from `KeyBlob.author`; it was graded within hours and the hole demonstrated with a staged probe. `author` records who last **published** a blob, and `approve_subscriber` republishes the tier's *current* key under the caller's authorship — so one ordinary approve by the successor produced a blob stamped with their own id over the predecessor's key, and the leg read it as "already re-keyed" and skipped that tier for ever, on a pass whose outcome reported nothing owed and rendered no line. No user action was required to trigger it and no deferral window was needed: `drain_auto_approvals` approves every `auto_approve` and payment-entitled request on connect and every 30 s, unsequenced against the leg, so one arriving follower on the reserved `followers` tier could close the window inside the successor's first session. **The fix gives the key its own era stamp**: `TierPeriod.minted_by` (additive, `Option<ActorId>`, `None` on a pre-upgrade period and read as owed — the safe direction) is written from `UserConfig::actor_id` by whichever custody transition *minted* the key and never rewritten, because a republish is not a mint. The predicate is now purely local — the nest is asked only the *second* question, whether the rotation's upload ever landed, by comparing its stored blob's freshness against the local `current` after `minted_by` has settled whose key is live. **The rejected alternative is worth recording**: having the ceremony record the inherited period version per tier would also close it, and was refused because it reintroduces progress state at rest and a ceremony-session dependency — the exact property that makes this leg re-runnable on a device that never saw the ceremony. Two regression tests stage what the eight original ones could not: a **successor-authored, predecessor-keyed** blob, and the same-session approve race with no deferral at all.

The nest half is `encrypted_remove` minus the mutation: the same verify-and-precheck prelude (now extracted and shared by all three upload doors), a roster check demanding the set be *unchanged*, and — until the nest-held plane's 2026-09-27 removal — an `unexpected_upload` refusal against a nest-held tier so two custodians could never mint for one tier (with the plane gone the code no longer exists; like every upload door the rotate door now refuses a tier with no stored blob, `key_blob_not_found`). **What is owed is DERIVED, with no progress state at rest**, matching every sibling leg: `TierPeriod.minted_by` records the identity that minted the period key, so a tier is owed exactly when this identity did not mint the key it is currently sealing under. Deriving from a stamp rather than from a clock is what makes the leg re-runnable on **any** session: `SuccessionTime` reaches only the session that ran the ceremony, and a leg that must survive a crash cannot depend on a value the next sign-in does not have. ⚠ **The stamp has to witness the KEY, and the first shipped attempt witnessed the BLOB instead — a live vulnerability, not a nicety** (filed by the security charter against this very entry and fixed 2026-09-22, the same-day entry above): the predicate read `KeyBlob.author`, which records who last *published* a blob, while `approve_subscriber` republishes the tier's **current** key under the caller's authorship — so one ordinary (auto-)approve by the successor stamped the stored blob with their own id over the predecessor's key, and the leg read that as "already re-keyed" and never ran again, silently, on a pass reporting nothing owed. It needed no deferral window: the author pump drains auto-approvals on connect and every 30 s, unsequenced against this leg, so one arriving follower on the reserved `followers` tier could close it inside the successor's first session. Neither `KeyBlob.rotated_at` nor the stored blob version can serve either, for the same reason — an approve advances both without minting anything; the blob's freshness is legitimately read only for the *second* question (did my rotation's upload land?), after `minted_by` has settled whose key is live. **The ordering is commit-first, deliberately inverting the subscriber-removal path's** (`key-material-hierarchy.md`'s `pending_removals` sentinel): a removal keeps sealing under the old key until the nest confirms, so a stalled upload never publishes under a key nobody can unwrap — here the old key is the *compromised* one, so continuing to seal under it is the exposure itself. The fresh key therefore lands in `current` (the outgoing one retained in `prior`, so the back catalogue survives) **before** the upload, which is also the whole crash-safety story and why no sentinel was added: a crash in between leaves the successor sealing under a key subscribers cannot yet unwrap, the next pass sees a stored blob still naming the predecessor and re-uploads *the same* key, and the content sealed meanwhile becomes readable the moment it lands — a delivery gap that heals retroactively, where a confidentiality leak never would. **Gated on the nest advertising `subscription-period-rotate`**, so against a nest that does not advertise it the pass is a clean no-op that *says so* (the rendered line names the still-open exposure and the remedy) rather than rotating into a key it cannot publish — a data-safety brake the compat-remnant sweep KEEPS, not an older-peer arm: the leg persists the fresh key before the upload, so a half-run rotation strands every subscriber, and a bare unknown-kind error cannot tell a nest without the door from an outage ([`../architecture/compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md) § Program 2, re-ruled 2026-10-02). Witnessed by five nest tests on the door (roster preserved, a dropped member refused, a replay refused as `stale_rotation`, a nest-held tier refused — retired 2026-09-27 with that refusal, an empty roster accepted — the last is what lets a never-subscribed tier terminate) and eight client tests on the leg (the rotation itself, the planted stamp stopping a second pass, an interrupted upload republishing the *same* key rather than minting another, the no-op against a nest without the door, a transport fault counted as a failure rather than read as "nothing owed", and one failing tier not stranding its siblings).

> **The enumeration in [`succession-aftermath.md`](succession-aftermath.md) § Re-key scope is now DECLARED PER TABLE rather than re-typed per reader — ratified 2026-08-12, after the hand-maintained list drifted once with a security cost.** `account_aliases` was missing from `record_succession` for as long as the address existed, and the miss kept a thief's mail password authenticating through the ceremony meant to end the theft (the address paragraph in [`succession-aftermath.md`](succession-aftermath.md) § Re-key scope). The uncomfortable part is that nothing had to be *discovered*: `bins/fauna-nest/src/db/actor_tables.rs`'s module doc already said succession does not read the per-actor table registry — ~150 tables there against the ~16 re-pointed by hand — so the drift was written down and un-actioned until it cost a security property. **Three lists claimed to be the same set and none of them were equal:** the ceremony, the boot reconcile (`repoint_left_behind_corpus`), and the test fixture whose own doc comment says it asserts "the same table set" as this blockquote. So each registry entry now carries a **third axis** beside the deletion policy — **move** (ownership, routing and reach follow the account), **stay** (signed history and attribution, participation that moves by propagation instead, *and* key material deliberately left behind), **burn** (standing authority a seed thief could have minted, deleted so re-granting is bounded and visible) — and a data-driven test seeds every registry table, runs the real ceremony, and fails when the observable disagrees with the declaration in *either* direction. **Why the deletion axis could not simply be reused:** `Purge`/`Retain` answers whether rows may be dropped, which is independent of whether they follow the account — `folders` is purge-on-delete and moves, `actor_mls_pubkeys` is purge-on-delete and must emphatically not. **Why "left behind because compromised" is filed as *stay* and not *burn*:** the ceremony genuinely does different things — it deletes a capability grant, and it leaves the seal keys in place — and leaving them is load-bearing, being exactly what arms the `succession_pending` tempfail, so grouping them with the burns would invite a future session to "finish the job" and break it. **The backlog is stated, not hidden:** most tables are not yet ruled, they sit at the status quo (nothing moves), and the count is ratcheted down-only so a new per-actor table cannot join un-ruled. Deliberately *not* a bulk sweep of all ~150 — a wrong *move* is a security regression while a wrong *stay* is the status quo, so the remainder is worked outward from the mail and routing planes where the one demonstrated failure lived.
>
> **And as of 2026-08-12 the two paths are DRIVEN FROM that declaration rather than merely checked against it.** Every table declaring a *plain* move — the leg is exactly `UPDATE {table} SET {column} = ?new WHERE {column} = ?old` — executes from one shared loop over the registry in the ceremony. A table joins the re-point by declaring it and by nothing else, so the inventories that "claimed to be the same set" can no longer disagree: there is one set. Three tables declare `Bespoke` instead, each with its reason, because their leg does strictly more than move rows (`contacts` absorbs superseded third-party edges, `admin_actor_ids` is a delete-then-insert so the successor's grant date is its own, `nostr_bunker_apps` revokes as it moves); they stay hand-written and are still judged on their observable by the same gate, which asserts rows *landing on the successor* rather than the absence of an abort — the distinction that matters, since of the two mis-sorted tables found in the earlier pass one aborted loudly and the other stranded every row in total silence.
>
> ⚠ **A FOREIGN KEY can turn any correct leg into a total ceremony failure, and no per-table ruling can see it — ratified 2026-08-12 after it shipped.** The registry declares what *should* happen to each table's rows; a foreign key decides whether the transaction that does it commits at all. With `PRAGMA foreign_keys = ON`, updating a referenced column, or deleting a referenced row, **aborts the whole transaction** while any child still names the old value — so a table whose own ruling is perfectly correct can deny the ceremony to the user. That is strictly worse than either mis-ruling the axis contemplates: a wrong *stay* is the status quo and a wrong *move* is a security regression, but an abort means the user cannot rotate away from a compromised key at all. It shipped once, on an **audit** column bound to a **live authority** row (`bridge_service_users.approved_by_actor_id` → `admin_actor_ids`), locking every bridge-approving admin out of succession and out of de-admin alike.
>
> **The two lessons are separable, and both generalize past this instance.** *(1)* An audit or provenance column must not be a foreign key to a table whose rows are legitimately deleted — authority tables lose rows by design, and binding history to them makes ordinary administration fail. *(2)* Where a coupled family genuinely must move together, **sequencing the legs cannot fix it**: updating the parent orphans the children, updating the children first points them at a parent that does not exist yet, and the reconcile's `UPDATE OR IGNORE` does *not* swallow a foreign-key violation the way it swallows a uniqueness one. Such a family moves only under `PRAGMA defer_foreign_keys` inside the transaction, in **both** paths, or not at all. This is enforced rather than remembered — `no_foreign_key_crosses_a_succession_leg` walks the real schema's foreign keys against the registry and fails the commit that introduces a crossing, including the one that would rule the still-`Unruled` `subscription_tiers` family.

> **That remedy is BUILT as of 2026-08-13, and building it corrected the remedy's own statement in one important place.** A coupled family is now *declared* — `COUPLED_MOVE_FAMILIES` names the tables a foreign key binds together — and the ceremony moves a declared family as one unit under `PRAGMA defer_foreign_keys`, so a plane like the tier family becomes ordinary work rather than unrulable. Three properties are worth stating because each was measured rather than assumed. **(1) Deferral makes *order* irrelevant and *completeness* absolute.** The check moves from each statement to the `COMMIT`, so no sequencing of the legs is needed at all — but a family whose parent is ruled `Move` while a child is left `Unruled` still aborts, now at the commit and now for the whole ceremony. That is why the declaration is checked: every member must declare a plain move before any of them moves. **(2) The pragma is set and never cleared by hand — clearing it is the one edit that would silently void the mechanism.** `PRAGMA defer_foreign_keys = OFF` mid-transaction does not resume checking the outstanding violations, it **discards** them: a half-moved family then commits clean and leaves a permanent orphan only `PRAGMA foreign_key_check` can find. That is strictly worse than the abort this whole remedy exists to prevent — loud and costly becomes silent and permanent — so deferral ends only where SQLite ends it, at the transaction's `COMMIT` or `ROLLBACK`. The cost, stated: a foreign-key failure in a later leg of the same transaction surfaces at the commit rather than at its own statement, paid only on nests where a family is actually declared. **(3) `UPDATE OR IGNORE` is no answer for a family.** It swallows a uniqueness violation but not a foreign-key one, so skipping a colliding parent while its children moved would still orphan them at the commit; the ceremony needs no such verb, its successor owning nothing a move could land on.

> **`COUPLED_MOVE_FAMILIES` shipped empty, and stayed empty only until the first plane was ruled — the tier plane is now its first declared member (§ Implementation status today).** The mechanism was built before its first user because declaring a family and *ruling* one are different acts: the tier plane's ruling turns on questions this machinery does not settle (whether `subscribers.author_id`, the creator, and `subscribers.subscriber_id`, the paying reader — two different people in one row — want the same verdict, and whether the nest-minted period keys should *rotate* at the ceremony rather than merely move). Shipping both at once would have graded a mistake in either as a mistake in both. The executor is therefore proven against synthetic families shaped exactly like the tier one, and the standing test `ruling_a_coupled_plane_needs_its_family_declared` keeps both halves honest — ruling a plane with no family declared is caught by name, and declaring it is what clears it.
>
> **The collision axis deliberately does NOT live in the registry, and the reasoning generalizes.** It is tempting to let each table declare what happens when the target already holds an equivalent row. But the ceremony is collision-free by construction — `record_succession` refuses `NewAlreadyRegistered` — so such a verdict is unobservable, and a per-table verdict that is invisible when correct and silent when wrong is a foot-gun, not a record — which is precisely how the defect shipped. So the ceremony's statement is a bare `UPDATE`, and a collision it meets is a bug that aborts the ceremony rather than a case to resolve. (A boot reconcile that re-pointed rows left behind by successions recorded before the in-transaction re-point used to resolve collisions by parking; it was retired 2026-09-30, § Implementation status today.)
>
> ⚠ **What being *generated from* the declaration costs, stated because it is the one property this change took away.** While the legs were hand-written, a wrong declaration was caught by disagreement with the observable: the leg still moved the rows, so an entry demoted to un-ruled failed the gate loudly. Generated from it, the two move together — demote a table and the executor simply stops moving it, which is exactly what un-ruled asserts, and every data-driven gate stays green (mutation-verified 2026-08-12: demoting `account_aliases` reds only the two *hand-written* address tests, and most tables have no hand-written test). The remedy is that the un-ruled ratchet is now an **exact** count rather than a ceiling with slack, so any table leaving the ruled set trips it by name. A ruling can be changed, but only deliberately.

> **Succession's in-scope set is NOT the deletion registry's, and that difference is a defect surface of its own.** Deletion asks *"does this row belong to actor X?"*, so a column naming X only as a third party is correctly excluded — purging on it would delete a row X does not own. Succession asks *"does this row still name an identity that no longer exists?"*, and a third-party reference is exactly as stale after a ceremony as an ownership row. Those columns therefore carry their own declarations. **The worked example is `mail_domains.catch_all_actor_id`, ruled *clear* — and it is worth reading how that ruling was reached, because it was first written as *stay* and that was wrong.** The *stay* reasoning was: the catch-all is admin-plane routing rather than the designated account's property (an admin may point it at an actor who does not own the domain), so a user's own ceremony must not silently re-aim a deployment-wide decision — with a stated cost of unmatched mail being black-holed to an unreadable identity, **a loss and not a leak**. The first half stands. **The cost was an overclaim: it conflated retrieval with sealing, and only retrieval is closed by the alias re-point.** Unmatched mail still resolves through the catch-all to the **retired** actor; that actor's recipient seal key deliberately survives (its survival is exactly what arms the `succession_pending` tempfail for the address that *did* move); and the surviving-key branch reports `succession_pending = false` unconditionally, the tempfail firing only when no key is on file. So every future catch-all delivery would be freshly sealed to a key derived from the MSEK the thief read, **with no end date** — strictly worse than the residuals this ceremony knowingly accepts elsewhere, which decay precisely because sealing *stops* at the ceremony. Not a black-hole: an open sealing channel to a burned key. **The ceremony therefore clears the designation, and clearing is not the concession *following* would have been:** following re-aims an admin's decision, which is the objection *stay* got right, whereas clearing merely removes a pointer that has become unsafe without inventing a new target — and it makes the failure **loud**, since unmatched mail is then rejected where an admin can see it rather than vanishing. Nothing irrecoverable dies (a designation is admin-recreatable in one gesture), so the alpha deletion carve-out is not engaged. What remains owed is the admin-visible surface — the domain row should show that its catch-all was cleared by a succession, so re-designating is a decision rather than a discovery — which is app UI under the one-configuration-surface invariant, never a nest-side auto-follow.

> **The lesson the correction above carries, stated because it is more reusable than the ruling itself.** The *stay* framing was inherited from the row that requested the ruling, and it was transcribed rather than attacked — the sort of load-bearing claim a transcription discipline exists to make falsifiable. It survived because it was *plausible and convenient*: it made the item non-urgent, which is precisely the shape the "attack it hardest when believing it means you get to stop working" rule names. The refutation came from a reviewer tracing the mechanism at source rather than reasoning about the summary, and it turned on a detail no summary carried — that leaving the seal keys behind, the very thing that makes the *account's own* address fail safe, is what makes the *catch-all* path fail unsafe. **A safety property established for one path is not evidence about a second path that reaches the same key by another route.**

> **A registry that can only see what it can name is complete only against its own vocabulary.** The walk that keeps the registry honest matches column *names* against `actor` / `author` / `owner`, and justified itself by observing that every entry already contains one of those roots — which is self-fulfilling, since the registry was built by that same heuristic. `folder_channel_claims.claimed_by` is the counterexample the succession axis surfaced: the succession transaction has always treated it as ownership ("the claim is authority"), yet it appeared in neither the registry nor its reasoned-exclusion list, because its column name contains none of the three roots. It is registered now. Its **deletion** disposition, left open here on purpose, is settled in [`account-data-plane.md`](../architecture/account-data-plane.md) § Nest-side requirements item 1 — `Policy::Purge`, backed by a channel-scoped cascade so purging the claim never strands a shared channel's other members.
>
> **And as of 2026-08-13 that vocabulary is CHECKED rather than asserted, which is the half that was actually broken.** `the_walks_vocabulary_can_name_every_registered_column` states what the old comment merely claimed: every column already in `ACTOR_TABLES` or `SUCCESSION_REFERENCES` must be findable by the word list the walk searches with. It red on **six** columns the moment it existed — three `recipient_id`s, `content_reports.reporter`, the `claimed_by` above, and `segment_records.scope_id` — so the justification had been false the whole time, including in the very example it offered. Five closed by widening the vocabulary (`recipient`, `reporter`, `subscriber`, plus an agentive `…_by` rule that `claimed_by` and `payment_claim_codes.redeemed_by` have now each paid for once); the sixth is declared a blind spot no vocabulary can close, because a **rename** carried it out of sight (`actor_id` → `scope_id`) and nothing about the new name reads as a person — the residual is caught instead by the gate that reds when a registry entry names a column the schema no longer has. The widening then surfaced eighteen more columns: twelve false positives of the new roots (`recipient` means an email ADDRESS in the mail plane, and sometimes a COUNT of them; `…_by` sometimes answers with a role rather than a person), and **six genuine actor columns no gate had ever seen** — `admin_actor_ids.added_by`, `group_members.invited_by`, `invite_requests.decided_by`, `pending_actions.cancelled_by`, `snapshots.tags_sealed_by` and `wireguard_peers.registered_by`. Those six were `Unruled` and ratcheted rather than ruled on the day the gate was fixed, for the same reason `COUPLED_MOVE_FAMILIES` shipped empty: fixing the gate that should have found a column and ruling that column are different acts. **The generalizable half: the way to make a heuristic honest is to point it at the data it filtered and assert it can still see all of it.** A heuristic that justifies itself by its own output is not a gate, it is a mirror.

> ⚠ **One of those six columns no longer exists (2026-08-23).** `wireguard_peers.registered_by` went with the whole WireGuard stack — table, `ACTOR_TABLES` entry, and the succession burn that resolved through it (user-directed; owner [`p2p.md`](p2p.md)). The dated rulings below are left as written rather than edited, because the reasoning is the point and rewriting a ruling to match today's schema would destroy the record of how it was reached. **Two things to carry forward, though:** the ruling's *argument* — a plane that authenticates on a key and consults the refusal plane nowhere must BURN its owner-binding rows, since a row left behind serves a seed thief while denying the successor even the ability to revoke it — is general, and is the same argument `key_packages` turns on. And the gate that would have caught a stale registry entry is the one this block praises: the check that reds when `SUCCESSION_REFERENCES` names a column the schema no longer has. It did its job here.

> **All six are RULED as of 2026-08-13, and the shape of the answer is the part worth recording: a `…_by` column's NAME predicts nothing about what it does.** The verdicts themselves are declared per column in `SUCCESSION_REFERENCES` and are deliberately not restated here. What generalizes is that the vocabulary which *finds* these columns — "who did it" — describes their grammar and not their function, so reading the set as "attribution, therefore stay" would have been wrong twice in six. Four are attribution and stay, each checked for what actually resolves through it rather than assumed (one of them, `admin_actor_ids.added_by`, turned out to be a **dark column** — written by nothing and read by nothing — so its ruling is recorded as conditional on that, for the session that eventually wires it). The other two were not attribution at all: `snapshots.tags_sealed_by` is a **provenance licence** two scrub passes resolve through, and it moves, because the ceremony moves the `folders.actor_id` half of the predicate they compare it against — left behind it survives only via the `sync_devices` arm, whose rows deliberately stay, so removing that device later un-scrubs the successor's tag plaintext permanently and, on a nest that has not yet run the flip inventory, destroys the sealed tags with it. `wireguard_peers.registered_by` is an **owner-binding** — WG-1 refuses a non-admin caller whose id differs — and it burns, on `key_packages`' argument exactly: WireGuard authenticates on the peer key and consults the refusal plane nowhere, so a peer a seed thief registered keeps its tunnel under any ruling that leaves the row, while the successor cannot unregister even their own. Moving it would hand over a binding with no surface to use, since no user-facing surface enumerates peers.
>
> **Ruling them also found the FK gate's one over-approximation, and narrowing it is a claim worth stating.** `no_foreign_key_crosses_a_succession_leg` treats a `Bespoke` move as possibly deleting rows, because a table-level bespoke leg may be a delete-then-insert (`admin_actor_ids` is). `snapshots` was the first **reference-only** `Bespoke` on a foreign-key parent, and the proxy fired on a leg that rewrites one non-key column and deletes nothing. The refinement: `Bespoke` counts as deleting only where the table also has an ownership entry, i.e. where the rows are the actor's own — a table reached only through the reference list holds, by that list's defining property, rows that are not the actor's to delete. `Burn` and `Partial` stay unqualified in either list. The assumption this rests on is now the load-bearing one and is stated rather than buried: **a reference leg that genuinely deletes rows must be declared `Burn` or `Partial`, never `Move`** — pinned in both directions against the real schema, so a gate that quietly stopped checking deletion at all fails the same test.

> ⚠ **A row whose PRESENCE denies authority must never be burned — ruled 2026-08-14, and it is the first place on this axis where a burn was the actively dangerous direction.** `share_tokens` reads like a registry of live share links and is not one: a `ShareToken` is client-minted, stateless and self-verifying, registration is deliberately *not* a serving gate, and `GET /share/{token}` consults the table for exactly one thing — to refuse a **revoked** token with 410. `is_share_token_revoked` answers `false` for a row that is not there. So deleting the rows of a retired identity does not end its share links; it **un-revokes** every link that identity had already killed. The table moves instead, which is also the only remedy the successor has: revocation and listing are both scoped to `author`, so a registry left behind is invisible *and* unrevocable while the links keep serving (the `nest_pairings` breach of `nest/common.md` § Client-state recoverability), and rows already revoked stay revoked because the flag travels with the row. **The general form, and it outranks the plane the table sits in:** before declaring a burn, ask what the *absence* of the row means to whatever consults it. Where absence means *denied*, a burn ends authority; where absence means *permitted*, a burn **grants** it. Only the consumer can answer that, never the table's name.
>
> **The serve-side completion — ruled 2026-08-15: after a succession, a token authored by the retired identity serves only through its registry row.** The move above hands the successor the kill switch for every *registered* link, but a token the thief minted and never registered has no row for any verdict to move — and it kept serving, because registration is deliberately not a serving gate and the serve path's author check passes (the ceremony keeps the `users` row). The gate closes exactly that class: `GET /share/{token}` consults the author's succession state, and an **unregistered** token whose author is succeeded refuses `410 Gone` (`share_routes.rs`; the registry consult is `CacheDb::share_token_registration`, whose `None` is what makes "unregistered" a first-class answer rather than "not revoked"). **This is the refusal plane's one rule reaching the last place the old key could still speak, not a second rule.** An unregistered token's only authority is the retired key's bare signature — honouring it is honouring the old key as live authority, with a client-picked `expires` that bounds nothing. A *registered* token's authority is different in kind: the then-owner deposited the row over an authenticated `fauna.share.create`, the ceremony moved it to the successor, and it is listed and revocable from the successor's app — so it keeps serving until the successor says otherwise, and the token's embedded old-key signature becomes attribution, like every other embedded signature that genuinely names the old key. Post-ceremony the classes cannot leak into each other: the old key cannot authenticate to register, and `fauna.share.create` refuses a caller who is not the token's author, so a retired-author token with a row was necessarily registered before the ceremony — the distinction is structural, no timestamp is consulted. **The honest counter-argument, answered rather than skipped:** a legitimate pre-ceremony unregistered link is indistinguishable from a thief's *by construction* — the token carries no evidence of which it is — and that indistinguishability is the argument **for** refusal, not against: any rule that serves one serves the other, so the class dies whole or survives whole, and surviving whole means a standing unauthenticated read channel with a thief-chosen end date. The cost falls only on links minted but never registered (empty in practice today — no shipped app mints ShareTokens yet, `core-client-kind-catalog.md` § Share's deferred adoption note), and the heal is one gesture by a party who exists by definition (the successor re-mints a fresh link to the same manifest); the `push_subscriptions` burn below accepted the same trade in the same words — what dies is one re-mint. Nothing changes for a live author — stateless serving stays the wire contract (`core-client-kind-catalog.md` § Share owns it), so no shipped client breaks — and nothing is resurrected: the revocation check runs first, and a predecessor-revoked moved row stays revoked, `410` either way.
>
> **And the same pass inverted the axis's other asymmetry: where a credential is honoured *instead of* an identity, `Move` is the dangerous direction — ruled 2026-08-14.** The standing rule is that a wrong `Move` is a security regression while a wrong `Stay` is the status quo, so rulings are worked outward conservatively. `eviction_tokens` runs the other way. `GET /api/v1/export` takes the token *in place of* an identity — when the Authorization header is not a session token the handler falls back to `validate_eviction_token`, which returns an actor id with **no identity check at all**, and then zips that actor's whole account. The refusal plane never sees the caller (the *does anything that honours these rows read an actor?* question, answered no). Because the token names whatever actor it is bound to, its value **follows the data**, and the data moves: a seed thief who read the string from their own app before the ceremony (it is shown to the account under eviction) would hold a credential aimed at the *successor's* entire corpus. `Stay` is not the safe fallback here either — left behind the row is merely useless *and* unrevocable, which is not the same as gone. So the token burns, and nothing irrecoverable dies with it: it is a means of access rather than data, and its one legitimate holder exports as the successor afterwards or has the admin re-issue — the bounded, visible re-grant this axis prefers everywhere. ⚠ A table's *deletion*-axis coverage says nothing about this axis: `delete_eviction_tokens` has covered these rows since long before, on eviction-cancel and account-deletion, and no succession path has ever called it.

> ⚠ **The classification rule has a second question, and it points the opposite way — ratified 2026-08-14.** *"Rows that confer future authority or access re-point; rows that record history/attribution stay"* asks what a row **grants**, because carrying a grant forward was the dangerous direction in every plane ruled before this one. A row that **limits** the account is the mirror image, and there the dangerous direction is leaving it behind. The reason is one sentence: **a succession is self-service.** Any account holder can perform one with their own recovery kit, so a limit that a ceremony sheds is not a limit — it is a limit with a reset button, and the button can be pressed again tomorrow. So: **anything keyed on an actor that constrains what that actor may do next must move.** The three tables that established it are the per-account-per-day list-recipient meter (`mail-mass-mailing.md` § The per-day per-account cap — left behind, the successor's first send reads zero and gets a fresh 20 000-recipient day), the anti-spam behavioural profile (its 1 h / 24 h / 7 d DM fan-out windows all empty at once), and the abuse-report table behind the consensus reputation score. Two riders worth carrying: the cost of moving a meter is **bounded and self-clearing** (the successor inherits one day's consumption, which the next UTC rollover zeroes) where the cost of not moving it is unbounded; and a reputation table looks like attribution — third-party testimony about a past event — but is consulted about what the sender may do **next**, so it functions as a live constraint, not a record. **The honest counter-argument, stated because it has to be answered rather than skipped:** a succession often follows a *theft*, so moving the liability can hand the victim damage the thief earned. It loses on all three axes — that case is rare, it is not self-service, and it has a remedy that does not require mis-ruling the table (admin action, plus the decay these tables already apply) — and one further fact settles it: the account's **external** identity is continuous across a ceremony, since the handle moves with it, so a local reset would only put the nest out of step with what its own federated peers still believe.
>
> **The same pass ruled the mailing-list plane, where a `Stay` strands a live public surface no client can reach — 2026-08-14.** A list is two rows that part company at the ceremony: its **address** is a `kind='list'` row in `account_aliases`, which moves with the address leg ([`succession-aftermath.md`](succession-aftermath.md) § Re-key scope), while its **management** is owner-scoped in every door (`mail-mass-mailing.md` § Wire shapes: "all per-user / owner-scoped"). Inbound delivery resolves through the alias and never consults the owner, so a list left behind keeps accepting mail and keeps serving one-click unsubscribes, while the successor — who now owns the address it sends from — cannot see it, edit it, send to it or delete it, and neither can anyone else, the retired identity being refused everywhere. That is a client-reachable state no client can fix (`nest/common.md` § Client-state recoverability), and the only lever it leaves is deleting the alias, whose `ON DELETE CASCADE` destroys the list and every subscriber row with it — data loss as the remedy for a mis-ruling. The list, its send audit and the account meter therefore move together. ⚠ **That blind spot CLOSED 2026-08-15** — `mail_lists` and `mail_list_sends` no longer sit in the registry gate's `SEED_BLIND` set (now empty, `db/actor_tables.rs`), so the generic data-driven sweep witnesses this ruling too, alongside its hand-written pins.

> **The content plane follows the account, and the fix for "a successor cannot delete its own legacy posts" is a MOVE, never a second rule — ruled 2026-08-14.** `content.author` is the nest-side **ownership** pointer: the delete rule (`routes::check_post_delete_authorization` — whose two stored-author checks are conjunctive, so the already-moved `segment_records.scope_id` twin alone could not heal it), the own-post enumeration (`fauna.posts.list`), notification routing, quarantine author-visibility and the deletion-axis federation retraction all resolve *forward* through it, while the attribution "posts stay attributed" protects lives in the **signed post bytes**, which no leg touches — the same argument that made moving `scope_id` uncontroversial, applied to its legacy twin. The AP-writer caveat is answered rather than assumed away: every production writer derives the column from the decoded payload's own author field, so the plain leg's `author = ?old` matches exactly the rows the retired identity signed — remote-authored ingest carries the remote id and the undecodable-raw arm a zero author, both unreachable by construction, so no `Partial` split is needed. Deliberately **not** a succession-chain consult in the delete path: the successor is an ordinary owner and the check keeps its one equality (the rejected-alternative blockquote above; the function's single-owner read-only contract is untouched). Moving with it: `content_scores.actor_id` (the `submit_scores` owner-binding — left behind, every re-score of the legacy corpus is refused forever once the pre-ceremony grants burn), `engagement_events.actor_id` (the trend export's k-anonymity gate counts DISTINCT engagers, so an un-moved log counts one human twice and walks a below-k pattern over the wire threshold; declared residual: toggle event-ids are content-addressed to the acting identity, so a pre-ceremony like is not successor-retractable and a re-like double-counts once — bounded and trend-decaying), `feature_usage` (the per-day feature quota — the limits-move rule verbatim, one bounded day inherited), and the **dark** `content_uid_map` (no production writer or reader — conditional ruling, the `email_domain_users` precedent). `content_reports.reporter` is deliberately deferred to the counterparty-columns pass beside `sender_reputation.reporter_actor` — the same Sybil-distinct-reporter class, graded once, coherently.

> **The delivery plane, and its burn is the first ruling on this axis aimed at an exposure the ceremony was leaving LIVE rather than latent — ruled 2026-08-14.** Every plane before it could be reasoned about as *where do these rows live afterwards*, because the retired identity stops acting at the ceremony. The delivery plane is different in one fact that no per-table verdict had needed until now: **a retired identity keeps being delivered to.** `deliver_inbox_payload_core` consults the succession table for the **sender** — the refusal that stops a stolen key posting fresh content — and nothing on that path asks whether the *recipient* has been succeeded, so a peer that has not propagated the statement goes on landing posts on the retired actor indefinitely. That is deliberate and correct (the alternative black-holes mail in flight during propagation), and it is what turns a residual row into a running one. **What that clause leaves unsaid is where such an arrival LANDS, and that was ruled 2026-09-26: on the successor.** The clause argues against *refusing* the peer; it never chose the retired actor as the destination, and the ceremony's own moves (`inbox_modes`, and `contacts`, `knocks`, `notifications` below) make the retired actor a trap — a post-ceremony arrival addressed to it fell back to `allow_knock` and no edge and became a knock plus a notification nobody can sign in to read. So `deliver_inbox_payload_core` resolves the addressed recipient through `succession_path`'s terminal hop *before* `reach_floor` and the inbox-mode routing (a sender the successor blocked is refused when addressing the predecessor), and judges existence at the terminal id (a successor since deleted took its predecessors with it — [`../architecture/account-data-plane.md`](../architecture/account-data-plane.md) § Nest-side requirements item 1 — and answers the unregistered-recipient `forbidden`, never a ghost knock). No wire change: the reply's `inbox_id` is the successor's row. Build ledger: § Implementation status today, the 2026-09-26 entry. **`push_subscriptions` burns**, in the shared reach leg beside `key_packages` and `nest_pairings` rather than in a call site of its own: a row is a caller-supplied endpoint URL plus the caller's own encryption keys, armed by an ordinary User-class subscribe — i.e. by exactly what a seed thief holds — and the dispatcher POSTs to it while authenticating nobody, which is this axis's standing test for *does the refusal plane reach here?* answered a third way. It is also unrevocable from every app **by construction**: there is no list kind at all, and unsubscribe must name a device id, so after the ceremony the rows belong to an actor nobody can authenticate as and no surface anywhere can enumerate — the `nest_pairings` stranding shape with a live feed running through it. No `Partial` is available, and the reason is the earlier ruling's verbatim: **a legitimate pre-ceremony registration is indistinguishable from a thief's**, because a subscription carries no attestation of who armed it. What dies is one re-registration. **Five tables move**, and each is a different reading of *the successor's own record of their own account*: `notifications` (the page and its unread badge — emptied by the ceremony that rescued it), `knocks` (the pending-reach queue `inbox_modes` gates into — and since that gate already moves, leaving the queue hands the successor a narrowed mode and none of the people it narrowed, the `inbox_modes` asymmetry read from the other side), `actor_message_dedup` (the import ledger — left behind, the ceremony's first visible effect is a mailbox of duplicates), `message_scan_results` (whose per-actor consumer seeds the scoring backlog from "the owner's mail item universe", so a record left behind seeds the successor from an empty one), and `personalization_models` (the at-rest half of the trained-topic registry the aftermath *already* carries — the account-state plane kind `fauna.state.personalization`, carried by the successor's walk ([`succession-aftermath.md`](succession-aftermath.md) § Re-key scope), where the `__config` re-seal carried it until the rail retired on 2026-10-02 ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)) — split from it, each orphaned factor degrades to a **zero term** rather than an error while the page still reads "trained", the `web_subdomain_enabled` shape). **Two stay, and both invert the reflex.** `actor_index_pubkeys` is `actor_mls_pubkeys`' sibling by its own migration comment — same block, same perimeter fetch, same job of sealing *future inbound* mail — so it takes its sibling's COMPROMISE verdict, recorded **conditional on the table being dark today** (no production writer exists, so the private half's provenance cannot be read off any producer; re-check it when the provisioning lands — the `admin_actor_ids.added_by` precedent). `actor_last_ip` is the sharper one: it has no getter at all, and its single consumer compares it to the address in hand to arm the new-location alert — so carrying it would make that alert **lie in both directions**, reading the successor's first honest sign-in as an intrusion and the thief's own re-use as routine, where a new identity legitimately starts with no baseline and a first insert is silent by construction. **Two of the six mutations are measurements rather than confirmations, and both sharpen the agreement-only finding instead of repeating it.** Flipping the burn to `Move(Plain)` — the security ruling reversed outright — left **both** data-driven sweeps and the exact-count ratchet green, and the mechanism is worth knowing: the registry-driven plain move runs *before* the burn leg, so under the flipped declaration the rows really do land on the successor and the burn then matches nothing, leaving executor and declaration in perfect agreement, which is all either sweep checks. The whole property — *a thief-planted destination must not be inherited* — therefore rests on two hand-written asserts. And severing the table from the burn's own table list reddened the ceremony sweep but **not** the reconcile's — the Plain-only-gate finding reproduced exactly: that gate covers `Move(MoveShape::Plain)` and nothing else, so a burn's backfill leg is witnessed by a hand-written pin or by nothing at all.

> **The completeness walk's vocabulary gained `sender` in the same pass, and the failure it closed is the same one twice — 2026-08-14.** `knocks.sender_id` and `notifications.sender_id` have always named an actor and were accounted for by **nothing**: no registry entry, no reference row, no exclusion. The tell is that `recipient` had been added the pass before while its own antonym had not — a vocabulary assembled one finding at a time keeps having the word for whichever half someone happened to look at, which is precisely the circularity `the_walks_vocabulary_can_name_every_registered_column` exists to break. Registering the two columns is what *forces* the widening (a registered column the walk cannot name reds that self-check), so the gate fix is not an optional extra here, and the mutation confirms which gate does the work: deleting `sender` again leaves `every_actor_shaped_column_is_registered_or_excluded` **green** — a narrower search finds fewer problems, indistinguishable from having none — and reds only the self-check, by name. `sender` is the one root that is also an everyday **mail** noun, so it surfaces ten envelope columns (addresses, domains, an address hash, a peer nest, a policy knob) that name no person; each is excluded **by name** rather than by narrowing the root back down, because narrowing is the move that fails silently. Both real columns join the reference backlog `Unruled` rather than being ruled here — they are the counterparty question (what happens to a reference when the *counterparty* succeeds), deliberately not answered by a pass whose subject was this plane's own rows.

> **The membership/participation cluster is ruled `Stay` end to end, all five on the same footing as the tables already left behind, and none of it was a cheap declaration pass — 2026-08-14 (backlog 45 → 40).** `actor_channels`, `channel_foreign_members`, `folder_member_access`, `group_members` and `groups.owner_id` all declare `Succession::Stay` (the last two were since retired with the group plane, 2026-09-26; the other three stand). `actor_channels` is the channel-fetch authorization, so both directions were live and the earlier asymmetry (grants move, limits stay) could not settle it by itself — the mechanism did, three ways: the propagation leg already re-registers the successor (the add-successor Welcome calls `register_actor_channel_gated`); a `Stay` strands nothing the successor *owns*, since every `folder_authz` gate takes an owner fast-path on `folders.actor_id` before ever consulting the roster, so the roster governs only membership in someone *else's* set; and — the decisive leg, one plane over from `recovery_registrations` — a `Move` would break the ceremony's own federation push, because `succession_push_targets` finds the peers holding residue by reading `actor_channels WHERE actor_id = ?old` and `push_succession_detached` runs it *after* the transaction commits, so moved rows would leave an empty target set and no peer nest would ever learn the succession happened. `channel_foreign_members` is the `sync_devices` shape in its purest form: already re-pointed by `record_peer_succession`'s bespoke two-step, never declared, and on the local ceremony its leg is vacuous by construction — the only producer fires on welcome delivery's federation-relay branch, so every row already names an actor homed elsewhere. `folder_member_access` takes the roster's verdict rather than asserting its own: the write gate is a conjunction, so a grant that moved alone would admit nothing. **Which leg moves the grant is ruled elsewhere (2026-10-02):** the propagation leg that moves the seat carries the predecessor's `folder_member_access` row with it — the sweep's Welcome on the home nest, the peer re-point on a set's foreign nest — so the grant still never moves alone and these three declarations stand for the transaction they govern; owner [`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, ruling (8)(j). `groups.owner_id` is a dark column that takes its live twin's verdict (the `role = 'owner'` row in `group_members`), since the two halves of one fact cannot be allowed to disagree. Both group tables are ruled **conditional on the plane being dark today** — no shipped app calls `fauna.conversations.group.{create,invite}` — with the owner-only directory freeze declared as the residual and re-check trigger for whenever that plane ships.

> **The curation cluster, and the transferable half is that a table's SECOND actor column can be the only one with security in it — ruled 2026-08-15.** Every pass before this one asked its questions of the column the registry names. `labelers` has two, and they answer opposite questions. `publisher_actor` — the registry column — is not an account pointer at all but the artifact's own self-signed `algorithm_id`, the keypair the stored bytes' Ed25519 signature verifies against at publish and again at every FFI instantiation; it **stays**, because the classification rule's "embedded signatures genuinely name the old key" arm applies literally here rather than by analogy, and because a moved one would advertise the successor as the signer of bytes they never signed. It confers nothing a move could rescue: the registry has no delete or retire verb at all, and a new version is admitted by signing with the algorithm key, which is client-side material a succession never touches. `caller_actor` is the enrolled identity, and it exists **because** the first column bounds nothing — the signing keypair is free and off-box-rotatable, so `MAX_LABELERS_PER_CALLER` was keyed on "the un-rotatable enrolled-user identity" instead. That is the sentence the ruling turns on: a succession is **self-service** (the liability blockquote above), so a left-behind count resets the cap in full, and the bound built to survive *keypair* rotation is defeated by *identity* rotation instead — repeatably, and permanently, since a catalog with no delete verb never gives back what a reset admitted. **Ask of every remaining table whether the column the registry names is the one that matters.** The other three rulings are the stranding shapes this axis already knows, on new surfaces: `feeds` is `web_domains` on a nest-wide **published** object (unfiltered `fauna.feed.list` versus owner-scoped edit and delete, so nobody can ever remove a stranded feed), `labeler_subscriptions` is `share_tokens` inverted — the row's **presence** is what keeps a nest-wide effect alive, since one unreachable subscription holds `count_subscriptions_for_labeler` above zero and blocks the withdraw for every other user — and `feed_global_factors` is simply the half of a composition whose other half moves. `feed_contributors` is left `Unruled` on purpose: its `author_id` names the counterparty a feed collects, not the row's owner, so it is the counterparty question and is graded with that class.

> **Three of the five mutations are measurements, and two of them are new.** *(1)* Flipping `labelers.publisher_actor` from `Stay` to `Move` left **everything** green — both data-driven sweeps, the FK gate, the exact-count ratchet and the pass's own hand pins. This is the unfalsifiable class in its purest form yet: no production writer can put an enrolled actor id in that column, so no reachable row distinguishes the two verdicts, and the generic sweep does not merely miss that — it seeds a synthetic row keyed on the acting actor and confirms whichever verdict is declared. Recorded in the reason rather than papered over with a pin that seeds a state the schema cannot reach. *(2)* Severing the **reconcile** arm of the reference leg while leaving the ceremony's intact also reddened nothing at all, out of 140 succession tests: `the_reconcile_moves_every_plain_leg_the_registry_declares` covers `Move(MoveShape::Plain)` entries of `ACTOR_TABLES`, so a `Bespoke` reference leg's backfill is witnessed by a hand-written pin or by nothing — the burn-side finding, holding identically one verdict class out. A backfill pin was written and red-verified against that severed arm before it counted as coverage. *(3)* Demoting either moved table to `Unruled` with the ratchet masked left all registry gates green and reddened only the product-observable pin, which is why those pins are written for the direction *not* chosen.

> **The long tail's remainder, and the finding is a new HAZARD SHAPE rather than a new answer: the first table on this axis whose danger is a TIMER — ruled 2026-08-15 (backlog 36 → 30).** Every ruling before this one asked where rows *live* after the ceremony, because a retired identity stops acting and — since the delivery plane — keeps being delivered to. `pending_actions` is neither: it is a queue of **delayed destructive operations that fire themselves**. A background executor ticks every 60 s and runs everything `status='pending'` whose `execute_after` has passed, **authenticating nobody** — the row *is* the authority, `push_subscriptions`' standing one plane over — and the delays run from 6 h (handle change) through 7 d (snapshot bulk prune) to 14 d (account deletion). A succession racing a seed thief therefore lands *inside* that window by construction; that is what the window is for. Left un-ruled, the ceremony meant to end the theft commits and the thief's queued deletion goes on counting down. **Neither `Move` nor `Burn` is the answer, and this is the second place on this axis where `Move` is the actively dangerous direction** (`eviction_tokens` was the first): three of the executor's arms — `snapshot.delete`, `snapshot.bulk_prune` and `admin.backup_purge_override`, the last a *hard* purge rather than a soft delete — resolve their target from the row's own `target`/`payload` **with no actor check at all**, so re-pointing a thief's queued prune aims it squarely at the corpus the ceremony has just moved to the successor. A `Burn` errs the other way, deleting the record that the action was ever scheduled — the act most worth leaving legible to the identity it was aimed at, which is the argument `pending_actions.cancelled_by` already carries. **So the rows stay and the ceremony writes the table's own terminal state**: every row of the retired identity that is still `pending` is cancelled in place, on the ceremony and the boot reconcile alike, with `cancelled_by` deliberately left NULL because no person cancelled them and naming either identity would be a false attribution on a row whose remaining value is being an honest record. ⚠ **The un-mark travels with it**: a snapshot action marks its targets `deletion_pending` at creation and nothing but a cancel ever clears it, so a disarm that skipped it would leave the *successor's* own snapshots excluded from their folder's retention floor and the auto-pruner's population permanently — a silent loss riding a security fix. **The general form: ask of every remaining table whether anything about it RUNS ON A CLOCK.** Where it does, the ceremony's own commit is not the end of the retired identity's reach, and no verdict about where rows live can reach it.
>
> **The other five are the shapes this axis already knows, and two of them correct a claim that was written down rather than checked.** `import_sessions` **moves**: its dedup ledger was moved by the delivery plane, so a `Stay` splits one mechanism in half — and the deciding fact is that the 30-day expiry sweep is itself owner-scoped, fired only on that actor's own create/list, so the one verdict that makes this ephemeral bookkeeping *immortal* is leaving it behind. `obligation_action_records.author_hex` **moves** with the content it is about (`content.author` moved the day before): it keys the author-facing transparency queue, so a `Stay` empties the successor's moderation page of the actions taken against posts they now own and leaves the record readable by exactly one actor — the retired one, refused everywhere — which is the transparency gap the takedown transaction's all-or-nothing shape exists to prevent, opened by the ceremony instead of by a crash. ⚠ Its registry entry described the record as **signed**, and no production row is: the only production writer stores an empty signature and the signing arm is test-only. Had it been true it would have argued for `Stay`, so it is corrected rather than relied on — the transcription discipline's own failure mode, caught on the entry being edited. `handle_cooldowns` **moves**, ruled **conditional on the table being dark today** (its readers are live, its producer has no production caller): the row is a 72-hour *exclusive reclaim right*, not a bare denial, so a thief who releases the victim's handle arms a clock that leaves the successor as the one actor who cannot take their own handle back, and when it lapses the handle is open to anyone. `audit_log` **stays**, and its argument is stronger than the usual attribution one: the column is *inside* a hash chain (`entry_hash` covers `actor_id`; each row's `prev_hash` is the previous row's `entry_hash`) whose links are served to the admin transparency surface, so a move is both a break an admin's own verification finds and a forgery in content. ⚠ **That verification only finds a move because the preimage is length-framed, and it was not always.** Until the `v2` domain tag the entry hash concatenated `actor_id`, `action`, `target` and `detail` raw, so it bound their *concatenation* and not their column boundaries: bytes moved across a boundary — `actor_id` emptied into the head of `action`, or `action` re-split against `target` — recomputed to the identical `entry_hash`, and an admin recomputing the chain from the served columns certified the tampered row. The framing is what makes the argument above true rather than merely stated. ⚠ **And a version TAG is not a version RECORD — the second half landed 2026-09-01.** The tag makes the two preimages non-colliding; it does not make them non-*interchangeable*, and until a row said which one it was written under, an auditor walking a chain that straddles the cutover had to keep a v1 arm live for **every** row it ever saw: never retirable (no query can name the last v1 row), never scopeable (no row is entitled to the strong format), so a certified row told an admin nothing about *which* arm certified it and the verification's meaning collapsed to its weakest. The rule now is **one preimage per row, selected from the version the row records, and any version the verifier does not know is REFUSED** — never tried against another format until one matches. `audit_log.entry_hash_version` and `pending_actions.chain_hash_version` carry it; a one-time classification recovers it for rows written before the column, and whatever recomputation cannot identify keeps saying *unrecorded*, which is honest, rather than being guessed at as `1`. `invite_requests` **stays**, and it is the cleanest **unreachable-by-construction** ruling this axis has produced — cleaner than `channel_foreign_members` (unreachable in practice) or `labelers.publisher_actor` (unreachable by column semantics) — because the *producer refuses the case by name*: `submit_invite_request_core` rejects an already-registered actor, and an approve consumes its row, so every surviving row names an actor with no `users` row, while both succession writers require one. Said plainly in the reason rather than pinned by seeding a row the schema's own producer would reject, per the standing instruction.

> **The two FEATURE-GATED bridge planes, and the whole pass is one discriminator: WHO CHOSE THE EXTERNAL DESTINATION — ruled 2026-08-15 (backlog 30 → 22).** `ap_*` (3 tables) and `bluesky_*` (5) are the same *shape* — a bridge that gives the account an identity on somebody else's network, both sitting outside the schema the data-driven sweeps walk — and they take **opposite verdicts**. Neither the plane's name nor the table's predicts which: what does is whether the destination is derived from the account or supplied by whoever set the link up. **ActivityPub's is derived, so it moves.** The AP username is minted from the Fauna handle at enablement and frozen, the actor URL is built from it, and *both* federation doors — WebFinger and the per-user inbox — resolve an arrival through that username. The handle moves with the ceremony (the class rule at the top of this section), so leaving the identity built on it behind is the `account_aliases` failure one plane over, with the arrival half of the delivery plane's finding on top: every remote `Create` and `Follow` addressed to the handle the ceremony *just transferred* keeps landing on the retired actor. The stranding is the sharper half. The username carries a `UNIQUE`, the enable path resolves a taken name by suffixing, and the only deleter is an unlink door scoped to the authenticated caller — so the successor is minted `<handle>-2`, a different fediverse identity with none of the followers, and can never reclaim its own name from an identity that is refused everywhere. A client-reachable state no client can fix ([`nest/common.md`](../architecture/nest/common.md) § Client-state recoverability). ⚠ **The key-material arm runs the OPPOSITE way to `actor_mls_pubkeys`, and that is worth stating because the reflex says otherwise:** the per-account RSA private key is sealed under the **nest** KEK, never under the user seed, so a seed thief never read it — there is nothing here to deliberately leave behind as compromised. A thief who merely flipped federation *on* hands the successor a presence one owner-scoped toggle away, aimed at the nest's own domain: the `spam_preferences` side of the attacker-chosen-destination test, not the `forward_all_to` side.
>
> **The Bluesky link's destination is supplied, so it burns.** `bluesky_did` is whatever account completed the OAuth flow, and linking is an ordinary User-class gesture — exactly what a seed thief holds. The link row *is* the actor→authority edge: its token columns are written empty (the session is keyed by DID, not by actor), so a linked-account lookup resolves straight into an authenticated third-party agent **with no further identity check** — the `eviction_tokens` class, a credential honoured *instead of* an identity. The cross-post setting rides that same row, which is what makes `Move` the actively dangerous direction here: carried forward, it publishes the **successor's** every public post into the repo the thief chose, with no end date. And `Stay` is not the safe fallback, for the reason `eviction_tokens` established — the unlink door is caller-scoped, so a row left on the retired identity is useless *and* unrevocable, by the successor and by everyone else. The four satellites burn with the binding rather than on arguments of their own: each is per-actor state *of that link*, and nothing user-irrecoverable dies with them — the Fauna posts and conversations they map to are `content` / `segment_records` rows that move with the account, and re-linking is one authorization gesture. The alpha deletion carve-out is therefore not engaged. The `ap_*` family additionally joins the reconcile's all-or-nothing parking list: its account row cannot merge (`actor_id` PRIMARY KEY *and* `username` UNIQUE) while its follows and post map carry no such constraint, so per-table parking would leave the terminal federating under its own name while serving the predecessor's followers — the Nostr and hosted-PDS rule a third bridge over.

> **Three of the seven mutations are measurements rather than confirmations, and the first is the one to carry forward.** *(1)* **A `Burn`'s registry declaration is documentation; a `Move`'s is the executor.** Demoting all five `bluesky_*` rulings to `Unruled` (ratchet masked) left **every test green**, because a burn is executed by a hand-written leg whose own table list is the authority — where demoting the `ap_*` rulings reddened the ceremony pin immediately, the plain-move loop being generated from the declaration. So on this axis a burn ruling can be silently reverted in the registry while the leg goes on burning, *and* a table can be declared `Burn` and never burn at all. That is fresh, measured evidence for making `Burn` registry-driven the way `Move` already is. *(2)* **A parking-list member's reconcile arm is hand-written too**, so demoting its declaration does not touch the backfill: the `ap_*` ceremony and backfill halves needed separate mutations and separate pins. *(3)* **A collision pin cannot grade itself.** Severing the reconcile arm outright left the all-or-nothing parking test **green** — "the family parked" and "nothing ever moved it" are observationally identical — so that pin is only meaningful beside the backfill pin that proves the arm moves anything at all. Forcing the guard to its move branch then reddened it with exactly the mis-attribution the ruling names: the account parked on the predecessor while its followers and its push witness moved onto the terminal.

> **The COUNTERPARTY columns, and they are the first class on this axis whose damage lands on a THIRD PARTY — ruled 2026-08-15 (table backlog 22 → 20, reference backlog 4 → 0, which empties it).** Every ruling before this one asked what a row grants or limits **its own** actor: carry a grant forward and a thief keeps authority, shed a limit and a self-service ceremony becomes a reset button. These six columns name **somebody else** — the reporter who flagged you, the person you DMed, the stranger who knocked, the author a feed collects — and the question they answer is neither. It is this: **every consumer here is counting or matching PEOPLE**, so a reference left on a retired identity does not merely go stale, it makes the nest believe **there are two humans where there is one**. `sender_reputation.reporter_actor` is the sharpest case, because the double-count defeats a defence built on purpose: the aggregate is Sybil-resistant by *grouping* on that column — one confidence per distinct reporter, scaled by a consensus weight that rises with the count — so a reporter who succeeds and reports the same sender again becomes two independent accusers, which is the single property the grouping exists to deny. `sender_behavior.target_actor` breaks in both directions at once: the fan-out windows count DISTINCT recipients, so one human who succeeds mid-window inflates an uninvolved sender's spam profile, while the correspondent-pair reply guard — which requires a matching `dm_sent` row for the same pair — stops matching, so that person's replies stop recording at all and the same sender reads *colder* than they are. `notifications.sender_id` sits inside the insert's own dedup key, so a sender who succeeds re-notifies people about events they were already told about. `knocks.sender_id`, `content_reports.reporter` and `feed_contributors.author_id` are the same shape on three more surfaces; the last of them moves because the discovery loop reads it as *where does this author live*, so a `Stay` silently empties a **different owner's** feed of that person's posts, with nothing for either party to see or fix.
>
> **Why they waited, and why waiting was not the same as being fine.** Every error above is **conservative** — a higher penalty, a more spam-suspicious profile, a duplicate rather than a silence — which is genuinely why the grant-shaped columns went first and is recorded here so the ordering is not read as an oversight. But conservative wrong data is still wrong data, and this class has a property the others do not: **the person it is charged to is not party to the ceremony at all.** They did not succeed, they cannot see the row, and no surface anywhere lets them appeal a reputation score inflated because someone who once reported them changed identity. That asymmetry is the argument for ruling them, and it is the transferable half: *ask who bears the error, not only which direction it runs.*
>
> ⚠ **Two mechanical facts this pass had to pay for, both already known and both worth stating where the ruling lives.** *(1)* A `SUCCESSION_REFERENCES` declaration is executed by **nothing**: the registry loop iterates `ACTOR_TABLES` only, so four of these six needed a hand-written leg on both paths, while `content_reports.reporter` and `feed_contributors.author_id` — being table entries — ride the loop for free. *(2)* Such a leg's **reconcile** arm is witnessed by no data-driven gate (the reconcile sweep covers `Move(MoveShape::Plain)` entries of `ACTOR_TABLES`), so both arms are pinned by hand and each was red-verified against the mutation that severs it. **Declared residual, stated rather than hidden:** on the reconcile a collision parks, and for the two counting tables a parked row *is* the duplicate the ruling exists to collapse — a backfilled reporter who had already re-reported under both identities still counts twice. Parking beats the alternatives (a bare `UPDATE` aborts the whole boot reconcile on the primary-key collision; deleting the loser destroys a user's own report), and the population is bounded to accounts succeeded before the leg existed.

> ⚠ **And one question this ruling deliberately does NOT settle, flagged so nobody closes it by accident.** `feed_contributors.author_id` carries `Policy::Purge`, which means deleting actor X removes rows from a **different owner's** feed — precisely the shape the in-scope-set blockquote above names as correctly *excluded* from the deletion registry. That is a deletion-axis question, not a succession one; it is carried to that axis's owner rather than answered here, and the entry deliberately **stays** in `ACTOR_TABLES` because re-filing it would change the deletion behaviour as a side effect of a succession ruling.

> **The MUA-facing bridge plane — the last twenty, which EMPTIES the backlog — and its shape is that ONE PLANE SPLITS INTO THREE by asking who the rows serve: the user, the bridge, or the record — ruled 2026-08-15 (backlog 20 → 0).** The twenty `bridge_*` tables read as one group because they share a prefix, and they are not one: **ten are the account's own resting content and move**, **four are key material a bridge fetches and burn**, **two are testimony about the theft and stay**, and the remaining four are a meter, two preferences and a notice, each ruled on the rule its own class already has. **The ten** — the IMAP placement/UID-window/subscription/tombstone four, and the CalDAV and CardDAV collection/item/tombstone threes — are the class rule at the top of this section applied literally: the mail bodies are `segment_records` rows that already move, every door here is `actor_id`-scoped, and the successor's MUA re-AUTHs to the **same address**, because the alias moved at the same ceremony. Left behind they are a mailbox, a calendar and an address book the successor can neither read nor delete while paying quota for them — user-irrecoverable data, so no burn was ever available, and unreachable from any client ([`nest/common.md`](../architecture/nest/common.md) § Client-state recoverability). ⚠ **They move as three per-protocol UNITS, not as ten independent verdicts**, and that is the transferable half: `ctag` / `highestmodseq` / `etag` / `uid_next` are one sync clock a protocol compares across a collection's tables, so a split verdict hands the successor's MUA counters that disagree with its contents. The tombstone logs are the sharpest case, because their `Stay` fails in the **resurrection** direction rather than the missing-data one — the items move, the tombstones do not, so a client syncing from its stored modseq is told about no removals and re-shows everything the account deleted. A left-behind tombstone is not inert residue; it is a deletion the user performed that the protocol never reports.

> **The four blobs burn, and this is the one place `actor_mls_pubkeys`' precedent must NOT be followed.** `bridge_wrapped_mls_blobs` and `bridge_wrapped_submission_tokens` wrap the MSEK under one MUA credential's secret; `bridge_mls_snapshot_blobs` and `bridge_webdav_keys_blobs` are sealed under the MSEK itself. All four derive from what the seed thief read, and all four are honoured by a consumer that never consults the refusal plane — the bridge fetch handlers run on a *bridge's* authenticated connection and take the target actor straight out of the request, so a superseded actor is as fetchable as any other. **`Move` is the actively dangerous direction here**, the third place on this axis where it is: the address moves to the successor at the ceremony, so a carried wrap makes the *thief's mail password* open the *successor's* mail — the `account_aliases` defect that started this whole axis, re-created one table over. **`Stay` is not the safe fallback**, on `eviction_tokens`' argument: the two credential-keyed tables' revoke doors refuse any target that is not the caller, and the two per-actor blobs have **no delete accessor at all**, so a left-behind row is unrevocable — for two of them by construction. What makes this a burn rather than the compromised-key-material `Stay` filed above is a single question: **is the row's PRESENCE load-bearing?** `actor_mls_pubkeys` stays because its presence is exactly what arms the `succession_pending` tempfail. Nothing reads the presence of these four (the one predicate that does is documented purely informational), and presence that arms nothing is standing authority. Nothing user-irrecoverable dies — the mail, calendars and contacts these blobs let a bridge *serve* are rows that move — so the alpha deletion carve-out is not engaged; the successor's client re-provisions under MSEK′, and this leg is the nest-side half that does not depend on the client ever running it.

> **The two bridge-reported logs stay, and the reason is sharper than ordinary attribution.** `bridge_audit_events` and `bridge_session_close_events` record that *this credential authenticated from this address at this time* — and on an account that is succeeding, the interesting rows are overwhelmingly the **thief's**. Re-pointing them would attribute the intrusion to the identity recovering from it, which is `bridge_service_users.approved_by_actor_id`'s argument verbatim. Both rulings are **conditional on their read side being dark**: the two wire kinds are write-only, their per-actor list functions have test callers only, and no list kind exists. ⚠ **Declared residual, and it is a surface question rather than a table one:** when that surface ships, it must reach the predecessor's rows *through the succession chain*, because the successor needs to read the evidence of their own theft without the record claiming they made it. **The remaining four:** `bridge_submission_quota` moves on the limits-move rule verbatim (a succession is self-service, so a relay cap a ceremony sheds is a cap with a reset button; one day inherited, zeroed at the next bucket rollover); `bridge_feed_subscriptions` and `bridge_search_policy` move as the owner's own curation, both otherwise stranded behind owner-scoped doors; and `bridge_restore_divergence` moves because it is a notice **about data** — every half of what it is about moves — recorded as unfalsifiable, since its `actor_id` has no production reader at all (the one consumer selects by `snapshot_id` and authorizes through the snapshot's owner).

> ⚠ **Two of the nine mutations settle what a green gate is worth for a BURN, and together they NARROW the finding rather than repeating it.** The measurement found that demoting all five `bluesky_*` burn rulings to `Unruled` left every test green, and drew the general rule *a `Burn`'s registry declaration is documentation; a `Move`'s is the executor*. **That rule held only where the table was feature-gated.** Graded against the hand-written leg these four shipped with, demoting all four burn declarations while the leg went on burning reddened the ceremony sweep immediately — and so did the opposite mutation, leaving the declarations in place while removing a table from the leg's own list. > **The floor roster's authorship column, and the first `Stay` on this axis that is NOT neutral — the pointer is resolved through, and it stays because the resolution fails closed — ruled 2026-09-11.** `channel_commit_watermark.last_commit_sender` (schema 64; [`conversation-rooms.md`](conversation-rooms.md) § The floor roster) landed as an actor-shaped column on a row that belongs to a *channel*, and the completeness walk caught it the same day — the third room-plane column to arrive without a ruling, after `rooms.owner_id`/`room_members.principal_id` (2026-09-09) and `room_generations.minted_by` (2026-09-10). This one fails that test — the roster-report door refuses a report at the newest commit's position from anyone but the stored sender — and is `Stay` regardless, because of *how* it resolves: by **equality with the authenticated reporter**. A retired identity is answered `superseded` at every handshake and its sockets are torn down inside the ceremony ([`identity-succession.md`](identity-succession.md) § Implementation status today, slice 3), so it equals nobody; a stale pointer therefore narrows the newest position to *no one* until the next commit rewrites the pair — which the succession's own propagation, two membership commits per group, add-successor and remove-old ([`succession-propagation.md`](succession-propagation.md) § Propagation), does in every room the owner holds. **The permissive reading the nullable column invites is wrong, and is stated here so nobody re-derives it:** the column admits a null because a row written before schema 64 names no sender, and the guard *fails open* on that residue — so `Clear` would not land the row in a handled state, it would reopen the newest position to every live member, the very defect the column was landed to close, on the one commit a succession is most sensitive about (in the theft case, plausibly the thief's own). `Move` is wrong twice: the successor did not send that commit and, as a new leaf (an MLS credential *is* the actor id), could not have; and until its add-successor commit lands it is not a live member of the stored floor, so the door's membership gate refuses it before authorship is ever consulted — the move would buy nothing and re-attribute a possibly thief-made commit to the identity recovering from it. No leg by construction, pinned anyway: `successions.rs::the_newest_commits_sender_stays_on_the_retired_identity` holds both fire points to the untouched pair, so a later `Clear`/`Move` reds a test instead of silently widening the guard.
