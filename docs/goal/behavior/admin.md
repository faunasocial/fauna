## Goal

The admin shell is the surface where a nest admin manages the nest itself: dashboard, **users** (the user-administration hub — the user list + invite-code minting + pending invite-request approval + direct admission of a known actor id, all framed around assigning a *tier*), tiers (definitions), aliases, mail policy, DNS, and the **Nest** page (nest-wide settings — NAT mode, the admin pairing toggle, the deployment-identity rotation ceremony, Factory Reset). Per the *Admin IA redesign* (2026-06-04, below), each remaining service control lives on its own feature page rather than a standalone "Services" toggle hub. The shell is reached via admin-only navigation entries (`admin_pages` in ui.yaml's `navigation` block); what "hidden from non-admin users" means is precisely that its **entry** is hidden — see § Navigation model point 1 for the one gate, and § Entry-level, never content-level for why the shell's *content* is not gated a second time. Every page within the shell exposes a unified `admin-nav-back` button that **exits the admin shell, returning to the non-admin app** (it is the "leave admin" affordance, *not* an inter-admin-page jump — switching between admin pages is the shell's own switcher; see § Navigation model), and each shell page's heading uses a per-page heading ID (`admin-dashboard-heading`, `admin-users-heading`, etc.).

This doc covers the shell + its pages as one user journey because they share the admin shell, the gating "is admin" check, and several cross-cutting concerns (the user-admission lifecycle on `admin-users`, users ↔ aliases ↔ eviction).

## Layout & flow

### Shell

- Admin pages are listed in `navigation.admin_pages` in ui.yaml: `admin-dashboard`, `admin-users`, `admin-settings` (nav label "Tiers"), `admin-nest`, `admin-mail`, `admin-calendar`, `admin-contacts`, `admin-files`, `admin-aliases`. (`admin-services` was removed and `admin-nest` added 2026-06-04 — § Admin IA redesign. `admin-calendar` was added 2026-06-17 — § 8 Calendar, the CalDAV-enable sibling of `admin-mail`. `admin-contacts` was added 2026-07-06 — § Contacts, the CardDAV-enable sibling of `admin-calendar`. `admin-files` was added 2026-07-08 — § Files, the WebDAV-enable sibling of `admin-contacts`. `admin-invite-requests` was retired 2026-05-29 — its pending-request rows are now the "Pending requests" section of `admin-users`.)
- Visibility gated on the user's admin role; non-admins do not see admin entries. The gate is computed by an `am-i-admin` server check (shared Rust, single source of truth).
- Entry points: the canonical gated entry is **`admin-tab`** — a single admin nav entry shown only when `am-i-admin` passes (a sidebar/tab row on desktop — web / linux / windows / macos / tui — and the idiomatic in-Settings entry on mobile — ios / android). It is declared in ui.yaml `navigation.gated_tabs` and is **lint-enforced across all 7 apps** (`scripts/lint-ui-elements.py --nav`, run via `just ui-lint` — advisory today, not wired into any merge gate, per `../architecture/merge-gates.md` § CI enforcement); genuine per-platform absences are declared in `navigation.nav_exceptions` with a reason + owner (so the gap is explicit, never silent). A secondary convenience link from the Status/Settings page to `/app/admin/` may *additionally* surface when the gate passes, but it does **not** substitute for the `admin-tab` nav entry. Both are gated by the same `am-i-admin` result.
- Every admin page carries an `admin-nav-back` button that **leaves the admin shell back to the non-admin app** (see § Navigation model).
- Linux note (from ui.yaml `navigation.layouts.desktop.notes.linux`): "Admin row hidden until confirmed".

### Navigation model (canonical — ratified 2026-06-01)

All seven apps use **one** admin navigation model: a **distinct admin shell** you enter and exit, *not* a set of admin pages flattened into the main app navigation. Concretely:

1. **Gated entry — `admin-tab`.** A single admin entry (`admin-tab` / admin sidebar row / "Nest Admin" link), shown only when the shared `am-i-admin` gate passes, opens the admin shell. The shell is a section the admin steps *into*; the normal app navigation is not cluttered with per-admin-page entries. **What that entry lands on — the Dashboard, never the sub-page a previous visit left open — is the cross-shell canonical-entry rule owned by [`../ui/README.md`](../ui/README.md) § Navigation model** (ratified 2026-08-13); it binds this shell and the Settings shell identically, so it is stated once there rather than twice here.
2. **Internal switcher — a vertical sidebar-swap on desktop; idiomatic on mobile.** Inside the shell, the admin pages (dashboard, users, settings, services, mail, aliases, plus the contextual detail pages `admin-dns` / `admin-bridges-pending`) are switched by a **vertical nav rail that replaces the main app sidebar in place** while the admin view shows: entering admin swaps the normal nav (conversations / feed / …) for the admin pages in the *same* sidebar slot — no second rail, no horizontal sub-tab bar, no separate window — and `admin-nav-back` (step 3) swaps it back. This is **one uniform shape on every desktop app** (web / windows / macos / linux), adopted 2026-06-03 to replace the former per-platform **horizontal** switchers, whose summed-tab width forced the whole window wider than the screen. Mobile (ios / android) keeps its platform-idiomatic nav (drawer / Compose routes) — there is no persistent sidebar to swap; the tui renders the admin sub-page rail atop the shell (its settings-shell pattern), the terminal-idiomatic equivalent of the sidebar-swap. The *page set* and *IDs* are uniform across all seven apps; only the per-platform nav widget differs. (This supersedes the prior "internal switcher is platform-idiomatic / allowed-divergence" rule — desktop is now uniform, a priority-#1 tightening.)
3. **Uniform exit — `admin-nav-back`.** Every admin page exposes `admin-nav-back`, which **exits the shell and returns to the non-admin app's primary view** (the main view, e.g. Conversations — the same landing as `settings-nav-back`; see `settings.md` § Navigation model). It is the single "leave admin" affordance. It is **not** an inter-admin-page jump and **not** "back to the admin dashboard" — switching among admin pages is step 2's switcher. **It lands on the primary view, not the Settings shell** (corrected 2026-06-07, user): admin is a top-level nav peer reached via the `admin_pages` nav entry, not nested under Settings, so exiting it parallels `settings-nav-back` (both "leave shell" affordances return to the main view) rather than chaining admin → settings → main. Apps must not rely solely on the main sidebar/tab-bar to leave admin; the in-shell `admin-nav-back` is required so the affordance is uniform and testable (`tests/e2e-unified/tests/test_admin_nav.py`).

#### Entry-level, never content-level (ratified 2026-09-09)

**The `am-i-admin` gate is on the nav ENTRY (point 1) and nowhere else. An app must NOT additionally gate the admin shell's *content* on the same check.** Once a page inside the shell is reached — by the gated entry, by a deep link, by a crash-recovery nav-stack restore, or by the e2e state protocol — it renders. This is one shape on all 7 apps: linux's "admin" content-stack child is built regardless of `is_admin` (only `show_admin_sidebar_row` reads it), tui gates only the visible sidebar set, windows gates the entry in `MainPage` and not `AdminShellPage`, and web's `admin/+layout.svelte` renders its children behind the authentication check alone.

Two reasons it is stated as a rule rather than left to each app:

- **The gate is not the security boundary — the nest is.** Every admin kind is `require_admin` server-side (`bins/fauna-nest/src/admin_ws_handlers.rs`), so a non-admin who reaches an admin page gets a *rejection to render*, not privileged data. A content-level gate therefore buys no safety; it only decides whether the user sees the refusal or a blank redirect.
- **Rendering the refusal is the required behavior.** Every admin page carries `error-message` and must surface its failed fetch there (`../architecture/e2e-conventions.md` convention 2); `tests/e2e-unified/tests/test_admin_error_surfacing.py` asserts exactly that on every app by force-navigating a **non-admin** to `admin-bridges-pending` / `admin-dns`. An app that redirects the non-admin away has no page left to surface anything, so it cannot satisfy the convention.

**Web carried the one deviation and it is closed (2026-09-09).** `apps/fauna-web/src/routes/admin/+layout.svelte` re-ran `checkIsAdmin` in its own `onMount` and `goto('/app/settings')` on a negative, unmounting every admin child page before it rendered — never described by this doc, and the sole cause of `test_admin_error_surfacing.py[web]` (both params) being red from 2026-08-16. Removed in favour of the root layout's single `userIsAdmin` nav gate. A consequence worth knowing when reading web tests: `tests/e2e-unified/tests/test_feed_manager_nest_switch_web.py` used that bounce as its "the RPC resolved" observable and now waits on the admin dashboard's own `error-message` instead (same `getClient()` path, via `fauna.admin.stats`).

**Reference implementation:** **linux** (`apps/fauna-linux/src/views/admin.rs` + `app.rs`, 2026-06-03) — the admin sub-stack is the content (the main content-stack's "admin" child); a shared `build_nav_rail` icon rail (`views/nav_rail.rs`, also used by the Settings shell — `settings.md` § Navigation model; with `admin-nav-back` on top) is swapped into the `OverlaySplitView` sidebar slot via the **content-stack's visible-child notify** (so it fires for the sidebar Admin row, the test agent's name-based nav, and Ctrl+<n> alike, always keeping `admin-nav-back` visible); `admin-nav-back` → the primary view (Conversations), mirroring `settings-nav-back` (`settings.md` § Navigation model). web (`apps/fauna-web/src/routes/admin/+layout.svelte`, 2026-06-03) is the second reference: the admin `+layout.svelte` renders its own shell whose vertical rail (`admin-nav-back` atop, then the page links) takes over the app's sidebar slot, while the root layout (`routes/+layout.svelte`) yields the full viewport for any `/app/admin` route — the same bare-canvas bypass it uses for onboarding — so the normal nav is replaced in place; web's `admin-nav-back` lands on the primary view (`/app/conversations`, 2026-06-08), mirroring `settings-nav-back` (the 2026-06-07 correction). The other desktop apps converge on this model (see § Implementation status — navigation, below).

### Admin IA redesign — per-page service toggles (RATIFIED 2026-06-04, research-backed)

**Supersedes the "Services hub" model in § 5 and the "Settings" naming in § 3 below; those sections are being restructured to match — built on **linux** 2026-06-04 (tracked internally); web/windows/macos/ios/android lift it via per-app follow-ups (tracked internally; see § N Nest § Implementation status).** User-ratified 2026-06-04: there is **no standalone `admin-services` page**. Each service's enable control lives on its feature page; the genuinely nest-wide settings get a dedicated **Nest** page. The page set becomes: Dashboard, Users, **Tiers** (was "Settings"), **Nest** (new), Mail, Aliases, + the contextual `admin-dns` / `admin-bridges-pending` / `admin-logs`.

Resolved by reading the nest's flag consumption (`bins/fauna-nest/src`):

- **`bridge` service flag is vestigial — dropped.** `fauna.admin.services.update name="bridge"` only writes `services.json`; **nothing gates behavior on it**. The real mail on/off is `fauna.bridges.set_mail_enabled` (`bridge_blob_handlers.rs:1213`) — it writes the DB, the `/data/imap-enabled` flag file, drives the s6 supervisor, and gates MTA/MDA startup (`mail_enable.rs`). So mail enable/disable is **just `admin-mail-enabled-toggle` on the Mail page** (already built); the Services `bridge` toggle is removed, not relocated.
- **`algorithm` service flag — dropped from the UI (no admin home).** When the toggle was dropped the flag was *not* literally unread: it gated the `fauna-algorithm` s6 sidecar, which the image's service watcher reconciled from `services.json`'s `algorithm` flag. But that sidecar was **service-to-service residue** — no Fauna app called it and the feed never consulted it, so toggling `algorithm` produced **zero user-visible behavior**; with no app consumer it had no feature-page or Nest-page home, and the toggle was removed. The sidecar itself was removed 2026-10-01 ([`../architecture/core-client-kind-catalog.md`](../architecture/core-client-kind-catalog.md) § Algorithm & Reputation), and the flag left with it (2026-10-02): `fauna.admin.services.list` no longer carries it, `fauna.admin.services.update` refuses the name as `invalid_params` like any unknown service, and a `services.json` still holding the key loads with the key ignored (a genuine algorithm feature would design its own control).
- **`dns` toggle** (the "Fauna controls DNS" master switch — not a nest flag, it's the `DnsManagementMachine` `all_managed` projection) moves to the **`admin-dns`** page (which already has the "Manage DNS" entry point).
- **`pairing` flag is LIVE** — it gates `fauna.pair.add` (`pair_handlers.rs:148`). It's the one homeless toggle and moves to the new **Nest** page.

### 2. Users (`admin-users`) — the user-administration hub

The single surface for the whole user-admission lifecycle. A nest admin admits a user three ways — approving a pending invite *request*, pre-minting an invite *code* the user types during onboarding, or admitting a known actor id directly — and in all three the admin's real choice is the **tier** (the tier *is* the quota: `AdminTier` caps `max_inbox_bytes` / `max_storage_bytes` / `max_devices` / `max_blob_size` / `max_feeds`; there is no per-user quota override). Setting the nest's registration posture is the same mental model one level up — "may anyone let *themselves* on?" — so it lives here too, and the page is **five sections**:

- Heading: `admin-users-heading`. Back: `admin-nav-back`. Errors: `admin-users-action-error`.

**Section 1 — Pending requests (`admin-users-requests-section`).** Folds in the former `admin-invite-requests` page. Pending invite requests submitted by users from `onboarding.invite_request`, rendered via the indexed `admin-invite-requests-list` component: `invite-request-row-actor` / `-handle` / `-message`, a per-row tier picker `invite-request-row-tier-select` (the tier to admit at), and `invite-request-row-approve-button` / `-deny-button` / `-deny-reason-field`. Approve admits the requester at the chosen tier (creating the account + deleting the request); deny attaches the optional reason. Approve **re-validates the stored handle at mint time**, not just at submission — format, reserved-handle-list membership, and not-since-taken by another actor — so a request can fail approval (surfaced via `admin-users-action-error`) and **stays `pending`** rather than being silently admitted or dropped; the admin retries (a different tier/label doesn't change the handle) or falls back to deny. The requester's onboarding poll picks up the decision (cross-page invariant, § Architectural rules 5) — **deny** directly from the persistent denied row; **approve** as *admission*: the row is gone, so the requester's machine runs its registered-probe on the `not_found` and advances to login (mechanism owner: `onboarding.md` § The pending-invite surface — until that lands, the shipped requester side mis-renders an approval as a terminal not-found error; see its § Implementation status today).

A **denied** row is not permanent: the nest prunes `denied` requests whose deny decision is older than 90 days, via a periodic background sweep — `pending` rows are never touched by age (only an admin's approve/deny action, or the nest-wide `MAX_PENDING_INVITE_REQUESTS` pending-row cap, governs those). Pruning clears the nest's one-row-per-actor block with no admin or app action, so a long-denied actor eventually becomes resubmittable even without walking the client-side cancel-then-resubmit path (`onboarding.md` § The pending-invite surface).

**Section 2 — Registration (`admin-users-registration-section`).** The nest's registration posture — who, if anyone, may create an account without the admin. A mode `select` (`admin-users-registration-mode-select`: open / invite required / closed) plus the **orthogonal** free-tier ceiling `admin-users-max-free-users-input` (a cap on free-tier accounts that applies *regardless* of mode; blank = no cap), saved together by `admin-users-registration-save-button` — one save, one kind: `fauna.admin.set_registration_mode { mode, max_free_users }` (Admin-class), which upserts the `nest_registration_mode` singleton and swaps the live value (no restart). Read back on `fauna.setup.status`. Owner of the posture semantics: [`../architecture/nest/public-mode.md`](../architecture/nest/public-mode.md) § Registration Modes.

The mode gates **registration only, never authentication** — closing registration must not lock out existing users, and `open` still admits nobody who hasn't registered (there is no auto-registration: an actor with no account is refused in every mode). `closed` is the default on a fresh nest, and it does not disable the **admin-driven** admission path: an admin can always approve a pending request (approval never rides the registration endpoint). Invite-*code* redemption, by contrast, is self-service and rides the mode: a code admits under `open`/`invite_required` and is refused under `closed` — anything else would collapse `closed` into `invite_required` (`public-mode.md` § Registration Modes owns the semantics; drift corrected 2026-07-22 — this sentence previously claimed code redemption worked under `closed`, which the code has never done and which the mode enum's own unrepresentability rationale forbids). Minting under `closed` is still allowed — the code becomes redeemable when the mode changes, and it remains consumable as a tier-upgrade token by an existing user in any mode.

*Target state (ratified 2026-08-22; element ID user-approved 2026-09-25, tui lead in flight):* the Registration section also gains the age require-knob — **"accept only signups carrying app age verification"**, default off — beside the mode select; semantics owned by `public-mode.md` § Registration Modes → *Age at registration* (band model: [`family-safety.md`](family-safety.md) § The account age band). Its element ID is `admin-users-registration-age-verification-toggle`, read back from `fauna.setup.status` and **saved by the section's `admin-users-registration-save-button`** — the save dispatches `fauna.admin.set_age_verification_required` beside `set_registration_mode`, only when the toggle's value changed, so the section keeps its one-gesture shape (the surface rules are the owner's: family-safety.md § App surface → *Age-band surfaces*).

**Section 3 — Admit (`admin-users-admit-section`, user-approved 2026-08-15).** Direct admission — the third account-creation path alongside invite-request approval and invite-code redemption, `fauna.admin.users.create` (`../architecture/nest/public-mode.md` § Registration & Identity owns the mechanism + the handle-less shape; not restated here). The admin types the actor id (`admin-users-admit-actor-input`, 64 hex chars — a malformed id is a local `admin-users-action-error` hint, nothing dispatched), names the handle the actor is admitted under (`admin-users-admit-handle-input` — the admit moment is the only place a handle is *named*; `fauna.admin.users.clear_handle` can later only *strip* a handle, never rename one, and has no admin UI of its own yet), and picks a tier (`admin-users-admit-tier-select` — admission is always choosing a tier, same as the other two paths). `admin-users-admit-button` dispatches `AdminClient::users_create`. A **deliberately blank handle** admits the handle-less state (`public-mode.md` § *A handle-less account*): the account registers and authenticates normally but cannot send from any deployment-domain `From:`, and — since a handle can only be *cleared*, never set or renamed after admission, and a registered actor cannot reach `fauna.account.register` to claim one itself — there is today no path back to a handle once admitted without one. *Implementation status:* built on **tui** (2026-08-15, the lead app — `apps/fauna-tui/src/admin/users.rs::admit_section`; **The inbox byte counter — a refund repays exactly its charge (ratified 2026-09-25).** The tier's `max_inbox_bytes` binds through one per-user counter, `users.inbox_bytes_used`: a delivery charged against the quota adds its envelope's length when it lands and the recipient's ack subtracts it again, and the nest refuses a charged delivery that would push the counter past the tier cap. **An ack refunds exactly what that envelope's delivery charged — never more, and nothing for an envelope delivered uncharged.** The delivery link records its own charge (`0` when uncharged) and the ack reads that record, so the refund never depends on re-measuring the envelope. The rule exists because the nest has uncharged inbox writers (security notices, subscription welcomes, and every writer when tier quotas are not enforced): an ack that refunded every envelope's size let each acked uncharged envelope deflate the counter below the recipient's charged, still-pending bytes, and the cap stopped binding. Under enforced quotas every principal-driven delivery — `inbox.deliver`, the MLS Welcome on both its same-nest and federation legs, room invitations — is checked against the quota and charged. A link recording no charge refunds nothing. Pinned by `bins/fauna-nest/src/db/mod.rs` (`acking_an_uncharged_row_refunds_nothing`, `the_ack_refunds_the_recorded_charge_and_nothing_without_one`).

#### Cutting a user off — eviction and suspension (ratified 2026-07-09)

There is **one** cut-off state, `suspended`, and **one** writer of it: the eviction state machine. The admin reaches that state two ways, and leaves it one way.

- **Evict** (`admin-users-evict-button` → `fauna.admin.users.evict`) starts the *timed* ladder: `warning` → (after the warning window) `suspended` → (after the suspension window) **deleted**. It is the "your account is going away" path. **The two windows are hard-coded constants, not an admin choice** — `fauna_protocol::node_policy::EVICTION_{WARNING,SUSPENSION}_DAYS`, both `14` (bucket (1) of the one-configuration-surface invariant: no app surfaces a control for them, so they are a Rust constant, never a knob). They are echoed to the user's client on `fauna.account.get` (`AccountNodePolicy`) so it can render the eviction-warning countdown (*The member is told*, below). **The deletion step is the ordinary account deletion (built 2026-09-27):** when the suspension window runs out the account enters `deleting`, and the eviction worker finalizes it through the same path an admin deletion takes, called directly: the post retraction, every per-actor leg and the purge walk over the account's local predecessors (owner [`../architecture/account-data-plane.md`](../architecture/account-data-plane.md) § Nest-side requirements item 1). It is never a pending action, whose delay would stretch the hard-coded windows and whose self-deletion arm would let the evicted user block the deletion by owning a room. The finalize's refusals still hold: an account that acquired the admin role, or guards supervised accounts, stays `deleting`, still cut off and with its data intact, and completes on the first tick after the role is removed or the links are resolved. The deletion is audited (`eviction.delete`).
- **Suspend** (`admin-users-suspend-button` → `fauna.admin.users.suspend`) enters the **same `suspended` state immediately**, with **no delete timeline** (`eviction_delete_at` stays null, so the ladder never advances to deletion). It is the "stop this account *now*" path — the abuse-in-progress response the timed ladder cannot serve.
- **Restore** (`admin-users-cancel-eviction-button` → `fauna.admin.users.cancel_eviction`) clears the state from *either* entry point, returning the user to normal with **no client-side recovery step and no re-onboarding**: same actor, same keys, same handle, same data, same tier. It is refused once the ladder has reached `deleting`, because the deletion has begun and a restore landing between its steps would hand back a half-reclaimed account. The row then offers no restore control (`fauna_client_admin::admin_user_row_controls`).

Suspending a user who is **mid-eviction** (still in `warning`) promotes them to `suspended` at once and **clears the pending delete timeline** — erring away from deletion, per the iron-clad *no user-data loss* invariant. The admin re-runs evict to schedule deletion. A suspended user is listed by `fauna.admin.evictions.list` with a null `delete_at`, which is what makes their row offer the restore control.

**The member is told — the eviction warning is a critical alert (ruled 2026-10-01; the app half unbuilt).** An eviction its target never hears of makes the warning phase an export window they cannot know to use. So for as long as an eviction stands in `warning`, the member's own app shows it on every page as a critical alert ([`critical-alerts.md`](critical-alerts.md) § Feeders, key `eviction:<actor_id>`): its lines give the date access ends, the date the account and its data are deleted, the admin's stated reason when there is one, and that everything can be exported until access ends — the export itself is the member's ordinary export page, since a `critical-alert` row is text. The alert is raised from the member's own `fauna.account.get` (`AccountEviction` beside `AccountNodePolicy`), which the nest already serves and re-announces with an `AccountUpdated` push on every change; it clears when a later read carries no eviction, and like every critical alert it cannot be dismissed while the eviction stands. It adds no element ID — the banner is the existing `critical-alerts` / `critical-alert` pair. *Why it clears that doc's severity bar:* the ladder ends in the deletion of data the member cannot recreate, the only remedy (export, or persuading the admin) is the member's own, the condition lasts two weeks, and nothing else in the product says a word — while the admin's own confirm text promises that the member "will be warned". A direct suspension is not this alert's: it carries no deletion timeline and leaves no signed-in member to warn, and its surface is the sign-in-refused launch page (below). *Implementation status today (2026-10-01):* the nest half is built — the record on `fauna.account.get`, the push at start, at cancel and at the move to `suspended`; no app reads its own account's eviction record, no feeder exists and no string says any of it, so today an evicted member is told nothing until sign-in is refused, when the export window has already closed. Tracked internally.

**What suspension prevents.** A suspended actor has **no caller class**, so it can dispatch **no** WS-RPC kind — not `User`-class, not anything, reads included. This is enforced at **dispatch** (`caller_class_for_actor`, re-read on every RPC), not merely at token mint, so it takes effect on a connection the user already holds, and it holds identically on an **open-registration** nest, whose auth handshake does not otherwise consult `users.suspended`. Suspension additionally revokes the actor's tokens, so no new connection authenticates, **and closes the connections it already holds** with WS 4401 — otherwise the socket stayed up feeding a suspended user their Push stream in real time, which the per-RPC dispatch gate does not cover (mechanism: [`../architecture/transport.md`](../architecture/transport.md) § Connection lifecycle → *Revocation teardown*). It is a **control, not a label**.

Denying *reads* too is deliberate and is what a private nest has always done — `check_actor_active` refuses a suspended actor authentication outright, so it could never read. Uniform denial makes suspension one rule with no read/write axis to get wrong across ~45 handler families. It does not cost the user their data (§ Product invariants, *User always controls their data*): the eviction ladder's **`warning` phase is the export window** — full access, for the whole warning period, before `suspended` is ever entered — and `suspend` itself schedules no deletion, so nothing is lost while the admin and user sort it out.

**Suspension is temporary and reversible by design** — which is what makes it safe to be this total. Because the only exit is a client-reachable button, an admin can never strand a user in a state that needs shell access to undo (`../architecture/nest/common.md` § Client-state recoverability). What the suspended user's own app shows — the sign-in-refused launch surface, with Retry as the way back in once restored — is owned by [`onboarding.md`](onboarding.md) § App-launch routing → *the previously-signed-in row*. A suspended user cannot re-admit *themselves* either: both registration doors (`fauna.account.invite_request.submit`, `fauna.account.register`) refuse an actor that already holds a `users` row as already registered, suspended or not — the wire ruling and its bounded disclosure are [`login.md`](login.md) § Errors — so Restore is the one way back for admin and user alike.

**An admin cannot be suspended, evicted, or deleted** (`fauna.admin.conflict`; `fauna.account.admin_role_held` on self-delete). A suspended admin loses admin dispatch too, so a suspended *sole* admin could never be restored by anyone — an off-box brick. Rather than detect-and-repair, the state is made unrepresentable: remove the admin role first (`fauna.admin.admins.remove`, itself guarded so the last superadmin cannot be removed), then suspend, evict, or delete the now-plain user. Evicting an account that *guards* a supervised user stays blocked on its own gate ([`family-safety.md`](family-safety.md) § Lifecycle gates). A user's *own* deletion is also refused while they own a community room another member could take over, and an admin's deletion of such a user is not ([`conversation-rooms.md`](conversation-rooms.md) § Roles and authorization, *An owner's account deletion*).

**The last-superadmin guard is a floor at the writer, not only a door check (ratified 2026-08-14).** The schedule-time refusal alone could not hold it: `admins.remove` is a 24 h-delayed quorum action, so the roster state a removal is admitted against is not the roster state it executes against — and a zero-superadmin box cannot invoke `fauna.admin.factory_reset` (admin-gated) and cannot be re-claimed (code file consumed), the exact off-box brick this section forbids. Three layers now hold the floor, one authoritative: **(1)** `CacheDb::remove_admin_actor` and `set_admin_role` — the only writers that can shrink the superadmin set (the succession ceremony *moves* the role inside one transaction and never crosses the floor) — refuse, atomically with the write itself, any mutation that would leave zero superadmins; **(2)** the pending-action executor parks a floor-refused removal or demotion as pending-and-retryable (the `admin.add` arm's registered-user posture — adding another superadmin unblocks it; a target already gone completes idempotently instead), the demotion arm included because a persisted action can outlive the upgrade that adds its door; **(3)** the scheduling door's synchronous `fauna.admin.conflict` is **target-aware**: removing a *non-superadmin* admin is legal regardless of the superadmin count, removing the last superadmin still refuses immediately. A **reservation count** at the door (refusing to schedule removals that could over-drain the roster) was considered and **declined**: pending actions can expire unapproved or be cancelled, so the door cannot know which will execute — with the writer-level floor, over-issuing is harmless, the excess removal parking until the roster can afford it.

**Symmetrically, an actor that is not a registered user cannot be *made* an admin.** `fauna.admin.admins.add` refuses a target holding no `users` row — at the door, and again in the pending-action executor, since a queued action can outlive the upgrade that added the door and the target's row can be deleted inside the action's delay window. `admin_actor_ids` is a table that neither user-creation nor user-deletion touches, so without this guard the roster could name an actor owning no account: an admin invisible to every guard on this page (they all reason over `users`), yet still resolving to `Admin` at dispatch. Together with the deletion refusals above, this is what makes `Admin ⊇ User` hold at **both ends of the role's life** ([`../architecture/api-layers.md`](../architecture/api-layers.md) § `Admin ⊇ User`). **A retired identity counts as unregistered for this purpose (2026-09-27).** A key that was succeeded keeps a handle-less `users` row until its successor is deleted ([`identity-succession.md`](identity-succession.md) § Enforcement on the home nest), so the row check alone would grant the role to a key that can never sign in again: dead weight in `admin_count` and in the removal quorum's eligible roster, approvals it can never give. Both the door and the executor therefore also refuse a target the succession table names as succeeded (`auth_core::successor_of`); the executor re-checks because a recovery can run inside the action's delay window. The role belongs on the successor, which is where the succession ceremony itself moves it. **Deletion guards the whole local chain the same way.** Deleting an account takes its local predecessors with it (their `admin_actor_ids` rows purged, their `users` rows deleted — [`../architecture/account-data-plane.md`](../architecture/account-data-plane.md) § Nest-side requirements item 1), so the admin-deletion refusals above cover every local predecessor as well as the account itself — at both deletion doors and again in `finalize_user_deletion`. Without that, a predecessor's admin row, which a grant made before the retired-key refusal existed may still hold, would leave without `admin.remove`'s quorum or the superadmin floor, and if it was the last superadmin the nest would be left administrable by nobody.

**Deletion is guarded for a stricter reason than suspension**, and on both doors (`fauna.admin.users.delete` and the user's own `fauna.account.delete`) plus the executor that finalizes them. Suspension is reversible; deletion is not, and it drops the actor's `users` row while leaving the admin role untouched — so an admin who is deleted keeps a role nobody can exercise, on a box that still reports **claimed** (the claim gate keys on an admin row existing, not on a user row) and whose only admin can no longer authenticate. Because a *sole* superadmin cannot demote themselves either, their exit from the nest is **`fauna.admin.factory_reset`** — the universal recovery floor ([`../architecture/nest/common.md`](../architecture/nest/common.md) § Client-state recoverability), which is itself client-driven. The finalize step refuses an actor still holding the role rather than stripping it, because a persisted pending action can outlive the upgrade that added the door guards, and silently returning a *populated* nest to fresh/unclaimed would let any stranger who reaches it claim the box and inherit the existing users' data.

**Not a moderation verdict.** Suspension is an account-lifecycle power, not a content one — it carries an eviction `category` (terms / capacity / legal / abuse / other) and free-text reason for the audit log, and nothing else. Per-post and per-actor content decisions live in [`moderation.md`](moderation.md).

**What identifies a user in an admin picker: the handle (ratified 2026-08-30).** Wherever an admin page offers a pick-a-user control — the admission guardian pickers above, the DNS catch-all + role-address pickers ([`dns-management.md`](dns-management.md) § Detail page), and the web apex picker (§ 7 Web) — the option a human distinguishes and the value the code binds is the account's **handle** (unique on the nest by construction), falling back to the **full actor hex** for a handle-less legacy account (also unique, never empty). The display **label is never a picker identity**: labels are freely editable (`fauna.admin.users.update`) and non-unique, so two accounts labelled `Alex` would silently bind first-match — the same silent-wrong-binding class as the 2026-07-24 raw-actor-hex picker defect ([`family-safety.md`](family-safety.md) § Implementation status today, the tui row), and uniquely unrecoverable on the guardian pickers because supervision is set only at admission. **The rule has two halves, and binding alone does not satisfy it.** An app that binds the selection to the actor id directly (an index-aligned option table — linux, android, windows, apple's DNS catch-all/role-address/web-apex pickers) satisfies the *binding* half regardless of what the option displays, but still owes the *distinguishing* half: the text it shows must be the handle/hex pair too, or a human picking between two same-labelled accounts cannot tell them apart even though the code would bind whichever row they click correctly. A string-round-tripping picker (tui, web, apple's admission guardian picker — the odd one out among apple's own picker families, `Picker(selection:)` tagged by `vm.guardianLabel(user)` rather than by actor id) has no such slack — its option texts must be injective by construction, which for it *is* the binding mechanism. Both halves are the one shared function, `fauna_client_admin::admin_picker_option` (the cross-app owner; tui's own `picker_option` delegates to it), shared by all three resolvers so they cannot drift apart again. **Landed:** tui (2026-08-30, closing a window where the DNS catch-all/role-address and web apex pickers had briefly resolved by the raw label after this rule was ratified); linux, android and web display it on all three picker families (2026-09-01 — before this, all three index-aligned/round-tripping apps bound correctly but displayed the raw label on the DNS catch-all/role-address and web apex families, having only ever fixed the guardian pickers); apple joined 2026-09-02, calling the same shared `admin_picker_option` through its generated FFI face rather than the family's own hand-rolled guardian-picker copy; windows joined 2026-09-07 for the DNS catch-all, role-address and web apex families, and its admission guardian pickers (`AdminUsersViewModel`/`AdminUsersPage`) followed 2026-09-09 — all four families now route through one internal `AdminActorOptions.Label` entry point in `FaunaApp.Core` (`AdminDnsPage` is WinUI code-behind with no VM seam otherwise, so this doubles as the two-same-label injectivity pin's home). All 7 apps now satisfy both halves on every picker family named above, apple's admission guardian picker included (2026-09-13, closing the one hand-rolled copy of the handle/hex-fallback logic that had stood apart from the shared function). The wire carries the handle per row as `AdminUser.handle` (additive 2026-08-30; `None` from a nest predating the field — the hex fallback covers it). The e2e action layer selects by whatever text a picker displays, which happens to equal the handle for every fixture's seeded admin (§ State & data shape: label defaults to handle at registration, and no e2e fixture edits it) — not because the harness treats handle specially. **Which accounts a picker offers: every account on the nest (2026-09-15).** Each picker family above offers every account on the nest — the DNS catch-all, role-address and web apex pickers every account, the guardian pickers every non-suspended one — read through the one shared `fauna_client_admin::users_list_all` (§ Where logic lives). Nothing told the admin the list was cut off. A search-backed picker for very large nests is not designed; paging to the list's `total` is the shape until one is. **Landed:** tui, linux and web (2026-09-15), proven by `tests/e2e-unified/tests/test_admin_picker_all_accounts.py` on a nest whose box claimer is older than every account on the default page; apple joined the same day — the DNS catch-all/role-address, web apex and both guardian pickers now share the one `FfiAdminClient.usersListAll()` FaunaKit read, proven green `--app macos,ios` (6/6); android joined the same day too — the DNS catch-all/role-address, web apex and both guardian pickers now share the one `ApiClient.adminUsersListAll()` Kotlin read over the same UniFFI face, compile-verified plus a Robolectric pin that each picker's option source is the all-accounts read, `--client android` e2e host-gated; windows joined the same day too — the DNS catch-all/role-address and web apex pickers now read `INestRpcClient.AdminUsersListAllAsync()` over the same `FfiAdminClient.UsersListAll()` face, and both guardian pickers read a separate `AdminUsersViewModel.GuardianCandidates` list kept apart from the paginated Users page, proven green `--app windows` (3/3) — closing it also fixed a windows FlaUI-bridge gap where `Select()` could never reach an option realized only after scrolling a large virtualized ComboBox popup (`tests/e2e-unified/flaui-bridge/Actions.cs`), which blocked the box-claimer pick regardless of retry duration. **All 7 apps now read every account through this shared helper — no picker family on any app pages `fauna.admin.users.list` for its options.**

**Held-for-friends backups reuse this lifecycle unchanged (ratified 2026-06-14).** A user who "holds a backup for a friend" admits that friend through this same admission lifecycle — approve their invite *request* or mint them an invite *code* — choosing a storage-only **`backup` tier** (`max_inbox_bytes = 0`, `max_feeds = 0`, `max_storage_bytes` = the offered space). The admitted guest is a handle-less `users` row (no inbox / MX / feeds) that can only own reserved folders and consume storage against the `backup` tier; their backup chunks are sealed under *their own* `BackupKey`, opaque to this nest. "Stop hosting" is the existing per-row eviction (`admin-users-evict-button`); **promoting a backup-guest to a full member later** is the existing `admin-users-tier-select` tier change (`fauna.admin.users.update`) — the account already exists, so it is a one-field change (no consent gate — `plaintext_mode_consent` is retired without replacement: no-modes, [`../architecture/nest/storage-modes.md`](../architecture/nest/storage-modes.md)). This adds **no** new admin IDs and **no** new authorization primitive — the `backup` tier is one more `tiers` row. Full design: [`backup-destinations.md`](backup-destinations.md) § State & data shape → *Held-for-friends enrollment*. **Implementation status (2026-06-16):** the `backup` seed tier landed (`db/migrations.rs` `SEED_TIERS`), and "stop hosting" now reclaims the evicted guest's space (every user-deletion path drops the actor's folders + `backup_custody` so GC reclaims their chunks — previously orphaned). ⚠ Until 2026-09-27 that did not hold for the eviction ladder itself: its deletion step deleted the `users` row inline and never reached the folder leg. It now runs the shared finalize (§ Cutting a user off above), pinned for an evicted `backup`-tier guest by `eviction::tests::an_evicted_account_is_finalized_through_the_purge_walk`. **Storage enforcement (2026-06-16):** the tier caps the admin chooses are now enforced for **both** `max_inbox_bytes` (the inbox-quota gate) **and** `max_storage_bytes` — `users.storage_bytes_used` is written and enforced uniformly for every tier by the client manifest-record / backup-custody paths (an over-cap record is rejected with `fauna.sync.storage_quota_exceeded`; supersede / delete credit bytes back). ⚠ **"Hard bound" holds for the `backup`/custody plane this sentence was written for, and NOT for the ordinary metered sync plane** (corrected 2026-08-06): custody charges every distinct retained generation, whereas the sync plane charges only each path's live head while superseded versions rest GC-pinned and uncharged — so on that plane `storage_bytes_used` is a live-set figure, not a bound on disk. Owner of the statement, the measurement, and the ruling that deferring it is an ordering call (reclamation must precede metering, or the quota wedges with no app-side remedy): [`file-versions.md`](file-versions.md) § Retention. **Device enforcement (2026-09-02):** `max_devices` is enforced too — `fauna.sync.register` reads the caller's tier and refuses a **new** device past the cap with the typed, client-renderable `fauna.sync.device_limit_exceeded`; until then the number was read at five places in the nest and compared at none, so the `AccountGetQuota.devices.max` every app shows the user was decoration and one account could grow `sync_devices` without limit. Three semantics, all deliberate: **`0` means *none*, never unlimited** — the same reading as the shipped `backup` tier's `max_feeds = 0`, and the two caps are enforced by the same `count >= max` shape so they cannot drift; a **re-register of a `device_id` the actor already holds always succeeds**, cap or no cap (the row is an upsert, and the provision path re-registers, so refusing it would strand a device at the limit with no way to re-label or renew); and the nest's own **WebDAV pseudo-device does not consume a user slot** (it is written by `fauna.bridges.webdav_record_change`, and is excluded by its deterministic per-actor id, so at most one row per actor is ever uncounted) — a client cannot mint that exclusion for itself, since `fauna.sync.register` refuses a `device_id` equal to the derived pseudo-device id outright, as malformed input, rather than treating the attempt as an ordinary register. **The displayed `used` count excludes it too (2026-09-15):** `fauna.quota.get`'s `devices.used` counts the same set the cap counts — the WebDAV pseudo-device excluded — so a capped user with WebDAV enabled sees `used == max`, never `max + 1`; the per-device **Devices list** the admin/user pages render is a separate, unfiltered read ([`webdav-server.md`](webdav-server.md) § Protocol surface — *Device identity*) and still shows that row, so a WebDAV user legitimately sees one more row than the `used / max` figure beside it. The admin-settable value is itself bounded — `fauna.admin.tiers.{create,update}` refuse a `max_devices` above a ceiling derived from the sync page loop's frontier writer cap, which sizes itself against this very number ([`../architecture/account-sync-plane.md`](../architecture/account-sync-plane.md) § Feeds and cursors). **The shipped `free` seed is 3 devices (ruled 2026-09-26; `personal` 5, `community` 10 — `db/migrations.rs` `SEED_TIERS`).** It was 2 until the day the cap became real, which an honest laptop-plus-phone fleet already met; 3 leaves room for one more row — a second co-located app on one machine keeps its own `sync_devices` row ([`../architecture/apps/sync-agent-credentials.md`](../architecture/apps/sync-agent-credentials.md) § Credential model, decision 5, deliberately unchanged: the quota counts rows, not machines) — so laptop + a co-located tui + phone fits. The seed is only a default: `INSERT OR IGNORE` means a fresh nest gets 3 and an already-provisioned nest keeps whatever its admin set, and the admin raises or lowers any tier's `max_devices` from the app UI (`fauna.admin.tiers.{create,update}`) — the tier *is* the quota. A free-tier user who needs a fourth device asks their admin, which is what a quota is for.

#### Admin continuity and succession — the roster surface and the two instruments (ratified 2026-08-11)

A deployment's continuity — domain renewal, deployment-seed custody, admission, the considered actions only an admin can take — rides on admin-role holders; residents' keys, replicas, and relationships are their own and survive any admin's disappearance ([`../architecture/nest/box-recovery.md`](../architecture/nest/box-recovery.md); the domain half: [`../architecture/nest/domains-and-tls-bootstrap.md`](../architecture/nest/domains-and-tls-bootstrap.md) § Domain loss). Continuity is provided by **two instruments, both built on existing primitives** — there is deliberately no third mechanism:

1. **A live co-admin (the roster surface).** The wire is complete and guarded — `fauna.admin.admins.{list,add,remove}` (delayed pending actions; the last-superadmin refusal; `Admin ⊇ User` held at both ends of the role's life, above) — and **no app renders any of it**, which is the gap this section ratifies closed. The surface is per-row controls on Section 5's user list, riding the same shared decision the cut-off controls ride (`admin_user_row_controls` + the existing `AdminUser.is_admin` flag): a plain registered row offers **`admin-users-make-admin-button`**; an `is_admin` row offers **`admin-users-remove-admin-button`** (the last-superadmin refusal surfaces in `admin-users-action-error`, like every other refused row act). Both are *scheduled* acts (the pending-action delay window), matching the destructive lifecycle controls beside them. ui.yaml minting of the two IDs rides the implementing session per the authority split; the roster is single-role today (`admin_actor_ids.role` defaults `'superadmin'` and nothing writes another value) and a junior admin tier is latent schema, deliberately **not** designed here. The 7-app build is entrusted to the batched trickle-down (tui first, per the lead-app rule).
2. **The admin's recovery kit is the deployment's succession instrument (the heir path) — already true by construction, ratified here so it is *stated* rather than emergent.** Identity succession re-points the admin role in the succession transaction ([`succession-aftermath.md`](succession-aftermath.md) § Re-key scope, table row 1; built), and deployment-seed custody follows through the ordinary aftermath — the account-state plane kind `fauna.state.deployment-seeds` crosses the succession with every other `GenerationTip`-sealed kind (the succession rider; the `__config` re-key that carried the map before retired 2026-10-02 — [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, steps (4) and (6)), and the successor's escrow blob carries the predecessor seed as the total-device-loss backstop. So an admin who wants their deployment to survive them leaves their recovery kit where their executor or heir will find it: the heir runs the succession ceremony, inherits the account, the admin role, and the seed custody in one designed path. Nothing new is built for this; the section's job is that an admin can *know* it.

**Seed custody extends to the whole roster.** A co-admin added after claim never received the claim-time seed hand-off; the mechanism extending custody to them — `fauna.admin.deployment_seed.get` plus the client-side self-healing capture — is owned by [`../architecture/nest/box-recovery.md`](../architecture/nest/box-recovery.md) § Mechanism (ratified 2026-08-11, same trust argument as the claim hand-off).

**What neither instrument confers:** user-data reach. An admin — original, co-, or heir — reads no resident's sealed content; what a box can read remains the set of user-minted capability grants, unchanged by role grants or succession.

**The refused third mechanism — designated-successor-on-inactivity.** A dead-man ladder (name an heir; the nest promotes them after N days of admin silence) was considered and is **refused**: the co-admin instrument dominates it — an admin who trusts someone enough to designate them can grant the role *now* — and what the timer adds is only a window in which absence is misread as death, handing a live admin's box to someone else while they are merely unreachable. This is the same family of refusal as identity-succession's "no admin-mediated re-point" and "no seed-only succession": continuity instruments must carry explicit, present consent.

**The two honest limits, stated rather than assumed away.** (a) **The domain registrar account is outside Fauna.** An heir needs registrar access (or its own estate path) to keep renewing the name; failing that, a surviving admin re-homes the deployment under a new name — the lapse story, timing clock included, is owned by [`../architecture/nest/domains-and-tls-bootstrap.md`](../architecture/nest/domains-and-tls-bootstrap.md) § Domain loss. (b) **No co-admin and no reachable kit ⇒ deployment continuity dies with the admin.** Residents keep their identities, their device replicas, and their own backup destinations; what dies is the deployment's operation — and reachability at the domain, when it lapses. That residual is priced, not solved: it is exactly what the two instruments exist to make avoidable in one considered act each.

### The admin audit log on `admin-logs` (design 2026-10-01 — IDs PROPOSED, rule-A sign-off asked the same day; unbuilt on every app)

Every admin action writes a row to the nest's hash-chained audit log ([`../architecture/nest/public-mode.md`](../architecture/nest/public-mode.md) § Admin Surface — kinds `fauna.admin.audit.{list,integrity}`), and each row is served with the format its hash was computed under so that an admin's own app can recompute the chain ([`succession-aftermath.md`](succession-aftermath.md) § Re-key scope, the `audit_log` ruling). **An admin reads and verifies that log from the app.** It is the accountability record between the admins of one nest (§ 2 → *Admin continuity and succession*), and there is nobody else to read it: with no operator to query a database ([`../principles.md`](../principles.md) § One configuration surface), a record no app shows is a record no human can reach. A wire-only log was considered and declined for that reason, and because the verify-it-yourself row format already presumes a reading client.

Placement: a section on the admin Logs page, below the log lines — the page an admin already opens to see what happened on this nest — adding no nav entry on any of the 7 apps. Proposed elements: `admin-audit-section`; `admin-audit-entry` (indexed) — one row per action, newest first: when, which admin (by handle, per § 2 → *What identifies a user in an admin picker*; the nest itself for a system entry), the action, and what it acted on; `admin-audit-more-button` — pages older entries (`before_id`); `admin-audit-integrity-status` — one line saying the chain checks out through the entries shown, or naming the first entry whose hash does not, or how many entries this app cannot check (a hash format the app does not know is refused, never guessed at).

*Where logic lives:* shared Rust — `AdminClient::audit_list` / `audit_integrity` (one method per kind, like the rest of that client) and a `fauna_client_admin` fold that composes each row's text and verifies the chain; the apps render. *Implementation status today (2026-10-01):* the two nest kinds are built and conformance-tested; nothing calls them — `AdminClient` has no method for either, and no app has a surface. ## Persistence

Admin actions write nest-side via the `fauna.admin.*` WS-RPC kinds (the shared `AdminClient`). The `/admin/api/...` HTTP twins are **deleted** (no-http-ws-rpc-everywhere; the last web consumer migrated 2026-06-06 and `admin-api.ts` was removed). There is no client-side admin cache — every page re-reads on entry/refresh (read-side state only, no long-term-store entries).

## Errors & edge cases

- Per-page error IDs:
  - Users (all sections): `admin-users-action-error`.
  - Aliases: `admin-aliases-action-error`.
  - Other pages: `error-message` (page-level).
- Pagination edge: empty page, last page.
- Eviction edge: cancel after eviction completed.
- Invite-code edge: max-uses zero, expiry.
- Pairing-toggle edge: failure to persist, partial state.
- Invite-request edge: deny-without-reason, race with user re-submission.
- Forwarder edge: `forward_target` to a hosted domain (rejected by `validate_forward_target` — a local-domain target is an alias, not a forward, `mail-aliases.md:115`); `pattern` collides with an existing exact alias or forwarder on `(local_domain, pattern)` (`conflicts_with_existing_alias`); `pattern` is a reserved local-part (`reserved_local_part`); `local_domain` not hosted. All surface to `admin-aliases-action-error`.
- Catch-all edge *(on `admin-dns`)*: clearing the only catch-all on a domain that was relying on it (unmatched mail reverts to `550 User unknown`); designating a non-existent actor.

## Architectural rules

1. **Single admin shell.** All 7 apps render the same admin shell with the same `admin-nav-back` and the same per-page heading IDs.
2. **Admin gating is shared Rust.** Whether the user is an admin is computed once in shared Rust; apps render the gate but don't compute it.
3. **Observer-driven rendering** once per-page snapshots exist.
4. **Indexed list IDs throughout** — `user-row[i]`, `admin-users-tier-select[i]`, `invite-code-item[i]`, `admin-settings-tier-item[i]`, `admin-dns-domain[i]` / `admin-dns-removed-domain[i]`, `admin-invite-requests-list[i]/...` (incl. `invite-request-row-tier-select[i]`). Scoped queries only.
5. **Cross-page invariant:** approving an invite request (the `admin-users` Pending requests section) must trigger the requester's onboarding flow to advance — that's a contract between admin actions and onboarding state machines, owned shared-Rust-side.

## Don't do these

- Don't render the admin shell to non-admins.
- Don't call the deprecated `/admin/api/...` HTTP twins from new app surfaces, and don't invent per-app admin endpoints. Everything goes through the `fauna.admin.*` WS-RPC kinds via the shared `AdminClient`.
- Don't compute admin gating per-app.
- Don't introduce per-page navigation patterns that bypass `admin-nav-back`.
- Don't carry the Linux "Admin row hidden until confirmed" rendering note as drift on other apps — the gating is shared Rust; the rendering is uniform.
- Don't deny an invite request without setting the reason when the deny-reason-field is non-empty (the requester's denial-reason surface depends on it).
- Don't build a separate per-user quota control — the tier *is* the quota; admission and change-tier assign a tier (`admin-users-tier-select` / `invite-request-row-tier-select` / the Invite section's `admin-settings-tier-select`).

## Done definition

An app is done with the admin shell when:

- [ ] Every admin page in ui.yaml `navigation.admin_pages` renders with its canonical IDs (the consolidated three-section `admin-users` among them).
- [ ] Admin gating is computed by shared Rust; non-admins do not see the shell.
- [ ] Each page drives off its snapshot getter (no client-side state for the snapshot data).
- [ ] User-administration (list / pagination / eviction / tier change / invite-code minting+delete / invite-request approve+deny), tier definitions, email domain management, and the pairing knob all go through the shared `AdminClient` (`fauna.admin.*` WS-RPC), not the HTTP twins.
- [ ] Cross-page contract holds: approving an invite request advances the requester's wizard.
- [ ] `tests/e2e-unified/ui-actual-<app>.yaml`'s `admin-*` blocks refreshed; `ui-actual-lint` introduces no new errors compared to the session's starting SHA.
