#### Linux FUSE binding (ratified 2026-09-26; S1–S4 — mount, hydrate on open + pass-through I/O, dehydrate + pins, flips + the crash guard — BUILT 2026-10-01/02, the app toggle (S5) BUILT 2026-10-04)

Linux realizes the on-demand surface as a **FUSE filesystem the per-user `fauna-sync-agent` mounts over the bound location** — the windows *location-level* shape (`folder-location-mode-toggle` on the bound row, `LocationConfig.mode` in the agent's `config.toml`, the one `SetLocationSyncMode` verb), chosen because a FUSE mount, unlike a File Provider domain, *can* take over an arbitrary user directory; apple's set-level toggle exists only because FP cannot, so linux does not adopt it. The user's direction ruling (2026-09-26): build it, with the `fuser` crate (crates.io under `cargo vet`, `default-features = false` — the pure-Rust `/dev/fuse` protocol, no libfuse link) plus the distro `fuse3` package's setuid `fusermount3` for unprivileged mounts, since the agent never runs as root (`../architecture/apps/sync-agent.md` § Packaging + lifecycle). Eight binding-specific rules:

- **The same host, a different OS binding.** The root runs the shared `run_hydration_loop` exactly as the windows cfapi root does — the folder-scoped `SyncEngine` as its `HydrationHost`, the `LocalWrites` watcher + `converge` as its write half (one uploader, never a second), `serve_populate` for listings, a `PlaceholderInvalidator` for dehydrate and pins — and the FUSE session thread contributes only what `cfapi_host.rs` contributes on windows: translating kernel requests into `HydrationCommand`s and completing them. A FUSE `PlaceholderInvalidator` replaces the cfapi one. `provider_face` (the control-inverted apple face) is deliberately **not** this surface's seam: a FUSE root is self-driving — it owns a watcher and the loop — so it belongs with the cfapi service under the shared multi-engine driver ([`on-demand-files.md`](on-demand-files.md) § *Hosting multiple on-demand folders*), and the headless FFI-seam proof it inherits from apple is the vehicle, not the host shape.
- **Mount-over: the bound directory IS the backing store, and the mount is a view of it.** The agent opens the bound directory before mounting and keeps that descriptor; every read and write of the *underlying* directory goes through it (the `/proc/self/fd/<fd>` reach, which is also the engine's `watch_dir`), and the FUSE view presents the union of the underlying entries (hydrated files, the user's own new files) and the state DB's `Placeholder` rows (`serve_populate` over `immediate_children` — names, sizes, mtimes, no bytes). The consequences are the point: nothing is ever moved or copied on a mode flip, an unbind, a sign-out or a crash, and once the mount is gone the directory is an ordinary directory holding exactly the hydrated files (a clean stop unmounts; a crash leaves a dead mount until the boot sweep — the lifecycle rule below) — the user's bytes are always at the user's path (`../principles.md` § The user always controls their data). There is no separate cache root; disk accounting is the user's own filesystem's (the view's `statfs` answers with the underlying filesystem's). **A request from the agent's own process is answered from the underlying directory alone** — no placeholder listing, no hydration: resolving a path under the reach (a `canonicalize`) looks names up through the view, and a lookup that waited on the root's driving loop from inside that loop would never be answered.
- **Hydrate on open; write through.** Opening a placeholder hydrates it: the FUSE thread hands the request to the loop, which streams the file into the underlying directory (`download_file_to_path`, temp-then-rename), records the served identity (`mark_hydrated` — the closed hydration→upload feedback loop in § *Implementation status today*), pushes `FileStatusChanged{Synced}`, and only then completes the open. Hydrations run off the FUSE dispatch thread so a slow fetch never stalls a listing, and several may run at once. Every other operation on a materialized file passes through to the underlying file, so a user write lands where inotify sees it and the shared watch→`upload_file` loop uploads it. A placeholder is *present*: `unlink` of one records the delete through `handle_delete` (a loop arm, never the FUSE thread), `rename` of one hydrates first (apple's rule), directories pass through (`rmdir` over remaining placeholder rows refuses `ENOTEMPTY`; a `rename` of a directory still holding placeholder rows answers `EXDEV`, so `mv` copies it — hydrating as it reads — rather than leaving its rows behind), and symlinks and hard links are refused in v1. A hydration downloads into a dot-named temp file beside its target and lands by rename, so the watcher and the scans never see a half-written file, and a file the user wrote at that name meanwhile wins.
- **Dehydrate ("free up space") removes the underlying bytes — and that removal is NEVER a delete.** `FreeSpace` and the pin reaction gate on `is_dehydration_safe`, flip the row to `Placeholder`, and only then unlink the underlying file. **Iron-clad: a FUSE root's `Placeholder` rows are outside the delete universe on both rails — the scan and the watcher — and this root never writes the seen mark (amended 2026-10-01; the 2026-09-26 wording predated the mark).** This is linux's form of *never mistake one for absent*: on cfapi a placeholder is a file on the disk, so once the engine has *seen* it there its absence is a delete ([`delete-propagation.md`](delete-propagation.md) § *An offline placeholder delete propagates*, decision (a)); here a placeholder is never on the underlying disk — the row is the file's only presence — so a seen mark on this root would make every browsed or freed file read as a user delete at the next sweep and record it on the nest. Four obligations follow, each one the binding's own and none a change to the cfapi rule: **(1)** the listing sink reports **nothing placed** — `serve_populate` marks exactly the set its sink vouches for, and a FUSE listing puts nothing on the disk; **(2)** the dehydrate records the row through an off-disk form that leaves it unseen, never through the mark that cfapi's in-place free earns; **(3)** the root boots as a **fresh registration**, so a mark that arrived with an inherited state DB is cleared before the boot sweep; **(4)** a watcher `Remove` for a path whose row is `Placeholder` is the provider's own unlink, never a user delete, and the write half drops it before it reaches `handle_delete` — the dehydrate additionally registers the rel with the recent-removal suppression before unlinking. `handle_delete` itself is unchanged and stays the ONE way a placeholder is deleted here: the explicit `unlink` through the mount (the rule above), handed to the loop by the FUSE thread. The order is row first, unlink second, because that is the crash-safe one: a crash in between leaves a `Placeholder` row over a file still on disk, repaired toward the bytes (back to `Synced` when the disk hashes to the recorded head, an ordinary local edit otherwise), where the reverse order would leave a `Synced` row with no file — a delete to the next sweep. Pins live in the row (`SyncEntry.pinned` gains its setter; cfapi kept them in the OS): a pinned placeholder hydrates eagerly, a pinned file refuses dehydrate. No automatic pressure-driven eviction in v1 — a policy a user might want to choose is an app-UI + nest-state decision, never a constant hidden in the agent.
- **Placeholder detection needs no OS attribute.** The underlying directory holds only genuinely local bytes, so `is_cloud_placeholder` answering `false` on linux is correct, not a gap: the present-but-unreadable hazards cannot arise because nothing unreadable is ever on disk, and reconcile's delete detection — over the rows with evidence, the `Synced` rows and the *seen* placeholders — never counts one here, since this root marks none seen (the dehydrate rule above). Two windows-isms in shared code are fixed with this binding: `path_map::overlay_abs_path` joins with `\`, and `normalized_path_to_rel` matches case-insensitively.
- **The mount lifecycle: a clean stop unmounts, a crash guard unmounts after a crash, and the boot sweeps what the guard could not (amended 2026-10-01 — measured, replacing "crash-safe by construction"; guard 2026-10-02).** Options: `fsname=fauna-sync-agent`, `subtype=fauna`, `default_permissions`, never `allow_other`. **`auto_unmount` is not available to this binding**, and that is a measurement, not a preference: the `fuser` crate refuses the option on an owner-only mount (it demands `allow_other` or `allow_root`, each of which needs `user_allow_other` in `/etc/fuse.conf` — off on a stock distro, and a widening this binding never takes), and the same option handed raw to `fusermount3` mounts but leaves the mount in place ten seconds after a `kill -9`. So a crashed agent leaves a **dead mount**: the directory answers every access with `ENOTCONN` until something unmounts it — the hydrated bytes are intact underneath, and unreachable at their path for that window. Boot reconcile, before any engine starts, lazily unmounts (`fusermount3 -uz`) every leftover `fuse.fauna` mount at a configured on-demand location — the linux twin of the windows ghost-registration sweep — for a ghost nothing else cleared. **The window closes without a restart, by the agent's own means, never by `allow_other`:** at every mount the agent re-executes itself as a **crash guard** — a child in a process group of its own holding the read end of a pipe whose write end only the agent holds; however the agent goes, the guard reads EOF and lazily unmounts the mount it was given, but only while that mount is still in the table under its mount id AND answers `ENOTCONN` (dead) — a successor's live mount at the same path, recycled id or not, is never touched. So with the agent dead the directory is an ordinary directory again within moments; a guard killed with the agent (a whole-cgroup stop) leaves its ghost to the boot sweep. Mounting needs an openable `/dev/fuse` and a `fusermount3` on PATH; the agent probes both at boot and reports the result as the additive `on_demand_available` field of its status reply (with `on_demand_unavailable_reason`, a stable code), which the apps read to render the toggle disabled with the reason ("needs the fuse3 package") — the offline-aware-controls shape, never a silent no-op. **One refusal the probe cannot see is per location:** Ubuntu confines `fusermount3` with an AppArmor profile that admits a mount point only under the user's home, `/mnt`, `/media`, `/run/user/<uid>` or `/tmp` (measured 2026-10-01: *mount failed: Permission denied* anywhere else). A root whose mount fails runs unmounted — its hydrated files sync two-way and no placeholder is listed — and the agent says so per location: `LocationInfo::on_demand_mount_error` carries a stable code — `mount-refused` for the helper's permission refusal, `mount-failed` for anything else — for exactly as long as that root runs unmounted, the shared binding model mirrors it onto the row (`BindingRow::mount_error`, on the reconcile and on the status-tick watch), and the app renders its line beside the row's switch, which stays live so the user can turn on-demand off. The linux row renders that line as untagged text like its other captions, so it took no element of its own.
- **Mode flips and unbinds are mount/unmount, nothing else.** always→on-demand: stop the resident engine, mount over the directory — every file already there is simply a hydrated file. on-demand→always: unmount, start the resident engine, which materializes every `Placeholder` row (a `Placeholder` row on a resident root is a pending download, never a delete; the windows flip is checked against the same rule at build time). Unbind, unprovision, sign-out and account switch: stopping the engine unmounts (the mounted session is a drop guard, like `CfApiConnection`), and the directory is left holding its hydrated files. A fresh linux binding starts always-resident (the agent's platform-scoped `fresh_binding_default`, [`on-demand-files.md`](on-demand-files.md) § On-Demand Files → *The choice is the user's*); whether linux follows windows to an on-demand default once its FUSE root can serve one is decided with that root, not before.
- **Install channels.** deb and `install.sh` declare/check the `fuse3` package (`../architecture/installers/linux-desktop.md` § Installation Files); AppImage boxes already run FUSE. Flatpak and Snap cannot mount from inside their sandboxes (no setuid `fusermount3`, no `/dev/fuse`), so there the probe reports unavailable and the toggle renders disabled with that reason — a stated limitation, not a per-channel design.

**Headless proof.** `bins/fauna-sync-agent/src/fuse_live_integration.rs`, the linux twin of `cfapi_live_integration.rs`: the agent's own host over a real mount in a temp dir, every assertion from **another process** (`ls`, `cat`, a write by a subprocess), opt-in behind a `fuse-live` cargo feature (it needs `/dev/fuse`) so the merge-gate check runs it on the linux dev machine. Same test names as the cfapi file wherever the rule is shared (populate, open-hydrates-and-flips-`Synced`, a cloud-only placeholder is never uploaded, a dehydrated file is never recorded as a delete, a local edit by another process is uploaded, zero-byte, a remote delete reaches the disk — cloud-only row, hydrated in-sync copy, and an unsynced edit that survives with its `delete_declined` conflict). The cross-app witness for `files-on-demand` outcome 1 is `test_folder_location_mode_toggle.py`'s linux arm over the real agent, plus a tier_3 read-path test (`test_folder_on_demand_read_path_linux.py`: bind → flip → the kernel's mount table, `ls`/`cat` and a write from subprocesses, the engine's own upload record → flip back) — both built with S5 — and the placeholder half through the apps, `test_folder_on_demand_hydrate_linux.py` (two seats of one account, convention 16's shape: the linux seat flips on-demand, a tui seat adds a file → it lists through the mount at its size with no blocks and the engine's row is a `placeholder` → a subprocess `cat` returns its bytes and the row is `synced` with the served identity → flip back leaves an ordinary file).

**Implementation status (2026-10-04): S1–S5 BUILT — the root mounts, lists, hydrates on open, passes I/O through, dehydrates, keeps pins, flips both ways and is unmounted by its crash guard, and the linux app's bound row flips it.** `fuser` 0.18 is admitted (linux-only dependency of the agent, `default-features = false`; the binary links no libfuse). `bins/fauna-sync-agent/src/fuse_host.rs` is the binding: `Reach` (the pre-mount descriptor; `/proc/self/fd/<fd>` is the engine's `watch_dir`, the loop's `sync_root` and the watcher's root — never canonicalized, since its canonical form is the mount point's own text), `mount_over` (the root's connect step in `engine_driver::run_on_demand_root`, made by `serve_hydration_root` after the boot sweep with `fresh_registration` always true) with its `CrashGuard` (the agent's hidden `__fuse-guard` mode), the filesystem (the union of the underlying entries and `serve_populate`'s placeholder children; `HydrationCommand::Materialize` hydrates through the engine's bounded-memory `download_file_to_path`; the pass-through ops finish on threads of their own; a directory still holding placeholder rows answers `EXDEV` to `rename`), `sweep_ghost_mounts` (run by `service.rs` before any engine starts) and `probe_available` (reported by `GetServiceStatus` as `on_demand_available` + `on_demand_unavailable_reason`; windows reports available, macOS `not-agent-hosted`). Shared Rust carries the rest: the engine's off-disk posture (`SyncEngine::set_placeholders_off_disk`, taken before the boot sweep — no `Placeholder` row is delete evidence, the watcher rail drops its remove, no seen mark is written, a `Placeholder` row over its own recorded bytes is repaired toward them), `SyncEngine::dehydrate_off_disk` + `bridge::free_local_bytes` (one road for *Free up space*, an unpin and a stale hydrated copy), pins in the row (`SyncDb::set_pinned`; `FreeSpace`/`PinFile`/`UnpinFile` reach the loop as `EngineCommand::{FreeSpace, SetPinned}`), and for the flips `SyncEngine::materialize_placeholder_rows` — the resident watch loop's pending-download pass after every pull, since the on-demand fold moves the change anchor past the rows it records — and `EngineHost`'s serialized restart (a replacement starts only once the engine it replaces has ended, so a resident engine never scans a live mount). Pinned live by `fuse_live_integration` — RUN by the `fuse-live-test-check` merge gate ([`merge-gate-catalog.md`](../architecture/merge-gate-catalog.md) § The heavy gate catalog) — and by `off_disk_placeholder_test.rs`, `resident_placeholder_test.rs` and `engine_host`'s restart tests; the per-slice record of what each test proves is the design record's.
