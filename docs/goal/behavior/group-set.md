## Cross-user shared-set transfer — the build

### Build design — the group set: a folder bound under an in-person share (design pass 2026-10-29; refutable at build time)

The ruling in [`p2p-shared-set.md`](p2p-shared-set.md) § Offline share initiation, contract point 1, births an in-person share as a recipient-set **group scope** and names it the first consumer of the file-sync-onto-scope-families direction ([`../architecture/account-sync-plane.md`](../architecture/account-sync-plane.md) § Substrate settlements, D4); this pass fixes the shapes a build executes cold so that a folder bound under such a scope carries its files device to device with no nest — [`../../features/offline-sharing.md`](../../features/offline-sharing.md) outcome 3. **Measured 2026-10-29:** the ceremony mints a fresh scope whose recipient holds an `Enrolled` entry and nothing else (`fauna_client_capabilities::group_ceremony::begin_group_share`); a folder set is a nest folder bound to an M2 group with content keys, and the two share no id space; the share pump composes specs from M2 bindings only (`share_glue::compose_specs`); the serve door's data arms admit the folder family only (`ShareServer::admitted_for_set`); and the group plane's write door refuses every `GenerationTip` kind (`GroupStatePlane::write_own`). **The alternative — letting the ceremony name an existing M2 folder and carry its membership and keys — is refused without a new ruling:** contract point 1 forbids retrofitting offline initiation onto MLS-keyed folders permanently, and its reasons (the delivery-service and arbiter dependencies the storage-keying ruling split away — [`../architecture/account-data-plane.md`](../architecture/account-data-plane.md) § The ratified decisions) are unchanged. What follows is the group content plane — the "group content-kind sealing" every status paragraph has pointed at since 2026-08-17 — as ten decisions.

**1. A group set is the scope itself: path state is plane entries, bytes are the share plane's chunks, the agent's state DB is a projection.** A folder bound under a group scope (a **group set**; the M2-keyed kind is a **folder set**) keeps no nest folder and no sequenced log: its file rows are class-2 entries of the group scope — the per-writer journal, the frontier vector and the lattice join the plane already gives every group kind (`fauna_account_plane::group_state_plane`) — and its bodies are the content-addressed, convergently sealed chunks and manifests the share leg already moves, served under the scope id as the set id. The sync engine's per-set state DB (`sync_entries`, the chunk index, the retained manifests, the scanner's tracked state) is kept for a group set exactly as for a folder set, as the **projection** the local tree is reconciled against — never the log. This is D4's own derivation (content = blobs, path state = entries, engine = projections) applied to the one family that has no other option: a group scope is arbiter-free by constraint (b) ([`../architecture/recipient-set-scheme.md`](../architecture/recipient-set-scheme.md) § The recipient-set scheme, the last bullet), so nothing may sequence it and convergence must come from the merge alone; the folder family's own convergence stays exactly as unruled as D4 leaves it. Refused: serving group rows as `own_change_log` rows over `fauna.peer.share.changes.list` with `seq: 0` and `sequenced: false` for ever — a pending row means "awaiting the nest", the tail page caps at `MAX_ROWS_PER_PAGE` rows (a set with more files never converges), and the provisional overlay orders by arrival, so two replicas would not fold alike; and a per-writer sequence in the state DB beside the plane that already has one.

**2. Three kinds join `fauna_protocol::group_state`.** `fauna.group.file` — **`GenerationTip`-sealed, `LatestWins`** — one entry per path, logical key the set's path hash (`fauna_core::path_crypto`'s keyed hash, keyed under the scope's content branch), value: the sealed path (names rest sealed, [`file-sync.md`](file-sync.md) § Sealed names & paths), `manifest_hash`, `size_bytes`, `change_type` (`put` | `delete` — a delete is a value phase, never a tombstone: the plane has no tombstone door and a deleted path must stay a merged fact), the **content generation id** (32 bytes — the group generation whose derived key sealed the manifest and chunks; **no `u64` version exists on this family and no code may synthesize one**: generation ids are content-derived and only partially ordered), the author's `LwwStamp`, and the author's device carriage — its `DeviceAuthorization` cert and a signature over the value core under a frozen context (`fauna.group.file.sig.v1 2026-10-29`), the roster record's shape; every byte field `serde_bytes`. `fauna.group.name` — **`GenerationTip`-sealed, `LatestWins`**, one cell (logical key `self`), the set's display name, written by the authority: the naming kind contract point 1 promised "with group content-kind sealing", and the smallest kind to pin the seal path with (a nameless set keeps its short id). Its value is `fauna_core::group_name::GroupNameRecord`, the file row's shape: a core binding the scope id, the UTF-8 name and the author's stamp instant, the author device's `DeviceAuthorization` carriage, and a signature over both under a frozen context (`fauna.group.name.sig.v1 2026-10-29`). A reader honours it only when the carriage passes the authority line's revocation-aware device check and the entry's `LwwStamp` is that device's signed instant, so a member holding the tip key cannot rename the set and a name a since-revoked authority device signed is retired; the check runs at the walk, before the merge, and again in the fold (`fauna_account_plane::group_set::fold_group_name`). `fauna.group.endpoints` — **`MachineryRoot`-sealed, `LatestWins`**, one cell per writer device (logical key the device hex), value `fauna_core::group_endpoints::GroupEndpointsRecord`: the file row's shape over a `fauna_core::device_endpoints::DeviceEndpointsEntry` — a core binding the scope id, the entry and the writer's stamp instant, the writer device's `DeviceAuthorization` carriage, and a signature over both under a frozen context (`fauna.group.endpoints.sig.v1 2026-11-02`) — the group twin of `fauna.state.share-endpoints`; machinery, because a member must dial before it holds any generation key, and because a custodian serving the scope later must route it. A reader honours a cell only when it sits under its writer device's key, the carriage chains that device to the authority (the line's revocation-aware check) or to a live roster member, the entry's `node_id` is that member's own actor, the signature verifies and the entry's `LwwStamp` is the device's signed instant — so a member can say where IT is and nothing else: a cell naming a co-member's node, or filed under a co-member's key with a later stamp, is refused at the walk before the merge and again in the pump's read, and a removed member's stored cell leaves the merge with its entry. All three are `p2p-share`-gated with the ceremony kinds (rule 5) and join the registry's law tests.

**3. The `GenerationTip` seal path — the account plane's v2 envelope under a group content schedule.** `GroupStatePlane::write_own` gains the arm its doc comment reserves: for a `GenerationTip` kind it resolves the scope's admissible, keyable tip (`fauna_core::group_generation::resolve_admissible_group_tip` over the merged mint, top-up and roster rows, the observer's wraps opened with its reception secret), derives the kind's keys from that generation's key through a **`GroupContentSchedule`** — `fauna_core::group_content::group_content_key`'s two-step under the frozen `fauna.group.content.{seal,nonce}.v1` pair, the `GroupMachinerySchedule` twin — and seals with `fauna_core::account_entry_crypto::seal_entry_v2`, the generation id in the envelope so a reader peeks it (`peek_generation_id`) and opens with the wrap it holds for it; **no admissible tip → the write refuses** (the fail-safe gap the severance mint pays, § The recipient-set scheme → *Mint triggers*), never a machinery-root fallback. The walk's trial-open gains the matching arm; a v2 row whose generation this replica holds no wrap for stays `unopened` and is re-presented by `reconcile`, as today; `adopt_rows` gains the counted `report.refused` pre-check that comment names. The room's group blob shape (`seal_group_content`) is NOT used for entries: a plane entry has coordinates and the entry envelope binds them ([`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Audience: a storage group, the per-kind bullet); the blob shape stays the shape of coordinate-less logs.

**4. Keys for bytes — one derived content key per group generation, the folder family's `chunk_crypto` root re-targeted.** The set's **content key** for generation G is `group_content_key(G's key, "fauna.group.file.content")` — a kind context of its own, so the path-state entries and the chunk bodies never share a key. The engine's key custody for a group set is a **`GroupContentKeys`** ring keyed by generation id — the tip (what new content seals under) and every retained generation this member holds a wrap for — built by one shared reader beside `group_scope_view` (`fauna_account_plane::group_set_keys(store, scope)`: roster, authority line, tip resolution and wrap opening in one place; the share glue, the engine host and the on-demand hosts all read it and none re-derives). `SharedSetSpec.content_keys` becomes family-aware (`SetContentKeys::{Folder(FolderContentKeys), Group(GroupContentKeys)}`), and every consumer that today indexes a key by `content_key_version` takes the row's generation id on this family. Manifests and chunks are then exactly what the share leg serves and pulls — `store key = hash(sealed body)`, the AEAD tag under the generation's key, `PeerShareBlobFetcher` through the one download walk — so nothing new verifies bytes.

**5. Who may write, and how a reader knows — enrolment at the row's generation, read off the wraps.** Every verified `Enrolled` member and the authority may author `fauna.group.file` (v1 sets are all-writer; a reader-only roster role is a later roster field, named here, not designed). A reader honours a file row iff (a) the carriage's cert chains the writer device to an actor M (`fauna_core::group_scope::GroupAuthority::verify_device_chain`'s shape, applied to a member's chain), (b) M is the authority, or the generation the row names carries a **wrap for M's entry** in the merged mint rows — enrolment at that generation as the lattice records it, no stamp consulted (stamps are advisory and there is no arbiter) — and (c) the signature verifies. Arm (b) is what keeps a removed member's past files in the set: a removed member cannot obtain a post-removal generation key, so cannot seal under one, and the rows it sealed while enrolled stay what they were; its bound was first written as the serve door's — a removed member still reaching a stale co-member's replica is admitted until the removal reaches it (§ The recipient-set scheme → *The membership witness*) — which holds per hop only, and the ruling at the end of this decision closes it. A row failing any arm is counted `refused` by the walk and never folded. A member's own removed device keeps its device secret and writes under the member's name until the member's reception-key rotation re-mints (trigger (2), unbuilt) — the member-fleet staleness bound the scheme already accepts, stated here so no build hides it. **Ruled 2026-11-02 — a removed member is honoured as of its removal, and a cell folds over each writer's latest row.** Enrolment at a generation is permanent, so a removed member still holding a pre-removal generation G0 could sign NEW rows naming G0 after its removal and arm (b) honoured them; one stale co-member merging such a row re-served it (the relay plane serves every row it takes, verbatim), every up-to-date replica then honoured it for good, and a far-future stamp made it the winner of every later latest-wins merge of its path — a removed member could plant, overwrite or delete any path, permanently, through one stale peer. Two rules close it, both pure functions of merged state and signed values, never of a reader's clock or of the order rows arrived in (the consensus ground: every reader folds the same value from the same bytes). **(i) The removal bound, arm (b′):** a member's row whose entry the reader's merged roster excludes is honoured iff its signed `stamped_at_ms` is not after the EARLIEST honoured `Removed` cell's `removed_at_ms` for that entry — the authority's signed instant, read off the roster as arm (b) reads the wraps — so a removed member is frozen at its removal: what it wrote before stays, as this decision always meant, and nothing it stamps later is honoured anywhere the removal has merged. **(ii) A writer-checked cell folds over each writer's latest row, honoured rows only:** a `fauna.group.file` cell, and the `fauna.group.name` cell — one mechanism for both writer-checked kinds — is the honoured row of greatest `LwwStamp` rank among the live relay rows of its item, one per writer (the relay plane's own serve law, one live row per `(item, writer)` superseded by the writer's `writer_seq` — a writer's log, the one order the plane has): a writer's newer row supersedes its older one in the cell whether or not the newer is honoured, across writers the latest honoured stamp wins, and a cell with no honoured row folds as no row. The merged `StateEntry` cell is that fold's cache: the walk re-derives it when a row of the item lands, honoured or not, and re-derives every writer-checked cell of the scope when a row the check reads lands (a roster cell, a mint, a top-up, a revocation), from the relay rows it holds, opened under the keys it holds; the plane's `LatestWins` policy is untouched for every other kind. A row the fold stops honouring — a removed member's post-removal row a stale co-member had merged, a revoked authority device's name — thereby yields the cell to the latest honoured row of another writer, or to no row; a path whose cell folds as no row leaves the set at the engine like a converged delete, decision 9's retention keeping a lifted own edit as on any winning delete (mechanics refutable at build time). **The residual, stated so no build hides it:** (1) a removed member can still inject rows stamped at or before its removal through a stale co-member, honoured as pre-removal writes — they reach only cells no live member has written since, lose to every later write, and are the standing the member held until the removal withdrew it; (2) its own clock's skew is its own cost: an honest row it stamped after the removal's instant on its own clock is refused with the rest, so its last writes in the skew window are lost to the set — no tolerance constant is minted, the plane has no clock; (3) a writer's refused row retires its own earlier honoured row from the cell — a removed member deleting its own files, the one thing it could always do; (4) an enrolled member's far-future stamp still holds its path against every later write until the member is removed — the all-writer v1 posture, under which an enrolled member may already overwrite or delete every path — and the removal is the repair: under (i) and (ii) every row it stamped after the removal is refused and each wedged cell re-folds; (5) a revoked authority device's rows stay refused outright, past ones included (a revocation is total over the device's signatures, `GroupAuthority`'s rule) — the authority re-writes what that device wrote, and under (ii) the name a current device writes wins the cell whatever stamp the revoked one carried (the fix of the future-stamped name). **Refused, each with its reason:** honouring a non-tip generation's row only for a cell already holding a row under it (order-dependent, never convergent — a losing row is gone from the cell); bounding stamps against the reader's clock (a row one reader refuses today another honours tomorrow, and the refused one resurfaces and wins once the clock passes it); re-sealing every path on each removal (the forward-secrecy price R15 declined); the superseding mint's stamp as the bound (the mint may lag the removal by as long as the authority is offline, and the roster is authoritative while wraps are derived). Build.

**6. The feed — the share serve set serves the group plane's relay rows, and the app-side share plane is the pump.** The share server's allowlist grows by ONE kind, the account plane's own feed kind `fauna.sync.changes.list` (`state-entry` class, a `group:` scope only — an account scope on this channel is refused loudly, as the sync leg refuses the file-row form), answered by the one `fauna_peer_sync::store_serve::serve_changes_list` core the sync leg and the custodian nest already share, so the three serve sides cannot drift; admitted by `verdict_admits_group` for the requested scope plus the per-request `GroupRosterState::is_entry_removed` re-consult that door's doc demands — the same re-consult the `manifests.get` and `chunks.pull` arms gain as their group family (one helper beside `admitted_for_set`, trying the folder family first, then the group family: the two 32-byte id spaces are disjoint by derivation). The kind and `SyncChangesListRequest`/`Reply` join `KIND_PAYLOAD_COVERAGE_P2P_SHARE` with corpus entries, and the allowlist pin grows with the allowlist (rule 2). The pull is the group-plane pump leg the scheme lists unbuilt: `share_glue::run`'s pass, for every scope this device holds a root for (`held_group_roots`) and every member endpoint it knows, dials and runs `GroupStatePlane::walk` with the peer channel as the plane's `rpc` — pull-both-ways, every member a source, the account peer leg's posture — then folds the merged `fauna.group.file` entries into the engine (decision 7). The cursor is the plane's own per-writer frontier (`stored_frontier`), no `share_pull_cursors` row. The seat is the session's one actor-keyed seat; the bind door, the brake and rule 7 are untouched.

**7. The engine seat — `FolderRef::Group`, the agent's state DB as projection, the app's share plane between.** `FolderRef` gains `Group([u8; 32])` (wire `group:<64-hex>`, the scope string), additive; a location binds under a group set through the same `AddLocation` door as under a folder set, the agent hydrating a per-set state DB and a `SyncEngine` whose nest leg is **absent** — no `changes.record`, no `changes.list`, no lease, no quota, no audience: a group set has no nest row and charges nobody, and the knobs a nest arbitrates for a folder set do not exist on this family in v1 (named, not designed). **The write side:** the agent's engine detects a local change, seals the manifest and chunks under the ring's tip key, mints and signs its own-pending row exactly as B2.5 does today (`mint_pending_own_change`, the generation id in place of a version), retains the manifest and indexes the chunks; the app-side share plane reads the group set's pending rows across the process boundary as the pump already reads `own_change_log` (`SyncDbShareStore::changes_since`), writes each as a `fauna.group.file` entry through `GroupStatePlane::put` — the author's carriage signed in the app process, which holds the device key — and upgrades the pending row in place with the writer seq: the `Ok(seq)` upgrade, by path, as a nest record does. **The read side:** after every walk the share plane reads the scope's merged `fauna.group.file` entries (the fold of decision 5), screens them against the projection's cursor and hands the changed paths to the engine through the existing ingest door (`ShareIngest`, `ingest_peer_page_landing`) under a third origin, `PeerPageOrigin::Group { scope }`: rows of this origin are **converged, not provisional** — no overlay row, no retire-on-arrival (nothing arrives later) — materialized through the share leg's fetcher over `manifests.get`/`chunks.pull` with set = scope, landing by the binding's policy as today. A concurrent put to one path from two members is the plane's `LatestWins`; what the losing replica's local bytes become the build measured (the status paragraph's *Measured* block: the judge overwrites a lifted own edit) and decision 9 rules. On-demand hosts run the same lift and fold in-process. `share_glue`'s spec composition joins `group_scope_states` with the agent's serve info (`GetShareServeInfo` listing group bindings by their `group:` ref) and the ring — one spec per bound group set. The app leg is the device-local `folder-location-*` section on a group-scope row, tui first ([`../ui/folders.md`](../ui/folders.md) § Element IDs, the offline-share entry): the shared `GroupScopeView` carries the full scope id and the folded `fauna.group.name`, and the binding is keyed by the scope's `FolderRef::Group` wire form — its identity and its set label both, so a rename or an M2 set of the same name never reaches it.

**8. Discovery and reach — endpoints are plane data; the bootstrap rides the ceremony.** A member's dial targets for a scope are the `fauna.group.endpoints` cells of its other members that pass the cell's writer check (decision 2's carriage, the kind's row above: each member's device signs where that member is, and nothing else), written by every seat at bind and refreshed on the M2 advertisement's cadence; the bootstrap is the ceremony's own: the initiator's endpoints row rides the deliver's machinery snapshot (one more adopted row, no new frame field), and the initiator's first dial of the recipient uses the compare code's candidates kept in its ceremony record, after which the recipient's own row has reached it. Reach is LAN candidacy over cached candidates plus iroh's direct dial — a group scope's members may live on different nests, so no relay serves it ([`p2p.md`](p2p.md) § The relay → *Across nests*), and a pair on two networks moves nothing until one is reachable, which the transfer row reads honestly ([`p2p-shared-set.md`](p2p-shared-set.md) § The transfer row of a pull that failed). A nest holding a group scope's sealed relay rows and chunks as a custodian — availability when no member is up — is the standing next step the plane's posture already allows (constraint (b): custody, never arbitration); named here, not designed.

**9. The losing replica keeps its edit — the loser's author is the retention seat (ruled 2026-10-30; the mechanics refutable at build time).** The conflict model is the folder family's, unchanged ([`conflicts.md`](conflicts.md) § Target model: every conflict auto-resolves, the losing version is always retained, the surface is a review list and never a chooser; the family split is recorded there, *Where the loser rests follows the family*) — what differs is only WHO retains. A folder set's nest retains every loser as a version when it lands the resolved report. A group set has no nest; its plane keeps one live relay row per path per writer (`retire_shadowed_relay_rows`), no history; and a body lives only where a member materialized it — so the one moment a superseded edit's bytes are known to exist anywhere is when its author's replica is about to overwrite them (the *Measured* block below: the judge's `Write` arm rests on "the old version stays nest-fetchable", false on this family). So **the author retains its own superseded edit, at that moment, before the write.** The trigger: the fold's converged landing (`PeerPageOrigin::Group`) would materialize a put, or apply a delete, over a path whose tracked head this device authored and lifted — the path's newest `own_change_log` row is sequenced and names the entry's manifest — and the disk is clean at it. Every other landing the judge admits overwrites a head some other author materialized and retains for itself, or bytes this replica fetched, so nothing of this replica's is lost there; an edit not yet lifted is never overwritten (refinement (3) of the lift and the fold). The order, fail-closed: (1) the local bytes are kept as a **retained version** under the set's state root beside the merge bases — never under the watch dir, which is the user's tree — keyed by the manifest hash the own row names (`own_manifests` already holds the manifest; serving the retained body to a member that asks for that manifest is named here, not designed); (2) the conflict is recorded in the set's own `sync_conflicts` as the row the folder family's nest would hold — `concurrent_edit`, resolved `latest_wins`, the winner the plane's row (its author, stamp and manifest, or the delete), the one candidate this replica's retained version; (3) only then the winner is written, or the fold's delete verdict applied. A retention that fails skips the row — counted, re-presented at the next fold — and writes nothing. What follows is each of the model's claims in plane terms. **The review list shows the row on the losing device, and "use the other version" re-publishes the retained bytes as a new local edit** — a fresh stamp, so the plane's `LatestWins` makes it the head on every member while the other version stays retained at its author: restore-as-re-point ([`file-versions.md`](file-versions.md) § Restore), the new row standing where the nest's re-pointed head row stands. **The text three-way merge moves, it is not lost:** the plane's merge is `LatestWins` and no device can change a cell's outcome, so a merged result is what a losing device *publishes* as its next row ([`conflicts.md`](conflicts.md) § Concurrent resolution, clause 1 — a resolution is an ordinary change), named here and not designed; until it exists a group set's effective policy is `Latest-wins-always`. **A winning delete is retained and then applied, never declined:** the folder family declines a tombstone over content the nest lacks because applying it would destroy the only copy, and the retention answers that reason, while the plane carries no causality to tell a user's second delete from a re-assert loop. **A versions list on a group set** is one row per writer per path plus what each author retains — named, not designed. Retained versions stay until their review row is used or dismissed; a cap is named, not designed (the build refined how often a loser arises — the status paragraph's *What the retention refined*, (5)). **Refused:** (a) a sibling "conflicted copy" file in the tree — no such shape exists on the folder family (the review list is the whole surface), and a sibling path would lift and propagate to every member as a new file; (b) the winner's replica as the keeper — it cannot be: when the loser's author pulls first, the body is gone before any other member could pull it; (c) accepting the loss as a stated bound — the ratified model holds on every family, and the 0.1.x window waives compatibility, never a user's edit. The engine half and the review-list surface, tui first, build it.

**10. A row names the head it wrote over — the base is a signed manifest, the check is a local equality, and a matched base drops the review row, never the retention (ruled 2026-10-30; the mechanics refutable at build time).** Decision 9's trigger fires on every landing over a lifted own head, and the build measured that the row cannot say whether its author SAW that head (the status paragraph's *What the retention refined*, (5)): a member editing the version it materialized from another lands a review row on that author's device, so every ordinary hand-off of a shared file lists a conflict that never was. [`conflicts.md`](conflicts.md)'s conflict is two edits neither of which saw the other, and a row that says what it saw is the folder family's causal watermark lifted to this family (`SyncChange.derived_through`, [`conflicts.md`](conflicts.md) § Target model → *The causal watermark*): there the claim is a set seq, a lower bound the receiver clamps; here the plane has no set seq and a path's head is a manifest, so the claim is the manifest. **The shape:** `GroupFileCore` gains `base_manifest`, optional — the manifest the author's replica tracked for the path when the edit was made, read from the projection before the write by the same engine that mints the pending row (refinement (3) of the lift and the fold keeps that head in place until the lift, so the base is exact against the author's own replica, never stale), `None` for a create over nothing or over a tracked delete; a delete row names the manifest it deleted. It rides INSIDE the signed core, as `writer_entry` does — additive and omitted when absent, so every row written before encodes byte-for-byte as it did and decision 2's frozen context stands; beside the core it would be an unsigned field a relaying member could strip or forge, and inside it the author alone asserts it and a relay carries it verbatim. **The check, at the reader:** the retention's trigger holds exactly as decision 9 states it — a converged landing over a path whose tracked head this replica authored and lifted, the disk clean at it — and on a hit the winner's base is compared with the own head's manifest: a local equality, no lookup of the base's own row (that row is the base writer's live relay row only until the writer writes again, and nothing in the check needs it). **Equal → an ordinary supersede: the bytes are retained exactly as before, but the record is a `superseded` row the review list never shows; absent or different → a concurrent loss, retained and listed as decision 9 built.** The retention stays unconditional because the base is a claim, not a proof: nothing a reader holds can show that the author materialized the head it names (a body reaches a member through any member's serve door, so the reader's own serve memo is no witness), so a member naming a co-member's head it never derived from — the one forgery the field opens — reaches exactly one thing, the review row, never the bytes; an enrolled member can already overwrite or delete every path at will (decision 5, all-writer), and listed-or-not is the whole of what a forged base changes. A `superseded` retention is the versions list's (decision 9: named, not designed) and the cap's first eviction class — the cap evicts `superseded` retentions before any listed loser, and a listed loser never while its row is open. **The four cases:** (a) the sequential edit — A edits the version it materialized from B and lifts with base B's manifest; at B the base is B's own lifted head: superseded, unlisted; at every other member the head is B's, not its own, so nothing of its own is overwritten and the trigger never fires; (b) the concurrent edit — neither saw the other, each row's base is an older head or none, so at each loser's author the base differs from its own head: listed, as decision 9 built; (c) the offline edit over an older head — A tracks X, B publishes Y, A edits over X before pulling and lifts with base X: whichever stamp wins the cell, the replica whose own lifted head is not the winner's base lists a loser and the replica whose head IS the base lists none — right on both sides, since the edit was concurrent with Y and was derived from X; (d) a delete — a base-matched winning delete retains as superseded, lists nothing and is applied; an unmatched one retains, lists and is applied — decision 9's delete arm unchanged, the base deciding the listing and never the apply. A stripped base cannot occur (it is signed), and a base naming a manifest the reader never had is case (b), the safe direction. **One duty the window defers:** the signing bytes re-encode the parsed core, so a reader older than a core field refuses every row carrying it — owed nothing while the product is 0.1.x ([`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 2, the fifth exception), and from 0.2.0 an additive core field needs the core to carry unknown fields through, or the signature to cover the received bytes: named here, not designed. The build carries the field through the core, the own row, the lift, the fold and the retention's record.
