## Implementation status today

The sections below describe target state for multi-domain mail hosting. Known gaps where current code lags target — read first when scoping a slice against this doc:

- **`mail_domains` table + admin WS-RPC surface** — table + DB API landed (tracked internally; foundation slice); the five admin WS-RPC kinds landed (tracked internally, § A1). Schema: `bins/fauna-nest/src/db/mail_domains.rs` (DB API: `add` / `soft_delete` / `restore` / `update_config` / `list_active` / `list_soft_deleted_within_30d` / `lookup_active` / `lookup_primary`). WS-RPC: `fauna.bridges.{add,remove,restore,list,update}_local_domain` (Admin-class, `bridge_routing_handlers.rs` + `bridge_method_allowlist.rs`), catalogued in `apps/bridges.md § Bridge-kind catalogue (caller classes)`, consumed via the shared `fauna_client_bridges::MailAdminClient`. The WS-RPC `add_local_domain` auto-determines `is_primary` (first domain = primary) and is idempotent on `domain_name`; `update_local_domain_config` carries only plain leave/set fields (`mta_sts_*`, `spf_record`, and `dmarc_policy_mode`, whose "clear" is choosing the default `reject` — `dmarc-reporting.md` § Multi-domain deployments); each per-domain knob needing a genuine clear gets its own dedicated set/clear RPC instead (`serialization.md` § Canonical IPLD dag-cbor → *Tri-state fields*): `set_catch_all_actor`, `set_role_address`, and `set_dkim_rotation_days` (the accelerated-rotation lever — § Selector). The legacy admin **HTTP** routes (`/api/admin/local_domains{,/{domain}/self_signed_cert}`, `admin_local_domain_{routes,tls}.rs`) were **retired** once all consumers migrated to the WS-RPC surface (no-HTTP directive; the e2e fixtures + the docker deploy test now call the kinds directly).

- **`whoami.Domain` + `whoami.dkim_selector` drift removed** — landed (tracked internally). - **Per-domain DKIM selector projection — built** (tracked internally; lifts the single-domain anchor from a prior track's Slice 1). `FetchConfigReply.dkim_selectors` is a `Vec<DomainDkimSelector>` — one `{domain, selector}` per **active** `mail_domains` row (each row's `dkim_selector`, defaulting to `"default"` when NULL), ordered like `local_domains`. It replaces the former single-anchor `primary_domain_dkim_selector`. **Signing is the nest's** (`mail-bridge-lifecycle.md` § DKIM provisioning (automatic) owns it): at the outbound hand-out the nest selects the signing domain by the **From: header domain** (RFC 6376 §3.6) via the shared `fauna_mail::outbound::dkim::select_signing_domain`, so each domain's outbound is signed with its **own** key. The bridge holds no key and consumes the same rule (UniFFI-exported as `select_signing_domain` — priority #2; never reimplemented in Go) for one thing: a From-header domain not in `local_domains` (and not a subdomain of any) is rejected at submission with `550 5.7.7 From: domain not local` (§ Signing-key selection at outbound time), keyed on the configured selector set. A local domain whose active selector has no key that opens leaves unsigned and is counted, never held. Proven by tier_3 `tests/e2e-unified/tests/test_mail_bridge_mta.py::test_submission_dkim_per_domain_from_selects_second_domain_key` (two local domains, each dkimpy-verified against its **own** published key record). The per-domain *selector label* is `"default"` for a domain whose `mail_domains.dkim_selector` is still NULL; the rotation writers (`force_rotate_dkim` and the scheduled auto-flip, § DKIM rotation below) write it per domain, and the `dkim_selectors` projection carries it.
- **Per-domain DKIM key generation — nest-held, minted when the domain is added (authoritative); DNS-record assembly built; cert provisioning not yet wired.** Each domain in the goal-doc has its own RSA-2048 + Ed25519 keypair (§ Per-domain DKIM); the store is `mail_dkim_keys(domain, selector)`, already per-domain, which `mail_domains` does not reference (§ Storage; the `dkim_key_blob_id` → `wrapped_blobs` indirection once named as a target was never built and its always-NULL column was dropped at nest schema 110). **The nest mints the key and keeps it (`mail-bridge-lifecycle.md` § DKIM provisioning (automatic) → *Custody moves to the nest* is the AUTHORITY for the mechanism; built 2026-10-03).** Adding or restoring a mail domain mints a fresh **Ed25519** key for its active selector (single key — the dual RSA+Ed25519 stays deferred, matching the live signing reality) on the connection that writes the row; boot does the same for any active domain found without one. The private half rests sealed under the nest's own key-encryption key beside the unsealed `public_dns_value`, and the nest signs with it at the outbound hand-out (`fauna.bridges.fetch_outbound_due`) — *no admin clicks, no client involvement, no bridge needed* (`bins/fauna-nest/src/mail_dkim_key.rs`; tier_3 `bins/fauna-nest/tests/mail_dkim_oracle.rs`). The tier_4 `tests/e2e-unified/tests/platform/docker/test_mail_deploy_dkim_auto_enable.py` (real deploy image: enable → approve → signed outbound `d=` aligned) asserts the outcome. **The former client-side keygen path was removed 2026-06-12** — `fauna-client-mail-settings::dkim_rotation` (`provision_initial_dkim_for_domain` / `rotate_due_dkim_selectors`), its `rpc_glue` / `fauna-ffi` / `fauna-wasm` wrappers, and the linux/windows add-domain + refresh triggers were all deleted as redundant with nest-side minting (it duplicated the nest's job and contradicted the custody model — § Per-domain DKIM → DKIM-key custody). The DNS-record bodies exist in `fauna_mail::dns::per_domain`; the DKIM TXT renders read-only + publishes from `admin-dns` (the `public_dns_value` rides `list_dkim_selectors`). Cert provisioning (§ Adding step 7.4) remains deferred. **Nest-side rotation new-selector provisioning — landed** (tracked internally): the scheduled rotation-mint (`bridge_routing_handlers.rs::run_scheduled_dkim_rotation_mint`, on the `main.rs` background-expiry tick before the auto-flip) mints the producer half the removed client sweep used to do — for each `dkim_rotation_due` domain with no rotation already in flight (newest-provisioned selector == active), it mints a fresh nest-held Ed25519 key under a `<YYYYMM>` selector (`CacheDb::mint_mail_dkim_key`), so the existing `run_scheduled_dkim_autoflip` then activates it after the 24 h cache-warmup. tier_3-proven by `test_mail_bridge_mta.py::test_scheduled_rotation_mints_new_selector_nestside` (due domain → nest mints `<YYYYMM>` in `list_dkim_selectors` → flip → outbound signed `s=<YYYYMM>`, dkimpy-verified). - **DKIM rotation — fully built and nest-side end-to-end** (emergency flip, tier_3-proven live with no restart; scheduled-due detection + signal; the 24 h scheduled auto-flip; **and the scheduled new-selector mint** — tracked internally). A **scheduled-automatic background behavior, not a wizard or button** (Option A 2026-06-09). Keygen + seal are nest-side throughout — the once-planned client producer (shared-Rust core in `libs/fauna-client-mail-settings::dkim_rotation`) was **removed 2026-06-12** and replaced by the nest mint (piece 5 below); no client ever holds the private key (tracked internally). The live per-domain selector flip is proven end-to-end by `tests/e2e-unified/tests/test_mail_bridge_mta.py::test_force_rotate_dkim_flips_active_selector_live` (tier_3: provision a 2nd selector for a *running* bridge, `force_rotate_dkim`, dkimpy-verify the outbound now signs `s=<new>` against the new selector's record with no restart); the full mint→flip cycle by `test_scheduled_rotation_mints_new_selector_nestside`:
  1. **Live flip, no restart — built.** The nest loads its signer afresh for each hand-out batch, so a flipped active selector — and a freshly-added domain — sign at the next hand-out with no process restart. The bridge's `mtaConfigHolder.ApplyConfig` (`bins/fauna-bridges/internal/mta/config_holder.go`) swaps in the new `dkim_selectors` on every `config_changed`, for its From-header ownership check alone.
  2. **Nest emergency `force_rotate_dkim` — built.** `fauna.bridges.force_rotate_dkim(domain)` (Admin; `bridge_routing_handlers.rs::force_rotate_dkim_handler`) flips `mail_domains.dkim_selector` to the domain's newest-provisioned selector (`mail_dkim_keys`, newest by `created_at` — the one the nest's rotation mint seated), skipping the 24 h wait, then pushes `config_changed`. Errors `no_dkim_selector_to_rotate` when nothing newer is provisioned. The selector-write rides the internal `MailDomainUpdate.dkim_selector` (not a manual admin knob — DKIM is automatic per `mail-policy-config.md`). Client method `MailAdminClient::force_rotate_dkim`.
  3. **Scheduled-due detection + signal — built** (tracked internally). The "when did the active selector activate" timestamp is the `mail_domains.dkim_selector_activated_at` column (`migrations.rs`; `MailDomain.dkim_selector_activated_at`), stamped on **every** selector flip by `update_mail_domain_config` — so the emergency `force_rotate_dkim` path and the future scheduled flip agree by construction; `None` until the first flip, with the due window then running from `added_at` (the first window). The due computation is the pure `db::mail_domains::dkim_rotation_due` / `MailDomain::is_dkim_rotation_due(now, default)` (per-domain `dkim_rotation_days` override, else the deployment-wide `DEFAULT_DKIM_ROTATION_DAYS = 90` = quarterly per `mail-policy-config.md` § DKIM, since no readable policy catalog for it exists yet). The **signal** the admin client reads is `MailDomainRow.dkim_rotation_due` (a nest-computed bool — the deployment default lives nest-side, so the client can't derive it itself) + `MailDomainRow.dkim_selector_activated_at`, both projected by `list_local_domains`.
  4. **24 h scheduled auto-flip — built** (tracked internally). The `main.rs` background tick (alongside the soft-delete GC) runs `bridge_routing_handlers::run_scheduled_dkim_autoflip`: it logs the due domains and, for each, auto-flips to the newest-provisioned selector **iff** that selector has aged past `DKIM_ROTATION_CACHE_WARMUP_MS` (24 h) — then pushes `config_changed` once so the MTA re-reads its selector set. Both rotation paths now share **one** flip primitive, `CacheDb::flip_to_newest_dkim_selector(row, min_provision_age_ms)` — the emergency path passes `0` (skip the wait), the scheduled path passes 24 h — so they agree on "newest-provisioned" + the activation stamp, and the flip is idempotent (re-running after a flip is a no-op, so a crashed tick is recoverable). A due domain with **no** newer selector provisioned yet is logged but not flipped: the rotation waits for the mint (piece 5) to provision one. It is a **scheduled-automatic background behavior, NOT a wizard** (§ ui.yaml surface — DKIM is admin-invisible); the once-proposed **emergency rotate button was considered and dropped** (Option A, 2026-06-09 — § Rotation), so `force_rotate_dkim` has no app UI trigger. Single Ed25519 key per selector (the dual RSA+Ed25519 stays deferred per the key/DNS/cert bullet above).
  5. **Scheduled new-selector mint — built** (tracked internally). The producer half, nest-side (replacing the removed client sweep). `bridge_routing_handlers::run_scheduled_dkim_rotation_mint`, on the same `main.rs` background-expiry tick **before** the auto-flip (piece 4), mints for each `dkim_rotation_due` domain with **no rotation already in flight** (idempotency gate: newest-provisioned selector == active — so re-running across the 24 h warmup, even across a month boundary, is a no-op until the flip lands). ## Goal

A single Fauna nest hosting mail for N domains end-to-end. Bar:

1. **Per-domain crypto + policy.** Each domain has its own DKIM keypair (with its own selector + rotation schedule), its own MTA-STS policy mode, its own DMARC policy (cross-link to `dmarc-reporting.md` § Multi-domain), its own catch-all designation (or no catch-all), its own role-address routing overrides.
2. **One MX target.** All N domains point their MX at the deployment's single mail server (`mail.<primary-domain>`). The mail server is one machine serving N domains via SNI — operational simplicity beats per-domain hostnames.
3. **Per-domain alias namespace.** `bob@domain1` and `bob@domain2` are distinct addresses; the resolver searches each domain's alias namespace independently. A user can claim addresses on multiple domains (deployment-wide actor identity, per-domain alias rows).
4. **One-click add/remove.** Admin adds a new domain via a wizard in their Fauna app: input the domain name → the client checks its **held** DNS-provider credentials cover the domain → nest flips the domain into `local_domains` + assembles the record **bodies** (`fauna.dns.list_records`) + provisions the cert via its own in-process ACME client, while the **client** publishes the assembled records (managed mode, via its held credentials) or shows them for the admin to paste (manual) — the nest never publishes DNS (`dns-management.md` § The two modes); the domain's DKIM key is then auto-provisioned **nest-side on the MTA's first read** (no client keygen — `mail-bridge-lifecycle.md` § DKIM provisioning (automatic)). Removal soft-deletes with 30-day recovery.
5. **Works out of the box.** A new domain ships with sensible per-domain defaults inherited from the deployment-wide settings; the admin only chooses the domain name at add-time — everything else is auto-defaulted: the MTA-STS policy mode is the nest's own and never an admin choice (§ Wizard steps, step 4), and the cert mode stays a Tier 2 override the admin *can* change, never a mandatory choice (§ Adding a new local domain step 3).

**Default-strict.** A new domain ships with `enforce` MTA-STS (after the fixed 7-day `testing` window, by the nest's own advance — § Per-domain MTA-STS → *The advance*), DMARC `p=reject; sp=reject`, DKIM keys auto-provisioned **nest-side on read** (keygen + seal run nest-side, never client-side; nest persists ciphertext only, never the plaintext private key — `mail-bridge-lifecycle.md` § DKIM provisioning (automatic)) — no catch-all (admin opts in explicitly per-domain). A misconfiguration of the multi-domain UX should not silently lower security on any domain.

## The `mail_domains` model

`mail.local_domains` is the deployment's set of mail-hosting domains. Behind the catalog binding, this is the `mail_domains` table — one row per current or recently-removed local domain. The single-string-list view (`mail.local_domains`) is a derived projection (the `domain_name` column of every row where `removed_at IS NULL`).

### Row shape

| Column | Type | Notes |
|---|---|---|
| `domain_id` | UUID | primary key |
| `domain_name` | TEXT | unique among non-deleted rows; lowercased; RFC 1035-syntactic |
| `is_primary` | BOOLEAN | exactly one row has `is_primary = true` (enforced via partial unique index `WHERE removed_at IS NULL`); the primary is the deployment's onboarding domain |
| `added_at` | TIMESTAMP | when the admin claimed the domain |
| `removed_at` | TIMESTAMP | nullable; non-null = soft-deleted (preserves audit + 30-day recovery window) |
| `restored_at` | TIMESTAMP | nullable; stamped when a soft-deleted row is restored within the window |
| `dkim_selector` | TEXT | the selector **label** (default `default`; NULL projected to `"default"`). The published record FQDN is `<selector>._domainkey.<domain_name>` |
| `dkim_rotation_days` | INTEGER | nullable; inherits `mail.dkim.rotation_days` if null |
| `dkim_algorithms` | TEXT[] | default `['ed25519', 'rsa-2048']` (both published) |
| `mta_sts_mode` | TEXT | `testing` / `enforce` — never set by a human. The add path always writes `testing` and the nest's advance is the only writer after it (§ Per-domain MTA-STS → *The advance*); the DDL's `enforce` column default is vestigial, and any other stored value is read as `testing` |
| `mta_sts_max_age_seconds` | INTEGER | default inherits global; minimum 86400 (1 day) — **project policy** (RFC 8461 sets only a maximum of 31557600 and recommends ≥ 604800) |
| `mta_sts_cert_mode` | TEXT | `expand_primary` / `wildcard` / `per_host`; default `expand_primary` |
| `catch_all_actor_id` | UUID | nullable; per-domain catch-all designation |
| `role_address_overrides` | JSONB | map of `{postmaster, abuse, noc, security}` → 64-char lowercase actor-hex; missing keys fall back to admin. `tlsrpt`/`dmarc_report` are **not** stored (always the deployment-wide processor — see § Per-domain role-address routing § Wire shape + storage) |
| `dmarc_overrides` | JSONB | the `<domain>` entry of `mail.dmarc.per_domain_overrides`; cross-link to `dmarc-reporting.md` § Multi-domain |
| `spf_record` | TEXT | the SPF TXT body for this domain; default `v=spf1 mx ~all` |

Indexes: `(domain_name) WHERE removed_at IS NULL` (the RCPT-TO local-domain lookup hot path); `(is_primary) WHERE removed_at IS NULL` (find-primary, with a uniqueness constraint enforcing exactly-one primary).

### The primary domain

Exactly one row has `is_primary = true`. The primary is the **claim-handle domain** — the `@domain` suffix of the handle the admin claimed with (`onboarding.md` § DNS configuration). It is the **sole determinant** of the deployment domain: there is no `FAUNA_DOMAIN` env var (retired — `domains-and-tls-bootstrap.md` § Env contract); the box boots domainless and learns its domain at claim. It is **auto-registered at claim time**: the wizard handle carries the domain (`alice@fauna.test`), the claim request forwards it as `mail_domain`, and for a real (`is_public_dns_name`) domain `claim_admin_core` calls `mail_enable::ensure_mail_domain_registered` to write the first `mail_domains` row (so `is_primary = true`, MTA-STS defaults `testing` / `expand_primary` matching the admin-dns add-domain path) — no manual admin-dns add-domain step. That primary row **is** the deployment identity: registering it also refreshes the sync `AppState.identity_domain` cache (a projection of the primary — no separate identity store) via `identity_domain_core::apply_primary_identity`, so `handle_domain()` / discovery / web / the TLS apex follow the claimed domain (`domains-and-tls-bootstrap.md` § Claim). A local-target claim (`alice@10.1.8.51`) registers nothing; identity falls back to `localhost`.

A **safety net** (`mail_enable::ensure_primary_mail_domain`) registers the same primary when claim-time didn't, so the primary is never silently missing on a real-domain box: when `mail_domains` is empty it auto-registers the nest's own domain, gated to a real (`is_public_dns_name`) domain — the mechanism, its two triggers (enable transition + nest boot), and the re-claim rationale are owned by `mail-bridge-lifecycle.md` § Mail-domain safety net (claim-time registration itself by `domains-and-tls-bootstrap.md` § Claim). It **composes** with claim-time registration — it fires only when nothing is registered, so a user who chose a *different* mail domain at claim is never overridden. The primary anchors:

- The **MX target**: every domain's MX record points at `mail.<primary-domain>` (one mail server hostname across the deployment).
- The **TLSRPT processor inbox**: peer MTAs send TLSRPT aggregate reports to `tlsrpt@<primary-domain>`, regardless of which of our domains they were trying to deliver to.
- The **DMARC processor inbox**: same logic — `dmarc-report@<primary-domain>` receives reports about every `local_domains` entry.
- The **List-Unsubscribe HTTPS endpoint**: the RFC 8058 one-click endpoint at `https://<primary-domain>/list/unsubscribe` works for lists hosted on any of the deployment's domains (`mail-mass-mailing.md` § The HTTPS endpoint owns the handler).
- The **MTA-STS / DKIM / ACME cert path**: the nest's own ACME-managed cert covers `mail.<primary-domain>` as the canonical SAN + extends to `mta-sts.<each-additional-domain>` per the `expand_primary` cert mode (see § Per-domain MTA-STS below).

Renaming the primary is **out of scope for this doc** — it's a multi-step admin action with extensive warnings (every peer MTA's cached MX / DKIM / DMARC / MTA-STS material would need to expire; the cert chain re-issued; the existing TLSRPT inbound flow re-routed). Covered by `mail-primary-domain-rename.md` — that doc owns the rename state machine, the cache-flush grace window, and the cert-chain re-issue ordering.

### Additional domains

Every non-primary row. Added post-onboarding via the workflow in § Adding a new local domain. No structural difference from the primary except `is_primary = false`; additional domains can be soft-deleted (the primary cannot).

## Per-domain DKIM

Each domain has its own DKIM keypair, **minted automatically nest-side and held by the nest** (built 2026-10-03 — `mail-bridge-lifecycle.md` § DKIM provisioning (automatic) → *Custody moves to the nest* is the authority for this custody decision). The key mints when the domain is added or restored, at boot for a domain found without one, and at rotation — never on a read. The nest persists the private half sealed under its own key-encryption key (`mail_dkim_keys`) beside the unsealed public components for DNS, opens it only to sign at the outbound hand-out, and no client and no bridge ever holds it.

> **DKIM-key custody:** admin/deployment-held (never per-user), generated nest-side and held by the nest, sealed under its own key-encryption key — the custody model, threat analysis, and provisioning mechanism are **owned by `mail-bridge-lifecycle.md` § DKIM provisioning (automatic)** (→ *Custody moves to the nest*, built 2026-10-03). What this doc adds: the DKIM key is a **distinct custody domain from user-content sealing** — per-user mail bodies are MLS-sealed to each *recipient's* key, while the DKIM key is the deployment's and shared across that domain's outbound; the two never mix (a DKIM key carries no decryption capability for user content, and a user-content key cannot sign DKIM).

### Key shape

> **Implementation status:** the shipped shape is a **single Ed25519 key** per selector (§ Implementation status today); the dual-key target below stays deferred.

For each `local_domains` entry, nest stores (the private half sealed under its own key-encryption key, plus the published public key):

- One **RSA-2048** keypair (broad-compatibility default per `mail-policy-config.md` Tier 2 `mail.dkim.algorithms`).
- One **Ed25519** keypair (RFC 8463 — peers that support it prefer the smaller signature).

Both keys' public components are published in DNS as separate TXT records under the same selector subdomain:

```
default._domainkey.<domain>. TXT "v=DKIM1; k=rsa; p=<rsa-pubkey-base64>"
default._domainkey.<domain>. TXT "v=DKIM1; k=ed25519; p=<ed25519-pubkey-base64>"
```

(Peer MTAs that don't support Ed25519 fall through to the RSA TXT record; peers that do support Ed25519 use whichever matches the signature in the message.)

### Selector

The selector is per-domain — the *label* (default `default`); its TXT records publish at `<selector>._domainkey.<domain>`. Selector rotation is **automatic, not a manual knob** (§ ui.yaml surface — DKIM is admin-invisible; there is no admin selector-name field): when a domain is due, the **nest** mints a new `<YYYYMM>` selector's key (and keeps it) and its public TXT publishes from `admin-dns`, nest waits 24 h for peer caches to update, then flips the signing key onto the new selector (the old TXT is later unpublished). The rotation window is captured in `mail.dkim.rotation_days` (default quarterly per `mail-policy-config.md` § DKIM). Rotation is **deployment-wide-default + per-domain override**: a domain that needs accelerated rotation (forensic event, key compromise suspicion) gets its own `dkim_rotation_days` value in the per-domain row — the **only** admin lever, since the rest is automatic. That lever is set/cleared via `fauna.bridges.set_dkim_rotation_days` (Admin; a shorter value makes the scheduled rotation fire sooner; `None` clears back to the deployment default) — a control-plane RPC with **no app UI** (DKIM stays admin-invisible), like `force_rotate_dkim`.

### Signing-key selection at outbound time

When the nest signs an outbound message at the hand-out, it selects the DKIM key by matching the **From: header domain** (the `d=` tag in the DKIM-Signature header per RFC 6376 §3.6 — the d= tag is the domain on whose behalf we sign). If From: domain is `<sub>.<our-domain>` (a subdomain we don't have an explicit `mail_domains` row for), the nest signs with the parent domain's key + sets `d=<our-domain>` and `i=<from>` (the i= tag carries the specific from address) per RFC 6376 §3.5. A message whose From: domain is **not** in `local_domains` (and not a subdomain of any local_domain) is rejected at submission with `550 5.7.7 From: domain not local`.

### What the bridge reads

Nothing is provisioned to the bridge: the DKIM key never leaves the nest (`mail-bridge-lifecycle.md` § DKIM provisioning (automatic) owns the mechanism). The bridge reads the per-domain selector set projected via `FetchConfigReply.dkim_selectors` (§ Implementation status today) for the From-header ownership check alone (§ Signing-key selection at outbound time).

### Rotation

DNS publish/unpublish of the selector's TXT records is **client-side** (the same managed-`DnsProvider` dispatch / admin-by-hand model that publishes every other per-domain record — § Per-domain DNS records, authoritative `dns-management.md`); the **nest** never publishes DNS. The nest-side rotation job is just: detect "due", signal it, and **flip the active selector** (`mail_domains.dkim_selector` → the new selector — what `FetchConfigReply.dkim_selectors` projects and the nest signs by).

- **Scheduled rotation:** every `dkim_rotation_days` (default quarterly), nest signals a rotation is due. **Provisioning the new selector's key is nest-side** — the nest mints it and keeps it (§ Per-domain DKIM → DKIM-key custody). The flow is **mint-first, then flip after the cache-warmup** (the new selector's TXT must be published *before* it signs, so receivers can verify once it becomes active — a flip-first ordering would sign under an unpublished key during DNS propagation): on the background tick, nest **mints** a fresh `<YYYYMM>._domainkey.<domain>` key (`run_scheduled_dkim_rotation_mint` — a new nest-held Ed25519 key under the `<YYYYMM>` selector, persisted in `mail_dkim_keys`) while the **old** selector keeps signing; its public-key TXT publishes from `admin-dns`; then once the minted selector has aged past the 24 h peer-cache warmup, `run_scheduled_dkim_autoflip` flips `mail_domains.dkim_selector` onto it (`DKIM_ROTATION_CACHE_WARMUP_MS`); the old TXT is later unpublished (in **managed** mode, by the client-side withdraw-aware converge reconcile once the old selector is revoked and drops from `list_dkim_selectors` — `dns-management.md` § Reconcile → Withdraw-aware convergence; in **manual** mode the admin removes it by hand). This is the *whole* nest-side cycle — the add-domain and boot doors mint only a domain's **active** selector, so the *next* selector is the dedicated mint job's. **Landed** (tracked internally; see § Implementation status — mint + flip + emergency `force_rotate_dkim` all built, tier_3-proven).
- **Emergency / accelerated rotation:** the *user-facing* accelerated path is **not a button** — DKIM is automatic + admin-invisible (no manual cards or wizard pickers, § ui.yaml surface; user directive 2026-05-24). An admin who needs faster rotation (forensic event, key-compromise suspicion) sets a shorter `dkim_rotation_days` on the per-domain row via `fauna.bridges.set_dkim_rotation_days` (§ Selector), which makes the **scheduled** path above fire sooner; the rest is automatic (nest mints the new selector + flips after the 24 h cache-warmup). The **immediate skip-the-24h** primitive `fauna.bridges.force_rotate_dkim(domain)` (Admin RPC) still exists and is tier_3-proven — it flips the active selector to the domain's newest-provisioned selector **immediately**, skipping the wait (accepting that messages signed during the cache-flush window may fail DMARC at receivers with stale caches), then pushes `config_changed`, and the nest signs `s=<new>` at the next hand-out (no restart) — but it has **no app UI trigger** (ratified Option A, 2026-06-09: an emergency rotate button was *considered and dropped* to keep DKIM uniformly automatic across all 7 apps; resurface it only with explicit user approval for a new `admin-dns` deviation). It remains reachable for incident response by the box owner with direct nest access / a future automated compromise-response policy.

## Per-domain DNS records

For each `local_domains` entry, nest assembles the following record **bodies** (authoritative here); how they reach DNS is the **two modes** of `dns-management.md`, which is authoritative on the publish model: when an **admin client** holds usable **persisted** DNS-provider credentials for the domain (Fauna-managed), the **client** publishes + reconciles them via the `libs/fauna-provisioning` `DnsProvider` dispatch (the nest never holds the credential or publishes — the nest-side credential table + publish loop are retired, `dns-management.md` § Where the credential lives); otherwise the admin publishes them by hand and the nest's `dns-management.md` § Live verification shows a red/green per-record check. (Additional domains delegated to a different provider: the admin adds that provider's credentials, persisted client-side the same way.) The record **bodies** below are authoritative regardless of mode:

| Record | Default body | Notes |
|---|---|---|
| `<domain> MX 10 mail.<primary-domain>.` | one row per local domain pointing at the single MX target | the actual mail server is one machine; all domains share it via SNI. **The target is fully-qualified (trailing dot)** — a dotless target is treated as zone-relative by some providers (Hetzner) and double-appended to `mail.<primary>.<domain>`, an unresolvable MX that bounces all external inbound (live example.com incident, fixed) |
| `<domain> TXT "v=spf1 mx ~all"` | from `mail_domains.spf_record`; admin-customizable | the `~all` softfail mode is the long-term-defensible default (`-all` is harsh but acceptable; admin can opt in) |
| `default._domainkey.<domain> TXT "v=DKIM1; k=rsa; p=<pubkey>"` | RSA key | one row per algorithm |
| `default._domainkey.<domain> TXT "v=DKIM1; k=ed25519; p=<pubkey>"` | Ed25519 key | second row |
| `_dmarc.<domain> TXT "<assembled-record>"` | per `dmarc-reporting.md` § DMARC policy publication | the per-domain DMARC overrides apply |
| `_mta-sts.<domain> TXT "v=STSv1; id=<policy-version-hash>"` | per RFC 8461 §3.2 | the id changes on policy file change so peer MTAs re-fetch |
| `_smtp._tls.<domain> TXT "v=TLSRPTv1; rua=mailto:tlsrpt@<primary-domain>"` | TLSRPT destination | all domains point at the single primary-domain processor |
| `_25._tcp.mail.<primary-domain> TLSA 3 1 1 <sha256(floor-key SPKI)>` | **automatic** — emitted only while the MX is on the floor | **One** host-level record for the whole deployment: every local domain MXes to the single `mail.<primary-domain>` host (§ Compile-time decisions), so a DANE sender to any domain looks up the pin here — not one record per domain. DANE-EE / SubjectPublicKeyInfo / SHA-256, pinning the served self-signed floor leaf's SPKI (= the **stable** floor key, `../architecture/nest/tls-certificates.md` § A/§ D, so a routine renewal never churns it). **Cert-coupled, not an admin opt-in** (symmetric to the published-MTA-STS-mode coupling below): present while the MX is on the floor, **withdrawn** once a trusted cert covers it (a floor-key TLSA against a trusted cert would DANE-fail). No DNSSEC probe — a non-DNSSEC sender treats the unsigned TLSA as absent (RFC 7672 §2.1.1), so publishing it is harmless there and does its job on DNSSEC domains. Built by `fauna_mail::dns::host::build_mail_tlsa_record`, emitted by the nest's `list_records` cert-coupling (`bins/fauna-nest/src/dns_handlers.rs::append_floor_mx_tlsa`) |

### Publication lifecycle

How the assembled bodies **reach** DNS is the **two modes** of `dns-management.md` (authoritative): in **managed** mode the admin's **client** publishes them via its held `DnsProvider` credentials; in **manual** mode the admin pastes them by hand, with the nest's live red/green verify (`fauna.dns.verify_records`) showing status. **The nest never publishes DNS** in either mode.

- **Initial publication** — `add_local_domain` writes the `mail_domains` row (the domain appears in the Domains list immediately); the record **bodies** are assembled by `fauna.dns.list_records`, and the **client** publishes them (managed) or shows them to paste (manual). Publication is never a hard gate on the add — a not-yet-green record shows red until it propagates (`dns-management.md` § Live verification), the admin is not blocked.
- **Per-domain policy change** — admin edits the per-domain detail page → nest re-assembles the affected record **body** (`list_records`) → the **client** re-publishes it (managed-mode reconcile) or the admin re-pastes it (manual). Lifetime in caches is bounded by the published TTL (3600 s default; matches the primary domain's TTL).
- **Domain removal** — nest soft-deletes the `mail_domains` row (30-day recovery); the **client** withdraws every record above (managed-mode reconcile) or the admin removes them by hand (manual). The MX record is withdrawn last (peer MTAs that have already initiated delivery against the cached MX get the final delivery in flight; future deliveries see NXDOMAIN on `<domain> MX` and stop).
- **Rate-limited** — the **client's** managed-mode reconcile rewrites at most one record per `local_domains` entry per minute, per `dmarc-reporting.md` § Architectural rules's TXT-rewrite rate limit (the rule generalizes across all per-domain records; it binds the client that writes to the provider, defending against an admin-UI loop DDoS-ing the provider — the nest has no DNS-provider write path). *(Not yet built — the managed-mode reconcile is create-only today; `dns-management.md` § Reconcile.)*

### Compile-time decisions (NOT configurable)

- The DKIM TXT record format (RFC 6376 §3.6.1) — not a knob.
- The MX target uniqueness (`mail.<primary-domain>` for all domains) — not a knob; admin running multiple mail servers needs a different deployment topology.
- The MTA-STS policy file format (RFC 8461 §3.2) — not a knob.
- The TLSRPT destination format (RFC 8460 §3) — not a knob.

## Per-domain MTA-STS

Each domain publishes its own `_mta-sts.<domain>` TXT record and serves its own MTA-STS policy file at `https://mta-sts.<domain>/.well-known/mta-sts.txt` per RFC 8461 §3.2.

### Policy file content

```
version: STSv1
mode: <enforce|testing>
mx: mail.<primary-domain>
max_age: <seconds>
```

Per-domain `mode` is allowed — a freshly-added domain runs `testing` while its MX record and DKIM publication propagate, and the nest moves it to `enforce` by itself (§ Wizard steps, step 4, ruled 2026-10-03); no admin sets it. The policy-version-hash in the TXT record (the `id=` value) is recomputed every time the policy file changes; peer MTAs detect the change via the TXT and re-fetch the policy file.

**The published `mode` is coupled to MX cert reality (cert-honesty rule).** The MX cert may fall back to the **always-live self-signed floor** if a trusted-cert renewal lapses ([`../architecture/nest/tls-certificates.md`](../architecture/nest/tls-certificates.md) § A) — and a domain whose MX is currently on the floor must **not** advertise `enforce`, or a sender that fetched the `enforce` policy then refuses the non-WebPKI MX (RFC 8461 §5). So while a domain's MX is on the floor the *published* mode drops `enforce → testing`, restoring `enforce` once a trusted cert is live; this doc owns the `mta_sts_mode` storage + values, `tls-certificates.md` § D owns the coupling rule. (On a **DNSSEC** domain the automatic self-signed-MX TLSA below keeps the floor MX DANE-trusted, so `enforce`-equivalent assurance survives without a CA — see the § Per-domain DNS records TLSA row.)

### The advance — `testing` to `enforce`, by the nest's own hand

No human sets a domain's MTA-STS mode (§ Wizard steps, step 4). The stored mode has two values, `testing` and `enforce`, and two writers: the add path, which always writes `testing`, and the nest's **advance**, which moves a domain to `enforce` once both conditions hold.

- **(a) The mail name is trusted.** The listener serves a CA-issued certificate covering `mail.<primary-domain>` — the same served-certificate reading the published-mode coupling uses (`cert_health_state` is anything but on-the-floor; `tls-certificates.md` § D). Every local domain MXes to that one host, so the whole deployment shares one trust reading. It is read at the moment of the advance only: the certificate need not have been trusted for the whole window.
- **(b) The window has run out.** Seven days — the Rust constant `MTA_STS_TESTING_WINDOW_MS`, no knob — counted from the later of the row's `added_at` and its `restored_at`. **A restore restarts the window** for a domain still in `testing`: while the domain was removed its policy host answered 404, so peers observed nothing and the days it spent removed are not warm-up. A domain that was already `enforce` when it was removed is still `enforce` when restored.

**Where it runs.** `mta_sts_advance::advance_mta_sts_modes`, called from the nest's hourly maintenance tick (`main.rs` — the tick that also runs the soft-delete GC and the scheduled DKIM rotation). That tick fires first at boot, so the boot pass and the periodic pass are one call site and a restart never strands a domain. It is deliberately **not** in the ACME lifecycle loop: that loop runs only on a nest that orders its own certificates, and a mail name can become trusted without it (client-driven issuance, `tls-certificates.md` § C) — the advance reads what the listener serves, not who ordered it. An hour's granularity is ample against a seven-day window.

**One-way and idempotent.** The pass is a single statement over active rows whose stored mode is `testing`, so running it twice, or crashing straight after it, changes nothing more. Nothing ever moves a domain back: a certificate that lapses after the advance lowers only what is *published* (the cert-honesty rule above) and leaves the stored `enforce` in place, so the published mode returns by itself when a trusted certificate does. After a pass that moved something the nest pushes `config_changed` (`local_domains`) to its bridges, as every other `mail_domains` mutation does.

**What the admin sees.** The advance changes the policy body, so the expected `_mta-sts.<domain>` TXT `id=` changes once (§ Policy file content), and the record list on `admin-dns` shows the new value like any other record change (`dns-management.md` § Live verification). There is no control, no prompt and no setting.

**The rename consequence.** `start_primary_domain_rename` refuses a target whose stored mode ranks below the current primary's (`mail-primary-domain-rename.md` § Don't do these — TLS-posture monotonicity). With no human setting the mode, the one way that refusal now arises is a target still inside its window under an `enforce` primary — and the remedy is to wait: the nest advances the target by itself, at most seven days after it was added (or restored) on a trusted mail name, and the rename starts then.

**No clock knob.** The pass takes `now` as a parameter (`advance_mta_sts_modes_at`, over `advance_mta_sts_testing_to_enforce_at`) and production passes the wall clock; the binary gains no environment variable or flag to move time (`../principles.md` § One configuration surface). Tests call the parameterised core.

### One owner for the MTA-STS wire vocabularies — no binary and no language re-derives them

Two token sets cross the nest ⇄ Go-bridge wire whenever mail is delivered: the **lookup outcome** (the `outcome` field of `fauna.bridges.fetch_mta_sts_policy`, distinguishing "no STS advertised" from "advertised but the body fetch failed" from "body unparseable" from "policy in hand") and the **RFC 8461 §3.2 `mode`** carried inside the policy body. Both have exactly one owner: `fauna_mail::outbound::mta_sts::MtaStsOutcome` and `::MtaStsMode`. Nest asks the owner in both directions (`as_wire` / `from_wire`, `as_str` / `FromStr`); the Go bridge names them through the `wsrpc.MtaStsOutcome` / `wsrpc.MtaStsMode` const families and never spells a token.

The stake is that the outcome is not a one-way report — it makes a **round trip through the other binary**. The bridge echoes it back on `report_tls_attempt` so nest rebuilds the same RFC 8460 §4.4 TLSRPT policy bucket without a second fetch, so a producer and a consumer that disagree mis-attribute every report; and RFC 8461 §5 makes the tokens load-bearing in the safety direction (a published-but-broken policy is treated as no-policy and must never force plaintext or refusal), so a token one side stops recognising becomes a delivery decision taken on a fallback arm. Nest answers an unrecognised outcome with `malformed` rather than guessing, because the fail-safe direction is not the same for all four.

The cross-language half is pinned like the mail-auth verdicts are, in the opposite direction: `libs/fauna-mail/tests/go_wire_outcome_contract.rs` derives both token lists live from the owning enums and pins `bins/fauna-bridges/internal/wsrpc/testdata/go-wire-outcomes.json`; `internal/wsrpc/go_wire_outcome_contract_test.go` compares that fixture against the Go const families in both directions and bans a hand-spelled token in `internal/mta/outbound.go`. The existing `reply-*.cbor` round-trip fixtures cannot cover this — they catch a field rename or type change, and a `string` field round-trips byte-identically whatever value it holds. Priority #2/#4.

### MTA-STS HTTPS cert (the cert mode)

The `mta-sts.<domain>` hostname needs a valid cert. **The issuer is the nest's own ACME client + per-SNI `MultiDomainCertResolver`** (HTTP-01 on a public nest, client-published DNS-01 behind NAT — `../architecture/nest/tls-certificates.md` § B), **not** an external `certbot` (the certbot phrasing below is legacy and describes only the *SAN strategy*, not the issuer). The `mta_sts_cert_mode` (Tier 2 knob, persisted per-domain via `mail_domains.mta_sts_cert_mode`) selects which SANs a domain's cert carries. It is auto-chosen at domain-add time (from the add flow's DNS-provider check, with a collapsed advanced override — § Adding step 3) and stays admin-editable post-add via `update_local_domain_config` — the primary-rename flow depends on that edit (`mail-primary-domain-rename.md` refuses a `per_host`/`wildcard` promotion target until the admin sets it `expand_primary`):

| Mode | When | SAN strategy (issued by the nest's ACME client) |
|---|---|---|
| `expand_primary` | additional domain on the same DNS provider as the primary | add `mta-sts.<additional-domain>` as a SAN on the deployment's primary cert. Works only if all domains validate under the same path (HTTP-01 needs the apex publicly reachable; DNS-01 needs the same client-held provider credentials). **Default for additional domains on the same provider as the primary.** |
| `wildcard` | admin opts for one-cert-per-domain | issue a wildcard cert for `*.<domain>` covering `mta-sts.<domain>` + future `<sub>.<domain>` needs; requires DNS-01 challenge. Useful if the admin wants the new domain isolated from the primary's cert lifecycle. |
| `per_host` | admin opts for minimal cert footprint | issue a single-SAN per-SNI cert for `mta-sts.<domain>` (the `web_content/cert.rs` per-domain loop → `MultiDomainCertResolver::add_domain`); safe + minimal but one cert per domain to renew. Useful for domains on a different DNS provider than the primary. **Default if the new domain shares no DNS provider with the primary.** |

Renewal is the nest's own ACME renewal task + the `cert_watcher_task` hot-reload (no process restart) — it extends to every per-domain cert; the admin manages no renewals manually. A renewal that lapses falls back to the per-SNI self-signed floor (`../architecture/nest/tls-certificates.md` § A), which the cert-honesty coupling above keeps from advertising `enforce`.

### Policy-file server

The HTTPS endpoint serving the MTA-STS policy file at `mta-sts.<domain>` runs on nest's existing HTTPS listener (the same port 443 SNI dispatcher that handles app traffic). On request for `https://mta-sts.<our-domain>/.well-known/mta-sts.txt`, the dispatcher:

1. Matches the requested **Host header** (`mta-sts.` prefix stripped) against `local_domains` (lookup → `mail_domains` row); if no match, returns 404 with empty body (peer MTA treats as MTA-STS unavailable). A well-formed fetch sends `Host: mta-sts.<domain>` matching its SNI, but the dispatcher keys on Host, not the raw TLS SNI value (`mta_sts_handler`, `lib.rs`).
2. Loads the `mta_sts_mode`, `mta_sts_max_age_seconds` from the per-domain row.
3. Assembles the policy file body.
4. Returns it with `Content-Type: text/plain; charset=utf-8` and `Cache-Control: max-age=86400`.

The policy file is **assembled on each request** (no caching layer) — the cost is negligible and avoids stale-content bugs.

## Per-domain TLSRPT

Each domain publishes `_smtp._tls.<domain> TXT "v=TLSRPTv1; rua=mailto:tlsrpt@<primary-domain>"`. The TLSRPT inbound report processor is **deployment-wide and lives at the primary domain** — peers send reports about delivery to any of our domains to the single processor inbox.

The processor (per `smtp-server.md` § TLSRPT inbound report listener) accepts inbound reports at `tlsrpt@<primary-domain>`, validates the JSON-schema body per RFC 8460 §4.4, stores in `tlsrpt_inbound_reports(submitter, report_id, received_at, payload)` with a `policy_published.domain` field tagged from the report body — the per-domain admin-pane dashboard filter reads that column. No per-domain inbox is needed; the processor partitions on read.

The TLSRPT outbound reporter (per `smtp-server.md` § TLSRPT outbound reporter) buckets verdicts by **peer domain** (the receiver's domain, not ours) and generates one report per peer per day. The reporter's per-our-domain context is incidental — it sees the inbound (peer-originated) mail under one of our `local_domains`, but the outgoing report's `policy_published.domain` is the **peer's** domain (we're telling them about their policy's behavior). Our local-domain identity is not in the outbound report.

Cross-link to `dmarc-reporting.md` § Multi-domain deployments (the canonical home). Each local_domain has its own `_dmarc.<domain>` TXT record assembled from the deployment-wide defaults + the per-domain override map (`mail.dmarc.per_domain_overrides`, stored in `mail_domains.dmarc_overrides` JSONB).

## Per-domain catch-all

`mail-policy-config.md`'s `mail.inbound.catch_all_actor` is **promoted from a single nullable actor_id to a per-domain map** `mail.inbound.catch_all_per_domain` (key = `<domain>`, value = `<actor_id>?`). Each domain may have its own catch-all designated actor or no catch-all. The existing single-value knob is kept as the deployment-wide default — applied to any `local_domain` entry not explicitly in the map (so adding a new domain doesn't surprise-enable a catch-all).

User-tier catch-all remains **forbidden** per `mail-aliases.md` § Kind 4 — the catch-all is admin-tier per-domain.

### On match at RCPT TO

Per the per-domain catch-all logic in `mail-aliases.md` § Resolution order step 5, but with two header stamps instead of one:

- `X-Fauna-Address-Catchall: true`
- `X-Fauna-Address-Catchall-Domain: <our-domain>` ← **new in this doc**

The second header lets the receiving actor's filter rules see which of the deployment's domains the catch-all fired on (`filter rules treat anything caught by catch-all on community-domain as low-priority`).

### Catch-all conflict-of-interest at remove-domain time

When the admin removes a domain that has a catch-all, the catch-all designated actor's mailbox may receive mail-in-flight during the propagation window (peer MTAs caching the MX). After `remove_local_domain` returns, the MTA rejects mail to the removed domain at RCPT TO (the domain is no longer in `local_domains`); the catch-all designation is irrelevant. The catch-all row is preserved in the soft-deleted `mail_domains` row in case of re-add (the catch-all comes back with the domain).

### Catch-all designation and account succession

A catch-all naming an actor who later undergoes account succession is **cleared, not followed or left in place** — the succession ceremony nulls `mail_domains.catch_all_actor_id` when it names the retired identity, rather than re-aiming it at the successor (an admin's routing decision isn't the succeeded account's to inherit) or leaving it pointed at the retired actor (whose surviving recipient seal key would otherwise keep sealing unmatched mail to a now-thief-derivable key indefinitely). Unmatched mail then rejects at RCPT TO instead of silently reaching a burned key; re-designating afterward is a fresh admin action. Mechanism + rationale: `succession-aftermath.md` § Re-key scope (the worked example there).

## Per-domain role-address routing

`mail-policy-config.md`'s `mail.inbound.role_addresses` is **promoted from a flat map to a per-domain map** `mail.inbound.role_addresses_per_domain` (key = `<domain>`, value = `{postmaster_actor, abuse_actor, noc_actor, security_actor, tlsrpt_destination, dmarc_report_destination}`).

### Default routing

Every domain's role addresses route to the admin's mailbox (the admin owns `postmaster@<each-of-our-domains>` by default). The admin override maps in `role_address_overrides` per `mail_domains` row.

### Per-domain override

The admin can override per-domain — e.g., delegate `abuse@<community-domain>` to a community moderator actor while keeping `abuse@<primary-domain>` on the admin. Override semantics:

- `postmaster@<domain>` / `abuse@<domain>` / `noc@<domain>` / `security@<domain>` — route to the per-domain-overridden actor's mailbox.
- `tlsrpt@<domain>` — special-cased: always routes to the **deployment-wide TLSRPT processor** regardless of per-domain override (cross-link to § Per-domain TLSRPT above — there is no per-domain TLSRPT processor).
- `dmarc-report@<domain>` — same special-case: always routes to the deployment-wide DMARC processor.

### Wire shape + storage (ratified 2026-06-08)

**Storage.** `mail_domains.role_address_overrides` is a JSON object keyed by the overridable role local-part with **64-char lowercase actor-hex** values (the crate-canonical actor-id string form, `fauna_mail::segments::placement::actor_id_hex`); an absent key falls back to the deployment admin. Only the four overridable roles are representable — `tlsrpt` / `dmarc-report` are **never** stored here (they always route to the deployment-wide processor, above). The column is SQL NULL when no override is set. Example (postmaster delegated, others on admin):

```json
{"postmaster":"ab12…<64 hex>"}
```

The typed shape is `fauna_protocol::bridge_routing::RoleAddressOverrides` (re-exported as `fauna_mail::aliases::role_overrides::RoleAddressOverrides`, whose `parse_stored`/`to_stored` are the column's one JSON encoding — pure, so the writer and the RCPT-time resolver agree on it). A malformed/undecodable value degrades to admin — never a 550 (the never-reject invariant).

**Wire (typed, 2026-10-02).** `MailDomainRow` — the row every admin-mail reply an app reads carries — holds `role_address_overrides: RoleAddressOverrides` and `dmarc_overrides: DmarcOverrides` (the shape [`dmarc-reporting.md`](dmarc-reporting.md) § Multi-domain deployments owns), never the column's JSON text: the JSON object is the at-rest encoding only. The nest projects each stored value through its typed shape, and a value that does not decode projects as **no override**, so one corrupt column never fails the reply it rides in — the same reading the resolver and the DNS surface take.

**Writer.** `fauna.bridges.set_role_address(domain, role, actor_id)` (Admin), a dedicated setter mirroring `set_catch_all_actor` — the per-key set/clear is a tri-state not DAG-CBOR-round-trippable, so it cannot ride `UpdateLocalDomainConfigRequest`. `role` is a `RoleAddressKind` enum of the four overridable roles (`postmaster` / `abuse` / `noc` / `security`); `actor_id = Some(32-byte ByteBuf)` designates the override, `None` clears it. The nest does an **atomic read-merge-write** of the override map so a set on one role preserves the others. (The `admin-dns-domain-role-address-*` client picker that calls this is a separate per-app track.)

**One owner for the role vocabulary — no app re-derives it.** *Which* roles are overridable, *in what order* the pickers draw them, each one's `role_address_overrides` storage key, and the tag the `SetRoleAddress` action carries are **one table**, `fauna_client_mail_settings::local_domains::role_address_options()` (over `RoleAddressKind::ALL` + `as_storage_key`). The storage key is load-bearing four times over — the JSON key the nest reads back, the reserved local-part routed, the `<key>@` caption, and the `admin-dns-domain-role-address-<key>-select` element-id suffix — so a client that spells it itself can silently address a role the nest does not recognise, designating nothing with no error anywhere. Rust apps call `as_storage_key` directly; every other app reads the table through its binding (web: the wasm `roleAddressOptions`), the same shape `family-safety.md` § Where logic lives uses for `content_floor_options` / `unknown_sender_options`. Priority #2/#4.

### Reserved local-parts per-domain independence

The reserved local-parts (`postmaster`, `abuse`, `noc`, `security`, `dmarc-report`, `tlsrpt`) are reserved **per-domain independently** per `mail-aliases.md` § Reserved local-parts. A user trying to claim `postmaster@domain2` is refused at create-time even if `postmaster@domain1` is owned by the admin (each domain's reservation is independent). The reservation list is deployment-wide via `mail.inbound.reserved_local_parts` (Tier 2); admin-added reserved local-parts apply across all local_domains uniformly.

## Per-domain alias namespace

Cross-link to `mail-aliases.md` § Storage (`account_aliases` already has a `local_domain` column with uniqueness on `(local_domain, pattern, kind)`). Each `local_domains` entry is a **separate alias namespace** — `bob@domain1` and `bob@domain2` are distinct addresses; the resolver searches each domain's namespace independently.

### Actor identity is deployment-wide

A user is one actor (identified by their handle on the primary domain at signup); the user can claim addresses on multiple domains as separate exact aliases. So one actor's `account_aliases` may carry, e.g.:

| pattern | local_domain | kind |
|---|---|---|
| `bob` | `primary-domain` | exact (the canonical signup alias) |
| `bob.smith` | `primary-domain` | exact |
| `bob-*` | `primary-domain` | wildcard_prefix |
| `bob` | `community-domain` | exact |
| `bob-newsletter` | `community-domain` | exact |
| `bob-*` | `community-domain` | wildcard_prefix |
| `bob-temp-AbCdEf` | `primary-domain` | disposable |

### Per-domain wildcard independence

One user can have a wildcard prefix on every domain they own addresses on (`bob-*@domain1` AND `bob-*@domain2` are two separate rows, one per local_domain). The one-wildcard-per-actor constraint per `mail-aliases.md` § Kind 3 is **per (actor, local_domain)**, not deployment-wide.

### Per-account alias cap composition

`mail.account.exact_aliases_max` (Tier 2, default 20) is **across all domains for one actor** — the cap is for storage/namespace abuse total, not per-domain. So a user can have 5 exact aliases on domain1 + 15 on domain2 = 20 total (at the cap); adding a 21st on either domain refuses with `409 exact_aliases_max_exceeded`. Admin override of the cap via `mail.account.exact_aliases_max` Tier 2 applies uniformly.

### Cross-user uniqueness per-domain

`(local_domain, pattern, kind=exact)` uniqueness means two **different** users can claim `bob@` on different domains (alice owns `bob@domain1` and a separate user owns `bob@domain2`). This is by design — the admin may operate `domain1` as their personal mail and rent `domain2` to a friend running their own users on it.

The deployment-wide "actor identity is one" rule means a single user is one actor regardless of how many addresses they own; but address-ownership-per-domain is independent. Two distinct users on the same deployment can both have `bob` as their handle if they signed up on different domains, except for the **handle-uniqueness rule** in `onboarding.md` § Handle entry: handles are unique within the deployment's user table (the user's handle is their primary-domain identifier; two users with the same handle on different domains is structurally forbidden by the user-table unique constraint on `handle`). So this concern is moot — `bob@domain1` and `bob@domain2` can be the same user (with two exact aliases) or one user vs. nobody, but not two distinct users. That "same user on both domains" property is exactly what makes a handle addressable on every active domain — see § Multi-domain handles.

## Multi-domain handles

A **handle** (`bob`) is the user's deployment-wide social identity — a bare local-part stored once in `users.handle` under a **global** unique constraint (`idx_users_handle`), mapping to exactly one actor (the Ed25519 keypair whose public key *is* the actor id). A handle is **not** per-domain-namespaced: unlike a mail alias (keyed `(local_domain, pattern)`, so two users may each hold the `bob@` alias on different domains — § Cross-user uniqueness per-domain), a handle belongs to one actor across the whole deployment. This section is the authority for how that one global handle relates to the deployment's N local domains; it is the handle-layer counterpart to the per-domain mail-address model above.

### The model: one handle, addressable on every active domain

The handle `bob` is **addressable and login-reachable as `bob@<domain>` for every active `local_domains` entry**, and resolves to the same actor no matter which of the deployment's domains it is reached under. This mirrors the mail send-from model — a user sends `From: <handle-localpart>@<any-owned-local-domain>` (§ Cross-domain submission policy) — and the deployment-wide-actor rule (§ Actor identity is deployment-wide): the `@domain` part of a handle reference selects *which of the deployment's domains the reference is expressed under*, never *which actor* (the actor is fixed by the bare local-part).

For a deployment serving `domain1` (primary) + `domain2`:

- `@bob@domain1` and `@bob@domain2` both resolve to the one actor `bob`.
- `bob` can be found and can log in via either domain.
- The **primary domain is the canonical / default display (identity) domain** — `AppState::handle_domain()`, the projection of the primary `mail_domains` row set at claim (`domains-and-tls-bootstrap.md` § Claim). A handle reference that names an active local domain is honored as-is; a bare-handle lookup (no domain) is reported under the identity domain.

There is **no per-domain handle namespace** and **no per-user "which domains am I on" table**: a handle is valid on *every* active local domain by construction, because the deployment serves them all for its single user population. Renting a domain to an independent user population with its own separate `bob` is therefore **out of scope** — it would require both a per-domain handle namespace and a per-domain actor population, which the global `users.handle` constraint (§ Cross-user uniqueness per-domain) forbids.

### Registration

`fauna.account.register` mints the **bare** handle and verifies the client's Ed25519 signature over the domain-tagged, length-prefixed `register_signed_message(actor_id, handle, domain, timestamp)`. The `domain` the server verifies against is **any active local domain** (or, on a box with none yet registered, the identity `handle_domain()`), so a user who reached the nest via a secondary domain (`bob@domain2`) can register — the signed domain need not be the primary. The signed domain is **not carried on the wire** (`build_register_request` bakes it into the signature only), so `register_core` tries each candidate (`handle_domain()` plus every active `local_domains` entry) and accepts the first that verifies. The handle is stored bare regardless (the domain is never persisted with it).

### Resolution and login report the live identity domain

`fauna.actor.by_handle` (`resolve_handle_core`), `fauna.auth.verify` (the silent-challenge launch reply), and the contacts enrichment all report the deployment's **live identity domain** — `AppState::handle_domain()`, the projection of the primary `mail_domains` row — never the stale `--handle-domain` boot seed. (Reading the raw `registration.handle_domain` field left a domainless-then-claimed box reporting `localhost` / `"unknown"` for a handle it actually serves under the claimed domain — the domain part of every user-visible handle would be wrong.) The per-domain **echo** — report `bob@domain2` when the reference named `domain2` — rides an additive optional `domain` field on `ActorByHandleRequest`: when it names an active local domain the resolver echoes it verbatim, when it names a domain this nest does not serve the resolver rejects with `fauna.actor.domain_not_local`, and when it is absent the bare-handle path (report the identity domain) is unchanged.

### Client reachability of a secondary domain

For `@bob@domain2` to *reach* this nest, `domain2` must resolve to it: the client's handle probe does `https://domain2` + the `_fauna._tcp.domain2` SRV lookup (`onboarding.md` § Handle entry), and the node resolver falls back to `:443` when the SRV is absent. The **primary** domain publishes the apex `A` → the nest (`fauna_mail::dns::host::build_host_dns_records`; no `_fauna._tcp` SRV — the `:443` fallback covers it). A **secondary** domain's per-domain mail record set (§ Per-domain DNS records) publishes only the *mail* records (MX/SPF/DKIM/DMARC/MTA-STS/TLSRPT/TLSA); the client-reachability apex `A`/`AAAA` → the nest is appended separately by the nest's `fauna.dns.list_records` assembly (`build_secondary_apex_records`), mirroring the primary's apex, so a client finds the nest via that domain. Mail delivery to `@domain2` is unaffected either way (its MX points at `mail.<primary>`, which resolves). **Exception — an in-flight primary-domain rename:** while a rename is *pre-flip*, the **new-primary** secondary additionally carries a transient `mail.<new-primary>` `A`/`AAAA` → the **mail host** (`build_mail_host_records`), so the in-process ACME HTTP-01 order can resolve `mail.<new>` and pre-provision that cert SAN *before* the anchor flip makes `<new>` the single `mail.<primary>` MX host. This is the one case a secondary carries a `mail.` row; it is withdrawn if the rename aborts. Authority: `mail-primary-domain-rename.md` § Behavior — cert chain re-issue ordering.

### Compatibility

The evolution is **additive-everywhere** (`../architecture/version-compatibility.md`): `@bob@domain2` and login-via-`domain2` newly *succeed* (or newly report the correct domain) where they previously failed or reported the wrong domain, while `@bob@<primary>` and the reply's identity-domain field are unchanged. No wire field changes meaning; the optional `domain` request field defaults to today's single-domain behavior when absent. There is **no `users`-schema change** — the handle stays bare and globally unique — so nothing at rest evolves.

## Cross-domain submission policy

A user authenticated as an actor may submit mail with `MAIL FROM:` matching any of their owned addresses on any of the deployment's `local_domains` (the user has equal authority over all addresses they own, regardless of which domain).

### Required invariants

- The `MAIL FROM:` domain MUST be in `local_domains` (`removed_at IS NULL`). The deployment is closed-relay; we don't accept submission for non-local domains. Per `smtp-server.md` § Submission policy.
- The local-part of `MAIL FROM:` MUST be an alias the authenticated actor owns. The MTA checks via `fauna.bridges.resolve_recipient(MAIL_FROM)` → returns the actor_id; the MTA compares with the authenticated actor. Mismatch rejects `550 5.7.1 Sender not authorized for this address`.

### Default: cross-domain submission allowed

By default, no per-domain submission restriction — a user with `bob@domain1` AND `bob@domain2` claimed may submit with either MAIL FROM. The default is permissive (a user owns all their claimed addresses uniformly).

### Optional: per-domain submission restriction

Admin can restrict per-domain submission via `mail.submission.allowed_domains_per_actor` (Tier 2; map of `<actor_id>` → list of allowed local-domains). Use case: a community-moderator actor that legitimately needs `mod@community-domain` for the moderator role but should not be sending as `mod@primary-domain` (the moderator's deployment-wide actor identity shouldn't impersonate the admin's primary-domain mailbox).

When the map is unset for an actor, the default applies (any owned address on any local_domain). When set, the MTA filters `MAIL FROM:` domain against the allowed list; reject with `550 5.7.1 Sender not authorized for this domain`.

### From: vs. MAIL FROM:

If `From:` (header) and `MAIL FROM:` (envelope) disagree, the MTA does **not** reject at submission — these are independent values per RFC 5321 / RFC 5322. The user has policy reasons to set different values (e.g., bounce-routing to a different address than display); the deployment doesn't enforce *alignment* at submission. **DKIM signing uses the From: domain** (RFC 6376 §3.6 — d= matches From:'s domain). **DMARC alignment at receivers** is the receiver's enforcement concern. Independence is not exemption: each of the two values is held to the ownership rule on its own — the envelope by § Required invariants, the header by § From: header ownership below.

### From: header ownership

**The one rule, both doors (ratified 2026-09-27).** A `From:` header whose domain the deployment signs for — an active `local_domains` entry, or a subdomain of one (§ Signing-key selection at outbound time keys the DKIM `d=` under the closest local parent) — must name an address the submitting actor **owns**: the actor's handle on any active local domain (§ Multi-domain handles), or an alias the alias resolver attributes to that actor (`mail-aliases.md`). Ownership is the **same predicate the envelope check applies** (§ Required invariants, `fauna.bridges.resolve_recipient` → `actor_id` equals the authenticated actor); a submission door that admits an address as `MAIL FROM` admits it as `From:`, and refuses it as both. Nothing on a subdomain can be owned (no mailbox exists there), so a subdomain `From:` is refused even for the handle. Why: the signer keys `d=` on this header, and receivers' DMARC aligns the header — a `From:` naming another local user would leave with the strongest authentication a receiver sees, spent on an impersonation; the envelope check never reads the header. A `From:` on a domain the deployment does not sign for is not ours to vouch for and is out of this rule's scope (the submission door's DKIM-coupled `550 5.7.7` and the app door's off-domain bypass keep their own owners).

**Exactly one mailbox.** The one `From:` field (`smtp-server.md` § Architectural rules → *Exactly one From field*) must name exactly one mailbox — RFC 5322 §3.6.2 allows a list, RFC 7489 §6.6.1 names rejection for it: two mailboxes would sign under the first's domain with a foreign one riding along; a group is its flattened members; a field naming no mailbox (display name only, no domain) leaves nothing to own. Refused before the ownership question is asked.

**Per door.** **Submission 465/587** (`submissionSession.Data`, after the From-field count and before the `Received:` strip and DKIM sign, independent of whether DKIM is configured): other than one mailbox → `554 5.6.0 From field must name exactly one mailbox`; an unowned address on a signed-for domain → `550 5.7.1 Sender not authorized for this address`, the envelope check's code; resolver unreachable → `451 4.7.1` (fail closed). The predicate is `assertSenderOwned` — the handle compared case-insensitively with no RPC, else `assertMailFromOwned`'s resolver call — and both `Mail` and `Data` call it. The mailbox list and the signer's `d=` anchor come from one shared-Rust reader (`fauna_mail::envelope::from_mailboxes` / `sender_domain`, headers only), so door and signer never disagree about which address the message is from. **The app door** `fauna.email.send` enforces the same rule on its in-domain `From:` — `mail-app-surface.md` § Sender-handle verification is that door's statement of it, and points here. The authenticated-sender stamp is unchanged by this rule: the submission door still stamps the envelope it validated (`smtp-server.md` § Architectural rules → *The `X-Fauna-*` namespace*) — both values are now the same actor's.

## Adding a new local domain (the admin workflow)

`admin-dns` page → "+ Add domain" (the existing `admin-dns-add-domain-button`) opens the add-domain form. The basic name-only form is shipped (linux + web); the richer wizard fields below (cert mode / catch-all / DKIM algorithms) extend that same `admin-dns` form when those knobs become writable — they are **not** a separate `bridges-detail` wizard (§ ui.yaml surface). Their ui.yaml IDs are allocated on `admin-dns` in the consuming track, not pre-invented here.

### Wizard steps (the behavior; IDs land on the `admin-dns` add-domain form)

1. **Input the new domain name.** The `admin-dns-add-domain-input` field (shipped). Validates RFC 1035 syntax; max length 253; lowercase normalization. Refuses an already-present `local_domains` entry (whether active or soft-deleted within the 30-day window — re-add is via the soft-deleted row's "Restore" affordance, not via Add).
2. **DNS provider check.** The **client** determines — from its own **client-held** DNS-provider credentials (captured at `onboarding.md` § DNS configuration and persisted client-side in `fauna.state.dns` per `dns-management.md` § Where the credential lives; the nest never sees them) — whether a held credential's client-side `verify()` reports a zone covering the new domain. If yes → the domain can be Fauna-managed (the client auto-publishes); proceed to step 3. If no → display the manual-DNS-instructions screen (same shape as `onboarding.md` § Deferred-DNS path's `dns_post_instructions` screen, but scoped to the new domain's records) with the **live red/green per-record verification** of `dns-management.md` § Live verification. **There is no confirmation click (ruled 2026-10-01, retiring the "DNS is set up" button this step kept):** the add is never gated on DNS, so a click would release nothing — the new domain's row on `admin-dns` *is* the instructions screen, each record with its value and its live status, there for as long as the admin needs it (live status is informational truth, **not** a hard gate — propagation lag must not strand the admin). No app, element id or stored flag ever carried the button.
3. **MTA-STS cert mode — auto-chosen; collapsed advanced override.** The client auto-chooses the SAN strategy from the step-2 provider check — `expand_primary` when a held credential covering the primary also covers the new domain, `per_host` when not (§ MTA-STS HTTPS cert) — and applies it silently; there is no mandatory picker step. (Target — today the shared machine writes the static default `expand_primary`, and the per-mode cert dispatcher is likewise not yet wired; § Implementation status today.) An advanced, collapsed-by-default radio (`expand_primary` / `wildcard` / `per_host`, description text per § MTA-STS HTTPS cert) exposes the choice for the rare deployment that genuinely needs to override — e.g. `wildcard` to isolate the new domain from the primary's cert lifecycle. Cert *provisioning* (issuance, renewal, floor fallback) is automatic and admin-invisible whichever mode is stored (the DKIM/TLS-automatic directive).
4. **MTA-STS policy mode — automatic: `testing` at add, `enforce` by the nest's own hand, no control on any app (ruled 2026-10-03).** This is the user's 2026-05-24 directive applied as written — MTA-STS is an automatic concern with no manual admin UI (`mail-policy-config.md` § Policy catalog, the UX-surface reconciliation banner) — and [`../principles.md`](../principles.md) § One configuration surface's test gives the same answer: no admin would *choose* a weaker transport policy for their own domain, they would only forget to strengthen it. Every new domain is stored `testing`; the nest moves the stored mode to `enforce` once (a) the deployment's mail name is served on a trusted certificate and (b) the domain has been in `testing` for the warm-up window, a Rust constant of 7 days. The *published* mode stays coupled to certificate reality in both directions, as before (§ Per-domain MTA-STS — the cert-honesty rule), so a lapsed certificate still drops what is published without touching the stored mode. There is no `none`: a domain this nest serves mail for always publishes a policy. No request carries the mode — it is on neither the add request nor `update_local_domain_config` — and no element id exists for it (the once-PROPOSED `admin-dns-domain-mta-sts-mode-select` is withdrawn); `mta_sts_cert_mode` is untouched by this ruling. How and when the nest advances: § Per-domain MTA-STS → *The advance*. Tier + catalog row: `mail-policy-config.md` § Tier 2 — TLS posture.
5. **Catch-all designated actor.** Optional picker → default unset; admin can pick themselves or any other actor; refuses non-existent actor IDs. (A genuine routing choice — folds onto the `admin-dns` per-domain row / add-domain form when the nest catch-all resolver lands; see § ui.yaml surface.)
6. **DKIM algorithms.** Inheritance toggle — default "inherit deployment default" (`['ed25519', 'rsa-2048']`); admin can override per-domain (rare; useful for compatibility with a specific peer that requires RSA-only).
7. **Confirm button.** **When this add would be the first** (no active `local_domains` row yet — the same condition the nest uses to derive `is_primary` below), the form warns before the client calls: it becomes the deployment's primary and can never be removed from any app, and the only exit is the primary-rename ceremony onto another domain (§ Removing a local domain; the consequence statement is owned by [`deployment-home-with-public-relay.md`](../architecture/nest/deployment-home-with-public-relay.md) § MUA reach). A second-or-later add is ordinary and warns of nothing. All 7 apps render this as untagged chrome above the submit control, driven by `LocalDomainsSnapshot::adding_first_domain` (a client-side UX hint mirroring the nest's own derivation — the nest stays authority on whether an add is actually first): tui, linux, web, and android landed 2026-08-22; macOS + iOS landed 2026-08-26, same shape (`AdminDnsView.swift`'s `addDomainSection`); windows landed 2026-08-27, `AdminDnsPage.xaml`'s `AddDomainPrimaryWarning`. Client calls `fauna.bridges.add_local_domain(domain, mta_sts_cert_mode, catch_all_actor?, dkim_algorithms?)` — no MTA-STS mode (step 4). Nest:
   1. Inserts the `mail_domains` row with `removed_at = NULL`, `is_primary = false`.
   2. **The DKIM key mints at add time.** Inserting the row mints the domain's key for its active selector on the same connection (`mail-bridge-lifecycle.md` § DKIM provisioning (automatic) → *Custody moves to the nest*; § Per-domain DKIM → DKIM-key custody), so the DKIM record is on the DNS page the moment the domain is (target: RSA-2048 + Ed25519 per the chosen algorithms; **today a single Ed25519** — § Implementation status). The nest keeps the private half sealed under its own key-encryption key and opens it only to sign.
   3. Assembles the DNS-record **bodies** (MX, SPF, DKIM TXT, DMARC TXT, MTA-STS TXT, TLSRPT TXT); the **admin's client** publishes them — via its held DNS-provider credentials (Fauna-managed) or by showing them for the admin to paste (manual). The **nest never publishes** DNS, per `dns-management.md` § The two modes (the older "nest publishes via the DNS provider" framing is superseded by the client-publish model). For the new selector's DKIM TXT specifically, the value comes from the **nest-minted** key's public half (`list_dkim_selectors`, populated the moment the domain is added) and publishes via the client's `DnsManagementMachine::Publish` path on `admin-dns`.
   4. The nest's **own in-process ACME client** re-issues the cert according to the cert mode (widen the primary cert's SAN set for `expand_primary`, a fresh wildcard cert for `wildcard`, a fresh per-host cert for `per_host` — **not** external certbot; § MTA-STS HTTPS cert). This is asynchronous + idempotent (the `cert_lifecycle_task` tick), not a synchronous add-time step; the domain serves on the self-signed floor until the trusted cert lands.
   5. Pushes `fauna.bridges.config_changed` to the MTA bridge — the realized push is **topicless** (`BridgeConfigChangedPush { reason }`; the bridge re-fetches the whole snapshot); the per-domain topic `mail/domain/<domain_id>` is the planned refinement (§ Implementation status today, topic-scoping bullet).
   6. Returns the new domain's row immediately (the insert is the only synchronous step). "Ready to accept mail" is reached asynchronously as the ACME cert lands and the client's published (or admin-pasted) records go green under live verify — surfaced via the per-record status on `admin-dns`, not gated inside this call.
8. **Success state.** Form closes; the new domain appears in the `admin-dns` domain list with its per-domain record matrix and status (DKIM healthy ✓ / DMARC published ✓ / MTA-STS testing ⚠ / Cert acquired ✓ render as `admin-dns-record-status` rows). Status updates on push events as records propagate.

### Idempotency

`add_local_domain` is **idempotent on `domain_name`** — calling with an already-active domain returns the existing row + a `Skipped` status. The wizard's "Confirm" button retried after a network blip re-runs without inserting a second row or generating extra keypairs; the client's managed publish is itself idempotent (`find_records` pre-flights each write — `dns-management.md` § Fauna-managed), so a retry never double-publishes.

### Failure handling

`add_local_domain` itself is a single atomic step — it inserts the `mail_domains` row or errors; there is no partial `provisioning_failed` row state (`mail_domains` has no `status` column; the earlier certbot-era synchronous-provisioning framing is retired). The two follow-on concerns fail **independently** and self-heal, so a failure never leaves the row wedged:
- **Cert issuance** is the nest's asynchronous ACME lifecycle (§ Wizard step 7.4). A failed/slow issuance keeps the domain on the self-signed floor and retries on the next tick — no admin action, no wedged state.
- **DNS publication** is client-side. In managed mode a publish failure (revoked token, provider 5xx, zone not found) surfaces as a **per-record error with a "re-enter credentials" affordance** on `admin-dns` (`dns-management.md` § Fauna-managed) — it does not fall back to manual silently; in manual mode the admin pastes records and watches the live red/green verify. Either way the row stays; the admin can remove it (soft-delete, 30-day recovery) if they abandon the domain.

### Per-domain warmup (cross-link)

The new domain inherits the deployment-wide warmup state per `mail-deliverability.md` (Track 4 #3) — the deployment's outbound warmup is per-deployment, not per-domain (the IP reputation is the deployment's IP, shared across all domains; adding a new domain doesn't re-warmup the IP).

## Removing a local domain (the admin workflow)

`admin-dns` page → the domain's row → "Remove domain" (the existing `admin-dns-domain-remove-button`) opens a confirm dialog.

### Confirm dialog text

> This will stop accepting mail for `<domain>`. Any user aliases on this domain stop resolving while the domain is inactive (mail addressed to them is refused); the rows are preserved for 30 days and come back if you restore the domain. The DKIM key for `<domain>` will be archived but not destroyed for 30 days (in case of re-add). After 30 days the archived key is destroyed and re-add requires a fresh keypair generation. Mail in-flight at the time of removal may still arrive; peer MTAs caching the MX record will see the record disappear once their TTL expires. Proceed?

### On confirm

Client calls `fauna.bridges.remove_local_domain(domain)`. Nest (the whole nest-side mutation — `remove_local_domain_handler`):

1. Refuses when the domain is the primary (or gated by the in-flight primary-rename guard, `mail-primary-domain-rename.md`), then **soft-deletes** the `mail_domains` row (sets `removed_at = NOW()`).
2. Pushes `fauna.bridges.config_changed` (the realized topicless push — § Implementation status today, topic-scoping bullet). The bridge re-fetches its snapshot, the domain drops out of `local_domains`, and the next RCPT TO targeting it is refused at the relay gate (`550 5.7.1 relay denied` — `smtp-server.md` § Error / tempfail strategy).
3. Returns the soft-deleted row.

**DNS-record withdrawal is not a nest step** — the nest never publishes or unpublishes DNS (`dns-management.md` § The two modes; see § Publication lifecycle above). In managed mode the **client's** withdraw-aware reconcile removes the records (MX last, so peer MTAs mid-delivery against the cached MX land their final delivery); in manual mode the admin removes them by hand, guided by the `admin-dns` matrix.

**Alias rows are untouched at remove time** — they go **dormant** with the domain (the RCPT relay gate refuses the domain before alias resolution ever runs), are hard-deleted with the row by the 30-day GC (§ After 30 days), and **revive automatically** if the domain is restored within the window (§ Re-add within 30 days). There is no per-alias `disabled` write at remove time; the earlier "auto-disable every alias row" design is superseded by this dormancy model.

### Re-add within 30 days

The "Restore" affordance (visible while `removed_at IS NOT NULL` and `now - removed_at < 30 days`) un-soft-deletes the row and re-pushes the config update to the bridge; the DNS records **re-publish client-side** (managed reconcile or manual paste — the nest never publishes), using the **preserved** DKIM key material (so peer MTAs caching the DKIM TXT keep validating signatures from the restored deployment). The domain's alias rows **revive automatically** — they were never mutated at remove time (§ On confirm — dormancy, not a disable write), so restoring the domain makes them resolve again.

### After 30 days

A nest periodic GC job destroys the DKIM key material, deletes the `mail_domains` row entirely, and drops that domain's (dormant) `account_aliases` rows. **Built** (tracked internally): `CacheDb::gc_expired_soft_deleted_mail_domains`, run each tick of the nest's background-expiry task (`main.rs`), hard-deletes — in one transaction, per expired row (`removed_at < now - 30d`; the primary can never be soft-deleted so is never expired) — the row plus its per-domain dependents: `mail_dkim_keys` (the sealed DKIM key, keyed by `(domain, selector)`), `bridge_tls_cert_blobs`, and the `account_aliases` rows for that `local_domain`. The dependents are deleted **explicitly**, not by FK cascade: the `account_aliases.local_domain → mail_domains.domain_name` `ON DELETE CASCADE` named here (and in § Storage) is a target-state addition that does not exist in the SQLite schema today (`account_aliases.local_domain` is a plain column), and the DKIM material lives in `mail_dkim_keys`. Were the cascade FK added later, the explicit alias delete becomes redundant but harmless. The per-domain DKIM TXT records are not republishable after this point.

### Primary domain cannot be removed

The primary domain has `is_primary = true`; the `remove_local_domain` RPC refuses with `403 cannot_remove_primary_domain`. Renaming the primary is a separate multi-step admin action — see `mail-primary-domain-rename.md`.

## Storage

The full `mail_domains` shape was named in § The `mail_domains` model above. Supporting tables:

- `mail_dkim_keys(domain, selector, …)` — the per-domain DKIM keys, one row per `(domain, selector)`: the private half sealed under the nest's own key-encryption key, beside the unsealed `public_dns_value` the DNS TXT record publishes (`mail-bridge-lifecycle.md` § DKIM provisioning (automatic) owns the mechanism). `mail_domains` does not reference it: the domain name is the join, and the 30-day GC deletes a removed domain's rows explicitly.
- `account_aliases(…, local_domain TEXT REFERENCES mail_domains(domain_name) ON DELETE CASCADE, …)` per `mail-aliases.md` § Storage — **target-state**; the `ON DELETE CASCADE` FK is not in the SQLite schema today (`local_domain` is a plain column), so the 30-day GC job deletes a removed domain's aliases **explicitly** rather than by cascade (§ After 30 days). When the FK is added the cascade would fire on `mail_domains` row deletion and the explicit delete becomes redundant.
- `tlsrpt_inbound_reports(…, policy_published_domain TEXT, …)` per `smtp-server.md` § TLSRPT inbound report listener — the per-domain partition is on the column tagged at ingest time, not on a separate per-domain inbox.
- `dmarc_inbound_aggregate_reports(…, our_domain TEXT, …)` per `dmarc-reporting.md` § Storage — same partition-on-column shape.
- `mail_outbound_warmup_state` per `mail-deliverability.md` (Track 4 #3) — per-deployment, not per-domain (the warmup IP is the deployment's IP).

The `mail_domains.dkim_algorithms` is a TEXT[] column for the simple case but rotates two keypairs (RSA-2048 + Ed25519) at quarterly cadence — each algorithm has its own selector lifecycle. Each algorithm's key is its own `mail_dkim_keys` row under its own selector (Ed25519 alone today — the dual RSA + Ed25519 stays deferred, § Implementation status today).

## Architectural rules

- **Exactly one primary domain.** Uniqueness constraint on `is_primary = true` AND `removed_at IS NULL`. The primary is the deployment's identity (signup handle suffix + MX target + processor inbox for TLSRPT/DMARC + List-Unsubscribe HTTPS origin).
- **One MX target across all domains.** `mail.<primary-domain>` is the canonical mail server hostname; every `<domain> MX 10 mail.<primary-domain>`. The actual mail server is one machine serving N domains via SNI. A deployment wanting per-domain MX hostnames needs a different deployment topology (out of scope for this doc).
- **Per-domain DKIM keys are independent.** Rotating one doesn't affect others; per-domain rotation schedules allowed; key compromise on one domain doesn't compromise the others.
- **Domain removal is soft + 30-day recoverable.** `removed_at` is the only mutation at remove-time; the row + sealed DKIM key + (disabled) account_aliases rows stay 30 days then GC. Restore within the window re-publishes records + re-uses the archived DKIM key. After 30 days, re-add is a fresh keypair generation.
- **Cross-domain user submission allowed by default.** A user owns all their claimed addresses uniformly across domains. Per-domain submission restriction is an admin opt-in via `mail.submission.allowed_domains_per_actor`.
- **Reserved local-parts are per-domain independent.** Each domain's `postmaster@`, `abuse@`, etc. is reserved separately; admin can claim `postmaster@domain1` and a community moderator can be delegated `postmaster@community-domain`.
- **Admin's role-address routing inherits from primary unless overridden.** The default is "every domain's `postmaster@` goes to the admin"; the override map is per-domain.
- **TLSRPT + DMARC processor inboxes are deployment-wide.** All domains' inbound reports land in the single processor at the primary domain; the partition is on the report payload's `policy_published.domain` field, not on a per-domain inbox.
- **The `local_domains` list is a derived projection.** The `mail.local_domains` flat-list view in `mail-policy-config.md` § Tier 2 is the `domain_name` column of every `mail_domains` row where `removed_at IS NULL`. Adding/removing a domain mutates `mail_domains`; the projection updates automatically.
- **DNS-record rewrites are rate-limited per-domain.** At most 1 rewrite per `mail_domains` row per minute — a constraint on the **client's** managed-mode reconcile (the client is what writes to the DNS provider; the nest has no DNS-provider write path), per `dmarc-reporting.md` § Architectural rules's TXT-rewrite rate limit — generalized.
- **Adding a domain doesn't re-warmup the deployment IP.** The deployment's outbound IP reputation is shared across all domains; warmup state is per-deployment, not per-domain (per `mail-deliverability.md`).
- **The handle-uniqueness rule is deployment-wide, not per-domain.** A user's handle (their primary-domain identifier) is unique across the deployment's user table; two distinct users with the same handle on different domains is structurally forbidden. So `bob@domain1` and `bob@domain2` are either (a) the same user with two exact aliases, or (b) `domain1`'s claim with `domain2`'s position unowned.

## Don't do these

- **Don't run multiple MX targets.** One mail server, N domains via SNI. An admin wanting per-domain MX hostnames is doing a different topology that this doc doesn't cover.
- **Don't store per-domain TLS keypairs separately from the deployment's ACME-managed cert.** The nest's own ACME-managed cert covers `mail.<primary-domain>` as the canonical SAN + extends to `mta-sts.<each-additional-domain>` via SANs (`expand_primary`) or wildcard (`wildcard`) or fresh per-host cert (`per_host`). Per-domain key isolation is via DKIM keypairs, not TLS keypairs.
- **Don't allow per-domain user-claim.** A user is a deployment-wide actor; their handle may differ per-domain via exact aliases, but the actor identity is one and the user-management surface is deployment-wide. Per-domain user namespaces (`alice@domain1` and a different `alice@domain2`) is structurally forbidden by the handle-uniqueness rule.
- **Don't tie domain removal to user deletion.** Removing a domain makes its addresses dormant (the user's `account_aliases` rows stop resolving with the domain — no per-alias mutation; § On confirm), not users. The user retains the rest of their addresses + can rebind to another domain.
- **Don't allow a hand-edited DNS zone file to bypass the per-domain assembly.** Consistent with the product invariant — all DNS config is set from a Fauna app. In **managed** mode the client's reconcile re-asserts the assembled records, so hand-edited records get overwritten on the next reconcile; in **manual** mode the live red/green verify flags any hand edit that diverges from the assembled expected value (`dns-management.md` § The two modes). The nest never rewrites DNS itself.
- **Don't share DKIM keys across domains.** Each domain MUST have its own keypair per RFC 6376 §3.1.4 — the `d=` tag uniquely identifies the signing domain. Sharing keys would let one compromised domain's key sign for the others (security-floor lowering, forbidden).
- **Don't allow the primary domain to be soft-deleted.** The primary anchors the MX, the processor inboxes, the List-Unsubscribe origin, the cert chain. Renaming the primary is a separate multi-step admin action with extensive warnings, covered by `mail-primary-domain-rename.md`.
- **Don't auto-merge two users who happen to claim the same handle on different domains.** The handle-uniqueness rule deployment-wide means this situation can't arise from signup, only from a corrupted state restore — investigation, not auto-merge.
- **Don't leave per-domain config changes on full-fleet re-fetch once topic scoping lands.** Target: each domain gets its own push topic (`mail/domain/<domain_id>`) so a change to `domain1`'s catch-all doesn't force a re-fetch of `domain2`'s config. **The realized push today is topicless** — whole-snapshot re-fetch on any change, correct but coarser (§ Implementation status today, topic-scoping bullet); a session must not build against the per-domain topic as if it existed.
- **Don't let the add-domain wizard skip the client-side DNS-provider credentials check.** If no held credential covers the new domain, the wizard surfaces the manual-DNS path; the client doesn't attempt managed publishes against a provider that will reject them. (The credentials check is client-side — the nest's `add_local_domain` just inserts the row and never sees a credential.)
- **Don't return the DKIM private key — sealed or not — over any RPC.** No client and no bridge needs it: the admin surface carries the public metadata only (`list_dkim_selectors`), and the key stays inside the nest's seal (`mail-bridge-lifecycle.md` § DKIM provisioning (automatic)).
- **Don't let a human set the MTA-STS mode.** The stored mode has two values and, after the add, one writer — the nest's advance (§ Per-domain MTA-STS → *The advance*). No request carries it, there is no `none`, and a stored value that is neither is read as `testing`. A per-domain mode can therefore no longer contradict the deployment-wide TLS posture (`mail-policy-config.md` § Tier 2 — TLS posture), which is what the update-time validator this bullet once described guarded against.
- **Don't allow soft-deleted domains to be claimed by a different actor during the 30-day window.** The soft-deleted `mail_domains` row + the dormant `account_aliases` rows preserve the original user's claim; re-add via Restore preserves the original ownership. A different user trying to "Add" a domain currently in soft-delete gets `409 domain_pending_recovery` until the GC fires.
- **Don't tie the per-domain DKIM rotation to a deployment-wide clock.** Per-domain rotation schedules allow independence — one domain rotating quarterly + another monthly (forensic concern) shouldn't trigger both at the same time. The rotation scheduler iterates per `mail_domains` row.
- **Don't run the resolver across `local_domain` boundaries.** A message to `bob@domain1` never resolves an alias on `domain2`; the resolver searches the alias namespace of the RCPT TO domain only. Cross-link: `mail-aliases.md` § Resolution order.
