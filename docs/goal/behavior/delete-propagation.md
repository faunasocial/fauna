## How a delete travels

**Deletes propagate the same way — and the disk, not the device id, decides whether one still has work to do.** A delete is a tombstone in the `sync_changes` log (`change_type = "delete"`, no manifest), and `changes.list` echoes it back to *every* device including the one that recorded it. **Two different actors record a delete under one device's id, and only one of them has already touched the disk:** the engine's own `handle_delete` removes the file and its row *before* recording, whereas a **app UI's delete** (the `media-delete-button` gesture — `../ui/media.md` § Element IDs) records the tombstone having never touched the disk at all. So the applying device **must not** decide by comparing device ids: it applies any tombstone that is its path's batch-latest change, whose file is still present, **and whose path it tracks as a live row** — which makes the engine-originated echo a natural no-op and the UI-originated one the real work. Three corollaries this rule exists to hold:

- **A skipped delete never comes back — for a *tracked* file.** The pull anchor advances to the batch's max seq whether or not a change was applied, so a tombstone declined once is excluded from every later pull. Declining it for a file the engine tracks as live strands it on disk permanently, while the nest and the explorer both treat it as deleted — a divergence the user can neither see nor undo. **This is why the row condition below is safe and this one is not:** an *untracked* or *recreated* file has no such divergence to strand, because reconcile sees an unknown/new local file and uploads it as a fresh create at a higher seq — which is exactly how every device converges on "the file exists". The anchor hazard is about abandoning a tracked file, never about refusing to destroy an untracked one.

- **The tombstone's subject is the ROW, not the path (ratified 2026-07-24).** `exists()` answers "is something here?", never "is this the file the tombstone refers to?". Two ways a *different* file occupies a tombstoned path, both user data that exists nowhere else: **no row at all** — a brand-new local file the engine has never synced, which is precisely what a folder freshly bound to a set with history contains; and **a tombstoned row with a file back on disk** — `delete_entry` soft-deletes (`state = Deleted`), so the row outlives the file, and a file there now is a **recreation** after the delete already landed. Applying the tombstone to either destroys the new file, and it compounds: with no live row, reconcile's delete-detection never queues an upload, so the bytes are simply gone. This is the same "another device may have since recreated it" hazard the re-record guard below names, reached by a different route — a *legitimately recorded* historical tombstone rather than an echoed one. The engine therefore declines a delete whose path has no live row, and fails **closed** (keeps the bytes) if it cannot read the row at all. **And the row alone is NOT sufficient — the disk must agree with it (correctedsecurity-review finding).** `local_hash` refreshes only when the upload path reaches "Mark as uploading", and a local edit sits behind the watcher debouncer first, whose timer resets on every event — so for a continuously-written file the row stays stale for the *whole* write, and the off-cadence nudge pull deliberately runs no converge before applying. In that window a row reads Synced with matching hashes while the disk holds bytes the nest has never seen. The delete arm therefore **re-hashes the file before unlinking** and declines on divergence from `local_hash` (fail closed on an unreadable file); reconcile then uploads the survivor as a fresh create. Pinned by tier_1 `pull_remote_changes_test::a_remote_delete_does_not_destroy_a_mid_debounce_edit_on_a_synced_row` (verified red first). **A tombstone may be applied only when BOTH conditions hold (corrected 2026-07-29, second pass):** the row's **state** says its content is settled — `Synced` or `Placeholder`, never `Uploading` (bytes in flight), `LocallyModified`/`Conflicted` (an observed edit) or `RemotelyModified`/`Downloading` (mid-apply) — **and** the disk still hashes to the row's `local_hash`. The state test is what excludes the in-flight upload, and it cannot be replaced by a hash test, because a mid-upload row's `local_hash` **is** the hash of the bytes on disk. ⚠ **`local_hash` and `manifest_hash` are different identities and must never be compared to each other** — the former is the content's hash, the latter the hash of the manifest that *reassembles* to that content (`ContentHash::of_raw(&manifest_bytes)`). They are equal only in a hand-seeded test row. Using `local_hash == manifest_hash` as a stand-in for "row-synced" therefore declined the delete on **every device that obtained the file by download** — the ordinary collaborative case — after which reconcile re-uploaded it as a fresh create, resurrecting deleted files fleet-wide. Pinned by tier_1 `::a_remote_delete_applies_to_a_downloaded_file_whose_manifest_differs_from_its_content` and `::a_remote_delete_does_not_destroy_an_edit_on_a_row_with_no_local_identity`, both verified red first; the mid-upload pin was strengthened to seed the **real** disk hash, the shape production actually writes. The symmetric *overwrite* path needs no such re-hash: `download_and_write_file` already reads the pre-image and routes divergence through conflict auto-resolve, durably retaining the local version before any write.
- **Batch-latest, not per-change — in BOTH arms.** A path deleted and recreated inside one batch records `delete@N` then `create@N+1`; applying the delete on its own would erase the *recreated* file, and a self-echoed create only re-bases (it downloads nothing), so those bytes would not come back. The highest-seq change per path wins — the same fold § On-Demand Files' placeholder population uses. **The rule binds the create/modify arm symmetrically (corrected 2026-07-24):** replaying `create@N` when `delete@N+1` supersedes it downloads a stale version **over** whatever the user has at that path, *before* the delete arm removes it — destructive, not merely wasteful. Only the delete arm folded this way until 2026-07-24; a folder freshly bound to a set with history hit the gap on every run.
- **Applying a remote delete must not record one back.** Unlinking the file raises an ordinary `Removed` watcher event on the applying device, which — unsuppressed — reads as *the user deleted this* and records a fresh tombstone on the nest. Two independent guards keep that loop shut, and both are needed: (1) the applied delete arms a **removal-echo** suppression that is a *separate* one-shot channel from the download-echo one, because both suppressions are consume-on-check and a shared token is eaten by whichever watcher event lands first — **a collision that runs in BOTH directions, and the second one loses user data**: a path downloaded and then remote-deleted in the same batch queues a `Created` *and* a `Removed` against one token, so the `Created` consumes it and the applied delete gets re-recorded to the nest (wasteful, and the recreate race below makes it dangerous); and, the mirror image, **a *user's* delete issued inside the download-echo window consumes the token the write's own event needed, so the user's genuine delete is never notified at all — no tombstone, no error, and the file resurrects on every other device** from the nest's still-live copy (measured live on macOS, 2026-08-05; the losing order is reachable there because macOS delivers the two events with enough latency between them, so a green Linux run does not absolve a daemon of it. ⚠ The mechanism was originally recorded here as *"FSEvents' coalescing latency"*; that attribution was **wrong and is corrected 2026-08-05** — the build was not on FSEvents at all, see § Config's *watcher backend* status note. The collision itself is real and platform-independent, and both guards stand). Two independent one-shot tokens make both unrepresentable, and the arm a watcher event consults must be chosen by the event's KIND, never by which token happens to be armed. And (2) `handle_delete` treats an **already-tombstoned** row as owing the nest nothing — `delete_entry` tombstones (`state = Deleted`) rather than removing, so a row-exists test alone lets every later delete event for that path re-record. Guard (2) is the load-bearing one: a tombstone means the first record provably landed (record-first), so a re-record can only ever re-broadcast a delete for a path another device may have since **recreated** — erasing the new file, a no-user-data-loss violation (`../principles.md`). **The nest now enforces the same rule independently, durably (nest-side idempotency guard).** Guard (2) is client-side — it stops an engine from ever *sending* the redundant delete, but a stale client that lacks it, or a different actor racing the same delete on a multi-writer set, still could reach the nest. `record_sync_change_metered` (`bins/fauna-nest/src/db/sync_storage.rs`) now no-ops any delete whose path head is already a tombstone, **regardless of the acting actor or `content_key_version`** — unlike the pre-existing exactly-once replay check just above it in the same function, which is deliberately keyed on the acting actor (two actors authoring identical *content* are still distinct authored versions). A delete carries no content to differ by author, so this is safe to broaden: it returns the tombstone's existing `seq` and appends no row, additive wire behavior only — older clients that already relied on a re-record being accepted still get a valid `seq` back, just the original one. **On a signed set the echo has one more condition: a signed delete over a signed tombstone is an echo only while that tombstone's signature still verifies under the set's STORED nonce.** A tombstone signed under a nonce the owner's custody reconcile has since retired verifies nowhere as current (`../architecture/writer-signed-change-records.md`, custody (e)), so the reconcile's re-record of that delete under the live nonce (custody (g)) is the path's only verifiable delete and lands as a new head — answering it with the retired tombstone's `seq` would leave every reader folding whatever lies beneath. A signed delete over an UNSIGNED tombstone lands for the same reason. Two signed deletes under the live nonce still dedupe, whoever signed them.

- **A wholesale-vanished folder is infrastructure failure, never user intent — reconcile holds it (the mass-delete floor, ratified 2026-08-02).** When a reconcile scan finds **none** of a multi-folder's synced rows on disk — the root still present, every tracked file gone at once — the delete-detection pass records **nothing**: an unmounted or renamed external volume, or a bound directory removed under the engine, must not erase the nest's copy of the whole set (no-user-data-loss, [principles.md](../principles.md)). The hold is **derived, not stored** — every reconcile re-evaluates it — so files reappearing (the drive remounted) resume ordinary sync with nothing lost, and a crash mid-hold cannot strand state (the derived-state shape of `nest/common.md` § Client-state recoverability). While held, `ReconcileStats.deletes_held` carries the count and the engine warns loudly; surfacing that count on the sync-agent status projection and the app-side *"your folder emptied — apply N deletions / reconnect the folder"* confirm affordance is the captured follow-on (propagation of a held set is an **explicit user action**, never this pass). Three deliberate boundaries: a **partial** vanish (some but not all rows missing) propagates per-file as before — that is ordinary sync semantics; a **single-file** set emptying propagates too (floor minimum = 2 — one file's absence is far likelier a genuine delete, and its loss magnitude is one version-retained file ([`file-versions.md`](file-versions.md))); and the **live watcher** path is untouched — an unmount emits no per-file remove events (the danger arrives via the next reconcile's empty scan, exactly what the floor covers), while a streamed file-by-file removal is genuine per-file evidence. The floor composes with the missing-root arm: `full_scan_filtered` **errors** on a root that is *missing* — and that is **ENOENT only**, a narrowness which is itself load-bearing: until 2026-09-20 a root that was merely **unreadable** took the scan's silent skip arm and came back empty, which is precisely the totality this floor engages on, so the failure reached the user as *"your folder emptied — apply N deletions"* and one click erased the set (see *unreadable is not absent* below, which withholds those rows so no such offer can be made); the floor closes the "root present, contents gone" window that the 2026-07-24 incident's 3-second ordering exposed (10 deletes propagated; the root itself vanished only afterwards).

*Implementation status today (2026-08-10, the status-projection half): **`deletes_held` now reaches the sync-agent status projection** — `EngineInfo.deletes_held` on the `ListEngines` reply, so an app can render "folder emptied — N deletions held" per bound set. The route is `ProgressEvent::DeletesHeld` (emitted by `reconcile` on **every** pass, zero included) → the agent's per-engine progress drain → `SyncServiceState::deletes_held` → the `ListEngines` handler. Three design points, each pinned: **(1) it rides the progress channel, not `ReconcileStats`** — the resident loop's `converge` discards those stats (`always_resident.rs`), which is why a held set was previously visible only in a log line; **(2) the report is held in agent memory, never stored**, giving it exactly the hold's own lifetime — a restarted agent answers `0` until its first pass rather than resurrecting a count no live engine stands behind, which is precisely the number the *"apply N deletions"* affordance must never be handed, and the drain deletes its set's entry when its engine stops; **(3) a pass that holds nothing reports `0`** rather than staying silent — since the hold is derived, a zero is the only thing that ever retracts a displayed hold, so a remounted drive clears the surface. `deletes_held` is a plain `u64` with `#[serde(default)]`, not an `Option`, because an agent reporting no hold and an older agent unable to report one mean the same thing to a reader ("do not warn") — unlike `corpus_reseal`/`reseal_drain` beside it, which must distinguish *cannot tell* from *nothing owed*. Pinned by tier_1 at all three links: the engine's emission and its self-clearing zero (`mass_delete_floor_test`), the drain's write plus entry-removal on engine stop (`engine_driver`), and the handler's per-set projection including the no-bleed-onto-siblings case (`pipe_server`). No app renders it yet — that is the ID-gated affordance above.*

*Implementation status today (2026-08-15, the verb half): **the apply-held-deletions mechanism is BUILT end-to-end below the UI** — `SyncEngine::apply_held_deletes` (`libs/fauna-sync-engine/src/engine.rs`) + the resident loop's invoke-and-reply command channel (`always_resident::EngineCommand`, routed per folder like the wake nudge) + the `ApplyHeldDeletes` agent IPC (`fauna_ipc::sync::RequestMethod`, replying `HeldDeletesAppliedInfo`). Three properties are the verb's safety content, each mutation-verified in `mass_delete_floor_test`: **(1) re-derive-now** — it applies what is missing at click time, never a displayed count, so a confirm racing a remount deletes nothing (`apply_held_deletes_refuses_when_the_files_came_back`); **(2) floor-gated** — below the floor it refuses and touches nothing, so it cannot serve as a general force-delete API (`apply_held_deletes_refuses_a_partial_vanish`); **(3) record-first resumable** — each row rides the ordinary `handle_delete` (failed record keeps the row `Synced`; a crash mid-apply leaves the remainder held or, at one row left, propagated by ordinary reconcile — the user-sanctioned outcome either way; nothing new is stored). The apply emits a fresh `DeletesHeld` count so the surface clears immediately. *The join lives in shared Rust so no app re-derives it: `EngineInfo.deletes_held` is reported per **set** and rendered per bound **path**, and `fauna_client_sync::agent::LocationBindingsModel::fold_engine_holds` mirrors the `ListEngines` roster onto every row bound to that set (`BindingRow::deletes_held`; the FFI twins are `FfiSyncAgentProvisioner::list_engine_holds` + `FfiLocationBindingsModel::fold_engine_holds`, so an app leg is a render plus one call). Four properties are load-bearing, each tier_1-pinned: **(1)** the fold is a **mirror**, so a set absent from the roster reads `0` — a stopped engine, a restarted agent and an agent too old to report the field all mean "no live engine stands behind this count"; **(2)** it is deliberately **not** part of the bindings `reconcile`, which runs on user mutations and reachability edges while the roster arrives on the agent-status poll — a reconcile that reset the hold would blank the surface between polls; **(3)** the apply is **non-optimistic and repaints from the reply**, since the agent's progress drain is asynchronous and a `ListEngines` issued right after the click can still answer the pre-apply number (`set_engine_hold` with `HeldDeletesAppliedInfo::remaining_held`); **(4)** `0` renders **neither** element — not a zeroed line, not a disabled button — because a standing offer to destroy files over a healthy folder is worse than no affordance at all. Apps fold the roster on their existing agent-status tick (10 s on both tui and linux): the hold is derived inside the agent on its own rescan cadence, so it needs a watch, not a hook. End-to-end coverage is tier_3 `tests/e2e-unified/tests/test_filesync_mass_delete_floor.py` — which empties the folder by **renaming the bound directory away and recreating it empty**, since a per-file `unlink()` sweep is genuine per-file evidence the watcher propagates with no floor involved, and would pass vacuously against a build with no floor.*

*Implementation status today (2026-08-28, the watcher's blind window — measured, not reasoned): the boundary above says the **live watcher** path is deliberately floor-free, because a streamed file-by-file removal is genuine per-file evidence where an unmount emits no per-file events at all. That stands. What does **not** hold is the unstated corollary a test premised itself on — that a watcher is blind to removals which happened before it started. On macOS it is not: FSEvents assigns event ids asynchronously, so a stream created with `SinceNow` can still deliver a removal that had already completed when the stream was created. Measured on macOS, 2026-08-28, with a 30-iteration probe over the real `LocalWrites::start`: **10 of 30** iterations delivered a `Removed` for a file unlinked microseconds earlier. inotify has no such window, so a green Linux run does not absolve the shape. Only the removals measured are known — ones completed microseconds before the watch; how far back the window reaches was not measured, and `SinceNow`'s contract is the reason to expect it bounded by the id-assignment lag rather than by the age of the removal. A vanish landing inside that window takes the floor-free per-file path on macOS where it would take the held path on Linux; one outside it reaches the floor through the next reconcile's empty scan exactly as described above. No production change is made for it: within that window the events are per-file evidence on their own terms, and widening the floor to the watcher arm would re-open the case the boundary was drawn to exclude. It is recorded because it is the kind of platform fact a reader re-derives wrongly: it surfaced as a flake in tier_1 `mass_delete_floor_test::the_resident_loop_routes_an_apply_command_to_its_engine` under the mac heavy tier's Rust-test gate (`mac-rust-test-check`), where the loop's own watcher consumed the pre-start removals through `handle_delete` and left the floor nothing to hold. The fix is a fixture, not a production guard: `pull_remote_changes_test::seed_tracked_row` seeds the `Synced` rows with **nothing written to disk**, so a test that runs a real watcher establishes the held-set precondition by construction instead of by winning a race (convention 14 — latency-independent state). Any future test that starts a watcher over its fixture directory uses it.

**The floor on an on-demand root — the same scan, over the rows with evidence (ratified 2026-09-28).** A windows binding now starts as a cfapi sync root by default ([`on-demand-files.md`](on-demand-files.md) § On-Demand Files → *The choice is the user's*), and the tier_3 witness above stages its vanish by renaming the bound directory away — which the cloud filter **refuses** on a registered root (`ERROR_CLOUD_FILE_ACCESS_DENIED`, WinError 395), so `test_filesync_mass_delete_floor.py` flips its fixture to always-resident first and the default windows shape has had no witness. The ruling, each point read off current code, not inferred: **(1) The floor reaches an on-demand root by exactly one path — the reconcile scan — and it does reach it.** The on-demand host runs `LocalWriteHost::converge` (drain → `reconcile` → upload) at startup and on every rescan tick, the same call the resident loop makes, so every pass evaluates the same derived hold; and its `DeletesHeld` verdict rides the same per-engine progress drain, which the agent spawns *before* it branches on mode. There is no second delete path to rule on: `libs/fauna-cfapi` registers only the read-side callbacks (`FETCH_DATA`, `CANCEL_FETCH_DATA`, `FETCH_PLACEHOLDERS`, `NOTIFY_DEHYDRATE_COMPLETION`) and no `NOTIFY_DELETE` — and none is wanted, because a cfapi delete notification would be per-file evidence like a watcher event, on the floor-free side of the boundary above, and the shared `notify` watcher already delivers exactly that (an Explorer bulk delete inside the root arrives file by file, is genuine intent, and propagates per file as it does on an always-resident root). **(2) The floor's universe is the rows with evidence — the `Synced` rows, and since the 2026-09-29 ruling below the *seen* `Placeholder` rows — and that restriction is load-bearing, not an always-resident leftover.** Directory listings populate lazily (`transfer_placeholders` marks one directory populated at a time; a subdirectory materializes on first browse), so a `Placeholder` row is a row whose on-disk placeholder may never have been created: a *never-seen* row's absence from a scan is evidence of nothing, and a floor that counted it would read every never-browsed subtree as a wholesale vanish. `reconcile` therefore lists the `Synced` rows, the placeholder rows this engine has itself put on, or observed on, this disk (the *seen* mark — *An offline placeholder delete propagates*, below) and the `LocallyDeleted` rows whose delete is still owed — one derivation, `SyncEngine::rows_with_evidence`, read by `reconcile` and `apply_held_deletes` alike; a never-seen `Placeholder` row is neither counted nor deletable by the scan (the live watcher's `handle_delete` still propagates a placeholder the user deletes — a row is deletable there unless already tombstoned), and a dehydrate flips a row back to `Placeholder` (`record_dehydrated` → `mark_placeholder`) and marks it seen — the file is freed in place, still on disk, so it stays in the universe whatever route the row took to `Synced` (a file uploaded from this disk was never transferred as a placeholder). The materialized placeholder itself, being on disk, is reported *present* by the scan — flagged, skipped by the hash path, counted by the delete path (*present-but-unreadable*, `on-demand-files.md`) — and `path_presence`'s `symlink_metadata` reading gives the same answer at the record-time re-stat (a reparse point is something holding the name), so the scan cannot mistake *free up space* for a delete at either link; that reading is sufficient, and it needs no placeholder-aware special case. Two consequences follow from the universe: a wholesale vanish of a root with exactly **one** row with evidence propagates that one delete (the single-file boundary in a different guise, the same one-version-retained loss magnitude), and one with **no** row with evidence — nothing hydrated, nothing seen — records nothing and offers nothing. **(3) The vanish shapes.** *The rename-away* the always-resident witness stages is unrepresentable on a root whose provider is **connected** — the cloud filter refuses it (WinError 395), a stronger guarantee than the floor; with the agent down the same rename is allowed, registered or not (measured on Windows 2026-09-29), which is the last shape below. *A vanished volume* (the drive holding the root unplugged) is the missing-root arm — `full_scan_filtered` errors on ENOENT and nothing is recorded — identical in both modes. *A graceful unregister* (`mark_root_for_full_teardown` on a mode flip or unbind) removes every un-hydrated placeholder from disk (measured, `cfapi_live_integration.rs`), but by then the loop future holding the watcher has already been dropped, and the files it removes belong to `Placeholder` rows whose seen marks the teardown clears before the unregister (decision (e) below), so no later scan counts them — an ordering guarantee plus rule (2), never a floor case. *A directory replaced while the agent is down* — a drive swapped, a restore tool, the user's own move while nothing ran; the shell registration may survive it (the crash-survivor registration the pinned-while-down pin measures) or have been removed out-of-band, but the replacement is not the directory the filter registered, so either way the restarted root boots as a **fresh registration** (decision (e) below: its seen marks are cleared before the sweep) — is the one shape that reaches the floor, and it reaches it through (1): the restarted root's startup `converge` finds every hydrated row missing and holds them. **(4) The verb reaches the engine through the same command channel, whatever the mode.** The hold surfaces on an on-demand binding (`folder-location-deletes-held` folds per bound path, mode-blind), so its confirm must reach that root's engine exactly as it reaches a resident one — a rendered offer whose verb errors is a bug. **An offline placeholder delete propagates — the sweep sees what the watcher would have seen (ratified 2026-09-29; built 2026-09-29).** The two-way ruling ([`on-demand-files.md`](on-demand-files.md) § *Sync direction*: on-demand is a storage choice, never a direction choice, and a change to a tracked file MUST be uploaded) covers a delete, and covers it whether or not the agent was running when the user made it: a delete silently reverted (the root) or lost (a browsed subdirectory) is that promise broken in a quieter voice. So the delete propagates — with exactly the live watcher's reach, never wider: **a delete of a placeholder that was on this disk.** Six decisions, each the answer to a question the 2026-09-29 measurement left open. **(a) The evidence is the engine's own record of the placeholder on this disk, per row — never the OS's populated bit.** A `Placeholder` row is *seen* once this engine has put its placeholder on the disk (the host reports every entry cfapi processed in `transfer_placeholders` — each entry's own result, never the requested set — marked AFTER the transfer succeeds, never before, so a crash loses evidence and never invents it) or has observed it present in a scan (the scan already reports placeholders present-and-flagged; marking on observation is what makes the mark self-healing after a lost write). A seen row's definite `NotFound` — the same `presence` re-stat, the same unreadable-prefix withholding as a `Synced` row's — is a delete; a never-seen row's absence is evidence of nothing, which is the lazy-population invariant restated as *never-seen is never evidence* (question 3 of the measurement holds by construction). The directory-level discriminator the measurement suggested (`CfGetPlaceholderStateFromAttributeTag`, the directory's populated bit) is refused on three counts: it is **coarse** — a row that arrives from the nest after its directory's listing reaches the disk only through (f)'s best-effort eager create, so *populated ∧ absent* would read a create that failed, or has not run yet, as a user delete, a false tombstone on the nest; it is **restart-unstable** — the root's bit is lost with its reparse point at every stop, and the measured subdirectory attributes change across the very restart the sweep runs over (`0x10` → `0x410`); and it is **host-specific**, where a per-row mark is a shared-Rust fact every host that puts placeholders on a scannable disk can supply (priority #2). The mark is one additive column on the row — device-local derived state, re-derivable from a scan — read nowhere but the delete universe. **(b) The floor (question 1) keeps its shape and its threshold; its universe widens from the `Synced` rows to the rows with evidence, `Synced` ∪ seen `Placeholder`.** One derivation (`missing_from_scan`) feeds `reconcile` and `apply_held_deletes` alike, so the hold, its count and the confirm verb cover seen placeholders with no new surface; point (2)'s two consequences are restated above in those terms (an on-demand root with nothing hydrated but two or more seen placeholders vanished wholesale now HOLDS and offers the confirm; the single-file boundary counts a lone seen placeholder). A vanished populated *subtree* is NOT a floor case and gets no per-subtree floor: on a registered root the filter refuses the rename-away and a vanished volume takes the root with it (the shapes of point (3)), so a subtree gone from inside a present, registered root is the user's act — the partial-vanish boundary the always-resident side already draws, propagated per file exactly as there. Never-seen descendants of a deleted subtree (a sub-subdirectory never browsed) stay `Placeholder` rows, are neither propagated nor repaired, and come back with the next listing of their parent — the residue the live watcher leaves today for the same delete (no file, no event), fail-safe on the destructive axis. **(c) The root (question 2) propagates too — evidence before re-population.** Reverting is not an acceptable steady state for the root; it is the same lost delete. The boot sweep runs over the tree as the downtime left it, BEFORE the root is connected: today `register_and_connect_shell` precedes `run_hydration_loop`, the re-registration re-arms the root's population, and the first browse after `CfConnectSyncRoot` lists every tracked row back. So the on-demand host's start becomes: the fold's row half (`prepare` opens the control plane and writes rows only) and the mark hygiene of (e) → the boot delete sweep (`reconcile`'s delete detection needs the DB and the disk, nothing else; with no provider connected nothing can re-populate under it) → connect → the watcher and everything else where it is (the fold's invalidation of stale hydrated copies dehydrates through cfapi and stays after the connect). After the sweep the re-arm's re-listing is idempotent (measured: the untouched sibling lists back) and lists nothing the sweep tombstoned; a browse racing the restart is unrepresentable in that order, and a test that stages one must find the deleted row absent from the re-listed set. **(d) A delete owed to the nest is durable — the row becomes `LocallyDeleted`, the mirror of `LocallyModified`.** Record-first stands (a failed record tombstones nothing), but on an on-demand root the disk cannot hold the evidence for it the way an always-resident root does: a seen row found gone whose record fails (the nest unreachable at boot — the commonest restart) would be listed straight back by the re-arm and the delete silently reverted, and the live watcher's `handle_delete` has the same hole today across a later restart. So a seen placeholder found gone — by the boot sweep, a tick sweep or the live watcher — leaves `Placeholder` for `LocallyDeleted` in the same pass: excluded from population listing and from every present-reading, retried by every later `reconcile`, tombstoned only when the nest acks — `LocallyModified`'s shape for the other direction. The flip lives in `handle_delete`, the one site every delete caller shares, so a replicated File Provider's `deleteItem` whose record fails holds its row the same way (no longer enumerated, while the OS retries the pending delete). The flip happens whether the floor then holds the set or not: a held `Placeholder` row that a re-armed population listed back would read present on the next pass and shrink the missing set below totality, releasing the held hydrated rows as ordinary per-file deletes. An owed delete meets the nest's log through the placeholder fold, and neither arm loses data: a remote **delete** settles it (the row is removed — nothing is owed), and a remote **edit** that moved the head after the offline delete wins (the row is re-pointed as a fresh, never-seen `Placeholder`, so its absence from this disk is not read as the old delete again); an unchanged head leaves it owed. A `LocallyDeleted` row whose placeholder a scan observes on the disk again (the old directory restored while nothing ran) was never deleted after all, and returns to a seen `Placeholder` with nothing recorded. A new `SyncState` variant, not a flag column: the enum is not FFI-exported (`to_display` is the app-facing vocabulary; `LocallyDeleted` displays as `Deleted` does, as nothing), and an exhaustive match is how the compiler finds every population, presence and badge site that must exclude it. **(e) Mark hygiene — the host's own removal of a placeholder is never a delete.** Two paths remove cloud-only placeholders by the product's hand, and both clear the set's marks BEFORE the removal, never after (a crash in between leaves placeholders on disk unmarked, and the next scan re-marks them; the reverse order would leave marks without files — false deletes): the graceful full teardown (`full_teardown_location` → `mark_root_for_full_teardown` on a mode flip, an unbind or a re-bind; measured: the unregister removes every un-hydrated placeholder), and a fresh registration — a root whose shell or filter registration did not survive the downtime has had its placeholders removed by the OS at the unregister, so the boot clears every mark before the sweep (the uninstall-then-reinstall over a leftover `fsid-<ref>.db`, the ghost sweep, point (3)'s out-of-band unregister and its replaced directory all land here; their hydrated rows still reach the floor as (3) rules). "Survived" means shell-registered AND filter-registered at the root's path, read before anything registers; a probe that errors counts as not survived — clearing is the fail-safe direction (fewer deletes, never more) — and a clear that fails fails closed: the root is neither swept nor served until the next engine start retries it, since marks that still claim placeholders the OS removed must never meet a sweep. The always-resident loop neither marks nor clears: a resident engine started over an on-demand root's DB (the mode flip) finds no marks and pulls the `Placeholder` rows down as it does today. **(f) No repair pass (question 4).** With propagation in, nothing dangles by this ruling's hand: a seen row gone is propagated, and a never-seen row is not on disk by definition and materializes with its directory's listing. The fold's new rows in a directory the OS already marked populated — a remote create that would otherwise never appear on this device, the two-way gap in the *other* direction, separate from this ruling — are pushed onto disk eagerly ([`on-demand-files.md`](on-demand-files.md) § On-Demand Files, its *Implementation status today*: `create_placeholder` on the fold's new rows, only into a directory the OS will not list again); that create marks the row seen on success like any other transfer. - **Unreadable is not absent — a path this process cannot read is never a delete (ratified 2026-09-20).** Every delete this system records rests on one inference: *a synced row's path was not found on disk, therefore the user removed it*. That inference is valid only when the pass could **look**, and three separate sites spelled *could not look* and *was not there* as the same `false` — `Path::exists()`, a `read_dir` whose `PermissionDenied` arm returned `Ok`, and a `WalkDir` iterator whose errors were dropped with `.filter_map(|e| e.ok())`. So a synced subdirectory going `chmod 000` — or a disk returning `EIO`, a network/FUSE mount going `ESTALE`/`ENOTCONN`, an unmounted volume — read as *every file under it deleted*, and those tombstones travelled to the nest and to every device of the set (for a shared set, to every member's copy) while every byte was still sitting on the user's disk.
