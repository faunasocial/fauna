> **Audience:** every app area (the banner renders on every authenticated page, all 7 apps); shared-Rust work adding feeders.
> **Purpose:** a user whose deployment is in a genuinely dangerous state must find out even if they never visit the page that detected it.

## Goal

Some client-detected conditions mean *possible compromise or impending unrecoverable loss* — not "an action failed." The product's pages are set-and-forget by design (a healthy deployment gives no reason to revisit Settings), so a page-local warning is structurally unseeable. Critical alerts therefore render as a **permanent banner list on every authenticated page**: prominent, destructive-styled, **non-dismissable** — an alert disappears only when the condition that raised it is re-checked and found resolved, never because the user swiped it away.

**The severity bar (deliberately high):** a critical alert asserts possible compromise of identity/keys, or a condition that will destroy user-irrecoverable data if unaddressed. Ordinary failures (a request failed, a bridge is down, sync is behind) are NOT critical alerts — they use the transient `error/warning/info-message` trio or their feature's own surface. Crying wolf here trains users to ignore the one banner that must never be ignored; a new feeder must clear this bar in its owning doc before posting.

## Mechanism

- **Shared registry** (`libs/fauna-client-alerts`, wasm-clean): an in-process, app-wide `CriticalAlerts` store of keyed alerts. `post(key, lines)` is idempotent per key (re-posting replaces the lines); `clear(key)` removes; an observer callback repaints the shell. Alert text is machine-composed `LocalizedText` (i18n keys, client-rendered verbatim) so all 7 apps say the same thing.
- **Observer dispatch is a synchronous hand-off, and the hand-off is never the repaint (ratified 2026-09-01).** `post`/`clear`/`clear_all` invoke every observer's `on_changed` in the posting caller's own stack before returning — deliberately, because the *sweep counts its own passes* barrier below only means what it says if a pass's repaint wakes are all handed to the shells **before** the completion bump: a detached/queued notify would put a repaint in flight past the barrier, re-opening the false-pass the barrier exists to prevent (and would couple this wasm-clean crate to a runtime). What makes synchronous dispatch safe is the observer's half of the contract: **`on_changed` is a prompt scheduling hand-off** — wake or schedule the platform's own repaint (tui wakes its render loop; linux `try_send`s to the GTK main loop; android writes a `StateFlow`; apple hops via a main-actor task; windows posts to its captured `SynchronizationContext`; web sets a Svelte store) and return. It must never block, never do I/O, and never touch UI-affine state inline: it runs on the posting feeder's thread, and an observer that stalls or dies there takes the feeder — and the rest of its sweep pass — down with it (measured on windows 2026-09-01: an off-UI-thread WinUI touch ended a pass between its feeders — `sweep-begin` logged twice, `sweep-end` once). Synchronous registry *reads* from inside the callback (`active`, `active_lines`, the pass counters) are allowed and normal; registry *mutation* (`post`/`clear`/`clear_all`) is not. The registry enforces mechanically what it can: the observer list is snapshotted and its lock released before dispatch (subscribing from inside a callback cannot deadlock), and each callback runs contained — `catch_unwind` natively, `catch` on the wasm shims' JS boundary — so a panicking/throwing observer (a foreign exception surfacing through UniFFI included) cannot end a pass and later observers still run, both pinned by mutation-graded tests. A *blocking* observer, by contrast, cannot be contained mechanically without detaching dispatch, which the barrier ordering above rules out — "must not block" is held by this contract and the per-app trampoline audit, while panic containment is mechanism. **A contained fault is still COUNTED, never silently discarded (ratified 2026-09-03).** `CriticalAlerts::observer_faults` is a lifetime `AtomicU64`, bumped from `notify`'s own `catch_unwind` `Err` arm natively and from each wasm chunk's shim on a caught JS throw (the native `catch_unwind` cannot see across that boundary) — a fourth counter beside the pass pair, readable through the same `uniffi::export` surface. Containment turning a loud failure into a silent one is a good trade only if something counts the silences: before this, `fauna-client-alerts` had no logging dependency at all, so a shell whose repaint hand-off died was indistinguishable, from anything readable, from a healthy one, and kept dying on every later notification.
- **Keys** are stable, feeder-scoped strings (e.g. `atproto-custody:<did>`), so a re-check updates its own alert rather than stacking duplicates.
- **Lifetime:** in-memory, per app session. A condition that still holds re-posts on its next check; one that resolved clears. No persistence — the detector, not a stored flag, is the source of truth (a stale persisted alarm that outlives its condition is the false-positive form of crying wolf). **"Session" means *identity*, not process:** a client MUST drop every alert (`clear_all`) wherever it tears authenticated state down — sign-out, **account switch**, nest-untrust, factory reset. Keys are identity-scoped (`atproto-custody:<did>`) and nothing re-checks a departed identity's DID, so an alert that survives the switch accuses the *incoming* account with a handle the user no longer has, permanently and un-dismissably — crying wolf by construction. A process-wide registry is the shape that gets this wrong; it is an identity-scoped singleton that outlives the window teardown.
- **Who runs the detector (ratified 2026-08-01).** A feeder that only runs while its own page is open is half a feature: the banner makes an alert visible everywhere, but nothing raises it for a user who never opens the page — the same set-and-forget blindness § Goal describes, moved one step back. So a feeder whose condition can arise while the user is elsewhere is driven from the **session-start sweep**, `libs/fauna-client-alert-sweep`: one shared entry point (`run_session_start_sweep`) that every app calls exactly once from the **universal post-auth hook it already has** (tui `session::establish`, beside `converge_seed_map` / `spawn_refresh_mail_epoch_schedule`; each app's equivalent). The trigger is per-app because session establishment is; *which* feeders run, in what order, and how a failure is handled are shared, so **a new feeder joins by editing the sweep crate, never by touching seven apps** (priority #1). Three properties are the sweep's contract: it is **best-effort** (sign-in never fails or waits on it), **every feeder runs independently** (one unreachable plane cannot skip another feeder's check), and **a failed read never clears** — unreachable is not resolved, so a standing alert outlives a nest that merely went offline. A feeder that is genuinely page-bound (a mint-instant TOFU check) may stay on its page's convergence; one whose condition is long-lived must be in the sweep.
- **How often the detector runs (ratified 2026-08-02).** Session start is the *first* sweep, not the only one: a desktop app left open for a week would otherwise check once, at the start of that week — the same set-and-forget blindness one step further back again. So the sweep **repeats on a clock for as long as the identity lives**, at `fauna_client_alert_sweep::RE_SWEEP_INTERVAL_SECS` (6 h), and an app's post-auth hook calls `run_alert_sweep_loop` — which opens with the session-start sweep — instead of a bare one-shot. The cadence is sized against **PLC's 72-hour contest window**, the deadline that actually binds: 6 h means a hostile rotation is detected with ≥66 h left to contest it, at four directory fetches a day. **A clock, not an event, is the only mechanism available** for feeders #1 and #3 — their condition is a change in the *public PLC directory*, which the nest never observes and therefore can never announce. **The loop stops on `CriticalAlerts::clear_all`**, which every app already calls at sign-out / account switch / factory reset per *Lifetime* above; that call is therefore the identity-teardown signal (`CriticalAlerts::teardown_epoch`) as well as the clear, and needs no per-app liveness plumbing. Feeder #2 is covered by the same clock ~120 times inside its 30-day window and deliberately gets **no** faster event-driven trigger, even though the nest's `SecurityNotifier` posts it a durable-inbox `SecurityNotice`: that notice carries only prose (`subject`/`body`, no machine-readable event kind), so re-checking selectively would mean asking the audited nest which of its own notices deserve an audit. (A third reason — that acking in the shared drain would consume a notice no app renders — retired 2026-08-10: the notice now renders via the notifications row, `notifications.md` § Security notices; the rejection stands on the remaining two.) The reasoning is kept on `run_alert_sweep_loop` so it is not rebuilt as if load-bearing. **A pass that ran before the account runtime is re-run at the custody door's readiness edge, not left to the clock (ruled 2026-10-01).** The post-auth hook fires before the seat's account runtime assembles (sign-in waits for neither), and feeder #1 reads the rotation keyring through that runtime, so a fresh sign-in's first pass commonly finds the ring unreadable. The wait after a pass whose ring read was refused therefore also ends when the door reports itself readable (`AtprotoIdentityStore::until_readable` — for the plane door, the moment the seat's runtime handle exists **and** its prologue — the first catch-up pass — has settled, since before that a replica the sign-out dropped reads an empty ring, which is not a refusal anyone retries), and the pass runs again then. The rule is **once per streak**: a pass that fails the ring read again waits out the ordinary clock, so a door that is readable yet failing cannot spin the loop, and the next pass that reads the ring re-arms the edge. It lives in the sweep crate and the seam, so it needs no per-app wiring, and sign-in still never waits on it.
- **The sweep counts its own passes** (`CriticalAlerts::sweep_passes_started`/`_completed`, bumped by the sweep around its feeder run): a pass publishes its start before its first feeder and its completion after its last, which is what lets a test anchor a *negative* assert ("this planted condition raises no banner") to the sweep's decision rather than to a clock. **`_completed` means every hand-off *returned or faulted*, not that every repaint was actually scheduled** (ratified 2026-09-03, correcting the 2026-09-01 dispatch-contract ratification's overclaim): a faulted hand-off schedules nothing, and is counted separately in `CriticalAlerts::observer_faults` (§ Mechanism above) rather than folded into "returned" — a negative assert that crosses the barrier should also check the fault delta is zero for the pass it cares about, or it may pass for the wrong reason. Test-facing contract and the reason the observable is a pair: [`../architecture/e2e-latency-independent-assertions.md`](../architecture/e2e-latency-independent-assertions.md) § convention 14 build-out.
- **Rendering contract** (ui.yaml `global:` owns the IDs): `critical-alerts` (view) is present iff ≥1 alert is active, on every authenticated page; each active alert renders one indexed `critical-alert[N]` text row. Placement/styling are per-app (idiomatic chrome), but the banner must be prominent and must not be dismissable while its alert is active.

**Why the replacement feeder clears the bar** (added 2026-08-01): the request is authorized by the identity seed *alone*, so a pending window the user did not open means someone else holds their seed — the severity bar's "possible compromise of identity/keys" in its most literal form. It is also the loss half: if the window closes uncontested, the attacker's key becomes the account's recovery root and the user's own kit stops working, permanently. And the condition is **long-lived and set-and-forget by construction** — 30 days in which the only remedy (veto, or succession) is one the user must be told about — which is exactly the case § Goal says a page-local warning cannot serve. The alert's lines render the countdown and the new key's fingerprint (`fauna_client_recovery::replacement::PendingReplacement`, whose doc comment already names itself the standing banner's model) so a user holding a kit can check whether the pending key is theirs. The **veto action** is not in the banner — a `critical-alert` row is text — it lives in Settings ([`../ui/settings.md`](../ui/settings.md) § Recovery kit).

**Why the handle-binding feeder clears the bar** (added 2026-08-01): the identity the user's rotation key protects is being published to the network under a name that is not theirs — or under none at all — so everyone who looks for the user finds someone else, durably and silently. That is possible compromise of identity in the § Severity bar's own terms, and it is set-and-forget by construction: nothing in the product would ever tell the user. The feeder's own doc owns the *mechanism*, the four shape decisions behind it (why the comparison is on the domain rather than the whole handle, why "nothing to check" is silent, why it is not gated on feeder #1's verdict, why the two keys stay distinct), and — equally load-bearing — the ruling that the *converse* check, the handle→DID direction, is **not client-side detectable and must not be built**: handle custody is domain custody.

**Why the domain-expiry feeder clears the bar** (ratified 2026-08-11, built 2026-08-12 — mechanism, signal set, and threshold rationale owned by [`../architecture/nest/domains-and-tls-bootstrap.md`](../architecture/nest/domains-and-tls-bootstrap.md) § Domain loss → *Detection*): a lapsed registration is both halves of the severity bar at once. The compromise half: whoever registers the name next **receives the deployment's mail** — including password resets for every external account tied to an `@domain` address — which is possible compromise of identity in the most practical form available. The loss half: phrase-only identity recovery resolves the home nest **from the handle's `@domain`**, and its direct-address fallback — built, but rendered on `tui` only, so most apps don't expose it yet — leaves a lapse severing the kit-only recovery path for most residents in practice — impending loss of a capability the user cannot recreate afterward. And it is set-and-forget by construction in a way none of the other feeders even match: the registrar's own renewal reminders go to an email address that may itself ride the expiring domain, so the failure mode eats its own warning channel; nothing else in the product would ever say a word before the failures start. The deliberately short 7-day pre-arm (auto-renew is invisible to RDAP, so a longer window would put an annual month-long false banner on healthy auto-renew deployments — this bar's crying-wolf failure) and the status-driven post-lapse arm are the owner doc's rulings. **This is the first deployment-scoped feeder, and its audience is every authenticated user, with role-differentiated lines** (only an admin can renew; a resident's stake — their addresses, their recovery locator — is real and their remedy different): the ruling and its grounds live with the mechanism.

**A feeder has three outcomes, not two (ratified 2026-08-02).** *Checked* (it ran and posted or cleared), *failed* (its plane was unreachable — the alert stands, the next sweep retries), and **skipped** (it had nothing to check: no ATProto identity, a `did:web` one, a mint with no DID yet, an empty rotation keyring, no handle domain). The third exists because the first two could not express "not applicable", and the gap that left was exploitable: a directory feeder with nothing to check returned without posting, clearing, **or recording** anything, while the sweep still reported every feeder reached — so no log could tell a declined audit from health. A skip is therefore **silent on the banner but never silent in the report** — it carries a stable reason token. A skip is *not* a failure: it never means retry, and it never justifies clearing a standing alert. Consequently a healthy deployment with no ATProto integration reports two skips, by design, and callers log failures and skips at different levels rather than branching on how many there are.

**A skip is never user-visible, and there is deliberately no "was this sweep complete?" accessor (ratified 2026-08-02).** The derived boolean existed, was made honest by folding skips into it, and never acquired a production consumer — all three app-facing callers branch on failures alone, each carrying a comment on why completeness must *not* gate anything: a healthy deployment with no ATProto integration is legitimately incomplete, and warning on that every session is § Severity bar's crying-wolf failure. What earns the answer "not user-visible" is the **floor**, not the severity bar alone: the one skip that was security-relevant — a box answering with nothing to decline being audited — is no longer a skip at all, because the floor turns it into a real audit that must pass or alarm. Every remaining skip is transient or by-design (an unsynced ring, a did:web identity, a mint in flight) and would accuse an innocent deployment. The `skipped` bucket itself stays and remains the ratified minimum above; consumers assert on it directly, since it names *which* feeder skipped and *why* — which a conflating boolean never could.

**What a sweep audits is not the audited party's to decide (ratified 2026-08-02).** A feeder's evidence being fetched independently is not enough if the *decision to fetch it* is not: the directory feeders took every gate — is there an identity, is it did:plc, does it have a DID — from one nest-computed reply, so a box could decline to be audited simply by answering with nothing. The rule is therefore that **a feeder's audit set is the union of what the nest names and what the client independently knows**, and the second half can only shrink to nothing when the client genuinely holds no anchor. For feeder #1 that anchor is the held rotation ring's directory-derived `published_for_dids`; the mechanism, its deliberate limits (it is feeder #1's floor only, and a retired identity reached through it is silent rather than alarming), and the matching rule for *clearing* a departed identity's alarm are owned by [`atproto-identity-custody.md`](atproto-identity-custody.md) § The audit floor and the departed-DID alarm. The general form belongs here because it applies to every future feeder: **if a feeder's gate is a value the audited party computes, the feeder needs a floor under it or a recorded skip above it — silence is what makes the gate exploitable, and the skipped bucket is the minimum.**

**A floor built only on *successful* checks is empty exactly where it is needed (ratified 2026-08-02).** The rule above was satisfied in form and defeated in substance: feeder #1's floor was `published_for_dids`, which is written **only on a passing verdict**, so for a genesis-time compromise — where the verdict never passes — the floor was empty and the audit set was still entirely the accused box's to choose. The general lesson, which every future feeder's floor must be checked against: **a floor derived from a feeder's own successes cannot cover that feeder's failure modes.** The fix adds a second source with deliberately weaker provenance — what the audited party *already claimed*, frozen client-side — whose security property is not independence but **irrevocability**: a box cannot unsay what it said. That is only ever sound for a floor, because a floor adds audit targets and can never mute one; it must never be promoted into evidence. Two corollaries with teeth: **(a)** a feeder's *gate* must be anchored on the data itself, not on the audited party's label for it (the sweep gated on the nest's `method` while the settings machine gated on the DID's own prefix, so a mislabelled identity was audited on one path and skipped on the other — **two production resolvers answering one question must share one predicate**); and **(b)** a rule that clears an alarm "because nothing client-side ties this to the account" has to be re-read whenever a new client-side tie is introduced, or it goes on clearing the very case the tie was added to catch. Mechanism, both floor sources, and the tightened clear condition are owned by [`atproto-identity-custody.md`](atproto-identity-custody.md) § The audit floor and the departed-DID alarm.

**The post-succession *unattested roster* is NOT a feeder, and must never become one (ratified 2026-08-02).** After the group sweep runs, `fauna_client_recovery::SweepReport` answers two questions, and only one of them is alert-shaped. The tempting one is not: `unattested_members()` — every member the ceremony did not itself add or remove — is by the sweep's own contract *"ordinarily the user's honest correspondents, and a normal healthy group has them — **not** a failure signal"*. Posting it would put a permanent, non-dismissable banner listing the user's friends on every page after every **successful** succession, which is § Severity bar's crying-wolf failure in its most literal available form. The roster is adjudication material, not an alarm; its surface is owned by [`succession-propagation.md`](succession-propagation.md) § Propagation → *MLS groups*. Two corollaries worth keeping, because each independently kills a shape that looks reasonable:

- **A one-shot "the ceremony finished" alert is mechanically impossible here, not merely discouraged.** § Mechanism → *Lifetime* drops every alert at **account switch**, and the succession ceremony's closing act *is* an account switch — the app signs out the succeeded identity and back in as the successor. An alert the ceremony posts is therefore cleared moments after it is posted, and making it survive would require exempting it from *both* the no-persistence rule and the clear-on-switch rule, the second of which exists precisely so an alert cannot accuse the incoming account.
- **The alert-shaped half is the other accessor**, `!old_leaf_removed_everywhere()` — groups where the ceremony did not finish, so the succeeded credential still has read access. That condition is genuinely re-derivable from durable local state (both MLS engines survive the switch), self-clearing once § Propagation's member-side re-add lands, and squarely inside the severity bar. It is the only succession condition a feeder should ever post. **It is not built yet, and the obstacle is this doc's own rule:** deciding it is a read of two co-resident MLS engines, which the sweep entry point (`run_session_start_sweep_at(rpc, config, alerts, actor_id, now)`) cannot reach, and adding an engine seam to that signature would touch all seven app call-sites — exactly what § Mechanism → *Who runs the detector* forbids. Whoever builds it resolves that seam question first; it is not a matter of writing another feeder body.

Anticipated future feeders (not built, listed so the shape is planned for): backup-destination failure past a data-loss horizon, client key-store corruption. Each lands via its own doc + a row here. (The domain-expiry watch graduated from this list 2026-08-11 and was built 2026-08-12.)

## Implementation status today

**The eviction-warning feeder is ruled and unbuilt (2026-10-01).** § Feeders' fifth row has no body in `libs/fauna-client-alert-sweep` yet: the nest serves the eviction record on `fauna.account.get` and no app reads its own. Why it clears the severity bar, what its lines say and when it clears are owned by [`admin.md`](admin.md) § Cutting a user off — eviction and suspension → *The member is told*. It is session-start-swept and clock-swept like the others and takes no faster trigger: a called-off eviction may stand on the banner until the next sweep, which errs on the safe side.

**The observer dispatch contract ratified and hardened 2026-09-01 — the shared-registry half of the windows sweep-wedge incident.** The § Mechanism dispatch bullet above is implemented in full: `CriticalAlerts::notify` snapshots the observer list and releases its lock before dispatching (a `subscribe` from inside `on_changed` no longer deadlocks), and contains each callback with `catch_unwind` — with the matching `catch` on both wasm chunks' `AlertsObserverShim` JS boundaries, where a Rust-side `catch_unwind` cannot reach. Pinned by mutation-graded tests at both levels: the registry's `a_panicking_observer_neither_kills_the_poster_nor_starves_later_ones` + `subscribing_from_inside_on_changed_does_not_deadlock` (each red under its mechanism's removal), and the sweep's `a_panicking_observer_cannot_wedge_a_pass_mid_flight` (a pass with a dying observer still runs its remaining feeders, keeps the alarm, and releases the convention-14 barrier). All 7 observers audited against the contract the same day, all conforming trampolines: tui (unbounded-channel `send` waking the render loop), linux (`try_send` to the GTK main loop), android (`StateFlow` write, inline `active()` read — a permitted read), apple/macos+ios (`Task { @MainActor }` hop), windows (`SynchronizationContext.Post` / thread-pool fallback — the incident's own fix), web (synchronous Svelte-store `recompute`). windows was the only violator ever measured, fixed at its own leg before this ratification. **The wasm half of the fault count had no test that could redden it until 2026-09-14** — every mutation-graded pin above is native-only, and zero `wasm_bindgen_test`s exercised the critical-alerts wasm path at all, so deleting `wasm_glue.rs`'s `note_observer_fault` bump reddened nothing on that target. Closed by `fauna-wasm`'s `a_throwing_js_observer_bumps_this_chunks_fault_counter` (`libs/fauna-wasm/src/critical_alerts.rs`, a `wasm_bindgen_test` under `just wasm-test-check`, mutation-verified: reddens alone when the bump is removed).

The e2e `test_custody_alarm_reaches_a_fresh_sign_in_before_the_runtime_assembles` witnesses it, with no wake and no ATProto-page visit: it signs out and back in on the same device, in the running app (a relaunch is not usable on web, where a reload drops the in-memory fake-directory override). The app log shows the first pass refused and the edge pass raising the alarm. The edge waits for the prologue as well as the handle: the runtime is up at assembly, before its first catch-up pass, so a replica that still has to catch up reads a short ring until that pass lands. On a native app that sign-out erases the replica, so the ring the edge pass reads is one the prologue keyed from escrow and re-presented in the same pass ([`account-data-taxonomy.md`](../architecture/account-data-taxonomy.md) § The generation machinery → *Escrow recovery*, item (3) owns the rule).

**Feeder #2 (pending RecoveryKey replacement) — detection built 2026-08-01; the caller landed the same day (tui only, see above).** The projection and the post/clear sync are shared Rust (`fauna_client_recovery::alerts`): `sync_pending_replacement_alert` routes both outcomes through one call so a vetoed or landed window takes its banner with it, and `refresh_pending_replacement_alert` is the single read a client's session-start and periodic refresh make. **Several nests, one alert (2026-10-01):** the bound nest's reading and each linked nest's (read by the runtime's secondary leg, handed over through `fauna_client_core::recovery_pending`'s linked readings and posted by every sweep pass) are separate sources of the one key (`CriticalAlerts::post_from`/`clear_from`): the alert stands while any source holds a window, shows the window that lands first, and a source reading nothing clears only its own reading. A transport failure deliberately **returns** rather than clearing — unreachable is not resolved, and clearing on error would let a nest that merely went offline silence a live compromise warning. The **caller** — the open design question until 2026-08-01 — is now the session-start sweep above, which is deliberately not the Settings page's lifecycle: the condition must reach a user who never opens Settings, and a poll driven by the page that displays the veto button would only ever fire for users already looking at it.

The identity-scoped clear the § Mechanism *Lifetime* bullet requires landed with tui (`CriticalAlerts::clear_all`, wired into tui's `drop_authenticated_state` and all six of linux's teardown paths). linux had shipped without it since 2026-07-23: its registry is a process-wide `OnceLock`, so an account switch carried the outgoing account's custody alarm into the incoming one — fixed in the same change. **The partial-teardown defect this bullet carried as OPEN is FIXED on tui (found 2026-08-13, fixed the same day), and its shape is the durable lesson: wiring the clear into the shared teardown is necessary but NOT sufficient — an arm can tear the session down without going through that teardown.** tui's two *mid-session escalation* arms — `DataMessage::NestIdentityChanged` (the nest-untrust case this bullet's list already names) and `DataMessage::IdentitySuperseded` — hand-wrote `session::sign_out` + `launch_machine = None`, the first two lines of `App::drop_authenticated_state`, and so skipped both the `clear_all` at its end and the `session_generation` bump at its start. It was **reachable, not theoretical:** the `IdentityChanged` surface offers a Trust action (`launch::LaunchAction::Trust`) that calls `trust_nest_identity()` and re-`route`s, and an `Online` snapshot there calls `session::establish` again **in the same process** — so the departed session's sweep loop, whose only stop signal is the `teardown_epoch` that `clear_all` alone bumps, kept polling the public PLC directory every 6 h beside the new one, one leaked loop per re-trust.

⚠ **The obvious fix does NOT work and was measured:** routing both arms through `drop_authenticated_state` reds `test_nest_identity_pin_post_auth.py::test_post_auth_valid_refresh_does_not_escalate --app tui`, because that teardown ends in `settings.clear_session()`, which zeroes the identity secret these launch-flow re-entries still need. **What landed instead is the narrower split:** `App::begin_identity_teardown` holds the two signals *every* teardown owes at its initiation — the counter, and `clear_all` — and `App::escalate_to_launch_surface` is the mid-session escalation shape (that call, then the sign-out pair, then the real launch re-entry) both arms now share, so a third arm added later cannot get it wrong by hand. The full teardown calls the same method rather than keeping its own copy. Pinned by `both_mid_session_escalations_count_and_clear_the_alert_registry` (tier_1, both arms), mutation-graded three ways: restoring either arm's old pair reds it at the counter, and deleting `clear_all` reds it at the registry.

**The same check — grep for every caller of your *sign-out primitive* that is not the shared teardown, not just "does my teardown call `clear_all`" — was run across the other six apps and closed 2026-08-14: only linux had the defect.** linux's gap was the `session_generation` counter half only (`clear_all` was already fleet-wide from the earlier fix above): its shared mid-session-escalation handler never called the teardown's counter bump, fixed with one added call. The other five came back clean by design, not luck: web and android each funnel every teardown through one canonical function (structurally immune to a caller forgetting the shared path), windows has no mid-session escalation arm yet to leak from, and apple's `tearDownSessionForSwitch()` already bundles both the counter and `clear_all` and is called by all three of its arms, including its own `NestIdentityChanged` catch — the one of the three with the same mid-session-escalation feature tui's defect lived in.

**web's registry is architecturally per-wasm-chunk, not per-process** — a native app shares one process-wide registry across every page for free; web's lazy-loaded wasm chunks are separately compiled binaries with their own linear memory, so a feeder's `Arc<CriticalAlerts>` can only live inside the chunk that hosts it (today: `fauna-wasm-atproto-settings`, feeder #1's home, **and the `fauna-wasm` core chunk, the session-start sweep's home since TRACK 4**). `apps/fauna-web/src/lib/critical-alerts.ts` is the aggregation layer that gives web the same cross-page behavior anyway: each chunk that hosts a feeder registers itself as a *source* once it loads, and the module merges every wired source's active alerts into one shared store the shell renders — a future feeder in a different chunk registers its own source the same way, no redesign needed. web's `clear_all` fires via the existing `actorScope.ts` registry (sign-out, account switch, and the e2e agent's session patches all go through the `identity` store) plus one explicit call site for factory reset, which deliberately does not change `identity`. **The same per-chunk split bit a *test-only* seam too, not just the registry:** `genesis_verify`'s PLC-directory override is an identical per-chunk `thread_local`, and TRACK 10 found it wired into only the atproto-settings chunk — see the TRACK 10 paragraph above for the fix.

**Declared gap — the succession "groups still owing the ceremony" feeder is ruled in, not built (2026-08-02).** § Feeders ratifies that this is the one succession condition worth a banner (and that the unattested roster is not), but no feeder posts it today and none should be written until the seam question that same bullet names is answered: the condition is a read of two co-resident MLS engines, and `run_session_start_sweep_at`'s parameters (`rpc`, `config`, `alerts`, `actor_id`, `now`) reach neither. Adding an engine provider to that signature would edit all seven app call-sites, which § Mechanism → *Who runs the detector* forbids in as many words, so the real work is designing the seam — an engine-provider trait behind the existing `config`-style indirection is the obvious candidate but is unproven, and the sweep crate must stay wasm-clean for web's core chunk. Until then a user whose sweep half-finished learns it from the ceremony's own outcome surface ([`succession-propagation.md`](succession-propagation.md) § Propagation → *MLS groups*) and nowhere else, which is a real hole: that surface renders once, and the condition it reports is long-lived.

**The sweep has its own end-to-end proof:** `tests/e2e-unified/tests/test_session_start_alert_sweep.py` (tier_3) creates a recovery kit, parks the 30-day window through the app's own *I Lost My Kit* gesture, establishes the session again, and asserts the banner is up **on the feed page** — the claim no unit test can reach, that session establishment actually runs the sweep and the alert crosses the registry into the app's chrome away from the page that caused it. Mutation-verified (removing the call from tui's post-auth hook fails it). A new app joins this proof by calling the sweep, the same way `CUSTODY_APPS` widens for the banner itself.

**End-to-end coverage is app-parametrized, not per-app:** `tests/e2e-unified/tests/test_atproto_custody_alarm.py` runs the whole feeder → registry → banner path (real mint, real bridge, tampered directory, alarm, un-tamper, clear) over every app that renders the banner. A new app's rendering is proven by adding it to that suite's `CUSTODY_APPS`, which is a build, not a marker widening.

**windows' e2e seam starts the loop, and a same-identity client rebuild keeps the alerts (2026-09-24).** Two windows deviations surfaced when windows joined the loud-surface witnesses (`e2e-latency-independent-assertions.md` § Implementation status today). **(1)** The e2e `session` seam, which never reaches `StartMainAppAsync`, ran only the one-shot pass, so under e2e no loop existed for `alert_sweep_wake` to wake. Both post-auth sites now call `CriticalAlertsSweep.StartForIdentity`: a first or identity-changing sign-in starts the loop, and a same-identity re-establish runs one pass instead of stacking a second loop (the split tui and linux make; the identity is the actor at a nest). **(2)** `App.DisposeNestClients` ran the whole actor-scoped drop on every client rebuild, a same-actor re-establish included, so each one `clear_all`ed the identity's standing alerts: an alarm whose next check could not read (an unreadable directory) stayed down, which is the "a failed read never clears" property broken from the app side. The drop now takes `identityEnds`: client-bound state still drops on every rebuild, while the alert registry and its loop record drop only when the identity actually ends (sign-out, account switch, factory reset — § Mechanism → *Lifetime*). Witnessed by `test_audit_floor_nest_silence.py --app windows` step 3, and pinned in `CriticalAlertsSweepTests`.

**apple keeps one loop per identity (2026-09-25).** `CriticalAlertsHost.startSweepLoop` used to restart the loop on every post-auth call by cancelling the previous Swift task. A Swift `Task.cancel()` never reaches a UniFFI future, though: the generated async call polls to completion. So the old loop kept running, and every same-identity re-establish (a re-dispatch after `trustNestIdentity()`, an e2e same-actor session patch) stacked another sweeper. The host now makes windows' split in shared FaunaKit (`CriticalAlertsLoopClaim`, one record for macOS and iOS): a first or identity-changing sign-in (the actor at a nest) starts the loop, and a same-identity re-establish runs one pass. `clearAll` forgets the record beside the epoch bump that stops the loop, so the two cannot disagree. The first loop keeps covering the identity across an `APIClient` rebuild, because the Rust loop holds its own `Arc` of the connection. Apple's same-actor re-establish already kept the alerts (its session patch drops actor-scoped state only on an actor change), so windows' deviation (2) never applied here. Pinned in `CriticalAlertsLoopClaimTests`.
