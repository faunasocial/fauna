## Goal

A person who set up a nest from the app can take it down from the app. Works-out-of-the-box has an exit half: without this view the only way out is the cloud provider's dashboard, a second dashboard for DNS, and a registrar support form for the transfer code. The view answers three questions — *which servers did Fauna create in my cloud account?*, *delete this one and clean up after it*, *give me my domain's transfer code* — and it answers them **with no reachable nest**, because the commonest reason to retire a box is that it is already broken or gone.

## Credential stance — the VPS token is re-entered, never persisted

**Decided: the view asks for the VPS provider credential every time, and never stores it.** Three reasons, any one sufficient. (1) A persisted token would rest on the account-state plane ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The kinds*), which rests on the nest *and* in each enrolled device's own replica ([`../architecture/account-replica-posture.md`](../architecture/account-replica-posture.md) § The replica boundary) — so, unlike under the `UserConfig` blob this reason was first argued against ("rests on the nest", re-argued 2026-10-02), a device that once read the row keeps it after the box is gone. What the replica cannot give is the primary case: the person retiring their only nest from a device that never held the row, or from a fresh one after the box is already gone, has nothing to read — so re-entry is still the floor the design needs, and a floor that always works beats an optimization that fails in the primary case. (2) A cloud token can create servers and spend money; keeping it for the deployment's lifetime to serve a once-in-a-deployment action is the wrong custody trade, and it would widen `dns-management.md`'s persisted-credential surface for no recurring benefit (DNS credentials are persisted because DNS reconciles continuously; nothing about a server does). (3) It is the existing shape: cloud recovery re-enters the token on `vps_config`. The token lives in machine memory for the page's lifetime and is dropped on exit.

**DNS credential, in preference order:** (a) the token just entered, when that provider also has DNS capability and its `verify()` reports a zone covering the domain (Hetzner, the bundled provider); (b) a held DNS credential (the account's DNS record, `dns-management.md` § Where the credential lives) covering the domain, when the view was opened from a signed-in session whose account runtime is up — the app passes the credential **into** the machine (the machine never reads config itself; § Where logic lives); (c) none → DNS cleanup is not attempted and the page lists what to remove by hand (§ DNS cleanup). **Resolved per domain, on *covering the domain***: both usable credentials are kept, and each domain the run cleans (§ DNS cleanup — several domains) goes through the first credential, in this order, whose zones hold it — a token holding some unrelated zone never shadows a held credential holding the right one. There is **no second credential form** in v1.

## Layout & flow

One page, `nest_retire`, in the onboarding-wizard family (hosted by the wizard host on every app, exactly as `nest_recovery` is — including over a live session, the append-mode precedent). Two entries, mirroring recovery's two:

- **`admin-nest` → *Retire this server*** (signed-in admin; a section beside Factory reset). Opens the wizard host in retire intent. Factory reset wipes a box the admin keeps; this destroys the box. The two sit adjacent and their labels must differentiate sharply.
- **`launch_retry` → *Retire a server*** (nest unreachable). Always shown there — unlike `launch-recover-button` it needs no custodied seed, only a cloud token.

Deliberately **no** entry on `identity_choice`: a destructive fifth button on the first screen a new person sees is the wrong trade; a person with no local account at all keeps the provider dashboard. Revisit on demand, not by default.

Page states, in order: **credentials** (the `vps_config` provider row, credential form and verify button, reused by ID — no region or server-type controls) → **list** (one row per listed server: name, attributed domain, address, a *current* badge on the box this session is signed into, an *unmarked* note on rows that carry no marker; an empty message that also says boxes created before 2026-07-08 predate the marker and are retired from the provider's dashboard) → **confirm** → **running** (two step rows: DNS, then Server) → **done** (outcome, plus any DNS left to remove by hand). Back from credentials returns to the entry that opened the page. The transfer-code affordance sits on the selected row in the list state and is independent of deleting.

## Box → domain attribution

A listed server carries a provider name, an id and addresses — not a domain — and the provisioning name is the domain with `.`→`-` (`my-site.example.com` and `my.site.example.com` collide), so the name alone never attributes. **A domain is attributed to a box only when verified: the domain's apex `A` record equals the box's IPv4.** Candidates, tried in order until one verifies: (1) the box's **PTR** (`get_ptr`, present on all six adapters; provisioning sets it to `mail.<domain>`, so strip the leading `mail.`); (2) domains the app passes in from local state (the signed-in account's nest domain, the pending-provision slot); (3) every zone the usable DNS credential's `verify()` reports whose dashed form equals the server name. Verification reads the `A` through the DNS provider's `find_records` when a usable credential holds a zone covering the candidate, else public DNS from the client — through `fauna_provisioning::probe`, the public resolver client the wizard already uses pre-auth, so the view adds no new third party. The provider holding the zone outranks the public resolver (it is authoritative and current; a resolver may serve a cached answer), so its "no" is final and public DNS is asked only when the provider could not be — no credential, no covering zone, or a failed read; a failed public read is *not verified*. A domain verified only through public DNS is attributed like any other, but nothing can be removed from a zone no credential holds: its confirm summary promises no removals and carries the by-hand list alone (§ DNS cleanup). **Unverified → the row shows no domain, DNS cleanup is skipped for it, and the transfer-code affordance is absent** — the server can still be deleted. Attribution never guesses. **A box may have served several domains**: the attributed domain is exactly the first candidate to verify in the order above (the PTR, tried first, names the mail host's domain); every *other* domain that verifies the same way is one of the row's **other verified domains** — planned or listed beside the attributed one, never a transfer-code target — and where that set comes from is § DNS cleanup → *Several domains*.

## Confirm shape

Irreversible and total: the server, its disk, and every account's data on it. The alpha deletion carve-out is about schema evolution, not about a person surprising themselves, so the confirm is stronger than factory reset's plain dialog:

- The summary names the **server name, provider, address, attributed domain and every other verified domain**, states that **all data on the server is destroyed and cannot be recovered except from a backup**, and states the **DNS plan** (which records will be removed automatically, or that none will and the list follows). On the *current* box it adds that this session's nest will stop existing.
- The person **types the server's name**; the confirm button enables on an exact match. Mandatory on every provider — it is what discharges `vps.md`'s mandatory per-box confirm for unmarked (OVH) rows, and one uniform shape beats a per-provider one.
- **The typed name binds the run to that server.** Passing the gate arms the run to the server whose name was typed; *retry* and *delete the server anyway* act on that server and no other, only while its run is on screen (and *delete anyway* only while the failed DNS step offers it), and leaving the confirm or the page disarms it. A row is selectable only in the list state, so nothing re-targets a confirm summary or a run once it names a server. The gate is therefore a property of the shared machine, not of each app wiring its buttons to the right states.
- Backups are **not** a gate (a person may retire a box they never used); the summary carries the fact, the Backups page carries the act.

## DNS cleanup — scope and order

**Order: DNS first, then the server.** Deleting the server first and crashing (or failing) before the DNS step strands `A` records on an address the provider will hand to a stranger — a dangling-DNS takeover — and the box has left the list, so the view can no longer reach the cleanup. DNS-first fails safe: a crash leaves a listed box with some records gone, and re-running converges (`find_records` pre-flight, `delete_record`, `delete_server` are all idempotent). The brief unreachability of a box about to be destroyed is no cost. A DNS-step failure stops the run before the server is touched and offers *retry* or *delete the server anyway* (which repeats the dangling-record warning and the by-hand list). The run records each planned removal's outcome as it walks the plan, so after a step that failed part way *delete anyway* adds to the by-hand list exactly the planned records not yet removed — ahead of the TXT, with the same still-points-at-the-box urgency the no-credential list gives them — and never the ones that are already gone.

**Scope: only records whose value points at the dead box, plus Fauna-remembered slot values — never a name sweep.** Removed: `A`/`AAAA` at the host-builder's name set (apex, `mail.`, `relay.`, `pds.`, `*.`) **whose value equals the box's address**; `MX` whose target is `mail.<domain>`; the floor `TLSA` at `_25._tcp.mail.<domain>`; the `_caldavs`/`_carddavs` `SRV` whose target is `mail.<domain>`; and, when the app passed in the DNS record, the remembered DKIM / `_atproto` / `_fauna self=` names through the existing marker-scoped converge passes run with an empty desired set (owner: `dns-management.md` § Fauna-managed). **Left in place and listed for removal by hand:** SPF, DMARC, MTA-STS and TLSRPT TXT — they live at names shared with non-Fauna records, carry no pointer to the box, and are harmless stale. PTR needs no cleanup (it dies with the address).

**Several domains — every domain verified to point at the box is cleaned, domain by domain.** A nest serves secondary local domains beside its primary, and publishes for each an apex `A`/`AAAA` → the box and an `MX` and DAV `SRV` → the deployment's one mail host, `mail.<primary>` (what a secondary publishes is `mail-multidomain.md` § Client reachability of a secondary domain and § Per-domain DNS records; a half-done primary rename leaves a `mail.<new>` `A` too). A retire that cleaned only the attributed domain would leave every other domain's apex on the released address — the takeover this section exists to prevent, one domain over. So the run plans the attributed domain's cleanup above and, for every **other verified domain** (§ Box → domain attribution), the same address name set (apex, `mail.`, `relay.`, `pds.`, `*.`) value-scoped to the box's addresses, its `MX`/`SRV` whose target is the attributed domain's mail host, and its own by-hand TXT — and no `TLSA`: the floor pin lives under the attributed mail host, whose plan covers it, and a name-keyed removal under `mail.<secondary>` would be the one name sweep. Value-scoping is what makes the whole name set safe to apply to every domain: a record that does not exist is a no-op, and a record the person has repointed is never touched. **Where the set comes from, with no reachable nest:** once a domain is attributed, every other domain the box may have served goes through *the same verification* as attribution — its apex `A` equals the box's IPv4, read through the credential whose zone covers it, else public DNS — drawn from (1) the domains the app passes in (from `admin-nest` the signed-in app passes the nest's active local-domain list, `mail-multidomain.md` § The `mail_domains` model; from `launch_retry`, local state alone), and (2) **every** zone every usable DNS credential reports — not only the dashed-name matches, since a secondary domain is named after nothing about the box. (2) is a scan that *reads*: nothing is removed on a name, and a zone whose apex points elsewhere is left entirely alone. A verified domain in a zone no credential holds goes to the by-hand list, exactly as the attributed domain would (next paragraph); each domain the run *can* clean goes through the credential whose zone covers that domain (§ Credential stance).

**When no usable DNS credential holds the domain's zone, the by-hand list is the whole output — and then it carries the value-scoped records too, ahead of the TXT, each with the value that identifies it.** The two halves are listed together but never read alike: the records above the TXT are the ones still pointing at an address the provider is about to hand to a stranger, so removing them is the same urgency the DNS-first order carries, while the TXT stay harmless stale. Telling such a person only about the four TXT would walk them into exactly the dangling-DNS takeover this section exists to prevent — the four providers with no DNS capability are the common case, not the corner. The value is listed because it is what says *which* entry at that name to delete: a record the person has since repointed is visibly not the one meant. The list is **derived from the same plan** the credential-holding path removes, so a record the plan learns to remove is a record this list learns to name.

## Transfer authorization code

Rendered only when the entered credential's provider has a registrar adapter with an auth-code call — today the bundled provider alone; no other registrar adapter has one, so for every other provider the row carries a one-line note that the code comes from the registrar's own dashboard. Pressing the button calls the adapter; `200` shows the code with a copy control (held in memory, never persisted, cleared on page exit); `202 available_after` shows the date the registry lock lifts. Requires a verified domain attribution. Dispatch exposes the capability as data (`supports_auth_code(provider_id)`) so the page never hard-codes a provider id; how the provider catalog represents it is `registry.md`'s.

## Where logic lives

All of it in shared Rust; apps render a snapshot and dispatch actions.

- **`fauna-provisioning`** gains `list_managed_servers` + `ManagedServer` on the `VpsProvider` trait (spec and per-provider filters: `vps.md` § Uninstall → *Listing primitive*) and `supports_auth_code`.
- **`NestRetireMachine`** — a separate machine type in the **`fauna-onboarding-machine`** crate (module `retire`), not new state on `OnboardingMachine` and not a new crate: it needs exactly that crate's dependency set, provider dispatch, fake-cloud base-URL seam and binding faces (UniFFI; `fauna-wasm-onboarding` — it must load pre-auth), while `OnboardingMachine` is already the largest machine in the tree. Snapshot: `{ phase: Credentials|Listing|List|Confirm|Running|Done, servers: [ManagedServerRow { server_id, name, ipv4, ipv6, domain: Option, secondary_domains, marked, current, transfer_code: Unsupported|Idle|Fetching|Code|AvailableAfter }], selected, steps: [Dns, Server], dns_plan: [DnsPlanLine { name, record_type, value, removed }], leftover_records, error, retired }` — `retired` is the row a finished run deleted, which has left `servers` by then. Actions: `SelectProvider`, `SetCredentialField`, the `hosted-auth` sign-in (`HostedAuthBegin`/`HostedAuthWait` — the same device flow the wizard's credential forms run, one shared implementation), `Verify`, `Select`, `FetchTransferCode`, `BeginConfirm`, `SetConfirmName`, `Confirm`, `Retry`, `ForceServer`, `Cancel`, `Back`, `SetCurrentIpv4`. The machine also owns what the page would otherwise re-derive: the credential fields and verify gate (`visible_fields`, `can_verify`), and every sentence that names what dies, the DNS plan or what is left to remove by hand, as `LocalizedText` the apps resolve (`confirm_summary`, `leftover_lines`, `transfer_code_note`, `step_label`, `step_note`). Inputs the app passes at construction, all optional: candidate domains (from `admin-nest`, the nest's active local-domain list beside the account's own domain — § DNS cleanup → *Several domains*), the current nest's address (for the *current* badge), and **every** held DNS credential (one per provider and set of zones; each domain goes through whichever one's zone covers it). An input the app learns after the page opened arrives through a setter (`SetCurrentIpv4`, `AddCandidateDomains`, `SetHeldDns`), and an app still reading one announces it (`ExpectAppInputs` … `AppInputsLanded`) so verify — where the machine reads them — waits for it. The machine never talks to a nest.
- **Apps** host the page in the wizard host. On a successful retire of the *current* box the app routes to its launch flow.

## Errors & edge cases

- **Crash or kill at any point** leaves a state the same view recovers: before the server step the box is still listed; after it nothing remains to do but the by-hand list, which the confirm already showed. No nest state is involved, so client-state recoverability is untouched.
- **Already gone** (`404` on either delete) is success.
- **Retired ≠ forgotten.** The box's custodied deployment seed stays in the account-state plane kind `fauna.state.deployment-seeds` ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The kinds*); `nest_recovery` may still offer it. Deliberate — re-provisioning the same identity elsewhere later, from backups, is the third exit guarantee. Do not "tidy" the seed away.
- **Web:** providers whose CORS policy is `proxy` are degraded exactly as for provisioning (`vps.md` § Supported Providers); no retire-specific rule.
- **Pagination:** the list follows every page; a truncated list that hides a fauna box is a bug.
- **A live-provision e2e box** (`fauna-e2e=1`) is an ordinary marked row.

## Don't do these

- Don't persist the VPS token, in account state or anywhere.
- Don't delete DNS by name sweep, and don't delete the server first.
- Don't attribute a domain from the server name alone.
- Don't branch on a provider id in an app or in the page logic.
- Don't gate the delete on a backup existing.
