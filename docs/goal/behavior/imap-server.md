## Goal

A single IMAP entry point per nest deployment, **served by the mail-bridge MDA role** (`bins/fauna-bridges/`, role discovered from nest by the enrolled service-user keypair — no `--mode=...` flag). Implements RFC 9051 (IMAP4rev2 baseline, **advertised alongside IMAP4rev1** for backward compatibility — § Capabilities), RFC 9208 (QUOTA), RFC 7162 (CONDSTORE + QRESYNC), RFC 6851 (MOVE), RFC 2177 (IDLE), RFC 5465 (NOTIFY), RFC 5256 (SORT/THREAD when upstream library support exists — see § Upstream-blocked gaps), and RFC 5161 (ENABLE). All mailbox state is nest-side; the MDA process is a stateless protocol terminator that holds only an in-memory snapshot of the current session's per-mailbox state plus the unwrapped MLS-decryption capability obtained at MUA-AUTH (per § Authentication; the capability is held session-scoped and used to decrypt sealed content per-record — § Content path).

**Bar: parity-or-better with Dovecot.** Any extension a hardened Dovecot install gives MUAs out of the box (IDLE, CONDSTORE, QRESYNC, MOVE, QUOTA, SPECIAL-USE, ENABLE, UIDPLUS, NOTIFY for incoming-mail push) must be present here. Beyond Dovecot's defaults, every mailbox write — APPEND, EXPUNGE, STORE flags, MOVE, COPY, CREATE/DELETE/RENAME — is atomic at the nest write boundary (the SQLite transaction that updates `bridge_imap_messages` / `bridge_imap_mailbox_state` / `bridge_imap_expunged` is the synchronization point; the MDA process never writes mailbox state directly).

**When in doubt, choose the stricter option.** Mirrors `smtp-server.md` § Goal: a non-conforming MUA that violates RFC 9051 in a way a strict reading would reject loses the connection rather than producing ambiguous mailbox state. Permissive carve-outs need explicit user approval and a counter.

## Process topology

| Port | Role | Process | TLS | AUTH |
|---|---|---|---|---|
| 993 | IMAP (implicit TLS) | mail-bridge MDA role | implicit, `MinVersion: TLS 1.2` (no `MaxVersion` cap, so 1.3 negotiates when the client offers it); cert lookup via the shared `bridgetls.Provider.GetCertificate` (`internal/tls/tls.go`) — `internal/mda/mda.go` builds its own `tls.Config` literal, there is no shared hardening-factory/cipher-pin (posture flow-traced and corrected in `smtp-server.md` § TLS posture per port) | OAUTHBEARER preferred; PLAIN over TLS fallback for legacy MUAs. AEAD-unwrap-as-AUTH against a per-credential wrapped-MLS-blob (see § Authentication; ratification of candidate (b), design ratified 2026-05-14, tracked internally, § Sub-question 1). |
| 143 | IMAP (STARTTLS) | mail-bridge MDA role | STARTTLS required; cleartext rejected with `BAD STARTTLS required` | same set as 993 |
| `/api/v1/ws/{actor_id}` | MDA ↔ nest RPC | WS-RPC + DAG-CBOR | TLS to nest's HTTPS listener | challenge-response over the WS subprotocol, signed by the MDA's enrolled service-user Ed25519 keypair; the MDA-role method allowlist is enforced nest-side (see `../architecture/apps/bridges.md` § Per-role method allowlist) |

There is exactly one MDA-role instance per nest deployment in the target shape; horizontal scaling is by enrolling additional MDA keypairs and load-balancing 993 / 143 across them. Per-session state (the unwrapped MLS capability, the in-memory `BodyStructureCache` reference, the CONDSTORE / QRESYNC client-position) lives in the MDA process only; persistent mailbox state lives in nest's SQLite (`bridge_imap_messages`, `bridge_imap_mailbox_state`, `bridge_imap_expunged`).

**Connection cap.** Both IMAP listeners are wrapped in the shared `internal/connlimit` global connection cap, with the **per-IP concurrent-connection cap** (`AuthPolicy.max_conn_per_ip`, hot-reloaded on `config_changed`) layered below it via `PerIPListener` — cap values, counters, and the full mechanism are owned by `smtp-server.md` § Connection-time limits. The IMAP-specific facts: the global ceiling is deliberately far above port 25's because IMAP legitimately holds many long-lived sessions (one persistent IDLE connection per mailbox per device); for 993 (implicit TLS) the cap wraps the raw socket below `tls.NewListener` so go-imap still detects `*tls.Conn`, while 143 (STARTTLS) wraps the raw listener directly; saturation is observable on `mda_connections_total{listener="imap-993"|"imap-143",result}` (`accepted`/`capped`/`per_ip_shed`); and the 993/143 listeners are published directly (§ Authentication), so they already see the real client IP — unlike CalDAV, no PROXY-v2 plumbing is needed first.

## Capabilities

The advertised set is owned by `bins/fauna-bridges/internal/mda/imap/capabilities.go::capabilityList()` (filtered through the vendored fork's `imapserver.Conn.availableCaps`) and pinned by `server_test.go::TestServerAdvertisesIMAPCapabilities`.

**Both IMAP4rev2 and IMAP4rev1 are advertised.** rev2 (RFC 9051) is the baseline the implementation targets — it folds IDLE / ENABLE / UIDPLUS / LIST-EXTENDED / MOVE / BINARY etc. into the baseline, so a rev2 client derives those from `IMAP4rev2` presence. rev1 is advertised **alongside** it because RFC 9051 §2 recommends a rev2 server also announce rev1 for backward compatibility, and a rev2-only advertisement is rejected outright by rev1-only clients — Python's stdlib `imaplib` raises `server not IMAP4 compliant`, and older MUAs / tooling cannot connect at all. Real servers (Dovecot, Gmail) advertise both. This serves the *works out of the box / widest client set* invariant at zero feature cost: the fork implements both profiles in one server (branching on `enabled.Has(IMAP4rev2)`), so a rev2 MUA still `ENABLE`s and uses rev2 while a rev1-only client gets rev1 response formats.

- **Pre-auth** (993 post-TLS / 143 post-STARTTLS): `IMAP4rev2 IMAP4rev1 SASL-IR LITERAL- AUTH=PLAIN AUTH=OAUTHBEARER`. `AllowInsecureAuth = false`, so the `AUTH=` mechs are withheld until the connection is TLS-protected (§ Authentication).
- **Pre-TLS** (a 143 connection before STARTTLS): the fork advertises `LOGINDISABLED` (and withholds the `AUTH=` mechs) until the connection is TLS-protected — the IMAP `LOGIN` command is honored (mapped to PLAIN auth-by-unwrap, § Authentication) but only over TLS, so a conforming MUA sees `LOGINDISABLED` and does not attempt cleartext LOGIN.
- **Post-auth**: adds `SPECIAL-USE LITERAL+ CONDSTORE QRESYNC QUOTA` (+ `QUOTA=RES-STORAGE` / `QUOTA=RES-MESSAGE`) and the rev1-compat caps the fork unlocks once rev1 is present (`UNSELECT ENABLE IDLE UTF8=ACCEPT`).
- **Never advertised** until their fork seam / upstream PR lands (§ Upstream-blocked gaps): `SORT` / `THREAD` / `NOTIFY` / `MANAGESIEVE` — advertising a capability the wire can't honor is worse than silent non-implementation.

## Authentication

Auth is **uniform** — every deployment uses the same AEAD-unwrap-as-AUTH mechanism (ratified as candidate (b) of the open question raised in `../architecture/nest/storage-modes.md` Appendix A; design ratified 2026-05-14, tracked internally, § Sub-question 1). The MDA fetches a per-(actor, credential) wrapped-MLS-blob via `fauna.bridges.fetch_wrapped_mls_blob(actor_id, credential_id)`, derives the unwrap key from the MUA-supplied credential, and AEAD-decrypts. **AEAD-success = AUTH-success.** AEAD-failure returns IMAP `NO Authentication failed` and `fauna.bridges.report_auth_event(result=fail)`. On success the MDA holds the unwrapped MLS-decryption capability session-scoped (`zeroize::Zeroizing`); on `LOGOUT` / idle timeout / session disconnect it zeroizes and calls `fauna.bridges.report_session_close(actor_id, credential_id, reason)`.

The mechanism never branches on storage mode — there is no storage mode (the axis is retired; `../architecture/nest/storage-modes.md`). The user's Fauna app provisions the wrapped-MLS-blob shape via `provision_wrapped_mls_blob`; the wrapped blob is the only credential format the MDA sees, and **nest holds no decrypt authority for the AUTH path**. The post-AUTH content path is uniform too — per-record discrimination (`OpenStoredRecord`) opens each record by its own strict shape rather than by any mode flag; see § Content path below.

| Mechanism | Notes |
|---|---|
| `OAUTHBEARER` (RFC 7628) | Preferred. The bearer-token value is the MUA credential used to derive the unwrap key (HKDF → AEAD; design ratified 2026-05-08, tracked internally). |
| `PLAIN` (RFC 4616) over TLS | Fallback for legacy MUAs. The password value is the MUA credential used to derive the unwrap key (argon2id → AEAD per the same crypto spec). |

`AllowInsecureAuth = false` on both 993 and 143. PLAIN advertised only after STARTTLS on 143. Both `OAUTHBEARER` and PLAIN are supported uniformly on every deployment (the ratification's default — uniformity outweighs the "PLAIN-only because the box owner can already read mail" UX argument, which applied only under the retired plaintext-mode posture; both KDF families are already implemented in `libs/fauna-mls/src/wrapped_blob/`).

**The IMAP `LOGIN <user> <pass>` command (RFC 9051 §6.2.3) is supported, over TLS only.** `Session.Login` (`internal/mda/imap/session.go`) maps it to the *same* AEAD-unwrap-as-AUTH path as `AUTHENTICATE PLAIN` — it builds a PLAIN payload from `<user>`/`<pass>` and runs `authenticatePLAIN`, so actor resolution, wrapped-blob fetch, AEAD unwrap, and the `report_auth_event` audit fire identically. LOGIN-over-TLS carries the same cleartext credential as PLAIN-over-TLS (no security delta), and supporting it widens MUA compatibility — `imaplib.login()` and legacy clients that speak only the `LOGIN` command can now connect. It is gated post-TLS: the fork's `handleLogin` rejects LOGIN with `NO [PRIVACYREQUIRED]` when `canAuth()` is false (no TLS, `AllowInsecureAuth=false`), and the server advertises `LOGINDISABLED` in the pre-auth capability set so a conforming MUA never attempts cleartext LOGIN. A failed LOGIN returns a tagged `NO Authentication failed` (an `*imap.Error`, not the `[SERVERBUG]` a bare handler error would map to). Note the distinction: the **SASL `AUTH=LOGIN` mechanism** is still **not** advertised (only `AUTH=PLAIN` / `AUTH=OAUTHBEARER` are) — RFC 9051 doesn't require it and the SMTP submission half converged on the same PLAIN+OAUTHBEARER set (per `smtp-server.md` § Auth on each port); it is only the IMAP `LOGIN` *command* that is now honored as a PLAIN-over-TLS equivalent. Pinned by `auth_test.go::TestLoginCommandSuccess` / `TestLoginCommandFailsWithWrongPassword`.

`SCRAM-SHA-256` is **not** advertised by the MDA. The earlier "SCRAM verifier on nest in plaintext mode" shape (candidate (a)) was retired by the I5 ratification of candidate (b); plaintext mode does not need a SCRAM path because nest holds no per-credential verifier.

The MDA reports every AUTH outcome via `fauna.bridges.report_auth_event` (success or fail), **stamped with the connecting client's source IP** (the 993/143 listeners are published directly, so this is the real client address); nest holds the audit log and feeds per-credential failure-rate signals back to its rate limiter. (`report_auth_event` rejects an empty `source_ip`, so the IP must be present — it is, on every accepted TCP connection.)

**Online-guessing / KDF-exhaustion brake.** Before the `validate_recipient` round-trip and the Argon2id AEAD-unwrap, the MDA checks a per-`(principal, credential_id, source-IP)` failure lockout — the **same** fixed-window counter the SMTP submission path uses (`mail.auth.max_auth_failures_per_minute`, catalog default, 1-minute window; `0` disables). The `principal` is the **canonical** `base@domain` the username resolves to (`auth.PrincipalKey`), so the forms that resolve to one credential (`alice`, `alice+`, `alice+default`) share one bucket rather than each getting a fresh per-credential allowance (§ B7). The `(limit+1)`-th failed attempt within the window is refused **before** any nest call or KDF, denying the attacker both the bridge's per-attempt KDF cost and an AEAD-timing oracle; the counter resets on every successful AUTH and on window rollover. Two coarser defense-in-depth buckets ride alongside the triple — per-(principal, credential_id) across all IPs at a small multiple of this limit and per-source-IP across all usernames at a larger multiple — closing the distributed/rotating brute force a per-triple bucket misses (§ F11; full mechanism in `mail-policy-config.md` § Submission policy AUTH-failure-lockout row). The lockout is held in the MDA process (shared across all IMAP sessions, hot-reloaded on `config_changed`); like the submission path, the locked branch is the one AUTH exit that skips `report_auth_event` (it would otherwise inflate the audit log during a sustained brute-force) and surfaces a bridge-local warn instead. Implemented in `internal/authlock` (shared with the MTA + CalDAV); see `mail-policy-config.md` § Submission policy for the catalog row and `caldav-server.md` § Network exposure for the CalDAV twin.

**Don't add a separate IMAP-bearer-token auth surface.** The legacy `bins/fauna-bridge-imap` bearer-token flow described in `smtp-server.md` § MUA-facing view (Thunderbird, Apple Mail) was retired with the legacy terminator (tracked internally). New code uses OAUTHBEARER (preferred) or PLAIN over TLS (fallback) only — both go through the same AEAD-unwrap-as-AUTH path; no mode-conditional branch in the MDA AUTH code.

## Content path

The post-AUTH content fetch is **ONE uniform step at the MDA bridge** (Phase-3 D1, design ratified 2026-07-07, tracked internally, built 2026-07-08; the storage-mode axis it used to fork on is retired, Phase 4 — `../architecture/nest/storage-modes.md`). After AUTH (per § Authentication), every IMAP / CalDAV read that returns a body or an index segment opens the stored record through the same path:

- At AUTH the session builds a **per-connection `MailRecordOpener`** from the MLS-snapshot plaintext (parsed ONCE — the F2 fix; the leaf secrets stay FFI-side and zeroize on session close).
- Each `encrypted_body` / `encrypted_index_hint` returned by `fetch_message_ciphertext` / `fetch_index_segments_since` / `query_events` / `get_event` goes through the one serve path (`OpenStoredRecord`): every record rests a sealed `MailRecordEnvelope` (the nest verifies the seal shape on every write) and HPKE-opens via the opener; an unsealed payload, a record that fails AEAD-open, or a session with no opener **errors** — corruption is never silently served, and no raw record is ever passed through (the legacy-raw pass-through was removed in the 2026-09-24 compat-remnant sweep, [`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § Dimension 2).
- **Mail (IMAP) opens are epoch-aware; CalDAV/CardDAV opens are not.** Every AUTH'd-session IMAP open site — FETCH (`fetch.go`), body-axis SEARCH's index-hint open (`search.go`), the `\Junk` re-train open (`store.go`), and the SELECT-time spam score (`spam_score.go`) — calls `mailfauna.OpenStoredRecordAt(opener, sealed, basis)`, the epoch-aware sibling of `OpenStoredRecord`, passing the record's own seal instant as `basis` (the `stored_at` wire field on `FetchMessageCiphertextReply` / `IndexSegment` — never `internal_date`; `0` = unknown, a standing-sealed record) so the opener tries the session's candidate per-epoch keys before the standing key. **The re-score drain (`rescore_drain.go`) is epoch-aware too, but through a different mechanism** — it has no AUTH'd session opener (it runs unattended, servicing a user-minted `content.read{mail}` capability grant), so it discriminates the fetched bytes with `mailfauna.IsSealedMailRecord`, then for a sealed record asks the capability registry for the grant's in-window candidate keys — `GrantSet.KeyForMailEpoch(owner, basis, now)` (`internal/capability/registry.go`), keyed off the same seal-instant basis (`ct.SealEpochBasisUnix()`) — and opens with `mailfauna.OpenMailRecordWithKey`, trying each candidate key in turn; never `OpenStoredRecordAt`. CalDAV/CardDAV opens (`report.go`, `sync_collection.go`, `autoschedule.go`) and the per-user spam model stay on plain `OpenStoredRecord` (standing key only) — calendar/card content and the spam model are not epoch-sealed. The epoch derivation, key schedule, and MSEK-rotation-grace mechanism are owned by `../architecture/encryption-at-rest.md` § Capability tiering → Content-sealing epochs (built 2026-07-18; write flip thrown 2026-07-19) and `../architecture/owner-key-material.md` § Path B-sibling-2 per-epoch extension; this doc names only the IMAP-side call sites.

There is deliberately **no per-reply discriminator field** on the I2b reply types — the discrimination is on the *bytes' own strict shape*, so `FetchMessageCiphertextReply`, `FetchIndexSegmentsSinceReply`, `QueryEventsReply`, `GetEventReply`, and the CalDAV payloads keep their bare `encrypted_*` byte fields unchanged (wire-shape stability of the ~22 shipped Phase C/D handlers preserved). One additive field breaks that otherwise-unchanged surface deliberately: `FetchMessageCiphertextReply::Found.stored_at` and `IndexSegment.stored_at` (both `i64`, unix seconds, always sent; `0` = unknown — the nest's append-time clock read failed, a standing-sealed record) carry the record's seal instant for the epoch-aware opener above — it is key-*selection* metadata, never a sealed/unsealed discriminator, so it doesn't reopen the "no discriminator" rule; `QueryEventsReply` / `GetEventReply` (calendar) carry no such field, matching CalDAV's non-epoch content path. The `storage_mode` field on `fauna.bridges.fetch_config`'s reply **remains** (other consumers: DKIM/TLS custody, claim-time consent copy) but has **no content-path consumer left** — the value is the constant `"encrypted"` from first boot (`../architecture/nest/storage-modes.md` § The transition contract).

**Bridge lifecycle (historical — the offline mode-migration tool never shipped).** The storage-mode axis is retired (`../architecture/nest/storage-modes.md`); there is no deployment mode to migrate between, and the `migrate --to` subcommand this section used to describe was never built — retired unbuilt (`../architecture/nest/storage-modes.md` § What replaced each piece of the axis). A bridge's only startup dependency on `fetch_config` today is reading the now-constant `storage_mode` field for wire compat; there is no restart-and-remigrate flow.

| RPC | Caller | `storage_mode` semantics |
|---|---|---|
| `fauna.bridges.fetch_config` (reply) | BridgeMda \| BridgeMta | No storage-mode field: the constant `storage_mode: "encrypted"` that rode here as a wire-compat shim left 2026-09-24 (`../architecture/nest/storage-modes.md` § The transition contract); the bridge never branched on it. |
| `fetch_message_ciphertext` (reply) | BridgeMda | `encrypted_body: bytes` — a sealed record's ciphertext (always sealed; the MDA opens it via `OpenStoredRecord`, above). `stored_at: i64` (seal instant, `0` = unknown) feeds the epoch-aware opener (`OpenStoredRecordAt`, above) — key-selection metadata, not a discriminator. |
| `fetch_index_segments_since` (reply) | BridgeMda | Per-segment `encrypted_index_hint: bytes` — same shape; no per-segment discriminator. Per-segment additive `stored_at: Option<i64>`, same epoch-selection role as above. |
| `query_events` / `get_event` (reply) | BridgeMda | Per-event `encrypted_body: bytes` + `encrypted_index_hint: bytes` — same shape; no per-event discriminator. |

This row of the contract was ratified by the I5 plan-area session on 2026-05-14 (the candidate-(i) reasoning is preserved in the internal design memo § Sub-question 2; ratification entry in the memo's revision history; tracked internally).

## Mailbox model

### Standard mailboxes

The following appear automatically after first AUTH; the MDA seeds them lazily on first SELECT against `bridge_imap_mailbox_state` (`uid_validity`, `uid_next`, `highestmodseq` initialized).

| Mailbox | RFC 6154 attribute |
|---|---|
| INBOX    | `\Inbox`    |
| Archive  | `\Archive`  |
| Drafts   | `\Drafts`   |
| Sent     | `\Sent`     |
| Trash    | `\Trash`    |
| Junk     | `\Junk`     |

One additional name is **protected without being standard**: the guardian held mailbox ([`family-safety.md`](family-safety.md) § The mail gate) — never seeded, no SPECIAL-USE attribute, but CREATE/DELETE/RENAME refuse it exactly like the six.

User-created mailboxes are flat or hierarchical with the canonical separator `/`. RFC 6154 special-use attributes other than the six above are not assigned — clients setting `\Archive` (etc.) on a non-standard mailbox lose the attribute on the next LIST.

### ACL

V1 is single-user: every mailbox is owned by exactly one `actor_id`, no sharing. RFC 4314 ACL is not implemented; `GETACL` / `SETACL` are not advertised. Shared-mailbox semantics are a future feature surface (out of scope here; revisit when the conversations / groups infrastructure exposes a shared-folder primitive that maps cleanly to IMAP).

### Subscriptions

`SUBSCRIBE` / `UNSUBSCRIBE` persist in `bridge_imap_subscriptions(actor_id, mailbox)` on nest; `LSUB` / `LIST (SUBSCRIBED)` reads from the same table. Subscriptions are per-actor, not per-credential. Idempotent on both directions per RFC 9051 §6.3.7 / §6.3.8 — SUBSCRIBE-twice and UNSUBSCRIBE-on-not-subscribed both succeed. SUBSCRIBE on a not-yet-CREATEd or already-DELETEd mailbox is also permitted (RFC 9051 §6.3.7); the subscription persists across the mailbox's lifecycle. `LIST RETURN (SUBSCRIBED)` issues two `list_mailboxes` round-trips (one for the full mailbox set, one with `subscribed_only=true`) and tags the intersection with `\Subscribed`; `LSUB` and `LIST (SUBSCRIBED)` issue one with `subscribed_only=true` and tag every result. LSUB-side mailboxes that no longer exist in `bridge_imap_mailbox_state` are silently dropped (the LSUB surface returns only currently-existing subscribed mailboxes; clients that need deleted-but-subscribed mailboxes track them client-side).

## Read surface (brief)

Read RPCs are already cataloged in `../architecture/apps/bridges.md` § Bridge-kind catalogue (caller classes) — the MDA invokes them verbatim and does not redefine the shape:

`list_mailboxes`, `select_mailbox`, `list_messages` (UID-paginated metadata + CONDSTORE incremental sync via `since_modseq`), `fetch_message_metadata` (per-UID metadata fetch), `fetch_message_ciphertext` (one ciphertext at a time), `search_messages` (flag + header axes; body axis falls through to local index decrypt), `sort_messages` (when upstream library support is present — see § Upstream-blocked gaps), `fetch_index_segments_since` (SEARCH's body axis; the segments are ciphertext on nest, decrypted ephemerally on the MDA inside the AUTH'd session), `get_quota` (per-actor quota-root usage + limits — RFC 9208 GETQUOTAROOT translation).

The read surface is straightforward translation of IMAP wire commands to nest RPCs; the spec is the authority for argument shape (`bins/fauna-nest/src/bridge_imap_handlers.rs` and the `bridge_imap_messages` schema in `../architecture/nest/common.md`). This doc focuses on the **write surface, the modern extensions, and quota composition** — the parts that have no specification today.

### Body-section FETCH (RFC 9051 §6.4.5)

A body-axis FETCH fetches the message ciphertext once (`fetch_message_ciphertext`), decrypts it ephemerally under the session MLS capability (`OpenMailRecord` — see § Content path), and serves the requested **section** of the resulting RFC 5322 plaintext. Real MUAs (Thunderbird, Apple Mail) sync headers with `BODY.PEEK[HEADER.FIELDS (…)]` and lazily fetch parts rather than pulling whole bodies, so the section forms are baseline parity-or-better-with-Dovecot, not an extension.

**Section extraction is shared Rust.** The MDA never re-parses RFC 5322 Go-side; it calls `fauna_mail::fetch_body_section(raw, spec)` (`libs/fauna-mail/src/bodysection.rs`, UniFFI-exported), which reuses the same `mail-parser` parse as `derive_body_structure` / `derive_envelope` (priority #2: MIME logic lives in shared Rust). Extraction is **verbatim** — the returned octets are sliced from the original message bytes, preserving header folding, line endings, and DKIM-relevant bytes exactly; the MDA does not re-serialise the header.

**Top-level sections (implemented).** With no numbered part, the specifiers are:

| Request | Returns |
|---|---|
| `BODY[]` | the whole message, byte-identical to the stored plaintext |
| `BODY[HEADER]` | the header block **including the terminating blank line** (everything up to and incl. the first `CRLFCRLF`) |
| `BODY[TEXT]` | everything **after** the header block's blank line (the body) |
| `BODY[HEADER.FIELDS (f1 f2 …)]` | only the named header lines, each verbatim, **in the order they appear in the message** (not request order — matching the go-imap reference `imapserver.ExtractBodySection` and Dovecot; MUAs parse into a map and are order-agnostic), followed by the blank-line terminator |
| `BODY[HEADER.FIELDS.NOT (f1 f2 …)]` | every header line except the named ones, in message order, + the blank line |

Field-name matching is case-insensitive; a requested field absent from the message is simply omitted (the blank-line terminator is still emitted). An optional `<origin.octets>` `<partial>` is applied last (RFC 9051 §6.4.5): an origin past the end of the section yields the empty string; a length running past the end clamps to what remains. `BODY.PEEK[<section>]` returns the identical octets to `BODY[<section>]` — `PEEK` only governs the `\Seen` side-effect (below), and the response token never carries `.PEEK`.

**Numbered MIME parts (implemented).** A part path is a dot-joined sequence of 1-based part numbers (`BODY[2]`, `BODY[2.1]`), addressing one MIME part of a `multipart/*` message and recursing into nested multiparts and encapsulated `message/rfc822`:

| Request | Returns |
|---|---|
| `BODY[N]` | the part's **contents**: a leaf part's body (without its MIME header), a `multipart/*` part's raw body (boundaries + children verbatim), or — for a `message/rfc822` part — the **entire encapsulated message** (its header + body) |
| `BODY[N.MIME]` | the part's **own** MIME header block (incl. the blank line) |
| `BODY[N.HEADER]` / `BODY[N.HEADER.FIELDS (…)]` / `BODY[N.HEADER.FIELDS.NOT (…)]` | for a `message/rfc822` part, the **encapsulated** message's header (filtered as above); for a non-message part, that part's own header (the go-imap reference's `openMessagePart` passthrough — Dovecot parity) |
| `BODY[N.TEXT]` | the encapsulated message's body (or the part's own body for a non-message part) |
| `BODY[N.M]`, `BODY[N.M.…]` | recurse: address sub-part `M` of `multipart/*` part `N`, or sub-part `M` of the message encapsulated at `N` |

Part addressing follows the §6.4.5 special cases: on a **non-multipart** message a leading `1` (`BODY[1]`) refers to the message itself (so `BODY[1]` ≡ `BODY[TEXT]`); a structurally-valid request for a part that does not exist returns the empty string (NIL), not an error. The CRLF immediately preceding a MIME boundary delimiter belongs to the boundary, so a part's body and an encapsulated message both end **without** that trailing CRLF (matching the go-imap reference's multipart reader). The `<partial>` substring and `BODY.PEEK[…]` behave exactly as for top-level sections.

**Decoded binary parts — `BINARY[…]` / `BINARY.SIZE[…]` (implemented).** RFC 9051 folds the RFC 3516 BINARY content extension into the IMAP4rev2 baseline FETCH items, so a `IMAP4rev2` client (rev2 is the baseline profile; rev1 is also advertised for compatibility — § Capabilities) may use them without a separate `BINARY` capability. `BINARY` addresses the **same numbered parts** as `BODY[N]` but returns the part's contents with its `Content-Transfer-Encoding` **removed**:

| Request | Returns |
|---|---|
| `BINARY[N]` | part `N`'s contents with its CTE decoded — `base64` / `quoted-printable` → raw octets; `7bit` / `8bit` / `binary` / no-CTE → verbatim. A `multipart/*` or `message/rfc822` part has no leaf CTE and is returned verbatim. Emitted as a `~{n}` **literal8** (it may contain NULs) |
| `BINARY[]` | the whole message: its header block + the CTE-decoded root body (the only section form besides `BODY[]` to include the header) |
| `BINARY.SIZE[N]` | the **decoded** octet count of `BINARY[N]` (an inline number, not a literal) — the count after CTE-decode, not the wire/encoded length |

Decoding is **CTE-only — never charset conversion** (RFC 3516): a `text/*` part fetched via `BINARY` returns the bytes after base64/QP decode in the message's original charset, not transcoded to UTF-8. Extraction is the same shared-Rust path (`fauna_mail::fetch_binary_section` / `fetch_binary_size`, `libs/fauna-mail/src/bodysection.rs`, reusing `mail-parser`'s own base64 / quoted-printable decoders). A part whose `Content-Transfer-Encoding` the server cannot decode (anything other than `7bit` / `8bit` / `binary` / `quoted-printable` / `base64`) is answered with a tagged `NO [UNKNOWN-CTE]` (RFC 9051 §6.4.5 — the server fails the request rather than returning undecoded bytes), never a silent empty body. The `<partial>` substring applies to the **decoded** bytes; `BINARY.PEEK[…]` governs only the `\Seen` side-effect.

**Unopenable records — served degraded, never an error to the FETCH.** A body-axis FETCH that reaches a record no key in the session's standing set opens — sealed to another recipient, or malformed or tampered at rest (a rotation never produces one: every generation is carried, `../architecture/owner-key-material.md` § Path B-sibling-2 → *Pre-rotation mail at rest*) — serves that one message degraded and carries on with the command. The message keeps its UID, FLAGS, INTERNALDATE, MODSEQ and RFC822.SIZE; its BODYSTRUCTURE, ENVELOPE, `BODY[…]` and `BINARY[…]` are all derived, by the same shared-Rust calls as a real message, from one fixed placeholder message: a 7-bit `text/plain` part whose Subject is `This message could not be opened` and whose body names the condition, with no From, Date or Message-ID, so the MUA falls back to the record's real INTERNALDATE and no identity is invented. This is the IMAP twin of the contained-condition rule `mail-app-surface.md` § Inbound client receive → *Unopenable records* owns: one bad record affects that record, never the messages a FETCH spans with it. **RFC822.SIZE stays the stored record's size** (`ciphertext_size`, as for every message — § Read surface): a metadata-only FETCH never opens the record, so serving the placeholder's length there would answer the same UID with two sizes depending on what else the FETCH asked for, and the mismatch with the `BODY[]` literal's length is the one every sealed message already has. **A MUA caches the placeholder per UID permanently:** unlike the app's per-run ledger there is no retry, so a placeholder served once stays in that MUA for that UID even if a later session's key set would open the record. That is accepted because the condition is deterministic for the key set; the MDA itself never caches the placeholder's BODYSTRUCTURE or ENVELOPE (the cross-session LRU), so a MUA that drops its cache, or a second MUA, gets the real message as soon as the record opens. **No opener at all** (the account has no MLS snapshot on file) is a session condition, not a record's, and still fails the FETCH: a placeholder there would be cached for every message in the mailbox. The MDA logs the condition at WARN once per record and at DEBUG after (`internal/mda/undecryptable.WarnDedup`, keyed by the record's message id and shared with the DAV collection read path), because every re-sync spans the record again.

> **Implementation status today.** **Slice 1 (top-level sections), Slice 2 (numbered MIME parts), `BINARY[…]` / `BINARY.SIZE[…]` (RFC 3516), and the `\Seen`-on-non-PEEK side-effect are DONE** (tracked internally): all three tables above + `<partial>` + the `[UNKNOWN-CTE]` failure mode are served over the real stack (tier_3 `test_mail_bridge_mda.py::test_mda_imap_sectioned_body_fetch` + `::test_mda_imap_numbered_part_body_fetch` + `::test_mda_imap_binary_section_fetch`; exhaustive shared-Rust unit coverage in `bodysection.rs`, Go-seam coverage in `fetch_section_test.go`), and a non-PEEK body/binary FETCH now implicitly sets `\Seen` (below). The only rejected form is the **top-level `MIME` specifier** (`BODY[MIME]` with no numbered part — MIME only has meaning for a part) (`rejectSectionedBodyFetches` in `internal/mda/imap/fetch.go`). The RFC-9051-baseline FETCH side-effect surface is now complete.
> - **`\Seen` on non-PEEK FETCH (implemented — tracked internally).** RFC 9051 §6.4.5: a non-`PEEK` `BODY[…]` / `BINARY[…]` FETCH implicitly sets `\Seen` on each fetched message; `BODY.PEEK[…]` / `BINARY.PEEK[…]` leave it untouched, and `BINARY.SIZE[…]` is a size query that never sets it. `fetchWithDecryptor` (`internal/mda/imap/fetch.go`) runs one pre-pass gated on the `wantsSeen` predicate: it collects the matched-but-unseen UIDs (mirroring the emit loop's numSet + `CHANGEDSINCE` filters against the pre-set modseq), sets `\Seen` on them in **one batched** `fauna.bridges.store_flags(op=add, [\Seen])` write, and merges the returned flags + bumped modseq back into the rows so the per-row emit reflects post-set state. Per Dovecot parity it then **force-emits `FLAGS`** (and, under CONDSTORE, the bumped **`MODSEQ`** — RFC 7162 §3.1.4) on the same FETCH response, set *before* emit, so the MUA learns the message is read on the same round-trip rather than via a follow-up unsolicited FETCH. The `store_flags` write also fans out the `BridgeMailboxState::Flags` IDLE push to sibling sessions (a parallel MUA learns it was read). tier_3 `test_mail_bridge_mda.py::test_mda_imap_seen_on_non_peek_fetch`; Go-seam coverage in `fetch_seen_test.go`.

Go-seam coverage in `fetch_body_test.go`: `TestFetchSpanningUnopenableRecordReturnsEveryMessage` (FETCH 1:3 over a mailbox whose middle record is sealed to another recipient returns three messages, the middle one the placeholder with its stored size, uncached, warned once across two FETCHes) plus the serve-rule arms `TestFetchRawRecordIsNeverServedVerbatim` / `TestFetchSealedRecordWrongKeyServesPlaceholder`. The rule is FETCH's alone; the other paths that open a stored record (MOVE/COPY, the `\Junk` re-train, body-search index hints) keep their own handling.

### SEARCH

The MDA splits each `SEARCH` / `UID SEARCH` request into **server-side axes** (handled by one `fauna.bridges.search_messages` RPC) and a **local body axis** (handled by decrypting per-message index hints inside the AUTH'd MDA session). The bridge ANDs the two axes after the server-side RPC returns; OR / NOT are scope-reduced (the MDA returns `BAD search criterion not supported` — Phase C+ may add them by issuing multiple `search_messages` RPCs and unioning client-side).

`SEARCH ALL` (RFC 9051 § 6.4.4 — the `ALL` key matches every message) carries **no terms on either axis**, so the MDA issues `search_messages` with an empty `terms` list and nest, applying "no filter", returns every UID in the mailbox (`search_bridge_imap_messages` adds no `WHERE` clause beyond `(actor, mailbox)`). The empty `terms` list MUST be encoded as a canonical empty CBOR array (`[]`, `0x80`) — **not** `null` — because nest strict-decodes `SearchMessagesRequest.terms: Vec<SearchTerm>` and rejects `null` for a list (the bridge's Go encoder coerces a nil slice to a non-nil empty slice for exactly this reason; `wsrpc.SearchMessages`).

**Server-side axes** (one `SearchTerm` per predicate; the handler ANDs them in SQL):

| IMAP criterion | Wire term | DB predicate |
|---|---|---|
| `KEYWORD <flag>` / `\Seen`, `\Flagged`, … | `HasFlag { flag }` | `instr(' ' \|\| flags \|\| ' ', ' \|\| flag \|\| ' ') > 0` (space-bounded so a keyword substring doesn't false-match a system flag) |
| `UNKEYWORD <flag>` | `LacksFlag { flag }` | negation of the above |
| `HEADER From <substring>` / `To` / `Cc` / `Subject` | `HeaderContains { field, value }` | `instr(field_norm, lower(value)) > 0` against the case-folded `*_norm` column |
| `SINCE <date>` | `SinceInternalDate { ts }` | `internal_date >= ts` (inclusive — RFC 9051 §6.4.4) |
| `BEFORE <date>` | `BeforeInternalDate { ts }` | `internal_date < ts` (exclusive) |
| `LARGER <n>` | `Larger { size }` | record block length (from the CARv2 `MultihashIndexSorted` index in the segment `.dat`, looked up by `segment_records.record_cid`) > size (strict) |
| `SMALLER <n>` | `Smaller { size }` | record block length < size (strict) |

**INTERNALDATE is the nest's own receipt time — never the sender's `Date:` header.** RFC 9051 §2.3.3 defines
INTERNALDATE as the server's internal date for the message, "the date and time it was received"; the
message's own `Date:` header is a *separate* fact the MUA already shows from the body. So on the inbound path
(MTA ingest and the nest→nest mail relay) `bridge_imap_messages.internal_date` is stamped from the
**nest-assigned** `MailFloorMetadata.received_at` — the same server clock reading the record's segment append
takes, floored to seconds — and never from `PublicMailMetadata.timestamp`, which is the MTA bridge's parse of
the sender's own RFC 5322 `Date:` header and is unauthenticated: nothing in SMTP or RFC 5322 obliges a sender
to be truthful there. Sourcing INTERNALDATE from it would hand the sender the SEARCH window: a backdated
header hides a just-arrived message from `SINCE`, a future-dated one surfaces an old message as recent and
pins it to the top of every INTERNALDATE-sorted mailbox. The header value is still carried and stored (as the
floor's `timestamp`) for display and for anything that genuinely wants the sender's claim; it is simply never
load-bearing for ordering, filtering, or retention. **Two deliberate exceptions, both client-supplied by
design:** `APPEND` takes the MUA's `date?` argument (§ Write surface — RFC 9051 §6.3.12 makes that the client's
to set) and mailbox migration replays the source server's INTERNALDATE, so an imported archive keeps its
history ([`mailbox-migration.md`](mailbox-migration.md)). Both enter through
`place_or_get_existing_placement`, not the inbound `place_inbound_mail` door.

At a relay hop the value is **forwarded verbatim** rather than re-stamped — the receiving nest is not where
the message was received — which is exactly what
[`../architecture/message-segment-store.md`](../architecture/message-segment-store.md) § Invariants means by
`received_at` surviving the relay while `stored_at` is overwritten locally. That preservation is only as
sound as the origin's sourcing, which is what this rule fixes.

**Local body axis** (`BODY` / `TEXT` criteria): the MDA fetches `fauna.bridges.fetch_index_segments_since(actor_id, mailbox=selected, since_modseq=0)` — sealed per-message index hints — and decrypts each segment locally under the session's MLS capability. Each plaintext hint is tokenized through the shared `mailfauna.Tokenize` (deterministic NFKC + UAX#29 word-segment + Unicode case-fold; `libs/fauna-mail/src/tokenizer.rs`), and a candidate UID matches when every query term tokenizes to at least one token AND all those tokens are present in the segment's token set. The match is **conjunctive across body terms** (every term must hit). A `BODY` search with no other axis fetches the full per-mailbox segment list; mixed criteria intersect the local match with the server-side `search_messages` result.

**Coverage-based acceleration (owned by [`content-index.md`](content-index.md) § Where the index is built).** Before the decrypt-and-tokenize scan above runs, the MDA asks the per-user content index — built by a desktop app and synced to the box, per that doc — which of the candidate messages it can already answer for, and takes that verdict directly, skipping the HPKE open entirely for a covered message; every uncovered message (including the whole mailbox when no index exists or the index query fails) falls back to the scan described above. This is a latency-only optimization — the SEARCH result set is identical either way — so this doc names only that it exists; the coverage/build mechanism is `content-index.md`'s to own.

> **Index-hint open uses `OpenMailRecord`, not `Decrypt`.** The index hint is an `EncryptToRecipient` `MailRecordEnvelope` (HPKE-sealed to the actor's leaf init pubkey — the *same* seal as the body, sealed by APPEND and MTA inbound), so `bodySearch` opens it with the snapshot-leaf-secret primitive `MlsCapability.OpenMailRecord(envelope, snapshot)` — identical to the body-FETCH path — **never** the MSEK-AEAD `MlsCapability.Decrypt` (which opens only the snapshot blob at AUTH). Conflating the two fails at runtime; a stub-decryptor unit test cannot catch it, so the body axis (and the `\Junk`-train body open it shares) is proven through the deployed stack by the tier_3 `test_mda_imap_search_body_axis_decrypts_index_hint` (tracked internally — parity-verification).

**Search-axis degradation.** The MTA bridge cannot read sealed bodies, so it can populate only the plaintext floor when it places a message. The four `*_norm` columns degrade as follows on inbound mail:

- `from_norm` ← case-folded `public_metadata.sender_domain` (always populated; the MTA reports the SPF/DKIM-vetted envelope domain on every ingest).
- `to_norm` / `cc_norm` / `subject_norm` ← empty string. Searches on these axes return zero matches — they are not "errored", they degrade to no-hit.

`fauna.bridges.append` (user-uploaded mail via MDA) likewise populates only `from_norm` (the MUA supplies the envelope domain via `AppendMessageRequest.sender_domain`). A future per-app uploader extension (Phase D+ scope) MAY tokenize From/To/Cc/Subject MUA-side before sealing and pass them in a sealed companion to populate the other three columns; the column shape is stable for that addition.

`COPY` / `MOVE` carry every `*_norm` column verbatim from the source row (no re-derivation — placement is the unit of indexed-substring inheritance). `EXPUNGE` deletes the row and its columns.

**Column cap.** Every `*_norm` column is capped at **1024 bytes** by the writer (UTF-8 char-boundary truncation, lower-case). A pathological 100 KB Subject header still bounds the SUBSTRING-index cost. Searches against truncated rows return zero matches when the query substring falls past the cap — acceptable Phase C floor; an extended-prefix MAY land alongside any future admin-tunable knob.

## Write surface

Every write goes through one nest RPC per IMAP wire command. The MDA process performs no SQLite work locally; the RPC is the atomic boundary.

> **Body size on the MDA↔nest wire (ratified 2026-07-12; both reference legs + ceiling
> retirement landed by 2026-07-18).** `append`'s `encrypted_body` and
> `fetch_message_ciphertext`'s reply body ride **inline** only up to the mail inline
> ceiling; a larger sealed body crosses the bulk-byte plane as a reference. Constants,
> enforcement points, and reply codes are owned by `mail-message-size.md` § Message size limits
> (cap rationale: `../architecture/transport.md` § Max frame). **Both legs are BUILT and
> live.** FETCH (read): `SealedBodyOf` (`internal/mda/imap/body_ref.go`) transparently
> resolves a fetch reply's body whichever way it arrived, so a MUA fetching a large
> message sees it byte-for-byte with no IMAP-visible difference. APPEND (write):
> `Session.Append` stages an over-frame sealed body via `mailstage.StageSealedBody` and
> names it by `body_ref`. **The ceiling is `max_message_bytes` alone** since ceiling
> retirement (the former ~8.06 MB at-rest limit is gone — continuation records rest any
> size); because IMAP APPEND has no SMTP perimeter clamp, nest's `append_message_handler`
> is its authoritative size gate, refusing an over-ceiling literal with the shared typed
> `message_too_large` that the MDA maps to an IMAP `BAD`. See `smtp-server.md` § Message
> size limits for the full current state.

### `\Junk` flag-change ↔ spam-training contract

Per `docs/goal/behavior/mail-spam.md` § Training signal sources, the `\Junk` flag-set / -unset (via STORE +/-FLAGS) and the MOVE / COPY into / out of the SPECIAL-USE `\Junk` mailbox are **explicit training signals for the per-user spam classifier**. The MDA trains on the user's behalf — agent-side, in its AUTH'd session: it opens the actor's sealed model (or starts from an empty one), applies the event, re-seals, and writes model and sealed history row in one `fauna.bridges.put_spam_model` (`mail-spam.md` § Encrypted-mode interaction):

- `STORE +FLAGS (\Junk)` → `label="spam"`, `source="imap_junk_flag"`.
- `STORE -FLAGS (\Junk)` → `label="ham"`, `source="imap_junk_flag"`.
- `MOVE` / `COPY` into a `\Junk`-marked mailbox → `label="spam"`, `source="imap_junk_move"`.
- `MOVE` / `COPY` out of a `\Junk`-marked mailbox → `label="ham"`, `source="imap_junk_move"`.

The MDA detects the `\Junk` mailbox via its SPECIAL-USE attribute (per § Standard mailboxes), not by the literal mailbox name — a locale-renamed Junk mailbox still fires. The MDA fires one event per wire action and never dedups; the one-lesson rule (a signal whose label matches the actor's newest recorded lesson for that message is a duplicate, so the MUA that pairs a flag-set with a MOVE teaches once) runs **nest-side**, on the `put_spam_model` carrying the history insert, not in the MDA. Labels, the source taxonomy, the dedup rule, and the classifier lifecycle (per-actor model storage, cross-actor isolation, cold-start, reset, encrypted-mode wrapping) are owned by `mail-spam.md` § Training signal sources; this section pins only the IMAP-side trigger contract above.

### Tombstone retention

**Built (2026-08-11), mirroring the CalDAV/CardDAV siblings' S6.8d2/S6.9 pattern.** The placement journal's `MailPlacementRecord::Expunge`, `MailPlacementRecord::Move` and `TombstoneRef` (`fauna_mail::segments::placement`, format v2) carry a required `deleted_at` (epoch seconds) — the field that makes a retention prune possible at all, the same v1→v2 bump `fauna_calendar`/`fauna_contacts` went through. The IMAP `expunge_handler` stamps `deleted_at` eagerly at EXPUNGE time and piggybacks `MailPlacementSegmentManager::prune_tombstones`, gated on the same effective `imap.tombstone_retention_days` (catalog default 30 / floor 7, per `mail-policy-config.md`) `ImapPolicyOverrides::effective()` returns on `fauna.bridges.fetch_config`'s reply. A `Move`-produced tombstone is stamped like a delete: each of the three `Move` writers sets the record's `deleted_at` from the same `now` `apply_move` writes to the source rows' `bridge_imap_expunged.expunged_at`, so the SQLite row and the journal agree and a journal replay reproduces the stamp (the fold never reads the clock), and the retention prune ages a moved message's tombstone out exactly as it does an expunged one's. (The pre-bump v1 read path and its boot heal retired 2026-09-24 — the compat-remnant sweep, [`../architecture/compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md) § Program 4.) `bridge_imap_tombstones_total` is emitted (`tracing`, `target: "nest_metrics"`) whenever a prune pass removes at least one tombstone.

**The prune floor (built 2026-10-08).** The prune trims only the placement manifest; the live `bridge_imap_expunged` table keeps every row, so on a running nest the expunge log stays complete. A restore, though, rebuilds that table from the manifest's surviving tombstones, so the prune leaves its mark there: each pass raises the mailbox's `MailboxState::pruned_modseq` to the highest modseq it dropped (omitted at rest while 0, so a never-pruned manifest encodes as before), the restore replay carries it into `bridge_imap_mailbox_state.pruned_modseq` (0 on every mailbox no restore touched), and `list_bridge_imap_expunged_since` answers `None` for a `since_modseq` below it — `list_messages` then reports no expunged UIDs, so neither the inline `SELECT (QRESYNC …)` nor `UID FETCH … (CHANGEDSINCE n VANISHED)` emits a partial `VANISHED (EARLIER)` (§ QRESYNC). A manifest rebuilt from the journal segments replays every `Expunge` record, so its tombstones are complete and its floor is 0. The CalDAV/CardDAV journals do not record a floor yet.

**See also.** The tombstone log is also persisted to the `__mail-placement` reserved folder (per `reserved-folders.md` § __mail-placement Sync) and pinned by snapshot rows alongside the content manifest, decoded via `MailPlacementManifest::decode_any_version`, which refuses any `format_version` but the current one (its pre-bump v1 read arm retired 2026-09-24 with the compat-remnant sweep).

### Atomicity rule

Every write RPC's nest-side handler holds **one SQLite transaction** spanning all state changes. MOVE in particular MUST NOT split into separate COPY + EXPUNGE transactions; an MDA-visible MOVE failure leaves both mailboxes untouched. The wire response is generated after the transaction commits; if the commit fails, the MDA returns `NO [SERVERBUG]` and the connection terminates (no partial-write recovery — re-issue from the client).

## CONDSTORE / QRESYNC (RFC 7162)

The MDA advertises `CONDSTORE` and `QRESYNC` capabilities by default — both are gates for any RFC 7162 behavior, so the client must `ENABLE` (RFC 5161) the relevant extension before the MDA emits CONDSTORE / QRESYNC responses.

### Per-mailbox MODSEQ

`bridge_imap_mailbox_state.highestmodseq` is a monotonic per-mailbox counter, incremented atomically on every state-changing RPC (APPEND, STORE flags, EXPUNGE, MOVE, COPY). *State-changing* is literal: an RPC that resolves to no actual change — a STORE whose UIDs already hold the requested flags, an EXPUNGE with nothing `\Deleted` left to remove — leaves the counter alone, so a client's own retry cannot manufacture modseq churn. It is **persistent across MDA restarts** (lives in nest's SQLite) and **stable across QRESYNC reconnections**. Reset (back to 1) happens only on CREATE; a RENAME preserves the counter alongside `uid_validity`.

`bridge_imap_messages.modseq` per row is the value of `highestmodseq` at the time of that row's last state change. CONDSTORE FETCH responses include `MODSEQ (<value>)` whenever the client has `ENABLE CONDSTORE`'d.

### CONDSTORE `UNCHANGEDSINCE`

`STORE seq UNCHANGEDSINCE modseq FLAGS (...)` (RFC 7162 §3.1.3) returns an `OK [MODIFIED uid_set]` response listing UIDs whose modseq advanced past the supplied value — the client knows which writes were rejected for staleness and which were applied. The atomicity rule extends to UNCHANGEDSINCE: the nest RPC checks every UID's modseq against the supplied value inside the transaction, and applies only the unchanged subset; the response reports both the applied and rejected partitions in one round-trip.

### QRESYNC `SELECT (QRESYNC ...)`

QRESYNC (RFC 7162 §3.2) lets a reconnecting client supply `(last_uid_validity, last_modseq, last_uid_set, last_known_uids)` and receive:

- `VANISHED (EARLIER) <uid_set>` — tombstoned UIDs since `last_modseq` (read from `bridge_imap_expunged`).
- A `FETCH` for every UID whose modseq has advanced past `last_modseq` (modseq, flags — body is not re-fetched unless the client asks).
- A new `OK [HIGHESTMODSEQ]` for the current state.

If `last_uid_validity` is stale (mailbox was deleted-and-recreated, or the box owner manually re-seeded), the MDA returns `OK [UIDVALIDITY <new>]` and the client falls back to a full resync. If `last_modseq` predates a pruned tombstone (§ Tombstone retention), the MDA does not synthesize VANISHED responses (it would be lying); it returns `OK [HIGHESTMODSEQ <new>]` and lets the client diff against its local snapshot. The test is the mailbox's prune floor (§ Tombstone retention → *The prune floor*): only a restore from a pruned manifest can lose a tombstone the live log would still hold, and below the floor `list_messages` reports no expunges at all.

**Implementation status (T3.2-b / T3.2-b2).** The fork's `(QRESYNC ...)` SELECT-param parser is live and the bridge forwards `(last_uid_validity, last_modseq)` to the nest, activating the restore-divergence detection (γ) below and emitting `OK [HIGHESTMODSEQ]` for the current state. The MDA emits `* VANISHED` for live expunges (EXPUNGE command, IDLE push) and `* VANISHED (EARLIER)` for a `UID FETCH … (CHANGEDSINCE n VANISHED)` (RFC 7162 §3.2.5.1) once the client has `ENABLE QRESYNC`'d. As of **T3.2-b2** the *inline* form is also emitted — the `VANISHED (EARLIER) <uid_set>` + changed-message `FETCH (UID FLAGS MODSEQ)` responses delivered **within the SELECT (QRESYNC) response itself** (the common-case fast-path of the bullets above), via the fork's `SelectData.QResync` output extension (`SelectQResyncData`/`SelectQResyncChange`) which the fork's `handleSelect` writes after `OK [HIGHESTMODSEQ]`. The MDA's `Session.Select` builds it (`buildInlineQResyncSelectData`) from `list_messages(since_modseq=last_modseq)` (the expunge-log tombstones) + `fetch_message_metadata` (the full UID-ordered row set, for the changed messages' sequence numbers), gated on the common case `last_uid_validity == uid_validity AND last_modseq <= highestmodseq`. The follow-up `UID FETCH … (CHANGEDSINCE last_modseq VANISHED)` path remains the fallback a client uses when SELECT carried no `(QRESYNC …)` parameter, and the MDA also degrades to it (logging, not failing the SELECT) if the inline delta-build RPCs error. Two tier_3 e2e (tracked internally) drive this over a real authenticated connection: `test_mda_imap_qresync_expunge_emits_vanished` proves the live-expunge path (`ENABLE QRESYNC` → `UID EXPUNGE` a `\Deleted` message → `* VANISHED <uid>` (RFC 7162 §3.2.10), not the per-UID `* <seq> EXPUNGE` fallback), and `test_mda_imap_qresync_select_inline_vanished_earlier` proves the **inline `SELECT (QRESYNC …)` fast-path** (T3.2-b2 — reconnect at modseq `m0`, expunge-since-`m0` UID surfaces as inline `* VANISHED (EARLIER) <uid>` within the SELECT response). The `(CHANGEDSINCE n VANISHED)` fetch-modifier fallback is now e2e-covered too (T5.5): `test_mda_imap_qresync_changedsince_vanished_fetch` drives `UID FETCH 1:* (FLAGS) (CHANGEDSINCE m0 VANISHED)` over a real authenticated connection and asserts the since-`m0` tombstone surfaces as `* VANISHED (EARLIER) <uid>` — exercising `fetch.go`'s distinct `list_messages(since_modseq)` → `FetchWriter.WriteVanishedEarlier` path (separate from the inline-SELECT fast-path above).

### Restore divergence detection

At `SELECT` time, when the client supplies QRESYNC `(last_uid_validity, last_modseq)`, the nest compares `last_modseq` against the target mailbox's `bridge_imap_mailbox_state.highestmodseq`:

- `last_modseq <= highestmodseq` (the common case): standard QRESYNC fast-path applies — server emits `VANISHED (EARLIER) <uid_set>` from `bridge_imap_expunged` plus `FETCH (MODSEQ ...)` for deltas. As of **T3.2-b2** the MDA emits these *inline* within the SELECT (QRESYNC) response itself (via `SelectData.QResync`); the `UID FETCH … (CHANGEDSINCE last_modseq VANISHED)` round-trip (landed T3.2-b) remains the equivalent fallback for clients that SELECT without the `(QRESYNC …)` parameter.
- `last_modseq > highestmodseq` (the post-restore window): RFC 7162 §3.2.5.2 stale-modseq applies. The server returns `OK [HIGHESTMODSEQ <highestmodseq>]`, the client falls through to a full resync of that mailbox, and the nest writes one row into `bridge_restore_divergence` (`protocol = 'imap'`, `collection = <mailbox name>`, `client_modseq = last_modseq`, `server_modseq = highestmodseq`, `lost_event_count = last_modseq - highestmodseq`, `mua_id` from the prior IMAP ID command or `NULL`). The row is forensic — server-side state wins; locally-cached flag changes the MUA had but never reached the backup destination are silently discarded on the MUA's next FETCH.

The divergence row pairs with the most recent `restore_history` row for the actor; the Backups page surface reads both tables to render the divergence banner (`docs/goal/ui/backups.md` § Restore divergence).

Library status (T3.2-b — landed): the vendored go-imap fork's `Session.Select` now receives `(last_uid_validity, last_modseq)` from the `(QRESYNC ...)` SELECT-param parser, and the Go bridge forwards them as `SelectMailboxRequest.client_qresync: Option<QResyncHint>` (`bins/fauna-bridges/internal/mda/imap/select.go` → `wsrpc.SelectMailbox`). The (γ) divergence detection in `bridge_imap_handlers.rs::select_mailbox_handler` therefore fires for real now: a MUA whose `last_modseq` exceeds the mailbox's `highestmodseq` writes a `bridge_restore_divergence` row — no nest-side change was needed.

## IDLE (RFC 2177)

`IDLE` blocks the IMAP wire connection until either (a) an unsolicited mailbox-state change matters for the SELECTed mailbox, (b) the MUA sends `DONE`, or (c) the per-server idle-timeout fires (default 29 minutes, just under the RFC 2177 §3 recommendation of 30; configurable per mail-policy-config — `imap.idle_timeout_seconds`).

> **Implementation status (idle-timeout teardown).** Path (c) is wire-observable: the vendored go-imap fork's `handleIdle` sets the IDLE *connection read deadline* to the session's `IdleTimeout()` value, and on expiry ends the inactive IDLE with an untagged `* BYE` + close (RFC 2177 §3 server-initiated end), via the `errIdleServerTimeout` hand-back (FORK.md row 19). The value is baked at `NewSession` from the MDA `imap.Backend`'s current (atomic) idle timeout, so a `config_changed` hot-apply of `imap.idle_timeout_seconds` binds on the **next** IMAP connection without a bridge restart. A tier_3 e2e (`tests/e2e-unified/tests/test_mail_bridge_mda.py::test_mda_imap_idle_timeout_hot_reloads_without_restart`) lowers the timeout over the real WS-RPC admin path, awaits the push, and asserts a fresh IDLE is `* BYE`'d near the new value with the bridge PID unchanged. (Before the fix (tracked internally) Slice 1 the seam-level timer in `Session.Idle` returned on timeout but `handleIdle` stayed blocked on the client's `DONE`, so the knob disconnected nobody and a hard-coded 35-min read deadline was the real idle-disconnect — an honest bug the tier_3 proof surfaced.)

### Push wiring

When the MDA enters IDLE, it registers an interest in `WsPushEvent::BridgeMailboxState { actor_id, mailbox }` events on the nest WS-RPC channel (the MDA is the actor for its enrolled service-user keypair; nest fans out by **the served user's actor_id** carried in the registration, not the MDA's own actor_id — see `../architecture/transport.md` for the push primitive).

Nest emits `BridgeMailboxState` on every mailbox write that affects an actor's IMAP state (APPEND from inbound mail delivery, APPEND from a sibling MDA process for the same actor, STORE flags from a parallel MUA session, etc.). The MDA translates the push to the appropriate IMAP unsolicited responses:

| Nest push | IMAP wire response |
|---|---|
| `BridgeMailboxState::Append { uid, flags, modseq }` | `* EXISTS <new-count>` + `* <seq> FETCH (UID <uid> FLAGS (...) [MODSEQ (<n>)])` — `MODSEQ` included when the session has `ENABLE CONDSTORE`'d (T3.2-a, via the fork's `WriteMessageFlagsModSeq`). |
| `BridgeMailboxState::Flags { uid, flags, modseq }` | `* <seq> FETCH (UID <uid> FLAGS (...) [MODSEQ (<n>)])` — `MODSEQ` included when CONDSTORE-enabled, as above. |
| `BridgeMailboxState::Expunge { uid, modseq }` | `* VANISHED <uid>` when the session has `ENABLE QRESYNC`'d (T3.2-b, via the fork's `UpdateWriter.WriteVanished`); otherwise the per-UID `* <seq> EXPUNGE` fallback. |
| `BridgeMailboxState::Move { src_uid, dst_uid, modseq_src, modseq_dst, side }` | both a source-side disappearance and an EXISTS+FETCH for the dst (on the respective IDLE channels — each SELECTed mailbox is its own subscription); the source side is `* VANISHED <src_uid>` under QRESYNC, else `* <seq> EXPUNGE`. The nest names each subscription's end in the required `side` (`source` / `destination`) and the MDA takes it from there alone: IMAP UIDs are per-mailbox, so `dst_uid` routinely also names an unrelated message in the source, and no UID lookup can tell the ends apart. |

### Fallback poll

The MDA does **not** fall back to polling — push events are reliable in the canonical transport (per `../architecture/transport.md` § Push frames and reconnect semantics). If the WS connection drops mid-IDLE, the MDA closes the IMAP connection with `BAD Internal error` and the MUA reconnects + reissues SELECT + IDLE; no message of the missed window is required because reconnect-time SELECT carries fresh state.

## NOTIFY (RFC 5465)

**Target-state — NOT yet advertised** (the go-imap wire seam is upstream-blocked; § Upstream-blocked gaps and § Capabilities "Never advertised" are the current-state authority). Once the seam lands, the MDA advertises `NOTIFY` so a single connection can express interest in events on **multiple mailboxes simultaneously** without entering IDLE on each. The wire is RFC 5465 §5; the MDA-side implementation is a wrapper around the same push registration mechanism IDLE uses (one nest push subscription per `(actor_id, mailbox)` pair the client expressed interest in) — that notification-router infrastructure landed in I5 Phase F.2 and is ready.

The event subset targeted for v1: `MessageNew` (RFC 5465 §5.2 — surfaces APPEND on each registered mailbox without the MUA having to SELECT it first), `MessageExpunge`, `FlagChange`, `AnnotationChange` (no-op — annotations not implemented), and `MailboxName` / `SubscriptionChange` (LIST / SUBSCRIBE side-effects don't yet emit nest pushes; that gap is tracked alongside the LIST-extended work).

### Quota root model

Every mailbox belongs to **exactly one quota root** named after the actor: `user/<handle>`. Per-mailbox sub-quotas are not implemented in v1 — the quota root spans all of a user's mailboxes (INBOX + Archive + Drafts + Sent + Trash + Junk + user-created). `GETQUOTAROOT <mailbox>` returns the single root + its usage.

### Resources

- `STORAGE` — total bytes across all `bridge_imap_messages` rows the user owns, computed by summing each placement's record-block length (looked up by `segment_records.record_cid` through the CARv2 `MultihashIndexSorted` index in the segment's `.dat`) over the actor's non-tombstoned mail records (each COPY-duplicated placement counts, mirroring Dovecot's QUOTA accounting) — plus the actor's calendar and contact records, since the root is shared across mail, calendar and contacts (composition owned by `caldav-server.md` § QUOTA — shared with IMAP). Ciphertext bytes count (the user is paying for the bytes nest stores, not the plaintext-equivalent). The deployment default comes from the **effective** `ImapPolicy.storage_bytes_default` — the catalog default ⊕ the admin `put_imap_policy` override (`mail.imap.storage_bytes_default` in `mail-policy-config.md` § IMAP server policy), resolved by `ImapPolicyOverrides::effective()`; catalog baseline 1 GiB. The IMAP wire publishes usage and limit in KiB per RFC 9208 §3.2.
- `MESSAGE` — total row count across all of the user's non-tombstoned `bridge_imap_messages` placements. The deployment default comes from the effective `ImapPolicy.message_count_default` (catalog ⊕ admin override, `mail.imap.message_count_default`); catalog baseline 50_000.

Per-tier override of either default is **future scope (Phase F+)** — the `tiers` table referenced in v0 drafts was the `subscription_tiers` table for content-author monetization, which is unrelated to IMAP quota. Per-tier IMAP-quota lands together with the user-account-tier surface; until then every actor sees the effective deployment-wide defaults from `ImapPolicy` (catalog ⊕ the admin `put_imap_policy` override).

### Composition with submission quota

The IMAP **per-mailbox storage quota** (RFC 9208) and the SMTP **per-actor submission quota** (`smtp-server.md` § Architectural rules — 1000 recipients/day + 100 recipients/message per actor; **no** per-actor messages/hour cap exists, corrected 2026-07-19) are **independent dimensions**:

- Per-mailbox quota bounds **what nest holds for you** (the steady-state size of your mail). Hitting it stops APPEND, EXPUNGE-required-before-more, and inbound mail delivery (the MTA bridge gets a `552 5.2.2 Mailbox full` translated from a `fauna.bridges.ingest_inbound_mail` over-quota response).
- Per-actor submission quota bounds **how fast you can send**. Hitting it stops outbound submission (`451 4.7.0 Per-account submission quota exceeded`) but does not affect IMAP read or write.

They never substitute for each other (sending 1,000 messages doesn't reduce your stored-mail quota; receiving 1,000 large attachments doesn't reduce your hourly submission cap).

Admin-visible: both quotas surface on the user's `mail-settings` page (the Tier-3 per-account UX home per `mail-policy-config.md` § Tier 3 — per-account + § Policy catalog banner; there is no `account-detail` page); over-quota events on either dimension are surfaced to the user as a UI notification + an inbox banner.

### Quota enforcement points

- APPEND (RFC 9208 §6.1) — pre-check on the nest RPC; over-quota returns `NO [OVERQUOTA] Mailbox quota exceeded`.
- COPY / MOVE (RFC 9208 §6.2) — pre-check on the destination mailbox; over-quota same code.
- Inbound mail delivery (MTA → MDA path, not an IMAP wire command but a peer write) — the MTA `fauna.bridges.ingest_inbound_mail` RPC over-quotas with a typed error the MTA maps to `552 5.2.2 Mailbox full` (permanent — sender bounces; the recipient sees no inbound but the bouncer surfaces the reason — there's no rule against bouncing a "your mailbox is full" notice, that's the normal RFC 3464 flow).
- EXPUNGE / DELETE — reduce usage; never blocked by quota.

## Architectural rules

- **One MDA-role process per nest deployment in the target shape.** Horizontal scaling is by enrolling additional MDA service-user keypairs; the AUTH ↔ unwrap mechanism scales linearly with users since unwrap is per-session.
- **All mailbox state is nest-side.** The MDA holds no per-user persistent state on disk. SQLite writes happen only via RPC; `bridge_imap_messages` / `bridge_imap_mailbox_state` / `bridge_imap_expunged` are the only IMAP state surfaces.
- **Every write RPC is one SQLite transaction at the nest boundary.** MOVE is atomic. STORE UNCHANGEDSINCE checks modseq inside the transaction. APPEND with multiple literals (RFC 9051 §6.3.12 — LITERAL+ multi-append) is one transaction per APPEND, not per multi-append batch.
- **The MDA is not the only writer of `\Seen`.** A first-party Fauna app sets it through a `User`-class call that can add `\Seen` to the caller's own `INBOX` rows and nothing else, over the same flag-write internals as `fauna.bridges.store_flags` — so a MUA sees an app's read like any other flag change (owner: [`mail-app-surface.md`](mail-app-surface.md) § Read state; built nest-side). `fauna.bridges.store_flags` itself stays `BridgeMda`-only.
- **Every state-changing RPC appends a placement event to `__mail-placement/<actor>/` paired with the SQLite transaction.** Implementation shape: the handler runs `state.db.apply_*` (which opens, mutates, and commits its own SQLite transaction internally), then calls `state.mail_placement.append_event(...)` which encodes the event, appends to the open segment, and atomically renames the placement manifest. Durability boundary is the placement-manifest fsync, not a unified WAL fsync — the segment record is durable once the manifest naming the segment renames into place. On crash between the SQLite commit and the manifest fsync, the segment can lag SQLite by at most one RPC's worth of state. **Plan 2 T9 lands the detection + WARN log** at SELECT (`bins/fauna-nest/src/bridge_imap_handlers.rs::select_mailbox_handler`); the CalDAV analog is T10 at sync-collection time (`bridge_caldav_handlers.rs::sync_calendar_since_handler`). **The WARN log is the terminal design for this gap, not a placeholder for a future synthesis track.** The originally-envisioned "synthesize-and-append" repair was **subsumed** at Plan 2 close-out (design ratified 2026-05-14, tracked internally, § Plan 2 status — T10 disposition; the IMAP T9 twin follows identically, same shared substrate and reasoning), because synthesis is the wrong frame on two counts. (1) In the disaster-recovery case there is nothing to synthesize *from* — the un-journaled SQLite rows died with the source nest; the restore has only the snapshot's placement manifest. (2) In the live commit-then-append crash window the ≤1-RPC gap is handled by the **(γ) restore-divergence detection + full-resync fallback**: a QRESYNC client whose sync-token falls in the gap observes `last_modseq > highestmodseq`, falls through to full resync per RFC 7162 §3.2.5.2 stale-modseq (over-conservative but always-safe), and the loss is forensically recorded in `bridge_restore_divergence`. The "extend the placement journal to carry pre-event state" framing is moot regardless: the journal record type **already** carries `StoreFlags { before_flags, after_flags }` — populated inside the same conn-mutex as the UPDATE (`bridge_imap_handlers.rs::store_flags_handler` ≈:798, `db/bridge_imap.rs::apply_store_flags`'s `StoreFlagsDbOutcome` doc ≈:362) — and structurally-distinct `Create` / `Rename` variants (`libs/fauna-mail/src/segments/placement.rs`); it is only the **SQLite mirror** that lacks `before_flags` and a Create/Rename discriminator, and synthesis *from that mirror* is precisely what was subsumed. The placement journal still exists so disaster-recovery restore from a backup destination reconstitutes `bridge_imap_*` tables with QRESYNC continuity per the same spec.
- **CONDSTORE modseq is monotonic per-mailbox, never reset except on CREATE.** RENAME preserves it. UIDVALIDITY follows the same rule, with the addition that CREATE assigns a unique-across-lifetime value (`<unix-millis> << 16 | <random16>`).
- **Push events are reliable, no fallback poll.** A dropped WS connection closes the IDLE; the MUA reconnects + re-SELECTs. No "missed event" recovery code exists or is needed.
- **AEAD-success = AUTH-success.** The MDA never holds a server-side credential database; nest holds wrapped MLS-key blobs, and the MDA AUTH code path only ever reads the wrapped form. Per § Authentication candidate (b) ratification.
- **AUTH outcomes are reported every time.** `report_auth_event(success)` and `report_auth_event(fail)` both fire; rate-limiter signals come from the audit log, not from in-memory MDA state.
- **`AllowInsecureAuth = false` on 993 and 143.** PLAIN advertised only over TLS. Cleartext AUTH on 143 pre-STARTTLS rejects.
- **Per-mailbox quota and per-actor submission quota are independent.** Neither substitutes for the other; both have their own enforcement points (APPEND/COPY/MOVE/inbound-delivery for the IMAP side, MAIL FROM-time for the submission side).
- **Tombstone retention defaults to 30 days, minimum 7 (§ Tombstone retention).** `expunge_handler` piggybacks `prune_tombstones` on every EXPUNGE, gated on the effective `imap.tombstone_retention_days`, mirroring the CalDAV/CardDAV siblings' S6.8d2 `prune_tombstones` wiring; QRESYNC clients reconnecting past the retention window fall back to `OK [HIGHESTMODSEQ]` rather than a (possibly incomplete) `VANISHED (EARLIER)` list.
- **NOTIFY events are per-IMAP-session.** Persistent NOTIFY across sessions is out of scope. The MUA re-registers on reconnect.
- **Quota root is per-actor (`user/<handle>`).** Per-mailbox sub-quotas are not implemented in v1. Per-actor defaults come from `ImapPolicy.storage_bytes_default` / `ImapPolicy.message_count_default`; per-tier override is Phase F+ (the prior `tiers.storage_bytes` reference pointed at a table that turned out to be the unrelated `subscription_tiers` for content-author monetization — proper per-tier override lands with the user-account-tier surface).
- **MUA-AUTH against the MDA never grants write access beyond the AUTH'd user's mailboxes.** The actor_id from AUTH is the only one any RPC carries; nest enforces.
- **APPEND strips the reserved `X-Fauna-*` delivery stamps from the literal before it parses or seals it** — the namespace is written only by the door that files a copy, and the SELECT-time scorer trusts the stamp whichever door that was; the rule, the door list and the `X-Fauna-Forwarded-By` carve-out are `smtp-server.md` § Architectural rules → *The `X-Fauna-*` namespace*. The dedup key is still computed over the literal as filed (§ Dedup in `mailbox-migration.md`).
- **MDA seals APPEND uploads to the actor's own MLS + index pubkeys before the nest RPC** (the at-rest invariant; spec ratification § MDA encrypts user mail to the actor's own MLS pubkey on APPEND, design ratified 2026-05-07, tracked internally). The bridge caches both pubkeys at AUTH time via `fauna.bridges.fetch_recipient_mls_pubkey` and `fauna.bridges.fetch_recipient_index_key`. The MLS pubkey MUST be provisioned for any actor that can AUTH — the inbound MTA path requires it for sealing recipient mail. The index pubkey is allowed to be `None` until Phase E ships production provisioning; until then the MDA falls back to the MLS pubkey for the hint envelope (mirrors the MTA inbound path's `ingestForRecipient` fallback exactly so the recipient's MDA opens the same shape regardless of who put the message there). Wire format stays stable when Phase E adds real provisioning — the recipient's MDA opens both envelopes the same way.

## Don't do these

- Don't add server-side mailbox state in the MDA process. SQLite writes flow through nest RPCs; the MDA is a stateless protocol terminator.
- Don't synthesize `VANISHED (EARLIER)` responses for tombstones older than the retention window. Lying about deletion history is worse than a fallback resync.
- Don't poll for mailbox changes when IDLE drops. Close the IMAP connection and let the MUA reconnect — the WS-RPC push contract is reliable.
- Don't reintroduce the legacy bearer-token AUTH flow described in `smtp-server.md` § MUA-facing view (Thunderbird, Apple Mail). It's transitional; the cutover replaces it with OAUTHBEARER (preferred) or PLAIN over TLS (fallback) — both flow through the same AEAD-unwrap-as-AUTH path per § Authentication.
- Don't reintroduce SCRAM-SHA-256 advertisement on the MDA (legacy plaintext-mode candidate (a)). The candidate (b) ratification removed the nest-side SCRAM verifier; advertising SCRAM with no verifier is worse than not advertising it.
- Don't branch the MDA AUTH code — or the post-AUTH content-fetch code — on the `storage_mode` field. Both paths are uniform: AUTH is wrapped-blob fetch, KDF, AEAD-unwrap; content fetch is per-record discrimination (`OpenStoredRecord`) on the bytes' own strict shape — see § Content path. `storage_mode` survives on `fetch_config`'s reply only as a compat constant for older bridges/clients (`../architecture/nest/storage-modes.md` § The transition contract).
- Don't add a per-reply `is_sealed` flag (or any other per-reply discriminator) to the I2b reply types. Discrimination is on the bytes' own strict shape (`OpenStoredRecord`, § Content path) — a legacy pre-Phase-3 raw record vs. a sealed record; per-reply branching is unnecessary, and the shipped Phase C/D types use bare `encrypted_*` bytes uniformly, so adding a flag now would require revising ~6 reply types and ~40 round-trip tests for cosmetic uniformity gain only. See § Content path.
- Don't write IMAP state to the MDA's local filesystem. The MDA's `--data-dir` is for logs + the keypair file only; mailbox state lives in nest's SQLite.
- Don't split MOVE into a separate COPY + EXPUNGE on the MDA side. The atomicity rule is at the nest transaction boundary; MOVE is one RPC.
- Don't advertise IMAP extensions that nest can't back. Every advertised capability has a corresponding RPC + handler; advertising `LIST-EXTENDED` without a working `list_mailboxes` extended-flags surface is a worse user experience than not advertising it.
- Don't share quota across users on the same nest. Per-actor quota roots are independent; one user filling their quota doesn't affect a sibling user.
- Don't allow PLAIN AUTH to skip the STARTTLS step on 143. RFC 9051 §11.1 is unambiguous; non-conforming MUAs get an error, not a security-degraded auth path.
- Don't conflate per-mailbox storage quota with per-actor submission quota in any UI surface or error message. They're different limits with different remediation paths.

## Upstream-blocked gaps

The mail-bridge MDA process uses `emersion/go-imap` v2 (`v2.0.0-beta.8`) — the same library the now-deleted legacy terminator used (retired; tracked internally), now with the minimal additive vendored fork at `bins/fauna-bridges/third_party/go-imap`. Server-side gaps:

> **Decision record (advisory, refutable):** how to close each gap below — land an upstream PR, vendor a minimal additive fork, or accept the gap — is decided per-item in the internal design memo (ratified 2026-05-23; tracked internally). The dovecot-parity *target* (these extensions working) is owned by this doc; that memo owns only the *mechanism*.

- **`SORT` (RFC 5256)** — not implemented and **not advertised** (per § Capabilities "Never advertised"; it is absent from `capabilityList()`); no fork seam exists yet. Upstream PRs #732 / #695 pending.
- **`THREAD` (RFC 5256)** — not advertised; same upstream blocker as SORT.
- **`CONDSTORE` (RFC 7162)** — **DONE (T3.2-a, via the vendored go-imap fork).** The wire seams that were blocked on upstream — `FetchResponseWriter.WriteModSeq` (emit `MODSEQ (<n>)`), the `MODSEQ` FETCH data item + `(CHANGEDSINCE <n>)` modifier parsers, the `(UNCHANGEDSINCE <n>)` STORE-modifier parser, `OK [HIGHESTMODSEQ <n>]` on SELECT, and ENABLE routing of `CONDSTORE` into `Conn.enabled` — now ship in `bins/fauna-bridges/third_party/go-imap` (see `FORK.md`; upstream PR #690 tracks MODSEQ). `CONDSTORE` is advertised post-auth. The MDA emits `MODSEQ` on FETCH/STORE responses once the client `ENABLE CONDSTORE`s (or names the `MODSEQ`/`CHANGEDSINCE`/`UNCHANGEDSINCE` items), and the `OK [MODIFIED <uid-set>]` precondition path (RFC 7162 §3.1.3) now activates against a real wire parser — the stale uid-set rides *inside* the response code (`internal/mda/imap/store.go` builds `Code: "MODIFIED " + <set>`, rendered verbatim by `writeStatusResp`), so a CONDSTORE-aware MUA can parse which messages failed and refetch+retry them. Two tier_3 e2e (tracked internally) drive CONDSTORE over a real authenticated connection: `test_mda_imap_condstore_fetch_returns_modseq` (`ENABLE CONDSTORE` → SELECT `[HIGHESTMODSEQ]` → `UID FETCH (FLAGS MODSEQ)` carries `MODSEQ (<n>)` from the real nest counter — the fork wire test only pins the same shape against a mock session returning fixed values), and `test_mda_imap_condstore_unchangedsince_returns_modified` (a STORE `(UNCHANGEDSINCE <stale-modseq>)` returns `[MODIFIED <uid>]` with the flag unapplied). The latter first surfaced a real interop bug — the uid-set was emitted only in the human-readable text, leaving `[MODIFIED]` empty so the client couldn't recover the set — fixed in the same change.
- **`NOTIFY` (RFC 5465) wire surface** — listed in `capabilityList()` for future-proofing but the library drops it at render-time and has no command parser. `emersion/go-imap v2.0.0-beta.8`'s `imapserver/` has no NOTIFY parser and no `Session.Notify` interface hook (grep confirms zero `Notify` matches in `imapserver/`). The MDA-side notification-router infrastructure landed in I5 Phase F.2 and is ready: when upstream adds the hook, one method on `Session` connects the existing router to the wire. Until then, MUAs see neither the advertisement nor a NOTIFY response. Per the rule at the bottom of this section, the wire never sees an advertised capability the server can't honor; the dead CapSet entry is harmless and reduces the upstream-landing diff to one line.
- **MODSEQ on unsolicited FETCH FLAGS (IDLE translation)** — **DONE (T3.2-a, via the fork).** The fork adds `imapserver/UpdateWriter.WriteMessageFlagsModSeq(seq, uid, flags, modSeq)`; the IDLE append/flags branches use it when CONDSTORE is enabled for the session, so the unsolicited `* <seq> FETCH (UID <uid> FLAGS (...) MODSEQ (<n>))` line carries the modseq from `MailboxStateEvent::{Append,Flags}.modseq` (RFC 7162 §3.1.7). When CONDSTORE is not enabled the plain FLAGS form ships. A tier_3 e2e (T5.7) proves this over the wire: `test_mda_imap_idle_fetch_carries_modseq_under_condstore` `ENABLE CONDSTORE`s on an idling session, has a second session APPEND, and asserts the idler's unsolicited `* <seq> FETCH` carries `MODSEQ (<n>)` (the real nest counter, n≥1) alongside `* EXISTS` — the plain IDLE test deliberately runs without CONDSTORE and skips MODSEQ. (NOTIFY-translated push remains gated on the NOTIFY entry below.)
- **`QRESYNC` (RFC 7162) server-emit** — **DONE (T3.2-b + T3.2-b2, via the fork).** The blockers are all closed: (a) `imapserver/select.go` now parses `(QRESYNC (uidvalidity modseq [known-uids [seq-match-data]]))` (and `(CONDSTORE)`) SELECT-params into `imap.SelectOptions.QResync`, which the bridge forwards as `SelectMailboxRequest.client_qresync` — activating the (γ) restore-divergence detection (§ Restore divergence detection); (b) the fork adds `Conn.writeVanished` + `ExpungeWriter.WriteVanished` + `UpdateWriter.WriteVanished` + `FetchWriter.WriteVanishedEarlier`, so once the client `ENABLE QRESYNC`s the MDA emits `* VANISHED <uid_set>` for the EXPUNGE command and the IDLE `BridgeMailboxState::Expunge`/`Move`-source push, and `* VANISHED (EARLIER) <uid_set>` for a `UID FETCH … (CHANGEDSINCE n VANISHED)` (RFC 7162 §3.2.5.1); (c) **T3.2-b2** adds the *inline* SELECT (QRESYNC) fast-path — `* VANISHED (EARLIER)` + changed-message `FETCH (UID FLAGS MODSEQ)` responses emitted **within the SELECT response itself** (RFC 7162 §3.2.5 common case) via the fork's `SelectData.QResync` output extension (`SelectQResyncData`/`SelectQResyncChange`), which the fork's `handleSelect` writes after `OK [HIGHESTMODSEQ]`. The MDA's `Session.Select` builds the inline set (`buildInlineQResyncSelectData`) gated on `last_uid_validity == uid_validity AND last_modseq <= highestmodseq`; the stale-UIDVALIDITY and restore-divergence (`last_modseq > highestmodseq`) cases deliberately omit it and let the client full-resync. `QRESYNC` is advertised post-auth (it implies CONDSTORE via `imap.CapSet.Has`). When QRESYNC is *not* enabled the per-UID `* <seq> EXPUNGE` fallback still applies, and the `UID FETCH … (CHANGEDSINCE n VANISHED)` round-trip remains the equivalent fallback for SELECTs that carry no `(QRESYNC …)` parameter (or if the inline delta-build RPCs error — the SELECT degrades to it rather than failing).
- **`QUOTA` server-side (RFC 9208)** — **DONE (T3.2-c, via the vendored go-imap fork).** The data side was already ready (`fauna.bridges.get_quota` → `get_quota_handler` → `imap_quota_usage`, aggregating record block length via `db.list_bridge_imap_quota_size_refs` + the CARv2 index by `record_cid` + placement count; ceilings from `ImapPolicy::default()`) and the MDA byte→KiB translation (`internal/mda/imap/quota.go`); the missing piece was the upstream server-framework wire seam, now in `bins/fauna-bridges/third_party/go-imap` (`FORK.md` row 17, no upstream PR yet): the `GETQUOTA` / `GETQUOTAROOT` command parsers + dispatch, the `SessionQuota` interface (`GetQuota` / `GetQuotaRoot`), and the `* QUOTA <root> (STORAGE used limit MESSAGE used limit)` / `* QUOTAROOT <mailbox> <root>` response writers. `QUOTA` is advertised post-auth together with its RFC 9208 §6 resource-type capabilities `QUOTA=RES-STORAGE QUOTA=RES-MESSAGE`. The MDA's `Session` implements `SessionQuota`, so GETQUOTA/GETQUOTAROOT against the `user/<handle>` quota root return live usage. (`SETQUOTA` is intentionally not implemented — Fauna quota ceilings are nest configuration, not an IMAP-settable knob; per-actor / per-tier override of the defaults remains Phase F+.)
- **`ManageSieve` (RFC 5804)** — no implementation. Basic filter-rules UI exists in nest (per `email-filters.md` § Email filter rules); they are not ManageSieve-compatible. Implementing ManageSieve is a future track (would expose the filter rules to standard MUAs that support it — Thunderbird's `manage sieve` add-on, etc.).

For each upstream-blocked extension, the rule is: advertise the capability only when the wire response can be generated correctly. Until then, the capability is **not** advertised — silent non-implementation is better than half-implemented behavior that breaks MUA assumptions.
