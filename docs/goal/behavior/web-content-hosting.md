## Goal

A nest user publishes a personal website or blog from their own nest with zero external hosting. Content comes from two sources: a folder of static files synced via fauna-sync (a folder whose **website toggle** is on — `folders.website_enabled`, flipped on the folder's row; the folders re-model phase 4 retired the former `mode = web` declaration, and the ratified no-migration ruling maps every legacy web-mode row to toggle-off), and regular Fauna posts flagged for web display. `.html.hbs` Handlebars templates in the synced folder are pre-rendered to static HTML on write (referencing the user's web-published posts), so all serving is static file delivery — no per-request template execution, no server-side user code.

Three addressing surfaces, in priority order for this track:

1. **Admin apex** (`https://<domain>/`, e.g. `https://example.com/`) — the deployment admin designates one actor whose `web` content serves the apex/main path, exactly as the admin designates a per-domain catch-all *mail* actor. This is the "one admin-sanctioned way of getting web content onto the main path." Served on the nest's own apex cert — no new DNS, no new cert.
2. **User subdomain** (`<handle>.<domain>`, e.g. `alice.example.com`) — opt-in per user; the user's own `web` content serves their subdomain. Reachable out of the box given one wildcard `*.<domain>` A record (published by the admin's client like every other record, `dns-management.md`); TLS is a per-subdomain HTTP-01 cert via the same `MultiDomainCertResolver` lifecycle as custom domains.
3. **Custom domain** (`alice.com`) — the user registers and DNS-verifies it; the nest obtains and renews its TLS cert automatically. (Built; app authoring UI deferred.)

A **separate origin per untrusted site is the security spine** of this model — apex and each subdomain/custom-domain are distinct origins, so one user's HTML can never read another surface's browser storage. Path-based `/<user>` on a shared origin is deferred precisely because it breaks that property (§ Same-origin security model).

## Content model

Three storage shapes, all per-actor, all referencing bytes in the existing content-addressed blob store (so dedup works across users and sizes count toward the user's nest quota):

- **Web-published posts** — a Fauna post flagged via a `content_links` row with `link_type = 'web_published'` and the URL slug in `status`. A uniqueness index ensures one slug per `(actor, web_published)`. No content-table schema change. Toggling publish/unpublish/edit triggers the render pipeline.
- **Static site files** — the `web_files` table (`actor_id, path, blob_hash, content_type, updated_at`). Files arriving in a website-enabled folder are routed here **in addition to** the normal head row (`web_files_projection::route_web_file_change`, keyed on `folder.website_enabled` since the folders re-model phase 4 — never instead of the head row, which is what pins the site's blobs against GC; `web_files` is not a reachability source). Files with server-side-execution extensions (`.php`, `.py`, `.rb`, `.cgi`, `.asp`, `.aspx`, `.jsp`, `.pl`, `.sh`) are rejected at sync time. A `.html.hbs` template or `_site.json` change additionally fires the render pipeline (below); static assets are served straight from `web_files`. A website-published folder **appears in Media like any other folder** (open call #4, executed with phase 4 — `../ui/media.md` § State & data shape owns the view claim); web-serving management lives in the web-settings UI. **Non-paywalled serving requires the folder's audience to be `public`** (`folders.md` § Target re-model): a public folder's producers — the sync engine, the WebDAV mount and the Media page (`../ui/media.md` § Encryption at rest → *One at-rest shape*, ruled and built 2026-10-06) — upload plaintext chunks behind a manifest, the ONE shape the serve walk below serves (it grows no blob-primary arm); a sealed, un-paywalled website serves nothing (fail-closed 404) until the owner declassifies or sets a paywall tier. The audience is read from the folder's **current row at the serve door on every request** (`web_content/serve.rs`'s plaintext arm, since 2026-08-19): a flip back to `private`/`shared` revokes the anonymous serve on the very next request, matching `folder_public.rs`'s semantics on the authenticated door, and never waits for the client-driven corpus re-seal (which is what stops the bytes *resting* plaintext, not what stops them serving). (The legacy `mode == "web"` spelling retired 2026-09-28 and the `mode` column with it — schema 94.) Both gates — the website toggle and this plaintext class — live in **one core**, `web_content/serve.rs::gate_web_file_folder`, because there are **three** consumers that turn a `web_files` row into bytes: the main serve path, the custom-`404.html` arm (which resolves its row by path alone), and the **render pipeline's input reads** — the `.html.hbs` listing, `_site.json`, and each template load. All three ask the core (the `404.html` arm since 2026-08-19, the render inputs since 2026-08-20), so a disabled or re-classified folder feeds neither a serve nor any later render. A sealed row is additionally never a render input (the v1 bound `monetization.md` § Pillar 2 ratifies), enforced at the listing, not only at the sync trigger. Any future producer of bytes from a `web_files` row asks the same core. **`web_files` is a *projection* of the folder's live sync heads, and a serving transition (re)builds it — the enable-time backfill (ratified 2026-08-20).** Sync-time routing maintains the projection incrementally only while the toggle is on at arrival, so without a transition-time reconcile, enabling the toggle on an **already-synced** folder serves nothing indefinitely (files re-record only on edits — a finished static site never does), and a delete recorded while the toggle was off leaves a stale row that would resurrect at re-enable. Both would break the phase-4 no-migration ruling's own premise (legacy `mode=web` rows map to toggle-off, *owner re-enables by hand*) and the followed-folder "turn it on" affordance. So `fauna.folders.update` reconciles the folder's projection on any serving transition that lands in an enabled state: upsert every live **plaintext-resting** head (the same latest-per-path fold snapshot-create uses; the plaintext class is exactly the class that can be a URL at all) through the same server-side-extension refusal as sync-time routing, and drop the folder's rows whose path has no live head — then the transition re-render runs, so re-rendered templates see the backfilled rows. Cost is O(folder heads) under the owner's own authenticated update, the snapshot-create class. **Sealed-resting heads are deliberately outside the backfill, and their half is client-driven:** the nest holds no names for them (S9), so a *sealed* folder's back-catalogue reaches `web_files` only via client-driven re-records — the audience corpus converge (`converge_corpus_to_audience`) covers the sealed→`public` journey, and the sealed toggle-on-after-sync journey is its twin, **`SyncEngine::converge_corpus_to_website`** (built 2026-08-20). Same shape, same reasons: the folder's projected `website_enabled` is itself the cross-device signal (it rides the same `fauna.folders.list` tick as the sync mode and the audience, so a toggle-ON reaches a *running* seat rather than waiting for a restart), the steady-state gate is one device-local `meta` row (`corpus_website`, absent reading as `off`, so a folder serving no website pays one read per tick), and the walk re-records every live head as a **no-novel-content reissue** (`proven_reissue` ⇒ `is_resolution`, so receivers whose frontier already passed those bytes skip them instead of merging an edit storm) — which routes each arrival into `web_files` with the sealed `content_key_version` intact. It fires only for a **sealed** folder: a `public` one rests plaintext, which is exactly the class the nest-side backfill above folds. A keyless engine leaves the marker unmoved rather than record a walk it could not perform. **The walk is additive, so it carries one more sentence: *and nothing else*.** Re-records say what exists and never what stopped existing, so a sealed path deleted while the toggle was OFF used to keep a row that kept SERVING after re-enable — a delete that does not take effect on a published surface, and the nest cannot fix it from its side (a sealed head rests no plaintext path, which is exactly why the nest-side reconcile skips sealed rows). So at the end of a fully successful walk the client declares the folder's **complete** live path set over `fauna.web.files.prune_sealed`, and the nest drops that folder's **sealed** rows outside it. Three bounds, each load-bearing: the kind touches only the **sealed** class (the plaintext class has its own nest-side reconcile built from real evidence, and a client's view of it is not authoritative), only **that folder's** rows, and only the **caller's own** — the folder resolves through the owner-scoped door. The declaration is sent **after** the walk and never before, so a partial pass (which already fails loudly rather than reporting a short result) can never declare a truncated set; an older client never sends the kind at all, so sealed rows stay untouched, which is the additive-everywhere reading — absence of a declaration is never read as *delete everything*. A corpus whose path list would not fit one RPC frame skips the declaration and keeps the stale-row residual, rather than truncating it. **Both ends refuse an *empty* `paths` on that declaration**: an empty set is indistinguishable from *nothing is live* and *this device has not caught up*, so honouring it at face value would read a seat's own incompleteness as a site-wide deletion. `SyncEngine::declare_live_web_corpus` never sends one; `fauna.web.files.prune_sealed` refuses one if sent — duplicated nest-side because doing so forbids nothing any shipped client can do (the client-side refusal is the only caller), and each end must survive being reached directly, not only through the other. **The residual that buys is bounded, and the fix does not change it:** an owner who deletes *every* page of a sealed site while the toggle is off keeps those rows until one page is added back, because the declaration that would clear them is exactly the one neither end will send. That is the deliberate trade — a stale row on a site with no live pages serves nothing a live page would have shadowed, whereas honouring the empty set would take a whole site down on a seat that had merely not caught up.
- **Rendered output** — the `web_rendered` table (same shape). Holds the pre-rendered Handlebars output, separable from source so it can be regenerated wholesale. A `web_rendered` row carries **no folder provenance on purpose** (a folder-less default site is legitimate — § Routing), so the serve arm for rendered rows is **not** folder-gated; what keeps a switched-off site's rendered pages from serving is the transition-fired re-render below, whose folder-gated inputs drop them.

## Routing, render, serving

- **Host-header routing:** the apex fallback handler (`web_content_or_info`) inspects the `Host` header and resolves it to an actor via an in-memory `HostResolver`, populated from three sources:
  1. **Apex** — the nest's own node domain (`<domain>`, and the bare/absent/unknown host) resolves to the **admin-designated apex actor** if one is set; otherwise it serves the built-in nest info page (unchanged fallback).
  2. **Subdomain** — `<handle>.<domain>` strips the `.<domain>` suffix and looks it up in the resolver's own `<handle> → actor` map (an in-memory table, not a per-request `db.resolve_handle` lookup): boot-seeded and kept live thereafter — on `fauna.web.set_subdomain_enabled` and by the boot walk itself — via `db.get_handle(actor)` over every opted-in actor, so only users who have **opted into** subdomain hosting *and* hold a non-reserved handle appear in the map.
  3. **Custom domain** — an exact match in `web_domains` (`active` rows): boot-seeded and kept live thereafter by the **domain lifecycle task**, which re-projects the whole `active` set onto the resolver's custom-domain map every pass (§ Registration and DNS verification step 5), plus an immediate drop on `fauna.web.domain.delete`. Routing therefore follows the table with no nest restart, in both directions.
  Reserved hosts (`mail.<domain>`, `mta-sts.<domain>`, `app.<domain>`, `_acme-challenge.*`) are never treated as web-content sites. The API router (`/api/v1/*`) and the local SPA mount (`/app`) sit **above** this fallback and are never shadowed by web content.
- **Path resolution order** (within a resolved site): user files (exact) → rendered files (exact) → directory index (`{path}/index.html`, user then rendered) → post pages (`/post/{slug}`) → 404 (user `404.html`, then rendered, then built-in). User files always shadow rendered files at the same path.
- **Render pipeline** runs on a `.html.hbs` or `_site.json` sync change, on a post's `web_published` flag change (`publish.set`/`publish.unset`), on a still-published post's own deletion (`fauna.posts.delete`; the delete removes its `web_published` link the same way `unpublish` does, so the trigger mirrors that one — `feed.md` § Post deletion → *Propagation*), on an account-deletion or eviction's post-retraction pass retracting at least one still-published post (`pending_actions::retract_actor_posts`, itself a dedicated trigger — rendered **once for the whole pass**, not once per retracted post, since the purge sweep that follows discards every render anyway; `account-data-plane.md` § Nest-side requirements item 1), on a web-serve grant mutation (the holder plane), and — since 2026-08-20 — on a folder's **serving transitions** (there is no separate "post edit" trigger — Fauna posts are immutable, so the only per-post events are publish/unpublish/delete, all three already covered by the flag- and delete-change triggers): the website toggle changing, the audience entering or leaving `public` (both via `fauna.folders.update`), and a website-capable folder's deletion. The transition triggers are what make the toggle actually stop the *rendered* half of a site: the re-render's folder-gated inputs (§ Static site files) drop the no-longer-serving folder's templates, and the render's whole-site replacement (*A reader sees a whole site or none*, below) drops its stale pages. A legal takedown or its overturn on a published post re-renders too, and a post a moderation flag withholds is never rendered — both owned by [`moderation.md`](moderation.md) § Legal takedown → *Posts*. So does any change of the region content policy in force for the declared situs, which every post's render folds — owned by [`region-blocking.md`](region-blocking.md) § The nest-as-publisher leg. It builds a template context (site metadata from `_site.json` or the user's profile; the `web_published` posts no moderation flag withholds, sorted by date), renders each `.html.hbs` (stripping `.hbs`), renders `_post.html.hbs` once per post to `post/{slug}.html`, writes results to `web_rendered`, and auto-generates `feed.xml`. **Safety limits (user templates are attacker-controlled — § Same-origin security model):** at most **1000 published posts** feed one render (the bounded context / top-level-loop cap), at most **100 `.html.hbs` templates** per actor, **5 s wall-clock per template**, enforced inside the render itself — Handlebars keeps no iteration counter, so the nest plants a deadline check at the head of every block body, and any loop (a nested `{{#each}}` that prints nothing included) stops within one pass over one body of the deadline; the render also runs under `spawn_blocking` + a timeout so it can neither pin a tokio worker nor block the runtime, but that timeout alone only abandons the blocking thread, which cannot be cancelled — a **4 MiB output cap per template render** (a `render_to_write` byte cap that aborts output amplification near-instantly; it bounds storage, not iteration), and a **1 MiB cap on a template's source** (bounding its parse and the work between two deadline checks). **Nesting is bounded too (2026-09-29), because a stack overflow is not an overrun the render can skip — it aborts the whole nest, and since the edit that synced the template also owes a render (*A revoke is durable*, below), the boot drain re-runs it into the same abort:** every render parses and runs on a thread of its own with a fixed **16 MiB stack**, and fails once it has used **8 MiB** of it — the same per-body check as the deadline, so a partial that renders itself (directly, mutually, by a computed name, or the page calling its own template) is stopped at a depth, not at the clock; and before parsing, since the parser recurses once per nesting level and cannot be checked from inside, a template is refused with more than **1024 block tags** (`{{#…}}`, `{{^…}}`, `{{else…}}`, raw blocks — counted wherever they appear, so no quoting hides one) or more than **128 `(` / `[` / `{` in one `{{…}}` expression** (a lexical count that errs only toward counting more). All are Rust constants. A template that times out / overruns / nests too deep is skipped, not fatal — the rest of the site still renders. If a user has posts but no templates, built-in minimal defaults render.
- **A revoke is durable (ratified 2026-09-19).** The pages are static, so removing content from a site is only complete once a render has dropped it — and a render runs *after* the state change that calls for it. What keeps the two from coming apart is the **owed-render marker**: one `web_render_owed` row per actor, written **in the same transaction as the state change** by every *revoking door*, discharged by the render that answers it, and **drained at boot** (`WebContentService::drain_owed_renders`, awaited before the nest serves) — the single atomic decision point plus boot reconcile of [`../architecture/nest/common.md`](../architecture/nest/common.md) § Client-state recoverability. A nest that stops between a revoking door's commit and its render therefore restarts owing that render, and pays it before it serves. **What makes a door revoking is what its state change CAN do, not whose act it is or what it meant:** a door whose commit can take content off the rendered site marks. Those are a still-published post's deletion (every caller of the delete core, the account-deletion retraction pass included — the delete's own transaction decides off the post's `web_published` link, the one its cascade removes, never by a read before it); a legal takedown (same link, same transaction as the withhold flag); `publish.unset` when it removes a link; a folder's serving transitions — **decided off the render-input gate's OWN answer, never off two named columns** (ratified 2026-09-20): what admits a folder's plaintext files as render inputs is `website_enabled && rests_plaintext_paths()`, so `update_folder_for_user` reads that predicate either side of its own UPDATE and marks when the ANSWER moves — which covers the legacy `mode = "web"` folder's move out of the plaintext-paths class, a transition that touches neither watched column and so used to commit in silence, and covers for free any column `rests_plaintext_paths` ever grows. One owner, `FolderRow::serves_plaintext_web_files`, asked by the serve gate and by the handler's enable-time backfill alike. Then a website-capable folder's deletion; and **every sync change at a render-input path** — a deleted template or `_site.json`, and an *edited* one too, because an edit can withdraw a paragraph and the nest cannot tell that from an edit that adds one — **with ONE predicate deciding what a render input IS, on both sides** (`web_content::render_input`, same ruling): the render's SQL listing folds ASCII case and the door's test did not, so `about.HTML.hbs` rendered a page on every render while its delete routed as a static asset and revoked nothing. The predicate FOLDS case rather than tightening — the widening direction, because tightening would close the same hole by silently un-rendering an author's page at the next render, a withdrawal nobody asked for — the SQL is a coarse pre-filter the render re-checks against it, and the `.hbs` strip folds with it. And **a label's arrival on a web-published post** (same ruling): the nest-as-publisher fold folds each post's labels through the content policy in force, so an arriving label can turn a shown post into a blocked or collapsed one on its own page, the index, the feed and every template that lists it ([`region-blocking.md`](region-blocking.md) § The nest-as-publisher leg), and `upsert_content_label` marks the post's publisher in the label write's own transaction — gated on `content_type == "post"`, with `fauna.labels.attach` rendering what it owes. Latent while the compiled-in region registry enrols no authority, and marked anyway: the census is decided on what a state change CAN do, not on what today's registry makes of it. The nest-wide region-policy re-render is no exception, and **the mark rides the policy write, not the walk** (ratified 2026-09-20): three writers can move the content policy in force for the declared situs — the `nest_region` declaration write (declaring and withdrawing alike), and the relay cache's `put_relay_artifact` / `retire_relay_artifact` — and each one marks every publishing site in one statement **inside its own transaction**, when and only when that write moves what the public pages fold (a declaration that actually changes; a *content policy* for a region on the declared situs's chain). The walk that follows the commit marks nothing of its own. The window this closes is the one a pre-walk mark cannot: a nest that stops between the policy write's commit and the walk's first statement would otherwise restart with the new policy in force, no site owed, and every page still rendered under the old one — and nothing is periodic here to notice. `publish.set` is the one purely additive door: it marks nothing. **A web-serve grant mutation marks nothing either, by a different argument:** a revoked grant's revoke is the *serve door*, which resolves the tier's period key from the live grant registry on every request (§ Paywalled serving), so a sealed page left behind by an unfinished render is unopenable the moment the grant is gone — its render only tidies the row. **Revoking doors fail closed.** A render that errors — anywhere: it replaces the site only in its last statement (*A reader sees a whole site or none*, below) — leaves the old pages in place, so a revoking door whose render errors **clears the actor's rendered site instead** (`rerender_fail_closed`, the shape the legal takedown always had): the site goes dark until the next successful render rather than keep serving what was just withdrawn. Under-publishing is the safe side and costs nothing irrecoverable — every rendered row is derived. `publish.set` alone stays best-effort: after a failed *add*, the old site is still output the author consented to. **A clear that lands discharges the marker** just as a render does — nothing removed still serves, which is all the marker promises — and leaves the site's **restore** owed instead, in the clear's own transaction (next bullet). Because every revoking door fails closed, a single post whose **body cannot be read** is left off the site like one no longer stored, never allowed to fail the whole render: with every revoking door failing closed, one unreadable post would otherwise take the whole site dark at each of them. **The doors render what is OWED, not what this call changed** (`WebContentService::render_owed`): the post-delete core, the folder doors, the retraction pass and the sync door key their render on the marker, so a client's retry of a request torn after its commit — which changes nothing the second time — still renders. `publish.unset` and the legal takedown re-render on every call. A discharge removes only the marker generation it read before its render began (the row's `nonce` is re-rolled by every mark), so a revoke committed *while* a render is running is never discharged by that render. ⚠ **The drain walks `web_render_owed`, never `list_web_publishing_actors`:** that list reads `content_links`, so it drops exactly the commonest owed site — the actor whose last published post was just deleted.
- **One render writes at a time, per actor (ruled 2026-09-20).** A render lists the site's posts and then renders page by page, every page behind an `.await`, before it writes (until the next bullet's ruling it also cleared first and wrote each page as it went), so two renders of one actor can be in flight at once — and until this rule nothing kept them apart: a render that listed a post *before* a revoke committed would write that post's page, its index entry and its feed item back **after** the revoke's own render had cleared and discharged the marker, leaving it serving with no marker, no restore owed and nothing periodic to notice. So: **renders of one actor may overlap in time, but only the one with the NEWEST LISTING may write.** The mechanism is a per-actor **render generation** (`web_render_generation`, one row per actor): every render bumps it immediately before its listing and carries the value it bumped to as its **claim**, and every mutation of the rendered stores — `web_rendered` and `web_rendered_sealed`, the clear as much as the upserts — happens only while that claim is still current, re-checked under the very connection lock the write takes, so no check-then-write race can slip past it. A render that finds itself superseded **abandons**: it writes nothing more, and **discharges nothing** — it settled no debt, so both the owed-render marker and the owed restore stay with whoever does write. To its caller it is still a success, not an error: the site it would have written has already been replaced by a fresher one, and a revoking door that treated it as a failure would blank a site that is perfectly correct. **The LISTING is what the generation marks, not the clear**, because a render's whole output is a function of what it listed; bumping at the clear would let a render that listed *before* a revoke outrank one that listed after it, which is the bug. **The fail-closed clear carries no claim and supersedes every render in flight** (`clear_web_rendered_owing_restore` bumps in its own transaction): it is the safety act, and a render resuming onto a site it blanked would put back exactly what the failed revoke withdrew, onto a site that then looks healthy while its restore is still owed. **Why a generation and not a per-actor lock.** A lock is the obvious shape and was refused on the adversarial case this finding turns on: the author controls both how long a render runs (the safety limits above — 5 s per template × 100 templates, then 5 s per page × up to 1000 per-post pages) and how often one starts (`publish.set`, a template sync), so a mutex would let them queue a **moderator's legal takedown** behind hours of their own renders, and queue more renders while it waited — trading a resurrection the adversary controls for a delay the same adversary controls. A generation blocks nobody: the takedown's render lists and replaces the site at once, and the render it superseded simply finds its replacement refused. **What the fence alone does not give** is a reader's view of a site *while* a render runs: it decides which render's pages end up at rest. That is the next bullet's.
- **A reader sees a whole site or none (ruled 2026-09-20).** Until this rule a render cleared the rendered rows first and then wrote page by page, so every request arriving mid-render saw a site whose clear had landed and whose pages had not: a 404 on a page that exists both before and after, an index or `feed.xml` missing posts. Under the safety limits above that window is minutes to hours on a large site, and every revoking door, every sync change and the region walk re-entered it. **That is a defect, not an accepted property.** The pages are the public internet's view of the author's site; a crawler caches a 404; nothing tells the author and nothing in the product asks them to accept it — and it is *not* the declared dark state, which is whole, owed its restore and shown to its author (the two bullets below), where a half-written site is none of the three. **So: a render replaces the site in ONE transaction, as its last act.** It accumulates the rows of **both** rendered stores in memory as it goes — a `web_rendered` row is `(path, blob_hash, content_type)`, a `web_rendered_sealed` row carries `tier` and `post_id` besides — while the bodies still stream to the content-addressed blob store as they are produced (every body is in the blob sweep's world from the moment it is stored — referenced while its render holds the site, collected past grace once nothing names it — so a superseded or failed render leaves only ordinary orphans: [backup-restore.md](backup-restore.md) § 9 step 2h owns how), and then deletes and rewrites both stores in one transaction under its claim (`db/web.rs::replace_web_rendered`). Both stores in one transaction for the reason one clear always covered both: a public page replaced while a formerly-gated post's sealed page stands behind it is the hole that one call closed. A reader therefore sees the site the last completed render wrote, then the site this one wrote, and never a mixture; a render that is superseded or errors has touched nothing. **What that would cost, and the rule that pays it: the withdrawal deadline.** Replacing at the end moves the clear from the render's start to its end, so a revoking door's render no longer blanks the withdrawn page at once — the old site, withdrawn content included, serves until the new one commits. How long that is, the *author* controls (the same safety-limit arithmetic the generation-not-lock ruling turned on), so an unbounded swap would let an author hold a **moderator's legal takedown** on the public internet for hours with a hundred slow templates — the adversary-controlled delay that ruling refused. The promptness *A revoke is durable* is owed is therefore a **bound, not a side effect**: a render that starts while the actor's owed-render marker stands, and has not committed within the **withdrawal deadline** (a Rust constant, `WITHDRAWAL_DEADLINE`, 10 s — nobody's preference, so nobody's knob), **clears the site under its own claim and carries on**, still committing whole at its end. Past the deadline a reader sees the old site, then *no* site, then the new one — still never a mixture. The deadline is measured from the render's claim, and what enforces it is a timer racing the render, not a check between pages, so a render stuck inside one await is cleared like any other. An ordinary site renders well inside it and is never dark; a site that does not is dark for the rest of its render — an availability cost that lands only on the author whose templates caused it, and buys them nothing: the withdrawn content is gone at the deadline whatever they do. **The deadline clear is a dark site like any other, so it is owed its restore in the same transaction** (`clear_web_rendered`, the one claim-carrying clear): *no dark site exists without the row that brings it back* holds universally rather than only for the fail-closed path — the author's status line is truthful during a long render, a nest that stops mid-render restarts owing both debts, and a best-effort render (`publish.set` while another door's marker stands) that errors after its deadline clear leaves a site the restore retry picks up, which it wakes. The render that carried on discharges that restore when it commits, like any completing render. The deadline clear **discharges nothing and bumps nothing**: it carries its render's claim, so it is refused once that render is superseded, and the marker is discharged by the commit as ever. A render with no marker standing when it began — `publish.set`, a grant mutation, a restore — has no deadline: nothing was withdrawn, and the old site is output the author consented to for as long as the new one takes. A revoke that commits *during* such a render starts its own render, which supersedes it and carries the deadline itself. **Where the fail-closed clear lands under this rule.** `clear_web_rendered_owing_restore` is unchanged and matters *more*: since a failed render now leaves the old site whole at every point of failure, not only before its clear, the fail-closed clear is the **only** act that withdraws the page when a revoking door's render errors — no longer the belt to a clear the render had usually already made. It still carries no claim, still supersedes every render in flight, still discharges the marker and owes the restore. **The owed restore's nonce is read after the render's claim is minted, not before** (the marker's is still read before the listing): any clear that lands before the mint is answered by this render's replacement, and any clear that lands after it supersedes the render, which then discharges nothing — so no ordering leaves a healthy site carrying a stale restore row. **Refused alternatives.** *Accept it* — above. *Clear first, write whole at the end* (no deadline, no timer): consistent but strictly **less** available than the defect it replaces — every template sync would take the whole site dark for the whole render, where today some of it serves. *Swap at the end with no bound*: the adversarial takedown delay. *Withdraw just the revoked pages at once*: a door cannot name them — a withdrawn post is on its own page, the index, the feed and every template that lists it, and a template edit withdraws a paragraph the nest cannot see.
- **A blanked site is owed its restore (ruled 2026-09-19).** A fail-closed clear is right about the revoke and wrong to stop there: after a *transient* storage error it left the author's whole site dark until they happened to publish, unpublish, flip a folder or sync a template — and no app tells them to. That is a nest state the user neither chose nor can see, which [`../principles.md`](../principles.md) § Works out-of-the-box does not allow behind everyday doors. So the clear records a second, separate state: one `web_restore_owed` row per actor, written **in the same transaction as the clear** (`db/web.rs::clear_web_rendered_owing_restore` — a site a failed render took dark cannot exist without the row that brings it back), and discharged by **any render of that actor that completes**, whichever door or pass asked for it (same `nonce` discipline as the marker: a clear that lands while a render runs is not discharged by that render). **Why a second state rather than keeping the marker:** the two are owed differently. A revoke is a *safety* debt — paid at once, fail-closed, drained before the nest serves, never paced. A restore is an *availability* debt — a render that keeps failing has to be paced, and nothing about it may delay serving everyone else. One row meaning both would force one of those policies onto the other. **Who pays it.** (1) The **boot drain**: after the owed revokes, `drain_owed_renders` makes one render attempt per blanked site (a site the revoke walk just tried is not tried twice). (2) The **restore retry**, which that same drain leaves running between boots: idle until a fail-closed clear wakes it, then one pass over every blanked site, paced by the nest's one backoff (`RetryState`/`next_attempt_delay` — the first attempt at once, then evenly spread, never more than that primitive's hard-coded hourly budget; the log is held in memory and seeded by the boot drain's own outcome). No knob: the pacing is a Rust constant. (3) Any door's render, as before. Every attempt goes through `rerender_fail_closed`, and a render writes nothing before its one replacing transaction (previous bullet), so a restore that errors leaves the site exactly as dark and as owed as it found it. **A render that fails for ever is retried for ever, deliberately, and that is bounded.** The earlier text discharged the marker so that a persistently failing render could not re-run at every boot; the restore does re-run — once per blanked site per boot, plus at most the backoff's budget of passes per hour — and each failing attempt is a render that errors before its write: a few reads. A *cap* on attempts was considered and refused: it would turn a long outage into a permanently dark site, which is the defect being closed, to save reads nobody will miss; and since an unreadable post body is skipped rather than fatal, what still fails a render persistently is a nest-wide storage fault, where one log line per pass is the signal an admin needs. **It cannot resurrect anything:** a render writes only what the current state lists, so a restore after a delete, an unpublish or a takedown comes back without them. **Scope of the schedule.** The retry renders *only* sites a failed render took dark. It is not a periodic re-render: a page that is merely stale is still replaced only by the door that made it stale, or the boot drain — which is exactly why revoking doors mark and fail closed. Whether the author is *told* is the next bullet.
- **A blanked site tells its author (ruled 2026-09-19).** The restore means the author never has to *act*; it does not mean they need not *know*. From the app a dark site looks exactly like a healthy one, and the app keeps handing out copy-link affordances for pages that answer 404 — the same defect the *no serving origin* ruling closes (§ Published-post management: “never silently hand out a dead link”), and a nest state the user cannot see, which [`../principles.md`](../principles.md) § Works out-of-the-box does not allow. **So: surfaced to the author, not acted on by them.** The `web-settings` page shows a status line (`web-settings-render-status`) while — and only while — the caller's `web_restore_owed` row exists: the published pages are temporarily down, the nest is bringing them back by itself, synced files are unaffected. It is information, with **no button**: a “retry now” would be a knob standing in for the retry the nest already paces, and would let a client drive renders past that pacing. The copy affordances stay enabled — the links are the right links and come back to life unaided; the status line is what makes handing one out an informed act. **The wire is one additive field on the read the page already makes:** `WebPublishListReply.rendered_pages_down: bool` (`fauna.web.publish.list`), `false` omitted from the encoding, so an older nest reads as healthy and an older client sees today's reply — no new kind, no poll, no push: the page reads it when it is visited, like everything else on it. It rides `publish.list` rather than `get_subdomain_enabled` because the state is about the *rendered* site whichever origin serves it (subdomain, custom domain or apex), and that read is already the rendered site's. Strictly caller-scoped: the reply says nothing about any other actor's site. **The admin gets no new element, deliberately.** What fails a render persistently is a nest-wide storage fault (previous bullet), not a web fault, and its signal — one warn line per retry pass — already reaches the admin *in the app*, on the `admin-logs` page; a per-feature “N sites dark” counter on `admin-web` would be a second, narrower witness of the same fault, and the first of one-per-subsystem. A nest-health surface, if one is ever ruled, is where such a count would belong. **Where the logic lives:** the nest projects the row's existence; `libs/fauna-client-web` carries the flag on `WebPageRead` (wasm + UniFFI twins); each app only paints the line. Rollout rust → nest → tui → the other six in trickle-down.
- **Serving layer:** resolves the account from `Host`, walks the path order, assembles the body, sets `Content-Type` from the stored field and cache headers (`Cache-Control: public, max-age=300` for HTML, longer for hashed assets). Static delivery only. **The two tables store their bytes differently, and the serve path discriminates:** a `web_rendered` row's `blob_hash` is the rendered body, stored verbatim (the nest wrote it), while a **`web_files` row's `blob_hash` is the sync change's *manifest* hash** — its body is assembled by walking manifest → chunks → blob store, stripping the nest's at-rest framing (`backup::encode_blob`) off every blob. Serving a `web_files` blob verbatim emits framed CBOR, not the file (the bug this rule now forecloses; the same walk feeds the render pipeline's `.html.hbs` / `_site.json` inputs).
- **Sealed static files (paywalled `web` sets; behavior owner `monetization.md` § Pillar 2):** a `web_files` row carries an additive `content_key_version` (NULL = plaintext, the public path; the ingest transcribes it from the sync change) plus the `folder_id` it was synced from — the set resolves both the grant-scope qualifier (its **name**) and the `web_paywall_tier` gate. A sealed row serves **only** through the paywall capability-URL token gate (the same gate as sealed post pages; the `(owner, path)` token scope covers file paths unchanged): token verify → the web-serve holder's granted folder content keys for that generation → manifest → chunks → decrypt → serve `Cache-Control: private, no-store`. No/invalid token, or no live grant → the **set-level paywall teaser** (tier + price + payment link, rendered at serve time) with **HTTP 402 Payment Required** — a folder has no per-path pre-rendered teaser the way a published post does, and 402 keeps a downloader from mistaking the teaser HTML for the asset. **Fail-closed rule: ciphertext is never served** — a sealed row whose set has no paywall tier (e.g. a shared-but-not-paywalled web set) is not served at all (404), and a sealed row that no candidate key opens yields the teaser, never bytes. **The one sync ingest rail, WS-RPC `fauna.sync.changes.record`, routes into `web_files`** (`web_files_projection::route_web_file_change`), carrying the M2 `content_key_version` a sealed (paywalled) set travels with; the `/sync/ws` data plane that was once a second rail is removed (`file-sync.md` § Relay serving → *The `/sync/ws` data plane leaves with the daemon*).
- **The manifest walk is bounded by the manifest's own declared size (ratified 2026-09-28).** A served file's manifest is uploader-authored and reachable by an anonymous GET of a site path or share link, and its chunk list may name one stored chunk tens of thousands of times. Repeats are legal in an honest plaintext file, so the walk (`web_content::file_bytes::read_file_by_manifest`, both arms) bounds by size, not distinctness: a list naming more chunks than `total_size` has bytes is refused before any chunk is read, and a running total refuses the chunk that carries the walk past `total_size` (over ciphertext in the sealed arm, which allows each chunk its frame byte and AEAD tag, and again over plaintext after decrypt). The declared `total_size` itself has no ceiling yet — see § Implementation status today.

- **After an identity succession the whole plane follows the account** — the apex binding, the files, the rendered output, the custom-domain rows and the subdomain opt-in alike. Which rows move, and why each one had to, is declared per table in `bins/fauna-nest/src/db/actor_tables.rs` and owned by `succession-aftermath.md` § Re-key scope; until 2026-08-12 only the first two moved, and the site of a succeeded account was reachable by nobody.

The authoring surface is the Fauna app (a publish toggle, the admin apex-actor picker, a subdomain opt-in, and a custom-domain registration screen) and fauna-sync — there is no nest-side CMS or admin panel (product invariant: configuration is set from apps, not CLI/config files).

## Admin apex hosting

The deployment admin designates **one actor** whose `web` site serves the apex/main path (`https://<domain>/`). This is the direct analogue of the per-domain **catch-all mail actor** (`fauna.bridges.set_catch_all_actor` → `mail_domains.catch_all_actor_id`, `mail-multidomain.md` § Per-domain catch-all): an Admin-scoped designation of an actor that receives the domain's "unaddressed" traffic — there, inbound mail with no matching alias; here, web requests to the apex host.

- **Designation RPC:** `fauna.web.set_apex_actor` (Admin-class), `actor_id: Option<32 bytes>` — `Some` designates, `None` clears (mirrors `set_catch_all_actor`'s set/clear shape). A companion `fauna.web.get_apex_actor` reads the current designation. Persisted nest-wide (the apex is the single node domain, not per-mail-domain), and the live `HostResolver`'s node-domain → apex-actor mapping is updated on set/clear and rebuilt at boot.
- **Content source:** the designated actor's own `web` folder + `web_published` posts — the apex actor authors exactly like any other user. The admin typically designates their own actor or a dedicated deployment/"org" actor.
- **Cleared = info page.** With no apex actor designated, the apex serves the existing built-in nest info page; designating an actor is purely additive and reversible.
- **Cert:** the apex is served on the nest's **own apex cert** (already provisioned) — apex hosting needs no new DNS record and no new certificate, which is why it is the cheapest surface and the first to ship.

## Custom domains and TLS

### Registration and DNS verification

1. The user registers a custom domain from their client (WS-RPC `fauna.web.domain.set` — WS-RPC-only; no HTTP twin exists). The nest generates a verification token and inserts a `web_domains` row with `status = 'pending'`. **Max 3 domains per account** (`MAX_DOMAINS_PER_ACCOUNT`), a cert-abuse guard.
2. The user publishes (from their client, which holds the DNS-provider key — the nest never sees it, per `dns-management.md`) a TXT record `_fauna-verify.<domain>` carrying the token, plus an A/CNAME record pointing the domain at the nest.
3. A background **domain lifecycle task** polls pending domains every 5 minutes and checks `_fauna-verify.<domain>` via the shared public-recursive `DnsVerifier` (the same resolver the unified DNS-management verify surface uses — **not** the DNS-provider API, **not** a stub). On a match it advances `pending → verified → active`.
4. Once `active`, the nest obtains a per-domain Let's Encrypt certificate via **HTTP-01** (never DNS-01 — consistent with the nest's own cert; the nest has no autonomous DNS-write capability and holds no provider key). The cert is written to `acme_dir/<domain>/` and installed into the live SNI resolver.
5. **Routing follows in the same pass.** After advancing statuses, the same lifecycle task re-projects the `active` set onto the live `HostResolver`'s custom-domain map, so a domain that goes `active` while the nest is running starts resolving immediately rather than at the next restart. It is a **replace-all reconcile, not an edge trigger** — the map *is* the projection — and a failed DB read skips the pass untouched rather than derouting every live site. This task, unlike the per-domain cert loop, runs unconditionally: routing must not depend on TLS + HTTP-01 ACME both being enabled.

All steps after the user sets the two DNS records are automatic; the user polls `fauna.web.domain.get` to watch `pending → verified → active`.

### Per-domain TLS — the SNI resolver

The nest's TLS listener uses a **`MultiDomainCertResolver`** (`acme.rs`) implementing rustls `ResolvesServerCert`:

- A lock-free (`ArcSwap`) `HashMap<domain, CertifiedKey>` of per-custom-domain certs, plus a **default cert** (the nest's own apex cert).
- On handshake, the SNI hostname selects the matching per-domain cert **if it is valid and covers the name**; an unknown SNI (or no SNI) falls back to the default cert. (A registered-but-expired/non-covering per-domain cert instead falls through to a per-SNI self-signed *floor* carrying that name — the cert-selection policy is owned by `architecture/nest/tls-certificates.md` § A, which this summary defers to.)
- It supports a **pending (certless) state** for cold-boot-with-ACME, exactly like the single-cert `ReloadableCertResolver` it replaces: the listener binds immediately and the first apex cert hot-swaps in via the cert-watcher with no restart.

**Channel binding is unchanged and load-bearing.** The `fauna.auth.handshake` handler signs the SPKI of the cert the nest *itself serves* over `spki_sha256 ‖ client_nonce` with `nest_signing_key` (`auth_handlers::build_cert_binding`, reading live via `acme::ServedCertSpki`). That signed SPKI is always the **default (apex) cert's** SPKI — the cert a Fauna *client* connects to the nest with. Per-custom-domain certs serve *web visitors* (browsers hitting `alice.com`), who do no Fauna channel binding. So `MultiDomainCertResolver` implements `ServedCertSpki` over its default cert; selecting a per-domain cert for a web visitor's SNI never changes what the handshake handler signs. (See `security.md` § Transport trust, Axis 1: the nest signs the SPKI of *its own* served cert, never one the client reports.)

### Separation from the nest's own / mail-bridge certs

Custom web-domain certs are a **distinct cert population** from the nest's own apex (+ `mail.<domain>`) cert:

- The nest's own cert is one multi-SAN chain (apex + `mail.<domain>` for each active mail domain, from `desired_san_domains()`), issued/renewed by `acme_http01::cert_lifecycle_task`. Custom web domains are **not** in that SAN set and must not be — different actors, separate cert and separate Let's Encrypt rate budget.
- Custom web-domain certs are **never sealed and fanned out to mail bridges**. `store_acme_material` (invoked from the apex cert-watcher) is apex-only, gated on the configured node domain; bridges only need the nest's own cert. The per-domain cert path stays out of that hook.

### Issuance, renewal, removal

- **Issuance:** for each `active` web domain lacking a current cert, run an HTTP-01 order (the shared `acme_http01::obtain_certificate` + the shared `start_http01_listener` / `ChallengeState` — challenges keyed by token, so concurrent multi-domain orders are safe), write to `acme_dir/<domain>/`, and call `resolver.add_domain(domain, cert)`.
- **Failed-validation backoff** reuses the nest's existing per-attempt retry budget (`acme_http01::RetryState` / `next_attempt_delay`) per-domain — the same rolling-window machinery the nest's own cert uses. No bespoke backoff.
- **Renewal:** re-issue when a domain's cert is within 30 days of expiry, same threshold as the apex cert.
- **Removal:** a client deregisters a domain via `fauna.web.domain.delete` (owner-scoped; `db.delete_web_domain` removes the row) — never a CLI op. The per-domain cert lifecycle loop is the **sole authority** over the resolver's per-domain map: each pass it reconciles the resolver against the `active` set, so a domain whose row is gone is dropped via `resolver.remove_domain(domain)` and its `acme_dir/<domain>/` deleted on the next pass (≤ the 5-min poll). One reconciliation loop owns add/renew/remove rather than scattering resolver mutations across request handlers. **Routing is the deliberate exception**: `domain.delete` drops the name from the `HostResolver` at once (the lifecycle task's reconcile is the steady-state authority and would catch it within the poll anyway), because a *cert* that outlives its row is inert while *routing* that outlives its row means the nest keeps serving content its owner just withdrew — and the still-installed cert means HTTPS does not mask that window.

## Same-origin security model

User-hosted web content is **attacker-controlled HTML + JavaScript**. The browser's only isolation boundary for it is the **Same-Origin Policy (SOP)**, keyed on **origin = scheme + host + port**. This section is why the addressing model puts every untrusted site on its own origin, and why path-based `/<user>` is deferred.

### The decisive fact

The Fauna web SPA stores the user's **raw Ed25519 master secret key**, in plaintext hex, in `localStorage` (the slot name is in [`../architecture/apps/web.md`](../architecture/apps/web.md) § localStorage Keys). Auth is key-based with **no passwords and no cookies** — the nest sets no `Set-Cookie`; every connection re-derives auth by signing the WS-RPC handshake with that secret (`silentSignIn(secretHex)`). So that slot holds the *sole, permanent* credential, and it is readable by any script running on the origin that owns that `localStorage`. **Sealing that slot at rest would not change this section** (the design is ruled and unbuilt — owner [`../architecture/apps/common.md`](../architecture/apps/common.md) § Credential storage → *The web app's posture*): a script in the origin reads the unlocked key from the page's memory, so every invariant below stays load-bearing whether or not the slot is sealed.

### Worst case — same-origin user content = drive-by master-key theft

If untrusted user content is ever served on the **same origin** as the SPA's `localStorage` (e.g. the SPA at `https://example.com/app` and user content at `https://example.com/eve`, both origin `https://example.com`), then a malicious page at `example.com/eve` can read the SPA's identity slot straight out of `localStorage` and exfiltrate the **victim's master private key** the moment the victim merely *visits* it while logged in — no click, no phishing. That is not session hijacking but **permanent, total identity compromise** (the key *is* the identity; recovery requires rotating identity, and the attacker already has what they took). Same-origin also lets the attacker `<iframe src="/app">` and script the SPA's DOM directly. This is the canonical reason GitHub serves Pages on `github.io`, Google on `googleusercontent.com`, etc.: **never serve untrusted HTML on the authenticated app's origin.**

### Origin vs. site

A registrable domain that is **not on the Public Suffix List** (e.g. `example.com`) makes all `*.example.com` distinct *origins* but the same *site*. So **subdomains fully isolate the SOP surface** (`localStorage`, DOM, service-worker scope) — the master-key theft above is impossible across `alice.example.com` ↔ `app.example.com` — but they do **not** isolate at the cookie/site layer (a `Domain=example.com` cookie, or cookie-tossing from a sibling subdomain, crosses it). The gold-standard fix for *both* layers is a separate registrable domain per untrusted content (the `github.io` pattern), which is expensive for self-hosters (a second domain + ideally a PSL entry per box) and therefore **out of scope**; the subdomain model is the chosen balance.

### Invariants this model relies on

1. **One origin per untrusted site.** Apex (`<domain>`), each user subdomain (`<handle>.<domain>`), and each custom domain are distinct origins. The trusted SPA lives on its own origin (`app.<domain>` in the canonical hosted deploy; CORS defaults to `https://app.fauna.social` — `node_policy_core::DEFAULT_CORS_ORIGIN`, boot-resolved from the `nest_cors_origins` row and admin-settable via `fauna.admin.set_cors_origins`). User content never shares an origin with the SPA.
2. **Auth is never cookie/ambient — load-bearing, not incidental.** Because all `*.<domain>` are the same *site*, the only thing that keeps an attacker subdomain from acting as the victim against the apex-hosted API is that there is **no ambient credential** — auth is an explicit per-connection signature from the identity secret, which lives in a different origin's storage the attacker cannot read. **No auth cookie may ever be introduced** while untrusted content shares the site.
3. **Reserved paths / hosts.** `/api/v1/*`, `/app`, `/.well-known/*` and the hosts `mail.<domain>` / `mta-sts.<domain>` / `app.<domain>` are never served as user content.
4. **No scope-broadening for user-served scripts.** The nest must not emit a permissive `Service-Worker-Allowed` header for user content, so a user's service worker cannot claim a scope beyond its own path/host.
5. **Clickjacking.** The SPA app origin sets `frame-ancestors 'none'` / `X-Frame-Options: DENY` so untrusted pages cannot UI-redress it (cross-origin iframes already cannot *read* it; this closes redress).

### Residual the model does not remove

**Phishing / brand trust.** `alice.example.com` (or a future `example.com/alice`) still carries the trusted `example.com` brand; a hostile user can serve a convincing fake login. SOP cannot touch this; only a separate registrable domain would, which is out of scope. Mitigation is UI/education, not architecture — accepted as inherent to single-domain self-hosting.

### Why path-based `/<user>` is deferred

`example.com/<user>` is the *only* addressing option that puts untrusted content on a shared origin, so it is safe **only** if the SPA *and* the API are first moved entirely off the apex origin (to `app.<domain>`), the apex becomes untrusted-content-only, and invariants 1–5 above all hold — including forbidding the self-host `/app`-on-apex SPA fallback. That is a larger, deployment-topology change. Subdomain + apex hosting deliver the same product outcome (admin home page + per-user sites) **without** it, so path-based is deferred until there is a concrete need that subdomains cannot meet.

### The nest-served `/app/` and the central origin (ratified 2026-09-24)

Every nest serves the bundled SPA at `/app/` and keeps doing so: it is the out-of-the-box path (a fresh nest with no internet still needs its app), the LAN/offline path, and exactly right for a self-hoster, whose own nest is their trust root. It is also the one place a nest chooses the code a browser runs, and that code holds the master secret (§ The decisive fact) — so *which origin a user should load the app from* is a trust decision, owned by [`../architecture/front-door.md`](../architecture/front-door.md) § Which origin a user loads the app from; this section owns only what the nest's `/app/` answers.

**The admin's one-click (nest state, app UI on all 7 apps; the nest half built 2026-09-27, the app UI built on tui and owed on the other six — § Implementation status today).** An admin setting chooses what this nest's `/app/` answers: **(i) bundled** — the SPA the nest ships (the default), or **(ii) central** — a redirect to the central origin's app entry with this nest pre-filled, so a user who arrives at the nest's own address is handed to the association-served code and lands on the handle-entry page already pointed at this nest. The redirect is a **302** to `https://app.fauna.social/app/<same path and query>` plus `nest=<this nest's handle domain>` — temporary, never a 301/308, because a browser caches a permanent redirect and an admin could not undo the choice for users who already followed it; the origin is the one Rust constant the CORS default already carries (`node_policy_core::DEFAULT_CORS_ORIGIN`), so no second knob names it; a domainless box has nothing to pre-fill and keeps serving bundled whatever the setting says. The default is (i) under the works-out-of-the-box invariant (`principles.md` § Works out-of-the-box): a fresh internet nest boots domainless and cannot know whether the central origin is reachable from its users, and a redirect to an origin that does not resolve is a dead nest for every browser. The choice is nest state (a `nest_web_app_origin` row beside `nest_cors_origins`, additive: an older nest answers unknown-kind and every app renders "this nest predates the choice"), set only from the app UI — a section on `admin-nest` beside NAT mode ([`admin.md`](admin.md) § N Nest → *Web-app origin*), never a config file or flag (`principles.md` § One configuration surface). Two rules hold in either mode. **The redirect honours invariant 3:** `/app` stays reserved and never serves user content — a nest-chosen redirect is an *answer* for the reserved path, not content on it, and `mount_spa`'s security headers ride it too. **It is not a trust control:** a user who follows the nest's redirect is trusting the nest to send them to the right place, which is exactly what a malicious nest would not do (front-door.md's claim); the redirect exists so honest nests consolidate their users on the checkable origin, and a user's typed or bookmarked origin always wins. One more reserved path follows the same choice by the same rule: the viewer page a fragment-keyed share link opens (`GET /share/<token>` on a navigation request — bundled, or the same `302`, under the same headers), owned by [`share-links.md`](share-links.md) § The private-file extension.

**What the bundled app answers for a path it does not have (ruled 2026-10-01, refutable; unbuilt).** The same answer the central origin gives ([`../architecture/front-door.md`](../architecture/front-door.md) § Public-vhost topology): a path that names no file is the app's page with status 200, because the app routes it in the browser — except under the content-hashed asset tree (`/app/_app/`), where a miss is **404**. A script that no longer exists must not come back as a page with a success status: a tab left open across an upgrade asks for the old build's hashed modules, and a page answered under a script's address is a wrong-type error the browser cannot explain and a cache may keep, where a 404 is the honest answer. One app, one answer on both origins. **Today** the nest answers every miss with the page — `mount_spa`'s file service falls back to `index.html` for all paths — and no test requests a missing asset.

**The `nest` query parameter is new work, not an existing feature** (the web app today reads only its e2e dial seam and the add-account flag from the URL). What it means — a prefill of the handle-entry page's domain part, through the shared onboarding machine, that never auto-connects or auto-trusts — is owned by [`onboarding.md`](onboarding.md) § 2 Handle entry → *Nest hint*; the redirect above is its first producer.

## Paywalled serving (the Pillar-2 hook — design ratified 2026-07-12, built)

## Architectural rules

1. **Static delivery only.** No server-side execution of user code; no per-request template processing. Templates are pre-rendered to static HTML on write. (A nest-owned stateless capability-token check before serving pre-rendered bytes is not user-code execution — § Paywalled serving.)
2. **Configuration from the app, never the box.** Domain registration, publish toggles, and `web` folder designation are all app/fauna-sync actions — no CLI flags, no hand-edited config.
3. **HTTP-01 only; the nest holds no DNS-provider key.** Custom-domain certs use HTTP-01 like the nest's own cert. DNS records (the `_fauna-verify` TXT and the A/CNAME) are published by the user's client, which holds the provider credential — never the nest (`dns-management.md` invariant).
4. **Channel binding is over the default cert.** The handshake-signed SPKI is always the apex cert the Fauna app connects with; per-domain certs serve only web visitors and never participate in channel binding.
5. **Custom web-domain certs are isolated** from the nest's own cert SAN set and from the mail-bridge seal-and-fan-out path. Per-subdomain certs follow the same isolation.
6. **One origin per untrusted site; auth is never cookie/ambient.** Apex, each subdomain, and each custom domain are distinct origins; the trusted SPA lives on its own origin; no `Set-Cookie` auth is ever introduced (§ Same-origin security model). Path-based `/<user>` is deferred for this reason.
7. **Apex hosting is an admin designation, mirroring catch-all mail.** One actor per deployment, set via `fauna.web.set_apex_actor` (Admin); cleared = info page; served on the nest's own apex cert (no new DNS/cert).
8. **Subdomain hosting is opt-in and uses per-subdomain HTTP-01.** A user opts into `<handle>.<domain>`; the cert is issued via the existing `MultiDomainCertResolver` HTTP-01 lifecycle; the one wildcard `*.<domain>` A record is published by the admin's client, never the nest.
9. **Where logic lives:** the nest owns serving and the domain/TLS lifecycle today. Anything genuinely shareable (e.g. domain-name validation) lifts to `libs/fauna-*` per priority #2 when a second consumer appears.

## Don't do these

- **Don't add custom web domains to the nest's own cert SAN set.** Separate cert, separate rate budget.
- **Don't seal/fan custom-domain certs to mail bridges.** Keep them out of `store_acme_material`.
- **Don't use DNS-01 or give the nest a DNS-provider key** for custom-domain certs. HTTP-01 only; the client publishes DNS.
- **Don't sign a per-domain cert's SPKI in channel binding.** The handshake signs the default (apex) cert's SPKI only.
- **Don't invent a new backoff** for failed validations — reuse `RetryState`/`next_attempt_delay`.
- **Don't do per-request Handlebars** or accept executable file types.
- **Don't serve untrusted user content on the SPA's origin**, and **don't introduce auth cookies** — both break the same-origin model. (Paywall visitor credentials are explicit bearer capability tokens, never cookies — § Paywalled serving.)
- **Don't build path-based `/<user>` hosting** without first moving the SPA + API off the apex origin and adopting the § Same-origin security model invariants.

### Serving the SPA is artifact wiring, not just a mount (ratified 2026-07-29)

Invariant 3 of § Same-origin security model reserves `/app` for the SPA. The nest
half of that has always been correct — `mount_spa` mounts it whenever
`config.nest.static_dir` is set — but **`static_dir` is not something the nest
knows; it is written into the deployment's persisted config by the deployment
artifact**. When it is absent the bundled `/app` answers a bare **404**: `/app` is
mounted unconditionally since the web-app origin choice (2026-09-27), because the
path is reserved whatever ships. Before that, an absent `static_dir` meant no route
at all, and `/app` fell through to `web_content_or_info`, which serves the nest info
page — a `200 text/html` indistinguishable from success to any positive-only check.

That split is the whole failure surface, and it opened once already: the Docker
image's `nest.toml` overlay was a `sed` anchored on a `require_registration` line
that `config/default.toml` stopped shipping (2026-07-13). A sed
address matching nothing is a silent no-op with exit 0, so **every Docker nest
first-booted 2026-07-13 → 07-24 served the info page at `/app`**, byte-identical
to `/`, with the invariant-#5 headers silently absent too. `spa_security_headers.rs`
was green throughout: it mounts `mount_spa` against a temp dir and so tests the
mechanism, never that the artifact configures it.

The standing rules that follow:

1. **The artifact's config writes are verified writes.** `docker/nest-toml-overlay.sh`
   is a separate, directly-runnable script (not inline `sed`) precisely so it can be
   tested without docker, and every write re-reads the file and **fails the boot**
   if the key is not there. A half-configured nest that serves is worse than one
   that refuses to start.
2. **`static_dir` is reconciled on every boot, not seeded on first run.** It is a
   hard-coded artifact constant (product-invariant bucket 1 — `principles.md`
   § One configuration surface), so no box has a value worth preserving, and an
   every-boot write is what lets a box deployed during a broken window self-heal on
   image pull. `cors_origins` stays first-run: it is a *seed* the app-set
   `nest_cors_origins` row supersedes (`installers/docker.md` § Environment Variables).
3. **Both halves are tested, at the tier that can see each.** The write itself:
   `tests/docker/test_entrypoint_overlay.py`, run against the real
   `config/default.toml` on the merge path (`just entrypoint-test`) and in CI's
   `installer-checks` job — so a future commit that renames or drops a `[nest]` key
   goes red there, not in production. The consequence: tier_4
   `tests/e2e-unified/tests/platform/docker/test_spa_serving.py` asserts a container
   from the real image answers `/app/` with the SPA, that `/` and `/app/` are *not*
   the same page, that the invariant-#5 headers ride the real mount, and that a
   box whose `nest.toml` predates the fix repairs itself on restart.

**Security posture (mechanisms owned here; landed 2026-06-23/24):**

- **SPA-origin headers (invariant #5).** `mount_spa` scoped to `/app`: `X-Frame-Options: DENY` + CSP `frame-ancestors 'none'` (header-only — invalid in `<meta>`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` — deliberately NOT applied to the apex/subdomain web-content fallback (isolated origins serving user-authored HTML). Proven: `spa_security_headers.rs` + the `--client web` e2e under the enforced CSP — **and, since 2026-07-29, `tests/e2e-unified/tests/platform/docker/test_spa_serving.py`, which asserts the headers on a real image's `/app` rather than on a directly-mounted `mount_spa`** (see § Serving the SPA is artifact wiring, not just a mount).
- **One SSRF-safe media-proxy core.** Both bridge media proxies (`/api/v1/media/proxy` bearer-gated + the bluesky `cdn.bsky.app`/`video.bsky.app` host-allowlisted twin) funnel through `media_proxy_routes::proxy_remote_media`: https-only, global-address-only, redirects disabled, resolved-IP pinned (`crate::ssrf`), a **fixed inert content-type allowlist** (raster image / video / audio / HLS; `image/svg+xml` deliberately excluded), always `nosniff` + `Content-Disposition: inline`. The bluesky route stays navigable + credential-less by design (subresource loads can't carry a bearer; the allowlist + nosniff close the navigable-XSS vector). A uniform fetch-to-blob-with-bearer posture across all 7 apps is a **deferred cross-app decision**, not needed to close the vector.
- **Render-pipeline DoS limits (§ Routing's "Safety limits", now enforced).** `spawn_blocking` + 5 s timeout per template (`service::render_bounded`), the same 5 s enforced in the render thread by a `RENDER_TIMEOUT` check planted at every block body (`render::inject_budget_checks`) since the timeout cannot stop the thread; a 4 MiB `CappedWriter` output cap (`MAX_RENDER_OUTPUT_BYTES` — storage, not iteration); a 1 MiB template-source cap (`MAX_TEMPLATE_BYTES`); context caps `MAX_RENDERED_POSTS` (1000) via `list_web_published_servable_capped` + `MAX_TEMPLATES` (100). **Deliberately NOT done:** (a) metering rendered output against the owner's storage quota — `web_rendered` is derived/regenerable and already bounded per render, so quota-charging derived bytes is the wrong shape; (b) debouncing/coalescing render triggers — each trigger is an authenticated owner action and each render is individually bounded, so coalescing is an efficiency refinement, not the DoS closure. Both are deliberate scope, not drift.
