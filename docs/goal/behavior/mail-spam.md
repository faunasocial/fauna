## Goal

A user marks one message as spam in their Fauna app (or in their third-party MUA via the `\Junk` flag); the per-user Bayesian classifier learns from that one event; subsequent inbound mail with similar content (n-gram features overlapping with the trained sample) lands in Junk instead of INBOX — for that user only, not for any other user on the same deployment. The user changes their mind, opens the training-history list, clicks **Undo** on the entry; the inverse training applies; the model is back to its previous state. Reset is one click and irreversible — model weights drop, cold-start logic resumes.

**Bar: parity with Gmail's per-user "report spam" / "not spam" buttons** — same one-click training, same routing fidelity (mail similar to the trained sample lands in the right folder), same per-user isolation (Alice's training doesn't affect Bob), same cross-IMAP-MUA fidelity (Thunderbird's `\Junk` flag-set, Apple Mail's "Move to Junk" gesture, the Fauna app's button — all three feed the same per-user model). Beyond Gmail's defaults, the user has visible training history with undo, an explicit reset, and end-to-end key control over the model file, which rests sealed under their own key (§ Encrypted-mode interaction).

**Symmetric design with mail-aliases.** Both are per-account personalization layers atop a deployment-wide policy floor (rspamd's deployment-wide pre-classification corresponds to the deployment-wide reserved-local-parts on the alias side). The user adds their personalization; the admin sets the floor; the two combine.

## Pipeline (recap from `smtp-server.md`)

The logical pipeline (steps 1, 3, 4 run at the MTA's DATA-end / pre-delivery stage; step 2 does **not** — see the caveat on it):

1. **rspamd deployment-wide pre-classifier** — content rules, RBLs, statistical signatures, scaled onto the 0–15 Bayesian scale (scaling mechanism + knob owned by `docs/goal/behavior/mail-content-scanning.md` § rspamd configuration). Same for every user; admin-tuned. ClamAV (separate binary pass/reject signal, runs before rspamd at the MTA perimeter) is named in the same doc § ClamAV configuration.
2. **Per-user Bayesian classifier** — n-gram-based Naive Bayes. Score range 0–15 (same scale as rspamd for combinator simplicity). Per actor; the actor's training history shapes the weights. **Placement caveat: this step never runs at the MX perimeter** — the perimeter passes `weighted_bayesian_milli = 0` permanently; the per-user term is scored **post-delivery** at the authenticated agent (the Fauna app, or the AUTH'd MDA session for third-party IMAP MUAs), which re-files spam to Junk there. This is uniform across every deployment — § Scoring placement is the rule (a nest-at-ingest scorer was never built and, since Phase 3 sealed mail at rest universally, is now un-implementable, not merely unbuilt); the perimeter combined score is effectively the rspamd score.
3. **Combined score** — `max(rspamd_score, weighted_bayesian_score)`; see § Combined-score formula. rspamd is the **sole deployment-wide content scorer** (it runs its own SPF/DKIM/DMARC/RBL + statistical + content rules); there is no separate auth/DNSBL heuristic. When rspamd is admin-disabled the deployment-wide term is 0 (an explicit opt-out, mirroring ClamAV-disabled).
4. **Routing decision (permissive auto-Junk default)** — `combined_score < spam_folder` → INBOX; `≥ spam_folder` → Junk. There are two score tiers, **Junk and reject**, and no hold between them (owner `mail-policy-config.md` § Inbound perimeter). **The `reject` tier defaults to disabled (`0`)** — out of the box the bridge scores + tags + delivers and **never 550-rejects on the content score**. Destructive actions are opt-in: an admin sets a non-zero `reject` tier (`smtp-server.md` § Inbound perimeter), or a per-user filter rule acts on the score (delete, redirect; `email-filters.md` § Email filter rules). The spam-folder threshold is per-account (`mail.account.spam_threshold_override`, Tier 3; default = `mail.inbound.max_score_before_spam_folder`, Tier 2). A **per-alias** tier sits above the per-account one; where the three tiers are resolved, and what the scorer therefore consults, is owned by `mail-aliases.md` § Spam-threshold override. Rationale: *user-controls-their-data* forbids silently bouncing/hiding mail on a score the user can't override; *works-out-of-box* still files spam to Junk. Perimeter hard-gates (auth, DNSBL reject-class, ClamAV malware) reject independently.

This doc adds the **training feedback loop** that updates step 2's weights based on user signal.

## Scoring placement

**Per-user Bayesian scoring runs at the same positions as search — never at the inbound-MX perimeter.** This is a corollary of the encryption-at-rest trust property (`content-scoring.md` § The placement matrix, per-user-secret row): a scorer needing a per-user secret (the model) may run only where the message **plaintext** *and* the user's **unwrap capability** coexist. At inbound-MX-delivery time the recipient is unauthenticated, so that is *neither* nest (the body is sealed-to-recipient and, since Phase 3, nest holds no read key at all) *nor* the MTA (it has the recipient's *public* key only — enough to seal mail *to* them, not to unwrap their model). So scoring is **post-delivery**, mirroring how IMAP `SEARCH`'s body axis already works (`imap-server.md` § SEARCH). (The placement *rule* is owned by `content-scoring.md` § The placement matrix; this doc's mail instance:)

**Where scoring runs: post-delivery at the authenticated agent, uniformly — never at the nest, and never at ingest.** The **Fauna app** (post-decrypt) and/or the **AUTH'd MDA session** (covers third-party IMAP MUAs) ephemeral-unwraps the sealed model under the session MLS capability, scores, and re-files spam to Junk.

*(Retired the former "Plaintext mode / Encrypted mode" two-column framing of this row 2026-07-13, since the storage-mode axis itself is retired — `nest/storage-modes.md`. The old plaintext-mode cell read "nest, server-side at ingest — decrypts the stored body with the actor's nest-held MLS read key"; superseded 2026-07-08 by Phase 3 and now **un-implementable, not merely unbuilt** — Phase 3 seals mail at rest universally and retired the plaintext-MSEK custody that fed it (the `actor_plaintext_msek` table is DROPPED, S4b; `get/put_plaintext_msek` have zero call sites), so a nest holds no read key and cannot decrypt a body at all — `encryption-at-rest.md`: "Server-side classifiers / FTS no longer read plaintext at rest in any mode." The nest-at-ingest scorer for that retired posture was never built.)*

**One shared-Rust scorer, three positions.** The scorer is a pure function in `libs/fauna-mail/src/spam/` over the shared canonical-token n-gram features (§ Per-user model storage); it compiles to nest (native), the MDA (Go via the existing UniFFI/cgo `mailfauna.*` binding), and the apps (WASM / UniFFI), producing byte-identical scores at every position (`content-scoring.md` § The shared-scorer shape). The combined-score seam (`combined_spam_score_milli(rspamd_scaled_milli, weighted_bayesian_milli)`, `libs/fauna-mail/src/spam/mod.rs`) takes the already-weighted Bayesian value the scoring position computes (§ Combined-score formula).

**Forbidden shapes** (`content-scoring.md` § "Don't ship plaintext to the nest to score it" + § The placement matrix):

- **No `score(message_bytes) → nest` RPC.** Shipping the body to nest purely to score it recreates the exposure the perimeter carve-out bounds and would puncture the at-rest sealing property — regardless of deployment, now that the storage-mode axis is retired (`nest/storage-modes.md`; no posture makes this pointless-but-harmless any more, since the nest holds no read key at all — § Scoring placement).
- **No per-user scoring at the MTA / inbound-MX perimeter.** Only the deployment-wide pre-classifiers (rspamd, ClamAV — no per-user secret) run there; they feed the combined score's rspamd term.

**Re-file timing.** Mail lands in INBOX and moves to Junk when the authenticated agent next scores it (the user's client syncs, or the MUA's AUTH'd MDA session runs) — uniformly, since there is no nest-at-ingest scoring position (§ Scoring placement); a per-message **"scored" watermark** prevents re-scoring on every sync. This is the same post-delivery freshness property IMAP `SEARCH` already carries (not instant-at-ingest). **Timing bound (ratified 2026-07-07):** "next scores it" must complete **before the message is first shown** — the agent scores any unscored message before surfacing it, and a standing-grant bridge scores at ingest; rule + mechanism owned by `content-scoring.md` § Timing: scored-before-visible (a Phase-3 build item).

The MDA implements the watermark as an internal IMAP keyword `$FaunaSpamScored` stamped via `store_flags` after scoring (`spam_score.go`): it is nest-persisted in the `bridge_imap_messages` flags column (the same channel `\Seen` / `\Junk` ride), so it survives across sessions/restarts, and it carries verbatim on `COPY` / `MOVE` (RFC 9051 §6.4.7) — so a message the user moves back out of Junk into INBOX stays scored and is not re-Junked. It is visible to MUAs like any keyword; should that visibility ever matter, the watermark MAY migrate to an invisible per-message nest column without changing the scoring logic (a keyword is not user-irrecoverable data).

The MDA SELECT-time pass runs **synchronously inside `Session.Select`** (before the snapshot), so it is bounded two ways: a whole-pass timeout backstop, and a **per-pass count cap** (`spamScorePerPassCap`, `spam_score.go`) — at most N un-watermarked messages are decrypted + scored per read-write `SELECT INBOX`, scoring the **most-recent (highest-UID)** first and deferring the older tail to the next SELECT (the watermark makes the scan resumable). This bounds the latency a cold-start large/just-migrated INBOX can add to one SELECT; steady-state the cap never bites (only the few newly-delivered messages are un-watermarked). The cap is internal latency tuning, **not** a configuration surface — a hard-coded constant, never a knob (a future track MAY revisit the value, or move scoring async, before GA).

**The Fauna-app score-at-ingest flow (on-device).** A pure-web/app user who never opens a third-party IMAP MUA is covered by the Fauna app itself — otherwise their INBOX is *never* per-user-scored (the MDA path fires only on an IMAP `SELECT INBOX`). The client already decrypts every inbound body as it drains `fauna.email.inbox.fetch` (`WasmConversationsManager::ingest_sealed_inbound` → `open_inbound_record`, `libs/fauna-wasm/src/conversations.rs`), so it scores **at ingest** over the just-decrypted plaintext — the client-side twin of the MDA's `scoreSelectedInbox` (`spam_score.go`). Per drain pass it: (1) fetches its sealed model once (`fauna.bridges.fetch_spam_model`, unwrapped under the session MLS capability — the identical `wrapped_blob` shape as a body); (2) scores each drained INBOX message whose `flags` (new on `InboxMessage`) does **not** already carry `$FaunaSpamScored`; (3) issues **one** batch `fauna.email.apply_spam_disposition` — watermarking every scored UID and moving the spam subset INBOX→Junk (§ Wire shapes). A message the on-device scorer classifies as spam is **kept out of the client's inbox thread view at ingest** (not surfaced, since it is moving to Junk this same pass) — the client-side twin of the MDA moving spam out of INBOX *before* the `SELECT` snapshot, so the user never sees on-device-detected spam in their inbox. Because `inbox.fetch` is incremental (`uid > afterUid`) each message drains once per client, so scoring is naturally once-per-message even before the watermark; the shared `$FaunaSpamScored` keyword's real job is **cross-agent coordination** — a user running *both* a Fauna app and a third-party MUA has each message scored by whichever agent reaches it first, and the other skips it (the keyword is nest-persisted in the same `bridge_imap_messages.flags` column, visible to both — § the MDA watermark paragraph above). The client applies the same per-pass count discipline as the MDA for a cold-start / just-migrated INBOX. The **shared orchestrator** (fetch → per-message score → batch disposition) is `RpcRequester`-generic Rust so every native app lifts it unchanged (priority #2); the web SPA is the reference leg.

## Training signal sources

Four sources, all explicit. **No implicit signals.**

### 1. Explicit "Mark as spam" gesture (Fauna app first-party) — SHIPPED on the conversation surface

The shipped first-party gesture is the **sealed client-train path**, not a server-side relay: a per-message **"Mark as spam"** item in the conversation message ⋯ actions menu (`dm-message-mark-as-spam-button` inside `dm-message-actions-menu` — allocated in `ui.yaml`), gated `!is_own` (received messages only). Pressing it:

1. The client (which already holds the decrypted body) calls the shared façade `MailSettingsMachine::train_spam_model_client_mail(text, is_spam=true, message_id, mailbox, subject)` (`libs/fauna-client-mail-settings`; FFI/wasm twins `train_spam_model_client_mail` / `trainSpamModelClientMail`).
2. The façade unwraps the actor's sealed model under the session capability, applies the training delta locally, **re-seals the whole model**, and commits it atomically with a **sealed history row** via `fauna.bridges.put_spam_model{history_op: Insert{message_id, mailbox, sealed_subject, sealed_delta, label, source}}` — `source = ManualOther` (the ratified first-party-button wire source), `mailbox = "INBOX"` as the honest display default (a conversation message has no IMAP mailbox).
3. The write is gated on the nest's `spam-model-sealed-at-rest` capability token and **degrades silently to a no-op** when mail isn't enabled or the token is absent — a conversation message is client-only encrypted content the nest can't read, so there is **no** server-train fallback for it.
4. There is **no server-side message move** — the gesture trains the model; disposition of *future* mail is the scorer's job (§ Scoring placement).

**Status:** built + tier_3-proven on **linux**, built on **windows** (2026-07-07), and built on **apple** — macOS + iOS (2026-07-13, shared FaunaKit `DmMessageBubble` + `APIClient.markMessageAsSpam`; `just swift-test` green, no dedicated tier_3 GUI e2e this session); the **web**, **android** and **tui** legs have since landed on the same façade (web `routes/conversations/+page.svelte` `markAsSpam`, android `ConversationsVM.markMessageSpam`, tui `conversations/mod.rs` `dm-message-mark-as-spam-button`; status corrected 2026-09-19 — this line previously still called web/android open follow-ups), so the gesture is on all seven apps. An **INBOX-mail-surface** mark-as-spam trigger (for a mail-first message list view) is target-state — it rides the same façade when that surface exists.

### 2. Symmetric "Not spam" affordance — target-state

The inverse gesture (`is_spam=false` — a "Not spam" item on a Junk-filed message) is **not yet built** on any app surface. When it ships it rides the same sealed client path (`train_spam_model_client_mail(text, is_spam=false, …)`), training ham and leaving re-filing to the user / the scorer's next pass. Until then, the ham signal comes from source 3 (a MUA clearing `\Junk` or moving out of Junk) and from per-row **Undo** on the training history (§ Undo).

### 3. IMAP `\Junk` flag changes (third-party MUA path)

When a third-party MUA (Thunderbird, Apple Mail, Mutt, …) sets the `\Junk` flag on a message via IMAP STORE or moves a message into the `Junk` mailbox via IMAP MOVE / COPY, the MDA bridge fires the training signal automatically. See `imap-server.md` § Write surface + the cross-link section there to this doc.

The contract (the `train(message_id, label, source)` shorthand throughout this section identifies the *user-action event*: the AUTH'd MDA session trains the sealed model agent-side and writes it, with its sealed history row, in one `put_spam_model` — § Encrypted-mode interaction, § Wire shapes):

- **STORE +FLAGS (\Junk)** → `train(message_id, label="spam", source="imap_junk_flag")`. Message stays in its current mailbox (Thunderbird's "Mark as junk" doesn't move; it just flags). The client may follow up with a MOVE to Junk; that is a second signal for the same lesson, which the one-lesson rule below collapses.
- **STORE -FLAGS (\Junk)** → `train(message_id, label="ham", source="imap_junk_flag")`. Inverse.
- **MOVE / COPY into Junk** → `train(message_id, label="spam", source="imap_junk_move")`. Subsumes the `\Junk` flag-set that some MUAs pair with it (the one-lesson rule below collapses the pair to one training event).
- **MOVE / COPY out of Junk** → `train(message_id, label="ham", source="imap_junk_move")`. Inverse, same rule.

**The one-lesson rule (ratified 2026-09-25; replaces the former 1 s `(actor_id, message_id, label)` window).** A training signal is a **duplicate** when the actor's **newest** `spam_training_history` row for that `message_id` already carries the same label: the lesson is on record and nothing has un-taught it since. The key is causal, never temporal — a flag-set followed by a MOVE minutes later over a slow link is still one lesson, and a nest restart between the two forgets nothing; a later opposite-label lesson re-opens the key (spam → ham → spam is three lessons — the user changed their mind twice); an undo (§ Undo) deletes the row, so the next mark trains again; and retention GC (§ Training-sample retention) bounds the rule exactly as it bounds undo — a lesson older than the retention window is no longer on record. The rule runs **nest-side, on the one write entry point, and nowhere else**: a `put_spam_model` carrying a `history_op: Insert` (the agent-side `\Junk`-train and the first-party app gesture, § 1) answers `outcome: duplicate_signal` and rejects the **whole** atomic write — model, history row and holder copy alike — so the stored model is byte-identical to the last accepted write. It evaluates one SQL predicate (`CacheDb::newest_spam_training_label`); the MDA fires one event per wire action and never dedups (`imap-server.md` § `\Junk` flag-change ↔ spam-training contract). The rule is not the replay guard: the kind keeps `forbid_replay = true` (`transport.md`'s per-kind rationale), because an intervening opposite-label lesson re-opens the key and a stale replayed request would then train. Witness: `docs/features/spam.md` outcome 19.

The MDA recognizes `Junk` by its `\Junk` SPECIAL-USE attribute, not by the literal mailbox name — a locale-renamed Junk mailbox (e.g., "Корзина" or "Spam") still fires the signal as long as the SPECIAL-USE is set correctly. (Per `imap-server.md` § Standard mailboxes, `\Junk` is one of the reserved special-use mailboxes.)

The training-history row's `source` field distinguishes the four signal types so the user's history list can show "marked as spam in Thunderbird" vs. "marked as spam via the Fauna app."

### 4. Account-creation initial classifier (cold start, deployment-baseline opt-in)

Not user-initiated — this is the **cold-start path**. See § Cold start; the deployment-baseline-opt-in flow is a single signal source for new accounts the admin has chosen to seed.

### Implicit signals are forbidden

The classifier does **not** train on:

- Read-then-delete (the user may have read the message and decided to delete for any reason; spam is a strong claim).
- Time-spent-on-message (telemetry surface this doc explicitly rejects).
- Deletion-without-opening (could be the user clearing a known-good newsletter from yesterday).
- IMAP STORE \Seen / \Deleted flag changes (those are not spam-related signals — they're "read" and "deleted").
- Reply patterns (the user replying to a message is not a "ham" signal — they may be replying to a phisher).
- Auto-archiving rules (the user may have archived for ham reasons or for spam reasons; we don't know).

The long-term reason: false-positive rate is too high on implicit signals; the surveillance footprint (tracking every read / delete / archive event for training) is the wrong default for a privacy-respecting product. Explicit training is one extra click; getting it right matters more than the click.

**A block is not a spam verdict — the two orphaned preferences are removed (ruled 2026-10-02).** Blocking a contact (`fauna.knocks.block`) says *I don't want to hear from this sender*, not *these messages are spam*: a harasser, an ex, an over-eager acquaintance are blocked for reasons the classifier must not learn as content features, and the block itself already stops the sender, so a model that learns one sender's wording buys little and risks quarantining legitimate mail that reads alike. Auto-train-on-block is therefore an implicit signal in this list at every position — the nest-side form the universal seal removed (it trained every recent inbound message, not even only the blocked sender's, in plaintext — § Implementation status today item 4b) and the client-side form a capability holder could rebuild alike — and the `spam_preferences.auto_train` toggle that gated it is **removed, not rebuilt**: the wire field on `fauna.spam.{get,set}_preferences`, the column, and the `auto-train` control on all 7 apps (`../ui/settings.md` § Spam moderation). The four sources above need no toggle: a user who does not want to train does not mark, and a future *block and mark as spam* affordance would be source 1 applied by the client to the sender's messages it holds — an explicit per-gesture choice, never a standing preference. **`spam_preferences.share_model` goes the same way:** its one meaningful value, `"model_weights"`, gated the plaintext model upload the seal retired (`moderation.md` § State & data shape, the model-sync bullet), and the only sanctioned model sharing is the explicit, grant-minting, revocable `contribute_baseline` opt-in (§ Encrypted-mode interaction), which stays exactly as it is — two sharing toggles side by side, one dead, misrepresent what leaves the device. Both are a wire contraction and dead schema under the fourth ratified exception (`../architecture/version-compatibility.md` § Dimension 2; the repository is still private): nest schema 120 drops the two columns, `ratified-breaks.txt` names the four struct fields, and the shared `SHARE_MODEL_VALUES` presentation contract leaves with its UniFFI, wasm and Go faces. Build state: item 4b(c).

## Per-user model storage

Each actor has one per-user Bayesian model held **nest-side, keyed by actor** (the `spam_models` table), **sealed under the actor's MLS-derived recipient key** — the same shape as mail bodies and the per-message index hints: nest holds it opaque, and the authenticated scoring agent ephemeral-unwraps it (§ Scoring placement, § Encrypted-mode interaction). Built universally 2026-10-02 (§ Implementation status item 4b). A user without mail enabled holds no recipient key, so has no model: there is nothing to seal to and nothing that could read it.

The model is a Naive Bayes classifier over **shared-tokenizer** n-gram features:

- **Tokenization**: the **shared canonical tokenizer** (`libs/fauna-mail/src/tokenizer.rs` — deterministic NFKC + UAX#29 word-segmentation + Unicode case-fold), the *same* tokenizer search and the per-message index hints use, so spam / search / indexing never diverge on what a token is. n-grams 1, 2, 3 are built from the **positional token stream** (`tokenize_positional`, preserving order + repetition) — **not** the deduplicated `CanonicalTokenSet` index hint, which drops the adjacency and frequency the n-gram model needs.
- **Features**: subject + body (text/plain parts only — text/html is converted to text first, scripts stripped); envelope `MAIL FROM` domain; `Return-Path` domain; sender display-name if present.
- **Weights**: per-n-gram `(spam_count, ham_count)`. Classification at inference time: Naive Bayes with Laplace (add-1) smoothing — a smoothed log-prior plus each distinct in-message n-gram's log-likelihood ratio sum to a log-odds value, which the shared `bernoulli_posterior` primitive (`libs/fauna-text-model/src/classifier.rs`, shared with the topic-factors trainable model) maps through a logistic to a probability in `(0, 1)`; that probability × 15, in milli-units, clamped to `0..=15000` (`SpamModel::score`). An untrained model scores the neutral `7500`. The additive per-n-gram counts are what make the per-event **undo** (§ Undo) a clean inverse.

Serialization: **version-tagged `serde_json`** over a sorted `BTreeMap` (deterministic; `libs/fauna-mail/src/spam/classifier.rs`), forward-compatible (unknown fields are preserved on a verbatim store, ignored on decode). Implementation lives in shared Rust — the model core (`SpamModel`/`NgramCount`/`SpamLabel`) in the mail-independent `libs/fauna-text-model` crate (lifted 2026-07-09 to share with the topic-factors trainable-factor model; `topic-factors.md` § S1), re-exported at `libs/fauna-mail/src/spam/classifier.rs` so every existing `fauna_mail::spam::*` path is unchanged; nest, the MDA (via UniFFI), and the apps (via WASM / UniFFI) all link the same library. (The transitional nest-only `bayespam` engine was retired 2026-06-29 — `bins/fauna-nest/src/bayesian.rs` now wraps the shared `SpamModel`; § Implementation status.)

### Bounded size

The model is bounded by `mail.spam.model_max_bytes` (default 1 MiB). Above the cap, the **least-informative n-grams age out** — those with the lowest total `(spam + ham)` count — to bring the model back under cap (`SpamModel::cap_to_bytes`, applied on every per-user-model persist); the per-class message counters are never evicted, so `sample_count` and the confidence ramp are unaffected by capping. (Eviction is **count-based, not recency-based**: the model carries no per-n-gram timestamp, and the lowest-count n-grams are both the least statistically useful and the most numerous, so dropping them best preserves classifier accuracy under the cap.) A user with no training has a < 10 KiB cold model; a user with active training tops out around 200 KiB after ~1000 samples; the 1 MiB cap is comfortably above the active-user steady state, so eviction effectively never fires for a real user.

Above ~10 MiB the classifier's inference cost (load + n-gram lookup at delivery time) starts impacting per-message latency; the cap exists to defend against that. The **same cap is applied to the deployment baseline after its merge fold** (§ Cold start, Path 2) so the redistributed aggregate — which is sealed + scored on every cold-start fetch — can't bypass the per-message inference budget.

**Implementation status:** the cap is enforced today as the **constant default** `MODEL_MAX_BYTES_DEFAULT` (1 MiB, `libs/fauna-mail/src/spam/classifier.rs`). The allocated Tier-2 admin knob (`bridges-detail-mail-spam-model-max-bytes`, `mail-policy-config.md`) is still **"Bucket C"** — neither projected nor admin-writable; making the bound admin-tunable is a deferred follow-on (it would plumb through `SpamPolicyThresholds` the same way the `bayesian_*` knobs do). (The model has no per-n-gram recency, so the historical "least-recently-updated" wording could not be implemented without a schema change + model bloat; the count-based policy is the implementable equivalent and the one that fires.)

### Transactional update

Each training event runs at a capability holder (§ Encrypted-mode interaction): it fetches the sealed model, unwraps it, increments the per-n-gram `(spam_count, ham_count)` for `label`, re-seals the whole model, and writes it back with its sealed history row in **one** `put_spam_model`, which the nest commits **in one SQLite transaction** before acking.

The nest serializes every `spam_models` write under one DB connection lock, but a training event's read-mutate-write spans a fetch and a put at the capability holder, so two concurrent events on one actor (two MUAs, or an MUA and the app) can lose the earlier update: the later write re-seals a model it fetched before the earlier write landed, while both history rows stand. **Open:** a compare-and-swap precondition on `put_spam_model` (the writer names the stored blob it read; a mismatch refuses and the holder re-fetches). (The historical temp-file + fsync + rename description predates the DB-row store.)

## Cross-actor isolation

**Alice's training never affects Bob's classifier.** The per-actor model file is the boundary; no shared write path.

Specifically:

- A bridge names the actor whose model it writes (`put_spam_model`'s `actor_id`), but it is not caller-choosable: only the `BridgeMda` class may name another actor (trusted naming, bounded by `require_local_mail_serving`), and the bridge always sets it to the IMAP session's own AEAD-authenticated actor — never a value a served user or third party can steer to someone else's identity; a `User`/`Admin` writes only their own model.
- No RPC exists for a user or admin to train another user's model directly.
- The shared deployment baseline (see § Cold start) is **read-only** from each actor's perspective — a user's training never writes back to the baseline.
- An admin **cannot** view another user's model (every row is sealed to the user's own key — opaque to the admin and the box alike — and `fauna-nest`'s authorization layer denies non-self reads besides).
- The admin **cannot** train another user's model. Any "admin override" RPC would be a violation of the user-controls-their-data invariant.

## Cold start

A fresh actor has no `spam_models` row. Two paths:

### Path 1 — rspamd-only

By default (no deployment baseline published; see Path 2), a fresh actor uses **rspamd-only scoring** until they have ≥ `mail.spam.bayesian_min_samples` training samples (Tier 2, default 50). Below that threshold, the per-user score is clamped to 0; the combined score is just the rspamd score. The long-term question says: a 10-sample classifier is worse than no classifier — it overfits to its first samples, quarantines lookalike legitimate mail.

Above the threshold, the classifier's confidence ramps from 0 to 1 linearly between `bayesian_min_samples` (50, weight 0) and `bayesian_full_confidence_samples` (200, weight 1). Below 50: weight 0 (per-user score is ignored). Between 50 and 200: weight = (samples - 50) / 150. At 200+: weight 1.

### Path 2 — deployment baseline (admin opt-in)

The admin may publish a **deployment-wide baseline** by clicking "publish current aggregate model as deployment baseline" on the flat `admin-mail` admin page (`admin-mail-publish-spam-baseline-button` — now built on all 7 apps, 2026-07-01; § Implementation status item 3). The action is **off by default** per the user-controls-their-data invariant — publishing aggregates participating users' training samples into a deployment-readable model. To opt the admin in:

1. The admin clicks publish → admin's client opens a confirmation dialog explaining the consequence (the deployment gets a model that reflects the aggregate spam-training corpus of opt-in users).
2. Each contributing user must **opt in** before their training is included — the `mail-spam` page has a "Contribute to deployment spam baseline" toggle (`mail-spam-contribute-baseline-toggle`), defaulted off. Opting in is the grant gesture: the toggle also mints (and off revokes) the scoped `content.read{spam-model}` grant that lets the box's aggregation holder read this user's model — § Encrypted-mode interaction owns that rule.
3. Nest aggregates only opt-in users' n-gram weights into the deployment baseline. **Storage: the single-row `spam_baseline` table** — the DB sibling of the per-user `spam_models` table, holding the same `fauna_mail::spam::SpamModel` serde_json shape. (The earlier `<data-dir>/spam-models/__baseline.bin` *file* description predates the table-backed per-user model store; per-user models live in `spam_models`, not files, so the baseline shares that one canonical store. Implemented (tracked internally, § Slice 5).) Aggregation is the additive n-gram merge of the opt-in users' `spam_models` rows (`SpamModel::merge`), gated on `spam_preferences.contribute_baseline = 1`. **After the fold the baseline is bounded to `mail.spam.model_max_bytes` the same way a per-user model is** (§ Bounded size — `SpamModel::cap_to_bytes`, dropping the least-informative n-grams), so the merged aggregate — which is the union of every contributor's n-grams and is sealed + scored on every cold-start fetch — can't exceed the per-message inference budget even when a contributor's own model approached the cap.
4. The baseline is **read-only** from each per-actor classifier's perspective. At scoring time, `fetch_spam_model` merges the published baseline into the actor's returned model as a **faded read-time prior** (the fold runs at the scoring agent over the sealed model, via the additive `baseline` reply field; for an actor with no stored model the nest folds the baseline onto a fresh model and seals the result on read, never persisting it — § Encrypted-mode interaction): the baseline contributes `(bayesian_full_confidence_samples − own_sample_count) / bayesian_full_confidence_samples` of its weight (clamped to `[0, 1]`; the merge is `SpamModel::merge_scaled`). The effect:
   - A **fresh** actor (0 own samples) inherits the **full** baseline (fade fraction 1). Its merged `sample_count` is the baseline's, which lifts the cold-start clamp (§ Combined-score formula) so the baseline's weights govern its scoring — "inherits the baseline as a starting point."
   - As the actor trains, the baseline **fades out exactly as the actor's own model ramps to full confidence** (`bayesian_full_confidence_samples`, default 200). The fade compensates the confidence ramp at every own-sample count, so there is **no cold-start cliff** — a conditional all-or-nothing merge (merge only below `bayesian_min_samples`) would zero the per-user term right at the threshold the user just earned; the faded merge keeps protection continuous.
   - At/above full confidence the baseline contributes **nothing** — the actor's own model fully governs. So a user can always train their filter to **override** the baseline (the *user-controls-their-data* invariant); a large baseline never permanently swamps a user's own ham-training.

   The merge is **read-time only**: the user's own training writes only to their own `spam_models` row; the baseline is never stored into it. No baseline published (or an actor already at full confidence) ⇒ no merge — the actor's own model, or rspamd-only cold start (Path 1). *(Decided Slice 5b (tracked internally), choosing the faded prior over both the naive conditional merge — which has the cliff — and an unconditional full merge — which violates user-control by swamping own training.)*

The user retains full control: they may opt out at any time, and they may delete their own model anytime. Either takes their counts out of what the deployment serves **at once**, not at the next republish — *A contributor's departure withdraws the baseline*, below, owns that rule. The admin cannot view individual contributions — the baseline is the only readable artifact, and the n-gram weights inside don't identify which users contributed.

**k-anonymity floor (BASELINE-KANON).** The "weights don't identify contributors" property only holds with several contributors — a baseline aggregated from a **single** (or near-single) opt-in contributor approximates that one user's model. So publishing is gated on a **minimum-contributors floor**: `publish_spam_baseline` publishes a real baseline only when at least `fauna_mail::spam::BASELINE_MIN_CONTRIBUTORS` (= **3**) opt-in contributors merged; below the floor it **withholds** — publishing an empty baseline that *withdraws* any prior one (the same "withdraw" the zero-contributor case takes, so opt-outs that drop a deployment below the floor also remove the served baseline), and the deployment falls back to rspamd-only cold start. The reply's `published: bool` is `false` when withheld, so the admin UI surfaces "not published — too few contributors". The floor is a **hard-coded safety constant, deliberately NOT a client knob**: it is a privacy *floor*, not a deployment *preference* anyone would tune (`principles.md` § One configuration surface) — `3` is a conservative minimum that defeats the degenerate single-/two-contributor case while permitting a baseline on any non-trivial deployment. *(Decided with the user 2026-07-01, choosing the hard-coded safety floor over an admin-configurable `K`; supersedes the earlier "K is an admin choice → client knob" framing.)* The related **BASELINE-POISON** tension — the admin cannot identify or exclude a deliberate poisoner — remains accepted; revisit only if a deployment enables a non-zero `reject` tier.

**Not sybil-resistant.** The floor is a *count* of opt-in contributors whose model decodes — it defeats the *natural* degenerate case (the contributor query joins `spam_models`, so an opted-in-but-untrained account with no model row never counts, and a lone honest contributor cannot reach 3), but it is **not** resistant to a *deliberate* sybil: an actor who enrolls and opts in `BASELINE_MIN_CONTRIBUTORS − 1` (= 2) trained — even trivially-trained — models alongside one real victim forces `contributors ≥ 3` and publishes a baseline that still approximates the victim's model. A count-based floor cannot distinguish sybils from honest contributors; a fully sybil-resistant floor needs enrollment/identity assumptions this deployment does not make (same caveat class as **BASELINE-POISON**, above). So the floor is a privacy *floor* for the honest-majority case — **not** a hard k-anonymity guarantee against a motivated attacker — and a future session should not over-trust it as one. Accepted; revisit alongside BASELINE-POISON if a deployment enables a non-zero `reject` tier.

**A contributor's departure withdraws the baseline (ruled 2026-09-21, refutable-advisory; it supersedes the earlier "drops from the next republish" wording here and in § Wire shapes).** The published baseline is a *sum*, and a sum cannot hand one contributor's counts back: the nest could not subtract a model that has since been retrained, reset or client-sealed, and the published singleton names nobody (deliberately — the paragraph above). So the only way to stop serving a departed contributor's counts is to stop serving the sum. **Rule: the moment a *summed contributor* departs — an actor holding a non-departed row in the inclusion record (*The floor applies to every published DELTA*, next paragraph), i.e. one whose model the last served publish actually summed — the nest marks that row departed and withdraws the published baseline**, and the deployment falls back to rspamd-only cold start (Path 1) until an admin publishes again, which rebuilds from the contributors then standing. **An actor with no such row withdraws nothing** (narrowed 2026-09-22, refutable-advisory): one who opted in or first trained after the last served publish, a sealed contributor that publish skipped (`skipped_contributors`), or one whose row a previous departure already marked — none of their counts is in what the box serves, so there is nothing to stop serving. (The exception once kept for a baseline served before the record existed went with the compat-remnant sweep, 2026-09-30: every served baseline since the genesis was published with its record.) The inclusion record is exact where a standing-since timestamp beside the opt-in would not be: an actor standing at publish time whose sealed half the run skipped was never summed. **Four departures, one rule:** (1) **account deletion** — the purge walk; (2) **opt-out** — `set_baseline_contribution(false)`; (3) **model reset** — `reset_spam_model`, the model that was summed is gone though the opt-in stands; (4) **revoking the `content.read{spam-model}` grant** — the read the counts were summed under. **Not departures:** a **succession** (the model and the opt-in both *move* to the successor, so the same person stands as the same contributor; only the sealed holder copy burns, and the successor's next write re-seals it), and a standing contributor's further training or undo (the sum is a snapshot of a contribution still consented to; the next publish refreshes it). **Why withdraw rather than let the counts ride until the next publish:** *(a)* a delete or a revoke takes effect when the **user** makes it, not when an admin — who cannot see who contributed, and may never return — next clicks; it is the rule that has a revoked materialization grant delete its derived views (`principles.md` § The user always controls their data) and an opt-out of report sharing recompute its aggregates immediately ([`report-sharing.md`](report-sharing.md)). *(b)* It needs **no contributor ids in `spam_baseline`**: it is keyed on the *departing* actor's own actor-keyed rows — their inclusion row, never served — at the moment of departure, which is also its one ordering constraint: **the withdrawal runs BEFORE the departure destroys that row**, so the purge walk withdraws first and deletes second, and a crash between the two leaves a withdrawn baseline and a retried deletion, never a deleted contributor behind a served sum. *(c)* A **serve-time check of the standing-contributor count was weighed and rejected**: it counts heads, not membership, so it would hide the old sum when three contributors became two and *re-serve it, departed counts included*, the moment any new opt-in made it three again. Withdrawal erases the sum rather than hiding it, so a later opt-in has nothing to resurrect. *(d)* A **rebuild fired BY the departure was weighed and rejected, and stays rejected under the standing choice**: it needs the holder drain (§ Encrypted-mode interaction), so it cannot run inside a deletion, and it would publish a sum differing from its predecessor by exactly the departed contributor's model — the sharpest case of what the delta floor (next paragraph) exists to refuse. A withdrawal reveals nothing; the nest's own publish runs on its cadence, never on a departure. **Accepted costs.** *Deliberate withdrawal*: a summed contributor may withdraw the baseline on purpose — a sender who wants this nest's cold-start users to see more spam has the motive — and nobody can attribute it, because the admin read carries no withdrawal reason (*Standing publish*, below). That is the departure right itself, and it is bounded: once per served publish the actor was summed into, since the departure marks their row and to withdraw again they must be summed again, by a publish that clears the delta floor. An actor never summed cannot withdraw at all *(this closes the earlier current-standing predicate's hole, under which any mail user could train once, opt in and straight back out, and withdraw the baseline after every publish; it had been accepted as over-withdrawal in the safe direction, on the premise that the nest keeps no record of who was summed — the inclusion record is that record)*. *Availability*: a departure costs the deployment its baseline until the next publish lands — an admin's, or the nest's own under the standing choice (*Standing publish*, below), and either one only once the delta floor lets it. *No recall*: every agent that fetched the aggregate still holds it — withdrawal bounds what the box serves and keeps from now on, never what it already handed out. **Shape:** withdrawn = the `spam_baseline` row absent, indistinguishable from never-published; the publish's own below-floor withhold keeps writing its empty model, and both serve nothing on both serving paths. The table has no actor column and so no `ACTOR_TABLES` row; its ruling is carried where a registry-less carrier's is — the declared entry in `db/actor_tables/tests/opaque_carriers.rs`, which cites this paragraph ([`opaque-carrier-walks.md`](opaque-carrier-walks.md) § The declared re-point axis).

**The floor applies to every published DELTA, not only to every published sum (the delta floor; ruled 2026-09-21, refutable-advisory).** Every user is handed each published aggregate in plaintext (§ Encrypted-mode interaction), so anyone can keep one baseline and subtract it from the next — no sybil, no privilege, no activity on the box. What the subtraction yields is the sum of whatever changed in between: a *join* yields the joiner's model, a *leave* the leaver's, and between two publishes over the same members, the recent training of whoever trained. The contributor floor above makes a published *sum* unattributable among at least three people; without the same rule on the *difference*, that protection lasts exactly one publish. **Rule: a publish that follows an earlier served baseline lands only when the contributions of at least `BASELINE_MIN_CONTRIBUTORS` (3) contributors changed since that baseline was built** — a change being a contributor joining, a contributor departing, or a standing contributor's model having been written since it was last summed. Below that the publish is **deferred**: nothing is written, the box keeps serving what it had (the earlier baseline if it still stands, nothing if a departure withdrew it), and the run reports `deferred`. It binds the admin's click and the nest's own run alike, and a deployment's first publish is bound by the contributor floor alone (its delta from nothing *is* the sum). The reference survives a withdrawal — a departed contributor's baseline is gone from the box but not from whoever fetched it, so the next publish is measured against the last one *served*, not the last one standing. **What it costs in state, and why that is not the record the departure rule refuses to keep.** Counting changes needs to know what was last summed: a nest-internal **inclusion record**, one row per contributor of the last served publish (the actor id + the `spam_models.updated_at` that was summed; a departure that leaves the account standing marks its row departed rather than deleting it, so leaving and rejoining before the next publish counts once), plus a never-decremented-between-publishes count of inclusion rows an account deletion purged. It is an actor-keyed table and so an ordinary `ACTOR_TABLES` row (Purge; Move — it follows the model and the opt-in), it is **never served to any client, the admin included**, and it tells the nest nothing it does not already hold at rest — the opt-in bit and the model row are per-actor today. The published singleton still names nobody. **Honest bounds.** Unattributable is not hidden: a token only one contributor ever trained shows in the sum and in the delta with that contributor's counts, exactly as under the contributor floor — both floors bound *who*, never *what*. And it is a count, so it inherits the sybil caveat above unchanged: two controlled accounts toggling around one victim's departure satisfy it. A small deployment will see publishes deferred for as long as fewer than three contributors are active; that is the floor working, and rspamd-only cold start (Path 1) is the fallback it always was.

**Standing publish — "this deployment keeps a baseline" is an admin choice, not a click that decays (ruled 2026-09-21, refutable-advisory; UI ids approved 2026-09-25 — `admin-mail-spam-baseline-standing-toggle` and the read-only `admin-mail-spam-baseline-state`, per-app build in § Implementation status today).** Once a departure can withdraw the baseline, a one-shot publish gesture leaves a deployment baseline-less most of the time, and there was never a gesture to *stop* publishing at all. So the choice is state: a Tier-2 admin setting in the spam policy ([`mail-policy-config.md`](mail-policy-config.md) § Spam owns the row), **default off**. **On:** the nest runs the publish itself on a fixed cadence — `BASELINE_REPUBLISH_INTERVAL`, a Rust constant of 24 hours, not a knob (nobody wants to choose it) — and each run is an ordinary publish bound by both floors. A run is *admin-less*, not *holder-less*: it is the same run the admin's click starts (§ Encrypted-mode interaction — register a pending run, poke the one resolved holder, await its submit with the bounded timeout, fold the two halves), and a holder that does not answer costs that run its sealed half, reported as `skipped_contributors` exactly as today. The cadence is decoupled from departures on purpose: a run never fires *because* someone left. **Off:** the nest stops running publishes **and withdraws the standing baseline** — the unpublish gesture the feature lacked. The admin's publish control stays as "publish now", bound by the same floors, and works with the setting off exactly as it always has. **What the admin can read** is the baseline's current state, never its history: an admin-only read returns `{published, contributors, sample_count, published_at, skipped_contributors, deferred, standing}`, rendering as "published over N contributors on <date>", "no baseline published", or either with "waiting for more contributor activity" when the last run was deferred. It deliberately carries **no withdrawal time and no withdrawal reason**: "withdrawn at T because a contributor left" beside an account deleted at T tells a small deployment's admin who was contributing, and *A contributor's departure withdraws the baseline* ruled withdrawn indistinguishable from never-published — that holds at this surface, the inclusion record being internal. No schema is owed for the published half (`spam_baseline` already carries `contributors` + `published_at`).

The opt-in framing reverses Gmail's default: there, all users implicitly contribute to a system-wide model; here, users explicitly choose, and the default is none.

## Reset

The `mail-spam` page → "Reset spam classifier" button (`mail-spam-reset-model-button`). The flow:

1. User clicks button.
2. Confirmation dialog: "This will delete your spam-training model and your training history. Future spam classification will start from scratch. This cannot be undone."
3. User confirms.
4. Client calls `fauna.bridges.reset_spam_model(actor)`.
5. Nest deletes the actor's per-user model (the sealed `spam_models` row) and all `spam_training_history` rows for the actor.
6. Nest emits a `BridgeSpamModelReset { actor_id }` push event (the user's other open app surfaces clear their training-history list).

Subsequent inbound mail uses cold-start logic (deployment baseline if the user opted in and the admin published one, else rspamd-only) until the user has ≥ `bayesian_min_samples` fresh training samples.

The reset is **irreversible**. No "undo the reset" — once weights are gone, they're gone. (A future "model snapshot before reset" feature could change this, but the long-term question says: reset is a deliberate destructive action with a clear contract; soft-reset would obscure the contract.)

## Training-sample retention

Per-message training labels persist in `spam_training_history` rows for 30 days (admin-tunable via `mail.spam.training_history_retention_days`, Tier 2, default 30):

| Column | Notes |
|---|---|
| `history_id` | UUID |
| `actor_id` | the user |
| `message_id` | the trained message's stable 32-byte content id (the `bridge_imap_messages` placement key) — the identifier the train RPC carries, not the RFC `Message-ID:` header. |
| `mailbox` (`mailbox_at_train_time`) | which mailbox the message was in when trained (`INBOX` / `Junk` / etc.), captured at train time from the placement lookup. |
| `sealed_subject` | the message's `Subject:` **sealed to the actor's own recipient key** by the writing capability holder (the `wrapped_blob` shape; an empty subject still seals to non-empty ciphertext) — `NOT NULL`, nest-opaque (it holds only the actor's public half). Returned on the list reply so a client renders `{unwrapped subject} · {mailbox}`. |
| `label` | `spam` / `ham` |
| `source` | `imap_junk_flag` / `imap_junk_move` / `manual_other` — the complete wire set (`TrainingSource`, `libs/fauna-protocol`). **`manual_other` is the ratified first-party-button source** (the shipped mark-as-spam gesture writes it — § Training signal source 1; ruled 2026-07-08, no `explicit_button` protocol variant is coming). The baseline is a read-time merge, never a per-message train event, so it has no source value either. On the client *display* enum, `ManualOther` projects to `ExplicitButton`, so first-party rows render "Fauna app" (`rpc_glue.rs::project_spam_history`; until 2026-09-25 it projected to `Other`, and the app's own lessons read "Other"). The client enum carries exactly the three wire sources (its dormant `ColdStartBaseline` and `Other` arms, with their `mail_spam.source_cold_start_baseline` and `mail_spam.source_other` strings, left 2026-10-01). |
| `model_delta_applied` | the distinct n-gram set the event added (`SpamModel::delta_ngrams`, serialized via the model's own `serde_json` codec) **sealed to the actor's own key**, nest-opaque. For a Bernoulli per-message event this *is* the complete forward delta — each listed n-gram +1, plus +1 to the class message counter — so the client-side undo unwraps it and replays its exact inverse (`SpamModel::apply_inverse_delta_ngrams`; § Undo). |
| `created_at` | wall-clock |

After 30 d the row is GC'd: the n-gram weight delta is permanent (the weights remain in the model file), but the per-message audit trail is gone. The user can no longer undo specifically that training event after 30 d; their only resort is reset-and-retrain.

**Grant-reach + consent interaction (ratified 2026-07-13 — the consent copy had understated the reach of the artifacts derived from a mail grant).** A `content.read{mail}` grant's key also opens the spam model and these history rows (`key-material-hierarchy.md` rule #7 — same recipient keypair, a crypto fact no app layer can durably exclude without new key material). Two rulings: **(1)** the user-facing mint-time / grant-log copy for the mail scope MUST name the derived reach in user voice (mail *and the spam-filter model and training history derived from it*) — **built the same day:** `nests.scope_mail` / `nests.mint_option_mail` (`i18n/strings/en.yaml`) carry that copy, live on all 7 apps via the shared generation pipeline (no per-app work needed); **(2)** the retention divergence — history rows reaching subjects of since-deleted mail for up to `training_history_retention_days`, and the model's n-grams persisting indefinitely — is **accepted as designed**: purging history on mail delete would break the undo contract this section exists for, and a separate history key would be a disproportionate re-key for this; the accurate consent copy is the fix. The app-layer mail/model/history split for the live holder keeps its planned crypto-free shape; a negative test that a mail grant never surfaces a non-mail drain row rides the next drain-plane change.

**Every row rests sealed (built 2026-10-02, § Implementation status item 4b).** A row is written only by a capability holder, atomically with the model write it records (`put_spam_model`'s `history_op: Insert`, which the nest refuses without a sealed subject and a sealed delta); the nest stores both opaque and returns them verbatim on `list_spam_training_history`, and an undo's inverse is applied where the key is (§ Undo).

### Undo

The training-history list (`mail-spam-training-history-list`, indexed component on the `mail-spam` page) renders the most recent N rows (default 100, paginated). Each row has an **Undo** button:

1. User clicks Undo.
2. The client — through the shared `MailSpamMachine` — unwraps the row's sealed forward delta (returned verbatim on `list_spam_training_history`) under the actor's own key, applies its inverse to the unwrapped model (decrements `spam_count`s if the row labeled spam, etc.), and re-seals the model.
3. The client writes the re-sealed model and the row's deletion in **one** atomic `fauna.bridges.put_spam_model{history_op: Delete{history_id}}` — never one without the other (an inverse applied twice corrupts the model).
4. Nest emits a `BridgeSpamModelUpdated { actor_id }` push event so other open surfaces refresh.

If the user has trained the same n-gram multiple times since the row in question, the undo applies cleanly (Bayesian counts are additive; subtracting one event's contribution leaves the others intact).

(Caveat: if an n-gram in a stored delta was since **aged out** by the size cap (§ Bounded size — only at the >1 MiB extreme, where the model is already lossy), undoing that event is a no-op for that n-gram — `apply_inverse_delta_ngrams` saturates at 0 and skips an absent n-gram. The message-counter decrement still applies, so the per-event undo stays consistent; only the aged-out n-gram's count isn't restored.)

## Combined-score formula

```
combined_score = max(rspamd_score, weighted_bayesian_score)
weighted_bayesian_score = bayesian_score * confidence_factor * bayesian_weight
confidence_factor = clamp((sample_count - bayesian_min_samples)
                         / (bayesian_full_confidence_samples - bayesian_min_samples),
                          0.0, 1.0)
bayesian_weight = mail.spam.bayesian_weight (default 0.7)
```

The formula constants ride Tier-2 knobs whose rows (tier / binding / surface / defaults) are owned by `mail-policy-config.md` § Spam + § Inbound perimeter: `mail.spam.{bayesian_weight, bayesian_min_samples, bayesian_full_confidence_samples}` (defaults 0.7 / 50 / 200 — the values used in the formula above) and the two disposition tiers `mail.inbound.max_score_before_{spam_folder, reject}` (defaults 5 / **0 = disabled**).

The score is carried on the wire in **milli-units** of the 0–15 scale (1.2 → 1200) because dag-cbor forbids floats; the tier thresholds are integer points, compared after scaling to milli. **`0 = disabled`** for a tier (the reject tier's default) — see § Routing decision for the permissive auto-Junk default.

**Why `max(rspamd, bayesian)` and not a weighted sum**: rspamd's score reflects deployment-wide rules + RBLs; the Bayesian's score reflects user-specific signal. Either one going hot is enough to mark as spam — they shouldn't cancel each other (a peer claiming "this is legitimate" shouldn't override the user's "I've marked 20 messages like this as spam"). The maximum captures the "at least one classifier flags it" semantic.

**Why `bayesian_weight = 0.7`**: a Bayesian score of 15 (the max) only contributes a combined score of 10.5 — a damper so even a strongly user-flagged feature won't dominate the deployment-wide signal. (With the permissive default the `reject` tier is disabled anyway, so a user-trained model can only route to Junk; the damper still matters once an admin opts into a non-zero `reject` threshold — it keeps a single-user-trained model from triggering 550 rejects to the world, which needs rspamd's deployment-wide signal too.)

**Why the linear confidence ramp**: between 50 and 200 samples, the classifier transitions from "no signal" to "full signal" smoothly. A step function at 50 would cause a discontinuity (mail at sample 49 lands in INBOX; same mail at sample 51 lands in Junk). Linear ramp avoids the discontinuity.

## Unlisted-recipient penalty

A **recipient-trust** term for the recipient-whitelist model (`mail-aliases.md` § Bulk import): the whitelist *is* the user's exact-alias set, so any mail to an address **not** on the whitelist — never-registered *or* dropped (a dropped address is deleted, so it is unknown and falls through the resolver to the catch-all) — is treated as spam. One additive term composes on top of the combined score:

```
effective_milli = max(rspamd_scaled_milli, weighted_bayesian_milli)
                + (recipient_unlisted ? unlisted_recipient_penalty * 1000 : 0)
```

- **`recipient_unlisted`** is true iff the delivery carries the `X-Fauna-Address-Catchall` header (`libs/fauna-mail/src/aliases/mod.rs`, stamped by the resolver on any catch-all match — exactly the "not on the whitelist" case). Content scoring still composes, so an "Earn $$$" blast to a *listed* address is still caught by rspamd/Bayesian.
- **`unlisted_recipient_penalty`** is a **deployment-wide admin knob** — a field on `SpamPolicyThresholds` (`mail-policy-config.md` § Tier 2), in **points**, **default `0` (opt-in / off)**. Small (e.g. `3`) tips borderline mail into Junk; large (e.g. `1000`) dominates any tier → guaranteed Junk. Deployment-wide, not per-user, because every disposition threshold is deployment-wide and there is exactly one catch-all actor per domain (spec §4.3).
- **Where applied — the Go MTA per-recipient delivery loop** (`bins/fauna-bridges/internal/mta/server.go`), **not** `decide_spam_disposition` and **not** the post-delivery agent scorer. The message-global disposition is computed once *before* per-recipient alias resolution, and the catch-all stamp is a **per-recipient** fact (`rcpt.headersToStamp`); so per catch-all recipient the loop recomputes `penalized_milli = combined_milli + penalty*1000` (shared helper `fauna_mail::spam::apply_unlisted_recipient_penalty_milli`, mirrored Go-side), re-runs the disposition, and files *that* recipient's copy accordingly. Non-catch-all recipients keep the message-global values.
- **Tier interaction:** with `reject` at its default `0` (off), a catch-all penalty can only reach the spam-folder tier → **Junk**. If an admin enabled the reject tier and the penalty carries a recipient's score over it, that recipient's copy is still filed to **Junk**, never refused: the message-global reject already answered at DATA, and refusing one recipient of a multi-recipient message afterwards would be backscatter. So the penalty's only outcome, at any setting, is Junk.
- **Both strategies, for free, via the existing catch-all toggle:** catch-all set to self + penalty > 0 → unlisted mail **delivered to Junk** (soft, reviewable — the default); catch-all *unset* → unlisted mail **bounced `550`** at the door (hard whitelist) and the penalty is inert (nothing delivered to score). The user picks via the existing per-domain catch-all designation (`mail-aliases.md` § Kind 4 — admin-tier).

## Encrypted-mode interaction

> **On the capability axis (the frame's target expression).** The seal-and-capability-holder-mutate shape below is the tier-1 rule of [`../architecture/content-moderation-and-ranking.md`](../architecture/content-moderation-and-ranking.md) § Sealing tier-1: the per-user model is a *per-user secret*, so the nest can never read / score / train / undo it in-process — every mutation runs at a **capability-holder** that holds the user's key: the user's **client** (post-decrypt, key held directly), the **AUTH'd MDA session** (session-scoped MLS capability), or a **content-processing bridge** holding a user-minted `content.read{mail}` + `content.label-write` grant (the general primitive of (design ratified 2026-07-04; tracked internally), of which the AUTH'd MDA session is the first instance). (The storage-mode axis this section once split on is retired — `encryption-at-rest.md` § The sealed posture; `nest/storage-modes.md` — so custody keys off this one capability axis alone.) **Built universally (2026-10-02, § Implementation status item 4b):** every model and every training-history row rests sealed; the nest stores what a capability holder sealed, refuses anything else, and mutates nothing.

The per-user model is sensitive: training samples are partially recoverable from n-gram weights (an attacker reading the model could reconstruct the lexical features of the messages the user trained on, though not the message content verbatim). The model is **sealed under the actor's MLS-derived key — the same wrapped-blob shape as mail bodies and the per-message index hints**; nest holds it opaque and unwraps nothing.

**Scoring placement is uniform — see § Scoring placement (the storage-mode axis is retired, `nest/storage-modes.md`; there is no second placement to split on).** Per-user scoring is **never** run at the inbound-MX / MTA perimeter: at delivery the recipient is not authenticated, so the bridge holds only their *public* key (enough to seal mail *to* them) and **cannot unwrap their sealed model** (`content-scoring.md` § Input classes, per-user-secret row). Instead — exactly like IMAP body `SEARCH` — scoring runs **post-delivery at the authenticated agent**: the **Fauna app** (post-decrypt) and/or the **AUTH'd MDA session** runs the shared scorer: it ephemeral-unwraps the actor's sealed model under the session-scoped MLS capability (the same capability the MDA already uses to open per-message index hints for body `SEARCH` and the `\Junk`-train body — `imap-server.md` § SEARCH), scores the decrypted body, and re-files spam to Junk. The third-party-IMAP-MUA user is covered by the MDA path; the Fauna-app user by the client path. *(A nest-server-side-at-ingest scorer over a plaintext-stored body — the former "plaintext mode" cell — was never built for that retired posture, and per Phase 3 (`encryption-at-rest.md` § The sealed posture) is now un-implementable — see § Scoring placement's own note.)*

Training at user-action time (mark-as-spam button, IMAP `\Junk` flag/move) is symmetric: the authenticated agent holds the unwrapped message bytes and unwraps the model under the same capability, applies the additive n-gram delta, and re-seals. (See § The write shape: the whole re-sealed model for the wire evolution.)

The model never persists unwrapped on nest disk (built — § Implementation status item 4b). The unwrapped copy lives in the scoring or training agent's worker memory for the duration of the operation, then drops with its stack frame; the scoring output is byte-identical at every position (one shared classifier).

**Delivery to the device — `fauna.bridges.fetch_spam_model` (§ Wire shapes).** The scoring agent gets the model the same way it gets a body: a self-scoped fetch returns the stored model — sealed to the actor (the `fauna_mls::wrapped_blob` shape) — **verbatim**, and the agent unwraps it under its session MLS capability. nest holds only the actor's *public* half, so it can seal *to* the actor but never reads back what any holder sealed, and the raw model never crosses the wire. The one blob the nest seals itself is the **cold-start seed** of an actor with no stored model: the published baseline faded onto a fresh model, sealed on read and never persisted (`stored_sealed = false`; a train position starts from an empty model instead — § Cold start Path 2, the fold is read-time only).

**The deployment baseline is grant-mediated: contributing = minting a read grant on your own model** (`publish_spam_baseline`, § Wire shapes; **ratified with the user 2026-07-12**, superseding the 2026-07-02 option-(b) "plaintext-nest-only" rule, whose mode antecedent the storage-mode retirement — Phase 4, `../architecture/nest/storage-modes.md` — removed; the capability plane that decision predated now exists and is the substrate here). Aggregating opt-in users' per-user models is a *cross-user* read with no single-client fallback (no one user's client holds the others' keys), so per [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Capability tiering it runs only at a position holding a reaching capability from **each opt-in contributor** — opting in *is* granting read of the contributed artifact. Concretely:

> **✅ KEY-SHAPE RESOLUTION (ratified 2026-07-13; refutable-advisory) — `content.read{spam-model}` is a KEYLESS scope, and the contributed artifact travels sealed-to-the-holder (the R2 (account-data-plane.md § The ratified decisions) shape of the gap found earlier the same day).** The gap, in one line: a client-sealed spam model is a `kind: "mail-record"` envelope sealed to the **recipient-mail keypair**, and the `content.read{mail}` payload *is* that secret byte-for-byte — so no `WrappedScopeKey` payload could make a spam-model scope narrower than `content.read{mail}` (mechanism + enumeration owned by [`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) rule #7 + § Don't do these, which names the two honest options). **Resolution — the keyless shape (R2), rejecting the own-derived-key shape (R1), on five grounds:** (1) *minimality by construction* — the holder opens contributor copies with its **own** service-user key and never holds key material of the user's; an R1 grant would convey a standing user-derived secret which, absent a content-sealing epoch (`encryption-at-rest.md` § Capability tiering's honest bound), outlives revocation if exfiltrated, whereas revoking R2 (stop serving + delete the copy) is airtight for all future content; (2) *no at-rest migration* — the user's own model keeps resting exactly as today (R1 would lazily re-key the shipped sealed back-catalogue, dropping contributors from the baseline until their next write); (3) *no new key material or provisioning* — R2 composes two built patterns: the keyless scope (`derive_scope_payload` → `None`, the `content.label-write` shape) and the HPKE-seal-to-bridge-service-user shape (`TlsCertBlob`; `fetch_bridge_pubkey` is already `User`-callable); (4) *audience hygiene* (`key-material-hierarchy.md` rule #2) — the model stays in the owner-only audience and the copy sits in the existing deployment-infrastructure audience, instead of R1 minting a key with a smeared "owner + granted holders" audience; (5) *freshness is sufficient* (checked against § Cold start Path 2) — every sealed-model write path runs at a capability position that re-seals the holder copy atomically with the model write, so the worst case (a v-older client writing model-only) is slightly-stale weights for that contributor, still counted. **Concretely:** the grant carries **no key**; the contributor's client/agent seals a **copy of the model** to the aggregation holder's published X25519 pubkey (`fauna.bridges.fetch_bridge_pubkey`) at opt-in and re-seals it on every sealed-model write while opted in (atomically with `put_spam_model`, an additive optional field); the copy rests nest-opaque beside the `spam_models` row (`key-material-hierarchy.md` § Audience: deployment infrastructure → Spam-baseline holder copy) and is served to the holder only while the grant stands; toggle-OFF / grant revoke / model reset deletes it. The grant is still minted — it is the audit + revocation record in the Nests grant log **and** the authorization the publish worklist is gated on (`holder_granted_scopes`), the same load-bearing keyless role `content.label-write` already plays on the drain's submit path — it just conveys no key material, which is the point. **Corollary, still true and accepted:** the existing `content.read{mail}` grant *already* opens every contributor's spam model and training history (rule #7's enumeration; graded defensible-but-undeclared, and routed onward for the live-grant judgment).

- **The opt-in toggle is the grant gesture.** `mail-spam-contribute-baseline-toggle` ON ⇒ the client sets `contribute_baseline`, **mints a keyless `content.read{spam-model}` grant** (the built GrantBlob plane — `fauna.capabilities.mint`, the same substrate as the re-score drain's `content.read{mail}`, with an empty `WrappedScopeKey` payload per the resolution above) to the box's aggregation holder — **the single approved off-box service user of the content-processor family, resolved by deterministic preference: a dedicated `ContentProcessor`-role holder when one is enrolled, else the mail MDA** (`resolve_content_processor_holder`; **holder ruling 2026-08-03, refutable-advisory**, closing the missing-holder gap). The ruling *restores* the identity the 2026-07-12 user ratification named — "the enrolled mail-bridge service user, i.e. the same content-processing holder that runs the re-score drain" — after the 2026-07-15 implementation (no stated rationale for excluding the MDA) narrowed it to a `ContentProcessor`-only role **no shipped binary can present**, which left the whole path inert in production once the in-process paywall holder was rightly excluded. Grounds: **(1)** a dedicated content-processor **never auto-approves** (`mail-bridge-lifecycle.md` § Onboarding auto-approval — deliberately a manual trust card), so a CP-only resolution structurally fails *works-out-of-the-box* the day sealing universalizes sealed contributors; **(2)** the MDA is already a content-processor-family grant holder — the trust plane's `CONTENT_PROCESSOR_ROLES = ["mda", "content-processor"]` (`ui/nests.md` § trust facet) routinely mints standing `content.read{mail}` + `content.label-write` to it for the re-score drain, and per `key-material-hierarchy.md` rule #7's corollary a mail grant *already* opens the granter's spam model — so a keyless model-*copy* grant to the MDA is strictly narrower than what mail-granting users already convey to it; **(3)** the old empty-submit race (an always-empty-worklist holder winning the first-submit-wins run) was killed **structurally** on 2026-07-16 by binding the publish run to the one resolved holder and poking it alone — never by the role exclusion — so admitting the MDA does not reopen it: a resolved holder with no reaching grants submits an honestly-empty half, the run withholds below the floor, and erosion stays visible in `skipped_contributors`; **(4)** the moment an admin approves a dedicated off-box `ContentProcessor`, the preference order flips to it and contributor copies migrate **lazily** — every sealed write re-attaches the copy to the then-current `holder_seal_target`, and a stale copy is a non-counting, admin-visible skip (the already-ratified heal semantics) — so the dedicated-holder end state is contained in this ruling, not foreclosed by it — **and never the nest's own in-process web-serve paywall holder** (fixed 2026-07-16: that holder self-approves a `ContentProcessor` row with an attested X25519 at boot and always held the earliest `created_at`, so it silently won this resolution — telling contributors to seal their models to a key whose secret rests in the nest's data dir, and binding every publish run to a holder that never dials in; the resolver now excludes rows carrying the `in_process` enrollment marker and returns `None` — no `holder_seal_target`, no run — when only in-process holders exist) — **and, when its stored model is client-sealed, seals the initial holder copy** (the model's current bytes, HPKE-sealed to the box's aggregation-holder X25519 pubkey — the client learns that pubkey from its **own `fetch_spam_model` reply's `holder_seal_target`** field (§ Wire shapes), which the nest populates from its own content-processor holder, so a **non-admin contributor needs no service-user roster enumeration** to mint or seal — this was already a non-blocker for *this* feature before `list_service_users` itself relaxed to `User | Admin` (closed 2026-07-17, `nest-trust-holder-discovery` — `bridges.md` § Bridge-kind catalogue); the underlying seal primitive stays the `User`-callable `fetch_bridge_pubkey`, `key-material-hierarchy.md` § Audience: deployment infrastructure → Spam-baseline holder copy); OFF ⇒ revoke + clear the bit, and the nest deletes the stored copy. The grant is standing trust-until-revoke (no content-sealing epoch covers this kind), per-user, logged, and revocable from the Nests-page grant log like any other grant — a strictly better privacy story than the retired plaintext-mode posture: per-user, explicit, revocable, and auditable, instead of implied by a deployment-wide flag. No new UI surface: the toggle already ships on all seven apps (tui since 2026-07-29, § Implementation status today item 5); only its write path widens from a preference bit to bit + mint/revoke (+ the copy-seal).
- **Aggregation runs at the granted holder, never nest in-process** (`encryption-at-rest.md` § Don't do these — no in-process decryption authority on the nest core). For the client-sealed contributors, publish = the admin's `publish_spam_baseline` drives the granted holder through the **holder-pull drain shape** (the third instance of the re-score plane: nest pokes the connected holder → the holder pulls a worklist of **sealed-to-holder copies** whose paired grants stand → unseals each with its **own service-user key** (never any key of a user's), merges additively (`SpamModel::merge`), and submits the merged half + its contributor count + **the contributors it merged, named** (`merged_contributors`, additive 2026-09-27) back). The nest caps that half (§ Bounded size) and applies the k-anonymity floor to its **contributor count** (`BASELINE_MIN_CONTRIBUTORS = 3`, § Cold start Path 2, unchanged: below the floor the publish withholds/withdraws). A contributor whose grant does not reach (revoked, or never minted by a v-older client) or whose copy is absent/undecodable simply doesn't merge and doesn't count toward the floor — and, because the holder names who it merged, is **not recorded as summed** either (*A contributor's departure withdraws the baseline*: a skipped contributor's departure withdraws nothing; a merged half that names no contributor is not folded at all — nothing named, nothing counted) — **but is no longer silent**: the reply carries an additive count of opted-in contributors that could not be merged this run (holder unavailable, no reaching grant+copy, undecodable), surfaced beside the existing "not published — too few contributors" so the admin sees the erosion instead of a quietly-shrunken count. Because there is no nest→bridge request/response channel (only push events + holder-initiated RPCs), the publish handler awaits the holder's submit against a pending run with a **bounded timeout**, keeping the admin reply synchronous on all 7 apps; a holder that doesn't answer in time ⇒ the run merges nothing — so it withholds below the floor — with the unmerged count honest. The toggle→grant wiring landed 2026-07-15 (§ Implementation status item 7, b3+b4+b5), ahead of the universal at-rest seal (2026-10-02, § Implementation status item 4b), which removed the nest's in-process merge of plaintext rows: the holder half is the whole publish.
- **The published aggregate stays deployment-readable by design**: the baseline's entire purpose is to be served to fresh actors; its content is k-anon-floored aggregate n-gram weights identifying no contributor; and it is not per-user content — it has no single key owner, and sealing it would add no confidentiality against the box that just computed it at a granted position.
- **The read-time faded merge runs at the scoring agent.** A stored model is sealed and returned verbatim, so the nest cannot fold into it: the reply carries an **additive `baseline` field** (the plaintext aggregate, or absent when no non-empty baseline is published; the nest never withholds it on the untrusted advisory `sample_count` — the agent's fade math already contributes zero at full confidence) alongside the sealed model, and the scoring agent (Fauna app / AUTH'd MDA session) applies `SpamModel::merge_scaled` locally against its own `sample_count` — the same fade math, byte-identical scores, executed at the capability position like every other per-user-secret operation. **No-double-fold rule:** the field is present **exactly when the nest did not fold**, and the agent folds **iff the field is present**. The one blob the nest folds is the cold-start seed of an actor with **no** stored model (the baseline faded onto a fresh model, sealed on read, never persisted), which rides with no `baseline` field and `stored_sealed = false`; a train position never trains on it (it starts from an empty model), so the read-time fold is never written into a user's model.
- **The admin publish control renders on every box** (`mail-policy-config.md` owns the row): the gate is no longer a deployment property but the reaching-contributor count, which the existing "not published — too few contributors" reply already surfaces. There is no hide-rule.

A secure-aggregation scheme removing the grant requirement remains a possible future addition, not a current requirement.

**There is deliberately no `score_message_with_spam_classifier`-to-nest RPC** (a prior draft listed one). Scoring runs at the scoring position (§ Scoring placement), and the `score(message_bytes) → nest` shape is forbidden (`content-scoring.md` § "Don't ship plaintext to the nest to score it"). The scoring *outcome* — re-file to Junk + stamp the "scored" watermark — reuses the existing mailbox-write machinery (`db.apply_move` COPY-then-EXPUNGE + the STORE-flags path), but the **caller surface differs by agent**: the AUTH'd MDA session issues the `BridgeMda`-class `fauna.bridges.store_flags` + `fauna.bridges.move` it already holds; the **Fauna app** — a `User`-class caller that *cannot* reach those `BridgeMda`-only RPCs — issues the single `User`-scoped `fauna.email.apply_spam_disposition` (§ Wire shapes): a batch "watermark these UIDs + move this subset INBOX→Junk" the nest executes blindly (it learns the placement change, never the score or which n-grams matched — `content-scoring.md` § Stages, "the nest sees the placement change but never the *reason*"). (The retired plaintext-mode nest-at-ingest position — never built, and per Phase 3 now un-implementable, § Scoring placement — would have filed INBOX/Junk directly at the nest, no client round-trip needed; it is named here only as the contrast the next parenthetical draws against.) *(So `fauna.email.apply_spam_disposition` **is** a new kind — the earlier "not a new kind" held only for the MDA, which reuses its existing `move`; a `User` client had no re-file RPC at all.)*

### The write shape: the whole re-sealed model

Every training event and every undo runs where the key is — the MDA / Fauna app unwraps its sealed model under the session MLS capability, applies the delta (or its inverse) locally alongside the message bytes it already holds, **re-seals the whole model**, and writes it back with its sealed history row in one `put_spam_model`; nest stores the sealed blob opaque and never merges (it holds only the actor's *public* half). *(Shipping only a `sealed_model_delta` for the nest to accumulate is **not** viable — nest can neither merge nor replay sealed deltas into a bounded model without the private key it does not hold; the whole-re-sealed-model write is the resolvable shape. A homomorphic sealed-merge / bounded sealed-append-log is a possible future optimization, not the baseline — refutable design, 2026-07-02.)* The earlier plaintext-relay shape — the body shipped to the nest's `train_spam_classifier` handler to train in its frame — served until the universal seal and is removed (§ Implementation status item 4b).

## Architectural rules

- **Explicit training only.** Four signal sources, all explicit (mark-as-spam, mark-as-not-spam, `\Junk` flag-set, MOVE-to-Junk). No implicit signals (read-then-delete, time-spent, etc.).
- **Per-actor model storage with cross-actor opacity.** Alice's model lives at her actor's path; Bob's at his; no cross-actor write path; no admin-side override.
- **Cold start clamps user score to 0 until N samples.** Default 50; linear ramp to full weight at 200. The damper protects against overfit at the cold-start boundary.
- **The model and its training history rest sealed under the actor's key.** Scoring, training and undo run on unwrapped bytes in a capability holder's worker memory; the nest stores only what a holder sealed (§ Implementation status item 4b).
- **Scoring placement = search placement.** Per-user scoring runs at the same positions as search — post-delivery at the Fauna app / AUTH'd MDA session, uniformly — **never** at the nest, **never** at ingest, **never** at the inbound-MX perimeter, **never** via a `score(bytes) → nest` RPC (`content-scoring.md` § The placement matrix; § Scoring placement). One shared-Rust scorer (`libs/fauna-mail/src/spam/`) runs at every position over the shared canonical tokenizer.
- **Reset is destructive and the user knows.** The confirmation dialog explicitly says "this cannot be undone."
- **Combined-score formula is `max(rspamd, weighted_bayesian)`** with a 0.7 weight on Bayesian. The defaults are knobs; the formula structure is not.
- **Permissive auto-Junk default.** Out of the box the bridge scores + tags + delivers; only the `spam_folder` tier is enabled (→ Junk). The `reject` tier defaults to disabled (`0`); destructive actions (550-reject, delete) are opt-in via an admin threshold or a per-user filter rule. The bridge never silently bounces or hides mail on a score the user can't override.
- **rspamd is the sole deployment-wide content scorer.** It runs its own SPF/DKIM/DMARC/RBL + content rules; there is no separate Fauna-side auth/DNSBL heuristic. The admin changes rspamd rules globally; per-user Bayesian is the personalization layer atop. rspamd admin-disabled ⇒ the deployment-wide term is 0 (no content scoring, an explicit opt-out mirroring ClamAV-disabled).
- **The deployment-baseline path is admin-trigger + per-user opt-in.** Off by default. Reverses Gmail's "all users contribute" default.
- **Per-user models never share write paths.** A future "share my spam corpus with my friend" feature would need a new RPC; doesn't exist today.
- **The nest enforces the per-actor authorization on every model write.** A `User`/`Admin` writes only their own model; a bridge may name another actor only as `BridgeMda` trusted naming for an actor whose local mail it serves (`put_spam_model`, § Wire shapes).
- **Aggregate-only admin surface.** The admin pane Spam handling card (per `mail-observability.md`) shows counts only; no per-user breakdown.
- **Training-history retention is 30 d by default; n-gram weights are permanent.** The audit trail expires; the learned model persists.

## Don't do these

- **Don't infer training signals from implicit user behavior** (read-then-delete, time-spent-on-message, deletion-without-opening, reply patterns). False-positive rate too high; surveillance footprint wrong by default. Explicit only.
- **Don't expose another user's training samples** to admins, the box owner, peer users, or "support" surfaces. The model is opaque to everyone but the user (every row is sealed to the user's own key).
- **Don't auto-train from "I never opened this message."** The "I'm too busy to read it" case is indistinguishable from the "I think it's spam" case without an explicit click. The long-term question ratifies explicit-only.
- **Don't share per-user models across actors** without their opt-in. The shared artifacts are exactly two, both per-user opt-in and both explicit-signal-only: the deployment baseline (§ Cold start, Path 2 — aggregated *model bytes*) and the k-anonymized per-item spam reports (`content-moderation-and-ranking.md` § Distributed report sharing, ratified 2026-07-07 — aggregated *flag counts*; mechanism built, `report-sharing.md` § Implementation status today).
- **Don't let the deployment baseline update from a user's training without their explicit opt-in.** Reversed Gmail default.
- **Don't store training samples beyond `training_history_retention_days`.** The n-gram weights are the permanent learning; the per-message audit is bounded.
- **Don't run the classifier without confidence-weighting in the cold-start window.** A 10-sample model trained on one phishing email would over-fit and quarantine legitimate similar-content mail.
- **Don't unify Alice's and Bob's per-user models for "performance."** Per-actor isolation is the security boundary; merging models defeats it.
- **Don't add an "admin override" RPC for training another user's model.** The user-controls-their-data invariant forbids it. Admin-controlled tuning is rspamd-side (admin-tier knobs on the deployment-wide pre-classifier), not per-user Bayesian.
- **Don't store the unwrapped per-user model on nest disk.** Worker-memory only for the duration of the score / train operation (built — § Implementation status item 4b).
- **Don't add a `score(message_bytes) → nest` RPC, and don't score per-user at the inbound-MX perimeter.** Scoring needs the per-user secret (the model) *and* the plaintext together — which at MX-delivery time exists at no position (the recipient is unauthenticated), and the nest itself never holds either. Score where search does: the authenticated agent post-delivery, uniformly (`content-scoring.md`).
- **Don't keep the per-user model on the nest-only `bayespam` engine.** The same scorer must run at nest / MDA / client over the shared canonical tokenizer; use the shared n-gram NB in `libs/fauna-mail/src/spam/`, not a nest-private crate with its own tokenization and opaque model.
- **Don't auto-reset a user's model on account deletion.** The user explicitly resets if they want to; account-delete removes the `spam_models` row with the rest of the account's per-actor data (same path as other per-actor rows).
- **Don't ship a "fast mode" that skips Bayesian for low-resource deployments.** The whole pipeline runs everywhere; resource-tunable knobs (model size cap, cold-start threshold) handle resource bounds, not feature toggles.
- **Don't expose the model file's raw bytes on any client-facing API surface** (no "export my spam model" button). A future export feature for portability would need a separate spec; today the model is internal data, not export content.
- **Don't reuse rspamd's score as the Bayesian score** for cold-start users (no "use rspamd as if it were the user's Bayesian"). Cold-start is rspamd-only by clamping the Bayesian's contribution; reusing rspamd's score as the Bayesian score would double-count.
- **Don't surface per-user model size on the admin pane.** Per-user metadata; user-tier surface only. Aggregate "total spam-model storage" on the admin pane is fine (no per-user identification).
