## Key custody and per-identity seniority
**Key-custody split (ratified 2026-07-19, derived from the user-controls-their-data invariant; per-identity seniority ratified 2026-07-29):** the *signing* key (day-to-day commit signing) is bridge-custodied by the nest-side state [`atproto-pds-bridge.md`](atproto-pds-bridge.md) § State & data shape describes — but for did:plc, **at least one rotation key is user-custodied: generated and held in the user's client** (the client credential store, the same pattern as DNS-provider keys), never held by nest or the bridge, and placed **senior to** any bridge-reachable key in the PLC operation ordering. What that seniority delivers, stated precisely (RE-STATED 2026-08-02 — the previous "cannot seize or permanently destroy" wording claimed box-*incapability*, which the custody does not provide): the bridge's junior key is **listed**, and PLC accepts a next op from any listed key, so a compromised bridge **can** sign operations up to and including a tombstone. The user's protection is a **superior contest position, not the box's incapability**: the user's key is strictly senior, so within PLC's 72 h recovery window the user's client can fork away and nullify any op a bridge-held key signed — seizure and destruction by the box are *contestable and detectable*, not impossible. Detection is built (feeder #1's custody check, the attribution rule below, feeder #3's handle binding); the contest itself — constructing and submitting the recovery fork with the senior key — **is built and reachable on all 7 apps** (design ratified, mechanism LANDED 2026-08-02, ceremony trickle-down complete 2026-08-30 with windows the last leg: the *recovery-fork contest* block below; § Implementation status today carries the per-app split). The fork builder exists (`fauna-client-atproto::recovery_fork`), the settings machine performs a consented contest on convergence, and **the ceremony that records the consent is rendered on all 7 apps** (tui since 2026-08-02, linux/web/android since 2026-08-22, macOS/iOS since 2026-08-26, windows since 2026-08-30, the last leg) — so the honest statement today is: the box cannot *quietly* seize or destroy the identity (the alarms fire inside the window, and a box-authored tombstone alarms by attribution); recovery is constructible in-product and **reachable by a user on any of the 7 apps**; the scalar still has **no export surface**, deliberately, because the in-product fork builder is the remedy; and a box op that goes uncontested for 72 h **stands permanently**. The enable flow mints this key client-side; identity control never has the nest as sole custodian. **Seniority is a per-identity fact, and the client holds a *keyring*:** `rotation_keys` in the `fauna.state.atproto-identity` rows is a union-merged, append-only ring in a deterministic stability order that does **not** encode seniority — which held key is senior for a given DID is that DID's own published log's fact, and each key remembers the DIDs it was published senior for (its *published-for* bindings, converged from the directory's own log, never from nest testimony). **A mint never reuses a key published for another DID — fresh-key-per-mint** — because the reuse would put the same `rotationKeys[0]` in two DIDs' permanent public logs, covertly linking them (the clean-break leak [`atproto-pds-bridge.md`](atproto-pds-bridge.md) § Disable & revocation's re-mint rule exists to avoid); consumers select the key that matters from the published log (custody verification: membership of the held ring; tombstone signing: the ring key the standing head lists), never from list position. *(Genesis-seniority verification — S4-C, LANDED 2026-07-23, closing the S1/S2 identity-mint TOFU finding; generalized to ring membership 2026-07-29: the client independently resolves the published `did:plc`'s operation log from the public PLC directory — its own HTTPS connection (`fauna-client-atproto::genesis_verify`), **no nest dependency**, so the box cannot sit in the middle of its own audit — and asserts **every standing (non-nullified) op** carries one of the client's held rotation keys at `rotationKeys[0]`. Membership is exactly as strong as the old single-key equality: keys enter the ring only through the client-side sole writer, so a hostile box cannot place one in the comparison set. Every op, not just the head: PLC's 72 h contest window means a box-senior genesis can nullify a later "corrected" op. A contradiction must survive **two consecutive convergences** before the alarm posts — the one legitimate cause (a sibling device's fresh re-mint key read from the log before this device's ring has synced it) dissolves with config sync, a real compromise persists far beyond one pass inside the 72 h window, and a self-clearing critical-alert flash would cost the alarm its credibility. **From the one-shot session-start sweep the same rule is re-expressed as a read ORDER rather than a wait (ratified 2026-08-02):** the sweep reads the published log *first* and the held ring *second*, and a mismatch against that strictly-newer ring alarms immediately. This is sound because of a **load-bearing ordering invariant of the mint path — a fresh rotation key is written to the account-state plane kind `fauna.state.atproto-identity` BEFORE the operation naming it can be published** ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The kinds*; `mint_rotation_key`'s write completes, and aborts the mint if it fails, before `set_integration_level` is called at all), so every op present in a log fetched at T already had its senior key stored nest-side before T, and a ring read after T must observe it. The legitimate race is therefore excluded *by construction* instead of out-waited — strictly stronger than the two-convergence rule and strictly faster (the alarm lands inside PLC's 72 h contest window rather than a session start later). ⚠ **Do not reorder the mint to publish before storing**, and do not let a sweep reuse a ring value read before the log: either silently reintroduces the false-alarm race this ordering removes. The settings-machine path keeps its two-convergence debounce, which is safe but slower, because it reads the ring before the log. A legacy non-`plc_operation` entry alarms too (a quiet skip would let a hostile box dodge the check by publishing in the v0 format); an unreachable directory or unparseable log is quiet-retried, never an alarm. A mismatch posts a **critical alert** to the cross-page banner ([`critical-alerts.md`](critical-alerts.md) — visible on every page, not just Settings → AT Protocol). The check runs from the settings machine on every status convergence, so the mint window — the TOFU-critical instant, when the user is on the page confirming — is covered on all 7 apps. **Honest residuals:** did:web has no directory to audit (its custody IS domain custody); the handle→DID binding is a separate question, **settled 2026-08-01 as feeder #3 below**; and a mismatch is detection, not prevention — the user's senior key can still contest inside PLC's 72 h window, which is why detection at the mint instant matters. Finding + original analysis: thesecurity review (tracked internally).)*

## The 72 h recovery-fork contest
**The 72 h recovery-fork contest — the remedy the seniority statement names (design RATIFIED 2026-08-02; mechanism + ceremony BUILT the same day, § Implementation status today).** When the custody alarm names a box-authored standing op, the user's in-product remedy is a **fork**: a `plc_operation` — never a new op type — whose `prev` names the **fork point**, signed with the held senior key, submitted over the client's own HTTPS to the directory. Under PLC's recovery rules a fork signed by a strictly-higher-priority rotation key of the fork-point op, within 72 h of the first op it displaces, nullifies that op and every descendant. Ten decisions, each load-bearing:

1. **The fork point is the custody verdict's own index — detection and remedy are two readings of ONE verdict.** `verify_audit_log` already reports the first standing op that violates custody (`standing_index` on every `MismatchReason`); the fork point is the standing op immediately before it, and everything from the violation onward is displaced — including good-*looking* later ops, which chain through the violation and were authored under the attacker's authority (the sandwich case the seniority check already pins). The contest never invents its own notion of "bad".
2. **A violation at the genesis has no contest, and the surface says so.** Standing index 0 leaves no earlier op to chain to — that is the TOFU failure, whose remedy remains abandoning the DID (fresh mint; nothing was ever burned for it). The ceremony surface renders the honest no-remedy state rather than a dead button; likewise a window already closed.
3. **The op's contents: the fork point carried forward VERBATIM, minus box authority.** The fork op is built from the fork-point op's own published JSON — every field, known or unknown, copied verbatim (a contest must not silently strip fields a future PLC schema added) — with exactly three changes: `prev` = the fork point's CID; `rotationKeys` = the fork point's list ∩ the held ring, order preserved (in product terms: the user's senior key alone — the bridge's junior key and any unknown key are pruned); a fresh `sig`. The box's repo *signing* key (`verificationMethods`) and the `atproto_pds` service entry are deliberately **kept**: identity authority is severed, availability is not. ⚠ **"Verbatim" needs a carrier, and the typed parser is not one** (2026-08-02): `PlcOpKeys` is a deliberately lossy slice — it has no `verificationMethods` field at all, and `PlcService` keeps only `endpoint` — so a builder written against it would *delete* the repo signing key at the exact moment this decision chose to keep it. The fork is therefore built from the fork-point entry's **unparsed JSON object**, retained beside the typed view by `parse_audit_log_with_raw` (one parse of the bytes, so the raw op a fork is built from and the typed op eligibility ruled on cannot come from two different reads), and pinned by a fixture carrying `verificationMethods`, a `services` entry with both `type` and `endpoint`, and a top-level field this codebase has never heard of. **Stated consequence the ceremony must carry, not only this doc:** keeping `verificationMethods` means a compromised box retains the key that *publishes* — it can still author posts as the user after a successful contest. Decision 4's lock-out is precisely scoped to the PLC layer, and the user-facing copy says so in as many words (`atproto_settings.contest_detail_contestable`); replacing the publishing key is a separate, unbuilt gesture — posts keep flowing and the network presence stays up while the user decides what next. A user who now distrusts the box holds sole op authority afterwards and can go further (delete-presence, migration, a lockdown op) — the contest restores the last good state rather than bundling a second decision into an act with a 72 h deadline.
4. **Post-contest the box is locked out of the PLC *rotation* layer permanently, by construction** — that layer only, never the whole PLC document (narrowed 2026-08-02: `verificationMethods` and `services` ride through the fork by decision 3's deliberate choice, so the box keeps the repo *signing* key and can still author posts as the user; what it can never again do is author a PLC **operation** for this DID). The directory validates each op's signature against its `prev` op's `rotationKeys`; the new head lists only user-held keys, so no bridge-reachable key can ever author another op for this DID. Stated consequence, accepted: the bridge's rename reconcile (`alsoKnownAs` updates, junior-key-signed) is refused by the directory from then on — an ordinary logged submit failure bridge-side, and re-delegating to a box (re-listing a fresh junior key with a senior-key-signed op) is a possible future feature, not part of the contest.
5. **Strictly-senior eligibility is checked as index 0, and only index 0.** PLC accepts the fork only from a key with strictly higher priority than the displaced op's signer. A held key at the fork point's `rotationKeys[0]` out-ranks every other possible signer by construction (the displaced op cannot carry the user's own signature — ring keys sign only through the client's own flows). A held key listed at any lower position proves nothing about relative priority; that shape (never produced by our mint flow) is honestly not-contestable.
6. **User-initiated, never automatic — iron-clad.** The client *detects* on a clock but *contests* only on the user's explicit gesture. An auto-contester is a detector promoted to an actor with power to nullify the **user's own** out-of-band operations — the day outbound migration ([`atproto-pds-bridge.md`](atproto-pds-bridge.md) § Design horizon) or third-party PLC tooling touches the log, an auto-fork would "defend" against the user's deliberate act. The gesture is **scoped to the named op**: it consents to contesting the specific standing op the alarm names (recorded by CID), so a new hostile op after a completed contest requires a new human decision. A standing "always contest" flag is exactly the auto-actor this rules out.
7. **Crash-safe and fleet-completable — the consent-record pattern:** the gesture writes `contest_intents` in the `fauna.state.atproto-identity` rows (append-only, union-merged by `(did, contested_op_cid)`, client-sole-writer through `fauna-client-atproto::rotation_key`, synced like the ring), and the settings machine's convergence performs it — re-deriving everything from a **fresh log read each pass**: the intent's named CID must still be the first standing violation, the window still open, the fork point still listing a held key senior, before anything is signed. A crash mid-submit retries idempotently (the directory is the durable record; no client-side "contested" flag exists); a sibling device holding the synced ring finishes what this device started; an intent whose named op is no longer standing is spent and inert forever. A log whose first violation differs from the intent's named CID is a *different* attack — nothing is signed; the surface re-presents for a fresh gesture.
8. **The alarm clears on the directory's evidence with ZERO new mechanism.** Once the fork stands, the nullified suffix leaves the standing chain, `verify_audit_log` answers `Verified`, and the existing `sync_custody_alert` takes the banner down — nest testimony is nowhere in the loop, before or after.
9. **No nest or wire additions, and no key-export surface — both deliberate.** The contest is wholly client-side (build, sign, submit, verify-back all on the client's own connections; nest learns nothing and has nothing to learn — its bridge simply finds its ops refused). And the scalar keeps having **no export surface**: the in-product fork builder IS the remedy; export serves only off-product tooling while adding a scalar-exfiltration surface, and may land later as its own deliberately-decided feature. The **sweep does not converge contests** either — it is a detector, and letting it sign identity ops would promote the best-effort feeder loop into an actor (the same boundary as decision 6, one layer down).
10. **Scope: feeder #1's verdicts** — `SeniorKeyDiffers`, `RetirementByUnheldKey`, `NotAPlcOperation`, each with a good prefix. Feeder #3's rogue-handle alarm names no violating op index, and legitimate renames move `alsoKnownAs`, so a handle-driven fork-point rule needs its own design — a recorded follow-on, not silently included.

**Where the contest's logic lives:** shared Rust — `fauna-client-atproto::recovery_fork` (pure plan/build/sign with the I/O split and canonical-cbor discipline of the tombstone module; `AuditEntry` gains `createdAt` for the advisory window math — advisory only, the directory's acceptance is the truth); the gesture + converge on the settings machine beside `request_tombstone`/`converge_tombstone`; the ceremony surface on the `atproto` page ([`../ui/atproto.md`](../ui/atproto.md) § Contest ceremony — rendered off **client-side evidence only**, so it stays reachable when the nest denies the identity, per the audit-floor rule below).

## Feeder #3 — the published handle binding
**Handle custody IS domain custody — and feeder #3 audits the half that is left (ratified 2026-08-01).** The residual above asked for a check on the handle→DID binding, sketching a cheap structural close for managed-DNS mode: compare the `_atproto.*` TXT rows the client sees through `fauna.dns.list_records` against the verified DID. **That check is not built, deliberately, and no future session should build it.** Two reasons, the second decisive. (1) `fauna.dns.list_records` is **admin-gated** (`require_admin` in `bins/fauna-nest/src/dns_handlers.rs`), so it cannot reach the ordinary users the threat targets — and on a hostile box the admin is the adversary. Worse, *both* halves of its answer are nest-computed — the expected value is derived from the nest's own DB (`append_atproto_handle_txts`) and the red/green status from the nest's own resolver (§ Live verification in [`dns-management.md`](dns-management.md)) — so on the very box the check exists to catch, it reads the attacker's own answer. (2) More fundamentally: a Fauna handle lives at `<localpart>.<the deployment's domain>`, and the handle→DID binding is a record in *that domain's* zone. **A box that owns the domain can bind the handle to any DID it likes** — the same statement this doc already makes about did:web, now recognized as general. No client-side check changes that, and the client cannot independently observe the zone either: the `DnsProviderSeam` exposes `verify`/`publish`/`teardown`/`find_records` (a targeted read at a known name) and no zone-wide enumeration (which is exactly why `reconcile_atproto_txt` needs a *remembered* name set). **The mitigation for a user who will not accept that is to own the handle's domain themselves** — the custom external-domain handle listed as a deferred nicety in [`atproto-pds-bridge.md`](atproto-pds-bridge.md) § Handle, which is the feature that actually closes this, not a detector.

What *is* soundly checkable is the **converse direction**, and it costs nothing: the DID this client's rotation key protects must be **published under a handle at the user's own deployment**. The published handle is `alsoKnownAs` on the DID's standing head operation — read from the same independent PLC audit-log fetch feeder #1 already makes (`fauna-client-atproto::genesis_verify::fetch_audit_log`, the client's own HTTPS, no nest in the path), so it is available to **every user, not just admins**, and it is tamper-evident: the log is append-only and public, so a box that published a rogue handle at any point cannot hide it by changing its answers now. Feeder #3 (`fauna-client-atproto::handle_binding`) alarms when the standing head names **no** `at://` handle under the expected domain, posting `atproto-handle:<did>` to the cross-page banner ([`critical-alerts.md`](critical-alerts.md)). **It clears the severity bar** on the § Severity bar's own terms: the identity the user's recovery key protects is being published to the network under a name that is not theirs (or under none at all), so the audience that finds them finds someone else — possible compromise of identity, and durable rather than transient.

**Four shape decisions, each load-bearing:**

- **The comparison is on the DOMAIN, not the whole handle** — because the ATProto handle is derived at read time from the current Fauna handle, so a **rename** legitimately leaves the published `alsoKnownAs` naming the old localpart until the nest's PLC update lands. Whole-handle equality would fire on that window, and since the sweep is one-shot per session (§ *Who runs the detector* in `critical-alerts.md`) the false alarm would stand, non-dismissable, for the whole session — the crying-wolf failure in its most expensive form. A rename never changes the domain. A stale localpart at the right domain is **reported in the sweep's log, never alarmed**.
- **"Nothing to check" is silent, always** — no hosted identity, a pending mint with no DID, a did:web identity (no directory log to audit; its custody *is* domain custody, so the comparison would be tautological), a nest reporting no handle domain, and an unreadable or unparseable log. Only a definite contradiction in a log the client actually read raises the banner. A retired identity (a `plc_tombstone` head) publishes no handle *by design* and is silent for that reason, not by accident.
- **It is NOT downstream of feeder #1's verdict.** Its comparison basis needs no rotation keyring, so gating it on feeder #1 having succeeded would make it unavailable exactly when a client's ring is unsynced — which is when a user most needs to be told their identity is published under someone else's name. What *is* enforced is **one accusation per event**: if feeder #1 already has `atproto-custody:<did>` standing for the same DID, feeder #3 stays silent rather than stacking a second banner on one compromise.
- **Two keys, because they are two accusations.** A wrong senior key and an unbound handle are different claims about the same identity and must not overwrite each other's text; the rule above is what keeps both from ever standing at once.

**What it does not catch, stated so no session mistakes it for closure:** a box that lies *consistently* — publishing a rogue binding while reporting a matching handle domain — defeats it, because the expected domain is nest-reported (`GetIntegrationStatusReply.handle_domain`). Strengthening that basis to a value the box cannot choose (the host of the connection the *user* chose) is the known next increment. And when inbound account migration ([`atproto-pds-bridge.md`](atproto-pds-bridge.md) § Design horizon) lands, an imported DID whose `alsoKnownAs` still names its former domain would read as unbound — **the migration path must update `alsoKnownAs` before the identity goes live, or teach this feeder the imported provenance**; that is a constraint on migration, recorded here so it is not discovered as a false alarm.

## The audit floor and the departed-DID alarm
**The held ring is an audit FLOOR, and a departed DID's alarm needs client-side evidence (ratified 2026-08-02, closing the hole where "the accused box decides whether it is checked, and can clear the alarm that accuses it").** Both feeders' *evidence* was already fetched independently of the nest — but every input deciding **whether to audit at all** came from one nest-computed reply (`atproto.get_integration_status`: `identity`, `identity.method`, `identity.did`, `handle_domain`), and so did the departed-DID alarm clear. That made a detector switchable by the party it detects — each half defensible alone, the composition the finding. Two rules close it, both resting on evidence the nest cannot author:

- **The audit set is the nest's answer UNIONED with the client's own floor, and the floor has TWO sources.** The first is `published_for_dids` — directory-derived by construction (decision (b) above), so a DID the client independently knows it published a key senior for is audited **whatever the nest says**. The second is `nest_named_dids` — **every did:plc the nest has ever named as this account's identity, frozen client-side at the moment it named it** (RATIFIED 2026-08-02; written by the same client-side sole writer, from both the settings machine's status convergence and the sweep's own pre-plan step). The ring only ever *adds* targets, so an empty floor from either source leaves behaviour identical to nest-testimony-alone, and neither can mute anything.

  **Why the second source is necessary — the first one is empty in exactly the case feeder #1 exists for.** `published_for_dids` is written **only on a *passing* custody verdict** (the `Verified` arm, in both production writers) plus the retirement burn. A genesis-time compromise never passes, so nothing is ever burned, so the floor was **empty precisely for the TOFU failure the feeder was built to detect** — leaving the audit set fully nest-gated in the one case that matters most. A floor built on that source alone is thereby narrowed to already-verified DIDs, not closed.

  **Why the second source is sound despite being nest testimony — and the honest statement of what it is NOT.** `nest_named_dids` carries **no custody claim and is not independent evidence**; a box can put anything in it by naming it. Its security property is *irrevocability*: the box cannot **unsay** what it already said. That is sufficient here and nowhere else, because a floor can only ever **add** an audit target and can never mute one — so a lie planted here raises an audit the box itself must then survive, never suppresses one. ⚠ **Never read an entry as evidence the DID is the user's**, and never reuse this value where the two provenances differ (below). Only auditable DIDs are frozen (did:web has no directory log, so flooring one would pin an audit that can never run), and the field is deliberately **not** consulted by `mint_rotation_key`'s reuse predicate, which still reads an empty `published_for_dids` as "reusable".

  **Shape, and why it is a new top-level key rather than a field beside `published_for_dids`:** it degrades to **absent, never poisoned**. An older client's read-modify-write drops an unknown top-level key wholesale — no floor from this source, i.e. exactly the pre-fix behaviour — whereas a parallel field *inside* `AtprotoRotationKey` would be stripped from a record that survives, re-creating a half-state from honest code. Additive (`serde(default)`), sorted + deduped, union-merged like `tombstone_consents` so a claim frozen on one device reaches every device — otherwise a box could shrink the audit set by telling a *second* device nothing.

  **One question, one predicate — the two production resolvers must not disagree (ratified 2026-08-02).** "Is this DID auditable?" is answered **from the DID's own `did:plc:` prefix**, never from the nest's `method` label for it, by one shared predicate (`fauna-client-atproto::genesis_verify::is_auditable_did`) that the sweep and the settings machine both call. They disagreed before: the sweep gated on `identity.method`, the settings machine on the prefix, so a real `did:plc:` reported under `method: "web"` was **audited on the settings page and skipped by the sweep** — the sweep being the one that matters, because it runs without the user opening a page. A box that mislabels its own method does not thereby earn an exemption from the audit; the gate is anchored on the data, which is also what the directory is keyed by. (The converse, a `did:web:` mislabelled `plc`, now correctly skips instead of 404-ing the real directory on every sweep forever.) It is **feeder #1's floor only**: feeder #3's comparison basis (`handle_domain`) is itself nest testimony, so a floor under it would not be independent of the audited party — its nothing-to-check state is instead made visible by the skipped bucket ([`critical-alerts.md`](critical-alerts.md) § Feeders). ⚠ **A DID reached through the floor is NOT the same as one the nest claims is live**, and the difference is load-bearing: `published_for_dids` keeps a **retired** DID permanently (the retirement path burns the key that signed its tombstone), so the floor meets every identity the user ever retired on every sweep. A terminally retired log is therefore **silent** for a floor-reached DID — the ordinary end of that entry's life — while staying an **alarm** for a DID the nest claims is the live identity, where a tombstone contradicts that claim outright. Without that split the fix would manufacture a permanent false alarm per retirement, which is the crying-wolf failure [`critical-alerts.md`](critical-alerts.md) § Severity bar exists to prevent. **RE-TAKEN 2026-08-02, composing with the re-stated seniority boundary: "terminally retired" means a tombstone whose signature verifies against the held ring** — attribution, not mere existence. A tombstone is the one op any *listed* key may sign, and the bridge's junior key is listed for life, so a tombstone-in-the-log is evidence of *a* retirement, not of the *user's*; reading it as consent would let the party that destroyed the identity also silence and clear the alarm for it. Attribution can always succeed for a legitimate retirement because the burn keeps the signing key in the ring forever; a tombstone no held key signed is **loud** in every context.
- **A departed DID's standing alarm clears only on a client-side reason, never on the nest's silence.** Two qualify: the DID is absent from **both floor sources** — no `published_for_dids` binding *and* no frozen `nest_named_dids` claim — so nest testimony really was the only thing that ever tied it to the account, or the **public log shows a terminal retirement attributable to the held ring**

  ⚠ **RE-TAKEN 2026-08-02: the first arm used to read `published_for_dids` alone, and that was the attack, not the benign case.** Its stated rationale — *"the genesis-time TOFU failure, where the verdict never passed so nothing was ever burned"* — describes the **compromise itself**, so the arm let the accused party clear the accusation in exactly the case that raised it. The rule rested on "nothing would ever re-verify it, so the alert would be permanent"; with the freeze both halves are false — the floor re-derives the verdict from the public log on every sweep, so the alarm is not *stranded*, it is *maintained*, by the directory rather than by the box. The arm survives only in its honest form: a client with **no record of any kind** (an older client whose read-modify-write dropped the key, or a config write that failed) has only ever had the nest's word, and the alarm goes when the word does. ⚠ The two sources are read **separately** here and merged only in the sweep's plan — the plan asks "which DIDs do I fetch?", where provenance is irrelevant; this rule asks "did anything but this box ever tie this DID to the account?", which either source answers independently (the condition re-checked and found resolved, per [`critical-alerts.md`](critical-alerts.md) § Mechanism → *Lifetime*; attribution per the re-take above — an unattributable tombstone clears nothing). The second is why "the client itself retired it" needs no separately stored flag — the retirement leaves its own evidence in the directory, **signature included**, and that evidence covers a *sibling device's* retirement too, which a local flag could not (the ring syncs; the signing key is burned into it forever). Everything else leaves the banner up: a live log whose senior key is not ours is the attack, and an unreadable directory is not a resolution. Both reads are paid only when an alarm is actually standing for the departed DID.

**Bounding clauses, kept so the fix is not over-read:** this defeats a *detector*, it does not create a compromise; the floor does not extend to the **unreachable**-nest arm, which was already correct (a failure means retry, clears nothing, and leaves every standing alert up, so it cannot compose with the clear the way an answer-with-nothing could); and the "does not catch a box that lies *consistently*" concession above is untouched — that is a different and more expensive lie.

## Implementation status today
**The keyring and its custody records live on the account plane — CUT 2026-09-30.** The rotation keyring, the tombstone consents, the contest intents and the nest-named DIDs are the account plane's `fauna.state.atproto-identity` kind (fleet-only, sealed under the generation tip, one row per element; [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) owns the kind), and every consumer reads and writes them through one injected door, `fauna-client-atproto::identity_store::AtprotoIdentityStore`, over the account runtime (`fauna_account_seams::atproto_identity::RuntimeAtprotoIdentity`; web's settings chunk through the account port). The sole writer `rotation_key` turns each read-modify-write into one join, which removes nothing — so a concurrent device's fresh key joins the ring beside this one's and can no longer be lost to a race — and the settings machine and the session-start sweep read the ring through the same door. With no runtime running, a read is "cannot verify" (quiet, retried) and a write is refused; nothing falls back to the former `UserConfig` field, which retired with the blob rail on 2026-10-02 ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)).

**The contest authenticates the log before it signs — LANDED 2026-08-02.** The contest path used to rule entirely on what the directory *said*, without authenticating it — the fork point's bytes, carried forward verbatim by decision 3, were signed with the user's genuine senior key over a chain nothing had verified. `fauna-client-atproto::plc_chain` now verifies the standing chain from genesis through the contested op — every entry's `cid` is the CID of its signed operation, each `prev` names the previous standing entry, each `sig` verifies against a key the op it chains to listed (both did:plc curves — the user's P-256 and the bridge's K-256), and the genesis must hash to the DID being contested — and `contest_plan` refuses to offer `Contestable` otherwise. **Detection is deliberately unchanged:** `verify_audit_log` keeps its membership-only basis, so a hostile log still raises the alarm and still renders the ceremony; what it may no longer do is produce a signature (decision 6's split — detect on a clock, act only on the user's gesture over evidence). The whole chain rather than just the fork point, because a *fabricated violation* spliced onto real operations chains and CIDs perfectly and would otherwise let an attacker with no compromise at all induce the user into nullifying their own recent history.

**The successful contest is proven end-to-end again — the bridge signs the seizure it is capable of (2026-08-02, closing the Known gap this bullet declared the same day).** The gap was real and structural: the e2e fake directory holds no rotation key the genesis lists — those are the user's senior key (client-only) and the bridge's junior key (bridge-only) — so its "seizure" hook could only ever produce a **forged** log, and the e2e that claimed to prove "the whole remedy, end to end" had passed because nothing verified signatures. Handing the fake either key would have been a worse hole than the unauthenticated log was, so the signer had to be the bridge. It now is: a **one-shot `--seize-did` / `--seize-rotation-key` mode**, compiled in only under `-tags fauna_e2e_seize` (convention 15's Go analogue of the native FFI flavors — a build tag, never an env var, since a runtime gate standing in for a compile-time boundary was itself one of the holes closed here), which reads the standing head, replaces `rotationKeys[0]`, signs with the bridge's own junior key and submits — through the **same** `FetchLastOp` → `BuildUpdateOpFromPrev` → `Sign` → `SubmitOperation` calls the handle-rename hook uses, so the contest is proven against the shipped mechanism rather than a test re-implementation. Three properties are asserted on the artifacts, not on trust: the production `atproto-bridge-build` greps its own binary for the flag name and fails if it is present, the e2e recipe asserts it IS present (a gate never verified in the positive direction is indistinguishable from a tag nothing honours), and a tier_1 pin holds the Dockerfile and the production recipe to the same rule. `test_recovery_fork_contest_end_to_end` is restored over that seizure: the alarm fires, the ceremony offers `contestable`, the user confirms, the directory records a fork nullifying the hostile op, the user's key is senior again and the alarm comes down. The forged-log case keeps its own test (`test_a_forged_seizure_alarms_but_is_never_signed`) as the matching refusal. **The seam is e2e-only and deliberately narrow: it needs the bridge's already-approved keyfile and a nest dial, binds no port, and no release path, Dockerfile or CI workflow sets its tag.** **Acceptance parity at the directory boundary (2026-08-02):** the fake directory now *validates* every submitted op the way `plc.directory` accepts one — ECDSA-SHA256 over the unsigned canonical dag-cbor against the authorizing rotation keys (the genesis's own list, else the list of the op `prev` names), fixed-size `r‖s` base64url, **low-S required** (the acceptor refuses the malleable twin; the client's read-side verifier deliberately accepts it in published history — different roles, both documented) — through an independent Python verifier, with cross-implementation vectors pinned on both sides (`tests/e2e-unified/tests/test_plc_acceptance_parity.py` ↔ `plc_chain`'s twin vector test, covering both production curves: the box's K-256 ops and the user's P-256 contest fork). A signature-encoding or canonicalization drift in a production signer therefore fails in a test, not at the real directory at the moment the remedy is used. The seniority/72 h *ruling* stays deliberately un-modelled in the fake — that ordering logic is exactly the Rust under test — and only F5 live interop proves the real directory.

**A log that does not authenticate is a no-remedy STATE, not a read failure — the ceremony says so (fixed 2026-08-02, drift introduced by the chain-authentication close).** That close correctly stopped the client signing against a chain it cannot verify, but returned that outcome as an *error*, which never reaches the ceremony card — so for the hostile-directory / MITM case the custody banner told the user their identity may be seized and the page it sent them to rendered nothing. That close's own doc comment claimed the opposite ("still raises the banner and still renders the ceremony"), so this was drift between stated intent and behavior rather than a design change. `ContestEligibility` gained `Unauthenticated(ChainFailure)` — a planned violation with no remedy, alongside `GenesisViolation` and `WindowClosed` — which renders under the existing `not-contestable` ui.yaml state with its own copy (`atproto_settings.contest_detail_unauthenticated`: the record does not check out, nothing was signed, try from another network). Decision 2's rule — *the ceremony surface renders the honest no-remedy state rather than a dead button* — now covers all three. Signing is refused exactly as before (`converge_contest` acts only on `Contestable`), so the security property is unchanged; what changed is that the refusal is legible. Pinned at three layers: the two chain-authentication probe shapes now assert the eligibility and that a CID is still named, a machine test pins each no-remedy state carrying *distinct* copy (they share one state value, so the detail line is all that distinguishes them), and the forged-log e2e asserts the rendered state and copy.

**A re-mint mints a FRESH senior rotation key — LANDED 2026-07-29**, closing the linkability residual this section had recorded (the reuse would have put the same `rotationKeys[0]` in the retired DID's and the new DID's permanent public logs — a covert, un-chosen link that survives even a handle rename and proves same-custody, where handle continuity is overt, user-controlled, and weak evidence anyway since a freed handle is re-claimable). The blocking question — *which key is senior after the ring holds two, and how do devices converge on it* — was answered by dissolving it: **seniority stopped being a property of the list and became a property of the identity** (§ Key custody and per-identity seniority). Four decisions are load-bearing. **(a) The ring entry remembers where it was published** (`published_for_dids`, additive at-rest evolution; same-key entries union their bindings on merge, since two devices converge the same public fact independently and a dropped binding would un-burn a key). **(b) The burn has two log-derived writers and no nest-testimony one:** the custody check's Verified arm records what the directory's log just showed, and the retirement path records the key that just signed the tombstone — the second is the guaranteed leg, since a retirement cannot complete without it, and the first heals bindings an older client's config rewrite may have stripped. **(c) Custody verification generalized to ring membership** (every standing op's senior key ∈ the held ring) — exactly as strong as the old single-key equality because only the client-side sole writer can put a key in the ring, and required for correctness once a fresh re-mint key can exist beside the burned one; a mismatch now also survives a one-convergence debounce before alarming (rationale in § Key custody and per-identity seniority). **(d) The tombstone signs with the ring key the standing head lists**, never a ring position — after a re-mint, the retired DID's log names the old key, and it is selected and signed with even though a fresher key leads the ring. Pinned by red-first tests at every layer (merge-union both directions; mint-never-reuses at the keyring level; the machine-level pin that a re-mint's `set_integration_level` carries a different pubkey than the burned key; the retire-path burn; the debounce both ways), each verified non-vacuous by a planted mutation failing at its named assertion. **Residuals, recorded honestly:** a key published whose *every* binding writer failed (directory unreadable for the identity's whole life **and** the retire-path write failing) would be reusable — two independent writers plus cross-device binding union make this a compound failure, and its consequence is the pre-fix behavior, not a new one; the archive itself still has **no reader surface** — no app shows a user which DIDs they have retired — a record kept for provenance rather than a feature. **The 72 h recovery-fork contest — MECHANISM LANDED 2026-08-02, ceremony the same day (next paragraph).** The remedy the seniority statement names is now constructible in-product. Four pieces, all client-side — the contest adds **nothing** to the nest, the wire, or the at-rest nest schema (decision 9), and reads only the public directory over the client's own connections. **(1) The consent record**: `contest_intents` in the `fauna.state.atproto-identity` rows (additive, union-merged on the `(did, contested_op_cid)` pair — the pair IS the scope of the consent — client-sole-writer via `record_contest_intent`). **(2) The shared-Rust builder** `fauna-client-atproto::recovery_fork`: `contest_plan` re-reads the verdict from `verify_audit_log` itself rather than re-walking the log, so "detection and remedy are two readings of ONE verdict" is structural rather than reviewed; `build_fork_op` carries the fork point forward as raw JSON (a field no version of this crate models is pinned to survive into the signed bytes); `sign_fork_op` reuses `sign_tombstone`'s exact canonical-cbor + low-S + `r‖s` discipline. **(3) The settings machine** composes the contest card from the directory's own log on every convergence and performs a consented contest, never an unconsented one — pinned by a test that arranges everything a hostile box can arrange (it names the DID, authors the violating op, and drives repeated convergences) and asserts nothing is signed. **(4) The card** is machine-composed (`AtprotoSettingsSnapshot.contest`) so seven apps cannot word an identity-compromise notice seven ways. Two rulings are worth carrying forward. **`HeldKeyNotSenior` is unreachable and is therefore an error, not a card state**: `verify_audit_log` gates every standing op on index-0 membership and stops at the first failure, so the op *before* the violation always has a held senior key — an op that lists a held key lower down is itself the violation, and gets contested rather than forked from. The residual check survives (it is what licenses a signature, and a license is never inherited), but as `ForkError::ForkPointSeniorNotHeld`. And an **unparseable `createdAt` does not close the window**: the deadline is advisory, the directory rules on lateness at submit, and refusing the remedy over a timestamp we could not read would hand the box a win it did not earn. Both terminal identity-custody gestures (`request_tombstone`, `request_contest`) are deliberately **outside** the machine's `uniffi::export` blocks until a shell renders their control, so neither ships as a dark capability; `request_tombstone` had drifted inside one and was moved out in the same commit. (tui consumes the machine as direct Rust, so its ceremony needs no export; the export lands with the first *native* shell that renders the control, per the same rule D10's delegation row followed.)

**The custody alarm names the remedy (2026-08-02, user directive).** `critical_alerts.atproto_custody_mismatch` is the only surface that fires when an identity is under attack, and it used to end *"do not trust it for anything sensitive, and contact whoever runs your nest"* — which, on this alarm specifically, pointed the victim at the party most likely to be the attacker and left the undo undiscoverable.
