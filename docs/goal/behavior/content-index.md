## Goal

One unified, Spotlight-style search across all of a user's own content — mail, calendar, conversations, posts, files, contacts, drafts, media — backed by a single per-user index. The index is built wherever the content can be read in plaintext, replicates to all of the user's storage locations, and references content that may be stored elsewhere via fetch-on-demand. It is itself one of the user's content kinds and follows the same encryption-at-rest rules as the rest.

## Two search backends today

Two distinct search stacks exist, and only one of them serves users today — a session building search work must not conflate them:

1. **The live FTS path (shipped, serving the Search page on every app).** `fauna.search.query` is the sole search wire surface (`bins/fauna-nest/src/search_handlers.rs`; its HTTP twin is deleted). The nest serves it from the **SQLite `content_fts`** table (`db/fts.rs::search_with_scoping`, called from `storage/sealed.rs::SealedStorage::search`) on **every** nest — the storage-mode axis is retired (`../architecture/nest/storage-modes.md`), and server-side search collapsed upward with it: `content_fts` is fed by the floor-derived corpus (public post bodies via `Post::body_text()` — the public preview when a post is gated — and profile handles/bios) plus, since 2026-08-02, the policy-gated public bridge corpus (§ Bridge content in the Search corpus), so every nest answers `fauna.search.query` from it and the former encrypted-mode `not_server_side` refusal is gone (`../architecture/encryption-at-rest.md` § Readable classes). Its `content_id` is `blake3(content_type:natural_id)` — an opaque FTS doc key, **not** the post/actor id (a result row cannot deep-link off it alone). The page-side behavior + this wire claim are owned by `../ui/search.md`. **Since 2026-09-09, `content_fts` gained a third, structurally different writer: a community conversation room's per-room derived view of its sealed log, built by the home nest only where the room's members grant it a read (a materialization grant, deleted on rotation).** This is private grant-scoped content, not the public floor-derived/bridge corpus above, and it does not (yet) participate in `fauna.search.query` — no query path keys off its `room-message:<room-id>` schema today, only the write-and-purge halves are built. The grant, the room-side mechanics and what still queries it are owned by [`community-rooms.md`](community-rooms.md) § The three classes → *Community*; this doc records only that the shared table now has this second class of writer.
2. **The per-user tantivy index this doc specs (built, and SERVING the Search page on every native app since 2026-08-03 — its one nest-side leg is deleted).** *(Corrected 2026-09-16: this line read "built, not yet queried by anything" long after the local arm was registered and serving — tui 2026-08-03, then macOS/iOS, android, linux and windows; see § Where queries run and § Status / plan state, which are the authorities on rollout. The stale wording mattered: it invited a session to treat a defect in this index as having no user-visible consequence.)* `libs/fauna-index` builds sealed segments only at a capability position, never the nest — but the Plan-5 mail leg violated that: **`IndexRegistry::ingest_mail` was LIVE via `routes.rs::spawn_ingest_mail` until 2026-07-12**, writing unsealed segments under the nest's `__index` folder — directly contradicting § Encryption posture below. (Its `ContentKind::Mail` tag was a decoy name: SMTP mail, which the Go MDA delivers via `fauna.bridges.ingest_inbound_mail`, never reached this indexer.) A prior revision of this doc claimed this arm "is retired with the storage-mode axis" — that was **false**; the Phase-4 demolition sweep that made that claim flow-traced a *different* system (`content_fts`, the SQLite FTS table backing `fauna.search.query` — see backend 1 above) and never touched this one. **Fix state (final, 2026-07-13): the nest-side writer is DELETED, not seal-retrofitted.** A nest-side seal was never implementable: the nest holds neither the MSEK nor the identity seed, so it cannot derive any index key (`../architecture/key-material-hierarchy.md` rule #7 places the master key in Path A, client-only, and the mail/calendar index-segment key in Path B, reachable only from a MUA credential at the MDA); the **symmetric master-key seal the crate ships** would have installed read custody on the nest (its holder can also *read*, which § Don't do these forbids the nest outright) — a property of *that primitive*, **not a general law**: the nest already write-only-seals content it provably cannot read, asymmetrically via HPKE, on the production D2 mail/CalDAV rails (`fauna_mls::wrapped_blob::seal_to_recipient`; correction ratified with the 2026-07-13 security verify, so a future session doesn't rule out write-only public-key sealing as such); and — the load-bearing half alongside the missing key root — compaction must read segments to merge them and nothing nest-side could ever serve a query, so even an HPKE write-only nest ingest is structurally incoherent. ## Bridge content in the Search corpus — the uniform per-bridge policy (ratified 2026-07-22, user-ruled; nest + shared Rust built 2026-08-02)

**User ruling (2026-07-22):** whether bridge content (Nostr events, Bluesky posts, ActivityPub posts, …) appears in the Fauna Search page is **one policy for every bridge — no per-bridge special cases**. This section owns the policy (it resolves what `../ui/nostr.md` § NIP-50 deliberately left unruled; that doc keeps only a pointer).

- **The split is by content class, never by bridge.** A bridge's **public** content (the public posts/events it relays, stores, or translates for the user) is eligible for the nest-side Search corpus — backend 1's `content_fts` — under the per-bridge controls below; public content is exactly the floor-derived class that table already holds, so the posture is unchanged. A bridge's **private** content (bridge DMs, Nostr gift-wraps, mail bodies) is **never** eligible for `content_fts` — it follows the sealed per-user index story (backend 2) like every private kind. Mail is the all-private case: already searchable via its own private path, contributing nothing to `content_fts`. This class split is what keeps the policy uniform: every bridge gets the same two-arm rule; no bridge gets a bespoke carve-out.
- **Per-bridge user controls** (app UI + nest state, the one-configuration-surface invariant), in increasing specificity: **(1)** the existing whole-bridge link/enable; **(2)** a **"show in search"** toggle — does this bridge's public content enter the Search corpus; **(3)** a numeric **"limit posts in search"** cap — how many of the bridge's newest posts stay indexed, the index load/churn control (bridge feeds are high-volume/high-turnover relative to first-party content). Both new controls are ordinary metadata-driven `BridgeSetting` rows (`bridges.md` § Bridge settings), supplied **uniformly by the provider registry** for every content bridge — never per-provider copies — so the settings surface needs no new machinery and no new ui.yaml IDs on the unified Bridges page; the dedicated bridge pages (nostr, mail-settings) mirror them through their existing settings surfaces (ID proposals at implementation, per UI consistency rule A). The cap needs an additive `number` `setting_type` (nest-side range validation; an old client skips the unknown type — additive evolution).
- **Indexing rides each bridge's nest-transit point, in lockstep — nobody runs an indexer** (the NIP-50 trigger-discipline precedent: the store is the indexer, by construction). With show-in-search ON, inbound public bridge content is indexed into `content_fts` at the existing path where it is stored or transits the nest, keyed by the standard `blake3(content_type:natural_id)` with a per-bridge `content_type` (`bridge.nostr` : event id, `bridge.bluesky` : at-uri, `bridge.activitypub` : object id); the same path's deletion/replacement/expiry arms remove the row (for nostr that means the NIP-09/NIP-40/replacement arms carry through). Known transit points: the Nostr relay store + the sync worker's inbound sweep; the AP inbox ingest. The Bluesky feed leg is currently a live proxy (`bluesky.feed.thread` translates on demand) — its indexable transit point (feed ingestion vs. notification sync) is pinned by the implementing session, honestly: a bridge whose content never rests on the nest indexes only what actually transits.
- **Dedup with native translations, by construction:** only **inbound, foreign-authored** content indexes. An outbound translation of a native Fauna post never indexes — its body is already in `content_fts` as the Fauna post — because the indexing hook lives only on inbound ingest paths; double-surfacing is structurally impossible rather than filtered after the fact.
- **Eviction = newest-N per bridge.** The cap is enforced at ingest: an insert past the cap evicts the oldest indexed row for that bridge (a recency window). Toggle-off **purges** the bridge's rows; lowering the cap prunes to it — both structural at the setting-write path, same lockstep discipline.
- **Defaults (works-out-of-the-box):** show-in-search **ON** with a moderate default cap, a hard Rust constant (order 1000: generous enough that a normal bridge feed's search horizon feels complete, bounded enough that a firehose-grade bridge cannot balloon the nest's FTS table); the user adjusts per bridge from the app.
- **Scope boundaries:** the relay-internal NIP-50 FTS (`nostr_event_fts`) is untouched — it serves the Nostr protocol surface, never `fauna.search.query`. Backend 2 is untouched. Search-page rendering of bridge rows (result-card shape, deep-linking off the natural id — `content_fts`'s opaque key cannot deep-link alone) is `../ui/search.md`'s domain.

## Engine and shape

- **Engine:** Tantivy 0.26 (since 2026-10-05, index format v4; Rust-native Lucene-equivalent), wrapped by the shared crate `libs/fauna-index/`. Chosen because its on-disk segment is already an immutable inverted-index file — the unit we ship as a sealed encrypted blob — and it gives BM25 + positions + phrase + multi-field for free. (Alternatives reviewed and rejected — SQLite FTS5, stork/Pagefind, custom `fst`+`roaring`, KV stores, service-process search engines — in that spec's D2.)
- **An engine bump is an index-format bump — and its migration is the retirement the index already has (ruled 2026-10-05, on the move from Tantivy 0.22 to 0.26; landed the same day in bump round 1 as v4 with the floor at 4).** A sealed segment's body is the engine's own `RamDirectory` serialized file by file — `meta.json`, the segment artifacts, `.managed.json` (`libs/fauna-index/src/index.rs`, `seal_to_bytes`) — so a Tantivy release that changes its index format changes the bytes of every segment, and a build on the old engine cannot open a segment the new one wrote. Three consequences, each a mechanism this doc or [`../architecture/version-compatibility.md`](../architecture/version-compatibility.md) § 2.2 already has: **(1) the bump raises BOTH numbers.** `CURRENT_INDEX_FORMAT_VERSION` because the format changed, and `MIN_READER_INDEX_FORMAT_VERSION` with it, because the change is non-additive. The floor is not optional: left at its old value, an older build would read the newer manifest as *newer-compatible*, fail to open its segments, and take the master class's rebuild arm (§ Encryption posture, *a blob that will not open under the key we hold*) — overwriting the manifest a newer build wrote, which that build would retire in turn, the two devices rebuilding the class at each other for ever. Raising the floor makes the older build refuse at the manifest, before it touches anything, with the typed `Incompatible` the builder already treats as permanent — healed only by updating the app (`fauna-client-index`, `IndexBuildError::is_permanent`). **(2) The migration is the tombstone-only retirement, because the index is derived.** A build on the new engine skips every segment stamped below its format at resume and the resuming builder tombstones it; the next walk re-stages the corpus — exactly the v3 retirement (§ Where the index is built, *Retirement mechanics*); no blob is deleted and nothing a user cannot recreate is touched, so I1 is satisfied and no user gate applies. The older build's local search for the class answers honestly ("update the app") until it updates; the nest never reads the index, so client↔nest interoperation is untouched. **(3) When it may land.** A floor raise is a compatibility break of the index's at-rest format: after the 2026-10 baseline it is a major-version event under I3 — or the build ships both engines for the transition window, keeping the old engine's dependencies (the usual reason for the bump) in the build. **Before the baseline it is free**: under the user's blank-slate rulings ([`../architecture/compat-remnant-sweep.md`](../architecture/compat-remnant-sweep.md), the 2026-10-04 paragraphs — no client and no nest is running anywhere; nothing is kept for backwards compatibility) not one segment or manifest exists at rest, so the Tantivy 0.26 move lands as an in-place cutover with no fixture, no dual-engine build and no compat arm: v3 → **v4 with the floor raised to 4**, the second free raise after v2's (§ Encryption posture, *Version pair*). The index format's declared breaking versions are therefore 2 and 4; a third needs the I3 window.
- **One logical index per user (per actor),** partitioned by content kind for query performance. Each kind's index is a set of immutable Tantivy segments; once written a segment is never mutated (new content → a fresh small segment; compaction — build work at build positions, ruled 2026-08-02, § Where the index is built — merges them).
- **Per-document fields:** content kind, content ID, timestamp, sender/author actor ID, and tokenized searchable text (body, subject, participants, …) — plus, eventually, classifier tokens (`tag:dog`, recognised OCR text, transcript words). **No stored fields:** the index holds tokens + metadata, not a copy of the source text — snippets render from the fetched content, not the index, which keeps the index ~25-30 % of plaintext instead of ~60-80 %.
- **Tokenizer:** the shared one in `libs/fauna-mail/` (NFKC, UAX#29 word segmentation, Unicode-aware lowercase, length/alphanumeric filter, sorted dedup) — byte-deterministic across platforms, so the same content tokenizes identically wherever it's indexed.

## What's indexed

All of the user's own content kinds — including content received from others (inbox mail, accepted calendar invites, group conversations they're in). It does **not** index other users' private corpora. Content the user only sees as a participant inherits the encryption posture of *the user's own* storage of it, not the original author's.

**On-device-junked mail is never indexed (stated 2026-08-03; structural, not a rule the builder enforces).** The receive path skips a record the on-device spam scorer suppressed *before* it reaches the ingest chokepoint the index seam sits on (`poll_inbound_mail_pages` `continue`s on `suppress_from_view`), so junk never reaches a builder in the first place. That is the intended posture — spam out of the user's search results, as it is out of their inbox view (`mail-spam.md` § Re-file timing) — and it is worth stating because nothing in the index layer would tell a reader it holds: a future change that indexed *before* the suppression check would silently put junk back into search results with no index-side code appearing to change. Mail the user later un-junks is re-presented on the next launch's mailbox re-walk, so recovery needs no separate re-index path.

Per-kind rollout: mail first (Plan 5 built a nest-side ingest — **unsealed, a bug; deleted 2026-07-13, see § Two search backends today** — so mail ingest now starts over at Plan 5b's capability position); calendar, conversations, posts, files, contacts, drafts later (Plan 9). Media (photos / video / voice) is indexed by **classifiers** — OCR (Apple Vision / Google ML Kit / Tesseract), image tags (MobileNet/EfficientNet ONNX), audio transcript (whisper-tiny ONNX), audio event tags (YAMNet ONNX), video (sampled frames + audio). Classifiers emit *tokens* that flow through the same Tantivy pipeline as text — no second index, no vector store; tag tokens get a `tag:` prefix so the user can filter explicitly. Caption / embedding models (BLIP-2, CLIP) are deferred. The classifier **ledger** (which classifier ran on which content, at which model version) plus the first classifier land in Plan 7; the rest in Plan 8. Classifier *model invocation* is app glue per platform (Apple Vision binding, ONNX runtime, …); `fauna-index` owns the ledger and the token ingest.

## Where the index is built, and where it lives

The index is built where the content is readable in plaintext — a capability position, never the nest. **Plan 5's nest-side ingest build violated this (unsealed, on the nest); it is deleted as of 2026-07-13 (§ Two search backends today) — nest-side ingest is retired for good, not pending a retrofit.** Every other kind is built by something holding the user's keys — the **MDA bridge** during an active MUA-AUTH session (which holds only the MSEK-derived mail/calendar index-segment key, so it builds and queries **only the mail and calendar slices** — `../architecture/key-material-hierarchy.md` rule #7), or a **user client** that owns the content (holds the full index master key, so it builds **every kind** — conversations / posts / contacts / drafts / media included). Plan 5b is the capability-position ingest with **two builder legs, and the sequencing is ratified (2026-08-02, S0(c) of the backend-2 rollout): the client-builder leg ships FIRST, the MDA leg second.** The client leg is pure shared Rust + existing sync (no Go FFI regen, no bridge session machinery), delivers the actual user story (private search in the apps' Search page) for **all** kinds rather than mail/calendar-over-IMAP, and every mail-kind byte it writes already uses the per-kind key split — so the later MDA leg *reads and extends* the same slices, redoing nothing. The MDA leg's independent value (IMAP `SEARCH` served from the sealed mail slice) is real but narrower, and it also carries the `MlsSnapshotBlob` grace-field shipment (§ Encryption posture / Path B-sibling-4) — **that grace field landed 2026-08-03, ahead of the rest of the leg, together with the `MailcalKeyRing` reader that consumes it** (`../architecture/owner-key-material.md` § Path B-sibling-4 → *Snapshot carriage* owns both). **The FFI seam the Go half calls landed 2026-08-03 too** — `FfiMailIndexSession`, minted from the session's `MlsCapability` so the MSEK never crosses the boundary, driving the *same* shared builder the client leg uses over an `FfiIndexRail` the bridge implements with its own transport. **Both Go halves landed 2026-08-03 — the leg is complete.** The MDA now resumes a session index at MUA-AUTH (from the same `MlsCapability` and snapshot plaintext its record opener parses), implements the `FfiIndexRail` over `fauna.bridges.index_{record,list}` plus the blob route, stages every hint plaintext its body-search pass already decrypts, and flushes a sealed segment + manifest at the end of that pass — so the user's mail slice is built at the bridge capability position and replicates to their devices. **The build rides the decrypt the search was going to pay for anyway**, rather than adding a second pass over the mailbox; a nil session (no snapshot, older nest, rail failure) is a normal state that simply builds nothing, exactly as the client leg skips a builder launch rather than failing login. **Serving `SEARCH` *from* the slice landed 2026-08-03, and it is a HYBRID rather than a swap** — the shape is forced by how the slice is built. Because the MDA indexes only what a body search made it decrypt, the slice holds whatever earlier searches happened to cover and is never "the mailbox"; answering purely from it would silently under-report, and scanning everything anyway would make it pointless. So each `SEARCH` asks the slice **which of this mailbox's messages it can answer for** and takes its verdict for those — skipping their HPKE opens entirely, which is where the leg's performance actually comes from — while everything else is scanned exactly as before, and the two verdicts union. Coverage is the **queryable** set (the opened reader's live content ids), deliberately *not* the builder's re-index guard: the guard also holds messages staged but not yet flushed, and the flush is best-effort, so a guard-based answer would drop a message whose segment never reached the rail out of `SEARCH` results with no error anywhere. Any index-side failure collapses the covered set to empty, degrading the pass to the pre-index scan bit for bit — a rail outage costs latency, never an answer. The AND semantics `SEARCH BODY` requires are served by a **second query entry point** (`Index::query_all_of`), not by the Search page's parser one, which stays OR-by-default because that is right for a Search page and wrong for IMAP; it builds the boolean query directly from tokens rather than assembling a query string, which removes the parser's escaping surface along with its default. **Its byte route needed a nest change nobody had noticed was owed:** `PUT /api/v1/blob/{cid}` was session-bearer-only, and the MDA holds no session bearer — see `webdav-server.md` § Bulk-byte plane, which owns that route's auth. Both legs landed 2026-08-03 (client leg S3, MDA leg S5); **the MDA leg's build half was RETIRED 2026-08-10** by the carrier ruling below — its query half (the hybrid `SEARCH` serve) is the leg's whole remaining job, and the prose above describing its staging/flush is history, not current shape. Phase D (the storage trait) landed 2026-05-11.

**The mail-kind content id is the RFC `Message-ID`, and that binds BOTH legs — the MDA leg does not honour it, which makes its query half inert (declared 2026-08-05).** The spelling was already ratified twice ([`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers, v1's stage-time-guard bullet, split out 2026-08-11; and § *Thresholds* below, whose "structurally always 0 %" rests on it) and is the shared seam's stated contract — *producer-owned and stable across devices, which is what makes an independently built segment dedup against another's* (`libs/fauna-conversations/src/index_sink.rs`). The client leg honours it, including the manager's synthetic `<hex(nest message id)@fauna.inbox>` fallback for a message that carried no header (`libs/fauna-conversations/src/backends/smtp.rs`). **The MDA leg keys on the bare hex of the nest's 32-byte message id instead** (`bins/fauna-bridges/internal/mda/imap/index_rail.go`, `indexDocID`) — not by preference but because the RFC `Message-ID` never reaches it: `IndexSegment` carries only the nest id, the nest does not store the header (`bridge_imap_messages` has no such column and in encrypted mode must not), and the sealed hint's plaintext is `tokenize(subject + body).canonical_bytes` — a flat token stream with no identity in it (`bins/fauna-nest/src/bridge_routing_handlers.rs`). Three consequences, in increasing severity:

- one message touched by both legs sits in the slice **twice**, under two ids, and neither leg's stage-time guard sees the other's copy (the guard is an exact `content_id` set) — unbounded at-rest growth on the user's store, and a fold that can never collapse the pair;
- an MDA-staged doc's navigation target is a nest storage id, not a thread id, so a row rendering from it cannot be opened (`../ui/search.md` § State & data shape);
- **the MDA's coverage question can never intersect a client-built slice, so the leg's payoff is zero exactly where the slice is richest.** `answer_body_search` decides coverage by byte-equality of the caller's candidates against the index's live content ids, and hex strings are disjoint from RFC `Message-ID`s **for every message** — with a header (`<a@x>` vs hex) and without one (`<hex@fauna.inbox>` vs bare hex) alike. Measured 2026-08-05 against a client-keyed slice: `covered=[] matched=[]`. So on any actor whose desktop app built the slice — the ships-first leg, which re-walks the *whole* mailbox every launch and so covers far more than opportunistic staging ever does — every `SEARCH` pays the full HPKE scan with nothing anywhere reporting it. The leg accelerates only against its own hex-keyed docs, which are the duplicates in the first bullet.

**Why the obvious fix is wrong, recorded so it is not re-derived: a per-message *sealed* identity carrier reintroduces the exact cost the leg exists to remove.** Coverage must be decided *before* any hint is opened, so a sealed `nest id → RFC Message-ID` field on `IndexSegment` would cost one HPKE open per candidate per `SEARCH` — and an HPKE open is dominated by the **KEM decapsulation, which is per-blob and independent of payload size** (more so under X-Wing), so opening a small ref instead of a large hint saves essentially nothing. A fix must therefore carry the identity either **unsealed** — meaning the nest stores the RFC `Message-ID` in plaintext, a new resting cross-account correlator that is a `path-sealing.md` / `../architecture/encryption-at-rest.md` question rather than a free choice — or **once per session instead of per message**: a client-published mapping, or coverage keyed on an additive *secondary* doc field the client leg populates rather than on the content id. Which of those wins is **RULED in the next paragraph (2026-08-10)**, and the ruling retires the MDA's build half (its staging was redundant wherever a desktop app existed, and was the only reason the duplicates accrued). Whatever the carrier, **no fix may make the guards fuzzy** — the `(kind, content_id)` key is what makes the upsert exact, so the answer is one spelling plus a real carrier, never a looser comparison.

**The carrier is RULED (2026-08-10, refutable-advisory): coverage moves onto an additive *secondary* doc field — the raw nest message id, written by the client leg — and the MDA's build half is RETIRED.** The client leg holds both identities in the same frame where the content id is chosen (`backends/smtp.rs` builds the synthetic fallback *from* the nest id), so every mail doc it stages now also carries `secondary_id` = the 32-byte nest message id; `answer_body_search` decides coverage — and translates matches back — against the live secondary ids, while the content id stays the ratified RFC `Message-ID` everywhere. The two rejected carriers, with grounds so neither is re-derived: **unsealed at rest is refused on posture** — Phase 3 deleted every plaintext-at-rest path for mail content in both modes (`../architecture/encryption-at-rest.md`), `bridge_imap_messages` deliberately rests only `from_norm`, and the RFC `Message-ID` is a stable cross-account correlator (the same value rests in every recipient's store); reintroducing a plaintext content-derived resting identifier to serve a *derived, re-buildable* index inverts the priority order. **The per-session sealed map is refused because its one advantage over the secondary field is empty** — the map is client-published, so it covers exactly the messages a client has already staged; an actor with no client-built slice has no map either, so the build half it "preserves" would build for nobody the secondary field abandons, and what remains is pure cost: a second unbounded rail artifact with its own compaction story, plus a translation layer. **The accepted cost is small and already ratified**: an actor with no client builder degrades to the pre-index hint scan — exactly what § Build vs. query ratifies for a builder-less actor, and exactly that actor's pre-S5 behavior — and the docs the MDA build half contributed were the corpus's worst (mis-keyed by the defect this section declares, un-navigable on the Search page per the second consequence above, subject-less, epoch-sorted when `StoredAt` was absent). Retiring the writer removes the duplicates at their source instead of teaching every reader about them. **Retirement mechanics**: the schema field is a format change, so the sealed-segment format bumps to v3 — *additive* (field handles resolve by name, so a v2 binary reads an all-v3 slice; the reader floor stays 2) — and each leg's resume tombstones pre-v3 mail/calendar-class segments before opening (tombstone-only, the ratified retirement; the index is derived and re-buildable, so no user gate applies), which retires the MDA's hex-keyed segments and heals the client's own field-less ones through one mechanism, with the next walk re-staging the corpus. The MDA's staging pass, its flush, and its nest-side write surface (`fauna.bridges.index_record`, the blob-PUT `IndexSegment` mint purpose) are removed in the same change — the MDA and nest ship in one image, so there is no skew window in which a deployed MDA still publishes. **The fix owes a cross-leg pin**: stage as the client leg keys, ask as the MDA asks, assert coverage — plus the one-document assertion — because the pre-fix tier was blind by construction (every case staged and asked in one self-consistent spelling).

**Ingest triggers, v1 — moved 2026-08-11 → [`content-index-ingest.md`](content-index-ingest.md)** (heading text unchanged — `§ Ingest triggers, v1`, and its `→ *sub-bullet*` citations, resolve there by changing only the file; the 42 source/test citations of this section deliberately keep pointing at this stub, one hop away). How the client builder learns there is content to index: the two arms every kind is built from (the receive-hook observer seam; the one-shot backfill, which mail takes as a stage-time guard instead), the per-kind arms that ride them (the Conversation catch-up and its boundary, drafts and contacts as snapshot kinds, posts and files as append kinds, media refuted for v1), the arm-attach lifecycle, per-kind doc identity, advisory ingest cursors, and the ratified **third-ingest-class template** every later kind starts from.

- **Where the builder lives: a new `libs/fauna-client-index` crate (native apps only — web is the declared exception). CREATED 2026-08-02 (S3).** It owns builder orchestration (the sink implementation, backfill passes, cursoring, sealing under the S0 keys, publishing over the fauna-sync file plane as the `__index` reserved set — the same per-actor reserved-set footing as `__drafts`) plus the synced-replica refresh and the local query handle the Search seam calls. `libs/fauna-index` keeps its scope (format, seal, query primitives); app glue only registers the sink and renders. **Built so far:** `MailIndexBuilder` — the mail-slice sink, staging on the receive path and, at flush, tokenizing into one immutable segment, sealing it under the MSEK-derived key, and publishing segment-then-manifest through an **async** `SegmentPublisher` seam (the sync rail is injected, so the crate carries no sync dependency). Staging is synchronous and non-blocking, which is what lets the receive-path seam keep its no-blocking contract; every await lives in `flush`, which the debounce trigger drives. **Publish order is load-bearing**: a crash between the two leaves an unreferenced segment (harmless, re-created — the advisory cursor never advanced), where the reverse order would leave a manifest pointing at a blob that does not exist. The production `SegmentPublisher` (`IndexRailPublisher`) landed 2026-08-03 — see the `__index` rail bullet below for its shape and the segment ceiling — and with it the **synced-replica refresh**: `resume_mail_builder` opens the published `manifest-mailcal.idx` off the replica (list → blob GET → unseal with the MSEK-derived key) so a returning device appends to the same segment chain and inherits the advisory ingest cursor, instead of restarting segment ids and re-walking the mailbox; a never-published actor gets an empty manifest, which is the first-run path and not an error. The **local query handle** landed the same day: `open_mail_reader` fetches every *live* segment the manifest names (tombstoned ones are skipped, which is how compaction's tombstone-only rule reaches query results without a blob ever being deleted), unseals each, and opens them as one queryable index — an actor with nothing published yields an empty reader, so *no local results* is a normal state rather than an error. **The builder's production lifecycle: BUILT 2026-08-03.** Every piece above was unreached code until app glue resumed a builder at login, registered it as the index observer *before* the receive loop starts, and drove `flush` from the debounce; all three now exist, on the shape the ordering requirement dictates. Resolving a builder is asynchronous (derive the key from the mail custody's MSEK, then list + open the published manifest), but the observer must be registered before the first poll — so the launch rides **`start_receive_loop`'s async prologue**, awaited to completion before the poll task spawns, exactly as the cross-device MLS replica restore does (`devices.md` § Cross-device MLS group-state sync, slice 5). That makes the ordering **structural rather than a race**: a spawned resume would have to win against the first mail page, and losing silently costs that launch's mail its searchability. The seam is `fauna_conversations::backend::IndexBuilderLauncher` (`async fn launch(&self) -> Option<Arc<dyn MessageIndexObserver>>` — tantivy-free, so this crate gains no builder dependency, the `MlsSyncLauncher` shape); the native implementation is `fauna_client_conversations::NestMailIndexLauncher`, which lives there because that is where the MSEK is loaded — **the rule that the MSEK never leaves Rust is about app glue, not crate boundaries**, so app glue passes a `NestClient` and receives an opaque observer, never a key. An arm that cannot resume at launch (mail not enabled, or a transient rail failure) is a normal non-fatal state that starts the loop with that arm absent — **and it is retried, not deferred to the next launch** (see the attach-later bullet below; the pre-2026-08-05 wording said "nothing is lost: the next launch re-walks the same mailbox", which is true *across* launches and false *within* one — the gap that wording licensed is exactly what the e2e found). Flush is **debounced, never per-message** (`fauna_client_index::spawn_flush_debounce`): a quiescence window that each staged doc extends, plus a periodic backstop and a logout flush, so a whole-mailbox re-walk coalesces into few segments instead of publishing one per message — the `segment_backup.rs` push-debounce shape. Pinned end to end by `libs/fauna-conversations/tests/index_launch_ordering_tests.rs` (first-pass mail reaches the observer, which only holds if the launch precedes the poll task).
- **How a segment reaches the nest: a dedicated `__index` rail kind — NOT the generic `fauna.sync.changes.record` (established at code level 2026-08-02, after a design pass concluded the opposite).** The publisher writes **one whole blob per path** into the blob store and the nest appends the `sync_changes` row **at the DB layer** — structurally `__drafts` (`bins/fauna-nest/src/db/drafts.rs`, `record_drafts_blob_change`; the retired `__config` rail had the same shape), and exactly the at-rest shape S2's standing pin already stages. Bulk bytes ride HTTP (the WS-RPC frame cap is 2 MiB — `fauna_core::transport::MAX_RPC_WS_MESSAGE_SIZE`; bulk binary is the HTTP carve-out), so the rail kind carries only `(path, blob hash, size)`. **Two independent reasons the generic record kind is closed to this, both refuted the "upload chunked, then record" plan:** (i) the nest *refuses* a reserved (`__`) set on that kind unless it is a custody-copy destination, and a rail must never be one — a custody record lands in `backup_custody` with `seq = 0` and deliberately never enters the `sync_changes` device-pull feed this design depends on; (ii) the nest's GC classifies a hash referenced only by reserved sets as a **direct blob** — pinned as the bytes themselves, never walked for chunks — so a chunked manifest recorded there would have its live chunks swept, silent unrecoverable loss on a user at-rest store. Pinned by `bins/fauna-nest/tests/conformance_folders.rs` `changes_record_refuses_a_reserved_rail_so_no_client_writer_can_use_it`. **Consequence for sizing: a segment must stay one blob** — the builder bounds segment size at flush rather than spilling to the chunk route (a hard-coded Rust constant; no human would choose it), and compaction (§ Where the index is built) respects the same ceiling. **No provisioning step precedes the first write:** the rail mints lazily via `get_or_create_reserved_folder`, so a fresh home nest needs no `fauna.sync.register`. **The byte route is `PUT /api/v1/blob/<cid_b32>`** (bearer-authed, raw-codec CID, `blake3(body)` verified server-side, idempotent under a repeat PUT) — *not* the multipart `POST /api/v1/blob`: a sealed segment is opaque bytes with no `UploadSidecar` class to declare, and the PUT branch stores them without the sidecar/strict-flip pipeline. **BUILT 2026-08-03 (S3):** `fauna_client_index::IndexRailPublisher` over `AuthClient` + `NestClient` — no sync-engine dependency of any kind — with the client-side ceiling at 8 MiB under the nest's 10 MiB `BLOB_BODY_LIMIT`; flush enforces it by capping docs per segment and halving an oversize batch, so a large backfill yields a segment *chain* rather than a blob the rail cannot carry. End-to-end proof (real router, real socket, real client): `bins/fauna-nest/tests/conformance_index_rail_publisher.rs`.
- **What bounds the rail, and the one axis deliberately left OPEN (closed/named 2026-09-20).** `record_index_blob_change` writes through the **unmetered** `record_sync_change`, which a reserved rail may do only while it is bounded by *construction* rather than by the storage quota ([reserved-folders.md](reserved-folders.md) § Drafts Sync → *The enumeration is closed on purpose*). `__index` is the **fourth** rail to take the write-time history collapse that bound rests on — [file-versions.md](file-versions.md) § Retention owns the rule and the three properties a rail must satisfy before joining, and this rail satisfies all three: its history is reachable by no wire surface (`fauna.index.list` is a per-path head reader and reserved sets are scoped out of the versions kinds), every path holds one **whole** blob rather than a delta (the publisher writes one whole blob per path — bullet above), and only rows strictly below the head are ever marked. Without it, the two manifests — rewritten on every flush — pinned one blob per flush **permanently**, an unbounded resting cost an honest builder reached just by running. A segment path is written once, so the same call no-ops there, and no reader is disturbed: a fold's tombstoned segments keep their own live rows and their blobs stay at rest (§ Compaction), so a replica mid-refresh on an older manifest still resolves every segment that manifest names. **And `size_bytes` is verified rather than believed:** `record` refuses a declared size that is not the held blob's real length, because that figure is what `fauna.index.list` reports back and what the shared fold planner budgets its merges on — a wrong one misplans every later compaction of the slice. **The axis left open, stated rather than enforced: the count of segment paths.** A fold retires a segment by tombstoning it in the manifest and leaving the blob at rest (§ Compaction — tombstone-only; physical reclamation is a distributed-GC question and deferred alongside the D7 ledger), so a long-lived account's retired segments accumulate as live rail rows that GC must keep pinning. Two things make closing it *not* this rail's move, and both are structural rather than scheduling: the nest may never read or sweep `__index` (§ Don't do these), so it cannot learn which segment a fold retired — tombstone state lives inside the sealed manifest — which makes any delete verb **client-driven** by construction; and a nest-side cap on the segment count would refuse an honest builder's next segment with no recovery path, since segment ids come from the manifest's own monotonic counter rather than from anything the nest can reset. So the order is: the distributed-GC precondition § Compaction defers, then a client-driven delete verb, then metering if the key space is still open. Until then this is a **named open bound**, not a closed one. **Its consequence for the read side is already taken: `fauna.index.list` and `fauna.bridges.index_list` are PAGED** (2026-09-20), lifting the shape the backup rail ratified (`fauna.backup.generation.list`) rather than inventing a second one — the page is cut at the frame byte budget, the cursor is the `path` itself (already a total order, since `path_hash` is `hash(path)`), and both clients walk to the cursor's absence. An unbounded path count makes this a correctness matter rather than an efficiency one: past the 2 MiB frame cap the unpaged reply was *undeliverable*, so a large enough index could never be refreshed again by its own owner. Additive in both directions, which the byte-budget cut is what buys: a pre-paging client sends no cursor and gets a reply at least as complete as any the frame could ever have carried, and a pre-paging nest ignores the fields and answers complete, its absent cursor ending the walk after one page. **A page may be empty while the walk continues** — the bridge plane's mail/calendar-class filter runs after the page is read, so a walk stops at the cursor's absence and never at the first empty page.
- **The rail has two planes, and the split is structural rather than a policy choice. BUILT 2026-08-03 (S5's authorization piece).** `fauna.index.{record,list}` are the **user plane**: User-class and *self-scoped* — the owning actor is the authenticated connection actor, so neither request carries an `actor_id` and a client only ever reaches its own `__index`. `fauna.bridges.index_{record,list}` are the **bridge plane**: BridgeMda-class and *explicitly targeted*, because the MDA connects as its own service actor and must name the MUA session's actor — the shape every MDA-on-behalf-of-user kind already uses (`fauna.bridges.fetch_mls_snapshot_blob`), rate-limited per (bridge, target) on a synthetic `_index` credential. **The MDA could not simply have been admitted to the user plane**: those kinds have no `actor_id` to name a target with, so admission would only ever have published into the *bridge's own* rail — and keeping them separate makes the inverse abuse unrepresentable too, since a `User` has no field with which to spoof another actor. **The bridge plane is mail/calendar-only, enforced on the PATH** (§ Encryption posture; § Architectural rules #3): `record` refuses a master-class path as an authorization error and `list` omits master-class entries, so a leaked MUA credential reaches neither the master-key slices nor even their per-kind segment counts. It must be the path rather than the bytes because **the seal carries no class discriminator** — both classes share the framing and its magic — so the nest, which holds no index key, has nothing else to decide on; `fauna_index::path_key_class` is that decision, total over every path the rail accepts. Pinned by `bins/fauna-nest/tests/conformance_content_index_rail.rs` (both planes, every master-class path, and the list filter).

Once built, the index **replicates to every storage location the user owns** — each of their apps and each of their nests — over the existing fauna-sync protocol, as the reserved folder **`__index`** (one instance per actor, on the same per-actor-scoped footing as `__drafts`/`__mail`; `libs/fauna-index/src/paths.rs`), holding `<kind>/seg-N.idx` segments + `manifest.idx` listing the live segments. Updates originate at the builder and propagate by additive merge; conflict/merge semantics are owned by `docs/goal/behavior/conflicts.md` § Conflicts (auto-resolve + version-retention — a dependency).

**Build vs. query is not the same question.** A device can *query* an index someone else built and synced without ever running the indexer. *Building* at a capability position is a steady background workload (decrypt → tokenize → seal → sync); iOS's background-execution budget makes "a phone is the builder" unreliable, and Android's is only somewhat better. So the realistic model is **a desktop app (or the MDA bridge during a session) builds and syncs; phones receive the segments and query the synced copy.** A user whose only device is a phone may have a lagging-or-empty index until a builder device comes online — that spec covers a foreground-incremental fallback for that case.

**How the split is enforced, since 2026-08-03 — a build-time constant, not a flag.** On the four UniFFI apps the decision is `fauna_ffi::index_launch::CLIENT_BUILDS_INDEX`, `false` on the iOS/Android targets and `true` on the desktop ones: the `conversations_session` factory wires the builder only where it holds, while registering the **query** side on every target, so a phone searches segments a desktop published and synced. It is a constant rather than an app-supplied flag because no human chooses it (the one-configuration-surface invariant's bucket 1 — `principles.md`), and `fauna-ffi` compiles once per target, so `cfg!(target_os)` *is* the derivation. **The same constant feeds the Task-delegation picker's `index` kind** (`participants.md` § The assignment picker), which is what stops a client from offering a self-pin its build can never honour, or withholding one it can — the two-directional drift the 2026-08-03 per-(client, kind) correction was made for. tui and linux, being direct-Rust desktop consumers, wire the builder unconditionally. The phone-only foreground-incremental fallback remains unbuilt.

**Compaction is build work — it runs only at the ratified build positions; no compaction grant exists (RULED 2026-08-02).** Merging segments must open them in plaintext (Tantivy has no ciphertext merge), so "who compacts" is identically "who reads the slice" — and the ruling adds **no new reader**: compaction requires exactly the read+write reach building already has, so any position that can build a slice compacts it, and only those positions ever do. Concretely: **user apps** compact every kind — phones included, because compaction is episodic and strictly cheaper than the ingest that produced the segments (no content fetch, no per-message decrypt), so it rides the same foreground-incremental budget § Build vs. query already gives a phone-only builder; a phone-only user's index compacts foreground-paced, like their ingest, never "never". The **MDA bridge in-session** compacts the mail/calendar slices it already builds and queries (the session-scoped index-segment key opens everything mail/cal compaction touches; lands with the S5 leg — no new key reach, and *not* a grant: it is the existing ratified capability position).

- **Mechanism (v1): fold-at-flush, in the builder. BUILT 2026-08-03.** A flush that would append segment N may instead merge its staged docs with small live segments its manifest view lists, publishing one merged segment and a manifest that tombstones the folded ones — same segment-then-manifest publish order, same wholesale manifest-rewrite discipline, same concurrency envelope as the flush path, so it adds **no new race class**: a lost manifest race degrades to an unreferenced segment (harmless, re-created) or an un-taken compaction (retried at the next threshold crossing), exactly the designed flush outcomes. **No exclusivity is required, and the D7 synced job ledger stays deferred to Plan 7** — compaction pulls nothing forward. The implementation is `fauna_client_index::compaction` (the pure input planner) plus `MailIndexBuilder::prepare_fold` / `plan_flush` (the rail I/O and the manifest write); `Index::merge_segments` — which had no production caller from its creation until now — is what does the merge. **The fold is best-effort by construction:** every reason not to fold (not eligible, nothing small enough under the one-blob ceiling, a merged result that turns out to exceed it) falls through to the ordinary append, which is always correct. Planning happens *off* the manifest lock because it does rail I/O, so the live-segment view can be stale by the time the write commits — deliberately unguarded, since `tombstone_segment` no-ops on an id that is no longer live, the merged segment's docs dedup against any surviving copy by `(kind, content_id)` at query time, and no blob is ever deleted. The worst outcome of a race is redundant bytes at rest, never a wrong or missing result.
- **Thresholds (ratified here — previously only an `index.rs` doc comment; hard-coded Rust constants, not a config surface — no human would choose these):** a kind is compaction-eligible past **16 live segments**, and a segment past **25 % tombstoned docs**. Read the first as *strictly past*: 16 live segments is fine, the 17th makes the kind eligible. **The second is inert for the mail slice in v1, and that is a property of mail rather than an unimplemented piece** (recorded 2026-08-03 when the compactor was built): a tombstoned doc is one superseded by a newer version of the same content id, and a mail content id is the immutable producer-owned RFC `Message-ID` which the stage-time re-index guard ([`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers, v1) declines to re-stage — so a mail doc is written once and never superseded, and the fraction is structurally always 0 %. It stays inert for every kind built so far, and **the drafts arm did not make it live either — it removed the reason to expect it to** (2026-08-05; [`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers, v1 → *Drafts are a snapshot kind*). Drafts were the case this bullet named, on the assumption that a mutable kind would append superseding docs; instead a snapshot kind republishes its whole corpus into a single segment and tombstones the rest, so it never has more than one live segment and neither criterion governs it. The measurement is therefore owed by the first **append** kind whose docs are superseded — which no currently planned kind is — and until one exists, `KindManifest` recording `next_seg_id` / `live_segments` / `tombstoned_segments` and **no doc counts** is a gap with no caller rather than a missing piece of a shipped feature.
- **Tombstone-only — a compactor never deletes segment blobs.** Folded segments move to the manifest's `tombstoned_segments`; the blobs stay at rest and in sync. Physical reclamation of tombstoned blobs is a distributed-GC question (no replica may still list the blob live) and is **deferred** alongside the D7 ledger — this rule is what keeps every compaction race non-destructive. Pinned as of the 2026-08-03 build: a fold leaves every superseded blob on the rail, never lists an id as both live and tombstoned, and a stale fold view degrades to a no-op instead of a manifest naming a blob that does not exist.
- **Why not a capability grant (option B), distinguished from the shipped re-score drain rather than dismissed by reflex.** The drain's `content.read{mail}` conveys **Path-B** material — a key class whose non-client exposure is already part of the ratified threat model (`key-material-hierarchy.md` rule #7's MUA-credential blast radius); it widens *who*, inside an existing class boundary, for obligations targeting content that rests **only nest-side**. An index compaction grant would wrap an **index key**: for the master class that is **Path-A material under an owner-only-unconditional ruling** (`key-material-hierarchy.md` § Index master key) — the first Path-A conveyance the system would ever mint, unshrinkable below the whole cross-kind master-class corpus (the scope rule, `encryption-at-rest.md` § Don't do these: a shared seal key cannot be narrowed by a `kind` string, and per-kind index keys do not exist), and **standing trust-until-revoke** (index keys have no content-sealing-epoch regime — mail epochs seal mail records, not index segments — so a "windowed" compaction grant would be exactly the theater `encryption-at-rest.md` § Capability tiering warns about). And the index's at-rest topology removes the drain's necessity argument: the index **replicates to its readers** — every querier is a key-holder with a local copy — so no consumer exists whose segments are real but who lacks a local position to compact them; compaction's entire payoff is query latency, queries run only at key-holding positions, and any such position folds locally. **No compaction grant is minted this major.** If a future major revisits granted index re-processing (re-indexing on a tokenizer bump over master-class kinds is the named harder case — `encryption-at-rest.md` § Capability tiering), the recorded preconditions are per-kind index keys (scope rule) and an index epoch regime (real windows), and the venue is the grant registry in `encryption-at-rest.md`.

**Retiring a superseded doc — a segment REWRITE, and the one reach `add_doc` does not have (RULED + BUILT 2026-09-16).** An append kind can need a doc retired without becoming a snapshot kind: mail's content id is the producer-owned RFC `Message-ID`, and the Message-ID collision rule ([`conversations-at-rest.md`](conversations-at-rest.md) § Receiving into the conversations view) lets a `Sent` copy **displace** a squatting `INBOX` one, so the content under an id this device already indexed is replaced. Why re-staging cannot finish the job is the substrate fact [`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers, v1 leans on for drafts: `Index::add_doc` issues a `delete_term` before its insert, but only within **one writer**, and `open_multi_segment` copies each already-sealed input in as-is — so the superseded doc stays queryable from its old segment and `merge_segments` does not collapse it either (both pinned by `libs/fauna-index/tests/cross_segment_supersession.rs`). **The asymmetry that makes retirement possible is about *which* writer issues the delete:** a writer that has already published segment N cannot reach back into it, but a writer opened **over** segment N can. `Index::rebuild_with(segments, replacements)` is that writer — it opens the holders as inputs, puts each replacement through `add_doc` so its own delete lands on the copied-in segment, and merges so the dropped docs go physically rather than surviving as a `.del` bitset riding the seal. **Shape and bounds, so this is not mistaken for a second snapshot kind:** the rewrite touches only the live segments that actually *hold* a replaced id (found by opening them — the manifest records which segments are live, never which ids each holds), it publishes one new segment and **tombstones its inputs exactly as a fold does** (retirement stays tombstone-only, like compaction's and the drafts supersede's — no blob is ever deleted), and it is **not gated on the compaction threshold** because it is owed rather than opportunistic. It is bounded by the holders themselves — each was already under the one-blob ceiling and comes back one doc lighter and one heavier — and an over-ceiling result **declines to the ordinary append**, the same non-destructive fallback an over-ceiling draft corpus takes: the stale copy stays queryable until a later flush retires it, which beats a segment the rail cannot carry. The read-back is real rail I/O and is affordable only because it is **rare**: nothing pays for it but a flush that actually carries a displacement. **Why this is a rewrite and not the drafts republish:** a snapshot kind bounds at-rest growth by rewriting its *whole corpus* per change, which is right for a corpus the size of a user's drafts and pathological for a mailbox — the same reasoning that kept posts append-shaped ([`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers, v1 → *Drafts are a snapshot kind*). Rewriting only the holder keeps the cost proportional to the event.

**The builder and the advisory task lease (RULED 2026-08-03; BUILT the same day on tui + linux, macOS 2026-08-17, windows 2026-08-24 — every builder now seated; [`participants.md`](participants.md) § Implementation status today owns the per-seat state).** `index` is one of the Task-delegation surface's heavy kinds, and the client builder **heartbeats its advisory lease for the lifetime of its attachment** — the lease primitive, cadence, and the display/pin semantics are owned by [`participants.md`](participants.md) § Coordination primitive → *The `index` kind under the lease*. What the lease **gates** is this doc's to own, and the rule is shape-based, not kind-based:

- **A stand-down may bind only build work whose queue re-presents.** The two build shapes differ structurally. **Pass-shaped** work re-derives its queue from durable state every time it runs — the launch catch-up walk (the receive loop re-pages the whole mailbox every launch and the stage-time guard recomputes the missing set, [`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers v1) and any future versioned re-index pass — so work skipped while yielding is retried by construction, exactly the property that makes `backup-upload`'s per-pass gate safe. **Stream-shaped** work sees each item once per session: the receive-path trickle's doc flows past the seam and is gone until the next launch's re-walk, so a stood-down seat's skipped docs would leave live, *visible* mail silently unsearchable on that seat until some later relaunch — a coordination dependency under a correctness property ("a mail that arrived this session is found", the tier_3 Success pin), bought for savings that are marginal because the trickle rides decrypts the receive path already pays for. **So: the lease gates the catch-up backlog and any future full-corpus pass; it never gates the trickle.** Every live builder stages and publishes its own arrivals regardless of who holds the lease — the same scope line the delegation policy itself draws (heavy background kinds under the policy; foreground/incremental work outside it — [`participants.md`](participants.md) § Task delegation → Concepts).
- **A corpus its store offers exactly once is stream-shaped — `Draft` has no catch-up window at all (found at code level + built 2026-09-25, while building the phone-finds witnesses).** The rule above is shape-based, and the draft corpus fails its test: `DraftStore` hands the seam the whole corpus once per compose change and once when the observer is registered ([`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers, v1 → *Drafts are a snapshot kind*), and nothing ever re-presents it — no sweep, no walk, no re-page. Yet the builder started **every** kind it stages inside a catch-up window, and the gate starts closed until the lease loop's first observe lands (a few hundred milliseconds, deliberately erring closed), so the registration re-offer raced the gate; a lost race withheld the corpus, and a withheld draft corpus is not "retried by construction" — it is lost on that seat until the user's next keystroke there. On the phone-finds shape the loss is total: a draft written on a phone is restored by the desktop at launch and indexed by no other seat, so the desktop losing that race leaves the draft unsearchable everywhere, silently. So `Draft` is the one kind with no catch-up window (`fauna_client_index::index_builder::has_catch_up_window`, total over `ContentKind`), and a stood-down seat stages and republishes its draft corpus like any live arrival — the redundancy is the bounded kind the next bullet accepts: one small snapshot rewrite per extra seat per change, converging by the tombstone-only supersede. Contacts' snapshot is different and stays a gated pass: it rides a reconcile walk that re-runs at attach and on every sweep. Pinned by `index_builder.rs` (`a_stood_down_seat_still_stages_the_draft_corpus`).
- **Launch-walk backlog is never offered to an UNDECIDED gate — the launcher awaits the lease's first answer (RULED + BUILT 2026-09-25, found at code level while building the phone-finds witnesses).** The gate starts closed until the lease loop's first observe→decide lands, and the pass-shaped kinds' launch offers are each made **once** per launch: the Conversation attach walk runs the instant `launch()` returns, the mailbox re-page on the first sweep after it. A closed-by-default gate withholds both, unrecorded (`a_withheld_backlog_doc_is_not_recorded_as_indexed` keeps the door open for a *later* re-offer — but nothing re-offers them until the next launch). That is fine on a seat that stands down, whose holder builds the same corpus, and a whole-session silent loss on the seat that turns out to WIN: its own restored history unsearchable until relaunch, and on the phone-finds shape indexed by no other seat. The race is the lease's first round trip against the arm resumes inside `launch()` — the walk itself does no I/O — so it is lost more often than "a few hundred milliseconds" suggests. **The ruling is the first of the three candidates: await, not re-offer or accept.** `NestMailIndexLauncher::launch` holds, after the arm resumes and before it returns (so the wait overlaps round trips already in flight), until the coordinator reports its first step complete (`LeaseCoordinator::settled` — a decision **or a failed attempt**, since a failure leaves the gate closed and the retry a heartbeat period away), bounded by a ceiling (`index_lease::FIRST_ANSWER_CEILING`); a late arm's attach (`ensure_arm`) waits the same way. Past the ceiling the walks are offered to a gate that errs closed — the accepted cost, now confined to a nest that answered the arms' rail reads but not one observe. Re-offering on gate open was not chosen: the `lease_changed` pump wakes only the coordinator, a gate-transition signal to the receive loop would be new machinery, and a mid-session open has nothing to re-offer (the previous holder built that backlog); acceptance was not chosen because the loss is silent and lands on the sole builder's first launch. A consequence: the Draft registration re-offer above no longer races the gate either, though Draft keeps no catch-up window on its own shape-based ground. Pinned by `libs/fauna-client-conversations/tests/index_lease_first_decision_tests.rs` (the launch suspended while a fake nest holds the observe reply; the ceiling paid, not skipped) and `fauna-client-delegation`'s `settled_flips_after_the_first_step_whatever_its_outcome`.
- **The redundancy this accepts is the small, bounded kind.** N live desktop builders each publish each new arrival: redundant bytes at rest, converging in results via the `(kind, content_id)` query-time dedup — the same worst-case family as the fold race above. What the gate eliminates is the N× *full-corpus* republish at first-build and re-index scale — the events whose redundancy grows with the corpus and is unreclaimable in v1 (tombstone-only, no GC).
- **The catch-up boundary is the session's first mail sweep — already a structural fact of the receive loop, not new machinery.** The first `poll_mail_feeds` of a session pages from UID 0 to the live tip in one call (`poll_inbound_mail_pages` loops until the source reports no more); everything after it is trickle. The build adds the *signal*, not the boundary. **Built 2026-08-03** as `MessageIndexObserver::observe_catch_up_complete` (default no-op, so an observer that does no pass-shaped work is structurally unaffected), fired once per session by the receive loop's mail-poll site. **One rule the build had to add, because the ratified wording did not reach it: only a sweep that completed *without a feed error* closes the boundary.** An errored poll never advances its cursor, so the walk is unfinished and the next sweep re-pages the same mail — closing on it would reclassify the entire remaining backlog as trickle, which the lease never gates, handing a stood-down seat exactly the N× full-corpus republish this section exists to prevent, and doing so precisely on the unlucky launches. Pinned over an ordered journal rather than an end state (`libs/fauna-conversations/tests/index_catch_up_boundary_tests.rs`): on a single seat, gated and ungated reach an identical end state once the walk finishes, so an end-state assertion here is a zero pin.
- **On battery, the tiering answers itself:** a desktop that is not currently a candidate (unplugged) yields the lease, so backlog-scale passes wait for a plugged-in builder — while its trickle continues, being foreground-incremental work outside the policy, the same split a phone-only deployment already lives with.
- **The MDA bridge is not a lease participant.** It has no device identity and no Task-delegation row, and its staging rides the body-search decrypts an active MUA session already pays for — marginal build cost ≈ 0, so there is no redundancy worth coordinating; its convergence is the same stage-time guard + query-time dedup. The S5 leg must not grow a lease client.
- **S4 inherits the rule as stated, kind-agnostically:** whatever a master-key builder's re-presentation shape turns out to be per kind, the gate binds the pass-shaped part and never the per-arrival trickle.
- **Compatibility is additive by construction:** the heartbeat is new behavior over the existing `fauna.delegation.{heartbeat,observe}` wire, constants stay hard-coded Rust, and an older client that never heartbeats simply keeps today's ungated behavior — overlap is the safe direction under idempotence, so mixed fleets converge with no wire or at-rest change.

## Where queries run — per app

A query runs against any readable copy of the index. The nest never holds an unsealed copy to query, on any box (the storage-mode axis is retired; `../architecture/nest/storage-modes.md`):

| | Query path |
|---|---|
| **Native apps** (Linux, Windows, macOS, Android, iOS, tui) | query their **synced `__index/` replica locally** via `libs/fauna-index` — directly on Linux and tui (direct-Rust consumers, no FFI hop), via UniFFI on the other four; the nest has nothing to query |
| **fauna-web SPA** | **no search over THIS index** until a fallback ships (§ open item below) — Tantivy can't run in a browser, so there's no local replica to query and no local arm; what web has is backend 1 alone, the floor-derived server-side `fauna.search.query` over `content_fts` (§ Two search backends today), so a search on web can still succeed, fail and say so — it just never finds the private corpus |

*(Table = target state. **Since 2026-08-03 the first row is real on tui**: its Search page queries this index locally through the shared `LocalSearchIndex` seam and merges those rows with backend 1's — see § Status / plan state. Every app still calls backend 1 — `fauna.search.query` over `content_fts` — per § Two search backends today. Local-arm registration by app, as of 2026-08-31: tui (2026-08-03), macOS + iOS (2026-08-04), android (2026-08-09), linux (2026-08-10, `conv_backend.rs::start_conversations_session`) and **windows (2026-08-31, `SearchResultsPage.xaml.cs`'s `Page_Loaded`, attaching on every load rather than once at a persistent post-login hook — windows rebuilds its `FfiSearchManager` per page visit today, so each visit is its own retry point)** attach it — every native app now registers the local arm.)* All native apps use the same shared query path (`fauna-index`'s `query(query, kinds, range, limit) -> Vec<QueryHit>`); the fauna-web SPA is the one app that can't, and that's a property of the **browser sandbox**, not of any platform — **the native iOS app indexes and queries locally exactly like the other native apps** (decided 2026-05-11; the earlier "iOS uses WS-RPC like web" wording in some docs was conflating the native app with the fauna-web SPA opened in mobile Safari). Results pointing to content stored on another of the user's locations come back as a pointer; the client follows up via fauna-sync's on-demand fetch — if that location is offline, the result is shown with a "content unavailable, [device] offline" indicator.

**One arm, one reader per key class — the composite (BUILT 2026-08-05).** The manager holds exactly **one** local-arm slot, deliberately: which readers exist is a native-side fact the engine-free shared manager must not learn. But the per-kind key split gives the index **two** classes with two manifests and two keys (§ Encryption posture), so a device that can search everything it holds needs **two readers**. Composing them behind one `LocalSearchIndex` (`fauna_client_search::CompositeLocalSearch`) is what reconciles those: glue registers one arm, and the classes stay separate types holding separate keys behind it — the query-side mirror of the build side's per-class fan-out (build fans out; query fans in). **This is also the fix for a gap that had made every master-class kind unsearchable.** The Conversation kind gained a producer and a place in `MASTER_KINDS_BUILT` on 2026-08-05, but app glue filled the single slot with the *mail/calendar* reader alone, whose class map answers `None` for every master kind and whose MSEK-derived key opens a different manifest — so conversation segments were sealed, published and replicated with **no query path able to read them back**, indistinguishable from never having been built and with no error anywhere. That is precisely the *Registration happens at BOTH ends of the pipeline* rule below, broken in the same rollout that recorded it, and the rule `MASTER_KINDS_BUILT`'s own doc comment states. Two consequences now structural: the master reader's kind ceiling derives from `KindClass::kinds()` rather than a hand-listed constant, so a new kind cannot be silently absent from it; and **a member that errors fails the whole arm** rather than degrading to a partial answer — a result list silently missing one class reads to the user exactly like that content not existing, which is the failure this slice removes. Each class is independently optional (the mail reader needs an MSEK that exists only once mail is enabled; the master reader needs only the identity seed every logged-in actor has), so an actor with neither yields no arm at all and the resolver re-asks on the next query.

**A kind resolves the way its content is shaped, not the way the first kind was.** The master reader's lookup seam was message-shaped (`locate(message_id)`), which fits Conversation because a Conversation doc's content id *is* its `MessageId`. Drafts extended that seam rather than reusing it (`locate_draft`, added 2026-08-05): a draft has no message to select inside a thread, so it resolves from the live `DraftStore` and navigates to the **composer** holding it (`SearchNav::Draft`, whose `thread_id` is `None` for the thread-less new-thread compose). Resolving from the live store rather than the index is also what keeps a *stale* hit honest in both directions — the rendered snippet is always the draft's current text, and a draft discarded since its segment was sealed resolves to nothing and is **dropped** under the existing unresolvable-hit rule (`../ui/search.md` § State & data shape) instead of opening an empty composer.

**The third ingest class resolves the same way, one step further out: from the live corpus over the wire, at query time (RULED 2026-08-05).** A third-class kind (contacts, posts — [`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers, v1) has no client-resident store, so the only live corpus is the nest-resident one, and the resolver performs the kind's own read before the arm's rows surface — one whole-book `query_cards` resolving every contact hit in a single round trip; one `fauna.posts.get` per post hit, bounded by the page size. It is the drafts honesty rule at wire distance: the snippet is the content's *current* text, and a hit whose read finds nothing (a deleted card or post) is DROPPED, which is what makes deletion display-correct with no index mutation. Three consequences, stated rather than left to be discovered: **the local arm is not near-instant for these kinds** — it settles within the same network envelope as the nest arm, which the page already waits for (`in_flight` holds for both; `../ui/search.md` § State & data shape); **an offline or failed resolve yields *no local rows* for these kinds, never an error row** — the existing no-reader posture; and **the refuted alternative is a client-resident replica of nest content per kind**, which would trade one wire read per query for a per-kind store with custody, staleness and sync obligations this design deliberately avoids — the index stores postings and snippets render from fetched content (§ Don't do these), and this *is* that fetch, paid when needed. Mail's own resolution differs in timing, not in kind: `locate_message` answers from an in-memory store *populated by the launch walk's own network reads* — resolve-at-launch versus resolve-at-query, never local-versus-impossible.

**fauna-web SPA content search — open item.** None of the fixes ship today; whichever is picked is tracked here, in the content-index design's § Search availability by nest mode × client, and tracked internally:
- query a peer device's index over the nest relay (cleanest — needs a peer-query endpoint + an "is an indexed device online?" signal);
- an MDA-bridge query backend (narrow — only while a bridge session is live);
- adopt wasm-threads workspace-wide (big — touches the toolchain pin, the build pipeline, every wasm crate, plus COOP/COEP cross-origin-isolation headers on the SPA host);
- upstream tantivy gains a thread-free indexing mode, or we vendor a patched tantivy with the thread spawns stubbed for `target_arch = "wasm32"`.
The realistic near-term answer is "the web SPA has no content search over this index" — acceptable because every *native* app (iOS included) does, and the web SPA still gets floor-derived server-side search over `fauna.search.query` (§ Two search backends today).

## Encryption posture — what's plaintext where

The index follows the same encryption-at-rest rule as the content it describes (full treatment: `docs/goal/architecture/encryption-at-rest.md` § Search and indexing):

- **On the nest:** every segment is AEAD-sealed under a per-segment data key (wrapped under a per-kind key, below); the nest stores and relays opaque blobs and can never read or query the index. Segment entries' location pointers are index-encrypted too, so only the index-key holder learns "this entry references content on location X." **`IndexRegistry::ingest_mail` violated this until 2026-07-12 (§ Two search backends today); the writer is deleted, and an idempotent boot reconcile purged the residue with sync tombstones (2026-07-13), restoring "the nest never holds an unsealed index"** — vacuously today (no kind has nest-side ingest; Plan 5b builds at capability positions only), and by the seal once Plan 5b lands.
- **Per-kind key split — the MDA bridge's index reach is mail/calendar only (`../architecture/key-material-hierarchy.md` rule #7, the blast-radius invariant).** So the bridge can build and query the mail + calendar slices during an active IMAP/CalDAV session without holding the cross-kind master key: the **mail-kind and calendar-kind** segments' data keys are wrapped under an **MSEK-derived index-segment key** (Path B — reachable from the MUA credential), while **every other kind's** segments (conversations, posts, contacts, drafts, media) are wrapped under the user's **index master key** (Path A — derived from the identity seed since the 2026-08-04 re-root, client-only, never reachable from a MUA credential; `../architecture/owner-key-material.md` § Path A-sibling owns the derivation). This requires `manifest.idx` to be **split per kind** — a small mail/calendar manifest sealed under the MSEK-derived key that the bridge opens, separate from the master-key manifest covering the rest — rather than one master-key-sealed manifest. **Consequence:** a leaked IMAP/CalDAV credential reaches the user's mail/calendar search slices and nothing else; unified cross-kind "Spotlight" search stays a Fauna-app capability (apps hold both keys and query across all slices in one pass — see § Where queries run). **Concrete shape (RATIFIED 2026-08-02, S0 of the backend-2 rollout; BUILT in `libs/fauna-index` + `libs/fauna-mls` the same day, S1 — no production caller yet, the first writer is S3):**
  - **Two manifest files, split by key class, same payload type and CARv2 framing:** `__index/manifest.idx` stays the **master-key manifest** and covers exactly the master-key kinds (conversation, post, file, contact, draft, media — and `classifier-ledger.idx` stays master-key too); a new `__index/manifest-mailcal.idx` is the **mail/calendar manifest**, sealed with the same master-direct AEAD framing but under the **mail/calendar index-segment key**, covering exactly the kinds mail + calendar. A kind never appears in the wrong-class manifest — the implementation refuses a wrong-class `append_segment` rather than trusting convention. A client (both keys) opens both files and unions the kinds; the MDA bridge opens only `manifest-mailcal.idx`.
  - **One builder per CLASS, holding a kind SET — the structural consequence of one manifest per class (BUILT 2026-08-05).** A builder rewrites its manifest wholesale on every flush, so two builders of one class would each publish a manifest naming only their own segments and silently strand the other's: the blobs stay on the rail, referenced by nothing, indistinguishable from never having been built. `IndexBuilder` therefore holds the set of its class's kinds that this seat builds, groups each flush's batch by `IndexedDoc::kind`, publishes **one segment per kind and then a single manifest listing them all** (the segments-before-manifest order is unchanged, and for the same reason), and the launcher claims arms **per class** rather than per kind so a second master kind's sweep finds the master arm already attached. Per-kind state stays per kind throughout — segment id chains, advisory ingest cursors, and the catch-up window ([`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers, v1 — *The boundary signal is per kind*), the last because a boundary describes exactly one kind's backlog. Which kinds a seat builds is a hard-coded Rust list, not a configuration surface (`principles.md`, bucket 1): a kind joins it once it has **both** a producer feeding the seam and a query-side resolver, so adding one lights up search rather than building an index the page cannot show. Today that list is `[conversation, draft, contact, post, file]` for the master class (contact joined 2026-08-06, post and file 2026-08-10) and `[mail]` for mail/calendar — calendar shares the mail class's key and manifest but has no producer yet. A kind in the set may be **append-shaped or snapshot-shaped** ([`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers, v1 → *Drafts are a snapshot kind*); both flush through the same builder, and the difference is only whether the flush appends its segment or supersedes the kind's previous ones.
  - **Version pair: both numbers raise 1 → 2** (`CURRENT_INDEX_FORMAT_VERSION` and `MIN_READER_INDEX_FORMAT_VERSION`, stamped by both manifests and both seal framings). The split is breaking — a v1 reader consulting only `manifest.idx` would silently see no mail/calendar kinds (data invisibility; a v1 compactor could GC their segments as unreferenced) — and the bump is free today because not one byte of the format exists at rest (`libs/fauna-index/src/version.rs`). Writers emit the stamp through `header_prefix` (AEAD-bound), per § Before Plan 5b item 2.
  - **The mail/calendar index-segment key** is MSEK-derived with the ratified context string `"fauna.mail.index-seg.v1 2026-08-02"`; its full key entry (derivation, rotation, grace, snapshot carriage) is owned by `../architecture/owner-key-material.md` § Path B-sibling-4 — the client derives it from the account's MSEK (its mail custody) for the client-builder leg; the MDA derives it from the session MSEK, with rotation grace carried in the snapshot per that entry. **The snapshot grace field (`index_seg_grace_keys`) is BUILT as of 2026-08-03** — the first piece of the MDA leg, landed ahead of its reader so the list is already at rest in published snapshots by the time anything relies on it.
  - Mail-kind and calendar-kind segments wrap their per-segment data keys under this key (same 48-byte wrapped-data-key segment framing, different wrap key); every other kind's segments and both master-direct files keep the keys stated above.
- **A blob that will not open under the key we hold is a STATE, not an error — and what that state means differs per key class (BUILT 2026-08-05).** Only *absence* used to be a fresh start, so a manifest sealed under superseded key material wedged its arm forever: every resume failed identically, the launcher retried each sweep, and the only witness was a warn promising a recovery that could not come. The two classes recover differently because their keys do. **Master class → rebuild:** the class is treated as unbuilt, the arm attaches with a fresh manifest, and the next flush republishes under the current key (the predecessor's blobs stay on the rail referenced by nothing — nothing is deleted, and the source content the index derives from is untouched). This is the ratified drop-and-re-index answer for a succession (`../architecture/owner-key-material.md` § Path A-sibling), and it is sound *here specifically* because the master key is convergent — seed-derived with no grace ring, so every device of the account derives the identical key and none can be discarding what a sibling still reads. **Mail/calendar class → surface it:** that key rotates through a grace ring (§ Path B-sibling-4) precisely so a rotation in flight is survivable, so a miss can be a merely stale ring, and rebuilding would answer a recoverable miss by discarding a corpus other devices still read. Two conditions bound the rebuild arm and both are load-bearing: it fires on an **AEAD failure alone** — a blob that unseals cleanly and then fails to decode still surfaces, because *written by a newer build* must never be healed by overwriting (`../architecture/version-compatibility.md` § 5 item 9) — and an unopenable **segment** rebuilds the whole class rather than being skipped, since a manifest that opens over segments that do not is the half-rewrapped state, and skipping would leave them listed live while the index silently answered short.
- **On a client:** the client holds the keys, so it can read its own index — exactly as it reads its own mail / conversations / etc. The `__index/` folder replica it syncs holds the **sealed** segments (that's the canonical synced shape, and what arrives from the nest); the client unseals them with its index master key to query. The working index it actually queries is decrypted (kept on disk or rebuilt per session — an implementation choice) and is protected only by the device's OS disk encryption, like everything else the client stores locally. There is **no "sealed at rest on the client" requirement**: sealing exists to keep an *untrusted box owner* out, and on the client the user *is* the box owner.

Re-indexing (on a tokenizer or classifier-model version bump) needs read access to the content plus write access to the index: a local pass at a capability position — during an active bridge session, or driven by a client (the nest never holds the index master key). The index format is versioned; replicating locations agree on the version before merging.

## What an app has to know about all this

Deliberately very little — the shape lives in shared Rust, not in per-app glue (priority #2):

- **`libs/fauna-index/`** (linked directly on Linux and tui, via UniFFI on Windows/macOS/Android/iOS, via WASM on web — though the WASM build is on hold) owns the segment format, the manifest, AEAD seal/unseal, the classifier ledger, compaction, and re-index orchestration. App glue calls it; it doesn't reimplement any of it.
- A client that participates in the index folder needs two things: the **`__index` reserved folder name** (per-actor-scoped, so fauna-sync mirrors it) and possession of the user's **index master key** (so it can unseal segments arriving from an encrypted nest — which it has, because it has the MLS key material the index key derives from).
- For *querying*, a client needs even less: it calls `IndexHandle::query(...)` and renders the hits. The minimal exposed surface (Plan 4) is `create_in_ram` / `add_doc` / `commit` / `query` plus the value types; sealed-segment opens (`open_encrypted`), manifest reading, classifier-ledger calls, and snippet rendering are added by Plans 5/6/7 only as a client actually needs them. Nest-only operations (manifest write, key rotation, path conventions) get no FFI exposure.
- The Search-page UI reads a shared snapshot and forwards gestures — see `docs/goal/ui/search.md`. No app composes result-card text or makes ranking/filter decisions itself.

## Architectural rules

1. **One engine, shared.** Search is `fauna-index`/Tantivy everywhere it runs (native apps, the MDA bridge during a session). No per-app search implementation; no second index path for classifiers (they emit tokens into the same pipeline). The fauna-web SPA, which can't run Tantivy in a browser, is the documented exception — it keeps the floor-derived `fauna.search.query` (backend 1) and has no content search over this index pending a fallback, never a bespoke browser index.
2. **The index is one of the user's content kinds.** It obeys `encryption-at-rest.md` — sealed on every nest, plaintext only on a client the user owns; never readable by the nest; never crosses user boundaries (each user owns their own index; no nest-spanning "all users" index).
3. **Build where plaintext is readable — a capability position, never the nest (the storage-mode axis is retired); query anywhere with a readable replica.** User apps build every kind; the **MDA bridge builds and queries mail/calendar only** (it holds only the MSEK-derived mail/calendar index-segment key, never the cross-kind master key — `../architecture/key-material-hierarchy.md` rule #7, blast-radius invariant). All locations with a readable replica can query the slices their keys open. **Compaction is build work and runs only at these positions** (ruled 2026-08-02 — § Where the index is built).
4. **Tokens are canonical and platform-deterministic.** Same `fauna-mail` tokenizer everywhere; a tokenizer or classifier-model version bump implies a versioned re-index.
5. **Where logic lives:** shared Rust by default — `libs/fauna-index/` (index, ledger, seal, compaction, re-index), `libs/fauna-client-index/` (builder + replica orchestration on native apps — [`content-index-ingest.md`](content-index-ingest.md) § Ingest triggers, v1), `libs/fauna-mail/` (tokenizer). App glue is limited to classifier model invocation (platform-native APIs), sink registration, and rendering the Search snapshot.

## Don't do these

- **Don't reimplement search per app.** Call `fauna-index`. (On an encrypted nest each device *does* hold a synced local copy of the index and runs the shared engine over it — that's the design, not per-app divergence.)
- **Don't give the nest a way to read or query the index.** No in-process keys on any nest; decryption authority is the MDA bridge during a session or the user's clients. (`encryption-at-rest.md` admits one further authority in principle — a holder of a user-minted grant, its § Capability tiering — but **no index-key grant exists this major**: compaction was ruled client/MDA-side 2026-08-02 (§ Where the index is built), and a master-class index grant additionally has unmet preconditions recorded there. This bullet forbids *standing, ungranted* nest read custody; it is not contradicted by that ratified grant primitive.)
- **Don't give the MDA bridge the cross-kind index master key (or let a MUA credential reach it).** The bridge's index reach is mail/calendar only, via the MSEK-derived per-kind key; the master key (covering conversations / posts / contacts / drafts / media) is client-only — `../architecture/key-material-hierarchy.md` rule #7. Wrapping non-mail/calendar segments under a key the bridge can reach would broaden the IMAP/CalDAV blast radius onto the whole search corpus.
- **Don't index across user boundaries.** Per-user index isolation is the privacy property.
- **Don't store the source text in the index.** No Tantivy stored fields; snippets render from fetched content. (Storing it would roughly double the index and re-introduce content the AEAD nonces stop fauna-sync from de-duplicating.)
- **Don't paper over the SPA's no-search-on-an-encrypted-nest gap with a fake/empty in-browser index.** Surface it honestly in the Search page; pick one of the open-item fallbacks if it matters.
- **Don't add a second index path for media / classifiers.** Tokens only, same pipeline.
- **Don't put a boot-time `__index` reconcile back on the nest.** The old one deleted every `__index` blob on every nest boot without inspecting a byte — correct while the only such blobs were the retired nest-side writer's unsealed residue, a **data-destroying bug** the moment a capability-position builder syncs real sealed segments in. It is **deleted as of 2026-08-02** (slice S2) and must not return in any form, gated or narrowed: `__index` is a user at-rest store the nest cannot read, so the nest has no basis for deciding any of it is disposable. Pinned by `bins/fauna-nest/tests/index_survives_nest_restart.rs`; see § Before Plan 5b writes its first byte.
- **Don't hand-assemble a seal header or bypass the format's version stamp.** The at-rest format carries the `(format_version, min_reader_version)` scheme and an AEAD-bound header prefix (*ibid.*); a breaking change raises the reader floor rather than silently reshaping the bytes.

## Before Plan 5b writes its first byte — two hard constraints

Plan 5b (capability-position ingest) is the moment `__index` stops being empty and becomes a **user at-rest store**, synced across a user's devices. Two things must be true *before* the first real segment is written, and neither can be retrofitted afterwards without a migration no reader in the field could perform.

**1. The boot purge must be REMOVED (not narrowed) — it is a content-blind `__index` shredder. ✅ DONE 2026-08-02 (rollout slice S2).** `bins/fauna-nest/src/db/index_purge.rs` (`purge_unsealed_index_folders`), called on **every** nest boot from `bins/fauna-nest/src/lib.rs`, enumerated every `__index` folder, tombstoned every live path through the sync journal, dropped the snapshots, and deleted the blobs. It **never inspected a byte** of any blob, had no format sniff, and was deliberately *not* marker-gated ("an idempotent boot reconcile, not a marker-gated migration"). That was exactly right while every `__index` blob in existence was unsealed residue from the deleted nest-side writer (§ Two search backends today) — deleting all of it was the remediation of a security finding. But it was unconditional: **the moment Plan 5b syncs correctly-sealed segments into `__index`, the next nest boot would tombstone and delete them.** So the purge was **deleted, not gated** — its residue-cleanup job is finished (every nest purged long since), and deleting is safer than inventing a predicate that could let residue survive and reopen the finding. **Sequencing (ratified 2026-08-02, S0(f)): the purge deletion (S2) lands in the same landing window as the first real writer (S3) — the same merge, or immediately before it.** It landed *immediately before*, which the ratification names as the benign side (nothing writes `__index` until S3; deleting later would have destroyed S3's first synced segments on the next nest boot).

**What now holds the line, permanently:** nothing on the nest boot path may delete `__index` content again — the module, its `db/mod.rs` registration and its `lib.rs` call site are gone, and the spot carries a comment saying why it must stay gone. The standing pin is `bins/fauna-nest/tests/index_survives_nest_restart.rs` (tier_3): it stages sealed `__index` segment + `manifest-mailcal.idx` blobs at rest, drives the **real shared serve loop** (`desktop_serve::run_serve_loop` → `start_server`, the whole boot), and asserts both journal rows are still `created` and both blobs still exist. It is deliberately written against the whole boot rather than the deleted function, so any *future* boot reconcile that sweeps `__index` reddens it too. (Red before S2 for exactly the right reason — the purge tombstoned the staged segment path.)

**2. The at-rest format is already versioned — do not un-version it.** `libs/fauna-index/src/version.rs` carries the `(format_version, min_reader_version)` two-number scheme (`version-compatibility.md` § 2.2, backlog item 10), and **both** the manifest payload and the two seal framings stamp it; the manifest additionally carries a `#[serde(flatten)] extra` catch-all and a version *peek*. This landed *before* any writer existed precisely so Plan 5b inherits it: a newer-additive index reads on an older build (I2), a newer-breaking one refuses with the typed `IndexError::Incompatible` and is left byte-for-byte intact (I1). The **per-kind manifest split** below (§ Per-kind key split) is the first real consumer — it is a *breaking* manifest change, so it must raise `MIN_READER_INDEX_FORMAT_VERSION`, not silently reshape the payload. **Ratified 2026-08-02 (S0): the split raises both numbers 1 → 2** — `CURRENT_INDEX_FORMAT_VERSION` and `MIN_READER_INDEX_FORMAT_VERSION` — stamped by both manifests and both seal framings; free today because no byte of the format exists at rest. The seal header's 8-byte prefix is AEAD-bound, so the version bytes are authenticated: a writer must emit its stamp through `header_prefix`, never hand-assemble a header.
