## User Experience

### Automatic Snapshots

Snapshots are created automatically by the scheduler, which checks every ~60 seconds for folders that have received new changes. When a folder has been quiet for the configured quiet period after a change, the scheduler creates a snapshot. No user action is required. Whether a given folder is snapshotted at all, and how long its own quiet period is, are the nest place's per-folder policy — § 8b.

### Manual Snapshots

Users can also create snapshots on demand at any time via the `fauna.filesync.snapshot.create_folder` WS-RPC kind. This is useful before a risky operation (bulk delete, large reorganization) or when the automatic schedule is too infrequent.

### Browsing Snapshots

Users can list all snapshots for a folder, inspect the file listing for any snapshot, and compare two snapshots to see what changed between them. Each entry shows path, size, modification time, and a BLAKE3 content hash.

### Restoring Files

Two restore paths are available, and both are **client-side reassembly** (ratified 2026-07-14): the client fetches the manifest + chunks by store key over the kept bulk-binary routes and decrypts locally — the nest holds ciphertext it cannot open (§ Security Properties; `file-sync.md` § Content-Addressed Storage), so plaintext can only ever exist where the keys live.

- **Single file** — retrieve any file from any snapshot by its `manifest_hash` (the snapshot file listing carries it): fetch the manifest, fetch each chunk, decrypt, verify the content address, reassemble. Suitable for retrieving an accidentally deleted or overwritten file. The shared-Rust walk is `fauna-sync-engine`'s `download_file_bytes_by_manifest` (native); a wasm twin for control-plane apps follows the `MediaBlobFetcher` seam precedent (`fauna-media-machine`).
- **Full restore** — restore an entire snapshot to a local directory, optionally filtered to a path prefix for partial restore. It is an app surface: pick the snapshot over `fauna.filesync.snapshot.*` and a destination directory, then run the same per-file client-side walk into it (§ 4 owns the walk, which apps have the surface, and the retirement of the legacy daemon's `fauna-sync restore` verb).

There is no **server-side** reassembly: the two legacy-plaintext HTTP routes that once reassembled on the nest (single file, ZIP archive — §§ 3–4) were deleted 2026-09-27 in the compat-remnant sweep (`../architecture/version-compatibility.md` § Dimension 2, the fourth exception), since they could serve only pre-seal plaintext and no app called them.

### Deleting Snapshots

Deletion is intentionally slow. A `DELETE` request creates a pending action with a 48-hour delay. The user can cancel during that window. After 48 hours, the snapshot is soft-deleted and held for another 30 days before the underlying blobs are eligible for garbage collection. This gives users a recovery window even after confirming a deletion.

Retention policies can be configured per-user to prune snapshots automatically according to a keep-last / keep-hourly / keep-daily / … schedule.

## Technical Flow

### 1. Snapshot Creation

**WS-RPC kind:** `fauna.filesync.snapshot.create_folder` (Track B15; the HTTP twin `POST /api/v1/snapshots` is **deleted** — only the two snapshot byte routes stay HTTP residue, § 2).

When a snapshot is requested (manually or by the scheduler):

1. The server queries the `sync_changes` **head feed** for the latest version of each file — the set's current state: the entry with the highest sequence number per path that is non-deleted and has a manifest hash. One plane for every snapshottable folder since the phase 3 head unification (2026-08-17, `file-sync.md` § Membership); reserved (`__`) custody-copy destination sets are refused snapshots entirely — § *Backup folders and snapshots* below.
2. A row is written to the `snapshots` table with:
   - `file_count` and `total_bytes` — summary statistics.
   - `parent_id` — the previous snapshot ID, used for delta tracking.
   - The **watermark** `max_change_seq` (the highest `sync_changes` sequence included), used by the scheduler to detect whether new changes have arrived since the last snapshot. The former custody-plane twin `max_custody_updated_at` is dropped (schema v39) — one plane, one watermark, one clock.
3. One row per file is written to `snapshot_files`:
   - `path` — the file's path within the folder.
   - `manifest_hash` — BLAKE3 hash of the manifest, which identifies the exact content.
   - `size_bytes`, `mtime`, `mode`, `file_type` — file metadata. (Today `mtime` records the change's record time, not the source file's mtime, and `mode`/`file_type`/`symlink_target` are written as `0`/`"regular"`/`NULL` — `bins/fauna-nest/src/db/sync_storage.rs:2380-2382`; the declared-vs-populated gap is item (d) of `../architecture/encryption-at-rest.md` § Implementation status today.)

The snapshot is a logical pointer into the existing blob store — no data is copied during snapshot creation.

Snapshot creation is **idempotent within a one-second window**: a `UNIQUE(folder_id, created_at)` constraint (created_at is seconds-granularity) means two creates for the same folder in the same wall-clock second — e.g. the 60 s auto-scheduler racing a client's manual `create_folder` — dedup to a single snapshot. The losing create returns the existing snapshot rather than an error, so a concurrent create never surfaces a `snapshot.internal` to a client (the "no client-causable error state" invariant). **This rule is not folder-specific** — message-kind creation (§ 5) obeys it too, with one deliberate difference in what the deduped row ends up holding; see § 5 *Same-second repeats dedup, keeping the fresher capture*.

### Backup folders and snapshots (head-unified 2026-08-17; custody ruling 2026-07-17 superseded for ordinary sets)

**Two set classes once shared the declared backup type, discriminated by the reserved (`__`) namespace (the one named seam: `fauna_nest::db::snapshots::is_reserved_backup_set`); the folders mode contraction (design pass ruled 2026-09-28) leaves ONE — the reserved custody copy, marked by the nest-internal `folders.custody_copy` flag and read through the seam's successor `is_reserved_custody_copy` ([`reserved-folders.md`](reserved-folders.md) § Destination capability) — while an ordinary folder simply has no type.** The snapshot subsystem treats the two oppositely:

- **Ordinary folders** (non-reserved names — any folder whose nest place keeps snapshots) **record to the `sync_changes` head feed and snapshot from it like every other folder** (folders re-model phase 3, 2026-08-17). The `snapshot_files` rows **pin** a superseded version's blobs against GC reclaim exactly as for Sync sets, and superseded head rows reclaim only after the client marks them via `fauna.sync.changes.supersede`. Durability model: **version history until client-verified supersede + snapshot pins, retention prunes snapshots** — strictly better recovery granularity than the 2026-07-17 custody shape, where a version created *and* superseded within one scheduler quiet window was unrecoverable. An accidental deletion stays recoverable (a delete is an append-only head record; blobs reclaim only when superseded-marked and un-pinned, within the deletion-safety windows of § 7).
- **Reserved (`__`) custody copies** (the nest-internal `custody_copy` flag) are cross-location backup **destinations** — custodian-held latest-per-path `backup_custody` for another location's data (§ A destination's capability; `message-segment-store.md` § GC-safety). They are **never snapshotted**: the scheduler skips them and `fauna.filesync.snapshot.create_folder` refuses them (`fauna.filesync.snapshot.pure_backup_destination`, a sibling of the four destination gates) — a snapshot pin on the custodian would defeat its reclamation contract and grow a friend's disk with no owner control. The data owner's snapshots live on the *source* nest.

The one record path, the WS-RPC `fauna.sync.changes.record` kind, sends reserved backup sets to custody and everything else to the head feed (the legacy `/sync/ws` data plane, once a second path routing identically, is removed — `file-sync.md` § Relay serving → *The `/sync/ws` data plane leaves with the daemon*).

**History (why this section exists):** from the 2026-06-15 custody redesign until 2026-08-17, ordinary backup-type sets recorded into `backup_custody` — first with a snapshot subsystem that read only `sync_changes` (empty snapshots, auto-snapshots never firing; found by windows's `test_backups_download.py`, fixed 2026-07-17 by teaching snapshots to read custody), then as the ratified custody shape. Phase 3's head unification retired that shape — the 2026-07-17 rejected-alternative *(a2) "route ordinary backup-type sets back to `sync_changes`"* is exactly what landed, its stated costs resolved by the re-model rather than re-derived: device-pull exclusion is per-seat flags now (delivery to accepting seats is design-correct, `folders.md` § Target re-model), Media reads the head for every mode, and the custody rows were **deleted, not migrated** (approved alpha deletion; `folders.md` § Implementation status today — the re-seed alternative provably delivered every folder's back-catalogue to every seat, `file-sync.md` § Membership ⚠). Pinned by `bins/fauna-nest/tests/backup_mode_snapshot_coverage.rs` (tier_3: record → real seq → snapshot file_count ≥ 1 → `snapshot.get` lists the file → GC preserves the snapshot-pinned superseded version, with an unpinned-version reclaim as the non-vacuity control).

### 2. Snapshot Browsing

The browsing / lifecycle surface migrated to WS-RPC (Track B15, `fauna.filesync.snapshot.*`); the HTTP twins below are **deleted** (`bins/fauna-nest/src/lib.rs` — only the snapshot byte downloads stay HTTP residue). `User | Admin` (file_set-name / snapshot-id scoped).

| Operation | WS-RPC kind | Deleted HTTP twin (≡) |
|-----------|-------------|-----------|
| List snapshots for a folder | `fauna.filesync.snapshot.list` (`folder` mode) | `GET /api/v1/snapshots?folder=X` |
| Snapshot details with file listing | `fauna.filesync.snapshot.get` | `GET /api/v1/snapshots/{id}` |
| Diff between two snapshots | `fauna.filesync.snapshot.diff` | `GET /api/v1/snapshots/diff` |
| Verify all chunks exist in blob store | `fauna.filesync.snapshot.check` | `POST /api/v1/snapshots/check` |
| Queue snapshot deletion (48 h pending action) | `fauna.filesync.snapshot.delete` | `DELETE /api/v1/snapshots/{id}` |
| Recover a soft-deleted snapshot | `fauna.filesync.snapshot.undelete` | `POST /api/v1/snapshots/{id}/undelete` |
| Apply a retention policy | `fauna.filesync.snapshot.prune` | `POST /api/v1/snapshots/prune` |
| Stamp a snapshot's sealed tag display copy (S8 D3; net-new, no HTTP twin) | `fauna.filesync.snapshot.stamp_labels` | — |
| Apply the set's own resting retention policy, preview + execute (ratified 2026-08-05; **wire + nest half BUILT 2026-08-05** — § 8 *The set-policy prune kind*) | `fauna.filesync.snapshot.prune_set_policy` | — |

The `diff` kind returns per-file status: `Added`, `Removed`, `Modified`, or `Unchanged`. The `check` kind walks every manifest and chunk reference and reports any missing blobs — useful for diagnosing storage integrity issues. No snapshot route is HTTP: a snapshot's bytes come back client-side over the file-sync byte plane (§§ 3–4). **Sealed-names amendment (ratified 2026-07-29; the wire + nest-side halves are BUILT, the client-side unseal render is not yet wired — `path-sealing.md` § Sealed names & paths):** browse/diff entries already carry `path_hash` + `path_sealed`, the diff join and the pruner's `keep_tags` matching already re-key to hash companions, and `snapshots.tags` already carries `tag_hashes` (server-side retention matching) + a sealed `tags_sealed` display copy. Still open: apps rendering names by unsealing instead of the plaintext column (their mirrors hold no key custody yet) — it lands after the major-gated flip.

**Row lifecycle fields (ratified 2026-08-05 — snapshot-shape design pass; NEST HALF BUILT 2026-08-05).** Folder-mode `list` deliberately returns soft-deleted and deletion-pending rows (behavior-preserving), but `SnapshotSummaryRow` carried no field distinguishing them — so every app rendered a recoverable-deleted snapshot exactly like an active one, and the § 7 windows were invisible from every UI. The row gains four additive `#[serde(default)]` fields, populated only in folder mode: `soft_deleted: bool`, `purge_after: Option<i64>`, `deletion_pending: bool`, `execute_after: Option<i64>`. Additive-everywhere ([version-compatibility.md](../architecture/version-compatibility.md)): an older client folds the new keys into `extra` and renders exactly what it renders today; a newer client against an older nest decodes their absence as all-active, likewise today's behavior. The owner-implicit message-kind mode keeps excluding both classes (unchanged) — and does so *by construction*, its query filtering both out before a row is ever built. UI semantics of the two non-active states: `../ui/backups.md` § Snapshot-list shape.

**Three of the four ride the snapshot row; `execute_after` does not.** The deadline lives on the *pending action*, and its two producers encode targets differently — `snapshot.delete` puts one id in `target`, an automatic `snapshot.bulk_prune` puts the whole batch in `payload.snapshot_ids` — so the `list` join goes through the same `snapshot_targets_of` both-shapes parser the cancel path uses, rather than a second decoder free to drift. A reader that knew only the single-id shape would render every **automatically** pruned row as a pending deletion with no date, which is precisely the state a user needs the date for. `execute_after` is populated only while `deletion_pending` holds: once the action fires the row is soft-deleted and its remaining window is `purge_after`. Pinned tier_3 by `conformance_filesync_snapshot.rs::list_projects_the_three_row_states_distinguishably` and `::list_projects_the_deadline_of_an_automatically_pruned_row` (the latter drives the real producer, `backup::prune::schedule_auto_prune`, rather than forging an action row). **The apps render it** — the row lifecycle and its deadline paint from the `fauna-backups-machine` snapshot (`../ui/backups.md` § Snapshot-list shape; a code check 2026-09-19 found `execute_after` read in tui's `backups.rs`, android's `SnapshotListScreen.kt` and web's `backups-machine.ts`), consistent with this doc's headline.

### 3. Restore: Single File

**Target state:** client-side (§ Restoring Files) — the client resolves the file's `manifest_hash` from the snapshot listing (`fauna.filesync.snapshot.get`), fetches the manifest + chunks over `GET /api/v1/manifests/{hash}` / `GET /api/v1/chunks/{hash}` (sealed chunks by their ciphertext store key), decrypts under the owner root / retained content-key generation, verifies the content address, and reassembles.

**Shared-Rust home: `fauna_core::file_download` (landed 2026-07-16).** One walk on a `BlobFetcher` seam, bound per target — natively by `SyncEngine` (`download_file_bytes_by_manifest`, over the pooled transfer worker), on web by `fauna-wasm`'s `snapshot_download.rs`. Mechanism + rationale are owned by `../ui/backups.md` § Where logic lives → *Single-file byte download*.

**No server-side reassembly route.** `GET /api/v1/snapshots/{id}/file/{path}` once reassembled a pre-seal plaintext file on the nest; its last shipped caller (web's `snapshotFileUrl`) moved to the client-side walk 2026-07-16, and the route was deleted 2026-09-27 in the compat-remnant sweep (`../architecture/core-client-kind-catalog.md` § Snapshots). The sibling sync-file route `GET /api/v1/sync/file/{path}` had been deleted 2026-07-14.

### 4. Restore: Full Snapshot

**Target state:** client-side (§ Restoring Files) — full restore is the client running the single-file walk (§ 3) per snapshot file into a local directory, from an app surface. **The legacy daemon's `fauna-sync restore --output` (`cmd_restore`) was the first implementation and left with the daemon (ruled 2026-10-01, removed 2026-10-02 — [`../architecture/apps/sync-agent.md`](../architecture/apps/sync-agent.md) § Headless deployment); the shared walk it drove stays.** *Implementation status today:* the app surface is built on macOS alone (next sentence) and owed elsewhere, tui first — which apps carry it and its element ids are not yet in `ui.yaml` and need the user's approval before they are; until it is built every other app restores a snapshot one file at a time (§ 3). The daemon's removal did not wait for it. The macOS `MacRestoreView` **now drives** the converged engine host's client-side restore (landed 2026-07-15: `FfiSyncEngineHost::restore_snapshot_to_dir` → `SyncEngine::restore_snapshot_files_to_dir` over the shared `download_file_bytes_by_manifest` walk, into a user-chosen directory). `cmd_restore` **converged onto the same walk 2026-08-20**: it no longer carries its own inline copy — `fauna_sync_engine::engine::restore_snapshot_walk` is the ONE per-file fetch/open/reassemble/verify/guard/write implementation both hosts drive, over each host's own `BlobFetcher` binding (`cmd_restore`'s kept byte routes vs. the resident engine's transfer-pooled fetcher).

**No server-side ZIP route.** `POST /api/v1/snapshots/{id}/restore` once streamed a nest-assembled ZIP of a pre-seal plaintext snapshot, refusing sealed sets loudly rather than exporting ciphertext (ratified 2026-07-14). No app called it after `MacRestoreView` moved to the client-side walk, and the route and its ZIP-assembly path were deleted 2026-09-27 in the compat-remnant sweep. Server-side reassembly never gains a sealed path: a sealed set's restore belongs client-side, where the keys live. The seek-back streaming-ZIP contract it pioneered lives on in the user-data export ZIP (`bins/fauna-nest/src/streaming.rs`).

### 5. Message-kind snapshots

The message-segment-store track (`docs/goal/architecture/message-segment-store.md`) ships stream-content kinds (mail, conversations, calendar, …) as per-(audience-scope)-per-kind segment chains. A snapshot of one kind for one scope pins the kind's content manifest (the kind-tagged `fauna_segment_store::Manifest`) and, **for kinds with a placement layer (mail, calendar)**, the kind's placement manifest (`MailPlacementManifest` / `CalPlacementManifest`; design ratified 2026-05-14, tracked internally). Conversations (`conv`) have **no placement layer** — a conv snapshot pins the content `Manifest` only, with `placement_manifest = NULL`.

`fauna.filesync.snapshot.create_message_kind` WS-RPC kind. Request shape (canonical-CBOR, defined in `libs/fauna-protocol/src/filesync.rs`):

```
SnapshotCreateMessageKindRequest {
  kind:     String,            // accepted: "mail" | "conv" | "post" | "calendar" | "card"
                               // (calendar + card create/restore landed with S6.9, 2026-07-10).
                               // Kind table: ../architecture/message-segment-store.md § Layout.
  actor_id: Option<ActorId>,   // mail/post: omit (defaults to the bearer). conv: Some(channel_id) per-channel, or None = batch all the bearer's channels.
}
```

```
SnapshotCreateMessageKindReply {
  snapshot_ids: Vec<i64>,   // one per snapshot row created (one for mail/cal/per-channel-conv; one-per-channel for batched conv).
  kind: String,
  actor_id: ActorId,
}
```

Per kind:

- **`mail` / `calendar` / `card`** — the bearer's WS-handshake-validated actor IS the snapshot owner; `actor_id` is omitted. The nest serialises content + placement manifests in the same SQLite transaction as the `INSERT INTO snapshots` row, so the pairing is never stale. Owner-only authorization.
- **`conv`** — the snapshot scope is a **`channel_id`** (the MLS group), not the bearer's actor. Authorization is **channel membership** (`bearer ∈ list_channel_actors(channel)`), not owner-equality (`create_conv` in `bins/fauna-nest/src/filesync_handlers.rs`). `placement_manifest = NULL`. The pinned manifest is anchored to the `__conv/<channel_hex>` reserved folder (`folders.actor_id = channel_id`, `get_or_create_reserved_conv_folder`). **Batched convenience:** `actor_id = None` snapshots **every channel the bearer belongs to** at time T (`list_actor_channels(bearer)`) — one `snapshots` row per channel, all ids returned in `snapshot_ids`; `actor_id = Some(channel)` snapshots just that channel. The pure-backup gate (`message-segment-store.md` § gate 4) is checked across the whole target channel set **before** any row is created, so a batch containing even one pure-backup channel refuses the entire call with zero rows written — never a partial commit for the channels checked ahead of it.

`snapshots.message_kind`, `snapshots.message_manifest`, and `snapshots.placement_manifest` (added in the message-segment-store Plan 3) carry the pin. Retention policies, hard-floor + pending-action + soft-delete safety windows, immediate-delete override semantics — all uniform with folder snapshots above.

Each `(scope, kind, time)` is one snapshots row. Coordinated DR — backing up mail and calendar together — is **two RPC calls**; the scheduler is free to emit mail and calendar at independent cadences, so close-in-time pairing is visible to the user in the Backups UI (`docs/goal/ui/backups.md`) but not guaranteed by construction.

**Same-second repeats dedup, keeping the fresher capture (ratified 2026-07-24).** The one-second idempotency of § 1 applies here too — a repeat `create_message_kind` for the same `(scope, kind)` inside one wall-clock second returns the first row's id instead of surfacing a `snapshot.internal`, because `time` is seconds-granularity and "one row per `(scope, kind, time)`" is the statement above. Message-kind creation differs from the folder path in **one** respect: a folder capture reads the `sync_changes` projection, so both racers pin logically the same state and the loser may simply return the existing row untouched, whereas a message-kind capture re-reads the segment store after a `finalize_open` — so the second capture can be genuinely *newer*. The nest therefore **writes the fresher manifest pair onto the deduped row** rather than discarding it: both callers get a snapshot at least as fresh as their own capture, no capture is ever silently lost, and the constraint's one-row-per-second promise still holds. This is safe precisely because message-kind manifests carry no GC reference — the reference walk of § 9 reads `snapshot_files`, which message-kind rows never populate — so replacing them cannot orphan a chunk. Rejected alternatives: sub-second `created_at` or a discriminator column (would change the meaning of `created_at` for retention bucketing in § 8, the watermark comparisons of § 1, and the wire, across all 7 apps — disproportionate to a one-second window), and a typed retryable error (pushes a retry loop into every app for a plain, legitimate user action, and still breaks the "no client-causable error state" invariant in spirit). Reconsideration trigger: a kind whose captures are expensive enough that redoing one inside a second is itself costly, or a client that legitimately needs two distinguishable snapshots within one second.

### 6. Message-kind restore

`fauna.filesync.snapshot.restore_message_kind` WS-RPC kind. Request shape:

```
SnapshotRestoreMessageKindRequest {
  snapshot_id: i64,
  confirm_id:  String,   // = snapshot_id retyped as a string
}
```

No HTTP route restores a snapshot of any kind; a folder snapshot (`message_kind IS NULL`) restores client-side (§ 4).

**`message_kind IN ('mail', 'calendar', 'card')`** (owner-only):

1. **Pre-conditions** — `confirm_id` matches snapshot id (else 400); bridge not serving the actor (`subscribe_mailbox_state` registration absent — else 409); the bridge's wrapped-MLS blob bundle present on the nest (`bridge_wrapped_mls_blobs`) *advisory only* (warned in response if not — bridge AUTH will fail until it is, but the restore proceeds).
2. **In one SQLite transaction:** drop `bridge_imap_*` / `bridge_caldav_*` rows for the actor; replay the pinned `placement_manifest` via the placement-journal replay API; rebuild `segment_records` from the reconstituted segment file footers (the whole floor-authoritative column set, `seq` included — the rows were dropped a step earlier, so an omitted column is destroyed; the completeness rule and its canonical-writer discipline are owned by `../architecture/message-segment-store.md` § `segment_records` SQLite mirror); insert a `restore_history` row.
3. **Post-condition** — the bridge comes back up via the client-driven bridge-lifecycle controls (the supervisor reconciles the flag-file state — `mail-bridge-lifecycle.md`; step 1's precondition guarantees it was not serving during the restore, so the admin's disable → restore → re-enable flow is the driving surface); MUAs reconnect via QRESYNC / sync-collection. UIDVALIDITY is preserved (placement manifest carries it); MUAs whose last observed modseq exceeds the restored highestmodseq fall through to RFC 7162 §3.2.5.2 stale-modseq full-resync. Divergence detection + the Backups-UI surface for "MUA ahead at reconnect" is owned by the IMAP+CalDAV restore design (ratified 2026-05-14; tracked internally) and surfaced on the Backups page per `docs/goal/ui/backups.md` § Restore divergence.

**`message_kind = 'conv'`** (the conversations-segment rollout's Plan 8 — landed via `restore_conv` in `bins/fauna-nest/src/filesync_handlers.rs`): the scope is a `channel_id`, so authorization is **channel membership** (`bearer ∈ list_channel_actors(channel)`), not owner-equality. **No bridge precondition** (no bridge serves conversations) and **no placement layer**. In one SQLite transaction: verify each pinned `live_segments` segment is on disk (else error — fauna-sync chunk pull incomplete), `DELETE FROM segment_records WHERE scope_id = <channel> AND kind = 'conv'`, rebuild the conv mirror rows from the pinned segments' on-disk footers (re-emitting each record's per-channel `seq`), **reinstate the restoring member's roster row** (`INSERT OR IGNORE INTO actor_channels`), and insert a `restore_history` row under the bearer. The conv reply carries no bridge-AUTH note. No post-restore bridge restart — clients re-pull the channel over the normal sync path.

The endpoint does not initiate any pull from a backup destination, and the join-with-`read`-capability outline this note once described is refuted — destination custody never enters the device-sync feed. The restore handler assumes segments are already locally available; content held on a destination reaches a rebuilt nest through the re-seed ceremony's nest-held pull-back leg (ratified 2026-09-26, [`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Client-device custodian (pull) → *Restore* → *The nest-held pull-back*). The ratified end-to-end shape for turning delivered backup *custody* into a live corpus — the custodian-device re-seed ceremony and the `fauna.backup.custody.materialize` verb, shared by both restore sources — is owned by [`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Client-device custodian (pull) → *Restore* (ratified 2026-08-22, not built).

### 7. Deletion Safety

Three layers of protection prevent accidental permanent loss:

**Layer 1 — Hard floor.** `fauna.filesync.snapshot.delete` is refused (a 409-class error) if it would leave fewer than 3 active snapshots for the folder. This minimum cannot be bypassed.

**Layer 2 — Pending action delay.** A successful delete does not remove the snapshot immediately. It creates a `SnapshotDelete` pending action with a 48-hour `execute_after` timestamp; the reply carries the `execute_after` time. The user can cancel the pending action during this window to abort the deletion. Bulk prune uses a **7-day** delay (`ActionType::SnapshotBulkPrune`) — the window an **automatic** retention prune schedules into (§ 8 *Arming*). Cancelling any snapshot-deletion action releases its targets' `deletion_pending` marks, so a cancelled deletion restores the snapshot to Layer 1's active count rather than stranding it outside its own hard floor.

> **The explicit `fauna.filesync.snapshot.prune` request (closed gap, 2026-08-01 — ruled shape (b), amended).** The kind now enforces Layers 1 and 3 and shares the automatic path's candidate population: its policy evaluates over the set's **active** snapshots only (the `backup::prune::is_active_snapshot` predicate both consumers share — a soft-deleted or deletion-pending row is never a candidate, so a prune cannot reach into the recovery windows the automatic path opened, and the policy's bounds bind over the population the user actually sees); the hard floor is clamped onto the union engine's output (newest candidates handed back, mirroring the automatic evaluator's guarantee 2); and the prune **soft-deletes**, opening the 30-day `purge_after` window per target — never the purge primitive. **Layer 2 is deliberately NOT interposed on this kind** (a deliberate ruling): the user asked for this prune synchronously, and soft-delete plus the undelete window satisfies no-user-data-loss on its own — which also keeps the reply semantics (`pruned` = pruned now) unchanged for its shipped caller, web's `snapshot_prune` wasm binding (the `fauna-sync` daemon, its other caller, was removed 2026-10-02). The dry-run preview and `remaining` are computed over the same filtered, floor-clamped population the real run uses.

**Layer 3 — Soft delete.** After the pending action executes, the snapshot is moved to `soft_deleted=1` with a `purge_after` timestamp set 30 days in the future. The snapshot remains recoverable during this window via `fauna.filesync.snapshot.undelete`.

Only after `purge_after` has elapsed does the GC consider the snapshot's blobs eligible for collection.

**Immediate-delete override (owner only).** Disk-full and "this snapshot must be gone *now*" emergencies are real; routing around the guardrails (manually deleting blobs, `dd`-ing free space) would erode the safety invariant worse than a strong-confirmation override does. `fauna.filesync.snapshot.delete_immediate` WS-RPC kind:

```
SnapshotDeleteImmediateRequest {
  snapshot_id: i64,
  confirm_id:  String,   // = snapshot_id retyped as a string
  acknowledge: String,   // "I understand this is immediate and irreversible."
}
```

Skips Layers 2 and 3 (the 48 h pending action and the 30 d soft-delete window). Layer 1 (the hard floor of 3 active snapshots) is **still enforced**. Owner only — nest admins, even on the owner's primary nest, cannot invoke the WS-RPC kind; the admin's local-disk lever is the manual-compact endpoint below. Mismatched `confirm_id` → `fauna.filesync.snapshot.confirm_mismatch`; mismatched `acknowledge` → `fauna.filesync.snapshot.acknowledge_mismatch`; neither mutates state. Segments freed by the deleted snapshot still observe their 14 d tombstoned-segment retention window before fauna-sync GC reclaims chunks (the override governs the snapshot lifecycle, not the segment lifecycle). See `docs/goal/architecture/message-segment-store.md` § Immediate-delete override for the segment-store-side details and `docs/goal/ui/backups.md` § immediate-delete UX bar for the never-a-one-click rule.

### 8. Retention Policy

**ARMED 2026-08-01 (see the RULING at the end of this section, and *Arming* below it).** Retention is configured **per folder** — the wizard's retention inputs, resting as the 2-field `RetentionPolicy { max_snapshots, max_age_days }` in `folders.retention_policy`; both nest-side prune consumers read that column and no other copy. The eight `keep_*` rules below are the **target rule vocabulary**; when built they grow additively on the same per-set policy, and only the explicit `fauna.filesync.snapshot.prune` request speaks them today.

**The two field families have different semantics, and that is deliberate.** The eight `keep_*` rules are restic-style **keep-rules, evaluated as a union**: a snapshot survives if *any* rule keeps it. The shipped 2-field policy is a pair of **bounds** — "Max snapshots retention" / "Max age in days for retention" — and a user who sets both is asking for *neither* to be exceeded, i.e. an intersection. Routed through the union engine, twenty snapshots taken inside one week would all survive "Keep snapshots: 7" and the storage bound the wizard sells would never bind, so the armed path evaluates the bounds directly (`backup::retention::evaluate_folder_retention_at`) rather than mapping them onto `keep_last` + `keep_within_secs`. A future build that adds the `keep_*` vocabulary to this column must state how the two families compose; it must not silently re-map one onto the other.

> **Version retention is a SIBLING per-set policy, never this column (ratified 2026-08-17, the retention-model pass).** Bounding *version history* rests in its own `folders.version_retention` column with its own bounds pair — owner: [`file-versions.md`](file-versions.md) § Retention. The no-silent-re-map rule above is exactly why: widening this **armed** column to a second plane would make every existing configured `max_snapshots` start binding version history its owner never asked to bound. The two columns never read each other; they meet only in § 8b's per-place editor, where the version knobs join as a fourth per-place knob when their build (approved 2026-08-17) lands.

| Field | Purpose |
|-------|---------|
| `keep_last` | Keep N most recent snapshots unconditionally |
| `keep_hourly` | Keep the newest snapshot per hour for the last N hours |
| `keep_daily` | Keep the newest snapshot per day for the last N days |
| `keep_weekly` | Keep the newest snapshot per week for the last N weeks |
| `keep_monthly` | Keep the newest snapshot per month for the last N months |
| `keep_yearly` | Keep the newest snapshot per year for the last N years |
| `keep_within_secs` | Keep every snapshot created within the last N seconds |
| `keep_tags` | Never delete snapshots with these tags, regardless of other rules |

**Algorithm:**

1. Tagged snapshots matching `keep_tags` are unconditionally protected.
2. Snapshots within `keep_within_secs` are kept.
3. `keep_last` N snapshots (by creation time) are kept.
4. For each interval type (hourly, daily, weekly, monthly, yearly): snapshots are grouped into buckets by `floor((now - created_at) / interval_secs)`. The newest snapshot in each bucket is kept.
5. Any snapshot not selected by any of the above rules is marked prunable and passed to `fauna.filesync.snapshot.prune` (which itself has the 7-day pending action delay).

The hard floor (3 active snapshots) is always enforced, even if the policy would prune below it — on the **automatic** path (`SNAPSHOT_HARD_FLOOR`, `backup/retention.rs`), the interactive single-snapshot delete (`check_snapshot_delete_allowed`), and (since 2026-08-01) the explicit `fauna.filesync.snapshot.prune` request, whose handler clamps the floor onto the union engine's output and soft-deletes (§ 7).

> **RULING (retention-model pass — refutable by the security review or at build time): the authoritative resting copy for automatic pruning is the per-set `folders.retention_policy` column. > **Arming (2026-08-01) — scheduled auto-pruning runs for the first time on any deployment.** Both consumers now share one implementation, `backup::prune::schedule_auto_prune`, which reads the per-set column and **schedules; it never deletes**. Each gate obligation, and how it was met:
>
> - **Absent / unparseable ⇒ keep everything.** `parse_folder_retention` returns three distinct arms — `NotSet` (no column, or one binding nothing: a `0` in a bound means *that bound is unset*, so an empty wizard box cannot read as "keep zero"), `Unparseable` (**refuse and log**, never guess — any value in this column that is not the canonical shape, such as a restic-style `keep_*` JSON, lands here: *The off-shape at-rest residual* below), and `Policy`. Only GC's phase 3 then purges. Nothing on the automatic path calls `delete_snapshots`.
>
> **Net user-visible effect:** a set with no policy keeps everything forever, exactly as before; a set whose owner filled in the wizard's retention inputs now has out-of-bounds snapshots enter a 37-day recoverable pipeline instead of accumulating unbounded against the storage quota. The actual run **soft-deletes** (Layer 3's 30-day `purge_after` window; Layer 2 deliberately not interposed — the same ruling as the explicit kind: a user-requested, previewed, synchronous prune with an undelete window satisfies no-user-data-loss). ### 8b. The nest place's snapshot policy (BUILT 2026-08-15 — folders re-model phase 2 slice d)

Retention (§ 8) answers *what the nest keeps*. Two sibling knobs answer *whether it snapshots at all* and *how long it waits for quiet* — together they are **the nest place's snapshot policy**, the folders re-model's per-place model applied to the one place every folder always has (`folders.md` § Target re-model → places). All three rest per folder; retention keeps its own column (§ 8) because it has a sealed display twin and moving a live column would buy nothing.

| Knob | Column | Unset (`NULL`) means |
|---|---|---|
| keeps snapshots | `folders.nest_snapshots` | the nest-wide behavior — snapshot |
| quiet period | `folders.nest_snapshot_quiet_secs` | the nest-wide scheduler cadence (`SnapshotScheduler::quiet_secs`) |
| retention | `folders.retention_policy` (§ 8) | keep everything |
| version retention | `folders.version_retention` (`file-versions.md` § Retention — **column + pipeline BUILT 2026-08-17; the editor knobs have since landed, tui first (`apps/fauna-tui/src/settings/folders.rs`) — per-app reach is `file-versions.md`'s to state**) | keep everything |

**Every knob is three-state, and the third state is the honest resting value.** `NULL` is *"nothing authoritative said"*, not a value: it is where every folder rests until its owner chooses, and where a folder returns when the owner picks "use the default". A `NOT NULL DEFAULT 1` was deliberately not used — it would have rested a snapshot-keeping claim on the reserved `__` destination sets, which are refused a snapshot **structurally** (a snapshot pin defeats the custodian's latest-per-path reclamation, `../architecture/message-segment-store.md` § GC-safety) and would then carry a policy they never obey.

**The owner's choice and the structural refusals never fight**, because they point opposite ways: `CacheDb::folder_needs_snapshot` returns false when the owner said no, *and* false when a structural rule says no. Only the absence of both yields a snapshot. So `nest_snapshots: true` is a *preference*, never a guarantee — read the verdict from that method, never the column alone.

**Wire.** `fauna.folders.update` carries an optional `nest_place: NestPlacePolicy { snapshots, quiet_secs }`, and both projections (`owner_summary` *and* `member_summary`) carry it back on `FolderSummary` — the same audience grading as `retention_policy` beside it, since this is policy about what the nest keeps rather than a disclosure of the owner's machine. The struct is **sent whole and applied whole**: a knob omitted from it clears back to unset. That split — set-vs-unchanged on the outer `Option`, on/off/default *inside* — is what expresses three states per knob over a wire that cannot round-trip a nested `Option` (dag-cbor). A negative `quiet_secs` is refused (`fauna.folders.bad_request`), never clamped: clamping would turn "wait for quiet" into "cut on every tick" silently. A `quiet_secs` above the ceiling of **seven days** (`NestPlacePolicy::MAX_QUIET_SECS`, the one home of the number) is refused the same way: a quiet period is how long a folder sits unchanged before its snapshot, so a week already means "only once the folder has gone still", and an unbounded value once let one account's own folder panic the nest-wide scheduler, which also carries every other folder's snapshots and the nest's own database backups (`../architecture/nest/common.md` § Client-state recoverability). The shared editor reads a value outside `0..=` the ceiling as unset rather than walking the owner into the refusal. A resting value past the ceiling (written before the bound, or past the handler) is still read without panic — the scheduler's quiet arithmetic saturates, so that folder simply never counts as quiet — and one folder's failed check costs only that folder's snapshot, never the pass. At rest this is schema **v37**, additive, `MIN_READER` unmoved, and it needs no backfill — unlike phase 2's device flags, which had a `role` string to derive from, *unset* here already is the correct value for every pre-v37 row.

**Reachable since 2026-08-16 — on the lead app.** The editor is the expanded folder row's `folder-nest-snapshots-select` (three-state: use the default / keep / don't keep), `folder-nest-quiet-input`, `folder-nest-retention-snapshots`, `folder-nest-retention-days` and `folder-nest-save-button` — element IDs user-approved 2026-08-15 as part of phase 2 slice e, and rendered on **any** folder, which is what replaced the wizard's backup-type-only retention step. All four save as ONE `fauna.folders.update`, because the policy applies whole; a control left blank (or set to "use the default") is written as *unset*, which is how a user takes a knob back. Built on **tui** (the lead app), then **linux + web + android 2026-08-16**, **macos + ios 2026-08-18**, and **windows 2026-08-21** (in code; its Windows compile + e2e verify is owed — [`../ui/folders.md`](../ui/folders.md) § Implementation status today); until a leg is verified on its platform, that app's folders rest unset exactly as before v37. **The editor is one implementation, not seven:** `fauna_folders_machine::nest_place` owns the buffers ⇄ policy mapping (prefill + write) on both boundary faces, so an app paints the five controls and never re-derives the three-state rules above — in particular that a zero retention bound renders **blank**, and that clearing retention means sending the binds-nothing policy rather than omitting the field. Per-app status + the UI contract: [`../ui/folders.md`](../ui/folders.md) § Implementation status today.

### 9. Garbage Collection

GC runs every **6 hours** with a **30-minute** orphan grace period (`GcScheduler`, `bins/fauna-nest/src/main.rs` — 21 600 s interval / 1 800 s grace; this is the one place the cadence is stated — other sections point here). An advisory lock prevents concurrent GC runs.

0. **Expire retained custody generations** — drop `backup_custody_generations` rows whose `superseded_at` is older than the grace window `T`, crediting their bytes back to the owner's quota. Runs **before** the reference set is built (never after), so a generation is either still protected or already gone — reversing the order would leave a cycle in which it is neither, the over-delete direction. Skipped on a dry run. Owner: [`segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Custody grace window (T).
1. **Auto-prune** — apply each folder's own resting `retention_policy` to every actor's sets, creating pending prune actions for snapshots that fall outside the policy (§ 8 *Arming*; a set with no readable policy is skipped, and this phase never deletes).
2. **Build reference set** — collect all `manifest_hash` values referenced by:
   - Active (non-soft-deleted) `snapshot_files` rows.
   - Live `sync_changes` entries (non-deleted, has manifest).
   - Live `backup_custody` rows (the destination-nest liveness for custody-copy sets — see the Known-gap note below).
   - **Live signed records (step 2f, built 2026-09-08)** — every blob a stored post or the newest profile row per author names: a feed-compose photo and its thumbnail, a video's manifest / segments / poster, a gated post's sealed body (`encrypted_ref`) **and its plaintext `attachment_refs`** (the hashes of the media sealed inside a body the nest cannot read — the floor addition [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Plaintext floor → Posts row ratifies), a profile's avatar and banner. The oracle walks the live `content` rows (`Post::blob_refs` / `Profile.{avatar,banner}` over `list_all_post_ids` + the newest `schema = 'profile'` row per author) rather than a reference table written at ingest: a deleted post leaves `content` first ([`../ui/feed.md`](../ui/feed.md) § Post deletion → removal order), so its blobs reclaim after grace with no delete leg to keep in step; every record already on the box is covered with no backfill; a replaced avatar reclaims because only the served row is walked. Chunkless like the ATProto arm (raw `POST /api/v1/blob` bytes, never a manifest), so pinned without the step-3 probe. **Why this arm exists:** every feed-compose writer (`upload_public_post_blob_bytes`, `upload_gated_post_blob`, `FeedManager::seal_compose_attachment`, the archive import's `upload_period_sealed_media`) and the avatar/banner upload POST to `/api/v1/blob` and record no `sync_changes` row — the ATProto arm's own comment had assumed Fauna media was pinned by the media library's `changes.record`, which is true of the Media page alone — so until 2026-09-08 every post's photo and every sealed post body was reachable from nothing and **deleted ~30 minutes after upload** on every nest with a blob dir (found 2026-09-07). A body that cannot be READ fail-closes the run like an unreadable manifest (step 6, `record_read_failures`); a row that does not DECODE is warned and skipped, not fail-closed, because every writer decodes before it stores (the only such rows are the degenerate inline fallback, which never named a servable blob) and a permanent nest-wide fail-close on one junk row would be the client-triggerable stall the manifest arm's hash-intact split exists to avoid. What the nest still cannot pin: a gated post authored by an app older than the field (its `attachment_refs` is empty — status quo for that post).
   - **Live conversation records (step 2g, built 2026-09-09)** — every sealed attachment blob a live conversation record names. The sender lists the sealed blobs' content addresses in plaintext beside the MLS-sealed envelope (`ChannelSendRequest::attachment_refs` — the floor addition [`conversations-at-rest.md`](conversations-at-rest.md) § Encryption at rest → *Attachment reachability* ratifies, 2026-09-08), and the nest records them beside the record's mirror row (`conv_attachment_refs`, same transaction). The oracle pins every hash whose `(channel, seq)` still has a live (non-tombstoned) `segment_records` row: a record the store has let go — a paired nest's relay-ack purge, or compaction — pins nothing, so its attachments reclaim after grace with no delete leg to keep in step; a cooperative chat `Delete` is a sealed message, never a store tombstone, and keeps the bytes as it keeps the envelope. Chunkless like 2e/2f. **Why this arm exists:** the attachment bytes enter through `POST /api/v1/blob` sealed under the channel epoch key and are named only inside a body the nest cannot open, so until 2026-09-09 every conversation attachment on every nest with a blob dir was swept ~30 minutes after upload (found 2026-09-08 as the 2f arm landed). A pre-field app's attachment messages record no refs and stay unpinned exactly as before. A foreign-homed channel is covered too since 2026-09-09: its attachment bytes rest on the channel's *home* nest beside the record and refs ([`conversation-rooms.md`](conversation-rooms.md) § The home nest → *Attachment bytes*), so this arm pins them on the one nest that holds both — the uploader's own nest never receives them and has nothing of the room's to sweep.
   - **Live rendered sites (step 2h, built 2026-09-22)** — every body a published site's rendered stores name, public (`web_rendered`) and paywalled (`web_rendered_sealed`), **plus every body a render still holding its site has staged** (`web_render_staged`). A render streams its bodies to the store as it goes and writes its rows in one replacing transaction at its end ([`web-content-hosting.md`](web-content-hosting.md) § Routing, render, serving → *A reader sees a whole site or none*), so between the two a body is named by nothing on the site while already carrying its `blob_metadata` row (the premise below). The staged reference is what keeps it, whatever the render's length against the grace: written under the render's claim **before** the body is stored, and deleted by the very transaction that writes the rendered rows taking the reference over. A render that loses its site stops pinning — every generation bump (a newer render's listing, the fail-closed clear) deletes that actor's staged rows, and a superseded render can stage nothing more — so the bodies of a superseded or failed render are ordinary orphans, collected past grace. A page replaced or cleared loses its reference with its row, and its body is collected the same way: **a site's resting cost is its live pages plus the bodies of the one render that holds it.** One over-pin is accepted: a nest that stops mid-render leaves that render's staged rows, which keep its bodies until the actor's next render begins. Chunkless — a rendered body is raw bytes, never a manifest — so pinned by row existence alone, like 2e–2g. Why the pair had to land together: the premise note below.
   - **Live content rows' spilled payloads (step 2i, built 2026-09-22)** — every blob a `content` row rests its payload in (`content.blob_hash`): the payload store spills any payload over 64 KiB to the blob store and names the hash in the row — an inbox envelope today (the inbox deliver door, a federation or conversation welcome), a legacy overflowed post body from before the segment cutover. While the row lives its payload IS that blob — an undelivered envelope the recipient has not drained, a delivered one its history still lists — so it is pinned by row existence alone; it reclaims past grace once the row goes (the account's inbox is deleted with the account). Chunkless: a spilled payload is raw bytes. Landed in the same commit as the spill's metadata row, for step 2h's reason: a row without this arm would have deleted undelivered inbox content.
   - Retained `backup_custody_generations` rows — superseded/tombstoned generations still inside the custody grace window `T` (30 d) on a **reserved destination** set. Step 0 below expires them first, so every row present here must survive this sweep. Mechanism + why the window exists: [`segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Custody grace window (T).
3. **Classify references** — a `manifest_hash` is one of two reference classes, and the walk must not conflate them:
   - **Direct-blob (reserved rails).** A reference whose every referencing row belongs to a **reserved (`__`) folder** — `__config` (retired 2026-10-02; the name stays reserved and its old rows keep this classification), `__drafts`, `__mls`, the `__index`/`__conv` segment stores ([reserved-folders.md](reserved-folders.md) § Drafts Sync) — points at the stored blob **itself**: a client-sealed opaque payload or raw segment bytes, never a decodable `ChunkManifest`. Pinning the hash protects it completely (it references no chunks); GC does not walk it for chunks. (`is_reserved_folder_name` is the single source of truth for the convention; a new direct-blob rail is covered automatically by its `__` name.)
   - **`ChunkManifest` (ordinary sets + all `backup_custody` rows).** Decoded to extract the chunk **store keys** (ciphertext hashes for sealed chunks). Custody rows are always manifest-class regardless of the set's name — the segment-backup coordinator's `upload_bytes` records genuine manifests even into `__`-named destination sets.

   **The name is a hint; the bytes decide (2026-07-12).** The direct-blob class is confirmed against the blob's **content** before its chunk walk is skipped: a candidate that actually decodes as a `ChunkManifest` is walked as one, whatever set it was recorded against. Reachability — the one thing a wrong answer here destroys — must never rest on a folder *name*, because a name is client-supplied. A rail blob does not decode as a manifest, so this is a no-op for every real rail; **that expected decode failure is not a `manifest_decode_failure`** and must not fail-close the sweep (counting it would disable reclamation on every cycle — the § 9 step-6 gate is for *manifest-class* references only). One exception (2026-07-13): a probe decode-failure whose bytes are also **not the preimage of their content address** cannot be a healthy rail blob — rails are keyed by their own bytes — so it is at-rest corruption of what may be a genuine manifest recorded under a reserved name, and it fail-closes exactly like the step-4 walk (this closes the *corrupt-rail-manifest* residual without re-arming fail-close-every-cycle). This makes the classification fail-safe in the only direction that matters: it can over-pin, never over-delete.

   **A read error is not an answer (2026-07-13).** The probe distinguishes *"the bytes say it is not a manifest"* (`Ok(Some)` + failed decode — the expected rail case above, uncounted) from *"the bytes could not be read"* (a blob-store `Err`: EMFILE/EIO/EACCES). The latter is **not** a classification: the blob is present and may be a manifest whose chunks are live, so it **counts as a `manifest_decode_failure` and fail-closes the run**, exactly as the step-4 walk does for the identical error. Folding it into "not a manifest" would hand back the destructive answer — skip the walk ⇒ sweep the chunks — on a transient error, and *uncounted*, so the step-6 gate would never fire. This matters beyond a normal transient corner: the probe is the **only** protection for the chunked-manifest-under-a-reserved-name rows a live nest already carries (the write-path guards only stop new ones), and it feeds the sweep that is now the box's **only** destructive consumer of the shared reachability oracle — the `__index` boot purge, which gated its own blob deletes on the same counter, was deleted 2026-08-02 (`content-index.md` § Before Plan 5b writes its first byte). Unlike a decode failure, a read error heals on the next run.
4. **Walk manifests** — for each `ChunkManifest`-class reference, decode it and extract the chunk store keys → build the full set of referenced chunk hashes. **A decode failure on hash-MISMATCHED bytes fail-closes the run** (step 6); a decode failure on hash-INTACT bytes means the reference *never was* a manifest — pinned, walk-free, never fail-close (see *Never a manifest vs. corrupt* below).
   - **4b. (Retired 2026-09-24) — the historical chunk-plane pair audit.** From 2026-09-09 the same decode fed a keyless fold, `(seal root, plaintext chunk hash) → store key`, reporting a chunk that rested under two ciphertexts of one (key, nonce) — the pre-2026-09-03 raw writers' residue — to the admin dashboard, classing a pair *pinned* when a snapshot kept its raw twin, and serving the owner's device a worklist (`fauna.sync.chunk_pairs.list`) to re-seal from. The compat-remnant sweep removed it with its tables, its kind and its device pass: after the 2026-09-24 baseline reset no such chunk rests anywhere, and the single seal door keeps a new one from forming ([`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § Per-chunk file-sync key owns both the invariant and this history). The walk no longer looks for pairs; the step number stays spent so later citations of 4c keep resolving.
5. **Find unreferenced blobs** — query `blob_metadata` for blobs whose hashes are not in the referenced set and whose creation time is older than the grace period (to avoid racing with an in-progress upload). The grace runs from a hash's **first** upload and is never renewed — `put_blob_metadata` is `INSERT OR IGNORE`, so a content-addressed re-`POST` of the same bytes leaves `created_at` untouched — which is why it covers an in-progress upload and nothing longer: a blob that must outlive it needs a live reference (step 2), and every composer therefore uploads at submit, when the naming post is stored in the same breath ([`../ui/media.md`](../ui/media.md) § Encryption at rest owns that upload-timing rule; `gc_sweeps_a_pick_time_upload_before_its_post_exists` pins the sweep side).
6. **Delete — only if every reference was resolved.** If **any** `ChunkManifest`-class reference is **corrupt** (present but not the preimage of its content address at any write layer), **or any reference of either class could not be read from the blob store**, the reference set is provably incomplete (that manifest's chunks could not be enumerated — and an unreadable direct-blob candidate cannot even be *classified*), so the delete phase is **skipped entirely for that run** (`manifest_decode_failures` on `GcResult`; error-level log per reference, naming the referencing set/actor/path rows via `manifest_reference_sources` so recovery is actionable without off-box forensics). Deleting against an incomplete reference set is the data-loss direction (the no-user-data-loss invariant outranks reclamation); disk-fill is independently backstopped by the § 12 blob-store disk guard, so a persistent corruption degrades to bounded disk growth + loud errors, never to silent chunk loss. Otherwise, remove the unreferenced blobs from the blob store on disk and from `blob_metadata`.

> **Why classification exists (found live on example.com, 2026-07-09).** Before the split, GC attempted to decode the `__config`/`__drafts` rail blobs as `ChunkManifest`s and warned `NotCanonical { trailing data }` every cycle (the sealed blob's `0x01` version byte parses as a complete CBOR integer, leaving the ciphertext as "trailing data"). Those references were still *pinned* (chunkless, so nothing was orphaned), but the warns were noise, and the walk's silent keep-going on a decode failure meant a *genuine* manifest failing to decode (bit-rot, format drift) would have silently orphaned — then deleted — its live chunks. The classification makes rail references decode-free by design; the fail-closed sweep makes a residual decode failure loud and harmless. A decode failure is *abnormal* after the split, so fail-closed does not disable GC in steady state. > **The manifest door validates (2026-07-13).** `POST /api/v1/manifests` refuses a body that is not a canonical `ChunkManifest` (`400`), so *"a `content_type='manifest'` blob really is a manifest"* is true by construction rather than a client assertion. Every legitimate writer already sends exactly this — all of them funnel through shared Rust's `serialize_manifest`/`canonical_encode` (the `SyncEngine` + the backup coordinator's `upload_bytes`; apple and android via the FFI; the Go WebDAV bridge; another, the `fauna-sync` daemon, was removed 2026-10-02) — so nothing real is turned away, and older clients still decode (the manifest's added fields are `serde(default)`). The check is a plain `canonical_decode` of the **wire** body, *not* GC's `decode_manifest` (which first reverses the nest's at-rest `encode_blob` framing). It stays correct after the § M2 sealed-manifest flip: the seal is a *field inside* the struct, so a sealed manifest still decodes. The direct-blob rails are unaffected — they upload via `/api/v1/blob`, a different route.

> **Never a manifest vs. corrupt — the hash decides (CLOSED 2026-07-13).** The door above is necessary but not sufficient: GC classifies by *reference class*, not by `content_type`, so an undecodable manifest-class reference used to fail-close step 6 nest-globally rather than being judged on its own bytes — a client-reachable stall of everyone's reclamation, engaging *No client-causable unrecoverable nest state*. The closure extends *"the bytes decide"* one level down: on a manifest-class decode failure, GC re-verifies the stored bytes against the reference's **content address** (`stored_bytes_match_reference`, `backup/gc.rs` — layer-aware: `blake3(decode_blob(stored))` for framed chunk/manifest writers, `blake3(stored)` for raw-stored rails, the decrypt-only layer under an at-rest key). **Hash-intact + undecodable ⇒ the bytes provably NEVER decoded as a manifest** — a content address is immutable, so no chunk was ever enumerable through the reference and the fail-close has nothing to protect: the blob stays pinned (over-pin, never over-delete), the reference is surfaced on its own `never_manifest_refs` counter at warn level with its referencing set/actor/path rows, and **the sweep proceeds**. **Hash-mismatch ⇒ genuine at-rest corruption** of what may have been a live manifest — the only case the fail-close was designed for, and it still fires (step 6). This closes the stall *including every such row already recorded* (the verdict is re-derived from bytes each run, so no backlog reconcile is needed) and restores the global fail-close to genuine corruption. Pinned by `gc_sweep_survives_a_recorded_reference_that_was_never_a_manifest` (tier_3, real handlers) + the `gc_never_manifest_reference_does_not_fail_close` / `gc_manifest_decode_failure_fails_closed` / `gc_probe_fails_closed_on_a_hash_mismatched_rail_reference` unit trio.

> **The integrity check's premise — every blob-store write keys by a server-verified hash of its bytes** (else a healthy blob would read as "corrupt" and spuriously fail-close). Audited 2026-07-13: every live writer server-computes or verifies its key (`/api/v1/chunks` + `/manifests` + mail-body staging at the framed layer; the `/api/v1/blob`, config/drafts/mls rail, video, link-preview, and payload-store writers at the raw layer — a census of *keys*, not of rows: the video and payload-store writers it names stored no `blob_metadata` row until 2026-09-22, see the premise note below) — with one exception, now fixed: the `ChunkResolver` device-fetch (relay) cache stored device-supplied bytes under the *requested* hash unverified, letting a lying source device seed blobs indistinguishable from corruption; it now discards (and never caches) fetched bytes that do not hash to the requested address (`chunk_relay.rs::verify_fetched`). ### 10. Blob Storage Pipeline

All content — manifests and file chunks — passes through the same encode/decode pipeline.

Backup chunks are produced by the **same shared chunker** (`libs/fauna-core/src/chunker.rs`)
and pushed over the **same `POST /api/v1/chunks` route** as ordinary file sync, so the
**chunk-size and transport contract is owned by [`file-sync.md`](file-sync.md) § Content-Addressed
Storage** (max chunk `MAX_CHUNK = 8 MB` ≤ the smallest tier's "max blob" limit; the `/chunks`
body limit is sized for it). A consequence worth
stating: before that contract was fixed, the chunker emitted chunks up to 64 MB while the nest
transport capped at ~2 MB, so backups of any file larger than ~2 MB silently failed to upload —
the same bug as large-file sync (the two share the chunker and `/chunks`). Any change to the
chunk-size bound therefore requires re-verifying the backup tier_3/tier_4 suites.

**Encode (write path):**

```
raw bytes
  → zstd compress
  → prepend 0x01 prefix byte (marks zstd compression)
  → ChaCha20-Poly1305 encrypt under owner's BackupKey (if configured)
  → store at blobs/{hash[0:2]}/{hash[2:4]}/{hash}
```

**Decode (read path):**

```
load blob
  → ChaCha20-Poly1305 decrypt under owner's BackupKey (if key present)
  → inspect prefix byte: 0x01 → zstd decompress, 0x00 → strip, other → as-is
  → refuse past the decode bound (never expand past it)
  → return raw bytes
```

**Every decode is bounded — no stored blob expands past a stated bound, whatever its prefix byte claims.** Several writers store a request body verbatim (video segments, blob PUTs, rail bodies, spilled payloads — the passthrough `compat-remnant-sweep.md` § Program 4, tranche B3 (iii) keeps), so the at-rest prefix byte is the client's to choose: a `0x01` ‖ zstd body of a few KB decodes, unbounded, to gigabytes — inside the anonymous `GET /api/v1/chunks/{hash}`, or inside the GC walk of a live post's `blob_refs`. So `backup::decode_blob` — the one decoder every blob-store reader goes through (the chunk and manifest doors, the relay resolver, the web-content serve, the mail body plane, user config, share mint, the GC probe and walk, the snapshot check, materialize, the folder mirror) — decompresses through `decompress_chunk_bounded` at **`backup::MAX_DECODED_BLOB`**, the shared chunk bomb guard (`fauna_core::compress::MAX_DECOMPRESSED_CHUNK`, 16 MiB), and a blob that would exceed it is refused, never expanded. The bound sits above every request body that can reach the store (the chunk/manifest and blob-PUT body limits, the WS message cap that bounds spilled payloads, a mail body chunk — compile-time pins beside the constant), so a legitimate blob always fits and a refusal means the bytes were never a nest-framed body: the GC's content-address probe then answers from the raw layer exactly as it always did for raw-stored bytes (§ 9). **The one population above the bound is the nest's own self-backup snapshot** (§ 11 — a whole-database hot copy or logical dump, served by no route): its reader, the restore command, decodes through `backup::decode_snapshot_blob` at the snapshot's recorded `size_bytes` (its `backups/<hash>.manifest.json` sidecar), and refuses a blob with no sidecar.

Storage is content-addressed: the on-disk path is derived from the BLAKE3 hash of the **stored body** — the plaintext hash for a plaintext chunk, the **ciphertext** hash for a client-sealed backup chunk (the convergent `BackupKey::convergent_chunk_root()` seal, carried in the manifest's `stored_hashes`; keying mechanism owned by [`../architecture/owner-key-material.md`](../architecture/owner-key-material.md) § Path A — FS-BIND FOLLOW-ON A). Identical content is stored exactly once, regardless of which file or snapshot references it — the seal is deterministic per owner, so identical plaintext seals to the identical stored blob.

### 11. Nest self-backup (DB hot-copy + logical dump) — bounded by retention

Separately from the user-facing folder/message snapshots above, the nest keeps **its own** disaster-recovery copies of the SQLite database: a **hot-copy** (`rusqlite` backup API → exact restorable `.db`) and a daily **logical dump** (portable NDJSON tar.zst). These are recorded in the `backup_snapshots` table (NOT `blob_metadata`), so the § 9 GC — which only reclaims `blob_metadata` blobs referenced by live snapshots — **does not** touch them. They therefore carry their **own keep-last-N retention**, applied after every write:

- **Cadence.** The hot-copy runs at most **hourly** and the logical dump **daily**, both gated inside the ~60 s scheduler tick (`DB_BACKUP_INTERVAL_SECS`). The hot-copy must **not** run every tick — doing so (and never pruning) wrote a fresh full-DB copy every 60 s to the blob store and filled example.com's disk to 68 GB.
- **Retention.** After each backup, `BackupService::prune_backup_snapshots` keeps only the newest N of that format (`KEEP_SQLITE_BACKUPS = 24`, `KEEP_LOGICAL_BACKUPS = 7`), deleting each pruned row **and** its blob file **and** its `backups/<hash>.manifest.json`. A content-addressed blob still referenced by a remaining row (an unchanged DB hashes identically across cycles) is preserved.

This keeps the self-backup store bounded (~24 hot-copies + ~7 dumps) independent of the user-snapshot GC.

⚠ **These copies share the ONE content-addressed blob root with user content, and the first pair lands at boot** — two facts the cadence above does not imply, and both have already cost a test its meaning. The hot-copy and the dump go through the same `DiskBlobStore` and the same `hh/hh/<hex>` fanout the chunk routes write (only the `backups/<hash>.manifest.json` sidecar tells them apart on disk); and `tokio::time::interval` completes its first tick immediately, at which point `last_db_backup`/`last_logical_dump` are still `-1`, so *both* run before any seat has connected. A fresh nest's blob store is therefore **never empty and already megabytes** — measured 2026-09-02 on a nest with nothing in it: 2 732 033 B of hot-copy plus 880 B of dump. Consequences for anyone reading the store: a "the store is non-empty" check witnesses nothing (it is true at boot), and a whole-store byte total is not a measurement of user content — subtract the hashes the sidecars name. The tier_3 content-residency witness (`tests/e2e-unified/tests/platform/sync/test_orchestrator.py::test_ws_metadata_only_folder_relays_bytes_without_resting_them`) made both mistakes and so could not pass from the day it was written; its `_content_plane_blobs` helper is the shape to copy.

⚠ **The hot-copies are written unencrypted in production** (the service is constructed with no `encryption_key`), so each is a complete copy of `nest.db` in the clear. That is unremarkable while the live DB holds the same plaintext — but it means the path-sealing S9 flip's plaintext scrub does **not** reach them, and the pre-scrub plaintext outlives a scrub by the retention window. **RULED 2026-08-01: the flip ratifies that window rather than invalidating this store** — these images are the destructive migration's only rollback, and the retention above closes the window by count-based rotation after 24 post-flip backup cycles. The ruling, its rejected alternatives, and the three flip-contract requirements it adds are owned by [`../architecture/encryption-at-rest.md`](../architecture/encryption-at-rest.md) § Carve-outs; this section owns only the mechanism and its retention.

### 12. Blob-store disk guard (hard backstop)

`DiskBlobStore::put` refuses a **new-blob** write when the filesystem's available space would fall below a floor (`DEFAULT_MIN_FREE_BYTES`, 2 GiB), via `statvfs` on the blob root. This is the deployment-wide backstop that makes the disk-fill outage class **unrepresentable**: even if some future writer leaks, no blob write can drive the disk to `ENOSPC` and brick the nest at boot (the nest's SQLite DB + WAL always retain headroom to write). The guard is bypassed for an **idempotent re-put of an already-stored blob** (it writes nothing) and never affects reads/deletes/dedup — so a box that *is* near-full stays readable and recoverable. A refused write surfaces as a normal upload/backup error (graceful), never a crash. The `statvfs` probe is Unix-only (the nest's deploy target is Linux Docker/VPS); on the dev/test-only Windows build, where POSIX `statvfs` is unavailable, `available_bytes()` fails-open (returns `u64::MAX`) so the binary builds and writes are never wrongly blocked — the guard is not a Windows concern.

Six semantics worth not re-deriving, each pinned by a mutation-verified tier_1 test:

- **`AuditVerdict::Unreachable` is deliberately NOT one of the three alerting states.** A destination unreachable right now says nothing about the backup's health — a laptop on a plane would otherwise raise a data-loss alarm every flight. It is not swallowed either: an unreachable pass never refreshes the last-passed clock, so sustained unreachability becomes `Overdue` on its own. That *is* the "no device awake for a week" case the constant is for.
- **`Overdue` is the escalation of a non-verdict, not a ranking above freshness.** A destination the client can actually read reports what it found; overdue is reserved for a read that could not be made. Checking overdue first would have reported `Overdue` for the first-ever audit of any destination older than the window — i.e. every existing user on the day this shipped.
- **Freshness floors the destination's high-water at `BackupDestination.added_at`.** A destination enrolled minutes ago legitimately holds nothing (the nest sweeps every 15 min), so judging its empty custody against a years-old local high-water would alarm on every enrollment. The floor starts the clock when the user asked for the backup; the slack then does its normal job.
- **The client's side of the freshness comparison is an OBSERVATION it wrote down, not a read.** `AuditStateSnapshot::observed_high_water` is the newest message-kind record this device has actually displayed, persisted monotonically alongside the audit records. It is deliberately not derived from the source nest: any live read is the audited party's own word, so a source that answers "nothing new" would make freshness unfailable forever — whereas what a device saw with its own eyes cannot be retracted afterwards. It never moves backwards (opening an old conversation must not erase the evidence that newer data exists), and it is **bounded by the observer's own clock**: the stamps it is fed are the sender's word (a FaunaMls message's timestamp is written by whoever sent it), so each *incoming* stamp is clamped to the audit clock's now plus `OBSERVATION_MAX_FUTURE_SKEW_SECS` (5 min, a drift cushion that is a sliver of the slack) before the monotonic comparison — one future-dated message from any correspondent would otherwise latch the high-water and hold every destination in a freshness failure for ever, burying a real one; the clamp never lowers a stored value. `None` — a client that has observed nothing — cannot fail freshness, which is what keeps a fresh install quiet. Each app feeds it from its own render path; linux uses the conversation list.

- **A `Passed` verdict means fresh AND included.** Inclusion sampling (`evaluate_inclusion`) draws `AUDIT_SAMPLE_K` records **per (destination, kind-scope)** — the ratified per-scope guarantee, so sampling K across a destination's whole custody set would silently weaken every scope but one — fetches each by manifest hash from **the destination**, and opens it under the owner's derived `NestBackupKey`. Present-and-openable is the whole test: a destination cannot forge bytes sealed under a key it never holds, and the walk verifies the reassembled file's blake3 against the manifest. The last-passed clock advances only when both arms pass, so `backup-destination-last-audit-time` means "fully verified at", not "was reachable at". Freshness runs first and short-circuits — it is free, while inclusion costs a fetch per sampled record. Two sharp edges: the seed is the pass's `now`, so successive passes cover different subsets (detection compounds across days rather than re-checking the same K forever); and a custody row reported **without a path counts as a failure, not a skip** — skipping it would hand a hostile destination a one-line bypass of the entire arm (report custody with paths omitted, never be sampled, pass forever).

- **The inclusion population is anchored in the set's own sealed ledger, never in the destination's list alone (2026-09-28).** Until then both arms drew their population from `fauna.backup.custody.list` — the audited party's own statement — so a destination that dropped older custody *and stopped listing it*, keeping only recent rows fresh, passed both arms, and the 81 % figure held only for rows that stayed listed with their bytes lost. The independent population is the `manifest.<kind>` mirror the source nest writes **last in every pass that moved content** (`../architecture/segment-backup-protocol.md` § Cross-location backup protocol): the source's own upload ledger for that set, one per (kind-scope, family), naming every live segment's `.dat` and, since the pair widening, its `.meta` — sealed under the owner's `NestBackupKey`, so the destination serves it but can neither author, edit nor forge it. It is the row's "source's upload ledger" candidate, delivered through the destination with no new wire kind and no trust in the source's *live* word. The rule (`evaluate_inclusion`): for every reserved-set mirror row the destination lists, the client opens the mirror under the owner's key and requires **every path it names to be custody at that destination** — live, or a retained generation inside `T` (the compaction window: the coordinator tombstones compacted-out paths first and re-uploads the mirror last, so between the two the live mirror legitimately names paths just tombstoned; a retained generation still holds the bytes and is restorable, so it counts, and it joins the sampling population like a live row). A named path that is neither is **missing with certainty** — no sample needed, so de-listing is caught at 100 %, not 81 % — and a mirror the destination cannot produce, or that does not open or decode, fails its set outright: a set without a readable ledger is unverifiable, and hiding the ledger is exactly the de-listing move. Live rows the mirror does not name yet (a segment uploaded moments ago, ahead of its mirror) stay in the population and are sampled as before, and the covered-folder mirror plane, which has no such ledger, takes its anchor from the attaching client's own replica index under the same rule (below). The one extra read this costs is the destination's retained-generation list, walked only after freshness passed and failing toward "could not ask" like the custody read. **Stated residuals, each with its own row:** the ledger's *generation* — a hostile destination rolling a whole set back to an earlier **genuine** state (an older sealed mirror plus exactly the segments it names, every stamp forged fresh), losing everything after that point and nothing before it — **is pinned since the same day, the next bullet**. A destination that de-lists the ledger row *itself* is judged by the pin's **vanished-ledger rule** since 2026-09-29, the next bullet. Rejected: an owner-facing "accept the vanished set" gesture (rule A — the owner can judge a vanished set no better than the pass can, and the loss window this rule leaves is `T` itself, the bound the whole design already accepts); dropping the pin on the first retained sighting (a destination could tombstone the ledger row honestly-looking, wait one pass, and then de-list at leisure). **Stated residuals:** during a genuine source regression a hostile destination may serve any post-regression ledger at or below the source's new counter and the pin re-bases to it, so the segments the source uploaded between that ledger and its counter are unguarded for that one pass (bounded by the event's rarity and by the pin catching up on every later pass); a rollback that precedes the device's first audit is invisible, and so is a ledger a device never saw — a set whose ledger row was de-listed before this device's first pass over it is the unanchored 81 % case, since nothing this device holds says the ledger existed; a set that vanished whole (ledger and every segment row, live and retained) is accepted once the window has passed since the device last saw its ledger live, the `T`-bounded loss the design accepts; a set re-created within seconds of a pass after its old pin lapsed may alarm for that one pass (the upload race, self-clearing next pass); pins die with a removed destination's record; and the accepted regression is a recovery moment the owner is not yet told about — the destination retains what the nest lost for `T`. ## Security Properties

- **Two-key model (ratified 2026-07-23, target state).** Client-originated data seals under `BackupKey` (client-only, never nest-held — the bullet below). Nest-originated message-kind segment backups seal under `NestBackupKey` (`owner-key-material.md` § Path A-sibling-0), delegated to the user's own source nest — sound because the key seals only data that nest already hosts; destinations stay blind under either key. Accepted residuals, stated: mail dropped at SMTP ingest is undetectable in any backup design (ingest trust); backup-loss-under-attack is bounded by the destination custody grace window (T = 30 d) for retroactive wipes and by the client audit cadence for staleness. **The grace window is BUILT (2026-07-24)** — retained generations, quota-charged, with client-drivable `fauna.backup.generation.{list,restore}` recovery over the owner's own connection to the destination ([`segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Custody grace window (T)); the **client audit loop is COMPLETE in shared Rust as of 2026-07-29** — freshness + overdue over the destination's own `fauna.backup.custody.list`, plus `AUDIT_SAMPLE_K` inclusion sampling under the derived `NestBackupKey`, its population anchored in the set's own sealed `manifest.<kind>` ledger (and, for a covered folder's mirror set, in the attaching client's own replica index) since 2026-09-28 — and renders on all 7 apps (§ Background Tasks → *Implementation status (audit loop)* owns the build status and the population's stated residuals).
- **Encryption at rest** — blobs are ChaCha20-Poly1305 encrypted under the owner's `BackupKey` (Path A in [`../architecture/owner-key-material.md`](../architecture/owner-key-material.md)) on the data owner's client (the only `BackupKey` holder, derived there from the identity seed) before upload. The nest holds ciphertext only, unconditionally — `bins/fauna-nest/src/chunk_routes.rs:54-64` calls `encode_blob` with `encryption_key = None`, hardcoded at `bins/fauna-nest/src/main.rs:741-747`. No nest reconstitutes content server-side today; restore is the data owner's client pulling chunks back and decoding locally.
- **Destination path-blindness (verified 2026-07-29)** — a backup destination, owner-administered or held-for-friends, never receives real file or directory names: the only production writers against a destination are the two segment-backup coordinators (`libs/fauna-sync-engine/src/segment_backup.rs:866`; `bins/fauna-nest/src/segment_backup.rs:383`), every path they record is synthetic (`<owner-actor-hex>/seg-NNNNNNNN.dat`, `manifest.<kind>`), and per-file metadata rides inside `BackupKey`-sealed manifest blobs. What a custodian *does* see is owned by `../architecture/encryption-at-rest.md` § Per-content-kind conformance → *Backups (held-for-friends)*. The *hosting* side is the opposite today — a nest hosting a user's live folders keeps plaintext paths per the Folder files / Backups (own data) rows there — a declared to-tighten gap under the 2026-07-29 paths-are-content ruling (that doc's § Carve-outs owns the tightening set and direction; the mechanism is ratified at `path-sealing.md` § Sealed names & paths).
- **Integrity** — every chunk and manifest is keyed by its BLAKE3 content hash. Corruption is detected at decode time when the computed hash does not match the stored key. **The manifest gets that check first, and unconditionally** (`fauna_core::file_download::fetch_manifest`, for every fetcher, before the decode and before the seal branch): it is the root the rest of the walk trusts — the whole-file compare, the per-chunk compare and the sealed chunks' key derivation all read their expected hashes *out of the manifest* — so a served document that is not the one asked for would otherwise be internally consistent with itself and pass every later check. A reader therefore detects a substituted *or* seal-stripped manifest, not only a corrupt body.
- **Operation lock** — full-restore ZIP streaming holds an advisory lock that blocks concurrent GC, preventing a race where GC deletes a blob that is mid-stream in a restore response.
- **Deletion delay** — the 48-hour pending action window and 30-day soft delete window protect against accidental or malicious deletion of snapshots.

## A destination's capability

- **A custody copy is pure-backup** — for friend-as-backup nests and the owner's own offsite-but-rarely-touched node. The gate is the custody-copy flag on the destination nest — enforced by `bins/fauna-nest/src/segments/compact_handler.rs`, `bins/fauna-nest/src/segments/compaction.rs`, `bins/fauna-nest/src/filesync_handlers.rs::create_message_kind_handler` (the live WS-RPC snapshot-create handler — the HTTP `snapshot_routes.rs` path rejects message-kind snapshots and routes the caller to the WS-RPC kind), and `bins/fauna-nest/src/bridge_imap_handlers.rs`. ## Known gap: bridge ciphertext and content-row data

## Known gap: segment-backup blobs vs GC

The § 9 GC builds its reference set from `snapshot_files` + live `sync_changes` only. **Segment-backup** chunks and their `manifest.<kind>` mirror are uploaded through the standard chunk pipeline (`/api/v1/chunks`, `/api/v1/manifests` → `blob_metadata` with `kind` `chunk`/`manifest`) but **intentionally skip** the SyncDb / `record_change` epilogue (`SyncEngine::upload_bytes`, `libs/fauna-sync-engine/src/engine.rs` doc comment; the coordinator is `libs/fauna-sync-engine/src/segment_backup.rs`). The only record that a given manifest is *live* is the **client-side** `segment_backup_manifest_state` table in the sync-engine SyncDb — the **nest holds no server-side record** of which segment-backup manifests (and their chunks) are current.

**Consequence.** On a destination nest — every node runs the § 9 GC (`GcScheduler`, ~6 h interval, 30-min grace, `bins/fauna-nest/src/main.rs`) — every segment-backup blob is unreferenced from GC's point of view, so it is **deleted one GC cycle after the grace period**: *data loss* of a live backup, the opposite of the "orphans never reclaimed" leak it might first appear to be.

**Why this was latent, not live, at discovery — and why it no longer depends on that.** When this gap was found, the segment-backup coordinator ran over `UserConfig.backup.destinations`, empty on every platform because the destination create/edit UI did not yet exist — a clean no-op, so no segment-backup blobs were uploaded anywhere and nothing was at risk. **That precondition no longer holds**: the destination create/edit/remove UI has since landed on all 7 apps (§ Background Tasks → *Implementation status today*, tier_3-proven 2026-06-15; tui 2026-07-24; `docs/goal/behavior/backup-destinations.md` § State & data shape + `docs/goal/ui/backups.md` § Manage backup destinations are both **ratified**, no open item remaining), so destinations are populated in practice today. The safety argument no longer rests on the coordinator being a no-op — it rests on the custodian-side redesign immediately below (landed 2026-06-15, `bins/fauna-nest/src/backup/gc.rs`'s `backup_custody_manifest_hashes` chain), which closes the gap independent of whether any destination is configured. The § 12 disk guard independently backstops disk-fill regardless.

**Resolution — custodian-authoritative custody (REDESIGNED 2026-06-15; supersedes the 2026-06-14 single-manifest "ledger", which was withdrawn at implementation time when it proved unable to protect a multi-segment backup — a backup is N per-segment `ChunkManifest`s + a mirror, not one manifest; full rationale: `docs/goal/architecture/segment-backup-protocol.md` § Cross-location backup protocol → *GC-safety — custodian-authoritative custody*).** GC-safety belongs to **the custodian holding the bytes**, derived *per-path* from what it received — not declared by the client. A backup is a **file-sync of the owner's reserved backup folder to the custodian**: the coordinator records each uploaded segment + the mirror as a path (`fauna.sync.changes.record` → `sync_changes`, the epilogue `upload_bytes` skips only on the *source*), and the custodian's GC walks the **latest non-deleted manifest per `(folder, path)`** across custody-copy reserved sets (between the `sync_change_manifest_hashes` collection and the manifest walk at `gc.rs:80`/`:86-158`). The model is **omission-safe** (a path the client doesn't re-mention stays live — never client-declared-full-set, which would make omission delete) and reclaims on **supersede** (new manifest, same path), **compacted-out** (`delete` for the path), or **destination removal** (drop the reserved set). The custodian (nest = first implementor) adds two custody behaviors: **device-pull exclusion** for custody-copy sets and **latest-per-path reclamation**. There are **no** `register_manifest`/`deregister_manifest` wire kinds and **no** client-declared manifest set (those were withdrawn — never implemented). **Do NOT** bolt a "protect every uploaded manifest forever" guard onto GC in isolation — that reintroduces the leak.

**Status — the custodian half LANDED + tier_3-proven 2026-06-15; the writer half is the NEST arm's since the slice-5 flip (the client coordinator that first proved it was deleted 2026-08-17).** Both backup-mode behaviors are realized by a thin dedicated **`backup_custody` projection** (PK `(folder_id, path_hash)`): the `fauna.sync.changes.record` handler routes custody-copy records into it instead of `sync_changes` (so device-pull exclusion is **automatic** — backups never enter the device-sync feed, nothing for `get_sync_changes_for_folder` to filter) with UPSERT-on-supersede / NULL-tombstone-on-`delete` / whole-set-drop-on-removal (latest-per-path by construction), the GC reference walk chains `backup_custody_manifest_hashes()` into the manifest set it decodes for chunk refs (`bins/fauna-nest/src/backup/gc.rs`), and `delete_folder_for_user` drops a backup set's custody so `fauna.folders.delete` is the GC-safe removal. Proven by `bins/fauna-nest/tests/segment_backup_gc_safety.rs` (custodian half, direct handler) **and** `bins/fauna-nest/tests/nest_backup_coordinator.rs` (the nest's own coordinator against a real served destination over a real federation handshake, with no client alive: record-on-upload → custody populated → the destination's chunk keys equal what the granted `NestBackupKey` root produces → removal teardown). The writer-side mechanics — `upload_bytes` returning its manifest hash, per-path record-on-upload + delete-on-compacted-out, lazy destination-side custody-copy provisioning (by the destination's federation record handler), and the *automatic* `reconcile_removed_destinations` loop over persisted `backup_destination_seen` rows — all live in the nest arm (`bins/fauna-nest/src/segment_backup.rs`; `message-segment-store.md` § *Supersede / remove handshake* → *Destination removal* owns the two teardown shapes). **The data-loss gap is closed.** The closure's residual condition — every custody-referenced manifest must decode for the walk to reach its chunks — is enforced fail-closed since 2026-07-09: an undecodable `ChunkManifest`-class reference skips the delete phase for that run instead of silently orphaning chunks (§ 9 steps 3–6, including the reserved-rail direct-blob classification that keeps `__config`/`__drafts`-style references out of the decode walk entirely).

## FAQ

**Q: What are the default retention policies?**
A: **Today:** retention is the per-set 2-field `RetentionPolicy { max_snapshots, max_age_days }` set at create-set time (§ 8 drift note); a set with no policy keeps everything. **Target** (§ 8, not yet built): the borg-style `keep_*` rules as additive fields on the per-set policy (§ 8's 2026-08-01 ruling), nothing pruned when unconfigured. There are no system-wide defaults — each user controls their own policy.

**Q: What's the default storage quota on a fresh nest?**
A: The "free" tier (default for new users): 100 MB inbox, 100 MB storage, 3 devices, 10 MB max blob, 5 feeds. "Personal" tier: 1 GB inbox, 10 GB storage, 5 devices, 100 MB blob. "Community" tier: 5 GB inbox, 50 GB storage, 10 devices, 500 MB blob.

**Q: How often do auto-snapshots run?**
A: The scheduler checks every 60 seconds for folders with new changes. It waits a 30-second quiet period (no new changes) before creating a snapshot. So a snapshot appears 30-90 seconds after the last file change.

**Q: How long before a deleted snapshot is actually gone?**
A: 48-hour pending action delay (cancellable) → soft delete with 30-day recovery window → hard purge. Total: up to 32 days from delete request to permanent removal.

**Q: How often does garbage collection run?**
A: Every 6 hours. Orphaned blobs younger than 30 minutes are protected (grace period).
