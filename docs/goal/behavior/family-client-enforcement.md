**Built — Slice E, the WINDOW half of the app legs (linux + web, 2026-08-01):** window enforcement is pure client-local clock, so § Screen time's build order puts it first — and it needs no wire traffic at all. Three pieces landed together. (a) **The guardian's editor** grew the three ratified inputs (`family-policy-screen-window-start-input` / `-end-input` / `-daily-minutes-input`); the two bounds are typed as `HH:MM` while the wire keeps minutes-from-local-midnight, so a new shared pair `fauna_core::screen_time::{parse_time_of_day, format_time_of_day}` (+ `parse_daily_minutes`) owns that conversion once for all 7 apps rather than each editor inventing its own reading of `"9:5"` / `"24:00"` / `"08:60"`. An **empty field means "this control is unset"**, which is how a guardian clears a limit — hence text inputs rather than pickers — and the editor sends a **present** `screen_time`, so an all-empty save really does remove every limit (absent would mean leave-unchanged and could never clear one). The save pre-validates through the *same* `ScreenTimePolicy::validate` the nest runs, so a refusal (half-set bounds, `start == end`, out-of-range budget) surfaces its reason on `error-message` locally instead of as a generic transport failure. (b) **The ward's lock** (`screen-time-lock` + `screen-time-lock-message`) renders off one new shared call, `fauna_core::screen_time::screen_lock_message(policy, now_local_minutes, used_today_minutes, guardian_handle) -> Option<LocalizedText>` — which calls `lock_state` itself rather than taking an already-computed verdict, so the **gate and its wording cannot drift** and "locked but nothing to name" is unrepresentable (the `render_verdict_composed` lesson applied preemptively). linux mounts it as a `gtk::Overlay` child over the page stack (`screen_lock.rs`), web renders it in place of the page content in `+layout.svelte` over a `screenTime.svelte.ts` store — the twin of each app's existing `content_policy` module. **Built — Slice E, the BUDGET half of the app legs (linux + web, 2026-08-01):** the heartbeat and both usage readouts, closing the pillar on the reference legs. The whole cadence is ONE shared state machine, `fauna_core::screen_time::UsageHeartbeat` — what counts as use, when to flush (`USAGE_REPORT_INTERVAL_SECS`, five minutes), what a failed report owes, and how the nest's cross-device total combines with minutes this device has not sent yet. Each of those is a place two apps could silently disagree and give one child two different bedtimes, so no app owns any of them; an app supplies only its clock, its UTC offset and whether it is being looked at. Four decisions in it are load-bearing and were NOT restatements of the section above, so they are recorded here. (a) **The lock does not wait for a heartbeat**: `used_today_minutes` is the nest total PLUS this device's unreported minutes, so the budget lock fires the minute it is reached and the cadence bounds only how fast *other* devices learn. (b) **Time on the lock screen is not use** — callers pass `active = foregrounded AND not locked`; crediting it would inflate the guardian's readout with minutes the child never spent, making the very readout this section requires report a number that never happened. (c) **A suspended device credits at most `MAX_ACCRUAL_STEP_SECS` (two minutes) per step**, so a closed lid cannot bill a child for eight hours; callers therefore MUST tick at least that often (linux's `LOCK_TICK_SECS` and web's `lockTick`, both 60s, are the same timer). (d) **A failed report re-credits its minutes** rather than forgiving them, because the section above defines the delta against the last *successful* report. The two readouts resolve through one shared `fauna_core::format::usage_today_line`, which is what makes the transparency rule ("the ward's summary shows the same number") structural rather than a convention two surfaces could drift from; the ward's copy is **folded into `family-policy-summary`** rather than claiming a new ui.yaml ID, since usage is a line of "the active policy, read-only" (the supervised section's element set is unchanged). Proof: 18 further `screen_time::tests` on a mock clock (cadence, re-credit, in-flight de-duplication, the suspend cap, lock-screen exclusion, the midnight lift, budget-clearing), 5 further linux `screen_lock::tests` (the status-read seed locking on first paint and its under-budget twin, budget-lifting unlocking, and the poke really accruing), and tier_3 `test_family.py::test_family_screen_time_budget_and_usage_readouts` — no-budget renders no readout, a guardian sets a budget through the real editor, both surfaces show the same figure, reported minutes travel ward→nest→guardian, and exhausting the budget flips the lock to its `LockedBudget` message. **⚠ Web-leg proof status (2026-08-02): both Slice-E web legs landed as CODE ONLY — the two tier_3 tests above had never once run `--app web`** (blocked first by the wasm-chunk-check red, then by an e2e-bridge false-death misclassification, both since fixed). **tui joined 2026-08-01 (Slice E, both halves at once — the lead-app leg).** It needed no FFI work: `apps/fauna-tui/src/family.rs` reaches `fauna_client_family::FamilyClient` in direct Rust, so every shared call the reference legs added was already in hand, and tui wrote **zero** screen-time logic of its own. Three things are worth recording because they are tui-shaped rather than lifts. (a) **The lock replaces the page pane by returning different elements from `App::page_elements`, not by painting over it.** That one list is the single source for the pane's paint, the automation registry *and* the focus ring, so gating there makes all three agree by construction — a terminal has no z-order to hide a control behind, and a lock that merely painted over the page would leave the ring able to Tab into it. ## Content policy — the client render-enforcement engine (v1.x design, firmed 2026-07-15)

Pillar 2's mechanism. Scope: the **social rail** (feed / posts / conversations) — mail reach is pillar 1's domain, and mail *content* scoring stays at the perimeter/MDA per `../architecture/content-scoring.md`.

**The engine is general, not guardian-only.** `moderation.md` § Categories & enforcement item 1 ratifies that a user's own `spam_threshold` / `phishing_threshold` "optionally collapse/hide flagged content in their own view" — a promise the code has never implemented (labels today produce a badge and a moderation-queue row, nothing more; the only built collapse verbs are muted-keywords and the legal-takedown tombstone). The v1.x content pillar builds that missing stage **once, for every user**, and the guardian policy composes into it — "for a supervised account, 'user-side' includes the guardian's policy" (`moderation.md:41`). Building it guardian-only would fork the exact engine the unsupervised path is still owed (priorities #1/#4).

- **One shared evaluator, revived in place.** § App surface's rule stands: the pillar extends `fauna_core::obligation::evaluate_obligations` rather than inventing a parallel engine. That export is currently dark (zero production callers) and shaped for the superseded 2026-03-15 server-pipeline framing, so it is **reshaped, not wrapped**: `ObligationRule.min_confidence` becomes per-mille `u16` (the dag-cbor float ban; the live classifier path is already per-mille), `EnforcementPoint` gains `ClientRender`, and `ObligationAction` gains the two client render verbs `Collapse = 8` and `Block = 9` (additive `#[repr(u8)]`; `obligation_action_label` already degrades unknown discriminants to "Flagged" on older clients). A small fold on top — `render_verdict(labels, rules) → Show | Badge | Collapse | Block` — is what render paths consume; rules are assembled from the user's own `spam_preferences` (their thresholds → `Collapse`) plus, when supervised, the guardian's content rules. **Strictest wins** (the severity sort the evaluator already has): a ward may set themselves stricter than the guardian floor, never looser.
- **The guardian rule shape** is a per-category floor over the four negative canonical categories (`nsfw`, `spam`, `phishing`, `commercial`): `inherit` (default — the ward's own preferences decide) | `collapse` (rendered collapsed, reveal affordance) | `block` (no reveal; a tombstone-style placeholder naming the policy, mirroring the legal-takedown render shape). There is deliberately no per-category confidence knob in v1.x — the trigger threshold is a hard-coded shared constant (no-operator bucket 1; a per-mille knob can join additively if real households need it). `trusted` is a positive signal and takes no floor.
- **Where it binds:** the two render surfaces, beside the collapse verbs that already exist there — the feed read model (beside `FeedManager::is_muted`) and the conversations render (beside the `legal_takedown_ref` collapse; labels come from the post-decrypt `classify_text` hook that already feeds `LocalDetectionStore`). **Honest bound, stated on the editor surface:** a floor binds only where a producer emits that category's label — today's built-in heuristic emits `spam`/`phishing`; `nsfw`/`commercial` are reserved categories that bind as their producers (labeler subscriptions, future classifiers) ship. A floor on an unproduced category is stored and waiting, not enforcement theatre.
- **Ward transparency:** the ward's read-only policy summary renders the content rules exactly as it renders the reach knobs; a blocked item's placeholder names the policy ("hidden by your family policy"), never silently disappears (§ The trust shape invariant 4).
- **A rule value a client cannot parse renders fail-closed** (`block`), the same rule as the reach knobs.
- **A policy that could not be FETCHED keeps the last-known state in force (ratified 2026-08-02 — the parse rule above covers a value the client *holds* but cannot read, this one covers the value it could not *obtain*).** Three clauses, binding every app:
  1. **A failed `fauna.family.status` read yields no information, and enforcement state never moves on no information.** The supervision inputs a client enforces (the content floor here, `content_notify`, and § Screen time's policy) transition only on a *successful* status read — which may report unsupervised and clear them — or on an identity change (the switch/sign-out isolation contract, `../architecture/apps/account-scoping.md` § The scoping taxonomy). In particular a failed refresh **never clears an already-loaded floor**: refresh fires at cold launch and on WS reconnect, exactly the moments a read is least likely to succeed, so clear-on-failure converts a transient outage — or airplane mode — into an unsupervised render on a fully *conforming* client. "Read failed" and "read says unsupervised" are different facts; plumbing that collapses them — a `try?`/`catch` mapping every error onto the absent-policy value, or an error arm that reuses the successful-unsupervised message shape — is wrong per this rule, and is exactly how three of the seven legs shipped (§ Implementation status today).
  2. **The last-known supervision snapshot is persisted per account, client-side** — supervised-by, the content floor, `content_notify`, and the screen-time policy; written on every successful status read, loaded at launch ahead of the first read, erased with the account's other stores. Persistence is what lets a cold start distinguish *unsupervised* (no snapshot, or one that says so) from *supervised, floor unknown* (a snapshot carrying the floor) — the distinction clause 1 cannot supply for a client that has never read yet, and without which the § Screen time window — deliberately enforced by pure client-local clock — turns airplane mode into a bedtime-lock bypass any child can perform. Class: **nest-authoritative replica, account-scoped placement** (`../architecture/apps/account-scoping.md` § The scoping taxonomy, classes 4/1). The record's shape + (de)serialization live in shared Rust — `fauna-client-family`, over the `fauna-client-accounts` `SecretStore` seam every app already holds — so seven apps cannot drift on it. Trust bound: at rest on the ward's device and ward-tamperable, inside pillar 2's declared conforming-client bound — and a deliberate act, where airplane mode is an accident. The viewer's *own* spam/phishing thresholds are deliberately **not** in the snapshot: failing them toward absent only under-enforces the viewer's own collapse (the benign direction), and they re-arrive with their own read.
  3. **Declared residual — the first-session-offline window:** a device that has never completed one successful status read for the account has nothing to remember and enforces nothing. Accepted: closing it would take blanket fail-closed, which blocks every unsupervised user's first offline launch; the window is one successful read wide, and any real onboarding performs that read immediately. The corollary runs the other way too: a graduated ward offline keeps the last-known floor until the next successful read clears it — fails toward enforcing, the transparency surfaces still name the policy, nothing is lost. (tui's existing gate — clear the floor when a successful read reports no guardianship — is the conforming shape of that clearing rule.)

- **A third source is BUILT into this engine (2026-09-09):** a region's published content policy composes into this same fold as one more strictest-wins rule set, beside the viewer's own thresholds and the guardian floor — one more argument on the composed call, the verdict precedence untouched, and the placeholder naming the region's authority as it names the family policy today. Two consequences for *this* engine, which is all this section owns: `render_verdict_composed` now returns a `ComposedVerdict { verdict, source }` rather than a bare verdict, because a blocked item has to be able to say whose rule blocked it; and the sources are folded **separately** rather than concatenated into one rule vector, which is what makes that answer possible. Nothing about the precedence, the trigger predicate, the fail-closed rule, or Guardian Notify's counting changed — the pre-existing hand-assembly test still agrees exactly. The source's content, its fetch path and its render are owned by [`region-blocking.md`](region-blocking.md) § The content plane, whose § Implementation status today records what of that is built (the shared-Rust half) and what is not (everything that would let a document reach a device).

## Guardian Notify (v1.x design, firmed 2026-07-15)

The guardian learns *that* the policy is acting — **category + count, never content, never a content identifier**. The 2026-03-15 spec's `NotifyConfig`/`NotifyPayload` HTTPS-callback shape is **superseded** (no operator-configured endpoints exist; delivery is nest-mediated like every other notification):

- **Source:** the ward's conforming client counts its own render-enforcement events (per category, per local day) and reports coarse aggregates — a new `fauna.family.notify_report { entries: [{category, count}], utc_offset_minutes }`, batched (at most hourly), carrying **no content ids** (`moderation.md`'s `scan_report` is the precedent for coarse-counts-only, but it is a write-only compliance beacon with no read path — Notify gets its own table). The nest verifies the caller is a supervised account with `content_notify` on and upserts `guardian_content_notices(supervised_actor_id, day, category, count)` — the same `INSERT … WHERE EXISTS (guardianship)` guard as the mail side tables: a no-op for unsupervised accounts, cascading with the ward, dropped at graduation. The `day` bucket is the **ward's local day, nest-stamped from its own clock via the clamped report offset** — the single bucket rule ratified 2026-07-16 in § Screen time (an absent offset degrades to UTC, so the nest keeps stamping the bucket itself and the ≤ one-doorbell-per-(ward, day, category) flood bound survives with client input limited to a ±14 h clamp).
- **Delivery rides the existing notification machinery** — nothing new client-side for the guardian: on the first report of a `(ward, day, category)` the nest writes an ordinary `notifications` row for the **guardian's** actor (a new `notif_type`, the ward as `sender_id`, the day bucket as the dedup key — so one doorbell per ward/category/day, not one per flagged item) and fans it out over the live per-actor push channel. The current count renders on the guardian's Family surface from an additive per-ward `content_notices` field on `fauna.family.status` — the notification is the doorbell; the status read is the truth.
- **Knob:** one guardian policy boolean, `content_notify` (default **off** — unsupervised-equivalent). The ward's policy summary shows it (transparency); the ward-side counting runs only when it is on.
- **Trust bound, stated honestly:** the count comes from the ward's conforming client — a modified client under-reports. Notify is a lens on pillar 2, so it inherits pillar 2's bound; the reach pillar and the guardian-enrolled device remain the mechanisms that hold against a non-conforming client.

## Screen time (v1.x design, firmed 2026-07-15)

Pillar 3. Client-enforced by construction (the nest cannot see, and must not gate, when a child's device is in use — enforcement is a render rule on the ward's clients).

- **Policy document** (all defaults = unsupervised-equivalent, i.e. absent): a **usage window** `screen_window_start` / `screen_window_end` (minutes from local midnight, wrapping windows allowed — "21:00–07:00" is the bedtime case) and a **daily budget** `screen_daily_minutes`. Both optional and independent.
- **Window semantics + write validation (ratified 2026-07-16):** the window is half-open `[start, end)` in minutes from local midnight; `start > end` wraps midnight (so "until midnight" is `end = 0` with a wrapping start — every real window is expressible). The nest **refuses** at `policy.update` (the § Policy-update compatibility refusal rule, extended from "cannot name" to "cannot honestly store"): a window bound outside `0..1440`; a half-set window (bounds come in pairs); and `start == end` — an empty window has two contradictory readings (always-locked vs. no-window), so the guardian must say which they mean: clear the window for "no window", set `screen_daily_minutes = 0` for a deliberate full lock (a budget of zero has exactly one reading, so `0..=1440` is the budget's accepted range). The shared validation rule lives on the Rust policy type itself (`fauna_core::screen_time`), so every app's editor pre-validates identically to the nest. A client *reading* a stored window it cannot make sense of fails closed (locked — the render surfaces are what's gated; the Family page stays reachable), the same fail-closed rule as the content pillar. A policy that could not be *fetched* is the other case and follows § Content policy's unfetched-policy ruling (2026-08-02): the persisted last-known snapshot stays in force — a failed status read never unlocks, never clears a window or budget, and the first-session-offline residual is the same declared one.
- **Window enforcement is pure client-local clock** — no new wire: outside the window a conforming ward client renders a full-screen lock naming the policy and the guardian (the supervised indicator's explanation surface), with the Family page reachable read-only (the ward must always be able to see who supervises them and what the policy is).
- **The day bucket is the ward's *local* day, computed by the nest (ratified 2026-07-16; one bucket rule for this pillar *and* Guardian Notify).** A daily budget must reset at the ward's local midnight (a UTC reset is broken at large offsets), but the nest is never told a timezone and a client-*chosen* day would be a client-controlled rowspace/dedup key — the hazard the Notify design deliberately avoided. The ratified shape keeps the bucket nest-derived: each report carries a **UTC offset in minutes**, clamped to `-720..=840`, and the nest stamps `local_day = (now_epoch_secs + offset·60) / 86_400` **from its own clock**. The key space stays bounded (for any real instant the clamp admits at most two adjacent buckets — a hostile offset is under-reporting-equivalent, already inside this pillar's conforming-client trust bound, and the Notify doorbell bound stays ≤ 2 buckets per real day). The nest records the last-reported offset on the guardianship link (`guardianships.ward_utc_offset_minutes` — coarse ward metadata, the `last_seen` disclosure class; it dies with the link at graduation), so `status` derives "the ward's today" for its readouts without any new read-side wire. An absent offset (an older client) is `0` = UTC — the graceful additive degrade.
- **Daily-budget enforcement needs cross-device accounting** (a per-device budget would multiply by device count): the ward's client reports foreground use in coarse heartbeats — `fauna.family.usage_report { minutes, utc_offset_minutes }` at a fixed cadence, where `minutes` is the client-aggregated foreground delta since its last successful report (clamped per report, mirroring `notify_report`'s delta+clamp shape) — and the nest upserts `guardian_usage(supervised_actor_id, day, minutes)` (guardianship-guarded like every family side table, day = the local-day bucket above) and returns `{ day, day_total_minutes }` in the reply, so the enforcing client learns the cross-device total at each heartbeat without a second read; a **zero-minute report is a read** (returns the total without crediting — the unlock-screen check). Reporting and accounting run **only while a daily budget is set**: with no budget the client sends nothing and the nest's upsert is a silent no-op returning zero (no usage accounting without a declared policy — and, like `notify_report`, every exit replies the same shape, best-effort telemetry). The guardian's Family surface shows per-ward usage (additive `usage_today_minutes` on `status`); the ward's summary shows the same number (transparency, an additive top-level `usage_today_minutes` on their own `status` read). Minutes-per-day is coarse metadata (same disclosure class as `last_seen`, which the device row already stores); the nest never learns *what* was used, only that a conforming client was foregrounded.
- **Build order:** window first (zero new infra, the high-value bedtime case), budget + accounting second.
- Same conforming-client bound as pillar 2, stated on the editor surface.
