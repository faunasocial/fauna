The uniform status read is `fauna_client_config::read_backup_status`, and it is **not a pure read**: a destination whose row in the source box's destination list (`fauna.state.backup`) survives without its `NestBackupKey` grant and source-side registry row — after an identity-succession rebuild, or a crash between deregistration's two writes — reads as unenrolled: `fauna.backup.status` reports `enrolled: false` with no rows — a naively-repointed page would render blank for a backup that is in fact running. When the projection reports not-enrolled *and* the list holds ≥1 destination, the read calls `reconcile_backup_enrollment` (re-issues enroll steps (1) grant + (4) `destination.register`, both already idempotent) and re-reads, returning the healed projection in the same call. An enrolled owner costs exactly one round trip and no list read; an owner with zero destinations is never enrolled by a read. The **destination-side writer grant (step 3) is deliberately not healed** — it needs a per-platform authenticated connection to each destination nest, and it governs whether the *nest's* uploads are accepted rather than whether the status is truthful; until the slice-5 flip supplies it, a healed destination honestly reported `last_upload_time: None` with a growing `backlog_count` while the in-app driver kept the backup current (the pre-flip state: the slice-5 flip completed 2026-08-16 and every app's in-app driver is deleted — `backup-restore.md`).
- **Client enroll/remove sequence — all four nest mutations landed 2026-07-24** — destination-add runs **one shared enroll sequence**, `fauna_client_config::enroll_backup_destination` (`libs/fauna-client-config/src/backup_enroll.rs`; see its module docs for the full five-step ordering + crash-safety proof): (1) grant the source nest this owner's seed-derived `NestBackupKey` (`fauna.backup.nest_key.grant`); (2) take the source nest's identity as its connection proved it — the caller's bound nest id, never the nest's own `fauna.nest.info` claim (step 3 below); (3) register the revocable nest-writer grant **at the destination** (`fauna.backup.writer_grant.register`, over the destination's own authenticated connection — never the federation channel, so revocation stays operable with the source nest fully hostile); (4) register the destination **with the source nest's own registry** (`fauna.backup.destination.register` — see next bullet); (5) the atomic list write (through `mutate_backup` since the plane cut — § Create / edit / remove protocol). Destination-remove runs the symmetric `deregister_backup_destination` (`fauna.backup.destination.remove` on the source nest, then the list row drops); it does **not** revoke the destination-side writer grant (a distinct trust-facet action), and it makes **no destination-side call at all** — the destination-side teardown is the coordinator's, on its next pass (§ Create / edit / remove protocol → *Remove*). ⚠ Between the slice-5 flip and **2026-08-16** that teardown had no owner: the flip retired the client coordinator that used to drive it and the nest arm's comment deferred to a client call that does not exist, so a removed destination kept every uploaded chunk GC-pinned indefinitely. Steps (1)–(4) are each individually idempotent and inert without step (5), so their relative order is free; the one hard constraint is that all four precede the atomic list write.

### Destination data model (ratified)

A **backup destination** is another storage location — for the v1 scope, a nest the owner administers (a 2nd owned nest, or an offsite node the owner controls) — to which the owner's reserved folders (`__mail`, `__conv/<channel>`, `__drafts` / `__index` / library media; the authoritative per-kind segment table incl. `__calendar` / `__card` / `__post` is [`../architecture/message-segment-store.md`](../architecture/message-segment-store.md) § Layout — don't re-derive kind lists here) are replicated as ciphertext sealed under the owner's `BackupKey` ([`../ui/backups.md`](../ui/backups.md) § Encryption at rest). It persists as one row per `(destination nest, reserved-folder kind)` in the source box's destination list — a `Vec<BackupDestination>` in the account-state plane kind `fauna.state.backup`, sealed like every fleet-only kind (the nest stores opaque bytes unconditionally; row grammar: [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The kinds*). The authoritative type lives in `libs/fauna-core/src/data.rs`:

```rust
struct BackupConfig { destinations: Vec<BackupDestination> }   // Default = empty (coordinator no-op)

struct BackupDestination {
    destination_id: String,             // stable client-assigned id; key in the sync_db state tables
    destination_nest_url: String,       // origin URL of the destination nest
    destination_actor_pubkey: [u8; 32], // destination nest's identity as the enroll connection PROVED it (pin, else possession proof — never the fauna.nest.info claim); every later connection is held to it; detects URL-change vs nest-change
    folder_name: String,              // reserved-set name on the destination ("__mail", "__conv/<hex>", …) — one row per kind
    added_at: u64,                      // unix seconds
    // mode_hint: String — RETIRED 2026-09-28 (ruled; deleted by the folders mode contraction — the *Capability* paragraph below). Was "sync" | "backup", mirroring the destination's `folders.mode`; v1 always "backup".
    display_name: Option<String>,       // RATIFIED ADDITION (this pass): user-facing label; None ⇒ derive from the destination domain
}
```

`display_name: Option<String>` is the one ratified addition (uniform with `MailCredential.display_name`); the implementation adds the field with `#[serde(default)]` so pre-existing `__config` blobs parsed unchanged (that rail retired 2026-10-02 — [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)). Every other field already exists.

**Kind discriminator (ratified 2026-08-02 — the third-kind design pass).** `BackupDestination` grows `kind: String` defaulting to `"nest"` (`#[serde(default)]`-shaped, so every pre-existing `__config` blob parsed unchanged while that rail lived) — values `"nest"` (this section), `"client-device"` (§ Third destination kind below), `"s3"` reserved for the S3 pass. Per-kind fields are **additive and optional**: the client-device kind adds `custodian_device_id: Option<String>` (the device's stable sync device id — the same id its file-sync engines present) and `capacity_cap_bytes: Option<u64>`; the nest-only fields (`destination_nest_url`, `destination_actor_pubkey`) rest at empty/zero sentinels on non-nest rows and are **never read** there. Shared Rust exposes a typed projection (a `DestinationKind` enum view over the flat row) so per-kind fields cannot be misread at call sites — the at-rest shape stays flat + additive (additive-everywhere evolution, `../architecture/version-compatibility.md`), the code shape is typed. The S3 pass adds its fields the same way.

**Capability is the destination nest's custody-copy flag, and `mode_hint` is DELETED (ruled 2026-09-28, the folders mode contraction design pass; built 2026-09-28).** `mode_hint` was informational (v1 always `"backup"`), mirroring a `folders.mode` that no longer discriminates anything: the destination nest provisions the copy itself and marks it `custody_copy` ([`reserved-folders.md`](reserved-folders.md) § Destination capability owns the rule, and retires the active-replica `"sync"` capability as a row state — a readable replica would be a grant). So the field, `DestinationRegisterRequest.mode`, the nest's `backup_destinations.mode` column, `segment_backup::BACKUP_MODE` and the coordinator's and `delegation_runner`'s mode filters (which dropped nothing) all delete in place — no alias, no read-fallback (the 2026-09-24 baseline reset, `../architecture/version-compatibility.md` § Dimension 2, fourth exception); every enrolled destination the coordinator finds is acted on.

**The list is per source box (ruled 2026-09-30; built 2026-09-30 — § Implementation status today).** A destination list answers one question — where does *this box* back this owner up — so an account that lives on several boxes keeps **one list per box, never one for the account**. On the retired `__config` rail that held by construction: the blob was per nest. On the account plane a scope is the account's ([`../architecture/account-sync-plane.md`](../architecture/account-sync-plane.md) § The bind leg, ruling 3), so the list row names its box in its key: one list row per **source box**, keyed by the source nest's identity **as the connection proves it** — the id Create step 3 names as the writer (§ Create / edit / remove protocol), never the nest's own `fauna.nest.info` claim. The key grammar is [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md)'s (§ The `__config` dissolution schedule, the kinds table's `fauna.state.backup` row). Every reader — the Backups page, the status read's enrollment self-heal (§ Per-destination status read), the succession aftermath's `NestBackupKey` re-grant, the Nests-page trust facet — reads the row of the box its connection is bound to and no other: a row under another box's identity is never rendered on this box's page, never merged into this box's list and never registered at this box, and a reader that cannot establish which box it is bound to reads no list at all — the read fails visibly and every write is refused (refined 2026-09-30 with the consumer cut: an empty list would silently hide the destinations the box really keeps) — never another box's.

**Why the box and not the account (read 2026-09-30).** The list already holds facts about one box: a covered folder's row names the source nest and one of *its* folder ids (`folder_name` = `__folder/<source-nest-hex>/<folder-id>` — § Ordinary-folder coverage), and a client-device row is a pull from one box, whose registry holds its capacity cap and its check-ins (§ Third destination kind). One box's destination is often another of the account's own boxes — the first example this section gives, a second owned nest — which a list shared by the account would enroll as a destination of itself. And per box is the shipped behaviour, which a plane kind delegates to (`config-dissolution.md` P1): a device binds to one nest and no app surface re-binds it (`account-sync-plane.md` § The bind leg, ruling 4), so only an account that lives on several boxes could tell the two readings apart, and for that account the other reading changes what its boxes do.

**Refused: one list for the account** — every box the account lives on backing up to every listed destination. A destination keeps an owner's reserved-kind custody copy under `(owner, kind)`, with no source nest in the set's name or in the paths recorded into it (read 2026-09-30: `fauna_sync_engine::segment_backup::reserved_backup_set_name`, and `resolve_backup_custody_set` in `bins/fauna-nest/src/federation_handlers.rs`; only a covered folder's mirror set embeds the source nest). Two boxes writing one owner's `__mail` to one destination would write the same segment paths from two unrelated segment numberings: each upload supersedes the other box's live copy, which then survives only as a retained generation for the grace window, and the `manifest.<kind>` mirror alternates between two ledgers ([`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Cross-location backup protocol owns the custody model). Making that reading safe takes a source-scoped layout on every destination — a wire change and an at-rest change — to buy a behaviour no one chose: each of the account's boxes would start backing up to every destination, charged to the owner's quota there, with no page on which the owner asked for it. (Two *deliberate* enrollments of one destination from two boxes are ruled separately, 2026-10-01: the destination refuses the second — `segment-backup-protocol.md` § Cross-location backup protocol → *The writer seat*.)

**The marks stay the account's.** A `destination_id` is minted fresh at every enroll, so it belongs to exactly one box's list, and an unattested-destination mark is keyed by it and needs no box: a verdict holds wherever the destination is listed, and the read fold prunes each box's list against all of the account's marks. Which destinations a succession marks is [`succession-aftermath.md`](succession-aftermath.md) § Re-key scope → *Adjudicating what the aftermath carries across*'s to state.

**A rotated box keeps its list (built 2026-09-30).** A box that rotates its identity ([`../architecture/nest/box-recovery.md`](../architecture/nest/box-recovery.md) § Deployment-seed rotation) keeps its database and its registry, so the list follows it. A device that finds no list row under the identity it is bound to, while the account holds list rows under other identities, fetches the bound nest's rotation chain and **re-files**, under the bound identity, the row of the latest identity a verified chain links to it (`fauna_protocol::nest_rotation::verify_chain` — both signatures at every hop, so no box can claim another box's list as its ancestor's). With no verified link a row is another box's, and the first paragraph's rule holds. The predecessor's row stays where it is — the kind has no tombstone — and is never read again. **The residue, stated:** an edit some device made to the predecessor's row after another device re-filed is not carried. **The re-file rewrites a covered folder's `folder_name` (ruled 2026-10-01; built 2026-10-05).** A mirror set's name follows the box's current identity, so each covered-folder row the re-file carries has its `__folder/<predecessor-hex>/<folder-id>` rewritten under the bound identity in the same write — the name the source now answers `attach_folder` with and the one the destination holds once the seat has moved. What else a rotation owes the backup plane — the destination's writer grant and the mirror set's name at the destination, both keyed on the source nest's identity — is ruled there: an owner's device carries both on the same verified chain ([`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Cross-location backup protocol → *The writer seat*).

**A rebuilt box keeps its list too, and is nobody's source until it is seeded (ruled 2026-09-30; the pull's arm BUILT 2026-09-30, the plane-only cut it gated BUILT 2026-10-01 — § Implementation status today).** A box rebuilt from its deployment seed after a total loss ([`../architecture/nest/box-recovery.md`](../architecture/nest/box-recovery.md) § Mechanism → *Restore*) re-presents the identity its list is keyed on, and the devices that outlived it carry the row back with the rest of the account's fleet scope (that doc's § The plane-era recovery floor, *a bind completes the replica*). That is correct, not a gap: the list records the owner's intent — where this box backs them up — and losing the box changes nothing about it; the re-seed's post-ceremony duty re-enrolls the very row the list still holds (§ Third destination kind → *Re-seed* → *Where the ceremony runs*), and the `__config` rail's empty list after a rebuild was an accident of the blob dying with the box, never a rule. What the loss changes is the corpus: a rebuilt box holds none, and until the ceremony makes it whole it must not act as the corpus's source — a custodian pulling from it would read every held segment as dropped, a coordinator pushing from it would supersede every generation a nest destination holds. **The registry cannot tell the two apart, and neither the heal nor the orphan read tries.** An empty registry is what a total loss and a succession burn ([`succession-aftermath.md`](succession-aftermath.md) § Re-key scope, the backup-enrollment row) have in common, and the heal's job is the same in both — rebuild the projection from the list, the authority (§ Per-destination status read); the orphan read keeps its one meaning, a sealed store no listed row names (`fauna_core::data::custodian_store_is_orphaned`), so after a rebuild on the plane this device's own custodian row, not the orphaned row, is where its copy is offered back ([`../ui/backups.md`](../ui/backups.md) § Restore after losing the nest). **What does tell them apart is the corpus, and the party that knows is each copy.** A box's saved segment counter is its own word about how far its corpus reaches — served on every `fauna.segments.list`, pinned per device by the audit, carried in every custody ledger — and a rebuilt box's counter restarts at zero: the accepted source regression at its extreme ([`backup-restore.md`](backup-restore.md) § Background Tasks → *Implementation status (audit loop)*, the accepted-regression bullet owns the owner-side moment, its floor and its notice, and covers a nest-kind destination here as at any regression). For the copy that is the owner's only one the guard is the custodian pull's own: a pass whose source reports a counter below the ledger the store holds pulls nothing, tombstones nothing and checks in nothing — it records the regression and waits for the seed ([`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Client-device custodian (pull) → *The pull never tombstones against a source below its copy* owns the arm). Materialize floors the seeded box's counter to the delivered ledger's generation, which is what lets the next pass resume, and the post-ceremony re-enrollment stays the idempotent re-register it always was. **Refuted:** retiring the list row in the rebuild ceremony — no client-side act observes the rebuild before a device connects, the re-provision runs on an admin's device while the custodian may be another, and the ceremony's own post-duty wants the row; judging the orphan read against the registry — the registry is what the heal rebuilds on every read, so the read would flip the moment the heal ran, and it would offer a re-seed over a succeeded box that holds its corpus; a nest-answered "fresh database" flag — the box cannot tell a first provision from a rebuild (both are an injected seed on an empty disk), and its saved counter already says what the flag would, in the shape the audit pins and materialize floors; withholding the heal at a regressed box — a second guard, reachable only through a seam from the status read into the custodian store on every host, protecting nothing the pull's arm does not, while the projection the heal rebuilds is what lets the page state the custodian row honestly (never checked in) with the gesture on it. **The residue, stated:** the `__config` rail's safety argument — *no host is built, because the registry is empty* — is void on the plane the moment the heal runs, so the consumer cut cannot go plane-only before the pull's arm lands (§ Implementation status today, the per-source-box entry).

### Custodian contract — the kind axis (ratified 2026-08-02)

Every destination kind — the v1 peer nest, the ratified S3 kind (above), the client-device kind (below), and any future kind — answers the same four questions; a proposal that cannot answer all four is not a destination kind:

1. **Identity + credential shape.** How the destination is named and what authenticates writes and control. Nest: origin URL + 32-byte nest pubkey (federation channel for the writer plane; the owner's own USER-class connection for control). S3: endpoint + bucket + region + access key + sealed secret. Client device: the owner's own device identity (its stable sync `device_id`) — the first kind with **no address at all**, which is what forces question 2.
2. **Writer designation — who moves the bytes.** The rule: **the always-on party drives; a destination that cannot listen pulls.** Nest and S3 are **nest-driven push** (the source nest's coordinator writes — the slice-5 writer principle). A client device is **destination-driven pull** (the device dials its nest when awake — its existing posture; it can never accept inbound traffic reliably).
3. **Retention + liveness.** How held bytes stay alive and how they reclaim: custodian custody records + GC walk + grace window T (nest — `../architecture/segment-backup-protocol.md` § Cross-location backup protocol); object-store lifecycle (S3, its pass); local store with latest-per-path + a local grace window, bounded by the user-set cap (client device).
4. **Audit answerability.** The owner's clients must be able to verify the destination holds what it claims (`backup-restore.md` § Background Tasks); a kind that cannot answer the audit is not a backup kind. Nest: direct list+fetch+open (built). S3: list+fetch through the object API (the S3 pass's adapter). Client device: the custodian self-audits with the existing loop and its check-in feeds the nest projection (§ Third destination kind below — inclusion-sampling a sleeping device is structurally impossible, so the loud/quiet line moves to intermittency thresholds).

**Naming yourself — a custodian check-in that does not name its device is REFUSED (ratified 2026-08-05).** Question 1 identifies a client custodian by its device, and every one of the owner's devices authenticates as the same actor — so the check-in's `device_id` is the only thing that says *which* device is speaking. It is therefore required: a check-in omitting it (or sending it blank) is refused, not recorded.

This is a deliberate, bounded exemption from the additive-everywhere default (`../architecture/version-compatibility.md`), which would ordinarily accept an absent field so a client older than it keeps working. The exemption is granted because here that older client **cannot exist**, structurally and not just by dating:

- A client-device destination row cannot exist without a non-blank `custodian_device_id` — registration refuses one, so every custodian row already names a device.
- The check-in kind has never been *served* by any nest whose request type lacked `device_id`: the handler and the field landed in the same commit, the kind having been registered a day earlier with no handler behind it. A check-in omitting the field was refused as an unhandled kind then, and is refused as an unnamed device now — it has never once been recorded.

So no client that ever had a working check-in is refused by this, and the guard becomes **structural rather than advisory** — it binds every caller instead of only those that volunteer their identity.

**Why it is worth refusing at all, given the writer is the owner's own authenticated device.** The check-in is not an adversarial-writer surface (`../architecture/segment-backup-protocol.md` § Client-device custodian → *Check-in*), and a wrong one cannot reassign who pulls — `custodian_device_id` has a single writer, and the check-in is not it. What it can do is make the status row **lie durably**: an audit verdict is carried forward across the debounced passes that carry none (so a rotten store cannot appear to recover on a silent pass), which means one wrong `ok` outlives the enrolled device's `failed` indefinitely. The rot alarm is then silenced by the very mechanism built to keep it ringing. A guard against that must not be one the caller opts into.

### Third destination kind — client device as custodian (RATIFIED 2026-08-02; the re-seed ceremony built on tui and the desktop agent 2026-09-26 on linux, macOS and iOS 2026-09-29 and on windows 2026-09-30, the android lift owed; see § Implementation status today)

**Direction settled by the user 2026-07-24** (*"The Client can be an iPad with 2TB storage. Clients should be backup targets."*); this section ratifies the *how*. Implementation is a captured follow-on track (tracked internally); § Implementation status today owns what is built and what is still owed.

**Definition.** A **client custodian** is one of the owner's own devices holding a full sealed replica of the owner's backup corpus — the same sealed segments + `manifest.<kind>` mirror a nest destination holds — pulled from the owner's source nest and stored locally under a user-set capacity cap. One `BackupDestination` row per `(device, reserved-set kind)`, exactly the nest shape; `kind = "client-device"` per the discriminator above.

**Bytes move by PULL, nest-mediated.** Per the custodian contract (question 2): the device has no stable address, sits behind NAT, and is backgrounded by its OS most of the day — and the authoritative corpus already lives on the nest (a laptop's edits reach it as ordinary sync), so "client→nest→client" collapses to "nest → custodian". The nest is the always-on hub each intermittent device converges on at its own schedule — the read-side mirror of the slice-5 writer principle. Two topologies considered and rejected:

- **Push to the device** — needs inbound reachability + a standing listener on a phone, and fights the OS scheduler (opportunistic background execution tolerates pull, not push). iroh relay + STUN exist in-tree, but the peer data plane is dormant fleet-wide and p2p is ratified as a pure optional optimization layer, never a correctness dependency (`p2p.md`).
- **Client↔client as the custody topology** — a chained nest→A→B replication compounds staleness at each intermittent hop, adds a rendezvous problem (two intermittently-awake parties), and answers none of the custody questions differently. Transport is not custody. **Peer-assisted pull is deliberately reserved** as a future transport optimization: chunks are content-addressed, so a LAN peer that already holds a chunk is an equally valid byte source (verify-by-hash makes peers untrusted-by-construction) — the custody authority (what to hold, per the nest's manifests), the audit, and the status projection are unchanged by where bytes came from. That optimization rides the `fauna-transport` seam if/when the peer data plane lights up (owner: `p2p.md`); nothing here builds it, and the pull path stays chunk-granular + source-agnostic so it can slot in without custody rework.

**What it pulls, and the seal.** The custodian enumerates the owner's per-kind segment state over its own authed connection (the `fauna.segments.list`-class control plane), diffs against its local store, and fetches missing bytes over the canonical content-addressed byte plane. It derives the owner's seal keys locally from the identity seed it already holds (`BackupKey`; `NestBackupKey` per [`../ui/backups.md`](../ui/backups.md) § Encryption at rest's seal split — both seed-derived) and seals into the same convergent chunk format a nest destination stores: the deterministic convergent seal makes the custodian's locally-sealed artifacts **byte-identical** to nest-destination artifacts, so restore, audit sampling, and any future custodian-to-custodian comparison work uniformly with no per-kind artifact branch. No new key material, and **no `NestBackupKey` grant is needed for a pull-only custodian** — the grant exists to let a *nest* seal on the owner's behalf; this custodian seals for itself. Pull-plane mechanics + custody-record semantics: `../architecture/segment-backup-protocol.md` § Client-device custodian (pull).

**Enrollment — three steps, on the custodian device itself.** Most of the five-step nest sequence does not apply (no destination server: no `fauna.nest.info` read, no destination-side writer grant, no `NestBackupKey` grant). Enrollment is explicit per-device opt-in, run ON the device being enrolled (it is that device's storage, and the pull runs there): (1) the user opts the device in on its own Backups page and sets the capacity cap; (2) register the destination with the source nest's registry (`fauna.backup.destination.register` — kind + `custodian_device_id`; the same idempotent kind as the nest case), so the nest can project status; (3) append the `BackupDestination` row(s) to the source box's destination list via `mutate_backup` (§ Create / edit / remove protocol's *Write mode* paragraph) — the same single atomic decision point. A crash at any point leaves only an inert idempotent registry row; the local store is derived state, re-buildable from a fresh pull.

**Status projection inverts, same rows.** `fauna.backup.status` keeps one row per destination with the same shape; for a client custodian the semantics invert: *last synced* = the last time the device checked in having caught up; *backlog* = how far the nest's head is ahead of the device's acked high-water. The nest computes both from the custodian's **check-in** — a small USER-class write on the device's own connection after each pull pass (`fauna.backup.custodian.checkin`; wire owned by `../architecture/segment-backup-protocol.md` § Client-device custodian). Labels are i18n changes only; no row IDs change. A custodian at its capacity cap reports that state distinctly (cap-reached), never as an ordinary lag.

**Intermittency semantics.** A device asleep for a week is normal; a device gone for a month is a failure. The overdue threshold for a client custodian is a distinct, longer bucket-1 Rust constant (the client-custodian sibling of `AUDIT_OVERDUE`, landing beside it in `backup-restore.md` § Background Tasks) — never user-set; the capacity cap is the kind's only knob. The custodian **self-audits with the existing machinery**: it is itself a client running the audit loop, its own store makes inclusion sampling a local read, and its freshness comparison uses the same client-observed high-water — so a hostile source nest that withholds new segments from the custodian is detected exactly as the existing freshness audit detects withholding. What the owner's *other* devices can see about the custodian is bounded by its check-ins relayed through the nest (advisory — a device that cannot be dialed cannot be sampled); the loud surface for "this custodian is gone" is the overdue threshold on its check-in age.

**Durability + labeling.** A client custodian never silently satisfies "you have an off-site backup": its rows are labelled distinctly (`backup-destination-kind-badge`), and when **every** configured destination is a client device the page shows a standing warning (`backup-sole-client-destination-warning`) — an evictable, wipeable, OS-managed device is a materially weaker durability story than a nest, and the user must see that, not discover it. Platform storage reality, stated per family: iOS / Android app storage carries **no durability guarantee under pressure** (evictable; the store must tolerate partial eviction — content addressing re-converges automatically on the next pull); the sealed store must be **excluded from platform cloud backups** (iCloud / Google device backup — replicating a sealed store whose opening seed sits in the same vendor's cloud keychain is key-hygiene smear plus double-charged storage); desktop stores live under the sync-agent's per-user data dir (`../architecture/apps/sync-agent.md`). The pull coordinator, diff, seal, store layout, cap enforcement, check-in, and label logic are **shared Rust** (the same client-arm leaves the nest coordinator reuses, plus a local blob-store sink — see the segment-store section above); per-platform glue is only *where the store lives*, the eviction posture, and the background-scheduling hook — the same split the audit loop's `state_path` precedent set. **The exclusion seam has a second consumer since 2026-08-26**: the W3 (account-data-plane.md § Workstreams) account store states the same three-arm `CloudBackupExclusion` on every assembly (its writer key is restore-excluded on the phones, so its dir must be too — `../architecture/apps/common.md` § Credential storage → *the store dir follows the row* owns that ruling); the enum became owned rather than borrowed for it, the desktop posture moved from the sync agent into `CloudBackupExclusion::platform_desktop`, and the FFI projection (`FfiCloudBackupExclusion`, `FfiCloudBackupExcluder` — renamed from the custodian-specific name) lives in `fauna-ffi`'s always-on `cloud_backup` module. The mechanism and its three arms stay owned here.

**Threat model — the seal is owner-keyed and custodian-agnostic; self-custody is the special case.** "The destination can never read your backup" is a property of the seal, not of nests: it holds for any custodian not holding the owner's seed — including a **friend's client**, exactly as for held-for-friends nests. What is special about the motivating case (your own iPad) is only that the custodian is *also an owner device*, so it holds the seed and can derive the opening keys. Both consequences are ratified:

- **Standalone restore — the strongest argument for the kind.** A self-custodian can restore with no nest alive anywhere: open its local sealed store under seed-derived keys, or seed a fresh nest from its held chunks. No nest destination can do that. (Both capabilities are BUILT; the second is the *Re-seed* ceremony below, whose only owed piece is the in-flight marker; § Implementation status today.)
- **The exposure is bulk + retention, not a new capability.** A logged-in device can already read everything live; what the custodian adds is the *complete* corpus, offline, deliberately retained. At rest the store is ciphertext (the same sealed chunks a nest holds), and the keys are derivable from the seed in the platform secure store — so the protection reduces to platform device encryption + OS unlock gating the secure store, and the honest statement is: **a stolen custodian device that can be unlocked is a full-corpus compromise**, versus a partial one for an ordinary device. The Backups page says so at opt-in (glue copy, no new ID); device-session revocation does not reach already-exfiltrated offline bytes and the design does not pretend it does.

**Friend-client custodians — deferred, and not for crypto reasons.** The seal story is friend-ready by construction (above). Deferred because: a friend's *device* is an intermittent dependency the owner cannot manage (availability); it is the friend's own storage (capacity); and the pull needs a genuinely new grant surface — a scoped, revocable list+fetch capability letting a *foreign actor's device* enumerate and fetch the owner's backup artifacts, which the own-device case avoids entirely (the device already authenticates as the owner). If demand appears, that grant design is the whole work item; nothing in the discriminator forecloses it.

**Re-seed — the ceremony behind "seed a fresh nest from its held chunks" (RATIFIED 2026-08-22, design pass; refutable downstream; phase 2 BUILT for both planes (reserved segments 2026-08-22, covered folders 2026-08-29); phase 3 BUILT for both planes (segments 2026-08-29, covered folders 2026-08-30) — the shared driver that puts all three in order landed 2026-09-26, the desktop caller and the tui gesture the same day; § Implementation status today).** Three phases, driven from the custodian device; wire mechanics owner: [`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Client-device custodian (pull) → *Restore*.

1. **Enroll first — the authorization answer is that no pre-enrollment write surface exists.** To "what may a client write into a nest that holds no state for the actor?" the ratified answer is **nothing**: becoming known to a nest is exactly what onboarding's claim/admission transition exists for, that transition already carries the crash-recoverability story (`../architecture/nest/common.md` § Client-state recoverability), and the custodian holds the owner's seed, so it can complete any enrollment the owner could. A pre-enrollment bulk-write door would add a second, anonymous-write authorization surface to the review perimeter for no capability gained — the same reasoning that refused a bespoke handshake on the writer plane. Same-identity recovery composes *outside* this ceremony: re-provisioning the dead box's identity is [`../architecture/nest/box-recovery.md`](../architecture/nest/box-recovery.md)'s (the deployment seed rests in the account-state plane kind `fauna.state.deployment-seeds`); re-seed works identically onto a fresh-identity nest.
2. **Deliver into destination posture.** The custodian re-seals its held corpus under the owner's `NestBackupKey` root (both roots are seed-derived on the device; the local store's own `BackupKey` seal is client-only and never crosses to any nest) and pushes over the existing client-authed byte + custody surfaces, so the target becomes an **ordinary backup destination** for the owner — custody rows, hash-verified auditability, the grace window, quota charging (destination-derived; a corpus larger than the fresh nest's default quota surfaces the ordinary `storage_quota_exceeded`, raised in the admin app — honest, not a special case), device-pull exclusion. Crash-safe by construction: every tear leaves a valid destination, and the push resumes by content addressing.
3. **Materialize behind an explicit owner gesture.** One new USER-class verb (`fauna.backup.custody.materialize`) flips a custody set to live source posture under the ordinary enrollment-time `NestBackupKey` grant — segments: unseal + reconstitute + rebuild the mirror, blake3-anchored to the pushed `manifest.<kind>`; covered folders: key-free row re-homing. **Empty-target rule — the rule is FRESHNESS, and emptiness is only its most obvious half (widened 2026-08-31):** a scope or folder already holding live records refuses, typed, with no force arm — **and so does a folder holding no records at all that carries any publication-bearing property**: group-bound (`mls_group_id`), declassified public (`audience`), website-serving, WebDAV-exposed or paywalled. An empty folder is not a fresh one: its audience already exists, so re-homing into it publishes the restored corpus to a roster the owner never chose for it (per-folder read grants hand every member the corpus's metadata, and a writer member can tombstone what was just restored — destroying it). The two halves are one rule with two wire faces, `target_not_empty` and `target_not_fresh`, because their remedies differ — point at another nest, versus name another folder or clear the property — and neither has a force arm. The family of properties is enforced by an exhaustive destructure so a publication-bearing column added later cannot join it unchecked. Target freshness is per-scope and enforced at materialize, never a whole-nest precondition, and nothing in the ceremony deletes anything that holds or ever held content (*No user-data loss* holds structurally; the one thing it supersedes is a never-used target's mailbox scaffolding, *Where restored mail lands* below; merging into a lived-in account is a named non-goal). **"Seeded" means a live account**: the owner signs in and the nest serves the corpus as if it had always hosted it; derived planes rebuild. Honest bounds, stated: only what the custodian held arrives (the `BACKED_UP_KINDS` sweep — mail, calendar, contacts and posts, each kind with its placement journal, *Where restored mail lands* below — plus attached folders; cap-refused segments are absent); reserved file rails converge via ordinary fleet sync on re-enrollment; box-scope state (admin config, tenancy) is box-recovery's concern, not account data. **A re-homed folder row is writer-signed (ruled 2026-09-30; part-built 2026-10-02):** the ceremony's seed-holding process creates each covered folder's target set through the shared create helper before phase 3, the delivery leg signs each row's statement, the request carries the signatures in pages, and the nest mints only what verifies — the ruling, the pseudo-device the rows carry and the refusals are [`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, ruling (7)(a), whose § Implementation status today carries what is built.

**An interrupted flip completes on retry, whatever arrived since — the in-flight marker (RULED 2026-09-29, design pass; refutable downstream; NOT BUILT — [`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Implementation status today).** The empty-target rule is judged **once, at the gesture**. Before materialize's first write that anything else could observe, it records the gesture durably beside the target's state — the set, the segment ids it is about to flip, and which journal shape the copy holds — and that record leaves in the one transaction that makes the corpus live. While it stands the target is *mid-flip*, not lived-in: a retry asks no freshness question (the marker already answered it), and everything live that the marker's ids do not name is **post-gesture activity** — mail that arrived while the flip was interrupted, and whatever the owner did with it — which the retry keeps, never refuses and never deletes. The window is real, not theoretical: the verb runs under the dispatcher's deadline and abort, so a large corpus can be torn mid-flip with the nest still serving, and a nest can die at any write. Three rules make the keep exact. **(1) The id space is partitioned first:** the content counter is floored to the corpus's ledger generation before any half is written, so an arrival's segment can never take, or reclaim, an id the corpus needs — which also closes the write-window race the verb had declined. **(2) The containers land before the halves:** for a journaled mail copy the corpus's mailbox tree (names, UIDVALIDITY, UIDNEXT, HIGHESTMODSEQ) is written to the target's mailbox state right after the marker, so every arrival from the gesture on mints its UID from the tree it will end in — above the corpus's UIDs, under the corpus's validity. **(3) The corpus's journal supersedes the target's, and post-gesture placements are re-filed into it** by mailbox name under the UID they already hold, flags and dates kept, a mailbox created where the corpus lacks one; the target's container-only scaffolding goes, as consequence (2) below already rules. Rows the ceremony did not write but the marker explains are re-stated from the journal in the same transaction, which is why that transaction may replace the placement tables wholesale and still loses nothing. What the marker is **not**: it is no force arm (a target without one is judged by the ordinary rule, and nothing but this verb writes one); it never expires (the gesture was given, the retry completes it however late, and the account's activity in between is kept); and it is no boot task — the nest never finishes a flip on its own, because the completing call's reply is what lets the driving app run its post-ceremony duty, so a nest restart mid-flip is one more interruption the owner's retry completes. **Declined:** holding the arrival doors while a flip runs (a durable hold would hold mail delivery hostage to a gesture the owner may never repeat; an in-process one closes nothing across a nest crash or the verb's own deadline abort), and handing the stranded case to the recovery verb (it re-appends the corpus's records under fresh ids and leaves the adopted, never-served segments as dead weight on disk). **Calendar and contacts** get the marker and the floor, and until their re-filing arm lands they still refuse a post-gesture arrival in their own journals — rare in practice: a DAV client is configured against a nest after it is seeded, while MX already points mail at it.

**Where restored mail lands (ruled 2026-09-26, design pass; refutable downstream; BUILT 2026-09-27 in shared Rust and the nest, tier_3-proven; the after-loss journey ran green end to end against it on linux and tui 2026-09-29 — § Implementation status today).** A materialized mail record lands **where it was**: in the mailbox it was filed in, under the UID it had, with its flags and modseq, in a mailbox tree that carries the source's UIDVALIDITY. One sentence makes that possible: **a backed-up message kind's corpus is its content segments *and* its placement journal**. It is the same pair a message-kind snapshot pins ([`../architecture/message-segment-store.md`](../architecture/message-segment-store.md) § Restore dispatch on message_kind), for the same reason: a content record holds only what its id determines, and everything mutable about it lives in the journal (that doc's invariant 2). The journal is therefore not a kind of its own on the backup plane. It is the kind's other half: it rides the kind's own set (`__mail`), both arms sweep it in the kind's own pass, and one `materialize` call flips both halves in one transaction, so no crash leaves mail live and unfiled. Paths, the serve plane and the verb's order are owned by [`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Client-device custodian (pull) → *Restore* → *The placement journal rides the set*. This section owns three consequences. **(1) The empty-target rule gains the journal's half, and it is once more freshness rather than emptiness.** A target whose journal has ever placed a message refuses `target_not_empty`, even when every one of those messages has since been expunged. A box that held mail and was emptied still carries tombstones and spent UIDs, and folding a backup over them would hand a mail client a vanished notice for a UID the restore had just made live. **(2) A never-used target's mailbox scaffolding is superseded, and that is the ceremony's one replacement.** A target that never placed a message may still hold mailbox-level state: the six standard mailboxes every account gets on first touch, a folder a mail client created when it connected, a subscription. The corpus's mailbox tree replaces it. Merging two trees has no correct answer for UIDVALIDITY, the state describes containers that never held anything, and the owner recreates an empty folder in seconds. What the ceremony never touches is anything that holds or ever held content. **(3) A copy that holds content and no journal is a delivery that has not finished, and refuses as one (`custody_incomplete`).** Every mail corpus since this ruling carries its journal, so a copy without one is a pass still under way; restoring it would leave mail live and in no mailbox, and a journal arriving later could never be adopted over a lived-in account. (Until the compat-remnant contraction of 2026-09-30 such a copy — filled by a source older than this ruling — was filed into the inbox instead; no such copy exists under the sweep's premise, so the filing and its `inboxed` count were removed.) **Calendar and contacts follow the same ruling over their own journals once they join the sweep (their nest-side arms are built — [`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Implementation status today).** An event or card lands in the calendar or addressbook it was in, under its ETag and change number. The freshness half counts placed items, removed ones and every change number a container has handed out past its first, so a lazily provisioned Personal calendar is scaffolding and a calendar that once held events is not; a CalDAV or CardDAV client's sync token is the UID's counterpart. Consequence (3) holds for them the same way, where restoring the content alone would leave events live in no calendar. Posts have no placement layer. **Refuted: a default placement as the primary leg.** Filing every restored record into the inbox, or into a dedicated "Restored" mailbox, loses exactly the state invariant 2 assigns the journal: which mailbox, which flags, which UIDs. The owner cannot recreate that for ten thousand messages, and this is the one recovery path left once the nest is gone. It also cannot be built first and replaced later, because a journal arriving over guessed placements is a merge into a lived-in account.

The interim state is the uniformity payoff: after phase 2 the target is indistinguishable from a nest-kind destination's corpus, so **materialization is one shared design for both restore sources** — a surviving nest destination's custody materializes with the same verb, its delivery leg being the **nest-held pull-back** rather than the custodian's push (ratified 2026-09-26: the owner's app — the one party that still knows where the copy is and is authenticated on both sides — pulls the surviving destination's custody off its `custody.list` and open blob routes and lands it on the target **as-is** over the very surfaces the custodian's push uses; no new door, no key material; the mechanics, the refuted join-and-pull outline and the reserved server-to-server transport: [`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Client-device custodian (pull) → *Restore* → *The nest-held pull-back*). It is **not a slice-5 revival**: the retired writer was the steady-state backup driver; this is a bounded recovery ceremony whose end state hands the pen straight back to the nest arm (the fresh nest's coordinator writes; the custodian resumes pulling; a surviving nest destination is re-enrolled on the target by the ordinary § Create sequence — the registry row it lived in died with the box — as the driver's post-ceremony duty). UI: the affordance is the Backups page's re-seed gesture, on the custodian's row and on the orphaned-store row; its five ids were user-approved 2026-09-26 and [`../ui/backups.md`](../ui/backups.md) § Restore after losing the nest owns the page.

**Where the ceremony runs, and what it leaves behind (ruled 2026-09-26).** The ceremony runs in the process that owns the custodian store: on mobile the app itself, which is the host there; on a desktop the per-user sync agent, reached through one confirm-gated local IPC verb, `ReseedCustodianStore`. The app is only the gesture's caller. That keeps the store's single writer: the agent stops its own custodian stint first, exactly as a reclaim does. The seed-holding app derives the `NestBackupKey` and hands it over for that call only ([`../architecture/owner-key-material.md`](../architecture/owner-key-material.md) § Path A-sibling-0 owns that custody ruling). The shared driver runs all three phases there over the agent's own authenticated connection, which after a same-identity rebuild is already the rebuilt nest's, and replies with the driver's outcome. **The driver's post-ceremony duty belongs to the caller, and it runs only once the whole corpus is live** (`ReseedOutcome::is_whole`): the custodian device re-registers itself on the target through the ordinary three-step custodian enrollment, so the custodian resumes pulling, and it does so only then because a pull against a target that does not yet serve the whole corpus cannot resume: a set the ceremony did not flip keeps a counter below the copy's ledger, which the pull's regression arm refuses ([`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Client-device custodian (pull) → *The pull never tombstones against a source below its copy*), and before that arm the pass read the missing part as gone. A surviving nest destination the corpus was pulled back from is re-enrolled by the § Create sequence after its pull-back (`fauna_client_config::reenroll_nest_destination_after_reseed`), whose writer-grant step takes the destination's seat over from the box the restored nest replaced ([`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Cross-location backup protocol → *The writer seat*). A result with a hole re-enrolls nothing, and the owner re-runs the gesture, which resumes by content address.

### Ordinary-folder coverage — destination places (ratified 2026-08-19, the per-folder attachment design pass; refutable downstream)

**Direction from the folders re-model ([`folders.md`](folders.md) § Target re-model → places): a folder's places include destination places — "blind sealed custody, today's backup destinations". This section ratifies the *how*: what it means to attach a backup destination to an ordinary folder.** It answers § Custodian contract's four questions for the attachment axis **once, kind-agnostically** — the answer covers the nest kind, the client-device kind, and the deferred S3 kind alike, rather than being restated per kind. This section is BUILT as of 2026-08-20 (one slice, tui leading the UI); § Implementation status today enumerates every piece and what remains.

**The two-level shape: enrollment stays per-actor; coverage becomes per-folder.**

- **Enrollment** (the trust relationship — identity resolve, grants, registry row, capacity cap, status row) is unchanged: per `(owner, destination)`, minted once by the existing sequences (§ Create for nests; § Third destination kind → *Enrollment* for custodian devices; the S3 pass for S3).
- **Coverage** is which corpora that destination holds. The reserved account rails (`__mail`, `__conv/<channel>`, …) stay **whole-account and implicit**, exactly as today — they are account data, not user folders, and a per-rail detach affordance would let a user silently un-back-up their mail while thinking they are managing folders. An **ordinary folder is covered per-folder, opt-in**: attaching an enrolled destination to a folder gives that folder a **destination place**; a fresh enrollment covers no ordinary folders. Opt-in is deliberate: ordinary folders can be very large (a media library), auto-covering everything on enroll would surprise on the destination's quota or cap, and the per-place model's whole point is that behavior is chosen per place.
- **Only the folder's owner attaches destinations, and only for folders with a row on the owner's own nest** (`FolderRef::Local`). Places are owner-plane state. A *member's* replica of a shared folder rides its sync seats and a *follower's* rides the public plane — a member or follower who wants offsite custody of someone else's folder is a named non-goal (it would need the foreign-actor list+fetch grant surface § Third destination kind → *Friend-client custodians* already defers).

**Custody unit — the folder's existing sealed chunk+manifest corpus, mirrored latest-per-path. NOT segments.** Segments exist to package many small DB records (the reserved rails); an ordinary folder is already a content-addressed file corpus, sealed at rest per its audience (owner `BackupKey`, the shared content key, or deliberately plaintext for `public`). The destination holds **the same bytes the source nest holds** — the live head's manifests + chunks, copied as-is:

- **No re-seal and no new key material.** The pushed bytes are already at-rest ciphertext, so the destination is blind for `private`/`shared` folders by construction, and this plane needs **no `NestBackupKey`** — that grant exists to let a nest *seal* on the owner's behalf, and nothing here seals. A `public` folder's custody is plaintext, and that is correct rather than a gap: the audience contract makes its content + names world-readable, so its offsite copy discloses nothing the flip did not — do not "fix" it.
- **Destination-side home: the owner's reserved set `__folder/<source-nest-id-hex>/<folder-id>`** (a **custody copy** — `folders.custody_copy`, [`reserved-folders.md`](reserved-folders.md) § Destination capability; written only by the two nest-side provisioners), one per covered source folder — the `__conv/<hex>` family precedent. The name embeds the **source nest's 32-byte id** because `folders.id` is per-nest (an owner with linked source nests can hold the same numeric id on both, and two corpora interleaving in one custody set would corrupt latest-per-path reclamation), and it uses the stable `folder_id` rather than the folder name so a rename never re-homes custody (the pinning rule the publicly-synced follow established). Because `is_reserved_folder_name` is `starts_with("__")`, **every reserved-rail custody behavior applies structurally, with no new code class**: custody routing (`is_reserved_backup_set`), device-pull exclusion (write-only custody, never materialized on a member device), the structural snapshot refusal on the destination, latest-per-path reclamation with the grace window T, and per-actor storage-quota charging.
- **The write is the ratified handshake, unchanged** (§ Destination-removal / supersede handshake): per-path custody records via the standard `fauna.sync.changes.record` path, omission-safe; supersede = a new manifest for the path; compacted-out = a path delete; detach = the destination-side set drops and its chunks reclaim. Audience flips need no special machinery: the declassify/re-seal passes re-record paths on the source, the next coverage pass mirrors the re-recorded corpus, and the prior generation rests under the grace window.

**Writer designation per kind (§ Custodian contract question 2) — unchanged, stated once for the axis:** `nest` (and the future `s3`) are **nest-driven push** — the source nest already holds the folder's sealed bytes and its head; its coordinator's sweep widens from `destination × BACKED_UP_KINDS` to `destination × (reserved kinds + that destination's covered folders)`; the S3 pass maps the same custody unit onto object keys. `client-device` is **destination-driven pull** — the custodian's pass pulls the covered folders' manifests + chunks **as-is** into the same local content-addressed store; for this plane there is no local seal step (the bytes arrive sealed), which makes the byte-identity property trivially structural.

**Retention + audit (questions 3 + 4).** The destination holds the **live head only**, plus the grace window's retained superseded generations — it is not a snapshot archive. Snapshots remain the *nest place's* derived plane ([`backup-restore.md`](backup-restore.md) § 8b), the two planes never read each other's knobs, and the destination-side `__folder/…` set is refused snapshots structurally like every reserved set. Destination-held snapshot history is a **named v1 non-goal**; if demand appears it is a per-destination-place policy — a sibling of § 8b's knobs — and its own pass. Audit: the floor for this plane is **hash-verified presence** (content addressing makes present-and-hash-matched exactly the integrity property custody protects); a custodian holding the opening keys (an owner device auditing an owner-sealed folder) may additionally run the full open as the reserved-rail self-audit does, but openability is not required where the auditor legitimately lacks keys (a shared folder's content key it was never granted) — and a hash mismatch or an unproducible live path is a **failure, never a skipped sample**. ⚠ **Which plane a sampled row belongs to is decided by the CLIENT, from its own attachment record — never from the reply being audited** (ratified 2026-08-21). The two arms are not equally strong: presence is rooted in the `manifest_hash` the destination itself supplied and is therefore self-consistent by construction, while the open runs under a key the destination has never held. So which arm scores a row is never read off the audited reply's own `CustodyItem.folder_name` — the party being audited must not choose the test it is graded by. The routing input is the set of `__folder/…` names **this client attached to this destination** (`fauna_client_backup::audit::attached_mirror_sets` over its pinned destination list, each name having arrived in an `attach_folder` reply from the owner's own nest); a `__folder/…` row the client never attached takes the full open and fails it. The derivation filters by shape rather than returning every `folder_name` for the destination, because coverage rows share the destination's `destination_id` and its reserved `__mail` sits in the same list — including it would route the one plane that *can* be opened to presence instead, weakening the same guarantee from the client's own side. **The population this plane's audit samples from is the attaching client's own replica index of the folder, never the destination's list alone (2026-09-28).** Mirror rows are the folder's own ciphertext copied with no re-seal, so nothing owner-sealed at the destination names them: the reserved rails' ledger anchor ([`backup-restore.md`](backup-restore.md) § Background Tasks → *Implementation status (audit loop)*) has no counterpart here, and presence over the destination's own list passed a destination that dropped part of a covered folder *and de-listed it*. What the destination cannot shrink is what the attaching client holds itself — its synced replica of the folder (the set's `fsid-<ref>.db`), whose live heads are the very `(hex(path_hash), manifest_hash)` pairs the coordinator writes each mirror row under, and which, like the freshness arm's observed high-water, is the client's own eyes: nothing the source or the destination says afterwards retracts it (a live `fauna.sync.files` read is not an anchor for the same reason it is not a freshness input — it is the source's word at audit time, and a source outage would then decide a *destination's* verdict). The rule (`fauna_client_backup::audit::reconcile_with_folder_indexes` — the ledger rule one plane over, feeding the same certain-miss and retained-row tallies): every head the replica names must be custody at the destination — **live** under that path with that manifest, or **retained** as a generation of that path with that manifest (the head was superseded since; the older bytes rest in the grace window and are sampled like a live row's) — unless the source recorded the head, or the folder was attached, less than `FRESHNESS_SLACK` ago (the coordinator's sweep may not have run: the same slack and the same `added_at` floor freshness grants the reserved rails, so a lagging mirror is this plane's freshness failure and a just-attached library is not); anything else — de-listed, substituted under a manifest the client never recorded, or lagging past the slack — is missing with certainty, caught at 100 % rather than 81 %. The replica witnesses only while it was itself known consistent with the source inside that same slack (a completed transfer or a clean pull pass — the sync engine's `last_sync` stamp): a device asleep for weeks may name heads superseded so long ago that the destination legitimately no longer retains them, and it falls back to the list for that set rather than alarm on its own staleness (`T` ≫ the slack makes a fresh replica unable to name a legitimately dropped head). The shell hands the replica in through the seam's one platform-shaped method (`BackupInclusionSource::folder_index`, backed by `fauna_sync_engine::segment_backup::ReplicaFolderIndex` over the device's sync state dir and bound source nest); a set the client never attached is never looked up. **Declared residuals — each a `None` from the shell, under which that set keeps hash-verified presence over the destination's list:** **web**, whose SPA holds no persistent replica of any folder (its listing is the live read above) — the audit's one declared platform absence, permanent by construction; a native device with **no seat** on the folder; a set of a **linked source nest** other than the one this device is bound to (the same numeric `folders.id` can exist on both, and `FolderRef::Local` names a row on the bound nest); and a replica **not consistent inside the slack**. A rejected alternative, so it is not re-derived: the source nest sealing a per-folder ledger into the mirror set — the reserved rails' shape verbatim, uniform across all 7 apps — would put a `NestBackupKey` seal into the one plane ratified to need none, and a source that stopped mirroring would keep its old ledger valid for ever, which is exactly the lag only the client's own replica can see.

**Coverage state + wire shape — the destination verbs own the write; `fauna.folders.places.set` stays device-only.** The nest drives the push and cannot read the sealed config, so authoritative coverage lives nest-side beside the registry: one row per `(owner, destination_id, folder_id)` (additive; a coverage table vs. a registry extension is the build's choice). The mutation is a new idempotent USER-class pair **`fauna.backup.destination.attach_folder` / `.detach_folder`** — deliberately NOT a widened `PlacesSetRequest`: that request is device-shaped (`device_id` + `PlaceFlags`, both required and both meaningless for a destination), so widening it would mean two mutually-exclusive address fields and one verb writing two tables under two auth flows; the one-owner rule applies to verbs as to claims — the folders plane owns device seats, the backup plane owns custody coverage. The folders page still *renders* destination places: the read may join coverage onto `FolderSummary` additively or take it from `fauna.backup.destination.list` (which gains each destination's covered folders — each with the folder's display name since 2026-09-29, the label a re-seed restores it under; `../architecture/segment-backup-protocol.md` § Client-device custodian (pull) → *Restore* → *Where a restored folder's name comes from*) — the build picks, additively. Client-side, coverage rides the **existing ratified row model** (§ Destination data model — one row per `(destination, rail)`): attach writes one more destination-list row for the same destination with `folder_name = "__folder/<source-nest-id-hex>/<folder-id>"` and, since 2026-10-06, the folder's display name and sealed label off the same listing (`folder_display_name`, `folder_label`; a re-attach refreshes them, an absent one erases nothing) — after a box loss the one place a nest-held folder's label survives, which the nest-held pull-back names the restored folder from; detach removes it; destination-remove drops all of the destination's rows exactly as today. The row model's latent per-rail dimension gets its first second value rather than a new list shape. (Today's enrollment writes the one `__mail` row and the sweep is the hard-coded `BACKED_UP_KINDS` — the reserved rails stay constant-swept even after coverage rows exist; a coverage row never gates them.)

**Anti-phantom clause.** The deleted `folder_destinations` table (v42) failed because it had a writer no app ever called and readers that always saw an empty list. This plane therefore lands as **one slice spanning the app gesture, the nest coverage row, the push/pull consumer, and a tier_3 proof** — the § Destination-removal handshake's "do not implement one without the other" rule applied at feature level. The attach/detach affordance needs net-new ui.yaml IDs (rule A — user approval at build time); nothing here pre-mints them.

### Create / edit / remove protocol (ratified)

There is **no destination CRUD WS-RPC kind** — a destination is a row of the source box's list in the account-plane kind `fauna.state.backup` (the row grammar and merge rule: [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule, the kinds table's row), so its create/edit/remove is a write through the account store's door, composed by the one shared mutation door `fauna_client_config::mutate_backup` over the helpers in `libs/fauna-client-config/src/mutate.rs` (`add_backup_destination` / `edit_backup_destination` / `remove_backup_destination` — one shared-Rust home, seven app consumers — priority #2). Create and remove additionally sequence the nest-side-backup RPCs below (own kinds) before that list write — see `libs/fauna-client-config/src/backup_enroll.rs`'s module docs for the full ordering + crash-safety proof.

**Write mode: one door, marks before the list (the plane's replacement for the 2026-08-11 CAS ruling).** Every writer on this plane — enroll, edit, remove, the folder attach/detach and the third-kind custodian enroll — goes through `fauna_client_config::mutate_backup`: it reads the box's state, applies the gesture, refuses a list over the row's size bound with the one localized refusal before anything is written, then puts the marks the gesture moved and only then the list. The list stays whole-record latest-wins, and a concurrent device's destination-removal verdict (the destination-mark adjudication plane — owned by [`succession-aftermath.md`](succession-aftermath.md) § Adjudicating what the aftermath carries across) rides its own mark row, which the read fold prunes the list against — so no writer can resurrect an adjudicated-away row, whichever list wins, and no CAS base is needed.

**Create (enroll) — `fauna_client_config::enroll_backup_destination`, the atomic decision point is the list write.** On `backup-destination-add-confirm-button`:
1. Resolve identity + verify reachability/authorization: connect to `destination_nest_url` as the owner's **stable cross-nest actor** (the same Ed25519 identity; works today for any nest the owner administers) — native `NestClient::connect` performs `fauna.auth.handshake` directly and keeps the session open; wasm anonymously handshakes then reconnects with the minted bearer — then take the destination's `nest_id` (the 32-byte `destination_actor_pubkey`) as **the identity that connection is bound to**: native, the host's pin (graduated by the login's SPKI compare) else a possession proof over the connection; web, the possession proof the handshake signature binds, pin-checked for the origin (a browser exposes no received cert — web's structural ceiling, [`../architecture/security.md`](../architecture/security.md) § Transport trust). `fauna.nest.info` supplies only the domain (the `display_name` default) plus a claim that must **agree** with the proven id — a disagreement refuses the enroll (`fauna_client_backup::trust::proven_destination_id`, shared by both resolvers) — so the recorded id is never a claim, which whoever answers the URL with valid TLS could set to anything. A failure here surfaces as a dialog error — the destination is not recorded.

   **Every later connection to the destination is held to that id.** The trust facet's writer rows and writer revoke, the recovery surface's generation list and restore, and the audit all open a destination through the one shared door `fauna_client_backup::trust::connect_destination`, which refuses any connection whose proven identity (the same pin-else-possession read, per platform) is not the enrolled `destination_actor_pubkey` — so a box answering a lapsed or hijacked destination URL is never taken for the destination: no forged writer-grant or generation view, no revoke swallowed by an impostor. A destination that genuinely changed identity is a different nest (the *Edit* rule below: remove + re-add).
2. Grant the source nest this owner's seed-derived `NestBackupKey` (`fauna.backup.nest_key.grant`) so its in-process coordinator can seal this owner's segments.
3. Register the revocable nest-writer grant **at the destination** (`fauna.backup.writer_grant.register`, over the destination's own authenticated connection from step 1 — never the federation channel, so revocation stays operable with the source nest fully hostile). **The writer it names is the source nest's connection-bound id** — the login's pin for the source origin, else a possession proof over the connection, refused when the nest's own `fauna.nest.info` claim disagrees (`fauna_client_pair::LinkedNestsMachine::bound_nest_id` and its native / FFI / wasm callers) — **never that claim**: the destination's writer gate keys on the handshake-verified `origin_nest_id`, so a grant keyed on a claim authorizes whichever nest the claim names. The same bound id keys every writer-grant row and writer revoke the Nests-page trust facet shows ([`../ui/nests.md`](../ui/nests.md) § Trust facet — backup rows), where a lying source is **not** refused: the revoke is the affordance a hostile source is revoked by, so its claim is simply never read. **A destination already holding this owner's backup from another box refuses the grant** (`fauna.backup.writer_seat_held`, naming the box that holds it; ruled 2026-10-01, built at the destination the same day): the create stops here with that reason in the add flow's error and records nothing, as on any refused grant. The rule and the one handover that moves a seat are `segment-backup-protocol.md` § Cross-location backup protocol → *The writer seat*'s.
4. Register the destination **with the source nest's own registry** (`fauna.backup.destination.register` — § State & data shape → *Source-side destination registration*), so the nest-side coordinator has a source of truth for where to back this owner up.
5. Append the `BackupDestination` row(s) to the source box's list via `mutate_backup` (see the *Write mode* paragraph above). **This single list write is the atomic decision point.** Steps 2–4 are each individually idempotent and inert without it — a crash before the list write leaves nothing but inert nest-side grants/registrations to clean up (self-healing on the next add), and a crash after it self-heals on the next coordinator pass. Enrollment writes no client-unrecoverable state on the destination — the destination-side reserved folder is provisioned **lazily by the coordinator** (next bullet), idempotently.

**Coordinator-driven destination provisioning — NEST-RUN for a `nest`-kind destination since the slice-5 flip (COMPLETE across all apps 2026-08-16).** No client is alive for this pass any more: the source nest's own in-process `NestBackupCoordinator` (`bins/fauna-nest/src/segment_backup.rs`) sweeps every enrolled owner × configured destination × `(kind, scope)` on its own periodic cadence, uploading new/grown segments (chunk + zstd + ChaCha20-Poly1305, sealed under the owner's `NestBackupKey`) and the `manifest.<kind>` mirror over the nest-writer grant, then records custody through the federation originator (**records each uploaded segment + the mirror as a path on the destination** — next section — the custodian's per-path liveness record, so the destination's GC keeps the backup). It needs no explicit `fauna.folders.create`/`members.add` step of its own — the destination's federation handler resolves-or-creates the owner's reserved custody-copy set (`custody_copy` — `reserved-folders.md` § Destination capability; minted with the flag set) lazily behind its grant gate. Full mechanism + build ledger: [`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Cross-location backup protocol. The retired **client**-driven coordinator (the `fauna.folders.create`/`members.add` provisioning this paragraph described pre-flip) was **deleted 2026-08-17**; `libs/fauna-sync-engine/src/segment_backup.rs` keeps only the shared leaves (`diff_segments`, `hash_segments_canonical`, `LiveManifestMirror`; the seal pipeline lives in `seal.rs`) plus the enroll-time `resolve_destination[_connected]` free fns; the **client-device custodian** kind's pull pass (§ Third destination kind) is a distinct, still-client-driven mechanism unaffected by this flip. Provisioning is idempotent and retried each pass, so a transiently-unreachable destination converges without stranding state.

**Edit.** `backup-destination-edit-button` reopens the dialog; the user changes `display_name` and/or `destination_nest_url`, then writes the edited row through `mutate_backup` (the same *Write mode* rule as Create/Remove above). If the re-resolved `nest_id` — proven over the new URL's connection exactly as Create step 1 proves it, never read from `fauna.nest.info` — still matches `destination_actor_pubkey`, it is the same nest (e.g. moved) and the coordinator continues. If it differs, the dialog treats it as a different nest and requires remove + re-add (warned inline).

**Remove — `fauna_client_config::deregister_backup_destination`; the coordinator reconciles the rest.** `backup-destination-remove-button` → `backup-destination-remove-confirm-modal` → on confirm: (1) deregister from the **source** nest's own registry (`fauna.backup.destination.remove` — the twin of create step 4; idempotent, so a refused call aborts the whole remove and leaves the list row in place, mirroring create's grant-refusal contract), then (2) drop the row(s) from the source box's destination list via `mutate_backup` (the *Write mode* paragraph above; the prune that keeps an adjudicated-away destination from resurrecting rides the mark rows it writes first) — the atomic decision point. **No synchronous *destination* call** (the destination-side nest-writer grant is not revoked here — a distinct trust-facet action). On its next pass the coordinator reconciles its local upload state against the live destination list and **tears the departed destination's custody down before forgetting it locally**, so that destination's GC reclaims the offsite chunks — the mechanism (which arm runs, over which channel, and why the nest arm's reclaim is one grace window behind the client arm's) is owned by [`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Cross-location backup protocol → *Supersede / remove handshake*. This makes removal a single atomic decision point + loop-reconcile (the crash-safety pattern in `nest/common.md` § Client-state recoverability): a crash mid-removal, or a destination offline at removal time, simply retries on a later pass — no client-unrecoverable state, no SSH/manual cleanup. A removed **client-device** destination has no coordinator pass to wait for: its custodian learns of the removal at its next check-in, which the nest refuses as not assigned, and stops its replica then (the wire: [`../architecture/segment-backup-protocol.md`](../architecture/segment-backup-protocol.md) § Client-device custodian (pull) → *Check-in*; the desktop host's reaction: [`../architecture/apps/sync-agent.md`](../architecture/apps/sync-agent.md) § A7).

### Destination-removal / supersede handshake — custodian-authoritative custody (corrected 2026-06-15)

The nest's § 9 GC (`docs/goal/behavior/backup-restore.md`) builds its blob reference set from `snapshot_files` + live `sync_changes` only, and runs on **every** node — so on a destination nest, a segment-backup blob (chunk or `manifest.<kind>` mirror) is referenced by nothing GC sees and is **deleted one cycle past grace = loss of a live backup**. The full nest-side design and rationale (incl. why the 2026-06-14 single-manifest "ledger" was withdrawn) is the owner section `docs/goal/architecture/segment-backup-protocol.md` § Cross-location backup protocol → *GC-safety — custodian-authoritative custody*; the gap is `docs/goal/behavior/backup-restore.md` § Known gap: segment-backup blobs vs GC. In one line: **GC-safety belongs to the custodian holding the bytes, derived per-path from what it received — not declared by the client.**

- **A backup is a file-sync to the custodian.** The coordinator uploads each segment + the `manifest.<kind>` mirror as files and **records each path's current manifest** on the destination via the standard `fauna.sync.changes.record` → `sync_changes` path (`upload_bytes` skips this today; that skip is a *source-nest* concern only). The custodian accumulates the per-path records into its own authoritative live set, which its GC walks (latest non-deleted manifest per `(folder, path)` across custody-copy reserved sets). `uploader_actor` is the authenticated bearer, never the wire.
- **Omission-safe.** A path the client doesn't re-mention stays live — the custodian never reclaims a backup path's chunks because a client failed to re-declare it. (This is the crux distinction from a client-declared *full-set* ledger, where omission silently deletes — unsafe across 6 first-party + third-party clients.)
- **Supersede** — a grown/re-uploaded segment is a new manifest for the same path → the prior manifest's now-exclusive chunks become GC-eligible. **Compacted-out segment** — a `delete` for that path → its chunks reclaim. **Destination removal** — the removal-reconcile above drops the reserved backup folder (or records deletes for its paths) → all chunks reclaim.
- **No bespoke wire kinds.** There is **no** `register_manifest` / `deregister_manifest` and **no** client-declared manifest set — the wire is the standard chunk + manifest + per-path `sync.changes.record`, so a third-party client implements only that. The custodian (nest = first implementor) adds two custody behaviors: it **excludes custody-copy sets from device-pull** (write-only custody, never materialized on a device) and **reclaims latest-per-path** (so superseded/removed segments' chunks free).

This is the **load-bearing shared design** between this UI and the nest-side backup work; the client's record-on-upload + delete-on-removal land **with** the nest's backup-custody record + GC walk (do not implement one without the other). Proof obligation (Track B): a **tier_3** test — upload N (≥2) segments to a destination → run GC → assert all segments' chunks + manifests survive; supersede one + compact one out → run GC → assert only the now-orphaned chunks reclaim; remove the destination → run GC → assert all reclaim. **Status 2026-06-15:** **both halves landed + tier_3-proven.** The **nest custodian half** — the custody record (a custody copy → `backup_custody`), device-pull exclusion, GC walk, and `delete_folder_for_user` dropping a backup set's custody (so `fauna.folders.delete` is the GC-safe removal) — through the real `fauna.sync.changes.record` handler + real GC (`bins/fauna-nest/tests/segment_backup_gc_safety.rs`). The **writer half** — record-on-upload + delete-on-compacted-out + the automatic removal-reconcile — was originally the client coordinator's, proven by `segment_backup_client_gc_safety.rs`; **since the slice-5 flip it is the nest arm's**, proven with no client alive by `bins/fauna-nest/tests/nest_backup_coordinator.rs`, and the client coordinator + its test were **deleted 2026-08-17** (dead-code-only coverage loss — the destination-side proofs above never depended on them). **The data-loss gap is closed.**

### Scheduling (ratified)

**One global coordinator cadence, not per-destination.** `BackupDestination` carries no schedule field; every runner sweeps all its `(destination, kind, scope)` tuples each pass on the one shared 15-min `PERIODIC_INTERVAL` (`backup-restore.md` § Background Tasks): the source nest's own coordinator for `nest`-kind destinations, and the client-device custodian pull for its kind (OS-scheduler-owned cadence on iOS/Android; foreground WS-RPC pushes wake the pull within a 5-s debounce). Per-destination cadence is deliberately omitted — it is divergence with no stated need; revisit only if a concrete requirement appears.

- **A timestamp alone does NOT prove an upload — RESOLVED 2026-07-29, see above.** Before the `last_content_synced_at` split above, the manifest mirror was re-uploaded (and the OLD `last_upload_time` column advanced) whenever `manifest_changed` (`bins/fauna-nest/src/segment_backup.rs`), which was true on an owner's **first** pass even with zero segments. `last_upload_time` now reads a column that only a real `record_custody`/drop advances, so this caveat no longer applies to it — but it's kept here as the reasoning trail, and the underlying fact about `manifest_changed`/`last_synced_at` (the bookkeeping column) is still true, just no longer what the UI reads. The drained **backlog** remains the independent pending-work signal; any future assertion on this row may still want to pin both.
- **A once-built page must re-read on becoming visible.** linux rendered a permanently stale "Last upload: never" because its destinations section is built once into the content `GtkStack` and only refreshed on mount and after add/edit/remove — so a status the nest advanced while the user was on another page stayed invisible until they mutated a destination. Fixed 2026-07-24 with a `connect_map` re-read (`apps/fauna-linux/src/views/backups/destinations.rs`), the same shape the Feed split uses. **Nor may it read while hidden (2026-10-06).** The status read heals a missing enrollment, so it is a write in effect, and it belongs to a page visit. linux kept a build-time read beside the `connect_map` one, which ran at every sign-in with the page hidden. After an identity succession the window rebuild landed that heal ahead of the aftermath's own re-grant leg, which then found nothing owed and painted no progress line ([`succession-aftermath.md`](succession-aftermath.md) § Implementation status today, leg 2). linux now loads the section only on `connect_map`, which fires on the first show too, as tui does by reading the page only when it is opened. **Checked on android 2026-07-29 — NOT affected, structurally exempt like web/tui:** the Backups page is a plain `composable("backups") { SnapshotListScreen(...) }` `NavHost` destination (`FaunaNavHost.kt`), never a persistently-mounted shown/hidden shell; even the drawer's `saveState`/`restoreState` navigation only preserves the `ViewModelStore`, not the composition — the composable (and its `LaunchedEffect(Unit) { vm.refresh() }`) is disposed on navigating away and freshly recomposed on every re-entry, so the status re-reads on every visit by construction. **Checked on windows 2026-08-25 — NOT affected, structurally exempt like android/web/tui:** `BackupsPage.xaml.cs` sets no `NavigationCacheMode` (defaults to `Disabled`), and `MainPage.xaml.cs`'s nav handler calls `ContentFrame.Navigate(pageType, _clients)` unconditionally per selection, so every visit builds a fresh page → `OnNavigatedTo` → `Page_Loaded` → `LoadDestinationsAsync` → `RefreshStatusesAsync`, by construction. **apple remains to be checked** when its call site is build-verified.

**Where the repoint bit, on linux (2026-07-24).** The repoint replaced linux's dedicated status-read thread — which owned a current-thread tokio runtime and `block_on`'d the read — with a bare `glib::spawn_future_local`. The GTK main thread holds no tokio enter-guard, so the read's `NestClient::request` (`tokio::time::timeout`) panicked its task on every call: the destination rows silently never rendered, with no error surfaced, which read as "you have no backup destinations". `test_backup_destination_crud[linux]` caught it; the read now goes back through the app's `spawn_with_snapshot` runtime hop, and a failed destination-list read surfaces in the page `error-message` instead of being swallowed into an empty list. The general lesson — real I/O belongs in the `produce` closure, never in the glib future — is recorded at `apps/fauna-linux/src/async_helper.rs`. Note the shape of the near-miss: every unit test passed throughout, because none of them crosses the glib boundary.

**The superseded source-side model is RETIRED AND DELETED (its keep-condition expired).** This subsection used to carry the pre-repoint per-app shape — each app building an ephemeral client `BackupCoordinator` and computing `destination_status()` source-side, with desktop "fold the read onto the live upload-driver handle" optimizations and web's degenerate carve-out — "kept for reference until the last app is repointed". That condition has expired: windows and apple verified their repointed call sites 2026-08-16 (macOS + windows both passed the end-to-end regression guard — `backup-restore.md` § *Flip status (slice 5)*), the `FfiBackupCoordinator` face was deleted 2026-08-16, and the client coordinator itself (with `destination_status()` and its `data_dir` canonical-path contract) was deleted 2026-08-17. The full historical shape lives in this file's git history (pre-2026-08-17).

The per-row text mapping is computed in **shared Rust** — `fauna_core::format::backup_last_upload_label` / `backup_backlog_label` ([`value-formatting.md`](value-formatting.md) § Backup destination status labels owns the contract, incl. the never-vs-real decision, the epoch-`0` guard, and the seconds→ms conversion): the app resolves the returned label through its i18n pipeline and, for a real timestamp, fills the label's `{when}` arg with the resolved shared relative time. ### Held-for-friends enrollment (ratified — 2026-06-14)

A **held-for-friends** destination is a backup destination on a nest the data owner does **not** administer — a friend's nest hosting the owner's encrypted backup. It is **not a new backup mechanism**: the seal (`BackupKey`, [`../ui/backups.md`](../ui/backups.md) § Encryption at rest), the chunk pipeline, the guest's reserved folders, the custodian's per-path GC-safety record, and the coordinator machinery are **identical** to the owner-administered case (the friend's nest is the custodian — it reclaims its own custody without ever holding the guest's `BackupKey`). The **only** difference is *who authorized the guest's account on the destination nest*. Concretely:

> **Held-for-friends = the owner-administered enrollment (§ Create), run against a destination nest on which the *holding* nest's admin has admitted the data owner as a storage-only user** — rather than the data owner being that nest's admin.

**Authorization = the existing admission lifecycle + a backup-only tier (no new primitive).** The nest's quota model is "the tier *is* the quota" (`docs/goal/behavior/admin.md` § 2 Users — there is no per-user quota override). So the friend-authorization handshake the prior scope deferred is the **existing user-admission lifecycle** (`admin.md` § 2 Users — approve an invite *request* or mint an invite *code*, both choosing a tier), with one addition: a **`backup` tier** whose caps are storage-only (`max_inbox_bytes = 0`, `max_feeds = 0`, `max_storage_bytes` = the space the holder offers; `max_devices` / `max_blob_size` set for backup chunking). The holding nest's admin admits the guest at the `backup` tier; the guest's `users` row (`bins/fauna-nest/src/db/migrations.rs`) is created **handle-less** (`handle = ''`, allowed by the partial unique index `idx_users_handle … WHERE handle != ''`) — no local-part, no MX routing, no inbox, no feeds: the account can **only** own reserved folders and consume storage against the `backup` tier's `max_storage_bytes`.

- **The guest's backup on the holding nest is structurally identical to a backup on any owner-administered destination.** The reserved-set create + member-add are the *same* `fauna.folders.create` / `fauna.folders.members.add` calls the owner-administered coordinator already makes (§ State & data shape → *Coordinator-driven destination provisioning*) — only run under the **guest's** `actor_id` (authorized because the guest is an admitted user; isolated by the existing `UNIQUE(name, actor_id)` per-actor reserved-set model — two actors on one nest each own their own). **No** holder-namespaced `__<kind>/<guest>` sets and **no** new folder authorization.
- **The holder reads nothing.** Chunks are `BackupKey`-sealed (the guest's identity-seed key, never on the holding nest), and the `backup` tier (inbox = 0, no MX) guarantees the guest never stores plaintext-readable content on the holding nest — so the holding nest cannot read the backup (the symmetric guarantee in `docs/goal/architecture/encryption-at-rest.md` § Per-content-kind conformance → *Backups (other user's data this user holds)*).

**Discovery / approval handshake (crash-safe, reuses admission's decision point).** The guest obtains the `backup`-tier account through the **existing** secondary-nest admission path — the holder mints an invite code and shares it out-of-band, or the guest submits an invite *request* the holder approves (`admin.md` § 2 Users, Sections 1–2). The guest's identity is their home-nest identity (unified across locations — `encryption-at-rest.md` § Goal; the multi-nest case `docs/goal/behavior/linked-nests.md` already covers). Once admitted, the guest adds the destination through the **already-ratified** `backup-destination-add-*` dialog ([`../ui/backups.md`](../ui/backups.md) § Manage backup destinations); enrollment then proceeds exactly as § Create (resolve `fauna.nest.info`, `fauna.auth.handshake` as the guest's stable actor — which now succeeds because the guest holds an account — append the `BackupDestination` row via `mutate_backup`). **Crash-safety is unchanged**: the holder's admission is the single atomic decision point on the holding side; the guest's coordinator enrollment is idempotent and reconciles each pass (§ Create / § Remove). A friend's nest offline at any step simply retries. (Before admission, the guest's enroll attempt fails `fauna.auth.handshake` — surfaced as the existing add-dialog error, the same path as an unreachable nest; no new affordance.)

**Stop hosting + promotion (the "make the friend a real user later" path).** The holder stops hosting via the **existing** eviction (`admin-users-evict-button`, `admin.md` § 2 Users); the guest's reserved sets + chunks are reclaimed by the holding nest's GC/retention (restore is always the owner pulling chunks back to a location they hold). To **promote a backup-guest to a full user later**, the holder changes their tier from `backup` to a normal tier via the **existing** `admin-users-tier-select` (`fauna.admin.users.update { actor_id, tier }`) — the account already exists, so promotion is a one-field change. Promotion carries no consent gate: `plaintext_mode_consent` is retired without replacement (no-modes, ratified 2026-07-12 — [`../architecture/nest/storage-modes.md`](../architecture/nest/storage-modes.md) § What replaced each piece of the axis) — the promoted user's live content rests sealed like everyone's, and what the holding box can read is their own grant set, visible per-user on the Nests page.

**No new ui.yaml IDs.** Because the guest is admitted through the existing admission lifecycle and enrolls through the existing `backup-destination-add-*` dialog, held-for-friends adds **no** `backups`-page or `admin-users`-page IDs — the prior scope's anticipated "friend-offer / guest-accept affordances" dissolve into the existing tier pickers + add-destination dialog. The `backup` tier surfaces as one more option in the existing tier pickers (`invite-request-row-tier-select` / `admin-settings-tier-select` / `admin-users-tier-select`). The only net-new artifact is a **`backup` seed tier** (a `tiers` data row in `migrations.rs` `SEED_TIERS`, carrying `max_feeds = 0`) — data, not UI.

**Implementation status (2026-06-16).** The nest enablement **landed** (tier_3 `bins/fauna-nest/tests/segment_backup_held_for_friends.rs`): the `backup` seed tier; the confirmation that a handle-less admitted actor owns its own reserved sets (`fauna.folders.create`/`members.add` authorize the `User` class, `caller_class_for_actor` ignores `handle`, `folders` is `UNIQUE(name, actor_id)`); and the **reclaim-on-stop-hosting** half above — every user-deletion path (`pending_actions::finalize_user_deletion`) now drops the actor's folders + `backup_custody` so the next GC reclaims their chunks (it previously left them orphaned, so GC protected them forever). **The remaining half LANDED 2026-06-16:** per-actor storage-quota **enforcement** — `users.storage_bytes_used` is now written and the `backup` tier's `max_storage_bytes` is **enforced** (no longer advisory). The client manifest-record / backup-custody paths charge each actor's logical bytes and reject "upload past `max_storage_bytes`" with the typed `fauna.sync.storage_quota_exceeded` error (criterion (c)); the same code path is uniform across all tiers, not backup-specific (mirrors the inbox-quota pattern). Proven by `segment_backup_held_for_friends.rs::held_for_friends_guest_over_cap_rejected` (backup tier) + `storage_quota.rs` (free/personal). See § Implementation status today for the documented residuals (raw-chunk path metered only via the GC orphan grace; legacy `storage_bytes_used` baseline 0, no precise backfill).

**Out of scope (future refinements, each gated on an unspecified surface).**
- **Per-user-offers-their-own-quota on a multi-user holding nest.** Admitting a guest consumes the *nest's* disk, which is admin-gated (tier control is admin-only). Letting a *non-admin* user offer a slice of *their own* quota to a friend needs a per-user sub-quota model that intersects the unspecified subscriptions/monetization surface (`docs/goal/behavior/monetization.md`) and partly contradicts "the tier is the quota" — deferred. v1 held-for-friends is admin-gated (on the common single-user holding nest, holder = admin, so this is invisible).
- **Per-guest distinct quotas.** Two backup-guests at different quotas need two tiers (the existing per-tier-is-the-quota constraint, not new to held-for-friends). The `backup` seed tier covers the common case; per-guest tiers reuse whatever tier-creation the admin surface provides.
