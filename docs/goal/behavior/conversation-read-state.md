## Goal

A thread read on one of the account's devices is read on all of them, a message that arrived while every app was closed is unread at the next launch, and nothing about either depends on a device clock. The product rule — what is unread, and that opening a thread reads it — is `conversations.md`'s and does not change. This doc gives that rule somewhere durable to live.

## One carrier per rail, and why not one for all

Read state needs two things from a rail: an identity for the thing being read that every device computes identically, and a position or flag that orders "read" against "arrived". The two rails that ingest today have different honest answers, and forcing one carrier over both would make one of them worse.

| Rail | What is marked | Cross-device identity | Carrier |
|---|---|---|---|
| Fauna-native (`Rail::FaunaMls`) | the thread, by position | the MLS channel id (`ThreadKey::Channel`) | the `fauna.state.read-marker` account-state record — § The read-marker record |
| Mail (`Rail::Smtp`) | each message | the message's `INBOX` UID on the nest | the message's IMAP `\Seen` flag — § Mail: `\Seen` is the marker |
| Any other rail | — | — | none ingests today — § A rail that ingests later |

**No mail `ThreadKey` is ever a cross-device key.** A `ThreadId` is minted per app run, and of the four `ThreadKey` variants only `Channel` is stable across devices. `Participants` and `SubjectKeyed` carry addresses and a subject line — content, which has no place in the key of a grant-mintable record — and `ByMessageReference`, the key every mail with an `In-Reply-To` gets, resolves to *whichever thread currently holds the parent*, which depends on the order this run ingested the mailbox. Two devices can thread the same mailbox differently and both be right. So mail read state is held per **message**, where identity is not in doubt, and a mail thread's unread count is derived from its messages on each device. The question "what keys a mail thread across devices" is answered by never needing the key.

## The read-marker record

`fauna.state.read-marker` — an ordinary class-2 account-state kind, registered in `fauna_protocol::merge_policy` beside the seen-set it is deliberately not (the split is `account-replica-posture.md`'s: the seen-set records what the account has *observed* and feeds custody; this records what the user has *read* and feeds a badge).

- **Key: `conv:<channel_id_hex>`** — one entry per native channel, lowercase hex, the same spelling `MessageId`s on that rail already embed (`conv:{channel_hex}:{seq}`). The `conv:` prefix is the rail's keyspace, so a later rail joins the same kind under its own prefix instead of minting a sibling kind. The plane blinds item keys before they reach a nest, so the channel id is not exposed by being a key.
- **Value: `ReadMarker { through: u64 }`** — every message in the channel whose channel `seq` is at or below `through` is read. `seq` is the rail's one cross-member ordering key ([`../architecture/message-segment-store.md`](../architecture/message-segment-store.md): read watermarks are `seq`-keyed), assigned by the nest inside the per-channel lock, identical on every device, and recoverable from every held message's id. The struct denies unknown fields and encodes canonically, like the seen-set's.
- **Merge: `MergePolicy::CrdtPerField`, with its own join — `max(through)`.** No existing arm is a max-register: the policy set is closed and each `CrdtPerField` kind brings its own join to `apply_class2`, so this kind adds one (`fauna_core::read_marker::ReadMarker::join`) with the usual law tests — commutative, associative, idempotent — and the usual byte-equality echo-stop in its dispatcher arm. `LatestWins` was considered and refused: it would let a device with a stale value and a fresh stamp move a marker *backwards*, re-presenting read messages as unread on every other device; a max-register cannot.
- **Retention: a device keeps an entry for as long as it keeps the account, and the entry's row at a nest follows the membership (amended 2026-10-01; the row rule built 2026-10-03).** `CrdtPerField` refuses tombstones, and this kind does not need one. On a device, a marker for a channel the user has left or deleted is a key and one integer, and nothing reads a marker for a channel the device does not hold. So a stale entry is inert, it stays, and there is no absorbing "retired" state. Keeping it is *useful*: re-joining the same channel resumes at the old position instead of re-presenting its whole history as unread. At a nest the marker is a live row, and those are capped: before this amendment a row was never taken away, so the population was every channel the account had ever been in, and a full scope refuses the first row of the next one. Now, when the account leaves a channel, each device that concludes the departure retires the rows it wrote for the marker, and no device writes one while it is out of the channel. A device that kept the entry and is in the channel again finds no row carrying it and writes one, which is how the re-join resumes. A device enrolled after the leave holds no entry, and for it a re-joined channel starts unread. Account deletion removes every entry and row with everything else in the scope. The row rule, the bound it leaves (2,044 conversations at once) and what an account past the bound is owed are [`../architecture/delegable-scope-reclamation.md`](../architecture/delegable-scope-reclamation.md) § Delegable-scope reclamation: one row per channel rather than one per device in parts (1) to (4), and a full scope in parts (5) to (7) (ruled 2026-10-01, not built).
- **What it cannot express, on purpose: "mark unread again".** A max-register never goes down. If that gesture is ever wanted it is a **sibling kind**, not a change to this one — an LWW-stamped per-thread "unread from `seq`" pin that the next open clears — because a changed value shape would be undecodable to every older build holding the frozen one. Nothing in ui.yaml asks for the gesture today.
- **Rung and sealing epoch:** delegable, generation 0 — argued in `account-data-taxonomy.md` § The audience ladder → *The read-marker rung*. The payload is a reference and a counter, pinned Secret-free in `fauna_protocol::secret_free` in the same edit as the registration.

**Who writes it.** Exactly one place decides a thread was read: `ConversationsManager::notify`, which reads the attended thread ahead of every snapshot. When that read changes anything on a native thread, the manager raises the channel's marker to the highest channel `seq` the thread holds. The raise is a read-modify-write through the account-state plane's writer door; it is idempotent and monotone, so the writer skips a raise the stored value already covers and may coalesce a burst (a thread held open while messages arrive) into its latest value. A raise that cannot be written — no runtime yet, plane refusal — changes nothing the user sees: the thread is already read in memory, and the next read of that thread raises again.

**How the manager reaches the plane.** `fauna-conversations` does not depend on the sync engine and must not start to. It declares a seam — `backend::ReadPositions`, the same shape as `backend::GroupReceptionKeys` — that `fauna-account-seams` implements over `AccountStoreHandle` (wasm-capable, so web registers it too once it hosts the runtime; `fauna-client-account-runtime` re-exports it), and that each app registers at its account-store-ready edge (not at login: the runtime resolves after it). The seam has two directions: `raise(channel_id_hex, through)` outward — synchronous and non-blocking, because the chokepoint is; the implementation queues it, coalesces a burst per channel and raises through the handle's door — and inward the glue hands the manager the current positions: once when the seam is registered, and again whenever they may have moved — whenever the one store-change watch fires ([`../architecture/account-runtime.md`](../architecture/account-runtime.md) § Multi-instance concurrency → *A runtime's own pump is a source of the notice too*): a run of this runtime's own pump that changed the store (its walk is where a sibling's raise arrives), or the store's cross-connection change counter moving (a co-located process holding the pump committed instead) — delivering only positions that changed. The plane has no per-kind change feed today; the glue re-reading this one small kind on that notice is this kind's answer, and a general feed, if one is ever built, is [`../architecture/account-sync-plane.md`](../architecture/account-sync-plane.md)'s to own. Registration is generational: an identity change retires the seam before the store is wiped, and a delivery under a retired registration is refused, so one account's positions never land on the next account's threads.

## Mail: `\Seen` is the marker

The nest already holds a per-message read flag for every mail the account has: IMAP `\Seen`, in the placement row of each `INBOX` message, read and written today by any third-party mail client the user points at their mailbox ([`imap-server.md`](imap-server.md)). **The app reads and sets that flag. There is no second marker.**

- **One truth.** A second marker beside `\Seen` can disagree with it, and then the user's phone says a mail is read while Thunderbird says it is not — about the same message in the same mailbox on the same nest. Every mail client the user has ever used treats the mailbox's flag as the read state; a Fauna app is one more mail client of that mailbox and behaves like one.
- **It dissolves the identity problem.** The flag is per message, keyed by the nest's own UID, so no thread identity has to survive across devices (§ One carrier per rail).
- **It keeps mail content out of the account-state plane.** A thread-keyed mail marker would have to carry participants and a subject in a delegable record's key.
- **It needs no account runtime**, so every app — web included — gets synced mail read state the day it builds.
- **What the nest learns:** that a message was read. A nest serving IMAP has always known that; nothing new is disclosed. The flag is placement metadata and rests unsealed, as it does today; the mail itself stays sealed.

**Reading it.** The inbox feed already carries each message's flag set on the wire, and the conversations glue already receives it — and drops everything but the spam watermark. The flag rides into the manager on `InboundMailRecord`, and a mail message is unread exactly when it is not own and does not carry `\Seen`. No floor, no clock: a mail that arrived while every app was closed has no `\Seen` and is unread at launch.

**Writing it.** Reading a mail thread sets `\Seen` on each of its unread `INBOX` messages in one batched call to a least-privilege `User`-class RPC that can add `\Seen` and nothing else (`mail-app-surface.md` § Read state owns the wire shape; it shares the MDA flag-write internals, so the change is journaled, bumps the mailbox's modseq, and reaches an `IDLE`-ing mail client like any other flag change). Own messages are never unread, so the `Sent` feed needs no flag write.

**Learning of a change made elsewhere.** A running app hears a wake push when any flag in its actor's `INBOX` changes — from another Fauna device or from a mail client — and answers it with one modseq-cursored fetch of the changed flag sets (same owner). A message that gained `\Seen` leaves the unread set. A message that **lost** it — a mail client's "mark as unread" — re-enters the set: on the mail rail the flag is the truth in both directions, which is the one place "mark unread again" already exists, supplied by the other client.

**When the write cannot reach the nest.** The read holds in memory for the run; the manager keeps the pending UIDs and sends them when the nest is reachable again. A run that ends first loses them, and those messages are unread at the next launch. That is under-durable by declaration and never wrong-direction: nothing is ever marked read that the user did not open. Whether the pending set should instead ride the persisted outbox is [`../architecture/account-offline-mutation.md`](../architecture/account-offline-mutation.md)'s contract to extend, at build time, not a second queue to invent here.

**A UID that moved.** A mail client that files a message into another mailbox changes its UID. The app's held UID then names nothing; the RPC ignores unknown UIDs, the message leaves the `INBOX` feed at the next launch, and nothing is wrong in between.

## A rail that ingests later

`Rail::Bridged` exists as a name (the Bluesky, ActivityPub and Nostr rails were deleted 2026-10-02 and 2026-10-03 in favour of it, [`../ui/conversations.md`](../ui/conversations.md) § Where logic lives → *The `Bridged` adapter*); no app ingests on it into the manager today. A bridged room's read state is the native carrier, keyed by room id, as that section rules. The rule for the day one does: if the upstream owns a read state of its own (as a mailbox does), that state is the marker and the app reads and writes it — the mail pattern; if it does not, and the rail has a per-thread total order every device sees identically, it takes a keyspace prefix in `fauna.state.read-marker` — the native pattern. A rail with neither gets a design pass, not a third carrier improvised in an app.

## How the carriers meet the in-memory set

`store::threads` holds, per thread, the set of unread message ids, and every app renders `ThreadSummary.unread_count` from it. The set stays: it is the one rail-neutral shape, and both carriers fill it.

- **Mail:** a message enters the set at ingest iff it is not own and lacks `\Seen`; a flag change delivered later adds or removes exactly that message; reading the thread empties the set and sends the flag write.
- **Native, position known:** when the seam delivers a channel's position `through` (absent entry ⇒ `0`), the thread's set becomes exactly `{ m : not own, not deleted, seq(m) > through }` — computed whole, replacing whatever was there. Later arrivals enter iff `seq > through`. Reading the thread empties the set and raises the marker. A raise arriving from another device removes every id at or below it.
- **Native, position unknown:** until the seam has delivered positions — every native app between launch and its account-store-ready edge, and a host with no account runtime for its whole run — the store cannot tell history from news, and falls back to the **launch floor**: a message stamped before the store was created is history. This is the pre-sync behaviour, kept as the fallback and nothing else. On a native app it is superseded, whole, the moment positions arrive, so its under-reporting and its clock comparison last seconds rather than the run. **The stamp the floor compares is, on the native rails, the sender's own claim** — a room's signed `sent_at_ms`, an end-to-end message's sealed `timestamp`, a nostr event's `created_at` (mail alone carries the nest's `INTERNALDATE`) — so a sender who backdates a message below the recipient's floor makes a live arrival read as history: no unread indicator and no banner. This under-report is declared, not defended: it only withholds attention (the message stays in its thread), and it pushes toward the floor's chosen direction. **Its unread half** lasts exactly as long as the fallback does — seconds on a native app, the whole run on web — because the fill rule above keys on the nest-assigned `seq` a fauna-native message id carries, which the sender does not choose (a nostr id carries none; that rail takes its carrier by § A rail that ingests later the day it ingests). **Its banner half does not retire with it:** the banner keeps its own floor read for the whole run on every app (the paragraph below; [`message-banners.md`](message-banners.md) § Where logic lives, rule 2). Pinned in `unread_tracking_tests.rs`, and for the banner in `notification.rs`.

The floor therefore leaves the mail rail at once and leaves the native rail on every app that hosts a runtime. **Its unread read is deleted from `store::threads` when the last host without an account runtime gains one** — § web. The floor value itself and its clock read stay: since 2026-09-22 the new-message banner decision reads the same `launch_floor_ms` off every snapshot ([`message-banners.md`](message-banners.md) § Where logic lives, rule 2), and "did this arrive while the app was running" keeps a run-start answer whatever read state knows.

**The one-time transition.** The first launch on a build with synced read state finds no markers and, for a user who has only ever read mail in a Fauna app, no `\Seen` flags. Every thread with a message from someone else shows unread once, and clears for good — on every device — as it is opened. This is accepted rather than engineered around: the alternative is a seed that writes "everything so far is read", which needs a once-per-account latch inside a frozen record, would stamp `\Seen` over the genuine unread state of anyone who does use a mail client, and buys a closed-alpha account one fewer afternoon of stale badges. The badges are true: those threads have not been opened under a regime that remembers.

## web

web hosts the account runtime since 2026-09-29 (`../architecture/account-client-lifecycle.md` § Implementation status today) and registers the read-position seam at its store-ready edge through the same `conversation_seams` join every host runs. Until that edge — the runtime still assembling, or a tab whose start failed — it has no replica to read a marker from and no plane to raise one through, and the floor below holds.

- **Mail read state is complete on web**, because its carrier is the nest's flag and needs no runtime.
- **The native rail on web keeps the launch floor** while no runtime is up, with its three declared gaps: a native message that arrived while the tab was closed shows no indicator, a native thread read on web is not read elsewhere, and a live native message its sender stamped before the tab opened counts as history (§ How the carriers meet the in-memory set, position unknown). Without the seam its store never leaves the position-unknown arm.
- No nest-side relay of the marker for web is designed here, and none is owed: web reaches class-2 state through its own runtime like every host.

## The proofs it ships with

- The join's laws, and the dispatcher arm's echo-stop, tombstone refusal and loud bad-value refusal — beside the seen-set's.
- **Two replicas, no nest:** a marker raised on one store converges on the other, and two concurrent raises converge to the higher — in the `fauna-sync-engine` peer-leg convergence harness, which drives real stores, the real writer door and the real merge dispatch with explicit walks and no sleeps.
- **Two devices, end to end in shared Rust:** manager A reads a native thread → seam → store A → walk → store B → seam → manager B's `unread_count` for that channel is zero.
- **Relaunch:** a store restored from a channel slice, given a position below the slice's newest message, reports exactly the messages above it unread — with the device clock nowhere in the assertion.
- **Mail:** an ingested record without `\Seen` is unread with no floor consulted; with it, read; a delivered flag change moves one message each way; reading a thread emits one batched flag write naming exactly its unread `INBOX` UIDs.
- **Nest:** the flag-write RPC adds `\Seen` and refuses to be anything else (no other flag, no removal, no other actor's mailbox), journals, and bumps modseq; the flag-change fetch returns exactly the rows past its cursor.

## Implementation status today

**Designed 2026-09-21; built 2026-09-24 — the native rail on every app that hosts an account runtime, the mail rail on all 7 apps.**

- **Built:** `fauna_core::read_marker` (the record, its join, its laws); the kind's registration, join arm and first-contact validation in `fauna_protocol::merge_policy`; its Secret-free pin; the two-replica convergence proof in the peer-leg harness.
- **Built — native rail (2026-09-24):** the monotone raise door and the keyed read on `AccountStoreHandle` (`raise_read_marker`, `read_markers`; the door is served inside a pass at its yield points, and nothing between its read and its write yields, so its read-modify-write cannot straddle a walk page), and the wait the glue re-reads on (the pass-completion wait `pass_completed_after` until 2026-10-02; since then the shared store-change watch, `fauna_account_seams::store_change`); `backend::ReadPositions` and its one implementation, `fauna_client_account_runtime::read_positions`, registered through the shared `conversation_seams::wire` beside the group-reception keys; the fill rule and the position-unknown arm in `store::threads` (the seq comes off the message id, `MessageId::channel_position`); the raise at the read chokepoint (`ConversationsManager::read_thread`, which `notify` and `mark_read` share). Proofs: the fill rule, the raise, the relaunch and the retired-registration refusal in `fauna-conversations`' `unread_tracking_tests.rs`; the door in `fauna-sync-engine`'s runtime tests; **two devices end to end** — two real runtimes over the peer leg, a real manager on each — in `fauna-client-account-runtime`'s `read_positions_convergence.rs`. tui and linux register the seam at their account-store-ready edge; the UniFFI hosts (windows, macOS, iOS, android) register it in `fauna-ffi`, whose session and store land in either order, from both edges — the store's install and the session's stash — each a no-op until the pair is complete (both orders pinned in `fauna-ffi`'s `account_runtime` tests). The same call gives those hosts the group-reception keys, which they had lacked.
- **Built — the app-level witness (2026-09-24, tui):** `test_conversations_read_state_across_restart.py` — a native message posted while tui was closed is unread at its next launch, behind a durability barrier on the store's marker (the `read_marker_state` e2e reader over the shared `read_marker_state_json`). The other runtime-hosting apps take its `skip_unbuilt` arm until they grow the same reader; web's arm is the declared absence below.
- **Built — mail rail, all 7 apps (2026-09-24):** `\Seen` rides `InboundMailRecord` (`has_seen_flag`) and `store::threads` decides a mail message's unread state from it alone — no floor on the mail rail. Reading a thread (`ConversationsManager::notify` → `read_thread`) owes one batched `mark_seen` naming exactly its unread `INBOX` UIDs; `fauna_conversations::mail_read::MailReadSync` holds the owed UIDs, the `(since_modseq, after_uid)` cursor (baseline: the first non-zero `highest_modseq` an `INBOX` page names) and the older-nest latch; `backends::smtp::sync_mail_read_state` drives both calls through the `INBOX` source. Native apps run it from the shared receive loop — every mail sweep, the `fauna.mail.flags_changed` wake (the rail's own `subscribe_kind`, beside `fauna.mail.received`), and a read's poke that sends the write at once; web runs the same driver from its mail pass (`WasmConversationsManager::syncMailReadState`), woken by the same push and by a read that owes a write. **The pending set stays in memory, by decision:** `mark_seen` is `OfflineSafe` and the outbox holds `OfflineQueued` intents only (`account-offline-mutation.md`), so there is no durable queue to extend; a run that ends first leaves those messages unread at the next launch. Pinned in `mail_read_state_tests.rs` and `mail_read`'s unit tests; the tui journeys (unread across a restart; read on one device, read on the other with no relaunch, still read after its restart) in `tests/e2e-unified/tests/test_mail_read_state.py`. The floor's own pins in `unread_tracking_tests.rs` now run on the native rail.
- **Ruled 2026-10-01, BUILT 2026-10-03 — the retention bullet's row rule.** A device that concludes the account left a channel retires its own row of the channel's marker, and of its seen-set entry, and sends none while it is out; it keeps the entry. A device still in the channel writes the marker back when no row carries it, and a device back in the channel writes it back at the old position. A marker raised at a full scope parks, and the device's later writes still land. The mechanism, its tests and the measurement are in [`../architecture/delegable-scope-reclamation.md`](../architecture/delegable-scope-reclamation.md) § Implementation status today.
- **Standing while any host can lack a runtime:** web has hosted one since 2026-09-29, but before its store-ready edge (or after a failed start) the launch floor's *unread* read in `store::threads` still serves as the native rail's position-unknown arm, so the arm stays in code. The floor itself outlives it as the banner decision's run-start stamp (`message-banners.md` § Where logic lives).
