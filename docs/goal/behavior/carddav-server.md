## Goal

A single CardDAV entry point per nest deployment, **served by the mail-bridge MDA role** (`bins/fauna-bridges/`; the *same* process that serves IMAP + CalDAV — one TLS termination, one WS connection to nest, one per-session decryption capability covers all three), implementing RFC 6352 (CardDAV baseline), RFC 6578 (sync-collection), RFC 4918 (WebDAV foundation), and RFC 6350 (vCard 4.0 parsing — server-side validation on PUT; vCard 3.0 accepted for MUA compatibility). All address-book and card state is nest-side (`bridge_carddav_addressbooks`, `bridge_carddav_cards`, `bridge_carddav_expunged`); the MDA process is a stateless protocol terminator that holds only the per-session unwrapped MLS-decryption capability and an in-memory cache of decrypted collection metadata for the AUTH'd session lifetime.

**Bar: parity-or-better with Radicale / Nextcloud / SOGo / Baïkal CardDAV** — exactly as `caldav-server.md` § Goal sets for CalDAV. Any extension a hardened Radicale install gives a Contacts client out of the box (sync-collection, ETag conditional updates, multistatus PROPFIND, addressbook-query, addressbook-multiget, PROPPATCH on collection metadata) must be present here. Beyond Radicale, every card write is sealed-to-recipient at the MDA before reaching nest — nest never sees plaintext vCard bodies (names, phone numbers, postal addresses, birthdays, notes).

**When in doubt, choose the stricter option** (mirrors `caldav-server.md` § Goal): a non-conforming client that violates RFC 6352 in a way a strict reading would reject loses the request rather than producing ambiguous address-book state. Permissive carve-outs need explicit user approval and a counter.

## What a CardDAV address book *is*, in Fauna terms

**The single most important design fact: a CardDAV address book is NOT the social contact graph.** A user's phone address book holds grandma's number, the plumber, a school — people who are overwhelmingly *not* Fauna actors and have no knock/edge. Mapping vCards onto the `contacts` table's `ContactStatus` edges would be a category error.

A CardDAV address book **is** the concrete, wire-shaped realization of the *user-private contact-record contents* layer that `contacts.md` §§ Persistence + Encryption-at-rest reserve (aliases, notes, labels, and cross-rail address-book mappings — one logical contact spanning a Fauna `actor_id` + mail address + XMPP JID). A vCard carries exactly these fields (`FN`, `TEL`, `EMAIL`, `ADR`, `BDAY`, `ORG`, `NOTE`, `IMPP`, `X-*`). CardDAV does not invent a third contacts concept — it **gives the deferred private-contact-record layer a format (vCard) and a server surface (CardDAV)**, backed by the `bridge_carddav_*` store rather than the (unbuilt) `__contacts` folder (§ Storage model; the supersession is recorded in `contacts.md` / `file-sync.md` / `encryption-at-rest.md`).

Two layers, cleanly separated, with an optional bridge between them:

| Layer | Backing store | Audience | What it holds |
|---|---|---|---|
| **Social contact edges** (`contacts` table) | plaintext routing floor | nest-readable (routing) | pending/accepted/confirmed/blocked between Fauna actors |
| **Address book (vCards)** | `bridge_carddav_*` (§ Storage model) | actor MLS pubkey (MDA-unwrapped per session) | standard vCards from/to any CardDAV client |

**Optional linkage (post-v1):** a vCard MAY carry an `X-FAUNA-ACTOR-ID` field so an address-book entry can *point at* a Fauna social contact, and the native Contacts page could surface "this person is also in your address book." Not required; the two stores are independent.

## Storage model — `bridge_carddav_*`, a structural mirror of the CalDAV bridge store

**Ratified 2026-07-06** (design § 3; storage-model decision confirmed by the user). Address-book vCards live in a new nest-side, MLS-pubkey-sealed, MDA-served store — a direct structural mirror of the shipped CalDAV bridge store:

| CalDAV (shipped) | CardDAV |
|---|---|
| `bridge_caldav_calendars` | `bridge_carddav_addressbooks` |
| `bridge_caldav_events` | `bridge_carddav_cards` |
| `bridge_caldav_expunged` | `bridge_carddav_expunged` (shared sync-token / tombstone shape) |
| `ProvisionCalendarRequest` / `put_event_ciphertext` | `ProvisionAddressbookRequest` / `put_card_ciphertext` |
| `query_events` / `sync_calendar` | `query_cards` / `sync_addressbook` |
| (`delete_event`) | `delete_card` |

The MDA seals each vCard via `EncryptToRecipientHybrid` to the recipient keypair it holds per session — the **same Path B (MSEK-derived recipient-mail) primitive CalDAV events use** (`../architecture/encryption-at-rest.md` Calendar-event-content + Contacts rows; `../architecture/key-material-hierarchy.md` rule #7 — a leaked IMAP/CalDAV/CardDAV credential reaches mail+calendar+address-book, and the address book adds a *content kind* sealed to that keypair, **not a new key** to the MSEK snapshot) — before `put_card_ciphertext`; nest's `bridge_carddav_cards` store **never holds plaintext vCard bodies**. Reads: the MDA fetches ciphertext + unwraps with the **same per-session capability it already holds for CalDAV** (`caldav-server.md` § Authentication), decrypts transiently to answer a REPORT / addressbook-multiget, and re-seals writes. **Zero new key audience, zero new AUTH flow.**

**Quota.** Card bytes draw on the account's one storage budget, shared with mail and calendar — composition and implementation status owned by [`caldav-server.md`](caldav-server.md) § QUOTA — shared with IMAP.

**Why not back onto `__contacts` / `BackupKey`** (the deferred contacts-at-rest design, 2026-05-13, tracked internally)? Three reasons, all pointing the same way:

1. **Security-minimal.** `__contacts` is sealed under the owner's `BackupKey` — a broad, identity-derived key. The CalDAV MDA holds only a narrow *session-scoped* MLS capability. Backing CardDAV onto `__contacts` would force handing the MDA the `BackupKey` (or a derivation), widening the server-side-decrypt blast radius. The `bridge_carddav_*` mirror keeps the MDA's capability exactly as narrow as CalDAV's.
2. **Proven / richest existing pattern (priorities #3, #4).** The CalDAV bridge store is shipped and battle-tested for precisely this "serve a generic DAV client server-side" job; the `__contacts` layer is *unbuilt* (verified 2026-07-06: `ContactsCache` is `pub struct ContactsCache;` empty, no `__contacts` handling in `bins/`/`libs/`). Priority #4 says pick the richest *existing* pattern — that's `bridge_caldav_*`.
3. **Substrate fit.** `__contacts` is a fauna-sync *folder* (whole-blob, owner-only). CardDAV needs per-*card* addressing, ETags, and sync-collection tokens — exactly what the bridge store already models per-event. A folder substrate would have to grow all of that.

This **supersedes the `__contacts`-for-address-books half** of the contacts-at-rest design. The private *overlay on social contacts* (a nickname/note attached to a Fauna actor you have an edge with) is a separate concept with its own home — settled 2026-09-19 as an account-state plane kind, neither `__contacts` nor this store (`contacts.md` § The private overlay).

**Durability & disaster recovery — DONE (ratified 2026-07-07; delivered S6.6–S6.11, 2026-07-09/11, bundled with the calendar kind exactly as promised — one step behind, never a CardDAV-specific mechanism).**

- **Card *bodies* rest in the `__card` segment store** (S6.6, 2026-07-09, same pass as calendar's `__calendar` cutover). `bridge_carddav_cards` keeps the metadata row — `uid_hash`/`etag`/`modseq`/`ciphertext_size`/`internal_date`/`encrypted_fauna_ext` — and no body column — the body rests only in the segment (the emptied `encrypted_body` column that once marked a row segment-served was dropped at nest schema 110). Address-book metadata plus the placement journal complete the picture.
- **Pre-cutover rows migrated** by the boot back-fill (S6.7, 2026-07-09), expand→migrate→contract, crash-resumable, no row dropped.
- **Compaction (S6.8b/c), snapshot create/restore (S6.9), and the cross-location-backup destination gates (S6.10) all landed 2026-07-10** — cards carry snapshot create/restore at mail parity plus the **destination-side** half of cross-location backup; **the off-box copy itself followed on 2026-09-29**, when cards joined the shared `BACKED_UP_KINDS` sweep (`../architecture/segment-backup-protocol.md` § Implementation status today); this sentence over-claimed both halves until corrected 2026-09-21, so each is stated exactly. **(a) Restore tells the MUA to reconverge; it does not keep the MUA's token alive.** A restore rewinds the collection, so an already-synced client's sync token lands ahead of the server's modseq, and the bridge answers it with RFC 6578 §3.8's `DAV:valid-sync-token` precondition failure (`bins/fauna-bridges/internal/mda/carddav/sync_collection.go`, the `SyncAddressbookSinceStale` arm), directing the full re-enumeration that serves the restored card back with an ETag, byte-identical and still sealed at rest; what may never happen is that stale token answered with a delta that silently omits the restored card (witness `tests/e2e-unified/tests/test_dav_content_at_rest_e2e.py::test_card_restore_tells_the_contacts_app_to_reconverge`; the CalDAV twin pins the same outcome in `tests/e2e-unified/tests/api/test_dr_restore.py`, where the divergence also feeds the Backups page's writes-lost banner). **(b) Nothing pushes a card segment off the source box.** S6.10 landed the four gates a nest *holding* a custody-copy `__card` folder enforces — it refuses to serve, compact or snapshot it (`../architecture/message-segment-store.md` § Destination capability) — but the source-side sweep that would fill such a folder is the shared `BACKED_UP_KINDS` list, which is mail-only with per-kind growth deferred uniformly for all kinds (`../architecture/segment-backup-protocol.md` § Implementation status today); widening it is a cross-kind ruling on that doc, never a CardDAV-page build. The nest self-backup (`backup-restore.md` § 11) is a box-local DB hot-copy and adds no off-box copy either. The mechanism, kind mapping, and the per-kind status table (mail/conv/post/calendar/card side by side) are owned by `../architecture/message-segment-store.md` § Implementation status today — its `card` row is the authority for exactly what landed and when.

## Process topology & attach pattern — a new protocol on the existing MDA (no new process)

CardDAV is HTTP/WebDAV on the wire, same family as CalDAV, so it is served by the **same MDA process** — one more handler on the shared listener, not a new bridge binary. It reuses, unchanged:

| Port / path | Role | Process | TLS | AUTH |
|---|---|---|---|---|
| `/carddav/{user}/` | CardDAV (REPORT + PROPFIND + PROPPATCH + PUT + DELETE + MKCOL) | mail-bridge MDA role | served at `mail.<domain>:443` via **SNI passthrough**, same cert as IMAP/CalDAV | HTTP Basic Auth → AEAD-unwrap-as-auth (the same one auto-generated PLAIN bridge password `(actor_id, "default")` that serves IMAP + SMTP + CalDAV) |
| `/.well-known/carddav` | RFC 6764 service discovery | mail-bridge MDA role | same | redirect post-auth to the user's principal `/{user}/`, whose unified PROPFIND advertises `addressbook-home-set`; served by the CardDAV chain even when CalDAV owns the root |
| `/api/v1/ws/{actor_id}` | MDA ↔ nest RPC | WS-RPC + DAG-CBOR | TLS to nest's HTTPS listener | challenge-response, signed by the MDA's enrolled service-user Ed25519 keypair |

- **Enrollment / role / allowlist.** The MDA is already an enrolled service-user with role `BridgeMda`. The only nest-side addition is a **new allowlist arm** in `bins/fauna-nest/src/bridge_method_allowlist.rs` permitting the `provision_addressbook` / `put_card_ciphertext` / `list_addressbooks` / `query_cards` / `sync_addressbook` / `delete_card` / `delete_addressbook` kinds to the `BridgeMda` class (default-deny, single chokepoint — `../architecture/apps/bridges.md`).
- **Shared 443 listener.** Landed in Slice 2d: the MDA binds ONE `:443` `http.Server` for `caldav_enabled || carddav_enabled`, path-muxing `/carddav/…` → CardDAV, `/…` → CalDAV, over a shared drain (`internal/mda/dav`). CalDAV serving is byte-identical to before. (A third mux arm — `/webdav/…`, the WebDAV files surface — landed per `webdav-server.md` § Process topology; that doc owns its build status.)
- **go-webdav.** `emersion/go-webdav`'s `carddav` package (already linked via the CalDAV terminator — `go.mod`, no new dependency) routes by path-segment depth exactly like its `caldav` package; the backend lives at `internal/mda/carddav/backend.go`, sibling to `internal/mda/caldav/backend.go`. **Emersion routes by full-path depth, so the CardDAV mount uses `Prefix=""`** (the backend paths already embed `/carddav`; verified vs go-webdav@v0.7.0).
- **AUTH / SNI / connection caps / per-IP keying / request timeouts.** **Identical to CalDAV — see `caldav-server.md` § Authentication, § Network exposure, and the connection-cap / PROXY-v2 / timeout paragraphs.** Nothing new; the CardDAV listener rides the same `internal/connlimit` cap, the same `internal/proxyproto` PROXY-v2 peel, the same lockout brake.

**Unified root principal (follow-up, non-gated).** When both protocols are on, a CardDAV client's root-principal PROPFIND (`/{user}/`) must advertise **both** `calendar-home-set` (`/caldav/{user}/`) **and** `addressbook-home-set` (`/carddav/{user}/`) so a client that only knows the server host can auto-discover the address book. A client pointed straight at `/carddav/{user}/` round-trips without it. Tracked internally (Track B).

## Independent enablement — `carddav_enabled`

Mirrors CalDAV's independent-enablement exactly (`caldav-server.md` § Independent enablement). CardDAV, like CalDAV, needs only the HTTPS surface — no MX/DKIM/SPF — so it gates separately from email; its claim-time default is the machine-derived rule owned by `onboarding.md` § 3b (handle locality AND the NAT axis), and it works when explicitly enabled on a domainless / bare-IP box via the floor cert + handle login.

- Nest singleton `carddav_enabled`, setter `fauna.bridges.set_carddav_enabled`, projected on `FetchConfigReply.carddav_enabled` (landed, slice 1). An **unset** singleton falls back to the mail toggle — `get_carddav_enabled().unwrap_or(mail_enabled)` (`bins/fauna-nest/src/bridge_routing_handlers.rs`; "falls back to mail_enabled so a fresh real-domain deployment gets a contacts surface out of the box") — until the admin explicitly toggles it. The MDA runs its CardDAV listener iff the flag is on (the MDA already runs iff `mail_enabled || caldav_enabled`; extended to `|| carddav_enabled`).
- Credential management is already reachable for a DAV-only mailbox (the mail-settings credential section renders on the shared `credential_management_reachable` predicate, which includes `carddav_enabled` — `../ui/mail-settings.md` § Credential-management reachability owns the full formula).

**App UI (approved 2026-07-06 — priority #1 gate cleared).** The deployment-wide toggle surfaces mirror CalDAV's exactly (§ Architectural rules — never a parallel invention): the intent is machine-derived at claim from the handle's locality (sibling of CalDAV's; no onboarding checkbox — the former `onboarding-enable-carddav-checkbox` retired with `encryption_mode_choice`, not relocated, no-modes ratified 2026-07-12, `onboarding.md` § 3b owns the mechanism), the claim-time launch glue fires `set_carddav_enabled(true)` and — when neither email nor CalDAV minted the shared MSEK — provisions the CardDAV-only mailbox, and the admin shell's `admin-contacts` page (`admin-contacts-carddav-enabled-toggle` over the shared `CarddavPolicyMachine`; `admin.md` § Contacts) is the change surface thereafter. **The mail-settings page carries no deployment toggle** (CalDAV has none either — the flag is Admin-class); its CardDAV work is the *per-actor* side: `MailConfig.carddav_enabled` is one term of the shared credential-section render predicate `credential_management_reachable` (owned by `../ui/mail-settings.md` § Credential-management reachability — `enabled || caldav_enabled || carddav_enabled || serves_webdav_set`) so an address-book-only actor can obtain + manage the bridge password. Also approved: a **native "Address Book" view** over `list_addressbooks` / `query_cards` (decrypted locally / zero-access — the vCards visible *in* Fauna, not only via third-party clients). **Nav placement (user sign-off 2026-07-07): a segment tab *within* the Contacts page** (`Contacts | Address Book`) — the vCard store stays a *separate store* from the social contact graph (§ What a CardDAV address book *is*), co-located in the Contacts UX rather than given a new top-level page (mirrors how CalDAV's Events is top-level, but the user chose Contacts-adjacent for the address book; `contacts.md` owns the resulting page UX). Its data layer is shared-Rust `libs/fauna-client-carddav` (`CardDavClient` + `query_cards_decoded` / `list_addressbooks_decoded` + the WASM-safe `vcard` reader + `unseal_card_body`); the per-app `ui.yaml`-element design + UniFFI/wasm bindings + build are the client slice's remaining TDD scope (§ Implementation status; tracked internally).

## Network exposure & discovery

- **`_carddavs._tcp.<domain>` SRV.** Published as a per-domain row in the unified DNS matrix (`dns-management.md` § Records covered), built by `fauna_mail::dns::per_domain::build_carddavs_srv_record` (sibling to `build_caldavs_srv_record`), record `_carddavs._tcp.<domain> SRV 0 1 443 mail.<domain>.` (priority 0, weight 1, port 443, target the deployment's single CalDAV/mail host — equals the MX target and the `_caldavs` target). TLS-only (`_carddavs`, no plaintext `_carddav` — CardDAV is HTTPS-only). Surfaced + verified by `fauna.dns.{list,verify}_records` like every other record. This is the SRV path macOS Contacts.app's *automatic* account setup uses (given `user@<domain>` it queries `_carddavs._tcp.<domain>` and connects to the named host:port, **without** following an apex cross-host redirect — the same behavior the CalDAV SRV solves for Calendar.app; `caldav-server.md` § Network exposure).
- **Apex `/.well-known/carddav`.** RFC 6764 cross-host discovery, the same `301` → `https://mail.<domain>/.well-known/carddav` bootstrap the CalDAV well-known uses (the unauthenticated apex can't know `{user}`, so it hands off to the bridge host's own discovery, which post-auth redirects on to the user's principal — § Process topology's table); `503` when CardDAV is **explicitly disabled** (`set_carddav_enabled(false)`) or when no primary mail domain is registered. (The former third condition — `503` before a storage mode was committed — is retired with the pre-mode gate itself: a nest is content-ready from first boot, so there is no unconfigured-storage state to gate on — `../architecture/nest/storage-modes.md` § Implementation status today.) An **unset** toggle inherits `mail_enabled` (§ Independent enablement), so a mail-enabled box answers the apex without an explicit opt-in — **the apex must never `503` while the MDA serves**, which is precisely the box on which the MDA "mounts `/carddav/` from boot" (§ Implementation status). The apex is storage-mode-independent, as CalDAV's and WebDAV's are.
- **Interop.** The same bare-username default-to-`PrimaryDomain` and single-segment-principal path quirks the CalDAV surface already solved apply identically (Contacts.app walks current-user-principal → addressbook-home-set). Reuse the shared `auth.SplitEmailDefault` + the emersion depth-routing principal placement.
- **nest never terminates CardDAV TLS.** Identical to CalDAV: on a single-IP box `:443` is fronted by the SNI-passthrough (L4) router (`<domain>` → nest, `mail.<domain>` → MDA); the router decrypts nothing, so no single process sees the union of nest traffic and CardDAV plaintext. Desktop / bare-IP boxes serve CardDAV directly on the same admin-set port family as CalDAV (`caldav-server.md` § Desktop / IP deployment + § Any-locator serving apply verbatim — CardDAV rides the same shared `:443`/admin-port listener).

## Threat model — inherited from CalDAV, no new plaintext point

Identical to `caldav-server.md` § Threat model: **not zero-access, by necessity** — a generic CardDAV client can't decrypt Fauna's sealing, so the MDA decrypts server-side per AUTH'd session (the ProtonMail-Bridge convenience tier). Fauna-*native* apps keep zero-access (they decrypt locally). Preserved:

- Storage is ciphertext-only — `bridge_carddav_cards` never holds plaintext vCard bodies.
- nest never sees vCard plaintext even in transit (SNI passthrough).
- The only process holding a decrypted address book is the MDA, only for the AUTH'd session.
- **No external plaintext-ingest boundary.** Unlike mail, vCards are written only by authenticated clients (a native app sealing locally, or a CardDAV PUT the MDA seals), so a contacts-only deployment has **no ingest window at all** (same as a calendar-only deployment). There is no anonymous-write surface analogous to inbound SMTP.

## Address-book collection model + read / write / sync surface

- **Lazy default addressbook.** First access lazily provisions a "Contacts" default addressbook (works-out-of-box parity with the lazy "Personal" calendar). Additional books via `MKCOL` / extended-MKCOL.
- **Read surface.** PROPFIND (Depth 0/1) on principal → `addressbook-home-set` → addressbook → cards; addressbook-query REPORT (property + text-match filters); addressbook-multiget REPORT (batch by href); ETag conditional GET.
- **Write surface.** PUT a vCard (server-side RFC 6350 validation — vCard 4.0 canonical, 3.0 accepted for MUA compat; reject malformed per "when in doubt, stricter"); the MDA seals the validated body to the actor MLS pubkey → `put_card_ciphertext`. A card-resource DELETE → tombstone in `bridge_carddav_expunged` (`delete_card`). A **collection**-level DELETE (on the address-book URL) → cascade-delete the whole book and every card it holds, atomically in one transaction under one lock (`delete_addressbook`), writing **no** per-card tombstones and clearing the book's existing ones — a re-sync of the removed collection gets 404 (the WebDAV "collection gone" signal), so per-card tombstones would be dead rows and, keyed by `(actor, addressbook_id)`, would leak a false expunged-history into a same-id re-provisioned book (the lazy "Contacts" book always reuses `blake3("contacts")[:32]`). Conditional card PUT/DELETE honor `If-Match`/`If-None-Match` ETags; a collection DELETE is unconditional. A **collection-level PROPPATCH** persists address-book metadata edits (`{DAV:}displayname`, `{urn:ietf:params:xml:ns:carddav}addressbook-description`): unseal the current metadata → mutate → re-seal → `provision_addressbook(update_metadata=true)`, returning a 207 multistatus (recognized props `200 OK`; unknown props `403 cannot-modify-protected-property` in the same body; empty PROPPATCH is an idempotent no-op that skips nest). A **card-resource** PROPPATCH is rejected `403` (cards are atomic re-PUTs — no per-card property mutation). Twin of the CalDAV collection-PROPPATCH (address books carry no color analog).
- **Sync model (RFC 6578).** `sync-collection` REPORT over `sync_addressbook`, returning changed/removed hrefs + a new sync-token; stale-token-past-retention returns `DAV:valid-sync-token` (mirror the CalDAV `SyncCalendarSinceReply::Ok { stale: true }` handling — `caldav-server.md` § Sync model).

## MDA ↔ nest WS-RPC contract

Seven MDA-class kinds (all `BridgeMda | User`-allowlisted, DAG-CBOR wire; types in `libs/fauna-protocol/src/bridge_routing.rs`):

| Kind | Wire type | Effect |
|---|---|---|
| `provision_addressbook` | `ProvisionAddressbookRequest` | create/ensure an addressbook row |
| `list_addressbooks` | `ListAddressbooksRequest` → `ListAddressbooksReply` | enumerate the actor's addressbooks (also the client-side Address Book view's read) |
| `put_card_ciphertext` | `PutCardCiphertextRequest` | upsert a sealed vCard (`CardEntry`) |
| `query_cards` | `QueryCardsRequest` | fetch sealed cards for a REPORT/multiget |
| `delete_card` | `DeleteCardRequest` | tombstone a card (`ExpungedCardEntry`) |
| `sync_addressbook` | `SyncAddressbookSinceRequest` | changed/removed since a sync-token |
| `delete_addressbook` | `DeleteAddressbookRequest` → `DeleteAddressbookReply` | cascade-delete a whole book + all its cards (`deleted{cards_deleted}` / `not_found`, idempotent) |

`delete_addressbook` (`carddav.Backend.DeleteAddressBook`) is shipped (Slice 3(C)); the cascade + no-tombstone semantics are in § Write surface.

## Architectural rules

- **Same concepts as CalDAV, never a parallel invention** (priorities #2, #3). Every CardDAV mechanism that has a CalDAV analogue reuses it: the shared `internal/mda/dav` listener, the `davauth` AUTH lift, the emersion depth-routing, the SRV/well-known builders, the sync-token shape. A CardDAV-only divergence needs a stated protocol reason.
- **Seal-always.** The MDA seals every card write; there is no plaintext-storage mode for `bridge_carddav_cards`. Since S6.12 (2026-07-10) the nest enforces it at the RPC edge: `put_card_ciphertext` rejects an unsealed `encrypted_body`/`encrypted_index_hint` with `fauna.protocol.malformed` (owner: `../architecture/encryption-at-rest.md` § Implementation status). (The storage-mode axis itself is retired nest-wide since Phase 4 — every nest content kind, bridge stores included, is now uniformly sealed with no mode branch at all — `../architecture/nest/storage-modes.md`.)
- **Additive at-rest evolution.** `bridge_carddav_*` columns grow via `reconcile_added_columns`; no drop/recreate of a card table (no-user-data-loss invariant — a vCard the user PUT is user-irrecoverable).
- **No caller reaches another actor's address books — same mechanism as CalDAV.** For a direct Fauna app, nest enforces `request.actor_id == connection actor` for every non-MDA caller (`require_dav_caller_scope`, `bins/fauna-nest/src/bridge_routing_handlers.rs`). **For the MDA** (`CallerClass::BridgeMda`), that gate deliberately lets `target` name any actor — one bridge process serves every user on the box — so on this path isolation rests entirely on the `WHERE actor_id = ?1` predicate in `query_carddav_cards` / `query_carddav_changes_since`, since `addressbook_id` on the wire is a fleet-wide constant for the lazy "Contacts" book (§ Address-book collection model :125) and any two clients naming a book the same slug collide too. Cross-actor isolation on this predicate is covered by `bridge_carddav.rs::query_carddav_cards_is_isolated_per_actor_on_shared_collection_id` and its `query_carddav_changes_since` twin.
