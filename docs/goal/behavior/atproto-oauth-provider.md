## Detailed design

### F4 detail — the OAuth provider

> **Moved 2026-09-05 → [`authorization-server.md`](authorization-server.md) § As built (verbatim):** *Endpoints on the PDS host*, *Client metadata resolution* (+ its four sub-bullets), *PAR — the pre-consent gate* (+ the closed `private_key_jwt` deferral and the ⚠ BOUNDED-not-unlisted correction), *DPoP at PAR* (+ its seven rulings), *Confidential clients* (+ its five rulings), *Consent ceremony wire flow* (+ its ten rulings), *`/oauth/token`* (+ its six rulings), *Grant registry* (+ the no-`revoke_grant` ruling), *`/oauth/revoke`* (+ its four rulings), the ⚠ *grant registry does NOT qualify as access-token revocation* ruling, and *AS-key rotation* (+ its four rulings). What remains below is the ATProto-specific half.

- **Scope model — what this AS advertises, what it accepts, and what the base scope grants.** `scopes_supported` has exactly one binding property: **every advertised scope must be one D8 can grant something under**, or the document lies (a client requests it, the consent screen shows it, the grant records it, and every call still denies). The list is therefore owned beside the matrix that honours it (`authz::GRANTABLE_SCOPES`) and pinned by walking each entry through the real `authorize`, never by re-stating what each ought to permit. **The same predicate decides what a request may ask for** (`authz::scope_grants_something`, one owner, two callers): accepting a *requested* scope the matrix denies everywhere is the identical lie moved one step later — and worse there, because it lands on the consent screen and in the grant, leaving the user having approved something that does nothing and the client author with no diagnosis. A PAR is additionally held to the client's **own declared `scope`** by exact-string membership: the metadata document is the client's public commitment, so a grant wider than it is one the client's users could not have audited. Membership is exact rather than subsuming because the ATProto grammar defines no subsumption relation between a declared `rpc:*?aud=*` and a requested `rpc:x?aud=y`, and inventing one would be a second opinion about scope meaning — the exact fork D8 exists to prevent. One keyed exception exists, owned elsewhere: an arm whose qualifier is the *user's* (the Fauna folder plane) is held to the document's bare declaration ([`authorization-server.md`](authorization-server.md) § Scope grammar → *The folder plane's qualifier is the user's*). The advertised set is the base `atproto`, the two transition scopes, and the wildcard exemplar of each parameterized family (`repo:*`, `blob:*/*`, `rpc:*?aud=*` — the grammar is open, so no exhaustive enumeration exists and the exemplar is both the honest maximum and a real grantable value). **Deliberately absent:** `transition:email` and `account:`/`identity:`, which parse but grant nothing here (no email account model; account management and handle authority live in Fauna, D6); and a collection-narrowed `repo:<collection>`, which is a *deferred* gap rather than an empty one — advertising a narrowing this server answers by refusing everything is worse than not offering it. **The base `atproto` scope grants the `SessionIdentity` lexicon class and nothing more** — basic account identity: who am I (`getSession`) and what is this server (`describeServer`). Narrow deliberately in both directions: it must grant *something*, because every spec-compliant request carries it and a client that could authenticate but not ask who it authenticated as is broken; and it must not grant *more*, because reads, writes, blobs, DMs, the AppView and service-auth minting each have a granular scope whose purpose is to say so explicitly — folding any into the base would make the grammar decorative and the consent screen an understatement.
  - **Session lifecycle is a PLANE boundary, not a scope width** (settled 2026-07-31). `createSession`/`refreshSession`/`deleteSession` are the **app-credential plane's own** lifecycle (D3 rung 1); the OAuth plane's lifecycle is `/oauth/token` and `/oauth/revoke`. So the answer is not a narrower base scope — it is that **no granular OAuth scope reaches them at all**, expressed by splitting the class in two (`SessionIdentity` / `SessionLifecycle`) rather than by a second gate the next reader could forget.
    - ⚠ **The class split alone never delivered that property, and the correction generalises past lifecycle** (2026-07-31 — the earlier finding's conclusion kept, its mechanism corrected twice over). Splitting a class only helps an arm that *reads* the class, and the `rpc:` arm does not: it matches an `lxm` pattern and an `aud` pattern and never asks what kind of operation it just permitted. So `rpc:*?aud=*` — the honest maximum this AS advertises — covered account mutation, session lifecycle and migration alike the moment anything supplied an `aud`, and the pin asserting the boundary passed **only because its probe left `aud` absent**, a second and unrelated condition doing the work the pin named. The property is now a **gate above every granular arm** (`authz::no_granular_scope_reaches`, an exhaustive match so a new class is a compile error): no granular scope reaches `SessionLifecycle`, `AccountMutation` or `Migration` — the three whose subject is *this box's own account and credential plane*, where naming a remote audience does not make the operation someone else's business. The next arm the grammar grows (`include:` permission sets) inherits it by construction. **Two things it deliberately does NOT do:** it does not withhold `Unknown`, because a third-party labeler or feed generator's own NSID classifies as exactly that and forwarding those is the `rpc:` family's whole purpose; and it does not key on "locally served", the shape first proposed — `getServiceAuth` is served locally and supplies an `aud` deliberately (§ F3 detail's two-checks-one-matrix ruling), so that axis would have been refuted by the landed code and "fixed" by breaking it. **What the reviewer named as the real gate — proxied-away plus the `fwdRequestHeaders` allowlist — is also not the whole story:** `proxyForward` mints a *fresh* service-auth token under the caller's own repo signing key before forwarding, so the caller's PDS token is indeed never forwarded, but a new assertion of the user's authority is. **The transition scopes are the deliberate exception:** `transition:generic`/`transition:chat.bsky` are *defined* by the spec as what an app password grants — that identity is why one `implicit_grant` serves both them and the app-credential plane — and narrowing them would make our `transition:` narrower than the ecosystem's, in the one scope family whose whole purpose is compatibility. **The finding's premise about live risk did not hold, and the correction is worth carrying:** all three verbs register `Auth: Public` and verify the app plane's refresh token handler-side, so they never consult the matrix at all (route registration → the frame's `route.Auth != Public` gate → the hook's `caller == nil` early return). The split closes a *latent* trap — a route registration is exactly what this matrix judges, so the day one of them is re-registered as authenticated, the decision must already be made — not a live path.
- **Permission sets (`include:<NSID>?aud=…`) — the resolution plane, ruled 2026-08-03 (the scope-model residual).** The grammar's last un-served family: the client names a Lexicon permission set, and this AS must resolve the set's published document and expand it into member scopes. Resolution is a caller-directed DNS+DID+HTTPS plane whose output feeds an authorization decision — the plane the write path deliberately refused (§ F2's vendored catalog) and this family cannot avoid, so the rulings below exist to bound it. The ecosystem facts they stand on are § Ecosystem reality's 2026-08-03 addendum; until the two build slices land, an `include:` scope refuses at PAR as a scope that grants nothing (the shipped fail-closed baseline — `scope_grants_something` has no arm for it).
  - **Expansion is FROZEN at the ceremony; a standing grant NEVER re-resolves.** The spec makes refresh-time re-expansion a MAY ("the computed permissions for the session *may* be updated"), and this AS declines it: the scope list the consent card showed is the grant's meaning for the grant's whole life. A client that wants the set's new members starts a new authorization flow — a fresh card is exactly where widening belongs, and "incremental authorization" is ordinary OAuth. Three consequences carry the design. **(1)** Token refresh performs **no resolution at all** — there is no refresh-failure arm, and no third party's DNS outage or PDS downtime can narrow, break, or log out a standing session. **(2)** The access token carries the frozen expansion itself, so the resource-server path stays read-free (the ⚠ *does NOT qualify* bullet's constraint, honored rather than re-opened; the AS and RS are the same host, so token size is bounded by our own header limits — the build pins a total-expansion cap per grant, refused at PAR so an oversized request fails at the developer's desk, never mid-session, and a round-trip test proves the max-size token clears our own listener). **(3)** The acknowledged trade: author-side *narrowing* does not propagate to standing grants either — the user approved the wider card, keeping it is consent-honest, and the user's remedy is the connected-apps revoke they already hold.
  - **One expansion per ceremony: computed at PAR, carried through the consent row into the grant row.** PAR resolves and expands (after the DPoP gate and client resolution — an anonymous caller still triggers no fetch), stores the expansion beside the pushed request, and the consent row records it; `fetch_consent`'s read-back rule extends to expansions — the grant records the member scopes **the card showed**, never a re-fetch at `/oauth/token`, so there is no card→grant TOCTOU window by construction. An include whose expansion grants nothing (empty after the ignore rules, or every member denied everywhere by the matrix) refuses at PAR exactly as a dead scalar scope does — the *Scope model* bullet's accepting-a-lie argument, applied to the expanded set.
  - **What bounds the fetch.** Depth is exactly **1 by construction**: a set holds permission objects, never other sets, so an `include`-shaped member is an invalid member and is **ignored** (the spec's own invalid-member precedent) — no recursion exists to bound. Fan-out: at most **8** `include:` scopes per authorization request (hard constant; beyond it the request refuses `invalid_scope` — generous over observed practice of 1–3, small enough that a cold-cache PAR costs a bounded set of resolution chains). Each hop rides the one guarded fetcher's existing size/time caps; a member-count cap per set and the total-expansion cap above bound memory and the grant row. **The set author's own two strings are bounded where they are read, and the whole set payload has a ceiling derived from the caps above rather than chosen (2026-08-03).** `title`/`details` are the one input here the scope grammar never inspects — third-party prose whose only other bound is the proof fetch's own megabyte — so they are **truncated** at the expander, on both the grapheme and byte axes, at the ecosystem's own caps for the same class of text. Truncating rather than refusing is the opposite call from the member-count cap one clause up, and deliberately: a truncated member list silently narrows a grant, while these two strings are *descriptive, not grant-bearing*, and refusing on their account would let a publisher's long prose break a user's sign-in. The payload ceiling is then arithmetic, not judgment: the total-expansion cap measures the **deduped union**, while the payload repeats every member under its own set entry and the hierarchy constraint bounds each set's *namespace* rather than the overlap between sets — so a legitimate family of sets in one namespace carries up to the fan-out cap's worth of copies, and the ceiling is set at exactly that worst case and measured at PAR. Anything narrower would be a refusal invented on this path; anything the *nest* stores that is narrower still is the mid-ceremony 502 the frozen-expansion bullet's "at the developer's desk, never mid-session" forbids, which is why the nest's storage ceiling is pinned against this one over the real encoding rather than restated as a constant. **Failure at PAR fails the whole request** (`invalid_scope`, naming the unresolvable set NSID, before anything is stored — the PAR bullet's refuse-before-storage rule): the spec mandates fail-at-session-start, and a partial grant would mean the user consents to a card missing the set the client asked for while the client believes it got it.
  - **The chain is authenticated end-to-end, and an unverifiable record is a failed resolution.** The NSID is syntax-validated by the pure parser **before any I/O** (parse once, fetch what was parsed). Then: DNS TXT `_lexicon.<reversed-authority>` → `did=<DID>` (DNS stays the ecosystem's root of trust for NSIDs, the same class as handle resolution — named, not "fixed"; results cached short per the lexicon spec's own caution); DID resolution through the existing `atprotoid` trust split (`did:plc` = the fixed directory over the ordinary client, `did:web` = the guarded fetcher); the record (`com.atproto.lexicon.schema`, rkey = the full NSID, at the DID's designated PDS) fetched through the guard **and verified** — MST inclusion proof plus commit signature against the DID document's signing key (a `sync.getRecord`-class fetch), because the hosting PDS is not the authority: most sets will live on big multi-tenant hosts, and the law is that what feeds an authorization decision is verified, never trusted. The lexicon spec specifies no record authentication; this ruling is deliberately stricter. The document cache carries the spec's constants (24 h stale / 90 d expiry, stale-on-failure) and a short negative TTL (the client-metadata precedent) — and note the cache serves only **new ceremonies**; the durable "stale copy" for a standing grant is the grant row itself, which is what makes a bridge restart lose nothing that matters.
  - **Expansion is the pure module's; Go only ever fetches** (§ F3 detail's module-owned-logic-over-caller-supplied-data split, realized). The `fauna-bridge-atproto` expander owns: the `include:` grammar (an **unknown query parameter on an include refuses the scope** — the loopback-client rule: an unread parameter is a configuration the client wrongly believes it made); document parsing; the **same-NSID-hierarchy constraint** (members may name resources in the set's own group or deeper, never siblings or parents — enforced by this module over whatever document arrives, so a hostile or compromised authority can widen only within its own namespace); the invalid-member ignore rules (`inheritAud` ∧ own-`aud` → ignored; unknown member types → ignored; every ignore surfaced as data for logs and diagnostics, never silently); and `inheritAud` application (the include invocation's `?aud=` flows into members that declare it; members with their own `aud` keep it; the output is **ordinary granular scopes**). D8 is untouched: the expansion output feeds `AuthzInput.scopes` exactly as its doc comment has always specified, so `no_granular_scope_reaches` and the whole matrix bind every member by construction — a set may declare what it likes; `SessionLifecycle`, `AccountMutation` and `Migration` stay unreachable. A client-chosen `?aud=` flowing into `inheritAud` members is the **same consented plane** as a directly-requested `rpc:…?aud=…` — the card renders the audience through the same describe path; no new capability exists.
  - **The consent card renders identity + description + the expansion, composed in the shared machine.** The set row is: the set **NSID verbatim** (the identity — never derived from, same as `client_id`), the resolved `title`/`details` (attacker-authored text: the `client_name` control-strip fence extends to these strings **in the same composition pass**), and every member scope through `describe_scope` — members are ordinary granular scopes after expansion, so the existing honest renderer covers them. The set-level description never *stands in* for the expansion: the machine hands every member row to all 7 apps, and collapse affordances are per-form-factor rendering of data that always crosses. `describe_scope`'s verbatim fallback is thereby superseded **for consent surfaces** (a bare `include:` never reaches a card — it is expanded before the row is stored); the fallback itself stays, for grammar this build predates.
  - **Advertisement is a named pin, not a ruling.** `scopes_supported`'s exemplar rule has no honest entry for an open NSID family (`include:*` is not a real grantable value), so whether and how the AS document signals permission-set support is pinned to the build slice: answered from the spec's AS-metadata surface if it speaks, else empirically by F5's reference-client run.
- **⚠ OPEN, for F5 to settle with real traffic: one OAuth sign-in now spends FOUR of the `ClassAuth` budget's ten, and a refresh spends one more.** `/oauth/par`, `/oauth/authorize` and `/oauth/token` share the per-IP `ClassAuth` bucket (10 / 5 min) with `createSession` — the arrangement `ratelimit.go`'s own table anticipated ("createSession + future PAR/token endpoints"), sized when a sign-in was **one** request. It is now four (the by-design nonce-less PAR, its retry, the authorize GET, the exchange), so one IP gets about two sign-ins per five minutes, and every refresh thereafter draws on the same bucket. **Behind NAT or CGNAT that is shared by everyone at the address**, and it is worth naming why the fit is uneasy: `ClassAuth` is tight because `createSession` is a *guessing* surface, whereas a refresh request carries a 256-bit token **and** a DPoP proof signed by a key the caller must hold — nothing to guess. The disposition for now is deliberately the **conservative** one (leave it; tightening is safe, loosening on a hunch is not, and § Detailed design already records these constants as "F1/F2 tune before ship"), but the shape of the fix if F5 shows real clients tripping it is to give the **refresh grant** its own budget rather than to raise `ClassAuth` — the guessing surface and the possession-proving one do not belong in one bucket. *(Surfaced 2026-08-01 by slice 7's own tier_3 run: the added token calls exhausted the module's budget and 429'd the next ceremony.)*
  - **Re-decided by the issuer's move onto the nest (TP5 S2), and the move settles it rather than tuning it.** The bullet above is a sizing complaint resting on one structural fact: the AS endpoints share `ClassAuth` **with `createSession`**, so a possession-proving surface and a *guessing* surface draw on one bucket — which is why it names "give the refresh grant its own budget" as the fix and "leave it" as the conservative disposition until F5 shows real clients tripping it. On the nest that premise is simply gone: `createSession` is an ATProto XRPC method on the PDS bridge, and the nest's issuer shares no budget with it or with any other guessing surface. The uneasy fit is therefore not tuned away — **it ceases to exist**, and the endpoints get per-route buckets of their own because there is no longer anything to share one with. `/oauth/{par,authorize,token,revoke}` each meter per source IP, and **the refresh grant meters separately from the authorization-code grant** — the recorded fix shape, reached by the move rather than by F5 traffic. ⚠ **What this does NOT do is loosen a number on a hunch:** each per-route bucket keeps `ClassAuth`'s own 10-per-5-minutes rather than a larger figure invented here, so no single endpoint is cheaper than it was; what changes is that a sign-in no longer spends four from one bucket, which was the measured defect. **Still open, and still F5's:** whether those numbers are right against real client traffic. The bridge's own arrangement is untouched while it still serves the endpoints, and retires with them. **Built as of TP5 S2's second step** (`bins/fauna-nest/src/oauth_as_rate_limit.rs`, with `/oauth/par`, the first endpoint that spends it): fixed-window per-(route, source) counters at the ported limit, applied as a `tower::Layer` on a per-endpoint sub-router so the ordering ruling — the endpoint's budget before the body — is structural rather than a comment about line order, and so a refusal carries no `DPoP-Nonce` (the nonce is the handler's, minted for requests the server has agreed to consider). One departure the nest needed and the bridge did not: a **loopback** source is metered against a separate aggregate ceiling rather than the per-IP one — bounded, not exempt, the posture [`../architecture/transport-connection.md`](../architecture/transport-connection.md) § Abuse posture ratified for the blanket governor — because the deployment's own co-resident callers, the e2e harness above all, would otherwise exhaust a budget sized for one stranger's first contact.
  - **Re-decided for `/oauth/token` alone by the polled consent starts (2026-09-26).** The typed-code and quiet-push starts ([`authorization-server.md`](authorization-server.md) § Consent) end with a client polling the token endpoint every 5 seconds by design — twelve requests a minute from one well-behaved device, `ClassAuth`'s whole five-minute allowance in under a minute — so at the per-route `ClassAuth` numbers above the grant RFC 8628 defines would refuse its own clients. So the token endpoint's layer is **poll-class** (the consent page poll's numbers, 60 per minute per source), and the two grants that are NOT polled each keep `ClassAuth`'s 10-per-5-minutes in a bucket of their own, spent after `grant_type` is parsed: the refresh grant's (already built) and now the authorization-code grant's. That keeps the ruling above intact — neither non-polled grant is cheaper than it was — while the endpoint stops starving the grant that must poll it. A polled grant needs no bucket beyond the layer: its handle is 256 bits, and per-flow `slow_down` pacing bounds what one client asks. Every other route keeps `ClassAuth`, the two start endpoints included. **Still F5's**, as above: whether any of these numbers is right against real traffic. Built in `bins/fauna-nest/src/oauth_as_rate_limit.rs` (`TOKEN_ENDPOINT_BUDGET`, `AUTHORIZATION_CODE_GRANT_BUDGET`).
  - **The ordering ruling binds, so the refresh bucket is spent one step later than the endpoint's.** § As built's `/oauth/token` ruling puts the per-IP limit **before the body is read**, which means no layer above the handler can know the `grant_type` — the fact that selects the bucket. The two are therefore spent at different depths and both before any state is touched: the endpoint's bucket ahead of the body, exactly as ratified, and the refresh grant's after `grant_type` is parsed but ahead of every lookup. That is additive to the ordering rather than a relaxation of it — the ruling's actual guarantee is that **every refusal precedes a write**, and nothing is written at either depth.
- **⚠ A route's declared auth CLASS is a claim about which planes may reach it, and every plane-level check below it is unreachable on a route whose class excludes the plane (found 2026-08-01 by slice 7's tier_3 run).** `com.atproto.server.getSession` was registered `AppSession` — correct while the app plane was the only one, and wrong the instant an OAuth token could exist: it made the base `atproto` scope unusable against **the one method that scope is defined to cover**, so a client could authenticate and then not ask who it had authenticated as, which is exactly the brokenness the *Scope model* bullet's narrowness argument rejects. Neither side's unit tests could see it — each was right about itself; the four-process run answered `401` on a token everything else had accepted. The route is now `Session` (either plane), and the general rule is pinned as a **sweep over the whole route table** rather than a per-route assertion: no route may be app-plane-only unless something decided that deliberately, with its own ruling here. **When a new credential plane lands, every route's class is a decision to re-make.**
- **The resource-server plane: `Authorization: DPoP`, and the scheme selects the plane.** An OAuth access token is presented with the DPoP scheme plus a per-request proof carrying `ath` (the presented token's hash) — the mode the shared module gained here, where at an *authorization-server* endpoint `ath` is refused and at a *resource server* it is required. Three checks make the binding real: the proof is over this request (`htm`/`htu`, built from our own published origin and never the caller's `Host`), its `ath` is this token's, and the proving key's thumbprint equals the token's `cnf.jkt`. ⚠ **Dispatching on the scheme is the security property, not a convenience:** the `Bearer` branch never reaches the OAuth verifier, so a `cnf.jkt`-bound token can never be honoured as a bearer credential. The liberal "try both verifiers" shape would discard the binding the whole plane exists to provide, with nothing failing to say so.
  - **This plane ISSUES a nonce on every response, because it REQUIRES one (added 2026-08-03).** Slice 7 inherited the DPoP gate's nonce requirement without its issuing duty: every OAuth-plane XRPC request needed a live server-issued nonce, and no XRPC response ever carried one. Since a nonce lives 4 minutes and an access token 15, a client was refused for the last eleven minutes of every token — and the refusal was the uniform `AuthenticationRequired`, byte-identical to a forged token, so a correct client had nothing to act on. It self-healed only when the client spent a **refresh rotation**, whose AS round trip re-harvested a nonce, which is why the shipped defect read as flakiness rather than as a broken plane. **The duty is now structural rather than remembered:** the frame issues the nonce for any request presenting the plane's scheme, decided from the same single reading of `Authorization` that selects the verifier, ahead of routing and rate limiting — so a 200, a 404, a 429 and an authz refusal all carry one, and no future route can be added without it. ⚠ **Issuing on refusals is the load-bearing half, twice over:** the refusal is the only response by which a stranded client can learn a fresh nonce, and issuing on *all* of them is what stops the header's presence from itself distinguishing one refusal from another.
  - **`use_dpop_nonce` is the ONE refusal this plane distinguishes, and the widening stops exactly there.** The frame answers it `401` with `WWW-Authenticate: DPoP error="use_dpop_nonce"` (RFC 9449 §7.2) while the response **body stays byte-identical** to every other refusal; a forged token, a wrong `ath`, a `cnf.jkt` mismatch and an unknown account all remain uniform. Telling the client this one fact leaks nothing — nonces are public and this server hands them out on request — whereas the others are the enumeration signal § Security posture summary forbids. Two structural properties keep the exception from spreading: the challenge is reachable **only below access-token verification**, so it is never an oracle about the token (a caller receiving one already holds a credential this AS signed), and it is unreachable from the `Bearer` branch, so the app plane cannot produce a challenge for a nonce it has no concept of. ⚠ **The repair deliberately did NOT drop the nonce requirement** — that is the cheapest-looking fix and it deletes a replay defence; the availability bug is fixed by supplying what the plane demands, never by demanding less.
  - **This plane keeps its OWN `jti` replay set, and the split is a privilege boundary rather than bookkeeping (decided 2026-08-03).** Slice 7 made the resource server a third caller of the one set PAR had sized and the token endpoint had re-decided, so neither decision had been taken for it. **Direction: unchanged — evict nearest-to-expiry and log.** The finding is right that the companion artifact differs (at `/oauth/token` a proof accompanies a code or refresh token that is single-use at its own store; here it accompanies a 15-minute *multi-use* access token, so an evicted `jti` re-opens a replay whose companion is not spent), but that changes what an eviction COSTS, not which way to fail: the replay buys a duplicate of exactly one already-captured request — `htm`, `htu` and `ath` bind the proof to that one — for an attacker who already holds the captured pair, i.e. who already has TLS compromise. Failing closed instead refuses **every call of every live session** while the set is full, as the uniform `AuthenticationRequired` a client cannot act on: the very plane-wide outage the bullet above had just fixed, and strictly worse than at PAR, where a refusal only delays a new sign-in. **Instance: separate, and that is the half that was actually missing.** The decisive fact is not the companion artifact but the PRIVILEGE each plane's entries are reachable from — recording here requires an access token this AS signed (token verification runs before the gate), while recording on the AS plane requires nothing at all, since `/oauth/par` is anonymous. Shared, one budget served both, so **an anonymous flood needing only source IPs degraded the replay defence protecting authenticated sessions**; separated, each plane's defence can only be degraded from its own privilege level. Which set a call uses is derived from the `ath` rule — already the one fact that distinguishes the planes — so a future gate caller cannot silently inherit the wrong one, the same single-classifier discipline the nonce fix applied to `Authorization`. **Capacity is re-derived per plane, against the budget that actually governs each.** The AS set's ground (`ClassAuth`, 10 requests / 5 min per IP → 8 entries per source IP per 4-minute window, so 8192 ≈ 1024 peers at their ceiling) governs nothing on the resource server, where an XRPC request spends its ROUTE's class: ClassAuthed 120/60s + ClassWrite 30/60s + ClassBlob 20/60s = **680 entries per source IP per window, 85×** the AS plane's — twelve maximum-rate peers against the inherited 8192. Raised to 65536 (≈96 peers at the ceiling, ≈550 at an ordinary polling client's rate), bounded in memory because the key is bounded (`jkt` 43 chars + the shared module's 256-char `jti` cap). ⚠ **Unlike the AS set this one can be driven to evicting a live entry by a plausible population** — restoring a 1024-peer margin would cost ~700k entries — which is why the eviction warning naming its set is load-bearing here rather than merely tidy: it is the only witness that the degraded window opened, and which set it names is the difference between an anonymous flood and one costing the attacker valid tokens.
- **Acceptance test:** the TS `@atproto/oauth-client-*` reference clients complete the flow (no conformance suite exists — § Ecosystem reality).
