## Goal

A WebDAV files surface per nest deployment, **served by the mail-bridge MDA role** (the same process serving IMAP + CalDAV + CardDAV — one TLS termination, one WS connection, one AUTH), implementing RFC 4918 (Class 1 + conditional requests) over the user's **existing folders**: a generic WebDAV client (GNOME Files, KDE Dolphin, macOS Finder, Cyberduck, rclone, the NextCloud apps' WebDAV mode; Windows Explorer read-only until Class-2 LOCK lands — § Protocol surface) pointed at `https://mail.<domain>/webdav/{user}/` browses, downloads, and uploads the folders the user has explicitly flagged for serving.

**Bar: parity-or-better with NextCloud's WebDAV files surface** for generic-client read/write access. A WebDAV write is an ordinary folder change — it propagates to every synced device through the normal orchestrator path, and sync-device edits appear to the WebDAV client as new ETags. **When in doubt, choose the stricter option** (the sibling docs' rule).

## What the WebDAV namespace *is*, in Fauna terms

**A view over the existing folder substrate — never a mirror store.** (CardDAV built `bridge_carddav_*` because no address-book store existed; a mirror for files would double bulk storage, break convergent dedup, have no write path, and go stale on every sync-device write the MDA can't read.)

```
/webdav/{user}/                                  ← root collection
/webdav/{user}/{folder-name}/                  ← one collection per served set
/webdav/{user}/{folder-name}/<relative-path…>  ← the set's files (normalized, forward-slash)
```

A third-party principal's bearer request names a folder by its id instead — `/webdav/{user}/{folder-id}/` (§ Key model → *A principal's read*, (6)).

Every **non-reserved** folder the user has flagged "serve over WebDAV" is exposed (per-set opt-in, default OFF — § Enablement). A folder has no type ([`folders.md`](folders.md) § Target re-model), so the former sync-type-only gate is retired (ruled 2026-09-28, the folders mode contraction design pass; built 2026-09-28): **served ⇔ `webdav_enabled` ∧ not reserved** — one shared predicate at the nest's four read sites (the update door's serve-on refusal, the mint gate, the bridge's folder filter at both its sites); every app's owner row paints the OWNER'S word for it instead — custody's serve window, [`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, ruling (7)(b)(ii). What is never served: reserved `__*` sets (the update door refuses a reserved name whole — `reserved-folders.md` § the management surface — and the read sites keep the structural conjunct as defence in depth, since serving a rail would expose its segment files and let `webdav_record_change` write into it), a `public`-audience folder and a metadata-only folder (the pairwise refusals, § Enablement point 2). A website-published folder is served like any other — its website plane is a separate fan-out, not a type — and so is a folder whose only originating device is an ingress (a DAV write is an ordinary owner write to the head; which devices receive it is each device's place).

## Key model — M2 content keys via the MSEK-sealed `WebdavKeysBlob` (ratified 2026-07-06)

File chunks today are sealed under the owner's `BackupKey`, which rule #7 (`../architecture/key-material-hierarchy.md`) forbids the MDA from ever holding. The ratified model:

- **A WebDAV-served set is content-key-sealed** — the M2 per-folder content-key mechanism (`mls-group-key-material.md` § M2: `FolderContentKeys` generations, convergent `chunk_crypto` sealing, ciphertext-hash store keys, generation stamping, fail-closed engines, rotate-on-removal, folder-key custody — the `fauna.state.folder-keys` account-plane kind). A fresh set created with serving on is born content-key (genesis at create); flipping an existing `BackupKey`-sealed set to served runs a **one-time client-side re-seal migration** (the owner's client re-chunks/seals under a genesis content key; old chunks become garbage only after verification — no-user-data-loss). The same migration slice fixes the shared-folders pre-bind history gap (tracked internally, appended 2026-07-06). **Who performs that migration for a file no driven engine holds** — every file of an owner whose apps run no sync agent, and any file an app's Media page recorded before the flip — is ruled in the *app-side seams* bullet below, (c): the flipping client itself, nest-sourced.
- **The MDA's capability is the served sets' content keys**, delivered via a new **`WebdavKeysBlob`** — per-actor, sealed under **MSEK** (the exact sibling of `MlsSnapshotBlob`; `owner-key-material.md` § Path B-sibling-3), stored opaque on nest (`bridge_webdav_keys_blobs`), provisioned by the user's client (`fauna.bridges.provision_webdav_keys_blob`, User-class) and fetched by the MDA (`fetch_webdav_keys_blob`, BridgeMda-class). Plaintext: per served set `{set_name, read_only, FolderContentKeys generations}`. At MUA AUTH the MDA unwraps MSEK (existing flow) → additionally unseals this blob → holds the keys in the same zeroized mlocked session memory, gone at session end. The client re-provisions on any served-set or generation change.
- **Revocation:** unflagging a set rotates its content key (the existing rotate machinery — exactly a member removal) and re-provisions the blob without it. **The owner's own back-catalogue converges to the owner root, not just the MDA's capability** (fixed 2026-09-13 — until then `fauna_core::crypto::effective_owner_key`'s 2026-09-09 fix, which made a content-keyed set's chunks never owner-keyed, had made the reverse transition — unflag, then read as the owner — silently impossible: `resolve_engine_key_binding` correctly degrades the disabled set to `Unbound` (owner-only), but the owner's own engine then held no key that could open what the served window had sealed under the M2 content key it just rotated away from): the owner's folder-key custody (`fauna.state.folder-keys`) retains every rotated-out generation (this bullet's own "rotates … rather than forgetting" — nothing is deleted), and `SyncEngine::set_retired_content_keys` offers that retained history to the now-owner-only engine as a **read-only** candidate — for a file's bytes and its sealed name alike (`FileDownloadKeys::label_open_roots` took the retired generations only from 2026-09-24; before then the engine opened a served-era file's bytes and never its name, so the file silently never landed) — a separate field from the engine's live `content_keys`, so it can never re-trip `effective_owner_key`'s `content_keyed` gate — beside the owner-key axis's own `predecessor_backup_keys`. The shared `SyncEngine::reseal_predecessor_sealed` walk (generalized rather than duplicated: it already asks "does this open under my current root", regardless of which retired root a chunk rests under) then re-seals the served-era back-catalogue under the owner's `BackupKey`, sourcing bytes locally when materialized or from the nest under the retired candidate otherwise. The walk runs only where an engine is *driven*, and since 2026-09-25 that is the bearer-only `bins/fauna-sync-agent` process alone: every location binding is the agent's, and the in-process resident half `fauna-ffi` once offered iOS and Android retired unused (`sync-engine-deployments.md`), so their construct-run-drop `build_engine` hosts never re-seal. That bearer-only agent builds every engine through the same `build_engine` since 2026-09-28 (`on-demand-files.md` § Shared sets on a capability host → *One mechanism*, question 2), so the retired generation reaches its engines by the very wiring above — `retired_serve_custody` over the custody its seed-less build loads, set beside `set_predecessor_backup_keys` (the matching widening first landed 2026-09-13 in the agent's own, now-retired builder) — and all four desktops (linux, macOS, Windows, tui) converge a disabled-but-previously-served set's back-catalogue. **On-demand (cfapi placeholder) roots run no reseal walk** (`bins/fauna-sync-agent`'s always-resident loop is the only caller of `reseal_predecessor_sealed`): there the retired candidate only restores **reads** of the served-era back-catalogue, never re-seals it onto the owner root — parity with how a retired owner key already behaves on an on-demand root. The apps' name-keyed read surfaces (the Media page first) hold the same retired candidates through the shared resolver (the *app-side seams* bullet below, (a)), so an unflagged set's served-era rows keep listing in-app without an engine. **Unflagging also adopts the served era (ruled 2026-09-30; BUILT 2026-10-02 — § Implementation status today):** before the flag falls, the owner's device signs every WebDAV pseudo-device row of the set in place and the nest refuses the flip while one is unsigned — the ruling, the kind and its refusal are [`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, ruling (7)(b). **The served state every reader judges the exemption by, and the sets this blob is provisioned for, are the owner's custody — not the nest's flag — under that doc's ruling (7)(b)(ii) (ruled 2026-10-02, NOT built; § Implementation status today).**
- **Blast radius (rule #7, widened deliberately at ratification):** a leaked bridge credential reaches mail + calendar + address book + **the explicitly-served folders** — never unserved sets, never account state/drafts/backups/`__mls`. Per-set, opt-in, revocable.
- **Custody note (mechanism ratified 2026-07-07):** `FolderKeyCustody` keying extends to sets without an MLS group via the **serve pseudo-channel** — `fauna_core::folder_keys::serve_custody_channel_id(name)` = `blake3::derive_key("fauna.folders.serve.v1", name)`, the same `[u8; 32]` shape as a derived `ChannelId` (no at-rest custody schema change; older devices decode + union-merge the entry verbatim), cryptographically disjoint from real channels (distinct context) and stable (sets have no rename; the nest addresses by `(name, owner)`). Sharing a served set later migrates custody pseudo→real inside `bind_set` (`custody::migrate_set_identity` — generations preserved, so stamped `content_key_version`s stay resolvable and members receive the served-era back-catalogue). A set both shared and served works unchanged — custody at the real `ChannelId`; members via the MLS envelope, the MDA via the blob; rotation re-provisions both. Every consumer resolves the custody identity through the one shared `custody_channel_for` (`fauna-client-folders::engine_binding`) — over the summary today, over the owner's custody entry once [`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, ruling (7)(b)(ii) is built: that ruling moves the served state itself, this blob's set selection and every reader's class exemption onto the owner's custody, and names what keeps reading the nest's flag.
- **Read AND write both work** because `chunk_crypto` is symmetric AEAD, and **both legs ARE the sync engine's own pipeline, whole-file, over the FFI — never a per-chunk primitive the Go side composes** (hardened 2026-09-03): GET = fetch manifest + chunks by store key, then `webdav_open_file` — the apps' shared `download_file_bytes_by_manifest` walk: generation selection (`keys_for(version)` — every same-version candidate is tried, `mls-group-key-material.md` § M2 *Generations*), AEAD open, unframe decided by the manifest's plaintext hash, whole-file verify; PUT = `webdav_seal_file` — the engine's `seal_blob` (chunk + the one `chunk_seal` frame→seal→re-key door, under `current`), upload, record the change stamped with the generation the seal reports. The reason it is the whole pipeline and not "chunk + `encrypt_chunk`": the chunk plane derives its (key, nonce) from the **unframed** plaintext hash but encrypts the **framed** body, so a second writer that frames differently (the MDA sealed raw until 2026-09-03) rests two plaintexts under one nonce — a two-time pad — and no reader ever errors on it. `mls-group-key-material.md` § Per-chunk file-sync key owns the invariant; the AEAD primitive is crate-private in `fauna-core` since then.
- **Sealed names & paths (ratified 2026-07-29; the MDA leg BUILT 2026-07-29 — build-out status owned by `path-sealing.md` § Sealed names & paths):** the MDA unseals listing rows' `path_sealed` per AUTH'd session under these same already-held content keys (via the shared-Rust FFI `webdav_render_paths`, never a Go reimplementation) and seals the path on every recorded write (`webdav_seal_path`, under the set's `current` generation — PUT, the delete tombstone, and both COPY/MOVE legs, so no DAV write is a keyless seam); the DAV hierarchy synthesis keeps operating on session-memory plaintext, the nest-side ETag head lookup re-keys to `path_hash`, and set names keep coming from this blob (which already carries them sealed). A row this session's keys cannot open is **omitted** from the listing per the ratified degrade — never a blank href, never a failed PROPFIND. **The 2026-08-02 contract flip retired the legacy-plaintext fallback** (`path-sealing.md` § Sealed names & paths owns the mechanism): a sealless write is now refused loudly (`fauna.bridges.path_seal_required`) at the `webdav_record_change` entry point rather than resting an unsealed row — since the MDA is co-deployed with the nest and seals every record it forwards (`webdav_seal_path`), this fires only on a wiring bug, never in normal operation.
- **The app-side seams — the Media page and every name-keyed reader/writer an app runs without an engine (ruled 2026-09-26):** a served set's custody is ONE identity, so the shared resolver the apps' read surfaces and the Media page hold (`fauna_core::folder_keys::FolderKeyResolver`; production impl `fauna_client_folders::NestFolderKeyResolver`) answers it exactly as the engine side's `resolve_engine_key_binding` does — through the same `custody_channel_for` and `retired_serve_custody`, never a second derivation. **(a) Reads and label seals.** An owned, group-less, served set resolves **content-keyed with no group id** (`ResolvedCustody::ContentKeyed` with `mls_group_id: None` — the read-side twin of `EngineKeyBinding::ServedUnshared`), its generations from the serve pseudo-channel; keys absent there resolve content-keyed-but-unresolvable, so every seal site fails closed and no chunk read falls through to the owner key (`FileDownloadKeys::served`, the twin of `ServedKeysMissing`) — never the owner root, and never a faked group id to reach the content-key path. A served-then-unflagged set resolves owner-only **plus** the served window's rotated-out generations as read candidates (`ResolvedCustody::OwnerOnly { retired_content_keys }` → `FileDownloadKeys::retired_content_keys`, the reader twin of the agent's `set_retired_content_keys`), so the Media page lists what the mount wrote and keeps listing it after the unflag. **(b) Writes.** An app upload into a content-keyed set — served, or bound to a sharing group, the one rule for both — is **the sync engine's own whole-file seal, never a Media blob primary**: `fauna_core::blob_seal::seal_blob` under the set's `current` generation (the module moved down from `fauna-sync-engine` for exactly this consumer; `webdav_seal_file` and the engine call the same function, so the artifacts are byte-identical across the three writers), the chunks then the canonical manifest over the byte routes (`POST /api/v1/chunks` keyed by ciphertext hash, `POST /api/v1/manifests`), the change recorded stamped with that generation and its path sealed under the same root — so the MDA, a synced device and a member all open it through the one `download_file_bytes_by_manifest` walk. Keys not yet in this device's custody → the gesture refuses with a page error and uploads nothing (fail closed); a foreign-homed set → refused likewise (this session holds no write token there). A blob primary is the shape only Media could ever open (`../ui/media.md` § Encryption at rest → *Content-keyed sets* owns the page's statement). **(c) Who re-seals the pre-serve back-catalogue.** The one-time re-seal (first bullet) is **the owner's client's duty, for every file, on every platform** — the promise stands; the desktop agent's local walk (`reseal_pending_under_current`, the Revocation bullet) is its fast path, not its only path. For a file no driven engine holds — every file of an owner whose apps run no agent (iOS, Android, web-only; `../architecture/apps/sync-agent.md` § Scope per platform), and any file an app's Media page recorded before the flip, on any platform — the **flipping client** converges the set's nest-resident heads itself, in shared Rust, right after `FoldersAuthor::serve_set(enable)` succeeds (`fauna_media_machine::served_reseal`, wired by every face through `fauna_client_folders::served_set_converge`): the set's change log folded latest-per-path, each head not stamped at the set's current generation **judged first by the shared verified-row judge** (`fauna_client_sync::row_judge` over `sync_row_verify::RowReader`) — an **unstamped** head opens under the owner root only when it verified as this account's own signed record of this set (`../architecture/writer-signed-change-records.md` § Writer-signed change records, ruling (5), the (D) enabler, set per record through `FileDownloadKeys::owner_signed_record`), and every other head (unsigned, no nonce, another writer, another set's nonce) is skipped, warned and counted, never re-sealed, since the owner root would open it and the re-seal would publish it to the mount; an admitted head is fetched in either shape `MediaMachine::download_file` reads (a Media blob primary, opened whole under the owner's bare key after its address check and re-sealed through the same `seal_blob` pipeline as (b); or a chunk manifest, re-sealed a window at a time through `fauna_core::nest_reseal::reseal_nest_copy_windowed`, the very function the engine's nest-bytes source runs), verified under the served generation alone, recorded as a `modify` stamped with the generation, signed through the seat's writer key (birth-shape signing) under the app's recording device (the one its Media gestures record under — each face passes it), a proven reissue (`derived_through` = the head's seq, `is_resolution`), its path sealed under that root, and its pre-re-seal rows superseded best-effort for GC (`fauna.sync.changes.supersede`). The order is the engine walk's, nest-sourced instead of disk-sourced, save that the verify precedes the record (this walk's only resume anchor is the nest head, so nothing is recorded that has not opened); idempotent under the deterministic seal, so a crash mid-walk — or a walk that could not start because the set's custody had not synced to this device yet — resumes at the next app start, never waiting on a re-flip (a re-flip is an unserve, which rotates the key): the folder launch resume every face already runs (`FoldersAuthor::resume_pending_removals`) re-drives the same walk over every owned, served, group-less set (`FoldersAuthor::converge_served_sets`), under the same recording device, cheap when nothing is owed (one set list, one change-log read per served set, nothing recorded). **Scope: served, group-less sets only** — a set bound to a sharing group is the M2 pre-bind pass's, run where the owner's engine lives (`../architecture/mls-group-key-material.md` § M2 → *Pre-bind re-seal migration* (C)), and the walk refuses it rather than become a second driver of that pass. **Coexistence with the agent (decided 2026-09-29):** the walk runs on every flip, a desktop whose agent binds the set included — the app cannot see whether an agent binds it, and for a chunk-manifest head the agent's own pass (armed by its custody re-read on the serve nudge) produces identical store keys and an identical manifest for the same bytes, so the two converge: dedup, not conflict, and whichever records second re-points the head at the same manifest. A Media blob primary is this walk's alone — the agent's pass moves a primary only between owner roots (the succession re-seal), never onto a content key.

- **A principal's read — the bearer door's key delivery (ruled 2026-10-05; the consent-time twin BUILT 2026-10-05 (wired on tui), the door BUILT 2026-10-05 — § Implementation status today).** The two sentences of § Independent enablement → *Third-party read + deposit* left open how the MDA opens a served set for a request that carries no MSEK. Ruled: **the principal lends the keys it holds, request by request** — the bearer door's second credential is the opened read twin. **(1) The twin is a grant, not a blob.** `fauna:folder:read:<id>`'s twin is the existing `content.read{folder, set}` tuple `fauna_client_capabilities::mint_folder_grant` already mints to the web-serve holder for a paywalled set (one wrap per content-key generation from the owner's custody; `set` = the set-name hash) — minted to the principal's attested X25519 key at consent by the approving app's shared machine (the records arm's path, [`../architecture/third-party-kinds.md`](../architecture/third-party-kinds.md) § The record doors → *Who mints the consent-time grant*; the seam that machine gains is the owner's folder custody — the one shared resolver the Media page and the engine binding already hold, answering a folder id's set name, its served state and its generations, fail-closed `Unwired` as the records path is), fetched by the principal over its own session (`fauna.capabilities.fetch`), ended with its principal (`fauna.principals.revoke` deletes every grant to the key), listed, reconciled and logged like every grant. **Its grant shape (ruled 2026-10-05): one grant per (principal, folder), under a derived id — never a tuple of the consent's records grant.** Each `folder:read` scope an approve covers is minted as its own grant to the principal's holder key, id `folder_principal_grant_id(owner identity secret, holder X25519 key, set name, generation)` — `blake3::derive_key` under its own domain string over `secret ‖ holder ‖ generation ‖ name` (three fixed-width prefixes, the generation a big-endian `u32`, so the name needs no length tag), the shape `folder_paywall_grant_id` derives the web-serve paywall grant by, plus the holder (*The generation* below; amended 2026-10-05); both derivations live in `fauna-client-capabilities` beside `mint_folder_grant` — with its own `Mint` event, planned, recorded and deposited by the same consent entry point beside the consent's one records grant ([`../architecture/third-party-kinds.md`](../architecture/third-party-kinds.md) § The record doors → *Who mints the consent-time grant*, amended to this). Why: the twin has a lifecycle the consent grant does not — renewed on every rotation of its set, revoked on its unserve, per folder (rule (4)) — and the owner has no other handle on it: the wire offers no owner-side enumerate, and the signed `GrantEvent`'s field set is frozen (`fauna_core::grant_event`), so the log cannot carry a tuple's `set`, and a fold into `kind` or `tier` would read as a factor or a regime marker to every existing reader. A derived id names the grant from what every device of the owner holds — the secret, the roster's holder key, the set name, the generation — with no persisted grant-id state. **The generation — the one input a `Revoke` changes (ruled 2026-10-05).** The owner's log treats a revocation as terminal by presence: `fauna_core::grant_event::latest_live_events_of` drops every event of an id that carries any `Revoke`, so a same-second merge tie can never resurrect a revoked grant, and the reconcile sweep revokes on the nest every id that fold does not hold live (`grant_log::unrecognized_grant_ids`; [`../ui/nests.md`](../ui/nests.md) § Trust facet — grants → *Reconcile*). An id derived over (secret, holder, set) alone would be dead after its first `Revoke` — a principal revoke, a key replacement, rule (4)'s unserve, a withdrawn approve — and every later re-mint under it (the same key consenting again, a folder unserved, re-served and requested again, an approve retried after a withdraw) would rest on the nest unseen by every owner surface and be ended by the owner's own sweep, which [`../principles.md`](../principles.md) § The user always controls their data rules out. So the id carries a generation, and **one walk is both the finder and the minter**: for (holder, set), walk `n = 0, 1, 2, …` deriving `id(n)` — an id the log holds no event for is the next free generation (stop: nothing is live); an id carrying a `Revoke` is spent (continue); any other is the live generation, and the fold's current grant under it is the principal's grant over the set. A mint always goes to the first unspent generation: a live one is re-minted in place under its own id, a spent prefix is skipped and the next generation is fresh. The walk reads the log alone — every device of the owner shares it and it merges by union — so devices with merged logs agree on the generation, and concurrent approves from equal logs converge on one id. Terminal revoke is untouched: each generation is its own id, and the walk never steps back to a revoked one. **The web-serve paywall grant carries the same generation (built 2026-10-05):** `folder_paywall_grant_id(owner identity secret, set name, generation)` derives over `secret ‖ generation ‖ name` under a `v2` domain string (the gen-less `v1` ids are unlogged, so the reconcile sweep ends any still resting on a nest and the launch keep-alive re-mints the set at generation 0), and its walk is this one — `derived_grant_generation`, one walk over an id-deriving closure for both grant kinds. `paywall_set` mints at the walk's generation, the rotation leg and the launch keep-alive renew the live one (or, for a set still paywalled with none live, mint the next), and `unpaywall_set` revokes the live one and records its `Revoke`: an unpaywall spends a generation, and the next paywall mints a fresh one the log reads live. **Accepted residual:** a device whose log lacks a sibling's not-yet-merged `Revoke` mints the spent generation again; the merge poisons it, the sweep ends it on the nest, no owner surface ever showed it live, and the next approve mints the next generation — a narrowing the nest could effect alone, zero new power to anyone. Why not the consent id: it is fresh per ceremony, so a retried approve could never replace in place, and the frozen `GrantEvent` cannot carry a `set`, so the finder could not name the set. Why not a terminal revoke relaxed for this class: it is the merge's safety property for every grant. Prior art for a derived replacement id: the succession re-mint's `remint_grant_id` (`fauna_client_capabilities::succession`). It is derived over the HOLDER KEY, not the `client_id`: a key replacement ends every grant to the old key and the same approve mints fresh ones to the new ([`../architecture/third-party.md`](../architecture/third-party.md) § The principal model → *Key replacement*), so the ids move with the key. A re-consent naming a folder the principal already holds re-mints in place under the live generation's id and the nest replaces (`put_capability_grant` is `INSERT OR REPLACE` on `(owner, grant_id)`): one grant per (principal, folder) at any time, and an approve retried after a lost reply converges. **A withdrawn approve ends only what it began (ruled 2026-10-05).** An approve deposits its grants before the resolve, and a resolve that does not land withdraws them (`fauna_atproto_settings_machine::consent_grant::withdraw`: the nest first, then the signed `Revoke`s). A folder twin the approve minted FRESH (the walk found no live generation) is withdrawn like the consent's records grant. A twin the approve re-minted IN PLACE over a live generation is left standing as re-minted: the principal's earlier access was the owner's earlier approve, a revoke here would end it, and what the re-mint changed is the owner's own act on the card — the set's wraps (what the earlier grant already lent, plus any generation rule (4) would have renewed in) and the approve's window, which stands. The planner therefore reports, per twin, fresh or replaced, and the withdraw revokes the fresh ones only. Two folders are two grants; the records tuples and the keyless `deposit` twin stay in the consent's one grant, which has no key lifecycle of its own. **The owner finds a principal's folder grants over a set in its own log, never on the nest:** the current grant carrying a `content.read{folder}` tuple to the holder whose id the generation walk over that holder and the set's name reaches live — the log is the owner's record of what it minted (record-then-deposit), so it is complete. **A folder read grant to a principal is a principal grant** on every owner surface — the trust facet, the history lens, the `Revoke`s recorded for `fauna.principals.revoke` and a key replacement — under the one predicate [`../architecture/third-party.md`](../architecture/third-party.md) § The principal model rule 4 owns (`view_model::is_principal_scope` admits the twin beside the `ext.*` kinds; the web-serve paywall grant shares the tuple but can never sit under a roster principal's key — the nest's `refuse_foreign_holder` refuses a consent attesting a bridge's key). Which folder a grant covers is answered by the same walk over the owner's sets, never by a log field. A second per-principal blob table (the 2026-09-05 wording's "`WebdavKeysBlob` generalized to a principal") is rejected: it would re-create provision, fetch, revoke and audit for one holder class the grant plane already serves. **(2) Served sets only.** The twin is mintable only over an owned set the owner's custody marks served (ruling (7)(b)(ii)): an unserved group-less set rests under `BackupKey`, which no grant may wrap ([`../architecture/key-material-hierarchy.md`](../architecture/key-material-hierarchy.md) § Don't do these), and serving is the owner's one explicit exposure act — so a third party reads a folder only after the owner has served it. The card refuses `folder:read` over an unserved folder with that reason (a `public` or metadata-only folder is unservable, so the refusal covers both); the approve never flips the serve flag — a re-seal migration and a MUA exposure must not hide behind a consent tap. **(3) What crosses which wire.** The principal opens its wraps with its holder key and sends, on every bearer request, the set's `FolderContentKeys` — the generation list the MSEK blob carries per served set (`ServedSetKeys.keys`), canonical CBOR, base64url — in one request header, `Fauna-Folder-Keys` (codec `FolderContentKeys::to_header_value`/`from_header_value`, the MDA decoding through the shared-Rust FFI), beside `Authorization: DPoP` and the `DPoP` proof: the per-request credential HTTP Basic already is for the password. The MDA keeps them exactly as it keeps the MSEK-unsealed blob — zeroized mlocked per-request memory, never logged, gone at request end — and serves from them the one set the token's scope names. Keys absent or wrong → every row is omitted (the sealed-names degrade) and no byte opens; a token alone opens nothing (no key), a twin alone opens nothing at the door (no token). **(4) Rotation and unserve.** A non-revoking rotation (a member removal of a shared-and-served set) reaches the principal as it reaches the web-serve holder: the owner's serve reconcile — the one that re-provisions this blob, re-run on the custody nudge — renews every live principal folder grant over the set — each holder's live generation, found by rule (1)'s walk over the owner's log — with the new generation's wrap (`fauna.capabilities.renew` with `appended_keys`; `FoldersAuthor::rotate_paywall_grant`'s shape generalized, never a second renew path, deduped nest-side) **at the grant's recorded window end, never a slid one**: a principal is never a blessed box and nothing renews its grants in the background, so a rotation adds keys and leaves the lapse where the consent put it. An unserve revokes exactly those grants, and only them — the principal's records grant is untouched, since the folder twin is its own grant; a re-serve hands nothing back, a principal reads again only after a new approve, which mints the next generation — in the serve-off tail, before the key rotates (nest first, `fauna.capabilities.revoke` per grant id, then the signed `Revoke`s, `grant_log::record_revokes`), in `serve_disable` and in the launch pass's unserve arm alike, so the honest-box end lands with the owner's act; the rotation is defence in depth and the door's served gate the backstop. **(5) Blast radius (rule #7).** During a bearer request the MDA holds exactly the keys the owner minted to that principal over a served set — keys the owner's blob already provisions to it at every Basic session — so rule #7's set is unchanged: served sets, per set, opt-in, revocable. **(6) The door is read-only and bridge-doored.** The bearer door answers OPTIONS, PROPFIND, GET and HEAD over `/webdav/{user}/{folder-id}/` for each folder the token's `folder:read` scopes name, the root collection listing only those; **the folder segment is the folder's id, not its name (ruled 2026-10-05)** — the id is the one name both ends hold: the principal's scope carries it, and the admission answers it beside the `name_hash` the substrate is addressed by, while a served set's row holds no plaintext name and the twin's tuple carries only the hash; an additive `name` on the admission's reply could not be filled for a sealed set, and a name carried with the keys header would be a second, unverified credential field (the deposit door addresses a folder by its id too, `/api/v1/folders/{id}/deposit`); every write method is `403` (the write door is deposit, [`file-sync.md`](file-sync.md) § Third-party deposit ingress). The MDA admits the token through the nest, not a JWKS: one BridgeMda kind, `webdav_admit_principal`, hands the nest the token, the DPoP proof and the request's method and URL, and the nest runs the one admission its own doors run (`principal_session::admit_presentation` — the issuer verifying its own token, a revoked family refused), answering the account, the principal's holder key, the scopes, `exp`, and per `folder:read` scope whether a LIVE `content.read{folder}` grant held by that key over that folder exists (the deposit door's re-resolution, kept where the grant rows are) and whether the folder is served now (the door's backstop). A refused admission is answered with the challenge the nest's own door renders — status, `WWW-Authenticate` and the fresh `DPoP-Nonce` — which the MDA relays verbatim, so a DAV client that sent no nonce learns one as at every nest door; the relay refuses a proof whose `htu` is not under `/webdav/` before admitting anything, so it never vouches a proof minted for another door. **The MDA admits every bearer request through the nest and caches no admission (amended 2026-10-05), so a revoke ends reads at the next request.** The 2026-10-05 wording cached an admission per token for a bounded interval; that would skip the proof on every cache hit — the proof's nonce and replay state live on the nest, so the MDA cannot check a proof itself, and a request carrying the token alone would ride an honest client's admission, undoing DPoP's possession check at this one door. The Basic auth-material cache does not transfer: it caches password-independent ciphertext and still verifies the presented secret on every request. That is the introspection form [`authorization-server.md`](authorization-server.md) § Mail clients permits, chosen over the PDS's JWKS path because the grant's liveness is part of the answer; the arm's coupling to the ceiling is that doc's § Scope grammar → *The read arm*. **(7) Forms.** A `device` principal is the door's holder today; a `remote` one is refused at PAR until a principal can create a folder (TP4; that arm); hosted code holds no DPoP token and reaches no DAV door — its folder read is a runner import, a later ruling. **Rejected:** serving ciphertext and manifests for the principal to open itself — it would re-implement the whole-file pipeline this doc forbids even the Go side to compose, and the existing byte routes would make the door redundant; a standing folder grant to the MDA's own holder key for served sets — it would turn every owner's session-bound served-set posture into a standing one to serve a feature only principals use.

Rejected alternatives (mirror store / native-client-only / new MSEK-derived wrap / handing the MDA `BackupKey`) are analyzed in the design doc § 3 — don't reopen.

## Bulk-byte plane — the HTTP carve-out, not WS-RPC

Chunks are up to 8 MB; the MDA↔nest WS-RPC plane is capped at 2 MiB/message. Bulk bytes ride the existing HTTP bulk-binary carve-out (`GET/POST /api/v1/chunks`, `/api/v1/manifests`). The **write/check** routes (`POST /chunks`, `/chunks/check`, `/manifests`) require a client bearer the MDA — a service user — does not hold; the **download** routes are open (ciphertext-by-hash — no key, no confidentiality). So: **`fauna.bridges.mint_bulk_byte_token(actor_id, folder, access: read|write)`** — the MDA, on its authenticated service-user WS connection during an AUTH'd session, mints a short-TTL token the write routes accept in place of a session bearer.

**What the token scopes — and where each guarantee lives (transport authz only; confidentiality is cryptographic):**

- **Mint gate (nest-authoritative) — the enforceable "cross-set" boundary.** BridgeMda-only, enforced by-purpose inside the handler: `fauna.bridges.mint_bulk_byte_token` gained a `purpose` field (`Folder` default, back-compat) and its top-level allowlist entry now also admits `BridgeMta` — but only for the unrelated `MailBody` purpose (a sealed mail body over the inline budget, `mail-message-size.md` § Message size limits); an MTA requesting `Folder` is refused (`an_mta_may_not_mint_a_folder_token`). For `Folder`, nest mints iff the named set exists, is owned by `actor_id`, is not reserved, and is served (`folders.webdav_enabled`) — the shared served-set predicate of § What the namespace is (a folder-type test no longer exists); otherwise `fauna.bridges.set_not_served`. You cannot obtain byte-route authz for a set that is not served to that actor. A third bridge-mintable purpose (`IndexSegment`, 2026-08-03) was **RETIRED 2026-08-10** with the MDA's index build half (`content-index.md` § Where the index is built — the carrier ruling): the wire variant stays, and the mint refuses it for every caller (`even_an_approved_mda_cannot_mint_an_index_segment_token`); the MDA's index leg is query-only, and blob GET needs no token.
- **Byte-route gate.** The write routes accept EITHER a full session bearer (existing sync clients) OR a bulk token whose `access == write`. A `read` token on a write route is a hard `403`; expired/unknown is `401`. (Defense in depth: the user's read-only-over-WebDAV preference is enforced *authoritatively* by the MDA at the PUT boundary — Guard 2 — since nest has no per-set read-only source; the `access` field lets a `read` token never write.) **The route set is four, not three, as of 2026-08-03:** `PUT /api/v1/blob/{cid}` joined the three chunk/manifest routes, because it is the byte half of the `__index` content-index rail and that rail has two builder legs — a user's client, which holds a session bearer, and the **MDA**, which holds none (`content-index.md` § Where the index is built). A session-only extractor there made the ratified MDA builder position unreachable from Go. The extractor is named `BulkWriteAuth` for that reason; the chunk route is *not* an alternative byte path for a segment, because it stores `encode_blob`-framed bytes and decodes symmetrically on its own GET, while the blob pair is verbatim in both directions — and both index builder legs write the same slice, so they must share one route. **Widening costs nothing at the byte layer:** what a `write` token gains is "store opaque bytes under their own CID", which `POST /api/v1/chunks` already grants into the same store; authority to make a stored blob *referenced* stays with the rail's record kinds.
- **The byte routes never branch on `purpose`** — every purpose yields identical power at the byte layer (next bullet), so the purpose is spent entirely at the mint. A route-side purpose check would read to a later session as if the token conferred something narrower than it does. Owner of the enum and this rule: `fauna_protocol::wrapped_blob::BulkByteMintPurpose`.
- **Store isolation (security).** Bulk tokens live in a store **disjoint from the session `TokenStore`**, so a bulk token can never be replayed as a full session bearer on WS-RPC or any other route.
- **Not a chunk-hash ACL.** The chunk store is a single global content-addressed store (dedup across all users; keyed only by ciphertext hash — no per-actor/per-set partition), so byte-layer per-set isolation is impossible without a forbidden mirror index (§ Architectural rules). Confidentiality *between* sets is the M2 content key — the MDA holds only served sets' keys (§ Key model) and an unserved set's ciphertext is useless to it. Listing-layer set-scoping is `webdav_list_files`. The token's `folder` is the mint-time served-set check + the audit attribution key. Total-storage **quota is enforced at `webdav_record_change`** (`record_sync_change_metered` → `507`, § Protocol surface), **not** at chunk upload — the chunk write routes are unmetered per-write (the pre-existing content-addressed-store posture; dedup makes a per-chunk charge meaningless).

The token conveys transport authz only — chunks are ciphertext; the content key never leaves the MDA session. Uploads carry `X-Content-Hash = blake3(ciphertext)` (the store key), passing the F9 check unchanged.

## Network exposure & discovery

- Same posture as the siblings, verbatim: `mail.<domain>:443` behind the SNI-passthrough router (nest never terminates WebDAV TLS); desktop/bare-IP boxes serve directly on the admin-set DAV port family with the floor cert + any-locator handle login (`caldav-server.md` §§ Network exposure / Desktop-IP / Any-locator).
- **Apex `/.well-known/webdav`** — `301` → `https://mail.<domain>/webdav/`; `503` until enabled. (A NextCloud-ecosystem convention, not RFC 6764.)
- **No SRV record — deliberate.** No mainstream client queries a `_webdavs._tcp`; publishing a dead record is noise. The admin UI + MUA panel surface the URL. (Recorded so no session "completes the symmetry".)
- **No anonymous WebDAV.** Everything requires auth.

## Threat model — inherited, with the per-set-scoped widening

`caldav-server.md` § Threat model applies: not zero-access by necessity — the MDA decrypts server-side per AUTH'd session (the opt-in convenience tier); Fauna-native apps keep zero-access. Preserved: chunk storage stays ciphertext-only (nest never sees file plaintext, at rest or in transit); **no external plaintext-ingest boundary** (files are written only by authenticated principals); blast radius per § Key model — user-chosen per set, revocable. File paths in sync sets seal at rest as of the S9 flip's 2026-08-02 execution (the 2026-07-29 paths-are-content ruling's mechanism — `../architecture/encryption-at-rest.md` § Carve-outs; `path-sealing.md` § Sealed names & paths); the one remaining declared gap is the per-set `folders.name`, gated on the per-app hash-sender batch. Sizes stay plaintext and exact by the re-ratified carve-out (not a gap), and WebDAV adds no new metadata exposure on top of that substrate either way.

## Protocol surface (v1) and deliberate deferrals

- **Read:** PROPFIND Depth 0/1 (from `webdav_list_files` — the `fauna.sync.files` MDA twin: plaintext paths folded latest-per-path; directories = the path-prefix tree); GET/HEAD (manifest → chunks → decrypt → stream); `getetag` = the **manifest hash**; `getlastmodified` = change `created_at`; `getcontentlength` = `size_bytes`.
- **Write:** PUT (streamed chunk+seal via shared-Rust FFI → chunk upload → `webdav_record_change`); MKCOL; DELETE (tombstone change); MOVE/COPY (manifest-level re-record — chunks never move; COPY is free by content addressing). `If-Match`/`If-None-Match` against the manifest-hash ETag; a lost race is `412`.
- **Device identity:** writes attribute to a stable per-actor pseudo-device (`"WebDAV"`, idempotently upserted, write-capable) so forwarding, self-echo skip, the Devices roster, and the **existing conflict machinery** behave normally. Registered through the DB-layer `register_sync_device` writer directly, **not** the `fauna.sync.register` RPC door — the door refuses this exact id from a client as reserved ([`admin.md`](admin.md) § 2 Users), so the internal writer must keep bypassing it.
- **QUOTA (RFC 4331):** `quota-available/used-bytes` from the same tier limits IMAP QUOTA serves; enforcement at `webdav_record_change` (`record_sync_change_metered` → `507`), not at chunk upload (the content-addressed chunk store is unmetered per-write).
- **Deferred, recorded:** **Class-2 LOCK** — v1 is Class 1 + conditionals; consequence: Windows Explorer's native mini-redirector maps read-write only with Class 2 (browse works; Cyberduck/rclone/GNOME/KDE/Finder/NextCloud clients don't need locks). Follow-on maps LOCK onto per-file leases (prior art: `fauna.folders.lease.acquire`). **DeltaV/versioning** (file versions exist nest-side). **Backup-set read-only browse.**

## Architectural rules

- **Same concepts as CalDAV/CardDAV, never a parallel invention** — shared listener, `davauth`, SNI, caps, the sibling toggle shape. A WebDAV-only divergence needs a stated protocol reason.
- **The substrate is the folder store; never a mirror.** No `bridge_webdav_*` content tables, ever.
- **Chunk crypto stays in shared Rust** — the MDA calls the chunker/sealer through the UniFFI Go bindings; no Go reimplementation.
- **Additive at-rest evolution** — `folders.webdav_enabled` via `reconcile_added_columns`; no drop/recreate; the re-seal migration deletes nothing until the re-sealed copy is verified.

**Where a client capability lives — the rule this slice settled (2026-07-12).** The folders page's `DevicesMachine` is built `(nest, observer)` and holds **no `ActorKeypair`**: it is deliberately a *keyless projection of nest state*. the MSEK lives in the account's mail custody (`fauna.state.mail`), so a keyless machine cannot see it, and threading a keypair in (or mounting a second `MailSettingsMachine` for one bool) would push key custody into a machine that wants none. Therefore: **a question about the actor's own secrets belongs on the key-bearing face that already answers it — not bolted onto the keyless snapshot.** The capability query rides the same face as the action it gates (`folders_can_serve_webdav` beside `folders_serve_set`), and depends on strictly *less* than the action: only the mail custody (`MailStore`; the `ConfigClient` until the `__config` rail retired), never the MLS engine, so a page can ask "may I offer this control?" as soon as the account runtime exists — a capability read that fails because the rail is not up yet is indistinguishable from "cannot", which would silently disable a legitimate control. The cost is one imperative call per page-visit instead of a snapshot field; that is the correct trade, and it generalizes to any future *"can I?"* gate on a keyless page.
