## The pages

### 4. DNS configuration (`dns_config`)

Single page. Two top-of-page checkboxes (`dns-buy-domain-checkbox`, `dns-same-provider-checkbox`) drive a row of provider buttons. Selected provider expands a credentials sub-form (`dns-credentials-form`, generated from `i18n/providers.yaml`), a verify button, a status text, and a TLD price display. A `dns-no-provider-message` appears when the user must buy the domain but no supported registrar carries the TLD. A `dns-set-up-later-button` skips DNS configuration on this page; manual DNS instructions are shown on step 7 after provisioning completes.

**This page covers the initial domain claim — the deployment's `primary` domain in the `mail_domains` model.** Additional local domains are added post-onboarding via the admin-pane "+ Add domain" wizard per `docs/goal/behavior/mail-multidomain.md` § Adding a new local domain (the admin workflow); the wizard there reuses this page's provider-credentials shape for delegating new domains.

**Credential persistence (target state).** The DNS-provider credentials verified here are **persisted client-side** (per `docs/goal/behavior/dns-management.md` § Where the credential lives) rather than used once and discarded — that is what lets the post-onboarding "Fauna controls DNS" mode and the add-domain wizard's provider check work for the deployment's lifetime. They land in the admin's DNS record, the account-state plane kind `fauna.state.dns` ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The kinds*; **the nest never receives or can decrypt the provider key**); the admin can decline (manual-DNS path).

**Capture at onboarding, seal via the launched app — one store, one writer.** The onboarding machine does **not** seal the credential itself: it has no account runtime to write the account state through (only the HTTP `NestApi` seam), and in the fresh-provision path the nest does not exist "at the end of the DNS step" (it is provisioned in step 6 and claimed afterward). Instead the machine **captures** the verified credential at the DNS step and **exposes** it via `OnboardingMachine::captured_dns_credential()` (`CapturedDnsCredential { provider_id, fields, label }` — `None` on the manual / unverified path). The **launched app**, once authenticated on the new nest, reads it at `wizard_outcome() == LoggedIn` and seals it through the *same* post-onboarding `DnsManagementMachine::PutCredentials` path the "Fauna controls DNS" mode uses (`build_dns_management_machine_with_credentials`) — so there is **one credential store with one writer (the `DnsManagementMachine`)**, no second config-put path in onboarding (priority #2). `PutCredentials` re-runs the provider `verify()` to (re)derive the covered zones, so what onboarding captured cannot go stale. *(Shared-Rust hand-off channel implemented — `captured_dns_credential()` over UniFFI + `capturedDnsCredentialJson()` over WASM (tracked internally, Slice 4). The per-app launch glue that reads it and dispatches `PutCredentials` is per-app TIER-2, Slice 6 — see `dns-management.md` § Implementation status today.)*

**A nest on a subdomain of a domain the admin already holds.** The provider "has the domain" (`provider_status() == ProviderHasDomain`, the status that enables Continue without buying) when one of the verified provider's zones **is** the handle's domain **or contains it** — `example.com` for `box.example.com`; with several candidates the longest one wins, and that same zone is the one provisioning publishes into (`covering_zone`, the one rule both readers share). The handle check sees such a name before any provider is chosen: it has no delegation of its own, so the outcome is `DomainAvailable`, but the resolver's answer names the **zone cut** — the owner of the SOA it returns, `example.com` for `dev.example.com` — and when that zone is a strict ancestor of the name with more than one label, the check records it (`NsProbe::enclosing_zone`, shared Rust) and says so: the message `handle_check.outcome.domain_available_inside_zone` names the zone and both readings ("if you hold `{zone}`, pick the DNS provider that hosts it; if not, register `{domain}`"), and Continue lands with `buy_domain` **off**, so every DNS provider stays selectable and the zone list settles the question at verify. **An in-zone name that already resolves is not available:** when it has an `A` record of its own (`NsProbe::in_zone_address`, looked up only for an in-zone name), someone has pointed it at a host — most often a nest already serving `box.example.com` that the admin is signing back in to — so the check skips both available outcomes and goes on to the `_fauna._tcp` SRV and nest-health probes exactly as for a delegated domain, landing on the ordinary `AlreadyOnNest` / `NestRunningUserUnregistered` / `UnregisteredUnclaimedNest` / `RegisteredNoNest` outcomes (without it, signing in to an existing nest on a subdomain dead-ended on `dns_config`, found 2026-10-05 against a staging box on a subdomain). A bare-TLD zone cut (`com` for an unregistered `foo.com`) is where every unregistered name lands, and keeps the plain available outcome. **The check carries no public-suffix knowledge, and the ruling accepts the one ambiguity that leaves:** a name under a multi-label suffix (`foo.co.uk`, zone cut `co.uk`) reads exactly like a subdomain of a held domain, so its buyer gets the both-readings copy and ticks "buy" themselves — after verify the registrar's quote shows as `UnregisteredBuyable`, and the checkbox stays enabled because the domain status is still `Unregistered`. Starting unticked is the cheaper error: a ticked box filters the list to registrars and hides the DNS host that holds the parent zone, while an unticked one costs a buyer one tick the status line asks for. A public-suffix list would remove the ambiguity, but it is a new dependency (the user's call) and is not needed for a working path.

The `buy_domain` checkbox state is **machine-derived, not client-toggled**. When `submit_handle_check_continue()` lands the wizard on `dns_config`, the machine sets `buy_domain = (handle_check.outcome == DomainAvailable && no enclosing zone was recorded)` (i.e. true on Unregistered, false on a name inside a zone — the paragraph above — and on RegisteredNoNest / RegisteredWithNest / etc.) before the snapshot is observed by the app. The app renders `dns_config().buy_domain` and forwards user toggles via `toggle_buy_domain(on)` for explicit overrides, but does NOT compute the initial value itself.

When `buy_domain` is checked AND `provider_status() == UnregisteredBuyable` AND the registrar's `requires_contact()` returns true (Gandi and Namecheap today), a WHOIS contact form (`dns-contact-form` container with 9 `dns-contact-{first-name,last-name,email,phone,address1,city,state,postal-code,country}-input` fields) renders below the status text. The form pre-fills from `dns_config().contact` when `verify_dns()` populated it via `Registrar::fetch_default_contact()`; user edits push back via `set_contact(contact)`. The form is NOT rendered for Porkbun or Cloudflare (`requires_contact == false`) — both use account-level contacts configured at the registrar's own dashboard; the `dns-registrar-notes-text` element below surfaces that reminder instead.

When a provider with `registrar_notes_key` set in `i18n/providers.yaml` (Porkbun and Cloudflare today) is selected AND `buy_domain` is checked, the optional `dns-registrar-notes-text` element renders the localized note (e.g. "Porkbun uses the contact details on your Porkbun account for domain registration. Make sure they're set at porkbun.com/account/settings before you continue."). The string key comes from the snapshot — the app looks it up via its i18n table, same pattern as `LocalizedText` elsewhere. Hidden when the selected provider has no `registrar_notes_key` or when `buy_domain` is unchecked.

**`hosted-auth` fields — a bundled provider's account token (`architecture/provisioning/bundled-provider-api.md` § Authentication owns the flow; `architecture/provisioning/registry.md` § Bundled provider owns the field type).** A field whose registry type is `hosted-auth` is not typed: the app renders it as a **button carrying the field's derived id** (`dns-credentials-form-{field.id}` — the id every generated field already has, so no new element is minted), labelled from the machine's `hosted_auth_state(field_id)`: `Idle` → `provisioning.hosted_auth.connect` ("Sign in at the provider…"), `Pending { user_code }` → `provisioning.hosted_auth.pending` ("Finish signing in in your browser — code {code}"), `Connected` → `provisioning.hosted_auth.connected`, `Failed { message }` → `provisioning.hosted_auth.failed`. Pressing it calls `hosted_auth_begin(field_id)` (the machine POSTs the device-authorization request to the sibling `base-url` field's address), the app opens the returned `verification_url` through the same open-URL affordance `dns-provider-open-browser-button` uses, then awaits `hosted_auth_wait(field_id)` — the machine polls until the token lands in `creds[field_id]` (at which point `can_verify_dns()` turns true) or the attempt expires. Nothing here is per-app except the button, the open-URL call, and the label lookup. **Degradation rule:** an app that has not built the button renders a `hosted-auth` field as a `secret` input — a token from the intermediary's own dashboard pasted there is equally valid — so an app awaiting its trickle-down stays functional, never broken. *Implementation status: tui first (the lead app), linux, web, and android next (android's leg is compile/Robolectric-verified only — android e2e itself is emulator-gated on the emulator host); macOS + iOS landed 2026-08-27 (one shared FaunaKit `DnsPriceConfirmButton`-adjacent lift in `CredentialsForm.swift`, e2e-verified via `test_bundled_provider_buys_domain_and_server_through_one_row --app macos`/`--app ios` — the first time either app completed the full bundled-provider journey). **Windows' button landed 2026-09-03** (`GenericProviderForm.xaml.cs`'s `HostedAuth` arm; repainted per tick via `RefreshHostedAuthButtons()`, called from `DnsConfigView`/`VpsConfigView`'s existing per-tick refresh since the control owns no tick of its own). The **whole device flow is one ViewModel call** on windows — `OnboardingViewModel.RunHostedAuth` owns begin → hand the URL to an open-URL callback → poll, and the view holds a single `HostedAuthRun` delegate: sequencing the two phases in the view put the second delegate's very invocation on the far side of a UI-thread continuation and a foreground-stealing browser launch, and the token poll was then never issued in four runs of five (2026-09-03; `OnboardingHostedAuthTests` pins the collapsed flow, browser-launch-throws case included). The two prerequisites this note used to name — no §6 BoM UI, and a bare-id-under-scope element convention — are both **closed** (2026-09-04; § 6's status below, and the composed `{dns,vps}-credentials-form-{field.id}` convention windows now shares with every other app). The journey is nonetheless still **not green on windows**, though its 2026-09-04 cause — an awaited machine call begun on the WinUI UI thread failing to progress under the journey's UIA load — was **fixed 2026-09-06** in the generated C# FFI async layer (`architecture/apps/native-async-execution.md` § C#: the FFI layer never needs the caller's thread back owns the rule and the fix), after which the journey clears hosted-auth, DNS verify and the contact form and reaches `vps_config` for the first time. What remains is a narrower, still-intermittent residue: `hosted_auth_wait` is entered and then issues no token request at all. Do not re-diagnose the fixed cause.*

**The price-confirm checkbox carries the withdrawal acknowledgement — for every registrar.** `dns-price-confirm-checkbox`'s label (`registrar.price_confirm`) states, besides the price acceptance, that registration begins immediately on *Buy and set up* and that the user therefore gives up any statutory right to withdraw from the purchase. One string on all 7 apps, applying to Porkbun and Gandi exactly as to a bundled provider: the wizard is the ordering surface in every case, so the acknowledgement is generic, not per-provider (priority #1). The registrar's own terms stay the registrar's — the wizard acknowledges the consequence, it does not restate them.

Driven by `dns_config()` snapshot getter and `provider_status()`. The app renders `visible_dns_fields()` rather than computing field visibility itself. Likewise it drives **per-provider button eligibility** from `dns_provider_eligible(provider_id)` (encoding `buy_domain → Registrar` / `same_provider_for_vps → Vps`), **the disabled row's on-screen reason** from `dns_provider_ineligible_reason(provider_id)`, **contact-form visibility** from `should_show_contact_form()`, **registrar-notes visibility** from `should_show_registrar_notes()`, and **no-provider-message visibility** from `should_show_no_provider_message()` — none of those rules is re-derived in the per-app shell (priority #2; the rule for the first is the same one the `toggle_*` deselect guards already use). All are exposed over UniFFI (`fauna-ffi`) and WASM (`fauna-wasm-onboarding`).

**The eligibility answer carries its own reason.** A greyed-out provider row must state why on the same screen — `ui/README.md` § Copy comprehensibility rule 5, whose whole point is that a dead control with no visible cause leaves the user stuck. `dns_provider_eligible` answers yes/no, which is enough to grey a row and not enough to explain it, so the machine also exposes **`dns_provider_ineligible_reason(provider_id) -> Option<LocalizedText>`**: `None` exactly when the row is selectable, else the i18n key naming which of the two constraints closed it — `ineligible_needs_registrar` (buy-domain is on, the provider can't register), `ineligible_needs_vps` (same-provider-for-VPS is on, the provider has no VPS), or `ineligible_needs_registrar_and_vps` when both. Each string names the checkbox that re-opens the row, so the refusal carries its own remedy (rule 5's Q4). Verdict and explanation come from one shortfall computation and therefore cannot disagree; an app that re-derived the reason from the capability table would be re-deriving exactly the rule this getter exists to own. One deliberate asymmetry: for a `provider_id` outside `PROVIDERS` the getter returns `None` while `dns_provider_eligible` returns `false` — that id has no row on screen, so there is no control to explain.

**The page's other disabled control, Continue, is explained by `dns_status_text_key()`.** That getter narrates four of the five `ProviderStatus` variants into `dns-status-text`, but returned an **empty** key for `NotReady` — which is the page's *entry* state, exactly where Continue is disabled, so every app painted a blank line beside a dead button. `NotReady` covers two conditions (no provider selected; selected but `verify_dns` hasn't landed) and rule 5's Q2 wants two messages, so the arm splits: `status_pick_provider` and `status_verify_credentials`, each naming the user's next act rather than the state. The remaining `can_continue_dns()` refusals are already covered by the variants that *do* narrate — `status_buyable` names the confirm box, `status_registered_elsewhere` and `status_not_buyable` name the way out. *Implementation status: landed 2026-08-05 in the shared getter, so all 7 apps inherit it without an app-side change — each already renders `dns-status-text` from this one call. Pinned by `not_ready_says_which_step_is_missing_instead_of_nothing` (machine) and tui's `the_entry_status_line_explains_the_disabled_continue`.* *Implementation status: shared getter + WASM wrapper (`dnsProviderIneligibleReasonJson`) landed 2026-08-05, unit-tested over all four shortfall combinations. Rendered on **tui** (the lead app) as an un-id'd explainer line directly beneath each disabled row — the same chrome shape rule 5's own `devices.wizard.name_required` exemplar uses, so no ui.yaml element is minted. The other six apps still paint the disabled row with no reason; that lift is tracked in the cross-app queue.* Likewise the **no-provider-message TLD** is the shared `handle_tld(handle)` derivation (the substring after the handle domain's last dot, or `None` when there is no real TLD — so the `.{tld}` message hides), not re-derived per app. The **no-provider-message visibility** is `should_show_no_provider_message()` = `buy_domain && handle_check.outcome == DomainAvailable { buyable_via_provider: false }` — a TLD property knowable from the handle-check probe alone, so the message shows up-front and does **not** require the user to first select + verify a provider, and does **not** depend on *which* provider is selected. This matches the message's TLD-scoped text; re-deriving it from `provider_status() == UnregisteredNotBuyable` is both late (that status is `NotReady` until a provider is selected + verified) and provider-specific (it mislabels a TLD that some registrar carries but the selected one does not). **Visual position (user-ratified 2026-07-18):** `dns-no-provider-message` renders up-front, immediately after `dns-buy-domain-checkbox` — before `dns-same-provider-checkbox`/`dns-provider-row` — on every app. This was a real, longstanding cross-app divergence (macOS/android already placed it there; iOS/web placed it low, after `dns-set-up-later-button`) rather than a platform-idiomatic difference, so it converges identically everywhere (priority #1); apple converged the same day (`dnsConfigFields` shared FaunaKit helper). *Implementation status: `handle_tld` is exported over both UniFFI (`fauna-ffi`) and WASM (`fauna-wasm-onboarding`) and consumed by macOS + iOS + android (android migrated off the buggy `substringAfterLast('.')`-on-the-whole-handle hand-roll, which leaked a local-part dot) and web (`onboarding/+page.svelte` now calls the `handleTld` WASM wrapper via `$lib/wasm-onboarding` instead of its former local `indexOf('@')`/`lastIndexOf('.')` copy). The visibility getter `should_show_no_provider_message()` is exported over UniFFI + WASM and consumed by macOS + iOS + android + web (android 2026-06-21, `DnsConfigScreen.kt` now gates `dns-no-provider-message` on `shouldShowNoProviderMessage()`, beside its existing `shouldShowContactForm`/`shouldShowRegistrarNotes` calls; web 2026-06-21, `onboarding/+page.svelte` now gates it on the wasm `shouldShowNoProviderMessage()` via the `Machine` wrapper, replacing its former local `provider_status() === 'UnregisteredNotBuyable'` predicate); **tui** renders it from the same getter (2026-07-12); linux + windows do not render `dns-no-provider-message` at all yet.*

*Implementation status (`visible_vps_fields()`, 2026-07-12): linux used to **re-derive** this getter inline in `views/onboarding/vps_config.rs` — a copy of the `Capability::Vps` filter *plus* a hand-rolled `FieldMeta → FieldMetaPlain` mapping — while the shared getter had zero call sites anywhere in `apps/fauna-linux/`. It now calls `m.visible_vps_fields()`, as its `dns_config` twin next door always did; tui consumes the getter from the start.*

### 5. VPS configuration (`vps_config`)

Single page. Provider row + credentials form + verify button + location picker + server-type radio (max 5 from `curated_offers` — or from the provider's own ordered catalog when `curated_offers` is the `*` wildcard, `architecture/provisioning/registry.md` § Bundled provider). Pre-selects the same provider as DNS where possible. Each server-type radio's label is rendered by the shared `server_type_label` helper (UniFFI for native, WASM for web) so all seven apps show one canonical shape — `{id} — {vcpu} vCPU / {mem_gb} GB / {disk_gb} GB disk / {price}/mo` (slash-separated, disk included) — pinned in `fauna-onboarding-machine` tests rather than re-derived per app.

**Mail-vs-social mode (decided here, before the box boots).** Whether the box provisions the **mail subsystem** is decided at this page via the `vps-config-mail-mode-toggle` — *not* the post-claim §3b derived enable, which runs **after** provisioning and so is too late to shape cloud-init. The reason it must live here: cloud-init must know mail-intent to decide whether to emit the `clamd`/`rspamd` content-scan sidecars (clamd holds its signature DB in RAM, ~1.5 GB — `installers/vps.md` § Minimum VPS Requirements), and the RAM is *also* chosen here (the server-type picker). So both the intent and the RAM land in one place, before boot.

- **Default** — the toggle is **ON iff the handle targets a real registerable domain** (the same `resolve_handle_domain(domain).is_public_dns_name` predicate as the §3b derivation's handle-locality axis, so the two stay consistent; §3b's NAT conjunct is vacuously satisfied here — a provisioned VPS is a public-axis box). Provisioning a VPS always uses a real domain, so the default is effectively ON; the toggle exists so a user who wants a **social-only** box can turn mail OFF.
- **RAM gate** — when mail is ON, the server-type radio offers/permits only plans with **`mem_gb ≥ 2`**; turning mail OFF unlocks the **1 GB** tier (the point of "conditional scanners" over simply raising the floor — a social-only box stays cheap). The gate reads `ServerTypeInfo.mem_gb`, already in scope on this page.
- **Effect** — the toggle drives `CloudInitParams::enable_mail` (`fauna-provisioning::cloud_init`): ON → mail ports `{25,465,587,993}` + scanner sidecars + the matching `ufw` rules; OFF → a lean nest+watchtower compose with no scanners. The toggle is deployment **topology** (it only provisions the box *for* mail); the box still serves mail only once the admin enables it post-claim (the runtime `/data/imap-enabled` gate). A **social-only box cannot later enable mail without a VPS resize** — a documented, accepted constraint (the scanners and a ≥ 2 GB plan would have to be added).

**Update channel (decided here, before the box boots).** Which builds the box's automatic updater follows is chosen on this page with the `vps-config-update-channel-row` radios — one per channel, keyed by channel id (`vps-config-update-channel-row[stable]`, `[test]`, `[dev]`), exactly one selected, **Stable** by default. It lives here for the same reason the mail-mode toggle does: the choice is the image tag written into the box's cloud-init compose, so it must be known before the box boots.

- **The three channels** — `stable` follows the `latest` tag (released builds); `test` follows `test` (release candidates under verification); `dev` follows `dev` (the newest development builds, not yet verified). The mapping is the shared `UpdateChannel::image_tag` (`fauna-provisioning`), the one place a channel becomes a tag; which pipeline moves each tag is owned by `architecture/build-system.md` § Image tags & channels.
- **Shown to everyone** — all three rows render for every user, each with a one-line description; there is no "advanced" disclosure (user-approved 2026-10-04). The image is publicly pullable at every tag, so hiding a channel would protect nothing.
- **Effect** — the selected channel drives `CloudInitParams::image_tag` (`fauna-provisioning::cloud_init`), which names both the image the box first pulls and the tag its updater polls. The choice is made at provisioning only: changing the channel of a box that is already running is not offered anywhere yet.

**Implementation status today (update channel).** Shared Rust is landed: the `UpdateChannel` enum and its tag mapping, the settable `VpsConfigState.update_channel`, `OnboardingMachine::set_provision_update_channel` / `provision_update_channel` (UniFFI + WASM), and `run_provisioning_inner` feeding the choice into `CloudInitParams::image_tag`; `vps-config-update-channel-row` is registered in `ui.yaml`. Per-app: **the rows render on tui only** (`wizard/vps_config.rs`, 2026-10-04); the other six apps provision `stable` until their rows land.

**Implementation status today.** Fully landed, shared + per-app. Shared Rust: `CloudInitParams::enable_mail` gates the scanner sidecars / mail ports / mail `ufw` rules in `build_cloud_init`; the settable `VpsConfigState.enable_mail: Option<bool>` field + `OnboardingMachine::set_provision_mail_mode`/`provision_mail_mode_enabled` methods + the shared `server_type_allowed_for_mail(st, enable_mail)` RAM-gate helper are exported over UniFFI + WASM (and the Go bindings); `run_provisioning_inner` feeds the toggle value (`snapshot.vps.enable_mail.unwrap_or_else(handle default)`) into `CloudInitParams::enable_mail`; `set_provision_mail_mode` drops a now-too-small selection so a mail box is never provisioned on a sub-2 GB plan; `vps-config-mail-mode-toggle` is registered in `ui.yaml`. Per-app: **the toggle renders on all seven apps** (verified 2026-07-10 — linux `views/onboarding/vps_config.rs`, web `routes/onboarding/+page.svelte`, windows `Views/Onboarding/VpsConfigView.xaml`, android `onboarding/VpsConfigScreen.kt`, macos `MacVpsConfigView.swift`, ios `VpsConfigView.swift`, tui `wizard/vps_config.rs`).

### 6. Nest provisioning (`nest_provisioning`)

Single page with three regions: a top price-summary region, a progress region rendered from `provisioning_snapshot()`, and a bottom navigation row. Page-level design was ratified 2026-04-27 (tracked internally); this section captures only what the app must render.

**Top region — price summary ("Bill of Materials").** `provisioning-price-bom` recaps, before the user commits, what the run is about to charge — up to two line items from `bill_of_materials()`: `provisioning-bom-domain-line` (one-time domain-registration price, shown only when the wizard is buying a new domain — i.e. `dns_config`'s buy-domain path was taken) and `provisioning-bom-vps-line` (the selected VPS's monthly price, always present — `vps_config`'s Continue already requires a server-type selection). Both prices were already surfaced, and for the domain explicitly agreed to, earlier in the wizard (`dns-tld-price-display` + `dns-price-confirm-checkbox` on `dns_config`; the server-type radio options on `vps_config`) — this region is a pre-commit recap, not a new price source, and each item's label reuses the identical `onboarding.provision.step.{domain,server}` i18n keys the progress rows below it render, so the recap and the step name always agree. Pure computation over already-in-state DNS/VPS data — no IO. **The domain line also discloses the renewal price and term:** `BillOfMaterialsItem.renewal_price_cents` (carried from the registrar's `renewal_cents` quote through `RegistrarAvailability::Buyable`) renders the line as `{label}: {price} for the first year, then {renewal}/year` (`onboarding.provision.bom_line_domain`); a registrar that quotes no renewal price falls back to the plain `bom_line`.

**Provisioning model.** Provisioning runs the shared Rust orchestrator (UniFFI for native, WASM for web, in-process for Linux) — every app invokes the same orchestrator, no registry HTTP middleman (the one per-target seam is the *probe client* it is handed — *Reaching the box* below). The orchestrator is idempotent: each step pre-flight-checks the world (cloud provider, DNS, running nest) and reports `Skipped` when the desired state already exists, so re-running on the same domain is safe and cheap. Four user-visible steps in fixed order: **Domain**, **Server**, **Dns**, **Online** (the latter polls the box's `GET /api/v1/health` **at its reach address** until 200, then **claims it** — *Provisioning = build + claim* below). Transient errors (timeout, 5xx, 408, 429) retry with exponential backoff up to a step-specific budget; terminal errors fail immediately and stop the run. **DKIM is not generated client-side:** the nest mints and holds its own DKIM signing key when the mail domain is added (`mail-bridge-lifecycle.md` § DKIM provisioning (automatic)), so cloud-init carries no DKIM material. The **Dns** step publishes the primary domain's record matrix — apex + `mail.<primary>` `A`, `MX` → `mail.<primary>`, `SPF`, `_dmarc` (**no DKIM record** — the orchestrator can't know the nest-minted key until post-boot, so publishing a client-generated one would publish a key the bridge never signs with) — assembled from the shared `fauna_mail::dns` builders (the `dns-records` feature), so it is byte-identical to what the nest's `fauna.dns.{list,verify}_records` renders post-claim (`dns-management.md` § byte-for-byte); the record **bodies** are owned by `mail-multidomain.md` § Per-domain DNS records, not re-defined here. The DKIM TXT is instead published post-boot from the nest's `mail_dkim_keys.public_dns_value` via the `admin-dns` page (tracked internally; landed 2026-06-22). The advisory reverse-DNS pointer is set to `mail.<primary>` (the FCrDNS/EHLO hostname) via the VPS provider's rDNS API.

The page is rendered from `provisioning_snapshot()`:
- `overall: OverallStatus` ∈ `{Idle, Running, Succeeded, Failed, Cancelled}` — drives button visibility and the bottom row's enabled state.
- `steps: Vec<StepSnapshot>` — exactly four entries (Domain, Server, Dns, Online). Each carries `kind`, `status` ∈ `{Pending, Running, Skipped, Succeeded, Failed}`, `substep: Option<SubstepKey>` (typed → i18n lookup, never English), `attempt`, `max_attempts`, `last_error`, `skip_reason`, and timestamps.
- `started_at_ms`, `finished_at_ms` — for the elapsed-time display; the app feeds them (plus its live `now_ms`) to the shared `fauna_provisioning::progress::elapsed_display`, which returns the canonical "{seconds}s elapsed" `LocalizedText` (see `value-formatting.md` § Provisioning elapsed). Computed UI-side, but single-sourced — never hand-rolled per app.
- `result: Option<ProvisionResult>` — populated when `overall == Succeeded`.
- `final_error: Option<String>` — populated when `overall == Failed` or `Cancelled`.

At most one step is `Running` at any time — there is no concurrency at the snapshot level. **Per-step row rendering** follows the shared visibility predicates (see *Where the step-row visibility rules live* below): the `provisioning-substep` text row shows on `Skipped` (the "already configured" placeholder) and on `Running`/`Failed` when the step carries a `SubstepKey` *or* an attempt suffix — i.e. exactly when the resolved i18n text is non-empty — and is hidden on `Pending`/`Succeeded`. Its `SubstepKey` renders via the i18n table (never English); when `max_attempts > 1` and `attempt > 1`, the `(attempt {attempt} of {max_attempts})` suffix is appended. The `provisioning-step-error` row shows only when the step is `Failed` **and** carries a non-empty `last_error` — a `Running` row mid-retry can still hold a stale `last_error` from an earlier attempt, which must not surface, so the rule is `Failed && !empty`, not "when populated".

Click handlers:
| Element | Action |
|---|---|
| Top-region "Buy and set up" CTA (architecture-defined) | `start_provisioning()`. Spawns the orchestrator task and returns immediately; observer ticks drive re-render. Idempotency makes this safe even after a partial prior run. |
| `provisioning-cancel-button` | `cancel_provisioning()`. Visible only while `overall == Running`. Cancel is soft — the orchestrator aborts at the next step boundary or retry iteration; already-created VPS/DNS resources stay, and a subsequent retry skips them. |
| `provisioning-retry-button` | `retry_provisioning()`. Visible while `overall == Failed` **or** `overall == Cancelled` — both are stopped-with-resources-intact states, and retry is the user's resume path out of either. Re-runs the whole orchestrator from the top; idempotency short-circuits completed steps, so this is functionally "resume from the failed/cancelled step." Resuming means the **same box**: the re-run reuses the pending-provision slot's claim code and expects the identity the box was built with (*The pending-provision slot* below) — the Server step's pre-flight is name-only, so a re-run that minted fresh ones would find the built box and could neither verify it nor claim it. (Without the `Cancelled` case a soft-cancel would strand the user with only Back, contradicting the soft-cancel-enables-retry semantics in the prose above.) |
| Bottom-row Continue | Disabled until `overall == Succeeded`. Calls `continue_from_provisioning()` → `OnboardingStep` and navigates to it. On the standard path `Succeeded` means *built **and claimed*** (*Provisioning = build + claim* below), so Continue lands on `NatModeChoice` (§ 3b-bis) exactly as a claim-code submit does — this page never exits straight to `Done`/`LoggedIn`; on the deferred-DNS path it lands on `DnsPostInstructions` (§ 7). (Ratified 2026-08-29; the pre-ratification `Done → LoggedIn` exit left the box **unclaimed** — § Implementation status today.) |
| Bottom-row Back (existing) | Standard Back. There is no destructive-cancel path that tears down resources — soft-cancel-only is the design decision. |

**Where the affordance rules live.** The button visibility/enabled conditions above are not re-derived per app; they are the typed predicates `OverallStatus::{is_idle, is_running, can_retry, can_continue}` in `fauna-provisioning` (the single source — `can_retry` is the one carrying the Failed-or-Cancelled rule and its rationale), surfaced to web through the machine accessors `provisioning_in_progress()` / `can_retry_provisioning()` / `can_continue_provisioning()` (and their wasm wrappers). Native apps may call the inherent `OverallStatus` predicates directly on the snapshot they already hold. Every app consumes these instead of comparing `overall == ...`.

**Where the step-row visibility rules live.** The per-step row conditions above (substep row, error row, attempt suffix) are likewise not re-derived per app; they are the additive boolean fields `shows_substep` / `shows_error` / `shows_attempt_suffix` on `StepSnapshot`, computed by `StepSnapshot::recompute_display` in `fauna-provisioning` — the single source of the rule, including the `Failed`-gate on the error row and the "resolved text is non-empty" logic for the substep row. Because `StepSnapshot` is a `uniffi::Record` (which cannot carry exported methods), the projection is delivered as **fields, not methods**: `ProvisioningSnapshot::enrich_display` fills them on the clone returned by `provisioning_snapshot()`, so every app — native (the Record fields), web (the JSON-parsed snapshot), and Linux (the same getter) — reads identical booleans. Each app renders the rows by these fields and never compares `status` / `last_error` itself. *Implementation status: all 7 apps now consume the shared `shows_*` fields — Linux (`views/onboarding/nest_provisioning.rs`), tui (`wizard/nest_provisioning.rs`, from the start, 2026-07-12), web (`+page.svelte`'s `step.shows_substep`/`shows_error`), macOS+iOS (`FaunaKit.ProvisioningStepRow`), Windows (`OnboardingViewModel.cs`'s `showsSubstep`/`showsError`/`showsAttemptSuffix`), and Android (`NestProvisioningScreen.kt`'s `StepRow`, adopted 2026-06-14 — its prior inline copy was the most drifted, substep only on `Running` + error ungated by status, so the adoption also fixed a bug). No app re-derives this rule inline anymore.*

**Reaching the box — the reach address (ratified 2026-08-29).** A freshly-provisioned box is reachable at its **captured public IP** the moment cloud-init finishes, and by its domain only much later: the A record the Dns step just published takes anywhere from seconds (Cloudflare) to 30 min–5 h (Hetzner Cloud DNS publishes in irregular batches — `../architecture/testing.md` § Gap 3) to reach the authoritative nameservers, and — decisive for the browser — the box boots **domainless** and can hold no trusted cert for a name it will only learn at the claim (`../architecture/nest/domains-and-tls-bootstrap.md` § Boot / § Claim; ACME for the domain is derived-off until then, `../architecture/nest/tls-certificates.md` § B). So **every link of the post-build chain — the Online poll, the claim, and the first main-app session — dials the box at its reach address, on all 7 apps**, while `state.nest_url` stays `https://{domain}` throughout as the *identity* URL: it is what the claim registers and what the account records (the local-target carve-out keys on the handle's `@domain`, never on the dial host — `../architecture/nest/domains-and-tls-bootstrap.md` § Claim). The behavior is uniform; the mechanism is per-target, and that is the one honest divergence: a **native** app dials the domain with a socket-level resolve override (`domain → ip:443`, SNI/`Host` intact) and accepts the self-signed floor provisionally, its trust being the channel binding plus the injected-seed identity root (`../architecture/security.md` § Transport trust, the *Client-provisioned box* row); the **web** app can override neither DNS nor TLS, so it dials `https://{ip}` literally and relies on the box's **IP bridge cert** — a WebPKI-trusted, short-lived Let's Encrypt certificate for the box's own public IP that the nest obtains from first boot (owner: `../architecture/nest/tls-certificates.md` § B-IP) — under the same identity root. Until that cert exists a browser can reach nothing (no DNS wait fixes it, and no test budget does); if it never arrives, the web wizard's only door is the manual browser exception (§ "Almost ready" surface, *web fallback*). The `Online` retry ceiling (480 × 5 s, `fauna-provisioning::progress`) therefore bounds **box boot + image pull + the IP cert's first issuance**, never DNS propagation — a ceiling, not a wait: the poll exits the instant `/health` answers. CORS for the browser's cross-origin poll is pre-settled (`../architecture/provisioning/registry.md` § Health-poll CORS).

**Provisioning = build + claim (ratified 2026-08-29).** `Succeeded` on the standard path means the box is built **and claimed**. The claim is the final substep of `Online` (`SubstepKey::OnlineClaiming`, rendered in the substep row like any other), run by the machine — not by the provider-facing orchestrator crate — the instant `/health` answers, over the pre-identity WS connection at the reach address: `fauna.setup.status`, then `fauna.auth.claim_admin` with the claim code the wizard minted and injected via cloud-init (`../architecture/installers/vps.md` § Admin Claim), the handle's local part and its `@domain` as `mail_domain`. It is **the same core the "Almost ready" surface's `recheck_manual_dns()` runs** (probe → claim → capture the deployment seed → route) — one claim implementation, shared by the in-session finish and the relaunch resume. The user never sees a code, which is what the guide has promised all along ("no claim code to type"). A box that already answers `claimed: true` is the recovery edge (our claim landed and its reply was lost): the machine confirms the box is *ours* by the silent challenge and continues — never a second claim, never an error. A rejected claim marks `Online` `Failed` with the claim's error; Retry re-runs the run (idempotency skips the built steps, re-polls, re-claims — with the code and identity the box was built with, never fresh ones: *The pending-provision slot* below). From `Succeeded`, Continue lands on `NatModeChoice` and the § 3b-bis / § 3b-ter tail runs exactly as after a claim-code submit; the identity is persisted at claim per § 3a's persistence callouts and the home nest at `LoggedIn` (§ Long-term store contract).

**The pending-provision slot — a quit or crash at any point resumes, from the app alone (ratified 2026-08-29).** The claim code exists only client-side until the box is claimed, so an app that dies between minting it and claiming would orphan a box nobody can claim — and a bill nobody can stop from the app — the exact shape `../architecture/nest/common.md` § Client-state recoverability forbids, and the CR-1 discipline answers it: **custody precedes dispatch.** The machine mints the code and the app persists the awaiting slot (§ Long-term store contract — the same per-actor `awaiting_dns` record the deferred-DNS exit writes: `nest_url`, `handle`, `claim_code`, `nest_actor_id` — the identity the box will boot with, the injected seed's derived public key and never the seed itself — and empty `dns_records`) **before `create_server` is called**, then completes it with the box's `reach_ipv4` the moment `create_server` returns; the write goes through the shared per-actor persistence moment (`fauna-client-accounts`), never per-app glue, and is read back like the factory-reset mint. **It registers the identity the box is built for (the slot is per actor) and never moves the active pointer (ruled 2026-09-25):** a first-run identity is already active from moment 1, and an "Add account" (append) identity becomes active only at the wizard's terminal, so an interrupted or abandoned append never hijacks the live session — the append consequences are owned by `onboarding.md` § Multi-account → *Append-mode deferred/incomplete states + abandonment*. It is cleared where every awaiting slot is cleared — the moment is `onboarding.md` § Long-term store contract's (*Mechanism*), not restated here. Consequences, in order: **quit or crash during Server/Dns/Online** → the next launch's awaiting-slot row (§ App-launch routing) lands on the "Almost ready" surface, which polls the box at `reach_ipv4`, claims it with the persisted code, and continues to `NatModeChoice` — nothing to type, nothing lost. **`create_server` failed and nothing was built** → the slot holds a code for a box that does not exist and the surface would wait forever, so it offers a way out (§ "Almost ready" surface, *exit*). **The user never comes back** → the box sits unclaimed on its floor and keeps billing at the provider, exactly as today; the slot resumes whenever they do. **The app's store is wiped** → the box is orphaned (claim-code custody is client-only by design) and the user deletes it at the provider — the one residue, and the same one the deferred-DNS path has always had. A wizard `reset()` ("start over") does **not** clear the slot — only the owner's clearing moment (`onboarding.md` § Long-term store contract) or the surface's explicit exit does — since a re-provision of the same domain would otherwise race the surface for a box that still exists; "Cancel" on this page is soft (resources stay), and the slot stays with them. **The slot is what a re-run resumes from (ratified 2026-08-29).** The Server step's pre-flight is name-only, so a re-run of the same domain — the Retry button, a "start over" onto the same domain, a relaunch onto the "Almost ready" surface — finds the box an earlier run built and skips `create_server`; that box boots with the *earlier* run's cloud-init, and a re-run that minted a fresh code and seed could neither verify it (`nest_actor_id is not the expected nest` — the correct hard-fail, aimed at the wrong box) nor claim it. So a re-run reuses the slot: it re-persists the same row before `create_server` (custody precedes dispatch, unchanged), re-holds the row's `nest_actor_id` as the first-contact root before its first dial — which is what makes the *Client-provisioned box* row's "no TOFU window" (`../architecture/security.md` § Transport trust) hold across a relaunch and not only within the run that injected the seed — and claims with the row's code. Only a Server step that actually **creates** a box (nothing was built, or the box was deleted at the provider) switches the row and the held root to the fresh seed that run injected. The seed is never in the slot: a re-created box gets a fresh one, and the derived public identity is all a resume needs. A same-name box this app never built still hard-fails at first contact — the name-only pre-flight cannot widen trust, only mis-aim it, and the machine logs which — and the machine's own copy of the row drops the moment the box is claimed, so a later provisioning of the same domain is a new box.

**Deferred-DNS path** (`provision_nest_no_dns`, taken when "Set up later" was clicked on step 4): the snapshot still transitions through four entries, but step 1 (Domain) and step 3 (Dns) are `Skipped` (no DNS provider to verify or write to), step 2 (Server) runs (VPS create + cloud-init; no DKIM keygen — DKIM is nest-provisioned post-boot), and step 4 (Online) is `Skipped` (no domain to poll yet, and no claim: the "Almost ready" surface performs it once the user's records resolve). Overall transitions to `Succeeded` immediately after step 2; the result carries the records-to-paste markdown that page 7 renders. The same four-row component handles both paths, and the pending-provision slot is written on this path too (before `create_server`) — its later `AwaitingManualDns` exit only *completes* the record with the records to paste.

### 7. Manual DNS setup (`dns_post_instructions`)

Shown only when "Set up later" was clicked on step 4. Renders the manual records the user must add at their registrar (apex/`mail` `A`, `MX`, `SPF`, `_dmarc`). The **DKIM** record is **not** in this list — it is auto-provisioned nest-side post-boot and published from the `admin-dns` page once the nest has minted its key (`mail-bridge-lifecycle.md` § DKIM provisioning). Single Continue button — `continue_from_dns_post_instructions()` returns `OnboardingStep::Done` and sets `wizard_outcome()` to `AwaitingManualDns`.

## "Almost ready" surface (post-provisioning DNS-pending)

Reached two ways (ratified 2026-08-29 — before that, the deferred-DNS exit
only): **(a)** the **deferred-DNS exit** — the user provisioned their own nest
but chose "Set up later" for DNS, so the wizard exits to `Done` with
`wizard_outcome() == AwaitingManualDns`; **(b)** a **relaunch after an
interrupted provisioning on either path** — the pending-provision slot (§ 6)
routes the launch here (§ App-launch routing), with `dns_records` **empty**
when DNS was not deferred. The app renders the "Almost ready" surface
**whenever `wizard_outcome()` is `AwaitingManualDns`** — it is *not* a wizard
step (`OnboardingStep` is unchanged), exactly as the exit-handling table
prescribes. This keeps the surface uniform across the same-session exit and
the relaunch-hydration path, and avoids growing the `OnboardingStep` enum
(which all seven apps match on).

**Two modes, one page.** The surface differs only in what it says. With
records: "add these at your registrar — we keep checking" (the record list,
the copy button, the recheck button). Without records — the resumed standard
path — the record list is empty and the status row carries the whole story:
"your server is starting; we'll sign you in the moment it answers — you can
close the app and come back." **An empty record list is a legitimate state
here, not the round-trip bug § Implementation status today describes** (that
bug produced an empty list *with* DNS deferred; the two are told apart by the
slot: a deferred exit always completes the record with its records).

Exactly **two** things differ between the modes, and both are derived from the
record list in shared Rust so no app decides either for itself: the resting
status copy (above), and whether **"Copy all" is enabled** — it is **disabled**
in the records-less mode, where there is nothing to copy and a click would
otherwise hand the user an empty clipboard, which reads as a broken page rather
than an empty one. **Disabled, never hidden:** `awaiting-dns-copy-button` is one
of the page's required `elements` in ui.yaml, so removing it in one mode would
be a per-mode element scope no other app could match. Recheck stays live in both
modes — it is what finishes the interrupted setup — and is disabled only while a
probe or claim is actually in flight.

**Reach.** The poll dials the box at the slot's `reach_ipv4` (§ 6 *Reaching
the box* — native via the resolve override the seeder re-arms, web via
`https://{ip}` under the IP bridge cert). A slot without `reach_ipv4` (a crash
between the mint and `create_server` returning, or a pre-2026-08-29 record)
dials `nest_url` and simply waits for DNS, as before.

**Identity.** The seeder re-holds the slot's `nest_actor_id` — the identity
the box was built with — as the first-contact root for the identity URL's host
before the first poll, so the resumed claim verifies the box it was told about
(the *Client-provisioned box* row, `../architecture/security.md` § Transport
trust: no TOFU window, across a relaunch too), and retains the row as the box
in flight, so a "start over" onto the same domain afterwards resumes it (§ 6
*The pending-provision slot*). A pre-field slot pins nothing and polls as
before.

**Exit.** The surface carries an explicit way out — "Use a different nest" —
for the box that will never answer (a `create_server` that failed after the
slot was written; a box deleted at the provider): it clears the slot and lands
the wizard at `handle_entry`, mirroring `launch_retry`'s
`launch-fallthrough-button`. Without it the resumed standard path is a
`CR-2`-shaped trap (`../architecture/nest/common.md` § Client-state
recoverability): a launch that can never leave a waiting page. Its element is
`awaiting-dns-fallthrough-button` (rule-A approved 2026-09-25); the machine's
`abandon_awaiting_manual_dns` is the one door — it clears the slot of the
identity being onboarded (through the injected pending-provision store, addressed
by that identity's secret, since on an append run the active account is a
different one) **before** it moves its own state, then lands `handle_entry`
holding the same identity, so a crash between the two relaunches onto the
surface with the exit still on it. The button is live at rest in both modes and
in every probe state, and off only while a claim is in flight
(`awaiting_dns_fallthrough_enabled`): a box that never answers spends its life
in `Checking`, and the exit exists for exactly that box.

**Web fallback (the manual browser exception).** When the IP bridge cert
cannot be had (CA outage, `:80` blocked at the provider) a browser cannot
reach the floor at all; after an Online-ceiling's worth of waiting the web
surface says so and names the one remaining door: open `https://{ip}` in a new
tab, accept the browser's security warning (a per-origin exception the SPA's
fetches and sockets then inherit), and come back. It is the only door that
has ever worked on web (found 2026-07-24, § 2) and it is ugly — a documented
fallback, never the primary path, built only once a bridge-cert-unavailable
case is actually observed.

**Where the logic lives:** shared Rust (`fauna-onboarding-machine`), like
every other onboarding flow. The machine owns:

- `awaiting_manual_dns_snapshot() → AwaitingManualDnsSnapshot` — the records
  to display plus an `AwaitingDnsState` (`Pending` / `Checking` / `Claiming`
  / `Claimed` / `Error { cause }`) and a `LocalizedText` message.
- `recheck_manual_dns() → OnboardingStep` — the polling method (below). The
  app calls it on a timer while the surface is shown, **single-shot**,
  mirroring `recheck_invite_status` (the app owns the cadence; the machine
  does not run an internal interval — this keeps native and wasm identical).
- `seed_awaiting_manual_dns(nest_url, handle, dns_records, claim_code)` — the
  relaunch hydration (after `seed_identity`).

**Transport — pre-claim = pre-identity WS-RPC (migration DONE).** Every
probe on this surface runs *before* the nest is claimed, so there is no
authenticated *actor* session — the probes ride the **pre-identity
(anonymous) WS-RPC kinds** (`fauna.setup.status`, `fauna.auth.claim_admin`,
per `docs/goal/architecture/transport-connection.md` § Pre-identity (anonymous)
connection). In production the onboarding machine drives them over
**`WsNestApi`** — the `NestApi` seam backed by the anonymous WS connection
(`libs/fauna-onboarding-machine/src/machine.rs`); the former HTTP twins
(incl. `GET /api/v1/setup-status`, retired in S4c2) are deleted. Each
`recheck_manual_dns()` does:

1. `fauna.setup.status` (over the `NestApi` trait, now backed by the anonymous
   WS-RPC connection) as a combined reachability + claim-status probe. A
   *transport* failure means DNS hasn't propagated yet **or** the nest is still
   booting — both surface to the user as "still waiting", so the machine does
   not distinguish them (snapshot stays `Pending`, the app keeps polling). The
   one probe failure that is NOT "still waiting" is the **typed identity
   verdict** — the probe's fresh connection failed first-contact graduation
   against the held root, i.e. the server that answered is not the box this
   client provisioned (`../architecture/security.md` § Pre-claim surfacing):
   that is terminal, never another poll.
2. If reachable and `claimed == false`: `fauna.auth.claim_admin` with the
   saved claim code + an Ed25519-signed payload (the same call
   `wizard_submit_claim_code` makes).

On a successful claim the machine routes to the post-claim setup step —
`NatModeChoice` (§ 3b-bis), **exactly the path `wizard_submit_claim_code`
takes**, clearing the awaiting outcome. (Recovery edge: if the probe reports
the nest is *already* claimed, the machine skips `NatModeChoice` and concludes
without re-claiming — through § 3b-ter's trust offer, which `onboarding.md`
§ 3b-ter rules is due on this route too (2026-09-21); a no-modes nest has no
unresolved setup state to check.)
Transient
failures (nest unreachable, 5xx on claim) leave the snapshot `Pending` so
polling continues; a rejected claim, a corrupt identity, or a first-contact
identity mismatch on any leg (`../architecture/security.md` § Pre-claim
surfacing) yields a terminal `Error`.

## Reach hint — the session reaches a freshly-provisioned box before its domain is live (ratified 2026-08-29)

Claiming the box is not the end of the DNS wait. `LoggedIn` hands the app
`nest_url = https://{domain}`, and on a Hetzner-published zone the domain may
not resolve for hours (§ 6 *Reaching the box*). Without help the first
main-app session fails — it dials by domain — and the user who was just
"signed in as the owner" meets a disconnected app, and on relaunch the
`launch_retry` surface. So the reach address outlives the wizard as the
account's **reach hint**: `reach_ipv4`, persisted per-actor beside `nest_url`
(`../architecture/long-term-store.md` § Multi-account evolution) by the shared
`LoggedIn` moment (`persist_logged_in`), read off the machine at the terminal
exactly like the deployment seed is. The rule lives in shared Rust — the launch
machine's silent challenge and the session connector, never per-app glue:
**dial the domain first; if that fails to connect (unresolvable, refused, or —
on web — untrusted), dial the hint — native as the resolve override with
SNI/`Host` = the domain, web as `https://{ip}` under the IP bridge cert; the
first successful domain dial deletes the hint.** **The hint moves the socket
and nothing else: on both arms the identity key stays the domain's**
(`../architecture/security.md` § Transport trust), so the app opens
**connected** at wizard exit and on every relaunch, on all 7 apps, and the
switch to the domain is silent by construction — one pin per box, nothing to
carry between authorities. A hint gone stale (the domain re-provisioned onto a
new IP) is refused rather than merely unlucky: the box answering at the
recycled address is judged against the account's *domain* pin — held from the
claim itself onward (`../architecture/security.md` § Transport trust, the
claim-seeded pin), so even the account's *first* post-claim contact is a
verify, not a TOFU — and cannot pass it, and the failed fallback is deleted on
the next domain success. Trying the
domain first is an availability rule, not the safety one — the safety comes
from the key. What the user sees while the hint is in use: nothing — no banner, no
degraded chrome; where DNS propagation is *shown*, on request, is the
`admin-dns` page's existing record verification. The hint is a bucket-1 fact
(auto-captured, never a knob) and a pure optimization: an app without it — a
pre-2026-08-29 record, or a second device signing in by handle — behaves
exactly as today and simply waits for DNS.
