#### Shared sets on a capability host (decided 2026-09-26; decisions 1 and 2 BUILT 2026-09-27; decision 2′ — the unreachable nest — ruled 2026-10-01, BUILT 2026-10-02; 4 built, not enabled; 3 answered 2026-09-30 and BUILT 2026-10-01 in shared Rust and on android, 2026-10-03 on apple; the agent's convergence BUILT 2026-09-27, the one builder and its cross-nest arm 2026-09-28; decision 1′ — the plane read — ruled 2026-09-30, BUILT and wired 2026-09-30 but for the apple credential store's item)

**What this rules.** A **capability host** is any on-demand host built through the capability constructor — the owner `BackupKey` plus a bearer, never the identity seed: apple's extension today, android's provider when it lands. Until this section such a host could serve owner-only sets alone. A set bound to an MLS group — a shared set, [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 content-key mechanism — failed closed at the engine build, so an owner's set stopped opening in Files the day it was shared, and a set shared *with* the user had no on-demand presence at all. The four decisions below close that for every capability host alike; none of them has a per-platform variant. The cross-user transfer plane's phone legs stand on the result ([`p2p-shared-set-build.md`](p2p-shared-set-build.md) § Cross-user shared-set transfer → *Phone peers — design*, the first of its three gates).

**1. The host loads custody itself — nothing is provisioned beside the `BackupKey`.** The content keys of a bound or WebDAV-served set rest in their holder's custody (the M2 *Custody* rule) — the plane kind `fauna.state.folder-keys` since the dissolution cut the field (2026-09-30), which a capability host reads as decision 1′ below rules; before the cut, the `__config` blob, sealed under that holder's `BackupKey` (the rail itself retired 2026-10-02 — [`../architecture/config-dissolution.md`](../architecture/config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)). That at-rest blob carried no signature envelope, so the `BackupKey` alone opened it — the seed was never load-bearing for those bytes, which is what already let the seedless sync agent host the account store. A capability host therefore resolves a set's keys as a seed-holding host does: from the same custody, over its own bearer connection, held in memory for the life of the engine and never written to disk. The app provisions **no per-set key** — not in the shared Keychain, not in android's secure storage, not as a constructor argument. *Why not provision them today:* while the host holds the `BackupKey`, a provisioned key narrows nothing (the `BackupKey` already opens the custody that holds every generation), and it would add a second channel that can go stale, a push on every custody change in two shells, and a rotation that cannot reach a host whose app is not running (decision 2). *Blast radius:* unchanged. The capability is still the `BackupKey` and a bearer; what is new is only that the host uses a breadth Phase 1 had already accepted. The seed stays out of the host (rule #6), and so does every piece of MLS state (rule #7): a capability host is never a group member, opens no envelope and ingests no custody. A generation reaches custody only through an identity-holding app of the same user — the owner's rotating device, or a member's custody-ingest leg — and the host reads what that app wrote. *What a removed member's host keeps:* nothing at rest. The generations that member held stay in their own custody, as on every device of theirs (content they could already read — M2 *Rotate-on-removal*); the set's row leaves their folder list, so their host's next build refuses and the plan drops the set; and content sealed after the removal is stamped with a generation their custody never receives, which fails closed. *One later addition to what the app provisions (ruled 2026-09-27, unbuilt):* the machine principal's writer key and its `DeviceAuthorization`, beside the bearer and over the same channel, so the host signs what it records — the design, the why (a device key is neither the seed nor MLS state) and the macOS/iOS split are [`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, ruling (1).

**This is Phase 1's mechanism, and Phase 2 supersedes it.** *Who runs the hydration host* above names the end state, a host that holds only its folder's key. The two statements are phases of one design, not alternatives: custody load is how a host that holds the `BackupKey` comes by a shared set's keys; the day owner-only content moves to per-folder keys and the `BackupKey` leaves the host, custody is no longer the host's to open, and each set's keys are delivered to it as a capability. One constraint on that delivery is recorded now, because this pass measured it: it must reach a host whose app is not running, from any of the user's identity-holding devices, through the nest — so a device-local hand-off from the app (a Keychain write, an in-process call) cannot be the whole of it.

**1′. On the plane, the host loads custody as the enrolled device it is — a throwaway fleet-scope replica keyed by the machine principal's wraps (ruled 2026-09-30; the shared-Rust half and the engine cut BUILT 2026-09-30, the apple store's item UNBUILT — *Implementation status* below; the build rows are at the end of this paragraph).** The dissolution moved shared-set custody off the `__config` blob onto `fauna.state.folder-keys`, a fleet-only kind sealed under the account's generation tip ([`../architecture/config-dissolution.md`](../architecture/config-dissolution.md), the kinds table), and the `BackupKey` deliberately does not reach a random generation — removed devices keep it ([`../architecture/owner-key-material.md`](../architecture/owner-key-material.md) § Path A-sibling-2, the generation axis). So decision 1's read stops working the day the cut lands, and no goal doc said how a host that hosts no account store reads a plane-only kind: the apple extension can reach no store root but its own container ([`on-demand-files-apple.md`](on-demand-files-apple.md) § Apple File Provider binding, *state unification*), and android's provider builds its hosts with no runtime running ([`on-demand-files-android.md`](on-demand-files-android.md) § Android SAF DocumentsProvider binding — a provider the OS starts for another app's picker has no app session). The ruling: **a capability host is a process of an enrolled device, and it reads a fleet-only kind exactly as an enrolled device does — from the wraps the plane addresses to the machine's device key.** The machine principal's writer secret is already in every capability host (the signer ruling, [`../architecture/writer-signed-change-records.md`](../architecture/writer-signed-change-records.md) § Writer-signed change records, ruling (1), *The capability host*), and that secret derives the device's X-Wing KEM keypair — the target of the inline member wrap on every mint and of every top-up row the fleet writes for the device — so nothing new is provisioned for the read. The mechanism is the box-recovery cold read's ([`../architecture/nest/box-recovery.md`](../architecture/nest/box-recovery.md) § The plane-era recovery floor, *(b)*; `fauna_account_plane::deployment_seed_recovery::cold_read_deployment_seeds`), generalized to a second key source: a **throwaway replica** — an `AccountStore` on the in-memory backend under an ephemeral writer key that is never published, a **pull-only** fleet plane over the host's own bearer connection (no walker mark, no publish path: the nest records nothing for the walk and the host authors nothing on the plane) — walks the `state-fleet` scope, keys every walked mint through the device arm (this device's inline wrap or top-up row, opened with the KEM secret against the mint's key commitment) or through the custody it holds, reconciles, and folds `fauna.state.folder-keys` through the plane's own door (`read_folder_keys` → `FoldersConfig::fold`). Everything the replica applies runs the plane's own code — the same writer-signature check, the same trial open, the same join — so a row the host folds is a row every replica folds; the plane's trust (prior tips, escrow holders) gates only sealing, and the host seals nothing on the plane. The replica is **one per (process, account)**, shared by every per-set host in the process and held for the process's life: decision 2's edges become one incremental walk each (the plane's stored frontier), and a process the OS kills starts from a full walk of the fleet scope — the account's fleet-only state, one scope, never the delegable `state` scope and never a content scope. **Retained keys — the host's custody is the credential store it already reads its signer from.** A generation this device obtained without a wrap on the plane — recovered from escrow at a seed-holding sign-in, or a top-up the reclaim pass has since retired because the app consumed it — is in the machine slot's `generation-keys` carriage and nowhere on the plane (the top-up pass never self-wraps: a self-wrap is noise to a store that persists its keys), so the host needs that custody beside the wraps: on **android** the host reads the machine slot itself, as it reads its signer (`SlotChangeSigner`), the slot's `RetainedKeyCustody` is its custody, and its own unwraps are recorded there exactly as the runtime's are; on **apple** the app-group credential store (`FileProviderCredentialStore`, the single-slot store that already carries the `BackupKey`, the bearer, the writer secret and the `DeviceAuthorization`) gains a `generation-keys` item, the **app** mirrors the machine slot's carriage into it on every slot write (the signer watch that already re-provisions the signer, the same trim as the slot's), and the **extension** records into it every generation it unwraps itself — so an app-dead mint reaches the extension by its wrap, an escrow-recovered generation by the mirror, and a generation the extension opened once needs neither again; both are the same custody class as the `BackupKey` beside them. *Blast radius — stated, not softened:* a capability host holds the whole device bundle, the `BackupKey` and the machine principal's secret, and so opens every fleet-only kind the machine's own apps open, not the one kind it needs. That is no more than the blob rail allowed (the `BackupKey` opened the whole `__config` blob, every field, until the rail retired), no more than the app process whose trust boundary it shares, and it brings the generation axis's removal severance with it, which a `BackupKey`-only custody never had: a removed device's host stops keying new generations because nothing wraps to it, and its bearer dies with the device row. What the dissolution would otherwise have narrowed for the host, it does not — that narrowing is Phase 2's, and Phase 2 now has two things to take out of the host, the `BackupKey` and the machine principal's secret: a Phase 2 host signs under a per-host key the device certifies and receives its folder's key as a capability, recorded here, not designed. *Rejected:* mounting the machine's account store (the sandboxed extension cannot reach the user domain — the two-domain law; on android it would tie a provider the OS starts for another app's picker to a runtime only a sign-in assembles; a store the iOS extension shares with the app through the container forks the mechanism per OS); the app provisioning per-set keys (decision 1's own argument — the rotation that must reach a dead app cannot); a copy of the slot's carriage alone, with no wrap read (the same hole: a mint made from another device while the app is dead never reaches it); pulling Phase 2 forward (a per-folder owner key for owner-only content and a per-host delivery kind are a design of their own, and the cut needs neither); a second reader outside the plane's code (one verifier — a row's admission is decided in `apply`, once); a blob mirror kept for these hosts (an E3 kind is born plane-only, `config-dissolution.md` P5). **A host whose machine has no principal yet reads no custody** (it has no device to read as): a bound set builds keyless, and an own set whose records are signed lists nothing — no row verifies without the set nonce custody holds — while every write is held with the reason; it rebuilds, over the custody it can now read, at the first refresh or seal that finds a principal provisioned. The replica is one per (process, account, nest), rebuilt when the principal is re-minted or the `BackupKey` it is handed differs, and it brings its own bearer connection up — no host's build connects it. The desktop sync agent is not this case: it hosts the machine's store (the seedless host) and reads the kind through its own handle; where that store cannot mount — a slot with no app-enrolled `BackupKey` — custody is unreadable and every bound set builds keyless until the machine signs in once, the refusal's own recovery.

**2. Rotation: the host re-reads custody at its own edges, and enforces the generation floor itself.** A set's keys are final at engine build, and an app-dead host has no app to rebuild it, so the host re-resolves on its own evidence at three edges: at **every build**; at **every refresh**, when the set's binding, the caller's access, or the set's content-key floor (the owner-stamped current version the nest keeps beside the set's envelope, which the set's row carries — [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 → *Multi-writer*) differs from what the engine was built on, or when that floor is still ahead of the generation the engine holds (custody arriving is not visible on the row, so a host behind the floor re-reads at every refresh until the generation is there); and **before a seal** — every write, a delete included, since a recorded path seals under the same generation — when that floor is ahead of the generation the engine holds (a row that cannot be read is decision 2′'s case: the seal stands on the last floor read, and nothing it produced is published to a nest until the row reads). Re-resolving is a custody re-read and an engine rebuild over the same state DB — never a domain removal, never a re-population. A set whose row is gone (deleted, or the caller removed from it) rebuilds into a refusal. A host that still lacks the generation after the re-read **fails closed per operation and keeps serving the rest**: a body stamped with that generation does not open (the fetch fails with the platform's error, never a stand-in body; the file's path rests sealed under the same generation — [`file-sync.md`](file-sync.md) § Sealed names & paths — so it does not list either), and a write is **neither sealed under the older generation nor acknowledged** — the edit stays where an un-recorded edit stays (the OS's pending queue on apple, the kept root on android) and is sealed when the generation arrives. The host holds an **owner's** sets to the floor exactly as it holds a member's. The nest's own floor exempts owner devices, because an owner's resident engine is re-keyed by the app that rotated; a capability host has no such trigger, and without its own check an owner's phone would go on sealing new files under the generation a removed member still holds. *The limit:* if none of the user's identity-holding apps has run since the rotation, the generation is not in custody and the host waits, failing closed, until one does. That is the price of keeping MLS state out of the host, and it is paid in availability, never in confidentiality (the one bound on that sentence is a rotation an unreachable host cannot learn of, on the peer plane alone — decision 2′). **A fourth edge, for a host that holds a live nest connection (added 2026-09-27; the nudge moved to the plane 2026-09-30).** Every `fauna.account.state.put` fans a `SyncChanged` nudge tagged with the written scope out to the writer's own connected devices ([`../architecture/account-data-plane.md`](../architecture/account-data-plane.md) § Nudges and backstops; the emit is the nest's `sync_handlers`), and every custody change — a rotation, a share, a serve or paywall flip, a member's ingest — is a write to the fleet scope (`state-fleet`), since custody is the fleet-only `fauna.state.folder-keys` kind. A host whose bearer connection carries pushes re-resolves on that nudge once the account store it reads through has walked the rows in, whatever the row says; the three edges above stay the correctness backstop, because the nudge is best-effort by construction. A host that reads custody through an account store it mounts reads that store's local rows, which only a walk brings in — so an edge whose re-read still leaves a bound set behind its floor or keyless has the store run a pass and reads once more: a lost nudge is healed by the edge that noticed it, not left to the store's own backstop. The desktop sync agent is the first such host (*One mechanism* below); a control-inverted extension, woken by the OS per request, has no standing connection and keeps to the three.

**2′. The nest unreachable: the floor gates what is published to a nest, and a seal stands on the last floor the engine read (ruled 2026-10-01; user-ratified 2026-10-16, the cost named below accepted; BUILT 2026-10-02 — *Implementation status* below).** Decision 2 as first written held every write whose pre-seal row read failed, and [`p2p.md`](p2p.md) § Cross-user shared-set transfer has a file authored with no nest in reach arrive on another member's device peer-to-peer. The own-pending row that plane serves is minted from the write's seal ([`p2p-shared-set-build.md`](p2p-shared-set-build.md) § *Build design — the row half*, the own-pending bullet), so on a resident host the hold removed the feature: the two could not both stand. The rule is one rule — for every host, for every writer (an owner's device and a writer member's seal through the same code and under the same generation, [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 → *Multi-writer*) and for both arms. **(a) A floor the host has read binds it whether or not the nest is in reach.** A generation behind the last floor read is never sealed under, and a row the last successful read found gone holds every write — decision 2 unchanged, offline as online. **(b) A seal stands on the last floor the engine read.** Every engine is built on one — a same-nest set's row, a cross-nest set's custody record — so when the pre-seal read fails, the engine seals under the generation it holds, that generation having met the last floor it read, and mints the write's own-pending row; the peer plane serves it as it serves any row. **(c) Nothing reaches a nest without a floor check made against a nest in reach.** A pass whose pre-seal read failed publishes nothing it sealed — no chunk, no manifest, no record — and the write stays un-acknowledged where an un-recorded edit stays. The control plane the read rides and the byte plane are separate connections, so this is a gate the engine enforces, never a side effect of being offline. The first pass that reads the row again decides: the floor still met, it publishes what it sealed (the seal is convergent, so the bytes are the ones peers already hold); the floor ahead, (a) holds until custody brings the generation, the write is re-sealed under it, the re-mint replaces the pending row, and what was queued under the older generation is completed unpublished (the drain's never-publish-prior-generation rule, [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 → *Multi-writer*). **(d) An own-pending row stamped below a floor the host has since read is withdrawn from the peer door** — the host now knows that seal is behind. *The two arms differ only in who makes (c)'s check.* A cross-nest set has no row here: its floor rides the custody record (*One mechanism* below, question 2), its engine has sealed on the last recorded floor since 2026-09-28 — which is (b) — and its publication check is the home nest's `stale_content_key` refusal, which never exempts the caller, always a member there. A same-nest host makes the check itself, because the nest's floor exempts an owner's devices. *A control-inverted host* (the File Provider extension, android's provider) acknowledges only what is recorded, so its write stays un-acked through an outage exactly as before; it serves no peer plane today, and its phone-peer leg inherits (b) when it lands ([`p2p-shared-set-build.md`](p2p-shared-set-build.md) § *Phone peers — design*). **What it costs, stated, not softened.** A person removed after the host's last floor read, whom the host still admits at the peer door — admission reads the MLS roster the device holds, and a removal reaches that roster through the nest too — can open what that host authors until it next reaches a nest, taken from that host or from another member's device that relays the row and has not learned of the removal either. Never from a nest: that is (c). So decision 2's *never in confidentiality* holds for everything published to a nest and for every rotation a host has read, and is bounded, on the peer plane alone, by what an unreachable host can know — the bound that plane already carries for its writer roster ([`p2p.md`](p2p.md) § Peer-served change-row provenance: the last roster stands offline and honors a recently demoted writer until reconnect). No staleness limit is set on (b): the roster and brake caches beside it carry none, the scenario the peer plane exists for runs for days, and a limit would be a number no user chose. *Rejected:* keeping the hold and re-stating the peer plane's promise as *a file recorded before the outage* — it deletes offline authorship, the own-pending leg's whole purpose, to close a window that needs a removal the host has not seen, the removed person within peer reach, and an outage, all at once; exempting the owner's resident engine — the trigger that exemption rested on was retired 2026-09-27 (the agent re-keys itself, [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § Implementation status today), and it would leave a writer member's identical seal held; a time limit on (b) — above.

**3. The presence plan: every folder this device is a delivery seat for, the account's own or shared with it (the user's answer, 2026-09-30: yes and yes).** Desired sets = (the account's own folders ∪ the folders shared with it) where this device is a delivery seat ∩ toggle-enabled ∖ the sets this device presents another way (apple: a bound location; android: an ingress). An owner's set does not leave the plan when it is shared: being bound to a group changes its keys, not its ownership. **The user's answer (2026-09-30):** a folder shared *with* the user appears in Files (iOS, android) and Finder (macOS) by default, as the user's own folders do, and `folder-on-demand-toggle` renders on a member's row as well as an owner's, so a member can hide it ([`../ui/folders.md`](../ui/folders.md) § Element IDs) — so the arm is ON, and nothing below is gated on a question any more. **What makes a device a delivery seat differs by role, and the difference is forced by where the device roster lives.** For an own folder it is the mode-free rule (*Auto-appear default-ON* above): this device's place has `accepts: true`. For a folder shared with the account it is **the membership itself**: the device roster is the *owner's* — a member's device holds no row in it and has no door to write one (the roster kinds resolve a folder by name among the caller's own) — and the engine already reads a member's absent seat as accepting (`fauna_sync_engine::config::accepts_from_seat`). Accepting the share is the member's yes, the toggle is how one device says no, and the toggle on a member's row is hide-only: it never writes a place. A member's seat is therefore never read through the roster — which is also what keeps a by-name roster read from answering for an own folder that wears the same name. **A shared folder joins once it is accepted, never when it is merely offered.** The nest lists a member row as soon as the owner rosters the account, before the member has joined the group, so the plan admits a shared folder only once the account's custody holds its content keys — the evidence the member's custody-ingest ran — and a folder from another nest once its custody record exists (written at accept; a record with no set name is not bindable and stays out). A stranger cannot put a folder into the user's file browser, and a folder whose keys custody does not hold could not list a single path anyway (decision 2). A shared-with-me set joins under the same per-set toggle, keyed by the same actor-scoped identifier, with the same default (ON — a placeholder tree costs metadata only); its display name carries its owner — `docs (alice)`, the owner's account display label ([`value-formatting.md`](value-formatting.md) § Account display label) — because a member can hold a set that wears the name of one of their own; a cross-nest set carries its owner's canonical `handle@domain`, as its home nest stamped it and the member's own nest verified it ([`../architecture/federation-shared-folders.md`](../architecture/federation-shared-folders.md) § Cross-nest shared folders + channel append → *The cross-nest owner label* owns the stamp, its trust rule and the record's join rule), and its home nest's host until that pair lands. **One mapping, in shared Rust:** `fauna_folders_machine::on_demand_presence::held_sets` turns the member-visible folder list and custody into the plan's input — role, seat, display name, and whether the account only reads the set — so no app maps a row itself. **A reader's host is read-only by construction, not by refusal:** it is built with no write half, the provider advertises no write, create, delete or rename capability on its items, and so the OS never hands it an edit. That is why the rule that a reader runs no engine ([`file-sync.md`](file-sync.md) § Multi-writer shared sets) does not reach it: the rule guards hosts over a directory the user can write behind the engine's back, where an edit that cannot upload would break *a change to a tracked file MUST be uploaded*, and a control-inverted host has no such directory. The host learns which it is from the set's own row at every build and edge, never from its caller: a reader granted `writer` rebuilds two-way at its next refresh, a writer demoted to reader rebuilds read-only at its next write's row read, and a write that reaches a reader's host anyway is refused with a typed refusal before anything is sealed, recorded or moved on disk — its sweep ingests nothing and it drives no re-seal. A writer's host is the ordinary two-way host. A cross-nest set's grant is the home nest's advisory stamp on the custody record (absent ⇒ reader); the home nest's write-token mint stays the enforcement. The binding's reader flag also picks the byte plane's bearer: a reader's engine takes the read token ([`../architecture/federation-shared-folders.md`](../architecture/federation-shared-folders.md) § Cross-nest shared folders + channel append → *Relay serving across nests*), never the write mint, which refuses a reader and would park it as a demoted writer; a writer's takes the write token. **What the two legs this once waited on still owe: nothing.** Member custody-ingest and the `writable_folder` gate family are built ([`../ui/folders.md`](../ui/folders.md) § Sharing → *Member custody-ingest read leg*; [`file-sync.md`](file-sync.md) § Multi-writer shared sets, same-nest).

**4. The day an own set is shared, nothing is removed and nothing is re-populated.** The set's `FolderRef` is stable across the transition (*A location binding identifies its set by a `FolderRef`*, above), so the domain, the state DB and every hydrated body stay where they are. The host observes the bind at its next refresh edge (decision 2) and rebuilds bound. What it must still be able to open is the content recorded **before** the bind: those records carry no generation stamp and rest under the owner root until the pre-bind re-seal pass moves them. That pass, and the two changes this decision asks of it — it runs nest-sourced on an owner host that holds no resident bytes, and the owner's bound reader opens an unstamped record under the owner root — are owned by [`../architecture/mls-group-key-material.md`](../architecture/mls-group-key-material.md) § M2 → *Pre-bind re-seal migration*. With them, every pre-bind file the owner's **pre-bind ledger** names stays openable on the owner's device through the transition — the ledger, its bound and the cases outside it are that section's *provenance ruling* — and a member sees a pre-bind file as a placeholder that opens once the owner's pass has reached it.

**One mechanism — the agent converges (decided 2026-09-27; the convergence BUILT 2026-09-27, the one builder and its cross-nest arm BUILT 2026-09-28, the federated floor BUILT 2026-09-28).** The desktop sync agent is a capability host too (`BackupKey` plus a bearer), and until this ruling came by the same keys another way: the identity-holding app resolved custody and pushed the result into the agent's capability, re-pushing on every custody change, with a retry and an app-derived *Keys pending* state around the push. That predates the seedless custody read the agent already runs for the account store, and it has the hole decision 2 names: a rotation made from any other of the user's devices reaches the agent only when the desktop app next runs — the nest's floor exempts an owner's uploads — so an app-dead agent goes on sealing under a removed member's generation. **The ruling: the agent is a decision-1 host and re-resolves at decision 2's edges, the custody nudge included** (the `__config` nudge until the dissolution's cut, the `state-fleet` nudge since 2026-09-30)**.** It resolves every set's keys in-process — custody through the account store it mounts (decision 1′; `ConfigClient::seedless` under the `BackupKey` it holds until the cut), the list over its own bearer connection, the same `fauna.folders.list` read and the same two resolvers as today's producer (the same-nest rows and the foreign union of custody's `ForeignFolder` records), given a seedless credential — and holds them in memory for the engines' life; the app provisions no per-set key. It re-resolves at every reconcile, on the nudge, and at its resident loop's per-tick row read when the binding, the access or the floor moved (a stamp change rebuilds the engine over the same state DB, as the re-push did), and holds a write un-acked while the row's floor is ahead of what it holds — an owner's sets as a member's, one implementation shared with the control-inverted host. Custody unreadable ⇒ a bound set builds keyless and fails closed per operation until an edge re-reads it; the edges are the retry, and there is no attempt budget. **Retired with it:** the pushed `content_key_bindings`, the resolve-before-provision withholding, the shared retry driver, every app-side trigger (login, bind, share, remove, the member custody-ingest observer hop — the ingest itself stays, it is the custody write the nudge announces) and the app-derived *Keys pending* input. **A remote create into an already-listed directory materializes — LANDED 2026-09-29 ([`on-demand-files.md`](on-demand-files.md) § On-Demand Files → *Sync direction*, in the create direction; the gap is `delete-propagation.md` § *The floor on an on-demand root*, decision (f)).** cfapi lists a directory once — `transfer_placeholders` completes it `DISABLE_ON_DEMAND_POPULATION` — so a fold that only wrote rows left a file created on another device invisible here: in the root until the next restart re-armed it, in a browsed subdirectory for ever. The fold now names its brand-new rows (`PlaceholderFold::created`, shared Rust) and the hydration loop's `apply_fold` pushes each onto disk (`bridge::materialize_created` → `fauna_cfapi::create_placeholder`), pushing `FileStatusChanged{CloudOnly}` for it: the row's path is walked down to its first segment not on disk, and that segment — the file, or a new directory left to list lazily on its own first browse — is created **only if its parent is already listed**. The discriminator is the OS's own answer to "will it ever ask again?": `fauna_cfapi::is_listed_directory`, `CF_PLACEHOLDER_STATE_PARTIAL` clear (measured: a never-browsed root `0x33`, browsed `0x3`; a never-browsed subdirectory `0x39`, browsed `0x9`); unreadable reads unlisted, so a directory still to be listed always gets the row from its own listing, never from a pushed twin. A successful create marks the row *seen* (decision (a) of the delete ruling), through the same `HydrationHost::mark_seen` a listing's placeholders take.

**Two-way on-demand folders — LANDED 2026-07-14 (USER-ratified the same day; [`on-demand-files.md`](on-demand-files.md) § On-Demand Files → *Sync direction*).** The Windows on-demand host uploads local edits, so a tracked file's change reaches the nest from an on-demand folder exactly as it does from an always-resident one. No new user-facing setting was needed: two-way is simply what a synced folder does.

*What it was.* The host was **one-directional**, in breach of the iron rule. Measured live 2026-07-14: a user edited a tracked placeholder; two subsequent rescans logged `placeholders=0`, the `transfer_queue` stayed empty, the sync-state row stayed `placeholder`, and the badge went on claiming `CloudOnly` — the edit was neither uploaded nor surfaced as a conflict. The root cause was a **missing capability wearing a policy's clothes**: `run_on_demand_root` constructed no file watcher, so Windows had no way to *learn* a local write had happened, and the code's own promised remedy (*"a later reconcile pass resolves the conflict"*, at the invalidation gate) was never built — `run_hydration_loop` had only cancel / rescan / reconnect / fetch arms. It had been written up as "download-only by design"; it was a bug.

*How it works.* The on-demand root drives the **shared** `fauna_sync_engine::always_resident` watch→`upload_file` loop — **one uploader, not a second implementation** (priorities #2/#4). `run_hydration_loop` now runs `LocalWrites` (watcher + debouncer + `is_user_write`) as one cancel-safe `select!` arm alongside the cfapi read callbacks, plus `LocalWriteHost::converge` (drain → reconcile → `upload_pending`) at startup and on the rescan tick as the backstop for edits made while the service was down. **The rule is enforced by the type system, not by a comment:** the write half is the shared `LocalWriteHost` trait, and the host's `HydrationHost` **requires it as a supertrait** — so a download-only on-demand host no longer compiles. (`libs/fauna-cfapi` registers no `NOTIFY_*` callbacks *for the upload path*, and does not need to: the shared `notify` watcher — `ReadDirectoryChangesW` under the hood — observes the write, and the placeholder guard is what makes that safe on a cfapi root. It *does* register `NOTIFY_DEHYDRATE_COMPLETION`, but only to keep the sync-status **row** honest when the OS frees a file's space — a read-only observation, entirely outside the write path; see § Per-file sync-status display → *Windows OS shell-overlay carve-out*.)

*Two consequences worth naming.* (1) **`EngineRole` is gone.** It existed to hand the on-demand root an *empty* `IgnoreMatcher` ("a download-only host makes no local writes to ignore") — which became a bug the moment the root uploaded, since an ignored file would be uploaded the first time the watcher saw it. Both roots now load `.faunaignore`, the role had no other effect, and it was deleted. (2) **Backup + on-demand is fixed by construction.** A `Backup`-mode set bound to an on-demand folder used to be inert in *both* directions — and because no change was ever *recorded*, the snapshot scheduler never ran either, so there was **no point-in-time recovery at all** (`backup-restore.md` § Snapshot scheduling). Backup has no separate change detector: it *is* this shared watch→upload loop. Since the folders re-model's phase 3 head unification (2026-08-17), an ordinary folder — a backup one included — records to `sync_changes` exactly like any other; only a **reserved** (`__*`) custody-copy cross-location backup-destination set routes to `backup_custody` (`is_reserved_custody_copy`, `bins/fauna-nest/src/db/snapshots.rs`).

*Pinned by* `cfapi_live_integration.rs` — headless, against a **real cfapi sync root**, with the **real `SyncEngine::upload_file`** (the harness host delegates its write half to a production engine; only the three nest-facing calls are faked, and the byte plane is a wiremock nest so an upload has somewhere to land): `a_local_edit_by_another_process_is_detected_and_uploaded` (which *also* pins that hydration must **not** echo straight back up — the watcher sees our own hydration write, and only `mark_hydrated`'s recorded content identity stops the re-upload) and `a_backup_mode_set_on_an_on_demand_folder_uploads` (a new file is adopted and uploaded, **while the cloud-only placeholder beside it is never touched** — our own `CfExecute(TRANSFER_PLACEHOLDERS)` materializes files the OS reports as ordinary `Created` events, so telling them apart is the watcher's job).

**The placeholder-safety guard is LANDED (2026-07-14)** — the prerequisite, and the half that was actively dangerous. `fauna_sync_engine::placeholder` now recognizes a cloud-only placeholder from OS file attributes; `ScannedFile::is_placeholder` carries it; `reconcile` skips them (without dropping them from the delete-detection set); and `upload_file` refuses one outright, so the failure is unrepresentable whichever caller reaches for it. Pinned by three live-cfapi tests (`a_cloud_only_placeholder_is_never_uploaded`, `a_dehydrated_file_is_never_recorded_as_a_delete`, plus the unit predicate), both **sabotage-verified**: removing the reconcile skip makes a 3-placeholder pass take **362 s**; dropping placeholders from the scan makes a merely-dehydrated file record a **delete** on the nest. See [`on-demand-files.md`](on-demand-files.md) § On-Demand Files → *A placeholder is present-but-unreadable*.

**The hydration→upload feedback loop is CLOSED (2026-07-14), and the recorded diagnosis of it was wrong.** It was written up as a watcher problem — "a naive watcher cannot tell the provider's own writes from the user's" — but its root cause was a **dishonest row**, and it fired through `reconcile` just as surely as through any watcher. `SyncEngine::mark_hydrated` recorded *only* `state = Synced`: no `local_hash`. Both upload paths decide "did this change locally?" by comparing exactly that field (`upload_file`'s *already synced, skipping* short-circuit and `reconcile`'s re-hash branch both test `entry.local_hash == Some(file_hash)`), so a freshly-hydrated file — `Synced`, `local_hash: None` — read as **locally modified** to both, and a two-way root would have re-uploaded every file it just downloaded, bumping a nest version per hydration. `mark_hydrated` now records the served content's identity (hash + size + mtime), which closes both paths with one change; a watcher-level suppression (`was_recent_download`) closes neither, being consume-on-check and not surviving a rescan. A **partial** hydration (cfapi may fetch only the range a reader asked for) deliberately records no identity — the placeholder guard keeps the file out of the upload path until it is genuinely local.

⚠ **The recorded identity is NECESSARY but NOT SUFFICIENT, and reading it as sufficient cost three sessions (corrected 2026-08-04).** Since the ack-honesty pass the skip also requires the row's **hydration anchor**: `if let Some(recorded_manifest) = entry.manifest_hash && entry.recorded_content_hash == Some(file_hash)` — it must return that manifest as the recorded head, and a proof-less `Synced` row deliberately re-drives upload + record instead (a failed record must stay retryable). So a row with a correct `local_hash` but **no `manifest_hash`** still re-uploads. That shape is unreachable in production — `record_placeholders_from_changes` writes `Some(manifest_hash)` on every placeholder row it records (0-byte included; `download_file_bytes` resolves the fetch manifest from that very field, so a `None` could not hydrate at all), and `update_recorded_head` sets it after every successful upload — but it *was* reachable in the `cfapi_live_integration` harness, whose seed wrote `manifest_hash: None` while faking `download_file_bytes`. That single unfaithful seed is what failed `a_local_edit_by_another_process_is_detected_and_uploaded` (`left: 1, right: 0`) from that change onward. It was reported and hoisted as an **engine regression in `mark_hydrated`**, chased as one across sessions, and left standing as a known-red that four sessions routed around; the engine was innocent throughout. Fixed 2026-08-04 by making the seed faithful, with the row's local identity now asserted separately from the upload count so a future red names which half broke.

⚠ **The remaining hazard for the wiring itself: the provider's own placeholder *creation* looks like a user's file creation.** `CfExecute(TRANSFER_PLACEHOLDERS)` materializes files in the root, and a `notify` watcher reports each as an ordinary `Created` event that `was_recent_download` does **not** cover. The placeholder guard above is what makes a shared watcher safe on a cfapi root; `LocalWrites::is_user_write` applies it at the source. **`is_user_write` also drops directory events outright (fixed 2026-07-17):** a directory is never uploadable content — a folder carries directories only implicitly via child paths — and every write *inside* a folder also raises a `Modified` event on the folder itself, so before this fix each child edit re-queued the parent directory and `upload_file`'s read of it logged a fresh error.

**In a metadata-only folder a seat's own record is not a dehydration proof (ruled 2026-10-01; BUILT 2026-10-04 in the shared gate, 2026-10-08 on the cfapi root).** The nest took no bytes, so the head cannot be fetched back from it. The rule, its reach — *free up space*, OS eviction, the cache-root demotion — and what is built and still unarmed are owned by [`relay-serving.md`](relay-serving.md) § Relay serving → *A holder keeps what it wrote* and that section's status paragraph. Here it means `is_dehydration_safe` answers *not safe* for such a body, so every road in this doc that takes the gate refuses it the way it refuses an unrecorded edit, with the same refusal shown to the user. **On a cfapi root such a body is kept pinned, and shown synced (decided 2026-10-08).** The OS evicts on its own only a file that is in sync and not pinned, and cfapi refuses to dehydrate or supersede a pinned file (`0x80070188`, measured by `cfapi_live_integration::diag_holder_keep_mechanics`), so the pin is the hold. The agent pins every body the gate keeps (`SyncEngine::keeps_own_record`, a row-only read) at three points: the in-sync assertion of the next paragraphs pins it before it vouches it, so a recorded upload in a metadata-only folder lands *kept on this device* and in sync, not with sync-pending arrows that would never clear; the posture refresh that installs a flip to metadata-only is followed, at start and on every rescan tick, by a pass pinning every hydrated own record not yet pinned (`SyncEngine::kept_own_records`, `bridge::pin_kept_own_records`), so a body vouched in sync while its folder was full stops being evictable in the pass that reads the flip; and an unpin — Explorer's *Free up space* — is refused by the pin reaction and the pin put back. The provider's own dehydrates take the gate's row-only check before the OS is asked (`bridge::free_local_bytes`). A pin the agent set stays when the folder returns to full: the agent cannot tell it from the user's, and keeping is the lossless direction; the user's own *Free up space* then frees the file. A stale hydrated copy that is such a body is not freed and re-pointed like the others: its seat fetches the new head over it first — same owner, *A superseded own-record body is replaced, never freed* (ruled 2026-10-04). On a cfapi root the engine's atomic write leaves an ordinary file — the placeholder and its pin go with the old one — so the agent re-anchors it and vouches it in sync through the same road; it is a fetched body now, takes no pin, and may be freed like any other.

The shape ruled is one answering primitive every arm is awaited through, with the materialize batch folded into it; the shape rejected was taking the write half's network legs off the loop, which would leave the re-pull, the corpus passes and the engine commands blocking.

**A recorded upload flips the file to the platform's in-sync state — LANDED 2026-07-17.** Until this landed, nothing ever told Explorer (or the sync-state row) that a two-way upload had actually finished — the Status column kept its sync-pending arrows on a file that had synced perfectly (measured live: `stale_hydrated=2`, only the dirty-file dehydrate refusal protected the bytes). The windows hydration loop now follows `apply_local_write`'s `LocalWriteApplied::recorded` — the rels whose `fauna.sync.changes.record` reached the nest, carried out of `SyncEngine::upload_file`'s new `UploadOutcome { recorded }` — with `flip_recorded_in_sync`: a still-cloud placeholder gets the in-sync assertion alone; an ordinary file (locally created, or an editor's replace-save destroyed the placeholder's reparse point) is first re-anchored as a **hydrated, not-in-sync** placeholder (`fauna_cfapi::convert_to_placeholder_anchored` — `CfConvertToPlaceholder` with no flags, the folder-relative path as its `FileIdentity`) and then takes the same assertion — bytes stay local either way. The flip keys on **recorded**, never on upload alone: bytes that reached the nest without a successful change record are unreachable for later hydration, so marking them in-sync would license a data-destroying dehydrate. It runs before the pin-reaction arm in the same tick, so an edit-then-unpin inside one debounce window sees the file already in-sync when its dehydrate is attempted.

**Recorded is necessary, not sufficient: the flip vouches only for the recorded content, atomically (2026-09-28).** The upload read the file before its record landed, so a save landing in between (an autosaving editor, a large file) is on disk when the flip runs — and that save has already tripped `CF_INSYNC_POLICY_TRACK_ALL`'s not-in-sync bit, the one refusal every dehydrate caller relies on (the pin reaction's bare dehydrate, a remote change's stale-hydrated invalidation, the shell's *Free up space*). An unconditional flip cleared it, and the next dehydrate freed the only copy of the newer edit. So every in-sync assertion on a FILE — this flip and the pin reaction's stale-refusal repair alike — goes through one road, `bridge::assert_recorded_in_sync`: (1) anchor an ordinary file not-in-sync (vouching for nothing, so safe unproven); (2) read the file's USN (`fauna_cfapi::file_usn`); (3) prove the disk is the recorded content (`SyncEngine::is_recorded_content`: row `Synced`, disk hash == `recorded_content_hash` — the dehydration gate's proof without its holder-keeps clause; a body that clause keeps is pinned before step 2, since the pin moves the USN); (4) assert in-sync only if the USN has not moved — `fauna_cfapi::set_in_sync(path, usn)` opens the file with a share mode that shuts out every other writer, deleter and renamer, re-reads the USN through that handle, and calls `CfSetInSyncState` on the same handle. A write landing any time after step 2 refuses the assertion, and none can land between the re-read and the call, so the bytes step 3 hashed are the bytes vouched for, or nothing is. A file another process holds open for writing refuses too (the next recorded upload retries), a volume with no USN journal (USN 0) never flips (honestly pending), and **no file is ever marked in-sync by a convert** — `CfConvertToPlaceholder` takes no USN condition, so the former `MARK_IN_SYNC` file convert and the pin repair's one-op `MARK_IN_SYNC | DEHYDRATE` convert are retired (`convert_to_placeholder_in_sync` now refuses a file; it serves the directory flip below). Why not cfapi's own condition: `CfSetInSyncState`'s `InSyncUsn` was measured on Windows 11 ARM64 to refuse `0x80070179` for every value, including the exact USN read through its own handle, so it cannot express "not written since" and is never sent. The shell's *Free up space* verb additionally gates on `is_dehydration_safe` itself (`pipe_server::handle_free_space`, via `SyncEngine::is_dehydration_safe_in` over the folder's state DB), so it does not depend on every in-sync assertion ever made being right. Pinned by `the_flip_never_vouches_for_a_save_newer_than_the_recorded_content`, `a_save_landing_during_the_proof_refuses_the_in_sync_assertion`, `the_free_space_gate_frees_only_the_recorded_content` (unit, any machine), live against a real root by `a_save_during_an_upload_survives_the_in_sync_flip_and_a_free_up_space` and `a_save_between_the_proof_and_the_in_sync_assertion_is_refused` (`cfapi_live_integration.rs`), and the OS fact itself by `live_population::set_in_sync_refuses_a_write_newer_than_its_usn`.

A second, coupled cause made the same symptom worse: the upload path deliberately left the row's `manifest_hash` at the pre-upload merge base (a record in flight may still fail), but the fold's stale-hydrated-row comparison (`file-versions.md` § Implementation status today → *Stale hydrated copies invalidated at service start*) reads that same column as the local head's identity — so once a record **succeeded**, the row still looked stale against the device's own echoed record, and the next fold queued the user's own fresh edit for dehydration as if it were a superseded remote copy. `SyncEngine::commit_recorded_head` now stamps the row (manifest + size + content-key generation) in both upload paths' record-success arms; a failed record still keeps the base, so a genuinely-failed upload is not falsely declared current.

**A folder whose known subtree is fully synced flips too — LANDED 2026-07-17.** The file-level flip above left every containing folder showing sync-pending arrows forever — directories were never flipped at all. The new shared predicate `SyncEngine::subtree_fully_synced(dir)` reports whether at least one live row exists under `dir/` with none in-flight or diverged (a cloud-only `Placeholder` child counts as synced, a `Deleted` tombstone is neutral, and **no rows at all is `false`** — a folder carries directories only implicitly via child paths, so an empty directory exists on no other device and must keep its honest pending state rather than claim a sync the fleet will never perform). After each file-level flip, `flip_clean_ancestor_dirs` walks every distinct ancestor of the batch's recorded rels, deepest-first, and flips each whose subtree is clean — `set_in_sync` for an already-cloud directory, else `convert_to_placeholder_in_sync` (which now opens with `FILE_FLAG_BACKUP_SEMANTICS` so a directory handle works at all). Never byte-freeing, same as the file-level flip.

Both flips are unit- and live-cfapi-tested (`a_recorded_upload_head_is_not_stale_on_the_next_fold`, `a_genuinely_moved_nest_head_still_classifies_stale`, `flip_recorded_in_sync_picks_the_repair_by_cloud_file_ness`, `subtree_fully_synced_requires_a_live_clean_subtree`, `clean_ancestor_dirs_flip_after_their_files`) and live-verified on a real box the same day (files flip to ✅, the next fold logs `stale_hydrated=0`, folders flip too). **Remaining leg** (tracked internally): the new directory `convert_to_placeholder_in_sync` path lacks its own live-cfapi test. The other two gaps this paragraph once named are closed, both fixed 2026-07-18: the *converge* backstop (rescan catch-up, offline edits, the startup-converge race) flips ✅ exactly like the live watch-loop arm, and `is_dehydration_safe` now also requires `recorded_content_hash` to match the disk hash, so an uploaded-but-record-failed edit fails the gate and is never dehydrated.
