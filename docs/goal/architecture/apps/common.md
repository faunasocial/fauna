## Goal

Every fauna app — web, linux, windows, macos, ios, android, tui — exposes the same content (feeds, inbox, conversations, groups, contacts, calendars, files, bridges, media) over the same nest API surface, with the same Ed25519 identity model, the same persistent per-actor WS-RPC channel, and the same MLS encryption for DMs and groups. Platform divergence is confined to library boundaries (WASM, UniFFI, P/Invoke, direct Rust) and OS integration (credential store, push transport, file watching) — not to behavior, data shape, or concepts.

## Implementation status today

The WS-RPC-everywhere migration is **complete**: every control-plane HTTP twin is deleted nest-side ("It was the LAST control-plane HTTP twin — none remain", `bins/fauna-nest/src/lib.rs:692`); the surviving HTTP surface is byte routes (blobs, video, snapshot/sync file bytes), WS upgrades, and deliberately-public federation-residue reads (e.g. `GET /api/v1/posts/{post_id}`, subscriptions `list_tiers`/`nest_info`/`get_delegation`). The shared binding seam (`FfiNestClient` + wrapper crates) is built, bound, and consumed on all seven apps (tui, like linux, consumes the wrapper crates directly — no FFI needed); per-cluster adoption state lives in each feature owner's `## Implementation status today`, not here. The subscriptions UI is built on all 7 apps, author side and consumer side (owner: behavior/monetization.md § Pillar 1; tui closed its consumer-side `subscription-settings` page 2026-08-02, the last client-side Pillar-1 gap on any app). The former apple credential-storage contract gap closed 2026-07-19: the shared `KeychainStore` now writes `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` (device-bound) by default with an opt-in "Back up identity to iCloud Keychain" toggle (§ Credential storage; ruling 2026-07-10). **The backup rule (§ Credential storage → *What a device's own backup carries*, ruled 2026-10-01) is met on web (as its declared exception), linux, windows, iOS and tui, and short on two cells:** (**windows** closed its cell 2026-10-03: the app's store is the shared crate's Credential Manager arm, which does not roam — `windows.md` § Key storage.) **android**'s secret is unreadable off the device, but the manifest declares only `allowBackup="false"` at `targetSdk = 35` (`apps/fauna-android/app/build.gradle.kts:30`) and no data-extraction rules, so on some devices a device-to-device transfer still carries the app-private tree — the sealed credential file without its key, and the account-store dir without its writer key; **macOS**'s device-only class applies on the data-protection plane alone, and every Developer-ID build is on the legacy plane today (`ios.md` § Credential Storage → *Keychain plane*), so a shipped mac build's identity travels sealed with a home-folder backup rather than staying — closed by path A if the portal allows it, and otherwise the standing answer.

**The web app's posture (§ Credential storage → *The web app's posture*, ruled 2026-10-01) is unbuilt.** Web's identity store is plain `localStorage` rows (`libs/fauna-client-accounts/src/web_store.rs`), no unlock surface exists on web, and the catalog's `identity-protected-on-this-device` outcome 4 does not hold there. The required launch prompt awaits user approval; the build rows are minted on that approval, and a refusal instead makes today's shape the posture, declared as an absence of that outcome on web.

## Authentication

Every app manages an Ed25519 identity and uses it to obtain short-lived bearer tokens.

### Identity

- **Generate:** `ActorKeypair::generate()` — 32 random bytes (secret key) → Ed25519 public key (ActorId). The secret key never leaves the device.
- **Import:** User pastes the 64-character hex secret key to restore an existing identity.
- **Secret storage:** § Credential storage below.

### Token Flow

Two pre-identity WS-RPC ceremonies; every HTTP auth twin is deleted. **Which to use:** `fauna.auth.challenge` + `fauna.auth.verify` (two round-trips, nonce-signed, clock-skew immune) at app launch when identity + nest_url are in the long-term store; `fauna.auth.handshake` (one signed request) for runtime refresh and headless callers. `fauna.auth.not_registered` ⇒ actor not registered on this nest ⇒ drop to the onboarding wizard per [`../../behavior/onboarding.md`](../../behavior/onboarding.md) § App-launch routing. Wire shapes, signature construction, TTLs/drift windows, token format, and error tables are owned by [`../../behavior/login.md`](../../behavior/login.md) — do not re-derive them here.

**Common rules:** subsequent requests carry `Authorization: Bearer {token}` (HTTP byte routes) or authenticate the WS handshake; refresh via `fauna.auth.handshake` before expiry — don't let the token expire mid-session.

### Credential storage

**Contract (every app that has a secure store to use — all but web):** the Ed25519 identity secret lives in the **platform secure store**, never plaintext on disk. **The web app is the declared exception today (stated 2026-10-01; until then this contract read "all apps" over a table whose own Web row said otherwise):** a browser offers a page no secure store, and today the secret rests **unprotected** in the origin's `localStorage` (the table's Web row; [`web.md`](web.md) § localStorage Keys) — readable by anything that can read the browser profile or run script in the app's origin. That is the built state, not the posture: the design that ends the exception is *The web app's posture* below — ruled 2026-10-01, unbuilt, and resting on one approval not yet given. On the native side, the one declared exception: `FAUNA_E2E_CREDENTIAL_DIR` (→ 0600 JSON file), shared by linux and tui, gated to test-capable builds only (`cfg(any(test, debug_assertions, feature = "e2e-agent"))`) — an e2e/test mechanism, not a production keyring-unavailable fallback (owner of the mechanics: `linux.md` § Credential Storage). tui additionally ships a genuine (non-e2e) headless arm for real headless/SSH deployments — see its table row and `tui.md` § Credential storage; linux has no such arm, so a keyring failure in a shipped linux build is a loud error, not a silent fallback. Per-device store management gets an app surface through the shared credential-store settings section (render home: `../../ui/settings.md` § Credential store; today only tui's sealed arm offers one — the change-passphrase affordance, mechanics in `tui.md` § Credential storage). The derived bearer token is a different matter and never rests in an app's credential namespace (or on any disk of the app's own): every app mints it fresh over `fauna.auth.handshake` and caches it only in process memory, per `(nest, identity)`, ~1-hour TTL, dropped on sign-out (`long-term-store.md` § Cleanup contract) — not "stored" anywhere for the secure store's disk-plaintext guarantee to apply to. **One declared hand-off (stated here 2026-10-01):** the apple File Provider extension is a separate process that must reach the nest while the app is not running, so the app provisions it a bearer — never the identity secret — through the shared app-group Keychain item (`FileProviderCredentialStore`; owner [`../../behavior/on-demand-files.md`](../../behavior/on-demand-files.md) § On-Demand Files → *Apple File Provider binding*, entitlement in [`macos.md`](macos.md)).

**The web app's posture (design ruled 2026-10-01; refutable until built; NOT built — § Implementation status today).** A browser is the second place a Fauna app runs with no secure store to use, and it gets the answer the first one got: **the sealed arm**. The web app keeps every row of its identity store sealed under a secret the person holds — a passphrase they choose, asked for at each launch — which is the promise the terminal app's headless arm already makes ([`tui.md`](tui.md) § Credential storage), so the contract above holds on all seven apps with no exception: the identity secret never rests unprotected. The seal is **required, not offered**: a lock a person may skip leaves most browsers holding a plain key and the contract still false there, and the headless arm has no skip either. **That requirement is a cost every person using the web app pays at every launch, and it awaits user approval** — asked 2026-10-01 with this design as the recommendation; until it is given, this paragraph is the ruled recommendation, nothing is built on it, and the built state above stands. Built, it also moves web's cell of the backup rule below from *travels unprotected* to *travels sealed*: a copy of the browser profile then carries rows that open only with the passphrase. Mechanics — the envelope, the unlock surface, tabs, the push worker, rows a browser already holds — are owned by [`web.md`](web.md) § Identity store at rest.

**What a seal at rest answers, and what nothing at rest can (the weighing behind the ruling).** Three shapes were weighed against four threats:

| Threat | Plain rows (built today) | A wrapping key the browser holds as non-extractable | Sealed under the person's passphrase (or passkey) |
|---|---|---|---|
| A copy of the browser profile: a stolen or imaged disk, a backup, a profile migration, a program that collects browser files | the key is lost | **no promise can be made**: the browser keeps the wrapping key's bytes in the same profile as the rows it wraps, and whether it protects them any further differs by browser and is nothing a page can observe | held — against offline guessing, to the strength of the passphrase under Argon2id; a passkey leaves nothing to guess |
| Someone at the unlocked computer while the app is closed | lost (the storage inspector shows it) | lost (a line typed into the console asks for the unwrap) | held |
| A script running in the app's origin: an injected script, a compromised dependency, an app served by a hostile nest | lost | lost (the script asks for the unwrap, or reads the seed from memory) | lost once unlocked (the script reads the seed from memory, or the passphrase as it is typed) |
| A program running as the person while the app is unlocked | lost | lost | lost |

Three rulings follow. **(1) The browser-held non-extractable key is not built.** It hides the key from the storage inspector and from a text search of the profile, and from nothing else in the table; shipping it would let the app claim a protection it cannot state. **(2) "The key never leaves the store" is not on offer on web, and no at-rest design pretends otherwise.** The shared wasm core signs and runs MLS with the raw seed in memory, and the page hands it between wasm chunks as a string; a seal protects the key at rest, not in use — which is all the native stores do for a running app either. **(3) A script in the origin is not an at-rest threat and has its own owners:** one origin per untrusted site ([`../../behavior/web-content-hosting.md`](../../behavior/web-content-hosting.md) § Same-origin security model) and which origin serves the app's code, and how that code is made checkable ([`../front-door.md`](../front-door.md) § Which origin a user loads the app from). The seal changes neither, and neither is relaxed because of it.

**What the web app may honestly promise.** Sealed: *your key is sealed in this browser under your passphrase; while the app is closed, a copy of this browser's files does not hold a usable key.* Never, sealed or not: that the web app protects the key from the code its origin serves. Until the seal is built, the honest sentence is the one the guide and the catalog page say today — the key sits in the browser's ordinary site storage, without that protection.

**A passkey is a second way to open the same seal, not a different design** (ruled the same day; a follow-on to the passphrase build, never a replacement for it). Where the browser and the person's authenticator offer the WebAuthn PRF extension, a passkey created locally — the nest takes no part — yields the wrapping secret in place of a typed passphrase: one touch at launch, and nothing an attacker holding the profile can guess at. It exists only in a secure context, on a named host, with a capable authenticator, so the passphrase stays the arm every browser has.

**Apple (ratified 2026-07-10; landed 2026-07-19, copy-not-move hardened 2026-07-19):** default accessibility `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` (device-bound — the secret never migrates via iCloud Keychain, nor via a device restore wherever the platform applies the class: iOS, and macOS's data-protection plane — the table's macOS cell says what the legacy plane does instead), plus an opt-in Settings toggle "Back up identity to iCloud Keychain" (`settings-icloud-backup-toggle`) that **adds** a `synchronizable` + `AfterFirstUnlock` backup copy while **keeping** each row's device-bound working copy (copy-not-move: opt-out deletes only the synchronizable copy, so iCloud's circle-wide delete propagation can never destroy another opted-in device's secret; `load` prefers the device-bound copy; every read/delete matches `kSecAttrSynchronizableAny`). A launch reconcile migrates pre-policy installs down to device-bound and re-lands a working copy on a restored device. Mechanics — the whole-namespace policy, the policy-free registry seam, the device-local preference — are owned by `ios.md` § Credential Storage. Fauna's own device-add + box-recovery remain the first-class multi-device story; iCloud sync is opt-in redundancy. The e2e in-memory keychain mode is a testing carve-out (owner: `apple-e2e-automation.md`).

**What a device's own backup carries (ruled 2026-10-01 — until then only the Apple paragraph above said anything, for two apps of seven).** The rule every app keeps: **the app never, by itself, puts the identity secret into a backup or a sync that leaves the device.** The secret leaves a device only by an act of the person — Identity Export, the recovery kit, adding a device, the apple opt-in copy above — and no app uploads, syncs or exports it on any other path. What the *device's own* backup, migration or account sync then does with the store the secret rests in is the platform's behaviour, not ours, and it is one of three cases — the table's third column says which, per platform, each cell verified on 2026-10-01 against our code at the cited line and against the platform vendor's own documentation (never a dependency's source): **stays** — the secret is bound to the device (a device-only keychain class, a hardware-backed key that cannot be exported), so a backup restored onto another device, or a device-to-device transfer, yields no readable secret there and the person comes back in by adding the device or with their recovery kit; **travels sealed** — the store is a file in the person's home directory or profile, their own backup of that carries it, and it opens only with the secret that unlocks the store (the keyring or login password, the Windows sign-in, the sealed file's passphrase); **travels unprotected** — web alone, the declared exception of the contract above. Two consequences fix what the rule asks of a platform. **(1) "Stays" is not a bar every platform must reach.** A desktop's home-directory backup is the person's own copy of their own machine under their own password, and a desktop offers an unsandboxed program no device-only class to ask for; "travels sealed" meets the rule. Where a platform does offer the stronger class and the app can use it, the app uses it — the apple default, and on macOS that means the data-protection plane (`ios.md` § Credential Storage → *Keychain plane*; whether a Developer-ID build reaches it is path A's open question, [`../installers/macos.md`](../installers/macos.md) § Identifier domain), so macOS's legacy-plane "travels sealed" is that plane's honest reading, not a second target. **(2) A store the platform itself sends to the person's other devices is the app putting the secret into a sync**, whether or not our code asked for it: choosing such a store breaks the rule, and the app must choose (or configure) one that does not roam — what moved the windows app off the Credential Locker (the table's Windows cell). One hygiene corollary: where the secret "stays" because the *key* that seals its file cannot leave the device, the sealed file should not travel either — it is unreadable where it lands, and a store that arrives without the key it was sealed under is dead weight at best (whether the app can even open such a file is unmeasured, and is the first thing the android row measures) — the android cell's shortfall. The opt-in cloud-keychain copy is a separate, declared act of the person and is untouched by this rule.

**The shared Rust credential slots on the phones (ratified 2026-08-26).** Shared Rust keeps credential slots of its own beside the identity — today the W3 (account-data-plane.md § Workstreams) account-store **writer key** in the T10 slot (`../account-replica-posture.md` § The store device principal), the rest of the principal bundle as it lands — through `libs/fauna-credential-store`, which drives the desktop stores itself (macOS login Keychain, Windows Credential Manager, freedesktop Secret Service — on the desktops the very arm the co-located `fauna-sync-agent` shares). **On iOS and android that crate has no arm**: the table above puts those targets' secrets in the *app's* store, and the crate's inert `no_keyring` arm drops every write — so until 2026-08-26 no phone ever assembled an account runtime in production: the writer-key mint's read-back found nothing and the assembly refused (the e2e redirect hid it, and only the e2e). The ruling: **the app lends its own platform store to shared Rust over the SAME `FfiSecretStore` seam the multi-account registry rides** — `install_platform_credential_store`, called once at launch beside the pin-store install (apple: `FaunaAccounts.installPlatformCredentialStore()` from both shells; android: `LaunchModule.provideSecretStore`) — and the crate's *foreign* arm writes **namespace-prefixed** rows (`fauna-account-store/<actor hex>`) through it, so the writer key sits in the one platform store beside the identity it was minted for. Three consequences follow, each pinned in `fauna-credential-store`'s own tests: **(1)** the foreign arm is selected only where no native arm exists, so the desktops are untouched and the shared FaunaKit launch path installs unconditionally for macOS and iOS alike; **(2)** on such a target it also **outranks the e2e redirect** — the app's own e2e carve-out (apple's in-memory keychain, android's file backend, both keyed on the same harness variables) is what keeps a test run off the device's real store, so the phone e2e exercises the production seam instead of a file the shipped build can never reach; **(3)** the prefix is what keeps two Rust namespaces that both key by actor id (the account-store slot and the agent's) from overwriting each other in one flat store. This is not a fourth production tier for the contract above — it is the table's own row, reached by Rust. **Durability follows the platform row, and the store dir follows the row (ruled 2026-08-26, the same day).** apple's rows are `ThisDeviceOnly` (device-bound, excluded from iCloud Keychain sync and from encrypted-backup restore — `ios.md` § Credential Storage). Had the account-store dir restored while its writer key did not, the next assembly would mint a fresh writer, the store's identity check would refuse it (refuse-don't-remint — `account-scoping.md` § Erasure follows scope records the stranding shape), and that device's account plane would sit on the blob rail (with no account state at all, since the rail retired 2026-10-02 — [`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)) with nothing on screen saying so — silent and undiscoverable (sign-out and remove-account do erase the root, at the price of a full identity re-import). **The ruling makes that state unrepresentable rather than detecting it** (`nest/common.md` § Client-state recoverability's preferred shape, cited by analogy — that invariant governs nest state): **the account-store dir is excluded from the same platform backup its writer key is excluded from**, stated by every assembly through the very seam the client-device custodian store already uses (`fauna_sync_engine::custodian_store::CloudBackupExclusion` — `behavior/backup-destinations.md` § Third destination kind → *Durability + labeling* owns the mechanism and the three arms). A sandboxed shell states its arm **beside the container it supplies** (`FfiStoreContainer { dir, exclusion }` — the two facts are one fact): iOS `ExcludedByShell` (the `isExcludedFromBackup` flip, the `CloudBackupExcluder` the custodian uses), android `DeclaredInManifest` (`allowBackup="false"` — android's posture made explicit; true of cloud backup, and **not of a device-to-device transfer** at the app's target API level, where the platform documents that the attribute alone no longer disables the transfer on some manufacturers' devices: there the dir can arrive without a readable writer key, which is the slot-lost-while-the-dir-survives shape below and self-heals as it does — corrected 2026-10-01, § *What a device's own backup carries*; the manifest rule that closes it is the android cell's row); a desktop passes no container and shared Rust states the desktop posture itself (`CloudBackupExclusion::platform_desktop`, lifted from the sync agent's custodian: no iCloud device backup exists on macOS, Time Machine is deliberately left alone). Applied on every assembly, after the dir exists and before anything opens it, and a failed exclusion aborts the assembly — the custodian's rule. No app grows a UI for it. What this deliberately does **not** cover is a slot lost while the dir survives (a reset login keychain, a pre-ruling backup restored to a phone) — the one such shape left representable, and **since 2026-08-27 it self-heals**: the next assembly fires the built succession rotation on the shape itself (`../account-replica-posture.md` § The store device principal → refinement 10) — the store's writer retired, the un-pushed tail re-authored under the slot's fresh key, nothing deleted, no UI. Silent auto-clearing of a replica was never a live option: `principles.md` § No user-data loss forbids an unapproved deletion. windows' native arm (Credential Manager) means the store-lending export is present in its bindings but unused — not a divergence, the desktop half of consequence (1).

**Test builds never reach the live OS keyring (2026-09-30).** A unit-test binary of any workspace crate must not talk to the developer's desktop keyring: `gnome-keyring-daemon` aborts on a client that vanishes mid-session, and every abort re-locks the login keyring for every process on the box (measured: a `cargo test -p fauna-tui --bins` made ~370 live Secret Service calls from its sign-out/reset tests before the gate — the same crash class `../e2e-launch-isolation.md` convention 10 closed for app launches). `libs/fauna-credential-store` answers it once, for every platform arm and every caller: its five public `keyring_*` functions pass through `live_keyring_allowed()`, which is constant `true` in a shipped build and `false` in any build carrying the crate's `no-live-keyring` feature — enabled from `[dev-dependencies]` only, so resolver 2 keeps it out of every plain build while workspace feature unification (`.cargo/config.toml`) carries it into every test build. Refused, the keyring behaves as the inert arm (reads find nothing, writes/deletes drop with a warning, the probe reports no usable keyring), and a process-wide `live_keyring_calls()` counter is what the guard tests (tui `session.rs`, linux `client.rs::keyring_guard_tests`) assert stays zero. Two explicit ways back: a harness launch, which always pins a per-launch `FAUNA_KEYRING_APP` namespace (so a binary a `cargo test` happened to build still works under the harness's private Secret Service), and the `allow-live-keyring` feature, forwarded only by the opt-in live suites (`fauna-credential-store/live-keychain`, `fauna-linux/live-secret-service`).

## Nest Connection

### Node Info

On first connection to a nest URL, fetch metadata over the pre-identity anonymous WS-RPC connection: **`fauna.nest.info`** (domain, nest ID, supported protocols, registration policy, tier list, moderation config — use it to validate the URL and pre-populate onboarding) and **`fauna.handle.available`** (handle availability, 300 ms debounce). The HTTP twins (`/api/v1/node-info`, `/api/v1/handle-available/{handle}`) are deleted.

### Registration (first use)

**`fauna.account.register`** on the anonymous connection. The registration ceremony (signed message construction, handle rules, registration modes, per-IP limits) is owned by [`../nest/public-mode.md`](../nest/public-mode.md) (registry: `registration`) — apps call the kind and render the outcomes; the onboarding wizard flow is [`../../behavior/onboarding.md`](../../behavior/onboarding.md).

### Subsequent Launches

Authenticate with the existing keypair using the token flow above. No re-registration needed.

### WS-RPC client binding (per platform)

The single persistent per-actor WS-RPC channel (`GET /api/v1/ws/{actor_id}`, bearer in `Sec-WebSocket-Protocol: fauna.v1, bearer.<token>`) is driven by the shared Rust `libs/fauna-client::NestClient`. Every app reaches it through its platform library boundary, so the connection lifecycle, auth handshake, reconnect supervisor, and per-kind metadata (deadlines, `forbid_replay`) live in shared Rust — never re-implemented per app. Typed Layer-3 calls (`fauna.bridges.*`, `fauna.email.*`, `fauna.subscriptions.*`) and other WS-RPC kinds go through the per-feature wrapper crates (`fauna-client-bridges::BridgesClient`, `fauna-client-email::EmailClient`, `fauna-client-subscriptions::SubscriptionsClient`, …), each generic over the `RpcRequester` transport (native `Arc<NestClient>` / wasm `WsRpcClient`) and backed by `NestClient` on native.

| Platform | WS-RPC client |
|----------|---------------|
| Web | `fauna-wasm` (Rust → WASM) — browser `WsRpcClient` singleton wrapping the shared client |
| Linux / tui | Direct Rust — `NestClient` and the `fauna-client-*` wrapper crates as Cargo dependencies, no FFI seam (`apps/fauna-linux/src/client.rs`; tui: `apps/fauna-tui/Cargo.toml`, e.g. `apps/fauna-tui/src/contacts.rs`) |
| Android / iOS / macOS | `fauna-ffi`'s `FfiNestClient` (UniFFI `uniffi::Object` wrapping `Arc<NestClient>`) |
| Windows | `fauna-ffi`'s `FfiNestClient` via the generated C# bindings (P/Invoke into `fauna_ffi.dll`) — consumed through `NestRpcClient`/`INestRpcClient` |

For the three UniFFI/P-Invoke apps, `fauna-ffi` exposes the *same* seam so Apple, Android, and Windows consume one shape — mirroring the Rust-native Linux and tui apps rather than each re-deriving it:

- **`FfiNestClient`** — `new(nest_url, secret)` builds the client from the actor's Ed25519 secret; `connect()` (async) authenticates the WS handshake and starts the reconnect supervisor, then blocks until `Connected` or a bounded timeout; `disconnect()` tears down. The WS connection authenticates itself, independent of any HTTP bearer loop the client already runs (a shared bearer source is a possible future optimization, not required for correctness since each handshake authenticates on its own).
- **`FfiNestClient::bridges()` / `.email()` / `.subscriptions()`** — vend the `FfiBridgesClient` / `FfiEmailClient` / `FfiSubscriptionsClient` typed-call sub-clients (one async method per WS-RPC kind), cheap thin wrappers over the shared `Arc<NestClient>`. `FfiSubscriptionsClient` mirrors `fauna_protocol::subscriptions::*` (tier CRUD, subscribe/unsubscribe, the author request queue, the KeyBlob fetch); `ActorId` crosses as `Vec<u8>`, `Timestamp` as `u64`, and signed envelopes reuse `FfiEmbedAsBytes` (the `mint_key_blob` output drops straight into `FfiEncryptedKeyBlobUpload`).
- **Dynamic per-bridge fields** (settings, link params, follow `extra`) cross the FFI as `FfiCborValue`, a recursive enum mirror of `fauna_cbor::Value`. CBOR encoding stays in Rust — apps build a typed tree, never carry their own codec.
- **Replay safety** is preserved structurally: the wrapper crates issue every call through `NestClient::request` (which never auto-retries on disconnect), so `forbid_replay` kinds (`link`, `add_follow`, `email.send`) are never silently re-issued regardless of which client invokes them.
- **Async execution + stack size:** a `fauna-ffi` `async` export's future is polled on the *foreign* executor's thread (Swift cooperative pool / Kotlin dispatcher), whose stack is much smaller than a tokio worker's — `async_runtime = "tokio"` supplies only a tokio *context*, not a worker thread. Large futures in the shared connect/handshake paths must be `Box::pin`ned so they don't overflow that small stack. Authority: `native-async-execution.md`.

## Desktop Residency

**The cross-app promise (owner; lifted here 2026-08-30 from the per-platform lifecycle sections): closing the app's window is never a silent stop.** On every windowed desktop, either something stays behind and keeps working — the app hidden in the system tray (Linux, Windows), or the app itself on macOS, where a window close is never a quit and the per-user sync agent additionally outlives an explicit Quit — or, where nothing can stay resident, closing the window quits and the Settings → General row says so. Where close-to-tray is a setting it defaults ON, the user's choice survives a relaunch, and an explicit opt-out is never overridden. The feature's other half, auto-start at sign-in, is owned per platform — [`windows.md`](windows.md) § App Lifecycle → *Auto-start at sign-in* (the rationale and the windows leg), [`linux.md`](linux.md) § Auto-start at sign-in, [`macos.md`](macos.md) § App Lifecycle → *Auto-start at sign-in* — and is the residency the home-screen widget's background currency rests on wherever no OS runs app code on the app's behalf (§ Home-screen widget).

Mechanisms stay owned per platform: [`linux.md`](linux.md) § System Tray (the tray-host gate, ksni, and quit-on-no-host), [`windows.md`](windows.md) § App Lifecycle → *Window close* (Win32 tray + `CloseToTray`, and why windows residency still matters — the app is the agent's bearer-minting service), [`macos.md`](macos.md) § App Lifecycle → *Window close* (a close is never a quit, and no close-to-tray setting, since there is nothing to close to) and § Sync (the A4 cutover: `fauna-sync-agent` outlives the app session — [`sync-agent.md`](sync-agent.md) § Packaging + lifecycle). The quit-time draft flush every close path also owes is a separate promise, owned by [`../../behavior/reserved-folders.md`](../../behavior/reserved-folders.md) § The leave-flush promise.

**Boundary — the promise names the three windowed desktops only.** web, iOS, Android and the terminal app have no desktop-residency lifecycle to promise anything about: the browser owns a tab's lifetime, the mobile OSes own background execution (§ Push Notifications; iOS's pull-based `BackgroundScheduler`), and a terminal process lives and dies with its invocation ([`tui.md`](tui.md) § System integration — no tray). "Start at login and close to tray" — both halves of the settings feature — is therefore absent by design on those four platforms, never a parity gap.

## Home-screen widget

**The cross-app promise (ratified 2026-09-26, user-ruled): a Fauna widget on the platform's home screen — the glanceable surface outside the app, wherever the platform has one — shows how many unread messages are waiting, and keeps that count current in the background without the app being opened.** The count is the account's total unread: the per-thread numbers the app's own conversations list shows, summed over **every** thread of the account — never over whatever a search or filter has narrowed that list to — by the shared `fauna_conversations` fold of the account's synced read state (`ThreadSummary.unread_count`, summed by `sum_unread`; what "unread" means is owned by [`../../ui/conversations.md`](../../ui/conversations.md) § State & data shape → *When a thread is read*, and the read markers reach every device over the WS-RPC plane, [`../../behavior/conversation-read-state.md`](../../behavior/conversation-read-state.md)) — never a per-app tally and never a second count query, so the widget can never show a number the app would not. (Reworded 2026-09-26: the nest holds no opening key for sealed messages and so has no unread count of its own to read; the earlier wording named one.) How the platform hosts, schedules and paints the widget is per-platform mechanism.

**Scope — five apps owe it, two have no home screen.** Android has it (mechanics: [`android.md`](android.md) § App Widgets — Glance, a periodic worker). **Linux has it (2026-09-26): the launcher badge**, the `LauncherEntry` count a stock Ubuntu dock, Plasma or elementary paint on the app's icon, with the per-desktop limit stated where the mechanism lives ([`linux.md`](linux.md) § Home-screen widget). **The two apple apps have it (2026-09-26): a WidgetKit widget**, one shared-Swift implementation on iOS and macOS ([`ios.md`](ios.md) § Home-screen widget); on macOS the background currency rests on app residency — auto-start at sign-in, whose decision, implementation status and the residual an explicit Quit leaves are owned by [`macos.md`](macos.md) § App Lifecycle → *Auto-start at sign-in*. **Windows has it (2026-09-26): the taskbar badge** — the OS-painted numeric badge on the app's taskbar button, chosen by the windows design pass over the Windows 11 Widgets board (Store-channel-only, out-of-process) and the overlay icon (gone once the window hides), with its per-channel identity condition stated where the mechanism lives ([`windows.md`](windows.md) § Home-screen widget). **Absent by design on web and tui, declared here:** the web app runs inside a browser tab and has no home screen to put a widget on, and the terminal app lives inside a terminal, which has none either — on both the *behaviour itself* is absent, not merely a mechanism, so the catalog's [`home-screen-widget`](../../../features/home-screen-widget.md) page declares both columns absent citing this section ([`web.md`](web.md) § Implementation status today and [`tui.md`](tui.md) § Declared platform absences index the absence).

**Witnessing it.** A widget lives outside the app's automation surface, so its witness is platform-specific — a Glance/Robolectric render of the widget from a seeded state, or the platform's widget host read from outside — and is marked for the apps it can drive, never gated on the others with a `declared_absence` ([`../feature-catalog.md`](../feature-catalog.md) § Cell semantics, the marked-witness rule). Linux's is written — the launcher badge read off the app's session bus ([`linux.md`](linux.md) § Home-screen widget → *Witness*); so is apple's, marked `macos`/`ios` — the snapshot the apple widget renders, read off disk from outside the app and compared with the app's own list ([`ios.md`](ios.md) § Home-screen widget); so is windows' — the badge the OS notification store holds for the app's AUMID, read under a lent package identity ([`windows.md`](windows.md) § Home-screen widget → *Witness*); android's is not yet.

## Two-click confirm

A destructive control that takes no modal — revoke or delete a mail alias, delete a mailing list, reset the spam model, cancel a running mail import, export or archive import — confirms inline: the first press arms it and relabels it in place (the relabel is the confirm's only visible affordance), a second press while armed performs the action, and an arm that sees no second press within 4 seconds disarms back to the resting label. The arm is page or widget state that a snapshot repaint never touches, so a repaint cannot disarm a control just armed. **The armed label is the feature's own descriptive confirm where its owner doc names one — `mail_lists.delete_confirm` ("Delete the list and all its members?"), `mail_spam.reset_confirm` ("Reset for good? This cannot be undone.") — and otherwise the one shared bare label `common.confirm_q` ("Confirm?")**: never `common.confirm` ("Confirm", the label of a plain confirm button that does not ask), never a hand-typed literal. Ruled 2026-10-06 on priority #4's richest existing pattern: linux, web, windows and apple already showed "Confirm?", tui alone "Confirm". `mail_aliases.revoke_confirm` is a per-feature key spelling the same "Confirm?"; it may later fold into `common.confirm_q`.

### Implementation status today

**tui, linux and web follow the rule (2026-10-06):** tui's four bare relabels (mail aliases, mail import, mail export, archive import) read `common::CONFIRM_Q`; linux's shared `wire_two_click` takes the armed label per call, so its mailing-list delete and spam reset show their descriptive confirms; web reads the keys, and its mail-import Cancel — which had cancelled on the first press, against `behavior/mailbox-migration.md` § Wizard steps — gained the arm. The mail-aliases e2e asserts the literal `common.confirm_q` on the apps that run it (tui, macos, ios). **Three apps lag:** **windows** hand-types `"Confirm?"` on five panels, its list delete and spam reset owing their descriptive keys; **apple**'s mail-import Cancel arms to `L.common.confirm`; **android** has the two-click only on the spam reset (labelled `common_confirm`), while the aliases overflow menu is a real dropdown whose Delete deletes on one tap and the list delete and import/export Cancel show no arm.

## Push Notifications

When a subscribed device has no live WebSocket connection of its own (its app closed or backgrounded), the nest sends that device a push notification via its transport — the decision is per device, ruled 2026-09-26 (§ Dispatch Logic). Most push is triggered by the same events that generate WebSocket notifications: inbox delivery, knocks, group invites/welcomes. One trigger is push-only, with no matching WS event: the periodic at-risk TLS-certificate-renewal nudge (`bins/fauna-nest/src/cert_nudge.rs`), which pushes an admin whose app hasn't renewed a drifting cert within the lead window — owned by [`../nest/tls-certificates.md`](../nest/tls-certificates.md) § C.4.

### Transports

| Transport | Platform | Endpoint format | Credential |
|-----------|----------|-----------------|------------|
| `web-push` | Browsers (Chrome, Firefox, Safari); android via UnifiedPush (ruled 2026-09-26, below) | Browser vendor relay URL — or a UnifiedPush distributor's endpoint, which is a Web Push endpoint | VAPID key (self-generated per nest) |
| `apns` | iOS, macOS | APNs device token (hex) | Apple .p8 key (fauna.social only) |
| `ws-device` | linux, windows, tui (the terminal on any desktop, macOS included) — delivered through the always-running per-user sync agent | the row's own `device_id` (no third party is dialled) | none — the nest's own authenticated WS-RPC channel |

**The table above is the TARGET set (user ruling 2026-09-26: linux, windows, android and tui gain push; the transports ruled by the design pass the same day).** `web-push`, `apns` and, nest-side, `ws-device` are built; client-side, tui's `ws-device` registration and the agent's linux banner arm are built and the other desktops' are build rows (§ Implementation status below); android's transport has a build row. The rulings:

**linux, windows, tui — `ws-device`: the sync agent is the wake stand-in, and no third party is involved (ruled 2026-09-26).** The per-user sync agent ([`sync-agent.md`](sync-agent.md)) is always running for the signed-in user, holds one authenticated WS-RPC connection per provisioned account and already consumes that connection's push events — so a desktop needs no relay to be woken. A `ws-device` row means *deliver this device's push over its own live connection*: instead of dialling anything, the nest sends a `fauna.push.notification` frame (title, body, url — the same strings the other transports carry) to the connections that announced that `device_id` (§ Registration → *Every connection announces*). The agent posts the frame as an OS notification — **only while no app is attached over the local IPC seam**; an attached app owns the machine's banners under its own focus rule ([`linux.md`](linux.md) § Desktop Notifications, [`windows.md`](windows.md) § Notifications), so exactly one process ever posts, and an app that receives the frame while open ignores it. A tap opens the app, at the frame's `url` where the platform's launch path allows. **The subscriber is the APP, never the agent:** it registers the row through `fauna.push.subscribe` under the same install-scoped intent bit and the same leave-shape drops as web and apple (§ Registration), so the Settings control, its element IDs and `notifications.md` outcome 9's witness are identical on all seven apps, and *push follows whoever is signed in* holds by the same mechanism — only the foreground actor's row exists, so the agent's other account hosts receive no frames. Content is the nest's generic strings ("New message", "Group invite", …): the agent is bearer-only and links no MLS, so it can render no more than web-push can. The OS sink per platform: linux `notify-rust` (already in the workspace through fauna-linux); windows the WinRT toast API through the agent's existing `windows` crate (a feature addition, no new crate — the toast attributed to the app so a tap launches it); macOS (tui's benefit only — the GUI app has APNs) through the same `notify-rust` crate, whose `mac-notification-sys` arm the dependency decision for tui's own desktop arm already approved (2026-09-26, [`tui.md`](tui.md) § System integration) — the agent's macOS arm is a build of its own, not a fresh decision. A machine with no desktop session — a headless agent, tui over SSH — has no sink: the agent says so over its IPC health surface and the Settings control renders its inline failure line. That is a runtime condition, not a declared absence, so outcome 9 stays on its page for every column and [`../feature-catalog.md`](../feature-catalog.md)'s 2026-09-19 contract-move rule does not fire. **WNS for windows was considered and rejected:** a Partner Center identity plus a nest-held credential in APNs's position, for a desktop the agent already wakes — a second shape where one serves (priority #1).

**android — UnifiedPush-first with the embedded-FCM fallback (user ruling 2026-09-26).** The candidates weighed: **UnifiedPush** — the distributor the user installs (ntfy, NextPush, …) issues an endpoint that is a Web Push (RFC 8030 / RFC 8291) endpoint, so the existing `web-push` transport, its VAPID key and its public-https dial rule serve it with **no nest change**; the app adds the UnifiedPush connector and subscribes exactly as web does — optionally with the **embedded FCM distributor** as the no-distributor-installed fallback, behind a fauna.social-operated rewrite proxy (a public https endpoint like any relay, holding the Firebase credential; the nest still speaks only `web-push`, and Google sees an encrypted blob); or **native FCM** — a fourth transport with a Google service credential in APNs's position (fauna.social-only, and it must pass the two-bucket test — never a `from_env` twin). The user ruled UnifiedPush-first with the embedded-FCM fallback (works out of the box on a Play phone, Google-free on a de-Googled one; the accepted cost is a fauna.social-run proxy and a Play/FOSS build flavour split); UnifiedPush-only and native FCM are rejected, so android adds no nest transport. Whatever the answer, a LAN-only distributor is refused by the outbound guard like any private-range relay — a self-hoster's distributor must be publicly routable https. **Correction to the cost (design pass 2026-09-26): no proxy and no Firebase project.** The rewrite proxy above was the embedded distributor's older contract. As published today (the UnifiedPush android specification AND_3.1.0 and the embedded distributor's own documentation), the embedded FCM distributor registers with Google's services for a Web Push subscription authenticated by the VAPID public key the app hands it at registration, and Google's servers accept Web Push requests directly provided they carry a VAPID authorization; a gateway exists only for an application server that sends push *without* VAPID. The nest signs every `web-push` dial with its VAPID key (RFC 8292) and hands that key out over `fauna.push.vapid_key`, so the fallback's endpoint is an ordinary Web Push endpoint on Google's host, dialled exactly as a Chrome subscription is: **fauna.social runs nothing and holds no Google credential, no Firebase project exists, and a self-hosted nest serves a Play phone out of the box.** The ruling stands unchanged in substance — UnifiedPush-first, embedded-FCM fallback — with its accepted cost reduced to the build flavour split. Two consequences for the app: registration passes the *current nest's* VAPID public key, so the subscription is bound to that key and an identity that moves to another nest re-registers (the endpoint-change re-subscribe path, never a fresh opt-in); and the witness is the android build's — this correction rests on the published documentation until a Play phone receives a push from a nest. Should that witness fail and a credential-holding relay prove necessary after all, it is a push service under [`../front-door.md`](../front-door.md) § Public-vhost topology's closed-tenancy rule — never a vhost or a unit on the door's box — and needs its own placement decision there first.

**Implementation status today:** the VAPID keypair is nest-self-generated — `ensure_vapid_pem` (`bins/fauna-nest/src/push.rs`) mints a P-256 keypair on first boot if the singleton `vapid_keypair` DB row is empty, persists it, and hands it to `PushService::new`; every later boot loads the same persisted key, so web-push works out of the box with no configuration. The standalone binary's `--vapid-pem` CLI flag (`bins/fauna-nest/src/main.rs`) is a dev-only override — a supplied key is used for that boot only and never written to the DB. APNs is still env-var-configured (`ApnsConfig::from_env`, `bins/fauna-nest/src/push.rs:55`), consistent with staying fauna.social-only. **The 2026-09-26 rulings are built nest-side only:** `fauna.push.subscribe` accepts a `ws-device` row (`push_handlers.rs`, `push::validate_ws_device_subscription`), `fauna.push.presence` tags the calling connection (`WsState::announce_device`), the dispatch is per device with the compatibility rider (`push::DevicePresence::action_for`, fed by `WsState::device_presence`), and a present `ws-device` row is delivered as `fauna.push.notification` (`PushEvent::PushNotification`, `WsState::notify_push_to_device`). **Client side, built 2026-10-01 (tui, the lead app, and the agent's linux arm):** the shared registration machine (`fauna_client_push::registration` — the intent bit, the which-actor record, the leave-shape drops, the `ws-device` subscription); the presence announce on the native shared client (`NestClient::set_push_presence`, re-sent by every (re)connect — **opt-in per caller**, so only an app that names the id its row is keyed under announces); tui's Settings toggle, re-arm at sign-in and drops at switch and sign-out; and the agent's arm (`bins/fauna-sync-agent/src/push_arm.rs`) — the account connection announces the capability's `device_id`, and a `fauna.push.notification` frame is posted through `notify-rust` on linux only while no app holds an attachment lease (`fauna_ipc::sync::RequestMethod::AttachApp`, held for the app process's life by `fauna_client_sync::attachment`). The sink is reported on `ServiceStatusInfo::notification_sink`. **Who announces today: tui, the sync agent and — since 2026-10-03 — the two Apple apps**, whose session start announces through `FfiPushRegistration::announce_presence`. The remaining build rows each name outcome 9 as their witness.

Nest-side there is nothing to do: `push.rs`'s single `APNS_TOPIC` already serves macOS device tokens, because both targets ship under one bundle id (`social.fauna.fauna`). One further macOS-only gap survives the entitlement: the Notification Service Extension that decrypts the rich `encrypted_payload` (§ Content Encryption) is iOS-side only, so macOS would show the generic `aps.alert` fallback until an AppKit analog exists.

### Registration

Apps register via the WS-RPC kinds **`fauna.push.{vapid_key,subscribe,unsubscribe}`** (the `/api/v1/push/*` HTTP routes are deleted — `fauna.push.*` is the sole surface), with a `transport` field (`"web-push"`, `"apns"` or, ruled 2026-09-26, `"ws-device"`; defaults to `"web-push"`). A `web-push` or `apns` subscription includes a push-specific P-256 public key and auth secret for payload encryption — the nest encrypts notification content so platform intermediaries (Apple, Google, Mozilla) cannot read it. A `ws-device` subscription carries its own `device_id` as the `endpoint` and no keys: nothing leaves the nest's authenticated channel, so there is no intermediary to encrypt against (§ Content Encryption).

**Every connection announces which device it serves — `fauna.push.presence { device_id }` (ruled 2026-09-26).** The dispatch decision is per device (§ Dispatch Logic), so the nest must know which device a live connection is — and a seed-minted bearer carries no device binding (`RpcConnection::bound_device_key` is `None` for it). A client-asserted id is enough here: all a connection can do with it is suppress or receive its own actor's push, which `fauna.push.unsubscribe` already lets it do. The `device_id` is the one the subscription row uses — the install's derived device id for that actor (`fauna_core::device_id::derive_device_id`, what web's `deviceIdForActor` already subscribes under and what the agent presents as its `SyncCapability::device_id`) — announced by the shared client once per (re)connect; the agent announces it on every account host's connection. **The announce also says what kind of connection it is (ruled 2026-10-03): an optional `stand_in: true` marks a connection that is the device's wake stand-in — the sync agent — rather than its app;** absent means an app. What the nest does with the difference is § Dispatch Logic's (*A wake stand-in's announce delivers*). Additive both ways: an older nest answers `fauna.protocol.unknown_kind` and the client goes on; an older client announces nothing and keeps the pre-ruling behaviour (§ Dispatch Logic, the compatibility rider).

**An endpoint is a destination the nest will dial on the subscriber's say-so, so subscribe refuses one it must never dial (ruled 2026-09-21).** `fauna.push.subscribe` is `User`-class: without a rule, any registered user could aim their nest's POSTs at an address of their choosing — the nest's own loopback, a private-range neighbour, a cloud metadata service. A `web-push` endpoint is a browser vendor's relay (§ Transports), so the rule is the nest's ordinary outbound-dial posture (`bins/fauna-nest/src/ssrf.rs`, shared with the media proxy, federation and link preview): **https only, on a public, globally routable address.** Subscribe enforces the half the URL text alone decides — scheme, a host, an IP-literal host that is globally routable, never a `localhost` name — and answers `fauna.push.invalid_request` with one message that names the accepted shape, never the check that tripped. It deliberately consults no resolver: the answer then depends on nothing but the request (no DNS latency inside the kind's deadline, no resolver oracle for the caller, no refusal of a good relay during a DNS outage), and a name's resolution can change after subscribe anyway, so the resolving half belongs to the dial (§ Dispatch Logic), which is the security boundary. An `apns` endpoint is not a URL at all but a device token the nest interpolates into the APNs request path, under this deployment's APNs credential; subscribe refuses anything but hex, so a token can never name another path on Apple's host. **The one allowance is compile-time and test-only:** a nest built with the `test-hooks` feature also accepts and dials a web-push endpoint on a **loopback IP literal** (`http` or `https`), so the dispatch witness can stand a listener of its own in for the relay; nothing wider is admitted (a private-range or metadata address is refused in a test build exactly as in a shipped one), and no shipped artifact compiles it (`../e2e-automation-surface-gating.md`).

**A re-arm never opts a device in.** An app re-registers on later launches only when *this install* has already completed the permission dance and landed a subscription — a durable, **install-scoped** intent bit (`account-scoping.md` § The scoping taxonomy, class 2), cleared the moment an unsubscribe is issued. The OS/browser notification permission is **necessary but never sufficient**: it answers whether a banner may be posted, it is not the user's answer to whether their nest may push here, and — correctly — a Disable inside the app does not touch it (revoking it belongs to the platform's own settings). An app that gates re-registration on permission alone therefore restores, at the next launch and silently, the subscription the user just deleted; push is the one data flow that leaves the nest for a third party on a schedule the user does not control, so *off* has to stay off (`../../principles.md` § The user always controls their data). A second record sits beside the intent bit — which actor the install's live row is registered under — so a leave-drop issues nothing on an install that never subscribed and forgets the row it removed. Web needs it for a further reason: a browser's `PushSubscription` outlives an identity change with nothing re-POSTing it, so web must notice the drift and reconcile. The Apple targets carry the same record since their lift onto the shared machine (2026-10-03); before it they kept the bit alone and re-armed by an unconditional subscribe in the token callback, which the machine's `rearm` — a subscribe only while the bit is set — replaces.

**The subscription follows the signed-in identity — at most one live row per install (ruled 2026-08-30).** The nest deliberately keys `push_subscriptions` by `(actor_id, device_id)` and can hold many actors' rows for one device; the *client* contract is that at most one is live per install — the actor currently signed in on it. The account switcher is a shared-device surface (`../long-term-store.md` § Multi-account evolution's per-account re-auth gate exists exactly because a background account can belong to a different person), and push is the one flow that leaves the nest for a third party on a schedule the user does not control, so a departed identity's live row would go on delivering that identity's activity — on APNs, with previews the install-wide keys decrypt — to whoever now holds the device. Therefore **every gesture by which an identity leaves the foreground drops that actor's row, issued by the leaving session itself at the last point its authority is in hand** — the `fauna.push.{subscribe,unsubscribe}` verbs are actor-scoped on the connection actor by design, so nobody else ever can. The three leave-shapes:

- **Switch** (the append flow's add-and-switch included) — the switch flow drops the outgoing actor's row before committing the switch; the incoming actor re-arms through the existing paths (web's `reconcileSubscriptionActor`, the shared machine's `rearm` at session start on apple and tui), which upsert the same `(actor, device)` key, so a re-armed actor never strays. Web's append wizard is the one switch commit that no longer holds the outgoing authority, so web drops at the add-account entry instead; an abandoned wizard self-heals because reconcile re-arms the still-active actor on its next identity settle. *Kept for background accounts* was considered and rejected — if a notify-me-for-background-accounts feature is ever wanted, it arrives as its own ruled per-account opt-in, never as the residue of nobody unsubscribing.
- **Sign-out** — the active actor's row drops before the credential erase (web sign-out is the all-accounts erase, and under this contract the active row is the only one the install holds).
- **Account removal** — a non-active account holds no row under this contract, so removal itself has nothing to drop; rows minted before this ruling are the accepted residue below.

Two riders. **The install intent bit survives every leave-shape** — only the user's explicit Disable clears it (clearing it on a leave-gesture would turn every sign-out into the silent opt-out the re-arm rule above forbids), so dropping the outgoing row never closes the channel the user left open (`account-scoping.md` class 2's constraint): the next sign-in on a subscribed install re-arms under the identity in front, no Settings visit, no permission prompt. **The drop is best-effort, never a gate** — a leave gesture must complete offline, so a failed unsubscribe strands the row rather than blocking the user. Stranded and pre-ruling rows are accepted residue with three reapers: the actor's next foreground on that device re-adopts the same-keyed row and its next leave drops it; succession burns it (`../../behavior/succession-repoint-axis.md`); endpoint death prunes it (§ Dispatch Logic). Nest-side nothing changes: no enumeration verb, no cross-actor cleanup.

**Implementation status (this ruling):** web implemented — the drop rides `performSwitch`, `identity.logout()`, and the add-account entry, and the which-actor record clears only on a successful drop (`push-actor.ts`); apple implemented, and on the shared `fauna_client_push::registration` machine since 2026-10-03 — vended over UniFFI as `FfiPushRegistration` (`libs/fauna-ffi/src/push_client.rs`; transport-general: the app hands `enable`/`rearm` the subscription it holds, `apns` on Apple, built in the OS's token callback), the intent bit and which-actor record in one install-scoped file under the app's base (`PushIntentStore`), `PushManager` keeping only the OS half (permission, device token, key pair); `PushManager.dropActorRow()` is the machine's leave-drop (never touches keys or the install intent bit, issues nothing on an install with no push history), wired into both targets' `switchAccount()` (before the registry write) and the shared `SignOutSection` (before the credential erase); account removal is a deliberate no-op (`AccountSwitcherVM.remove` doc comment) since a non-active row holds nothing to drop under this contract — latent anyway behind the `aps-environment` entitlement (§ Push Notifications above); tui implemented 2026-10-01 on the shared `fauna_client_push::registration` machine — the intent bit and which-actor record in one install-scoped file under the flat config base, the drop issued from `session::sign_out` (which sign-out, switch and factory reset all reach) over the leaving session's own client before it disconnects, bounded so a leave completes offline, and the re-arm at every sign-in; the other three apps — linux, windows, android — hold no push call-site yet (`../../behavior/succession-repoint-axis.md` § Implementation status today) and adopt the same shared machine unchanged (windows and android through the same `FfiPushRegistration` seam); web keeps its own copy until its push trickle-down lifts it onto the machine (priority #2).

### Dispatch Logic

**The decision is per device, not per actor (ruled 2026-09-26).** For each of the actor's subscription rows the nest asks whether a live connection announcing that row's `device_id` exists (§ Registration → *Every connection announces*; which announces count for which transport is the stand-in paragraph below). For `web-push` and `apns` a present device is **skipped** — its own app is connected and renders the event itself — and an absent one is dialled: the payload encrypted with RFC 8291 aes128gcm and sent via the row's transport, failed or expired endpoints (HTTP 404/410) cleaned up. For `ws-device` presence **is** the delivery: the `fauna.push.notification` frame goes to that device's live connections (the agent's, and the app's if open, which ignores it), and an absent device is skipped with nothing queued — the agent is always running, so absence means the machine is off, and a missed frame costs only the banner (the event itself is durable). The old rule — skip every push when the actor has *any* connection (`WsState::has_connections`) — is retired: a tray-resident desktop app and, worse, the always-connected sync agent made it read the user as present everywhere for ever, silencing their phone and browser. Two riders. **Compatibility:** a connection that announced no device keeps the old rule — its presence suppresses every `web-push`/`apns` row of the actor, exactly as before — so an older app degrades to yesterday's behaviour and never to double banners. **Cross-device quieting is not this rule:** "don't buzz my phone while I'm typing on the desktop" would be a ruled user preference (nest state, app UI — `../../principles.md` § One configuration surface), never a side effect of the presence check.

**A wake stand-in's announce delivers; it never suppresses (ruled 2026-10-03 by a design pass).** "Present", for the relay transports, means *the device's app is connected and renders the event itself* — and the sync agent is not that: it announces the install's device id only so that device's `ws-device` frames reach it (§ Transports), and renders nothing of its own. Read as an app, its always-on connection makes a macOS install's `apns` row unreachable for as long as the Mac is on: the macOS app keys its row under the same derived id the agent announces (one id, `FfiAccountRegistry::device_id_for_actor`, feeds both the app's registration and the capability it provisions the agent with), and the agent has no macOS sink to post through (§ Transports, the status paragraph), so a Mac whose app is closed would get no banner by either road. So the announce says which kind of connection it is (`stand_in`, § Registration → *Every connection announces*) and the nest counts the two kinds apart. **A stand-in announce is a delivery point for that device's `ws-device` row and nothing else:** it never makes the device present for `web-push` or `apns`, and — being an announce — it never triggers the compatibility rider above. **A relay row is skipped only while an app connection announcing its device is live.** The macOS app-closed case follows with no rule of its own: the app's process is gone, only the agent's stand-in announce names the device, the `apns` row is dialled and APNs raises the banner; while the app runs — a tray-resident app with no window included, since it is still connected and raises its own banners (§ Desktop Residency) — its own announce skips the row, as on any device. **The rule has no platform arm:** the agent announces as a stand-in on every OS, which changes nothing for linux, windows or tui, whose rows are `ws-device` and are delivered to a stand-in exactly as before. Compatibility is additive both ways (`../version-compatibility.md` § I4): an older nest absorbs the unknown field and reads a plain announce, and an older agent sends none — either pairing behaves as before this ruling (the agent's device has its relay row skipped), never as a double banner. The trust argument of § Registration is unchanged: the flag is client-asserted, and all a connection gains by setting it is that its own actor's relay push is dialled. Rejected: **the agent stays silent where it has no sink** — an unannounced connection is the compatibility rider's trigger, so a silent agent would suppress every relay row of the actor, phone and browser included, which is the failure the per-device ruling retired, and it would put a per-platform arm where a uniform rule serves (priority #1); **the macOS app registers `ws-device` and the agent posts** — the agent's macOS sink cannot be built (measured 2026-10-03, [`tui.md`](tui.md) § System integration), and it would trade APNs's encrypted rich content for the generic strings; **inferring the kind from the connection's credential** — the announce is already the explicit, client-asserted statement of what a connection serves, and a second, implicit signal beside it would be one more thing to keep in step. **Order:** this is built before the `aps-environment` gate (§ Transports, the ⚠ paragraph) opens, so no macOS install ever holds an `apns` row under the old reading.

**Every web-push dial runs the full outbound guard, every time (ruled 2026-09-21).** The subscribe-time check (§ Registration) is a courtesy refusal; the dial is the boundary. Each POST goes through `ssrf.rs`'s guarded client: https only, the host resolved and **every** resolved address globally routable, the connection pinned to those verified addresses (no DNS rebinding), redirects off (a permitted relay cannot `302` inward). A row the guard refuses from its URL text alone can never be dialled — it predates the subscribe-time check — so it is cleaned up like a dead endpoint; a row refused on a resolver's answer is skipped and kept, because that answer can change.

**A push can never stall the person who caused it (ruled 2026-09-21).** The endpoints are the *recipient's* choice, and the events that trigger a push are other people's writes — an inbox delivery, a knock, an invite, a removal — so a sender's call must never run at the speed of a stranger's push relay. Two bounds, both hard-coded constants (nobody has a reason to choose them — `../../principles.md` § One configuration surface): **(1) off the reply path** — the *decision* (which of the actor's devices are present right now?) is taken synchronously inside the sender's handler, so it reflects the moment of the delivery, and the dispatch itself (the subscription read and the POSTs) runs as a background task scoped to the serving generation; nothing a sender is told depends on a push's outcome, so no synchronous-before-reply property is kept. **(2) bounded in time** — each request, web-push and APNs alike, has a 10-second ceiling, and one whole dispatch (all of an actor's subscriptions, dialled in turn) a 30-second one, so an endpoint that accepts a connection and never answers costs one background task a fixed number of seconds and costs no sender anything. Subscriptions a deadline cuts off are simply not pushed that time: push is best-effort. The one awaited caller is the certificate-renewal nudge, which is already a background loop with no sender behind it.

**Implementation status today (2026-09-21):** implemented nest-side — `push.rs` § *The dial policy* (`validate_subscription_endpoint`, `web_push_client`, `dispatch_offline_push`, `PUSH_REQUEST_TIMEOUT` / `PUSH_DISPATCH_DEADLINE`), every sender-triggered call site routed through `dispatch_offline_push`. Pins: the shipped-build refusals at subscribe and at the dial, the two time bounds against a listener that never answers, and the sender not waiting, in `push.rs`'s own tests (the shipped posture is asserted on cfg-free strict functions, so the all-features gate arm runs it); the any-build refusals end to end in `tests/e2e-unified/tests/api/test_push_api.py`; the dispatch itself, and *no push while connected* anchored on the nest's test-only dispatch-decision counter rather than on an empty listener, in `tests/e2e-unified/tests/api/test_push_dispatch.py`. No app change: the apps already register real relay URLs and hex tokens. **Per-device rule (2026-09-26): implemented nest-side.** `dispatch_offline_push` takes a `DevicePresence` snapshot (`WsState::device_presence`) in the sender's handler and hands it to the background dispatch, which decides each row with `DevicePresence::action_for`; `cert_nudge.rs` feeds `maybe_send_push` the same snapshot. Pins: the per-row rule, the snapshot-at-the-event bound and `ws-device` delivery in `push.rs`'s tests; end to end in `test_push_dispatch.py` — an announced present device skipped while an absent one is dialled, an unannounced connection suppressing it, and a `ws-device` row delivered as a frame and skipped when not live — anchored on the test-hooks counters (decisions before the reply; outcomes summed before `settled` moves). **The stand-in announce (ruled 2026-10-03): NOT BUILT.** Today `PresenceRequest` carries `device_id` alone, `WsState::device_presence` folds every announce into one set, `DevicePresence::action_for` skips a relay row for any announced device, and the agent's account host announces plainly (`bins/fauna-sync-agent/src/account_host.rs`, `set_push_presence`) — so the agent reads as an app. No install is affected yet: the only relay row keyed under an agent-announced id is a macOS `apns` row, and none can be registered until the entitlement gate opens.

### Content Encryption

Both transports use the same encryption scheme: ECDH key agreement with the subscriber's P-256 public key, HKDF-SHA256 key derivation, AES-128-GCM encryption. Web push sends generic content ("New message") since the encryption is mandatory by spec. APNs sends encrypted rich content (sender name, preview) in an `encrypted_payload` field alongside a generic `aps.alert` fallback — the iOS Notification Service Extension decrypts before display. `ws-device` needs neither (ruled 2026-09-26): the frame rides the nest's own authenticated, identity-pinned WS-RPC channel (`../security.md` § Transport trust) with no intermediary, and carries the same generic strings web-push carries.

## Minimum Viable App

A new platform needs at minimum:

1. **Ed25519 keypair** — generation (`ActorKeypair::generate()`) and import (hex secret key), with secure platform storage (§ Credential storage).
2. **Auth token flow** — silent-challenge (WS-RPC `fauna.auth.challenge` + `fauna.auth.verify`) at launch; `fauna.auth.handshake` (WS-RPC) for runtime refresh.
3. **Feed display** — `fauna.feed.*` reads with source badges.
4. **Post creation** — `fauna.posts.create`.
5. **Inbox** — drain over the WS-RPC kinds `fauna.inbox.fetch` (peek) + `fauna.inbox.ack` (consume); a read-only display surface peeks and never acks.
6. **WebSocket** — the persistent WS-RPC connection for calls + real-time updates.
7. **MLS engine** — encrypted DMs via key packages, Welcome flow, local encrypt/decrypt.

Everything else (sync, groups, calendars, bridges, subscriptions) can be added incrementally.
