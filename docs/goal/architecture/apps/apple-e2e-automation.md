# Apple (macOS + iOS) E2E automation — in-process, registry-driven

Owns: apple-inprocess-automation
Status: ratified
Authority: apple-app e2e driving architecture — the in-process automation server, AutomationRegistry + the `automation*` modifiers, the per-instance-port model, iOS simulator isolation, and the macOS/iOS driver contract; supersedes the retired XCUITest/AutomationMode bridge (and the frozen 2026-03-30 apple-bridge spec); the cross-app e2e contract (`/element/*` shapes, test-id naming, tiers) → [`../e2e-conventions.md`](../e2e-conventions.md) § Cross-app e2e conventions; the reference in-process shape → [`linux.md`](linux.md) § E2E automation.

## Why this exists (the problem with XCUITest)

Apple was the lone app driven by an external cross-process bridge (XCUITest driving `XCUIApplication`), which intrinsically enables macOS **AutomationMode** — a single machine-wide resource that wedges reboot-only on any unclean exit and serializes every apple e2e run on the machine. Driving the app **in-process** needs no AutomationMode → nothing to wedge, per-instance ports → concurrent runs. This is the priority #1/#3 uniform shape: apple matches linux, which already drives itself in-process.

## Why a registry, not accessibility (the Phase-0 finding)

SwiftUI has no in-process introspection: the NSAccessibility tree is built lazily only for an *external* AT client (an in-process walk sees an empty `AXGroup` shell), and `AXUIElementCreateApplication(getpid())` needs a manual TCC grant (violating *works out-of-the-box*) and deadlocks on self-query. So the automatable surface is **built explicitly by the views**: each interactive control registers its action/value closures in a test-only `AutomationRegistry`, keyed by the same test id it already carries in `.accessibilityIdentifier(...)` — the in-process analogue of GTK's widget tree, sound by construction and platform-agnostic (macOS and iOS share one driving path).

## Architecture

Mirrors `linux.md` § E2E automation; same `HttpBridgeDriver` `/element/*` contract, apple-specific backend.

1. **`AutomationRegistry`** (`FaunaKit/Sources/FaunaKit/Testing/AutomationRegistry.swift`, `@MainActor`). Maps test id → `Entry { activate, doubleActivate, text, value, setValue, options, isEnabled, visibleText }` closures. The slot lifecycle is driven by **three signals answering three different questions** (2026-07-16; rule 2a): **show** = window attachment (`_AttachmentSentinel`, a zero-size representable riding every registered element's `.background`; `.onAppear` doubles as an upsert-idempotent fallback) — an upsert that appends on first show and *un-hides in place* on a comeback; **repeated ids are index-addressable in on-screen document order** (top-to-bottom, then left-to-right, resolved at lookup time from each slot's live sentinel geometry — NOT registration order, which SwiftUI does not deliver reliably: a macOS `Form`'s rows register bottom-up, the wizard frequency-pick defect, and an iOS lazy `List` registers rows as they materialize; geometry also makes the flat index agree with `.automationScope`'s visual indices, and backs the `/element/attr?attr=frame` read); **off-screen** = the **conjunction** of `.onDisappear` AND window detach → `hide` (slot kept, invisible to every lookup). Neither signal alone proves the element left the screen — `.onDisappear` also fires for a NavigationStack root merely *covered* by a pushed detail (pop restores it with no balancing `.onAppear`), and window detach also fires for a macOS table row scrolled out of an eagerly realized `List`, which the driver contract counts (macOS tests index below-the-fold rows); both fire together for the states that must read absent (a deselected tab, an iOS lazy-`List` scroll-out, an iOS push over the root), and a sentinel-less context trusts `.onDisappear` alone (the pre-sentinel lifecycle); **gone** = view-identity death (`@State` storage deinit) → `unregister`, the only signal that actually removes, by the registering view's **stable token** (not LIFO — token removal keeps surviving rows' occurrence index aligned when a non-tail row disappears). Views also **re-register their closures on every body pass** (`refresh`, in place by token — see rule 2). Zero-cost no-op in production (`AutomationRegistry.isEnabled` gates on `FAUNA_E2E_AGENT_PORT`) — but the runtime gate is the *inner* switch only: release artifacts must compile the automation surface out entirely, per [`../e2e-automation-surface-gating.md`](../e2e-automation-surface-gating.md) § Cross-app e2e conventions, convention 15 (ratified 2026-07-23; apple's `#if DEBUG` leg landed 2026-07-24 — `TestAgent`, `InProcessAutomationServer`, and `AutomationRegistry`'s internals are gated, the `automation*` view modifiers stay always-compiling with no-op fallbacks since production call sites use them unconditionally, and a release-build `strings`-grep confirms zero automation symbols).
2. **`automation*` view modifiers** (same file): `.automationActivate(id, isEnabled:text:value:doubleActivate:) { action }`, `.automationValue(id, text:value:isEnabled:)`, the `automationText(id, @autoclosure)` label wrapper (renders `Text` + registers the same string, so render and read can't drift), `automationField(id, text: Binding, visibleText:)` (the optional `visibleText` reader backs `/element/attr?attr=visible` for a field whose rendered text differs from its source, e.g. the compose field's concealed markdown markers; `nil` elsewhere so an unwired reader fails loudly instead of silently falling back to the source), `.automationSelect(id, value:, options:, set:)` (Pickers/Sliders via `POST /element/select`; `options` is the picker's live-rendered choice list — convention 11's twin rule (2026-08-10, [`../e2e-conventions.md`](../e2e-conventions.md) § Cross-app e2e conventions) — a `select` value absent from it is refused 409, not written through; `nil` keeps a not-yet-converted call site's old unchecked write-through). Applied **alongside** `.accessibilityIdentifier(id)`, never replacing it. An actuatable control that is also *read* registers both faces in the **same** `Entry` (a second `.automationValue` for the same id would split activate and read across two index slots): `value` backs `/element/attr`, `text` backs `/element/text` and falls back to `value` when absent — so a row whose stable machine identity differs from its rendered label passes **both** (`calendar-event-block`: `value` = the event id, `text` = the summary, which is what every other app's driver reads back for that id).
3. **`InProcessAutomationServer`** (same dir; `#if os(macOS) || os(iOS)` — pure Foundation + Darwin sockets). A BSD-socket HTTP server on the per-instance `FAUNA_E2E_AGENT_PORT` serving `/element/{click,double_click,type,clear,text,visible,count,enabled,attr,select}`, the `/app/{state,commands}` state protocol (shared `serializeState`/`handleTestCommand` callbacks; `ready=false`-while-processing + a bounded render-settle so state commands ack only after the re-render registered new controls), `/health`, `/tree`, `/registry`, and `/element/scroll-into-view`. `/scroll` (blind page-step), `/screenshot` and `/dismiss-dialogs` are stubs (as on linux).

    **`/element/scroll-into-view` is REAL on both apple apps** (2026-08-02) — it centres the element in every enclosing scroll view, innermost outward, by walking up from that element's own registration sentinel, and both drivers set `_supports_scroll_into_view = True`. It had been grouped with the stubs above, justified "as on linux" — which was never true of *this* route: linux implements it (`apps/fauna-linux/src/automation/agent.rs::scroll_into_view`), as do web, windows and tui, so apple was the lone app of the seven without a targeted scroll. The reply shape is linux's 1:1 (`{"found": true}`, else an `error` string; a resolvable element under no scroll view is an `error`, not a success). Two properties are load-bearing and cost prior sessions real time to learn: **nearest-ancestor, not largest** — the retired XCUITest bridge picked the largest scroll view on screen and so scrolled the background window instead of a presented sheet; walking up from the sentinel makes that unrepresentable, and continuing outward past the first hit is what reaches the nested single-scroll `PreferencesView` panes the old bridge could not. **Centred, not merely visible** — windows' FlaUI bridge flips `!IsOffscreen` at ~25% visibility, below the shared 500‰/750‰ engagement-cue gates, so edge-aligned "success" would report a dwell the user never had. The scroll drives the real clip view / content offset, so a dwell measured after it is an honest exposure rather than an injected one.
4. **App-shell wiring** (`FaunaMacApp.swift`, `FaunaApp.swift`): `startInProcessAgentIfNeeded()` under `FAUNA_E2E_AGENT_PORT`. Every e2e gate — mock backends, e2e reset, the release-feed stub, `KeychainStore`'s **in-memory mode** (mandatory: an ad-hoc-signed terminal launch otherwise blocks on a securityd ACL prompt) — keys on the ONE `FaunaE2E.isActive` predicate.
5. **Drivers** (`drivers/macos.py` `MacosInProcessDriver`, `drivers/ios.py` `IosInProcessDriver`, both on the `InProcessAgentDriver` base): launch the app directly with a per-instance port + isolated state and POST to the in-app server. macOS launches the **bare** swift-build binary — never the `.app` bundle (§ Registration rules rule 9; the one opt-in exception is § Artifact launch mode). iOS launches via `simctl` into a **per-pytest-session ephemeral simulator** (`_create_ephemeral_simulator`, deleted at exit) with per-session-keyed derived data, so iOS e2e is concurrent across sessions like macOS/linux.

## Registration rules (load-bearing — copy these, don't rediscover them)

1. **Additive modifiers, never wrappers:** register with the `automation*` modifiers next to the existing `.accessibilityIdentifier(id)`; a pure modifier can't capture a `Button`'s action, so the activate closure **must invoke the same named method** the control's action invokes (extract one method both sites call).
2. **Live reads — the registry re-registers every body pass, so capture style no longer matters** (fixed 2026-07-12; the `.id(...)` workaround this rule used to mandate is **retired** — don't add new ones). `.onAppear` fires once per view *identity*, but a SwiftUI view is a **value**: each body pass rebuilds the `Entry` with closures capturing *that pass's* values. Registering only at `.onAppear` therefore froze the **first** render's closures forever, so a view capturing its model struct **by value** (`let folder: FolderSummary`, read as `folder.webdavEnabled`) served the driver a stale read indefinitely — while the on-screen SwiftUI rendering stayed fully live (SwiftUI re-derives the real `Binding` at interaction time), making it **invisible to a human and to render-only tests**. It surfaced as a *silent no-op*: the folder serve-OFF click kept computing `apply(!isOn)` = `apply(true)` off a stale `isOn`. Views capturing a **reference** type (`vm.snapshot?.webdavEnabled`) dodged it by luck — a stale closure still reads through the live reference — which is why it survived so long, and why "just capture a VM" was never a rule anyone could rely on. `_AutomationRegister.body` now calls `AutomationRegistry.refresh` on every pass, in place by token, so **both capture styles behave identically**. Slot order, count, and visibility are untouched (`refresh` of an absent token is a deliberate no-op, never an append; a hidden slot's body pass updates closures without un-hiding — being rendered by SwiftUI is not the same as being on screen).

    **2a. Show/hide is WINDOW ATTACHMENT, not `.onAppear`/`.onDisappear` — because SwiftUI's pair is unbalanced** (fixed 2026-07-16; iOS Gap B). A `NavigationStack` detail push fires the root's `.onDisappear`, but the pop fires **no** matching `.onAppear` — the root was never structurally removed, so it never "re-appears". Under the old remove-on-disappear lifecycle, one detail push therefore *permanently* deregistered every root-level element (`calendar-date-label`: `count == 0` on a visibly rendered label, unrecoverable by any navigation — the property that long masqueraded as a render race). The platform window attachment IS balanced: UIKit/AppKit re-attach the uncovered root's view on pop, a re-selected tab's view on switch-back. So every registered element carries an `_AttachmentSentinel` in its `.background` (e2e-gated, zero production cost): attach → `register` (upsert — a hidden slot un-hides **in place**, never a tail re-append, which would shift every survivor's occurrence index); the conjunction of detach AND `.onDisappear` → `hide` (slot kept in place — either signal alone also fires for still-visible states: a covered root's disappear, an eagerly-realized macOS table row's scroll-out detach); identity death → `unregister` (the real removal). A sentinel-less context trusts `.onDisappear` alone. **Which vote an `.onDisappear` casts is read off the sentinel at that instant, and ONLY "still attached" is a cover** (2026-08-05; `AutomationRegistry.hideSignal`): attached → the single `disappear` vote (the covered root, restored by the pop with no balancing `.onAppear`); **detached OR sentinel-less → definitive**, because a view that has already left its window is an exit, not a cover — and holding out for a detach vote that was demonstrably already missed is what stranded one slot on **every `.navigationDestination` pop**: SwiftUI tears a popped destination's hosting views down without always delivering `didMoveToWindow(nil)`, so the slot sat `VISIBLE(no-geo)` forever and the driver resolved occurrence **[0]**, a DEAD form instance, while the live form kept its own state (a test typing weight `1.5` submitted the previous test's `2000` permille; a `select` never switched the live branch — 10 such zombies measured in one iOS module run). The same teardown is closed from the other side by the sentinel's own death: **a DEALLOCATED probe votes detach** (one replaced for a still-live view identity is marked superseded and votes nothing), which is the only signal that survives here — SwiftUI holds a popped destination's `@State`, and therefore defers `_AutomationLifecycle.deinit`'s `unregister`, well past the pop, which is why three generations of the same ids were observed alive at once. **Neither is a change to the conjunction above** — the registry still needs BOTH votes to hide a geometry-less slot; what changed is the accuracy of the votes the view layer emits, and mis-voting cannot hide a live element because an on-screen view has geometry and geometry-FIRST ignores votes for it. Pinned by `AutomationRegistryTests.swift` § *`.onDisappear`'s vote accuracy* (`onDisappearVotesDefinitivelyUnlessTheSentinelIsStillAttached`, `aDisappearWhileDetachedHidesAGeometrylessSlot`, `aDeallocatedSentinelVotesDetachSoAPoppedSlotCannotLinger`, `aReplacedSentinelDoesNotVoteForTheSlotItsSuccessorOwns`). Visibility is **geometry-FIRST**: an ATTACHED slot (sentinel realized, so its `geometry()` is non-nil) is decided by its live frame ALONE — on-screen (x-origin within the window) = present, parked off-window on x = absent — and **votes are irrelevant to it**. Votes decide ONLY a geometry-less slot (detached — a detached sentinel reports nil geometry — or a context with no sentinel: macOS's eagerly-realized below-the-fold rows, an iOS lazy-`List` scroll-out). Geometry must be primary, not a both-votes-gated guard, because UIKit churn does **not** reliably deliver both off-screen votes: a re-attached dead cell parked at the transition offset (observed x≈−74…−89 for a just-deleted row) arrived with only ONE vote, so the old `if !(sawDisappear && sawDetach) { return true }` short-circuit read it present with the dead row's closures — the `test_event_create_and_delete[ios]` delete-zombie. Deciding an attached slot purely on its frame removes the vote race: a live view settled on screen (a NavigationStack root uncovered by a pop, which fires no balancing `.onAppear`) is present, and the parked zombie is absent, however many votes churn delivered. (Geometry-FIRST catches only the *parked* zombie. A live trace on 2026-07-16 found a SECOND delete-zombie manifestation it cannot catch: an iOS lazy `List` POOLS a removed row's hosting view still ON-SCREEN — x≈32 — so geometry-FIRST reads it present, and its `_AutomationLifecycle.deinit` fires only when the pool slot is later reused, well past the test window. That one is fixed app-side per **rule 6**, not in the registry: the iOS Events agenda (`CalendarListView`) + detail (`EventDetailView`) were lazy `List`s; converting them to eager `ScrollView { VStack }` tears a removed row down at once → deinit → unregister. This supersedes an earlier `.id(vm.events.map(\.id))` band-aid on the lazy `List`, which a trace proved flaky — see the resolved-known-open note below (`test_event_create_and_delete` + the rsvp/reminder union-card leak).) The test is deliberately **horizontal-only**: **vertical** overflow must stay present — an eager `ScrollView { VStack }` page (rule 6) keeps below-the-fold content attached beyond the window's height, and the driver legitimately drives those closures without scrolling. Regression gate: `tests/e2e-unified/tests/test_automation_registry_lifecycle.py` (Class 2 + the remount control) and the `FaunaKitTests/AutomationRegistryTests.swift` order-restoration + geometry-FIRST tests.
3. **Stay in the host body tree:** anything a test must reach may not live behind a `.sheet`, `Menu`, `.confirmationDialog`, `.popover`, or a tap-driven `NavigationLink` — system presentation layers don't reliably `.onAppear`-register, and the driver performs no real gestures. Convert to an inline `@State`-driven reveal (the disable-confirm/MSEK pattern; also the cross-app shape — web/linux render these inline) or a state-driven `.navigationDestination(item:)` push off a `@Bindable`-projected binding.
    **3a. A confirm that MUST stay in a `.alert` needs two extra things, and neither is optional** (measured 2026-09-21 on macOS; `folder-residency-confirm`). Rule 3 says keep it out of a presentation layer, and where the cross-app shape allows that, do. The folder confirms cannot: `folder-audience-public-confirm` / `folder-residency-confirm` / `folder-delete-confirm` are `.alert`s on every app, so converting apple alone would be the per-app divergence priority #1 forbids. For those, rule 3's premise needs one correction and its consequence two fixes. **The correction:** alert content DOES `.onAppear`-register — the slot appears exactly on present. **What it can never do is de-register.** SwiftUI does not fire `.onDisappear` for alert content, and the `_AttachmentSentinel` rides in `.background(...)`, which an alert's content builder never realizes — so there is no probe to report a window detach, none to die, and no geometry either. The dismissed slot measures `VISIBLE(no-geo) geo=nil votes=-`: **zero** votes, not the lone detach vote the rule-2a lifecycle would predict, so nothing in that lifecycle can ever retire it and `is_visible` answers `true` for the rest of the process. **(i)** The host therefore declares the ids' lifetime from its own `isPresented` binding — `View.automationPresentation(ids:isPresented:)`, over `AutomationRegistry.hideAll`, which casts both votes at once. Safe to hand a bare id by construction: `hideAll` only votes, and geometry-FIRST means a slot settled on screen elsewhere under the same id shrugs it off. **(ii)** `.automationActivate` inside presentation content must ALSO dismiss the presentation. A real press of an alert Button does two things — runs the action, and lets SwiftUI clear the binding — and the seam reaches only the action, so answering a confirm through it left the modal **genuinely on screen**; the tell was not the stuck id but the *next* test's folder wizard never opening, because a live modal blocks the next sheet. Dispatch the mutation first and clear the binding after: clearing first tears the alert down with the write still queued and loses it. An invisible shim rendered only while dismissed is refused by e2e convention 1. Pinned by `AutomationRegistryTests.swift` § *Presentation-hosted slots* and by `test_folder_residency_control.py`'s flip-back arm, which is the only witness on any app that asserts a confirm is GONE — which is why three apple passes hunted this and the audience twin never saw it.

4. **Positional `[idx]` ids on re-filtering lists:** a `ForEach` that bakes a literal index into the registered id must tie row identity to `(index, stable-content-key)` via `.id(...)` — else a membership/order change leaves a stale slot registered under the old index.
5. **Scoped queries:** a container that must support `scope="card[N]/..."` pushes `.automationScope(id, index:)`; each slot stores its ancestor scope path and scoped queries resolve by **descendant matching** (e2e-conventions.md § convention 1) — a query may name only the containers it cares about (`scope="quoted-post"`, no `card` prefix), leaving the ones between it and the root implicit, since `AutomationRegistry.scopeRoot` searches for the queried `(id, index)` step anywhere below the previously resolved step, not only as a root-anchored prefix (fixed 2026-08-24 — apple was the last of the four scoped-query apps still root-anchored; the bug was already live via `QuotedPostCard`'s own nesting inside `post-card`, not merely latent). Ids without a pushed scope fall back to the flat occurrence-index heuristic.
6. **Pages render eagerly — on BOTH apple apps:** a page that must be fully drivable uses `ScrollView { VStack { GroupBox } }` (every `Admin*View`'s shape), **not** `Form` or `List`. An iOS `Form` is a lazy `List` whose off-screen sections never `.onAppear`-register. **macOS is exempt only for `Form`, NOT for `List`** (corrected 2026-07-30; the earlier "macOS realizes eagerly and masks it" was read as covering both, and it does not). A macOS `List` is an NSTableView that realizes rows lazily, so a row APPENDED to a live `ForEach` can go unbuilt indefinitely — no view, no `.onAppear`, no registration, and therefore no way for the driver to tell it from a write that never landed. Measured on the macOS Events agenda: after a successful create the list showed only the earlier event for the full 30 s budget with exactly ONE `event-card` slot registered (`1/1 visible` — not a second slot hidden or geo-parked) and ~300pt of empty pane below it, while a view-mode round trip that ran no query rendered both. That is `test_event_create_and_delete[macos]`, red ~35% under machine load across five sessions. It also means a row COUNT on a lazy macOS list is not a measure of the data — the count saturates at whatever the table happened to realize, which is why the events module's count barriers had to be swept to identity barriers (2026-07-29) before this was understood. Converting to an eager `ScrollView { VStack }` restores both the count and the identity.
7. **Inject commands mutate what the view observes:** route every test-inject through the app-level VM/manager the rendered view reads (one `.environment`-injected instance), never a fresh `api.<thing>Manager()` — and read e2e state from that same instance.
8. **`error-message` registers only when non-empty** (the cross-app "built hidden, shown on error" contract).
9. **macOS launches the bare binary.** The fixed-bundle-ID `.app` launch wedges WindowServer over repeated launch-and-die cycles (app alive, zero windows, empty registry — the fleet-wide "render-death" once misdiagnosed as VM degradation); the bare binary's per-build ad-hoc identity never wedges. `assert_render_ready` stays as a tripwire. **The one sanctioned exception is the opt-in artifact mode — § Artifact launch mode below — which restores the same property explicitly rather than dropping it.**

10. **A registered WRITE must reach the model before it returns — `.onChange` is one update pass too late** (measured 2026-09-21; `dm-text-field`). `/element/type` sets the bound `@State` synchronously, but a field whose model push rides `.onChange(of:)` has only updated the *field*: SwiftUI runs that observer on its NEXT update pass. Anything the driver does next that reads **model-derived** state — the leave-flush doors read `ConversationsManager.draftsSnapshotBytes()`, not the field — then races that pass. It is invisible in tests that type and then assert on the field, and it does not fail cleanly: the model is simply one edit behind, so a correct `saveIfChanged` no-ops and the run reads as a product gap. Measured as **pass/fail/pass on three identical `test_apple_leave_flush.py` ios runs** with no code change between them — the wall-clock dependence e2e convention 14 forbids, arriving through the automation surface rather than through a `sleep`. **So a control whose `automationField` binding is separate from the real input's binding pushes to the model IN ITS OWN SETTER**, and `.onChange` stays as the funnel for every other writer (the real text view, restore, a toolbar mutation). Only the automation path changes — a real keystroke keeps its ordinary one-pass propagation, which is what convention 11's fidelity rule actually asks for: the agent's write must leave the state a keystroke would, and by the time a user quits or backgrounds, a keystroke's has reached the model. The repeat `.onChange` fire is harmless where the model setter is idempotent; check that before applying this to a new control.

11. **A control whose rendered label CHANGES registers `text:` with the same expression as its title — a bare `.automationActivate(id) { … }` reads `""` through `/element/text` however the button renders** (measured 2026-09-25; `mail-aliases-list-item-overflow-menu`, after `mail-lists-list-item-delete-button` and `mail-spam-reset-model-button`). `paintedTexts()` reads `entry.text?() ?? entry.value?() ?? ""`, and a SwiftUI `Button` gives the registry no way to see its own title, so a two-click confirm's armed relabel — the only visible affordance the confirm has — rendered correctly for a user and stayed unreadable to every test until one first asserted it. Share the label expression between the `Button` title and the `text:` closure (one method both call, rule 1's shape). **The guard is behavioural, not static:** an e2e reads each armed confirm's label (mail-aliases outcome 29, mail-lists outcome 6, mail-spam's reset), asserting the literal armed wording (`apps/common.md` § Two-click confirm).

    **No source scan backs this rule — decided 2026-09-25, revisit when a test-first read of another dynamic label finds a further gap.** What IS gated is the *presence* class (`apple-automation-registration-ratchet-check`, § Implementation status: a new `.accessibilityIdentifier(id)` with no registration at all); `ui-actual-lint` covers ids only and says nothing about registration either way. The `text:`-less dynamic-title class was measured with a throwaway regex scan: 16 of 693 `.automationActivate` sites (14 after the two-click-confirm fixes, the only two-click confirms among them) — the rest are toggle and submit-progress swaps (`Show`/`Hide`, `Saving…`, `Send`/`Sending`, `New event`/`Cancel`). A scan cannot see a title built by a helper or computed property (false negatives) and would freeze the read-by-nobody swaps as baseline noise, while the failure it targets is loud and a one-line fix the moment a test reads the label.

## Artifact launch mode (opt-in; `--macos-artifact`)

Ratified 2026-08-09. The **default driving path is unchanged and stays bare-binary** — every apple e2e test in the fleet rides it, and rule 9 above is untouched. This section governs a separate, opt-in mode whose subject is the **shipped artifact**: the `Fauna.app` bundle `just mac-app` assembles, which `mac-dmg` packages and the all-in-one installer `.pkg` installs.

**Why it exists.** A bare Mach-O has no bundle identity, no Info.plist, no `Contents/Resources`, no embedded app extensions, no bundled `fauna-sync-agent`, and no code signature carrying entitlements. All of that is created by packaging and consumed at runtime, so the default path exercises none of it. This is the client-side analogue of the packaging-bug class tier_4 exists to catch for the nest ([`../testing.md`](../testing.md) § The four-tier taxonomy) — on Apple platforms packaging is precisely where runtime behaviour changes.

**The mechanism, and the mine it avoids.** Rule 9's cause was the FIXED identity, not the bundle: the bare binary is safe because its ad-hoc identifier is per-*build*, so no two launches share one Launch Services identity. The artifact mode reproduces that property deliberately — each launch **stages a private copy** of the bundle (APFS clone) into its own temp dir, rewrites `CFBundleIdentifier` to `social.fauna.fauna.e2e.<pid>-<port>`, and re-signs ad-hoc **carrying the original entitlements forward** (the plist edit invalidates the signature, and re-signing without the entitlements would silently change the artifact's capability posture). It then launches the copy's inner executable directly, exactly as the bare path does — which keeps the per-instance env and PID ownership the driver depends on, while `Bundle.main` still resolves to the staged `.app`. `assert_render_ready` stops being a formality here and becomes the actual assertion: a reintroduced fixed id renders fine *once*, then stops.

**The subject is the DEBUG-config bundle, and that substitution is pinned, not assumed.** Convention 15 compiles the automation surface out of release artifacts entirely, so `build/Release/Fauna.app` — the bundle that actually ships — has no in-process agent and cannot be driven at all. The debug bundle is a faithful stand-in because `just mac-app` branches on `{{config}}` in exactly two places (the FFI flavour and `swift build -c`) and every packaging step after that is config-independent. A test reads the recipe and asserts that, so a future `$CONFIG` branch around a packaging step turns red at the moment the substitution stops being honest.

**Scope and cost.** Run-level and single-valued, like `--nest docker`: the flag swaps what `--app macos` launches, so any macOS journey can be replayed against the artifact. The same flag is the collection gate on `tests/e2e-unified/tests/artifact/` — without it that directory is never imported, so no default sweep or tier filter can reach it. The suite is `tier_4`, opt-in, and never the inner loop: `just e2e-macos-artifact-test`.

## The actuation gate (`isEnabled`)

The five routes that **drive** a control — `/element/{click,double_click,type,clear,select}` — consult the resolved `Entry.isEnabled` predicate before invoking the registered closure. A control the real UI has `.disabled(...)` is therefore not actuable by the harness, which is the cross-app rule stated in [`../e2e-conventions.md`](../e2e-conventions.md) § Cross-app e2e conventions, convention 11 (*an illegal command is the same failure one layer down*) — not restated here. Read routes (`/element/{text,visible,count,enabled,attr}`) are unaffected: reading a disabled control is exactly how a test asserts that it *is* disabled.

Apple mechanism:

- **Decision** — `InProcessAutomationServer.actuationGate(route:id:index:isEnabled:strict:)`, pure + `static` so it is unit-testable with no socket, app or registry (`FaunaKitTests/AutomationActuationGateTests.swift`); the five routes share the one `gateActuation` call site each.
- **No predicate ⇒ *inherit*, and only then enabled** (since 2026-08-17; it read "no predicate ⇒ enabled" before). `_AutomationRegister` reads SwiftUI's `\.isEnabled` — the cumulative, non-revocable "has any ancestor disabled me" — and folds it into the registered predicate (`AutomationRegistry.folding`, pure and unit-pinned). A control greyed only by an ancestor used to report `enabled=true`, because `nil` reads as enabled and `strictEnabled` consults the very predicate that is `nil`; the driver's answer and the real UI then disagreed in the direction that costs debugging (the test actuates it, nothing happens, the failure presents as a *product* bug). Two consequences worth stating: an explicit `isEnabled:` still wins on specificity where the ancestor is enabled, and the fold sees **ancestors only** — a `.disabled(…)` written *inside* the automation modifier (`.disabled(…).automationActivate(…)`, the minority order) is invisible to it, which is exactly the population that already hand-mirrors its predicate. Registrations that pass no predicate and sit under nothing disabled stay drivable, unchanged.
- **The offline gate no longer publishes a key of its own.** `.faunaGate(kind)` applies `.disabled(!available)`, so the fold above already carries its verdict to the registry; the dedicated `faunaOfflineGateEnabled` environment key it used for that between 2026-08-16 and 2026-08-17 is **deleted**, and its deletion is the proof the general read subsumes the special case. See [`../account-offline-mutation.md`](../account-offline-mutation.md) § The offline-mutation contract.
- **Live, never captured.** The predicate is called per request, because registrations re-run every body pass and close over view state (`!vm.isBusy`, `!form.canCreate`). A snapshot would refuse a control that has since enabled — worse than not gating.
- **Refusal shape** — HTTP **409** (not 404: the element was resolved; its *state* is the problem, and `drivers/http_bridge.py` maps 404→`LookupError` but every other code→a loud `RuntimeError`), body `{"error": "element is disabled: <id>[<index>] — <route> refused …", "id", "index"}`.
- **Default since 2026-08-05; the staged rollout is complete.** Refusal is on unless a run opts out with `FAUNA_E2E_PERMISSIVE_ACTUATION` (`FaunaE2E.strictEnabled`, set by pytest's `--permissive-actuation` for the session-scoped apple launch). With the opt-out the route still drives the control but `NSLog`s one `[InProcessAutomation] DISABLED-ACTUATION <route> id=<id> index=<n>` line, which reaches the macOS driver's captured `app.err` (`drivers/macos.py::app_stderr_text`), so a test can read its OWN violations mid-run without a new red. The flag inverted at the flip — it was `FAUNA_E2E_STRICT_ENABLED`, an opt-IN, while the blast radius was unmeasured.
- **The permissive mode is the measuring instrument and outlives the flip** — it is not a vestige of staging. It is what a future broad change to either apple app re-measures itself with, and the shape linux (2026-09-10) and windows (2026-09-14) kept when their own rollouts flipped, so it is kept deliberately rather than deleted with the staging it served.
- **Whole-suite enumeration is the PERMISSIVE run, not the strict one** (`--actuation-log PATH` → `FAUNA_E2E_ACTUATION_LOG`, `FaunaE2E.actuationLogPath`). This composes the opposite way round from the obvious guess, and the reason is the load-bearing part: a strict refusal **fails its test**, and a failed test **stops**, so a strict sweep reports at most the *first* offender per test and silently hides every later one. A permissive sweep turns nothing red, so it enumerates offenders exhaustively *and* doubles as the pre-existing-red baseline the flip decision has to subtract — which matters on a suite whose macOS baseline already carries ~75 unrelated failures. The strict mode's job is enforcement after the flip, not discovery before it.
- **The measured blast radius (2026-08-03, full permissive `--app macos` sweep, 1440 passed / 99 failed / 65 skipped / 11 errors in 1h41m)** — across **1575 tests observed, 4 violating calls on 3 elements**, all on the `click` route. One (`contact-actor-id-lookup`) is the gate's own probe test driving a disabled control on purpose. The other two were real: `create-feed` (2 tests) and `admin-factory-reset-button` (1 test). **All three registrations were CORRECT** — each `isEnabled:` predicate mirrors the view's real `.disabled(...)` (for the reset button, the whole danger-zone `GroupBox` carries `.disabled(vm.isBusy)`, which SwiftUI propagates down) — so there were **zero registration bugs**, and every violation was the harness driving a control no user could reach. The shared cause was one idiom: `wait_for(id)` proves an element RENDERED, not that it is ENABLED, so `wait_for` + `click` fires in the window where a control is visible but transiently disabled (`!form.canCreate`, `vm.creatingFeed`, `vm.isBusy`). Fixed with `HttpBridgeDriver.wait_until_enabled` at the offending call sites — the explicit form of what Playwright's `click()` does for web automatically.
- **Why the log file exists at all** — `app.err` lives in the launch's temp dir and the `app` fixture cold-relaunches at every module boundary (`helpers/module_relaunch.py`), so stderr markers cannot survive a sweep. `FAUNA_E2E_ACTUATION_LOG` names one run-scoped file that every launch appends to (best-effort: an unwritable sink never fails the app under test), while pytest stamps a `=== TEST <nodeid>` boundary before each test, so every marker arrives attributed to the test that caused it rather than a timestamp to correlate by hand. Unit-pinned in `FaunaKitTests/AutomationActuationGateTests.swift` (`AutomationActuationLogTests`); e2e proof of the wiring in both modes: `tests/e2e-unified/tests/test_apple_disabled_actuation.py`.
- **A test that WANTS the forbidden state re-arranges the precondition; it does not open the gate (2026-08-28).** The blast-radius sweep above is about tests that meant to drive an *enabled* control and raced its enabling — `wait_until_enabled` is the whole fix there. The other shape arrives eventually and takes a different answer: a test whose scenario *requires* a control the gate correctly disables. The measured instance is the two CR-2 crash-recovery journeys (`test_crash_recovery_journeys.py`, `nest/common.md` § Client-state recoverability), which arranged a permanently-failed factory reset by killing the nest and *then* clicking `admin-factory-reset-confirm-button`. `fauna.admin.factory_reset` is `OnlineOnly` (`libs/fauna-protocol/src/offline_class.rs`), so once the admin-plane `.faunaGate` fan-out landed the gate refused that click with its 409 — correctly, and the journeys had been arranging a state no user can reach for as long as the gate has existed. **The refusal message names `--permissive-actuation`, and reaching for it here would be the wrong move**: it is session-wide (`conftest.py`, the apple launch is session-scoped), so it disables enforcement for every test in the run to un-say one gate that is telling the truth — the enumeration instrument used as a bypass. What the journeys do instead is arrange the same end state through a door the product really has: they confirm against a **live** nest that parks the dispatch ahead of its handler (`rpc_hold_test_hook`, `e2e-latency-independent-assertions.md`), then take the nest down with the request still parked. The user-reachable story — an admin starts a reset that never lands — is also the deterministic one, and the gate stays enforced. **The general rule: when the gate refuses, ask whether a real user could reach the state at all. If not, the test's arrangement is what is wrong, not the gate.**

## The two introspection routes: `/tree` diagnoses one lookup, `/registry` describes the frame

They answer different questions and neither replaces the other.

- **`GET /tree`** → `AutomationRegistry.debugDump()`, a text dump of **every slot including hidden ones**, with the exact inputs `effectivelyVisible` decides on (live sentinel geometry, off-screen votes), the ancestor scope path and the Entry capability letters. Its job is *"why did this one lookup resolve absent"* — geometry-parked vs. vote-hidden vs. geometry-less vs. scope-path mismatch — read by a human on a failing run. The hidden slots are the point.
- **`GET /registry`** → `AutomationRegistry.snapshot()`, one **record per VISIBLE element** — `id`, `index` (the same occurrence index the driver addresses it with, so a finding can be re-driven verbatim), `enabled`, `declares_enabled` (a *declared* enabled distinguished from a merely *defaulted* one), `actuable`, `editable`, `scope`, `frame`. Its job is *"what is on screen right now"*, read by a **checker** that quantifies over the whole frame instead of over hand-picked ids ([`../e2e-conventions.md`](../e2e-conventions.md) § convention 17). Visible-only, deliberately: it is the screen an invariant quantifies over, and a hidden slot is indistinguishable from an absent one everywhere else on the wire. No cap and no sampling — a truncated list reads as "checked everything" when it did not.

Driver side: `PlatformDriver.registry_snapshot()` (`None` where an app publishes no such surface, `[]` where it looked and found nothing — **opposite** answers that a caller must not collapse, or it reports a clean sweep of a surface it never read). The first consumer is `helpers/registry_audit.py`, whose rulings are pinned at tier_1 in `tests/test_registry_audit.py` and which asserts the two frame-scope properties of losing the nest: **monotonicity** (a gate only ever subtracts, so no control may go disabled → enabled) and **reach** (at least one control must actually have changed, or the gate did nothing measurable and a per-control assertion proves nothing). Neither needs an allow-list of legitimately-offline controls; the checklist phrasing that does need one is `focus-fanout`'s `== 1` mistake in a new costume, because a page's offline-safe controls are most of the page.

## The leave-door routes: each apple target gets its own, and both drive the real delegate

The leave-flush promise ([`../../behavior/reserved-folders.md`](../../behavior/reserved-folders.md) § The leave-flush
promise) is worded door-neutrally — "closing its window, switching away on your phone, quitting" —
because the platforms' leave doors genuinely differ. The automation surface mirrors that rather
than inventing one uniform pseudo-door:

- **`POST /app/lifecycle/quit` (macOS only)** → `NSApp.terminate(nil)`, exactly what the Quit menu
  item sends, so the real `applicationShouldTerminate` gate runs — its bounded drafts/cue flush and
  its `.terminateLater` reply included. It replies *before* terminating, so the caller never has to
  race a process exit for its HTTP response. Driver: `MacosInProcessDriver.quit_app()`.
- **`POST /app/lifecycle/background` (iOS only)** → the real
  `UIApplicationDelegate.applicationDidEnterBackground` on the real `UIApplication.shared.delegate`,
  the same selector UIKit sends on a swipe home. The simulator offers no outside-the-process way to
  background an app (`simctl` has no such verb), so this is the door. The app keeps **running**
  afterwards — backgrounding is not an exit — which is why the flush it triggers rides a
  `beginBackgroundTask` extension and why its witness asserts nest-side state, never process death.
  Driver: `IosDriver.enter_background()`.

**`/window/close` is NOT macOS's leave door and must not be used as one.** Closing a window is
deliberately never a quit on macOS — the sync agent outlives the app session and there is no
close-to-tray setting ([`macos.md`](macos.md) § Sync) — so `performClose` never reaches
`applicationShouldTerminate`. It remains the right route for what it actually tests: that closing a
window does *not* stop the app.

**What these routes prove, and what they do not.** They drive the app's own real delegate callback,
never a test-only flush entry point, so the witness covers the app's own wiring on its own door.
They do not prove that AppKit/UIKit *invoke* those callbacks — that is Apple's contract, exactly as
linux's close-request witness does not prove that GTK emits `close-request`.

## Baseline discipline

The Apple e2e suite is gated by a checked-in baseline rather than a per-change job. Without
a gate, a regression's detection window is however long until someone next runs the
affected test file, which can be weeks on a suite this large. `e2e-apple-baseline` (a dedicated dev-fleet script) runs the full `--client
macos` suite plus a `--client ios` run, diffs every test's outcome against the checked-in
`tests/e2e-unified/baselines/apple-baseline.json`, prints new reds/greens/skips, and
refreshes that file — schema + delta semantics in `tests/e2e-unified/baselines/README.md`.
The session responsible for apple e2e verification runs it as its first act each launch,
before consuming any apple-side signal. A new red is the regression signal; pre-existing
(already-baselined) reds — the apple-gated items tracked —
are not. The format is deliberately what a future CI gate would consume directly.

## Declared platform absences

1. **`focus_move` / `switch_pane` on iOS** (convention 17 layer (c)'s walk vocabulary — [`../e2e-conventions.md`](../e2e-conventions.md) § convention 17; contract `fauna_e2e_agent::{FOCUS_MOVE, SWITCH_PANE}`). Two independent reasons, either alone sufficient: **(a)** UIKit exposes no public in-process API to trigger the focus engine's Tab-equivalent traversal the way AppKit's `NSWindow.selectNextKeyView`/`makeFirstResponder` do — that mechanism responds only to real hardware key/press events, which an app process cannot synthesize into its own responder chain (unlike AppKit's `NSApp.sendEvent`/key-view-loop machinery, which is a supported in-process call). **(b)** iOS's own shell has no sidebar/content two-region split for `switch_pane` to cross in the first place — `MainTabView` (`Fauna-iOS/App/ContentView.swift`) is a bottom `TabView`, not a `NavigationSplitView`, so there is no keyboard-focus-crossing "sidebar" region analogous to tui's `Zone::Sidebar` or macOS's `NavigationSplitView` first column. macOS honours both commands (`FaunaKit/Sources/FaunaKit/Testing/FocusWalkTestCommand.swift`); iOS refuses both by name, citing this section, per convention 17's own prescribed outcome for a genuine structural absence — never a private seam that fakes the traversal.
