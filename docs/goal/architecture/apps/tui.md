# TUI App (`fauna-tui`) — target state

Owns: tui
Status: ratified — § Open decisions all resolved; parity milestone reached 2026-07-19 (M9: user-approved core-journey page set, language flip executed)
Authority: this doc owns TUI-app architecture (TUI shell, terminal render walker, the key-hint footer, e2e automation server, headless credential storage, external media handoff, TUI-specific settings surface, parity gating). Defers to `common.md` for cross-app behavior, `../app-guidelines.md` for the rule book, `../render-model.md` for the render model, and ui.yaml for element IDs / per-page scope.

> **Audience:** anyone implementing `apps/fauna-tui/` (area registered 2026-07-10 with the M0 commit — see § Rollout).
> **Name:** `tui`, not `cli` (renamed 2026-07-12, user-directed). Crate, binary, area, e2e client token and ui.yaml platform flag are all `tui`; the `cli` name stays free for such a tool (the one in-tree argument parser that carried it, `bins/fauna-sync/src/cli.rs`, left with the legacy daemon on 2026-10-02).
> **Purpose:** the target architecture for the seventh fauna app — a full-screen terminal UI (TUI) in pure Rust, feature-equivalent to the other six apps except the declared absences in § Declared platform absences.

## Goal

A single monolithic Rust binary `fauna-tui` — a full-screen terminal UI (ratatui + crossterm) where the async backend (tokio), MLS, sync, and P2P run in-process with `fauna-*` crates linked directly as Cargo dependencies, exactly like the Linux app minus GTK: no FFI, no IPC, no sidecars. Same pages, same concepts, same shared-Rust logic as the other six apps; platform divergence confined to the terminal paint layer and OS integration.

**Why a seventh app (ratified 2026-07-09, user-approved):** first-class UX over SSH and on headless boxes; a power-user surface; the fastest and least flaky e2e driver in the fleet; a standing forcing function for priority #2 (an app with no platform toolkit exposes any logic still trapped in app shells). The cost is acknowledged and accepted: at the parity milestone every cross-app sweep becomes ×7.

**Lead app (ratified 2026-07-29).** `fauna-tui` is the **default app of the rust-first development workflow**: the default e2e app on every machine, and the first app every new UI feature lands on — the other six follow in batched per-app trickle-down passes. Flow, defaults, and carve-outs are owned by [`../testing.md`](../testing.md) § Default app and nest mode (journeys needing a § Declared platform absences capability lead on web instead). Practical consequence for tui sessions: the ui.yaml-completeness backlog (`ui-actual-tui.yaml` `missing_pages` + per-page `missing_from_client`, tracked internally) is now the fleet's critical path — closing it is what makes the e2e defaults flip safe.

## Cross-platform: one app, three desktop OSes

**`fauna-tui` is cross-platform: it is built and tested on Linux, macOS and Windows alike.** It is not a Linux app. Nothing in the stack is Linux-specific — ratatui + crossterm abstract the terminal on all three (crossterm drives the Windows console API as well as ANSI/VT), tokio and the `fauna-*` crates are already tri-platform (the same crates back `fauna-desktop`, `fauna-windows` and `FaunaKit`), and there is no GUI toolkit to port. This is the payoff of the no-FFI, no-toolkit design: the *one* binary runs everywhere its dependencies do.

Consequences a session must respect:

- **Development is not pinned to one platform.** The app is built and tested from a Linux, macOS or Windows development machine alike. Linux is merely the *primary* one, because the nest and the cross-app e2e harness are most convenient there — not because the app is Linux-only.
- **Platform divergence is confined to OS integration, never to pages or paint.** The five genuinely OS-specific seams are: the credential store (secret-service on Linux, Keychain on macOS, DPAPI/Credential Manager on Windows — contract owner `common.md` § Credential storage, with the headless passphrase fallback below), desktop notifications, the external-media default-handler call (`xdg-open` / `open` / `start`), how the local sync agent is started and reached (systemd user unit over a unix socket vs. a detached child over the per-SID named pipe — owner [`sync-agent.md`](sync-agent.md) § Packaging + lifecycle), and **how the graphics probe hands the terminal a byte and reads one back** (a `/dev/tty` descriptor vs. the console API's `CONIN$`/`CONOUT$` — § Rendering). Note what the fifth one is *not*: the query, the reply format, the parse and the protocol decision are one shared implementation, and only the transport under them has two bodies. Everything else — every page, every element ID, the render walker, the element/focus/registry model — is identical on all three by construction.
- **Sync is at parity on all three since 2026-07-24.** The sync-agent surface below (§ Sync-agent control surface) was unix-only for its first year of life, not by design but because the shared control client was; the shared client went cross-platform on 2026-07-24 (`sync-agent.md` § Implementation status today), so a Windows `fauna-tui` provisions, binds locations and reports agent health exactly as the Linux and macOS ones do. The one deliberate remainder is the `loginctl enable-linger` offer, which has no Windows meaning (§ Declared platform absences' reasoning: the Run key always has a logon session).
- **Parity is per-app, not per-OS.** `fauna-tui` is *one* app in the parity ledger (the 7th), not three. A page is done when it is done; it does not need a per-OS row.
- **The main-thread stack budget is equalized at link time, never left to the OS default.** Windows reserves **1 MiB** for the main thread against Linux/macOS's **8 MiB**, and a *debug* build's async state machines are far fatter than a release build's — rustc gives every await point across every match arm its own slot instead of overlapping them. Measured 2026-07-31 on Windows: one `nav` to Settings peaked at **837 KiB** of main stack (the same nav in release: **26 KiB**), which overflowed the 1 MiB reserve and killed the app with `STATUS_STACK_OVERFLOW` on **every** Settings sub-page, while no other top-level page came close. Two halves, and both must stay: `apps/fauna-tui/build.rs` links Windows binaries with `/STACK:8388608` so the three OSes agree on the budget, and `app::PageOp::run` **boxes** each nested `op.run()` future so a nav does not spend it needlessly (837 → 630 KiB, and the whole caller chain shrank with it). A new page's op is awaited as `Box::pin(op.run()).await`, never bare. Shipped **release** artifacts were never at risk; this is a debug/e2e-build concern, and the cliff is what made a generic bloat problem present as a Windows-only crash three frames from its symptom.

## Form factor and navigation

`fauna-tui` is a **desktop form factor** app: sidebar navigation with the standard `{page}-tab` IDs, pages mirroring ui.yaml one-to-one, every page carrying its `error-message` element. It is *not* a scriptable command-line tool (§ Non-goals). Navigation conventions: owner `../../ui/README.md` (ui-navigation).

## Key-hint footer

**A keyboard-only app must name its keys, because it cannot draw them.** The six pointer apps advertise an affordance by rendering a control the user can see and click; a terminal has no such channel, so an affordance nobody already knows about does not exist. This is the same asymmetry § Declared platform absences encodes, read in the other direction — and it is why the footer is a **tui-only element** (`nav-key-hints`, ui.yaml `global.platform_elements`, `tui: [nav-key-hints]`) rather than a shared one. User-approved 2026-08-02 under UI-consistency rule A, which gates a new persistent element and the layout change it implies.

*The evidence that opened it:* a live user pressed `←`, landed on the sidebar with the page unchanged, and asked "how do I get back to Settings?". The nav model was correct and the focus cue had just been strengthened; nothing on screen ever *named* a key.

- **One line, bottom of the authenticated shell, full width, dimmed.** Full width because it describes the shell's keys rather than one pane's, and the 24-column sidebar would wrap it. The split happens *before* the sidebar/page split, so both panes shorten by one row instead of the footer overpainting content; `Min(1)` on the body keeps content ahead of the hint on a terminal too short for both.
- **Every hint names a binding that would fire on the CURRENT focus.** This is the contract, not a nicety. `q` quits only while no text input holds the ring — with one focused the same key types a literal `q` — so the quit hint is **absent** while typing, and Enter reads *open* over a control but *next* over an input. A fixed hint string would be false exactly when the user is most likely to test it. Both arms read `App::focused_input`, the same predicate the key handler branches on, so the footer cannot drift from the keymap.
- **Absent wherever the shell is not on screen.** The gate is `authenticated() && !showing_launch_surface()`, the same one the rest of the shell chrome uses — *not* `authenticated()` alone, which looks right and is wrong: the append-mode "Add account" wizard runs over a live session, where `App::screen_elements` deliberately emits no sidebar, so a pane hint there would name a gesture with no second pane. Paint and registry read the one predicate, so a hint is never registered without pixels behind it.
- **Chrome, never a control.** Registered as text with no `Role`, so the focus ring cannot walk onto the row explaining what the focus keys do.
- **It advertises only keys that exist.** There is deliberately no `? help` hint: tui binds no `?` today, and a footer naming a dead key is worse than no footer. `Esc` is likewise omitted — its meaning is contextual across nine separate arms (lightbox, compose dialog, feed/conversations/contacts sub-pages, settings sub-page, re-auth prompt, folder wizard), and a hint mirroring them would be the hand-written second table that drifts. Both are reconsiderable; neither is a silent omission.

## Sidebar quit row

**A terminal app has no window chrome to close.** The six GUI/mobile apps all
have an OS-native way to end the session — a titlebar close button, Cmd+Q,
Alt+F4, or simply backgrounding — none of which exist for a process attached
to a tty. tui's only other way out is `q` (unless a text input holds focus)
or Ctrl+C (`App::handle_key`), both keyboard-only and, per the same
discoverability lesson § Key-hint footer above already learned, not
something a user finds unaided — this one from a live report on 2026-08-03.

`exit-tab` (ui.yaml `global.platform_elements`, `tui: [exit-tab]`) is a real
sidebar row, always last — below `admin-tab`/`family-tab` when either is
gated in — built on `Page::Exit`, the one variant deliberately kept out of
`Page::ALL` (`pages.rs`). Two design points fall out of reusing the existing
row machinery rather than inventing a parallel one:

- **The ring can rest on it like any other row.** tui's sidebar selection
  *is* `App::page` (no second cursor — `App::focus_next`'s doc comment), so
  arrow-key arrival on Exit paints it highlighted over an empty body, same as
  any page still building out. Nothing quits yet.
- **Only actuation quits — Enter, a click, or the e2e agent's
  `/element/click`, no confirm dialog.** All three actuation surfaces
  (keyboard `spawn_gesture`, mouse `click_sidebar`, the e2e agent's
  `run_gesture`) already fold through `App::gesture_work` — the one door
  `../e2e-conventions.md` point 11 exists to enforce — so the `Gesture::Nav(Page::Exit)`
  arm there is the single place that intercepts it and sets `should_quit`
  directly instead of applying a nav. One door, one intercept, no
  actuation-path-specific copy to drift.

User-approved 2026-08-03 under UI-consistency rule A (a new persistent
element). tui-only by the same asymmetry the key-hint footer encodes: the
other 6 apps have their own OS-native quit path and gain nothing from an
in-app duplicate.

## Architecture: monolithic Rust TUI binary

- **UI:** ratatui + crossterm; full-screen alternate-buffer TUI; keyboard-first with mouse support where the terminal offers it.
- **Async backend:** tokio multi-threaded runtime, same as Linux.
- **In-process everything:** `NestClient` and the `fauna-client-*` feature crates as direct Cargo dependencies (the same dependency shape as `linux.md` § Architecture — the second direct-Rust app, no FFI seam at all). WS-RPC binding per `common.md` § WS-RPC client binding.
- **Event loop:** a single loop selecting over terminal input events and the backend's `UiMessage` mpsc channel — the message taxonomy Linux uses (`linux.md` § Message Flow). *(Assessed 2026-07-16: the enum itself does **not** lift to shared Rust — both apps' `DataMessage` payloads are deliberately app-shaped (linux carries GTK/db row types, tui carries page `Outcome` types), so only the outer taxonomy is common, and that is a convention, not code. The priority-#2 surface between the two Rust-native apps is the shared managers, projections and serializers, which is where the lifts have in fact landed. Because it is a convention rather than a contract, tui's copy need not carry variants it has no payload for: its `Action`/`Realtime` variants were placeholders that nothing constructed across five milestones and were dropped with the 2026-07-16 consolidation, leaving `Data`/`Noop`.)*

### The page-module contract

Every authenticated page is one module implementing the same shape (established M3–M5; normative for every new page):

- A `State` struct hanging off `App` — session-scoped (rebuilt at login, dropped at sign-out) unless genuinely client-local (the settings prefs).
- An `Action` enum (the page's gestures), dispatched as `Gesture::<Page>(Action)` through the one gesture door.
- `apply_local(&mut App, Action) -> Option<Op>` — the synchronous local half; the returned `Op` is the network half and owns only `Arc`s so it crosses a `tokio::spawn`.
- `Op::run() -> Outcome` and `apply_outcome(&mut App, Outcome)` — the fold back onto page state.
- `field` / `set_field` for editable buffers, `elements(&App) -> Vec<Element>` (the one list paint, the automation registry and the focus ring consume), and `state_json` serving the page's declared ui.yaml `state_fields`.
- **A page's error must reach the ONE error funnel — never a page-pushed `error-message` element.** `App::error_line_text` is the single producer of that id: the paint, the automation registry and the state protocol's `messages.error` all read it, which is what stops them disagreeing. A page that instead pushes its own `Element::label("error-message", …)` from its `elements()` looks correct to a human *and* to `is_visible`, but is **unreadable by the cross-app `error_text()`** — that helper prefers `messages.error` and falls back to the element only when the key is **absent**, and tui always emits the key, so a null there resolves to `""` and the fallback can never run. The error is then silently invisible to every test that asks for it: the dropped-error-surface shape of [`../e2e-conventions.md`](../e2e-conventions.md) point 2, wearing a costume. So a page routes its error either by folding it into `App::errors` (the shared-manager case, next bullet) or — when the error is derived from a held snapshot with its own precedence — by exposing a pure `page_error` that `App::page_snapshot_error` reads. A page wanting a genuinely page-scoped second error surface gives it its own id (the `admin-aliases-action-error` discipline), never this one. Pinned by `App::tests::no_page_pushes_an_error_message_element_of_its_own`, which visits every page **and every sub-page**.
- **A page backed by a shared manager must bridge the manager's error onto `error-message`.** The `error-message` element is registered globally off `App::errors`, but a shared manager (`FeedManager`, `MediaMachine`, …) owns its own page error and reports it on its *snapshot* — so the two are different places, and a gesture that fails **inside shared Rust** surfaces nothing unless the fold copies it across. That is the dropped-command shape ([`../e2e-conventions.md`](../e2e-conventions.md) point 11) wearing a costume: no error *and* no effect, indistinguishable from a real product bug. Sync on both edges the manager can change it — the fold of any manager-driven `Outcome`, and the observer tick (Media's `sync_page_error` is the reference). A app-glue error (a file the app itself could not read) is written to `App::errors` directly, and the manager's error takes precedence on the next tick.
- **Actuation duality:** the e2e agent path **awaits** the `Op` and folds its `Outcome` before the single-shot HTTP reply; the keyboard path **spawns** it and the `Outcome` rides the `UiMessage` channel. One `apply_local` serves both paths.
- **Nav-edge fetches return an `Op` the agent's nav handler awaits** (the one `on_nav_enter` hook, which `App::apply` returns and the agent's nav runs) — never a fire-and-forget spawn, which can race a same-visit mutation and clobber it with a stale snapshot (the events-slice lesson; the Privacy sub-page's `Op::FetchPrivacy` was the proven shape the hook generalizes).

Two rules make the contract enforceable by the compiler rather than by review (implemented 2026-07-16 — see § Implementation status):

- **Field ownership is carried on the `Field` type itself, exhaustively.** `Field` nests a page-owned field enum per page (`Field::Feed(FeedField)`, …), exactly as `Gesture` nests per-page `Action` enums, and every match on it — `App::field`/`set_field` and each page's own — is exhaustive with no fallback arm. Adding an editable field without declaring its owning page **fails to compile**; it can never silently route to a fallback owner.
- **Gesture dispatch is one generic door parameterized on await-vs-spawn**, not hand-written per-page arms repeated across the keyboard and agent paths. The door applies a gesture's local half and returns only the work still to run, so the *caller* chooses how to run it; the nav edge uses the same shape. A gesture that reaches no dispatch must be a compile error, never a green ack (`../e2e-conventions.md` point 11).

## Rendering

- **Bodies:** a terminal walker paints `RenderDocument` blocks/spans into ratatui text — app glue per `../render-model.md`; no body parsing or render state in the app.
- **Images:** inline via terminal graphics protocols (kitty, iTerm2, sixel), with a half-block cell fallback on terminals without one. Protocol choice is **auto-detected, never configured** (bucket 1 of the configuration invariant — no human chooses it). Three rules make that work:
  - **Ask the terminal, don't guess from the environment.** The primary-device-attributes query (`ESC [ c`; a sixel-capable terminal reports attribute `4`) is what actually answers *"can this terminal paint a sixel"* — `TERM` answers *"what termcap applies"*, a different and unreliable question. Env signals are consulted only where they are definitive (`KITTY_WINDOW_ID`, `TERM_PROGRAM=iTerm.app`), and only to *skip* a probe whose answer could not change the outcome. The probe runs once, at startup, and must run **after raw mode is on and before the event stream reads stdin** — crossterm parses the reply into an internal event that never surfaces, so a probe racing the event loop has its answer silently eaten and every terminal on earth reads as incapable.
  - **The question is one implementation; only the transport has two bodies.** Unix hands the query to a `/dev/tty` descriptor and reads the reply as a byte stream. Windows has no such descriptor: the query goes to `CONOUT$`, the reply comes back off `CONIN$` as *console key events* — one per character, each with its key-up twin — and is reassembled into the same bytes before the same parser reads it. Two Windows-specific rules fall out. **Key-up records must be dropped**: keeping them doubles every character, turning `ESC [ ? …` into `ESC ESC [ [ ? ? …`, which contains no reply at all — so the failure is not a mis-read but a silent "no terminal on Windows supports anything". And **the probe must not ask a console that would print the question**: without `ENABLE_VIRTUAL_TERMINAL_PROCESSING` on the output handle the console renders `ESC [ c` as three glyphs on the user's screen and no reply is coming, so the probe checks for it and declines rather than corrupting the display — every *other* failure in this path costs only the half-block fallback, which is why this one alone is guarded. Note what is deliberately **not** here: the probe sets no console mode of its own. `ENABLE_VIRTUAL_TERMINAL_INPUT` looks required and is not — a console delivers a device-attributes reply as key events either way (measured by mutation against the tier_3 e2e, 2026-08-01), and setting it would both surprise crossterm's event stream and leave the mode flipped if anything between set and restore panicked.
  - **A multiplexer offers sixel or nothing.** Inside tmux/screen, kitty and iTerm2 escapes are stripped unless passthrough is enabled — and asking a user to enable it is not a configuration surface fauna has. tmux 3.4+ parses sixel natively, so sixel is the one arm that survives; and since the outer terminal is not discoverable from inside a multiplexer, the relayed DA1 reply is the *only* signal that can decide it. This is the case that makes the query load-bearing rather than merely tidy.
  - **Images are a post-paint pass, never the `Line` model.** A protocol image is an escape sequence addressed to a cell rect, which a scrolled `Paragraph` cannot carry. So the element list stays the registry, the half-block art stays painted underneath as the fallback, and protocol graphics overlay it after the frame is drawn — writing straight to stdout, which ratatui does not own. This is the one place the app's "everything is a text line" model legitimately breaks, and it breaks in exactly one seam. The art staying underneath is not redundancy: it is the fallback if the terminal overstated itself, the **eraser** for the protocols that composite into the text grid (sixel, iTerm2 — a repaint of the cells removes them; kitty keeps its own layer and must be deleted by id), and the app's e2e paint observable (§ Implementation status).
- **Control characters are stripped at the paint funnel, never at the sources.** Every line tui paints is passed through `fauna_core::control_chars::strip_control_chars` — the project's one strip implementation, shared with the log plane (`observability.md` § Ring-ingest sanitization) — inside `ui.rs`'s `element_lines` and at every widget boundary in that module. **Rationale:** a terminal treats a control character as an *instruction*, and ratatui preserves ESC/BEL verbatim into the cell grid (probed 2026-07-29), so content that reaches the grid unstripped can clear the reader's screen, set the window title, or forge row structure. Practically all painted content is remote-authored — a post body, a remote-chosen display name, and third-party OpenGraph `og:title`/`og:description`, which needs **no Fauna account at all** (the nest's link-preview parser applies only `str::trim` and a char-count cap). **The gate is at the sink on purpose:** the source list is open-ended (the og class was found one commit after the first two were), one funnel covers every present and future source structurally, and it costs nothing legitimate because styling is applied by the renderer and never by content bytes. A per-source filter is the shape to refuse. Newlines are consumed as row *structure* by the `'\n'` split that precedes the strip, so a surviving newline could only forge that structure. **This is terminal-specific — the GTK/HTML/SwiftUI/Compose surfaces do not interpret these bytes**, so it is a tui rule rather than a cross-app one; `render-model.md` § Where logic lives already assigns painting wholly to app glue.
- **A page whose LAYOUT is load-bearing asserts the paint, not only the registry.** The element list is both the registry and the paint source, and the two are *different consumers* of it — so anything registered answers `is_visible`/`click`/`get_text` correctly whether or not a pixel of it painted where a human could see it. That inverse is a structural blind spot, and it is not hypothetical: the month grid shipped painting all 42 day cells on ONE clipped line while every id assertion passed, and the identity-export QR once painted as a single unscannable strip. **No e2e test on any app can catch this class — no driver reads pixels** — so the obligation sits in tui's own unit tests. The rule: a surface that arranges elements in rows/columns/tables (`Element::inline` / `starts_row`), or whose body is a matrix in one element's text or `Element::art` (a QR, a thumbnail), carries at least one assertion through the `crate::ui::painted_line_texts` seam pinning its painted *shape* — how many lines, which cells share a line, where the column bands fall — alongside its id assertions. A grid whose header is painted by a *different* element than its cells shares one width constant between them, since nothing else relates the two.
- **Control vocabulary (ratified 2026-08-03 — the paint answer to "is this a button, a checkbox, a dropdown?").** A terminal has no widget chrome, so control KIND and current STATE must be legible from the painted text itself; a live user reported both as "completely unclear / unknowable". One idiom per kind, total over `element.rs::Role` — a new role variant must extend this table in the same change:

  | Kind (`Role`) | Paints as | State it shows |
  |---|---|---|
  | `Label` | `text` (or `prompt: value`) | — |
  | `Button` | `[ text ]` | one-shot action; disabled = DIM |
  | `Button` + `.nav()` | `text ▸` | a **destination**, not an action — activation lands you on another surface |
  | `Button` + `.nav_back()` | `◂ text` | the surface's **way out** — activation returns you where you came from (a sub-page's Back, an area's Exit) |
  | `Checkbox` | `[x] text` / `[ ] text` | independent on/off |
  | `Radio` | `(*) text` / `( ) text` | **which of a one-of-N group is current** |
  | `Select` | `prompt: < value >` | the current value, ALWAYS visible (`display` slot carries the human form of a raw wire value; `label` is the prompt on every role uniformly) |
  | `Input` / `InputCommit` | `prompt: value_` | the caret marks "typing happens here"; every input MUST carry a label — an unlabelled one prompts with its raw element id, and walk invariant I3 fails the suite on the class |
  | `Button` + `.cell()` | `text` raw | a fixed-width **canvas cell** of a grid, not a control — the month day cells, the week/day time slots |
  | (chrome) | bare text | un-id'd explainer/hint lines (`Element::chrome`) |

  Five rules ride the table: **(1)** a mutually-exclusive group is `Radio`, never a stack of checkboxes (reads as independent toggles) or plain buttons (shows no selection at all) — each option mirrors its selection in a `state` attr for drivers. **A group that marks NONE is the same copy bug as a disabled control with no reason** (rule 3, read across from controls to state): N identical `( )` rows answer nothing, so the surface owes the reason on its `error-message` — "your current inbox mode has not loaded" — and never a *guessed* default, which would state a policy the account may not hold. Both halves are dynamically enforced by walk invariant I5 (two marked is always a bug; zero marked requires a stated reason), which found the Privacy page's four unmarked inbox-mode rows on its first run: the fetch failure behind them had been dying in a `tracing::warn!`. **(2)** `REVERSED` stays the focus affordance exclusively — selection is a marker, never reverse video (the field-report collision class); **(3)** disabled-with-no-reason is a copy bug — pair every user-reachable disabled control with a visible explainer line (`../../ui/README.md` § Copy comprehensibility rule 5, the cross-app owner of that requirement); **(4)** **brackets promise "acts now", so a destination must not wear them** — every control whose activation lands the user on another surface is `.nav()` (a settings/admin rail row, an in-page link to a sibling page), and a control that acts on the *current* page is not, however much the screen then changes. The ▸ promises **another surface of this app**, so a handoff that leaves it entirely — `subscription-offer-payment-link` / `gated-post-payment-link` (spawn the browser at an external checkout), the external-media open — keeps the brackets: it is a one-shot act with a consequence outside fauna, and reading it as "just another page over here" would understate it. **(5)** **a way OUT points the other way (ratified 2026-08-03).** Rule 4 takes the brackets off every destination, and `settings-nav-back` / `admin-nav-back` plainly are destinations — but `Back ▸` would drop the brackets correctly and then promise *onward*, which is worse than the `[ Back ]` it replaced. The arrow carries two promises, "another surface" and "which way", and only the first is shared: a back affordance takes the **mirrored glyph, leading** — `◂ Back`, `◂ Exit` — which is also the idiom every other app already ships for the same control (priority #3). `Element::nav_back()` sets `nav` too (a way out is still a destination), the way `starts_row` sets `inline`; the paint arm for it must precede the forward one. The boundary against rule 4's own carve-outs: **Cancel keeps its brackets** — abandoning a wizard step acts on the *current* surface — and so does anything leaving fauna entirely. Enforcement is dynamic, not per-page: walk invariant I4 fails the suite on any `*-nav-back` element that is not `nav_back`, so the sub-pages still being added inherit the rule instead of each being audited.

  **The vocabulary is one function, and a row is only geometry (ratified 2026-08-03).** `ui.rs::control_text` is the table's sole implementation, shared by both painting paths — an element on its own line and an element as a cell in an inline row — because an idiom belongs to the *control*, not to where it sits. The inline path used to keep a partial copy that dropped `Role::Button`'s brackets for everything in a row; the grids that motivated it do need raw text (a day cell is `label(..).clickable(..)`, and `clickable` makes it a `Role::Button` whose body is nonetheless canvas), but the blanket rule also silently caught the genuine inline *controls* — `calendar-item` and the agenda RSVP row — which painted as bare text and so read as labels. **So canvas is the marked case (`.cell()`) and everything else inherits the vocabulary**, because the two failure directions are not symmetric: a control painted bare fails silently, while a canvas cell painted as a control moves its column alignment and reds the paint assertion its grid is already required to carry. The first consumer of the corrected default is the Events **pan row**, which now paints `[ < ] August 2026 [ > ]` on one line — grouped, because adjacency is the only channel a terminal has for relatedness, and *bracketed*, because the bare `< August 2026 >` an unmarked inline run would produce is the `Select` idiom for a different control.

  **Why nav is a flag and not a `Role` (ratified 2026-08-03).** The table is one idiom per control KIND, and nav is not a kind — a rail row and a Copy button are the same widget with the same gesture, focus and registry behavior. What differs is only the promise the paint makes, so `Element::nav()` is paint-only (`element.rs`), the `inline`/`starts_row` builder-flag shape; making it a `Role` would fork every match arm that treats a button as a button for a purely visual difference. The finding it closes: the Settings rail painted `[ Copy ]` (copies the actor id *now*) and `[ Account ]` (goes to the Account page) identically, two rows apart — a live user reading the rail asked which rows were "navigational?" and the screen had no answer. Pinned by `settings/root.rs`'s rail tests (every untagged rail row is a destination; `account-actor-id-copy-btn` is not) and `ui.rs`'s paint tests.

  **The constrained-channel principle (user-stated, 2026-08-03).** The other six apps express *relatedness* through layout (a field and its button share a card), *importance* through visual hierarchy, and *state* through color — channels a terminal UI mostly lacks (DIM exists for disabled but is subtle terminal-to-terminal, which is why rule 3 backs it with text; color support varies and is never load-bearing). tui expresses the same three things structurally and textually instead: **relatedness** by adjacency and indentation (a hint line sits directly under the control it explains; a commit button directly after its field) and by copy that names its object (the button says what it commits, the prompt names the field); **importance** by ordering (the thing that matters most paints first) and sparing text markers, never by color alone; **state** by the marker vocabulary in the table above. When a screen feels illegible here but fine on the other apps, the missing layout/color channel is usually what it was leaning on — port the *information*, not the visual trick.
- **Source badges, i18n, value formatting:** same shared surfaces as every app (owners: `../../ui/feed.md`, `../i18n-platform-sections.md`, `../../behavior/value-formatting.md`).

## External media handoff (audio/video) — opt-in

Inline video/audio playback is a declared platform absence (§ below). Playback delegates to the **OS default-handler mechanism** (`xdg-open` on Linux, `open` on macOS) — the OS already owns "which program plays video", so fauna adds no program-picker knob.

Whether handoff happens at all is a **user choice → app UI** (configuration invariant): a TUI-specific setting `external-media` with values **ask (default) / always / never**. *Ask* prompts inline before launching anything; *never* shows metadata only. Surface: a `tui-settings` page mirroring the `web-settings` per-app-page precedent — ui.yaml page `tui-settings` (`platforms: [tui]`) with the `tui-settings-external-media` select (ID family user-approved 2026-07-09; renamed from `cli-settings` with the 2026-07-12 rename). The handler call is the one place this setting is OS-divergent: `xdg-open` (Linux), `open` (macOS), `start` (Windows).

**Persistence is client-local** (resolved 2026-07-15). The choice rests in `$XDG_CONFIG_HOME/fauna-tui/prefs.json`, written by the UI and never hand-edited — **not** in the synced account state (the account-state plane). The configuration invariant's "user choice → nest state" line addresses account/feature choices that every app shares; `external-media` is instead a **tui-client-*type*-specific rendering preference** — no other app has an inline-AV absence, so no other app renders the setting (`platforms: [tui]`), and it cannot take bucket-2's "all-6-app UI + nest state" shape. Its closest precedent is this app's own client-local credential store (§ Credential storage — per-device, UI-driven, in the same config dir), and it carries no wire/at-rest commitment, so it can move into an account-state plane kind later if it should ever sync across a user's devices. This is not config-file *theatre*: the UI (the select) is the surface, and `prefs.json` is only its store — no human edits it to change behavior.

**Implementation status: BUILT end-to-end (M6 slice 3b, 2026-07-16).** The setting, its client-local `prefs.json` persistence, and the handler seam — the mode gate (`ask`→prompt / `always`→launch / `never`→suppress) and the OS-divergent spawn (`xdg-open`/`open`/`start`, with a `FAUNA_TUI_MEDIA_OPENER` test-injection point) — landed M5 (`apps/fauna-tui/src/settings/tui_settings.rs` § *External-media handoff seam*, 2026-07-15). The four trigger/confirm IDs (`media-external-open-{button,confirm-modal,confirm-button,cancel-button}`, `platform_elements: [tui]` on the `media` page, user-approved 2026-07-16) are **implemented**: the trigger paints on `media-item-detail` only for an audio/video item (the shared `fauna_core::share::is_audio_video_filename`, derived from the single-source `content_type_for_filename` map) and only under ask|always (under `never` it is absent entirely, never painted-but-inert) and only once version rows are loaded; `ask` arms the inline confirm; confirm/`always` run the shared `MediaMachine::download_file` query (two-provenance — see the corrected bullet below), materialize per the ratified hardened-temp-file shape (`apps/fauna-tui/src/media_handoff.rs`), and hand the path to `spawn_external_handler`; cancel is a pure no-op. Proven by unit tests on every mode/predicate branch and by the tier_3 e2e `test_tui_media_external_open.py`, whose ask→confirm journey asserts the handed-off file's **bytes equal the uploaded plaintext** plus the `0600` mode, real extension, and runtime-dir location. The paragraphs below record the traced shape and its one landed correction, for the next reader:

**⚠ The pre-build framing "wire the built seam to a call site" was wrong (corrected 2026-07-16).** `spawn_external_handler` takes a **url**, and nothing on the Media page could produce one: `MediaItemSummary` carries **no** content hash for the file, only `thumbnail_hash` (`libs/fauna-media-machine/src/snapshots.rs` § `MediaItemSummary`), and `MediaMachine` offered no full-file fetch — only `fetch_thumbnail`. No app had a media download before this slice (tui's is the first), so the trigger needed a **plaintext-bytes path** first, and it is a shared-Rust motion (priority #2), not tui glue:

- **The walk already exists and must be reused, not rebuilt:** `fauna_core::file_download::download_file_bytes_by_manifest(fetcher, keys, manifest_hash, content_key_version, relative_path)` — "the **one** implementation of the walk every app runs" (owner: `../../behavior/backup-restore.md` § 3 + `../../ui/backups.md` § Where logic lives → *Single-file byte download*, re-ratified 2026-07-14). Keys come from `FileDownloadKeys::owner(backup_key)`, which tui already holds. **Corrected 2026-07-16 while building: the recorded hash has TWO provenances, so the walk alone cannot serve the detail surface.** The sync-change record's `manifest_hash` field names whichever store the producer used: a **Media-page upload** rests as *one sealed blob-store primary* (`MediaMachine::do_upload` records `POST /api/v1/blob`'s reply hash), while a **sync-engine upload** rests as *sealed chunks behind a chunk-store manifest*. The shared query (`MediaMachine::download_file`) therefore tries the blob primary first — its miss is a **typed** `NotFound` (the stores are disjoint), and its resolve is byte-for-byte `fetch_thumbnail`'s proven posture (fetch by hash → content-address verify → owner-key decrypt) applied to the primary — and walks the chunk store on the miss. A verify/decrypt failure on either arm is a real error and never falls through.
- **The manifest hash is already on the detail surface** — each `file-version-item` row carries `manifest_hash` (`snapshots.rs` § `FileVersionSummary`); the latest version is the current file. This is *why* the trigger belongs on `media-item-detail` rather than on `media-item`.
- **The one missing piece was the fetcher — landed 2026-07-16.** `file_download::BlobFetcher` (`/api/v1/manifests/{hash}` + batched `/api/v1/chunks/{hash}`) was implemented natively only by `fauna-sync-engine`'s `EngineBlobFetcher`, which needs a `SyncEngine` + its `rusqlite` `SyncDb`; **tui runs no sync engine and has no local folder root**, so it could not reuse that arm. `fauna-media-machine` grew its own native + wasm impls to fill the gap (`src/download_fetcher.rs`, since deduped away — next bullet), injected by both `build_media_machine`s, exposed as the `MediaMachine::download_file` query so every app inherits the capability that `../../ui/media.md` § User actions already lists as the detail surface's remit ("per-item detail / **download**").
- **Deduped 2026-07-18 (priority #2 — five near-identical impls collapsed to two).** `fauna-media-machine`'s native + wasm `download_fetcher.rs` impls were byte-for-byte duplicates of `fauna-client`'s `NestPublicChunkFetcher` (native, predating media's copy) and `fauna-wasm`'s two wasm impls (`WasmSnapshotBlobFetcher`, `WasmMailBodyFetcher`). One binding per target now: native `fauna_client::NestPublicChunkFetcher`; wasm `fauna_core::file_download::WasmPublicChunkFetcher` (feature `blob-fetch-wasm`) — `fauna-core` is the wasm-reachable neutral home neither `fauna-client` (native-only) nor either wasm crate alone could be. `fauna-media-machine/src/download_fetcher.rs` is deleted; `nest_api::ws_rpc::build_media_machine` constructs the two neutral-home types directly.
- **Then, and only then, materialization — the hardened temp file (ratified 2026-07-16; loopback streaming REJECTED).** The bytes must reach a program that cannot decrypt: they land in a temp file which the handler opens. Note `download_file_bytes_by_manifest` reassembles the **whole file in memory** by design ("callers chunk the transfer themselves") — acceptable for a first cut; a large video wants the streaming composition (`fetch_manifest` + `fetch_decoded_chunks`, public for exactly this reason) as a follow-on, not a blocker.

**Why a file and not a loopback stream** (the security-boundary design pass, 2026-07-16):

1. **The ratified mechanism above only works on a file path.** The OS default-handler resolves a *file* by content type; handed a URL, `xdg-open`/`open`/`start` resolve the URL-***scheme*** handler — the web browser, never the media player. Making a loopback stream reach a player would force this app to pick the player itself, which is exactly the program-picker knob this section bans (configuration invariant, bucket 1). Loopback is incompatible with the mechanism, not merely costlier.
2. **On a multi-user box — the SSH-server case, this app's differentiating environment — the file is *stronger*, not weaker.** A `0600` file in a `0700` dir is filesystem-protected. A loopback URL must carry its access secret in the player's command line, which the process table exposes to **every local user** for the stream's whole life; TCP loopback has no peer-identity check, and media players don't open unix-socket URLs.
3. **Exposure class is set by the handoff itself, not the transport.** The user consents per-action (*ask* is the default) to hand plaintext to an external program that will itself buffer, cache, and swap it. Transport choice changes the plaintext's duration and location, only. What the design owes is minimized persistence, access, and lifetime — below.
4. The project's no-plain-HTTP posture would need a new carve-out, plus Range/seek server complexity, to reach the weaker result.

**The ratified file shape:**

- **Location — the most private, most ephemeral per-user dir the platform offers.** Linux: `$XDG_RUNTIME_DIR/fauna-tui/media/` — tmpfs, per-user `0700`, cleared at logout, so the plaintext never touches persistent disk at all; fall back to a `0700` `fauna-tui-media-{uid}` dir under the system temp dir only when `XDG_RUNTIME_DIR` is unset. macOS: the per-user Darwin temp dir (`std::env::temp_dir()`) + `fauna-tui/media/`. Windows: `%TEMP%\fauna-tui\media\` (per-user-profile ACL).
- **Permissions:** the dir is created `0700`; each file is created `0600` with create-new semantics (never reused, never truncating an attacker's pre-placed path).
- **Naming:** a random stem plus the item's **real extension** — extension is load-bearing, it is what the OS resolves the handler by.
- **Lifetime — bounded, crash-safe, event-driven.** The player's lifetime is unknowable (the opener detaches), so deletion hangs on events, not on player exit: the handoff dir is **swept at app start, app exit, sign-out, and factory reset**, and **each new handoff deletes prior handoff files first** (so at most one clip rests at a time). POSIX unlink-while-open is safe (the player keeps its fd); a Windows delete-while-open fails harmlessly and the next sweep collects it. A crash leaves files only until the next launch — and on Linux only in tmpfs, gone at logout/reboot regardless.

**Feed video — the same seam, RULED 2026-10-02 ([`../render-model.md`](../render-model.md) § D6c → *Inline playback* owns the cross-app ruling: the native player as app glue on six apps, the `video-thumbnail` element as the activation surface carrying `state` ∈ `idle`/`loading`/`playing`/`error`, never autoplay; this paragraph owns tui's leg; UNBUILT).** Activating a feed `video-thumbnail` (list card and post detail alike) runs this section's mode gate and materialization exactly as `media-external-open-button` does: `never` leaves the element an inert label (it is the block's only element, so it must still paint — inert, not absent, unlike the Media page's trigger); `ask` arms the inline confirm; `always` fetches at once. Three byte paths land in the hardened temp file above and go to `spawn_external_handler`: a `Video` on a public post is one unauthenticated `GET /api/v1/blob/<hash>` (signed plaintext — no manifest walk, no key); a `Video` on a gated post is the sealed blob opened through the same path the feed's sealed-image arm uses (`FeedManager::is_sealed_media`); a `ProxiedVideo` is a bearer `GET` of its proxied path (tui needs no playback ticket — it is not a `src=` fetch; the ticket exists for players that cannot carry a bearer). The handler is handed a FILE, never a URL (§ *Why a file and not a loopback stream*); whole-file in memory is the ratified first cut, as above; the file's extension comes from the block's media type. The element publishes `state` like every app's — `playing` once the handler is spawned, `error` on a failed fetch — so the tier_3 pin asserts the state and that the handed-off file's bytes equal the posted clip, the `0600` mode, the real extension and the runtime-dir location, exactly what `test_tui_media_external_open.py` already proves for the Media page. **The one open question is ui.yaml's, not this doc's:** the `ask` confirm reuses `media-external-open-{confirm-modal,confirm-button,cancel-button}`, whose `platform_elements: [tui]` scope is the `media` page only; extending it to `feed` is a per-page scope change under UI-consistency rule A and waits for the user's yes — an `always`-only build in the meantime would ship the default mode broken, so the leg is not built until it is answered.

## Credential storage

- **Desktop session:** the OS-native secure store, per § Cross-platform (contract owner: `common.md` § Credential storage — registry `credential-storage`, ratified 2026-07-10). On Linux, freedesktop secret-service, same as the Linux app (mechanics → `linux.md` § Credential Storage); on macOS, login-Keychain generic passwords, never `kSecAttrSynchronizable` (iCloud Keychain never sees them — `fauna-credential-store::mac_keychain`); on Windows, Credential Manager (`fauna-credential-store::win_credman`, landed 2026-07-19 — § Implementation status today for the verification leg). What the device's own backup carries on each arm, the sealed file included, is one cross-app rule: `common.md` § Credential storage → *What a device's own backup carries*.
- **Headless (no OS secret store reachable — the SSH/server case, this app's differentiating environment; it is the *absence of a desktop session*, not the OS, that selects this arm):** a passphrase-encrypted store file under the platform data dir, unlocked at launch. Format + selection ratified 2026-07-14 (resolving § Open decisions item 2):
  - **What is sealed:** the app's whole logical credential-namespace map (the same account→value map the shared `AccountRegistry` reads — identity secrets, `fauna/index`, the onboarding wizard's resume slots; never a bearer token, which no app persists — [`common.md`](common.md) § Credential storage) as **one** AEAD blob. This is a client-side wrap of the identity seed per `key-material-hierarchy.md` § Architectural rules #6 (the apps' own contract, **no new key category**); the versioned context string below satisfies rule #3.
  - **KDF:** Argon2id v1.3, the shared `fauna_core::kdf` parameter set (`Argon2idParams::interactive()`: m=64 MiB, t=2, p=1 — the same triple as the wrapped-blob PLAIN path, and the same DoS-bounds validation on read, so a tampered header is refused before argon2 allocates). Params + a 16-byte random salt are recorded in the file header, so a future cost tightening reads old files unchanged.
  - **AEAD:** ChaCha20-Poly1305, 12-byte random nonce per write, AAD = `"fauna.credential-store.v1\0" || namespace` (defeats cross-namespace file substitution). Wrong passphrase and tampered file are one indistinguishable AEAD failure; the error copy honestly names both. AEAD success **is** the passphrase check — no separate verifier rests in the file.
  - **File:** `{config_dir}/{namespace}.sealed` (`$XDG_CONFIG_HOME/fauna-tui/fauna-tui.sealed` by default), self-describing versioned header (magic `FAUNACREDSTORE\0`, version byte, KDF triple, salt, nonce, ciphertext+tag), 0600, written tmp+rename so a crash can never truncate the only copy of an identity. An unknown version byte refuses loudly as "written by a newer build" — never reinterpreted, never overwritten.
  - **A write never overwrites a map it could not read** (ratified 2026-08-31). Every mutation is a whole-map read-modify-write, and the re-seal needs only the process's **cached** key — it never consults the read — so a read falling back to "empty" for any reason other than *the file does not exist* renames a one-entry map over a namespace holding `legacy/secret`, `fauna/index` and every per-actor secret, with no second copy anywhere. Three arms reach that: a read error (EIO, EACCES), a parse failure (truncation, bad magic, a newer version byte), and an AEAD failure under the cached key (an external re-key). The read contract is therefore **split**: the infallible warn-to-empty read serves lookups alone, and every write path takes a fallible twin that yields empty only on "no file" and **refuses the write** otherwise — dropping one write is recoverable, destroying client-only-resident key material is not (`../../principles.md` § No user-data loss, iron-clad even under the alpha carve-out). The refusal also preserves the user's only *evidence*: growing a corrupt file back into a valid, unlockable, empty store converts a loud recoverable corruption into a silent unrecoverable loss. The re-key takes the namespace file lock across its read → re-seal → rename for the same reason mutations do — the in-process state mutex guards the *key*, not the file, and is invisible to the second `fauna-tui` process, which is the whole topology this arm lives in (two SSH sessions over one sealed namespace).
  - **Backend selection is auto-detected, never a knob** (configuration invariant, bucket 1): ① `FAUNA_E2E_CREDENTIAL_DIR` (e2e file backend, as ever) → ② an existing sealed file wins (data-present precedence: a box that was headless when the identity was stored never silently switches to an empty keyring and strands it) → ③ a live-probe of the OS secure store selects the desktop arm (Secret Service: connect + default collection + **unlocked**; macOS Keychain: default keychain present + **unlocked** + writable, via the purely observational `SecKeychainGetStatus` — no dialog can appear) → ④ otherwise the sealed arm. `FAUNA_E2E_FORCE_HEADLESS_STORE` is a test-only carve-out forcing ④ on a desktop dev box. Implementation: `fauna-credential-store::CredentialStore::new_with_headless_fallback` + modules `sealed` and `mac_keychain`.
  - **Unlock UX:** the `tui-unlock` ui.yaml page (user-approved 2026-07-14) owns the screen **before** launch routing — `launch::start` reads the long-term store, so nothing may run until the store serves reads. Existing file → unlock mode (one masked input; wrong passphrase paints `error-message` and stays); first headless run → create mode (passphrase + confirm), deliberately **before onboarding**, because mid-wizard exits (a pending invite, a deferred-DNS claim code) persist durable secrets. The inputs register a same-length bullet mask — the passphrase value never enters the automation registry or `/app/state`. A factory reset deletes the file **and relocks** (the next onboarding re-chooses its passphrase). Secrets follow the `SecretBytes`/`Zeroizing` convention (derived key, plaintext map buffers). **User-approved 2026-08-05: a change-passphrase (re-seal-under-a-new-passphrase) affordance SHOULD exist** — today's only path is factory reset (destroy + re-onboard), a real gap for the SSH/server admin this app targets. Framed as a **shared "credential store settings" concept** the other apps may later fill differently, not declared tui-only (though today it is structurally reachable only here — the sealed arm is selected by the absence of a desktop session). The re-key flow must **surface a "back up your recovery seed first" nudge**, since the sealed file has no verifier/escrow (AEAD success *is* the passphrase check) and a forgotten new passphrase after a re-key is a self-inflicted version of today's already-unrecoverable case. **Design ratified 2026-08-06 (ID family user-approved the same day):**
    - **Primitive:** `SealedFileStore::change_passphrase(current, new)` in `fauna-credential-store::sealed`. It verifies `current` against **the file itself** — parse the header, derive under the header's own salt+params, AEAD-open; the open *is* the check, deliberately independent of the process's cached key, so a file some other actor re-keyed is never clobbered on the strength of a stale cache. It then re-seals the **same decrypted map** under a fresh 16-byte salt, the **current** `Argon2idParams::interactive()` triple (a re-key is the one moment a future cost tightening propagates into old files), and a fresh nonce — AAD unchanged (`"fauna.credential-store.v1\0" || namespace`: same purpose, same context string, per `key-material-hierarchy.md` rule #3; no new key category, per rule #6). Written 0600 via tmp+rename; on success the process's cached key/salt/params swap to the new derivation, so the running session keeps serving reads and writes uninterrupted.
    - **Crash-safety (the client-state-recoverability shape, applied at rest):** the rename is the **single atomic decision point**. At every crash instant the file is wholly-old or wholly-new — never truncated, never mixed — so exactly **one** of the two passphrases opens it, and the ordinary `tui-unlock` surface recovers either outcome with no special handling, no journal, and no representable half-state.
    - **Surface:** the shared credential-store settings section — render home [`../../ui/settings.md`](../../ui/settings.md) § Credential store (section after Recovery kit; `credential-store-*` ID family). The modal's three inputs follow the `tui-unlock` masking contract (registered text is a same-length bullet mask; raw values only in local buffers, never in `/app/state`); the submit is **synchronous** on both actuation paths for the unlock-submit reason (two Argon2id derives ≈ 200 ms, under the driver's single-shot-read budget). Validation mirrors create: empty entries refused, new/confirm mismatch refused, wrong current answers the honest wrong-or-corrupt copy — all on the page's `error-message`, modal kept open; success disarms the modal, zeroes the buffers, and paints `credential-store-rekey-success`. Rendered **only while the sealed arm is active** — the OS-store arms have no passphrase to change.

Consequences: the "macOS GUI login session gets the desktop arm" sentence above is true of the *selection* and false of the *outcome* — the desktop arm is selected, reports success, shows nothing, and so never degrades to the escape; and the sync agent's macOS sink ([`common.md`](common.md) § Push Notifications → *Transports*) cannot be built on this crate. Both await the user's decision on the macOS path; until then the code is unchanged. Two measured properties a future change should know: the first `show()` blocks the UI tick for ~0.3 s (the dispatch is synchronous, because the degrade-to-escape needs the result), and **tui over SSH on macOS is unmeasured** — whether an SSH session sees the console user's login keychain as unlocked, and so picks the desktop arm like windows does, has not been observed. **Windows — measured 2026-09-28:** the arm compiles and the `os_notify` unit tests pass on Windows (16/16, including `windows_always_selects_the_desktop_arm`), and the message-banner journey (`test_conversations_message_banner.py --app tui`) is green there too — closing the win half of the "mac and win" compile claim above. Since the Credential Manager probe is constant `true`, the unpackaged `fauna-tui.exe` always takes the desktop arm; whether the `tauri-winrt-notification` toast visibly renders is the same last inch no test reads (an unregistered AUMID can be refused by the platform, which `show()` would surface as `Err` and degrade silently to the escape — unmeasured here). **Known gap — Windows over SSH:** the Windows Credential Manager probe is constant `true` (no lock state, no session bus — § Credential storage status below), so on windows the desktop arm always wins, including a tui run over an SSH session where the toast lands in a session nobody sees and the escape would have reached the user. Accepted rather than answered with a second, windows-only desktop-detection heuristic; the unit test `os_notify::tests::windows_always_selects_the_desktop_arm` pins it, so changing it is a visible decision.
- **Remote-authored text reaching a terminal escape is sanitised as a security boundary.** A terminal escape is the one notification sink in the fleet where an attacker-supplied string is not merely *displayed* but **parsed as control input**: a message body carrying `\x1b` or `\x07` would terminate the OSC string early and leave the sender's remaining bytes being read by the emulator as fresh control sequences — retitling the window, clearing scrollback, or worse on terminals with permissive OSC handlers. So every string crossing into an escape has its control characters stripped first (`os_notify::sanitize`, whitelist-by-property via `char::is_control` rather than a blocklist of known-bad sequences, plus a length cap), and the unit tests assert a hostile body and a hostile thread label both come out inert. The six GUI apps are not exposed to this — they hand their strings to a notification daemon or OS API that treats them as data — so it is named here, in the owner doc for the arm that *is* exposed, rather than left as a quiet `replace()` at the call site.
- **No tray.** StatusNotifierItem is a GUI-desktop concept; absent here (ui.yaml `optional_elements`/`platform_elements` scoping).
- **Session-instance guard (owner: [`account-scoping.md`](account-scoping.md) § Concurrent instances).** tui is the first **retired** app (2026-08-15, W5.6 (account-data-plane.md § Workstreams)): same-account `fauna-tui` instances now coexist (`ServingMode::Concurrent`), each holding a *shared* per-account lock, with exclusivity narrowed to the three genuinely exclusive critical sections (schema migration, the engine-singleton role, and the conversations-engine role lock) — a non-role-holding instance's conversations surface refuses honestly (`conversations.errors.served_elsewhere`) rather than the process exiting. tui remains the platform with no raise-the-window affordance underneath — a terminal multiplexes freely, unlike the other desktops' re-keyed per-OS-login guard — so the shared lock is still the only thing standing between two `fauna-tui` processes and a shared-state race outside those three sections.
- **Sync-agent control surface (ratified 2026-07-18; BUILT — milestone A6 closed 2026-07-23: provisioning, location-binding UI, local-agent health, and the `enable-linger` offer; owner: [`sync-agent.md`](sync-agent.md) § Implementation status).** fauna-tui is the TUI control surface for the per-user sync+backup agent — the "tiny TUI usable over SSH" of the 2026-07-18 mandate is this app, not a separate micro-tool (a micro-CLI would duplicate auth/i18n/e2e/parity for nothing fauna-tui lacks — the § Non-goals "eighth app" cost). Three roles: the ordinary nest policy plane (its Folders settings sub-page gains the binding section the desktop apps have); the local `fauna-ipc` seam driven directly in Rust (per-set status, bind/unbind, pause); and — the differentiator — **headless provisioning**: on an SSH-only box fauna-tui holds identity (§ Credential storage) and therefore mints + provisions the agent's capability itself, then offers `loginctl enable-linger`. Milestone A6 of the design.
- **In-app routes (`fauna://`) — a launch argument, never an OS handler (ratified 2026-10-02).** The grammar is the one shared `fauna_core::app_route` (navigation only; the consent route's mechanism is [`../../behavior/authorization-server.md`](../../behavior/authorization-server.md) § Consent → *How the same-device handoff is built*). tui registers no `x-scheme-handler`; a route reaches it as the first `fauna://` argument on its command line — the same argv leg the windows app reads before its installer's protocol registration ever enters ([`windows.md`](windows.md) § Shell Extension → *The Share hand-off*), what a `.desktop` `%u` would pass, and what a user pastes after a device app shows the link. The argument is parsed once at startup through `AppRoute::parse` (an unparseable one is logged and dropped, never an error surface — a terminal is not what a stranger's link launches), held across the launch flow, and applied through one door (`App::apply_route`) once the session is signed in: the consent route navigates to the connected-apps page and calls the shared machine's `open_handoff`, which reveals the card; the two share routes take the same door whenever a producer for them exists on this platform (today only the Windows Explorer leaf mints them). No forward to a running instance: tui has no app↔app IPC (absence 5) and needs none here — same-account instances coexist (the session-instance guard above), so a second `fauna-tui fauna://…` is simply another instance showing the card. The e2e seam is an automation command (`open_route`) feeding a URI to the same door, so the journey needs no relaunch inside PAR's 90-second window; the argv leg is unit-pinned. Consequence, declared as absence 8 below: a device app on a box whose only Fauna app is tui finds no handler for `fauna://` and takes the browser door or the typed code instead.

### Update check

Built 2026-09-26, with the channel. The cross-platform promise — you can ask the app whether a newer version is out, and when one is, it says so and where to get it — and its desktop + tui scope are owned by [`../installers/README.md`](../installers/README.md) § Knowing a newer version is out; the terminal app's channel, the "here" the notice names, is [`../installers/tui.md`](../installers/tui.md). **The door** is the Settings root's About block (`apps/fauna-tui/src/settings/about.rs`; tui has no General sub-page, and `../../ui/settings.md` § Live-data placement puts the landing's live cells there): `settings-app-version` (the one product version, `product-version.md` § The model), `settings-check-updates-button` — the asked check, notify-only; its label carries the check's state, the linux General page's shape — and `update-available-notice`, painted only when a check found a newer release, naming the version and the release page. **The one rule every desktop follows** (amended 2026-10-03): the asked check, plus ONE unasked look per sign-in — `session::establish` spawns it, through the shared `fauna_client::update_look::look_at_sign_in_over_http` — which paints that same notice when a newer release is out and nothing otherwise (a failed look is silent; the asked check keeps its "Check failed" label), never overwrites a check the user started meanwhile, and runs again only at the next sign-in (sign-out resets the block). No timer, no download, no self-replacement, no toggle. **What decides the answer is shared** (`fauna_core::version`: the endpoint, the feed's shape, the semver rule, the release-page URL; `fauna_client::update_look`: the round trip and the sign-in look), so this app cannot disagree with linux, windows or macOS about any of it; the module is the two calls and the paint. No OS notification: the terminal has no persistent toast, and the in-page notice is the whole promise. **The e2e seam** is `FAUNA_E2E_RELEASE_FEED_URL`, compile-gated exactly like `FAUNA_E2E_DOWNLOAD_DIR` (convention 15) and behind `e2e_mode_enabled` within a test-capable build: the walk (`tests/e2e-unified/tests/test_app_version_and_updates.py`) serves the feed itself and moves only its origin — the production path, parse and decision run unchanged — and witnesses both halves: the asked check, and the sign-in look in both directions (a newer release painted with nobody pressing, from one request; the running version painting nothing). A session that walks no update check gets a closed loopback origin, so no e2e sign-in ever reaches the real feed.

## E2E automation

A `TuiDriver` implements the standard `PlatformDriver` contract against an **in-process automation server** over a local socket (the pattern `apple-e2e-automation.md` established), with every widget carrying its ui.yaml ID. Headless runs use a ratatui test backend or a pty — no display server needed, making a Linux dev machine's parametrization `[web, linux, tui]` and this likely the cheapest driver in the fleet. Testing conventions: owner `../testing.md`.

## Declared platform absences

Declared the same way web's absences are: here, plus ui.yaml platform scoping — never silently.

1. **Inline video/audio playback** — replaced by the opt-in external handoff above.
2. **Screen-reader accessibility** — a TUI exposes no AT-SPI/UIA tree; the six GUI apps remain the accessible surfaces. (Terminal-level accessibility — high-contrast, font scaling — comes free from the user's terminal.)
3. **Camera/QR capture** — `qr-camera-view` is already `optional_elements`; absent here. QR *display* renders as Unicode blocks.
4. **Drag-and-drop and OS file pickers** — replaced by path entry with completion and a file-browser widget. *(This is the ratified answer for every "how does a terminal choose a file?" question — it is shipped on feed's `compose-file`, profile's `profile-edit-avatar`/`-banner`, and conversations' `attachment-button`. 5. **Forwarding an add-account intent to a running instance, and therefore `launch-instance-add-account-button`** — the launch-collision chooser's "log in as a new user" affordance (`account-scoping.md` § Concurrent instances) forwards the intent over an app↔app IPC channel; tui has none, and building one was rejected as disproportionate to this single affordance (user decision 2026-08-01). `launch-instance-chooser`/`-chooser-item`/`-focus-existing-button`/`error-message` still ship on tui — only the add-account leg is scoped to `platform_elements: [windows, linux]` in ui.yaml. **Raising the instance that serves an account** is absent for the same structural reason (no window manager can raise a terminal), so `launch-instance-focus-existing-button` takes the ratified degrade instead: it re-probes the lock, continues as a plain launch when the sibling has gone, and otherwise prints where the account is served and exits (owner: `account-scoping.md` § Concurrent instances → the raise channel).

## Non-goals

- **A scriptable subcommand surface** (`fauna post create …`, `--json` output) is **out of scope for this app and its parity definition**. It is also why this app is named `tui`: the `cli` name is **reserved, unclaimed**, for exactly such a tool, so that if one is ever user-approved it does not have to fight a TUI for its name. It is a second UX paradigm that cannot conform to ui.yaml and would need its own parallel command taxonomy, parity ledger, and test surface — an eighth app in disguise, and an erosion vector for the configuration invariant ("just script it" replacing "build the UI on all apps"). If ever wanted, it is a separate, separately-user-approved track. The TUI keeps its action layer (the code translating UI events into `fauna-client-*` calls) cleanly separated from the widget layer so such a surface *could* reuse it — a code-structure nicety, not a commitment.

**Press arbitration moved out of the event loop** (2026-08-11) — the mouse arm's inline double-press synthesis is now `press.rs`, and the loop calls one door (`press::left_press`) plus one `tokio::select!` arm (`press_hold`, an **absolute** deadline: this arm is re-created every spin, so a relative sleep would restart the window on each unrelated event). Two things forced it. **It was wrong**: the old `is_double` compared `ui::HitTarget::Page(index)` — a position in *one frame's* element list — across two presses, while the first press's gesture had already run and repainted the page under it (the user-visible effect, and the cross-app class, are events.md's — [`../../ui/events.md`](../../ui/events.md) § Implementation status today, the *day cell's two gestures collide* bullet). **And it was untestable where it lived**: a `main.rs` loop body cannot be driven by a test, so the only in-process cover was the automation door, which dispatches an element's second gesture directly and therefore proves nothing about two presses from a hand. The module is UI-free and clock-injected (`Arbiter::press`/`expire` take `now`), so cadence logic is pinned by tier_1 tests with synthetic instants rather than by a test racing a wall clock (`../e2e-latency-independent-assertions.md` point 14), and `press::journey` drives real presses through `ui::render`'s own hit map over successive frames — the standing tui answer to "the automation door is not evidence the human path works". Two rules the module makes structural: **only an element that defines a usable second gesture is ever held**, so no ordinary control pays double-press latency for a gesture it does not have; and **a press pair is decided by element identity, never by position**, with actuation re-resolving through that identity — an async repaint between the two presses renumbers the list, and the old code had no defence against it. 12 tests, all mutation-verified against the pre-fix semantics.

**The page-module contract's target state is implemented** (§ Architecture; the consolidation the 2026-07-16 architecture review queued, landed 2026-07-16 — the gap this section previously declared is CLOSED). Both target-state clauses hold:

- **Field ownership is exhaustive.** `Field` nests a page-owned enum per page (`Field::Feed(FeedField)`, `Field::Settings(SettingsField)`, …), mirroring how `Gesture` already nested per-page `Action` enums. `App::field`/`set_field` are one exhaustive match with no fallback arm, so the seven `is_*_field` predicates and the silent fall-through to the wizard are gone. - **Gesture dispatch is one door.** `gesture_work(&mut App, Gesture) -> GestureWork` applies every gesture's local half and hands back only the work still to run; the caller picks await-vs-spawn (`automation::run_gesture` awaits and folds before the single-shot reply, `App::spawn_gesture` spawns and the outcome rides the channel as one `DataMessage::Page(PageOutcome)`). Two supporting conventions landed with it. **One nav-edge hook** — `on_nav_enter(&mut App, Page) -> Option<PageOp>`, with `App::apply` handing the refresh back rather than firing it, so the agent's nav *awaits* it: `navigate_to` cannot return before the fetch is folded, where the previous fire-and-forget spawn let a subsequent single-shot read see the pre-fetch frame (and could land a stale snapshot *after* a same-visit mutation — the events-slice bug, which is why events resets and deliberately fetches nothing. **A same-page nav re-runs that hook (corrected 2026-08-01): only the shell-state resets — the Settings rail Root, the Admin Dashboard, the Events List/today seat — stay edge-scoped, while the data refetch fires either way.** "Navigate to the tab I am already on" is how every app's e2e spells *reload* (`actions/*.py`: `reload = navigate`, documented as a fresh refetch), and what a user re-selecting their current tab means. tui had gated the whole hook on the edge, so every tui `reload()` was a silent no-op while the other six apps refetched — a driver's green ack for work never done (`../e2e-conventions.md` point 11), and the reason a ward's screen-time readout sat at 0 after a heartbeat that had demonstrably landed). **One `Outcome` convention** — feed and conversations were the last two pages using a bare error-string fold and a `NetworkOp` type; all eight now carry the contract's `Op`/`Outcome`/`apply_outcome`.
