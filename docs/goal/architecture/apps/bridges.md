## Concept

A **bridge** is a Fauna process that speaks the canonical client transport — WS-RPC + DAG-CBOR on `/api/v1/ws/{actor_id}` — but represents an external protocol endpoint (SMTP, IMAP, CalDAV, ATProto federation, ActivityPub, Nostr, …) instead of a human user. Bridges are peer clients of nest, on the same transport as the seven user apps; they do not have a privileged side channel.

Key properties (lifecycle details — startup, enrollment, re-keying, reconnect, shutdown — in `docs/goal/behavior/mail-bridge-lifecycle.md`):

- **Ed25519 service-user keypair** — file-backed, one per bridge process; generated by the bridge binary on first run if absent; enrolled in the admin's Fauna app (the bridge self-announces zero-touch via the loopback-gated pre-identity `fauna.bridges.request_enrollment`, creating a `pending` row that surfaces as an approval card via `fauna.bridges.list_pending_bridges`; the legacy HTTP pre-registration routes are removed — `mail-bridge-lifecycle.md` § The retired pre-registration path). The keypair file's location is OS-deployment topology — the supervisor process knows where it is — but everything else *about* the bridge (its role, its config, its capability scope) is nest state. **On a UID-split deployment (the production Docker image), the keypair is instead *artifact-minted* and the bridge is load-only**: loopback alone no longer authorizes enrollment, so the artifact mints each role's keypair and registers its blessed pubkey, and `request_enrollment` requires the enroller to prove possession of that blessed key — exact bytes/env/wire in `security.md` § Enrollment proof-of-possession contract; the bridge-self-generates path is the lenient fallback for a binary-only / dev nest.
- **Bridge-class actor_id** — minted by nest at enrollment time, distinct from any user actor_id. The bridge connects to its own `/api/v1/ws/{actor_id}` and runs its own challenge-response over the WS subprotocol (see `transport.md`).
- **Role from nest, never from argv.** The bridge process discovers its role (e.g., `mail.mta` vs. `mail.mda`, the now-landed `atproto.pds`, or future `nostr.relay`, …) by calling the role-gated `fauna.bridges.whoami` RPC after authentication; nest replies with the role + the per-role configuration. There is no `--mode=...` CLI flag on any bridge binary — see `principles.md` § One configuration surface.
- **Lifecycle: supervisor-managed, admin-toggled.** The bridge process is supervised by **s6-overlay** (in the published Docker image) or **systemd** (in bare-metal deployments). Nest never spawns or kills bridge processes directly — it only mutates flag-file state that the supervisor reads. The **admin** (the `/data/claim-code` claimant, one per box — the only configuring human; no operator role exists, `principles.md` § One configuration surface) toggles "enable mail" from their Fauna app; nest writes the `/data/imap-enabled` flag file in response (the flag is **nest's output**, the materialization of the app-UI toggle — never the admin's input), and the supervisor brings the `fauna-mail-bridge` services up. Admin un-toggles → nest removes the flag → the supervisor brings the bridge down. The bridge binary itself does not know which supervisor runs it; it would behave identically under runit, plain `docker run`, or a `go test` harness.
- **Per-role method allowlist, enforced nest-side.** Each bridge role has an explicit set of `fauna.bridges.*` methods it is permitted to call. An MTA cannot invoke MDA methods even if the running binary is the same; the allowlist is keyed off the role nest assigned to the bridge's keypair, not anything the bridge claims about itself.
- **No direct access to user MLS keys.** Any decryption capability a bridge needs to do its job is unwrapped on demand from a per-credential or per-deployment wrapped blob, scoped to the smallest time window the protocol supports. Nest holds no signing or decryption capability either — wrapped blobs are opaque to it.

## Why this shape

- **One transport, one auth model.** A bridge looks like any other client of nest. The same observability (per-actor connection state, per-method allowlist denials, push events) applies to bridge actors without bespoke nest-side surfaces.
- **No CLI-driven configuration.** Per `principles.md` § One configuration surface, anything a user or admin chooses — which bridges run, DKIM keys, TLS / ACME details, spam thresholds, federation peers, mail submission settings — is set from a Fauna app, propagated via nest state, and consumed by bridges over WS-RPC. The bridge binary's only args are artifact-set topology/diagnostics: `--keypair-file`, `--nest-endpoint`, `--log-level`, optional `--data-dir`, plus `--dry-run` (diagnostics), `--print-pubkey` (artifact blessed-registry provisioning; exits before any nest dial), and `--operator-hatch` (the explicit topology-hatch TOML path — the *concept* was renamed **topology hatch** corpus-wide 2026-07-09; the flag/file keep the legacy name until the WI3 port-migration touches them). None is behavior configuration; all are set by the deployment artifact, never hand-edited.
- **No second key-distribution channel.** All long-lived keys a bridge needs (TLS, per-user MLS) live as opaque wrapped blobs in nest state and are unwrapped at the bridge process boundary on demand; a key only the nest uses (DKIM) never reaches a bridge. Adding a bridge type doesn't require new key-distribution machinery — only a new wrapped-blob schema if the protocol needs one.
- **Audited capability surface.** Every method a bridge can call is on nest's per-role allowlist. Adding a new RPC is a security-review boundary; it can't be reached by a bridge until the role's allowlist contains the method.

## Don't do these

- **No bridge-specific transport.** Use `/api/v1/ws/{actor_id}` + DAG-CBOR + the standard challenge-response auth. The bridge-as-client pattern is the only mail-side pattern in the system; a Unix-socket / HMAC JSON-RPC side channel is the anti-pattern this concept replaces.
- **No `--mode={role}` CLI flag.** Role is nest-side. A new bridge that wants to share a binary across two roles enrolls two service-user keypairs; the process supervisor runs the binary with the right keypair file; the binary asks nest which role this keypair has.
- **No env-var configuration.** `FAUNA_BRIDGE_*` env vars are artifact-set deployment topology only — never a surface a human edits. Everything else lives in nest state and is fetched at startup + watched for changes.
- **No direct user-key access.** A bridge that needs to decrypt user content uses a per-user wrapped blob unwrapped at the credential boundary (e.g., IMAP AUTH for the MDA), scoped to the session. A bridge that needs no decryption (e.g., MTA) holds no decryption capability at all.

## Capability-allowlist enforcement

The per-role allowlist (§ Concept "Per-role method allowlist", § Why this shape "Audited capability surface") is the all-class matrix `bins/fauna-nest/src/bridge_method_allowlist.rs::is_permitted(class, kind)` — `class` ∈ {`BridgeMta`, `BridgeMda`, `ContentProcessor`, `BridgeAtprotoPds`, `Custodian`, `User`, `Admin`} (`ContentProcessor` and `BridgeAtprotoPds` are both live today, not merely anticipated: `ContentProcessor` is held by nest's own in-process web-serve paywall holder, which self-approves at boot (`mail-spam.md` § The opt-in toggle is the grant gesture) — a *standalone external* content-processor bridge remains unbuilt, though `register_service_user` already admits one; `BridgeAtprotoPds` is the ATProto PDS bridge, `atproto.pds`, § Active bridges above; `Custodian` is not a bridge role at all — a device holding a live custody-capability grant, least-privilege-gated to a handful of kinds, owned by `account-replica-posture.md` § Replica posture — it shares this matrix only because the central gate (below) is class-agnostic), resolved from the connection actor by `caller_class_for_actor`, with a `_ => false` default-deny.

It is enforced as a **single central chokepoint** in `routes::dispatch_request` (gate **1d**): every *registered, non-pre-identity* kind an authenticated connection sends is checked against `is_permitted` **before** the handler is spawned, so a kind absent from the allowlist is bridge-unreachable (and unreachable by any class) by default. The per-handler `require_class` / `require_permission` calls remain as defense-in-depth and carry the finer User-vs-Admin + caller-scope logic the coarse central gate does not. Pre-identity bootstrap / discovery kinds (`pre_identity_allowlist`) are exempt from the class gate — an anonymous connection is confined to them at gate 1b, and an authenticated connection may still call them.

Coverage is guarded by the test `bridge_method_allowlist::tests::every_registered_kind_is_gated`, which builds the live router (`lib::build_rpc_router`) and asserts every registered non-pre-identity kind is permitted for at least one class — so a new handler added without an allowlist arm fails the build, keeping "every method is on the allowlist" honest. (Earlier, enforcement was per-handler only; the central gate replaced it after a 2026-06-23 review finding, and the coverage test above is what keeps the matrix complete.)

The pre-identity exemption and the class allowlist are two disjoint sets by construction — a kind is either pre-identity (gate 1b admits it anonymously, gate 1d skips its class check) or class-allowlisted, never both, since a kind in both would have a dead `is_permitted` arm and stay anonymously reachable regardless of what the matrix says. `every_registered_kind_is_gated` cannot catch this (it skips pre-identity kinds too, by the same predicate) — the disjointness is pinned separately by `bridge_method_allowlist::tests::no_kind_is_both_pre_identity_and_class_allowlisted`.

**`ThirdParty` — reach as data under the compiled ceiling (ratified 2026-09-05, the third-party integration chain; built 2026-10-01, its connection 2026-10-02 — § Implementation status today).** The matrix above is the right property and must survive third parties, so: **(1) the ceiling stays compiled** — `CallerClass` gains one variant, `ThirdParty`, and the matrix gains its arms: the *maximum* any principal may ever reach, reviewed like every other arm, covered by the same sweep test. **(2) The per-principal reach is data under the ceiling** — a principal's roster row ([`../third-party.md`](../third-party.md) § The principal model) carries its approved scope set, and the chokepoint checks `is_permitted(ThirdParty, kind)` **and** `scope_covers(principal.scopes, kind)`; a principal can never exceed the ceiling by any row content, and a row can only narrow. **(3) Class is re-resolved per RPC**, so revoke severs live sessions — the `Custodian` arm's existing pattern. **(4) Roles for hosted plugins are the same data**: a plugin's "role" is its principal row; there is no `--mode=`, no compiled role-table entry per plugin (§ Concept's role-from-nest rule, applied to code Fauna did not write). The Fauna scope grammar the `scope_covers` check reads is [`../../behavior/authorization-server.md`](../../behavior/authorization-server.md) § Scope grammar's.

**How the class meets the connection (ratified 2026-10-01; rules (a)–(d) built in `principal_handlers::dispatch_principal` 2026-10-01, the connection that calls it 2026-10-02).** The session a principal dispatches on is [`../transport-connection.md`](../transport-connection.md) § Connection lifecycle → *The principal session*'s; four rules here follow from it. **(a) The class is resolved from the connection's principal binding, never from an actor id.** `caller_class_for_actor` has no `ThirdParty` answer: the gate asks it only for a connection that carries an actor, and for a principal connection reads the principal row and the account's authority instead — both live → `ThirdParty`, either gone → no class, the every-kind refusal; the account's external-apps switch is a third read beside them, and OFF is the same no-class answer ([`../../behavior/atproto-pds-full.md`](../../behavior/atproto-pds-full.md) § Detailed design → F1 detail, the kill-switch bullet, owns what the switch suspends). An account's own class (`User`, `Admin`) is therefore unreachable from a principal session by construction, not by a check that could be forgotten. **(b) The scope set checked is the narrower of two.** `scope_covers` reads the row's `granted_scopes` *intersected with* the scope set of the token the session was opened with: the row carries what the user most recently agreed to and narrows every live session at once, and the token carries what that grant family was consented for and keeps an older family's session from picking up a later ceremony's wider set. Nothing in either widens the other. **(c) A scoped kind names exactly one scope arm; a session kind names none.** The kind → arm mapping is compiled beside the matrix, and the sweep test that covers the arms also holds it equal to the grammar's live arms (the predicate rule, owned by the grammar). **Two refinements, ruled 2026-10-02 with the fourth and fifth arms ([`../../behavior/authorization-server.md`](../../behavior/authorization-server.md) § Scope grammar → *The planes ruled 2026-10-02*): a *scope-dispatched* kind — `fauna.sync.changes.list`, whose request names an account-plane scope — names the arm its scope family names (`ext:<kind>` → records; `state` → personalization, read only; every other spelling refused), so the compiled mapping carries that small set for the one kind and the handler picks by the request's scope; and a *refining* qualifier arm — `fauna:feed:read:account` over the two public timelines — adds the account's reading to kinds the bare arm already covers without entering the mapping for them: the bare arm stays each one's arm, and the handler reads the refinement off the session's scopes. The sweep test's two equalities hold as before — every arm reaches at least one kind of its own (the refining arm reaches the three custom-feed kinds), and every scoped ceiling kind names a live arm.** **(d) A `ThirdParty` kind has a handler of its own.** A matrix arm is necessary and not sufficient: the kind is served by a handler registered for principal callers, which receives the binding (account, principal, scopes) rather than an actor id, and the sweep test holds the principal-handler set equal to the `ThirdParty` ceiling. The existing arm being widened first is `fauna.capabilities.fetch` — `BridgeMda | ContentProcessor` today — whose principal handler serves only grants wrapped to the row's own `holder_x25519`. **The second widening (ratified and built 2026-10-02): `fauna.nostr.bunker.bind` under the `fauna:identity:op:<class>` arm** — `ThirdParty` only, no actor class, its principal handler in `nostr::bunker_handlers` (compiled with the `nostr` feature, like the bunker cluster it binds into) — whose reach reads the qualifier's class (`PrincipalReach::IdentityOp`) — a kind is covered only by a class its custodian performs ([`../../behavior/authorization-server.md`](../../behavior/authorization-server.md) § Scope grammar → *The second arm*). **The third widening (ratified and built 2026-10-02, S8a): `fauna.account.state.put` and `fauna.sync.changes.list` under the `fauna:records:rw:<qualifier>` arm**, whose reach reads the request's `scope` — covered only for an `ext:<kind>` the grant's qualifier covers, and for the put only as the row's own writer key ([`../third-party-kinds.md`](../third-party-kinds.md) § The record doors owns the three checks). Their principal handlers sit beside the actor twins in `sync_handlers` (`principal_account_state_put_handler`, `principal_changes_list_handler`); the list also refuses every selector the actor door takes besides the scope — a folder, a cross-nest route, a custody `of_owner`, any item class but `state-entry` — and records no walk mark, a principal being no replica of the account. **The deposit widening (built 2026-10-03, S9a): `fauna.folders.deposit` under the `fauna:folder:deposit:<folder id>` arm** — `ThirdParty` only, no actor class (its actor-router half is refused at the central gate, as `fauna.nostr.bunker.bind`'s is), its principal handler in `folder_deposit` — whose arm-wide reach is the gate's and whose per-folder half, the request's folder named by one of the session's qualifiers, is the handler's ([`../../behavior/file-sync.md`](../../behavior/file-sync.md) § Third-party deposit ingress owns the door). **The events widening (built 2026-10-05): `fauna.events.poll` under the `fauna:events:subscribe` arm** — `ThirdParty` only, no actor class (its actor-router half refused at the central gate, as the deposit kind's is), its principal handler in `events_doors` — whose arm-wide reach is the gate's and whose per-scope half, the filter `fauna_scope::event_reaches`, is the handler's ([`../transport.md`](../transport.md) § Push events → *Third-party event doors* owns the doors).

## Bridge-kind catalogue (caller classes)

*(Moved here 2026-07-08 from `architecture/nest/storage-modes.md` § WS-RPC bridge kinds — cluster-#3 mail review: the catalogue's organizing axis is the per-role caller-class allowlist this doc owns. `storage-modes.md` was since rewritten for the no-modes ratification and no longer carries a stub pointer to this section.)*


`fauna.bridges.*` is the WS-RPC surface the MTA / MDA bridges (and, for a few user-facing kinds, the user's Fauna app) call into nest. Caller class is gated per kind by `bins/fauna-nest/src/bridge_method_allowlist.rs`; `BridgeMta` and `BridgeMda` actors enroll **zero-touch** via `request_enrollment` (a loopback-gated *pre-identity* kind — the bridge self-announces a fresh keypair to create a `pending` row, no caller class; it is the only enrollment surface), `User` callers are any authenticated actor on a WS connection. The transport is the same per-actor WS-RPC channel `architecture/nest/common.md` § WS-RPC channel describes (one WebSocket per actor, kind-routed dispatcher, idempotency cache); only the kind namespace differs.

The catalogue below partitions kinds by phase as they land. Phases A/B/C/D/E/F have all shipped (mail bridge; Phase-D/E/F status → § Implementation status today).

**Phase D — encrypted-mode CalDAV r/w (6 kinds, shipped).** Placement-layer tables `bridge_caldav_calendars` / `bridge_caldav_events` / `bridge_caldav_expunged`. **When the bridge stops serving — the fate of its rooms (ruled 2026-10-03; refutable until the first third-party bridge is revoked by a real user).** A bridged room belongs to `(account, bridge id)`: its id is derived from them (`bridged_room_id`), never from a principal id, and the principal that serves it is whichever live roster row of the account declares that `bridge.id` — at most one, refused at consent ([`../third-party.md`](../third-party.md) § The manifest → *The `bridge` block*). The room row's `bridge_principal_id` is that resolution, cached. Four consequences, each a rule of the family:

1. **The rows are the user's and survive every ending.** Messages in both directions are sealed to the user; no verb of the family — the revoke included — deletes a room or a message ([`../../principles.md`](../../principles.md) § No user-data loss). The floor seat keeps naming the principal that served the room until another adopts it: the room's class is transport-only *because* a bridge read it, and unseating the bridge would re-derive its history as end-to-end, which is false ([`../../behavior/conversation-rooms.md`](../../behavior/conversation-rooms.md) § Bridged rooms).
2. **A room with no serving principal is disconnected — readable, never writable.** `rooms.list` carries it with `disconnected: true` (additive; absent means connected), its label falling back to the bridge id and its glyph to the generic `bridge`; `inbox.fetch` serves it as ever; `send` refuses it with the typed `fauna.bridges.bridge_disconnected`; `rooms.open` on that bridge id refuses as `address_refused`, no bridge admitting the address. The app's half is already ruled: a bridge absent from the backend's registry leaves its threads on the rail's most-restrictive vector and the generic glyph ([`../../ui/conversations.md`](../../ui/conversations.md) § Where logic lives → *The `Bridged` adapter*, ruling 2 (b); `BridgedBackend::set_identities`), so the glue fills the registry from connected rows only and the composer closes by itself — how a disconnected thread is *labelled* is the render slices' question. What disconnects a room: the one verb (`fauna.principals.revoke`, and the plugin uninstall that runs the same cascade — [`../third-party.md`](../third-party.md) § The principal model, rule 4), and a re-consent of the same document whose manifest no longer declares a `bridge` block or declares another id. **Not the external-apps switch:** OFF is a pause, not an ending — the rooms stay connected, sends keep queueing under the per-principal cap and drain when the switch comes back.
3. **The undrained outbox ends with the principal; the Sent copy stays and says so.** An outbox item is ciphertext sealed to the serving principal's key — derived from the Sent row, recreatable by sending again, openable by nobody once that principal is gone (the revoke ends the key's every reach, rule 4; a re-consent attesting a *new* holder key strands the old key's items the same way). So the moment a principal stops serving — the revoke, the manifest change above, or a holder-key replacement at `/oauth/token` — the nest deletes the principal's undrained items **in the same transaction** and stamps each one's Sent row (`undelivered_at`; `BridgedMessageInfo.undelivered`, additive), so the thread can say *not delivered* instead of lying by omission; the revoke then nudges each touched room with `conversation_changed`. Nothing is kept for a later ceremony to drain: a message the user composed before revoking an app must not leave through that app after a re-consent, and the user sends again. A receipt the far side already gave stays as it was.
4. **A principal that comes to declare a bridge id adopts the id's rooms, in the consent transaction.** Whether it is the same document consented again — a new principal id, since the revoke deleted the row — or a different document the user chose for the same network, the consent's find-or-create rebinds every room of `(account, bridge id)` to it: the row's serving principal, its snapshotted `bridge_x25519` and capability vector, and the floor's bridge seat. The rooms reconnect at once, history intact, new sends sealed to the new key, and no claim is refused for their sake: refusing a bridge id while rooms exist would strand the user's own rooms behind a verb the apps do not offer ([`../../principles.md`](../../principles.md) § Client-state recoverability). The adopting bridge learns the far room ids and participants the rows carry — the far network's own names, which it serves anyway — and never a message, since none is sealed to it. The same rebind runs when the serving principal re-consents under a replaced holder key (the rooms' key refreshes) and, defensively, on every `room.upsert`, so a first-party in-process leg with no roster row keeps its rooms current too. The consent sends no push: the app's registry follows its next `rooms.list` read, which the render re-runs when a consent lands. Pinned by `db::bridged_conversations::tests::a_principals_end_deletes_only_its_undrained_outbox_and_a_new_principal_adopts_the_rooms`, `db::third_party_principals::tests::a_bridges_rooms_follow_the_bridge_id_through_revoke_and_re_consent` and `bridged_conversation_handlers::tests::a_revoked_bridges_room_is_read_only_until_a_principal_adopts_it`.
