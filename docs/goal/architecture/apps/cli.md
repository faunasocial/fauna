## Goal

A user tells an LLM "post this", "what did my sister write about the trip", "move last week's invoices into the Accounting folder", "approve the pending bridge", and the LLM does it against the user's own nest, over tools whose reach is exactly the set of grants the user minted from their own app, revocable in one row, audited per operation — on any LLM host, with the user's content leaving their device only where the user chose a hosted model.

The design is **one app, two shells**: a device binary for LLM hosts that launch a local server (stdio, or a loopback HTTP listener), and a nest-hosted WASM component for hosts that can only reach a remote URL. Both run one shared tool catalog, and both are **principals** of the user in the sense [`../third-party.md`](../third-party.md) § The principal model already ratified — a first-party-shipped app that deliberately authenticates like a third party, because the actor driving it reads untrusted text for a living.

**Built 2026-10-18 — the loopback streamable-HTTP transport.** `fauna-cli mcp --listen` binds `127.0.0.1` on a free port (`http::bind` takes no address, so a non-loopback bind is not expressible), prints the URL `http://127.0.0.1:<port>/mcp` once on stdout and serves `POST /mcp` through the same method layer and the same principal session as stdio: a request is answered `200` `application/json`, a notification `202`; the shell offers no server-sent stream and no session id, so `GET` and `DELETE` answer `405`. It is a small in-tree HTTP/1.1 reader on the shell's existing tokio (no HTTP server crate was added to the dependency graph). There is no auth header — loopback is the trust boundary — so the listener closes DNS rebinding itself, per MCP's streamable-HTTP rule: a `Host` that is not `127.0.0.1`, `localhost` or `[::1]` with the listener's own port, or an `Origin` that is present and not a loopback origin, is refused `403` before the method layer. Tests: tier_1 `libs/fauna-cli/tests/http_transport.rs` (the catalog over HTTP; the foreign `Host`/`Origin` refusals) and tier_3 `test_cli_mcp.py` (the consent journey run over both transports through `drivers/cli_mcp.py`'s `transport="http"`, and `test_the_http_listener_refuses_a_foreign_origin_and_host`). **Gap:** connections are served one at a time, each answered once and closed — enough for a host on the same machine; a keep-alive or concurrent-connection listener is a later refinement if a host needs it.

- `docs/goal/behavior/authorization-server.md:133` — the typed-code start: `/oauth/device_authorization` → a `user_code` the app shows → the user opens Fauna → *Connect an app* → types it → card → approve → the app polls with the device-code grant; built nest side.
- `docs/goal/architecture/transport-connection.md:1109` — a principal holds no Ed25519 actor key and no nest bearer; its transport credential is a DPoP-bound access token; the connection is the principal's, class re-resolved per RPC, never `User`.
- `docs/goal/architecture/third-party.md:164-168` — the WASM plugin world imports `nest-api` (one WS-RPC call as this principal through the principal chokepoint), `state`, `holder` (grant opening performed by the host, the secret never in plugin memory), `http`, `clock`, `log`, and exports `lifecycle` and `ingress` (a request the nest terminated); caps are constants.
- `docs/goal/architecture/third-party.md:158` — hosted code is headless (TP2); roles for hosted plugins are the principal row, never a `--mode=`.
- The MCP specification (revision 2026-07-28) — its authorization is OAuth 2.1 + RFC 9728 + RFC 8707 + the Client ID Metadata Document, and "a personal server exposing an MCP server to the user's agents" is an established pattern; the standards survey behind the third-party chain chose the nest's issuer stack with this in mind.
- `docs/goal/architecture/apps/bridges.md:79` — a principal connection resolves to `ThirdParty` or to no class, never `User` or `Admin` (rule (a)); and `:80` — an admin-plane kind is served to a principal only under an admin arm and the account's live admin authority, read per RPC as a fourth predicate (rule (e)) — so admin reach for this app is the admin's consent plus the admin's standing role, never a class.
- `docs/goal/principles.md` § One configuration surface — a value is either not chosen by any human (a constant, or IPC wiring the launching artifact sets) or a user/admin choice in app UI + nest state; no third tier.

## The principal shape — why not an eighth key-holding app

The seven apps hold the user's identity key and a nest bearer. This app holds **neither**, by ruling (2026-10-17), and the reason is the actor behind it: an LLM is an execution engine for the text it reads, and its tools will read mail and posts from strangers — the same box-sourced-text-is-untrusted posture the maintainers apply to themselves. With the identity key in the LLM's process, one injected mail could sign posts, mint grants, retire a nest or delete data as the user. As a principal it gets exactly what every connected app gets, and nothing is new:

- **Reach is a user-minted grant** — per scope, time-bounded, revocable from the connected-apps roster, every operation on the roster's record. What the LLM can read is a `content.read` tuple over a named scope; what it can write is a `content.write` authorization or a keyless `identity.op` class; what it can never do is anything on the sovereign deny list.
- **Identity-bearing acts go through the oracle.** Posting as the user is the built `post.author` class; signing a Nostr event or an ActivityPub request is its custodian's class; the LLM's process never holds the key, so a compromise of the LLM host leaks the granted scopes for the grant's window and no more — TP4's property, applied to a first-party binary.
- **Transport is the principal session**, a DPoP-bound token; class is re-resolved per RPC from the row. A revoke bites at the next call and sweeps the socket.

The rejected shape — a key-holding app with a self-policed tool allowlist — puts the policy in code instead of in keys, and collapses the token and grant layers [`../third-party.md`](../third-party.md) § Architectural rules rule 2 keeps apart. It would also have made this the one app whose compromise is total, held by the one actor most exposed to injection.

**First-party, yet a third-party principal.** The app ships signed by the organisation and its Client ID Metadata Document is the organisation's, so the consent card resolves a known publisher — but the nest treats it as it treats any document: no registrar, no admin-side mint, the user's own consent act is the only door (rule 1 of the principal model). Being first-party buys it one thing only: the nest-hosted shell ships inside the nest (§ The nest-hosted shell), so a deployment has it with no download and no catalog entry.

## One catalog, many front-ends

The catalog — every tool's name, input schema, annotations, the ui.yaml page it serves, and its handler — is one shared crate, **`libs/fauna-cli`**, transport-agnostic and shell-agnostic. A shell supplies a transport and a host: `apps/fauna-cli/` (the device binary: MCP over stdio, or a loopback streamable-HTTP listener) and the nest-hosted component (§ The nest-hosted shell) are the two shells the 2026-10-17 ratification covered; the human `argv` front-end (`fauna-cli post create …`, `--json` output) is the **third shell** over the same catalog, approved the same day — the catalog is designed so that a shell costs a shell, never a second taxonomy, and the paragraph below is all the third one needed.

**The `argv` shell (approved 2026-10-17, user ruling) — the same binary, a human or a script at the terminal.** `fauna-cli <noun> <verb> [--flag …]` is *derived* from the catalog, never authored beside it: the tool `post_create` is the command `post create` (the name's first segment the noun, the rest the verb), each property of its input schema a `--kebab-case` flag with the schema's description as its help, the tool's description the command's `--help`, a tool's required properties also accepted positionally in the schema's order, and the device shell's connect flow the command `fauna-cli connect <handle>` (that positional rule over the `connect` tool, no special case), which prints the `user_code` the human types into *Connect an app* and stays until the approval settles, so the next command resumes the stored connection. Output is the tool result rendered for a terminal when stdout is a tty, and the result's JSON verbatim under `--json` or whenever stdout is not a tty; a tool error is the manager's error on stderr with exit code 1, a usage error exit code 2. Annotations govern the terminal as they govern a host: a tool marked destructive asks on a tty (a "no" does nothing and exits 1) and refuses without `--yes` off one, with exit code 2. Same principal, same credential namespace, same arms, same ceiling — the `argv` shell reaches exactly what the MCP shell reaches, so it is the user's own hands on their own grants and **not an operator surface**: the sovereign-act boundary (§ The sovereign-act boundary) and the configuration invariant ([`../../principles.md`](../../principles.md) § One configuration surface) hold unchanged, and a command the catalog has no tool for does not exist — a wanted command is a wanted tool, added to the catalog for every shell. Parity costs nothing new: the derivation is total, so the catalog snapshot already describes the command tree; a tier_1 test walks the catalog and asserts every tool is a command and every property a flag, and the tier_3 journey drives the binary once by `argv` beside its MCP run. A script that pipes `--json` output into an LLM has put that LLM where an MCP host stands, with the same posture (§ Prompt-injection posture).

**Tools are the managers' operations, named by ui.yaml's pages.** Each tool declares the ui.yaml page it serves (`feed`, `contacts`, `admin-mail`, …) and is a verb of that page's shared manager, projection or machine — never a UI gesture (no "click compose-button"): the LLM composes a post, it does not drive a widget. Page vocabulary keeps one taxonomy across the eight apps (priority #3); the manager layer keeps the logic in shared Rust (priority #2); and the gesture layer stays the seven apps' own. The same rule that bars a page from pushing its own error element on tui applies here: a tool's error is the manager's error, verbatim, as an MCP tool error — never swallowed into an empty success.

**Annotations are load-bearing.** Every tool carries MCP's `readOnlyHint` / `destructiveHint` / `idempotentHint` truthfully, because every serious host confirms or refuses on them; a write tool with `readOnlyHint: true` is a bug of the dropped-command class. The catalog also marks each tool with the scope arm it needs, so a host can list only what the user's grant reaches (§ Reach grows one plane at a time).

**Resources and prompts.** Read-only projections that an LLM wants whole (a profile, a folder listing, the admin dashboard) are MCP resources beside the tools; the onboarding and admin runbooks a human must do themselves are MCP prompts that *coach* (§ The sovereign-act boundary). Neither is a second taxonomy: both declare their page like a tool. **The resource scheme and the first resource (ruled 2026-10-17):** a resource URI is `nest://<page>[/<id>]` — the catalog projects the user's nest — and never `fauna://`, which is the in-app deep-link grammar (`fauna_core::app_route`) and stays it. The first is the account's own profile at `nest://profile`, with any actor's at the template `nest://profile/{actor_id}` (`resources/templates/list`), each the decoded display fields as JSON through the one shared decode (`fauna_client_profile::decode_profile_display`), read with `fauna.profile.get` under the profile arm ([`../../behavior/authorization-server.md`](../../behavior/authorization-server.md) § Scope grammar → *The profile arm*); `resources/list`, `resources/templates/list` and `resources/read` join the layer beside `tools/*`. A profile edit is a tool (`profile_set`, under `fauna:identity:op:profile.author`), since a resource is read-only by MCP's own contract. The notifications plane is tools only — `notifications_poll`, which never marks read, and `notifications_mark_read`, the write the host confirms (*The notifications arms*, the same section) — because a poll is a verb with a cursor, not a projection an LLM wants whole.

## Not a ui.yaml app

ui.yaml owns element IDs and per-page element scope for the seven interactive apps; this app has no elements, so it has **no ui.yaml platform flag, no `ui-actual-cli.yaml`, and never adds an ID**. Its parity artifact is the **catalog snapshot**: a `cli-catalog` recipe (minted with the first build) regenerates `tests/e2e-unified/catalog-actual-cli.yaml` from `libs/fauna-cli` (checked in, the `ui-actual-<app>.yaml` convention transposed), and a cheap lint holds every ui.yaml page to one of four states in this doc's ledger (§ The feature ledger) — a page in none of them is a lint red, so the ledger can never silently lag the spec. "All 7 apps" phrasing stays correct for ui.yaml, e2e app parametrization and per-element parity; this is the eighth app in the repo's app count and in every rule that speaks of apps as programs (priorities #1–#3, the guides), and its parity is per page, not per element.

## Reach grows one plane at a time

Today the `ThirdParty` ceiling admits a narrow kind set (`ext.*` records, served folders, the bridge kinds, the oracle doors, the personalization plane) and the scope grammar has arms for exactly those. The catalog can reach a first-party plane — feed, contacts, events, mail, media, folders, profile, search, the admin pages — **only once that plane has a device-app arm and its `ThirdParty` kinds under the ceiling**, so every page group lands as one slice of three parts, each in its owner's doc: **(1)** the arm in the scope grammar ([`../../behavior/authorization-server.md`](../../behavior/authorization-server.md) § Scope grammar — the fourth arm, `fauna:feed:read:account`, is the first — built 2026-10-10 with its `ThirdParty` feed kinds, no grant twin since nothing it reads is sealed, and the arm the catalog's first served group reads through) with its twin in words on the consent card; **(2)** the plane's read tuples minted to a device principal's holder key and its `ThirdParty` kinds under the compiled ceiling ([`bridges.md`](bridges.md) § Capability-allowlist enforcement; [`../encryption-at-rest.md`](../encryption-at-rest.md) § Capability tiering's holder-class widening); **(3)** the catalog's tools for that page group, reading through the capability-holder opening code and writing through the plane's door — the oracle for anything identity-bearing, the plane's own door otherwise. A plane whose door is a user-keyed seal (an outbound mail copy, a calendar write) gets its write authorization as a `content.write`-class tuple over that plane, never a bearer. **Order of planes** (what an LLM is most asked for first; each its own tracked work item): feed + profile + search + notifications; contacts + events; mail (the pages `mail-*`, `mail-settings`); media + folders; the admin pages for an admin-consented principal (the admin arms — `fauna:admin:read:<page>` and its `rw` twin, one qualifier per non-sovereign admin page, the first built 2026-10-17; the sovereign admin acts never enter them — § The sovereign-act boundary); nostr, atproto, p2p, moderation, family, personalization, muted words, labelers, subscriptions. The consent card for this app therefore grows arm by arm; a user who grants only the feed arm has an LLM that sees only their feed.

## The sovereign-act boundary

"Only an LLM" holds for operating the account, **not for owning it.** The following stay with a human on a first-party app — not as a parity gap but as the trust model's floor — and the catalog offers them at most as a read or as a coaching prompt:

- **Everything the sovereign deny list names** (`SovereignOp`): PLC rotation, handle, domain, key succession, the MLS identity root.
- **The onboarding ceremony** — every `onboarding.*` page: identity creation and import, the recovery kit and recovery entry, emergency lockout, handle and DNS, VPS provisioning, nest provisioning, claim codes, NAT mode, the trust prompt, nest recovery and retirement. A recovery secret passing through an LLM context is a key leak, and on a hosted model it is a leak to a third party's servers.
- **The grant plane itself**: consent (minting a principal, including this app's own), revocation, the devices, sessions, nests, connected-apps and backups pages — read-only tools at most (status, lists, the audit record), never a mutation. An LLM that could widen its own grant has no boundary.
- **Account deletion and factory reset.**
- **The admin plane's sovereign acts (ruled 2026-10-17).** An admin's consent reaches the admin pages through the admin arms, and the same floor holds there: an admin act that **widens authority or touches the grant plane** — adding or removing an admin, approving or rejecting a pending bridge, revoking or re-keying a bridge service user, removing a custody host, approving or vetoing a pending admin action; that **mints, rotates or reveals key material or a secret** — the deployment seed, the issuer key and the session secret, a TLS certificate, DKIM, the SRS and list-unsubscribe secrets, a registration that carries a client secret; that **touches identity** — clearing a user's handle, the host address, the primary-domain rename (the deny list's handle and domain, for other accounts and for the server); or that **destroys what a user cannot recreate** — deleting a user, scheduling an eviction, a legal takedown, the factory reset — is sovereign: never a kind of any admin string, a read or a coaching prompt at most. Everything else an admin does daily — admitting members and approving or denying invite requests, suspending and reinstating, tiers and quotas, every policy and toggle, forwarders and local domains, the apex actor, the update channel, reports and logs, a host restart, garbage collection, moderation blocks and report resolution — is operating the server and is served under the page's `rw` string. Each page's build row applies this rule kind by kind and names the kinds in the arm's bullet ([`../../behavior/authorization-server.md`](../../behavior/authorization-server.md) § Scope grammar → *The admin arms*).

So a user needs one first-party app somewhere — a phone suffices — for the ceremonies, and day-to-day everything else is the LLM's. An MCP prompt per ceremony walks the human through it in the app's own words; the catalog never asks the LLM for a secret and never accepts one as a tool argument (§ Credentials and configuration).

## The device shell

`apps/fauna-cli/`, a cross-platform Rust binary like tui's (Linux, macOS, Windows), launched by the LLM host — and obtained the way the terminal app is: `fauna-cli` is the third member of the terminal app's release archive and of the `.pkg` component and MSI feature that carry `fauna-tui`, same targets, same signatures, same `install.sh` ([`../installers/tui.md`](../installers/tui.md) § The ratified channel owns the channel; its decision 4 is the ruling, built 2026-10-18 on the recommendation and ratified by the owner 2026-10-20). `fauna-cli mcp` serves MCP over stdio; `fauna-cli mcp --listen` serves streamable HTTP on a loopback port it prints, for hosts that dial a URL on the same machine. That subcommand and that flag are the whole of the MCP shell's command line (the `argv` shell's derived commands sit beside them, § One catalog, many front-ends → *The `argv` shell*) — they are IPC wiring the launching artifact (the host's server configuration) sets, bucket 1 of the configuration invariant, never a preference. **No nest URL, no account, no token on the command line or in a file the user edits:** the account comes from the consent ceremony. **The connect tool:** the first tool call on a host with no principal answers with one instruction for the human; the LLM asks the user for their handle (not a secret), calls `connect(handle)`, the shell resolves the handle to the nest domain the way "sign in with Fauna" does, starts the typed-code ceremony and returns the `user_code` for the human to type into *Connect an app* on any of their apps — or, on a desktop with a first-party app installed, the same-device handoff opens the card directly. Several accounts are several principals, one row each; a tool names its account only when the shell holds more than one.

**Several accounts.** Every tool but `connect` takes an optional `account` argument — the handle the user connected the account with — and a resource URI takes `?account=<handle>`; one static schema, whatever the shell holds, because a host lists tools once and would never see an argument that appeared with the second account. With one account held the argument is omitted; with several, a call naming none is refused with the held handles so the LLM asks the user which. The `connect` answer names the account it is for. Each account's slot rests under this app's namespace keyed by the account's id (the token answer's `sub`), never the handle, beside one index item naming each slot's handle; the index is one store item, so the store's item cap bounds how many accounts a shell keeps (the shared registry's bound, [`../long-term-store.md`](../long-term-store.md) § Multi-account evolution), and a connect past it is refused. The slots are never the shared `AccountRegistry`, which holds identity keys this app must never hold (rule 1).

**A dropped session.** A principal session the nest closed (a restart, a network blip) is redialled when a call finds it gone — once, with the held token while it is not near expiry, else with the refresh grant. A read-only tool (the catalog's `read_only` annotation) is then run again on the new session; a write is never retried — the nest may have applied it before the socket went — and its answer says it may or may not have taken effect, so the LLM checks before repeating it. `idempotent` does not license a retry: an idempotent write is still a write the host confirmed once. A redial that fails leaves the account connected on the lost session, so the next call tries again and a nest still restarting is a wait, never a new ceremony.

**Credentials.** The DPoP key, the refresh grant and the grant-wrapped scope keys rest in the headless credential store [`tui.md`](tui.md) § Credential storage owns (the OS keychain where one is usable) under this app's own namespace — the store the sync agent and tui already share, no second format — and nothing in it is ever handed to the LLM (rule 6). **On a box with no usable OS secret store — the unattended arm, RULED 2026-10-18 (built the same day, § Implementation status today):** the namespace rests in a `0600` plaintext file under this app's own data dir, selected by the same auto-detected resolution as tui's headless arm (the e2e dir; else an existing file wins; else the live three-way probe, *locked* and *absent* both selecting the file) — no passphrase, no human step, never a knob (bucket 1 of the configuration invariant: data the binary keeps, like `device.db`, not a file a human edits); written atomically through `fauna_core::secret_file` and `Zeroizing` in memory; and **declared, never quiet**: the arm's cause reaches the `connect` answer and the host's stderr as one sentence saying that the connection rests on disk under file permissions alone and that the *Connected apps* page revokes it in one row. Why it holds: [`common.md`](common.md) § Credential storage protects the identity secret, which this app never holds (rule 1); what rests is bearer-class — a DPoP key, a refresh grant and grant-wrapped scope keys under the `ThirdParty` ceiling, revocable in one row and audited — narrower custody than the fleet's two sanctioned unattended precedents at the same user boundary (the sync agent's `BackupKey` on `0600` disk, [`sync-agent-credentials.md`](sync-agent-credentials.md) § Credential model; the install device secret, `fauna_sync_engine::engine_lifecycle::load_or_create_install_device_secret`); and against the one process that matters — the LLM host, which launched this shell as the same OS user and sits outside Fauna's trust boundary (§ Hosting cases) — the file arm is no weaker than the keyring arm, since Secret Service and Credential Manager draw the same same-user line. Rejected: a passphrase in the host's configuration (rule 7, the configuration invariant); unlock delegation over a `fauna-ipc` door from a co-resident first-party app (a headless box has no resident custodian — tui over SSH is not resident, and the sync agent is bearer-only and faces the identical at-rest question with no passphrase to delegate — so the door adds a threat model for no custody gain and a second mechanism where the fleet has one); and connect-per-launch (a human step on every host session, since MCP stdio servers are launched per session, an orphaned grant per launch, and no custody gain — the in-memory token is as readable by the same-user host as the file). The sealed passphrase arm stays tui's: this app has no surface for it and never creates a `.sealed` file. The arm is a shared constructor beside tui's in `fauna-credential-store`, for every process with no human surface and no identity secret; the sync agent adopts it under the custody its own doc already sanctions.

**Local content work.** The device shell holds the user's granted scope keys, so it opens sealed content locally like a native app and can run the on-device index for its granted scopes (`search` is served on this shell with no nest-side help). Folder operations go through the same `fauna-ipc` seam the sync agent exposes when the agent is present, and through the folder doors otherwise.

## The nest-hosted shell

The same catalog compiled as a component against the `fauna:plugin@0.1.0` world: `nest-api.call` is its WS-RPC, `holder.open-grant` opens the user's grants without the secret ever entering the component, `ingress.handle` receives the MCP requests the nest terminated — so MCP's transport is the plugin ingress, and MCP's authorization is the nest's own issuer, which already speaks the stack MCP requires (the Client ID Metadata Document, PAR, DPoP, RFC 9728 protected-resource metadata). A remote host connects to `https://<nest>/…` (the exact path is the build row's, under the ingress rule) and signs in through the ordinary consent ceremony; the nest serves protected-resource metadata pointing at itself.

**It ships inside the nest** (ruled 2026-10-17; refutable until first build): the component is carried in the nest binary, listed on the Bridges page as a first-party plugin an admin installs with the ordinary install card — the install creates the install row and starts the runner — and each user then consents from their own app, which is what binds that user (install ≠ grant, [`../third-party.md`](../third-party.md) rule 3). A deployment therefore has it out of the box, with no catalog download and no Docker.

**What it can serve is the materialization tier's question.** A nest-hosted principal may hold reads over the user's pre-existing sealed scopes (TP4), but a component on the nest has no local index and no device: served *search* over sealed content, and any derived view it keeps between requests, is exactly the materialization grant [`../encryption-at-rest.md`](../encryption-at-rest.md) § Readable classes class 4 defines — so this shell's build row is **gated on that design** and lands after the device shell. Until then the shell can serve what a stateless per-request read serves (open a scope, answer, forget), which is most of the ledger's *served* column.

## Prompt-injection posture

The LLM will read hostile text and may be steered by it; the design assumes it and bounds the blast radius in four layers, none of which trusts the model: **(1)** the grant bounds reach — a read-only mail grant cannot send, a feed grant cannot touch mail; **(2)** truthful tool annotations let the host confirm or refuse writes and destructive calls; **(3)** the oracle's deny list and its hard-constant rate ceiling bound identity-bearing acts regardless of what the model asks for; **(4)** every operation lands on the roster's audit record the owner reads from their app. Two rules of the catalog's own: a tool result carries content as **data** (MCP content blocks), never text that addresses the model — the catalog adds no instruction of its own to any result, so a result containing an imperative is the content's, which the host is free to treat as a detection signal; and no tool chains another tool on the content it read (no "act on what this mail says" verb) — chaining is the model's, under the host's confirmation.

## Test surface

The e2e client token is `cli`; its driver speaks MCP's JSON-RPC over stdio, or over the loopback HTTP listener, with the standard library — no MCP client dependency in the harness. Tier placement follows [`../testing.md`](../testing.md) § The four-tier taxonomy: the catalog crate's handlers tier_1 against a mocked principal session; the consent journey tier_3 across a real nest, tui approving the typed code, and the cli reading what the arm grants and refused what it does not; the nest-hosted shell tier_3 through the plugin host and the issuer with a real OAuth ceremony. Every plane's build row proves its arm red-first: the tool refuses before the grant and serves after it. The MCP protocol layer itself is either the official Rust SDK admitted through the dependency bump queue or a minimal in-tree JSON-RPC over the two transports; the first build row decides with the owner and files the need — MCP's revisions move fast (the WIP-1 survey's one caution), which argues for the SDK if it passes review.

## Architectural rules

1. **The app never holds an identity key or a nest bearer.** Its credential is the principal session's DPoP-bound token; its keys are the wraps its grants carry. A design that puts an Ed25519 actor key or a bearer in this process has made it the eighth key-holding app the ruling rejected.
2. **Reach is the user's grants under the `ThirdParty` ceiling, never a tool allowlist in this crate.** A tool the grant does not cover is refused by the nest; the catalog's arm markings are a courtesy to the host, not the enforcement.
3. **One catalog crate; a shell is a transport and a host, nothing more.** A tool that exists in one shell and not the other is drift.
4. **Tools are page-named manager verbs, never gestures, never a second taxonomy.** A new tool declares its ui.yaml page or it does not compile.
5. **Sovereign acts are never tools.** The deny list, the onboarding ceremony, the grant plane and deletion are reads and coaching prompts at most.
6. **No secret ever crosses the model boundary.** The connect flow returns a `user_code` the human types elsewhere; nothing the credential store holds is a tool result or argument.
7. **Every user-facing knob is app UI + nest state.** The device shell's command line is the host's wiring (transport only); the nest-hosted shell's role is its principal row; neither reads a config file.

## Don't do these

- **Don't build this as a mode of tui, or as a `--mcp` flag on any app.** The reserved-name ruling and § The principal shape both forbid it: a key-holding process is the wrong principal.
- **Don't mint the principal anywhere but the user's own consent act** — no first-run "trust this binary" on the nest, no admin-side mint for a user, no bundled credential.
- **Don't hand the LLM a recovery kit, a seed, a passphrase or a `user_code` to enter on its own behalf.**
- **Don't add tools that drive widgets** (`click`, `type-into`) — that is the e2e agent's contract, not a user surface.
- **Don't reach a plane without its arm.** A kind served to this app's principal outside the `ThirdParty` ceiling is a hole in the ceiling, not a feature.
- **Don't keep a derived view on the nest-hosted shell without a materialization grant.**
- **Don't add a ui.yaml ID for this app.**
- **Don't author an `argv` command beside the catalog.** The command tree is derived from the tools; a command with no tool is a second taxonomy and an operator surface in the making.

## Open decisions

1. **The Client ID Metadata Document's URL and publication.** A `fauna.build` path under the organisation's control, published through the public-texts process ([`../public-texts.md`](../public-texts.md)) since it is a text the public reads; the dev carve-out (`http://localhost/plugins/<stem>`, loopback only) serves development meanwhile. Its first wording is the device shell's build row's draft.
2. **Conversations for a device principal — RULED 2026-10-17: the co-resident first-party app as a local oracle.** The signed-in first-party app hosting the account's conversations engine on the same device is the custodian of two keyless oracle classes, `conversation.read` and `conversation.send`, served over a second `fauna-ipc` door; the per-room export and the bridge-class membership are rejected there, and the room's class does not move. Owner, with the revoke bound, what the principal's process holds and what each shell serves: [`../../behavior/conversations-oracle.md`](../../behavior/conversations-oracle.md).
3. **The human `argv` front-end — RULED 2026-10-17: approved**, the third shell over the catalog, specified in § One catalog, many front-ends → *The `argv` shell*; built 2026-10-18 (§ Implementation status today).
4. **The consent card's copy for this app** — that what is granted reaches whichever assistant the user connects — is a public text and a public-texts request row when the device shell lands.
5. **Where exactly the nest-hosted shell's MCP endpoint sits** under the ingress rule, and whether its protected-resource metadata is the issuer's discovery document or a sibling — the build row's, within [`../../behavior/authorization-server.md`](../../behavior/authorization-server.md)'s issuer rules.
6. **How the device shell unlocks the headless credential store — RULED 2026-10-18: the unattended arm.** A `0600` file under this app's own data dir, auto-selected when no OS secret store is usable, declared in the `connect` answer, no passphrase and no human step; a passphrase in the host's configuration, unlock delegation over `fauna-ipc` and connect-per-launch are rejected in § The device shell → *Credentials*, which owns the ruling.
