## Credential model

The agent is a **bearer-only + minted-capability host** (`EngineCredential::BackupKey`; never the identity seed — `key-material-hierarchy.md` rules #6/#7). Two ratified extensions beyond the 2026-07-17 windows shape:

- **The capability persists** in the per-user platform secure store via `libs/fauna-credential-store` (namespace `fauna-sync-agent`): macOS login Keychain; linux Secret Service, with the `0600`-file backend sanctioned for headless boxes (an unattended agent cannot answer a passphrase; `BackupKey`-on-`0600`-disk is narrower custody than the deployment-3 daemon's sanctioned seed-in-TOML, same user boundary); windows Credential Manager (`fauna-credential-store::win_credman`, same arm as `tui.md` § Credential storage — verification closed 2026-07-20). Rationale: an agent that must run app-dead cannot depend on a login-time push — the FP extension's Keychain precedent, generalized. In-memory copies stay `Zeroizing`; un-provisioning deletes the record and stops engines. The identity-holding app remains the only minter.
- **Content keys are not provisioned (ruled and built 2026-09-27).** The capability carries the `BackupKey` and a bearer and nothing per set: the agent reads the account's folder-key custody itself — through the account store it mounts under that key (`fauna.state.folder-keys`, since 2026-09-30; the `__config` custody under `ConfigClient::seedless` before it) — and resolves every bound, served and foreign set's keys in-process, re-reading at its own edges. **The reach is the fleet-only rung's, not a per-kind one (stated 2026-10-02):** every `GenerationTip`-sealed kind — `fauna.state.backup`, the succession ledger — opens to the agent's wrapped writer key exactly as `folder-keys` does (`BackupKey` alone opens no tip-sealed row; what admits the agent is its enrollment and the wrap a seed-holding sibling supplies — [`../owner-key-material.md`](../owner-key-material.md) § Path A-sibling-2), and what the agent *reads* is what it holds a reader for ([`sync-agent.md`](sync-agent.md) § Control plane split names the two it deliberately does not). The app-pushed `content_key_bindings` blob and its re-push are the older shape, retired by the build; a capability that still carries the retired key decodes with it ignored. Owner of the ruling and the edges: [`../../behavior/on-demand-files.md`](../../behavior/on-demand-files.md) § Shared sets on a capability host (decisions 1–2, *One mechanism*); the advertised transition: [`sync-agent.md`](sync-agent.md) § Control plane split.
- **Agent-side bearer renewal — the device-scoped renewal grant (mechanism ratified 2026-07-19).** The 2026-07-19 flow-trace settled the design fork: the bearer plane has **no presentation-renewal** — the only production token mints are `fauna.auth.{handshake,verify}` (`bins/fauna-nest/src/auth_core.rs`), both requiring the identity keypair — so the additive grant path is the mechanism. At provision, the identity-holding app mints a fresh Ed25519 **renewal device keypair** (never the identity seed; the [`devices.md`](../../behavior/devices.md) § DeviceAuthorization device-level-keypair concept applied), signs a `DeviceAuthorization { actor_id, device_key, capabilities: [RenewBearer], expires_at: None }` with the root key, and registers it on the agent's `sync_devices` row via the authenticated kind **`fauna.sync.device_grant.register`**; the private half rides the additive `SyncCapability.renewal_signing_key` IPC field (same trust boundary as `backup_key`) and persists in the credential store with the rest of the capability. App-dead, the agent runs its own TTL loop: near bearer expiry — a lead owned by `fauna_protocol::auth` and pinned strictly under the nest's `TOKEN_TTL_SECS`, planned on the `expires_at` every provisioned bearer carries ([`sync-agent.md`](sync-agent.md) § Implementation status today owns that seam), because this loop is the token-lifetime contract's third participant ([`login.md`](../../behavior/login.md) § the direct-auth kind owns the contract and both failure directions) — it opens the ordinary anonymous WS and calls the pre-identity kind **`fauna.auth.device_handshake`**, signing `DEVICE_HANDSHAKE_V2 ‖ actor_id ‖ device_key ‖ timestamp_be ‖ nest_id ‖ nonce` with the renewal key (domain-tagged from day one — `fauna_protocol::sig_domain`; nest-bound since 2026-09-23, the identity read off the connection first — [`../../behavior/login.md`](../../behavior/login.md) § Binding the nest owns the binding; the direct-auth ±30 s drift window, replay guard, active/lockout checks all apply). The nest verifies the stored grant (root-key envelope signature + `RenewBearer` capability + key match) and mints an ordinary 1-hour session bearer, visible in `fauna.sessions.list` like any session and labeled there with its minting device key (the additive `minted_by_device` field — what lets the sessions list distinguish a device-grant renewal from an app sign-in). **Revocation (hardened 2026-08-15):** deleting the device (`fauna.sync.devices.delete` — the existing devices UI) ends **every** authority the grant conferred, in one gesture: the grant row is deleted, the grant's device key is **tombstoned** in `revoked_device_grants` atomically with the row delete (so replaying the same root-signed grant over `fauna.sync.register` + `fauna.sync.device_grant.register` can never re-attach it, and the tombstoned key can never mint again — the nest keeps a memory of the revocation), and every session the grant already minted is revoked from the token store (each mint is tagged with its minting device key, so the delete revokes exactly those sessions and no others — an app sign-in survives a device delete). Before 2026-08-15 revocation was only the row delete — no tombstone, so a deleted grant was not permanently ended; the tombstone is what makes "revocation is the control" true against the threat it names. Legitimate re-enrollment is never blocked: every provision mints a **fresh** renewal keypair, and the tombstone keys on the revoked public key alone. Un-provisioning deletes the agent's persisted copy. The grant deliberately carries **no expiry** — an expiring grant would silently stop app-dead sync, the exact breach this closes; revocation is the control, and as of 2026-08-15 it actually is (pinned by `bins/fauna-nest/tests/conformance_device_revocation.rs`). ⚠ **"In one gesture" survives a mint racing the delete, and that took a second fix (2026-08-15).** Checking the revocation memory *before* the mint is not sufficient on its own: the check and the token insert are not one transaction, and an inserted token is live for its whole TTL (`TokenStore::validate` consults only `expires_at`). The mint therefore **re-reads the revocation memory after the insert** and drops the token it just created. That is total rather than merely narrower, because the delete commits its tombstone strictly before it sweeps: either the tombstone is visible to the post-insert re-read (the mint removes its own token) or it commits after that read, in which case the sweep necessarily runs after the insert and removes it. Pinned by `auth_core::device_auth_tests::a_mint_racing_its_own_revocation_leaves_no_live_bearer`, which enters the window through a `#[cfg(test)]` causal barrier rather than by out-waiting a race, and drives the real delete handler so the ordering the argument rests on is production's. **Compat (I4):** both kinds are additive — against an older nest the register/handshake fail typed and the agent degrades to app-pushed `RefreshBearer`; an older agent ignores the unknown IPC field. The minted bearer is a full session token (a sync-scoped token tier is a possible future narrowing, deliberately not built here). App-pushed `RefreshBearer` remains the immediate path while the app runs. (The FP extension shares this mechanism via `FfiBearerProvider` — its Keychain-mediated staleness problem is the same bug.) **The renewal is scheduled on the agent's own clock (stated 2026-09-23; [`login.md`](../../behavior/login.md) § Token lifetime on the client's clock).** Every deadline the loop plans on is this machine's: an app-pushed `expires_at` comes from a mint on the same machine, already anchored at receipt, and `fauna_anon_client::mint_bearer_over_device_handshake` anchors `now + expires_in` at receipt like every shared mint, so the lead never compares the nest's absolute deadline against the local clock — a machine hours off the nest neither hot-loops renewals (ahead) nor serves a dead bearer (behind). What stays clock-bound is the **ceremony**, deliberately: `fauna.auth.device_handshake` is a machine-to-machine mint and keeps the direct-auth ±30 s drift window, so on a machine whose clock is more than 30 s off the nest's the app-dead renewal is refused (`fauna.auth.timestamp_drift`) and retried on the loop's backoff, and the bearer is kept fresh only while an app runs and pushes `RefreshBearer` (whose own mint is the clock-immune silent challenge). That residual is accepted rather than closed: an unattended machine's clock is kept by the OS's network time sync, unlike a user's device clock set by hand, and closing it would need a device-key twin of the silent challenge — a new pre-identity kind no current need justifies.
- **A refused renewal is terminal (ratified 2026-09-27; the report made sticky and the wording brought to the one-credential shape 2026-10-01, on the user's 2026-09-30 ruling; the sticky half built 2026-10-03 — § Implementation status today).** The renewal loop retries every failure on its backoff *except one*: `fauna.auth.not_registered` answered to the **store principal** — the machine's only renewal key (the RULED 2026-09-28 block below, decision 1), so there is no second key whose answer could differ. That answer means the nest holds no grant for this machine any more — the device was removed from the devices list, the nest was factory-reset, or the enrollment never registered — so no retry can succeed, and retrying for ever is how a dead agent hammered the production nest on 2026-09-24. The agent then **drops its bearer** (the capability stays, with an empty bearer: `bearer::mark_renewal_refused`), persists that, and **mints nothing more on its backoff**. Because every client the agent runs reads its bearer from that one slot, the empty bearer stops them all *before their sockets* — the control plane, every folder engine's client, the custodian's reads — and the account host takes its mount (and the device-principal leg riding the same dead grant) down. The rule is the agent's own: an app's session refusing `not_registered` mid-session is already the session-ending `SignInRefused` verdict (`transport-connection.md` § Connection lifecycle, the supervisor-stop record), which this matches rather than duplicates. Pinned by `renewal::tests::not_registered_on_the_principal_is_terminal`, `…::a_transport_failure_is_not_terminal` and, end to end against a fake nest, `custodian::tests::a_refused_renewal_dials_nothing_until_an_app_re_arms_it`.
  - **What the agent dials and what it reports are two separate states (user-ruled 2026-09-30).** *Dialling* follows the bearer slot, as above: any app provision or `RefreshBearer` writes a real bearer into it and re-arms every client, so while an app runs, sync continues on the app's own session. *Reporting* follows a **refusal record**, which a pushed bearer never clears: the agent answers `ServiceStatusInfo::needs_reenrollment = true` from the refusal until **a renewal under the principal succeeds**, and nothing else ends it short of un-provisioning. The reason is measured: every signed-in desktop app pushes `RefreshBearer` on its 30 s convergence tick (`fauna_ipc::convergence`), so a report read off the bearer slot was true for at most ~30 s in each hour while an app was open to show it, and continuously only while none was — and an app's own bearer is evidence about the app's session, never about whether *this machine's* grant exists. What the report is for — the *Not enrolled* reading of `sync-agent-status` — is owned by [`sync-agent.md`](sync-agent.md) § Local agent health.
  - **The refusal record names what was refused, never a secret.** It holds the nest URL, the principal's **public** key, and whether the enrollment ceremony's registration latch (`PrincipalSlot::grant_registration_row`, the evidence `renewal::principal_is_registered` already reads) said *registered* at that moment. It is agent-private state, not app↔agent contract: it persists beside the capability in the agent's credential-store namespace under a key of its own — so the refused state survives an agent restart exactly as the capability does, and `SyncCapability`, the IPC type an app fills, gains no field an app could set — is mirrored in memory so the status reply stays a field read, and is deleted with the capability on un-provision. An absent or unreadable record reads as *not refused*.
  - **A refused agent asks the nest again in exactly two cases.** (1) **At once, when the evidence differs from the record** — a different nest, a principal key it has not been refused on (the successor principal a removed machine returns as: [`../account-replica-posture.md`](../account-replica-posture.md) § The store device principal → *Principal succession after a device delete*), or the latch now reading *registered* where the record says it did not (the ceremony's nest legs landed after the refusal — bound 6(a) of the RULED 2026-09-28 block below — or a device-limit wait ended). One probe per distinct evidence: a probe that is refused rewrites the record to the evidence it was refused on, so the same dead key is never asked twice on this path. The provision and `RefreshBearer` handlers wake the renewal loop while a record stands, which makes *at once* one convergence tick; the evidence read is a credential-store read on the loop, never on the status path. (2) **Otherwise only on the ordinary schedule** — at the renewal lead of whatever bearer an app last pushed, which is at most one attempt per bearer lifetime and none at all while the bearer is empty. So an app-dead refused agent still dials nothing, and the 2026-09-24 hammering cannot return by either path. A refused attempt drops the bearer again, as the first did (the app's next tick re-arms it); a successful one writes the minted bearer, deletes the record and clears the report.
  - **Recovery is the user signing in again on the machine, and nothing else** ([`../nest/common.md`](../nest/common.md) § Client-state recoverability). The app's bearer restores sync at once, its enrollment pass re-enrolls the machine — as a successor principal after a removal, by a fresh registration after a factory reset and re-claim — and the agent's next probe clears the report with no further gesture. A recovery that changes none of the three pieces of evidence clears on case (2)'s schedule instead.
  - **A rejected credential asks at once (ratified 2026-10-03).** Left to its schedule the renewal loop asks only at the renewal lead of the bearer in the slot, and a bearer an open app keeps pushing never reaches its lead — so two answers the nest gives the agent's *readers* are routed to the loop as a request to mint now. (a) **A `401` to the slot's bearer** at any capability-bearer client (the WS upgrade, a 4401 close, a content call): the client hands the rejection back through the slot it read the bearer from (`bearer::CapabilitySlot`), naming the bearer it presented. (b) **`fauna.auth.not_registered` on the account host's device-principal leg**: the leg signs `fauna.auth.device_handshake` with the very key this loop renews with, so its refusal is the renewal's own answer heard early. The loop then mints at once and the ordinary arms decide — a minted bearer re-arms every client (the rejecting reader waits a bounded time for the answer, so its retry carries the new bearer), `not_registered` is the terminal refusal above, any other failure stays on the loop's backoff. **The leg's refusal enters the terminal state only through that mint, never directly:** the loop is the single decision point, so a leg refused mid-ceremony (a mint racing the enrollment's nest legs) cannot drop a bearer the nest would still renew. **Bound: at most one such mint per distinct slot bearer.** A rejection naming a bearer the slot no longer holds, one about a bearer the loop has already asked for, or one arriving while the bearer is empty asks nothing — so a reader or a leg retrying on its own ceiling never becomes a mint per retry. **The leg follows the refusal, not the slot:** it signs as the refused principal, so while the refusal record stands the account host hosts no device-principal leg — the runtime rides the capability bearer, as on a machine no app has enrolled — and an app's re-armed bearer brings back the capability clients, never the leg (`account_host::HostInputs::device_leg`; the renewal that ends the refusal re-mounts with it). Before 2026-10-03 neither answer reached the loop: `CapabilityBearer` had no `notify_401`, so a supervisor re-presented the dead bearer at its 60 s ceiling until the renewal lead (up to ~55 min, and never while an app kept pushing), and the leg's refusal only voided the registration latch while it redialled at its own ceiling. Pinned by `bearer::tests::a_401_hands_the_presented_bearer_back_to_the_renewal_loop`, `renewal::tests::a_rejection_asks_once_per_distinct_bearer` and, against the real binary and a real nest, `agent_process_tier3::a_refused_device_leg_ends_the_credential_while_the_app_bearer_still_works`.

- **The signed-out reconcile (ratified 2026-08-12).** The two extensions above are what make a lost teardown message dangerous: together they mean the agent's authority to serve an account **survives the app, the session, and the machine's power state**, and the only thing that ends it is one best-effort local `UnprovisionCapability` per teardown path. A *wedged* (not dead) agent that misses that message, or a connect that times out under load, therefore used to leave a signed-out account's engines serving indefinitely and reviving on every reboot — because the grant carries no expiry, nothing else expires either, and **nothing reconciled what the agent serves against the box's signed-in state**. The remedy keeps the no-expiry decision intact (an expiring grant would silently stop app-dead sync — the breach that decision exists to close) and adds the missing reconcile instead:
  - **The app records the sign-out durably *before* it sends the message.** `SyncAgentProvisioner::unprovision` writes a `SignedOutMarker { actor_id, signed_out_at_ms }` into the agent's own credential-store namespace (`fauna_ipc::sync`, which owns the namespace, the keys, the record framing and the decision, because two processes agreeing on a store location *is* app↔agent contract). Both processes build that store through `CredentialStore::new`, so an e2e `FAUNA_KEYRING_APP` redirect moves the capability and its marker together, never one without the other. Writing before sending is the whole point: the durable record must not depend on the message it is insurance for.
  - **The agent revokes itself against that record, on its own evidence, at two points.** At **boot**, `restore_authorized_capability` refuses a marked capability and deletes it, so a second reboot cannot re-litigate it. In the **renewal loop**, the same check runs ahead of every renewal decision, which is the arm a reboot cannot supply: an agent that never restarts would otherwise never re-read its authorization. That loop's sleep is capped so the check runs at least every 5 minutes rather than once per bearer lead (~55 min).
  - **The decision is ORDERED, never a latch** — `capability_is_signed_out(cap, marker)`, true iff the marker names the capability's own actor **and** the capability was provisioned at or before the sign-out. A re-provision (signing back in) outranks the marker by construction, so clearing the marker is an optimization rather than a correctness requirement — which matters, because `SecretStore::set`/`delete` are infallible and a failed clear is undetectable. A flag would have inverted the original breach: a stale one would silently stop a signed-in user's sync. Every capability the app pushes is stamped (`SyncCapability.provisioned_at_ms`, a required field — a record without it fails to decode), not just the first, or later provisions would look older than they are; a capability built but never stamped reads as time 0 and so loses to any marker — the fail-safe direction.
  - **The marker may only ever *remove* authority, never grant it**, so every ambiguous read leaves the agent serving exactly as before: no marker, an unreadable marker, a malformed actor id on either side, no credential store. And it is actor-matched because the slot is single — a sibling app sitting at account A's onboarding screen must not tear down account B's sync.
  - **Not in scope, deliberately:** this bounds the *local* failure. A nest-side revoke at sign-out (deleting the `RenewBearer` grant, which would bound the window at one bearer TTL even against a machine that never runs the app again) needs a narrower kind than today's `fauna.sync.devices.delete` — that deletes the whole device row, which signing out of one app should not do. **That kind now exists as a ruled design: `fauna.sync.device_grant.revoke`** (the ruling under the W5 (account-data-plane.md § Workstreams)-convergence bullet below — its app/user authorization arm is exactly this consumer) — **and the sign-out leg is BUILT (2026-09-14; § Implementation status today → the RULED 2026-09-14 entry).** A sign-out retires, nest-side, both credentials this machine registered for the account while it still holds them: the **store principal's** grant, as the account runtime's own last act before its store closes (proof of possession by the writer key — `AccountStoreHandle::shutdown_for_sign_out`, reached through the shared stop's `StopReason::SignOut`), and the **legacy renewal grant** this provision minted, from the provisioner's teardown over the session arm (`SyncAgentProvisioner::unprovision`). The runtime's retirement first stamps the store as signed out, ahead of the device's own fleet removal, so no runtime on that store reads the removal as one to heal from ([`../account-replica-posture.md`](../account-replica-posture.md) § The store device principal → *Principal succession after a device delete*, decision 1, the third trigger, owns it). The principal's retirement also vacates its placeholder row (decision 2's 2026-09-14 refinement, below). An account switch — after which the slot survives — retires nothing: the same key is loaded again at the next sign-in, and a tombstoned one would read as removed-from-account and cost a successor mint, so every host states which of the two it is doing and the shared stop never guesses.

- **W5 convergence into the store device principal (ratified 2026-08-10, refutable until W5 code — resolves the account-data plane's T11).** The renewal grant's shape becomes the *machine's* model: the account-data plane's store device principal ([`../account-replica-posture.md`](../account-replica-posture.md) § The store device principal) is one Ed25519 device keypair per (machine, account), its root-signed `DeviceAuthorization` persisted in the shared per-user credential slot (that doc's T10). When W5 lands, the agent stops minting its own renewal keypair at provision and mounts the shared slot instead: the store principal's authorization carries `RenewBearer` among its capabilities, `fauna.auth.device_handshake` renews against it unchanged (same domain tag, same nest-side verify), and the machine appears **once** in the devices list — one `sync_devices` row per machine, not one per process. Provisioning over IPC still pushes the engine-specific remainder (set bindings, content-key bindings, predecessor keys per bound (3)); the principal itself comes from the slot, so `SyncCapability.renewal_signing_key` becomes a compat field for pre-W5 agents. Migration is client-driven and additive: the first identity-holding app to enroll the machine under W5 mints the store principal and registers it; an un-upgraded agent keeps its old grant and old slot until then, and an older nest that lacks nothing here — both kinds predate this — needs no change.

  ⚠ **Refutation, recorded 2026-08-15 while building W5.5b** (T11 was ratified *refutable until W5 code*; the refutation belongs here, in the owner section, rather than being silently diverged from). This bullet also had that first app **delete the agent's old agent-only grant row** (*revocation = device-row deletion, as ever*). Building it showed that step is unsafe **as an app-side action**, and it is now owed to a later slice:

  - **The app cannot know when the agent has converged.** A grant row is not bookkeeping — deleting it revokes, and since the 2026-08-15 revocation hardening above *tombstones*, the very key the running agent renews with. An app deleting on its own enrollment is guessing that the co-located agent is a W5 build that has already switched to the principal.
  - **On linux that guess is usually wrong**, and § Local agent health says so: `SystemdAgentSpawner` never restarts an already-active unit, so *Restart pending* is the common, expected state after an upgrade. New app + **old still-running** agent is therefore the normal post-upgrade pairing, not a corner — and deleting the old row there stops app-dead renewal within one bearer TTL (≤ 1 h), silently, until the user happens to reboot. That is precisely the breach the no-expiry decision above exists to prevent, re-entered from the other side.
  - **The safe ordering inverts the actor:** the agent deletes its *own* legacy row once it has actually renewed under the principal at least once — the only process that observes the convergence. That is a new self-revocation authority for a bearer-only process, so it was a design question, deliberately not decided in the refutation.

  **RULED 2026-08-15 — the refutation is resolved: the agent self-retires, over a new narrow grant-revoke kind, and the app's legacy mint gains a negotiated stop.** Five decisions, each with its reason:

  1. **Yes, the agent may revoke its own legacy grant — self-revocation of one's own credential confers no new authority.** The caller must prove possession of the very key being retired (below), and possession of that key already *is* the authority the grant confers (it mints bearers); a revoke can only destroy the caller's own power, never reach anyone else's. The retirement is also a **security fix, not bookkeeping**: a machine showing two `sync_devices` rows makes the user's revocation gesture incomplete — deleting the principal's row leaves the legacy grant renewing (the b2a fallback works *against* the user exactly when it matters), so "one gesture ends the machine" is only true once the machine has one row.
  2. **The kind is `fauna.sync.device_grant.revoke` — the grant named by its device public key, never the whole device row** (`fauna.sync.devices.delete` stays the devices-UI user gesture). Semantics are exactly the 2026-08-15 hardening's triple, factored: delete the grant row, tombstone the key in `revoked_device_grants` atomically, revoke every session that key minted. Two authorization arms, either sufficient: **(app/user arm)** an identity-authenticated session of the owning account — this is the narrower kind the signed-out reconcile's *"captured, not built"* nest-side sign-out revoke has been waiting for, so the two needs share one kind; **(self arm)** a proof-of-possession signature by the named device key over a domain-tagged payload (`fauna_protocol::sig_domain`, `DEVICE_GRANT_REVOKE_V1 ‖ actor_id ‖ device_key ‖ timestamp_be ‖ nonce`, the `device_handshake` drift/replay/lockout gates), presented on any authenticated session of the account. Additive (I4): an older nest fails it typed and the caller degrades to keeping the row — today's two-row state, safe. **The app/user arm gains a second consumer and one refusal (ruled 2026-10-01; built 2026-10-01 — `fauna_account_plane::removed_grants`, and the refusal in `device_grant_revoke_handler`):** a runtime revokes over it, at every nest it completes, the grant of a device its merged state reads removed ([`../account-data-taxonomy.md`](../account-data-taxonomy.md) § The generation machinery → *Fleet-scope reclamation*, clause (4) → *The nest half follows merged state* owns the rule), and that arm refuses the key of a guardian-marked row ([`../../behavior/family-safety.md`](../../behavior/family-safety.md) § Full visibility for young children → *The device marker* owns the refusal); the self arm is unchanged.
  3. **The evidence bound is retry-after-each-principal-renewal, no latch, no new timer.** While the agent still holds a local legacy key, each successful `fauna.auth.device_handshake` mint under the *principal* key is followed by a revoke attempt for the legacy key on the same session; on nest-confirmed success (a not-found answer counts — the user already deleted it) the agent deletes its local legacy copy, whose absence is the terminal state. A crash anywhere re-runs the sequence at the next renewal; an old nest just retries later on the renewal cadence. No durable marker, nothing to reconcile.
  4. **The app's legacy mint stops only by negotiation, never by guess.** At provision, the app skips the fresh legacy mint+register iff the machine's store principal exists in the shared slot **and** the agent's IPC has advertised principal support (an additive capability field on the provision exchange; absent = older agent). An un-advertising agent keeps receiving the legacy mint exactly as today — its two-row state persists and self-heals when it upgrades (step 3 retires the leftovers). Stopping on slot-presence alone was considered and REJECTED: an older agent given a capability with no renewal key it can use is app-dead-renewal silently dead — the breach this whole section exists to prevent. Pushing the principal's writer key *as* `renewal_signing_key` to bridge old agents was also REJECTED: it duplicates the machine's primary credential into a second namespace for a transitional case the negotiated gate handles without custody widening.
  5. **Downgrades heal through ordinary provision, and `renewal_signing_key` stays a compat field.** After retirement, a downgraded (pre-W5) agent boot-restores a capability with no usable legacy key and app-dead renewal stops **loudly** (renewal-loop errors, backoff) until the next app provision mints a fresh legacy keypair — the tombstone keys on the revoked public key alone, so re-enrollment is never blocked (the hardening's own guarantee; the build verifies this path end-to-end). The field's eventual removal is a version-compat call (`version-compatibility.md`), not this ruling.

  ⚠ **One build-time inventory is a precondition, not an afterthought:** everything nest-side that references the legacy row or its device id — the backup-destination registry's `device_id` match (§ Control plane split's worked example), the sessions list's `minted_by_device` labels, the devices-list projection — must be enumerated before the delete lands, so retiring the row orphans nothing (the expected resolution is that those references either already key on the principal's row post-enrollment or are display-only, but that is verified, never assumed).

  ⚠ **The inventory RAN (2026-08-15, the blocking first leg) and refuted its own expected resolution — so the build retires the GRANT and never the row.** What it found, verified rather than assumed:

  - **There is no agent-only `sync_devices` row.** The legacy grant sits on the **machine's real sync device row**: `fauna_client_sync::setup_renewal_grant` calls `fauna.sync.register` and `fauna.sync.device_grant.register` under *the same* device id — the app's stable `device.db` id (`fauna_sync_engine::engine_lifecycle::load_device_id`; linux `sync::device_id`, tui `media::device_id_hex`, and the id every provisioned agent presents as `SyncCapability.device_id`) — and with the **user-visible label**. The prose above (and T11's "one per process") pictured a separate agent row; code has one row shared by app and agent, exactly as `apps/fauna-linux/src/sync.rs` says it intends ("so the nest sees one device").
  - **Deleting that row would orphan eight references and then heal wrong.** `folder_members.device_id` (primary key), `sync_changes.device_id`, `folders.source_device_id`, `folder_destinations.device_id`, `snapshots.device_id`, `upload_leases.device_id`, `sync_conflicts.device_id`, `sync_conflict_candidates.device_id` — **none of them an SQL foreign key**, so a row delete orphans silently instead of cascading. And `SyncClient::record_change`'s `device_unregistered` self-heal would re-register the row under `SELF_REGISTER_LABEL` at the next change, replacing the user's device name with a placeholder.
  - **The two named display references are clean.** The custodian's assignment read (`bins/fauna-sync-agent/src/custodian.rs::read_assignment`) matches `SyncCapability.device_id` against the `backup_destinations` registry — a separate table the retirement does not touch. `minted_by_device` is display-only in `fauna.sessions.list`, and the retirement revokes exactly the sessions the retired key minted and closes their sockets (`AppState::revoke_device_authority`), leaving app sign-ins alone.

  So decision 2's *"never the whole device row"* is not a nicety — it is the only safe shape, and `fauna.sync.device_grant.revoke` clears the `auth_device_key` / `auth_grant` columns while the row, its label and its memberships stay. **The consequence for T11 is recorded in § Implementation status today: retiring the grant does NOT make the machine appear once in the devices list, because the second row is the *principal's*, not the agent's.**

  **Refinement 2026-09-14 — a retirement VACATES the grant's own placeholder row.** Decision 2's *never the whole device row* protects the row the user recognises: the named row, whose id is the install's own and carries the label and the `folder_members`. The writer-pub-hex placeholder (decision 3) is the one row that is *not* that — it exists only to carry the credential until the adopt moves it, its id IS the key, and a placeholder with no grant is roster junk nothing converges or deletes. So `fauna.sync.device_grant.revoke` now deletes the row named by the retired key when one exists (`sync_storage.rs::revoke_device_grant` → `GrantRevokeOutcome::placeholder_deleted`), with its expected-zero `folder_members` and **regardless of whether the row's columns still held the key** — a row a pre-fix sign-out stranded already reads NULL there, and this is the only call that can ever name it. The adopt's own vacate rule, applied to retirement; the named row is untouched by construction (its id is no key's hex). Why this exists: the whole-suite linux sweep of 2026-09-14 found that the harness's per-test sign-out → sign-in cycle stranded one placeholder per cycle — the product's own sign-out did, and a free-tier user hits the two-device wall on the second cycle — because the sign-out told the nest nothing and the next sign-in's adopt was refused by the legacy grant this very provision had minted (`adopt_target_occupied`, the healthy `AwaitingAdopt` state) until a sign-out erased the key for good. Pinned by `conformance_device_revocation.rs::retiring_the_principal_vacates_its_placeholder_and_keeps_the_named_row`, `…::retiring_a_grant_on_the_named_row_keeps_the_row` and `…::retiring_a_key_sweeps_a_grant_less_placeholder_it_names`. Compat (I4): additive — an older nest clears the columns and keeps the row, the pre-fix state.

  **Built (W5.5b, 2026-08-15): the convergence, and the retirement.** The agent prefers the store principal and falls back to its own pushed seed, per renewal, trying each in turn (`bins/fauna-sync-agent/src/renewal.rs::signing_keys_to_try`) — so one machine renews as one principal wherever an app has enrolled it, with no window in which a machine can renew under neither. Since 2026-08-15 it also **retires the surplus credential**: a mint under the principal is followed by `fauna.sync.device_grant.revoke` for the legacy key on that same session, and a nest-confirmed answer deletes the local copy. `SyncCapability.renewal_signing_key` stays a compat field, populated for the same two reasons as before (an unenrolled machine has no principal — the older-agent reason was retired 2026-09-24 with the compat-remnant sweep's program 3, [`sync-agent.md`](sync-agent.md) § Implementation status today) and now *withheld* — never removed — when the co-located agent advertises that it renews as this actor's principal.

  **Two build-time refinements of the ruling, recorded here rather than silently diverged from** (the same discipline W5.6's role-lock landing used):

  1. **Decision 2's app/user arm is account-scoped, not identity-session-scoped, and cannot be otherwise today.** The nest's `RpcHandler` receives the connection's actor id and no token metadata, and a device-grant-minted bearer is by design "an ordinary session token" (the sync-scoped tier is named above as a deliberate non-goal), so "an *identity*-authenticated session" is not a distinction the handler can draw. It would also buy nothing while any bearer of the account may already call `fauna.sync.devices.delete`, which revokes this grant *and* deletes its device row. The narrowing becomes both expressible and worth making when a scoped token tier lands.
  2. **Decision 4's advertisement is actor-qualified and asserted by the agent, not a bare capability bit checked against an app-side slot read.** `ServiceStatusInfo.store_principal_actor` names the account this agent can renew for as the machine's principal — one positive claim by the process that will actually do the renewing, covering both halves of the ruled `slot ∧ advertises` predicate. Two reasons the shape changed: a bare boolean would have told an app signing in as account B that the agent (still serving A, and holding A's principal) had B covered — stranding B with no renewal credential, the ruled breach reached from a new direction; and the app-side half is not reachable from `fauna_client_sync`, which cannot depend on `fauna-sync-engine` (that crate depends on *it*). The reply field is a cached read refreshed at provision, at boot restore and after each renewal — never a keyring lookup on the status path, which rides the app's convergence tick.

     ⚠ **"Covering both halves" was under-built until 2026-09-13 — the agent's own read of the `slot` half rested on writer-key PRESENCE, which the writer-key mint establishes before any grant exists (finding ).** `refresh_store_principal_presence` answered from `principal_bundle::load_writer_key(..).is_some()` alone — true the instant a writer key is minted, whether or not `fauna.sync.register` + `fauna.sync.device_grant.register` have ever succeeded for it. **Fixed 2026-09-13:** the evidence is now the same content-addressed latch the ceremony itself writes on that registration succeeding (`principal_bundle::PrincipalSlot::grant_registration_row`), read write-free so the answer is correct from the first status call after a restart, exactly as this paragraph already required. **What this does NOT close:** the latch is not nest-scoped — it answers "registered on some nest", not "registered on the capability's own nest". A machine whose principal is enrolled against a different nest than the one this capability names still advertises true; only a live `fauna.auth.device_handshake` success against that specific nest closes that case, which the renewal loop's own preference-order fallback (`signing_keys_to_try`) still absorbs on the agent's own renewal path. This is distinct from the device-delete state: a tombstoned grant's device authorization no longer loads, so it correctly reads as unregistered — not a gap.

  **RULED 2026-08-15 — the device-row topology: the store principal is a CREDENTIAL of the machine's named device row, never a device beside it.** This resolves what the refutation left: T11's *"the machine appears once in the devices list"* — and the converse hole, a user's delete gesture on the row they recognise not ending app-dead renewal. Grounding facts, verified in code by the inventory and re-verified at this ruling: the mint path binds a grant to a *key*, not a row (`device_auth_core` → `get_sync_device_grant(actor, device_key)`), so a grant's residence row determines exactly one thing — **revocation reach** (`delete_device` tombstones the row's own `auth_device_key`); grant columns are row-independent (`set_sync_device_grant` writes any key onto any `(actor, device_id)` row); and the placeholder row was W5.4b's expedient (the ceremony did not know the machine's device id), its own doc comment marking it transitional. Five decisions:

  1. **Target topology: one row — the named one.** The principal's `DeviceAuthorization` registers on the machine's real sync device row (the row carrying the user's label and the `folder_members`); the writer-public-key-hex placeholder row is a transitional state, not a topology. A `sync_devices` row models a device the user recognises; the principal is a machine *credential*, which is precisely what the row's grant columns exist to carry. This makes `fauna.sync.devices.delete` on the one named row structurally end the machine — tombstone the principal key, so renewal and every process bearer it minted die with the memberships — with **no schema change, no at-rest migration, and no new wire shape on the delete path**. Two shapes REJECTED, with reasons: **(a) migrate the machine's sync identity onto the writer key** — an at-rest re-key of eight non-FK reference columns on every nest the account syncs with, under the no-user-data-loss invariant, plus a re-seal of every device-label (the seal salt *is* the device id — `device_label_salt`) and a semantics change to `SyncCapability.device_id` and the this-device marker, all to relabel an opaque internal id; and it inverts the model — the writer key is a credential of the machine, while the install id predates and outlives any one principal (a tombstoned principal must not orphan the machine's row identity). **(b) Project the two rows as one** — the nest holds no machine-binding between them, so projection needs a new linkage column anyway; the duplication persists for every future consumer to know about; and "one gesture ends the machine" becomes a display-layer claim, exactly the shape the 2026-08-15 revocation hardening's history warns against.
  2. **Enrollment targets the machine row directly whenever no live legacy renewal can be displaced — the negotiated advertisement decides, client-side.** The enrolling app resolves the machine's row id: the co-located agent's presented sync device id when an agent exists (an additive `ServiceStatusInfo` field beside `store_principal_actor` — the agent already presents it as `SyncCapability.device_id`), else the app's own stable `device.db` id. It registers the principal's grant on that row directly **iff** no live legacy grant can be displaced: no agent present, or the agent advertises principal support for this actor (the negotiation), and the app itself has minted no legacy grant this provision. A row that does not exist yet is register-created under `SELF_REGISTER_LABEL` (no human has named it; the first real registration supersedes the placeholder label); a row that exists gets **only** `device_grant.register` — grant columns, label untouched. Otherwise — a present, non-advertising agent, i.e. an old agent that may still renew with the legacy key on this very row (single grant columns per row) — the enrollment registers the placeholder row exactly as today, and decision 3 converges it later. Overwriting a *stale* legacy grant whose agent is gone is cleanup, not a breach: the only dangerous displacement is a still-running legacy renewer, which is exactly what non-advertisement detects. Fresh machines therefore converge to one row on day one, even against an older nest — both kinds predate this ruling.
  3. **The transitional placeholder converges by a new atomic move kind — `fauna.sync.device.adopt` — never by composing register + delete.** One transaction: verify the named grant (by its auth device key) currently rides its own self-registration row (`device_id = hex(auth_device_key)`); move the `auth_device_key`/`auth_grant` columns onto the named machine row; delete the vacated placeholder row **without tombstoning** — adopt moves a live credential, it does not revoke one, and `fauna.sync.devices.delete` on that row would tombstone the principal forever. Typed refusals: target row absent; target row's grant columns occupied (a legacy grant still lives there — the caller retries after the retirement clears them). Authorization: the same two arms as `fauna.sync.device_grant.revoke` (an authenticated session of the account; or proof-of-possession by the named key). Caller: the enrolled runtime's registration pass, idempotently on its ordinary cadence — no new timer; a nest-confirmed move re-latches the pass's registration record. An older nest fails the kind typed and the two-row state persists exactly as today — safe, and self-healing on upgrade.
  4. **Delete means "end this machine", and the succession gap is NAMED, not hidden.** With one row, the user's delete is the machine-ending gesture by design. Today the aftermath is a silent strand: the slot still holds the tombstoned writer key, `ensure_enrollment_registered` is latched and never re-mints, `device_grant.register` refuses the tombstoned key (`GrantRevoked`) — so even a fresh identity-holding sign-in never heals renewal, and (worse, pre-convergence) the placeholder row *invites* this by listing as junk ("fauna") a tidy user deletes. Interim ruling, part of the build: the runtime treats the typed tombstone answers (register `GrantRevoked`; renewal not-registered while the slot records a registration) as a **loud removed-from-account state** surfaced to the app — never a silent latched death. The full remedy — minting a *successor* principal for a machine whose store is already bound to the tombstoned writer key — is **RULED at its owner** ([`../account-replica-posture.md`](../account-replica-posture.md) § The store device principal → *Principal succession after a device delete*): revival is a fresh enrollment, never a resurrection — an evidence-gated automatic successor mint at the next ceremony-capable sign-in, an in-place writer rotation in the migration critical section, and the un-pushed tail re-authored under the successor. **BUILT 2026-08-15** — the owner section carries the nine build-time refinements (among them: the probe is grant-first, so a deleted machine's sign-in learns "revoked" without re-creating the row the user deleted; and, since 2026-08-26, its register target follows this decision's third condition) and its § Implementation status today the mechanism + proofs.
  5. **Boundary stated: per-actor, per syncing identity.** Every `sync_devices` row is per `(actor, device)`. A second co-located app that independently engages sync keeps its own named row — a pre-existing multiplicity bounded by the single-slot agent ([`account-scoping.md`](account-scoping.md) § Concurrent instances); the principal rides the machine's *syncing* row as resolved by decision 2. Agent-less enrollments (mobile; a store-plane-only machine) produce exactly one row — the app's own id, placeholder-labeled until the user names it — which is the "appears once" contract on those platforms too.

     ⚠ **What decision 5 does NOT rule, recorded because a code comment claimed the reverse and cost a track a leg (refuted 2026-08-19).** It does not make a device id **machine-scoped across accounts**: `fauna_client_sync::agent::agent_sync_device_id` carried a doc comment reading *"a device id names the machine, not an account: the same box syncing as a different actor is still the same `sync_devices` device id … (decision 5)"*, and that is the inverse of the boundary above. Both shapes are conformant — **transitionally, since 2026-09-20: the ruling that closes this block gives all 7 apps one per-account derived id, which keeps this boundary and retires the machine-flat shape** — and the one-row contract is a per-`(actor, device)` claim throughout. The agent's own advertisement is not actor-qualified for a narrower reason that stands on its own: the capability store is single-slot, so the one id it advertises already belongs to the account it serves.

  **Compat (I4):** everything is additive — one new kind (`fauna.sync.device.adopt`), one additive IPC status field; every version mix degrades to the current two-row state, which this ruling reclassifies as the transitional shape. **BUILT 2026-08-15** — § Implementation status today owns what is and is not wired.   ⚠ **Decision 2's THIRD condition — *"and the app itself has minted no legacy grant this provision"* — was never implemented, and its absence took whole machines' account data path down (found + built 2026-08-26).** `enrollment_target_device_id` gated on the *agent's* advertisement alone, so its no-agent-answering arm targeted the machine row directly — while the very same app's provisioner, moments later, minted a legacy renewal grant onto that row (`SyncAgentProvisioner::start`'s else-arm, taken precisely because no agent is up yet to advertise).   ⚠ **Say that last part narrowly — the over-broad form of it cost a work item.** Until 2026-08-26 this paragraph and `enrollment_target_device_id`'s doc comment both read *"no later pass re-registers it"*, full stop.   **Three bounds on that build, recorded because each is a notch narrower than the sentence one wants to write** (the same over-reading this section has now paid for twice; each bound was attacked by an independent verification pass the same day, which sharpened all three and ruled on the third). **(1) CLOSED 2026-08-26 — the condition is now asked once and answered once.** It had been asked *twice*: `Some(row)` proved only what the agent advertised at the *runtime's* read instant, while the provisioner's mint decision was a **separate live read at a different instant**, and the agent genuinely cold-starts between them. The two could disagree inside one provision in both directions, so a sub-second window survived in which the principal was still evicted through the `Some` arm. The verification pass narrowed where: the window existed only where the agent-named row *is* the app's own `device.db` row — the mint always targets the app's own id, so an agent presenting a different id never collided with it — and that is the common case, not a corner. **The build, and why this shape rather than the other one:** the provisioner *publishes what it decided*, rather than the resolution being hoisted above both spawns and threaded down. Hoisting would have to reach **four** hosts (`apps/fauna-linux/src/app.rs`, `apps/fauna-tui/src/sync_agent.rs`, and both `libs/fauna-ffi` entry points), which is precisely the per-app declaration `platform_provisions_colocated_agent` was derived once to avoid — and the wrong value there is silent. Publishing keeps the answer where the *act* is: the provisioner already knows what it did. Concretely — `fauna_client_sync::agent::decide_and_record_legacy_mint` is the one act that both reaches the decision and records it, and `enrollment_target_device_id` consumes that verdict instead of re-deriving the question from a later observation. - **Retired owner keys after an identity succession — read-only, chain-scoped, and owed an end (ratified 2026-08-04).** A succession re-points corpus *ownership* in one nest-side transaction but moves no *seal*, so every chunk already at rest stays sealed under the **predecessor's** `BackupKey` while the successor derives a new one ([`../../behavior/succession-aftermath.md`](../../behavior/succession-aftermath.md) § Re-key scope owns the corpus row and the re-seal that ends this). The agent is the process that opens those bytes on desktop — it hosts every always-resident engine (§ Scope per platform) — and on the case the aftermath exists for, a successor restoring onto a **fresh** device, *nothing* is in a local watch dir, so every read is a predecessor read. The identity-holding app therefore pushes the account's retired owner keys in the capability, over the additive `SyncCapability.predecessor_backup_keys` IPC field, at the same trust boundary as `backup_key`. Three bounds are part of the ratification, not implementation detail: **(1) this account's own succession chain only** — the list is `AccountRegistry::predecessor_backup_keys`' walk of the identities *this device holds the retired secrets of*, never another account's and never material the device would otherwise not hold; **(2) read-only by construction** — the value reaches `FileDownloadKeys::predecessor_backup_keys` and nothing else, and no seal root consults that field, so no agent-performed upload can land under a key the aftermath exists to retire; **(3) it is owed an end** — the keys are pushed only while a re-seal is owed and the capability is re-provisioned without them once the corpus is re-sealed, at which point the retired seed stops being load-bearing. The alternative — keeping the agent on the current key and doing the predecessor read in the app — was **rejected**: it needs a second in-process byte path beside the engines the agent already hosts, which is the divergence § Scope per platform exists to prevent, and it leaves an app-dead successor dark indefinitely. ⚠ **Bound (3) is enforced as of 2026-08-05** — the bullet below owns the design; § Implementation status today → A8 owns the build. - **Bound (3)'s enforcement design (ratified 2026-08-05, the design pass).** Six rulings, each answering a gap the 2026-08-05 recon established (the coverage/staleness/rendezvous trio, plus two the design pass found):
  1. **Per-device scope is exact, not a compromise.** The keys in a capability serve only the engines *that agent hosts* (bound (2): they reach `FileDownloadKeys` and nothing else, per hosted engine), so a device whose hosted engines have all verifiably drained no longer needs the keys in its agent — regardless of any other device's state. The cross-device-rendezvous gap therefore does not bind *this* license; it binds only an account-level "succession fully discharged" statement, which is a display concern and **never a license for anything** (the escrow container's far harder bar is owned by `identity-succession.md` § Seed escrow).
  2. **The license is a recomputable predicate, never a latch.** Evaluated app-side at each convergence-loop provision from a fresh agent answer, failing **toward pushing**: agent unreachable, an engine unqueryable, a set un-folded, fields absent (older agent) → the keys stay. An event that re-creates need — binding a predecessor-era set, a new succession — flips the predicate back and the keys return on a following tick; the interim is a fail-closed read failure that heals. That recoverability is *why* automatic enforcement is acceptable at all, and it holds only because the registry keeps the seeds and ruling 6 keeps every irreversible consumer off this license.
  3. **The per-engine observable is (fold-evidence AND live-list-empty), never the pass record.** "Drained" for one engine = the placeholder fold has completed at least one full non-deferred round against the nest since the engine's DB was created (a dedicated `SyncDb` meta marker stamped at `pull_remote_changes`' two non-deferred exits; a deferred batch must not stamp — an unopened sealed path may be exactly a predecessor-sealed label) **and** `SyncDb::list_pending_current_root_reseal` is empty at answer time. A fresh empty DB has an empty list and is precisely *not* drained (the family — and today's catch-up even runs the re-seal pass before the first fold, so first-pass-empty is the common successor case, not a corner). `CorpusResealPass` / `EngineInfo.corpus_reseal` remain display-only reports.
  4. **The wire carrier is additive on the existing status surface:** per-engine fields on `EngineInfo` (`ListEngines`), computed fresh in the handler from the live list + the fold marker. `#[serde(default)]` both directions; an older agent's response simply lacks them, which ruling 2 reads as "cannot tell" → keys stay.
  5. **The `current_root_sealed` sentinel is valid only for the root generation that wrote it.** Nothing clears the boolean today, so a *second* succession (B→C) leaves B-era entries stamped current while actually sealed under the retired B root — the re-seal pass would skip exactly that corpus and the list would drain vacuously. This is a defect in the existing re-seal mechanism independent of the license, and the enforcement leg must fix it: persist the stamping identity (the account's current actor id) beside the sentinels; an engine coming up under a different actor id clears every sentinel and the fold marker before serving the observable.
  6. **This license reaches the capability contents and nothing else.** Never the account-registry rows, never the escrow container, never a user-facing "succession complete" claim. The registry keeps retired seeds indefinitely (only the user's own account-removal deletes them), and the escrow drop answers to `identity-succession.md` § Seed escrow's account-complete bar alone.

The ungated pre-bind re-seal (`reseal_pending_under_current`) is the **uniform agent shape** (idempotent and self-terminating on the local row's generation stamp; the sealed-`__config` sentinel identity-holding apps once cleared was retired 2026-09-25 — `../mls-group-key-material.md` § M2 *Pre-bind re-seal migration*) — formerly recorded as a windows-only deviation.

Grounding facts, each verified in code:

- **A fresh key store per launch mints a fresh writer key.** The account runtime's placeholder device id is `hex32(writer pubkey)` (`account_runtime.rs::ensure_enrollment_registered`), and the writer key is mint-or-load from the per-actor credential slot (`resolve_writer_key_serialized` → `writer_key_from_slot`).
