The user's desktops run **one per-user agent process** — `bins/fauna-sync-agent`, generalized from the windows-only sync service (the `fauna-sync-service` crate, retired 2026-10-02) — so file sync is **always running for that user**: the GUI app being closed never stops it. The GUI app and fauna-tui (over SSH) are both full control surfaces.

## Scope per platform

The agent hosts everything **always-resident**: the folder engines (shared `always_resident` loop over the shared `EngineHost` multiplexer — one engine per bound folder, per-set `fsid-<ref>.db`, one shared `device.db`). ~~and the segment-backup `BackupCoordinator::run_forever`~~ — **WITHDRAWN 2026-07-23: the agent gains no segment-backup role.** Segment backup of the nest-originated message kinds moves **nest-side** under `NestBackupKey` (owner: `backup-restore.md` § Background Tasks; the 2026-07-23 nest-side-segment-backup design record (tracked internally)), which supersedes the D6 milestone — backup status becomes a nest projection uniform across all 7 apps, and the in-app desktop backup drivers retire into the nest-side path, not into this agent. The on-demand surface stays platform-bound: **windows** cfapi roots in the agent (already true); **macOS/iOS** on-demand stays in the File Provider extension (the ratified carve-out — `fileproviderd` is already the OS's service for that surface); **linux** on-demand is a FUSE root hosted by the agent, mounted over the bound location — ratified 2026-09-26, built through its lifecycle, reached by no app yet (the owner carries the status); owner `../../behavior/on-demand-files.md` § Linux FUSE binding. Per-set agent↔extension partitioning needs no protocol: the one-local-presence-per-set rule decides it.

**Stays app-side:** photo-library ingress (TCC/PhotoKit belongs to the app; the app is that set's one writer), one-shot restore walks, and iOS entirely (no daemons; extension + `BGProcessingTask` unchanged). Per-file display state: interactive reads over the IPC seam (`GetFileStatus`); high-volume badge folds may read `fsid-<ref>.db` read-only cross-process (the FP-extension precedent). Nothing else touches the agent's DBs.

**The agent is also the desktop's push wake stand-in (ruled 2026-09-26; owner [`common.md`](common.md) § Push Notifications → *Transports*, the `ws-device` transport — built on linux 2026-10-01, the windows and macOS arms unbuilt; status in the owner).** It already holds the per-account WS-RPC connection: it announces the machine's device id on it (`fauna.push.presence` — as a wake stand-in, never as the app: ruled 2026-10-03, owner `common.md` § Dispatch Logic), receives `fauna.push.notification` frames for the account whose app subscribed, and posts them as OS notifications only while no app is attached over the IPC seam; headless, it reports *no notification sink* over § Local agent health so the app's control can say so. "Attached" is a lease: an open app holds one IPC connection that sent `AttachApp` for its whole process life, and the lease ends when that connection closes, a crash included (`fauna_ipc::conn_scope`). The subscription itself is the app's, never the agent's.

**The agent is also the desktop's relay-serving seat (ruled 2026-10-01; owner [`../../behavior/file-sync.md`](../../behavior/file-sync.md) § Relay serving — built 2026-10-01).** Its resident engines hold the bodies of every bound folder, so it is the process that announces them on a WS-RPC connection of its own and answers the nest's asks, app open or closed. It dials no data-plane socket.

## Packaging + lifecycle (per-user, works out-of-the-box)

The agent always runs **in the user's logon session, per user** — never LocalSystem, never root (the `BackupKey` session-boundary rule, `file-sync.md` § Who runs the hydration host). Installed by the platform artifact; **ensured by the app** at the universal post-auth hook; kept alive by the platform's per-user mechanism:

- **windows** — MSI ships `fauna-sync-agent.exe`; HKLM `Run` key launches it per-logon under the user's token (OneDrive model); the app's session-scoped convergence loop also spawns it on demand.
- **macOS** — the `.pkg` sync component installs a per-user LaunchAgent `social.fauna.sync-agent.plist` (`RunAtLoad` + `KeepAlive`, enabled — replacing the shipped-disabled `social.fauna.sync` daemon plist), **exec'ing the bundled copy `Fauna.app/Contents/MacOS/fauna-sync-agent` when the app component is installed** (bare `/usr/local/bin` only on a services-only install) so that whatever the agent is ever attributed to is the app's shared subject (`../installers/macos.md` § Identifier domain, decided 2026-08-24); a `.dmg`-only install self-installs the LaunchAgent at first post-auth (`~/Library/LaunchAgents` + `launchctl bootstrap gui/$UID`). **The agent's data root, socket, logs and pin store are all in the user domain — `~/Library/Application Support/Fauna/{sync,sync-agent.sock,trust}` — and the agent NEVER opens the app-group container (ruled 2026-08-25):** macOS 15+ TCC-prompts a launchd-spawned process for the container on every instance and no user decision binds the next one, so a data root there is unreachable by construction (`../installers/macos.md` § Identifier domain, record item 5). The per-domain form of the state-unification law — the container is the sandboxed File Provider extension's root, the user domain is everyone else's, and no set's state is ever needed across the two — is owned by `../../behavior/on-demand-files.md` § Apple File Provider binding, *state unification*. This is *lifecycle tending of the app's own helper* (the ratified windows pattern), not the retired `SyncDaemonManager` control-plane violation — sync management still goes through the nest.
- **linux** — the app writes + enables a systemd **user** unit `fauna-sync-agent.service` (`Restart=always`, `WantedBy=default.target`) at first post-auth (the autostart-`.desktop` shape; e2e-gated off). Headless boxes: fauna-tui offers `loginctl enable-linger` (built 2026-07-23 — the `sync-agent-linger-toggle` on its Folders page; § Implementation status today). Per-install-channel exec forms, the unit's uninstall-inertness condition, the Flatpak host-unit seam, and the Snap app-child interim: `../installers/linux-desktop.md` § Installation Files.

There is deliberately **no "disable the service" knob** (bucket 1 — artifact wiring): the agent's *work* is entirely user-chosen through existing UI (bindings, modes, destinations, Pause). An agent with nothing to do idles. Agent-local files (its config/state dir) are written only by the agent/installer — never human-edited.

**macOS keychain authorization on a fresh install — MEASURED 2026-08-28 (severity: one sticky prompt, not a recurring tax).** The agent shares the account-store credential slot with the app: it *reads* the T10 writer key and device-authorization at `fauna-account-store/<actor-hex>` (`renewal.rs`, `principal_bundle::load_writer_key` — load-only, never a mint) and holds its own `fauna-sync-agent` capability rows. On macOS all of these land on the **legacy `login.keychain-db` plane**, because the data-protection plane is unreachable under the shipped Developer-ID signature (no provisioning profile — [`../installers/macos.md`](../installers/macos.md) § Identifier domain owns the measurement and the why). Legacy-plane ACLs bind to *code identity*, so:
- The identity-holding **app** mints the shared `fauna-account-store/<actor>/backup-key` + `/device-auth` rows during account-runtime assembly; as their creator it is auto-authorized (no prompt for its own reads).
- The **agent**, reading those app-created rows, is not their creator, so a **fresh box shows exactly one agent ACL prompt** (*"fauna-sync-agent wants to use …"*) at its first read — the fresh-install prior is **≥ 1, not 0** (the row's "strong prior: zero" is refuted: the creator-is-authorized rule covers the agent's *own* rows, not the app-minted slot it reads). One **Always Allow** sticks across future signed builds, because the agent's designated requirement is *identifier + team*, not cdhash (measured 2026-08-23; the account-store rows' ACLs already list both the app's and the agent's DR-based entries as trusted). It does **not** re-prompt per update — the retracted "prompts whenever code identity changes" reading applied only to the ad-hoc twin incident, never to signed builds.

Eliminating even that one prompt would mean moving the shared `fauna-account-store` slot to the entitlement-gated data-protection plane — and that is **not** what the ratified path does. **Path A (ratified 2026-08-28, `../installers/macos.md` § Identifier domain → *Path A*) deliberately leaves this slot on the legacy plane**: it is shared with **fauna-tui** (ad-hoc/unsigned — cannot reach the DP keychain) and read by this **bare launchd-agent binary** (not a bundle — the DP keychain needs an app/appex-like bundle carrying a profile), so it cannot move without breaking tui. Path A embeds provisioning profiles for the *app's* Swift `KeychainStore` (`ios.md` § Credential Storage) and the *File Provider appex*, both bundles; this agent slot is not among them. So the agent's single sticky prompt is the one keychain prompt the ratified design accepts — one Always-Allow per fresh box, sticky under the Developer-ID DR, not an emergency.

## Control plane split

Unchanged from `sync-engine-deployments.md` § Control Plane Principle: **policy through the nest** (folders, mode, retention, destinations — nest rows, edited from any app, read by the agent), **never over local IPC**. (The reconcile cadence itself left this list with phase 5's de-knob, landed 2026-08-20 — the agent's `HydrationHost::rescan_interval` is now a hard-coded constant, not a row it reads; `sync-engine-deployments.md` § Config owns the contract.) (Selective sync was the one exception until 2026-08-27, when the row's `include_paths`/`exclude_paths` joined the postures the shared engine installs off its authoritative row read — the agent's hydration host reaches them through `SyncEngine::refresh_sync_mode` like every other seat, with no agent-local carrier and nothing new on the IPC seam; `file-sync.md` § Status owns the mechanism.)

**Worked example, because "destinations" is where this rule gets re-litigated: the client-device backup custodian's assignment.** When the agent hosts this device's custodian replica ([`behavior/backup-destinations.md`](../../behavior/backup-destinations.md) § State & data shape → Third destination kind, which owns the kind), it needs two values — the `destination_id` of this device's own row and its capacity cap. The authoritative copy is the source box's destination-list row of the account-state plane kind `fauna.state.backup` ([`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule → *The kinds*), which this process does not consult — and not because it cannot: the agent is an enrolled *seedless fleet member* that mounts the account store under its `BackupKey` and opens every fleet-only kind its writer key is wrapped into, `fauna.state.folder-keys` among them ([`sync-agent-credentials.md`](sync-agent-credentials.md) § Credential model; until 2026-10-02 this sentence said "structurally cannot open … bearer-only", a reading the blob era never supported either). It does not consult the owner's sealed list because the registry, not that list, is what the source nest *enforces*, and the agent's assignment is a fact about that nest. The shape that follows from the rule above, and the built one, is that the agent reads the row back from the source nest's destination registry (`fauna.backup.destination.list`, the registration's own read-back) over its authed control plane and matches on its own `SyncCapability.device_id` — the cap therefore rides the registry row, not just the sealed plane row. Provisioning it over the local IPC seam was considered and is **wrong twice over**: it is the one thing this section forbids for a destination, and it would make the cap — the kind's only knob, whose exhaustion *stops* the backup — changeable only while an app runs on this same machine, when the owner may well be raising it from their phone. The general test the example illustrates: a value is IPC-eligible because it is *structurally local* (this device's location↔set binding, its capability), never merely because this device is the one that acts on it. The local `fauna-ipc` seam carries only the structurally-local: (1) capability provisioning (`ProvisionCapability`/`RefreshBearer`), (2) device-local location↔set binding, (3) local introspection + shell integration (`GetFileStatus`/pin/unpin/free-space, status, pushed events), (4) `ListEngines` and device-global `Pause`/`Resume` (persisted agent-side), and (5) `ApplyHeldDeletes` — the user's explicit confirm of a mass-delete-floor hold on one bound set, which is structurally local by the same test as (2): the hold is derived from *this device's* scan of *this device's* bound folder, and the agent re-derives it at the call rather than trusting anything the caller passes (behavior owner: [`../../behavior/delete-propagation.md`](../../behavior/delete-propagation.md) § A wholesale-vanished folder is infrastructure failure), and (6) `GetCustodianStore`/`ReclaimCustodianStore` (2026-08-21) — measuring and freeing **this device's own sealed custodian store**, structurally local by the same test as (2) and (5): the reply is a measurement of this process's disk, and the store's location is this process's to resolve, which is the same reason `GetShareServeInfo` is a verb rather than an app-side re-derivation. ⚠ Note what they deliberately do **not** carry, because it is the pattern the worked example above forbids: the agent is never told *whether* the store is orphaned. That verdict needs the destination rows, which this process keeps no reader for (it could open them — the correction above — and the rule is that it does not act on them), so the app decides it (shared rule `fauna_core::data::custodian_store_is_orphaned`) and the agent contributes only the guarantee that is genuinely local — it stops its own custodian stint before deleting the bytes under it, and refuses rather than racing a teardown that will not finish. Affordance owner: [`../../ui/backups.md`](../../ui/backups.md) § Manage backup destinations → *Reclaim this device's copy*. And (7) `ReconcileAccountRuntime` (2026-10-06) — run one full pass of the account store this process has mounted, now: structurally local because it names this process's own pump and carries nothing, the app having already rested the device-local row the pass reads; a quiet no-op when no store is mounted or an app's runtime holds the engine; plain fail-fast, since the pump's backstop re-drives a missed ask (behavior owner: [`../../behavior/p2p.md`](../../behavior/p2p.md) § Per-device participation → *Enforcement*, (c) Promptness). The `GetBackupStatus` op (stubbed `[]` since A1b) is **retired as of the 2026-07-23 nest-side-backup ratification** — backup status is a nest projection, not an agent read; the codec variants get deleted with the flip.

**The location-binding control plane is scoped to the LOGIN — never to the agent handle, and never to a page** (ratified 2026-08-05, after the windows instance below). The optimistic `LocationBindingsModel`, the reconcile that pushes it, and the agent-reachable edge that re-drives that reconcile all hang off session state that exists from the first instant of an authenticated session; the binding UI is one *renderer* of that model among several (the e2e `data.sync.locations` block is another), and it subscribes rather than owns. Two failures follow directly from getting this wrong, and both are silent:

- **Scoping the model to the agent handle loses binds during start-up.** Building the provisioner costs one or more nest round-trips (`setup_renewal_grant`, and any content-key resolve a platform does first), so on a connection that is still down at login the handle appears seconds later — ~10 s observed on windows, two 5 s RPC timeouts, and *wider* on a slow nest. Every binding surface gated on that handle refuses for the whole window, and a one-shot refusal is a lost bind: the user picked a folder, the UI accepted the gesture, and nothing was recorded. Record into the login-scoped model instead and let the attach edge push it — then start-up latency delays the push and can never drop it.
- **Routing the reachable edge through a page pushes nothing in exactly the case the edge exists for.** A page-hosted notifier is by contract a no-op while the page is closed, which is nearly always; the pending binds it was meant to flush therefore sit unpushed until the user happens to make another gesture on that very page — the same "reconcile fires once, at attach" failure, reintroduced one level up.

**The same rule binds the SESSION ITSELF, not just the binding model — a session is published before it provisions (ratified 2026-08-06, after the windows instance below).** The session handle must be reachable by teardown from the instant it exists, because the thing a teardown has to undo — the agent's provisioned capability — is created by *starting* the session, and the start is the tail of a chain that takes seconds. Concretely: **building** a provisioner is agent-invisible (`SyncAgentProvisioner::new` touches no wire), and **`start()`** is what registers the renewal grant and spawns the convergence loop that pushes `ProvisionCapability`. So the ordering is forced — supersede, build, *publish*, then start — and the supersession check sits between publish and start, where it can still prevent a provision rather than having to reverse one. Two failures follow from getting it wrong, and both leave a **signed-out account still being served**, which `../../behavior/on-demand-files.md` § Multi-account × File Provider (consequence 1) forbids:

- **Publishing only after the start makes teardown a silent no-op for the whole window.** The app's session field stays null while the chain runs, so a sign-out lands, finds nothing to unprovision, returns success — and the build it could not see goes on to provision seconds later. The teardown reported success and did nothing.
- **Checking supersession only after the start forces the wrong repair.** Having already provisioned, the discard arm must now *undo*, and it cannot do so unconditionally: a session superseded by a **newer login** must not unprovision (that clobbers the capability the incoming login just installed — the same bug from the far side), while one superseded by a **teardown** must. Deciding correctly there needs a supersession *cause* the generation does not carry; deciding at all is avoidable by not provisioning in the first place.

The two causes are distinguished by which teardown verb the caller invokes (drop-the-handle vs unprovision), never by inspecting the generation. A handle whose start races a teardown re-checks the cause once the start returns and re-tears-down only for the unprovision cause — the residual window the shared loop cannot close by itself, since `unprovision()` cancels a convergence task that a mid-flight `start()` has not spawned yet.

**Content keys are the agent's own — BUILT 2026-09-27.** The agent resolves every set's content keys in-process from the account's folder-key custody (`fauna.state.folder-keys`, read through the account store it mounts since 2026-09-30), and re-reads them at its own edges; the app provisions no per-set key and pushes nothing when custody changes ([`../../behavior/on-demand-files.md`](../../behavior/on-demand-files.md) § Shared sets on a capability host → *One mechanism* owns the ruling and the edges). A set the agent's resolution does not name gets no engine: absent is *not keyed yet*, never owner-only. **No advertisement is needed:** every agent this software ships resolves content keys itself, so the status reply carries no such bit. The `resolves_content_keys` advertisement and the app-side gate that withheld a provision from an agent not advertising it — the pre-convergence binary of the 2026-09-27 upgrade window — were removed by the compat-remnant sweep ([`../version-compatibility.md`](../version-compatibility.md) § Dimension 2: no such agent exists), so `full_provision` in `fauna_client_sync::agent` provisions every reachable agent. The reverse skew — a converged agent under an older app, or a capability the agent persisted before the upgrade — needs nothing: the retired key decodes as unknown and is ignored (`fauna-ipc`'s `a_capability_carrying_the_retired_content_key_blob_still_decodes`). *Retired with this build:* the app-pushed `SyncCapability.content_key_bindings` blob, the resolve-before-provision withholding (2026-08-06), the per-set withholding of a set the blob did not name (2026-09-08, narrowed 2026-09-13) and the keys-before-bind ordering on every app — git history holds their reasoning.

linux is the reference shape (`apps/fauna-linux/src/sync_agent.rs`): the model lives in the module's installed session state, `reconcile()` sits beside it, and the Folders page is repainted by it (`rerender_bindings`) rather than driving it. The repaint is guarded on the rendered union actually changing — a no-change rebuild destroys live widgets under the user's cursor. Its `install()` is the reference for the paragraph above too: it installs the module's session state **synchronously** and merely `rt.spawn`s `start()`, so `teardown()` can always reach the provisioner — the shape windows adopted in 2026-08-06's fix (`SyncAgentSessionHost`, unit-tested in `SyncAgentSessionHostTests`).

**Transports:** length-prefixed canonical dag-cbor (the existing `fauna-ipc` frame) over the per-SID named pipe `\\.\pipe\fauna-sync.<SID>` (windows), a `0600` unix socket in a `0700` per-user dir (`$XDG_RUNTIME_DIR/fauna/sync-agent.sock` on linux — relocated to the instance-shared `$XDG_RUNTIME_DIR/app/<app-id>/fauna/sync-agent.sock` when `FLATPAK_ID` is set, since the rest of the runtime dir is per-sandbox-instance tmpfs and the app + host-unit-spawned agent run as separate instances of the same app-id, `installers/linux-desktop.md` § Flatpak; `~/Library/Application Support/Fauna/sync-agent.sock` on macOS). `fauna-ipc` lives at `libs/fauna-ipc` (moved from `apps/fauna-windows/`). **Both server halves live there too** — `unix_transport::serve` and, since 2026-08-24, its windows sibling `pipe_transport::serve` (the pipe DACL builder, accept loop and client handler the agent and the FaunaBridge service had each hand-copied). They share one frame loop, so `MAX_FRAME_SIZE` has a single enforcer across every transport and both directions. The agent's `run_pipe_server` is now a wrapper passing its own handler and its own **empty** extra-trustee list; the per-binary DACL policies are deliberately distinct and owned by [`windows.md`](windows.md) § IPC.

**The client verifies WHO is serving before it speaks a word (windows; ratified 2026-09-21).** `\\.\pipe\` is a **machine-wide** namespace and a SID is not a secret on a shared box, so reaching `\\.\pipe\fauna-sync.<SID>` proves only that *someone* created that name. Any other local account can create it while the victim's agent is down — after a logout, or between agent restarts — and doing so wins twice: the victim's agent then fails its own `FILE_FLAG_FIRST_PIPE_INSTANCE` create and exits (§ The agent is single-instance per user), and the victim's app connects to the squatter and pushes its nest **bearer** (`RefreshBearer`) together with a `SyncCapability` carrying **the owner's `BackupKey`** (`ProvisionCapability`). The single-instance mutex cannot help — it is `Local\`-scoped, living inside the victim's own session. So `sync_pipe_client::connect_pipe_to`, the one place every consumer passes through (the FFI provisioner for C#, fauna-tui on windows, all three shell-extension handlers inside `explorer.exe`, and the unshipped dev tool `shellext-fixture`), **resolves the serving process's token user — `GetNamedPipeServerProcessId` → that process's `TOKEN_USER` — and refuses any pipe not served by this user, before the client object exists and therefore before any frame can be written.** Three properties make that refusal load-bearing rather than decorative:

- **Any failure to determine the server's identity is itself a refusal, never a fallback to a weaker check.** A cross-user `OpenProcess` is `ACCESS_DENIED`, so an unanswerable probe is the attack's own signature; a second check to fall back to would merely let the attacker choose which check runs. The pipe object's owner (`GetSecurityInfo`) is the check deliberately *not* used: reading it needs `READ_CONTROL`, which the squatter's own DACL grants or withholds, and it false-negatives on a legitimate server running elevated, whose default object owner is `BUILTIN\Administrators` rather than the user.
- **The refusal is a distinct terminal error — never retried, and never reported as a missing agent.** The ensure-the-agent wait below answers a failed connect by spawning and re-probing for 10 s; against a squatted name every spawn dies on its own first-instance create, so retrying would burn the whole budget and then report *"agent unreachable"* about a machine whose agent is fine and whose name has been taken.
- **The connect grants the server `SECURITY_IDENTIFICATION`, not the local default `SECURITY_IMPERSONATION`.** A named-pipe server may impersonate its client; capping the level at *identify* means a squatter cannot act as the user against anything else on the box even during the instant before it is refused.

The unix twin needs none of this, and the reason is not that it is less exposed: its socket's parent (`$XDG_RUNTIME_DIR` / `~/Library`) is already per-user, so the namespace an attacker would have to reach into is not shared in the first place.

**The unix socket path has a hard length budget** — `sockaddr_un.sun_path` is 104 bytes on macOS, 108 on linux — and it is *derived*, so a caller relocating the base dir can overshoot it: macOS appends a fixed 50-byte `Library/Application Support/Fauna/sync-agent.sock` to the home dir, and any home under macOS's ~48-byte `/var/folders/…/T/` tmp root exceeds the cap. Over-budget is not a degraded mode but a total one: the agent spawns, binds nothing, exits, and the *client* side reports `agent unreachable for <op>` — indistinguishable from a missing agent unless something names the real cause. So `fauna_ipc::unix_transport::check_socket_path_len` rejects an over-long path before bind (and before `prepare_socket_dir`'s side effects), naming the path, its length and the limit; the e2e harness holds the same budget from its side when it relocates a launch HOME for isolation (`e2e-launch-isolation.md` § point 10). Found 2026-07-24, when it silently cost the macOS seat of the tri-machine live filesync run.

**The agent is single-instance per user.** At startup — before restoring its capability or starting engines — it takes a kernel-arbitrated exclusive lock scoped to its own per-user transport: a `flock` on `<socket>.lock` (unix, `fauna_ipc::unix_transport::InstanceLock`) or a named mutex derived from the per-SID pipe name (windows, `bins/fauna-sync-agent/src/pipe_server.rs::InstanceLock`, keyed via `fauna_ipc::sync::mutex_name_for_pipe`); a losing duplicate logs and exits cleanly having touched nothing. This is what makes the unix server's stale-socket unlink-before-bind safe, and on windows it closes the gap `FILE_FLAG_FIRST_PIPE_INSTANCE` alone leaves open: without either guard, a spawner racing a slow-binding agent (the convergence loop re-probes on every tick/poke) can start a second agent that steals the live socket / races the pipe create and syncs the same DB as the same device. A connect-probe is not enough — two cold-starting agents can both probe before either binds; the kernel-arbitrated lock has no such window, and a crashed holder releases automatically (unix: the flock; windows: the OS closes the mutex handle when the process's last handle to it goes away) — no stale-lock state either way. The unix lock file is deliberately never deleted. Spawners additionally skip the spawn while a previously-spawned child is still live (churn avoidance, not the correctness guard).

**Consumers:** the linux GTK app and **fauna-tui** link the Rust client directly — fauna-tui on **every OS it runs on, windows included** (the client resolves the platform transport through one `fauna_ipc` endpoint seam: the per-user unix socket on linux/macOS, the per-SID named pipe on windows); Swift **and C#** consume the same client via the `fauna-ffi` UniFFI surface (`FfiSyncAgentProvisioner`). **There is no per-app IPC codec**: the C# wire-pinned codec's retirement was ratified 2026-07-24 (user-directed; design record tracked internally) — see § Implementation status today for the gap. **fauna-tui is the TUI control surface** — a full app that drives the nest policy plane, drives this seam, and on a headless box **mints + provisions** the capability itself (it holds identity via its sealed credential store). No separate micro-CLI exists or is planned.

The provisioning **convergence loop** (probe → spawn-if-absent → `RefreshBearer` → full re-provision on `NoCapability`; 30 s tick + poke) is shared Rust, consumed by all four desktop app stacks (GTK/FaunaKit/fauna-tui directly; C# through the FFI provisioner). The tri-state `RefreshBearerOutcome` + pinned `"no capability provisioned…"` error prefix remain cross-process contract.

**The `UnprovisionCapability` reply is a receipt: the agent's own mount of the account store is down when it arrives (built 2026-09-23).** The agent mounts the shared account store as the app-dead runtime host, takes no serving lock over it, and is instead dismissed by this verb before an app erases that store ([`account-scoping.md`](account-scoping.md) § Concurrent instances → *An erase refuses while a sibling serves the account*). So the agent clears the capability, wakes its host stint rather than leaving it to its recheck tick, and replies only once the stint's teardown has finished — the runtime shut down and the stint's nest leg closed (`bins/fauna-sync-agent/src/account_host.rs`, the `hosted_account` slot on its state). A teardown still running at the agent's 4 s budget — under the apps' 6 s pipe ceiling — is answered with a refusal, never a false `Ok`. Two consequences follow. **The app awaits the reply before its erase**: a spawned un-provision is a race the erase wins; the app still erases when the agent is unreachable or refuses (degrade open, the posture the erase's other probes take). **A same-account sign-out → sign-in no longer keeps the old mount**: the old stint has ended by the reply, so the re-provision mounts afresh, where a stint whose inputs compared equal used to survive over the store unlinked in between. A provision wakes the stint too, so an account switch that arrives without an un-provision first stops the outgoing mount at once rather than at the next tick.

**A verb with NOTHING BEHIND IT TO RETRY ensures the agent is running first; every other verb keeps failing fast (ratified 2026-08-27).** The loop above can afford to lose a race against its own spawn — it re-probes in 30 s. So can most of this seam, and deliberately: the binding model re-pushes a failed bind on the next reconcile (§ *The location-binding control plane is scoped to the LOGIN*), `PullFolderNow` is a fire-and-forget nudge whose backstop is the engine's own rescan tick, and a page that could not read simply re-renders. **A confirm modal has no such backstop: it fires once, and a refused act is a lost gesture rather than a delayed one.** On windows that single attempt reaches a **separate process's named pipe, which does not exist until that process has started**, so a gesture landing inside the app's own lazy-spawn window fails with `agent unreachable for <op>: … The system cannot find the file specified` — indistinguishable, to the caller, from having no agent at all. The pipe client's `ERROR_PIPE_BUSY` retry does not cover it and should not: a *busy* instance is a transport race, an *absent* pipe is the caller-level question "is the agent even up".

So exactly the retry-less verbs — `ApplyHeldDeletes`, `ReclaimCustodianStore` and `ReseedCustodianStore` (all three behind a confirm; the last carries the owner's `NestBackupKey` for that one call, [`../owner-key-material.md`](../owner-key-material.md) § Path A-sibling-0 owns why), plus the test-only `CustodianRunPassNow` — connect through the same probe → spawn-if-absent → re-probe wait the loop's tick runs, bounded (10 s) so a box where the agent *cannot* start fails the gesture rather than hanging it, and spawning at most once (idempotent by the live-child gate above, so it can never race the loop into a second agent). **The test for a new verb is not "does it act?" but "if this attempt is refused, what re-drives it?"** — nothing → ensure; a tick, an edge, a re-render → fail fast. `GetServiceStatus` is the standing counter-example: § Local agent health polls it to answer *is the agent up*, and a read that starts the agent would be reporting on what it just started. The sign-out teardown push and the signed-out-onboarding reconcile are excepted from the far side — both are best-effort against an *already-reachable* agent, and must never start one in order to tear it down.

The wait lives once, in the shared provisioner's exchange, so linux, fauna-tui, macOS and windows are covered by one implementation (priority #2) — including fauna-tui **on a windows host**, which is where the gap was measured (2026-08-27). On unix it is invisible: the app direct-spawns the agent into its own isolated runtime dir, so the endpoint exists before any verb can run.

**The sync-status projection (ratified 2026-08-02 — the field semantics of `SyncStatusInfo`/`EngineInfo`/`LocationInfo` on this seam).** Every status field is a real projection from the per-set engine state DBs, computed by shared Rust (`fauna_sync_engine::db::SyncDb::transfer_backlog` / `tracked_totals`) and folded by **one** handler helper, so `GetServiceStatus`, `GetSyncStatus` and `ListEngines` can never disagree:

- **`files_pending` / `bytes_pending`** — the fold of the per-file **display** states: a file counts exactly when its badge reads `Uploading`/`Downloading` (`SyncState::to_display`, whose map [`file-sync.md`](../../behavior/file-sync.md) § Per-file sync-status display owns), so the aggregate is badge-coherent by construction. Bytes are **whole-file** sizes (the "3 items, 2.4 GB" queue reading) — per-file live progress is deliberately NOT this projection's job; that is the push channel, ratified directly below.
- **`last_sync`** — when this device was last **known consistent** with the nest: the freshest of two engine-side `sync_anchor` stamps, `last_transfer_at` (a file-level content transfer completed — advances only when content actually moved, the `segment_backup_state.last_content_synced_at` honesty rule) and `last_clean_pass_at` (a converge/pull pass completed clean AND left nothing pending). An idle-but-checking device stays fresh; a device with a stuck backlog goes honestly stale. Aggregate = max across sets.
- **`connected` = a capability is provisioned** (the same signal `ServiceStatusInfo.connection` carries — one meaning, both places); **`syncing` = the engine host is serving**. Before 2026-08-02 the two status handlers disagreed on `connected` (one reported engine liveness); that drift class is retired by the shared helper.
- **`EngineInfo.files_pending`/`bytes_pending`** — the per-set split of the same fold; `serving` is keyed by the mapping's `engine_key()` (the `FolderRef` when the binding carries one — keying by set *name* misreported `false` for every ref-carrying binding, fixed 2026-08-02). `EngineInfo` deliberately carries **no** `last_sync` field yet — adding one is a cheap additive wire change (`Default`-having struct, per the struct-update fixture rule) with no current consumer: windows dropped `ListEngines`/`EngineInfo` consumption entirely with the 2026-08-05 C# codec retirement (the codec was deleted, not regenerated, and windows' Status page instead reads the aggregate `SyncStatusInfo.last_sync` over the FFI `sync_status()` call — § Implementation status today (c)), and the only other reader, fauna-tui, uses `EngineInfo` for `corpus_reseal`/`reseal_drain`, never a timestamp. Build it when a real per-engine-freshness consumer appears, not speculatively.
- **`LocationInfo.file_count`/`total_bytes`** — what the folder *holds* (every tracked non-`Deleted` row), not the backlog.

**The live transfer window (ratified 2026-08-15 — the semantics of `EventKind::SyncProgress` on this seam).** The status surface rests on **two** channels, and they answer different questions. The projection above is the *durable queue* ("Uploading 3 items, 2.4 GB"): whole-file sizes, computed from the state DBs, survives a restart, polled. `EventKind::SyncProgress` is the *live window*: what is moving **right now**, in bytes, folded in agent memory and pushed. Neither substitutes for the other, and an app renders the live window over the polled projection while a transfer is in flight.

- **One window per engine, spanning a whole pass — not one file.** `converge` uploads files sequentially, so the set of open files is empty for a moment between every pair of files; a window that closed on "nothing open right now" would retract and re-open once per file, so a hundred-file pass would flicker `1 item` a hundred times instead of counting up to `100 items` once. The window therefore closes on an **idle grace period** with nothing transferring, not on the open set emptying. (`ProgressEvent::CycleDone` would be the natural pass terminator and is deliberately *not* used: it has no production emit site.)
- **A drained window retracts itself with an all-zero frame.** Same rule, and same reason, as `ProgressEvent::DeletesHeld`: this state is derived and in-memory, so a zero is the *only* thing that ever takes a painted "Uploading 3 items" off a surface. A last frame left at 100% would stay painted until the next transfer, possibly for days. An engine that stops mid-transfer retracts on its way out for the same reason.
- **`bytes_done` counts a completed file whole, not the bytes that moved.** `ProgressEvent::ChunkDone` fires only for chunks actually *uploaded*, and the upload pipeline skips every chunk the nest already holds — so a fully-deduped file transfers no chunks at all. `FileDone` settles the file to its `FileStarted` size; without that a deduped transfer sits at 0% and then jumps. The per-file arithmetic is clamped, so `bytes_done > bytes_total` (a bar past 100%) is unrepresentable.
- **The push is coalesced, never per-chunk.** A 4 GB file fires ~65,000 `ChunkDone`s and the engine uploads chunks concurrently, so the raw rate is bounded by the network rather than by anything a UI can paint. Frames are flushed on a fixed cadence and only when the fold actually moved. A flush always folds everything already queued first — a frame built from a partly-drained queue reports a number that lags the engine by an arbitrary amount.
- **In-memory is correct here, and is not a gap to "improve" into a DB field.** The window has exactly the lifetime of the transfers it describes: a restarted agent reports nothing in flight — which is true — rather than resurrecting a byte count no live engine stands behind.

Mechanically the handlers open a **second read connection** per bound set (`sync_db_path_for_binding` — identity-keyed under R1 (account-data-plane.md § The ratified decisions); `SyncDb::open` sets WAL + a 5s busy_timeout for exactly this), best-effort per set: an unreadable set contributes nothing rather than failing the poll, and a bound-but-never-served set reports honest zeros ("0 when idle or not yet known").

**Placement:** a new global shell element `sync-agent-status` (`ui.yaml` `components.sync-agent-status`), sibling to `connection-status`, top of the sidebar on the apps that drive a local agent — windows/macos/linux and (since A6 landed, 2026-07-23) fauna-tui **on every OS it runs on** — windows included since the cross-platform client landed 2026-07-24 (§ Implementation status today) — since web/android/ios have no local agent process. `sync-agent-status-version`/`sync-agent-status-uptime` are optional child elements shown alongside the primary indicator (e.g. a dim subtitle line); exact placement is a per-app implementation choice — linux uses a subtitle line, windows landed the same global-shell placement as linux (three `AutomationId`-bearing `TextBox`es in `MainPage.xaml`'s global-message `StackPanel`, sibling to `connection-status`) rather than `StatusPage`'s existing `VersionText`/`UptimeText` fields, which stay a separate, optional, not-required follow-up (they have no `ui.yaml`/`AutomationId` presence and read a different, unrelated source).

**State derivation (client-side, no new wire fields):**

- **Not running** — the client's `GetServiceStatus` IPC call itself failed (no socket / connect error). Distinct from `connection: Disconnected` in the response, which requires a *successful* IPC round-trip.
- **Restart pending** — the call succeeded but `ServiceStatusInfo.version` differs from the app's own compiled-in build version. The agent binary ships in lockstep with the app in the same installer/bundle (§ Packaging + lifecycle) — a version mismatch means an update replaced the on-disk binary but the still-running agent process hasn't picked it up.
- **Running** — the call succeeded and the versions match.
- **Keys pending** (ratified 2026-09-25 from [`../../ui/folders.md`](../../ui/folders.md) § Sharing a folder's ruling; derivation moved to the agent and built 2026-09-27 — § Implementation status today) — the call succeeded, and the agent reports that some bound set's engine holds a content-key generation behind its row's `content_key_floor`, or was built keyless because custody could not be read (`ServiceStatusInfo::keys_pending`, additive; derived in `bins/fauna-sync-agent`'s `content_keys::keys_pending` from its own resolution — no nest round trip on the status path). Until the generation reaches custody the agent **holds** writes to that set rather than sealing them under the older generation, which after a removal is the generation the removed member still holds ([`../mls-group-key-material.md`](../mls-group-key-material.md) § M2 *Rotate-on-removal*). The threshold is the agent's own re-resolve edges: true from the first edge that found the floor ahead until an edge lands the generation, so it reads *pending*, never *failed* — and it covers a rotation made from another device while this app was closed, and a set the user is a member of. `agent_health_state()` reads it off the reply. A pending generation outranks a version mismatch because it is the one state with a security consequence and a clock, and Restart pending is the weeks-long normal on linux (the whole order is stated once, under *Not enrolled*). Same four apps as the element.
- **Not enrolled** (label and derivation user-ruled 2026-09-30, ratified 2026-10-01, built 2026-10-03) — the call succeeded, and the reply's `needs_reenrollment` is `true`: the nest holds no grant for this machine, so the agent can keep nothing in sync once the app is closed. This doc owns only the reading; what sets the field and what clears it — a successful renewal, never an app's pushed bearer — is [`sync-agent-credentials.md`](sync-agent-credentials.md) § Credential model → *A refused renewal is terminal*. The label is state-phrased like the other four, and it is true whichever way the machine lost its enrollment — removed from the devices list on another device, a factory-reset nest, an enrollment that never registered or is still waiting on the device limit — which is why it is not an instruction: *Sign in again* was rejected because it is wrong while the device limit is what blocks re-enrollment, and *Signed out* because it reads as the app's own session state one line above. The remedy is signing in again on this machine, and the user guide says so; the reading then clears by itself — like *Keys pending* it is a reading, never a control. `agent_health_state()` reads the field off the reply as a fifth `AgentHealthState` variant, and `FfiAgentHealthState` gains it **appended last** (UniFFI ordinals); the string is `status.sync_agent.not_enrolled`. **Precedence when several hold: Not running > Not enrolled > Keys pending > Restart pending > Running** — *Not enrolled* is the one reading that waits on the user and never ends by itself while the app is closed, whereas a pending generation lands on the agent's own edges. Same four apps as the element.

No agent-side or wire change is needed: the app already knows its own build version, and `GetServiceStatus.version` already reports the running process's. Shared derivation lives in `fauna_client_sync::agent` (`AgentHealthState`, `agent_health_state()`, `SyncAgentProvisioner::get_service_status()`) so the two Rust-native desktop apps (linux, macOS) share one health enum (five states since *Not enrolled* landed) instead of two reimplementations. **Windows correction (found 2026-07-20 while landing the windows leg):** "the app already knows its own build version" holds for a Rust-native app (`env!("CARGO_PKG_VERSION")` inside the app's own crate) but NOT for windows — the .NET assembly's `AssemblyInformationalVersion` is MSBuild-derived (`1.0.0+<git-sha>` by default) and does **not** track the Cargo workspace version, so comparing it against `GetServiceStatus.version` ("0.1.0") would read Restart-pending forever. Fixed with one small new `fauna-ffi` export, `fauna_ffi_build_version()` (`libs/fauna-ffi/src/version.rs`), returning the **linked `fauna-ffi` crate's own** `CARGO_PKG_VERSION` — correct because `fauna-ffi` and `fauna-sync-agent` both inherit `version.workspace = true` from the same `Cargo.toml`. Windows compares against this, not its assembly version.

**Per-platform "restart pending" reality (recon 2026-07-20, cited so a future session doesn't redo it):** Windows's `KillFaunaSync` custom action (`apps/fauna-windows/installer/Package.wxs:121-125`) force-kills the running agent *before* `InstallFiles`, synchronously, but does not relaunch it (relaunch is app-side, on next app start/logon per the same comment) — so Windows transiently shows **Not running**, not Restart pending; a live app↔agent version-mismatch window doesn't occur there. **The IPC itself still has a skew window on Windows (verified 2026-10-02 against the installer):** the shell-extension DLL is installed `Permanent` and versioned (`Package.wxs`, the orphan-cleanup comment beside `KillFaunaSync`), so an upgrade leaves the previous `fauna_shell_<oldver>.dll` loaded in Explorer until Explorer restarts, and that older shell extension's pipe client talks to the newer agent the app relaunches. That window, plus linux's and the `.dmg` channel's, is why both ends of the app↔agent protocol answer a frame they cannot decode for that one call, never by dropping the connection ([`../transport.md`](../transport.md) § Schema and forward-compat discipline → *Rule 3 in full*): an agent refuses an unknown verb with the typed `UNSUPPORTED_METHOD_ERROR_MESSAGE`, a client fails the one call whose reply it cannot read at once (`ReplyNotUnderstood`) and skips an unknown event, and `agent_health_state()` reads either answer to `GetServiceStatus` as **Restart pending** — something answered, from another release. macOS's `.pkg` postinstall (`installer/macos/scripts/common.sh:54-69`) runs `launchctl kickstart -k` on upgrade — a synchronous restart, negligible window — while the `.dmg` self-heal spawner (`SyncAgentSpawner.swift`) only probes when the socket is *absent*, so a stale-version window is real on that channel (and would be on the not-yet-live Sparkle channel). Linux's `SystemdAgentSpawner::ensure_unit_running` (`apps/fauna-linux/src/sync_agent.rs`) heals the unit *file* on an `ExecStart` change but never calls `systemctl --user restart` — `start`/`enable --now` are no-ops against an already-active unit — so **Restart pending is the common, expected case on Linux** until crash, reboot, relogin, or a manual restart. Auto-restarting the agent to close that window is a deliberate non-goal here (killing the engine mid-transfer to force a restart is a bigger, separately-approved-needed behavior change) — this section only surfaces the state to the user.

1. **The base-dir resolution must yield an ABSOLUTE path — fixed 2026-07-20.** A LaunchAgent bootstrapped from the installer's root session can start with **`HOME` unset**. `SyncPaths::production_base_dir()` used `env::var("HOME").unwrap_or_default()`, so an unset HOME produced a **relative** base dir, which `fauna_log::init` then panicked creating `<base>/logs` against launchd's cwd of `/` — crash-looping the agent under `KeepAlive` with no log explaining why (five panics observed before it happened to start). **S1 — the client-side server-identity check on the windows pipe (landed 2026-09-21; § Transports → *The client verifies WHO is serving before it speaks a word*).** `fauna_ipc::win_token::pipe_server_user_sid_string` is the probe; `sync_pipe_client::verify_pipe_server_is` refuses on mismatch *or* on an unanswerable probe, before the `SyncPipeClient` is constructed; the connect now sets `SECURITY_IDENTIFICATION` through `OpenOptionsExt::security_qos_flags` (std masks SQOS out of `custom_flags`, so the flag had to move to its own builder call to take effect at all); and `fauna_client_sync::agent::connect_ensuring_agent` takes a `terminal` predicate — `is_server_identity_refusal` in production — so the 10 s ensure-the-agent wait returns a refusal immediately instead of spawning against a name it can never win. The agent's own first-instance create failure now names the pipe and the name-taken hypothesis rather than a bare `Access is denied`. **Every in-tree consumer of the per-SID pipe goes through it.** The last one that did not — `fauna-ctl`'s sync client, which opened `current_user_pipe_name()` with a raw `tokio` `ClientOptions` and so neither verified the server nor capped the impersonation level (missed by both the `NamedPipeClientStream` and the `CreateFile` greps, being a third spelling of an open) — was moved onto `AgentEndpoint::connect`, and the tool was then deleted outright (2026-10-02, with the FaunaBridge service's pipe — [`installers/windows.md`](../installers/windows.md) § Feature Tree); `sync_pipe_client`'s own test still aims the real connect path at the SYSTEM-served pipes.

**The cross-account arm is pinned, and needs no second account — the "this needs an admin-created user" reading was wrong.** Windows already runs pipe servers under a *different* account that any ordinary user may open: the `NT AUTHORITY\SYSTEM` RPC endpoints (`\\.\pipe\{eventlog,srvsvc,wkssvc,atsvc,epmapper,lsass,InitShutdown,LSM_API_service}`). Pointing the production connect path at one is the squatter's shape exactly — a pipe answering under an account that is not ours — so `a_pipe_served_by_another_account_is_refused_with_no_privilege_needed` pins it directly, unprivileged. **Measured 2026-09-21 on Windows: all eight refuse, every one of them through the *could-not-identify* arm** — `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` on a foreign-account server returns `ACCESS_DENIED`. That is the rule above earning its keep rather than a curiosity: had a failed probe been allowed to fall through to a weaker check, or to a shrug, **every one of those eight would have been accepted**. A hand-made second local account would vary only *which* foreign account, not the code path. Mutation-verified — removing the verify call reddens exactly this pin and the injected-SID one, leaving the accept arm, the probe-failure arm and the impersonation-level pin green.
