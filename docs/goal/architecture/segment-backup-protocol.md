## Cross-location backup protocol

**Writer identity — REDESIGNED 2026-07-23 (nest-side writer BUILT 2026-07-24; the client-driven path below still ships alongside it until the slice-5 flip deletes it).** The segment-backup writer becomes the **source nest itself**: its in-process coordinator reads its own local segment files (no HTTP self-fetch — the transitional `GET /api/v1/segments/...` route loses its only consumer and retires with the flip), seals under the owner's `NestBackupKey` (`owner-key-material.md` § Path A-sibling-0), and uploads to each destination authenticated as the **nest** under a user-minted, revocable **nest-writer grant** registered at the destination at enroll. Because a custody writer's supersede power is delete power, two destination-side mechanisms bound a rogue source: a **custody grace window T = 30 days** (superseded/tombstoned generations' chunks retained ≥ T before reclaim — custody-level retention, never snapshot pins; quota-charged; client-drivable generation restore + grant revocation within T) and the seed-holding clients' **audit loop** (freshness + inclusion sampling, direct-to-destination). Custodian-authoritative custody below (omission-safe, latest-per-path, record-on-upload) is **unchanged** — only who records it and the reclaim timing change. **Nest→destination auth transport — RATIFIED 2026-07-23 (slice-3 design round; auth plane BUILT 2026-07-23).** The writer plane rides the **existing nest↔nest federation WS-RPC channel** (`federation.md` § Peer-auth model): the source nest's coordinator connects to each destination with the ordinary `fauna.federation.hello` handshake, and the destination's gate is the **nest-writer grant row it wrote itself** when the owner's client registered the grant — serve iff the row's writer nest pubkey equals the connection's verified `origin_nest_id`, the owner scope matches, and the grant is unrevoked (a nest signature is attribution, the grant is the authorization — the `channel.fetch` gate shape reused). **Not pairing-gated:** `is_paired` stays scoped to the private nest-sync surface; the user-minted grant is the allowlist entry, exactly as `folder_member_access` authorizes cross-nest folder writers. The kinds mirror the shared-folder write plane and are owned by `federation.md` § Nest-writer backup plane (custody record relay, exactly-once by content; short-lived write-only bulk-byte token mint with a Rust-constant TTL — bulk bytes never ride the federation channel; revocation refuses the next *mint*, an outstanding token's residual window is one TTL, the same accepted contract as `fauna.federation.folder.write_token.mint`). The owner's client talks to the destination **directly** (its own authed connection, USER-class kinds) for grant register/revoke/list, generation list/restore, and the **live-custody read `fauna.backup.custody.list`** (BUILT 2026-07-24 — the latest-per-path custody this destination holds for the owner: `folder_name`, `path`/`path_hash`, `manifest_hash`, `size_bytes`, and the destination's own `updated_at` receipt clock; tombstoned paths excluded, since a tombstone is the absence of custody) — so revocation remains operable with the source nest fully hostile, and so does *verification*: the audit loop's whole premise is that `fauna.backup.status` is the source nest reporting on its own uploads, and only the party holding the bytes can say what is actually there. Its consumer is `backup-restore.md` § Background Tasks' audit loop. **Built 2026-07-23 (slice-3 auth pass):** both federation kinds + the `require_backup_writer` gate + the destination grant store (`backup_writer_grants`) + the client `fauna.backup.writer_grant.{register,revoke,list}` USER-class family, tier_3-proven over a real handshake (`conformance_backup_writer_grant.rs`). The record relay resolves-or-creates the owner's reserved custody-copy custody set lazily behind the gate (owned by the owner, so `record_change_core`'s owner-pays metering charges the enrolled member for their own conv backup per the v1 shape). **Destination-side custody grace window `T` + generation list/restore — BUILT 2026-07-24** (see § *Custody grace window* below). *Rejected alternative:* a bespoke "lighter signed handshake" — it would re-implement the replay protection, TLS-SPKI binding, and discovery the federation channel already provides, and violate `federation.md` § Peer-auth's "do not invent a new envelope" rule while permanently adding a second nest-auth surface to the review perimeter. *Reconsideration trigger:* a destination class that is not a Fauna nest (e.g. an S3-compatible store) — that class gets its own transport design; **The writer seat — one source box per owner at a destination, and how the seat moves (RULED 2026-10-01; the destination half, the wire, the device's carry, the custodian's re-key and the source half BUILT — § Implementation status today).** The grant above keys the writer's authority on the source nest's identity, and so does a covered folder's mirror set name (§ *Ordinary-folder mirror records* below), while an owner's reserved-kind custody copy rests under `(owner, kind)` with no source in its name or in its paths. Two cases follow that nothing above decides, and both were reproduced before this ruling (§ Implementation status today names the tests). **Two source boxes of one owner granted at one destination** write the same segment paths from two unrelated segment numberings: each pass supersedes the other box's live copy, both boxes read as fully backed up, and a restore returns a mix. **A source box that rotates its identity** ([`nest/box-recovery.md`](nest/box-recovery.md) § Deployment-seed rotation) is refused at the gate, its status row says nothing of it, its predecessor's grant stays in force for a key the box no longer holds, and once the owner grants the successor a covered folder's mirror splits across two sets. They are one design, because whatever refuses a second writer must still admit the first writer's successor. The paragraphs below are that design.

**The seat.** At a destination an owner's nest-written custody has **one writer seat**: one row per owner, naming the one source nest that may write this owner's custody here, whether its grant is in force or revoked, and when the seat was taken. `backup_writer_grants` is that row (before schema 105 it was one row per `(owner, writer nest id)`, any number of them, and a revoke deleted its row). The gate keeps its shape — serve iff the connection's verified `origin_nest_id` is the seat's holder and the grant is in force — and refuses with a typed reason, `fauna.backup.writer_not_seated`, so a refused source can tell a refusal from an outage. **A revoke keeps the row**: it ends the holder's authority and leaves the seat held, because a revoke says *this box may no longer write* and never *another box may now overwrite what it wrote*; registering the holder again re-grants it. The seat covers both planes a grant covers, the reserved kinds and the covered-folder mirrors: a source registers every destination for its reserved kinds, so a box seated for folders alone would hold a destination whose reserved passes are refused for ever.

**A second source box is refused at its enrollment.** `fauna.backup.writer_grant.register` naming a writer other than the seat's holder is refused `fauna.backup.writer_seat_held`, the reply naming the holder (the error's `holder_nest_id` detail), while the owner's custody at this destination holds any live path. The second box's enrollment therefore fails at its grant step ([`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § Create / edit / remove protocol, step 3), on the page where the owner asked and before anything is recorded, and the first box's copy is never touched. This is the rule every other collision on a reserved name already follows — the role holding live state wins and the newcomer is refused ([`../behavior/reserved-folders.md`](../behavior/reserved-folders.md), the *A rail and a custody copy are told apart* paragraph) — extended to the one collision it did not cover, two writers. **When the custody holds no live path** — never written, or torn down by a removal (§ *Supersede / remove handshake* below) — the registration takes the seat: the previous holder's row is replaced in the same transaction and the seat's clock restarts. Generations retained from before the seat's clock are the previous writer's numbering: they age out under T, charged as ever, and `fauna.backup.generation.restore` refuses them (`fauna.backup.generation_before_seat`), since restoring one would put two numberings into one set by another door.

**How the seat moves — the owner's device carries it.** `writer_grant.register` gains `succeeds: <nest id>` (additive). Naming the seat's holder, over the owner's own authenticated connection to the destination, it moves the seat in one transaction: the successor becomes the holder with the grant in force, the predecessor's authority ends, the seat's clock is kept (the corpus continues, so its retained generations stay restorable), and every mirror set of this owner named under the predecessor (`__folder/<predecessor-hex>/<folder-id>`) is renamed under the successor. Custody rows key on the set's row id, so the rename moves no row and no byte, and the reserved-kind sets carry no source in their names and need nothing; a set already resting under the successor's name is left alone, and the predecessor's then keeps its own. A `succeeds` that does not name the holder is refused `writer_seat_held` and changes nothing, an owner with no seat here included; repeating a completed handover is a plain refresh. The destination verifies **no chain**: the owner is the authority over the grant and over the sets renamed, and could reach the same state by revoking and enrolling again at the cost of the mirror. A device names `succeeds` in two situations and in no other. **(1) Rotation:** the seat names an identity that a verified rotation chain links to the identity the device is bound to (`fauna_protocol::nest_rotation::verify_chain`, both signatures at every hop, the chain fetched from the bound nest as the list re-file already does), and the seat's grant is in force. That is automatic and takes no gesture. A revoked seat is not carried: the freeze outlives the rotation, and the owner's next enrollment of that destination from the rotated box names the predecessor then. **(2) A restore ceremony** that made this box the continuation of the corpus the holder wrote — a re-seed onto a fresh-identity nest, or the nest-held pull-back leg: the ceremony's re-enrollment of that destination names the box it replaced, and the ceremony's own confirm is the gesture (owed with those ceremonies; neither re-enrolls a nest destination today). Everything else is a second box, and is refused.

**Where the carry runs, and what else follows the identity.** The carry is shared Rust beside the trust projection (`fauna_client_backup`) and runs over the `BackupDestinationConnector` every shell already hosts, from two callers: the audit pass, ahead of its freshness arm and — on the first pass under a changed bound identity — regardless of `AUDIT_MIN_INTERVAL`; and the Nests-page trust facet's read, which already lists each destination's grants. Any of the owner's devices may carry and the act is idempotent, so no device needs to have seen the predecessor. The source nest carries nothing: every derivation there reads its current identity, and its upload state names destinations and folder ids, never a set name — which is why, once the seat has moved, its next folder pass lands beside the files it already sent. One rule covers every *stored* copy of a mirror set's name: **the name follows the box's current identity, and each store re-keys on the same verified chain** — the destination in the handover above; the list row's `folder_name` at the re-file (`backup-destinations.md` § State & data shape → *A rotated box keeps its list*); a client-device custodian's held mirror sets at its first pull bound to the successor, before that pull diffs (§ Client-device custodian (pull)); and the audit's client-local pins and mirror-plane population with the list row.

**Why a device, and not the destination on a chain (refused).** The rotated box could present its rotation chain over the federation channel and have the destination move the grant by itself — no device needed, no window. Refused: the chain's licence is the **superseded** key's signature, and a compromise-driven rotation assumes the adversary holds exactly that key. Anyone holding a superseded seed could sign a competing hop to a key of their own, dial the destination with it, and take the owner's writer seat — delete power bounded only by T — without interposing on anyone's path. A client's re-pin accepts that licence only because its plane has no stronger factor and because the client dials the box's true locator (`box-recovery.md` § The rotation statement (wire)); here neither holds — the source dials the destination, and the stronger factor exists: the grant is user-minted, and the owner's own session at the destination is an authority no nest key carries. It is the reasoning by which [`../behavior/identity-succession.md`](../behavior/identity-succession.md) refuses old-key continuity, on a plane where it applies. **The residue, stated.** (i) From the rotation until the first device carries, the predecessor's grant is still in force, so a holder of the superseded seed can write as the predecessor — the exposure rotation exists to end. It is bounded by T and the audit loop, and the carry closes it; bearer eviction brings every live device to its re-pin within one reconnect (`box-recovery.md` § Client acceptance → *Live-session convergence*), and the first audit tick after it carries. (ii) A device whose pin an interposing thief captured during convergence — that doc's stated, unsolved case — would carry the seat to the thief's key; every other device's trust row then reads a holder its own chain does not reach.

**What the owner sees meanwhile.** A refused writer is a state, never a lag: the source's status row reports that its destination refuses it (the row's `writer_state` — `backup-destinations.md` § Per-destination status read owns the field and its render), from the first refused pass until the next accepted one. A refused enrollment surfaces `writer_seat_held` in the add flow's own error. The trust facet's writer row for a seat held by another identity keeps reading *missing* ([`../ui/nests.md`](../ui/nests.md) § Trust facet — backup rows) until a device carries it.

**Refused alternatives.** *A source-scoped set name for the reserved kinds* (`__mail` under the writer's id, as the mirror sets are): it would let two boxes share a destination, and it is the wrong trade. A custody copy carries its rail's own name so that materialize flips it in place and one collision rule holds on every nest; a source in the name gives every reader a dimension that only a destination serving two boxes can tell apart — the custody list, the generation surface, the audit's population, re-seed, materialize; and a rotation would then re-key **every** set at every custodian, where a missed carry leaves a silently partial set under the new name rather than a refusal. *A writer remembered per custody set*: a grant covers every plane, so a second box would sit half-refused for ever — its folders accepted, its reserved passes refused. *The last enrollment wins*, the second box's grant tombstoning the first box's copy: the owner enrolling one box would destroy another box's backup one grace window later, on a page that never mentioned it. *A mirror-set name that never changes* (a namespace id fixed at attachment): every derivation — the destination's from the verified origin, the source's, the audit's — reads the current identity, and each would need the namespace instead; re-keying four stores once per rotation is the smaller surface. *The status heal registering a plain grant for the bound identity whenever none is in force*: it would undo the owner's own revoke, and with no chain behind it would hand the seat to whichever box the device happens to be bound to. **The limit this accepts, stated:** an account that lives on two boxes cannot back both up to one destination nest; the second enrollment is refused with the reason. Where the account's boxes replicate one another the second copy would be the same corpus under another numbering. *Reconsideration trigger:* a deployment that needs it for boxes holding different content — it gets a source-scoped namespace beside this one in its own design pass, and the seat row is the record that pass would migrate from.

**Reclaim rate-cap — RULED not-a-parameter (2026-07-23).** Retained superseded/tombstoned generations charge the owner's quota (above), so a supersede storm write-refuses at the owner's own quota boundary while T retains everything it superseded — **quota-charging is the rate cap**. The deferred defense-in-depth cap from the design record stays unbuilt; build trigger: a measured abuse signal quota-charging fails to bound (destination GC pressure or disk-guard trips attributable to a single writer's supersede churn).

**Conv multi-member shape, v1 — RATIFIED 2026-07-23.** The channel's home nest runs one (member, destination) coordinator tuple per **locally-homed enrolled member** — a member whose home nest *is* the channel's source nest and who holds a `NestBackupKey` grant + configured destinations — sealing the shared channel bytes (scope = `channel_id`) under that member's key, charged to that member's quota at their own destinations (N_local× multiplicity, ≤ the client-driven design's N×). A foreign member cannot enroll in v1 **by construction, not omission**: the root `NestBackupKey` is granted only to the user's own source nest, never to a foreign channel-home nest. Coverage bound, stated: channel content survives the home nest's death via any local enrolled member's restore; a channel with no locally-homed enrolled member is unprotected until the named follow-up — per-scope subkeys (`owner-key-material.md` § Path A-sibling-0, named future direction) grantable to a foreign channel-home nest, riding whatever flow first builds foreign-channel enrollment UI.

The wire surface that turns this layout into a usable cross-location backup was ratified 2026-05-15 (tracked internally). The two control-plane WS-RPC kinds (`fauna.segments.list` and `fauna.segments.changed`) and the one data-plane HTTP-residue endpoint (`GET /api/v1/segments/{kind}/{actor_hex}/{segment_id}`) compose with the existing fauna-sync chunk pipeline (`POST /chunks/check`, `POST /chunks`, `POST /manifests`) to ship segments from a source nest to a destination nest. The data owner's client mediates uniformly across every source nest — the same code path regardless of what capability grants the source nest holds, by construction (the protocol never opens an MLS-sealed record payload; the plaintext/encrypted deployment-mode axis this once branched on is retired — `nest/storage-modes.md`). The owner-only `BackupKey` seal applies on every chunk; the destination stores opaque ciphertext.

**Byte-source endpoint — a permanent route (ruled 2026-10-01).** `GET /api/v1/segments/{kind}/{actor_hex}/{segment_id}` (with its `/meta` sibling, next paragraph) is the segment plane's **permanent** byte route: `application/octet-stream`, CARv2 bytes since Layer 3, owner-or-custodian-authed (`bins/fauna-nest/src/segments/segment_route.rs`; listed in `api-layers.md` § Remaining HTTP). It was once called a transitional facade that a by-CID migration (Plan 5 close-out) would delete in favour of `GET|PUT /api/v1/blob/{cid_b32}`; that migration was never scheduled, two consumers have since been built on this route (the adopting replica's bootstrap and the client-device custodian's pull), and from the 2026-10 baseline on a served route can only be removed at a major. A by-CID fetch stays an additive option (a CID field on `SegmentRef`), never a replacement of this route within the major.

**The pair door — `.../{segment_id}/meta` (LANDED 2026-08-11).** The route family serves **both** halves of a segment: the `.dat` at the path above and its `.meta` sidecar at `GET /api/v1/segments/{kind}/{actor_hex}/{segment_id}/meta`. Same auth on both — owner, or a custodian holding a live capability row over that owner's content plane (slice 2, LANDED 2026-08-16 — `crate::custody_admission`; `api-layers.md` § HTTP residue) — and same finalize-on-read (which is also what puts the sidecar on disk — `finalize()` writes it). Two consumers: the **adopting** replica of [`account-data-plane.md`](account-data-plane.md) § *the bootstrap contract*, for which the sidecar is not optional — `record_order` lives nowhere else, and it is what rebuilds the local record index in append order (CARv2's own index is digest-sorted) — and, since **2026-08-29**, the **client-device custodian's pull** (`SourceBinding::segment_pair`), which ships the sidecar opaque beside its `.dat` so the backup corpus is reopenable (§ *The backup corpus carries the pair* below); a backup pass still never reads a record. Two shape rulings worth not re-deriving: the sidecar is a **path sibling, not a query parameter**, so a nest predating it answers a clean 404 (rendered client-side as the typed `SegmentMetaUnavailable` — "this nest is too old", never a misparse of `.dat` bytes as dag-cbor); and it carries **no `Range`**, because a single-digit-KB blob has nothing to resume. Both halves are permanent together (§ Byte-source endpoint above).

**The backup corpus carries the pair — RATIFIED + BUILT 2026-08-29.** Until this date every backup arm read and shipped `seg-NNNNNNNN.dat` alone, so nothing the corpus held could be reopened (`FramedSegment::open` refuses a `.dat` without its sidecar — the record footers, `record_order` + the per-record floor metadata, exist only in the `.meta`; found at the materialize build, 2026-08-22). The widening, all shared Rust (`fauna_sync_engine::segment_backup`) and additive everywhere:
- **Path.** `segment_meta_rel_path(scope_hex, id)` = `{scope_hex}/seg-NNNNNNNN.meta`, the sibling of `segment_rel_path` in the same reserved set — an ordinary custody path (latest-per-path liveness, the grace window T, GC, the custodian's cap and self-audit all see one more path per segment and nothing new). One shared read-side parser, `parse_segment_rel_path`, replaced the three hand-parses (pull, re-seed, audit) that a new file per segment would have drifted.
- **Wire.** `SegmentRef` carries `meta_blake3_hex` — a required field since the compat-remnant contraction of 2026-09-30, so a listing or mirror without it is refused at decode — minted by `fauna.segments.list` from the sidecar on disk, so the `manifest.<kind>` mirror anchors **both** halves and every pull verifies both in transit (`SegmentPair::verify_against`, the same check the bootstrap source runs). The `SegmentSource` seam's `.dat`-only method is gone: `segment_pair` is the read (a `.dat`-alone fetch is unrepresentable), `segment_meta_bytes` exists only for the backfill; the nest arm reads both files under the scope lock (`SegmentManager::read_segment_pair`). No independent sidecar change detector is needed: a finalized pair is immutable (compaction mints a *new* id and tombstones the inputs; in-segment tombstone counts live in the SQLite mirror, not the sidecar), so the sidecar rides its `.dat`'s diff decision. **`SegmentsListReply` carries `next_segment_id` (2026-09-28; required since 2026-09-30):** the source's saved `KindManifest::next_seg_id` for the listed `(kind, scope)`, which `LiveManifestMirror::next_segment_id_seen` now carries as the ledger's **generation** on both writers (`fauna_sync_engine::segment_backup::live_manifest_mirror` — the one place the counter is chosen, never below the greatest live id plus one). The saved counter never decreases while the source's data directory lives — append, compaction and re-seed adoption only raise it — where the derived value drops on an empty-output compaction of the top segment; and materialize adopts the ledger's generation as the re-seeded nest's counter floor (`SegmentManager::adopt_segments`, § Implementation status today), so a re-seed never restarts below the dead nest's generation. Its consumer is the audit's generation pin: `../behavior/backup-restore.md` § Background Tasks → *Implementation status (audit loop)*, seventh bullet. Since 2026-09-29 the same floor is client-drivable (the verb BUILT, the pass's call at acceptance NOT BUILT — § Implementation status today) on a lived-in source: `fauna.segments.counter_floor` raises the saved counter to the device's pinned generation when its pass accepts a source regression, so the destination's not-yet-reused lost segments are never overwritten (§ Client-device custodian (pull) → *Restore* → *Recovery into the lived-in nest that regressed*, part (0)).
- **Existing corpora — the backfill class.** Content addressing cannot fill a path that was never pushed, and every pre-widening `segment_backup_state` row says "done" (the corpus-gap-#1 lesson, below). So the row gained `last_meta_size: Option<u64>` (additive column; NULL on every pre-existing row *on purpose*) and the **shared** diff gained `to_backfill_meta`: an unchanged `.dat` whose row records no sidecar has its `.meta` fetched and pushed **alone** on the next pass by the custodian pull (`PullReport::backfilled_meta`; a custodian's "row" is its held index, and the live `.meta` sibling is what fills the field) — then never again. The nest coordinator's own backfill leg is retired (the compat-remnant sweep, 2026-09-30): it records every segment with its sidecar, so its diff never names one. Bounded cost stated: the mirror hash shifts exactly once per owner on upgrade (its refs now carry the sidecar hash) — one retained supersede under T, then stable; the backfill moves sidecar bytes only (single-digit KB per segment).
- **Accounting + teardown.** One more custody row per segment, each charged from held bytes as every reserved-set row is. Compaction and the removal teardown tombstone the `.meta` path only where the state says it was placed (`PlacedSegment::meta_pushed`), so a destination filled before the widening never receives a tombstone for a path it never held. The custodian admits a pair as **one unit** against its cap: a `.dat` held without its sidecar is exactly the half-corpus this closes.
- **Re-seed delivers the pair** (`.dat`, then its `.meta`, per segment, mirror last) and reports `sidecarless_segments` — a store that never completed a post-widening pull delivers its `.dat`s (they are real custody) but says which segments the target cannot yet reopen, rather than calling the corpus whole. A live `.meta` whose `.dat` is not live is not delivered.
- **Untouched by construction:** standalone restore (`CustodianStore::open` walks `file_download`, never `FramedSegment`) and the audit arms (a `.meta` row is one more owner-sealed row to sample). Since 2026-09-28 the mirror is also the inclusion arm's **population anchor** — every path it names must be custody at the destination, live or retained — which is one more reason it is written last: `../behavior/backup-restore.md` § Background Tasks → *Implementation status (audit loop)* owns that rule.
- **A sidecar in the corpus is anchored, or it is not restored — RULED 2026-08-30.** The mirror is the **only** thing binding a sidecar to its `.dat`. `FramedSegment::open` asserts two lengths and nothing about content (block count == `record_order.len()`, `floor_metadata.len()` == the same), and the seal is convergent *by design*, so it carries no path or scope binding — any sidecar of the same owner with an equal record count unseals and opens at whatever path it is served from. So the `meta_blake3_hex` check is **unconditional**, in transit and at materialize: the hash is a required field of every `SegmentRef` (since 2026-09-30), so a mirror or listing that does not name a sidecar is refused at decode, and a sidecar is never restored on the strength of that length check. A corpus holding **no** sidecar for a segment its mirror names is refused by its own name (`custody_incomplete`). One corollary keeps the half-anchored corpus **unreachable** rather than merely refused: a pass that backfills sidecars stores the mirror naming them **first**, under the ordinary cap check — so a cap-refused mirror or a crash mid-pass leaves "the mirror names a sidecar not yet held", the designed not-yet-caught-up refusal that the next pass heals, never "a sidecar held that nothing names". The rule is a restore-**integrity** one — the custodian never holds the key, so confidentiality was never at stake — and it is what makes `backup-destinations.md`'s "a destination holder is untrusted by construction" true of the sidecar half too.
- **Proofs.** tier_3 `bins/fauna-nest/tests/nest_backup_coordinator.rs::the_pair_a_destination_holds_reopens_as_a_segment_with_its_records` — the pair is opened off the destination's own byte plane under the granted key, written into a fresh segment area, and `FramedSegment::open` reads every record back — and `..::a_pre_widening_destination_gets_its_sidecars_backfilled_without_re_moving_the_dat` (staged through the production owner-authed custody door); tier_1 twins for the custodian pull (`custodian_pull.rs` — a real pair written by the segment store reopens out of the local store; the pre-widening backfill fetches sidecars only; a torn pair is refused; the cap admits pairs whole; compaction tombstones both halves), the re-seed leg, the diff's backfill class, the parser, and the wire's refusal of a ref without its sidecar hash.

**`conv` joins the serve plane — RULED 2026-08-18, BUILT the same day.** The reason is that the alternative would contradict ratified design rather than complement it: the shared-audience carve-out ([`account-replica-posture.md`](account-replica-posture.md) § The custody grant + ceremony → *Shared-audience carve-out*) already ratifies a `conv` channel entering a cross-account custody grant as an explicit list entry, and the backup plane's *Conv multi-member shape v1* (§ Cross-location backup protocol above) already ratifies each member independently arranging resilience for the shared sealed history — so a serve plane that cannot serve conv would leave a ratified grant form permanently unserveable, a gap and not an asymmetry. The serve contract, each piece anchored in a prior ruling:

- **Addressing — the actor field carries the channel.** `fauna.segments.list { kind: "conv", actor_id: <channel_hex> }` and the byte/pair routes at `/api/v1/segments/conv/<channel_hex>/...` — exactly the spelling the destination-capability gate already ratified (`folders.actor_id = channel_id`, § Destination capability) and the scope vocabulary already writes (`content:conv:<channel_hex>`). For the four actor-scoped kinds the actor field is both scope id and custodied owner; for conv it is the **scope id alone**, and the owner is read off the authorizing grant row.
- **There is deliberately NO channel-enumeration door.** No request on this plane answers "which channels does this member have" — a custodian can name only the channels its verified grant explicitly lists, which is the coverage-enumeration ruling applied verbatim (enumeration is an authorization computation, never an observation computation; the explicit-list form is self-naming). "Which conversations does this account have" stays sealed ([`../principles.md`](../principles.md) § *The user always controls their data*): the grant discloses exactly the channels its minting member deliberately named at ceremony time, nothing more.
- **Authorization is the member-mint rule**, owned by the shared-audience carve-out (see there — including which roster is the membership authority: the floor roster, never the send-writable `actor_channels` routing roster): an `Account` grant refuses conv loudly (built, mutation-graded — `custody_admission.rs`); a conv plane serves only under an explicit-list row naming exactly `content:conv:<channel_hex>` whose owner is a **current member** of the channel, membership re-derived on every request beside the live-row re-check, so leaving the channel severs serving exactly as revoke does.
- **Coverage bound — uniform with backup v1, plus the roster bound.** Conv serves from the nest that holds the channel's segments: the channel's **home** nest. A locally-homed member's mint covers the channel; a foreign member's mint is honest under-coverage (their own home nest holds no segments for it, so enumeration is empty there) until foreign-channel enrollment builds — the same bound, and the same follow-on trigger, that *Conv multi-member shape v1* states for backup. **Second honest bound (the membership-authority consequence): a channel with no floor-roster row fails closed on this plane**, because the nest then holds no non-self-assertable membership record for it (a DM was such a channel until the client began reporting every end-to-end room's roster at its birth, 2026-09-10 — [`account-replica-posture.md`](account-replica-posture.md) § *Shared-audience carve-out*).
- **What the custodian holds and serves.** Class-1 sealed `ChannelEnvelope` records — keyless bytes-at-rest, no MLS anything beyond blobs already opaque to it — served onward to the **granting member's own fleet only** (custody's contract never serves other M2 members; a member pulls the shared plane from their own account's replicas).

**Per-kind generalization.** The protocol surface is kind-parameterised: `fauna.segments.list { kind, actor_id }`, `GET /api/v1/segments/{kind}/...`, `fauna.segments.changed { kind, ... }`. **Conversations, posts, and calendar/card have all landed their destination-side capability enforcement** (conv = the conversations-segment rollout's Plan 9; post = Track C posts, Plan C; calendar/card = S6.10, 2026-07-10): conv reuses the protocol with `kind = "conv"` and `actor_id = channel_id`, post with `kind = "post"` and `actor_id = author`, calendar/card with `kind = "calendar" | "card"` and `actor_id = actor` (the mail shape), each plus its four-gate capability at § Destination capability (for post, gate 1 is satisfied by construction — no plaintext post-serving surface is bound to backup custody). The `segment_route.rs` HTTP residue served mail only until 2026-08-11, when **post** joined it (and `fauna.segments.list`) for the adoption arm — § *Which kinds the two planes serve* above. That is a *read* surface only: a kind is backed up when the shared `BACKED_UP_KINDS` (`libs/fauna-sync-engine/src/segment_backup.rs`) lists it — `"mail"`, `"post"`, `"calendar"` and `"card"` since 2026-09-29 (§ Implementation status today) — not by its presence on the read planes, and conv, which scopes on a channel rather than the owner, is not in it. Every backup runner treats segment bytes as opaque, so the conv case is the same per-scope sweep shape as mail — for conv the data owner is each *member* (scope = `channel_id`, each member's seal is under their own key material; DM = 2×, group = N×, long-term-accepted per spec § D7). The multi-channel/per-member *orchestration* (which channels a member backs up, to which destinations) is deferred uniformly with growing the nest arm's kind list.

**GC-safety — custodian-authoritative custody (corrected 2026-06-15; supersedes the 2026-06-14 "live-segment-backup-manifest ledger").** Segment-backup chunks + the `manifest.<kind>` mirror are uploaded through the standard chunk pipeline but **deliberately skip** the `record_change` epilogue (`SyncEngine::upload_bytes`), so they appear in no `snapshot_files` / `sync_changes` row. The § 9 GC (`docs/goal/behavior/backup-restore.md`) runs on **every** node and builds its reference set from exactly those two tables — so on a *destination* nest every segment-backup blob is unreferenced and is **deleted one cycle past grace = loss of a live backup** (the data-loss gap in `backup-restore.md` § Known gap: segment-backup blobs vs GC).

> **Why the 2026-06-14 "ledger" design was wrong** (flow-traced against the coordinator + `segment_backup_round_trip_test.rs` at implementation time, 2026-06-15). It proposed a nest table of *one* live `manifest_hash` per `(owner, scope, kind)`, registered by the client via `fauna.segments.register_manifest` and walked by GC. Two load-bearing flaws:
> 1. **A backup is N manifests, not one.** The coordinator uploads each segment as its own `upload_bytes` call, and each `upload_bytes` produces its own `ChunkManifest` (`engine.rs::upload_chunked_bytes`; the round-trip test asserts "2 segments + 1 mirror = 3 manifest POSTs"). The `manifest.<kind>` mirror is a `LiveManifestMirror` (a list of `SegmentRef`s keyed by *file-content* blake3), **not** a `ChunkManifest` over the segment chunks. So registering one manifest hash protects at most one segment's chunks; GC deletes the rest = the data loss the feature exists to prevent.
> 2. **Client-declared liveness is unsafe at scale.** A *full-set re-declaration* protocol makes GC-safety depend on every app — including third-party — correctly enumerating the live set every cycle, forever: **omission deletes.** One client with an off-by-one, offline across a grace cycle, or buggy → silent data loss of a backup (or, in the protect-forever variant, an unbounded chunk leak that fills the destination's disk).

> **Walk semantics (owner: `backup-restore.md` § 9).** How GC consumes the custody set — reference classification (direct-blob rail vs `ChunkManifest`), the chunk walk, and the 2026-07-09 fail-closed rule (an undecodable manifest skips the delete phase for that run rather than silently orphaning its chunks) — is specified in [`backup-restore.md`](../behavior/backup-restore.md) § 9 Garbage Collection; this section owns only the custody *projection* the walk reads.

**The corrected model — the custodian owns liveness, per-path and incrementally.** GC-safety is a property of **the custodian holding the opaque bytes**, not of the uploading client. A backup is a **file-sync of the owner's reserved backup folder to the custodian**: the coordinator uploads each segment + the `manifest.<kind>` mirror as files and **records each path's current manifest** on the custodian (the standard `fauna.sync.changes.record` → `sync_changes` path `upload_bytes` skips today — the skip is a *source-nest* concern, never a destination one). The custodian accumulates these per-path records into its own authoritative live set; GC walks that set. This is **omission-safe**: a path the client doesn't re-mention stays live — a custodian never reclaims a backup path's chunks because a client failed to re-declare it. Reclamation fires only on an explicit **supersede** (a new manifest for the same path → the prior manifest's now-exclusive chunks reclaim) or explicit **delete** (compacted-out segment, or destination removal → path / folder deletion). This is exactly the file-sync reclamation contract, applied to backups; *omission-safe + explicit-delete* is the crux distinction from the rejected full-set ledger (*omission-deletes*).

**What the custodian (= the nest, the first implementor) does, beyond plain file-sync** (the **nest half landed + tier_3-proven 2026-06-15** — the dedicated-projection realization below; `bins/fauna-nest/tests/segment_backup_gc_safety.rs`. The record-on-upload + removal-reconcile that feed it are the **nest arm's** since the slice-5 flip — tier_3-proven with no client alive by `bins/fauna-nest/tests/nest_backup_coordinator.rs`; the client coordinator that originally fed it, and its end-to-end test, were deleted 2026-08-17 — see § Implementation status today):
- **(a) Custody-copy folders are device-pull-excluded.** A reserved custody-copy set (`folders.custody_copy` — `../behavior/reserved-folders.md` § Destination capability; the nest-internal flag, written only by the two provisioners) is write-only custody — never served to a device's catch-up query. **Realized** by routing a **reserved** custody-copy destination set's records (`is_reserved_backup_set`, becoming `is_reserved_custody_copy` — § *Scope clarification* below; an ordinary folder's records route to `sync_changes` like every other folder) into a dedicated `backup_custody` table (below) instead of `sync_changes`, so the exclusion is **automatic by construction** — there is nothing for `get_sync_changes_for_folder` to filter (the records simply aren't in the device-sync feed). (The MLS device-sync fanout was already decoupled — it lived in the WS data plane's `FileChanged` handler, removed 2026-10-02, never in the `sync_changes` insert — so recording posts to no channel.)
- **(b) Backup custody reclaims latest-per-path.** Plain `sync_changes` is append-only with no prune, so GC's `SELECT DISTINCT manifest_hash FROM sync_changes` protects *every* version ever recorded — acceptable for the device-sync feed, a leak for backups. The custodian's backup reference set is the **latest non-deleted manifest per `(folder, path)`** across custody-copy reserved sets, so a superseded segment's old manifest drops out and its exclusive chunks reclaim. **Realized** as the thin dedicated `backup_custody` projection (`MIGRATIONS_BACKUP_CUSTODY`; PK `(folder_id, path_hash)`, UPSERT on supersede, `manifest_hash = NULL` tombstone on compacted-out, whole-set delete on destination removal) the `fauna.sync.changes.record` handler maintains for **reserved** backup sets — latest-per-path by construction (no GROUP-BY over append-only history), the cleaner of the two options the design floated.

**Scope clarification (re-scoped 2026-08-17): custody routing keys on RESERVED (`__*`) custody-copy destination sets only** — the seam is `fauna_nest::db::snapshots::is_reserved_backup_set`, becoming `is_reserved_custody_copy` over the nest-internal `folders.custody_copy` flag when the mode contraction lands (ruled 2026-09-28, `../behavior/reserved-folders.md` § Destination capability). From 2026-07-17 to 2026-08-17 the routing keyed on the folder's declared backup type alone, which also swept in ordinary user backup-type sets (the folder wizard's backup type, Photo Library included); the folders re-model phase 3 **head unification** moved those to the `sync_changes` head feed like every other folder, and their legacy custody rows were deleted (approved alpha deletion — `../behavior/folders.md` § Implementation status today). A reserved destination set is never snapshotted (scheduler skip + `pure_backup_destination` refusal), because a snapshot pin on the custodian would defeat (b) with no owner control. Owner of the snapshot mechanism: [`../behavior/backup-restore.md`](../behavior/backup-restore.md) § *Backup folders and snapshots*. This section's custodian contract is stated for destination sets and is unchanged.

**GC reference-walk extension** (`bins/fauna-nest/src/backup/gc.rs`, **landed 2026-06-15**): the GC reference walk chains `backup_custody_manifest_hashes()` (the live, non-tombstoned custody manifests) into the `all_manifests` set GC decodes for chunk references — alongside `snapshot_manifest_hashes` / `sync_change_manifest_hashes`. Manifests are stored **plaintext** and production GC runs with `encryption_key = None`, so the custodian decodes backup manifests to reach their chunk references **without holding the owner's `BackupKey`**. GC's walk needs only the manifest's **store keys** (`store_keys()` — for a sealed-chunk manifest that is `stored_hashes`, the ciphertext blob keys the custodian already holds); a sealed-chunk manifest names no plaintext `file_hash`/`chunk_hashes` (they ride sealed — `mls-group-key-material.md` § M2 *Sealed manifest hashes*), and GC needs none — the held-for-friends case works unchanged (the friend's nest reclaims its own custody without ever decrypting content; chunk bodies stay opaque ciphertext).

**Supersede / remove handshake (replaces register/deregister-set):**
- **Per-path record on upload** — the coordinator records each uploaded segment + the mirror as a path on the custodian (manifest-hash carried; `change_type` `create`/`modify`), right after the chunk + manifest upload (well inside GC's 30-min grace). **No** full-set re-declaration.
- **Backpressure — RULED 2026-10-13; BUILT 2026-10-13 (`segment_backup::relay_custody_record`).** The destination's federation throttle admits custody records at the writer-plane budget (`federation.md` § Nest-writer backup plane → *Throttling* owns the budget and why), and a `rate_limited` answer to a custody record is **backpressure, never a failed pass**: the coordinator waits a short constant (`RECORD_BACKPRESSURE_WAIT`, 2 s) and retries the same record, and after a full throttle window of consecutive refusals (`MAX_RECORD_BACKPRESSURE_RETRIES`, 30) it **pauses** that `(destination, kind)` tuple — progress kept, since every recorded path's `segment_backup_state` row already advanced before the pause (the record-before-advance ordering above), the tuple counted *paused* and never *failed* in the pass outcome, so it cannot stall the `backup-upload` lease ([`../behavior/participants.md`](../behavior/participants.md) § The nest as runner), and the next tick resumes where it stopped. One relay helper under the custody record carries the contract to every caller — the content pass, the placement journal, the folder-mirror axis and the removal/detach teardowns. The backlog the status row reads ([`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § Per-destination status read) drains across ticks at the destination's admitted rate with `writer_state` ok — an ordinary lag, which is what it is. Constants are Rust, refutable with telemetry.
- **Compacted-out segment** — recorded as a `delete` for that path → custody entry drops → its now-orphaned chunks reclaim.
- **Destination removal** — the trigger: a destination the owner removed (dropped from its source box's destination list and, via `fauna.backup.destination.remove`, from the source nest's registry), detected by the nest coordinator's removal-reconcile at the start of every `run_all_tuples` pass, which reconnects via the per-destination `backup_destination_seen` row the coordinator persists each pass and forgets the local rows only once the teardown lands. Single atomic decision point + loop-reconcile (crash-/offline-recoverable, no SSH cleanup; `nest/common.md` § Client-state recoverability). At the destination, **two teardown shapes exist, decided by who is authenticated — one automatic driver ships (the nest's); the other shape is a standing owner capability with no driver**:
  - **Writer-authenticated (the nest arm — the shipped automatic teardown)** — `NestBackupCoordinator::reconcile_removed_destinations` records a per-path `delete` over the nest-writer grant for every path its own `segment_backup_state` / `segment_backup_manifest_state` rows say it placed there. It **cannot** use the set delete: that authenticates as the owner, which the source nest is structurally unable to do. So the tombstones take the ordinary writer path and their generations are retained for `T` — the deliberate bound on a rogue source nest's delete power (§ Custody grace window), which is why this arm reclaims one grace window after removal rather than instantly. Its dial is pinned against the `nest_id` stored beside the URL in `backup_destination_seen`, which its one writer — this arm — always stores, so the column is `NOT NULL` (the local-only teardown once kept for a pin-less row went with the compat-remnant sweep, 2026-09-30). **Landed + tier_3-proven 2026-08-16** (`nest_backup_coordinator.rs` — the teardown itself, and that a refused teardown keeps its rows so a later pass completes it).
  - **Owner-authenticated (a destination-side capability; nothing drives it automatically)** — `fauna.folders.delete` of the owner's reserved backup set drops **all** its `backup_custody` entries in the same transaction (`delete_folder_for_user`, **landed 2026-06-15**), retained generations included, → every chunk it protected reclaims on the next GC. Generations go too because this is the *owner's* authority over their own backup, not a writer's (`SyncDb::delete_backup_custody_for_folder`'s own note). The client coordinator that drove this automatically pre-flip was **deleted 2026-08-17** (the seam corollary's ratified retirement); what remains is an ordinary owner-class API any app — or a future "forget this destination now" affordance, or an S3-class destination design — can call. Still pinned without that driver: the delete handler's reserved-backup carve-out (`conformance_folders.rs::delete_still_allows_a_backup_mode_reserved_destination_set`), the generations-included drop (`sync_storage.rs`'s in-crate remove-credits-back-retained-bytes test), and custody-drop → full reclaim (`segment_backup_gc_safety.rs` scenario 3).

**Ordinary-folder mirror records (BUILT 2026-08-20 — the coverage slice's wire mechanics; the attachment concept is owned by `../behavior/backup-destinations.md` § Ordinary-folder coverage).** A covered folder's mirror rides this same plane with three additions, all additive: **(1)** `FedBackupChangesRecordRequest` gains `folder_id: Option<i64>` — when present the destination derives the custody set as `__folder/<origin-nest-hex>/<folder-id>` from its own **verified** `origin_nest_id` (`folder_backup_set_name`, the `reserved_backup_set_name` sibling), never from a writer-declared name, so a writer can never aim custody at another source nest's mirror namespace; the `kind` on such records is the attribution constant `"folder"`, and an older destination that drops the unknown field falls into the kind-derived branch and refuses loudly rather than mis-filing. **(2)** The destination custody **path is the source row's `path_hash` hex** — a synthetic plaintext machine path, uniform across sealed- and plaintext-path source rows so supersede keying cannot fork when a folder's audience flips — and the request's additive `path_sealed: Option<Vec<u8>>` carries the source row's sealed name blob as-is (already ciphertext, blind to the destination) so a restore can recover names under the owner's keys. **(3)** The bytes are **copied as-is, never re-sealed** — the pushed manifests + chunks are the source nest's at-rest corpus, moved over the same `WriteTokenBearer` byte plane the segment pass uses, so no `NestBackupKey` is involved anywhere on this axis; every reserved-rail custody behavior (grace window T, destination-derived charging, device-pull exclusion, snapshot refusal) applies structurally via the `__` prefix.

### Custody grace window (T) — BUILT 2026-07-24

The three bullets above describe reclamation as it applies to an **ordinary** folder. On a
**reserved destination** set the reclaim is *delayed*, and that delay is the rogue-source mitigation:
since the custody writer is now the owner's **source nest**, supersede power is delete power, and a
compromised source could otherwise erase a whole backup by re-recording every path with junk.

- **T = 30 days**, `fauna_protocol::backup::BACKUP_CUSTODY_GRACE_SECS` (shared since 2026-09-29;
  the nest re-exports it as `crate::backup::gc::BACKUP_CUSTODY_GRACE_SECS`) — a bucket-1 Rust
  constant (no human ever chooses it). All the client-side `AUDIT_*` cadences
  (`backup-restore.md` § Background Tasks) sit ≪ T by construction, which is what bounds
  loss-under-attack by *audit cadence* rather than by T. A client renders deadlines from the
  `grace_secs` the destination reports, never from the constant; the one client reader of the
  constant is the audit's vanished-ledger rule, which floors the reported window at it because the
  audited party's word cannot shorten the window its own retention is judged by
  (`backup-restore.md` § Background Tasks → *Implementation status (audit loop)*, seventh bullet).
- **Retention is a side table, not a delayed delete.** A supersede/tombstone *forgot* the prior
  generation before this landed — `backup_custody` is PK `(folder_id, path_hash)`, so the UPSERT
  overwrote `manifest_hash` in place and the GC reference walk could never see it again. The
  displaced generation is therefore **moved** into the append-only `backup_custody_generations`
  (PK `(folder_id, path_hash, manifest_hash)`; a repeat supersede of an already-retained content
  refreshes its clock rather than adding a row, so a flapping path keeps a bounded row set). The
  LIVE row keeps latest-per-path semantics byte-identically, so every existing custody consumer is
  unaffected.
- **Scope: reserved destination sets only** (`is_reserved_folder_name` + the custody-copy flag). An
  ordinary user folder is written by the owner's own client and already pins its superseded
  versions with real snapshots (§ Scope clarification below; `backup-restore.md` § *Backup folders and
  snapshots*) — retaining generations there too would double-protect and double-charge
  the same bytes. A reserved destination set is never snapshotted, which is exactly why it needs
  this instead of a pin.
- **Quota-charged for the whole window** — this *is* the supersede rate cap (ratified 2026-07-23,
  "reclaim rate-cap = not-a-parameter"): a supersede storm walks the owner's own quota boundary and
  the next write is refused with `storage_quota_exceeded`, so no bespoke limiter is needed. Bytes
  are credited back when the generation reclaims at T, and also when the owner deletes the set
  (their own authority over their own backup is not what the window bounds).
- **The charge is DESTINATION-DERIVED, never writer-declared (2026-07-29 — review (xxxi-c)).**
  For the cap above to bind, the charge must be real: a writer-declared `size_bytes: 0` would make
  a supersede storm free. So on a **reserved destination set** `record_change_core` ignores the
  wire `size_bytes` (kept for attribution/compat) and charges the bytes this nest **actually
  holds** — the named manifest blob plus its distinct `store_keys()` chunks, at the
  server-measured stored sizes the chunk/manifest POST routes metered into `blob_metadata`
  (`backup/custody_charge.rs`). A record naming bytes the destination does not hold — absent
  manifest, undecodable manifest, or a missing referenced chunk — is **refused** with the typed
  retryable `fauna.sync.backup_bytes_not_held`, never charged as zero or as declared (an
  unreadable manifest fails closed); an honest writer never sees the refusal, because both
  coordinators record *after* their upload (record-on-upload above). The charged amount is stored
  in the custody row, and every credit leg (tombstone, T-reclaim, set-delete) reads the row back,
  so charge/credit stay symmetric across versions with no floor constant. A content-identical
  re-record (the live manifest recorded again — a crashed-ack re-drive) is a freshness touch:
  no charge, no retained generation. Ordinary (non-reserved) folders keep the declared
  size — their writer is the owner's own client on the owner's own quota, the same posture as the
  whole device-sync metering plane; the charge-honesty boundary is exactly the grace window's
  foreign-writer trust boundary. Corollary: custody on a reserved set can only ever reference
  decodable manifests whose chunk sets are fully held — the same set the GC walk can enumerate —
  and `custody.list`'s `size_bytes` becomes the destination's own statement of held bytes
  (pre-derivation rows keep the declared value until re-recorded).
- **GC ordering is load-bearing.** `do_gc` reclaims expired generations **before** building the
  reference set, and `collect_reachable_hashes` pins every generation row that still exists — so
  "the row exists" and "its chunks must survive this sweep" are the same statement, with no cycle in
  which a generation is neither reclaimed nor protected. The reclaim lives in `do_gc`, not in
  `collect_reachable_hashes`, because the latter is the box's shared reachability oracle rather than
  a sweep step — it was written that way for a second consumer, the `__index` boot purge (which had
  to pin generations without expiring them; deleted 2026-08-02, `content-index.md` § Before Plan 5b),
  and the separation still holds for any future one.
- **Client-drivable recovery** — `fauna.backup.generation.{list,restore}`, USER-class, spoken by the
  owner's client on its **own** authed connection to the destination (never through the source: the
  source is the writer being recovered from). `list` reports each retained generation with its
  `superseded_at` + the window `grace_secs`; `restore` promotes one back to live, retaining the
  generation it displaces by the same machinery, so restoring is never itself destructive. Both are
  owner-scoped by the authenticated actor, so a caller only ever reaches custody held for itself.
  **Both list reads are paged (2026-07-29; `fauna.backup.custody.list`
  identically):** a supersede storm is exactly when these reads matter, so an unpaged serve that
  breaks the 2 MiB frame at a few thousand rows would make the backup unrecoverable for the whole
  window. Each reply is cut at the ratified byte budget (`transport.md` § Max frame corollary,
  frame − 64 KiB, `take_page_within_budget`) and carries a **server-minted** opaque `next_cursor`
  (additive; the deterministic order's tiebreaker is a rowid no client can see, so the cursor cannot
  be client-derived) — present iff more rows remain. The shared-crate walk
  (`fauna_client_backup::{generations,audit}`) follows `next_cursor` to absence with a no-progress
  guard that degrades to `Unreachable` (fail toward "could not ask", never false-clean), so no shell
  owns paging. Compat is additive-everywhere: a cursor-less request (old client) is answered with a
  budget-bound first page — every case where that shows fewer rows than the unpaged serve is a case
  where the unpaged serve could not be delivered at all — and an old nest ignoring the cursor answers
  its complete unpaged reply, whose absent `next_cursor` ends the walk after one page.
  **Client leg — shared Rust BUILT 2026-07-29, no shell yet.** `fauna_client_backup::generations`
  owns the whole projection (`list_retained_generations` / `restore_generation` over the same
  `BackupDestinationConnector` the trust facet opens, plus the two `BackupNestSeam` methods the
  `impl_backup_nest_seam!` macro writes for every app's glue), so a shell implements no recovery
  logic. Three things it settles once, for all 7 apps: `expires_at` is derived from the wire's
  `grace_secs`, never a client-side copy of `T`; a destination that cannot be reached is
  `Unreachable`, never an empty "nothing to recover"; and a `restored: false` reply is the product
  state *past-`T`-or-unknown*, not a failed restore. Proofs: 12 tier_1 tests
  (`libs/fauna-client-backup/src/generations.rs`) + tier_3
  `bins/fauna-nest/tests/conformance_backup_generation_client.rs`, which supersedes a real custody
  row and lists/restores it through the shared seam, and pins the quiet failure by aiming the same
  calls at a nest that holds no custody. **The UI is the open gap:** `ui/nests.md` § Trust facet —
  backup rows ratifies only the seal + writer-grant rows, so where retained generations render and
  under which element IDs is **not yet ratified** and needs rule-A ID approval before any shell is
  built. No FFI/wasm projection exists yet either — it lands with that first shell rather than
  standing as an uncalled export.

**Proof (tier_3, `segment_backup_gc_safety.rs`):** inside T a superseded/compacted-out generation's
chunks survive the real `garbage_collect`; past T they reclaim and their bytes are credited back;
and the full rogue-recovery journey — source overwrites a segment with junk → owner lists the
retained generation → restores it → the junk ages out → the restored backup is what survives — runs
end to end through the real `fauna.sync.changes.record` handler.

**Custodian portability (updated 2026-08-02 — the second custodian is now ratified, design-only).** The liveness record + reclamation is a property of *whatever holds the bytes*. The nest is the **first** custodian implementor; the **second is now ratified: the owner's own client device**, nest-mediated pull (§ Client-device custodian below — the constraint that nothing weld "custodian = multi-tenant nest" into the wire held, which is exactly what made the kind cheap to ratify). The "client backs up to a peer client with no nest" case remains the *same* contract on a peer custodian (a peer derives liveness from what it received and reclaims its own disk — exactly what a safe backup target needs, and what the rejected client-declared ledger could never give a peer) and remains **not built and not designed** — do not pre-build it. A `Custodian`-shaped abstraction, if the implementation wants one, lands *with* the client-device consumer, not before.
