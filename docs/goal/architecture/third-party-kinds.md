## Kind namespacing + third-party kinds (D3/A6 — ruled 2026-08-11)

Kind strings freeze on first seal, so the namespace grammar must predate
the first third-party kind ever written — it is a paragraph now and nearly
impossible to retrofit:

- **`fauna.*` is reserved for first-party kinds.** Third-party kinds take
  a DNS-anchored prefix — `ext.<domain>.<name>` (e.g.
  `ext.example.com.reading-list`) — with the same frozen registration
  columns every kind declares: class, merge policy (the closed five-policy
  set), audience rung, floor contribution (default: nothing). **The exact
  grammar — which part is the domain, which the name, and how a wildcard
  reads it — is § The grammar (ruled 2026-10-02).**
- **Third-party kinds register via a signed kind-manifest riding the plane
  itself** (finding A6), not a compiled-in registry row: the manifest
  (signed by the publisher's domain-anchored key) declares the kind's
  class and merge policy from the closed set, so any up-to-date *engine*
  converges kinds whose *semantics* it has never seen — without it, a new
  third-party kind's convergence would wait on a binary bump on every
  replica, recreating the schema-migration coupling this plane exists to
  kill. First-party kinds stay compiled registrations (they ship with the
  binary). **The audience rung is structurally outside the manifest**: it
  remains key-branch-enforced (§ The audience ladder), so a manifest can
  declare merge semantics but can never widen who opens the kind.

**Third-party kinds under the third-party integration chain (TP7, ratified
2026-09-05; unbuilt — no manifest type or parser exists, and the default
rung is fleet-only, so no `ext.*` kind is grantable today).** Four
sharpenings, each on the ruling above:

- **The kind-manifest is the same signed object as the `kinds` member of the
  principal's Client ID Metadata Document**
  ([`third-party.md`](third-party.md) § The manifest) — one signature by the
  publisher's domain-anchored key covers both the OAuth identity and the
  kind semantics, so a kind's publisher and a principal's publisher cannot
  disagree. The manifest declares class, merge policy (from the closed
  five-policy set), floor contribution and requested scopes — **and nothing
  about audience.**
- **The audience rung is set by user consent at grant time, performed by
  the key holder.** At consent the user's device (1) verifies the manifest
  signature against the domain the document is served from; (2) admits the
  kind's class and merge policy into its local registry, so the engine
  converges it (finding A6's whole point); (3) derives the kind's key branch
  on the **delegable rung** and wraps it to the principal — `content.read` +
  `content.write` tuples over that kind prefix × epoch
  ([`encryption-at-rest.md`](encryption-at-rest.md) § Capability tiering →
  *Third-party holders*). Nothing widens without the key holder's act. The
  per-rung sub-scopes (A5, § The audience ladder) are the mechanism; the one
  an `ext.*` grant subscribes is § The `ext` sub-scope.
- **Own-domain kinds are "the app's own data"; a foreign kind is legal
  under the same consent with a louder card.** A manifest naming a kind
  outside its own domain prefix is refused at resolution; a *scope request*
  for another publisher's kind is legal, but the kind's semantics still come
  from its own publisher's manifest. **No `fauna.*` kind is ever grantable
  to a principal by name** — first-party kinds are reached only through the
  Fauna scope family's *plane* verbs
  ([`../behavior/authorization-server.md`](../behavior/authorization-server.md)
  § Scope grammar).
- **Two doors onto the same plane, because a remote server will not speak
  DAG-CBOR WS-RPC:** the plane's existing put/get/walk kinds over WS-RPC
  (device apps, hosted code), gated by caller class and token scope, records
  sealed client-side under the kind's branch; and an **HTTP record door**
  for remote servers — `/api/v1/records/{kind}[/{key}]` with `GET`/`PUT`/
  `DELETE` and a cursor walk, bearer = a DPoP-bound access token, body = the
  sealed record bytes the principal sealed with its granted keys. The nest
  stores opaque bytes and validates only the floor (kind string, size,
  merge-policy-compatible envelope); the kind manifest is the schema
  authority and travels with the principal. The door's HTTP-residue
  classification is [`api-layers.md`](api-layers.md) § HTTP residue's.
  Which kinds the WS-RPC door is, and what each checks: § The record doors.

## The grammar (ruled 2026-10-02; refutable until the first `ext.*` seal)

**`ext.<publisher>.<name>`, where `<name>` is exactly one label and `<publisher>` is everything between `ext.` and the last `.`.** The 2026-08-11 spelling left the split ambiguous — a DNS name is itself dot-separated, so publisher `example.co` with name `uk.notes` and publisher `example.co.uk` with name `notes` minted one string, and a string-prefix wildcard for `example.co` reached everything `example.co.uk` publishes. Making the name a single label is what makes the publisher recoverable from the string alone: two distinct `(publisher, name)` pairs can never spell one kind, and a wildcard needs no prefix test.

- **`<publisher>` is the publisher's domain, lowercase, exactly as it is the host of the metadata document's URL** (`client_id`): one or more DNS labels of `a–z 0–9 -` (no leading or trailing `-` in a label, each 1–63 bytes, the whole at most 253), an internationalized name in its punycode (`xn--`) form, never a trailing dot, never a port, never an IP literal's brackets. **Host equality, not a registrable-domain rule:** `api.example.com` is its own publisher, and `example.com` can neither claim nor cover its kinds — the same-origin rule the document's identity already rests on, applied to the kind. The loopback developer carve-out's synthesized document ([`third-party.md`](third-party.md) § Developer loop) publishes under its loopback host literally, so a dev plugin's kinds never collide with a real publisher's.
- **`<name>` is one label of `a–z 0–9 _ -`, starting with a letter or digit, 1–63 bytes, and never containing `.`.** A hierarchy a publisher wants inside its namespace is spelled with `-` or `_` (`reading-list`, `room_member`), never with a dot; `ext.example.com.reading.list` is refused as malformed, not read as publisher `example.com.reading`.
- **Parse by the last dot, refuse rather than repair** — the scope string's posture ([`account-sync-plane.md`](account-sync-plane.md) § Feeds and cursors → *The scope string*, ruling 3). Strip `ext.`, split at the last `.`, validate both halves; uppercase, an empty half, a bad label, or a `fauna.` prefix is a parse error. One shared-Rust constructor and parser (`fauna_protocol::ext_kind` — a `ExtKind { publisher, name }` whose `Display` is the canonical string) is the only door, and every consumer below — the manifest parser, the scope family, the `records` arm's reach check, the overlay — takes an `ExtKind`, never a `&str` it splits itself.
- **The wildcard matches one label.** A `records` qualifier `ext.<publisher>.*` covers exactly the kinds whose parsed publisher **equals** `<publisher>` — structurally, after parsing the kind, never by `starts_with` on the string. `ext.example.co.*` covers `ext.example.co.notes` and not `ext.example.co.uk.notes`, whose publisher is `example.co.uk`. The Fauna family's own charset and its "one trailing `.*`, `records` only" rule are unchanged ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Scope grammar → *Wildcards*); what changes is what the `.*` *means*.
- **The string freezes at first seal and is a key-schedule input** (`fauna_core::crypto::Branch::for_kind`: `entry_key = keyed_hash(seal_root, kind)`, `item_blind = keyed_hash(item_blind_root, kind)`), so a kind is never renamed and never reused; a publisher that needs new semantics mints a new name.

## The manifest — wire form and signature (ruled 2026-10-02; refutable until the first manifest is published)

[`third-party.md`](third-party.md) § The manifest says the `fauna` object is signed by `publisher.key`; this section is the bytes.

- **The `fauna` member is a JWS in compact serialization** (RFC 7515 § 7.1) — a string `BASE64URL(header).BASE64URL(payload).BASE64URL(signature)` — **whose payload is the UTF-8 JSON text of the extension object** (the object [`third-party.md`](third-party.md) § The manifest's example shows). The signature covers the payload bytes as transmitted, so there is **no canonicalization step**: a verifier checks the signature over the exact bytes it then parses, and a third-party implementation has no key-ordering, number-formatting or escaping rule to get subtly wrong. A `fauna` member that is a bare JSON object is an unsigned manifest and refuses at resolution; so does a JWS whose payload is not a JSON object or carries an unknown member (the unread-parameter rule, [`third-party.md`](third-party.md) § The manifest). A standard OAuth consumer sees one unknown string member and ignores it, as it ignored the object.
- **One key encoding: `did:key` over the Ed25519 multicodec** (`z6Mk…`). `publisher.key` inside the payload and the JWS header's `kid` both carry it and must be equal; a JWK, a bare base64 key, or any other DID method refuses. One spelling is the scope-string posture, the row's `publisher_key` column holds the raw 32 bytes, and `did:key` is the signing-key encoding the ATProto stack the issuer already speaks uses.
- **One algorithm: `EdDSA` (Ed25519).** The header is exactly `{"alg":"EdDSA","kid":"<did:key>","typ":"fauna-manifest+json"}`; any other `alg` (including `none`), a missing `typ`, or a `crit` member refuses — the posture `fauna_bridge_atproto::client_assertion` already takes for its one algorithm. Ed25519 rather than the issuer's ES256 because every Fauna signature a replica verifies is Ed25519 already (entry writer signatures, `GrantEvent`, `DeviceAuthorization`), and the manifest is verified by replicas on the plane, not only by the nest: an ES256 manifest would add P-256 verification to every app's shared Rust, web's wasm included, for one document.
- **Domain anchoring is same-origin.** `publisher.domain` must equal the `client_id` URL's host (lowercase, exact); every kind in `kinds` must parse (§ The grammar) with that publisher; a document served from any other host refuses at resolution. The key's authority is being served over HTTPS from that host.
- **What the signature adds over same-origin HTTPS — two things, both real.** (1) **Off-fetch verification**: the manifest rides the plane (§ The kinds vocabulary → *the plane row*), and every replica that meets it there verifies `(payload, signature)` against the publisher key the consenting device pinned, without fetching anything — the nest relays it and cannot alter it. (2) **Key continuity**: a re-resolved document whose `kid` differs from the row's `publisher_key` is refused for that row until the user re-consents; the ceremony with the new document replaces the key on the row, exactly as a ceremony presenting a different holder key does ([`third-party.md`](third-party.md) § Implementation status today). A publisher's key rotation is therefore a visible re-consent, never a silent swap under existing grants.
- **The `service_auth` member rides the same JWS** (ruled 2026-10-02): its vocabulary, its caps and its resolution-time refusals are [`third-party.md`](third-party.md) § The manifest's; the bytes and signature rules above cover it unchanged, and `verify_manifest` is still the one door that parses it.

## The kinds vocabulary (ruled 2026-10-02; refutable until the first manifest is published)

Each entry of `kinds` is `{"kind": "<ext kind>", "class": "state", "merge": "latest-wins", "floor": "none"}` — four members, each a closed string, unknown members and unknown values refused:

- **`kind`** parses under § The grammar with the manifest's own publisher; duplicates refuse; at most **64** kinds per manifest (a bound against a manifest that floods the overlay; refutable).
- **`class`** names the taxonomy class the kind's rows belong to. **One admitted value, `state`** — class-2 account state, the only class the plane's doors carry ([`account-data-taxonomy.md`](account-data-taxonomy.md) § The classes). `record` is reserved for a class-1 content-addressed door no slice has designed and refuses today. (The member stays so that the admitted set can widen without a wire change; the compiled registry has no class column because every compiled kind is class-2 — the overlay checks the value and drops it.)
- **`merge`** names the kind's merge policy by its fixed spelling: `immutable`, `crdt-per-field`, `latest-wins`, `three-way`, `nest-cas` — the five arms of `fauna_protocol::merge_policy::MergePolicy`, spelled once here so a manifest can always be *parsed*. **Admitted in v1: `latest-wins` only.** It is the one policy an engine applies to a payload it cannot type — whole-record, ordered by the stamp the entry carries — so it is the one a kind unseen at compile time can be converged under, which is finding A6's whole claim. The other four refuse at resolution with the reason each has: `crdt-per-field` dispatches a per-kind typed join (`apply_class2`'s `CrdtPerField` arm matches on the kind) and is admitted only when a schema-free field-wise merge exists — a declared design slice, not v1; `three-way` needs a resolver no kind has wired; `nest-cas` needs a nest arbiter a third-party kind has none of (the nest stores opaque bytes); `immutable` is the class-1 policy. Consequences inherited from the policy: the kind **admits a stamped tombstone** (`MergePolicy::admits_tombstone`), and every entry **carries the LWW stamp** in its `merge_meta` (`requires_stamp`), refused at the writer door without it exactly as a first-party LWW kind.
- **`floor`** names what the kind adds to the plaintext floor ([`encryption-at-rest.md`](encryption-at-rest.md) § Plaintext floor — "default for new kinds: nothing"). **One admitted value, `none`.** Every class-2 entry already pays the plane's own floor — scope, blinded item key, writer id, writer seq, op, ciphertext size, and the cleartext generation id of a v2 form — and a manifest may not ask the nest to read anything inside the seal. The member exists so that a future ruling widening the set has a place to land; today any other value refuses.
- **Rung and epoch are not members, and are not choices.** Every manifest-admitted kind is `AudienceRung::Delegable` at `SealingEpoch::Gen0`: delegable because a third-party kind exists to be granted, and the manifest may never widen who opens it (TP7); generation 0 because the delegable branch never gains a generation axis (`fauna_core::crypto::DelegableSchedule` — only the fleet branch derives per generation). The cost is the one every delegable kind pays and is stated: a revoked principal that kept the kind's pair can go on *opening* rows of that kind sealed after its revocation, which TP4 accepts because the only remote holders are holders of scopes they created ([`encryption-at-rest.md`](encryption-at-rest.md) § Capability tiering → *Third-party holders*, revocation honest-box). What it can no longer do is *write* — § Principal write authority.
- **The registry overlay.** `fauna_protocol::merge_policy`'s lookups (`merge_policy`, `audience_rung`, `sealing_epoch`, `kind_keys`) answer for the compiled table first and then for an **admitted-kinds overlay** the engine holds per account: a set of `(ExtKind, MergePolicy)` the consenting device admitted, carried to the account's other devices by **the plane row** — a first-party kind `fauna.state.kind-manifest`, fleet-only, `LatestWins`, `GenerationTip`, logical key = the document's `client_id`, value = the compact JWS verbatim plus the admitting device's `admitted_at`. Fleet-only by the default-narrow rule: no grantee needs it (a principal has its own manifest), and that the user connected a given app is theirs alone. Each device re-verifies the JWS when it reads the row, so the overlay is never built from a nest-asserted policy; the nest's `declared_kinds` column is an index for its doors, never the engine's authority. A revoked principal's row stays (re-consent re-writes it; the user's rows under those kinds stay readable); a kind the overlay does not know is the compat answer the compiled registry already gives — `None`, "not on the plane here", relayed unopened.

## The `ext` sub-scope (ruled 2026-10-02; frozen at the first row under it)

**One scope per kind: `ext:<kind>`, the kind string verbatim after the family tag** (`ext:ext.example.com.notes`). A new family under the frozen family-first grammar ([`account-sync-plane.md`](account-sync-plane.md) § Feeds and cursors → *The scope string*, which lists it in one line and defers here).

- **Per kind, not per publisher.** The A5 rule is that a grantee's subscription is narrow and churn it cannot open is invisible to it ([`account-data-taxonomy.md`](account-data-taxonomy.md) § The audience ladder → *Per-rung sub-scopes are the granting shape*). A single-kind grant (`fauna:records:rw:ext.example.com.notes`) must not observe the timing of sibling kinds' rows, so the scope is the kind's; a wildcard grant subscribes one scope per kind the manifest declares — the set is known at consent, bounded by the manifest's 64. The price is N feeds for N kinds, accepted.
- **Verbatim kind, no transform.** The content family puts the kind tag verbatim after its tag for the same reason: one rule, nothing to re-derive, and the publisher is recoverable from the scope string by § The grammar's parse. The parser (`fauna_protocol::scope::Scope`, a new `Ext(ExtKind)` arm) refuses a remainder that does not parse as an `ext.*` kind.
- **Home scope by derivation.** `home_scope_for_kind` answers `ext:<kind>` for any string that parses as an `ext.*` kind — from the string alone, with no registry row; the overlay is consulted only for the kind's policy, rung and epoch.
- **Admission forms.** It is an **own-account** scope on the delegable rung: `AdmittedScopes::AllOfAccount` and `AllOfAccountSinglePrincipal` admit it (`is_own_account_scope` learns the family), so the account's device replicas and its custodians hold it as they hold `state`; it is **never co-authored** — one account's data, however many writers sign into it, so `is_co_authored_scope` stays false; a principal's grant names it in the explicit `Named` form, per kind.
- **The nest serves it per door (ruling 4 of the scope string).** The nest serves `ext:<kind>` for an account when a live principal row of that account declares the kind, **or** the scope already exists on this nest — so revoking the principal never makes the user's own rows unreadable to the user's own replicas. A scope for a kind no row declares and no row ever created refuses `invalid_request` "unknown scope", the refusal `is_served_scope` gives today, which a replica treats as *not served yet*, never as empty.
- **The "A5 owed first" sentences are settled.** The partition is built and the per-kind sub-scope an `ext.*` grant subscribes is this family; its build is S8a's, and the sentences in the owner docs now point here.

## Principal write authority (ruled 2026-10-02; refutable until the first `content.write` grant is minted)

A reader verifies every entry's in-seal Ed25519 writer signature under the entry's own `writer_id`; whether that writer was *authorized* is the authoring-chain layer above the walk (`fauna_core::account_entry_crypto` § *The in-seal writer signature*). A principal's attested holder key is X25519 and cannot sign, so a principal that only held keys could read and could seal, but could sign nothing — every row it sealed would fail `open_entry`. Four rulings:

- **The principal has a second attested key, its writer key: Ed25519, attested as the start parameter `fauna_writer_ed25519`** beside `fauna_holder_x25519` — same carriage (PAR, `/oauth/device_authorization`, `/oauth/bc-authorize`; unpadded base64url, exactly 32 bytes; malformed → `invalid_request`), same binding-not-proof posture (a client that attests a key it does not hold can write nothing, since the key's only power is exercised by signing), and the same refusals at `/oauth/token` with nothing recorded: a writer key another of the account's principals holds, and a key the nest knows as one of the account's own writers (every `writer_id` on the account's state feeds is cleartext to the nest) or an enrolled bridge's. The roster row gains `writer_ed25519` (nullable, unique per account where present), the roster read `PrincipalInfo` gains the same field, and a later ceremony presenting a *different* writer key replaces it and ends, in the same transaction, the account's capability grants to the holder whose `content.write` tuple names the old writer — never the grant the replacing approve deposited for the new one — the holder-key rule applied to the second key ([`third-party.md`](third-party.md) § Implementation status today); the owner's log records that end at the approve, for both keys alike ([`third-party.md`](third-party.md) § The principal model → *Key replacement*). A principal that attested a holder key and no writer key is read-only over its kinds and is told so on the card.
- **`content.write` is keyless.** The AEAD pair `{entry_key, item_blind}` is one symmetric unit — there is no "write half" of the branch to wrap — so the class carries no key payload (the shape `content.label-write`, `deposit` and `identity.op` already take). What it carries is the **authorization**: an owner-signed record that the holder's writer key may author this kind. **The key rides the tuple's factor, never a new field** (re-ruled 2026-10-02 at the S8a build, correcting the design pass's "`GrantBlob` and `GrantEvent` gain `writer`": `GrantEvent`'s field set is frozen for this major — its signature is verified over the re-encoded *deserialized* struct, so an older device that drops an unknown field fails the verify and its log merge erases the event, `fauna_core::grant_event::GrantEvent`'s doc): each `content.write` tuple's `factor` is `writer:<hex>` — the holder's attested writer key as the consenting device read it from the ceremony, canonical lowercase hex (`fauna_core::grant_event::writer_factor`) — the tuple's license confined to that one key, exactly as a `labeler:<hex>` factor confines a labeler's (`ScopeTuple::factor`), and the event-log twin folds it into `kind` as it folds every factor (`GrantEventScope::with_factor`). Neither frozen shape grows. Tuples are **per kind**: at consent a wildcard scope expands to the manifest's declared kinds, and the grant carries, for each, a `content.read` tuple with its wrapped pair and a `content.write` tuple with none — `ScopeTuple.kind` = the full `ext.*` string, so a prefix never has to be expanded at read time. The pair is derived from the owner's delegable branch, which the generic `derive_scope_payload` (custody-fed, schedule-free) does not hold, so an `ext.*` read tuple takes the dedicated mint `fauna_client_capabilities::mint_ext_kinds_grant` — the folder grant's shape — and the generic path answers it `ExtKindUsesDedicatedMint`; a `content.write` tuple is keyless on either path.
- **Who admits a principal-authored row, and where.** Three positions, each checking what it can: **(1) the nest's door** refuses a principal session's put whose `writer_id` is not the row's `writer_ed25519` (a principal writes only as itself) or whose scope is not one its grant covers (§ The record doors); it never reads the seal. **(2) The account's own replicas** admit a row in `ext:<kind>` from a writer that is not one of the account's devices (enrolled in, or removed from, the verified `fauna.state.device-set` view — a principal holds no fleet-only key, so it can forge neither) iff the owner's grant log holds a `Mint` or `Renew` event carrying a `content.write` tuple over that kind whose writer factor names the row's `writer_id` — **ever minted, revoked or not**: a row the user kept is the user's data (reference case 2 of [`third-party.md`](third-party.md): leaving is one revoke and the records stay), and rows carry no trusted time a window could be checked against. A row from an unknown writer is skipped and counted (`WalkReport::unmergeable`'s posture), never fatal. **(3) A principal reading its own scope** verifies the signature only — the existing layer — and the chain check above it is the same declared gap [`../behavior/devices.md`](../behavior/devices.md) § Device-signed authoring carries for device writers; nothing new is excused here.
- **Revocation.** Deleting the roster row ends write authority where it can be ended: the principal session is swept and no new one opens, so the nest's door closes at once; the grant log's `Revoke` event ends the authorization the owner's app renders. Rows already admitted stay. A row signed by the revoked writer and introduced *afterwards* can reach the account's replicas only through a nest that colludes with it (the nest holds the door), which is exactly the honest-box bound TP4 already accepts for revocation ([`encryption-at-rest.md`](encryption-at-rest.md) § Capability tiering → *Third-party holders*); no replica-side rule can do better without trusted time, and none pretends to.

**Where logic lives.** The seal is the shared one: a principal seals with `fauna_core::account_entry_crypto::seal_entry`, its writer key in the device key's place and its `writer_id` the key's public half, so a device app or hosted plugin links the same function and a remote server implements the same frozen form (the S8b conformance pin). The grant is built by `fauna_client_capabilities::mint_grant` with the new tuple class and field; the replica-side admission is the account plane's walk (`fauna_account_plane::account_state_plane`), the nest's checks are the principal handlers' (§ The record doors).

## The record doors (ruled 2026-10-02; the WS-RPC half is S8a's, the HTTP half S8b's)

- **The `records` arm exists in S8a, because an arm cannot exist without a ceiling kind.** `fauna:records:rw:<qualifier>` — qualifier required: one `ext.*` kind or `ext.<publisher>.*`, parsed by § The grammar; a wildcard's publisher must equal the document's host at PAR; a single foreign kind is legal with the louder card, and is grantable at consent only if the account already admitted that kind through its publisher's manifest (else the card refuses it as not yet known on this account). Grant twin: yes — the per-kind `content.read` + `content.write` pair above. Card row: what it reads and writes (the publisher, the kind count) and that keys to exactly those records are wrapped. The arm's own rules in the grammar's words are [`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Scope grammar → *The third arm*.
- **The kinds it reaches, for a principal session: `fauna.account.state.put` and `fauna.sync.changes.list`** — widened to `ThirdParty` under `PrincipalReach::Scope(Records)`, each served by a principal handler of its own ([`apps/bridges.md`](apps/bridges.md) § Capability-allowlist enforcement → *How the class meets the connection*, rule (d)). **Per-kind reach check, in the handler, before anything else:** the request's `scope` parses as `ext:<kind>`; one of the session's `records` scopes covers the kind (an exact kind, or a wildcard whose publisher equals the kind's — structurally, § The grammar); for the put, `writer_id` equals the row's `writer_ed25519`. `fauna.account.state.retire` stays `User | Admin` — compaction is the owner's. `fauna.sync.changes.list` on a principal session serves exactly the `ext:<kind>` scopes the grant covers and refuses every other scope string, so the principal never lists `state-fleet` or a content scope by any spelling, and lists `state` only read-only and under the fifth arm, `fauna:personalization:rw`, never under this one — the kind is scope-dispatched between the two arms ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Scope grammar → *The planes ruled 2026-10-02*; amended 2026-10-02, the day this section was ruled). The two kinds enter the ceiling behind a test that a principal's list of its own scope returns its rows and that any other scope — and any put as another writer — refuses.
- **S8a ships the WS-RPC door; S8b adds the HTTP door over the same checks.** `/api/v1/records/{kind}[/{key}]` is the same three checks on a bearer token with the body as the sealed entry, classified as residue because the far end cannot speak WS-RPC ([`api-layers.md`](api-layers.md) § HTTP residue). S8a's tier_3 journey therefore drives the principal session, not HTTP.
- **The HTTP door's wire (ruled 2026-10-05 at the S8b build): one admission, one dispatch, the plane's own coordinates.** Every request is admitted as the principal session's upgrade is — `Authorization: DPoP <token>` and its proof (`htm` the request's method, `htu` the door's `https` URL without its query), a built Fauna-family scope, the failed-credential throttle — the principal is resolved once (a revoked row, an account without authority or external apps OFF refuse), and the request is dispatched onto the two principal handlers above, so the ceiling, the `records` reach check and the writer check are the WS-RPC door's own and the storage path is the plane's one put. **`{key}` is the row's 32-byte blinded `item_key` in hex**, never a logical key (the nest holds none). `PUT /api/v1/records/{kind}/{key}?writer_seq=N` puts a `state-put` row whose body is the sealed entry and whose `writer_id` is the principal's attested writer key — never named by the request; `DELETE` is the same put with op `tombstone` and the principal's sealed tombstone entry as the body (a deletion is an ordinary sealed entry; `fauna.account.state.retire` stays the owner's); both answer `{"seq"}`, the nest-log seq. `GET /api/v1/records/{kind}?cursor=N` is the cursor walk — one page of the kind's feed past `cursor`, `{"records": [...], "cursor": N}`, the walk done at the first empty page; the cursor is the feed's serve-order watermark (sent as `held_through_seq`, answered from `complete_through_seq`, [`account-sync-plane.md`](account-sync-plane.md) § Feeds and cursors), and the door marks no walker, so a principal's walk holds back no retire — and `GET /api/v1/records/{kind}/{key}` is that walk filtered to one item (`404` when it holds none). A served record is the feed row's cleartext coordinates (`key`, `writer`, `writer_seq`, `op`, `seq`) and its `entry`, byte for byte, in unpadded base64url. The floor the door checks: the kind string (the handler's `ext:<kind>` parse — a `fauna.*` kind is reachable by no name), the size (the body is bounded at the plane's entry ceiling before it is buffered), and the gen-0 (v1) envelope shape an `ext.*` kind's row must have — checked in the principal put handler, so both doors refuse alike. Refusals render the handler's code under its HTTP status (`403` reach, `400` floor, `409` a stale `writer_seq`). Every admitted request counts against a per-principal limit, a hard-coded constant (`bridge_rate_limit::RECORDS_DOOR_LIMITER_CONFIG`; `429` with `Retry-After` when spent).
- **Who mints the consent-time grant: the approving app's shared machine, in one entry point, mint before resolve.** The card reads the ceremony's attested keys and the resolved manifest (`PendingConsentRow` gains `holder_x25519`, `writer_ed25519` and the manifest JWS, additive), so the row says what will be wrapped. On approve, one shared-Rust entry point (`fauna_client_capabilities::ext_consent::prepare_ext_consent_grant`, beside `mint_grant`; the apps' shared approving machine calls it, none re-implements a step) does, in order: (1) verify the manifest JWS against the document's host, decide the covered kinds (`plan_ext_consent`: a wildcard expands to the manifest's declared kinds of its publisher, an own-publisher single kind must be declared, a foreign single kind must already be in the account's overlay) and publish the `fauna.state.kind-manifest` row, from which the overlay admits them (`fauna_client_config::KindManifestStore`, implemented on the account-store handle); (2) derive each covered kind's delegable pair (`DelegableSchedule::for_kind`); (3) build the `GrantBlob` — the per-kind tuples, each `content.write` tuple carrying the writer factor (`mint_ext_kinds_grant`) — HPKE-wrapped to the attested holder key, sign its `Mint` event and record it in the grant log, releasing the blob only against the log the write stored (record-then-deposit, as every grant); the machine then deposits it with `fauna.capabilities.mint` and (4) resolves the consent (`fauna.bridges.atproto.resolve_consent`, today's call). A request naming no `records` scope mints nothing here and resolves as before. Mint precedes resolve because the row is minted nest-side at `/oauth/token`, after the consent, with no client in the loop; grants are keyed by holder key, so the principal fetches it over its session once the row exists. A ceremony that is approved and then never redeemed leaves a grant wrapped to a holder no row names; the nest sweeps such a grant when the request expires, the same deletion `fauna.principals.revoke` already performs for a deleted row, and the owner's reconcile view shows it gone. **The same entry point is the home of every twin an approved scope names (ruled 2026-10-05):** the keyless `deposit` tuple plans beside the records tuples into the one grant a consent mints — one `Mint` — while each keyed folder read twin leaves the same entry point as ITS OWN grant per (principal, folder) under a derived id, with its own `Mint` (amended 2026-10-05; the shape, the id and why: [`../behavior/webdav-server.md`](../behavior/webdav-server.md) § Key model → *A principal's read* rule (1)) — each arm's planner owned by its arm's doc; the folder twins' seam, the owner's folder custody on the consent machine, is [`../behavior/webdav-server.md`](../behavior/webdav-server.md) § Key model → *A principal's read*.

## Architectural rules

1. **The publisher is recoverable from the kind string alone, and every consumer recovers it the same way** (§ The grammar): no prefix test, no second parser, no per-consumer split.
2. **A manifest is verified over the bytes that are parsed.** No canonicalization, one algorithm, one key encoding.
3. **A manifest declares semantics and never audience, and only semantics an engine can apply to a payload it cannot type.** The admitted `merge` set widens only with a schema-free merge.
4. **Read capability never conveys write authority.** The pair is one unit; authority is the owner-signed `content.write` record naming a writer key, checked by every position that can check it.
5. **A principal reaches its own rows through doors gated by its scope, as itself.** No door serves a principal a scope its grant does not cover, and no put lands under a writer id that is not its own.

## Don't do these

- **Don't match a `records` wildcard by string prefix** — parse the kind, compare publishers.
- **Don't accept a bare `fauna` object, a JWK, a second `alg`, or a detached signature over canonicalized bytes.**
- **Don't admit `crdt-per-field`, `three-way`, `nest-cas` or `immutable` from a manifest** until the ruling that makes each convergeable blind exists here.
- **Don't put the rung or the epoch in the manifest, or in the overlay as data** — both are consequences of the kind being manifest-admitted.
- **Don't wrap a "write key".** There is none; `content.write` is keyless.
- **Don't let a principal list `state`, `state-fleet` or a content scope, under any spelling.**
