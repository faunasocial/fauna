## Goal

The hand-maintained matrix that seeded this design answered *what a new user gets, per app* with marks a person judged and notes a person wrote — and a judged mark goes stale silently, because nothing that happens later revises it. Half of that matrix was already generated and gated by the day this design was ratified (which tier_4-marked files drive which app), which is exactly how far a marker-derived floor can go: it can say a test *could* run for an app, never that it ran, never what it proved.

The catalog replaces judgement with records. Every cell must have four properties:

1. **Colour from outcomes.** A cell's mark is computed from what tests did, on which commit, against which artifact — never typed.
2. **A version on every cell.** The mark carries the product version and the nest mode of the run that produced it, so the catalog is legible as the label on a release.
3. **Discoverable both ways.** From a feature page you reach the tests that witness it; from a test you reach the feature it witnesses.
4. **Tests demonstrably ran on the commit that gets tagged.** A release tag cannot be minted without a recorded candidate run at that commit and that artifact digest.

Pre-1.0 the catalog is the **honest label** on a release, not a green-everywhere precondition: a tag needs the run to have *happened and been recorded*, not to have passed everywhere.

## The page

One file per feature, **`docs/features/<slug>.md`**; the slug is the identity (no numbers, kebab-case, stable for life — renaming a slug is a rename of every marker and ledger line that names it, done in one commit). `docs/features/` is the *published* catalog; the goal partition that used to be called `features/` is `docs/goal/behavior/` since 2026-08-26 precisely so the word is unambiguous.

**Front-matter** (YAML, fenced at the top of the page):

| Key | Meaning |
|---|---|
| `slug` | equals the filename stem; the lint refuses a mismatch |
| `title` | the row label in the matrix, user voice |
| `section` | which matrix section the row sits in (the seed's sections: getting in, everyday, your data and devices, mail/calendar/contacts, bridges and other networks, money, family and personalization, admin area — a section is a heading, not a concept, and pages may mint new ones) |
| `goal` | the owning goal doc and section for the feature (`behavior/onboarding.md § 3a`) — the one place the mechanism is described |
| `guide` | the user guide that explains it (`guides/app-tour.md § Feed`) |
| `absences` | a map `app: "<goal-doc citation>"` — the platforms on which the feature is absent **by design**, each with the goal-doc sentence that declares it; the matrix renders `—` there. A key of the form `<app> (outcome N)` or `<app> (outcomes N, M)` is a **per-outcome absence** instead: the column is excused by design from those `[app]` outcomes alone and still owes, and renders a real cell for, the rest (§ The coverage contract, *A column a goal doc excuses from some outcomes*) |

**Three sections, in this order:**

1. **`## What a user gets`** — user voice, present tense, no internal vocabulary, no element ids: what a person can do once this works. It ships verbatim to the site.
2. **`## Coverage contract`** — § The coverage contract. Hand-authored; stamped with the date and the commit it was written against.
3. **`## Status`** — a fenced block the render owns (§ Render). Never hand-edited; the lint refuses a page whose block is stale.

**The page never restates a goal-doc mechanism.** Its `goal` key and the contract's per-outcome citations are pointers; the contract *is* the goal section, as a list of observable consequences. This is the same relation the user guides have to the goal docs: the guide says what you get, the goal doc says how it is done, and neither copies the other.

## The coverage contract

The contract is the list of **user-observable outcomes** that, taken together, mean the feature works — and, for each, the tests that witness it. Grammar:

```markdown
## Coverage contract

Stamped 2026-08-26 at 8213688bbc.

1. [app] A signed-in person sees their own posts in the feed within one refresh — `docs/goal/ui/feed.md` § Reading
   - `tests/e2e-unified/tests/test_feed.py::test_own_post_appears`
2. [app] Composing with an image attaches it and shows the thumbnail — `docs/goal/ui/feed.md` § Compose
   - `tests/e2e-unified/tests/test_feed.py::test_compose_with_image`
3. [nest] A post the person deletes stops being served to followers — `docs/goal/behavior/delete-propagation.md` § Posts
   - (none)
```

Rules:

- **Numbered outcomes, each on exactly one surface** — `[app]` or `[nest]` (§ The two surfaces) — **each citing the goal-doc section it comes from.** An outcome that cites nothing is a claim about the product with no owner; the lint refuses it.
- **An outcome or witness line found anywhere outside `## Coverage contract` is refused, not silently dropped** — the parser reads outcomes only inside that block, so a stray `N. [app]`/`N. [nest]` or witness line left in another section (a page-added `## Workstream`, say) would otherwise vanish uncounted with every gate green; `parse_page` raises, naming the file and line.
- **Test ids are node ids without parametrization** — `tests/…/test_x.py::test_y`. The run matches them by prefix against collected items, so one contract line covers every app and nest-mode parametrization of that test.
- **`(none)` is a legal, honest mapping**: the outcome is part of the feature and no test witnesses it yet. A contract with any `(none)` outcome is **partial**; one with none is **full**. Fullness is a property of the contract, derived — never a mark someone types.
- **Maintainer-only witnesses (ruled 2026-09-09).** The catalog ships whole and the tests tree does not: the publish allowlist drop-paths the suites a public clone cannot run (live infrastructure, unshipped dev-fleet tooling, imports that raise outside the maintainers' tree), so a plain citation of one of them sends the public reader to a test they do not have — the same DANGLING class [`publish-gates.md`](publish-gates.md) § Publish-hygiene gate refuses for unshipped `scripts/` paths and pruned recipes. Such a witness is written `- (maintainer-only)`: the node id sits inside the provenance span the transform excises ([`../README.md`](../README.md) § Writing protocol), so the maintainers' tree keeps a citation the lint, the ledger and the render all read exactly as any other — it counts for fullness, records outcomes, stamps cells — and the shipped page carries only the mark. The render spells the same witness the same way in the page's `## Status` table (rule 5 keeps the two in step), and a shipped page reads `(maintainer-only)` with no id, which the parser accepts as a line naming no test. The mark is a checked claim, not an exemption list: rule 2 reds an unmarked witness whose file does not ship *and* a marked witness whose file does (a mark that outlived its reason hides real, public evidence), reading the allowlist through `features_lint.py`'s own `main()`; the curated tree is checked from the other side by the twelfth publish-hygiene check, `dangling_witness_check`. Measured the day it was ruled: seven citations across three pages, all to four drop-pathed files; the shipping test that motivated `(maintainer-only)` for each is exactly the one the allowlist records beside its `drop-path` line.
- **Written by hand, at the project's heaviest review weight, never generated.** Which outcomes constitute the feature, and which test really proves which outcome, is judgement — the one thing the marker-derived floor could not do. The stamp names the date and commit the author read.
- **An outcome names what the user gets, never where it happens (ruled 2026-08-30).** The column already says where: fullness is read per column (§ Cell semantics), each column judged against the citations that can speak for it — so **one platform-neutral outcome, citing each platform's own witness, gives every column exactly its own verdict**: full where its witness exists, honestly short where none can yet. A contract written as one outcome *per platform* ("On the web…", "On Windows…") defeats that arithmetic — each column can satisfy only its own line, every other line is `(none)` for it under any witness set that could ever be written, and the page is completable on no column by construction: ⚠ becomes a mark no run can revise, the judged-stale-mark failure (§ Goal, property 1) reintroduced through authoring. When one promise is fulfilled through per-platform channels or mechanisms, write the promise once, in words true on every platform that has it, anchored in the goal section that owns the cross-platform promise ([`installers/README.md`](installers/README.md) § The channel contract is the worked example), and cite each platform's witness under that one outcome; mechanism detail that differs per platform is goal-doc material, and a claim only one platform's app makes is another feature's outcome, cited on that feature's page. Two things the ruling leaves untouched: **⚠ never means "not applicable here"** — inapplicable-by-design is front-matter `absences` and nothing else, with the evidence rules unchanged (a page's own prose is never evidence for an absence; the per-outcome witness set and the declared, goal-doc-cited absence are) — and **an outcome's own words never scope it to platforms**, which would be an absence claim resting on prose: a column excused from one outcome by design says so in `absences`, under the same evidence rules (next rule). The boundary the ruling draws: *permanently partial under every witness set anyone could write* means the contract is mis-authored — re-author it; *partial until the product or its test arrives* (a store channel that does not exist; an unwritten test) is the honest state of the world, and the derived per-column `(none)` is exactly how it should read.
- **A column a goal doc excuses from some outcomes: a per-outcome absence (ruled by the user 2026-09-26, superseding both the 2026-08-30 refusal of per-outcome platform scoping and the 2026-09-19 split-only design).** Some contracts hold outcomes one column can never witness *by design* while that column owes the rest of the page: [`files-in-standard-apps`](../../features/files-in-standard-apps.md) outcome 4 on web, iOS and Android, which keep no synced local folder for the mount to meet (the page [`local-folder-sync`](../../features/local-folder-sync.md) is absent on all three) while they owe, and witness, the page's other outcomes. Left alone such a column is permanently partial, § Closing a gap's done-state is unreachable for it, and the pressure that creates is exactly the cheat that section forbids. **Re-authoring** (the per-column precedent under § Implementation status today) repairs a sentence whose *wording* presupposes one mechanism while the column delivers the same promise through another door; it does not apply when the column delivers nothing of the kind, and softening the outcome until it is true there stays refused. **The remedy is the per-outcome absence**: an `absences` entry keyed `<app> (outcome N)` or `<app> (outcomes N, M)` (§ The page) takes those outcomes off that column's contract and nothing else — they never block it, their witnesses leave its set (so a record it can never have does not hold its cell short), and they are not its backlog nor counted in their gap's reach — while the column keeps a real cell judged on everything it owes. It stands on exactly the evidence a page-level absence does: the goal-doc sentence declaring the *behaviour itself* absent on that platform, the user's explicit approval, and one `outcome-absence-added` record per (app, outcome) in the contract-move log (§ Closing a gap). What keeps it from becoming the cheap local escape the 2026-09-19 design feared is mechanical: every per-outcome absence still lives in the one front-matter map a reader audits, and the page's `## Status` table prints it beside the outcome it excuses; the parser refuses an entry naming a `[nest]` outcome (a nest record counts for every column, § The two surfaces), an outcome the contract lacks, a column already absent from the whole page, or **every** outcome of the page (a column excused from all of them has none of the feature, and that is the page-level entry, spelled once); the gate keys each entry by the outcome's *sentence*, so a renumbering that re-points it at another outcome is a new move on the record; and rule 6 of the lint reds an entry whose outcome has a witness that passed on that column. **A split is still the right shape when the excused outcomes are, together, a feature a user would name** — the two landed on the user's approval of 2026-09-26, [`formatting-as-you-type`](../../features/formatting-as-you-type.md) and [`pin-a-job-to-this-device`](../../features/pin-a-job-to-this-device.md), stand, each passing the three honesty tests that shape needs: (1) the split page is a feature a user would name, (2) *every* outcome on it is absent on the declared column, and (3) the column still owes, and can complete, everything left on the original page — but it is no longer the only honest shape, and one outcome is not a feature. The evidence rule reads the same for both forms: a goal doc saying a platform lacks a *mechanism* is not grounds for an absence (macOS lacks the collision chooser and still has that feature, by another door), while a goal doc declaring the *behaviour itself* absent on a platform is exactly the citation `absences` requires.
- **A stale stamp is the reader's warning, not a gate.** The lint checks the mapped tests exist and carry the marker; it does not judge the outcomes. Re-stamp when the feature's goal section changes materially.

## The two surfaces

Every outcome is witnessed on one of two surfaces, and a cell folds both:

- **`app`** — proven **per app, through that app's UI**: the test drives the app with the `app` fixture family (or a browser for web), so the witness is what a person of that platform would see. The outcome is recorded in that app's ledger and counts for **that column only**.
- **`nest`** — proven **once, app-independently, observed from outside**: an SMTP/IMAP/CalDAV peer, a real Mastodon, the WS-RPC wire, the image's own health endpoint — the shapes under `tests/platform/docker/`, `tests/api/` and `tests/live/`. The outcome is recorded in `nest.json` and counts for **every column**. A `tests/platform/docker/` test stands up its own nest image, so it is a witness of *that* artifact rather than of the run's: its record carries the booted image's own provenance (§ The ledger, *own-artifact records*) and the venue counts like the other two.

A cell is the conjunction: **app outcomes for that column ∧ nest outcomes**. Consequences:

- A **nest-only feature** (every outcome `[nest]`) renders as **one cell spanning all seven columns**, stamped with the nest image digest of the run. The seed's separate nest-side table dissolves into this — those rows become nest-only pages.
- The **install row** ("Get the app") is `app` surface, witnessed by the artifact and real-session suites (`tests/artifact/`, `tests/real_session/`): the thing under test is the shipped or installed artifact itself.
- **Pages are written from the fauna user's perspective even when the witness is a third party.** "People who email you while you are away get a reply" is the user's outcome; that an SMTP peer observed the reply is the witness, not the sentence.
- **The split is a free no-operator check.** A `[nest]` outcome that involves a *choice* — a threshold, a peer, an enablement — with no `[app]` outcome anywhere on the page is configuration-file theatre: a knob nobody can reach from the only configuration surface there is ([`../principles.md`](../principles.md) § One configuration surface). Automatic concerns — DKIM, TLS, MTA-STS, ACME, which [`../behavior/admin.md`](../behavior/admin.md) § 6. Mail keeps off the manual form by design — legitimately have none, because there is no choice. The lint flags the shape; a page that is legitimately nest-only says so in its `What a user gets`, with the literal phrase **`nothing to choose`** — one recognised wording, so the opt-out is a deliberate, greppable act rather than an accident of phrasing. **What the phrase claims (ruled 2026-10-01):** that everything the page promises happens with nothing chosen — not that no setting anywhere touches its subject. Certificates arrive by themselves and an admin may still pick the authority; the mail server runs with no tuning and an admin may still tune it. Such a choice is an `[app]` outcome on the admin page that owns it, and the nest-only page's prose says where the choosing happens instead of denying it ("nothing to choose to get this", then the pointer). The phrase does not rescue a page whose own outcomes cannot happen until someone chooses: that page is not nest-only, and owes the `[app]` outcome.

## Cell semantics

Per app column, computed by the render from the contract (§ The coverage contract) and the ledger (§ The ledger):

| Mark | Meaning (computed) |
|---|---|
| ✅ | contract **full** AND every mapped test's newest ledger outcome for this column is `passed` (or `xpassed`) — on **every platform** that recorded it (§ The ledger, *Platform keying*) |
| ⚠ | contract **partial**, or the mapped outcomes are mixed — some pass, some `failed` / `skip_unbuilt` / `xfailed`, **including a mix ACROSS PLATFORMS**: one test passing on linux and failing on windows is exactly this row's "mixed", never a ✅ |
| ❌ | mapped tests exist and none of them passed for this column |
| *(empty)* | **no ledger entry** for this feature and column — a claim about our records, nothing more ([`testing.md`](testing.md) § What the tree may assert about testing, rule 4); the legend never says "untested" |
| — | a front-matter **absence** for this app; a `declared_absence` skip in the run confirms it, a *passing* test on a declared-absent app is a lint error (the declaration is stale). A **per-outcome** absence renders no `—`: the column's cell is computed as any other, over the outcomes it owes (§ The coverage contract) |

**The marks are ✅ ⚠ ❌, not traffic-light circles, on purpose.** The state itself is a word in the data (`matrix.json`: `full` / `partial` / `failing` / `none` / `absent`), and the site renders colour from that; the glyphs are only the committed markdown's rendering. Coloured-circle emoji are the internal review log's severity vocabulary, and the publish gate counts them in every shipped tree ([`publish-gates.md`](publish-gates.md) § Internal-identifier ratchet) — a public matrix using them would be indistinguishable from that vocabulary and would need the gate widened for every rendered cell. The seed used circles; it never shipped.

Four rules the marks rest on:

- **`skip_environment` outcomes are never recorded.** A missing credential or an unreachable port says nothing about the feature; the previous ledger line stands. The same holds for a live box that is not set up for the run — one that answers the admin probe `fauna.auth.not_registered` (the live preflight, `testing.md` § Default app and nest mode → *Live mode*).
- **A test with more than one platform's record folds to one outcome for cell purposes: passing only if EVERY platform passed** (§ The ledger, *Platform keying*). One test can now carry a linux outcome and a windows outcome side by side, so "the mapped tests' outcomes" is never read straight off `tests[node id]` — it is folded first, and a fold that disagreed with itself would let one platform's pass hide another's fail, exactly the miscount the keying change exists to stop. A cell's own stamp/date/dirty/base follow the same shape one level up: `cell.platforms` holds each platform's own complete-observation record, and the top-level fields are the oldest of them (the same "shows the oldest artifact" rule the app/nest halves already follow, below).
- **Only a run that collected the feature's whole tagged set for that app re-stamps the cell — and *that app's* set is the citations that can witness *that column*, never all seven apps' together.** A contract normally witnesses one outcome once per app (a linux test, a windows test, a tui test), and a test carrying `@pytest.mark.<app>` runs only on the apps it names — which is exactly what the run's own app axis deselects on. So a column's set is its **applicable** citations: the ones marked for it, plus every unmarked one (an unmarked test is parametrized over whatever the run selected, so it can speak for any column) — and a test restricted to a client set by **parametrization** rather than by a mark is narrowed to that set exactly as a mark would narrow it, because the run's app axis deselects on both. Reading the set as the union across all seven instead makes such a cell **permanently unstampable in every mode on every machine** — no box can collect windows' and linux' and macos' witnesses in one run — which is what it silently did until 2026-08-30 (§ Implementation status today). The same narrowing applies to fullness: an `[app]` outcome with no applicable witness is `(none)` *for that column*, so the column is **partial**, exactly as a literal `(none)` would make it — without which narrowing the set alone would manufacture a ✅ from a sibling platform's witness. `[nest]` outcomes are never narrowed, because a nest record counts for every column by definition. A `-k` subset, a deselection, or a run that collected the set but skipped part of it for environment updates the per-test ledger lines it touched and leaves the cell stamp alone. The cell's stamp is therefore always the stamp of a *complete* observation — **and it names ONE artifact.** When the observation's records all carry one stamp (every ordinary feature; a feature witnessed wholly under `tests/platform/docker/`, whose records carry the booted image's stamp — § The ledger, *own-artifact records*) that is the cell's. When they name two artifacts (a `tests/api/` witness against the run's nest beside an own-image witness against the booted image) the cell shows the **oldest** — the artifact whose commit is a strict ancestor of every other's, the same older-of-its-stamps rule the two halves follow below — and where git cannot order them (one commit under two modes, unrelated or unseen commits) the observation updates the per-test lines and leaves the cell stamp alone, exactly as a subset does.
- **A witness that can drive only some apps is MARKED for them, never gated by a `declared_absence` on the others (ruled 2026-09-26).** The two gates answer different questions: an `absences` entry or a `declared_absence` skip says the *platform lacks the behaviour*, while `@pytest.mark.<app>` says *this test can drive these apps* — a web-only read through `eval_js`, a native-only twin of a web journey. Gating such a test on the apps it cannot drive records a `skipped: absence` on a column the page does not declare absent, which is a permanent red no run can clear (`features-gaps --reds` lists the class); marking it narrows it out of those columns' sets under the applicable-citations rule above, so the column's outcome is witnessed by its own twin and nothing is owed of the test that cannot run there. Not a contract move: the page's witness set is unchanged.
- **The nest half is a conjunct on every column.** A feature whose `[nest]` outcomes have no ledger entry renders empty on every column, however green its `[app]` half — and vice versa. Each cell shows the *older* of its two stamps.

Because fullness is read per column, a column short of full is short of it for a **nameable outcome** — one no test that can speak for that column witnesses. That is a question about the contract alone, answerable by the parse with no run at all, and **`just features-parity`** is it: per page, the columns some run could ever complete and the outcome blocking each of the rest (`Page.completable` / `Page.blocking`, one definition shared with `full_for`). The sharpest verdict it gives is a page completable on **no column** — its blank cells are then a fact about the contract, not about our records, and no run on any machine in any mode will move them. Distinguishing those from ordinary blanks is what stops a coverage backlog being read off a page list by hand. That view is **page-major** — the columns one page is short on — which is what a reader of one page wants. Routing the backlog wants the **transpose**, because a trickle-down pass and the queue that receives its capture are both per app, never per feature ([`testing.md`](testing.md) § Default app and nest mode), so **`just features-parity --column <app>`** asks what one column is short of across every page and **`--by-column`** prints all seven as one table (`column_backlog`, the same `blocking` rule read from the column's side). Its split is the routing decision: an outcome a **sibling column already witnesses** is this column's parity debt, closable by a lift with the reference named, while an outcome **no column witnesses** is an unwritten test owned by the feature's area, which no app queue can close by lifting anything. A declared-absent column has no backlog at all — `—` is neither completable nor short, so counting it would read a designed absence as coverage debt. A column's debt is the right unit for **doing** the work and the wrong one for **moving** it, so `--by-column` prints a second unit beside it: an outcome witnessed on a single app is short on six columns, and sending each column's list to its own app queue would mint that one piece of work six times — the per-feature × 6 shape [`testing.md`](testing.md) § Default app and nest mode refuses, arriving through a count rather than through a plan. **`Gap.reach`** — how many columns one missing witness blocks — separates them: reach 1–2 is a **straggler**, this column genuinely behind its siblings and ordinary trickle-down for its queue; reach 5+ is a **wide** gap belonging to one cross-app row, never one row per short column. Between them, reach 3–4 is **trickle-down in flight**: three or four columns already carry the witness, so the references exist and what remains is the ordinary batched per-app pass — it rides in the same per-app row as that column's stragglers, never a row of its own per feature, and a gap of any reach that **tui** owes goes to tui's queue first with new-feature urgency (the lead app lagging a feature its siblings shipped). **`just features-parity --column <app> --max-reach 4`** prints exactly that batch (`column_trickle_down`), so a per-app row derives its list and re-measures its premise with one command and never transcribes it. Reach ranks liftable debt only, so an outcome nobody witnesses is excluded rather than ranked as reaching all seven.

## Closing a gap

**A cell short of ✅ is closed by product work and a recorded run — never by an edit to the catalog (user directive 2026-09-19).** The catalog is the instrument that measures the distance between the product and its goal docs; an edit that moves a cell without moving the product makes the instrument lie, and every later session plans from the lie. The sanctioned moves are exactly four: **build** the feature on the app that lacks it, **write** the witness an outcome lacks, **fix** what a red witness found (in the product, or in the test when the test is what is wrong — a timing-brittle test is defunct, [`e2e-conventions.md`](e2e-conventions.md) convention 14), and **run** the column's whole set so the ledger records it.

**Never a gap-closing move:** deleting, merging or softening an outcome; deleting a page; adding an `absences` entry; re-pointing an outcome at a weaker test; skipping, `xfail`ing or deselecting a witness so a red stops being recorded; hand-editing a ledger file, a `## Status` block, `MATRIX.md` or `matrix.json`. The test for any contract edit is **would this edit be made if no cell moved?** — the edits this doc does sanction pass it on their own grounds: an outcome *added* because the goal section promises more than the contract lists (cells move down, honestly); a re-authoring under the mis-authoring boundary (§ The coverage contract — *permanently partial under every witness set anyone could write*, and only that); a re-stamp after the goal section changed. **A new `absences` entry is a new per-app deviation and needs the user's explicit approval, like any other**, on top of the goal-doc sentence the front-matter must cite; a column that is short because its product or test has not arrived stays honestly short.

**The gaps come in three layers, and only the first two are visible in the matrix.** (1) **A cell short of ✅** — by cause, computable per cell from the contract and the ledger: *short* (an outcome no test that can speak for the column witnesses — `just features-parity`; a missing witness very often hides a missing implementation on that app, so the first act is to check the app, not to write the test), *unrun* (a mapped test with no record for the column) and *red* (a mapped test whose newest record did not pass — a skip included, since a skip is recorded as not passed; its recorded class, `unbuilt` or `absence`, subdivides the cause rather than adding a fourth; and where no record exists at all the cell is *unrun*, which cannot tell a test that would skip as unbuilt from one that would pass). (2) **An outcome the goal section promises and the contract does not list** — found only by reading the page against its `goal` section. (3) **A user-facing feature the goal docs ratify that exists on no app** — it has no page by § Implementation status today's first ruling, so the matrix cannot show it at all; it is tracked as a work item in the owning area's queue, and its page is minted with the first implementation. Done means all three are empty: every goal-doc-ratified user-facing feature has a page, every page's contract lists what its goal section promises, and every cell without a declared absence is ✅.

**The contract surface only shrinks on the record (ratified 2026-09-19).** The never-moves above are prose, and prose does not stop a session that reads a red cell as its task, so a cheap merge gate compares the catalog's **contract surface** — the pages, each page's outcomes (surface and sentence), its `absences`, and each outcome's witness set — between the merge's base and its tip. **Monotone moves pass silently**: a page added, an outcome added, a witness added, a `(none)` replaced by a witness, an absence removed, a citation or a stamp changed. **Shrinking moves red the merge**: a page removed, an outcome removed or reworded (any change to its surface or sentence — a typo fix included, because the gate cannot tell a softening from a correction and must not try), an absence added (on a new page too; page-level, or per-outcome — the latter matched by the outcome's sentence, so an entry re-pointed at another outcome by a renumbering is an addition too; narrowing a page-level absence to some outcomes is monotone), a witness removed (a re-pointed witness is a removal plus an addition; so is a renamed test). A slug rename (§ The page) that git follows as a rename is compared as one page and passes when nothing else shrank. A shrinking move lands only when **the same merge appends one record per move** to the catalog's contract-move log — an append-only file beside the ledger, which like the ledger does not ship — naming the date, the slug, the move, its subject (the outcome sentence, the app, `<app>: <outcome sentence>` for a per-outcome absence, the test id, or the new slug), the **goal-doc citation that justifies the edit on its own grounds** (it must resolve, like any contract citation) and one sentence of why; an added absence additionally names **where the user's approval is recorded**. The gate checks that the record exists, matches the move and cites something real. **It cannot check that the justification is true or that the user was asked, and does not pretend to**: its job is to turn a silent edit into a loud, deliberate, permanently listed act — the red names this section, and the log is the audit list the standing gap driver reads on every pass, record by record, against the test above. **A record may be filed late (2026-10-02):** one carrying a `landed_in` commit (it must be in the checkout's history) files the move that commit made after the fact; it never covers a move of the merge that appends it, so no session excuses its own edit that way, and the merge gate does not demand it match one. **The asynchronous check's range run replays the range one catalog-touching commit at a time** rather than net-diffing it: its base is the last all-green tip and stands still while any gate is red, and over thousands of commits a net diff classifies a move by the range's end state, so records the merges landed honestly stop matching and the gate can never clear. Each commit's moves need a record anywhere in the range; a record matching no single commit's move is not an error there, because a merge lands several commits. Two channels stay outside it, by ruling rather than oversight: **muting a witness** (`skip`, `xfail`, deselect) cannot raise a cell, because a skipped or xfailed outcome is recorded as not passed and an unrecorded one leaves the previous record standing (§ Cell semantics) — so it is left to the skip ratchet ([`e2e-conventions.md`](e2e-conventions.md) convention 7) and earns no second mechanism here; and **weakening a witness's body or hand-editing a ledger file** changes no contract surface and is caught only by reading the commit behind a cell that moved, which is the same driver's first act on every pass.

## The marker

- **`@pytest.mark.feature("<slug>", …)`** — registered in `tests/e2e-unified/pytest.ini`; a test may name several slugs. It is the test → feature direction of discoverability; the contract is the feature → test direction, and the lint (§ The catalog lint) keeps the two consistent.
- **Validated at collection**: an unknown slug (no `docs/features/<slug>.md`) is a collection error, exactly like the strict `tier_N` marker check — a typo cannot silently create a feature nobody has a page for. ⚠ **The validation is on EVERY pytest run under `tests/e2e-unified/`, so its cost is everybody's cost**: it needs the slug *vocabulary* — the page filenames — and nothing more. It read that vocabulary through the per-column witness split until 2026-09-05, which `ast.parse`d and `ast.walk`ed all ~757 test modules and then discarded the result with `set(...)`: **1.9 s added to the collection of every suite in the tree** (measured on Windows, an unrelated 111-test suite 4.9 s → 3.0 s; `payments-excision-spine-check` 3.4 s → 1.4 s). `helpers/feature_ledger.py::known_slugs` reads the pages directly and `contract_surfaces` — the expensive one — is called only where the split is actually used; `test_known_slugs_is_the_pages_and_costs_no_tree_scan` pins both the agreement and the absence of the scan, because equality alone would stay green if the cheap path became the expensive one again.
- **`--feature <slug>`** (repeatable) selects the tests carrying the marker; combined with `--app` and `--nest` it is the way to re-witness one feature on one app in one mode.
- **App attribution** is decided by the run, not the marker: a test that launched an app driver is attributed to that app, by `helpers/app_surface.py::app_name` — for **every** driver it launched (a multi-seat test that drives three desktop apps witnesses all three); a test that launched **no** app driver is a `nest` witness. A marker never says which app; the `app`/`nest` surface is fixed by the contract line, and a mismatch (a `[nest]` outcome whose test drove an app, or a `[app]` outcome whose test drove none) is a lint error.

## The ledger

**Written by the run, committed by the session** — the same discipline as the per-app `ui-actual-<app>.yaml` snapshots: every e2e run on every machine updates the ledger for the apps it drove; the session reviews the diff and commits it with its work (the one unattended committer is the merge-gate check pass — *Check-pass observations*, this section's last paragraph). Layout:

```
docs/features/ledger/
  web.json  linux.json  windows.json  macos.json  ios.json  android.json  tui.json
  nest.json
  releases.json          # § Tag gate and release table
```

**One file per app so that three machines' runs never conflict** — a run on one machine touches only the files of the apps that machine drove, plus `nest.json` when it ran nest witnesses.

**The ledger is the render's INPUT and does not ship** (the publish allowlist drop-paths `docs/features/ledger`, 2026-08-27, with the first real run). Two reasons, and the first is mechanical: every record stamps the run's **full** commit, so a shipped ledger trips `secret_scan`'s default-deny on bare hex runs — measured, six failures from one test file's records — and it grows a new commit on every e2e run on every machine, which makes allowlisting it unbounded by construction. The second is that nothing public needs it: `matrix.json` is the only thing the site imports and every page's `## Status` block is committed, so the published tree carries the whole rendered picture without the bookkeeping behind it. Same treatment and same reason as `tests/e2e-unified/baselines/apple-baseline.json`. **Where the ledger directory is absent, `load_ledger` refuses — a hard stop, never an empty ledger (2026-09-09):** the one checkout without it is a public clone, and an empty ledger there is not "nothing recorded" but a render that would blank every committed `## Status` block and a rule-5 lint reporting every page stale (measured: 100 of the 107 findings a public `just features-lint` used to print). One precise refusal naming this section instead; the parse-only views (`features-parity` and its column reports) read no ledger and still work anywhere.

**The writer is the existing `--baseline-json` hook family extended in place** (`conftest.py`: `pytest_runtest_logreport` / `pytest_sessionfinish`; the schema note in `tests/e2e-unified/baselines/README.md` says "don't fork it; extend it in place", and this is that extension): per item it already records outcome and duration; the ledger adds the feature keys, the skip class, the surface attribution and the stamp. It is **on by default** (`--no-feature-ledger` opts a run out) — a run that observed something and did not record it is the failure this doc exists to prevent.

**Record schema** (`schema: 2`), per (feature, test id, **platform**) inside an app file:

```json
{
  "schema": 2,
  "app": "tui",
  "features": {
    "feed-read": {
      "cell": {
        "stamp": "0.1.2-dev+8213688b standalone", "date": "2026-08-26", "complete": true, "dirty": false, "base": "7f0c41a2e9…",
        "platforms": {
          "linux": { "stamp": "0.1.2-dev+8213688b standalone", "date": "2026-08-26", "complete": true, "dirty": false, "base": "7f0c41a2e9…" }
        }
      },
      "tests": {
        "tests/e2e-unified/tests/test_feed.py::test_own_post_appears": {
          "linux": {
            "outcome": "passed",
            "skip_class": null,
            "stamp": "0.1.2-dev+8213688b standalone",
            "version": "0.1.2",
            "commit": "8213688bbc…",
            "base": "7f0c41a2e9…",
            "image_digest": null,
            "nest_mode": "standalone",
            "dirty": false,
            "date": "2026-08-26",
            "platform": "linux"
          }
        }
      }
    }
  }
}
```

- `outcome` — the pytest outcome (`passed`, `failed`, `error`, `skipped`, `xfailed`, `xpassed`); `skip_class` — `unbuilt` / `absence` for the two declared skip shapes of convention 7, `null` otherwise. An environment skip writes nothing (§ Cell semantics).
- `version`, `commit`, `image_digest`, `nest_mode` — **the record's provenance, and it is per record.** For an ordinary test it is the run's: `version` the product version at the run's commit, read from `Cargo.toml [workspace.package] version` ([`product-version.md`](product-version.md) § Source of truth); `commit` the full git commit; `image_digest` the `sha256:` digest of the nest image `docker` mode's **provider actually resolved and booted** — `--nest docker:<ref>`'s ref when one was given, else the provider's own default (`fauna-nest-test:local`), never the bare CLI argument alone (a plain `--nest docker` still runs against a real, possibly-pulled image) — `null` outside docker mode and for a genuinely locally-built image, which carries no registry digest at all; `nest_mode` `standalone` / `docker` / `live` ([`testing.md`](testing.md) § Default app and nest mode). For an **own-artifact test** — one that boots its own nest image, every `tests/platform/docker/` module — it is the booted container's: `nest_mode` is `docker` unconditionally (a fact about the test, not the run), `image_digest` that image's own registry digest (`null` for one built rather than pulled), and `version` / `commit` what its `/api/v1/health` reported (`bins/fauna-nest/src/build_identity.rs`) — *own-artifact records*, below. `platform` — the host OS the run ran on (`linux` / `macos` / `windows`), never a host name — and, since *Platform keying* below, also the key one level up.
- `dirty` — whether the run's working tree carried uncommitted changes outside `docs/features/ledger/` when it was collected (*Dirty trees*, below): `true` means `commit` is a lower bound on the code the run observed, not its name. Always `false` on an own-artifact record — the image is a built artifact, and the checkout that ran the test is not in it. A record written before the field existed carries no key and reads as clean; the render treats absence as `false`.
- `base` — the newest commit on `origin/main` in the record's commit's own history, `git merge-base <commit> origin/main` as the checkout knew that ref when the commit was read (*Rebased commits*, below): the one sha in the record that still resolves after the pre-merge rebase has replaced `commit`, and a lower bound on the code the record observed. `null` when git could not say (no `origin/main` ref, no git) — unknown, never guessed. On an own-artifact record it is the *image commit's* base, asked when the container answered health. A record written before the field existed carries no key and reads as unknown.
- `cell` — written only by a run that collected the feature's whole tagged set for this app (§ Cell semantics); `complete` is that fact, recorded, and `dirty` and `base` are those of the records whose stamp the cell carries. The top-level fields are the OLDEST across every platform present (*Platform keying*, below); `cell.platforms` holds each platform's own, undisturbed.
- `nest.json` has the same shape with `"app": "nest"`.

**Stamp grammar — one stamp per cell, release-grade legible at a glance:**

| Run | Stamp |
|---|---|
| a release-candidate run (§ Release-candidate run) | `<version> <nest-mode>` — `0.1.2 docker` |
| any other run | `<version>-dev+<short commit> <nest-mode>` — `0.1.2-dev+8213688b standalone` |
| any other run, from a **dirty** tree (*Dirty trees*, below) | `<version>-dev+<short commit>.dirty <nest-mode>` — `0.1.2-dev+8213688b.dirty docker` |
| an own-artifact record, in any run (below) | `<image version>-dev+<image commit> docker` — never the bare form, never dirty |

The `-dev+<sha>` form is semver build metadata: it never collides with a real version string, and the tag gate ignores it. `.dirty` is a *second* build-metadata identifier — dot-separated, because a second `+` would not be semver — so a dirty stamp is still one legal version string, and still never the bare form. **A `<version> <mode>` stamp without `-dev` therefore means, on its own, "this cell was witnessed against the byte-identical released artifact at the commit that carries that version"** — the legend says this once, at the top of the matrix.

**Own-artifact records (ruled 2026-08-29).** A test that stands up its *own* nest artifact — every `tests/e2e-unified/tests/platform/docker/` module, which boots the locally-tagged `fauna-nest-test:local` — is a witness of that artifact and never of the run's, so stamping it with the run's `commit`, `image_digest` and `nest_mode` would name three things it never touched (the image was built at some other commit, and may be weeks behind; the run's `--nest docker:<ref>` digest is not that container's; and it is a docker artifact whatever the run's mode says — measured the day the class landed, a fifteen-day-stale tag would have written eleven ❌ against working product code). Its record therefore carries the container's own provenance, captured at the one door every container fixture passes through (the package's `wait_for_health`, at the moment the image answers `/api/v1/health`) and attached to the fixture whose setup observed it, because those fixtures are module-scoped and a per-test slot would reach only each module's first test. Four rulings, binding until re-ruled: **(a) the stamp is always `<image version>-dev+<image commit> docker`, never bare** — the bare form is the release-candidate run's claim about the artifact *it* verified (§ Release-candidate run re-verifies the run's image, not a container some test booted), and class (7)'s axis half deselects the venue from docker-mode runs in any case; **(b) a record names exactly one artifact**, so the writer *declines* — tallied and printed in the terminal summary, apart from the mode-gate tally because such a test RAN, never silent — when the test observed no booted container's identity (a fixture that did not go through `wait_for_health`), more than one distinct image, or an image whose health reports no commit sha (`dev` / `unknown`: a hand-built image; a built-not-pulled image *with* a stamped sha records honestly, with `image_digest: null`); **(c) the cell stamp follows § Cell semantics' one-artifact rule** — a feature witnessed wholly under this venue takes the image's stamp, a feature mixing venues shows the oldest artifact; **(d) `releases.json` is untouched** — the release table records candidate *runs*, an own-artifact record is never one, and the tag gate reads only the table. Owner of the class and of its axis half — the docker/live deselection, which stands: these tests still bring a second container and ignore the run's nest — [`testing.md`](testing.md) § Default app and nest mode, exclusion class (7).

**Dirty trees (ruled 2026-09-02).** A record is licensed *because* it is first-party "on the commit it names" (below) — and `commit` names the code only when nothing uncommitted sits on top of it. The default inner loop (edit, run, commit while it builds) is exactly the tree where something does, and until this ruling nothing on the ordinary path asked: measured the day it was ruled, a docker-mode run from such a tree stamped nine cells with a claim commit at which the tests it recorded could not even have been collected in that mode. A cell naming an unreproducible commit is worse than a blank one — blank invites work, wrong invites trust. Four rulings, binding until re-ruled: **(a) a dirty tree never refuses a record** — "a run that observed something and did not record it is the failure this doc exists to prevent" holds, and there is no `--allow-dirty`-style flag because there is nothing to bypass. **(b) It MARKS instead, in the data and in the stamp** — `dirty: true` on every record and on the cell a complete observation stamps, and `.dirty` as a second build-metadata identifier (the stamp grammar above), so the matrix and the page show it at a glance and a machine reader never parses a string for it. The meaning is *the commit is a lower bound on the code the run saw*; the next run from a clean tree supersedes it like any newer observation. A dirty cell still counts as witnessed, honestly labelled — leaving the cell unstamped would blank the matrix for the most common way a real result is ever produced. **(c) There is ONE definition of dirt** — `git status --porcelain` outside `docs/features/ledger/`, tracked modifications and untracked files alike, measured once at collection beside the commit — and the release-candidate gate refuses by that same function (§ Release-candidate run), so the gate and the mark cannot disagree about what counts. The exemption is that directory alone: a run *writes* it, and counting its own output would make every second run dirty for a reason that says nothing about what was observed; the catalog's pages are dirt like any other file, because a page holds the contract the run judges completeness against. **(d) A tree git cannot read is dirty, not clean** — clean is the claim that needs proof. What the mark does not claim: it is measured at collection, so an edit made *during* a long run goes undetected (the same window the commit stamp has always had); and an own-artifact record is never dirty, its provenance being the image's. A record written before the field existed carries no key and reads as clean, because nothing can now say what those trees looked like; the nine cells the ruling was found by had already been re-stamped from a clean tree the same day.

**Rebased commits (ruled 2026-09-06).** `commit` is the run's own HEAD, read once at collection — and every landing path rebases onto `origin/main` before it fast-forward-pushes, so whenever main moves between a run's collection and its merge the record ships naming a commit that resolves **nowhere in main's history**: the orphan the rebase left behind. That is not a rare window but the ordinary one for any run long enough to matter — measured the day it was found, a 35-minute live run's record landed naming a commit already unreachable, and the day it was ruled **49 of the 212 distinct commits named across the seven ledger files were orphans**. It is the ledger's instance of the fleet-wide trap the tree's own rule already names — cite a SHA only once it resolves on `origin/main`, the test being `git merge-base --is-ancestor` — and the sibling of *Dirty trees* one level up: `dirty` says *HEAD plus edits nobody can name*, this says *a main commit plus commits that never landed under that name*. In both, what a reader wants is one sha that resolves and honesty about what it names. Four rulings, binding until re-ruled: **(a) `commit` keeps naming what ran, and is never rewritten** — not at merge, not at render. The obvious patch, the merge script writing the post-rebase sha into the record, would make it name a tree that never ran (it now contains other sessions' commits): an honest orphan traded for a dishonest resolvable, the exact trade *Dirty trees* refused. **(b) Every record ALSO carries `base`** — `git merge-base <commit> origin/main` as the checkout knew that ref when the commit was read (`helpers/feature_ledger.main_base`) — which resolves by construction (it is an ancestor of the checkout's `origin/main`, itself an ancestor of the real one, and main only ever fast-forwards) and means what `dirty` makes `commit` mean, one level up: **a lower bound on the code the run saw**. A checkout whose `origin/main` is stale records a base older than it need be, never a wrong one. Asked once per run at collection beside the commit, and once per booted container at the health door for an own-artifact record, whose image commit has its own place in main's history unrelated to the checkout's HEAD; never on the per-report path. **(c) Unknown is `null`, never a guess** — no `origin/main` ref (a repository with no remote), no git, no commit — and the session summary says so, as it says when HEAD is ahead of main at all: that condition is the orphan's precondition, and unlike the orphan itself it is knowable at the run. **(d) The render marks nothing and the stamp grammar is unchanged.** Whether a sha is reachable is a fact about the *renderer's* checkout — what it last fetched — not about the record, and rule 5 (§ The catalog lint) holds the committed render equal to a fresh one on every machine; a reachability mark computed at render would make the lint disagree across boxes, and computed at collection it cannot be known. So the stamp's `+<sha>` is *what ran*, resolvable on main or not, and `base` in the ledger is the reader's door to a tree that is. What this does not claim: a record written before the field carries no key and reads as unknown — nothing can now say where those commits sat, and the next run re-stamps; and `base` is as fresh as the checkout's `origin/main` was at collection, which a session that never fetched leaves older than the truth.

**Platform keying (ruled 2026-09-06).** A record was keyed by (app, feature, test id) alone, with `platform` an ordinary mutable field — so for any app that runs on more than one platform (tui on Linux, macOS and Windows dev machines; web on all three), a run on one platform silently OVERWROTE the record from another. The ledger could say "tui passed" or "tui failed", never "tui passes on linux and fails on windows", which is exactly the shape a platform-specific defect has — and it hid a real one: `test_sign_out_erases_the_account_scoped_state_directory` read `tui: passed (platform: linux)` and had never been run on tui/windows at all; when it finally was, it failed — a signed-out user's `mls_state.db` and account store survived the erase, because Windows refuses to delete an open file while POSIX `unlink` does not. A reader consulting the ledger — including a reviewer verifying a change's premises, which is exactly what happened — concluded tui was fine; the overwriting run then destroyed the linux record too. Four rulings, binding until re-ruled: **(a) `tests[node id]` is `{platform: record}`**, one merge-able slot per platform instead of one slot total — a run's own records share one platform (a run has one host), so the writer never has to choose between two platforms' outcomes, only add its own alongside whatever else is there. **(b) `cell` gains the same split**: a `platforms` sub-map holds each platform's own complete-observation stamp (the same fields the top level always carried), so a linux run and a windows run can each independently complete the feature's whole tagged set without erasing the other's stamp. The top-level `cell` fields stay the OLDEST across every platform present — the same "shows the oldest artifact" rule the app/nest halves of § Cell semantics already follow — so an old reader that only ever looked at the top level keeps seeing a legal, conservative answer. **(c) The render FOLDS, never picks one platform and drops the rest**: a mapped test's outcome, for cell purposes, is `passed` only if every platform that recorded it passed — one failing platform is a *mixed* outcome exactly like a `failed` sibling test, never masked by a passing one (§ Cell semantics, rule 2). The matrix keeps its seven app columns unwidened; a page's own `## Status` block is where the disagreement the folded cell papers over becomes visible, one line per (app, platform) rather than one per app. **(d) `schema` bumped to 2** — the shape changed under every existing key, and a reader should be able to tell the two apart on sight; the 2,599 existing records across all seven ledger files were re-keyed in place by their own already-stored `platform` field (never dropped, never re-derived by re-running), and every historical `cell` was attributed to the platform whose still-present record shares its exact stamp. What this does not change: `nest_mode` stays a plain field, not a second key — it already travels on the stamp (`<version> <mode>`) and § Cell semantics' one-artifact rule already folds `standalone`/`docker` within one run the same way platforms now fold across runs; keying by it too would collide with that rule rather than extend it.

**Why a run-written record is allowed to say what happened.** [`testing.md`](testing.md) § What the tree may assert about testing bans a document from stating what testing *has happened*, because such a claim is uncorrectable — it decays in place. The ledger is the one exception, and it is the exception *because* it does not decay: it is **first-party** (written by the run that observed the outcome, on the commit it names, against the artifact it names) and **revisable** (the next run overwrites it; a rebuilt tree re-witnesses). It is a record of what *our* runs observed, which is rule 4's "claim about our records" — the same class as `pinned-previous-build.toml`. The amendment recording this stands in that section.

**Check-pass observations are published, not discarded (ruled 2026-09-20).** The merge-gate check's nightly pytest legs ([`merge-gate-check.md`](merge-gate-check.md) § Merge-gate check) run feature-tagged suites inside a pristine tree pinned at a fetched `origin/main` tip, so their records are the highest-provenance observations this ledger can get — never `dirty`, and `commit` equal to `base`, resolving on main for ever — and until this ruling every one of them was thrown away when the gate handed its tree back. Measured the day it was ruled: 23 distinct `tests/api/` and `tests/platform/sync/` witnesses those legs run had **no committed record at all**, holding 74 cells at *unrun* (the nest half is a conjunct on every column — § Cell semantics), six of them short of nothing else; and the newest committed record of any gated-suite test in `nest.json` was nine days old while the legs re-observed it every night. "A run that observed something and did not record it is the failure this doc exists to prevent" carries no exemption for a run nobody watches, and *run* is one of § Closing a gap's four sanctioned moves — the check makes that move nightly, on the one tree nobody can dispute. **The check pass is therefore this ledger's second committer, and the only unattended one.** What a session's review of its ledger diff protects against — a dirty tree, an orphaned commit, an environment the run should not have trusted — the pinned tree excludes by construction, and ruling (c) excludes by verdict. Six rulings, binding until re-ruled: **(a) the unit is the record, never the file** — the tree is restored between gates, so each gate starts from the tip's committed ledger and a file-level copy would keep only the last gate's writes: the pass harvests, at each gate's exit and before the restore, the test records and complete-observation cell stamps that gate changed, and accumulates them outside the tree; **(b) one publish per pass, at its end, with the render in the same commit** — the harvest is upserted onto the ledger files *as `origin/main` has them at publish time*, the render (§ Render) is re-derived from that result, and ledger and render land as one commit, so rule 5 (§ The catalog lint) never sees a check-pass commit stale; a lost push race re-derives both from the moved main, never replays a precomputed tree; **(c) a pass that reached no verdict publishes nothing, and a RED pass publishes** — INFRA-blocked, abandoned on the gate timeout, or discarded because the tree moved: those errors are facts about the box, the setup-`error` pollution § Implementation status today already counts, and they stay out. A red *verdict* is the opposite case: a failed witness's record is exactly what § Cell semantics derives ❌ from, the matrix then agrees with the red section the same pass publishes and clears with it, and what may never claim a cell is an *incomplete* observation — which `cell.complete` already encodes; **(d) main wins a contended key** — where `origin/main`'s record for a (feature, test id, platform) differs from the one the pinned tip carried, a session has recorded it since the tip and its record is the newer observation: the harvest drops its own record for that key, and with it that feature's harvested cell stamp (a cell names ONE complete observation) — and a cell stamp `origin/main` itself re-stamped since the tip, for the same (feature, platform), is contended the same way and keeps main's; **(e) a no-news pass is damped** — a harvest that would change no outcome, skip class or cell completeness and add no key publishes only when the newest committed record it would replace is more than seven days old, because every publish re-stamps the gated cells and so rewrites `MATRIX.md`, `matrix.json` and their pages' `## Status` blocks under every in-flight session whose own run touched the same pages — mechanical to resolve (re-render) but a fleet-wide nightly cost for a stamp nobody reads between releases; news always publishes the same pass; **(f) the writer's scope is `docs/features/ledger/<app>.json`, `nest.json` and the render's own outputs, nothing else** — no contract, no front-matter, and never `releases.json` (a check pass is never a candidate run; § Tag gate and release table). What this does not change: the record schema and the stamp grammar (an ordinary `-dev+<sha>` stamp), rule 5, and *committed by the session* for every other run on every machine. Where the harvest hooks in and how the commit is built without a working tree is [`merge-gate-check.md`](merge-gate-check.md) § Merge-gate check's.

## Render

**`just features-render`** reads every page's front-matter and contract plus the ledger, and writes three things — four, once a build is verified — idempotent, pure stdlib, sub-second, so it runs unconditionally and the lint (§ The catalog lint) checks the committed output is current (the `i18n-generate` / `i18n-check` split):

1. **`docs/features/MATRIX.md`** — the committed, cold-readable matrix: the legend (one paragraph, from this doc's § Cell semantics and the stamp grammar), one table per `section`, the release table (§ Tag gate and release table). Each cell: the mark, the stamp, a link to the page.
2. **Each page's `## Status` block** — the feature's own row, per app, with the stamps and the per-test outcomes, so a page is complete on its own.
3. **`docs/features/matrix.json`** — the same model as data, and the **only** thing the public site imports.
4. **`tests/e2e-unified/pinned-previous-build.toml`** — but *only* once the release table holds a verified row (§ Tag gate and release table → *The pin is derived from it*; a promoted row until 2026-10-02). Until then the render leaves the hand-written pin alone and rule 5 does not check it; the render takes the file over on the first verified build and never gives it back.

**No second HTML generator.** The features page in `sites/fauna-social/` imports `matrix.json` at build time — the bylaws pattern ([`build-system.md`](build-system.md) § Public website build owns the recipe and its declared sources; `docs/features/` is one of them) — so the site can never disagree with the committed matrix, and there is exactly one derivation from the ledger. Built 2026-08-27 as `/features`: its prose is single-sourced from `docs/sites/fauna-social/features.md` like every other page's, and the `.astro` file holds placement and styling only — it computes no mark and judges no cell, and a cell state it does not recognise still renders that state's own glyph rather than disappearing.

**It ships.** `docs/features/` is a shipped tree (the publish allowlist restricts `docs` to `docs/features/`), so the publish gates apply to every page and to the render's output: the leak-check (no internal vocabulary, no private hostnames or paths), the internal-identifier ratchet (provenance inside ``, which the transform excises — [`../README.md`](../README.md) § Writing protocol), and the dangling-pointer ban. Test node ids are `tests/…` paths, which the allowlist ships except for the suites it drop-paths by name, so a contract's citations are live links in the public tree — and the few that could not be are spelled `(maintainer-only)` (§ The coverage contract), never left dangling. **The render and the lint themselves are maintainer operations**: their input is the ledger, which does not ship (§ The ledger), so `load_ledger` refuses in a checkout without it rather than blanking every committed `## Status` block; the four catalog scripts still ship so the tooling is readable and its fixture-world tests run publicly (`just shipped-suite-test`).

## The catalog lint

**`just features-lint`** — cheap tier, both merge scripts ([`merge-gates.md`](merge-gates.md) § Local-merge gates), parse-only, path-scoped to `docs/features/**` and `tests/e2e-unified/**`:

3. every marker-tagged test appears in some page's contract (a marker with no contract line is a witness nobody asked for);
4. no `[nest]` outcome maps to a test that launches an app driver, and no `[app]` outcome to one that launches none (static — "launches an app driver" is the closure `scripts/features_scan.py` computes: the transitive closure over fixture definitions, the tree's `conftest.py` plus the module under scan, from the few door fixtures that obtain a driver themselves; OR a module-wide import of a driver factory — `drivers.create_driver`, the shared launch harness, the seat/skew helpers, the tui headless-store launcher — the same shape as the playwright rule (a launcher two test modules share is a helper in `helpers/`, registered as a factory; a driver borrowed from a *sibling test module's* private helper is a door the closure cannot see, which is how the tui re-key journey read as launching no app until 2026-09-26); OR a class autouse fixture requesting a door. 5. the committed `MATRIX.md`, every `## Status` block and `matrix.json` equal a fresh render, and so does the derived `pinned-previous-build.toml` once a build is verified (`features-render --check`);
6. no cell is ✅ on an app the page declares absent, and no witness of an outcome a column is declared absent from has passed on that column; no page has `[nest]` choice-outcomes with no `[app]` outcome unless its `What a user gets` says the feature has no user-facing choice.

## Release-candidate run

**`just e2e-release-candidate <image> [--app …]`** — the run whose stamps carry a bare version. It refuses to start unless:

- the working tree is **clean** — `git status --porcelain` empty outside `docs/features/ledger/`, the run's own output; § The ledger's *Dirty trees* is the one definition, and the gate reads the very function the ordinary run marks by — and
- **HEAD equals the image's `FAUNA_BUILD_COMMIT`** (`bins/fauna-nest/src/build_identity.rs`; the value is an `ENV` in the image's shipped stage, readable by `docker inspect` without booting it — set there since 2026-08-29: every image built before then carried it only compiled into the binary, so this precondition refused them all and no candidate run had ever been possible; pinned by `tests/e2e-unified/tests/test_feature_ledger.py`), and
- the image has a **registry digest** (`RepoDigests` non-empty — a locally built image has none; a candidate is always the immutable `:sha-<commit>` tag the pipeline pushed, [`build-system.md`](build-system.md) § Image tags & channels).

It then runs the suite in **`docker` mode against exactly that image** (`--nest docker:<image>` — tier_3 journeys elevate to tier_4 at collection, [`testing.md`](testing.md) § Default app and nest mode) with `--release-candidate`, which the ledger writer honours only after re-verifying the same three preconditions itself (defence in depth: the recipe is the convenient door, the plugin is the gate). Every ledger line and cell it writes is stamped **`<version> docker`** where `<version>` is `Cargo.toml [workspace.package] version` at HEAD — **there is no version argument**: the bump commit already allocated the number ([`product-version.md`](product-version.md) § Bumping), and a run cannot claim a version its commit does not carry. Alongside, it writes the row's `candidate_run` date into `releases.json` — minting the (version, commit, digest, date) row, or upserting into the one `release-verified` already minted for this build (§ Tag gate and release table).

**The two halves are deliberately not symmetric.** The nest under test is the **byte-identical shipped artifact** — the digest is what promotion copies. The app half is necessarily an **e2e-flavoured build of the same commit**: the automation surface is compiled out of release builds on every app ([`e2e-automation-surface-gating.md`](e2e-automation-surface-gating.md) convention 15), so no release binary can be driven. A bare-version stamp on an app cell therefore means "the app *source* at the released commit, driven through its UI, against the released nest artifact" — the strongest witness the convention allows, and the legend says so once. The artifact suites (`tests/artifact/`) are the exception that drives a release-shaped client, and the install row is what they witness.

## Tag gate and release table

**`just release-tag`** mints the `v<version>` tag — and there is no other sanctioned way to mint one. It refuses unless `releases.json` holds a **release-candidate run at exactly HEAD's commit AND exactly one image digest** — the same lesson [`build-system.md`](build-system.md) § Image tags & channels learned for promotion (*verify the artifact, not just the commit*: a commit can have several builds; the tested one is the only one the tag may name). A fix after a candidate run means a new commit, a new image, a new run — **the same version string is legal until it ships** ([`product-version.md`](product-version.md) § Version strings are never reused), so the sequence is: bump → build → candidate run → (fix → build → run)* → tag → promote (the promote being the public repository's `:latest` since 2026-10-02 — the next paragraph). Pre-1.0 the gate asks that the run **happened and was recorded**, not that it was green everywhere (§ Goal).

The tag is a **git tag**, created by the recipe on HEAD; no tag exists yet on either repository, so the recipe — not a workflow precondition — is where the gate lives. `release.yml` (in the public-files tree since 2026-08-31 — [`release-integrity.md`](release-integrity.md) § Release signing → *When a release workflow publishes*) fires on `v*` tags pushed to the **public** repository, so the public tag that cuts a binaries release is a separate deliberate act after `just release-tag` mints the internal one that names the release.

**Promotion copies the tested digest.** The nest image promoted to the public repository's `:latest` + `:<version>` — the only promote left after the 2026-10-02 channel ruling: the private repository stages and verifies and promotes nothing (owner of both pipelines: [`build-system.md`](build-system.md) § Image tags & channels) — must be the digest the candidate run recorded; the target state of that promote step is "green verify at test.example.com **and** a tag whose release-table row carries this digest". Until the public pipeline is built nothing promotes and `promoted` stays `false` on every row.

**The release table** (`releases.json`, rendered into `MATRIX.md`): one row per build the catalog has something to say about (re-keyed 2026-10-02 with the private `:latest`'s retirement; one row per candidate run before) — `version`, `commit` (the repository's git object id, sha1), `image` (the exact tag the run drove) and `image_digest`, `date` (the row's newest observation), **`verified`** (the date the private pipeline's verify gate went green on this build — written by **`release-verified <headSha>`** in the dispatching session; the field the pin derives from), **`candidate_run`** (the date of the newest release-candidate run — written by the run itself; the field the tag gate reads, so a verified-only row never satisfies it), `promoted` (boolean: this digest became the **public** repository's `:latest` — flipped by **`just release-promoted <commit>`** in the session that drives that promote, dormant until the public pipeline exists), and `shipped_apps`, the **per-app shipped version** where a store carve-out shipped one app at a later patch (§ Release train). It is the one record of what was released: the reader sees at a glance which builds reached the staging box, which were measured, which became production, and which app, if any, lags. A row is minted by whichever act comes first — `release-verified` or the candidate run — and the other upserts into it on the key below; the digest both record is the registry's manifest-list digest of `ghcr.io/faunasocial/nest:sha-<sha>` (`docker image inspect`'s `RepoDigests` for the pulled tag, `docker buildx imagetools inspect` for the un-pulled one), the same identity, so the key agrees. **`release-verified` resolves the digest off the registry and never reconstructs it**; `--digest` overrides for a registry the session cannot reach.

**A row is keyed on `(commit, image_digest)` and upserted, never blindly appended.** A candidate run is re-runnable by design — a flake, a wider `--app` set, a second machine's leg — and re-running the *same* artifact at the *same* commit is one release observed twice: the date and `candidate_run` advance, `verified` and `promoted` are preserved, no second row appears. Only a genuinely different build of the same commit is a second row, and that is exactly the case the tag gate refuses. Without the upsert the gate's "exactly one digest" would be satisfiable one moment and ambiguous the next for no reason but a repeat run.

**The row's own commit and digest are allowlisted for the publish gate in the same act that writes them.** Both are bare hex runs in a shipped tree (`matrix.json`, `MATRIX.md`, the derived pin), and `secret_scan` default-denies those, so a release would otherwise red the merge that lands it — the trap the pin file's header has warned about since 2026-07-12 and that took `origin/main` red on 2026-08-27 over four commit SHAs of the version-skew grid's own. `just release-promoted` therefore appends entries to the publish gate's approved-secret-fixtures allowlist alongside the render, with a reason naming the release row. The values are public by construction — a commit in this repository's history, and what `docker pull …@sha256:…` resolves — so the decision the allowlist records is a standing one about a *class*, not a fresh judgement per release; a release process whose every use reds the merge gate is one people route around.

**The pin is derived from it.** `tests/e2e-unified/pinned-previous-build.toml` — "the most recent verified staged build pair", [`version-compatibility.md`](version-compatibility.md) § Dimension 6 (re-ruled 2026-10-02; "production release pair" until the private `:latest` was retired) — is written by `just features-render` from the newest row carrying a `verified` date (newest by that date, ties by position), and the lint checks it (rule 5). Its semantics are unchanged and still owned there; what changed in 2026-08-27 is that it is no longer a second hand-maintained copy of a fact the release table already holds, and `release-verified` is the act that advances it (`release-promoted` did, until the private promote was retired; it now records the public `:latest` only). **Newest by `verified`, never by date alone**: a candidate that went red at the verify gate never proved it serves anywhere, and pinning it would aim the whole skew grid at an artifact nobody runs — which is the distinction § Dimension 6's update rule is built on.
