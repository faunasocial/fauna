## Goal

The hand-maintained matrix that seeded this design answered *what a new user gets, per app* with marks a person judged and notes a person wrote — and a judged mark goes stale silently, because nothing that happens later revises it. Half of that matrix was already generated and gated by the day this design was ratified (which tier_4-marked files drive which app), which is exactly how far a marker-derived floor can go: it can say a test *could* run for an app, never that it ran, never what it proved.

The catalog replaces judgement with records. Every cell must have four properties:

1. **Colour from outcomes.** A cell's mark is computed from what tests did, on which commit, against which artifact — never typed.
2. **A version on every cell.** The mark carries the product version and the nest mode of the run that produced it, so the catalog is legible as the label on a release.
3. **Discoverable both ways.** From a feature page you reach the tests that witness it; from a test you reach the feature it witnesses.
4. **Tests demonstrably ran on the commit that gets tagged.** A release tag cannot be minted without a recorded candidate run at that commit and that artifact digest.

Pre-1.0 the catalog is the **honest label** on a release, not a green-everywhere precondition: a tag needs the run to have *happened and been recorded*, not to have passed everywhere.

## The page

One file per feature, **`docs/features/<slug>.md`**; the slug is the identity (no numbers, kebab-case, stable for life — renaming a slug is a rename of every marker and ledger line that names it, done in one commit). `docs/features/` is the *published* catalog; the goal partition that used to be called `features/` is `docs/goal/behavior/` since 2026-08-26 precisely so the word is unambiguous.

**Front-matter** (YAML, fenced at the top of the page):

| Key | Meaning |
|---|---|
| `slug` | equals the filename stem; the lint refuses a mismatch |
| `title` | the row label in the matrix, user voice |
| `section` | which matrix section the row sits in (the seed's sections: getting in, everyday, your data and devices, mail/calendar/contacts, bridges and other networks, money, family and personalization, admin area — a section is a heading, not a concept, and pages may mint new ones) |
| `goal` | the owning goal doc and section for the feature (`behavior/onboarding.md § 3a`) — the one place the mechanism is described |
| `guide` | the user guide that explains it (`guides/app-tour.md § Feed`) |
| `kids-owed` | optional, a comma-separated list of kids columns (`android-kids, ios-kids`) the page is OWED on although the parent column is absent from it — the one exception to the parent's absence carrying to its kids column, for the `kids-app` page, whose outcomes are false on every main build by design and true on the kids build; the parser refuses a non-kids value and a column `absences` also excuses |
| `ui-pages` | optional, a comma-separated list of the `tests/e2e-unified/ui.yaml` `pages:` keys the feature's contract tests drive (`feed, compose`); the lint refuses a key that names no page there. It is what lets the pre-landing touched-set selector name this page when a ui.yaml edit lands inside one of those pages ([`delayed-testing.md`](delayed-testing.md) § What a session runs before landing, class 3) — it selects tests and carries no coverage claim, so no cell reads it |
| `absences` | a map `app: "<goal-doc citation>"` — the platforms on which the feature is absent **by design**, each with the goal-doc sentence that declares it; the matrix renders `—` there. A key of the form `<app> (outcome N)` or `<app> (outcomes N, M)` is a **per-outcome absence** instead: the column is excused by design from those `[app]` outcomes alone and still owes, and renders a real cell for, the rest (§ The coverage contract, *A column a goal doc excuses from some outcomes*) |

**Three sections, in this order:**

1. **`## What a user gets`** — user voice, present tense, no internal vocabulary, no element ids: what a person can do once this works. It ships verbatim to the site.
2. **`## Coverage contract`** — § The coverage contract. Hand-authored; stamped with the date and the commit it was written against.
3. **`## Status`** — a fenced block the render owns (§ Render). Never hand-edited; the lint refuses a page whose block is stale.

**The page never restates a goal-doc mechanism.** Its `goal` key and the contract's per-outcome citations are pointers; the contract *is* the goal section, as a list of observable consequences. This is the same relation the user guides have to the goal docs: the guide says what you get, the goal doc says how it is done, and neither copies the other.

## The coverage contract

The contract is the list of **user-observable outcomes** that, taken together, mean the feature works — and, for each, the tests that witness it. Grammar:

```markdown
## Coverage contract

Stamped 2026-08-26 at 8213688bbc.

1. [app] A signed-in person sees their own posts in the feed within one refresh — `docs/goal/ui/feed.md` § Reading
   - `tests/e2e-unified/tests/test_feed.py::test_own_post_appears`
2. [app] Composing with an image attaches it and shows the thumbnail — `docs/goal/ui/feed.md` § Compose
   - `tests/e2e-unified/tests/test_feed.py::test_compose_with_image`
3. [nest] A post the person deletes stops being served to followers — `docs/goal/behavior/delete-propagation.md` § Posts
   - (none)
```

Rules:

- **Numbered outcomes, each on exactly one surface** — `[app]` or `[nest]` (§ The two surfaces) — **each citing the goal-doc section it comes from.** An outcome that cites nothing is a claim about the product with no owner; the lint refuses it.
- **An outcome or witness line found anywhere outside `## Coverage contract` is refused, not silently dropped** — the parser reads outcomes only inside that block, so a stray `N. [app]`/`N. [nest]` or witness line left in another section (a page-added `## Workstream`, say) would otherwise vanish uncounted with every gate green; `parse_page` raises, naming the file and line.
- **Test ids are node ids without parametrization** — `tests/…/test_x.py::test_y`. The run matches them by prefix against collected items, so one contract line covers every app and nest-mode parametrization of that test.
- **`(none)` is a legal, honest mapping**: the outcome is part of the feature and no test witnesses it yet. A contract with any `(none)` outcome is **partial**; one with none is **full**. Fullness is a property of the contract, derived — never a mark someone types.
- **Maintainer-only witnesses (ruled 2026-09-09).** The catalog ships whole and the tests tree does not: the publish allowlist drop-paths the suites a public clone cannot run (live infrastructure, unshipped dev-fleet tooling, imports that raise outside the maintainers' tree), so a plain citation of one of them sends the public reader to a test they do not have — the same DANGLING class [`publish-gates.md`](publish-gates.md) § Publish-hygiene gate refuses for unshipped `scripts/` paths and pruned recipes. Such a witness is written `- (maintainer-only)`: the node id sits inside the provenance span the transform excises ([`../README.md`](../README.md) § Writing protocol), so the maintainers' tree keeps a citation the lint, the ledger and the render all read exactly as any other — it counts for fullness, records outcomes, stamps cells — and the shipped page carries only the mark. The render spells the same witness the same way in the page's `## Status` table (rule 5 keeps the two in step), and a shipped page reads `(maintainer-only)` with no id, which the parser accepts as a line naming no test. The mark is a checked claim, not an exemption list: rule 2 reds an unmarked witness whose file does not ship *and* a marked witness whose file does (a mark that outlived its reason hides real, public evidence), reading the allowlist through `features_lint.py`'s own `main()`; the curated tree is checked from the other side by the twelfth publish-hygiene check, `dangling_witness_check`. Measured the day it was ruled: seven citations across three pages, all to four drop-pathed files; the shipping test that motivated `(maintainer-only)` for each is exactly the one the allowlist records beside its `drop-path` line.
- **Written by hand, at the project's heaviest review weight, never generated.** Which outcomes constitute the feature, and which test really proves which outcome, is judgement — the one thing the marker-derived floor could not do. The stamp names the date and commit the author read.
- **An outcome names what the user gets, never where it happens (ruled 2026-08-30).** The column already says where: fullness is read per column (§ Cell semantics), each column judged against the citations that can speak for it — so **one platform-neutral outcome, citing each platform's own witness, gives every column exactly its own verdict**: full where its witness exists, honestly short where none can yet. A contract written as one outcome *per platform* ("On the web…", "On Windows…") defeats that arithmetic — each column can satisfy only its own line, every other line is `(none)` for it under any witness set that could ever be written, and the page is completable on no column by construction: ⚠ becomes a mark no run can revise, the judged-stale-mark failure (§ Goal, property 1) reintroduced through authoring. When one promise is fulfilled through per-platform channels or mechanisms, write the promise once, in words true on every platform that has it, anchored in the goal section that owns the cross-platform promise ([`installers/README.md`](installers/README.md) § The channel contract is the worked example), and cite each platform's witness under that one outcome; mechanism detail that differs per platform is goal-doc material, and a claim only one platform's app makes is another feature's outcome, cited on that feature's page. Two things the ruling leaves untouched: **⚠ never means "not applicable here"** — inapplicable-by-design is front-matter `absences` and nothing else, with the evidence rules unchanged (a page's own prose is never evidence for an absence; the per-outcome witness set and the declared, goal-doc-cited absence are) — and **an outcome's own words never scope it to platforms**, which would be an absence claim resting on prose: a column excused from one outcome by design says so in `absences`, under the same evidence rules (next rule). The boundary the ruling draws: *permanently partial under every witness set anyone could write* means the contract is mis-authored — re-author it; *partial until the product or its test arrives* (a store channel that does not exist; an unwritten test) is the honest state of the world, and the derived per-column `(none)` is exactly how it should read.
- **A column a goal doc excuses from some outcomes: a per-outcome absence (ruled by the user 2026-09-26, superseding both the 2026-08-30 refusal of per-outcome platform scoping and the 2026-09-19 split-only design).** Some contracts hold outcomes one column can never witness *by design* while that column owes the rest of the page: [`files-in-standard-apps`](../../features/files-in-standard-apps.md) outcome 4 on web, iOS and Android, which keep no synced local folder for the mount to meet (the page [`local-folder-sync`](../../features/local-folder-sync.md) is absent on all three) while they owe, and witness, the page's other outcomes. Left alone such a column is permanently partial, § Closing a gap's done-state is unreachable for it, and the pressure that creates is exactly the cheat that section forbids. **Re-authoring** (the per-column precedent under § Implementation status today) repairs a sentence whose *wording* presupposes one mechanism while the column delivers the same promise through another door; it does not apply when the column delivers nothing of the kind, and softening the outcome until it is true there stays refused. **The remedy is the per-outcome absence**: an `absences` entry keyed `<app> (outcome N)` or `<app> (outcomes N, M)` (§ The page) takes those outcomes off that column's contract and nothing else — they never block it, their witnesses leave its set (so a record it can never have does not hold its cell short), and they are not its backlog nor counted in their gap's reach — while the column keeps a real cell judged on everything it owes. It stands on exactly the evidence a page-level absence does: the goal-doc sentence declaring the *behaviour itself* absent on that platform, the user's approval — explicit, or ADVISORY where that sentence already stands: the entry lands as a declaration the user may veto for `ADVISORY_VETO_DAYS` ([`fleet-daily-asks.md`](fleet-daily-asks.md) § The daily asks → *The advisory approvals*; owner-ruled 2026-11-10) — and one `outcome-absence-added` record per (app, outcome) in the contract-move log (§ Closing a gap). What keeps it from becoming the cheap local escape the 2026-09-19 design feared is mechanical: every per-outcome absence still lives in the one front-matter map a reader audits, and the page's `## Status` table prints it beside the outcome it excuses; the parser refuses an entry naming a `[nest]` outcome (a nest record counts for every column, § The two surfaces), an outcome the contract lacks, a column already absent from the whole page, or **every** outcome of the page (a column excused from all of them has none of the feature, and that is the page-level entry, spelled once); the gate keys each entry by the outcome's *sentence*, so a renumbering that re-points it at another outcome is a new move on the record; and rule 6 of the lint reds an entry whose outcome has a witness that passed on that column. **A split is still the right shape when the excused outcomes are, together, a feature a user would name** — the two landed on the user's approval of 2026-09-26, [`formatting-as-you-type`](../../features/formatting-as-you-type.md) and [`pin-a-job-to-this-device`](../../features/pin-a-job-to-this-device.md), stand, each passing the three honesty tests that shape needs: (1) the split page is a feature a user would name, (2) *every* outcome on it is absent on the declared column, and (3) the column still owes, and can complete, everything left on the original page — but it is no longer the only honest shape, and one outcome is not a feature. The evidence rule reads the same for both forms: a goal doc saying a platform lacks a *mechanism* is not grounds for an absence (macOS lacks the collision chooser and still has that feature, by another door), while a goal doc declaring the *behaviour itself* absent on a platform is exactly the citation `absences` requires.
- **A stale stamp is the reader's warning, not a gate.** The lint checks the mapped tests exist and carry the marker; it does not judge the outcomes. Re-stamp when the feature's goal section changes materially.
- **A contract item is not a public text (the owner's ruling of 2026-10-15, [`public-texts.md`](public-texts.md) § The boundary).** The coverage contracts are excluded from the public-texts boundary with the spec they transcribe, so the session that lands a witness writes its item in the same change — no request, no round; the merge gate reads the inventory's exclusion of this section — while the page's title, lead and `## What a user gets` are public texts and change only through a request.

## The two surfaces

Every outcome is witnessed on one of two surfaces, and a cell folds both:

- **`app`** — proven **per app, through that app's UI**: the test drives the app with the `app` fixture family (or a browser for web), so the witness is what a person of that platform would see. The outcome is recorded in that app's ledger and counts for **that column only**.
- **`nest`** — proven **once, app-independently, observed from outside**: an SMTP/IMAP/CalDAV peer, a real Mastodon, the WS-RPC wire, the image's own health endpoint — the shapes under `tests/platform/docker/`, `tests/api/` and `tests/live/`. The outcome is recorded in `nest.json` and counts for **every column**. A `tests/platform/docker/` test stands up its own nest image, so it is a witness of *that* artifact rather than of the run's: its record carries the booted image's own provenance (§ The ledger, *own-artifact records*) and the venue counts like the other two.

A cell is the conjunction: **app outcomes for that column ∧ nest outcomes**. Consequences:

- A **nest-only feature** (every outcome `[nest]`) renders as **one cell spanning all seven columns**, stamped with the nest image digest of the run (in `MATRIX.md`; the site repeats the one mark under every app, § Render). The seed's separate nest-side table dissolves into this — those rows become nest-only pages.
- **A `[nest]` outcome whose promise the shared client code keeps — a seal the nest stores opaque, an artifact the client rebuilds before the nest's gate sees it — is witnessed app-less through the e2e harness library, never re-surfaced `[app]` and never through a second app-less driver (ruled 2026-10-13).** The test drives the same shared-Rust funnel the apps call — the feed manager's train, rebuild and publish paths, the account-plane seat, the model byte-seal — through `fauna-ffi`'s `e2e-harness` flavor and `tests/e2e-unified/fauna_ffi.py`, puts or publishes the funnel's output over the real wire, and reads what the nest kept from outside: its SQLite file and its replies. It launches no app driver, so § The marker attributes it `nest`, and its record counts for every column exactly as the client code it drove ships in every app. Re-surfacing such an outcome `[app]` would reword it — a shrinking move § Closing a gap refuses — and would witness per app a guarantee the apps share; a new test-only binary or a Go twin of client Rust would be a second mechanism beside the one that exists. The library, its gate and its networked-export shape are [`e2e-automation-surface-gating.md`](e2e-automation-surface-gating.md)'s (§ Implementation status today, the C-ABI bullets); the exports the three outcomes this ruling settled still need are captured, not built (§ Implementation status today).
- The **install row** ("Get the app") is `app` surface, witnessed by the artifact and real-session suites (`tests/artifact/`, `tests/real_session/`): the thing under test is the shipped or installed artifact itself.
- **A principal of the user that is no column — the cli app — is a PAGE whose outcomes are `[nest]`, and the app that approves it is a helper seat (decided 2026-11-07 by the design row, advisory — the owner may overrule).** A column names what a person installs and uses *as a Fauna app, through its UI* (the kids ruling, § Cell semantics): the cli app ([`apps/cli.md`](apps/cli.md) § Not a ui.yaml app) has no UI, no ui.yaml flag and no `--app` axis of its own, its per-page parity is already held by its own feature ledger and catalog snapshot, and what an assistant gets does not vary with the Fauna app the person otherwise uses — so a `cli` column would be a second parity instrument whose cells no UI witness could fill, and `[app]` outcomes credited to the approving app's column would grade the approver seven times over for one fact, manufacturing six columns of parity debt or absences no goal doc declares. The cli is therefore one page, [`fauna-for-ai-assistants`](../../features/fauna-for-ai-assistants.md), whose outcomes are what the assistant gets, proven once and observed from outside by the protocol client — the MCP driver is the observer, as an IMAP peer is — so they are `[nest]` and a record counts for every column. Three readings follow. **The approving app is a helper seat.** Typing the code into *Connect an app* is [`connected-apps`](../../features/connected-apps.md)' own first outcome, graded per column there; in a principal's journey it only seeds the grant, and the thing under test is the principal's reach — so a cli witness launches no app driver: the consent is given app-less over the issuer (the `tests/api` consent shape connected-apps' `[nest]` outcomes already use, `fauna.oauth.consent.lookup_code` on the user's own session), § The marker attributes it `nest`, and the card's own claim for this app — its name and the assistant-reach line — is an `[app]` outcome of connected-apps with a marked witness of its own. The six tui-parametrized journeys of 2026-10-17 are mis-shaped for a `[nest]` outcome under the lint's reading (rule 4 reads the fixture closure; the ledger attributes them to tui): until they are re-shaped the page's outcomes read `(none)`, the honest state — never `[app]` on tui, which would be the wrong surface wearing a witness. **One exception, by the mechanism's own shape:** an outcome whose promise depends on the co-resident Fauna app — the conversations plane, served through the custodian app's door ([`../behavior/conversations-oracle.md`](../behavior/conversations-oracle.md) § The custodian and the door) — is `[app]` on the custodian's column, exactly as connected-apps 42 already grades it; web and the phones can never be that custodian, which is a per-outcome absence put to the owner, never declared by a session. **The archive member** — `fauna-cli` beside `fauna-tui` ([`installers/tui.md`](installers/tui.md) § Decisions, 4) — is the page's own `[nest]` outcome, witnessed by the artifact suite's launch-less check of the installed binary, not an outcome of [`get-the-app`](../../features/get-the-app.md), whose outcome ends with an app open and signed in. Nothing here needs a third surface or a per-page column declaration: the two surfaces and the columns stand.
- **Pages are written from the fauna user's perspective even when the witness is a third party.** "People who email you while you are away get a reply" is the user's outcome; that an SMTP peer observed the reply is the witness, not the sentence.
- **The split is a free no-operator check.** A `[nest]` outcome that involves a *choice* — a threshold, a peer, an enablement — with no `[app]` outcome anywhere on the page is configuration-file theatre: a knob nobody can reach from the only configuration surface there is ([`../principles.md`](../principles.md) § One configuration surface). Automatic concerns — DKIM, TLS, MTA-STS, ACME, which [`../behavior/admin.md`](../behavior/admin.md) § 6. Mail keeps off the manual form by design — legitimately have none, because there is no choice. The lint flags the shape; a page that is legitimately nest-only says so in its `What a user gets`, with the literal phrase **`nothing to choose`** — one recognised wording, so the opt-out is a deliberate, greppable act rather than an accident of phrasing. **What the phrase claims (ruled 2026-10-01):** that everything the page promises happens with nothing chosen — not that no setting anywhere touches its subject. The mail server runs with no tuning and an admin may still tune it. Such a choice is an `[app]` outcome on the admin page that owns it, and the nest-only page's prose says where the choosing happens instead of denying it ("nothing to choose to get this", then the pointer). The phrase does not rescue a page whose own outcomes cannot happen until someone chooses: that page is not nest-only, and owes the `[app]` outcome.

## Cell semantics

Per app column, computed by the render from the contract (§ The coverage contract) and the ledger (§ The ledger):

| Mark | Meaning (computed) |
|---|---|
| ✅ | contract **full** AND every mapped test's newest ledger outcome for this column is `passed` (or `xpassed`) — on **every platform** that recorded it (§ The ledger, *Platform keying*) |
| ⚠ | contract **partial**, or the mapped outcomes are mixed — some pass, some `failed` / `error` / `xfailed`, or some pass while another mapped test for this column has no ledger entry yet (a whole half with none is *(empty)*, below) (an unbuilt witness with no real red beside it is *unbuilt*, below), **including a mix ACROSS PLATFORMS**: one test passing on linux and failing on windows is exactly this row's "mixed", never a ✅ |
| ❌ | mapped tests exist and none of them passed for this column, and none is unbuilt (*unbuilt*, below) |
| *(empty)* | **no ledger entry** for this feature and column — a claim about our records, nothing more ([`testing.md`](testing.md) § What the tree may assert about testing, rule 4); the legend never says "untested" |
| — | a front-matter **absence** for this app; a `declared_absence` skip in the run confirms it, a *passing* test on a declared-absent app is a lint error (the declaration is stale). A **per-outcome** absence renders no `—`: the column's cell is computed as any other, over the outcomes it owes (§ The coverage contract) |
| *unbuilt* | the column is held short of ✅ by **build work**: at least one applicable `[app]` witness is **unbuilt** for this column — its newest record is `skipped: unbuilt`, or the surface registry ([`e2e-conventions.md`](e2e-conventions.md) convention 7) declares a *product* surface the witness requires not built on this app — and no record on the column, app half or nest half, is a real red (`failed` / `error` / `xfailed` / a skip of no class). A pass or an unrun witness beside it changes nothing: the unbuilt witness is the known fact. Read **before** the nest conjunct — such a column cannot reach ✅ until the app builds, whatever the nest half says. A real red beside an unbuilt witness is ⚠, because the failure is the more urgent signal. The state word in `matrix.json` is `unbuilt`; the glyph is the build's choice under the marks paragraph below, never a coloured circle (decided 2026-10-25) |

**The marks are ✅ ⚠ ❌, not traffic-light circles, on purpose.** The state itself is a word in the data (`matrix.json`: `full` / `partial` / `failing` / `unbuilt` / `none` / `absent`), and the site renders colour from that; the glyphs are only the committed markdown's rendering. Coloured-circle emoji are the internal review log's severity vocabulary, and the publish gate counts them in every shipped tree ([`publish-gates.md`](publish-gates.md) § Internal-identifier ratchet) — a public matrix using them would be indistinguishable from that vocabulary and would need the gate widened for every rendered cell. The seed used circles; it never shipped.

Four rules the marks rest on:

- **A setup-time `NestModeError` is never recorded (ruled 2026-11-01).** A `--nest` value the run cannot honour — the keyed image absent, a mode not built — is refused in setup, before the thing under test booted; `testing.md` § Default app and nest mode already says a test a mode cannot serve is "never recorded", and the writer (`_feature_ledger_note`) now holds the same for the refusal that slips past collection. The previous ledger line stands, as for an environment skip. A stray `error` record such an invocation wrote before this ruling is removed by hand in the commit that cites it (no prune class covers it).
- **`skip_environment` outcomes are never recorded.** A missing credential or an unreachable port says nothing about the feature; the previous ledger line stands. The same holds for a live box that is not set up for the run — one that answers the admin probe `fauna.auth.not_registered` (the live preflight, `testing.md` § Default app and nest mode → *Live mode*).
- **A test with more than one platform's record folds to one outcome for cell purposes: passing only if EVERY platform passed** (§ The ledger, *Platform keying*). One test can now carry a linux outcome and a windows outcome side by side, so "the mapped tests' outcomes" is never read straight off `tests[node id]` — it is folded first, and a fold that disagreed with itself would let one platform's pass hide another's fail, exactly the miscount the keying change exists to stop; the representative a non-passing fold keeps is a real red before an unbuilt skip, so an `unbuilt` record on one platform never hides a failure on another. A cell's own stamp/date/dirty/base follow the same shape one level up: `cell.platforms` holds each platform's own complete-observation record, and the top-level fields are the oldest of them (the same "shows the oldest artifact" rule the app/nest halves already follow, below).
- **Only a run that collected the feature's whole tagged set for that app re-stamps the cell — and *that app's* set is the citations that can witness *that column*, never all seven apps' together.** A contract normally witnesses one outcome once per app (a linux test, a windows test, a tui test), and a test carrying `@pytest.mark.<app>` runs only on the apps it names — which is exactly what the run's own app axis deselects on. So a column's set is its **applicable** citations: the ones marked for it, plus every unmarked one (an unmarked test is parametrized over whatever the run selected, so it can speak for any column) — and a test restricted to a client set by **parametrization** rather than by a mark is narrowed to that set exactly as a mark would narrow it, because the run's app axis deselects on both. Reading the set as the union across all seven instead makes such a cell **permanently unstampable in every mode on every machine** — no box can collect windows' and linux' and macos' witnesses in one run — which is what it silently did until 2026-08-30 (§ Implementation status today). The same narrowing applies to fullness: an `[app]` outcome with no applicable witness is `(none)` *for that column*, so the column is **partial**, exactly as a literal `(none)` would make it — without which narrowing the set alone would manufacture a ✅ from a sibling platform's witness. `[nest]` outcomes are never narrowed, because a nest record counts for every column by definition. A `-k` subset, a deselection, or a run that collected the set but skipped part of it for environment updates the per-test ledger lines it touched and leaves the cell stamp alone. The cell's stamp is therefore always the stamp of a *complete* observation — **and it names ONE artifact.** When the observation's records all carry one stamp (every ordinary feature; a feature witnessed wholly under `tests/platform/docker/`, whose records carry the booted image's stamp — § The ledger, *own-artifact records*) that is the cell's. When they name two artifacts (a `tests/api/` witness against the run's nest beside an own-image witness against the booted image) the cell shows the **oldest** — the artifact whose commit is a strict ancestor of every other's, the same older-of-its-stamps rule the two halves follow below. **Two stamps at that one commit are ordered too, weakest claim first (ruled 2026-10-31):** both name that commit, so the ordinary mixed nest page, whose image is the run's own commit, stamps on every whole run. A dirty stamp goes first, because the cell's `dirty` travels with the chosen stamp and a clean choice would hide dirty witnesses (*Dirty trees*, (b)); then the modes in the order `standalone`, `docker`, `live`, from the box's own binary to a deployed nest; then a `-dev` stamp before a bare one, because a bare stamp claims every witness saw the released artifact. Where git cannot order the commits (unrelated or unseen ones) the observation updates the per-test lines and leaves the cell stamp alone, exactly as a subset does.
- **One artifact, several runs: two runs of the same CLEAN stamp on the same platform complete the set together (ruled 2026-11-01).** The whole-set rule asks that every member of the column's set was observed against ONE artifact, and the stamp is what names an artifact: commit, nest mode and cleanliness. An observation is therefore of the artifact, not of the invocation that made it, so when a run observes only part of a column's set, each member it did not observe counts as observed if its ledger record on this run's platform carries one of this run's own clean stamps. The run then stamps the cell exactly as a run that collected the whole set would (`feature_ledger.borrowable`, read by `cell_complete`, and the borrowed records join the stamp choice). It exists because some sets cannot be collected by one invocation by design: the drafts-survive set holds a witness that re-times the autosave window beside witnesses that need the production window, and conftest refuses that mix in one selection (`_refuse_drafts_window_collision`), so the cell was unstampable on every column. It also covers the ordinary case of a session re-running its reds in a second invocation at the same commit, which left three tui cells (feed-delete-own-post, nostr, multiple-accounts) stale with every member green at one clean stamp. Three things never combine. A dirty stamp neither lends nor borrows, because its commit is only a lower bound and two dirty runs of one HEAD may have seen different edits (*Dirty trees*). Another platform's record does not combine, because `cell.platforms` keeps each platform's own complete observation. Another stamp does not combine, because that is a different artifact. Splitting the set by window class in the contract was weighed and declined: it moves a harness constraint into every page that cites a re-timed witness, and it leaves the re-run-at-one-commit case unsolved.
- **A witness that can drive only some apps is MARKED for them, never gated by a `declared_absence` on the others (ruled 2026-09-26).** The two gates answer different questions: an `absences` entry or a `declared_absence` skip says the *platform lacks the behaviour*, while `@pytest.mark.<app>` says *this test can drive these apps* — a web-only read through `eval_js`, a native-only twin of a web journey. Gating such a test on the apps it cannot drive records a `skipped: absence` on a column the page does not declare absent, which is a permanent red no run can clear (`features-gaps --reds` lists the class); marking it narrows it out of those columns' sets under the applicable-citations rule above, so the column's outcome is witnessed by its own twin and nothing is owed of the test that cannot run there. Not a contract move: the page's witness set is unchanged. A two-seat witness can need the same narrowing inside one test: a phone marked as a member column must not also collect as the owner, so `@pytest.mark.first_seat(<apps>)` names who may hold the first seat and outranks the app marks for that seat at collection. And a seed only a desktop can make does not excuse a phone from an outcome about the device the journey ends on: a helper seat seeds, the phone is the seat under test (*A helper seat is not an app under test*, § The marker).
- **Two sources, one observation: a record is the NEWER of the ledger's and the published last-green snapshot's for its key (built 2026-11-01).** Conftest writes both from one event ([`delayed-testing.md`](delayed-testing.md) § The last-green directory, *one event, two projections*), but a session's ledger note lands only when that session commits it, while the check publishes the snapshot from the machine's store — so the committed ledger can hold an outcome the snapshot has already superseded (measured 2026-11-01: 55 linux reds from one sweep whose re-run greens no session committed). Every cell reader — the render, the lint, `features-gaps` — therefore reads, per ledger record (app file × test × platform), the snapshot `docs/features/last-green/<platform>.json` in the tree, **never the machine-local store**, so every checkout renders the same matrix. The two keys meet on the stripped node id: an app file's record is answered by the keys carrying its app token in its own nest mode (the default mode unstamped; a `docker` record with no stamped key by a lone unstamped one — an own-artifact test), the nest file's by keys naming no app, and EVERY variant the ledger collapsed (`[linux-eml]`, `[linux-mbox]`, …) must answer and agree, or the ledger stands; a seat-set key (`[2seat-native+native]`, `[docker-2seat-tui+tui]`) names its apps through its seat MODES, each resolved on the snapshot's platform by the one mode→app table conftest's `_apps_for_seat_pair` reads (`tests/e2e-unified/helpers/seat_modes.py`, the platform name mapped to its `sys.platform`), with the § The marker crediting — a device-only seat (`phone`, `web`) credits only itself — so `native+native` answers the linux record on `linux` and never tui's, a seat key is never taken by the no-app-token fallback, and a mode the platform cannot launch answers nothing (built 2026-11-01; until then a seat key fell into that fallback, so a stale `tui+tui` record could answer a linux one). The snapshot supersedes when its newest observation is on a later DAY than the ledger record's (the ledger keeps the day only), or on the same day when its last green's merge base descends from the ledger record's — both on `origin/main`, so every checkout answers alike. Only `green`, `skip:unbuilt` and `skip:absence` supersede, read with the ledger's classes (a dirty green is a dirty pass and marks its cell dirty, as a dirty ledger pass would): the directory also notes reds the ledger deliberately declines — the setup-time `NestModeError` above, an own-artifact test naming no artifact, a `--strict-app` refusal the ledger records as `skipped: unbuilt` — so a directory red cannot say the ledger would have recorded it, and a newer red reaches the matrix only through the ledger (the tester's red lands as a janitor entry). Only records the ledger already holds are superseded — the slug a test answers for is the ledger's knowledge — and the files are never rewritten: lint rule 6 and `features-prune` judge the files as written, and a hand edit of a ledger file stays a never-move (§ Closing a gap).
- **The nest half is a conjunct on every column.** A feature whose `[nest]` outcomes have no ledger entry renders empty on every column, however green its `[app]` half — and vice versa. Each cell shows the *older* of its two stamps. The nest half's own stamp is the fold of its platform LEGS — complete only once every leg holds one (§ The ledger, *Stale records*, ruling (h)).

Because fullness is read per column, a column short of full is short of it for a **nameable outcome** — one no test that can speak for that column witnesses. That is a question about the contract alone, answerable by the parse with no run at all, and **`just features-parity`** is it: per page, the columns some run could ever complete and the outcome blocking each of the rest (`Page.completable` / `Page.blocking`, one definition shared with `full_for`). The sharpest verdict it gives is a page completable on **no column** — its blank cells are then a fact about the contract, not about our records, and no run on any machine in any mode will move them. Distinguishing those from ordinary blanks is what stops a coverage backlog being read off a page list by hand. That view is **page-major** — the columns one page is short on — which is what a reader of one page wants. Routing the backlog wants the **transpose**, because a trickle-down pass and the queue that receives its capture are both per app, never per feature ([`testing.md`](testing.md) § Default app and nest mode), so **`just features-parity --column <app>`** asks what one column is short of across every page and **`--by-column`** prints all seven as one table (`column_backlog`, the same `blocking` rule read from the column's side). Its split is the routing decision: an outcome a **sibling column already witnesses** is this column's parity debt, closable by a lift with the reference named, while an outcome **no column witnesses** is an unwritten test owned by the feature's area, which no app queue can close by lifting anything. A declared-absent column has no backlog at all — `—` is neither completable nor short, so counting it would read a designed absence as coverage debt. A column's debt is the right unit for **doing** the work and the wrong one for **moving** it, so `--by-column` prints a second unit beside it: an outcome witnessed on a single app is short on six columns, and sending each column's list to its own app queue would mint that one piece of work six times — the per-feature × 6 shape [`testing.md`](testing.md) § Default app and nest mode refuses, arriving through a count rather than through a plan. **`Gap.reach`** — how many columns one missing witness blocks — separates them: reach 1–2 is a **straggler**, this column genuinely behind its siblings and ordinary trickle-down for its queue; reach 5+ is a **wide** gap belonging to one cross-app row, never one row per short column. Between them, reach 3–4 is **trickle-down in flight**: three or four columns already carry the witness, so the references exist and what remains is the ordinary batched per-app pass — it rides in the same per-app row as that column's stragglers, never a row of its own per feature, and a gap of any reach that **tui** owes goes to tui's queue first with new-feature urgency (the lead app lagging a feature its siblings shipped). **`just features-parity --column <app> --max-reach 4`** prints exactly that batch (`column_trickle_down`), so a per-app row derives its list and re-measures its premise with one command and never transcribes it. Reach ranks liftable debt only, so an outcome nobody witnesses is excluded rather than ranked as reaching all seven.

**Not built is DECLARED, and the matrix reads it without a run (decided 2026-10-25 by the design row, advisory — the owner may overrule).** Until this ruling a cell learned that an app had not built a feature only when a test ran on that app and reached a `skip_unbuilt` gate its author had written, as an `if app not in (...)` inside the test body or an action class — a shape neither the render nor the cause view can read, so a blank or unrun cell could not tell *not built* from *not tested*, an app lacking a feature with no gate failed on a missing element instead of skipping, and a recorded skip outlived the gate that wrote it (the measurement is in § Implementation status today). The fix is one source that the gate and the render both read: **convention 7's surface registry** (`tests/e2e-unified/surfaces.toml`, owned with the gate, the marker and the ratchet by [`e2e-conventions.md`](e2e-conventions.md) convention 7) — one entry per surface key, a ui.yaml id where one exists, its kind (`product`: the APP lacks it; `harness`: the e2e driver or harness lacks it for that app) and the apps that built it. The gate every test and action class already executes (`require_surface`) reads it at run time; this catalog reads the same file statically. Five readings this doc owns:

- **The test → surface map is the union of two readers.** (a) The test's `requires_surface` markers, read by the same `ast` scan as its app markers (§ The marker; optional, except where the gate must pre-empt a fixture — convention 7's 2026-09-22 rider), and (b) the `surfaces` list every ledger record carries since the registry — every `require_surface` call the run reached, fired or not — unioned over the test's records on every platform and in every ledger file. A run on any app therefore teaches the map what every other column will meet, and a test with neither a marker nor a record is read exactly as before. **The union is a prediction for a column with no record of its own; a record is judged on what its own run met (decided 2026-10-30, advisory — the owner may overrule).** A record that can say which gates its run reached — one carrying `surfaces`, or any record dated 2026-10-26 or later, since the writer omits an empty list — counts a key only another record taught (a *borrowed* key, never one of the test's own markers) only if it reached that key itself: its ungated reading and lint rule 7(a) read the map minus the borrowed keys it did not reach (`features_catalog.Declared.requires`, `record_reach`, `SURFACES_RECORDED_SINCE`). Without this a gate the test stopped calling stayed in the map for as long as any platform's newest record predated its removal, so a column's real red read as *unbuilt (ungated)* and its pass tripped rule 7(a) until another machine happened to re-run the test (measured 2026-10-30 on the windows column of `test_folder_location_free_space.py`). It reads a removed gate, and a gate narrowed behind a branch only some apps take, correctly whatever order the runs land in; the cost is an added gate, which reaches a column's record only once that column runs the new code — until then its older failure reads as the real red it then was. A record written before the writer listed reached gates cannot say, and still reads the whole map. Weighed and declined: *supersession by date* (a key drops once a newer record omits it) — it flips with the order runs land in, so a narrowed gate's next run on the branch that keeps it puts the merge-blocking rule-7(a) finding back. **A declaration counts for a column when the registry says that app has not built a `product` surface the map says the witness requires.** A `harness` surface never makes a cell *unbuilt* and never counts as a red: the witness is *unrun — the harness cannot drive it here*, a sub-cause the cause view names beside *short* (§ Closing a gap), because a missing driver capability says nothing about the app.
- **Why this is not the second truth § Keeping every cell current declined.** The declined shape was a `built:` map in page front-matter or a line of owner-doc prose: a claim nothing ran against, consumed by the render alone, so a wrong entry stood for ever. The registry is the gate the run EXECUTES, and the run refutes it in both directions: an over-claim (declared built, not built) lets the witness run and fail on the missing surface — a real red the cell shows at once; an under-claim (declared unbuilt, built) is a lint error the moment a passing record of a test that requires the surface exists on that column — the same rule a passing test on a declared-absent app already trips — and a `--strict-app` red until then. It stands exactly where `absences` and `@pytest.mark.<app>` stand: hand-written inputs the instrument confirms or refutes, never a hand-judged cell. And it removes truths rather than adding one — 209 free-text `surface=` strings and three scattered homes of the same fact (literal app tuples in guards, module constants such as `_BUILT_APPS`, trivial-constant driver predicates such as `has_day_cell`) become one file. The decline stands against the shapes it named; it does not reach this one.
- **One state, two routes.** The computed route (a `skipped: unbuilt` record) and the declared route (registry × map) feed the same *unbuilt* reading in the marks table; a cell is *unbuilt* on either, and ⚠ when a real red stands beside either. A pre-registry record — `skipped: unbuilt` with no `surface` key — read as a product-unbuilt record until the one-time prune dropped them (2026-10-28, below); none remains.
- **Staleness is decided by the registry, and the record is pinned to its surface.** A `skipped: unbuilt` record carries `surface`, the key the firing gate named (§ The ledger). When the registry later lists that surface as built on the record's column, the record is STALE: the render reads it as *unrun*, never as unbuilt and never as a pass; lint rule 6 refuses a ledger that holds one; `features-prune` drops it — so the commit that widens a registry entry runs the prune and carries the result, exactly as the commit that moves a marker does (§ The ledger, *Stale records*). The widening is the act of saying *built*; the record was an observation of a gate that no longer fires there, and the next run on that column re-records whatever the test now does. Pre-registry records could not be matched to a surface, so the migration's final step pruned every surface-less unbuilt record at once (2026-10-28, `features-prune --unbuilt-without-surface`); where a gate still fires, the next run writes the record back with its key.
- **An ungated failure is read for what it is.** A `failed` or `error` record on a column where the map and the registry say the test requires a product surface that app has not built is an **ungated failure**: the gate is missing from the test, or the record predates the declaration. The record keeps its outcome; the cause view lists it as *unbuilt (ungated)* and names the test, whose fix is one of two edits (add the gate, or widen the registry); and the cell reads it as unbuilt, not as a real red, because the registry — refutable as above — says what the failure means. The hiding this invites is named and fenced: *declaring a surface unbuilt on an app that has it* is a never-move (§ Closing a gap), and a surface keyed by a ui.yaml id that `ui-actual-<app>.yaml` records as present on that app cannot be declared unbuilt there (a lint error naming both files). Narrowing an entry — an app dropped from `built` — is the honest correction of an over-claim and needs no record; the red witness that motivated it is the evidence.

**A second store identity of an app, with a surface set of its own by design, is a COLUMN — the kids channels `android-kids` and `ios-kids` (decided 2026-11-07 by the design row, advisory — the owner may overrule; the shape itself is the owner's ruling D-K6 of 2026-09-25, [`../behavior/account-age-band.md`](../behavior/account-age-band.md) § The account age band, the kids-app bullet: *the feature catalog gains a column per kids channel, never a second catalog*).** A column names what a person installs and uses, and Fauna Kids is such a thing: the android and ios apps built under the `kids` flavor, with its own store identity (`social.fauna.faunakids`), its own listing, its own users (supervised accounts) and a surface set the owner fixed by design (D-K5's *Kept*, *Excised* and *Floored* lists). Recording its runs under the parent app's column would make one cell speak for two artifacts whose surfaces differ by design — a conversations witness green on the main build and a link-preview witness red on the kids build fold into one android cell that can say neither, and the ledger's stamp names a commit, a nest mode and a cleanliness, never a flavor — while recording nothing leaves the build children use with no witnessed state at all. So the two kids channels are columns of their own, read exactly as the seven — the same marks, the same whole-set re-stamp, the same two surfaces, the same `--strict-app` reading — each with its own ledger file (`android-kids.json`, `ios-kids.json`, [`feature-ledger.md`](feature-ledger.md)) written when the run's app axis names it (`--app android-kids` / `--app ios-kids`: the parent app's driver launching the kids identity — the kids APK, the `Fauna-Kids-iOS` build product — on the parent's venue, keyed to the parent's platform in the last-green snapshot). **A kids column's applicable set is its parent's:** a witness marked `android` or `ios`, or unmarked, can speak for the kids column of that app, because the kids build is that app's UI with planes removed — a test that can drive android can drive android-kids — and a witness whose journey crosses an excised plane is kept out of the kids column by the page's absence (a `declared_absence` skip), never by a mark; the surface registry gains the two columns, listing a product surface as built on them where the kids build keeps it, while a harness surface — the driver's — answers for a kids column as for its parent. **What the parent lacks by design, its kids column lacks too:** a page-level absence declared on `android` or `ios` makes the kids column absent from the page, and a parent's per-outcome absence excuses its kids column from that outcome — under the parent's citation, carried by the parse (`features_catalog._inherit_kids_absences`), with no move of its own at the contract gate, since the parent's record already carries the approval; a kids per-outcome entry on a page its parent is absent from is refused. **Absences on the kids columns are the owner's D-K5 list, approved once:** every page whose outcomes live in an excised plane — the feed and composing, search and discovery, every bridge and mail page, web publishing, monetization, outbound links and link previews, connected apps, labelers, personalization, nest setup and retirement, photo backup, critical alerts — declares `android-kids` and `ios-kids` absent citing that bullet, and the contract-move records name it as where the approval is recorded; a page the list does not plainly cover (a kept plane with one excised outcome — a per-outcome absence) is put to the owner before it is declared. A store flavor that keeps the main listing's identity (`store-safe`, `store-no-payments`) is NOT a column by this ruling — it is the same thing a person installs from the same listing — and how its omissions are read is a question of its own. The floor's own outcomes — what the kids build does that no `—` can say: a link shown as plain text that opens nothing, a profile only for a confirmed contact with no Follow and no Tiers, remote pictures never fetched, the four categories blocked whatever the guardian chose, the not-supervised screen, no nest setup or retirement offered — are one page of their own, `kids-app`, owed on the two kids columns and declared absent on the seven, because on the main builds they are false by design: a seven-column absence is the honest shape here, where the credential store's six were not (§ Implementation status today, 2026-09-26 — there a platform-neutral page existed; here the outcomes have no main-build reading). Until the columns are built the page cannot land (the parser refuses an unknown column) and the kids build has no cell — § Implementation status today.

## Closing a gap

**A cell short of ✅ is closed by product work and a recorded run — never by an edit to the catalog (user directive 2026-09-19).** The catalog is the instrument that measures the distance between the product and its goal docs; an edit that moves a cell without moving the product makes the instrument lie, and every later session plans from the lie. The sanctioned moves are exactly four: **build** the feature on the app that lacks it, **write** the witness an outcome lacks, **fix** what a red witness found (in the product, or in the test when the test is what is wrong — a timing-brittle test is defunct, [`e2e-conventions.md`](e2e-conventions.md) convention 14), and **run** the column's whole set so the ledger records it.

**Never a gap-closing move:** deleting, merging or softening an outcome; deleting a page; adding an `absences` entry; declaring a surface unbuilt on an app that has it (the surface registry, § Cell semantics — it turns a red the app owes into an *unbuilt* it does not); re-pointing an outcome at a weaker test; skipping, `xfail`ing or deselecting a witness so a red stops being recorded; hand-editing a ledger file, a `## Status` block, `MATRIX.md` or `matrix.json`. The test for any contract edit is **would this edit be made if no cell moved?** — the edits this doc does sanction pass it on their own grounds: an outcome *added* because the goal section promises more than the contract lists (cells move down, honestly); a re-authoring under the mis-authoring boundary (§ The coverage contract — *permanently partial under every witness set anyone could write*, and only that); a re-stamp after the goal section changed. **A new `absences` entry is a new per-app deviation and needs the user's approval, like any other — explicit where no goal doc yet declares the behaviour absent on that platform, advisory where one does (the entry is a declaration with a veto window, [`fleet-daily-asks.md`](fleet-daily-asks.md) § The daily asks → *The advisory approvals*; owner-ruled 2026-11-10)**, on top of the goal-doc sentence the front-matter must cite; a column that is short because its product or test has not arrived stays honestly short.

**The gaps come in three layers, and only the first two are visible in the matrix.** (1) **A cell short of ✅** — by cause, computable per cell from the contract and the ledger: *short* (an outcome no test that can speak for the column witnesses — `just features-parity`; a missing witness very often hides a missing implementation on that app, so the first act is to check the app, not to write the test), *unrun* (a mapped test with no record for the column) and *red* (a mapped test whose newest record did not pass — a skip included, since a skip is recorded as not passed; its recorded class, `unbuilt` or `absence`, subdivides the cause rather than adding a fourth — and since 2026-10-25 *unbuilt* is read from the surface registry as well as from the record (§ Cell semantics, *Not built is declared*): an unrun or failed witness on a column that has not built a `product` surface it requires is *unbuilt* (a failed one is listed as *unbuilt (ungated)*), one held by a `harness` surface is *unrun — the harness cannot drive it here*, and where neither a record nor a declaration exists the cell is *unrun*, which cannot tell a test that would skip as unbuilt from one that would pass). (2) **An outcome the goal section promises and the contract does not list** — found only by reading the page against its `goal` section. (3) **A user-facing feature the goal docs ratify that exists on no app** — it has no page by § Implementation status today's first ruling, so the matrix cannot show it at all; it is tracked as a work item in the owning area's queue, and its page is minted with the first implementation. Done means all three are empty: every goal-doc-ratified user-facing feature has a page, every page's contract lists what its goal section promises, and every cell without a declared absence is ✅.

**Every live gap row is a prerequisite of the done-state, so the drive runs at whatever width the fleet has (user-directed 2026-10-28).** Capturing a gap in the queue that owns it is half the job: a row nothing points at is drained only when that queue's own session or a pool happens past it, and the done-state cannot say how far away it is. So every open row whose success performs one of the four moves for a catalog cell — a build, a witness, a red's fix, a run, the venue a column needs to run at all, or the decision a specific gap waits on — is named by the done-state's typed prerequisite (its `AFTER` line, [`task-kinds.md`](task-kinds.md) § Kinds), written by whoever mints or routes the row and audited by the driver on every pass; the row stays in its owning queue, at its own weight and machine, and lapses out of the prerequisite by landing. The done-state is then an objective the broker serves on every machine at once, assigning each launchable gap row from any queue by its score ([`fleet-scheduler.md`](fleet-scheduler.md) § The assignment; until 2026-11-02 target loops did it, [`next-loop.md`](next-loop.md) § The loop → *The target loop*), with the driver's own pass laid between them as a `STANDING` task's is, once its rest has run out ([`fleet-scheduler.md`](fleet-scheduler.md) § The assignment) — the width is the human's to choose at launch from the load, never a figure written here. A row the driver is unsure serves a cell is left out: a spurious prerequisite only spends a judged session on wanted work, but the list is the drive's whole map, so it names what closes cells and nothing else.

**The driver's pass yields tasks — per machine, biggest gaps first, nit-picking rather than none, 25 a pass, walked by a coverage log (user-directed 2026-10-29).** Feature parity is not expected to be reached: the drive is perpetual, and its product is launchable rows. Capture alone is not feed — at pass 33 the map held 235 open rows of which ONE could launch on Linux, the rest held, asked, tagged for another machine or waiting on a mind, and the pools idled; and a pass minting only Windows and macOS rows would leave Linux as empty as before. So: (1) **the pass was laid once any machine's launchable gap rows fell under the feed floor, 10** (the loop's mechanism retired 2026-11-02 — [`next-loop.md`](next-loop.md) § The loop → *The target loop*, ruling (c) → *The driver's queue is fed* — and the trigger restored in the broker 2026-11-06: a machine whose launchable rows fall under 10 makes the goal's own pass governor demand on its own checkout, [`fleet-control.md`](fleet-control.md) § The pool governor → *A driver goal is fed*, which also reads the brake below; from the `GOAL` kind's retirement, ruled 2026-11-08, the driver is a `STANDING` task carrying `**Feed:** 10` and the outcome — the task the minted parts hold — is a task of its own, [`task-kinds.md`](task-kinds.md) § Kinds → *A `GOAL` task is the fleet's flag*, ruling (4)); (2) **the yield is PER MACHINE**: for each of Linux, Windows, macOS the pass reads that machine's count from the outcome task's target report for that machine, SKIPS a machine at 10 or more, and for a machine under it mints toward **25 new rows a loop there could lay today** (open, unclaimed, ungated, no open `AFTER`, no ask, tagged that machine or `any` where it owns `any`) — never a row for a machine already at its floor; (3) **the tui column first, then biggest gaps first** within a machine (the tui rung owner-ruled 2026-11-13): tui is the lead app ([`testing.md`](testing.md) § Default app and nest mode) — a feature built there builds its shared Rust first, the app runs on every dev machine and it is the quickest to iterate on — so every feature is wanted on tui before the other apps, and while the tui column holds a cell short of ✅ the pass reads EVERY such cell against its owner before any other rung, on every machine whatever its count, and does not end until at least one row that closes a tui cell is launchable or working in the fleet: it mints the piece that can launch, or lifts the met gate that holds one, ahead of any row for another column, and its record names, cell by cell, what holds each tui cell it could not feed (an ask, a venue, a release run, a tester's shard); only then the WIDEST list (reach 5+, one cross-app row each, tui first), then the reach histogram downward, then the column with the most owed slots, then the nobody outcomes, then the reds by run, then the unrun columns, then the stamps over the currency bound; (4) **down the ladder rather than none**: when every large gap on a machine is already owned by a row that can launch, the pass mints the small work — a single red, a single unrun cell, a `.dirty` re-read, a stale stamp's re-run, a witness whose assertion was rewritten on one column — because small rows are feed too and an empty yield is a defect of the pass, not a state of the product; (5) **never a second row for the same success**: a gap owned by a row that cannot launch is fed by minting the piece that CAN (the leg on a machine that runs, the half before the ask, the run that needs no venue) with the held row `AFTER` it, or by removing the blocker — a lapsed gate released, a met ask answered, a stale premise re-derived — never by duplicating the held row; (6) **the pass is an INCREMENTAL sweep over the coverage log, `docs/features/ledger/driver-coverage.jsonl`** (append-only, beside the ledger and like the ledger never shipped): one record per (machine, area) the pass examined — an area is a catalog page or a cause bucket of a column (`reds:<run>`, `unrun:<slug>`, `stale`; `*` the whole machine) — with the pass, the date, the catalog tree and the page blob it was read at, the outcome (`minted` with the rows, `owned`, `exhausted` with the blocker named, `clear`) and a note. The pass opens a machine's walk with the log's viewer: areas never lit first, then areas lit at a state that has moved since, then by oldest light, and an area whose newest record reads `exhausted` or `clear` at the current state is skipped without a look; it records every area it looked at, the empty ones included, through the log's writer, because *nothing here* is exactly the light that saves the next pass; (7) **a machine that cannot be fed is braked**: a pass that runs out of legitimate rows for a machine below 25 writes `--area '*' --outcome exhausted` naming the blocker, and the selector does not lay the pass for that machine while the machine's GAP SET is unchanged — the record carries `gaps`, a digest of every cell short of ✅ in the columns the machine can be fed rows for (Linux: linux, web, tui, android; macOS: macos, ios, tui; Windows: windows, tui), each cell by its page, column, state, causes, short outcomes and unrun and red witnesses, and nothing a re-observation moves (a stamp, a date, a red's kind); a commit that opens, closes or changes such a cell lets the light in again, a tester observation commit that re-renders the catalog and moves none does not (2026-11-07: keyed to the catalog tree, the brake was lifted hourly by those commits and re-fed a pass every rest for a machine whose gaps were all asks); a record with no digest falls back to the catalog tree; and the daily pass still audits (the pass's own skip of that machine's walk — the coverage plan's `brake` — and, since 2026-11-06, the governor's feed, which does not count a braked machine as starved). The never-moves above bind every row minted: a row's success is one of the four sanctioned moves, never a catalog edit.

**The contract surface only shrinks on the record (ratified 2026-09-19).** The never-moves above are prose, and prose does not stop a session that reads a red cell as its task, so a cheap merge gate compares the catalog's **contract surface** — the pages, each page's outcomes (surface and sentence), its `absences`, and each outcome's witness set — between the merge's base and its tip. **Monotone moves pass silently**: a page added, an outcome added, a witness added, a `(none)` replaced by a witness, an absence removed, a citation or a stamp changed. **Shrinking moves red the merge**: a page removed, an outcome removed or reworded (any change to its surface or sentence — a typo fix included, because the gate cannot tell a softening from a correction and must not try), an absence added (on a new page too; page-level, or per-outcome — the latter matched by the outcome's sentence, so an entry re-pointed at another outcome by a renumbering is an addition too; narrowing a page-level absence to some outcomes is monotone), a witness removed (a re-pointed witness is a removal plus an addition; so is a renamed test). A slug rename (§ The page) that git follows as a rename is compared as one page and passes when nothing else shrank. A shrinking move lands only when **the same merge appends one record per move** to the catalog's contract-move log — an append-only file beside the ledger, which like the ledger does not ship — naming the date, the slug, the move, its subject (the outcome sentence, the app, `<app>: <outcome sentence>` for a per-outcome absence, the test id, or the new slug), the **goal-doc citation that justifies the edit on its own grounds** (it must resolve, like any contract citation) and one sentence of why; an added absence additionally names **where the user's approval is recorded** — or the declaration that stands in for it (`advisory D<n>`, the declared ledger's entry, which the gate finds on the same tip: class `absence`, its claim naming the page). The gate checks that the record exists, matches the move and cites something real. **It cannot check that the justification is true or that the user was asked, and does not pretend to**: its job is to turn a silent edit into a loud, deliberate, permanently listed act — the red names this section, and the log is the audit list the standing gap driver reads on every pass, record by record, against the test above. **A record may be filed late (2026-10-02):** one carrying a `landed_in` commit (it must be in the checkout's history) files the move that commit made after the fact; it never covers a move of the merge that appends it, so no session excuses its own edit that way, and the merge gate does not demand it match one. **The asynchronous check's range run replays the range one catalog-touching commit at a time** rather than net-diffing it: its base is the last all-green tip and stands still while any gate is red, and over thousands of commits a net diff classifies a move by the range's end state, so records the merges landed honestly stop matching and the gate can never clear. Each commit's moves need a record anywhere in the range; a record matching no single commit's move is not an error there, because a merge lands several commits. For the same reason a net-zero span cancels: the moves commits *i..j* made on one page are dropped when that page at *j* has no shrinking move against it before *i* (an outcome reworded and restored inside one merge), because the merge gate's net diff saw no move there and refuses a record for one. Two channels stay outside it, by ruling rather than oversight: **muting a witness** (`skip`, `xfail`, deselect) cannot raise a cell, because a skipped or xfailed outcome is recorded as not passed and an unrecorded one leaves the previous record standing (§ Cell semantics) — so it is left to the skip ratchet ([`e2e-conventions.md`](e2e-conventions.md) convention 7) and earns no second mechanism here; and **weakening a witness's body or hand-editing a ledger file** changes no contract surface and is caught only by reading the commit behind a cell that moved, which is the same driver's first act on every pass.

## The marker

- **`@pytest.mark.feature("<slug>", …)`** — registered in `tests/e2e-unified/pytest.ini`; a test may name several slugs. It is the test → feature direction of discoverability; the contract is the feature → test direction, and the lint (§ The catalog lint) keeps the two consistent.
- **Validated at collection**: an unknown slug (no `docs/features/<slug>.md`) is a collection error, exactly like the strict `tier_N` marker check — a typo cannot silently create a feature nobody has a page for. ⚠ **The validation is on EVERY pytest run under `tests/e2e-unified/`, so its cost is everybody's cost**: it needs the slug *vocabulary* — the page filenames — and nothing more. It read that vocabulary through the per-column witness split until 2026-09-05, which `ast.parse`d and `ast.walk`ed all ~757 test modules and then discarded the result with `set(...)`: **1.9 s added to the collection of every suite in the tree** (measured on Windows, an unrelated 111-test suite 4.9 s → 3.0 s; `payments-excision-spine-check` 3.4 s → 1.4 s). `helpers/feature_ledger.py::known_slugs` reads the pages directly and `contract_surfaces` — the expensive one — is called only where the split is actually used; `test_known_slugs_is_the_pages_and_costs_no_tree_scan` pins both the agreement and the absence of the scan, because equality alone would stay green if the cheap path became the expensive one again.
- **`--feature <slug>`** (repeatable) selects the tests carrying the marker; combined with `--app` and `--nest` it is the way to re-witness one feature on one app in one mode.
- **App attribution** is decided by the run, not the marker: a test that launched an app driver is attributed to that app, by `helpers/app_surface.py::app_name` — for **every** driver it launched (a multi-seat test that drives three desktop apps witnesses all three); a test that launched **no** app driver is a `nest` witness. A marker never says which app; the `app`/`nest` surface is fixed by the contract line, and a mismatch (a `[nest]` outcome whose test drove an app, or a `[app]` outcome whose test drove none) is a lint error.
- **A helper seat is not an app under test (ruled 2026-10-14).** "Every driver it launched" presumes symmetric seats: N GUIs of the app the item is parametrized by, each one a seat a person of that platform could be sitting at, every one observing the outcome (the two-GUI inbox-drain proof, the convention-16 seat pairs). The cross-app pairs are not that — a linux sender for a web receiver, a macOS or tui builder seat for a phone under test, a tui organizer on the android column, a tui seat on a viewer column (`conftest.py::_CROSS_APP_FIXTURE_APPS` is the list): the second app plays the *peer*, and the outcome is observed on the app the run's app axis selected. Attributing the peer's column too stamps it with an outcome its app never demonstrated as the app under test: the cross-member reaction witness recorded `linux: passed` against "a reaction from someone else shows on your copy" when linux's seat *gave* the reaction and web's copy showed it. **The rule: an app-parametrized item is attributed to the apps its parametrization names** (`_item_param_apps` — a seat pair names both), a driver it launched for any other app is a peer and writes no record, an item with no app parametrization keeps the launched-driver reading, and one that launched none is `nest`. A test whose outcome is genuinely observed on both seats of two different apps is parametrized by the pair, which names both. The mark rule (§ Cell semantics) already keeps a correctly marked peer record out of its column's cell, so this moves no cell: it is the ledger's honesty — the per-test outcome column a page's `## Status` prints showed the peer column as a pass, and an *unmarked* cross-app test would have stamped the peer's cell outright. ## Render

**`just features-render`** reads every page's front-matter and contract plus the ledger, and writes three things — four, once a build is verified — idempotent, pure stdlib, sub-second, so it runs unconditionally and the lint (§ The catalog lint) checks the committed output is current (the `i18n-generate` / `i18n-check` split):

3. **`docs/features/matrix.json`** — the same model as data, and the **only** thing the public site imports.
