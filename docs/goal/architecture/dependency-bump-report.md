# Dependency bump report — the consequences of a version bump, before its code runs — target state

Owns: dependency-bump-report, bump-round, bump-queue, whole-effects-analysis
Status: ratified — the rule, the report's shape and its two further layers owner-ruled 2026-10-04; built the same day (§ Implementation status today); the owner-opened round, the between-rounds queue and the whole-effects analysis owner-ruled 2026-10-05 and built the same day, the round half in force only once the repository is public (§ Who opens a round); the out-of-round security fix ruled 2026-10-05: it waits for a round (§ Who opens a round)
Authority: owns what is known about a dependency version bump BEFORE any of the new versions is installed, built, run or read — which new code would run on the build machine and when, which would ship and where, and which crude-but-safe checks its source passed. Neighbours that do **not** own this: [`release-integrity.md`](release-integrity.md) owns dependency verification as a whole — the scanners, the minimum release age, the review venue, the exception lists; this doc is one step inside that, run per bump.

## Goal

**Ruling (the owner's, 2026-10-04): before a version bump's code runs on a build machine or is read, the bump's consequences are laid out in one table, produced by a tool, for every bump.** A lockfile bump is new third-party code arriving in three places at once: on the machine that builds it, in what it builds, and in the context of whoever reads it. The scanners in `release-integrity.md` answer whether a known advisory matches a version; none of them answers what the bump *does* — whether the new code runs at compile time, under a build tool and with what permissions, or only in a test; whether it ships to users; and whether anything checkable vouches for where its bytes came from. Without the table that question is answered by intuition, one bump at a time, and there will be many bumps.

## The report

**One row per package version the bump adds or changes**, for every tracked `Cargo.lock` — the workspace's and each vendored fork's own standalone lock — and every tracked `deno.lock` (each found from the index, like the npm audit). Every column is computed from lockfiles, manifests, registry metadata and scanner verdicts; none needs a model to read dependency source, and none runs dependency code.

- **Identity:** ecosystem, package, old version → new version (or *new*), the new version's publish age, and whether the change came in through the security-fix bypass of the minimum release age.
- **Runs on the build machine, and when.** Cargo: a crate with a build script or a proc-macro target runs *at compile*, any other compiled crate runs *in tests* — read from `cargo metadata` target kinds, which compiles nothing. npm: no recipe, script or workflow passes Deno's `--allow-scripts`, so install scripts never run, and the column still flags a version that has one, since the flag would make it run; every tracked Deno task runs its build tool inside the Deno build sandbox ([`build-system.md` § The Deno build sandbox](build-system.md#the-deno-build-sandbox)), so every package in a build graph runs *at build, inside that sandbox* — what the sandbox grants, and what it does not contain, is that section's.
- **Ships, and where.** Cargo: in the normal-dependency closure of which shipped binary (the nest, an app, the mail bridge's FFI library), or nothing shipped. npm: in the web app's bundle (the closure of `package.json` `dependencies`) or build-only (`devDependencies`); the site's static output.
- **Crude-but-safe checks on the source** — signals, not a review:
  - *Publisher continuity:* the new version is published by the same trusted-publishing repository, or the same publisher account, as the version it replaces. A change is a finding.
  - *Provenance:* npm's SLSA attestation (`dist.attestations`), or crates.io's trusted-publishing record (`trustpub_data`: repository and commit). Provenance the old version had and the new one lacks is a finding: it is the signature of a hijacked publish. crates.io publishes no attestation (trusted publishing there is an authentication, not a signature), so for a crate the record is checked, not verified.
  - *Size delta:* old → new unpacked size and file count (npm), crate size and line counts by language (crates.io). A patch or minor bump that grows sharply is a finding.
  - *Integrity:* the fetched artifact's hash equals the lockfile's.
  - *Mechanical pre-scan:* the deterministic, injection-immune scanner `release-integrity.md` already runs over introduced crates, run over each new artifact, npm included; verdict lines only.
  - *Vetting:* for a crate, whether a `cargo vet` import or trusted-publisher entry covers the new version.
- **Verdict per row:** `GREEN` (no finding), `FLAG` (a finding a person should look at), `RED` (a pre-scan RED, an integrity mismatch, or lost provenance) — by fixed rules in the tool, never by judgement. The report never lifts a RED: a pre-scan RED is lifted only by the review venue's ruling on its flagged lines (`release-integrity.md` § Reviewing untrusted source → *Ruling a pre-scan RED outside a review*), recorded against the exact artifact in the pre-scan ledger; the report reads that ledger and shows a RED the venue cleared on these exact bytes as cleared (a `FLAG`), never on another version or other bytes (`release-integrity.md` § Reviewing untrusted source → *The pre-scan ledger*).

**Two modes.** *Candidate:* resolve the proposed bump on a scratch copy, which fetches registry metadata only and installs nothing, and report on the diff — this is the one run before the owner decides. *Landed:* report on the lockfile diff between two refs, so the same table can be produced after the fact for any bump.

**A check that could not run is a finding, never a pass.** An artifact not fetched or not hash-checked, a pre-scan or malcontent run that did not happen, an npm signature not checked, an unknown publish date or publisher, an old version whose artifact is unavailable (so no delta exists) — each is at least `FLAG`; a report run without fetching marks every row `n/a`. Strings the report prints that came from a registry or an attestation — a repository, a commit, a signer — are printed only when they match a strict shape (owner/name, a 40-hex commit), and a signer's ref is reduced to its kind (branch, tag, commit), never its text. Artifacts come only from the two registry hosts, size-capped, and are extracted under member-count and size caps into exactly one top-level directory, which is what the scanners are pointed at (a crate's build script sits there).

**A stated limit: resolution and metadata put the new sources on disk.** `cargo metadata` and `cargo vet` download and unpack the candidate crates into Cargo's own registry cache before the owner decides. Nothing in them is executed and nothing is read by a model, but the bytes persist outside the report's temporary directory; the npm side holds its artifacts only in that directory.

**What the report is not.** It is not a review: a malicious version that passes every crude check is reported `GREEN`. What reads source is still the review venue, and what holds back unknown malice is still the minimum release age (`release-integrity.md`). The report decides nothing on its own; it is what the owner decides from.

## The two further layers (owner-ruled 2026-10-04)

- **A YARA-based behavioural scanner beside the regex pre-scan: malcontent.** Every staged artifact, old and new, is analysed in ONE run of Chainguard's malcontent container, digest-pinned, with no network, a read-only root and the artifacts mounted read-only. Only its rule identifiers and risk levels are consumed — its match strings are excerpts of the scanned files and are dropped where its output is parsed. A bump answers for the HIGH and CRITICAL behaviours its new version raises that the old version did not: a new CRITICAL is `RED`, a new HIGH is `FLAG`. Comparing behaviour sets per package, not files, is deliberate: bundlers rename their output chunks every release, so a per-file diff reports noise. Rejected alternatives: a Python scanner that had archive-extraction remote-code-execution advisories in 2026 (it unpacks exactly the attacker archives this scans), and dynamic analysis (it runs the code). **The image's publisher signature is not verified**: its signatures are in a format the GitHub CLI does not read, and the tool that does is a further install; the image is pinned by digest, which fixes the bytes but not who made them.
- **npm provenance is verified cryptographically by the GitHub CLI** (`gh attestation verify --bundle <the registry's SLSA bundle> --digest-alg sha512`) against the tarball whose hash already matched the lockfile — no new tool. The source repository the provenance claims is enforced; the workflow that signed it may live elsewhere (a reusable release workflow) and is read back from the verified certificate: same repository or same owner is unremarkable, **another owner's workflow is `FLAG`**, and so is a self-hosted runner; a signature that does not verify is `RED`. Measured 2026-10-04: with the source repository alone enforced, a same-owner reusable workflow fails verification, which is why the signer is read back rather than required. crates.io publishes no attestation, so a crate's trusted-publishing record is reported, not verified.
- **Pre-scan findings are judged as a delta too:** a finding count the old version already had is not the bump's; a new package has no old version, so its whole verdict counts.

## A round of bumps — the venue once, last (owner-ruled 2026-10-04)

**Ruling (the owner's, 2026-10-04): bumps are taken in rounds — many at a time, every ecosystem and tool together — and a round reaches the review venue at most once, at its end, as the check of last resort.** The owner's words: "There must be only one pass in the venue per round of bumps across all languages and packages. All other avenues must be tried first, all bumps seen as a collective, no separating languages or tools."

- **A round is one collective candidate.** Every pending bump — Cargo, every tracked `deno.lock`, a third-party tool, whatever else a lockfile pins — is resolved together and reported in one table, never split by language, ecosystem or tool into separate passes.
- **Every other avenue comes first.** A package that would need a read is first met by everything that does not use the venue: another version (an older fix, a later one past the minimum release age), dropping or replacing the package, the scanners and the report's crude checks, and the owner's own reading of a change small enough to read by eye. *Example, 2026-10-04:* `http-cache-semantics` 4.2.0 → 4.3.0 (4 files, +35/−12 lines; the fix for the site's last advisory, published the same day) was read by the owner from a diff of the two hash-verified tarballs, found free of injection and malware, and taken through the security-fix bypass on that reading — the venue was not used.
- **One venue pass carries what is left, whatever its language.** Every RED the round still holds, and every package nothing else could settle, goes to the venue together in a single pass at the round's end. So the venue must be able to read every ecosystem the round can carry — npm/JavaScript as well as Rust crates.
- **A round's landing includes the pre-scan ledger update** (`release-integrity.md` § Reviewing untrusted source → *The pre-scan ledger*: the session landing a dependency runs it), so the round's REDs at the exact bytes it landed are known while its venue pass is still to come. Rounds 1 and 2 (2026-10-05/06) both landed without it; run afterwards, it found nine REDs round 1's pass had never seen.
- **A RED found after its round's venue pass waits for the next round's pass (owner-ruled 2026-10-06, in a manual session, choosing "fold into round 3's pass" over a residue pass for round 1).** It is not a second pass for the closed round: it joins the single venue pass of the next round to reach its end, beside that round's own REDs. **What is given up:** the CI pre-scan stays red on `main` until that pass rules it, so anything waiting on a green pre-scan waits for the round too. **What bounds it:** the RED is never waived meanwhile — the gate keeps failing closed and re-asserts it daily (`release-integrity.md` § *The pre-scan ledger*).
- **The 2026-10-04 round is the counter-example:** it used the venue separately for one tool's crates and then for one bump's six npm REDs, while other bumps of the same round were still undecided.

The venue's own rules for how a pass is reviewed (quorum, RED rulings, delta reviews) are `release-integrity.md` § Reviewing untrusted source; this section owns only when a round goes to it.

## Who opens a round, and what lands without one — nothing (owner-ruled 2026-10-05)

**Ruling (the owner's, 2026-10-05, in two directives): there is only ever ONE bump round, it is opened only by the owner, every dependency add and bump across every ecosystem and tool is analysed and presented to the owner together in that round as one table and one decision — and no dependency add and no dependency bump lands without that analysis.** The owner's words: "what I am reacting to is the totally haphazard way I am presented with version bumps. I want there to ever only be one bump round, initiated by me, and then all bumps are analyzed and presented *in one round*. Now it seems every second session is about new dependencies." And: "expressly forbid any new dependency adds or bumps without a corresponding analysis … which looks at absolutely all effects so that the decision to bump or add dependencies can be taken in one go." The measured cause: on 2026-10-05 one queue held five rows, each produced by a separate session, each putting its own consequence table to the owner for its own approval — § A round of bumps above governed only the venue pass, and the practice around it was one row, one table and one ask per bump.

- **Two halves, two switches — the queue binds now, the merge refusal once the repository is public (owner-ruled 2026-10-05, in two steps).** The owner first scoped the whole section to the public repository, then split it the same day: a request is useless unless requests are grouped, so the grouping binds at once and only the hard refusal waits. **The queue half is in force now:** a session that meets a dependency need records a queue entry (§ *Between rounds a need is a queue entry*) and never mints a per-bump work item or puts its own consequence table to the owner; minting one is refused and the merit judge refuses one it meets (*Enforced, never trusted* (3)); the daily advisory check's red asks for queue entries. The owner may open a round at any time, and it takes every queued need at once. **The round half binds once the repository is public:** until then the merge path refuses nothing (*Enforced, never trusted* (1) is built and only notes what it would refuse), the report's candidate mode needs no round, and a bump the owner directs on their own — approving that bump's own consequence table (§ The report, run on the candidate) — may still land out of round. The minimum release age, the never-read-dependency-source rule and the owner's approval before any new version is built, run or read hold in both regimes. Two switches decide which halves the tooling enforces; the round half's is turned on in the commit that makes the repository public.
- **Only the owner opens a round.** No session, scheduled cycle, scanner red, merge gate, merit judge, advisory alert or queued task opens one. A round is recorded in `supply-chain/bump-round.toml` on the owner's in-the-moment word in chat — the same standard as the public commit message's go-ahead, never inferred from an earlier approval — and that file is what the merge path reads. One round at a time; a round closes before the next opens; its number is the round's name everywhere (the record, the commits, the queue entries it took).
- **A round is every pending need at once, presented once.** Everything the queue holds is resolved together on a scratch copy — `Cargo.lock`, every tracked `deno.lock`, Go modules, Gradle, SwiftPM, NuGet, a third-party tool or toolchain, a CI action, a container image — and reported as ONE table carrying the whole-effects analysis (§ The whole-effects analysis), presented to the owner ONCE, complete, in chat; the session then stops and waits. The owner decides every item in one reply — approve, reject, amend, or leave for the next round — and the decision is recorded verbatim beside the table in `supply-chain/rounds/round-<N>.md`. Execution then lands commits that name the round; a RED or an unsettled package goes to the venue once, at the round's end (§ A round of bumps). A need the round cannot resolve (a version under the minimum release age, a conflict) stays queued and is reported as such.
- **Between rounds a need is a queue entry — never a row, never an ask.** A session that meets a dependency need — a crate, package, module, tool, toolchain, action or image it wants added or moved, or an advisory naming a fix — records one entry in `supply-chain/bump-queue.toml`: ecosystem, package, current version, wanted version or `new`, why, who recorded it, when, and the advisory id when one names it. Then it goes on without the dependency: the dependent work is captured as a queued task that waits on the NEED — an `AFTER` item `need <ecosystem>:<package>` on the row ([`next-files.md`](next-files.md) § Kinds → *A dependency need is a prerequisite the queue resolves*), which holds while the need is queued and lapses by itself once a round has decided it, whichever way the owner decided — or built another way. It never edits a lockfile or a manifest's third-party entries, never resolves to a new version, never mints a per-bump task, and never puts a consequence table to the owner. The daily advisory check's red follows the same path — a queue entry marked advised, triaged in the janitor section — and the owner, who reads the hosting service's alerts and every halt, decides whether it opens a round. The monthly currency cycle (`release-integrity.md` § Dependency currency) surveys and queues what moves in range, which majors exist and which advisories stand; it bumps nothing.
- **What is a change.** A version added or moved in any tracked lockfile or in a manifest's third-party entries: `Cargo.lock` and every `Cargo.toml` dependency section, `deno.lock`/`deno.json`/`package.json`, `go.mod`/`go.sum`, the Gradle build files and the Gradle verification file (`verification-metadata.xml`), `Package.swift`/`Package.resolved`, the NuGet references, `rust-toolchain.toml`, the pinned actions and image digests, and the vendored forks' own lockfiles and manifests. A package LEAVING — a removal with no version added or moved, like the 2026-10-05 `ksni` codegen commit that shed nine packages — is not an add or a bump: it may land out of round and is reported after the fact in landed mode. A path or workspace crate is not third-party.
- **Enforced, never trusted.** (1) The merge path refuses a lockfile or manifest add or move while no round is open, and one whose landing commit carries no `Bump-Round: <N>` trailer. (2) The report's candidate mode runs only inside an open round; landed mode always. (3) Minting a per-bump work item anywhere but the round's own queue is refused, and the merit judge refuses one it meets. (4) The session rule stands where every session reads its rules. What of this is built: § Implementation status today.
- **Where rounds live.** One dedicated checkout of the fleet owns rounds. The between-rounds queue is the data file, deliberately not a row in a work queue: a queued task is launchable work that a session runs, a judge reads and ageing retires, while a need is not work until the owner opens a round; and a file is what both the round's candidate assembly and the merge gate read. **The round is not a node in the row graph either — a row that depends on a bump waits on the need, never on a row standing for the round (owner question 2026-10-05, ruled the same day).** The round's own row is the work of running the round once the owner has opened it, parked on their word, and nothing gates on it. Two shapes were rejected: a forever row every bump gates on (a standing row is the idle sweep's kind, judged and relaunched at every pool pass with nothing to do between rounds, and a gate on a row that never closes reads CONDITIONAL for ever, lifted only by hand), and a row minted per round ahead of the owner's word (a round that leaves a need behind would lapse that need's dependents falsely, and row numbers would be spent on rounds nobody opened). What the graph draws instead is the queue itself: the route map puts the bump queue behind every row whose `AFTER` line names a need still queued, and a closed round's record (`supply-chain/rounds/round-<N>.toml`, the needs it took as data beside the markdown) is what lapses the item — one owner per claim, nothing minted, no false MET. The queue, the round file and the records are fleet process, not product: they name development checkouts, machines and work-queue rows by design and carry the owner's words verbatim, so the publication transform withholds them — this document ships and describes the mechanism; the records stay in the development repository.
- **A security fix out of round — none: it waits for a round (owner-ruled 2026-10-05, option (a) of § Open decisions).** An advised fix is a queue entry like every other need, marked advised; the daily advisory check's janitor red and the hosting service's alerts put it before the owner, and the session that meets it always asks the owner at its halt to open a round — the owner's word still opens it. The minimum release age's security-fix bypass (`release-integrity.md` § Dependency verification) is taken only inside the round that takes the fix, under its four conditions; nothing moves out of round.

## The whole-effects analysis (owner-ruled 2026-10-05; the column set is this doc's)

**The round's table carries every effect of the whole round, so the owner decides every add and bump in one go.** Per package version, the columns of § The report, plus:

- **Compiled, or lock-only.** Whether any target of the workspace compiles the entry at all, read from the membership of `cargo tree --workspace --target all -e normal,build,dev --all-features` (and the npm closure for Deno) — never assumed from the lockfile. Membership is the union over every feature of every member, because a crate only a non-default feature pulls in is compiled by that feature's build; lock-only is left for entries no feature combination reaches, such as optional subtrees of third-party crates that no member enables. The Runs and Ships columns read `cargo metadata` under the same flag, so all three columns come from one resolve. Measured 2026-10-05 on the ratatui 0.30 candidate: 33 of 46 changed entries were never compiled, which the Runs and Ships columns, read from the lock graph alone, overstated. A lock-only entry still counts as present (it is resolvable code) and is reported as such.
- **Per-artifact reach.** Which shipped artifact's normal-dependency closure holds it: the nest, each of the 7 apps by name, the mail bridge's FFI library, the web bundle — not "an app".
- **Forced move.** Which requested bump pulled this entry along (a transitive move the owner did not ask for, such as `bitflags` under `ratatui-core`), so the table shows the asked-for set and its consequences apart.
- **Format-bearing.** Whether the package is on the tracked list `supply-chain/format-bearing.toml` — crates whose version decides an at-rest or wire format: the index engine, the serialization crates, the CBOR/DAG-CBOR codec, the SQLite bindings, the MLS stack — in which case the bump is also a compatibility question under `version-compatibility.md` and says so in the row.
- **Toolchain requirement.** The package's `rust-version` (or engine/SDK requirement) against the pinned toolchain; a requirement the pin does not meet is a finding.
- **Migration estimate.** The semver distance and the count of our own call sites (`rg` over our tree for the crate's paths), with the crates and apps that hold them — never measured by compiling the candidate, which would run its code before the decision.
- **Advisories, per round.** `cargo audit`, `deno audit` and `govulncheck` before and after the candidate: every advisory closed, every one opened, and every exception in `.cargo/audit.toml` and `supply-chain/npm-audit-exceptions.toml` the round makes stale, by id.
- **Binary size and build time — after the decision, never guessed.** No candidate can measure them without building the new code, so the round's table marks them *measured after the decision*, and the landed-mode report on the round's first build fills them in the round record.

## Open decisions

- **Who signs off a report — RESOLVED 2026-10-05 by § Who opens a round:** the owner, once per round, every item in one reply; an all-`GREEN` table proceeds no more on its own than any other, because the round is the owner's decision, not the report's.
- **A security fix out of round — RESOLVED 2026-10-05, option (a):** put to the owner with round 1's table; their reply "Your recommendations for all" took the recommendation — an advised fix waits for a round the owner opens, with the session's ask at its halt always made (§ Who opens a round, last bullet). Options (b), a one-item round asked for at a halt, is subsumed (the ask is always made; the owner opens a round of any size), and (c), the pre-ruling bypass with no round, is retired.
- **Pinned hashes for the app package managers — RULED by the owner 2026-10-05, in a manual session (verbatim: "1 yes, 2 no").** (1) *Gradle — yes:* the Android app commits a Gradle dependency-verification file (`apps/fauna-android/gradle/verification-metadata.xml`, a SHA-256 per artifact, transitive ones included), and the report checks a Gradle artifact against it before the repository's own checksum. Committing it pins every version restored that day, so it lands only inside a round, as that round's item, never out of round. (2) *SwiftPM — no:* the report does not fetch a SwiftPM pin's revision. github.com is not added as an allowed host, and a SwiftPM row stays unfetched, a finding (§ Implementation status today).
- **Where it runs besides on demand** — wiring it into the scheduled supply-chain workflow on every lockfile change is not built.
