# Dependency bump report — the consequences of a version bump, before its code runs — target state

Owns: dependency-bump-report, bump-round, bump-queue, whole-effects-analysis, dependency-review-rule, dependency-step-log
Status: ratified — the rule, the report's shape and its two further layers owner-ruled 2026-10-04; built the same day (§ Implementation status today); the owner-opened round, the between-rounds queue and the whole-effects analysis owner-ruled 2026-10-05 and built the same day, the round half in force since the repository went public, switched on 2026-10-14 (§ Who opens a round); the out-of-round security fix ruled 2026-10-05: it waits for a round (§ Who opens a round); the quiet round and the guided round owner-ruled and built 2026-11-10, the Security page's per-item approval ruled, built and withdrawn the same day (§ Who opens a round → *The quiet round*, *The guided round*; § Implementation status today)
Authority: owns what is known about a dependency version bump BEFORE any of the new versions is installed, built, run or read — which new code would run on the build machine and when, which would ship and where, and which crude-but-safe checks its source passed. Neighbours that do **not** own this: [`release-integrity.md`](release-integrity.md) owns dependency verification as a whole — the scanners, the minimum release age, the dependency review sandbox, the exception lists; this doc is one step inside that, run per bump.

## Goal

**Ruling (the owner's, 2026-10-04): before a version bump's code runs on a build machine or is read, the bump's consequences are laid out in one table, produced by a tool, for every bump.** A lockfile bump is new third-party code arriving in three places at once: on the machine that builds it, in what it builds, and in the context of whoever reads it. The scanners in `release-integrity.md` answer whether a known advisory matches a version; none of them answers what the bump *does* — whether the new code runs at compile time, under a build tool and with what permissions, or only in a test; whether it ships to users; and whether anything checkable vouches for where its bytes came from. Without the table that question is answered by intuition, one bump at a time, and there will be many bumps.

## No new software without a review — and every step by a tool that logs it (owner-ruled 2026-11-10)

**Ruling (the owner's, 2026-11-10, iron-clad): no new software reaches a dev machine or the product without a review, the review is run by tools and never by hand, and the tools log every step.** The owner's words, in a guided round whose table had offered "take" on adds no report had covered: "this should *never* happen. You should not do it and you should not allow me to do it. Any new dependency brought in by a 'tree' is a new dependency, and needs to go through vetting, security vulnerability scanning, the lot." Then: "We should mandate tools for working with any dependency, and mandate that the tool check the whole tree, in detail. … The iron-clad rule: No new dependency (including version bumps and transitive dependency trees, as well as tools - in short any new software running on the dev machines or anywhere in the product, including the web page) is allowed without a review process. This review process should include at least a) a security vulnerability check from reputable sources, as many as possible, b) an age >= 7 days (can be overruled by the user's word), c) if a) is unclear, a code reading in the dependency review sandbox." And the order of work: "So the first step is to mandate tools for evertything, which will log all the steps we take for later review, then make sure those tools live up to the iron-clad rule."

- **What it covers — every piece of third-party software, by any road.** A package added, a version moved, and EVERY package either pulls in: a package a tree brings is a new dependency like one asked for by name, with a row and a review of its own (this answers the question § Who opens a round → *The quiet round* (4) left open: a transitively added package is a new library). Every ecosystem a lockfile or manifest pins; every tool, toolchain, CI action and container image; an operating-system package; and anything the product loads at run time, a script or font a public page fetches included.
- **The review, per package of the whole tree.** **(a)** known vulnerabilities, from every reputable source the ecosystem has (the advisory scanners of [`release-integrity.md`](release-integrity.md) § Dependency verification, the hosting service's alerts, the vendor's security notices for an operating-system package); **(b)** published at least 7 days ago, overruled only by the owner's word naming that package (`release-integrity.md` § Minimum release age — the security-fix bypass); **(c)** a reading in the dependency review sandbox when the checks leave a question (§ A round of bumps). **Four more, proposed by the session that took the ruling and put to the owner in the same exchange — the owner ruled on the two questions asked beside them and struck none:** **(d)** malice is not a vulnerability, so the takeover and malware signals of § The report count as (a) does — a publisher or source repository changed, an install script or native binary added, sharp size growth, the malware-behaviour scan, the injection pre-scan — and any `RED`, or any such signal no other avenue settles, goes to the dependency review sandbox, not only an unclear advisory result; **(e)** a check that could not run is a finding and never a pass (§ The report); **(f)** the reviewed bytes are the bytes that run: an exact version and checksum pinned, and the landing compared with the reviewed table package by package; **(g)** nothing new is built, installed or run before the decision — resolving a lockfile is the only step taken on a candidate.
- **An operating-system package (owner-ruled 2026-11-10, "1 yes"):** its review is the machine's signed vendor repository as the channel, the vendor's security notices as (a), and the owner's approval of that install — no 7-day age and no dependency review sandbox, since it has no publish age that means anything and its source is not practical to read.
- **The quiet round stands (owner-ruled 2026-11-10, "2 yes"):** it runs this same review on every row and takes no new package, no flag outside its allow-list and nothing under 7 days; what is absent is only the owner's click.
- **Every step is a tool's, and the tool logs it.** Recording a need, opening a round, resolving a candidate, reporting it, presenting, deciding, backing a move out, landing, closing, and installing a tool are each one verb of the round tool; none is done by a hand-typed resolver or installer command, and a session's hand-typed one is refused. Each verb appends one line to the round's step log: when, which checkout and machine, the verb and its typed arguments, the exact command it ran and its exit code, each touched lockfile's hash before and after, the package moves read from the lockfile itself, and the outcome — a refusal included, with its reason. The log holds typed fields only: what a resolver, registry or build printed is third-party text and stays out of it (kept beside it, untracked, under its hash). The log is the round's record for a later review: what was done, in order, by whom, and what each step changed.
- **The tool refuses what the rule forbids.** A decision to take a need is refused unless the round's own stored report holds a row for every package the need's resolution moved or added, at that version; the merge path refuses a landing that moves or adds a package the decided table did not hold at that exact version. A recommendation, a summary or a queue entry's reason is never what a decision rests on.
- **A package a taken need's resolve moved is that need's consequence — whether or not the queue also holds a need for it (owner-ruled 2026-11-11, in guided round 22).** The report attributes a row to its own need when the queue holds one for the package (`requested`) and to the forcing need otherwise (`forced by …`); the monthly survey queues a need for every package with a newer version in range, so the 26 packages that move with `wasmtime` each read `requested`, and the merge path refused the landing of a take the owner had made with all 27 rows before them. The owner: "if a need is a need because of a need the round took, does that need not also belong to the round?" It does. The merge path counts a moved package's row under its own need, the forcing need, and every need whose standing resolve step in the round's log moved the package to that exact version; the close takes the queued need of such a package with the need that moved it, since it landed. Unchanged: the package still needs its own report row at that exact version, a step a backout voided or that failed serves nothing, and a package no taken need's step moved is refused.
- **A take nothing landed stays queued (2026-11-12, round 26's `cargo:ring`).** Round 26's report listed `cargo ring` under "requested, NOT moved by this candidate (stays queued unless resolved)": a feature-only need (the same version, a feature to enable), which a lockfile candidate cannot move. Its digest still read it `takeable`, on the rows four tools' own trees held for `ring`. The close then dropped it as taken although the landing wrote no manifest line, so the feature stayed off until a merit judge found it a day later. Two rules follow. First, a row of a tool's own tree (the lock a tool's crate publishes) belongs to that tool, never to a workspace need of the same name, so a need whose resolve moved nothing and wrote nothing reads `nothing moved` and cannot be taken. Second, `bump-round close` takes a decided take only if something landed it: one of the round's successful resolve steps moved its package or wrote a manifest for it, a successful `installed` step ran for it, or a commit landed under the round's `Bump-Round:` trailer changed a manifest or pin line naming it (a lockfile line never counts, because a lock line naming a package is often another package's dependency list). Any other take goes back to the queue carrying the outcome `taken but not landed`, and the round's record lists it under its own heading. A feature-only need is therefore landed by the round's own manifest edit under the trailer, which the close verifies. A need decided without being taken (`--took` alone) lands nothing by design and is not checked.
- **Tools are reported like packages.** A third-party tool, toolchain, action or image has a report of its own kind — version, checksum, source channel, advisories, age — and is undecidable in a round without it. The report's design: § The report → *The tool report*.

**Running the same bytes again is not this rule's question.** Bytes an approval already let run on a machine may run there again without a second ask, by hash, under the conditions [`release-integrity.md`](release-integrity.md) § The re-run grant owns (owner-ruled 2026-11-10; built 2026-11-11).

## The report

**One row per package version the bump adds or changes**, for every tracked `Cargo.lock` — the workspace's and each vendored fork's own standalone lock — and every tracked `deno.lock` (each found from the index, like the npm audit). Every column is computed from lockfiles, manifests, registry metadata and scanner verdicts; none needs a model to read dependency source, and none runs dependency code.

- **Identity:** ecosystem, package, old version → new version (or *new*), the new version's publish age, and whether the change came in through the security-fix bypass of the minimum release age.
- **Runs on the build machine, and when.** Cargo: a crate with a build script or a proc-macro target runs *at compile*, any other compiled crate runs *in tests* — read from `cargo metadata` target kinds, which compiles nothing. npm: no recipe, script or workflow passes Deno's `--allow-scripts`, so install scripts never run, and the column still flags a version that has one, since the flag would make it run; every tracked Deno task runs its build tool inside the Deno build sandbox ([`build-system.md` § The Deno build sandbox](build-system.md#the-deno-build-sandbox)), so every package in a build graph runs *at build, inside that sandbox* — what the sandbox grants, and what it does not contain, is that section's.
- **Ships, and where.** Cargo: in the normal-dependency closure of which shipped binary (the nest, an app, the mail bridge's FFI library), or nothing shipped. npm: in the web app's bundle (the closure of `package.json` `dependencies`) or build-only (`devDependencies`); the site's static output.
- **Crude-but-safe checks on the source** — signals, not a review:
  - *Publisher continuity:* the new version is published by the same trusted-publishing repository, or the same publisher account, as the version it replaces. A change is a finding.
  - *Provenance:* npm's SLSA attestation (`dist.attestations`), or crates.io's trusted-publishing record (`trustpub_data`: repository and commit). Provenance the old version had and the new one lacks is a finding: it is the signature of a hijacked publish. crates.io publishes no attestation (trusted publishing there is an authentication, not a signature), so for a crate the record is checked, not verified.
  - *Size delta:* old → new unpacked size and file count (npm), crate size and line counts by language (crates.io). A patch or minor bump that grows sharply is a finding.
  - *Integrity:* the fetched artifact's hash equals the lockfile's.
  - *Mechanical pre-scan:* the deterministic, injection-immune scanner `release-integrity.md` already runs over introduced crates, run over each new artifact, npm included; verdict lines only.
  - *Vetting:* for a crate, whether a `cargo vet` import or trusted-publisher entry covers the new version.
- **Verdict per row:** `GREEN` (no finding), `FLAG` (a finding a person should look at), `RED` (a pre-scan RED, an integrity mismatch, or lost provenance) — by fixed rules in the tool, never by judgement. The report never lifts a RED: a pre-scan RED is lifted only by the dependency review sandbox's ruling on its flagged lines (`release-integrity.md` § Reviewing untrusted source → *Ruling a pre-scan RED outside a review*), recorded against the exact artifact in the pre-scan ledger; the report reads that ledger and shows a RED the dependency review sandbox cleared on these exact bytes as cleared (a `FLAG`), never on another version or other bytes (`release-integrity.md` § Reviewing untrusted source → *The pre-scan ledger*). **A pre-scan RED on the new version is a `RED` row whatever the old version carried (owner-ruled 2026-11-11):** a bump answers for what it added in every other pre-scan category, but a RED the old version also had is unruled on the new bytes until the ledger clears exactly those — reason `pre-scan RED, no disposition for these bytes` — so the verdict column alone tells a reader, and the quiet round's fixed rule, that the dependency review sandbox is owed (round 22's table carried one such row as `GREEN` over a pre-scan cell `RED → RED`).

**Two modes.** *Candidate:* resolve the proposed bump on a scratch copy, which fetches registry metadata only and installs nothing, and report on the diff — this is the one run before the owner decides. *Landed:* report on the lockfile diff between two refs, so the same table can be produced after the fact for any bump.

**A check that could not run is a finding, never a pass.** An artifact not fetched or not hash-checked, a pre-scan or malcontent run that did not happen, an npm signature not checked, an unknown publish date or publisher, an old version whose artifact is unavailable (so no delta exists) — each is at least `FLAG`; a report run without fetching marks every row `n/a`. Strings the report prints that came from a registry or an attestation — a repository, a commit, a signer — are printed only when they match a strict shape (owner/name, a 40-hex commit), and a signer's ref is reduced to its kind (branch, tag, commit), never its text. Artifacts come only from the two registry hosts, size-capped, and are extracted under member-count and size caps into exactly one top-level directory, which is what the scanners are pointed at (a crate's build script sits there).

**A stated limit: resolution and metadata put the new sources on disk.** `cargo metadata` and `cargo vet` download and unpack the candidate crates into Cargo's own registry cache before the owner decides. Nothing in them is executed and nothing is read by a model, but the bytes persist outside the report's temporary directory; the npm side holds its artifacts only in that directory.

**What the report is not.** It is not a review: a malicious version that passes every crude check is reported `GREEN`. What reads source is still the dependency review sandbox, and what holds back unknown malice is still the minimum release age (`release-integrity.md`). The report decides nothing on its own; it is what the owner decides from.

### The tool report — a tool and an operating-system package (designed 2026-11-10)

**A tool has no lockfile, so its candidate is a logged step and its report is read from the channel that would deliver it.** This is the report § No new software without a review owes a tool before it can be decided; the design is the session's under that ruling, and what it decided where the ruling is silent is listed at the end, refutable. What of it is built: § Implementation status today.

- **A tool need names the tool and the machine: `tool:<name>@<machine>`.** The name is the dev-tool inventory's ([`dependency-advisories.md`](dependency-advisories.md) § Dependency verification → *Dev tools: the inventory and its daily check*); the machine is a dev machine, or `ci` for a tool a tracked workflow installs on a runner. One need is one tool on one machine, since the installed version, the channel and the install are each per machine. A tool need that names no machine gets a row with verdict `n/a` and the reason `names no machine`, and is never takeable.
- **The candidate is made by `resolve`, which installs nothing and downloads nothing.** For a tool need the step records the target version in the round's step log, and that step IS the candidate: the report reads, per tool need, the round's newest successful `resolve` step, and a tool need with none has no row. An exact version is mandatory (`--precise`) for every channel but the operating system's, where the target is whatever the machine's signed package index offers: there the step runs two read-only commands on the machine itself — the index's policy for the package and a SIMULATED install — and logs, as the step's moves, every package the simulation says would be installed or upgraded, each from its installed version to its candidate. Both commands are logged with their exit codes like every resolver command.
- **One row per piece of software the install would put on the machine**, in the round's one table and its stored report, ecosystem `tool`. Columns: the name and machine; the version installed today → the target (or *new*); the channel, as one of the typed kinds below; the checksum or signature that channel gives for the target; its publish date and age where the channel has one; the advisories open against the TARGET version, with those the move closes; publisher or source-repository continuity where the channel exposes it; requested, or forced by which requested tool; and the verdict with every reason. The version installed today is read as the daily tool check reads it — on this machine from the tool itself, on another from the versions that machine reported through the fleet — and a tool the inventory lists that could not be read is a finding.
- **What each channel gives — the typed source an inventory entry carries.**
  - *The operating system's signed repository* (an operating-system package): the candidate version and its origin from the machine's package index, the SHA-256 that index records for the package file (the index is what the vendor signed), no publish date. An origin that is not the distribution's own archive — a third-party repository — is `RED`: it is not the channel the ruling names. An index last refreshed more than a day ago is a finding, since refreshing it is a privileged step the report never takes.
  - *A release archive on the hosting service* (a vendor's prebuilt binary, a vendor installer that fetches one): the release's publish date and the named asset's SHA-256 digest from the hosting service's API, the fourth allowed host, read field by field; an asset the API gives no digest for is a finding.
  - *winget* (a Windows tool installed from the community package repository; owner-directed 2026-11-11 in guided round 24 — "take the time to fetch date and checksum by reputable means … this will be useful for the next 1000 bump rounds" — and built the same day): the installer manifest that repository holds for the exact version, read through the hosting service's API, typed fields only — every SHA-256 it gives for the machine's architecture (what winget itself checks the download against), and for the date the manifest's LAST commit, so a hash edited after publication makes the version young again. A manifest that is missing, names another package or version, or gives no hash for the architecture is a finding. An entry that also names the vendor's own release asset is checked against it: a vendor digest that is none of the manifest's hashes is `RED`. A package the manifest lists as a dependency is software the install may bring: the row names it and reads `tree not read` (verdict `n/a`) — unless the dependency is itself a winget tool the inventory lists for the SAME machine, which is software that machine already holds and the daily tool check watches, so the row names it as covered (owner-ruled 2026-11-11 in guided round 24, on the Visual C++ runtime `uv`'s manifest depends on: asked whether to approve it by word, inventory it, or avoid it, the owner chose "A", the inventory).
  - *Go's own archive* (`vendor archive (go.dev)`; the source kind `go-archive`, built 2026-11-11): the SHA-256 the vendor's download index (`go.dev/dl/?mode=json`, one more allowed host, JSON only) lists for the exact file the entry names, and for the date the release tag `go<version>` of `golang/go` on the hosting service — an annotated tag's own date, else the tagged commit's — because the index carries no date and the project publishes no hosting-service releases; a file the index does not list, or a tag the service does not hold, is a finding (`checksum unknown`, `publish date unknown`), never a guess.
  - *Channels with no machine-readable record stay `other`*: Apple's own tools and updates (Command Line Tools, Xcode, macOS updates, the system `git`/`curl`/`jq`), Windows Update's programs, and Google's Android command-line tools publish no per-version checksum or date a reader can fetch, and the static build on Linux names no hosting record; a winget entry whose tool reports a version that is not the manifest's `PackageVersion` (Git for Windows, the Build Tools), or whose reported version is another project's (llvm-mingw reports the clang it bundles, not its release tag; the .NET SDK is read as the newest 10.x runtime), is typed `other` until a reading exists that maps one to the other.
  - *PyPI:* the version's upload time, yanked flag and per-file SHA-256 from the index's JSON record (one more allowed host), typed fields only; a yanked version is `RED`.
  - *crates.io* (a helper built by `cargo install`): what a crate row already reads — the publish date, the checksum, the publisher account and the trusted-publishing record, compared with the installed version's for continuity.
  - *Anything else* (a vendor's own download site, a store): nothing machine-readable, so the checksum and the publish date are `unknown` — findings — unless the need's resolution names the SHA-256 the vendor publishes (`--sha256`), which the row then carries as `stated by the vendor, not verified`.
- **The tree: a tool whose install brings other software has a row for each piece, or it is not takeable.** An operating-system package's tree is the simulated install's set. A `cargo install` builds the crate's whole dependency tree on the machine: its rows are the packages of the `Cargo.lock` the crate itself publishes, read from the hash-checked crate file, reported as Cargo rows under the tool's name, and the install is `--locked`; a crate that publishes no lockfile cannot be reviewed as a tool. A PyPI tool with requirements is installed only from a hash-pinned requirements lock the `resolve` step writes under the 7-day age, one row per entry; the lock is the need's — one per tool and machine, compiled for that machine's platform and the repository's pinned Python (a requirement only Windows takes is in the Windows lock and no other), never one universal lock per tool, since the needs of one tool on three machines are decided apart and may sit at different versions; a PyPI tool's baseline, which installs nothing, has its installed environment for its tree (§ *Where the ruling was silent*, item (1)). A prebuilt archive is one artifact and one row: what it bundles is not enumerable and is named under what is not checked. Until a channel's tree is read, a tool of that channel gets its own row with the reason `tree not read` and verdict `n/a`.
- **Advisories are asked about the target version, by the inventory's identities.** The same identities and the same source the daily tool check uses, asked at the target version instead of the installed one, graded against the same exception list. An unexcepted advisory open at the target is `RED`; for an operating-system package the daily check's vendor-fix rule holds — an id the vendor has published no fix for is counted, not a finding, and an id fixed in a version later than the candidate is a finding. A new tool has no inventory entry yet, so the entry is written in the round, before the report, carrying its identities and marked as awaiting its install; a tool with no identity any source knows is a finding at every report as it is at every scan.
- **Verdict, by fixed rule.** `GREEN` no finding; `FLAG` a finding; `RED` an open advisory at the target, a yanked version, a non-vendor operating-system origin, a publisher change on crates.io with lost trusted publishing; `n/a` when the advisory check did not run, the tree was not read or the need names no machine. A tool row is always the owner's — no quiet round takes one (§ Who opens a round → *The quiet round*) — and a take is refused on a row whose verdict is `n/a`: for a tool the advisory check and the tree are the whole of the review, so a review that did not run is no review.
- **An operating-system package is the same row with three differences (the 2026-11-10 ruling's "1 yes").** No age column and no age finding; the vendor's notices as the advisory source; and never the dependency review sandbox — a `RED` operating-system row is not carried to the round's dependency review sandbox pass (§ A round of bumps), it is simply not installed. The owner's approval of that install is the round's decision taking the need.
- **The rows are rows of the round's stored report, so nothing has a second path.** `decide --take tool:<name>@<machine>` is checked as every take is: the stored report must hold the need's row and a row for every move of its `resolve` step at that exact version, and the report must be newer than that step — the tool's equivalent of *a lockfile moved after the report*. An unreported tool need is refused as before.
- **The install is the fleet's to carry out once the owner has approved it (owner-directed 2026-11-13; designed, the install step built and off until ratified); `installed` is the logged step that records it.** Who carries an approved install out, how its bytes are held to the row and what a failure leaves is § *Carrying out an approved bump*, below. Until the built step is switched on (the rule is ratified, 2026-11-14), the owner installs the tool on the machine after the decision (a command the round's session hands over with the decided version and checksum, never runs). Then `bump-round installed --need tool:<name>@<machine> --version <v>`, run ON that machine, reads the installed version as the daily check does, and requires three things: the need is one its round took, `<v>` is the version the round's row decided, and the version read equals it. A match logs the step and writes the reviewed version into the tool's inventory entry, clearing its awaiting mark; a mismatch logs the step as refused, with both versions, and writes nothing. With `--artifact <file>` it also hashes the downloaded file against the row's checksum before the owner installs from it, and logs which was checked; without it the step logs `artifact not checked`. The verb installs nothing, and a round may close before it runs: the step is appended to that round's log whenever the install happens, and the daily check prints every entry still awaiting its install.
- **The reviewed version is held, and drift from it is a finding.** Once an entry carries a reviewed version, the daily tool check compares it with the installed one and reports a difference: the bytes that run are no longer the bytes that were reviewed (the ruling's (f)). An operating-system package is exempt — its vendor's signed updates are the channel working, and being behind them is already the finding.
- **A tool a workflow installs on a runner (`@ci`) is a pin.** Its version is read from the tracked line that pins it, never from a runner; a line that names no exact version is itself the finding its need exists to fix. Its `resolve` step writes that one line, its row is this row, the landing commit is the install — there is no `installed` step — and the merge path checks the line's version against the decided row.
- **Toolchain, action and image pins keep their own rows** (§ Implementation status today, *Toolchain, action and image pins*): identity, reach, runs, age where a source dates it. What this design adds for them is the merge path's check — a commit that moves a pin is refused unless its round's stored report holds that pin's row at that exact value for a need the round took — and an advisory cell where the inventory gives the pinned thing an identity.
- **What is NOT checked, said on the row.** No source is read: a tool's source, like any dependency's, is read only in the dependency review sandbox. The contents of a prebuilt archive are not enumerated, so what it bundles has no rows. A checksum the channel publishes proves what the channel serves, not who built it; a signature is recorded where the channel's own installer verifies one (the operating system's) and is otherwise `not verified`. The bytes on the machine after an install are not hashed against the row — the version is compared, and the downloaded file only when it is given.
- **Where the ruling was silent — two items owner-ruled 2026-11-10, one the session's.** (1) **A baseline (owner-ruled 2026-11-10, "1 baseline"):** every tool installed before the ruling — each entry of the tool inventory on the three dev machines — goes through the tool review once that review is built, in one sitting the owner decides as one table: its channel, checksum, age and advisories read at the version installed today, and that version recorded as the entry's reviewed version, so drift from it is a finding from then on (*The reviewed version is held*, above); until its baseline row is decided, the daily advisory check is what reads an entry. A baseline is one queued tool need per inventory entry, spelled `tool <name>@<machine> --current installed --wanted baseline` (the queue refuses either word without the other, on any other ecosystem, or for a name and machine the inventory has no entry for); its `resolve` runs on the entry's machine, reads the installed version as the daily check reads it (an `@ci` pin from its tracked line), takes no `--precise`, installs, downloads and simulates nothing, and logs that version as the one move, to itself; an entry with no version reading (no `apt`, `pin_file` or `version_cmd`) is refused there, so every entry carries one — an `unscanned` entry too, which the daily check then reads and holds to its reviewed version though it asks no advisory source; an operating-system package's step also logs the installed binary package's version and the archive the index still serves it from, an origin no longer read being a finding rather than a third-party archive; a `cargo install` tool's baseline reviews every package of the lockfile its installed version publishes; a PyPI tool's baseline reviews every package of the environment its program is installed in — the whole environment, since all of it is importable when the tool runs — read by one read-only command, `uv pip freeze` against that environment's interpreter (the program's sibling `python`; an entry whose `version_cmd` names no absolute program path names no environment and is refused), each package a row at the version installed, the step failing when the environment's copy of the tool is not the version read, and an installed entry that is no PyPI version (a local or editable install) having no row, a finding on the tool's row — no lock is written and the venv is never aligned to one; and the every-package sweep (`apt_all`) takes no baseline at all — its packages move by the distribution's own updates outside the round (item 2), each graded daily on its vendor's fix, and the queue refuses one; the owner decides it in the round's table like any tool row, and its `installed` step — nothing is installed, the version read must still be the decided one — writes that version as the entry's `reviewed`. An entry that already has a version-moving need queued takes no baseline: the queue holds one need per tool and machine, and that need's own `installed` step writes `reviewed`. (2) **Self-applied operating-system updates stay outside the round (owner-ruled 2026-11-10, "2 confirm"):** the distribution's unattended security updates and the macOS and Windows system updaters arrive on the signed vendor channel the ruling names as an operating-system package's review, and the daily check reads the result; holding them for a decision would delay security fixes. (3) A new advisory-source or registry host is added to the report's allowed hosts by the change that needs it, as the earlier ones were — the session's default, refutable.

### Carrying out an approved bump — the fleet installs it, on every machine it names (owner-directed 2026-11-13; designed the same day)

**The owner's approval of a tool or toolchain bump makes the fleet carry it out; nobody installs by hand, and nobody notices a machine left behind.** The owner's directive of 2026-11-13, as the release session that received it recorded it: "design automated toolchain bumps on all machines — an approval from the owner causes the fleet to actually bump the tool on macOS, Windows or Linux; for `uv` on Windows this requires draining the machine first". It changes who carries out an approval, never who gives one: every tool row is still the owner's (§ *The tool report*, the verdict bullet), the review rule of 2026-11-10 is untouched, and nothing here lets a session type an installer. What the 0.1.7 attempt met, which this design answers: a Go patch release was a hand diff over five files plus three hand installs; the queue held per-machine tool needs that nobody carried out after their approval; and replacing `uv` on Windows under running sessions fails or corrupts them. The design is the session's under that directive, its choices listed at the end, refutable. What of it is built: § Implementation status today.

- **The unit of approval stays one tool on one machine; a toolchain is one need for the whole fleet.** A tool need is `tool:<name>@<machine>` and its row is the tool report's row, unchanged: the version installed → the target, the typed channel, the checksum that channel gives for THIS machine's artifact, its date and age, the advisories open at the target and those the move closes. The table prints the needs of one tool on several machines together under the tool's name, with one line saying whether the targets agree, and `decide --take tool:<name>@*` takes every one of them whose row is takeable. A **toolchain** — a tool whose version a tracked file pins — is one need, `toolchain:<name>`, and its approval covers three things at once: the lockstep set (below), and the install on every machine whose inventory entry names that pin (`pin = "toolchain:<name>"`). Its `resolve` step logs one move per such entry, the report gives each a tool row reading `forced by need toolchain:<name>`, and the take is refused while any of them is `RED` or `n/a`, as for any forced row. So the owner never approves a pin whose installs were not on the table.
- **The carrier is the install step: a verb of the round tool, run on the machine by its fleet agent on the broker's call, with no session in it.** `bump-round install --need tool:<name>@<machine>` runs ON the machine. The broker asks the machine's agent for it (the agent action `install`, carrying the round and the need and nothing else); the step itself reads everything it acts on — the version, the channel, the checksum, that the round took the need, that no retraction stands — from the round's record and stored report at `origin/main`. So the message that starts an install can name only an install the owner has already approved, and a session, a queue row's text or a model's reading is never between the approval and the bytes. The broker's trigger is the tracked state itself: an inventory entry marked `awaiting = "round <N>"` whose need round N took and whose `installed` step is not logged is owed an install, read every janitor period; the trigger is the decision's landing, never a row a session must pick up. A tool on `ci` has no install step (its landing commit is the install, as before).
- **What the step runs: the channel's own installer at the exact decided version, or a download it checks itself — one typed recipe per channel kind, in code.** *A release archive or the vendor's archive* (`github-release`, `go-archive`): the step downloads the entry's named asset into a scratch directory, hashes it, and unpacks it BESIDE the installed copy only when the SHA-256 equals the row's; the swap into place is one rename where the install is one file or one directory. *winget*: `winget install --id <id> --version <v> --exact`, winget checking the download against the manifest hash the row carries; the step first reads the manifest hash again and refuses when it is no longer the row's. *crates.io*: `cargo install --locked <name>@<v>`, under a `build` slot. *PyPI*: `uv pip install --require-hashes -r <the need's lock>`. *A toolchain its manager installs from the pin* (the Rust toolchain through `rustup`, CPython through `uv`): the manager's own install of the pinned version, run by the step so it is logged and happens once, quietly, instead of inside whichever build first meets the new pin. A channel with no checksum the step can hold the bytes to (`other`, a vendor checksum only `stated`) is never carried out by the fleet: it stays the owner's step, as below.
- **The permission to run is the run-ledger entry the approval seeded; the step asks the ledger, never its own judgment.** A round's decision on a tool row seeds the entry for that row's checksum on its machine ([`release-integrity.md`](release-integrity.md) § Dependency verification → *The re-run grant*, *Seeding at approval*), with the install profile the recipe declares for its channel kind (network on for the fetch alone, the tool's own install paths writable, no secret, no sudo). The step hashes what it fetched and asks the ledger for that hash under that profile before anything runs; a hash the ledger does not hold, a retraction or a wider profile refuses the step. Its first run writes the machine's journal line, and the step is logged in the round's step log with every command, exit code and hash, as every verb's is.
- **The record is written by the broker from its own tree.** The machine's step reports typed facts — the need, the version read after the install, the artifact's hash, each command's exit code — and the broker's checkout writes the `installed` step line and the entry's `reviewed` version and lands them, as it writes claim lines; no machine commits from an agent. `bump-round installed` stays as the same check by hand, for an install the owner ran.
- **Installs first, pins after: a toolchain's lockstep commit lands once every machine that holds the toolchain reads the target.** A newer tool builds an older pin, and an older tool under a newer pin either fails every build on that machine or sends the toolchain's manager to fetch it mid-build; so the order is decision → installs → the lockstep commit. The round's session lands the commit when the per-machine reading (below) shows the target on each machine the need's rows name, and the merge path refuses it sooner. A machine whose agent is not reporting (down, being rebuilt) does not hold the landing — nothing builds there — and its install is the first thing its agent is asked for on its return, under a hold with the cause `install`, before any launch. A machine that is up and whose install failed does hold it, and is red (below). A toolchain its manager installs from the pin lands at once with the decision's commit, the step then materializing it on each machine.
- **The lockstep set: every tracked line that pins one toolchain is written by ONE `resolve` step and held together by a parity gate, so a partial bump cannot land.** Go is the built reference: the `toolchain` line of each `go.mod`, the builder image's tag and digest, the vetted-image table's entry and the docs naming the release, written by the one `toolchain:go` step and held by the Go gate. Every other toolchain gets the same two things, its set declared once in code (one table the resolve step, the gate and the report all read). The sets as measured by search of the tree on 2026-11-13: **Rust** — `rust-toolchain.toml`'s channel and the build-system doc's line naming the pin (no image stage or workflow names the nightly: the image's rustup and every workflow read the toolchain file, and the workflows' `dtolnay/rust-toolchain@stable` is a different, floating toolchain with its own queued need); **CPython** — `.python-version`, the tier-4 workflow's `--python`, the public CI's note on the pin, and the Linux host, macOS, Windows and Windows-runner setup steps; **the .NET SDK** — `global.json` and the public release workflows' exact `setup-dotnet` input; **`uv` on the CI runners** — `scripts/install-uv.sh`'s version and its installer checksum (the dev machines' `uv` is installed per machine, not pinned by any tracked line); **Gradle** — the wrapper's distribution line and its checksum; **the JDK** — the Android build files' Java level, every `JAVA_HOME` default (justfile, scripts), the apt package and the setup docs; **the Android platform** — the build files' `compileSdk` and the setup docs' SDK package; **the Android build tools** and **the NDK** — the setup docs alone, since no build file names them. **Deno and `just` have no set: no tracked line pins either** — every workflow's setup input floats (`deno-version: v2.x`, `setup-just` with no version) and every machine's install is its own; each one's queued setup-version need writes the first exact line, which joins its set in the same change. A set's members exclude, by rule, prose naming a pin's history, a public text naming a toolchain (it moves through the public-texts process), the fleet's own session rules, a floating setup input and an image pin (the image ecosystem's, save Go's builder image). A set holding a checksum line (Gradle's, `uv`'s) is resolved with `--sha256`, the line written from it. A toolchain whose set is not declared is refused by `resolve` as not built, as today. The parity gate is one cheap parse-only gate over the table (the Go gate generalised), on the merge path.
- **An install that needs the machine quiet is carried out under a drain the broker puts itself.** An inventory entry says whether its install may run under live sessions: `install = "live"` or `"quiet"`. The defaults follow what the operating system allows — on Windows a running program's file cannot be replaced, so every entry there is `quiet` unless marked `live`; on Linux and macOS a one-rename swap is `live`, and an install that rewrites a tree in place (a virtual environment's packages, an SDK directory) is `quiet`. The first case is `uv` on Windows, which every recipe runs. For a machine with quiet installs owed, the broker puts the drain's hold with the cause `install` ([`fleet-launch-and-halt.md`](fleet-launch-and-halt.md) § The launch and the halt → *A drain is a hold* owns the hold, the deadline and DRAINED), on the approval's standing as its word; all of a machine's quiet installs go in one drain, and one machine is drained for installs at a time, so the fleet keeps working. Past DRAINED the step also waits for what a drain leaves alone — a manual session and a detached run are never stopped for an install; while one runs a program of the tool, the reading says who holds it — then installs, verifies, and the broker lifts the hold. A release attempt in flight is treated as its parts are: its unattended sessions get the deadline like any other and resume from their captured state, a detached step of it is waited for, and the attempt is neither ended nor failed by the drain; a release round's own tool bump is that same drain, asked for by the attempt that needs it.
- **What needs a privilege stays the owner's own step, asked once with the exact command.** An entry whose install needs `sudo` or an elevated shell (`privilege = "sudo"` or `"admin"`: an operating-system package on Linux, a machine-wide installer on Windows), one Apple or Microsoft delivers through its own updater, and one whose channel gives the step no checksum, is not carried out by the fleet. The decision puts ONE item on the daily asks per machine, holding every such install of the round as one paste-safe block with the decided versions; the owner runs it; the agent's next reading sees the target and the broker writes the `installed` record, so the owner reports nothing back. The run ledger never covers a run with sudo, and this design asks for no new privilege on any machine.
- **A failure leaves the old tool in place, reds a named reading, and never leaves the fleet split in silence.** The step's order is fetch, hash, install beside, swap, read the version, run the entry's version command once; any step failing puts the old copy back (the swap undone; for winget, the previous version installed again — bytes its ledger entry already covers) and the machine resumes on the old tool. *A hash that is not the row's* is a different event: nothing is installed, every other install of that round on every machine is held, and the item goes to the top of the daily asks as a security finding, since the channel served bytes the owner did not approve. Every other failure is a red section of the janitor's file named for the machine's installs, which a fixer session takes like any red.
- **The per-machine version reading.** The broker already holds the tool versions each machine reports. The reading puts them side by side per tool: installed on each machine, the entry's `reviewed` version, the version a round has decided and not yet installed, and one state — `current`, `owed` (decided, not installed), `installing`, `waiting` (who holds the machine), `failed`, `split` (machines of one tool at different versions with no install owed that would close it), `owner's` (a privileged step asked). `fleet security` and the Security page print it; `split` and `failed` are reds, and `owed` older than a day is one.
- **What stays out.** Which bumps the owner decides is unchanged: a tool row is never a quiet round's, a `RED` or `n/a` row is never takeable, the operating system's self-applied updates stay outside the round, and a new tool still needs its inventory entry and its review first. A resolver or installer command is still never typed by a session — the install step is the tool that runs it. The rule's sentence that a session presents install commands and lets the owner run them gained its exception on the owner's ratification of this design (2026-11-14, "yes" via `fleet answer`, recorded in the rule with the owner's words): an approved install the step can hold to a checksum without a privilege is the fleet's. Until the build's switch is turned on, an approved install is still the owner's to run as § *The tool report* says.
- **Where the directive was silent — the session's choices, refutable.** (1) The carrier is a broker-called step with no session, not a row a session picks up: a quiet install cannot be run by a session of the machine it drains, and a deterministic step keeps a model out of the path between approval and bytes. (2) Installs precede pins, and a machine that is down does not hold a landing. (3) One machine drains for installs at a time, and an install never stops a manual session or a detached run; on Windows the drain may include a reboot of the machine when an install needs one, the owner's word of 2026-11-13 17:39: "It is OK to drain and reboot win as part of tool upgrades" — the reboot follows the drain's own rules (unattended sessions resumed from captured state, manual sessions and detached runs waited for, never cut). (4) The hold is put on the approval's standing, with no second word from the owner. (5) The fleet carries out only what it can hold to a checksum without a privilege; the rest is one ask per machine per round.

## The two further layers (owner-ruled 2026-10-04)

- **A YARA-based behavioural scanner beside the regex pre-scan: malcontent.** Every staged artifact, old and new, is analysed in ONE run of Chainguard's malcontent container, digest-pinned, with no network, a read-only root and the artifacts mounted read-only. Only its rule identifiers and risk levels are consumed — its match strings are excerpts of the scanned files and are dropped where its output is parsed. Before the run the report unpacks every archive the scanner would expand (it picks them by file name), recursively and under the artifact's caps, beside the archive, and removes the archive: the scanner keys an archive member by a path inside its archive, so two archives holding a member of one path would collide in its output and one's behaviours vanish, while an unpacked file is keyed by its own full path; an archive the report cannot unpack — a format it does not open, unreadable, unsafe, over the caps or nested too deep — makes its artifact's row `n/a`. Its output is read per artifact, never per run: an archive member the scanner expanded after all is attributed to the artifact whose archive holds it, and, since a same-path member of another archive may then have been lost without a trace, makes every row `n/a`; output naming an artifact in a form the reader does not know makes that one row `RED` (*scanner output outside the staged tree* — it may be the artifact steering the scanner, so the dependency review sandbox reads it), output it cannot read makes that row `n/a`, every other row keeping its verdict; output naming no staged artifact at all fails the run, naming how many such entries and the artifacts staged, and a path it printed is logged only as a hash. A bump answers for the HIGH and CRITICAL behaviours its new version raises that the old version did not: a new CRITICAL is `RED`, a new HIGH is `FLAG`. Comparing behaviour sets per package, not files, is deliberate: bundlers rename their output chunks every release, so a per-file diff reports noise. Rejected alternatives: a Python scanner that had archive-extraction remote-code-execution advisories in 2026 (it unpacks exactly the attacker archives this scans), and dynamic analysis (it runs the code). **The image's publisher signature is not verified**: its signatures are in a format the GitHub CLI does not read, and the tool that does is a further install; the image is pinned by digest, which fixes the bytes but not who made them.
- **npm provenance is verified cryptographically by the GitHub CLI** (`gh attestation verify --bundle <the registry's SLSA bundle> --digest-alg sha512`) against the tarball whose hash already matched the lockfile — no new tool. The source repository the provenance claims is enforced; the workflow that signed it may live elsewhere (a reusable release workflow) and is read back from the verified certificate: same repository or same owner is unremarkable, **another owner's workflow is `FLAG`**, and so is a self-hosted runner; a signature that does not verify is `RED`. Measured 2026-10-04: with the source repository alone enforced, a same-owner reusable workflow fails verification, which is why the signer is read back rather than required. crates.io publishes no attestation, so a crate's trusted-publishing record is reported, not verified.
- **Pre-scan findings are judged as a delta too:** a finding count the old version already had is not the bump's; a new package has no old version, so its whole verdict counts.

## A round of bumps — the dependency review sandbox once, last (owner-ruled 2026-10-04)

**Ruling (the owner's, 2026-10-04): bumps are taken in rounds — many at a time, every ecosystem and tool together — and a round reaches the dependency review sandbox at most once, at its end, as the check of last resort.** The owner's words: "There must be only one pass in the dependency review sandbox per round of bumps across all languages and packages. All other avenues must be tried first, all bumps seen as a collective, no separating languages or tools."

- **A round is one collective candidate.** Every pending bump — Cargo, every tracked `deno.lock`, a third-party tool, whatever else a lockfile pins — is resolved together and reported in one table, never split by language, ecosystem or tool into separate passes.
- **Every other avenue comes first.** A package that would need a read is first met by everything that does not use the dependency review sandbox: another version (an older fix, a later one past the minimum release age), dropping or replacing the package, the scanners and the report's crude checks, and the owner's own reading of a change small enough to read by eye. *Example, 2026-10-04:* `http-cache-semantics` 4.2.0 → 4.3.0 (4 files, +35/−12 lines; the fix for the site's last advisory, published the same day) was read by the owner from a diff of the two hash-verified tarballs, found free of injection and malware, and taken through the security-fix bypass on that reading — the dependency review sandbox was not used. **The owner's diff — only the changed text parts (asked by the owner in guided round 24, 2026-11-11; built the same day).** The owner, after reading two whole diffs in that round: "Please mint a row to handle diff files better. Only 10% of these diffs were comments, the rest was normal code. I would like you to only show me the comments. This is possible since we have both versions, so giving me the whole diff is avoidable. Please build that tool." And earlier the same session: "Please open the diff files in Zed, and do this automatically from now on." So a need whose note asks to see a change gets `bump-round owner-diff --round <N> --need <cargo|npm>:<package>`: it fetches the locked version's archive and checks it against the base lockfile's checksum or integrity, fetches the candidate's and checks it against the stored report's `prescan_hash`, refuses on either mismatch, and writes ONLY THE CHANGED TEXT — the words of the change's comments, doc comments, strings and other text parts and of its non-code files, never a line of code, the code and the text the other version already holds counted (the lexers: Rust; JavaScript and TypeScript — JSX and TSX are read as non-code) — as ASCII-only pages of at most 1000 words, on the manual prompt injection check's renderer, opened in Zed by the verb itself, with a coverage check that refuses on any difference; what a page shows and what is handed over afterwards are [`owner-reading-pages.md`](owner-reading-pages.md)'s. Nothing of a page reaches the session: it sees counts, the diff id and paths. The owner answers each page as in the whole-file pass (`injection-clear diff-verdict`); what the reading covers, and the hand-off of the diff to a session once every page is approved (`injection-clear diff-read`), are `release-integrity.md` § Reviewing untrusted source → *The manual prompt injection check*, its last part.
- **One dependency review sandbox pass carries what is left, whatever its language.** Every RED the round still holds, and every package nothing else could settle, goes to the dependency review sandbox together in a single pass at the round's end. So the dependency review sandbox must be able to read every ecosystem the round can carry — npm/JavaScript as well as Rust crates.
- **A round's landing includes the pre-scan ledger update** (`release-integrity.md` § Reviewing untrusted source → *The pre-scan ledger*: the session landing a dependency runs it), so the round's REDs at the exact bytes it landed are known while its dependency review sandbox pass is still to come. Rounds 1 and 2 (2026-10-05/06) both landed without it; run afterwards, it found nine REDs round 1's pass had never seen.
- **A RED found after its round's dependency review sandbox pass waits for the next round's pass (owner-ruled 2026-10-06, in a manual session, choosing "fold into round 3's pass" over a residue pass for round 1).** It is not a second pass for the closed round: it joins the single dependency review sandbox pass of the next round to reach its end, beside that round's own REDs. **What is given up:** the CI pre-scan stays red on `main` until that pass rules it, so anything waiting on a green pre-scan waits for the round too. **What bounds it:** the RED is never waived meanwhile — the gate keeps failing closed and re-asserts it daily (`release-integrity.md` § *The pre-scan ledger*).
- **A RED known before the decision is ruled by the dependency review sandbox BEFORE its need can be taken (owner-ruled 2026-11-11, after guided round 22; amends the three bullets above for that case).** Round 22 landed `wasmtime` 49.0.5 with one package's pre-scan RED still unruled — the table had carried it under a `GREEN` verdict, the guide asked "do you take it with the RED sent to the venue?", the owner answered "Yes let wasmtime go to the review venue", and the move landed while the dependency review sandbox row was still unclaimed. The owner, on learning that: "I think we should change the tooling here to require a venue review before 'take it' is possible." So: a need whose tree holds a row that is `RED`, or whose new bytes carry a pre-scan RED the ledger has no clearing disposition for, is NOT takeable — the tool refuses the take, whoever asks (what clears new bytes, the one tool-proven carry-over of an earlier ruling included, is the ledger's rule: `release-integrity.md` § Reviewing untrusted source → *The pre-scan ledger*); the round sends those rows to the dependency review sandbox, and the need becomes takeable only once the ledger holds a disposition clearing those exact bytes. While the dependency review sandbox is out of tokens, that disposition may be the owner's own: the manual prompt injection check (owner-ruled 2026-11-11; `release-integrity.md` § Reviewing untrusted source → *The manual prompt injection check*), run by the round's own verbs (`bump-round injection-check`, `injection-verdict`) in place of the sandbox's pass for the two text classes, and read back by `report` exactly as a sandbox ruling is — `present`'s wait accepts either. A need whose every new-bytes RED the ledger's carry-over clears (each one an injection-class line identical, by fingerprint, to one the dependency review sandbox cleared for an earlier version of the same package; built 2026-11-11) is takeable with no dependency review sandbox step: the report shows the RED as cleared, naming the version the clearing rests on. Every other avenue still comes first, and the dependency review sandbox still takes a round's REDs together in one pass — but that pass now comes before those needs' decision, not after their landing. What it costs, said to the owner in the same exchange: an advisory fix whose tree carries a RED stays unlanded, its advisories open, until the pass has ruled. A RED first found AFTER a landing (a scanner rule added later, a ledger update run late) still follows the bullet above: never waived, ruled in the next pass. **The pass is a step of the round itself (the owner, the same exchange: "The venue review should be a part of the bump round").** The round resolves and reports, sends every such row to the dependency review sandbox in its one pass, waits for the rulings while it stays open, and only then presents the table — so the owner decides once, on a table whose REDs are already ruled, and a need the dependency review sandbox cleared is taken in the round that found it; a need the dependency review sandbox upheld is not takeable and its line says so. The round's step log records the pass (which rows went, the ledger dispositions that came back). **How the round hands the rows over and reads the rulings back (designed 2026-11-11):** the dependency review sandbox stays the only place dependency source is read (`release-integrity.md` § Reviewing untrusted source), so the two sides meet only in typed data. The round tool's `sandbox-check` verb, run after `report` and before `present`, lists every unruled-RED row of the stored report with the facts the dependency review sandbox rules on — package, version, lockfile checksum, extracted-tree hash and RED keys, which the report's row carries as typed fields — mints the pass's one work item in the dependency review sandbox's queue naming them, and logs the step; `present` is refused while a row so listed has no ledger disposition; the dependency review sandbox's session rules and writes the pre-scan ledger, as for every RED; the round then runs `report` again, which reads the ledger, and the digest reads a need the dependency review sandbox cleared as `takeable` and one it upheld as `RED upheld by the dependency review sandbox — not takeable`. A round with no such row needs no `sandbox-check` step. **The quiet lane** is untouched by an owner's round waiting on a pass: the waiting round holds only the needs it took, and the quiet lane opens, decides and closes beside it (*Two lanes*). A quiet round sends nothing to the dependency review sandbox and never waits: a need whose tree holds an unruled RED is not eligible, returns to the queue as the owner's with that reason, and is ruled in the pass of the owner's next round (a design decision of the session that built the refusal, the narrower reading; the owner may rule that a quiet round runs a pass of its own). A `RED` verdict with no pre-scan RED is sent in the same pass, but no ledger entry can rule it, so `present` does not wait on it and its need stays `not decidable` (a design decision of the session that built the verb). The refusal of the take, the report's verdict, the `sandbox-check` verb and `present`'s wait are built (§ Implementation status today).
- **A hold-back — a package taken back to a version the lock held before, on the owner's word (0.1.7 attempt 1, 2026-11-13).** Round 38 moved `libc` 0.2.189 → 0.2.191, whose iOS targets lack a type `netdev` 0.45.1 names, and no newer in-range `netdev` or seven-day-old `libc` existed; the owner approved holding `libc` at 0.2.189, and neither the round's resolve (which refuses every downgrade, the age never asking for one) nor a hand lock edit (refused at landing) could make the move. So a round's `resolve` makes exactly one kind of downgrade, the hold-back: the owner's words, quoted verbatim, naming the package — or verbatim in the owner's own note on that need, as a numbered reply ("4 A") is recorded; one package, to one exact version older than every version the lock holds of it; a version a tracked lockfile on `origin/main` held before, read from git history, so the bytes are ones a round already reviewed and the fleet already ran — the step logs the word and the commit that last held it; any other package going down in the same step is still refused, and a quiet round never holds back. The move is a row of the round's report like any other — direction `down`, which keeps it the owner's (never auto-eligible), carrying the need's text, the owner's word and that commit, the round's advisory delta naming any advisory the older version reopens — and it lands as any take does: `decide --take` on that row and the merge path's check of the row at that exact version. **Its row is graded as a return to reviewed bytes, never as a new version (round 39, 2026-11-13):** when the target's lockfile checksum is the very entry `origin/main`'s lock held at that commit, every comparison with the version being left (provenance lost, publisher changed, size, install script, native binaries — facts about the version left, read backwards) is no verdict reason but a note phrased about that version ("0.2.191 gained provenance 0.2.189 does not carry"); the row carries the standing the newest closed round's report recorded for exactly that version and checksum, naming the round (its verdict, its pre-scan ruling), or, when no closed round rows those bytes, is graded on its absolute checks alone — integrity, vet, the pre-scan counted whole, the malware scan, the advisories going back reopens; and its verdict is `FLAG` at best, never `GREEN` and never auto-eligible, a reason naming the hold-back keeping it the owner's, takeable on the recorded word. An absolute finding still reds it as any row — a pre-scan RED with no ruling, carried or on the ledger, a malware-scan rise, an advisory reopened, a carried `RED` — and a checksum other than the held entry is no return to reviewed bytes: it is graded as a new version, its RED reasons kept. A need met after a release round was presented is taken at the round's next `present`, a further table (the release round, below).
- **The 2026-10-04 round is the counter-example:** it used the dependency review sandbox separately for one tool's crates and then for one bump's six npm REDs, while other bumps of the same round were still undecided.

The dependency review sandbox's own rules for how a pass is reviewed (quorum, RED rulings, delta reviews) are `release-integrity.md` § Reviewing untrusted source; this section owns only when a round goes to it.

## Who opens a round, and what lands without one — nothing (owner-ruled 2026-10-05)

**Ruling (the owner's, 2026-10-05, in two directives): there is only ever ONE bump round, it is opened only by the owner, every dependency add and bump across every ecosystem and tool is analysed and presented to the owner together in that round as one table and one decision — and no dependency add and no dependency bump lands without that analysis.** The owner's words: "what I am reacting to is the totally haphazard way I am presented with version bumps. I want there to ever only be one bump round, initiated by me, and then all bumps are analyzed and presented *in one round*. Now it seems every second session is about new dependencies." And: "expressly forbid any new dependency adds or bumps without a corresponding analysis … which looks at absolutely all effects so that the decision to bump or add dependencies can be taken in one go." The measured cause: on 2026-10-05 one queue held five rows, each produced by a separate session, each putting its own consequence table to the owner for its own approval — § A round of bumps above governed only the dependency review sandbox pass, and the practice around it was one row, one table and one ask per bump.

- **Two halves, two switches — the queue bound at once, the merge refusal once the repository was public — both now in force (owner-ruled 2026-10-05, in two steps; the second switched on 2026-10-14).** The owner first scoped the whole section to the public repository, then split it the same day: a request is useless unless requests are grouped, so the grouping binds at once and only the hard refusal waits. **The queue half is in force now:** a session that meets a dependency need records a queue entry (§ *Between rounds a need is a queue entry*) and never mints a per-bump work item or puts its own consequence table to the owner; minting one is refused and the merit judge refuses one it meets (*Enforced, never trusted* (3)); the daily advisory check's red asks for queue entries. The owner may open a round at any time, and it takes every queued need at once. **The round half is in force since the repository went public:** the merge path refuses an add or move with no round and no trailer (*Enforced, never trusted* (1)) and the report's candidate mode needs a round in flight; before the flip the merge path only noted what it would refuse and a bump the owner directed on their own — approving that bump's own consequence table (§ The report, run on the candidate) — could land out of round. The minimum release age, the never-read-dependency-source rule and the owner's approval before any new version is built, run or read hold in both regimes. Two switches decide which halves the tooling enforces; both are on, the round half's since 2026-10-14.
- **Only the owner opens a round — but for two standing grants, the release round and the quiet round (both below).** No session, scheduled cycle, scanner red, merge gate, merit judge, advisory alert or queued task opens one otherwise. A round is recorded in `supply-chain/bump-round.toml` on the owner's in-the-moment word in chat — the guided round's included (*The guided round*, below) — the same standard as the public commit message's go-ahead, never inferred from an earlier approval — and that file is what the merge path reads. One round at a time in each of two lanes — the owner's and the quiet one (*Two lanes*, below); a round closes before the next of its lane opens; its number is the round's name everywhere (the record, the commits, the queue entries it took).
- **A round is every pending need at once, presented once.** Everything the queue holds is resolved together on a scratch copy — `Cargo.lock`, every tracked `deno.lock`, Go modules, Gradle, SwiftPM, NuGet, a third-party tool or toolchain, a CI action, a container image — and reported as ONE table carrying the whole-effects analysis (§ The whole-effects analysis), presented to the owner ONCE, complete, in chat; the session then stops and waits. The owner decides every item in one reply — approve, reject, amend, or leave for the next round — and the decision is recorded verbatim beside the table in `supply-chain/rounds/round-<N>.md`. Execution then lands commits that name the round; a RED or an unsettled package goes to the dependency review sandbox once, at the round's end (§ A round of bumps). A need the round cannot resolve (a version under the minimum release age, a conflict) stays queued and is reported as such.
- **Between rounds a need is a queue entry — never a row, never an ask.** A session that meets a dependency need — a crate, package, module, tool, toolchain, action or image it wants added or moved, or an advisory naming a fix — records one entry in `supply-chain/bump-queue.toml`: ecosystem, package, current version, wanted version or `new`, why, who recorded it, when, and the advisory id when one names it. Then it goes on without the dependency: the dependent work is captured as a queued task that waits on the NEED — an `AFTER` item `need <ecosystem>:<package>` on the row ([`task-kinds.md`](task-kinds.md) § Kinds → *A dependency need is a prerequisite the queue resolves*), which holds while the need is queued and lapses by itself once a round has decided it, whichever way the owner decided — or built another way. It never edits a lockfile or a manifest's third-party entries, never resolves to a new version, never mints a per-bump task, and never puts a consequence table to the owner. The daily advisory check's red follows the same path — a queue entry marked advised, triaged in the janitor section — and the owner, who reads the hosting service's alerts and every halt, decides whether it opens a round. The monthly currency cycle (`release-integrity.md` § Dependency currency) surveys and queues what moves in range, which majors exist and which advisories stand; it bumps nothing itself — what it queues lands in a quiet round when it is auto-eligible (*The quiet round*, below) and is the owner's otherwise.
- **What is a change.** A version added or moved in any tracked lockfile or in a manifest's third-party entries: `Cargo.lock` and every `Cargo.toml` dependency section, `deno.lock`/`deno.json`/`package.json`, `go.mod`/`go.sum`, the Gradle build files and the Gradle verification file (`verification-metadata.xml`), `Package.swift`/`Package.resolved`, the NuGet references, `rust-toolchain.toml`, the pinned actions and image digests, and the vendored forks' own lockfiles and manifests. A package LEAVING — a removal with no version added or moved, like the 2026-10-05 `ksni` codegen commit that shed nine packages — is not an add or a bump: it may land out of round and is reported after the fact in landed mode. A path or workspace crate is not third-party.
- **Enforced, never trusted.** (1) The merge path refuses a lockfile or manifest add or move while no round is open, and one whose landing commit carries no `Bump-Round: <N>` trailer. A line that repeats a pin already in the file — the same text, up to a Dockerfile FROM's platform flag and stage name — is no add or move and needs no round (owner-ruled 2026-10-19, "No round needed, it's the same pinned digest": the second FROM of the pinned Rust image that puts the image's wasm stage on the build platform). (2) The report's candidate mode runs only inside an open round; landed mode always. (3) Minting a per-bump work item anywhere but the round's own queue is refused, and the merit judge refuses one it meets. (4) The session rule stands where every session reads its rules. What of this is built: § Implementation status today.
- **Where rounds live.** One dedicated checkout of the fleet owns rounds. The between-rounds queue is the data file, deliberately not a row in a work queue: a queued task is launchable work that a session runs, a judge reads and ageing retires, while a need is not work until the owner opens a round; and a file is what both the round's candidate assembly and the merge gate read. **The round is not a node in the row graph either — a row that depends on a bump waits on the need, never on a row standing for the round (owner question 2026-10-05, ruled the same day).** The round's own row is the work of running the round once the owner has opened it, parked on their word, and nothing gates on it. Two shapes were rejected: a forever row every bump gates on (a standing row is the idle sweep's kind, judged and relaunched at every pool pass with nothing to do between rounds, and a gate on a row that never closes reads CONDITIONAL for ever, lifted only by hand), and a row minted per round ahead of the owner's word (a round that leaves a need behind would lapse that need's dependents falsely, and row numbers would be spent on rounds nobody opened). What the graph draws instead is the queue itself: the route map puts the bump queue behind every row whose `AFTER` line names a need still queued, and a round's record (`supply-chain/rounds/round-<N>.toml`, the needs it settled as data beside the markdown — written at the close, and by a round that stays open, the release round, at each need's settlement: the `settle` step, the per-need half of `close`, run by the landing of a commit under the round's trailer (the landing tool, after its verdict, settles each round the landed commits' `Bump-Round` trailers name and lands the record as a second commit) and named `SETTLE OWED` by `bump-round status` while owed; designed and built 2026-11-13, the rule and its status in [`task-kinds.md`](task-kinds.md) § Kinds → *A need lapses when its decision has LANDED*) is what lapses the item — one owner per claim, nothing minted, no false MET. The queue, the round file and the records are fleet process, not product: they name development checkouts, machines and work-queue rows by design and carry the owner's words verbatim, so the publication transform withholds them — this document ships and describes the mechanism; the records stay in the development repository.
- **A security fix out of round — none: it waits for a round (owner-ruled 2026-10-05, option (a) of § Open decisions).** An advised fix is a queue entry like every other need, marked advised; the daily advisory check's janitor red and the hosting service's alerts put it before the owner, and the session that meets it always asks the owner at its halt to open a round — the owner's word still opens it. The minimum release age's security-fix bypass (`release-integrity.md` § Dependency verification) is taken only inside the round that takes the fix, under its four conditions; nothing moves out of round. **Amended 2026-11-10 by *The quiet round*:** an advised fix that is auto-eligible lands in a quiet round with no ask; one that is not — the bypass always — is an owner-decision item on the Security page, and the halt's ask is made as before.
- **The release round (owner-ruled 2026-10-17): the release checkout has the owner's standing word to open a round at any time in order to get a version out.** The word that opens a version's attempt ([`release-attempt.md`](release-attempt.md) § The release attempt) opens one round that stays open until the attempt ends; a need the attempt meets — an advisory the triage rule holds the release for, a tool pin a shipped workflow needs — is presented in it as it arises, one table each, and decided by the owner's reply; the round closes with the attempt, and a need outside the attempt's scope stays queued. Still one round at a time; still the owner deciding every item; the standing grant covers the OPENING, by that one checkout, for that one purpose, and nothing else — every other checkout waits on the owner's in-the-moment word as before. The round runs where the attempt runs, the one exception to *Where rounds live*.
- **The quiet round (owner-ruled 2026-11-10): tooling has the owner's standing word to open a round that takes only what the owner never denies, decides it by fixed rule, lands it and closes — the second standing grant, after the release round.** The owner's words: "About 'every bump is the owner's decision in a round' - in practice I never deny anything which has no security vulnerabilites. Amend this rule so that security flags of minor/low threat are auto-approved." And, the same day: "I want a bump of an existing package to go ahead if it does not trigger a user approval like we outline here, but would like to still manually approve installs of new libraries." The grant covers the OPENING as well as the decision, because an item reaches a table only inside a round: an auto-approval with no opener would change nothing. The round's record quotes the grant as its opening word, as a release round's quotes its own.
  - *Who opens it, and when.* The daily advisory check and the monthly currency cycle (`release-integrity.md` § Dependency currency), each at the end of its own run, when no round is open and the queue holds a need that no quiet round has reported yet, or whose candidate version has moved since one did — so a need already returned as the owner's does not reopen a round every day. Only a need the fixed rule could ever take counts — one of an auto-eligible ecosystem asking for the newest version in range: a tool, Go or SwiftPM need, a pin, a major or an add is the owner's in every quiet round, which could only return it, so it never makes one due (the narrower reading, built 2026-11-12 after the opener opened seven rounds in one day on such needs alone; a round opened for another need still takes and returns it). A candidate has moved only against the version the last quiet round graded: a fixed release an advisory names counts when it is newer than that version, and a need returned with no graded version is not moved by a fix it was returned beside — a re-target, which spends the report, makes it new. A quiet round defers only while another quiet round is open (*Two lanes*, below). The opener mints the round's work item in the rounds' checkout as the owner's word does, and the fleet runs it.
  - *What it presents.* Every queued need, as every round does: one table with the whole-effects analysis, written to the round's record with nobody waiting on it.
  - *What it decides — the auto-eligible items, by a fixed rule in the tool over the report's verdict strings and typed fields alone.* Never over a recommendation, a summary or any other prose: a model wrote that, and text injected through a build log can reach it. An item is one requested need plus every row its forced moves add, and it is auto-eligible only when ALL of these hold: **(1)** its ecosystem is Cargo, npm through a tracked `deno.lock`, NuGet with a lockfile, or Gradle with its verification file; **(2)** the need is a patch or minor move of a package the lock already holds, to the newest version in range — an UPWARD move, read from the row's typed `direction` (`up`), since a distance word like `minor` carries none: a move backwards, a move to a version of equal precedence, or one the tool cannot order is the owner's (quiet round 23 rowed two downgrades `GREEN`, `minor` and `patch`); **(3)** every row is `GREEN`, or a `FLAG` whose reasons ALL stand in a closed allow-list — a constant of the tool, today the one reason `cargo vet: no audit or exemption covers`, extended only by an owner's ruling recorded here; **(4)** no row adds a package the lock did not hold — a new library is the owner's to approve, whether asked for or pulled in by a move (owner-ruled 2026-11-10: a package a bump pulls in transitively IS a new library — § No new software without a review); **(5)** every row's version was published at least 7 days ago by the publish date the report read from the registry, never by the resolver's own age setting, one half of which can fail open; **(6)** the round's advisory delta opens no advisory in a lockfile the item moves (closing any is fine, and an exception the move makes stale is deleted in the same commit) — each scanner reads one tree's lockfile, so an opened advisory bars every item with a row in that lockfile, whichever package it names, and bars every item of the round when no need has a row there or the tool cannot place the scanner's scope (a session's reading of 2026-11-11, the owner's to refute: read round-wide, nine advisories one site's lockfile opened made all 538 needs of a quiet round the owner's, so no quiet round could land while any lockfile opened one); **(7)** no row carries a reason that a check could not run — `not run`, `not checked`, `unknown`, `unfetched`, an old artifact unavailable, `unreadable`, `n/a` — § The report's *A check that could not run is a finding* made a bar. A table with no finding at all is the plain case, and proceeds.
  - *What stays the owner's — everything else, each with its reason named on the item.* Any `RED`; every other `FLAG` — a publisher changed, a provenance repository changed, gained or lost, a sharp size growth, an install script or a native binary added, a new malcontent HIGH, a new pre-scan finding, another owner's signing workflow, a self-hosted runner, a version younger than 7 days, a toolchain requirement unmet or unchecked; a major; an add; a format-bearing row; Go and SwiftPM; the toolchain, CI-action, image and tool pins; and the minimum release age's security-fix bypass, ALWAYS, whatever the advisory's score (`release-integrity.md` § Minimum release age).
  - *How it lands.* The tool records the decision itself — `decision = "auto under the quiet-round ruling of 2026-11-10: <n> GREEN, <m> FLAG (allow-listed)"`, the eligible items named — the session lands them under the round's trailer and closes the round. A need the rule did not decide returns to the queue as every undecided need does, now carrying the round's report row for it and the reason it is the owner's: that is the item the Security page shows. An eligible item whose landing needs any change of ours beyond the lockfile and the version it names — a compile error, a failing test — is NOT repaired in a quiet round: its move is backed out and the need returns to the queue as the owner's, reason `needs migration`, because the session of a quiet round never acts on what a dependency's build prints. Nothing of a quiet round goes to the dependency review sandbox (§ A round of bumps): an item that would is not eligible. **A stored report row is spent by the next round that resolves the same need (designed 2026-11-11).** A returned need's row graded the bytes ITS round's resolve produced, and it gates nothing outside that round — every take is gated by its own round's fresh report — so it is a reading, and the next round that resolves the need and leaves it, quiet or the owner's, supersedes it at its close, read off the digest the owner decided on (never the one after the landing's backout): a fresh row of that round for the need replaces it (still the owner's, with the digest's reason, when not takeable); a resolve that moved nothing, or was refused or failed, produced no bytes to grade, so the earlier row is dropped and the need carries that round's outcome in its place (`nothing moved`, `not decidable — <the step's reason>`), which the Security page shows at the level an in-range move earns, never critical; a need the round never resolved keeps its row. Nothing is dropped silently: the outcome stands on the need and in the round's record, and a RED whose bytes a resolve still produces is graded again by the round that produces them, where it is the owner's to decide. A round closed before its close did this is re-read once by `bump-round restamp <N>`, which never touches a need a later round read, a package the owner decided in that round, or a need recorded after its close. **A row graded RED for an advisory fixed in a newer release is spent by re-targeting the need (built 2026-11-11):** `bump-round need … --retarget` moves a queued need no round holds to that release — the new target, why, advisory and source replace the old, the stored row, reasons and outcome go, the owner's note stays — because no one would take a target the report already found vulnerable; the next round grades the new target. **The fleet re-targets on its own, and an advisory RED names its way out (built 2026-11-12):** at the end of every daily advisory check the quiet round's opener re-targets each queued need no round holds and the owner has not noted whose stored report row is RED for open advisories alone, any of them fixed in a known release newer than the row's target, to the newest of those releases — the one that closes the most (`source = "dep-advisory-check"`, one line each); **a row only partly fixable is re-targeted too (ruled 2026-11-12)**, since no one takes a target the report found vulnerable and the advisories with no known fix are still open at the installed version: those stay the owner's, graded again at the new target by the next round; and since no reading of bytes clears an open advisory, the digest never sends such a RED to the dependency review sandbox — its reason names the advisories and the way out: re-target to the fixed release, or, with none known, the owner's acceptance of the target version (an exception at it, pending until the install — `dependency-advisories.md` § *Dev tools*) or the tool's removal, and for a row partly fixable both, the release named with how many of the advisories it fixes and the rest named by id; a byte-level RED keeps the sandbox, and a row RED for both carries both. **A spent advisory RED on a tool need is cleared by the same opener (built 2026-11-12):** a tool row's advisory RED is a reading of the advisories open at its target, so when that day's tool audit scans the target and finds none — the advisories misread, or excepted since — the reading is spent while `--retarget` has no other target to move to; the opener then drops the stored row, reasons and outcome of each queued tool need whose reading no round holds — no round holds the need, or a LATER round than the one whose report made the row (amended 2026-11-13: a round's close writes its rows back, and the next round may take the need before any daily pass, so the old rule left a spent reading for the holding round alone to remove; a row the holding round graded itself stays its reading until its next report) — and the owner has not noted whose RED rests on open advisories alone (no pre-scan or byte-level RED, no malware hit, no reason but its advisory sentences and the channel facts every round reads again), when the audit printed it `CLEAN` at exactly the row's target (`dep-tool-audit.py`'s positive reading, carried in the findings file as `tools_clean`) and posted no finding against it — one `cleared` line each, the next round grading the target fresh; a tool the audit did not scan, scanned at another version or could not run over keeps its row.
  - *Two lanes: the quiet round and the owner's round never wait on each other (owner-ruled 2026-11-10, built the same day).* The owner, after an approval on the Security page opened an ordinary round and the first quiet round was put off behind it: "I was not aware that this caused a 'quiet round' to be postponed indefinetely. I think these should be separate, so that the quiet round (being totally autonomous) should run in parallel with and not interfere with the users's round." So there are two lanes, at most one round open in each: the **owner's lane** (a round opened on the owner's word in chat, the guided round's included, and the release round) and the **quiet lane** (a round tooling opens). Neither lane's opening, deciding, landing or closing reads the other lane's state. **(a) A need is in one round at a time.** A round takes a need by writing its number on it, and a need so held is invisible to the other lane until its round closes or returns it. The quiet round takes every queued need not held; a round opened in chat, and the release round, take every need not held by an open quiet round. **(b) Every command names its round.** With two rounds open, `bump-round present|decide|close`, the report's candidate mode and the merge path's trailer check take the round's number; a command given none acts when exactly one round is open and is refused, naming both, when two are. The merge path accepts a `Bump-Round:` trailer naming any open round, and a commit moves only packages of needs that round holds. **(c) The lockfile is settled at the landing, never by waiting.** Both lanes resolve into the same lockfiles from their own base. The round that lands second rebases as any change does; when the lock it reported against has moved under a package of its own needs — the same package, or one its move forces — it resolves those needs again on the new tip and reports them again before landing: a quiet round decides the fresh rows by the same fixed rule and returns what is no longer eligible, an owner's round puts every row that changed to the owner again, in its session's chat, before landing it. A move the other lane landed is part of the base, so it is never the unaccounted move that makes every item the owner's. **(d) The page shows both.** The Security page's round line names each open round and its lane, and an item's `STATE` says which holds it.
  - *The owner is told after, and may revoke.* The round's digest — what moved, from and to, under which reason — goes in that session's halt message and in the next release attempt's record, and each item stands on the Security page as `landed`. The owner revokes any item in chat — the guided round's included; a revocation is a pin-back need the session records and the next round takes, quiet rounds included only when the pin-back is itself auto-eligible.
- **The guided round — the owner's round, started from the Security page and decided in a session (owner-ruled 2026-11-10; it withdrew the page's per-item approval, built and removed the same day).** The owner, after a day of approving items one by one on the page: "I have changed my mind and do not want to do individual approvals from the Security page. Instead I want 1) 'quiet' rounds done regularly for what can be bumped automatically, 2) the Security page to alert me to new vulnerabilities found in the daily scan and new needs from the fleet. I want do be able to press a key in the Security page to start a bump round - where I will probably, as you say, answer 'your recommendations for all' quite often. But I want a fable session to guide me." So the owner's lane has one way in from the console: a key on the Security page starts a **fable guide session** ([`fleet-surfaces.md`](fleet-surfaces.md) § The surfaces → *The Security pane*, `security-round`), and everything that is the owner's word is said in that session's chat — the same standard as every owner-opened round. The session briefs the owner first (the daily scan's verdict, the vulnerabilities and warnings open, the needs that are the owner's, a count of the routine moves left to the quiet round), proposes the round's scope — by default every item with a finding and every add, major and pin, the routine in-range moves staying with the quiet round — and opens the round on the owner's yes, quoted as the opening word. It resolves and reports as every round does, presents the ONE table with its own recommendation on every line, and takes the owner's reply verbatim as the decision; "your recommendations for all" decides every line as recommended, except that the security-fix bypass is decided only when the reply names it — and a `RED` is decided by nobody's reply: its need is not takeable until the dependency review sandbox has cleared those bytes (§ A round of bumps, owner-ruled 2026-11-11, which withdrew "a `RED` is decided when the reply names it") — or, while the dependency review sandbox is out of tokens, until the owner has approved every page of its flagged text in the manual prompt injection check, which the guide runs in the same session (`release-integrity.md` § Reviewing untrusted source → *The manual prompt injection check*). **What the guide tells the owner about the table is the tool's digest, pasted, never the guide's own summary (owner-directed 2026-11-11, after round 22, where a model reading a 91-line table said "no RED" over an unruled one and recommended `take` on three needs the report held no row for):** `present` prints, and writes into the round's record, a digest computed from the stored report's typed fields and the step log alone — per need exactly one of `takeable` (rows for the need and for every package its resolve step moved, none an unruled RED; with the packages it pulls along and which of them hold a queued need of their own), `not decidable — <the tool's reason>` (no row, a verdict that did not run, a refused or unbuilt resolve, an unruled RED) or `nothing moved`, then **Named decisions**, one line for every row whose new bytes carry a pre-scan RED with no disposition, every `RED` verdict and every move under the minimum release age; the guide adds only its recommendation on each `takeable` line. `decide --take` is refused for every need the digest does not read `takeable`. A decided round takes a further `decide --body`, which adds the owner's later word to the decision; and the owner's own words about one need (`decide --note`, or `note` between rounds) stay on the need when it returns to the queue, printed by `status` and by the digest of every later round that holds it. It lands under the round's trailer, closes, and gives the digest. The key press itself opens nothing and decides nothing, so the verb is refused to nobody: a session started by anyone else still has no owner in its chat. The session's steps are the `bump-round` skill (`.claude/skills/bump-round/SKILL.md`).

## The whole-effects analysis (owner-ruled 2026-10-05; the column set is this doc's)

**The round's table carries every effect of the whole round, so the owner decides every add and bump in one go.** Per package version, the columns of § The report, plus:

- **Compiled, or lock-only.** Whether any target of the workspace compiles the entry at all, read from the membership of `cargo tree --workspace --target all -e normal,build,dev --all-features` (and the npm closure for Deno) — never assumed from the lockfile. Membership is the union over every feature of every member, because a crate only a non-default feature pulls in is compiled by that feature's build; lock-only is left for entries no feature combination reaches, such as optional subtrees of third-party crates that no member enables. The Runs and Ships columns read `cargo metadata` under the same flag, so all three columns come from one resolve. Measured 2026-10-05 on the ratatui 0.30 candidate: 33 of 46 changed entries were never compiled, which the Runs and Ships columns, read from the lock graph alone, overstated. A lock-only entry still counts as present (it is resolvable code) and is reported as such.
- **Per-artifact reach.** Which shipped artifact's normal-dependency closure holds it: the nest, each of the 7 apps by name, the mail bridge's FFI library, the web bundle — not "an app".
- **Forced move.** Which requested bump pulled this entry along (a transitive move the owner did not ask for, such as `bitflags` under `ratatui-core`), so the table shows the asked-for set and its consequences apart.
- **Format-bearing.** Whether the package is on the tracked list `supply-chain/format-bearing.toml` — crates whose version decides an at-rest or wire format: the index engine, the serialization crates, the CBOR/DAG-CBOR codec, the SQLite bindings, the MLS stack — in which case the bump is also a compatibility question under `version-compatibility.md` and says so in the row.
- **Toolchain requirement.** The package's `rust-version` (or engine/SDK requirement) against the pinned toolchain; a requirement the pin does not meet is a finding.
- **Migration estimate.** The semver distance and the count of our own call sites (`rg` over our tree for the crate's paths), with the crates and apps that hold them — never measured by compiling the candidate, which would run its code before the decision.
- **Advisories, per round.** `cargo audit`, `deno audit` and `govulncheck` before and after the candidate: every advisory closed, every one opened, and every exception in `supply-chain/cargo-audit-exceptions.toml` and `supply-chain/npm-audit-exceptions.toml` the round makes stale, by id and crate.
- **Advisory reach — researched before the question reaches the owner (owner-ruled 2026-10-17).** Every advisory a round's table, a release round or a release attempt's triage would put to the owner carries a reach finding established FIRST, by an opus research pass: inline when the session runs as opus, an opus subagent when it runs as fable or sonnet. The owner's words: involving them "might slow things down by up to 10 hours, so using opus to figure this out (within reason) is preferred." The finding goes in the question with its evidence — reached, not reached, or what stayed open and why — and "within reason" is a bounded pass of a few builds and greps.
