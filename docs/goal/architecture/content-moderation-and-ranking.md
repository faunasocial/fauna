## The one operation

Every moderation, personalization, and ranking behavior reduces to: **run scorers over content to produce per-factor scores, then apply each score with one of two verbs.** "Spam", "phishing", "NSFW", "a custom feed of cats", "the home feed", "a content-label badge" are not separate features — they are the same pipeline with a different factor and a different verb.

The **scoring substrate is `content-scoring.md`**: a scorer is a pure function over a uniform `ScoringInput`, run at whatever trust position holds the inputs, and its output is persisted on the **metadata bus** (floor / deployment-data — never the content). This doc governs what happens to those scores *after* they land on the bus.

## The two verbs

A factor's score is applied as either (or both):

- **Filter — threshold.** `score(NSFW) > τ` → collapse / hide / warn; `score(spam) > τ` → route to Junk; `score(phishing) > τ` → banner. The threshold is per-applier (see tiers): the user's own τ for their personal filters, the deployment's τ for compulsory mail-ingest.
- **Sort — rank.** Use the score as an ordering key. The home feed sorts by a relevance factor; a "cats" custom feed sorts by a *catness* factor descending; a "hide low-quality" view sorts by a quality factor. This is `feed.md`'s `order=score` generalized to *any* factor.

The same factor can feed both (spam can Junk-filter *and* down-rank). Filtering and sorting are verbs, not scorer types — which is why moderation and ranking share one architecture.

## Composition — feeds are composable score functions (RESOLVED 2026-07-06, user)

The two verbs share a deeper primitive: **there is one building block — a scorer — and a feed is a composition of scorers.** A feed's ordering key is a **weighted sum over bus factors**, `final = Σ wᵢ · factorᵢ`, and the feed then orders by it. The two verbs are facets of this one mechanism:

- **Sort** is a factor contributing to the ordering key with a **positive** weight (promote): a "cats" feed weights *catness* high; the home feed weights relevance.
- **Filter** is a factor contributing a **strong negative** term: a muted-keyword scorer returns e.g. **−1000** on a match, which swamps any promotion and sinks the item below any page a client ever renders → **practically excluded, and soft/reversible** (the content is not destroyed, just sunk; un-mute restores it). There is no separate "filter" code path — **filtering is what an extreme-negative score does under ordering.**

Two properties fall out:

- **Composability + scope.** A factor is applied **per-feed** (a named, browsable feed = a composition dominated by one factor — "cats") **or globally** (folded into *every* one of the user's feeds — global cat-promotion, or a global muted-keyword penalty). The *same* "cats" scorer can be both a standalone feed and a global promotion signal. Conflicts resolve by **arithmetic** — a `+10` promote and a `−1000` mute on the same item sum to `−990`, mute wins, with no special-case logic.
- **Content-level, not feed-only.** Scorers score *content*, so a user's composed lens applies wherever content is rendered — feed, **conversations**, notifications — not only in a feed view. A global muted keyword mutes it everywhere.

**Muted keywords are therefore not a separate subsystem:** they are a **deterministic tier-1 penalty scorer** (`fauna_core::keyword::body_excludes_matches` → a large negative score on match), composed globally. This subsumes the "filter verb" framing of Q3 into the composition model, and merges the two net-new UI surfaces (custom-feed training + muted keywords) into **one** per-user personalization surface — both are entries in the user's single tier-1 ruleset. **The penalty weight is per-keyword and user-assignable, default −1000 (user ruling 2026-07-10; the shape built 2026-10-02)** — each muted-keywords entry is a `MutedKeyword { keyword, weight }`, `weight` per-mille in `[−1000, 0]`, so a user can soft-demote one term and hard-sink another through the same composition arithmetic. A match contributes the matching keyword's weight as the factor's value (`fauna_core::scoring::muted_keywords_penalty_entry`); **several matching keywords contribute the strongest (most negative) weight, never their sum**, so the factor stays one value in `[−1000, 0]` and three softly muted terms cannot sink an item past a hard mute. A stored weight outside the range reads as its nearest bound — a mute never promotes. **Only a keyword at the full −1000 collapses** an item behind its reveal, a feed post (`feed-post-muted`) and a conversation message (`dm-message-muted`) alike (`fauna_core::scoring::muted_keywords_collapse`, the one decision every app calls): the collapse is the hide verb, and a softer weight asks for less of a term, not for it hidden — so a soft match demotes a post in a ranked feed and changes nothing in a conversation, which is not ranked. A new term is muted at −1000 and re-adding a term keeps its weight. **The page offers the weight as two levels (ratified 2026-10-02): *Hide* — the full −1000, the default — and *Show less* — `fauna_core::scoring::MUTED_KEYWORD_SHOW_LESS_WEIGHT`, −500, the midpoint: a demotion a user notices in a ranked feed, and one a hard mute still outranks under the strongest-weight rule.** `fauna_core::scoring::MutedKeywordLevel` is the one place the two levels map to weights, and a stored weight reads back as a level by the collapse threshold (`Hide` iff it collapses), so the picker never shows a hide it does not perform; the record keeps the full per-mille range, so a finer control later is an additive change. The write path is one shared delta — `fauna_client_config::preference_records::set_muted_keyword_weight` under `fauna_account_plane::preference_surfaces::set_muted_word_level`, faced by the UniFFI `set_muted_word_level` / `muted_keyword_level` and the wasm `setMutedWordLevel` / `mutedKeywordLevel` (built 2026-10-02). The picker's UX is [`../ui/settings.md`](../ui/settings.md) § Muted words — the level picker; its build state, § Implementation status today.

**Tier-1 personalization is entirely soft / composable scoring** — every user preference is a score, nothing is a hard drop, everything reversible. The only **hard** exclusions live in **tier-2 / enforcement**, a different tier with a different trust story: the legal-obligation takedown tombstone (§ Resolved design decisions Q5, built) and a blocked user. Those are guaranteed removals, not personalization, and are unaffected by this model.

**Where composition runs** follows the tier seal rules unchanged: tier-1 **sealed** factors (a user's *catness* model; their keyword list applied to MLS-sealed conversations) compose **client-side or at a capability-holder** — the nest can't read them; **transparent** factors over public / plaintext-mode content compose **nest-side** (`feed.md` § The read model, `db/feeds.rs::query_feed`, `order=score`). The multi-factor bus (Q1) holds the per-factor scores both positions read. **The nest + shared-Rust engine is BUILT 2026-07-08** (wire/at-rest composition shape, composed `order=score` over the bus, the global factor set, the shared keyword-penalty scorer, the tested sealed-factor zero-term seam — detail: `feed.md` § Feed-rule types → Frame reconciliation); the client-side sealed-factor apply + the unified all-6-app authoring surface remain (tracked internally), see § Implementation status.

## The three model-authority tiers

Every scoring model belongs to exactly one tier, and the tier fixes both *who controls it* and *how it rests at rest* (all content is sealed at rest in both modes — the mode is key-custody):

| Tier | Controlled by | For the user | At rest (sealed in **both** modes — the mode is key-custody, not byte-shape) |
|---|---|---|---|
| **1 — User** | the user, **voluntary** | their own personalization / filtering | **Sealed** under the user's key — the user's data. Nest-opaque; only a **capability-holder** reads / scores / mutates it: a **client or AUTH'd bridge session** holding the user's key directly, or a **content-processing bridge** holding a user-minted `content.read{kind}` + `content.label-write` capability. |
| **2 — Admin / nest / authority** | the deployment / a legal authority, **compulsory** | applied *to* them | **Transparent** (plaintext floor / deployment-data). Not the user's private data; the user can see what is imposed and why. The **model** needs no key; applying it to the user's *sealed* content needs a user-minted capability (§ background re-processing). |
| **3 — Community** | another party (a shared model), **voluntary for the user** | opt-in | **Transparent** — a signed, versioned, inspectable published artifact (`AlgorithmLabeler`). Subscribing = minting that community scorer a scoped, revocable capability over the content it may label (public content needs none; scoring the user's *restricted/sealed* content is an explicit grant). |

**The seal-vs-transparency rule falls out of data ownership.** Tier 1 is the user's private judgment about their own content → it is user data → sealed under the user's key at rest **in both modes** (`encryption-at-rest.md` § Per-content-kind conformance; `mail-spam.md` § Encrypted-mode interaction). Tiers 2 and 3 are *not* the user's private data — they are authority policy and community artifacts that are meant to be **inspectable** — so they stay transparent. This transparency is itself an agency property: the user always sees the compulsory and community filters acting on them, while their own filters stay private *even from the box owner*.

## Sealing tier-1 (capability tiering)

Direct corollary of `encryption-at-rest.md` § Capability tiering and `content-scoring.md` § Input classes (the *per-user secret* row): a tier-1 model is a per-user secret, sealed under the user's key at rest **in both modes**, so **the nest can never read, score with, train, or undo it in-process** — those run only at a position that holds the user's key, i.e. a **capability-holder**:

- **The user's client**, post-decrypt (Fauna app; or a per-community/personal scorer running there) — holds the keys directly, needs no minted grant.
- **The AUTH'd bridge session** (the MDA holds the session-scoped MLS capability during an IMAP/CalDAV session).
- **A content-processing bridge holding a user-minted, scope-limited, revocable `content.read{kind}` + `content.label-write` capability** — the general primitive (design ratified 2026-07-04; tracked internally) of which the AUTH'd MDA session is just the first instance. This is what lets a scorer run *on the box* against sealed content without the box owner reading it: **scope is cryptographically self-enforcing, and mint authority lives off-box with the user** (the only confidentiality boundary — a nest-side capability check is audit/revoke, not box-owner-proof).

So the nest stores the sealed blob and serves it, but every read/mutate/re-seal is a capability-holder's. **Tier-1 is self-servicing for its own updates:** the user's model changes (`train` / `undo`) originate at a position that already holds plaintext + the key (the client or AUTH'd session), so re-scoring happens *there, at update time* — **no background bridge needed**. Tiers 2 and 3 differ: their models are transparent (need no key), but applying them to a user's *sealed* content, retroactively and with no user present, is the **background re-processing** case the content-processing-bridge + user-minted capability exists for (see § tier-3 below). The retired plaintext/encrypted mode binary — "nest-readable server-side on a plaintext box" — is subsumed by this axis: a plaintext box is just the extreme where the user has granted broad standing capabilities; every box is sealed-at-rest, and "how much it can do server-side" = "what the user has granted it."

## Tier-3 community models & background re-processing

A tier-3 community model is the archetypal **background re-processing** case: a *transparent* model, published by another party, applied retroactively to a backlog of the user's *sealed* content with no user present. The capability substrate resolves how it works end-to-end:

- **The model is a transparent, published artifact.** Represented by the existing `AlgorithmLabeler` scaffolding (`libs/fauna-core/src/scoring.rs`): a signed, versioned, size- and resource-bounded WASM labeler the user can **inspect before and while subscribing** (the transparency the tier requires).
- **Subscribing = minting a capability.** Because the model is transparent it needs **no key**; only the *content* it scores does. So subscribing a community labeler over content that isn't already public **is** the act of minting it a scoped, revocable `content.read{kind}` + `content.label-write` capability (`fauna.capabilities.mint`), shown as one entry on the nest-trust facet's client-authoritative forensic grant log — per-app frontier owned by `ui/nests.md` § Implementation status today. Unsubscribe = revoke. **The app-side act (BUILT on tui 2026-09-27, lifted to the six 2026-09-29 through the shared builder — § Implementation status today, leg 5):** `LabelerCatalogMachine::subscribe` of a `wasm` labeler whose content kind is sealed (`mail`) discovers the nest's `mda` holder (`fauna_client_bridges::discover_holders`, the derivation the Nests-page picker uses), mints the per-labeler grant below for the **standard** window (`DEFAULT_GRANT_WINDOW_SECS` — a subscription is not a one-off, and the bounded grant is never loop-renewed, `ui/nests.md` § Expiry / renewal), records its signed `Mint` event and persists it **before** depositing (`grant_log::UndepositedGrant`, `ui/nests.md` § Record-then-deposit), then calls `fauna.labelers.subscribe` naming the `grant_id`; `unsubscribe` revokes that grant nest-first (`fauna.capabilities.revoke`, then the signed `Revoke`) before dropping the row, finding it in the log by the labeler factor its tuples carry (`grant_log::current_labeler_grant`). **The honest degrades:** no `mda` holder enrolled, or mail not enabled for the account, still registers the row (the nest seeds its backlog) with no grant and says so on the page's `error-message` (`labeler_catalog.subscribed_without_mail_holder` / `subscribed_without_mail`) — an un-granted subscription never drains, exactly like a revoked one, and silence would read as a working labeler. A public-content labeler, a `list` or a `text-model` mints nothing. **The grant is per labeler in the wrap itself (ratified 2026-09-27):** every tuple of that grant — and so every HPKE wrap's AAD — carries `factor = labeler:<id>` (the `ScopeTuple::factor` qualifier, owned by `encryption-at-rest.md` § Capability tiering), so its keys open the content only to compute that labeler's score and its label-write licenses only that factor; the composed "read and filter my mail" grant carries no factor and licenses **no** community labeler. The holder selects keys by (owner, factor) and pins the fetched module's signed `algorithm_id` to the factor's id (`fauna_core::scoring::verify_labeler_metadata_for`, the one helper every position that fetches a module by id shares), and the nest's worklist and `submit_scores` mirror the same rule — so a compromised nest cannot run a module of its choosing over sealed content by naming it in the worklist, and a subscription with no per-labeler grant never drains (an honest degrade, exactly like a revoked grant).
- **Public vs. restricted content.** Labeling **public** content needs no capability — anyone can score public bytes, so a community labeler runs freely over them. Labeling a user's **restricted/sealed** content requires the explicit per-labeler grant above (an advanced opt-in). This keeps the common case (public-content labelers) friction-free while making "let this community model read my private posts" a deliberate, revocable, logged decision — consistent with the ratified "capabilities are the trust surface."
- **Where it runs.** A native app that already holds the keys **self-serves** (no minted grant needed — it re-scores its own content when it fetches the model). A **background / thin-client** case (re-score a backlog with no user present, or a web SPA that can't run the scorer) runs as a **content-processing bridge** under the minted capability — the same primitive the MDA and the FTS indexer are instances of.
- **Re-score obligation.** When a community (or admin, tier-2) model version changes, the per-user re-score is driven by the `scorer_version` / `tokenizer_version` watermark against a model-version bus (`encryption-at-rest.md` § Capability tiering; design § 2.5) — it drains whenever a capability-holder for that content kind next appears (client online, MDA session, or an active granted window). The deployment-baseline spam model (`mail-spam.md` § Cold start, Path 2) and the federation sender-reputation exchange were the original proto-instances; the general community-labeler publish/subscribe registry (a `fauna.*.labeler.*` wire over the `AlgorithmLabeler` scaffolding) is now built too — see § The concrete registry, next, and § Implementation status today (leg 5).
- **The concrete registry** (design ratified 2026-07-07, tracked internally; leg 5 / Q4). The `fauna.*.labeler.*` wire is **`fauna.labelers.{publish,list,inspect,subscribe,unsubscribe}`**. **Publish** is an algorithm-service-actor operation (any authenticated actor; the publisher signs the artifact) — no net-new *human* UI **for the `wasm` kind**, so priority #1 is untouched; the trust gate is inspect-before-subscribe + the revocable scoped grant + the sandbox, not publish. (**D8** — § Resolved design decisions 2026-07-12, below — carves out the one human publish path: a user publishing their own trained topic factor as a **List**, whose surface + identity model are owned by [`../behavior/topic-factors.md`](../behavior/topic-factors.md) § Publishing a trained factor. Read that before concluding publish has no client caller — it now has exactly one.) **Subscribe** records a nest `labeler_subscriptions` row and calls `upsert_model_version(labeler_factor, version)` — *that* registration is the whole "so the drain re-scores" step; the grant itself is the client's existing `fauna.capabilities.mint` (mint authority stays off-box with the user) in the per-labeler shape (§ *Subscribing = minting a capability*; the shared mint is `fauna_client_capabilities::mint_bounded_mail_labeler_grant`), linked 1:1 so the settings page shows one entry. A public-only subscription carries no grant. **Unsubscribe** drops the row; the client revokes the grant (drain goes dark). Each labeler writes one bus factor `labeler:<algorithm_id>` at `tier=TIER_COMMUNITY`. **The execution boundary is the crux, and bigger than the wire:** the WASM sandbox (`libs/fauna-labeler` — wasmi, fuel/memory-bounded, empty `Linker` ⇒ deterministic + no host I/O; moved out of the nest in Slice 2) is now exposed FFI-reachably via `run_wasm_labeler_score` (`libs/fauna-ffi`), which folds in the `Vec<Label>` → `ScoreEntry` mapping (`fauna_core::scoring::labels_to_score_entry`) — **and the re-score drain worker's Go `rescoreUnit` now has a `labeler:`-factor branch** (`rescore_drain.go`, Slice 3b) that inspects the transparent module, unseals the owner's content under the minted grant, runs `label()` via the shared FFI, and submits a `labeler:<hex>` tier-3 `ScoreEntry` — so a subscribed community labeler's score lands on the owner's `content_scores` (proven end-to-end by tier_3 `test_capability_labeler_drain.py`, Slice 3c). The nest never runs a labeler over a *user's* sealed content; the runtime lives in a shared FFI-reachable crate (priority #2) so the holder invokes it under the minted grant, mapping unsealed content → `LabelerPostInput` and `label()`'s `Vec<Label>` → one per-mille `ScoreEntry`. The whole execution boundary — decode, re-verify, clamp, run, decode the labels — is one function, `fauna_labeler::run_published_labeler`, and the one position where a nest runs it is placement's to name: a community room's home nest, over that room's messages, under the wrap its members seated it with, for the labelers the room names ([`content-scoring.md`](content-scoring.md) § The placement matrix, the *capability-holder* row; mechanism [`../behavior/community-rooms.md`](../behavior/community-rooms.md) § The three classes → *What the home nest does with its read*).

- **Artifact kinds — `wasm` | `list` | `text-model` (`wasm`/`list` ratified 2026-07-08, user-directed 2026-07-07: "a tier-3 labeler need not be code"; `text-model` ratified 2026-08-13 — D8's v2, below).** The published labeler carries an additive **artifact-kind** axis. **`wasm`** is everything above. **`list`** is a signed, versioned, size-bounded dag-cbor map `content_id → score` (integer per-mille ∈ [0,1000], the same range every bus factor emits; filter/boost *sign* comes from composition weights, § Composition) — a curated content list as a shareable tier-3 artifact. Evaluation is pure membership lookup: **no execution, no sandbox, no capability, no holder, no drain** (v1 is public posts only — a List over restricted content would leak what the curator could see, deferred; a `mail` List is rejected at publish). Because no holder exists, the **nest itself materializes** the List's `content_scores` rows — the same nest-side tier-3 shape as the `report:spam` aggregate: rows `(content_id, 'post', labeler:<id>, score, tier 3, actor_id = NULL)` are written at subscribe / resynced at republish / withdrawn at last-unsubscribe / joined on post arrival, and **only ever for ids present in `content_meta`** (the public/feed-participating gate — never a blind row for content this nest hasn't seen). `actor_id` is NULL because the bus's actor column is the content-at-rest *owner scope* (mail → recipient), which a public post does not have — feed composition JOINs by `content_id`. List factors stay **out of `model_versions`** (nothing to drain — the `report:spam` precedent). Inspect returns the raw artifact, so the client renders the exact id→score map before subscribing — the strongest inspect-before-subscribe of any kind. Decision record: the design spec's 2026-07-08 Block A revision entry (D8–D14).

  **`text-model` (ratified 2026-08-13 — D8's v2 half, its privacy-scrub design pass run by user pull; the nest half BUILT 2026-08-21, the subscriber half not yet — § Implementation status today).** A signed, versioned, size-bounded dag-cbor **Bernoulli n-gram count table** — `{more, less}` counts per n-gram plus the two class document-counters — scrubbed at publish per [`../behavior/topic-factors.md`](../behavior/topic-factors.md) § Publishing a trained factor (the mechanism owner: rebuild over public explicit examples only, distinct-document prune floor, informativeness-bounded vocabulary, full-vocabulary review). Unlike a List it **generalizes to unseen content**; unlike `wasm` it is **pure data, not code** — evaluation is the shared `fauna-text-model` scorer over the artifact's counts, deterministic by construction, **no sandbox, no fuel bounds**. **A subscription is evaluated at the subscriber's client, never the nest** ([`content-scoring.md`](content-scoring.md)'s placement matrix prohibits nest-side content evaluation even over public posts, and the MDA drain is mail-scoped — the subscriber's own client is the one position where post plaintext meets the artifact; the matrix's one nest position, a community room's home nest running the models the room names over that room's messages, is a room's choice and not a subscription — the *capability-holder* row): the factor rides the client-side zero-term compose seam exactly as a sealed tier-1 factor does — **no `content_scores` rows, no `model_versions` entry, no drain, no holder, and no grant** (the client scores only content it already reads), with the compound keyset cursor carrying pagination and the page-boundary honesty trade applying verbatim. Subscribe records the `labeler_subscriptions` row **only** (no `upsert_model_version`, nothing to materialize); the client fetches the raw artifact via `inspect` at feed (re)load and follows version bumps there. The kind axis stays per-version under one publisher identity, so a factor may upgrade List → Model as an ordinary version bump — **republish resync clause:** when a new version's kind is not `list`, the nest **withdraws** that labeler's materialized List rows. `content_kind: "post"` only at v1 (`mail` rejected at publish, the List's rule). Inspect renders the **full vocabulary** — n-gram, class direction, document count — so a subscriber sees exactly what the model matches on before subscribing; a client meeting an unknown artifact `version` (the tokenizer contract) treats the factor as **inert and says so**, never silently mis-scoring.

- **The attachment facet of the `label()` input ABI (ratified 2026-09-10 by the bytes-half design pass; BUILT the same day — § Implementation status today, leg 5).** A `wasm` module's input is its own **signed declaration**: `AlgorithmLabeler.input_schema` (`fauna_core::scoring::LabelerInput`) carries a fifth flag, **`needs_attachment_bytes`**, beside the four v1 declarations — and unlike them it selects the **shape** the host encodes. A module that does not declare it reads `LabelerPostInput` exactly as every module before the flag did; one that does reads `LabelerInputWithAttachments` — the v1 bytes **followed by** the facet, `Vec<LabelerAttachmentInput { mime_type, size_bytes, bytes }>`, the item's attachments in the author's order (BARE encodes a struct as its fields unframed, so the facet is an appended suffix: a module author decodes v1 and then the facet, and the one shared encoder `fauna_labeler::encode_labeler_input_for` is how every position produces it). Five rules, each pinned by a test rather than stated: **(1) Compat is additive on a signed record.** The flag is `skip_serializing_if` false, so every artifact published before it stays **byte-identical** and its stored signature verifies on a holder that knows the flag; a holder that predates the flag decodes a flagged artifact without it, re-encodes without it, and **refuses it as unverified** — at publish, or at inspect (`verified` reads false and subscribe stays disabled). That is the posture, not a wart: a holder that cannot supply what a module declared it reads never runs it without, and one that cannot show a subscriber what the module reads never calls it verified (`fauna_core::scoring::labeler_tests`, the three pre-flag-shape pins; `version-compatibility.md` § I4). **(2) A position that holds no bytes hands the declared shape with an empty facet** — the mail holder (`fauna_ffi::run_wasm_labeler_score`, whose attachment mapping stays deferred) and the post positions — never a silent v1 the module would mis-decode. **(3) Only a position inside a read fills it:** today one nest position, in its two acts — a community room's home nest, in the act that indexes each **message** and in the act that indexes each room-restricted **post** it stores, under the wrap its members minted ([`../behavior/community-rooms.md`](../behavior/community-rooms.md) § The three classes → *What the read covers*) — and only when a named labeler declares the flag; the blobs are opened once per item, handed to every declaring module, and dropped with the pass. The two acts seal their media differently — a message's attachments under the message's generation, a post's media under the post's own per-post key — and that difference is the whole of what varies: one loop applies the bounds for both (`fauna_labeler::build_attachment_facet`, whose callers supply only the fetch and the key model), so no position can hand a module a facet another position would have bounded differently. **No derived view carries bytes** (that doc's § *Forbidden*). **(4) The bounds are constants, never knobs** (`principles.md` § One configuration surface): `fauna_labeler::LABELER_ATTACHMENT_BYTES_MAX` (8 MiB per attachment), `LABELER_ATTACHMENT_FACET_MAX_BYTES` (24 MiB per item) and `LABELER_ATTACHMENT_FACET_MAX_CANDIDATES` (64 attachments per item) — the two byte ceilings applied by `AttachmentFacetBudget` on the **opened** length, never the author's declared size; an attachment over either byte ceiling — or past the candidate ceiling, or whose opened length cannot fit what is left of the item's budget, or one that does not open, or whose blob is absent — rides the facet with its declared metadata and **empty bytes**, withheld rather than truncated, so a module never classifies half a picture and can tell a withheld attachment from an empty one by `size_bytes`. **The ceilings bound the host's own work, not only what the module is handed** (the unbounded half, closed 2026-09-11): the list the loop walks is the item's own **sealed** body — a message's `attachments`, a post's media — which its author writes and which no send-time check can bound, precisely because it is sealed, so a candidate that cannot be admitted is never fetched and never decrypted. Three refusals do that work: past the candidate ceiling; once the item's budget is spent (`AttachmentFacetBudget::remaining() == 0` — never a failed `admit`, which a zero-length plaintext still passes, and which a budget with room left returns for a big attachment before admitting a smaller one after it); and when the sealed length less `SEALED_FRAMING_ALLOWANCE` already exceeds the remainder, since a seal is its plaintext plus framing under either key model. **The third of those is decided BEFORE the read, by asking the host how big the stored seal is** (the pre-read half, closed 2026-09-11): the loop takes a `sealed_size` probe beside its fetch, and a position that can answer refuses both sealed-length checks — the absolute ceiling and the item's remainder, together `sealed > min(MAX, remaining) + SEALED_FRAMING_ALLOWANCE` — with no blob read at all; on the nest the answer is the metadata row the upload route wrote from the bytes it stored (`db::blobs::get_blob_sizes`, one batched query per item), which is the host's own measurement and never the author's declared `size_bytes`. Until it landed, those two refusals ran only after `store.get` had read the whole blob, so an author naming distinct pinned uploads that each declare a few bytes over blobs at the upload ceiling was charged a full read for every one of them. ⚠ **An absent answer means “no answer”, never “refuse”** — a position may have no probe, and a blob may be stored with no metadata row behind it (the relay and backup write paths), so both fall through to the read and the honest facet survives; the same trap, and the same resolution, as the empty-refs rule below. The candidate ceiling is 64 because that is the nest's own per-record pin cap (`MAX_ATTACHMENT_REFS_PER_RECORD`, pinned equal to it by a static assertion beside it): an item naming more attachments than its record could have pinned is naming blobs that record never pinned. The facet a module reads is the same either way — every attachment still rides, in the author's order — and only the host's work differs. **Two further bounds close the residual those three refusals left** (2026-09-11), because all three key on *bytes handed over* and a candidate that never opens hands over nothing — so an author who named one stored-but-unopenable upload 64 times was charged 64 blob reads and 64 failed AEADs while the budget sat untouched at its ceiling. **First, one fetch and one open per distinct content address:** the loop remembers what resolving an address yielded — the opened plaintext, or that it does not resolve here — and serves every later entry naming it from that one resolution. A repeat is handed **the same bytes**, admitted position by position exactly as a wasteful host would admit it; it is never withheld for being a repeat, because the facet carries no identity and withholding would change what the module reads rather than only what the host paid. **Second, a message's candidates are bounded by what the record itself pinned:** an entry whose address is absent from that record's own `conv_attachment_refs` — the sender's plaintext list beside the sealed envelope — is not read at all. That is a **new withhold reason**, and the only one that turns on nest state rather than on the item: a blob that is stored, opens, and fits can still ride withheld because this nest never recorded the message as pinning it. ⚠ **An EMPTY refs set means "no record to check against", never "nothing was pinned"** — the field is additive and a sender may omit it, so a message from an app that predates it pins nothing on the record and must keep its facet; read the other way, the cross-check would silently blank the bytes for the honest case it exists to protect. The bound is the **message** arm's alone: `conv_attachment_refs` is the conversation kind's table and holds nothing for a room-restricted post's media, so the post arm keeps the candidate ceiling as its only count bound. **What remains after all of them** is honest to state: a sender that uploads, pins and names 64 *distinct* blobs each **within** the per-attachment ceiling that do not open still pays 64 fetches and 64 failed AEADs. The dedupe removes the one-upload-many-names amplification, the cross-check bounds distinct work to what this nest recorded, the pre-read probe removes every read a recorded size already rules out, and the decrypt moving off the async worker (below) bounds who pays for the rest; bounding that last remainder would need a refusal keyed on *work done* rather than on bytes handed over, which is not built — a blob inside the ceiling that does not open is indistinguishable, before the AEAD, from one that does. **And the decrypt does not run on the async worker:** the facet is built inline in the send path, and an AEAD over up to the per-attachment ceiling is CPU-bound work of the same class as the `wasm` run it feeds, so it goes to the blocking pool exactly as that run does — a slow or hostile open costs one pool thread, not every connection sharing a worker. The ceilings follow from the sandbox's 64 MiB host memory ceiling (the whole input lands in the module's linear memory in one `alloc`, so a declaring module sizes its memory for the facet plus its working set) — not from anything a deployment would choose. **(5) Every attachment kind rides, and the module decides by `mime_type`** — a video is over the per-attachment ceiling by construction and reaches a module as metadata. The inspect panel renders the declaration beside the four v1 flags (`LabelerInspectView::needs_attachment_bytes`; tui first, the other six apps by trickle-down — leg 5's per-app state). Rejected alongside: a second `label_bytes` export (an export name is neither signed nor shown to a subscriber, and a declaring module at a bytes-less position would be run *without* rather than handed its shape); an ABI version number on the metadata (says only that something changed where the flag says exactly what the module reads — the declaration vocabulary that already exists); truncating an oversize attachment (a classifier over half a picture is a wrong signal, not a weaker one).
- **The output half of the `label()` ABI — what a module emits, and how that shape evolves (ratified 2026-10-02 by the design pass; host half BUILT 2026-10-05, inspect surfacing not yet — § Implementation status today, leg 5).** A module's output is a positional BARE `Vec<Label>` — `fauna_core::scoring::Label { category, confidence: f64, source: LabelSource }` — and positional means **nothing about it is additive**: a `LabelSource` variant or a `Label` field added on one side makes the other side's decode fail outright or mis-read every later byte, and the failure reads as a broken module, never as a newer one. Before this ruling no stamp of any kind stood between module and host (the input side is declared by the five flags above; the output was described only as "the v1 shape"), so the `LabelSource` ledger line's *ladder* ground named a version that did not exist. **Ruling: the output shape is the module's own signed declaration, beside the input one.** `AlgorithmLabeler.output_schema` (`fauna_core::scoring::LabelerOutput`) carries one field, **`label_abi: u16`** — the revision of the `Label` record the module emits — and `fauna_core::scoring::LABEL_ABI_CURRENT` is the revision a build reads (1 today). The field is additive on the signed record exactly as the fifth input flag is (rule (1) above, verbatim): absent reads 1 and `skip_serializing_if` omits 1, so every artifact published before it stays byte-identical and verifies, and a holder that predates the field refuses a stamped artifact as unverified rather than running it. Three positions read the stamp, and each answers differently: **(i) the runner** — `fauna_labeler::run_published_labeler_bare`, the one execution boundary — reads it after the signature verify and **before compiling or running the module**, so before the BARE decode can be reached: `label_abi > LABEL_ABI_CURRENT` is refused with the typed `LabelerAbiNewer { declared, supported }`, never a decode error — the ladder's "read before the strict decode, or the refusal reads as corruption"; **(ii) the subscriber at inspect** — `LabelerInspectView` renders the declared revision beside the five input flags, and a revision newer than the app's own `LABEL_ABI_CURRENT` reads **inert and says so** with subscribe disabled, the `text-model` bullet's unknown-`version` posture, never a silent subscription whose every drain item the holder would refuse; **(iii) the nest's publish gate stores it unexamined** — the `text-model` `version` rule again: the revision is a contract between the module and whatever runs it (the mail holder, a room's home nest, a self-serving native app), and a nest refusing a revision it does not know would make an older nest refuse a newer client's artifact (the gate still compiles the module and verifies the signature, as before). **Raising it:** a new `LabelSource` variant or a new `Label` field raises `LABEL_ABI_CURRENT` and rewrites the `LabelSource` ledger line in the same commit, and the host keeps every earlier revision decodable for the rest of the major — a module declaring `label_abi = k` is decoded with revision k's shape and mapped forward (the within-major bidirectional rule, [`version-compatibility.md`](version-compatibility.md)). That is the **ladder** ground of [`transport.md`](transport.md) § Schema and forward-compat discipline, rule 3 answer 4, for `LabelSource`: the stamp is the signed `label_abi`, read before the strict decode. The codec itself stays BARE, and why is [`serialization.md`](serialization.md)'s to say (the one sanctioned `serde_bare` boundary, because `Label.confidence` is a float). **Why a revision number here, where the input ruling above rejected one:** the input's flags select among shapes the *host* composes, so a number would name a menu item less exactly than the flags do; the output has no menu — the module emits fauna's own `Label` record at one revision of this section, and the revision is exactly what it emits, nothing finer exists to declare. The input rejection stands and does not reach the output. Rejected alongside: a module-exported version (an `abi_version` global or function) — an export is neither part of the signed metadata nor shown at inspect without parsing the module (the ground the second export was rejected on above), its refusal would surface only inside a holder after the fetch, and one module would carry two declaration surfaces; re-encoding the output as canonical dag-cbor so the ordinary carrying and collapsing arms apply — canonical dag-cbor forbids floats and the float is this boundary's reason to exist, so that route re-rules `serialization.md`'s float decision rather than evolving the ABI, and is not taken; freezing the output at revision 1 by decree — "how a label was derived" is a vocabulary that will grow, and a frozen record would route the growth through `category` strings.

## Distributed report sharing (ratified 2026-07-07, user)

The per-item, cross-user signal — "100 people flagged this same email as spam → strong spam signal" — is a **voluntary, explicit, k-anonymized report share**, distinct from the model-baseline aggregate (`mail-spam.md` § Cold start, Path 2). A user who flags content (starting with mail marked spam; the same shape extends to other factors later) may **opt in** to sharing *the fact of the flag* — never the content, never their identity beyond their own nest. Ratified invariants:

- **Opt-in, default off, per user** — an app toggle mirroring `mail-spam-contribute-baseline-toggle`; opting out stops future contributions. (One configuration surface: app UI → nest state.)
- **k-anonymity before existence.** A per-item aggregate becomes readable *anywhere* (including by the local admin) only once ≥ k distinct local reporters exist (k ≥ 3, the `BASELINE_MIN_CONTRIBUTORS` pattern). Below k, individual reports live only as caller-scoped rows on the reporter's own nest.
- **Only `(content-hash, factor, count)` crosses any boundary** — never reporter identity, never content bytes. Content identity is a canonical hash computed where plaintext legitimately exists (the MTA perimeter for mail, pre-seal; posts already carry a content id) and stored as floor metadata.
- **No central registry — peer-to-peer aggregate exchange only.** Aggregation is per-nest; cross-nest movement rides the federation channel (its own dedicated `fauna.federation.reports.{exchange,export}` kind — `federation.md` § the federation-call table, Report exchange/export row), each nest holding only the aggregates of peers it chose to talk to. No party can accumulate a global corpus of user judgments to later sell — structurally, not by policy.
- **Peer counts never scale local consensus** (the hostile-signer invariant, `federation.md` § Federation residue surface — the Report exchange/export row, with the reason in *The reputation leg is ruled removed* → *What outlives the leg*): a peer nest's claimed count collapses into a single non-scaling corroboration bucket, because `nest_id`s are self-minted and free; only *local* k-anonymized reporters scale the signal.
- **The aggregate is a transparent tier-3 factor** on the scores bus (e.g. factor `report:spam`), applied through the **user's own thresholds** — it informs, it never compels (the § Boundaries no-social-censorship rule stands; mail-perimeter policy remains tier 2's).

**Implicit signals cross a user boundary only as k-anonymized per-item aggregates (the shared-engagement stance — REVISED 2026-07-12, user; supersedes the 2026-07-07 explicit-signals-only absolute).** Implicit engagement signals (views, dwell, watch-time, skips) **never cross a user boundary as per-user event streams, raw timings, or identity-attributed records** — but a user MAY opt in (default off, per user) to contributing **client-derived, coarse per-item verdicts** (watched-to-completion / skipped) to the same voluntary, k-anonymized per-item aggregate plane as reports: only `(content-id, factor, count)` becomes readable, only at ≥ k distinct local contributors, under every invariant in this section verbatim. Cross-user training signals are therefore: explicit voluntary artifacts (the model baseline, per-item reports) **plus these k-anonymized implicit aggregates — never a per-user behavioral corpus.** A shared engagement model trained on identifiable behavior (the TikTok shape) remains **out of scope by design**; Q2's rationale (raw engagement is admissible *only* inside tier-1 factors that are private and never shared) still governs everything below the aggregate plane. Mechanism owner: [`../behavior/engagement-cues.md`](../behavior/engagement-cues.md) (the `signal:*` factors, D6).

**Adaptation of shared signals = composition (+ faded merge where the format supports it).** A subscribed tier-3 model or report aggregate is adapted per-user by **composing** it — weighting it alongside the user's tier-1 factors (§ Composition) — and, for model formats with a merge operation, by a **faded read-time merge** (the Bayesian `merge_scaled` cold-start prior is the exemplar). Opaque artifacts (WASM labelers) are never mutated per-user; personalization composes *around* them. No per-user fine-tuning of shared artifacts is planned.

**Build:** fanned out 2026-07-07 (tracked internally, leg 7). **The mechanism is ratified (2026-07-07, same track): [`../behavior/report-sharing.md`](../behavior/report-sharing.md) is the owning feature doc** — canonical mail report-hash, report/peer schema, k-gate choke point, score-from-count curve, client + federation wire kinds, opt-in/opt-out semantics. This frame keeps owning the six invariants above; on conflict about an invariant, this doc wins.

## Boundaries with the product invariants

- **One configuration surface.** All three tiers are configured through the apps, persisted in nest state — the user picks their tier-1 models / thresholds / custom feeds and subscribes to tier-3 communities in their app; the admin sets compulsory tier-2 policy in the admin app. No config-file/env knob (product invariant).
- **User controls their data.** Tier-1 models are the user's, sealed at rest in both modes, revocable, and never readable by the box owner except under a capability the user themselves minted (and can revoke).
- **Social moderation stays a personal filter (no nest-wide social censorship).** `moderation.md` is iron-clad that no social post is removed for everyone and there is no admin "remove for all" surface. This frame preserves that: for **social** content a tier-2 authority produces a **transparent label**, and *enforcement* (collapse/hide) is the **user's own threshold** on that label — the compulsory shape of tier 2 is scoped to the **mail perimeter / ingest** (quarantine / reject at DATA-time), to the **one narrow legal-obligation case** (genuinely illegal content — a transparent, appealable, audited extension of `obligation_action_records`, never a general admin lever; § Resolved design decisions Q5), and — **planned, direction user-ratified 2026-07-29** — to **region blocking**: a region authority's transparent, permanently-public published algorithm applied **app-side** in that region (visible block + the algorithm's reason, region-scoped, never a nest-wide removal, no admin lever; mechanism owner [`../behavior/region-blocking.md`](../behavior/region-blocking.md), Status: partially-specified — the shared region/authority plumbing is resolved and built, this content-blocking plane is not).
