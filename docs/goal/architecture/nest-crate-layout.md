# The nest's crate layout — one crate today, a wide crate graph as the cut lands

Owns: nest-crate-layout
Status: ratified 2026-10-30 as the target state — the module map, the target crate graph and the order of the cuts, from the design pass that answered the owner's question; nothing is cut yet, and the first cut carries its own measurement before the second starts (§ *Implementation status today*).
Authority: the crate boundaries of the nest server's own code — which crate a nest-side module belongs to, the dependency direction between the nest crates, how the nest's cargo features reach across them, and the measurement that admits a cut. Not: where shared Rust goes (a module that belongs in a `libs/fauna-*` crate goes there first — that rule is older than this doc and outranks it), the feature spine itself ([`dynamic-features.md`](dynamic-features.md) § The cargo feature spine), or any machine's build layout.

Last verified: 2026-10-30 (the map taken on the tree of that day; `just nest-crate-map map` regenerates it).

## Why

Every nest build ends in one rustc: `bins/fauna-nest` is a single library crate, and a library crate is the unit rustc compiles, so its frontend — type check, borrow check, the monomorphization walk, crate metadata, coherence — runs as one job however many cores the build holds. Measured on the Linux development machine, that frontend is about 70 of the nest library's 89 s, and rustc's parallel frontend (`-Zthreads`, adopted there at four threads) recovers about a third of it and no more; on the Windows machine the same one rustc is the long pole of every nest flavor, at about one busy core on a wider grant. Past that, more cores reach a nest build only through the crate graph: several nest crates cargo compiles side by side, and a touched file that rebuilds one small crate instead of the whole server.

A split pays twice over for the test build, because the nest's own unit tests are 41 % of its lines (224,202 of 552,788 on 2026-10-30) and today compile into one test harness beside the library; after a cut each crate's harness builds in its own rustc, beside the others. The integration harnesses under `bins/fauna-nest/tests/` (320 of them) are already one crate each and are untouched by the cut except for linking a few more rlibs.

## The map (2026-10-30)

`just nest-crate-map map` lists every top-level module of `bins/fauna-nest/src` with its production lines (the `#[cfg(test)]` items and `tests/` files stripped), its feature gate, and which other top-level modules it references (`crate::x` paths, `use crate::{…}` lists, `super::x` from a top-level file), then the strongly connected components of that graph. The scan is textual — path sites, not symbols — so it is the map a cut starts from, not the compiler's word. What it says of the tree of 2026-10-30:

- **313 top-level modules, 322,641 production lines** (545,970 with tests), plus `lib.rs` (4,860 lines: the HTTP router, the RPC router's registration list and `start_server`) and `main.rs` (1,958).
- **One cycle holds 188 modules and 289,389 production lines — 90 % of the crate.** The other 125 modules are small and already acyclic: leaf utilities (`api_error`, `config`, `ssrf`, `blob_store`, the rate limiters) and the many `*_test_hook` modules.
- **Two hubs make the cycle.** `routes` (5,101 production lines) defines `AppState`, the one struct every handler takes — 217 modules reference `routes`, 419 sites name `AppState` — and `AppState`'s fields are typed by 23 other modules, so `routes` references 62. `db` (94,199 production lines, 29 % of the crate, 121 files, 122 inherent `impl CacheDb` blocks) is referenced by 149 modules and references 43 back: 55 of its outward sites are `segments::records_db`, the rest the bridges' schema and helper functions, `backup`'s prune scheduler and constants, `mail_enable`'s port reconcilers, `moderation_withhold`, and single constants of a dozen modules.
- **The other hubs are small and point downward**: `rpc_errors` (in-degree 102), `rpc_router` (93 — its handler type takes `Arc<AppState>`), `bridge_method_allowlist` (70), `api_error` (62), `segments` (40), `bridge_routing_handlers` (39, the mail stack's root at 11,166 lines), `principal_handlers` (38 in, 39 out: half a type every handler family implements, half a dispatch table over every handler family).
- **The registration seam already exists at the top.** `lib.rs`'s `build_rpc_router` is a list of one `x_handlers::register_x_handlers(&mut b)` call per module, and `build_router` mounts each module's HTTP routes the same way — the shape a crate graph wires its leaves with.
- **By codegen weight the picture is flatter than by lines.** A `-Zdump-mono-stats` dump of the nest library (`just nest-crate-map mono <dump>`) attributes 74 % of the estimated code size to dependency generics instantiated by nest code (`std` 20 %, `fauna_protocol` 10 %, `tokio` 10 %, `fauna_cbor` 10 %, `serde_ipld_dagcbor` 6 %); of the nest's own quarter, `db` is a fifth (4.9 % of the whole), `federation_handlers` 1.4 %, `nostr` 1.1 %, `bridge_routing_handlers` 1.0 %. So `db` is line-heavy and codegen-light — what it moves off the tail is frontend time, which scales with lines and items, not LLVM time.

## The cut

The target is a wide graph: a thin base, the database, one kernel crate holding `AppState`, then as many sibling crates as the handler families give, each compiling at once, and the binary crate on top doing nothing but wiring. The membership is the `PLAN` table of `scripts/nest-crate-map.py`, and `just nest-crate-map plan` scores it against the live tree: per-crate production lines and every **back-edge** — a reference from a crate to one it may not depend on — with its site count. A back-edge is work the cut must land (a move, an inversion, a trait); zero back-edges is a buildable graph. On the tree of 2026-10-30 the full plan carries 499 back-edge sites over 42 crate pairs.

The rules the plan rests on, each a decision a cut applies without re-asking:

1. **Shared Rust first.** Before a module is placed in a nest crate, ask whether it belongs in a `libs/fauna-*` crate; protocol-shaped types a bridge's nest side carries (a relay event, an outbound-queue item) go to that bridge's `libs/fauna-bridge-*` crate, not to the nest kernel.
2. **`AppState` stays one struct, in core, and every field's type is a core, base, db or `libs/fauna-*` type.** A field whose type's module is kernel-sized stays whole in core (the limiters, the registries, the OAuth runtime, `segments`' placement managers). A field whose type drags a whole subsystem into core — `backup::service::BackupService` (9,032 lines), `web_content`'s service, resolver and holder (5,640), `federation_pool::FederationChannelPool` (2,879, tied to `federation_handlers` by 22 sites), `plugin_runner::PluginRunner`, `push::PushService` — is reached through a trait object core defines (`Arc<dyn …>`), the implementation in its sibling crate and the `Arc` wired by the binary; which of these five actually leave core is the second cut's measurement, not a rule here (§ *The cuts, ranked*).
3. **The bridge sub-states stay in core, typed over core.** `state.rs`'s `NostrState`, `BlueskyState` and `ActivityPubState` are `AppState` fields; the bridge-module types they name today (`nostr::relay_endpoint::NostrRelayEvent`, the gift-wrap and bunker limiters, `bluesky`'s OAuth client handle) move down — to core where they are plain event or limiter types, to `libs/fauna-bridge-*` where they are protocol shapes (rule 1) — so a bridge crate depends on core and never the reverse.
4. **A sibling crate registers itself; the binary wires it.** Each sibling exports `register(&mut RpcRouterBuilder)` and an HTTP `router() -> axum::Router<Arc<AppState>>`, and `fauna-nest`'s `build_rpc_router` and `build_router` call them in today's order — the lists in `lib.rs` already have this shape, module-qualified. `principal_handlers` splits the same way: `PrincipalHandler`, `PrincipalBinding`, `PrincipalCaller`, `resolve_principal`, `dispatch_principal` and `admin_twin` (what 38 modules take from it) stay in core; the table that names every family's `principal_*_handlers` (what it takes from 39 modules) becomes a registration the binary assembles.
5. **Inversions over the database.** `db` calls nothing above it: a constant it reads from above moves down beside its reader; a function it calls from above (`backup::version_prune::schedule_version_auto_prune`, `mail_enable`'s port reconcilers, the bridges' `apply_schema` and `db_helpers`) is either database code misfiled above — it moves into the db crate under the same feature gate — or a callback the caller supplies (a schema-hook list `CacheDb::open` runs, a prune scheduler the caller passes).
6. **Paths keep working through re-exports.** `fauna-nest`'s `lib.rs` keeps `pub mod db`, `pub mod routes` and the other names as re-exports of the crates that now own them (`pub use fauna_nest_db as db;`), so `fauna_nest::db::…` in the 320 integration harnesses and `crate::db::…` inside a crate that re-exports it stay valid; call-site churn is not part of a cut.
7. **Visibility widens at the crate edge only.** A `pub(crate)` item used from another crate becomes `pub`; one used only inside its crate stays. Where a widened surface must not become API, it is `#[doc(hidden)]` or behind a sealed trait. 910 `pub(crate)` sites exist today, 91 of them in `db`.
8. **Features propagate from the root.** `fauna-nest` keeps every flavor feature as the root of the spine ([`dynamic-features.md`](dynamic-features.md) § The cargo feature spine): `nostr = ["dep:fauna-nest-nostr", "fauna-nest-core/nostr", "fauna-nest-db/nostr"]` and the same shape for `bluesky`, `activitypub`, `test-hooks` (the optional `fauna-nest-test-hooks` crate plus core's test-hook fields) and `payments`; a deep nest crate's feature is opt-in and reaches only the `cfg` sites that crate holds. `store-safe` stays the root's complement feature, unchanged.
9. **Tests travel with their code.** A module's `#[cfg(test)]` items move with it into its crate's harness; `test_support` splits like `principal_handlers` — the fixtures over `AppState` and `CacheDb` stay in core under its `test-helpers` feature, the mail-stack fixtures (`seed_recipient_seal_key`, the spam baseline helpers) go to the mail crate's.
10. **The two nest crates that already exist are not seams of this cut.** `libs/fauna-nest-http` is the nest's HTTP surface as apps consume it (paths, bearer, error shapes) and `libs/fauna-nest-supervisor` the service shells' port logic; together 2,434 lines, std-only or app-facing by design. They sit beside `fauna-nest-base` as its peers, nothing server-side moves into them, and `api_error`'s shape stays the nest's own unless it proves identical to `fauna-nest-http::error`'s.

## What a cut costs

- **Dependency generics instantiate again per crate.** 74 % of the nest library's codegen is dependency generics; each crate instantiates what it uses. In the dev profile rustc shares upstream instantiations with downstream crates (`share-generics` is on at `opt-level = 0`), so the inner loop pays little; the release profile does not share, so the image and installer builds do more LLVM work in total, spread over more parallel rustcs.
- **Whole-crate passes shrink, per-crate passes multiply.** Crate metadata (26–27 s of the nest library today), coherence (15–17 s) and the monomorphization walk (22–24 s) are per-crate whole-crate passes that scale with the crate's items — the reason a touched file in a smaller crate rebuilds faster — but every crate pays its own metadata and coherence pass.
- **More link inputs.** Each of the 320 integration harnesses links the nest's rlibs; link is 1.3 s today and grows by the rlib count, not by their size.
- **One hash move.** The first cut changes the nest library's `-C metadata`, so every seeded build directory recompiles the nest once and every integration harness relinks once; a fresh crate starts its incremental cache cold once.
- **A wider grant, or oversubscription.** `-Zthreads=4` and crate parallelism compose only when the grant has the cores: two nest rustcs at four threads each on a four-core grant is the oversubscription the eight-thread reading showed (+10 % on a wide pass). The measurement reports each cut with and without `-Zthreads=4`.

## The cuts, ranked

Ranked by frontend time moved off the tail per back-edge site the cut must land (`just nest-crate-map plan` prints the sites; the counts are the tree of 2026-10-30):

1. **`fauna-nest-db` out (cut 1).** 97,667 production lines, 30 % of the crate, every `impl CacheDb` already inside it. 116 back-edge sites: `db → core` 88 (55 of them `segments::records_db`, which moves whole; 7 `backup` constants and the prune scheduler; 6 `moderation_withhold`; the rest single constants), `db → mail` 14 (`mail_enable` 6, `dav_pre_split` 3, `email_handlers` 2), `db →` the bridges 6 (schema and helpers under the feature gates, rule 5), `db → social/admin/files` 8. What it buys: a touched file outside `db` rebuilds 70 % of today's frontend; the nest's unit-test build becomes two harnesses side by side (29 % and 71 % of the lines); the cold library build changes little, because the rest's frontend starts when `db`'s metadata is ready and `db`'s codegen overlaps it. Every later cut needs this one below it.
2. **The three bridge crates and `test-hooks` out (cut 2).** 25,085 production lines together; needs rules 3 and 4 (the sub-state types moved down, `bridge_legs` and `bridge_schema` to the binary) and the schema hooks of rule 5. Back-edges: `core → nostr/bluesky/activitypub` 20 (all `state.rs` and `routes`' post fan-out), `social → nostr` 23 (`federation_handlers` and `nest_sync_worker`, the post fan-out again), the bridges `→ nest` 21. What it buys beyond the lines: a feature-less build no longer compiles a line of a bridge, and `cargo build -p fauna-nest --features nostr` pulls one crate.
3. **The sibling handler crates (cut 3): mail, social, files, web, admin.** 118,353 production lines over five crates that compile at once; the bulk of the remaining back-edges (`core → social` 64, `core → mail` 37, `web → mail` 31, `social → files` 22, `admin → mail` 19 …) are the trait objects of rule 2 and the dispatch tables of rule 4. The order inside the cut is by what each sibling's back-edge count costs against its lines: `social` with federation folded in, then `mail`, then `files`, `admin`, `web`.

The fallback is written here too: **if cut 1's measurement shows under 10 % on both the inner loop and the test harness, a split does not pay** — the verdict is recorded in this section with its numbers, the remaining cuts are dropped, and the width question goes back to the parallel-frontend rows.

## Measuring a cut

A cut's effect is idle cores, so it is timed only under the quiet-window rule, on the Linux development machine's probe method: the base tree and the cut tree are two probe checkouts of the same commit; each rep runs, at one fixed four-core grant, the cold nest build (`build --locked -p fauna-nest --features test-hooks,nostr`) and the cold nest unit-test harness (`test --no-run --locked -p fauna-nest --lib --features test-hooks,nostr`, both crates' harnesses after the cut), then the inner loop — one touched file in the cut-off crate, one in the remaining core — recording wall time, mean busy cores over the pass and peak rustc RSS, with and without `-Zthreads=4`, two alternating reps per arm.

Written down before the first rep, as the rule asks: the expected effect of cut 1 is 25–30 % on the inner loop for a file outside `db` and 20–30 % on the harness build; the cold library build is expected inside ±5 % and is reported, not claimed; the noise floor is the same arm's spread, under 10 % on a quiet host. A spread wider than the effect stops the run.

## Implementation status today

- **2026-10-30 — the map and the plan exist; no crate is cut.** `scripts/nest-crate-map.py` (`just nest-crate-map map|plan|mono`) is the map, the plan's membership and the scorer; the numbers in this doc are its output on that day's tree. `bins/fauna-nest` is still one library crate; `libs/fauna-nest-http` and `libs/fauna-nest-supervisor` are the only nest-named crates beside it (rule 10).
- **Cut 1 and its measurement, then cuts 2 and 3, are queued as implementation rows carrying these rules**; each lands its half of this section when it closes, and cut 1's numbers decide whether cuts 2 and 3 run (§ *The cuts, ranked*, the fallback).
