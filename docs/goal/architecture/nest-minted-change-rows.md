## The nest-minted row classes

  - **(7) The two nest-minted row classes the flip left unsettled — the covered-folder re-home, and a set's served-era WebDAV rows once serving ends (ruled 2026-09-30, design pass; refutable downstream; (a) BUILT 2026-10-02, (b) and its (i), the unstamped pseudo-device row (ruled 2026-10-02), BUILT 2026-10-02 — [`writer-signed-change-records.md`](writer-signed-change-records.md) § Implementation status today).** Both are rows the nest mints or holds for the owner without any writer's key, and both close by the one idiom ruling (1)(ii) already set for the conflict winners: **the owner signs the statement of a row the nest mints or holds, exactly as the nest will store it, and the nest verifies each signature at the door as at record** (`crate::change_signature::verify_carried` over the statement rebuilt from the row under the set's STORED nonce, the signer's cert by reference on a home nest) **and stores the row with the pair.** The request carries the signatures — never a new writer, never a new class exemption — and the statement's `device_id` stays the row's own, because the chain binds the signer to the *actor* and the roster check is by actor.
    - **(a) The covered-folder re-home — `fauna.backup.custody.materialize`'s folder arm; the ceremony is [`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § Re-seed, phase 3.** Three rulings. **(i) The target set is created by the shared create helper, never by the nest inside materialize.** Every set the owner's nest lists has a custody entry at least as old as the set (the *Custody shape of the set nonce* sub-bullet, (d)); the arm's own in-transaction folder create (`sync_storage.rs::materialize_folder_custody` → `create_folder_with_options_in_conn`) breaks that rule, mints a set with no nonce, and is RETIRED: the ceremony's seed-holding process — the app on a desktop, before it starts the agent's job; the app itself on a phone — creates each delivered covered folder's target under its display name through `fauna_client_folders::set_lifecycle::create_set` (custody first, nonce minted, the entry reaching every owner host through the account-state plane (`__config` when ruled) and the agent through its own re-resolve of custody at the job's start) — **unless the owner's custody still holds a live entry for that name**, which after a box loss it does (nothing deleted the lost set): then the target IS that set re-homed, re-created at the nest under that entry's nonce with no second mint, because two live entries for one name resolve to the earliest (custody (c)'s pick) and a fresh mint would leave the device signing under the lost set's nonce while the nest holds the new one, every re-homed row refused `signature_invalid` (found by the after-loss e2e, 2026-10-02; a deleted set's entry is retired, so its name mints afresh) — and the arm materializes only into a set the nest lists that carries a stored nonce, refusing a missing one typed (`target_missing` — the remedy is the caller preparing the set) and a nonce-less one as `stored_set_nonce` already does. The freshness rule and the torn-run "ours" classifier are unchanged: a target the previous attempt prepared and half-filled resumes, and a fresh empty folder the owner created by hand adopts. **(ii) The ceremony signs every re-homed row.** The delivery leg already holds the store's rows and the host's signer (`fauna_sync_engine::reseed::ReseedDelivery::with_record_signing`); per delivered folder set it signs the statement of each row the arm will mint — the target's nonce (resolved by the target's display name, as every other record's is), the owner as `actor_id`, the row's `path_hash`, `manifest_hash`, `change_type = "create"`, `size_bytes` (**the manifest's `total_size`**, read on both sides from the manifest the statement's `manifest_hash` names — the size ruling below), the source's `path_sealed` verbatim, no `content_key_version`, no `thumbnail_hash`, no `derived_through`, `is_resolution = false` — and the request carries them **in pages**: `signer_key` plus the signatures keyed by `path_hash`, the page size one Rust constant, both additive fields on `CustodyMaterializeRequest`. The nest re-homes exactly the rows whose signature is carried and verifies, one transaction per page, refusing the page whole on a row that does not verify (`signature_invalid` / `author_mismatch`, the record door's own codes) or names no custody row, and the reply gains `remaining` so the driver loops until nothing is owed; a folder-set request carrying no signatures is refused `signature_required` — the arm never mints an unsigned row again, which is what retires the flip's stop-gap refusal. **Where the statement reads its size (ruled 2026-10-02; BUILT 2026-10-02): `size_bytes` is the manifest's `total_size`, and both halves read it from the manifest the statement's `manifest_hash` names** — the leg from the manifest its store holds (`CustodianStore::read_manifest`), the arm from the manifest blob this nest holds (the one `decode_manifest` its charge derivation already runs, `crate::backup::custody_charge`) — and the arm mints the row with that figure. Three reasons. It is the file's logical size exactly as the source's own engine declared it (the engine records a change's `size_bytes` from `uploaded.manifest.total_size`), so a restored row reads as the source row did. It is bound to the statement already: the manifest is content-addressed by a hash the signature covers, so the two sides cannot hold different figures for one row. And both sides already decode that manifest, so no wire field and no column is added. Never the custody row's `size_bytes`: on a reserved destination set that column is the nest's derived CHARGE (`upsert_backup_custody` — the manifest blob plus every distinct chunk, as stored), a metering figure the quota legs credit back and no reader shows as a file size (the after-loss e2e measured 238 charged against 39 declared for one row, every other field of the statement equal); and never the store's recorded source size (`HeldRow::source_size_bytes`, which drives the pull's diff and the delivery's report). The refusals: a custody row whose manifest this nest does not hold or cannot decode refuses the set `custody_incomplete` naming the row — the manifest was held when custody was recorded (the charge derivation refuses `backup_bytes_not_held` otherwise) and GC keeps a live custody's manifest, so this is a torn delivery or corruption and re-delivery is the remedy; a held row whose manifest the store cannot decode holds the set `rehome_unsigned` with the reason, as a malformed store row does today. **Rejected:** a `size_bytes` carried on each `RehomeSignature` (an additive wire field for a figure both sides already hold; owner-attested but unbound to the manifest, so a leg could sign a size the manifest contradicts and the nest would mint it, and a missing field needs a refusal arm of its own); a declared-size column beside the charge in `backup_custody` (an at-rest migration storing what the same row's manifest already carries, NULL for every row delivered before it); the leg computing the nest's charge (couples the client to the nest's metering rule, and mints the charge as the file's size — the second defect the e2e showed). The statement's `device_id` is the owner's **re-seed pseudo-device id**, `fauna_core::label_custody::reseed_pseudo_device_id(owner)`, derived beside the WebDAV one, computed identically on both sides and refused at `fauna.sync.register` like it: a re-homed row must not carry the ceremony device's own id, because every engine treats a row under its own device id as a self-echo and downloads nothing for it (`SyncEngine`'s apply fold), so the one device that ran the ceremony would never hydrate the folder it restored; and it must not carry the nest's identity (today's value), which no client holds a handle to at that point. The pseudo-device is a label the row carries — never a registered device, never an exemption: the row is owner-signed. **(iii) What the driver refuses.** A host whose signer or nonce source cannot sign for a folder set holds that set's materialize with the reason — a typed `ReseedOutcome` gap, `is_whole` false — and never sends an unsigned request, exactly as the capability host holds a write that finds no usable signer. **Rejected:** the owner's engine re-recording the delivered custody through the ordinary record door (the design row's option (b)) — that door derives `path_hash` from a plaintext `path`, so a host would have to open every sealed name it re-homes, impossible for a name sealed under a group generation the host no longer holds and needless when the signature covers the sealed bytes verbatim; it also loses the arm's one-transaction atomicity and its nest-side freshness check, and no engine runs for a folder no device syncs. Also rejected: keeping the nest's identity as the `device_id` and plumbing it to the driver; a nest-minted nonce for the target (trust-on-first-use, (k)); a class exemption for re-homed rows (a nest-mintable unsigned class in a live folder is the plant-before-bind hole reopened). **Out of scope, unchanged from the arm's declared shape:** a re-homed row of a formerly content-keyed source still carries no generation stamp — the custody row has none to re-home — so its bytes open only where the owner's custody retains the source's generations. **The nest-held pull-back's re-home (2026-11-05):** its rows come from the holder nest's own `custody.list`, not from a store this device filled with rows it verified, so the owner's signature there attests the owner's acceptance at the ceremony's confirm, under the bounds [`client-device-custodian.md`](client-device-custodian.md) § Client-device custodian (pull) → *Restore* → *What the pull-back trusts the holder for* rules — the one owner of that residual; nothing here changes.
    - **(b) A set's served-era WebDAV rows once serving ends — the owner ADOPTS them in the same gesture, and the flag cannot fall while one is unadopted.** Ruling (1)(i)'s exemption is read live (`fauna_protocol::sync_row_verify::RowReader::is_webdav_pseudo_row` over the set's `webdav_enabled` — over custody's serve window once (ii) is built), so on the day the owner turns a set's WebDAV serving off every pseudo-device row would stop verifying and every file the DAV plane ever wrote would vanish from every reader while its bytes stay on the nest. A reader cannot narrow the exemption to "rows recorded while served" — when a row was recorded and when the flag flipped are both the nest's word — and keeping the exemption for ever on a set that was once served hands the nest the planting power of residual (vi) without end. So closing the plane is a custody move: **the shared disable composition (`fauna_client_folders::orchestration::FoldersAuthor::serve_disable`, which every app's `folder-webdav-toggle` drives) first signs every ADOPTABLE WebDAV pseudo-device row of the set in place — heads, superseded versions and strict deletes alike, adoptable by (i) below, the statement being the stored row with its own pseudo `device_id` — through a new owner-only kind, `fauna.folders.served_rows.adopt`, paged like (a) and keyed by `seq`, whose nest half verifies each signature as at record and fills the row's `signature` / `signer_key` columns without minting a row, moving a seq or touching exactly-once; then flips the flag — and the flip OFF is REFUSED `served_rows_unadopted` (count carried) while any adoptable pseudo-device row of the set is unsigned ((i)).** A DAV write that lands between the sweep and the flip is one more row to adopt on the composition's own bounded retry, and the retry converges because the flip is what stops the plane. No torn state exists on either side of the flip: before it the rows are exempt (a signature on top changes nothing), after it every one verifies as the owner's; there is no launch-resume leg, no engine pass, and nothing to do for a folder no device syncs. Adoption is deliberate laundering of the served window and is stated as such: a row the nest planted while the set was served (residual (vi), accepted) becomes the owner's when the owner closes the plane — the same window, now bounded by the flip instead of open for ever — and the version-history projection keeps the served era whole because superseded rows are adopted too. Serve-OFF on a never-served set is unaffected (no such rows). **Rejected:** refusing the rows (hides the user's own files — the bytes are not lost, but every app reads the folder as emptied); a "recorded while served" reader rule (unverifiable, above); a class exemption for ever (widens (vi) without end); adopting after the flip with a retry leg (a WebDAV-only folder has no engine to retry in, and the launch resume would owe a change-log walk per formerly served set for ever, or a custody marker for one gesture); re-recording new owner heads instead of signing in place (moves every seq, drops the served era from the history, races the frontier).
      - **(i) The unstamped pseudo-device row — the adoption signs only the honest recorder's row shape, and nothing a stamp does not bind (ruled 2026-10-02, design pass; adversarially reviewed the same day — two blocking findings re-ruled, six corrections folded in; refutable downstream; BUILT 2026-10-02 — [`writer-signed-change-records.md`](writer-signed-change-records.md) § Implementation status today).** Adoption signs rows unopened, and a row that verifies as the owner's is offered the owner-family roots by two arms: after the flip the set is owner-only and the ordinary owner-only read offers them before any stamp is consulted (`FileDownloadKeys::owner_open_roots`, (8)(c)'s "ordinary owner-only read"), and while the set is still content-keyed (D)'s read offers them to an unstamped record that verified as the holder's own (`content_open_roots` → `prebind_owner_roots`). Ruling (10)(c) — built 2026-10-02, before the adoption shipped, as this ruling requires — binds a STAMPED record's manifest and chunks to its generation's content key whoever signs it. An unstamped, non-delete pseudo-device row is bound to nothing: a lying nest that plants one naming a manifest the owner sealed under its owner root in another set would, once the row is adopted and the flag is down, have that manifest opened under the owner root here — ruling (5)'s copied-record class, with the adoption as the signing door. And the stamp binds only the bytes: the sealed label carries its own generation, and a label with none is opened under the owner-family roots for any row signed as the current identity (`label_open_roots`' `gen: None` arm, no `owner_signed_record` gate); a thumbnail opened under the owner key whatever the stamp (the Media machine's thumbnail read, until 2026-10-22 — it now opens under the row's stamp, [`../ui/media.md`](../ui/media.md) § Encryption at rest → *A thumbnail rests as its file rests*); so a stamped planted row carrying a generation-less `path_sealed` or a `thumbnail_hash` copied from another owner set would become the owner's for good through the same door. Three rules. **(1) The adoption signs exactly the ADOPTABLE rows — the honest DAV recorder's row shape, no wider — by one function, `fauna_protocol::sync_writer_sig::served_row_adoptable` over the served row: the row is a STRICT delete (`change_type == "delete"` AND no manifest) or a non-delete carrying a `content_key_version`; its sealed label's generation is present; and `thumbnail_hash`, `derived_through` and `is_resolution` are unset — every field the recorder never sets, by construction.** The function is called by the composition's sweep, by the nest's adopt handler — which refuses a page naming a row it rejects, whole — and by the nest's count, which fetches the set's unsigned pseudo-device rows and applies the same function in Rust: one home, no SQL mirror. A delete is strict because a delete that carries a manifest is not inert — the version history lists every row with a manifest whatever its `change_type`, and the agent's restore admits an unstamped version signed as the current identity — so an adopted "delete" with a manifest would be a restorable, owner-signed, unstamped head; a strict delete opens nothing, and a tombstone the nest planted while the set was served is residual (vi)'s accepted word, so adopting it changes no reader's view. A row the function rejects is skipped by the sweep and never signed; after the flip every reader judges it as what it is — no longer exempt (`RowReader::judge`: `is_webdav_pseudo_row` is false once `webdav_served` is off) and unsigned (`Refused(Unsigned)`) — so the planted manifest, name or thumbnail opens nowhere, and a stale reader that still believes the set served sees residual (vi)'s window and nothing more. The sweep returns the skipped count in the composition's result (a log line and the tier_1 proof; no UI: on an honest nest it is zero by (3), and on a lying one the vanishing of a row the nest invented is the correct view). What an adopted stamped row can open is bounded to **a generation this set's custody entry holds**: a served set with no sharing group keys its serve custody by the set's name, so generations of an earlier set of the same name would be reachable if custody kept them — the name-reuse case is a residual below, not closed here. **(2) The flip refusal counts exactly the adoptable rows still unsigned — `served_rows_unadopted` carries the count of the set's pseudo-device rows with no signature that (1) would sign — so an unadoptable row never holds the flag.** The count is the honest contract and no more: the refusal runs on the nest, so a lying nest can refuse the flip for ever whatever it counts — residual (ii)'s wholesale withholding, no new power, and the owner's remedy is the same (the set's bytes rest on a box the owner no longer trusts). What the rule buys is that an honest nest never strands an owner behind a row the client will not sign, and that the composition's bounded retry converges on one count both sides compute from one function; the DAV recorder has stamped every content row since it was written, so no legacy population exists to strand. **(3) The recorder refuses, beside its `path_seal_required` refusal and of the same kind — a guard that fires only on a wiring bug — a non-delete record without a stamp (`fauna.bridges.content_key_version_required`), a delete record carrying a manifest, and a sealed label whose generation is absent (the nest parses the label header without opening it, as `filesync_handlers` already does).** A served set is never public (serve-ON is refused on a public-audience folder and declassification is refused while served — `folder_handlers.rs`'s update arm, both directions), so the MDA seals every write under the set's current generation and records that generation (`backend.go` `Create`; a copy carries the source's), seals the label under the current generation, and records a delete with no manifest and no stamp; the honest DAV population is adoptable by construction, and the refusal makes it provably so — (1)'s skip and (2)'s exclusion then fire only against a lying nest, which the recorder cannot stop and (1) does. One honest write the recorder could not catch, because it arrives stamped, is the MDA's to refuse: a copy or move of a row that lists with no generation — an owner-device head not yet re-sealed by the served re-seal walk, which runs after serving starts — would stamp the new row with the current generation although its manifest rests under the owner root, a row no reader opens under (10)(c), and a MOVE would then tombstone the real source: a user-data loss on an honest path. So `copyOrMove` refuses a nil-stamp source as its read refuses it (`errNoGeneration`, the 503 `readFileBytes` answers), before the keys are unsealed and before any record or tombstone, and a copy keeps the source's own stamp (BUILT 2026-10-09, proven by `copy_move_test.go`; not gated on the adoption). **Residuals, since ruled:** *the exemption's flag was the nest's word* — `ReaderBinding::webdav_served` is fed from `FolderSummary::webdav_enabled` until (ii) is built, so a nest that keeps answering `webdav_enabled` after the owner's flip keeps residual (vi)'s window open on every reader that believes it, the label and thumbnail channels of exempt rows included; the window is bounded by the flip on an honest nest, and bounding it on a lying one needed the served state carried in the owner's custody — ruling (ii) below; *name-keyed serve custody* — the name-reuse reach of (1)'s bound — ruling (iii) below (both ruled 2026-10-02). **Rejected:** adopting the unstamped row and leaving (10)(c)'s reader to refuse it (it does not — an unstamped record is exactly the one (10)(c) leaves to the owner root); lifting the recorder's metering `is_delete` (`change_type == "delete"` OR no manifest) as the delete test (admits the delete-with-manifest row above); counting every unsigned pseudo-device row (strands an honest owner behind a row the sweep must not sign); a SQL mirror of the predicate beside the function (two homes for one test — the label-generation check alone needs the header parsed); opening each row on the client before signing it (a read of every served-era row per flip, for a check the row's shape already states and (3) already makes provable); refusing deletes too (an unsigned delete is refused after the flip and the path's last adopted head comes back — every DAV-side delete resurrected); a reader rule "an unstamped pseudo-device row is never admitted" (a third class in `judge` for a row (1) already leaves unsigned, and a stale served flag would exempt it first anyway).
      - **(ii) The served state is the owner's word — custody carries the serve window, and every judgement a client makes about it reads custody, never the nest's row (ruled 2026-10-02, design pass; adversarially reviewed the same day in two passes — three blocking findings re-ruled, fourteen corrections folded in; refutable downstream; BUILT — § Implementation status today).** Today the served state has one source and it is the nest's: `FolderSummary::webdav_enabled` feeds the reader's exemption (`ReaderBinding::webdav_served` — `fauna-sync-engine`'s `engine_lifecycle.rs`, and `fauna-client-sync`'s `row_judge.rs` for the projection readers), the engine's live binding and the Media page's resolver (`custody_channel_for` answers the serve pseudo-channel iff the row says served, `resolve_engine_key_binding`'s served arm and `engine_lifecycle.rs`'s owner-only shortcut branch on it, `BindingBasis` rebuilds the edge on it; `retired_serve_custody` answers iff it says not), the served-set walk's launch list (`converge_served_sets`), the owner row's toggle on every app (the shared `fauna-devices-machine` snapshot transcribes it) and the MUA URL row's `serves_any_webdav_set`, and — the widest — the `WebdavKeysBlob` reconciler, which provisions the MDA with the content keys of every owned set the roster flags served (`webdav_provision.rs`, `reconcile_webdav_keys_blob`'s `webdav_enabled` filter — for a shared set, the real channel's whole generation history). So a lying nest holds three powers through one bit: residual (vi)'s window with no end (it keeps answering served after the owner's flip, and every reader keeps exempting its pseudo-device rows, label and thumbnail channels included); **the content keys of ANY content-keyed set the owner holds, a shared set it never served included** — flagged served, the set's generations ride into the MSEK-sealed blob at the owner's next reconcile and the MDA opens them on the nest's own box at the user's next DAV or mail login, so rule #7's blast radius ([`../behavior/webdav-server.md`](../behavior/webdav-server.md) § Key model) widens from "the explicitly-served folders" to "whatever the nest flags"; and, as (iii)'s compounding case, a live binding onto a deleted namesake's serve generations. Five rules. **(1) Custody carries the serve window.** `FolderKeyCustody` gains `served_at: Option<u64>` and `unserved_at: Option<u64>` (micros, the flipping device's clock — the unit `rotated_at` and `retired_at` use); **the entry is served while it is live AND `served_at` is present and above `unserved_at`** (`FolderKeyCustody::is_served`, one predicate at every site, as `is_live` is; liveness is in it because a delete retires the entry and writes no `unserved_at`, and a tombstone of a set deleted while served must never read served); both stamps join to the later — the pair has the shape of (l)(v)'s `retired_at`/`lifted_at`, so a stale device's copy of either flip cannot undo the later one and a replayed envelope cannot re-serve or un-serve — but **a tie reads NOT served**, where (l)(v)'s tie reads live: each pair resolves its tie to its safe side; and a serve-on stamps strictly above the entry's `unserved_at`, a serve-off strictly above its `served_at`, so a clock that stepped back between two gestures still orders them (two devices flipping opposite ways at once resolve by wall clock, last writer wins — the two-copy intent problem has no better answer, and the loser's gesture is one flip away). **`served_at` is written by the owner's serve-on gesture and by NOTHING else — never from the nest's flag, not once, not one-shot** (rule (5) says why); `unserved_at` by serve-off and by the launch pass's one arm (3). **Serve-on** writes `served_at` in its one custody write BEFORE the nest flag — for an unshared set the write that already mints or reuses the genesis (`serve_enable`'s `key_named_set`), for a shared set a write that today does not exist (the closure is empty when `channel_id` is `Some`; the `content_keys` precheck stays), so a set custody calls served always holds keys and the reconciler's `ServedSetKeysMissing` becomes a sync lag, never a state; **serve-off** writes `unserved_at` in the ONE custody write that already rotates (`serve_disable`'s `rotate_set` write), AFTER the adoption and after the nest has accepted the flip — custody keeps saying served across the sweep-and-flip rounds, so a DAV row landing between a sweep and a refused flip stays exempt until the next round adopts it, and the flip is still what stops the plane. The custody identity is unchanged: `channel_id` stays the pseudo-channel from the first serve-on or paywall (`paywall_set` keys an unshared set there too) or the real channel from a bind, and the two stamps say whether that identity's DAV plane is open now — keys at the pseudo-channel never meant served, and now nothing reads them as if they did. **(2) Every client judgement reads custody.** The reader's exemption: `ReaderBinding::webdav_served` is the entry's `is_served` — on the engine side from the custody `engine_lifecycle.rs` already loads for the nonce (the owner's live pick by name, a member's entry at the real channel), on the projection side through the source `row_judge.rs` already consults (today a `SetNonceSource` asked only for sets that carry a signed row, with an early return for a projection that carries none; it becomes a binding source — nonce AND served state — asked for every set the projection names, since the set whose rows are all unsigned DAV rows is exactly the one that needs the answer), and for a cross-nest member from its own entry (`resolve_foreign_binding`'s hard-coded `false` goes). The live binding and the resolvers: `custody_channel_for` takes custody beside the summary and answers from the owner's live entry (`channel_id` and `is_served`) or the member's real channel — still the one shared resolution, now over the owner's word — and with it `resolve_engine_key_binding`'s served arm, the owner-only shortcut and `retired_serve_custody` (answers for an entry that is not served); `BindingBasis` drops the flag (no binding reads it), and `FolderEngineKeys` carries the stamps (4) so the agent's custody re-read is the rebuild trigger when they move; "content-keyed with no group" means the name's live entry holds the pseudo-channel and is served, "owner-only plus retired candidates" means it is not. The `WebdavKeysBlob` reconciler provisions **the sets the owner-scoped list names AND custody calls served** — owned ∩ `is_served`, never a member entry (a member's entry carries the owner's stamps under (4), and the member's blob sits on the member's box, outside rule #7's radius) — and the nest's flag selects nothing; the served-set walk's launch resume walks the same sets. The owner row's toggle and the MUA URL row paint `is_served` (one field on the shared snapshot `fauna-devices-machine` builds, joined from the custody the app already loads for the Media resolver — the seven apps re-read the snapshot, not the roster), so the state the user acts on is the state the compositions act on. The peer leg needs nothing new: `fauna_peer_share::judge_peer_row` judges with the receiver's own reader, which this rule feeds, and admits an exempt row only on the channel's proof as before. **What keeps reading the nest's flag:** the nest's own gates — the MDA's folder filter, `webdav_record_change`'s door, the mint gate, the update door's refusals (serve-on on a public or metadata-only folder; a public or metadata-only change while the flag is on), the count behind `served_rows_unadopted` — which are the nest's word about its own plane (correct on an honest nest, the adversary's on a lying one, and nothing a client should ever have believed); and `FolderSummary::claims_unsealed`'s "a served folder never arms", a read that can only REFUSE an unsealed public read, which a lying nest achieves by withholding anyway. **(3) Disagreement is resolved at the owner's launch pass, only ever in the ≤-intent direction, and the two provisioned copies are reconciled there too.** The pass is `FoldersAuthor`'s launch resume (the neighbour of `resume_pending_removals` and `converge_served_sets` — the author holds the files client, the custody store, the mail store and the group seam; `reconcile_set_custody` has no group handle and no MSEK, so the arms are the author's), over custody read with `load_for_write` (a fresh fetch, so a lagging device acts on the plane's state, not its cache), per owned set the nest lists, after (g)'s custody reconcile and before the two provisioning reconciles below. *Custody served ∧ flag off* is the crash state of BOTH gestures — a serve-on that wrote custody and died before the flag, a serve-off whose flip landed and died before the custody write — and the state a nest lying "off" produces; the three are indistinguishable and one answer is safe for all: **unserve in custody** (the serve-off tail: `rotate_set` + `unserved_at` in one write, `is_served` re-checked inside the closure so two devices never rotate twice for one flip, the envelope republished for a shared set). The interrupted serve-on reverts (the user flips again; exposure ≤ intent), the interrupted serve-off completes, the lying nest achieves a denial — bounded to one rotation per owner serve-on, since only the gesture writes `served_at`. *Custody not served ∧ flag on* is a lying nest, a device whose custody has not yet synced a sibling's serve-on, or the honest race the review found (a lagging device's late serve-off overtaking a sibling's re-serve-on, so the blob that sibling provisioned carries a set custody no longer calls served): **the flag is left alone** — a push from a lagging device would undo a sibling's gesture, and every judgement of the owner's already follows custody — **and the provisioned copies are brought to custody.** So the `WebdavKeysBlob` reconcile joins the launch pass unconditionally on every MSEK-holding device (`NoMsek` → nothing to do; a desired-state atomic replace, one list and one provision — today its only production caller is `serve_set`, which is why the race above could stand) and re-runs on the custody nudge; and so does an **envelope reconcile** for every shared set the owner holds: fetch the stored envelope, open it under the current epoch through a new `open_envelope` on the `FolderGroupCrypto` seam (today it has only `seal_envelope`), and **publish the JOIN of custody and the envelope only when custody is strictly ahead** — never a stale bundle over a newer one, which a lagging device would otherwise push and the members' writes would then fail the nest's monotonic floor; **only an envelope this identity signed is joined** (the owner's other devices sign as it — ruling (11)(b)): one any other key signed is replaced by custody alone, never joined (its generations would be laundered into the owner's re-signed envelope) and never left standing because it names custody's live nonce as retired — **skipping a channel with a staged pending removal** (its Remove may be merged and its generation unpublished; publishing custody's keys under the post-Remove epoch would hand the departing member the window) and skipping a channel whose envelope does not open at this epoch (nothing is published on a failed read). That heals the serve-off that died between its custody write and its republish (members would otherwise keep exempting on an honest nest) and the serve-on that died before publishing. **The adoption never runs outside a served window:** `serve_disable` sweeps only when custody calls the set served — on {custody not served, flag on} it pushes the flag off and signs nothing (a refusal `served_rows_unadopted` surfaces as the error it is), a branch no UI offers (defence in depth for a direct caller): since the toggle paints custody, the gesture a user is offered on such a set is ON, and ON is the owner's word opening the window — on a lying nest the rows it planted while it lied become exempt by the owner's choice to serve, exactly residual (vi), and a following OFF adopts them inside a window the owner declared; a lying "served" alone launders nothing. The nest's update door refuses a public or metadata-only change while its flag is on, so in this state the user reaches that change by ON then OFF (the honest serve-off clears the flag) — one extra flip, bounded to the migration day (5) and a lying nest. **Accepted, stated:** a sibling's launch pass inside the one-RPC window between a serve-on's custody write and its flag unserves it (≤ intent, the toggle visibly flips back); a device whose custody lags the plane despite the fresh read (the nest withholding the newer custody — residual (ii)) provisions the blob without the sibling's newly served set until the next pass or nudge on a current device (a denial, no wider); a serve-on from a device that does not hold the group cannot publish, and the unserve arm's rotation on such a device waits for the envelope reconcile of a device that does; and **members' exposure changes:** today an honest nest discloses `webdav_enabled: false` on every member row, so every member — same-nest or cross-nest — refuses the owner's pseudo-device rows and the DAV plane of a shared served set is invisible to them; under (4) members read the owner's stamps and admit the served era, which **extends residual (vi) to members for the window the owner declares** — the correct view of a set the owner serves, and bounded as the owner's is — and, since a member's stamps arrive only in the envelope, a nest that withholds the owner's republished envelope holds that member in the window: the member-side (vi), as wide as lying the flag to it would have been, and accepted with it. **(4) Members and the wire.** `ContentKeyEnvelopePayload` (a map) gains the two stamps beside the generations and the nonce; `merge_received_keys` joins them into the member's entry (to the later, so an envelope the nest replays cannot move the window and a member's copy only advances to what the owner last said); the owner publishes on every serve flip of a shared set — serve-off already republishes, serve-on publishes inside its custody step, before the flag (a publish that fails before the flag is reverted by the next launch's unserve arm) — and the envelope reconcile of (3) catches what a crash left out. `FolderEngineKeys` carries the stamps beside the nonce on every arm — the agent's custody re-read is then the binding-edge rebuild when the stamps move and the roster row does not. A cross-nest member is the same envelope; the MDA needs none — its capability is the blob, which (2) scopes. **(5) Compat, and the migration that is a user gesture.** At rest additive on `FolderKeyCustody` under the 2026-09-24 baseline (`#[serde(default)]`, emitted only when set — a never-served entry keeps its bytes; `FoldersConfig::merge` joins both to the later, so the blob arm and the plane arm share the statement, P1); wire additive on the envelope payload's map and on `FolderEngineKeys`; no re-seal, no data loss. **There is no automatic stamping of a set served before the build.** An entry written before the build carries no stamps and reads not served; a set the nest flags served while custody says not served is the lying-nest state by definition after the build, and any arm that stamped it served on the nest's say-so — one-shot or not — would hand a lying nest exactly the key lever this ruling closes (after the build, `bind_set` and `paywall_set` still mint keyed, stamp-less entries, so "keyed and stamp-less" never means "served before the build"). The migration is therefore the owner's — **one flip ON per set served before the build** (serve-on is idempotent on the nest: the update door accepts an already-on flag, `key_named_set` reuses the key, the walk skips heads already at the current generation, the blob replace converges) — and its day-one cost is stated whole: at the first launch on the new build the blob reconcile drops every pre-build served set, so **the mount goes dark for them** (the MDA holds no key; a DAV write fails closed) until the flip; every reader refuses their DAV rows and their engines bind owner-only, so new owner writes seal under the owner root until the flip; **a mixed fleet flaps** — a device on the old build provisions the blob from the flag, a device on the new one from custody, each launch overwriting the other — so the release note says every device updates together; and to spare **two full re-seals** per such set (the retired-candidate reseal walking the back-catalogue onto the owner root, then the flip walking it back), the desktop agent's `reseal_predecessor_sealed` HOLDS for a keyed, stamp-less entry whose roster row says served — a nest can only delay a re-seal that way, the safe direction, and the hold ends with the stamps. Nothing is lost in the window: rows and bytes stay on the nest, and the bearer-only agent needs no migration leg (it loads the custody the gesture wrote). **Rejected:** a bool (a flip-flop no join-only door can land — (l)); the serving generations' range instead of two stamps (a window per serve era, re-derivable from the rotation history only with a start marker per era — the stamps are that marker, and a reader needs only "now"); pushing the nest's flag to custody's state on every disagreement (a lagging device undoes a sibling's serve-on; with every client judgement on custody the flag is irrelevant to the owner's hosts, which is the point); adopting on the unserve arm (a serve-off that died after the flip already adopted, a serve-on that died before the flag has no rows, and a lying nest's rows must never be signed); keeping `resolve_foreign_binding`'s `false` and the member rows' non-disclosure as the members' answer (the honest answer only while the flag was the nest's word; a served shared set's DAV plane invisible to its members was a withholding, not a design); a nest-side "served since" stamp (the nest's word again); a client-side `WebdavKeysBlob` filter on the nest's flag alone (closes the key lever and leaves the window); a one-shot stamping arm gated on an account-level marker (trust-on-first-use at the one launch a lying nest needs, permanent once taken — the user's single flip costs less than that residual); an envelope reconcile that republishes on any difference (a lagging device would push a stale bundle over a newer one); a third toggle state for "served at the nest only" (a new UI variant on seven apps for a state the ON gesture already resolves). **(6) A re-publish that advances no epoch reaches a member through the nest's echo of the envelope itself, and a generation a member cannot open is a request, as a row it cannot verify already is (ruled 2026-10-09, design pass; refutable downstream; built 2026-10-09 — § Implementation status today).** Rule (4) puts the stamps on the envelope, and (11)(b) names what makes a member fetch it on a quiet channel — a moved nonce echo, or a `signature_invalid` request from the engine host — beside the two the add path has, the join-time ingest and an applied commit ([`mls-group-key-material.md`](mls-group-key-material.md) § Admitting a member). A serve flip moves none of them: `serve_enable` seals under the current epoch and posts no commit, `serve_disable` rotates and re-publishes the same way, and so does the launch pass's envelope reconcile (3). Measured 2026-10-09: on tui and macOS the owner's first share-plane advertisement after the flip takes over the epoch and posts a commit, which the member's poll applies — the stamp arrives by accident; a windows owner advertises nothing, and its member never learns the set is served. The serve-off half is worse: the member keeps the pre-rotation generation, every owner upload after the flip fails closed at its content open, and the floor echo (`FolderSummary::content_key_floor`) holds its own seals behind a generation it has no way to obtain — the floor edge is a rebuild over the same custody, never a fetch. Two rules. **(a) The nest echoes the envelope's digest.** The envelope row keeps, beside the blob, a blake3 digest of the blob exactly as `content_key.put` stored it (the owner-signed bytes), written at every put, and `fauna.folders.list` projects it as `FolderSummary::envelope_digest` (wire-additive; both arms, as the floor rides). The echo is **only ever a reason to fetch**, the nonce echo's posture exactly: a member takes nothing from it — the envelope it then fetches verifies under the owner's signature and is ingested by (11)(b)'s rules as before — so a lying echo buys one fetch per check and never a key, a stamp or a nonce, and a withheld echo is the withheld envelope of (3)'s member-side residual, no wider. The sink remembers, **in process memory**, the digest of the envelope it last fetched for each channel — beside the request stamps it already remembers; a launch re-fetches every set anyway, so custody carries nothing new — and owes one fetch when the echo differs; a first sighting with nothing remembered owes nothing, as a request older than the session owes nothing. One mechanism covers every re-publish that advances no epoch alike — serve-on, serve-off's rotation, the reconcile's join, a re-mint the nonce echo already covers — for one 32-byte field on a list reply the member reads once a minute. **(b) The engine host asks for a generation it cannot open.** The request stamp of (11)(b) (`SyncEngine::set_custody_refetch_request`, `FolderKeyReader::request_refetch`) is written also when a served batch holds an admitted row, on a set this account does not own, whose `content_key_version` names a generation custody holds none for — the same device-local row, coalesced per burst, read by the same sink arm. This is the backstop that reaches a cross-nest member, who has no row on its own nest to echo a digest (the nonce echo never reached it either), and it closes the rotation half on every member whether or not (a) has fired: a row a member cannot open is a request, not a stuck engine. **Rejected:** *a commit per serve flip* — the epoch is MLS's membership and key-material clock, not a notification bell; it would cost a self-Update commit per flip on every served shared set, a take-over first on a channel the owner does not author, re-enter the member-takeover race by design, and leave the reconcile's join with no trigger; *lazy convergence on the first refused row* — the serve stamp would reach a member only when a DAV row happens to arrive, a member that only reads would paint the set unserved for ever, and the rotation half is unreachable that way without (b), which stays the backstop and never the mechanism; *a nest-minted sequence or `updated_at` echo* — a nest-chosen number where an owner-derived one exists, and one the member cannot check against the bytes it fetched; *persisting the remembered digest in custody* — buys nothing over a launch that re-fetches anyway, at the price of an at-rest field. **The e2e witness** stays `test_webdav_shared_set.py`'s barrier — the member's engine restarts on the served stamp before any mount write — which under this rule is met within one re-fetch check of the flip on every owner app, share plane or none. **Accepted, stated:** a cross-nest member learns of a serve-on only through (b), when the first DAV row reaches it; a nest that lies the echo every minute costs the member one fetch a minute.
      - **(iii) Name-keyed serve custody — a tombstone lends nothing to the name (ruled 2026-10-02, same pass; BUILT 2026-10-11 — § Implementation status today).** Verified against the tree: no rename kind exists (`FolderKeyCustody::name` is write-once, (a); the nest addresses a set by `(name, owner)`), so the "renamed" half is void — a future rename kind must move the entry in place, nonce and all, and re-point its pseudo-channel the way `migrate_set_identity` re-points a bind, and is a design pass of its own; delete RETIRES the entry and purges nothing ((e), (l): `set_lifecycle::retire_live_entries`, the keys kept for no-data-loss), and a re-create mints a fresh nonce-bearing entry with no `channel_id` beside the tombstone (e). The reach: a by-channel read joins the keys of the LIVE entries holding the channel, and of all of them only when none is live ((l)(i), `custody::joined_keys`). So a re-created set that is served again — `key_named_set` puts the pseudo-channel on the fresh live entry — never joins the tombstone's generations: rule (1)'s bound holds, and an adopted row stamped with the dead incarnation's generation opens nowhere ((10)(c)). The one arm that reaches the tombstone is the none-live fallback, and `retired_serve_custody` takes it for a re-created set that is NOT served (the fresh entry holds no channel): the dead namesake's serve generations come back as the new set's read candidates — inert today, since every consumer of the candidates (`FileDownloadKeys`' offered roots for stamped versions, the label roots, `reseal_predecessor_sealed`'s verify) opens only an admitted row and the re-created set admits only rows signed under its own nonce ((g) never re-signs an incarnation retired before the pick into it: `set_nonces_for` leaves such an entry out), and under (ii) a lying "served" no longer turns those candidates into a live binding — but a wrong answer that switches the reseal pass on for every re-created set, and a door the day any reader admits anything else under them. **Rule: a set's retired serve candidates are resolved over the set's OWN entries — every same-name entry not retired before the earliest `created_at` of the entries carrying the live nonce (the pick, the live nonce-less key holders (c) and (g) leave beside it, and the twins an identity move retires, (l)(ii)) — never over an entry retired before that; and when the name has no live nonce-bearing entry at all (a pre-ruling nonce-less live entry), the candidates come from the LIVE entries only, never a tombstone. This is the selection `set_nonces_for` already makes for the retired nonces, lifted into one helper both take, so nonces and candidates cannot drift — with the one difference stated: `set_nonces_for`'s nonce-less arm keeps tombstones as migration input, which is right for a nonce and is exactly the lending (iii) forbids for a key.** (l)(i)'s none-live arm is unchanged for the by-channel reads it was ruled for; a set's candidates are a by-name question and never take it. Shared with `set_nonces_for`, and accepted as it is there: the clock-skew edge of a delete on one device stamped above a re-create on another (the same owner's devices, seconds apart), which includes the tombstone as the name's own — a retire floors only on the entry's own lift, never on a sibling's `created_at`; and an entry with no `name` is invisible to any by-name selection. Accepted, stated: the deleted incarnation's rows and bytes stay on the nest under generations the owner's custody keeps for ever (no-data-loss), reachable through the tombstone by channel and through nothing else. **Rejected:** purging serve custody at delete (no-data-loss, (e)); a nonce-keyed pseudo-channel so a re-create derives a fresh channel (the set would change identity at serve-on, the blob and the MDA address by name, and (k) rejected the same move for the nonce); leaving `retired_serve_custody` on the fallback (above); a narrower "live pick plus twins retired after it" selection (drops the live nonce-less key holder's served-era generations — a read loss).
