## The convention — convention 10 (== point 10)

10. **An app launch is isolated from the box it runs on (ratified 2026-07-17).** A test's result must never depend on what the dev machine's desktop session happens to be doing. A harness-launched app inherits its launcher's whole world — env, display, buses — so every channel through which the box can reach into the app is closed at launch, and the closure is **the default**, opted out of explicitly by the few tests that must drive the channel themselves. The axes today, all in `drivers/linux.py::launch` (linux is where a real desktop session is richest; the same principle binds any app whose driver launches a local process): a fresh `XDG_DATA_HOME`/`XDG_CONFIG_HOME`, a per-launch keyring namespace + private credential store, a per-launch agent port, a throwaway Xvfb display (`_headless_render_cmd_env` — also why the app can't steal focus on a real Wayland/RDP session), and a **private D-Bus session bus** (`_wants_private_bus` → `drivers/session_bus.py`). One carve-out, narrow and pinned by a test: a caller that passes its own `DBUS_SESSION_BUS_ADDRESS` owns the bus (`helpers/tray_bus.py`; the tray tests must drive host-present *and* host-absent, which no fixed default expresses). **`use_real_keyring` rides that carve-out, and is no longer one of its own (ruled 2026-09-15).** That mode's subject is a real Secret Service *implementation* — libsecret over D-Bus to a real `gnome-keyring-daemon`, unlocked-collection semantics, slots that survive a force-quit + relaunch — and until 2026-09-15 it "kept the ambient bus because its subject is the real Secret Service", i.e. it reached the **developer's desktop keyring**. That was the one channel left open, and it was machine-wide, not test-wide: `gnome-keyring-daemon` aborts on a client that vanishes mid-session, which is what a force-quit test does, systemd restarts it with the login keyring **locked** (it has no password; only a desktop login supplies one), and from that second every other client of that keyring loses its secrets until a human logs in. The subject never needed the developer's daemon, only *a* daemon, so the test's `LibsecretCredStore` now runs one **for itself**: a private `gnome-keyring-daemon` on a private session bus over a throwaway keyring, unlocked non-interactively (`--login` with the password on stdin, then `--start`, `drivers/secret_service.py`), handed to the launch as its bus; the pytest-side seed/sweep/read helpers (`tests/common/keyring.py`) take that bus's address and have no ambient-bus path at all, so no harness code can reach the desktop keyring by construction; a daemon that dies mid-test is restarted over the same keyring with nothing lost; and the driver **refuses** the mode without a caller-owned bus rather than fall back to either the ambient bus or an empty private one (`_secret_service_bus_missing`, pinned in `tests/test_linux_bridge_env.py`; the daemon mechanics in `tests/test_private_secret_service.py`). The machine precondition shrank from "an unlocked desktop session" to "`gnome-keyring` and `dbus-daemon` installed", so these tests no longer skip on a headless box. **Windows adds four axes of its own (the first two 2026-07-22).** (a) The sync agent's named pipe is per-*user*, so an app launch reaches whatever agent holds it — the installed product's, or a sibling dev checkout's — which is why a windows launch sets `FAUNA_E2E_SYNC_PIPE` to a per-launch name and talks only to the agent it spawned; mechanism owned by [`apps/sync-agent.md`](apps/sync-agent.md) § Per-launch pipe isolation. **RULED 2026-09-21 — that isolation is the DEFAULT on windows, not an opt-in, because the rule this convention states is *never the box's agent*, never *no agent*.** Until then the windows app started no agent at all under a bridge unless a suite carried `real_sync_agent`, which read as caution and was in fact a coverage hole with a measured cost: linux and tui both spawn the real agent binary as an isolated per-launch child under e2e (`apps/fauna-linux/src/sync_agent.rs` skips only the machine-global systemd user-unit surface; `drivers/tui.py` sets this very pipe by `setdefault`, on win32 too), so windows alone never exercised the production sync bring-up — and since the machine's named `sync_devices` row is registered by that bring-up's renewal-grant mint and by nothing else on an agent-hosting platform ([`apps/sync-agent-credentials.md`](apps/sync-agent-credentials.md) § Implementation status today), **no windows e2e could assert a named-row invariant at all**: `test_sign_out_device_roster.py`'s mid-assembly case had to be weakened from an exact roster to a subset the day before. The posture is now one of three, session-wide because the windows app is session-scoped, and it is chosen by **markers, never a knob** (a test-harness axis, so the no-configuration-surface rule does not reach it): the default isolates; `real_sync_agent` *without* `isolated_sync_agent` keeps the machine-global per-SID pipe for the installer full journey, which tests the INSTALLED product and must rendezvous where the installer put it; `no_sync_agent` withholds the pin entirely for a suite that must spawn nothing. **What makes the isolation structural rather than conventional** is that the app's own gate is keyed on the pin — `App.xaml.cs::HydrationSessionEnabled` requires *both* `FAUNA_E2E_SYNC_PIPE` and `FAUNA_E2E_SYNC_AGENT_BIN` — and shared Rust spawns **nothing** when a pinned binary misses, where an unpinned spawn walks its candidate list down to `%ProgramFiles%` (`agent_spawner::WindowsDetachedSpawner`). Teardown needed nothing new: that spawner is deliberately not `CREATE_BREAKAWAY_FROM_JOB`, so the agent sits inside the job object point 9 already binds the bridge → FaunaApp → agent tree to. The one real cost is that `fauna-sync-agent.exe` builds on every windows e2e invocation once the default is in force, which is why the collection-time prebuild hoist and the launch env read the posture from **one** predicate (`conftest.windows_isolates_its_sync_agent`) — the two spellings drifting apart is exactly how a cold cargo build lands inside a test's own budget. **Implementation status: BUILT 2026-09-22 — `conftest._WINDOWS_ISOLATED_AGENT_IS_DEFAULT` is `True`, so a windows e2e launch naming no posture spawns and provisions its own agent.** The default sat staged for a day on a gap that was windows' own, and whose first reading was wrong: an app-log bracket (`[sync-agent] session start ENTER` → `BUILT` → `INSTALLED` → `content-key bindings pushed`) is emitted entirely before `SyncAgentSession.StartAsync` is awaited, so its silence about `fauna.sync.register` was evidence of nothing; with the shared provisioner instrumented at its mint choke point (`fauna_client_sync::agent::start` logs the decision and the id at `info`), the mint was plainly decided and reached under the right id, and `sync.register` then failed ~5 s later with `The connection to the nest was lost`. **The cause was a per-app divergence:** windows built its provisioner on a one-shot `new FfiNestClient(nestUrl, secret)` that was never `Connect()`ed — that constructor does not open the socket, so every request waited out its kind's deadline — where macOS builds its on the app's live connected client (`APIClient.syncAgentProvisioner` → `ensureNestConnected()`). windows now does the same: `NestRpcClient.BuildSyncAgentProvisionerAsync` and `FolderEngineKeyBindingsAsync` ride the login's own cached connection, and `SyncAgentSession` holds no client of its own at any of its three former sites (the provisioner build and both content-key resolves). **Witnessed end to end:** `test_relaunch_device_accrual.py` (both cases, three cold relaunches each, roster unchanged — one stable named row per actor) and all three `test_sign_out_device_roster.py` cases pass `--app windows` with the named-row barriers running rather than skipping. **Blast radius, measured on a bounded set before any sweep (`test_feed.py`, `test_folders.py`, `test_filesync_bind_history.py`, 42 cases):** with the default off, 37 passed and 5 failed; with it on, the first run showed a real regression the agent exposed — every `test_folders.py` wizard case timed out on `wizard-next-button`, because a registered machine is now a device place on the create wizard's step 2, and its four checkboxes pushed the navigation row, which sat inside the same unbounded stack, below the dialog's fold (`FoldersPage.xaml` now scrolls the steps in a bounded viewer and keeps the nav outside it). After that fix the same set plus the five witness cases ran 45 passed and 2 failed, both failure classes also present in the default-off run (the feed's tag-chip case, and a UIA `0x800705B4` timeout that moves between folders cases run to run); wall time was unchanged, and no `sync.register` failed across 19 agent sessions. The whole-suite windows sweep ran 2026-09-24 and was graded 2026-09-26 (504 files: 468 clean, 36 red): exactly one red was flip-caused and is fixed (a sync-agent credential-namespace exemption in `test_sign_out.py`); every other red is independent of this default — fixed, closed under its own row, or captured as an open row — as told apart by solo agent-on and agent-off reruns, except that a file whose tests carry an agent posture marker (`isolated_sync_agent`, `real_sync_agent`, `no_sync_agent`) cannot be told apart that way, because the marker wins over the default. (b) The **data dir** — `%LocalAppData%\Fauna`, holding `mls.db`, the daily-rolling `logs/fauna.log.<date>`, `drafts.json`, `config-replica` and the nest-identity pin store — is the profile of the *installed* product too, and on a dev box that app auto-starts at sign-in, so an un-isolated run shares one SQLite store and one log file with a live `FaunaApp.exe --autostart`. `drivers/windows.py` therefore defaults `data_dir` to a per-driver-instance mkdtemp (→ the app-side `FAUNA_E2E_DATA_DIR` override, `BackupPaths.DataDir`), kept on the driver so `recover()` stays a same-device restart; a caller-supplied dir still wins, for the two seams that hand one root to a *sequence* of drivers (the version-skew at-rest grid, `alice_second_device`). Before this the override was set **only** when a test asked, so every other windows launch wrote into the real profile — which is why the default, not the opt-in, is what `tests/test_windows_driver_data_dir_isolation.py` pins. (c) **`%LOCALAPPDATA%` itself, the ancestor both windows roots derive from (2026-09-03) — and this one was DESTRUCTIVE, which is why an isolated *app-level* variable was never enough.** Closing (b) closes the app's own flat base, but shared Rust never reads `FAUNA_E2E_DATA_DIR`: `fauna_account_store::root::production_base()` reads `LOCALAPPDATA` and returns `%LOCALAPPDATA%\Fauna\sync` — the unified account-store root, a *different* root ([`apps/account-scoping.md`](apps/account-scoping.md) § Erasure follows scope: "a sibling of an app's flat base, not a child of it"), which `AccountStateDir.Erase`/`EraseAll` sweep by passing `storeContainer: null` → `StoreRoot::platform()`. So every windows e2e UI sign-out ran `remove_dir_all` over **every** well-formed 64-hex actor dir in the developer's real profile — a test destroying real data outside its launch, not merely reading it. The fix is the same one-ancestor relocation linux/tui and macOS already rely on (`XDG_CONFIG_HOME`, `HOME`), and it is the reason to prefer relocating the ancestor over patching each derived path: it closed the trust home (`cert_binding::windows_trust_home`) and the sync-agent's legacy-state probe in the same move, with no per-path table to keep in sync. The driver's default data dir now hangs off it as `<LOCALAPPDATA>\Fauna`, so an isolated launch reproduces production's *relationship* between the two roots rather than only isolating them individually; a caller-supplied `data_dir` is still honoured verbatim and is not re-parented, which is why the resolved store root is published separately (`_resolved_store_root`) instead of derived from the data dir. The gap was found by a reviewer verifying a *different* change's premises, not by a failing test — the harness had no assertion on this root at all, and `tests/common/scope_store.py`'s windows adapter deliberately excluded it precisely because asserting on it would have meant reading the real profile; the standing lesson is the one this point already states — **an isolation axis is per-platform because the path derivation is per-platform**, and a per-*app* override does not close a shared-Rust derivation that reads a different variable. **Like the macOS `HOME` axis, this one binds every driver launching a WINDOWS process, not just the desktop one:** `drivers/tui.py` had the identical leak on win32 and was fixed in the same pass — tui's flat base is XDG-derived on every platform, so the `XDG_CONFIG_HOME` relocation isolates it there too, but `account_scope::erase` passes `StoreRoot::platform().base()` as a second root and shared Rust's windows arm consults no XDG variable, so a `--app tui` sign-out swept the real profile exactly as the app's did. Both drivers now publish the resolved root as `_resolved_store_root` (`None` on unix, where `<config_home>/fauna/sync` is derivable) and `tests/common/scope_store.py` reads it rather than re-spelling the derivation — a second harness-side spelling of a per-OS path is how the erase assertion and the erase itself drift apart. (d) **The desktop's foreground (2026-09-28)** — linux closes it with the throwaway Xvfb display above; windows has no such display, and a harness-launched FaunaApp lives in the SAME interactive session as whoever is working on the box (an RDP user, on Windows), so a launch that activates its window, or a bridge gesture that moves the foreground, takes their keyboard focus — dozens of times a run. It is closed at both places focus can move. **The launch:** `drivers/windows.py` passes `--e2e-no-activate` on every launch (and `recover()` keeps it), and a test-agent build (`DEBUG || FAUNA_E2E_AGENT`, so artifact-set wiring rather than a knob) SHOWS its window without activating it and marks it `WS_EX_NOACTIVATE` — `App.xaml.cs::ShowLaunchWindow`, the one path both activation sites (the launch-instance chooser and the foot of `OnLaunched`) take, publishing `state["launch"]["window_activated"]`; a shipping build still activates, and `activate_window=True` in a launch config is the explicit opt-out for a test whose subject is the activation. Not activating at launch was measured NOT to be enough: WinUI's text automation peer focuses its control before a ValuePattern `SetValue`, and focusing a control in an inactive window activates it, so the first typed text re-took the foreground; `WS_EX_NOACTIVATE` refuses activation as a side effect while an explicit `SetForegroundWindow` (the bridge's physical fallbacks) still wins. **The gestures:** every UIA pattern the bridge prefers (Invoke, Toggle, SelectionItem, ExpandCollapse, ValuePattern, Scroll) is a COM call into the provider and, on that window, never moves the foreground; what does move it — a physical `SendInput` fallback, which needs the foreground, and UIA `SetFocus`, which ACTIVATES the containing window as a side effect (measured by `test_flaui_input_lock_windows.py`) — goes through one recorder, `flaui-bridge/Actions.cs::RecordForegroundTake`, so the takes are named fallbacks rather than silent ones; and the pattern gestures themselves run under `WatchForeground`, which records any call after which the app newly owns the foreground, so a provider that activates its window on its own is named rather than assumed away. **These opt-outs are real and stay:** the physical-only gestures (a double-click, a caret key, a scroll with no ScrollPattern), the physical fallbacks behind every UIA-preferred gesture, and the `LostFocus` commit of an editable, which UIA cannot fire without `SetFocus`; `test_flaui_input_lock_windows.py` measures foreground ownership by design. So the property is scoped, not absolute: **a UIA gesture path never takes the foreground**, pinned by `tests/test_windows_no_focus_steal.py` (the app's published decision, the bridge's empty take record, and the OS's `GetForegroundWindow` never naming the app, across a launch and a UIA-only journey), and **which tests still take it through a fallback is RECORDED, not promised away** — the teardown hook drains the bridge's record per test (`helpers/foreground_takes.py`), a gitignored corpus keeps the gestures, and the run's terminal summary names the tests. `FindInnerEditWithRetry` used to issue its `SetFocus` nudge on the first miss, on the belief that `SetFocus` is focus-free; it now polls focus-free first and nudges, recorded, only when the composite's inner Edit never realizes on its own. The foreground half of this needs an ATTACHED session to witness: a disconnected one has no foreground to take (it reads 0), and there the decision and the take record carry the case. **macOS adds one axis that binds every driver launching a macOS process, not just the desktop one (2026-07-24):** the sync agent's socket is **HOME-derived** there (`~/Library/Application Support/Fauna/sync-agent.sock` — the `cfg(target_os = "macos")` arm of `fauna_ipc::unix_transport::default_socket_path`, which consults no XDG variable), so a launch inheriting the real `HOME` resolves the *machine-global* socket that the installed `/Applications/Fauna.app` agent holds. `drivers/macos.py` had relocated `HOME`+`CFFIXED_USER_HOME` all along; `drivers/tui.py` had not — it isolated only the XDG trio, which is exactly the right closure on linux and buys nothing on darwin — so a macOS tui **seat** would have driven the developer's real agent against the live nest. Both drivers now relocate it, and because the socket adds a fixed 50-byte suffix that must fit macOS's 104-byte `sun_path`, both also derive the launch root from `/tmp` rather than the `/var/folders/…` default and reject an over-long pinned home by name (gates: `test_tui_driver_env.py`, `test_driver_isolation.py`). The lesson generalizes: **an isolation axis is per-platform because the path derivation is per-platform** — closing the linux channel does not close the darwin one. Rationale, learned the expensive way: close-to-tray is persisted + default-ON, so `should_hide_to_tray()` reduces to "is `org.kde.StatusNotifierWatcher` on the bus we inherited" — a name gnome-shell owns and drops at will. Every linux assertion about window close was silently reading the developer's desktop, `test_engagement_cues.py`'s `wait_app_exit(15)` failed by the hour, and **three sessions misdiagnosed it** — as a timeout, as a test-ordering dependency, and as a shared-Rust flush hang — before the bus was identified (2026-07-17). This is the same shape as the snap-Chromium ProcessSingleton retirement in point 9: when machine-global state leaks into a run, delete the dependency rather than serialize on it or raise the timeout. **The per-module cold relaunch is the same law applied to the app's own past (7-app contract, ruled 2026-08-02).** The `app` fixture cold-relaunches the session-scoped app process at every test-module boundary, so each module starts against a fresh instance — the baseline it would see run in isolation: a session-scoped process accumulates state its in-process `reset()` does not model, and that surplus is prior-test history leaking into a run exactly like an inherited bus. The contract is driver-type-free (`helpers/module_relaunch.py`): it asks `driver.supports_cold_relaunch()` — derived from whether the driver class really overrides `recover()` (`drivers/http_bridge.py`), never a per-app table or platform list — and routes the relaunch through `driver.recover()`, where each platform's cost honestly lives. `reset()` still runs per-test *within* a module, and the reset probe (`FAUNA_E2E_RESET_PROBE`) stays the standing detector for reset()-survivable state — it caught a real shared-Rust factory-reset bug (`4827594821`) that a relaunch landed first would have masked, so the relaunch is hygiene on top of the probe, never its replacement. **A relaunch is the same MACHINE restarting its app, so two things survive it: the machine's store principal (ruled 2026-09-13) and its install device secret (ruled 2026-09-20).** A real install keeps its per-actor T10 credential slot — the store writer key and the principal bundle beside it — across a restart; a launch that loses it mints a fresh writer key and enrolls a fresh placeholder device row that nothing retires, one per relaunch, which walked a whole-suite linux run's session actor into the nest's 64-device tier cap a third of the way in. Since the one-credential shape (RULED 2026-09-28) a lost slot adds no row — the fresh key re-enrolls on the machine's named row — so the carry now keeps the writer key continuous with its replica, which `test_relaunch_device_accrual.py`'s writer-key assertion pins; the placeholder rows measured in this paragraph are history. So every relaunching driver — linux, tui, windows, macOS and iOS — carries exactly that slot across a relaunch (`drivers/http_bridge.py`, the principal-slot carry): the relaunch harvests the previous launch's per-actor `fauna-account-store` entries, and an actor's first authenticated session patch after it restores that actor's whole slot into the store before the app sees the patch. **An actor the replaced launch signed in and no longer holds was signed OUT in it, and the harvest drops its copy (2026-09-21)** rather than keeping the one an earlier launch left: that sign-out retired the enrollment nest-side and erased the slot, which is where a real machine stands after a sign-out and a restart — holding no key for the account — and restoring the older key hands the app a credential the nest has already forgotten, so principal succession mints a successor on a fresh row (the windows mechanism below, reached on every driver by a module whose last test left the actor signed out; measured in [`apps/sync-agent-credentials.md`](apps/sync-agent-credentials.md) § Implementation status today). **And the slot never travels without its replica (ruled 2026-09-15).** A writer lives exactly as long as its journal ([`account-replica-posture.md`](account-replica-posture.md) § The store device principal, refinement 11), so a key restored over a fresh account-store dir is a key the app abandons on sight — it mints a fresh writer and enrolls a new device, the very accrual the carry exists to stop; before that ruling the same shape re-issued seqs the nest already held (84 `stale_writer_seq` refusals in one whole-suite linux sweep, with `publish_pending` wedged behind each). The carry therefore harvests the actor's `account-store` dir under the launch's unified store root beside its slot — a COPY, since the `reset()` after every relaunch erases the source — and lays it down under the new launch's root at the same first sign-in, and only for an actor whose whole slot it holds: a relaunch models a true restart of the machine's store principal, never a deliberate exercise of the retire arm. Every driver publishes that root as `_resolved_store_root` AFTER its carry begins, so the harvest reads the launch being replaced (linux/tui `<XDG_CONFIG_HOME>/fauna/sync`, macOS the relocated HOME's `Library/Application Support/Fauna/sync`, iOS the container's — harvested BEFORE the `simctl uninstall` that destroys it — windows `%LOCALAPPDATA%\Fauna\sync`), and `tests/test_driver_relaunch_pin.py` pins the replica half beside the slot half on all five. linux, tui, macOS and iOS harvest in `launch()` (apple in the store half both its drivers share, `InProcessAgentDriver._resolve_credential_store`), since every launch gets a fresh store, and nothing else survives there but the install device secret below — the identity trio and the per-launch app data (XDG dirs; apple's relocated home or reinstalled container) stay fresh, so the relaunched app still starts signed out. **windows harvests in `recover()` instead (2026-09-14), and empties the store there too (2026-09-21).** Its relaunch re-posts the same session body, so the credential dir it names has to outlive the process that opened it and cannot be swapped for a fresh one the way linux's is. What the relaunch decides is therefore not WHICH dir the new process gets but whether its predecessor's credentials are still in it: `recover()` harvests the slot and then empties the dir, between the old process's kill and the new one's start, so the relaunched app comes back signed out exactly as the other four do. Until 2026-09-21 it emptied nothing and let the `reset()` after the relaunch drop the slot instead — which worked, but put windows alone in reaching that reset with a LIVE account runtime attached, and those e2e `reset`/`logout` arms have been sign-out-shaped since 2026-09-14 (`App.xaml.cs::HandleTestCommand` → `DisposeNestClients(signOut: true)`). So the relaunch retired this machine's enrollment nest-side — the nest vacated the placeholder row and revoked the grant — and the carry then laid the harvested slot back down at the first sign-in, handing the app a credential the nest had already forgotten; shared Rust's principal succession minted a successor, and the actor collected one fresh `fauna` row per relaunch (`test_relaunch_device_accrual.py --app windows`, red at relaunch 1 of 3, twice, 2026-09-21). Moving the erase is what makes this convention's own rule — a relaunch is never a deliberate exercise of the retire arm — true on windows rather than merely stated: the reset after a relaunch now finds an app that is already signed out, the structural no-op it is everywhere else. `preserve_state_across_relaunch()` is the opt-out, and on windows it is now a real pin rather than a standing `True` that pinned nothing: it suppresses the erase for a test asserting client-side durability across a restart, `reset()`'s `_clear_relaunch_pin` drops it at the per-test boundary, and `hard_reload()` reads it to decide between waiting for the app's own auto-login and replaying the session — which is why the standing `True` was wrong twice over: every windows relaunch preserved the session whether or not a test had asked, and `hard_reload()`, reading an always-empty pin set, replayed a login into an app that had already auto-logged-in. `launch()` still settles the caller-owned bound below, on the launch that chose the store, and that same bound governs the erase: a caller who supplied `credential_dir` or `keyring_app` owns what rests there — the version-skew at-rest grid hands ONE store to a SEQUENCE of driver instances — so a relaunch never empties it. **Where the slot rests is per app, so the carry reads it from one table (2026-09-14).** `common.cred_store.account_store_location` names the file and a key prefix: the File backend's own namespace file on linux, tui and windows, a sibling `fauna-account-store.json` on macOS, and — because iOS has no native Rust keyring arm, so the namespace rides the foreign seam — `fauna-account-store/`-prefixed rows inside the app's own `keychain.json`, which the restore merges into without touching the identity rows beside them. The restore-at-sign-in rule holds on iOS unchanged, and it holds only because FaunaKit's e2e keychain backing re-reads that file on every operation and takes `<file>.lock` for every mutation, as the Rust File backend does (`KeychainStore.e2eReload`): a backing that loaded the file once per process never saw a slot restored into it, and flushed its stale map over the slot at its next write. Three bounds keep it narrow, each pinned by `tests/test_driver_relaunch_pin.py`: it restores **only an actor being signed in** (a whole-file copy leaves slots that no process's registry knows and so no sign-out can erase — exactly what `test_sign_out.py`'s account-store assertion refuses); **only once per launch** (a sign-out → sign-in inside one process mints afresh, as production does, so an erase that dropped the slot but kept the store still surfaces — and since 2026-09-14 production's sign-out also retires that enrollment nest-side, so the fresh mint replaces a row instead of stacking one beside a stranded placeholder; [`apps/sync-agent-credentials.md`](apps/sync-agent-credentials.md) § Implementation status today, the RULED 2026-09-14 entry, whose `test_sign_out_device_roster.py` is the sign-out-shaped proof beside this bound's relaunch-shaped one); and **never into a store the caller owns** (a supplied `credential_dir` or `keyring_app`, `use_real_keyring`, tui's sealed `headless_store`, apple's `preserve_state_across_relaunch()` pin). The relaunch-shaped proof is `tests/test_relaunch_device_accrual.py`; the device-row reasoning is owned by [`apps/sync-agent-credentials.md`](apps/sync-agent-credentials.md) § Implementation status today. **The install device secret is the second survivor, and it is carried at LAUNCH, not at a sign-in (ruled 2026-09-20; linux and tui built 2026-09-22, macOS and iOS the same day).** The id of the named sync device row an account registers is derived from an install-scoped secret and the account ([`apps/sync-agent-credentials.md`](apps/sync-agent-credentials.md) § Credential model), so fresh dirs per launch are a new machine per launch — one new named row per relaunch for every actor that signs in with a device id the app refuses to adopt, the per-launch accrual the principal carry closed for the placeholder. The secret names no account, so no other actor's residue can ride in with it and it is laid down before the app starts: `HttpBridgeDriver._carry_install_device_secret`, called from `launch()` with the app's install dir (linux: the flat `<XDG_CONFIG_HOME>/fauna/sync`; tui: `<XDG_CONFIG_HOME>/fauna-tui/sync` on every platform), copies what the launch being replaced left on disk — so a launch that lost its secret (its data dir wiped, the fresh-machine case) carries none forward — and only a secret of exactly 32 bytes, since a torn mint is one every later derivation refuses for good and copying it would spread one dead install across the rest of a sweep. Its fresh-machine opt-out is the principal carry's caller-owned bound above, and it never overwrites a secret the launch already holds. **Where the secret rests is per app, and its at-rest SHAPE is too — which moves WHEN it is laid down (macOS and iOS, 2026-09-22).** linux and tui keep it as a file under an install dir; a secret-store app keeps it as a ROW in the store the app already has, under shared Rust's own logical key `install/device_secret` (`fauna_client_accounts::device_id::INSTALL_DEVICE_SECRET`), hex-encoded. So the carry has a second face — `HttpBridgeDriver._begin_install_device_secret_row_carry` + `_restore_install_device_secret_row`, from the store half both apple drivers share (`InProcessAgentDriver._resolve_credential_store`, where their principal-slot carry already begins) — with the same harvest and the same bounds, a JSON merge instead of a file copy. **The harvest stays at launch; the restore moves to the first sign-in, and that is load-bearing rather than incidental.** A file written before the app starts is untouched afterwards, but on a secret-store app the store IS the app's keychain, and every apple relaunch is followed by a `reset()` whose `resetToFactory` sweeps *every* row in the service (`KeychainStore.deleteAll` — deliberately not just the identity three, so a pending-factory-reset slot cannot leak into the next test). A row laid down at launch is therefore erased before any sign-in can derive from it, and the carry would buy nothing — the same shape that made windows harvest its principal slot in `recover()` instead of at `launch()`. Restoring beside the principal slot, in `set_state` before the app sees the patch, puts the secret back on the far side of that erase. It is **once per LAUNCH, not per actor or per sign-in**: the secret names no account, so no other actor's residue can ride in with it, and a *later* reset inside one launch is a factory reset, which the ruling says ends the install secret — the next sign-in after it correctly mints afresh. The harvest still runs LAST in the store half, after `seed_credentials`, which replaces the file wholesale. The carry copies that ONE row and leaves every row beside it alone in both directions — a whole-file copy would hand the new launch the previous one's identity and it would start signed IN, when every launch must begin signed out. The 32-byte rule is the file leg's, applied to the DECODED value, so a truncated or non-hex row is dropped the same way a torn file is; and both faces write through one `_merge_store_rows`, which is also the principal restore's writer (the `<file>.lock`, the 0600 tmp+rename), so the lock, the mode and the merge cannot drift apart on a file the app reads as key material. Pinned by `tests/test_driver_relaunch_pin.py` (tier_1, driving linux's and tui's real `launch()` and apple's real store half, with the launch-then-reset-then-sign-in ordering asserted in both directions) and `tests/test_relaunch_device_accrual.py::test_relaunching_an_un_forced_sign_in_keeps_its_named_row` (tier_3, which runs on iOS but not macOS — see the named-row gate below); each remaining app's leg extends this one carry to wherever that app keeps its secret, once the app derives its id from it ([`apps/sync-agent-credentials.md`](apps/sync-agent-credentials.md) § Implementation status today owns which have).

**The named-row barrier reads each app's own id where it keeps it (2026-09-22; its no-row gate retired 2026-09-29).** `helpers/enrollment.await_named_row` is the causal barrier an un-forced sign-in rests on, and it reads the app's OWN persisted id back from wherever that app keeps it — the account-scoped sqlite `device.db` on linux and tui, the per-account registry slot `fauna/{actor}/device_id` in the app's own credential store on macOS, iOS, windows, android and web (web's store is the page's `localStorage`; android's is the on-device e2e credential file, read over the bridge's `GET /credentials`), read through the harness's one adapter (`common.cred_store.attach_cred_store`; the store lands every logical key verbatim, so shared Rust's key IS the row name). Every app has a reader, so a driver that reaches the reader's fallthrough has not launched — a harness error, never an unbuilt skip. The per-account slot alone: apple and windows both retired their pre-registry single slot, their session patches enrol the identity in the registry, and a native `device_id` row would report whichever account was last active — which is worse than no barrier at all, since it greens the exact accrual the derivation exists to stop (owner of the slot: [`long-term-store.md`](long-term-store.md) § Downgrade mirror + abandoned-append recovery). But a reader is not enough to make the barrier latch: the row must be registered, and a barrier that can only time out reports a 240 s wait as a failure of the app under test. Since the one-credential shape ([`apps/sync-agent-credentials.md`](apps/sync-agent-credentials.md) § Credential model, RULED 2026-09-28, bound (c)) every app that hosts the account runtime registers its named row from the enrollment alone — it targets the app's own derived id and register-creates the row when the nest lists none, whether or not the launch starts an agent — and since 2026-09-29, when web began hosting the runtime, that is every app, so the barrier's no-row gate is retired. Until then a default macOS or windows launch, which starts no agent, enrolled a writer-pub-hex placeholder instead, and both skipped here unless the launch pinned its agent. Pinned tier_1 by `tests/test_enrollment_named_row_readback.py`. An app that cannot relaunch is a declared, output-visible absence, equality-pinned per driver by `tests/test_module_relaunch.py` (today: android, whose bridge keeps no relaunchable session) — never a resurrected type list. History: built 2026-06-13 for the apple apps' XCUITest accessibility-tree corruption and type-gated `is_macos() or is_ios()` until 2026-08-02, when the gate itself was ruled drift — two platforms, two mechanisms, one signature. **A relaunch contract is only as strong as the harness's grip on its own app (windows, ruled 2026-08-13).** The bridge must hold a handle to the process it launched that nothing else can invalidate — and on windows it did not: `SessionManager.Launch` passed the bridge's **own** `Process` object to `Application.Attach(Process)`, and FlaUI's `GetMainWindow` — the door every element find goes through — calls `Dispose()` on the process it holds whenever the main window handle is missing (`WaitWhileMainHandleIsMissing`, proven by stack trace). One object, two owners, and the owner that did not expect it lost its only view of its own app: every later `Refresh()`/`Id`/`HasExited` threw `InvalidOperationException`, so `Quit`'s kill loop read a **live** app as "already gone" — the leak the data-dir sweep had been silently compensating for on every relaunch — and, because a FlaUI `Application` is unusable once its process handle is gone, every later find failed too, costing real feature coverage on pages with nothing to do with process lifecycle (2-3 of `test_backups.py`'s 15 cases per run, with an onset that moved between runs because it depends on when a find catches the window transiently missing). The rule generalizes past FlaUI: **hand a third-party library an identifier, never the harness's only handle.** The bridge now attaches by **pid** and re-attaches when FlaUI drops its own copy. Pinned headlessly by `tests/test_bridge_handle_lifetime_windows.py`: any **windowless** process is permanently in the disposing state, so the whole bug reproduces against the real `SessionManager` with `ping` standing in for the app — no GUI, no nest, no app build, seconds rather than a multi-module e2e run. The data-dir sweep stays the standing detector; this is what makes its silence mean "nothing leaked" rather than "the net caught it again". **The law binds tier_1 too, not only driver-launched processes (ruled 2026-08-06).** A GTK widget unit test is not a pure computation: it `present()`s real windows and an autohide `gtk::Popover` takes a *display-wide* keyboard and pointer grab, so `cargo test -p fauna-linux` run against the developer's ambient `$DISPLAY` puts 280 tests on the desktop every other process on the box shares. It cost two distinct intermittent failures, on a dev machine that routinely runs many builds and test processes in parallel: six concurrent test processes fighting over the one grab had the losers' popover popped straight back down (4 failures / 150 runs concurrent, 0 / 60 alone), and — because a popped-up popover leaves its `gtk::Entry` focused with its whole value *selected* — a single key event delivered anywhere on that desktop replaced the entry's value outright, which three sessions read as an uninitialized-memory read through `gtk_editable_get_text()` (payloads with no trace of the value the test set, of differing lengths, several being long runs of one character: key auto-repeat, not heap garbage). The fix is the same throwaway Xvfb `drivers/linux.py::launch` already uses, moved inside the process so no invocation can bypass it — `apps/fauna-linux/src/testid.rs::start_private_display` gives the one GTK test thread a display of its own, pinned by `testid::widget_tests_run_on_a_private_display`. Generalizes to any tier_1 suite that instantiates real widgets: **the tier does not change the law — a test that opens a window is a launch.** **The nest is the deliberate inverse, and it needs its own rule (ruled 2026-08-17).** `nest_instance` is `scope="session"` and is shared by every test *and* every app parametrization — that is by design (one nest, N apps, which is what makes cross-app journeys possible), so the answer is never to isolate it. The answer is that **a test may not mint a name the nest treats as unique, nor poll for a bare count, nor act on index 0.** `test_admin_users_hub.py` broke all three: five hard-coded admission handles, a `invite_request_count() < 1` poll, and `approve_request(index=0)`. The nest refuses a handle already assigned (`submit_invite_request_core` → `fauna.account.handle_taken`), so whichever app ran first admitted `joiner`/`evictee`/… and every app after it **raised inside the submit helper, before a single assertion** — 21 failures across a three-app sweep from a module that is 9/9 green on any one app. The failure wears the costume of a product bug in the app, and it did: the row filed against it concluded "all-app ⇒ nest-side or shared, not driver", which is exactly backwards — with one shared nest the three apps are **not independent witnesses**, so an all-app failure is equally the signature of cross-app contamination. The discriminator is one run: the same module on one app. Compounding it, a *failed* approval leaves its request `pending` ([`../behavior/admin.md`](../behavior/admin.md) § 2 Section 1), so index 0 becomes the earliest **stuck** row and every later approve re-runs the same old failure — which is how one broken test presents as seven broken ones. So: mint per-submission identifiers (`prefix + secrets.token_hex(3)`, the idiom `conftest.py` already uses for handles), locate rows by identity (handle / actor id) exactly as `admin.user_row_index` does, and poll for *your own* object rather than for a count that a sibling test or a sibling app already satisfies. **A fourth form of the same mistake is asserting a nest-wide SETTING equals its catalog default** — diagnosed the next day and initially filed as a separate native-vs-web product split. `test_admin_mail.py`'s field tests each asserted the page hydrates to the catalog default, then *saved a new value into the one shared mail config*: in sweep order web ran first, hydrated 5, saved 7 — and linux and tui then hydrated 7, expected 5, and failed **before a single key was typed**. It was read first as a shared-Rust product bug and then as a bug in the `http_bridge` driver's `clear_and_type`, neither of which is reachable from a failure in the hydrate assert; the file is 11/11 green on any single app. Its sibling `test_admin_role_address.py` is the same rule broken by a *module-level* `_DOMAIN = f"…{secrets.token_hex(4)}"` — unique per import, therefore shared by all three parametrizations, and its own assert names the symptom (*"freshly-seeded … unexpectedly already has role overrides"*). **Assert against a ground-truth read of the setting, not a literal** (`_nest_now`), and choose a save target guaranteed to differ from what is already there (`_distinct_target`) so a round-trip cannot pass by coincidence. That is also the stronger claim: "the page shows 5" pins hydration only while the nest happens to hold 5, whereas "the page shows what `get_mail_config` returns" pins that hydration tracks the nest at all times — which is what a round-trip test exists to prove. Catalog defaults are a nest-side fact and belong to the API tier. **The generalization worth carrying: on a shared nest, an all-app failure is the CHEAPEST thing to misread as product evidence, and the discriminator is always the same one run — the same tests against a single app.** **A fifth form is worse than the other four, because it does not contaminate the shared nest's state — it destroys the shared IDENTITY (ruled 2026-08-30).** `test_user` is `scope="session"` for the same reason `nest_instance` is, and accumulating state on it is the point; but the identity-succession ceremony revokes every bearer of the predecessor inside the succession transaction, so a test that drives it against `test_user` signs out **every later test in the run**. Each one's login is then refused, the app routes to the identity-import flow instead of coming online, and the login seam's connection barrier burns its full 60 s before erroring — so the symptom is a whole-module `ERROR` in a module that has nothing to do with succession, and nothing in the failure names the cause. Measured: in a 3 347-test docker sweep, one such test at outcome 467 killed every barrier-exposed module from outcome 492 to the end of the run (65-92 % of them, for fourteen hours, never recovering), while modules that never log in interleaved green throughout — which is why three sessions read it as a load spike and bisected it as an accumulation. Two lessons generalize past succession. **(a) Grade a shared-nest cut over EXPOSED outcomes only** — here, tests that reach the login barrier; the raw rate is diluted by roughly half by tests that could never have failed, and that dilution is exactly what made a step change read as a transient. **(b) A cascade UNDERCOUNTS product defects rather than merely adding noise**: eight tests that fail in a short run were never reached at all, so their real failures were invisible behind the errors. The fence is mechanical, because prose was not enough — the rule was already written in three fixture docstrings and was violated twice in one file regardless: `tests/test_no_succession_on_the_shared_identity.py` refuses the authoring shape at collection time on every app, deriving the shared-identity fixture set from `conftest.py` rather than a hand-written list, and `helpers/shared_identity.py` is the fail-open runtime backstop for the raw-`set_state` path a source scan cannot see. The dedicated fixtures a ceremony must use — `ungranted_app`, `succeedable_app` — already existed throughout. **A sixth form leaves the shared identity signable but poisons its MAIL KEYS (ruled 2026-09-21).** Two journeys did it to `test_user`: a backup precondition registered a stand-in recipient seal key ("nothing here opens the blob") on an actor with no mailbox yet, and the disable-mail journey turned its mail off and back on, a teardown that strands every record already delivered ([`../behavior/mail-credentials.md`](../behavior/mail-credentials.md) § MSEK lifecycle). Either way a record in the shared mailbox can never open. Every later module's cold relaunch re-drains it and raises the unopenable-mail floor ([`../ui/conversations.md`](../ui/conversations.md) § Errors & edge cases → *A fifth truth*), which no gesture clears, so every later "page shows no error" assertion in the run fails on a count that only grows (measured on linux: 2 records by 24 % of a whole-suite sweep, 5 by the messaging module). The rule: a precondition that needs a mailbox enables one the way a user does, through the app, and never writes a key the account does not hold; a journey that must leave a record unopenable runs on `dedicated_actor_app`. The fence is mechanical, as for the fifth form: a harness WS-RPC call of `fauna.bridges.provision_recipient_mls_pubkey` aimed at a shared identity is refused before it is sent (`helpers/shared_identity.py`, called from the client's `call`), and the session nest's admin counts as shared from the moment `nest_instance` creates it. A journey whose mail goes to the deployment admin (role addresses) therefore runs on a mail venue whose admin is its own. **A harness bridge choosing its own listening port is bridge-general, not windows-specific, and needed the same never-one-shot discipline this whole point already states for every other channel (ruled 2026-09-22).** Two independent out-of-process bridges draw from the identical 18000-19000 range on the same box — `flaui-bridge/Program.cs` (windows) and `web-bridge/server.py` (every `--app web` launch) — and until now each called `Start()`/bound its listener exactly once with no retry, so any two alive at once collided with odds ≈ (bridges alive)/1000: measured 3 collisions in 240 concurrent windows launches (30 at once × 8 trials), all `HttpListenerException (183)`, plus one that killed a real two-seat test mid-suite. The rule: **any harness child that picks its own listening port retries a bounded number of DISTINCT ports on a bind conflict, and reports its port only after a successful bind** — never a one-shot draw. windows implements this as `flaui-bridge/PortPicker.cs::BindFreshPort`, retrying on the whole bind-conflict error-code family (183 ERROR_ALREADY_EXISTS *and* 32 ERROR_SHARING_VIOLATION — a plain-socket holder, confirmed experimentally to throw the OTHER code, so a fix that only caught 183 would silently miss a collision with the web bridge), pinned by `tests/e2e-unified/tests/test_bridge_port_retry_windows.py` with no real listener.
