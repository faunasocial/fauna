## Goal

User data belongs to the user. **Every nest stores user content sealed at rest beyond the plaintext routing floor — there is no storage mode** (the plaintext/encrypted deployment binary is retired; direction ratified 2026-07-04, transition ratified 2026-07-12 — `nest/storage-modes.md` owns the retirement mechanics; the legacy-mode compat shims it carried left the wire 2026-09-24). What a given box can *read* is not a deployment property but the user's per-box choice: the set of capability grants that box currently holds (§ Capability tiering), minted, audited, and revoked from the user's apps. A user's identity (MLS keys, actor ID) is unified across all locations they use; the same person may run a home nest holding their broad grants and a VPS holding none, federated by fauna-protocol.

Universal everywhere: a small enumerated list of routing/scheduling metadata is plaintext (the floor — necessary for the system to function), plus the explicitly plaintext-by-design kinds (public posts, `Profile`). Beyond that, content rests sealed; reading happens only at capability positions.

## The sealed posture (formerly "the two storage modes")

The claim-time trust statement — *do you trust the box with plaintext content?* — is retired as a deployment question. Its two answers survive as the two extremes of the grant axis: a box with no grants can route, hold, and serve sealed bytes but cannot read (the old encrypted mode's property); a box the user trusts holds broad, auto-renewed grants (the old plaintext mode's capability — now explicit, scoped, time-bounded, revocable, and logged per box on the Nests page).

**The uniform posture.** Every nest holds user content sealed at rest beyond the floor: mail bodies, calendar events, vCards, conversation messages, restricted posts, the per-user search index — sealed under the owner's keys or the audience's keys (per-kind mechanics in § Per-content-kind conformance). Fauna-native compose drafts (`__drafts`) and media (per-blob-keyed by audience) are sealed under the owner's keys (the user's settings and the private contact overlay likewise, as account-state plane items — `docs/goal/ui/contacts.md` § The private overlay); the nest **never holds `BackupKey`** (the user's client mediates the chunk-encrypt-and-upload step per § Cross-flow → Backups). The contact-relationship-existence table (`bins/fauna-nest/src/db/contacts.rs`'s `contacts` SQLite table) stays in the plaintext floor everywhere — the knock/DM-arrival hot path reads it on every Fauna inbox delivery (not real email — `docs/goal/ui/contacts.md` § Persistence). The federated `Profile` record is signed plaintext everywhere — it has no private sub-record (the `Profile` conformance row). Public/signed posts and their attached media are plaintext by design. IMAP/CalDAV/CardDAV are served by the mail-bridge MDA process; AUTH-by-unwrap yields a session-scoped capability, and the serve path opens records per-record under it — there is no mode-discovery step (the `fauna.bridges.fetch_config` `storage_mode` constant that outlived the axis as compat ballast left the wire 2026-09-24 — `nest/storage-modes.md` § The transition contract). Disk-encryption posture is determined by the underlying OS and the user's environment.

**Client-side at-rest posture is owned elsewhere:** the app-side per-account replica rests plaintext in the user's OS context by ratified decision — owner [`account-replica-posture.md`](account-replica-posture.md) § Local at-rest posture; this doc's sealed posture governs every *nest*.

**What used to be "plaintext mode"** — a box the user trusts doing server-side content work — is expressed as **capability grants**: the user's client mints the box standing scoped read grants (broad + auto-renewed for a blessed home box), audited and revocable per box on the Nests page. Per-user MLS read keys, and every other decrypt authority, reach a box only as a grant or a session capability — never as a deployment posture. TLS private keys follow the wrapped-blob pipeline (provisioned wrapped to bridge service-user pubkeys, unwrapped at the bridge), and DKIM signing keys are the nest's own deployment-infrastructure secret, sealed under its key-encryption key (`key-material-hierarchy.md` rule 5); the residual on-disk-PEM custody tightening is a security-backlog item independent of any mode.

**Threat model on granting broadly.** A user who mints a box a broad, auto-renewed content-read grant gives that box's owner (and disk) read access to the granted scopes for as long as the grant renews — functionally the old trusted-box exposure, now explicit, scoped, time-bounded, revocable, and recorded in the client-authoritative grant log (a leak's suspect set narrows to boxes holding a reaching grant during the window). Identity is never grantable: no grant reaches the identity signing key (`key-material-hierarchy.md` rule #7), so a maximally-granted box eavesdrops, never impersonates. Human count is orthogonal: each user grants (or doesn't) independently; there is no deployment-wide consent to a posture, so the former join-time consent screen is retired.

**Implementation: one sealed storage layer.** Single `bins/fauna-nest`. Shared `libs/` (parsing, mail-auth, spam, tokenization, kind registry, routing logic, IMAP/CalDAV protocol, SMTP MX, DKIM signing, ACME, content-index engine/format `libs/fauna-index/`) over one storage implementation: ingest verifies seal shape per audience class and never runs plaintext-derived processing (no server-side classify/EXIF/thumbnail arm); byte storage — the `content` table, the reserved-folder segment stores (`__mail`/`__calendar`/`__card`/`__conv`, authority `docs/goal/architecture/message-segment-store.md`), the `bridge_blobs` wrapped-blob store, `DiskBlobStore`, floor metadata — is identical everywhere. There is no mode-unresolved state and no pre-mode gate: a nest is content-ready from first boot. (Phase 4 closed this: the three-impl `Storage` trait and the mode machinery are gone — `bins/fauna-nest/src/storage/` is `mod.rs` + `sealed.rs`, one `SealedStorage` impl live from boot; see § Implementation status today and `nest/storage-modes.md` § Implementation status today.)

**Common deployment patterns.**

- *Trusted hardware (home server, laptop, family box).* Users mint the box broad auto-renewed grants; server-side content work (re-scoring, future FTS indexing) runs under them.
- *Untrusted hardware (VPS, shared infrastructure).* Users mint nothing, or narrow short-lived grants; the box routes, holds, and serves sealed bytes; reading happens in sessions and on clients.
- *Hybrid.* Home box holding broad grants + VPS holding none, same human, federated by fauna-protocol — see [`nest/deployment-home-with-public-relay.md`](nest/deployment-home-with-public-relay.md) for the asymmetric (private + public) shape.

## Plaintext floor

The following metadata is plaintext on every nest. Required for the system to route, fan-out, schedule, and audit; encrypting it would force the nest to fetch-and-decrypt every record on every routing decision.

- **Identifiers.** Actor IDs (public by design). Message IDs, event IDs, file IDs (opaque routing pointers).
- **Sizes.** Ciphertext sizes (rounded — hides exact size while permitting quota counters and storage planning). **Carve-out (re-ratified 2026-07-29):** file-sync surfaces store exact sizes — the manifest's plaintext `total_size`/`chunk_sizes` and individually-addressable ciphertext chunks already expose them (accepted-forever, `mls-group-key-material.md` § M2 *Sealed manifest hashes*), and DAV `getcontentlength`/quota/restore need exactness; rounding there would be size-theatre over a stronger existing signal.
- **Timestamps.** Per-message/event timestamps for sort, filter, scheduling.
- **Routing tables.** `recipient_local_part → actor_id` mapping for inbound MX. Envelope FROM (for SPF audit).
- **Relationships.** Existence of contact / follow / group-membership edges (for fan-out routing).
- **Mailbox structure.** Folder names, hierarchy. Per-message flags (read/unread/answered/seen). IMAP needs these without decrypting bodies.
- **Mail report-hash.** The canonical `report_hash` v1 — unkeyed blake3 over the canonical subject + body, one per message whether or not the recipient shares reports — in the segment footer and the `segment_records` mirror: the cross-user content-equality key report sharing aggregates on. The one content-derived floor item, and to a floor reader an exact-text guess-and-confirm oracle; that residual is **accepted (2026-09-27)** with its bound and rationale owned by `../behavior/report-sharing.md` § Threat model & accepted limitations.
- **Counters and rate state.** Per-actor submission quota, greylist (sender, recipient, IP) tuples, audit logs.
- **Wrapped key blobs.** Opaque ciphertext: per-`(actor, credential_id)` MLS-key blobs, per-`(domain, selector)` DKIM blobs, per-`(domain)` TLS cert blobs. Nest stores; nest cannot read.

Adding a new content kind to the system requires deciding what (if anything) about it joins the floor. Default for new kinds: nothing — only routing/scheduling metadata that the nest must read on its own joins the floor.

**Deployment-key uniformity.** Wrapped TLS-cert blobs follow one protocol
everywhere: HPKE-wrap to the bridge's per-instance service-user pubkey, the
bridge fetches via `fauna.bridges.fetch_tls_cert_blob` and unwraps locally
with its own secret; certs are ACME-issued or admin-provisioned (three paths —
`mail-bridge-lifecycle.md` § TLS provisioning), `provision_tls_cert_blob`
being the admin-class RPC for the explicit path. DKIM keys are not on that
pipeline: the nest mints them automatically, holds them sealed under its own
key-encryption key and signs at the outbound hand-out — no manual admin UI,
no bridge holding one (`mail-bridge-lifecycle.md` § DKIM provisioning
(automatic)).
(A box owner with process access to the bridge could extract the unwrapped
TLS key — the same physical-access reality as any co-resident process; the
residual on-disk-PEM custody tightening is tracked on the security backlog.)

## Readable classes (the ceiling — formerly "Plaintext ceiling per mode")

The ceiling is the same on every nest: **floor + the explicitly readable classes.** A readable class is content the nest can read at rest for a stated, enumerated reason — never a deployment posture:

1. **Plaintext-by-design kinds** — public/signed posts and their attached media, the federated `Profile` record, restricted-post public previews. Readable by anyone by construction; serving, indexing, or searching them reads nothing sealed, so floor-derived search over this class runs server-side on every nest uniformly.
2. **Capability-granted readable classes** — content the *user's client* has explicitly granted a holder standing scoped read access to, via the grant primitive (§ Capability tiering). The re-score drain's `content.read{mail}` grants are the shipped instance. A second instance — **the web-paywall readable class** (ratified + the post half's nest leg landed 2026-07-12: holder, sealed render, and the serve-time capability-URL gate; the `web`-folder half landed 2026-07-13 — per-set tier flag, `content.read{folder:set}` grant scope, sealed static serving, and the shared `FoldersAuthor` paywall/rotate/unpaywall orchestration; visitor entitlement (Pillar 3 checkout/claim on the teaser) and the remaining client legs pending — `behavior/monetization.md` § Implementation status): the creator's client mints the nest's web-serve holder (its own enrolled service-user identity) a standing scoped grant — exactly the paywall tier's period key and/or the `web` folder's keys — so it can serve paywalled web content server-side; behavior, gate, and visitor-token design owned by `behavior/monetization.md` § Pillar 2.
3. **Legacy artifacts — none readable any more.** Pre-Phase-3 raw records on formerly-plaintext boxes were retired by the 2026-08-17 record-identity cutover, and nest-minted legacy subscription period keys by the 2026-09-27 compat-remnant sweep; the nest holds no subscription period key (`nest/storage-modes.md` § Legacy artifacts).

4. **Owner-materialized views — the materialization tier (direction ratified 2026-08-10, user directive; refutable until first build; nothing is built).** A user may mint their **own nest** the widest grant tier — a **materialization grant** — permitting that box to keep **readable derived views** (per-kind projections and the user's own search index) of the granted **own-actor scopes** at rest, built nest-side from the sealed canonical planes under the grant's keys. This is the per-user, per-box successor to what the retired plaintext mode granted every resident at once: the same authorization plane as every grant (client-minted, scoped, audited, revocable — § Capability tiering), the same threat model as a broad standing grant (§ The sealed posture: the box and its disk read the granted scopes while the grant stands — a standing grant's holder key already rests on the same disk as the sealed bytes, so this tier changes the at-rest *form*, not the trust boundary), with the at-rest form made honest instead of nominal. Its first use case is nest-side full-text search over the user's own mail. Bounds, each load-bearing:
   - **Canonical planes never unseal.** A record's identity is its sealed block's CID (`account-data-plane.md` § Store logical schema), so unsealed canon is not a lesser posture but a different identity system; sync, custody, backup, and federation continue to see exactly one sealed shape, and posture never appears on the wire (R7 (account-data-plane.md § The ratified decisions)).
   - **Own-actor scopes only** — mail, calendar, card, own posts, own folders. Member/shared scopes (a `__conv` channel, a shared folder) are co-authored: one member's opt-in must not expose co-authors, and conversations are additionally out by construction (class-5/MLS material is never grantable). The client-side mint surface refuses non-own-actor scopes.
   - **Views are derived state, never truth**: never a sync unit, never backed up, rebuildable from canon at any time — and they rest **outside `nest.db`** (a per-actor materialized area of the data dir), excluded from the self-backup hot-copies and the logical dump, precisely so deletion at revocation is real rather than outlived by backup blobs.
   - **Revocation = keys dropped + views deleted**, recorded in the grant log. Honesty bound, stated in the opt-in UI copy rather than buried: deleting the views is enforced by the same trust the grant itself expressed — a box hostile or compromised during the window has seen the content regardless (identical to the standing-grant bound in § Capability tiering); revocation restores the sealed-at-rest state going forward, with cryptographic teeth exactly where bounded/epoch-sealed kinds provide them.
   - **Retroactive by construction**: the box materializes whatever already-held sealed history the grant's keys open — no client re-upload, no forward-only mixed-store cliff; opting out deletes the views and nothing else.
   - **Serving ACLs unchanged**: the grant widens what the box may hold readable, never who may query it — every query surface keeps its per-user session/grant authentication, and views never cross user boundaries (the per-user index isolation rule below is untouched).
   - **Nest-only holder in v1**: a custodian *device* (`account-replica-posture.md` § Replica posture) refuses materialization grants until the W8 (account-data-plane.md § Workstreams) custody consent surfaces (T16) exist — whether a friend's device may hold your readable views is a two-sided product question, not a storage one.
   In `account-replica-posture.md` § Replica posture's vocabulary this tier is exactly "the owner flips their own nest's replica of their own account to reading posture": materialization follows key reach uniformly, app and nest alike (charter R9). That doc owns the replica/posture framing; this class owns the at-rest property.

**Everything else rests sealed on every nest, for every account — no deployment exception**, subject only to the owner-facing exception below. The sole per-user carve-in beyond that is class 4's owner-materialized views over the user's *own* scopes on their *own* nest — derived state under a live grant; canonical planes stay sealed for every account on every nest. Per-user search-index segments (the synced `__index` rail) are sealed alongside the content they describe; per-kind seal mechanics are the conformance table below.

**Owner-flipped public-audience folders (ratified 2026-08-13) are the one exception to sealed-by-default, not a fifth readable class.** A folder whose owner sets its audience to `public` rests unsealed — content, names, and paths (they are URLs), integrity-protected only — behind an explicit per-folder owner confirm naming that consequence; flipping back re-seals only future writes. This is an owner choice about their own data, not a nest/deployment posture, so it does not weaken "no deployment exception" above. Full statement + authority: `principles.md` § The user always controls their data.

**The declassification is owner-ATTESTED, and a seat verifies the attestation before it writes one unsealed byte (ratified 2026-09-21).** A nest's `audience: "public"` on a `fauna.folders.list` row is a *claim*, never an instruction: the projection-trust model (`security.md` § Transport trust) covers what a client **displays**, and a projection may not direct a client to unseal — the at-rest property above is written against every nest, the user's own included. What arms the plaintext arm is the **audience attestation**: an Ed25519 signature by the folder owner's identity key (an actor id *is* that public key, `fauna-core` `identity`) over the domain tag `fauna.folders.audience-attestation.v1`, the owner's actor id, the folder id, the folder name, and a **counter** — every element length-prefixed. **Its origin is the owner confirm itself:** the shared `set_audience` gesture every app's `folder-audience-public-confirm` lands in mints it and sends it on the same `fauna.folders.update` that flips the audience; the nest **only stores and serves the blob** (`FolderSummary.audience_attestation`, both projection arms) and verifies nothing, because the nest is the adversary this defends against — a nest-side check would protect no one. **One verifier, `FolderSummary::judge_declassification` in `fauna-protocol`, is the only way any seat reads the verdict** — the engine's live seat resolver (which was also the `bins/fauna-sync` daemon's, until its removal 2026-10-02), the engine binding decision, the pushed agent capability, and Media's seam — and it answers *unsealed* only when ALL of these hold: the row claims `public` and is not WebDAV-served (the pre-existing fail-safe); an attestation is present; its signer equals the **trusted owner identity the seat supplies**; its folder id equals the row's; the signature verifies over the name **the seat is acting under** (never a name the row supplies alone); and its counter is not below the seat's remembered floor. **Anything else seals** — absent, malformed, wrong signer, wrong folder, stale — the direction every reader already took for an absent verdict. **The trusted owner identity never comes from the nest.** For a folder the seat's own account owns it is the seat's own actor id (an app derives it from the identity seed, as `bins/fauna-sync` did until its removal; the bearer-only sync agent holds it in the capability its app pushed over local IPC). For a member's seat it is the folder channel's **MLS-authenticated owner** — the leaf-verified Welcome sender recorded at join (`folder_channel_owner`), **as re-pointed by the owner's verified succession** (amended 2026-09-22): the marker follows the succession chain from an anchor the nest cannot forge — the chain-verified in-group statement on a member's seat, the device's own registry on the successor's — under one rule that also admits the successor's roster commits, owned by `federation.md` § Cross-nest shared folders + channel append → *The marker follows the owner's verified succession*; so once a seat has learned of the succession, an attestation signed by the retired key fails as a wrong signer and **burns**, and only the successor's arms it, while a seat the statement never reached keeps the retired key as its anchor (the residual `succession-propagation.md` names for a group the sweep never reached) — never the `owner_actor_id` / `owner_handle` the nest fills on a member row; a member seat with no recorded owner (a join older than 2026-08-24, which stamped none) has nothing to verify against and **seals**. A seat that holds no MLS state — the bearer-only sync agent, the File Provider helper — has no member anchor at all, so its member seats **seal** (amended 2026-09-28: the agent builds through the same `build_engine` as every host since that date, so it judges its own rows rather than receiving an anchor beside the keys). **Replay after a flip-back is refused by a device-held floor, not by the nest:** the seat persists, per folder, the counter it last armed under and a floor (`AttestationMemory`, a device-local `SyncDb` meta row for the engine seats); arming at counter *c* raises the floor to *c*, and **a successful list that does not verify the folder public burns the armed counter — the floor becomes *c + 1*** — so the attestation a seat saw withdrawn can never re-arm it, while a list the seat could not read changes nothing (the same keep-the-last-posture discipline the sync mode has). An honest re-flip always clears the floor because the minting client takes `max(now_ms, served_counter + 1)`, and the nest keeps serving the last attestation after a flip-back (inert — no reader consults it on a non-public row) precisely so that a second owner device with a slower clock still mints above it. The flip-back itself needs no attestation: sealing is always safe. **What a seat with no history trusts, stated plainly:** a fresh device, or one offline through the entire private interval, holds no floor, so it accepts any *genuine* attestation the owner once signed for this folder id and name — the nest can replay one, and only for a folder its owner really did make public at some point; no nest-mediated record can close that (a nest that can replay the attestation can roll back an owner-sealed rail blob such as `__drafts` to a fresh device just as easily), so the residual is accepted and named rather than papered over. **A folder created public** cannot carry the attestation on `fauna.folders.create` — it binds the folder id the nest mints at INSERT — so the creating gesture follows the create with the attesting update, and until that lands the folder **seals**; a re-sent `public` on an already-public folder re-mints, which is also how a folder declassified before this mechanism existed is healed (the owner re-confirms; nothing auto-mints, because a client that signs whatever audience its nest reports is the defect restated).

**Sealed at rest in both modes (Phase 3, built 2026-07-08 S1–S3); plaintext-at-rest is now only the pre-S4 legacy residue.** The **mail and calendar** kinds are sealed to the recipient's standing MSEK-derived recipient-mail HPKE keypair (mail ingest post-2026-07-19: a per-epoch derived sibling of it, for a recipient with a published schedule — § Capability tiering → Content-sealing epochs) at ingest **in both storage modes** — the formerly mode-conditional shape is retired: the two mechanisms that produced it, **no-seal-at-ingest** (the MTA / IMAP APPEND / CalDAV PUT / nest in-domain perimeter shipping parsed plaintext in plaintext mode) and **unseal-on-receipt** (relay mail opened with a deposited plaintext MSEK), are both **deleted** (design `2026-07-07-phase-3-sealed-both-modes-design.md` D1/D3; every seal site resolves the recipient key through the single D2 resolver — `CacheDb::get_recipient_seal_key` nest-side, `wsrpc.ResolveRecipientSealKeys` bridge-side — the seam that later becomes epoch-indexed). The CARv2 framing and floor metadata stay plaintext on disk in both modes (the Mail-body conformance row + [`message-segment-store.md`](message-segment-store.md) § At rest vs transport); the *payload* is uniformly sealed. **Legacy residue — RETIRED 2026-08-17.** Records ingested in plaintext mode before Phase 3 used to rest as literal plaintext in `__mail`/`__calendar`, converging to sealed via the **S4 boot-time public-key-only backfill** (`content_seal_backfill.rs`, built 2026-07-08), which resealed them to the owner's registered pubkey **in place, preserving each record's at-rest identity**. The 2026-08-17 record-identity cutover retired that path instead of letting it keep running: the cutover's boot reconcile tombstones every pre-cutover mail/calendar/card/conv record outright (an alpha-carve-out hard cutover, user-approved, not a migration — `principles.md` § No user-data loss; `message-segment-store.md` § Record identity per kind), so there is no raw corpus left for a backfill to walk — `content_seal_backfill.rs`, its boot call, its marker table, and its e2e harness are all deleted. A box that predates the cutover therefore holds no plaintext residue for these kinds post-boot: every surviving pre-cutover record was already sealed, and everything else was tombstoned. Server-side classifiers / FTS no longer read plaintext at rest in any mode — reading happens at capability positions only (the AUTH'd MDA session, the user's client, or a granted content-processing bridge; § Capability tiering), with the scored-before-visible timing bound owned by `content-scoring.md` § Timing. **Conversation messages *and restricted-post bodies* were never mode-conditional — sealed at rest in both modes throughout** (§ purpose test below + the Conversation-messages and Posts conformance rows). History of the design-(a)-vs-(b) decision this supersedes: the plaintext-content-at-rest design (ratified 2026-07-03; tracked internally).

**The read-position purpose test (formerly "the plaintext-at-rest purpose test").** The mode-era test — plaintext at rest requires both consent (plaintext mode) and a genuine read-at-rest purpose — retired *with* the mode: consent-as-a-deployment-posture no longer exists, so **nothing earns plaintext-at-rest any more** beyond the by-design classes above. What survives, and governs every new design, is the test's second half: **a purpose satisfied by reception-time or capability-driven processing never justifies storing plaintext.** A nest is an always-on relay/agent acting *for* the user's clients: it **keeps** what the user needs kept (relay, time-shifting while a client is offline, backup). The mode-era test demanded BOTH (a) deployment-wide consent (plaintext mode) AND (b) a genuine server-side purpose requiring the box to *read* the content at rest; with (a) retired, the nest keeps the **sealed** version of everything, and (b) survives as the question of *where reading runs*. The purposes split in two: *reasons to keep the data* — pure relay, time-shifting, and backup (backups are `BackupKey`-sealed by the client regardless; the nest never holds `BackupKey`) — are served perfectly by the sealed bytes, because they need the box to *hold* bytes, not *read* them; *reasons to read* — server-side compute the box does for the client: spam/abuse scoring (esp. of arbitrary senders), full-text indexing, classification, content preparation/enrichment, and serving read-only protocol clients (IMAP/CalDAV MUAs) that cannot decrypt themselves — require reading, at a capability position. An ungranted nest is the minimally-eavesdroppable baseline (only the plaintext floor — routing metadata, sizes, timestamps, roster — leaks). The read-position split is **per-content-kind, decided by purpose — never a per-user or per-kind at-rest toggle** (§ Don't do these): **mail**'s read purposes (third-party IMAP fetch, spam from strangers, FTS) are served at the AUTH'd session, the perimeter, and granted holders, while **conversations** (Fauna apps decrypt them, conversation FTS is a client capability, DM-abuse is metadata-gated) have no read-requiring purpose at any position — the end-to-end and transport-only classes, that is; a **community** room seats its home nest as a member with a wrap, and the purposes of that read are enumerated, closed, and bounded to metadata by [`../behavior/community-rooms.md`](../behavior/community-rooms.md) § The three classes → *What the home nest does with its read* (the Conversation-messages conformance row's declared exception, below). **Restricted posts** refine the test's crucial words — ***at rest***: their read purpose (FTS + classifiers) *is* real and their `derive_post_key` seal *is* openable by a key-holding receiver, yet they rest **sealed**, because that purpose is satisfied by reading the body **at reception** (transient-decrypt → index/score → keep the derived artifact, discard the plaintext), not by holding it plaintext at rest. So (b) means a purpose requiring the box to read the content ***at rest*** (persistently) — a purpose a reception-time or capability-driven pass satisfies does **not** earn plaintext-at-rest. Sealed-at-rest is the rule for every kind: the box reads content only transiently — at reception, or later under a user-minted capability (the content-processing-bridge pattern, design ratified 2026-07-04, tracked internally) — and keeps only sealed content + derived metadata. **One grant-gated refinement (2026-08-10): under the owner's materialization grant (§ Readable classes class 4), "keep the derived artifact" may keep it *readable* on that user's own nest** — the discard-plaintext rule stays binding at every other position, and the canonical content the artifact derives from stays sealed regardless. A nest is deliberately never an *authoring* device — it holds no identity signing key (rule #7) — so the worst a nest compromise yields is eavesdropping, never impersonation; keeping the identity off the nest is what bounds a nest breach to a recoverable content breach rather than identity theft (see § Trust property under compromise).

## Cross-flow behavior

Data-owner's storage policy follows the data: when data lands on a storage location, *that location's* policy governs how it's stored, but the data owner's keys (or absence thereof) determine what the location can actually see.

| From | To | Sender's "Sent" copy | Network transit | Recipient's storage |
|---|---|---|---|---|
| Any nest A → any nest B | different humans, or same human's boxes | sealed on A to the sender's own standing recipient-mail keypair | TLS (or in-process if same nest) | sealed on B to the recipient's registered keypair (B's MTA seals post-parse via the single seal-key resolver) |
| Backup of any nest's data on any other nest | | — | sync protocol over TLS | ciphertext on the destination nest, sealed under the data owner's `BackupKey` |

Notes:
- Cross-Fauna transit between MTAs is plaintext over TLS (same as today's mail). The privacy property differs at storage, not transit.
- The sender's "Sent" copy is sealed to the *sender's own* standing recipient-mail HPKE keypair (`owner-key-material.md` § Path B-sibling-2; not the recipient's), so the sender retrieves their Sent folder over IMAP with their own MUA credential. The MTA bridge produces both copies during outbound.
- Backups always travel as ciphertext sealed under a data-owner-derived key the destination never holds; the destination stores opaque blobs unconditionally. **Which key — split ratified 2026-07-23:** client-originated data (folders, `__drafts`, media, held-for-friends) under `BackupKey` (client-side seal, never nest-held — unchanged); nest-originated message-kind segments (`__mail`/`__conv`/`__post`/`__calendar`/`__card`) under `NestBackupKey`, sealed by the **source nest's** in-process coordinator — sound because that nest already hosts and floor-reads those segments, so the delegation adds no read power anywhere (`owner-key-material.md` § Path A-sibling-0 owns the key; the 2026-07-23 nest-side-segment-backup design record (tracked internally) is the design record). **Slice 1 (shared Rust) is BUILT (2026-07-23):** `NestBackupKey::derive` + its convergent chunk root (`libs/fauna-core/src/crypto.rs`), the `OwnerSealKey::{Client,SourceNest}` seam now carried by `SyncEngine`/`FileDownloadKeys` (a pure widening — every shipped client engine stays on the `Client` variant and seals byte-identically to before), and the `SegmentSource` trait a nest-hosted coordinator reads local segments through (`libs/fauna-sync-engine/src/segment_backup.rs`). **Slices 2–3 are BUILT too (2026-07-23 through 2026-07-29):** an owner grants their `NestBackupKey` to a source nest via `fauna.backup.nest_key.grant` (`bins/fauna-nest/src/backup_handlers.rs`, `db/nest_backup_keys.rs`), whose in-process coordinator (`bins/fauna-nest/src/segment_backup.rs`) seals and uploads to each registered destination over the nest→destination federation auth plane, with no client alive — tier_3-proven end-to-end (`bins/fauna-nest/tests/nest_backup_coordinator.rs`). **Coverage today is `mail` only** (`BACKED_UP_KINDS`, `bins/fauna-nest/src/segments/backup_source.rs`) — `conv`/`post`/`calendar`/`card` each need their own per-kind arm before the Backups conformance rows below describe more than mail as sealed under `NestBackupKey`; ## Search and indexing

A unified, Spotlight-style search across all of a user's content kinds — mail, calendar, conversations, posts, files, contacts, drafts, media — backed by a single per-user index. The index lives wherever the user has storage, replicates between those locations, and references content possibly stored elsewhere via fetch-on-demand.

The feature itself — engine, what's indexed, the build/query/sync model, per-app × per-mode availability, the classifier story — is specified in [`docs/goal/behavior/content-index.md`](../behavior/content-index.md); deeper mechanics (segment file format, classifier ledger, the exact UniFFI/WASM surface, AEAD seal/unseal, plan sequencing) are tracked internally (design ratified 2026-05-10), whose § Search availability by nest mode × client is the per-app × per-mode matrix. This section is the encryption-at-rest view: on conflict about index *mechanics* the internal design wins; on conflict about the *encryption-at-rest property* this doc wins.

**Index shape.** One per-user index, partitioned by content kind for query performance but a single logical store. The engine is Tantivy, wrapped by `libs/fauna-index/`; each kind's index is a set of immutable Tantivy segments, every segment AEAD-sealed and shipped through fauna-sync as the `__index/<actor>/…` reserved folder. Each entry: content kind, content ID, location pointers (which storage locations of the user hold this content), tokenized searchable text (body, subject, participants, etc.), metadata for sort/filter (timestamp, sender, attachment-presence). The tokenizer is shared Rust (`libs/fauna-mail/`, landed in I1) — same canonical tokens regardless of where indexing happens. NFKC normalization, Unicode word segmentation, optional CJK segmentation, stop-word and stem rules; deterministic across platforms.

**Where the index lives.** Replicated to every storage location the user owns: each of their clients (laptop, phone, etc.) and each of their nests. Replication rides the existing fauna-sync protocol; updates originate at the location that produces or receives the content and propagate to peers via additive merge. Conflict resolution and detailed merge semantics are owned by `docs/goal/behavior/conflicts.md` § Conflicts (re-pointed there 2026-07-10, per the registry). In practice not every replica *builds* the index — building happens only at a capability position, never on an *ungranted* nest (the storage-mode axis is retired; `nest/storage-modes.md`): a desktop app, the MDA bridge during an active session, or the owner's materialization-granted nest (§ Readable classes class 4 — which additionally keeps its own *readable* index of that user, a local derived artifact that never syncs) does the ingest work — decrypt → tokenize → seal → sync — while phones receive the synced segments and only *query* them, because iOS's (and, to a lesser degree, Android's) background-execution limits make continuous background indexing on a phone unreliable. A user whose only device is a phone may have a lagging-or-empty index until a builder device comes online (the content-index spec covers a foreground-incremental fallback for that case).

**Encryption posture.** The index is itself one of the user's content kinds and follows the same rules: sealed under the user's index key on every nest; queryable on the MDA bridge during an active session (session-scoped key), off-nest by clients holding the user's keys, or by a holder of a user-minted index grant — never by an ungranted nest. A materialization-granted nest (§ Readable classes class 4) additionally builds and queries a *readable* index of its owner server-side — the honest fast path for that user's `fauna.search.query` and IMAP SEARCH, and the one shape that gives the thin web SPA (and a phone-only user, whose builder-device gap the paragraph above names) full content search with no local engine. (Floor-derived search over the plaintext-by-design class — public posts, public previews — is the one server-side search every nest serves; § Readable classes.)

Index entries reference content stored elsewhere via opaque pointer (location ID + content ID + content hash). The pointer is index-encrypted, so only the index-key holder learns "this entry references content stored on location X."

**Where queries run.** Any storage location holding a readable copy of the index can serve queries:
- Nest-side queries over sealed index slices run on the MDA bridge during active IMAP/CalDAV sessions (session-scoped MLS-decryption authority unwrapped at AUTH), or under a user-minted index grant. Off-session and ungranted, queries run on the user's clients only. For results pointing to content stored on another of the user's locations, the reply carries a pointer; the client follows up via fauna-sync to fetch on demand.
- Native apps (Linux, Windows, macOS, Android, iOS, tui) each hold a full replica of the index and run the engine (`libs/fauna-index`) locally — directly on Linux and tui, via UniFFI on the other four; results pointing to content stored elsewhere are fetched on demand. **The fauna-web SPA is the one exception:** Tantivy can't run in a browser (it spawns threads; `wasm32-unknown-unknown` has none), so the SPA has no local index and no content search over this index until one of the fallbacks in the content-index spec ships (peer-device query over the relay, an MDA-bridge query backend, wasm-threads workspace-wide, or a thread-free Tantivy); it keeps the floor-derived server-side search over `fauna.search.query` (§ Readable classes). This is a property of the browser sandbox, not of iOS: the native iOS app indexes and queries locally exactly like the other native apps (decided 2026-05-11 — see the content-index spec's § Search availability by nest mode × client).

**Cross-device fetch.** Following a result that points to content stored elsewhere uses fauna-sync's on-demand fetch. The destination location may be online or offline; if offline, the result is returned with a "content unavailable, [device] offline" indicator. Composing search results with sync is a property of this design, not a separate mechanism.

**Cross-user search scope.** The index covers the user's own corpus only — including content received from other users (their inbox, accepted calendar invites, group conversations they're in) — but it does not index other users' private corpora. Content the user only sees because they're a participant inherits the encryption posture of the storage at the user's locations, not the original message-author's: a group conversation the user participates in is in their index sealed per this doc at every location holding it.

**Tokenizer and re-indexing.** Tokenizer changes (new language support, new normalization rule) require re-indexing. The index format is versioned; replicated indices declare their format version, and a user's locations agree on the version before merging. Re-indexing requires unwrapping the user's index key — during an active session, driven by a client, or by an index-granted holder.

## Content scoring and classification

Any algorithm that scores or classifies user *content* — spam pre-classification (ClamAV, rspamd), the per-user Bayesian, user filter / Sieve rules, feed ranking, future classifiers — must read plaintext to run. The at-rest property above therefore fixes where such an algorithm may run; [`content-scoring.md`](content-scoring.md) is the governing framework (the placement rule, the pure shared-Rust scorer shape, the scoring-metadata bus). The corollary it derives from this doc:

- The nest core **runs no content scorer at rest** on any deployment. Scoring happens where plaintext legitimately lives: the **mail-bridge perimeter** (pre-seal, the transient-plaintext carve-out), the **user's client** (post-decrypt), or a **granted content-processor** draining re-score obligations under a user-minted capability — a set that since 2026-09-10 includes the nest itself exactly where it holds a key by the owner's or the members' own grant (a community room's home nest, seated with its room-read wrap; an own-scope materialization grant), at reception and never at rest: [`content-scoring.md`](content-scoring.md) § The placement matrix's *capability-holder* row owns that placement and its bounds. Only the scorer's *output metadata* (score / verdict / label) is stored on the nest, as floor or deployment-data — never the content that produced it. Shipping plaintext to the nest purely to score it is forbidden; it would recreate the exposure the perimeter carve-out bounds.

This is the same shape § Search and indexing takes for the index classifier, and `mail-forwarding.md` §§ 198/248 take for forward-rule eval. On conflict about the at-rest property, this doc wins; about the scorer-placement framework, `content-scoring.md` wins.

The eval *timing* is one half; the forward *config at rest* is the other (`mail-forwarding.md` § Storage-mode interaction → Where the forward config lives at rest): **all** forward config — **user** forward config (`forward_all_to` + per-rule `forward` destinations) and **admin** external forwarders (`account_aliases` `kind='forwarder'`, `mail-aliases.md` § Kind 7) alike — rests in the **plaintext floor in both modes**, like every other `account_aliases` row, the catch-all designation, and `local_domains`. The MTA reads it directly at the perimeter to make the forward decision. (These are config, not a content kind, so they extend this § rather than the per-content-kind table — same as the DKIM/TLS keys.) **Deferred upgrade:** sealing *user* forward config wrapped-to-the-MTA-bridge-service-user pubkey (the bridge-readable `TlsCertBlob` class — opaque at nest rest, HPKE-Opened only at the perimeter, distinct from the owner-sealed user-settings row (the account-state plane kinds), which no nest or bridge can open) is a planned additive upgrade for separate-bridge deployments, where the seal's protection against nest-disk theft is real (it is co-resident-theater single-box). Tracked internally (§ N1b); until then user forward config is plaintext floor.

## Capability tiering (the trust surface; formerly "by storage mode")

The trust property has a system-wide corollary: **a content operation — serving, searching, or scoring user content — runs at a capability position, and which positions exist for a given box is its grant set.** Every feature is available everywhere; only its *execution position* varies: content serving is the AUTH'd MDA session opening records per-record ([`../behavior/imap-server.md`](../behavior/imap-server.md) § Content path); search over sealed slices is the session, the client, or an index-granted holder (§ Search and indexing); scoring is the perimeter, the client, or a granted content-processor (§ Content scoring and classification). A box holding broad standing grants does all of this server-side — the old plaintext mode's capability, now data the branch checks. A grant may also be **keyless** — conveying sync-custody authority with no read reach at all: the account plane's custodian replicas admit on exactly such a grant ([`account-replica-posture.md`](account-replica-posture.md) § Replica posture owns that concept). The one non-tiering case, per [`content-scoring.md`](content-scoring.md): a *deployment-wide* pre-classifier that needs no per-user secret runs at the **mail-bridge perimeter on every nest** (the uniform, branch-free shape) — the perimeter holds inbound plaintext regardless of any grant.

**The tier ladder, stated once (2026-08-10):** a grant conveys, in increasing reach — **keyless custody** (sync-custody authority, zero read reach), **scoped read** (open the named scopes at capability positions; artifacts kept are sealed-or-metadata per the purpose test), and **materialization** (scoped read *plus* the right to keep readable derived views of the named own-actor scopes at rest — § Readable classes class 4; nest-only holder in v1). For account-plane class-2 kinds, the grantable universe is bounded one level below the ladder: only **delegable-rung** kinds are mintable at all — fleet-only-rung kinds (operational secrets) sit on a key branch the grant machinery structurally cannot reach, at any tier ([`account-data-taxonomy.md`](account-data-taxonomy.md) § The audience ladder owns the rung model; R13, 2026-08-11). A materialization grant is standing/auto-renewed by nature (a view that dies weekly is churn, not a feature), its concrete scope-string and holder-identity shape finalize at first build (additive grant-plane vocabulary, no new crypto), and its revocation obligates the holder to delete the views — the delete is logged against the grant, and its enforcement bound is the honest one stated in class 4.

**Third-party holders (ratified 2026-09-05, the third-party integration chain — rulings TP4 and TP11; the principal model is [`third-party.md`](third-party.md)).** A grant's holder may be a **third-party principal**'s X25519 key — an approved remote server, device app or nest-hosted plugin — minted by the user's own app exactly as a grant to a nest is: declared `scope: Vec<ScopeTuple>`, a window, HPKE-wrapped minimal derived keys per tuple × epoch, under the scope-narrowness rule of [`key-material-hierarchy.md`](key-material-hierarchy.md) § Don't do these. Today the holder must be an admin-approved bridge service user or the in-process `ContentProcessor` (`bins/fauna-nest/src/bridge_method_allowlist.rs`, the `ContentProcessor` arm, admitted via `register_service_user`) — widening the holder class is the gap. Three things change with the holder class. **(1) The grantable set is bounded by the arm (TP4):** a *remote* principal is grantable only over scopes it created — its own `ext.*` kinds, a folder it made — never a read grant over the user's pre-existing sealed scopes (mail, existing folders, conversations, personalization models); those are reserved for **device apps and nest-hosted code**. A remote service that must process such data ships a hosted plugin; a remote AI agent's nest-hosted half holds the grant and answers with derived views, never keys. Per-folder sharing to a principal through the ordinary audience mechanism is a separate user act under the audience ladder, not under this rule. Revocation stays honest-box for every kind but mail (the bound stated above); TP4 is what makes that acceptable — the only remote holders are holders of scopes they created. **(2) Two new classes beside `content.read` / `content.label-write`:** `content.write` over the principal's own `ext.*` kinds — **keyless** (ruled 2026-10-02, correcting the 2026-09-05 "write half of the branch": the kind's `{entry_key, item_blind}` pair is one symmetric unit that read already conveys, so what the class carries is the owner-signed authorization naming the holder's attested Ed25519 writer key as an author of the kind, minted at consent beside the per-kind `content.read` tuples that carry the pair — [`third-party-kinds.md`](third-party-kinds.md) § Principal write authority owns the key, the fields and who admits a principal-authored row), and **`deposit`**, which carries *no key at all* — the audit + revocation record for a write-only folder ingress the nest seals on the user's behalf ([`../behavior/file-sync.md`](../behavior/file-sync.md) § Third-party deposit ingress); a keyless class is the shape `content.label-write` and `content.read{spam-model}` already take. **(3) A third keyless class, `identity.op`**, authorizes the **oracle** — the principal may ask the first-party key custodian to perform named operation classes against named keys, and never holds the key; its policy table, the sovereign deny list, and who mints it are [`key-material-hierarchy.md`](key-material-hierarchy.md) § Audience: deployment infrastructure → *The oracle*. Every scope a third party is granted has its **twin on the consent card** — the card row says what the token permits and what keys will be wrapped, in words ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Scope grammar). The per-rung partition (A5, [`account-data-taxonomy.md`](account-data-taxonomy.md) § The audience ladder) is built, and the per-kind sub-scope a `content.write` grant subscribes is ruled ([`third-party-kinds.md`](third-party-kinds.md) § The `ext` sub-scope) and ships with the first such grant. **The folder read twin is no new class (ruled 2026-10-05):** `fauna:folder:read:<id>` carries the existing `content.read{folder, set}` tuple — the paywall grant's shape, one wrap per content-key generation — held by the principal's key over a served set only; its mint, delivery to the bearer door, renew on rotation and revoke on unserve are [`../behavior/webdav-server.md`](../behavior/webdav-server.md) § Key model → *A principal's read*.

**The fallback is always present, so server-side is an optimization.** For a per-user operation the client holds the keys (post-decrypt), and native apps keep a full local index replica so search works with no server-side help (§ Search and indexing → Where queries run); the AUTH'd MDA session is the bridge-side fallback during an active IMAP/CalDAV session. Plaintext-mode server-side execution is therefore an optimization over an always-available client/bridge path, not the only path — so a plaintext nest is *more capable*, never *required*, for any per-user content operation.

**The general extension — background re-processing under a user-minted capability (BUILT — Phase 2, 2026-07-06; design spec).** The three server-side positions above (serve / search / score) are all *reception-time or serve-time* — a key-holder reads content it already holds. The one operation that reads *content at rest later* — re-scoring on a model change, re-indexing on a tokenizer bump — is the target of the **content-processing-bridge + scoped-capability** pattern (design ratified 2026-07-04; tracked internally); it generalizes the MDA/FTS/DKIM prior art into one primitive and is the substrate under [`content-scoring.md`](content-scoring.md)'s compute abstraction. **Load-bearing honest bound (that spec's § Phase 2 Step 1, resolved 2026-07-04): a capability's "time limit" is NOT cryptographically enforcing on _future_ content until the target kind is sealed under a rotating _content-sealing epoch_ — and no content kind is today** (every at-rest base key is standing, rotating only on membership events — MSEK hard-revoke, subscriber removal, MLS commit). So on an untrusted box a background grant is a **standing "trust-until-revoke" grant, not a crypto-time-boxed one**, until the per-kind re-key that introduces such an epoch lands (mail's landed 2026-07-18/19 — § Content-sealing epochs below; not part of Phase 3 itself, which sealed mail/calendar to one standing key). Scope and un-forgeability *are* crypto-self-enforcing; expiry's teeth are at off-box key-acquisition and future-only, and even then only over an epoch-sealed kind. The primitive is now **BUILT** (Phase 2 — the nest re-score drain plane + the Go MDA drain worker, proven end-to-end tier_3 on 2026-07-06; [`content-scoring.md`](content-scoring.md) § The re-score drain plane). The honest bound above governed every kind through the write flip (2026-07-19); mail is now the sole exception (§ Content-sealing epochs below) — a post-flip bounded mail grant's window is a genuine cryptographic bound. Every other kind (calendar, conversations, restricted posts, …) still has no content-sealing epoch, so a background grant over them remains standing trust-until-revoke. § The sealed posture remains authoritative for reception/serve-time content handling; this primitive is the additional *at-rest re-processing* path (re-score on a model bump, re-index on a tokenizer bump). **The full wire shape is built** (that spec's § Phase 2 Step 2): the `GrantBlob` CBOR shape, the one new `for_capability` HPKE-AAD arm (no other net-new crypto) — a scope tuple's two optional qualifiers, `set` (the folder scope, 2026-07-12) and `factor` (the per-labeler license: `labeler:<id>` confines a `content.read` wrap to computing that one labeler's score and a `content.label-write` tuple to writing that one factor; absent = the built-in perimeter factors; 2026-09-27), join that AAD only when present, so every older grant's bytes and binding are untouched and a store can never re-label a wrap as licensing a different set or labeler, the owner-minted / holder-fetched `fauna.capabilities.{mint,fetch,renew,revoke}` RPCs plus the drain plane's `{rescore_worklist,submit_scores}`, and the re-score obligation reusing `content-index.md`'s per-user `tokenizer_version` watermark against the `model_versions` bus. A fifth owner-side kind, `fauna.capabilities.reconcile` (an ids-only reconcile sweep — a reconcile read, never an audit read), is **RATIFIED 2026-08-15 and BUILT end-to-end (nest half 2026-08-15, client sweep 2026-08-16)**; its polarity argument and every constraint on it are owned by `ui/nests.md` § Trust facet — grants → *Reconcile*.

**Content-sealing epochs (mail first) — DESIGNED 2026-07-18; B1–B5 BUILT 2026-07-18; write flip THROWN 2026-07-19.** The per-kind re-key that upgrades the honest bound above from advisory to cryptographic is now funded, designed, and **built** for **mail** (launch consumer, user-ratified 2026-07-18: a standing background scorer/indexer on an untrusted box; design spec tracked internally, built as five slices — shared-Rust derivation, client mint/renew, pubkey schedule, gated ingest cutover, holder/drain honoring — the last proven end-to-end on a real nest: a windowed grant cannot open content sealed one epoch past its held set even holding every key it ever fetched). Mechanism in brief — the design spec is the frozen rationale, this paragraph is the owner-doc summary: the mail sealing epoch is `floor(unix_seconds / MAIL_SEALING_EPOCH_SECS)` (weekly; a hard-coded per-kind Rust constant — no config surface); per-epoch keypairs derive independently from MSEK (client-side root, forward-bounded by construction — no hash chain); the owner's client pre-publishes a ~26-epoch pubkey schedule so the MTA can seal with no client online, with a never-bounce degradation (stale schedule → newest published epoch key → standing key; mail ingest never bounces on epoch machinery); the nest bounds that schedule table nest-side (hardening 2026-07-19): a provision's epoch indices must sit within ±2× the publish horizon of the current epoch and each actor's stored schedule is capped at 64 rows with prune-oldest (`MAX_ACTOR_EPOCH_SEAL_KEY_ROWS`) — provision-write-path guards only, ingest untouched; the `MailRecordEnvelope` byte-shape is unchanged (openers select keys by record timestamp + a bounded trial chain); a mail grant is either **bounded** (per-epoch wraps only) or **master-key** (standing wrap) — never both in one grant, or the window would be theater (the nest's renew handler enforces it over the merged wrap set, `wall_clock_epoch_regime_conflict`); and a bounded grant's window is never wider than its wraps: a renew that moves a per-epoch wall-clock scope's end across a sealing-epoch boundary must carry a wrap for every epoch it newly covers, or the nest refuses it (`uncovered_bounded_extension`, added 2026-09-27 — the extension epochs are `epoch_of(old_end) + 1 ..= epoch_of(new_end)`; an equal-end renew, the rotation heal's shape, extends nothing), so a keyless bump can never advertise a window whose tail no key opens. **Wrap retention — the window SLIDES, it never grows (ratified 2026-09-28; BUILT the same day):** a renewal re-centres the window on the renewal instant — the end moves to `now + L` and the start to `max(old_start, now − L)`, L the grant's mint-time length (`grant_log::renewal_window`, the ONE computation the manual renew and the auto-renew loop share) — so a renewed grant keeps one mint-length of history behind the renewal and one ahead, and its window is never wider than 2L (at most 27 weekly epochs for the standard ~90-day grant). The renew carries the new start (`RenewGrantRequest.new_epoch_start`, additive; absent keeps the stored start, which is also the folder kind's shape — its wraps are generation-indexed, not calendar epochs); the nest refuses a start that moves backward (widening into the past would need wraps the renew cannot prove) or past the end, and on EVERY renew prunes every per-epoch wall-clock wrap below `epoch_of(start)` from the merged set (`fauna_mls::wrapped_blob::prune_wraps_below_window_start`), so the held epoch set is exactly the window's epochs; the rotation heal re-wraps the *recorded* window as it stands (an equal-window renew), so both client drivers and the nest agree on the retained set. Why a ruling was needed: without retention every renewal appended one wrap per newly covered week for ever — a wrap is ~2.5 KB to a classical holder and ~3.6 KB to a post-quantum one (the 2432-byte per-epoch secret plus KEM ciphertext and framing, k × 2432 at a rotation-boundary epoch), so a weekly-renewed grant crossed the nest's then-64 KiB blob cap within months of renewals and the silent auto-renew loop went dark with only the liveness pill saying so. The cap is now 256 KiB (`MAX_CAPABILITY_GRANT_BYTES`, sized from the 2L bound with rotation headroom — a nest constant, never a knob). Rejected: keeping full history and scaling the cap (unbounded growth, ~220 KB at 60 epochs and rising for ever), and re-minting at a threshold (a fresh mint covers no history at all and churns the log twin). The trade the ruling accepts: a holder can no longer open content sealed more than one mint-length before its latest renewal — a scorer or indexer has processed it by then, and its derived views persist under the materialization tier; the user-facing duration stays the trust's *lifetime*, not its lookback (`ui/nests.md` § Expiry / renewal → *Duration and blessing*). Proven by the nest handler test that renews a post-quantum bounded grant weekly through 60 epochs and stays accepted with exactly the slid window's epochs held. **MSEK-rotation heal for bounded grants (amendment 2026-07-19):** a grant carries at most ONE wrap per `(scope, epoch)` — universal for wall-clock kinds, mint-side and renew-side alike (the builder refuses duplicate per-epoch wraps; the nest's renew replaces a differing-bytes wrap in place) — and cross-generation coverage rides *inside* the one wrap: an epoch that more than one MSEK generation could have sealed (a rotation-boundary epoch, plus its one-epoch propagation tail) gets a payload concatenating each such generation's 2432-byte per-epoch secret, newest first, chunk-trialed at the single shared length-dispatch site with AEAD arbitrating (the same try-each shape as the folder kind's two-keys-per-version CRDT precedent). Which generations qualify is computed from **recorded rotation instants** (`MailConfig.prior_msek_retirements`, additive, keyed by the prior-MSEK value): each generation covers epochs from its activation to its retirement + 1; every rotation records the instant in the same write that retains the generation, so a retained prior always carries one (the pre-amendment reading — a prior with no recorded instant is provably pre-flip and skipped — was retired 2026-09-24 by the compat-remnant sweep ([`compat-remnant-sweep.md`](compat-remnant-sweep.md) § Program 4); an unrecorded prior is now an inconsistent config and still contributes no epochs, since its interval is unknowable). This makes the renew replace-heal lossless across rotation boundaries and lets a post-rotation bounded mint cover pre-rotation in-window content; the old generation's epoch-*root* is never wrapped into a grant (it would reach old-lineage epochs beyond the window). `WrappedScopeKey.epoch` is a per-kind key-lineage index: for `folder` it is the content-key **generation version** (landed); for `mail` (and later `calendar`) it is the wall-clock sealing epoch; the AAD's kind binding keeps them cryptographically disjoint. Legacy content stays sealed under the standing key forever (zero re-seal, no data loss); the epoch regime applies to newly ingested mail only, behind **two gates**: per-recipient schedule publication (automatic — and since the 2026-09-24 compat-remnant ruling the client publishes it unconditionally: the `mail-epoch-schedule` advert and the absent-advert `None` degrade are retired together with `pq-hybrid`'s, `security/post-quantum.md` § Capability negotiation; **Multi-nest.** A user may run several nests holding different grant sets at once (§ Goal); each location does what its grants permit, and a client holding the content locally self-serves regardless. The refinement of **preferring a reachable broadly-granted nest's server-side path and falling back to local/bridge work when none is reachable** — a cross-nest capability negotiation — is the intended direction but is **not yet specified or built**: today's connect-time capability negotiation ([`version-compatibility.md`](version-compatibility.md) § Dimension 3) carries feature-family tokens, and no doc yet defines routing server-side work to a granted peer. It matters only for a **thin client** (the fauna-web SPA, which cannot run the index engine — § Search and indexing); every native app already self-serves locally, so the negotiation is an efficiency refinement, not a correctness requirement.

**Cross-user operations have no client fallback → they require every contributor's grant, or they are not offered.** An operation that must read *several users'* content — the deployment spam-baseline aggregation ([`../behavior/mail-spam.md`](../behavior/mail-spam.md), `publish_spam_baseline`: an additive merge of opt-in users' per-user models) — cannot fall back to any single user's client, which holds only that user's keys. With no plaintext mode to gate on, such an operation runs only at a position holding a reaching capability from **each opt-in contributor** (opting in = granting read of the contributed artifact); a deployment where contributors have not granted simply does not offer the baseline. The feature degrades with the granted trust, exactly as it degraded with the mode. A secure-aggregation scheme removing the grant requirement is a possible future addition, not a current requirement.

## Carve-outs and known plaintext-floor items to tighten

Not blocking but worth tightening over time (the first four are tracked in the mail-bridge spec):

- **Hash recipient local-part on inbound MX routing** (mail-bridge Task 18). Replaces plaintext `local_part → actor_id` mapping with `H(local_part) → actor_id`. Defeats `*@domain` enumeration from a compromised nest.
- **Hash envelope FROM on inbound** (mail-bridge Task 19). Removes "who-emails-whom" graph from plaintext metadata.

The Folder files / Backups (own data) conformance rows now describe the sealed posture.
- **Mail `report_hash` — RATIFIED 2026-09-27 as an accepted residual, not a tightening.** The only content-derived floor item (§ Plaintext floor) stays unkeyed and resident for every mail; any tightening (keying, sealing, report-time computation) is a report-sharing mechanism change owned by `../behavior/report-sharing.md` § Threat model & accepted limitations, which states the oracle's bound and why each alternative breaks the ratified attach/late-copy/nest-attested binding.
- **The flip's self-backup window — RULED 2026-08-01 (*ratified with a named bound*, not fixed).** The nest's own disaster-recovery hot-copies (`behavior/backup-restore.md` § 11: hourly `rusqlite` hot-copy of `nest.db`, keep-last-24, written **unencrypted** in production) are full pre-scrub DB images the S9 scrub + VACUUM never touches, so the scrubbed name/path planes outlive the flip inside them. Ruling: **the flip does NOT invalidate the self-backup store — the window is ratified, bounded by the existing rotation, and named here.** *Invalidate at the flip* was rejected because those images are the only rollback for a user-approved destructive migration at the exact moment it runs — a no-user-data-loss hazard, which outranks a bounded confidentiality window whose adversary (the hosting-nest operator, or any at-rest reader of the box) lawfully held the identical plaintext until the flip. *Invalidate once the flip is confirmed good* was rejected as machinery without a payer: it shrinks an already-marginal exposure from ~a day to ~minutes at the price of a new post-flip state (confirmed-but-not-yet-invalidated) whose crash windows would need their own boot reconcile. **The named window:** pre-flip plaintext rests in at most 24 hot-copy blobs until **count-based** rotation replaces them — `prune_backup_snapshots` deletes row + blob + manifest after every backup, and after 24 post-flip backups every pre-scrub row (and so every pre-scrub blob, shared-hash or not) is gone — i.e. the window closes after 24 post-flip backup cycles, ≈ 24 hours of nest **uptime** (wall-clock longer only while the nest is down, when the box serves nothing). Three requirements are part of the S9 flip contract so the bound is real rather than assumed: **(1)** the flip takes a fresh hot-copy immediately after scrub + VACUUM commits, so a clean recovery anchor exists from the first minute and no later restore path depends on a plaintext-bearing image; **(2)** the scrub is **idempotent and boot-reconciled** — restoring any pre-flip image re-runs it before serving, so a disaster restore inside the window cannot silently reopen the plaintext planes; **(3)** the D5 byte-scan proof extends over the self-backup store on the rotation clock — rotation is count-based, so the pin drives `backup_database` 24× synchronously (latency-independent by construction) and asserts no remaining self-backup blob carries the scrubbed marker, with the named mutation (rotation withheld / retention raised) reddening at the marker while an ordinary user-content blob stays out of scope (the self-backup verify contract items 1, 2 and 4). **All three were BUILT 2026-08-02; (1) RETIRED with the flip by the 2026-09-24 genesis of the nest schema** (`nest/common.md` § Database), under which no pre-flip image exists, so no restore path can depend on one — the steady-state window (keyless-writer plaintext a hot-copy captured before the boot scrub cleared it) was never (1)'s to close and stays bounded by (2) and the rotation: (2) the every-boot scrub, `run_scrub_plaintext` in `run_migrations`, which re-runs on any restored image before it serves and `VACUUM`s when it cleared anything; (3) `conformance_at_rest_byte_scan.rs::the_self_backup_store_rotates_out_scrubbed_plaintext` — 24 synchronous `backup_database` cycles, the 23rd-cycle positive control standing in for the named mutation, an ordinary content blob pinned out of rotation's scope. Encrypting the self-backup blobs under the deployment-key subkey (the `cursor_seal` precedent) was considered and rejected **for this finding**: that key rests on the same box, so it withholds nothing from the at-rest reader this ruling names; a future off-box backup destination carries its own key question. The daily logical dump is out of scope — `DUMP_TABLES` omits every name-plane table, **pinned since 2026-08-15** by `export::logical::tests::the_dump_carries_no_sealed_plane` (it was a point-in-time manual verification before that): the gate walks the live schema for `sealed`/`*_sealed` columns and fails if any such table is in `DUMP_TABLES`, so it also catches a sealed column newly grown on a table the dump already carries. ⚠ This makes the dump's hand list a **confidentiality boundary rather than drift** — `account-data-plane.md` § Nest-side requirements item 1 lists it as unclaimed W1 follow-on, and pointing it at `ACTOR_TABLES` or at a whole-schema walk would pull the name-plane tables in and break this carve-out's scope bound; the constant's own doc comment carries the warning.

These tighten the plaintext floor — the entire surface visible to an ungranted box owner — and apply universally if/when implemented.

## Migration

**There is no mode migration** — there are no modes to migrate between, and the offline `migrate --to` subcommand the mode era specified was never built and is retired unbuilt. What the mode-era migration protected is handled elsewhere:

- A formerly-plaintext box's raw at-rest records for mail/calendar were sealed **in place, identity-preserving,** by the Phase-3 boot-time seal backfill (`content_seal_backfill.rs`) through 2026-08-17 — **retired that day**: the record-identity cutover's boot reconcile now tombstones any pre-cutover mail/calendar/card/conv record outright instead of resealing it in place (an alpha-carve-out hard cutover, user-approved, not a migration — `principles.md` § No user-data loss), so the backfill module and its marker table are deleted, not still running (`nest/storage-modes.md` § Legacy artifacts; `message-segment-store.md` § Record identity per kind).
- The trust a plaintext deployment expressed is re-expressed as grants each user's client mints (broad + auto-renewed for a blessed box); "tightening posture" is revoking grants, and "trusting new hardware" is minting them — no offline tool, no downtime, reversible per scope.
- Identity, backups, and floor data were never mode-dependent and are untouched.

## Trust property under compromise

**Broadly-granted-box compromise (the old "plaintext-mode compromise", improved).** Attacker on a box holding broad content-read grants reads the granted scopes of the granting users, for the life of the grants — and **nothing else**: no identity signing key lives on any nest (grants never reach it, rule #7), so the attacker eavesdrops on granted content but cannot sign-as-user or impersonate anyone to the federation — a strictly smaller blast radius than the retired plaintext mode, whose box held the users' MLS read keys and whose owner was unrecorded. Each user's exposure is individually bounded by their own grant set and ends at revocation/expiry; the client-authoritative grant log records which boxes held reaching capabilities during the window. For a user holding a materialization grant (§ Readable classes class 4) the attacker reads that user's views directly rather than via the granted keys — the same reach, one fewer step — and post-revocation the sealed state is restored by the view deletion the revocation obligates. Ungranted users on the same box have only the floor exposed. Federated content the nest holds for *other* users (backups for friends) stays opaque — no keys for those owners on this box.

**Ungranted-box compromise (the old "encrypted-mode compromise" — now the baseline of every nest).** Attacker reads routing metadata, audit logs, IMAP flags, mailbox structure, ciphertext sizes, counters. **Cannot read content** (encrypted under per-user MLS keys nest doesn't have). **Can sign DKIM as the deployment's domains** (the DKIM key is the nest's own deployment-infrastructure secret, sealed under a key derived from the deployment seed the box also holds — `key-material-hierarchy.md` § Audience: deployment infrastructure → *The oracle* → *The DKIM class is the outbound spool's own door*; it opens no content, and a box that mints the key and names its published half could always sign as the domain). **Cannot impersonate any user** (no password hashes, no token verification). **Cannot serve TLS for the deployment's domain** (TLS private keys held at bridges as ciphertext blobs). Materially stronger property than Proton's: Proton's server holds DKIM keys and verifies auth; ours doesn't.

**Ungranted-box compromise + a target user's IMAP/CalDAV/CardDAV/WebDAV credential.** Attacker fetches that user's `WrappedMsekBlob` and unwraps with the credential, recovering MSEK. Reads that user's **mail, calendar, and CardDAV address book** (going forward and any historical mail / calendar / vCards still stored) plus their **mail/calendar search-index slices** — and additionally unseals the `WebdavKeysBlob` to read (and write) **the folders that user explicitly flagged "serve over WebDAV"** — and nothing more. By the blast-radius invariant (`key-material-hierarchy.md` rule #7) the MUA credential does **not** reach the user's conversations, group-restricted posts, the rest of their search index, **unserved folders**, `BackupKey`-sealed content (drafts / backups / library media), the fleet-only plane kinds (the user's settings and the private contact overlay among them), or the identity/signing key — so the attacker cannot read the user's messages, decrypt their other content, or impersonate them on the federation. (The blast-radius change each DAV surface introduces: CardDAV added the address-book vCards — same recipient keypair, no new key; WebDAV adds the explicitly-served sets' M2 content keys — per-set, user-opt-in, revoked by rotation; the private contact overlay and every unserved set stay out of reach.) Same outcome as direct credential compromise plus access to the served surfaces at rest — the standard worst case for any encrypted storage where decryption capability and at-rest data live on the same machine, here bounded to the mail/calendar/contacts/served-files surface the credential serves.

**Cross-deployment mail.** Sender's nest stores the "Sent" copy sealed to the sender's own keypair; the recipient's nest stores the delivered copy sealed to the recipient — regardless of what either box's users have granted it. Network transit is plaintext over TLS, same as any mail. The privacy property differs at the grant table, not on the wire.

## Architectural rules

- **There is no storage mode.** Sealed-at-rest beyond the floor and the readable classes is universal; a box's read capability is its grant set, controlled from the user's apps (`nest/storage-modes.md` owns the retirement + shims).
- **There is no per-user or per-deployment encryption toggle.** The *canonical* at-rest byte shape is one shape; grants change who can *read*, never how canonical bytes rest. The one grant tier that changes what may additionally *rest readable* is the materialization tier's derived views (§ Readable classes class 4) — derived state, never canon, never the wire.
- **The plaintext floor is identical everywhere.** Shared `libs/` enforces the floor; everything beyond it differs only by grant set.
- **Federation is grant-blind.** The wire never carried the mode and never carries the grant table; a peer cannot tell what a box's users have granted it. Nest-side sealing applies to nest-side storage only.
- **New content kinds extend the per-content-kind conformance table in this doc** in the same commit that introduces them. Default for new kinds: floor = whatever routing metadata the nest must read; everything else sealed.
- **Search index follows the user.** Each user has one logical index, replicated to all of their storage locations, sealed at each. No nest-spanning index that crosses user boundaries.
- **Identity is unified across a user's storage locations.** Same MLS keys and actor ID on every box and client; grants never change identity, and no grant reaches the identity signing key.

## Don't do these

- **Don't reintroduce a storage-posture flag** — per-user, per-kind, or deployment-wide. The canonical at-rest shape is one shape; read capability is a grant, which is data a branch can check. (A materialization grant is not such a flag: it is grant-plane data — client-minted, scoped, revocable, audited — it covers derived views only, and it changes no canonical byte, no wire behavior, and no serving ACL; § Readable classes class 4.)
- **Don't store any new content kind in plaintext** without a readable-class justification and a row in the conformance table here.
- **Don't expose APIs that let the nest core decrypt user content.** No in-process MLS keys on any nest. Decryption authority is the MDA bridge during active sessions, the user's clients, or a holder of a user-minted grant.
- **Don't leak trust state on the wire.** From a federation peer's perspective every nest looks the same — no protocol field may reveal a box's grant set (as none ever revealed its mode).
- **Don't index across user boundaries.** Each user owns their own index; no nest-spanning index covering "all users on this nest." Privacy depends on per-user index isolation.
- **Don't have the nest mint, widen, or renew its own grants.** Mint authority is the user's client, off-box — the confidentiality boundary of the whole design.
- **Don't add a scope kind whose wrapped key opens more than the scope names.** A grant is only as narrow as its `WrappedScopeKey` *payload* — the `ScopeTuple` is advisory metadata, and `AadBinding::for_capability` binds who may unwrap the *grant*, never what the key inside may *open*. A content kind that shares another kind's seal key therefore cannot get a narrower scope by being given a new `kind` string; it needs its own domain-separated key first, or a keyless scope conveying the artifact rather than the key. Rule + the live instance (`content.read{spam-model}` over the recipient-mail secret — resolved 2026-07-13 to the keyless + artifact-sealed-to-holder shape): [`key-material-hierarchy.md`](key-material-hierarchy.md) § Don't do these + rule #7, which owns this; flow in `../behavior/mail-spam.md` § Encrypted-mode interaction.
