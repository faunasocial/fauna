## The rule (one sentence)

> A content scorer runs at a trust position **only if every input it needs is available there**; its output — reduced to a score / label / verdict — is persisted as floor or deployment-data metadata that any later scorer can read from any position.

Everything below is the consequence.

---

## Why this is a corollary of encryption-at-rest, not a new policy

`encryption-at-rest.md` already fixes the trust property: every nest stores user content sealed at rest beyond the plaintext floor — there is no storage mode, no deployment posture that holds content readable (`encryption-at-rest.md` § The sealed posture; the retirement mechanics are `nest/storage-modes.md`'s). So a content scorer, which must read content to score it, can never run in the nest process — the nest never legitimately holds plaintext beyond the floor, on any box. This doc's placement rule is the content-scorer instance of the same corollary that governs *serving* and *search*; [`encryption-at-rest.md`](encryption-at-rest.md) § Capability tiering is the umbrella statement (with one refinement: a deployment-wide pre-classifier that needs no per-user secret defaults to the perimeter uniformly — § The placement matrix).

A content scorer must *read content* to score it. So the at-rest property already decides where one may run: the nest has only ciphertext + floor metadata → **it may not run any content scorer.** It may store and serve scoring *metadata*; it must never compute it from content.

That's the whole game. The nest is the persistent store under the box owner's physical control, and "the box owner cannot read content" is the property. Computing a content score *in the nest process* would require plaintext in the nest, puncturing the property. So a content scorer must run somewhere that legitimately holds plaintext — and there are exactly two such places.

---

## The two plaintext positions

1. **The perimeter (the mail bridge), pre-seal.** Inbound external mail arrives at the MTA in plaintext; the MTA *must* hold it to verify, score, and seal it to the recipient. This is the already-accepted transient-plaintext carve-out in `encryption-at-rest.md` — and it is scoped to the **perimeter**, not the nest. A bridge is a "lightweight scoring client": a deployment-side component trusted with transient plaintext at the ingest edge. It runs the perimeter scorers, then seals; only the *result metadata* crosses to the nest. Prior art: `mail-forwarding.md` § 198 ("an MTA-perimeter decision, happening on plaintext bytes the MTA already holds in-process during the inbound DATA stage") and `mail-spam.md` § Pipeline ("at the MTA's DATA-end / pre-delivery stage").

2. **The user's client, post-decrypt.** The client holds the user's keys and can decrypt content the user owns. Scorers that need content the perimeter doesn't have, or a per-user secret, run here — after delivery.

The nest is **neither** of these. It is the persistent store. Shipping plaintext *to the nest* purely to score it (e.g. a `scan_message_content(plaintext) → nest` RPC) is the **anti-pattern** this doc forbids — it recreates the exposure the perimeter carve-out exists to bound. `mail-forwarding.md` § 248 already names the sibling mistake ("a rule evaluator runs on the stored ciphertext … is the wrong shape and would break the sealed-at-rest invariant"); shipping plaintext to the nest is the same error from the other side.

## Input classes

A scorer's inputs fall into three classes, and the class is what gates placement:

| Input class | Examples | Where it's available |
|---|---|---|
| **Metadata** (prior scores, floor fields) | a prior ClamAV verdict, rspamd score, SPF/DKIM/DMARC verdicts, DNSBL hits, timestamps, sizes, sender domain | **Everywhere.** Floor / deployment-data is always plaintext (`encryption-at-rest.md` § Plaintext floor) and is servable to clients. Portable to nest, bridge, and client. |
| **Content** (the plaintext body / headers / attachments) | "does the body contain `INVEST NOW`", MIME-structure rules, n-gram features, malware signature match | Only where plaintext lives: **bridge** (perimeter, pre-seal), **client** (post-decrypt). Never the nest. |
| **Per-user secret** (a sealed per-user model / rule set / key) | the per-user Bayesian model, a user's private Sieve rules | Only where the user's unwrap capability is present: the **client**, or an **AUTH'd MDA session** (the bridge holds the session-scoped capability then). **Not** at inbound-MX-delivery time — the recipient is not authenticated then, so the bridge has only the recipient's *public* key (to seal), not the private key (to unwrap a per-user secret). |

## The placement matrix

| Scorer's inputs | Where it runs |
|---|---|
| Metadata only | nest, bridge, or client (metadata is portable) |
| Content + deployment config (no per-user secret) — e.g. ClamAV, rspamd, deployment-wide filter rules | **bridge (perimeter, pre-seal)** or client (post-decrypt) — never the nest |
| Content + per-user secret — e.g. per-user Bayesian, per-user Sieve rules | **client (post-decrypt)** or an AUTH'd MDA session — never inbound-delivery-time, never the nest |
| Federated inbound post (`fauna.federation.post.forward` relay accept — content + deployment config) | no nest-side classification — `process_on_ingest` is deleted (`nest/storage-modes.md` § Implementation status today); the relay accepts unconditionally, uniform with a local create; post scoring is the reception-time / capability-holder story (capability-axis note below) — never the nest process |
| Region-blocking algorithm over web content the nest itself publishes to the open internet (public plaintext + the region's published transparent algorithm — no per-user secret) | **nest, as publisher** — one of the two sanctioned nest-position content evaluations (the other is the capability-holder row below) (**BUILT 2026-09-10**, direction user-ratified 2026-07-29; scoped to the public web render of published posts, where no user app exists to apply the block; every in-app surface stays app-side). Mechanism owner and build state: [`../behavior/region-blocking.md`](../behavior/region-blocking.md) § The nest-as-publisher leg |
| Content the nest holds a key for **by its owner's or its members' own grant** — a **community room's** log, opened under the home nest's room-read wrap ([`../behavior/community-rooms.md`](../behavior/community-rooms.md) § The three classes → *Community*); a restricted post at reception on a key-holding nest ([`../behavior/restricted-posts.md`](../behavior/restricted-posts.md) § Encryption at rest); an own-scope materialization grant (`encryption-at-rest.md` § Readable classes class 4) — scored with a **transparent** model (tier 2 or 3, [`content-moderation-and-ranking.md`](content-moderation-and-ranking.md) § The three model-authority tiers) and no per-user secret | **the nest, as that scope's capability-holder** (ratified 2026-09-10 by the room-model design pass; its refutable window closed unrefuted at the first community-room label build the same day — § Implementation status today) — at **reception**, in the act that already opens the bytes to index them, in-process or in its content-processing bridge (which of the two is artifact-set IPC wiring, never a knob); output rides the bus as labels/scores and no plaintext is kept. The grant bounds the scorer three ways: **never a tier-1 model** (a per-user secret the holder does not hold); **never content it holds no wrap for**, and never a wrap it minted for itself — the nest reads through a key its owner or the room's members made, or not at all; and **which models run is the grant authority's own choice in the app** — for a community room, the room policy its owner/admins sign (`community-rooms.md` § The three classes → *What the home nest does with its read*) — never a deployment setting. |

**Federated inbound posts (row added 2026-07-11; nest-side classification retired Phase 4, 2026-07-12).** A post relayed by a paired private nest is content the receiving relay holds in-process at ingest, exactly like a local `fauna.posts.create` body — so placement follows the same rule: the relay never classifies, uniform with the local-create path. *Public* posts are signed plaintext regardless (`encryption-at-rest.md` § Per-content-kind conformance, Posts row), so for them "never the nest" is the § Architectural rules prohibition, not an input-availability gap; restricted posts arrive sealed and the input-availability argument applies as usual.

**Uniform default for inbound-mail scorers: run at the perimeter (bridge), pre-seal.** The bridge is the plaintext entry point for inbound mail — it has to be, to receive external SMTP — so scoring there needs no per-posture branch. The body rests sealed uniformly (`encryption-at-rest.md` § The sealed posture), handled separately from scoring. Running at the perimeter rather than the nest is the uniform shape (priority #1) and avoids a per-mode code path.

**Per-user Bayesian placement (resolved 2026-06-29 — owner: `mail-spam.md` § Scoring placement).** It follows the **search** placement: scoring runs post-delivery at the authenticated agent — the Fauna app (post-decrypt) and/or the AUTH'd MDA session. It is **never** computed at inbound-MX-delivery time (the recipient is unauthenticated then — the bridge holds only their *public* seal key, per the per-user-secret row above), and the message is never shipped to nest to score it. One shared-Rust scorer (`libs/fauna-mail/src/spam/`, the canonical-token n-gram NB) runs at every position identically.

**Deployment-wide content models at the client position (ruled 2026-10-02) — a tier-3 `text-model` subscription, never a nest-served binary.** A transparent model the whole deployment shares (tier 2 or 3, [`content-moderation-and-ranking.md`](content-moderation-and-ranking.md) § The three model-authority tiers) reaches the client position only as a **tier-3 labeler artifact the user subscribes to** — signed, versioned, inspectable, evaluated at the subscriber's client (the frame § Tier-3 → *Artifact kinds*, `text-model`); its output rides the per-row labels into the shared verdict rule like every other factor. The pre-frame on-device ONNX arm (an opaque unsigned binary + vocabulary served from two nest config-file paths over `GET /api/v1/moderation/{model,vocab}`, loaded by web, linux and android, scored by nobody) is **retired**, not lifted into the shared rule: it had no tier, no labeler identity and no subscription (so no user agency over a compulsory model), its only artifact was an email-corpus logistic regression, it was configured by hand-edited file paths no deployment ever set (configuration-file theatre — `principles.md` § One configuration surface), and it ran three different runtimes on three apps while four apps had none. Lifting it would have rebuilt the `text-model` subscriber half with a worse artifact. Build state: § Implementation status today, 2026-10-02.

> **On the capability axis (frame § Sealing tier-1) — the placement positions ARE capability-holders.** The matrix reads the frame's tier-1 access rule: the **per-user-secret** row (client / AUTH'd MDA session) is exactly the set of positions holding the user's key. The frame adds a **third** such position for the *background* case — a **content-processing bridge** holding a user-minted, scope-limited, revocable `content.read{kind}` + `content.label-write` grant — that runs a scorer *on the box* against sealed content without the box owner reading it (the AUTH'd MDA session is its first instance; the FTS indexer another). This turns "the nest may not score" from a mode-era rule into the general rule *a scorer runs only at a capability-holder for the keys its inputs need*. Tiers-2/3 models are transparent (need no key), but applying them to a user's *sealed* content with no user present is that background-re-processing case (frame § Tier-3 community models). **Substrate: BUILT.** The `content.read{kind}` / `content.label-write` scope taxonomy and the content-processing-bridge holder loop are implemented — § The re-score drain plane below is the taxonomy's proven instance (tier_3 end-to-end, `test_capability_rescore_drain.py`), and the app-UI capability-mint surface that mints the grant in production has since landed too (`ui/nests.md` § Implementation status today) — nothing remains open in this plane. This doc's placement rule is unchanged by it — the capability axis is the *general* statement this doc's placement matrix is today's instance of. **The nest is one of those positions exactly when it holds a key by the owner's or the members' own grant** — the materialization tier over an own scope, and a community room's home nest seated with its own room-read wrap by the members' act — and then only for the purposes the grant was made for; the *capability-holder* row above is that case's placement, and § Architectural rules bullet 1 states the boundary. Its store position gains nothing from this: everything sealed to others is as opaque to it as before.

## Timing: scored-before-visible (ratified 2026-07-07)

The matrix says *where* a scorer runs; this rule says *when it must have run*: **any scorer whose output can affect whether or how content is first presented — spam disposition, malware verdict, filter placement, presentation-gating content labels — MUST complete before the user first sees that content.** "Post-delivery" scoring is post-*acceptance*, never post-*visibility*. Two layers implement it:

- **Delivery-time fast path (grant-holding boxes).** Perimeter pre-classifiers already run pre-seal at the MTA (accept / reject / Junk decided before delivery — the § placement-matrix uniform default). For **per-user** scorers, a content-processing bridge holding a standing user-minted grant (`content.read{mail}` + `content.label-write`; the default grant on trusted boxes) drains a **new-message score obligation at ingest**, so per-user placement lands moments after delivery — before any session would list the message.
- **Serve-time gate (the structural guarantee, all boxes).** Every path by which sealed content becomes visible passes a capability-holding position — the AUTH'd MDA session (IMAP) or the user's client (post-decrypt). That position MUST score any still-unscored content (scoring-bus watermark missing or behind) **before surfacing it** — before the message is announced in the mailbox view, before the client renders it. Visibility requires the unwrap key, and the key-holding position scores first — so the invariant holds even on a box with no standing grant, at the cost of first-serve latency.

**Implementation status of this rule:** ratified 2026-07-07 (Phase-3 GO); **both layers BUILT 2026-07-08** (S5). Serve-time gate: the AUTH'd MDA session scores before surfacing — the SELECT-time pass (`internal/mda/imap/spam_score.go::scoreSelectedInbox` before the `select_mailbox` snapshot) plus the IDLE-append branch (scores before the `EXISTS` emit, `idle.go`); those two paths are the whole announce surface (`Session.Poll` is a no-op; IMAP EXISTS-monotonicity bounds FETCH). Delivery-time fast path: a new delivery seeds a behind-version `labeler:<hex>` `content_scores` obligation per subscribed labeler (`CacheDb::seed_new_mail_labeler_obligations`) and pokes the MDA drain via the `fauna.bridges.rescore_ready` push — per-user placement lands moments after delivery on grant-holding boxes (tier_3: `test_capability_labeler_drain.py`). Inbound spam placement already ran at the perimeter, so for spam the rule held via the SELECT gate before the fast path existed.

## The shared-scorer shape

A scorer is a **pure function** over a uniform input bundle:

```
fn score(input: &ScoringInput) -> SubScore
// ScoringInput = { content: Option<MessagePlaintext>, prior: PriorScores { clamav, rspamd, auth, dnsbl, … }, per_user: Option<UserModel> }
```

It does not know or care *where* it executes. The architecture's only job is to **assemble `ScoringInput` from whatever sources the running position has, and route the output.** One implementation, run at multiple positions via thin per-position orchestration shims:

- **bridge** (perimeter) — via the cgo / UniFFI binding the mail bridge already uses; `content` from the in-process plaintext, `prior` from what it just computed.
- **client** (post-decrypt, post-delivery) — via UniFFI (Apple/Android/desktop) or WASM (web); `content` from local decrypt, `prior` fetched as metadata, `per_user` from the locally-held model. The per-user mail model is delivered by `fauna.bridges.fetch_spam_model`, **sealed to the actor** + unwrapped under the session capability — never a raw-model wire read (`mail-spam.md` § Wire shapes, § Encrypted-mode interaction). This is the model→device read; the converse body→nest read is forbidden (next §). *(Status: the **client** leg is now **enabled** — `fetch_spam_model` is `User`-scoped, a caller fetching only their own model, since the posts-`train` read-authz fix landed (`mail-spam.md` § Implementation status item 4). The MDA covers third-party-IMAP-MUA users; the **Fauna-app on-device mail scorer** — the client-side scorer position, with its `User` re-file surface `fauna.email.apply_spam_disposition` — has its per-app build status owned by `mail-spam.md` § Implementation status item 6 (not restated here, to avoid drift).)*

This is not new: `libs/fauna-mail/src/spam/mod.rs` (`combined_spam_score_milli` / `apply_unlisted_recipient_penalty_milli` / `decide_spam_disposition`) and the shared tokenizer (`libs/fauna-mail/`, "same canonical tokens regardless of where indexing happens" — `encryption-at-rest.md` § Search and indexing) already follow it. Keeping scorers as pure shared-Rust functions over `ScoringInput` is what makes "the same algorithm runs on an unencrypted nest *or* the iOS app" true rather than aspirational (priority #2).

## The scoring-metadata bus

A scorer's output, reduced to its verdict / score / flagged-rule-set, is persisted as **floor or deployment-data metadata** — never the content that produced it. That persisted metadata is the *bus*: it makes one scorer's output a portable input to any downstream scorer, at any position.

Existing bus entries:

- **`content_scores`** (nest table) + **`MailFloorMetadata.scores`** (segment footer) + **`IngestInboundMailRequest.scores`** (wire) — the **uniform multi-factor array** `[{factor, score, tier, scorer_version}]`, the canonical bus shape since 2026-07-05 (see the frame-target note below for the full contract). The per-kind entries below are the **detail records** the rows summarize — populated beside the rows, never their source (ratified at the contract phase, 2026-09-28).
- **`content_labels`** (nest table) — the **category-verdict plane** `{category, confidence_per_mille}` written by scoring positions over `fauna.labels.attach`; consumed by the moderation queue, the feed filter rules (`FilterRule::{HasLabel,LabelBelow,LabelAbove}`), and the per-row badge projection (owner: `../behavior/moderation.md` § Per-row badge data path). Distinct from `content_scores` by role: labels are category verdicts (with attestation/provenance), `content_scores` rows are composable numeric factors.
- **`message_scan_results`** — ClamAV verdict + rspamd score / rules (deployment-data plaintext; `mail-content-scanning.md` § Per-message scan-result storage).
- **`smtp_verdicts`** — SPF/DKIM/DMARC + spam disposition (deployment-data; `smtp-server.md` § Log shape).
- **per-segment `floor_metadata`** — SPF/DKIM/DMARC/ARC + spam score + spam disposition in the segment footer (`encryption-at-rest.md` § Per-content-kind conformance, Mail-body row).
- **`IngestInboundMailRequest.{spam_score, spam_disposition}`** — the perimeter's scores riding into the nest on the ingest call (the bridge already does this for spam; pre-classifier verdicts join the same request).

The rule for the bus: **metadata only.** The body / attachments that produced a verdict rest sealed (`encryption-at-rest.md` § The sealed posture); the score is not. Disclosing a 32-bit float + a rule-name list is not disclosing content (`mail-content-scanning.md` § Deployment-data, NOT user content).

> **The multi-factor bus (canonical since 2026-07-05).** The canonical row is `fauna_core::scoring::ScoreEntry` — integer per-mille `score` (no dag-cbor floats), `tier` 1/2/3 (the frame's authority tiers), `scorer_version: u32` (the watermark driving the re-score obligation). One row per item × factor (spam, phishing, NSFW, feed-relevance, `labeler:<id>`, …); it rides the wire (`IngestInboundMailRequest.scores`, additive `#[serde(default)]`; a non-empty wire array is authoritative), the segment footer (`MailFloorMetadata.scores`), and the nest's `content_scores` table (`content_kind`-agnostic, uniform `get_content_scores` read). **The contract phase (2026-09-28): the perimeter mints the rows, the nest derives nothing.** The ONE per-kind verdict → row mapping is `fauna_core::scoring::perimeter_mail_score_rows` (shared Rust, exported over UniFFI), which the Go MTA calls once per recipient at the ingest edge — the spam score is per-recipient once the unlisted-recipient penalty applies — and sends on the wire beside the per-kind fields; the nest stores the array as-is (empty = the perimeter scored nothing, the own-submission Sent copy, → no rows). Units on the bus: `spam` and `rspamd` are **milli-points on the 0–15 spam scale** (the `RspamdScore::scaled_milli` unit; the expand-phase derivation had floored `spam` to points, corrected here without a `scorer_version::SPAM` bump because no row of that era exists at rest — `version-compatibility.md` § Dimension 2, the 2026-09-24 baseline reset); verdict factors map Pass→0, SPF SoftFail→500, a definitive Fail→1000, ClamAV Infected→1000; a scorer that did not run emits no row (ClamAV `NotScanned` — every submission-door delivery, a disabled scanner — and `BypassedOversize` are exactly that, and the nest's `message_scan_results` detail record agrees: `mail-content-scanning.md` § Per-message scan-result storage). **The per-kind fields and columns are the detail record, ratified to stay — not a shape awaiting retirement.** The classification the contract phase settled: every per-kind wire field has a consumer other than the retired derivation (`verdicts` → `smtp_verdicts` + the floor's flat strings, `clamav_verdict` + `rspamd_score` → `message_scan_results` with signature / raw score / rule breakdown, `spam_score` → the floor mirror, `spam_disposition` → placement), and every per-kind column is *richer* than the row that summarizes it, so nothing is derivation-only and no column retires (`mail-content-scanning.md` § Per-message scan-result storage's "never a data-dropping change" holds trivially). The one field a row duplicates byte-for-byte, the floor's `spam_score` points, stays: it is the at-rest mirror of what filter rules match on, and removing it would be a wire break for four bytes. Writing a factor's row **is** the `content.label-write` capability at the key-access layer (frame § Sealing tier-1). Nothing remains open in the bus's own contract.
>
> **Footer = ingest provenance; `content_scores` = live current score; the re-score drain writes only the SQL row (self-healing).** The two copies play different roles once a re-score can *mutate* a score: the segment-footer `MailFloorMetadata.scores` is the **immutable ingest-time provenance** (a finalized segment footer is append-only — `libs/fauna-segment-store` has no in-place footer rewrite; only a compaction *rewrite* produces a new floor), while the nest's `content_scores` table is the **live, mutable current** score (`insert_content_scores` is `INSERT OR REPLACE` on `(content_id, factor)`). So the re-score drain (design § 2.5 step 4) writes back **only** to `content_scores` — a pure content-free metadata upsert; it never re-seals the at-rest segment. The "recovery rebuilds the SQL mirror from the footer" invariant still holds and is **self-healing under re-scores**: a mirror rebuilt from footers re-seeds the *ingest* `scorer_version`, which is (by construction) behind any bumped registry version, so the obligation gap **re-fires the drain** and the current scores are re-derived. A future rebuild-path implementer must therefore seed `content_scores` from the footer and let the drain reconcile — **not** try to make the immutable footer track re-scores.
>
> **The re-score drain plane (BUILT; tier_3-proven end-to-end 2026-07-06, `test_capability_rescore_drain.py`).** Two holder-gated, content-free RPCs: `fauna.capabilities.rescore_worklist` (which of a holder's granted owners' content is behind on which factor — `content_scores_behind` intersected with the holder's `content.read{kind}` grants) and `fauna.capabilities.submit_scores` (write back re-computed `ScoreEntry` rows, authz'd against the `content.label-write` grant for the content's *stored* owner and stored `content_kind` — never the holder-claimed ones — fail-closed per batch). The unseal + re-run happens off-box at the holder under its user-minted capability — the grant primitive is owned by `encryption-at-rest.md` § Capability tiering. The Go drain worker (`bins/fauna-bridges/internal/mda/rescore_drain.go`) rides the MDA holder and triggers at startup / `config_changed` / the `fauna.bridges.rescore_ready` ingest push / a 12 h backstop; factor scope is the built-in perimeter scanners (clamav + rspamd) under the composed "read and filter my mail" grant, plus community labelers (`labeler:<id>`, tier-3, sandboxed WASM) — each only under the owner's per-labeler grant naming it, matched at the holder's key selection and again at the nest's worklist and `submit_scores` (`content-moderation-and-ranking.md` § Tier-3 → *Subscribing = minting a capability*). On revoke the drain goes dark while obligations stay owed (a re-mint drains them). The app-UI mint surface (the nest-trust facet's scope-first mint flow, `ui/nests.md` § Implementation status today) is now built on every app — nothing remains open in this plane.

> **The bus is what compositions read.** Feeds compose bus factors into an ordering key — the composition mechanism (weights, per-feed/global scope, the filter-as-strong-negative verb) is owned by `content-moderation-and-ranking.md` § Composition model, and the read model by `feed.md` § The read model (both live since 2026-07-08: `fauna_core::scoring::CompositionEntry` + `query_feed_scored`). This doc owns only the bus shape those compositions read; transparent factors compose nest-side, sealed tier-1 factors at a capability-holder / the client. Client-side apply + authoring UI status: `feed.md` § Implementation status today.

## Stages: perimeter pre-classifiers → downstream composites

Scorers compose into a DAG. The first stage runs at the perimeter at ingest; later stages consume the bus.

- **Stage 1 — perimeter pre-classifiers.** Deployment-wide, no per-user secret. Run at the bridge, pre-seal. Affect initial placement (INBOX / Junk) and perimeter accept / reject / tempfail. Examples: ClamAV (binary pass / reject), rspamd (content score). They write the bus.
- **Stage 2 — composites and per-user scorers.** Consume the bus (Stage-1 metadata) plus content and/or a per-user secret. Run on the client post-delivery, or an AUTH'd MDA session; never the nest. Examples: the per-user Bayesian; user filter / Sieve rules; a composite like *"spam if `message_scan_results.clamav` ≥ T **and** the body matches `INVEST NOW`."* The composite's ClamAV input is metadata (portable, from the bus); its body-match input is content (so the composite itself runs where plaintext lives — the client, or an AUTH'd MDA session). If it re-files mail, the nest sees the placement change but never the *reason* (the rule + the match stay on the client).

## Architectural rules

- **The nest never runs a content scorer over content it holds no key for.** As a *store* it stores and serves scoring metadata; it never computes a score from content it cannot open, and never acquires a key in order to. Corollary of the at-rest property (`encryption-at-rest.md` § The sealed posture). Two scoped positions where the nest is something other than a store, both placement-matrix rows: the nest **as publisher** — the region-blocking apply over public web content it itself serves to the open internet (owner [`../behavior/region-blocking.md`](../behavior/region-blocking.md)), public plaintext it legitimately holds, serving an audience no app mediates — and the nest **as a capability-holder** (ratified 2026-09-10) — a community room's home nest reading under the wrap the members seated it with, or an own-scope materialization grant — bounded to transparent models, to the purposes the grant was made for, and to keys the owner or the members minted to it. For everything sealed *to others*, and every in-app surface, the rule is absolute: a wrap the nest holds for one room opens nothing else, and the store position never borrows the holder's.
- **Never ship plaintext to the nest to score it.** No `scan(plaintext) → nest` RPC. The perimeter scores on the plaintext it already holds and sends only the verdict.
- **The plaintext carve-out is the perimeter's, not the nest's.** The bridge is trusted with transient plaintext at the ingest edge; the persistent nest store is not.
- **Scorers are pure shared-Rust functions over `ScoringInput`.** One implementation; per-position orchestration shims assemble inputs and route outputs. No per-position re-implementation.
- **Inbound-mail scorers default to the perimeter.** The bridge is the plaintext entry point for inbound mail; running there is the uniform, branch-free shape.
- **Metadata is portable; content and per-user secrets are not.** Placement is gated by input class (see the matrix). Per-user secrets are unavailable at inbound-MX-delivery time.
- **Output is metadata, not content.** A scorer's persisted result is its verdict / score / flagged rules — never the bytes it scored.

---

## Don't do these

- **Don't run a content scorer on the nest over content it holds no key for.** No plaintext there; it would puncture the at-rest property. And don't let the store borrow the holder's position: a scorer at the nest reads only through a wrap the room's members or the scope's owner minted to it (the *capability-holder* row), never through a key it minted for itself, an operator toggle, or a classify-on-ingest hook over bytes it merely relays.
- **Don't add a `scan_message_content(plaintext)`-to-nest RPC** (or any "ship the body to the nest so it can score" path). Score at the perimeter or on the client; send only metadata.
- **Don't fork a scorer by execution position.** Same pure function, different `ScoringInput` assembly per position. Forking invites algorithm drift.
- **Don't assume a per-user secret is available at inbound delivery.** The recipient is unauthenticated then; the bridge has only their public (seal) key. Per-user scoring is client-side or AUTH'd-session-side.
- **Don't persist the scored bytes in the metadata bus.** Verdict / score / rule-names only; the body stays sealed.
- **Don't let a downstream scorer's *reason* leak to the box owner.** If a client-side composite re-files mail, the nest sees the placement change, not the rule or the content match.
