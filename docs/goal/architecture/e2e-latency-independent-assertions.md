## The convention — convention 14 (== point 14)

14. **Assert latency-independent state, never wall-clock timing (ratified 2026-07-23).** Every dev machine runs 3–15 concurrent sessions; that load is the environment in which a test must deliver a trustworthy verdict, so a test that only passes solo is itself the bug (USER plea 2026-07-23) — a false red under load is byte-for-byte indistinguishable from a real product bug, and misattributing one has repeatedly burned multi-session root-cause hunts (the pre-hardening `test_nest_flip_resilience` history: four wrong reconnect-bug theories). Nine mechanisms, in preference order:
    - **Positive waits: named generous budgets + deadline polls.** Wait ceilings are named module/shared constants (`*_WAIT_S`, → `helpers/budgets.py` once built) sized **far above any non-pathological delay** — never tuned to observed latency — consumed by deadline polls (`while time.monotonic() < deadline`, a short sleep only as poll cadence) that return the instant the condition holds: a generous ceiling costs a green run *nothing*; only genuine failures spend it, still bounded by convention 9's per-test ceiling. Assert the eventual property, never latency itself (backoffs are jittered by design). Template: `tests/test_nest_flip_resilience.py` (the 2026-07-18 `INGAP_WRITE_WAIT_S` hardening) — including threading the budget into the action call's `timeout=` rather than trusting a short driver default. **Rider — a generous ceiling is sound only when the awaited event is causally inevitable.** If an unsynchronized startup transition can disqualify the event outright — e.g. an emitter that seeds its cursor in its own goroutine, so events committed before a late-scheduled seed are reclassified as pre-start history — then no ceiling helps: the wait is lose-forever rather than late, and the red tracks machine load exactly like a latency flake. Barrier on the startup transition's completion first (expose it as a diagnostics observable if the product lacks one), then wait under the budget. Worked example — and proof this convention binds below the e2e tier, in plain Go/Rust unit tests: the mail-bridge firehose harness (`bins/fauna-bridges/internal/atprotofirehose/firehose_test.go` — `run()`'s seed barrier over the broadcaster's `Seeded()` diagnostic, plus `TestSlowConsumerIsDropped`'s event wait; de-brittled onto the seed barrier after a green-alone/red-under-load failure that root-caused to the seed race, not to latency — which is why the fix is a barrier and not a longer wait). **Rider — wait for the STATE YOU ASSERT, never for a proxy that renders earlier; and never re-enter the page to retry, which restarts the load you are waiting on.** A page's chrome (a section header, an "add" button, a tab) renders *synchronously* with the page, while the data it frames arrives from an async fetch — so `wait_for(<chrome id>)` followed by a read of the *rows* is a read of the pre-fetch page, and it is latency-dependent no matter how long the `wait_for` ceiling is, because the ceiling is satisfied instantly. Two compounding traps: **(a)** an app whose page owns a per-mount machine pays that fetch on *every* mount, while an app that builds its machine once at session attach has its data before the paint — so the same read passes on one app and fails on another for reasons that have nothing to do with the product (**both shapes are correct**; the test must encode neither); **(b)** a retry loop that navigates AWAY and back to "re-fetch" **remounts**, discarding the in-flight load and resetting its clock, so the loop can poll for its whole budget and never once observe a settled page. Poll the asserted collection itself, within one mount. Case: `test_preflight_this_seat_sees_the_shared_set` read the Folders row list the instant `folder-add-button` appeared and re-entered the page each poll — measured on macOS against the live account (2026-07-31, three consecutive mounts) the add button is up at **0.00 s with 0 rows** and the five rows register **0.21 s** later, so the seat reported "0 folders" for a 90 s budget against an account that owns five. It read as a macOS **product** bug ("a user signing in sees none of their folders"), killed two operator-coordinated tri-machine rounds (`20260730-01`/`-02`), and sent three sessions after the nest projection, the MLS join-filter and apple's `list_folders` — none of which were ever at fault; instrumenting the shared machine settled it in one run (`refresh: snapshot committed folders=5` beside a harness count of 0). Helper `_await_folder_rows`; gates `test_the_row_read_waits_for_the_list_not_for_the_add_button`, `test_a_settled_page_pays_nothing_to_be_read` (`tests/test_multiseat_handshake.py`). **Same trap outside the UI — a file's EXISTENCE is a proxy for its CONTENT.** Anything that publishes through a shell redirect (`> file`, in `sh` or in a `.cmd`) has the target **created and truncated before the bytes land**, so an existence-poll returns inside that gap and reads `""` — a correctly-delivered value reported as empty, and the emptiness then reads as *"the argument never arrived"*. Poll the content (or publish atomically via a rename). Case: `apps/fauna-tui/src/os_open.rs`'s `spawn_via_launches_the_opener_with_the_url`, whose existence-poll failed ~10% of windows runs (3/60 and 6/40 in an A/B repro) and stood as a suspected product bug in the windows `start` seam — including a plausible BatBadBut/`%~1`-escaping theory — until the argv was observed directly and found intact; the spawn was healthy throughout. Note both arms carried the race: the `.cmd` arm merely *exposed* it, because `cmd.exe` widens the create→write gap that `sh` usually wins. **Rider — the ceiling's FLOOR is look-up-able, never a feel: a verify budget must exceed the driven RPC kind's registered deadline** (`libs/fauna-protocol/src/kind.rs`, plus the retry envelope where the path auto-retries) — the protocol's own worst legitimate case IS a non-pathological delay. `fauna.bridges.link` is a 30 s kind whose client path additionally waits out a WS reconnect *inside* that budget before transmitting (`fauna-client::client.rs::request_inner`), and a 15 s verify poll spent three sessions declaring protocol-legal completions "lost RPCs" under load (the bridges link "flake" 2026-08-01): the `linked: False, error: None` signature was manufactured by the budget inversion plus an error capture that read at t≈1 s and t=15 s — both before a slow failure could surface its error at up to t=30 s. Corollary: sample the (transient) error channel INSIDE the verify poll every iteration and keep the first non-empty value; a one-shot read before or after the poll structurally misses a slow failure. Case: `tests/test_bridges.py::_await_linked`. **Rider — the COMMAND-ACK budget is the same rule applied to the harness's own plumbing, and it is the one every suite pays (hardened 2026-08-16).** An ack — the app echoing `last_command_id` back on `/app/state` — is a liveness signal that always arrives on a healthy app, and every ack site is a deadline poll, so a generous ceiling is pure upside and a tight one is a flake generator for *every* suite that posts a command. `drivers/http_bridge.py` carried bare literals instead: `set_state` and `call_machine_method` at `10.0`, `call_command` at **`5.0`** — the same mechanism with an unexplained 2× split that made the flakiest path the tightest. The tell that it was already failing: call sites had begun bumping past it one at a time (`timeout=60` in `test_backups.py`, `timeout=20` in the family tests), which is precisely the per-call-site drift `BRIDGE_RPC_TIMEOUT_S`'s own comment warns can never be complete. All four sites (`set_state`, `call_machine_method`, `call_command`, `barrier`) now resolve one named `BRIDGE_ACK_BUDGET_S = 60.0` at call time, monkeypatchable like its sibling. Measured basis: a single windows push logged `serialize=2102ms post=488ms` under load — `serialize` being in-process state marshalling, pure CPU, so a CPU-starved app thread loses seconds at a time on a box running 3–15 sibling builds — against `provider=0–26ms serialize=0–24ms post=1–12ms` on a quieter box, a ~48× spread. Proof that generous costs nothing: `test_agent_barrier.py --app windows` (three ack-heavy tests) runs **3 passed in 13 s** under the 60 s ceiling. ⚠ Do **not** extend this to web's `call_command`/`set_state`/`barrier`: their `timeout` parameters are vestigial signature compatibility — those overrides are synchronous JS-eval short-circuits that never poll — so changing them would imply a mechanism that does not exist.
    - **Negative asserts: causal anchors, never settle-sleeps.** "X must not happen" cannot be proven by sleeping N seconds and peeking — a short window silently false-*passes* when X is merely late, a long one taxes every green run. Anchor absence to causal order instead: **(a)** the **`barrier` test-agent command** (a convention-11 cross-app contract entry): ack only after all UI-thread work enqueued before the command has run; **(b)** a **generation counter** — the app exposes via `get_state` a monotonic counter incremented *synchronously at the initiation point* of teardown/reload/session-rebuild; the test reads it before the trigger, positively awaits the trigger handler's completion observable, issues `barrier`, and asserts the counter unchanged; **(c)** a **FIFO sentinel** — push a sentinel through the same pipeline the would-be event rides and await it; everything enqueued earlier has run. Corollary: a would-be effect must be *initiated synchronously* inside a handler whose completion is observable — if the product schedules it asynchronously with no initiation marker, that is a product-side restructure, not a longer sleep.
    - **Timer-driven behavior: never sleep to reach a firing.** The `--features test-hooks` surface owns this: a fake clock (`/api/v1/test/outbound/clock`) plus `run_now` pokes (`/api/v1/test/pending_actions/run_due` and `/api/v1/test/outbound/emit_tlsrpt_now` are the pattern) — advance the clock, poke the cycle, deadline-poll the cycle's positive completion observable, then assert. Cadence *logic* (interval math, once-per-X gates) belongs in tier_1 Rust tests under a mocked clock; the e2e keeps one wiring proof via the poke.
    - **Pre-fetch windows: HOLD the read, never race it.** A whole class of rule is about what an app shows *before* a read has answered — [`../ui/settings.md`](../ui/settings.md) § Privacy sub-page ("Until `inbox_mode_get` has answered, the mode is *unknown*"), [`../behavior/family-safety.md`](../behavior/family-safety.md) § Cold start (an unresolved supervision read must not collapse into "unsupervised"). Their failure mode is a client that paints a plausible **guess** and corrects itself a round trip later, which every post-fetch assertion passes, because by the time one looks the guess is gone. The window cannot be raced (a zero-wait read right after navigating is exactly the wall-clock dependence this convention forbids — a fast local nest answers before the test's next line runs, so the assertion passes only on the runs where it passes at all), and it must not be manufactured by freezing the nest process (forbidden outright, and `nest_instance` is a session-scoped fixture every other test shares). The mechanism is the network analog of the fake clock above: the `--features test-hooks` surface **holds one named RPC kind's dispatch pending until the test releases it** — `POST /api/v1/test/rpc-hold/{kind}`, its `GET` arrival observable, and the `release` twin (`bins/fauna-nest/src/rpc_hold_test_hook.rs`, driven from `tests/e2e-unified/helpers/rpc_hold.py`). Two properties make it latency-independent rather than merely slower: the park is **unbounded and test-ended** (it runs before the per-kind deadline timeout, so no budget expires under the assertion), and **arrival is observed, not assumed** — the test deadline-polls `holding >= 1` before asserting, so it can never read the UI before the app has even issued the request and call the result a pre-fetch paint. Selection is by *kind*, decided per request, so there is no ordering to lose a race against — the same reason `channel_refusal_test_hook` selects by envelope class. Template: `test_inbox_mode_is_unknown_while_its_fetch_is_still_pending`. **Its failed-request twin (2026-09-21):** `POST …/rpc-hold/{kind}/refuse` answers every request of the kind — the parked ones and every later arrival — with an error reply (`fauna.test.refused`, the generic `error.unexpected` copy) instead of running the handler, until `release`, and `GET` counts them in `refused`, the arrival observable. It is the state for rules about what an app does when the nest turns a request away, which no ordinary input provokes (the nest has no length or tag limit a user could trip) — template `test_feed_compose_in_flight.py::test_a_post_that_fails_to_send_says_so_and_keeps_what_you_wrote`. And a hold only opens a *mutation's* in-flight window to a test that can keep acting while it waits: tui's agent `click` awaits the gesture's whole network half before replying, so tui answers `press_key(id, "Enter")` as the keyboard's activation instead — the same gesture through the spawn path a keypress takes (`apps/fauna-tui/src/automation.rs`), driven by `FeedActions.start_submit`.
    - **Multi-party rendezvous: assert your OWN visibility, not just theirs.** In a test where N machines rendezvous through shared state, the natural wait is peer-only — "I can see the others" — and it silently never asserts the converse, "the others can see me". That asymmetry is invisible in every phase whose peer wait happens to outlast the party's own write propagating, i.e. it passes on **latency luck**, and it collapses in the LAST phase: the last party to arrive finds every peer's state already present, returns immediately, and is torn down before its own contribution drains — so it prints PASS **while starving the peers that block on it**, and they then fail naming *it*. Every party must therefore end on a deadline poll for its own contribution being observable *at the shared source of truth* (not merely written locally). Case: live multiseat run `20260724-06` — the macOS seat passed while `20260724-06-done-macos.txt` never reached the nest, with all nine other run files present; gate `tests/test_multiseat_ack_barrier.py`, barrier `_await_own_ack_on_nest`. Same blind spot, earlier phase: a peer-only `expect` reported a peer missing when the seat's *own* file had been destroyed locally, misdirecting three sessions at the wrong machine. **Rider — such a barrier may only assert on a read whose completeness it can prove: presence is sound from any read, absence only from a COMPLETE one.** Where the shared source of truth is read through a UI that can under-report (a lazy list registering only on-screen rows), a partial read makes "my contribution is missing" indistinguishable from "I could not see it", so the barrier must **abstain with a loud UNCERTIFIED warning** instead of failing — a false red there fails a *correct* run and sends the next session hunting a nonexistent bug, which costs more than the starvation it was guarding against. Carry the completeness flag out of the read itself (`_read_set_listing` → `(names, rows)`), and let the **last** read decide, so one early unregistered row cannot excuse a genuine starvation for the rest of the window. Gates `test_a_lossy_read_does_not_red_the_barrier`, `test_completeness_of_the_LAST_read_decides`. **Second rider — completeness has TWO axes, and a row count proves only one: a poll is only a poll if each read RE-PULLS the shared source.** Registration (rows present but unreadable — the lazy list above) is what `(names, rows)` catches; **freshness** is invisible to it, because a stale snapshot's count is as stale as its names. Where the UI's fetch fires only on a navigation *edge* (enter-is-the-trigger — the Media page on every app), a wait loop that re-navigates to a page it is already on re-reads one frozen snapshot, "complete" by row count and arbitrarily old — the barrier degenerates to a one-shot read plus dead polling. And the **last-finishing** party is structurally the victim: its own contribution is written seconds before the first poll, so the upload loses that race every time. Force the edge on every read (re-enter the page — `MediaActions.reenter`, the `feed` → `media` toggle). Case: run `20260724-07` — the merge and all uploads converged tri-machine and the linux seat's barrier certified live (183 s), but the macOS seat **false-red-ed a healthy run**: its ack was provably nest-visible with 5+ minutes of window left while 600 s of edge-less "polling" re-read the pre-upload snapshot (root-caused from the session transcript + `App::apply`'s `edge = page != prior`, 2026-07-29 — NOT the lazy-list gap; the terminal app registers every snapshot row). Gates `test_listing_read_pulls_fresh_state_even_when_already_on_media`, `test_the_run_20260724_07_frozen_listing_must_not_red_the_barrier`. **Proven live 2026-07-29 — run `20260729-01`:** with the edge forced on every read, all three seats (linux, macos, windows) printed `cohort converged … — PASS` on one id, the previously false-red macOS seat certifying in 351 s of the same 600 s window that had produced the frozen-snapshot red. The fix is validated on the exact seat class the bug singles out — the last-finishing party — so this rider is a proven mechanism, not merely a pinned one.
    - **Budget an ASYMMETRIC wait separately from a symmetric one — a shared machine's queue is part of the wait.** One flat window across every phase of a multi-party rendezvous conflates two different waits. A *symmetric* rendezvous ("we all edit at once") wants a **tight** budget: it is the concurrency the test exists to prove, and a party allowed to stroll in late still passes while proving nothing. An *asymmetric assembly* wait — every party blocking on one designated party's output, plus the cold build and **machine-wide slot queue** in front of it — wants a **much larger, separately-named** budget, because none of that latency is the behavior under test and none of it is something the waiter can hurry. Sizing the assembly wait like the symmetric one fails healthy cohorts on load alone; sizing every phase like the assembly one silently stops proving overlap. Note the slot queue specifically: a fair queue bounds a waiter's *position*, never its *duration* (a sibling's full `--app` sweep holds a slot 15+ min), so cross-machine start skew is unbounded in wall-clock terms even on a perfectly fair machine, and only the assembly budget can absorb it. Case: the live multiseat round's `_await_files` applied `WINDOW` to all four phases, so a peer that won its e2e slot instantly burned its entire window while the creator was still queued — the round then read as a product failure. Now phase 1 alone takes `ASSEMBLY_WINDOW` (derived from `WINDOW`, never a bare constant, so a deliberately-widened run widens with it) and the module's `@pytest.mark.timeout` is re-derived to still bound the widened worst case — bounded always (point 9). Gates `tests/test_multiseat_handshake.py`.
    - **"Does not reproduce" is not a verdict — CONTEND for the race, don't wait for it.** A load-sensitive red is usually met the other way round: the gate goes red, a session re-runs the test a handful of times, it passes, and the red is written off as *a flake* — the convenient label, in the sense of the authoring-rigor iron-clad, because believing it means the work is over. Repetition alone is a weak instrument: a race between a caller and a thread it just spawned needs the two to *contend for a core*, and a 28-core box under ordinary load simply hands them one each. **So squeeze the cores instead of adding runs: `taskset -c 0 <test-binary> --exact <test>` in a loop.** Worked example, 2026-08-15 (`fauna-client-sync`'s `agent::liveness_tests::a_refresh_converges_the_cached_answer`, which redded `workspace-test-check`): unpinned it was **0 failures in 300 runs** at load 16.5, and two sessions had already recorded it as not reproducible — one filing it as "most likely a load-induced flake". Pinned to a single core it was **15 in 300**, with the gate's exact panic line, in under a minute; the defect was real and structural (`read_and_refresh` spawns the probe and *then* loads the value it asserts on, with no happens-before edge between them). The same move generalizes past `taskset` — oversubscribe the machine, pin the process, or shrink the thread pool — the principle is that a scheduling race is *provoked*, never awaited. Corollary for the fix: re-run the **same** contention that produced the red (here 0/300 pinned, after) — a green solo run proves nothing about a bug a solo run could never show. ⚠ **Pinning alone silences a race BETWEEN tests — force the thread count back up.** The instrument above provokes a race *inside* one test (a caller and the thread it spawned). The other class is two tests in one binary contending over **process-global** state, and there `taskset -c 0 <bin>` on its own is not merely weak but actively self-defeating: libtest sizes its default thread pool from `sched_getaffinity`, so pinning to one core silently sets `--test-threads=1` and removes the very concurrency being hunted. Say the count explicitly: `taskset -c 0 <bin> --test-threads=8 <filter>` — one core, many threads, maximal preemption. Worked example, 2026-09-09 (`fauna-provisioning`'s `progress::tests::run_step_narrates_every_attempt_so_a_stalled_dial_is_visible`, which redded `workspace-test-check` with an *empty* tracing capture): pinned whole-binary it was **0 failures in 40 runs** — every one of them sequential, so the hypothesis could not even be expressed — while pinned at `--test-threads=8` over the six `run_step` tests it was **2 in 300**, and the captured lines named the defect. `tracing` caches each callsite's interest process-globally on first use; five sibling tests drove the same `run_step` callsites with no subscriber installed, and libtest sorts by name, so the capturing test won those callsites in every sequential ordering and could lose them only under concurrency — which is exactly why four earlier re-runs at `--test-threads` 2/8/16/32 on an idle box had recorded it *not reproducible*. The fix was one process-global subscriber for the whole binary (0 in 600 after); an intermediate attempt that kept the thread-local subscriber and merely added an `EnvFilter` measured **4 in 300** and lost *every* line instead of one — a thread-local install cannot govern a process-global cache, and the measurement is what said so. Generalize past `tracing`: **a test asserting on any process-global facility is latency-independent only if it owns that facility for the whole binary, not merely for its own thread.**
    - **Never assert a primitive the ENVIRONMENT merely promises — assert what the code DECIDES (2026-09-11).** The convention's other mechanisms are about *when* a test reads; this one is about *what it rests on*. A test that races N processes to prove "exactly one wins" is not asserting the code's exclusion logic at all — it is asserting the exclusion of whatever primitive that logic is built on, in whatever environment the suite happens to run in, and it reports a defect in *our* code when that primitive is the thing at fault. The distinction is invisible while the primitive holds, which is why it survives review: `mkdir(2)` is atomic, so racing on it *looks* like a free way to prove a lock. **Measured counter-example, and the reason this is a mechanism rather than a style note:** `/usr/bin/mkdir` on the project's primary Linux dev VM is **uutils coreutils 0.8.0** — the Rust reimplementation Ubuntu ships as its default coreutils, not GNU — and its `mkdir` returns **success to several concurrent callers racing one path**: 19.5–58.5% of rounds across tmpfs (`/dev/shm`) and ZFS (`/work/tmp`), at both 2-way and 6-way concurrency, the winners sharing a single inode with both markers present, while a raw `os.mkdir` burst on the same box, same filesystems, same session, same barrier is **0/800**. Sequential exclusion is correct (`mkdir X` twice → the second is `File exists`), so nothing catches it but concurrency. The kernel, the filesystem and the agent sandbox are all exonerated by that bisect; the userspace binary is the whole of it. **The test-side rule that follows:** where the property is the code's own decision, find the form that proves it without the race. `merge-gate-check-mac.sh`'s `steal_lock` excludes via a *tombstone* — `mkdir "$LOCK.stealing.$assessed"`, created and never removed — which is order-independent, so N **sequential** attempts carrying one staleness assessment prove exactly what N concurrent ones would (first wins, all others refused) and prove it deterministically, in milliseconds, on every machine. Case: `test_mac_only_one_stealer_can_take_a_stale_lock_however_deep_the_burst` (`tests/e2e-unified/tests/test_merge_gate_check_mac.py`), whose 6-way-burst ancestor redded intermittently on that machine for a full session while the mac script it tests was correct throughout, and which held the 28th merge gate unarmed while it did. **Corollary for the fleet's own locking, not just its tests:** a `mkdir`-based mutual exclusion is only as sound as the `mkdir` on the machine running it, so a lock that must hold on a machine whose `mkdir` is uutils uses `flock(2)` (as `merge-gate-check.sh` and `build-slot.py` already do) rather than a directory. **But the swap moves the failure mode rather than removing it, so make it with the successor's own hazard in view:** a directory lock's unlock is a `rm -rf`, which cannot be inherited, while `flock(2)` is held on the *open file description* — which `exec` hands to every child and which outlives the process that opened it. Measured hours after the fleet's first such swap, 2026-09-11: the merge script's asynchronous gate-check kick, which outlives it by design, inherited the merge lock and held it for its whole run, so the lock was found held by seven processes with no merge alive and every later merge on the box refused, naming an empty holder. **So release the lock before spawning anything long-lived, and treat a held lock with no holder on record as the leaked-descriptor signature it is** — the same shape that once wedged a machine's whole heavy gate tier for 2 d 23 h.
    - **Declared residue: `# sleep-ok: <reason>`.** A few assertions are genuinely time-based (a steady-state absence over real elapsed time — e.g. proving a systemd unit stays inactive across `RestartSec` windows); they carry the same-line annotation stating why no causal anchor can replace them. Enforcement is a down-only ratchet lint on the cheap merge tier (per-file baseline of unannotated `time.sleep` counts must never rise) — **landed 2026-07-24**; gate mechanics → [`build-parity-gates.md`](build-parity-gates.md) § *Sleep-ratchet gate*.

  **Why `online` crosses the boundary already decided.** The gate's polarity is *online unless the word is a KNOWN offline word* — deliberately asymmetric, so an older app meeting a future state word keeps its controls live rather than greying them. A barrier waiting for equality with `"connected"` therefore agrees with the gate on every word that exists today and **hangs to its full ceiling on the first new one** — the one case the gate was built to tolerate. It did not, and the mechanism that prevented it is worth stating as a rule: **mutation-grading a negative assert forces its tier_1 pin to be built in the same slice**, because (D6c's F3) an absence-guarding barrier cannot be graded by releasing it early — that makes the absence trivially true and the e2e passes vacuously — so the grade has nowhere to go *but* the ordering pin underneath. Every D6 slice therefore landed its own pin as it went: `outbound_retry.rs`'s `crossing_four_hours_warns_once` for the `delay_warned_at` once-per-message gate D7's charter named as its example (a pure decision fn with `now` injected — no mock clock needed, which is the cheaper seam wherever the product already takes its clock as an argument), `obligation.rs::take_due`'s `NOTIFY_REPORT_MIN_INTERVAL_SECS` gate, the alert sweep's two counting pins, the rescore drain's serve-ordering pin, and D6e's fan-out counter. ⚠ **The alert sweep's 6 h interval is pinned at COMPILE time rather than by a test** — `const _: () = { assert!(RE_SWEEP_INTERVAL_SECS * 4 <= PLC_CONTEST_WINDOW_SECS) }` — which is the stronger form (widening the cadence past PLC's 72 h contest window is a build failure, not a silently weakened guarantee) and which any "does this constant have a test?" audit will report as *uncovered*. Prefer it wherever a cadence must stay inside a deadline that is itself a constant. **What the slice actually closed is the class D6's survey could not see:** that survey enumerated `time.sleep ≥ 2 s`, so a test that waits out a cadence **without sleeping for it** — a long budget, or a shortened-but-still-wall-clock tick — was structurally invisible to it. `helpers/budgets.py`'s `MLS_HANDSHAKE_S` names the class in its own docstring ("the poll-only receive loop's own cadence, not a push"), and the client receive loop's backstop is *shortened* for the e2e (`FAUNA_CONV_POLL_SECS=2`, `libs/fauna-conversations/src/session.rs`) rather than replaced by a poke. Two sites of that class were **attempted and deliberately left alone** — `test_fauna_mls_cross_device_sync.py` and its web twin, whose "give device A's 2 s poll a few cycles to fold in B's takeover commit" precondition waits — and the reason they resisted is the entry's most reusable half. ⚠ **These are a precondition-side instance of D6e's "unable to fail" shape, and precondition waits hide it far better than negative asserts do.** The cycle-count wait exists so A's follow-up send exercises the takeover path; when the fold-in is late, A's send is a stale blind-append — which **still grows the channel**, so the test's own assertion still passes. The wall-clock form cannot fail for the reason it exists, and load makes it *more* likely to certify the wrong path while looking green. Generalises as: when a sleep guards a *precondition* rather than an outcome, ask what the following assertion does if the precondition is missed — if it still passes, the sleep is not a slow barrier, it is no barrier. ⚠ **But the obvious barrier is forbidden by the product's own design, and that was established by RUNNING it, not by reading:** the natural anchor — wait for A to render B's reply — was implemented and measured **red at 90 s on tui** (the full `MLS_HANDSHAKE_S` budget), because devices A and B are the *same actor sharing one leaf*, and a sender cannot MLS-decrypt its own application messages (pinned tier_1 by `libs/fauna-client-mls-sync/gate_impl.rs::twin_device_cannot_decrypt_its_own_log_message_but_bob_can`, and the very property that forces own history onto the replica plane rather than log replay — `devices.md` § Cross-device MLS group-state sync). A can never observe B's *message*; it can only fold in B's *commit*, whose effect is an epoch advance that **no app exposed when D7 ran**. So these two sites were never a test rewrite at all: they needed a product-side observable (the channel's epoch, or a count of folded-in commits, published through the agent state the way `SESSION_GENERATION_KEY` and `ALERT_SWEEP_PASSES_KEY` are), and until it existed the wall-clock wait was the honest placeholder — left in place, with this entry as the reason. **That observable landed 2026-08-14 as slice D8 (next entry), and both sites now anchor on it.** The generalisable rule, and the one that would have saved the run: **before choosing a barrier, check whether the observable it needs is one the product is *designed* to withhold** — an encrypted-messaging test can want a barrier that cryptography forbids, and that is not a bug in either the test or the product. The remaining sites of this class are the poll-cadence family (the conversations/MLS receive-loop backstop and the mail read-feeds that ride it), which want a `run_now`-style poke on the client receive loop rather than a shortened tick. **That poke and its cycle observable landed 2026-08-14 as slice D9** (two entries down), which closes this family: the loop can now be asked for a cycle and the cycle's completion is readable, so no consumer needs the shortened tick. (landed 2026-08-14, slice D8) **the twin-device fold-in observable — the barrier D7 proved the product was withholding, now published.** `FaunaMlsBackend::folded_commits` (`libs/fauna-conversations/src/backends/fauna_mls.rs`) keeps a per-channel monotonic count of inbound commits this device **incorporated**, bumped at exactly one site — a wrapper around `apply_inbound_commit` that observes the verdict — so a `CommitApplyOutcome::Stalled` provably cannot bump it, which is the whole soundness argument: `Stalled` *is* the un-incorporated case, and a barrier released on it would hand the test the stale-epoch state it exists to rule out. It is published top-level as `fauna_e2e_agent::MLS_FOLDED_COMMITS_KEY` (`{channel_hex: count}`), derived once in `fauna_conversations::state_json::mls_folded_commits_json` so each app leg is a one-line read — landed on **tui, linux, web and android** (web via the `mlsFoldedCommits` wasm export → `$lib/e2e-automation` → the bridge's state assembly; android via `ConversationsSession::mls_folded_commits_json`'s UniFFI twin — `&self.backend()` delegating straight to the same free function — re-parsed by `TestAgent.kt::serializeState`, landed 2026-08-14; its `test_fauna_mls_cross_device_sync.py` run is still host-emulator-gated — since it was entrusted as this track's own prerequisite, ahead of the track itself, rather than left to surface later as a mystery refusal); **macOS + iOS landed 2026-08-15** (`ConversationsSession::mlsFoldedCommitsJson`'s UniFFI twin, read in both `FaunaMacApp.swift`/`FaunaApp.swift`'s `serializeState()`); **windows landed 2026-08-25** (`App.xaml.cs` reads the same UniFFI `ConversationsSession.MlsFoldedCommitsJson()` and publishes it top-level in the state serializer, matching the other five legs; `test_fauna_mls_cross_device_sync.py[windows]` PASSED in 918s with the fold-in barrier active, previously refused loudly per convention 11). Consumed by `helpers/waiting.py::await_folded_commit_after` under the named `MLS_COMMIT_FOLD_S` budget; both D7 sites' waits are gone (sleep-ratchet 4→3 on the native file, and the web twin off the baseline entirely). **Three design points worth carrying.** (1) **A count, not the epoch number**, though `MlsEngine::current_epoch` was right there: an epoch is a value a *replica restore* can also produce, so "epoch > baseline" cannot separate "I folded in their commit" from "I reloaded a replica that was already ahead" — the same argument `ACTIVATION_GESTURES_KEY` makes against a flag, one step further. (2) **`{}` and `null` are different answers and the plumbing keeps them so**: an app with the leg but no session yet publishes `{}` (a legitimate zero), an app with no leg publishes nothing — collapsing them would turn an unbuilt leg into a silent "no fold-ins yet" and spend the whole budget instead of naming the gap in one line. (3) **The baseline must be read BEFORE the peer writes**; read after, it can already include the fold-in, leaving the wait hunting a second commit nobody authors. 📏 **Measured, because "a generous ceiling costs a green run nothing" is a claim worth checking rather than repeating:** instrumented on tui, the barrier returns in **0.00 s** — by the time it is first polled, the two waits already between B's send and it (B's local echo, then the nest-side record-count poll at 1 s cadence) have given A's receive loop ample room, so the fold-in is invariably already done. The green run pays literally nothing for a 90 s ceiling, and the run-to-run spread on this test (5–108 s across four runs) is journey and launch cost, not barrier cost — worth knowing before anyone "optimises" the budget down. 🧪 **Mutation-graded by RUNNING three mutants** against the tier_1 pins (`gate_impl.rs::a_twin_device_takeover_bumps_the_other_device_folded_commit_count` + `re_walking_the_log_does_not_re_count_an_already_folded_commit`): inverting the bump condition reds both; and the *product*-side mutant — the own-leaf resync arm never converging (`Advanced` → `Stalled`) — reds the twin-device pin while correctly leaving the foreign-commit pin green, which is the discrimination the e2e barrier rests on. **And the non-vacuity check the slice could not skip was run LIVE on tui, as a pair against one mutant binary:** with the product mutant compiled in, the new barrier **fails at 90 s** naming `folded commits … now: 0`, while swapping the barrier back for the old `sleep(6.0)` **PASSES in 11 s** — same binary, same broken product. That is the D7 entry's "unable to fail" claim demonstrated rather than argued: the record-count assertion downstream cannot distinguish a takeover from a stale blind-append, because both grow the channel. ⚠ The second pin is not decoration: the chat rail re-walks its log from 0 on its own (the Rule-2 future-epoch heal), so "a re-walk must not re-count an already-folded commit" is a reachable path, and without it a heal could release the barrier in place of the peer's commit — the pre-trigger world satisfying a post-trigger assertion. (landed 2026-08-14, slice D9) **the receive loop's run-now poke and its cycle observable — the poll-cadence family the D7 entry above hands over, closed on its own terms.** The client receive loop (`ConversationsSession::start_receive_loop`) is the delivery path for MLS conversations, the durable inbox-apply drain and the mail read-feeds, and its backstop is a 30 s ticker; the e2e's answer had been to *shorten* the tick (`FAUNA_CONV_POLL_SECS=2`), which lowers the odds of a false pass without changing the shape. Both halves of mechanism 3 now exist: `ConversationsSession::poke_receive_cycle` is an arm of the loop's own `select!` that expands the identical `full_sweep!` the ticker expands (the poke changes *when* a cycle happens, never what it does), and `ReceiveCycles{started,completed}` counts cycles at that single `full_sweep!` site — published as `fauna_e2e_agent::CONV_RECEIVE_CYCLES_KEY` via the shared derivation `state_json::conv_receive_cycles_json`, so each native app leg is a one-line read. Landed on **tui, linux, web and android** (web mirrors both halves on its own pump rail, since that loop is wasm-excluded; android via `ConversationsSession::conv_receive_cycles_json`/`conv_receive_now`'s UniFFI twins, a `conv_receive_now` `TestAgent` command arm, and the `conv_receive_cycles` top-level state key in `TestAgent.kt::serializeState` — landed 2026-08-14; android is the one app that cannot fall back on the old shortened-tick lever at all, since `FAUNA_CONV_POLL_SECS` is never forwarded to an Intent-launched app, so this poke is its only way to anchor delivery without a real sleep); **macOS + iOS landed 2026-08-15** (`ConversationsSession::convReceiveCyclesJson`/`convReceiveNow`'s UniFFI twins, wired into both apple shells' `serializeState()`/`handleTestCommand()`; also gained a small app-agnostic e2e test, `test_conv_receive_cycle_poke.py`, since the canonical `test_fauna_mls_two_client_inbox_drain.py` consumer's second-instance fixture is linux/tui-only); **windows landed 2026-08-25** (`App.xaml.cs` reads the same UniFFI `ConvReceiveCyclesJson()` off the e2e real-conversations session and publishes it top-level; `TestAgent` gained a `conv_receive_now` case poking `App.ConvReceiveNowForTest()`), closing the last app gap — no leg still refuses loudly per convention 11. Consumed by `helpers/waiting.py::await_receive_cycle_after` under the named `RECEIVE_CYCLE_S` budget; `test_fauna_mls_two_client_inbox_drain.py` — the canonical push-suppressed drain proof — is the first consumer and no longer depends on the shortened tick. **Four design points worth carrying.** (1) **Signal-plus-counters, not an awaited ack**: a oneshot reply would be a true barrier but hangs whenever no loop is running (a session built and never started, a poke issued pre-auth), because the reply waits in a queue nobody drains; counters degrade loudly instead — the consumer's deadline poll fails naming the app and the key. (2) **Two counters, for the `ALERT_SWEEP_PASSES_KEY` reason**, not one: `completed > started_at_trigger` is immune by pigeonhole to a cycle that was already in flight when the trigger landed, which matters concretely on linux, where a re-injected session's old loop runs until its next liveness check. (3) **A poke that lands mid-sweep must not be lost** — the native signal stores a permit, and web keeps a `wantCycle` flag the running pass cannot absorb; without that, a consumer pokes and then waits out the very backstop it was avoiding. (4) **The cadence rule went to tier_1, which is the split the convention asks for**: `resolve_poll_secs` is now a pure function with its own tests (including `0` falling back rather than making `tokio::time::interval` a busy loop), so the e2e keeps exactly one wiring proof. 🧪 **Mutation-graded by RUNNING three mutants** against the three loop-level tier_1 pins: a poke arm that never sweeps reds both poke pins (and correctly leaves the counter-ordering pin green); counter theatre — a poke arm that bumps the counters without sweeping — reds the fetch assertion specifically; and both bumps moved to the end of the sweep reds the ordering pin, which is the mutant that would have made the pigeonhole unsound while every test still passed. ⚠ **The pins mute the ticker (a one-day cadence) rather than racing it**, so a later cycle is provably the poke's — without that, a generous budget lets a tick supply the cycle and the pins pass under a deleted mechanism, the "unable to fail" shape D6e and D7 both kept finding. One self-inflicted instance was caught and fixed here too: the mid-sweep pin first used `notify_waiters` to release its held fetch, which drops the wake when the release wins the race — it passed once, then hung to the full budget.
