## Goal

Fauna uses several distinct symmetric and asymmetric keys, each tied to a different *audience* (who is allowed to read the protected content). Without an explicit map, every new content kind risks (a) reusing a key whose audience doesn't match (broadcast a backup secret to a group; seal owner-only data under a rotating group key that loses access when membership changes); or (b) inventing a new key category for an audience already served, multiplying the per-platform key-management surface for no security gain. This doc is the explicit map.

The single load-bearing question for any new content kind is: **who is allowed to read the plaintext, ever?** The answer picks the key. Everything else (lifecycle, rotation, AEAD framing) follows from the audience.

## Roots

All long-lived key material in the system derives from one of four operational roots (plus the offline RecoveryKey standing above the identity seed). Knowing the root tells you the audience and the threat model.

| Root | Per | Holder | Storage |
|---|---|---|---|
| **User's Ed25519 identity seed** (32 bytes) | per user | the user (across all their devices that participate as full clients) | on each participating device, in that app's credential store — how it is protected there is the apps' contract, not a system property (§ Architectural rules #6; owner [`apps/common.md`](apps/common.md) § Credential storage). Cross-device distribution at onboarding (QR-code import, recovery phrase, etc.) is owned by `docs/goal/behavior/onboarding.md` / `docs/goal/behavior/devices.md`. Never resides on the nest — unconditionally, no-modes; there is no posture that permits it. **Ratified 2026-07-23, built (nest-side 2026-07-29; lead-app ceremony 2026-08-02): the seed is a bounded delegate of the offline RecoveryKey** — an identity can be *succeeded* (re-pointed to a fresh keypair, old key refused) via a RecoveryKey-signed statement, so seed theft is recoverable; ceremony owner: `docs/goal/behavior/identity-succession.md`. |
| **User's RecoveryKey root** (32 bytes; ratified 2026-07-23 — primitives built 2026-07-24 in `libs/fauna-core/src/recovery.rs`; registration, seed escrow and the succession ceremony built — status bullet above) | per user | the user, **offline only** (paper/QR recovery kit — never any device, never account state, never anywhere the identity seed unlocks) | Ed25519 signing key = the root directly; X25519 escrow KEM secret via `BLAKE3::derive_key("fauna recovery escrow x25519 2026-07-23", recovery_root)` (rule #3). Signs only the succession-plane records (registration, succession statement, replacement/veto), each domain-tagged; the derived X25519 half unseals the seed-escrow blob resting opaque on the home nest. | **MLS group state** (per-group, openMLS-managed) | per MLS group | the group's current membership at each epoch | held in each user's MLS read-side state on their Fauna apps (which hold the identity seed); persisted at rest under the owner's identity-seed path (Path A, `BackupKey`-class — owner-only), opaque on the nest, reachable only by the user's own Fauna apps. Cross-device sync of this state — plus the owner's per-channel conversation-history slice, which includes own-message plaintext that no log replay can rebuild (a sender cannot MLS-decrypt its own application messages) — rides the `__mls` reserved folder under `BackupKey` via `fauna.mls.{get,put}`; mechanism authority [`../behavior/devices.md`](../behavior/devices.md) § Cross-device MLS group-state sync (design ratified 2026-07-05; slices 1 + 2a + 2b landed — the shared-Rust replica core, the `fauna.mls.{get,put}` plane with CAS, and the `fauna.conversations.channel.send` device-owned-epoch commit gate; the client sync wrapper (slice 4) + client-side commit rebase (3) pending). **Not** sealed under MSEK, **not** reachable from a MUA (IMAP/CalDAV) credential, and **not** held on the MDA bridge — see rule #7 (blast-radius invariant). This is distinct from the MSEK-sealed `MlsSnapshotBlob` of Path B, which carries only mail/calendar read material and no group/epoch state (`libs/fauna-mls/src/wrapped_blob/mls_snapshot_plaintext.rs`). |
| **Deployment Ed25519 signing key** | per nest deployment | the admin, and the nest itself (deployment-infrastructure material, not user data — unconditional, not mode-gated) | plaintext file in the nest data dir; the Nest-internal key-encryption key derives from it (and seals the DKIM signing keys, among others), and the TLS cert key the bridges serve is wrapped to each bridge's service-user pubkey. *Implementation today* keeps the seed on the nest — cached in the DB `nest_keypair` row, durably homed in `nest_deployment.key`, and **preserved across a factory reset** (`bins/fauna-nest/src/deployment_key.rs`) so the channel-binding `nest_actor_id` a client TOFU-pins (`security.md` § Transport trust) does not silently rotate when the box is wiped + re-claimed. It still rotates only on a deliberate admin event (§ Rotation schedule), never on a reset. **Off-box recovery** — after *total box loss* (the disk and its `nest_deployment.key` destroyed, which a factory reset never does), the seed is custodied in the admin's account state (the account-state plane kind `fauna.state.deployment-seeds` — [`config-dissolution.md`](config-dissolution.md) § The `__config` dissolution schedule → *The kinds*) and re-installed at re-provision so the rebuilt box keeps the same `nest_actor_id`; see [`nest/box-recovery.md`](nest/box-recovery.md). **This is the nest's *single* identity (decision 2026-06-29, implemented):** a legacy *separate* random `nest_identity.key` (what `fauna.nest.info`/federation/backup-destination/pairing/sync historically keyed off — a March-2026 accident, never reconciled) has been **retired into this deployment key** — `NestIdentity` is now a view over the reconciled deployment seed (`start_server` derives it via `NestIdentity::from_seed`), so the one custodied seed restores the whole nest identity (tracked internally). |
| **Bridge service-user keypair** (X25519 + Ed25519) | per (bridge_role, bridge_id) | the bridge process | private halves on the bridge host, unwrapped at bridge startup; public halves stored as plaintext routing metadata on the nest. Every nest runs the MDA/MTA bridge processes uniformly (no-modes) — this is not conditional on a storage posture. |

Every other key in the system is *derived* from one of these four roots, or is a transient session key derived from one of these via a standard KEM (HPKE base mode) or KDF (HKDF, BLAKE3 `derive_key`, Argon2id).

**`epoch_secret` is the openMLS exporter output, not a stored field.** Throughout this doc "the MLS group's `epoch_secret`" is shorthand for the *labeled exporter output* obtained from openMLS via `MlsGroup::export_secret(crypto, label, context, 32)` — the RFC 9420 § 8.5 exporter mechanism. Each fauna primitive that wants an epoch-bound key calls the exporter with its own primitive-specific label, so two primitives operating at the same epoch on the same group derive independent 32-byte secrets via domain separation. Live call sites:

- `derive_blob_key` root — `libs/fauna-mls/src/engine.rs:1639,1978` with label `"fauna.blob.v1"` (the on-commit `:1639` path also stashes the per-epoch key for grace-decrypt; the on-demand `:1978` path, `export_blob_key`, serves current-epoch blob-key queries).
- `derive_post_key` (Mls variant) root — `libs/fauna-mls/src/engine.rs:2173-2180` with label `"fauna.subscription.v1"` via `export_subscription_secret`, which also returns the current `epoch` number so callers tag the right epoch.
- A **room-restricted post's** base for an end-to-end room (`../behavior/restricted-posts.md` § Encryption at rest → *Room-restricted*) — `MlsEngine::export_room_post_secret` with label `"fauna.room.post.v1"`, returning the epoch beside it. Like the blob key it outlives its epoch on a native device: the engine keeps each epoch's secret before every merge that advances the group (`room_post_secret_at`), which is what lets a post sealed at an earlier epoch still open for a member who held that epoch.
- `chunk_crypto`-adjacent exporters — `MlsEngine::export_chunk_key` with label `"fauna.chunk.v1"` (`libs/fauna-mls/src/engine.rs:2005-2011`; the pre-M2 interim chunk root, retired for bound sets) and `MlsEngine::export_folder_keys_key` with label `"fauna.fileset-keys.v1"` (`libs/fauna-mls/src/engine.rs:2092-2098`; seals the M2 content-key *envelope*). Under the live M2 mechanism the `chunk_crypto` root for a bound set is the per-set **content key** distributed via that envelope, not an exporter output (§ Audience: an MLS group → *M2 content-key mechanism*).

The exporter output itself is *not* persisted in the MLS snapshot blob — it is re-derived from the snapshot's group state on demand and held in `zeroize::Zeroizing<…>` mlocked memory (see § Plaintext key lifetime on bridges below).

## Derived keys, by audience

The taxonomy is **the audience for the decrypted plaintext** — who must, ever, be able to read it. Two keys serving the same audience would be redundant; one key serving two audiences would mean a removal in one context revokes access in the other.

### Audience: owner only (one user, all of their devices, forever)

**Moved 2026-08-05 → [`owner-key-material.md`](owner-key-material.md)** (heading text unchanged —
`§ Audience: owner only`, `§ Path A…`, `§ Path B…` all resolve there by changing only the file).
The audience definition for the taxonomy: content one user must read on all of their devices,
forever — membership never changes, so the keys never rotate on a membership event. Two derivation
families serve it: **Path A** rooted in the identity seed (`BackupKey`, `NestBackupKey`, the index
master key) and **Path B** rooted in a MUA credential (the MSEK and its sealed-blob siblings).
Which family a new owner-only kind belongs under — and every entry's mechanism, custody and
status — is owned by that doc.
### Audience: an MLS group at a specific epoch (a defined membership set that can change)

**Moved 2026-09-06 → [`mls-group-key-material.md`](mls-group-key-material.md)** (heading text
unchanged — `§ Audience: an MLS group at a specific epoch`, `§ M2 content-key mechanism` and every
`§ M2 …` sub-heading resolve there by changing only the file).
The audience definition for the taxonomy: content a **defined membership set that can change**
must read. Membership changes are the whole difficulty — the keys must rotate when a member is
removed (forward secrecy), and a joiner must be given a way to reach history sealed before it
arrived. Three entries serve it: the **per-chunk file-sync key** (`chunk_crypto`), rooted not in
the raw `epoch_secret` but in the M2 **content-key generation** the group distributes and
rotates; and the two per-content per-group seals **`derive_post_key`** (group-restricted post
bodies) and **`derive_blob_key`** (conversation attachment blobs), both rooted directly in the
group's `epoch_secret`. Each entry's derivation, custody, distribution and status — and the M2
mechanism whole — is owned by that doc.

### Audience: an opaque set of subscriber pubkeys at a point in time (audience-restricted posts, dynamic membership without an MLS group)

**Subscription `KeyBlob` X25519 wrapping** — `libs/fauna-core/src/subscription/crypto.rs`

- **Root:** the author's chosen *period key* (32 bytes, generated per-subscription-period by the author).
- **Derivation per recipient:** ECDH(author-ephemeral X25519, subscriber X25519 pubkey) → `BLAKE3::derive_key(context = "fauna.keyblob.v1", key_material = shared_secret)` → ChaCha20-Poly1305 with a random 12-byte nonce. One `KeyBlobEntry` per subscriber per period; envelope shape `ephemeral_pubkey (32) || nonce (12) || ciphertext+tag`. Beside the entries the signed blob carries a **key witness**, `key_commitment = BLAKE3::derive_key("fauna.keyblob.commit.v1", period_key)` (optional, omitted when absent — additive since 2026-09-24): the author holds no entry of its own blob, so this is how it tells which key a stored blob wraps; the rule that reads it is owned by `docs/goal/behavior/succession-aftermath.md` § Re-key scope, the period-keys row.
- **Period-key lifecycle:** rotates on every membership change (a subscriber removed forces a new period key, re-wrapped to the remaining subscribers); archival key material is minted per-subscriber on demand to backfill historical periods.
- **Client-minted at-rest custody (author's client).** The period key has no nest-side home — the nest mints, holds and wraps no subscription period key (`bins/fauna-nest/src/subscription_handlers.rs`; the nest-held plane that served legacy pre-Phase-4 tiers was removed by the compat-remnant sweep on 2026-09-27, [`version-compatibility.md`](version-compatibility.md) § Dimension 2, the fourth ratified exception) — so the author's client generates it at tier-create and retains it as **owner-only** state in the account plane's `fauna.state.subscriptions` kind — one fleet-only row per period key and one per staged removal, sealed under the account's generation tip (Path A-sibling-2 — [`owner-key-material.md`](owner-key-material.md)), synced across the author's device fleet and never readable by a nest; the rows, their key grammar and their join are owned by [`config-dissolution.md`](config-dissolution.md) § The `__config` dissolution schedule (the kinds table's row), and `fauna_core::data::SubscriptionsConfig` is their read fold, which every consumer reads and writes through one `fauna_client_subscriptions::PeriodKeyStore` over the account runtime's handle (plane-only since 2026-09-30; no `UserConfig` path remains). Per tier it keeps the `current` period plus every rotated-out `prior` period (uncapped — unlike `mail.prior_mseks`'s cap-2 — because new-subscriber archival backfill needs the full period history); each `TierPeriod` carries its `version` + `rotated_at` so the client can correlate archival fetches and so the nest's `rotated_at`-monotonicity check (`stale_rotation`, per the 2026-05-15 broadcast-KeyBlob spec) is satisfiable. The mint orchestration reads `current` to wrap the live roster and rotates (push `current` into `prior`, generate a fresh key, bump `version`, strictly advance `rotated_at`) on a removal. Because a removal's fresh key is **irrecoverable once the nest stores the re-wrapped `KeyBlob`** (lose it and the author can neither read their own future content nor mint for new subscribers in that period — a no-user-data-loss violation), the rotation is **crash-staged**: the new period is written as a staged-removal row and persisted *before* the network upload, then committed into `current` only once the nest confirms, the staging settled in the same step (a crash between upload and commit resumes from the sentinel idempotently — `not_subscribed` on the re-upload means "already applied"). This mirrors `MailConfig::pending_rotation`'s MSEK-rotation sentinel; every staging is its own row, so a peer device's staged key is never dropped, and a settled staging stays settled (the plane deletes nothing). ⚠ **The post-succession rotation deliberately does NOT use this sentinel, and the asymmetry is the ruling rather than an oversight** (`succession-aftermath.md` § Re-key scope, the period-keys row): staging exists so a removal keeps sealing under the *old* key until the nest confirms, and after a succession the old key is the compromised one — continuing to seal under it is the exposure being closed. That leg therefore commits the fresh period into `current` *before* the upload, which meets the same irrecoverability hazard by the same persist-before-upload ordering. What it owes is derived from `TierPeriod.minted_by` — the identity that minted the period key, stamped by whichever custody transition minted it and never rewritten, since a republish is not a mint — and an interrupted upload is recovered by the stored blob being older than the local `current`. ⚠ **Neither question may be answered from `KeyBlob.author`**: that records who last *published* a blob, and an ordinary approve republishes the current key under the caller's authorship, which is how a predecessor-keyed blob came to read as successor-minted and retired the rotation silently, fixed 2026-09-22. Every write is a per-row join at the store's writer door, so a concurrent multi-device write never drops a period key, and nothing is ever deleted — a period once recorded stays. Lifecycle owner: `fauna-client-subscriptions::orchestration` (`SubscriptionsAuthor`) over the pure `custody` transitions.
- **Protects:** audience-restricted posts' period key (the per-post body is then sealed via `derive_post_key(period_key, post_id)`, and any media attached to those posts is sealed under the same `derive_post_key`-derived per-post key, with random nonces per blob — per `docs/goal/ui/media.md` § Encryption at rest). See `docs/goal/behavior/restricted-posts.md` § Encryption at rest, "Audience-restricted" class.
- **Audience justification:** the subscriber set is dynamic but not heavy enough to want a full MLS group (thousands-member groups have non-trivial tree/commit cost; subscriber tiers do not need the ratchet machinery a conversation needs). The `KeyBlob` design amortizes wrapping over a period; rotation cost is paid only on removal, not per post.

`KeyBlob` minting (`create_key_blob_entry` per subscriber, assembled and signed by `mint_key_blob`) and period rotation are managed by a device delegated `ManageSubscribers` via the `verify_key_blob_signature` chain — the author's client, for every tier (the nest mints no `KeyBlob` since the nest-held plane's 2026-09-27 removal). `mint_key_blob` produces both ordinary-period and archival blobs (caller-supplied `wrapped_key` is the period key; the resulting `KeyBlob` shape is identical). See `docs/goal/behavior/restricted-posts.md` § Encryption at rest for the client-minted consequence.

The account-data plane's storage-group keying

The recipient-set scheme owns the roster/lattice/witness mechanics; R15 the
rationale). Key-material half, all reusing ratified formats:

- **Content root:** the **group generation key** — 32 bytes, random per
  generation, content-derived generation id with the R14 key↔id commitment
  ([`owner-key-material.md`](owner-key-material.md) § Path A-sibling-2 →
  The schedule build design). Removal-class membership changes mint a new
  generation; adds wrap the retained bundle to the joiner (archival
  backfill, as the subscription scheme below).
- **The machinery root (sealing ruling, 2026-08-17 — what seals the group's
  MACHINERY kinds; BUILT with 1b the same day):** the group's
  machinery kinds — birth record, roster entries, mint rows, top-up rows,
  the "cannot key" self-heal signal — seal under a dedicated **group
  machinery root**: 32 random bytes minted by the initiating account at
  scope birth, immutable for the scope's life, handed to each member at
  admission inside the same X-Wing wrap bundle as the retained generation
  bundle, and healable by the same member top-up vehicle when missing.
  Content kinds are untouched: they seal under the generation tip per the
  content-key bullet below. **Custody of a member's held copy (ruled at the
  ceremony build, 2026-08-17):** the root is random and the admission
  bundle one-shot, so each member persists it in their OWN account plane —
  `fauna.state.group-machinery-root`, one Immutable row per scope,
  fleet-only + `GenerationTip`-sealed for the reception keypair's key-reach
  reason (the member's whole fleet must read the group; a stolen device
  falls out of reach at the next fleet mint). Held group *generation* keys
  deliberately get no such row: their wraps rest in the group plane and
  re-open with the reception secret on demand. This is the group's `SealingEpoch::Gen0`
  analogue — the account plane's bootstrap stratification
  ([`owner-key-material.md`](owner-key-material.md) § Path A-sibling-2 →
  The schedule build design, *Bootstrap stratification*) transplanted, with
  **possession replacing derivability**: members share no cross-account
  root secret to derive from, so "derivable forever from `BackupKey`"
  becomes "held forever from admission". Bootstrap terminates at the root
  by construction: a joiner unwraps the root from its admission bundle and
  can then read the whole roster and mint DAG, evaluate tip admissibility,
  and find its generation wraps — before holding any generation key.
  - **Forced, not chosen — every alternative dies on contact.**
    *Tip-sealing* is circular by construction: roster coverage is what
    makes a mint admissible (charter § The recipient-set scheme, delta
    (ii)), so resolving the tip requires reading the roster, which would
    require the tip. *Chain-sealing* (machinery of generation N under
    generation N−1) breaks joiner bootstrap — an add wraps only the
    retained bundle, so a joiner holds nothing for a shredded intermediate
    generation and could never read the mint DAG it must merge to find the
    tip — and couples machinery readability to content-key retention,
    defeating per-generation shred. *The birth generation doubling as the
    root* is the cheapest-looking variant of the same mistake: it conflates
    the audience/epoch axes R14 split deliberately and makes the birth
    generation forever unshreddable. *Cleartext machinery* rests the
    group's social graph unsealed on every custodian — refused by the
    sealed-at-rest invariant. *Authority-account key material* is owner-only
    — non-authority members could never derive it. *Per-member sealed
    copies* fork the at-rest form per reader, which breaks the shared
    plane's content-addressed convergence and the R7 one-form posture.
  - **Id-bound at birth (the R14 key↔id commitment, applied):** the birth
    record gains a `machinery_root_commit` field —
    `BLAKE3::derive_key(<frozen commit context>, root)` — so the
    content-derived scope id commits to the root. A joiner unwraps the
    root, opens the birth record, re-derives the scope id it was offered,
    and refuses a root whose commitment does not match: root substitution
    at admission is detected at the joiner, never trusted from the
    ceremony. Two parties naming the same scope id therefore provably hold
    the same machinery-reading capability — a split-root scope is a crisp
    refusal, not silent AEAD garbage. (Amended slice 1a's
    `GroupBirthRecord` before any production scope existed; the record is
    **frozen** since the 1b landing, 2026-08-17.)
  - **Derivations:** per-kind machinery entry/item keys repeat the ratified
    two-step shape (`derive_key` for domain separation + `keyed_hash` per
    kind — Path A-sibling-2's pattern) under **two frozen group-named
    context strings** (minted at the 1b build:
    `fauna.group.machinery.{seal,item-key}.v1 2026-08-17`,
    `fauna_core::crypto::GroupMachinerySchedule`), with the machinery root
    as key material; the sealed form is the unchanged class-2 entry envelope.
    (New strings, not the account-state pair: the account plane reuses its
    contexts *across generations of one schedule*; a different plane gets
    its own named pair, as `chunk_crypto` and `path_crypto` do.)
  - **Never a severance mechanism, never rotated.** Severance is wrap
    targeting on generations (content) plus roster supersession
    (admission); rotating the root would re-seal all machinery and sever
    nothing. Exposure, stated honestly (the R14 posture): every
    ever-admitted member keeps the root for the scope's life, so roster
    history and mint METADATA — generation ids, member actor keys,
    reception pubkeys, removal events — stay readable to past members
    forever, while generation KEYS minted after a removal never reach them
    (wrap targeting severs) and transport admission refuses a removed
    member new rows at its next evaluation, so the retained root opens only
    ciphertext already held or obtained out of band. A custodian (no root)
    sees nothing past the custody floor. The exposure is per-scope: one
    group's root says nothing about any other scope. The same retention
    holds for a device removed from the AUTHORITY's account, where what it
    must lose is authorship rather than reach — severed by revocation rows
    on the plane, never by this root
    ([`recipient-set-scheme.md`](recipient-set-scheme.md) § The
    recipient-set scheme → *Severance, per axis*).
- **Wrap:** the same X-Wing (PQ-hybrid) envelope as R14's device and escrow
  wraps (`fauna_mls::wrapped_blob::xwing_envelope`) — one wrap format,
  never a fork. Target: each member's **group-reception X-Wing keypair**.
- **The group-reception keypair (per account):** the secret half is a
  fleet-only, `GenerationTip`-sealed kind in the member's own account plane
  — so its custody, device-removal severance, and escrow ride the member's
  own R14 machinery, nothing group-specific. The public half is published
  actor-signed (nest-served like key packages; carried peer-wise over
  authenticated channels in the no-nest profile). It **rotates on the
  member's own fleet mint** (device removal at minimum), and the rotation
  is the member's re-mint signal to every group holding them — the
  static-per-account-target rule-6 hole (T20 constraint (c)) is closed by
  this coupling.
- **Per-kind content keys (BUILT 2026-09-09):** derived from the generation
  key per kind context (`BLAKE3::derive_key`, the T14 stratification
  pattern) — content seals under the tip; older generations stay retained
  for existing content, exactly the R14 posture.
  - **As built (`fauna_core::group_content`):** the ratified two-step under
    a **third** frozen group-named context pair —
    `fauna.group.content.{seal,nonce}.v1 2026-09-09` — `derive_key` for the
    plane, `keyed_hash` for the kind, so two content kinds of one group
    never share a key and the content branch is unrelated to the machinery
    branch or to any account branch on the same 32 bytes (pinned by
    `the_content_branch_is_independent_of_the_machinery_branch_and_of_every_account_branch`).
    The sealed form is the `blob_crypto` shape rather than the class-2
    entry envelope: ChaCha20-Poly1305 with a *keyed* deterministic nonce
    (convergent, no candidate-plaintext oracle) plus the **generation id as

    reader knows which wrap to open, and the binding is what makes
    relabelling a refusal rather than an opaque AEAD failure. The class-2
    envelope was not reused because its AAD is account-plane entry
    coordinates (writer id, scope, kind, key) that a shared log addressed by
    `(channel, seq)` does not have.
  - **Content kinds so far:** `fauna.conversations.room.message` — a
    **community conversation room's** log
    ([`../behavior/community-rooms.md`](../behavior/community-rooms.md)
    § The three classes → *Community*), which is therefore also the first
    consumer of the wraps below — and, since 2026-09-10,
    `fauna.conversations.room.attachment` for that room's attachment blobs
    (same § → *Attachments — the second content kind*, which owns why it is
    a second kind and what the home nest's read covers), and
    `fauna.conversations.room.post` — not a seal of its own but the **base**

### Audience: deployment infrastructure (bridge service users; one specific bridge process)

The entries here serve keys that the *deployment's own processes* — the nest and its bridges, not the users — need to operate. The `WrappedMsekBlob` covered in [`owner-key-material.md`](owner-key-material.md) (Path B under owner-only) is *not* in this category: its plaintext audience is the user.

**Room-read keypair — the home nest as a community room's reader (ratified 2026-09-08; keypair BUILT 2026-09-09, its first consumers BUILT the same day).** One reception keypair per nest in the recipient-set scheme's own shape (§ Audience: a storage group — the same wrap format members use), of the *service* class the nest already holds (the deployment identity, the issuer signing key below), minted at boot and never by a read.

- **As built (`bins/fauna-nest/src/room_read_key.rs`, schema 52):** a random 32-byte ikm sealed under its own dated context (`nest_kek::ROOM_READ_CONTEXT`) in the single-row `nest_room_read_key` table and registered in `nest_kek::SATELLITES`; the X-Wing keypair is re-derived from the ikm through the **member-side kind's own** two frozen contexts (`fauna_core::group_generation::GroupReceptionKeyRecord`), so the nest is a recipient of exactly the same kind as every other member rather than a parallel one. The public half is published on `fauna.nest.info` as `room_read_pubkey` — a public key of the deployment, beside `nest_id`, because a wrapping device needs it *before* the membership exists, so a membership-gated read would be a chicken-and-egg. A nest that predates the field omits it, which reads correctly as *this nest cannot be a community room's reader*.
- **When it mints — at boot, never on a read (2026-09-13; the same day extended to the issuer signing key's active signer and the OAuth refresh-token signing secret below, which carried the same window).** `start_server` runs one boot step, `nest_kek::mint_at_boot`, before the serving generation it builds answers anything. It reads the deployment seed from `nest_keypair` under the same database guard it inserts under, so the seed it seals under is the one the database holds at that instant, and it seats this row, the issuer key set's active signer, and the refresh-token secret. Every consumer of those rows only looks its row up, and an absent row is the named `nest_kek::NotProvisioned` error, never a mint. Every door that mints on purpose reads the seed from `nest_keypair` on the connection it writes on, never from the serving generation's copy, and holds the database guard from that read through its insert. That covers the issuer key's two rotation arms and the forced session-secret arm, each inside its own transaction. It also covers the family members with no boot moment (2026-09-13). The per-account ones mint on a user's act: the ATProto authoring sub-key `K` on its first fetch, a deposited nsec on its link, the NIP-46 bunker signer on its first invite, an ActivityPub account's key on enable. The ActivityPub instance actor is a single row, but it needs the nest's domain, so boot cannot mint it on a domainless nest, and its first use after a later domain claim is what mints it. The reason is the rotation ceremony's bounded hand-off window ([`nest/box-recovery.md`](nest/box-recovery.md) § Deployment-seed rotation): after the transaction commits, the outgoing generation still holds the retired seed in memory. A write sealed under that copy seals the row under a seed the box no longer has. That row never opens again, and the satellite walk refuses it on every later rotation, so no further rotation could commit. Minting at boot takes every read off the minting path and seats the rows before any ceremony can run; a nest upgrading into this rule mints on that restart. Pinned by `room_read_key::tests::rotation_window`, by the `rotation_window` tests beside the OAuth doors, and by a rotation-window test beside each door with no boot moment.
- **Why sealed-random and not seed-derived** (the ratification's "minted from the deployment seed at first boot" reads either way as to *what* is minted — *when* is the bullet above; resolved at the build, 2026-09-09). This key's **public** half rests in rows *other members minted* — a room's generation key wrapped to it at admission — so its identity must survive a deployment-seed rotation. A keypair derived directly from the seed would change identity the moment the seed rotates, silently making every community room's wrap to this nest unopenable, and no ceremony could repair it: the rows sit on other members' planes. The satellite shape has exactly the security property this section claims — DB-only exfiltration of the wraps opens nothing without the deployment seed — while `nest_kek::reencrypt_satellites` re-keys the row on rotation and the reception public key stays put (pinned by `room_read_key::tests::a_seed_rotation_keeps_the_reception_public_key`).
- **The consumers (BUILT 2026-09-09, schema 57).** The birth ceremony seats this nest's `room_read_pubkey` on the room's floor as its own wrap target — the nest's key, never one the founder named — an owner/admin device's generation mint wraps to it like any other member, and the nest opens that wrap to build the room's **search index** over the sealed log. Rotating it out of a mint revokes the read *and deletes the views in the same act* — as far as that revoke reaches: it binds an **honest** home nest, and is not a cryptographic revocation against one that misreports its own floor ([`../behavior/community-rooms.md`](../behavior/community-rooms.md) § Implementation status today → *How far the revoke reaches*, which owns the bound). Which of the read position's purposes are built is [`../behavior/community-rooms.md`](../behavior/community-rooms.md) § Implementation status today's to say; this section owns only the key.

- **What it opens:** the room generation keys of the community rooms homed on this nest — each wrapped to it by an owner/admin device at admission and on every rotation, one recipient among the members' ([`../behavior/community-rooms.md`](../behavior/community-rooms.md) § The three classes → *Community*). Never a room's machinery root and never an authority: the nest reads, it does not mint or rotate.
- **Audience justification and threat model:** the nest is a *member* of a community room by the members' own act — inviting the home nest is what makes a room community-class — so the readable position is a grant the room made and can rotate out. The key gives no reach into any end-to-end room (no wrap is ever made to it there; TP12 is a theorem under TP8), and no reach into any room homed elsewhere (a relay nest holds ciphertext only). DB-only exfiltration of the wraps opens nothing without the deployment seed; full nest compromise reads the community rooms the nest already reads by design and nothing else. Rule #4 is untouched for every user-only content class; rule #5 places it beside the issuer key.

A nest-minted grant would put the record somewhere the user's app cannot vouch for. Where a format is opaque to the oracle (a raw byte string), the policy is the class's *rate and revocation* alone, and the class is marked as such. **The sovereign class is never on this table, and is stated as an enumerated deny list, not an omission:** PLC rotation, handle and domain changes, key succession ([`../behavior/identity-succession.md`](../behavior/identity-succession.md)), the MLS identity root — anything that changes *who the user is* is user-device-only and never delegable. **The ATProto classes ride the protocol's own door (RULED 2026-10-02; refutable downstream — it reads rule #9's "a keyless `identity.op` grant" as the *Fauna family's* grant shape, not the only one).** The oracle's own rule — where a protocol has a remote-signing standard, the oracle speaks it — decides `atproto.commit`, and ATProto's standard is the PDS itself: a client never asks a PDS to sign a commit it built, it calls `com.atproto.repo.*` under OAuth `repo:` scopes and the PDS builds, signs, chains and announces the commit. Three facts make this the only shape. **(1) Custody:** the repo signing key is bridge-held, sealed to the PDS bridge's attested key, and constraint C7 of [`../behavior/atproto-pds-full.md`](../behavior/atproto-pds-full.md) forbids widening it — a nest-side custodian cannot sign, and a nest kind that "hands the signing to the bridge" would be `createRecord` re-spelled over WS-RPC, with the bridge calling `ingest_external_write` back to the very nest that forwarded it. **(2) A commit is not a detached signature:** it names the MST root only the repo holder computes, so a principal-built commit could not be applied without re-deriving it — which is `applyWrites`. **(3) Ecosystem reality:** a standard ATProto client knows no Fauna scope; gating the write on a second, Fauna-family grant would break every one of them. So the class is carried by the ATProto family: the write funnel ([`../behavior/atproto-pds-full.md`](../behavior/atproto-pds-full.md) § F2 detail) IS the `atproto.commit` door, the Go PDS bridge is its custodian, the ATProto consent row (`atproto_oauth_grants`, or the app credential) is the grant the user approves and revokes on the connected-apps surface, and **the Fauna family never carries it**: `atproto.commit` is no `IdentityOpClass` variant and no `fauna:identity:op:` qualifier (pinned — `identity_op::tests::the_atproto_commit_class_is_never_a_fauna_family_qualifier`); the enum stays "one variant per class the Fauna family carries". A Fauna principal that wants the account to post reaches `post.author`, and the projection carries the post to ATProto — a Fauna-family ATProto write would be a second path to one effect. `atproto.service_auth` is the other way round and stays a Fauna-family class — a detached JWT a Fauna principal consumes, with no ATProto-plane consent row to ride — ruled in *The bridge-held custodian — `atproto.service_auth`* below; `getServiceAuth` under `rpc:` scopes at D8 keeps serving OAuth-plane clients beside it. **What the oracle's properties still owe at that door — one implementation row (UNBUILT):** *(i) the live check per key operation* — an ATProto access token is registry-checked only at refresh, a 60-minute bound that is fine for a proxied read and wrong for a key operation; the funnel's `ingest_external_write` round trip is the nest's per-write moment, so the bridge forwards the session-family id it already holds (`xrpc.Caller.SessionID`; an additive optional field) and the nest refuses a write whose `atproto_sessions` row is revoked or expired or whose grant row is revoked — a revoke bites at the very next write, at zero extra round trips; *(ii) the ceiling* — `RateWindow` per session, two integers on the session row at the same handler (the frame's per-IP limiter is not per principal); *(iii) the per-operation record* — one row per write per session, newest 256, the `nostr_oracle_ops` shape, served to the owner's app beside the Nostr record. The policy row is already enforced: `repo` must equal the session's account (`atprotopds.checkWritePreconditions`), the funnel chains and CAS-checks every commit, and no `com.atproto.identity.*` NSID is served — a route-table pin test rides the same row.

**The bridge-held custodian — `atproto.service_auth` (ruled 2026-10-02; refutable until the class is built; unbuilt).** The repo signing key is NOT nest custody: it rests in `atproto_identity_key_blobs` sealed to the `atproto.pds` bridge's attested X25519, which only that bridge opens ([`../behavior/atproto-pds-full.md`](../behavior/atproto-pds-full.md) § Key material inventory, C7 — so the 2026-09-05 table's "the nest's `atproto` custody" was loose wording, corrected here). `Custodian::AtprotoRepoKey` is therefore the **first-party PDS bridge**, and the class is performed in two halves with ONE policy site. **The nest's door** (`bins/fauna-nest/src/atproto_oracle.rs`, the Nostr custodian's `authorize`/`record` shape — a `ThirdParty` kind reached only by an `identity.op` qualifier whose class this custodian performs) does everything the key is not needed for: the principal row and the owner's live grant to its attested key, re-resolved per request; the class's own policy (the table's row — the declared set read off the roster row per request, the deny half, the lifetime clamp); the `RateWindow`, kept per `(account, principal)` on `atproto_oracle_principals`; and the per-operation record (`atproto_oracle_ops`, newest 256 per principal — the audit split above). **The handoff** is the shape every nest→bridge call already takes ([`transport.md`](transport.md) § Request lifecycle refuses a nest-started request, so the permission-set call's push-out/RPC-back pattern is reused, never a new frame): the door pushes `fauna.bridges.atproto.service_auth_requested` — a random `request_id`, the account, `aud`, `lxm`, the clamped `exp` — to every connected approved PDS bridge, and the bridge answers over the BRIDGE-class kind `fauna.bridges.atproto.deliver_service_auth` with the token or a refusal; the two legs are correlated by the waiter registry the permission-set call's is lifted into (`bridge_round_trip.rs`, one shape for every such call), under a hard-constant deadline. **The bridge adds no policy of its own**: the push arrives over its authenticated nest connection, the nest door IS the decision, and the bridge mints with the signer it already holds (`repoSignerForActor` + `MintServiceAuth` — the same key and claim set as `getServiceAuth`, `iss` the account's DID), clamping the lifetime to the one shared constant; an older bridge that ignores the push kind answers nothing, which the deadline turns into a refusal. **Every failure is the one closed-world refusal** — no approved PDS bridge connected (decided before any push goes out), a shed waiter, a bridge-side refusal, the deadline — answered as the door's `permission_denied`, never a token this nest did not receive. **Why this class stays a Fauna-family class at all**, given that `getServiceAuth` under `rpc:` scopes already serves OAuth-plane clients: the consumer here is a Fauna principal — a plugin or remote app that holds a Fauna grant family and no ATProto session — and a service JWT is a detached credential it can carry to the service itself; there is no ATProto-plane consent row for such a principal to ride (which is exactly why `atproto.commit` does NOT take this road — the paragraph that follows). **Proof split:** the policy arms and the correlated round trip (a captured push answered through the deliver handler) tier_1 in the module; the mint itself tier_3 in `tests/e2e-unified` against the real Go bridge (`test_atproto_oracle.py` — the bridge cannot run inside a Rust test), where a token for a declared `(aud, lxm)` verifies ES256K against the signing key in the account's DID document.

**The DKIM class is the outbound spool's own door — `mail.dkim` (RULED 2026-10-03; BUILT 2026-10-03).** The table's "first-party migration" is a custody decision, and [`../behavior/mail-bridge-lifecycle.md`](../behavior/mail-bridge-lifecycle.md) § DKIM provisioning (automatic) → *Custody moves to the nest* owns it: why the key is the nest's and not the MTA's, when the key mints, the one sign site, the removal of the sealed-to-MTA path (2026-10-04). This doc owns the key's entry and the class's place on the oracle. **The key.** One per (domain, selector), a *service* key of the class the nest already holds, in the issuer signing key's shape: minted nest-side, the private half (Ed25519 or RSA — whatever [`../behavior/mail-multidomain.md`](../behavior/mail-multidomain.md) § Per-domain DKIM provisions) sealed at rest under the nest-internal key-encryption key with its **own** dated context string (rule #3; `nest_kek::MAIL_DKIM_CONTEXT`, `"fauna mail dkim key encryption 2026-10-03"`), in the `BackupKey` wire shape, in `mail_dkim_keys.key_wrapped`, and registered in `nest_kek::SATELLITES`, so a deployment-seed rotation re-wraps it and the published selector stays valid. Today every mint is Ed25519. It mints under § Room-read keypair → *When it mints*: at boot for the mail domains that exist, at the deliberate door for a new one or a rotation, never by a read. The unsealed public half is the DNS record. **Audience and threat model:** the nest itself. It is the deployment's identity to peer MTAs, never a user's key, and it opens no content — rule #4 is untouched and rule #5 places it beside the TLS floor key. DB-only exfiltration signs nothing without the deployment seed. Full nest compromise signs as the domain, and already could: the nest mints the key and names the public half the admin publishes. The internet-facing SMTP process holds no DKIM key, and the bridge's identity can be re-keyed without touching the deployment's. Losing the key loses nothing a user authored; the rotation path mints a successor. **Not a Fauna-family class.** A DKIM key belongs to the deployment, and an `identity.op` grant is a *user's* device vouching for operations on that user's own identity keys. No user can mint a grant over a key that is not theirs, so there is no grant to re-resolve and nothing a consent card could say. Like `atproto.commit`, the class is carried by its own plane: `mail.dkim` is no `IdentityOpClass` variant, no `fauna:identity:op:` qualifier (pinned by `the_mail_dkim_class_is_never_a_fauna_family_qualifier`, beside `the_atproto_commit_class_is_never_a_fauna_family_qualifier`) and no `ThirdParty` kind. A third-party principal that sends mail does so through a mail door, and its message is signed at the same site as anyone's. **The oracle's properties at that door.** *The live check:* the caller is the approved MTA bridge, and `caller_class_for_actor` re-resolves its roster row on every RPC, so an admin's revoke refuses the very next hand-out ([`apps/bridges.md`](apps/bridges.md) § Capability-allowlist enforcement); the admin's approval is the grant. *The policy:* the table's row, checked against nest state. The door reads the message itself, so the format is not opaque and the class is not rate-and-revocation-only. A detached-signature kind taking a header hash could not check the From domain, and one taking the header bytes would send every message's headers through a second call to a nest that already holds the message — which is why the door is the spool. *The ceiling and the record:* a signature exists only for a spool row, and every spool row was admitted by the nest-side outbound meters ([`../behavior/mail-app-surface.md`](../behavior/mail-app-surface.md) § Outbound metering; the submission quota in [`../behavior/smtp-server.md`](../behavior/smtp-server.md) § Architectural rules) and names its submitter. The meters are the class's ceiling and the spool row is its per-operation record; a second `RateWindow` and a second operations table would count the same events twice.

### Audience: the public (no key)

Public posts, signed `Profile` records, public ACME cert chains (the public half), federated wire transport (TLS handles confidentiality on the wire, the at-rest content is `Post`-signed plaintext) — and, since the folders re-model phase 4 (2026-08-17), **`public`-audience folder content**: a folder whose owner explicitly declassified it (`folders.md` § Target re-model; the invariant exception is owned by `principles.md` § The user always controls their data) rests as plaintext chunks under blake3 content addressing — the self-describing `stored_hashes = None` manifest shape every reader passes through — with plaintext names/paths (they are URLs). The seal sites' selection is the armed `SyncEngine::with_public_audience` flag, never a missing key: a keyless non-public engine still fails closed. No symmetric or asymmetric key wraps the plaintext; integrity comes from blake3 content addressing (folder chunks) or Ed25519 signatures (posts/records).

## Why two fauna-sync paths — `BackupKey` vs `chunk_crypto`

A natural question for any future reader: the code has two distinct chunk-encryption paths (`BackupKey` and `chunk_crypto`), both ChaCha20-Poly1305, both in fauna-sync's domain. Why?

**Both are live** (the shared-folders track landed 2026-06 → 2026-07): `BackupKey` protects the owner-only fauna-sync content kinds — backups and ordinary *unbound* (single-user) folder chunks (and `UserConfig` until its rail retired 2026-10-02 — [`config-dissolution.md`](config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)) — while `chunk_crypto`, rooted in the set's M2 per-set content key, seals *group-bound* shared folders. The engine's precedence is gated on the bound-marker (`SyncEngine::effective_backup_key` is `None` for a bound set), so a bound set never silently falls back to `BackupKey`.

The reason the two paths exist as a design — and the reason this hierarchy keeps them distinct rather than collapsing them — is the **audience axis** above:

- **Cross-user-shared folders (live for `chunk_crypto`).** A folder shared by multiple users via an MLS group is a *dynamic-membership* audience: members join (the user grants access to a collaborator), members leave (access revoked), the active set must keep working at each transition. The standard primitive for managed dynamic membership with forward secrecy is MLS, and fauna already runs MLS for messaging — so using the group as the key-*distribution* channel (the M2 per-set content key, rotated on removal) costs no additional key-management surface. Deterministic per-chunk derivation off the root secret **+ the chunk content hash** is what makes content-defined dedup work across group members holding the same generation.
- **Backups, single-user folders (live for `BackupKey`; `UserConfig` until its rail retired 2026-10-02).** Owner-only audiences. The user is the only authorized reader, period — and "the user's device fleet" is a special case of "owner-only" because every device of theirs holds the identity seed. There is no membership question, no rotation-on-removal need. A static `BackupKey` deterministically derived from the identity seed is the right primitive — every one of the user's devices re-derives it independently, no distribution mechanism is needed, "forward secrecy from yourself" is not a threat, and the cost of a one-member-MLS-group-per-user is avoided.

The two keys are therefore not redundancy. Using `chunk_crypto` for owner-only content would require a one-member MLS group per user just to have an `epoch_secret`, with rotation overhead for content that doesn't benefit from rotation. Using `BackupKey` for cross-user-shared folders would have to invent a per-share key distribution + rotation mechanism MLS already gives for free.

The corresponding architectural rule below (#1) is: pick the key by audience, not by convenience. Ordinary single-user (unbound) folders remain on `BackupKey` now that the cross-user path has shipped — single-user fleets do not benefit enough from MLS overhead to migrate; migrating them for uniformity stays an option. Either choice is consistent with the audience rule.

## Walkthrough: CalDAV / IMAP encryption-key story

A natural-question section because IMAP/CalDAV are the most key-heavy user-facing surface and the question "which key does the nest use to decrypt mail when the MUA fetches it?" deserves a definitive answer in `docs/goal/`. **Short version: `BackupKey` is not involved in the IMAP/CalDAV path at any point, and the nest itself never holds a decrypt capability for it.** The mail/calendar decryption path runs on the user's MLS read-side keys, reached through Path B (`WrappedMsekBlob`'s MSEK) — the AUTH/unwrap mechanism and the post-AUTH content fetch are both uniform, no storage-mode axis exists (`../architecture/nest/storage-modes.md`; see [`../behavior/imap-server.md` § Authentication](../behavior/imap-server.md) + § Content path). The nest holds ciphertext only for every mail/calendar/card record (`SealedStorage`, the sole `Storage` impl since Phase 4) — there is no server-side plaintext copy of the user's MLS keys anywhere, for classifiers, FTS, or federation-receive (those paths were retired with the storage-mode axis; `content-scoring.md`, `content-index.md`).

The MDA bridge — the Go mail-bridge binary in its MDA role (role discovered from nest by the enrolled service-user keypair, no `--mode=...` flag) — is the sole IMAP/CalDAV protocol server; owner: [`../behavior/imap-server.md`](../behavior/imap-server.md) §§ Authentication / Content path. This walkthrough covers what is unique to this doc: **which key opens what** at each step.

1. User's primary client at credential-enable: generates random 32-byte MSEK; serializes the **mail/calendar read-side snapshot** (the standing recipient-mail keypair material of [`owner-key-material.md`](owner-key-material.md) § Path B-sibling-2 — not MLS group/epoch state, per rule #7); seals snapshot under MSEK (`seal_mls_snapshot`); derives a per-credential AEAD key from the MUA credential (Argon2id for PLAIN, HKDF-SHA-256 for OAUTHBEARER); seals MSEK under that key (`seal_wrapped_msek`); uploads both blobs to the nest via `fauna.bridges.provision_wrapped_mls_blob` and `provision_mls_snapshot_blob`. The nest stores them as opaque ciphertext (`bridge_wrapped_mls_blobs`, `bridge_mls_snapshot_blobs`); it cannot read either.
2. MUA AUTH: the MUA sends `LOGIN <actor>@<domain> <credential>` (PLAIN) or the OAUTHBEARER equivalent to the MDA bridge.
3. MDA fetches `WrappedMsekBlob(actor_id, credential_id)` via `fauna.bridges.fetch_wrapped_mls_blob`, derives the unwrap key from the credential the MUA just supplied + the KDF params baked into the blob, and AEAD-decrypts to recover MSEK. **AEAD success is AUTH success** — there is no separate password-hash check; cryptographic ability to unwrap is the proof of credential.
4. MDA fetches `MlsSnapshotBlob(actor_id)` and AEAD-decrypts under MSEK to recover the user's **mail/calendar read material** — the standing recipient-mail HPKE keypair(s) of [`owner-key-material.md`](owner-key-material.md) § Path B-sibling-2 (current + one per prior generation, every generation ever retired — ruled 2026-10-06). Per rule #7 the snapshot carries **no** MLS group/epoch secrets, membership, or leaf indices — those stay in Path A's Fauna-app audience and never reach the bridge.
5. The bridge can now open this user's mail, calendar, and CardDAV address-book content — HPKE-opening each `MailRecordEnvelope` / sealed `bridge_carddav_cards` vCard with the recovered recipient-mail secret ([`owner-key-material.md`](owner-key-material.md) § Path B-sibling-2; the same secret opens all three — `docs/goal/behavior/carddav-server.md` § Storage model) — and serve it over IMAP/CalDAV/CardDAV; it also unseals the `WebdavKeysBlob` under the same MSEK to serve the explicitly-WebDAV-served folders ([`owner-key-material.md`](owner-key-material.md) § Path B-sibling-3). It **cannot** open the user's conversations, group-restricted posts, or unserved folders (those need keys the bridge never receives — rule #7). MSEK + snapshot are held in `zeroize::Zeroizing<…>` mlocked memory; both are zeroized on LOGOUT, IDLE timeout, or session disconnect. Nothing persists on the bridge across sessions.

`BackupKey` is not touched anywhere in this flow. The user's identity seed is not on the bridge. The user's long-term Ed25519 signing key is not exported in the snapshot — the bridge can read mail but cannot sign as the user on the federation.

This path never touches `BackupKey` or the subscription `KeyBlob`; the only fauna-sync chunk key it will ever hold is a **WebDAV-served** set's M2 content key via the `WebdavKeysBlob` ([`owner-key-material.md`](owner-key-material.md) § Path B-sibling-3, ratified 2026-07-06 — per-set opt-in, never `BackupKey`-sealed chunks). Everything else serves other content kinds.

### Why `BackupKey` is *not* used here

The question "could we just have the bridge derive `BackupKey` from the identity seed and use it for the IMAP path too?" is worth answering explicitly:

- The bridge cannot derive `BackupKey` — it has no access to the user's identity seed. The seed lives only on the user's primary client; giving it to a third-party MUA, or to a bridge process under the box owner's control, would defeat the trust model that puts the seed on a user-trusted device.
- Even if it could, `BackupKey` is wrong for this use. The bridge needs a session-scoped credential-bound unwrap (the MUA supplies a credential the user can rotate or revoke; the bridge must lose access on credential revocation). `BackupKey` is identity-bound and lifelong — to revoke bridge access you'd have to rotate the identity seed (catastrophic) instead of one credential.

The two keys are therefore separate by design, not by accident. This is rule #1 ("pick the key by audience") applied: the *plaintext-audience* is the same user in both cases, but the *delivery surface* is different (fauna's own client with the seed vs. a third-party MUA with a credential), so they need different unwrap keys.

(Live-vs-pending status for this whole surface — the running Go MDA, the retired `--mode` flag, the wrapped-blob handlers — is in `## Implementation status today` at the top of this doc.)

## Plaintext key lifetime on bridges

The wrapped-blob design keeps every unwrapped key out of long-lived nest state. Once any of the entries above is unwrapped on a bridge process for use, the same discipline applies uniformly: held in `zeroize::Zeroizing<…>`-wrapped memory, `mlock`ed against swap, zeroized on the earliest of session close / IDLE timeout / LOGOUT / process exit / explicit refresh. This section consolidates the per-bridge specifics that were previously dispersed across the wrapped-blob design (tracked internally, ratified 2026-05-08).

- **MDA bridge — IMAP/CalDAV.** At every MUA AUTH the bridge derives the per-credential AEAD key from the MUA-supplied credential, AEAD-decrypts `WrappedMsekBlob` to recover MSEK, then AEAD-decrypts `MlsSnapshotBlob` under MSEK to recover the user's mail/calendar read material (the standing recipient-mail HPKE keypair(s) — [`owner-key-material.md`](owner-key-material.md) § Path B-sibling-2). **All of it** — the per-credential AEAD key, MSEK, the unsealed snapshot bytes, the derived recipient-mail secret(s), and (once Plan 5b's capability-position index build lands, `../behavior/content-index.md`) the MSEK-derived mail/calendar index-segment key — lives in `zeroize::Zeroizing<…>` mlocked memory for the session's lifetime and is zeroized on LOGOUT, IDLE timeout, or session disconnect. The bridge holds **no** MLS group/epoch material (`derive_blob_key` / `derive_post_key`-Mls keys, epoch secrets) — that state is not in the snapshot and never reaches the bridge (rule #7); the one ratified exception is the explicitly-WebDAV-served sets' M2 content keys via the MSEK-sealed `WebdavKeysBlob` ([`owner-key-material.md`](owner-key-material.md) § Path B-sibling-3 — per-set opt-in, same mlock/zeroize session discipline, and these are per-set *content* keys, never group epoch secrets). Nothing persists on the bridge across sessions; a re-AUTH repeats the unwrap from scratch.
- **MTA bridge — SMTP submission.** The bridge holds no DKIM key: the nest signs at the outbound hand-out (§ Audience: deployment infrastructure → *The oracle* → *The DKIM class is the outbound spool's own door*) and the bridge relays the bytes it is handed. TLS private keys are unwrapped from `TlsCertBlob` at bridge startup and on cert renewal, held mlocked until renewal swaps in the next blob. `WrappedSubmissionTokenBlob` unwraps at SMTP-submission AUTH, the inner `SubmissionToken` lives mlocked for the submission session, zeroized on session close. Both bridges treat unwrapped key material as untouchable by user-facing code paths beyond the operation each key authorizes (TLS-terminate, submit-as).
- **The nest itself.** Holds no unwrapped *user-content* key material of any kind — no MLS keys, no MSEK, no recovered mail/calendar secrets; `SealedStorage` (the sole `Storage` impl since Phase 4) never reads what it stores. The one exception is the *deployment*-scoped Nest-internal key-encryption key (§ Audience: deployment infrastructure → Nest-internal key-encryption key), which is derived on demand from the deployment signing seed for the operation that needs it (encrypt or decrypt a Nostr privkey) and dropped — same `Zeroizing` wrapper, no mlock needed because the call sites are short-lived synchronous functions, not session-scoped. The nest does hold its own **deployment-infrastructure** secrets unconditionally, on disk, outside the user-content tier entirely — e.g. the TLS floor private key it generates and persists for self-signed serving (`bins/fauna-nest/src/self_signed_cert.rs::load_or_create_floor_key`, `floor-privkey.pem`) — these are nest identity material, never a user's key, and were never mode-conditional. DKIM signing keys are deployment-infrastructure secrets of the same kind, held sealed under the Nest-internal key-encryption key and opened only for the hand-out that signs (§ Audience: deployment infrastructure → *The oracle* → *The DKIM class is the outbound spool's own door*); no bridge process ever holds one.

**Carrier shape — the rule that binds on clients too (ratified 2026-08-05).** The discipline rule below is about **lifetime**: *how long* unwrapped material may live, and *where*. It is not the whole of custody, and reading it as an exemption for clients is the mistake this ratification caught — the earlier 2026-08-05 ratification applied zeroize-on-drop custody to the **index master key**, which the next sentence names as a permitted long-lived *client* holder, and the two only appear to contradict because they answer different questions. The second question is **shape**, and it binds every holder of user-content key material, client and bridge alike:

- **A derivation hands its output out non-`Copy`** — `Zeroizing<[u8; 32]>`, never a bare array. A bare `[u8; 32]` is `Copy`, so it is silently duplicated on every assignment and pass-by-value, and no duplicate is ever zeroized; `Copy` and `Drop` are mutually exclusive in Rust, so *being non-`Copy` is what makes zeroize-on-drop expressible at all*. This covers the window between derivation and its custody type or its wrapping, which is where the material is barest. Live instances: `derive_index_master_key`, `derive_index_segment_key`, `derive_mail_epoch_root` — the whole MSEK/seed-derived family, no member left bare (priority #4: fixing one member of a family splits it).
- **A long-lived carrier is non-`Copy` and zeroizes on drop.** The lifetime rule permits a client to hold `BackupKey`, MSEK, MLS state and the index master key for a whole login session; it never permitted holding them in a type that duplicates itself invisibly. On a *cache* — one value read by many consumers — a `Copy` carrier's duplicate count is unbounded, which is strictly worse than the single-hop derivation case the bullet above covers. Live instance: `MailKeys` (`libs/fauna-client-conversations/src/lib.rs`), the one shared lazily-derived mail-key cache, which holds the MSEK root itself; it is `Clone` + `ZeroizeOnDrop` and not `Copy`.
- **Custody ends at a foreign-language boundary, and that is stated rather than papered over.** Where derived material must cross into JS or app glue (e.g. `MailSettingsMachine::mail_epoch_roots`, flattened to one `Uint8Array`), no Rust wrapper can follow it; the rule is then that what crosses is the narrowest sufficient material — generation-scoped mail read material, never a root that reaches further (rule #7) — and the crossing is documented at the call site.
- **Pinned at compile time — and the two cases need *different* pins.** A **derivation** carries a `const _…_IS_NOT_COPY: fn(&[u8; 32]) -> Zeroizing<[u8; 32]> = …;` pin, so reverting its return type to `[u8; 32]` fails the *build* at the pin rather than only wherever a call site happens to be strictly typed. The conflicting-impl trick (an `impl<T: Copy>` blanket plus a concrete impl) does **not** work here and pins nothing — coherence rejects it against a foreign type like `Zeroizing` whether or not that type is `Copy`. A **carrier** needs no separate construct: deriving `ZeroizeOnDrop` generates a destructor, and re-adding `Copy` beside it is then rejected outright — `error[E0184]: the trait `Copy` cannot be implemented for this type; the type has a destructor` (verified by running the mutation, 2026-08-05). Either way a runtime test cannot do this job: it can observe neither an absent `Drop` nor an implicit copy.

- **The best carrier is no carrier — hold the cache HANDLE and ask per use.** Where a shared cache already owns the material, a consumer that copies the key out of it becomes a second custody site to keep in step, and the bullets above then only govern how badly it does so. Holding the cache `Arc` and asking at each use removes the question: the borrowed value lives for one call and dies with it. Live instance: `NestContactCorpus` (`libs/fauna-client-conversations/src/lib.rs`), the contacts resolver, which held a bare session-lived MSEK copied out of [`MailKeys`] until that was closed 2026-08-10; it now holds `Arc<MailKeyCache>` — the posture the contacts *walk* had used all along, which is why fixing it added no new custody type (priority #4). A key check at attach time is then a **readiness** question — may this reader claim the kind — and must keep nothing from the cache. **This case needs a third kind of pin**, because what it asserts is an *absence*: neither a derivation's return-type pin nor `ZeroizeOnDrop`'s destructor says anything about a type that correctly holds no key material, and no runtime test can observe an absent field. A `const` assertion on the struct's width does — `_NEST_CONTACT_CORPUS_HOLDS_NO_BARE_KEY` fails the build with `E0080` if the 32-byte field is reintroduced, which is the single most likely regression, since copying the key out of the cache reads as the obvious way to reach it.

**The 2026-08-12 survey — the closed enumeration (owner of the sweep's result; [`owner-key-material.md`](owner-key-material.md) § Implementation status today points here).** The rule above was ratified 2026-08-05 against the family a finding happened to name, and declared its own remainder unswept. Every other holder is session- or operation-scoped.

## Architectural rules

1. **Pick the key by audience.** Owner-only content uses one of two paths — `BackupKey` (identity-seed-derived; for client surfaces that hold the seed) or `WrappedMsekBlob`'s MSEK (MUA-credential-derived; for IMAP/CalDAV via the MDA bridge); group-shared content uses an `epoch_secret`-derived key (`chunk_crypto`, `derive_post_key` for the `Mls` variant, `derive_blob_key`); dynamic-broadcast-tier content uses the `KeyBlob` X25519 wrap; deployment-infrastructure material a bridge must hold (the TLS cert) uses the wrapped-blob HPKE shape against that bridge's service-user pubkey, and deployment-infrastructure material only the nest uses (DKIM signing) is a member of the Nest-internal key-encryption family. A new content kind picks from this list — it does not invent a new category.
2. **One key per audience.** Two keys serving the same audience are redundant; one key serving two audiences means a removal in one context revokes access in the other.
3. **Domain-separate every derivation.** Every BLAKE3 `derive_key` / HKDF expansion off a shared root uses a domain-separated context string, versioned with the year-month-day of introduction (`"fauna backup encryption key 2026-03-12"`, `"fauna.gated.v1"`, `"fauna.blob.v1"`, `"fauna.wrapped-blob.oauth.v1"`, `"fauna.chunk.v1"`). New context strings are versioned too; never reuse a string for a different purpose.
4. **The nest holds no key that opens user content (no-modes; unconditional — there is no other posture).** Wrapped MLS-key blobs and TLS cert blobs are stored opaque; unwrapping authority lives on the user's primary device or on a bridge during an active session. The nest's plaintext floor is metadata only. `SealedStorage` (the sole `Storage` impl since Phase 4) never reads what it stores — there is no server-side classifier / FTS / federation-receive path that needs per-user MLS keys, and none is permitted to be added without explicit user approval + a Don't-do-these entry in `encryption-at-rest.md` (the retired "plaintext-mode nest holds the keys it needs for its server-side functions" trust statement described exactly the surface no-modes eliminated).
5. **The nest's own deployment-infrastructure secrets are held unconditionally, on disk, outside the user-content tier entirely.** The TLS floor private key it generates and persists for self-signed serving (`bins/fauna-nest/src/self_signed_cert.rs::load_or_create_floor_key`, § Plaintext key lifetime on bridges) is deployment identity material, never a user's key — this was never mode-conditional and is not a downgrade of rule 4. DKIM signing keys sit beside it: the deployment's identity to peer MTAs, never a user's key, held by the nest sealed under its Nest-internal key-encryption key (§ Audience: deployment infrastructure → *The oracle* → *The DKIM class is the outbound spool's own door*). `BackupKey` never lands on the nest either — the chunk-encrypt step happens on the data owner's client, unconditionally (the client is the only `BackupKey` holder), and the nest is the destination, storing ciphertext opaque.
6. **User-identity seed wrapping is a client-side concern, not a system property.** No protocol property rests on how a device keeps the user's Ed25519 identity seed: the system depends only on the device being trusted by the user. How each app protects the seed at rest is the apps' own contract, owned by [`apps/common.md`](apps/common.md) § Credential storage — its per-app table, the sealed arm for a device with no secure store, and the web app's posture are stated there and nowhere else. (Corrected 2026-10-01: this rule had said the seed is plaintext on disk by default, which the apps' contract has not allowed on any native app since it was written.)
7. **A MUA (IMAP/CalDAV/CardDAV/WebDAV) credential reaches only mail + calendar + the CardDAV address book + the folders the user explicitly serves over WebDAV — never conversations, posts, unserved sets, or identity. (Blast-radius invariant.)** The MSEK / `WrappedMsekBlob` path (Path B) is the *mail-and-calendar-and-address-book-and-served-files* owner-only path. The material it conveys to the MDA bridge at MUA-AUTH — the MSEK-sealed `MlsSnapshotBlob` plus anything derivable from MSEK, plus (ratified 2026-07-06) the MSEK-sealed `WebdavKeysBlob` of [`owner-key-material.md`](owner-key-material.md) § Path B-sibling-3 carrying **only the explicitly-WebDAV-served sets'** M2 content keys (per-set, user-opt-in, revoked by content-key rotation — `docs/goal/behavior/webdav-server.md` § Key model) — must be exactly the keys needed to read the user's mail, calendar, and CardDAV address book at rest: the standing recipient-mail HPKE keypair(s) ([`owner-key-material.md`](owner-key-material.md) § Path B-sibling-2; current + the last-2 grace keypairs) — the **same** keypair also opens the CardDAV `bridge_carddav_cards` vCards (`docs/goal/behavior/carddav-server.md` § Storage model: the address book adds a *content kind* sealed to the recipient keypair, **not** a new key to the snapshot, so the conveyed key material is unchanged) — and, once Plan 5b's capability-position index build lands, the **mail/calendar index-segment key** (`docs/goal/behavior/content-index.md` § Encryption posture). It must **never** convey the user's MLS group/epoch state (ratchet tree, `epoch_secret`s, `derive_blob_key` / `derive_post_key` material), the content-index **master** key, `BackupKey`, the identity seed, or the content key of any folder the user has **not** flagged for WebDAV serving. Those belong to the *Fauna-app* owner-only audience (Path A — reached from the identity seed) and are sealed under an owner-only key a MUA credential cannot derive. **Why this is a rule and not an implementation detail:** a MUA credential is structurally weaker than the identity seed — it is a password or bearer token typed into third-party mail apps, cached in OS keychains, and presented to the MDA bridge on every login — so its leak (combined with at-rest data access on an encrypted box) is a *more probable* compromise than identity-seed theft. Bounding its reach to mail + calendar + the CardDAV address book + the explicitly-served WebDAV sets keeps that blast radius off the user's conversations, group-restricted posts, unserved folders, search index over those kinds, and federation identity; the worst case is `encryption-at-rest.md` § Trust property under compromise → "Ungranted-box compromise + a target user's IMAP/CalDAV/CardDAV/WebDAV credential". Consequently the `MlsSnapshotBlob` is **permanently scoped to mail/calendar read material**; the MLS group/epoch state conversations and group posts need is placed in Path A's audience, not in it. The v1 wire shape complies (`libs/fauna-mls/src/wrapped_blob/mls_snapshot_plaintext.rs` carries `leaf_init_keypairs` = `derive_recipient_hpke_keypair(MSEK)` per grace generation, plus — 2026-07-18 — `mail_epoch_grace_roots`, prior generations' derived mail-epoch roots: strictly more mail read material, nothing beyond this rule's mail/calendar bound). **Supersession (refutable):** this reverses the earlier ratified target — stated in the frozen design (tracked internally, ratified 2026-05-14) and, until this change, mirrored in this doc's § Roots / [`owner-key-material.md`](owner-key-material.md) § Path B, `encryption-at-rest.md` § Group memberships, `docs/goal/ui/conversations.md`, and `nest/storage-modes.md` — that sealed the full MLS group state under MSEK. That target was never implemented (the v1 snapshot is mail-only), so the reversal carries no migration. A downstream session that finds a concrete reason the MDA bridge must reach MLS group state (e.g. a bridge-side feature beyond IMAP/CalDAV that cannot move to the client) should refute this rule explicitly here rather than quietly re-broadening the snapshot. **Enumeration correction (2026-07-13) — the recipient keypair reaches a FOURTH content kind: the per-user spam model.** A client-sealed spam model, and the sealed `subject` / n-gram `delta` of each `spam_training_history` row, are ordinary `kind: "mail-record"` envelopes under `AadBinding::for_mail_record()`, HPKE-sealed to the *same* `derive_recipient_hpke_keypair(MSEK)` / `derive_recipient_xwing_keypair(MSEK)` pubkey as a mail body (`libs/fauna-mail/src/spam/model_write.rs`; the nest's `fetch_spam_model` seal-on-read calls the same `seal_recipient_blob` helper the body seal uses; the Go MDA's `\Junk`-train re-seal likewise). Exactly like CardDAV, this adds a **content kind** to the keypair's reach, **not a key** to the snapshot — the conveyed key *material* is unchanged, so this rule's bound is not breached (a MUA credential that reaches the user's mail also reaches a model *derived from* that same mail). It is enumerated because the **consequence is load-bearing for the capability plane**: the recipient-mail secret is the spam model's *only* opening key, so `content.read{mail}` already conveys read of the model and its training history — and **no capability scope whose payload is that secret can be narrower than `content.read{mail}`, whatever its `kind` string says** (§ Don't do these; `encryption-at-rest.md` § Capability tiering). **Resolution (ratified 2026-07-13):** `content.read{spam-model}` is accordingly a **keyless** scope — no grant wraps the recipient-mail secret for a narrower purpose; the contributor's client seals a model *copy* to the aggregation holder's own pubkey instead (§ Audience: deployment infrastructure → Spam-baseline holder copy; flow owned by `docs/goal/behavior/mail-spam.md` § Encrypted-mode interaction).
8. **Domain-separate every *signing context* of a shared signing key — the signing analogue of rule #3.** When one Ed25519 key signs in more than one protocol context, each signed message MUST begin with a distinct constant domain-separation prefix (the codebase convention is `b"fauna.<context>.v<n>\0"`, NUL-terminated so no tag is a prefix of another — the registry — shared across every domain-separated signing key in the system, not only the deployment key — it also carries the **device/custodian** key family (`DEVICE_HANDSHAKE_V2`, `DEVICE_GRANT_REVOKE_V1`, `DEVICE_ADOPT_V1` for the sync-agent renewal device key, added 2026-07-19 through 2026-08-15, the handshake re-cut nest-bound 2026-09-23, `DEVICE_ADOPT_V1` retired 2026-09-29 with its kind — reserved, never reusable, because an adoption body re-splits into a revoke body; `CUSTODY_HANDSHAKE_V2` for the nest-custody proof-of-possession, likewise nest-bound, owned by `account-replica-posture.md` § Replica posture; `apps/sync-agent-credentials.md` § Credential model owns the renewal-device mechanism) and the single-context `ACCOUNT_AGE_CLAIM_V1` tag, signed by the *platform's* attestation key (Apple App Attest / Google Play Integrity) rather than any Fauna-held key, owned by `docs/goal/behavior/family-safety.md` § The account age band — lives in `fauna_protocol::sig_domain`), so a signature made in one context can never be reinterpreted as valid in another — cross-context confusion is then *structurally* impossible rather than resting on the message formats happening to be disjoint. This binds the **deployment Ed25519 signing key** in particular: post the single-identity unification (§ Roots) it is the nest's *single* identity, and has signed across **six distinct protocol contexts** (three since retired) — the TOFU **cert-binding** transport proof (A — **two producers** sharing the `CERT_BINDING_V1` tag: `auth_handlers::build_cert_binding`, over `served_cert_spki ‖ client_nonce` (and, on the verify path, `served_cert_spki ‖ challenge_nonce ‖ client_nonce`), and its cert-*optional* twin `auth_handlers::build_identity_binding`, which serves the pre-identity `fauna.auth.nest_handshake` and signs the **bare nonce** when the nest has no readable served SPKI; `security.md` § Transport trust), the now-**retired outbox** envelope (B — see *Implementation status* below), the **federation** CID (C), the now-**retired** **subscription KeyBlob** (D) and **archival KeyBlob** (E) — see *Implementation status* below — and the **deployment-seed rotation statement** (F, `fauna_protocol::nest_rotation::NestRotation` — signed twice per statement, once by the superseded key and once by the successor; nest half BUILT 2026-08-12, [`nest/box-recovery.md`](nest/box-recovery.md) § Deployment-seed rotation) — where the first three formerly used a separate `nest_identity.key`, and D/E signed subscriber key material with the deployment key via `fauna_core::encoding::sign_envelope` (→ `SignedEnvelope::sign`) over the bare dag-cbor CID until their retirement; F signs a canonical dag-cbor **structured statement**, not a bare CID, and was tagged from birth. **Implementation status (COMPLETE 2026-06-30; outbox retired 2026-07-10; KeyBlob retired 2026-09-27):** the registry + helper landed (`fauna_protocol::sig_domain`) and **exhaustively enumerates all six historically-shipped contexts**. **Three carry an applied tag today** — the **cert-binding** (A, `CERT_BINDING_V1`), the **federation** CID (C, `FEDERATION_HELLO_V1`), and the **deployment-seed rotation statement** (F, `NEST_ROTATION_V1` — applied from birth 2026-08-12, since a new deployment-key signing context has no compat reason to go untagged, per § Don't do these). The **outbox** envelope (B, `OUTBOX_FORWARDED_POST_V1`) carried an applied tag from 2026-06-30 until 2026-07-10, when post-forwarding moved onto the channel-authenticated `fauna.federation.post.forward` kind and the nest stopped signing each forward — the retired JSON `ForwardedPost` envelope + its signer were deleted outright, so `OUTBOX_FORWARDED_POST_V1` is now **retired and permanently reserved** in the registry (never reusable); the retirement only *strengthens* the exclusion argument below by removing a deployment-key signing context outright rather than merely tagging it. The **KeyBlob** (D/E) was **documented exempt** (`KEYBLOB_V1`, reserved-not-applied — *KeyBlob exemption* below) until 2026-09-27, when the compat-remnant sweep removed the nest-held subscription period-key plane: the nest wraps no period key any more, so both KeyBlob signers left the nest and every `KeyBlob` is minted and signed by the author's client, never the deployment key. `KEYBLOB_V1` is now **retired exactly as B's tag was — reserved, not applied, never reusable** — and this retirement likewise only strengthens the exclusion argument: the deployment key has **no untagged or bare-CID signing context left**. The cert-binding's `CertBinding.tagged_sig` carries `CERT_BINDING_V1 ‖ served_cert_spki ‖ client_nonce`; the legacy untagged `sig` half that once rode beside it for pre-tag clients, and the verifier fallback that accepted it, were removed 2026-09-24 by the compat-remnant sweep (`version-compatibility.md` § Dimension 2), so no untagged channel-binding signature exists — and the structural guarantee never depended on that removal: it is delivered by every *verifier of another context* requiring its own tag. The **federation** signer (C, `bins/fauna-nest/src/federation_sig.rs` `sign_payload`/`verify_payload`) signs *and* verifies over `FEDERATION_HELLO_V1 ‖ cid`; because federation is **not live in alpha** (no external peers) the tag is enforced with **no legacy fallback** — there is no compat oracle on this context. C is the one context with a **cross-language** verifier: the Python e2e harness signs the federation hello byte-identically (`tests/common/helpers.py` `sign_as_nest` → `tests/common/envelope.py` `sign_dagcbor_envelope`, both prepending the same tag), proven by a green tier_3 federation run (`test_post_forwarding.py` / `test_federation.py` / `test_namespace_sync.py`, all of which complete the hello handshake). No live forgery existed at any point (independent review, tracked internally — both directions NOT-REFUTED). **KeyBlob exemption (D/E — second-pass review, tracked internally, resolved 2026-06-30; moot since the 2026-09-27 retirement, kept as the reservation's rationale):** the deployment key ALSO signed the **subscription KeyBlob** (D) and the **archival KeyBlob** (E) in `bins/fauna-nest/src/subscription_routes.rs` via `fauna_core::encoding::sign_envelope` → `SignedEnvelope::sign` over the **bare dag-cbor CID**. That single context was **documented exempt** (registered as `KEYBLOB_V1`, *reserved-not-applied*) rather than carrying an applied tag, for three compounding reasons. **(1) No forgery reduction:** the signed message is a fixed CID with no attacker-influenced tail, so cross-context confusion needs a blake3 collision/preimage on that CID (infeasible) — defense-in-depth only. **(2) Tagging is uniquely expensive *and* anti-uniform here:** unlike A/B/C (bespoke per-context signers where prefixing a tag is a one-liner), the KeyBlob is the *only* deployment-key context riding the **universal embed-as-bytes `SignedEnvelope` sign-over-CID wire** shared by every signed Fauna kind (Post, Profile, DeliveryReceipt, ContactRequest, DeviceAuthorization, Tombstone, ShareToken); its signature lives in the fixed **100-byte envelope** (36 CID ‖ 64 sig) pinned by the cross-language fixtures (`libs/fauna-cbor/tests/cross_language_interop.rs`), so a tag can be neither a struct field (circular — it would sit *inside* the signed value) nor an envelope extension (breaks the 100-byte invariant). Applying it would fork KeyBlob onto a bespoke sidecar signature across all 7 apps (KeyBlobs are verified by subscriber clients ⇒ a bare-bytes change is a wire break) for zero security gain — pure divergence/tech-debt. **(3) Structural separation by exclusion** (see the audit below): once A/B/C carry their tags, the KeyBlob is the *sole* deployment-key context that verifies a bare CID, so there is no second bare-CID verifier for a KeyBlob signature to be confused with. `KEYBLOB_V1` stays **reserved** in the registry (pre-distinct + prefix-free, never reusable). **Pre-external-peer audit (COMPLETE — covers all six):** the deployment-key verifiers are A (cert-binding), C (federation) and F (deployment-seed rotation statement) — all tagged; B (outbox) is retired — no signer and no verifier remain (both were deleted 2026-07-10), so it can neither source nor be a confusion *target* — and D/E (KeyBlob) are retired from the deployment key (2026-09-27): no deployment-key KeyBlob signature is produced, so none exists to be confused. A, C and F each require a **distinct, prefix-free** tag on their preferred (or, for F, only) path (`CERT_BINDING_V1` vs `FEDERATION_HELLO_V1` vs `NEST_ROTATION_V1`, all NUL-terminated), so a tagged signature in one cannot verify in another; A's legacy untagged fallback (removed 2026-09-24, above) accepted only a message that **begins with the nest-controlled served SPKI** — `served_cert_spki ‖ client_nonce` on the handshake paths, `served_cert_spki ‖ challenge_nonce ‖ client_nonce` on the verify path — and **two structural guards, applied 2026-08-26, make that true of every byte either producer signs untagged** rather than leaving it to the shapes happening to be disjoint. **(i)** Both producers *enforce* the canonical nonce length (`fauna_protocol::auth::CLIENT_NONCE_LEN` = 32, or its 64-byte challenge fold on the verify path) in the single shared signer `auth_handlers::sign_channel_binding`, refusing any other length instead of signing it — the wire fields are `ByteBuf`s a caller can make *any* length, and a 4-byte nonce behind a 32-byte SPKI would have made the untagged message exactly 36 bytes. **(ii)** The untagged half is emitted **only where that SPKI prefix exists**: on the twin's bare-nonce path (no readable served SPKI — where every signed byte would be the caller's) no untagged signature is produced at all, and the wire-required `CertBinding.sig` carries the *tagged* signature's bytes, which costs no consumer because every client that knows `fauna.auth.nest_handshake` postdates the tag and `nest_trust::verify_binding_signature` prefers `tagged_sig`. So every untagged deployment-key message is 64 or 96 bytes — **never a 36-byte CID by construction**, not attacker-forgeable into another context's tag. Before those guards the twin was a pre-identity signing oracle over caller-chosen bytes on a cert-less nest and this clause was false, C accepts only messages beginning with `FEDERATION_HELLO_V1`, and F (unlike A) shipped with no untagged legacy path to begin with — it accepts only its own canonical dag-cbor `NestRotation` encoding prefixed with `NEST_ROTATION_V1`. **The deployment key therefore has no untagged bare-CID context at all** (while D/E lived, the KeyBlob was the sole one, and a lone bare-CID verifier had no second context to be confused with: a KeyBlob signature could satisfy neither A — a 36-byte CID ≠ served-SPKI ‖ nonce by length/structure — nor C or F, lacking their prefixes). Cross-context confusion is thus **structurally excluded across all six contexts**, and introducing any *new* deployment-key signer — over a bare CID or anything else — is forbidden without its own applied tag (§ Don't do these). The cross-protocol domain-separation audit is **complete**.

   **The rule binds the ACTOR (user) key too — audit COMPLETE (2026-08-17), tagged-only.** Rule #8 is explicitly *"shared across every domain-separated signing key in the system, not only the deployment key"*, but before this audit its coverage extended only to the deployment key. The **actor** key — the far more widely used shared signer — signs in **ten live contexts, every one now carrying an applied `sig_domain` tag with no untagged accept path anywhere**, each built and verified through a single-source `fauna_protocol` builder so signer and verifier cannot drift: **direct-auth login** (`AUTH_HANDSHAKE_V2`, `fauna_protocol::auth::handshake_signed_message`, verified `auth_core::direct_auth_core`), **challenge/verify** (`AUTH_VERIFY_V2`, `auth::challenge_verify_signed_message`, verified `auth_core::verify_core`) — both re-cut **nest-bound** in place on 2026-09-23 (the retired `.v1` tags stay registered, never reusable; `login.md` § Binding the nest owns the binding), **registration** (`ACCOUNT_REGISTER_V1`, `account::register_signed_message`, verified per candidate domain in `account_core::register_core`), emergency **lockout** (`ACCOUNT_LOCKOUT_V1`, `account::account_lockout_signed_message`), one-time **claim-admin** (`CLAIM_ADMIN_V1`, `claim::claim_admin_signed_message`), **invite** submit/cancel (`INVITE_SUBMIT_V1` / `INVITE_CANCEL_V1`, `invite::invite_{submit,cancel}_signed_message` — the cancel tag replaced the ad-hoc `b"cancel"` literal), and the wizard **NAT-mode / storage-mode** commits (`SETUP_NAT_MODE_V2` / `SETUP_STORAGE_MODE_V1`, `nat_mode::nat_mode_signed_message` / `storage_mode::storage_mode_signed_message` — two contexts the original audit's table missed, byte-twin newline-canonical bodies told apart only by tag). The NAT-mode commit is **nest-bound** (`SETUP_NAT_MODE_V2`, joined 2026-08-31, verified by `nat_mode_core::commit_nat_mode_core`): the unbound `SETUP_NAT_MODE_V1` form named no nest, so one admin signature verified at every nest where that actor was admin (two independently-claimed nests accepted the same blob); V2 appends the target nest's own identity to the signed bytes and the nest requires it to match its own. V1 was accepted alongside through a transition window until the compat-remnant sweep removed that arm in place on 2026-09-24 (`version-compatibility.md` § Dimension 2, the fourth write-off); its tag stays registered, never reusable. One more candidate surface, the client-side **domain-search** signer (`sign_domain_search`), was found to have **no nest verifier or route at all** — dead code end-to-end — and was **deleted** (client-core + ffi + wasm exports + app wrapper shims) rather than tagged. **The variable-length contexts (registration, invite-submit) are additionally length-prefixed** — every element, tag included, as `(len as u64)_be ‖ bytes` (`sig_domain::domain_separated_length_prefixed`, the injective push-relay encoding) — closing item 3's re-split ambiguity (adjacent `handle`+`domain` / `handle`+`message` with no delimiter, reachable on a multi-domain nest whose verifier tries every active domain as a candidate).

   **The historical finding, for the record:** two of these actor-key ceremonies — the no-nonce login handshake and claim-admin — used to build confusable signing messages, so a signature minted in one context could verify in the other; lockout was distinguished only incidentally. The audit above closed the class outright. **Closure (2026-08-17):** slice 1 landed the additive-for-compat transition (dual-emit + `tagged_signature` sidecar + `ACTOR_KEY_UNTAGGED_FALLBACK` shim, mirroring cert-binding), and the same-day ruling that this is a one-time, pre-user reset (no migration owed) ratified collapsing it: the sidecar fields, the fallback constant, and every transitional verifier were **deleted**, and the single `signature` field of each request now carries the tagged signature outright. This was deliberately **stronger than the cert-binding transition** at the time (whose legacy untagged fallback persisted safely because its message began with the nest-controlled served SPKI): here the untagged form WAS the confusable one, so no fallback survived at all. The cert-binding fallback has since gone the same way — the untagged `sig` half and its verifier fallback were removed 2026-09-24 by the compat-remnant sweep, so the deployment key signs no untagged channel-binding bytes anywhere. The structural property — a signature from any actor-key context can never verify in another — is pinned by `bins/fauna-nest/src/routes.rs` `actor_sig_domain_tests` (login-shaped and tagged-login signatures never claim; claim and lockout never cross) plus the per-builder tag/cross-context tests in `fauna-protocol`. `version-compatibility.md` I2/I4 remain the law for future evolution of these ceremonies; the 2026-08-17 reset is a one-time pre-user event, not a precedent.

9. **No third-party code ever holds an identity key, and the sovereign class is never delegable (TP11, ratified 2026-09-05).** A third-party principal — remote, device or nest-hosted — reaches identity-bearing operations only through the oracle (§ Audience: deployment infrastructure → *The oracle*), with a keyless `identity.op` grant its user minted and can revoke — or, for a protocol with a standard grant of its own, through that protocol's consent row at that protocol's door, the oracle's properties enforced there (amended 2026-10-02 — § *The ATProto classes ride the protocol's own door*); the key stays with its first-party custodian. The nest terminates TLS for any path or SNI name a plugin serves, so no plugin holds a certificate key either ([`security.md`](security.md) § Co-resident process trust boundary). Rule #7's "identity is never delegated" now binds a third kind of participant.

## Don't do these

- **Don't use `BackupKey` for shared content.** It is owner-only; "share" via `BackupKey` would require distributing the identity seed.
- **Don't use `epoch_secret`-derived keys for owner-only content.** Inheriting MLS rotation for a one-reader case is overhead for no security benefit and forces a single-member MLS group existence per user per content kind.
- **Don't derive new keys from any root without a versioned, domain-separated context string.** Even if "obvious" (e.g., another BLAKE3-derive off the identity seed for a new purpose), a new context string is required so a future protocol revision can change one purpose without invalidating others.
- **Don't expose any key on the nest beyond the wrapped-blob floor shapes.** Adding a new key-bearing surface (a per-user secret the nest holds) is a downgrade of the sealed posture and requires explicit user approval + a Don't-do-these entry in `encryption-at-rest.md`.
- **Don't conflate the two fauna-sync paths.** `BackupKey` (owner-only content — backups, unbound single-user folders) and `chunk_crypto` (rooted in the M2 per-set content key an MLS group distributes; live for group-bound shared folders) are not interchangeable; documentation that lumps them together as "the fauna-sync per-user key" is incorrect even if both use ChaCha20-Poly1305. The two live paths share an AEAD primitive and a transport layer but differ in audience, derivation, and rotation.
- **Don't conflate `BackupKey` with the IMAP/CalDAV MSEK.** Both serve "owner only" audiences but they are separate, unrelated key material — `BackupKey` deterministically derives from the identity seed (no per-credential lifecycle), the MSEK is freshly generated random bytes wrapped under a credential-derived key (rotatable / revocable per credential). The MDA bridge can never derive `BackupKey` (it has no identity seed); the MUA path cannot use `BackupKey` (a third-party MUA cannot be trusted with the seed). The two paths exist precisely because the user reaches their data along two delivery surfaces with different trust models. Reusing one for the other's content kind defeats credential revocation in one direction and weakens the sealed posture in the other.
- **Don't put MLS group/epoch state, the index master key, or any non-mail/calendar opening key into the MSEK-sealed `MlsSnapshotBlob` (or anywhere else a MUA credential reaches).** The one ratified extension is the separate `WebdavKeysBlob` ([`owner-key-material.md`](owner-key-material.md) § Path B-sibling-3) carrying **only explicitly-WebDAV-served sets'** content keys — per-set, opt-in, revocable; anything broader broadens the IMAP/CalDAV blast radius onto conversations, group-restricted posts, and the user's whole search corpus — violating rule #7. If the MDA bridge needs to index mail/calendar, give it a *mail/calendar*-scoped index-segment key (MSEK-derived), not the cross-kind master key. The unified cross-kind index is a Fauna-app capability, not a bridge one.
- **Don't mint a capability scope whose wrapped key opens more than the scope names.** A `ScopeTuple` is *advisory metadata*; the `WrappedScopeKey` payload is the real capability. `AadBinding::for_capability` binds **who may unwrap the grant** — never **what the key inside may open**: once unwrapped, a recipient-mail secret opens *every* `kind: "mail-record"` envelope, and that envelope's AAD (`AadBinding::for_mail_record()` = `build_aad("mail-record", &[])`) carries **no owner, kind, or scope component** to discriminate on. So a scope is only as narrow as its *key material*. Before adding a scope kind, verify its payload opens **only** that kind: `content.read{post}` (→ the tier `period_key`) and `content.read{folder}` (→ the per-set M2 content key) satisfy this; a `content.read{spam-model}` wrapping the recipient-mail secret would **not** — it would silently convey mail + calendar + vCard read, i.e. be `content.read{mail}` under another name. When a content kind shares another kind's key, you have two honest options and must pick one *before* minting the scope: give the kind its own domain-separated derived key + `AadBinding` + envelope `kind` (rule #3), or convey the **artifact sealed to the holder** instead of conveying a key (the keyless-scope shape `content.label-write` already uses). Never ship the scope string alone and call it a boundary. *(The live instance is resolved: `content.read{spam-model}` took the second shape — keyless + artifact-sealed-to-holder, ratified 2026-07-13; `docs/goal/behavior/mail-spam.md` § Encrypted-mode interaction.)*
- **Don't add a new signer over attacker-chosen raw bytes with the deployment key (or any shared signing key) without a constant domain-separation tag.** The deployment key signs in multiple protocol contexts (rule #8); a new un-tagged signer over caller/peer-influenced bytes turns the shared key into a cross-context signing oracle. Add a new tag to `fauna_protocol::sig_domain` in the same change, prefix every signed message with it (rule #8), and confirm no existing share-key verifier accepts the new format.
- **Don't add an untagged bare-CID deployment-key signer.** The deployment key has no untagged signing context left: the KeyBlob (D/E), the one bare-CID context rule #8 once documented exempt (tagging it would have forked the 100-byte embed-as-bytes envelope across all 7 apps for zero forgery reduction), retired on 2026-09-27 when the nest stopped wrapping subscription period keys. A deployment-key signer over a bare CID via the universal `SignedEnvelope` wire would re-open the cross-context confusion the #8 audit excludes, so any new deployment-key signing context — even one signing over a CID — MUST carry its own applied `sig_domain` tag (exactly as the federation context C did, a fresh bespoke signer with no shared-wire barrier). There is no grandfathered exception; `KEYBLOB_V1` stays reserved and is never reused.
- **The client-minted `KeyBlob` is signed the way every record is, and rule #8 covers it by the record-wire argument, not by a tag (confirmed 2026-09-27, the sweep's follow-through).** Since the nest stopped wrapping period keys, every `KeyBlob` is signed by the author's device/actor key (`mint_key_blob`, `libs/fauna-core/src/subscription/crypto.rs`) via `SignedEnvelope::sign` over the bare CID — the universal embed-as-bytes record wire that same key uses for `Post`, `Profile`, `DeviceAuthorization`, `Tombstone` and every other signed record. So for an actor key a bare-CID signature is not one exempt context among tagged ones: it *is* the record wire, and its separation is structural by a different route than the deployment key's exclusion argument. The signed message is a fixed 36-byte CID over the record's own canonical dag-cbor bytes — the KeyBlob exemption's reason (1), no attacker-influenced tail, holds verbatim, and the author signs only records its own client built — and every verifier decodes the CID's preimage as its own record type (`decode_signed_bytes`), so a record legitimately signed as one kind lacks every other kind's required fields and verifies as nothing else. The actor key's *tagged* contexts (`AUTH_HANDSHAKE_V2`, `ACCOUNT_REGISTER_V1`, `CLAIM_ADMIN_V1`, `ACCOUNT_LOCKOUT_V1`, the invite pair, …) are exactly its signatures over bytes that are not a self-describing record — nonces, challenges, statements — which is rule #8's line for that key family: a new actor-key signature over anything but a record's own CID takes a tag; a new signed record kind takes none, and never a bespoke sidecar signature.
- **Don't mint a grant that wraps an identity key, and don't add a sovereign operation to the oracle's table** (rule #9). The oracle's table grows only with an operation class whose policy predicate the custodian can enforce before signing; `identity.op` stays keyless.
