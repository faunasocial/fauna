### Sessions

Active auth tokens. Users can list and revoke sessions across devices, or lock out all sessions in an emergency.

> **Migrated to WS-RPC; all four HTTP twins deleted** (re-verified 2026-07-07 — `lib.rs` records the session twins' deletion beside the auth-ceremony comments). `fauna.sessions.{list,revoke,revoke_all,lockout}` (Track B2, tracked internally) ride the per-actor bearer WS, gated `User | Admin`. `revoke_all` names the session to keep by **`keep_token_id`** in the request — the WS connection drops the raw bearer, so the client supplies the `token_id` it learned at mint (the `fauna.auth.{handshake,verify}` replies return `token_id`). The authed `sessions.lockout` carries no signature (the connection authenticates the actor). The no-token Ed25519 recovery channel — the one path that must work when no *authenticated* WS can be opened — is the pre-identity kind **`fauna.account.lockout`** (tracked internally): it rides the **anonymous** WS connection and authenticates from the signed payload (Ed25519 over the domain-tagged `account_lockout_signed_message`, blocks all auth for the hard-coded 24 h window (`devices.md` § Emergency lockout — the request carries no duration); `account_handlers::lockout_handler` over `account_core::lockout_core`), exactly as `fauna.account.register` does — the anonymous connection is the designed home for no-bearer signature-authed surfaces, so it is **not** residue.
>
> **Former routes → kinds (all deleted):** `GET /api/v1/account/sessions` → `fauna.sessions.list`; `POST …/sessions/revoke-all` → `fauna.sessions.revoke_all`; `DELETE …/sessions/{token_id}` → `fauna.sessions.revoke`; `POST /api/v1/account/lockout` → `fauna.account.lockout` (pre-identity).

### Inbox & Messaging

> **Client drain migrated to WS-RPC (tracked internally):** the durable per-actor store-and-forward delivery queue (contact-requests, knocks, group invites/messages, MLS Welcomes, security notices, cross-nest DMs) is drained over `fauna.inbox.fetch` + `fauna.inbox.ack` — kinds shipped (`libs/fauna-protocol/src/inbox.rs`, `inbox_handlers::register_inbox_handlers`), gated `User` (Admin inherits), caller-scoped by construction (no `actor_id` param).
>
> - **Fetch/ack semantics.** `fetch` is a pure peek of undelivered items; the client **explicitly `ack`s** the ids it has durably applied, which marks them delivered. This **fixes the latent data-loss bug** in the HTTP twin `GET /api/v1/inbox/{actor_id}` (`routes::get_inbox`), which marked items delivered the instant they were *read* — dropping them if the client crashed before applying. `PushEvent::InboxItem` is the best-effort prompt; the fetch+ack drain is the delivery guarantee. The `GET` twin was **deleted 2026-06-09** (the surviving carriers `poll_inbox` / `mark_delivered` are kept); `GET …/bare` (BARE-encoded fetch) was deleted earlier, no consumer.
> - **Ratified read-only-surface ack policy (2026-06-09):** a read-only *display* surface **peeks via `fauna.inbox.fetch` and never `ack`s** — acking on a surface that doesn't durably apply would re-introduce the mark-on-read data loss. Only the durable-apply drain (`fauna_client_inbox::drain`, below) calls `fauna.inbox.ack`.
> - **Skip cursor — an un-appliable item must not shadow the queue behind it (2026-08-06).** `fetch` takes an optional `after_id`; the reply is the undelivered rows whose delivery-link id is greater than it. **Skipping is not acking**: a stepped-over row keeps `status = 'undelivered'` and is returned again by the next cursor-less fetch, so nothing is dropped and nothing is consumed unrendered. It exists because a kind the client has no surface for (today `ContactRequest`; `SecurityNotice` was one until 2026-08-10, when it gained the notifications-row surface + honest ack — `notifications.md` § Security notices) or an `InboxKind::Unknown` from a newer nest is *permanently* un-ackable: without a cursor the drain stopped at such a head, and once those items filled one page (`INBOX_FETCH_DEFAULT_LIMIT`, 100) **the missed-push backstop below stopped delivering — silently, permanently, and on the one path that exists because push is best-effort.** `NewTokenIssued` fires on every new-IP sign-in, so the queue fills on its own. The cursor is additive and omitted when absent, and a client that sends it to a nest predating it detects the non-advancing page and stops rather than spinning (`version-compatibility.md`).
> - **Per-app adoption:** web's twin call-sites were dead code, removed; linux's vestigial `fetch_inbox` drain was removed (tray badge + quick-switcher derive from the shared `ConversationsManager` snapshot; linux's legacy `data.conversations` e2e field is null); android's widget badge peeks via the `FfiInboxClient` UniFFI seam (`inboxRpc().fetch`); apple watchOS peeks via `inboxClient().fetch(limit: 0)` (2026-06-12); windows carries an unused `DirectNestClient` fn, no live call-site. **No app calls the deleted `GET` twin.**
> - **Cross-nest delivery (the former POST):** `POST /api/v1/inbox/{actor_id}` — a Fauna-native signed `(ContactRequest, Post)` tuple (Ed25519 sign-over-CID, **NOT** ActivityPub) — migrated to two WS-RPC legs: client→home-nest **`fauna.inbox.send`** (sender-bound, local-deliver-or-originate) → nest→nest **`fauna.federation.inbox.deliver`** (both landed 2026-06-06; twin **deleted 2026-06-09** — linux/apple/windows ✅, android off-gate, web dead-code-removed; `federation.md` § Federation residue surface).
> - The legacy `GET /api/v1/ws/{actor_id}` "notifications WebSocket" **is** the unified WS-RPC connection itself — there is no separate notifications channel.

| Method | Path / Kind | Purpose |
|--------|------|---------|
| WS-RPC | `fauna.inbox.send` | Client→home-nest social inbox delivery: sender-bound (`cr.sender == caller`), local-deliver or originate the federation leg (`fauna.federation.inbox.deliver`). Former `POST /api/v1/inbox/{actor_id}` deleted 2026-06-09. |
| WS-RPC | `fauna.inbox.fetch` | Peek the caller's undelivered inbox items (no status change), optionally from the `after_id` skip cursor. Former `GET /api/v1/inbox/{actor_id}` deleted 2026-06-09. |
| WS-RPC | `fauna.inbox.ack` | Mark applied items delivered (caller-scoped, idempotent) |
| GET | `/api/v1/ws/{actor_id}` | The per-actor WS-RPC connection itself (transport-connection.md § Connection lifecycle) — every authenticated request/reply and push rides it; not a separate notifications channel |

### Rooms

The room plane (`fauna.conversations.room.*`) — the one membership model every conversation shares, whatever its transport. Owner: [`../behavior/conversation-rooms.md`](../behavior/conversation-rooms.md).

| Kind | Class | Offline | Purpose |
|---|---|---|---|
| `fauna.conversations.room.create` | User | OnlineOnly | Found a community room — the **birth ceremony** ([`../behavior/conversation-rooms.md`](../behavior/conversation-rooms.md) § The room). The request carries a 32-byte salt and the creator's own signed initial policy, and neither an id nor a class: `room_id` is derived from that birth record, so it commits to whose key founded the room, and the class is derived from the member set the ceremony seats — the creator as the one `owner` and this nest as a `member` of kind `nest`, which is what makes the class `community`. A room founded here is **floor-authoritative**, so the mirror door below is refused on it. |
| `fauna.conversations.room.roster_report` | User | OnlineOnly | Report a room's membership to its home nest — the **floor roster** ([`../behavior/conversation-rooms.md`](../behavior/conversation-rooms.md) § The floor roster). For an end-to-end room the roster is a member-reported mirror: the MLS group is the authority and the nest cannot see inside it, so the committing device reports the roster each membership commit produced. The nest replaces the room's roster wholesale and reads it for routing fan-out, the custody serve door, the relay gate and succession targets — never for confidentiality. Reports are ordered by the log position of the commit each follows (additive `commit_seq`; a late one is acked `superseded_by` and not applied — § The floor roster owns the rule). Refused on a room the ceremony above founded: a room has exactly one membership authority. |
| `fauna.conversations.room.list_roster` | User | Read | Read a room's live floor roster and its derived class. Admitted only to a live member of the room named — a room id is unguessable, but one leaked id must not turn into the room's membership list. |
| `fauna.conversations.room.invite` | User | OnlineOnly | Invite a principal into a room — the inviter's signed act ([`../behavior/conversation-rooms.md`](../behavior/conversation-rooms.md) § Join rules and invites). **It does not seat the member**: the nest records the invitation and the invitee's own `accept_invite` writes the roster row, so a room's floor never names someone who has not agreed to be there — the one place the room plane deliberately diverges from the dormant group plane. Who may invite is the room's join rule; the invitee's reach policy gates it exactly as it gates a group Welcome. |
| `fauna.conversations.room.accept_invite` | User | OnlineOnly | Accept your own pending invitation — the act that seats the member. One-shot: an accept arriving after the room removed the invitee is refused rather than re-seating them. |
| `fauna.conversations.room.remove` | User | OnlineOnly | Remove a member. Owner and admins remove anyone whose role is not `owner`; **the owner's membership is not removable until ownership is transferred**, since an owner-less roster would strand invite and remove forever. Removing the home nest is the read-grant revoke ceremony and is refused here. |
| `fauna.conversations.room.leave` | User | OnlineOnly | Leave a room — remove yourself. Its own door rather than a self-addressed remove, because the authorization differs in kind: removing someone else is a rank the roles table grants, leaving is a right every member but the owner has. |
| `fauna.conversations.room.set_policy` | User | OnlineOnly | Replace a room's signed policy — name, join rule, history policy, admin set ([`../behavior/conversation-rooms.md`](../behavior/conversation-rooms.md) § Roles and authorization). The nest **stores it and cannot author it**: an admin-set change needs the *owner's* signature, the rest takes an owner's or an admin's, and the version is a strict ratchet at exactly `stored + 1`. Storing a policy reconciles the floor roster's roles to it — the signed policy is the authority members render and `room_members.role` is the projection every nest-side gate reads. Ownership is not settable here. |
| `fauna.conversations.room.set_labelers` | User | OnlineOnly | Name the transparent labelers a **community** room's home nest applies to the room's messages — a signed record beside the policy, not a field of it ([`../behavior/community-rooms.md`](../behavior/community-rooms.md) § The three classes → *What the home nest does with its read*). Owner or admin signs; strict ratchet from version 1; every id must be a `wasm` or `text-model` artifact this nest's labeler registry publishes; an empty set stops the labelling. Refused on a room whose authority is its MLS group. Read back on `room.list_roster`. |
| `fauna.conversations.room.transfer_ownership` | User | OnlineOnly | Hand a room to another live **user** member — the owner's own act, signed by the outgoing owner, whose role in the previous version is what lets it change the owner field. Moves the roster row with the bytes: the incoming owner becomes `owner`, the outgoing one takes the rank the new policy gives them. Transferring to an owner homed on another nest needs the re-homing ceremony and is refused until it exists. |

> **Minted 2026-09-09**, additively beside the group kinds (since retired, § Groups above; [`version-compatibility.md`](version-compatibility.md): the wire only ever grows within a major). The two membership doors are **exclusive by provenance**: `create` founds a room whose floor the nest's own ceremonies write, `roster_report` mirrors a room whose authority is an MLS group the nest cannot read, and each refuses a room born through the other. The membership half — invite/accept, remove, leave — lands with them (2026-09-09), so a community room can be founded, seated and unseated on one nest. The governance half — `set_policy`, `transfer_ownership` — lands with them. Still unbuilt: the community class's sealed send/read, and **cross-nest invite delivery** (the inbox plane's payload is the group plane's `(ContactRequest, Post)` pair, and the room plane needs its own payload kind rather than a dependency on the plane being retired).

### Blobs & Media

> **Stays HTTP** — blob bytes are CID-addressed octet-stream per the residue list. The canonical surface is `GET|PUT /api/v1/blob/{cid_b32}` (base32-lower CIDv1 in URL path, server-side `blake3(body) == cid.digest()` verification; landed in CBOR-DAG-everywhere Layer 3); a hex-keyed shape (`POST /api/v1/blob` + `GET /api/v1/blob/{hex}`) serves blob bytes too and is equally permanent (ruled 2026-10-01, `api-layers.md` § Remaining HTTP). Both URL shapes share one `BlobStoreBackend` (same on-disk bytes; sniffed by path-parameter shape — multibase `b…` routes through the CID branch, hex through the hex branch). HLS manifests are protocol-required `application/vnd.apple.mpegurl`. The metadata side (upload-receipt, transcode status) migrates to WS-RPC kinds (`blob.upload.notify`, `video.transcode.status`); the bytes themselves never become a WS-RPC payload (>1 MiB per `transport.md` § Wire format).
>
> **The hex shape is not vestigial — it is the sole upload path every current client and feature actually uses.** General post/profile media and thumbnail uploads build a `multipart/form-data` (`sidecar` + `bytes` parts) body against `POST /api/v1/blob` on every app (`bins/fauna-nest/src/blob_routes.rs::upload_blob` rejects any other Content-Type with 400): native Rust (`libs/fauna-client/src/media_upload.rs:63,70,126`), sync-engine thumbnail backfill (`libs/fauna-sync-engine/src/nest_client.rs::upload_blob_multipart:324-358`; the file's raw-body `upload_blob` at line 299 has no caller), windows `DirectNestClient` (`apps/fauna-windows/FaunaApp/FaunaApp.Core/Services/DirectNestClient.cs:503,512,527`), apple's shared `buildBlobMultipart` (`apps/fauna-apple/FaunaKit/Sources/FaunaKit/Core/BlobUpload.swift:46-66`, its doc comment naming the same shape on windows/android/linux), and web's own `FormData`-based `uploadBlobMultipart` (`apps/fauna-web/src/lib/api.ts:219-248`). The **FaunaMls conversation-attachment path** rides the same legacy `POST`/`GET`-by-hex pair, never the canonical base32 `cid_b32` PUT/GET — native `NestConversationsRpc::blob_put`/`blob_get` (`libs/fauna-client-conversations/src/lib.rs:938-1013`) now builds proper multipart too (fixed 2026-07-20), but the wasm arm `WsConversationsRpc::blob_put` (same file:2373-2409) still POSTs a **raw, non-multipart** body — a distinct, still-open gap the nest's strict Content-Type check would reject (current adoption status owned by `docs/goal/behavior/conversation-attachments.md` § Attachments). Either way, no FaunaMls arm touches the canonical PUT. The reason the legacy shape persists is structural, not historical inertia: the canonical PUT takes a raw `application/octet-stream` body keyed by a pre-known CID in the URL and carries no multipart/sidecar slot, while every caller above needs to carry an `UploadSidecar` (mime / media-processing / attachment classification) alongside the bytes. Conversely, `GET|PUT /api/v1/blob/{cid_b32}` has **no current production caller anywhere in the codebase** — only `bins/fauna-nest/tests/blob_routes.rs` exercises the CID branch directly. "Canonical" names the CBOR-DAG-everywhere target shape this doc ratifies, not today's call-site share.

The `fauna.wireguard.peer.{register,unregister}` kinds are **deleted**, with the
whole WireGuard stack (user-directed; owner
[`../behavior/p2p.md`](../behavior/p2p.md) — iroh-QUIC is the only substrate).
Their HTTP twins had already gone in the WS-RPC-everywhere rip-out, and the
admin family `fauna.admin.wireguard.{status,peers,keygen}` (§ Admin, Track C5)
went in the same change. Nothing replaces them: under iroh a `NodeId` **is** the
Ed25519 actor key, so there is no key to register and no per-nest peer registry
to consult. The removal is recorded as an applied instance in
[`version-compatibility.md`](version-compatibility.md) § Dimension 2, under the
user's population ruling.

**One rule outlives the door it was found on — port validation.** `register`
took a bare `as u16` on `listen_port`, which *wraps* rather than refuses: `-1`
read as 65535, `65536` and 2³² as the unbindable `0`, `70000` as 4464 — so a
peer's stored endpoint named a port nobody listens on while the sender saw a
successful register. The 2026-08-18 fix refused anything outside `1..=65535`,
and did the check **before** the feature branch so a runtime-less nest answered
alike (the `fauna.admin.gc` validate-before-the-service-lookup ordering, § Track
C / C3). **That rule is general and still binding on every kind that carries a
port** — it is owned by
[`../behavior/value-formatting.md`](../behavior/value-formatting.md) § Port
validation, not by this deleted door. Same for the ordering: validate before the
service lookup, so an unavailable subsystem and a bad request stay
distinguishable.

### Share

> **Stays HTTP** — `/share/{token}` exists to be opened by a browser belonging to a non-Fauna recipient; the public landing pages don't migrate. The Fauna-app side of share-link *creation* is the WS-RPC control plane `fauna.share.{create,list,revoke}` (shipped — see below).
>
> **Share-link control plane (`fauna.share.{create,list,revoke}`) — mechanics.** ShareToken is **client-minted, stateless and self-verifying**: the client signs a self-contained token (`fauna_core::share::ShareToken`), base64url-encodes it into a `/share/{token}` URL, and the nest verifies it offline at GET time (`bins/fauna-nest/src/share_routes.rs`). The nest **never** mints tokens (it never holds a user's signing key) — so `fauna.share.create` does **not** create the token; the client mints it and `fauna.share.create` **registers** its metadata server-side (a `share_tokens` row: token-id = `blake3` of the signed bytes, author, manifest_hash, `filename_sealed` — the author's sealed copy of the name, the only form the nest holds since 2026-10-01 (owner [`../behavior/share-links.md`](../behavior/share-links.md) § The filename rests sealed) —, expires_at, public, revoked, created_at). `fauna.share.list` returns the calling actor's registered tokens; `fauna.share.revoke` sets `revoked`; `GET /share/{token}` gains a revocation-list check (revoked → `410 Gone`). This is the only design consistent with both the non-Fauna-recipient browser GET (self-contained token) and the product invariant that share affordances are **user-revocable from their app** (encrypted-mode redesign § "User always controls their data"). Registration is **not** a serving gate for a **live** author — an unregistered token still serves statelessly (backward-compatible links); only an explicit revoke produces `410`. One succession-scoped exception: a token authored by an identity a ceremony has retired serves only through its registry row, so an unregistered one refuses `410` — ruling + reasoning owned by `succession-aftermath.md` § Re-key scope (the share-registry blockquote's serve-side paragraph, 2026-08-15). One mint-side **type gate** (INFO-2, FS-BIND family): `fauna.share.create` refuses (`fauna.share.unsupported_encrypted_set`) when the token's manifest is present in the blob store and positively parses as content-key-sealed (`ChunkManifest.stored_hashes.is_some()`) — the public GET can only emit ciphertext for an end-to-end-encrypted set and already refuses it 403 at serve time (`share_routes.rs`), so registering would hand the sharer a dead link; the gate is best-effort by design (an absent manifest — mint-before-upload — or an undecodable blob registers as before; the serve-side 403 stays the authoritative gate). Caller class is `User | Admin`; the three kinds are float-free (hashes ride as hex `String`). **A sealed file becomes linkable only through the fragment-keyed link** (ratified 2026-09-25; owner [`../behavior/share-links.md`](../behavior/share-links.md) § The private-file extension): an additive `key_in_fragment` token field, an additive `key_envelope` on `fauna.share.create` and the `share_tokens` row, and a separate ciphertext-only arm of `GET /share/{token}` — the 403 above is untouched by it, and both refusals gain the mirror exemption that section states. The nest half is built (2026-09-27: the token field, the envelope on the wire and in the registry, the mint-side mirror exemption, and the arm — the navigation `GET /share/{token}` answering `/app/`'s service, `GET /share/{token}/manifest` and `GET /share/{token}/chunk/{index}`, the latter two under the open credential-less CORS of the public byte routes); the author seam and the viewer page are not — status in that doc's § Implementation status today.
>
> **The `public` flag — restricted shares are BORN GATED (ruled 2026-08-16).** `ShareToken.public` is the only thing the flag decides today: **`true` is servable, `false` is refused** — `403` at `GET /share/{token}`, and `fauna.share.create` refuses to register one at all (`fauna.share.restricted_shares_unimplemented`), so the refusal lands at share time rather than as a dead link (the same reasoning as the E2EE type gate above). `/share/{token}` therefore *is* one unauthenticated surface, exactly as the route table and § Caller classes say: every token it serves is public. **What the flag is not, and never was, is access control.** The `Authorization: FaunaIdentity <actor>:<sig>` header that once stood in front of a `public: false` token was never one: the token type carries no audience field for a presented actor to be compared against. That scheme is **deleted** (2026-08-16); `FaunaIdentity` is not an authorization scheme on this route or any other. Live exposure was nil throughout — at the ruling nothing minted a `ShareToken` outside tests, and the first app caller (2026-09-28) mints `public: true` only — which is why the flag was left refusable rather than removed from the wire: it is the door to gate when the feature is built. **Building restricted shares means** a real audience on `ShareToken` (additive-everywhere, with a compat story for tokens minted without it) **plus the app UI that sets it** — "who may open this link" is a user choice, so by `principles.md` § One configuration surface it is app UI + nest state, never a bare wire flag; the serve-side arm then becomes that audience check. Pins: `share_routes::tests::{a_non_public_token_is_refused_not_served, a_public_token_gets_past_the_flag_gate}` (the pair isolates the flag from every other gate) and `conformance_share::a_non_public_token_is_refused_at_mint`.
>
> **Implementation status today: shipped** (tracked internally, hub Track E1). A **net-new feature** (not an HTTP→WS-RPC migration). Wire types `libs/fauna-protocol/src/share.rs`; kinds `kind.rs::register_share_kinds` + dispatched via `share_handlers::register_share_handlers` (`bins/fauna-nest/src/share_handlers.rs`); persistence `share_tokens` (`bins/fauna-nest/src/db/migrations.rs::MIGRATIONS_SHARE_TOKENS` + `db/share_tokens.rs`); gate in `bridge_method_allowlist.rs`. **Flow:** client mints a `ShareToken` and calls `fauna.share.create{token, filename_sealed}` → `create_handler` verifies it, requires `token.author == conn actor`, refuses a registration without its sealed name, derives `token_id = fauna_core::share::token_id_from_base64url` and inserts via `register_share_token` (the name rests as `filename_sealed` alone — the table has no plaintext column since schema 103) → `fauna.share.list` reads `list_share_tokens_for_author` → `fauna.share.revoke{token_id}` sets `revoked` via `revoke_share_token` → `GET /share/{token}` (`share_routes::handle_share`) recomputes the same `token_id`, reads the registry verdict via `share_token_registration` (`None` / `Some(revoked)`), returns `410 Gone` when revoked, and — unregistered tokens only — refuses `410` when the author has been succeeded (the serve-side succession gate above). Tier_3 coverage `bins/fauna-nest/tests/conformance_share.rs`. **Per-app share-creation UI (S-adopt) is adopted on tui (2026-09-28)** through the shared author seam `libs/fauna-client-share` and the Media machine; the other six apps follow in the batched trickle-down — its design (which files can carry a link, the create / list / revoke surfaces, the author seam) is owned by [`../behavior/share-links.md`](../behavior/share-links.md).

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/share/{token}` | View a shared post or file via a time-limited token link (public, no auth — and *only* public: a `public: false` token is refused `403`, see *The `public` flag* below). A token revoked via `fauna.share.revoke` returns `410 Gone` (`share_routes::handle_share`). |

### Push Notifications

Push subscription management for Web Push, APNs and (ruled 2026-09-26) the `ws-device` transport. Push is sent on inbox delivery, knocks, and MLS Welcome (group invites); skipped per device when that device's own connection is live (`../architecture/apps/common.md` § Push Notifications → *Dispatch Logic* — the actor-wide skip survives only for a connection that announced no device).

> **Migrated to WS-RPC (tracked internally, § B22); HTTP twins deleted.** `fauna.push.{vapid_key,subscribe,unsubscribe}` — the push-subscription-management surface (`libs/fauna-protocol/src/push.rs`, `push_handlers::register_push_handlers`) — is the **sole surface**: the HTTP twins (`GET /api/v1/push/vapid-key`, `POST /api/v1/push/subscribe`, `DELETE /api/v1/push/subscribe/{device_id}`) were **deleted** in the WS-RPC-everywhere rip-out (`lib.rs` "push_routes deleted — `fauna.push.*` is the sole surface"; re-verified 2026-07-07). All fields are `String`/`Option<String>`/`bool` (no floats); write replies are `{ ok: true }`. The actual *push delivery* to Web Push / APNs endpoints is server-to-third-party HTTP and stays as is. Gate `User | Admin` — `subscribe`/`unsubscribe` are actor-scoped device management, and `vapid_key` (no-auth on HTTP) rides the **authenticated** connection: push subscription is inherently post-login, so there is no pre-identity caller. No-push-service → `fauna.push.unavailable`; empty `device_id`/`endpoint` or unknown `transport` → `fauna.push.invalid_request`. **Adoption:** web via the wasm `WsRpcClient` façade over the shared `fauna-client-push::PushClient<R>` (`libs/fauna-wasm/src/rpc.rs` → `apps/fauna-web/src/lib/{rpc,push}.ts`; the browser `serviceWorker`/`PushManager.subscribe` work stays client-side); apple via the `FfiPushClient` UniFFI seam (`libs/fauna-ffi/src/push_client.rs`, vended as `FfiNestClient::push()`; OS-side APNs token + keychain material stays in `PushManager`). tui (2026-10-01, linked directly) and windows (2026-10-08, through `FfiPushRegistration`) subscribe `ws-device` rows through the same crate's shared registration machine (`fauna_client_push::registration`); linux/android have **no push call-site today** — when they surface push they adopt the same `fauna-client-push` crate/seam, no nest work.

`fauna.push.subscribe`'s `transport` field is `"web-push"` (default if omitted) or `"apns"`. For `web-push`, `endpoint` is the browser push URL and `key_p256dh`/`key_auth` are required. For `apns`, `endpoint` is the APNs device token (hex) and `key_p256dh`/`key_auth` are the device's push-specific P-256 public key and auth secret for payload encryption. **Ruled 2026-09-26, built nest-side:** `"ws-device"`, whose `endpoint` is the row's own `device_id` and whose keys are absent; and the kind **`fauna.push.presence`** `{ device_id }` → `{ ok }` (`User | Admin`, `OnlineOnly`) — every connection announces the device it serves, the per-device dispatch's oracle; an optional `stand_in` on the request is ruled 2026-10-03 and not built (owner § Dispatch Logic) — plus the push event **`fauna.push.notification`** `{ title, body, url }`, a `ws-device` row's delivery frame. No app announces or registers `ws-device` yet (the client half rides `fauna-client-push`). Owner `../architecture/apps/common.md` § Push Notifications → *Registration*.
