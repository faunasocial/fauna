## The conventions

Tests live at `tests/e2e-unified/`: one `PlatformDriver` per app, action classes in `actions/`, platform-agnostic pytest in `tests/`, shared fixtures in `conftest.py`. The conventions, numbered for citation:

1. **Every UI element gets an ID from `ui.yaml`.** Add to `ui.yaml` (the page's `elements` + the registry), then implement per platform: web `data-testid`, windows `AutomationProperties.AutomationId`, android `Modifier.testTag`, iOS/macOS `accessibilityIdentifier`, linux `set_widget_name`. Naming `{feature}-{purpose}` kebab-case; tabs `{page}-tab`; list items `indexed: true`. Same IDs everywhere; never invent app-specific IDs. Reference components rather than flattening child IDs, use scoped queries (`scope="post-card[2]"`) rather than global counts, and never add invisible shim elements — if a platform's real UI doesn't match `ui.yaml`, propose a `ui.yaml` change instead. **Scope resolution is DESCENDANT matching (ruled 2026-08-14).** Each step of a `scope` names a container found *anywhere below* the previous step's subtree — below the app root for the first step — and the queried id is then found anywhere below the last step; a step's `[n]` indexes those instances in **document order below the previous step**. So a scope names only the containers it cares about and leaves the ones between them implicit: `post-card[1]/quoted-post` and the bare `quoted-post` are both legal, the second being the same query with the outer container left unnamed. The rejected alternative — a *full ancestor chain from the root* — loses on three counts: it is what the DOM/AT-SPI/UIA engines physically do not do (Playwright's `locator`, GTK's recursive `collect_in`, UIA's `FindAllDescendants` are all descendant searches, and the first two cannot even name a "chain from the root" for the untagged wrappers a real widget tree is mostly made of); it makes this convention's own `post-card[2]` example wrong; and under it adding a test ID to any wrapper **silently** breaks every scoped query beneath it. An app whose registry is flat rather than a real widget tree must therefore *emulate* the walk — resolve each step against the container instances below the previous one — and not compare recorded ancestor paths from the root; the reference implementation is tui's `Registry::scope_root` (`apps/fauna-tui/src/automation.rs`). Descendant matching is strictly more permissive than root-anchored matching, so an app moving to it keeps every scoped query it already answered.
2. **Every page has an `error-message` element** — tests read it via `app.error_text()`/`has_error()`; auth failures surface as exceptions.

   **Rider — the element must be ABSENT when there is no error, and the state read must see the real one (ratified 2026-08-04).** The convention's value is carried almost entirely by the *negative* assertion every such test opens with (`assert not is_visible("error-message")`); if the id resolves to something permanently present, that line can never fail — and it can never meaningfully pass either. Windows shipped for months with **three** surfaces wearing `error-message` simultaneously — a global 1×1 TextBox, 24 per-page 1×1 mirror TextBlocks (whose "cleared" value was a literal `" "`), and the page's own InfoBar — the first two unconditionally on-screen. Since a driver resolves an id widely and asks only "is it on screen", `is_visible("error-message")` was **structurally true on a clean page**, so `test_conversations_compose_error.py` failed at line one on windows the first time it was ever actually run, and the entire assertion class had been untestable there meanwhile. Two obligations follow, and they are separate: **(a)** a shim carrying a shared id leaves the accessibility tree when it has nothing to say (linux gets this structurally — `automation/find.rs::is_showing` prunes non-showing widgets; tui/web build the surface hidden; windows collapses it via `MessageShim.ShouldShow`, with whitespace counting as absent); **(b)** whatever `error_text()`/`has_error()` actually resolve to must be fed by the *real* error, not only a test-injected one — where an app answers those from its state protocol, a page that surfaces an error without publishing into that channel is indistinguishable from a page that swallowed it (windows' `App.CurrentErrorMessage`; linux's `messages.error` falls back to reading the mapped widget for the same reason). **Three shapes satisfy (b), and an app must implement one of them deliberately (surveyed across all 7 apps 2026-08-11):** *(i) the read path falls back by itself* — linux's `messages.error` producer resolves the mapped `error-message` widget when the app-level banner is silent, so no page owes any discipline; *(ii) the key goes absent when the funnel is silent* — web (`bannerMounted && bannerHasMessage`) and android (`TestAgent.messagesJson` returns `null`), which hands the shared helper back its element fallback for every page, present and future; *(iii) one funnel plus a guard test* — tui's `App::error_line_text` as the single producer, pinned by `no_page_pushes_an_error_message_element_of_its_own`, and windows' every-page publish into `App.CurrentErrorMessage`. Shapes (i) and (ii) are the robust ones because they cannot be regressed by a *new* page; (iii) is only as good as its guard, and windows has no equivalent of tui's. ⚠ **A present-but-all-null `messages` object is none of the three** — it is the defect: android shipped one until 2026-08-11, and every page-scoped ViewModel error (`AdminDnsVM.error`, `AdminNestVM.error`, `MutedWordsVM.errorMessage`) read back as `""` the whole time. The generalization worth carrying past this instance: **an assertion that cannot fail is not coverage**, and a suite of positive-only assertions will not tell you which of the two you have — both windows tests here asserted only positives after their first line, which is exactly why the collision survived.
3. **Navigation is unified per form factor** — desktop sidebar/tab-bar, mobile bottom-tab/drawer, tui's own sidebar idiom, all sharing `{page}-tab` IDs (canonical per-app model, owned by [`../ui/README.md`](../ui/README.md) § Navigation model — not restated here). Branch on `driver.is_mobile()`/`is_web()` — never on the driver's type name. A platform branch over ~3 lines means the IDs aren't unified enough.
4. **Login/onboarding:** Ed25519 key-based auth, no passwords; two phases (identity then nest); all IDs in `ui.yaml`'s `onboarding` section; per-app exceptions in [`../behavior/login.md`](../behavior/login.md).
5. **API-helper tests** (`tests/e2e-unified/tests/test_api_helpers.py`) hit the nest API directly and verify response contracts — no UI, no driver. Add one whenever a failure could be UI-side *or* API-side.
6. **Don't debug with screenshots — failures diagnose themselves.** **Moved to [`e2e-self-diagnosing-failures.md`](e2e-self-diagnosing-failures.md) § The convention — convention 6** (2026-09-28 split), together with its four riders and its whole build-out record. The convention keeps this number: *convention 6* / *point 6* stays the citation key and resolves there.
7. **Don't skip tests for platform differences — and a skip is not coverage.** Platform checks live in the action layer, never test files; the only *permanent* valid skip is structural impossibility (the `--client`/`--app` filter usually handles that). The action layer being the sanctioned *home* for a platform check does not make an action-layer skip sanctioned: a skip meaning *"this app hasn't built the surface yet"* hides in exactly the way a test-file skip does. Both report the same `s` inside a summary line — `1 failed, 4 passed, 5 skipped` — that a hurried reader counts as fine, so nobody can tell *"tui runs this"* from *"tui skips this quietly"*. Therefore **every skip that depends on which app is under test must declare which of three things it is**, through `tests/e2e-unified/helpers/app_surface.py` (ratified 2026-07-29):
   - **`skip_unbuilt(driver, surface=…)`** — this app has not built the surface: **temporary parity debt**. Skips normally, **fails under `--strict-app`**, and is tallied and printed at the end of *every* run (flag or not), so the count is a visible down-only ratchet rather than a number someone has to go looking for.
   - **`declared_absence(driver, capability=…, doc=…)`** — a **permanent** platform absence declared in a goal doc ([`apps/tui.md`](apps/tui.md) § Declared platform absences; web's absences likewise). Always skips, `--strict-app` included — there is nothing to build, and a flag that fires on legitimate absences is one nobody leaves on. The `doc` citation is **required**: an absence with no declaration is unbuilt debt wearing a better name.
   - **`skip_environment(reason)`** — not an app property at all (no network, a domain that turns out to be registered, a missing live credential). Always skips; no amount of app work would make it run on this box.

   **One layer up, the same trap catches an automated *gate*, and `--fail-on-skip` is the answer there (ratified 2026-08-13).** A release pipeline reads an exit code, not a summary line — and `pytest -m <gate-suite>` exits **0** when every one of its tests skipped, so a gate can promote an artifact on the strength of an `N skipped` summary line. The three helpers above cannot close this: a gate does not care *why* its suite failed to run (a missing live credential is `skip_environment`, entirely legitimate in an inner-loop run and fatal in a gate run), only *that* it did. So a gate invocation adds **`--fail-on-skip`**, which reds the run and names every skipped test with its reason. It is deliberately broader than `--strict-app`/`--strict-nest` — those each red only their own helper's skips — and is **for pipeline invocations only**, never the inner loop, where legitimate skips are constant. First consumer: the promote-after-verify pipeline's CD gate over `-m cd_suite` ([build-system.md](build-system.md) § Image tags & channels).
   **Rider — a scope declaration that must pre-empt a FIXTURE belongs on the MARKER, not in the body (ratified 2026-09-22).** The action layer is this convention's home for a platform check, and an in-body `skip_unbuilt()` reads as equivalent to an app marker — until some fixture in the test's closure becomes a real PRECONDITION that raises on the same apps the guard would have declared. Then the guard never speaks: pytest runs every fixture before the body, so the test ERRORs where it meant to declare, and this convention's whole accounting (a declared skip, tallied and ratcheted) is replaced by a red nobody asked for. Measured: `real_faunamls_app` became a real precondition on the launch-gate-silent apps (it witnesses the real FaunaMls rail in the app's own log — `helpers/real_rail_control.py`), and the three two-real-engine moderation tests, whose `require_second_real_engine_fixture_supported()` guard sits in the test body, would have errored on macOS/iOS instead of declaring their linux+tui scope. The same mechanism had already been true of them on windows for as long as that branch has polled `data.conv_real_backend_active` — an in-body guard is simply not reachable behind a fixture that refuses first. `pytest_collection_modifyitems` already prefers the marker for the adjacent, weaker reason (an in-body skip under the wrong client *“inflat[es] the skip count and hides genuinely-missing coverage”*); this is the strong form of the same preference. Keep the action-layer guard as the runtime backstop and as the single place the supported set is DESCRIBED — the marker is its collection-time shadow, so widening one means widening both, and the guard's docstring is where that duty is written down.


   This is the mechanical form of a standing user directive: *"no skips" means no **hidden** skips — genuinely-missing functionality is visibly tracked, not fake-green and not buried in the skip count* (2026-05-30, during the linux/nest e2e mandate; that pass fixed **mode 1** by making conftest *deselect* platform-marked tests rather than count them as skips, and the three helpers here close modes 2–4 the same way). That three-way split is the whole mechanism: `--strict-app` is trustworthy only if it fires on exactly the skips an app could close by *building something*. Enforcement is the cheap-merge-tier `scripts/check_app_gate_ratchet.py` (parse-only, ~1 s, path-scoped) — a per-file **down-only ratchet** on app-gated skips *not* routed through those helpers, mirroring `check_sleep_ratchet.py`'s gate + committed-baseline shape. Pre-existing debt is grandfathered per file; a brand-new file starts at zero.

   **Why the count is mechanical and not a markdown table.** The 2026-07-29 measuring pass recorded *"there are exactly three of these gates today, all in `actions/admin.py`"* — and it was wrong at the moment it was written: `actions/backups.py` and three sites in `actions/onboarding.py` were already there, and an AST scan keyed on the *class* rather than on three known names found **97 across 66 files**. The enumeration was keyed on the gates someone already knew about, so it could only rediscover them. Any form of this count maintained by hand decays the same way, which is why it lives in a scan and a baseline file.

   **The same class hides in a per-app capability table.** A table that answers "not implemented" for an app it has never *heard* of produces identical silent skips: `client_capabilities.py` resolved a driver to an app by matching substrings of its class name, no substring of `TuiDriver` matched any arm, so tui fell through to `"unknown"`, every state-section lookup answered False, and the "declares a capability but returned null" assertion was unreachable for tui — while both honesty suites, which carry no app marker, collected for it and appeared to pass (found + fixed 2026-07-29; `app_surface.app_name()` is now the single resolver, asking the driver's own `is_*()` predicates).

   **Mode 5 — a fixture that skips on a driver-CAPABILITY predicate, not an app-IDENTITY predicate (found 2026-07-29 during admin-shell work, closed 2026-07-30 during e2e-parity work).** `killable_app` (`tests/e2e-unified/tests/test_crash_recovery_journeys.py`) skipped on `driver.supports_unclean_kill()` — a `PlatformDriver` method whose base body is a trivial `return False`, exactly like an `is_X()` identity predicate in *shape*, but answering a capability rather than an identity. The guard names no app and no `is_X` call, so the static scan (above) could not see it by construction: the tell is not the skip site but a **base-class default that silently answers for every subclass that forgot to override**. It hid all 11 crash-recovery journeys on tui for as long as the driver existed — `HttpBridgeDriver`'s inherited `supports_unclean_kill` tested `self._app_proc`, a Popen tui has never had (it owns its app child as a pty session leader instead) — reading as a *structural* impossibility when it was ordinary unbuilt debt (fixed; the fixture now routes through `skip_unbuilt`). Two pieces close this mode, both in `scripts/check_app_gate_ratchet.py`, sharing one source of truth (`capability_predicate_names()` — every `PlatformDriver` method whose body is a trivial `return <constant>`, excluding the `is_<app>` identity family and bare `-> None` action hooks): **(1)** the static scan's gate-predicate set is now `APP_PREDICATES` union that capability set, so a bare skip under `if not driver.supports_unclean_kill():` is caught exactly like `if driver.is_tui():`; **(2)** `--capability-debt` is a separate, purely informational report (not a gate — an inherited answer is not automatically a bug, e.g. linux correctly inherits `supports_unclean_kill` from `HttpBridgeDriver`) listing, per capability predicate, which class in each of the 7 leaf drivers' MRO chain actually answers it — a coverage-debt inventory no skip-site scan can produce, run via `just app-gate-capability-debt`.
   **Mode 6 — the same class one tier down, in a Rust `#[test]`, when the UI toolkit is single-threaded (found + closed 2026-08-02).** Everything above is written for the pytest suite, but nothing about the failure is Python-specific: a test that decides at runtime not to run its body, and returns normally, reports success. `apps/fauna-linux` had exactly that. GTK4 binds to the thread that called `gtk::init()`, and **libtest gives every `#[test]` its own thread — it spawns one per test even under `--test-threads=1`, for panic isolation** — so a shared `gtk_test_init_or_skip() -> bool` helper returned `false` on every thread but the first, and all 65 widget tests opened with `if !gtk_test_init_or_skip() { return; }`. Measured on the primary dev VM, `cargo test -p fauna-linux --bins`: **64 of the 65 skipped in a run that printed `250 passed; 0 failed`.** About five widget assertions actually executed, and *which* five depended on thread scheduling — so the set was not even stable between runs. Every linux view assertion touching a widget was in that bucket (toggle/cancel bars, load-more visibility, the events grids, the onboarding widgets); they were not wrong, they were **unrun**, and any session that "verified linux behavior by running the suite" had verified about 7% of it. It had already hidden a real defect: the per-module `widget_names` helpers walked from `root.first_child()` and so never checked the page landmark id, which the landmark assertion would have caught had it ever run.

   **The rule: when a toolkit pins work to one thread, MOVE the body to that thread — never skip it.** The fix (`apps/fauna-linux/src/testid.rs`) replaces the guard with `run_on_gtk_thread(f)`: one dedicated thread owns `gtk::init()` for the process, every test body is shipped to it and awaited, and a panic inside the body is re-raised on the calling test thread so libtest reports a real failure carrying the original message. All 65 assertions run, on whatever thread libtest picks, and per-test names and granularity survive. **The helper deliberately has no skip path** — it either runs the body or panics — which is the enforcement: the mechanism that let a widget assertion silently not run no longer exists to be called, and a *new* GTK test that forgets the wrapper fails loudly rather than quietly. A body that hangs is bounded by a named budget (point 14) and marks the shared thread wedged, so later tests fail immediately naming the culprit instead of each burning the budget. The cheap-merge-tier gate `gtk-test-skip-guard-check` (a dedicated dev-fleet checker, parse-only, ~0.8 s, path-scoped to Rust changes) keeps the class at **zero** — a hard zero rather than a down-only ratchet, because the count is genuinely zero repo-wide, so any hit is new. The next app whose UI toolkit is single-threaded inherits this rule, not a fresh reinvention of the silent skip.

   **Mode 7 — the suite never reaches its body at all, because the HARNESS put a build in front of it (found + closed 2026-08-24).** Modes 1–6 are all a test deciding not to run itself. This one is the layer above: the tests were fine and were never given a chance to execute. `item.fixturenames` is not a list of fixture *requests* — pytest also puts every DIRECTLY-parametrized argname in it — so a session-scoped autouse fixture gated on *"does any selected test use the local nest"* matched the bare name `app` in `@pytest.mark.parametrize("app", [...seven app names...])`, resolved `nest_instance`, and parked a cold `just` build of `fauna-nest` in front of the very first test. With zero output, because the build had not printed yet. The victim was `tests/e2e-unified/tests/test_app_surface_declarations.py` — **this convention's own proof half** — so every guarantee above (that `--strict-app` reds unbuilt debt but not a declared absence, that an absence carries its citation, that `app_name` resolves all seven apps, that the static scan sees all four gate shapes) had been evaluated on no path at all, while the static half stayed green on the merge path and hid the loss. Nothing was failing behind it: the file is 50 passed in 0.13 s once the collision is lifted. **Rider — the same mode reaches a proof through a FIXTURE BODY, and the cure is the STUB, never a declared skip (ratified 2026-09-22).** Mode 7's collision was at collection; one layer in, a proof that calls a fixture's `__wrapped__()` directly inherits whatever the fixture does FIRST — and five of the six `*_app_path` fixtures build the app before they resolve it (deliberately: `tui_app_path`'s docstring records a "green" journey run that drove a 55-minute-old binary). Four proofs in that same file stubbed only the resolver, so the routing decision they exist to pin was gated on a real `just linux-debug` / `just tui-debug`: on macOS, which has no GTK, the linux pair died `RuntimeError: building the 'linux' app failed on BOTH the original attempt and the retry`, and the tui pair charged a machine-wide build-slot wait to a tier_1 proof this paragraph measures in tenths of a second. **The subject of a proof about a fixture's DECISION is the decision, so every arrangement the fixture makes before it — a build above all — is stubbed**, exactly as the same file's macos/windows/ios siblings always did. `skip_environment` is the wrong answer here and the tempting one: nothing about a routing decision is a box property, so declaring it would leave this convention's own proof half unrun on a whole machine — the failure this convention exists to stop, wearing the name of one of its own three helpers. Removing the build from the fixture is worse still. **And stubbing a call is not free: the call becomes an unproven claim**, so the stub is paid for with a proof that it is still made — `test_app_path_fixture_builds_before_it_resolves` asserts each fixture calls `_ensure_app_built` with its OWN app name, and `test_android_app_path_does_not_build` pins the one fixture deliberately exempt. The file is 63 passed in 0.23 s at that point, still with no build in front of it. **Rider — the arrangement is rarely a build, and a box-shaped red can be hiding a box-shaped VACUOUS GREEN (ratified 2026-09-22).** Sweeping the rest of the macOS tier_1 for the same family found the shape twice more, and neither was a fixture or a build. A dev-machine storage wrapper had ownership proofs that already stubbed `zfs`, `mountpoint` and `chown` — the unstubbed arrangement was **GNU `stat -c '%u:%g'`**, which BSD `stat` answers `stat: illegal option -- c`, so the wrapper silently took its `$SUDO_UID` fallback and two proofs asserted against a value the box had manufactured. Generalise accordingly: **an arrangement is anything the code under test consults before it reaches the decision being proved** — a build, a container runtime, a GNU-only flag, a privilege — and the machine you happen to be on is not part of the subject. **The sharper half is the second file.** `test_a_bundle_without_scanners_fails_rather_than_skipping` — the module's self-declared load-bearing anti-vacuity proof — asserted `main(...) == 1` and `"GATE FAIL" in out`, and on a box with no docker BOTH passed, because `bundle-scanner-probe.py`'s `shutil.which("docker")` check returns 1 with that very message **before** the scannerless branch it exists to pin ever runs. Only a third assertion on the service names noticed. So *a skip is not coverage* has a twin: **a PASS that fired on an unrelated early return is not coverage either**, and a box property is exactly the thing that quietly reroutes a proof into one. Two duties follow. (1) When a box-shaped red is next to an assertion that still passes, **ask what that assertion passed ON** before fixing the red — the red was the only thing reporting the vacuity, and curing it with a skip would have sealed the vacuity in permanently. (2) A proof whose subject sits behind an early return **asserts that it got past it** — here, `assert "docker is not on PATH" not in out`, which mutation-reds on the pre-fix shape. The companion habit is to prefer reading the artifact over asking the runtime: that file's `docker compose config --services` call became a direct YAML read of the bundle's own `services:` keys, paid for by a pin that the bundle uses no `include`/`extends` — so the premise is now proven on every box instead of unproven wherever docker is absent.

   **The blast radius was the whole tier, not one file.** A survey of the collected `--tier 1` selection found **2176 items with `_session_uses_local_nest` true on the strength of three parametrized argnames and zero real `app` fixtures** (the second victim being the payments-excision spine suite). A selection that is nest-free *by definition* was paying a full nest build — and on the docker-only runner that has no rust toolchain it would not have merely been slow, it would have failed outright. That is precisely what the "tier_1 sessions stay nest-free" unit test claims to guarantee; the claim was false in production the whole time, because the unit test's fake item had no parametrization to collide.

   **The rule: read a collected item's fixture closure only through `helpers/fixture_closure.py`, never by name.** A name counts as a direct param only when **both** signals agree, and each half is load-bearing: `callspec.params` alone would drop **indirect** params (`indirect=True`), whose real fixture genuinely does run — putting a real build back inside a test's own 900 s budget, the exact bound inversion the collection-time prebuild exists to prevent; and the "fixturedef belongs to pytest" test alone would drop pytest's own **built-in** fixtures, which a 3653-item survey caught it doing to `tmp_path`, `monkeypatch` and `tmp_path_factory` in every closure in the suite. Unknown shapes answer "real", because a spurious prebuild is wasted work while a missing one is a bound inversion. Enforcement is structural rather than another unit test: an AST pin requires every closure read in `conftest.py` and `helpers/` to route through the discriminator or carry an allowlist entry stating why it is safe, and a companion test reds when an allowlist entry outlives the read it exempts. Unit tests can only pin the callers that were already wrong; the pin is what catches the **next** caller making the same mistake, which is how this class returns.

8. **Drive the behavior-under-test through the app UI — test the way a user would.** The only config surface is the apps ([`../principles.md`](../principles.md) § One configuration surface), so a journey test's **mutations** are driven by driver UI actions, never a raw RPC/HTTP call standing in for the user — an API-only mutation path tests something no user can do and greens while the real UI path is broken. Three things are legitimately non-UI and outside this rule: **(a)** dedicated API-contract tests (point 5; `tests/api/`); **(b)** fixture **setup** arranging preconditions — arranging the world ≠ the action under test; **(c)** external black-box verification (health/TLS probes, port scans, SMTP/IMAP banner checks) — observing the box the way an outside scanner would. The sole carve-out for a *mutation* taken as an API shortcut: permitted only if a app-UI-only equivalent test proves a real user reaches that state through the UI — cite that test in a comment.

   **An arrangement is a fixture's OWN obligation, and a new nest-side policy gate owes its e2e fan-out in the same commit (ratified 2026-08-03).** Carve-out (b) permits arranging preconditions; the failure mode is arranging only *some* of them. When a nest gate starts refusing a request that used to be served, every fixture whose world no longer satisfies it becomes red — and the refusal usually surfaces far from its cause, because an app renders an unrecognised wire code as the generic "something went wrong" ([`version-compatibility.md`](version-compatibility.md) Dim 4), so the test fails two assertions later on a *missing effect* rather than on the refusal. Two duties follow. **Landing the gate**: sweep every module that trips it and arrange it in the same commit — a partial sweep is worse than none, because the modules that *were* arranged look like proof the class is handled. **Writing the arrangement**: put it where the object is created — the fixture that registers a peer owes that peer's reachability — and prefer one helper that makes the whole precondition atomic over a line each test must remember. The worked instance is `tests/api/conv_api.py::reachable_peer`: registering a peer, minting their key packages, and *accepting the sender* are one call, because the DM plane's `inbox_mode` enforcement ([`../behavior/direct-messages.md`](../behavior/direct-messages.md) § Reach policy owns the ruling) made the third fact load-bearing on 2026-08-02, its landing commit arranged four modules, and the ~13 it missed each failed as a vanished Welcome or an unconsumed key package — costing several triage passes that variously theorised a dying nest session and a broken module-relaunch contract before anyone read the nest's own `details` string.

   **A UI-free CONTROL beside the UI test is legitimate — and is not the shortcut above (ratified 2026-07-31).** The rule says a journey's mutations go through the UI; it does not say a *non-UI* question must be asked through the UI. When a UI test's subject is something the app merely *hosts* — cross-machine sync convergence, a nest-side projection, a background engine — the app sits on the critical path of a question it is not the subject of, and every app defect reads as a failure of the subject. Then a second test may drive the same subject with the app removed entirely, **provided all four hold**: (a) the UI test stays and stays primary — the control never replaces it, because the seams only the app has (its agent-spawn seam is the standing example — see point 9) go untested in the control; (b) the control shares the UI test's expectations *by import*, never by copy, so the two can never disagree on a byte and a mixed run still converges; (c) what the control does **not** prove is written down where a reader meets it, not inferred; and (d) it is a **bisect**, not a convenience — the pair's value is that green-control + red-UI localises the fault to the app in one round instead of three. The first worked instance was the multiseat filesync round: `tests/e2e-unified/tests/test_filesync_multiseat_live.py` drives three desktop apps, and a twin ran the same run-file protocol against three headless `fauna-sync` daemons with no app at all. It was built because rounds `20260730-01` and `-02` each spent three machines and half an hour discovering that the *macOS app* rendered zero folder rows — a question the control answers on one machine in a minute. **That control is retired (2026-09-30):** once the nest refused the daemon's unsigned records it could no longer write, and no app-free writer can sign (the agent's change signer is the principal writer key only an app's enrollment certifies; [`e2e-live-sync-convergence.md`](e2e-live-sync-convergence.md) § The convention). The rider still licenses a UI-free control wherever one can reach the subject without the app; for sync convergence the nearest bisect is now the one-machine `tui+tui` cell beside the `native` one.
9. **The harness is self-terminating (ratified 2026-07-14, after the 10 h wedge incident).** Nothing supervising the run is a safety net — a runner can be interrupted or killed at arbitrary times, so the harness itself bounds every wait and reaps every child; wedge states are made unrepresentable, not manually reapable (the [`nest/common.md`](nest/common.md) § Client-state recoverability spirit, applied to the harness). **A corollary with teeth, learned the hard way on iOS (2026-09-22): a bounded wait is only as good as the PRECONDITION it waits for, and a diagnosis printed in an error message is a load-bearing claim that ages like any other.** `IosInProcessDriver._ensure_booted` waited for `simctl list devices` to say `Booted` — which is the start of a simulator's boot, not the end of it: measured, `Booted` at **1.1 s** and `simctl bootstatus -b` finished at **513 s**, a 512-second window in which the device is up in name while installd and FrontBoard are not answering. Every bound downstream was correctly set and every one of them was then spent waiting on a device that had simply never been asked to finish (`terminate` 120 s + `uninstall` 120 s + `install` 300 s ≈ the whole 9-minute failure), and because the boot completed while the first test was failing, only ever the FIRST test of an invocation died — so the harness's own timeout message came to assert *"the simulator is wedged, not slow"* and to name the machine-wide `simctl shutdown all` as the cure. It was neither wedged nor slow, and that cure would have dropped another run's simulator, breaching this very point's process-safety rule to fix a problem that did not exist. Three rules follow. **(a)** Wait for the *completion* signal the platform actually offers (`bootstatus -b`), never a status word that a state machine passes through on its way up; where one spelling of "ready" exists, a second, weaker one beside it IS the defect. **(b)** Such a wait is a build-class cost, so convention 10's hoist applies to it: `conftest._get_ios_setup` starts the boot before the app build and collects it after, and `_prebuild_binaries` runs the whole thing at collection time, keeping a legitimately multi-minute boot out of a test's own 900 s budget. **(c)** When a failure's own message names a cause, verify it before building on it — a capture that inherits the message's diagnosis inherits its error. Pinned tier_1, with no simulator, by `tests/e2e-unified/tests/test_ios_boot_completion.py`. Six mechanisms, each with a red-on-regression proof — the first five in `tests/e2e-unified/tests/test_harness_self_termination.py`, the sixth beside its code:
   - **Every test is bounded — but HOW a wedge is reported is platform-split, and the split is load-bearing.** pytest-timeout enforces `timeout = 900` per test phase (`pytest.ini`), and conftest **refuses to run** when the plugin is missing rather than silently reverting to unbounded. On POSIX the `signal` method raises inside the hung test, so it dies as an ordinary failure and the session — summary and counts included — carries on. **Windows has no `SIGALRM`**, so the plugin falls to its `thread` method: it dumps every thread's stack and then `os._exit`s the process, ending the run at `+++ Timeout +++` with no summary, no counts, and **no traceback for any test that had already failed**. So "a wedged test dies as a normal failure" is a POSIX-only half of this bullet; on windows the diagnosis is carried instead by convention 7's live-reason line, which is exactly why that rider covers FAILEDs and not only ERRORs. Both halves are asserted rather than skipped (`tests/test_harness_self_termination.py` § 2) — the POSIX-only skip that used to hide the windows half was itself how two failures went permanently unattributable. Suites with a documented longer budget override with an explicit `@pytest.mark.timeout` (`tests/live/` 5400s; `tests/platform/docker/`, `version_skew`, `live_box` 3600s) — bounded always, unbounded never, and no *default* exceeds 15 min.
   - **The web browser is Playwright's bundled Chromium on every machine** (`drivers/browser.py`: explicit `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` → bundled → system fallback). Decision 2026-07-14: the snap Chromium and its machine-wide serialization flock (`drivers/chromium_lock.py`) are **retired** — the snap's per-machine ProcessSingleton was the root constraint behind the wedge class (silent flock queueing, same-process self-deadlock, an orphan browser wedging the next run), and the flock existed only because `playwright install chromium` was refused on ubuntu26.04-arm64, which an install-time `PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu24.04-arm64` resolves (the per-machine setup notes carry the exact command; verified: two concurrent bundled instances coexist). Concurrent browser runs — sibling sessions' web lanes, a tier_4 docker smoke beside a `--app web` run, a second same-process driver — are safe by construction, with nothing to serialize.
   - **Every harness child dies with its run.** Harness-spawned processes (web bridge, nest, mail bridge, xvfb + desktop app) are process-group leaders with Linux `PR_SET_PDEATHSIG` armed and their new process group registered with this run's pipe-EOF reaper — darwin's equivalent, since it has no parent-death signal at all (both inside `drivers/port_util.popen_group_kwargs`) and are torn down group-wide (`terminate_tree`: TERM → wait → KILL sweep); the web bridge forwards SIGTERM/SIGINT to its own group so the playwright node + Chromium subtree dies with it. Net guarantee: `kill -9` of pytest reaps the whole tree with **no cleanup code running** (kernel-delivered). Reapers only ever signal process groups this run created — never a pid discovered by name (process safety). **Windows has no process group to kill, so it gets the equivalent mechanism, not a weaker one** (2026-07-24): `port_util.reap_descendants_of(pid)` binds a launch **and every descendant it later spawns** to a `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` job object, which the kernel closes when the run dies for any reason — the same no-cleanup-code-required guarantee PDEATHSIG gives on Linux. `terminate_tree` reaches only the process it was handed, so before this a **grandchild** simply outlived the run: fauna-tui spawns `fauna-sync-agent`, a process *built* to outlive the app that started it (right in production, an orphan in a test), and the orphan then answered the next launch's pipe and held its own `.exe` against the next compile — found on the first windows run of the tui agent leg, 2026-07-24. Pinned by `test_job_object_reaps_a_grandchild_of_a_killed_spawner` (mutation-verified: disarming the flag turns it RED); the POSIX skip in that file is per-test rather than file-wide precisely so the platform whose orphans are hardest to see still runs its own proof. `drivers/tui.py` adopted it first (2026-07-24); **every remaining harness spawn site followed 2026-08-02** — the nest (`tests/common/nest.py::_spawn_and_wait`), the web bridge (`drivers/web.py`, whose playwright-node + Chromium subtree is precisely the grandchild case), and the mail bridge's three spawn/respawn sites in `conftest.py` (the respawn re-arms, because a job binds a *pid* and a rebind is a new process). The spawners still arming only `popen_group_kwargs()` are POSIX-only by construction — the linux app driver, `dbus-daemon`, the fake tray watcher — and are listed with their reasons in `test_every_spawn_site_arms_the_windows_half_too`, which fails on any new site that arms only the POSIX half **and** on a stale exemption. **The generalizable lesson, and the reason that structural test exists rather than just the four fixes: a mechanism armed by a SEPARATE call after the spawn will be forgotten.** The POSIX half rides *inside* `Popen(**popen_group_kwargs())` and so cannot be omitted; the Windows half is a second statement, and was in fact omitted at four of the five sites for the eight days after tui adopted it — invisible everywhere except a run on windows. What made the nest's instance expensive was blast radius, not the orphan itself: the leaked nest held its own pinned `fauna-nest-e2e-<hash>.exe` open, and because that name is deterministic per (features, profile), the NEXT run's `shutil.copy2` in `build_node` failed with `[WinError 32] … used by another process`, attributed to the `nest_binary` fixture — so a *failing* run silently armed the *following* run's failure, and the second failure presented as a build break in a tree that builds fine (cost a full ~13-minute run to identify, 2026-08-02). Pinned by `test_nest_spawn_dies_with_a_killed_run`, which drives the real `_spawn_and_wait` against a stub HTTP "nest" so the proof is a seconds-long process-lifetime question with no build in it. **The web bridge was leaking the same way**, and its fix is mutation-verified (disarming the call leaves the bridge alive after its run is `TerminateProcess`'d) and pinned end-to-end by `test_reap_drill_killed_pytest_leaves_no_orphans_win` — the Windows twin of the 3c reap drill, where a child pytest launches a real bridge + Chromium, is killed with no cleanup code, and the job must take the entire browser subtree; it also confirms that binding the bridge does not disturb Chromium's own sandbox job objects. Writing that twin **enabled the web lane on windows in this file** (2026-08-02): `test_second_web_driver_in_one_process_is_safe` had carried the blanket POSIX skip even though its subject is a *browser* singleton and the snap-Chromium constraint it replaced never existed off Linux — a stale skip which left the only test exercising the web-bridge spawn path unrun on the very platform whose orphans this section is about (point 7: a skip is not coverage). The file now runs 10 proofs on windows, up from 8. **A driver that hand-rolls its teardown silently opts out of all of this, and that is how the macOS seat orphaned `fauna-sync-agent` for months (found + fixed 2026-07-29).** `drivers/macos.py` and `drivers/tui.py` each open-coded "group TERM → wait → `proc.kill()`" instead of calling `terminate_tree`, which leaks the agent two ways: the `os.getpgid(pid)` call sat *inside* the `except ProcessLookupError` that was meant to tolerate an already-dead app, so once the app had exited and been reaped (the driver's own health-loop `poll()` does that) **no signal was sent at all**; and the escalation was a single-process `proc.kill()` rather than a group SIGKILL sweep, so a TERM-ignoring grandchild survived too. Two lessons generalize. **(a) Folklore about *why* a process survived is worth re-measuring:** this orphan was recorded for five days as "the agent ignores SIGTERM", which is false — the agent registers only `tokio::signal::ctrl_c` (SIGINT), so SIGTERM keeps its default disposition and kills it; it never *received* one. **(b) A backstop can hide a missing mechanism from the platform that has one.** `drivers/tui.py` had the identical hole yet reaped correctly, because a pty child is a session leader and the kernel SIGHUPs the foreground group when it exits — so the *pty*, not the teardown, was doing the work. macOS's plain-`Popen` launch has no such backstop and orphaned immediately. The tui gap is real but only observable with a grandchild that ignores SIGTERM **and** SIGHUP, which is ordinary `nohup`-style daemon behaviour and one disposition away for a process built to outlive its parent. Both drivers now call `terminate_tree`; pinned by `test_macos_teardown_reaps_the_agent_when_the_app_already_exited`, `test_macos_teardown_reaps_a_term_ignoring_agent`, and `test_tui_teardown_reaps_a_term_ignoring_agent`, all red-verified against the hand-rolled shape. The same file's `_pids_in_group` also read Linux `/proc` unconditionally, so **every proof in it errored on darwin** — the platform with no PDEATHSIG, i.e. the weakest reaping story, was the one never running its own proofs; it now falls back to `ps` off Linux. **The DETECTOR itself had the same shape of hole, closed 2026-08-14: `test_every_spawn_site_arms_the_windows_half_too` opens a file only if it already contains `popen_group_kwargs(`, so it catches "armed the POSIX half, forgot the Windows half" and is structurally blind to "armed NEITHER half".** A spawn site that never learned the convention was invisible; only one that half-learned it was caught — which is how `drivers/windows.py` sat unarmed indefinitely under a green pin (found 2026-08-05). The blindness was not only per-file: an AST census of all 115 spawn call sites found `conftest.py` holding three armed spawns **and one unarmed one** (the `just <recipe>` build spawn), so the pin opened that file, passed it on the armed sites, and never saw the other — the bug class hiding inside a file the detector considered covered. Seven infrastructure sites were unarmed (the AP nest, the windows sync agent and CalDAV nest, the android instrumentation client, that build spawn) and two more wore a **weaker shape that looks armed**: a bare `start_new_session=True` is the same setsid *without* `PR_SET_PDEATHSIG`, and `track_process()` only registers an atexit teardown a SIGKILL never runs, so `drivers/macos.py` and `drivers/posix_pty.py` had no guarantee at all when it mattered. All are now on the shared `popen_group_kwargs()` spelling. The second detector, `spawn-arming-ratchet-check` (a dedicated dev-fleet checker, cheap merge tier), is deliberately split by surface: **infrastructure** (`conftest.py`, `drivers/`, `helpers/`) is an **absolute** gate with no baseline, since its debt was measured to zero; **test files** are a **down-only ratchet** over 99 grandfathered sites, because most are genuinely short-lived children (18 of them are `test_build_slot.py`'s own tests of the slot mechanism) where a blanket widening would go loudly red for no safety gain. Red-verified by the discriminating mutant: disarming the AP nest spawn *including its import* — so the file contains no `popen_group_kwargs(` at all — leaves the original pin reporting **1 passed** while the new gate fails naming `helpers/ap_nest.py`. Also `bins/`-adjacent cleanup in the same pass: `tests/e2e-unified/bridges/process_manager.py` was an unarmed nest spawner with **zero consumers** since it was added four months earlier, deleted rather than armed — arming dead code would have made the exemption list lie. The generalizable lesson is one level up from the bullet above: **a detector keyed on the presence of a half-applied convention can only find half-adopters.** Key it on the *spawn*, which is the thing that actually exists, and let the exemption list carry the judgment. **And macOS had NEITHER half, for months and invisibly (found + closed 2026-08-22).** darwin has no `PR_SET_PDEATHSIG` and no job objects, so `popen_group_kwargs()` there was a bare `os.setsid()`: every mac harness child was held only by `terminate_tree`/atexit — cleanup code, which is precisely what a SIGKILLed pytest never runs. The cost was measured twice in one day on macOS: an e2e trio (the `FaunaMacOS` app, its `fauna-sync-agent` child, and a `fauna-nest-e2e` instance) outlived its pytest by 4h31m, and an independent recurrence hours later found **five** orphans from a single still-live checkout — two nests, two `fauna-mail-bridge` processes and an app — all reparented to PID 1, ages 4–7 h, holding two ports and ~375 MB while the session that spawned them kept adding more. **The rule the Windows case set applies unchanged: the platform without the primitive gets the equivalent mechanism, not a weaker one.** darwin's equivalent is **pipe EOF** — a pipe's last writer closing is kernel-delivered whether or not any cleanup code runs. `port_util._start_reaper()` starts ONE helper per run holding the read end of a pipe whose only writer is the pytest interpreter, and every child registers its own new pgid on that pipe **from inside `preexec_fn`** — so the arming rides within `Popen(**popen_group_kwargs())` and cannot be forgotten, the same property that makes the POSIX half unskippable and that the separate-call Windows half kept losing at four of five sites. On EOF the reaper sweeps every registered group TERM → wait → KILL; on a *clean* interpreter exit the atexit hook sends `BYE` first and the reaper exits **without signalling**, because a bare pgid number is indistinguishable from one the OS has since recycled, and firing on a recycled group could reach a sibling session's run (process safety). **It is armed on every POSIX platform, Linux included, deliberately:** this same section records darwin as "the platform with no PDEATHSIG, i.e. the weakest reaping story, [and] the one never running its own proofs" — a mechanism that executes only on the machine that needs it is a mechanism that rots, so the Linux dev machines' runs red-verify macOS's guarantee on every run. Pinned by `test_parent_reaper_kills_every_registered_group_when_the_spawner_is_sigkilled` (two armed groups, each holding a **SIGTERM-ignoring grandchild** — the shape that discriminates, since PDEATHSIG only ever signals the direct child and leaves such a grandchild alive on Linux too, and the shape the incident actually had: the sync agent is the *app's* child, the bridge's workers are the *bridge's*) and `test_parent_reaper_signals_nothing_after_a_clean_exit` (the recycled-pgid guard, asserted against the reaper's own **exit** as the causal barrier rather than a settle-sleep, point 14). Both are red-verified against discriminating mutants: dropping the registration write leaves both groups alive; suppressing `BYE` kills a group on a clean exit. The same change retired `test_nest_spawn_dies_with_a_killed_run`'s darwin skip, whose stated reason — "a declared platform gap there (testing.md § 9)" — **was never declared in any goal doc**: undeclared code drift wearing a citation, which is how a ratified guarantee goes unenforced on one platform without anyone reading a contradiction. That test now runs and passes on macOS unchanged. A **container** is the one child the kernel cannot reap with the group; the nest-mode axis's docker provider reaps those by label instead — owner [`testing.md`](testing.md) § Default app and nest mode, ruling (4) of the N-nests design.
   - **A machine-wide lock wait is loud and bounded.** Every machine-wide lock prints its holder(s) — pid + cwd (+ command) — immediately and once a minute, and fails the acquiring run with that diagnosis after a bound, so "slow sibling" and "wedged sibling" are distinguishable and nothing ever sleeps forever. Three locks exist: `helpers/live_box_lock.py` (serializing destructive tests against a shared live box; default bound 1800s, `FAUNA_E2E_LIVE_BOX_LOCK_TIMEOUT`) and the machine-wide **e2e slot pool** (a dedicated dev-fleet slot manager, acquired by conftest for any run selecting a tier_2/3/4 test, so N sessions' full e2e runs queue — 2 slots — instead of thrashing the shared machine; default bound 7200s, `FAUNA_SLOT_TIMEOUT`). Kernel flock in both — a crashed holder auto-releases. The third is the **windows physical-input mutex** (2026-08-01, `flaui-bridge/Actions.cs::_inputMutex`), and it is deliberately shaped differently from the other two: a named Win32 mutex held *inside the C# bridge* — not python — for a whole keyboard **ceremony**, session-scoped (`Local\`) because foreground ownership and `SendInput` are themselves per-session, so a `Global\` name would over-serialize sessions that cannot interfere. **The critical section is every operation that can move the foreground, not just the injection** (`Actions.cs::FocusThenInject`): UIA `SetFocus` *activates the containing window*, so focus, the focus-landing click and the keystrokes are one section. The mutex first shipped guarding only `ForegroundApp()`+`SendInput`, which does not work — a sibling still **blocked on the mutex** steals the foreground with an unlocked `el.Focus()` and collects the holder's keystrokes. That is measured, not reasoned: `tests/test_flaui_input_lock_windows.py` drives two bridges into a deterministic overlap (one holds the section open while the other is fired into it) and reads back each app's own text field; with the narrow boundary app A received nothing and app B received `'aaaaaaaaaabbbbbbbbbb'`, with the ceremony-wide boundary each app receives exactly its own text. The test stays honest by construction: `FAUNA_E2E_INPUT_LOCK=off` re-runs the same interleaving unserialized and is green only if the sibling's keystrokes really do land in the wrong app, so a lock that stopped working cannot present as a passing test. **Why it must exist:** `SendPhysicalInput`'s error-5 retry only covers a sibling stealing foreground from *us*; the damaging inverse is that when we *win* the foreground race, a sibling's in-flight `Keyboard.Type` lands in **our** app — a keystroke no process in this run sent, e.g. an ESC that closes a `ContentDialog` with its confirm handler never run, so the ceremony silently no-ops (modal closed, no RPC, no error) and is indistinguishable from a lost RPC without an app-side trace. Its wait is bounded at 30 s and then **degrades to running unlocked with a loud stderr warning** rather than failing the run — the one deliberate departure from "fails the acquiring run after a bound", because the critical section is milliseconds and converting a rare stall into a red would cost more than it catches; an abandoned mutex (bridge died mid-input) is caught and treated as acquired, which is the self-healing the other two get from kernel flock.
   - **A binary build — and the machine-wide `build`-slot wait in front of it — is never charged to a test's own clock (2026-07-29).** The session fixtures that build binaries (`nest_binary`, `mail_bridge_binary`, `seal_helper_binary`, the per-app build) delegate to memoized ensurers that `pytest_collection_finish` runs at collection time (`conftest.py::_prebuild_binaries`, beside `_prebuild_web_spa` and the `e2e` slot, which were always correctly placed there). Before this, the `just` recipes' unconditional `{{slot_build}}` acquisition (bounded 5400 s) landed inside the first requesting test's 900 s budget — a **bound inversion** that failed a healthy test as a bare `Timeout (>900.0s)` whenever concurrent builds elsewhere on the machine held both build slots, i.e. a verdict tracking machine load rather than the behavior under test: the harness-side violation of point 14's thesis, unfixable by pre-building (that removes the compile, never the slot wait). Laziness is exact (the collected items' fixture closures + app parametrization decide what builds); a collection-time build failure replays in the requesting fixture (correct attribution, no re-queue) while unrelated tests keep running. **The fixture-driven prebuild has a blind spot: a test that shells out to a `just` recipe directly, requesting no fixture, is invisible to `_prebuild_binaries`'s fixture-closure scan by construction** — measured 2026-08-16 when nine atproto e2e files did exactly that for `atproto-bridge-build`(`-e2e`), one dying as a bare `Timeout (>900.0s)` under fleet contention; closed by converting all nine onto `atproto_bridge_binary`/`atproto_bridge_e2e_binary` session fixtures.
   - **A run that stops making progress ends itself, and a whole-suite run has a wall-clock ceiling (2026-09-30).** Bounding every test is not bounding the run: a bridge whose thread pegs and never frees turns EVERY later test into a full boot-class wait plus the death-confirm poll, each one correctly classified *alive* (`http_bridge._timeout_verdict` — silence with accepted connects is a stall, not a death), and the run never recovers — measured 2026-09-30, a web tier_2/3 measuring run paid ~490 s on nine tests in a row, sat at 59% after 13 h and held the one-wide `e2e_other` lane the whole time. Two bounds, both ending the run with `pytest.exit` (exit 3, the render preflight's fail-fast shape): **(a)** `http_bridge.BRIDGE_PEGGED_STREAK_ABORT` (3) pegged verdicts on one driver with no bridge answer between them — any HTTP answer, error codes included, or a clean `/health` restarts the count, so a slow boot that finishes is never cut short — abort the run naming the streak and the test it ended in; **(b)** `--max-run-secs` stops a run from STARTING another test once that long has passed since its first (collection and the slot queue hold no e2e lane, so they are not counted; the running test stays bounded by its own 900 s), naming how many of the selection ran — `just e2e-tier-23-check` passes the nightly gate's own `GATE_MAX_SECS` (8 h), so a measuring run launched on its own is bounded too and a run the gate abandons at that bound ends itself rather than holding the lane as an orphan. Proofs: `test_bridge_death_classification.py::test_a_pegged_streak_aborts_the_run` / `::test_any_bridge_answer_between_pegged_verdicts_restarts_the_count`, and `test_run_ceiling.py`.

The convention keeps this number: *convention 10* / *point 10* stays the citation key and resolves there.

11. **The test-agent contract: a test agent MUST NOT silently drop a command (ratified 2026-07-14).** Every app's in-app test agent either **honours** a command or **fails loudly** — an unknown command, an unimplemented one, and a seam that throws all surface on the app's own `error-message` element (convention 2), never in a `.debug` log and never as a bare `return`. Silence is the single most expensive failure mode the harness has: a dropped command produces *no* error and *no* effect, so the test fails on a downstream read (`list_threads() == []`, "the bubble never rendered") that is indistinguishable from a genuine product bug — and the next session goes looking for one. Two real instances, both apple, both costing multiple sessions: a missing `conversations_real_resolve_send_new` that read as MLS **at-rest data loss**, and a swallowed `inject_inbound` throw that read as a lost async race. Corollary: **an agent's command table is a cross-app contract** — a command any app implements is one every app must either implement or explicitly refuse, so `helpers/skew_client.py`-style capability tuples stay honest rather than silently over-claiming. **Second corollary, ratified 2026-08-14 — the e2e state provider does NO blocking I/O.** An app's `serializeState`/`SerializeState`/`state_json` assembly is the **ack path**: a command is acknowledged only when the state push carrying its id completes, so anything added to serialized state must be a **field read, not a round trip**, and a round trip that can outlast the ack budget makes *every* command on that app unackable. **Nor may its cost follow the size of what a field summarizes (2026-09-21):** a provider that publishes on a tick — linux's does every 50 ms, on the GTK main thread — pays its whole cost every tick, so a read that deep-clones the data behind a count holds the thread for good once that data is large; the shared conversations serializer cloned every message of every thread, one ~3 MiB mail made each linux publish cost ~230 ms, and the barrier ack and every dialog map beneath DEFAULT priority starved while the heartbeat beat ([`apps/linux.md`](apps/linux.md) § Message Flow). This is the same disguise as a dropped command and is why it belongs to this convention rather than to convention 14: the suite does not fail as "the state push is slow", it fails as an unrelated feature's command being silently dropped, and **three separate investigations, in two independent efforts, each read it as a product bug in whatever feature their failing command belonged to** (the windows `provider=6007ms` measurement, told in full in [`e2e-latency-independent-assertions.md`](e2e-latency-independent-assertions.md) § *Implementation status today* → convention 14's windows-leg entry). **The provider is only the commonest source, not the boundary: the rule is that nothing blocks the thread that serves the agent.** On linux the agent's command drain and state refresh are a `glib::timeout_add_local` tick on the GTK main thread, so *product* work on that thread — nothing to do with the state provider — can make the whole app unackable: every claim→app journey has been dying on `agent timeout — the UI thread did not reply within 25s` since 2026-08-14, read at first as the newly-landed `trust_prompt` page until an A/B with the page disabled cleared it. ✅ **That red CLOSED 2026-08-18, and it was never GTK-thread blocking at all** — the cause was linux's `driver.reset()` rebuilding the wizard with a *fresh* `OnboardingMachine`, which dropped the e2e `provider_base_urls["nest"]` override while its mirrored launch-side dial override survived, so the returning admin's handle check probed an unresolvable host and Continue never enabled (fixed in shared Rust so every native app inherits it; `git log --grep 'a rebuilt wizard lost the e2e nest override'`). The obvious-looking culprit had already been measured and REFUTED along the way: three launch paths did run a `block_on` on a tokio runtime built and dropped on that thread (a genuine latent hazard, since `Runtime::drop` joins the blocking pool and tokio resolves DNS on `spawn_blocking(getaddrinfo)`), but moving all three off it on 2026-08-16 changed the failure set *not at all*, and a drop-duration detector added in the same commit never once fired. **The transferable lesson is the search order, not the answer**, and it survives the close intact: when a whole app goes unackable, suspect **any** synchronous work on its agent-serving thread, measure *where the thread actually sits* before believing a located hypothesis, and prefer the app's own off-thread idiom — linux's `async_helper::run_on_tokio`, already the shape of its cold-launch path — over a larger ack budget, which convention 14 forbids anyway. **Since 2026-09-02 the "measure where the thread sits" half is a MECHANISM, not an instruction** — `fauna_e2e_agent::UiThreadHeartbeat` is a liveness stamp the host's main loop touches every 250 ms, and the 504's message now carries its verdict: a **stale** beat (≥2 s) says the main loop is not running at all, while a **fresh** beat says the loop is alive and served other work, so *this op* is the slow one. **The stale branch names TWO suspects, and since 2026-09-10 it decides between them itself** — "synchronous work on the thread" is a bug to fix and "the box starved the process" is not, and a stale beat alone cannot tell them apart. So the agent beats a *second* stamp from a plain OS thread of its own (`process_liveness`), read at the same instant: fresh there while stale on the loop means the process was on a core the whole time and the main loop still did not advance — **synchronous work on the UI thread, in our code**; stale in both means nothing in the process ran, the agent's own sleeping thread included — **the box, not an app finding**. It is agent-owned rather than a host hook precisely so no host adopts it: supply a main-loop heartbeat and the split comes free. Why it was needed: the FIRST whole-suite `--app linux` sweep to run with a heartbeat (2026-09-02, 6.5 h, 3552 tests) produced **304** stale-beat timeouts across ~50 modules and not one could be attributed, so that sweep was unenumerable for the same reason the un-instrumented one before it had been. **The split's first reading is in (2026-09-10) and it indicts the app, not the box:** the third whole-suite `--app linux` sweep (6:13:34) failed 205 tests, and **110 of them died on a stale-loop timeout reading "the process itself was RUNNING"** — zero of the box kind — spread over 53 modules and landing mostly on *read* routes (`/element/visible` 91 of 110). So the linux app holds its GTK main thread for 25 s+ at a time under e2e load, and that one cause is more than half the linux suite's red; what holds it is the next measurement (the thread's stack at a stale beat), and the fix is the app's own off-thread idiom, never a larger ack budget. **That measurement landed 2026-09-10 and is agent-owned like the split above** (`fauna_e2e_agent::stall`): on the app-side verdict — and *only* that one, since a stack attached to a starved-box stall would send a reader hunting a blocking call that does not exist — the agent asks the stalled thread for its own stack, from outside. The mechanism is a directed `SIGURG` (chosen because its **default disposition is ignore**, so a signal arriving with no handler installed can never kill the app, where `SIGRTMIN+n` and `SIGPROF` would) to the thread that last beat the heartbeat, an allocation-free `_Unwind_Backtrace` into a static buffer inside the handler — the convenient shapes (`std::backtrace::Backtrace`, the `backtrace` crate) allocate, and a handler that allocates can deadlock the very thread it is diagnosing if it interrupted `malloc` — and symbolization (`dladdr` + binutils `addr2line`) back on the agent's own thread, where allocating is safe. Two samples 300 ms apart plus the thread's `/proc` CPU delta separate the two shapes of synchronous work, which need opposite fixes: **parked** (no CPU, same frame twice — a lock, channel, or syscall) versus **computing** (burning a core, usually moving). The same timeout also names the previous op served and the last command injected, because a stall that began *with* the timed-out op and one already running when it arrived accuse different code. **And the instrument closed the finding it was built for (2026-09-11).** Its first three stacks all named one shape — an *accessor or a tag that reads as free at its call site*, called once per post card by the feed's render: `offline_gate::declare_wire_kind` scanned every declaration already made in order to add one, so building a page was O(N²) over a process-global glib lock (the `COMPUTING` verdict — burning a core, not parked); `set_test_id` stamped a tooltip on every tagged widget and `gtk_widget_set_tooltip_text` blocks on an X11 round trip, so the automation surface was measuring its own overhead — and, invisibly, it made `offline_gate::apply` read every tagged control as one whose tooltip the page had already written, so the gate's withheld-reason could never land where a test could see it; and `FaunaClient::actor_id()` re-derived an Ed25519 keypair on every call. Each was fixed at the source and pinned by a **count**, never a duration (convention 14). The fourth whole-suite `--app linux` sweep (2026-09-11, 4:19:21) then produced **zero** stale-loop timeouts of either kind — 142 → 0 — with the suite's red falling 212 → 89 and nearly two hours off the wall clock; the 89 that remain are ordinary feature failures, so an `--app linux` sweep is **enumerable** for the first time since this class was opened. Two lessons outlive the three fixes: not one of them would have been found by *reading* the feed, because none looks like work at its call site; and removing the largest cut merely promotes the next, so the instrument is re-run after each fix rather than once at the end. Hosts adopt nothing: the beat already names the thread, so a host that supplies a main-loop heartbeat gets the capture free — and off Linux it reads `UNMEASURED`, never "no stall found", by the same rule the heartbeat itself follows. An agent-side counter could never supply that split, because the drivers issue ops one at a time and the agent therefore never observes the thread serving anything else while it waits. A host that has not adopted the stamp reads `UNMEASURED`, never "stalled" — a missing measurement must not manufacture a finding. Adopted on **linux** (a glib timer tick) and, since 2026-09-10, on **tui** — where the beat is a combinator wrapped around the whole main loop (`automation::beat_while_pending`), never an arm of its `select!`: tui's arms await their ops inline, and `select!` polls no other arm until the winner returns, so a beat arm is starved during exactly the waits it exists to classify and a slow op merely waiting on the network would read as a blocked loop. Wrapped around the loop's future, the ticker is polled whenever the loop yields and cannot be while its thread is held — the split itself — and it forces no repaint, since re-polling a suspended future never re-runs the loop body. The general rule for any future async host: **beat where the loop yields, not where it spins.** What prompted it: a whole-suite `--app linux` sweep on 2026-08-28 produced **150** of these timeouts, spread evenly across all ten deciles of a six-hour run, and not one of them could be attributed — the sweep was unenumerable for exactly that reason. ⚠ **And note which half of that was still true**: the refuted *hypothesis* was about this red, not about the hazard. The hazard was real and still live — five libsecret wrappers in `client.rs` were building their runtime on the calling thread, every one reached from a GTK handler, until `gtk-thread-tokio-check` (a dedicated dev-fleet checker, parse-only, cheap merge tier) made the class un-landable on 2026-08-19. Refuting a hypothesis retires the *suspect*, never the *rule*. The shared liveness read that closes this class for every app — `fauna_client_sync::agent::any_engine_serving_cached`, a last-known-answer field plus a bounded one-at-a-time background refresh — is the pattern to copy whenever a state block wants a value only I/O can produce: **cache the answer, refresh it off the ack path, and let the consumer's own polling supply the freshness.**

    **A command that FAILS is loud only if it carries its REASON, and a `Result`-less gesture hides one (2026-08-03).** Two rules, both found by the same swallow. **(a) The reason travels, not just the fact.** An arm that reports "something went wrong" leaves the driver exactly where the log line did: the nest refused a Welcome with `forbidden: recipient is not accepting new conversations`, no test saw that string, and the refusal surfaced two assertions later as a *missing* Welcome — which reads as a half-completed MLS bootstrap, not a policy refusal, and was triaged as one for a full pass. So the surfaced text names the command **and** quotes the app's own error. **(b) A gesture with no `Result` is not a gesture that cannot fail.** The manager's membership/label ops (`confirm_add_participant`, `remove_participant`, `rename_thread`) are *UI* gestures: they return `()`/`Option` and report a failed wire op only by stamping the page error, because that is what the on-screen control needs. An agent arm awaiting one therefore has **no return value to check**, and a `Result`-shaped wrapper around it (`e2e_remove` → `Ok(())`) is a swallow wearing a type signature — it can only ever report the pre-flight parse. The arm must read the slot back (`ConversationsManager::page_error_diagnostic`) and turn it into the failure it reports. Generalise: **when wrapping a UI gesture for an agent, find where the gesture puts its failure before trusting what it returns.** Two corollaries this fixed in passing: the failure slot is **nav-independent** (a refusal is not a property of whatever page is on screen — tui's `refused_agent_command`, linux's `SharedState::agent_command_failure`, both ahead of any page error in `messages.error` and both cleared only by `reset`); and the action layer matches on the **agent-failure marker**, never on "the error box is non-empty", so a *product* error a test meant to provoke is never mistaken for an agent failure.

    **A HALF-APPLIED command is a dropped command, and the worst shape of it (2026-07-30).** The two instances above are commands that did *nothing*; the more expensive shape is one whose cheap effects land while its load-bearing effect does not, because the cheap effects then make `get_state` **actively lie** and the test reads plausible-but-wrong data instead of nothing. Canonical instance: linux's `set_state({session})` naming a *different* actor while an authenticated window was already mounted. Its shell-build branch is gated on `current_stack.borrow().is_none()` (`apps/fauna-linux/src/main.rs`, guard present since 2026-04-02), so the `session_override`, the keyring write and the account-cache seed all became actor B while the live `FaunaClient`/`NestClient`/`feed::host` manager stayed actor A's — `get_state` reported B, the app drove A. On `test_gated_post_compose.py`'s subscriber leg that made the author's own custody unseal the gated body into the "subscriber's" card, so a *privacy* assertion failed by **leaking the full body**; and once the freshly stored credentials reached the live client's token refresh, the same binary could instead read an empty feed — two unrelated-looking symptoms from one dropped command, which is why the test presented as *flaky* rather than honestly red and survived three sessions of diagnosis. Two rules follow: **(a)** a session/identity-scoped patch must rebuild every identity-scoped singleton or refuse — reducing "switch actor" to the already-proven "reset, then login" is the cheap way to honour it; **(b)** when a test needs to assert *which* identity is live, read a surface the live session populates (linux's `account-actor-id` comes from `DataMessage::AuthSuccess`), never `get_state`'s session block — that block is the agent's own override, i.e. what the patch *asked for*, so it can never falsify the patch. Pinned by `test_second_login_live_clients.py::test_second_login_as_a_different_actor_switches_the_live_session`; the windows/apple/android arms of the same contract are unbuilt (see the apps area queue).

    **The twin rule: an agent MUST NOT silently ACCEPT an impossible command either — a picker refuses a value the frame did not offer (ratified 2026-08-03).** Dropping a command fails the test on a downstream read; *over*-honouring one is worse, because the test **passes**. `select(id, value)` that writes `value` through to the state machine without checking it against the options the app actually painted drives the app to a state **no keystroke can reach** — convention 8's forbidden "API-only mutation path" wearing a UI costume — and the whole failure mode *"the option list is wrong"* becomes structurally untestable through `select`, on every test that uses it. Found the expensive way: the first version of `test_upload_into_a_freshly_created_empty_folder` **passed against the un-fixed code** it was written to pin, because `select` set the Media filter to a set the page had never offered; the defect (an empty folder could never be an upload target) was *half* an option-list bug, and it took a live user to find it. So: **a select op resolves its value against the options that frame rendered, and refuses — loudly, naming what was offered — when it is absent.** Membership is not a proxy for reachability, it *is* reachability: the same list drives the keyboard/click path a user has.

    **The split is between actuating a widget and calling a writeback, and it predicts exactly which apps had the hole.** An agent that drives the *rendered* control cannot express the bug — it has to find the option before it can click it — so **linux** (`string_model_index` over the `DropDown`'s `StringObject` model → `{"error": "value not found"}`), **web** (Playwright `select_option`, which throws when no `<option>` matches), **windows** (`Actions.cs::Select` scans the expanded `ComboBoxItem`s and throws naming the visible ones) and **android** (`ElementOps.select` expands, then `By.text(value)` or throws) have always refused, for free. ***Refusing for free is not the same as refusing well*, and two of the four were refusing badly** — found only because the cross-app pin asserts the message, not just the raise. linux answered a bare `"value not found"`; web answered only after `select_option` burned its full 30 s timeout, with Playwright's "did not find some options". Neither named the value, the picker, or what **was** offered (convention 6), and both rode the default **404**, so the driver scroll-retried three times for a widget already on screen and then raised `LookupError` — reporting *"not rendered yet"* for an element it had found. Both were upgraded 2026-08-03 to a 409 naming the value and the painted list. **The general rule: refuse with the option list in hand** — every one of these mechanisms has already enumerated the options in order to fail, so saying what they were is free. windows was already the exemplar (`Select target 'x' not found in 'id' (visible items: …)`). A **value-writeback registry** has nothing to look up: **tui** dispatched `SelectTarget::gesture(value)` and **apple** calls `automationSelect`'s `set(value)`, both acking whatever string arrives. The rule is therefore not "add a membership check to `select`" — that would duplicate four correct widget-layer implementations — but **"a registry that registers a picker registers its option list too"**: the data that makes refusal possible is exactly the data the paint already has. Apps SHOULD answer `409` rather than `404` for this refusal (the element *was* found, so the driver must not scroll-retry looking for it); the shared agent honours an `error` reply's own `"status"` for that purpose (`libs/fauna-e2e-agent/src/lib.rs::element`), and the driver raises `drivers/http_bridge.py::SelectOptionNotOffered`. **The uniform, bridge-agnostic assertion a test makes is the invariant, not the status code:** the call raises *and* the picker's value is unchanged.

    **What counts as "offered" is one shared rule, because the suite drives keys and apps paint labels.** A cross-app test selects a **stable key** (`"this-device"`, `"BodyContains"`) while the app paints a human, often localized, **label** (`"This device"`, `"Body contains"`) — so membership is *exact match first, then a lowercase-alphanumeric normalized match*, with exact always winning so two genuinely distinct options can never be conflated. This is not reachability weakened: the user picks a row rather than typing, and a normalized key resolves 1:1 onto a row the frame really painted. The matcher is `fauna_e2e_agent::select_match`, shared by every direct-Rust app, and **an app must dispatch the matched OPTION, never the raw wire string** — handing the mutator a value the frame never painted is the same write-through bug one layer down. It is shared because the asymmetry was invisible while nobody checked: linux normalized inside its `DropDown` lookup, tui checked nothing at all, and the suite's key-driven selects passed on both — one by matching, one by writing through. The moment tui started refusing it was stricter than linux for no stated reason, which `test_task_delegation.py` caught immediately (`select(…, "this-device")` against tui's painted `[Automatic, This device]`). Any app adding this check adopts the same rule, or it will red honest tests.

    **What `session.authenticated` means: "the authenticated main app is MOUNTED", never "credentials exist" (ratified 2026-08-09).** The state protocol's `session.authenticated` is the arrival signal every native app's tests wait on — `tests/common/launch_harness.py::reached_authenticated_app` polls it for all six native apps (web alone reads a rendered shell — see the web refinement below). So its meaning is a **cross-app contract**, and exactly one reading is correct: the flag is true while the app is showing its authenticated main shell, and an explicit `set_state({"session": {"authenticated": …}})` patch overrides it while set (the override is what keeps an agent-driven login honest when its shell hand-off is deferred; it is cleared by `reset`/`logout`, and by nothing else). Reference implementation: `apps/fauna-linux/src/main.rs`, `authenticated_override.unwrap_or(app_state.is_some())`.

    **Stored credentials are NOT a session, and that is the whole point.** The launch machine routinely routes a *credentialed* relaunch to the wizard — verify 404 → `invite_request`/`claim_code`, or an awaiting-manual-dns "Almost ready" (`behavior/onboarding.md` § App-launch routing) — so an agent deriving the flag from "an identity key is loaded" reports `true` for an app that is sitting in onboarding. The failure that follows is **silent-green**, the class these conventions exist to kill: `reached_authenticated_app` returns immediately, and every assertion after it runs against whatever surface happens to be up. Windows published `_cryptoService?.HasKey == true` until 2026-08-09 and was fixed to the contract above; the two that got it right did so by deriving from a fact that cannot go stale — the mounted window (linux's `app_state.is_some()`) or the mounted page (windows' `rootFrame.Navigated` hook) — rather than from a boolean somebody has to remember to clear on sign-out, factory reset, account-abandon and a failed switch. **A new app's agent adopts the derived form; a flag assigned at the login seam is the bug, not the implementation detail.**

    **Web refinement: where "mounted" and "authenticated" come apart, publish the STRICTER fact (2026-08-17, web).** The ratified reading above derives the flag from the mounted authenticated shell, which on the six native apps *implies* a live session: their shells mount only once the launch machine reaches `Online`, at the cost of a real round trip. Web's does not — the SPA renders its authenticated shell from `localStorage` cache with the nest unreachable — so on web "mounted" is exactly the *credentials exist* reading the paragraph above forbids, and deriving from it would reintroduce silent-green rather than cure it. Web therefore publishes the stricter fact: **verified against its nest on this load**, set where the silent challenge returns verified (`store.ts::refreshFromServer`), never persisted and never derived from the cached handle. That is the reading `helpers/waiting.py::await_session_actor` already documents and every app's append journey needs ("no app sets them without its launch machine having reached `Online`"). Two consequences worth keeping: `reached_authenticated_app` deliberately keeps web on its DOM shell wait, because *it* wants the weaker "a shell is up" and an offline relaunch must satisfy it; and **the generalizable test for any app is "can this flag be true without a round trip?"** — before 2026-08-17 web's could not be true *at all* (the `registered` field its agent published had been dropped from the identity object as "derivable from the cached handle", so it was `undefined` for every real session and true only under a `set_state` injection: a cross-app observable that structurally could not be true, which is the same silent-green class seen from the other side, and it cost a session a full 120 s budget reading it as a product dead end).

    **The patch must move the PERSISTED source of truth too, not just the in-memory singletons — or the app's own self-heal reverts the switch (2026-07-30, web).** The rule above says "rebuild every identity-scoped singleton"; web satisfied that and was *still* broken, which is the generalization worth carrying. Web's agent reset the feed + conversations manager singletons on an actor switch but wrote the incoming actor only into the **legacy** identity-secret slot, never moving the account registry. The registry is the source of truth and that slot is only its mirror (`apps/fauna-web/src/lib/accounts.ts`'s `accountsBoot`), so the next page load's `identity.init()` did exactly what it is designed to do: `mirrorActiveToLegacy()` re-mirrored the OUTGOING account's secret back over the slot just written and `set(healed)` reverted the identity store — *after* the managers had been correctly rebuilt for the incoming actor. Note the shape: **the app was not buggy; its self-heal was correct, and it was healing away a state only the half-applied patch could create.** The damage then surfaced two layers from its cause — `getClient()` follows the reverted identity and retires the incoming actor's WS client, so the live `WasmFeedManager` (built over that connection) read through a **closed socket**: every query returned empty with nothing thrown, no `error-message`, and the browser console ring ending on `ws client closed; reconnect loop exiting`. Three sessions read that ring line as the cause; it was the last link. So: **(c)** for every identity-scoped patch, ask what the app re-reads on its *next* load — a registry, an index, an active-account pointer — and move that too; a patch that leaves the persisted pointer naming the outgoing actor is half-applied even when every live object was rebuilt correctly. Linux had the identical cause and fix, web the twin — and in both, the correct remedy already existed elsewhere in the same handler (linux's production switch path; web agent's own `reset` branch, which had cleared the registry for this exact documented reason since long before). **Suspect drift before design.**

    **The agent's in-place switch is STRICTER than production's, and that is a feature — the app must not depend on the reload (2026-07-31, web).** Rules (a)–(c) all say what the *patch* owes. This one is the converse, and the reason the class kept producing chapters after the agent was correct: an agent that switches actors **in place** exercises a transition the product may never perform. Web's real account switcher `window.location.assign`es (`routes/settings/[[subpage]]/+page.svelte::performSwitch` — a full reload re-runs the launch flow), so every scrap of page-local state dies by construction; the agent's session patch instead `goto`s client-side, keeping the component alive. Actor-scoped state that only ever died *by reload* then survives its actor. Instance: `routes/feed/+page.svelte` kept six per-post caches (`decodedPosts`, `decoding`, `mediaResolving`, `quoteResolving`, `previewResolving`, `unlockOfferResolving`), each keyed by post id alone and each doubling as `augmentPost`'s fire-once guard — so the outgoing actor's ids permanently suppressed the incoming actor's lazy resolves, and `gated-post-price` never painted while the post itself listed fine. Note this is the **same file** whose `manager` rebuild had already rekeyed on `secretHex` *for this exact reason*, with the comment recording it: the singleton was fixed, the caches beside it were not. So: **(d)** when an in-place switch exposes state the product's reload would have discarded, fix the **app** — reload-independence is the stronger invariant and the one a real client-side switch will eventually need — and do not "fix" it by making the agent hard-reload, which hides the fragility instead of removing it. The tell that this is (d) and not a fresh bug class: sibling apps pass the identical test because their fire-once guard is the manager snapshot itself (`post.unlock_offer.is_none()`), actor-scoped by construction. **A per-app side cache beside a shared snapshot is the shape to search for.**

    **An ILLEGAL command is the same failure one layer down: an actuation route must not drive a control the UI has DISABLED (2026-08-02, apple).** The rule above binds the *state-protocol* command table; the `/element/*` actuation routes owe the same honesty. web has it by construction — Playwright's `click()` auto-waits for enabled and fails loudly; since 2026-09-12 the web bridge answers that failure with the same named 409 as every in-process agent (`tests/e2e-unified/web-bridge/server.py::_actuate`, on click, double-click, clear and select; `type` stays unmapped because `press_sequentially` waits for nothing), so a cross-app test can assert the refusal itself on web rather than a bare Playwright timeout — but an in-process agent that looks a control up in its own registry and calls the registered closure will happily activate something no user could reach, because nothing in that path consults the control's enabled predicate. That is not a *dropped* command but an **illegal one silently honoured**, and it presents identically: the click "succeeds", the app does nothing (or does something a guard would have refused), and the test fails on a downstream read that reads exactly like a product bug. apple ran this way from the in-process cutover until 2026-08-02 — `actions/events.py::_submit_compose` had to read the enabled flag itself before every click purely to tell harness-drove-a-disabled-submit from the create-was-lost-downstream case. **So: every route that DRIVES a control (click, double-click, type, clear, select — not the read routes) consults the registered enabled predicate first, and a disabled control is refused with a named, greppable error naming the element and the reason.** Gating click alone is not compliance: typing into a disabled field is the same illegal act, and a half-applied gate leaves the hole open for the next session to rediscover. An entry that registers no predicate is enabled — the default the read routes already serve. Because a mature app has hundreds of such registrations, the sanctioned rollout is staged, not flipped: land the refusal behind a run-scoped flag whose permissive mode still drives but logs one greppable marker per violation, sweep the WHOLE suite in that mode so a single run enumerates every offending call site with no new red, triage that list to empty, and only then make refusal the default — keeping the permissive mode afterwards, because it is the instrument any later broad change re-measures itself with. Three rules the apple rollout paid for: **enumerate permissively, never strictly** (a refusal reds its test, and a red test stops, so a strict sweep reports at most the first offender per test and hides the rest); **the sweep needs a known-positive control** — a test that drives a disabled control on purpose, whose marker must appear in the log, since otherwise "zero violations" and "the detector never ran" read identically (that artifact once reported a whole apple target clean while 567 of its tests had silently skipped); and **measure every target the flag governs, never just one** — apple's macOS sweep did not catch its iOS offender. **A fourth rule the windows leg paid for, 2026-09-11: the enumeration need not be ONE process, and on a shared box it should not be.** A whole-suite sweep is a many-hour monolith, and a monolith that dies loses everything — windows lost three in a row, each killed mid-prebuild with no verdict. The OS's own account of them, checked on the third failure, is that they were **terminated, not crashed**: across both death windows the Windows System log held no `Resource-Exhaustion-Detector` and the Application log no `Application Error` and no Windows Error Reporting record, and a crashing process leaves one. That retired the cargo/linker-contention theory two sessions had been working from and left **no hygienic fix to make** — serializing the builds would not have saved any of the three — so the answer is topological: `scripts/actuation-sweep-chunks.py` runs the sweep as resumable chunks that all append to ONE `--actuation-log`, so the union of chunks IS the enumeration, a kill costs only the in-flight chunk, and `--start-at` resumes. Two design points worth copying. **Chunk on MODULE boundaries** — the `app` fixture already relaunches every capable app at each one (convention 10's per-module cold relaunch), so a module is the harness's own unit of isolation. And **sweep only tier_2+**: a marker is emitted by the agent or bridge that actuates, reachable only through a driver, so an in-process tier_1 test *cannot* emit one — and because tier markers are strictly enforced, the four tiers partition a selection exactly, which makes that an **exact** claim rather than a convenient one (measured on windows: 2672 + 128 + 802 + 20 == 3622 == the whole selection, so tier_1 was 74% of the run and zero possible markers). **Grade with `scripts/actuation-sweep-report.py`, not by eye**: it enforces signal 1 (every planned chunk finished, naming the `--start-at` when not) and signal 2 (**every** marker the app's known-positive control drives is present, not merely the first) before it will call a log an enumeration — the same "gating click alone is not compliance" argument one layer up, since a probe covering click *and* select proves only the click detector when only the button's marker arrives, and an empty offender list for every select call is then indistinguishable from a select gate that never ran, and its `PARTIAL` verdict states the trap directly — with chunks outstanding a *listed* element is a real offender, but an EMPTY list means nothing at all, because the chunks that never ran cannot report what they would have found. **apple COMPLETED this rollout 2026-08-05** and is the worked example (mechanism + both sweeps' numbers owned by [`apps/apple-e2e-automation.md`](apps/apple-e2e-automation.md) § The actuation gate). **The other in-process agents inherit the rule, not apple's flag name** — linux's `actuate_click` (`apps/fauna-linux/src/automation/agent.rs`) and windows' bridge owe the same check, each staged the same way. **linux STARTED 2026-08-20 and COMPLETED this rollout 2026-09-10**: all five drive routes consult GTK's effective `is_sensitive()` through the shared Rust half (`libs/fauna-e2e-agent::gate_actuation`), and refusal is the **default** (`--permissive-actuation` opts out). 13. **A redirected pipe MUST be drained for as long as the child lives (ratified 2026-07-22).** Any harness child spawned with `stdout=subprocess.PIPE` / `stderr=subprocess.PIPE` (or C# `RedirectStandardOutput/Error`) has a ~64 KB OS buffer, and when it fills the child's **next write blocks its calling thread forever**. A *handshake* read is not a drain: reading `readline()` until a `BRIDGE_PORT=` line stops the moment the port arrives, and everything the child logs afterwards accumulates against that ceiling. Every driver that redirects therefore hands the streams to `drivers/port_util.py::drain_pipes`, which runs daemon reader threads for the process's life and keeps a bounded tail for diagnostics. **Why this is a convention and not hygiene:** the windows bridge hit its worst form — the app under test *inherits* the bridge's stdout/stderr (`flaui-bridge/SessionManager.cs::Launch` starts it with `UseShellExecute=false` and no redirect of its own) and the app's native subscriber writes every line to stderr (`libs/fauna-log` `init` = ring + rolling file + **stderr**). Once the buffer filled, the next log write blocked whichever thread emitted it; when that was the **UI thread**, the WinUI dispatcher stopped draining, so `DispatcherQueue.TryEnqueue` still *succeeded* while the queued test-agent post-action never ran — `set_state` then failed with `App did not acknowledge command … within 10.0s` against an app that was alive, with its agent poll loop keeping a perfect ~1 s heartbeat. **The diagnostic signature of this whole class: it tracks cumulative output VOLUME, not product state** — so it strikes late in a run, presents as a flake tied to whatever test happens to run second, survives every product-side hypothesis, and *adding* log lines makes it strike **sooner** (the dose-response that finally identified it). It was chased as a product bug across seven separate turns (windows family-nav), each of which correctly eliminated a real product suspect. Corollary for instrumentation: a diagnostic that itself logs through the product's native path (windows `ShellLog` → `FaunaFfiMethods.LogMessage`) *changes the failure timing*, so pure diagnostics use a file-only writer (`FaunaApp.Core.Logs.E2eTrace`) instead.
