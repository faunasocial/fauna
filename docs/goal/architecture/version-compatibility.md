## 0. The trigger: alpha begins now

Fauna entered its **alpha testing phase on 2026-06-14**. From this point there are real testers with real data on real nests (the live `example.com` box already serves its admin's real mail and calendars). The phase change flips one foundational assumption:

> The pre-alpha policy **`feedback_no_migration_paths_preproduction`** — *"don't write migration paths; when a table's shape changes, `DROP` it and recreate it empty"* — is **RETIRED.** It was correct while there was no data to lose. There is now.

This doc replaces it with the alpha-onward contract below.

## 1. The compatibility contract (absolute invariants)

These are **absolute invariants** in the sense of [`nest/common.md`](nest/common.md) § Client-state recoverability — hard requirements, never "goals", never traded away for convenience. A change that violates one is a **bug**, not a deferred feature.

### I1 — Never destroy user-irrecoverable data (iron-clad)

**No schema or data evolution may discard data a user cannot recreate — ever.** No `DROP TABLE`, no `nest.db` wipe, no "recreate empty" on any table that holds user-or-admin-irrecoverable state (mail in flight, delivered mail, calendars, content, aliases, keys, settings the user set). This holds **even at a major-version bump**: a major bump *migrates* data (expand→migrate→contract, § 2.1), it never drops it.

- **Scope is precisely *user-irrecoverable* data.** Dropping a genuinely **ephemeral / derived / lock** table — `gc_locks`, `operation_locks`, re-derivable auth `sessions`, a recomputable cache, `mail_outbound_warmup_state` (derived from first-send) — is **not** a violation, because nothing a user owns is lost. A migration that drops such a table MUST carry a one-line comment stating *why* the table is recreatable (so the next reader can tell a safe drop from a data-loss bug). When unsure whether a table is user-irrecoverable, treat it as irrecoverable.
- This invariant is the data-layer corollary of the existing **Client-state recoverability** invariant (no client-reachable off-box brick): a destructive migration that strands a tester needing their data restored off-box is exactly the brick that invariant outlaws, extended from "nest state" to "user data".

### I2 — Full bidirectional compatibility within a major version

Within a single major version **M**, a client of *any* version interoperates with a nest of *any* version — **the client may be newer or older than the nest** — and a client may talk to **several nests of differing within-M versions at once**. This covers (per the user's scope decision, 2026-06-14):

- **(own nest across upgrades)** a tester whose client and nest update on different cadences — an old phone app against a freshly-updated nest, a new desktop against a nest nobody updated in months; **and**
- **(federation peers)** a client/nest interacting with *other admins'* nests running different within-M versions.

"Forward compatible" = an **older** peer keeps working when it meets a **newer** one (it ignores what it doesn't understand). "Backward compatible" = a **newer** peer keeps working against an **older** one (it degrades to the features the old peer supports). Both directions are required.

### I3 — Compatibility breaks only at major versions, only if unavoidable

A **compatibility break** — a change after which an old peer can *no longer interoperate* — is permitted **only at a major-version bump**, and only when genuinely unavoidable (e.g. a security fix that makes an old wire shape unsafe). Even then it ships with a **deprecation/transition window** announced ahead of the bump, and it still obeys **I1** (data is migrated across the bump, never dropped). Within a major version, evolution is **additive only** and both directions of I2 always hold. This is the standard semantic-versioning contract: **minor/patch = always compatible; major = may break, with a transition path and no data loss.**

**Where the window is announced (ruled 2026-10-01; nothing built, no major bump planned).** In the release notes of every release inside the window, and in the apps themselves: an admin whose nest, and a person whose app, will stop interoperating at the bump is told so by the app, with the date, on the update notice they already see — never only in a channel a person who just uses the app does not read (`principles.md` § One configuration surface: the apps are where people are reached). The wording and the element are designed with the first major bump that needs them; whoever plans that bump owes the design before the window opens.

### I4 — Additive-everywhere is the mechanism

I2/I3 are *delivered* by one discipline applied on every versioned surface: **add, never remove-or-rename-in-place, within a major version.**

- **Wire** (transport.md): new fields are additive and absorbed by the `extra` catch-all on old peers; new kinds are tolerated as `fauna.protocol.unknown_kind` / the `Unknown` push envelope; nothing is removed or renamed in place within a major.
- **At-rest schema** (nest/common.md): new columns/tables are additive and back-filled on boot by `reconcile_added_columns`; an older binary opening a newer DB ignores columns it doesn't know. Non-additive changes use expand→migrate→contract (§ 2.1), never a drop.
- **Capabilities** (§ 3): a newer peer *negotiates down* to what an older peer advertises rather than assuming a feature exists.
- **FFI binding boundary** (build-system.md § UniFFI app bindings): an additive field on an existing `#[derive(uniffi::Record)]` type carries `#[uniffi(default = …)]`, so the generated Swift/Kotlin/C# `init` gains a defaulted parameter and existing memberwise-construction sites keep compiling — the same additive discipline applied where shared Rust meets hand-written app code.

## 2. Scope boundary — the compatibility surface vs. internal code

The alpha trigger freezes the **compatibility surface only**: (a) the **wire** (WS-RPC kinds, frame/payload shapes, DAG-CBOR encodings) and (b) **at-rest/DB data**. Everything observable *across* a version boundary lives here and is now governed by I1–I4.

It does **not** freeze **internal code structure.** Refactoring Rust modules, unifying an app component across the 7 apps, renaming an internal function, restructuring a screen — none of it is observable across versions, so the long-term stance (*"prefer breaking things to do it right; minimize per-app divergence"*, priorities #1–#4, `principles.md` § Engineering principles) is **unchanged** for internal code. *"Alpha is now"* means **data and the client↔nest↔nest contract are production; internal code remains freely malleable.** When a refactor would change the wire or the at-rest shape, it crosses into the frozen surface and I1–I4 apply.

### 2.1 The expand→migrate→contract discipline (the only legal non-additive change)

A genuinely non-additive at-rest change (rename a column, change a type, add a `NOT NULL` column, split/merge a table) MUST be staged so both the old and new binary operate correctly at every step and **no row is dropped**:

1. **Expand** (release *N*): add the new column/table additively (the reconciler lands it on existing DBs). The new binary **dual-writes** old+new and **reads new-or-old**; the old binary keeps using the old shape, oblivious.
2. **Migrate** (release *N*, online): back-fill the new shape from the old for existing rows, idempotently, on boot or lazily.
3. **Contract** (a *later* release, only once every supported binary writes the new shape): stop writing the old column. Physically removing the old column is itself a destructive change — defer it to a **major bump** (I3), and even then via a table-rebuild that copies every row, never a `DROP` that loses data (I1).

This keeps `CREATE TABLE` blocks the single source of truth (so the additive reconciler still works) while making the hard case safe in both directions.

Until the genesis reset these were recorded in code as `DECLARED_BREAKING_VERSIONS: [u32; 4] = [32, 34, 39, 42]` (`migrations.rs`), a `const` assertion pinning `MIN_READER_SCHEMA_VERSION` to one of exactly these four values so an additive bump could never drag the floor along unnoticed and a real break could not land without a matching doc entry. The assertion retired with the history it pinned. The genesis itself raised the floor to 79 (the genesis paragraph above), guarded instead by the compile-time assert that the floor clears `RETIRED_LINEAGE_MAX_SCHEMA_VERSION`; the first post-genesis breaking change restores the per-break guard over its own number.

A single monotonic version can't tell "newer-but-additive-compatible" (an old binary *should* keep working — I2 backward-compat) from "newer-and-breaking" (an old binary *must* stop and surface an honest error). So the nest records **two** numbers, both binary constants:

- **`schema_version`** — bumped on **every** schema change (additive or not). The DB's "what shape am I" stamp.
- **`min_reader_version`** — the oldest binary `schema_version` that can still safely **operate** a DB this binary wrote. Bumped **only** on a non-additive/breaking change — i.e. the *contract* step of § 2.1, deferred to a major bump (I3). Additive changes leave it untouched (that is what makes an old binary keep working against a newer additive DB).

Both live in an additive single-row **`schema_meta`** table (created in a `CREATE TABLE` block so the reconciler lands it on existing DBs — I1-safe; a `PRAGMA user_version` holds only one 32-bit int, hence a table). They are written at the **end** of `run_migrations`, after migrations succeed. A DB with no `schema_meta` table or row is read as the baseline, `BASELINE_SCHEMA_VERSION` — the genesis pair (79, 79) since the genesis reset, because the only unstamped database `check_genesis` admits is an empty one, a nest's first boot (before the genesis the baseline was 1, for an alpha DB predating this feature).

**Boot-time check** (at `CacheDb::open`, *before* applying migrations), comparing the DB's recorded `db_v`/`db_min` against this binary's `bin_v = CURRENT_SCHEMA_VERSION`:

| Condition | Meaning | Action |
|---|---|---|
| `db_v ≤ bin_v` | binary is up-to-date or newer than the DB | run migrations to upgrade the DB forward (normal additive path), then restamp `bin_v`. |
| `db_v > bin_v` **and** `db_min ≤ bin_v` | DB is newer but only *additively* (within this binary's floor) | operate normally — the reconciler already tolerates the extra columns (I2 backward-compat). Do **not** restamp down. |
| `db_v > bin_v` **and** `db_min > bin_v` | DB carries a **breaking** change this binary predates | **incompatible** — surface the honest typed error (Dim 4), do **not** run destructive migrations, corrupt, or fail lazily at first insert. |

**Detection is not refusal (I2), and not an off-box brick (Client-state recoverability).** On the incompatible verdict the nest must **not** `bail!`/crash-loop (that strands the admin off-box). It boots into a **degraded "needs-update" mode** that comes up far enough to answer the anonymous pre-identity surface (`fauna.nest.info`) and to reject connects with the typed `fauna.nest.outdated` `RpcError` (this *boot-time* degraded path emits `fauna.nest.outdated`; the sibling **`fauna.nest.schema_mismatch` — for a *query-time* mismatch the boot gate cannot catch — was minted 2026-07-13 and is emitted from the shared `rpc_errors` seam, see Dim 4) carrying a localized message ("this nest is running an outdated version and must be updated") — so a client sees an actionable update prompt, never a silent crash-loop. This couples directly to Dim 4 (error classification) and Track 3 (app rendering): the degraded-serve path is the hardest part of the Track 2 implementation.

## 3. The six dimensions

Each dimension is **target state** followed by **status today** (honest, code-verified 2026-06-13/14). Anchors are `file:line` at the verified commit; consumers re-check against current code before acting.

### Dimension 1 — At-rest schema evolution (the nest DB + client-local stores)

> **Client-local column drops carry their own migration (2026-08-24).** The WG-era `wg_public_key` columns in `fauna-peer`'s `peer_contacts` / `device_endpoints` were `NOT NULL` with no default, so removing the field from the writer would have made every post-upgrade insert fail on an existing database. Both stores drop the column on open. The general rule is the one the folders-rename leg below already states — a change crossing an at-rest boundary needs its fallback in the *same* commit — applied to a drop rather than a rename; the compat reasoning for the matching wire half is § Dimension 2.

**Target.** The nest DB evolves additive-only within a major version; non-additive changes use expand→migrate→contract (§ 2.1); **no migration ever drops user-irrecoverable data** (I1). A nest binary tolerates a DB written by a **newer** binary (backward/downgrade safety): unknown columns/tables are ignored, never a hard failure that bricks boot. A recorded **`schema_version`** exists for **detection and honest error surfacing** — *not* for refusal: on a version it can't safely operate, the nest surfaces a typed, client-actionable error ("this nest needs updating / re-provisioning", Dimension 4), it does **not** silently corrupt or fail lazily at first insert.

The same contract governs **client-local at-rest state** (§ 2 names at-rest data, not only the nest DB): identity/keys, MLS state, the account index, config replicas, and sync caches evolve additive-only within a major, and every store holding **user-irrecoverable** data whose format can evolve carries a version scheme (the § 2.2 two-number pattern where non-additive evolution is conceivable) so an older build **honestly detects** newer-breaking data instead of silently misreading it — and, for stores an older build *rewrites wholesale*, never silently drops fields a newer build wrote. Where a store's **placement** changes rather than its schema — the per-account scoping of class-1 client state, owner `apps/account-scoping-dispositions.md` § Serialized switching — the same floor applies and is met by copy-never-destroy adoption: the flat store an older build reads survives intact, so a downgrade destroys nothing; what that doc owns is the bounded visibility consequence, which the at-rest downgrade cell encodes via `skew_client.HEAD_MLS_STORE_IS_ACCOUNT_SCOPED`. That flag alone proved insufficient the first time a pin actually postdated the scoping commit (measured 2026-07-22): the "previous" build was *itself* already scoped, so the downgrade cell needed a mirror pin-age gate — `PREV_BUILD_MLS_STORE_IS_ACCOUNT_SCOPED` — exactly the `PREV_BUILD_SUPPORTS_REAL_SEND` / `PREV_BUILD_SUPPORTS_HOME_ISOLATION` pattern (§ Dim 6) applied a third time; both cells are green on `macos` with it in place.

### Dimension 2 — Wire / WS-RPC evolution

**Target.** Additive-only within a major version (I4). New fields ride the `extra` catch-all on old peers; new kinds surface as a typed `fauna.protocol.unknown_kind` (request) or the `Unknown{kind,payload}` envelope (push) that an old peer degrades on; **no kind or field is removed or renamed in place** within a major. Kinds are **not** versioned with a `.v2` suffix in the normal case — additive in-place is the rule; a `.v2` kind is introduced **only** for an unavoidable breaking change at a major bump (I3), versioning *that one kind*, not the namespace.

**One ratified exception to the in-place rule — the folders rename (2026-08-13).** Phase 1b of the folders re-model renamed ~20 kinds (`fauna.file_sets.*` → `fauna.folders.*`, plus the admin/federation/bridge twins), their 7 error codes, and ~90 payload field names **in place**, with no alias and no dual-serving. That is precisely what the target above forbids within a major, and it is not an oversight: the user directed it explicitly ("no compatibility shim, no dual-serving, no frozen protocol spelling — the user updates all consumers", ratified 2026-08-13; the claim's owner is [`../behavior/folders.md`](../behavior/folders.md) § Target re-model). It rides the same alpha reasoning as the S9 at-rest break — a closed alpha whose few clients the user re-rolls himself — so it is a **one-time, user-ratified write-off against I4, not a precedent**: the additive-only rule stands for every other change, and this exception must be re-ratified before alpha ends. Consequence for Dimension 6: until the pin moves past the release that carries the rename, the version-skew grid is expected-incompatible. **Correction (2026-08-15): the original prediction that the pinned-previous login+DM cells "do not reach" a folder method was wrong, and measurably so** — the rename touched ~90 payload field names, not just the `fauna.file_sets.*` → `fauna.folders.*` kind namespace, and one of those renamed fields (`SyncBackupStatusReply.file_sets` → `.folders`) sits on `fauna.sync.backup_status`, an RPC every native app calls as part of ordinary post-login state population. So the pinned-previous-client-↔-HEAD-nest cell now fails at LOGIN itself, not on a folder-page visit: measured 2026-08-15 against the pinned build (predates the rename by 10 days) — `test_version_skew_real_binary.py::test_previous_client_journey_against_head_nest[linux]` FAILED (`fauna.sync.backup_status: Decode error: decode reply: schema mismatch: missing field 'file_sets'`), and the at-rest cell (`test_client_at_rest_upgrade.py::test_previous_build_state_opens_under_head_build[linux]`) FAILED downstream of the same cause (the previous build errors before writing any MLS state). This is the same shape as the 2026-07-13 `fauna.setup.storage_mode` break the grid caught, and it closes the same way — by the pin-update rule (a routine production release dispatch clears it, no code fix owed).

**A second ratified exception — the actor-key `sig_domain` reset (2026-08-17).** The signing-domain sweep re-defined the signed bytes of every actor-key ceremony **in place** — login handshake, challenge-verify, registration, lockout, claim-admin, invite submit/cancel, the NAT/storage-mode commits — from their untagged legacy forms to domain-tagged (and, for the variable-length contexts, length-prefixed) messages, deleting rather than dual-serving the untagged accept paths and the slice-1 `tagged_signature`/fallback transition machinery. A pre-sweep app cannot authenticate to a post-sweep nest (or vice versa). This rides the 2026-08-17 ruling that this is a one-time, pre-user reset (no migration owed) — the same closed-alpha reasoning as the folders rename above — so it is a **one-time, user-ratified write-off against I2/I4, not a precedent**; the security ruling + mechanism are owned by [`key-material-hierarchy.md`](key-material-hierarchy.md) § Architectural rules #8. Consequence for Dimension 6: until the pin moves past the release carrying the reset, the version-skew grid's cross-version login cells are expected-incompatible (the pinned-previous client signs untagged login bytes a HEAD nest refuses), clearing by the pin-update rule as with the folders rename — and the grid declares that window mechanically, by pin ancestry, rather than trusting this prose (§ Dimension 6 *Expected-incompatible windows*).

**A third ratified exception — the login nest binding (2026-09-23, user-ruled).** Every bearer-minting signature — `fauna.auth.{handshake,verify,device_handshake,custody_handshake}` — now names the nest it is addressed to ([`../behavior/login.md`](../behavior/login.md) § Binding the nest), and the change was made **in place**: the signed bytes and the request shapes changed (a required `nest_id`, a required handshake `client_nonce`), the unbound `.v1` forms were retired with **no accept path kept**, no capability advert and no transition window. The window was designed and the user declined it explicitly: *no real users yet; the public repository's first release is being minted now, so this is the last such moment* — and, more broadly, that every backwards-compatibility remnant carries a cost forward and is to be removed now while the *upgrade mechanisms* (versioned tags, adverts, the `extra` catch-all) stay. As with the two above it is a **one-time, user-ratified write-off against I2/I4, not a precedent**: a pre-binding peer fails its first ceremony (`fauna.protocol.malformed` — the request lacks `nest_id` — or `fauna.auth.signature_failed`) in both directions. Consequence for Dimension 6: until the pin moves past the release carrying the binding, every cross-version login cell is expected-incompatible, declared by pin ancestry (`helpers/prev_build.py::RATIFIED_INPLACE_BREAKS`), clearing by the pin-update rule.

**A fourth ratified exception — the compat-remnant sweep (2026-09-24, user-ruled; ONE ratification for the whole sweep, not a write-off per item).** The 2026-09-23 ruling above generalised: every backwards-compatibility remnant kept only so an OLDER PEER keeps working — an accept path, fallback, shim, retry arm, advert-gated downgrade or "legacy nest / older client" branch — is removed **in place**, with no accept path, no advert and no transition window, while every **upgrade mechanism** stays (the per-context `sig_domain` tags and their `.vN` versioning, the `NestHandshakeReply` capability-advert shape, the `extra` catch-all and `#[serde(default)]` discipline, `fauna.protocol.unknown_kind`, the schema-version scheme, I1–I4 themselves). **Scope — UNIVERSAL since the 2026-09-24 widening (user-ruled the same day; programs 1–2 ran under the original client↔nest↔nest-wire-only scope).** The ruling's premise: **no Fauna installation and no Fauna data exist anywhere**, and the public repository's first commit (the 2026-10 baseline) follows the sweep, so that no public code carries a pre-sweep shape — every installed version descends from that public tree. So the scope is the whole repository, at-rest included: every remnant kept only so a peer, an installation or stored data PREDATING the sweep keeps working — an accept path, fallback, shim or retry arm for an older peer; a read-fallback or `#[serde(alias)]` for a pre-rename stored blob; a schema floor, migration step or "legacy row" arm for a pre-sweep at-rest shape; an "older app / older agent" arm on the same-machine app↔sync-agent IPC — is removed in place, because nothing predating the sweep exists to be served, and (`../principles.md` § No user-data loss) there is nothing to migrate and no deletion to approve. What stays is unchanged in kind: the **upgrade mechanisms** — every `#[serde(default)]`, capability advert, versioned tag, the `MIN_READER_SCHEMA_VERSION` scheme and the migration *runner* are how post-sweep additive evolution works — and any "compat" whose job is something other than a pre-sweep peer or blob: a foreign-protocol MUA, a hostile-nest guard, or a LIVE reading of an absent value (a `None` `commit_seq` on a roster report is what a current client sends for a leave, not an older client's). **This is the LAST such sweep, and it ends at the 2026-10 baseline: from that commit on, I1–I4 and [`../principles.md`](../principles.md) § No user-data loss apply in full and unchanged — the next compat removal is a major bump with a transition window, never a sweep.** *(Superseded in its end date by the fifth exception below: the user extended the window through every `0.1.x` on 2026-10-08, so I1–I4 bind again from `0.2.0`.)* Like the three above it is a **one-time, user-ratified write-off against I2/I4, not a precedent**; the additive-only rule stands for every change after it — and the two additive-evolution gates keep enforcing it: each of the sweep's field-level breaks is listed, by key and the exact transition ratified, in `libs/fauna-protocol/schemas/ratified-breaks.txt` (the gates' one allowlist, owner [`transport.md`](transport.md) § Schema and forward-compat discipline), so the gates skip exactly the ratified findings and nothing else. Consequence for Dimension 6: the grid's pinned-previous cells are expected-incompatible until the pin advances past the sweep's commits (`helpers/prev_build.py::RATIFIED_INPLACE_BREAKS`). **The sweep's ledger — what each program and tranche removed, what it judged LIVE and kept, the dead-schema ruling, what is still queued, and the borderline items — is owned by [`compat-remnant-sweep.md`](compat-remnant-sweep.md)**; every item there rides this one ratification. **Who writes a ledger line (user-ruled 2026-09-30, on the early audit's twenty wire-field contractions A1–A20, every one approved).** Because this exception is ONE ruling for the whole remnant class, a `ratified-breaks.txt` line for a **sweep-class remnant** — a field, arm or kind kept only for a pre-sweep peer, installation or stored shape, its every current writer verified to always send the value (or no reader of it at all), the entry citing the sweep and dated inside its window — is a **transcription a session writes itself**, in the commit that carries the removal; it is never a per-line ask, and a session that halts on a batch of such lines is misreading this paragraph. A line for anything else is a **user ruling given in the moment, never a session's call**: a live kind or field retired by a cutover (the `device.adopt` retirement below), a retype (below), any break outside the sweep's definition, and every line from the 2026-10 baseline on. The ruling's reason, so it is not re-asked: before the baseline a contraction costs one commit, while from the baseline on the same change is a major bump carried by every third-party decoder, and adding a field back stays cheap and additive for ever — so for the remnant class removal is the default and keeping is what needs a reason; an always-sent optional field is a permanent "absent means?" question every third-party decoder answers on its own, and an optional field whose absence selects a weaker security rule is a downgrade switch handed to the least trusted party on the wire.

**A fifth ratified exception — the 0.1.x compat-free window (2026-10-08, user-ruled).** The user extended the fourth exception's premise to every `0.1.x` product version: when 0.1.3 was first proposed for publishing, nothing had been released anywhere — no store build installed, no nest image existed — and more in-place breaks were expected, so **while the product version ([`product-version.md`](product-version.md), root `Cargo.toml` `[workspace.package] version`) is `0.1.x`, no wire, IPC or at-rest backwards compatibility is owed**: a field, variant or kind may be removed, renamed or retyped in place, with no accept path, no read-fallback, no migration step and no transition window, and no `ratified-breaks.txt` line is written for it. It covers client↔nest↔nest, app↔sync-agent and every at-rest shape alike. **Consequence the ruling accepts:** an alpha tester's 0.1.x install may stop reading its own data, or stop talking to a nest of another 0.1.x, after any 0.1.x upgrade; the fix is a fresh install, not a migration, and that is no deletion needing the [`../principles.md`](../principles.md) § No user-data loss carve-out's per-case approval. What stays is unchanged in kind, as in the fourth exception: every **upgrade mechanism** (the `extra` catch-all and `#[serde(default)]` discipline, capability adverts, versioned `sig_domain` tags, `fauna.protocol.unknown_kind`, the schema-version scheme and migration runner, the enum ledger). **Mechanism:** both additive-evolution gates read the product version and, inside the window, print a break against their base as a note instead of failing; the catch-all rule, the enum ledger and `ratified-breaks.txt`'s only-grows check still fail as before (`tools/check-additive-evolution` `in_compat_free_window`, `scripts/check-cddl-evolution.py` its twin). **The window closes at `0.2.0`:** from the commit that raises the product version to `0.2.0`, I1–I4 and § No user-data loss apply in full, every break is refused again, and the first `0.2.x` is the compatibility baseline every later version within the major keeps. #### MLS application-message payloads (client↔client) — additive-only, delivered by skip-on-unknown (ratified 2026-08-02)

The `ChannelMessage` a member seals into an MLS application message (`ChannelMessageBody` and its nested enums — `libs/fauna-mls/src/types.rs`) is a wire surface between **clients** of possibly different versions: the nest never opens it, so no server-side catch-all or negotiation can mediate, and the `extra`-field mechanism above does not apply to an *enum variant*. Additive variants are nonetheless legal within the major, because every shipped decoder already degrades cleanly: an unknown variant fails that **one record's** dag-cbor decode inside `MlsEngine::decrypt`, and the shared poll loop (`poll_inbound_conv`) skips undecodable records without stalling the feed — the older member stays in the group and misses one message's *meaning*, never the channel. Two obligations this places on any new variant:

1. **Rendering-only loss.** The skipped record is unrecoverable for that device (the MLS ratchet advanced before the decode failed), so a new variant may carry only content whose loss degrades *rendering* — authoritative state must stay independently fetchable. A variant whose loss would break correctness needs a different surface, not a carve-out here.
2. **No split operations.** The failure is per-record, so one logical operation must never be split across a known and an unknown variant such that a partial decode misleads an older member.
3. **Nothing a person would have seen is lost without a word (ruled 2026-10-01).** A skipped record leaves no trace in the older app, and that is right for housekeeping a person never sees — the first applied instance below is of that kind. It is wrong for a message: the sender believes it was read and the reader does not know there was anything to read. The decode failure cannot tell the two apart (the whole record fails before its kind is known), so a blanket "a message could not be shown" line would fire for housekeeping too and is **not** the remedy. The duty sits with the new variant instead: one that carries something a person would see ships either with a fallback an older app can show, carried where the older decoder reads it, or behind a capability check so it is never sent into a group with a member that cannot read it. Nothing is owed in code for it today; the rule binds the next variant that carries a person's content.

Pinned by `an_unknown_group_meta_variant_fails_only_that_records_decode` (`libs/fauna-mls/src/types.rs`) plus the skip contract in `poll_inbound_conv`'s doc. First applied instance: the in-group succession statement, `GroupMetaMessage::Succession` ([`../behavior/identity-succession.md`](../behavior/identity-succession.md) § Implementation status today).

#### The one exception — a kind **no shipped version ever called** (ratified 2026-07-12)

The no-removal rule exists to protect **deployed callers**: I2 promises every (client × nest) pair within a major keeps working, so removing a kind some released client still calls would break that pair. A kind that was *registered on the nest but never wired to any caller* has no deployed caller to protect — **no** (client × nest) pair within the major can observe its removal — so it may be deleted rather than carried, dead, to the next major.

**The guard that makes this narrow, and not a licence to break compat:**

> **Never-had-a-caller** is removable. **No-longer-has-a-caller** is **not** — a kind that any shipped version once called stays, within the major, forever. "We think nobody uses it any more" is exactly the reasoning this rule exists to forbid.

**Evidence standard — cite it in the commit; a bare "it's unused" is not enough.** Both must hold, over *all history*, not just HEAD:

1. **No caller ever existed**, in any commit on any branch — `git log -S '<kind>' --all -- apps/ libs/fauna-client*` returns nothing. (HEAD-only greps miss a caller that shipped and was later removed — which would make the kind *no-longer*-called, i.e. NOT removable.)
2. **Not peer-reachable**: the kind is not on the nest↔nest surface (`fauna.federation.*`), and no bridge/sidecar emits it.

**Applied three times under the never-had-a-caller exception.** First: the pre-frame behavioral surface `fauna.engagement.{record,list}` + `fauna.access_grants.{create,list,revoke}`, deleted 2026-07-12 (frame D9; inventory owned by [`../behavior/engagement-cues.md`](../behavior/engagement-cues.md) § Retirement) — both nest-registered from inception with zero emitters in any client, in any version ever shipped. Second: `fauna.admin.folders.add_destination`, deleted 2026-08-18 alongside the v42 at-rest break (§ 2.2) — the admin-only writer was verified never called by any app or daemon in any supported deployment before deletion. Third: the admin storage-migration kinds `fauna.storage.migrate.{start,status,reset,delete_source}`, deleted 2026-09-27 after the ruling that the primary blob backend is artifact-set ([`nest/common.md`](nest/common.md) § Blob Store → Backend) — both prongs empty over all history, the deleted HTTP twins' paths included; their `migration_progress` table stops being written but is not dropped (§ 2.1 step 3).

**Applied once by USER POPULATION RULING — a different route, recorded separately so the two are never conflated (2026-08-23): the WireGuard kind set.** Removed: `fauna.wireguard.peer.{register,unregister}`, `fauna.admin.wireguard.{status,peers,keygen}`, and the push kind `fauna.peer.signal`. These do **not** clear the never-had-a-caller bar — apps *did* call them (tui's and windows' P2P registration pages, android's `ApiClient`), so by the guard above they are **no-longer-has-a-caller** and would ordinarily have to stay registered-but-dead until the next major.

They were removed anyway, because the population judgment that the guard reserves *to the user* was made **by the user** (2026-08-22/23, directing the deletion of the WireGuard stack: "we are using iroh for now and there is no point in compiling wireguard"). That is the sanctioned route — the guard forbids a *session* reasoning "we think nobody uses it any more"; it does not forbid the user ruling on their own deployed population. The supporting evidence put to them:

- **No shipped nest could ever answer these kinds.** All-history `git log -S 'fauna-nest/wireguard' -- Dockerfile .github/workflows/` is empty: no released image ever compiled the `wireguard` feature, and a featureless nest answered `fauna.wireguard.unavailable` (`bins/fauna-nest/src/wireguard_handlers.rs`). So every client call against every shipped nest already failed — removing the kinds changed a failing call into a differently-failing call, not a working pair into a broken one.
- **The (client × nest) pair the rule protects therefore never existed in a working state**, which is what made the ruling narrow rather than a precedent for "probably unused".

**What the kind removal did NOT reach, and what closed it four days later.** The 2026-08-23 deletion deliberately kept `fauna.peer.exchange`'s optional `wg_public_key` field and the `PeerContact` / `DeviceEndpoint` / client-SQLite `wg_public_key` columns as vestigial carriers, on the reading that deleting a *field* is subtractive on a still-live kind and so forbidden within the major "regardless of any population judgment". **That reading was retired 2026-08-24 (user-directed) and the carriers are now GONE**, closed early against the next-major trigger that originally gated it: *"I don't think the major version bump gate is meaningful when we don't have real users — the few we have are onboard with this."* Two independent things had to hold, and both were verified before the removal landed:

1. **The population ruling, extended from kinds to fields.** This is the same route the WireGuard kind set took above — the guard forbids a *session* reasoning "we think nobody uses it any more"; it does not forbid the user ruling on their own deployed population. First application at **field** level.
2. **The removal is unobservable in both directions anyway** — which is what makes it narrow rather than a licence. `PeerExchangeRequest`/`PeerExchangeReply` both carry the `#[serde(flatten)] extra` catch-all, so a WG-era peer that still sends `wg_public_key` has the value **absorbed**, never rejected; and the field was `Option` + `#[serde(default)]` on every build that ever declared it, so a still-deployed WG-era peer decoding a current exchange that omits it gets `None` rather than a decode error. Both directions were pinned in `libs/fauna-protocol/src/peer.rs` until the 2026-09-30 compat-remnant sweep removed the WG-era pins with the population they served (`compat-remnant-sweep.md`); the unknown-field catch-all stays pinned there (`exchange_request_absorbs_an_unknown_field`).

   The independent witness is the one already built for this exact question: `fauna-peer-channel`'s checked-in fuzz corpus, whose pristine replay is a declared **wire-compat canary** ("a captured payload that no longer decodes is a compat break"). `fuzz/corpus/kind_payloads/peer_exchange_{request,reply}-1.bin` were captured from a real exchange *while the field still existed*, and they replay green against the field-less structs — the removal is invisible to a byte-for-byte WG-era payload. ⚠ **Those two corpus files deliberately still contain the `wg_public_key` key and must never be regenerated to "clean them up"**: regenerating them destroys the only artifact that proves a deployed peer's bytes still decode.

**The guard, so this is not read as a general field-removal licence.** A field may be removed in place within a major only when **all three** hold, each evidenced in the commit — and the evidence must be **all-history**, exactly as the never-had-a-caller standard above demands, because a HEAD-only grep cannot see a build that once required the field: **(a)** every build that ever declared it declared it `Option` (or `#[serde(default)]`), so its absence cannot fail an older peer's decode; **(b)** the receiving struct carries the `extra` catch-all, so its *presence* cannot fail a newer peer's decode; **(c)** no shipped code ever read the value.

The evidence put up for `wg_public_key`: `git log --all -S 'wg_public_key' -- libs/fauna-protocol/src/peer.rs` returns **one** commit (the slice-6 kind set), which introduced both fields already `Option<String>` + `#[serde(default)]` beside the `extra` catch-all — so no shipped build ever declared it required, and the WG-era writer that would have populated it was deleted with the stack before any of it went live. Miss any one and the field stays — a required field, a `strict` opt-out struct (the in-image `bridge_routing` data-plane), or a field some build actually consumed is exactly the case I4 exists for. Note this is strictly narrower than the folders-rename and `sig_domain` write-offs above, which **did** break deployed pairs and were accepted anyway; this one breaks none.

**The at-rest half is NOT unobservable, and needed a real migration.** The client-local `peer_contacts.wg_public_key` and `device_endpoints.wg_public_key` columns are `BLOB NOT NULL` **with no default**, so a database created by a pre-removal build rejects every post-removal insert (`NOT NULL constraint failed`) until the column is gone — the client-side face of the § Dimension 1 rule that an at-rest boundary needs its fallback in the same commit. Both stores dropped the column on open, keyed on the column's own presence (idempotent, no version-ladder interplay), until the 2026-09-30 compat-remnant sweep removed the drop with every store that could hold the column; the genesis `CREATE TABLE`s never declare it. No user-recoverable data dies: the columns have held nothing but `Default` zeroes since the stack was deleted, and nothing ever read them.

**Explicitly NOT in this change, and closed two days later on its own evidence (2026-08-26):** `bins/fauna-push-relay`'s own `push_tokens.wg_public_key` column and its `PUT /v1/push-token` signing field. That was a *different* carrier with a different open question (no client crate calls the endpoint at all), and it was deliberately not folded into the above — which turned out to matter, because it does **not** need the population ruling at all. **It clears the stricter never-had-a-caller bar outright:** `git log --all -S 'push-token' -- apps/ libs/` returns nothing, so `PUT /v1/push-token` has never had a caller in any commit on any branch — no (client × relay) pair can observe the field's removal, because no pair ever existed. The value was write-only besides: the only reader of a stored token is the wake handler, which reads `platform` and `push_token` and never touched the key. So the three-part field guard is satisfied vacuously rather than by argument, and the removal is recorded here as evidence, not as a second population ruling.

  The at-rest half needed the same real migration the client stores did: `push_tokens.wg_public_key` was `BLOB NOT NULL` with no default and the relay's schema is a bare `CREATE TABLE IF NOT EXISTS` with no version ladder, so a database created by a pre-removal relay would reject every post-removal insert until the column is gone. `RelayDb::open` dropped it, keyed on the column's own presence (idempotent), until the 2026-09-30 compat-remnant sweep removed the drop with the pre-removal databases it served. ⚠ The two golden vectors named in [`api-layers.md`](api-layers.md) § Push relay pin the **wake** encoding, not push-token, and were correctly left untouched — a push-token element drop leaves them byte-identical.

  This was the **last `wg_public_key` in the tree**: what remains under that name is comments and the WG-era fuzz-corpus payloads above (the drop-on-open migrations and the protocol pins went in the 2026-09-30 compat-remnant sweep).

The matching at-rest half — `DROP TABLE wireguard_peers` at schema v47, with `MIN_READER_SCHEMA_VERSION` deliberately **unchanged at 42** — is recorded in § 2.2; the two halves landed in one commit.

**Assessed and REFUSED once — the negative precedent (2026-07-17): `fauna.event.rsvp`.** A plan claimed the push kind was "never produced on any nest version" and therefore removable. The all-history evidence standard falsified it: the first shipped production image (dispatched 2026-06-13 for the alpha start) contained a live producer on the legacy plaintext path (`event_social_routes.rs`, removed 2026-06-14 in the plaintext-calendar retirement). That makes it **no-longer-has-a-caller** — not removable — so the kind stays registered-but-dead (annotated in `push_events.rs`) until the next major bump, while its job moved to the new additive `fauna.calendar.changed` ([`transport.md`](transport.md) § Push events carries the full verdict). This is the guard working as designed: run the `git log -S … --all` check *before* trusting any "never called" claim — a HEAD-only grep would have said yes here, and been wrong. **Overridden 2026-09-24 by the compat-remnant sweep (the fourth ratified exception above) — the second application of the user-population route beside WireGuard, not a relaxation of the guard.** The population judgment the guard reserves to the user was made by the user (2026-09-23: *no real users yet*), so `fauna.event.rsvp` left the wire with the sweep's third tranche — enum variant, kind string, encode arm, CDDL type and the clients' ignore-arms; a pre-retirement nest's push now lands as `Unknown` and is ignored like every unmodelled kind — together with the two other dead-registered kinds the same ruling covers: `fauna.moderation.scan_report` (dead since 2026-07-19, [`../behavior/moderation.md`](../behavior/moderation.md) § State & data shape) and `fauna.admin.set_require_registration` (registered-and-rejecting since 2026-07-12, [`nest/public-mode.md`](nest/public-mode.md)). The guard itself stands for every session after it: a "never called" claim is still checked against all history before it is believed, and "we think nobody uses it" is still not a session's call to make.

#### The mirror rule — retiring a *sender* of a kind a shipped peer still **requires** (ratified 2026-07-14)

The no-removal rule above protects deployed **callers** of a kind. The § Dim 6 real-binary grid exposed the mirror-image hazard on 2026-07-13: deleting the last client-side **sender** of a kind that a shipped **nest still requires to reach a working state**. The storage-mode retirement kept the nest-side kind registered as a shim (I4 respected) but deleted every client-side `fauna.setup.storage_mode` call in the same stroke that removed the nest-side *requirement* — so a HEAD client claiming a nest from the then-pinned release stranded it mode-unresolved forever (content writes gated on a commit no client would ever send). The break came from the requirement, not the registration: I4's additive-wire discipline cannot see it, because nothing was removed *from the wire*.

**The rule: a client-side call that any shipped within-major peer *requires* to reach a working state survives until the major bump — retiring its UI is fine; the call itself survives in a minimal, UI-less form.** The surviving form is keyed on the old peer advertising the old shape (so it never fires against a current peer) and carries an auto-derived value where the retired UI used to ask the user (the report-shim principle of [`nest/storage-modes.md`](nest/storage-modes.md) § The transition contract, rule 1, applied in the client→nest direction). "We think no such peer is still deployed" is exactly the reasoning the one-exception guard forbids for callers, and it is equally forbidden here — the population judgment belongs to the user, the mechanism to the code. **Applied once so far:** the storage-mode compat commit (rule 5 of that contract) — the wizard step gone from all apps, the shared onboarding machine silently committing `encrypted` after claiming a nest that reported itself mode-unresolved. That application was itself retired 2026-09-24 by the compat-remnant sweep (the fourth ratified exception above): the doctrine stays for the next retirement of that shape; its one instance is gone with the pre-Phase-4 population it served.

### Dimension 3 — Version & capability negotiation

**Target.** At connect, a client learns the nest's version **and a capability set** (which kinds/features it supports) so it can **hide or disable** features the nest is too old (or too new) for, instead of letting the tester invoke them and hit a raw error (I2 "newer peer degrades down"). Symmetrically the nest tolerates a client that omits newer fields. The handshake rides the existing **anonymous / pre-identity** connection and MUST respect the **anonymous version coarsening** (below) — full version/build is admin-side only.

**Status today.**
- ✅ **Version surfaces exist.** `fauna.nest.info` is an **anonymous** pre-identity WS-RPC handler ([`discovery_handlers.rs:69,216`](../../../bins/fauna-nest/src/discovery_handlers.rs)); its reply carries `version`, `software`, **`protocols`**, `subhandles`, `registration` ([`:79`](../../../bins/fauna-nest/src/discovery_handlers.rs)). `fauna.admin.status` also carries `version` ([`admin_ws_handlers.rs:1885`](../../../bins/fauna-nest/src/admin_ws_handlers.rs) — the admin-status handler; moved out of `discovery_handlers.rs` in the WS-RPC migration). The `protocols` list is the **seed of a capability set** already on the wire.
- ✅ **Anonymous version is coarsened to `major.minor`** ([`discovery_core.rs:434`](../../../bins/fauna-nest/src/discovery_core.rs); ratified in [`federation.md`](federation.md) § anonymous surface) for anti-fingerprinting. **Constraint:** any capability handshake exposed to anonymous callers must stay at this granularity; precise version/build stays admin-side (the update-check loop, startup logs).
- ✅ **A skew-tolerance precedent exists.** `fauna.setup.status` carries `mail_subsystem_ok`, and **"a nest predating the field is read as `true` (no alarm on version skew)"** ([`nest/common.md:40`](nest/common.md)) — the canonical pattern for an older nest omitting a newer field.
- ✅ **Capability-set wire mechanism built (2026-06-16, tier_1 + tier_3).** The nest now advertises a **build/version capability set** on the anonymous `fauna.nest.info` reply, the seed promised above grown into a real negotiated set:
  - **Wire shape (ratified):** a new sibling field `NestInfoReply.capabilities: Vec<String>` ([`discovery.rs`](../../../libs/fauna-protocol/src/discovery.rs)), `#[serde(default)]` so it is additive-everywhere (I4) and an older nest that predates it decodes to `vec![]`. **Not** an overload of `protocols`: `protocols` stays the federation/interop list (bridge UIs gate on *it*), and the capability set is the distinct fauna-native feature-support gate. The third gate — `setup.status` runtime flags (`email_enabled`, …) — stays "the admin enabled it (via app UI)". **A client hides a feature when *either* its capability token is absent (nest too old) *or* its runtime flag is off.**
  - **Token registry + degrade helper (shared Rust):** `fauna_protocol::discovery::capability` (token `const`s + `supports(caps, token) -> bool`, mirroring `pair::capability`). A token the nest does **not** advertise reads as **unsupported** — the safe, non-erroring degrade, the same "an omitted field never errors" principle as `mail_subsystem_ok` (here the value that fits the semantics is *unsupported / hide*, not `true`).
  - **Coarseness honored:** tokens are coarse feature names (`mail`/`calendar`/`subscriptions`/`file_sync`), never a patch/build fingerprint — consistent with the `major.minor` version coarsening and the existing `protocols` posture.
  - **Honest scope note (forward-looking infrastructure):** the day-1 token *content* is thin by design — bridge gating is already served by `protocols`, and every fauna-native feature-family is always-compiled in this major version, so there is no *within-major* feature an older nest lacks **yet**. The value is the mechanism: when a future within-major feature lands, it appends its token, older nests omit it, and newer clients gate on it (I2). This is the same "tolerate before any bump" enablement as the segment-store `min_reader_format_version` field. Proven tier_1 (`fauna-protocol`: degrade-on-omit + `supports` semantics) + tier_3 (`test_wire_version_skew.py::test_nest_info_advertises_capability_set` — the real binary advertises a coarse set; a future token is absent → read unsupported).
- ✅ **Bridge-management UIs consume the build-capability gate *by construction* (verified 2026-06-16).** The nest's `fauna.bridges.list` is server-filtered (cfg-gated provider registration — the same gate that builds `protocols` — plus the per-bridge runtime `available` flag), and the bridges/Nostr pages render purely from that list on all apps, so a bluesky-only nest never surfaces nostr/activitypub affordances. Gating them on `protocols` would be redundant. (Mechanics: the bridges feature docs.)
- ✅ **Feed-subscription selector consumes the gate on all 7 apps — tui joined 2026-08-10, closing the last gap.** The per-app hard-coded `bridge-form-bridge-select` list is driven everywhere by the shared `FeedManager::refresh_available_bridges` → `FeedSnapshot.available_bridges` (projected from `fauna.bridges.list`), one uniform dropdown hidden when empty (priority #1/#4); tui's `bridge-feed-subscribe-toggle` is likewise painted only when `snapshot.available_bridges` is non-empty (`apps/fauna-tui/src/feed/mod.rs`, the affordance's own comment cites this section). tier_1 (`fauna-feed`) + tier_3 (`test_feed_bridge_selector_gating.py`, green macos/ios/windows; app-agnostic, confirmed green on tui 2026-08-24 (2 runs) and web (1 run)).
- ✅ **`capabilities` set gained real consumers (2026-06-24 → 2026-07-18) — the predicted future arrived.** The original four (`mail`/`calendar`/`subscriptions`/`file_sync`) launched as universally-compiled baseline tokens with nothing to gate. Four more tokens have since been added to the [`discovery::capability`](../../../libs/fauna-protocol/src/discovery.rs) registry, each landing *with* its client-side gate rather than speculatively — exactly the "first consumer arrives when a future within-major feature appends its token" case this section once described only hypothetically: `spam-model-sealed-at-rest` (2026-07-06 — the sealed-spam-model client-write path; ### Dimension 4 — Honest version / compatibility error surfacing

**Target.** A version- or schema-mismatch failure maps to a **typed, client-actionable** `RpcError` code with a **localized** message ("This nest needs to be updated / re-provisioned" — never a server SQL phrase), and is **distinguishable** from transient/connectivity errors so the client can route the user correctly (update prompt vs. retry). The mapping lives **nest-side** (internal failure → typed code) and **client-side** (render the localized `message`, not the raw `details`).

**Status today — built end-to-end on all 7 apps; the nest-wide query-time residual is CLOSED (2026-07-13).**
- ✅ The wire error is structured: `RpcError{ code: String, message: LocalizedText{key,args}, details: Option<Box<Value>> }` ([`error.rs:41`](../../../libs/fauna-protocol/src/error.rs)) — a code + an i18n key rendered client-side + an opaque details blob (`details` was boxed 2026-07-30 to shrink `RpcError`'s in-memory size; the box is transparent to serde, so the wire shape is unchanged — decision record: `transport.md` § Wire format → In-memory representation).
- ✅ **Query-time schema mismatch now surfaces as the typed `fauna.nest.schema_mismatch` (NeedsUpdate), not the auto-retried `fauna.protocol.internal` (Transient) — closed 2026-07-13.** The former hazard: the copy-pasted `fn internal(err) -> RpcError` helper (one per handler module) mapped *any* internal failure to a generic internal code, and `fauna.protocol.internal` is classified `RpcErrorAction::Transient` ([`error.rs`](../../../libs/fauna-protocol/src/error.rs)) — *safe to auto-retry* — so a query-time `no such column …` / `no such table …` (the case the boot-time `schema_meta` gate structurally cannot catch) reached the client as a retryable transient and was **silently retried forever** instead of raising the update prompt. ### Dimension 5 — Federation across nest versions

**Target.** Nest↔nest exchange obeys the same additive + capability-negotiation discipline (I2/I4) across *other admins'* differing within-major versions; a non-negotiable break is a major-version event (I3). The "version floor" concept stays, but admitting an older peer is **negotiated degradation**, not refusal, wherever the security model allows.

**One refusal already reaches a member (measured 2026-10-01).** A cross-nest call that the other nest refuses because it predates the kind is answered by the caller's own nest with the typed `fauna.federation.peer_nest_outdated` — the needs-update class, never retried, localized ("The other side's nest is running an outdated version and does not support this yet") — through `rpc_errors::map_peer_relay_error` at every peer-relay site (conversations, folders, sync, posts). The person sees it as the text of the action that failed, on whatever surface shows that failure; no app has a surface of its own for it and none is owed. No test drives the producer.

**Status today — far-future, with prior art.** Fauna **deploys as a single nest (`example.com`) today** ([`federation.md`](federation.md) § Implementation status today), so cross-admin version skew is not yet a live concern. The mechanism prior art exists: a dial→`ChannelUnsupported` capability negotiation, and the nest↔nest channel as the "production version floor" ([`federation.md`](federation.md) § version floor). The HTTP-interim fallback was **retired in slice 5** as a deliberate pre-alpha simplification, so a channel-only build currently surfaces `PoolError::Unsupported` rather than degrading; federation.md records that a future multi-admin deployment **must** re-introduce a negotiated fallback before admitting older peers. **Under this doc's I2 that re-introduction is a requirement (at multi-admin time), not an option** — recorded here as a gap, owned by federation.md. **The negotiated fallback must include the *signature* layer, not only capability negotiation:** the federation hello signature is domain-tagged `FEDERATION_HELLO_V1` with no legacy fallback, so a tagged nest cannot complete the hello with an older untagged peer (the sig fails before negotiation). Admitting an older peer therefore needs a transition at the hello-sig layer too (accept untagged hello sigs during a window, or floor at the tag version) — cross-ref [`federation.md`](federation.md) § version floor.

**Pinned-previous-build convention (ratified 2026-07-12).** The real-binary grid needs a durable name for "the previous released build". Pre-1.0 there are **no `v*` release tags** (none exists on either repository; no GitHub Release has been cut) and the workspace version (`0.1.0`) is degenerate — the only real release identity is the manual production image dispatch (`build-nest-image.yml`; [`build-system.md`](build-system.md) § Image tags & channels). So:

- **The pin is a repo constant:** `tests/e2e-unified/pinned-previous-build.toml`, carrying `commit` (the full `headSha` of the most recent dispatch whose verify gate went green — the update rule below), `nest_image` (`ghcr.io/faunasocial/nest:sha-<commit>` — the immutable production tag), and `released` (date, for staleness visibility). This is test-infrastructure data naming an artifact, not operator configuration — no human tunes it to change deployment behavior.
- **Semantics:** "previous build" = the most recent **verified staged build pair** (re-ruled 2026-10-02, the update rule below; "production release pair" until the private `:latest` was retired) — the immutable nest image *and* the client source at that same commit. The skew under test is HEAD ↔ pin, both directions.
- **Previous app binaries are rebuilt from source at `commit`** (no app release artifacts exist pre-1.0): a detached checkout of the pin commit, built and cached on the machine that owns that app's toolchain, under `<large-temp-root>/fauna-prev-builds/<commit>/<profile>/` keyed by commit + cargo profile (release profile preferred — `debug_assertions` can diverge; a session choosing debug for speed records that in the test). When app release artifacts exist (post-`v*` tags), the convention upgrades to downloading them; the pin's `commit` field is the join key either way.
- **Update rule (re-ruled 2026-10-02 with the private `:latest`'s retirement — [`build-system.md`](build-system.md) § Image tags & channels, the channel map): the pin advances when a build passes the private pipeline's VERIFY gate** — `build-nest-image.yml`'s *verify* job, or `restage-nest.yml`'s for an already-built `:sha-<sha>`, green against the staging box — not merely when a release is dispatched, and no longer on a promote, because the private repository promotes nothing. "Previous build" is therefore **the most recent verified staged build pair**: the newest `:sha-<sha>` the pipeline proved serving on the staging box, and the client source at that commit. *Why the verify gate and not production:* (1) the artifact the alpha boxes run IS the verified `:dev` (staged on dev.example.com), so this is the build HEAD must stay compatible with now; (2) under "one build, promoted through stages" the public repository's `:latest` is only ever a manifest copy of a `:sha-<sha>` the private verify already passed, so the pin never trails a build production did not pass through first; (3) a pin that waited for the public pipeline (gated on the public release and the store milestones) would sit inside its expected-incompatible windows (§ Dimension 2's genesis and sweep) for the whole wait, with the grid measuring nothing — the one measurement it exists for. **What is load-bearing is unchanged:** a dispatch that goes red at the verify gate never moves the pin, because an unverified candidate never proved it serves anywhere — the class the gate exists to keep out, and the 2026-08-03 re-pin incident that motivated it; and with the `skip_verify` break-glass cut alongside the promote job there is no ungated path left at all. The session that drives the dispatch records the verified build in the same session — a step of the release procedure (the nest-image-release skill). *(Until 2026-10-02 the rule read "advances when promoted to `:latest`"; the promote was the mechanical consequence of the same green verify, so no pin recorded under the old rule is wrong under this one.)* **The pin is DERIVED, not hand-written (landed 2026-08-27, the feature catalog's step 4; re-keyed 2026-10-02)** — `just features-render` writes it from the newest row of the catalog's release table that carries a `verified` date, and `release-verified <headSha>` is the act that writes that row in the dispatching session and lands the publish-gate allowlist entry the new SHA needs; `promoted` — a row's copy to the public repository's `:latest` — no longer moves the pin. The semantics above are unchanged and still owned here; what went in 2026-08-27 is the second hand-maintained copy of a fact the release table holds, and with it the hand-editing step whose omission was the pin's standing failure mode. `just features-lint` rule 5 checks the committed pin against the table. Until the table holds a verified row the render leaves the pin alone, so today's hand-written value stands until the first build recorded through `release-verified`. Owner of the table: [`feature-catalog.md`](feature-catalog.md) § Tag gate and release table.

**Conformance for an independent implementation (design pass 2026-09-24; nothing built).** The trademark-law lever against embrace-extend-extinguish — a "Fauna Compatible" badge licensed only to an implementation that passes a published conformance suite, and withdrawn from one that breaks compatibility — needs a compliance definition, and the seam is **the wire, not the e2e driver contract**. `PlatformDriver` drives an app through the in-app automation surface and the `ui.yaml` ids, which are ours and compiled out of every release artifact ([`e2e-automation-surface-gating.md`](e2e-automation-surface-gating.md), convention 15); asking a foreign implementation to embed them would turn a test seam into a public API and would test its UI, which is not what "compatible" means. **What "compatible" means** is this doc's contract observed at the wire: an implementation completes a published journey set against the reference peer using only registered kinds, degrades on a withheld capability token instead of failing (§ Dimension 3), tolerates unknown fields and `fauna.protocol.unknown_kind` (I4; [`transport.md`](transport.md) § Schema and forward-compat discipline), names the nest in every bearer-minting signature ([`../behavior/login.md`](../behavior/login.md) § Binding the nest), and produces content a conforming peer can read — signed canonical envelopes, and MLS application payloads under the additive skip-on-unknown rule (§ Dimension 2). Extension is legal only in the additive forms this doc already allows (new fields, `ext.*` records, new kinds a peer may refuse gracefully); an implementation that *requires* an unregistered kind to complete a published journey is by definition not compatible. **Two directions, two runners.** A candidate **nest** is tested by the crafted-peer suites that already exist — `tests/e2e-unified/tests/api/` (`ws_api.py`, `bare.py`) and `test_wire_version_skew.py` — pointed at a target URL by an env-gated live runner in the shape of `libs/fauna-provisioning/tests/bundled_conformance.rs` ([`provisioning/bundled-provider-api.md`](provisioning/bundled-provider-api.md) § Conformance suite: the suite IS the compliance definition, prose never outranks it), plus a federation leg in which a reference nest peers with the candidate ([`federation.md`](federation.md) § Uniform migration + mixed-version safety). A candidate **client** is never driven by our harness: it runs the published journey by its own means against a reference nest with a reference tui seat as the witness — the two-seat shape of [`e2e-live-sync-convergence.md`](e2e-live-sync-convergence.md), convention 16 — and the suite grades what the reference side observes: the witness reads every post and decrypts every DM the candidate sent, the fork-observability signals ([`transport.md`](transport.md) § Telemetry: the witness's `rpc_unknown_kind_observed_total` and the nest's subprotocol-mismatch warn-log) stay silent for the session, and a run with a capability token withheld shows the candidate hiding the feature rather than erroring. The reference tui and the reference nest are the oracle, and the badge licence names the suite revision a run passed. Those signals were designed as detection without enforcement; the badge is their enforcement, out of band, in trademark law. Build trigger (a second independent client implementation reaching users) and the trademark half: the organization doc's § Certification mark.

9. **Account-index + `UserConfig` honest-rewrite gates** (shared Rust, `fauna-client-accounts` + `fauna-client-config`) — stores an older build rewrites wholesale must not silently drop a newer build's fields. **Account-index half DONE 2026-07-13 (tier_1):** `AccountIndex`/`AccountEntry` gained the `#[serde(flatten)] extra` catch-all (mirroring `UserConfig`'s — an older build now re-emits fields it does not understand rather than dropping them on rewrite) and the § 2.2 two-number `(schema_version, min_reader_version)` pair, `#[serde(default)]` so every pre-scheme index reads as baseline `1`. **The `actor_id`-retype → whole-index-unparseable → legacy-fallback-orphans-secrets cliff is killed at its root:** the registry used to collapse "no index" and "an index I cannot parse" into the same `None` (`parsed_index`), so an unreadable index fell back to the legacy single slot and the next write *"healed"* (overwrote) it — stranding every other account's `fauna/{actor}/secret` in the keystore, referenced by nothing and unrecoverable from any app UI. Those two states are now distinct (`IndexState::{Absent, Readable, Unreadable}`): `migrate_legacy` refuses to migrate over an unreadable index, every mutator returns the typed `AccountError::IndexUnreadable`, reads report nothing rather than a misleading single account, and the on-disk blob is left byte-for-byte intact (tier_1-proven, including the malformed-JSON case and the no-restamp-down guard on a newer-additive index). **The two causes of `Unreadable` were split 2026-09-09** — they had shared one verdict and one message, and their remedies are opposites. A failed parse is now retried as a stamp-only `AccountIndexStamp` peek (the note-(a) pattern below, which `AccountIndex` had lacked): **a stamp above our floor is the version case with the numbers it actually read** — which is precisely the `actor_id`-retype cliff this item names, an index undecodable *here* and intact *there* — while an unparseable blob with no readable stamp is the distinct `AccountError::IndexMalformed`, whose message neither quotes numbers it never read nor tells the user to update an app that cannot help. The old arm reported the corrupt case with **invented baseline numbers**, printing the self-contradictory `schema_version=1, min_reader_version=1, this build=1 — update the app`. **The refusal itself is unchanged in both arms:** "nothing here can parse it" is a fact about this build, never evidence that the blob names no accounts, so I1's no-overwrite guarantee applies identically — a rebuild of the index from the legacy single slot was considered for the corrupt arm and **rejected**, being the exact heal item 10 below names. **`UserConfig` half DONE 2026-07-13 (tier_1; retired with the `__config` rail 2026-10-02, § 4):** the sealed payload carries the same `(schema_version, min_reader_version)` pair (`fauna-core/src/config_version.rs`), `#[serde(default)]` so every `__config` in the field reads as baseline `1`. The gate also fires on the **read** path (`unseal_user_config`), so a client can never even obtain a config it would go on to re-seal. Two design points worth carrying forward: (a) `ConfigVersionStamp` **peeks the version pair out of a payload this build cannot parse** — serde ignores unknown keys, so the stamp survives a future retype of any other field, which is the difference between an actionable "update the app; your config is intact" and an unactionable "corrupt"; (b) `persist_local` collapsed "no local replica" and "a replica I cannot read" into one `None` and then *overwrote* the latter ("self-healing") — **the account-index cliff, replayed**, and it would have destroyed the local replica's multi-nest deployment-seed union, the only surviving record of a box whose nest is already gone. Absent and unreadable are now distinct; best-effort may decline to write, never destroy. Re-seals never restamp a newer-additive config down (`max`, not `ours`).

10. ✅ **`fauna-index` format evolvability — the last store of this hazard class** (shared Rust, `libs/fauna-index`) — **DONE 2026-07-13 (tier_1).** The `IndexManifest` payload and **both** seal framings now carry the § 2.2 two-number scheme (`libs/fauna-index/src/version.rs` — `CURRENT_/MIN_READER_/BASELINE_INDEX_FORMAT_VERSION`, `IndexFormatVerdict`, `check_index_format_compatibility`, restamp-with-`max`), mirroring `fauna-core`'s `config_version.rs`, `fauna-mls`'s and `fauna-segment-store`'s `version.rs` and the nest DB's `check_schema_compatibility`. One `u8` pair serves both halves — the seal carries its numbers as **bytes in a binary AEAD header**, which physically caps them, and a single width keeps the payload and the envelope from drifting into two dialects of one scheme (#3).

    **What made this one different: the format has no back-catalogue.** Every sibling scheme was a retrofit over a store already holding user bytes. Here the audit found **zero production callers** — the only writer (nest-side `IndexRegistry::ingest_mail`) was deleted days earlier and its residue purged, so no byte of the format exists at rest. Two consequences shaped the fix. (a) The scheme is **free exactly now** and becomes a migration of user data the moment the client-side builder ("Plan 5b") writes the first byte — the index is not staying empty (nest-side ingest is retired *for good*; the index's only future is a client/bridge at-rest store synced across devices) and a **breaking** manifest change landed on this scheme the same day it was ratified (the per-kind split, 2026-08-02). So this landed "**version before any write**" — strictly stronger than the siblings' "tolerate before any bump". (b) There was **no writer to gate**, so a refuse-to-rewrite gate would have been a dark capability; the refusal lives in the *primitive* instead, and the constraint on the future writer is recorded in the owner doc (below).

    **The mechanism.** `manifest.rs` gains `min_reader_version` (`#[serde(default)]` → every conceivable pre-scheme manifest reads as baseline `1`) plus the `#[serde(flatten)] extra` catch-all (mirroring `UserConfig`/`AccountIndex`: the manifest is rewritten wholesale on every `append_segment`/`tombstone_segment`, so without it an older build would silently *drop* a newer build's fields), and a **peek** (`IndexManifest::peek_stamp`) that reads the version pair out of a payload this build cannot decode — the piece that makes a refusal actionable ("too old, index intact") instead of an unactionable "corrupt". `seal.rs` spends one of the two reserved header bytes (offset 6, the same offset in **both** framings) as `min_reader_version`, and replaces both exact-match `version != VERSION` rejects — which orphaned *every* future blob and reported it as an `IndexError::Crypto` indistinguishable from corruption — with the verdict. The new typed `IndexError::Incompatible { file_v, file_min, bin_v }` is distinct from `Crypto` and `SchemaMismatch` by design: collapsing "written by a newer build, data intact" into a generic "corrupt" is what licenses a caller to *heal* by overwriting, and that conflation is precisely what produced the item-9 cliffs.

    **The 8-byte header prefix is now bound as AEAD associated data**, reversing the v1 "why no AAD" call — and the reversal is *caused by* the versioning. v1's concrete objection was that binding the *nonce* or *wrapped data key* would break cheap-rewrap; a **static** prefix does not (rewrap copies bytes 0..8 verbatim, so both tags still verify — which also means a rotation by an older build can never restamp a newer segment down, § 2.2 for free). v1's other claim — that static-field AAD buys nothing — held only while there was **one** version and an intolerant reader: nothing to roll back *to*. Making readers tolerate a *range* of versions is exactly what creates a version-rollback surface, so binding the prefix is what pins each body to the format that produced it. Affordable only because nothing has ever written the format to disk.
