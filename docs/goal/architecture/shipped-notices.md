## Why

Fauna is offered under MIT or Apache-2.0 at the recipient's choice, and both ask that their text travel with a copy: MIT that its copyright and permission notice be included in copies, Apache-2.0 (its section 4) that a recipient be given a copy of the licence. A binary a person installs is a copy, and a pointer to a repository is not the text. Every shipped binary also contains other people's code — the compiled Rust crate graph, the Go mail bridge's modules, the web app's npm packages, the Windows App SDK runtime and WebView2 loader, the Android libraries — nearly all under licences (MIT, the BSD family, ISC, Apache-2.0) that ask the same of whoever redistributes it: the component's own copyright line and licence text, and for Apache-2.0 the contents of its `NOTICE` file. The canonical text of a licence does not carry a component's copyright line, so the obligation is met only by the component's own file.

## The rule

**Every artifact Fauna ships in binary form carries three files: `LICENSE-MIT`, `LICENSE-APACHE` and `THIRD-PARTY-NOTICES`.** The first two are the repository's own files, byte for byte. The third is generated for that artifact from what that artifact links or bundles — never the whole repository's dependency set, and never a hand-kept list. On Windows the three carry a `.txt` extension so that they open; elsewhere a channel follows its platform's convention (§ Per channel). An artifact whose build cannot produce its notices file fails, like any named asset the build did not produce.

**The notices file has three parts.** (1) A fixed header: what the file is, that Fauna itself is under MIT or Apache-2.0 with the two texts beside it, and that each component below stays under its own licence. (2) One entry per third-party component in the artifact: its name, its version, where it comes from (the registry or module path), its licence as an SPDX expression, and the component's own licence and notice files verbatim. (3) Components under a licence that asks for more than attribution (`MPL-2.0`, `LGPL-2.1-or-later` in today's allowlist) are listed again in a closing section that names where the exact source of that version is obtained. Identical licence files are printed once and referred to by the entries that share them.

**The source repository's `THIRD-PARTY-NOTICES.md` is a different file with a different question** — what the repository contains — and stays as it is, under its own gate. Where both need the same fact (a Go module's licence id), the generator reads it from that tracked file, so the fact has one home.

## How the notices file is produced

**One generator, one manifest, no new tool.** The generator, `just shipped-notices <artifact> <out>` (`scripts/shipped-notices.py`), reads `installer/shipped-notices.toml`, the one tracked manifest that names each artifact of § Per channel and the roots of its closure. It uses only the resolvers each ecosystem's build already runs, so it adds no dependency; a tool it turned out to need would be a dependency need like any other ([`dependency-bump-report.md`](dependency-bump-report.md) § Who opens a round).

**The closure is the artifact's own, per ecosystem:**

- **Rust:** `cargo tree -e normal` for the artifact's root packages, over the whole lock fetched first (`cargo fetch --locked`, the locked and checksummed set: a build fetches only its own targets' packages, and the offline resolve reads every package of the lock), with the features and target triple its recipe builds, resolved per root (`CARGO_RESOLVER_FEATURE_UNIFICATION=selected`, as every artifact build sets it — a workspace-wide resolve would list about twice what the artifact links); build and dev dependencies are not in a binary and are left out, and so are procedural macros, which run in the compiler (`-e normal,no-proc-macro`); an artifact whose build makes several cargo invocations lists one root group per invocation, each resolved with its own features and targets; a file for one binary — a release asset, a terminal archive, a Linux packaging, one architecture's installer — is resolved for the triples that binary is built for (`--target`, repeatable, keeping in each group only the triples named, and refusing a group left with none or a triple no group names), while an artifact that carries several triples in one package (an Android app's four ABIs) lists the union; workspace members are Fauna's own and are left out; a vendored fork is a third-party component.
- **Go:** the module list the built binary itself records (`go version -m <binary>`), which is exactly what was linked — a fraction of `go.sum`; a module under Fauna's own module path (`github.com/faunasocial/fauna/…`, an in-repository `replace`) is Fauna's own and is left out, and a vendored fork a `replace` points into the repository is a third-party component, named by the upstream module it forks at the version its `dep` line requires, from "the Fauna source repository, <its repository path>", as the Rust leg names a path dependency — that path resolved against the main module's directory (the manifest's `module`, where a build stages the binary elsewhere), never the binary's; a linked module the module cache lacks is fetched inside the main module, so `go.sum` checks it, and one still absent fails the generator.
- **NuGet:** the resolved package set of the published app (`project.assets.json`), which names the Windows App SDK and WebView2 packages — only the packages one of its restore targets gives an asset that reaches the published output (`runtime`, `native`, `runtimeTargets` or `resource`); build tooling, with build assets alone, is left out and named in a verdict line. Beside it, the runtime packs a self-contained publish copies into the output — the .NET runtime, and the Windows SDK projection every app targeting a Windows version carries — which the restore lists as downloads, never as packages: read off the published app's `deps.json` (its `runtimepack` libraries), the publish of the one runtime the run's Windows target names; a runtime pack's third-party notices file is copied like any package's (§ How the notices file is produced, *The texts are copied, not read*).
- **Bundled binaries:** a binary an artifact ships that no resolver lists — the mail bridge's `libunwind.dll`, the llvm-mingw toolchain's runtime library — is named in the manifest with its version, origin and licence id, and with the licence file its build copied out of the toolchain beside it (the toolchain's own, staged where the binary is, since the job that writes the notices has no toolchain); the binary must be staged, and a named file that is not fails the run rather than letting the standard text stand in unnoticed.
- **Toolchain runtime code:** a toolchain links its own code into every binary it builds, and no resolver lists it. **The test for an entry is what the piece's terms ask of an object-form copy:** where they ask that a notice or a licence text accompany the copy, the artifact's notices owe an entry carrying that text; where they lift that from code a compile or link puts into a program, or ask no notice of theirs of a redistributed program, nothing is owed and the piece is left out, on the reading recorded here. Each owed text is the toolchain's own file, copied byte for byte on the job that writes the notices (or staged by the job that has the toolchain), and a toolchain without the file fails the run. **Owed:** (a) *the Rust standard library* (`std`, `core`, `alloc` and the crates built into them; MIT OR Apache-2.0, the id the Rust project declares for it, and both ask it of a copy in any form) — every artifact with a Rust root group gets one entry, written by the generator with no manifest line, named with the release and commit `rustc -vV` reports for the pinned toolchain the run resolves with, its text that toolchain's `share/doc/rust/COPYRIGHT-library.html` under `rustc --print sysroot`, the Rust project's own generated notice for the standard library and everything built into it; that file is HTML of about 1.5 MB, so this one named file passes under a ceiling of 4 MiB in place of 256 KiB, the UTF-8 and NUL checks unchanged. (b) *The Go standard library and runtime* (BSD-3-Clause, which asks a redistribution in binary form to reproduce its notice) — every artifact with Go binaries gets one entry per Go version its binaries record (the first line of `go version -m`), its text `LICENSE` at `go env GOROOT`, copied only when the job's `go env GOVERSION`, asked inside the binary's main module, is the version the binary records (both follow the bridge module's `go.mod`); a different version fails the run. (c) *The .NET app host* (the app's `.exe` is the launcher of the `Microsoft.NETCore.App.Host.<rid>` pack with the app's name written into it; MIT) — an entry of the NuGet leg for the runtime the published app's `deps.json` names (its `runtimeTarget`). Where the restore downloaded the pack (`project.assets.json`'s download list names it: the publish's runtime is not the .NET SDK's own host's), its version is that list's and its id and files are the pack's in the package cache, as any package's are. Where the SDK supplied it from its own packs folder (the host's runtime — arm64's on an arm64 machine, x64's on the x64 release runner), the restore downloads none and that copy carries no `.nuspec` and no licence file: its version is the .NET runtime pack's the same publish copied (the SDK resolves both from its one bundled runtime version), the SDK's copy must be there at that version (`packs/Microsoft.NETCore.App.Host.<rid>/<version>` beside the `dotnet` the job runs), and its id and files are that runtime pack's — the same .NET release's, whose packs carry the same licence, notices and version-record files (10.0.8's host and runtime packs, compared by checksum). A publish whose `deps.json` names no runtime, or an app host placed by neither source, fails the run. (d) *The mingw-w64 runtime* the gnullvm link puts into the Windows mail bridge and its FFI library (its startup objects and the static part of its C runtime, under terms that ask a binary redistribution to reproduce their notices) — a `bundled` component of the MSI whose `binary` is the bridge that carries it, its version the llvm-mingw release, its id read from a structured record and held in the exception table with its reading, its text the mingw-w64 licence files the toolchain carries (`share/mingw32/COPYING*` under the target triple's directory), staged beside the bridge as `llvm-mingw/mingw32/` and carried by the mail-bridge part as libunwind's file is; it is named as a whole, since a notice too many costs nothing and one too few is the fault. (e) *The Android NDK's sysroot* (every Android link puts bionic's startup objects into the library; their notices, under BSD-style terms that ask a binary redistribution to reproduce them, are collected in the sysroot's own notice, while the NDK's package metadata names only the SDK licence agreement of the download) — every artifact with a Rust root group resolving for an Android triple gets one entry, written by the generator with no manifest line, found through the compiler driver each triple's link runs (the `android-ffi` drivers on `PATH`; every triple must resolve to one NDK), named with the `Pkg.ReleaseName` and `Pkg.Revision` of the NDK's `source.properties`, its text that NDK's `toolchains/llvm/prebuilt/<host>/sysroot/NOTICE`; that file is about 480 KiB, so this one named file passes under a ceiling of 1 MiB, and it is named as a whole, as (d) is. (f) *The GNU C Library's statically linked part* (its startup objects `crt1.o`, `crti.o`, `crtn.o` and its non-shared archive `libc_nonshared.a`, which every `*-linux-gnu` link puts into the program): the distribution's structured record for the C library's development package (the DEP-5 `copyright` of `libc6-dev`) names no link exception for them, only LGPL-2.1+ for the files outside its named stanzas, and LGPL-2.1 asks a work linked with the library to carry notice of it and a copy of the licence — so it is owed, named as a whole under LGPL-2.1-or-later, its text that record and the licence text it points to, read on the job that links, and a job without the record fails the run. The generator writes it with no manifest line for every artifact with a Rust root group resolving for a `*-linux-gnu` triple (a group naming no target counts as its host's) or with a Go binary whose `go version -m` records `CGO_ENABLED=1` and `GOOS=linux` (the nest image's mail bridge is one), named with the `dpkg-query` version of `libc6-dev`, its texts `/usr/share/doc/libc6-dev/copyright` and `/usr/share/common-licenses/LGPL-2.1`, and its source the distribution's source package of that version (Launchpad for Ubuntu, snapshot.debian.org for Debian, read from `/etc/os-release`; another distribution fails the run). Each packaging's C library, read: the terminal archive and the bare release binaries link on the release job that writes their notices; the Debian package and the AppImage link on the host the recipe runs on; the nest image's notices stage runs on the same Debian release as its Rust and Go builder stages (bookworm), so its record is that release's; the Flatpak and the Snap link the C library of their runtime (the GNOME SDK's) or base (`core24`'s), which the one notices file every packaging copies cannot name — its entry carries the same terms, read on the job that writes it, and each runtime's own source is the runtime publisher's to offer; a notice too many costs nothing, and naming the runtime's own version is left to the day a packaging writes a file of its own. **Left out:** *the compiler runtime builtins* an LLVM toolchain links (compiler-rt, and a statically linked libunwind; Apache-2.0 WITH LLVM-exception, whose exception lifts the licence's notice conditions from the portions a compile embeds in object form — `libunwind.dll`, shipped as a file of its own, is not such a portion and keeps its bundled entry); *GCC's runtime library pieces*, under the GCC Runtime Library Exception, which does the same; and *the static MSVC C runtime* of the `crt-static` builds, which Microsoft's terms for Visual Studio's distributable code permit inside a program and for which they ask no notice of Microsoft's to accompany it.
- **Installer tooling:** a packaging tool may put its own code into the package it writes, code that runs while the package installs or uninstalls and is never placed in the installed folder; no resolver lists it and no staged file is it. **The package is the artifact a person receives, so the rule's "links or bundles" is asked of the package, and the toolchain bullet's test decides: what do the piece's terms ask of an object-form copy.** One channel has such code today. **Owed: the WiX Toolset code the Windows MSI carries** — the custom-action libraries its Util and Firewall extensions put into the package (`util:ServiceConfig`, `util:RemoveFolderEx`, `firewall:FirewallException`) and the stock dialog set its UI extension contributes (`WixUI_FeatureTree`). WiX's own package metadata declares no licence id: the `wix` tool package's `.nuspec` names its licence as a file, `OSMFEULA.txt` (6.0.2, read 2026-11-13), and that file says the software is under the Microsoft Reciprocal License and that a binary release may be redistributed where the redistribution complies with it, notices included; the Reciprocal License's conditions reach a distribution of any portion in compiled form. That the code only runs at install time lifts nothing: the copy is in every package handed out. So the `windows-msi` artifact owes one entry, a `bundled` component named as a whole (as Owed (d) is), *WiX Toolset install-time code*: its version the WiX version the build pins (the tool and its three extensions at one version, which `release.yml` and the Windows setup guide name and a tier_1 test holds equal to the manifest's), its origin the three extension packages, its id `MS-RL`, which is outside the allowlist and passes on the manifest's exception table with this reading — the allowlist is not widened for it. The licence asks nothing about source of an object-form copy, so the entry is not in the closing section. **Where its files come from:** the package holding the code does not exist when the notices are written and the restored extension packages carry no licence file, so `just windows-msi-notices` — which runs on the job that has WiX, the assembly job and the test fixture alike — stages a `wix/` directory under the bundled directory: the Util extension's library from the WiX extension cache at the pinned version, the component's `binary` (the file the code is taken from; a job without WiX at that version fails there), `wix/OSMFEULA.txt` copied from the tool package in the .NET tool store at that version, and `wix/MS-RL.txt`, the licence's standard text, since the package's own file names the licence without carrying it. That text is the tracked set's (*The texts are copied, not read*, below), which for this holds one more text than the allowlist's: an id an exception of a `bundled` component names is fetched and checksummed like the others. The Microsoft Store package is packed by the Windows SDK's packer, which adds no code of its own, and owes nothing here; a channel whose packaging tool comes to embed code of its own is read the same way before it ships.
- **npm:** the web app's runtime `dependencies`, each followed through the names its own `package.json` lists under `dependencies` and resolved by the lockfile (the lockfile also lists a package's peers and its optional platform binaries, which are not in the served app); build-time packages are left out, except those whose runtime code the bundler inlines into the served app (Svelte's runtime, SvelteKit's client), which the manifest names.
- **Android:** the release runtime classpath Gradle resolves, read from the dependency report the Android build writes (`gradle :app:dependencies --configuration <the release configuration>`); a library's licence files are copied out of its archive (`META-INF/LICENSE*`, `NOTICE*`).
- **Swift:** none today — the Apple package pins no remote dependency; a pinned one would join through `Package.resolved`.

**The licence id comes from structured metadata, never from a text a session reads:** the `license` field `cargo metadata` reports, a package's `.nuspec` or `package.json` licence field, a Maven POM's licence entry, or its parent POM's where it declares none, as Maven inherits it (a POM names a licence, not an id: the generator's table maps the names in use, and an unmapped name is no id), for a bundled binary the id its manifest entry records, and for a Go module the id the repository's `THIRD-PARTY-NOTICES.md` table records (for a vendored fork, its row of that file's vendored-source table). Every id must fall inside `deny.toml`'s `[licenses] allow` list — the one licence allowlist, now for everything shipped and not only for crates. A component with no id, or an id outside the list, fails the generator unless the manifest's exception table records it with a reading (an entry's name may end in `*` to cover a package family; the Microsoft runtime packages, whose terms are Microsoft's own, are the first entries). Where a component declares no id and its exception records one inside the allowlist (read, like any id, from structured metadata — the source repository's licence as its forge's API reports it, say), that id stands for the component's own: it is shown, and its standard text stands in when the component carries no file.

**The texts are copied, not read.** For each component the generator copies the component's own licence and notice files (`LICENSE*`, `LICENCE*`, `COPYING*`, `NOTICE*`, `UNLICENSE*`, or the file its manifest names) and its third-party notices files (`THIRD-PARTY-NOTICES*`, `ThirdPartyNotices*`, attributing code the package bundles), in every ecosystem, byte for byte out of the package cache the build already fetched the locked, reviewed bytes into. It copies and does not interpret: a file must be valid UTF-8, carry no NUL and be under 256 KiB, or it is left out and reported. A component from which no licence file was copied — a `NOTICE*` or a third-party notices file attributes, it is never the licence, so copying one does not stand in for it, while a file the toolchain or bundled leg names for its component is that component's licence file whatever its name (the NDK sysroot's `NOTICE` holds bionic's licences) — gets the canonical text of its licence id from `supply-chain/licence-texts/<id>.txt` — a tracked set holding one text per id in the allowlist (and one per id an exception of a `bundled` component names, the installer-tooling bullet's `MS-RL`), fetched once from the SPDX licence list at a pinned version with its checksum recorded (`just licence-texts-fetch`, through the GitHub contents API the dependency tooling already uses) — under a line saying no licence file was copied from it.

**The generated file is dependency-authored text and is treated as dependency source.** It is a build output, never tracked, and no session opens it or the cached licence files; a session reads the generator's verdict lines only — the component count per ecosystem, the files copied, the fallbacks, the files left out, the ids refused — and every test asserts on those lines and on the file's structure ([`release-integrity.md`](release-integrity.md) § Reviewing untrusted source without being subverted). The header, the entry labels and the closing section's sentences are the generator's own wording and a public text ([`public-texts.md`](public-texts.md) § Exemptions).

**What holds it in place:** the generator's unit tests over fixture closures; per channel a tier_1 authoring test that the packaging source stages the three files where § Per channel says; the workflow-shape test's asset list for the release assets; and the cheap gate `shipped-notices-check` (`just shipped-notices-check`, on both merge scripts): every id in `deny.toml`'s allowlist has its fallback text, matching the checksum `SOURCE.toml` records, every artifact in the manifest names a row of § Per channel verbatim, and every exception carries a reading.

## Build order

The generator, the manifest and the fallback texts first; then each channel, the Windows MSI's first since the gap was found there; the generator's wording and the Windows licence page's sentence about where the texts are go through a public-texts request beside the MSI's.
