### The hosting service's dependency alerts (owner-ruled 2026-10-03)

**Ruling (the owner's): the hosting service's dependency alerts (Dependabot alerts) and its opt-in alerts for reported-malicious packages are ON for every repository of the project; its security updates and version updates are OFF.** The alerts are an **alert, never a gate**: `cargo audit`, `govulncheck`, `cargo vet` and `cargo deny` stay exactly as they are. What the alerts add is an alert when an advisory is published instead of at the next scheduled cron (up to seven days when this was ruled; up to one since the schedule went daily on 2026-10-04), and the reported-malicious-package feed for Go and npm, which `cargo audit` does not read; they add no new third party, since the code is already hosted there. The update features stay off because they open pull requests on branches, while this project lands only by fast-forward to `main`, and because a bot proposing versions nobody has reviewed works against both the dependency review sandbox and the minimum release age above. **An alert nobody reads is the inert scanner of 2026-07-17 again** (the note at the top of this section): where the alerts are read, and by whom, is recorded here when the setting is switched, and until it is, the ruling is not implemented. **Switched on the private repository 2026-10-04, and the reader is the owner:** the alerts go to the organization's administrators, which is the owner, in the hosting service's own alert view and notifications; nobody else is on the access list. The public repository gets the same switch once it is public, read by the same person. **`deno.lock` entries raise no alerts (measured 2026-10-04, the day the alerts were switched on):** the hosting service's dependency graph for the private repository holds 13 npm packages — exactly the direct dependencies the two tracked `package.json` files name (11 for `apps/fauna-web/`, 2 for `sites/fauna-social/`) — and none of the transitive packages the two `deno.lock` files pin (121 and 341 locked npm entries); neither lockfile has a JSR entry. So for the web trees the alerts watch the direct dependencies only, at the range the `package.json` states rather than the locked version, and the locked npm closure is watched by nothing here: `cargo audit` and `govulncheck` do not read it. **Owner-ruled 2026-10-04: the locked npm closure is checked for known vulnerabilities too** — the standing check is the next subsection. Not adopted, and recorded so nobody re-opens it cold: connecting a third-party scanner App to either repository — a new third party on the repositories is the owner's call under the dev-machine rules, and it was not made.

### Go modules: reachable and module-level (owner-ruled 2026-10-05)

**Ruling (the owner's): every tracked `go.mod` is checked at module level as well as at symbol level, and a module-level finding is fixed by a bump or recorded as an owner-approved exception — never left as an alert nobody grades.** `govulncheck` in its default mode (`just mail-bridge-vulncheck`, the runner's `govulncheck` job) reports a vulnerable module only when our code reaches its vulnerable symbols; the hosting service's alerts report every vulnerable version a `go.mod` pins. On 2026-10-05 that gap was 52 open Go alerts our scans had never named. So the module-level check runs `govulncheck -scan module` over every tracked `go.mod` — the scanner already vetted for the symbol-level scan, so no new third party — and grades the findings against `supply-chain/go-module-exceptions.toml`, whose discipline is the npm exceptions' own: one entry per (module, advisory, package), our own reasoning (for Go, that the symbol-level scan finds no call path into the affected code), each approved by the owner individually, and an entry that matches nothing fails the check. **It runs as the third half of the daily `dep-advisory-check`** (§ *The scheduled scans run daily*), so its red lands in the janitor queue. **Module mode follows the starting package's imports, not the whole `go.mod`** (measured 2026-10-05 on the bridge: started in `cmd/fauna-mail-bridge` it missed an otel advisory that `cmd/fauna-atproto-bridge` reports; a module root without Go files fails, and module mode refuses a package pattern), so the check scans from every directory holding the module's own Go files and unions the findings — about a minute once the scanner is cached; it compiles no package of ours. **It also reads the Go vulnerability database, which is fuller than the hosting service's feed for Go:** on 2026-10-05 it named `x/crypto` fixes up to 0.56.0 where the alerts said 0.52.0, one `x/crypto` advisory with no fixed release, and an otel advisory the alerts never raised. The symbol-level scan stays the gate on reachability; the module-level check is what keeps the alerts and our own scans saying the same thing.

### Swift packages: our own check against OSV.dev (owner-ruled 2026-10-05)

**Ruling (the owner's): every tracked SwiftPM `Package.resolved` is checked for known vulnerabilities by a check of our own that installs nothing.** Until 2026-10-05 only the hosting service's alerts read the Swift pins. The options weighed: a script of ours against OSV.dev's query API; the same against the hosting service's advisory API (ties the check to an authenticated client, and OSV.dev already carries those advisories); a third-party scanner that parses `Package.resolved` (Trivy, or OWASP dependency-check, whose SwiftPM support is experimental) — new software on a dev machine, each its own install decision, and none covering more. So the Swift check reads each file as JSON and asks OSV.dev's batch query API (ecosystem `SwiftURL`) about every pinned version, grading the answer against `supply-chain/swift-audit-exceptions.toml` with the same exception discipline as npm and Go. No tracked file at all is a pass, not an error: SwiftPM writes no `Package.resolved` for a package that pins no remote dependency, the Apple package's state since 2026-10-08; an exception still recorded then fails, since it can match nothing. The batch answer carries advisory ids only, so no advisory text reaches the check; a branch or revision pin cannot be looked up by version and fails as unversioned rather than reading clean. It reads JSON only, so it runs on any machine — the macOS app's pins are checked on Linux without building it. It runs daily as the fourth part of `dep-advisory-check` ([`merge-gate-catalog.md`](merge-gate-catalog.md), 30th gate).

### Dev tools: the inventory and its daily check (owner-ruled 2026-11-10)

**Ruling (the owner's, 2026-11-10): the tools Fauna is built WITH are checked for known vulnerabilities in every daily scan, like the packages it is built FROM.** The owner's words: "Plese make sure tools like uv, python etc are also considered in each security scan round." Until that day every check read a lockfile, and nothing read the machine: uv, the Python interpreter, Deno, the Go toolchain, the cargo-installed helpers and the operating-system packages a build calls were installed once and never looked at again.

- **The inventory is tracked.** One entry per tool and machine: where its bytes came from (the channel), how its installed version is read on that machine — its own version line, or dpkg for an operating-system package — and under which identities the advisory source knows it; where no package manager owns its files, also the commands and install prefixes that are its, so every program a recipe runs on a machine is owned by a package or an entry. A tool added to a machine is added to the inventory in the same change ([`dependency-bump-report.md`](dependency-bump-report.md) § No new software without a review). An entry with no identity yet says why and is printed as unscanned at every run, so the gap stays in sight. **Built 2026-11-10:** an entry also carries the typed source its channel is read through (set where the channel text makes the kind certain — the distribution's packages, the crates.io helpers, pytest — the rest read as `other` until a round types them), the version a round reviewed (written only by the round tool's `installed` step) and, for a tool decided but not yet installed, an awaiting mark the check prints instead of reading a version; a reviewed version the installed one differs from is a finding, an operating-system package exempt. A tool a tracked workflow installs on a runner is an entry of machine `ci` carrying `pin_file` and `pin_re` in place of a version command: its version is the one capture of that pattern on its line in each file, read where the daily check runs on Linux, and no line naming one is the finding `unpinned`. An entry whose identities also cover a toolchain, action or image pin names it (`pin`), so the bump report can ask about that pin's rows. What reads and writes them is [`dependency-bump-report.md`](dependency-bump-report.md) § The report → *The tool report*.
- **The check is the sixth part of the daily one.** It reads this machine's entries, reads each installed version from the tool itself, and asks OSV.dev in one batch — the source the Swift check already uses, which answers for PyPI, crates.io, Go, the distribution's own notices and a project's release tags alike (measured 2026-11-10). It installs nothing. Its verdict joins the daily one, its findings go to the Security page under the tool's name, and a finding asks what every finding asks: a queued need for the tool, decided in a round.
- **How it grades.** An advisory against an installed version is a finding unless an exception records that tool, machine, id and version with a reason; an exception matching nothing is a finding. **An exception at a queued tool need's target is PENDING, not stale (built 2026-11-13):** the owner's acceptance of a move whose newest release still carries an advisory no release fixes can be recorded only at the target, so an entry whose tool, machine and version equal a queued tool need's wanted version, while the tool is graded at another version, is printed as pending, naming the need, and is not a finding; the tool report grades the target by it — the advisory named on the row as accepted, never RED — and it is an ordinary exception once installed, a finding again if the need goes or is re-targeted first. A version that cannot be read is a finding, an unreachable source leaves the tools unverified, never clean. **An operating-system package is graded on its vendor's fix:** the distribution lists every CVE it tracks, fixed or not, so an id with no fixed version in this release is counted on one line and is not a finding — nothing could be installed — while an id WITH one means the machine is behind its vendor's updates, and is. Every installed operating-system package is graded so, not only the ones the inventory names (its `os-packages` entry, one line per package behind a fix). **Each finding names the release that fixes it (built 2026-11-12):** the `fixed` version closing the range that holds the installed version; `none` when that range is open; and for a tool known by its repository's tags (the interpreter, ffmpeg) — whose records carry commit ranges, not versions — the lowest release of the repository newer than the installed one that the record's enumerated versions leave out, a release of the installed series before a newer series, since that is the release the advisory source itself answers unaffected; `none` when the commit range has no end, `unknown` when the record enumerates no versions or the repository's tags cannot be read. **A tool whose module is versioned apart from its releases is asked at the module's own release (built 2026-11-12):** the Docker 29 engine is the Go module `github.com/moby/moby/v2` at `v2.0.0-beta.N`, while `github.com/docker/docker` stopped at the 28 series and every later record lists it open with no fix — so asking that frozen module about the engine read five fixed holes as `fixed none`. Such an identity names the repository, its release tag and its module tag prefix, and is asked at the module tag on the commit of the installed release's own tag, or — a release with none of its own — of the newest final release of its series at or below it that has one, an older module release that can only overstate what is open; no such release is a version that cannot be read. **A repository-keyed record with no fix event is open at every later release, whatever its enumeration says (built 2026-11-13):** the advisory source answers such a query by the releases the record enumerates, and a record last enumerated before the installed release was tagged leaves it out though nothing fixed it — PSF-2026-38, enumerated to 3.14.7 on 2026-08-25, read the interpreter's 3.14.10 as unaffected. So a repository identity at a point release is asked a second time at its series' first release, and an id only that question answers is a finding, `fixed none`, when its record's commit ranges have no end event; any other id only that question answers is dropped, the source's own answer standing — it can only overstate what is open. (The session's shape, refutable.)
- **Every machine's tools, through the fleet (owner-directed 2026-11-10: "extend the tools check to win and mac too - make them report their tool versions through the fleet").** A machine other than the one the daily check runs on reads its own inventory entries and sends the versions to the fleet broker at every pass of its own check: per tool its name, the version read and the advisory-source queries that ask about it — typed fields only, a report carrying anything else refused whole. The daily check reads the reports back and grades all three machines in one pass, each finding under `<tool>@<machine>`. A machine with inventory entries and no report, a report over 48 hours old, and a tool its report could not read or does not carry are each a finding; a machine with no inventory entry yet is printed as such at every run.
- **Only typed fields are read:** advisory ids and their aliases, each record's `modified` stamp, versions and a record's range events — never its summary or details.

### The scheduled scans run daily (owner-ruled 2026-10-04)

**Ruling (the owner's): every scheduled dependency scan runs once a day; it was once a week.** A scan on a push sees a bump that brings a vulnerable version in. What it cannot see is an advisory published against versions already locked, where nothing in the tree changed — only a schedule catches that, and a week was judged too long for a published hole to go unseen. So `supply-chain.yml`'s schedule is daily, and every job that answers to it runs daily: `cargo-audit`, `npm-audit`, `cargo-vet`, `cargo-deny`, `vendored-forks`, `image-currency`, and `govulncheck` — whose roughly eight minutes on the shared host were put to the owner and accepted. The push-time scoping is unchanged: `govulncheck` still scans on a push only when Go module files moved. **The advisory audits that build nothing also run daily on Linux** — `cargo audit --deny warnings`, `dep-npm-audit`, `dep-go-module-audit` (Go at module level) and `dep-swift-audit`, as the merge-gate check's `dep-advisory-check` ([`merge-gate-catalog.md`](merge-gate-catalog.md), 30th gate) — because a red on the runner reaches nobody, while that gate's red lands in the janitor queue every session triages at startup; an unreachable advisory source reads INFRA there, never green. `govulncheck`'s symbol-level scan stays on the runner only.

### The locked npm closure — a known-vulnerability check over every `deno.lock` (owner-ruled 2026-10-04)

**Ruling (the owner's): every npm package a tracked `deno.lock` pins — direct and transitive — is checked for known vulnerabilities.** The two Deno trees are the web app (`apps/fauna-web/`) and the project site (`sites/fauna-social/`). Neither `cargo audit` nor `govulncheck` reads their lockfiles, and the hosting service's alerts see only the direct dependencies each `package.json` names (the subsection above), so before this check the locked closure was read by nothing.

**Mechanism.** `dep-npm-audit` runs Deno's own `deno audit --frozen` in every directory that tracks a `deno.lock` — found from the index, so a new Deno tree is covered without anyone listing it — and grades what the scanner reports. It is the npm sibling of the `cargo-audit` and `govulncheck` jobs and runs beside them as `supply-chain.yml`'s `npm-audit` job: on the daily cron, on dispatch, and on every push to `main` or pull request that touches a `deno.lock`, `deno.json` or `package.json`. Like its siblings it is post-push detection on the self-hosted runner, not a merge blocker, and a red job is the check working. The scanner sends the locked package versions to the registry's advisory endpoint and installs nothing; `--frozen` keeps it from rewriting a lockfile. It is a scanner over a lockfile, so it carries no source-reading exposure; the advisory titles it prints are third-party text, and the wrapper prints only each advisory's id, package, severity and vulnerable range.

**Exceptions are recorded, never implied.** The scanner exits non-zero on any advisory and its own ignore option takes CVE ids while it reports GHSA ids (measured on Deno 2.7.14, 2026-10-04: a GHSA id passed to it suppressed nothing), so the wrapper carries the exception list: `supply-chain/npm-audit-exceptions.toml`, one entry per tree, advisory id and package, each with its reasoning and date. An advisory is closed by moving the lockfile to a fixed version inside a round the owner opened ([`dependency-bump-report.md`](dependency-bump-report.md) § Who opens a round; until then the advised package waits in the queue) — inside the minimum release age above, or through its security-fix bypass. An exception is for an advisory that cannot be fixed yet and whose vulnerable code is shown not to run in anything this project ships or builds; "the site is static" is a starting point for that showing, not the showing. The check fails on an advisory with no exception, on an exception that matches no reported advisory (it is removed, so it cannot cover a later one), and — exit code 2 — whenever the scanner did not run or printed something the wrapper cannot read, so a registry outage never reads as a clean tree. The wrapper's own unit tests hold those three behaviours.

**Scope.** Known vulnerabilities only: like `cargo audit`, it says nothing about a malicious version no advisory names — that is the minimum release age's job, and the dependency review sandbox's. Reachability is not computed (unlike `govulncheck`, which reports only reachable Go vulnerabilities): every advisory that matches a locked version is reported, including ones in server-side or dev-server code a static build never runs, which is what the exception list is for.

### The release attempt's advisory reading (owner-ruled 2026-10-17)

**Ruling (the owner's, 2026-10-17, taking the recommendation): a publication's audit reads a PINNED advisory snapshot for the attempt, and a new advisory is TRIAGED, not failed on.** Measured on 0.1.4: five registry events in 60 hours (two advisory batches, three yanks or withdrawals with no advisory) each forced a dependency move, an owner round, a new source and a full regrade, although no public CI run ever failed on a vulnerability and neither advisory batch was introduced by the release. The mechanism:

- **The snapshot.** At attempt start the attempt record pins a commit of the RustSec advisory database (and the dates of the Go, npm and OSV readings); the audit's gate run — locally and on the runner — reads that snapshot (`cargo audit --db <checkout> --no-fetch`, the commit a dispatch input of `supply-chain.yml`), so the local reading and the runner's are one reading and the attempt never goes red on a database change alone. The daily scheduled scan keeps fetching the newest database: it is the detector, the pin is for the gate.
- **The delta.** Before the squash-merge one fresh-database read is taken, and every advisory it adds over the snapshot is triaged: **an advisory against a crate version the release INTRODUCES — absent from the previous public release's lockfile — stops the attempt**, the boundary this section exists for; **an advisory the previous public release already carried does not stop the release** — it is a queue entry, and the fix rides the next train — **unless it clears the severity bar.**
- **The bar (owner-ruled 2026-10-17; re-ruled the same day, widened from the nest and read at the vulnerable code):** an advisory that is network-reachable (CVSS `AV:N`) with high integrity or availability impact, whose vulnerable code a shipped artifact — the nest, any of the 7 apps, the mail bridge's FFI library, the web bundle — links AND feeds untrusted input, holds the release for a round when the advisory names a fixed version, and otherwise ships with a patch train opened the same day. Everything else ships and queues. The vulnerable crate sitting in an artifact's dependency graph is only the tool's pre-filter: it makes a `HOLD` provisional, never final, until the reach reading below settles it. The same triage applies to an advisory already in the attempt's pinned snapshot as to one the fresh read adds: carried and below the bar, or carried and not reached, is a note and a queued need, never a red; only an advisory against a version the release introduces stays a red (`STOP`).
- **Reach is read at the vulnerable code (owner-ruled 2026-10-17).** No linked symbol of the vulnerable code in an artifact means not reached, whatever input it takes; linked code fed untrusted input means reached; linked code fed only trusted input is a reading that names its call sites. The research is a dedicated reach pass ([`dependency-bump-report.md`](dependency-bump-report.md) § The whole-effects analysis → *Advisory reach*): which code the advisory names comes from its `affected.functions` field when present, else from its title or CVE alias at most, never from the dependency's source (§ Reviewing untrusted source without being subverted); our own call sites by `rg`; a third-party path by the symbol table of an unstripped build of each shipped build command — same packages, features, profile and target as the artifact — beside a positive control (a crate of ours calling the vulnerable function, built the same way, whose object shows the symbol). A small or `#[inline]` function, which leaves no standalone symbol, is read with the nightly's `-Zprint-mono-items` instead. Symbol names are dependency-authored text: the output is grepped for the expected path and never paged. A build-script or proc-macro use is build-machine exposure, the bump report's Runs column, not artifact reach. What the pass cannot settle goes to the owner as an open question.
- **A not-reached finding is an exception entry, and it ships before the owner reads it (owner-ruled 2026-10-17).** It is recorded in `supply-chain/cargo-audit-exceptions.toml` — which replaces `.cargo/audit.toml`'s id-only ignore list, in the Go and npm exceptions' shape (§ Dependency verification, the module-level Go ruling): one entry per (advisory, crate, version), with the reasoning, structured evidence (artifact, build command, object checked, symbol grepped, call sites), the recording session and model, and the lockfile hash it was read at; the daily check, the runner and the release read the same file, and an entry that matches nothing fails the check. Only such a reach pass writes an entry, and the tooling refuses one without its evidence fields. The release ships on it; the owner reads every new entry in that session's halt message and in the attempt record, and may revoke it, which turns it back into a `HOLD`. An entry is void when its crate version moves, the lockfile changes the features of a crate between us and it, or a new call site of the crate appears; a void entry is read again before the next release. On a recorded entry the session dismisses the matching Dependabot alert citing the entry, when its token may; otherwise that dismissal is the owner's click, named in the halt. The first case under it: RUSTSEC-2026-0367..0369 against `zip` 2.4.2 and 8.6.0 name only `extract`, which our code never calls (the nest's DMARC-report ingestion reads entries into memory), and a test binary linking `c2pa`'s `Reader` held no `zip` symbol at all — not reached on that build; the linux app's `c2pa` build, which adds the `file_io` feature, was read separately the same day and holds no `zip` extraction symbol either (§ Implementation status today).
- **The delta grades what the release ships, never the dev machines' own software (2026-11-10).** The daily check's dev-tool part — the tool inventory and the OS-package sweep — reads the build machines, not a lockfile an artifact is built from: build-machine exposure, as a build-script use is (the reach bullet above). The release delta leaves those findings out and prints only their count; the daily check, the Security page and the Security objective own them. Measured: 0.1.6's tag met 553 UNGRADED lines on `curl@mac` and Ubuntu packages the day the tool part joined the check's wrappers.
- **The delta reads the attempt's tip against the release before it** — never the checkout's moved dependency files, never the release itself after its merge; [`release-attempt.md`](release-attempt.md) § The release attempt, step 6, owns when and of which tree.
- **Hygiene never stops a release.** A yank or withdrawal with no advisory, a stale exception entry, an `unmaintained`, `unsound` or `informational` advisory are notes in the attempt record and queue entries; the daily `dep-advisory-check` and the scheduled workflow keep `--deny warnings` and grade them red on `main`.
- **The advisories themselves are data, cached.** Every advisory a tracked lockfile meets — its facts as the source states them, at the revision read, beside our reading of it with the revision that reading was made against — lives in the advisory cache, refreshed by tooling and checked for drift daily and at the attempt; owner [`advisory-cache.md`](advisory-cache.md).

What is built: the snapshot, the attempt record, the delta and its triage, wired into `pr`; and since the same day the re-ruling — the exception file, the widened bar, the snapshot's own triage and the reach pass's symbol check (§ Implementation status today).
