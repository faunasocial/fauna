## Why this doc exists

**Ruling (the owner's, 2026-10-15): information about Fauna outside the apps changes only through one process — a request to change it, a review that reads the request against every other public text and the code, and a round that lands every approved change together on the owner's go-ahead.** The owner's direction: create a general text reviewer responsible for keeping all publicly available information consistent with each other and with the code, taking inspiration from the dependency bump round ([`dependency-bump-report.md`](dependency-bump-report.md) § Who opens a round) — a request, a review in the context of everything else that is public, and a round in which all public information is updated together instead of piecemeal.

**Re-ruling (the owner's, 2026-11-12): a round is a tool, not an impediment, and the fleet opens it.** The owner's words: "Enough rounds should always be open. We design the trigger for the round to be open, and that trigger is if it needs to be open to achieve an objective. 'The round' is a tool, not an impediment. Rounds should be done each night and added to the ask, and public texts should be checked before every release and/or as part of the release." This replaces every sentence of this document that makes the opening of a round the owner's in-the-moment word: a round is open whenever an objective needs one, the fleet runs a round each night and puts what the owner must read or decide on the owner's asks, and a release checks the public texts before it or as one of its own steps. What the owner keeps is what the round's content needs from them (§ The round), never the opening. The details were designed the same day: § The round (the trigger, the night's close, what reaches the owner) and § The release's check (§ Rulings, 24).

**The measured cause.** Public texts about Fauna had been written here and there, each by one session with the view of its own task and no view of the whole: a privacy page brought back for a store submission, a terms page drafted for another, two store listings, review notes, a code-signing policy, guides, a public README, a trademark policy, catalog pages, the text the nest serves at its root, the body of a GitHub release. Each makes claims about the product that the others also make, in other words, and no reader ever saw them side by side. The first draft of the terms page had, in the owner's reading, a number of problems its authoring session could not see — not because the session was careless but because the frame was one page, and the problems were between pages and between a page and the code. One inventory, one review that reads it whole, one landing: that is the only shape in which "consistent with each other and with the code" is a property anyone can check.

## The rule — in force since 2026-10-15

**Every change or addition to a text the public reads about Fauna outside the apps is a request (§ The request), reviewed against the whole inventory and the code (§ The review), and landed together with the other approved requests in a round, which the fleet opens whenever a landing needs one (§ The round). No session writes or changes a public text on its own, whatever its task needs** — a store submission, a release, a guide for a feature it just shipped. The session files the request and goes on without it: its dependent work waits on the request, never on a shortcut. The one place a public text is written outside a round is a *draft* — a new text's first wording, written into its source file by the requesting session so the reviewer has something to read; a draft is not published, not deployed, not entered into a console and not wrapped into a page until its round. Where every session reads its rules the rule stands as a short iron-clad naming this doc.

## The boundary — what is a public text

**The test, in one sentence: a text about Fauna, written or chosen by a human, that a person who is not signed into a Fauna app can read, and that the organisation publishes, serves or submits.** Three words carry it. *About Fauna* — it makes claims about the product, the organisation or how to get, check or use the software; a licence text or a third-party notice is public but says nothing about Fauna and is a frozen record (below). *Written or chosen by a human* — generated output is not a text, its generator's wording is (§ Exemptions). *Not signed into an app* — a visitor, a store reviewer, a package-page reader, a person a nest's public page reaches; what a user reads inside an app is the apps' own string (below).

**Classes, by how the text reaches its reader.** Every public text is in the tree — a text only ever entered by hand into a console or a form is drafted in the tree first, and the inventory names its source file.

- **Published by a pipeline from the tree:** the site's pages (`docs/sites/fauna-social/*.md`, rendered at build time by `sites/fauna-social/`) and the site's own chrome (navigation labels, the footer, the not-found page); the public repository's root texts — the README, the trademark policy, the contributing guide, the code of conduct, the security policy — and its docs landing page (`docs/README.md`); the user guides (`docs/guides/`); the catalog pages' hand-written prose (`docs/features/`, [`feature-catalog.md`](feature-catalog.md) § The page format); the prose fields of the official-apps list (`installer/official-apps.json`, rendered on the site's official-apps page); the HTML the nest binary serves to anyone — its root page, its built-in not-found page, the paywall doors, the authorization-consent pages, a public folder's listing; the body text the release workflows write into every GitHub release; the Linux software-centre listing (the AppStream metainfo's summary and description) and the installer descriptions a Windows setup shows. **A site deploy publishes every site text at once**, at every version's sync ([`product-version.md`](product-version.md) § Bumping), so it refuses while the build would wrap a site text still in draft — an inventoried source under the site's trees or the official-apps list whose entry is `drafted`, or whose newest change landed as `Public-Texts-Round: draft` — and lists the open requests naming a site source for the owner to read before the GO. **The public repository sync withholds a draft member's WORDS, never the member (2026-10-23; reshaped 2026-10-28 by the design task, advisory, the owner may overrule at the version sync's presentation)**: the guides and catalog pages ship whole with every sync, so a draft written into either tree would reach the public before its round — and its tree's entry is `live`, and a round may land a passage inside a draft member, so neither the entry's status nor the member's newest commit can see it. A member's draft is therefore recorded per file, in its `[[tree]]`'s `drafts` list in the inventory: the draft commit that writes a member lists it there, only the numbered round approving the member takes it off (or a commit deleting the file), and the merge gate refuses either half done otherwise. Until then the sync ships the member with its **text regions** replaced by the tree's fixed placeholder — the regions are what the merge gate gates in the member, the file less its exclusions and its generated regions: the whole file of a guide; a catalog page's `title` and § What a user gets, its front matter, coverage contract and status block untouched — and every **render** of those words carries the same placeholder from the render itself ([`feature-catalog.md`](feature-catalog.md) § Render: `matrix.json`'s `title` and `what`, `MATRIX.md`'s row label), so the site's features table, which imports the committed `matrix.json` at the sync commit without passing the transform, shows it too. The placeholder is one shape for every tree: the member's file stem where a title stands (a catalog page's slug, which already ships in its tests, its matrix link and the surface registry), and one fixed sentence saying the text is being written where a body stands. It is the publishing tool's own text, like the draft pull request's fixed placeholder title and body ([`publish-gates.md`](publish-gates.md) § The release attempt), not a text about Fauna, so it is no request; the owner reads it where the sync's presentation shows what the sync publishes. The 2026-10-23 shape deleted the member instead, on the premise that a guide is a whole file nothing else needs — measured false on 2026-10-28 for both trees: a shipped test's `@pytest.mark.feature` marker names a catalog page's slug and makes the shipped suite uncollectable without the page (seven tests, three pages, the 0.1.6 sync refused at the grade); the committed matrix carried the three pages' titles and leads verbatim, so the file's deletion withheld nothing; and the docs landing page and a sibling guide linked the withheld AI-assistant guide, two dangling links. Withholding the words keeps the tree's referential integrity — every slug, link and marker resolves — and withholds exactly what the round has not approved; withholding the referrers too would rewrite shipped test source and leave the catalog inconsistent, and an authoring rule that lands a draft page without markers or outside the render would cost the ledger the draft period's records and fight the catalog's own rule that a page and the markers naming it land in one commit. A member already public when it is listed keeps its file and loses its words at the next sync. One reading of "still a draft" serves both publish paths: a per-file record, an entry `drafted` with no round's approval, or (where the path reads history) a newest change landed as `Public-Texts-Round: draft`.
- **Submitted by hand into a console or form, from a draft in the tree:** the three stores' listings and their review or certification notes; the contact details a store publishes ([`installers/store-listing-contact.md`](installers/store-listing-contact.md)); the hosting service's organisation and repository descriptions and the container package's page; the code-signing foundation's application. For every one of these **the readback rule applies**: the text is landed only when it has been read back from the console or the live page and the reading recorded ([`installers/store-listing-contact.md`](installers/store-listing-contact.md) § The readback rule, which owns it).
- **A class with its own rule — the public commit messages.** Every permanent commit message on the public repository is public text, presented to the owner verbatim and approved before it exists anywhere public ([`release-attempt.md`](release-attempt.md) § The public-repository gates → *Every permanent public commit message comes from an approved summary file*). That rule is older and stricter than the round, and stands: a sync summary is never queued for a round. Since 2026-10-17 it is one go per version: a minor later modification of an approved summary needs no new go. What this doc adds is that its author writes under the review's checklist (§ The review) — the same claims, the same words, nothing the code does not back.

**Excluded — and why.**

- **The apps' own strings — except the marked public subset (ruled 2026-10-15, § Rulings, 5).** What a signed-in user reads inside an app is product UI, owned by the UI spec and changed under its own rules ([`../ui/README.md`](../ui/README.md)); the catalog is about 1,200 strings that churn with every feature on all 7 apps, and a "Save" label says nothing about Fauna. But the boundary test reaches inside the app at three points: a prospect who installed the app reads the welcome, sign-in, recovery and onboarding screens before they are a user; a store's reviewer runs the app, and the kids app's certification turns on what its screens say; and a listing's screenshots publish those screens a second time. So **a declared subset of `i18n/strings/en.yaml` is a public text**, marked in place with `public-text:` regions exactly as the nest's served strings are, under a three-fold inclusion rule: **(1) every string shown before sign-in** — welcome, sign-in, recovery, onboarding, about and legal screens, by-continuing notices; **(2) every string that states a property, guarantee or policy of the product** — encryption, who can read what, data control and deletion, retention, spam handling, paywall and pricing statements, the kids app's age and safety claims; **(3) every string that names or links a public page.** The unmarked remainder of the catalog, and `ui.yaml` itself (ids and per-page scope, not sentences), stay the UI spec's. Ownership under the one-owner rule is unchanged: the goal doc owns the claim, `ui.yaml` the element and its presence, and the marked string is a text making the claim, as a site page is; it still lands through the apps' own path (`en.yaml`, then the generated constants), under the round's trailer. Another locale, when one exists, is a translation the review may correct, as it may the bylaws' English. **The companion rule** stays as the net for a string not yet marked: an app string that makes a claim a public text also makes rides along in the request *for review*, so the words agree, and — if it meets the inclusion rule — is marked in the same round. The review covers it; the UI spec still owns its element. **The cli app's answers are the same subset, by the same rule (decided 2026-10-19 by a request's review).** The cli has no string catalog: its answers are Rust constants that a connected assistant relays to the human ([`apps/cli.md`](apps/cli.md) § The device shell). So an answer string meeting the three-fold rule is marked in place in its Rust source with `public-text:` regions, as the nest's served strings are, under its own inventory entry. The rest of the catalog's text (tool descriptions, schemas, claim-free errors) stays the cli's own, as an app's unmarked strings do.
- **The nest's messages to its own users** — notification mails, alerts, API error strings — are product output to a person inside the product, owned by the feature's goal doc.
- **The shipped spec under `docs/goal/`** — engineering text under its own protocol (one owner per claim, the registry, the lint), ratified doc by doc by the owner; its reader is a contributor, not the public the owner's direction names. **Ruled 2026-10-15 (§ Rulings, 1): excluded;** the spec's public-facing summaries — the docs landing page and the README — are inventoried whichever way it goes. The catalog pages' **coverage contracts** follow the same decision: each item is a goal-doc claim transcribed with the tests that witness it — "the contract *is* the goal section" ([`feature-catalog.md`](feature-catalog.md) § The page) — extended by the session that lands each test, so it is excluded with the spec while a page's own prose (its title, its lead, § What a user gets) stays the text.
- **Code, comments and tests.**
- **Generated output** — the rendered catalog matrix and its data file, the catalog pages' status blocks, the third-party notices, the official-apps identity tables, the sitemap: § Exemptions.
- **Archived copy** — a site edition that lost its bake-off, a superseded page — is not published.

**Frozen records — inventoried, consistency-checked, never requested.** The association's governing documents (the bylaws in Norwegian and their English translation, which the site renders from `docs/governance/`) change only by the association's own procedure; the licence texts are standard. The review checks that no other text contradicts them — the site's copy constraints already forbid overclaiming the bylaws — and may request a correction to the *translation*, never to the record.

## The inventory

**One tracked file lists every public text.** Per text: an id; the source file; where it is published or submitted and by what mechanism; its audience; the goal docs that own the claims it makes; the claims themselves, each with its owner doc; which other texts make the same claims; its status (live, drafted, not drafted, empty, frozen record); and **when and in which round the owner last approved it** — `unrecorded` for everything approved before the process existed, which on 2026-10-15 is every text. A tree of uniform texts (the guides, the catalog pages) is one entry with a glob and the regions a generator owns; every file under it is inventoried by construction. A table of **exclusions** names each path the boundary leaves out and why, so the completeness check (§ Enforced, never trusted) has a complete answer for every file under an inventoried tree.

**Who writes it.** A request names the entry it changes, or adds the entry for a text it introduces; the round writes the approval fields when it lands; the first consistency round (§ Implementation status today) enumerates the claims the first cut left blank. Nothing else edits it — an entry's approval date is a record of the owner's word, not of a session's opinion.

## The request

**What a request carries:** the text or the change (a new text's draft lives in its source file; a change is the diff or the sentences, before and after); the publish path — which pipeline, which console field, which page; why — the need, the submission, the release, the correction; **every claim the text makes about the product, each with the goal-doc section, or the code, that makes it true today**, and for each claim the other inventoried texts that make it too; the companion app strings, if any (§ The boundary); and the inventory entries it touches.

**Who files one, and where.** Any session, in the one queue, serving the version task of the release the text is for, else the objective target of the task that needed it (the closure invariant, [`fleet-scheduler.md`](fleet-scheduler.md) § Objectives, rule 2; owner-ruled 2026-11-08). A request is never landed by its author: the session that wrote the draft has the view of one task, and the review exists to supply the other.

## The review

**One session, never the request's author, reads the request against the whole inventory and the code, and either amends the text until it passes, or refuses the request with the reason.** The review is a pickup of the request's task like any other — judged before it is claimed, by a mind that is not the executing one — and the reviewer's weight follows the text (ruled 2026-10-15, § Rulings, 3; the mechanism ruled 2026-10-20, § Rulings, 18): the session on the queue runs at opus whatever the task's tag, and for a legal-adjacent text (terms, privacy, a policy, anything a store's or an authority's reviewer reads) — the task tagged `fable`, with its `**Fable because:**` reason — that opus session dispatches the review pass to a fresh read-only fable reviewer and acts on its findings; a guide, a catalog page or an app string is reviewed at opus, the ordinary weight, and may not carry the fable tag. The checklist, every item of which is a pass or a named failure:

1. **Every claim is true today.** Each claim the request lists cites the goal-doc section that owns it, and that doc's implementation-status section agrees that the mechanism is built as described; a claim about target state is written as one ("will", "is planned") or not at all. A claim no goal doc owns is checked against the code and the owner doc is amended first — a public text never becomes the only home of a fact about the product.
2. **The same claim is worded the same way everywhere.** Where another inventoried text makes the claim, the two agree in substance and, where the audience is the same, in words; where they do not, the request grows to cover the other text or the reviewer refuses it.
3. **The owner's frame, the copy constraints and the voice rules.** Nothing contradicts § Words from the owner, and the text leads with what those words lead with. The site's six corrections — never overclaim the bylaws, no trademark symbol or notice, the pre-store constraints and the rest — bind every page and, by the owner's direction, every public text that makes the same kind of claim; "software", never "platform"; the catalog's voice for a catalog page ([`feature-catalog.md`](feature-catalog.md)); user voice and visible labels, never element ids, for a guide.
4. **The publish gates' vocabulary.** A text that ships in the public repository passes the leak-check and the identifier ratchet ([`publish-gates.md`](publish-gates.md)) — no internal queue or review pointer, no dev-fleet name, no personal detail of anyone; the reviewer runs the gates' checks on the draft rather than discovering them at the merge.
5. **The frozen items.** Nothing contradicts a governing document or a licence; no legal characterisation in the project's own voice is written back in — the sentences the 2026-08-30 legal sweep took out of the shipped spec stay out by the spec's own rule ([`../README.md`](../README.md) § Writing protocol → *State mechanisms, never law*), never by a wait on anyone (ruling 20); the owner's standing corrections — recorded with the texts they corrected, in the site README and in this doc's round records — are not undone by a fresh enthusiastic sentence.
6. **The claims table is complete.** A sentence that makes a claim the request's table does not list is itself a finding: the reviewer adds it, with its owner, or strikes the sentence.

**The review's output** is the text as it would land, its completed claims table, the companion strings as they would land, and a verdict: *ready for the round*, or *refused* with the reason, or *returned* to the author for a draft the reviewer cannot repair. A ready request waits only for its package (§ Convergence), never for a round: the landing opens one when none is open (§ The round). A refusal stays on the task, citable; a returned request is re-filed.

**A question goes to the owner when it is found, never saved for the round (ruled 2026-10-17, § Rulings, 6).** Most findings are not decisions: a text that disagrees with a ratified goal doc or with § Words from the owner is corrected to match, and no one needs to read the correction for it to be true. A finding that *is* a decision — two defensible framings, a claim no ratified doc settles, a goal-doc contradiction the text cannot be worded around — is put to the owner at once, as one short question with the reviewer's recommended answer: directly in a manual session, as a `NEEDS-USER` ask on the request's task otherwise. The answer is recorded where the next reviewer reads it — in the owner doc that owns the mechanism, or in § Rulings here; § Words from the owner changes only in the owner's own wording — so no later text contradicts it and the same question is never asked twice. A request with an open question is not ready. **Inside a version round (§ Rulings, 23, 2026-10-24) the preparing session answers the question itself** — under the goal docs and § Words from the owner, taking the reviewer's recommended answer unless a ratified doc says otherwise — records the decision and its ground in the round's record and in the owner doc that owns the mechanism, and goes on; the owner reads it at the version sync and may overturn it there, as an ordinary request. Nothing inside the round waits on the owner.

## Convergence — the package that lands in the round

**Before a package lands, its texts are composed and converged by machine, within a fixed budget, so the owner reads a finished thing and never a pass (ruled 2026-10-17, § Rulings, 7; the budget ruled 2026-10-24, § Rulings, 22).** The steps, run by the session preparing the package in the queue's checkout:

1. **Compose.** Every ready request the package carries (its composition task names them), and every consistency finding on the same texts, is applied to one candidate copy of each text — one version per text, never two requests' competing drafts of the same paragraph.
2. **Converge, within the budget (§ Rulings, 22; it replaces the two-clean-passes exit of rulings 7, 11 and 21).** The package is frozen at its first pass: no request joins it after that (a late request waits for the next package), and code landing under it re-opens nothing — the composer re-words a claim the code moved, in every sentence that states it, and the closing pass reads the result. A fresh, read-only reviewer with no view of earlier passes reads against the inventory, the code, the owner docs' implementation-status sections, § Words from the owner and § The review's checklist, and reports findings only, each tagged one of two kinds: **FALSE** — a reader of the published sentence would believe something the code does not do, cited to the owner doc and the code — or **WORDING** — everything else: consistency, voice, precision, a label. Only a FALSE finding in a published sentence counts; a WORDING finding is applied and never re-opens a pass; the pack, the front file, a Why cell and a claims delta are the composer's bookkeeping and never a finding (the pre-gate checks what it can). A FALSE finding is fixed in every sentence of the package and of the inventory that states the claim, in one edit, before the next pass. The shape, single readers throughout: **pass 1**, full — one reviewer per texts file and one cross-file reader (none for a package of one file); **pass 2**, scoped — one reader over the sections pass 1 changed, with their shared-owner sections and pins; **pass 3**, full and closing — one reviewer per file and one cross-file reader; no FALSE finding in a published sentence there and the package has converged, its WORDING findings applied. Otherwise the fix is swept and **pass 4**, a last closing full pass, runs, after which the package has converged whatever it reports: its FALSE findings are applied, verified against the code by the preparing session, and listed in the round record as late fixes for the owner's eye. Four passes is the cap and is never exceeded. A finding that is a decision — two defensible framings, a claim no ratified doc settles — is decided by the preparing session under § The review's last paragraph, recorded, and never holds a pass. A package holding a legal, store or console text takes a fable reviewer in place of the opus one on that texts file in passes 1 and 3 (§ Rulings, 19 as amended); no confirmation pair follows. A claim found false after a package has landed is an ordinary request, reviewed once (§ The review); convergence is never re-run.
3. **Gate.** The publish gates' checks (§ The review, item 4) run clean on the composed package.

**A package lands when** no request in it has an open question, it has converged under step 2, the gates are clean, and every claim's owner doc agrees that the mechanism is built as the text states it. It lands under an open round (§ The round), with its digest and its texts written into the round's record; when no round is open, the landing opens one with the tool (§ The round → *The fleet opens a round, on need*).


### What convergence costs, and how it is made cheaper (design pass 2026-10-20)

Parts 1, 2 and 5 are target state under the rulings as they stand. Parts 3 and 4, and the exit question in part 5, are target state since the owner ruled them on 2026-10-21 (§ Rulings, 21). **Read with ruling 22 (2026-10-24):** wherever a part below counts passes toward two consecutive clean passes, dispatches pairs or leaves the exit open, step 2 above now governs — single readers, four passes at most; the parts stay as the record of what each mechanism is for.

**The data point.** The four packages so far took 72 to 90 passes each:
- **Theme 1:** 85 passes, 53 of them a single fable reviewer, before pairs were ruled.
- **Theme 2a:** 90 passes and about 300 reviewer dispatches.
- **Theme 2b:** 74 passes and 38 cross-file readers, about 185 dispatches in all. Each 2b reviewer read package 2a's three texts files whole, about 490 kB, to check perhaps a dozen shared sentences.
- **Theme 2c:** 72 passes and about 320 dispatches.

The tallies come from the four convergence records, and the records hold no token counts. From them come three causes and one non-cause:
- **Mechanical defects:** about a fifth of all findings needed no judgement:
  - a Before no longer verbatim;
  - a broken fence;
  - a bold label absent from the string catalog;
  - a stale anchor or line citation;
  - internal vocabulary.

  One survived 54 passes in theme 2b, until reviewers read the materialized guides rather than the package.
- **Sentences shared across packages:** about 25 findings per package, and most of the re-openings after a file or a package had converged.
- **Whole-state re-reading:** every pass re-read every unchanged sentence of its file, and of the neighbouring packages it consulted.
- **The non-cause:** late passes are not diminishing returns. In the last third of each record, 40–75 % of findings were still substantive, a claim false against the code. The bar is earning its cost, so it stays, and only the waste around it is cut.

**1. A mechanical pre-gate before every pass (target state).** Before any reviewer is dispatched, the preparing session runs one script over the composed package; a red goes back to the composer and spends no reviewer.

The script first builds a scratch tree. It folds, in round order, every earlier-landing package's After texts, then this package's, into a copy of every source the package names. A Before must be found exactly once in the tree as it stands when its task is applied. The script then refuses:
- two changes whose Befores overlap;
- unbalanced or mismatched fences, a table row with the wrong cell count, or a heading or list broken by a splice;
- a relative link or anchor that resolves to nothing in the tree as it would land;
- a bold span that is neither a value in a string catalog the inventory names — `i18n/strings/en.yaml`, the nest's and the cli's marked regions — nor on the package front file's list of emphasis;
- an italic span that is a value in such a catalog (a label is bold);
- a backticked string key that is not a key in `i18n/strings/en.yaml`;
- a companion string that does not parse or sits outside its public region;
- a `file:line` cited in a Why cell, a claims delta or a note, whose line no longer holds the text it quotes or names;
- a task whose After changed while its section's claims delta did not;
- a pinned shared sentence (part 3) that is not verbatim.

Finally it runs the leak-check and the identifier ratchet over the scratch tree, never over the live sources. These are step 3's gates, now run before every pass as well as at the end.

A red on a bold span is answered by changing the text. An addition to the emphasis list is a change the reviewers read. Whether a label is the one that screen shows stays the reviewer's check (§ The review, item 1). The reviewer's brief stops asking reviewers to hunt for what the script catalogs; a mechanical defect a reviewer still sees is reported, and is a finding against the script too. The package format the script reads is one grammar for every package: section headings `### <publish path> § <section>`, Before → After tables, and fenced long blocks.

**2. An owner pack for the per-file reviewers (target state).** The preparing session builds one table per package and keeps it current as fixes land. Each entry gives:
- a claim;
- its owner doc's file and section, with the owning sentence quoted;
- the code path and symbol where the claim is a mechanism (file and function or constant, never a line number), which the pre-gate checks exists;
- the sentences in other packages and in approved round texts that state the same claim, quoted with their location.

A per-file reviewer reads its texts, the pack and the places it cites, not the neighbouring packages whole. The pack is a map, never a verdict: it says where to look, not that a claim holds, and the reviewer verifies everything it relies on. Each pass's cross-file readers read without it: the neighbouring packages' After texts and the approved round texts whole, as today. So a claim the pack omits is still read by two fresh minds on every pass. The pack names no pass, finding or reviewer (ruling 11): it carries the state, never a report.

**3. One owner per shared sentence across packages (target state, § Rulings, 21; it changes what counts as unchanged text under ruling 7).** A sentence that two packages carry is listed once, in a pin list, under the package that owns it: the package landing first, or the approved round text it comes from. It converges there, and that package's reviewers are given the citing locations as neighbours. Every other package carries it verbatim, which the pre-gate checks, and re-copying a changed pin is a mechanical edit that does not restart the citing file's count. A citing package's reviewers still read the pinned sentence in its context and report it. The finding goes to the owner's section, whose count restarts; the citing file's count does not. **What it gives up:** a pinned sentence cannot bend to one context. Where a context needs other words, the sentence is unpinned there and composed as that package's own.

**4. Scoped passes between full passes (target state, § Rulings, 21; it amends step 2's "reads the whole composed package" for the passes that do not count).**
- **The opening:** the package opens with a full pair, two readers per texts file and two cross-file readers.
- **After a fix:** the next pair reads only the changed sections, each with the sections that share an owner with it (from the pack) and its pinned sentences.
- **The closing:** once the scoped pairs are clean, a full pair reads every file plus the cross-file read. Only full passes count toward ruling 7's two consecutive clean passes. A finding there is fixed, scoped-checked, and followed by a fresh full pair.

The stated bar is unchanged: the package converges on two consecutive clean full passes over one unchanged state. **What it gives up:** the many intermediate full re-readings that today catch an error in a sentence no one changed. That kind of finding now waits for the next full pair, so the redundancy is lost, not the bar.

Counting convergence per section was weighed and not proposed: the late substantive findings above show that a section with two clean readings can still hold a false claim, and the closing full pair is the guard against exactly that. The per-file sit-outs the three guide records used are a form of the same thing. In them, a texts file once clean was left unread while the others re-ran. A scoped pair never counts toward ruling 7; only the full pairs do.

**5. A cost ledger (target state), and no automatic exit.** Each package's convergence record opens with a ledger:
- dispatches by kind (composer, reviewer, cross-file reader);
- the subagent tokens each dispatch's completion report gives;
- the pre-gate reds;
- the passes.

The next package is judged against the data point above. Ruling 21 set no cap, because the late-pass data refuted diminishing returns; ruling 22 (2026-10-24) set one — four passes, step 2 — once the ledgers of five packages had priced the bar: 22M, 23M, 81M, 38M and 7M reviewer tokens over 71, 41, 106, 73 and 22 passes, each package one to four days, with the re-openings traced to bookkeeping findings, one claim class fixed one sentence per pass, code moving under a package held open for days, and precision refinement of true sentences. The ledger prints a `CAP` line once a package's passes reach four; the 40-dispatch report of ruling 21 is retired with the exit it served.

## The round

**The fleet opens a round, on need (re-ruled by the owner 2026-11-12, § Rulings, 24; it replaces "only the owner opens a round").** A round is opened by the round tool at the moment a landing needs one and none is open — a converged package about to land, the night's close landing one (below), the release's check landing a fix (§ The release's check) — and nothing else waits for it: `open --trigger <name>:<row>` records, in place of a word, the task whose landing needed the round, and the opening is part of that landing. No ask whose content is to open, close or approve a round reaches the owner. The owner may still open one by their word, recorded as before. **Rounds may overlap:** the day's round and a release's fix may stand open together, each commit's trailer naming exactly one open round; a correction (§ Exemptions) needs none. A round's number names it everywhere — the record, the commits, the inventory's approval fields.

**A round is a day's: opened at the day's first need, closed at the night's close (2026-11-12; it replaces ruling 23's version round, whose owner-opened start was the annoyance ruling 23 named — its other halves stand: the queue works task by task, nothing inside the round waits on the owner, a decision a reviewer raises is taken by the session and recorded).** Each package lands as it converges (§ Convergence) under the round then open, opening one if none is; a package converging across several nights lands in the round open when it lands. **The night's close:** once a day at `NIGHT_HOUR` (03:00 Europe/Oslo, best-guessed; before the daily asks' render at its own hour, so the night's declarations are on the morning's page), the broker's fleet janitor launches one opus session on the queue's checkout — the janitor's clock, as the daily asks' grader and check are launched ([`fleet-daily-asks.md`](fleet-daily-asks.md) § The daily asks → *The sessions*) — which (a) composes every ready request no package holds into the next package, so no ready request waits more than a night to start converging; (b) lands every package whose convergence is done and whose gates are clean; (c) writes the day's digest into the round's router and closes the round with the tool, which lists the corrections landed since the previous round; and (d) puts what reaches the owner on the asks (next paragraph). A day with nothing landed has no round to close. The night's close is the floor, never the only lander: a package that converges at noon lands at noon.

**What reaches the owner, and how — declarations on the daily asks, and the real decisions as asks (2026-11-12).** For every text the owner answers for personally that landed in the round — the legal-adjacent texts, every store listing and console or form text, and any text restating § Words from the owner — the night's close writes one entry to the declared ledger, class `public-text`, naming the text, the round and the record's member file that holds it verbatim, with the advisory approvals' veto window ([`fleet-daily-asks.md`](fleet-daily-asks.md) § The daily asks → *The advisory approvals*); the owner's veto mints a request task in this queue at horizon 1 carrying their words, which amends or withdraws the text through the next round. The texts had landed before the owner read them since ruling 23; the declaration moves the reading earlier and holds nothing. A question only the owner can answer — two live options that no goal doc, prior ruling or § Words from the owner settles — is a `task-ask` on the request's task, graded onto the daily asks like any ask, and only that request waits on it. Everything else lands and is reported in the round's digest. The owner still reads, at each version sync's commit-message presentation, every round closed since the previous sync, and their go there is owed in any case. What each package writes into its round's record as it lands:

- **A digest of one screen:** what changes, grouped by claim rather than by text ("'sealed' now worded one way across fourteen texts"), every owner ruling the package brings into the texts, every decision the session took in the owner's place, its passes, and its late fixes (§ Convergence, step 2, pass 4).
- **Verbatim, the texts the owner answers for personally:** the legal-adjacent texts (the terms, the privacy page, every policy), every store listing and console or form text (the owner enters those by hand), and any text that restates § Words from the owner.
- **Everything else complete** — every changed text before and after under its publish path, its claims table beside it — named by its absolute path, for the owner to read as much or as little of as they choose.

**The record stays readable whole (ruled 2026-11-05).** A version round lands many packages, and a record holding all of them outgrows what a session can read in one call (round 7's reached 185,556 B with eight days to the 262,144 B ceiling). So the round's file is a router, never the record's body: it holds the round's opening (the trigger, or the owner's word), any widening, one entry per landed package (the package's heading and a link) and the round's close, and each package writes its part — the digest, the verbatim texts, the paths, the passes and late fixes — into a member file of its own. A citation names the round file and the package's heading, which the router keeps, so it resolves however the parts are filed. A member file is one package, which convergence keeps small; one that would still near the ceiling splits on its own texts files, the same way. Rounds 1–6 closed below the ceiling and stay single files.

The owner reads the record when they choose, and the published texts at the version sync's presentation, where their go is owed in any case. A text they amend or reject at any point before the sync is an ordinary request or correction on its task, and nothing lands twice; an amendment after the sync is the next round's. The inventory's approval fields name the round for every text in it.

**Landing.** A converged package lands at once: the source files in one commit sequence carrying the round's trailer (`Public-Texts-Round: <N>`, § Enforced, never trusted); the site built and deployed and the live page read back against its landed source by a session (ruling 15), the deploy and readback carried by a follow-up task when the next deploy is not at hand (ruling 17); a store text (a listing, its review or certification notes, a TestFlight description or a build's notes) entered by the owner — the one hand that holds the consoles — at the upload of the version it describes to that store, never earlier (ruling 16), and read back under the readback rule, the reading recorded in the owning doc; the companion strings through the apps' own path. The package then writes the inventory's approval fields, naming the round, and its part of the record; the round closes at the night's close; a store text's approval field names the round at once, and its entry at the next store upload never holds the round open (ruling 16). A text the owner rejects is closed with the owner's reason on its task.

**Where rounds run.** In the queue's own checkout, on the one machine that builds the site.

**What the round is not.** It is not the public commit message's approval, which the sync that publishes the landed texts still owes separately under its own rule; it is not a goal-doc ratification — a text that needs a goal doc amended (§ The review, item 1) carries that amendment with it, under the goal-doc protocol; and it is not a node other work waits on — a task that needs a public text waits on the *request*, never on a task standing for the round, for the reasons the bump round records ([`dependency-bump-report.md`](dependency-bump-report.md) § Who opens a round → *Where rounds live*).

## The release's check — every release attempt reads the public texts against its tip (designed 2026-11-12, § Rulings, 24)

**A step of every release attempt reads the public texts against the code at the attempt's tip, and it is red like any other step when a text is false or missing.** It runs at the attempt's open on the pinned tip, beside the grade ([`release-attempt.md`](release-attempt.md) § The release attempt, step 3), publishes nothing, and so sits inside the train's 24-hour clock ([`product-version.md`](product-version.md) § Bumping) and never in front of it. Two halves:

1. **The mechanical half, no model, minutes:** the pre-gate over every inventoried text at the tip; every text the release publishes exists in the tree and was landed under a round — the release body and its known issues, the site's pages, and every store text a store leg refuses to run without ([`installers/store-review.md`](installers/store-review.md) § The store legs); no request task serving the version's objective is still open — a request whose `AFTER` line names an open task outside this queue is not that tip's (its text is true only once that code lands, which the tip lacks; decided on 2026-11-13 during 0.1.7's release, where such a request reached the version through another objective's outcome task): the check names it and does not red on it, and the same holds for a request its author filed at horizon 2 or later (a later train's by its own declaration; a red of this release is filed at horizon 1); and every claim citation in the inventory's claims tables resolves at the tip (the file exists, the section heading it names exists).
2. **The reading, by single opus readers (in bounded parts, below):** every text with a claim whose owner doc or code path changed between the previous version's tip and this tip is read against the code at the tip; only a claim FALSE against the code is a red — ruling 22's bar — and a missing or unclear sentence is a request for the next round, never a red.

**The reading divides into bounded parts, each one fresh opus reader (designed 2026-11-12; it amends item 2's "one pass", never ruling 22's single readers).** The unit of the reading is the claim, never the text: each selected claim is judged against the code alone, so claims split freely, and a text is not a bounded unit — the guides tree alone held 504 of the 677 claims selected from 0.1.6's tip (190,883 of the prompt's 286,071 characters), so a partition by text leaves one reader with two thirds of the work. **The partition is mechanical:** the selection's claims, grouped by text and, inside a tree, by member file, in the inventory's order, are packed into parts of at most `READER_PART_CHARS` characters of prompt each (40,000, best-guessed — about a hundred claims, a seventh of the measured reading; tuned by hand from the readers' results, never by a dated reading row), a group kept whole while it fits in an empty part and split at claim boundaries when it does not; every part names its own sources and is self-contained. The parts are read side by side, one fresh opus reader each, under item 2's bar unchanged. **The reading's verdict is one, recorded in parts:** each reader's verdict is its own `reading` row at the tip, carrying `part` (`k/n`) and the partition's fingerprint; the half is green only when every part of the newest partition at the tip is recorded green, red when any part is red, and missing while any part is unrecorded — so the public tag's refusal is unchanged in meaning. A partition the tip's move replaced is read afresh whole: parts of an older tip count for nothing. **The citations are narrowed where it is honest, not to fit a reader:** a claim citing a whole goal doc (`X.md` with no `§`) moves with every edit of the doc and is the larger half of the selection's needless width (116 of the 328 moved citations measured, an eighth of the characters), so the pre-gate counts whole-goal-doc citations in the inventory's claims tables and that count may only fall — a new or edited claim cites the section that owns it; a claim citing an owner doc's `Implementation status today` stays allowed, since that section is where "built" and "not yet" are owned and a claim that a feature exists rests on it, and its daily motion is the price of reading such a claim at every release. Dropping both kinds would have cut the measured reading by a fifth only (to 232,801 characters), which is why the partition, not the narrowing, is what bounds a reader.

**A red is fixed inside the version.** A false claim whose fix changes no claim's substance lands as a correction; any other fix is a request task at horizon 1 converged at once under ruling 22's budget and landed under an open round, opening one if none is (§ The round); the tip then moves as for any fix ([`release-attempt.md`](release-attempt.md) § The release attempt, step 4). The public tag refuses while the check's newest reading at the tip is red or missing. **The mechanical half also runs in the release-readiness lane** ([`release-attempt.md`](release-attempt.md) § The release attempt, step 2) once that lane is built, so a missing text is met before the attempt opens rather than inside it.

## Exemptions

- **Generated output is exempt because no mind writes it.** The rendered catalog matrix and its data file, the catalog pages' status blocks, the third-party notices, the official-apps identity tables, the sitemap, a release's auto-generated change list: each is a function of tracked inputs and a generator whose own wording *is* inventoried (the matrix legend's paragraph, the official-apps prose fields, the release body). A generator's wording changes through a request; its output never waits for one.
- **A pure correction lands out of round (ruled 2026-10-15, § Rulings, 2).** A fix that changes no claim — a misspelling, a broken link's target, a date the text itself cites wrongly, a markup error — would cost a request, a review and a round to land one character. It lands under the trailer `Public-Texts-Round: correction`, may reach a publish path (it *is* landed, unlike a draft), and **the next round's record lists every correction landed since the previous round, read by the owner with the round** — trust at the commit, verification at the round. Adding a page is never a correction. A fix that changes a claim is a request, whatever its size.

## Enforced, never trusted

1. **The merge path refuses a change under an inventoried path whose landing commit carries no `Public-Texts-Round: <N>` trailer** (or `draft` or `correction`, below and § Exemptions) — the twin of the bump round's `Bump-Round:` refusal, a cheap parse-only gate reading the inventory's source paths and globs, within the merge budget ([`merge-gates.md`](merge-gates.md) § Local-merge gates → *The 10-second budget*). A draft is a change too: it carries the trailer of no round, so **a draft lands with `Public-Texts-Round: draft` and the gate additionally refuses a draft that reaches a publish path** — a page wrapped into the site, a workflow body, a served string — by the same path list. **What a change is follows the file the words sit in,** because a served string in a 4,700-line Rust file is a text while the file is not: a Markdown text is gated whole (less the sections a generator writes and the sections the inventory's exclusions cut out), a `path.md § Section` source that section only, a JSON source the values at the keys its entry lists, and every other file only the lines between a `public-text: <id>` marker line and its `public-text-end: <id>` line — so adding a marker changes no text, and removing or moving one does. Adding a page to the site publishes one, and needs a numbered round. The console classes cannot be gated at the merge; their enforcement is the readback rule.
2. **A request-shaped task is refused anywhere but the queue, and the merit judge refuses one it meets** — a session cannot route around the review by minting "update the privacy page" into its own queue.
3. **The inventory is complete, both ways:** every source path and glob it names exists, and every file under an inventoried tree is covered by an entry or an exclusion — a cheap gate, so a new guide or a new catalog page cannot appear uninventoried.
4. **The session rule stands where every session reads its rules**, pointing here.

What of this is built: § Implementation status today.

## Where requests live — tasks, and why

**Requests are tasks in the queue's file, not entries in a data file.** The bump round keeps its between-rounds needs in a data file and argues the opposite ([`dependency-bump-report.md`](dependency-bump-report.md) § Who opens a round → *Where rounds live*): a version need is not work until a round, and a file is what both the round's assembly and the merge gate read. Here the reasoning cuts the other way. A text request **needs a mind between filing and landing** — the review is work a session runs, a judge vouches for and ageing retires, exactly what a task is for; its parked state (ready, awaiting the round) is a gate a round lifts; its refusal is a verdict on a task; and the round's assembly reads the file's ready tasks as the bump round reads its queue. What the gate reads is the *inventory*, not the queue — so no data file is needed for enforcement either. A request that is only a note ("the README should mention the terminal app someday") is still a task: a task with a horizon is how this fleet remembers work.

15. **A session reads the deployed site back (ruled 2026-10-19, in a manual session, on round 1's open landing).** Once the site is deployed, the round's session reads every page of the round back from the live site against its landed source and records the reading in the round's record. The owner does not read it back. The console texts stay the owner's to enter, and the readback rule still applies to them.
16. **A store text is entered when the app is uploaded to that store (ruled 2026-10-19, in a manual session, on round 1's open landing).** An approved store listing, its review or certification notes, a TestFlight description and a build's notes go into a console only at the upload of the version they describe, in the same sitting. The round's approval stands until then; the round closes without waiting for the upload, and the upload's submission enters the approved text, with no new round unless the text itself has to change.
17. **A round closes once its texts are approved and their sources landed (ruled 2026-10-19, in a manual session, closing round 1).** The site deploy follows the version's sync and can be a day or more away, and the store texts wait for their store upload (ruling 16). ## Words from the owner — the frame every public text is consistent with

**The owner's own statement of what Fauna is (2026-10-15, written into this doc at ratification; the blocking-parties sentences reworded by the owner later the same day, after weighing an admin block of reported content and keeping the current shape; the third exception reworded by the owner again on 2026-10-16, on ratifying the admin block of a single reported item; the blocking sentences restated by the owner once more later on 2026-10-16 as three actors × four ways — simple rules and prompts for on-device LLMs, which all three may use and under which guardians and governments never see the content, and manual blocking on a legal takedown or on a user's report, which only an admin may do, seeing only what is plaintext on the nest; the per-nest rules sentence reworded by the owner on 2026-10-19, from "Per-nest rules, which a nest admin publishes and users accept when joining, are planned.", once the rules were built — the build state lives in the paragraph below, not in the words), kept verbatim.** It is the frame: every public text, and every marked app string, says what Fauna is in a way that is consistent with these words — not by repeating them, but by never contradicting them and by leading with what they lead with (the individual's control, the three kinds of data, the nest as just another app, the organisation that builds and does not host). > Fauna is "digital sovereignty for the individual" - the core functionality is that the user controls both data they create (A) and also controls their experience of other users' data, whether it is pushed like incoming e-mail and feeds (B) or downloaded on-demand (C). Users can freely control the sorting and filtering of the data they create. There are three actors who can block other users' content: 1) governments, 2) guardians, 3) nest admins. They can block using a) simple rules, b) or LLM prompts for on-device LLMs, c) manual blocking (the actor makes a manual decision) based on legal takedown, d) manual blocking based on reports by other. 1-3 can all block using a and b. 1-2 never see the content itself. 3 can also block using c and d and in these cases see the content that is plaintext on the nest - but blocking always leaves a visible notice and a permanent record, and the author can appeal. A nest admin can also suspend an account on their nest, and receives user reports, which inform the admin but remove nothing by themselves; there is no silent blocking of content by an admin. A nest admin can also publish per-nest rules, which users accept when joining. Blocking is always additive (content is blocked if any of the parties block it) and visible to the user, with an explanation.
>
> Fauna runs on any device the user has and both A+B+C data can freely move between these. Fauna also offers a "nest" component that can run on rented hardware, typically a 24/7 publicly reachable VPS rented from a hosting provider, which is the main way data of type B reaches the user. The nest can also run on e.g. a Raspberry Pi at home. The nest is "just another app" but with e2ee as default and opt-in weakening of that encryption, in order to maintain the user's digital sovereignty (by preventing surveillance by the hosting provider).
>
> The organization Fauna Social creates the software and publishes them to App Store, Play Store and Microsoft Store, but does not host any servers or nests for users. Fauna Social maintains the servers dev.fauna.build, test.fauna.build and fauna.build, used for 1) testing new releases of the nest software component and 2) letting reviewers from the App Store, Play Store and Microsoft Store test the apps' integration with the nest component.
