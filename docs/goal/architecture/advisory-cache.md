# Advisory cache — the advisories Fauna's lockfiles meet, as data, beside our reading of each — target state

Owns: advisory-cache
Status: ratified — design pass 2026-10-17 (user-directed the same day), refutable by its build rows where a measurement contradicts it; the record, its script, its three recipes and the four flow integrations built 2026-10-17 (§ Implementation status today)
Authority: owns the tracked local copy of the advisory FACTS the scanners report against Fauna's lockfiles and the per-advisory READING a mind recorded — what is cached, from which source at which revision, how it is refreshed, what counts as drift and what drift asks of a session, and the rule that prose cites an entry rather than restating a fact. Neighbours that do **not** own this: [`release-integrity.md`](release-integrity.md) § Dependency verification owns the scanners and the minimum release age, and [`dependency-advisories.md`](dependency-advisories.md) every exception list and the release attempt's advisory reading (the pinned snapshot, the delta and the severity bar); [`dependency-bump-report.md`](dependency-bump-report.md) owns the bump queue and the round a fix lands in; [`publish-gates.md`](publish-gates.md) owns the attempt; [`dependency-verification-log.md`](dependency-verification-log.md) owns the dated history.

## Goal

**Ruling (design pass 2026-10-17, user-directed): the advisories Fauna cares about are held in one tracked file as data — the facts each scanner's source states, copied as fields and never as text, with the source revision each fact came from — and beside each entry the reading a mind recorded, stamped with the revision it read; tooling refreshes the facts, reports every drift against a reading as an action a session takes, and never edits a reading by itself; prose names an advisory by id and cites its entry instead of restating what the advisory says.**

The vulnerability picture Fauna reads is entirely third-party and moves daily: the RustSec advisory database (a community repository, read at one pinned commit per release attempt and at its head by the daily check), the Go vulnerability database behind `govulncheck`, the npm registry's advisory endpoint behind `deno audit`, OSV.dev behind the Swift check, and the GitHub Advisory Database behind the hosting service's alerts. Our own notes about those advisories live in prose that does not move with them — a goal-doc sentence naming a fixed version, a bump-queue need, an attempt record's note or triage, an exception entry's reasoning — and nothing reconciles a note when its advisory is amended, re-scored, withdrawn or gains a fix. The first drift found: a sentence of [`dependency-advisories.md`](dependency-advisories.md) § Dependency verification → *The release attempt's advisory reading* named a fixed version for an advisory whose database entry stated a patched range, and the release it named was only the one the registry had not withdrawn that day — a registry fact, not the advisory's — so the sentence had fused the two; it was rewritten later the same day. The cache separates them for good: the advisory's range is a fact the refresh copies; which release a round moves to is the round's reading.

## Scope — which advisories

**An entry exists for every advisory a scanner of § Dependency verification reports against a version locked in a tracked lockfile that scanner reads** — the root `Cargo.lock`, every tracked `deno.lock`, every tracked `go.mod`, every tracked `Package.resolved` — at the current `main` tip **or** in the previous public release's lockfile (the set the delta already reads as `previous`), **whether or not an exception list excepts it**, and of every kind the scanner reports (a vulnerability; `cargo audit`'s `unsound`, `unmaintained` and `informational` warnings). The excepted ones are the point: an advisory in the cargo exception list (`.cargo/audit.toml`'s id-only ignore list today; `supply-chain/cargo-audit-exceptions.toml`, the evidenced per-(advisory, crate, version) file the 2026-10-17 re-ruling replaces it with) or in one of the three other exception files is exactly one we hold a reading on, and the ordinary gate run hides it (`cargo audit` drops an ignored id from its report entirely — `settings.ignore` names it and the lists omit it, measured 2026-10-17). So the census that decides membership runs each scanner in a form that lists everything: `cargo audit --json --file <the lock>` from a working directory holding no `.cargo/audit.toml` (measured 2026-10-17: the report then carries every ignored vulnerability and warning, with `settings.ignore = []`), and each wrapper's parsed findings before its exception list is applied; the census stays config-less whichever file holds the cargo exceptions, so it is right before and after the move.

A yank is not an advisory — it carries no id — and stays where it is, in `supply-chain/yanked-exceptions.toml`. The Gradle verification file and the NuGet lockfiles are read by no scanner of ours; the hosting service's alerts read them, so an alert against one of them enters the cache through the alert source at a release attempt (§ Sources and cadence) and through nothing else. The vendored forks' own lockfiles are the vendored-forks job's and are out of scope here.

**An entry is never deleted.** When its package no longer matches either lockfile — the dependency left, or moved past every affected range — the next refresh marks it `status = "retired"` with the date and stops comparing it; a retired entry keeps every fact and reading it held, because the attempt records, the round records and the log cite it by id, and a reader of those should still find what was read.

## The record

One file, `supply-chain/advisories.toml`, written only by the tool (the refresh for the facts, the read command for a reading; never by hand), one `[[advisory]]` table per `(id, ecosystem, package)`, ordered by id so a diff reads as a list of changes. Each table holds two halves that are written by different hands and never by the same one:

- **Facts — copied as data, overwritten whole by every refresh, never edited by a session:** `id` (the scanner's native id: `RUSTSEC-`, `GHSA-`, `GO-`), `aliases` (the other ids the source lists: CVE, GHSA), `ecosystem` (`cargo` | `npm` | `go` | `swift` | `gradle` | `nuget`), `package`, `kind` (`vulnerability` | `unsound` | `unmaintained` | `informational`), `locked` (the versions of ours the advisory matched, each tagged `current` or `previous`), `patched` and `unaffected` (the ranges exactly as the source states them — RustSec's `>=9.0.0`, an OSV `fixed` event, an alert's `first_patched_version`), `cvss` (the vector string, empty when the source gives none), `cvss_source` (`alerts` when the vector is the hosting service's alert's because the entry's own source gives none, empty otherwise), `withdrawn` (the date, empty otherwise), `published` (the advisory's own date), `source` (`rustsec` | `osv` | `govulncheck` | `alerts`), `source_rev` (the RustSec commit; an OSV record's `modified` stamp; an alert's `updated_at`), `first_seen` (the date the refresh first wrote the entry), `status` (`open` | `retired`) and `retired` (the date). **Never stored and never printed:** the title, summary, details, references, keywords and categories — every free-text field is third-party text that would turn a data file into instructions ([`release-integrity.md`](release-integrity.md) § Reviewing untrusted source without being subverted); the id is the pointer to all of it, and the id is enough.
- **The reading — ours, written only by the read command, never touched by a refresh:** `read_rev` (the `source_rev` the mind read), `read_at` and `note` (our own words — what we concluded, never the advisory's). The reading does **not** copy the need, the exception or the attempt triage that implements it: those live where they live (`supply-chain/bump-queue.toml`, the exception lists, `supply-chain/attempts/<version>.toml` — one owner per claim), and the check joins them to the entry by id when it prints. What the reading adds is the one fact none of those files hold: **which revision of the source the conclusion was reached against**, which is what makes drift measurable. The two revisions are complementary, not duplicates: a reach-evidenced cargo exception entry records the lockfile hash it was read at and is void when OUR side moves (the crate version, a feature between us and it, a new call site — `dependency-advisories.md` § Dependency verification → *The release attempt's advisory reading* → *A not-reached finding is an exception entry*); the reading records the source revision and is drift when THEIR side moves (the range, the score, a withdrawal). The check reads the second; the exception tooling the first.

## Refresh and drift

**The refresh** runs the census, fetches each matched advisory's facts from its source, writes the file with every fact half replaced and every reading half untouched, retires what no longer matches, and stops — the commit is the session's. It is deterministic over its inputs: the cargo facts come from the advisory-database commit it was given (the attempt's pin; the daily head otherwise) and the others carry their own stamps, so the file at a commit says exactly what was read and when.

**The check** is read-only and is the detector: it re-reads the sources, compares them to the tracked facts, and for every entry that **holds a reading** and whose facts moved in a load-bearing field prints one line naming the entry, the field, both values and the action — never applying it. The classes and their actions:

- **fix** — a patched range appeared or moved → *re-triage: a fixed version exists; queue the need or amend the queued one's `wanted`*;
- **score** — the CVSS vector changed; the line says whether the bar of [`dependency-advisories.md`](dependency-advisories.md) § *The release attempt's advisory reading* is crossed in either direction → *re-triage under the bar; an attempt triage of this id is of the old score*;
- **withdrawn** — the source withdrew the advisory → *retire the reading: delete the exception entry or close the need; the next refresh retires the entry*;
- **range** — a locked version of ours entered or left an affected range (the range widened or narrowed, or our lock moved) → *re-read: the reading was of another version*;
- **alias** — a new alias appeared → recorded by the next refresh, no action; the line is informational.

A fact change on an entry with **no** reading is not drift — it is a finding, and the scanners already grade findings; the check says nothing about it. The exit code is the daily gate's grammar: 0 nothing drifted, 1 at least one action line (RED), 2 a source could not be read (INFRA — a tip whose advisories cannot be compared is unverified, never green). **The red clears only by a mind:** the session does what the line asks, then the read command, which stamps `read_rev` with the current `source_rev` and writes the file; the commit carries the note. The check also reports an exception entry (in any of the exception files, the cargo one included), a queued advised need or an attempt triage whose cache entry has **no** reading or a reading at an older revision than the entry's facts — a conclusion recorded somewhere without the reading that dates it is the drift this file exists to end.

## Prose cites the entry

**Target-state prose — a goal doc's ruling or mechanism, a runbook's rule, a round record's rationale — names an advisory by its id and never restates its fixed version, patched range, score, affected range or withdrawal.** Where the fact bears on the sentence, the sentence names the class of fact ("names a fixed version", "is network-reachable under the bar") and the entry carries the value; a reader who needs the number opens the entry, which the refresh keeps current, instead of a sentence nobody will. **Exempt, because they are history and not claims:** a dated measurement — an entry of the log, a `## Implementation status today` paragraph recording what a scan read on a date, an attempt record's note or triage, a round's table — records what the source said that day, and rewriting it when the source moves would falsify the record. A cheap-tier lint flags an advisory id followed on the same line by a fixed-version or patched-range phrase in a goal doc outside those exemptions, and the sentence that prompted this doc is the first it would have caught.

## Its place in the flows already built

- **The daily check.** `advisory-check` runs as the fifth part of `dep-advisory-check` ([`dependency-advisories.md`](dependency-advisories.md) § Dependency verification → *The scheduled scans run daily*; the 30th gate of [`merge-gate-catalog.md`](merge-gate-catalog.md)), so a drift lands in the janitor queue every session triages at startup; its INFRA on an unreachable OSV.dev is the gate's INFRA. The gate stays hermetic: the daily check reads no hosting-service alert (that needs an authenticated client the gate does not carry); alerts enter at the attempt.
- **The release attempt.** `release_attempt.py audit` runs the refresh at the attempt's pinned advisory-database commit — the cargo facts from the snapshot, the others live with their stamps, and the preflight's alert list (the hosting service's alerts opened since the attempt opened, which the attempt mode already prints for the delta) folded in as the alert source — so the attempt's tip carries the cache that matches its snapshot and the record needs no copy of the facts. The delta prints beside each of its lines the entry's reading (`read at <rev>` or `unread`), and grades an `UNGRADED` addition from the cache's vector when the source carries one: the class then shrinks from "every npm, Go or Swift advisory" to "an advisory no source scores" — the vector half of the bar only; the reach half stays the delta's artifact pre-filter and the reach pass (§ Dependency verification → *Reach is read at the vulnerable code*) (measured 2026-10-17: OSV.dev carries the vector for RustSec records and none for the GHSA and Go samples, whose GitHub alert carries one). The attempt's own triage (`release_attempt.py triage`) stays per attempt and is not a reading: a reading is a conclusion about the advisory, a triage a decision about one release.
- **The queue and the exception lists.** the need recorder and the attempt's triage command end by printing the read command's line for the id; an exception entry added or kept without a reading at the current revision is what the check reports. Nothing here moves a version: a fix is a need, and lands in a round (`dependency-bump-report.md` § Who opens a round).
- **Publication.** The file is fleet process in the way the bump queue is — its notes name queue rows and checkouts by design — so the publication transform withholds it (`drop-path supply-chain/advisories.toml`, landing with the file); this doc ships and describes the mechanism, and the public reader has the id, which is the public pointer.

## Sources and cadence

| Ecosystem | Membership (the scanner, in census form) | Facts | Revision recorded | When |
|---|---|---|---|---|
| cargo | `cargo audit --json --file Cargo.lock` from a config-less directory (every ignored id reported) | the report's own fields: aliases, date, cvss, withdrawn, patched, unaffected, kind | the advisory-database commit (the attempt's pin; `HEAD` daily) | daily; the attempt |
| npm | `deno audit --frozen` per tracked `deno.lock` (ids, severity word, vulnerable range) | OSV.dev `GET /v1/vulns/<GHSA id>`: aliases, affected events, severity vector when present, withdrawn, modified | the record's `modified` stamp | daily; the attempt |
| go | `govulncheck -scan module -format json` per tracked `go.mod` — its stream carries each finding's OSV record whole | that record's fields | its `modified` stamp | daily; the attempt |
| swift | OSV.dev `POST /v1/querybatch` per tracked `Package.resolved` | OSV.dev `GET /v1/vulns/<id>` | `modified` | daily; the attempt |
| gradle, nuget — and a cross-check of the three above | the hosting service's open alerts (`gh api repos/…/dependabot/alerts`, the preflight's own read) | the alert's `security_advisory`: ghsa and cve ids, the cvss vector, `withdrawn_at`, `first_patched_version`, `vulnerable_version_range` | the alert's `updated_at` | the attempt only |

**What a newer RustSec commit found is kept by a refresh at an older one.** The daily check refreshes at the database's `HEAD`; a release attempt's refresh reads its pin, which is older once a day has passed. An entry whose `source_rev` is a commit the refresh's database does not contain (read from the local mirror) keeps its facts — only `locked`, our own census, is taken anew — and is not retired for being absent from the older read: the older database cannot speak to what it predates, and the attempt's fresh read (its advisory delta) reads the live database anyway. A refresh at `HEAD` carries no such limit.

**What only the alerts state is kept between attempts.** An entry the alert source minted (a Gradle or NuGet one) and a vector it filled are not re-read by a refresh or a check that reads no alerts — the daily check, a hand-run refresh — so those keep them as they stand and compare neither: what was not read is neither retired nor drift. The next attempt's refresh reads the alerts again, and only then does a closed alert retire its entry or a vector the alert no longer gives count as a `score` drift.

**No new tool and no new fetch channel:** every source above is one a scanner of § Dependency verification already reads — the RustSec mirror under the pinned-snapshot cache, the npm registry through Deno, the Go database through `govulncheck`, OSV.dev through the Swift check, the alerts through the preflight; OSV.dev's per-id endpoint is the same host the batch endpoint is on. A source that would need anything installed or a new host is a dependency need in the bump queue, never installed by the session. Measured 2026-10-17: OSV.dev resolves ids of all three ecosystems (a RustSec id, a GHSA id, a Go id) to one record shape — `id`, `aliases`, `modified`, `published`, `withdrawn` when set, `affected[].ranges[].events` with `introduced`/`fixed`, `severity[]` when the source scored it.
