## Goal

The organisation needs exactly one thing from a nest on the public internet: a place that is always free, run by the organisation, reachable from anywhere, and running the numbered release under acceptance — so that app-store reviewers can sign in, and the organisation's own testers can accept a release before it ships, the way a user meets it. It needs that nest to be the only thing its name is attached to. A nest that also serves a community, holds people's data and shares its costs is a different thing, with a different operator; tying the organisation's name to such a nest ties the organisation to how that nest is run and paid for — a question for the organisation itself, not this doc. So the organisation runs **three nests in one zone of its own, `fauna.build`** — a domain registered for user acceptance testing ("uat") and nothing else — and **a community-run deployment is not the organisation's**: a deployment like any other, run outside it.

## fauna.build — the acceptance nest

**Role.** The nest a store reviewer is sent to and the nest a tester accepts a release on. It is the organisation's one live view of the UAT channel — the numbered release every Stable deployment in the world is about to receive, running where the organisation can accept or refuse it.

**Channel: `:test`, the UAT channel (the user's decision 2026-10-13, superseding `:latest` of 2026-10-10), with one release-order rule.** The acceptance nest runs the numbered release under acceptance — the one that becomes `:latest` unchanged once the owner approves the promote, that approval being the UAT sign-off ([`image-pipeline.md`](image-pipeline.md) § Image tags & channels, the UAT bullet) — so a reviewer and a tester meet the release before it ships, which is what acceptance means; the 2026-10-10 line "the release, never the candidate" is retired with it. The nest still has to be at least as new as the app build under review, so the order holds in two halves: **the nest reaches `:test` and this nest serves it before the version's app builds go to the stores' pre-release tracks, and the promote to `:latest` precedes the public store release**; the rule is owned by the release table ([`release-table.md`](release-table.md) § Tag gate and release table). Within a major version the wire compatibility rule would make the order a courtesy; under 0.1.x, which owes no compatibility, it is the only thing keeping them matched.

**Exposure: firewalled until the owner lifts it, then no firewall.** The owner ruled on 2026-10-17 that all three nests — `dev.fauna.build`, `test.fauna.build` and `fauna.build` — stay behind their own cloud firewalls until further notice, so the acceptance nest is provisioned and firewalled exactly like its siblings, and the opening below is the owner's act alone, taken on their in-the-moment word; no session lifts or loosens it on its own judgement. Once lifted, the nest serves the internet: [`deployment-threat-model.md`](deployment-threat-model.md) § Concern 1a applies to it in full, by design, and it is the organisation's first nest of which that is true. What makes that acceptable is not hardening beyond the product's own — it is that nothing falls with it: it holds reviewer and tester accounts only, no dev-fleet credential and no cloud credential ([`deployment-threat-model.md`](deployment-threat-model.md) § What a fallen box cannot reach), its zone and project reach nothing but itself and its two siblings (§ One zone, one project), and it is re-created in one command. It runs **the product as shipped** — mail inbound and outbound, the scanner sidecars, federation and the ActivityPub bridge all on, exactly as a user's deployment has them — because an acceptance nest with features switched off accepts nothing; the abuse posture is the product's own per-actor limits plus invite-only accounts.

**Accounts: invite-only, minted by the organisation (the user's decisions 2026-10-10 and 2026-10-14).** There is no open sign-up. The organisation mints **one reviewer account per store** — `microsoft-reviewer`, `apple-reviewer` and `google-reviewer` on `fauna.build` — and tester accounts for its own people. One account per store, not one shared by all three (ruled 2026-10-14): a secret leaked from one console, or a reviewer's lock from Settings → Sessions ([`../ui/sessions.md`](../ui/sessions.md)), then reaches that store's review alone, and each account is revoked without touching the other two consoles. Each account's identity is minted on the dev host and kept there beside the nest's own provisioning identity; the nest's admin admits it through the app's admin UI by its public key and handle — the direct admission of a known actor id ([`../behavior/admin.md`](../behavior/admin.md) § 2. Users, Section 3 — Admit) — so the secret is never sent anywhere to create the account. Each store's review notes name the nest, that store's reviewer handle and the sign-in steps in the store's own form; the identity secret rides in that store's review-access field and nowhere in the tree. **A reviewer's lock has no admin lift (ruled by the owner 2026-10-23).** A reviewer can lock their account for 24 hours from Settings → Sessions with the secret every reviewer of that store holds ([`../ui/sessions.md`](../ui/sessions.md)); nothing in the product lifts it early, and none is added for this nest — the remedy is the 24 hours or a re-creation (*Disposable*, below), which re-admits every account from its kept file, and every store submission follows a re-creation on the version under review, so each submission meets unlocked, freshly seeded accounts. **The identity files have one copy, on the dev host (ruled by the owner 2026-10-23).** The reviewer, tester and admin identity files live on Linux alone, in the same place and under the same protection as the fleet's cloud tokens, which already reach far more than these organisation-minted test accounts do; no second copy is kept, in a password manager or anywhere else. Losing them costs new accounts and new secrets in the three store consoles, which the owner accepts. **The two staging boxes hold the same accounts (ruled by the owner 2026-10-28).** `dev.fauna.build` and `test.fauna.build` get the three reviewers and the tester too, each box with identities of its own minted and kept the same way, admitted and seeded by the same provisioning drive, so that the store reviewer journey runs as an automated test where automated tests may — never on `fauna.build`; those identities are in no store console. On the two staging boxes alone the tester's seed also carries one priced tier and one post sold on its own, made on the full build, because a store build's buyer half must show a priced tier and a sold post without their price (`docs/features/store-install.md` outcomes 2 and 3) and cannot make either; `fauna.build` never gets them, its content being a store reviewer's first run, where a payment link buys nothing. **The witness hosts' testers — the one identity that is kept off the dev host, and the secret-free route for it (ruled 2026-11-05).** A store-install witness signs in to `test.fauna.build` through the shipped app's own UI from the machine that runs it — the macOS development VM for the TestFlight install, the Linux dev host for the Play install — so that machine needs an admitted identity of its own, and carrying a reviewer's identity file there would copy a secret between machines on every re-creation (a recurring human act, with no sanctioned channel for it). Instead each witness host mints its OWN tester, `<platform>-tester` (`macos-tester`, `linux-tester`, `windows-tester`), keeps it where the drive keeps its own identities on that machine (mode 0600, one copy, reused for good), and publishes only its public key and handle into the tracked registry `tests/e2e-unified/org-testers.toml`; the provisioning drive reads the registry on every run of a staging box — a resume on a seeded box included — and admits each entry by public key, as it admits the reviewers, so the identity survives every re-creation with no human step. The secret never leaves the machine that uses it, which is this section's own principle; the reviewers', the seeding tester's and the admin's files stay on the dev host alone, as ruled above. A witness tester is never registered for `fauna.build` (humans only) and is seeded with nothing: its subject is the store install and a sign-in, not a reviewer's first run. The witness signs in as its host's tester; only where no tester is minted and registered on the host — the dev host, which keeps the reviewers' files — does the store's reviewer stand in. **The live filesync round's seat account — the one identity copied between machines, once (2026-11-08, the daily grading's least-privilege call).** The three-machine filesync round signs every seat in as one account — three devices of one user ([`e2e-live-sync-convergence.md`](e2e-live-sync-convergence.md) convention 16 (d)) — so its seed must be on all three seat machines, which a per-host tester cannot give. It is `multiseat-seat` on `dev.fauna.build` alone, a NON-admin account minted on the dev host beside the org accounts, admitted by public key on every run of the drive and seeded with nothing; the owner copies its one file to the macOS and Windows dev VMs once, and a re-creation re-admits the same key from the dev host's file, so the copy is never repeated. The box's admin seed stays on the dev host alone: it is no seat.

**Disposable means re-creatable in one command — on a calendar, and before every complex connection (ruled 2026-10-17).** The reviewer credentials in the store consoles must stay valid across every re-creation, so a re-creation re-provisions the nest on Test, re-admits the same accounts from their kept identity files, and runs the serving gate; it happens weekly, at every UAT entry, and on demand — an incident, a major bump, a wish for a clean slate. **And before every complex connection from a dev machine (the owner's ask, 2026-10-17):** a box a stranger can hold may already have fallen, so a dev machine trusts no acceptance nest beyond a plain HTTPS probe unless the box was re-created since the last such connection — one complex connection per re-creation. **One exemption, the admin's reports pass while a store review is open (ruled 2026-11-01):** while the store-review record holds an `in-review` submission of the version the box serves, the admin may resolve reports as often as the review needs without spending the connection, but only through a client that carries none of the third-party native code [`deployment-threat-model.md`](deployment-threat-model.md) § Concern 2, path 2 accepts as residue — headless, shared Rust alone (memory-safe parsers; no browser engine, WebView or media decoder), doing two things only, listing the open reports and resolving them, rendering no media and no HTML, every byte the box returns handled as untrusted data; the full admin app is never that client. Why the shape, not the credential: the admin identity is already kept on the dev host, so a token minted at the re-creation would remove nothing — the rule rations a dev machine's exposure to a box a stranger may hold, and the exemption is bounded by what that exposure can reach. [`installers/store-review.md`](installers/store-review.md) § During a review owns when the pass runs. A complex connection is anything more than that probe: a sign-in, a seeded data load, the re-admission of an account, a log pull; the serving gate and the stage's credential-free observation stay probes. Automated live tests never connect to it at all — the harness refuses the acceptance nest as a target, whatever the run declares ([`testing.md`](testing.md) § The shared-box rule) — so the rule binds the re-creation's own tooling and the people who test on it from a dev machine; the re-creation's own sign-ins, re-admissions and seeding are the re-creation, not a connection to a box that has been running. The re-creation also re-seeds the reviewer accounts' content, so a reviewer meets the same account each time. **Re-created on a calendar too (ruled 2026-10-17, overturning the earlier "never a scheduled wipe"):** weekly and at every UAT entry, the cadence a constant in the tree, never a setting; a missed re-creation surfaces as a red, never silently. **The weekly re-creation holds while a store review is open (ruled 2026-11-01):** while the store-review record holds an `in-review` submission of the version the box serves, the calendar defers it and the miss check exempts the same window, so a reviewer mid-session never loses their account's state to the timer; the re-creations a review itself calls for stay ([`installers/store-review.md`](installers/store-review.md) § During a review). Each re-creation drops the reviewer and tester accounts' content and re-seeds it from the dev host — acceptable under [`principles.md`](../principles.md) § No user-data loss because these are organisation-minted test accounts, not user data (the owner confirmed it the same day).

**The re-creation drives the box with the release's own app, a part-way death is not retried, and the certificate budget is a ledger (ruled 2026-11-01).** Three rules with one cause: every re-creation from 2026-10-29 died after buying its server, because the drive ran the tip's app against the 0.1.5 `:test` nest, and inside the 0.1.x window the tip owes the release no compatibility ([`version-compatibility.md`](version-compatibility.md) § Dimension 2, the fifth exception) — a client-side shim is refused for this skew as for every other. **(1) The app is the release's.** Every organisation operation on one of its nests from a dev host — the provisioning drive of all three kept boxes (the acceptance re-creation included), the store reviewer journey on the two staging boxes, the headless reports pass — runs a client built from the private commit the box's image was built from, never from the tip: the image's revision label, read off the registry before anything is bought (a public build's label is a public commit, paired to its private source by the `Sync-Point:` trailer the release table also records — [`release-table.md`](release-table.md) § Tag gate and release table, *Promotion copies the tested digest*; a private `:dev` build's label is the private commit itself), built and cached by the pinned-previous-build mechanism keyed on that commit rather than on the pin ([`version-compatibility.md`](version-compatibility.md) § Dimension 6), so one release costs one build. Why this and not a skew check that refuses early: a reviewer meets the release's app against the release's nest, so that pair is the one the drive witnesses, and the cross-version pair is the skew grid's business, never an organisation nest's — true after 0.2.0 as well, so the rule reads no version window. The harness itself stays at the tip (it reaches the nest only by HTTP probes and drives the app by ui.yaml ids, as the grid drives a pinned app), and the drive asserts before the buy that the app it runs is the image's commit. The fleet's live tests against `dev.fauna.build` are tests of the tip, fail without buying anything, and stay at the tip. Consequence accepted: a client absent at the release's commit is unavailable for that release — 0.1.5 carries no reports pass, so duty 1 of [`installers/store-review.md`](installers/store-review.md) § During a review falls back to the admin app's one complex connection per re-creation until the next release — honest, and self-resolving. **(2) A death is not retried by the timer.** A re-creation the teardown started that wrote no record within its run bound is DEAD: the trigger does nothing on it, the miss check is red naming the death, and only a re-creation run by hand — a mind has read the failure — starts the next one. The acceptance nest is down meanwhile (the teardown ran first), and a six-hourly retry would not change that: every attempt buys a server and spends a certificate, and a fault of the drive's fails identically every time (six boxes in three days, measured). **(3) The certificate budget is a ledger.** Let's Encrypt issues five certificates for one exact set of names per seven days, refilled continuously (one back about every 34 hours), and every box bought requests one for the box's three names. The state file records each buy, and the teardown refuses the sixth within seven days, naming when the oldest falls out — a wait, never bypassed. The arithmetic keeps the cadence weekly: the calendar spends one, a UAT entry one, a re-creation a review asks for one — three in a hard week — so the budget binds only through failures, which rule (2) caps at one per fault.

**What the organisation observes there.** The serving gate passes against the acceptance nest with no cloud token and no firewall admission, which lets the public pipeline's *stage* observe `:test` landing there as an optional, credential-free last step (the 2026-10-11 observation of `:latest` at promote, moved with the nest's channel on 2026-10-13: what `:latest` names after a promote is the digest this nest has been serving through acceptance, so a promote has nothing new to observe here) — **an observation, never a gate (ruled 2026-10-11):** it runs only after the push has happened, its result is printed and cannot fail the run or feed anything back, because this is the one organisation nest a stranger can hold, and a box a stranger can hold must not be able to fail or stall a release ([`deployment-threat-model.md`](deployment-threat-model.md) § Concern 1a); and the nest's own update is the Watchtower hop every Test deployment makes, so a stage push that fails to land anywhere is seen here first. While the 2026-10-17 firewall stands, the observation reads the nest as unreachable from the runner; that is printed like any other result and, being no gate, changes nothing.

## One zone, one project

**One zone, a registered domain of its own.** `fauna.build` is a domain the organisation registers for this and nothing else (chosen 2026-10-12, after the provider refused `uat.fauna.social` as a zone: its zones are registrable domains, never subzones, so a delegated subzone of fauna.social could not live in the uat project), and the three nests are records in that one zone — the acceptance nest at the apex, the dev and test nests under it; the zone is the one the admin's app manages (DNS-01 renewal, the mail record matrix). The fauna.social apex carries nothing for it. A fallen nest holds that zone's credential sealed to its admin's keys; what the zone reaches is the three nests, not fauna.social, the organisation's mail or the front door's names — [`front-door.md`](front-door.md) § Public-vhost topology records that the door serves nothing under this name. **The zone's defaults are five minutes (ruled 2026-10-23):** its default TTL and its SOA minimum — how long a resolver keeps a "no such record" answer — are both 300 s, so a name looked up before its box exists, or after it is re-created at a new address, is right again within minutes; set on the zone 2026-10-23, the same figure every record Fauna publishes carries ([`../behavior/dns-management.md`](../behavior/dns-management.md) § Records covered → *TTL*). The registration is org-attributable and rostered in the expense ledger.

**Four projects, cut by who holds each token (ruled 2026-10-17; two until then).** The provider scopes a credential to a project, so the organisation's projects are cut by who holds a token: the **zone project** holds the `fauna.build` zone and nothing else; the **uat project** holds the dev and test nests with their firewalls and the live suite's throwaway boxes, made there under the zone so no automated run ever holds any other token; the **acceptance project** holds the fauna.build box and its firewall; the **production project** holds the fauna.social apex zone and the front-door box. The verify jobs in CI hold uat-project tokens; the acceptance- and production-project tokens live on the dev host alone and never enter CI; and the credential each nest's admin app keeps for managed DNS is a zone-project token of its own, one per nest, never the fleet's token file (the threat model's token-per-consumer rule). The threat model owns that split and the reasoning — what each token can and cannot reach, and why not two, three or five projects ([`deployment-threat-model.md`](deployment-threat-model.md) § Concern 2 path 5); this doc only states what lives where.

## Deployments the organisation does not run

A deployment run outside the organisation — a community-run one included, on whatever terms its operator sets, cost-shared usage tiers included — is a deployment like any other. The organisation's side of that is simple and fixed:

- **It is a deployment like any other.** It pulls the public `:latest` with its own Watchtower as every deployment does; the organisation's pipeline never pushes to it, never verifies at it, and no fleet script names it as a default or a target.
- **Nothing of the organisation's lives under its zone**, which is why the dev and test nests live under `fauna.build`: the organisation's release gate must not depend on a zone it does not control.
- **The organisation does not run it, pay for it or hold its admin seed**, and the expense ledger does not roster it as org-attributable.
- **No store listing, review note, app, guide, site page, fixture or example names it, as the organisation's or otherwise.** That shipped text names no deployment the organisation does not run is the organisation's own choice — its name attaches only to what it runs (§ Goal) — decided 2026-10-21 without counsel under [`public-texts.md`](public-texts.md) § Rulings, 20; a text that would name one, as "a community-run deployment" or otherwise, is a public-texts request like any other, decided in its round by the owner; code and docs use the reserved example domains for examples and fixtures.
