It owns no mechanism: which image tag each channel carries and the pipeline that moves it → [`image-pipeline.md`](image-pipeline.md) § Image tags & channels; the threat enumeration over a deployed nest and the mitigation per path, the per-project credential split included → [`deployment-threat-model.md`](deployment-threat-model.md); the fauna.social public web box and its vhosts → [`front-door.md`](front-door.md); the provisioning drive and the live-test rules → [`testing.md`](testing.md); whether the organisation is a trader → [`installers/store-listing-contact.md`](installers/store-listing-contact.md) § The classification question, never here.

## Goal

The organisation needs exactly one thing from a nest on the public internet: a place that is always free, run by the organisation, reachable from anywhere, and running the numbered release under acceptance — so that app-store reviewers can sign in, and the organisation's own testers can accept a release before it ships, the way a user meets it. It needs that nest to be the only thing its name is attached to. A nest that also serves a community, holds people's data and shares its costs is a different thing, with a different operator; tying the organisation's name to such a nest ties the organisation to how that nest is run and paid for — a question its counsel answers, not this doc. So the organisation runs **three nests in one zone of its own, `fauna.build`** — a domain registered for user acceptance testing ("uat") and nothing else — and **a community-run deployment is not the organisation's**: a deployment like any other, run outside it.

## The three nests

| Nest | Channel | Who uses it | Exposure | Automated tests |
|---|---|---|---|---|
| `dev.fauna.build` | `:dev` (the private repository's stage) | the private pipeline's verify job; the fleet's live tests | behind its own cloud firewall, the verify job admitted per run | yes — the shared-box rule's automated side |
| `test.fauna.build` | `:test` (the public repository's stage) | the public pipeline's verify job | behind its own cloud firewall, the verify job admitted per run | yes — the shared-box rule's automated side |
| `fauna.build` | `:test` (the UAT channel — the numbered release under acceptance, which becomes `:latest` unchanged) | app-store reviewers, the organisation's testers, the organisation itself | **none — the open internet** | **no** — humans only (§ The shared-box rule in [`testing.md`](testing.md)) |

The dev and test nests are the staging pair [`image-pipeline.md`](image-pipeline.md) § Image tags & channels describes, under these names; nothing about their role, firewall or verify admission is decided here. The acceptance nest is new, and the rest of this doc is about it and about what the organisation does not run.

## fauna.build — the acceptance nest

**Role.** The nest a store reviewer is sent to and the nest a tester accepts a release on. It is the organisation's one live view of the UAT channel — the numbered release every Stable deployment in the world is about to receive, running where the organisation can accept or refuse it.

**Channel: `:test`, the UAT channel (the user's decision 2026-10-13, superseding `:latest` of 2026-10-10), with one release-order rule.** The acceptance nest runs the numbered release under acceptance — the one that becomes `:latest` unchanged once the owner approves the promote, that approval being the UAT sign-off ([`image-pipeline.md`](image-pipeline.md) § Image tags & channels, the UAT bullet) — so a reviewer and a tester meet the release before it ships, which is what acceptance means; the 2026-10-10 line "the release, never the candidate" is retired with it. The nest still has to be at least as new as the app build under review, so the order holds in two halves: **the nest reaches `:test` and this nest serves it before the version's app builds go to the stores' pre-release tracks, and the promote to `:latest` precedes the public store release**; the rule is owned by the release table ([`feature-catalog.md`](feature-catalog.md) § Tag gate and release table). Within a major version the wire compatibility rule would make the order a courtesy; under 0.1.x, which owes no compatibility, it is the only thing keeping them matched.

**Exposure: no firewall.** The nest serves the internet from its first day: [`deployment-threat-model.md`](deployment-threat-model.md) § Concern 1a applies to it in full, by design, and it is the organisation's first nest of which that is true. What makes that acceptable is not hardening beyond the product's own — it is that nothing falls with it: it holds reviewer and tester accounts only, no dev-fleet credential and no cloud credential ([`deployment-threat-model.md`](deployment-threat-model.md) § What a fallen box cannot reach), its zone and project reach nothing but itself and its two siblings (§ One zone, one project), and it is re-created in one command. It runs **the product as shipped** — mail inbound and outbound, the scanner sidecars, federation and the ActivityPub bridge all on, exactly as a user's deployment has them — because an acceptance nest with features switched off accepts nothing; the abuse posture is the product's own per-actor limits plus invite-only accounts.

**Accounts: invite-only, minted by the organisation (the user's decisions 2026-10-10 and 2026-10-14).** There is no open sign-up. The organisation mints **one reviewer account per store** — `microsoft-reviewer`, `apple-reviewer` and `google-reviewer` on `fauna.build` — and tester accounts for its own people. One account per store, not one shared by all three (ruled 2026-10-14): a secret leaked from one console, or a reviewer's lock from Settings → Sessions ([`../ui/sessions.md`](../ui/sessions.md)), then reaches that store's review alone, and each account is revoked without touching the other two consoles. Each account's identity is minted on the dev host and kept there beside the nest's own provisioning identity; the nest's admin admits it through the app's admin UI by its public key and handle — the direct admission of a known actor id ([`../behavior/admin.md`](../behavior/admin.md) § 2. Users, Section 3 — Admit) — so the secret is never sent anywhere to create the account. Each store's review notes name the nest, that store's reviewer handle and the sign-in steps in the store's own form; the identity secret rides in that store's review-access field and nowhere in the tree.

**Disposable means re-creatable in one command, never a scheduled wipe.** The reviewer credentials in the store consoles must stay valid across every re-creation, so a re-creation re-provisions the nest on Test, re-admits the same accounts from their kept identity files, and runs the serving gate; it happens on demand — an incident, a major bump, a wish for a clean slate — not on a calendar.

**What the organisation observes there.** The serving gate passes against the acceptance nest with no cloud token and no firewall admission, which lets the public pipeline's *stage* observe `:test` landing there as an optional, credential-free last step (the 2026-10-11 observation of `:latest` at promote, moved with the nest's channel on 2026-10-13: what `:latest` names after a promote is the digest this nest has been serving through acceptance, so a promote has nothing new to observe here) — **an observation, never a gate (ruled 2026-10-11):** it runs only after the push has happened, its result is printed and cannot fail the run or feed anything back, because this is the one organisation nest a stranger can hold, and a box a stranger can hold must not be able to fail or stall a release ([`deployment-threat-model.md`](deployment-threat-model.md) § Concern 1a); and the nest's own update is the Watchtower hop every Test deployment makes, so a stage push that fails to land anywhere is seen here first.

## One zone, one project

**One zone, a registered domain of its own.** `fauna.build` is a domain the organisation registers for this and nothing else (chosen 2026-10-12, after the provider refused `uat.fauna.social` as a zone: its zones are registrable domains, never subzones, so a delegated subzone of fauna.social could not live in the uat project), and the three nests are records in that one zone — the acceptance nest at the apex, the dev and test nests under it; the zone is the one the admin's app manages (DNS-01 renewal, the mail record matrix). The fauna.social apex carries nothing for it. A fallen nest holds that zone's credential sealed to its admin's keys; what the zone reaches is the three nests, not fauna.social, the organisation's mail or the front door's names — [`front-door.md`](front-door.md) § Public-vhost topology records that the door serves nothing under this name. The registration is org-attributable and rostered in the expense ledger.

**One project for the three nests.** The provider scopes a credential to a project, so the organisation's projects are cut by what a token reaches: the **uat project** holds the `fauna.build` zone and the three nests with their firewalls; the **production project** holds the fauna.social apex zone and the front-door box. The verify jobs in CI hold uat-project tokens; the production-project token never enters CI; and the credential each nest's admin app keeps for managed DNS is a uat-project token of its own, one per nest, never the fleet's token file (the threat model's token-per-consumer rule, § Concern 2 path 5). The threat model owns that split and the reasoning ([`deployment-threat-model.md`](deployment-threat-model.md) § Concern 2 path 5); this doc only states what lives where. The live test suite's throwaway boxes are made in the uat project too, under its zone, so no automated run ever holds the production token. Two projects, not three, because the acceptance nest is disposable by construction — a leaked uat-project token can rebuild it, which is what the organisation itself does on demand — and a third project would buy a console step and a token file for a box that holds nothing.

## Deployments the organisation does not run

A deployment run outside the organisation — a community-run one included, on whatever terms its operator sets, cost-shared usage tiers included — is a deployment like any other. The organisation's side of that is simple and fixed:

- **It is a deployment like any other.** It pulls the public `:latest` with its own Watchtower as every deployment does; the organisation's pipeline never pushes to it, never verifies at it, and no fleet script names it as a default or a target.
- **Nothing of the organisation's lives under its zone**, which is why the dev and test nests live under `fauna.build`: the organisation's release gate must not depend on a zone it does not control.
- **The organisation does not run it, pay for it or hold its admin seed**, and the expense ledger does not roster it as org-attributable.
- **No store listing, review note, app, guide, site page, fixture or example names it, as the organisation's or otherwise.** Whether the organisation may list one at all — as "a community-run deployment" — is counsel's question, asked in the classification round ([`installers/store-listing-contact.md`](installers/store-listing-contact.md) § The classification question); until that answer, shipped text does not name it, and code and docs use the reserved example domains for examples and fixtures.
