The first-run installer flow for the **home-with-public-relay** deployment — a public relay nest on a VPS that holds no read grants (sealed bytes only) and a private nest on residential hardware its household trusts (broad user-minted grants; content opened at the AUTH'd serve — the storage-mode axis this pattern was originally written against is retired: [`../nest/storage-modes.md`](../nest/storage-modes.md)), paired so inbound + Sent mail relays from the public box to the home box holding the canonical store. This is the installer half of [`../nest/deployment-home-with-public-relay.md`](../nest/deployment-home-with-public-relay.md). Validated end-to-end: tier_4 `tests/e2e-unified/tests/platform/docker/test_mail_relay_two_nest.py` proves the SNI-router/`:443` fronting, IMAP LAN exposure via `FAUNA_LAN_BIND_IP`, no-MTA boot, and the full external-MTA→public→home→MUA round-trip + no-readable-copy property. See § Implementation status today.

## The two boxes

| | Public box (VPS) | Private box (home) |
|---|---|---|
| Trust posture (grants — [`../nest/storage-modes.md`](../nest/storage-modes.md)) | no read grants minted (relays/holds sealed bytes only) | trusted by its household (broad user-minted grants; opens content at the AUTH'd serve) |
| NAT axis | public (default; client-confirmable at onboarding) | private (`FAUNA_MODE=private` **seeds** the pre-claim default; the app confirms/sets it authoritatively at onboarding + admin panel) |
| Role | internet-facing relay: MTA (port 25 in/out), submission (465/587), public TLS, holds wrapped ciphertext transiently | canonical plaintext store + the user's identity/MLS keys; serves IMAP/CalDAV to LAN MUAs |
| Mail bridge | MTA + MDA | **no MTA**; MDA serves IMAP/CalDAV on the LAN |
| Provisioned by | the setup wizard ([`vps.md`](vps.md)) or `docker-compose.yml` | `docker-compose.home.yml` (this doc) |

Both run the **same** `bins/fauna-nest` image; they differ only in the NAT axis (app-set at onboarding; `FAUNA_MODE` only seeds the pre-claim default) and in what their users grant them (a grant set, not a deployment mode — [`../nest/storage-modes.md`](../nest/storage-modes.md)). There is **no "VPS-frontend mode" flag** ([`../nest/deployment-home-with-public-relay.md`](../nest/deployment-home-with-public-relay.md) § Don't do these).

## Bring-up order

### 1. Provision the public box

Deploy a normal public nest on a VPS via the setup wizard ([`vps.md`](vps.md)) or the standard `docker-compose.yml` ([`docker.md`](docker.md)) and claim admin from your app (no storage-mode step — the box is content-ready sealed from first boot; mint it no grants and it holds sealed bytes only). Enable mail from your app (the admin "enable email" toggle) and publish the mail DNS (MX/SPF/DKIM/DMARC) from your client per [`../../behavior/dns-management.md`](../../behavior/dns-management.md). This box is the user's public mail identity; it is provisioned exactly like any other public nest — nothing here is home-relay-specific.

### 2. Bring up the private home box

On the residential hardware (home NAS / basement box) on the user's LAN, the primary path is a one-command dev-fleet installer script — it embeds `docker-compose.home.yml`, writes the `.env` (prompted, or `--non-interactive` from the `FAUNA_LAN_BIND_IP` env), accepts `FAUNA_DEPLOYMENT_SEED` for total-box-loss recovery (custody model: [`../nest/box-recovery.md`](../nest/box-recovery.md)), supports a `--check` dry run, and optionally handles Docker install, GHCR login, and a data-backup cron. Drift-guarded by a dedicated dev-fleet test.

The manual fallback (what the script automates): copy `docker-compose.home.yml`, create a `.env`, and `docker compose -f docker-compose.home.yml up -d`:

   ```
   FAUNA_LAN_BIND_IP=192.168.1.50       # the box's LAN IP (binds MDA IMAP 993/143 + CalDAV)
   FAUNA_DEPLOYMENT_SEED=<64-hex>       # RECOVERY ONLY — the seed your client custodied; omit on a fresh install
   ```
   (No `FAUNA_DOMAIN` — it is retired; the box boots domainless and is reached by its
   LAN IP, `../nest/domains-and-tls-bootstrap.md` § Env contract. Nor does anything
   name the public box: linking the two from your app in step 3 records it.)

Then claim admin from an app on the LAN. **There is no storage-mode step** — the axis is retired and the box seals at rest like every nest ([`../nest/storage-modes.md`](../nest/storage-modes.md)). If you want the home box doing server-side content work, mint it grants from your app's Nests page afterwards; **serving your mail over LAN IMAP/CalDAV needs no grant** (the AUTH'd MDA session is itself the capability position).

The home box comes up with (verified by Slice 3, [`../nest/deployment-home-with-public-relay.md`](../nest/deployment-home-with-public-relay.md) § Private-axis behavior on the home box): the perimeter parser **not started** (no MTA enrolled), the IMAP/CalDAV listener **LAN-only** (CalDAV bound **directly** on `FAUNA_LAN_BIND_IP:8443` — the `caldav_bind_host` topology hatch, router-bypassing on a bare-IP/home box whose `mail.<domain>` SNI route is unusable; IMAP bound on `FAUNA_LAN_BIND_IP:993/143` — the sanctioned topology hatch opt-out over the private-axis loopback default), **ACME not run** (force-disabled on the private axis), and a **self-signed LAN cert** at boot (optionally replaced by a publicly-trusted cert synced from the public box over namespace-sync, Slice 4).

> ✅ **CalDAV port (fixed 2026-06-20):** the home box serves CalDAV by binding `FAUNA_LAN_BIND_IP:8443` directly (the 2026-06-19 `caldav_bind_host` design — **not** the older loopback `:8444` SNI-router route). An earlier collision — the nest also bound `0.0.0.0:8443`, so the MDA `EADDRINUSE`-crash-looped and served neither IMAP nor CalDAV — is **resolved**: the nest's internal listener moved off 8443 to **`3000`** (`FAUNA_PORT`), so `8443` is CalDAV's alone. See `caldav-server.md` § Implementation status today (⚠ COLLISION FOUND 2026-06-20 → RESOLVED).

**Networking.** The bundle uses `network_mode: host` so the in-container MDA can bind the box's real LAN IP and the SNI router can front `:443` on the LAN. A behind-NAT home box has no public-routable interface, so all-host-interface binds are LAN-only in practice. **nest's own internal listener binds loopback** under host networking — the compose sets `FAUNA_BIND_ADDR=127.0.0.1` so nest's WS-RPC/HTTP surface (`:${FAUNA_PORT:-3000}`) is *not* a second face on the LAN; every co-resident consumer (the SNI router's default/PROXY backends, the MTA `--nest-endpoint`, the relay sidecar) already dials `127.0.0.1:${FAUNA_PORT}`, so loopback is transparent to them, and the only deliberately LAN-exposed surfaces are the SNI router `:443` and the MDA's IMAP `993/143` on `${FAUNA_LAN_BIND_IP}`. (The explicit loopback bind is what keeps that surface off the LAN under host networking; bridge-networked deployments keep the image default `0.0.0.0` because their netns isolates the port.) **If the box has a public IP**, do not use host networking — switch to bridge networking and publish only `${FAUNA_LAN_BIND_IP}:443:443`, `:993:993`, `:143:143` so nothing is reachable from the public internet (and set the MDA IMAP binds to `0.0.0.0:993/143` so Docker's port mapping does the LAN restriction). The home box must never expose IMAP/CalDAV to the public internet ([`../nest/deployment-home-with-public-relay.md`](../nest/deployment-home-with-public-relay.md) § Don't do these).

### 3. Pair the two nests

Pairing is the user's own action from their app, not the installer's — the installer **seeds** only the pre-claim NAT-mode default (`FAUNA_MODE=private`, so the box boots LAN-bound with no MTA/ACME *before* any client connects — no exposure window); the client provisions the authoritative NAT mode (onboarding wizard + admin toggle, persisted in nest DB state — [`../nest/common.md`](../nest/common.md) § NAT mode) and the pairing itself — the authorization, the public box's URL the home box's workers dial, and whether your posts are forwarded there, all on your own pairing row (owner: [`../nest/private-mode.md`](../nest/private-mode.md) § Implementation status today; product invariant: nest policy is app-set, never CLI/env). If the home box reaches the public box at a private address (a LAN, a VPN, a docker bridge), link from the home box's **admin** account: only an admin's row names the deployment's topology, so only its URL may be non-global ([`../nest/private-mode.md`](../nest/private-mode.md) § Pairing Flow). Because the relay is asymmetric (the home box polls the public box), the relationship needs the user's `fauna.pair.add` row on **both** nests ([`../nest/private-mode.md`](../nest/private-mode.md) § Pairing Flow):

- **Public box** authorizes the home box to pull — link the home box's nest id while your app is connected to the public box.
- **Home box** row makes its sync/relay worker run, against the public box's URL the row records — link the public box while your app is connected to the home box (on the LAN).

Each nest's id (its Ed25519 public key) is shown in the app's nests settings (`nests-item-nest-id`, abbreviated hex). The **primary UX is one Link action that seeds both ends** — `LinkBoth`, built on all 7 apps (the client, authenticated to both nests, writes both rows — [`../../behavior/linked-nests.md`](../../behavior/linked-nests.md) § One action seeds both ends); the two directional links above remain the fallback (e.g. the out-of-band single-end path). Default capabilities (`default_self_sync()`, owned by [`../nest/private-mode.md`](../nest/private-mode.md)) include the `mail_pull` relay grant, so mail relays out of the box.

Once both rows exist, the home box's worker drains the public box's sealed `__mail` over the federation channel, appends each record to its own store, and acks → the public box purges (no readable copy remains). LAN MUAs read the plaintext mail from the home box over IMAP/CalDAV; outbound submission and MX delivery stay on the public box ([`../nest/deployment-home-with-public-relay.md`](../nest/deployment-home-with-public-relay.md) § Outbound mail).

## Native (systemd) home box

The Docker bundle is the recommended path. A native-systemd home box is the [`linux-nest.md`](linux-nest.md) install with `mode = "private"` seeded in `nest.toml` (nothing names the public box — the pairing in step 3 does), the MDA IMAP listeners bound to the LAN IP via the topology hatch, and no MTA service enrolled. The pairing (step 3) is identical — it is the user's app action, independent of how the binaries are packaged.
