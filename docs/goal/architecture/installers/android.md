## Goal

One release **AAB** (Android App Bundle), built reproducibly from the same tree as every other app, signed via **Play App Signing**, and distributed through **Google Play as the primary channel**. F-Droid and a direct-download APK are follow-on channels once the source is public. The developer account is owned by the organization — never an individual — with a second board member as co-admin for continuity. **When a version's build goes up (ruled 2026-10-13):** to Play's testing track only after the nest of that version is on `:test` and the acceptance nest fauna.build serves it, to production only after the nest promote to `:latest` — the order is the release table's ([`../release-table.md`](../release-table.md) § Tag gate and release table), the channel's semantics [`../image-pipeline.md`](../image-pipeline.md) § Image tags & channels → *The UAT channel*. Which Play tracks pass Google's review (internal testing does not), the states an upload passes through and where its live state is recorded (`installer/store-review.toml`) are [`store-review.md`](store-review.md)'s.

**Four shipping build types, one tree (the `foss` split ruled 2026-08-24; the `kids` flavor ratified 2026-09-25).** `release` is the Play AAB (for `0.1.4` the Play AAB is `storeSafe`, next paragraph); `storeSafe` is `release` minus the gated-feature registry members ([`../dynamic-features.md`](../dynamic-features.md) § The App-Store escape hatch); **`foss` is `release` minus every proprietary Google Play client library** — the F-Droid / direct-download artifact. ## Signing model

Android has no CA-issued developer certificate — both keys below are self-generated; the "certificate" a store relationship provides is the **developer account** plus **Play App Signing**.

- **App signing key: Google-generated and Google-held** (Play App Signing — mandatory for new Play apps). Devices verify installs against it; Google re-signs each AAB on delivery. Choosing Google-generated (rather than uploading our own) means the key that user devices trust can never leak from a dev machine.
- **Upload key: a locally generated keystore** that signs what we upload to Play. Held on the primary dev machine **outside the repository** (never committed, never in CI secrets until a release pipeline exists); passwords held by the user. An upload key is recoverable — Google support can register a replacement after identity re-verification — so local custody is acceptable where it never would be for the app signing key.
- **Release builds** read the keystore from an untracked, machine-local properties file; when it is absent the release build simply stays unsigned (dev machines and CI don't need the key to build). Concretely: a dedicated dev-fleet script generates the keystore (PKCS12, RSA-4096, alias `fauna-upload`, 25-year validity) into `~/.config/fauna/android/upload-keystore.jks` and writes the sibling `signing.properties` that `app/build.gradle.kts` reads; the password is generated (32 hex chars from the kernel CSPRNG; `--prompt` types your own instead), passed to `keytool` through the environment rather than argv, and never lands in a tracked file. Generated is the default because Gradle must open the keystore unattended — the password therefore sits in plaintext beside the `.jks` whoever picks it, so permissions rather than the password guard the key, and a typed one only adds the risk of forgetting it. The consequence: back up the whole directory, not just the `.jks`. Signing is therefore *opportunistic* — the `signingConfig` materialises only where that file exists, so every other machine still builds the identical R8/minify path and only the final upload artifact needs the key.
- **The upload artifact is an AAB, built by `just android-bundle` (`release`), `just android-bundle-store-safe` (`storeSafe`, the `0.1.4` upload) or `just android-bundle-store-no-payments` (`storeNoPayments`, the upload from `0.1.5` on — § Goal)** — Play splits the bundle per device itself and will not take the APK `just android-release` produces. The three recipes share one body: it greps the bundle's dex for the debug `TestAgent`'s own strings, which is [`../e2e-automation-surface-gating.md`](../e2e-automation-surface-gating.md) point 15's release-artifact check applied to android's shipping artifact, and reports whether this machine signed it. The `storeSafe` bundle also runs the store-safe excision scan on itself (`scripts/android-store-safe-scan.sh`, the pattern list `just android-store-safe-check` holds the witness APK to): no payments, zaps or peer-to-peer-sharing element id in its dex and no kind string in its dex or native library, with an always-rendered id and a kept plane's kind string as positive controls so an empty scan cannot pass; the `storeNoPayments` bundle runs the same scan's `no-payments` mode, which proves the payments and zap patterns absent and the sharing ones present. Both store build types are `initWith(release)` with neither an application-id nor a version-name suffix, so their bundles carry the main Play package, the fleet `versionName` and the release signing config.
- **Play's "automatic protection" (installer-source check) is DECLINED — 2026-08-22, surfaced live at app creation.** Play offers to inject a check into the shipped code that prompts users who obtained the app from any other source to re-download it from Play. Three ratified positions rule it out: § Goal makes **F-Droid and direct-download APK follow-on channels**, so the check would nag our own users for using our own channels; [`../../behavior/region-blocking.md`](../../behavior/region-blocking.md) § Region determination treats **sideloaded and self-built apps as a first-class case** with its own determination rule, not an anomaly; and § Goal requires the AAB be **built reproducibly from the same tree**, which a post-upload code injection defeats — the thing users could rebuild and compare against would no longer be the thing that ships. The toggle lives under Play Console → App integrity and takes effect per release, so it must be verified OFF before each upload, not once.

- **Direct-download APKs are a separate signing domain**: Play App Signing covers only Play-delivered artifacts, so a direct APK needs a key we hold and protect ourselves. That custody decision is deferred until the channel exists. F-Droid signs its own builds from public source (their standard flow), so it adds no key custody here.

## Versioning

`versionName` is the product version — the ONE fleet-wide string, sourced from the root `Cargo.toml` (owner: [`../product-version.md`](../product-version.md); the `version-lockstep-check` merge gate holds them equal) — and `versionCode` is **derived from it arithmetically**, never tracked by hand as a second number:

```
versionCode = major * 10000 + minor * 100 + patch
```

So `0.1.0` → `100`, `0.1.1` → `101`, `1.0.0` → `10000`. One number a human edits (the product version); the counter Play actually enforces follows mechanically. Bumping the product version can never *lower* the counter, which is the property Play requires — it rejects both reuse and regression of `versionCode`.

**A reship of unchanged product code bumps the patch version — fleet-wide.** Play refuses a `versionCode` it has already accepted in any upload, a never-rolled-out draft included; whether deleting such a bundle from the App bundle explorer frees the code is undocumented, and the project never relies on it ([`../product-version.md`](../product-version.md) § Version strings are never reused or re-meant → *An upload spends the string*, ruled 2026-10-07 on the refused `0.1.2`/`102` draft) — so every upload spends its code, and a re-upload after a refused rollout is a reship at the next patch. This scheme deliberately gives each product version exactly one code. The reship rule itself is now owned fleet-wide by [`../product-version.md`](../product-version.md) § Reships (it generalizes what this section first ratified for Play): the bump is a one-commit product-patch bump across every surface, and only the store that demanded the re-upload ships it.

**Why derived-and-committed rather than computed at build time.** A `versionCode` generated from git history (commit count, tag distance) is monotonic on this repository's linear `origin/main` and needs no human step — and it was rejected anyway, for two reasons:

- **F-Droid builds from source, not from this checkout.** It is a declared future channel (§ Release channels), and its builds run in F-Droid's own environment against a source tarball or tag, where a commit-count derivation is either unavailable or yields a different number than the Play upload claimed. A `versionCode` that cannot be reproduced from the source tree alone actively fights a channel this document already commits to.
- **It would be a second mechanism.** Windows hand-maintains its version in a committed file; a git-derived Android counter would make the two stores disagree about where a version comes from, for no gain (priority #1).

**Both numbers live in `apps/fauna-android/app/build.gradle.kts`**, and the file states the arithmetic beside them so the relationship survives a cold read.

`versionCode` is capped by Play at 2 100 000 000; this scheme reaches that only at major version 210 000, so the ceiling is not a practical constraint.

## Store constraints

- **Target API floor: Play refuses an upload whose `targetSdk` is below its current floor — API 36 since the floor was hit on 2026-10-07.** The first internal-testing rollout (`0.1.2`/`102`) was blocked with *"Your app targets API level 35 and must target at least API level 36"*. `compileSdk` and `targetSdk` therefore track the floor together (`app/build.gradle.kts`), and the SDK platform every build machine installs follows them. Google raises the floor roughly yearly; a raise opts the app into that Android release's targeting-gated behaviour changes, each of which is checked against the code at the bump and recorded as handled or not applicable.
- **Android 16 (API 36) behaviour changes, checked 2026-10-07:** edge-to-edge can no longer be opted out of — not applicable, the app never opted out (no `windowOptOutEdgeToEdgeEnforcement`; API 35 already enforced it) and its screens handle insets; predictive back is on and `onBackPressed()` is no longer called — compatible, back navigation is Compose `BackHandler` with no `onBackPressed`/`KEYCODE_BACK` override; orientation, resizability and aspect-ratio restrictions are ignored at smallest width ≥ 600dp — not applicable, the single activity declares none and nothing calls `setRequestedOrientation`; `elegantTextHeight`, `scheduleAtFixedRate`, `BODY_SENSORS`, the Bluetooth bond-loss intents and `MediaStore#getVersion` — not used; safer intents (`intentMatchingFlags`) and the local-network permission — opt-in, not opted into (no `NsdManager`); app-owned photos pre-selected in the picker — not applicable, the app requests full `READ_MEDIA_IMAGES`/`READ_MEDIA_VIDEO`, never partial access.

- **Play's payments policy against Fauna's payments plane (read 2026-10-16 from Google's own pages; ruled 2026-10-18 — (b), no payments, at the end of this bullet).** *The policy, by item.* The Payments policy (Play Console Help, "Payments", nine numbered items; the page carries no date, and the Policy Archive's newest version is the 2026-08-26 PDF): item 2, apps charging for in-app features, content or services "must use Google Play's billing system for those transactions unless Section 3, 8, or 9 applies", with subscriptions and "service upgrades" among its examples; item 3, that billing system "must not be used in cases where" the "payments include peer-to-peer payments, online auctions, and tax exempt donations"; item 4, "apps may not lead users to a payment method other than Google Play's billing system" except where items 3, 8 or 9 apply; items 8 and 9, an alternative billing system in the app, or a link out of it, for "users in eligible countries/regions" only under a program the developer enrolls in (the user-choice billing page lists the EEA, Australia, Brazil, Indonesia, Japan, South Africa, the UK and the US for non-game apps, and requires the alternative-billing API integration, every transaction reported within 24 hours and a service fee; South Korea and India have programs of their own). Google's FAQ "Understanding Google Play's Payments policy" draws the line that matters here: a user-to-creator tip is peer-to-peer, and the billing system is not required (and "must not be used"), "in cases where 100% of the tip or contribution from a user goes to the creator" and "the payment does not grant access to any digital content or services" — "If any of these things is not true, then Google Play's billing system must be used"; in-app steering "includes directly linking to a webpage that could lead to an alternate payment method"; and a consumption-only app may show content that is "part of a paid service" and "provide additional information about purchasing options without direct links" (its example wording: "Go to our website to upgrade your subscription to Premium"). Two more pages bound the reading. For US users, since 2025-10-29 under the Epic injunction, Google "will not require Google Play Billing" and does not prohibit other payment methods or links (the 2026-03-04 settlement asks the court for a revised injunction; the external-links and alternative-billing programs carry transaction reporting and service fees from 2026-10-01, external links from 2026-12-01) — a US-only regime that Fauna's region-blind payments plane cannot ride without per-region gating and a transaction report it has no view of, so it is not relied on. And the "Cryptocurrency Exchanges and Software Wallets" policy notes "Non-custodial wallets are out of scope"; Fauna holds no keys and no funds and is no wallet at all — it reads zap receipts ([`../../behavior/monetization.md`](../../behavior/monetization.md) § Zap receipts) — so zaps are outside it. *Set against the plane.* Fauna the organisation is never a party to any payment: every payment runs user→user (a tip to an author, a tier or a per-post unlock bought from an author, membership bought from a nest's admin) through a provider the payee chose, and nothing takes a cut, so the only question is which payments grant access. **Tips** (that doc's § Tips: no entitlement consequence by construction; every zap is a tip until a Nostr-advertise ingress exists) meet both FAQ conditions — peer-to-peer, Play billing must not be used — and the app's tip surface (`post-tip-total`, `post-tip-count`, `post-tip-list`) displays receipts and links nowhere. **Tiers, per-post unlocks and nest membership** grant access, so item 2 binds them on Play outside the US: the buyer-side affordances that open an author's payment URL (`subscription-offer-payment-link`, `gated-post-payment-link`, `gated-post-buy-button`) are exactly the "directly linking to a webpage that could lead to an alternate payment method" the FAQ names — and Play's billing system cannot carry them either, since the recipient is a user rather than the developer and no alternative-billing program fits a plane with no transaction view. **Claim-code redemption** (`subscription-claim-redeem-*`: a code the buyer obtained elsewhere) and the **author side** (provider management, claim mint and void, the asking-price inputs, zap-signer designation) sell nothing in the app and lead no buyer anywhere — the consumption-only shape the FAQ allows. *The three postures put to the owner.* **(a)** The full `release` build rests on reading every Fauna payment as peer-to-peer, which the FAQ refuses for the access-granting ones; a rejected update or a policy-violation removal of the listing is the realistic outcome, with the hatch ([`../dynamic-features.md`](../dynamic-features.md) § The App-Store escape hatch) as the recovery. **(b)** No payments at all — `storeSafe` today, the no-payments flavour that keeps sharing once it exists — has no policy exposure, and loses tips, the one plane Play permits, with the rest. **(c), recommended:** a hybrid cut along Google's own line — keep tips, claim redemption, the author side and sharing; excise only the buyer-side purchase link-outs and buy prompts of the access-granting offers (a tier row keeps its name, price and description, a gated post its badge and price; no link). The same line is Apple's: App Store Review Guideline 3.2.1 (vii) allows "a monetary gift to another individual without using in-app purchase" when "100% of the funds go to the receiver of the gift" and 3.1.1 forbids the link-out, so (c) is a candidate for one store flavour on all three stores rather than a Play-only shape, which is why the flavour matrix leaves room for it as a third flavour ([`../dynamic-features.md`](../dynamic-features.md) § The App-Store escape hatch → *The store flavors*, *Room for a finer cut*) and it is not ruled here. *Holds under every posture.* No Play Billing integration serves payments (it must not be used for the peer-to-peer ones and cannot be used for the access-granting ones); the queued `com.android.billingclient:billing` need (`supply-chain/bump-queue.toml`) serves the android region leaf's storefront arm and is unaffected. Under (a) and (c) alike the organisation's own nests never sell membership or tiers to Play users through the app — a payment to the developer is item 2's own case. If (a) or (c) is ever ruled, the Play Console declarations the posture needs (the in-app-purchase and financial-features answers) are public texts: request rows under [`../public-texts.md`](../public-texts.md) § The rule, never written by the session that lands the build. ***The ruling (owner, 2026-10-18): (b).*** Play ships without payments — the `storeNoPayments` flavour, sharing kept — from `0.1.5`, and keeps doing so **until each app has made its first successful release in every store it ships through**; only then is payments on Play, (a) or (c), re-opened, as a fresh owner ruling. The recommendation above stands as the reading that ruling will start from, not as a posture anything ships. Under (b) nothing else moves: no Play Billing need (the queued one serves the storefront arm, above), no Play Console payments declaration, no public-texts request; the hybrid's third flavour is not built ([`../dynamic-features.md`](../dynamic-features.md) § The App-Store escape hatch → *The store flavors*, *Room for a finer cut*).
