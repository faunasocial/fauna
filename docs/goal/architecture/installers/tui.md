## What any channel must satisfy

These are constraints the existing goal docs already impose; they hold whichever channel is chosen.

- **The artifact is two binaries, not one.** The terminal app is the control surface for the per-user sync agent and its spawner expects `fauna-sync-agent` beside `fauna-tui` ([`../apps/tui.md`](../apps/tui.md) § Sync-agent control surface). A channel that ships `fauna-tui` alone ships an app whose Folders and Devices pages cannot provision sync.
- **The headless box is the terminal app's defining use.** The terminal app exists to be "usable over SSH" on a machine with no desktop session, with a sealed-file credential store for exactly that case ([`../apps/tui.md`](../apps/tui.md) § Credential storage). A channel that can only be reached by installing a desktop package (GTK, a window server) does not serve that machine.
- **The contract's ending is the same as every other app's:** obtain it the way the platform provides it, and end with the app open and signed in ([`README.md`](README.md) § The channel contract). The witness is an install-then-drive test added to the existing `get-the-app` outcome 1, in the Linux leg's shape, with a debug-configuration binary as the installed subject because release builds compile the automation surface out ([`../e2e-automation-surface-gating.md`](../e2e-automation-surface-gating.md)); that substitution is honest only while the install path branches on no build configuration.
- **Which flavor ships follows the venue.** A store-hosted package carries the `store-safe` build (`just tui-store-safe`); a direct download or OS package carries the full default-feature build, which needs a release recipe of its own.
- **The train.** The nest and all seven apps ship at one version, and "every app's channel that exists" is what a release cuts ([`../product-version.md`](../product-version.md) § Bumping). Once a terminal-app channel exists it rides every release; until then it holds nothing back.
- **macOS signing decides the credential experience.** The macOS login-Keychain entry the terminal app, the desktop app and the sync agent share is access-controlled by the reading binary's signing identity; the terminal app is ad-hoc signed today ([`macos.md`](macos.md), the credential-slot notes). An ad-hoc or unsigned terminal app is re-prompted for Keychain access whenever its binary changes, and a browser-downloaded unsigned binary is quarantined by Gatekeeper. Only a Developer ID-signed binary avoids both.

## Candidate channels

### A — ride the desktop packages

`fauna-tui` joins the payload of each platform's existing package: `$PREFIX/bin/fauna-tui` in the five Linux methods (`install.sh`, `.deb`, Flatpak, Snap, AppImage), a component or an added binary in the macOS `.pkg` (Developer ID-signed and notarized with the rest), `fauna-tui.exe` in the Windows MSI (SignPath-signed with the rest) and, as the `store-safe` flavor, in the Store MSIX.

- For: opens no new public surface; inherits each package's signing, update path and uninstall; the sync agent is already in every one of those payloads, so the two-binary constraint is met for free; on macOS it is the only option here that gives the terminal app a stable Keychain identity.
- Against: **does not serve the headless box** — the Linux packages install a GTK desktop app and its dependencies, and a Flatpak/Snap/AppImage sandbox is an awkward home for a terminal program launched over SSH; the terminal app on a server is the case the app was built for. Five Linux methods plus two Windows packages plus the `.pkg` is eight payload edits and eight places for the binary to drift.

### B — per-OS archives from the tag-triggered release workflow

`release.yml` gains `fauna-tui` and `fauna-sync-agent` in its build loop for the four targets it already builds (Linux x86_64 + aarch64, macOS x86_64 + aarch64) and the Windows job gains both arches; each pair is published to the GitHub Release as one archive per target, covered by the same `SHA256SUMS` and per-file cosign bundle as every other artifact. The user downloads, verifies, unpacks into a directory on `PATH`, and runs `fauna-tui`. A small `install.sh` in the archive (the Linux desktop leg's shape: copy two binaries into a prefix, `--uninstall` removes them) gives the witness test a real install step to run.

- For: serves the headless box directly; rides a workflow, a signing scheme and a publication venue that already exist for the server binaries, so it is an extension of an existing channel rather than a new surface; one build definition for all three operating systems; ships the full flavor.
- Against: no auto-update (the user re-downloads per release, as for the server binaries); on macOS the archive's binary is ad-hoc signed unless the macOS release job Developer ID-signs and notarizes it — without that, Gatekeeper quarantines a browser download and the Keychain re-prompts on each update; on Windows an unsigned `.exe` draws a SmartScreen warning unless it goes through the same SignPath signing as the MSI.

### C — a language-registry install (`cargo install`)

- For: one command for a user who already has a Rust toolchain.
- Against: the weakest posture on every axis the project cares about. It publishes the terminal app *and the whole `libs/fauna-*` tree it depends on* to a registry as a second, permanent, separately-versioned public surface; the user compiles unattested source against whatever dependency versions resolve that day unless `--locked` is remembered; it needs the pinned nightly toolchain; it cannot deliver the sync agent beside the binary; and nothing is signed. It fits neither the release-integrity model nor the two-binary constraint.

## The ratified channel

**B as the terminal app's channel, with A's macOS and Windows legs as the signed form of the same binaries — and C refused.** Concretely: the release workflow builds and publishes the `fauna-tui` + `fauna-sync-agent` archive for every target (the channel, and the only one that reaches a headless machine); the macOS `.pkg` and the Windows MSI additionally carry the same `fauna-tui` binary, because on those two systems the package is what gives it a trusted signature and, on macOS, a stable Keychain identity. The Linux desktop packages are left alone: a Linux user with a desktop installs the archive as easily as a server user does, and eight payload edits buy nothing the archive does not. `apps/fauna-tui/Cargo.toml` gains `publish = false`, making the refusal of C mechanical. This is the superset of A and B trimmed to the legs that each earn their place. **On macOS the archive's `fauna-tui` and `fauna-sync-agent` are Developer ID-signed and notarized by the macOS release job before the macOS archive counts as published** — an ad-hoc-signed archive never ships (Gatekeeper would quarantine a browser download and the Keychain would re-prompt on every update). **The Windows Store MSIX does not carry the terminal app.**

**Mechanics, as built.** The payload is defined once, in `apps/fauna-tui/packaging/assemble-archive.sh`, and installed by the `install.sh` it stages beside the binaries; the release workflows and the witness both run those two scripts, so they cannot disagree about the layout. Archives are named `fauna-tui-<target>` after the release's existing `<crate>-<target>` convention (`x86_64-linux`, `aarch64-darwin`, `x64-windows`, …). The Linux and Windows legs live in `release.yml`; the macOS legs live in `release-macos.yml`, because that workflow's `sign` job is the only place the Developer ID certificate and the notary key exist — `release.yml`'s darwin legs build server binaries with no signing step at all. The Windows archive is a zip with no `install.sh` (the user unpacks it into a directory on `PATH`); the MSI is the signed, on-`PATH` form there. In the desktop packages the terminal app is its own selectable component on both systems — `TerminalApp` in the MSI, `social.fauna.tui` in the `.pkg`, default on — never folded into the sync or desktop-app component, so unticking either leaves it installed.

The witness, under any of these: `tests/e2e-unified/tests/artifact/test_tui_installed_product.py`, tier_4, runs the archive's real `install.sh` into a repo-private prefix with debug-configuration binaries staged in place of release ones, asserts both binaries landed, drives a login-to-feed journey through the installed `fauna-tui`, and uninstalls — added as a witness line under `docs/features/get-the-app.md` outcome 1, with a recorded run closing the terminal app's cell.

## Decisions (user ruling 2026-09-26)

1. **Channel:** the recommendation — B (per-OS `fauna-tui` + `fauna-sync-agent` archives from `release.yml`) everywhere, plus the macOS `.pkg` and the Windows MSI carrying the same binary; C (`cargo install`) refused.
2. **macOS archive signing:** Developer ID-signed and notarized before the macOS archive is published; no ad-hoc-signed interim.
3. **Windows Store MSIX:** does not carry the terminal app.
