## Goal

One signed iOS build per version train, archived from the recorded public commit at the product version, uploaded to App Store Connect and served to its audience by **TestFlight** before the first public release and by **the App Store** from the first public release on. The same bundle, the same source and the same version string as every other app on the train ([`../product-version.md`](../product-version.md) § Bumping); the two channels differ only in who may install and in which review the build passes.

## Signing

- **Identity:** `Apple Distribution: Fauna Social (7457N3M72H)`, minted 2026-08-22 and held in the login keychain of the macOS development VM with its `.p12` in the organization's password manager. It signs both channels: a TestFlight build is an App Store distribution build.
- **Profiles:** an **App Store** distribution provisioning profile for the app's App ID and one for each embedded extension's App ID, wired into the **manual** signing of the four iOS targets — the app, its File Provider pair and its widget (`CODE_SIGN_STYLE = Manual`; automatic signing would need an Apple account session on the build machine, which the next bullet forbids). Each target's Release configuration names the `Apple Distribution` identity, the team and its profile by **name** — names survive a regeneration, UUIDs do not — scoped to the device SDK, so simulator and macOS builds stay ad-hoc signed; `apps/fauna-apple/ExportOptions-AppStore.plist` names the same four profiles for the export. A profile is a snapshot of its App ID's capabilities, so it is generated **after** the App ID carries every capability the app declares (push notifications, Declared Age Range, App Attest) and regenerated whenever one is added. Profiles expire yearly; renewal is the channel's one recurring maintenance cost.
- **The Apple account stays off the development VM (user ruling 2026-08-22).** The VM holds signing identities and profiles; every portal act — minting a certificate, a profile or an App Store Connect API key, answering a questionnaire, managing testers — happens in a browser on the host, signed in as the organization's Apple account, never on the VM.
- **What the archive proves:** `tests/e2e-unified/tests/artifact/test_ios_archive.py` has two legs. The unsigned leg archives the real device target in the Release configuration with signing disabled — the SDK, the arm64 compile, the extension embedding, the layout — and runs on any macOS box. The signed leg archives with signing on, exports a signed `.ipa` to disk and reads the signature, each bundle's embedded profile and the signed entitlements back off it; it then signs the unsigned leg's archive with the tree's own signer (`scripts/ios-store-sign.py`, [`store-review.md`](store-review.md) § The store legs, *How the iOS store app is signed*) and holds the two packages equal — each bundle's signed entitlements key for key and value for value, its embedded profile, its authority, and the files outside the signatures — so the exporter stays only as this reference; it runs where the identity and the four profiles are installed and skips as an environment gap elsewhere. **Neither leg contacts Apple:** manual signing, no `-allowProvisioningUpdates`, no authentication key, an export `destination` of `export` and `manageAppVersionAndBuildNumber = false` — `test_apple_identifier_pins.py` pins the tracked half on every machine.

## The channel

**TestFlight is the pre-release channel, and the alpha audience is TestFlight EXTERNAL testers (user ruling 2026-10-07).** External testers are invited by email or by a public link, need no App Store Connect account and hold no role on the team; up to 10,000 may be invited, and a build serves them for 90 days from upload. The price is **Beta App Review**: the first build of each version is reviewed before an external group can install it, which brings the App Store review questions forward to the alpha — and that is wanted, because a finding at the alpha is cheaper than the same finding at the public submission. **Internal testing is rejected for the alpha:** an internal tester must be an App Store Connect team member holding a role, and an alpha tester is not staff and gets no console access. Internal testing stays available for the team's own smoke installs of a build before it is submitted to review; it is never the audience. **When a version's first external build goes up (ruled 2026-10-13):** after the nest of that version is on `:test` and the acceptance nest fauna.build serves it — the reviewer Beta App Review sends signs in there at the matching version — and the public App Store release of the version only after the nest promote to `:latest`; the order and its reason are the release table's ([`../release-table.md`](../release-table.md) § Tag gate and release table), the channel's semantics [`../image-pipeline.md`](../image-pipeline.md) § Image tags & channels → *The UAT channel*. Which of these tracks pass a review, the states an upload passes through, where its live state is recorded (`installer/store-review.toml`) and what the organisation does while a review is open are [`store-review.md`](store-review.md)'s.

Two consequences, both ruled 2026-10-07 and owned where they belong: **the user-initiated reporting surface is built on iOS before the first external build** ([`../../behavior/moderation.md`](../../behavior/moderation.md) § User-initiated reporting, the sequencing clause — Guideline 1.2 is what Beta App Review would otherwise raise), and **the store-safe archive's payment-link question is answered first** ([`../dynamic-features.md`](../dynamic-features.md) § The App-Store escape hatch owns what the archive may carry).

**The App Store is the release channel.** The public listing is a separate, later act: the App Store submission with its screenshots, the rating questionnaire (§ Listing posture) and the full App Review. Nothing in the alpha publishes the listing; the official-apps manifest's `app-store-listing` entry stays `pending` through TestFlight with a sentence saying the app is in invitation-only testing, under the uniform listing rule [`../release-integrity.md`](../release-integrity.md) § Release signing → *The official-apps list* states.

**Testers' addresses live in App Store Connect only** — never in a file, a commit message or a note; an invitation is sent from the console or as the public link, and the invited group is named in this document by its role, not its members.

## Upload mechanics

1. **The source tree is the recorded public commit at the product version** — the rule and the record are [`../release-integrity.md`](../release-integrity.md) § Release signing → *A store upload is built from a recorded public commit*; on the macOS VM that is a clean checkout of the public repository at that commit, never the private tree.
2. **Archive unsigned, then sign:** `xcodebuild archive` of the `Fauna-iOS` scheme in the Release configuration over the store-safe device `FaunaFFI.xcframework` (`just apple-ffi-store-safe` — the host-only flavor the debug recipes stage has no `ios-arm64` slice and cannot link, and plain `just apple-ffi` carries the payment surfaces the store build excises), with signing OFF (`CODE_SIGNING_ALLOWED=NO`) and the excision flags `just apple-ios-store-safe-check` passes (`OTHER_SWIFT_FLAGS` `-D FAUNA_EXCISE_PAYMENTS -D FAUNA_EXCISE_P2P_SHARE`) — the build half, which holds no credential; then the sign half: the tree's own signer, `scripts/ios-store-sign.py`, signs the archived app bundle by bundle with the Distribution identity and each bundle's App Store profile over the entitlements it computes, packages the `.ipa` and reads every bundle back ([`store-review.md`](store-review.md) § The store legs, *How the iOS store app is signed*). The exporter is off the release path. The archive is the store-safe flavor the Apple family ships ([`../dynamic-features.md`](../dynamic-features.md) § Platform-family surface excision); `just apple-ios-store-safe-check` is its unsigned witness.
3. **Upload** with Apple's own tool — `xcrun altool --upload-package` on the signer's package, which validates it before it uploads — authenticated with an App Store Connect API key (the store key below in the release workflow); the tracked `ExportOptions-AppStore.plist` stays export-only and serves only the archive test's reference; no third-party upload tooling on the path where signing material is in memory ([`../release-integrity.md`](../release-integrity.md) § Defense priority). The first upload is done by hand on the macOS VM, as one command — `just ios-store-upload <version> upload` runs steps 1–3 end to end (`export`, its default mode, stops before the upload) and prints the store-review lines the session then writes from the console reading ([`store-review.md`](store-review.md) § The record); it teaches a later workflow what to reproduce — the workflow transcribes that recipe, as the Windows store legs' workflow transcribes theirs — and is the irreversible moment the bundle identifier and the version history begin.
4. **In App Store Connect:** the build processes (it asks no export-compliance question: the Info.plist key answers it, next bullet), the build is attached to the external group and submitted to Beta App Review; the invitation goes out when review passes.

**From the store leg on, the upload is a step of the release (designed and built 2026-11-12, not yet run — § Implementation status today).** [`store-review.md`](store-review.md) § The store legs owns the shape: the app is built unsigned by a job of `release-macos.yml` that holds no credential, and the signing, the upload with Apple's own tool, the TestFlight groups and the Beta App Review submission are steps of that workflow's approved `sign` job. The signing there is the tree's own signer, bundle by bundle with each bundle's profile and a computed entitlements set, not step 2's signed archive and export (corrected 2026-11-12: an archive built unsigned and signed by the exporter carries no entitlements — the same section's *How the iOS store app is signed*). Steps 1–4 above then describe the source tree, the flavour, the upload and the console acts the workflow transcribes, `just ios-store-upload` becomes the macOS rehearsal of the same two halves (build unsigned, then the signer; its `export` mode), and the roles of the two keys diverge as the next paragraph foresaw: the Developer-role key keeps notarization and the fleet's reads, and a second key of the App Manager role, resting only in the `release-macos` Environment, uploads and submits.

**One App Store Connect API key serves notarization and upload.** [`macos.md`](macos.md) § Build Pipeline → *Required Environment Variables* already names the key (`FAUNA_NOTARY_KEY_FILE` / `_KEY_ID` / `_ISSUER`) as what the release workflow notarizes with; a key of the Developer role may notarize and upload alike, so the same key, held the same way (the release Environment's secrets, or the maintainer's local store), is the upload credential — a second key is minted only if the roles ever diverge. It is role-scoped and revocable on its own and keeps the Apple account's password and second factor out of every machine.

**Export compliance:** the key's value and why are owned by [`../export-compliance.md`](../export-compliance.md) § What each store form answers (the organization's representative's questionnaire answer is a legal attestation, theirs alone, given in an authenticated App Store Connect session — App Store Connect → the app → App Information → App Encryption Documentation). What this channel depends on: **App Store Connect's upload validation refuses a bundle that declares non-exempt encryption (`ITSAppUsesNonExemptEncryption` `true`) and carries no `ITSEncryptionExportComplianceCode` matching the app's export-compliance record** (measured 2026-11-01: "Invalid Export Compliance Code … the export compliance key value [] in the app's Info.plist doesn't match"). Since 2026-11-06 the key is `false` — the questionnaire, answered that day, needs no documents and so issues no code — so the upload carries no code and App Store Connect asks no encryption question per build. **The record is read from App Store Connect, never relayed by hand:** `just ios-export-compliance` reads the app's encryption declarations — state, answers, `codeValue` — through the App Store Connect API key below (from the `FAUNA_NOTARY_*` triple, else the local store `~/.config/fauna/asc/` — the `.p8` and a one-line `issuer` file), and `tests/e2e-unified/tests/live/test_ios_export_compliance_live.py` (macOS, tier_4) holds the Info.plist to that record in both directions: with the key `false`, the plist pins no code and App Store Connect holds no standing declaration with one; with the key `true`, the pin equals the newest standing declaration's code. So a drift — Apple asking for a fresh declaration, or a code issued that the key ignores — is caught before an upload rather than at it.

**What upload validation checks that no local build does (measured 2026-11-01):** an app icon (`CFBundleIconName` and the 120 px iPhone and 152 px iPad tiers — the target's single-size `AppIcon` asset catalog, rendered from the brand mark) and `UISupportedInterfaceOrientations` (all four on iPad, for multitasking). `xcodebuild` archives and exports a bundle without either; `test_apple_identifier_pins.py` pins the project half and `test_ios_archive.py`'s signed leg reads them off the exported bundle.

**The privacy manifest.** App Store Connect also checks, at upload, that a bundle calling one of Apple's required-reason APIs declares it with a reason in a privacy manifest. `Fauna-iOS/Resources/PrivacyInfo.xcprivacy` is copied into the app and its File Provider extension — the two iOS bundles of the main app that link FaunaKit and the shared-Rust library — and declares `UserDefaults` (`CA92.1`, the app's own settings), file timestamps (`C617.1`, the stat family the shared-Rust storage layer and the File Provider call on files in the app's container) and disk space (`E174.1`, the statfs/statvfs family the storage layer calls before writing), the three categories the Swift sources and FaunaFFI's symbol table show; `NSPrivacyTracking` is false and the collected-data types are the App Store listing's App Privacy answers, each linked, untracked, for app functionality. A new required-reason API in either the Swift or the Rust code adds its category here in the same change. The widget and the File Provider UI link neither library and carry none; the kids app collects a different set and has no manifest yet. `test_apple_identifier_pins.py` pins the manifest and the two Resources phases; `test_ios_archive.py`'s unsigned leg reads it off the archived app and extension, its signed leg off the exported `.ipa`. The photo-library purpose string App Review reads names the user's nest.

## Versioning

`CFBundleShortVersionString` / `MARKETING_VERSION` is the product version — the one fleet-wide string [`../product-version.md`](../product-version.md) owns, held equal by the `version-lockstep-check` gate — and `CFBundleVersion` / `CURRENT_PROJECT_VERSION` is **pinned at `1`** (§ Reships there): each version train gets exactly one upload, so a build App Store Connect rejects or a tester round that needs a new build mints the next product patch fleet-wide and is uploaded from the commit that carries it. TestFlight's own "a newer build for this version" path is therefore never used.

## Listing posture

- **One main listing per store (D4).** One Fauna app on the App Store; under-13 users get the separate contacts-only kids app, never a second social listing — owner [`../../behavior/account-age-band.md`](../../behavior/account-age-band.md) § The account age band (the kids-app bullet).
- **The rating questionnaire is answered honestly.** Fauna redistributes and lets people interact with user-generated content through a feed, so the social-media question is answered *yes*, which rates the main app at least **13+**; the 13+ / 16+ answers follow from the truthful ones and are never shaded toward a younger rating. The storefront facts behind this are [`../../behavior/family-safety.md`](../../behavior/family-safety.md)'s.
- **What the App Store publishes about the organisation, and what the account declared** → [`store-listing-contact.md`](store-listing-contact.md) § App Store; a console answer that changes listing content is read back before it is recorded (the same doc's § The readback rule).
- **No DSA trader declaration is recorded here**: the specification states no legal classification ([`../../README.md`](../../README.md) § Writing protocol → *State mechanisms, never law*); what the owner declared on the account — non-trader, the owner's 2026-10-18 decision on how to declare — and what the console shows are recorded as read back in [`store-listing-contact.md`](store-listing-contact.md) § The classification question.
