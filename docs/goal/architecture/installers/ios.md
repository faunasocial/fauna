## Goal

One signed iOS build per version train, archived from the recorded public commit at the product version, uploaded to App Store Connect and served to its audience by **TestFlight** before the first public release and by **the App Store** from the first public release on. The same bundle, the same source and the same version string as every other app on the train ([`../product-version.md`](../product-version.md) § Bumping); the two channels differ only in who may install and in which review the build passes.

## Store identity

- **Bundle identifier `social.fauna.fauna`** — the same string as the macOS app (Apple keeps one record for both), the Android application id and the linux app id, under the leaf rule [`macos.md`](macos.md) § Identifier domain owns. It froze at registration (2026-08-22) and can never change. The embedded extensions carry `social.fauna.fauna.<Extension>` (the project's `PRODUCT_BUNDLE_IDENTIFIER` values), one App ID each.
- **App Store listing name `Fauna Social`**, reserved 2026-08-22; on the device the app is still *Fauna*. The listing name is the App Store Connect record's, not the bundle's display name.
- **Team ID `7457N3M72H`** — the seller every App Store page and TestFlight invitation shows as *Fauna Social*; pinned in `fauna_core::platform_ids` and published from the official-apps manifest ([`../release-integrity.md`](../release-integrity.md) § Release signing → *The official-apps list*).
- **The kids app is a second record** — bundle identifier `social.fauna.faunakids`, a build flavor of this target, owned by [`../../behavior/family-safety.md`](../../behavior/family-safety.md) § The account age band (the kids-app bullet); it is not part of the channel this document ratifies for the alpha.

## Signing

- **Identity:** `Apple Distribution: Fauna Social (7457N3M72H)`, minted 2026-08-22 and held in the login keychain of the macOS development VM with its `.p12` in the organization's password manager. It signs both channels: a TestFlight build is an App Store distribution build.
- **Profiles:** an **App Store** distribution provisioning profile for the app's App ID and one for each embedded extension's App ID, wired into the **manual** signing of the four iOS targets — the app, its File Provider pair and its widget (`CODE_SIGN_STYLE = Manual`; automatic signing would need an Apple account session on the build machine, which the next bullet forbids). Each target's Release configuration names the `Apple Distribution` identity, the team and its profile by **name** — names survive a regeneration, UUIDs do not — scoped to the device SDK, so simulator and macOS builds stay ad-hoc signed; `apps/fauna-apple/ExportOptions-AppStore.plist` names the same four profiles for the export. A profile is a snapshot of its App ID's capabilities, so it is generated **after** the App ID carries every capability the app declares (push notifications, Declared Age Range, App Attest) and regenerated whenever one is added. Profiles expire yearly; renewal is the channel's one recurring maintenance cost.
- **The Apple account stays off the development VM (user ruling 2026-08-22).** The VM holds signing identities and profiles; every portal act — minting a certificate, a profile or an App Store Connect API key, answering a questionnaire, managing testers — happens in a browser on the host, signed in as the organization's Apple account, never on the VM.
- **What the archive proves:** `tests/e2e-unified/tests/artifact/test_ios_archive.py` has two legs. The unsigned leg archives the real device target in the Release configuration with signing disabled — the SDK, the arm64 compile, the extension embedding, the layout — and runs on any macOS box. The signed leg archives with signing on, exports a signed `.ipa` to disk and reads the signature, each bundle's embedded profile and the signed entitlements back off it; it runs where the identity and the four profiles are installed and skips as an environment gap elsewhere. **Neither leg contacts Apple:** manual signing, no `-allowProvisioningUpdates`, no authentication key, an export `destination` of `export` and `manageAppVersionAndBuildNumber = false` — `test_apple_identifier_pins.py` pins the tracked half on every machine.

## The channel

**TestFlight is the pre-release channel, and the alpha audience is TestFlight EXTERNAL testers (user ruling 2026-10-07).** External testers are invited by email or by a public link, need no App Store Connect account and hold no role on the team; up to 10,000 may be invited, and a build serves them for 90 days from upload. The price is **Beta App Review**: the first build of each version is reviewed before an external group can install it, which brings the App Store review questions forward to the alpha — and that is wanted, because a finding at the alpha is cheaper than the same finding at the public submission. **Internal testing is rejected for the alpha:** an internal tester must be an App Store Connect team member holding a role, and an alpha tester is not staff and gets no console access. Internal testing stays available for the team's own smoke installs of a build before it is submitted to review; it is never the audience.

Two consequences, both ruled 2026-10-07 and owned where they belong: **the user-initiated reporting surface is built on iOS before the first external build** ([`../../behavior/moderation.md`](../../behavior/moderation.md) § User-initiated reporting, the sequencing clause — Guideline 1.2 is what Beta App Review would otherwise raise), and **the store-safe archive's payment-link question is answered first** ([`../dynamic-features.md`](../dynamic-features.md) § The App-Store escape hatch owns what the archive may carry).

**The App Store is the release channel.** The public listing is a separate, later act: the App Store submission with its screenshots, the rating questionnaire (§ Listing posture) and the full App Review. Nothing in the alpha publishes the listing; the official-apps manifest's `app-store-listing` entry stays `pending` through TestFlight with a sentence saying the app is in invitation-only testing, under the uniform listing rule [`../release-integrity.md`](../release-integrity.md) § Release signing → *The official-apps list* states.

**Testers' addresses live in App Store Connect only** — never in a file, a commit message or a note; an invitation is sent from the console or as the public link, and the invited group is named in this document by its role, not its members.

## Upload mechanics

1. **The source tree is the recorded public commit at the product version** — the rule and the record are [`../release-integrity.md`](../release-integrity.md) § Release signing → *A store upload is built from a recorded public commit*; on the macOS VM that is a clean checkout of the public repository at that commit, never the private tree.
2. **Archive and export:** `xcodebuild archive` of the `Fauna-iOS` scheme in the Release configuration over the store-safe device `FaunaFFI.xcframework` (`just apple-ffi-store-safe` — the host-only flavor the debug recipes stage has no `ios-arm64` slice and cannot link, and plain `just apple-ffi` carries the payment surfaces the store build excises), with signing ON and the excision flags `just apple-ios-store-safe-check` passes (`OTHER_SWIFT_FLAGS` `-D FAUNA_EXCISE_PAYMENTS -D FAUNA_EXCISE_P2P_SHARE`), then `xcodebuild -exportArchive` with the `app-store-connect` method and the manual profiles named in the export options. The archive is the store-safe flavor the Apple family ships ([`../dynamic-features.md`](../dynamic-features.md) § Platform-family surface excision); `just apple-ios-store-safe-check` is its unsigned witness.
3. **Upload** with Apple's own tools — the exporter's upload destination or Transporter — authenticated with the App Store Connect API key below; an upload through the exporter uses its **own** export options file (or an `-exportOptionsPlist` override), never an edit of the tracked export-only `ExportOptions-AppStore.plist`; no third-party upload tooling on the path where signing material is in memory ([`../release-integrity.md`](../release-integrity.md) § Defense priority). The first upload is done by hand on the macOS VM; it teaches a later workflow what to reproduce and is the irreversible moment the bundle identifier and the version history begin.
4. **In App Store Connect:** the build processes, the export-compliance question is answered (next bullet), the build is attached to the external group and submitted to Beta App Review; the invitation goes out when review passes.

**One App Store Connect API key serves notarization and upload.** [`macos.md`](macos.md) § Build Pipeline → *Required Environment Variables* already names the key (`FAUNA_NOTARY_KEY_FILE` / `_KEY_ID` / `_ISSUER`) as what the release workflow notarizes with; a key of the Developer role may notarize and upload alike, so the same key, held the same way (the release Environment's secrets, or the maintainer's local store), is the upload credential — a second key is minted only if the roles ever diverge. It is role-scoped and revocable on its own and keeps the Apple account's password and second factor out of every machine.

**Export compliance:** `ITSAppUsesNonExemptEncryption` is `true` on the app target's Info.plist, so App Store Connect asks the questionnaire on the first upload; the organization's representative answers it from the posture [`../export-compliance.md`](../export-compliance.md) owns (a legal attestation, theirs alone, given in an authenticated App Store Connect session). The compliance code App Store Connect returns is then recorded as `ITSEncryptionExportComplianceCode` in the same Info.plist, so every later build inherits the answer instead of re-asking it.

## Versioning

`CFBundleShortVersionString` / `MARKETING_VERSION` is the product version — the one fleet-wide string [`../product-version.md`](../product-version.md) owns, held equal by the `version-lockstep-check` gate — and `CFBundleVersion` / `CURRENT_PROJECT_VERSION` is **pinned at `1`** (§ Reships there): each version train gets exactly one upload, so a build App Store Connect rejects or a tester round that needs a new build mints the next product patch fleet-wide and is uploaded from the commit that carries it. TestFlight's own "a newer build for this version" path is therefore never used.

## Listing posture

- **One main listing per store (D4).** One Fauna app on the App Store; under-13 users get the separate contacts-only kids app, never a second social listing — owner [`../../behavior/family-safety.md`](../../behavior/family-safety.md) § The account age band (the kids-app bullet).
- **The rating questionnaire is answered honestly.** Fauna redistributes and lets people interact with user-generated content through a feed, so the social-media question is answered *yes*, which rates the main app at least **13+**; the 13+ / 16+ answers follow from the truthful ones and are never shaded toward a younger rating. The storefront facts behind this are [`../../behavior/family-safety.md`](../../behavior/family-safety.md)'s.
- **No DSA trader declaration is recorded here**: that question is frozen pending counsel and no session restores or rewords it.

- **Prerequisites of the first external build, both landed (2026-10-07/08):** the iOS paint of user-initiated reporting ([`../../behavior/moderation.md`](../../behavior/moderation.md) § Implementation status today) and the store-safe archive's payment-link ruling, whose renders are now behind `FAUNA_EXCISE_PAYMENTS` ([`../dynamic-features.md`](../dynamic-features.md) § Platform-family surface excision).
