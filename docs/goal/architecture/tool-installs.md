## Carrying out an approved bump — the fleet installs it, on every machine it names (owner-directed 2026-11-13; designed the same day)
**The owner's approval of a tool or toolchain bump makes the fleet carry it out; nobody installs by hand, and nobody notices a machine left behind.** The owner's directive of 2026-11-13, as the release session that received it recorded it: "design automated toolchain bumps on all machines — an approval from the owner causes the fleet to actually bump the tool on macOS, Windows or Linux; for `uv` on Windows this requires draining the machine first". It changes who carries out an approval, never who gives one: every tool row is still the owner's (§ *The tool report*, the verdict bullet), the review rule of 2026-11-10 is untouched, and nothing here lets a session type an installer. What the 0.1.7 attempt met, which this design answers: a Go patch release was a hand diff over five files plus three hand installs; the queue held per-machine tool needs that nobody carried out after their approval; and replacing `uv` on Windows under running sessions fails or corrupts them. The design is the session's under that directive, its choices listed at the end, refutable. What of it is built: § Implementation status today.

- **The unit of approval stays one tool on one machine; a toolchain is one need for the whole fleet.** A tool need is `tool:<name>@<machine>` and its row is the tool report's row, unchanged: the version installed → the target, the typed channel, the checksum that channel gives for THIS machine's artifact, its date and age, the advisories open at the target and those the move closes. The table prints the needs of one tool on several machines together under the tool's name, with one line saying whether the targets agree, and `decide --take tool:<name>@*` takes every one of them whose row is takeable. A **toolchain** — a tool whose version a tracked file pins — is one need, `toolchain:<name>`, and its approval covers three things at once: the lockstep set (below), and the install on every machine whose inventory entry names that pin (`pin = "toolchain:<name>"`). Its `resolve` step logs one move per such entry, the report gives each a tool row reading `forced by need toolchain:<name>`, and the take is refused while any of them is `RED` or `n/a`, as for any forced row. So the owner never approves a pin whose installs were not on the table.
- **The carrier is the install step: a verb of the round tool, run on the machine by its fleet agent on the broker's call, with no session in it.** `bump-round install --need tool:<name>@<machine>` runs ON the machine. The broker asks the machine's agent for it (the agent action `install`, carrying the round and the need and nothing else); the step itself reads everything it acts on — the version, the channel, the checksum, that the round took the need, that no retraction stands — from the round's record and stored report at `origin/main`. So the message that starts an install can name only an install the owner has already approved, and a session, a queue row's text or a model's reading is never between the approval and the bytes. The broker's trigger is the tracked state itself: an inventory entry marked `awaiting = "round <N>"` whose need round N took and whose `installed` step is not logged is owed an install, read every janitor period; the trigger is the decision's landing, never a row a session must pick up. A tool on `ci` has no install step (its landing commit is the install, as before).
- **What the step runs: the channel's own installer at the exact decided version, or a download it checks itself — one typed recipe per channel kind, in code.** *A release archive or the vendor's archive* (`github-release`, `go-archive`): the step downloads the entry's named asset into a scratch directory, hashes it, and unpacks it BESIDE the installed copy only when the SHA-256 equals the row's; the swap into place is one rename where the install is one file or one directory. *winget*: `winget install --id <id> --version <v> --exact`, winget checking the download against the manifest hash the row carries; the step first reads the manifest hash again and refuses when it is no longer the row's. *crates.io*: `cargo install --locked <name>@<v>`, under a `build` slot — on Windows through `scripts\cargo-win.cmd`, the machine's cargo, which sets up the MSVC build environment (`cl.exe`, `INCLUDE`, `LIB`) a crate's C build script compiles in. *PyPI*: `uv pip install --require-hashes -r <the need's lock>`. *A uv-managed CPython* (`uv-python`): the step reads its own machine's uv listing again, downloads the build it names from the hosting service and hashes it against the row, then runs `uv python install <key> --install-dir <install_dir> --mirror file://<that download's directory> --no-bin --no-cache`, so uv installs the very bytes held to the row and checks them against its own pinned hash; uv installs side by side, so the old interpreter is never touched, and a build that does not read back is uninstalled again. *A toolchain its manager installs from the pin* (the Rust toolchain through `rustup`, the kind `rustup`): the manager's own install of the pinned channel — a dated nightly or a stable release, never a moving channel — run by the step so it is logged and happens once, instead of inside whichever build first meets the new pin; the step holds the channel's manifest to the publisher's own SHA-256 beside it, then runs `rustup toolchain install <channel>` with the pin file's components and targets, rustup checking each component against that manifest, side by side with the toolchain the checkout builds with, and uninstalls one it installed that does not run. *The Android SDK's command-line tools* (`android-repo`): the archive Google's SDK repository lists for the version and the entry's host, named in the row by the report, held to the bytes the report reviewed (Google states only a SHA-1) and swapped into `install_dir` as a tree. A channel whose publisher gives no checksum (`other`, a vendor checksum only `stated`) is held to the bytes the report reviewed, and a target the installed tools cannot yet name waits for the move it rides on — the bullet *No sudo: the fleet does it once approved*, below; only a privilege keeps an install the owner's.
- **The permission to run is the run-ledger entry the approval seeded; the step asks the ledger, never its own judgment.** A round's decision on a tool row seeds the entry for that row's checksum on its machine ([`release-integrity.md`](release-integrity.md) § Dependency verification → *The re-run grant*, *Seeding at approval*), with the install profile the recipe declares for its channel kind (network on for the fetch alone, the tool's own install paths writable, no secret, no sudo). The step hashes what it fetched and asks the ledger for that hash under that profile before anything runs; a hash the ledger does not hold, a retraction or a wider profile refuses the step. Its first run writes the machine's journal line, and the step is logged in the round's step log with every command, exit code and hash, as every verb's is.
- **The record is written by the broker from its own tree.** The machine's step reports typed facts — the need, the version read after the install, the artifact's hash, each command's exit code — and the broker's checkout writes the `installed` step line and the entry's `reviewed` version and lands them, as it writes claim lines; no machine commits from an agent. `bump-round installed` stays as the same check by hand, for an install the owner ran.
- **Installs first, pins after: a toolchain's lockstep commit lands once every machine that holds the toolchain reads the target.** A newer tool builds an older pin, and an older tool under a newer pin either fails every build on that machine or sends the toolchain's manager to fetch it mid-build; so the order is decision → installs → the lockstep commit. The round's session lands the commit when the per-machine reading (below) shows the target on each machine the need's rows name, and the merge path refuses it sooner. A machine whose agent is not reporting (down, being rebuilt) does not hold the landing — nothing builds there — and its install is the first thing its agent is asked for on its return, under a hold with the cause `install`, before any launch. A machine that is up and whose install failed does hold it, and is red (below). A toolchain its manager installs from the pin lands at once with the decision's commit, the step then materializing it on each machine.
- **The lockstep set: every tracked line that pins one toolchain is written by ONE `resolve` step and held together by a parity gate, so a partial bump cannot land.** Go is the built reference: the `toolchain` line of each `go.mod`, the builder image's tag and digest, the vetted-image table's entry and the docs naming the release, written by the one `toolchain:go` step and held by the Go gate. Every other toolchain gets the same two things, its set declared once in code (one table the resolve step, the gate and the report all read). The sets as measured by search of the tree on 2026-11-13: **Rust** — `rust-toolchain.toml`'s channel and the build-system doc's line naming the pin (no image stage or workflow names the nightly: the image's rustup and every workflow read the toolchain file, and the workflows' `dtolnay/rust-toolchain@stable` is a different, floating toolchain with its own queued need); **CPython** — `.python-version`, the tier-4 workflow's `--python`, the public CI's note on the pin, and the Linux host, macOS, Windows and Windows-runner setup steps; **the .NET SDK** — `global.json` and the public release workflows' exact `setup-dotnet` input; **`uv` on the CI runners** — `scripts/install-uv.sh`'s version and its installer checksum (the dev machines' `uv` is installed per machine, not pinned by any tracked line); **Gradle** — the wrapper's distribution line and its checksum; **the JDK** — the Android build files' Java level, every `JAVA_HOME` default (justfile, scripts), the apt package and the setup docs; **the Android platform** — the build files' `compileSdk` and the setup docs' SDK package; **the Android build tools** and **the NDK** — the setup docs alone, since no build file names them. **Deno and `just` have no set: no tracked line pins either** — every workflow's setup input floats (`deno-version: v2.x`, `setup-just` with no version) and every machine's install is its own; each one's queued setup-version need writes the first exact line, which joins its set in the same change. A set's members exclude, by rule, prose naming a pin's history, a public text naming a toolchain (it moves through the public-texts process), the fleet's own session rules, a floating setup input and an image pin (the image ecosystem's, save Go's builder image). A set holding a checksum line (Gradle's, `uv`'s) is resolved with `--sha256`, the line written from it. A toolchain whose set is not declared is refused by `resolve` as not built, as today. The parity gate is one cheap parse-only gate over the table (the Go gate generalised), on the merge path.
- **An install that needs the machine quiet is carried out under a drain the broker puts itself.** An inventory entry says whether its install may run under live sessions: `install = "live"` or `"quiet"`. The defaults follow what the operating system allows — on Windows a running program's file cannot be replaced, so every entry there is `quiet` unless marked `live`; on Linux and macOS a one-rename swap is `live`, and an install that rewrites a tree in place (a virtual environment's packages, an SDK directory) is `quiet`. The first case is `uv` on Windows, which every recipe runs. For a machine with quiet installs owed, the broker puts the drain's hold with the cause `install` ([`fleet-launch-and-halt.md`](fleet-launch-and-halt.md) § The launch and the halt → *A drain is a hold* owns the hold, the deadline and DRAINED), on the approval's standing as its word; all of a machine's quiet installs go in one drain, and one machine is drained for installs at a time, so the fleet keeps working. A drain leaves a manual session and a detached run alone, and the install waits only for one that runs a program of the tool (the machine's agent reads it off the process list, under the directory the install step itself refuses on; what it cannot read holds), the reading naming the holder: a session at its prompt holds nothing. No hold is put while a holder stands; past DRAINED the step installs, verifies, and the broker lifts the hold, and a hold whose installs have waited 15 minutes on a holder is lifted with the installs still owed and not put again for an hour, nor while the holder stands. An install waiting over a day is a red whose line names the holder, the owner's one ask. A release attempt in flight is treated as its parts are: its unattended sessions get the deadline like any other and resume from their captured state, a detached step of it is waited for, and the attempt is neither ended nor failed by the drain; a release round's own tool bump is that same drain, asked for by the attempt that needs it.
- **What needs a privilege stays the owner's own step, asked once with the exact command.** An entry whose install needs `sudo` or an elevated shell (`privilege = "sudo"` or `"admin"`: an operating-system package on Linux, a machine-wide installer on Windows), and one Apple or Microsoft delivers through its own updater, is not carried out by the fleet (since 2026-11-15 a missing checksum or recipe no longer makes an install the owner's — the bullet *No sudo: the fleet does it once approved*, below). The decision puts ONE item on the daily asks per machine, holding every such install of the round as one paste-safe block with the decided versions (an operating-system package's one `apt-get install` naming every package its resolve moves, so the source's binaries move together; an open item whose block is no longer the one owed — minted by an older broker — is closed and asked again with the owed block); the owner runs it; the agent's next reading sees the target and the broker writes the `installed` record, so the owner reports nothing back. The run ledger never covers a run with sudo, and this design asks for no new privilege on any machine — the one path that does is the second brake (the bullet *The second brake*, below), ratified by the owner 2026-11-16 and in force on a machine only once its helper is built and the owner has set it up there.
- **Apple's own tools on macOS move by macOS's own automatic update, in a window the fleet makes for it; they are never an owner's command block (designed 2026-11-15 on the owner's word of that day in guided round 39, "I want this to be automatic, remember? Let's find a way to do that in the future"; the session's design, refutable; the fleet's half BUILT, its macOS witness owed, § Implementation status today).** *What the class is, as measured in the inventory that day:* no macOS entry carries a `privilege`; the owner's class on macOS is the seven entries Apple delivers (`macos`, `curl`, `jq`, `python3-system`, `git`, `xcode`, `swift` — an `other` channel, no recipe, no checksum) and no macOS tool has a recorded advisory exception, so what the owner met is the daily check's own findings on those entries. *The mechanism:* five of the seven (`macos`, `curl`, `jq`, and the Command Line Tools' `python3-system` and `git`) arrive only through Apple's updater, which is the signed vendor channel of *The tool report*'s item (2) and stays outside the round; the owner switches macOS's automatic download and install of system updates, security responses and system files on ONCE (five `defaults write` lines under `sudo`, the one-time step; a major macOS upgrade is not among what those settings install and stays the owner's decision), and from then on the fleet's part is to read and to make room, with no privilege of its own: (1) macOS's agent reads, unprivileged, the five settings and what the updater lists as pending and whether it needs a restart, and reports them beside its tool versions; (2) a pending update that needs a restart makes the broker put the drain's hold on macOS with the cause `os-update` in the night window (02:00–05:00 local, at most one night in three, never while a release attempt's macOS leg runs — the hold, the deadline and DRAINED are [`fleet-launch-and-halt.md`](fleet-launch-and-halt.md)'s), so macOS finds the machine idle and installs and restarts by itself; (3) if the window's first hour passes with the update still pending, the broker restarts macOS through the restart it already has (the cause `os-update` joining the pre-approved causes; the grant is the one already installed for it, `shutdown -r now`), and macOS returns by its automatic login as after any fleet restart; (4) the broker lifts the hold on the new boot, the daily check reads the new versions, and the per-machine reading shows these entries with the state `Apple's` and the pending update's name, never `owner's`; (5) three windows that end with the same update pending are a red named `os-update:mac` in the janitor's file, a fixer's, not an ask. Which of (2) and (3) macOS actually honours — whether a drained macOS installs by itself, and whether a plain restart applies a downloaded update — is not known and is the build's first measurement on macOS; the design holds either way since both are tried in order. *Candidates weighed and not taken:* a NOPASSWD wrapper fixed to Apple's updater (`softwareupdate --install`) would be a new privilege, against the bullet above, and is believed not to work unattended on Apple silicon, where installing a system update asks for a volume owner's password even under root — so it would need the owner's password held by the fleet, a general privilege no fixed argument list narrows; and leaving the entries as reported exceptions is what stands today, with the owner as the installer. *What a compromised session could do with the taken design:* nothing it could not do before — it gains no command; the settings are root-owned, the restart grant is unchanged, and the worst a forged pending reading buys is one drained night window in three. *What stays the owner's:* `xcode` and `swift` — Xcode arrives through an Apple account the fleet holds no credential for, an update of it moves a toolchain and can drop a pinned simulator runtime, so it is never switched to automatic; it stays a round's row and the owner's install, the one hand-run macOS step left, and the daily asks say so in those words. *The other half of the row's class — a macOS entry with no recipe or checksum that Apple does not own:* `just`, `deno` and `go` are user-home installs whose entries name no typed source; each gets the release-archive source its vendor already publishes, as `uv` and `gh` have, and is then the fleet's by the recipe above — no privilege involved, the channel reading put to the owner in a round's table as any tool row is.
- **A failure leaves the old tool in place, reds a named reading, and never leaves the fleet split in silence.** The step's order is fetch, hash, install beside, swap, read the version, run the entry's version command once; any step failing puts the old copy back (the swap undone; for winget, the previous version installed again — bytes its ledger entry already covers) and the machine resumes on the old tool. *A hash that is not the row's* is a different event: nothing is installed, every other install of that round on every machine is held, and the item goes to the top of the daily asks as a security finding, since the channel served bytes the owner did not approve. Every other failure is a red section of the janitor's file named for the machine's installs, which a fixer session takes like any red.
- **The per-machine version reading.** The broker already holds the tool versions each machine reports. The reading puts them side by side per tool: installed on each machine, the entry's `reviewed` version, the version a round has decided and not yet installed, and one state — `current`, `owed` (decided, not installed), `installing`, `waiting` (who holds the machine), `failed`, `split` (machines of one tool at different versions with no install owed that would close it), `owner's` (a privileged step asked). `fleet security` and the Security page print it; `split` and `failed` are reds, and `owed` older than a day is one.
- **What stays out.** Which bumps the owner decides is unchanged: a tool row is never a quiet round's, a `RED` or `n/a` row is never takeable, the operating system's self-applied updates stay outside the round, and a new tool still needs its inventory entry and its review first. A resolver or installer command is still never typed by a session — the install step is the tool that runs it. The rule's sentence that a session presents install commands and lets the owner run them gained its exception on the owner's ratification of this design (2026-11-14, "yes" via `fleet answer`, recorded in the rule with the owner's words): an approved install the step can hold to a checksum without a privilege is the fleet's. The build's switch was turned on the same day; and since the owner's ruling of 2026-11-15 every approved install that needs no privilege is the fleet's, a missing checksum or recipe being the fleet's to supply (the bullet *No sudo: the fleet does it once approved*, below).
- **One take covers the same version on every machine (owner-ruled 2026-11-15, in the guided session of round 39; BUILT 2026-11-15).** When the owner takes a tool bump on one machine, the same version of that tool is approved on every other machine whose inventory entry has the same channel kind and publisher, provided that machine's own report row is `GREEN` with a publisher checksum and pulls in no package the first take did not cover. The round tool derives this by its fixed rule over the inventory and the stored reports; no session judges it, and a quiet round still takes no tool row — the owner's decision on the first machine is the decision. A hold on a machine's installs (the Windows installs held until a release rehearsal has its verdict) and the rule for an install with a `privilege` are unchanged (no recipe or no checksum: the next bullet); a different channel (apt on one machine, a vendor release on another) is never the same source. The owner's reason: a malicious or vulnerable tool does the same damage whichever dev machine it reaches. The per-machine row stays because the file differs per platform and can carry an advisory or a tampering of its own. The rule runs at every `decide` and at every `report` of a decided round (`derive_tool_takes`): a need it takes joins the round's taken needs and seeds its install like any take, its record naming the first take and quoting the owner's words; a need it does not take prints `not decidable by the rule — <reason>` and stays the owner's; and a machine with the same channel whose need has no candidate yet gets its resolve and report at that version minted once, as a row tagged that machine, so the other machines' rows reach the round without a session remembering them. Each is a `derive` step in the round's log.
- **No sudo: the fleet does it once approved (owner-ruled 2026-11-15, in a manual session on macOS; the session's design under that ruling, refutable; parts (1) and (2) BUILT 2026-11-15, part (3) BUILT on Linux and for its red the same day and on macOS the same day, part (3) on Windows NOT BUILT, § Implementation status today).** The occasion: the owner's take of `python@mac` 3.14.10 fell to an owner's command block, because the report reads a uv-managed CPython's checksum from the INSTALLED uv's download list, uv 0.13.4 lists nothing past 3.14.8, and the row was written "a uv move comes first" with no checksum, which the install step refuses. The owner: "You must design the fleet upgrade so that this happens automatically", and "no sudo -> you do it if approved". So an approved install whose entry needs no `sudo` is the install step's, whatever its channel: a missing recipe, checksum or prerequisite is a mechanism the fleet owes, never a command block for the owner. A privilege does not by itself make an install the owner's either — the owner the next day: "I did not mean 'no sudo' should be done by the fleet, I just mean that if there is no sudo required then the fleet can definetely do it, and should, according to the rules. The sudo/admin things the fleet can do is more tightly controlled and acts as a second brake, still, not all sudo commands need the user to run them." A privileged install (`sudo` on Linux, an elevated shell on Windows) is a separately and more tightly controlled class: the fleet carries one out only through a narrower privileged path the owner sets up once — the second brake — designed in the bullet *The second brake*, below (its ratification asked, § Implementation status today); until that path covers an install, it stays the owner's command block (the bullet *What needs a privilege*, above). What Apple delivers moves by macOS's own update (the bullet on Apple's own tools, above). Three parts carry it. *(1) A take waits for the move it rides on, then reads itself again.* A tool row that could not be checksummed because another need of the same machine must move first (today: a uv-managed CPython whose build the installed uv does not list) is takeable with an `after` edge to that need (`tool:python@mac` after `tool:uv@mac`), the edge read off the row's own finding by the round tool, never by a session; the take is recorded and nothing is seeded. When the record of the first need's install lands, the broker asks the machine's agent to run the waiting need's report row again ON that machine (`bump-round report --need`), which reads the new uv's listing and the standalone build's publisher digest into the row; a row that now reads takeable at the decided version is seeded and installed under the take already given, with no further word; one that reads otherwise (`RED`, another version, still no build) returns to the owner as a new item. The take is of the version; the bytes are still held to a publisher checksum read before anything runs. *(2) A channel that states no checksum is held to the bytes the report reviewed.* Where the publisher gives no digest, the report downloads the very file the install step would fetch (a release asset on the hosting service, its redirect followed only to the service's own asset hosts, streamed into a hash and dropped, never kept or read) and records that file's SHA-256 in the row with `checksum_source = "reviewed"` — every other checksum reads `publisher`, or `stated` for a vendor's checksum a resolve passed by hand, and the table prints which; the row keeps a finding naming it, so it reads `FLAG`, takeable by the owner; the approval is of those bytes, the run ledger is seeded with that hash, and the install step fetches again and installs only bytes of that hash, a mismatch being the security finding of the failure bullet as for a publisher's hash. A reviewed hash is that one artifact's, never the publisher's word for the version, so it never carries a take to another machine: the rule of the bullet *One take covers the same version on every machine* still asks a publisher's checksum. A channel with no recipe yet (`other`, `stated`) has no file the step would fetch, so it gets its reviewed hash with its recipe, part (3). *(3) Every entry with no privilege gets a recipe and an install directory.* Measured in the inventory 2026-11-15, the entries with neither a recipe nor a privilege outside the Apple-delivered class: Linux android-sdk, deno, go, rust-toolchain; Windows deno, ffmpeg, kache, llvm-mingw, python, rustup, rust-toolchain, uniffi-bindgen-go; macOS rust-toolchain. Each gains a typed `source` of a recipe kind (a new kind added to the recipe table in code where none fits; a toolchain its manager installs from the pin through the manager recipe above) and an `install_dir`. Until an entry has one, an approved move of it is a red of the machine's `installs-<machine>` janitor section — the fleet's missing mechanism, fixed forward — not an ask.
- **The second brake: a privileged install runs through one root-owned helper per machine, whose own fixed rule bounds what can be installed whatever the round's record says (DESIGNED 2026-11-16 under the owner's ruling of that day, quoted in the bullet above; the session's design; RATIFIED by the owner 2026-11-16, unchanged — the answer "yes" to the design as put on the daily asks; the Linux helper BUILT 2026-11-16 and DEPLOYED by the owner 2026-11-16, the Windows one NOT BUILT; in force on a machine only once its helper is built and the owner has deployed it there, § Implementation status today).** *The principle.* The first brake is the owner's take of the row in a round, as for every install. But the round's record, the inventory, the broker and the machine's agent are all written or run by the dev user, so a session that had been turned against the fleet could forge every one of them. For an install with no privilege that forgery buys nothing the session could not already do, since it runs as that user. For a privileged one it would buy root. So the second brake is a helper that trusts nothing the dev user can write: the approval chooses WHAT is installed, and the helper, from root-owned settings the owner puts in place once, bounds what COULD ever be installed. The bound holds with the first brake forged. *The path on Linux.* One root-owned script, `/usr/local/sbin/fauna-privileged-install` (its source tracked in the tree, short enough to read in one sitting, deployed by the owner by hand as the `cargo-target-zfs` wrapper is — [`build-target-layout-linux.md`](build-target-layout-linux.md) § The ownership contract is the prior art), allowed by one `NOPASSWD` sudoers line naming that one path, and one root-owned allowlist, `/etc/fauna/privileged-install.allow`, each line a binary package name and the repository origin it may come from. Its whole grammar is three verbs: `install <package>=<version> [<package>=<version> …]`, `refresh` (the package lists' update, no argument) and `check` (prints the deployed script's and the allowlist's SHA-256, so the agent can report a deployed helper that is not the tracked one). `install` refuses unless every one of these holds, each checked by the helper itself: (1) every named package is on the allowlist and already installed, and the named version is newer than the installed one — never a new package, never a downgrade;
