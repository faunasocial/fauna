## Implementation status today

- **Packaging witnesses have no surface, and — ruled by step 4, 2026-08-27 — they are not getting one.** The suites that prove an artifact installs *without* driving its UI (`tests/platform/{linux,macos,windows}/test_installer*.py`, `tests/artifact/test_ios_archive.py`, the store-package tests) are neither `app` (rule 4: they launch no driver) nor `nest` (a nest record counts for every column, and a `.deb` install proves linux alone). A third `artifact` surface, attributed per app by the suite's own app marker, was mechanically available — the suites already carry `@pytest.mark.<app>` — and is **refused** anyway, because the question a cell answers is *did a user-observable outcome hold on this app*, and the install row's outcomes are written that way: "the packaged app installs **and launches**". A file-layout assertion over a `.deb` does not witness that sentence; letting it colour the cell would be the catalog telling its reader that something was proven which was not — the exact dishonesty the run-written ledger exists to remove, arriving through the surface model instead of through a hand-judged status. The honest reading of linux's `(none)` on [`get-the-app`](../../features/get-the-app.md) outcome 4 is "no test yet installs the linux package and opens the app", which is true and is a real gap; macOS and Windows have exactly such install-then-drive tests, so the shape exists and the road to a green cell is to widen it, not to lower the bar. A third surface would also have cost a third completeness rule, a third stamp scope and a third answer to "does this record count for one column or all seven" — real complexity bought for a category whose members are better fixed than accommodated. **The widening began the same day and is tracked per app, not per feature**: **linux is done** — `tests/e2e-unified/tests/artifact/test_linux_installed_product.py` runs the real `install.sh` into a private prefix under `build/` and drives the *installed* binary through login-to-feed, so outcome 4 has a witness that makes the sentence it claims. Doing that turned `tests/artifact/` from an apple directory into the app-agnostic one this doc's taxonomy always described (`--client-artifact` gates collection, `--macos-artifact` implies it, and the directory's `_MODULE_OS` map prunes every module whose OS is not the running box's), which is where each remaining app's install-then-drive witness belongs. Two rulings the linux leg settled, binding until re-ruled: **the installed subject is a DEBUG-config binary**, because convention 15 compiles the automation surface out of release builds so a release binary cannot be driven at all — the same substitution the macOS bundle already makes, honest only while the install channel branches on no build configuration, which a test in that module pins by reading the script; and **the terminal app got no install outcome while it had no distribution channel** (§ Columns today) — its channel, [`installers/tui.md`](installers/tui.md), was ratified and built 2026-09-26, and the cell closed the way this ruling prescribes: a tui install-then-drive witness (`tests/artifact/test_tui_installed_product.py`, the archive's real `install.sh` over debug binaries) on the existing channel-neutral outcome 1, never a tui-specific outcome; while it had no channel, "install the terminal app" was not a user-observable outcome at all, and [`get-the-app`](../../features/get-the-app.md)'s prose already says what is true: the six native apps are built from source today. That is a blank cell meaning "no run recorded", not a `(none)` outcome, and minting an outcome to fill it would be the same lowered bar in reverse. **The apple leg applied that same test to iOS and reached the same answer (2026-08-27, on macOS)****: outcome 5 is now Android-only, and the iOS install is not an outcome today.** iOS fails the terminal app's test on both halves — no distribution channel — **not for want of a signing identity**: enrollment was approved 2026-08-13 and all four certs were minted 2026-08-22 (Team `7457N3M72H`; `Apple Distribution` is live on macOS), the bundle id is registered and the listing name reserved. What is absent is a channel that *serves* the app: no build is submitted, first submission is still gated on the gap the compliance audit found, and the `Fauna-iOS` target is still `CODE_SIGN_STYLE = Manual` with no profile wired, so the archive this tree can build is unsigned) and, at the time, no distribution doc (§ Columns today then named "no ios distribution doc"; `installers/` had no `ios.md`, and [`apps/ios.md`](apps/ios.md)'s single "App Store" mention is one cell of a macOS-comparison table about *updates*, not a channel spec — [`installers/ios.md`](installers/ios.md) was ratified 2026-10-07, TestFlight then the App Store, and the channel still serves nothing). A **simulator** install was the tempting witness and is refused: `xcrun simctl install` puts a hand-assembled **Debug** `.app` built off the SPM package on a simulator, which is a different channel *and* a different build configuration from the App Store's signed Release `.ipa` — so the linux leg's debug substitution above does not carry, its honesty condition being "the install channel branches on no build configuration", which the store channel plainly does. Citing such a test under outcome 5 would prove "a locally built debug app launches on a simulator" while the page claimed the store install had held: the same dishonesty this ruling refuses, one platform over. So the iOS half was **removed rather than witnessed or split** — a simulator-install outcome would be the minted-to-fill-a-cell outcome the terminal app was denied, and iOS's blank cell now means what tui's meant until the terminal app's channel was built (2026-09-26). **Nor was a front-matter `absences: ios` the answer**, which is the mechanism the row's own wording pointed at: § Cell semantics defines that entry as "a front-matter **absence** for this app", rendering `—` and confirmed by a `declared_absence` skip in the run — it says the *feature* is absent on that column. "Get the app" is not absent on iOS: the app exists and is obtained the way all six native apps are obtained today, by building from source. Only the *store channel* is missing, which is one outcome, not the feature — and declaring the whole column absent to express a missing outcome would be a second, quieter dishonesty in place of the first. The credentialed inch (`-exportArchive` to a signed `.ipa`, then a real-device install) is a user gate, captured as such; the outcome is minted when the channel exists, not before. **Android's half was left to its own leg, which reached the same answer (2026-10-14):** Android has a distribution doc ([`installers/android.md`](installers/android.md) § Goal), but its Play record was then a draft with nothing uploaded. So the only honest witness, an obtain-then-drive test of the *store* install, could not be written, and an `adb install` of a locally built APK is the simulator trap one platform over. The upload has existed since 2026-10-09 (`0.1.3`/`103` on internal testing, [`installers/android.md`](installers/android.md) § Implementation status today; the 2026-10-14 wording missed it), and how that store install is driven is the next bullet's ruling. The column stays honestly short until that witness runs. **Every remaining install-row gap is now a store-channel or web-channel witness, each waiting on its channel and tracked per app**.
- **How the Android store install is driven (ruled 2026-11-03).** Convention 15 strips the in-app `TestAgent` and its launch seams from the Play build, and the harness's own bridge cannot reach that build either: `BridgeInstrumentation` ships in the app's test APK (`social.fauna.fauna.test`) and instruments `social.fauna.fauna` in the app's own process and UID (its `AppLauncher` writes the credential seed into the app's `filesDir`), and Android attaches an instrumentation only to a package signed with the same certificate. Play re-signs every delivery with the Google-held app signing key, so that bridge can never attach to a store install. **The honest route is an out-of-process driver, and it leaves convention 15 intact:** a separate, self-instrumenting UiAutomator test APK, with its own package and key, that reaches the app only through `UiAutomation`, the accessibility tree any accessibility service reads. The ids are already there: the release build keeps `testTagsAsResourceId = true` (`MainActivity`, main source set), which exposes the ui.yaml ids in that tree and adds no capability ([`e2e-automation-surface-gating.md`](e2e-automation-surface-gating.md) § Implementation status today, the accessibility-id bullet). Such a driver has none of the same-UID powers: no credential seed, no log or download read, no trust, clock or region seed. So the journey signs in through the app's own UI, against a nest the release build accepts with no seed. **Which nest, and which account (settled 2026-11-04):** the store build pins no nest — it reaches whatever nest a handle names, over TLS only, since its network security config refuses cleartext (`apps/fauna-android/app/src/main/res/xml/network_security_config.xml`), so the harness's plain-HTTP standalone nest is out of reach and the nest is a deployed box. The acceptance nest `fauna.build` is the one the version's build is accepted against, but it is humans-only and the harness refuses it ([`testing.md`](testing.md) § The shared-box rule); the witness uses `test.fauna.build`, the staging box serving the same `:test` image as the shared-box rule's automated side ([`org-nests.md`](org-nests.md) § The three nests). The account cannot be minted by the journey: the release build's onboarding registers a fresh identity only with an invite code (`OnboardingMachine::redeem_invite`) and the organisation's nests are invite-only, so the journey signs in as an identity the staging-box provisioning drive admitted through the app's admin UI, importing its file — the very steps a Play reviewer takes. **Which identity (ruled 2026-11-05):** the witness host's own tester, `<platform>-tester`, minted and kept on the machine that runs the witness and admitted on the box from the tracked registry of public keys, so no secret travels between machines; on the dev host alone, where the drive keeps the reviewers' identities, that box's own `google-reviewer` stands in where no tester is minted ([`org-nests.md`](org-nests.md) § fauna.build → *Accounts*, the witness hosts' testers). The choice lives in one shared helper, `tests/e2e-unified/helpers/store_install_account.py` (`witness_account`), which the iOS witness shares. **The subject is asserted on two facts, because either alone is matched by something else:** the installer of record is the Play Store (`pm get-install-source-info social.fauna.fauna` names `com.android.vending`), and the installed signing certificate is Play's app signing key ([`installers/android.md`](installers/android.md) § Implementation status today, the Play signing keys). **An `adb install` of the universal APK that Play's Developer API generates is NOT the store install, and is ruled out as this witness:** its certificate is Play's, but it is installed by the shell rather than the Play Store, and it is the universal APK rather than the split set Play delivers to a device. It may stand as a mechanism test of the Play-signed artifact, but it never colours outcome 1. **Obtaining is the driver's act too:** the Play Store app on the device, signed in to an account on the internal testers list, is opened at the app's listing and its Install button is pressed through the same `UiAutomation`. The human inch is the one-time Google account sign-in on that device (the account's credentials and second factor), a user gate. The venue's AVD image is `google_apis`, which carries no Play Store, so the witness needs a second AVD on a Play Store system image beside it. **The driver's code landed 2026-11-03; it builds once the owner's bump round admits its two dependency declarations, the exact UiAutomator and NanoHTTPD artifacts the app's androidTest already resolves, which that round adds with the module's `settings.gradle.kts` include (the head of `apps/fauna-android/store-driver/build.gradle.kts`):** the `store-driver` module (`just android-store-driver`), whose instrumentation targets its own package, shares the find/actuate half of the harness bridge's element operations through `apps/fauna-android/automation-shared/` and adds only the obtain verbs and a launcher-entry start; its witness is `tests/e2e-unified/tests/artifact/test_android_store_install.py` (`just e2e-android-store-test`), which skips as environment without a Play Store device or without the reviewer's identity file, and takes no sign-in input of its own. Until that AVD is up and the run is recorded, android's `get-the-app` cell stays short.
- **How the iOS store install is driven (ruled 2026-11-04).** This is the Android ruling's twin, and it leaves convention 15 intact too. A TestFlight delivery is a Release build that Apple re-signed, and the harness's iOS driver cannot reach it: that driver talks to the in-process TestAgent of a DEBUG build on a simulator, and convention 15 compiles the TestAgent, its launch seams and the `AutomationRegistry` out of every Release build. **The honest route is an out-of-process driver:** a separate XCUITest runner bundle (`apps/fauna-apple/StoreDriver/`, bundle id `social.fauna.storedriver`, `just ios-store-driver`) on a physical iPhone. It reaches the installed app only through the accessibility tree, by `XCUIApplication(bundleIdentifier:)`. The ids are already there, because every view sets `.accessibilityIdentifier(Ids.<x>)` outside `#if DEBUG` ([`e2e-automation-surface-gating.md`](e2e-automation-surface-gating.md) § Implementation status today, the apple identifier bullet; `test_ios_store_driver_pins.py` pins every id the driver reads). The runner compiles the generated `Ids` table from FaunaKit's source, so the driver and the app cannot disagree about an id. It has no in-process powers (no credential seed, no log read, no launch environment), so the journey signs in through the app's own UI, the same steps as the Android witness and on the same nest: `test.fauna.build`, as the macOS host's own tester `macos-tester`, minted and kept on that machine and admitted on the box by the staging-box provisioning drive from the tracked registry of public keys (the Android bullet's *Which nest, and which account*; [`org-nests.md`](org-nests.md) § fauna.build → *Accounts*, the witness hosts' testers; `tests/e2e-unified/helpers/store_install_account.py`). The reviewer handle `apple-reviewer` stays the review notes' alone. The host reads the identity file and passes the handle and the seed to the runner's environment, and cuts the seed out of everything the runner reports, because XCUITest's console prints the text each `typeText` typed. **A simulator never counts:** TestFlight installs only on a device, and a simulator install is the different channel and different build configuration the apple amendment above refused. **The subject is asserted on two facts, because either alone is matched by something else.** First, TestFlight installed it: the app was absent when the module started, the runner pressed Install in TestFlight, and TestFlight then showed the app as installed (its Open button). A TestFlight install left over from an earlier run fails this fact, so the module refuses an app that is already installed. Second, the device does not class the install as a developer app: `devicectl device info apps` lists it only with the non-developer apps, and `builtByDeveloper` is not true. A build signed with the Apple Development identity, or an Apple Distribution `.ipa` installed by Xcode or `devicectl`, fails this fact. iOS gives a host no installer-of-record field the way Android's `pm` does. That is why the first fact is an observation made during the run. **Obtaining is the driver's act too:** the runner opens TestFlight, finds the app under its on-device name, presses Install, and waits for Open. **The human inch is the device, set up once by the owner:** an iPhone paired with the macOS development VM, with Developer Mode and Settings → Developer → Enable UI Automation on; the device's UDID registered in the developer portal, and an iOS App Development profile named `Fauna Development social.fauna.storedriver` (covering the runner's App ID and listing the device), generated from the host browser and installed on the VM, which the runner's target signs with; and TestFlight signed in to an Apple Account in the app's tester group. These are portal acts, and portal acts stay on the host (the Apple account stays off the development VM; [`installers/ios.md`](installers/ios.md) § Signing). The first signed build of the runner may ask once for `codesign` access to the Apple Development key in the VM's keychain, which the owner answers. **The code landed 2026-11-04:** the runner (`StoreDriverTests.swift`, two methods, `testObtainFromTestFlight` and `testSignInToFeed`), the host half `tests/e2e-unified/helpers/ios_store_driver.py`, which runs one method per call with `xcodebuild test-without-building` on the paired device and reads the outcome from the result bundle, and the witness `tests/e2e-unified/tests/artifact/test_ios_store_install.py` (`just e2e-ios-store-test`). Without the device it skips as environment. The sign-in test also skips as environment, naming the recipe, until the macOS host's tester is minted there and registered (`just org-tester-mint`, run once by a session on that machine) and the drive has admitted it on the box. **One thing the first device run settles and records here:** whether SwiftUI exposes `main-tab-view` itself on the device or only the tab bar it hosts (`feed-tab`, the Android witness's mark, is registered in-process only on iOS). The runner accepts either and says which one it found. Until that run, which needs TestFlight to serve a build first, iOS's `get-the-app` cell stays short.
- **How the Windows Store install is driven (ruled 2026-11-04).** The Store package is a self-contained Release publish in the `store-no-payments` flavour ([`installers/windows.md`](installers/windows.md) § Store distribution), so convention 15 has compiled its `TestAgent` out: no state publication, no commands, no seed, and no `FAUNA_E2E_*` variable is read, so the driver's ordinary `launch()` — which waits on that state and hands the app an environment relocating every store — cannot drive it. **The route is the one Android's ruling took, out of process, and it leaves convention 15 intact:** the FlaUI bridge already reads and acts on the app's UI Automation tree from outside it, and a Release build's tree carries the ui.yaml ids as its AutomationIds with no in-app seam ([`e2e-automation-surface-gating.md`](e2e-automation-surface-gating.md) § Implementation status today, the Windows AutomationIds bullet, which records the measurement and why that is no automation surface). **The launch is activation by AUMID** (`<PackageFamilyName>!FaunaApp`), the shell's activation manager starting the application the way its Start-menu entry does (`flaui-bridge/SessionManager.cs::ActivateApplication`, reached as `WindowsBridgeDriver.launch_activated`): a full package's identity reaches only a process started in its context, and an exe started from the package's folder runs with none ([`installers/windows.md`](installers/windows.md) § Store distribution, the measurement of 2026-09-28), so every identity assertion below reads a process the OS activated. Nothing else is posted — no arguments, no environment, no seed — readiness is the window's UIA tree showing onboarding's identity choice, or the main window for an install the run has already signed in on, and the driver's own heartbeat keeps the bridge alive with no agent polling it. **The subject is asserted on three OS facts, because a registered layout matches everything else:** `Get-AppxPackage FaunaSocial.FaunaSocial` reports `SignatureKind` `Store` and `IsDevelopmentMode` false, and the running process's package full name is the installed package's (`helpers/windows_store_install.py`). A layout registered with `Add-AppxPackage -Register` under the reserved identity shares the name, the publisher and the family name `FaunaSocial.FaunaSocial_hra91aebets7r`, and fails the first two — measured 2026-11-04 on the staged arm64 layout: `SignatureKind` `None`, `IsDevelopmentMode` true, full name `FaunaSocial.FaunaSocial_0.1.5.0_arm64__hra91aebets7r`, and the cited node, run alone against it, skipped as environment naming both facts. **The witness is `tests/e2e-unified/tests/artifact/test_windows_store_install.py`** (`just e2e-windows-store-test`): its one cited node skips as environment unless the Store delivered what is installed, and the development-mode nodes — the same activation and journey on the layout `just windows-store-package <arch> store-no-payments FaunaSocial.FaunaSocial "<the Partner Center publisher>"` stages, registered for the run and removed after — carry no feature mark, so no run of them colours the cell, and one asserts that the subject check refuses that layout. **The `store-install` outcomes ride the same module (2026-11-08):** seven Store-subject nodes, one per outcome half of `docs/features/store-install.md` and each cited there, every one with an uncited registered-layout twin. Each relaunches the activated install, signs in only when it opens on onboarding, and reaches its screen by clicks alone — the nav tabs, the profile's tabs, the Settings rail, Find User — since a Release build has no state protocol. An absence is read as UIA tree membership after the screen's own anchor is found, and the ids are pinned to the `Views\Payments` and `Views\P2pShare` XAML that draws them (`tests/e2e-unified/tests/test_windows_store_install_pins.py`, the iOS pins' twin), so no absence is of an id a full build never draws. Outcome 5's Microsoft Store half is the in-person share KEPT: the panel opens on the account's compare code. The buyer halves read another author's priced tier and sold post, which the module seeds on its loopback nest through the composer's own wire doors; the iOS twin reads the staging box's seeded account instead, because a phone reaches no harness nest. **The journey signs in through the app's own UI against a nest the Release build accepts with no seed:** a nest serving TLS on its loopback authority, with that authority as its handle domain and the actor registered ahead, which the app trusts on first contact ([`transport-trust.md`](transport-trust.md), the LAN-IP and loopback row); the key is typed into the import screen and the handle into handle entry. Its Android and iOS twins sign in as their store's reviewer on `test.fauna.build` instead (`helpers/store_install_account.py`), because a phone reaches no harness nest; the Windows app runs on the harness's own box, so it reaches one, and the witness needs no reviewer identity file, which is kept on Linux alone ([`org-nests.md`](org-nests.md) § fauna.build → *Accounts*). **The sign-in leg's venue (ruled 2026-11-06):** a Store build names no credential namespace of its own (the override is compiled out with the rest), so its sign-in writes this Windows user's production `fauna-windows` and `fauna-sync-agent` rows in Credential Manager. Its writes under `%LocalAppData%` land in the package's own store (the manifest declares no virtualization opt-out), so the package catalogue and Credential Manager are what the run shares with the user. The venue is convention 12's one named exception for this sign-in ([`e2e-conventions.md`](e2e-conventions.md), the Windows arm, the Store witness's sign-in): Windows's own Windows user, approved as disposable. The convention owns its bounds; the module's `sign_in_venue` enforces them before either sign-in node starts. Apart from that, a guard refuses to start a Store build at all on a user whose production namespace holds a row, because the build would open signed in as that account. **The development-mode journey is shown green on Windows (2026-11-07):** `test_a_registered_layout_signs_in_to_the_feed` drove the public Store workflow's 0.1.6 arm64 store-no-payments package — its `.msix` unpacked as it is and registered ([`installers/windows.md`](installers/windows.md) § Deployment paths, item 3) — from activation through key import and handle entry to the feed, and afterwards no row stood under either namespace and no package of the family was registered. In the same session the subject check refused that registered layout and the activation node passed. The host was oversubscribed during both runs (the VM ran on about a third of the cores it billed), and the first run failed when one read the app's UI thread could not serve inside the bridge's per-call budget ended the arrival wait outright; that wait now keeps such a read for its failure message and lets its deadline decide. **Obtaining stays the witness run's:** the module adopts an existing Store install and never presses the Store app's Get, so the Store-served run installs from the Store first. **The x64 leg (the owner's ruling, 2026-11-07):** the Store serves each member of the private audience the package for their device's architecture, and x64 goes in the submission beside arm64 ([`installers/windows.md`](installers/windows.md) § Store distribution, the alpha paragraph), but the fleet has no x64 Windows device, so the Store-served run is Windows's, on arm64, and the x64 leg is witnessed in two halves instead. (b) **The device half:** one alpha tester's reported install from the private audience on an x64 PC, recorded in [`installers/windows.md`](installers/windows.md) § Implementation status (Store channel) as device class and OS version only — no name, no account. **The cell stays coloured by arm64's recorded Store-served run alone** ([`feature-catalog.md`](feature-catalog.md) § Cell semantics): the x64 half is a recorded ruling, not a cell witness, and neither (a) nor (b) colours anything. The real witness it stands in for is the option the owner did not take now: an x64 Windows 11 device joining the fleet and running the same Store-served module (arm64-only was declined).
