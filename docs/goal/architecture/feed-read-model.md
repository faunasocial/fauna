## State & data shape

### The read model — where the visible list is computed, and where post bytes are read

Two layers, both Rust, neither in app glue:

1. **Nest-side selection / filter / sort / FTS / pagination.** The visible post list is computed on the nest by `query_feed` / `query_feed_scored` / `query_feed_for_authors` (`bins/fauna-nest/src/db/feeds.rs`), reached via `fauna.feed.posts` (a custom feed), `fauna.feed.local.posts` (this nest's local feed) and `fauna.feed.author.posts` (one author's posts — *The author read* below) (`bins/fauna-nest/src/feed_handlers.rs`; shared `*_core` fns in `feed_routes.rs`). The nest translates the feed's shared `fauna_core::scoring::FilterRule` set into the index query — **rule evaluation is the nest's SQL** ("shared Rust" is satisfied because the rule *type* and *encoding* are shared and the single evaluator is the nest; no client re-filters), applies the chronological (`created_at` micros) or score (`order=score`, micro-units) ordering — where a feed carrying a **composition** (frame § Composition, landed 2026-07-08) orders by the composed key `Σ (weight_permille · factor_value) / 1000` over the `content_scores` bus (JOIN by `content_id` alone; a factor with no row — including any sealed tier-1 factor the nest cannot read — contributes 0, the nest-side seam) with `"engagement"` = `content_meta.score` expressed per-mille, and a feed without one orders by the legacy single nest-computed score, folds the optional `search` term in as a `BodyContains` filter (**search is a re-query, never a client-side filter over the loaded list**), and paginates by cursor. A `discovery`-scoped feed additionally aggregates contributor nests via `fauna.federation.feed.query` + `peer_query.rs`, merged nest-side; the home nest hands the client one ordered stream.

   **`created_at` is bounded only going forward — at every door that writes a remote-asserted one.** `content.created_at` is the column this read model sorts on, and the local feed serves it to every local user, so a value dated ahead of the nest's own clock would pin its post atop the chronological feed until real time caught up. Every door that writes an author's, a peer's or a bridged server's `created_at` into it therefore refuses one too far ahead (`bins/fauna-nest/src/storage/mod.rs`) — **one comparison, two cushions (ruled 2026-09-15):**

   - **A Fauna-native post — ~2 minutes** (`reject_future_created_at`): a post a Fauna author's client signed, whether it arrives at the local `fauna.posts.create` door, on the federation forward leg, through the trend-exchange fetch, or as the discovery poller's index stub (whose `created_at` is the peer's own unsigned claim).
   - **A bridged foreign-protocol plane — ~1 hour** (`reject_future_bridged_created_at`): the ActivityPub inbox's `Create` and `Update{Note}` (a Note's `published`) and the Nostr sweep (every kind but the NIP-59 gift wrap, whose timestamp is randomized by design — [`nostr.md`](../ui/nostr.md) § Implementation status today). There the value is a remote server's or client's clock and a refusal is silent to its author, so the cushion is the drift this nest already allows a remote clock (the ActivityPub inbox's signed-`Date` window, [`../behavior/activitypub.md`](../behavior/activitypub.md) § Security posture): a tight one would silently drop an honest peer whose clock drifts, and an hour still ends the pin.

   Both **refuse, never clamp**: rewriting a translated post's date changes the hashed post every replay re-derives, and clamping only the column leaves each re-derivation from the body (a restore, nest-link replication) to reopen the pin. The comparison is made in the timestamp's own unsigned domain, so a value past `i64::MAX` is refused rather than wrapped negative. **The doors are enrolled mechanically, not listed:** the census test `every_content_created_at_writer_is_partitioned` walks every production writer of the column and requires each to be classified — a bounded door (its bound call held to the code), a relay whose own callers are walked in turn, the SQL itself, or a writer no remote value reaches (the nest's own clock, another plane's row, replication inside one deployment) — so a new door fails there until someone decides which it is. **The owner's own backup restore is the one door that never refuses:** a future-dated own post is the user's data. The past stays unbounded: backdating and an archive import's original, long-past `created_at` ([`../behavior/archive-import.md`](../behavior/archive-import.md) § What each category becomes) sort exactly where they say. **The bound is a DOOR rule, and no boot pass may re-litigate it at rest:** a stored value that passed its door is final, so any at-rest pass that would rewrite `content.created_at` by magnitude — the one such pass that ever existed, the reconcile of the three units three writers disagreed on until 2026-08-03, ran one-shot behind its own marker row and retired with the 2026-09-24 genesis of the nest schema — must be **one-shot behind its own marker row**, because a repeating one cannot tell a legacy seconds value from a legal 1970-1973 microsecond instant and would lift the latter centuries into the future, past every door's bound and atop the chronological feed for good.

   **The score-order cursor is a compound keyset cursor** (`(score_cursor, score_cursor_created_at)`, both echoed from the previous reply; ratified + landed 2026-07-11). The scored sort is `ORDER BY key DESC, created_at DESC`, so the cursor must carry **both** the boundary row's ordering key *and* that row's `created_at`: resume on `key < k OR (key = k AND created_at < ts)`. A key-only cursor is not a position in a compound sort — it silently **skips every row tied on the boundary key**, and it fails to advance *at all* when the key is flat. Flat keys are not exotic: a composition of only **sealed** tier-1 factors (the canonical trained-topic feed — [`../behavior/topic-factors.md`](../behavior/topic-factors.md) § Scoring) has every nest-side term 0 by the zero-term seam, so a key-only cursor dead-ends such a feed after one page. With the tiebreak the flat-key case degenerates to plain chronological keyset pagination, which is the correct order for a flat key. `score_cursor_created_at` is additive on `fauna.feed.posts` (request + reply): an older nest ignores it, and a client that sends the key alone still advances on the legacy strict predicate (re-inheriting its tie-skipping). Pinned by `bins/fauna-nest/tests/composed_feed.rs` (`composed_cursor_does_not_drop_posts_sharing_the_boundary_key`, `a_sealed_only_composition_paginates_to_completion`) + `scored_feed.rs` (`a_key_only_cursor_still_paginates_for_a_pre_keyset_client`).

2. **Client-side snapshot assembly.** `FeedManager` calls the kind for `selected_feed`, maps each `FeedPostItem` → `PostSummary` (micros→millis on `timestamp`; `classify_sources(source)` drives badges; `quoted_post_id` drives the embed; `media_hash` starts `None`, resolved lazily per `has_media` post by `resolve_media` — the blob hash lives in the post *body*, which the feed-index projection deliberately never reads, so it costs one `fauna.posts.get` + decode, the same per-post augmentation as the quoted-post fallback — and **once per post per manager**: the decode is kept keyed by `post_id`, which is the body's hash, and re-folded onto every page a `reload`/`load_more` lands, so a refresh never paints a live card media-less nor costs a second fetch, and an app's playing `video-thumbnail` survives it (`render-model.md` § D6c → *Inline playback*); unlike a resolved quote it is never forgotten at a reload, since a post the nest stops serving is simply absent from the landed page), appends each paginated page onto `posts` **deduplicating by `post_id`** (the only dedup the client does — guarding the cursor-boundary repeat case), **preserves the nest-supplied order** (never re-sorts — § Anti-patterns), sets `has_more` from the returned cursor, and `notify()`s. The embedded quoted-post card is projected by a shared `libs/fauna-feed` helper from the already-loaded post set (falling back to a batched `fauna.posts.get` for a quote outside the loaded page) — the single shared quoted-post projection that retires the per-app divergence.

**Posts of authors you follow on other nests — the federated follow (ruled 2026-10-16; BUILT in the nest 2026-10-17 and on tui, linux and android 2026-10-19, the other four apps UNBUILT — § Implementation status today).** The owner's answer to the question this doc could not settle: **a follow reaches across nests.** A reader on nest A who follows an author on nest B has B's author's posts — public and gated alike, as **envelopes** — delivered to A, which stores them in its own index and serves them through this read model exactly as it serves a local author's: the local feed stays a read of this nest's index by locality and rules, and what changes is what the index *holds* — beside every local author's post, the posts of the authors this nest's users follow elsewhere, each listed to the follower who brought it (a per-reader source, never a nest-wide one: following is one user's choice, and a stranger on A does not meet B's author's posts because a neighbour follows them). A seat on a room still buys no delivery (`../behavior/restricted-posts.md` § Encryption at rest, ruling 1). What crosses is the envelope only — the sealed body, the `KeyBlob` and every attachment stay on the author's nest, fetched by the reader's client by content address from that nest's public blob route (bulk bytes never ride federation — `../architecture/federation.md` § Federation residue surface, the *Federated follow* row owns the kinds); the subscription and the period-key wrap to a remote follower are `../behavior/monetization.md` § Pillar 1 → *A follow across nests*. Push by the author's nest or pull by the follower's, the envelope's residency rules, the cross-nest `KeyBlob` wrap, a remote follow's re-point on succession and the delete leg were decided 2026-10-16 and are owned by [`../behavior/federated-follow.md`](../behavior/federated-follow.md) — push through the outbox, the subscriber's own signed intent carried by their nest, the envelope stored marked with no cached bytes, the `KeyBlob` read through the follower's own nest, a per-reader locality join in the feed reads, the widened tombstone door; for a post whose author the reader does not follow, a post reaches a reader on another nest by the deep-link relay (*Opening a post the timeline never loaded* → *A post homed on another nest*, below).

**The author read — `fauna.feed.author.posts` (ruled 2026-10-13; built 2026-10-16 for the account, 2026-10-17 for a principal — § Implementation status today).** `{ author: hex actor id, cursor?, limit? } → { posts: Vec<FeedPostItem>, cursor? }`, in the `fauna.feed.*` namespace beside `local.posts` and `trending.posts` and named for what it reads (one author's posts), so the day a follow reaches across nests (ruled 2026-10-16 as target state — *Posts of authors you follow on other nests* above; built in the nest 2026-10-17) a remote author's read changes inside this kind's handler and nowhere else. Handler shape = `fauna.feed.local.posts`'s account arm: `FeedReader::Account`, `require_permission`, User class on the bridge allowlist, `Read` offline class, the kind catalog. **A third-party principal reaches it through an arm of its own, `fauna:feed:read:author` (ruled 2026-10-16; built 2026-10-17 — § Implementation status today), never through the shipped `fauna:feed:read`, which may not grow a kind ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Scope grammar → *A scope string's reach never widens*; the arm, its card row and why a string of its own: § Scope grammar → *The author arm*). Handler shape = `fauna.feed.local.posts`'s principal twin: `principal_timeline_reader` reads the session as `FeedReader::Principal` under the author arm alone and as `FeedReader::PrincipalAccount` when it also holds `fauna:feed:read:account` — the account's view, public posts only — and the kind enters the `ThirdParty` ceiling under the author arm in `principal_reach`. So the reader set is the one specified on 2026-10-13: the account, and both principal arms held to the off-box predicate. Served by `db::feeds::query_feed_for_authors` with no rules and the local feed's mandatory set (the spam guard, the viewer's block list), always chronological on the local feed's `created_at` keyset cursor; every moderation flag binds (`MODERATION_SERVABLE`, already in that query) and an off-box reader is additionally held to `PUBLIC_POST_SERVABLE` (a `FeedAudience` threaded into `query_feed_for_authors`, whose one caller today, the federation feed query, is unchanged). It is a *feed* read: for an on-box reader a gated envelope lists exactly as the local feed lists it. Two things it is deliberately not: `fauna.posts.list`, the index rail's self-scoped body enumeration (no `actor_id` by construction — [`../behavior/content-index.md`](../behavior/content-index.md) § Ingest triggers); and a filter rule — `FilterRule::AuthorInSet` is declared wire-only and `push_rule_conditions` refuses it, so an author rule on a custom feed is no shortcut and is not introduced. Pinned by `bins/fauna-nest/tests/conformance_feed.rs` — only that author's posts; a gated envelope for the account; public-only for an off-box reader (at the query, `FeedAudience::OffBox`); the viewer's block list empties it; a quarantined post excluded; the cursor pages.

**A REFRESH keeps the posts on screen until the new page lands; only a SWITCH clears them up front (ratified 2026-08-28).** `reload` claims a generation, then re-queries — and what it does to `posts` *before* the fetch depends on whether the query changed. A **switch** (a different `selected_feed`, Trending, a changed `search_query`) clears the list immediately: feed A's posts under feed B's header is a lie, and the reader must never see one. A **refresh of the query already on screen** (the reconnect re-hydrate, the post-submit refresh, a manual pull) must NOT clear: those posts are still true, and the landed page replaces the list wholesale anyway, so the list still converges — a post deleted server-side does not linger. The manager decides this itself, by comparing the query it is about to run against the one the current posts were committed for (`loaded_query` = `(selection, search_query)`, written on the Ok arm only), rather than each caller passing a flag it could pass wrongly. **Why it is a rule and not a preference:** clearing up front means any refresh whose fetch never lands strands the reader on an EMPTY feed with `status = Loading`, no `error` to explain it, and nothing that recovers — an app suppresses a second re-hydrate while the first is still running, so the blank persists until the user navigates away. That is a real state on a flapping connection (a nest flip, a bearer re-mint), it costs the user their whole timeline, and it is invisible to any test that only asserts the *end* of a healthy reload. Pinned at tier_1 by `manager.rs::a_same_feed_refresh_keeps_its_posts_while_the_fetch_is_in_flight` and its twin `a_switch_clears_its_posts_while_the_fetch_is_in_flight`, which park the fetch at the mock's reload-race gate and read the list; and end to end on tui, web, linux, macos, ios and windows by `test_feed.py::test_a_refresh_keeps_the_posts_on_screen_and_only_a_switch_clears_them`, which parks the real reload at the manager's test-only one-shot hold (`FeedManager::hold_next_reload_for_test` — the reload publishes the list it kept or cleared, then waits for `release_held_reload_for_test` before fetching) and reads the page while a Feed-tab re-entry and a typed search are each in flight. While a hold is armed, an app's e2e agent starts a feed op without awaiting it: a held reload cannot land until it is released, so an awaited trigger would park the agent with it. That is why this is a client-side hold and not the nest's reply hold (`helpers/rpc_hold.py`, `bins/fauna-nest/src/rpc_hold_test_hook.rs`, which serves the pre-fetch windows): an agent that awaits the reload cannot tell a held reply from a slow nest, so it would park on it; a hold the manager owns is one the agent can read (`reload_hold_armed_for_test`) before it decides to await.

**Where post *bytes* are read from — the load-bearing decision for the posts at-rest segment-store rollout.** `query_feed` and its siblings read **only the feed-index projection** — the floor columns (`content.{id,author,created_at,source}` + `content_meta.{has_media,is_reply,score,reply_count,repost_count,quarantined,suppressed}`), the tags (`content_links`), the list-card preview (`content_meta.preview` — *The list-card preview* below; until 2026-09-29 the FTS body doubled as the preview store, which no bridged post has), the SQLite-FTS body index (`content_fts`), and the classifier scores (`content_labels`). **They never read `content.payload` (the post body bytes)** — verified against `feeds.rs::query_feed`'s `SELECT`. The full body is read by several single-post paths — `fauna.posts.get`/`get_post_core`, post-reference resolution, the ActivityPub outbox, video manifests, export, moderation, federation-get, and web-content rendering — but **never by `query_feed`**. (Pre-cutover, production stored post bodies inline in `content.payload` for ≤64 KiB and spilled larger bodies to the blob store via `payload_store`; the cutover retires both for posts.) Therefore the posts segment-store rollout (`docs/goal/architecture/message-segment-store.md` § Implementation status today) moves **only the body bytes** (`content.payload` → opaque records in `__post/<actor_hex>`) and **retains the nest-maintained feed-index projection** (the `content` floor columns + `content_meta` + `content_fts` + `content_links` + `content_labels`, rebuildable from segments on recovery exactly like `segment_records`) as the read model `query_feed` scans **unchanged**. Single-post detail reads the body from the segment by CID instead of `content.payload`. This is the **mail template applied to posts**: mail bodies live opaque in `__mail` segments while the `segment_records` mirror + IMAP placement serve the hot reads; for posts the hot read is the cross-actor feed query, which runs off the projection, not the body. The cutover (write + read flip landed 2026-06-15, `segments::post::{store_post,load_post_body}`; tier_3 `segment_post_cutover.rs`) moved the body-byte authority into the `__post` segments while **retaining** the `content` projection row with an empty `payload` — unlike the conv cutover (which dropped its legacy `content` rows entirely), posts keep the row because `query_feed`'s read model lives there. A reader resolves a body **segment-first**, falling back to `content.payload` for the one shape that rests inline: a body `store_post` cannot decode has no author, so no segment scope. Every other post rests in its author's `__post` segment and is segment-backup-eligible. (The 2026-06-16 boot back-fill that moved pre-cutover inline bodies into segments retired 2026-09-25 with the nest schema's genesis (`compat-remnant-sweep.md` § Program 4) — no pre-cutover post rests anywhere.) The projection stays capability-appropriate by construction — `content_fts` indexes only plaintext-readable bodies (public bodies + restricted previews everywhere; full restricted bodies only where the nest holds the relevant keys, built by a reception-time transient-decrypt with the body itself resting sealed — **target; today the restricted *preview* only, § Encryption at rest → Implementation status**), and the cross-actor projection over *public* post floor is **not** a "cross-user index" violation (that rule, `content-index.md`, governs the per-user Tantivy index — a different mechanism from this SQLite-FTS feed index; the feed is a public social read by design).

**The list-card preview is a column of the feed-index projection, never a lookup into the Search corpus (ruled 2026-09-29; built the same day — § Implementation status today).** Until this ruling `query_feed` and its two siblings (`query_feed_scored`, `query_feed_for_authors`) filled `body` by a correlated subquery into `content_fts` keyed by the post id — the FTS row `insert_and_index` writes for a native post doubled as the preview store — and every bridge-ingested post reached every app with an EMPTY list card: ActivityPub, nostr and Bluesky all store through `segments::post::store_post` with a `source`, whose projection writer (`put_post_with_source_index_only`) writes no FTS row, and the bridge Search corpus keys its rows by `blake3(content_type:natural_id)`, never the post id. The coupling was accidental, so the rule is: **`content_meta.preview`** — a nullable additive `TEXT` column (`../architecture/nest/common.md` § Upgrade safety lands it on a long-lived `/data` without a hand `ALTER`) holding the first 500 characters of `Post::body_text()`, **exactly the string the native FTS row indexes today**, so the projection holds no plaintext it did not hold before (a gated post's preview is still its public preview; bridged text is foreign public content, readable class 1 of `../architecture/encryption-at-rest.md` § Readable classes, so sealing constrains nothing here) — carried on `PostMetadata` and written by `write_post_index`, the one funnel every feed-visible post passes (native, all three bridges, the segment restore), so a writer can no more mint a card without its text than without its `content_meta` row; a census test enrolls every production `content_meta` writer the way `every_content_created_at_writer_is_partitioned` enrolls the `created_at` doors. The three feed reads take `COALESCE(cm.preview, '')` and the FTS subquery goes; the one-shot backfill for rows written before the column (a version-guarded `run_migrations` step, the shape its retirements already take) copies each `post/%` FTS body into the NULL previews, so the read never falls back to the corpus and a media-only post's `''` is distinguishable from a pre-column row's NULL. **Why not the two alternatives:** FTS-indexing bridged posts under `post/%` by post id would put every bridged post into `content_fts` outside the per-bridge show-in-search control and its newest-N cap — the cap exists precisely so a firehose-grade bridge cannot balloon the FTS table ([`../behavior/content-index.md`](../behavior/content-index.md) § Bridge content in the Search corpus), and a query-time source filter would turn a structural control into a filter; and an app-side `fauna.posts.get` for each empty-bodied card is a per-card round trip on all 7 apps against this section's founding rule (list cards never read bodies). **Corollary — the feed's text filters over bridged posts read the Search corpus, because it is the only text index of bridged content there is.** `BodyContains` / `BodyExcludes` rules — and the page's search, which `feed_routes::search_to_filter` folds into a mandatory `BodyContains` — matched only `content_fts` rows of a `post/%` schema by post id, which a bridged post never has, so until this corollary no keyword feed and no feed search ever showed one. A second, unbounded text index of bridged posts is exactly what the cap forbids, so those filters reach a bridged post through its corpus row: `bridge_index_map` gains the post's `content.id` beside the blake3 key (nullable — the nostr relay-store plane indexes events that hold no post row), and the filter's `IN` admits a `bridge.%` row through it. The consequence is by construction, not a preference: with show-in-search OFF for a bridge, or past its cap, its posts match no text filter; the preview column above is untouched by either control — the card always shows its text.

**Opening a post the timeline never loaded — the deep-link resolve (ratified + landed 2026-08-10).** `post_detail` was designed against a `post-card` click, where the post is in `posts` by construction. A **search result row** is the first caller that can name a post the feed query never returned (`../ui/search.md` § Where logic lives → *Result navigation (deep link)*): older content, an account the viewer doesn't follow closely, anything past the loaded page. A detail surface reading `snapshot.posts` alone then paints a blank dialog. So the manager owns a single-post resolve — `FeedManager::resolve_post(post_id)` — with these ratified properties:

- **Where the post lives: one `deep_linked_post` slot beside the list, never inside it.** Pushing a deep-linked post into `posts` would corrupt the load-more cursoring, surface a post the user never scrolled to *in their feed list*, and lose it again on the next `reload` (which replaces the list wholesale). **Exactly one slot** — a detail surface shows one post at a time — so there is no cache to grow and **no eviction policy to get wrong**; re-opening the same post is free, alternating between two costs one fetch each, and the slot is cleared whenever the timeline already covers the post. This is deliberately *not* the `resolved_quotes`/`resolved_previews` unbounded-map shape: those fold into many list rows, this renders one surface.
- **The read is `fauna.posts.get` + decode**, the same single-post door `resolve_quoted_post`'s out-of-page fallback uses. Because it decodes the **raw signed envelope** it knows more than a list card does — the full body (not the 500-char FTS preview), a real `Verified`/`Failed`, and the media hash without `resolve_media`'s second fetch. It cannot know what only the feed-index projection holds: interaction counters, content labels, the web-publish slug, the protocol source, or the per-viewer pair (`viewer_repost_id`/`viewer_liked` — same class, deliberately not carried by the deep-link door). None of those are in ui.yaml's `feed.sub_pages.post_detail` element scope; a surface that grows to need one needs the wire to carry it, never a guess client-side.
- **The projection must not drift from the nest's indexer.** `has_media` / `is_reply` / tags / `quoted_post_id` are shared `fauna_core::data::Post` accessors (`has_media()`, `is_reply()`, `indexed_tags()` — lowercased, the spelling `content_links` holds — and `quoted_post_id()`), used by **both** the nest's `extract_post_metadata` and the client's `map_fetched_post`, so the same post reads identically whichever door opened it (priority #2/#4).
- **The rendered set is timeline + slot, everywhere.** `FeedSnapshot::rendered_posts()` / `find_post()` are the one definition of that union: every per-post lazy resolve (media, quote fold, link preview, unlock offer, muted-keyword collapse) and every unseal writes through it, so a deep-linked post gets the same treatment as a listed one. *Ranking* paths deliberately do not — the scored window, exemplar picking and re-rank read `posts`, because a deep-linked post holds no position in the ordered list.
- **A legally-taken-down post resolves to `PostResolution::TakenDown { reference }`, and the slot takes a tombstone `PostSummary`** (refinement built 2026-08-10). The nest withholds its body from every viewer, so there is no *post* to project — but there is something to render, and it belongs where the post would have been. `resolve_post` therefore parks `PostSummary::taken_down(post_id, reference)` in the slot (id + `legal_takedown_ref`, everything else `Default`: no body, no author, no timestamp, `verification` `Unchecked` because nothing was withheld-then-verified), so `find_post` answers for the requested id and each app branches on `legal_takedown_ref` to paint `fauna_core::obligation::legal_takedown_tombstone(reference)` **in the body area, in place of the post** — the third surface of the one concept, beside the quoted-post embed and the DM bubble (`../behavior/takedown-and-block.md` § Legal takedown owns that surface list). The page error surface no longer stands in for a body. The outcome is still returned, because a caller may need to skip work a live post would have earned (tui skips the gated-unseal leg on it). *Replacing* the slot is what protects the property the earlier clear-the-slot shape existed for — no earlier post may sit on screen under a different post's takedown notice — and protects it strictly better than emptying it did.
- **A gated deep-linked post unseals exactly as an on-screen one does.** The resolve and the unseal are ordered legs of one detail-open door, because a post outside the timeline has no snapshot row to ask "is this gated?" of until the fetch lands.
- **A post homed on another nest — the relay (ruled 2026-10-16, the first step of the cross-nest ruling in *Posts of authors you follow on other nests*; the relay and the shared resolve BUILT 2026-10-16, the apps' half built on tui, android, linux and macos and unbuilt on the rest — § Implementation status today).** `fauna.posts.get` answers from this nest's store, so a post this nest never received — a room post whose author is homed elsewhere, met by a member through the room's search (`../behavior/community-rooms.md` § Implementation status today) — misses here although its home serves it. The door gains a second resolve, `FeedManager::resolve_post_from(post_id, nest_url)`: the caller names the post's home when it knows it (a room search hit carries the room's home — the `RoomPostKeys::room_home_nest_url` seam), the manager reads this nest first and on `fauna.posts.not_found` asks its own nest to relay — the distinct kind `fauna.posts.get_remote { post_id, nest_url }` → `fauna.federation.post.get` (`../architecture/federation.md` § Federation residue surface, the post-fetch row, owns the kind, its gate and why it is distinct rather than an additive field) — and parks the result in the one slot with every property above intact: decoded and bound to the requested id, the takedown tombstone forwarded. `resolve_post(post_id)` is unchanged, and a resolve with no home named never relays. **The reply is the envelope alone:** the summary carries an additive `home_nest_url` so the byte legs the apps run — the sealed body behind `gated_blob_hash`, a photo's `media_hash`, its thumbnails — fetch by content address from the home's public `GET /api/v1/blob/{hash}`, direct, as a foreign room member already fetches a room attachment (`../behavior/conversation-rooms.md` § The home nest → *Attachment bytes*); how the app trusts the home's TLS on that direct dial — a self-signed home included — is `../architecture/transport-trust.md` § Transport trust, the federation-granted row's *post arm* (ruled 2026-10-19): the reply carries an additive `home_nest_actor_id` beside `home_nest_url`, the identity this nest dial-proved for the home when it relayed, folded onto `PostSummary.home_nest_actor_id` and read by `blob_home` with the host, and the plane graduates a per-process pin against it before the first byte; nothing fetches a foreign post's bytes from this nest, which holds none, and no byte rides the nest↔nest channel. The unseal is the ordinary one — a room post opens under the room's key the device holds — and the verdict read already picks `fauna.posts.room_labels_remote` from the room's recorded home, so a foreign member's card paints the room's labels the day the post resolves (`../behavior/restricted-posts.md` § Encryption at rest, *Built* detail (v); outcome 21 of the catalog page). Bridged `author_display` is not relayed: the home's bridge projection is the home's, and a raw envelope names its author — whom the reader's own client then dresses from the author's own signed profile, if they opened it to other nests (*The remote author's byline*, next). **The browser reads the same route direct (ruled 2026-10-21; BUILT 2026-10-21, the SPA's adoption pending — § Implementation status today):** the home's blob GET joins the nest's open-CORS byte router, so the SPA fetches a foreign home's bytes as the native apps do — no bearer, the same cap and digest check, the home from `blob_home` — with no pin, since a browser's fetch is WebPKI only: a home on the self-signed floor is unreachable from web and its post stays teased there, declared and never cured by a relay through this nest, which holds none of a foreign post's bytes and carries none (`../architecture/transport-trust.md` § Transport trust, the post arm's *browser's leg*, owns the ruling, the rejected relay and the residual).
- **The remote author's byline — the face resolve (ruled 2026-10-19; BUILT 2026-10-19 in shared Rust and on tui, android and linux, unbuilt on the other four — § Implementation status today).** A card or detail dialog of a post homed on another nest (`PostSummary.home_nest_url` set — a relayed post, a delivered follow post) names its author from the author's **own signed profile**, read by **this client** through its own nest's relay, once per author per window, and only when the author chose to show it beyond their nest ([`profile.md`](../ui/profile.md) § Where logic lives → *The remote read* owns the opt-in, the kind pair and the fallback). The mechanism is the feed's lazy-resolve pattern, nothing new: **`FeedManager::resolve_author_face(post_id)`**, guarded on a rendered post with a home and no face (`home_nest_url: Some`, `author_display: None`; a post homed here never relays), reads `ProfileClient::profile_get_remote(author, home)` — the one shared method the Profile page's header read uses, so the two never diverge — decodes the bytes through the one signed verify (`decode_profile`), binds the signer to the post's `author` (another actor's profile is no face: a home cannot pair a post with someone else's name), and writes the face onto **`PostSummary.author_display`** — the carrier [`../behavior/bridges.md`](../behavior/bridges.md) § Unified feed ingestion → *Bridged authors* shaped for exactly this second filler ("never a second one"), so **the card's label changes nowhere on any of the 7 apps**: every card already hands `author_display` to `peer_display_label` ([`../behavior/value-formatting.md`](../behavior/value-formatting.md) § Peer display label), and the chain reads nickname → display name → id as before. **One relay per `(author, home)` per window:** the manager memoizes the answer beside its quote, media and preview memos (`resolved_previews`'s shape), an in-flight slot folds the N cards of one author into one relay, and the answer lands on every rendered post of that author — list and deep-link slot alike (`rendered_posts()`) — in one notification. **Every outcome writes** (the tips convention, `Some(TipView::default())`): not opted in, home unreachable or refusing, `rate_limited`, a body that does not decode or names another signer all resolve to `Some(AuthorDisplayView::default())`, so the label falls through to the id exactly as for `None`, the guard closes, nothing retries within the window, and nothing reaches `error-message` — the author's choice and the network's failure look the same on purpose (the home's one `not_found` already hides which). The face is **`display_name` alone**: the `Profile` carries no handle (`profile.md` § Where logic lives → *Field ownership*), and the avatar is the avatar lane's — fetched by `Profile.avatar`'s content address from `PostSummary::blob_home` through `PostBlobHosts`, never from this nest, by the first avatar renderer (the open bridged-avatar lane; the view may grow an additive `avatar_hash` then). **Trust class:** the author's own signed word, verified by this client — a stronger class than the bridged face sharing the field; the chain does not distinguish them because `author_display` is display, never identity (identity is `author`, and the viewer's nickname wins). **The driver** is each app's existing per-post fire-once resolve walk — tui's `feed/mod.rs::fire_resolves_for` on the `FeedChanged` tick (the same tick whose next pass kicks the image byte fetches), linux's `render_posts`, web's `feed-post-host`, windows' `FeedPage`, apple's and android's card triggers — each gaining one guarded call, as the tips resolve did; the author window (`profile.md` § Layout & flow → *The Posts tab*) inherits it through the same walk. **Why the client and not the nest** (a face the author's home derives and ships with the delivery or the relay): **consent must bind at read time** — a face stamped at delivery outlives an opt-out (the author flips to `ThisNest`; every follower's nest keeps the stamped name), while the relay re-asks the home, which checks `audience` on every answer; **a stored face is the deferred receive-write** — the follower's nest stores the delivered envelope, so a face beside it is a stored projection of a remote profile that never updates (`profile.md` § Where logic lives → *Federation receive-write is deferred*); and **the trust class** — a nest-derived face is nest-asserted (the bridged class), while every other surface naming a native author paints a signature this client checked. Why not the bare id: once the read exists, a follow journey whose cards name people by hex is a cost the feed declares unacceptable. **Throttle posture:** the client's half is the memo (one relay per author per window — a page of fifty posts by fifty remote authors is fifty relays, the same order as the lazy resolves the page already fires, and never one per card); the nests' half is the relay's `User` class on this nest and the home's per-origin channel throttle ([`../architecture/federation.md`](../architecture/federation.md) § Security → *Rate limiting*); a `rate_limited` answer is a no-face outcome, never a retry loop. The window-held face and the no-caching rule: § Architectural rules, rule 1. A **local** native author's card is outside this rule: its face is the nest's to project, batched, into the same field — ruled 2026-10-19 and owned by [`../behavior/bridges.md`](../behavior/bridges.md) § Unified feed ingestion → *Bridged authors* → *The local native author* (the nest half built 2026-10-19 — § Implementation status today).
