## The convention — convention 6 (== point 6)

6. **Don't debug with screenshots** — use `driver.is_visible()`/`get_text("error-message")`/`count()`; read the error element before the main assertion and put its text in the failure message — failures must diagnose themselves.

   **Rider — diagnose against a witness you HOLD, never against a party you have no evidence about (ratified 2026-07-31).** "Failures must diagnose themselves" includes naming the right suspect. A multi-machine test's seat cannot observe its peers, so a message like *"the folder never appeared — was the linux seat started?"* asserts exactly the fact the failing process holds no evidence for. That guess has now been wrong **twice**, each time sending the diagnosis to the wrong machine: the closed "NEVER ARRIVED" misdiagnosis, and run `20260730-02`, where the macOS seat spent its full 1200 s budget blaming a creator seat that had in fact created the set and was concurrently exchanging files with the third machine — the real fault was the accusing app's *own* row list. The remedy is structural, not tonal: **before blaming a peer, re-read the same shared state through a DIFFERENT local surface.** `_diagnose_missing_set_row` (`test_filesync_multiseat_live.py`) reads the set through the Media explorer when the Folders row list comes up empty — two surfaces sharing a nest, not a code path — so "the set is on the nest and this app still shows no row" becomes a *local* verdict the seat can actually justify. Three obligations follow: a second witness that confirms the state ⇒ say the fault is local; a witness that is inconclusive ⇒ say **that**, never default to blame (an empty Media read is consistent with both a peer that never ran and a genuinely empty set, so it proves neither); and always dump what the failing surface *did* render — **a rendered count of zero is itself the evidence**, because a lazily-realized row costs the count as well as the row and therefore raises no exception to mark it (§ point 1's registration rules; [`apps/apple-e2e-automation.md`](apps/apple-e2e-automation.md) rule 6).

   **Rider — a deadline loop in the actions layer must SIGNAL on timeout, never fall through silently (ratified 2026-09-11).** A wait helper that polls toward a deadline and then just `return`s cannot be told apart from one whose awaited state actually arrived — the caller proceeds as if the wait had succeeded, and the eventual failure lands on an unrelated downstream assertion, misdiagnosed as a product bug. Measured: `ConversationsActions._wait_thread_open` (`actions/conversations.py`) returning silently on a chrome-only timeout made a mail bubble that takes 40.7s to render read as a broken chunk-rejoin for two days; `_wait_add_participant_dialog_closed` (same file) and `BridgesActions._wait_for_linux_action_label` (`actions/bridges.py`) shared the same shape and let their callers proceed as if a membership mutation or a link/unlink snapshot refresh had landed when it might not have. The rule: **no deadline loop may exit without signalling — either it raises** (the default; build on the shared `helpers.waiting.wait_until`, or a hand-rolled `AssertionError` carrying `self.driver.diagnose(...)` in the `_wait_resolve` style) **or it returns a value the caller must consume** — an unconditional `return`/fallthrough with nothing for the caller to act on is always the defect, whatever the helper is named (most of the population isn't `_wait`-named). This is NOT "every wait must raise": `_ensure_on_conversations_page` (`conversations.py:1341`) legitimately falls out of its deadline loop silently because an empty conversation list is a real, documented, caller-independent state (its callers assert on `list_threads` instead) — the rule is about *signalling*, never about banning a documented-legal silent settle. Enforcement follows convention 7's own precedent: a per-file **down-only ratchet**, `scripts/check_deadline_loop_ratchet.py`, mirroring `check_sleep_ratchet.py`'s shape rather than a hand-maintained count.

   **Rider — a long run's ERRORs and FAILEDs must be attributable on the run's OWN clock, and a module that never requested the fixture is no evidence about it (ratified 2026-08-30; widened from ERRORs-only to FAILEDs 2026-09-21).** pytest holds every traceback until the end-of-run summary. That is invisible at ten minutes and ruinous at scale: the 2026-08-30 docker-mode sweep ran **17 hours** and produced **135 fixture ERRORs** whose reason nobody could read until it finished, so three consecutive sessions bisected the cascade as a black box — re-running ten- and twenty-minute cuts to guess at a string the run had been holding the whole time. So `conftest.pytest_runtest_logreport` prints one truncated crash line the moment an ERROR **or a FAILED** is recorded (`_print_live_reason`; pinned by `tests/test_live_error_attribution.py`, whose survives-a-kill half is the tier_2 `tests/test_harness_self_termination.py` § 2). **The "ERRORs only, deliberately" carve-out was RETIRED on 2026-09-21**, and its retirement is the more general statement of this rider: it rested on a FAILED test being "already reported", which is true only of a run that *reaches its summary*. A held traceback dies with ANY abrupt end — and on Windows that end is the ORDINARY one, because pytest-timeout has no `signal` method there, so its `thread` method dumps every thread's stack and then `os._exit`s the process, and neither `pytest_sessionfinish` nor the terminal reporter's failure summary ever runs (convention 9's *Every test is bounded* bullet states the same split). Measured: an 11-file windows run printed `F` twice, wedged in a third and died at 900 s with **no summary and no counts**; neither failure reproduced in three isolated re-runs, so both causes are permanently unrecoverable. The two labels stay distinct — `[e2e] ERROR` for a *precondition* failing, `[e2e] FAILED` for the subject under test — because the diagnoses are, and the print is never fatal either way, following the same rule as `_write_feature_ledger`. **Its corollary is the rider above, one layer up.** Attributing that same cascade, a pass cited eight modules that stayed green *inside* the burst window as proof the cause could not be environmental — but **six of the eight never request a barrier-carrying fixture at all**, so they were never exposed and held no evidence either way. Measured across the sweep's first 214 modules: **all 135 ERRORs fall inside the 133 modules whose fixture closure reaches `_login_app_as`, and not one of the other 81 modules errored** — perfect separation, no counter-examples. A green module earns the right to be evidence *against* a hypothesis only once it is shown to observe the mechanism at all: **exposure first, then inference.**

   **Rider — a NEGATIVE visibility read is vacuous on a scrollable surface, and a negative leg is not evidence until a mutant has failed it (ratified 2026-09-21).** `is_visible` has exactly one driver-side implementation (`drivers/http_bridge.py::is_visible`), which forwards to each app's own `/element/visible` — so its meaning is the **bridge's**, not the driver's, and the bridges do not agree. windows' answers `elements.Length > 0 && !elements[0].IsOffscreen` (`flaui-bridge/Actions.cs::IsVisible`): literally the same `WalkScope` + `FindAll` lookup `Count` does, plus a **viewport** predicate. So on windows `assert not is_visible(x)` asks *"is x absent OR merely below the fold"*, and an element the defect really did paint answers **False** for the boring reason. Measured 2026-09-21: the forged-c2pa test's negative read **passed against a header-relay mutant** — the exact defect it exists to catch — because the forged card is the feed's second row and sat below the fold; `count` read **2** the whole time. The positive half protects nothing, since it reads the on-screen card. Two honest forms, and the choice is a property of the container, not of the app: **(a) `driver.is_absent(id, scope=…)` — the DEFAULT wherever "absent" means "out of the tree"** (a `Visibility`-gated WinUI element, an empty `ItemsSource`, an unrendered row; the one spelling of what this rider first wrote as a bare `count(…) == 0`). On windows it **is** `count(id, scope=…) == 0` (`drivers/windows.py::is_absent`): `is_visible` minus the viewport predicate, so it is exact in both directions — an offscreen-but-painted element still counts — and it issues **no scroll**, which matters because a UIA `ScrollIntoView` deep in a scroll container can take the FlaUI bridge down outright (`drivers/windows.py::is_nav_tab_revealed` records it killing the bridge mid-run). On every other app it is `not is_visible` (the `PlatformDriver.is_absent` default) and **deliberately not `count == 0`**: web's `/element/count` is `locator.count()`, which counts a hidden-in-DOM element, so a bare count in a multi-app test would red a correct web build — and only windows' `/element/visible` carries a viewport predicate at all (read 2026-09-21: android `ElementOps.isVisible` is `findAll(id).isNotEmpty()` and its `count` is `findAll(id).size`, linux `is_mapped()`, apple's visible registry slots, tui's painted-frame registry — there `Visible` and `Count` are the one `registry.matches` query — and web Playwright's `is_visible`). So the per-app difference lives in the driver shell and a test states only the intent; an app whose bridge turns out to carry a viewport predicate adds its own override, and `tests/test_driver_is_absent.py` pins who overrides so that is a deliberate act. ⚠ **A helper that returns a bare `is_visible` and is asserted through `assert not helper()` hides the same trap from every gate**: `SettingsActions.identity_qr_shown` — the identity QR, the secret itself — did, until it read `not is_absent`. **(b) `is_visible_scrolled(id, scope=…)`** (`drivers/base.py`) — for the cases (a) cannot serve: the element stays in the tree when logically absent, or the container **virtualizes**, so an offscreen row is never realized and a count of 0 would itself be vacuous. It degrades to a plain `is_visible` where a driver has no scroll support, and a genuinely absent element still answers `False`, so it can never red a correct build. ⚠ It is a **windows-side** form, not a cross-app one: on web the scroll is a Playwright `scroll_into_view_if_needed` that waits for the locator to *appear*, so on a genuinely absent element it runs the whole bridge timeout (`drivers/web.py::is_nav_tab_revealed` records the 500) — which is why a multi-app negative read reaches for (a), never (b). ⚠ **Neither form is self-proving.** A negative leg is coverage only once a **mutant of the defect it names has failed it** — convention 11's mutation duty, applied to the assertion class that needs it most: a negative read is the one whose green is indistinguishable from its own vacuity. This obligation is general; [`e2e-systematic-ui-walks.md`](e2e-systematic-ui-walks.md) § The convention — convention 17 states red-verification only for **walk invariants**, which is a strictly narrower scope and does not discharge it for hand-authored negatives. **An index ≥ 1 in an id or a scope is the loud signal** — `post-card[2]`, `device-card[N]`, `vps-server-type-radio[5]` all name something that can sit past the fold by construction — but it is the LOUD subset, not the class: an un-indexed read on a long scrolling surface (a provisioning page's Cancel button, a settings page's warning line) is the same trap, honest only by an unpinned assumption about how much fits the window. `scripts/check_negative_visibility_ratchet.py` therefore gates **every** bare `assert not …is_visible(…)` — the id `error-message` excepted, which convention 2's rider owns — down-only from a committed baseline (§ *Implementation status today*).

   **Rider — an app launch that times out names its suspect from four witnesses the launching process holds, and the budget stays a named constant (ratified 2026-10-30).** A readiness gate on a harness-launched app — the loop that waits after `launch()` or a relaunch for the app's agent to answer — ends one of two ways, and until 2026-10-30 its timeout said only that it had timed out: `drivers/windows.py`'s launch gate raised *"TestAgent poll loop never became responsive within 90s of launch … the app process may have failed to start, or is catastrophically starved of CPU"*, naming both suspects and neither, while its `recover()` twin already printed the process state, the epoch-fenced pushes and the app's log; linux, tui, macOS and iOS raise *"in-process agent never became healthy"*, android *"bridge not ready after Ns"*. Measured: a windows run errored at setup after 9293 s on that line, the session guessed starvation from the broker's tick history alone, and only a later read on Windows of the app's own log — one line, `fauna client logging initialised`, 79 s after the launch — settled that the app had started and stalled under the guest's 2-CPU fence ([`fleet-core-broker.md`](fleet-core-broker.md) § What a grant guarantees). The rule has three parts. **(1) Four witnesses, every one held by the launching process, none a guess about a peer** (the first rider, applied to the machine the app runs on): **(a) the process** — alive, or exited with its code (the bridge's `/session/status` on windows, `Popen.poll()` on linux/tui/macOS, the simulator pid on iOS, the instrumentation bridge on android), and **how much CPU it was given** — its own user+kernel time over the wall time since launch, read from what the harness already holds (`Process.TotalProcessorTime` on windows; `/proc/<pid>/stat` on linux and tui, for the app's own pid resolved under the handle, which is `xvfb-run`'s shell wherever that wrapper leads; `ps` on darwin; the device's `/proc/<pid>/stat` over `adb` on android), because that figure says what the app actually got where a lane's *k* says only what was asked — **and whether it asked for more: the time it spent waiting for a CPU, runnable and not running** (the kernel's own run-queue wait where it keeps one: the longest-waiting thread's `/proc/<pid>/task/*/schedstat` on linux, tui and the device; where it keeps none, the thread table sampled once a second from the launch until the app's agent first pushes its state — on windows by the bridge itself, on its own timer, never from the driver's gate loop, whose one iteration can spend 30 s in a UIA main-window resolve, the share of samples with a Ready thread; on darwin by a thread in the driver through the launch gate, the share of `ps -M` reads with an `R` thread less the app's own share of a core, because `R` covers running as well as runnable), because own CPU share says what the app got and cannot tell *not given* from *did not ask*: a launch that blocks on a lock or a socket spends as little CPU as a starved one (ruled 2026-10-30, after the quarter-core rule alone read a blocked launch as `STARVED`); **(b) the app's own record** — the launch's log tail where that launch keeps it (windows `<data_dir>/logs/fauna.log.<date>` and the inherited stderr the bridge drains, linux/tui the launch's `app.err` and the XDG log, apple the relocated home's, android logcat over `adb`, narrowed to the app's pid) and the timestamp of its first line, which dates the app's own launch handler (on windows `InstallLogging` is `OnLaunched`'s first statement); **(c) the timeline on the harness's clock** — the launch's post or spawn at +0 s, the first log line at +t, the deadline at +budget, printed as offsets so a 79 s gap to the launch handler is a number and not an inference; **(d) the machine over [+0, deadline]** — read from this machine's own agent ledger (`core-agent-probes.jsonl` in the slot dir, which the core agent writes on every machine: the fence's `cpus` against the lane's *k*, `priv_pct`, `phantom`, busy and outside — a local file, no network) and, best-effort, the host's line for the same ticks (`core-broker.py`'s `fetch_ticks`: `host_cores`, `steal_host`), each absence stated. **(2) The verdict is the message's FIRST line**, because the live-reason line (the third rider) carries 197 characters of it and a `[e2e] ERROR` at setup is read from that line alone: `launch timeout (<budget> s): FAULTED — <the exit-code phrase, or the log's fatal line>` when the process exited or its record holds a fatal (a `[fauna] FATAL`, a panic, `0xC0000409`); `STARVED — the app ran <c> core-s in <w> s and waited for a CPU <r> % of them; fence <n> of <k>, priv <p> %, phantom <q>, steal_host <s>` when it is alive without a fault, its own CPU share over the window is under a quarter of a core AND it waited for a CPU at least a quarter of the window — it asked and was not given — the machine's reading printed as the why (`steal_host` is context and never the decider: on 2026-10-29 it read the guest's storm, not the host); `STALLED, NOT STARVED — ran <c> core-s, waited for a CPU <r> % of <w> s; last line "<…>" at +<t> s` when it is alive, unfaulted and either was given its CPU (a quarter of a core or more: a launch that spins) or asked for none (under the quarter, and waiting under a quarter of the window: a launch that blocks) — both the app's, its log tail beside it, the two told apart by the figures on the line; `UNKNOWN — <the witness that could not be read, and why>` when (a), the ledger, or — under the quarter-core line, where it decides — the CPU wait cannot be read; the inconclusive witness says so, as the first rider demands, and never defaults to either suspect. The two quarters are one pair of named constants (`LAUNCH_STARVED_CORE_SHARE`, `LAUNCH_STARVED_WAIT_SHARE`). The two launch paths of one driver — the first launch and the relaunch — raise or print through ONE builder with the driver supplying the witnesses, shared across the drivers in `drivers/http_bridge.py` so the grammar cannot drift per app (priorities #1–#3; windows' `ack_timeout_diagnostics` and its `recover()` print are the prior art it folds). **(3) The budget stays a named constant with its measured basis beside it, never load-aware and never retried inside the test** (windows' `_RELAUNCH_READY_BUDGET_S` at 90 s from its measured cold start under load, the others' 30 s: a per-driver figure under one name): convention 14's shape is a generous named budget and a deadline poll, a budget that widens with the load reading is a wait nothing bounds (a kernel storm lasts hours; convention 9), and a retry under the same load spends a second budget to hide what the reservation exists to fix at its layer — a `STARVED` launch is the reservation unmet ([`fleet-core-broker.md`](fleet-core-broker.md) § What a grant guarantees): the harness NAMES it and the fence's own rulings answer it. A `STARVED` first line is an environment red; what a grade or a late-red blame does with it is that venue's ([`delayed-testing.md`](delayed-testing.md) § Blame for a red found late). **Evidence is the three forced launch failures** — the app's start broken on purpose (a test-agent-build fault hook, artifact-set wiring like the reset probe, never a knob), the app's CPU held back on purpose (the launched process pinned to one CPU that a burner saturates), and the app blocked on purpose (the same hook parking the main thread for good before anything else starts) — whose first lines read `FAULTED`, `STARVED` and `STALLED, NOT STARVED` respectively with no log opened by hand; the mechanism is pinned headlessly beside it with fakes for every witness (`tests/test_bridge_handle_lifetime_windows.py`'s shape). Build-out: § Implementation status today.

   **Rider — an app the harness finds dead of a crash when it closes it fails the test phase that found it, and the exit is read BEFORE the close (ratified 2026-11-04).** A harness close of an app — a driver's teardown, a test's `quit_app()` or `kill_uncleanly()`, the close inside `recover()`'s relaunch — ends the app however it was, so an app that had already died of a crash reads exactly like a clean close: the relaunch hands the next test a live app and the run stays green. Measured 2026-10-10 on Windows: a `MediaPlayer` disposed under the `MediaPlayerElement` still showing it killed the windows app with `0xC000027B` at every unload of a playing slot, and `test_feed_video_playback.py --app windows` read **5 passed** while the app died three times; only the machine's application event log knew. The rule has three parts. **(1) The exit is read before the close, never after:** a close is a kill (windows' `SessionManager.Quit` is `Process.Kill`, no WM_CLOSE), so the close itself cannot raise the crash, and it drops the handle the exit is read from — once it has run, what the app died of is unreadable. **(2) Only a crash fails, read off the witness the closing process holds** (the first rider): on windows the bridge's tracked handle, a crash being an NTSTATUS of error severity or `STATUS_BREAKPOINT`. A live app, no tracked handle (nothing launched, or the harness's own earlier kill), a kill, a signal, a clean quit and an ordinary exit code stay silent, because a journey may end its app any of those ways on purpose. The failure's first line is the verdict — `the app died before <close> closed it: <exit phrase>` — then when it died on the harness's clock (`it exited +t s after its launch, d s before this close`), then the post-mortem an ack timeout carries: the app's crash reports whole, the output tail, the shared core's log, read before the close's cleanup reclaims the data dir the log lives in. **(3) It is the ERROR or FAILED of the phase the close ran in, and no caller can swallow it:** the driver RECORDS the death (`helpers/app_deaths.py`) rather than raising at the close, and phase wrappers raise it as `AppDiedBeforeClose` at the end of the setup, call or teardown phase that found it — a raise at the close would vanish into the multi-seat helpers that wrap each seat's teardown in a bare `except Exception`, and would skip the cleanup other callers do after it. The close and its relaunch go ahead, so the tests after it run on a live app. A death found by the relaunch that opens a test is that test's setup ERROR — the commonest case, since a reset that navigates away from the state the earlier test left is what unloads it, and the earlier test's report is already written: its second line names the last test to finish before that setup, and the timing says how long before the close the app died. A phase that already failed keeps its failure as the death's context — a reset the dead app never acknowledged, a skip saying the bridge could not recover. **One death fails one test:** a failure that already reported it — windows' ack-timeout verdict `app process: DEAD — …` names the dead launch with a tag (`app_deaths.tag`) — marks that launch reported when its phase fails, and a close that later finds the same dead launch prints it instead of failing the next, innocent test; a verdict in an error the harness swallowed (the reset the `app` fixture recovers from) marks nothing, which is the silent path this rider closes. ## Implementation status today

- **Convention 6's close rider — the windows leg is BUILT (2026-11-04) and the web, android, linux, tui, macOS and iOS legs are BUILT (2026-11-05).** `drivers/windows.py::_read_exit_before_close` runs at the head of each windows close — `_stop_app` (the teardown half), `quit_app`, `kill_uncleanly` and `recover()`'s relaunch — and reads `/session/status` before the `DELETE /session`. `_is_crash_exit` takes an NTSTATUS of error severity (the `0xC…` codes, the CLR's `0xE0434352`) or `STATUS_BREAKPOINT`, and leaves `TerminateProcess(-1)` (what `Process.Kill` leaves, a sibling bridge's data-dir sweep say) and `CTRL_C_EXIT`. `_app_death_report` composes the verdict, `_exit_instant_phrase` and `ack_timeout_diagnostics`. The bridge's `/session/status` gained `exited_at` (`SessionManager.AppExitedAt`); its `--self-test-launch-status` pins the instant and that neither the exit code nor the instant can be read once the close has run. `helpers/app_deaths.py` holds the registry and the setup, call and teardown wrappers, registered as a plugin by conftest's `pytest_configure`. Pinned headlessly by `tests/test_windows_close_reads_exit.py` (tier_1: the read's order, every silent ending, the relaunch still relaunching, the wrapper's outcomes, a setup's naming of the test before it, the one-death-one-test tag, the registration). **Evidence, red first on Windows (2026-11-04), the `TearDownPlayer` fix reverted in a scratch tree:** `test_feed_video_playback.py --app windows` — 5 passed over three deaths on 2026-10-10 — read 1 failed, 4 passed, 3 errors.
