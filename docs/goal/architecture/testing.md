## The principle

A bug that reproduces only on example.com is a **fidelity gap**: some property of production that no local tier exercises. The fix is never "test on prod more" — it is to identify the missing property and push it down into the cheapest tier that can hold it. Prod is the *last* line, reserved for the irreducibly-live (real ACME certs, real external senders, real third-party clients, the real VPS network). Everything else must be reproducible in `just e2e-tier-4-test` or below.

## The four-tier taxonomy (mocking depth)

Every test belongs to exactly one of four tiers; the tier declares **how much of the stack is real**. Pin the marker on the file with `pytestmark = pytest.mark.tier_N` (list-form when combining with other markers). The `--tier <n>` pytest flag and the `just e2e-tier-{1,2,3,4}-test` recipes filter by it.

1. **tier_1 — In-process unit tests.** No nest binary, no app driver, no external process. Pure Python (or Go-package tests in `bins/*/internal/<area>/`). Fast (<1s), deterministic. Examples: `tests/e2e-unified/tests/test_scope_parser.py`, `test_fauna_ffi.py`. **The web SPA's own tier_1 equivalent lives outside the pytest tree** (`just web-unit-test`, wired into the cheap merge-gate scripts) — `apps/fauna-web/src/lib/**/*.test.ts`, run via `deno test`, no `pytest`/`tier_N` marker (the marker enforcement can't see non-Python files).
2. **tier_2 — Real driver + mocked backend.** Real app driver (web/linux/macos/ios/windows/android), real UI surface, but **at least one binary or external dependency is replaced by a stub** — `fakes/fake_bridge_daemon.py`, `fakes/fake_cloud.py`, wiremock, DNS fakes, `set_*_snapshot` state injection, a mock SMTP relay or OS keychain. Fast enough for inner-loop UI work but cannot catch wire-format or encrypt/decrypt drift between binaries.
3. **tier_3 — Full stack (locally-built binaries).** Every binary real, real wire end-to-end, real SQLite, real seal/AUTH/decrypt. Uses the `nest_instance` / `logged_in_app` / `admin_app` / `nest_binary` fixtures (which spin a real `fauna-nest` **binary** — and, for mail, spawn the `fauna-mail-bridge` process directly). API-only tests in `tests/e2e-unified/tests/api/` count as tier_3 — UI absence isn't a mock. Only tier_3 (and above) catches cross-binary drift like an MTA-side encrypt producing a payload the MDA-side decrypt rejects. It **cannot** catch Docker image/packaging/supervision bugs — spawning binaries directly bypasses the Dockerfile, the `docker/s6/*` run-scripts, and boot-time gates.
4. **tier_4 — Full deployment-artifact stack.** The test's subject is a real **deployment artifact under real supervision**, not locally-built binaries. Four shapes today: the real nest **Docker image** plus its `docker/`-defined sidecars (the `fauna-mail-bridge` MTA/MDA roles under s6 supervision, clamd, rspamd), wired on a docker network — the closest in-CI mirror of a real deployment, living under `tests/e2e-unified/tests/platform/docker/` — a real **installed desktop package under real service supervision** (the Flatpak-installed linux app driving its systemd user unit, living under `tests/e2e-unified/tests/real_session/` — convention 12 below governs *where* those may run) — and a **live-remote deployed box** (ruling 2026-07-22): a test whose target nest is an already-deployed real box, whether example.com (`live_box`/`live_nest` marked, env-gated) or an ephemeral provisioned VPS (`tests/live/`, `FAUNA_E2E_LIVE=1`-gated), runs against the production image under its real supervision by construction, so it is tier_4 regardless of where the *app* half runs — the pre-ruling `tier_3` marks on the `live_box` suites were drift, since "every binary real" described the mocking depth but ignored that the deployed artifact is exactly what the tier boundary names — and a **shipped CLIENT artifact** (ratified 2026-08-09): the macOS `Fauna.app` bundle, a DMG-installed copy of it, and the iOS device `.xcarchive`, living under `tests/e2e-unified/tests/artifact/`, opt-in behind `--macos-artifact` (`just e2e-macos-artifact-test`). It is the client-side statement of this tier's own rule: every apple e2e test otherwise launches the bare swift-build Mach-O, which has no bundle identity, Info.plist, embedded framework, or entitlement-bearing signature — so packaging, the layer where Apple runtime behaviour most changes, is exercised by nothing. Mechanism + the per-instance-bundle-id discipline that makes it concurrency-safe: [`apps/apple-e2e-automation.md`](apps/apple-e2e-automation.md) § Artifact launch mode. Only tier_4 catches **image/packaging/supervision** bugs the binaries hide: a workspace crate missing from the Dockerfile dep-cache COPY list, an s6 run-script that never starts a service, a subsystem no app UI path actually enables, a systemd unit whose exec/condition lines point at the wrong deploy path. Slowest tier — builds an image/package and starts containers/services (live-remote instead pays env gating + a real network); opt-in (`just e2e-tier-4-test`; `--real-session`; the live env gates), never in the inner loop.

**Decision tree for a new test:** running against a real deployment **artifact** — the Docker image + sidecars (`tests/platform/docker/`), an installed desktop package under real supervision (`tests/real_session/`), or a live deployed box (`live_box`/`live_nest`, `tests/live/`)? → tier_4. Spinning a real `fauna-nest` **binary**? → tier_3. Real app driver, but stubbing the bridge / cloud / DNS / nest WS-RPC / SMTP relay / keychain? → tier_2. No driver and no nest, pure in-process? → tier_1. Unsure between 3 and 4? If a binary nest can't reproduce it (it's a packaging/supervision concern), it's tier_4; otherwise tier_3 (bias toward stronger guarantees). Strict marker enforcement is the default: pytest collection fails if any selected test lacks a `tier_N` marker; `scripts/tag-test-tiers.py` is idempotent and auto-classifies new files (anything under `tests/platform/docker/` → tier_4) — rerun it after adding tests or fix the marker manually.

### tier_1 on android: Robolectric must share the UniFFI bindings (ratified 2026-07-30)

**Every Robolectric test in `apps/fauna-android` runs under `com.fauna.app.testing.FaunaRobolectricTestRunner`, never `RobolectricTestRunner` directly.** The runner shares `com.fauna.ffi.*`, `uniffi.*` and `com.sun.jna.*` with the parent class loader instead of letting each sandbox copy them.

The reason is that UniFFI's generated statics are not ordinary per-process Java state — they are a namespace **shared with Rust**. `FfiConverterType*.handleMap` is the only way Rust can resolve a handle back to a Kotlin object, and initialising `UniffiLib` registers the callback vtables into Rust's globals, last writer winning. A second copy in a sandbox therefore captures the vtables while the plain-JUnit tests keep inserting into the application loader's map, and Rust hands back a valid handle to a map that has never seen it.

That failure does not look like what it is. The generated callback evaluates `handleMap.get(...)` **outside** `uniffiTraitInterfaceCall`'s try/catch, so the resulting exception escapes into JNA, which logs a warning and returns without touching the out-params — leaving the call status at its zero-initialised *success* code and an empty return buffer. Rust lifts from zero bytes and reports `UnexpectedUniFFICallbackError(reason: "not enough bytes remaining in buffer (0 < 1)")`, naming neither handles nor class loaders. Because load order moves with allocation and GC timing, it presents as an order-dependent flake in whichever test happens to run later — for three sessions it was mis-bisected to a worker-reflection test that never touches the FFI. Two corollaries worth keeping: **the real exception is in the test XML's `<system-err>`, never on the console** (`grep 'Invalid handle'`), and a Kotlin compile failure leaves the *previous* run's XMLs in place, so `BUILD SUCCESSFUL`/`FAILED` alone is not a verdict. Pinned by `FfiBindingsSingleHandleMapTest`.

**Disambiguation:** the `tier0` / `tier1` / `tier2` markers (no underscore) are a separate axis — feature **breadth** (smoke / core journey / extended journey). `tier_1`…`tier_4` (with underscore) are mocking **depth**. A test can be both (`pytestmark = [pytest.mark.tier1, pytest.mark.tier_3]` = a core-journey test that runs the full stack). The no-underscore markers predate this taxonomy; the disambiguation is intentional — don't rename them.

## Default app and nest mode — the rust-first inner loop (ratified 2026-07-29)

**The default development workflow is end-to-end Rust.** Of the 7 apps, only `tui` is both truly cross-platform and pure Rust — no FFI, no toolkit, no browser ([`apps/tui.md`](apps/tui.md) § Goal) — and the nest is pure Rust; so the default inner loop for a feature is **shared Rust → nest → tui → tier_3 e2e**: one cargo workspace, one warm target dir, one machine, with no wasm-pack/deno/MSBuild/Xcode/Gradle/docker on the critical path. Everything non-Rust moves off the default path and behind explicit gates: the async `wasm-chunk-check` merge-gate leg guards web's compilability on every libs-touching merge ([`merge-gate-check.md`](merge-gate-check.md) § Merge-gate check), `just web-check` runs at web trickle-down entry, and tier_4 sweeps guard packaging/supervision.

Three defaults, each overridable per run:

- **Default app: `tui`, on every machine.** The e2e default app set is `[tui]` (all three dev platforms build and run it — `apps/tui.md` § Cross-platform). Cross-app sweeps pass `--app` with the full per-machine set; an app-specific track names its app. **The flip makes sweeps load-bearing:** tests for surfaces an app lacks deselect under `--app tui`, and cross-app regressions surface only in sweeps and trickle-down entry runs — so batched per-app parity passes are part of the workflow, not optional hygiene.
- **Default nest mode: `standalone`.** The nest-mode axis answers one question per run — *what fills the real-nest slot?* — with three modes (the third mode and the mechanics paragraph below ratified 2026-08-01): **`standalone`** — the harness spawns the locally-built `fauna-nest` binary (today's `nest_instance`-family fixtures); seconds to start, fresh private state — the red-green debugging loop lives here, and the axis must add ZERO cost to this default path; **`docker`** — the real image + `docker/` sidecars under s6 supervision (today's `tests/platform/docker/` shape); heavy to build but ephemeral: fresh private state inside the true deployment artifact, provable *before* a production release; **`live`** — an already-deployed real box (default example.com), zero provisioning but shared (flock-serialized) and **stateful**: the only mode with real DNS/TLS/network and accumulated state, hence the only one that catches works-on-fresh-only bugs — and its admin capability comes from the machine's ambient identity store (the same seed the two-seat live test reads; never a hard-coded path), so harness user-provisioning works there unchanged. Modes never differ in wire, at-rest, or configuration *semantics* (the only config surface stays the apps — [`../principles.md`](../principles.md) § One configuration surface; mode selection is bucket-1 artifact wiring, never a production knob); what varies is packaging/supervision (docker) and environment/state (live). The desktop-embedded nest daemons (windows service / macOS launchd) are a separate *artifact*, covered by tier_4's installed-package arm — an artifact class, not a harness mode.
- **TUI-first feature flow.** A new UI feature lands ui.yaml + shared Rust + tui first; the other six apps follow in **batched per-app trickle-down passes** — one dedicated pass lifts N accumulated features per app. Batching is where the build-cost savings actually come from: per-feature × 6 apps recreates the old cost with extra latency. The parity-debt meter is the `ui-actual-*` diff set; a trickle-down pass is due when an app's debt materially grows. **Carve-out:** a feature whose core journey needs a declared tui platform absence (`apps/tui.md` § Declared platform absences — inline AV, camera/QR, screen-reader tree, drag-and-drop) names **web** (the other cross-platform app) as its lead in its TODO. What makes the lag window safe at the protocol level is [`version-compatibility.md`](version-compatibility.md)'s additive-everywhere rule: lagging apps stay wire-compatible while they wait. Priorities #1–#3 are unchanged — uniformity still binds; only the *order of landing* changes.

**Modes map onto the tier axis; they do not replace it.** A tier classifies what bug classes a test *can catch* — a per-test property, pinned in its marker, covering tiers 1–2 where no nest exists at all. A mode is a harness input, meaningful only within tiers 3–4. A mode-agnostic journey test runs as tier_3 in standalone mode and as tier_4 in docker or live mode (live-remote ruling, § taxonomy point 4); the convergence target is exactly that — **one test source, written mode-agnostically over the nest fixture axis; never per-mode twin files** (the two-seat sync twins are the in-repo cautionary tale: keeping two files from drifting forced their legs into a shared third module plus a do-not-import-each-other note — a hand-built parametrization seam that still leaves two files to maintain). Per-mode files remain right only where the mode is the test's *subject*: **standalone-only** — anything driving the nest-side instrumentation surface (test-hooks fake clock, `run_now` pokes, snapshot injection), because convention 15 compiles that surface out of release artifacts and the image *is* a release artifact (client-side test agents are unaffected — apps stay locally built in every mode); **docker-only** — tests whose subject is packaging/supervision (s6, SNI fronting, sidecar topology, volume upgrades); **live-only** — the irreducibly-live suites (real ACME/DNS/external senders; Gap 3). **A SHIPPED LIMIT IS A TEST CONSTRAINT, NOT A ROUTE INTO THAT CLASSIFICATION (ratified 2026-08-30).** A release image binds every shipped rate limit — the anonymous account-creating throttles [`federation.md`](federation.md) owns, whose two split budgets the harness build lifts *at compile time* and therefore only in standalone — and inside a container every actor reaches the nest from the one gateway address, so a per-source budget is a budget per RUN. A journey test whose **subject is not the budget must FIT the shipped one**: reduce the fixture's calls (share one admitted account across the module; take the admin-authenticated admission path for an account whose admission is not under test), never pace them (convention 14 rules a wall-clock retry DEFUNCT — that exact `sleep`-and-retry was deleted from this very module once already), and never lift a limit in the release flavour (convention 15). **standalone-only is then available only to a test whose subject genuinely needs more than a shipped budget inside one window** — every other blanked cell in the release-candidate run below is a coverage hole, not a classification. Worked example: `tests/e2e-unified/tests/test_family.py` cost 30 invite-request submits against a budget of 10 and went red from its 6th test onward under `--nest docker`; the fix was to make it cost 6, and no test was reclassified.

**The docker-mode run against a released image is also the feature catalog's release-candidate vehicle** (ratified 2026-08-26): `just e2e-release-candidate <image>` is a `--nest docker:<image>` run whose tier_4-elevated outcomes are recorded per app with a bare-version stamp, and the `@pytest.mark.feature("<slug>")` marker is what ties a test to the catalog page it witnesses — owner [`feature-catalog.md`](feature-catalog.md) § Release-candidate run and § The marker; this section owns only the mode axis those ride on.

**A docker-mode run observes the IMAGE's nest, not the source tree's.** The image is cut by an explicit dispatch and can be days behind `main` ([`build-system.md`](build-system.md) § Image tags & channels owns the tags and when they move), so any *nest-side* observation in docker mode — a log line present or absent, a field emitted, a limit's shape — is evidence about the code compiled into that image and about nothing else. Before treating a search of the source tree as evidence about a container, check the image's build date against the commit being reasoned from (`docker image inspect -f '{{.Created}}' <image>`, or grep the shipped binary for the string in question); the measured failure is a session that read a `warn!` in the current source, grepped a container built three days before that line landed, found nothing, and retracted an observation that had been correct. *Client*-side observations — RPC error codes, test outcomes, app logs — are unaffected: apps stay locally built in every mode.

**Mode mechanics (ratified 2026-08-01 — this paragraph closes the former open marker-mechanics decision).** The mode is a **run-level input**: `--nest standalone|docker[:image]|live[:url]`, default `standalone`, single-valued per run (drivers and the shared nest are session-scoped; docker/live are scheduled sweeps by the economics above, never inner-loop multipliers — multi-mode coverage composes as separate invocations via `just` recipes). The chosen mode is stamped into every test ID as a single-value parameter (`test_x[tui-docker]` vs `[tui-live]` — per-mode distinguishability in logs and flake history without per-mode files). The file's `tier_N` marker stays the **authored floor**; collection stamps the effective `tier_4` marker on mode-agnostic tests in docker/live runs, so `--tier` selection stays truthful per run and strict per-file enforcement is unchanged. **Eligibility is classified exclusion, not opt-in**: by default a test runs in all three modes; the excluded classes are inferred (fixture closure + guarded nest-handle capabilities that fail loudly naming the marker to add — never a bare KeyError, never a silent skip) and tallied/ratcheted with convention 7's machinery: (1) **fresh-state** tests (unclaimed / reclaimable / factory-reset flows) — standalone+docker only, there is no virgin live box; (2) **nest-side instrumentation** — standalone-only, per above; (3) **global-admin-mutating** tests (spam thresholds, mail domains, federation peers — anything outside the run's own account, whether the test sends the kind itself or drives the admin shell through the app UI) — excluded from live by default under § The shared-box rule, individually re-admittable under its non-destructive carve-out (`@pytest.mark.live_ok`: a proven revert-on-teardown in the ordinary case), and switched off for a whole run by the disposable-box declaration (`--live-box disposable`, § The shared-box rule → *The disposable-box declaration*); (4) **db/proc-poking** tests — excluded wherever the handle lacks the capability; (5) **host-spawned-bridge** tests — excluded from docker *and* live, because `fauna.bridges.request_enrollment` is loopback-gated at the dispatcher and that gate fails closed: a bridge process the harness runs on the host is not a loopback peer to a containerised nest (nest sees the docker gateway address) nor to a box on another machine, so it is refused `fauna.bridges.remote_enrollment_unsupported`, never opens its listeners, and its whole module times out waiting on `/healthz`. Unlike (1)–(3) this class is a fact about the **product**, not the harness — cross-IP bridge enrollment is deliberately deferred ([`../behavior/mail-bridge-lifecycle.md`](../behavior/mail-bridge-lifecycle.md) § Cold boot step 3) — so it is a classification and not a gap to close: the faithful docker shape for mail is the image's **own** s6-supervised bridges dialling the container's loopback, which `tests/platform/docker/` already drives. Class (5) is checked ahead of (3), whose fixture half it now wholly subsumes, so the reason a reader gets names the enrollment gate rather than the shared-box rule, and `@pytest.mark.live_ok` cannot re-admit past it (it answers the shared-box rule, which is a policy; this one is structural). **Class (5) has a body half too (2026-08-29), for the same reason class (3) needed one**: a test can drive `request_enrollment` itself over an anonymous WS client with no bridge fixture anywhere in its closure, and one does — so the same call-graph scan answers it, over a kind set pinned by equality to nest's own `pre_identity_allowlist::requires_loopback_peer` rather than restated. **And a THIRD door (2026-09-02): the test that runs the bridge ITSELF.** Neither half above sees a body that `subprocess.Popen`s the built bridge binary inline — there is no spawning fixture to name, and the kind is never reached from Python at all, because the bridge that calls it is a separate process. Seven ATProto/Bluesky bodies are exactly this shape, so the signal taken is the BINARY fixture, one AST hop ahead of the spawn (`nest_surface.BRIDGE_BINARY_FIXTURES`): a test asks for a built bridge binary in order to run one, there being nothing else to do with it. It is pinned by equality to the product rather than hand-listed — a prebuild fixture belongs there exactly when the binary it builds reaches `wsrpc.EnrollAndAwaitApproval` — which is why the seal helper, built out of the very same `bins/fauna-bridges/` tree but performing a client-side seal step and never enrolling, is deliberately absent. **Its effect on a collection is deliberately NOTHING**: every one of these tests builds a local nest too, so `classify`'s first match already excluded them and no test moves mode. What moves is the **account** — the ratified order puts `nest_binary` (MIXED, closable where the binary is incidental) ahead of `bridge_spawn` (a FACT), so until this door existed all seven read as closable routing work, and routing them would have turned seven clean collection-time exclusions into seven runtime ❌ against product code behaving exactly as ratified. **(6) test-hooks-driving tests — excluded from docker *and* live, because the automation surface is compiled out of release artifacts** (convention 15 below; nest implements it as `#![cfg(feature = "test-hooks")]` on every `*_test_hook.rs` module), so every route under `/api/v1/test/` answers 404 on an image or a live box. Like (5) this is a fact about the artifact rather than a harness gap or a product defect, and it is matched on the prefix — the harness builds these URLs by f-string and some carry path parameters, so no whole-route literal exists — with a tier_1 pin asserting every route those Rust modules register really does sit under it. Both halves were found the same way: they were the last two failures of a docker-mode `tests/api/` run, each of which would have written a ❌ accusing working product code. **(7) own-artifact tests — excluded from docker *and* live, and recorded in the feature ledger with their OWN artifact's provenance, never the run's, because the test brings its own nest artifact.** Every `tests/e2e-unified/tests/platform/docker/` fixture boots the locally-tagged image `fauna-nest-test:local`; the run's `--nest` flag neither configures that container nor describes it, so such a test witnesses *that* artifact and never the run's. This is the image twin of class (2)'s binary rule and fails the same way one artifact along — and the ledger half was the sharper edge: with run-level provenance a self-contained test made all three fields (`commit`, `image_digest`, `nest_mode`) false at once, breaking the first-party premise that licenses the ledger at all, so since 2026-08-29 its record carries the booted container's provenance per record, and is declined where no single artifact can be named ([`feature-catalog.md`](feature-catalog.md) § The ledger, *own-artifact records*). Inferred from the fixture closure exactly as (2) is, and derived from the package's AST — seeded on the image TAG rather than on `docker_build`, since a fixture can boot the image without building it. Measured 2026-08-29: a docker-mode `--feature` sweep selected 81 of the package's 89 tests and 11 died `fauna.auth.signature_failed`, because the tag on that box had been built before the actor key went tagged-only — a controlled differential put the same `tests/api/` slice at 107 passed against the pulled release image and 108 errors against the stale tag, so with the ledger on (its default) those 11 would have written ❌ cells accusing working product code. **Checking which commit an artifact carries no longer needs that differential**: the nest image stamps the built commit both as `.Config.Env`'s `FAUNA_BUILD_COMMIT` (read by the release-candidate gate) and, since 2026-08-31, the standard `org.opencontainers.image.revision` label — `docker inspect <tag> --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'` answers "is this artifact older than fix X" as one command, mechanically, instead of the timestamp inference this class's incident required. The venue keeps its own recipe (`just e2e-tier-4-test`), where it claims no axis and is the right way to run it. On live, isolation is **account-scoped**: the fixture layer provisions its own users per run and reaps them at teardown, so an ordinary journey test touches no foreign state by construction and § The shared-box rule's non-destructive carve-out is satisfied structurally; convention 16's file-token namespacing remains for surfaces genuinely shared across runs (the long-lived sync folder). **The reap is `fauna.admin.users.suspend` (immediate) followed by `fauna.admin.users.delete` (scheduled), and the two-step is a fact about the nest, not a harness shortcut**: `users.delete` alone does not delete. That kind schedules a pending action whose delay is **7 days** (`ActionType::AdminDeleteUser`, `bins/fauna-nest/src/pending_actions.rs`), and the admin surface has no execute-now kind — a deliberate cooling-off window for the one action that erases a user, which the harness works *with* rather than asking to weaken. `suspend` is the immediate half (`suspend_user_now` + token revocation + socket close), so from teardown the account cannot authenticate, connect, or generate activity — which is the property the carve-out actually needs, since a human on the box sees nothing. The delete then executes on the box's own schedule. So a live run leaves a suspended, delete-scheduled account for up to a week: a real (small, self-reaping, loudly-warned) departure from "teardown removes every artifact the run created", stated here rather than left to be discovered, and closed properly by the ephemeral staging box (§ Gap 3) rather than by a weaker delete. Owner of the mechanism + the warning text: `tests/e2e-unified/helpers/live_accounts.py`. **(9) feature-set-binary tests — excluded from docker *and* live, a FACT of the same kind as (6) rather than a routing gap (ratified 2026-09-02, refuting this arm's own first count of it).** A test whose nest must be **compiled** with `test-hooks` depends on a *behaviour* a release artifact does not carry, and class (6) cannot see it: (6) matches the `/api/v1/test/` route prefix, while this dependence never touches a route. The ActivityPub outbound SSRF guard exempts a loopback target only under `#[cfg(feature = "test-hooks")]` and only with `FAUNA_TEST_AP_ALLOW_LOOPBACK` set (`bins/fauna-nest/src/activitypub/outbound.rs::test_loopback_allowed`), and every AP peer this harness can host *is* at loopback — the federation suite's in-process peers directly, and the real-fediverse interop stack through Mastodon's loopback-published TLS front. So `ap_binary` and the fediverse `peer` stack are honestly blank in an image-backed mode forever, where they had been sitting in `nest_binary`'s MIXED bucket reading as closable routing work. **The class is narrower than "a non-release feature set", and that distinction is the measurement rather than a nicety** — the arm's own scoping note had put four fixtures here on the strength of the phrase. The image ships `--features bluesky,nostr,activitypub` (`Dockerfile`), so a fixture pinning `bluesky` (`bluesky_nest_binary`, `bluesky_node_binary`) asks for a capability the artifact already has and stays closable debt; and `bridges_nest_binary`'s deliberately single-provider build is load-bearing only because `BridgesActions.link` clicks `bridge-action-button` at `index=0` on every app that renders bridges inline — a test-side disambiguation, so it too stays debt rather than becoming a fact about the artifact. Both halves are pinned by equality rather than restated: members and non-members alike are derived from the feature string each fixture actually builds with, and the image's own feature set is parsed from the `Dockerfile`, so the class reds rather than silently under- or over-excluding if either moves. One app-specific note, corrected 2026-09-09 (it had said the web driver loads the SPA *from the nest*, which the harness has never done): **web stays locally built in every mode like every other app.** The browser loads the working tree's test-flavour SPA from the harness's own CORS proxy and reaches the run's nest — the image's, in docker mode — through it; the artifact's own `/app` SPA is a release build with the automation surface compiled out (convention 15) and is never what a run drives. So a docker/live web run is a client-side red-green loop against the artifact's nest, the same thing it is for tui; the mechanics are Docker mode fact (g) below.

**N nests per run, and per-nest start options (ratified 2026-08-29 — the two questions behind the largest class of docker-blank catalog cells).** Measured against this tree with the catalog's mode audit (two collect-only runs joined against the coverage contracts, no container): the binary-closure class blanks 57 of the catalog's 105 pages (234 witnesses) and is the *sole* blocker on 22 of them, and its witnesses cluster into two shapes, not fifty fixtures — a test that wants a **second** nest (`two_nodes`, `second_nest`, `two_trend_nests`, …: 32 witnesses over 15 pages) and a test that wants a **bespoke** one (`dedicated_mail_nest`, `crash_nest`, `skew_nest`, `paid_nest`, the `tests/api/` self-spawners: 16 over 7, then a long tail). Both are answered by one mechanism, in four rulings. **(1) Every nest the harness starts is the mode's provider's to start, and `start` is N-ary by construction.** The provider protocol is already `start(nest_binary, tmp_path_factory, label, **options)` and `nest_instance` is merely its first caller; the ~20 conftest dedicated-nest fixtures (`_make_nest`) and the module-local self-spawners (`two_nodes`, `crash_nest`, `skew_nest`, …) route through `provider_for(run_mode()).start(...)` with the binary resolved lazily exactly as `nest_instance` resolves it. **The seam also takes the binary's NAME, so a fixture can name its own build** (added 2026-10-05): a test that needs a provider the standalone default build does not compile names its build fixture (`_start_dedicated_nest(…, binary="bluesky_nest_binary")`) rather than declaring it as a parameter. Standalone resolves that name just as lazily, and a non-local mode serves the run's image in its place. The name is admitted only when the image ships the build's subject (`IMAGE_SERVABLE_BINARY_FIXTURES`), never for a class (9) build: the seam refuses one at setup, and `DEDICATED_NEST_BINARIES` pins every named build at collection, which is also what keeps the build in the collection-time prebuild. Standalone's provider *is* `_make_nest`, so the default path stays byte-identical and pays nothing. A second (third) nest is the zero-option call: the same image the run named, never another; its own `/data` bind-mount under pytest's tmp tree; its own published `127.0.0.1:<port>` from `find_free_port` — the **port-allocation prerequisite**, landed 2026-08-29 when the last twelve fixed nest ports (`two_nodes` 13001/13002, `three_nodes`, ten `PORT_*` literals) became allocated ones; `find_free_ports(n)` serves an N-at-once fixture, and its close-then-reuse race is why a start retries on a bind collision rather than pre-reserving. **Host networking for a test container is REJECTED, and this paragraph is where that ruling lives**: the image's s6 tree binds fixed ports (`:443` router, `:8443` CalDAV, the mail ports), so under host networking two nests in one run — or two sibling sessions on the shared dev box — collide. All containers of one run instead join **one per-run user-defined network**, the venue's proven topology (`tests/platform/docker/helpers.py::create_network` + `--network`; sidecars addressed by IP literal because docker's embedded resolver SERVFAILs under churn), created on the provider's first start and removed with the session. **(2) `peer_url` is a contract key every mode answers — the authority ANOTHER NEST in the run dials** (standalone: `url`; docker: `https://<container-ip>:3000`, the shape the venue's two-box relay records on its home-side pairing row; live: `url`), and a test composes `nest_b["peer_url"]` instead of `f"http://127.0.0.1:{port_b}"`. **But a nest-dials-nest journey between two containers is refused by the product, and that refusal is exclusion class (8) — a fact about the nest, not a harness gap.** The federation dialer's SSRF guard (`federation_channel::validate_peer_url`) rides a loopback-literal carve-out for in-process and tier_3 peers and otherwise requires a globally-routable https target; a container network is RFC1918 by construction, and a fake-DNS name resolving into it is refused the same way (`NonGlobal`). Production peers are globally routable, so this is the security posture working — the docker mode cannot host it, exactly as it cannot host a host-spawned bridge (class (5)). The two-nest cluster therefore splits: **host-driven** two-nest tests (the harness drives each nest itself — the cross-nest API contract tests, a `second_nest` the *client* dials as a backup destination) run in docker; **nest-dials-nest** tests (the exchange originator, the trending fetch, the welcome relay, `fauna.inbox.send`'s `recipient_nest_url`) are classified out with a reason naming the guard, inferred the way class (5)'s body half is — a kind set pinned by equality to the nest's own callers of `validate_peer_url`, never restated by hand. **That set is WIDER than "a kind whose handler dials", and this sentence is the record of the measurement that widened it (2026-08-29, refuting this ruling's own first wording).** Class (8) is *a kind whose handler causes this nest to dial a caller-supplied peer URL — whether the handler dials it synchronously or **enrolls** it for a background worker to dial later*; and the enrolling half is the half that matters more, because it is the half that fails **silently**. The trending fetch is the case that forced the question. Its entry point is `fauna.feed.contributors.grant`, whose handler hands `req.nest_url` straight to `add_contributor_core` (`feed_routes.rs:719`) — which validates the URL not at all and upserts the row; the refusal then happens minutes later, inside the discovery poll loop's own dial (`discovery.rs:355` → `peer_query.rs:85` → `originate_feed_query` → the pool's `resolve_peer_nest_id`), where it is absorbed as a failure count, a demotion to `cold`, and finally a row DELETE (`discovery.rs:505`–`531`), never surfacing to the caller at all. So a docker two-container trending test does not fail with `non-global`: the grant succeeds, and the test times out waiting for content that was never going to arrive — the same product refusal wearing the least informative shape it has. `fauna.backup.destination.register` is the identical shape (`backup_handlers.rs:436` stores `destination_nest_url` unvalidated; `segment_backup.rs` dials it later through `originate_backup_write_token_mint`), and so is the box-pairing relay (`nest_sync_worker.rs:467` resolves the stored pair URL and answers a refusal with `warn!` + `return 0`). All three are class (8). The wire surface is wider still and has not been fully traced — `custody.rs::owner_nest_url`, `pair.rs::nest_url`, `folders.rs::nest_url` all carry a caller-supplied peer authority. **Class (8) is an ADDRESS-shaped refusal, not a KIND-shaped one — so it has no kind set, and this sentence replaces the kind-set pin this ruling first specified (measured 2026-08-29, refuting its own second wording).** Class (5) can pin to `requires_loopback_peer` because nest gates *by kind*, at the dispatcher, before the handler runs. Nothing of that shape exists here: the guard fires on the **address**, inside the federation pool, below the kind layer — and for the enrolling half, minutes later in a background worker. Four candidate instruments were built and closed by measurement against this tree, and they are recorded because each is the obvious next idea: **(a)** a static parse of `validate_peer_url`'s callers cannot reach an enrolling kind at all (the dial is connected to the handler only through a stored column and a worker); **(b)** the harness's own `peer_url` contract key, taken alone, could not distinguish a peer use from a client's own dial while the two-nest tests still composed their own loopback URLs; **(c)** the peer-authority REQUEST FIELD name is ambiguous in the harness and not merely sparse — `nest_url` is also this harness's ordinary parameter name for *the nest I am dialing* (`ApiActor(nest_url=second_nest['url'])`, `put_blob(nest_url, ...)`), so the same word means opposite things on the two sides of the wire: it selects 132 tests alone, and conjoining it with kind-reach still admits same-nest round-trips (`test_dm_roundtrip`, `test_key_package_lifecycle`) through a shared helper's optional parameter, while kind-reach by itself scores **zero** on every real witness (`test_federation.py`, the trending pair, `two_nodes`); **(d)** a dataflow from a second nest's handle to a peer field has no enumerable seed — a second nest reaches a test through arbitrarily-named fixtures that unpack tuples (`recipient_app, nest_b, recipient = folder_share_recipient_app`), so the taint would have to chase the whole fixture graph and would be wrong silently. **What classifies is the harness's own act of handing one nest's authority to another, and after this ruling's transport half that act has exactly one spelling: reading `peer_url` off a nest handle.** So the instrument is the contract key itself — a test whose reach READS `peer_url` is class (8) in docker — which is sound because nothing else reads it (measured: zero readers outside the mode-axis pins; conftest only ever *writes* the key) and because a client dialing its own nest correctly keeps using `url`. That makes the genuine population small and hand-verifiable rather than inferred: **four relay sites** in three files today. Two guards keep it honest, and both are pins by equality rather than restatements: a **ratchet** requiring every peer-authority field assignment to draw its value either from a `peer_url` read or from a source that is not another nest's handle (so a new `nest_url=other_nest['url']` reds the gate instead of silently under-excluding), and a **posture pin** on the guard itself — `validate_peer_url` still carves out loopback literals only and otherwise demands a globally routable target — so if the guard ever widened to accept RFC1918, class (8) would go red rather than keep excluding tests the product had started allowing. Deliberately NOT part of this: making the enrolling handlers validate at enrollment time. It is a real product improvement with a precedent already in the tree (`custody_hosting_handlers.rs` refuses `owner_nest_url` where the depositing client can see why, through `fauna_core::counterparty_url` — a *different* policy from this one, deliberately address-class-blind), but it is a nest-area product tradeoff (it also refuses a peer enrolled before its DNS resolves) and the harness must not need it: the classifier above is complete without it. Rejected: sharing one container's network namespace so peers meet at a loopback literal (`--network container:<b>`) — it forces `FAUNA_PORT` off 3000 (the documented CalDAV `EADDRINUSE` trap) and collides every sidecar's fixed port. **(3) A bespoke nest is a set of start options, classified by WHERE THE KNOB LIVES, and the provider declares which it honours.** Every option a fixture passes today (`unclaimed`, `handle_domain`, `registration_open`, `serve_tls`, `dial_host`, `extra_env`, `config_overrides`) is one of three kinds. *A product choice a user or admin makes in the app is not a start option at all*: it is applied **after** boot over the wire, mode-agnostically, the way `_dedicated_mail_nest_impl` already registers its mail domain and clears the spam gates — `registration_open` is `fauna.admin.set_registration_mode` after the claim (`config/default.toml` deliberately seeds none); a real-name `handle_domain` is the **domained claim** (the box boots domainless and learns its domain at claim — [`nest/domains-and-tls-bootstrap.md`](nest/domains-and-tls-bootstrap.md) § Claim), and a nest the provider claims that way is pointed at the run's pebble or the CA's *staging* directory, never at production from a dev box; mail domain, spam policy, CalDAV port and the enable toggles are admin kinds. Those fixtures stop passing such options at start — drift resolved toward the product's own surface. One residue stays standalone-only *by ratified design*: a handle domain that is an IP-literal **authority** (`127.0.0.1:<port>` — `cross_nest_foreign`, the two-nest box-recovery journeys) is the `--handle-domain` conformance-harness seed § Env contract of that doc wants dead, and the claim gate registers no local target; an option the provider cannot honour is a declared absence (class (4)), **never a mounted `nest.toml` and never a new entrypoint env** — both would be configuration-file theatre. **`handle_domain` therefore splits into two option NAMES, and the split is by WHICH MECHANISM SETS THE DOMAIN rather than by what the value looks like (refined by the build 2026-08-30; the wording above implied a value-level registerable-vs-IP-literal test, which the classifier cannot read and which measurement refutes twice over).** `FIXTURE_START_OPTIONS` is AST-pinned to the kwargs a fixture literally passes and both shapes spell the value as a bare `Name` (`handle_domain=authority` beside `handle_domain=MAIL_PRIMARY_DOMAIN`), so no value-sniffing rule can separate them at collection and honourability has to be legible in the option's *name*. The two names are **`claim_domain`** — the domained claim the harness already makes (`claim_admin(mail_domain=d)` → `claim_core` registers the primary `mail_domains` row → `apply_primary_identity` → `AppState.identity_domain`, which `handle_domain()` reads at top precedence), a wire act any provider that claims can perform and therefore honoured in **every** mode — and **`handle_domain_seed`**, the `--handle-domain` boot seed above, standalone-only and a class (4) declared absence everywhere else. Three measured facts decide which name a site takes, and the last two are why “the registerable ones all move to the claim” is wrong. **(a) The domained claim needs the HARNESS to claim the nest.** An `unclaimed=True` fixture has no harness claim to carry a domain — the *client* drives that claim through the app, which is the entire point of the fixture — so its handle domain stays the boot seed however registerable the value is; `unclaimed_mail_nest_ui`, `unclaimed_mail_nest`, `unclaimed_real_domain_nest` and `empty_store_unclaimed_nest` are `handle_domain_seed` sites for that reason alone, not because `fauna.test` is unclaimable. **(b) A domain is registered through exactly ONE door.** `add_local_domain` is idempotent *by domain name* and answers an already-active domain with `skipped: true`, **silently discarding that caller's `mta_sts_mode`, `mta_sts_cert_mode`, catch-all and DKIM-selector arguments**; every mail-shaped fixture and test in the suite registers its own domain with `mta_sts_cert_mode: "per_host"` while the claim path hard-codes `"expand_primary"`, so pre-registering at claim would turn each of those calls into a no-op leaving a *different* cert mode than the caller asked for — a silent behaviour change, not a redundancy. A site that registers its own domain therefore takes **neither** name: it drops the start option and lets its own `add_local_domain` set the identity, which is exactly what that call has done since it began calling `apply_primary_identity`. **The drop has one precondition, found while building it: the registration must happen before the nest is handed out.** Seven fixtures register inside the fixture body, a few lines after the claim and well before the `yield`, so their identity is live for every consumer and the option was pure redundancy. Five *tests* register the same domain much later — after `register_handled_actor` has already signed over it — and for those neither move is available yet: the claim would pre-empt their own registration, and the drop would leave the nest on the `localhost` fallback for the half of the test that runs first. They keep `handle_domain_seed` and a comment until that registration moves onto the claim, which is a per-test change rather than a harness one. **(c) So the honourable population is small, and is counted rather than assumed** — claimed **and** non-self-registering is the whole of it, against seven sites that lose the option outright and eight that keep the seed. **The ACME half of this ruling costs nothing to honour, also measured**: `apply_primary_identity` wakes the cert lifecycle, but `main.rs` arms that task only on the public NAT axis, in HTTP-01 mode, and **not under `FAUNA_INSECURE_DISABLE_TLS`, which every tier_3 e2e nest sets** — so a plain-HTTP test nest runs no ACME at all and the claim door adds no issuance the suite was not already doing, the mail fixtures having driven the identical `apply_primary_identity` through `add_local_domain` all along. “Pointed at the run’s pebble or the CA’s staging directory” is a live requirement only for the `serve_tls=True` sites, and every one of those is a seed site. *Artifact wiring is a container start parameter the provider honours*, each already catalogued in [`installers/docker.md`](installers/docker.md) § Environment Variables: `unclaimed` (skip the claim; the code is already on the handle), `serve_tls` (trivially — the image has no plain-HTTP posture), `extra_env` restricted to catalogued IPC (`FAUNA_DEPLOYMENT_SEED` for box recovery, the log level for the crash beacon — the s6 run scripts are `with-contenv`, so container env reaches the nest), `dial_host` (publish on the LAN address instead of `127.0.0.1` — the SPKI-pin branch), and the MX-override / scanner-sidecar addresses the venue's helpers already wire. `config_overrides` retires rather than ports — refined by the build (2026-08-29): no fixture passes it, so `_make_nest`'s parameter and every provider's declaration of it are gone, and `common.nest.start_nest`'s same-named parameter followed on 2026-10-02, when its last caller's seed — a private nest's pull target — moved onto the user's pairing row (`nest/private-mode.md` § Implementation status today). *A host-spawned bridge is not a knob*: `dedicated_mail_nest`'s MTA/MDA are class (5), and the docker shape of a mail nest is the image's own s6 bridges enabled through the product's toggle, its mail ports published to free host ports, the venue's sidecars (fake DNS, scanners, stub MX) beside it. The handle's port facts (`mx_port`, `imaps_port`, `caldav_port`, submission) come from the publication; its host-spawn affordances (`mda.respawn()`, the MTA log file, the metrics port) are declared absences — s6 owns the rebind in the image, which is why the admin-CalDAV-port rebind test stays standalone-only. **That list of absences was measured wider than ratified, and this sentence is the record (built 2026-09-02).** Two more affordances are host-spawn facts of exactly the same kind and had to join it: the in-process **stub MX** (an SMTP sink the harness spawns, reached through the operator-hatch `mta_mx_override` the image's bridges do not read — so docker's answer is a fake-DNS sidecar, a different mechanism rather than a different value) and the **DKIM pair** (`dkim_selector` / `dkim_public_dns_value`, which the standalone fixture provisions at spawn). Each is a per-TEST exclusion rather than a per-fixture one, and that distinction is what let the venue route at all: exactly four test functions read one, against three fixtures whose other consumers route perfectly well, so excluding by fixture would have discarded most of the arm's gain and excluding by nothing would have let a routed test reach a container and die on an `AttributeError` in its own body. **`rebind_after_enable` is NOT among the absences, and calling it one would be the arm's easiest mistake**: the standalone venue plays s6 because the binaries e2e has no supervisor, and the image *is* supervised, so there the same call is a DIFFERENT ACT — “wait until the bridges are serving again”. A `None` there strands every consumer that drives an enable through the app UI; a no-op makes them all pass vacuously. **A standalone-only option does NOT make a fixture unroutable, and conflating the two cost this ruling seven fixtures for a month (built 2026-09-02).** A fixture asking for `handle_domain_seed` can route through the provider seam like any other; what changes is only which reason excludes it — the MIXED `nest_binary` closure, which reads as closable work, or the named class (4). The reasoning that kept them out ("routing an unhonourable option would turn a clean collection-time exclusion into a setup-time refusal") describes routing *without* the table entry, which is a mistake and not a property of the option; routed with it, the classifier speaks first and the provider's runtime refusal never fires. **The IP-literal shape needed one mechanism and it is a VALUE, not an option**: the sentinel `common.nest.OWN_DIAL_AUTHORITY`, resolved inside `start_nest` to `f"{dial_host}:{port}"` — the same two values its `url` is composed from, so the domain a handle resolves to and the authority a client dials cannot disagree. The premise it retires is that such a fixture needs its authority known *in advance*: the authority only has to be known to whoever composes it, and that is the nest. A caller that had to allocate the port in order to compose the string was, for that reason alone, a caller that could not let a provider allocate it. *The seam*: a provider declares `supported_options`; the classifier holds a fixture→options table pinned by an AST equality test to the kwargs each fixture literally passes (the pin `LOCAL_NEST_FIXTURES` already carries), and a non-empty `needs − supported` is a collection-time declared absence naming the option and the mode; the provider's runtime refusal of an undeclared option stays as the backstop, never as the classifier. A provider that grows an option un-excludes every fixture needing only what it now supports, with no table edit. **A provider ALSO declares which of the options it does not honour it will NEVER honour (`permanently_unsupported_options`, added 2026-09-02), and that split is the difference between a work item and a fact.** "This mode does not turn that knob" had been two statements in one sentence: a knob a provider could grow — closable, which is the whole reason this class grades MIXED — and one ratified unturnable, which makes the cell it blanks honestly blank forever. Docker honours every option a fixture asks for **except** `handle_domain_seed`, which this ruling settles by name (the only ways an image could take a boot seed are a mounted `nest.toml` or a new entrypoint env, both banned above), so the class was **100% permanent while grading as 100% closable** — and it was the last MIXED *sole* blocker in the whole docker audit. Live is the same fact in the other shape and declares the all-options sentinel rather than a list: the harness started no nest there and cannot restart one with different flags, so the permanence is a property of the mode and enumerating today's option names would re-open the question every time one is added. The declaration lives on the provider beside `supported_options`, for that table's own reason — the thing that knows how to start a nest is the thing that knows which knobs it can never turn — and the default is empty, which is the safe direction here: an undeclared permanence reads as closable debt, over-reporting work rather than hiding it. **(4) Resource ceiling: a docker-mode run is ONE `e2e` slot, and its containers are that run's nests.** The run walks the fixture graph standalone walks as processes — one session nest plus at most three per-test dedicated nests (`three_nodes`) — so ≤4 containers per run and ≤8 per machine at the pool's width, and a default container is the nest, the router and the watcher (the mail, atproto and relay services are `down` until toggled): a standalone nest plus docker's overhead. No new pool and no per-container slot in `build-slot.py` — the pool bounds *runs*, the fixture graph bounds containers. What the pool cannot bound is a **leak**: convention 9 reaps every harness child with its process group, and a container is the one child the kernel does not reap. So every container and network the provider starts carries the labels `fauna-e2e=1` and `fauna-e2e-run=<run id>` — the live suite's provider-label sweep (§ Gap 3), applied to docker — the provider's first start in a session sweeps labelled leftovers whose owning run is dead (pid plus start-time liveness — the same check the fleet's session-liveness probe already makes) before starting its own, and the session's end removes its own by run id; the `fauna-nest-axis-*` name prefix is the legacy union, as the Hetzner sweep unions its `e2e-` prefix. Disk needs nothing new: `/data` is pytest's tmp on pytest's schedule, and the writable layer goes with the container. **Refutable downstream**: a build finding that contradicts any of (1)–(4) updates this paragraph first, then the code.

**Implementation status (this section).** The three defaults are real and the nest-mode axis is built out: `tui` is the sole default app on all three dev platforms, `standalone` is the default nest mode and its collection is byte-identical to the pre-axis harness, and `--nest docker` / `--nest live` are complete providers behind a classifier that accounts by ratified class for every test they cannot run. The N-nests build-out's routing arm is complete (2026-10-05): no `nest_binary` consumer is left OPEN, so every remaining one is a named PREMISE, a test whose subject is the locally-compiled binary. What remains is the mail-venue work named below. **This paragraph group states the current fact only.** The pass-by-pass record of how it got here — each pass's date, its measured collection counts and its refuted premises — is in this file's git history, which is the archive for it; a count quoted from a past pass is stale by construction (lesson 1 below), so re-run the instrument rather than reading one off a doc.

**The defaults flip is DONE.** `get_available_apps()` returns `[tui]` on all three dev platforms; the old per-platform sets moved to `sweep_apps()`, reachable as the `--app sweep` token, so one command means "this machine's full set" on every dev machine alike (`github` is untouched: not a dev box, consulted by nothing today, and its runner cannot build tui at all). Two properties of it are load-bearing and neither was free. `pytest_collection_modifyitems` applies the effective app set **whether or not the `--app` flag is present** — an absent flag means "this machine's default set", never "no filtering"; both filtering hooks used to key on the flag, so a bare run did no app filtering whatsoever and would have gone on collecting every `@pytest.mark.ios` / `web` test on every machine after the flip. And the client-independent suites (`tests/api/`, ws-rpc) deliberately stay in the *bare* run, dropped only by an explicit `--app`: they are pure nest/Rust tests with no driver, exactly what the rust-first loop wants most, and keying their removal on the flag also keeps `pytest tests/e2e-unified/tests/api/` collecting. **A collection diff is necessary and NOT sufficient** for a per-app coverage claim: file-level markers deselect, but a test can also collect for tui and then skip in its body or in the action layer, which no `--collect-only` can see. Convention 7 (§ below) owns that half — the `--strict-app` run mode plus the app-gate ratchet are what make such a claim falsifiable.

**The axis itself.** `--nest standalone|docker[:IMAGE]|live[:URL]` (plus `E2E_NEST`) resolves at `pytest_configure` into `helpers/nest_mode.py`; `nest_instance` and every routed dedicated-nest fixture start through a provider registry; and every nest the harness starts is a `NestHandle` whose *capability* keys (`db_path`, `proc`, `tmp_dir`, `config_path`, `node_binary`, `blob_dir`, `log_path`) raise a self-diagnosing `NestCapabilityError` naming the mode and the marker to add, rather than a bare `KeyError` or a `.get()` answering `None`. An unbuilt mode **refuses the run** at configure time as a `UsageError` rather than falling back to standalone — a silent fallback would report a green certification run against a nest it never started. Standalone declares every capability, so the guard is a verified no-op on the default path. `peer_url` is a contract key on every handle in every mode — `url` wherever no network boundary intervenes (standalone, live), the container's own `https://<ip>:3000` in docker, the one mode where the two differ and therefore the reason it could not stay an alias. The mode is stamped into the ids of nest-dependent tests only, and **the default mode is deliberately NOT stamped**: `[tui]` means standalone, `[tui-docker]` means docker. Stamping the default renames ~1400 ids including most of the apple baseline's keys, and that gate classifies a changed id as `added`+`removed` and never as `NEW RED` — so a real apple regression in that window would read as a benign addition, a false green in a gate only an apple-capable machine can regenerate. It would also buy less than assumed: pytest orders parametrized args by fixture scope, so the stamp's *position* is not stable, which weakens exactly the baseline/flake-history distinguishability that justified it. The whole axis is pinned headlessly in `tests/e2e-unified/tests/test_nest_mode_axis.py` (tier_1), each pin red-verified against a temporarily-reverted implementation.

**Docker mode** starts the real image with `docker/` sidecars under s6 and claims admin over the wire; `just e2e-docker-mode-test` is the sweep recipe, and `just e2e-release-candidate <image>` the release-candidate vehicle (§ above). Seven facts about it are load-bearing. **(a) The provider never builds the image** — building the nest image on a dev VM is forbidden ([`build-system.md`](build-system.md) § Image tags & channels), so an absent image is a loud refusal naming both remedies (pull a published tag, or dispatch the build workflow) rather than a surprise 20-minute build. **(b) `/data` is a host bind-mount, not a named volume**, so `db_path` / `blob_dir` / `tmp_dir` stay real capabilities and SQLite-poking fixtures survive the mode switch — it works because the image's `fauna` user is uid 1000, the same uid the dev VMs run as. `DOCKER_ABSENT` is therefore exactly **two** keys, each with its stated reason: `config_path` (the entrypoint writes its own) and `node_binary` (it lives in the image — and re-spawning a local one would be testing standalone while reporting docker). **(c) `log_path` is answered by following the container's log** into `<tmp_dir>/nest.log`, the same path standalone publishes, so every reader is mode-blind with no edit. Two consequences are deliberate: the file carries the whole CONTAINER's output rather than the nest's alone, which for a mode whose point is the deployed artifact is the more honest answer (any filter narrow enough to keep only "the nest's" lines would eventually drop the one line a test was waiting for), and the re-attach boundary is captured **before** `docker start`, while the container is down and can log nothing — a re-attach that replayed history would let a beacon from an earlier operation satisfy a watch armed for this one. **(d) A nest can be restarted in place, and can also exit itself.** `proc` survives as a container adapter with the `terminate`/`wait`/`kill`/`poll` surface the harness uses (`kill()` **is** `docker kill`, so a test that kills its nest to model total box loss models it faithfully here). `start_in_place` is a provider-answered key — docker's runs `docker start` on the **same** container (same published port, same bind-mount, fresh process tree under the image's own s6); a handle answering no such key falls through to the standalone binary re-spawn. Modelling it as Watchtower's container *replacement* would have been the tempting mistake: that swaps the artifact, and a mode whose entire claim is "this exact image" must not silently run a different one mid-test. `resume_after_self_exit` answers the factory-reset path the same way, and per mode in opposite directions — standalone has no supervisor so the harness becomes one; docker has a real one so the harness must do NOTHING, since a `proc.wait()` there waits on the CONTAINER's exit, which never comes. What witnesses the flip is the caller's own fresh/unclaimed convergence poll, latency-independent per convention 14 and strictly stronger than "some process exited within 30 s". **(e) N nests per run.** `_DockerProvider.start` is N-ary, each call taking its own port with **one** retry on a bind collision (a second is not a race but a machine out of ports, so it is loud) and joining the run's **one** user-defined network, created on the first start and removed at process exit. Every container and network carries `fauna-e2e=1` + `fauna-e2e-run=<pid>-<start ticks>`, and the first start of a session sweeps labelled leftovers whose owning run is gone. **The sweep fails CLOSED and that is the load-bearing half**: an unparseable owner, a pid the OS declines to answer for, and this run's own containers are all left alone, because the cost asymmetry is the inverse of the fleet's session-liveness probe — a false "dead" here deletes a sibling session's running nest, where a false "active" only starves a queue. It makes the same two-part pid-plus-start-ticks test that probe makes, **re-implemented inside the harness deliberately** rather than imported from tooling that is not part of the published tree (a harness reaching into it would work on a dev box and break on a contributor's clone). It has no age heuristic at all: a four-hour sibling run is not garbage. **(f) Mail and CalDAV venues are a provider METHOD** (`_start_mail_venue`), because a venue's mail listeners must be published at container start while the fixture-options table is name-level and mode-independent — a need that exists in docker and not in standalone is precisely what that table cannot express. Both venues answer one contract, so a consuming test reads the same attributes either way, and the docker one is a single container started through the provider's own `start`, inheriting the run network, the label sweep, the bind-collision retry and the claim. **(g) Web reaches the image through the harness's CORS proxy, and BOTH of the proxy's hops carry the run's floor-cert posture (measured 2026-09-01, closed 2026-09-09).** A browser can reach a nest only through `conftest._serve_spa_proxy` — the raw nest sends no CORS headers — and that proxy serves the *working tree's* test-flavour SPA, so a docker-mode web run drives the locally built web client against the image's nest, exactly as every other app stays locally built in every mode. The proxy's two hops used to disagree: the HTTP hop rode `common.auth`'s installed floor-cert opener and already spoke TLS to a marked loopback nest, while the WebSocket splice opened a bare socket and spoke plaintext into the image's TLS listener — lesson (5)'s signature, a connection dropped below application logging with the nest's log clean — so every web app-driven journey under `--nest docker` died at login, and one pass read that as "structurally never" and generalised the two cert-trust legs' web declaration onto every `https://` login, blanking the whole web column as a declared absence. **That was harness debt wearing a FACT's clothes, and `nest_surface.py`'s own taxonomy says which it is: a mode that could run the test once the harness support exists is `mode_unbuilt`, never `declared_absence` — and closable debt is closed, not ratified as a numbered class.** The splice now asks `common.auth.upstream_tls_context`, the same conjunction the opener and `ws_sslopt` apply (a loopback host AND a `mark_tls_nest`-marked port → the unverified context the floor cert needs; anything else, a real box on a real ACME cert included, → full verification), and the declaration is back at the two fixtures whose SUBJECT is the client's trust decision (`self_signed_nest`, `spki_pinned_nest`), which web structurally does not make ([`security.md`](security.md) § Transport trust). An ordinary journey against a TLS nest asserts nothing about trust: the proxy is a CORS shim the harness stands up in every mode, and the posture it applies is the one every native client already grants the harness-started floor cert. Pinned end-to-end in `test_nest_mode_axis.py`: a real TLS listener completing the upgrade behind the real proxy, the converse for an undeclared listener, and the non-loopback guard.

**Two container facts the design did not have, both measured as failures first, and both generalise.** Publishing the CalDAV port is necessary and not sufficient: without `FAUNA_LAN_BIND_IP` the entrypoint pins the DAV listener to the container's own loopback behind the always-up SNI router, which routes DAV only by a `mail.<domain>` SNI, so a published 8443 accepts TCP and immediately EOFs while every mail listener beside it serves. And CalDAV must be turned ON at venue setup, because standalone's MDA binds a CalDAV listener from an operator-hatch pin whatever the deployment toggle says — which is why every consumer reads `caldav_port` after a MAIL enable and never enables CalDAV at all — while the image has no hatch and gates the four DAV protocols independently. That hatch pin was a host-spawn affordance hiding in plain sight; the venue's answer is the product's own toggle. The same asymmetry decides the CalDAV-only venue, which is the MTA-free shape of the same method rather than a second setup: a CalDAV-only deployment never writes `/data/imap-enabled`, so the image's MTA re-downs itself by its own s6 run-script gate — that venue therefore publishes no SMTP or IMAP port, runs neither content scanners nor a resolver (both exist for the inbound SMTP perimeter, and a deployment terminating no SMTP meets none of those gates), and answers both MTA-shaped questions by **refusing** rather than by reading the supervisor, since the image's idle MTA reports `down … normally up` and a live check would tell a test that requires an MTA that it has one. The container handle reads its SHAPE off its own publication, keeping "no port 25 published" and "runs no MTA" one fact rather than two that can disagree. **The fake-DNS sidecar is part of the venue, and the reason is not the MX override**: a published container port turns on every loopback-EXEMPT perimeter gate at once. The MTA exempts loopback peers from the HELO-identity and sender-domain checks by design (local relays and cron legitimately send from non-resolving domains, mirroring postfix's `permit_mynetworks`-before-`reject_unknown_sender_domain` ordering), so a standalone venue — a host process its tests dial at `127.0.0.1` — never meets either, while a container sees the same client arrive over the published port as the docker gateway and meets all of them. They surface one at a time, each looking like a plausible one-off (`554 HELO identity check failed`, then `550 Sender domain has no DNS records`); **the venue difference is the CLASS of gate, not the individual gate.** The HELO one is answered by policy (setting it false reproduces standalone's effective posture rather than relaxing past it); the sender-domain one is answered by making it PASS, which is the higher-fidelity move — so the venue publishes A+MX for exactly the three domains the standalone hatch overrides, existence only, because the gate asks about the ENVELOPE sender's domain and on an inbound delivery that is never the local one.

**Live mode** resolves an already-deployed box (`:URL` > `FAUNA_LIVE_NEST_URL` > the project's own live box), takes its admin identity from the machine's **ambient** identity store, resolved **per box** by `helpers/multiseat_config.resolve_secret(url)`: `FAUNA_LIVE_SECRET_HEX` > the box's own provisioning identity (the `secret_hex` its staging-box provisioning test minted into `~/.config/fauna/staging-box/<host>.json`) > `~/.fauna-id` — never a path baked into the harness, and never one box's seed offered to another (2026-10-04: example.com's `~/.fauna-id` offered to `dev.example.com` was refused `not_registered` and skipped a whole run as a reset box) — and starts nothing: the provider is a resolve-and-verify whose token mint doubles as the reachability probe, so a wrong URL, a dead box or a wrong seed fails there with that diagnosis instead of surfacing later as an unrelated test failure. **That probe is the live preflight (`helpers/live_box_door.py`, `reaching_the_live_box(…, admin_probe=True)` and `preflight_admin`; user-directed 2026-10-04):** a box that is down, or that answers `fauna.auth.not_registered` to the admin seed (unclaimed, reset, or the wrong box's seed), is a fact about the BOX, so the run skips as environment and records nothing, its skip text naming the seed's source (`live_box_door.admin_probe_what`) — the same answer anywhere else, and every other typed refusal, stays the product speaking. A live test that fails after the preflight passed is therefore a real signal about a box shown to be claimed. Four things are load-bearing. **(a) `LIVE_ABSENT` is all seven capability keys**, each with its own reason — one fact wearing seven hats: the nest is on another machine, so these are local-machine questions a live run should not be asking, and the guard refuses by name rather than answering `None`. **(b) Neither docker nor live builds a local `fauna-nest`** (`nest_mode.builds_local_nest`): both were paying a cold ~15–25 min cargo build plus its machine-wide `build`-slot wait for an artifact they never execute, and making it a property of the mode is what stops it being forgotten per-test. `nest_instance` therefore resolves `nest_binary` **lazily**, only where a local binary is what fills the slot — the change that made the binary-closure rule expressible at all, since it was unstateable while `nest_instance` declared the name for everybody. **(c) Account-scoped isolation.** Each run creates its own account rather than sharing a long-lived seed, which is possible because the DoH phase of the handle check resolves the handle's DOMAIN only (`fauna-onboarding-machine`'s `run_handle_check_phases`, phase 2 — NS records + TLD validity), never its localpart; what binds a handle to an account is phase 4's silent challenge, which authenticates the imported secret and reads back the handle the nest stored. So an account registered *seconds ago* answers `AlreadyOnNest { handle_matches: true }` exactly as a year-old one does. The corollary is a requirement, not a detail: the account must be registered **with** a handle, because a handle-less one reads as `already_on_nest_handle_differs` and never reaches the feed. The assertive-cleanup finalizer is **kept and live-gated**, not dropped as redundant — the reap suspends immediately and only *schedules* the delete ~7 days out, and convention 16 makes "a run deletes what it created and says so when it cannot" a condition of the standing unattended authorization; the reap knows an account because the harness's one WS-RPC wire core (`clients/_ws_rpc_core.py`) notes it on the successful reply of every account-creating kind (`helpers/live_accounts.ACCOUNT_CREATING_KINDS`), whichever helper, fixture or test body sent it — never a per-call-site note, which most creators omitted (one interrupted 2026-10-04 sweep leaked 53 accounts that way). An invite request is noted as *pending*, because only an admin's approval — on live, made through the app UI, which no harness dial observes — turns it into an account; the reap reads the nest's `not_found` on a pending entry as never admitted, not as residue. A succession ceremony the app runs moves an account and its handle to a fresh actor id no harness dial observes, while the retired id keeps a handle-less row the nest suspends without complaint — so before suspending anything the reap lists the box's users and reaps whichever actor now holds a handle the run minted (handles are unique per box), and a failed listing is a printed warning naming the handles it could not follow. Every nest a live run starts is the same box and the ledger is run-wide, so only the last open handle on the box reaps — a module-scoped dedicated nest's teardown that reaped suspended the session `test_user` mid-sweep (measured 2026-10-05). The reap's lines reach the run's log through `pytest_terminal_summary`, since pytest discards a passing test's captured finalizer output. The live handle records the box's HOST per port beside the TLS scheme (`common.auth.mark_nest_authority`, read by `port_base_url`), so a helper keyed by port reaches the box instead of loopback; the host is addressing only, and a non-loopback box stays certificate-verified. `--nest live` also engages the shared-box flock from the mode rather than from a marker plus an exported env var. **(d) Global-admin mutation is classified by KIND, not by test.** The kinds are a closed vocabulary that `libs/fauna-protocol/src/kind.rs` registers, whereas the tests calling them are open-ended — and a prefix scan over test bodies was measured and rejected (its hits polluted by read-only kinds and by *error codes that are not kinds at all*; membership in a closed vocabulary excludes those by construction, which is the whole reason the inversion works). The partition is **derived from the nest's own authorization boundary**, not from a name heuristic: `bridge_method_allowlist.rs::is_permitted` maps each kind to a `CallerClass`, and a kind an ordinary `User`-class caller may invoke cannot mutate outside that caller's account without the nest having a privilege bug — so **R1** ([`account-data-plane.md`](account-data-plane.md) § The ratified decisions) User-class ⇒ account-scoped, **R2** an `Admin`-class *read* ⇒ account-scoped (this is what stops the pollution: the `*.list` and `get_*` reads are what test bodies name constantly), **R3** a stated carve-out for the harness's own account provisioning, which is *argument*-dependent rather than per-kind safe. Anything the three rules do not admit is global, so the lazy direction is the safe one. **Kinds whose caller class is a bridge role are argument-scoped rather than caller-scoped** (they take an explicit `actor_id`), so R1's argument does not extend to them and they are global even when read-shaped — a choice made on measurement, not taste: admitting the read-shaped bridge-role kinds excludes *exactly the same tests*, so it buys no coverage while requiring a kind-by-kind judgement about which "reads" secretly write, and that judgement is genuinely treacherous (`kind.rs`'s own comment on the cluster is wrong in both directions). The partition is pinned to `kind.rs` **by equality**, not by a ratchet, so registering a new admin/bridge kind fails a tier_1 test until somebody classifies it — a ratchet would let the newest and least-reviewed kind be the one nobody looks at. The mechanism half is a fn-name-keyed AST call graph over the whole e2e tree **and `tests/common/`**, whose wire helpers conftest imports (`helpers/kind_reach.py`), built lazily and only when a live run asks, so the standalone inner loop pays nothing; keying on the bare function name merges same-named functions across modules, which over-approximates, and over-approximating is the safe direction here. **A function also reaches the literals of every top-level constant of its own module that it names (2026-10-05)** — a `@pytest.mark.parametrize(…, _PUT_CASES)` table, an `ARM_BUTTON = "admin-…"` element-ID name — because the dev.example.com tui sweep's collection still selected a test that would have overwritten the box's global mail policies (its kinds sat in its parametrize table) and the deployment-seed rotation journey (its admin IDs sat in module constants); the scan's own policy tables (`nest_surface.py`) are not resolved, and the admin shell's way out (`nest_surface.ADMIN_SHELL_EXIT_IDS`, the `admin-nav-back` anchor the launch harness waits on) marks no journey. **A test's reach is its own function's plus every fixture's in its closure (2026-09-25):** a global mutation a fixture makes is the test's. Until then the graph was rooted at the e2e tree alone and consulted only the test function's name, so a module fixture adding a mail domain, or `test_user` lifting the `free` tier's caps through `common.auth.set_tier_caps`, ran on the live box unseen, and every live run lifted `free` for every user on it. The one carve-out is a fixture that **disables its mutation on live** (`nest_surface.LIVE_SELF_GATED_FIXTURES`, pinned so none joins silently): the autouse primary-mail-domain pin, `nest_instance` (which refuses `--reclaim-cycle`'s factory reset on live) and `test_user`. **On live `test_user` writes no tier row:** `tiers.update` and `tiers.create` are global and no kind deletes a tier to reap one, so the run's account keeps the box's `free` caps, or moves itself (`users.update` on its own actor, the provisioning carve-out) onto a tier named `e2e-harness` when the box's admin has created one — creating it is the admin's choice, never the harness's. **The admin defines it through the tui admin Tiers page** (the add-a-tier form, `admin.md` § 3 — user-directed 2026-10-04: the app UI, no API): `tests/e2e-unified/tests/test_live_e2e_harness_tier.py` drives exactly that, opt-in via `FAUNA_LIVE_DEFINE_HARNESS_TIER=1` and never part of a sweep — it copies `free`'s caps with `max_devices=64` and `max_feeds=1000`, is a no-op when the tier is already listed, and the tier is permanent (the wire has no tier delete). Defined on `dev.example.com` 2026-10-04. **The app is a third door, and the kind scans cannot see it (2026-10-04).** A journey test mutates through the admin shell (convention 8 — the app, never an API call standing in for the user), so the kind the nest executes is sent by the tui/app process and no string in the Python call graph names it; a tui sweep against the staging box that day rotated the OAuth issuer key and the session secret, designated the web apex actor, set the spam unlisted-recipient penalty to 1000 and flipped NAT mode, pairing and the DAV toggles, every one by a test both kind scans read as eligible. The answer is the same graph over a **second closed vocabulary the spec registers**: the element IDs ui.yaml lists on an `admin-*` page and on no other page (`nest_surface.admin_shell_element_ids`, derived from the spec at the first live classification and never hand-listed — an ID the spec also lists on a non-admin page, `error-message` or the log viewer's rows, says nothing about where the app is). **There is no account-scoped half to admit**: the admin shell is by definition the one surface where every admin-chosen, nest-wide value is set ([`../principles.md`](../principles.md) § One configuration surface), so where the kinds needed R1–R3 to keep reads in, the shell needs nothing, and a read-only admin journey lost to live is the safe direction exactly as an unclassified admin kind is. A test's reach is its own plus its fixtures' here too, which is what makes a fixture list unnecessary: `admin_app` waits for `admin-dashboard-heading`, so every fixture that lands the app in the shell names an admin element itself. Re-admission is `@pytest.mark.live_ok` under § The shared-box rule's non-destructive carve-out, with the blast-radius argument in the docstring — the harness-tier definer above and the live-box bootstrap are its first residents, both additive-only acts the box's admin opts into by env; a whole RUN is re-admitted by the disposable-box declaration, never a test (§ The shared-box rule → *The disposable-box declaration*). Measured at the change: the scan deselects 150 of the ~6,000 live-eligible test functions, all of them admin-shell journeys. One refinement to the graph landed with it, because the bare-name merge was the scan's dominant false positive: a bare call to a **module-private** function (`_state`, `_off`) resolves in its own module, which is what the leading underscore means — four test modules each defining their own `_state` had inherited a live-provisioning test's, and lifting the merge also returned 45 tests the kind scan had excluded the same way; an attribute call to a private name keeps the merge. **(e) A box that stops answering is environment, never a record (2026-09-23).** Because the session nest and `test_user` are cached, a box that is down when the run first touches it would fail every test behind them in setup, and a setup `error` is a recorded outcome; one run launched minutes after an outage turned a dozen working tui features ❌ that way. So the harness's first contacts (the provider's probe, the shared account provisioning) go through `helpers/live_box_door.reaching_the_live_box`, which on live turns a failure where the box never answered (refused or reset, DNS, TLS, a 502/503/504 at the upgrade) into a declared `skip_environment`, the class [`feature-catalog.md`](feature-catalog.md) § Cell semantics never records. Anything the box *answered* (a typed refusal, a 500, a link that died mid-request, a reply that never came) stays an `error`, because it may be the product. Off live the door is transparent.

**What only a harness-started nest gives is deselected at collection, never recorded (2026-10-05).** The first full tui sweep against `dev.example.com` recorded about sixty tests as failed live cells that live mode could never have passed — the harness had collected them, so (e)'s environment door never applied and each landed as a ❌ against working product. Four classes, each read off the test's own code or fixtures, now deselect them. **`in_process_tier`, docker and live:** a `tier_1` test is in-process with no nest for a mode to choose — a mode is meaningful only within tiers 3–4 — so it belongs to the standalone run, and some pin the standalone environment itself. **`absent_capability`, live only:** the test's own code reads a capability key (`db_path`, `proc`, …) off the handle, which (a) refuses by name. "Own code" is the test function, the module-level fixtures and class methods of its module it requests, and the module-private functions those call bare (`kind_reach.own_code`); a shared helper counts only by name, from a table derived from `helpers/`, `clients/`, `actions/` and `tests/common/` (`capability_helpers` — `stop_nest` reads `proc`, `segment_dir` reads `db_path`), never through the merged call graph, which floods on words this common (measured: 5,709 of 6,633 tests through methods named `stop`, `close`, `launch`). Live only because live answers no capability key at all, while docker answers some and its helpers ask the provider before reading one. **`one_live_box`, live only:** a closure holding two nest-starting fixtures (the keys of `FIXTURE_START_OPTIONS`, `nest_instance` among them) needs two distinct boxes, and every nest a live run starts is the same box (c) — a backup destination, a linked nest or a second user's "other" nest lands where that identity already exists (`user already exists`), and a federation test between the two passes vacuously. **`harness_box`, live only:** the test asserts a premise only a nest this harness started holds — a loopback address, no public domain, a feed nobody else posts to — declared with `@pytest.mark.harness_box` or, for a fixture whose premise it is, `nest_surface.HARNESS_BOX_FIXTURES`; docker keeps these, a docker nest being a fresh nest on this machine's loopback too. Two existing classes grew a door each. **Class (4)** now reads a start option the test's own code passes as a truthy literal to a nest-start entry point (`provider.start(…, unclaimed=True)`), and a fixture its own code requests lazily (`request.getfixturevalue("self_signed_nest")`), which pytest's closure never lists; only this class reads the lazy names, because a lazy request is often mode-conditional (`nest_binary` behind `builds_local_nest`). **Class (6)** now matches the kinds only a `test-hooks` build registers (`nest_surface.TEST_HOOK_KINDS`, pinned by equality to what the `#[cfg(feature = "test-hooks")]` modules of nest's `lib.rs` `.add(…)`: `fauna.protocol.echo` today), and the call graph gained one edge it had lacked: a call to a class reaches that class's own `__init__`/`__enter__`/`__exit__`, keyed by the class name — the type a constructor call names — while an explicit dunder call stays no edge (three search journeys armed the rpc-hold hook through `FailingNestArm.__enter__` unseen). Where a red was harness rather than premise the test was fixed instead: loopback dials take the handle's own URL (`port_base_url`), a post count that saturates at the feed's 50-card first page asserts the test's own posts, and the anonymous-gate proof calls a kind every build registers. A multi-machine round that dials its own box (`test_filesync_multiseat_live.py`) is `standalone_only`: a `--nest` sweep must never aim it at a box the run did not name.

**Exclusion is inferred, never hand-listed**, and `helpers/nest_surface.py` is where that lives. A test whose fixture closure reaches a nest-*binary* fixture wants the binary and is standalone-only by construction; the same closure shape carries the other ratified classes (`local_nest_fixture`, `unsupported_option`, `permanent_option`, `own_image`, `bridge_spawn`, `loopback_kind`, `private_peer`, `test_hooks`, `global_admin`, `venue_option`, `venue_host_affordance`, `feature_set_binary`, and the four below: `in_process_tier`, `absent_capability`, `one_live_box`, `harness_box`). The tally prints at the end of every non-standalone run, with `--strict-nest` as the `--strict-app` twin; its machine-readable twin `--nest-gates-json PATH` carries each excluded test's repo-relative id, the rule that excluded it and the feature slugs it witnesses, plus everything the run selected — the two halves the catalog's mode audit joins against the coverage contracts to answer *which pages* a class blanks ([`feature-catalog.md`](feature-catalog.md) § Cell semantics). `--collect-only` fills it, so the audit costs one collect and no container. **Its `--baseline` control is what makes the classifier's account of a mode falsifiable** rather than self-reported: every test a standalone collection selects that the mode neither selects nor gates was dropped with no ratified class at all, and that control has read **0 silently dropped** at every pass. Every hand-written table in the module — the fixture sets, the start-options map, the feature-set map — is pinned to the tree's own **AST by equality** rather than by a down-only ratchet, so a new fixture reds until someone classifies it; the first such pin earned itself immediately, hand-reading having produced 13 names where the AST found 20. Start options follow the same shape: each provider declares `supported_options` (standalone's pinned by equality to `_make_nest`'s own signature, since a set that derived itself could never tell you reality had moved; docker's the honest small set; live's empty and permanently so, a start option being a property of a nest the harness *starts*), the two refusals are one shared implementation reading off that declaration rather than two prose restatements that can drift from it, and **a falsy option is not a request** — the defaults are `False`/`None`, so a fixture spelling one out is asking for the default. A provider that grows an option un-excludes every fixture needing only what it now supports, with no table edit here; that promise has been measured rather than asserted at several arms. The one place a runtime refusal is the *only* possible answer is `extra_env`: the options table records that a fixture passes it, never which keys, so a value-level rule cannot be reached at collection at all — loud at setup is the whole of that contract, and a deliberate exception rather than a gap. `extra_env` itself is allowlisted and **added to** the provider's own wiring, never substituted for it, pinned disjoint from the port, NAT-mode seed and claim code, because an unrestricted one is a general-purpose entrypoint-env hatch reachable in one mode only — the configuration-file theatre [`principles.md`](../principles.md) § One configuration surface bans, arriving disguised as test convenience.

**The private-peer class is the one that had to exist before routing could start.** `RULE_PRIVATE_PEER` excludes, **in docker only**, a test whose reach READS the `peer_url` contract key off a handle, gated on a nest being in its closure so a headless pin that merely asserts on the key can never be reported as a private-range peer. The reach rides the same call graph the kind classes use, through a third selector: subscript **loads** only. That narrowing is load-bearing rather than tidy — the graph is keyed on the bare function name and the docker provider *writes* `{"peer_url": ...}` inside a method named `start`, so counting string constants attributed the key to almost the entire suite where counting loads attributes it to six functions. Live is untouched by construction: a live peer IS globally routable, which is the whole distinction the class draws. **Completeness has its own guard, because the classifier reads only one side.** A relay written against `url` is not merely unclassified but INVISIBLE — and a client this process dials itself is the same syntax — so no rule can separate them and a reviewed set does: the functions that feed a peer-authority field from `url` are pinned, each annotated with whose nest it is, and a new one reds with the question it has to answer. The class is pinned to the nest by **posture** rather than by a kind set, since it has none to pin to: a pin asserts `validate_peer_url` still carves out loopback *literals* only and still demands `resolve_global_addrs`, so a guard that widened to accept RFC1918 reds this instead of leaving the class excluding tests the product had started allowing. It was red-verified with a real dial — two containers of the published image on one run network, nest A asked over the wire to relay a public-folder fetch from nest B at B's own container IP, A's log refusing `federation peer URL resolves to a non-global address` — and **that measurement produced the finding that decides the class's shape: the refusal is invisible at the wire.** The client is told `fauna.folders.internal` with `details='federation fetch failed'` and nothing more, the cause existing only in the nest's own log, so a test allowed to run in docker and assert "this is refused" could not distinguish the SSRF posture from a broken network, a dead peer or a TLS fault, and would report a red of unknown cause. Excluding at COLLECTION with a named class is therefore not merely tidier than letting the test run; it is the only shape that yields a truthful report.

**Every sole blocker in the docker audit is now a FACT** — the property the accounting arm was for. Reaching it took two splits. `feature_set_binary` separates the tests that depend on a non-release feature set being compiled in, and the decisive question is not whether a fixture builds one (they all do — the image's set differs from every harness set, so the naive phrasing would dissolve the whole class rather than trim it) but whether the *test* depends on the difference; it is pinned by an AST equality over each fixture's own feature string — members and exempted non-members alike — plus a `Dockerfile` parse of the shipped set, so neither side can drift from what is actually built or actually shipped. And `permanent_option` splits the never-honourable start options out of `unsupported_option`, which left the report entirely. So the one MIXED class remaining is `nest_binary`, and it sole-blocks nothing: no catalog page is blanked solely by something that reads as closable work. What is left of it is a list of tests to route for their own coverage, never a list of cells being kept blank — and **every one of its consumers carries a pin-enforced disposition**: PREMISE (the locally-compiled binary is what the test is a witness OF, so routing would assert nothing) or OPEN (routable, simply not yet routed). The triage set is empty, which makes the pin stricter rather than idle: "triaged" means "needs a disposition and is not named in that set", so with nothing exempted the next file to take a binary fixture reds on the commit that adds it. The fact-vs-debt half is **derived, never recorded** — the pin re-runs the real classifier (`nest_surface.all_rules`) over each consumer's reconstructed closure and reads the verdict out of the audit's own `RULE_VERDICTS`, so no third copy of "which rules are FACT" exists to go stale, and no reader is asked for a judgement a computation can make. A test carrying `nest_binary` *and* a rule whose verdict is already FACT is not routable-but-unrouted: the FACT holds it out of docker whatever happens to its binary, so routing it frees no cell and would only turn a clean collection-time exclusion into a runtime ❌ against product code behaving exactly as ratified. The derivation's own failure mode is asserted directly rather than inferred from plausible-looking numbers: every consumer's reconstructed closure must still make the classifier name a binary rule, because a broken conftest walk would return no rules for anybody, intersect no FACT, and silently resurrect the whole population as apparent work. The instrument is an AST scan resolved through the **conftest chain**, not just the test module (the module-local-only form misses every caldav/mail/dav gate in the run), cross-checked once against a real `--nest docker` collect's own gate set as a strict superset and deliberately kept a superset because it is machine- and mode-independent: it grades every platform family's tests from whichever dev machine runs it, and answers identically on all of them, which no collect can.

**Six lessons from the build-out, kept because re-deriving them is expensive.** **(1) A census is a measurement, not a memory** — re-run the scan, never quote the last pass's number; every count this build-out recorded went stale within two passes, which is why the disposition pin holds its remainder exact *by filename* rather than as a total, and why a filename reds on the commit that adds it where a total would not. **(2) An option table answering "yes, this mode honours it" is not the same question as "yes, this test can run there"** — a cluster asking only for an honoured option was nonetheless unroutable because each test also spawned a host bridge inline in its own body, which a fixture-name-keyed rule cannot see; the honest first move there is to teach the classifier the inline spawn, then re-measure, because until then the `nest_binary` count is optimistic. **(3) Several classifier rules match by fixture NAME**, so a new fixture sharing a name with one elsewhere silently inherits that stranger's rule, with a fluent and entirely wrong reason — the hazard `nest_surface`'s docstring warns of, recorded again at the fixtures themselves because the warning lives in the file you are not reading when you write a new one. **(4) "Unused fixture parameter" is a reading, never a rule** — in one directory a `nest_binary` parameter nothing references is dead weight whose deletion is the whole routing; two directories away the identical syntax is deliberate and load-bearing, declaring a dependency a harness method hides inside its own `build_node()` call. Only reading the fixture body tells them apart, and a mechanical sweep would reopen the very hole the class exists to close. **(5) A textual pin cannot close a scheme class alone.** A pin holding hand-composed `http://127.0.0.1:{port}` at zero missed a helper carrying the scheme in a *parameter default*; against a container that sent `ws://` at the image's TLS listener, a connection dropped with no HTTP response **below any application logging** — so the nest's log stayed clean and the harness saw a bare `WebSocketConnectionClosedException` naming nothing. `common.auth.port_base_url` is the ONE place the port→scheme fact lives, and the pin that closed the class asks what each helper **returns** for a marked port rather than how it spells it, which is the check no spelling can fake. **(6) Read the code being called before triaging from the calling code.** Several families were triaged standalone-only on the strength of what their test bodies looked like — killing a process, poking SQLite, restarting a nest — when every one of those acts was already mode-agnostic by delegation. Relatedly, docker answers `db_path` / `blob_dir` / `tmp_dir` / `proc`: the capability-absence class bites on **live**, which answers none of them, not on docker, and reading it the other way would have left a routable family permanently classified.

**Android's run venue — A2, ruled by the user 2026-09-26: remote adb through a tunnel.** The per-machine app sets above name no machine for `android` because none can run it: the emulator needs hardware virtualization no dev VM exposes, so an android e2e run has never been recorded. Whatever venue is chosen must hold four constraints, which follow from the venue's security posture rather than from any one option: **(1)** the emulator host carries only the Android SDK emulator and platform-tools; **(2)** nothing unauthenticated listens on a network interface — adb-over-TCP to an emulator is an unauthenticated device shell, so a remote-adb venue tunnels it, and the tunnel is dialed from the more trusted machine toward the less trusted one, never the reverse; **(3)** the device reaches the test nest as its own loopback (`adb reverse`), with cleartext permitted to `127.0.0.1` in the debug source set only — production's no-cleartext network policy is never widened and no test nest binds a LAN address for the device's sake; **(4)** the run's records land in the feature ledger through a dev-VM session's commit, whichever machine produced them. The options weighed against these are remote adb in two shapes, sessions on the emulator host, a USB device, and a dispatch-only hosted runner with KVM. **The ruling (2026-09-26) is A2:** the emulator host gains only the Android SDK emulator + platform-tools; the driver runs adb as a pure client against the tunnelled server, and the venue's machine setup lives in the internal dev-setup notes; the bridge forward and android-mode test nests use fixed, pre-forwarded port ranges rather than `find_free_port()`, and — per the caveat below — the tunnel carries those nest ports so the device's `adb reverse` loopback on the emulator host reaches the nest on the dev VM. Hosted runner (D), USB (C) and sessions on the emulator host (B) were not chosen. **The three venue-independent pieces are BUILT (2026-09-20), and none of them is a run.** Constraint 3's debug network policy is `apps/fauna-android/app/src/debug/res/xml/network_security_config.xml`: cleartext to `127.0.0.1` and nothing else, in the `debug` source set and nothing else, with `base-config` left refusing. Its witness is a **source-set assertion over every shipping build type** — `release`, `storeSafe` and `foss`, derived from `build.gradle.kts` rather than listed — not the artifact grep that `android-store-safe-check` and `android-foss-check` use, and the difference is the mechanism rather than the rigor: those absences are R8 folding a constant-gated branch, where "should fold" is only a claim until an artifact is measured, while a build-type resource is not an input to another variant **by construction of the build graph**. What can actually rot is which directories each shipping variant reads, so that is what is measured, and a `srcDir` addition pulling a debug directory into a shipping type reds. The `adb reverse` leg runs per nest port in `tests/e2e-unified/drivers/android.py` — from the launch config's `url` plus any additional `nest_ports`, with `ensure_reverse` for a nest started after the app, and removal at teardown keyed on the **driver's own record of what it opened**, never on the forward's port (they are different mappings in opposite directions, and keying removal on the forward leaks every reverse onto the device). The device is named run-level by `--device-serial` / `E2E_DEVICE_SERIAL` (`tests/e2e-unified/helpers/android_device.py`), reaching the **availability probe as well as the driver**, so a box with both an emulator and a handset attached cannot probe one and drive the other, and `unauthorized`/`offline` is no longer read as present. All three are pinned by tier_1 tests against a fake `adb` on a private PATH, so they hold on machines that can neither build nor run android. **The A2 half of the harness is BUILT (2026-10-01), and it too is not a run.** *The run-level input* is `--adb-server` / `E2E_ADB_SERVER` (the same file, the `--device-serial` shape): adb's own socket spec, narrowed to `tcp:127.0.0.1:<port>`, reaching **every adb invocation as `-L <spec>`** through `adb_argv` — now genuinely the one home of the adb command prefix, which the availability probe and the driver both build from — and never as a process-level environment variable. The explicit host is mandatory and that is measured, not assumed: adb reads a bare `tcp:<port>` as a LOCAL server and starts one when nothing listens, while against `tcp:127.0.0.1:<dead port>` the client exits at once with "cannot start server on remote host" and spawns nothing (adb 37.0.0) — so a run whose tunnel is down finds no device and reports android **unavailable, never red**, instead of silently driving a fresh, empty local server. A non-loopback host is refused outright (constraint 2). *The fixed ports have one home*, `tests/e2e-unified/helpers/android_venue.py`: the dev VM's loopback listener for the tunnelled adb server (18509), the bridge-forward range (18510–18517, one per device seat) and the nest range (18600–18631), all below the ephemeral range `find_free_port()` draws from. The dev VM's adb listener is deliberately **not adb's default 5037**: any bare `adb` call there starts a local server on 5037, which would stop the tunnel binding and, with the tunnel up, hand the remote emulator to every sibling session's bare probe. With the input set, the driver's forward port is a **lease** on the bridge range and both nest providers (standalone and docker) take their port from a lease on the nest range through one seam, `android_venue.nest_port`; without it both are `find_free_port()` exactly as before. A lease is an exclusive kernel lock on a per-port file in a machine-wide directory, held for as long as the port is in use — cross-process because two e2e lanes can run android at once, and released by the kernel when its holder dies, so a killed run strands nothing. A nest started on a port of its own choosing is refused at the `adb reverse`, with the cause, rather than left to fail as a connection error naming nothing. *The tunnel command* is generated from the same constants by `just android-tunnel-spec`: one remote forward for the adb server and one per bridge port, one local forward per nest port, every one `127.0.0.1` at both ends, failing whole if any forward cannot bind. All of it is pinned by tier_1 tests (`test_android_venue.py`, and the venue cases of `test_android_device_serial.py` and `test_android_driver_adb.py`) with no emulator and no tunnel. **One caveat the venue ruling absorbs, rather than a venue-independence claim:** `adb reverse` maps the device's loopback to the machine running the adb **server**, which is not necessarily the machine driving pytest — so a venue that dials the tunnel from a second machine must put the test nest where the adb server runs, or the device's loopback reaches the wrong box. **Still not built:** any android e2e RUN at all — the first record through the venue, which waits on the install steps on the emulator host. A nest a test starts on a port it picked itself, outside the two providers, is not reachable from the device until that test takes its port from the same seam; the driver's refusal names each one as it is met.

## The three fidelity gaps (each tied to a live-only bug)

Live-only bugs to date cluster into exactly three gaps. Each names the property prod has that local tiers lack, and the tier that should hold it.

### Gap 1 — real-client wire quirks
Local mail tests authenticate and speak the protocol the way *our* Python helpers do, not the way real MUAs do. Real clients send idiosyncratic bytes our helpers never emit.

- **Canonical example:** Apple Calendar/Mail send a **domain-less bare local-part** (`test`) as the SASL/Basic-auth username, not the full address. Every local mail test authenticated with the full `test@example.com` (or the sub-addressed `test+cred@example.com`) form — all carry the domain — so the strict username parser's rejection of a bare local-part (the pre-fix `auth.SplitEmail`) shipped and only surfaced when a human pointed real Calendar.app at the box.
- **Target:** every mail-auth surface (IMAP, SMTP submission, CalDAV) is tested over the **matrix of username forms real apps send** — full address, bare local-part, RFC 5233 `+credential` sub-address — in `tier_3` (and `tier_4`), so a regression in any form fails locally. Higher fidelity still: a small **wire-trace corpus** captured from real Apple/Thunderbird account-setup + discovery, replayed against the MDA; and/or one suite driving a real headless client (`vdirsyncer`/`khal`, headless Thunderbird) that runs on a Linux dev machine without a Mac.

### Gap 2 — the real mail-flow perimeter
Local tests use controlled senders and mocked/loopback DNS, so the full inbound/outbound perimeter (greylisting, SPF/DKIM/DMARC/ARC, DANE/TLSA, per-IP caps, rate limiters, rspamd/clamd) is only partly exercised end-to-end.

- **Examples:** the CalDAV `REPORT`→`bridge_rate_limit` 401 — never tripped locally because no test reproduced a real MUA's request *burst*; greylist tempfail on first inbound; DANE/TLSA fetch behavior.
- **Target:** `tier_4`'s default shape is a **two-party mail loop** (nest-A ⇄ nest-B over the `fakes/fake_dns.py` UDP sidecar + `docker run --dns`) with the **full perimeter ENABLED** and run in **prod-parity config** — Encrypted mode, the SNI-router container in front, the PROXY-protocol path, greylisting + SPF/DKIM/DMARC + rspamd/clamd on. Much of the plumbing exists (`fakes/fake_dns.py`, the docker sidecars, `tests/platform/docker/test_mail_relay_two_nest.py`); the work is making the round-trip + prod-parity config the *default* tier_4 posture, not an opt-in subset.

### Gap 3 — irreducibly-live: real certs, real apps, real network
Real ACME certificates, real external senders (Gmail), real third-party clients on real OSes, and the real Hetzner network can only be had on a real box.

- **Examples:** the hyper `header_read_timeout` panic (only under real long-running TLS load), the SNI-router PROXY-protocol client-IP erasure (only the real `:443` topology), the refresh-loop log-disk-fill (only over real wall-clock).
- **Target:** an **ephemeral staging box** — a throwaway VPS (or local containers with an ACME-*staging* cert + a real test subdomain) that the `live_box`-marked tests target, spun up + torn down per run. `deploy-verify <host>` already generalizes to a second host. Staging is the live tier; **example.com (production) is never the automated-test target.**
  - **Realized (the provision→verify→teardown half):** `tests/e2e-unified/tests/live/test_hetzner_provision.py` (marker `live_provisioning`; `just e2e-live-provision`) provisions a **fresh real Hetzner VPS** through the actual app onboarding path (real `api.hetzner.cloud` — server + DNS on one token), waits for the nest to come up with a real ACME cert under a unique `e2e-<runid>.<zone>` subdomain, runs the deploy-verify gate set against it (health/build-commit, TLS trust, the run's own admin claim — `Online`'s last substep — followed by the wizard's UI tail to `LoggedIn`, mail-port banners, DKIM publish-match reusing the dev-fleet deploy-verify DKIM checker, and an external firewall scan replacing the SSH-only ufw inspection), and **always tears the box + DNS records down**. Doubly-gated (opt-in `FAUNA_E2E_LIVE=1` + `HETZNER_API_TOKEN`) so no default run provisions, and it never targets example.com (the shared-box rule below). **Still open:** retargeting the *destructive shared-nest* `live_box` suites onto a **persistent** managed staging box (a fresh-per-run provision is too slow for every `live_box` test) — that is what retires the shared-box disruption.
  - **Hetzner beta DNS ~30-min propagation — solved by reach-by-IP (current state).** Hetzner's beta Cloud DNS propagates an API-token RRset write to the authoritative nameservers in ~30 min (vs ~40 s for a web-console write of the same endpoint; method-independent, reported to Hetzner) — so nothing on the provision path may gate on fresh DNS. Both consumers therefore reach the box **by its captured static IP**, MITM-safe because the nest is identified by its keypair, not its domain (`../nest/domains-and-tls-bootstrap.md` § Goal) and channel binding fuses the cert to the nest identity regardless of hostname (`security.md` § Transport trust Axis 1). The connection keeps `https://{domain}` (SNI/`Host`/cert-identity intact — an IP-literal `nest_url` would trip the § Claim `!is_public_dns_name` local-target carve-out) and carries a **temporary DNS override** `domain -> <captured-ip>:443`: **(a)** the provisioning **Online poll** (`fauna-provisioning::orchestrator::run_all_steps` takes a `probe_for_ip` factory; `fauna-onboarding-machine::local_nest_probe_client_resolving`) — provisioning succeeds in ~5 min DNS-independently, the 480 s budget is a fallback; **(b)** the **production wizard's own admin-client connection** (`fauna-anon-client::AnonymousNestClient::connect_resolving`; `WsNestApi`'s shared `resolve_override`, written by `stash_provisioning_result`, cleared on `reset()`), live-validated 2026-07-06 on a real box via the real `wizard_submit_claim_code` bridge arm — and since 2026-08-29 the claim is the run's own `Online` substep (`../behavior/onboarding.md` § 6 *Provisioning = build + claim*), so the e2e drives no claim of its own: it walks the wizard's tail through the UI (`helpers/live_provision.py::finish_provisioned_wizard`), and a second submission of the code would be refused `already_claimed`. The claim carries **`mail_domain`** (the handle's `@domain`; else the box stays identity-less at `localhost` and ACME never issues — `claim_core.rs` registers the primary domain from the claim, not the reach address); the e2e enables mail post-claim, and only the **real-ACME-cert TLS-trust gate** still absorbs the ~30-min DNS wait (inherent to verifying a real cert; 40-min budget). **Remaining:** deployment-seed injection at provision to close the first-contact TOFU window (intersects `../nest/box-recovery.md`; coordination-gated, tracked internally). *History: 2026-07-04 finding (the "nest never served :443" premise was a misdiagnosis — the box was healthy on its IP the whole time) → stopgap (Online budget 180→480 + e2e gate reorder for domainless boot) → orchestrator reach-by-IP → wizard reach-by-IP, live-validated 2026-07-06.* **Target (ratified 2026-08-29):** the reach-by-IP override is native-only, and on web the wall was never DNS but TLS (a domainless box has no trusted cert a browser will accept) — so the reach address generalizes to all 7 apps via the nest's IP bridge cert (`../nest/tls-certificates.md` § B-IP), the wizard claims the box itself as Online's last substep, and the address outlives the wizard as the account's reach hint; owner `../../behavior/onboarding.md` § 6 / § Reach hint.
  - **Debugging a failed live box (SSH inspection — debug-only, NEVER committed).** A provisioned box carries no ssh key (the no-SSH product invariant); the temporary debug-key recipe (a persistent Hetzner key + an env-gated, **uncommitted** patch to `hetzner.rs` `create_server`) is operational procedure, not target state — it lives in the internal dev-setup notes. The invariant half stays here: **revert the patch before any merge** — an env-gated ssh backdoor still violates the no-operator invariant; after any `FAUNA_E2E_KEEP` run, manually delete the `e2e-*` server + clear its `e2e-<runid>` DNS rrsets.

## The shared-box rule (coordination, not a tier)

Automated live tests and human/manual testing **must not share one box**. The `live_box` flock (`tests/e2e-unified/helpers/live_box_lock.py`) serializes automated-vs-automated runs on one machine, but a human's manual session is not a flock participant — so a `live_box` test that factory-resets the box (e.g. the CalDAV TRACK-A 3-client test) silently yanks state out from under a human mid-session (observed 2026-06-04: repeated ~15-min factory resets disconnected a human's app and rotated the mail credential under them). **Automated `live_box` tests target the staging boxes (Gap 3) — user ruling 2026-10-04: `dev.example.com` from every dev machine, `test.example.com` (created after the public flip) from CI; example.com is never a test target any more, for humans + final hand-proof only.** The destructive-suite rule stands for any box a human also uses: **destructive `live_box` suites are never run unattended against it** — a human present at (and aware of) the run is the only guard the flock cannot provide; the flock alone is not clearance.

**Non-destructive carve-out (ratified 2026-07-22, with the user-directed live AP suite).** A `live_box` test that is **non-destructive** — no factory reset, no credential or storage-mode mutation, no deletion or modification of any pre-existing data, and a teardown that removes every artifact the run itself created — may target example.com, unattended, under the flock. The destructive/non-destructive line is the *human's experience of the box*: a run the human could sit through signed-in without noticing more than a transient test artifact is non-destructive; anything that logs them out, rotates a credential, or resets state is not. Each such test's docstring must state its blast-radius argument explicitly (what it mutates, why that is invisible to the human, and what teardown removes) — an undocumented mutation is a rule violation, not an oversight. First resident: the live ActivityPub serving-surface test (enable → assert → unlink; the AP instance-actor rotation hazard in `../../behavior/activitypub.md` § Architecture is *why* it must never factory-reset). Second resident: the live-box bootstrap (`tests/e2e-unified/tests/test_live_box_bootstrap.py`, `just e2e-live-bootstrap`, user ruling 2026-09-26) — on an already-claimed box it only signs in and mutates nothing; on an **unclaimed** box its claim, NAT-mode choice, mail credential and bridge approvals are the deployment's first-admin setup, the box's intended durable state, so it deliberately has no teardown (no human exists on an unclaimed box to notice).

**The disposable-box declaration (2026-10-04).** Exclusion class (3) is this rule's mechanism in `--nest live`: it deselects every global-admin-mutating test because a human may be signed into the box. The CD gate (`just e2e-cd-gate`, [`build-system.md`](build-system.md) § Image tags & channels) runs against a box the pipeline wipes by design, and there the policy protects nobody and deselects the gate's own factory-resetting residents — invisibly, since a deselect is not a skip and `--fail-on-skip` never sees it (measured against the staging box 2026-10-04: `test_believable_live_mail_roundtrip` and `test_live_mail_receive_ui_only` both read `global_admin` under `--collect-only`, and the gate would have passed green having run neither). **The box is disposable, not the test, so the RUN declares it**: `--live-box shared|disposable`, a run-level input beside `--nest live:URL`, default `shared`, and `disposable` is **refused** unless the mode is live and the box it resolves to (the provider's own precedence: `:URL` > `FAUNA_LIVE_NEST_URL` > the project's live box) is one of the staging boxes this rule names — `nest_mode.DISPOSABLE_BOX_HOSTS`, `dev.example.com` and `test.example.com`, pinned to the image workflows' `VERIFY_HOST` so the box the pipeline verifies on is always one the gate can declare; example.com is refused by construction, so a `cd_suite` run pointed at it still deselects. On a declared run class (3) is off through every door (the marker, the fixture list, both kind scans, both admin-shell scans) and **nothing structural moves**: a local binary, a host-spawned bridge or a test hook excludes from live by a fact about where the nest runs, and the box being disposable changes none of them. **Two shapes were weighed and rejected.** A `cd_suite` marker re-admission (the `live_ok` shape) puts the box's property on the test, and a `cd_suite` test run through `just e2e-live-mode-test` against the production box would then factory-reset it. A per-box table that made the staging box *always* disposable would turn every ordinary sweep against it destructive — the 2026-10-04 tui sweep that rotated the staging box's keys was exactly a run nobody meant to be destructive, and the box's admin dogfoods it between gate runs. The flag has deliberately **no env equivalent**: a declaration that makes a run destructive sits in the invocation someone reads, never in an ambient export a later shell inherits. The recipe is the fourth load-bearing part of the gate invocation; `test_cd_gate_completeness.py` pins that it carries the declaration and that both residents are selected under it and deselected without it, and `test_nest_mode_axis.py` pins the grammar, the three refusals and that only class (3) moves.

**A resolved seed is ambient, so it is never a destructive test's opt-in (2026-10-05).** Every `live_box` module resolves its admin seed per box (`helpers/live_box_door.admin_seed`, over `multiseat_config.resolve_secret`), so a staging box this fleet provisioned runs with nothing exported. Before that, an exported `FAUNA_LIVE_SECRET_HEX` was doubling as the "yes, run this" switch of the factory-resetting modules, and resolving their seed silently would have made them runnable on any run that found one. **A destructive module therefore gates on the run's disposable-box declaration** (`live_box_door.destructive_live_box`, the mechanism above) — it skips on every run that did not declare its box disposable, the standalone `FAUNA_E2E_LIVE=1` run included — **and drives the declared box itself** (`nest_mode.live_url`), so an exported `FAUNA_LIVE_NEST_URL` naming another box can never be the one it resets. A non-destructive module (the carve-out above, or a re-issue whose own opt-in is not the seed) adopts the resolved seed and keeps the `live_box` opt-in as its only gate. `tests/e2e-unified/tests/test_live_seed_resolution.py` classifies every `live_box` module naming the seed variable, refuses a raw env read of it, and evaluates each module's gate under a temp-HOME staging-box file: the non-destructive ones runnable, the destructive ones skipped on a shared run and runnable only on a declared one. **The mailbox and the box are resolved the same way (2026-10-05).** A destructive mail module's mailbox comes from `live_box_door.mailbox` (over `multiseat_config.resolve_mailbox`): `FAUNA_LIVE_MAIL_ADDRESS` / `FAUNA_LIVE_MAIL_PASSWORD`, each overriding its own field, > the box's staging-box file `handle` / `mail_password` — the identity it was provisioned under, which is what a factory-resetting module re-claims as — > for the password alone, one derived from the box's resolved admin seed (`derived_mail_password`), because the provisioning test nulls a password it did not choose and the resetting modules choose one at re-enable, so every module of a run, port 25's IMAP read-back included, computes the same value with no state written. A non-destructive module's box is the `--nest live` run's own (`live_box_door.live_box_url`; `FAUNA_LIVE_NEST_URL` outside a live run). So `just e2e-cd-gate https://dev.example.com` runs with nothing exported, and the same tier_1 file pins the mailbox and URL resolution beside the seed's.

**Derive what the box knows; env is an override, never a precondition (ratified 2026-08-16, user-directed — *"this detail needs to be a part of the test"*).** A `live_box` test may require only the two things no box can tell it: **where** it is (`FAUNA_LIVE_NEST_URL`) and **who** it is (the admin seed — resolved per box like live mode's, § Default app and nest mode → *Live mode*, with `FAUNA_LIVE_SECRET_HEX` its override). Anything the nest can answer for that identity — first among them the account's **handle** — is derived in-test from the secret, and its env var survives only as an override. The rule exists because the alternative is *not* merely inconvenient: a value that lives in no artifact in the repo or on any dev machine turns every "run this against the live box" ask into a `NEEDS FROM USER:` stall, and the substitute a test reaches for instead is a **guess** — the example handle from its own docstring, shipped as a default — which fails silently where a demand would at least stop. Both shapes were live until 2026-08-16, and the demand alone blocked the AP journey after that day's example.com release with the binary built, the secret located, and the box verified clean. **The mechanism is the wizard's own** (`tests/e2e-unified/helpers/live_handle.py`): the handle check runs a key-based silent challenge, `AlreadyOnNest` returns the registered handle, and the machine signs in as *that* rather than as what was typed — so what a test types is a routing input (the `@domain` half drives discovery), never an identity claim. Two states are refused rather than guessed, because each would otherwise fabricate a handle and assert against it: a **handle-less account** (the machine substitutes the typed handle, so a probe returns looking real) and an **unregistered identity** (the wizard routes to claim/invite — claiming a live box under a probe handle is damage no teardown reaches). **Ordering follows from it:** a test whose preconditions need the handle runs its handle-*independent* checks first, then signs in to learn the handle, then the rest — legal precisely because sign-in mutates nothing, which is the carve-out's own standard. Where derivation genuinely cannot apply — a test that factory-resets and **re-claims** (post-reset the handle is one it chooses, not one the box can report), or one that never signs in at all — the module says so in a declared, ratchet-enforced classification rather than leaving the next session to rediscover it.

## What the tree may assert about testing (ratified 2026-08-24, user-directed)

A document in this repository may state what tests **exist in it**. It may not state what testing **has happened**. Artifacts reach people the tree never observes — users build, install and exercise them on platforms and in configurations no maintainer sees, and nothing reports that back — so "never tested on x64" is not a cautious admission. It is a claim the tree has no standing to make, and it is *uncorrectable*: it goes stale the moment someone does test it, silently, with no mechanism that would ever revise it. That is the failure this section exists to prevent — an assertion no reader and no gate can check, decaying in place.

1. **Never write that something has not been tested, has never run, or is never exercised.**
2. **Prefer the positive statement of what exists** — "x64 install/uninstall is covered by the smoke in `release.yml`" names a file the reader can open, and stays true.
3. **What this project has *released* IS knowable, and licenses a real inference.** You cannot test what was never built, and you cannot install what was never released: "the Play record holds no release, so there is no installed base" is sound, because the release channel is ours to know. ⚠ **Built and released come apart once the source is public** — anyone may build — so anchor such a claim to the release channel, never to the build.
4. **Where a gap must be signalled and is not a release-channel fact, make it a claim about our records, not about the world:** "no test report is filed for the ARM64 runtime install." Absence of a report is not knowledge of absence of testing. **Otherwise: silence.** A document that does not need to assert a testing gap should not assert one.

The line against a doc's own `## Implementation status today`: that section describes **the code**, which the tree can read, and it stays. Testing claims describe **the world**, which the tree cannot read, and they go.

**The one record that may say what happened: a run-written ledger (ratified 2026-08-26).** A claim that decays in place is banned because nothing revises it; a record that is **first-party** (written by the run that observed the outcome, on the commit and against the artifact it names) and **revisable** (the next run overwrites it) is rule 4's "claim about our records", in the same class as `pinned-previous-build.toml`. The feature catalog's per-app ledger is that record, and the only form in which "this was witnessed" may appear in the tree — a cell with no ledger entry renders empty, never "untested". Owner: [`feature-catalog.md`](feature-catalog.md) § The ledger.
