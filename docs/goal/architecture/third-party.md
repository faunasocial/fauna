> **Audience:** every area — the nest, all 7 apps, and anyone writing code that runs on or beside a nest.
> **Purpose:** the destination. One object (the Client ID Metadata Document) and one nest-side identity (the principal) serve every arm of third-party integration: remote servers, device apps, same-device apps, and code hosted on or beside the nest. **Tokens authorize transport; grants carry keys; identity-bearing acts go through the oracle.** No third-party code ever holds a user's identity key.

## Goal

A third party integrates with Fauna through exactly one door: an HTTPS-hosted **Client ID Metadata Document** that is its self-authenticating identity, extended — for code the nest hosts — with Fauna members that a standard consumer ignores. Every approved document mints one **third-party principal** on the user's nest: an X25519 holder, its declared kinds, its granted scopes, one roster row. What a principal may reach is decided by three layers that never collapse into one: an access token from the nest's own issuer (transport authority), a user-minted capability grant (key authority), and a typed, scoped, audited, instantly revocable **oracle** for the operations that need an identity key. Hosted code is **headless**, runs as a WASM component or a curated-catalog container, and is supervised, keyed and proxied by the nest. Revocation is one verb: delete the row.

## Implementation status today

**The principal row is the one mechanism here that is built** (the first bullet). What else exists today, and what each ruling generalizes:

- **Built 2026-09-26 — the principal row (TP1, § The principal model), for consent-minted `remote`/`device` principals.** `third_party_principals` holds the ratified shape, one row per `(account, client_id)`, found-or-created by the consent-backed redemption at the nest's `/oauth/token` — the code grant and both polled grants (the typed code and the quiet push), through one owner — **in the same transaction** as the grant row and its session family (`bins/fauna-nest/src/db/third_party_principals.rs::upsert_principal_in_tx`, called from `record_atproto_oauth_grant`), so a grant never lands without its principal and a refused principal rolls its grant back. A second ceremony for the same document finds the row: `last_used_at` and `granted_scopes` take that ceremony's values, `label` keeps the resolved name the first card showed, and the new grant family joins the ones already there, since each ceremony mints its own. **Execution form** is derived from how the client authenticates, read off its own document (rule 3): a confidential `private_key_jwt` client is `remote`, a public one `device`; `wasm` is the install leg's (below), `container` waits for the supervisor. A consent-minted row's `declared_kinds` and `publisher_key` are what the consented document's verified kind manifest said (since 2026-10-02, S8a — the nest's resolver refuses a document whose `fauna` member does not verify against its host; [`third-party-kinds.md`](third-party-kinds.md) § The manifest). **The holder-key attestation (rule 2) is a start parameter, `fauna_holder_x25519`** — at PAR, and at `/oauth/device_authorization` and `/oauth/bc-authorize` for the two polled starts (unpadded base64url, exactly 32 bytes; malformed → `invalid_request` at the start). It is chosen here because no owner doc names a carriage. It rides the DPoP-proven start, so it reaches the row only through a code or polled handle redeemed by the same DPoP key. That is **binding, not proof of possession**: X25519 cannot sign, so a client could attest a public key it does not hold. Two refusals keep that from reaching anyone else's grants: a key another of the account's principals holds, and a key an enrolled bridge or content processor holds (the web-serve holder, a mail bridge), each refused at `/oauth/token` as `invalid_grant` with nothing recorded. A standard client presents no key, and its row mints with `holder_x25519` NULL. A later ceremony presenting no key leaves the row's key alone. A ceremony presenting a *different* key replaces it and ends, in the same transaction, the capability grants the account had minted to the old one, which no roster row would name any more. **Its twin, the writer key `fauna_writer_ed25519`, is built the same way since 2026-10-02 (S8a)** — same starts and carriage, the row's `writer_ed25519` and `PrincipalInfo.writer_ed25519`; its refusals and its replace rule are [`third-party-kinds.md`](third-party-kinds.md) § Principal write authority's. **The roster read and the one verb are built** as the USER-class, self-scoped `fauna.principals.list` (each row also carries `live_grants`, the count of its live grant families, so a principal a forced rotation or a per-grant revoke left with no working connection shows as such) and `fauna.principals.revoke`. The revoke deletes the row and, in one transaction, ends every unrevoked grant family for `(account, client_id)` through the same session+grant row pair every revocation writes, and deletes every capability grant the account minted to the principal's key. Proven tier_1 (the table's cascade and refusal arms) and tier_3 (`tests/e2e-unified/tests/api/test_third_party_principals.py`, a full browser-start ceremony against the real PDS bridge). A principal calls `fauna.capabilities.fetch` itself since 2026-10-02, over its own session ([`transport-connection.md`](transport-connection.md) § Connection lifecycle → *The principal session*; `test_third_party_session.py`); the roster test above still asserts the revoke's capability arm owner-side, through `fauna.capabilities.reconcile`, independently of the consent-time grant a `records` consent mints (pinned principal-side by `test_ext_kinds.py`). **Built 2026-10-03 — the principal as a trust-facet participant (rule 5's fold) and the revoke's log entries.** `fauna_client_capabilities::view_model::{principal_trust_facet, principal_history}` fold the owner's grant log over the principal's one-key holder set, keeping only third-party grants (rule 4's one predicate, `is_principal_scope`: an `ext.*` kind, the `deposit` tuple or the `content.read{folder}` read twin — the twin and deposit admitted 2026-10-05 — so a roster naming another holder's key reaches nothing else); the connected-apps machine reads the row's *lasts-until* from that facet (§ The roster model) wherever the consent-grant seams wire the grant log (tui, linux, macos and ios today). When `fauna.principals.revoke` lands, that machine records a signed `Revoke` for each grant the log still holds live for the principal's key (`grant_log::record_principal_revoke`), so the history lens can say why they vanished. **Built 2026-10-05 — the owner's end of a key replacement (§ The principal model → *Key replacement*).** `fauna_client_capabilities::view_model::{replaced_key, grants_ended_by_key_replacement}` decide what an approve replaces of the roster's keys and select, from the owner's log, the third-party grants that replacement ends — a replaced holder's every one, a replaced writer's the ones whose `content.write` tuple names the old writer. ## The shape in one page

Four arms — a remote **server**, a **device** app over the network, a same-device app talking to the **local Fauna app**, and code **on or beside the nest** (plugins, bridges). One object serves all four:

| Layer | What it is | Same for every arm? |
|---|---|---|
| **Identity** | the Client ID Metadata Document at an HTTPS URL ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § As built → *Client metadata resolution*) | yes — hosted code adds extension members (§ The manifest), standard consumers ignore them |
| **Principal** | one roster row per approved document (§ The principal model) | yes |
| **Consent** | two legs beneath one card: user-agent or install approval ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Consent) | the leg differs; the card and the row do not |
| **Transport authority** | a DPoP-bound access token from the one issuer, scoped, short-lived | yes |
| **Key authority** | a user-minted capability grant to the principal's key ([`encryption-at-rest.md`](encryption-at-rest.md) § Capability tiering) | the *set of grantable scopes* differs by arm (TP4) |
| **Identity-bearing acts** | the oracle ([`key-material-hierarchy.md`](key-material-hierarchy.md) § Audience: deployment infrastructure → *The oracle*) | yes |
| **What it can touch** | `ext.*` records, folder deposit and read, events, posting through the oracle's `post.author` class and following through `fauna:follow:write`, the feed and personalization planes, conversations via the room model | yes, scoped by grants |
| **Execution** | remote, device, WASM component, curated container (§ Execution forms) | the form differs; the contract does not |

Two invariants every section preserves: **the nest never holds a user key** ([`../principles.md`](../principles.md) § The user always controls their data), and **the only configuration surface is the apps** (§ One configuration surface) — every choice below is a hard-coded Rust constant, artifact-set IPC, or an app-UI-backed nest-state row.

## The principal model

A **third-party principal** is the nest-side identity of one approved metadata document for one account:

```
principal_id, client_id (the document URL), holder_x25519, writer_ed25519?,
execution_form ∈ { remote, device, wasm, container },
declared_kinds, declared_service_auth, granted_scopes, created_at, last_used_at, label, publisher_key?
```

`writer_ed25519` (ruled 2026-10-02) is the principal's second attested key — the Ed25519 key it signs the rows it authors with, attested beside the holder key under the same rules ([`third-party-kinds.md`](third-party-kinds.md) § Principal write authority); a principal that attested none is read-only over its kinds.

`declared_service_auth` (ruled 2026-10-02) is the manifest's `service_auth` member as consented (§ The manifest) — the set the oracle's `atproto.service_auth` class is bounded by, `[]` for a document that declares none.

It is the generalization of the three rosters that exist today with the same shape (§ Implementation status today) into one, and of the two grantee identities that exist today into one that a **user** can create.

**Rules.**

1. **A principal is minted only by a consent act on the user's own authenticated app** ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Consent). There is no registrar, no dynamic-registration endpoint, and no admin-side principal creation for user-scoped principals. A nest-hosted plugin is minted by the *admin's* install approval (§ The runner contract) and then bound to each consenting user by that user's own consent — **install ≠ grant**.
2. **The holder key is the principal's**, generated by the principal, attested at consent; the nest stores the public half. A remote or device principal's key is the key it fetches grants with (`fauna.capabilities.fetch`); a hosted principal's key is minted inside its sandbox and never leaves it.
3. **The principal's caller class is a row attribute** derived from its execution form and its approved scopes, never from anything the process claims about itself — the same rule that gives a bridge its role from enrollment rather than argv ([`apps/bridges.md`](apps/bridges.md) § Concept). Reach is data under a compiled ceiling: [`apps/bridges.md`](apps/bridges.md) § Capability-allowlist enforcement → *`ThirdParty`*.
4. **Revocation is one verb: delete the roster row.** That kills the grant family, stops future epochs' key delivery, invalidates the oracle capability, and — for a hosted principal — stops the runner. **What the owner's log counts as the principal's grants (ruled 2026-10-05): every current grant to its holder key whose scope a consent mints — an `ext.*` kind, the `deposit` tuple, or the `content.read{folder}` read twin — one predicate (`view_model::is_principal_scope`) behind the trust facet, the history lens, the `Revoke`s the revoking app records (`grants_ended_by_principal_revoke`) and the key-replacement end's selector; the nest's end is by holder key alone, so the predicate is the log's guard against a roster row naming some other holder's key, and the nest's `refuse_foreign_holder` keeps such a row from existing.** What a remote principal already fetched is bounded by TP4 ([`encryption-at-rest.md`](encryption-at-rest.md) § Capability tiering → *Third-party holders*). A conversation bridge's rooms are the user's and outlive the verb — disconnected, read-only, adopted by the next principal declaring the bridge id; its undrained outbox ends with it ([`apps/bridges.md`](apps/bridges.md) § Bridge-kind catalogue → Phase G → *When the bridge stops serving*). Suspension without deletion is the account's external-apps switch, which pauses every principal of the account at once ([`../behavior/atproto-pds-full.md`](../behavior/atproto-pds-full.md) § Detailed design → F1 detail, the kill-switch bullet).
5. **Every principal is visible in the participants model** ([`../behavior/participants.md`](../behavior/participants.md) § The participant model → *Third-party principal*), so the trust and delegation facets the user already has for devices and nests cover it. Two vocabularies are deliberate: a principal is a **participant** in the trust model and may be a **member** of a conversation room ([`../ui/conversations.md`](../ui/conversations.md)).

**Key replacement — the owner's log records the end at the approve (ruled 2026-10-03; built 2026-10-05, § Implementation status today).** A later ceremony for a `client_id` the account already holds a row for may attest a *different* holder key, or a different writer key. The nest replaces the row's key at `/oauth/token` and, in the same transaction, ends the grants the old key reached — every third-party grant the account minted to the old holder; for a replaced writer, every third-party grant to the holder whose `content.write` tuple names the old writer (`upsert_principal_in_tx`, § Implementation status today; [`third-party-kinds.md`](third-party-kinds.md) § Principal write authority). That end is the nest's guard over reach no roster row names any more, and it stays. **The signed log's record of it is the OWNER'S act, the approve.** When the user approves a consent whose attested key (`NestConsentRow.holder_x25519` / `writer_ed25519`) differs from the key the roster currently names for the same `client_id` (the connected-apps machine's last roster read), the approving app — once the resolve has answered live, so a failed approve ends nothing — ends those same grants itself, nest first (`fauna.capabilities.revoke` per grant id, the narrowing direction) and then as signed `Revoke`s in the owner's log (`grant_log::record_revokes`; the holder selector is `view_model::grants_ended_by_principal_revoke`, the writer selector its `content.write` sibling): exactly the pattern the roster's revoke verb records by (`record_principal_revoke`). **Why this and not its two rivals.** Recording on an *observed* key change — the roster read says the holder moved — would make a nest-reported fact the trigger of a signed `Revoke` the owner never performed: nest-influenced content in the signed log, the channel the audit rule closes ([`../ui/nests.md`](../ui/nests.md) § Trust facet — grants → *Reconcile*; `grant_log::unrecognized_grant_ids`, property 1), and a lying roster could write "revoked" history over a live grant. Never recording, and showing a "no longer held" state derived from the reconcile answer instead, would feed a nest read into the audit view, which that ruling makes unrepresentable by design. Recording at the approve is admissible on the trust polarity the reconcile sweep itself rests on: the trigger is the owner's own act on a card they read; the new key is the attested key that approve already mints a fresh grant to (a nest lying about it already gains a grant to a key of its choosing — the binding-not-proof posture, accepted above); and the old key is the roster's reading used only as a *selector over the owner's own log*, confined to `ext.*` grants, as the roster revoke has used it since 2026-10-03 — a lying roster buys at most the ending of another principal's third-party grants, a narrowing the nest could effect by deleting rows anyway. Zero new power to a lying nest. **Two consequences are accepted, not open.** An app that abandons its own ceremony after the owner approved it has its old key's reach ended all the same: the owner approved the app under the key it declared, an app that never redeems is cut off until it completes a ceremony (the fail-safe direction), and in the honest case the owner's end and the nest's are seconds apart. And the log may still lag the nest in the narrowing direction — an approving app whose consent-grant seams are not wired, a crash between the resolve and the record — until the grant's window lapses; nothing derived from a nest read is ever shown in its place. The card says what the approve ends when the key differs, in the scopes-in-words block it already renders ([`../ui/connected-apps.md`](../ui/connected-apps.md) § User actions; a new element is rule A's question).

**Hosted principals — how an install fits a table keyed per `(account, client_id)` (ruled 2026-10-02; refutable until the first plugin is installed).** The row above is one account's; an install is the nest's act and no account's. So a hosted plugin has **one install row and N binding rows**, all sharing the document's `client_id` and the plugin's one holder key. The **install row** is minted by the admin's approval under the reserved **nest owner** — the all-zero actor id (`bins/fauna-nest/src/db/third_party_principals.rs::NEST_OWNER_ACTOR`), the placeholder every nest-side-not-an-account slot already uses; no account has it, so the row sits in nobody's roster and is reached only by the admin's `fauna.plugins.{install,list,uninstall}` kinds (Admin class, surfaced on the Bridges page, [`../behavior/bridges.md`](../behavior/bridges.md) § Bridge settings). It carries `execution_form = wasm`, the manifest's `publisher_key` and `declared_kinds`, and `granted_scopes` = the scopes the document declares and the admin approved it may ask each user for — a ceiling, since the install grants nothing (rule 1); its hosted half (`hosted_plugins`: the pinned module digest, the declared hosts, ingress, the settings schema, who installed it and when) and its state scope (`plugin_state`) are the runner's. A **binding row** is an ordinary row of one account, minted by that user's own consent to the plugin's document through the one find-or-create every consent runs (`upsert_principal_in_tx`), which recognizes an installed document and copies the install's form and holder key onto the binding (a hosted plugin attests nothing at a start it never makes), while the consent decides the scopes and mints the grant exactly as for a remote principal; it is the user's roster row, revoked by the user's one verb, which ends that account's grants and leaves the plugin running for everyone else. **The holder key is one per plugin, minted by the host at install** (`fauna_plugin_host::HolderKey`): the public half is every row's `holder_x25519` (the per-account uniqueness index is untouched — one key may bind many accounts, never two documents of one account), the secret rests beside the module in the data directory (`plugins/<principal_id>/holder.key`, mode 0600 — the host side of the sandbox's state scope, never a column the plugin's `state` import could read), and the plugin reaches it only through `holder.public-key` and `holder.open-grant` (§ Execution forms → *WASM components*). **Uninstall is the admin's one verb**: one transaction ends every binding row through the same cascade `fauna.principals.revoke` runs — its grant families, the capability grants that account minted to the plugin's key — then deletes the state scope, the hosted half and the install row; the runner is stopped after the commit (`uninstall_hosted_plugin`). **A user binds from the plugin's settings card** (TP2, TP9's first-contact-is-user-initiated): *Connect* opens a pending consent row assigned to the caller over the install row's ceiling scopes through the one shared opener, and the card the user already knows — the plugin's resolved name, publisher and execution-form badge, the scopes in words — approves into the binding row and the grant; a hosted plugin never starts a consent itself, since it holds no client credentials and makes no PAR. The binding mint, that start and its card are owed (§ Implementation status today).

## The manifest — extension members of the metadata document

The document is standard OAuth client metadata plus one namespaced member the nest reads and every other consumer ignores. **On the wire the `fauna` member is a string — a compact JWS whose payload is the object below** ([`third-party-kinds.md`](third-party-kinds.md) § The manifest owns the bytes: `EdDSA` only, `did:key` only, no canonicalization); the object is shown decoded:

```json
{
  "client_id": "https://bridge.example/fauna-client.json",
  "client_name": "Matrix bridge",
  "redirect_uris": [],
  "grant_types": ["urn:openid:params:grant-type:ciba"],
  "token_endpoint_auth_method": "private_key_jwt",
  "jwks_uri": "https://bridge.example/jwks.json",
  "scope": "fauna:records:rw:ext.bridge.example.* fauna:conversations:bridge fauna:identity:op:nostr.sign_event",
  "fauna": "<compact JWS, EdDSA, kid = did:key:z6Mk…, payload = the object below>"
}
```

```json
{
    "version": 1,
    "publisher": { "domain": "bridge.example", "key": "did:key:z6Mk…" },
    "execution": { "form": "container", "image": "ghcr.io/faunasocial/plugins/matrix@sha256:…" },
    "kinds": [ { "kind": "ext.bridge.example.room", "class": "state", "merge": "latest-wins", "floor": "none" } ],
    "settings_schema": { "…": "the BridgeProvider settings vocabulary" },
    "service_auth": [ { "aud": "did:web:api.bsky.app", "lxm": ["app.bsky.feed.getFeedSkeleton"] } ],
    "bridge": {
      "id": "matrix", "glyph": "bridge",
      "address_grammar": "^@[^:]+:.+$",
      "capabilities": { "supports_attachments": true, "supports_markdown": false, "supports_reactions": true, "supports_message_delete": true, "supports_per_message_reply": true, "supports_membership_change": true, "supports_recipient_selection": false, "supports_rename": true, "supports_subject": false, "delivery_mode": "Async" }
    },
    "ingress": [ { "path": "/matrix/", "sni": null } ],
    "events_uri": null
}
```

**Rules.**

- **The `fauna` object is signed by `publisher.key`**, whose control of `publisher.domain` is proven the same way the document URL proves the client identity (same-origin). The `kinds` member **is** the signed kind-manifest [`third-party-kinds.md`](third-party-kinds.md) § Kind namespacing + third-party kinds requires — one signature covers both the OAuth identity and the kind semantics, so a kind's publisher and a principal's publisher cannot disagree (TP7's mechanism is that doc's). The signature's carriage, key encoding and algorithm, and the closed vocabulary of each `kinds` entry, are that doc's § The manifest and § The kinds vocabulary (ruled 2026-10-02).
- **A document whose `fauna.execution.form` is `container` is admitted only through the catalog** (§ Curated containers), which pins the digest; a document naming an image outside the catalog refuses at resolution. **The `wasm` form's `execution` member (ruled 2026-10-02, refutable until the first plugin is installed) is `{ "form": "wasm", "module": "<https URL of the component>", "digest": "sha256:<hex>", "hosts": ["api.example.com", …] }`:** `module` is fetched through the one guarded fetcher at install, capped at `fauna_plugin_host::PLUGIN_MODULE_MAX_BYTES`, and refused unless its SHA-256 equals `digest` — the publisher's signature over the manifest thus pins the exact bytes the nest runs, and an update is a new document with a new digest, re-approved; `hosts` is the plugin's **whole outbound surface** — the hosts its `http.fetch` import may reach, host-equal and lowercase under the same rule the kind grammar applies to a publisher, `https` only, never an IP literal — and a document that declares none reaches nothing. There is no member for ambient reach, because there is none to declare.
- **`settings_schema` is the existing `BridgeProvider` settings vocabulary** rendered by all seven apps ([`../behavior/bridges.md`](../behavior/bridges.md) § Bridge settings) — under TP2 this is a plugin's whole user-facing settings surface.
- **`service_auth` (ruled 2026-10-02; refutable until the first manifest declaring it is consented) is the declared set the oracle's `atproto.service_auth` class is bounded by** ([`key-material-hierarchy.md`](key-material-hierarchy.md) § Audience: deployment infrastructure → *The oracle*, the table row and *The bridge-held custodian*): a list of entries `{ "aud": "<service DID, optionally #fragment>", "lxm": ["<NSID>", …] }` — exact strings, no wildcard, no prefix; at most `MAX_SERVICE_AUTH_AUDIENCES` (16) entries of at most `MAX_SERVICE_AUTH_METHODS` (64) methods each, constants in `fauna_protocol::kind_manifest`; an entry's unknown member refuses like any other. An `lxm` the custodian would never mint for — account mutation, migration, session lifecycle, the mint itself, and any `com.atproto.*` method the classifier does not yet name, which fails closed because the PDS's own namespace is where a new one of those four would appear (`fauna_bridge_atproto::authz::service_auth_lxm_admitted`) — refuses the whole manifest at resolution; an unclassified method in any other namespace is a service's own lexicon and is admitted; so a publisher learns at publication, never at the first call; a document whose `scope` names `fauna:identity:op:atproto.service_auth` and declares no `service_auth` entry refuses at resolution too — the scope would grant nothing. The set is saved on the roster row at consent (§ The principal model, `declared_service_auth`) and read there per request by the door; a principal consented from a document without the member holds `[]` and is refused every mint.
- **The `bridge` block (ruled 2026-10-02; refutable until the first bridge manifest is consented).** `id` is a one-label lowercase name under the kind grammar's label rule, unique per account roster at consent; the first-party ids `nostr`, `bluesky`, `activitypub`, `email` and `fauna` are reserved and refuse. **`glyph` is the lowercase id of one member of the small fixed set** (`libs/fauna-core/src/source_glyph.rs`, `SourceGlyph::ALL`; `bridge` — the generic bridge concept, 🌉 — joins the set with the adapter's first slice, appended last for UniFFI discriminant stability; any other string refuses the document), never an image. `address_grammar` is a regex over the far network's own address spelling, at most `MAX_BRIDGE_ADDRESS_GRAMMAR_BYTES` (256) bytes, compiled at resolution with the `regex` crate (linear-time by construction) and refused if it does not compile — it is matched nest-side only (`conversation.rooms.open`), never shipped to an app's picker. **`capabilities` is the `ThreadCapabilities` record verbatim** (`libs/fauna-conversations/src/capabilities.rs`) **minus `encryption`**, which no bridge may declare: the room's class derives it ([`../ui/conversations.md`](../ui/conversations.md) § Where logic lives → *The `Bridged` adapter*, ruling 1), and a block that names it refuses — so a bridge declares exactly what the apps already gate on, and nothing the apps derive. **How the block evolves (ruled 2026-10-04).** The manifest parse stays strict — a member or capability this build does not name refuses the document, so a nest never consents to a block it cannot read in full. The *stored and served* block is additive: a nest re-serves the roster row it stored, and an older nest or app may be the one reading it, so a member a newer build added is kept in the block's catch-all and a capability value that is neither a flag nor a string is carried whole ([`transport.md`](transport.md) § Schema and forward-compat discipline, rule 4 and rule 3's open, carrying answer). A carried capability reads as not offered.
- **Unknown members inside `fauna` refuse** — the loopback-client rule that an unread parameter is a configuration the client wrongly believes it made ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § As built → *Client metadata resolution*).
- **`ingress` and `events_uri`** are consumed by [`security.md`](security.md) § Co-resident process trust boundary (nest-terminated TLS + the identity-aware proxy) and [`transport.md`](transport.md) § Push events → *Third-party event doors* respectively. **`events_uri` (ruled 2026-10-05) is an `https` URL whose host is exactly `publisher.domain`, on the default port, with no credentials and no fragment** — the domain the manifest's signature already proves control of, so a consented document can only ever aim the nest's signed notifications at the publisher's own server; `null` or absent declares none, anything else refuses at resolution (`fauna_protocol::kind_manifest::validate_events_uri`). What is POSTed there, when, and under which key are `transport.md`'s and `key-material-hierarchy.md`'s.

## Execution forms

**TP3 fixes the pair: WASM components and curated Fauna-namespace container images.** No foreign native binaries. Build order between the two runners is the implementation plan's call.

### The runner contract (shared by both forms)

The nest starts, stops and updates a hosted principal; hands it its sidecar bearer and the nest endpoint as **artifact-set environment** (bucket 1 of [`../principles.md`](../principles.md) § One configuration surface — never hand-edited; the same channel the first-party bridges get, [`apps/bridges.md`](apps/bridges.md) § Why this shape); mints its X25519 key inside the sandbox; exposes exactly the WS-RPC kinds its scopes cover; and proxies its declared ingress. The plugin dials the loopback listener the sidecar channel already is (`bins/fauna-nest/src/sidecar_channel.rs`). **TP2 — headless:** a hosted plugin ships no UI; its user-facing surface is its schema-declared settings card plus what it writes into records, folders and conversations, rendered by the seven apps. A plugin that needs a dashboard publishes a companion web app under its own document — a remote app, not a plugin. **Roles for hosted plugins are the principal row**: there is no `--mode=`, no compiled role-table entry per plugin.

**The install-approval leg.** The admin picks a catalog entry or, for WASM, the document URL; the nest resolves the document, verifies the publisher signature over the Fauna members, and shows the **same consent card** with an install section: execution form, requested kinds, requested scopes, settings-schema summary, the publisher, the pinned digest. Approval creates the principal, starts the runner and hands it the sidecar bearer. **Install grants nothing over any user's sealed data**: each user who wants the plugin to touch their scopes consents from their own app, which is what mints that user's grant to the plugin's key. An admin cannot consent on a user's behalf. The card's mechanics are the consent ceremony's ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Consent).

### WASM components

The portable first-class form: runs wherever the nest runs, standalone binary included, so a fresh nest has plugins with no Docker. Capability-based by construction — the host links exactly the declared imports: outbound HTTP to named hosts, the nest API, a state scope, a clock; nothing ambient. Fuel and memory caps as the labeler runtime already applies (`libs/fauna-labeler`). The labeler interpreter has no host I/O by design; a bridge-capable plugin needs a component-model runtime, which the user approved 2026-09-26 — `wasmtime` with the component model, crates.io under cargo vet, admitted through the normal vet flow and never read as source (the dependency-review venue is [`release-integrity.md`](release-integrity.md) § Reviewing untrusted source without being subverted).

**The contract as built (2026-10-02; `libs/fauna-plugin-host`, the one crate every embedder of the sandbox links).** A plugin is a component against the **`fauna:plugin@0.1.0` world** (`libs/fauna-plugin-host/wit/plugin.wit`, the authority on the bytes of every import and export; this paragraph is the summary). Imports: **`nest-api`** — `call(account, kind, payload)` is one WS-RPC call as this principal, for a bound account or the install row, dispatched through the principal chokepoint (the `ThirdParty` ceiling, then that binding's scopes — the plugin's reach is the row's data, as for a remote principal, and the nest's `dispatch_principal` is the one door), and `bindings()` lists the accounts bound to it; **`state`** — get/put/delete over the plugin's own scope; **`holder`** — `public-key()` and `open-grant(owner, wrapped)`, the second performed by the host with the shared `unseal_capability`, so **the holder secret is never lowered into plugin memory** (rule 2's "minted inside its sandbox" is realized as *minted by the host into the sandbox's state scope, reachable as operations only*: neither the plugin's own code nor any remote party can extract it; the nest process, which owns the sandbox's memory anyway, can — the property a container plugin's volume has, stated rather than overclaimed); **`http`** — `fetch` to the document's declared hosts, refused before any dial otherwise; **`clock`**; **`log`**. Exports: **`lifecycle`** (`start` once per instance, `stop` best-effort) and **`ingress`** (`handle` over a request the nest terminated, carrying the nest-asserted actor as a field of the record, never a header). **Caps are constants** (`PLUGIN_MAX_MEMORY_BYTES` 64 MiB, the labeler ceiling; `PLUGIN_FUEL_PER_CALL`, about a second of CPU, budgeted afresh for every export call; `PLUGIN_MODULE_MAX_BYTES` 16 MiB on the component). **A spent budget or a trap ends the call as a typed fault and poisons the instance**; the host survives, re-instantiates, and counts — a plugin that faults repeatedly is the admin's to uninstall, never the nest's to keep retrying blind. A refused memory growth is a failed `memory.grow` the plugin observes, not a fault. The nest's side — the boot walk over `hosted_plugins`, start/stop on install and uninstall, `HostServices` over the chokepoint and the guarded fetcher — is `bins/fauna-nest/src/plugin_runner.rs`; the route that feeds ingress is still owed (§ Implementation status today).

### Curated containers

The ecosystem's form for existing Go/Python bridges. **Catalog only:** each entry is `(document URL, image digest re-published under the Fauna namespace, publisher class)` under the exact policy every image Fauna references already follows — digest-pinned, "recorded and pinned, not audited", present in the vetted table, merge-gated, on the monthly currency cycle ([`release-integrity.md`](release-integrity.md) § Third-party container images owns that policy; this doc owns only *admission* — which entries exist). The admin installs from the app UI (§ The runner contract); a **plugin supervisor** holds the Docker socket in Watchtower's trust class and starts plugin containers unprivileged, network-restricted to their declared hosts, with the sidecar bearer as environment ([`installers/docker.md`](installers/docker.md) § Supervisor sidekick socket — the `allowedServices` list becomes catalog-driven data under a compiled ceiling). Arbitrary user-supplied images stay out: they collide with all four parts of the pin policy and are the "operator one layer up" the invariant forbids.

### Not a form: foreign native binaries

Strictly dominated by containers on Linux and unsandboxed elsewhere. Fauna's own Go bridges keep the native sidecar + Landlock form ([`security.md`](security.md) § Co-resident process trust boundary) because they are first-party signed artifacts.

### Developer loop

A dev nest accepts a local WASM file or a local image by an explicit dev carve-out mirroring the loopback OAuth client ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § As built → *Client metadata resolution*): synthesized document, "Development plugin" displayed name, loopback only.

## The roster model

One roster replaces the three surfaces of the same shape (§ Implementation status today): **every principal is a row** — resolved name, publisher domain, execution-form badge, scopes in words, created, last used, the trust facet's *lasts-until* (the latest window end among the third-party capability grants — those over an `ext.*` kind — that the owner's grant log holds live for the principal's holder key; a principal holding none, because it consented to no `records` scope, attested no key, or the app has no grant log wired, keeps the declared fallback: the latest horizon among its live OAuth grants, open-ended when any has none), **Revoke** — plus the *Connect an app* entry (the typed-code start) and the *Requests* tray (the quiet push start). Mail app-passwords remain rows of the same roster (credential class "app password", revoke = the existing blob revoke); NIP-46 bunker apps become principals whose only scope is `fauna:identity:op:nostr.*`. This doc owns the **model** — the row shape and what each column derives from; the page (layout, states, element IDs, per-app frontier) is [`../ui/connected-apps.md`](../ui/connected-apps.md), and the Settings rail slot is [`../ui/settings.md`](../ui/settings.md) § Navigation model.

## Reference cases

Four cases that exercise every ruling; each names what it needs.

1. **"Sign in with Fauna" on a website.** The site publishes its document naming its redirect URL and `openid profile`; a visitor types their handle, the site resolves it to the nest domain, reads discovery, pushes a PAR with PKCE + DPoP; the nest pushes the consent card with the binding code to the visitor's apps; the visitor compares and approves; the site receives an ID token. Every relying-party library works unchanged; revoke is one row on the connected-apps page. Needs TP5, TP6.
2. **A dating app (remote server + its own mobile app).** Sign-up is case 1 via the same-device handoff (TP9). The card additionally asks for `fauna:records:rw:ext.dating.example.*` and a read grant over that scope for the matching server's key; profile and swipes are sealed records under the app's own kinds; the server holds keys to exactly that scope (TP4: it created it) and computes matches through the HTTP record door; messaging opens a Fauna conversation — identity is never delegated. Leaving is one revoke; the records stay the user's. Needs TP4, TP7.
3. **A swipeable video viewer over the account's own feed.** A device app requesting `fauna:feed:read:account` (the account's reading of its local timeline and custom feeds — public posts, its own order and like/repost state) and `fauna:personalization:rw` with its grant twin; a public post's media it fetches through the public blob door like any reader. It runs the same shared cue engine the first-party apps run so its verdicts train the user's sealed factors — possible only because the grant wrapped the plane's model key for it, which is why the models rest under a key of their own rather than the BackupKey ([`../behavior/topic-factors.md`](../behavior/topic-factors.md) § At rest). TP4 admits this grant class for a **device** app, and the arm refuses a remote one at PAR. Needs TP4, the fourth and fifth arms ([`../behavior/authorization-server.md`](../behavior/authorization-server.md) § Scope grammar → *The planes ruled 2026-10-02*).
4. **A third-party Matrix bridge.** A curated-catalog container whose document carries the `bridge` block. Install approval creates the principal and starts it; each user links their Matrix account through the plugin's settings card (TP2) and consents to `fauna:conversations:bridge` + `fauna:records:rw:ext.bridge.example.*`. Rooms appear as bridged rooms with the declared capability vector and a transport-only label; inbound is sealed to the user before the nest sees it, outbound is sealed to the bridge. It never enters the seven apps, never joins an MLS channel, never holds a Fauna identity key. Needs TP2, TP3, TP8, TP10, TP11.

## Architectural rules

1. **One document type, one principal.** A second identity object or a second registrar is the anti-pattern TP1 rules out; a new arm reuses the document and the row.
2. **Tokens authorize transport; grants carry keys; the oracle performs identity-bearing acts.** A design that lets a token open a sealed byte, or a grant stand in for a token at the dispatch chokepoint, has collapsed two layers.
3. **Install ≠ grant.** Admin approval of hosted code never touches any user's sealed scopes.
4. **Reach is data under a compiled ceiling.** A principal row can only narrow what the `ThirdParty` class arm permits ([`apps/bridges.md`](apps/bridges.md) § Capability-allowlist enforcement).
5. **Every new user-facing knob this surface grows is app UI + nest state** — the catalog, the requests tray, the per-client block, the settings card. Never a file, an env var, or a flag.

## Don't do these

- **Don't add a dynamic-registration endpoint or an admin-side "create principal" for user-scoped principals.** Consent on the user's own app is the only mint.
- **Don't let a plugin ship UI.** A settings card from `settings_schema` is the whole surface (TP2).
- **Don't admit an image outside the catalog, and don't admit a foreign native binary** (TP3).
- **Don't mint a read grant over a user's pre-existing sealed scope to a remote principal** (TP4). A remote service that must process such data ships a hosted plugin.
- **Don't build a third-party mechanism that presumes membership in an MLS group** (TP12). Under TP8 a bridge is a member only of a room whose class already says the bridge reads it.
- **Don't let a plugin hold a certificate key or terminate its own TLS** (TP11 — [`security.md`](security.md) § Co-resident process trust boundary).
