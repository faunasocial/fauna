> **Audience:** anyone building or gating a controversial-class feature; nest + shared-Rust work (the policy store + enforcement floor); app work (gate rendering, build flavors); release/build-system work (flavors, artifact verification).
> **Purpose:** some features can rub platform owners (Apple) and governments the wrong way — payments for content, bulk file sharing. This doc is the one mechanism for (a) **dynamic gating**: legitimate rule-setters can disable or *limit* such features with granular, quota-shaped policies, and (b) **compile-time excision**: any such feature can be shipped **completely compiled away** in a build flavor, fast, as an App-Store escape hatch.

Two rulings this pass made, recorded because a later session would otherwise re-derive them wrongly:

- **`zaps` composes with `nostr` structurally, by module placement — not by a cargo edge and not by `cfg(all(…))` at each site.** The nest's zap surfaces live inside the already-`nostr`-gated `src/nostr/` subtree, so the reachable surface is `nostr AND zaps` by construction. `zaps` must **not** declare a `nostr` edge: `zaps` is default-ON, so that edge would pull the nostr bridge into the *default* nest binary — the same class of accident as a default-features change reaching a consumer that opted out. And `nostr` must not imply `zaps`, or the Damus flavor (nostr on, zaps off) becomes unexpressible, which is the entire point of the subset member.
- **What excises is the *comparison*, never the price at rest.** An excised nest still accepts, stores and re-serves a tier's `asking_price` — the at-rest and wire-compat invariants both demand it. So the nest's storage path speaks the ungated wire type (`fauna_protocol::subscriptions::TierAskingPrice`) end to end, and `fauna_payments::asking_price::AskingPrice` is constructed at exactly one site: the zap purchase path, inside the `zaps` gate, where money is judged against a price. ## Goal (the charter, user directive 2026-08-10)

Two capabilities, both required:

- **(a) Dynamic gating.** Rule-setters — governments per region, parents/guardians per ward, admins per nest, users for themselves — can enable, disable, or **limit** controversial-class features, the same way content-blocking filters work. Limits are **granular and quota-shaped**, e.g. *"max 50 files per week, to max 10 distinct accounts per month"* for file sharing — the feature stays fully usable person-to-person while mass distribution is structurally prevented: Fauna must not be buildable into the next The Pirate Bay, and that property must not depend on anyone's goodwill.
- **(b) Compile-time excision.** Every controversial-class feature compiles only behind a feature flag, so a build flavor can ship with the feature — and the very ability to turn it on — **completely compiled away**, verifiably. This is a deliberately quick-to-exercise **escape hatch** for the day a feature threatens to block an App Store update: a known, perpetually-green build flavor, not a design that has rotted by the time it is needed.

## What this is NOT (hard boundaries)

Gating bounds feature **availability and volume**. It never touches confidentiality or integrity:

1. **No gate weakens encryption.** No tier — region, admin, guardian, or self — can obtain a decrypt path, weaken sealing, or read content as a policy effect. The nest still decrypts nothing ([`nest/storage-modes.md`](nest/storage-modes.md)); what a gate sees is the same plaintext-floor operation metadata the nest already sees.
2. **No surveillance as a side effect.** Usage accounting stores coarse per-feature counters (counts per window), never content, never per-item logs beyond what the feature's own mechanism already stores. The family-safety Notify rule — *category + count, never content* — is the ceiling for what any rule-setter learns.
3. **Core communication is not a gated feature.** Messaging, mail, calendars, contacts, the social feed, moderation-framework participation, and E2EE itself are Fauna's identity and are never registry members. A jurisdiction that demands weakening those is answered by not shipping there (excision at the distribution level), never by a gate. Region-scoped *content* decisions are the sibling plane ([`../behavior/region-blocking.md`](../behavior/region-blocking.md)), not a feature gate.
4. **No silent gates.** Every active restriction is visible to the person it binds — which feature, what limit, which tier set it (§ Transparency) — the same visible-and-reasoned invariant region blocking holds for content.
5. **No config-file tier.** Policy is data in nest state reached through app UI or the sanctioned authority channel; "the government / the operator edits a config file" is not a representable design ([`../principles.md`](../principles.md) § One configuration surface).

## The gated-feature registry

### Membership criteria

A feature is **controversial-class** when any of these holds:

1. **Platform-owner policy risk** — the feature class has documented app-store policy sensitivity (real-money flows outside platform IAP, content marketplaces, off-store payment rails).
2. **Regulatory divergence** — jurisdictions materially differ on the feature's legality or required limits (payment regulation, copyright-liability exposure for bulk distribution, crypto-adjacent rails).
3. **Abuse-at-scale inversion** — the feature is a materially different product (legally and socially) at high volume than at personal volume, so quota-shaped limits are the difference between "family tool" and "distribution platform".

Membership is ratified by the user, recorded here, and carried in code as a shared-Rust registry (§ Wire & data shape) — one catalog, consumed by nest and all 7 apps, so the gated set can never diverge per app (priority #1).

## The rule-setter model

### The tiers

Six sources of restriction, ordered outermost first **by scope** (tier numbers order scope, not importance — the ratified priority order below differs, and under the meet neither ordering has any mechanical effect). Each can only **tighten** — composition is the meet (§ below) — so no tier needs authority over another and no precedence disputes are representable.

| Tier | Principal | Scope | Mechanism | Bucket ([`../principles.md`](../principles.md) § One configuration surface) |
|---|---|---|---|---|
| 0 — Excision | the platform owner / app store (the build flavor is its mechanism) | the artifact (per storefront) | the feature is compiled away (§ Compile-time excision); nothing to configure. The grain may be finer than a whole feature when a store polices one affordance — the Damus precedent (the zap button off posts, the rest untouched) — still bucket-1 flavor wiring, never a runtime knob | bucket 1 (artifact wiring) |
| 1 — Structural defaults | nobody (Rust constants) | every deployment | built-in generous quota ceilings per feature — the anti-abuse floor that holds even where no policy source exists (§ The quota grammar) | bucket 1 (hard-coded) |
| 2 — Region | a region's administering authority, as **published policy data** | accounts/deployments the region claims (attachment per § below) | the authority-published feature-policy document, riding the same region/authority plumbing as region blocking (§ The region tier) | data through the sanctioned authority channel — never an admin lever for the *content* of region policy |
| 3 — Admin | the nest admin | every account on this nest | per-feature enable/disable + limits in the admin UI, persisted in nest state — the existing runtime-flag tier (`caldav_enabled` / `set_mail_enabled`, "the admin enabled it (via app UI)" — [`version-compatibility.md`](version-compatibility.md) § Dim 3) grown a quota shape | bucket 2 |
| 4 — Guardian | the ward's guardian | one supervised account | a `features` sub-document on the guardian policy, riding `fauna.family.policy.update` with absent-means-unchanged ([`../behavior/family-safety.md`](../behavior/family-safety.md) § Policy-update compatibility) | bucket 2 |
| 5 — Self | the user | their own account | self-imposed per-feature limits in Settings, persisted in nest state so the floor enforces them (the user is a legitimate rule-setter for themselves) | bucket 2 |

**Rule-setter priority (user-ratified 2026-08-10, OQ-2).** Rules constrain **both apps and nests, and apps are the primary subject** — apps are what users interact with and what stores police; the nest floor (§ Evaluation points) is what makes a rule hold against non-conforming and version-skewed clients, not the rule's primary addressee. The external rule-setters, in priority order: **(1) governments** (the region tier), **(2) app stores / platform owners** (tier 0 — per-storefront flavor wiring), **(3) parents/guardians** (the guardian tier), and **(4) admins — a distant fourth**, able to set rules only for the nest they admin. Tiers 1 and 5 are not external rule-setters: one's principal is nobody, the other is the user themselves. Design tension between rule-setters' needs resolves in this priority order; composition never does (the meet is order-free).

The admin tier is not new authority: admins already enable/disable whole features nest-wide (mail, CalDAV) through app UI. What this doc adds to that tier is the quota shape — the full policy document, meet-bounded like every tier (ratified at OQ-2: a *tier*, not a relay; the meet already makes "may an admin relax past region policy?" unrepresentable, and the priority order above makes the admin the least-privileged external rule-setter by design). The guardian tier extends the family-safety policy document exactly the way v1.x pillars did — additive sub-document, defaults = unsupervised-equivalent — and, unlike the content pillar, it carries **no conforming-client caveat**: feature gates are nest-enforced (§ Evaluation points), so a modified client cannot bypass a guardian's feature limit the way it can bypass a content floor.

### Composition — the meet rule

The effective policy for an (account, feature) pair is the **meet** (most-restrictive combination) of every applicable tier:

- availability = AND of every tier's allow (any tier's `deny` denies);
- each quota dimension = MIN across tiers (an unset dimension in a tier is "no opinion", not "unlimited past tier 1") — **per (dimension, window) cell**, refined at build time (§ The quota grammar);
- tier 1's structural constants are always present, so the meet is never unbounded on a dimension the registry declares for the feature.

**Every surviving bound carries the tier that set it** (W2). Attribution is not decoration: boundary 4 and § Transparency both require the bound person to see *which* tier binds them, so the meet propagates a source tier per cell rather than reducing to bare numbers. On an exact tie the **outermost-scope** tier (the lowest tier number) is named — deterministic, and it attributes the restriction to the tier the person can do least about. A tie is not a precedence claim: both tiers bound identically, so the choice changes what is *displayed*, never what is enforced. The ratified priority order (governments > app stores > guardians > admins) keeps its deliberate absence of mechanical effect.

Because every tier can only tighten, "may an admin relax below the region policy?" is unrepresentable rather than forbidden-by-rule — the same make-bad-states-unrepresentable technique as the handle-less admin ([`nest/common.md`](nest/common.md) § Client-state recoverability). The in-code precedent for strictest-wins multi-source composition is the shared render-verdict engine (`fauna_core::obligation::render_verdict_composed` — own thresholds + guardian floor, explicitly built to take further rule sources; owner: family-client-enforcement.md § Content policy). Feature gating composes *operation* verdicts, not render verdicts — the shape is shared, the code is not.

### The region tier — one region/authority model, two planes

Fauna already has a ratified region/authority direction for **content**: each authority (in practice a country) administers its region and publishes a completely transparent blocking algorithm whose history stays public forever ([`../behavior/region-blocking.md`](../behavior/region-blocking.md) § The ratified direction). The feature-gating region tier is the **second plane on the same model**: the same authorities, the same publication transparency (published, examinable, append-only public history), publishing a *feature-policy document* (the quota grammar below) instead of a content algorithm.

The shared plumbing — **how regions are determined, how authorities are enumerated and authenticated, how they publish and sign, where the public history lives, and the unfetchable-policy failure mode** — was **resolved 2026-08-10** (region-blocking.md § The region/authority plumbing — ratified-refutable; determination and render scope user-ratified the same day), designed **once** for both planes (that doc owns it; this doc consumes it): a Fauna-curated signed region registry (compiled-in snapshot + refresh), one signed artifact envelope whose second payload kind is this doc's feature-policy document, a universally mirrorable append-only transparency log with the log-inclusion-validity (CT) property, **declared-never-detected** region determination, and **last-known-good** fail posture. The two feature-gating-specific notes that fed that pass are settled with it:

- **Attachment.** Store-distributed app builds bind per storefront (the app's region, shading into tier 0); nest-side enforcement binds the accounts a deployment hosts at the **deployment's admin-declared region** (its legal situs, declared in admin UI, nest state — never IP-derived).
- **Fail posture:** last-known-good, **ratified** — a fetched policy stays in force until replaced, never silently relaxing; the family-safety three-clause shape applied one level up (region-blocking.md § The region/authority plumbing → Fail posture owns the statement).

**Honest trust model, stated on purpose** (the family-safety conforming-client honesty rule, applied one level up): Fauna is open source and self-hosted, so the region tier binds *conforming deployments* — a determined admin can patch their nest, exactly as a determined teenager can patch a client. The load-bearing compliance mechanisms are structural: tier 1's constants ship in every build, store-distributed apps enforce client-side and can be excised per storefront, and the authority channel makes lawful operation the effortless default (works-out-of-the-box lawfulness). What this design refuses to build is coercive: remote kill switches into self-hosted deployments, region auto-detection/fingerprinting, or any government-facing control plane into a deployment.

## The policy shape

### The quota grammar

A per-feature policy document, identical at every tier that can express one:

- `availability: allow | deny | limit` (`limit` = allow, bounded by the dimensions below);
- quota dimensions, each `Option<bound>` (absent = no opinion at this tier):
  - **operation count per window** — e.g. files shared per week, claims minted per day;
  - **distinct counterparties per window** — e.g. new share-recipient accounts per month (the fan-out bound: the dimension that separates person-to-person from mass distribution);
  - **size per operation / volume per window** — byte or machine-comparable-value caps where the feature moves bytes or priced goods;
- windows are a closed enum (`day | week | month`), evaluated over the account's local day (the clamped-offset rule family-safety's screen time established).

**Refined at build time (W2, 2026-08-10).** Three shapes the ratified grammar left open, settled by building it:

- **A dimension holds at most one bound *per window*, not one bound.** Two tiers bounding the same dimension over different windows ("50 per week" against "10 per day") have no common numeric minimum, so a single-bound shape would have to invent a conversion or silently drop a restriction. One cell per (dimension, window) makes the meet an element-wise `min` and evaluation a conjunction — every present bound must hold. This is what makes the meet total; see § Composition.
- **Windows are trailing, not calendar** — `week` sums the last 7 day buckets, `month` the last 30. A calendar boundary is a reset a distributor can simply wait for, and it would make a bound's real strictness depend on the day of the month.
- **The `counterparties` dimension is counted in the table like every other dimension; the feature's own records are consulted only to decide whether an operation's counterparty is *new*.** Storing the identities would be the per-item ledger boundary 2 forbids, so distinctness cannot be recomputed from a log — but it does not need to be. The split is: at spend time the caller resolves the operation's **newness delta** against the feature's own mechanism (a share roster, a claim table — "not currently in the records ⇒ new", the "beyond what the feature's own mechanism already stores" carve-out), and that delta is added to the same day buckets `operations` and `volume` use. The verdict function receives a summed count and never learns who.

  **The load-bearing property is monotonicity: a counterparty, once counted, stays counted for the window's trailing span regardless of any later removal or revocation — removal must never refund counterparty quota.** This is what makes the dimension the structural gate § Charter members calls it. Sourcing the *count itself* from the records instead would make it refundable, because those records are user-mutable by design (roster removal is an ordinary act, grants are revocable, and *"user always controls their data"* makes the removal affordance mandatory — record durability can never be assumed): an add→share→remove cycle would hold the observed count under any bound while the true number of distinct recipients grew without limit, voiding the bound entirely.

  **On the "same person on three days would count three times" objection** (which is what first argued against buckets): it indicts *per-appearance* increments, not newness-delta increments. A standing counterparty contributes `1` the first time and `0` every time after, so a repeat recipient is not re-counted. One residual is accepted deliberately: remove→re-add inside a window counts twice. That is fail-tight — it over-counts against the person cycling records, which is the behavior a bound wants to deter — and the alternative is exactly the refundable shape above. *(Recorded during a nest security-review finding: the doc's original wording and `fauna_core::feature_gate` shipped in the same commit and disagreed, the code holding the sound shape. A future revision is legitimate on one ground only: naming an explicitly **add-durable** record source that survives removal for the window's span, with that durability property stated.)*

The charter example encodes as: `p2p-share: limit { ops: 50/week, counterparties: 10/month }`. Per-feature applicable dimensions are declared in the registry (a dimension the registry doesn't declare for a feature is unrepresentable in its policy).

Tier 1's structural defaults are **generous constants sized for the personal-use ceiling, prohibitive only at distribution scale** (the spouses moving hundreds of GB between their own devices — 2 counterparties, huge bytes — must never feel a gate; sharing to hundreds of strangers must be structurally impossible). Constants live in shared Rust beside the registry, one value set fleet-wide, revised only by ratification here.

### Evaluation points — the enforcement split

The family-safety honesty split ([`../behavior/family-safety.md`](../behavior/family-safety.md) § Guardian policy), applied to feature gates:

1. **Nest-side enforcement is the floor.** Every gated operation is an existing nest-arbitrated operation (share-roster writes, claim mints, provider enablement, unlock buys) whose occurrence is plaintext-floor metadata the nest already sees — so the nest enforces availability + quotas **without any content access**, and the gate **holds against non-conforming and version-skewed clients** (an old client that predates gating calls the old kinds and receives the typed refusal — no bypass). The verdict is one shared pure function (the `supervised_reach_verdict` shape): `feature_verdict(registry entry, effective policy, usage counters, op) → Allow | Deny | OverQuota`, composed nest-side at each gate surface.
2. **Client-side rendering is the courtesy layer — for the tiers the nest enforces.** Apps read the effective policy + remaining quota and hide/disable gated affordances with an honest "limited by …" surface instead of letting the user hit refusals (the Dim-3 hide-or-disable rule, [`version-compatibility.md`](version-compatibility.md)). Rendering is never the enforcement *of nest-arbitrated operations* — but the app side is not merely decorative either: for the tiers whose subject is the artifact itself (tier 0's compiled absence, tier 1's constants shipping in every build, and a store build's storefront-bound region posture), the app **is** the enforcement point, which is what makes apps the primary rule subject (§ The rule-setter model) and what keeps a store-distributed build lawful even against a patched nest (the honest trust model, § The region tier).

Typed refusals ride the Dim-4 pattern ([`version-compatibility.md`](version-compatibility.md) § Dimension 4): a distinct `RpcError` code (localized, client-actionable, naming the binding tier), never a generic internal error.

### Usage accounting

Nest-side per-(account, feature, dimension) counters in day buckets (the `guardian_usage` shape), pruned past the largest window; windows are evaluated by summing buckets. **All three dimensions live in the table**, including `counterparties`, whose bucket increment is the operation's newness delta rather than its raw counterparty count (§ The quota grammar's third refinement owns why, and why the count must never be re-derived from mutable records). Buckets are append-only within a window: nothing decrements them, which is what makes a counterparty bound unrefundable. **Where a day starts is one shared rule, not this plane's own** — `fauna_core::day_bucket` (lifted out of the nest's family handlers in W2, 2026-08-10): the nest's own clock plus the client's clamped UTC offset, so the feature plane and family safety's screen time can never disagree about which bucket an instant lands in (family-client-enforcement.md § Screen time owns the rule's rationale; the clamp is what bounds the key space, making a hostile offset under-reporting-equivalent rather than a way to mint fresh quota). Counters are coarse **counts only** — no per-item ledger is added by this mechanism (boundary 2). Counting is atomic with the gated operation (spend-on-commit, the correlation-budget precedent), so concurrent operations cannot overshoot a quota by racing.

### Transparency & auditability

- Every account can read its own effective policy: which features are limited, the remaining quota, and **which tier binds each restriction** (region policy by name + version, "your admin", "your guardian", "your own setting") — the supervised-indicator principle generalized, and the feature-plane twin of region blocking's visible-and-reasoned invariant: there is no restriction you cannot see.
- Every policy write (admin, guardian, self) writes an audit row (the `family:*` audit precedent); the active region document's identity + version is part of the transparency read. Region-policy *history* transparency (public, append-only) is the shared authority-channel property (region-blocking.md invariant 2).
- A guardian-tier feature limit is visible to the ward exactly as reach/content policy is (family-safety § The trust shape, invariant 4).

### Fail posture

- **A fetched region policy persists in nest state and stays in force until replaced** — an unreachable authority channel never silently relaxes a gate (last-known-good — **ratified 2026-08-10**, region-blocking.md § The region/authority plumbing → Fail posture), and staleness past the channel's refresh cadence surfaces admin-side as a warning, not an outage.
- **A deployment no region claims** (fresh install, unresolved determination, offline) runs tiers 1/3/4/5 with gated features **ON at tier-1 structural defaults** (user-ratified 2026-08-10, OQ-3 — never off-by-default): structurally bounded by the constants, fully works-out-of-the-box.
- **Usage counters unavailable** (should be unrepresentable — they are local nest state) → the gate fails closed for the operation, never open.
- **An authored policy document this nest cannot decode denies at its own tier** — never *"this tier said nothing"* (ratified + built 2026-08-11). Every tier here can only tighten, so an authored document **is** a restriction somebody set; skipping an unreadable one is byte-identical to its absence and therefore *lifts* it — silently, on planes whose whole purpose is to hold (a guardian's nest-enforced limit on a supervised minor, a region's legal one). Reading it as `deny` is the only over-approximation available when the content is exactly what is unknown, and it is the same direction as the counters clause above, for the same reason: local nest state that should be unrepresentable, and unreadable, must not relax a gate. Four properties keep it from becoming an outage — **(1)** only an *authored* document denies; an absent row stays "no opinion at this tier", so a deployment nobody has written a policy on is untouched (the works-out-of-the-box arm above is unchanged); **(2)** the deny carries its tier through the meet, so `fauna.features.status`, the typed refusal, and the family status read all name who binds the caller (§ Transparency, boundary 4) — the ward is told *guardian*, the account *admin*, and nothing is hidden; **(3)** every writer on every tier is a whole-document replace, so re-authoring from the app that owns that tier clears it — in-app at every tier, no shell, no migration ([`nest/common.md`](nest/common.md) § Client-state recoverability); **(4)** it is a backstop, not a routine path — the document shape is additive-tolerant (every field defaults, unknown keys are ignored), so a newer nest's document decodes on an older one and only true corruption or a non-additive wire break reaches this arm.
- **A source that stops being readable does not retire what it already wrote.** The region tier's stored artifact is re-folded against the current registry; if it still *verifies* but its payload no longer decodes, the bounds the last successful fold wrote **stay in force** — last-known-good, exactly as the first clause says, because a re-derivation that fails replaces nothing. This is distinct one line away from the retirement rule it sits beside: an artifact that no longer **verifies** is Fauna de-listing the authority (§ The region tier), and that *must* clear the tier. Unreadable-payload is a statement about this build's decoder; failed verification is a statement about the authority.
- **An unreadable *declaration* stays fully-open for enforcement, but its reads must not mistake corruption for absence** (ruled + built 2026-08-12). A `nest_region.region` row that no longer parses enforces as "no declaration" — the situs is nobody's restriction, so this is the *"a deployment no region claims"* arm above, not the undecodable-document one — while the Region-tier rows the last fold wrote keep binding (the previous clause: the re-fold stops running rather than clearing them). The **reads** therefore must not answer "no region document" while those bounds bind: `fauna.admin.region.get` and `fauna.features.status` recover the binding document's identity from the artifact store — keyless, sound because the store structurally holds at most one region's rows (the declaration write seam retires every other region's artifacts on **any** declaration change, keyed on what survives rather than on the outgoing value, so an unreadable outgoing declaration cannot skip retirement; the same seam keeps the kept region's document and bounds when the admin re-declares the region the corrupt row meant) — and the admin read carries `declaration_unreadable`, whose shared app wording names the recovery: re-declare or withdraw, a whole-value replace that clears the row in-app ([`nest/common.md`](nest/common.md) § Client-state recoverability). The general decision rule this instantiates — fold by consequence direction, the read moves with the fold — is owned by [`nest/common.md`](nest/common.md) § Unreadable stored values.

**What the editor expresses — the whole grammar, at both tiers, and nothing else.** *On / Off* (two choices, never three: `limit` is what the shared seam writes when *On* carries at least one bound, `allow` when it carries none, and *Off* writes `deny` with no bounds — a rule-setter chooses whether and how much, never a serialization detail); one optional number per **declared** (dimension, window) cell, in the registry's order (dimension major, window minor — the order the read already paints); and the per-operation cap, last, only where the member declares `volume`. A dimension the registry does not declare for the member is not rendered, which makes the nest's `UndeclaredDimension` refusal unreachable from an app rather than merely handled. Magnitudes are typed in the unit the read displays them in (the shared 1024-scale for bytes, whole sats for millisats) and parsed by the shared seam, never per app. An empty cell is *no opinion*, not zero; zero is a legitimate bound and means what it says. **The self tier is not a reduced grammar**: a user may turn a gated feature off for themselves, which is the self-exclusion case the tier exists for.

**Save is a whole-document replace, so the editor always starts from the authored document** — which is why it cannot be built over `fauna.features.status` alone. That read answers a different question (the *effective* meet for the bearer): a bound the tier authored that lost the MIN to a tighter tier is invisible in it, so an editor seeded from it would silently drop that bound on the next save; and for the admin tier it is the admin's *own account's* meet, self-limits and guardian tier included, not the nest-wide document at all. There is no cooling-off on removing one's own limit: a tier that can only tighten must never be able to trap its own author (the de-escalation ruling, § Implementation status today), and a delay is a product decision nobody has made.

**Tighten-only is rendered, never enforced twice.** Nothing refuses a looser value — § Composition makes relaxing unrepresentable, and a client-side "too loose" validation would be the second answer the nest deliberately declines to be. What the editor owes instead is honesty about effect: each cell carries a note when the **ceiling** — the meet of the tiers *outside* the one being edited — already binds at or below the typed value (*"No effect: the built-in limit is already 50 per week"*, the tier named as the read names it), and the *Off* choice is noted the same way when an outer tier already denies. The ceiling is composed **nest-side**, through the one resolver, and arrives on the authored-document read (for the guardian tier, on the ward's status entry); the client composes no meet here either (the source-level pin on `fauna-client-features` stands).

**Refusals and failure.** Input the seam cannot parse goes to the page's `error-message` with no dispatch (the serving-port shape). **With no nest, Save and Remove are disabled at all three hosts with the standard offline reason — never queued, and never left live to fail (ruled 2026-10-04).** One rule decides it at every host, the one every gated control already follows: the offline class of the kind the tier's write ends in (`AuthoringTier::write_kind`), asked through the shared gate. All three kinds are `OnlineOnly` — the admin and self kinds as this plane's own, and the guardian tier's carriage `fauna.family.policy.update` by the ruling [`account-offline-mutation.md`](account-offline-mutation.md) § The offline-mutation contract → *A policy the nest enforces is written online* owns — so the editor needs no host-specific gate input, and the family screen's own save button desensitizes beside it. Two other shapes were weighed and refused: a gate input other than the kind (a second mechanism beside the class table, minted for one leg — the guardian save's fresh read — that the gate deliberately never decides on), and building the guardian's document from the last read instead of a fresh one (the save would then write reach knobs the editor never showed, stale, over a newer save from another device). The guardian host as built on tui predates the ruling — [`../behavior/family-safety.md`](../behavior/family-safety.md) § Implementation status today records the gap. ## Compile-time excision

*(A second ratified tier-0 application beyond the store-safe flavor: the kids-app artifact's compiled-in content-policy floor — decision owned by [`../behavior/family-safety.md`](../behavior/family-safety.md) § The account age band, ratified 2026-08-22, and the shape — a `kids` flavor of the android/ios apps with the four content categories floored at `block` — ratified there 2026-09-25; the mechanism below is unchanged.)*

### The cargo feature spine

Each registry feature is a cargo feature in its owning crates, following the two-halves rule of the proven test-surface excision (e2e-automation-surface-gating.md point 15, the in-repo template for "compiled out, verifiably"):

- the owning crates gate the feature's modules/exports on `feature = "<key>"`;
- **a consumer never names the feature on a dep line; it forwards from its own feature** (the `fauna-wasm` forwarding pattern) — so one flavor switch at the app/FFI build controls the whole dependency tree, and a plain build can never re-acquire an excised feature by accident;
- FFI/wasm exports are keyed on the **feature alone, never the profile**, so generated bindings are a pure function of the feature set;
- **a subset member declares its superset as a cargo feature dependency** (`zaps = ["payments"]` in each owning crate): excising the superset excises the subset by construction, excising the subset alone stays possible, and the relation lives in one place instead of being re-derived per surface (§ Charter members owns which members are subsets);
- **default-on at the flavor ROOTS, opt-in in the deep shared crates** — refined from a flat "default-on everywhere" when the spine was first built (2026-08-10, W1; the doc was ratified-refutable and this is the refutation). Cargo features are *additive and unified*: a default-on feature in a deep crate is switched back on by any consumer that takes that crate with default features, so `--no-default-features` at the flavor root excises nothing. Measured, not theorised — the first store-safe `libfauna_ffi.so` built green and still carried all six `fauna.payments.*` kind strings, because 17 crates depend on `fauna-protocol` with defaults on. A **flavor root** is a crate a build flavor is built *from* (`fauna-ffi`, `fauna-wasm`, each app binary), where the switch is real; there `default` genuinely means "a plain build ships the feature", which is the posture § Goal (b) asks for. The invariant is pinned by `tests/e2e-unified/tests/test_payments_excision_spine.py`, because putting the feature back into a deep `default` compiles, type-checks, and silently turns the escape hatch into a no-op.

**The excised flavor is expressed as a complement feature, not a command-line list.** A root declares `default = ["store-safe", "<key>"]`, where `store-safe` names every surface that is *not* a registry member; the excised build is then `--no-default-features --features store-safe`. This keeps exactly one list: a new surface is added to `store-safe` once and is in `default` by construction. Spelling the complement on each recipe's command line instead rots the first time someone adds a feature and updates one place — and rots *invisibly*, since both flavors still build.

Product-feature cargo flags are established practice, not a new species: the nest's bridge features (`bluesky` / `nostr` / `activitypub`) and `fauna-media`'s `process_media` (the compile-away-to-a-stub precedent) gate real product surfaces today. Two more did until 2026-08-23 — the nest's `wireguard` and `fauna-protocol`'s `p2p` (absent ⇒ pushes decode to `Unknown`, inert not erroring) — and both were deleted with the WireGuard stack. Their retirement is itself the practice working: an excisable feature that stops being wanted is *removable*, not permanently owed.

### Platform-family surface excision

The app-side halves mirror point 15's per-family mechanisms: the platform shells gate the feature's UI + glue behind the family's compile condition (web: a vite define + the isolated-module pattern so production builds emit neither code nor chunk; Swift: a dedicated compilation condition; C#: a define; Kotlin: a BuildConfig constant + R8 stripping; Rust apps: the same cargo feature). An excised flavor = the FFI/wasm built without the feature **plus** the shell built with the matching condition off — the bindings' absence makes a half-excised build a compile error, not a silent leak.

**An app binary is a flavor root, so the switch lives on the app crate** — same two-halves shape as the library roots (`default = ["store-safe", <members>]`, complement named once, members forwarded from the app's own feature rather than from a dep line). A complement that is legitimately *empty* is still declared, for the reason `fauna-wasm`'s is: the day a non-registry default feature is added there, the bare `--no-default-features` spelling would silently drop it, and both flavors would still build.

⚠ **The compile condition catches the glue; it does NOT catch the render, and that gap is the app-shell half's defining hazard** (measured on tui, 2026-08-14). Gating the dep makes every *call* into the plane a compile error — which is the property above, and it is real: flipping tui's manifest produced exactly the set of glue sites, no grep required. But a feature's read model may be an **ungated inert record** by design (`PostSummary.tips` — the resolver is gated, the field is not, so it stays `None` forever in an excised build). The section that renders it then compiles perfectly, paints nothing, and **still ships every element id it would have painted**. Dead is not absent, and criterion 1 below is a `strings`-grep. So: *every* surface of a gated plane carries its own compile condition on the **render**, not only on the resolver feeding it. This is the same trap `TipView` sprang on `ffi-store-safe-check` (2026-08-11) — red with no sender anywhere in the graph — and the reason an app-shell witness cannot be replaced by a library-root one.

**The apple family's condition is NEGATIVE (`FAUNA_EXCISE_PAYMENTS`), and that is forced by the toolchain rather than chosen (2026-08-15, the apple leg).** Every other family's switch is positive — a cargo feature, a vite define, a `BuildConfig` constant — and defaults ON at the flavor root. Swift cannot express that from a recipe: `swift build` / `xcodebuild` can only **add** a compilation condition (`-Xswiftc -D…`), never remove one, so a positive `FAUNA_PAYMENTS` would have to be declared in `Package.swift` and could then not be switched off by the store-safe recipe (short of an environment-variable-driven manifest, whose evaluation SwiftPM and Xcode both cache). One condition per registry member, named for the excision and absent by default, is what the toolchain does support. **The invariant survives the inversion and is in fact stronger:** a plain build ships the plane with *no* configuration at all, so a new target, a stray `swift build`, or an Xcode scheme cannot silently excise it — the failure direction a positive-and-forgotten define would have had. What the inversion costs is that the shell's flavor is not readable from a manifest, which is why the apple leg's structural pins are recipe- and source-shaped (`tests/e2e-unified/tests/test_payments_excision_spine.py` — including the toolchain-free pin that a FaunaKit source carrying a payments element id must carry the condition too).

**How the condition reaches a local SwiftPM package's targets, settled 2026-08-22 (the iOS archive leg).** The premise that blocked that leg for a week — *Xcode does not propagate `OTHER_SWIFT_FLAGS` from an app target into a local SwiftPM package's targets, and every payments surface lives in the `FaunaKit` package* — is **true as stated and still not the obstacle**, because it is about target-level *inheritance*. A **command-line** build setting is a different mechanism: `xcodebuild … OTHER_SWIFT_FLAGS='$(inherited) -D FAUNA_EXCISE_PAYMENTS'` applies at the highest precedence to every target in the build, package targets included. That is what the archive recipe uses, and the proof is Swift-only so it cannot be confused with the Rust flavor's own excision: the generated element ids `subscription-provider-` (15 → 0) and `subscription-claim-` (10 → 0) live in `FaunaKit/Sources/FaunaKit/Generated/UiIds.swift`'s `#if !FAUNA_EXCISE_PAYMENTS` extension, Swift source no Rust feature can remove. **Neither of the other two candidates is needed, and one of them would have been wrong:** SwiftPM **traits** are positive-polarity by construction, so adopting them would invert the ruling above and break the `#if !FAUNA_EXCISE_PAYMENTS` source pins — an inversion that would have to be re-ruled here first, never slipped in as a build detail; an **environment-variable-driven `Package.swift`** stays unnecessary, and its manifest-caching hazard untested.

Toolchain-free pins in `test_payments_excision_spine.py` hold the field, the source-set split, the twins' shared surface, both source halves (no shared file names a ceremony face; every shared file painting a `p2p-share` id carries the constant), and the witness's two columns. `just android-store-safe-check` watches all four prefixes in its store-safe column and `offline-share-` in its default column. **Measured 2026-09-30, `classes*.dex` default vs store-safe:** `offline-share-` 1/0, `offline-receive-` 0/0, `share-transfer-` 0/0, `share-serve-` 0/0, and the ceremony face `FfiCeremonySeat` 7/0; the payments prefixes are unchanged at 14/0, 9/0, 5/0 and `nostr-zap-signer-` 6/0. ⚠ The default column's 1 is `offline-share-own-code` alone. In every minified android build, R8 folds the section's two gates (`showsEntryButtons`, `showsCodeWidgets`) to false and drops the rest of the render with them. That defect is release-only and predates this leg: a baseline build without it measured the same. So `offline-receive-` joins the default column only once it is fixed.

**The android family's condition is a `BuildConfig` constant, but the constant alone cannot carry the GLUE — Kotlin has no inline compile-time exclusion, and that splits the shell's excision in two (2026-08-16, the android leg).** Every other family removes the render and its FFI reference with one construct: a cargo `#[cfg]`, a Swift `#if`, a vite define feeding the isolated-module pattern. `if (BuildConfig.PAYMENTS)` is not that construct — it is an ordinary runtime branch, and its body must still **typecheck** even in the flavor that will fold it away. A store-safe build's generated Kotlin face has no `FfiPaymentsClient`, no `FfiProviderItem`/`FfiClaimItem`, no `paymentsKnownKinds`/`paymentsWebhookUrl` and no `FfiFeedManager.resolvePostTips` at all, so a *shared* file naming one does not compile no matter how the constant is set. The android shape is therefore **both halves at once**: the glue lives in per-build-type **source sets** (`app/src/payments/` for `debug`+`release`, `app/src/noPayments/` for the `storeSafe` build type — signature-identical twins of one `PaymentsGlue.kt`), with app-owned seam records so shared view models and Composables never name an FFI payments type; the render keeps the **constant**, and R8 folds it. Both halves are load-bearing and they fail differently: drop the source-set split and the excised flavor stops compiling; drop the constant and it compiles, paints nothing, and ships every element id. ⚠ **The half that is R8's rather than the compiler's is the one to distrust** — a constant-gated `if` that R8 *should* fold is not the same claim as an id that is absent, which is why the android leg's structural pins include two toolchain-free source checks (`test_payments_excision_spine.py`: no shared source names a payments FFI symbol; every shared source painting a payments element id carries the constant) *and* why its artifact witness is not optional.

**This shape is not invented for `payments` — it is the one android already uses for convention 15, measured.** The automation surface takes exactly the same two halves on this app ([`e2e-automation-surface-gating.md`](e2e-automation-surface-gating.md) § point 15's android leg): `TestAgent` lives in the `debug` source set with an inert same-signature twin in `src/release/`, and `MainActivity`'s two agent-touching blocks are wrapped in `if (BuildConfig.DEBUG)` — with R8 explicitly described there as "a second line of defence rather than the mechanism". That leg was verified by a `strings`-grep of the release APK's `classes.dex` showing **zero** `TestAgent` occurrences and zero `FAUNA_E2E_*` literals, which is standing in-repo evidence that R8 does fold a false `BuildConfig` constant and strip the branch's string constants on this exact artifact. So the mechanism is proven; what `android-store-safe-check` measures is whether it holds for *this* surface, whose renders are Compose composables rather than an activity's `onCreate` blocks.

**The web family's condition is a build-time ENVIRONMENT VARIABLE, and its removal is done by module isolation rather than by any compiler (2026-08-16, the web leg).** `__FAUNA_PAYMENTS__` is a vite `define` fed by `FAUNA_WEB_PAYMENTS`, so — unlike a cargo feature or a Gradle build type, and like apple's compilation condition — no manifest anywhere states which flavor an artifact is; web's structural pins are recipe- and source-shaped for that reason. The define is nonetheless **positive and default-ON**, which apple's could not be: a `define` is a plain config expression, so a *recipe* can remove a condition, and the flavor-root rule applies as written. What is genuinely web's own is the second half. **Folding a branch to `false` does not unlink a module** — a Svelte component's template is a module-level construct, so an element id inside a folded `{#if}` may still be emitted with the module that declares it, and a function in an unconditionally-bundled module keeps its NAME in the artifact however dead its callers are. So the web shape is: **the glue in exactly one isolated module (`$lib/payments`) and the renders in exactly one directory (`$lib/components/payments/`), both imported only from behind the condition.** Its faces had to *move* to get there — the RPC seam out of `$lib/rpc`, the wasm faces out of `$lib/wasm`, the resolved formatters out of `$lib/value-format` — because all three of those ship in every bundle. ⚠ **The half to distrust here is the bundler's**, as R8's is on android: nothing in the language removes the chunk, so the artifact witness is not optional, and three source pins (no shared source names a face; no shared source paints an element id; every importer carries the condition) are what keep the isolation from decaying between runs.

**A gated plane's user-facing INPUTS excise with it, and preserving their data is the wire's job, not the form's (ratified 2026-08-14, one answer for all 7 apps).** The worked case is the subscription tier editor's **asking-price** field: a store-safe build renders no price input (criterion 1 — it is the monetization gesture, and criterion 5 makes "the ability to turn it on" part of what excision removes), while `TierAskingPrice` stays ungated on the wire so a priced tier a full client authored keeps round-tripping (§ Wire-compat posture). The two do not conflict, and the reason is a property of the update verb, not of the form: an absent `asking_price` means *keep the stored value* ([`../behavior/monetization.md`](../behavior/monetization.md) § The asking price owns that rule), so an excised build editing a priced tier preserves the price with **no carry-through code at all**. The generalizable rule: **before excising an input, check that omitting its value means *keep*, never *clear*** — if omission clears, the excision is a silent data-loss bug, and the wire needs that distinction before the UI may be gated. ⚠ **The worked case's own claim was measured false on the Rust shells (2026-10-07):** apple, web, android and windows gated the asking-price input from their own legs, but tui pushed `subscription-tier-form-asking-price` with no `#[cfg]` and linux still does — the id sat in the catalog, only web's witness listed it, and a catalog entry one family's witness watches is a claim about that family alone. tui's leak closed in the pass that ruled the class below; linux's is that family's leg (§ Implementation status today).

**The price-and-route class — which subscription and sold-post surfaces are inside the `payments` plane (ruled 2026-10-07, fable; refutable at build time).** The question came from the first run of the iOS archive witness: the four ratified prefixes measured 0, and `subscription-offer-payment-link` was still in the excised binary — an external payment link, in the artifact the escape hatch exists to submit. An excised build therefore shows a priced tier as an ordinary approval-gated tier — name, description, Subscribe — and a sold post as an ordinary gated post, badge and nothing more; and it can author neither a price nor a sale. The differentiator the row's first investigation proposed (*does gating this id remove functionality the free path shares?*) gives the same answer on every id and stays as the cross-check for the next candidate. **Two edges, named so they are not re-derived:** omit-means-keep holds for every input the class excises — `tiers.update` reads a missing `price_hint`/`payment_url` as keep (monetization.md § The asking price), and the sell composer's fields are create-time — so an excised editor preserves a priced tier exactly as the asking-price case did; and a sale staged on a full client and synced into an excised one is not that build's to show — its gate select reads as the gated answer the shared state otherwise carries, and nothing in the excised shell can stage one. **Catalog shape and sequencing.** The ids enter `gated_features.payments.id_prefixes` as full ids — `subscription-offer-`, `subscription-tier-`, `gated-post-` and `compose-sell-` each also cover ids outside the plane — and they enter it **last**, with the final family's render gates: the entry moves the Swift and C# constants into the gated tables and the web constants into `$lib/components/payments/generatedIds.ts`, and the windows source pin reads the catalog directly, so an entry landing ahead of a shell's gates breaks that shell's store-safe build, or web's typecheck, instead of guarding it. ### What "completely compiled away" means (verifiable)

An excised artifact contains, provably:

1. **No UI surface** — the feature's element IDs absent (`strings`-grep of the artifact, the point-15 verification). **Prose included, exactly as in criterion 2** (ruled 2026-08-18, closing the question the android column parked below): a *doc comment* naming a gated element ID fails this criterion exactly as a render does, and for criterion 2's own three reasons — both criteria are discharged by one `strings`-grep of a stripped artifact, which cannot tell a painted ID from a comment; UniFFI propagates docstrings into the generated Swift/Kotlin face, so an excised build would ship a face *documenting* the UI it excised; and a split reading would make one `strings` line a pass or a failure depending only on which pattern list matched it, which is not a rule a witness author can apply. **The remedy is to gate the doc line, never to reword it:** `#[cfg_attr(feature = "<member>", doc = " …")]` keeps the kebab ID spelled verbatim in the source — `rg post-tip-total` still finds every driver — while removing it from the artifact, so the grep-ability this project trades on costs nothing. Which IDs belong to a member: § *Which element IDs belong to a gated feature* above;
2. **No wire senders** — the feature's kind strings absent. **Absent means absent, prose included:** the verification is a `strings`-grep of a stripped artifact, which cannot tell a sender from a comment, so a *doc comment* naming a gated kind fails this criterion exactly as a sender does — and does so legitimately, because UniFFI embeds docstrings in the library metadata and propagates them into the generated Swift/Kotlin face, where an excised build would otherwise document the plane it excised. The trap is specifically the **ungated** exported item that a gated resolver populates (the deliberately-ungated inert record, § below): gate the kind's *name* to the gated code, not just the code (`TipView` did this on 2026-08-11 and turned `ffi-store-safe-check` red with no sender anywhere in the graph);
3. **No listener** — for `p2p-share`, no share data plane at all ([`../behavior/p2p.md`](../behavior/p2p.md) § Wormability posture rule 5);
4. **No capability advertisement** — an excised nest build omits the token;
5. **No re-enable path** — there is no runtime flag, hidden setting, or agent command that restores the feature; only shipping a different build does.

Each flavor carries an artifact-level absence test (tier_4 shape) asserting 1–2 by `strings`-grep, kept green per § below.

### Wire-compat posture of an excised build

An excised build is **a peer without a capability, never a fork of the wire** ([`version-compatibility.md`](version-compatibility.md) I2/I4): an excised client simply never invokes the feature's kinds and hides its surfaces by its own compiled absence; a full client against an excised nest sees the token missing and degrades exactly as against an older nest. Version-skew tests pin both directions (the Dim-6 grid gains an excised-flavor axis for registry features).

At-rest data from before an excision **survives untouched** (no-data-loss invariant): excising a feature removes the ability to operate it, never a migration that destroys what it stored.

### The feature-matrix test story

Compile-gating without test-gating is the documented failure: a feature-gated plane can compile in the shipped flag shape while no test exercises it there — the union-vs-parts gap the post-merge gate now guards. Therefore:

- both the default flavor **and** the excised flavor build and run their test subset; the excised flavor's suite asserts the feature is absent (the absence test) *and* that everything else still works;
- the excised flavors are kept **perpetually green** by the asynchronous merge-gate check ([`merge-gate-check.md`](merge-gate-check.md)) — an excision-flavor compile check on the machine that owns each platform — or a scheduled build where a merge-gate tier is too heavy; a rotted escape hatch is the failure mode this section exists to prevent.

**Built for `payments` (2026-08-10, W1) and `zaps` (same day, W1.5).** The keep-green leg is `just ffi-store-safe-check`, one of the async dev-fleet merge-gate check's heavy gates (scope: any `.rs`/`Cargo` change — a stray dep line can put a plane back while *every* flavor still builds). It is now **three-column**, one per interesting flavor of a two-member registry: **store-safe** (`--no-default-features --features store-safe`) asserts 0 occurrences of both planes' kind strings, UniFFI faces **and element-id prefixes**; **Damus** (`--features store-safe,payments`) asserts payments *present* and zaps *absent*; **default** asserts both present. **The element-id axis was added 2026-08-18 and it was not decoration — it was live.** The column had scanned criteria 2 and 5 only, on the reading that a library root paints nothing; a store-safe `libfauna_ffi.so` was meanwhile carrying **9** `post-tip-` + **1** `subscription-claim-` lines, every one a docstring on a deliberately-ungated inert surface (`TipView`/`TipSenderView`, `value_format`'s tip and claim formatters). Fixed at the carrier — the id-naming doc lines now ride `#[cfg_attr(feature = "payments", doc = …)]` — and re-measured on the artifact the same day: **9 → 0** and **1 → 0**. The generalizable rule for the next library root: **a UniFFI cdylib is a criterion-1 surface even though it paints nothing**, because docstrings are part of the artifact and part of the generated face. A one-column absence check passes vacuously against a wrong pattern, a no-op build, or a renamed kind — the same trap the atproto bridge's positive seize-seam witness closes. The middle column carries its own distinct load: manifest text proves `zaps` implies `payments`, and **only an artifact can prove the converse fails** — without it, `zaps` could be an alias of `payments` with every structural pin still green. It runs on the **host** target, so every machine keeps the hatch honest without an Apple toolchain. The structural half (manifest shapes, rule (b), the subset edge, the complement-feature invariant) is pinned by `tests/e2e-unified/tests/test_payments_excision_spine.py`, tier_1, no build required.

**⚠ The wasm flavor root was declared but not excisable until W1.5 — measured, and worth the next member's attention.** W1 landed `payments` at "both flavor roots"; the manifest said so and the structural pin agreed, but nothing ever *built* `fauna-wasm --no-default-features`, and it did not compile: `rpc.rs` imported `fauna_client_payments` and named `fauna_protocol::payments::` unconditionally, so the declared switch was inert. W1.5 found it while adding the second member and fixed it in the same pass (the payments exports now ride their own `#[cfg]`-ed `#[wasm_bindgen] impl` block, as the zap ones do). **The generalizable rule: a flavor's manifest entry is a claim, and the only thing that discharges it is a build of that flavor.** W1.5 verified the three wasm flavors by hand, which left the root exactly where W1 had it minus one bug — hand-verification being the thing that rots. **That gap is CLOSED (2026-08-10): `just wasm-store-safe-check` is the wasm column, the merge-gate check's 15th gate** — see *The wasm root's own column* below.

**The wasm root's own column (2026-08-10).** `just wasm-store-safe-check` is the three-column witness over `fauna-wasm`, built for `wasm32-unknown-unknown`, and it is the only thing anywhere that compiles the excised web bundle. **It is not redundant with the ffi column, and the reason is worth stating precisely because the obvious version of it is wrong.** The two graphs are *not* meaningfully disjoint: of the 42 `fauna-*` crates in `fauna-wasm`'s `[target.'cfg(target_arch = "wasm32")'.dependencies]` block, 40 are also `fauna-ffi` dependencies (measured 2026-08-10) — only `fauna-rpc-wasm` and `fauna-wasm-panic-hook` are wasm-exclusive. The load-bearing difference is the **cfg set, not the crate set**: a host-target build never compiles `#[cfg(target_arch = "wasm32")]` code at all, and `fauna-wasm`'s entire WS-RPC face (`src/rpc.rs`, gated at the `mod`) is exactly that. **That is not a hypothetical — it is precisely the W1 defect**: `rpc.rs` named `fauna_protocol::payments::` unconditionally, and no host build in the workspace could have seen it, `ffi-store-safe-check` included. Two lesser differences compound it: each root resolves the shared crates with its **own** feature set (`fauna-protocol` with `default-features = false, features = ["js"]` here, differently there), and each root's `payments`/`zaps` forwarding is its own declaration, so one root being correct says nothing about another's. Nor is it covered by `wasm-seam-check`/`wasm-chunk-check`: those build the default flavor. **The rule that generalizes to every future root: one witness per flavor root, built for that root's own target — a sibling root's witness is never evidence about yours.** ⚠ **That rule paid out on 2026-08-18, on the criterion-1 axis this column also lacked.** An earlier pass had just fixed the docstring carrier at the `fauna-ffi` root and pinned it there; this root carried the identical defect, unwitnessed, because the column's patterns were kind strings and faces only — the same gap the ffi column had. Measured on the store-safe artifact: `post-tip-` **3** + `subscription-claim-` **1**, all four doc lines on ungated inert formatters (`tipAmount`, `tipCount`, `tipMore`, `claimStatusLabel`), fixed at the carrier with `#[cfg_attr(feature = "payments", doc = …)]` and re-measured **4 → 0**. The column now carries `PAY_ID_PATS` in all three columns, so the ids must be *absent* from store-safe and *present* in the Damus and default flavors. **Two findings worth keeping.** (1) The docstrings are in the `.wasm` this recipe already greps — no `wasm-pack`, no glue generation, so the criterion-1 axis cost this column nothing beyond a pattern array; the row that opened this expected to need a glue build and was wrong in the cheap direction. (2) `web-store-safe-check` cannot cover it either way: its `snapshot()` deletes every `__wbindgen`-bearing file before grepping, so its `post-tip-`/`tipAmount` assertions are about the SPA's own TypeScript, never about the generated face. **Ratified 2026-08-18: a criterion-2 pattern belongs on that axis only if it genuinely excises there** — `web-store-safe-check` dropped its own `tipAmount` entry from that axis's pattern list for exactly this reason (an inert formatter whose glue the `__wbindgen` exclusion deletes regardless of `FAUNA_WEB_PAYMENTS`, so the pattern was satisfied by that deletion alone, never by the flavor build); the element-id patterns beside it stay, because those genuinely do excise per `FAUNA_WEB_PAYMENTS`. Naming a face that never excises on an axis, even when it is a real exported symbol elsewhere, is not a stricter check — it is a tripwire for the next session that revisits the exclusion, wearing the axis's clothes.

**The cost decision, recorded so it is not re-litigated.** The obvious objection to a third column is that wasm builds are the `just web-check` class of work (~30 min, all chunks) and a merge-gate tier cannot absorb three of them. That objection dissolves once the artifact is separated from the *pipeline*: `wasm-pack` is a release build **plus** `wasm-bindgen-cli` **plus** `wasm-opt`, but the witness needs none of them — a plain `cargo build --target wasm32-unknown-unknown` emits the cdylib `.wasm` directly, and that artifact already carries **both** witness axes, the `fauna.payments.*`-style kind strings and the wasm-bindgen export names (`paymentsProvidersSet`, `nostrZapTotal`, …) that are the web twin of the UniFFI faces the ffi column greps. Measured: **79 s for a cold default column** — whole dep graph from scratch, under the build-slot queue on a loaded machine — against the ffi column's "a few minutes cold". So the full three-column witness costs roughly what a *compile-only* check would have, and unlike a compile-only check it can actually see a leak rather than only a broken build. The cheaper alternatives were considered and rejected on that basis: a compile-only three-flavor `cargo check` catches the one defect that already happened (a declared-but-uncompilable flavor) and **nothing** about excision itself, which is the vacuity trap this section already names one level up; a scheduled build — the sanctioned fallback where a tier is genuinely too heavy — buys nothing when the tier can afford the real thing.

**(2) The grep is scoped to the SPA's own output, and that scope has a second, non-obvious exclusion.** SvelteKit copies `static/` into `build/`, so the built tree also holds the wasm chunks — the *wasm root's* artifact, which has its own column and which this recipe deliberately does not rebuild (that is what keeps a web column from costing two full wasm builds). The witness therefore drops every file containing `__wbindgen` — by content, since chunk names are content hashes — and column 2 is what stops that exclusion from ever hiding a real leak.

**(3) The store-safe recipe must not be staleness-gated.** `just web` rides `build-if-stale`; a payments flavor flip changes no source file, so a gated `web-store-safe` would find the tree fresh and hand back whichever flavor was built last — the plane shipping in the artifact a store submission carries, with nothing failing. The witness clears `build/` and snapshots each column's output for the same reason: both flavors write the same directory.

The witness therefore holds those ten at exactly 1 in store-safe (`table_only`: the table and no render) and at least 2 in default (`rendered`), and takes them to 0 in the re-run after the catalog row. **(1) THE MARKUP IS NOT IN THE ASSEMBLY, and an assembly-only scan is a silent false green.** The WinUI XAML compiler does not compile markup into `FaunaApp.dll`; it emits a `.xbf` per page **beside** it (`App.xbf`, `Views/*.xbf`, `Controls/*.xbf`), and that is where every `AutomationProperties.AutomationId` literal lives. The first version of this column scanned the assembly alone. It reported `subscription-provider-` 15/0, `subscription-claim-` 10/0, `post-tip-` 5/0 — numbers that matched **web's and the iOS archive's exactly**, which is what made them so convincing — and it passed **GREEN** with an ungated `post-tip-count` sitting in a page outside `Views/Payments/`. The agreement was worthless as corroboration: 15+10+5 is precisely the 30 ids in the generated const table, all three shells' counts derive from the same ui.yaml, and the scan had never seen a render at all. **What the fixed scan then showed is the corroboration the coincidence was not:** the counts rose to 29 and 19, i.e. **14** rendered `subscription-provider-` ids and **9** rendered `subscription-claim-` ids on top of the table's 15 and 10 — and 14/9 is exactly what the macOS column measures for the same two surfaces. Two unrelated shells agreeing on what they *paint* is evidence; two generated tables agreeing on what one YAML declares is not. `post-tip-` stayed at 5 at the time, all of it table: windows painted no tip surface yet (that gap closed 2026-08-30, and the prefix now reads 13/0 — see point (5) below). **The generalizable rules, both paid for:** *ask where the toolchain actually puts compiled UI before choosing the artifact to grep* — "the app's binary" is an assumption, not a fact, and on this family it is false; and *cross-shell agreement between two witnesses is not evidence when both numbers come from one generated source.* The column now scans the assembly (for the const table) **and** every `.xbf` (for the renders), refuses to run at all if no `.xbf` is found — a layout change would otherwise make every element-id assertion vacuous again — and asserts the payments pages' own `.xbf` files are absent in the store-safe output and present in the default one, so the csproj item-removal is witnessed directly rather than inferred from an id count.

**(2) The two criteria land on different artifacts, as they do on android — but the split falls in a different place.** Android splits dex (criterion 1) from the whole archive (criterion 2) because an APK is a ZIP. Windows splits **managed from native**, because the C# shell spells no `fauna.payments.*` literal anywhere: the kinds live in the native cdylib, and the only C# occurrences are XML doc comments, which — unlike a Rust docstring, which reaches the artifact through UniFFI metadata — never reach IL at all. Asserting kind strings on `FaunaApp.dll` would therefore have been vacuous in **both** columns. The managed side instead carries a UniFFI **face-name** axis, the C# twin of the wasm export names web greps, and it is a real column rather than a decoration: `mod payments_client` is `#[cfg(feature = "payments")]` whole, so a store-safe build's generated face loses all three names.

**(3) The scan had to learn a second encoding.** Every prior column runs `strings -a | grep`, which works on an ELF, a Mach-O and a dex because their string data is UTF-8. A .NET assembly keeps `const string` values in the `Constant` metadata table and every `ldstr` literal in the `#US` heap, **both UTF-16LE**, and `.xbf` stores its strings the same way. GNU `strings` reads those with `-e l`; the `strings` on Windows is `llvm-strings`, whose entire option set is `--all`, `--bytes`, `--radix`, `--print-file-name`. A verbatim copy of tui's recipe therefore reports **0 for every pattern in both columns**. Hence `scripts/strings-utf16.py`, and hence a pin that asserts the scanner's *behaviour* rather than the recipe's text — it is the one claim here that reading the recipe cannot check.

**(4) Both columns wipe `bin/` + `obj/` first, for all three projects.** Both flavors write the same output directory and a flavor flip touches no source. The wipe covers `FaunaApp.Core` too, not just the WinUI project: the define reaches Core (MSBuild propagates no `DefineConstants` across a `ProjectReference`, so each csproj states it and a global `/p:` reaches all three), and Core is where the faces this recipe greps live. Measured incidentally: MSBuild *does* hash `$(DefineConstants)` into its up-to-date check, so a narrower wipe happened to work — which is the kind of hope a gate should not rest on.

**(5) A render-only fix, "verified by diff review only," left the store-safe flavor NOT COMPILING at all — and nobody ran this recipe for a week (2026-08-30 → 2026-09-06).** The tip-surface move (point (1) above) extracted the MARKUP into `Views/Payments/` correctly, but its landing commit's own message admitted the windows/iOS/macOS/web legs could not be compiled from the machine that built it, and so were "verified by direct diff review only." The review missed that `FeedViewModel.ResolvePostTipsAsync` — the VM method the extracted markup's code-behind still calls — invokes the `#[cfg(feature = "payments")]`-gated `FfiFeedManager.ResolvePostTips` with no `#if PAYMENTS` guard, and neither did its one call site in `FeedPage.xaml.cs`. A store-safe build therefore failed `FaunaApp.Core` outright (`CS1061: 'FfiFeedManager' does not contain a definition for 'ResolvePostTips'`) — not a leaked id, a build that does not exist. **The generalizable rule:** a payments RENDER can be excised correctly while a payments ACTION call site one layer under it stays unguarded, because the render-level `test_payments_excision_spine.py` pins are source-pattern checks over markup/const-tables — they have no way to see a VM method's own gated FFI call. The excision boundary is drawn at the ACTION/wire-kind layer, not the display layer: a struct field like `PostSummary.tips` and the value-formatters that render it (`FaunaFfiMethods.TipAmount`/`TipCount`/`TipMore`) are correctly UNGATED (they paint nothing and send no kind on their own), so only the two call sites that actually invoke the gated FFI function needed `#if PAYMENTS`. **This is also why this recipe is worth its ~22 min cost even though it is deliberately not a merge gate (§ below):** a compile break here is invisible to every other gate in the fleet, cheap gate and heavy gate alike, until a session runs it by hand.

**The mutant that grades this column** is an ungated `AutomationId` carrying a payments id, in a page outside `Views/Payments/` — tui's `Element::label("post-tip-count", " ")` translated to markup. It compiles clean in both flavors, paints an empty `TextBlock` nobody would notice, and no compile gate anywhere can see it. Red-verified twice, to opposite effect: the assembly-only column passed it GREEN, and the fixed column fails at `post-tip- = 1`. Re-run it after any change to this recipe's artifact set — it is the only thing that separates "the renders are excised" from "the scan cannot see the renders", and those two are indistinguishable from a green.

**The nest's own column (2026-08-10).** `just nest-store-safe-check` is the same two-column shape over `bins/fauna-nest`, and another of the merge-gate check's heavy gates. ## The App-Store escape hatch (runbook target)

From "Apple blocks the update over feature X" to "excised iOS build submitted" in **hours, not days**:

1. X's cargo feature + platform condition already exist (they ship with the feature — a registry feature may not land without its flag, § Don't do these);
2. the store-safe flavor (a named justfile recipe per store platform) builds the app with X's feature off — a one-line flavor edit if X was not already in the flavor's excision list;
3. the flavor's absence test + test subset run green (they have been running green continuously via the merge-gate tier);
4. submit; the nest and every other platform are untouched (wire-compat posture above).

## Don't do these

- **Don't ship a registry feature without its flag.** A controversial-class feature that cannot be excised is the escape hatch rotting at birth. (`payments` predates this rule and was retrofitted in W1; `zaps` — ratified at OQ-1 with its read surfaces already shipped — is the second retrofit, § Implementation status today item (e).)
- **Don't gate client-side only.** Rendering is courtesy; the nest floor is the gate (§ Evaluation points).
- **Don't add a per-item usage ledger for gating.** Coarse counters only (boundary 2).
- **Don't auto-detect region unilaterally.** Region determination is the shared authority-plane question (region-blocking.md open question 1), answered once — never an ad-hoc per-feature geolocation.
- **Don't build a runtime "master switch" that re-enables an excised feature.** Excision means the artifact cannot do it, period (§ What "completely compiled away" means, item 5).
- **Don't fork the wire per flavor.** One protocol; excised builds are peers without capabilities.
- **Don't let any tier see content.** Quota evaluation reads operation metadata the nest already has; nothing else.
- **Don't re-derive the region plumbing here.** Determination, authority registry, publication/signing, public history, and the unfetchable-policy posture are designed once with region blocking — two planes, one model.

The deciding argument was the plane's own asymmetry: **tier 1 is a ceiling no tier can raise** (composition is the meet, § Composition), so a too-tight constant binds real users with no runtime remedy and costs a release to fix, while a too-generous one is tightened by any of the five tiers below. Err generous at tier 1. Every other cell was ratified as proposed. The numbers below ship in `fauna_core::feature_gate` and are **in force wherever no other tier speaks**. A future revision edits the constants and this table together.

  The reasoning that sets the two sizing classes apart is **the membership criteria themselves**:

  - `payments` and `zaps` are members under criteria **1 + 2** (app-store policy risk, regulatory divergence) and *not* 3. Scale is not what makes them controversial, so tier 1 must not cap a successful creator: its job is an anti-runaway ceiling — a compromised account or a looping client minting claims — set well above any human pattern. Jurisdictional value thresholds (AML and the like) diverge so widely that a fleet-wide constant could only be wrong; those belong to the region tier, which tightens.
  - `p2p-share` is a member under criteria **2 + 3**, where the scale inversion *is* the point: the counterparty bound is the structural gate that makes the Pirate-Bay shape impossible without anyone's goodwill, while operations and volume stay generous enough that no personal use meets them.

  | Feature | operations | counterparties | volume | per-operation |
  |---|---|---|---|---|
  | `payments` | 1,000/day · 10,000/month | 1,000/day · 5,000/month | 21,000,000 sat/day · 210,000,000 sat/month | unset |
  | `zaps` | 2,000/day · 20,000/month | 1,000/day · 10,000/month | 2,100,000 sat/day · 21,000,000 sat/month | unset |
  | `p2p-share` | 500/day · 5,000/month | **50/week · 100/month** | 1 TB/day · 10 TB/month | unset |

  Per-value notes: a viral post can genuinely sell to a four-figure audience in a day, so `payments` counterparties must not bite at 1,000/day; `zaps` arrive *inbound without the account acting*, so their operation ceiling is higher than the payments plane's while their value ceiling is an order of magnitude lower (tips are small, and a rail would clear 2.1M sat/day instantly); `p2p-share`'s month bound binds harder than its week bound (4 × 50 > 100) on purpose, allowing a burst — moving a household onto a shared album — without allowing sustained fan-out; the doubling ratified 2026-08-11 preserved that relationship rather than flattening it. The per-operation cap is unset everywhere because one legitimate file may be arbitrarily large; it exists for a rule-setter to set, not for tier 1. Two tests state the charter's own sizing sentence directly: `the_spouses_moving_hundreds_of_gigabytes_never_feel_a_gate` and `fan_out_to_hundreds_of_strangers_is_structurally_refused`.

  For scale: the charter's illustrative region policy (*"max 50 files/week to max 10 accounts/month"*) is far tighter than tier 1 on the counterparty dimension (10/month against 100/month) — which is the intended relationship, tier 1 being the generous floor a region tightens.
