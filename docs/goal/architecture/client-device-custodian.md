## Client-device custodian (pull) — ratified 2026-08-02; the shared-Rust half is BUILT (2026-08-02)

The second custodian implementor is the owner's own client device — the **third destination kind** (`../behavior/backup-destinations.md` § State & data shape → *Third destination kind* owns the kind, discriminator, enrollment, UI, status semantics, and threat model; this section owns the transport + custody mechanics). It is **nest-mediated pull**, not the no-nest peer case ([`segment-backup-protocol.md`](segment-backup-protocol.md) § Custody grace window (T), its closing paragraph):

- **Pull plane.** The custodian enumerates the owner's per-kind segment state over its own authed USER-class connection (the `fauna.segments.list` control plane) and fetches missing bytes over the segment byte route (`GET /api/v1/segments/{kind}/...` and its `/meta` sibling — permanent, § Byte-source endpoint; a by-CID fetch over `GET /api/v1/blob/{cid_b32}` would need a CID field on `SegmentRef`, an additive wire change). Chunk-granular and source-agnostic by construction — which is what keeps the reserved peer-assisted-pull optimization (`../behavior/backup-destinations.md` § State & data shape → Third destination kind) a pure transport substitution later.
- **Seal reproduction, not artifact shipping.** The custodian derives the owner's seal keys locally from the identity seed (`BackupKey` / `NestBackupKey` per § Writer identity's seal split — both seed-derived) and seals pulled segment bytes into the same convergent chunk format (`convergent_chunk_root()`); the deterministic seal makes its local artifacts **byte-identical** to a nest destination's, so no staging or per-custodian seal work lands on the source nest. Implementation reuses the client-arm leaves the nest coordinator already reuses verbatim (`diff_segments`, `hash_segments_canonical`, `LiveManifestMirror`, the chunk+seal pipeline) with a **local blob-store sink** — a new consumer of those leaves, NOT a revival of the slice-5-retired client→nest-destination writer.
- **Custody = the local store; liveness = latest-per-path + a local grace window.** The custodian derives liveness from what it holds (the same custodian-authoritative principle): latest non-deleted manifest per path stays live; a superseded generation is retained for a local grace window (the T analogue — a bucket-1 constant that may differ from the nest's T) bounded by the user-set capacity cap. At cap, retained generations reclaim first; then the custodian **stops pulling and reports cap-reached** rather than silently evicting live paths. Partial OS eviction is tolerated by construction — content addressing re-converges on the next pull.
- **Check-in.** The source nest projects the custodian's `fauna.backup.status` row from a small USER-class check-in the device writes on its own connection after each pull pass — `fauna.backup.custodian.checkin { destination_id, high_water, held_bytes, cap_state }` (exact payload shapes at impl time; additive-everywhere). The nest computes *backlog* as its head minus the acked high-water and *last synced* as the last caught-up check-in. The check-in is the owner's own device reporting on itself — the adversarial-writer machinery (grace window T, destination-derived charging) does not apply; there is no foreign writer. **A check-in the owner's registry cannot place is refused with the typed `fauna.backup.custodian_not_assigned`** (built 2026-09-29): no row by that `destination_id` (the owner removed it), or a client-device row registered to a different device. That is the authority saying this device is no longer that destination's custodian, so it is a code of its own and never `fauna.protocol.malformed` plus a details string, which a host could not tell from a reworded message. A host reacts by re-reading its assignment at once (the desktop agent: [`apps/sync-agent.md`](apps/sync-agent.md) § A7). The other refusals — a missing `device_id`, a `nest`-kind row — stay `fauna.protocol.malformed`: they are malformed requests, not a changed assignment. An older client maps the unknown code to the generic rejection, which is what it did with the malformed refusal before, so the code is additive (`version-compatibility.md`).
- **The pull never tombstones against a source below its copy (ruled 2026-09-30; the arm and its store record BUILT 2026-09-30, the record's fold into the Backups page BUILT 2026-10-03 in shared Rust and on tui, linux and android — § Implementation status today).** Every pass already reads the source's saved counter beside its listing (`SegmentListing::next_segment_id`, § Cross-location backup protocol → *Wire*) and stores it in the `manifest.<kind>` ledger it writes (`live_manifest_mirror`, the generation the owner-side audit pins) — but it never compared the two, so a source whose counter went backwards read as a source that dropped every segment above its new counter: the pass tombstoned them, the check-in reported the device caught up, and the copy — for a client-device custodian after a total loss, the owner's only one — drained onto the local grace clock. From this ruling a pass compares first: for each family, the listing's counter (`None`, the pre-field reply, counts as zero) against the `next_segment_id_seen` of the ledger the store holds for that set and family; **below** it, the pass is refused as a **source regression** — no fetch, no diff, no tombstone, no mirror write, no check-in (a check-in would tell the nest the device is caught up on a corpus it does not hold), the assignment's covered-folder passes held with it — and the regression is recorded on the store's audit record (the generation held, the counter served, the pass's instant), where the client-device row's `DestinationAuditRecord` folds it into `accepted_regressions`, so `alert_reasons` yields the fifth reason, `SourceRegressed`, and the Backups page says it with no new element ([`../behavior/backup-restore.md`](../behavior/backup-restore.md) § Background Tasks → *Implementation status (audit loop)*, the accepted-regression bullet, owns the record's meaning and the notice; [`../ui/backups.md`](../ui/backups.md) § Audit-alert surface the render). It does not clear itself on the counter (**superseded 2026-10-09, BUILT the same day**): the accepting pass also floors the source, the admitted pass holds the lost copy, and the record outlasts the counter — *Restore* → *Recovery from this device's own store*, part (0′), owns the three rules. A store that holds no ledger for the set has nothing to compare and pulls freely — the first pass. A ledger the store holds live but cannot open (evicted or rotted bytes, awaiting the repair only a running pass makes) compares as the greatest segment held live plus one — a floor the honest source's counter still clears, since it rose past every id it minted — so an unreadable ledger never admits a pass against a corpus-less source. **Why the pull and not the registrar:** a rebuilt box ([`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § State & data shape → *Destination data model* → *A rebuilt box keeps its list too*) is re-registered as a source by the status read's heal exactly as a succeeded box is — on the account plane its list survives to be healed from — so the only party that can tell the corpus-less box from the burned registry is the copy, and the pull is where the copy meets the source's word; the comparison is the audit's pin at the custodian (the same `next_segment_id_seen`, the same source's word), and it costs nothing on an honest pass. **What lifts it:** the re-seed — materialize floors the seeded box's counter to the delivered ledger's generation (*Wire*, the counter's monotonicity), so the next pass finds the counter at or above the held ledger, sees the seeded segments it holds byte-identical as held, and checks in; or, for a box that lived on, the accepted regression's own floor (*Restore* → *Recovery into the lived-in nest that regressed*, part (0)). **Never a data-loss verb:** a refused pass changes the store only by the record, and nothing about the copy is judged here; an honest compaction keeps its counter, so the arm never fires on one — the reason the saved counter is carried at all. **Proof obligation (tier_1, `custodian_pull.rs`, mutation-graded):** a source listing nothing at counter zero against a store holding a ledger at N tombstones nothing, fetches nothing, writes no check-in and records the regression; the same source back at N resumes and the record clears; a counter below N but above zero (a rollback) refuses the same way; the honest empty-output compaction that lowers the greatest live id but not the counter pulls as before; a store holding no ledger pulls from any source. **Tier_3:** the after-loss journey (`tests/e2e-unified/tests/test_backups.py::test_after_losing_the_nest_the_devices_copy_restores_the_mail_onto_the_rebuilt_one`) runs with the custodian re-registered at the rebuilt box before the gesture — the copy is whole when the gesture runs, the restore reports whole, the count stays one.
- **Restore.** Standalone: open the local store under seed-derived keys, no nest involved (BUILT — `custodian_pull`'s dropped-source proof). **Re-seed — RATIFIED 2026-08-22 (design pass, refutable downstream; phases 2 and 3 BUILT for both planes, the ceremony driver, the nest-held pull-back leg and the gestures NOT — § Implementation status today):** the custodian populates a nest that holds no corpus for the owner. The ceremony, its authorization shape and the empty-target rule are owned by `../behavior/backup-destinations.md` § Third destination kind → *Re-seed*; this bullet owns the wire mechanics:
  - **No pre-enrollment write surface exists.** Delivery starts only after the owner is ordinarily enrolled on the target (claim or admission — Re-seed phase 1); every write below rides the owner's own authenticated session. The plane gains no new principal and no new door.
  - **Delivery lands the target in DESTINATION posture over the existing surfaces, sealed under the `NestBackupKey` root.** The custodian opens its local store (the standalone-open capability) and re-seals each segment through the same sink-agnostic `seal.rs` pipeline under the `NestBackupKey`-derived root — the local store rests under `BackupKey` (`custodian_host.rs`, `OwnerSealKey::Client`), which is client-only key material no nest may ever hold, while both roots are seed-derived on the device, so the convergent re-seal is deterministic and produces custody **byte-identical to what the dead source nest's own coordinator would have pushed to a nest destination**. Bytes ride the canonical client-authed bulk-byte plane (`POST /chunks/check` / `/chunks` / `/manifests` — the write extractor's owner-session arm; never a new WS-RPC byte path); custody rides the existing client-authed `fauna.sync.changes.record` reserved-set arm (per-path, omission-safe; destination-derived charging, grace window T, device-pull exclusion and snapshot refusal all structural via the `__` prefix). Covered-folder mirrors push **as-is** — they already are the source's at-rest ciphertext — under their held `__folder/<source-nest-hex>/<folder-id>` names; writer-declared names are safe on this door because the authenticated writer is the owner aiming only at their own actor-scoped custody (the federation door's derive-from-`origin_nest_id` rule guards cross-*source-nest* attribution, which has no analogue here). The reserved sets get-or-create idempotently server-side (the federation relay's lazy-provision rule applied to the owner-authed arm; which existing idempotent door provisions is the build's choice, additively) — under the landing name `__landing/<kind>` since the 2026-10-21 ruling, never the rail's ([`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § __mail Sync → *The landing set*). Every tear mid-delivery leaves an ordinary, auditable, GC-safe backup destination; a re-push converges by content addressing.
  - **Materialization is ONE new USER-class verb — `fauna.backup.custody.materialize` (payload shapes at build time, additive-everywhere)** — flipping one custody set from destination posture to live source posture, per `(kind, scope)` or per covered folder, under the owner's ordinary `fauna.backup.nest_key.grant`: open the sealed chunks under the granted key, reconstitute each segment **pair** — `.dat` and `.meta`, each blake3-verified against the pushed `manifest.<kind>` mirror (`SegmentRef.blake3_hex` / `meta_blake3_hex`) — write the segment area, rebuild `segment_records` from the footers the sidecar carries (the mirror-is-rebuildable property § 6 restore already relies on), one transaction per set. ⚠ **Refuted at build 2026-08-22, corpus widened 2026-08-29.** The corpus then carried `seg-NNNNNNNN.dat` alone, and `FramedSegment::open` **requires** the sidecar (`iter_records()` — the footers — is built entirely from the sidecar's `record_order` + `floor_metadata`, neither derivable from the CARv2 file), so the segments arm could not be built as ratified. Both push arms, the custodian's store and the re-seed leg now carry the sidecar at `segment_meta_rel_path`, a custodian's pre-widening corpus completes itself through the diff's backfill class, and the mirror anchors both halves — § *Cross-location backup protocol* → *The backup corpus carries the pair* owns the mechanics and proofs. The segments arm is therefore unblocked, and **it is BUILT (2026-08-29)** — `bins/fauna-nest/src/backup/materialize.rs`, served as a USER-class kind whose owner is the authenticated connection's actor, so the set a caller names is always their own. It reads the mirror to learn which segments to restore, opens every pair through the nest's own blob store (a local `BlobFetcher`, not a loopback of its HTTP routes), verifies both halves in memory **before writing any of them**, then writes the area and rebuilds the mirror in one transaction. A segment whose sidecar custody is absent is refused by name (`fauna.backup.custody_incomplete`) rather than reconstituted `.dat`-alone. § Implementation status today carries the refusal catalogue and the proofs. A covered-folder materialize is **pure row re-homing, no keys anywhere**: the mirror's manifests + chunks already ARE the at-rest folder corpus, so the verb re-creates the folder set and its per-path rows from custody's `(path_hash, path_sealed, manifest_hash)`; the folder's display name rides the verb payload, and custody deliberately never carries it — where the driving custodian gets it is *Where a restored folder's name comes from* below (amended 2026-09-29: this bullet used to say "the driving custodian's own folder state knows it", which no state a custodian holds after a box loss can honour). **That arm is BUILT (2026-08-30)** — `materialize_folder_set` beside the segment one, dispatched on the set-name axis (the two namespaces are disjoint by construction, and each parser re-derives its own name rather than matching a prefix). It reads the custody set, validates every row before writing any, and re-homes them in ONE transaction that enforces the empty-target rule **at the write, and only there** — a top-of-verb read holds no lock, the lesson the segments arm paid for, so an outer early-out would buy nothing and give the rule a second place to drift. The source's path hash comes from the custody row's own leaf, which both push arms record as that hash hex-spelled; the live rows are minted through the same metered `sync_changes` insert every other record door uses (extracted as `record_sync_change_in_conn` so the axis composes into its transaction instead of forking a second row writer), so dedupe, retained accounting, the owner ceiling and the member cap behave identically. Five folder-axis refusals join the segment ones: `target_not_empty` (the same rule, the same code, still no force arm), `target_not_fresh` (2026-08-31 — the same rule's other half: an empty target carrying `mls_group_id`, `audience`, `website_enabled`, `webdav_enabled` or `web_paywall_tier`, read in the SAME transaction as the id and classified by an exhaustive destructure so a later publication-bearing column cannot join the family unchecked; its own code because the remedy differs — name another folder or clear the property, rather than point at another nest), `custody_unsealed` (a row delivered with no sealed name — recoverable by a pull pass then a re-delivery, which moves no bytes), `custody_incomplete` (a row with no recoverable source address, or a set holding no live custody at all — this plane's answer to the segment axis's missing mirror, custody rows being its corpus), and invalid-params for a missing or reserved display name. A torn run **resumes**: an existing row whose `(path_hash, manifest_hash)` is one this call would itself write is this ceremony's own, and is skipped rather than refused — the folder-axis form of the segment arm's occupied-path classifier, and what keeps a crash from making a set permanently un-materializable. **The folder arm's request carries the owner's signatures (ruled 2026-09-30; BUILT 2026-10-02 — status owner [`writer-signed-change-records.md`](writer-signed-change-records.md) § Implementation status today):** additive fields — the signer key and one signature per row keyed by `path_hash`, in pages, the reply answering how many rows remain — and the arm mints only a carried row that verifies under the target's stored nonce, into a target the shared create helper prepared; the ruling is [`writer-signed-change-records.md`](writer-signed-change-records.md) § Writer-signed change records, ruling (7)(a).
  - **Empty-target rule: materialize REFUSES a target that is not fresh** — the rule and its scope are `../behavior/backup-destinations.md` § Third destination kind → *Re-seed*'s; this bullet owns only its wire face, which is **two codes**: `target_not_empty` (the target holds live records the ceremony did not write) and `target_not_fresh` (the target holds none but carries a publication-bearing property, which the refusal names so the owner knows which to clear). Both are typed refusals naming what exists, neither has a force arm, and the ceremony deletes nothing anywhere (*No user-data loss* structurally; merging into a lived-in account is a named non-goal — succession-class stories own that). A refused custody set survives (the retry's input); a succeeded one is the **landing set**, which the verb reclaims once the landing is whole — ruled 2026-10-21 with the landing name that keeps a delivered copy off the owner's own rail, superseding this bullet's earlier sentence that both survive and reclaiming is the owner's gesture: [`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § __mail Sync → *The landing set* (the reclaim BUILT; its status is there).   - **The nest-held pull-back — the delivery leg when the surviving copy is on another nest (RATIFIED 2026-09-26, design pass; refutable downstream; BUILT in shared Rust 2026-10-06; which apps host it — § Implementation status today).** The three questions the pass had to answer: **(1) The owner's app drives the pull, not the rebuilt nest.** The app is the only party that still knows where the copy is (the destination row survives in the account plane's destination list, `fauna.state.backup` — [`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § State & data shape → *Destination data model*; the nest-side registry died with the box) and the only party authenticated on both sides. A rebuilt nest pulling over federation would need a nest-to-nest read grant at the destination — a new principal and a new door, refused for the reason phase 1 refuses a pre-enrollment write door: no capability gained. **(2) Authorization is nothing new, and no key material moves.** The addresses come from `fauna.backup.custody.list` over the owner's own authenticated connection to the destination (`fauna_client_backup::trust::BackupDestinationConnector` — the audit loop's read, which the source nest's death does not touch because the destination admitted the owner directly, `../behavior/backup-destinations.md` § Held-for-friends); the bytes come off the destination's open content-addressed routes (`/api/v1/manifests/{hash}`, `/api/v1/chunks/{hash}` — the audit inclusion arm's `BlobFetcher`, bearer-less because confidentiality there is the seal's); the landing on the target is exactly the custodian leg's — the owner-session bulk-byte plane behind `BlobPushSink` and the client-authed `fauna.sync.changes.record` reserved-set arm, which get-or-creates the set — the landing set, `__landing/<kind>`, since the 2026-10-21 ruling ([`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § __mail Sync → *The landing set*). The leg opens nothing and derives neither `BackupKey` nor `NestBackupKey`, because **what a nest destination holds already IS the nest-posture corpus** — the source's own coordinator sealed it under the granted `NestBackupKey` root — so every path moves **as-is**, the covered-folder arm's rule applied to both planes, and byte-identity with a nest destination is the identity function rather than a re-seal's determinism. **(3) It composes with enroll-first unchanged**: phase 1 (ordinary enrollment on the target, a write-capable device, the `NestBackupKey` grant) precedes it, and it is one delivery leg beside the custodian's behind the driver's leg seam, so the driver runs the same grant → deliver → materialize order and the verb asks nothing about which leg wrote the custody. **Mechanics.** Per reserved segment set the list names (set names are read off the custody rows — a re-seed cannot ask the dead source which kinds it backed up, `run_covered_folders`'s reasoning): every live row, `.dat` then `.meta` per segment in segment order, the `manifest.<kind>` mirror **last**; per path: fetch the manifest by the row's `manifest_hash`, fetch its chunks, `POST /chunks/check` → `/chunks` → `/manifests` on the target, then record custody with the row's own plaintext `path` and `manifest_hash` — bytes before custody, resumable by content addressing, every tear an ordinary GC-safe destination: `fauna_sync_engine::reseed`'s order, for its reasons. The covered-folder plane rides the same leg: `CustodyItem` additively carries `path_sealed` (2026-10-06 — the target's folder materialize re-homes from it), and the destination's path scrub (`migrations.rs`'s `SCRUB_PLANES`) leaves a reserved set's machine-authored leaf in place — on that plane the leaf is the source `path_hash` hex-spelled, nothing else can re-derive it, and it is a routing key, not content. (The build found the boot scrub nulling it beside the sealed name, so every reboot of a destination made its folder rows unaddressable; the `backup_custody.path` plane now exempts a reserved `__` set.) A row the list cannot address (`path` absent) is refused by name, `custody_unaddressable`, never skipped. Both planes move without a key: a manifest names its chunks' store keys and its `total_size` in the clear, and every fetched byte is verified against the hash that addressed it. **Refuted: the join-and-pull outline.** `backup-restore.md`'s note had the rebuilt nest *join* the destination's reserved set with `read` capability and let fauna-sync ship the chunks; the custodian-authoritative custody model made that impossible by construction on 2026-06-15 — destination custody never enters the device-sync feed (`sync_handlers.rs`'s reserved-set arm answers `seq` 0: write-only custody, never pulled by a device), which is the device-pull exclusion the model exists for. Nothing in this leg reopens it. **Reserved, not built: a server-to-server transport.** The corpus transits the owner's device twice (down from the destination, up to the target) — bounded and acceptable for a one-shot recovery ceremony a human is watching, and it is what lets the leg run from every app, web included (both fetchers and the bulk plane exist on wasm; the custodian leg cannot). If measured restores make that bandwidth the problem, the substitution is one owner-authed USER-class verb on the target taking the destination URL plus the address list, the target fetching the same hash-verified bytes off the same open routes itself; it changes transport only (custody rows, ordering, materialize and its refusals are untouched — the pull path stays chunk-granular and source-agnostic for exactly this reason), and it is not built now because it costs a new verb, a long-running job model with a progress read, and an outbound-fetch (SSRF) posture on a user-named URL, for a bandwidth saving no restore has yet needed. **Honest bounds.** Only what the destination holds arrives — a backlog at the moment the source died is gone, and the status row said so while the source lived; the leg takes the destination's **live head** (`custody.list` is latest-per-path), so an owner whose source overwrote custody before dying rolls the generation back on the destination first (`fauna.backup.generation.restore`, § Custody grace window (T)) and pulls after — the two verbs compose, and the leg never reads retained generations itself; `size_bytes` on the re-recorded row is the destination's derived figure, which the target re-derives and never meters. After materialize the target holds the pulled set redundantly, exactly as after the custodian leg — reclaiming it is the owner's set-delete gesture — and the surviving destination is not yet the target's destination: re-enrolling it is the ordinary five-step § Create sequence (`../behavior/backup-destinations.md` § Implementation status today's enroll bullet), the driver's post-ceremony duty, which on a same-identity rebuild finds the destination-side writer grant already standing. **Proof obligation (tier_3, `nest_backup_coordinator.rs` § Phase 3's harness):** the real nest coordinator delivers A's mail to destination B; a third nest A′ is enrolled fresh (and, in a second arm, rebuilt under A's deployment seed); the leg pulls B → A′ and `custody.materialize` runs on A′; the mail reads back through A′'s ordinary read path and the delivered custody is byte-identical (same store keys, same manifest hashes) to what B holds; a tear after a `.dat` and before its `.meta` resumes to the same end state; a generation rolled back on B is what arrives. The driver-level journey (the user picks the nest destination in the app and restores) is the ceremony driver's witness, not this leg's.

  - **The store is set-qualified — one path namespace for every set this device holds (RULED 2026-09-28, design pass; refutable downstream; BUILT 2026-09-29 — § Implementation status today).** A held row's path is `{set_name}/{path_within_set}` for **every** row: the segment axis rests at `__mail/{scope_hex}/seg-NNNNNNNN.{dat,meta}`, `__mail/{scope_hex}/placement/…` and `__mail/{scope_hex}/manifest.mail` — and `__post/…`, `__calendar/…`, `__card/…` alike, `reserved_backup_set_name(kind)` being the prefix — exactly as the covered-folder axis already rests at `__folder/<source-nest-hex>/<folder-id>/{path_hash_hex}`. The store's namespace is therefore the destination's own `(set, path)` pair joined by `/` — the same two values the nest's `backup_custody` row carries for the same bytes — with no third grammar: one formatter (`held_path(set, path_in_set)`) and one inverse (`path_in_set(set, held)`) beside the store, through which every mover derives and parses a row path; the within-set layout (`SegmentFamily`, `segment_rel_path`, the folder leaf) is untouched and is still what rides the wire. **Why this and not the other candidates.** A bare-kind infix (`mail/{scope_hex}/…`) would be a third naming scheme beside `__mail` on the destination and `__folder/…` in this same store, and leaves a channel-scoped set (`__conv/<hex>`) nowhere to put its channel; one store root per `(account, kind)` fragments what is per *device* by design — the capacity cap, the writer lock, the reclaim sweep's reference set, the audit record and the footprint the apps show — and still needs a set axis inside each root for the folder plane; prefixing only the new kinds is the asymmetry priority #1 forbids. **Every writer writes the qualified form, and nothing reads any other.** No store holds an unqualified row: the pre-ruling read-time fold (an unqualified path read as `__mail/{path}`, and the collapse of rows sharing an identity) was removed in the 2026-09-30 compat-remnant sweep (`compat-remnant-sweep.md`), since no store written before the ruling survives the baseline reset. The index carries the two-number scheme `version-compatibility.md` § Dimension 1 asks of every user-irrecoverable client store (`(schema_version, min_reader_version)` on the index envelope, `#[serde(default)]` → baseline 1), stamped `(2, 1)`; the reader floor is the mechanism a future format change raises, and an index whose floor is past this build is refused, never rewritten. **What the ruling leaves exactly where it is.** `high_water` is per kind, parsed within the kind's own set, so the check-in agrees with the nest's per-`(scope, kind)` `owner_segment_head` and never counts another kind's ids; the custodian's self-audit samples the live paths flat as before (a per-set stratum is now one `split_once('/')` away, and the owner-side inclusion audit's `(folder_name, scope)` stratum is over the nest's custody rows, which this does not touch); the reclaim sweep is by reference set, path-agnostic; the re-seed leg delivers `path_in_set` into `set` for both axes through the one inverse — what reaches a nest is byte- and path-identical to before, so the materialize verb, the removal teardown's `from_serve_kind` and every destination-side reader are untouched; the desktop agent's pipe verbs carry counts and the reclaim/re-seed gestures, never a row path. **Then, and only then, `BACKED_UP_KINDS` grows to `["mail", "post", "calendar", "card"]`** — the sweep, the pull and the re-seed leg all read the one constant, and every nest-side arm is already built (§ Implementation status today). **Proof obligations (tier_1, shared Rust):** a store holding mail rows, then pulling `post` and `calendar`, leaves every mail row live and byte-identical; a qualified `__mail/…` row is never re-fetched by a pull listing the same segment; the re-seed leg delivers each kind into its own set with the within-set path unchanged; `high_water` for one kind ignores another kind's segments.

  - **Recovery into the lived-in nest that regressed — by record, never by path (RATIFIED 2026-09-29, design pass; refutable downstream; the leg, the verb's mail, post, calendar and contacts arms and the floor verb BUILT 2026-09-29; the pass's floor call at acceptance BUILT 2026-10-03; the gesture BUILT on tui 2026-10-08, the other six apps to follow — § Implementation status today).** The trigger is the accepted source regression (`../behavior/backup-restore.md` § Background Tasks → *Implementation status (audit loop)* → the accepted-regression bullet owns the moment, the device-side record and the notice): the owner's source nest came back from an older copy of its data directory, its saved counter went backwards, and a destination still holds the segments the nest lost — live where the climbing counter has not reused their id, retained `T` from each supersede where it has (§ Custody grace window (T)). Neither ratified journey fits — the re-seed ceremony refuses a lived-in target (*Empty-target rule*, no force arm) and the pull-back assumes a rebuilt one — and no by-path landing can: after the rollback the nest and the copy disagree on what one segment id holds. **The ruling: the copy's lost records come back as records.** A record's identity is the CID of its bytes (`message-segment-store.md` § Record identity per kind), a content record holds only what its id determines while everything mutable lives in the placement journal (that doc's § Invariants binding any kind whose body moves out of a SQLite column, invariant 2), and compaction already moves records between segment files under fresh ids with their CIDs intact — so a segment id names a container, not a record, and a lost record needs no id back, only its bytes, its mailbox and its flags. Three parts, in order. **(0) The floor — the acceptance stops the overwriting.** When a device's pass accepts a source regression it calls one new USER-class verb on the source, `fauna.segments.counter_floor { kind, scope, floor }` (name and payload at build time; the serve-kind tag names the family, `mail-placement` for the journal, so each family floors on its own key), raising the source's saved `KindManifest::next_seg_id` to the device's **pinned** generation — the pre-rollback counter the device read off a ledger the source itself sealed, never the destination's served number, so a hostile destination cannot inflate it. It is the floor materialize already applies at re-seed (`SegmentManager::adopt_segments`' counter-floor half, factored out to stand alone): monotonic, idempotent, taken under the scope's segment lock so an open segment finishes at its id and the next rotation takes the floor; a floor the id space cannot honour is refused invalid-params, and the caller's worst case against its own nest is spending ids — no capability an owner's device lacks today. Bucket 1: no human chooses it. Effect: every id the copy numbered is spent on the source too, so a lost segment not yet overwritten stays live at the destination for as long as the owner keeps the destination, charged like any live row; only the generations overwritten before the acceptance run on the `T` clock, which is why the notice's record stands while the destination holds lost custody rather than for a fixed window (the loop's owner doc, the accepted-regression bullet's revision). **(1) The delivery leg — the pull-back's, generation-inclusive.** The owner's app drives, exactly as the pull-back's question (1) rules and for its reasons; nothing new is authorized and no key material moves — what the destination holds is the source's own nest-posture ciphertext under the `NestBackupKey` root the source holds a grant for. Per reserved set of the regressed kind, both families: the leg lists the live rows (`fauna.backup.custody.list`) and the retained generations (`fauna.backup.generation.list`, the same owner-authed connector), fetches every generation of every path by manifest hash off the destination's open routes — skipping a segment the source already holds byte-identical per its own `fauna.segments.list` (both hashes), an economy only; the verb below owns correctness — and lands each on the source over the owner-session bulk-byte plane and the client-authed `fauna.sync.changes.record` reserved-set arm, into the source's **landing set** for the kind — `__landing/<kind>`, [`../behavior/reserved-folders.md`](../behavior/reserved-folders.md) § __mail Sync → *The landing set*, ruled 2026-10-21 — under the path it had at the destination. **Every copy is opened sealed-only (ruled 2026-10-13):** the destination names every manifest the leg fetches, and the hash check proves only that the served bytes are the ones it named, so a self-built *plaintext* record or ledger there would be opened, resealed under the owner's `nest_root` and laundered onto the source as owner-sealed custody — the leg's reader sets `FileDownloadKeys::sealed_only`, a plaintext copy fails the run loudly (`PLAINTEXT_REFUSED`) and nothing of it lands; a reserved set's copy is always the source's nest-posture ciphertext, so no honest copy is refused (the rule's owner: `../behavior/backup-restore.md` § Security Properties → Integrity). A path recorded twice supersedes, and the source's own window retains the displaced generation, so the order among generations is immaterial and the verb reads live and retained rows alike; the content family lands before the journal's and every mirror generation last. Resumable by content addressing, every tear an ordinary GC-safe destination, web-capable like the pull-back, and no custodian store is touched (the leg runs in the app; the desktop agent's IPC exists for the store's single writer, which this never is). **(2) The verb — `fauna.backup.custody.recover`, USER-class on the source, materialize's sibling, owner-scoped like it.** It never refuses a target for what the target holds: that is the whole difference from materialize, and it is why no force arm is added anywhere — a lived-in target needs a different verb, not a weaker rule. Order, materialize's mirror image: the refusals that need no bytes (`not_enrolled`, the set shape, a kind in `BACKED_UP_KINDS`); then every mirror generation the set holds, live and retained, both families, opened under the grant; for each content mirror every pair it names must be present among the set's rows by the hashes it names — a missing half is `custody_incomplete` naming it, cured by re-delivery, unless the target itself holds that half byte-identical under the mirror's hash — the leg's skip — which then stands in for it — and every pair is blake3-verified in memory and admitted through `FramedSegment::open` (the re-hash-against-the-CID predicate of § Record identity, the one kind-agnostic admission check) before anything is written. **The recovery set** is every record those segments hold whose CID the target holds in no `segment_records` row of that `(scope, kind)`, live or tombstoned: the target's own history wins, so a message the owner deleted after the rollback stays deleted and a record the source kept, compacted or not, is never duplicated. **The write is the ordinary one, per record.** Each recovered record is appended verbatim below the typed boundary — the compaction carrier: bytes and CID untouched, the sidecar's own floor metadata and bucket carried, save the floor's two local facts, `seq` and `stored_at`, restamped into the footer as into the mirror row exactly as the relay's verbatim carrier restamps them (so a later rebuild from the footers recovers the same cursor) — into the source's open segment under its climbing counter, and its mirror row is written by the kind's canonical insert helper (the whole column set; `stored_at` now, a fresh relay `seq` — to a puller it is a new arrival, which it is). For a kind with a placement journal the placement lands **in the same transaction as the mirror row**: the verb replays each delivered journal mirror generation into a scratch state it never writes to the target's journal area, takes for the record the placement the newest generation naming it gives — mailbox and flags; the UID and modseq it had are not restored, they are the lived-in target's to mint — and files it through the same door an arrival takes, under a fresh UID in that mailbox, created by name if the owner removed it after the rollback. A mail record no delivered journal names lands in the inbox unseen — the arrival's own landing, and safe here where the re-seed's consequence (3) refuses to guess: no later pass brings this journal, and a record live in no mailbox for ever is the only alternative. A calendar or contacts record no journal names is not appended (`unplaceable`, counted in the reply): its row is built from the journal, and content without one is what the orphan reaper tombstones — what "names" means for those two kinds, and the collisions their placement can meet, are the next bullet's. Posts recover as records alone. Because held now implies filed, the verb is idempotent by construction: a re-run recovers what is missing and nothing twice, and a tear after k records leaves k ordinary records live and filed for the re-run to finish. It ends by applying the floor of (0) to the greatest `next_segment_id` over the mirrors it recovered (a no-op after an accepted regression; the guard for a recovery driven before that floor landed) and replies with counts — recovered, already held, filed, inboxed, unplaceable — and the floor. No bridge precondition: appends and placements are what the bridge serves alongside every day, and a mail client sees the recovered messages as new ones over the ordinary QRESYNC path. Never `target_not_empty`, never a force arm, never a wholesale DELETE. **Rejected:** (a) the local snapshot restore's kind-level replace — the copy's live rows mix the source's post-rollback writes with what it lost, so no whole state exists to replace with, and the replace would destroy exactly the writes *No user-data loss* protects; (b) renumbering with a re-pointed journal — the journal points at CIDs, not segment ids, so re-pointing is the wrong axis and re-filing the right one; (c) a generation roll-back on the destination followed by a forced materialize — it rolls the destination's live head back over the post-rollback writes and needs the force arm the rule refuses. **Threat model:** the pull-back's — the owner's app, the owner's sessions on both sides, the destination's open hash-verified routes, no new principal, no new door, no key material moved; the floor verb and the leg's writes are owner-authed acts against the owner's own nest, bounded by what an owner's device may already do to it. **Post-recovery duties, the leg's:** the driving device clears its own accepted-regression record on a whole reply; at the destination it tombstones the recovered paths its live ledger does not name (the same reserved-set arm, retained `T`, reversible by `generation.restore`), so the copy stops charging for what the source now holds under new ids and re-uploads by its next pass; the delivered set on the source is redundant, and reclaiming it is the owner's set-delete gesture, as after materialize. **Honest bounds:** the recovered messages carry fresh UIDs, so a mail client that cached the old ones sees them as new;   - **Recovery's calendar and contacts arms — the three collisions ruled (RULED 2026-09-29, design pass; refutable downstream; BUILT 2026-09-29 — § Implementation status today).** The two DAV kinds recover through the verb of the bullet above with one difference in what *filed* means: a mail record is filed *somewhere*, an event or card is filed *as the current version of one resource* — `(collection, UID)`, the row the DAO keys on and the one thing a collection holds only once (`../behavior/caldav-server.md` § Validation → *UID uniqueness per calendar*; `../behavior/carddav-server.md` for cards). Identity is mail's: a record's CID is the content hash of its sealed envelope (`message-segment-store.md` § Record identity per kind), so admission (the carv2 re-hash) and the held-ever check are kind-agnostic and only the placement is the arm's own. **What the journal says.** The verb folds every delivered journal generation — live and retained, in any order — and keeps per `(collection, UID)` the placement or tombstone with the **highest change number** (both are numbered on the collection's one counter, so a tombstone above a placement is a later deletion and a placement above a tombstone a later re-add); absence from a generation is never a deletion, because the destination's newest generations are the regressed source's own post-regression pushes and are silent about everything it lost. A delivered record is **placeable** when that fold names its own `event_id`/`card_id` (the floor's — every record carries it) as the current version of its `(collection, UID)`; every other record — superseded before the regression, deleted before it, or never journaled — is `unplaceable`, counted and not appended, since its row is built from the journal and seating it would put a second version of one UID into a collection. Placement gives the collection and the effective sidecar (`encrypted_fauna_ext`, carried verbatim onto the row) and nothing else: the ETag and change number are minted by the ordinary door, exactly as mail's UID is. **(a) The collection holds the UID already — the later write wins, by server receive time.** A live row for the record's `(collection, UID)` under another record is one of two things the target cannot tell apart by content: the stale pre-regression version the lost record superseded (kept by the older copy of the data directory), or a version the owner's device wrote *after* the regression (a re-upload from a cache, a fresh edit). Every row and every content record carries the server's own receive time (`created_at` — the same clock on the same nest; the row's is the target's own and the record's rides in a floor the mirror's hash binds, so a destination forges neither), and every lost record was born after the copy the target came back from, so the rule is the DAO's own: a row born **no later** than the lost record is the version it replaced, and the record files through the same replace-by-UID door a PUT takes — the old id tombstoned into the expunge table, the row replaced, the change number bumped, the displaced record tombstoned if nothing references it — doing now what the source did then; a row born **after** it is the owner's post-regression act and stands: the lost version is not appended and counts `already_held`, which for a DAV kind therefore means *the target holds the record, or holds its resource in a later version*. The target's own tombstone for the resource reads the same way: an expunge stamped after the lost record's birth is a post-regression deletion of that UID and wins (`already_held`); an older one is history the pre-regression re-add already overrode, and the record files. A tie in seconds is a pre-regression pair (a restore takes longer than a second) and files. **(b) The collection is gone — created by id, as mail creates a mailbox by name.** A calendar or addressbook the fold names that the target lacks — lost in the regression, or removed by the owner after it — is provisioned through the ordinary door under its own id with the fold's `encrypted_metadata` and journaled, before the first record files into it; one the target holds under other metadata keeps the target's (the owner's later act, or a rename the regression lost — no merge exists, and the owner renames in seconds). A collection the owner deleted *before* the regression can come back this way, with the records a delivered generation older than the deletion still names — a resurrection, never a loss, and the owner deletes it again. **(c) The change counter is floored, never restored.** ETag and change number are the target's to mint, but a CalDAV or CardDAV client holds a sync token from before the regression — a change number the regressed collection has since reused for post-regression writes — and an incremental sync asks only for numbers above it. So before the first record files into a collection, that collection's `highestmodseq` (and `ctag`, kept in lockstep) is raised to the greatest `highestmodseq` any delivered generation's fold holds for it: the pre-regression counter as the source's own sealed journal pins it, monotonic and idempotent — part (0)'s floor applied to the collection's counter — so every recovered row is numbered above every token a client could hold and reaches it as a change; a client whose token is above the counter (a collection recreated at 1) is already sent to a full resync (`../behavior/caldav-server.md` § Restore divergence). Post-regression rows numbered inside the reused range stay invisible to such a client — the regression's own damage, which the accepted-regression notice owns, not the recovery's to repair. **The write, per record:** the collection prepared as above; the record appended verbatim under the target's counter and its mirror row written by the kind's canonical helper, with the resource decision and the row's insert-or-replace in **the same transaction as the mirror row** through a transaction-taking form of the replace-by-UID door; the `PutEvent`/`PutCard` journaled after the commit, as the arrival's is; the collection's change notification sent as a PUT's. Held now implies filed, so the re-run and the torn run are idempotent as mail's; `filed` equals `recovered` for both kinds and `inboxed` is always zero. **Rejected:** (i) filing a colliding lost version as a copy under another UID — the UID is inside the sealed body, and a nest that cannot read it cannot rewrite it; (ii) refusing the verb on a collision — one owner-made edit would hold the whole recovery hostage; (iii) comparing versions by change number across the regression — the regressed counter reuses numbers, so a post-regression write and a lost pre-regression one are incomparable by it, which is why the rule reads the receive time; (iv) treating absence from the newest generation as deletion — that generation is usually post-regression and knows nothing of what was lost. **Honest bounds:** a lost edit the owner re-made after the regression keeps the re-made version (mail's re-fetch bound, with the UID forbidding the second copy mail tolerates); a pre-regression deletion whose tombstone the retention prune had already dropped from every delivered generation is not honoured, and the event comes back; a deletion the regression itself undid (of a record the older copy still holds) is not replayed — that record is `already_held`, as for mail. **Proof obligation (tier_3, the mail proof's harness in `nest_backup_coordinator.rs` with `put_events` / `put_cards`):** the copy taken at M; after it a new calendar with events, an edit of a copy-era event, and a delete of a post-copy event; the regression; after it the owner re-uploads one lost event's UID and deletes one copy-era event; floor, leg, `recover`; then every lost event reads back in its calendar exactly once by CID, the copy-era event's row replaced by its lost edit (the old id in the expunge table), the re-uploaded UID keeping the post-regression version, the pre-regression delete and the post-regression delete both standing, the new calendar back under its id and metadata, a sync-collection from a pre-regression token listing every recovered event, the counts as ruled, a second `recover` recovering nothing, and the torn run re-running to the same end; the card twin verbatim. Tier_1 beside the verb: the per-resource fold (highest change number, absence never deletes), the receive-time rule both ways with the tie, the expunge rule, the missing-collection creation, the counter floor, and the `unplaceable` count — each red under its mutation.

Two mechanics of this section became concrete there and are worth stating here rather than in the UI doc: **the nest computes `caught_up` itself** — the device reports where it got to and the nest, the only party that knows its own head, decides whether that is level, so a check-in made while still behind neither advances nor clears the row's "last synced" stamp; and **`backlog_count = head − high_water` saturates**, because a custodian can legitimately sit *ahead* of the nest (its pass sealed segments the nest has since compacted away) and an underflow there would render as a backlog of four billion. The nest's head is derived the same way the custodian derives its own `high_water` — greatest segment id held, plus one — deliberately, since two differently-derived figures subtracted from one another is how an off-by-one becomes a permanently-lagging status row.   **The write refuses on disk, not only on the mirror (hardened 2026-08-30).**
  *"Deletes nothing anywhere"* was a property of the caller's state, not of the
  write: the segment area was written with the shared atomic helper — write-tmp
  plus **rename**, and a rename replaces. The empty-target rule that was supposed
  to make that safe reads the SQLite mirror, and DB rows are not disk files. Two
  gaps followed. A scope whose records are all tombstoned counts zero live while
  its `seg-*.dat` files remain, because purge is SQL-only and the files die later
  in the store's own GC. And the rule ran at the top of the verb, a whole corpus
  fetch-decrypt-verify before the write with no per-scope lock held, so mail
  arriving in that window created a segment at the same base id a started-empty
  corpus's own ids use — making collision the default case. Either arm ended in
  destroying records the owner actually had, and left the mirror pointing at
  bytes that were gone (the rebuild only inserts; the wholesale DELETE lives in
  `restore_mail`, not here). Three guards now, and the middle one is not
  redundant: `finalize_open`; **the empty-target rule re-asserted at the write**,
  which is what catches arrived mail whose ids do *not* collide and would
  otherwise merge a corpus into a scope that has since become lived-in; and every
  destination path checked free before **any** half is written, each half then
  written `create_new`. The pre-flight keeps *verify-everything-before-writing-
  anything* true of this block too — refusing halfway would leave orphan halves
  the next attempt then refuses on. This restores the discipline the rest of the
  directory already keeps (`FramedSegment::create` opens `create_new`; the store
  *removes* an orphan rather than writing through it, after a 0-byte
  `seg-00000040.dat` once permanently 451'd all mail for an actor), and it takes
  the same trade: a crash mid-write can leave a partial file. **That last clause
  used to read "reclaiming it is the same explicit step the store already takes",
  and it was never true of this path** — the store's reclaim is keyed on the
  `.dat`, so the lone `.meta` this write order makes likeliest (meta first, each
  half `sync_all`'d with its parent directory fsync'd) is invisible to it; and it
  fires only inside an APPEND's rotation, which would make the scope non-empty
  and trip the empty-target rule instead. With no operator role to clear it by
  hand, an unreclaimed orphan was a client-reachable, client-UNRECOVERABLE state
  — a bug under [`nest/common.md`](nest/common.md) § Client-state recoverability,
  in the verb whose whole purpose is recovering from disaster. What clears it is
  the ceremony's own guard 3, below.

  **Guard 3 classifies an occupant instead of refusing every one of them
  (hardened 2026-08-30).** The discriminator is deliberately narrower than "this
  scope holds no live records, so anything here is fair game" — true today and
  still too weak to delete by, since it licenses removing bytes whose provenance
  was never established. What IS provable is whether a file is this run's own
  interrupted write: a crash leaves a **prefix** of the half being written (the
  empty file being the limiting case, and the exact 0-byte shape of the live-nest
  precedent), and foreign content is not a prefix of ours. So an occupant that is
  a prefix of what this run means to write is reclaimed and rewritten; a pair
  that is *already adopted and complete* is **resumed** — an adopted segment is
  committed, so it is never deleted, and the run skips the rewrite and finishes
  the mirror the crash interrupted; anything else is refused as before. That
  second arm closes the window the adopt step itself opened: halves on disk and
  adopted, with the `segment_records` rebuild never committed, is a state a retry
  now completes rather than refusing forever. The refusal string no longer tells
  the reader to "reclaim it and retry" — an instruction addressed to a role that
  does not exist ([`../principles.md`](../principles.md) § One configuration
  surface); it names the one action a client has, re-delivering the set from the
  custodian.
  **And the corpus survives the first mail that lands on top of it (hardened
  2026-08-30).** The guards above stop the ceremony destroying what is already
  there; this is the mirror-image hazard — the ordinary mail path destroying
  what the ceremony just wrote, one delivery after the flip. Materialize wrote
  the halves itself and rebuilt the mirror, but never advanced the per-scope
  **kind manifest**, and a target that has never appended still reads
  `next_seg_id: 1`. The store reclaims whatever `.dat`/`.meta` sits at the id it
  is about to open — correctly, since a *committed* segment can never
  legitimately be there, an invariant every other writer earns by advancing the
  counter as it writes. So the first ordinary mail rotated onto `seg-00000001`,
  found the corpus's first segment and unlinked both halves while doing textbook
  crash recovery, on the very first mail the re-seeded nest received. The fix is
  in the writer, never in the reclaim: `SegmentManager::adopt_segments` makes
  the ids live and moves `next_seg_id` past the highest of them — and, since
  2026-09-28, up to the ledger's own generation
  (`LiveManifestMirror::next_segment_id_seen`) when that is higher, so a
  re-seeded nest never re-mints ids the dead nest minted and retired, and its
  first ledger reads as a continuation to every device that pinned the dead
  nest's — called as soon
  as the halves land and **before** the mirror rebuild, so a crash between the
  two leaves segments protected-but-unserved rather than served-by-rows-pointing-
  at-bytes-the-next-append-deletes — and protected-but-unserved is recoverable
  because guard 3's resume arm above completes it on the next attempt, which is
  what makes that ordering a choice rather than a trade. It updates the CACHED per-scope state, not
  just the file: the ceremony's own `finalize_open` has already loaded the
  manifest, so a disk-only write would keep handing out `next_seg_id = 1` from
  memory and the collision would fire with no crash at all.

  just the mail incident above):** any writer that lands *committed* segments
  outside the ordinary `append_record_with_bucket` / `compact_with_filter`
  path MUST call `SegmentManager::adopt_segments` for those segments —
  adopt-before-mirror-rebuild, the same ordering materialize uses — before
  they are served. `bins/fauna-nest/src/backup/materialize.rs`'s

  inherits this obligation, not just mail's history. Skipping it is not a
  new failure mode — it is this exact incident, reproduced on that kind's
  own corpus the moment its first ordinary write rotates onto a
  never-adopted id.

- **The custodian's local copy now HEALS (2026-09-20)** — § Client-device
  custodian (pull) → *Custody = the local store* has always read "partial OS
  eviction is tolerated by construction — content addressing re-converges on
  the next pull", and until now nothing re-converged anything. Three defects,
  all in `libs/fauna-sync-engine`, each red-first and mutation-verified:
  - **The wrong generation could stay live.** `CustodianStore::put` tested its
    duplicate against *any* non-deleted generation rather than the live one, so
    content that went A → B → A inside the grace window left B live and a
    standalone restore handed back replaced content; a tombstoned path the
    source relisted unchanged stayed tombstoned for ever. It now compares
    against `live_at`, the module's one liveness derivation.
  - **Missing bytes were never re-fetched.** The self-audit found them and the
    check-in reported them — an alarm with no remedy behind it, on the one
    destination kind whose whole argument is restoring with no nest alive. The
    verdict now carries its failing paths (`AuditRecord::failed_paths`), the
    next pass re-enters them into the segment diff and skips the covered-folder
    axis's unchanged-head early-out for them, and `CustodianStore::put_repair`
    rewrites their bytes unconditionally — eviction leaves a chunk absent and
    rot leaves it present-but-wrong, and the convergent put that trusts a file
    at its content address heals neither. A flag leaves the list only on
    **proof** — the pull re-produces the path, or a later audit re-samples it
    and it passes — or when its path stops being live; never on attempt, and
    never because a later audit, sampling only `AUDIT_SAMPLE_K` of the live
    paths, did not open it (`record_audit` keeps every standing flag the new
    report did not sample). The *verdict* stays the audit's to change, so a
    healed store still reports failing until the audit re-samples — and every
    self-audit re-opens each still-live standing flag on top of its
    `AUDIT_SAMPLE_K` rotating paths (2026-09-27), so a flag whose repair
    re-fetch keeps failing (the source can no longer serve it, or the cap
    refused it) holds the verdict, and every check-in, failing; a flag the
    pull re-produced passes that re-open and leaves on it.
  - **Two passes could overlap on one unlocked store.** On mobile the scheduled
    `run_all_kinds` and the foreground push loop genuinely run together, and
    `reclaim`'s sweep deletes by reference set — so one pass's in-pass reclaim
    could sweep the other's written-but-unindexed blobs, and two puts could lose
    each other's index row. There is now one writer lock **per store root**
    (process-global, keyed by root — handles on one root are routinely several),
    held across put / repair / tombstone / backfill / reclaim / audit-record
    writes and across no read, so a restore never queues behind a pass.
    `fauna-ffi`'s `ActivityGuard` is unchanged: it covers the *manual* reclaim,
    which is the case this lock does not replace.
  - **Follow-ups (2026-09-23).** *Reclaim* had the same-second tie liveness
    had: A → B → A in one pass gave the first and third rows one
    `(path, manifest_hash, stored_at)` identity, so expiring the superseded A
    also dropped the live one and left B the path's latest. Identities are now
    unique — a writer re-recording a held identity replaces the earlier row and
    appends the new one last (`push_generation`), and `held` collapses a twin in
    an older index to its newest occurrence. A repair is charged at what it
    **adds** (`CustodianStore::charge_for`: nothing, for a half already live at
    that manifest — the mirror included), so a converging repair heals at the
    cap instead of being refused there. And a flagged segment re-fetched only
    for repair whose fetch fails is skipped (`PullReport::unrepaired_segments`,
    flag kept) rather than aborting the kind's pass; a segment never held
    still stops the pass, because skipping it would let `high_water` rise over
    a gap.
