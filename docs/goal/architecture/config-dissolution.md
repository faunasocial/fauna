## Migration + compatibility (W7)


### The `__config` dissolution schedule (ruled 2026-08-12; refutable until the first E3 slice builds)

R13's user-deferred migration sequencing, scoped (analysis record: the
2026-08-12 dissolution-design doc, internal plans tree — tracked internally,
not shipped; frozen). The
schedule moves every remaining `UserConfig` field from the CAS blob onto
per-kind plane entries under four binding principles: **(P1)** a rail move,
never a merge redesign — each field keeps its shipped merge semantics exactly
(every rule in `format_user_config.rs` was chosen against a named
loss/resurrection hazard); **(P2)** kind granularity is the **invariant
closure** — fields sharing a merge-time invariant share a kind (the
destination-mark `Removed` prune reaches into `backup.destinations`, the seed
scalar folds into the seed map, the owner chain gates the grant-event union —
three closures a field-per-kind reflex would break); **(P3)** mixed-rule
composites embed a per-kind `updated_at` inside the value so their internal
latest-wins halves stop riding the blob-global stamp; **(P4)** decode posture
per policy — CrdtPerField kinds `deny_unknown_fields` (a CRDT arm re-encodes;
tolerance would silently strip a newer field; where a value type must stay
blob-tolerant until step (6), a strict round-trip does the same job — *The
backup state* below), LatestWins kinds decode
tolerantly (LWW adopts bytes verbatim); **(P5)** two bridge modes — LatestWins
kinds use the shipped **markered** bridge (`plane_mirrors`), CrdtPerField
kinds bridge **marker-free** (the join is the reconciliation in both
directions; markers never grow entries for join kinds — and, since the 2026-09-27
reschedule, P5 binds the E1 cluster alone: an E3 kind never bridges, M/C
below; since closure step (5), 2026-10-01, the bridge is deleted and no kind
bridges); **(P6)** the nest is
untouched at every phase (kinds are blinded; the blob rail's nest half serves
unchanged until the contract phase — scheduled before the 2026-10 baseline
since 2026-09-27, M/C below).

**The kinds — the registration table, REFRESHED 2026-09-28 over the current
struct (*The closure order* below, step (3), E3's first act).** Strings are proposed, frozen only at first
seal; policy, rung and epoch freeze with the string. Every E3 kind is
**fleet-only** (the ladder's default rung — no Secret-free pin, the
reverse-direction conformance test refuses one; each field's rung reasoning:
[`account-data-taxonomy.md`](account-data-taxonomy.md) § The audience ladder →
*The `UserConfig` disposition*) and seals under **`GenerationTip`**
([`owner-key-material.md`](owner-key-material.md) § Path A-sibling-2: no
fleet-only kind seals a production entry under the root-derivable-forever
branch; only the bootstrap machinery is `Gen0`), an account-scoped row
(`TipRowScope::Account`) whose first production write resolves or mints a tip
at the door. The *delegates to* column names the shipped rule (P1) the plane
arm calls — where that rule still lives inline in `merge_user_configs`, the
slice lifts it onto the value type (`<Type>::merge`) byte-for-byte and the blob
arm calls the same function, so the two rails cannot drift; *posture* is P4's;
*web* says whether the kind's consumer set reaches `libs/fauna-wasm*`, in which
case the slice waits for *The closure order* step (2) — **every kind but one
does, so the lead slice is the one that does not.** The E1 cluster
(`moderation`, `sync_prefs`, `personalization`, `delegation`) is registered
delegable since 2026-08-11 and is not repeated here.

**Bounded rows (ruled 2026-09-28; the lead
slice's e2e run refuted the default).** Every plane entry seals under the

that grows with use. The default "one row per account at key `self`" holds
only for a record whose size is so fixed (a settings cluster, a scalar

envelopes or key material** — `group-share-ceremony` (one sub-record per

freshest, the ones still owed) with a monotone marker for what it dropped.

too (the tree-wide rule, its mechanism and its guard are

**The ledger (ruled 2026-09-29) — the third application, and the one that
settles the chain's authorship on the plane.** `fauna.state.succession-ledger`
splits into five row families, the key's first segment dispatching as the lead
slice's does. The grant log and the three mark planes are **one row per
entity**: an event row (`event/<grant id>/<sig>`) holds one signed `GrantEvent`
and is write-once — Ed25519 is deterministic over the content, so two honest
writers never differ and a differing value under one key is a row-content
refusal; a mark row (`grant-mark/…`, `member-item/…`, `filter-mark/…`, each
keyed on the row and its raising event exactly as the blob's per-key unions are
keyed) holds one mark, its arm the verdict-precedence minimum. The "bounded set
plus a monotone marker" remedy is **refused for both**: the log is append-only
forensic history whose whole point is that nothing erases it, and an adjudicated
mark is kept, never deleted, by the ruling that made re-runs idempotent
([`../behavior/succession-aftermath.md`](../behavior/succession-aftermath.md) §
Adjudicating what the aftermath carries across) — so nothing in either may be
dropped, and per-entity rows are the only bounded shape. The chain (`actor_id` +
`prior_actor_ids`) is the **one row that grows, and it stays ONE row**
(`chain`): it grows by 34 B per succession *ceremony* — an identity-lifetime
event under a `RecoveryKey`, never a use-time count — and the size pin seals a
512-succession chain under half the cap. Per-link rows keyed by the retired
identity were refused: `one_owner_chain` is a predicate over two whole chains,
and the case it exists to refuse — a fork, two successors of one predecessor,
the thief's race — is exactly the case per-link rows would collide on and force
a per-key choice the fold has no basis for. **`one_owner_chain` stays, as the
`chain` row's plane arm** (P1: the gated sorted union and the successor pick,
byte-for-byte; a pair the gate refuses is `BadValue`, the row-content refusal
the walk skips on every reconcile, so each replica keeps its own chain — the
blob's "two chains never converge", kept), **and the tip does NOT subsume it**:
a plane entry's signature proves that a device's writer key signed it and the
tip proves possession of a generation key — possession again, as the blob's
unseal was, and the pre-succession thief holds every pre-succession generation
(R14 excludes the retired identity from the generations minted after the
ceremony, not from the ones it held); the owed authoring-chain check
([`owner-key-material.md`](owner-key-material.md) § Implementation status today,
the `DeviceAuthorization` covering the writer) will prove that the writer was an
authorized device, never whose chain a value describes. The gate is about
content and stays a property of the value type. What moves is *where* the
union's allowed-signer clause runs: on the blob at merge time, over "our chain
plus a linked peer's"; on the plane at READ, over the folded chain —
`SuccessionLedger::fold` seeds the chain with the runtime's own identity, joins
the stored `chain` row through the chain arm, and retains only the event rows
verifying against the folded `actor_id` ∪ `prior_actor_ids`, which is the same
set. A stranger's event row is stored and invisible; it costs a row any tip
holder could write anyway — the plane-wide R14 exposure the authoring-chain
check closes, not this kind's. **The door refuses** an event verifying against
no id of the attested set — this identity plus `AccountRegistry`'s attested
predecessors ([`account-data-taxonomy.md`](account-data-taxonomy.md) § The
generation machinery → *The source of `prior`*; `retain_attested_grant_events`'
rule, moved to the door) — and any value not naming its key. **The succession
fold of the row — the `__config` leg's plane form.** No re-seal: pre-succession

*Rotation*, the succession rider; history is never re-sealed forward). The
successor's runtime, in the post-store-ready pass it runs once at its

**The mail plane (ruled 2026-09-30) — the fifth application, and the one that changes a shipped merge
rule.** `fauna.state.mail` splits into two row families, the key's first
segment dispatching. The credentials are **one row per credential**

the sibling credential list already rides per-entity rows (one shape for both).
