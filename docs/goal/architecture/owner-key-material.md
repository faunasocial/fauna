### Audience: owner only (one user, all of their devices, forever)

The user reaches their own content along two distinct paths in fauna, depending on which client they use. Both lead to the same audience (the user), but the unwrap-key source differs:

- **Path A — identity-seed-derived (`BackupKey`).** Used by fauna's own clients, which already hold the identity seed. fauna-sync content (drafts, backups, ordinary file chunks today; the `__config` blob too until it retired on 2026-10-02 — [`config-dissolution.md`](config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)), plus any future client-held owner-only state, decrypts under `BackupKey`.
- **Path B — MUA-credential-derived (`WrappedMsekBlob`'s MSEK).** Used when the user reaches their account via a third-party MUA (IMAP/CalDAV client) talking to the MDA bridge. The MUA cannot be given the identity seed (it's a separate program with a separate trust model); instead it sends a credential (PLAIN password or OAUTHBEARER token), the bridge derives an unwrap key from the credential, and that key opens a pre-prepared `WrappedMsekBlob` to recover a fresh symmetric key (MSEK) that in turn opens the user's MLS read-side snapshot. The audience is still the user, but the credential serves as the cryptographic proof of identity in lieu of seed possession.

The two paths are independent: `BackupKey` and the MSEK are unrelated key material — the MSEK is **freshly generated random bytes** on the user's primary client, not derived from `BackupKey` or the identity seed. See [`key-material-hierarchy.md`](key-material-hierarchy.md) § Walkthrough: CalDAV / IMAP encryption-key story for the end-to-end flow.

#### Path A — `BackupKey` (identity-seed-derived) — `libs/fauna-core/src/crypto.rs:28-118`

- **Root:** the user's Ed25519 identity seed.
- **Derivation:** `BLAKE3::derive_key(context = "fauna backup encryption key 2026-03-12", key_material = identity_seed)`. Static; deterministic; no rotation.
- **AEAD:** ChaCha20-Poly1305, 32-byte key, 12-byte **random** nonce per blob, Poly1305 tag, framed `[version=0x01][nonce(12)][ciphertext+tag]`. Optional zstd compression layer (prefix-byte signalled). **Exception — chunks riding the content-addressed chunk route** (backup segments + owner-only file-sync chunks, the two bullets below): those seal through the **convergent** `chunk_crypto` primitive under the domain-separated root `BackupKey::convergent_chunk_root()` (deterministic key+nonce from the chunk's plaintext hash) and are store-keyed by the **ciphertext** hash, so the AEAD body satisfies the route's F9 anti-poisoning check (`blake3(body) == X-Content-Hash`) — the same shape as M2 content-key chunks (§ *At-rest blob keying*; FS-BIND FOLLOW-ON A, user-ratified 2026-07-07). The random-nonce frame remains for whole-blob uses (`__drafts` writes, thumbnails, the nest-internal KEK). **It has no chunk-route corpus:** a `ChunkManifest` without `stored_hashes` means the stored chunks are **plaintext, unconditionally** — the read path never treats it as a framed seal, because every pre-convergence framed chunk upload was rejected 400 by the F9 route and never stored (the FS-BIND FOLLOW-ON A live-broken finding), so no framed chunk blob ever rested anywhere.

- **Audience justification:** the seed is the one piece of cryptographic material a user's devices must already share (it's how they sign as themselves), so any per-device-fan-out distribution problem is already solved. No outside reader is ever authorized.
- **Threat model:** anyone holding the identity seed reads it. `BackupKey` is uniformly *not* held on the nest — it is derived on the user's client from the identity seed and used there to seal/unseal; the nest only ever sees the resulting ciphertext. (The nest *does* hold its own deployment DKIM signing key and deployment TLS private key as plaintext files in the data dir, unconditionally — those serve the nest's own deployment-infrastructure functions, never a user's; per-user MLS read-side keys are never nest-held, in any circumstance, so `BackupKey` has no reason to land on the nest either.) "Forward secrecy from yourself" is not a meaningful threat; static derivation is correct.

The nest also derives a *deployment-scoped* `BackupKey`-shaped key from its own Ed25519 signing seed — see [`key-material-hierarchy.md`](key-material-hierarchy.md) § Audience: deployment infrastructure → Nest-internal key-encryption key, where this primitive has its own entry. Same pattern (BLAKE3-derive a context-separated symmetric key from an Ed25519 seed), different root (the deployment seed, not the user seed) and different audience (the nest itself, not the user).

#### Path A-sibling-0 — `NestBackupKey` (identity-seed-derived; delegated to the user's own source nest) — ratified 2026-07-23, nest side BUILT 2026-07-24

- **Root:** the user's Ed25519 identity seed. **Derivation:** `BLAKE3::derive_key(context = "fauna nest backup key 2026-07-23", key_material = identity_seed)`, plus a domain-separated convergent chunk root mirroring `BackupKey::convergent_chunk_root()` — `BLAKE3::derive_key(context = "fauna.nest-backup.chunk.v1", key_material = the NestBackupKey bytes)` (landed 2026-07-23, `libs/fauna-core/src/crypto.rs`; both context strings are frozen for the life of the key and KAT-pinned — editing either silently breaks every already-uploaded backup). Static; deterministic (restore survives total device loss); no rotation — rotation/epoch schemes bound *delegates* whose access should be windowable, and this seal must open the owner's whole back-catalogue forever (design record: tracked internally (2026-07-23 nest-side segment backup) § Rejected alternatives).
- **Seals:** cross-location backups of the **nest-originated message kinds** (`__mail`, `__conv/<channel>`, `__post`, `__calendar`, `__card` segment files + their `manifest.<kind>` mirrors), sealed by the **source nest's in-process backup coordinator** before upload to destination nests. Destinations store opaque chunks — the framing/metadata floor included, which is this key's entire marginal value (record payloads inside segments are already sealed by each kind's ingest authority).
- **Custody — the deliberate exception to "no nest holds a backup key":** the user's client mints/derives it and **grants it to their own source nest** at first destination-enroll (revocable; surfaced in the nests-page trust facet). This is sound because the key seals only data the source nest already hosts and floor-reads by design — *co-locating a key with the data it seals adds no exposure* — and it is what makes backup freshness independent of any user device being awake. `BackupKey` (Path A) remains **never nest-held**: it seals client-originated data the nest must not read. Deliberately symmetric, not asymmetric: the sealer holds the plaintext by construction, and convergent (deterministic) sealing preserves idempotent retries + per-owner dedup.
- **Custody — handed per call to the owner's own desktop sync agent for one re-seed (ruled 2026-09-26).** On a desktop the client-device custodian's sealed store belongs to the bearer-only sync agent, which cannot derive this key (it never holds the seed — [`apps/sync-agent-credentials.md`](apps/sync-agent-credentials.md) § Credential model). The re-seed ceremony ([`../behavior/backup-destinations.md`](../behavior/backup-destinations.md) § Third destination kind → *Re-seed*) needs it on the store's side, both to grant it to the target and to re-seal the held corpus under it. So the seed-holding app derives it and hands it to the agent **inside the one confirm-gated local IPC verb that runs the ceremony** (`ReseedCustodianStore`, [`apps/sync-agent.md`](apps/sync-agent.md) § the retry-less verbs). The agent uses it for that call only, in `Zeroizing` memory, and never persists it; the next re-seed needs a fresh handoff. This widens nothing: the key is nest-holdable by design, and the ceremony's own first phase grants it to the target nest. And the agent already holds, under the strictly client-only `BackupKey` it was provisioned with over the same seam, the very corpus this key would seal. What the agent gains is the power to seal that corpus for a nest, which is the act the owner just confirmed. Refused alternatives: the app opening the agent's store itself (a second process on a single-writer store, racing the agent's pull), and provisioning the key with the standing capability (a nest-delegable root persisted on disk for a ceremony that runs once per box loss).
- **Threat model:** a compromised source nest gains no *read* power from this key (it hosts the data regardless); what it gains is destination *write/supersede* power, mitigated by the destination-side custody grace window (T = 30 d) + the seed-holding clients' audit loop — owner: `segment-backup-protocol.md` § Cross-location backup protocol; analysis: the 2026-07-23 design record.
- **Named future direction (not owed): per-scope subkeys for foreign-channel conv enrollment.** The root is granted **only to the user's own source nest, ever** — which is why a foreign member cannot enroll a channel homed elsewhere (conv v1 shape: `segment-backup-protocol.md` § Cross-location backup protocol). The recorded direction for that follow-up is a per-scope subkey derived from the `NestBackupKey` bytes with a fresh domain-separated context string (frozen + KAT-pinned by the slice that builds it, per this section's discipline — not minted here), bounding a foreign channel-home nest's grant to that one channel while staying deterministic from the seed (restore survives device loss). It rides whatever flow first builds foreign-channel enrollment UI.

#### Path A-sibling — Index master key (identity-seed-derived; owner-only) — design ratified 2026-05-10, tracked internally, § Encryption; derivation re-rooted + ratified 2026-08-04

- **Root:** the user's Ed25519 identity seed — the third seed-derived sibling beside `BackupKey` and `NestBackupKey`, independent of both by context-string domain separation (rule #3). **This re-roots the 2026-05-10 pin** ("derived from the user's MLS root as a separate sub-key from MLS read-keys"), revised 2026-08-04 at the derivation-ratification gate because the pinned root does not exist: the implemented MLS architecture has no per-user root — every `fauna-mls` exporter secret is group/epoch-scoped (`fauna.blob.v1`, `fauna.chunk.v1`, `fauna.fileset-keys.v1`, `fauna.subscription.v1`, `fauna.room.post.v1`), and inventing one solely for this key would add mechanism for no property. The property the old pin was buying — rotation independent of the MLS ratchet — holds trivially for a seed-derived sibling (the seed never ratchets). Seed-derivation was also chosen **over minting random material stored in the account's synced state** (the MSEK shape; `BackupKey`-sealed in the `__config` blob when this was ruled): a deterministic derivation makes every seed-holding client compute the same key with nothing stored and nothing synced — which *is* the ratified audience below — structurally rules out the two-device first-login mint race a random key would carry through that state's merge (concurrent derivations produce identical bytes; concurrent mints fork the key), and survives total device loss with no escrow beyond the seed's own.
- **Derivation:** `BLAKE3::derive_key(context = "fauna.index.master.v1 2026-08-04", key_material = identity_seed)` — generation 0, built 2026-08-04 as `fauna_core::crypto::derive_index_master_key` (KAT-pinned beside its siblings; the context string is frozen for the life of generation 0). **Rotation is a generation bump, not a context edit:** a future rotation slice mints generation N as its *own* frozen context string plus a rewrap pass (`fauna_index::seal::rewrap_segment_master_key` rewrites only the 48-byte wrapped data key per segment — the format was built for this) or a re-index pass; because generation N's bytes are fully determined by (seed, N), two devices rotating concurrently derive the identical new key — no fleet race can fork it. **Succession:** when the identity seed itself rotates (the succession ceremony), the key re-derives under the successor seed like its siblings — `succession-aftermath.md` § Re-key scope carries the row; the index is *derived data*, so rewrap-under-the-new-key and drop-and-re-index are both complete answers. **Which one the code takes today, and it is not a placeholder: drop-and-re-index, automatically, at the moment the successor first meets a blob it cannot open** (built 2026-08-05). The succession re-points the whole `__index` folder to the successor, so the predecessor-sealed `manifest.idx` is *present* on the successor's rail — and "present but unopenable" had been an error rather than a state, which wedged the master arm permanently while a retry log promised recovery. The rebuild arm is keyed on an AEAD failure specifically (a blob that unseals and then fails to *decode* still surfaces — a manifest a newer build wrote must not be healed by overwriting, `version-compatibility.md` § 5 item 9), and it is **master-class only**: this key is convergent — every device derives the identical key from the identical seed — so no device can be rebuilding what a sibling still reads. Its mail/calendar counterpart deliberately does not take it (§ Path B-sibling-4 — that key rotates through a grace ring, so a miss there can be a merely stale ring). Mechanism + the class asymmetry: `../behavior/content-index.md` § Encryption posture. *Status: **IN PRODUCTION USE since 2026-08-05** — the S4 master-key builder derives it at login in `NestMailIndexLauncher::master_index_key` and seals every built master-class kind's segments + `manifest.idx` under it; which kinds that is today is `content-index.md` § Status's to track (conversation first, growing since). The key is derived per login and never stored, synced, or handed to app glue.*
- **Custody of the derived bytes (ratified 2026-08-05):** the custody type for this key is **`fauna_index::IndexMasterKey`** — non-`Copy`, zeroize-on-drop, `pub(crate)` byte access — and the derivation hands its output out as **`Zeroizing<[u8; 32]>`**, not a bare array. A bare `[u8; 32]` is `Copy`, so it is silently duplicated on every assignment and pass-by-value and is never zeroized; `Zeroizing` is neither (`Copy` and `Drop` are mutually exclusive in Rust), which makes no-implicit-copy **structural** rather than a handling convention, and satisfies § Bridge-process discipline's zeroize-on-drop rule for the window between derivation and wrapping. **Deliberately *not* a second newtype in `fauna-core` beside `BackupKey`/`NestBackupKey`**, which is the shape a reader expects from the "third seed-derived sibling" wording: `fauna-index` cannot depend on `fauna-core` (its dependency list is curated to keep the wasm build possible at all — `libs/fauna-index/Cargo.toml`), so a `fauna-core` newtype would mean **two** custody types for one key with a bare `[u8; 32]` hop between them via `to_bytes()` — reintroducing the very gap it would claim to close. The siblings can hold one custody type each only because *their* consumers may depend on `fauna-core`. The same shape applies to the MSEK-derived § Path B-sibling-4 key, so the index-key family keeps one rule. Pinned at compile time (`_INDEX_MASTER_KEY_IS_NOT_COPY` in `libs/fauna-core/src/crypto.rs`): reverting the return type to `[u8; 32]` is a type mismatch. A runtime test cannot observe an absent `Drop`, and the conflicting-impl (`impl<T: Copy>` blanket + concrete impl) trick does **not** work here — coherence rejects it against a foreign type like `Zeroizing` whether or not that type is `Copy`.
- **AEAD:** XChaCha20-Poly1305 (24-byte random nonces — `fauna_index::seal`, as built; an earlier revision of this entry said ChaCha20-Poly1305, pre-dating the implementation) over the small index-metadata files (`manifest.idx`, `classifier-ledger.idx`) directly under the master key; per-segment data keys are **wrapped under the master key** and seal the immutable Tantivy segments `seg-N.idx` one-shot.
- **Protects:** the user's per-actor content-index — the `__index` reserved folder (per-actor-scoped, no actor path segment — `libs/fauna-index/src/paths.rs`) holding the Tantivy segments, the manifest, the classifier ledger.
- **Audience justification:** owner-only, identical to `BackupKey`. Every one of the user's apps (Linux, Windows, macOS, Android, iOS, tui) holds the index master key and runs Tantivy locally over the **full cross-kind** index. The MDA bridge does **not** hold the master key (rule #7) — during an active IMAP/CalDAV session it holds only the **mail/calendar index-segment key** (MSEK-derived, reached via Path B; see `docs/goal/behavior/content-index.md` § Encryption posture), enough to build and query the mail + calendar index slices it serves, and never the conversation / post / contacts / drafts / media slices. So unified "Spotlight across everything" is a *client* capability; the bridge's index reach is mail+calendar only. **The nest never holds the master key, unconditionally** — the `__index` reserved folder rests sealed under it like any other Path-A-protected folder; the nest keeps no plaintext index mirror of its own (`docs/goal/behavior/content-index.md` § The live FTS path: the nest's own SQLite `content_fts` is a separate, always-plaintext, public-preview-only mechanism, not a copy of this index).
- **Threat model:** anyone holding the master key reads the user's full search corpus (every indexed token from every content kind). Same audience as `BackupKey`; same trust model. Rotation cadence is per-user, driven by the user's apps; the index format is versioned so a key rotation is a re-encrypt pass over the existing segments (or a re-index pass, identical from the segment-store's perspective).
- **Why a separate primitive, not just `BackupKey`:** the two share a root but not a lifecycle — the index master key rotates by its own generation axis (bump + rewrap/re-index, the Derivation bullet above) with `BackupKey` untouched, whereas sealing the index under `BackupKey` directly would force the lifecycles together: any future `BackupKey` re-key would invalidate the index alongside every fauna-sync-protected folder the user owns (drafts, contacts, backups, library media), and an index-only rotation would be unexpressible. Distinct context strings keep the derived keys cryptographically independent, so holding one still confers nothing about the other.

#### Path A-sibling-2 — Account-state entry keys (`BackupKey`-derived; owner-only) — frozen 2026-08-10 (T14, the account-data plane's pre-W2 gate); derivations BUILT 2026-08-10 (`libs/fauna-core/src/crypto.rs`)

  argument is custody, not cryptography: the account-data plane's device-principal bundle

  `BackupKey` and never the seed, and a seedless enrolled device must derive every key of the
  plane — rooting one step below the seed makes the schedule derivable by exactly the principals
  that may read (R7 reading replicas) with nothing new distributed. Transitively seed-rooted, so
  restore-from-seed reproduces everything.
- **Derivation (two frozen context strings + keyed-hash steps; KAT-pinned when built):**

    per-kind **entry key** `entry_key(kind) = BLAKE3::keyed_hash(entry_seal_root, kind_utf8)`.

    wire/journal **item key** `item_key(kind, key) = BLAKE3::keyed_hash(item_blind(kind), logical_key_bytes)`

    `chunk_crypto`/`path_crypto` pattern. Both context strings are frozen for the life of
    generation 0 — editing either orphans every sealed entry at rest and on every custodian.
- **Why keyed item keys when `path_hash` is a plain hash:** the file-sync `path_hash` floor
  carve-out (unkeyed BLAKE3 of the path — `encryption-at-rest.md` § Carve-outs) stands for file
  scopes, where paths are arbitrary user strings. Class-2 logical keys are drawn from an
  enumerable vocabulary (registered kinds × known field names), so an unkeyed hash is
  dictionary-reversible and would tell every custodian and the nest *which setting* changed. The
  keyed blind makes item keys stable-but-opaque: relays route, retain latest-per-writer, and
  dedup on them; nobody without the blind can name them.
- **The audience-ladder branch split (R13, ruled 2026-08-11; BUILT 2026-08-11 — see
  § Implementation status today for the code shape):** the schedule
  forks into two sibling branches under the same root, one per grantable posture
  ([`account-data-taxonomy.md`](account-data-taxonomy.md) § The audience ladder owns the rung
  semantics). The two context-string pairs above are the **delegable** branch — the branch
  grants reach. The **fleet-only** branch derives identically under its own frozen context
  strings — minted at build time as
  `"fauna.account-state.fleet-only.seal.v1 2026-08-11"` and
  `"fauna.account-state.fleet-only.item-key.v1 2026-08-11"`, KAT-pinned like these; additive,
  nothing sealed under the delegable strings is touched — and is **structurally outside the
  grant-mintable universe**:
  grant bundles are minted from a delegable-only schedule type that does not contain the
  fleet-only branch, so **no typed path** from a fleet-only kind reaches a grant — a
  **typed-path guarantee**: no typed value below a root yields a non-delegable kind's raw
  pair. It is not an unwritable expression: the roots themselves (the backup key, a
  generation key, a group's machinery root) are held as raw bytes by necessity — they wrap
  plaintext and fill bundle slots — and the context strings are public, so a root holder can
  recompute any kind's pair and hand it to the public from-raw-pair constructor a granted
  position uses. That route is guarded by review, not by types: a root's holders are the
  fleet's own code. Domain separation makes the branches cryptographically independent —
  possession of every delegable kind key reveals nothing about any fleet-only key.
- **Grant fit ([`encryption-at-rest.md`](encryption-at-rest.md) § Capability tiering):** the
  grant unit for kind K is the pair `{entry_key(K), item_blind(K)}` — a granted read position
  finds and opens exactly K's entries and cannot recognize, name, or open any other kind's —
  **and only delegable-branch kinds are mintable** (R13, above). A
  full reading replica derives the whole schedule from the `BackupKey` in its bundle; no per-kind
  distribution problem exists.
- **The generation axis (R14, ruled 2026-08-11 — mint machinery CODE as of 2026-08-13,
  build steps 1–7 plus the first-need mint trigger, production generations now exist:

  mechanics when built):** everything above is **generation 0** — the root-derived branches,
  frozen, KAT-pinned, derivable-forever from `BackupKey`. Generations **≥ 1 are random**,

  device set inside their enrolled bundles, and **HPKE-escrowed** (wrapped to the identity
  public key) at each explicitly-chosen escrow holder — the user's nest by default, several
  holders for tunable redundancy. Sealed entries and blocks carry their generation id
  beside the form version; per-generation entry/blind derivations repeat the two-step

- **Rotation (rewritten to the R14 axis 2026-08-11; the superseded T14-era text prescribed

  a generation that has sealed data must never exist un-escrowed, so no writer seals under a

  **History is never re-sealed forward:** generations coexist, and per-generation shred is the
  deletion granularity — a rotation is a mint, never a re-seal migration; re-sealing old
  windows under the new tip would collapse exactly the granularity R14 buys.

  keys:** concurrent mints fork the tip rather than collide — a generation id is
  content-derived from the mint itself (parent tip, member set, minter), never a bare local
  ordinal, so two concurrent "N+1"s are two distinct generations. Every replica converges on
  the same winner with no communication: the tiebreak is the plane's standing
  no-local-preference discipline (order derived from content, never from arrival or
  locality), and it runs over **admissible tips only** — a tip whose member set includes a
  device the observer's merged device-set state excludes **or cannot verify as a member**

  generation machinery) is inadmissible, and since removals
  are monotone it drops out fleet-wide as the removal propagates. The losing tip is **retired
  for sealing, retained for reading** (reads walk every generation held; writes seal under
  the winning tip only — the § Path B-sibling-4 keyring's read/write asymmetry); re-sealing
  its short window's entries under the winner empties it, after which the ordinary shred
  machinery deletes it (an emptied loser is the one generation whose deletion destroys
  nothing). **An exclusion is never lost with a losing mint:** removal intent is device-set
  plane state, not a property of the mint that carried it — a replica whose merged device-set
  state is narrower than the winning tip's member set mints again on the merged set, so two
  concurrent removals both take effect within one further mint. No arbiter seat is required —
  a nest's star topology merely makes forks rare and short-lived (operational, never
  protocol-level, R6) — so this story holds unchanged in the no-nest profile (R11).
  **Succession (the R14 rider; re-ruled 2026-10-01 after the first cut was measured red on a successor holding its own schedule; built the same day — § Implementation status today): a succession is a fresh root for the device set and a continuous mint DAG.** Generation 0 re-derives under the successor seed's `BackupKey` like every Path A key, so the successor's replica opens none of the generation-0 rows its predecessor sealed. Two things cross anyway, each by its own ruled road: the delegable rows, by the successor walk's carry ([`../behavior/succession-aftermath.md`](../behavior/succession-aftermath.md) § Re-key scope, ruled 2026-10-01), and the random generations ≥ 1, which **cannot re-derive** and cross as a key and its mint record, below. Nothing else of the machinery crosses.

  **What is re-made, never carried.** A device's keypair is per (machine, account), so a succession gives every device a new id: each enrolls afresh under the successor root, the successor publishes its own escrow target, and the predecessor's device-set, wrap, receipt, target, reach and unkeyable rows are no part of the successor's merged state. So no device the retired root enrolled is a member, a wrap target or a healer under the successor. "The predecessor identity is excluded exactly like a removed device" holds by construction, for a seed thief's self-enrolled device as for any other, with no removal for the user to find; and the fleet view verifies an enrollment cert against the account root alone ([`account-data-taxonomy.md`](account-data-taxonomy.md) § The generation machinery, *The source of `prior`*). The rows themselves stay on the feed the successor inherits until the reclamation pass retires them: that doc's § The generation machinery → *Fleet-scope reclamation*, clause (3)(i), the predecessor arm (ruled 2026-10-01, not built), and clause (3)(g) for a predecessor device's device-level rows.

  **What crosses: the key, and the mint record of exactly the generations whose key the device carries.** *The key.* A device carries its predecessor slot's retained keys into the successor's slot at the successor runtime's assembly, and the home nest **keeps** the predecessor-keyed escrow wraps through the ceremony (re-ruled 2026-10-01; the first ruling burned them inside the ceremony's transaction, and *The kept wrap*, below, owns the measurement, the rule and what it costs): a seed-holding successor device that keys none of a generation whose record it can open recovers the key from the kept wrap under the retired seed, in its first full pass. *The record.* The runtime is handed, for each attested predecessor, that identity's generation-0 keys for the one kind `fauna.state.generation-mint`: beside the delegable schedule the walk's carry already holds, derived from the same retired `BackupKey`. The walk is handed nothing else of the retired fleet-only branch. A fleet-scope row that does not open under the successor's schedule is tried under them. One that opens is **carried** when (a) its record binds to its own key (the logical key is the content-derived id of its core) and its minter signature verifies, and (b) the device's retained bundle holds, at that id, a key matching the core's commitment; any other is left as an unopened row is. Carried means the walk's carry shape: merged by the kind's own join and, where the merge takes it, re-authored as the walking device's own row, value verbatim, sealed under the successor's generation-0 fleet branch. The retired keys only ever open, as the delegable ones do.

  **Why the mint record, and why only it.** Every pass that moves a generation key reads the generation's mint row: the re-escrow pass deposits per live mint row, escrow recovery asks per receipted mint row and checks the opened wrap against the core's commitment, the top-up pass heals per live mint row, a reach lists live mints, and the re-seal pass reads supersession off the DAG. Measured 2026-10-01: a successor that holds a carried key and no mint row deposits nothing; its next write mints a parentless generation, and a device holding only the successor seed reads no pre-succession tip-sealed row. With the record in merged state each of those passes is the pass it already is. The record is also the one machinery row that is history about the generation itself and not authority under an identity. Its core and its signature name the predecessor's devices and are immutable, which is what the re-key classification keeps as it is (`succession-aftermath.md` § Re-key scope, the classification rule); enrollments, targets and receipts confer authority and are re-made.

  **What the standing passes then do, unchanged.** Every seed-holding or key-holding runtime's pump re-escrows whatever generation it keys that no trusted holder has receipted for the current identity: to the successor's published escrow target, receipted under the successor's target key. Per-identity escrow targets and identity-bound receipts are what make the handover representable (the key grammar: [`account-data-taxonomy.md`](account-data-taxonomy.md) § The generation machinery, the escrow-target and escrow-receipt kinds). The walk that carries the record runs ahead of that pass, so the first full pass of the first carrying device closes the window the burn opened. A device holding only the successor seed then walks the re-authored mint row and the receipt, both sealed under the successor's schedule, and recovers the key from the holder (the taxonomy's *Escrow recovery*); a seedless successor device is topped up by any device that keys the generation.

  **Forward sealing: trigger (d) is no mint of its own.** A carried generation is never a sealing candidate under the successor: its member set names the predecessor's device ids, and the successor's device set never holds them. So the first tip-sealed origination under the successor finds no candidate and mints by trigger (a), naming the carried generations among its parents; the successor's first generation supersedes the predecessor's last by an ordinary DAG edge. From there a carried generation is what any superseded generation is: read for as long as rows rest under it, its account-level rows re-sealed under the tip by the re-seal pass's hand-over arm, shredded when nothing rests under it (`account-data-taxonomy.md` § The generation machinery → *Fleet-scope reclamation*, clauses (3)(g) and (3)(e). The predecessor devices' own device-level rows under it are retired by clause (3)(g)'s let-go arm, ruled and built 2026-10-01, so the shred follows — § Implementation status today). The re-escrow pass therefore never mints, at a succession as at a holder change.

  **The retired machinery keys open only to retire (ruled 2026-10-01; built 2026-10-02 — § Implementation status today).** The predecessor's machinery rows are not carried, and the ceremony does not clear them either: the feed moves to the successor with them on it. So the runtime also derives, for each attested predecessor, that identity's generation-0 pair for every other fleet-only machinery kind (device-set, wrap, unkeyable, closed, reach, escrow-receipt and escrow-target today; the registry's fleet-only generation-0 kinds), from the same retired `BackupKey`, in the same derivation, open-only by type. They go to one consumer: the fleet scope's reclamation pass on the bound nest. It opens a row under them to learn that the row is that identity's machinery, and of which kind, and then retires it ([`account-data-taxonomy.md`](account-data-taxonomy.md) § The generation machinery → *Fleet-scope reclamation*, clause (3)(i), which owns the rule, the measured count and what stays). The walk never tries them, no open that vouches a row to the publish diff tries them, and no row opened under them is merged, re-authored or pushed. So *Refused*, below, stands as it reads: no device the retired root enrolled becomes a member, a wrap target or a healer, and the retired `BackupKey` authors nothing. The keys add nothing to what a device can read, because a host that attests a predecessor already holds that identity's `BackupKey`.

  **Refused.** *Opening all of the predecessor's fleet-only generation-0 rows into the successor's state* — what the first cut's proof did, by seating both identities on one schedule. It keeps every device the retired root ever enrolled as a member and a wrap target until the user removes it, makes the retired `BackupKey` a standing authoring key for the successor's machinery, and is what § Re-key scope's clause (4) refuses. *Carrying keys bare*, with the deposit, recovery and top-up passes re-cut to run per bundle key: a second machinery beside the first in every pass, and a key↔id check with no core to read. *Carrying the core in the bundle beside the key:* the bundle is a capped credential item, and no bundle written before this ruling holds one. *Handing the rows over to a successor generation in place of escrowing the key:* a many-pass re-seal that races device loss where the deposit is one request, and it reaches only rows the hander has already walked; it happens anyway, afterwards, as the hand-over arm above.

  **The kept wrap — the ceremony burns no generation's last escrow copy (measured and ruled 2026-10-01; built 2026-10-02 — § Implementation status today).** The first ruling had the ceremony burn every predecessor-keyed wrap, calling a generation no device keys at that moment "already dead". It was not dead: the holder could produce it until the burn, and nothing makes a device key it first. Escrow recovery runs inside a seed-holding runtime's full pass, and the ceremony runs pre-identity, with no session at all, because the thief can revoke every session and invoke the seed-signed lockout ([`../behavior/identity-succession.md`](../behavior/identity-succession.md) § Enforcement on the home nest). So the canonical theft — the only device stolen, the seed restored from the phrase on a new machine, the identity rotated at once — burned the only copy of every generation ≥ 1, and under them rest the account's reception key, mail custody, senior ATProto rotation key, period keys and folder keys. **Measured 2026-10-01** (`conformance_account_state_walk.rs::an_unkeyed_successor`): a successor seat holding both seeds and no generation key, after the burn, keys nothing, carries no mint record and reads no reception key, with 11 live rows resting under the generation for good; with the wraps kept at the holder and nothing else changed, the same — the pass opens wraps under the successor's secret alone, and the walk carries no record it cannot key. **The rule, the nest half.** `generation_escrow_wraps` is `Succession::Stay`: a wrap rests under the actor id that deposited it, which is the identity whose target it seals to, and the ceremony touches none. `fauna.generation.escrow.get` serves the authenticated account's wraps and those of every identity the nest's recorded successions retired into it (the chain account deletion already walks), filtered or not; `put` and `delete` stay the account's own. A retired identity's wrap of a generation is swept in the transaction of the first `put` that lands a wrap of that generation under the successor — the deposit it was kept for — and by the three paths that already take a wrap: the belted receipt retire's escrow sweep and the user-gated `escrow.delete` delete every wrap the chain holds for the generation, and the account's deletion takes the chain's rows ([`account-data-plane.md`](account-data-plane.md) § Nest-side requirements item 1, *Deletion reaches the account's predecessors*). **The rule, the client half.** The seed-holding successor runtime is handed each attested predecessor's identity seed beside its `BackupKey` (the registry holds both; the seedless agent holds neither and recovers nothing, as today). The fleet walk keeps, for the pass, the list of predecessor mint records that opened under the mint-kind keys and were not carried for want of the key — conditions (a) met, (b) not — exactly as the delegable walk keeps its retire candidates ([`../behavior/succession-aftermath.md`](../behavior/succession-aftermath.md) § Re-key scope → *The predecessor's own row is retired behind the carry*); the list lasts one pass and is never stored. The escrow-recovery pass asks the holder for each such generation, filtered, and opens every wrap in the reply under the current identity's escrow secret and then under each attested predecessor's, checking the key against the core's commitment as it does any wrap; a key that checks is recorded in the retained bundle. The pass that keys a generation re-presents the scope, so the walk behind it carries the record, and the re-escrow pass behind that deposits the generation under the successor's target, which is what sweeps the kept wrap. The request bound: a predecessor's receipt is unopenable under the successor, so the bound for these generations is the mint-kind open itself — only a holder of the retired `BackupKey` could have sealed the record — plus the answered-once memo every recovery request has; a thief who floods mint rows before the ceremony buys one filtered request each, once per runtime. **What keeping the wrap costs, stated.** A wrap sealed to the retired target rests at the holder, under the retired id, from the ceremony until the successor's deposit — or for good when no successor device ever keys the generation. After the ceremony it is fetchable by the successor's authenticated session alone (the retired key is refused at every door) and openable only with the retired seed. The party that can do both is the owner's own device. Beyond today, a reader of the holder's store who also holds the retired seed, but not a device bundle, learns the generation keys; that party already opens every generation-0 row the retired identity sealed with the `BackupKey` the same seed derives, and the successor's own kit blob carries the predecessor seeds on purpose, so that the corpus sealed before the succession stays openable (`identity-succession.md` § Seed escrow). The kept wrap is that same material's key on this plane. Against it stood a certain, total loss in the one flow the ceremony exists for, and the first ruling's reason — thief-readable — protected nothing: a thief holding the seed read the wraps before the ceremony or holds the keys on the stolen device, and cannot fetch them after. **Refused.** *A precondition on the ceremony's client* (key every receipted generation first, refuse or warn when one cannot be keyed): keying needs a session as the retired identity, which the lockout the ceremony escapes denies the owner, and a warning that sends the user to sign in as the thief's identity first is the same thing with a prompt. *Keeping the wrap only until a successor receipt exists, then burning:* that is what the rule does, on the successor's deposit and never on a timer. *Moving the wraps to the successor's id in the ceremony:* the nest cannot read a wrap, so a moved row could not be told from the successor's own at the sweep; the actor id is the target identity, and `Stay` keeps that fact in the row.
  **Residuals, stated.** (i) A generation no surviving device keys and no holder wraps is already dead, before the ceremony as after it: the stated R14 residual, not a loss succession introduces. The ceremony makes no generation dead (*The kept wrap*): one the holder wraps at ceremony time is keyed by the first seed-holding successor device's first full pass. (ii) Until that pass the keys rest on devices and in the holder's retired-targeted wraps; a seedless successor device holding no key waits for a top-up. (iii) A device that carries a key and is served no predecessor mint row for it carries no record; the key stays readable on that device, and unescrowed, until a device that is served the row walks. (iv) What a walk is served under the retired keys is bounded as the delegable carry's is, by who could write into the scope before the ceremony plus what a peer relays; conditions (a) and (b) admit only the true record of a generation this device had already keyed. A `Shredded` record of one crosses by the same join and drops the key, as it does on any replica. (v) The predecessor's rows rest on the feed the successor inherits until reclamation retires them, and a row under a generation no successor device keys and no holder wraps rests there until the user lets the generation go. `account-data-taxonomy.md` § The generation machinery → *Fleet-scope reclamation*, clauses (3)(g), (3)(i) and (3)(j), own the rule, the measured count, the bounds and the let-go.

(The v1 wire shape matches this scope: `leaf_init_keypairs` plus, since 2026-07-18, the additive `mail_epoch_grace_roots` — prior generations' derived mail-epoch roots, still strictly mail read material per § Path B-sibling-2's per-epoch extension — and, since 2026-08-03, the additive `index_seg_grace_keys` (§ Path B-sibling-4 → *Snapshot carriage*), prior generations' derived mail/calendar **index-segment** keys: index-token read material over exactly those two kinds, never mail bodies and never the cross-kind index master key.)
- **What wraps MSEK:** a per-credential symmetric AEAD key derived from the user's MUA credential. Two derivation paths exist by credential type:
  - **PLAIN** (password) → `Argon2id v1.3` with provisioning-time defaults (`m=65,536 KiB, t=2, p=1`, 16-byte random salt baked into the blob), outputs a 32-byte ChaCha20-Poly1305 key.
  - **OAUTHBEARER** (bearer token) → `HKDF-SHA-256` with `prk = HKDF-Extract(salt = blob.salt, ikm = token_bytes)` and `info = "fauna.wrapped-blob.oauth.v1" || actor_id || credential_id`.
- **AEAD over MSEK:** ChaCha20-Poly1305, random 12-byte nonce per provision, AAD-bound to `(kind = "wrapped-msek", actor_id, credential_id)` to defeat blob substitution.
- **Storage on the nest:** opaque CBOR-encoded bytes in `bridge_wrapped_mls_blobs(actor_id, credential_id, blob, created_at)`, plus a separate `MlsSnapshotBlob` per actor; provisioned via `fauna.bridges.provision_wrapped_mls_blob` + `provision_mls_snapshot_blob`; fetched by the MDA bridge via the corresponding `fetch_*` WS-RPC calls (`bins/fauna-nest/src/bridge_blob_handlers.rs`).
- **Lifecycle:** provisioned by the user's primary client at IMAP/CalDAV-credential enable. Unwrapped on the MDA bridge at every MUA AUTH (not cached across sessions; AEAD-success *is* AUTH success — there's no separate password-hash check). MSEK + decrypted snapshot live in `zeroize::Zeroizing<…>` mlocked memory for the session lifetime; zeroized on LOGOUT / IDLE timeout / session disconnect.
- **Client-side persistence.** MSEK persists on the user's Fauna app fleet in the account-state plane kind `fauna.state.mail`, sealed under its generation tip per § Path A-sibling-2 — an audience-compatible container (the fleet is exactly that audience; the kind: [`config-dissolution.md`](config-dissolution.md) § The `__config` dissolution schedule → *The kinds*). The client-side lifecycle — the record's field layout, the credential-secret co-storage, the every-client-is-primary rule, rotation/recovery — is owned by `docs/goal/behavior/mail-credentials.md` § MSEK lifecycle; this doc owns only the audience/derivation taxonomy above.
- **Audience justification:** the user, accessed via an external MUA that cannot be trusted with the identity seed. The credential is the cryptographic gate; the bridge gets session-scoped decryption authority for the duration of an active connection and nothing more, and the nest never holds an unwrap key, unconditionally (per the candidate (b) ratification — see the bullet below).
- **Uniform AUTH/unwrap mechanism (candidate (b) ratified 2026-05-14).** The MDA bridge serves IMAP/CalDAV the same way on every nest — the retired plaintext/encrypted-mode split never differentiated this path either (per the Phase E1 / mail-bridge reconciliation). The AUTH/unwrap mechanism is **uniform**: the user's Fauna app provisions a `WrappedMsekBlob` via `provision_wrapped_mls_blob`, and the bridge unwraps it identically at MUA-AUTH. **The nest itself never holds the user's MLS read-side keys plaintext on disk, in any circumstance** — no nest-side classifiers/indexers/federation-receive path ever needed or held that plaintext copy (those paths were retired with the storage-mode axis; confirmed dead by `docs/goal/behavior/content-index.md`'s finding that the nest holds neither the MSEK nor the identity seed (so it can derive no index key), and `docs/goal/behavior/moderation.md`'s finding that no server-side social classification exists); the MDA AUTH code path only ever reads the wrapped form. The earlier "candidate (a) — `verify_credential` RPC keyed by password hash on nest" alternative was retired; the nest holds no per-credential verifier, unconditionally. Ratified into [`docs/goal/behavior/imap-server.md` § Authentication](../behavior/imap-server.md); reasoning tracked internally (design ratified 2026-05-14, § Sub-question 1).

#### Path B-sibling — `WrappedSubmissionTokenBlob` (MUA-credential-derived, MTA-side) — `libs/fauna-mls/src/wrapped_blob/mod.rs` (per wrapped-blob spec § Per-credential submission-token blob)

Same per-credential AEAD-wrap surface as Path B's `WrappedMsekBlob`, indexed by `(actor_id, credential_id)`, AAD-bound the same way, with the same Argon2id-PLAIN / HKDF-SHA-256-OAUTHBEARER KDF split. The **plaintext is different**: a `SubmissionToken` (`{actor_id, credential_id, issued_at, expires_at, max_recipients, max_messages_per_day, user_sig}`) rather than an MSEK. The MTA bridge unwraps it at SMTP-submission AUTH, verifies the inner `user_sig` against the user's signing pubkey, and treats successful unwrap + sig-verify as authentication for the submission session. **No decryption capability is conveyed by this blob** — the MTA gets only the right to submit on behalf of the actor for this credential, until `expires_at`. Token refresh cadence is a user-client / server-side policy choice (default 7-day re-issue / 30-day expiry per the spec); admin-tightened single-VPS postures cap `expires_at ≤ 3 days`.

The wrap-key derivation, AAD binding, uniform (unconditional) AUTH mechanism, and credential-revocation semantics (soft vs. hard) are identical to `WrappedMsekBlob` — submission tokens are not separately listed elsewhere in this doc because they reuse Path B's audience (the user, accessed via a third-party MUA, with the credential as cryptographic gate) and Path B's mechanism (credential-derived AEAD-wrap, AAD-bound to `(actor_id, credential_id)`). The shape exists as a distinct blob so the MTA's submission path and the MDA's IMAP/CalDAV path do not require each other's privilege. Same `zeroize::Zeroizing<…>`-wrapped mlocked-for-session-lifetime discipline as MSEK on the MDA bridge (see [`key-material-hierarchy.md`](key-material-hierarchy.md) § Plaintext key lifetime on bridges).

#### Path B-sibling-2 — Recipient mail HPKE keypair (MSEK-derived) — `libs/fauna-mls/src/wrapped_blob/mod.rs:1499-1640` (`seal_to_recipient` / `unseal_mail_record`, plus the PQ-hybrid `seal_to_recipient_xwing` / `unseal_mail_record_hybrid` variants — `security/post-quantum.md`)

The standing per-recipient HPKE keypair the MTA bridge seals **inbound mail at rest** to, and the MDA bridge / the user's clients open with. This is the concrete realization of the "HPKE init private keys (current + last 2 rotations)" line in the Path B snapshot-plaintext contents above — it is **not** an OpenMLS leaf/init key. Plain inbound mail shares no MLS group with the sender (it arrives from arbitrary external SMTP / federation peers), so there is no group/epoch secret to key it with; and OpenMLS abandons the KeyPackage `init_key` private half after build + deletes the leaf `encryption_key` pair on commit-merge, so there is nothing stable to export. It is therefore Fauna-managed.

- **Root:** the actor's MSEK (Path B).
- **Derivation:** `BLAKE3::derive_key(context = "fauna.mail.recipient-hpke.v1 2026-05-23", key_material = MSEK)` → 32-byte X25519 secret; pubkey via the X25519 basepoint. Deterministic per MSEK → **fleet-consistent**: every device holding the same MSEK (the account's mail custody, `fauna.state.mail`) derives the identical keypair, so any device can register the pubkey and any can open mail sealed to it (the I3 deterministic-idempotency requirement).
- **AEAD:** HPKE base mode, same suite as the DKIM/TLS wraps (KEM DHKEM(X25519, HKDF-SHA-256), KDF HKDF-SHA-256, AEAD ChaCha20-Poly1305), over each `MailRecordEnvelope`; fresh ephemeral DH per message.
- **Protects:** inbound mail bodies + index hints at rest (the `encrypted_body` / `encrypted_index_hint` envelopes the MTA produces per inbound message; `docs/goal/behavior/imap-server.md`). The matching **public** key is registered as plaintext routing metadata in nest's `actor_mls_pubkeys` table via `fauna.bridges.provision_recipient_mls_pubkey` and read by the MTA via `fetch_recipient_mls_pubkey`.
- **Registration authz:** the **user self-registers their own** recipient pubkey — `provision_recipient_mls_pubkey` is `User`-reachable with a `target == caller` check (mirroring the sibling user-provision kinds `provision_wrapped_mls_blob` / `_mls_snapshot_blob` / `_submission_token`); `Admin` may register any actor's (bridge-perimeter / migration). Wired into `enable_mail` (step 2 of the first-enable order, `docs/goal/behavior/mail-credentials.md` § Partial-state-during-minting). Per the product invariant "user always controls their data / nest config is set from apps" — no admin step gates a user's ability to receive mail.
- **Rotation:** rides MSEK. Rotates **only on hard-revoke** (MSEK rotation — see [`key-material-hierarchy.md`](key-material-hierarchy.md) § Rotation schedule, MSEK row); stable across ordinary snapshot refreshes so the MTA's cached recipient pubkey stays valid. On hard-revoke the client re-registers `derive(MSEK′).pubkey`, and the re-sealed snapshot carries `derive(MSEK′)` (current) + the prior `derive(MSEK)` keypair(s) (last 2) for grace-decrypt of in-flight mail sealed to the old pubkey. Prior MSEKs are retained in `MailConfig.prior_mseks` (cap 2).
- **Audience justification:** owner-only, identical to MSEK (Path B). The MDA bridge holds it (via the unsealed snapshot) only during an active session; the user's clients hold it via MSEK — **the same current + grace set as the snapshot, from the one shared derivation** (`fauna_mls::wrapped_blob::derive_standing_mail_keypairs`, which `build_mls_snapshot_plaintext` serializes for the MDA and the client receive path holds directly; both trial it through `open_mail_record_standing`), so what either holder can open the other can too. (Until 2026-09-15 the clients' receive path derived the current generation only — a drift from this set that blinded a rotated client to its pre-rotation standing mail; `behavior/mail-app-surface.md` § Inbound client receive owns the client-side consequence.) The nest never holds the secret (no-modes; unconditional — there is no other posture) — only the registered pubkey, which is public.
- **Threat model:** anyone holding MSEK derives it (same exposure as the snapshot it lives in). Forward secrecy on hard-revoke comes from MSEK rotation — the new keypair is unrelated to the old, and the old secret is dropped from `prior_mseks` once past the 2-rotation grace window.
- **Custody of the derived bytes (ratified 2026-08-05):** the mail-epoch root of the *Per-epoch extension* below is handed out as **`Zeroizing<[u8; 32]>`**, the same rule its two MSEK/seed-derived siblings took on the same day (§ Path A-sibling, § Path B-sibling-4) and for the same reason — a bare `[u8; 32]` is `Copy`, silently duplicated and never zeroized. It is the **strongest** member of that family, which is why leaving it bare was the sharpest gap: rule #7 bounds the index-segment key to index-token read material over mail/calendar and never mail bodies, whereas this root is complete for *every* per-epoch mail content key of its MSEK generation. The need was already recognised as a hand-wrapping **convention** at three call sites (`bounded_mail_mint.rs` ×2, `fauna-ffi/src/mail.rs`) before it was a signature; making it the signature is what stops a fourth site from forgetting, and those three hand-wraps were deleted as redundant in the same change. Compile-time pin `_MAIL_EPOCH_ROOT_IS_NOT_COPY` in `libs/fauna-mls/src/wrapped_blob/mls_snapshot_plaintext.rs`. Full shape rule, including why it binds on clients: [`key-material-hierarchy.md`](key-material-hierarchy.md) § Plaintext key lifetime on bridges → *Carrier shape*.
- **Why not derive-from-seed or random-persisted:** seed-derivation never rotates (seed rotation is catastrophic) → a captured recipient secret opens all past+future mail forever, contradicting the snapshot's forward-secrecy posture. Random-persisted would add a new synced wire field and make fleet-consistency depend on sync timing, for the same result MSEK-derivation gives by construction.
- **Per-epoch extension (BUILT 2026-07-18 — the mail content-sealing epoch; design spec tracked internally; owner of the mechanism: `encryption-at-rest.md` § Capability tiering → Content-sealing epochs):** alongside the standing keypair, per-epoch siblings derive from the same MSEK root in **two steps**: a per-generation **mail-epoch root** `BLAKE3::derive_key("fauna.mail.epoch-root.v1", MSEK)`, then each epoch key with the epoch index folded into the key material — `BLAKE3::derive_key(context = "fauna.mail.recipient-hpke-epoch.v1", key_material = epoch_root ∥ LE64(e))` (X25519 half; ML-KEM-768 half under the epoch ML-KEM context, mirroring the standing X-Wing shape; `libs/fauna-mls/src/wrapped_blob/mls_snapshot_plaintext.rs`, golden-byte-pinned). Independent PRF outputs per epoch — deliberately **not** a chain, so a wrapped set of epoch secrets bounds forward derivation (the capability-expiry requirement). Same fleet-consistency, same rotation story: rides MSEK; hard-revoke resets the epoch lineage; **grace is the intermediate root, not the prior MSEK** — the snapshot's additive `mail_epoch_grace_roots` carries one 32-byte root per prior grace generation (aligned with `leaf_init_keypairs[1..]`), complete for that generation's mail-epoch reads and powerless beyond them (rule #3's least-privilege shape — the reason the two-step split exists: under a one-step `MSEK ∥ LE64(e)` derivation, rotation grace would require carrying the raw prior MSEK or an unbounded secret enumeration). The epoch-aware MDA opener repeats its trial chain per root (current generation's root re-derived from the session MSEK, then each grace root); the opener retains only the scoped roots, never the MSEK. For **windowed (bounded) grants**, cross-generation coverage of a rotation-boundary epoch never wraps a root: the single per-epoch wrap's payload concatenates each qualifying generation's 2432-byte per-epoch secret (newest first, chunk-trialed, AEAD-arbitrated), with qualification computed from the rotation instants recorded in `MailConfig.prior_msek_retirements` (keyed by the prior-MSEK value — the merge reorders `prior_mseks`, so alignment is never positional) — mechanism owner: `encryption-at-rest.md` § Capability tiering, amendment 2026-07-19. **The write flip landed 2026-07-19** (`MAIL_EPOCH_SEALING_WRITE_DEFAULT = true`) — newly ingested mail for a recipient with a published epoch schedule now seals under these per-epoch keys; pre-flip content and recipients with no published schedule stay on the standing recipient-mail keypair. Full flip-checklist status: `encryption-at-rest.md` § Capability tiering → Content-sealing epochs.

#### Path B-sibling-3 — `WebdavKeysBlob` (MSEK-sealed served-set content keys) — ratified 2026-07-06; built (`docs/goal/behavior/webdav-server.md` § Key model owns status)

The per-actor blob that carries the M2 content keys of the folders the user has **explicitly flagged "serve over WebDAV"** to the MDA bridge. Same shape and discipline as `MlsSnapshotBlob`: sealed under MSEK, stored opaque on nest (`bridge_webdav_keys_blobs`), provisioned/refreshed by the user's client (`fauna.bridges.provision_webdav_keys_blob`), fetched + unsealed by the MDA at MUA-AUTH, held in `zeroize::Zeroizing<…>` mlocked memory for the session, zeroized on session end.

- **Root:** MSEK (the wrap); the *contents* are the served sets' `FolderContentKeys` generation bundles ([`mls-group-key-material.md`](mls-group-key-material.md) § Audience: an MLS group → M2) — random per-set material, not MSEK-derived.
- **Protects (conveys):** per served set `{set_name, read_only, content-key generations}` — read AND write capability over exactly those sets (the `chunk_crypto` AEAD is symmetric). Never `BackupKey`, never an unserved set's key, never MLS group/epoch state (rule #7).
- **Audience justification:** the user, reaching their *own served files* via a generic WebDAV client that cannot decrypt Fauna's sealing — the same Path-B audience as MSEK, extended per-set by explicit opt-in.
- **Rotation / revocation:** unflagging a set rotates its content key (the M2 rotate machinery) and re-provisions the blob without it; MSEK rotation re-wraps the blob like the snapshot. The owner's own client-side convergence of the served-era back-catalogue onto the owner root — the client-only mechanism this rotation makes necessary — is `webdav-server.md` § Key model's Revocation bullet, not this blob's concern.
- **Why a second blob and not the snapshot:** the snapshot is permanently scoped to mail/calendar read material (rule #7's supersession note); served-set keys have an independent lifecycle (per-set flag flips, content-key rotations) and a distinct consumer path — folding them into the snapshot would couple refresh cadences for no gain.

#### Path B-sibling-4 — Mail/calendar index-segment key (MSEK-derived) — RATIFIED 2026-08-02 (backend-2 rollout S0); derivation BUILT 2026-08-02 (S1), snapshot grace field + grace-list READER BUILT 2026-08-03 (S5), the Go MDA that DRIVES it BUILT 2026-08-03 (S5 — build half; serving `SEARCH` from the slice is the remaining half)

The per-kind wrap key of the content-index per-kind key split (`docs/goal/behavior/content-index.md` § Encryption posture, which owns the manifest-split mechanics): mail-kind and calendar-kind index segments' per-segment data keys, and the `__index/manifest-mailcal.idx` mail/calendar manifest, are sealed under this key instead of the content-index **master** key — which is what bounds a MUA credential's index reach to mail/calendar (rule #7) while letting the MDA bridge build and query those two slices in-session.

- **Root:** the actor's MSEK (Path B).
- **Derivation:** `BLAKE3::derive_key(context = "fauna.mail.index-seg.v1 2026-08-02", key_material = MSEK)` → 32-byte symmetric key (rule #3: fresh, versioned, dated context string). Deterministic per MSEK → fleet-consistent, exactly like § Path B-sibling-2: every client derives it from the account's MSEK in its mail custody (the client-builder leg needs no snapshot), and the MDA derives it from the session MSEK at MUA-AUTH. The derivation lives beside the sibling derivations in `libs/fauna-mls/src/wrapped_blob/` (golden-byte-pinned when built); `fauna-index` consumes the 32 bytes opaquely (its `key.rs` stance).
- **Custody of the derived bytes (ratified 2026-08-05, alongside § Path A-sibling):** identical rule to the master key — the custody type is **`fauna_index::IndexSegmentKey`** (non-`Copy`, zeroizing) and the derivation returns **`Zeroizing<[u8; 32]>`** rather than a bare `Copy` array. The two index-key derivations were fixed **together on purpose**: the finding that prompted it named only the master key, but repairing one member of a two-member family would have created exactly the divergence priority #4 forbids, since both derivations had the same bare-array shape and the same consuming-newtype relationship. Compile-time pin `_INDEX_SEGMENT_KEY_IS_NOT_COPY` in `libs/fauna-mls/src/wrapped_blob/mls_snapshot_plaintext.rs`; see § Path A-sibling for the full reasoning and for why no second `fauna-core`/`fauna-mls` newtype is minted.
- **AEAD use:** wrap key for mail/calendar per-segment data keys (48-byte wrapped-DK field of the segment framing) and the direct AEAD key for `manifest-mailcal.idx` (master-direct framing) — XChaCha20-Poly1305, the crate's framing, never a new envelope.
- **Protects:** the mail-kind + calendar-kind slices of the user's `__index` set — and nothing else; the master key (Path A-sibling) keeps every other kind. Never conveys mail *content* keys — a holder can read index tokens over mail/calendar, not mail bodies (those need § Path B-sibling-2).
- **Audience justification:** same audience as MSEK (Path B) — the user's clients (via their own MSEK) and the MDA bridge during an active session. The nest never holds it (no-modes, unconditional).
- **Snapshot carriage (the precise form of the "will carry" statements in § What MSEK seals and rule #7):** the **current** generation's key is *never carried* — it re-derives on demand from the session MSEK, exactly like the current mail-epoch root; **grace** rides the snapshot as an additive `index_seg_grace_keys` field on `MlsSnapshotPlaintext` — one 32-byte derived key per prior grace MSEK generation, newest first, aligned with `leaf_init_keypairs[1..]`, omitted when empty (the `mail_epoch_grace_roots` shape verbatim). **BUILT 2026-08-03** (S5's first piece): the field is on `MlsSnapshotPlaintext` and `build_mls_snapshot_plaintext` fills it from the same `take(SNAPSHOT_GRACE_KEYPAIRS).skip(1)` history slice as the mail-epoch roots, so both real producers — enable-mail (`fauna-client-mail-settings/src/machine.rs`) and rotation (`.../rotation.rs`) — emit it today. It shipped **ahead of its reader on purpose** — the field must be *at rest in already-published snapshots* before any consumer can rely on it, so shipping it together with the reader would have stranded every snapshot written before that day.

  **The reader landed the same day (2026-08-03):** `fauna_client_index::MailcalKeyRing` builds `[derive(session MSEK)] ++ [each `index_seg_grace_keys` entry]` — the `MailRecordOpener::new_with_msek` shape verbatim — and `open_segment` / `open_manifest` walk it newest-first, returning the first key that opens the blob. Two properties are load-bearing and pinned: **reads** try the whole ring, while **writes** use the current generation only (sealing under a grace key would extend a superseded generation's reach forward, which is what rotation exists to end); and a blob outside the ring is refused with an error that names the miss as a ring exhaustion, so a segment older than the grace window reads as a rewrap-pass gap rather than corruption. Both `__index` rail reads go through it, so the client leg and the MDA leg inherit rotation grace from one implementation.
- **Rotation:** rides MSEK, like sibling-2. On MSEK rotation the rotating client re-wraps every mail/calendar segment header to the new generation's key (`rewrap_segment_master_key` — O(header) per segment, bodies untouched) and re-seals `manifest-mailcal.idx`, in the same pass that re-provisions the snapshot; the grace list covers the convergence window (the MDA trial-opens per grace key, as the epoch opener does per grace root). Hard-revoke: the grace list is dropped with `prior_mseks`, and un-rewrapped segments become unreadable to the bridge until a client's rewrap pass — fail-closed, never data loss (clients re-derive every generation they still hold).
- **Threat model:** anyone holding MSEK derives it — same exposure class as the snapshot. A leaked MUA credential (+ at-rest access) reads the user's mail/calendar *search tokens*; it never reaches the conversations/posts/contacts/drafts/media slices (master-key-wrapped, Path A) — the § Trust property under compromise bound.
- **Why not the master key with a narrower grant:** the master key is one key over the whole corpus (rule #2 — one key per audience); handing it to the bridge session-scoped would put the full cross-kind corpus inside the MUA-credential blast radius, which is precisely what rule #7 forbids. A second key with a genuinely different audience is the rule-#2-conformant shape, and the manifest split is what makes it real at the file layer.
