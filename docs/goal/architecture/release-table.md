## Release-candidate run

**`just e2e-release-candidate <image> [--app …]`** — the run whose stamps carry a bare version. It refuses to start unless:

- the working tree is **clean** — `git status --porcelain` empty outside `docs/features/ledger/`, the run's own output; § The ledger's *Dirty trees* is the one definition, and the gate reads the very function the ordinary run marks by — and
- **HEAD equals the image's `FAUNA_BUILD_COMMIT`** — or the image is the public repository's build of the tree published from HEAD, its `FAUNA_BUILD_COMMIT` a public commit paired with HEAD as § Tag gate and release table's *Promotion copies the tested digest* states — (`bins/fauna-nest/src/build_identity.rs`; the value is an `ENV` in the image's shipped stage, readable by `docker inspect` without booting it — set there since 2026-08-29: every image built before then carried it only compiled into the binary, so this precondition refused them all and no candidate run had ever been possible; pinned by `tests/e2e-unified/tests/test_feature_ledger.py`), and
- the image has a **registry digest** (`RepoDigests` non-empty — a locally built image has none; a candidate is always the immutable `:sha-<commit>` tag the pipeline pushed, [`image-pipeline.md`](image-pipeline.md) § Image tags & channels).

It then runs the suite in **`docker` mode against exactly that image** (`--nest docker:<image>` — tier_3 journeys elevate to tier_4 at collection, [`testing.md`](testing.md) § Default app and nest mode) with `--release-candidate`, which the ledger writer honours only after re-verifying the same three preconditions itself (defence in depth: the recipe is the convenient door, the plugin is the gate). Every ledger line and cell it writes is stamped **`<version> docker`** where `<version>` is `Cargo.toml [workspace.package] version` at HEAD — **there is no version argument**: the bump commit already allocated the number ([`product-version.md`](product-version.md) § Bumping), and a run cannot claim a version its commit does not carry. Alongside, it writes the row's `candidate_run` date into `releases.json` — minting the (version, commit, digest, date) row, or upserting into the one `just release-verified` already minted for this build (§ Tag gate and release table).

**The two halves are deliberately not symmetric.** The nest under test is the **byte-identical shipped artifact** — the digest is what promotion copies. The app half is necessarily an **e2e-flavoured build of the same commit**: the automation surface is compiled out of release builds on every app ([`e2e-automation-surface-gating.md`](e2e-automation-surface-gating.md) convention 15), so no release binary can be driven. A bare-version stamp on an app cell therefore means "the app *source* at the released commit, driven through its UI, against the released nest artifact" — the strongest witness the convention allows, and the legend says so once. The artifact suites (`tests/artifact/`) are the exception that drives a release-shaped client, and the install row is what they witness.

## Tag gate and release table

**`just release-tag`** mints the `v<version>` tag — and there is no other sanctioned way to mint one. It refuses unless `releases.json` holds a **release-candidate run at exactly HEAD's commit AND exactly one image digest** — the same lesson [`image-pipeline.md`](image-pipeline.md) § Image tags & channels learned for promotion (*verify the artifact, not just the commit*: a commit can have several builds; the tested one is the only one the tag may name). A fix after a candidate run means a new commit, a new image, a new run — **the same version string is legal until it ships** ([`product-version.md`](product-version.md) § Version strings are never reused), so the sequence is: bump → build → candidate run → (fix → build → run)* → tag → promote (the promote being the public repository's `:latest` since 2026-10-02 — the next paragraph). Pre-1.0 the gate asks that the run **happened and was recorded**, not that it was green everywhere (§ Goal).

The tag is a **git tag**, created by the recipe on HEAD; no tag exists yet on either repository, so the recipe — not a workflow precondition — is where the gate lives. `release.yml` (in the public-files tree since 2026-08-31 — [`release-integrity.md`](release-integrity.md) § Release signing → *When a release workflow publishes*) fires on `v*` tags pushed to the **public** repository, so the public tag that cuts a binaries release is a separate deliberate act after `just release-tag` mints the internal one that names the release. **Every version release pushes it (ruled by the owner 2026-10-14):** one train, one tag, and every installer the version ships is built by the public release workflows from it. The tag is pushed from the standing mirror by `fauna-publish`, the only push path to the public repository ([`publish-gates.md`](publish-gates.md) § Local-merge gates → *The standing mirror and the push origin*), and the push **refuses unless every Environment a release workflow publishes through (`release`, `release-macos`) carries a required reviewer and a deployment rule admitting `v*` tags only**. The first run that references a missing Environment creates it unprotected ([`release-integrity.md`](release-integrity.md) § Release signing → *When a release workflow publishes*, item 1), so the tag is the last point where that can be refused. **Where the tag sits (ruled by the owner 2026-10-14, taking the recommendation put to them): at UAT entry, as a pre-release.** The push follows the stage that moved `:test` + `:<version>`, the candidate run against that image and the internal tag `just release-tag` mints — so the public tag names the one commit and digest the run recorded, and the step refuses without the internal tag, without the two protected Environments, without a green deploy of the site at the internal tag's commit (the train's site surface, [`product-version.md`](product-version.md) § Bumping), when the version string is not the public commit's own, and when the public repository already holds the tag — and both release workflows create the version's GitHub Release as a **pre-release**: the direct-download channel's pre-release track (the Windows MSI, the `.dmg`, the Linux and terminal binaries), the counterpart of the stores' TestFlight, Play-testing and private-audience tracks ([`image-pipeline.md`](image-pipeline.md) § Image tags & channels, the UAT bullet, decision (4)), so a tester who downloads rather than installs from a store meets the version under acceptance. After the promote to `:latest` — the UAT sign-off — `fauna-publish release` flips the pre-release to the release: the direct-download channel's public release, after the promote exactly as half (b) below orders a store's. A version that fails UAT stays a pre-release for good, as its `:<version>` image stays staged — the string is spent, never reused. Each of the two acts is world-visible and runs only on the owner's in-the-moment GO, like the sync PR; the release jobs additionally wait for the owner's approval in their Environment on every run. The alternative — one tag after the promote, a full release at once — was declined: it keeps every direct-download tester out of acceptance. Both steps are `fauna-publish`'s (§ Implementation status today).

**The commit a tag names is a `main` commit (owner-ruled 2026-10-17).** The release source is always an `origin/main` tip and a fix is a new tip ([`release-attempt.md`](release-attempt.md) § The release attempt), so the candidate run's HEAD, the internal tag, the public commit's `Sync-Point:` and the ledger's ancestor ordering all name commits on `main`; the base-pin-plus-cherry-picks source 0.1.4 was published from is retired, and 0.1.4 itself takes no tag ([`product-version.md`](product-version.md) § Current values). The public tag push and the release flip follow the one go the version's text received with no further chat go; each release workflow's Environment approval stays the owner's.

**The nest precedes the apps, in two halves (ruled 2026-10-10; re-cut 2026-10-13 with the UAT channel — [`image-pipeline.md`](image-pipeline.md) § Image tags & channels, the UAT bullet).** The organisation's acceptance nest tracks `:test`, the UAT channel, and is where a store reviewer signs in ([`org-nests.md`](org-nests.md) § fauna.build), so a reviewer must meet the version under review and never the one before: **(a)** the nest reaches `:test` and the acceptance nest serves it before the matching app build is uploaded to any store's pre-release track (TestFlight external, Play testing, the Store's private audience — each installer doc owns its own track) — and, **ruled 2026-10-20 (owner, as proposed 2026-10-18 — wait by default, withdrawing is the owner's)**, `:test` does not move past a version while a store review of that version's app build is open: the next version's first public image dispatch waits for the last open review to close, unless the owner withdraws it and lets that version's store release go unmade; the hold binds only while a reviewer can meet a mismatched nest (throughout 0.1.x, and at each major bump) and only once the acceptance nest serves reviewers at all — what counts as open, the record it reads and the owner's choice are [`installers/store-review.md`](installers/store-review.md) § The `:test` hold's; **(b)** the promote to `:latest` lands before the public store release of the same version. Within a major version the wire compatibility rule would make the order a courtesy; under 0.1.x, which owes no compatibility, it is the only thing keeping them matched. Of the two halves only half (a)'s hold is enforced, by the public image dispatch; the upload order and half (b) are not (§ Implementation status today).

**Promotion copies the tested digest.** The nest image promoted to the public repository's `:latest` (`:<version>` moves earlier, at UAT entry beside `:test`, from the same digest — [`image-pipeline.md`](image-pipeline.md) § Image tags & channels, the UAT bullet) — the only promote left after the 2026-10-02 channel ruling: the private repository stages and verifies and promotes nothing (owner of both pipelines: [`image-pipeline.md`](image-pipeline.md) § Image tags & channels) — must be the digest the candidate run recorded; the target state of that promote step is "green verify at test.fauna.build **and** a tag whose release-table row carries this digest". Under the two-pipelines design (2026-10-09, [`image-pipeline.md`](image-pipeline.md) § Image tags & channels, part 4) the public repository builds its OWN artifact of the published tree, so the digest here is the PUBLIC build's: the candidate run drives the public `:test` image, and the promoted row is keyed on the private commit the public one was published from with `public_commit` recorded beside the digest (`just release-promoted <commit> --public-commit <sha>`). **The pairing is the public commit's `Sync-Point:` trailer** — every public sync commit the publish tool writes names the private rev it snapshotted, and the squash-merge keeps the message — read in the standing mirror (or `--public-clone <dir>`): a public commit pairs with a private one exactly when its Sync-Point is a prefix of it. The candidate run accepts a public build on that pairing, keys its row on HEAD and records the image's own commit as `public_commit`; `release-promoted --public-commit` refuses an unpaired commit, and one other than the `public_commit` the candidate run already recorded (one helper, `tests/e2e-unified/helpers/feature_ledger.py::public_build_refusal`, for both). Until the public pipeline first runs nothing promotes and `promoted` stays `false` on every row.

**The release table** (`releases.json`, rendered into `MATRIX.md`): one row per build the catalog has something to say about (re-keyed 2026-10-02 with the private `:latest`'s retirement; one row per candidate run before) — `version`, `commit` (the repository's git object id, sha1), `image` (the exact tag the run drove) and `image_digest`, `date` (the row's newest observation), **`verified`** (the date the private pipeline's verify gate went green on this build — written by **`just release-verified <headSha>`** in the dispatching session; the field the pin derives from), **`candidate_run`** (the date of the newest release-candidate run — written by the run itself; the field the tag gate reads, so a verified-only row never satisfies it), `promoted` (boolean: this digest became the **public** repository's `:latest` — flipped by **`just release-promoted <commit>`** in the session that drives that promote, dormant until the public pipeline exists), and `shipped_apps`, the **per-app shipped version** where a store carve-out shipped one app at a later patch (§ Release train). It is the one record of what was released: the reader sees at a glance which builds reached the staging box, which were measured, which became production, and which app, if any, lags. A row is minted by whichever act comes first — `just release-verified` or the candidate run — and the other upserts into it on the key below; the digest both record is the registry's manifest-list digest of `ghcr.io/faunasocial/nest:sha-<sha>` (`docker image inspect`'s `RepoDigests` for the pulled tag, `docker buildx imagetools inspect` for the un-pulled one), the same identity, so the key agrees. **`just release-verified` resolves the digest off the registry and never reconstructs it**; `--digest` overrides for a registry the session cannot reach.

**A row is keyed on `(commit, image_digest)` and upserted, never blindly appended.** A candidate run is re-runnable by design — a flake, a wider `--app` set, a second machine's leg — and re-running the *same* artifact at the *same* commit is one release observed twice: the date and `candidate_run` advance, `verified` and `promoted` are preserved, no second row appears. Only a genuinely different build of the same commit is a second row, and that is exactly the case the tag gate refuses. Without the upsert the gate's "exactly one digest" would be satisfiable one moment and ambiguous the next for no reason but a repeat run.

**The row's own commit and digest are allowlisted for the publish gate in the same act that writes them.** Both are bare hex runs in a shipped tree (`matrix.json`, `MATRIX.md`, the derived pin), and `secret_scan` default-denies those, so a release would otherwise red the merge that lands it — the trap the pin file's header has warned about since 2026-07-12 and that took `origin/main` red on 2026-08-27 over four commit SHAs of the version-skew grid's own. `just release-promoted` therefore appends entries to the publish gate's approved-secret-fixtures allowlist alongside the render, with a reason naming the release row. The values are public by construction — a commit in this repository's history, and what `docker pull …@sha256:…` resolves — so the decision the allowlist records is a standing one about a *class*, not a fresh judgement per release; a release process whose every use reds the merge gate is one people route around.

**The pin is derived from it.** `tests/e2e-unified/pinned-previous-build.toml` — "the most recent verified staged build pair", [`version-compatibility.md`](version-compatibility.md) § Dimension 6 (re-ruled 2026-10-02; "production release pair" until the private `:latest` was retired) — is written by `just features-render` from the newest row carrying a `verified` date (newest by that date, ties by position), and the lint checks it (rule 5). Its semantics are unchanged and still owned there; what changed in 2026-08-27 is that it is no longer a second hand-maintained copy of a fact the release table already holds, and `just release-verified` is the act that advances it (`release-promoted` did, until the private promote was retired; it now records the public `:latest` only). **Newest by `verified`, never by date alone**: a candidate that went red at the verify gate never proved it serves anywhere, and pinning it would aim the whole skew grid at an artifact nobody runs — which is the distinction § Dimension 6's update rule is built on.

## Release train

**A release is a train — the nest and all seven apps ship simultaneously at one version, with the store-mechanical reship as the one carve-out.** Owner: [`product-version.md`](product-version.md) § Bumping (ratified 2026-08-26, user-confirmed). What this catalog contributes: the candidate run stamps the train's version on every cell it witnesses (§ Release-candidate run), the tag gate makes the train's tag conditional on a recorded run (§ Tag gate and release table), and the release table's **per-app shipped version** is where a reship carve-out becomes visible instead of inferred from a store's sparse history.

## Implementation status today

**The nest-before-apps order (2026-10-10, re-cut in two halves 2026-10-13) is enforced only in half (a)'s `:test` hold:** `fauna-publish stage <version>`, the public image dispatch, refuses while a store review of the version `:test` serves is open (since 2026-10-20; [`installers/store-review.md`](installers/store-review.md) § The `:test` hold). Otherwise the order is stated, not enforced: no script refuses a pre-release-track upload whose version is not yet on `:test`, nor a public store release whose version has not been promoted; the acceptance nest it protects does not exist yet, so the first enforcement point is that nest's provisioning track or the store rows that follow it.

**The public version tag (ruled 2026-10-14; § Tag gate and release table): the sequence is ratified, the Environments are protected, and both steps are built; no tag has been pushed.** `fauna-publish tag <version>` pushes the annotated public tag from the standing mirror, and refuses without the internal annotated tag, without a single-digest candidate row at that tag's commit recording a `public_commit`, when that public commit's Sync-Point does not pair with it or it is not on public `main`, when its `Cargo.toml` is another version, when the public repository already holds the tag, without a green `deploy-site.yml` run at the internal tag's commit (read live from the run titles, since 2026-10-17), and unless both Environments read live as protected; `fauna-publish release <version>` finds the promoted row by the internal tag's commit — never by the version string, which may carry several rows — and flips the pre-release, a no-op on one already flipped. Both release workflows' publisher steps create a pre-release, pinned by the public-workflows shape test; the publish tool's own tests drive every refusal against a throwaway mirror whose `origin` is a local bare repository, with `gh` faked. No `v*` tag exists on the public repository. The `release` and `release-macos` Environments were created on 2026-10-14 by the version-release session on the owner's word, through `gh api`, and read back: one required reviewer (the maintainer account), self-review allowed (the account that pushes the tag is the one that approves), administrator bypass off, and exactly one deployment rule, tags `v*`. The tag step's refusal reads those facts live on every run, never this record. The first tag — 0.1.4's — also waits on the public Release workflow's first green dry run.

**Re-keyed 2026-10-02, built 2026-10-12:** § Tag gate and release table's `verified` and `candidate_run` fields, `just release-verified` (the version read at the dispatched commit, the digest resolved off the registry or passed with `--digest`), the pin's derivation from the newest `verified` row (`scripts/features_catalog.py::newest_verified`, which rule 5 checks) and the tag gate reading `candidate_run` only. `just release-promoted` no longer writes the pin. **No build has been recorded through it yet**: the table is still empty and the committed pin is the last hand-written one (its header already the derived text); the first green verify after this is what exercises `just release-verified` end to end. The `public_commit` field, the candidate run's acceptance of a Sync-Point-paired public build and `release-promoted --public-commit` (2026-10-09, § Tag gate and release table) are built 2026-10-13, with `public_commit` rendered beside the digest in `MATRIX.md` and allowlisted for `matrix.json` — tested on throwaway trees, never yet against a real public build; the public promote itself (`scripts/release-nest-image.sh promote`, which verifies the signature the public stage made) is built and has not run. The ruling behind the re-key — the private repository's `:latest` is retired — is [`image-pipeline.md`](image-pipeline.md) § Image tags & channels'.
