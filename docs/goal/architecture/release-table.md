## Release-candidate run

**`just e2e-release-candidate <image> [--app …]`** — the run whose stamps carry a bare version. It refuses to start unless:

- the working tree is **clean** — `git status --porcelain` empty outside `docs/features/ledger/`, the run's own output; § The ledger's *Dirty trees* is the one definition, and the gate reads the very function the ordinary run marks by — and
- **HEAD equals the image's `FAUNA_BUILD_COMMIT`** — or the image is the public repository's build of the tree published from HEAD, its `FAUNA_BUILD_COMMIT` a public commit paired with HEAD as § Tag gate and release table's *Promotion copies the tested digest* states — (`bins/fauna-nest/src/build_identity.rs`; the value is an `ENV` in the image's shipped stage, readable by `docker inspect` without booting it — set there since 2026-08-29: every image built before then carried it only compiled into the binary, so this precondition refused them all and no candidate run had ever been possible; pinned by `tests/e2e-unified/tests/test_feature_ledger.py`), and
- the image has a **registry digest** (`RepoDigests` non-empty — a locally built image has none; a candidate is always the immutable `:sha-<commit>` tag the pipeline pushed, [`image-pipeline.md`](image-pipeline.md) § Image tags & channels).

It then runs the suite in **`docker` mode against exactly that image** (`--nest docker:<image>` — tier_3 journeys elevate to tier_4 at collection, [`testing.md`](testing.md) § Default app and nest mode) with `--release-candidate`, which the ledger writer honours only after re-verifying the same three preconditions itself (defence in depth: the recipe is the convenient door, the plugin is the gate). The same flag gives the run a slot lane of its own, `e2e_rc`, in place of the long lane the dev-tree runs and the verify drain share, so the release's witness and the queue never wait on each other ([`build-slot-pool.md`](build-slot-pool.md) § the `e2e` pool bullet → the release-candidate lane). Every ledger line and cell it writes is stamped **`<version> docker`** where `<version>` is `Cargo.toml [workspace.package] version` at HEAD — **there is no version argument**: the bump commit already allocated the number ([`product-version.md`](product-version.md) § Bumping), and a run cannot claim a version its commit does not carry. Alongside, it writes the row's `candidate_run` date into `releases.json` — minting the (version, commit, digest, date) row, or upserting into the one `just release-verified` already minted for this build (§ Tag gate and release table) — with the publish-gate entries the row's hex needs in the same act (`release_gate.record_candidate`); an invocation that ran no test (a collection refusal) records nothing. **The suite runs as two invocations (2026-11-11):** `drafts_autosave_window_ms` re-times the drafts debounce for every app of its session, so conftest refuses a selection holding it beside a production-window test, and the recipe runs `-m "not drafts_autosave_window_ms"` and then `-m drafts_autosave_window_ms`, the second whatever the first reported — both `--release-candidate`, both upserting the one row (0.1.6's single invocation ran nothing).

**The two halves are deliberately not symmetric.** The nest under test is the **byte-identical shipped artifact** — the digest is what promotion copies. The app half is necessarily an **e2e-flavoured build of the same commit**: the automation surface is compiled out of release builds on every app ([`e2e-automation-surface-gating.md`](e2e-automation-surface-gating.md) convention 15), so no release binary can be driven. A bare-version stamp on an app cell therefore means "the app *source* at the released commit, driven through its UI, against the released nest artifact" — the strongest witness the convention allows, and the legend says so once. The artifact suites (`tests/artifact/`) are the exception that drives a release-shaped client, and the install row is what they witness.

**The regression verdict (owner-ruled 2026-11-06, with the UAT sign-off re-ruled to the acceptance set — [`image-pipeline.md`](image-pipeline.md) § Image tags & channels, the UAT bullet, decision (2)).** Pre-1.0 the run is a measurement for the tag gate (§ Tag gate and release table), and the promote's sign-off reads it as a verdict: **`just release-acceptance [<version>] [--against <v>]`** grades every cell the version's `<version> docker` records cover — a cell is one (ledger file, feature) pair — against the same cells of the **previous release**: the newest promoted version below it, and while none below it is promoted the newest with a candidate run (a version is released by its candidate run). A cell is **red** when any of its records is a real red (`failed`, `error`, `xfailed` or an unclassed skip — the catalog's own reading, [`feature-catalog.md`](feature-catalog.md) § Cell semantics), **green** when none is and one passed, and says nothing when every record is a classed skip. It **refuses** on a cell green at the previous release and red now, on a red cell the previous release's run never read, and on a red record of a test carrying **`@pytest.mark.release_gate`** whatever its cell did before (the marker a test carries when its red alone must hold a version); a cell red at both is reported as still red and not refused — a known defect is not this version's regression — and so are the fixed cells and the cells the previous run read and this one did not. The records are read from the ledger's **git history**, not its tip: a record holds one slot per platform and the next dev run overwrites it ([`feature-ledger.md`](feature-ledger.md)), so every commit whose ledger diff touches the stamp is read, oldest first, then the working tree, the newest record per (file, feature, test, platform) winning — a re-run of the same version supersedes its earlier legs. The verdict reads only: the tag gate is unchanged.

**A test-side correction after the cut reaches the verdict through a correction run (ruled 2026-11-11).** The verdict stays a reading of committed data — the ledger's history and the release table — and of nothing else: no test is waived by hand and the grading tree's classifier is never consulted, so a version's verdict is the same whoever grades it and whenever. A correction made on the test side after the version's commit — a harness defect fixed, an exclusion the classifier now infers — reaches it only through a **correction run**: `just e2e-release-candidate <image>` from a **correction tree**, which the commit precondition accepts as a third shape beside the two above. A correction tree is the version's commit (the commit either of those two shapes accepts as HEAD) plus commits that **(i)** change only **test-side paths** — `tests/`, the run's own ledger output, Rust that is compiled only under the `e2e-harness` feature, and the release gate's own script (`release_gate.py`), which writes the run's record and ships in no artifact, so a tree branched at a version's commit carries the gate that accepts it (one constant in the gate; a test pins each Rust entry to sit behind that `cfg`) — and **(ii)** each carry the `(cherry picked from commit <sha>)` trailer of a commit that is an ancestor of `origin/main`: a correction lands on main first and is carried back, never written on the side. The image and the product source the app half is built from are then exactly the version's, so the bare-version stamp means what it meant (the paragraph above on the two halves). The run stamps `<version> docker` as always (the version file is not a test-side path) and writes no new release-table row: it upserts the version's own row, keyed on the version's commit and never on the correction tree's, adding one entry to the row's **`corrections`** list — the date, the main commits carried, and the exclusions below. It is normally a focused selection of the tests the correction touches, and its records supersede the earlier legs by the newest-wins reading. **A test the correction tree now excludes writes no record** ([`testing.md`](testing.md) § Default app and nest mode: a test a mode cannot serve is never recorded), so its old red would stay the newest for good; the correction run therefore lists, in its `corrections` entry, every selected test its collection gates under a FACT rule (`helpers/nest_surface.py::FACT_RULES`) for which the version's history holds a real red, each with the rule that gates it — written by the run from the classifier's own verdict, never by hand. The verdict sets a listed test's records aside before grading its cell, for the version and for the previous release alike, and reports them as **excluded since the cut**, never as a refusal — a `release_gate` test included: the exclusion says the artifact can never serve the test. A test gated under a MIXED rule is not listed: a closable gap is not a fact about the artifact, and its red stands. What a correction run cannot carry is a change outside the test-side paths — that is a new commit, a new image and a new run (§ Tag gate and release table), and for a version that has shipped, a new version. Declined: the grader reading a current-tree `--nest-gates-json` payload (the verdict would move with main's classifier and cost a build per grading), a re-run from a later tree of main (the app half would no longer be the released source), and a hand-written per-test waiver (against [`testing.md`](testing.md)'s *Exclusion is inferred, never hand-listed*).

## Tag gate and release table

**`just release-tag`** mints the `v<version>` tag — and there is no other sanctioned way to mint one. It refuses unless `releases.json` holds a **release-candidate run at exactly HEAD's commit AND exactly one image digest** — the same lesson [`image-pipeline.md`](image-pipeline.md) § Image tags & channels learned for promotion (*verify the artifact, not just the commit*: a commit can have several builds; the tested one is the only one the tag may name). A fix after a candidate run means a new commit, a new image, a new run — **the same version string is legal until it ships** ([`product-version.md`](product-version.md) § Version strings are never reused), so the sequence is: bump → build → candidate run → (fix → build → run)* → tag → promote (the promote being the public repository's `:latest` since 2026-10-02 — the next paragraph). Pre-1.0 the gate asks that the run **happened and was recorded**, not that it was green everywhere (§ Goal).

The tag is a **git tag**, created by the recipe on HEAD; the gate is checked before every public push, so the recipe — not a workflow precondition — is where the gate lives. `release.yml` (in the public-files tree since 2026-08-31 — [`release-integrity.md`](release-integrity.md) § Release signing → *When a release workflow publishes*) fires on `v*` tags pushed to the **public** repository, so the public tag that cuts a binaries release is a separate deliberate act after `just release-tag` mints the internal one that names the release. **Every version release pushes it (ruled by the owner 2026-10-14):** one train, one tag, and every installer the version ships is built by the public release workflows from it. The tag is pushed from the standing mirror by `fauna-publish`, the only push path to the public repository ([`publish-gates.md`](publish-gates.md) § Local-merge gates → *The standing mirror and the push origin*), and the push **refuses unless every Environment a release workflow publishes through (`release`, `release-macos`) carries a required reviewer and a deployment rule admitting `v*` tags only**. The first run that references a missing Environment creates it unprotected ([`release-integrity.md`](release-integrity.md) § Release signing → *When a release workflow publishes*, item 1), so the tag is the last point where that can be refused. **Where the tag sits (ruled by the owner 2026-10-14, taking the recommendation put to them): at UAT entry, as a pre-release.** The push follows the stage that moved `:test` to the candidate, the candidate run against that image and the internal tag `just release-tag` mints — so the public tag names the one commit and digest the run recorded, and the step refuses without the internal tag, without the two protected Environments, without a green deploy of the site at the internal tag's commit (the train's site surface, [`product-version.md`](product-version.md) § Bumping), when the version string is not the public commit's own, and when the public repository already holds the tag — and both release workflows create the version's GitHub Release as a **pre-release**: the direct-download channel's pre-release track (the Windows MSI, the `.dmg`, the Linux and terminal binaries), the counterpart of the stores' TestFlight, Play-testing and private-audience tracks ([`image-pipeline.md`](image-pipeline.md) § Image tags & channels, the UAT bullet, decision (4)), so a tester who downloads rather than installs from a store meets the version under acceptance. After the promote to `:latest` — the UAT sign-off — `fauna-publish release` flips the pre-release to the release: the direct-download channel's public release, after the promote exactly as half (b) below orders a store's. **The flip also refuses while no green `deploy-site.yml` deploy exists at a commit of the version — the sync point, or a dead-link fix on private main carrying the same version (2026-11-11)**: fauna.social is part of the release, so the release is not flipped before its site is live; the flip, like `promote-ready`, reads that newest green deploy and records the site `live` in the release table (below), so no session has to run `deploy-site` a second time. A version that fails UAT stays a pre-release for good, as its `:<version>` image stays staged — the string is spent, never reused. Each of the two acts is world-visible and runs only on the owner's in-the-moment GO, like the sync PR; the release jobs additionally wait for the owner's approval in their Environment on every run. The alternative — one tag after the promote, a full release at once — was declined: it keeps every direct-download tester out of acceptance. Both steps are `fauna-publish`'s (§ Implementation status today).

**The commit a tag names is a `main` commit (owner-ruled 2026-10-17).** The release source is always an `origin/main` tip and a fix is a new tip ([`release-attempt.md`](release-attempt.md) § The release attempt), so the candidate run's HEAD, the internal tag, the public commit's `Sync-Point:` and the ledger's ancestor ordering all name commits on `main`; the base-pin-plus-cherry-picks source 0.1.4 was published from is retired, and 0.1.4 itself takes no tag ([`product-version.md`](product-version.md) § Current values). The public tag push and the release flip follow the one go the version's text received with no further chat go; each release workflow's Environment approval stays the owner's.

**The nest precedes the apps, in two halves (ruled 2026-10-10; re-cut 2026-10-13 with the UAT channel — [`image-pipeline.md`](image-pipeline.md) § Image tags & channels, the UAT bullet).** The organisation's acceptance nest tracks `:test`, the UAT channel, and is where a store reviewer signs in ([`org-nests.md`](org-nests.md) § fauna.build), so a reviewer must meet the version under review and never the one before: **(a)** the nest reaches `:test` and the acceptance nest serves it before the matching app build is uploaded to any store's pre-release track (TestFlight external, Play testing, the Store's private audience — each installer doc owns its own track) — and, **ruled 2026-10-20 (owner, as proposed 2026-10-18 — wait by default, withdrawing is the owner's)**, `:test` does not move past a version while a store review of that version's app build is open: the next version's first public image dispatch waits for the last open review to close, unless the owner withdraws it and lets that version's store release go unmade; the hold binds only while a reviewer can meet a mismatched nest (throughout 0.1.x, and at each major bump) and only once the acceptance nest serves reviewers at all — what counts as open, the record it reads and the owner's choice are [`installers/store-review.md`](installers/store-review.md) § The `:test` hold's; **(b)** the promote to `:latest` lands before the public store release of the same version. Within a major version the wire compatibility rule would make the order a courtesy; under 0.1.x, which owes no compatibility, it is the only thing keeping them matched. Of the two halves only half (a)'s hold is enforced, by the public image dispatch; the upload order and half (b) are not (§ Implementation status today).

**Promotion copies the tested digest.** The nest image promoted to the public repository's `:latest` (and `:<version>` beside it, written once by the same promote from the same digest once the public tag names the built commit — [`image-pipeline.md`](image-pipeline.md) § Image tags & channels, the UAT bullet's decision (3)) — the only promote left after the 2026-10-02 channel ruling: the private repository stages and verifies and promotes nothing (owner of both pipelines: [`image-pipeline.md`](image-pipeline.md) § Image tags & channels) — must be the digest the candidate run recorded; the target state of that promote step is "green verify at test.fauna.build **and** a tag whose release-table row carries this digest". Under the two-pipelines design (2026-10-09, [`image-pipeline.md`](image-pipeline.md) § Image tags & channels, part 4) the public repository builds its OWN artifact of the published tree, so the digest here is the PUBLIC build's: the candidate run drives the public `:test` image, and the promoted row is keyed on the private commit the public one was published from with `public_commit` recorded beside the digest (`just release-promoted <commit> --public-commit <sha>`). **The pairing is the public commit's `Sync-Point:` trailer** — every public sync commit the publish tool writes names the private rev it snapshotted, and the squash-merge keeps the message — read in the standing mirror (or `--public-clone <dir>`): a public commit pairs with a private one exactly when its Sync-Point is a prefix of it. The candidate run accepts a public build on that pairing, keys its row on HEAD and records the image's own commit as `public_commit`; `release-promoted --public-commit` refuses an unpaired commit, and one other than the `public_commit` the candidate run already recorded (one helper, `tests/e2e-unified/helpers/feature_ledger.py::public_build_refusal`, for both). Until the public pipeline first runs nothing promotes and `promoted` stays `false` on every row.

**The release table** (`releases.json`, rendered into `MATRIX.md`): one row per build the catalog has something to say about (re-keyed 2026-10-02 with the private `:latest`'s retirement; one row per candidate run before) — `version`, `commit` (the repository's git object id, sha1), `image` (the exact tag the run drove) and `image_digest`, `date` (the row's newest observation), **`verified`** (the date the private pipeline's verify gate went green on this build — written by **`just release-verified <headSha>`** in the dispatching session; the field the pin derives from), **`candidate_run`** (the date of the newest release-candidate run — written by the run itself; the field the tag gate reads, so a verified-only row never satisfies it), `promoted` (boolean: this digest became the **public** repository's `:latest` — flipped by **`just release-promoted <commit>`** in the session that drives that promote, dormant until the public pipeline exists), and `shipped_apps`, the **per-app shipped version** where a store carve-out shipped one app at a later patch (§ Release train). It is the one record of what was released: the reader sees at a glance which builds reached the staging box, which were measured, which became production, and which app, if any, lags. A row is minted by whichever act comes first — `just release-verified` or the candidate run — and the other upserts into it on the key below; the digest both record is the registry's manifest-list digest of `ghcr.io/faunasocial/nest:sha-<sha>` (`docker image inspect`'s `RepoDigests` for the pulled tag, `docker buildx imagetools inspect` for the un-pulled one), the same identity, so the key agrees. **`just release-verified` resolves the digest off the registry and never reconstructs it**; `--digest` overrides for a registry the session cannot reach.

**A row is keyed on `(commit, image_digest)` and upserted, never blindly appended.** A candidate run is re-runnable by design — a flake, a wider `--app` set, a second machine's leg — and re-running the *same* artifact at the *same* commit is one release observed twice: the date and `candidate_run` advance, `verified` and `promoted` are preserved, no second row appears. Only a genuinely different build of the same commit is a second row, and that is exactly the case the tag gate refuses. Without the upsert the gate's "exactly one digest" would be satisfiable one moment and ambiguous the next for no reason but a repeat run.

**The row's own commit is allowlisted for the publish gate in the same act that writes it.** It is a bare hex run in a shipped tree (`matrix.json`, and the derived pin once the row is verified), and `secret_scan` default-denies those, so a release would otherwise red the merge that lands it — the trap the pin file's header has warned about since 2026-07-12 and that took `origin/main` red on 2026-08-27 over four commit SHAs of the version-skew grid's own. Every writer of a row — the candidate run's record, `just release-verified` and `just release-promoted` — therefore appends entries to the publish gate's approved-secret-fixtures allowlist (and the identifier ratchet's exemptions for the `MATRIX.md` short SHAs) alongside the render, with a reason naming the release row. The digest takes no entry: every render spells it `sha256:<64 hex>`, a span `secret_scan` claims as a content digest, and an entry no finding matches — a digest's, or the pin's for a row the pin does not derive from — is orphaned on arrival, which reds the gate as surely as a missing one (measured 2026-10-23 on the 0.1.5 candidate row). The values are public by construction — a commit in this repository's history, and what `docker pull …@sha256:…` resolves — so the decision the allowlist records is a standing one about a *class*, not a fresh judgement per release; a release process whose every use reds the merge gate is one people route around.

**The pin is derived from it.** `tests/e2e-unified/pinned-previous-build.toml` — "the most recent verified staged build pair", [`version-compatibility.md`](version-compatibility.md) § Dimension 6 (re-ruled 2026-10-02; "production release pair" until the private `:latest` was retired) — is written by `just features-render` from the newest row carrying a `verified` date (newest by that date, ties by position), and the lint checks it (rule 5). Its semantics are unchanged and still owned there; what changed in 2026-08-27 is that it is no longer a second hand-maintained copy of a fact the release table already holds, and `just release-verified` is the act that advances it (`release-promoted` did, until the private promote was retired; it now records the public `:latest` only). **Newest by `verified`, never by date alone**: a candidate that went red at the verify gate never proved it serves anywhere, and pinning it would aim the whole skew grid at an artifact nobody runs — which is the distinction § Dimension 6's update rule is built on. **The artifacts of a version (asked for and ratified 2026-11-09 with [`fleet-versions.md`](fleet-versions.md), which shows them; not built — § Implementation status today).** The table's row for a version says what the nest image is and nothing of the rest, so `releases.json` gains a second list, `artifacts` (the schema number rises by one; a reader of the older schema reads `releases` as before): one entry per ARTIFACT and version, keyed `(version, artifact)` and upserted as rows are — `artifact` (a name from the committed map of release legs, and the image: the nest image, each Linux package, the Windows installer, the Windows Store package per architecture, the macOS app, the terminal app's archive per platform, the Android and iOS apps, and whatever leg the map gains — and `site`, fauna.social at the version, which no leg builds), `commit` (the `main` commit it was built from), `digest` or `sha256` where the artifact has one, `channel` (where it was published: the registry, the public release, a store, a site), `run` (the workflow run that built it), and `state` with a stamp per state reached — `built` (the release workflow produced it; for a store, the upload built and no tester can install it yet, uploaded or not), `submitted` (handed to a store's review), `live-test` (at least one tester can install it from a store's own testing track — TestFlight, a Play testing track, the Microsoft Store's private audience; added 2026-11-12 with [`fleet-versions.md`](fleet-versions.md) § The apps of a release, which owns why), `live` (anyone can get it there), `withdrawn` — and `note`. Written only by the tooling that performs the act: the grading of the stage's public image run (`fauna-publish stage <version> --grade <run>`, which reads the run green) writes the nest image `built` with that run and the digest `:<version>` resolves to, the tag step writes it too (a re-run safe backstop that pairs the private commit), and the promote writes it `live`; the release workflows publish into the public repository and cannot write this table, so the step that waits for their files — the site deploy, which refuses until the pre-release carries every file — reads them back `built`, with the hosting's own sha256 of each, and the flip writes them `live`; the site deploy writes `site` `live` when it reads back a green `deploy-site.yml` deploy at the version's sync point (its channel `fauna.social`, its run that deploy's — the dispatch itself writes nothing; `fauna-publish promote-ready` and `release` read the newest green deploy at a commit of the version and record the site `live` themselves, and a second `deploy-site` run still does too); a store's `submitted` and `live` are written by `just store-review` in the same act that records the store's verdict (in review, approved or rejected → `submitted`; serving on the store's public track → `live`; serving on a testing track → `live-test`, the store's own reading that a tester can install it; withdrawn → `withdrawn`; the Store's submission is one entry per architecture). **`live` is the channel's public release (clarified 2026-11-09 with the build):** a pre-release and a staged image tag are `built`, and a store's testing track a tester can install from is `live-test`, never `live` — the counterparts the UAT entry above names — so a version that stays a pre-release shows nothing live. Every writer is safe to re-run: a state already stamped keeps its first stamp, a state below the current one is refused (`withdrawn` follows any), and a different digest on an entry already `live` is refused as another build under a spent version. A Release file maps to the leg that builds it; a signature bundle or the checksum list is no artifact, and a file no leg places is left out and named, never guessed. A version that did not build an artifact has no entry for it — absence is 'not shipped in this version', never a state. The hex an entry adds is allowlisted for publication as the rows' is — today no publication carries it: the table itself is withheld from the public tree and no shipped render reads the list, so the render that first shows it adds the entries in the same act.

## Release train

**A release is a train — the nest and all seven apps ship simultaneously at one version, with the store-mechanical reship as the one carve-out.** Owner: [`product-version.md`](product-version.md) § Bumping (ratified 2026-08-26, user-confirmed). What this catalog contributes: the candidate run stamps the train's version on every cell it witnesses (§ Release-candidate run), the tag gate makes the train's tag conditional on a recorded run (§ Tag gate and release table), and the release table's **per-app shipped version** is where a reship carve-out becomes visible instead of inferred from a store's sparse history.
