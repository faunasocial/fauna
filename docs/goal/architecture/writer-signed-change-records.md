## Writer-signed change records

- **Writer-signed change records — the per-manifest group binding (ruled 2026-09-27; adversarially reviewed the same day — three blocking findings re-ruled below, the corrections folded in; PARTLY BUILT — § Implementation status today).** The cryptographic restoration consequence (b) above deferred and the end state clause (4) of the provenance ruling under (D) names: every change record carries its writer's signature, so `author_actor_id` becomes a verified fact rather than the nest's word, the plant-before-bind class closes in both halves, and the pre-bind ledger is superseded before it is built. Six rulings, answering the six questions the design row asked:

  - **(3) What each reader does — one rule: a record that does not verify is not a record.** The nest refuses it at ingest (`record_change_core`, both the same-nest kind and the federated relay; the two conflict kinds the same way) with typed `signature_invalid`, `signature_required` and `author_mismatch` — the signed `actor_id` must equal the authenticated recorder or the federated `requesting_actor_id`; `author_actor_id` stays nest-stamped and now merely agrees; the nest checks nothing about the set nonce beyond equality with the stored one (it is the client's binding, not the nest's). Every client reader verifies **before** fold, apply, materialize, download or re-seal — the owner engine, the member engine, the capability host, web's Media reader, tui — and a row that fails is **skipped, warned and counted**, treated as absent (the cursor advances, the path frontier does not). Verification = the signature under `signer_key` + the authoring chain to the signed `actor_id` with `SyncWrite` + the signed `actor_id` is the set's owner (the reader's own id on an owned row; on a member's, as ruling (11)(c) names it) or a `writer`-access roster member per the reader's roster read + the set nonce is this set's — its live one, or a retired one of its lineage under ruling (11)(c). **A succession moves the nest's stamp and no signed byte, so a row written under a since-retired identity is served naming its successor — how a reader recovers the signed actor, who attests the link, and what it judges again is ruling (8).** **The roster read is a new ungated engine leg**, not the p2p leg's `refresh_share_writer_roster` (which is `p2p-share`-feature-gated, returns early for a cross-nest member and clears on `not_shared`): same-nest via the actor roster kind, **cross-nest via the same roster read relayed to the set's home nest** (ruled 2026-09-29, replacing the never-built "foreign-folder record's members": the `ForeignFolder` record carries the member's OWN advisory `access`, never a roster, and a nest-projected authorization fact has no place in `BackupKey`-sealed custody — the kind, its gate, disclosure and the distinct client kind are [`federation.md`](federation.md) § Cross-nest shared folders + channel append → *The cross-nest writer roster read*). The reader installs the relayed reply's `writer`-access members exactly as the same-nest reply's, and **a foreign set's owner is that reply's `role == "owner"` row**: on a host carrying an MLS engine the channel's MLS-recorded owner is the pre-read seed (both are writers, no precedence to settle); a bearer-only host (the capability host) has no seed, so on a foreign set the owner's rows hold like any member's until the first read — the roster leg runs on demand before a batch that needs it, so the hold is one read wide. Rejected for the cross-nest arm: members carried on the `ForeignFolder` record (a per-device stale copy merged by the custody CRDT, where the same-nest reader keeps no on-disk roster either — both planes stay in-memory, refreshed on the mode tick and on demand); MLS membership plus a separately carried access map (membership is not authorization — (5)(iii) — and the map IS the roster read). **Offline, the last roster stands; no roster ever read ⇒ owner-only** (a member's rows are refused until the first read succeeds — the fail-closed direction). The class exemptions are exactly (1)'s WebDAV pseudo-device rows on a served set, nest-minted `is_retention` rows, `state-entry` rows and `record-cid` rows; every other unsigned row is refused. **An item class routes a row away from the file reader, not past its check (clarified 2026-10-01; BUILT 2026-10-03 — § Implementation status today):** a `state-entry` or `record-cid` row is verified by its own plane and is never a file row, so the readers this ruling governs — the engine's pull, the peer door, the projection readers — pass one by unconsumed, the cursor moving on; none folds, applies or opens it. The nest re-homes exactly the rows whose signature is carried and verifies, one transaction per page, refusing the page whole on a row that does not verify (`signature_invalid` / `author_mismatch`, the record door's own codes) or names no custody row, and the reply gains `remaining` so the driver loops until nothing is owed; a folder-set request carrying no signatures is refused `signature_required` — the arm never mints an unsigned row again, which is what retires the flip's stop-gap refusal. **Where the statement reads its size (ruled 2026-10-02; BUILT 2026-10-02): `size_bytes` is the manifest's `total_size`, and both halves read it from the manifest the statement's `manifest_hash` names** — the leg from the manifest its store holds (`CustodianStore::read_manifest`), the arm from the manifest blob this nest holds (the one `decode_manifest` its charge derivation already runs, `crate::backup::custody_charge`) — and the arm mints the row with that figure. Three reasons. It is the file's logical size exactly as the source's own engine declared it (the engine records a change's `size_bytes` from `uploaded.manifest.total_size`), so a restored row reads as the source row did. It is bound to the statement already: the manifest is content-addressed by a hash the signature covers, so the two sides cannot hold different figures for one row. And both sides already decode that manifest, so no wire field and no column is added. Never the custody row's `size_bytes`: on a reserved destination set that column is the nest's derived CHARGE (`upsert_backup_custody` — the manifest blob plus every distinct chunk, as stored), a metering figure the quota legs credit back and no reader shows as a file size (the after-loss e2e measured 238 charged against 39 declared for one row, every other field of the statement equal); and never the store's recorded source size (`HeldRow::source_size_bytes`, which drives the pull's diff and the delivery's report). The refusals: a custody row whose manifest this nest does not hold or cannot decode refuses the set `custody_incomplete` naming the row — the manifest was held when custody was recorded (the charge derivation refuses `backup_bytes_not_held` otherwise) and GC keeps a live custody's manifest, so this is a torn delivery or corruption and re-delivery is the remedy; a held row whose manifest the store cannot decode holds the set `rehome_unsigned` with the reason, as a malformed store row does today. **Rejected:** a `size_bytes` carried on each `RehomeSignature` (an additive wire field for a figure both sides already hold; owner-attested but unbound to the manifest, so a leg could sign a size the manifest contradicts and the nest would mint it, and a missing field needs a refusal arm of its own); a declared-size column beside the charge in `backup_custody` (an at-rest migration storing what the same row's manifest already carries, NULL for every row delivered before it); the leg computing the nest's charge (couples the client to the nest's metering rule, and mints the charge as the file's size — the second defect the e2e showed). Five rules. **(1) Custody carries the serve window.** `FolderKeyCustody` gains `served_at: Option<u64>` and `unserved_at: Option<u64>` (micros, the flipping device's clock — the unit `rotated_at` and `retired_at` use); **the entry is served while it is live AND `served_at` is present and above `unserved_at`** (`FolderKeyCustody::is_served`, one predicate at every site, as `is_live` is; liveness is in it because a delete retires the entry and writes no `unserved_at`, and a tombstone of a set deleted while served must never read served); both stamps join to the later — the pair has the shape of (l)(v)'s `retired_at`/`lifted_at`, so a stale device's copy of either flip cannot undo the later one and a replayed envelope cannot re-serve or un-serve — but **a tie reads NOT served**, where (l)(v)'s tie reads live: each pair resolves its tie to its safe side; and a serve-on stamps strictly above the entry's `unserved_at`, a serve-off strictly above its `served_at`, so a clock that stepped back between two gestures still orders them (two devices flipping opposite ways at once resolve by wall clock, last writer wins — the two-copy intent problem has no better answer, and the loser's gesture is one flip away). **`served_at` is written by the owner's serve-on gesture and by NOTHING else — never from the nest's flag, not once, not one-shot** (rule (5) says why); `unserved_at` by serve-off and by the launch pass's one arm (3). **Serve-on** writes `served_at` in its one custody write BEFORE the nest flag — for an unshared set the write that already mints or reuses the genesis (`serve_enable`'s `key_named_set`), for a shared set a write that today does not exist (the closure is empty when `channel_id` is `Some`; the `content_keys` precheck stays), so a set custody calls served always holds keys and the reconciler's `ServedSetKeysMissing` becomes a sync lag, never a state; **serve-off** writes `unserved_at` in the ONE custody write that already rotates (`serve_disable`'s `rotate_set` write), AFTER the adoption and after the nest has accepted the flip — custody keeps saying served across the sweep-and-flip rounds, so a DAV row landing between a sweep and a refused flip stays exempt until the next round adopts it, and the flip is still what stops the plane. The custody identity is unchanged: `channel_id` stays the pseudo-channel from the first serve-on or paywall (`paywall_set` keys an unshared set there too) or the real channel from a bind, and the two stamps say whether that identity's DAV plane is open now — keys at the pseudo-channel never meant served, and now nothing reads them as if they did. **(2) Every client judgement reads custody.** The reader's exemption: `ReaderBinding::webdav_served` is the entry's `is_served` — on the engine side from the custody `engine_lifecycle.rs` already loads for the nonce (the owner's live pick by name, a member's entry at the real channel), on the projection side through the source `row_judge.rs` already consults (today a `SetNonceSource` asked only for sets that carry a signed row, with an early return for a projection that carries none; it becomes a binding source — nonce AND served state — asked for every set the projection names, since the set whose rows are all unsigned DAV rows is exactly the one that needs the answer), and for a cross-nest member from its own entry (`resolve_foreign_binding`'s hard-coded `false` goes). The live binding and the resolvers: `custody_channel_for` takes custody beside the summary and answers from the owner's live entry (`channel_id` and `is_served`) or the member's real channel — still the one shared resolution, now over the owner's word — and with it `resolve_engine_key_binding`'s served arm, the owner-only shortcut and `retired_serve_custody` (answers for an entry that is not served); `BindingBasis` drops the flag (no binding reads it), and `FolderEngineKeys` carries the stamps (4) so the agent's custody re-read is the rebuild trigger when they move; "content-keyed with no group" means the name's live entry holds the pseudo-channel and is served, "owner-only plus retired candidates" means it is not. The `WebdavKeysBlob` reconciler provisions **the sets the owner-scoped list names AND custody calls served** — owned ∩ `is_served`, never a member entry (a member's entry carries the owner's stamps under (4), and the member's blob sits on the member's box, outside rule #7's radius) — and the nest's flag selects nothing; the served-set walk's launch resume walks the same sets. The owner row's toggle and the MUA URL row paint `is_served` (one field on the shared snapshot `fauna-devices-machine` builds, joined from the custody the app already loads for the Media resolver — the seven apps re-read the snapshot, not the roster), so the state the user acts on is the state the compositions act on. The peer leg needs nothing new: `fauna_peer_share::judge_peer_row` judges with the receiver's own reader, which this rule feeds, and admits an exempt row only on the channel's proof as before. **What keeps reading the nest's flag:** the nest's own gates — the MDA's folder filter, `webdav_record_change`'s door, the mint gate, the update door's refusals (serve-on on a public or metadata-only folder; a public or metadata-only change while the flag is on), the count behind `served_rows_unadopted` — which are the nest's word about its own plane (correct on an honest nest, the adversary's on a lying one, and nothing a client should ever have believed); and `FolderSummary::claims_unsealed`'s "a served folder never arms", a read that can only REFUSE an unsealed public read, which a lying nest achieves by withholding anyway. **(3) Disagreement is resolved at the owner's launch pass, only ever in the ≤-intent direction, and the two provisioned copies are reconciled there too.** The pass is `FoldersAuthor`'s launch resume (the neighbour of `resume_pending_removals` and `converge_served_sets` — the author holds the files client, the custody store, the mail store and the group seam; `reconcile_set_custody` has no group handle and no MSEK, so the arms are the author's), over custody read with `load_for_write` (a fresh fetch, so a lagging device acts on the plane's state, not its cache), per owned set the nest lists, after (g)'s custody reconcile and before the two provisioning reconciles below. *Custody served ∧ flag off* is the crash state of BOTH gestures — a serve-on that wrote custody and died before the flag, a serve-off whose flip landed and died before the custody write — and the state a nest lying "off" produces; the three are indistinguishable and one answer is safe for all: **unserve in custody** (the serve-off tail: `rotate_set` + `unserved_at` in one write, `is_served` re-checked inside the closure so two devices never rotate twice for one flip, the envelope republished for a shared set). The interrupted serve-on reverts (the user flips again; exposure ≤ intent), the interrupted serve-off completes, the lying nest achieves a denial — bounded to one rotation per owner serve-on, since only the gesture writes `served_at`. *Custody not served ∧ flag on* is a lying nest, a device whose custody has not yet synced a sibling's serve-on, or the honest race the review found (a lagging device's late serve-off overtaking a sibling's re-serve-on, so the blob that sibling provisioned carries a set custody no longer calls served): **the flag is left alone** — a push from a lagging device would undo a sibling's gesture, and every judgement of the owner's already follows custody — **and the provisioned copies are brought to custody.** So the `WebdavKeysBlob` reconcile joins the launch pass unconditionally on every MSEK-holding device (`NoMsek` → nothing to do; a desired-state atomic replace, one list and one provision — today its only production caller is `serve_set`, which is why the race above could stand) and re-runs on the custody nudge; and so does an **envelope reconcile** for every shared set the owner holds: fetch the stored envelope, open it under the current epoch through a new `open_envelope` on the `FolderGroupCrypto` seam (today it has only `seal_envelope`), and **publish the JOIN of custody and the envelope only when custody is strictly ahead** — never a stale bundle over a newer one, which a lagging device would otherwise push and the members' writes would then fail the nest's monotonic floor — **skipping a channel with a staged pending removal** (its Remove may be merged and its generation unpublished; publishing custody's keys under the post-Remove epoch would hand the departing member the window) and skipping a channel whose envelope does not open at this epoch (nothing is published on a failed read). That heals the serve-off that died between its custody write and its republish (members would otherwise keep exempting on an honest nest) and the serve-on that died before publishing. **The adoption never runs outside a served window:** `serve_disable` sweeps only when custody calls the set served — on {custody not served, flag on} it pushes the flag off and signs nothing (a refusal `served_rows_unadopted` surfaces as the error it is), a branch no UI offers (defence in depth for a direct caller): since the toggle paints custody, the gesture a user is offered on such a set is ON, and ON is the owner's word opening the window — on a lying nest the rows it planted while it lied become exempt by the owner's choice to serve, exactly residual (vi), and a following OFF adopts them inside a window the owner declared; a lying "served" alone launders nothing. The nest's update door refuses a public or metadata-only change while its flag is on, so in this state the user reaches that change by ON then OFF (the honest serve-off clears the flag) — one extra flip, bounded to the migration day (5) and a lying nest. **Accepted, stated:** a sibling's launch pass inside the one-RPC window between a serve-on's custody write and its flag unserves it (≤ intent, the toggle visibly flips back); a device whose custody lags the plane despite the fresh read (the nest withholding the newer custody — residual (ii)) provisions the blob without the sibling's newly served set until the next pass or nudge on a current device (a denial, no wider); a serve-on from a device that does not hold the group cannot publish, and the unserve arm's rotation on such a device waits for the envelope reconcile of a device that does; and **members' exposure changes:** today an honest nest discloses `webdav_enabled: false` on every member row, so every member — same-nest or cross-nest — refuses the owner's pseudo-device rows and the DAV plane of a shared served set is invisible to them; under (4) members read the owner's stamps and admit the served era, which **extends residual (vi) to members for the window the owner declares** — the correct view of a set the owner serves, and bounded as the owner's is — and, since a member's stamps arrive only in the envelope, a nest that withholds the owner's republished envelope holds that member in the window: the member-side (vi), as wide as lying the flag to it would have been, and accepted with it. **(4) Members and the wire.** `ContentKeyEnvelopePayload` (a map) gains the two stamps beside the generations and the nonce; `merge_received_keys` joins them into the member's entry (to the later, so an envelope the nest replays cannot move the window and a member's copy only advances to what the owner last said); the owner publishes on every serve flip of a shared set — serve-off already republishes, serve-on publishes inside its custody step, before the flag (a publish that fails before the flag is reverted by the next launch's unserve arm) — and the envelope reconcile of (3) catches what a crash left out. `FolderEngineKeys` carries the stamps beside the nonce on every arm — the agent's custody re-read is then the binding-edge rebuild when the stamps move and the roster row does not. A cross-nest member is the same envelope; the MDA needs none — its capability is the blob, which (2) scopes. **(5) Compat, and the migration that is a user gesture.** At rest additive on `FolderKeyCustody` under the 2026-09-24 baseline (`#[serde(default)]`, emitted only when set — a never-served entry keeps its bytes; `FoldersConfig::merge` joins both to the later, so the blob arm and the plane arm share the statement, P1); wire additive on the envelope payload's map and on `FolderEngineKeys`; no re-seal, no data loss. **There is no automatic stamping of a set served before the build.** An entry written before the build carries no stamps and reads not served; a set the nest flags served while custody says not served is the lying-nest state by definition after the build, and any arm that stamped it served on the nest's say-so — one-shot or not — would hand a lying nest exactly the key lever this ruling closes (after the build, `bind_set` and `paywall_set` still mint keyed, stamp-less entries, so "keyed and stamp-less" never means "served before the build"). The migration is therefore the owner's — **one flip ON per set served before the build** (serve-on is idempotent on the nest: the update door accepts an already-on flag, `key_named_set` reuses the key, the walk skips heads already at the current generation, the blob replace converges) — and its day-one cost is stated whole: at the first launch on the new build the blob reconcile drops every pre-build served set, so **the mount goes dark for them** (the MDA holds no key; a DAV write fails closed) until the flip; every reader refuses their DAV rows and their engines bind owner-only, so new owner writes seal under the owner root until the flip; **a mixed fleet flaps** — a device on the old build provisions the blob from the flag, a device on the new one from custody, each launch overwriting the other — so the release note says every device updates together; and to spare **two full re-seals** per such set (the retired-candidate reseal walking the back-catalogue onto the owner root, then the flip walking it back), the desktop agent's `reseal_predecessor_sealed` HOLDS for a keyed, stamp-less entry whose roster row says served — a nest can only delay a re-seal that way, the safe direction, and the hold ends with the stamps. Nothing is lost in the window: rows and bytes stay on the nest, and the bearer-only agent needs no migration leg (it loads the custody the gesture wrote). **Rejected:** a bool (a flip-flop no join-only door can land — (l)); the serving generations' range instead of two stamps (a window per serve era, re-derivable from the rotation history only with a start marker per era — the stamps are that marker, and a reader needs only "now"); pushing the nest's flag to custody's state on every disagreement (a lagging device undoes a sibling's serve-on; with every client judgement on custody the flag is irrelevant to the owner's hosts, which is the point); adopting on the unserve arm (a serve-off that died after the flip already adopted, a serve-on that died before the flag has no rows, and a lying nest's rows must never be signed); keeping `resolve_foreign_binding`'s `false` and the member rows' non-disclosure as the members' answer (the honest answer only while the flag was the nest's word; a served shared set's DAV plane invisible to its members was a withholding, not a design); a nest-side "served since" stamp (the nest's word again); a client-side `WebdavKeysBlob` filter on the nest's flag alone (closes the key lever and leaves the window); a one-shot stamping arm gated on an account-level marker (trust-on-first-use at the one launch a lying nest needs, permanent once taken — the user's single flip costs less than that residual); an envelope reconcile that republishes on any difference (a lagging device would push a stale bundle over a newer one); a third toggle state for "served at the nest only" (a new UI variant on seven apps for a state the ON gesture already resolves).
      - **(iii) Name-keyed serve custody — a tombstone lends nothing to the name (ruled 2026-10-02, same pass; NOT BUILT — § Implementation status today).** Verified against the tree: no rename kind exists (`FolderKeyCustody::name` is write-once, (a); the nest addresses a set by `(name, owner)`), so the "renamed" half is void — a future rename kind must move the entry in place, nonce and all, and re-point its pseudo-channel the way `migrate_set_identity` re-points a bind, and is a design pass of its own; delete RETIRES the entry and purges nothing ((e), (l): `set_lifecycle::retire_live_entries`, the keys kept for no-data-loss), and a re-create mints a fresh nonce-bearing entry with no `channel_id` beside the tombstone (e). The reach: a by-channel read joins the keys of the LIVE entries holding the channel, and of all of them only when none is live ((l)(i), `custody::joined_keys`). So a re-created set that is served again — `key_named_set` puts the pseudo-channel on the fresh live entry — never joins the tombstone's generations: rule (1)'s bound holds, and an adopted row stamped with the dead incarnation's generation opens nowhere ((10)(c)). The one arm that reaches the tombstone is the none-live fallback, and `retired_serve_custody` takes it for a re-created set that is NOT served (the fresh entry holds no channel): the dead namesake's serve generations come back as the new set's read candidates — inert today, since every consumer of the candidates (`FileDownloadKeys`' offered roots for stamped versions, the label roots, `reseal_predecessor_sealed`'s verify) opens only an admitted row and the re-created set admits only rows signed under its own nonce ((g) never re-signs an incarnation retired before the pick into it: `set_nonces_for` leaves such an entry out), and under (ii) a lying "served" no longer turns those candidates into a live binding — but a wrong answer that switches the reseal pass on for every re-created set, and a door the day any reader admits anything else under them. **Rule: a set's retired serve candidates are resolved over the set's OWN entries — every same-name entry not retired before the earliest `created_at` of the entries carrying the live nonce (the pick, the live nonce-less key holders (c) and (g) leave beside it, and the twins an identity move retires, (l)(ii)) — never over an entry retired before that; and when the name has no live nonce-bearing entry at all (a pre-ruling nonce-less live entry), the candidates come from the LIVE entries only, never a tombstone. This is the selection `set_nonces_for` already makes for the retired nonces, lifted into one helper both take, so nonces and candidates cannot drift — with the one difference stated: `set_nonces_for`'s nonce-less arm keeps tombstones as migration input, which is right for a nonce and is exactly the lending (iii) forbids for a key.** (l)(i)'s none-live arm is unchanged for the by-channel reads it was ruled for; a set's candidates are a by-name question and never take it. Shared with `set_nonces_for`, and accepted as it is there: the clock-skew edge of a delete on one device stamped above a re-create on another (the same owner's devices, seconds apart), which includes the tombstone as the name's own — a retire floors only on the entry's own lift, never on a sibling's `created_at`; and an entry with no `name` is invisible to any by-name selection. Accepted, stated: the deleted incarnation's rows and bytes stay on the nest under generations the owner's custody keeps for ever (no-data-loss), reachable through the tombstone by channel and through nothing else. **Rejected:** purging serve custody at delete (no-data-loss, (e)); a nonce-keyed pseudo-channel so a re-create derives a fresh channel (the set would change identity at serve-on, the blob and the MDA address by name, and (k) rejected the same move for the nonce); leaving `retired_serve_custody` on the fallback (above); a narrower "live pick plus twins retired after it" selection (drops the live nonce-less key holder's served-era generations — a read loss).
  - **(8) Rows signed under a retired identity — the succession-crossing reader rule (ruled 2026-10-01, design pass; adversarially reviewed the same day in two passes — three blocking findings re-ruled, then six corrections to the re-rule folded in; refutable downstream; the shared judge, the projection readers, the engine's half, the nest's roster carriage, (8)(e)'s re-read and (8)(f) BUILT 2026-10-01, the nest's cert-table key of (i) 2026-10-02; (j), the roster carriage's three states, ruled 2026-10-02 and NOT built — § Implementation status today).** A succession moves the nest's bookkeeping and no signed byte. For an account homed on the set's nest the change journal and the cert table follow the corpus — `sync_changes.actor_id` and `sync_signer_certs.actor_id` are both declared `Move(Plain)` in the nest's `ACTOR_TABLES` registry (`bins/fauna-nest/src/db/actor_tables.rs`, the registry [`../behavior/succession-aftermath.md`](../behavior/succession-aftermath.md) § Re-key scope points at) — so a row the predecessor **P** wrote is served ever after with `author_actor_id` = the successor **S**, its `signature` still over a statement naming P, its `signer_key` still P's device key (or P itself), its cert still naming and root-signed by P. For a cross-nest writer the set's home nest re-points only the roster (`channel_foreign_members`), so the stamp keeps naming P while the roster names S. Either way the signed actor is a retired identity of a current writer, and rulings (2) and (3) were written for a reader on which the served author, the signed actor and the writer are one id. On the moved row each of that reader's three steps fails: the statement rebuilt from the served author is not the one that was signed; the cert is cached under the actor it names and looked up under the author; and the owner check knows one id. Since the projection readers began judging (2026-09-29) this empties a successor's inherited Media listing, and the engine's pull skips the same rows. **The nest's record half needs one thing, the cert table's key ((i), ruled the same day)**: the cert already moves with the rows it verifies and is served from the row's moved key, bytes untouched — but under the key that table was built with, a later cert for the same device key replaces it. The rulings:
    - **(a) The signed actor is recovered from the signature, never from the nest's stamp.** A row names its signer by `signer_key` alone and the signature covers the statement's `actor_id`, so the signed actor is whichever candidate the row verifies under: the served `author_actor_id` (every row no succession has moved — one verification, as today); `signer_key` itself (a direct signature by a since-retired identity); the actor each carried cert certifying `signer_key` names (a delegated one). *Verifies* is ruling (3)'s whole cryptographic check with that candidate as the statement's `actor_id`: direct only when `signer_key` equals the candidate, delegated only through a cert the candidate root-signed, carrying `SyncWrite`, certifying `signer_key`, unexpired at the row's `created_at`. One signature does not verify over two statements, so at most one candidate succeeds, the order is a cost choice only, and the nest chooses nothing: a lying `author_actor_id` or a planted cert can make a row fail, never pass. The reader's cert cache stays keyed `(the actor the cert names, device_key)` — already the key a row's *signed* actor finds it under — and gains the by-`device_key` read the third candidate needs. On a reader the served `author_actor_id` is thereby demoted from *must agree* to *first candidate*; at ingest (3)'s `author_mismatch` is unchanged, since a recorder is always a live identity.
    - **(b) A retired identity writes as its successor, and the link is the successor's own signature.** The signed actor **A** is admitted iff it resolves to a current writer **W** of the set — the owner, or a `writer`-access roster member — as W itself or as a predecessor of W at any depth. **The link is proven, never projected:** an unbroken chain of landed succession statements from A to W, each link's `new_sig` verifying under that link's own successor (`SignedIdentitySuccession::verify_new_sig`) — the walk the profile plane already runs to decide whether a predecessor-signed base is the successor's own (`fauna_client_profile::proven_predecessors`, [`../ui/profile.md`](../ui/profile.md) § After an identity succession → *A successor device with no recorded succession link*), lifted to the one shared verifier beside the statement type. The last link is W's own word naming the identity it succeeded, which no nest can mint; each earlier link is the word of an identity W's chain already vouched for. It is deliberately not the full succession verdict (`recovery_sig` under the known chain head): the question is not *was this succession authorized* but *does W own what A signed*, and the weakest party the walk trusts — a holder of a predecessor's key, who can sign a link naming any id as *its* predecessor — could already sign rows as that predecessor outright. **Precedence, so no served link can re-attribute a row:** A as a writer itself wins over any chain that claims A; and where chains ending at two different writers both claim A, the row is admitted and attributed to A, to neither of them. **Where the statements come from:** *(i) for a roster writer* (every member row, and the owner row as a member reader sees it) they ride the roster read — an additive field on `FolderActorMember`, on the owner row and each `writer` row only, filled by the set's home nest from the successions it has recorded (its own accounts' and the peer successions federation delivered — the walk over `actor_successions`, not the local-accounts-only one), through the one projection both roster doors share (the same-nest read and its cross-nest relay — [`federation.md`](federation.md) § Cross-nest shared folders + channel append → *The cross-nest writer roster read* owns the kind and its disclosure). The nest still decides *who is a writer* (residual (iii), unchanged); it cannot decide whose predecessor anyone is. *(ii) for the reader's own account* two sources stand, equally strong: the account's **attested predecessor set** — `AccountRegistry::attested_predecessor_actor_ids`, attestation by possession of the predecessor's seed ([`account-data-taxonomy.md`](account-data-taxonomy.md) § The generation machinery → *The source of `prior`*, the 2026-09-13 ruling), which an identity-holding app reads off its registry and hands the sync agent on `SyncCapability::predecessor_actor_ids` — and, for a host that was handed none (a device restored from the successor's seed alone, a capability host), the same statement walk ending at its own id, over the roster's owner row or the pre-identity `fauna.recovery.succession.lookup`. Never the account record's writer-asserted `prior_actor_ids` (the succession ledger's `chain` row since that kind's cut, `__config` when ruled). The attested ids outlive the predecessor *keys* where a host drops those ([`apps/sync-agent-credentials.md`](apps/sync-agent-credentials.md) § Credential model, bound (3)), so the version history under them still verifies. The MLS-recorded owner — a member seat's pre-read seed — names one id and keeps no history: once that marker re-stamps, the retired owner's rows resolve through the roster's owner row like any member's, **held, never refused**, until the first roster read.
    - **(c) What a verified row reports, and what a predecessor's signature may open.** The verdict names both identities: the **writer** W, the current identity, and the identity the row was **signed as**, A. *W is for attribution*: version history renders it, a judged projection stamping it over the served `author_actor_id`, so that field stays, as (3) promised, always a verified one — sound only because (b)'s link is W's own signature, where a nest-projected link would let the nest write as any member it chose. *A is for everything that asks what this signature itself vouches for.* The cert is cached and relayed under A (a holder retaining a row for the p2p relay keeps the cert under A, so the row stays self-contained, and the peer door reads the signed actor from the verdict, never from the served stamp). A row is this device's **own echo** only when signed as the reader's *current* identity — a predecessor-signed row is never one, whatever `device_id` it carries. And **of the owner-root family — the current `BackupKey` root and each predecessor's — a row signed as predecessor A is offered only A's own root and the roots of A's predecessors, never the current root nor any root later in the chain than A, on every arm that opens its bytes or its label**: the ordinary owner-only read, part (D)'s unstamped open, and the unstamped label arm alike. Only a row signed as the current identity is offered the current root (and, as today, every predecessor's beside it). Without that bound the retired seed and a lying nest together could name, in one of the account's sets, the manifest or the sealed path of a file the successor created after the ceremony in another; the successor's device would open it under its own current root, and the pre-bind pass would re-seal it to the first set's audience — its members at once on a shared set, or whoever an owner-only set is later shared with or served to — the copied-record class (5) closes, reopened. With it, a retired identity's signature reaches only bytes that identity could itself have sealed. Two consequences are part of the rule. The bound needs the predecessor keys carried **paired with their actor ids, in chain order**, to every open, and the verdict's A carried with each admitted row to the label open — at ruling time the pairing was dropped at the capability and at every hop after it, and the owner-signed memory recorded a manifest without its signer (both carried since 2026-10-01 — § Implementation status today). And a predecessor-signed row that opens under none of the roots the bound allows it — sealed under a later root, or admitted on a host that proved the link by statements and holds no predecessor root at all — is **a noted skip under (f), never a transient hold**: a hold there would stall every later row of the set behind a row this host can never open.
    - **(d) Two existing rules follow the same chain.** *The WebDAV class exemption*: the pseudo-device id is a pure function of an actor id (`label_custody::webdav_pseudo_device_id`), so a served set's pseudo-device rows recorded before the succession carry the *predecessor's* pseudo-device and would otherwise be judged as unsigned; ruling (1)(i)'s exemption therefore reads: the pseudo-device of the set's owner **or of a predecessor of the owner by (b)**, on a set whose row says `webdav_enabled`. Those rows are the nest's word by construction (residual (vi)) and an exempt row never arms the owner-root open, so the nest gains nothing; ruling (7)(b)'s adoption walks the same pseudo-devices. *The re-record leg* (the custody sub-bullet's (g)): a head a predecessor's device signed under a since-retired nonce is one no successor device can reproduce byte for byte, so it would never reach the live nonce. The leg therefore also carries across a head that verifies under the retired nonce as signed by a predecessor A of this account by (b) — **but as a re-seal, never as its bare re-sign**: only once the head's bytes have opened under a root (c) allows A are they re-sealed under the current root and recorded under the live nonce. A re-sign alone would move a predecessor's signature to the current identity's without opening anything, and the row it produced would then be offered the current root — (c)'s bound, escaped in one step. Ruling (11)(d) generalizes this leg into the succession take-over: a stamped head or a public set's row is re-signed over the same manifest once its label and manifest have opened under the key they rest under, and the source is the device's own local state wherever it holds any. *A version restore is the same act and takes the same rule (added 2026-10-01, from ruling (9)'s review)*: restoring a version records a new head carrying the historical manifest verbatim under the restorer's signature (`SyncClient::restore_version`), so a version signed as a predecessor A is restored only once its bytes and its label have opened under a root (c) allows A, re-sealed under the current root where they rest under an owner root; a predecessor's version that opens under none of them is not restorable, and says so. The third caller of that record — the review list's *use the other version* — and what makes a stamped version safe to re-point without opening it are ruling (10).
    - **(e) The roster is read again before a writer is refused.** A row that verifies cryptographically but whose signed actor resolves to no writer is refused today against whatever roster the reader last read — so a member's first rows under a new identity, or any newly granted writer's, are refused by a reader whose in-memory roster predates the grant. On the nest pull the reader re-reads the roster once per batch holding such a row and judges again (the judge-again-after-one-read shape the never-read case already has). A re-read that fails changes nothing in (3): the last roster stands, the refusal stands against it, and (f) is what keeps that refusal from being a loss. The projection readers already read a fresh roster per listing; the p2p share leg's cached roster stores each writer's proven predecessor ids beside the writer, so a peer-served inherited row is judged offline as it is on the nest pull.
    - **(f) What the cursor already passed is judged again — by heads, never by replay.** Two refusals differ. A row that fails cryptographically is not a record. A row that verifies under this set's nonce but whose signed actor resolves to no writer *on this reader, now* is a record this reader cannot yet attribute, and for it the engine does two things. **It notes the skip** on the row's path (the note a row that can never apply on this device already takes), so a later local edit of that path does not claim to derive from a head this device never read — without it, a device that skipped a predecessor's head and then edited its stale copy would stamp the edit as a successor of that head, and every device that did read the head would fast-forward the stale bytes over it. **And when what the reader admits by gains something** — a writer granted, a predecessor proven, a seed restored, a predecessor's root arriving on a host that held none; never on a loss or a reorder, and once on every device with the build that ships this ruling — the engine reads the set's log **up to its own cursor and no further**, whole before it folds anything, and folds, per path, only the latest non-retention row the judge now admits, and only when that row is above the path's frontier; a delete at or below the frontier is a duplicate. **Refined on build (2026-10-01), because the delete arm advances no frontier:** *above the frontier* reads above the path's frontier and its edit-frontier both (the second knows this device's own acked edit before its echo is pulled), and **a delete head is folded only where this device noted the skip of that very row** — a delete it already applied reads as above both frontiers for ever, and a file re-created since is `Synced` on disk before its record is acked, so folding the old delete there would unlink bytes that exist nowhere else. The note is released once the ordinary delete arm has spoken, so no delete is folded twice. The cost is stated, not hidden: a delete refused *before* this build noted nothing and stays unfolded — a stale file kept, never a live one lost. Rows above the cursor are the ordinary pull's, in order, as always. Never a replay of the log through the ordinary fold, and never a head taken from above the cursor: the delete arm carries no frontier check and the cross-nest read is paged, so an old delete replayed a page ahead of the create that superseded it — or pulled after a head pass had already folded that create — would unlink a live file with nothing left to re-offer it. The trigger is durable state, since the roster itself is held in memory only: the engine stores, per set, the ids it last admitted by, so a restart gains nothing it had already, and a marker that the pass is owed, cleared only when the pass completes, so one that fails part-way runs again. Nothing is lost in the meantime — the rows rest on the nest. The projection readers hold no cursor and need nothing: a listing is judged whole on every refresh.
    - **(g) What it does not close — residual (vii) of (5).** Admitting P's signature after P retires means a succession does not end P's power to *sign* for the sets it owned or wrote, and on the owner's own hosts such a row reads as the account's own — more than residual (iii) gives, which makes an actor a writer and never the owner. Whoever holds the retired seed — the thief the ceremony answers — can still mint a cert and sign a row under the set's nonce (the nest stores every nonce, and the old seed opens the custody that held it). The bound is delivery and reach. *Delivery*: no honest path carries such a row — the home nest refuses the retired key at every authenticated surface — so it reaches a reader only through a nest that lies, or over the p2p leg of (v) from a peer the share leg admits. *Reach*, by (c): the row opens only bytes sealed under the retired root or an earlier one (or, on a bound set, under a generation the retired seed's custody held), so what the pair can plant is content the thief sealed, or pre-succession content of the same account copied between its sets — never anything the successor sealed after the ceremony. It is not self-limiting: the registry keeps retired seeds indefinitely and the agent's key drop is a recomputable predicate, so the roots stay offerable; and where the corpus re-seal moves a head it re-records what it admits under the successor's own signature, so a planted row that is not noticed becomes a genuine head there (it moves none on a set whose chunks rest under content keys — bound, or served — nor on a public one, `SyncEngine::reseal_predecessor_sealed`; there the planted row simply stays the head — corrected 2026-10-01: this clause used to say the re-seal re-records everywhere). No reader-side cutoff by position exists to rule — `seq` and `created_at` are the nest's, so *refuse a predecessor's row above the succession* binds only the honest nest, which never serves one. The closure is the cut of ruling (11) (ruled 2026-10-02, not built): the successor re-mints the set's nonce, every later row is signed under the new one, and a reader holding it treats the owner's chain's rows under the old nonce as history and refuses one under the new — not the per-writer chain this clause named until 2026-10-01, which (9) rules is not built. What (11) leaves open is its (j).
    - **(h) Rejected.** *Re-signing the inherited rows in the aftermath*: a successor must verify a row before vouching for it, which is this rule, so it replaces nothing; the corpus re-seal re-records under the successor's signature only the heads it moves (corrected 2026-10-01: this clause used to say every head; on a bound, a served or a public set it moves none, and the predecessor's heads stay live under its signature), and what else stays predecessor-signed § Re-key scope's classification keeps immutable; and replacing a stored signature needs a mutation door on a log whose integrity is that it has none. A cut under ruling (9)(e) may still re-record inherited rows, but after this rule has verified them and never in its place. *A nest-served `signed_actor_id`*: the second author field (2) refuses, and one a reader could not trust — it would only select among candidates (a) already enumerates. *Declaring `sync_changes` `Stay`* so the stamp keeps naming P: it repairs the statement rebuild alone — the owner check still needs (b) — and undoes the registry's declared re-attribution, leaving the successor's journal under an actor that no longer exists. *Bare predecessor ids on the roster row* (this ruling's first draft, refused on review): a nest-projected link lets the nest list a key of its own as a member's predecessor and have every reader attribute the nest's rows to that member — attribution forgery, which (iii) never gave. *Predecessors read from `__config`*: the 2026-09-13 ruling. *The full chain-verified succession verdict as the link*: it needs each identity's home nest as an anchor (`fauna_core::recovery::verify_succession_against_chain`'s contract) and a known chain head a reader of someone else's set does not hold, to answer a question (b) does not ask. *The group's witnessed credential swap, or a per-channel history beside the owner marker, as the member reader's source*: a bearer-only host has no MLS seat, and the statement walk gives every host the same proof; the marker rule keeps guarding the two powers it exists for. *Re-pulling the log from the start through the ordinary fold* (the first draft's (f), refused on review): not idempotent, for the reasons (f) gives. *A cutoff by `seq`*: (g).
    - **(i) The nest's cert table keys a cert by the identity it names, beside the row's actor and the device key (ruled 2026-10-01, design pass; refutable downstream; BUILT 2026-10-02 — § Implementation status today).** `sync_signer_certs` was built keyed `(actor_id, device_key)`, the latest verified cert replacing the stored one. That is sound while one identity certifies a key: ruling (2)'s re-ceremony certifies the same key again for the same actor, and the newer cert verifies the older rows. A succession breaks the premise. The move re-points `actor_id` and rewrites no cert byte, so the slot `(S, K)` then holds a cert naming P, and the first record that S's own grant for the same device key K lands replaces it. Every row K signed as P is then served without the one cert it verifies under — (a)'s third candidate is never enumerated — and it fails on every reader, the owner's and each member's, for good: the table is written only at ingest, under the recorder's live grant, and a retired identity records nothing, so no client door puts the cert back. The roster's statement carriage of (b) does not make this harmless: the statements prove whose predecessor P is and carry no cert. **No shipped client reaches it** — the writer key is one keypair per (machine, account) (ruling (1)), so a successor's machine mints its own, and a direct signer's key is its actor id — **but the nest checks none of that**: it stores a grant over whichever device key the successor's root certifies, and the successor's machine still holds the predecessor slot's secret. A stored shape that is sound only by a client convention the nest cannot see is a state one non-conforming client reaches and no client repairs ([`nest/common.md`](nest/common.md) § Client-state recoverability), and it is cheap to close only now: from the 2026-10 baseline on a primary key changes by a table rebuild with a reader floor, staged inside a major ([`version-compatibility.md`](version-compatibility.md) § 2.1), where today it is one schema step. So **the key is `(actor_id, device_key, cert_actor_id)`**, where `cert_actor_id` is the `actor_id` the stored `DeviceAuthorization` names — written at ingest from the cert that verified, and never moved or rewritten afterwards. `actor_id` stays exactly what it is: the stamp of the rows the cert verifies, `Move(Plain)` at a succession, and the key the purge and export legs follow. Within one triple the latest verified cert still wins (ruling (2)). **A list reply's side table carries every cert stored at a row's `(actor_id, signer_key)`** — one per identity that certified that key in the row's actor's history — and the reader needs nothing new: its cache is already keyed by the actor a cert names, (a) already picks among several certs for one device key, and `signer_certs` is a list on every wire that carries it, so no wire shape moves. **No move can collide under this key, by what the nest itself enforces:** ingest stores a cert only under the recorder it names (by reference the chain verifies to the recorder; inline a cert naming another actor is refused `author_mismatch`), so a row is written with `cert_actor_id` equal to its `actor_id`, and a move changes `actor_id` alone — the rows a ceremony moves onto S name P or a predecessor of P, and S's own name S. A federated writer's inline cert rests at `(F, K, F)`, which no succession on this nest reaches. *Rejected.* *Keeping the pair key and recording the client convention as the reason it holds*: the paragraph above — the nest cannot see the convention, and the cost of being wrong is permanent. *Declaring the table `Stay`*, which makes the pair key name the cert's own actor with no new column: the read would then need the predecessor walk for every signer on every page, and the purge and export legs, which follow `actor_id` generically today, would each need it too — or a deleted account leaves its predecessors' certs behind and its archive carries signatures a reader cannot check. *A read by `device_key` alone*: it answers a reader of one account's row with every identity that ever certified that key on this nest. *Refusing, at grant registration, a device key the account's history already certified under another identity*: a refusal door for a state the wider key makes harmless, and it would bind every later client to the convention.
    - **(j) The roster carriage's three states — a fan-in on peer-learned links, a retired member id that keeps its seat and its grant, and a cross-nest writer's successor left without its grant (ruled 2026-10-02, design pass; refutable downstream; (1)–(4) BUILT 2026-10-03 — § Implementation status today).** Building (b)'s source (i) — the set's home nest fills each writer row's statements from `actor_successions` — met three states (b) does not rule, each a question of who a nest may speak for. One principle settles all three, and it is the one § Re-key scope already states for participation: **a seat and its grant travel together, by the propagation leg that moves the seat — never by the ceremony transaction and never by the owner's hand — and a nest holds one predecessor per identity.** The member's chain stays uncut throughout ((11)(c)(3); (11)(j) residual (5)); the `Stay` declarations of 2026-08-14 (`actor_tables.rs`, the membership cluster [`../behavior/succession-repoint-axis.md`](../behavior/succession-repoint-axis.md) § The declared re-point axis rules) stand for the transaction they govern.
      - **(1) A fan-in is refused at the door, never carried.** The home leg already makes a lineage linear: `record_succession` refuses `NewAlreadyRegistered`, so a local identity is born by at most one succession — the collision-free property § Re-key scope rests on. The peer leg (`record_peer_succession`) checks only the predecessor (`OldIsLocal`, `AlreadySucceeded`), so two statements verified against two home nests, each naming a different predecessor of one successor, both land, and the fan-in is the one state in which the carriage's one-chain field, `succession_committed_at`'s `MAX`, the heal pairs' terminal walk, `proven_predecessors`' ordered list and (11)(c)'s ordered owner's chain all meet a shape none was written for. So **the peer leg refuses a statement whose successor this nest already holds a link into, local or learned** — a new `SuccessionRefusal` arm, logged at warn, since an identity that signed two successions is a state the honest ceremony cannot produce — and the first-landed link stands. The nest thereby chooses nothing a reader trusts on its say-so: both links are the successor's own `new_sig`, so neither is a forgery, and what is withheld is one of the member's own words — the power residual (iii) already grants. The refused statement's residue on this nest (the second predecessor's foreign memberships and contact edges) stays under that retired id, and the set's owner re-invites the successor — today's remedy for a lost push; the hourly pull is refused again at no cost. With the invariant on both legs the walk's fan-in arm is unreachable: `succession_statements_into` reads one link and reports a second as an invariant violation, and the pin `the_walk_into_an_identity_stops_at_a_fan_in` turns into *the second link into an identity is refused and the first stands*.
      - **(2) The retired seat — the attribution is intended while the seat stands, and the Welcome that seats the successor ends it.** Between the ceremony and the sweep's add-successor Welcome ([`../behavior/succession-propagation.md`](../behavior/succession-propagation.md) § Propagation, *MLS groups*) the roster lists the retired id **P** as a `writer`, and (b)'s precedence attributes P's rows to P, not to the successor **S**. **That reading is ruled correct**, and it is what (11)(j) residual (5) already states: a member's chain carries no cut, so (b)'s precedence is the whole rule for it, the nest's word on who writes is residual (iii) and no more, and a row so attributed reads as a retired identity's own, which (8)(c) already bounds. (11)(c) decides membership in the *owner's* chain by statements before the precedence only because that chain carries the cut; nothing here reaches a member's chain, and (11)(k)'s refusal of *cutting a member's predecessor on the member's re-grant* holds unchanged — after the move below P's rows stay admitted, attributed to S through the chain. **The leg that ends the seat is the one that seats the successor:** when the sweep's Welcome lands for a local recipient S on a channel where a recorded predecessor P of S (the `actor_successions` walk into S) holds a seat, the nest — in the same write that registers S (`welcome_deliver_core`'s same-nest roster register) — re-points P's `folder_member_access` row to S and removes P's `actor_channels` row. The grant follows the seat and never moves alone, which is the 2026-08-14 conjunction kept, not broken; and the `Stay` on `actor_channels` is likewise kept, since its reason is the ceremony's push reading the roster under P *after the commit* (`push_succession_detached` → `succession_push_targets`): that read happens once, at the ceremony, before any Welcome can arrive, and the build makes the order a property of the code. The thief holding P's key gains nothing: P is refused at every door of its home nest from the commit, and what a lying nest can plant signed as P is admitted through S's chain exactly as (8)(g) and (11)(j)(5) state — attributed to S instead of to P, the reading every member's reader has today for a succeeded writer whose grant the owner took back by hand.
      - **(3) A cross-nest writer's successor takes the grant with the roster row.** On a set's home nest a foreign member's seat *is* its `channel_foreign_members` row, and `record_peer_succession` already re-points that row — and the contact edges — in the statement's own transaction ([`federation.md`](federation.md) § Cross-nest shared folders + channel append, *Identity succession re-points the member, never the binding*); the grant did not ride it, so the roster named S with no grant, S could write only once the owner granted again, and P's grant row sat orphaned under an id the roster no longer listed. So **the same transaction carries P's `folder_member_access` rows on the channels whose roster row it moved**, and no orphan is left. It is (2)'s rule on the other leg: here the seat moves in the transaction, so the grant moves in the transaction; on the home nest the seat moves at the Welcome, so the grant moves at the Welcome. The binding's own collision rule — the predecessor's `home_nest_id` row is kept — is untouched; it answers a different question (who may rebind) with a different stake.
      - **(4) The collision rule, the owner's hand, and what was rejected.** Where S already holds a grant on the channel (separately invited before the statement or the Welcome reached this nest), **S's own grant stands and P's is dropped** — the owner's later and more specific act about the identity now in play; no security dimension exists, since only the set's owner mints grants. Deliberately not the contact collapse's stricter-status rule: there both edges are the holder's own choices about one peer and the stricter protects the holder from an un-block behind their back; here both grants are the owner's, and the one naming S is the one the owner meant for S. The owner's hand is otherwise unchanged — `members.set_access` and `members.evict` override whatever the propagation carried — and no declaration in the registry moves. **Rejected.** *Carrying both branches of a fan-in*: sound attribution (both are the member's word) at the price of a multi-chain wire field, a DAG reader and no answer to (11)(c)'s *which of two identities is earlier* across branches — machinery for a state the home leg forbids. *Picking a branch by a stated order and keeping both links recorded*: an invariant violation left on disk for every consumer to guard separately. *The fan-in arm as built*: a member's inherited rows fall silently out of every reader's listing (held, never refused, so nobody is told), and the invariant holds on one leg and not the other. *The owner's re-grant as the designed leg* (today's state): a member's recovery costs one manual act by every owner of every set the member wrote in, for a question the statement already answered, and until each owner acts a possibly-stolen key is listed as `writer` indefinitely. *The owner's device moving the grant when it witnesses the pair in the group*: a second client-side mechanism for what the nest already recorded or verified, fired only while the owner's device is online, once per owner device per set. *Moving the grant in the ceremony transaction* (a `Move` declaration): the 2026-08-14 conjunction — a grant moved before its seat admits nothing, and the seat cannot move there. *Filtering a superseded local id out of the roster projection*: between the ceremony and the Welcome P's rows would resolve to no writer and be held off every member's listing, where today they stay listed as P's — an availability loss for a window the user's offline device can make long. *Keeping P's seat as a `reader` row after the move*: a retired id rendered on every member's roster until an owner evicts it, for nothing. *Refusing a peer statement whose successor is a local account* (the home leg's `NewAlreadyRegistered` carried over whole): the peer nest's `users` row says nothing about that identity's lineage elsewhere, and the one invariant the carriage needs is one predecessor per identity on this nest, which (1) states exactly.
  - **(9) The per-writer chain is not built, and residual (vii) does not wait on it (ruled 2026-10-01, design pass; adversarially reviewed the same day — the facts held, and seven blocking findings refused the cut mechanism the first draft ruled in (e), which is withdrawn to a design pass with those findings as its brief; refutable downstream).** Rulings (2), (5)(i) and (8)(g) named one closure for two residuals: a per-writer gapless chain with withholding detection, after the account plane's `writer_seq`, with the successor signing where each predecessor's chain ends. Checked against the code and against what each residual needs, that name covered three separate things — a replay bound, a withholding bound and a succession cut — and they are ruled apart.
    - **(a) The model does not do what it was named for.** The account plane's `writer_seq` detects no withheld row: a gap in a writer's sequence is legal at ingest, and that plane accepts withholding rather than closing it ([`account-sync-plane.md`](account-sync-plane.md) § The class-2 entry form, *What this closes, and what it deliberately does not*, corrected with this ruling). What it does give is a coordinate inside what the writer signs, so one entry cannot be served as another or as newer than it is, a reuse refusal at the relay, and a reader's refusal of two different entries at one coordinate. That is a replay and equivocation bound and nothing more.
    - **(b) This log is not served gapless, and its writers are not journals.** Four facts, each a design of its own to change. *The served log omits rows by design*: `changes.list` reads only rows that are not superseded, and both the re-seal reclaim and the version-retention purge stamp rows superseded, so an honest nest already serves a writer's rows with holes on any set old enough to have pruned a version. *A signed statement need not land, and may land twice*: the nest refuses a record at the quota after the writer has signed it, and the record door's exactly-once compares against the path's head only, so a retry that arrives after another row took the head lands the same statement again. *Rows are signed out of log order*: ruling (7)(b) signs a served set's old rows in place, long after their `seq`. *A writer is not one journal*: the seed-holding apps' side recorders — Media upload and delete, archive import, web among them — sign with the identity key and keep no state per set, while the sync agent, the File Provider extension and the in-process hosts sign for the same account from other processes, and on macOS the agent and the extension share the principal key and no state directory. A counter that is gapless across all of them is the account plane's whole journal-lifetime machinery ([`account-replica-posture.md`](account-replica-posture.md) § The store device principal — one home per counter, a writer living exactly as long as its journal, the lost-slot and burnt-journal heals) built again at every signing site.
    - **(c) What a chain would buy here is narrow.** For residual (i) it would let a reader that walks the log and remembers each chain's high-water drop a replayed row as a coordinate it has passed, and it would make a nest that withholds one row withhold everything that writer signed for the set after it. It gives nothing to a reader with no memory — the Media projection and the version history, where (i) is unbounded today, are per-path rows the nest picks and each listing is judged afresh — nothing to a reader that joins later, which a nest can serve any earlier state of the set (no cut escapes that either, unless it rests where such a reader must find it — (e)), and nothing against withholding a writer's tail (residual (ii)). For residual (vii) it gives nothing on its own: the holder of a retired seed certifies a key no reader has seen and starts a chain. What closes (vii) is the statement that ends the predecessor's rows, and a chain only makes one form of that statement short.
    - **(d) So the chain is not built, and it is not waiting on a date.** Not on the first public release: the statement is signed, so a chain is a second statement version beside `fauna.sync.change.writer-sig.v1` whenever it comes, and with the baseline closing at the repository's flip that cost is the same next month as next year — there is no birth shape left to catch. Residual (i) stays as (5) states it, bounded by the per-device guard and the two frontier checks. Evidence re-opens it, not the calendar: the served log becoming gapless per writer for a reason of its own, a reader with memory replacing the per-path projections, or a replayed row reported from a deployment. The bound to weigh first on that day is on the reader, not the wire — the record door already treats one signature as one statement, so a resident reader that remembers the signatures it has folded for a path could drop a replay with no new signed field; (b)'s double landing is its first obstacle, since such a reader must still agree on the head with one that remembers nothing.
    - **(e) Residual (vii) needs a cut, not a chain — and the cut is not ruled here.** What ends a retired identity's power to sign for a set is a statement its successor signs; (c) shows a chain is no part of that. The statement's form was ruled the same day as ruling (11): the set nonce re-minted by the successor, which every later row is signed under, so a nest that withholds the cut withholds the future; each of the seven findings below is answered there by its number, and the two forms weighed below are its (k). Until (11) is built, (vii) stands exactly as (8)(g) states it. The first draft of this ruling ruled one form: the successor re-records under its own signature what its predecessors' rows still hold live on a set (a *take-over*), then signs a per-set *closure*, after which a row signed as a predecessor is history and never a head. Review refused it as a mechanism on seven counts, and they are the pass's brief. **(i)** A closure a nest can withhold narrows (vii) to the readers that hold it; it does not close it. Neither the owner's custody (the account plane accepts withholding, (a)) nor the content-key envelope (a member already holding one is served every later row without the next) binds a nest to deliver it; only a member that joins later is safe, since it opens no earlier envelope. **(ii)** A take-over adopts whatever the nest serves when it runs — a row planted before it, or an older head served with the predecessor's genuine delete withheld — and once a closure makes that delete inert the resurrection is permanent, which is worse than residual (i) is today. **(iii)** The record door answered a signed delete over a signed tombstone with the tombstone's `seq` and inserted nothing, so a re-recorded delete never landed and still reported success — **fixed 2026-10-02**: the door treats such a delete as an echo only while the tombstone verifies under the set's stored nonce (`../behavior/delete-propagation.md` § Deletes propagate the same way), and the re-record leg counts a re-record only when the door answers with a `seq` above the head it re-recorded. **(iv)** No re-record may skip the open: a label's key is chosen by the label's own generation field, never by the row's signed `content_key_version`, so re-signing a predecessor's row unopened hands it the current root — (8)(d)'s escape — and the record door derives `path_hash` from a plaintext path the sweeping host may be unable to open. **(v)** A closure is a loss of admission, and (8)(f) judges again only on a gain, so a row folded before the closure arrived stays a head. **(vi)** A predecessor's version restored from the version history is re-signed as the current identity — the same escape, one gesture away, and open under ruling (8) with or without a cut ((8)(d), amended with this ruling). **(vii)** A take-over's re-records are charged like any record, so a successor near its quota cannot finish one. The pass also weighs the two forms the draft dismissed too quickly. *A cut by time* — a predecessor's rows live for a fixed window after the succession statement's signed `created_at`, by the reader's own clock — cannot be withheld, since a reader that admits a predecessor's row at all holds that statement; its price is availability, because what no device took over inside the window is hidden. *The set nonce re-minted at the take-over* is the one carrier under which withholding the cut also hides every row the successor records after it; its price is the custody ruling's (g) on a set with other writers, where each device re-records only what it signed itself. And three things any form must state: whether a closure signed by an identity that has itself since retired still binds; what the p2p door and its cached roster consult; and that a served set's pseudo-device rows stay exempt across it (residual (vi)).
    - **(f) Rejected.** *Building the chain now to catch a birth shape*: (d). *A cut that enumerates* — the successor signing each predecessor chain's last coordinate: it needs (b)'s chain; a counter alone does not bind, since whoever holds a predecessor device's key signs again at a coordinate below it; and pinning each chain's last hash instead makes a reader that holds one row fetch every row after it to check the pin. *Treating a predecessor's rows as history from the link alone, with no cut*: it empties the successor's inherited listing until a take-over ends, the failure ruling (8) exists to repair.
  - **(10) A conflict candidate is re-signed only as a judged version — the review list's *use the other version*, the choose-winner, the signature on the loser a report retains, and the stamp a verbatim re-point rests on (ruled 2026-10-01, design pass; adversarially reviewed the same day — one blocking finding re-ruled as (c), the corrections folded in; refutable downstream; BUILT 2026-10-03 — § Implementation status today).** A conflict row and its candidates are the nest's word: `fauna.sync.conflicts.list` serves each candidate as `{manifest_hash, device_id, size_bytes, created_at, content_key_version}` out of a nest table, no field of it signed, and two doors put the reading device's signature over what it names. The review list's one-tap *use the other version* (`fauna_devices_machine::DevicesMachine::use_other_version`) records the latest non-winning candidate through the shared restore record (`SyncClient::restore_version`), its manifest, size and generation verbatim; the choose-winner (`fauna.sync.conflicts.resolve` with a winner) has the chooser sign the head row the nest mints from the candidate (`SignedChange::for_choose_winner`). Either way a head signed as the current identity names a manifest only the nest vouched for, and every reader then offers it the current owner root. A nest that lies about a conflict's candidates can so name, in set Y, the manifest of a file the owner sealed under its owner root in set X, and one tap makes it the owner's own head of Y, which the pre-bind pass, the served-set walk or a declassification then moves to Y's audience: ruling (5)'s copied-record class through a door (5) did not list, with no retired seed needed. Ruling (8)(d) closed the same act for the two version-history restores; this closes it for the conflict surface, settles the one version-bearing row no signature covered, and repairs the premise (8)(d)'s built half rested on. The rulings:
    - **(a) The conflict row names; a judged version vouches.** A device signs over a candidate's manifest only after finding it as an **admitted version** in the judged version history of the conflict's own set and path — `SyncClient::versions_list_judged`, soft-pruned versions included, **looked up under the hash of the very path the record will carry** (derived from the rendered path, never read off the conflict row, so a conflict that names one path and hashes to another restores nothing across paths). A version's row is signed under this set's nonce over this path's hash, so a manifest copied from another set, another path or a deleted predecessor of this set has no admitted version here, and a candidate with none is not a candidate — ruling (3)'s one rule, read for this surface: the gesture declines with the reason and records nothing. What is recorded is the **version's** signed `size_bytes` and `content_key_version`, never the candidate row's: the stamp decides which roots the head is ever offered, so it is not taken from an unsigned field. Where several admitted versions carry the manifest, the pick is one signed as the current identity, else a stamped one, else the latest.
    - **(b) Then it is a restore, and takes the restore's branch — one decision, shared by every door.** **Signed as the current identity** — on the picked version, or on any admitted row of the same set carrying the same manifest, since the statement binds the manifest to the set (the Media machine's verdict memory, kept by set and manifest) — → re-pointed verbatim. **Any other admitted version carrying a content-key stamp** → verbatim, because a stamped record is never offered an owner root: (c), and sound only once (c) is built. **Any other unstamped version** — a predecessor's, another writer's, an exempt class's — is ruling (8)(d)'s case: opened under a root its own signature may reach and re-sealed where the surface holds a byte seam, refused with the reason where it does not or where no such root exists. The review list holds no byte seam, so there it refuses and names the file's version history, where the same version is listed and the Media restore performs the re-seal. The branch is **one shared function** over a judged version (beside `versions_list_judged`), consumed by the Media restore, the sync agent's verb and the review list: the three surfaces already share the record, and a rule each re-derived is how the third door came to have none.
    - **(c) The stamp binds the root, on every arm of every reader.** (b)'s second arm is the sentence (8)(d)'s built half took as fact — a stamped version *opens under its generation whoever re-signs it, never under an owner root* — and the code does not make it true: on a set that is neither bound nor served the owner-family roots are offered whatever the stamp says (`FileDownloadKeys::owner_open_roots`, consulted before the stamp on the manifest arm and the chunk arm alike). So the retired seed and a lying nest can sign, in an owner-only set, a row naming a manifest the successor sealed after the ceremony and carrying any stamp at all; the judge admits it as a predecessor's, a restore re-points it verbatim *because it is stamped*, and the head — now signed as the current identity — opens under the current root on every reader: (8)(c)'s bound escaped through the door (8)(d) was written to shut, on the Media restore and the agent's verb as built. The rule that makes the sentence true: **a record carrying a `content_key_version` is opened under that generation's content key — live, or retired on a set no longer content-keyed — or not at all; no owner-family root is ever offered to it, on any arm that opens its bytes (the manifest, the chunks, a blob primary), whatever the set's mode and whoever signed it.** The stamp is the writer's signed statement of the generation the bytes were sealed under (*Generation-stamping + selection on read*), so an honest stamped record never rests under an owner root and loses nothing. Bound to the record rather than to the set, the rule outlives every later change of mode — a serve-off leaves the set owner-keyed with its stamped heads still stamped — which a test of the set's mode at restore time would not.
    - **(d) The reporter signs the loser it retains.** A resolved report retains the reporter's own losing candidate — the version its device produced and never recorded — as an `is_retention` row, which ruling (1)(ii) left "unsigned by class" and ruling (2) left out of the statement as "nest-minted, carries no content". That is true of the row for the fold and false for a reader of versions: the row is the only record of that edit, the version history projects it, and since the projection readers began judging (2026-09-29) it is judged as an unsigned row and refused — the reporter's losing version is absent from the version history on every app, and under (a) it would never be the review list's *other version* either, which on a latest-wins row it is whenever the local side lost. So the report carries a **second signature, by the same signer, over the retention row exactly as the nest will mint it**: `device_id` = the losing candidate's (the reporter's own), its `manifest_hash`, `size_bytes` and `content_key_version`, the request's `path_hash` and `path_sealed`, `modify`, no thumbnail, `derived_through` = `losing_derived_through` as sent, `is_resolution = false` — every field one the reporter knows when it signs, so the report stays one request and one transaction (a second row's statement, not the two statements over the *winner* that (1)(ii) rejected; its two-round-trip shape stays rejected, and the record door still mints no retention row: its request carries no such flag) — **and `is_retention`, which joins ruling (2)'s covered fields, encoded only when true**, so every statement signed before this ruling is byte-for-byte what it was. The flag is covered because it is what the signature must not survive losing: served with the flag stripped, a retained loser signed as an ordinary edit would verify on every engine as the reporter's fresh edit of the path — the loser-as-peer-edit the loser-row ruling closed (2026-08-05, [`../behavior/conflicts.md`](../behavior/conflicts.md) § Concurrent resolution & ancestor freshness), handed back to a lying nest. Covered, a stripped flag fails the statement; a flag added to an ordinary row fails it for a reader of versions and is accounted and skipped by the fold — the fabricated retention row (5) already lists, nothing more. The nest verifies the loser's signature as it verifies the winner's (the statement rebuilt from the row it is about to mint — the same candidate its own pick selects — under the stored nonce, the signer by reference), refuses `signature_invalid`, refuses `signature_required` a resolved report that retains a loser and carries none, and stores the pair on the retention row.
    - **(e) One row, two readers.** *The fold* keeps ruling (3)'s class exemption exactly: a retention row is accounted and skipped, its signature not consulted, since nothing of its content is consumed there — a row with no signature (minted before this build) accounts as it does today. *A reader of versions* takes no such exemption: the version-history projection carries the flag (`FileVersionInfo::is_retention`, additive, into `as_change_row`), and the projection judge verifies a retention version by its signature like any row — signed as its reporter, admitted iff that reporter is a writer — so an unsigned retention row is not a version, on the listing, a download or a restore. The flag and the judge's change land in one build: the flag alone would route every unsigned retention row through the fold's exemption and list it, which is the door of this ruling under another name — a row the nest alone minted, naming a manifest for the owner to sign.
    - **(f) The choose-winner is the same act.** The chooser signs a candidate only when (a) finds it as an admitted version and (b) says verbatim; it builds its statement from the **version's** signed size and generation, and refuses on the device — nothing sent — where the candidate row's `device_id`, `size_bytes` or `content_key_version` differ from the version's, since the nest mints the head from its own candidate row and the row it would mint is then not the version that verified. An unresolved report mints no row, so of its candidates only the incoming side — already a signed row of the set — can ever be chosen; the reporter's local side stays on that device's disk, where the fallback kept it. A resolve that names no winner signs nothing and is untouched. No app renders a chooser ([`../ui/folders.md`](../ui/folders.md) § Conflicts); the arm is ruled because the shared machine and both binding surfaces still export it.
    - **(g) A host that runs no reader signs only what it sealed from its own bytes.** *(Moot since 2026-10-02: the one such host, the legacy daemon, was removed — `apps/sync-agent.md` § Headless deployment; the rule stands for any future host.)* The legacy headless daemon applied what it pulled without the reader (the named residual — § Implementation status today), and it holds the identity seed and signs its resolved reports with it: when the incoming side wins it signs a winner naming a manifest no judge admitted, and a clean merge seals incoming bytes it opened under the owner root into a manifest it then signs. Either turns a row the nest planted into a head signed as the current identity, which every verifying reader of the account then trusts — more than the residual grants, which is one device reading unverified rows. So it is cut here rather than left to the daemon's retirement: the daemon signs a resolved report only when the winner is its own local version; an incoming-side winner and a merge are reported unresolved (the fallback it already has), the local copy kept.
    - **(h) What it closes, and what it leaves.** Closed: a manifest of another set, another path or a deleted predecessor named as a candidate (no admitted version); a version re-served as a candidate with its stamp or size altered (the version's signed fields are what is recorded); a stamped row a retired identity signed over bytes under a later root, re-pointed unopened on any restore door ((c)); a retained loser re-served as an edit (the covered flag); a planted row laundered through a host with no reader ((g)). Left, stated: **which admitted version is "the other one" is still the nest's word** — the conflict row is display metadata no one signs — so a lying nest can point the gesture at any other admitted version of the same path of the same set, and one tap re-signs it: a re-point among versions every reader of the set already holds, reversible like any restore, and less than residual (i) gives the nest with no tap at all. A writer member can sign a retention statement over any manifest, as it can an ordinary row; it vouches as that member, is never offered an owner root, and (b) refuses it unstamped.
    - **(i) Compat.** The wire is additive: a loser signature on the report request beside the winner's, the flag on the version projection, a statement key present only when true; (c) and (g) change no wire at all. The ingest requirement of (d) is birth-shape on ruling (4)'s condition, re-read for this build — it lands before the first release from the 2026-10 baseline, or else relaxes to *verify when present* for the major (an older reporter sends no loser signature and may not be refused, I2). That relaxation is the whole of what a late landing owes: no reader gains a legacy arm either way, because an unsigned retention row is simply not a version — the state every judging reader is in today. (c) is a reader's rule and wants the same birth: an older reader keeps offering the owner root to a stamped record, which is the hole, not a compatibility. Retention rows minted before the build stay unsigned and unlisted, their bytes retained and pinned on the nest; nothing is destroyed, and this ruling builds no backfill (the only sound one would be the reporting device vouching from its own ledger, never from the nest's row) — whether one is owed for that population is the user's call.
    - **(j) Rejected.** *Each candidate's signed statement and certs carried on `conflicts.list`* (the first option weighed): a second projection of rows the version history already serves with their certs, a second site building the cert side table, and no binding the listing lacks — the nest would still choose which genuine row to attach. *Refusing every unstamped candidate*: on an owner-only set every version is unstamped, so the gesture would never work where conflicts are commonest, while stamped candidates would still be re-signed unjudged. *The retention exemption on the version readers*: (e). *A second domain tag for the retained statement*: the same security from a second tag and a second verifier arm, where the covered flag keeps one statement and one judge. *Recording the loser as an ordinary signed change before the report*: ruling (1)(ii)'s rejection stands. *Opening the candidate's bytes as the check*: the owner root is account-wide, so bytes copied from another of the owner's sets open — only the set-bound signature tells the sets apart, which is ruling (5). *Opening every version another signature recorded before re-pointing it, stamped or not* (the review's own direction for (c)): it needs a byte seam at every restore door, and leaves every other reader offering an owner root to a stamped record. *Re-pointing a stamped version verbatim only while the set is content-keyed*: the head outlives the mode ((c)). *A reporter-signed conflict record binding its candidates*: it would close the residual in (h) at the price of a new signed object for display metadata, against a re-point that is reversible and reaches nothing new. *Giving the legacy daemon the reader*: a feature on a host this major retires ((g) is a cut, not a build).
