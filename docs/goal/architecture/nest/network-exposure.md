# Network exposure — what opening a port reveals

Owns: network-exposure
Status: ratified
Authority: This doc owns the **cross-cutting exposure posture** — for every listening surface, what an anonymous / non-owner / federated observer *should* be able to learn about a user, and the rulings that settle the "will ≠ should" deltas. It owns no *mechanism*: cert/SAN topology → `tls-certificates.md`; the published DNS record set → `behavior/dns-management.md` + `behavior/mail-multidomain.md`; SMTP/greylist behavior → `behavior/smtp-server.md`; the Nostr/Bluesky/ActivityPub bridge surfaces → `ui/nostr.md` / the bridge docs; serving-port split + health → `common.md`; runtime crypto discipline → `architecture/security.md`; the sealed-at-rest property → `architecture/encryption-at-rest.md`. This doc references those owners and states only the exposure *consequence and ruling*, which no other doc owns.

The product invariant this doc operationalizes: **user content rests sealed on every nest; what a box reveals to a stranger is only what a user published to be public, what the deployment must emit to function as a federated host, and a bounded set of metadata side-channels** (`principles.md` § User always controls their data). This doc says, per surface, which of those three a disclosure is — and where a disclosure is none of them, that is a bug.

## The three buckets every disclosure falls into

1. **Published** — the user chose to make it public: a public post, a profile, a monetized post's free teaser, a cross-post to another network. Exposed to whoever the publication reaches; that is the point.
2. **Structural** — the deployment *must* emit it to be a federated mail/social host that other software can reach: DNS records (MX/SPF/DKIM/DMARC/MTA-STS/TLSA/SRV), TLS certificates (and their Certificate-Transparency shadow), protocol banners, and discovery metadata (`node-info`, NIP-11, WebFinger). Reducible only by not offering the service.
3. **Side-channel** — metadata not deliberately published: counts, existence oracles, timing differences. This is the only bucket where "should" can diverge from "will," and therefore the only bucket that yields findings.

A disclosure that is **none of the three** — a stranger learning something a user did not publish, that the service did not need to emit, via a channel that was not a deliberate side-channel — is a leak to fix.

## Target posture, per surface

**Always-on surfaces (no bridge gates them).**
- **Health** (`GET /api/v1/health`, `common.md` § serving-port) — *should* reveal the build SHA + version to anonymous callers. Ruled acceptable (the credential-less redeploy-verify contract needs it on a pre-claim box); the SHA reveals nothing not in the public source tree. Structural.
- **Discovery** (`node-info`, `handle.available`, `actor.by_handle`) — *should* reveal nest identity/pubkey, coarsened (major.minor) version, which bridges/features/registration policy are available, and handle existence. It *must not* reveal user or post counts — those stay Admin-only. Structural. (Owner of the fields: `common.md` / discovery; this doc owns the "no counts to anonymous" ruling.)
- **Subscription tiers** (`GET /api/v1/subscriptions/tiers/{author_id}`) — *should* reveal a monetizing author's tier names/prices/payment URLs to anonymous callers (the web paywall and federation need it). Published (the author chose to monetize publicly). The author id is public, so treat tier structure as world-readable by design.
- **Web paywall render** — a gated post's **free teaser** (`Post::body_text()`) *should* be world-visible; the full body must stay ciphertext behind a live entitlement. Published.
- **P2P relay address discovery** (UDP 7842 on a nest with a public name; mechanism owned by [`../../behavior/p2p.md`](../../behavior/p2p.md) § The relay → *Address discovery, and what rides a relayed path*) — *should* tell any anonymous caller that completes a QUIC handshake with the relay its own address as the relay sees it, and nothing about anyone else: no member, no device, no other peer's address, no traffic. That a relay runs here is already public (the `relay.<apex>` name and its certificate). Before the box has a public name the relay holds no certificate, so the port answers only QUIC version negotiation — the versions it speaks, no address. The home box runs host networking with no public name, so there the port is bound on its own network interfaces and answers the same version negotiation and nothing else. Amplification, measured 2026-10-05: an unsolicited 1200-byte datagram draws a 55-byte version-negotiation reply; the handshake's own reply size was not measured. Structural.

**Bridge/feature surfaces (disabling the feature removes them entirely).**
- **Nostr relay** — *should* serve, to anyone, the public non-gated posts of users who **opted into content exposure**, and nothing else: gated/sealed/DM content structurally excluded. COUNT and full-text search over that same public corpus are acceptable (the corpus is public). What *should not* leak: whether a specific pubkey is a local depositor via an **unsigned** probe (a signature must gate any membership-revealing response — see § Rulings F4). In the **outbound** direction every relay the nest dials is a caller-supplied URL — a user's publish list, a pasted `bunker://…?relay=` parameter, a follow's relay hints, a paired nest's serving box — and *should* go through the shared SSRF guard like every other caller-supplied-URL fetch, private-network relays included (see § Rulings F7).
- **Bluesky** — a cross-post *should* publish only the opting-in user's own content + identity to the firehose. A **mentioned** user who did not opt in *should not* have their signing key published (see § Rulings F2).
- **ActivityPub** (in the shipping image since 2026-07-16; `installers/docker.md` § Feature flags) — shipping the feature exposes zero content; only per-actor enablement federates, in **both** directions (outbound was always enablement-gated; inbound ingest is gated by a follow/addressed-target relationship check — see § Rulings F6). An enabled actor's public posts, profile, and follow **counts** (never the follower *list*) are Published. The nest-level **instance actor** (`/ap/instance`, WebFinger `acct:<domain>@<domain>`) is always mounted and mints on first probe regardless of any account's enablement — Structural, like nodeinfo/webfinger: it publishes no user content, only a server-owned signing identity a secure-mode peer needs to verify our fetches. Every AP dial to a remote-chosen URL — the inbox's actor fetch, the delivery worker's POST to a remote-declared inbox, and the instance actor's signed `GET`s — goes through the shared SSRF guard like every other caller-supplied-URL fetch (see § Rulings F1).
- **Mail** — the MX/submission/IMAP/CalDAV surfaces are Structural once mail is enabled. Recipient existence and username validity *should not* be an anonymous oracle beyond what SMTP inherently leaks; the catch-all actor is the in-band close, and login paths *should* be timing-uniform across valid/unknown users (see § Rulings F3, F5).

**Inherently public, permanent (bucket 2, no retraction).** TLS certificate SANs (apex + every mail domain together; each opted-in `<handle>.<nest_domain>`; each custom domain) are logged to Certificate Transparency permanently. The published DNS record set reveals the full mail/service structure. The Bluesky firehose retains every cross-post. Feature-gating or not-opting-in prevents *future* emission; nothing retracts what was emitted. A user-facing consequence to state plainly (the guide does): enabling a public-facing capability is a one-way disclosure of the associated identifiers.

## Rulings (settled `will ≠ should` deltas)

The point-in-time evidence, per-surface catalogue by observer class, and the file:line flows behind these rulings are in a dated exposure review (tracked internally).

- **R1 (account-data-plane.md § The ratified decisions) — a gated post's teaser being searchable is intended; do not "fix" it.** The full-text search corpus is fed only `Post::body_text()`, which for a gated post is the public preview the paywall already renders anonymously; sealed-derived content never enters the index (`storage/sealed.rs` documents "leaks nothing"). The `search_fts_public` name is correct — the corpus is genuinely public. A future session must not add a `gated_tier` exclusion to search to "match" the feed/trend/signal consumers: those exclude gated posts from *feed placement*, a different concern. **No code change.**
- **F1 — every ActivityPub outbound dial must route through the shared `crate::ssrf` guard. RESOLVED 2026-07-16; shipped with AP.** AP has **two** caller-supplied-URL sinks, not one: the inbox's remote-actor fetch (dialed pre-signature-verification) *and* the delivery worker's POST to `target_inbox`, which is taken from the `inbox`/`endpoints.sharedInbox` of the actor document the remote itself served. Both are guarded, and both dial through one owner, `activitypub/outbound.rs`. Not accepted on the same terms as the link-preview/federation SSRF precedents, which *are* guarded.
- **F2 — a mentioned user's signing key must not be published to the firehose without their opt-in.** A Bluesky cross-post that mentions a non-linked user should omit the mention facet (or resolve to a public handle URL), not emit the raw actor pubkey. **Design ruling + fix captured.**
- **F3 — mail login must be timing-uniform across valid and unknown users.** The wire text is already uniform; a dummy KDF for unknown users is required so timing does not distinguish them. **Fix captured.**
- **F4 — Nostr must not answer a depositor-membership question from an unsigned probe.** The gift-wrap recipient/membership check must follow signature verification (or the response must be uniform). **Fix captured.**
- **F5 — SMTP recipient existence is an accepted, in-band-mitigable side-channel; the family-safety ward's distinct reject text is not.** Recipient enumeration is endemic to SMTP and closed per-domain by a catch-all actor (shipped off). The ward's *distinct* "approved senders only" reject additionally reveals the mailbox is a restricted ward; that text should be unified with the generic `550`. **Open question retained:** whether the default deployment should reject uniformly for all local domains regardless of existence — a stronger default at some cost to legitimate bounce behavior; unresolved, surfaced to the user.
- **F6 — an unsolicited public `Create{Note}` to the shared/any-user AP inbox must not be stored or indexed absent a local relationship to it. RESOLVED 2026-07-19 (ruling (a), user-directed).** A relationship gate applies after the audience gate: the shared inbox stores a Note only when a local enabled account follows the signature-verified sender or is the addressed target; otherwise accept-and-drop, no retry, no oracle. Brings the inbound direction into line with outbound's pre-existing per-actor enablement gate, so "shipping AP federates nothing on a zero-enabled-account nest" now holds in both directions. Mechanism owned by `behavior/activitypub.md` § The inbound relationship gate.
- **F7 — every outbound Nostr relay dial must route through the shared SSRF guard, and a private-network relay is refused even on the user's own list. RESOLVED 2026-09-29.** Four dial sites (the sync worker's connection pool, the NIP-46 bunker drain, the interaction publish fan-out, the `remote`-link handshake) reach every relay through one lib-side choke point, `fauna_bridge_nostr::relay_client::RelayClient::connect`, which now **requires** a `RelayDialPolicy` and connects only to addresses it resolved and verified under it (the shared `fauna_core::resolve::resolve_permitted_addrs`, predicate `is_global_ip` — the same classifier `crate::ssrf` and F1 use), so a refused target costs no socket and the handshake cannot re-resolve past the check. Three facts settle the ruling: **(a) severity is LOW, fixed rather than accepted.** Every URL source is user-supplied today — the publish list and the bunker string are pasted in the app, and the only production writer of a follow's `relay_hints` is the user-authenticated `add_follow`; nothing ingests NIP-65/NIP-05 advertisements — so this is **self-SSRF**, which matters on a multi-user nest (any account can make the shared box dial its private network) but is not third-party-triggerable. The reach is a WebSocket upgrade: a non-101 reply fails the handshake and its body never surfaces (pinned), so the effect is a blind port/status oracle, wider than the accepted federation-dialer loopback oracle (`validate_peer_url`) because it reached private ranges and IMDS — hence fixed. It becomes MEDIUM the day hint ingestion is built, which is why the hint path is guarded now rather than then. **(b) No private-network allowance for a user-listed relay.** A self-hosted LAN relay is a plausible wish, but the dial runs from the nest's network position, not the user's, and on a shared nest one user's LAN entry is every other user's exposure; the guard is uniform with F1, the media proxy and the federation dialer, and a relay is reached by a name resolving to a globally-routable address like every other peer. Should a real deployment ever need one, the shape is an **admin choice in nest state behind the app UI on all 7 apps** (`principles.md` § One configuration surface), never a flag or env — not built, and not queued, until a deployment asks. **(c) The loopback allowance is a test affordance, in two shapes.** An e2e nest admits a loopback relay only under `test-hooks` **and** `FAUNA_TEST_NOSTR_ALLOW_LOOPBACK` (AP's `FAUNA_TEST_AP_ALLOW_LOOPBACK` pattern, loopback-only, production compiles neither); an in-process test whose paired peer nest sits on `127.0.0.1` passes `RelayDialPolicy::PublicOrLoopback` to the worker constructor instead, since a dependency build carries neither the feature nor the env (the federation dialer's accepted production loopback carve-out is not repeated here — injection makes it unnecessary).

## Implementation status today

- **ActivityPub ships in the image as of 2026-07-16** (`Dockerfile` builds `--features bluesky,nostr,activitypub`; `installers/docker.md` § Feature flags). The AP postures above now describe the running binary, not target state. **Shipping the feature still exposes no content** — the routes mount for everyone (nodeinfo, webfinger, inbox, and the always-present instance actor), but federation is per-actor opt-in in both directions (§ Rulings F6, fixed 2026-07-19).
- **R1 is fully implemented** (search corpus is teaser-only) — the ruling is "leave it," so no gap.
- **F1 is CLOSED** (fixed 2026-07-16, in the same commit that shipped AP — the ship was gated on it). All AP outbound sinks — the inbox's actor fetch, the delivery worker's POST, and the instance actor's signed `GET`s (added 2026-07-22, for peers that refuse an unsigned fetch of their own objects) — route through `activitypub/outbound.rs` → `crate::ssrf`; unit tests pin the loopback / private-range / IMDS / cleartext rejections. `ssrf_safe_https_client` also takes a per-caller `User-Agent`: AP sends one (a second interop peer refuses an unattributed request outright), while the media proxy and link-preview fetchers deliberately send none, so as not to identify this deployment to whatever origin they fetch — a **should** ruling this guard's signature now encodes rather than leaving to each caller to get right. The AP e2e reaches its loopback fediverse server, and a real-hostname interop peer via a second, narrower resolve-override + extra-CA hook, through `test-hooks`-gated exemptions that stay **loopback-only** either way; production compiles neither. The guard bounds the dial, not the reply: every body a caller-supplied URL serves is read through the guard's capped readers (`crate::ssrf::read_capped` / `read_prefix`, 2026-09-28); AP's bounds are in `behavior/activitypub.md` § Security posture.
- **F2–F5 are FIXED** (2026-07-16): the running nest now exhibits the `should` side on every shipped bridge. F2 omits the Bluesky mention facet; F4 verifies the gift-wrap signature before the depositor check; F5 unifies the ward RCPT reject with the generic `550 "User unknown"`; F3 runs a same-implementation dummy Argon2id on the unknown-user IMAP/CalDAV path. Adversarial validation (all four CONFIRMED, none a false positive), the F2 *omit* ruling, and the red-first pins are in a dated security-review verdict (tracked internally). **F5's larger question** — should the default deployment reject uniformly for all local domains regardless of existence — remains an **open user-surfaced ruling** (§ Rulings F5), not yet decided.
- **F6 is CLOSED** (fixed 2026-07-19, ruling (a) — the follow-driven inbound relationship gate). Red-first pin confirmed RED pre-fix; keys on the signature-verified actor, never the Note's self-claimed `attributedTo`; verified by an independent security-review pass (tracked internally).
- **F7 is CLOSED** (fixed 2026-09-29). The guard's seat is the lib (`relay_client::RelayDialPolicy`, required by `RelayClient::connect`; `nip46::NostrConnectClient::dial` takes it too), the resolve-and-pin mechanism is shared with `crate::ssrf` through `fauna_core::resolve::resolve_permitted_addrs`, and the nest computes the policy once, `nostr::relays::relay_dial_policy` → `NostrState::relay_dial_policy` (the sync worker takes it by constructor; the fan-out and the remote link read it from state; `for_test` is production-faithful, so an in-process test with a loopback peer sets the allowance on its own state or worker). Red-first pins, per source: a loopback relay refused before any TCP connect (the listener behind it sees no connection) for a follow's hints and a paired serving box (`sync_worker::tests`), the user's publish list (`interact::tests`), a bunker string's relays (`nip46::tests`) and the lib choke point itself; private ranges, ULA, CGNAT and IMDS refused under either policy; the production policy pinned `PublicOnly` without the e2e env; and the blind-effect claim pinned (a non-WebSocket reply's body never reaches the dial error). The in-tree consumers of the allowance are `conformance_nostr_proxy_delegation`'s in-process HEAD worker dialing its loopback PUB and `nostr_link_proof`'s linking nest reaching the first nest's loopback bunker relay. **The store-time half is built too (2026-09-29):** what the text alone decides — an IP-literal host the policy refuses, a `localhost` / `*.localhost` name (judged as loopback), no `ws`/`wss` scheme and host — is refused when the user adds it, the `parse_https_url` precedent: in every app before the RPC through the shared `fauna_protocol::nostr_relay::relay_url_refusal` (under `is_global_ip`), and again on the nest for the relay list, a follow's hints and a bunker string's relays (`bridge_provider.rs::refuse_undialable_relays`, `invalid_params`, before any write or dial) under `NostrState::relay_dial_policy`, so the loopback affordance admits at store time exactly what it admits at dial time. A DNS name is never resolved at store time; the dial still judges it. The app-side message and per-app adoption are owned by [`../../ui/nostr.md`](../../ui/nostr.md) § Errors & edge cases.
- **P2P relay address discovery is built (2026-10-05)** as § Target posture states it; the version-negotiation figures were measured against the relay binary on loopback, and the image-level witness (`test_iroh_relay.py::test_published_discovery_port_answers_from_outside_the_container`) exists.
