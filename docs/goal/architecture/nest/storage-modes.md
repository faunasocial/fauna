# Nest: Storage — the sealed posture (the storage-mode axis is retired)

Owns: storage-modes
Status: ratified — the no-modes target (direction ratified 2026-07-04; transition mechanics ratified 2026-07-12); the demolition gap is declared in § Implementation status today
Authority: this doc owns what the storage-mode *axis* used to own, re-expressed for its retirement — the single-binary sealed posture, the boot story with no unresolved state, the legacy-mode wire shims and their lifetimes, and the legacy at-rest artifacts a formerly-moded box carries. `encryption-at-rest.md` owns the at-rest *property* (the plaintext floor, readable classes, per-content-kind conformance, the capability-grant primitive) and wins on conflict there. `behavior/onboarding.md` + ui.yaml own the onboarding screens; `nest/common.md` owns the shared nest substrate.

> **Audience:** nest + shared-Rust work (storage layer, boot, wire shims); every app area (the onboarding step retirement and the grants trust surface).
> **Purpose:** the destination — **there is no storage mode.** Every nest stores user content sealed at rest; a box's trust is its current set of user-minted capability grants, per-scope and revocable, not a deployment-wide binary chosen at claim time.

## Implementation status today

**The nest carries no storage mode (built 2026-07-12).** The axis is gone from the server, and the app half's core surface (the onboarding/launch machine states, the six per-app views, ui.yaml) is gone too; the trailing sweep, Nostr's nsec-deposit gate, and the rule-5 compat commit (all below) landed — and on 2026-09-24 the compat-remnant sweep removed the transition contract's wire shims and the compat commit in place (`../version-compatibility.md` § Dimension 2, the fourth write-off), so the retirement is complete with no shim left on the wire.

A fresh nest is content-ready from its first instruction. The nest also classifies nothing at ingest on any box (`process_on_ingest` / `index_on_ingest` deleted with the plaintext arm) — scoring runs only at capability positions (`../content-scoring.md` § The placement matrix). Both gates are the same class split, owned by `../../behavior/content-index.md` § Bridge content in the Search corpus.

## Goal

One nest binary, one storage posture: **user content rests sealed beyond the plaintext routing floor, on every nest.** There is no claim-time trust question, no deployment-wide mode, no unresolved state. What used to be the mode binary is now the two extremes of one axis a user controls per box, per scope, at any time: a box holding **no grants** behaves like the old encrypted mode (it can route, hold, and serve sealed bytes — it cannot read); a box the user trusts holds **broad, auto-renewed grants** (the old plaintext mode's capability, now explicit, scoped, time-bounded, revocable, and logged) — and the axis's top end is the **materialization tier** (2026-08-10): the user's own nest keeping readable derived views of their own scopes, `encryption-at-rest.md` § Readable classes class 4. The grant surface — mint, audit, revoke, the client-authoritative grant log — lives on the Nests page of every app (`ui/nests.md`); the grant primitive is owned by `encryption-at-rest.md` § Capability tiering.

## What replaced each piece of the axis

| The axis had | Replaced by |
|---|---|
| The claim-time trust statement (`encryption_mode_choice`) | Nothing at onboarding (a nest is content-ready from first boot, sealed). The "do you trust this box?" question survives only as an optional one-tap default-grant shortcut (apps feature; built on tui 2026-08-14, the other six trickle down — flow placement, the built shape and its two honest bounds are owned by `../../behavior/onboarding.md` § 3b-ter) — trust is expressed by minting grants, whenever the user chooses. |
| `plaintext_mode_consent` for joining users | Retired without replacement — there is no deployment posture to consent to. What a specific box can read is visible per-user on the Nests page (its grants), not implied by joining. |
| The write-once `nest_mode` row + `storage-mode` marker + boot reconcile | No mode persistence. The row and marker outlived the axis as read-only legacy artifacts until the compat-remnant sweep removed both (2026-09-27, § Legacy artifacts below); the boot reconcile and the mode-unresolved gates are deleted — no unresolved state exists. |
| The `Storage` trait's three impls | One sealed implementation. Ingest verifies seal shape per audience class; there is no server-side classify/index/thumbnail arm reading user plaintext. |
| The mode-as-a-thing offline migration tool (`migrate --to`) | Retired unbuilt. There is nothing to migrate between; a formerly-plaintext box's raw records were sealed by the Phase-3 boot backfill, and its trust re-expresses as grants its users mint. |
| Server-side search/classifiers "in plaintext mode" | Capability positions only: the AUTH'd MDA session, the user's client, or a granted content-processor (the re-score drain). Floor-derived search (public post bodies + public previews) is served by every nest uniformly — it reads nothing sealed. |
| The MDA's `fetch_config.storage_mode` content-path fork | One serve path with per-record discrimination (`OpenStoredRecord`); the wire field was emitted as a constant `"encrypted"` until the compat-remnant sweep dropped it (2026-09-24). |

## The transition contract (client-version skew) — RETIRED 2026-09-24

For the window between the axis's retirement (2026-07-12) and the compat-remnant sweep (2026-09-24, `../version-compatibility.md` § Dimension 2, the fourth user-ruled write-off), an older client could still drive mode-commit onboarding and route its own flows off the mode the nest reported, and a newer client could still bring a pre-Phase-4 nest to a working state. The contract that carried that window (ratified 2026-07-12; the client→nest sender rule 2026-07-14) is recorded here as history — none of it is on the wire any more:

1. **Report the posture, not a mode.** A no-modes nest answered every legacy mode probe with the encrypted-mode value — `fauna.setup.status` → `mode: "Encrypted"`, `fauna.auth.verify` → `storage_mode_pending: false`, `fauna.bridges.fetch_config` → `storage_mode: "encrypted"` — honest, and the value that steered every older client onto its encrypted-mode paths (the only ones that still existed). **Retired:** the three fields left the wire; a peer still sending one lands in the receiving struct's `extra` catch-all.
2. **`fauna.setup.storage_mode` was a validate-then-accept-and-discard shim** — the full ceremony (signature, timestamp, claimed-admin, known mode string), nothing persisted, the requested mode echoed, `mode_conflict` never returned. **Retired:** the kind is unregistered (`fauna.protocol.unknown_kind` to a caller); its `SETUP_STORAGE_MODE_V1` signing tag stays registered so the bytes are never reused.
3. **Every surviving conditional keys on observable data, never on a mode flag** — nsec deposited (Nostr bridging), grant held (the drain); nest-holds-period-key (legacy subscription tiers) was one until its plane was removed 2026-09-27. **Still the rule** (§ Architectural rules 3 and 7 own it); the per-record `is_sealed_mail_record` discrimination is the pattern. (The legacy `nest_mode` row present conditional retired 2026-08-17 with the seal-backfill it gated, and the row itself 2026-09-27, § Legacy artifacts below.)
4. **New client × old nest:** a new client kept *reading* `mode`/`storage_mode_pending` and routed a still-moded nest's admin to the browser path. **Retired** with the fields.
5. **The sender survived the retired UI (the client→nest mirror of rule 1):** after every successful claim the shared onboarding machine probed setup-status and, iff the nest reported `mode: None`, silently committed `encrypted` — the I2 break the real-binary version-skew grid found 2026-07-13 (`../version-compatibility.md` § Dim 6), and the first application of § Dim 2's *mirror rule* (retiring a call a shipped peer still *requires* only in a minimal UI-less form). **Retired:** the compat commit, its `NestApi::submit_storage_mode` seam and its tests are gone; the mirror rule itself stays as doctrine for the next retirement of that shape.

## Legacy artifacts (a formerly-moded box carries these)

**Deletion ruling (user, 2026-07-12):** for the demolition of plaintext mode, existing plaintext-mode rows need **no conversion** — deleting instead of migrating is fully OK (still pre-launch). A demolition slice may therefore drop a legacy plaintext store rather than build a migration for it (applied first to `nostr_dms` in S8.9: plaintext DM rows deleted at the schema rebuild). Already-built converters (the seal backfill below) stood as-built until its own retirement (2026-08-17, below); the ruling removed the *obligation* to convert, it never required removing already-working machinery either.

- **The `nest_mode` row + `{data-dir}/storage-mode` marker — RETIRED (2026-09-27).** Neither was written after the axis retired (2026-07-12), and once the seal backfill below went (2026-08-17) nothing in production read them either; they were kept only under I1's never-dropped rule, which the compat-remnant sweep's baseline reset overrides for pre-sweep remnants (`../version-compatibility.md` § Dimension 2, the fourth ratified exception). The genesis does not create the `nest_mode` table (dead schema: it was created empty and had no writer); the nest has no marker handling, factory reset included (it used to delete the marker beside `nest.db`), and the shared `StorageEncryptionMode` type went with its last reader.
- **Pre-Phase-3 raw records — RETIRED (2026-08-17).** The boot-time seal backfill (`content_seal_backfill.rs`) used to seal residual raw `__mail`/`__calendar` records in place on a legacy-plaintext box, identity-preserving, until it reported complete for a kind. The 2026-08-17 record-identity cutover retired that path instead of letting it keep running: its boot reconcile tombstoned every pre-cutover mail/calendar/card/conv record outright (an alpha-carve-out hard cutover, user-approved, not a migration — `principles.md` § No user-data loss; `message-segment-store.md` § Record identity per kind), so there is no raw corpus left for a backfill to walk — `content_seal_backfill.rs`, its boot call, its marker table, and its e2e harness are all deleted (the marker table is absent from the nest schema's 2026-09-24 genesis). `nest_mode` row presence is no longer any code path's gate.
- **Nest-minted subscription period keys — RETIRED (2026-09-27).** Tiers created under plaintext mode once held nest-side period keys, served by key-presence through a nest-wrap arm; the compat-remnant sweep removed that plane in place (nothing predating the sweep exists to serve — `../version-compatibility.md` § Dimension 2, the fourth ratified exception), so the nest mints, holds and wraps no subscription period key and every tier is client-minted (`../../behavior/monetization.md` § Pillar 1). Its read kinds (`epoch_secret.get` / `archival_blob.get`), the `mls_in_encrypted_mode` refusal and the nest's tier-MLS accessors followed on 2026-09-27 (`../../behavior/restricted-posts.md` § Encryption at rest, room ruling 8, lifted); the plane's four writer-less tables (`period_keys`, `tier_mls_groups`, `tier_epoch_secrets`, `tier_transitions`) and the never-read `actor_successions.period_keys_rotated_at` column were dropped the same day by schema 91's one-shot retire step (`bins/fauna-nest/src/db/migrations.rs`, `retire_tier_mls_schema`).
- **The default grant a formerly-plaintext deployment "receives"** is minted by each user's client (mint authority never moves on-box — `encryption-at-rest.md` § Capability tiering); until a user mints, the box simply holds no read capability, which is a strict privacy improvement and no functional regression (serve/search/score already run at capability positions).

## Boot story

A fresh nest boots content-ready: storage is the single sealed implementation from the first instruction; there is no pre-mode gate, no 409/503 "mode not configured" state, no wizard step between claim and use (works-out-of-the-box). Claim gates remain exactly where claim is genuinely required (admin surfaces). There is no mode-related boot work left at all: the one that existed, the legacy seal backfill on boxes carrying the legacy row, retired 2026-08-17 with the record-identity cutover (§ Legacy artifacts above).

## Architectural rules

1. **One binary, one posture.** No storage mode, no per-user encryption toggle, no runtime or offline mode switch. The trust axis is the per-box grant set, controlled from the user's apps. (The account plane's per-replica posture — `../account-replica-posture.md` § Replica posture, ratified 2026-08-10 — is not such a flag: it is *derived* per replica from user-minted capability reach, changes how nothing rests on any nest, and leaves every rule in this doc intact.)
2. **Sealed-at-rest is universal for canonical stores** — the plaintext floor (`encryption-at-rest.md` § Plaintext floor) is identical everywhere; everything beyond it rests sealed under the owner's keys or an audience key the nest does not hold. The one grant-gated carve-in — a user's own materialization grant keeping readable *derived views* of their own scopes on their own nest — is owned by `encryption-at-rest.md` § Readable classes class 4 (2026-08-10); it is grant data, never a mode, and canonical planes stay sealed under it.
3. **Reading happens only at capability positions** — the AUTH'd MDA session, the user's client, or a holder of a user-minted grant. No nest code path may read user content "because the box is trusted"; trust is a grant, and a grant is data the branch can check.
4. **From a federation peer, nothing changed** — the wire never carried the mode, and grants are equally invisible; peers cannot tell what a box's users have granted it.
5. **Both bridges (MTA/MDA) run everywhere**; the MTA seals post-parse to the recipient key via the single resolver, the MDA opens per-record under session capability. No mode discovery step (the `fetch_config.storage_mode` constant that outlived the axis as compat ballast left the wire 2026-09-24).
6. **DKIM/TLS custody is mode-independent** — TLS by the wrapped-blob provision/fetch protocol, DKIM as the nest's own sealed deployment secret (`../key-material-hierarchy.md` rule 5); the remaining on-disk-PEM tightening is a security-backlog item independent of any mode.
7. **No new wire surface may branch on a stored deployment posture.** A feature that needs to read content declares its capability position (session, client, or grant) — the corollary of rule 3 for designs.

## Don't do these

- **Don't reintroduce a deployment-wide trust flag** in any form — a config value, a "home box" boolean, an implicit "co-resident = trusted" assumption. The grant set is the only trust state.
- **Don't have the nest mint, widen, or auto-renew its own grants.** Mint authority is the user's client, off-box; nest-side auto-anything on grants deletes the confidentiality boundary.
- **Don't reintroduce the legacy wire surfaces** (`fauna.setup.storage_mode`, `SetupStatusReply.mode`, `VerifyReply.storage_mode_pending`, `FetchConfigReply.storage_mode`) — they carried the transition window and left the wire 2026-09-24; a mode is not a thing a peer is told.
- **Don't reintroduce mode persistence** — no `nest_mode`-style row, no data-dir mode marker, no stored posture a boot or feature reads (§ Legacy artifacts above records their removal).
- **Don't gate a feature on "plaintext mode"** — if it needs plaintext, it names a capability position; if none fits, it does not ship (the plaintext-at-rest purpose test is retired *with* its subject: nothing earns *canonical* plaintext-at-rest any more; the sole readable-at-rest surface is the materialization tier's derived views, a capability position like any other — `encryption-at-rest.md` § Readable classes class 4).
- **Don't split the binary** by posture, deployment shape, or human count (unchanged rule from the axis era).
