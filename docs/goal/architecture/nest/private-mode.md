## Goal

A nest a user runs on hardware they control (home NAS, family server, basement box) that participates in the wider Fauna network by pairing with a public nest that acts as its relay. Pairing is per-user and user-authorized (see § Pairing Flow). The private nest holds the user's local data; the public nest sees only opaque ciphertext for forwarded content and acts as the relay through which external clients, federation peers, and remote senders reach the private nest's actors. Identity is the private nest's Ed25519 keypair; the nest↔nest channel is authenticated once with that key at the federation handshake.

---

## What Makes a Nest "Private"

A private nest is not internet-facing. It runs on a home network or behind NAT and cannot receive inbound connections from remote nests or clients on the public internet. Its defining characteristic is the pairing relationship: it pairs with a public nest that acts as its relay and proxy for external communication.

The private nest stores data locally — personal files, encrypted MLS messages, namespace entries — **sealed at rest beyond the plaintext routing floor, exactly like every other nest** (owner: [`storage-modes.md`](storage-modes.md); mechanics: [`../encryption-at-rest.md`](../encryption-at-rest.md)). What the home box can *read* is whatever capability grants its users have minted for it, plus the AUTH'd sessions its MDA serves. The public nest sees only opaque content for everything that is not deliberately public: for sealed content originating on the private nest (namespace entries pushed) the private nest client-encrypts before push; for content originating externally (inbound mail, federated messages from third-party nests) the public nest encrypts at the perimeter to the recipient's standing keys before storage. In either direction, the public nest cannot read that content. The one deliberately-readable class is the **forwarded public post** (§ Post Forwarding): its whole purpose is public reachability, so it rides the channel verbatim (canonical embed-as-bytes, author-signed) and the relay reads it to serve feeds, search, and the create-side bridge fan-out — the same plaintext-by-design class as a public post on any nest. *(This sentence previously listed "posts forwarded" among the client-encrypted classes — drift against § Post Forwarding's ratified verbatim wire, fixed 2026-07-16.)*

Key properties:

- No direct user registration — users register on the public nest.
- No federation endpoints — no ActivityPub, WebFinger, or cross-nest welcome delivery.
- No bridge management — bridges run on the public nest only.
- No admin panel for external users.

## Public/private is a NAT axis, not a trust axis

"Private" = no public-internet inbound MX/HTTPS endpoint, runs behind NAT, paired with a public nest as relay. **It is not a statement about how content is encrypted at rest.** Every nest — public or private — stores user content **sealed at rest** beyond the plaintext routing floor (owner: [`storage-modes.md`](storage-modes.md); mechanics: [`../encryption-at-rest.md`](../encryption-at-rest.md)).

**The storage-mode axis that used to cross this one is retired** (no-modes, 2026-07-12): there is no plaintext/encrypted deployment binary, so the old 2×2 collapses to the single NAT axis. What a given box can *read* is its current set of **user-minted capability grants** — per-box, per-scope, time-bounded, revocable, managed from the Nests page of the user's app ([`../../ui/nests.md`](../../ui/nests.md)) — and that is orthogonal to NAT posture too: a home box its household has granted broad read capability does server-side content work (the old "plaintext box"), while a box holding no grants can route, hold, and relay sealed bytes it cannot open (the old "encrypted box"). A private nest is *typically* the granted one and a VPS *typically* the ungranted one, but nothing in the NAT axis enforces that — the grant set does.

**The NAT mode is app-set, not env/CLI policy.** It is chosen in the onboarding wizard and changeable from the admin panel, persisted in nest DB state — owner: [`common.md`](common.md) § NAT mode (wizard step: [`../../behavior/onboarding.md`](../../behavior/onboarding.md) § 3b-bis). The concrete two-box composition is [`deployment-home-with-public-relay.md`](deployment-home-with-public-relay.md).

## Pairing Flow

Pairing is **per-user multi-homing**: a user authorizes one of their nests to sync their account's content from another, managed from the user's own app ("Linked nests" — see [`../../behavior/linked-nests.md`](../../behavior/linked-nests.md)). It is **not** an admin action. A public-nest admin holds a nest-level policy knob (default-on) that can disable or limit user-initiated pairing, but does not approve individual pairings. The relationship is generalizable to N nests (the schema is N-per-actor).

1. The user authorizes the pairing from their own app via the bearer WS-RPC `fauna.pair.add` (owner-scoped — a user can only pair their own account), supplying the private nest's Ed25519 public key (`private_nest_id`, learned from the nest's app surface — the nests settings page — or an out-of-band code), the requested capabilities, and an optional expiry. The public nest checks the admin pairing policy (§ Nest Pairing Policy in [`public-mode.md`](public-mode.md)) and stores the pairing record under the **calling user's** `actor_id`:

   | Field | Description |
   |-------|-------------|
   | `actor_id` | The user who authorized this pairing (the account the linked nest syncs) |
   | `private_nest_id` | Ed25519 public key of the private nest |
   | `capabilities` | What the linked nest may sync on the user's behalf (`mls_pull`, `namespace_sync`, `post_forward`, `mail_pull`, `nostr_push`), and — ruled 2026-09-30 — whether it holds a replica of the account plane (`account_replica`, § The account-plane replica) |
   | `expires_at` | Optional expiry timestamp; after expiry all sync requests are rejected |
   | `nest_url` | User-supplied URL of the paired nest (app display, and on a private nest the target its workers dial for this row's actor — § Implementation status today) |
   | `label` | User-supplied label for the paired nest (app display) |

2. The private nest can now sync. There is **no** admin approval and **no** "pending" state. The peer-authed `POST /api/v1/pair` + `/api/v1/pair/revoke` handshake endpoints are **retired** — the user grants and revokes; the nest does not "request" a pairing or unpair itself.

   **The private nest needs its own local pairing row to act.** The sync/relay worker (`nest_sync_worker.rs::run_sync_cycle` → `list_pairing_targets()`) reads the **private nest's own** `nest_pairings` and only syncs actors that hold a row there, each against the `nest_url` its row records — so the row authorizing the *public* nest must be stored on the *private* nest, seeded by the user running `fauna.pair.add` while their client is connected to the private nest. The public nest holds the **complementary** row authorizing the private nest to pull (its federation handlers gate every pull on `is_paired(actor, nest_id)` / `pairing_has_capability(actor, nest_id, …)` against the connection's verified nest identity). Because the relay is asymmetric (private polls public — § MLS Message Buffering / § Namespace Sync), a working relationship therefore needs the user's authorization recorded on **both** nests; both are ordinary `fauna.pair.add` calls (the general multi-homing model — log into 2+ nests, then pair them). The pull *target* on the private side is that row's `nest_url` (§ Implementation status today). **The pull target may sit on any address the home box can reach (ruled 2026-09-25)** — a LAN, a VPN or CGNAT range, a docker bridge network — because it is the deployment's own topology, not a URL a request names: the federation dialer's SSRF guard, which refuses every non-global https peer, exempts the deployment's pull target from its global-address arm (it must still be https), while every request- or peer-named URL keeps the guard whole. **Re-decided 2026-10-01 for the move to the row's `nest_url` (§ Implementation status today): the exemption follows authority over the deployment, not where the URL is stored.** A pairing row whose actor is an admin of the private nest names the deployment's topology — the admin is the one human who chooses it (`principles.md` § One configuration surface) — so its `nest_url` keeps the exemption; a row written by any other user is a request-named URL and passes the guard whole. The dialer decides from the row's actor at dial time, so the exemption is never a field a request can set and lapses with the admin role. The **one-action-seeds-both** app UX (the user enters the other nest's address; the client, authenticated to both, writes both rows) is the primary path — shared `LinkedNestsMachine.LinkBoth`, live on all 7 apps ([`../../behavior/linked-nests.md`](../../behavior/linked-nests.md) § One action seeds both ends); the two directional single-end links remain the out-of-band fallback. Concrete two-box composition: [`deployment-home-with-public-relay.md`](deployment-home-with-public-relay.md) § Pairing.

3. All subsequent sync calls ride the authenticated nest↔nest federation channel (§ Sync transport below) — there is no per-call signing; the channel identity established at the handshake is checked against the pairing rows on every kind.

The user revokes a pairing from their own app at any time via the bearer WS-RPC `fauna.pair.revoke`; revocation takes effect immediately and in-flight requests using the revoked key are rejected. The admin can disable pairing nest-wide via the pairing-policy knob.

## The account-plane replica (ruled 2026-09-30; built 2026-09-30)

A sixth capability, **`account_replica`**, a member of the default self-sync set: the user's recorded choice that this linked nest holds a sealed copy of their account plane — the two account-state scopes and an escrow wrap of every generation — so that the nest can serve recovery when the nest their devices are bound to is lost. It differs from the other five in who acts on it. They authorize the *linked nest* to pull or push over the federation channel, and the serving nest checks them on every kind. This one authorizes nothing nest-to-nest and no nest checks it: the account's own devices read it off the pairing row and deliver the replica themselves, over their own authenticated session on the linked nest, where the account is registered and its own doors already admit it. The mechanism, its bounds, and why the pairing channel does not carry it are owned by [`../account-sync-plane.md`](../account-sync-plane.md) § The bind leg, ruling 4. What the linked nest can read of the replica is nothing beyond the custody floor. Removing the capability, or unlinking, ends the replica as that ruling states. The capability is additive on the wire: a nest that does not know the string is simply never a replica.

## Sync transport

All paired-nest sync rides the long-lived **nest↔nest federation WS channel** (`/api/v1/federation/ws`). The private nest dials out and authenticates once at `fauna.federation.hello` with its Ed25519 nest key (mutual nest-key auth — transport + handshake owner: [`../federation.md`](../federation.md)); every subsequent request is a kind-routed CBOR struct (`FedSyncPullRequest`, `FedMlsPullRequest`, …) gated on the **connection's verified subject `nest_id`**: `is_paired(actor, nest_id)` plus the per-capability check for the kind. There are no per-call envelopes and no bearer tokens for nest-to-nest communication.

History: this surface rode interim HTTP routes (`/api/v1/nest-sync/*`, per-call sign-over-CID envelopes) until Spec Y2 slice 5 retired them; the JSON body shapes documented before 2026-07 are dead.

## MLS Message Buffering

When a remote sender creates a DM channel with an actor whose home is a private nest, the Welcome and subsequent channel messages land on the public nest. The private nest polls the public nest to retrieve them.

- **Pull — `fauna.federation.sync.mls_pull`** (capability: `mls_pull`). Request: `actor_id`, `since_seq` — no client-supplied limit; the reply page is server-capped at `segments::SERVE_PAGE_MAX_RECORDS` (500 records) and closes early rather than overflowing the 2 MiB WS frame. Returns buffered messages in sequence order starting after `since_seq`; the public nest reads buffered ciphertext from the per-channel `__conv` segment store (`list_actor_channels` → `segments::conv::read_for_scopes_after_seq`).
- **Acknowledge — `fauna.federation.sync.mls_ack`.** Request: `actor_id`, `up_to_seq`. Confirms delivery up through `up_to_seq`; the public nest calls `segments::conv::tombstone_up_to_seq`, hiding messages with `seq <= up_to_seq` from subsequent reads (physical reclaim of tombstoned segment bytes is the Plan 8 conv compaction — `segments::conv::compact_bucket`).

The private nest is responsible for the polling interval. There is no server-push to the private nest; it must poll actively to receive messages in near-real time.

See `../data-flow.md` — "DM send (cross-nest)" for the full sequence diagram showing how messages arrive at the public nest before the private nest polls.

## Namespace Sync

Generic encrypted data sync between paired nests. The namespace mechanism is a content-addressed key-value store where entries are client-encrypted and actor-signed. The public nest never decrypts namespace data — it stores and forwards opaque ciphertext.

- **Pull — `fauna.federation.sync.pull`** (capability: `namespace_sync`). Request: `actor_id`, `namespace`, `since` cursor. Returns entries from `namespace_entries` where `seq > since`, up to a page limit; the cursor is a sequence number, advanced by the client after each page. Wire entries carry `entry_id`, `ciphertext`, `actor_sig`, and `updated_at`.
- **Push — `fauna.federation.sync.push`.** Request: `actor_id`, `namespace`, `entries[]`. Entries are written to `namespace_entries` under the verified peer nest as `source`.

**A namespace belongs to one actor, and the door enforces it (ruled 2026-09-21).** A namespace is a 32-byte id, and the only one that exists is an actor's **self-namespace** — the actor's own public key; what a record *is* lives in its `entry_id`. Pull and push both refuse a `namespace` that is not the `actor_id` the calling nest is paired for: a pairing is one user's own act, so it can never reach another account's entries, to read them or to overwrite them. The sync worker likewise carries each paired actor's own namespace and no other. If a wider namespace is ever wanted it arrives with its own ownership rule, here, first.

**The nest does not verify `actor_sig` at the door, and cannot.** The signature convention is per entry kind (each domain-separates its own message — e.g. the LAN-TLS cert entry, `fauna_mls::wrapped_blob::lan_cert`), so only a consumer that knows the kind can check it, and every consumer must: a namespace entry is untrusted until its consumer has verified the signature against the namespace's actor **and** applied whatever authority the act needs (the cert installer: an admin of the installing nest — [`tls-certificates.md`](tls-certificates.md) § B tier 2).

**Schema: `namespace_entries`** (PK: `(namespace, entry_id, source)`)

| Column | Description |
|--------|-------------|
| `namespace` | The **owning actor's 32-byte id** — enforced, no longer a convention (the rule above): `fauna.tls.publish_cert` writes the caller's own id, the sync worker carries each paired actor's *self-namespace (= the actor pubkey)* and no other, and both federation kinds refuse a namespace that is not the paired actor's. There are no named logical namespaces — the one producer today is the LAN-TLS certificate entry. Being a person column, it carries the table's deletion and succession ruling ([`../../behavior/opaque-carrier-walks.md`](../../behavior/opaque-carrier-walks.md) § The declared re-point axis) |
| `entry_id` | Client-assigned stable identifier for the logical record |
| `seq` | Monotonic sequence number assigned by the receiving nest |
| `ciphertext` | Opaque encrypted payload — nest never decrypts |
| `actor_sig` | Ed25519 signature from the actor over the entry content |
| `source` | Which nest wrote this entry (supports multiple sources per `(namespace, entry_id)`) |
| `updated_at` | Last-write timestamp (also carried on the wire entry) |

Multiple sources are allowed per `(namespace, entry_id)`. Conflict detection and resolution are deferred to the client — the nest stores all versions and lets the client merge on pull.

## Post Forwarding

Private nest users can participate in the public feed by forwarding signed posts to the public nest.

**Kind:** `fauna.federation.post.forward` on the public nest (capability: `post_forward`).

The request carries a sign-over-CID `Post` envelope (canonical dag-cbor body, embed-as-bytes per `../serialization.md` § Embed-as-bytes for signed payloads) signed by the actor's Ed25519 key over the 36-byte CID. No *nest* signature rides along: the federation channel authenticates the originating nest once at handshake, so the relay's identity is already established and the only signature on the wire is the author's end-to-end binding. The public nest:

1. Verifies the actor signature.
2. Confirms the pairing authorizes this relay — the `(author, origin_nest_id)` row must carry the `post_forward` capability. Enforced when the nest's submission policy is `paired_only`; under the default `open` policy any peer nest may relay a validly-authored post.
3. Takes the same ingest path a locally-created post goes through — **whether a relay classifies a forwarded post, and where post scoring runs at all, is owned by [`../content-scoring.md`](../content-scoring.md) § The placement matrix** (*Federated inbound post* row). *(The relay-side classification this step described in 2026-07-11 was retired with the storage-mode axis in Phase 4; `process_on_ingest` no longer exists.)*
4. Stores the post in the `__post` segment store under `post_id = blake3(canonical_encode(EmbedAsBytes))` — the same id the originating nest derived, so relaying the stored body verbatim is lossless and idempotent (`store_post` upserts; a redelivery is a no-op). A post this nest has seen deleted is answered `Ok` and not stored again — owner [`../../ui/feed.md`](../../ui/feed.md) § State & data shape → *Post deletion*.
5. Includes the post in feeds for subscribers on the public nest.
6. Iff the post was **newly** stored, runs the same create-side bridge fan-out as a local `fauna.posts.create` (`routes::spawn_post_bridge_fanout`: ActivityPub `Create`-push + Bluesky write-through, each self-gated on the author's own enablement on this nest). Rationale + mandate model owned by [`../../behavior/activitypub.md`](../../behavior/activitypub.md) § The produce direction (paired-deployments bullet); the newly-stored gate keeps outbox retries from double-publishing. The storage-replication and outbox-origination legs deliberately do **not** fire on a forwarded receive — they are not per-actor bridge legs (and a public nest never re-forwards; the outbox enqueue is private-mode-only).

The private side originates this from its **outbox**: `fauna.posts.create` enqueues the stored body when its author holds a pairing row on this nest carrying `post_forward` — forwarding is that user's choice, recorded by their own `fauna.pair.add`, never a nest-wide switch — and the outbox worker drains the queue over the channel to the `nest_url` of each such row, retrying with exponential backoff and never dropping an entry it could still deliver — a refusal (a missing `post_forward` capability, or a relay-side content rejection at step 3) keeps the post queued, so a later capability grant or policy change still delivers it, **however long the refusal lasted**. The backoff doubles from 30 seconds and is capped at about 8.5 hours, and there is no point past which a refused entry stops retrying: the grant and the policy that end a refusal live on the relay (its pairing row, its submission policy), where the private nest cannot see them change, so the next retry is the only way it can find out. A **retry ceiling** (ten failures) still exists and bounds the queue in exactly the two cases no grant can end: an entry the nest cannot even send (its bytes do not decode, or its type has no federation kind) and an entry whose author no longer has an account on this nest (the queued deletion an account deletion kept, below). Each keeps its retries up to the ceiling and leaves at it. An entry past the ceiling that is still retrying is *stuck*: its count and the queue depth are the queue's observables, and a stuck forward is something its user must be able to see from the app, never only in a log ([`../../principles.md`](../../principles.md) § One configuration surface). A user's own `fauna.pair.add` re-arms that user's queued entries for an immediate retry — the one-action link adds the relay's row at the same moment — as a nudge, never the mechanism: correctness rests on the retry. **The nudge is throttled per entry and the drain is fair per author (ruled 2026-09-24):** a re-arm (this one, or `fauna.pair.forward_retry` below) makes an entry due no sooner than **60 seconds after that entry's last attempt** — a hard-coded constant, not a knob; the anchor is the attempt time the failure record stamps (`outbox.last_attempt_at`), so re-arming every second retries each entry at most once a minute — and each worker pass takes **every author's oldest due entry in turn** (then every author's second, and so on; one author's own entries stay oldest first, so a post still goes before its own deletion), so one author's backlog of refused entries never fills a pass while another author's newer entry waits. On a nest several users share, the queue is a common resource, and neither a user's retries nor their refusals may starve anyone else's forwards.

Each queued entry is stamped with its author (`outbox.author_id`) so that an account's deletion can find its own queue: a queued *post* is dropped, a queued *deletion* that can still be sent is kept and leaves when sent, or at the retry ceiling. Owner of that ruling: [`../../behavior/opaque-carrier-walks.md`](../../behavior/opaque-carrier-walks.md) § The declared re-point axis.

**The queue is the user's to see and to act on — from the Nests page of the nest that holds it (ruled 2026-09-23).** Whose page: the user's, not the admin's. The queue is per author, the refusal is ended by the user's own act (the relay-side `post_forward` grant, minted by their own `fauna.pair.add` — the one-action link from Settings → Nests), and § One configuration surface forbids a state a user must fix that only an admin's log line reveals. So the reading rides the page whose refresh already answers "which nests carry my account": `fauna.pair.list`'s reply carries an additive `forward_queue` field — the caller's own queued count, their stuck count (past the retry ceiling), and the most recent failure the worker recorded on any of their entries (`outbox.last_error`, an additive column the failure record stamps on every failed send; a successful send deletes the row, so nothing clears it in place. Part of it is the relay's own error code — relay-chosen text — so the nest stores it **control-stripped and cut to 200 characters** (a cut one ends in `…`), keeping the reply far under the WS-RPC message cap whatever the relay answers; the app still renders it as untrusted text) — which every app renders on the Nests page as one page-level status while the count is non-zero and hides otherwise. A public nest reports zeros (nothing enqueues there); an older nest omits the field and an app shows nothing. Two owner-scoped actions, bearer `User` like the pairing kinds: `fauna.pair.forward_retry` re-arms the caller's own queued entries for an immediate retry (the same nudge `fauna.pair.add` gives, for the user who granted the capability on the relay's own side rather than by linking from here — the worker would otherwise wait out a backoff of up to 8.5 hours before it could find the grant); `fauna.pair.forward_discard` drops every entry the caller has queued, posts and deletions alike (the posts themselves stay on this nest — only their relay leaves; a queued deletion the relay never received leaves the relay's copy in place, which the user can delete from the relay itself). No admin-wide reading: the admin of a private nest is one of its users and sees their own queue like everyone else, and the worker's log line remains the operator-free diagnostic. The page UX and IDs: [`../../ui/nests.md`](../../ui/nests.md) § Forward queue.

This allows private nest users to appear in the public social graph and post to channels or feeds without exposing their home nest's address or IP to other users.

**Deletion — the delete twin (built 2026-07-15).** So a forwarded copy on the public nest does not outlive the original (`feed.md` § State & data shape → *Post deletion* → Propagation): `fauna.federation.post.delete` on the public nest, gated by the same `post_forward` capability — a delete rides the removal half of the same relay grant, not a separate one. The request carries the signed embed-as-bytes `Tombstone` (`req.body` from `fauna.posts.delete`) **verbatim**; the public nest re-verifies the tombstone's own author signature exactly as the forward leg does, then applies the deletion through the shared `delete_post_core` (the same author/idempotency checks a local delete uses). A replayed delete is a no-op (`AlreadyGone`, still `Ok`). Origination mirrors § Post Forwarding's create leg: on a private nest whose author's own pairing row carries `post_forward`, `fauna.posts.delete`'s signed-only path (not the connection-actor-trust `unrepost`, which builds an unsigned tombstone with no author-verifiable artifact to relay) enqueues the tombstone as an outbox entry, drained by the same outbox worker as `post.forward`. tier_3 proof: `conformance_cross_nest_post_delete`.

**Residue (declared gap, not target state).** One pre-existing asymmetry, not asserted by this section:

- The private side does not gate forwarding on the local post's own quarantine/suppress decision — matching its sibling outbound paths (nest replication, Bluesky write-through), none of which are quarantine-gated. Enforcement semantics are owned by [`../../behavior/moderation.md`](../../behavior/moderation.md) § Categories & enforcement.

## Email

A private nest does not run an inbound MX listener (no public port 25), and on residential hardware typically cannot do outbound MX delivery either (residential ISPs commonly block port-25 outbound). Mail in a private nest deployment flows through the paired public nest, over the **sealed-`__mail` relay** — built, channel-only:

- **Inbound:** the public nest's MTA bridge receives mail, seals it to the user's standing recipient-mail keys at the perimeter, and stores the sealed `MailRecordEnvelope` in the `__mail` segment store. The paired private nest pulls the sealed records via `fauna.federation.sync.mail_pull` (capability: `mail_pull`; verbatim envelope bytes + floor metadata), appends them to its own `__mail` store, and acks via `fauna.federation.sync.mail_ack`; the public nest then tombstones + purges the acked records. This is the transient-relay analogue of § MLS Message Buffering — **not** the generic § Namespace Sync KV. Deployment composition + per-app frontier: [`deployment-home-with-public-relay.md`](deployment-home-with-public-relay.md) § Implementation status today.
- **Outbound:** MUAs submit on 465/587 to the public nest's submission listener. The public nest signs DKIM and MX-delivers to the recipient, and relays a "Sent" copy to the private nest **via the same `__mail` relay as inbound** (one path, both legs).
- **MUA reach:** the private nest serves IMAP/CalDAV on a LAN-bound listener; MUAs connect on the LAN. TLS optional — the LAN-TLS cert is issued by the public nest's ACME and shipped to the private nest via namespace-sync (`lan_cert::install_client_issued_cert`, called from the sync step; tier_3 `conformance_cross_nest_lan_cert`).

The full per-deployment specifics for the **single-user home box behind a public relay** live in [`deployment-home-with-public-relay.md`](deployment-home-with-public-relay.md). The **multi-human household private nest** — several users' sealed content on one home box, under distinct grant sets — is underspecified; § Implementation status today.

## Use Cases

**Personal file server** — A home NAS running `bins/fauna-nest` with fauna-tui and the per-user sync agent. Local files are accessible across devices; the public nest handles MLS messaging and federation with the rest of the network. Content rests sealed on the home box; the owner's client opens it, and grants let the box itself index or serve where the owner wants that.

**Family nest** — Shared storage and group messaging for a household. Storage on the home box is sealed under each user's keys per the encryption-at-rest invariant, and each member's grants decide independently what the box may read on their behalf. The public nest handles external contacts and ActivityPub federation; the private nest keeps family files and group history at home.

**Mail-canonical-on-residential** — User runs a private nest at home for canonical mail/calendar/messaging storage; mail enters and exits through a public nest on a VPS that they also run. Both boxes seal at rest; the home box opens mail at the MDA's AUTH'd session capability, needing no grant to do it. See [`deployment-home-with-public-relay.md`](deployment-home-with-public-relay.md).

**Privacy-focused** — A private nest restricts content flow to opaque ciphertext the public nest cannot read, and the home box itself stores content sealed. The threat model for a compromise *of the home box* is bounded by the grants its users have minted for it: with no grants, the disk yields only the plaintext floor; with broad standing grants, a compromised box can read what it was trusted to read (and disk-at-rest encryption remains the user's OS-level responsibility either way). Identity is never grantable, so even a maximally-granted box eavesdrops — it never impersonates.

## Security Properties

- **Identity is the keypair.** The private nest proves its identity once per connection with an Ed25519 handshake at `fauna.federation.hello`; there are no shared secrets or API keys to rotate. Every sync kind re-checks `is_paired` + the capability against that verified connection identity.
- **Replay resistance is a channel property.** With per-call envelopes retired, replay is prevented at the transport/session layer (authenticated handshake + TLS); cursors (`since_seq`/`up_to_seq`) make repeated requests idempotent rather than harmful.
- **Namespace entries are actor-signed.** Every consumer verifies `actor_sig` against the namespace's actor key before trusting an entry (the nest cannot check it at the door — the signature convention is per entry kind, § Namespace Sync). A compromised relay or nest can store a forged entry but cannot make a consumer accept it.
- **Expiry limits blast radius.** Pairing records carry an optional expiry. If a private nest key is compromised, the pairing expires automatically; the user can also revoke immediately from their own app (`fauna.pair.revoke`).
- **Public nest is untrusted for content.** All message and namespace content is encrypted before leaving the private nest. The public nest is a delivery mechanism, not a trusted store.
