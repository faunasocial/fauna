# Nest: The update channel and the updater — target state

Owns: update-channel
Status: ratified 2026-10-13 (refutable by the user) — the nest side (slice 1), the updater (slice 2, witnessed at tier_4) and its self-update (slice 3) are built, verification and the UI are not; the ledger in § Implementation status today names every slice
Authority: owns **which builds a running box follows and how that is changed after provisioning** — the update channel as nest state (its at-rest home, its seed from the image tag, the admin kinds that read and write it), the **never-downgrade rule** (the one shared decision over a running version and a candidate), and the **Fauna updater** that enacts the channel on a box: what it replaces, what it holds, what it reads, what it refuses, and how it updates itself. **NOT owned here** — the three channels, their tags and which pipeline moves each tag → [`../image-pipeline.md`](../image-pipeline.md) § Image tags & channels; the wizard page where the channel is first chosen → [`../../behavior/onboarding-provisioning.md`](../../behavior/onboarding-provisioning.md) § 5; the Docker-socket trust class → [`../security.md`](../security.md) § Watchtower (auto-update) trust; the compose bundles' service wiring and the `FAUNA_*` catalog → [`../installers/docker.md`](../installers/docker.md); release signing and the consumer-side verification control → [`../release-integrity.md`](../release-integrity.md) § Release signing; the at-rest downgrade guard (`min_reader_version`, the degraded needs-update boot) → [`../version-compatibility.md`](../version-compatibility.md) § 2.2; the recoverability invariant this closes a breach of → [`common.md`](common.md) § Client-state recoverability; the admin page's placement of the control → [`../../behavior/admin.md`](../../behavior/admin.md) § N Nest.

## Goal

A box follows one of three channels — Stable, Test, Dev — and the admin can change which one from their app at any time after provisioning, with no shell on the box. The choice takes effect on the box's own next check, and a box never moves onto a build older than the one it runs.

Today the channel is baked into the box's compose file as the image tag at provisioning and polled by Watchtower, which follows whatever image reference the container was created with; nothing in any app changes it afterwards, so a box on Test or Dev leaves its channel only by an edit to the compose over SSH. That is a client-reachable state fixable only off-box, which [`common.md`](common.md) § Client-state recoverability calls a bug, and with Test now the channel real users accept releases on and Dev an unverified build, "stuck on Dev after a broken build" is the case that will happen. This doc is the design that closes it.

## The three decisions

**1. The mechanism is a Fauna-owned updater that replaces Watchtower, in every bundle alike.** A container cannot change the image reference it was created with, and the nest runs inside one: re-pointing a running box means re-creating its container from a different reference, which only a holder of the Docker socket can do. Watchtower holds the socket but offers no way to be told a new reference — it follows the container's own, and its instant-update API only re-checks that one — so every path that keeps Watchtower (an env file the compose interpolates, a helper the compose ships) still needs a *second* socket holder or a host-side script, and only the cloud-init bundle has a host to script; the two compose bundles users copy by hand have none. [`../release-integrity.md`](../release-integrity.md) § Third-party container images part 4 already names "replacing Watchtower with a Fauna-owned signature-verifying updater" as the target, so the channel change is built on that updater rather than on a mechanism the updater would retire. It replaces Watchtower in all three bundles — the cloud-init compose, `docker-compose.yml` and `docker-compose.home.yml`, which ships Watchtower exactly as the VPS compose does — so the home path is the same design, not a special case. The updater is the one socket holder a box runs; two updaters would fight over the same container.

**2. The never-downgrade rule is one shared decision, run by the updater to act and by the nest to explain.** A move to a newer channel takes effect at the box's next check; a move toward Stable takes effect only when the channel's current build is at least the running version, never earlier. § The decision owns the exact rule. The at-rest guard behind it is unchanged and stays the last line: an older image opening a newer `/data` boots the degraded needs-update mode instead of touching the data ([`../version-compatibility.md`](../version-compatibility.md) § 2.2), and the updater's next check moves such a box forward again.

**3. The channel is nest state, set from the admin's app, seeded once from the image tag.** Bucket 2 of the one-configuration-surface invariant ([`../../principles.md`](../../principles.md) § One configuration surface): a user choice, so it has UI in all seven apps and rests in nest state; the image tag the artifact was installed with is read only while no admin has chosen (the seed bucket of [`../installers/docker.md`](../installers/docker.md) § Environment Variables, the shape `FAUNA_MODE` has). § The channel as nest state owns the row and the kinds; [`../../behavior/admin.md`](../../behavior/admin.md) § N Nest owns where the control sits on the page.

## The channel as nest state

**At rest.** One singleton row, `nest_update_channel` (`id = 1`, `channel TEXT NOT NULL`, `set_at`), the shape of `nest_max_storage_bytes`: an **absent row** means no admin has chosen, so the nest follows the seed; a **present row** is the admin's choice and wins. The value is a channel id (`stable` / `test` / `dev`), never an image tag or a reference: the one place a channel becomes a tag stays `UpdateChannel::image_tag` (`fauna-provisioning`), and its inverse `UpdateChannel::from_image_tag` is minted beside it for the seed.

**The seed.** The nest container's environment carries `FAUNA_IMAGE_TAG` — the same variable both compose files already interpolate into the `image:` line (`${FAUNA_IMAGE_TAG:-latest}`), repeated as an environment entry; the cloud-init compose writes the literal tag it wrote into `image:`. A tag that is a channel tag seeds that channel; any other tag (`:sha-<sha>`, `:<version>`, a local build's) seeds **no channel**: the box is *pinned*, follows nothing until an admin picks a channel, and the UI says so. An absent variable seeds Stable, matching the compose default.

**What the nest reports.** The channel in force — the row, else the seed — is served two ways. *To the updater and the deploy gates:* a `update_channel` field on `GET /api/v1/health` beside `version`, `commit` and `build_id` (`bins/fauna-nest/src/build_identity.rs` owns that body; the degraded needs-update boot serves `null`, since it opened no database). The channel is not a secret — every tag is publicly pullable and the health body already names the exact version — and health is the surface built so a box can be identified without a shell on it, which is precisely the updater's need. *To the admin's app:* `fauna.admin.update_channel.get` (Admin class), answering `channel` (an `UpdateChannel::id`, absent on a pinned box), `running_version`, and — resolved from the registry on the read and cached for a few minutes, absent when the registry is unreachable — `channel_head_version`, so the app can say whether a held move has caught up; the write is `fauna.admin.update_channel.set { channel }` (Admin class, admin-signed like the region kind; an id that names no channel is refused), audited as `admin:update_channel.set` like the region and web-app-origin writes. Both carry the channel as its id string, never the enum: `fauna-protocol` sits below the `fauna-provisioning` crate that owns `UpdateChannel`, and a string lets a newer nest's channel reach an older app as an unrecognised value rather than a failed decode — the shape the web-app origin read has. An older nest's unknown-kind answer to the read is the "this nest predates the choice" state, never a failed read. Both kinds, the row and the seed are owed on the nest before any updater reads them.

## The decision

The one rule, in shared Rust (`fauna-provisioning::update_channel`, beside the enum; UniFFI and WASM export it with the rest of the module) and consumed by both the updater and the nest's read reply, over four inputs — the running image's version and digest, the candidate's version and digest:

- same digest → **Current**: the box already runs the channel's build — *same* meaning any digest in common, since one image answers to several (the registry names a head by its index, platform-manifest and config digests; the engine knows a running image by its id and the digests it was pulled as); nothing to do. This is also how a move toward Stable *completes* when Stable promotes the very build the box runs on Test: no re-create, no restart — the channel is simply followed from then on.
- candidate version **≥** running version → **Apply**: pull, verify (§ The updater), re-create. Equal versions with different digests apply, because every build of a train carries the train's version string (`:dev` moves many times at one version) and a re-staged build of a numbered release is a different, newer artifact of the same version.
- candidate version **<** running version → **Hold**, carrying both versions: the channel is recorded and followed, but the box stays on its build until the channel reaches it. This is the only outcome a move toward Stable can take while Stable is behind, and the sentence the admin's app renders ("Following Stable from the next Stable release that is at least 0.3.1; this server runs 0.3.1 from Test") is the shared fold's, not the app's.

Versions are the image's `org.opencontainers.image.version` label, which the `Dockerfile` stamps from the workspace version at build (the `FAUNA_VERSION` build arg both build drivers pass, the value `CARGO_PKG_VERSION` of `fauna-nest` carries) beside the revision label it already carries; the updater reads it from the running container's inspect and from the candidate manifest's config blob, so no pull happens before the decision. An image without the label (every image built before this lands) is treated as version zero: a box on such an image applies anything, which is the forward move it wants, and a candidate without the label is never applied over one with it.

## The updater

**What it is.** `fauna-updater`, a second binary of the **same nest image** — `bins/fauna-updater`, copied beside `fauna-nest` into `ghcr.io/faunasocial/nest` — run as a second container of that image with its entrypoint overridden (`entrypoint: ["/usr/local/bin/fauna-updater"]`), at the same tag the nest container names. One image means one tag set, one signature, one stage and one promote in [`../image-pipeline.md`](../image-pipeline.md) § Image tags & channels, with nothing added to that pipeline, and zero extra disk on the box (the layers are shared); the second image, `ghcr.io/faunasocial/updater`, was considered and declined for doubling every leg of that machinery.

**What it holds — the socket and nothing else.** `/var/run/docker.sock` is its only mount: no `/data`, no `/opt/fauna` path, no environment, no port, no inbound listener of any kind. The trust class is exactly Watchtower's — host-root-equivalent through the socket, the accepted posture of [`../security.md`](../security.md) § Watchtower (auto-update) trust, which transfers to whichever component holds the socket — and the inbound surface that posture had to reason about (Watchtower's HTTP API) is gone with it: the updater takes no requests, so `WATCHTOWER_HTTP_API_UPDATE` / `WATCHTOWER_HTTP_TOKEN` retire. The sidecar audit over every shipping bundle (`deployment-threat-model.md` concern 1a: only one service names the socket, and no sidecar holds a secret or a volume) keeps holding with the updater as that one service.

**What it reads — a pull model, three inputs, all of them data.** (1) The nest's `/api/v1/health` over the bundle's own network, at the address and `FAUNA_PORT` the nest container's own inspect gives (its address on the bundle network; `127.0.0.1` under the home bundle's host networking, which the updater shares) — so the updater needs no setting to find it — over TLS first and plain HTTP second, the image's own `HEALTHCHECK` pair, since a deployed nest serves TLS on that port (its ACME certificate, or the self-signed bootstrap one), and with the certificate unverified, because it names the box's public name or nothing, never the bundle address dialled, and nothing rides on it (the reply is a selector, *What it refuses* below) — polled every minute: the `update_channel` field is the channel to follow, else — when the field is `null` or the nest is too old to serve it — the tag on the nest container's own image reference, as Watchtower followed it; a reference whose tag is no channel tag means *pinned*, and the updater holds until the nest reports a channel. (2) The registry, at the channel's interval (next paragraph) and immediately after the reported channel changes: the manifest digest behind the channel's tag and its config blob's version label, by anonymous `HEAD`/`GET` against `ghcr.io/faunasocial/nest` — never a pull before the decision says Apply. (3) The Docker API: the managed containers, found by the label `social.fauna.update=true` (replacing `com.centurylinklabs.watchtower.enable`; label-gated exactly as before, so the sidecars stay unmanaged until [`../release-integrity.md`](../release-integrity.md) § Third-party container images part 4 brings them under the Fauna namespace and labels them), each one's image digest and version label.

**What it refuses.** The nest's answer is a *selector*, never a reference: the updater maps the reported channel to a tag of the one image name it was built to follow, and no text from the nest, the registry or a label can name an image. A compromised nest can therefore move itself between Fauna's own channels — to Dev, the newest unverified build, or hold itself on Test — and nothing else, and the never-downgrade rule applies to a nest-requested move as to an admin's, so it cannot roll itself back onto an older, vulnerable build either. An unreachable nest or registry is a skipped check, never a fallback to "latest"; an unparseable health body or label is data that does not parse, logged and ignored, never an instruction.

**What it does on Apply.** Pull the digest; verify its signature (§ Verification — the control this updater was named for, in its own slice); then the rolling re-create Watchtower did: inspect the running container, create its successor from the new digest with the same configuration (environment, ports, volumes, labels, restart policy, `stop_grace_period`), stop the old one within its grace period so the nest's WS 1001 broadcast and flush complete ([`../transport-connection.md`](../transport-connection.md) § Graceful shutdown), start the successor, remove the old container and, once nothing runs it, the old image. The container's recorded image reference may say `:test` while the box follows Stable; the reference is not the source of truth, the updater's channel is.

**The check interval is a constant per channel, and a security parameter (ratified 2026-10-14, replacing the one-hour-everywhere of 2026-10-13).** **Dev and Test: every minute. Stable: every hour.** Both are Rust constants beside the decision, read through `UpdateChannel::registry_check_interval` — bucket 1 still, since the channel is the admin's choice and its interval is not — plus the immediate check on a channel change. The two numbers answer two different precedents the first ratification did not weigh. *A minute on the pre-release channels* is what the app-provisioned boxes already polled at under Watchtower (their cloud-init rendered a 60 s poll, whatever the channel), and what both pipelines' serving gates assume: the verify job waits 600 s for the staging box (dev.fauna.build on the private pipeline, test.fauna.build on the public one — [`../image-pipeline.md`](../image-pipeline.md) § Image tags & channels) to serve the staged build, a budget the pull and the boot need most of, so a check slower than about a minute would fail that gate on most runs; the pre-release boxes are few — the organisation's nests and testers' — so their registry cost is bounded. The gate's timeout therefore stays where it is. *An hour on Stable* bounds what the check adds to the exposure window [`../deployment-threat-model.md`](../deployment-threat-model.md) concern 1a names — the time from a public fix to its deploy — at one hour on top of a promote that is a human act measured in hours, and keeps the many boxes off the registry: a check is six anonymous requests today (the token challenge, the tag's `HEAD`, the index, the platform manifest, the config blob), so a thousand Stable boxes at a minute would be a hundred requests a second against a registry whose anonymous limits GitHub does not publish, against about two at an hour. The hand-copied bundles' 24 h Watchtower default, which the first ratification measured against, was never a reasoned number. A check whose `HEAD` digest matches the last one seen for that tag ends there (built 2026-10-14: `Registry::head` remembers the last head per tag and platform), so a steady-state check on a pre-release box is three requests, not six. The poll of the nest is local and free at once a minute.

**It updates itself, in lockstep.** The updater runs the image it updates, so after moving the nest to a digest it moves itself to the same one, by the hand-off Watchtower uses shaped to the bundles' `restart: unless-stopped`: it steps aside under the re-create's `-fauna-updater-old` name, creates its successor under its own name from the new digest with its own configuration (the socket mount, the entrypoint override, its labels and restart policy — never the `social.fauna.update` label, which would make it one of the containers it re-creates), starts it and parks; the successor's first act is an API stop of the predecessor (an exit alone the restart policy would undo), then its removal and, nothing running it any more, the old image's. It finds its own container by id — the engine's bind mount of its `/etc/hostname` names it, under host networking too — never by a label. Every interruption settles to one updater: a predecessor that finds its successor created but never started starts it (the nest already runs that build, so the newer updater wins), and takes its name back only when that start fails, when the successor is missing, or when, parked, it finds the successor not running five minutes on; an updater a failed hand-off left behind catches up the next time the nest is found current. An updater built before this hand-off never moves itself — its box moves when its compose is re-applied — which is no end state, because an updater frozen at install day is the one component a bug in which only a re-provision fixes.

**Verification (the slice the updater was named for).** Before an Apply the updater verifies the candidate digest's cosign signature against the Fauna release identity — the consumer-side secondary control [`../release-integrity.md`](../release-integrity.md) § Release signing has waited for a consumer to build; the identity, what is signed and when are that doc's. Until it lands the updater applies on digest and version alone, which is strictly what Watchtower did; the Sigstore client it needs is a dependency add and so a queue entry for the owner's bump round, never a per-row add ([`../dependency-bump-report.md`](../dependency-bump-report.md) § Who opens a round), and the slice is gated on that round.

**The bundles.** In all three bundles the `watchtower` service becomes `fauna-updater` as described (same image and tag as the nest, the entrypoint override, the socket as its only mount, `restart: unless-stopped`, the shared logging anchor), the nest's label becomes `social.fauna.update=true`, `FAUNA_IMAGE_TAG` is repeated into the nest's environment as the seed, and `WATCHTOWER_POLL_INTERVAL` goes (the interval is a constant). `nickfedor/watchtower` leaves the vetted third-party table — a package leaving is not a bump — and the compose-shape tests, the sidecar audit and the cloud-init render tests follow in the same change; the comments across the goal docs that describe Watchtower as what runs today stay true until that change lands and are swept by it.

## The UI

A section on the admin Nest page directly after the web-app origin — the same class of nest-wide deployment fact as NAT mode, the serving port and the origin, adding no nav entry on any of the seven apps — mirroring the NAT-mode radio shape; the page's placement is [`../../behavior/admin.md`](../../behavior/admin.md) § N Nest's, the IDs below are **proposed under rule A and await the user's approval**, and tui leads as on every feature ([`../testing.md`](../testing.md) § Default app and nest mode):

- `admin-nest-update-channel-section` (view) — container / scope for the section;
- `admin-nest-update-channel-stable-radio`, `-test-radio`, `-dev-radio` — one per channel, pre-selected from the read, each labelled and described by the wizard's own strings (`UpdateChannel::label_key` and `description_key_for_major`, so the compat line the wizard shows while the product owes no compatibility shows here too and disappears at 0.2.0 with no app change); on a pinned box none is selected;
- `admin-nest-update-channel-save-button` — commits `fauna.admin.update_channel.set`;
- `admin-nest-update-channel-status` (text) — what the box follows now and when a change takes effect: the running version; "Following Test — new builds are picked up within the hour"; the Hold sentence of § The decision with both versions; on a pinned box, that it follows no channel until one is chosen; on a nest predating the choice, that it cannot be set from the app yet.

Every sentence is the shared fold's (`fauna_client`'s admin fold over the `get` reply, the decision run on `running_version` and `channel_head_version`, exported over UniFFI and WASM), rendered by each app; no app computes a channel sentence. The read folds onto the same nav-edge read as pairing, the serving port, the region and the origin, so every nest-page write re-reads it. When the control lands the provisioning page's "The choice is made here" sentence ([`../../behavior/onboarding-provisioning.md`](../../behavior/onboarding-provisioning.md) § 5) and the guide's "cannot be changed from the app afterwards yet" go, and the admin guide's Nest section gains the control.

## Tests

- **tier_1** — the decision over the four inputs (every cell of the digest × version matrix, the missing-label cases), `UpdateChannel::from_image_tag` round-trips, the fold's sentences; the updater's container re-create builds the successor's configuration from an inspect fixture, and its self-update hand-off and every interrupted hand-off settle to one updater over a recording engine; the compose-shape tests over all three bundles and the rendered cloud-init (one socket holder, the entrypoint override, the seed env, the label).
- **tier_3** — the nest side end to end: the seed from `FAUNA_IMAGE_TAG` and its pinned case, `set` → `get` → `/api/v1/health` reporting the row, the unknown-kind answer on an older binary; the tui section driving `set` through the UI (`test_admin_nest.py`).
- **tier_4** — the real updater against the real image on the self-hosted runner: a harness-served registry on loopback (the Docker daemon accepts plain HTTP from `127.0.0.0/8`, the `FAUNA_E2E_RELEASE_FEED_URL` precedent for a compile-gated origin seam) holding the image under several tags and version labels; a box on Test whose Stable is older is held and says so, is current when Stable reaches its digest, and is re-created when a newer build appears; a channel change from the app is picked up on the next check; the nest's WS 1001 drain completes inside the grace period; the self-update hand-off leaves one updater running the new digest.
