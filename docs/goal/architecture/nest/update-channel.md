## Goal

A box follows one of three channels — Stable, Test, Dev — and the admin can change which one from their app at any time after provisioning, with no shell on the box. The choice takes effect on the box's own next check, and a box never moves onto a build older than the one it runs.

Today the channel is baked into the box's compose file as the image tag at provisioning and polled by Watchtower, which follows whatever image reference the container was created with; nothing in any app changes it afterwards, so a box on Test or Dev leaves its channel only by an edit to the compose over SSH. That is a client-reachable state fixable only off-box, which [`common.md`](common.md) § Client-state recoverability calls a bug, and with Test now the channel real users accept releases on and Dev an unverified build, "stuck on Dev after a broken build" is the case that will happen. This doc is the design that closes it.

## The three decisions

**1. The mechanism is a Fauna-owned updater that replaces Watchtower, in every bundle alike.** A container cannot change the image reference it was created with, and the nest runs inside one: re-pointing a running box means re-creating its container from a different reference, which only a holder of the Docker socket can do. Watchtower holds the socket but offers no way to be told a new reference — it follows the container's own, and its instant-update API only re-checks that one — so every path that keeps Watchtower (an env file the compose interpolates, a helper the compose ships) still needs a *second* socket holder or a host-side script, and only the cloud-init bundle has a host to script; the two compose bundles users copy by hand have none. [`../release-integrity.md`](../release-integrity.md) § Third-party container images part 4 already names "replacing Watchtower with a Fauna-owned signature-verifying updater" as the target, so the channel change is built on that updater rather than on a mechanism the updater would retire. It replaces Watchtower in all three bundles — the cloud-init compose, `docker-compose.yml` and `docker-compose.home.yml`, which ships Watchtower exactly as the VPS compose does — so the home path is the same design, not a special case. The updater is the one socket holder a box runs; two updaters would fight over the same container.

**2. The never-downgrade rule is one shared decision, run by the updater to act and by the nest to explain.** A move to a newer channel takes effect at the box's next check; a move toward Stable takes effect only when the channel's current build is at least the running version, never earlier. § The decision owns the exact rule. The at-rest guard behind it is unchanged and stays the last line: an older image opening a newer `/data` boots the degraded needs-update mode instead of touching the data ([`../version-compatibility.md`](../version-compatibility.md) § 2.2), and the updater's next check moves such a box forward again.

**3. The channel is nest state, set from the admin's app, seeded once from the image tag.** Bucket 2 of the one-configuration-surface invariant ([`../../principles.md`](../../principles.md) § One configuration surface): a user choice, so it has UI in all seven apps and rests in nest state; the image tag the artifact was installed with is read only while no admin has chosen (the seed bucket of [`../installers/docker.md`](../installers/docker.md) § Environment Variables, the shape `FAUNA_MODE` has). § The channel as nest state owns the row and the kinds; [`../../behavior/admin.md`](../../behavior/admin.md) § N Nest owns where the control sits on the page.

## The channel as nest state

**At rest.** One singleton row, `nest_update_channel` (`id = 1`, `channel TEXT NOT NULL`, `set_at`), the shape of `nest_max_storage_bytes`: an **absent row** means no admin has chosen, so the nest follows the seed; a **present row** is the admin's choice and wins. The value is a channel id (`stable` / `test` / `dev`), never an image tag or a reference: the one place a channel becomes a tag stays `UpdateChannel::image_tag` (`fauna-provisioning`), and its inverse `UpdateChannel::from_image_tag` is minted beside it for the seed.

**The seed.** The nest container's environment carries `FAUNA_IMAGE_TAG` — the same variable both compose files already interpolate into the `image:` line (`${FAUNA_IMAGE_TAG:-latest}`), repeated as an environment entry; the cloud-init compose writes the literal tag it wrote into `image:`. A tag that is a channel tag seeds that channel; any other tag (`:sha-<sha>`, `:<version>`, a local build's) seeds **no channel**: the box is *pinned*, follows nothing until an admin picks a channel, and the UI says so. An empty value — an unset `${VAR}` interpolated without a default — seeds Stable, matching the compose default; an **absent** variable seeds none, because it marks a nest the image does not run (next paragraph).

**Where the channel applies (ruled 2026-10-19).** A channel is enacted by the updater, and the updater runs only where the image runs: in a bundle. The nest the Windows and Mac installers carry, a nest installed directly on a Linux machine (`install.sh` under systemd — there is no Linux package for the nest, [`../installers/linux-nest.md`](../installers/linux-nest.md) § Implementation status today; corrected 2026-10-19 from "a Linux package nest") and a local build run as a plain process — no container, no socket holder, nothing that could pull an image — so on them **no channel applies**: not *pinned* (a pinned box is an image box awaiting a choice) but outside the mechanism. The nest tells the two apart by the seed variable's **presence**: every bundle repeats `FAUNA_IMAGE_TAG` into the nest's environment (an unset value interpolates to the compose default, so it is never absent there) and nothing else sets it, so an absent variable is a nest the image does not run — artifact-set IPC, bucket 1 of [`../../principles.md`](../../principles.md) § One configuration surface, the shape `FAUNA_FRONTED_BY_ROUTER` has (`update_channel::enactable`). Not the updater's report file: only a live updater writes it, and the overdue line exists for the dead or absent one. On such a nest the channel in force is none, whatever `nest_update_channel` row an earlier build wrote; `/api/v1/health` serves `update_channel: null`; the admin read answers `enactable: false` (additive — absent on an older nest and then read as `true`, since every older nest is an image nest); `fauna.admin.update_channel.set` is refused, so "a channel chosen that nothing follows" is unrepresentable rather than a state the UI would have to explain; the registry watch of § What the updater reports → *The complement* is not spawned, so a packaged nest asks the image registry nothing; and the apps paint the section read-only with the sentence § The UI names. Such a nest learns of a newer version through the daily release check alone ([`../installers/README.md`](../installers/README.md) § Knowing a newer version is out) and is updated the way it was installed.

**What the nest reports.** The channel in force — the row, else the seed — is served two ways. *To the updater and the deploy gates:* a `update_channel` field on `GET /api/v1/health` beside `version`, `commit` and `build_id` (`bins/fauna-nest/src/build_identity.rs` owns that body; the degraded needs-update boot serves `null`, since it opened no database). The channel is not a secret — every tag is publicly pullable and the health body already names the exact version — and health is the surface built so a box can be identified without a shell on it, which is precisely the updater's need. *To the admin's app:* `fauna.admin.update_channel.get` (Admin class), answering `channel` (an `UpdateChannel::id`, absent on a pinned box and on a nest the image does not run), `running_version`, `enactable` (whether a channel can be enacted here — *Where the channel applies*, above), and — resolved from the registry on the read and cached for a few minutes, absent when the registry is unreachable — `channel_head_version`, so the app can say whether a held move has caught up; the write is `fauna.admin.update_channel.set { channel }` (Admin class, admin-signed like the region kind; an id that names no channel is refused), audited as `admin:update_channel.set` like the region and web-app-origin writes. Both carry the channel as its id string, never the enum: `fauna-protocol` sits below the `fauna-provisioning` crate that owns `UpdateChannel`, and a string lets a newer nest's channel reach an older app as an unrecognised value rather than a failed decode — the shape the web-app origin read has. An older nest's unknown-kind answer to the read is the "this nest predates the choice" state, never a failed read. Both kinds, the row and the seed are owed on the nest before any updater reads them.

## The decision

The one rule, in shared Rust (`fauna-provisioning::update_channel`, beside the enum; UniFFI and WASM export it with the rest of the module) and consumed by both the updater and the nest's read reply, over four inputs — the running image's version and digest, the candidate's version and digest:

- same digest → **Current**: the box already runs the channel's build — *same* meaning any digest in common, since one image answers to several (the registry names a head by its index, platform-manifest and config digests; the engine knows a running image by its id and the digests it was pulled as); nothing to do. This is also how a move toward Stable *completes* when Stable promotes the very build the box runs on Test: no re-create, no restart — the channel is simply followed from then on.
- candidate version **≥** running version → **Apply**: pull, verify (§ The updater), re-create. Equal versions with different digests apply, because every build of a train carries the train's version string (`:dev` moves many times at one version) and a re-staged build of a numbered release is a different, newer artifact of the same version.
- candidate version **<** running version → **Hold**, carrying both versions: the channel is recorded and followed, but the box stays on its build until the channel reaches it. This is the only outcome a move toward Stable can take while Stable is behind, and the sentence the admin's app renders ("Following Stable from the next Stable release that is at least 0.3.1; this server runs 0.3.1 from Test") is the shared fold's, not the app's.

Versions are the image's `org.opencontainers.image.version` label, which the `Dockerfile` stamps from the workspace version at build (the `FAUNA_VERSION` build arg both build drivers pass, the value `CARGO_PKG_VERSION` of `fauna-nest` carries) beside the revision label it already carries; the updater reads it from the running container's inspect and from the candidate manifest's config blob, so no pull happens before the decision. An image without the label (every image built before this lands) is treated as version zero: a box on such an image applies anything, which is the forward move it wants, and a candidate without the label is never applied over one with it.

## The updater

**What it is.** `fauna-updater`, a second binary of the **same nest image** — `bins/fauna-updater`, copied beside `fauna-nest` into `ghcr.io/faunasocial/nest` — run as a second container of that image with its entrypoint overridden (`entrypoint: ["/usr/local/bin/fauna-updater"]`), at the same tag the nest container names. One image means one tag set, one signature, one stage and one promote in [`../image-pipeline.md`](../image-pipeline.md) § Image tags & channels, with nothing added to that pipeline, and zero extra disk on the box (the layers are shared); the second image, `ghcr.io/faunasocial/updater`, was considered and declined for doubling every leg of that machinery.

**What it holds — the socket and nothing else.** `/var/run/docker.sock` is its only mount: no `/data`, no `/opt/fauna` path, no environment, no port, no inbound listener of any kind. The trust class is exactly Watchtower's — host-root-equivalent through the socket, the accepted posture of [`../security.md`](../security.md) § Watchtower (auto-update) trust, which transfers to whichever component holds the socket — and the inbound surface that posture had to reason about (Watchtower's HTTP API) is gone with it: the updater takes no requests, so `WATCHTOWER_HTTP_API_UPDATE` / `WATCHTOWER_HTTP_TOKEN` retire. The sidecar audit over every shipping bundle (`deployment-threat-model.md` concern 1a: only one service names the socket, and no sidecar holds a secret or a volume) keeps holding with the updater as that one service.

**What it reads — a pull model, three inputs, all of them data.** (1) The nest's `/api/v1/health` over the bundle's own network, at the address the nest container's own inspect gives — its address on the bundle network at `:443`, the SNI router whose no-SNI default route is the nest, since the image binds the nest's own port on container loopback ([`../deployment-threat-model.md`](../deployment-threat-model.md) § Concern 1a); `127.0.0.1` at its `FAUNA_PORT` under the home bundle's host networking, which the updater shares — so the updater needs no setting to find it — over TLS first and plain HTTP second, the image's own `HEALTHCHECK` pair, since a deployed nest serves TLS there (its ACME certificate, or the self-signed bootstrap one), and with the certificate unverified, because it names the box's public name or nothing, never the bundle address dialled, and nothing rides on it (the reply is a selector, *What it refuses* below) — polled every minute: the `update_channel` field is the channel to follow, else — when the field is `null` or the nest is too old to serve it — the tag on the nest container's own image reference, as Watchtower followed it; a reference whose tag is no channel tag means *pinned*, and the updater holds until the nest reports a channel. (2) The registry, at the channel's interval (next paragraph) and immediately after the reported channel changes: the manifest digest behind the channel's tag and its config blob's version label, by anonymous `HEAD`/`GET` against `ghcr.io/faunasocial/nest` — never a pull before the decision says Apply. (3) The Docker API: the managed containers, found by the label `social.fauna.update=true` (replacing `com.centurylinklabs.watchtower.enable`; label-gated exactly as before, so the sidecars stay unmanaged until [`../release-integrity.md`](../release-integrity.md) § Third-party container images part 4 brings them under the Fauna namespace and labels them), each one's image digest and version label.

**What it refuses.** The nest's answer is a *selector*, never a reference: the updater maps the reported channel to a tag of the one image name it was built to follow, and no text from the nest, the registry or a label can name an image. A compromised nest can therefore move itself between Fauna's own channels — to Dev, the newest unverified build, or hold itself on Test — and nothing else, and the never-downgrade rule applies to a nest-requested move as to an admin's, so it cannot roll itself back onto an older, vulnerable build either. An unreachable nest or registry is a skipped check, never a fallback to "latest"; an unparseable health body or label is data that does not parse, logged and ignored, never an instruction. Every digest the registry supplies (the head's `Docker-Content-Digest`, an index entry's, the config's) is parsed as `sha256:` plus 64 lowercase hex digits before it reaches a URL path or the pull reference, and each manifest and config body is hashed against the digest that named it before it is parsed (`fauna_provisioning::update_channel::registry::Digest`, built 2026-10-15) — until cosign verification (§ Verification) lands the digest is the only integrity anchor, and a served config can no longer claim a version its digest does not cover.

**What it does on Apply.** Pull the digest; verify its signature (§ Verification — the control this updater was named for, in its own slice); then the rolling re-create Watchtower did: inspect the running container, create its successor from the new digest with the same configuration (environment, ports, volumes, labels, restart policy, `stop_grace_period`), stop the old one within its grace period so the nest's WS 1001 broadcast and flush complete ([`../transport-connection.md`](../transport-connection.md) § Graceful shutdown), start the successor, remove the old container and, once nothing runs it, the old image. The container's recorded image reference may say `:test` while the box follows Stable; the reference is not the source of truth, the updater's channel is.

**The check interval is a constant per channel, and a security parameter (ratified 2026-10-14, replacing the one-hour-everywhere of 2026-10-13).** **Dev and Test: every minute. Stable: every hour.** Both are Rust constants beside the decision, read through `UpdateChannel::registry_check_interval` — bucket 1 still, since the channel is the admin's choice and its interval is not — plus the immediate check on a channel change. The two numbers answer two different precedents the first ratification did not weigh. *A minute on the pre-release channels* is what the app-provisioned boxes already polled at under Watchtower (their cloud-init rendered a 60 s poll, whatever the channel), and what both pipelines' serving gates assume: the verify job waits 600 s for the staging box (dev.fauna.build on the private pipeline, test.fauna.build on the public one — [`../image-pipeline.md`](../image-pipeline.md) § Image tags & channels) to serve the staged build, a budget the pull and the boot need most of, so a check slower than about a minute would fail that gate on most runs; the pre-release boxes are few — the organisation's nests and testers' — so their registry cost is bounded. The gate's timeout therefore stays where it is. *An hour on Stable* bounds what the check adds to the exposure window [`../deployment-threat-model.md`](../deployment-threat-model.md) concern 1a names — the time from a public fix to its deploy — at one hour on top of a promote that is a human act measured in hours, and keeps the many boxes off the registry: a check is six anonymous requests today (the token challenge, the tag's `HEAD`, the index, the platform manifest, the config blob), so a thousand Stable boxes at a minute would be a hundred requests a second against a registry whose anonymous limits GitHub does not publish, against about two at an hour. The hand-copied bundles' 24 h Watchtower default, which the first ratification measured against, was never a reasoned number. A check whose `HEAD` digest matches the last one seen for that tag ends there (built 2026-10-14: `Registry::head` remembers the last head per tag and platform), so a steady-state check on a pre-release box is three requests, not six. The poll of the nest is local and free at once a minute.

**It updates itself, in lockstep.** The updater runs the image it updates, so after moving the nest to a digest it moves itself to the same one, by the hand-off Watchtower uses shaped to the bundles' `restart: unless-stopped`: it steps aside under the re-create's `-fauna-updater-old` name, creates its successor under its own name from the new digest with its own configuration (the socket mount, the entrypoint override, its labels and restart policy — never the `social.fauna.update` label, which would make it one of the containers it re-creates), starts it and parks; the successor's first act is an API stop of the predecessor (an exit alone the restart policy would undo), then its removal and, nothing running it any more, the old image's. It finds its own container by id — the engine's bind mount of its `/etc/hostname` names it, under host networking too — never by a label. Every interruption settles to one updater: a predecessor that finds its successor created but never started starts it (the nest already runs that build, so the newer updater wins), and takes its name back only when that start fails, when the successor is missing, or when, parked, it finds the successor not running five minutes on; an updater a failed hand-off left behind catches up the next time the nest is found current. An updater built before this hand-off never moves itself — its box moves when its compose is re-applied — which is no end state, because an updater frozen at install day is the one component a bug in which only a re-provision fixes.

**Its health (ruled 2026-10-20).** The updater container inherits the image's `HEALTHCHECK`, and nothing listens inside it, so the image's check is role-aware rather than overridden per bundle: where the container's PID 1 is `fauna-updater` it runs `fauna-updater --health`, and otherwise it probes the nest's own listener as before. `--health` reads a heartbeat that the loop writes in the container's own writable layer (`/tmp`, no mount) after every pass in which a managed nest's health read answered. It exits 0 while that heartbeat is no older than ten minutes (`liveness::STALE_AFTER`: a pass that pulls and re-creates the nest writes no beat while it runs). So `healthy` means the updater is running and can reach the nest it keeps current, and `unhealthy` means it is wedged or cut off from its nest, which is the first thing a drifted box is read for. The alternatives were declined for the record. *Turning the inherited check off in each bundle* (`healthcheck: disable: true`) would make the status say nothing. *A compose override per bundle* would be a fourth line to keep in step across three bundles and their two published copies, and it would reach a box only when the box is re-provisioned. The image carries the check to every box at its next update, and the hand-off carries it to the successor, because `successor_body` drops a `Healthcheck` equal to the old image's and so the new image's applies. Nothing acts on the status (`restart: unless-stopped` ignores it). It is read off `docker compose ps` by whoever reads a drifted box, and the admin's own signal stays the nest's `update overdue` line (§ What the updater reports).

**Verification (the slice the updater was named for).** Before an Apply the updater verifies the candidate digest's cosign signature against the Fauna release identity — the consumer-side secondary control [`../release-integrity.md`](../release-integrity.md) § Release signing has waited for a consumer to build; the identity, what is signed and when are that doc's. Until it lands the updater applies on digest and version alone, which is strictly what Watchtower did; the Sigstore client it needs is a dependency add and so a queue entry for the owner's bump round, never a per-row add ([`../dependency-bump-report.md`](../dependency-bump-report.md) § Who opens a round), and the slice is gated on that round.

**The bundles.** In all three bundles the `watchtower` service becomes `fauna-updater` as described (same image and tag as the nest, the entrypoint override, the socket as its only mount, `restart: unless-stopped`, the shared logging anchor), the nest's label becomes `social.fauna.update=true`, `FAUNA_IMAGE_TAG` is repeated into the nest's environment as the seed, and `WATCHTOWER_POLL_INTERVAL` goes (the interval is a constant). `nickfedor/watchtower` leaves the vetted third-party table — a package leaving is not a bump — and the compose-shape tests, the sidecar audit and the cloud-init render tests follow in the same change; the comments across the goal docs that describe Watchtower as what runs today stay true until that change lands and are swept by it.

## What the updater reports

**The question (ruled 2026-10-14; refutable by the user).** On a Dev-channel box the first question after a push is "the push landed — why did the box not move?", and today its answer (registry unreachable, manifest unreadable, pull failed, signature refused, re-create failed, hand-off failed) lives only in `docker logs fauna-updater`, off the box's app surface. The updater is the one Fauna service a working nest cannot relay through the sidecar log plane ([`../apps/observability.md`](../apps/observability.md) § The sidecar log plane): it holds the socket and nothing else — no `/data`, no environment, no inbound listener — so it has no credential to present on either wire leg, and handing it one would change the audited posture. [`../apps/observability.md`](../apps/observability.md) § What retires the `dev.fauna.build` shell accepted this as the sunset's one live residual and asked for the design below; this section owns it.

**The ruling — the engine-written report file: the socket is the credential.** The updater reports through the one thing it holds. It writes a small, schema-fixed report into the nest container's own filesystem through the engine's `PUT /containers/{id}/archive` (the API behind `docker cp`), into the container it already finds for the health poll, and the nest lands the report's events in the remote ring as `updater:<event>` entries — attributed by the leg they arrived on, exactly as the wire legs attribute by authenticated identity, never by anything the payload says. Four reasons it wins. **(1) The updater's declaration does not change by a byte** — the socket stays its only mount, no environment, no port, no token — so the sidecar audit ([`../deployment-threat-model.md`](../deployment-threat-model.md) § Concern 1a) holds unchanged, and the posture [`../security.md`](../security.md) § Watchtower (auto-update) trust accepts is the posture that writes the file: a writer that can already replace the nest's container can write a file into it, so no trust edge is added. **(2) The nest gains no inbound surface and no secret** — one bounded read of a path in its own root filesystem, by a process that runs unconfined already (Landlock wraps the bridges and ffmpeg, not the nest). **(3) The authentication is the socket itself:** the writers of that path are the engine's socket holders, the host's root, and the nest's own UID — and a compromised nest already owns its ring, so forging an `updater:` line gains it nothing — while a co-resident sidecar cannot write it: not a scanner container, and not a bridge in the nest container's other UIDs, since the directory is root-owned and `0755`. **(4) It is network-independent** — the VPS bundle's network and the home bundle's host networking alike — and it works on a stopped nest container: the report waits for the next boot.

**Rejected, each for the record.** *(b) A token channel* — `/internal/updater/ws` in the relay's shape: the relay's token is minted at the nest's boot and read off the container filesystem the two share (`sidecar_tokens.rs`), which the updater does not share; every way of handing it one either goes through the engine's archive API — the file's own mechanism, plus a WS client, plus a token — or injects it into the nest's environment at a re-create, which leaves no channel until the first Apply and plants an environment entry an updater chose. Strictly more than the file for the same posture. *(c) Nest-side inference alone* tells *that* an update is overdue, never *why*; it ships below as the file's complement, not its substitute. *(d) A listener on the updater the nest polls* breaks "no inbound listener of any kind", and under the home bundle's host networking it would be a host-wide one. *(e) A volume shared by the two services* is a second mount on the updater, which the audit forbids.

**The file.** Its path is one Rust constant beside the decision (`fauna_provisioning::update_channel`, shared by the two binaries of the one image — nothing to configure, bucket 1 of [`../../principles.md`](../../principles.md) § One configuration surface): a root-owned `0755` directory the image creates (`Dockerfile`; `/var/lib/fauna-updater`, the file `report.json` — `report::REPORT_PATH`) in the container's **writable layer** — never under `/data` (a volume the nest seals into; a report is not user data) and never a tmpfs (the archive API resolves the container's root filesystem and its volume mounts; a tmpfs exists only inside the container's mount namespace, so a write "into" it lands underneath and is invisible inside). The writable layer is per container, so a re-created nest starts with an empty directory and a report never outlives the container it describes. The content is a JSON document carrying the plane's batch payload and a schema number — `{ schema, events: [{ seq, timestamp_ms, level, event, message }], dropped }` ([`../apps/observability.md`](../apps/observability.md) § Wire) — with one addition, a per-event `seq` that strictly increases across updater restarts and hand-offs, so the nest can tell what it has already landed — the larger of the ledger's last `seq` plus one and the event's wall-clock milliseconds, the ledger read back from the container (`GET` on the same archive API) the first time an updater process writes to it, so a successor or a restarted updater continues it and an updater that cannot read it back still numbers above it; it holds the **last 32 events** the updater produced for that container, a bounded retained history, oldest evicted and every eviction counted into `dropped` as the wire legs count a queue overflow. The updater writes it whole on every event, as a single `0644` root-owned entry in one `PUT`; a read that finds it mid-write does not parse and is retried on the next tick, never logged. It needs no new dependency: the engine client it has (`bollard`'s upload) and a one-entry ustar archive it writes itself.

**The nest's read.** Polled, never inotify — a dependency add for nothing, when a stat of one small file per tick is free: at boot and every ten seconds. The nest keeps an in-memory high-water `seq`; the events above it become the plane's batch (`dropped` = the file's count less the last count seen) and go through the one admission gate every leg shares — `log_plane::admit`, under the new fixed source id `updater` (`LogSource::Updater`): the sanitization, the event charset, the per-source bucket and the split ring, all unchanged. At a nest start the mark is zero, so the retained history lands again — on purpose: the ring is in memory, and an admin opening `admin-logs` after a nest restart sees the updater's recent outcomes rather than nothing. A file that does not parse, or carries an unknown `schema`, is ignored at debug and never becomes a ring entry; an unknown event code is landed as it is (the charset bounds it), so an updater and a nest of different builds — the window between the nest's Apply and the updater's self-update, or an updater that never self-updates — interoperate additively.

**The catalogue — the updater's compile-time module, under the plane's authoring rule.** Events are emitted on transitions and decisions, never per tick, which keeps the catalogue an order of magnitude under the bucket. Levels: **error** for a failed Apply step, **warn** for a hold and for a check that has started failing, **info** for an Apply, a recovery and the pinned state.

| Event | Level | When | Interpolates |
|---|---|---|---|
| `check.registry_failed` | warn | the first failed registry check after a success, or the first ever | the failure kind (a closed enum: dns, connect, tls, timeout, an HTTP status class, an unparseable manifest — a head whose version label does not parse is no failure, it reads as version zero), the channel, the interval |
| `check.registry_recovered` | info | the first success after failures | the failure count, the outage's duration |
| `check.nest_unreachable` / `check.nest_recovered` | warn / info | the same transition pair for the health poll; the message says the updater skips its checks meanwhile (an unreachable nest is a skipped check, never a fallback — § The updater) | the outage's duration, on the recovery |
| `decision.hold` | warn | once per (running, head) pair the decision holds | the channel, both version labels |
| `decision.pinned` | info | once per tag seen | the tag |
| `apply.started` | info | the Apply decision | the channel, the candidate's version, the digest prefix |
| `apply.pull_failed` | error | the pull, or the tag after it | the failure kind (enum: not found, registry, engine), the digest prefix |
| `apply.verify_refused` | error | reserved for § Verification's slice | the refusal kind (enum) |
| `apply.recreate_failed` | error | the re-create | the step (enum: rename, stop, create, start) and that the old container was put back |
| `apply.completed` | info | written to the successor after its start | the running version, the digest prefix, the re-create's duration |
| `self_update.completed` / `self_update.failed` | info / error | by the successor once it retires its predecessor, or by the predecessor on a failed hand-off | the step (enum: tag, rename, create, start) |
| `reconcile.settled` | info | an interrupted re-create or hand-off settled at start | what was found (enum: a finished re-create, an unfinished one put back, a hand-off taken back) |

The interpolation rule: a digest's first twelve hex digits; a version label or an image tag only once it matches `[0-9A-Za-z.+-]{1,64}` — else the fixed word `unparseable`, since a label is registry-sourced text, data and never an instruction; a channel id; the closed kind and step enums; counts and durations. **Never** an engine or registry error string, a URL, a container id or the health body's text — the updater's own stderr keeps those, as every source's does.

**The complement — the nest's own `update overdue` line.** A dead, absent or crash-looping updater writes no report, and a box still on Watchtower has none, so the nest logs this one itself (its own ring, target `update_channel`, warn, once per channel head — keyed by the head's digest): when the shared decision says Apply for the resolved head, and has said so for longer than the channel's interval plus a boot allowance (`UPDATE_OVERDUE_ALLOWANCE`, ten minutes — the serving gate's budget). The nest cannot know its own image's digests, and on versions alone every build of a train is Apply against every other (they share the train's version), so a current box would be "overdue" — so the decision's same-build test is asked of the commit (corrected 2026-10-17, building slice (7)): the head's `org.opencontainers.image.revision` label (`REVISION_LABEL`, the registry read's `ChannelHead::revision`) against the commit the nest binary was built from (the same `FAUNA_BUILD_COMMIT` the `Dockerfile` stamps both with, prefix-tolerant); the same commit is Current, another commit runs the never-downgrade rule on the versions, and a local build (`dev`) or a head without a revision says nothing, never a false overdue. The head is resolved on a tick every `CHANNEL_HEAD_TTL` through the read's own cache (more often only under a shortened e2e allowance), not only on the admin read. The watch runs only on a nest run from the image (§ The channel as nest state → *Where the channel applies*, ruled 2026-10-19): a packaged or installer nest spawns none and asks the registry nothing — it can follow no channel, so there is nothing to be overdue. No `update applied` line: the Apply restarts the nest, whose boot line already names the running version. It says *that*, never *why*; beside the file's `updater:` entries it is the whole answer, and alone it is the answer an old box gives.

**Trust posture.** Unchanged in class ([`../apps/observability.md`](../apps/observability.md) § Trust posture): an `updater:` line is a diagnostic report from the socket holder — sanitized, bounded, rate-limited, attributed — that can mislead exactly as far as a compromised updater, which already holds the box, can; a compromised nest gains nothing by forging one. Build: slice (7) of § Implementation status today.
