# Nest deployment: private home box behind public relay — target state

Owns: home-relay
Status: ratified
Authority: the home-box-behind-public-relay deployment composition — the inbound/Sent mail relay handoff (mail_pull/mail_ack as composed here), the two-row both-ends pairing model + one-action LinkBoth auto-provisioning, per-user serving-toggle usage, LAN-only MDA posture + optional LAN-TLS cert distribution, and the trusted-home-box + ungranted-relay composition on the private NAT axis; defers NAT-mode semantics to nest/common.md (nat-mode owner) with the axis docs private-mode.md/public-mode.md, the sealed storage posture to storage-modes.md, the grant primitive + readable classes to ../encryption-at-rest.md, cert policy to tls-certificates.md, bridge lifecycle + DKIM/TLS provisioning to ../../behavior/mail-bridge-lifecycle.md, DNS custody to ../../behavior/dns-management.md, pairing/multi-homing to ../../behavior/linked-nests.md, MSEK lifecycle to ../../behavior/mail-credentials.md, installer packaging to ../installers/home-relay.md.

The destination for a single-user-or-household hybrid deployment where mail enters the world through a public nest on a VPS the user grants nothing, and is stored canonically on a private nest on residential hardware the household trusts. Specifies the federation handoff for inbound mail, the outbound submission path, MUA reach over LAN, the cert distribution channel, and the no-perimeter-parser configuration of the private home nest. Fully implemented — all five § Done-definition checkboxes met across six slices (Slice 6, 2026-06-04; sealed-at-rest relay Phase-3 D3, 2026-07-08); see § Implementation status today.

---

## Goal

A single human or household running mail on hardware they fully trust at home, with a public-internet-facing relay on a VPS for the parts that residential hardware cannot do (port-25 inbound, port-25 outbound, stable IP, public TLS termination). The residential nest holds the canonical store and all of the user's identity material (MLS keys, actor ID); the VPS nest holds sealed bytes only and acts as a transient relay. Both nests run the same `bins/fauna-nest` and both store user content **sealed at rest** — there is no storage mode ([`storage-modes.md`](storage-modes.md)). They differ on two axes that *are* real: the **public/private NAT axis** (app-set), and their **grant sets** — the household's apps mint the home box standing read grants; nobody grants the VPS anything.

**What the two boxes are, precisely** — this is the "single-user-or-household, hybrid" pattern of [`encryption-at-rest.md`](../encryption-at-rest.md) § The sealed posture → Common deployment patterns (*"Home box holding broad grants + VPS holding none"*):

- **The VPS (public axis, no grants).** It routes, holds, and serves sealed bytes; it cannot read them. Not because of a deployment posture, but because it **holds no key**: the MTA seals each message at ingest to the recipient's MSEK-derived HPKE keypair (§ Inbound mail step 2), and the VPS is never given a grant that reaches it.
- **The home box (private axis, broadly granted).** It holds the canonical store, the user's MLS private keys, and their actor identity. Its household trusts it, and expresses that trust as **user-minted capability grants** — broad, auto-renewed, revocable, audited per box on the Nests page ([`../../ui/nests.md`](../../ui/nests.md)) — which is what lets it do server-side content work (re-scoring; future FTS indexing) on content it holds.

> **Load-bearing: the home box needs NO grant to serve the mail.** Reading relayed mail over IMAP/CalDAV happens at the **AUTH'd MDA session** — a capability position in its own right ([`../encryption-at-rest.md`](../encryption-at-rest.md) § Capability tiering): the MUA AUTHs, the MDA unwraps the user's wrapped-MSEK credential, and the serve path opens each record under that session. Grants are for content work *beyond* serving. So a freshly-linked home box serves relayed mail immediately, with an empty grant set — the deployment works out of the box, and granting is an *upgrade*, never a prerequisite. (The retired "plaintext mode" was never what made this work: relayed mail has rested verbatim-sealed on **both** boxes since Phase-3 D3, 2026-07-08, and has always been opened at the AUTH'd read.)

## Topology

```
┌─ VPS (public axis, no grants) ─────┐         ┌─ Residential (private axis) ────┐
│                                    │         │                                  │
│  Internet  ───port 25──►  SMTP     │         │   nest core                      │
│                           bridge   │         │   (sealed store, MLS keys,       │
│                              │     │ pairing │    actor identity Ed25519 key)   │
│                              ▼     │ ◄─────► │                                  │
│                          public    │ federa- │            │                     │
│                          nest      │ tion    │            ▼                     │
│                     (holds no key) │         │   IMAP/CalDAV listener           │
│                                    │         │   bound to LAN interface         │
│  MUAs ──port 465/587──► MTA submit │         │            │ LAN                 │
│  (public internet)      / MX out   │         │            ▼                     │
│                                    │         │           MUAs                   │
└────────────────────────────────────┘         └──────────────────────────────────┘
```

**VPS holds:** SMTP bridge (MTA mode), the public-axis nest, the user's wrapped MLS-key blobs and the deployment's per-(domain,selector) DKIM key (deployment material the public nest holds sealed under its own key-encryption key, not per-user), public TLS certs for the MX hostname. It holds **no read grant** from this user and no key that opens their mail.

**Residential holds:** the nest binary on the private axis (no perimeter parser; IMAP/CalDAV bound to LAN), the user's MLS private keys, the user's actor identity Ed25519 keypair, the canonical mail/calendar store (content rests **sealed**, as on every nest, and opens at the AUTH'd MDA session or in the user's client — [`../encryption-at-rest.md`](../encryption-at-rest.md) § Readable classes), optionally a TLS cert issued by the public nest and shipped over federation, and whatever **standing read grants** the household's apps have minted it.

**The residential box may run on a Windows or macOS desktop, not only Linux/Docker.** The topology is protocol-based — the same `bins/fauna-nest` + Go `fauna-mail-bridge` MDA runs on a home desktop via the desktop installers (the MSI / `.pkg`). Making a Windows/macOS nest actually *serve* the residential IMAP/CalDAV listeners — cross-compiling + supervising the MDA, **MDA role only** (the MTA stays on the public nest) — is designed in the desktop-native CalDAV/IMAP design (ratified 2026-06-18; tracked internally).

**Pairing:** standard per-user pairing with the public nest as the relay side, per [`private-mode.md`](private-mode.md) § Pairing Flow. The user authorizes their own pairing from their client (`fauna.pair.add`); no admin approval is involved, and the user need not be the nest admin.

Because the relay is **asymmetric (the private nest polls the public nest)**, the working pairing relationship needs an authorization row on **both** nests, and both are the user's own `fauna.pair.add` (no new mechanism):

- **On the public nest:** `(actor, private_nest_id, caps incl. `mail_pull`)` — this is what **authorizes the private nest to pull** (the public nest's federation handlers gate every pull on it: `pairing_has_capability(actor, origin_nest_id, mail_pull)` / `is_paired(actor, origin_nest_id)`). Seeded when the user links the *private* nest while their client is connected to the public nest.
- **On the private nest:** `(actor, public_nest_id, caps, nest_url)` — its **presence is what makes the private nest's sync/relay worker run for that actor**, against the public nest's URL the row records (the worker reads the private nest's own `nest_pairings`; owner [`private-mode.md`](private-mode.md) § Implementation status today). Seeded when the user links the *public* nest while their client is connected to the private (home) nest.

This is the general per-user multi-homing model ([`../../behavior/linked-nests.md`](../../behavior/linked-nests.md)) — *"log into 2+ nests, then pair them"* — applied to the two boxes the user runs. The **one client action that seeds both ends** (the client, authenticated to both nests, writes `fauna.pair.add` to each — the user enters the other nest's address and the client discovers both ids via `fauna.nest.info`) is **built on all 7 apps** (shared `LinkedNestsMachine.LinkBoth`, § One action seeds both ends in linked-nests.md; native render lifts landed 2026-06-13, web dispatches `LinkBoth` over the wasm peer seam, tui's Nests page landed 2026-07-24). The two directional single-end links remain the out-of-band fallback. The user sets the private box's **NAT mode** (`public`/`private`) from their client — in the onboarding wizard and changeable from the admin panel, persisted in nest DB state ([`onboarding.md`](../../behavior/onboarding.md) § 3b-bis; mechanism: the app-set NAT-mode design, ratified 2026-06-15, tracked internally). The installer only **seeds** the pre-claim default (`FAUNA_MODE=private`, used before any client has set the authoritative DB row — see § Implementation status). The user provisions the NAT mode and the pairing from their client — the authorization and the *pull target* (the public box's URL, recorded on the home-side row; the address guard lets it be non-global only on an admin's row — [`private-mode.md`](private-mode.md) § Pairing Flow) — never CLI/env (product invariant: nest policy is app-set).

**The same link action also provisions the user's mailbox onto the home box — automatically, reusing the public box's MSEK.** The mail keys (`bridge_*` blobs: MLS snapshot, recipient-mail pubkey, wrapped-MSEK read credential) are per-nest and do **not** federate, so the home box must be provisioned independently of the public box; the **only** thing that must match across the two is the MSEK (the home box's MDA can decrypt the relay's seal-to-recipient only if it derives the *same* recipient keypair). Because the MSEK lives in the account's fleet-only mail custody on the **client** (`fauna.state.mail`, the account plane) — which neither nest can read — only the client can provision the home box, and it does so by re-sealing the account's MSEK onto the home box rather than minting a fresh one. This rides the link: the client, already authenticated to both boxes for `LinkBoth`, builds a peer-bound mail machine against the home box carrying the account's mail custody and dispatches `ProvisionRelayMailbox` (`libs/fauna-client-mail-settings`). The home box gets the **read recipe only** — no submission token, since it runs no MTA (§ Outbound mail). A fauna client logged into the home box reads the same MSEK from the same custody — the account plane is the account's, whichever box the client is connected to — so relayed mail is readable there with nothing copied per box (the per-box `__config` mail-section copy the link once wrote, user-ratified 2026-07-09 when the MSEK lived in the box's `__config`, went with the 2026-09-30 consumer cut). So a non-technical user links their home box once and relayed mail is immediately readable there — in their fauna client *and* over LAN IMAP — with no second "enable mail" step (MSEK lifecycle + the one-per-actor-across-every-box rule: [`../../behavior/mail-credentials.md`](../../behavior/mail-credentials.md) § MSEK lifecycle, rule 8).

## Inbound mail

External MTA → public nest:

1. Sending MTA delivers to the user's domain's MX, which resolves to the VPS. SMTP bridge (MTA mode) terminates the SMTP session and runs the standard inbound policy stack from [`smtp-server.md`](../../behavior/smtp-server.md): connection-time policy, STARTTLS gate, RFC-5322 parse, SPF/DKIM/DMARC/ARC verification, spam scoring.
2. Bridge seals the parsed message body and index hint to the user's MSEK-derived standing recipient-mail HPKE keypair (`EncryptToRecipient`), ships to the public nest with verdicts (per [`mail-bridge-lifecycle.md`](../../behavior/mail-bridge-lifecycle.md)).
3. Public nest stores the wrapped blob plus the standard plaintext-floor metadata (message ID, ciphertext size, timestamp, recipient routing, envelope FROM, verdicts). Public nest cannot read the body.

Public nest → private home nest:

4. The paired private nest pulls the new inbound-mail records from the public nest by **polling `__mail` over the nest↔nest WS-RPC federation channel** (Spec Y2 slice 4, live in prod) — the transient-relay analogue of the conversation `mls_pull` / `mls_ack` buffering (per [`private-mode.md`](private-mode.md) § MLS Message Buffering, whose **settled target transport is that same channel**), via new channel kinds `fauna.federation.sync.mail_pull` / `.mail_ack`. **Not** the generic `namespace_entries` KV (mail lives in the `__mail` segment store, not in namespace entries), and **not** a new HTTP `/api/v1/nest-sync/*` route — the HTTP nest-sync shape is interim residue slated for retirement ([`../federation.md`](../federation.md) § Implementation status today, slice 5), so the relay is built channel-only. The sealed `MailRecordEnvelope` records travel as opaque ciphertext (HPKE-sealed to the user's standing recipient-mail HPKE keypair); the public nest never holds a key to open them.
5. The private nest **places each relayed record into its IMAP mailbox** (INBOX, or Sent for own-submission / Junk per the floor's spam disposition — assigning the home box's *own* local UID) so the MDA serves it. The record is stored **verbatim-sealed** on the home box, as on every nest (Phase-3 D3, built 2026-07-08): the relay ships sealed bytes and the home appends them exactly as sealed (`relay_actor_mail` → `append_sealed_record`, `bins/fauna-nest/src/nest_sync_worker.rs`); the AUTH'd MDA session or the user's client opens them on read via the per-record discrimination path ([`../encryption-at-rest.md`](../encryption-at-rest.md) § Readable classes). **No grant is involved** — the AUTH'd session is itself the capability position (§ Goal). The former *unseal-on-receipt* mechanism (a home box opening each record with a client-deposited plaintext MSEK) is **RETIRED**: the `actor_plaintext_msek` custody table is **dropped** (Phase-3 S4b; absent from the nest schema's 2026-09-24 genesis), `fauna.bridges.provision_plaintext_msek` lived on as an **accept-and-discard compat shim** (an older client's deposit call succeeded but stored nothing) until the compat-remnant sweep removed the kind on 2026-09-24, and the client's `ProvisionRelayMailbox` (`libs/fauna-client-mail-settings`) no longer transmits the plaintext MSEK to any box. tier_3: `conformance_cross_nest_mail_relay.rs::home_without_any_key_material_stores_relayed_mail_sealed_verbatim` and `conformance_cross_nest_home_relay_journey_client.rs::home_relay_journey_stores_relayed_mail_sealed_never_literal_plaintext` (the full client-driven loop: real `LinkBoth` provisions the read recipe, deposits nothing, the relayed record lands sealed and opens with the recipient's own MSEK-derived secret — no data loss). **The placement IS new relay code (Slice 6):** the IMAP fetch path joins `bridge_imap_messages`, so a relayed record that lands only in `__mail` (no placement) is invisible to the MDA — the relay mirrors the MTA-ingest placement (`relay_actor_mail` → `place_relayed_record`).
6. On ack, the public nest **tombstones** the acked records (the `__mail` segment) **and expunges the IMAP placement** the MTA created at ingest (`bridge_imap_messages` — `purge_mail_placements_up_to_seq`), then reclaims the segment via the scheduled compaction sweep (the conv `mls-ack` → tombstone → compaction reclaim is the model). Expunging the placement is **Slice 6 relay code**: tombstoning the segment alone leaves the placement row (and its metadata — sender domain, timestamp, UID) visible in the MDA's INBOX (the `EXISTS` count reads placement rows directly), violating the no-readable/persistent-copy property. After purge the public nest holds no readable or persistent copy of the mail — the property the e2e test asserts (§ Done definition).

**Retention window — target-state.** The shipped shape is purge-on-ack plus indefinite retention of un-acked mail (the private nest may be offline; purging is destructive). A configurable per-user retention *window* on the public nest — identical for this deployment and for any other nest's users, not VPS-frontend-specific — is a deferred feature (app UI + nest state when added; see § Implementation status today).

### Relay frame budget (ratified 2026-07-12; rule 1 built 2026-07-13, rule 2 live since the 2026-07-18 continuation-write flip)

The federation channel rides the same 2 MiB WS frame as every WS-RPC surface
([`../transport.md`](../transport.md) § Max frame), and `mail_pull` pages by **count**
(up to 500 records per reply) with **no byte budget** — so one reply whose assembled
envelopes exceed the frame is unsendable, and because the puller's contiguous-ack
discipline (correct, keep it) can never advance past an undelivered record, the actor's
relay **stalls permanently at that page**: every later message stays on the public box,
invisible to the user. Reachable when ratified — the perimeter then admitted raw messages to
~8 MB, and a v1 envelope (the write format until 2026-07-18, since retired) crossed 2 MiB at
roughly a 1 MB raw message. Two rules close it:

1. **The `mail_pull` reply is byte-budgeted.** The handler assembles records until the
   next one would overflow the frame budget, then closes the page early (`up_to` = the
   last included seq). Never skip-and-continue: a skipped record that the ack cursor
   passes is purged un-relayed — irrecoverable loss. A shorter page is always safe (the
   puller simply pulls again). **Built 2026-07-13** (`mail_pull_handler`,
   `bins/fauna-nest/src/federation_handlers.rs`; pinned by
   `conformance_cross_nest_mail_relay.rs::mail_pull_pages_close_early_on_the_frame_budget`
   and `::a_single_over_frame_record_freezes_the_pull_instead_of_skipping`).
2. **No single record may exceed the frame — by construction, not by guard. LIVE since
   2026-07-18.** With continuation records
   ([`../message-segment-store.md`](../message-segment-store.md) § Continuation records),
   every stored record — parts and heads alike — is frame-sized, so rule 1's early-close
   always makes progress. Continuation *writes* were gated off from 2026-07-13 until the
   deployed-reader confirmation cleared on **2026-07-18** (the same gate as the v2
   envelope flip; `../message-segment-store.md` § Continuation records → Implementation
   status). **Both rules are now live.**

   **Deployment consequence: the blocker is LIFTED — a public relay box may now go in
   front of real mail.** (A plain single-box nest was never affected: no relay leg.)

   ⚠ **Carry-over for any box that ran between 2026-07-12 and the flip:** a single
   over-frame record written in that window (reachable at ~1 MB raw once the bulk-plane
   legs opened the perimeter) still stalls that actor's relay at rule 1's boundary with a
   loud per-record error. Such a record is **not** healed retroactively by the flip — new
   writes split, old ones do not. The remedy is the targeted re-append-as-parts heal on
   the source, now possible since writes are enabled.

**Topology invariant the headless-part reaper's proof rests on (stated 2026-07-18): no
nest both relay-pulls an actor's mail and locally ingests mail for that same actor.** The
paired deployment satisfies it by construction — the MTA lives on the public box; the
private nest receives that actor's mail only via `mail_pull`. A future shape that puts a
family-writing MTA (or LAN-SMTP ingest) on a relay *destination* must revisit
`reap_headless_parts` first — its head-above orphan proof is provenance-blind and would
falsely reap a relayed family awaiting its head (owner detail:
[`../message-segment-store.md`](../message-segment-store.md) § Continuation records).

## Outbound mail

MUA → public nest:

1. The user's MUAs (Thunderbird, Apple Mail, K-9, etc.) submit on port 465/587 to the public nest's submission listener — the same MTA bridge in submission mode. Submission travels over the public internet from wherever the MUA device is (home, mobile, traveling).
2. Bridge does MUA-AUTH, unwraps the user's submission token from a per-credential wrapped blob fetched from nest. The deployment DKIM signing key never reaches the bridge: the public nest holds it and signs at the outbound hand-out — owner: [`mail-bridge-lifecycle.md`](../../behavior/mail-bridge-lifecycle.md) § DKIM provisioning (automatic).
3. Bridge parses and enqueues the message on the public nest, which DKIM-signs it at the outbound hand-out; the bridge MX-delivers it to the recipient's MX server.
4. Bridge ships a "Sent" copy to the public nest, sealed to the user's MSEK-derived standing recipient-mail HPKE keypair (the same seal as inbound). Sent copy stores as a wrapped blob alongside inbound mail.
5. The Sent copy relays to the private nest via the same `mail_pull`/`mail_ack` path as inbound (§ Inbound mail steps 4–6): stored verbatim-sealed, opened at the AUTH'd read.

The private home nest does NOT terminate submission, sign DKIM, or do outbound MX delivery. The deployment's DKIM key lives on the public nest only, sealed under that nest's own key-encryption key — the same custody it has on any normal multi-human nest.

**Why submit to the public nest and not to the private nest over LAN/mesh:**

- The private nest doesn't run the submission listener (it's in `private` mode; no perimeter parser, no submission listener).
- DKIM signing and MX delivery happen at the same trust boundary regardless (the public nest, since residential ISPs block port 25 outbound). Splitting signing from delivery would require shipping the DKIM key to residential — an unnecessary additional copy of a sensitive key.
- MUAs on the user's mobile devices have no LAN/mesh path to residential when the user is traveling. The public nest is reachable from anywhere.

## MUA reach (IMAP / CalDAV)

The private home nest runs an IMAP/CalDAV listener bound to its **LAN interface only** — no public-internet binding. MUAs on devices on the same LAN connect directly. There is no proxy through the public nest, no tunnel for IMAP traffic, no plaintext IMAP traffic flowing through the VPS.

**TLS posture:**

- **Default: the nest's own self-signed certificate, from boot.** The IMAP/CalDAV listener always terminates TLS — the mail helper has no plaintext mode and refuses a sign-in over an unencrypted connection — on the self-signed certificate every nest writes at first start ([`tls-certificates.md`](tls-certificates.md) § A. The self-signed floor), so a mail app is asked to accept it once. The listener never binds to a non-LAN interface. (This bullet said "Default: no TLS … accepts plaintext" until 2026-10-01, contradicting the next bullet, § Cert provisioning summary, § Implementation status today, and the code.)
- **Optional: a publicly trusted certificate for the LAN listener.** If a publicly-trusted cert is wanted for a hostname under the user's domain (e.g., `home.example.com`, with an A record pointing to a non-public-routable IP), HTTP-01 can't validate it, so it is obtained via a **client-published DNS-01 challenge** — the admin's client holds the DNS-provider key and publishes the `_acme-challenge` TXT (per [`../../behavior/dns-management.md`](../../behavior/dns-management.md) § Where the credential lives); **no nest holds DNS-provider keys or writes DNS**. Either way the resulting cert is shipped to the private nest over the namespace-sync channel and written plaintext on residential (a private-key-on-trusted-storage box; disk-encryption posture is the underlying OS's and the user's, per [`../encryption-at-rest.md`](../encryption-at-rest.md) § The sealed posture).

**The home box stays domainless, and must never be given the apex.** Claimed at its LAN address, it registers no mail domain and its identity stays the `localhost` fallback — the deliberate local-target carve-out owned by [`domains-and-tls-bootstrap.md`](domains-and-tls-bootstrap.md) § Claim. In *this* composition that is the resting state, not a step to undo: the apex `example.com` resolves to the **public** nest, so registering it on the home box would make two boxes claim one identity while DNS points at only one of them. Nothing in the deployment needs it — inbound arrives by federation pull, not by local RCPT-TO resolution (§ Inbound mail), outbound goes through the public nest's submission (§ Outbound mail), and the mail key that must match across the two travels on the link, not in a domain name (§ Pairing). A publicly-trusted LAN name, if the user wants one, is the separate `home.example.com` + client-published-DNS-01 path in the bullet above — a *different* name from the apex, and its own opt-in.

> ⚠ **Adding a first domain here is a ONE-WAY DOOR — say so before inviting a user through it.** The first domain added to a domainless box becomes the **primary**, and the primary row *is* the deployment identity; the primary can never be removed ([`../../behavior/mail-multidomain.md`](../../behavior/mail-multidomain.md) § Removing a local domain), and the only other exit is the primary-**rename** ceremony, which is gated on the primary being non-local and in any case only moves the identity to *another* real domain ([`../../behavior/mail-primary-domain-rename.md`](../../behavior/mail-primary-domain-rename.md)). There is no revert-to-domainless from any app. This is **not** a client-state-recoverability violation (`common.md` § Client-state recoverability): the box keeps working and renaming onto the right domain is a genuine client-side exit — but it is irreversible enough that the published home/relay guides deliberately do not tell the user to add a domain here. Pinned by `adding_a_real_domain_to_a_domainless_box_is_a_one_way_door` (`bins/fauna-nest/tests/storage_mode_api.rs`), the sibling of the local-target claim test — **red-verified**: with the `is_primary` guard in `soft_delete_mail_domain` temporarily disabled the test fails, so it observes the guard rather than passing incidentally. Note the ACME loop this *cannot* cause: on the private axis ACME is force-disabled outright (`acme_enabled = node_mode != Private && …`, `bins/fauna-nest/src/acme.rs`), so a domain added to a default home box orders no certificate and retries nothing.

Neither nest holds DNS-provider credentials (client-held — owner: [`dns-management.md`](../../behavior/dns-management.md)). The private nest does NOT run its own ACME client; the public nest's own MX/HTTPS certs ride HTTP-01, and the optional residential cert follows the bullet above.

**Off-LAN reach** (the user's mobile device when they're traveling): out of scope of this doc. The user has two reasonable options, neither owned here: (a) read mail via a Fauna app that sees the same store via fauna-sync; (b) reach residential over a mesh/VPN they configure separately. The IMAP/CalDAV listener does not bind to mesh interfaces by default — mesh reach is a deployment choice the user makes outside this spec.

The public nest does NOT serve IMAP/CalDAV for this user, even though as a normal nest it could (the AUTH'd MDA session would open the records without any grant — which is exactly why the toggle exists). This is a **per-user, user-set** IMAP/CalDAV-serving toggle: it lives in the user's own `mail-settings` (the user controls where they read their mail, per the product invariant — it is **not** an admin-only knob; the admin sees it read-only for audit), defaults **on**, and the deployment user turns it **off** on the public nest. Mechanically (Slice 2, landed 2026-06-03) it is a **per-actor nest DB flag** (`actor_mail_serving`, default on / absent ⇒ on), set by the user via the User-class, caller-scoped RPC `fauna.bridges.set_mail_serving_enabled` and read via `fauna.bridges.get_mail_serving_enabled` (a User reads its own; an Admin reads any actor's for the read-only audit view). The nest-side MDA-serving gates consult it **per request**: `require_local_mail_serving` (`bins/fauna-nest/src/bridge_imap_handlers.rs`) for every IMAP serving handler, and the `BridgeMda`-only path of the CalDAV handlers (`bridge_caldav_handlers.rs`) — one flag covers both protocols the MDA hosts. It is deliberately **not** carried in `fauna.bridges.fetch_config`: that reply is *deployment-wide* (one bridge-actor config that gates listener binding), whereas this is per-actor; and the Go MDA serves every IMAP/CalDAV operation via a fresh nest RPC with **no local mail/calendar cache**, so the nest-side gate alone fully enforces the opt-out — no `fetch_config` field, no `config_changed` push, and a flip takes effect on the MUA's next operation. The user's own Fauna app (the `mail-settings`/Events surfaces, which reach `bridge_caldav_*` as `User` class on their own actor) is never gated by this flag — it governs where the *MDA* serves external MUAs/CalDAV clients, not whether the user can read their own data. Other users on the same public nest are unaffected. The UI home + element ID fit the ratified flat mail-UX (the `mail-settings` family — **no `bridges-detail-*` IDs**): the ID `mail-settings-serve-here-toggle` is allocated in `ui.yaml` and rendered on **all 7 apps** as of 2026-06-07 for the original six (linux lead 2026-06-03; web + android 2026-06-04; windows 2026-06-04; macos + ios via the shared FaunaKit `MailSettingsView`), plus tui via `MailSettingsMachine`; see `mail-settings.md` § Local IMAP/CalDAV-serving toggle.

## Cert provisioning summary

The general server-side cert policy this deployment specializes — the always-live
self-signed floor, the tiered trusted-cert acquisition (HTTP-01 for the public
nest, client-published DNS-01 for the non-routable residential cert), and how a
cert stays alive and trusted — is owned by
[`tls-certificates.md`](tls-certificates.md). This table is the home/relay
specialization of it.

| Cert | Hostname | Issuer | Where it lives | Served on |
|------|----------|--------|----------------|-----------|
| MX SMTP | `mx1.example.com` | public nest's ACME | public nest disk + SMTP bridge `CertReloader` | port 25 STARTTLS, 465/587 on the VPS |
| Public nest WS-RPC / federation | public nest's domain | public nest's ACME | public nest disk | public nest's HTTPS endpoint |
| (Optional) Private home nest IMAP/CalDAV | e.g., `home.example.com` (A points to RFC1918 / non-public-routable) | LAN self-signed (default), or client-published DNS-01 (§ MUA reach TLS posture; owner: dns-management.md) | shipped via namespace-sync, written to private nest disk plaintext | private nest's LAN-bound IMAP/CalDAV listener |

A non-public-routable hostname can't use HTTP-01; the publicly-trusted option is the client-published DNS-01 path (§ MUA reach). The simpler default is the **LAN self-signed cert** (the LAN is the trust boundary), which needs no DNS at all.

## Architectural rules

- **The public-side nest is a perfectly normal nest that happens to hold no grants.** No "VPS-frontend mode" flag, no special code paths, no storage posture. Everything specific to this deployment is per-user configuration that applies only to users who opt in. Other users on the same nest are unaffected. (Engineering Priority #1: minimize divergence.)
- **The private-side nest runs the same `bins/fauna-nest` on the private NAT axis.** The NAT axis is the *only* deployment-wide axis, and it is **app-set** (at onboarding + changeable from the admin panel, persisted in nest DB state — `FAUNA_MODE` is only the pre-claim seed). It is not a permanent CLI/env policy. There is no storage-mode axis to set: both boxes seal at rest ([`storage-modes.md`](storage-modes.md)).
- **The home box's trust is its grant set, not its deployment shape.** Being the household's box, being on the LAN, being co-resident with the user — none of these grant it anything. Read authority reaches it only as a **user-minted capability grant** (for content work) or an **AUTH'd session capability** (for MDA serving). The one is minted from the Nests page; the other is the MUA's AUTH. See [`../encryption-at-rest.md`](../encryption-at-rest.md) § Capability tiering.
- **All identity material lives on the residential nest, except DKIM and TLS certs.** MLS keys, actor identity Ed25519 keys, and the canonical (sealed) content live on the residential box. The DKIM key lives sealed on the public nest (which signs). TLS certs are public-by-design and live on whichever box serves them.
- **Federation between the two nests uses the standard private-nest pairing mechanism.** No new transport, no new auth. The same `private-mode.md` flow.
- **Per-user retention on the public nest is the only knob for "how long does the VPS hold ciphertext."** It is a regular nest feature, not VPS-frontend-specific.
- **No nest holds DNS-provider keys or writes DNS** (owner: [`dns-management.md`](../../behavior/dns-management.md)). The public nest's own certs (MX, public-side HTTPS) ride **HTTP-01**; the optional residential IMAP/CalDAV cert is LAN self-signed or client-published DNS-01 (§ MUA reach).
- **Submission goes to the public nest, signing happens on the public nest, MX delivery happens on the public nest.** The private nest has no role in the outbound mail path, only in receiving the "Sent" copy via federation.
- **This relay seam generalizes to any server-side bridge that needs to read content.** Mail is the first consumer; **Nostr bridging is the second, and is now built** ([`../../ui/nostr.md`](../../ui/nostr.md) § Architecture). The delegation argument is now a *capability* argument, not a mode one: translating content to Nostr events requires reading it, so the bridge head must be a box holding a reaching capability — in this deployment, the home box. (Bridging is gated per-user on the user's **nsec deposit**, the explicit per-user trust act, not on any deployment posture — `nostr_accounts.encrypted_privkey` presence, per `nostr::db::any_nsec_deposited`; the earlier interim gate on the legacy `nest_mode` row was retired 2026-07-12, the row now inert for Nostr — `storage-modes.md` § Implementation status today.) Reuses this pairing + the federation channel + the per-actor `nest_sync_worker`, gated by a new `nostr_push` capability over `fauna.federation.sync.nostr_{push,pull}` (head-originated both ways; pull is non-destructive — unlike mail there is no purge-ack). Mechanism owner: [`../../ui/nostr.md`](../../ui/nostr.md) § The bridging gate → Phase 2 (spec ratified 2026-07-22). One refinement to this doc's earlier prediction: Nostr needs **no `PostLinkHook` consumer** — unlike the MSEK (client-held, only a client can move it), the proxy vouch derives entirely from the pairing + the head's first push, which auto-provisions the public box's keyless account row. Spec ratified 2026-07-22; built 2026-07-23, T1–T6 conformance-proven ([`../../ui/nostr.md`](../../ui/nostr.md) § Implementation status today).

## Don't do these

- **Don't add a "VPS-frontend mode" to the nest binary.** Use the existing per-user settings (retention, IMAP/CalDAV-bridge-disabled, pairing) instead. *(This anti-pattern still holds after the NAT axis became app-set, 2026-06-15: that work did **not** add a new mode value — it kept `NodeMode::{Public,Private}` and only moved its **provisioning** from env to client. No "relay"/"p2p"/"vps-frontend" enum value was added; "relay" stays the existing `fauna.pair.add` pairing and "p2p" stays the automatic LAN transport.)*
- **Don't reintroduce a deployment-wide trust flag to describe the home box** — not a "home box" boolean, not a "trusted" config value, not an implicit "it's on the LAN / it's co-resident, so it may read." This is the axis that was just retired; re-adding it under a new name is the one way to undo the retirement ([`storage-modes.md`](storage-modes.md) § Don't do these). The home box's read authority is a **grant** (data a branch checks) or an **AUTH'd session**, and nothing else.
- **Don't tunnel MUA IMAP traffic through the public nest.** The home box's store is reached on the LAN, and the MDA opens records there under the MUA's AUTH'd session. Tunneling IMAP through the public nest would expose *opened* mail to the VPS during user sessions, defeating the deployment's privacy property.
- **Don't run a DNS-writing ACME client on either nest.** DNS credentials are client-held (owner: [`dns-management.md`](../../behavior/dns-management.md)); don't run an ACME client on the private nest at all.
- **Don't move DKIM signing to the private nest.** Signing without a delivery path (residential ISPs block port 25 outbound) means the signing key has to ride to the public nest on every outbound message anyway. The uniform wrapped-blob pattern is the right answer.
- **Don't run the perimeter parser on the private nest "just in case."** It would either be dead code (mail isn't routed there) or, worse, create a second potential entry point with no clear semantic for which nest is authoritative.
- **Don't bind the private nest's IMAP/CalDAV to all interfaces.** LAN-only. Public-internet IMAP exposure for this user lives nowhere in this deployment.
