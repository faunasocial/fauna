## Goal

After a nest's box is **completely lost** — the cloud VPS deleted, the self-hosted disk dead, the whole `/data` gone — the **admin's client** re-instantiates a working nest with **no SSH, no shell, no manual surgery**, such that:

1. the rebuilt box re-presents the **same `nest_actor_id`**, so every app that TOFU-pinned it (and any public domain's DNS `self=`) reconnects without a trust break; and
2. the user's content (posts, mail, calendar, files, contacts) is restored from the user's backup destinations.

This is the recovery floor extended from *"the box survived a wipe"* (factory reset, `nest/common.md`) to *"the box is gone."*

## Total box loss vs. factory reset — what is actually lost

`nest/common.md` § Client-state recoverability already solves recovery when the **disk survives**: factory reset preserves the nest's deployment identity on disk and restores it at the next boot (the preserved-file table and the restore mechanism are owned there — one owner), so the re-claimed nest re-presents the **same** identity. That preservation is purely on-box.

**Total box loss destroys the disk itself**, so every "Preserved" file in that table is gone — crucially the raw 32-byte seed in `nest_deployment.key`. With no off-box copy, a rebuilt box mints a *fresh random* deployment seed on first boot → a **new `nest_actor_id`** → every TOFU-pinned client rejects the next channel binding as an identity change and never reconnects (a stuck `Disconnected`, exactly the gap `nest/common.md` describes for an *unwanted rotation*), and a public domain's `self=` record no longer matches. The nest's identity is the one piece that **cannot be regenerated** — it *is* the identity. Everything else is either restorable (user data) or re-derivable (below).

## What must be recovered

- **Nest identity — the deployment Ed25519 signing seed (= `nest_actor_id`).** Irreplaceable. Must be custodied **off-box** to survive total loss. This is the subject of this doc. **The deployment seed is the nest's *single* identity** — it backs the channel-binding `nest_actor_id` clients TOFU-pin **and** (post-unification, decision 2026-06-29, now implemented) `fauna.nest.info`, federation, the backup-destination pubkey, multi-nest pairing, and the nest's own sync `device_id`/`service_id`. The legacy *second* key `nest_identity.key` has been **retired** into the deployment key (`NestIdentity` is a view over it), so the one custodied seed restores the *whole* nest identity. See § Single-identity unification.
- **User data** — restored from the user's backup destinations per `backup-restore.md` (BackupKey-sealed, replicated to the owner's other locations; the seal is the *data owner's* key, so the recovery box never needs to decrypt it to hold it). Out of scope here beyond the reference.
- **Re-derivable, no backup needed** — the TLS cert (re-issued via ACME on the new box), the DKIM signing key and MX/SPF/DMARC/DKIM records (re-provisioned + re-published by the admin's client, which holds the DNS keys — `dns-management.md`), and the bridge keypairs (the co-located bridges re-enroll against the rebuilt nest and are auto-approved once mail is re-enabled, § Onboarding auto-approval). A/AAAA are re-pointed to the new box's IP via the DNS API.

## Mechanism — client-custodied deployment seed

**Where the custody map rests: the account plane** — the fleet-only, tip-sealed kind `fauna.state.deployment-seeds`, one row per custodied box (its row grammar, decode posture and merge rule: [`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule). § The plane-era recovery floor owns how it is read before sign-in and written before the runtime exists; this section keeps the *what*: the seed that is custodied, its two origins, the co-admin channel, and the restore primitive. *(History: until the consumer cut the map rested in the `__config` blob, BackupKey-sealed and copied onto every owned box by a seed-map fan-out; the fan-out, the blob's device-local replica and the claim-time capture retired with the cut.)*

The deployment signing seed is custodied in the **admin's own account state** — sealed under the account's generation key like every fleet-only kind, readable by any of the admin's enrolled devices and, after total device loss, by the identity seed alone through escrow recovery. This is the realization of the `key-material-hierarchy.md` target that *"the deployment-signing seed itself stays on the admin's client."* Custodied there, the seed survives the box.

**Capture — two origins, both ending with the seed in the admin's account state:**

- **Client-provisioned cloud VPS** (the handle-first wizard, our orchestrator holds the cloud + DNS keys): the admin's client **generates** the deployment seed and **injects it at provision** so the box boots with that identity instead of minting its own; once the admin's client is signed in to the new box, the custody leg (§ The plane-era recovery floor, *(c)*) fetches the seed back from it and merges it. *(No new exposure: a cloud-hosted box's keys are on the provider's disk regardless of who minted them — the cloud-trust assumption is unchanged. A self-hosted seed never transits a third party.)*
- **Claim-an-existing box** (self-hosted / BYO, where the nest minted its own seed on first boot): the nest serves the deployment signing seed to an admin over the **authenticated** WS-RPC channel (`fauna.admin.deployment_seed.get`), and the admin's client merges it through the plane door. This is the one nest→client exposure of the seed; it is gated to a roster admin over the authenticated channel — an admin already holds full nest-admin authority, so it crosses no new trust boundary. The claim reply still carries the seed on the wire, populated and unread (removing it is a wire change for [`../version-compatibility.md`](../version-compatibility.md) to schedule).
- **A later-added co-admin captures the same seed over the same channel (ratified 2026-08-11).** A co-admin granted after claim ([`../../behavior/admin.md`](../../behavior/admin.md) § Admin continuity and succession) never saw the claim, so without this leg the roster's continuity promise is hollow — the survivor would hold the role but not the recovery custody. The claiming admin and a co-admin now capture the same way: the custody leg is self-healing rather than event-driven — an admin's client that finds itself on the roster with no custody entry for the bound nest captures idempotently at its next edge, so the leg needs no push, survives crashes, and converges late-added devices the same way. **Honest cost, stated:** removal from the roster does not retract a captured seed — no mechanism untells a secret — so demoting an admin leaves their copy standing; the remedy for a hostile ex-admin is a deliberate seed-rotation event — § Deployment-seed rotation below — which makes the retained copy worthless rather than pretending to retract it.

**Restore — re-provision with the saved identity:** the admin's client (on any surviving device, or after re-onboarding its own identity seed per `onboarding.md` / `devices.md`) re-provisions a fresh box with the saved deployment seed **installed at provision** (cloud-init env for cloud; an installer input for self-hosted), so the new box re-presents the **same `nest_actor_id`**. It then re-points A/AAAA to the new IP via the DNS API, lets the box re-issue its TLS cert and re-provision DKIM, and restores user data from the backup destinations. Pinned clients reconnect seamlessly (same channel-binding identity; `self=` still matches). The unifying primitive is **"provision a box with a caller-supplied deployment seed"** — used identically at first provision (client-provisioned origin) and at recovery.

## Deployment-seed rotation — the deliberate rotation event (ratified 2026-08-11; nest half + tui app half BUILT 2026-08-12, other 6 apps pending — § Implementation status today)

**What this is.** The one sanctioned way a deployment **changes** its identity: a successor deployment seed (⇒ a new `nest_actor_id`) adopted by the box **with a signed continuity bridge**, so enrolled apps re-pin without a trust break and every superseded seed stops authenticating anything. This is the "deliberate admin event" every seed-stability rule has always carved out (`key-material-hierarchy.md` § Roots; `nest/common.md` § Factory reset) and the remedy the co-admin leg's honest-cost paragraph prices its irrevocable holder set against (§ Mechanism above): **no mechanism untells a secret, so the only way to evict a hostile ex-holder is to make the secret they hold worthless.** Before this design, rotation was a self-inflicted outage — a fresh identity with no bridge strands every TOFU-pinned app on the identity-changed warning (`security.md` § Transport trust), and the nest-internal KEK's ciphertexts (step 4 below) become undecryptable.

**When.** Deployment-rare, admin-initiated, and **immediate — no pending window.** The delayed-pending-action shape the roster acts use is deliberately *not* copied: delay serves the attacker in the compromise-response case, and rotation takes nothing from legitimate roster members (their custody self-heals, § Custody after rotation). Triggers: a roster member was removed and must lose recovery custody (the hostile-ex-admin case); a custody device was exposed; hygiene.

**Ordering rule — rotate only into a clean roster.** The successor seed reaches **every current roster member** via the self-healing capture (§ Mechanism, co-admin bullet), so rotating while the party being evicted still holds a roster seat hands them the successor and achieves nothing. The remove must be effective first (it is a delayed pending action — `admin.md` § Admin continuity); the rotate handler **refuses while any admin-remove pending action is in flight**, and the app's confirm surface lists the current roster — the set that will inherit — before dispatch.

### The ceremony

**The client mints; custody precedes dispatch (the CR-1 discipline, `nest/common.md`).** The driving admin's client generates the successor seed (`generate_deployment_seed`, the cloud-provision origin reused), **durably custodies it first** — a new `deployment_seeds` map entry keyed by the successor `nest_actor_id`, sealed + saved + fanned out exactly like a claim capture — and only then dispatches **`fauna.admin.deployment_seed.rotate`** (Admin-class, authenticated channel; the seed transits the same accepted class as the claim hand-off, in reverse — `SecretString` in memory, § Trust & audience). A caller therefore cannot flip a box to an identity nobody has persisted; a crash anywhere before dispatch leaves at worst an orphan custody entry — harmless, re-drivable — never an uncustodied live identity.

**One nest transaction (the atomic decision point):**

1. **Verify:** the seed derives to a fresh identity. Deriving to the current head → `AlreadyRotated`, an idempotent ack (retry safety — the client-minted seed makes the retry converge by construction). Deriving to any superseded ancestor → refused: a revoked identity never returns. Any admin-remove pending action in flight → refused (ordering rule above).
2. **Append the rotation statement** (wire below) to the append-only `nest_rotation_log`, seq = head + 1.
3. **Swap** the DB `nest_keypair` row to the successor.
4. **Re-encrypt the nest-internal KEK satellites under the successor-derived keys, in the same transaction** — **every** member of that family, whose authoritative list is `bins/fauna-nest/src/nest_kek.rs`'s `SATELLITES` (the derive context strings are unchanged, only the root bytes rotate — `key-material-hierarchy.md` § Rotation schedule, Nest-internal KEK row, which owns the membership rule). The box holds both roots at this instant and never again; skipping this step is user-data loss of the deposited-nsec class. ⚠ **Do not re-enumerate the family in prose here** — this step listed three ciphertext kinds until 2026-08-12 and omitted the ATProto authoring sub-key, a ratified sibling of the same entry; the single list in code is what the ceremony walks, and it is deliberately **not** cargo-feature-gated, because the shipped flavors differ in which planes they compile and a gated walk would skip whatever the rotating binary was not built with.

Post-commit, the handler also **clears the bearer token store** — the live-session convergence forcing function; the ruling and its refused alternatives live in § Client acceptance → *Live-session convergence*. Post-commit, `nest_deployment.key` is rewritten. A crash between commit and rewrite heals at boot: `reconcile_deployment_keypair` gains rotation-awareness — an on-disk key matching a **superseded ancestor** in the rotation log means the DB decision stands and the file is rewritten forward. Today's "on-disk identity wins" rule holds only for keys the log does not supersede (first-boot adoption and the inert env seed are unchanged). Every write here passes the `nest/common.md` § Client-state recoverability verification question: the transaction is the single decision point, and every tear lands in a state a client (or the boot reconcile) drives forward.

**No dual serving.** From the commit on, the box signs channel bindings — and everything else — with the successor only; a superseded key never signs again. The bridge for pinned clients is the **statement chain**, not a transition window of the old identity: serving the old identity "for compatibility" would hold open exactly the impersonation window rotation exists to close.

**Adoption by the running process — in-process serve-generation restart (ratified 2026-08-12).** The transaction rewrites the DB; what makes § No dual serving true of the *live* box is that, once the rotate reply has flushed, the nest **tears down its serving generation and re-enters `start_server`** — the same in-process re-enter the admin serving-port change already uses (`desktop_serve.rs`), now with a second edge (`AppState.serve_restart`, fired by the rotate handler on the factory-reset reply-flush delay) and available on every shape, the standalone binary included. A *serving generation* is the server task, every in-flight connection task, and every long-lived worker spawned by `start_server` or the post-start section — all scoped to a per-generation `CancellationToken` + `TaskTracker` (`AppState::spawn_scoped`); teardown cancels, then awaits the tracker bounded, then re-enters, and `start_server` rebuilds the entire object graph — identity, signing key, the subscription-MLS credential, every worker with its derived material — from the rotated DB. The process never exits.

Why not the two obvious remedies:

- **Not a per-site field swap.** The running process's object graph *is a cache of the identity* — the two `AppState` fields are only the visible tip: workers clone the seed at construction, the subscription-MLS credential is built from it at startup, and the rotate handler itself reads its `old_seed` from the stale field (so a second rotation in one process would sign against the wrong predecessor). A swap's completeness rests on enumerating every cache — the enumeration failure mode step 4 above was already bitten by once. Rebuilding the graph is the only shape whose completeness is structural.
- **Not a process exit.** `std::process::exit` + supervisor restart rebuilds the same graph but adds a dependency on an external supervisor the box cannot guarantee — sanctioned supervisor-less shapes exist (a dev `./fauna-nest`, the e2e harness), and a rotation that leaves the box down until a human returns fails `nest/common.md` § Client-state recoverability in spirit even where the on-disk state is perfect. Factory reset's exit is **not** precedent: its exit is load-bearing (the wipe must run at boot, before the DB opens); rotation has no boot-time semantics, so it must not import the supervisor dependency without the reason.

**The bounded hand-off window, stated rather than hidden:** between the commit and the teardown, the old generation may still sign — the rotate reply itself must flush on a connection the old generation serves (the same reply-flush delay factory reset uses). This is transition mechanics bounded at the sub-second class, not a compatibility window: no *new* connection is ever answered by the ancestor after the re-enter, and in-flight connections are torn down, never migrated. Teardown completeness is ratchet-enforced — a long-lived spawn in the nest's serve graph that bypasses `spawn_scoped` is refused by a source-level test (request-scoped/one-shot tasks carry an explicit `spawn-ok` marker); if the ratchet ever proves leaky, the named escalation is a runtime-per-generation, where any spawn dies with its generation by construction. ⚠ **The ratchet did prove leaky once, and how it leaked is the rule to carry forward** (fixed 2026-08-12): **drain-reach, not task shape, decides whether a task is safely "connection-scoped".** Federation and sidecar peer WS connections *looked* connection-scoped — they die with their connection — but the class's justification names two mechanisms that must actually reach the task (the 1001-drain of `state.ws`, and hyper's idle timeout for plain HTTP), and a peer channel is **neither** a `state.ws` client nor plain HTTP, so both clauses missed it while the task held `Arc<AppState>` for a peer-controlled duration. A second blindness rode with it: a guard that greps for bad *spawns* cannot see a defect that consists of **not spawning** — reverting these routes to an un-scoped `on_upgrade` closure removes the spawn entirely — so the connection-future shape carries its own pin beside the marker ratchet. If you cannot name the teardown mechanism that reaches a task, it is not connection-scoped; it is unscoped.

**Both ratchets cover the whole nest source tree, and going tree-wide is what proved the leak was a population rather than an incident (2026-08-12, row 89).** That fix surveyed the two files it had in hand; applying the same drain-reach rule across `bins/fauna-nest/src` found **three more WS upgrade families of the identical shape** — the sync-device channel, the nest-link worker channel, and the public `/nostr` relay endpoint — each holding `Arc<AppState>` on axum's detached per-connection task, none of them a `state.ws` client, none plain HTTP. None was a regression; each had been that way since it was written. The rule that follows is about *how the guarantee is checked*, not about those three routes: **a teardown-completeness guard walks the tree; it never carries a file list**, because a list is only ever as complete as the sweep that wrote it. The division of labour is fixed: the **marker ratchet** (`state.rs::boot_worker_spawns_are_generation_scoped_or_marked`) makes every bare spawn declare a class with a *named* bound, and the **upgrade-shape pin** (`peer_channel_upgrades_are_generation_scoped`) covers the defect that consists of not spawning, its exemptions each naming the mechanism that reaches the connection. Two deliberate rulings sit inside them, both of the form *keep the guard unfoolable*: the marker ratchet does **not** skip `#[cfg(test)]` regions — exempting them requires the guard to decide where a test region ends, and a region detector that over-claims silently exempts production spawns, which is the precise failure it exists to prevent (measured cost of the honest alternative: 10 extra `spawn-ok(test)` markers) — and both guards suppress only comment lines and needles inside string literals, an error that biases toward a false red.

**A cleanup written at the end of a loop is invisible to cancellation, and cancellation is the only teardown path.** The fourth defect the same sweep found was not a spawn site at all: the Nostr worker's NIP-46 bunker drains were bare `JoinHandle`s in a worker-local map, aborted by a loop after the worker's select-loop `break`. That loop is real and reachable — on the channels-closed path. `spawn_scoped` cancels by **dropping** the worker future, so the `break` never runs, the cleanup never executes, and a `JoinHandle` **detaches** rather than aborts on drop: after a rotation the superseded generation's drains kept running beside the successor's, signing with the retired nest key. The invariant that now holds: a generation's drains stop when that generation ends. The remedy is structural — the record owns its abort (`impl Drop for BunkerDrain`), so leaving the map *means* stop draining however the record leaves it — and the general rule is: **a task's shutdown must ride the same event that ends its owner, not a statement placed after the owner's loop.** Where a task holds a handle for its own within-generation reconcile (respawn on roster change, reconnect on a dead connection), owning the abort in the handle's record is the shape; `spawn_scoped` per respawn would leak one supervisor per cycle.

### The rotation statement (wire)

`NestRotation { old_nest_actor_id, new_nest_actor_id, seq, rotated_at }`, canonical DAG-CBOR, detached signatures each over the domain-separation tag **`NEST_ROTATION_V1` = `b"fauna.nest-rotation.v1\0"`** — a new deployment-key signing context, so the tag is mandatory before anything ships (`key-material-hierarchy.md` rule #8 + § Don't do these; registered in `fauna_protocol::sig_domain` in the same change that first signs):

- `old_sig` — by the superseded deployment key. **Mandatory and load-bearing: it *is* the continuity license.**
- `new_sig` — by the successor key. **Mandatory** — possession proof, so a rotation can never point at a key the box doesn't hold (the succession statement's `new_sig` rule, verbatim).

⚠ **This inverts identity-succession's `old_sig` rule deliberately, and the inversion must not be "fixed" toward either precedent.** The user plane refused exactly this shape (`identity-succession.md` § Don't do these — the retired `KeyRotation`: *"a thief holds the old key; that shape is takeover, not recovery"*) **because a strictly stronger factor exists there**: every registered identity has an offline RecoveryKey the thief cannot hold, and anchoring on old-key continuity would displace it. The nest plane has no RecoveryKey analogue, and what it does have differs per Axis-2 row (`security.md` § Transport trust):

- **Public-domain deployments** anchor on **DNS `self=`** — the second factor this plane genuinely has. A resolving client accepts whatever head the zone names; the chain's job on this row is only the propagation window (below).
- **TOFU rows (LAN / self-signed)** have continuity as their *entire* trust model by construction — first-contact-plus-never-changed is all a pin ever asserted. An old-key-signed chain is that same model applied to a change of key, and it is materially stronger than bare key continuity because a nest, unlike a user identity, **has a locator**: clients dial the box the admin controls, so the legitimate chain propagates from the true endpoint to every app that connects, while a thief must hold an active per-victim MITM position to present a competing one — the same position they would need to impersonate the un-rotated nest, now time-bounded by convergence instead of open-ended (§ honest statement below).

**Chain, not statement.** The log serves the full ordered chain (seq 1..head); a consumer walks from the identity it holds to the head, verifying both signatures per hop and strictly-increasing seq. Rotations are deployment-rare; the chain stays trivially small.

### Client acceptance — re-pin on a verified chain

On a channel-binding identity mismatch (pinned ≠ presented), **before** surfacing the identity-changed warning, the client fetches the chain — a pre-identity **`fauna.auth.rotation_chain`** kind over the same connection (anonymous-door discipline from birth: `is_throttled_anonymous_kind` + the pre-identity allowlist, with the allowlist's stale-entry ratchet covering it) — and re-pins **iff both**:

1. a valid chain links its pinned identity to the presented head, and
2. **the live Axis-1 binding it already holds proves possession of that head** — the statement licenses the re-pin; the live binding proves the presenter. A harvested chain alone never moves a pin, so an offline forgery is worthless without an active MITM position at acceptance time.

On acceptance the client stores `(head, seq)` and **refuses every superseded ancestor henceforth** — downgrade protection: the thief's copy of the old key stops working against every converged client, which *is* the eviction. A chain that does not extend the accepted head, or a second distinct head at an accepted seq, is **fork evidence — hard warning naming both heads, no silent path and no re-trust button on that surface** (the succession chain's extend-the-head rule, transposed). No valid chain → today's `IdentityChanged` warning with its explicit re-trust, unchanged. The acceptance slots into the shared pin core (`fauna_client_core::nest_trust`) *before* `LaunchPhase::IdentityChanged` is entered — one place, every app inherits.

**Live-session convergence — bearer eviction rides the rotation decision (ratified 2026-08-13).** Acceptance runs at the graduation entrypoints — bearer mints and launch wrappers — so nothing above guarantees a **live** session ever reaches it: the nest's bearer token store deliberately survives the in-process serving-generation restart (created outside the serve loop precisely so an unrelated restart — the serving-port change — does not sign every device out), and a reconnect that re-authenticates with a held bearer runs no graduation. Measured on the admin journey's first run (2026-08-13): a clean ceremony left the driving app's own pin on the predecessor — within the honest statement's "as clients converge" letter, but the eviction window for a long-running app was **unbounded**, and rotation exists to time-bound exactly that exposure. So the rotate handler **clears the bearer token store** immediately after the committed transaction returns: a bearer is itself a credential minted under the predecessor's authority — under a compromise-driven rotation it is part of what eviction must cover — and the teardown that follows already forces every live session to reconnect, so the cleared store converts that reconnect into 401 → re-mint → graduation → the rotation bridge above. Every live session converges within one reconnect of the rotation, at zero steady-state cost, over the exact client path total box loss already proves. The client requirement is not new: the store is in-memory, so every full process restart — every deploy — already wipes it, and every app class demonstrably recovers (the native supervisor's 401 → clear + re-mint; wasm re-mints on every post-initial reconnect because the browser hides the upgrade status; the Go bridge re-establishes bearer auth on every re-dial; the sync agent re-authenticates before every reconnect) — the rotation was the one identity-relevant restart that did not behave like a restart. Crash-atomicity is structural rather than transactional: the store cannot join the DB transaction, but any tear that loses the clear kills the process and the in-memory store with it, and an upgrade racing the sub-second commit→clear window dies with the generation teardown moments later. Two refused alternatives, argued in place: **not acceptance-at-every-reconnect** — a handshake per reconnect forever, no wasm seam (on web the reconnect path already *is* the mint path), and it leaves predecessor-era bearers valid to TTL; its one distinct virtue, an ordinary-reconnect identity re-check, is defense-in-depth orthogonal to rotation. **Not generation-scoping the token store** — the generation edge also fires on the serving-port change, which must not evict every session on an unrelated admin act; the clear keys on the rotation commit alone. The bulk-byte token store and the challenge stores need no clearing: they are rebuilt per generation inside `start_server` and die with the teardown by construction. The offline outbox rides through untouched: WS-RPC auth is bound at the upgrade, so a queued drain never sees a per-request 401 — a drain in flight at teardown records a transport fault and retries on the next pump pass, over the re-minted connection, converging through the durable idempotency tier (`transport.md` § Idempotency and reconnect-with-resume).

**DNS row and the propagation window.** The ceremony flips the box first; the admin's client then re-publishes the `_fauna.{domain}` TXT `self=` record (the client holds the DNS keys; the nest never writes DNS — `dns-management.md`). A resolver-rooted client still resolving the stale `self=` accepts the chain link stale-root → head for the TTL window; once DNS converges the chain is idle on this row.

**Version skew (additive, within-major).** Old nests never emit a chain — nothing changes for them. Old clients never fetch one — they surface the existing identity-changed warning with its explicit re-trust affordance: degraded (a human judges what the chain would have proven) but recoverable in-app, healing when the app updates. New client + new nest converge silently. The custody `superseded_by` marker (below) rides a catch-all, but ⚠ **not** `UserConfig`'s (the whole record retired with the rail 2026-10-02 — [`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6); on the plane a row with a non-empty entry `extra` is refused — *The kinds*): that one flattened **top-level** `__config` keys only and never covered a key *inside* a `deployment_seeds` entry, so as originally written this sentence was false at code level (any pre-field client dropped the marker, and had been dropping `domain` the same way since it shipped). Made true rather than weakened, 2026-08-12: `DeploymentSeedEntry` carries its **own** `extra` catch-all (§ Version compatibility's mechanism, at entry scope — additive, and an empty flatten map emits no keys, so no existing sealed blob changed). A client older than the catch-all itself still drops the marker — cosmetic (a stale recovery row), never data loss.

### Custody after rotation

The successor entry exists before dispatch (mint rule above); every other roster member converges via the **custody leg** — at its next edge it holds a roster seat and no custody entry for the *new* `nest_actor_id`, so the leg's `deployment_seed.get` + merge fire idempotently (§ The plane-era recovery floor, (c)). The predecessor entry is **marked, never deleted**: `DeploymentSeedEntry.superseded_by: Option<nest_actor_id>` (additive; present-wins in the per-key union merge — the same asymmetry as seed-present-wins), written by the rotating client and by any client that verifies the chain (that second writer is the custody leg's mark reconcile — ruled 2026-09-30 in § The plane-era recovery floor, (c) — which re-derives the mark from the verified chain at every edge the leg runs on, so a mark that failed once is healed at the next edge). **The predecessor is the entry the connection is *bound* to** — `LinkedNestsMachine::bound_nest_id()`, the identity the login pinned (a plaintext loopback nest with no pin proves it by a possession proof over the connection), checked against the box's own `fauna.nest.info` claim and refused on disagreement, never that claim on its own — so a rotation can only ever mark the box it is talking to (owner: [`security.md`](../security.md) § Transport trust). The recovery projections **exclude superseded entries**: re-provisioning a box with a superseded seed would rebuild an identity every converged client now refuses, so the recovery UI must be structurally unable to offer it. The seed bytes are retained — a wrongly-marked entry loses nothing, and unmarking is a client act against the chain.

⚠ **The exclusion is enforced at the resolution point, not per projection** (built 2026-08-12). `recoverable_box_ids` and `selfhosted_recovery_command_for` are *not* the only recovery readers — the re-provision drive (`fauna-onboarding-machine`'s `RecoveryConfigReader`) and both self-hosted-command getters resolve a seed of their own, and the drive is the consumer that would actually rebuild the box on a refused identity. So the resolution-point read itself — today `DeploymentSeedEntry::seed_for` over the folded map, the `UserConfig::deployment_seed_for` form having retired with the whole record 2026-10-02 ([`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)) — returns `None` for a marked entry (a per-projection filter would miss the readers it does not enumerate), and the labelled box list every app renders goes through one shared row projection (`fauna_client_config::recoverable_boxes_in`) rather than each app re-deriving it from the raw map — which is what the native and wasm getters were doing, and what would have left every one of them listing a rotated-away box. The folded map itself deliberately keeps serving superseded entries: the cross-device merge needs them to keep retaining their bytes. Filtering reader-by-reader is completeness-by-enumeration — the same failure mode the ceremony's own KEK-satellite step was bitten by.

⚠ **A resolution-point filter covers reads, not *propagation* — the seed-map fan-out's lesson (built 2026-08-12; the fan-out retired with the plane-era consumer cut).** The fan-out copied the admin's custody map onto each owned box, and a copy that dropped the marker was a live entry again; so propagation was made a **fold, not a fill** — each row joined through the same per-entry lattice the cross-device merge uses (`DeploymentSeedEntry::fold_from` — label join, present-wins supersession, `extra` union). On the plane that lattice is the `fauna.state.deployment-seeds` kind's own merge arm ([`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule → *The kinds*), and no fan-out of this kind exists (§ The plane-era recovery floor, (a)).

**The rotation once also moved the legacy primary mirror forward — retired 2026-09-24.** `UserConfig.deployment_seed` (the pre-map single-seed scalar) was re-pointed at the successor when it named the predecessor, so a pre-map reader was never handed the refused seed. The compat-remnant sweep ([`compat-remnant-sweep.md`](../compat-remnant-sweep.md) § Program 4) removed the scalar with every read of it: no pre-map build exists, so the map entry's supersession marker is the whole mechanism.

### What rotation does and does not do — the honest statement

**Does:** evicts every holder of superseded seeds from the box's *authentication* authority, fleet-wide as clients converge; restores a closed holder set (the current roster); re-roots the nest-internal KEK.

**Does not:**

- **Untell anything.** Content, metadata, and credentials the ex-holder saw while enrolled stay seen.
- **Beat an attacker holding a live MITM position during convergence.** A thief who holds a superseded seed *and* actively interposes on a victim's path before that victim first reaches the real box can present a competing chain and capture that client's pin. That is the same position needed to impersonate the un-rotated nest; the ceremony converts an open-ended exposure into a race the legitimate side starts from the true endpoint — and sealed-at-rest bounds the prize either way (nest impersonation yields the metadata floor, never sealed content). Stated, not solved: on TOFU rows there is no stronger anchor to buy.
- **Rotate anything outside Fauna.** The DNS/registrar credential, the cloud-console account, and a provider-persisted user-data blob carrying an old *injected* seed are the admin's own out-of-band hygiene — the same family as the registrar limit in `admin.md` § the two honest limits.
- **Retract historical artifact signatures.** A deployment-key-signed artifact signed by an ancestor stays verifiable where it predates its hop (the chain vouches). KeyBlobs are no longer such an artifact: since 2026-09-27 the deployment key signs no `KeyBlob` — every one is minted and signed by the author's client (`../key-material-hierarchy.md` § Architectural rules #8) — so a rotation has no live KeyBlob to re-sign. Authentication authority dies at acceptance; artifact history is display-grade continuity — the succession plane's attribution rule, transposed.

**Satellites the build must carry (named here so no slice ships without them):** the KEK re-encryption (in-transaction, step 4); the boot-reconcile rotation-awareness; the nest's own sync writer identity re-derives — its old writer's rows stay inert under per-writer frontiers (additive; `account-data-plane.md`); the account plane's escrow receipts, which the box signs with its deployment key, are re-issued under the successor by each key-holding device, with no fresh generation minted, and a fresh device may still recover through a receipt a verified ancestor signed (ruled 2026-09-30, not built — [`../account-data-taxonomy.md`](../account-data-taxonomy.md) § The generation machinery → *A holder change re-receipts and never mints*; the rotation ceremony was ratified before the generation machinery was built, and this list never named it); federation-peer and backup-destination re-pinning ride the chain **when those trust planes go live** (declared forward obligations — `federation.md` / `backup-restore.md` own their consumers); a rotated **source** box owes the backup plane the same for everything keyed on its own identity (read 2026-09-30, this list never named it) — the writer grant each destination holds for it, a covered folder's mirror set name, and the account plane's per-box destination list, which a device re-files under the successor on a verified chain (the list's rule is built — [`../../behavior/backup-destinations.md`](../../behavior/backup-destinations.md) § State & data shape → *Destination data model*; the grant and the set name are ruled 2026-10-01 and not built — an owner's device, never the destination on a chain the box presents, carries both on the same verified chain: [`../segment-backup-protocol.md`](../segment-backup-protocol.md) § Cross-location backup protocol → *The writer seat*, which also states what a holder of the superseded seed can still do at a destination until the first device carries); both self-hosted installers and the cloud re-provision drive keep injecting whatever seed the custody map serves, which the projection filter restricts to the head.

## The plane-era recovery floor (ruled 2026-09-30; the bind leg built, the reads and the custody leg built and wired — § Implementation status today)

**What this rules.** The custody map's home moves from the `__config` blob to the account plane: the fleet-only, tip-sealed kind `fauna.state.deployment-seeds`, one row per custodied box (row grammar, decode posture and merge rule: [`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule, the kinds table). § Mechanism's *what* is unchanged — which seed is custodied, from which two origins, under which seed→`nest_actor_id` check, and the restore primitive. What changes is where the map rests, how it is read before sign-in, and how a write that cannot land yet stays owed. The blob gave this kind three things the plane does not give by moving the bytes: a copy on every box the admin owns, a read that needs no account runtime, and writers that need none either. Each is ruled below, and no consumer is cut over until all three are built. *(All three are built and every consumer is cut — § Implementation status today; the blob rail itself retired 2026-10-02 — [`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6).)*

**(a) The multi-box floor is the plane's own — no fan-out of this kind.** The promise stands as § Trust & audience states it: reach any surviving box, recover any dead one. Stated exactly, as the blob delivered it: a surviving owned box serves, to a holder of the identity seed alone, the seed of every box custodied by a device that has bound to the surviving box since that custody landed; a box no custodying device has bound to since serves only what it was given. The case it exists for is an admin who loses every device together with the box their account lives on, while another of their boxes survives — the home nest and its devices lost together, the public relay still running ([`deployment-home-with-public-relay.md`](deployment-home-with-public-relay.md)). Without the floor the dead box's identity is unrecoverable there, and with it every ciphertext a restored backup holds under the nest-internal KEK that identity roots (§ The ceremony, step 4). On the plane the floor is a requirement on how a runtime binds to a nest, never a second copy of one kind: **a bind completes the replica** — whenever an account runtime is bound to a nest, that nest ends the first settled pass holding (i) every live row of the account's fleet scope that the device holds and can vouch for, its own or a sibling device's, and (ii) for every generation the device keys, an escrow wrap that nest has receipted under its current identity. The device is the carrier, as it was for the blob. A fresh device holding only the seed then reads the map from that nest with the cold read of (b). The same invariant is what a **rebuilt** box needs (same identity, empty disk: the devices that outlived it make it a replica and an escrow holder again — the replica half of recovery, which the blob never had) and what a **rotated** box needs (same disk, new identity: a receipt signed by a superseded ancestor is not a receipt under the current one). **Refused:** *a plane-level fan-out of this kind alone* — a seed row is unreadable at a second box without a wrap that box holds for the generation sealing it, and wraps and the rows that vouch for a generation are facts of the whole scope, so a one-kind fan-out is the whole invariant built badly; *keeping the blob copy as a named exception to the dissolution* — it keeps `fauna.config.{get,put}`, the whole-record type and the device-local replica alive for one field, the dual home the schedule exists to close, and it leaves the rebuilt and rotated cases unsolved for every other kind; *a ratified degraded floor*, the account's home nest as the only holder — the seed is the one piece § What must be recovered calls irreplaceable, and the case above is an ordinary deployment, not an edge. **The mechanism is the plane's, ruled the same day:** [`../account-sync-plane.md`](../account-sync-plane.md) § The bind leg owns it — what can be asked of the bound nest is asked and what it lacks is pushed, and what a device must remember about a nest is keyed by that nest's replica — with the holder half in [`../account-data-taxonomy.md`](../account-data-taxonomy.md) § The generation machinery → *A holder change re-receipts and never mints*. **Who carries the rows, stated honestly.** The floor is only as real as the flows that bind a row-holding device to a second box, and that was as true of the blob. Read 2026-09-30, an identity's device keeps one nest URL, no app surface re-binds a signed-in identity to another nest, and sign-out erases the device's store; the two-nest journey reaches its second box by clearing the stored nest URL by hand. In the deployment the floor exists for, the devices bind to the home nest and the relay is only linked, so no device carries anything to it. The bind leg keeps the floor where the blob left it and mends the rebuilt box; it does not make the promise true for that deployment. **What does, ruled the same day and not required for the cut:** a nest the user has linked is a secondary replica that their own devices complete over a second connection, without ever binding to it — [`../account-sync-plane.md`](../account-sync-plane.md) § The bind leg, ruling 4, with the capability in [`private-mode.md`](private-mode.md) § The account-plane replica. With (c)'s custody leg running over the same connections, an admin who links their boxes custodies every one of them and every linked box can serve the map. Nest-to-nest replication was weighed for this and refused there.

**(b) The reads — three sources, one resolver, and a read never waits for the runtime.** Every recovery read runs where no account runtime exists: the onboarding wizard's box list and self-hosted command, the re-provision drive's `RecoveryConfigReader`, and the launch-retry entry. So the map has three readers, all shared Rust in the plane's door crate, and the existing getters keep their names and signatures over them — no app's recovery screen changes shape. **The handle** (signed in, store ready): `AccountStoreHandle::deployment_seeds`. **The local read** (this device's own account store, no runtime, no nest): rows rest opened in the local store ([`../account-replica-posture.md`](../account-replica-posture.md) § Local at-rest posture), so the read needs the actor and the store's location and nothing else — no generation key, no seed, no engine election; it answers empty for a store that does not exist and never creates one, and it is safe beside a process that hosts the engine. It replaced the device-local `__config` replica, retired with the rail 2026-10-02 ([`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6)). **The cold read** (a reachable nest, a device with no store for the account): given an owner-authenticated connection and the identity seed, it walks the fleet scope into a throwaway in-memory replica, asks the nest once for every escrow wrap it holds for the account, opens each with the seed-derived escrow secret against the mints it walked ([`../account-data-taxonomy.md`](../account-data-taxonomy.md) § The generation machinery → *Escrow recovery* owns who may open a wrap and how), and folds the kind. It needs no escrow receipt: a receipt bounds what a recurring pass may ask for, and this is one reader asking once — so it works at a rebuilt or a rotated box whatever the receipts in merged state say. **It writes nothing** — no enrollment, no device-set row, no escrow target, no mint, no put. A read that joined the fleet would leave a phantom device behind every abandoned recovery, which is why the full runtime, which enrolls inside its readiness barrier, is the wrong tool. Reading without the fleet's admissibility checks is safe for this kind because its rows certify themselves: a row must name its key's box and carry a seed that derives to that box's id (the plane's strict decode), so nobody who lacks a box's seed can forge or mark that box's row, and every unwrap still checks the mint's key commitment. **The resolver:** a surface that runs before sign-in reads **the local read joined with the cold read** — the local read always, the cold read whenever a nest URL resolves and answers — through the kind's own lattice (`DeploymentSeedEntry::merge_seed_map`); a failure of either source leaves the other. **Never either-or on whether a nest URL is stored:** a surviving device's stored nest is, in the case recovery exists for, the dead box. A signed-in surface reads the handle, and before store-ready the local read. The projections every surface renders through (`recoverable_boxes`, the self-hosted command, the resolution-point read that excludes a superseded entry — § Custody after rotation) take the folded map. On web both pre-login readers link into the onboarding chunk, as the blob-era reader did, so the seed stays inside Rust; no runtime exists there for the account port to reach.

**(c) The writes — every owed write is a reconcile; nothing is parked, and nothing is written at claim time.** A custody write goes through the plane door, which exists only once the account runtime is assembled and which refuses while no generation tip resolves; today every writer runs before that, holding the seed in memory only. Parking the seed on disk until the door opens was weighed and refused: the one durable store that exists before the runtime is the account registry, which on web is script-readable `localStorage`, and a park is needed only for a fact that cannot be re-derived — none of these is such a fact. **Capture is a reconcile — the custody leg.** One shared function, run whenever a session has both an authenticated connection and the account-store handle: at whichever of the post-auth edge and the store-ready edge lands second (the edges that also run the ledger's post-store-ready pass — [`../../behavior/succession-aftermath.md`](../../behavior/succession-aftermath.md) § Re-key scope), and at every later post-auth edge. It resolves the bound nest's id; if the fold holds a live entry for it, it is done, with no round trip; otherwise it asks whether this identity is an admin (fail-closed), fetches the seed over `fauna.admin.deployment_seed.get`, refuses one that does not derive to the bound id, resolves the box's domain, and merges the entry. This is the co-admin self-heal of § Mechanism, re-pointed at the plane, and it becomes the **only** capture: the claim reply's seed is no longer consumed. The hand-off was single-use, held in memory, and ahead of the door on every host, so a crash lost it and a reconcile was needed regardless; and the box serves the same ground truth to its admin for as long as it lives. With it go the onboarding machine's captured-seed channel, every host's latch, and the capture-path transit of the seed through foreign code (§ Trust & audience — that accepted exposure is removed, not re-accepted). The reply field itself stays on the wire, populated and unread: removing it is a wire change for [`../version-compatibility.md`](../version-compatibility.md) to schedule, not part of this ruling. The bar the claim-path write met stays — a bounded transient retry, and a user-visible warning when a run ends with custody unconfirmed for an admin of the bound nest — and gains a retry at the next edge, which the one-shot write never had. **The leg also runs over each linked nest's connection (ruled 2026-09-30).** Capture as ruled above reaches only the box a device is bound to, and a device binds to one. Where the runtime holds a second connection to a nest the user has linked ([`../account-sync-plane.md`](../account-sync-plane.md) § The bind leg, ruling 4), the same steps run against it — that connection's bound id, the admin check there, the fetch there, the seed→id refusal against that id — and the mark reconcile likewise. **The window, stated:** a box lost between its claim and the first merge that lands is not custodied — seconds on a healthy path, and the blob's capture needed the same box for its own write. **The seed-map fan-out retires** with the blob: (a) replaces it, and the device's own store replaces its replica. **Rotation keeps custody-before-dispatch, literally.** The drive (§ The ceremony) takes the handle and refuses plainly without one. It merges the successor's entry, waits until that row is published to the bound nest, and only then dispatches; a door refusal or a publication that does not arrive aborts before dispatch, leaving at worst the orphan entry the ceremony already tolerates. **The supersession mark is a reconcile too.** The drive still writes it after the dispatch, and the custody leg re-derives it: when the fold holds a live entry for any id other than the bound one, the leg fetches the bound nest's rotation chain, verifies it to the bound head, and marks every custodied ancestor the chain names with its successor. That is what makes § Custody after rotation's "any client that verifies the chain" true, and a mark that failed once stops being a permanent caveat.

## Trust & audience

The custodied seed is owner-only — a row of the fleet-only account-state plane kind `fauna.state.deployment-seeds`, sealed under the account's generation key (§ Mechanism) — and readable only by the admin's own devices; the admin already controls the nest, so off-box custody adds no trust boundary. It is uniform on every nest — the box *also* keeps the seed on its own disk (implementation today; the on-disk identity wins after first boot), but the **recovery** copy is always the client's. *(This sentence was once qualified "across storage modes" — that axis is retired (`storage-modes.md`); seed custody never varied with it.)* The seed is therefore only as recoverable as the admin's **own identity seed**: if the admin loses every device *and* kept no identity-seed backup, the nest identity is unrecoverable — the same backstop that governs all owner-only key material (identity-seed recovery — QR import / recovery phrase — is owned by `onboarding.md` / `devices.md`, not re-solved here).

**Cloud-init user-data exposure of the seed — ACCEPTED (user decision, 2026-06-30).** On the client-provisioned cloud path the seed is rendered into the cloud-init compose `environment:` block (`build_cloud_init`), submitted as VPS **user-data** — which is IMDS-readable by non-root on-box processes *and* persisted in the provider's user-data store **beyond the box's life** (a step past "keys on the box's disk"). This is **accepted as-is**, not redesigned, because the cloud provider is already inside the cloud-box trust boundary (a cloud-hosted box's `nest_deployment.key` lives on the provider's disk regardless of who minted the seed — § Mechanism, client-provisioned cloud VPS), and because the same permanent seed must reach the box at provision *somehow*; the self-hosted installer `.env` (root-owned, `0600`) is in fact a **narrower** exposure than user-data. **Recommended hardening (orchestrator, non-blocking):** require IMDSv2 (token-gated metadata) so a blind-SSRF can't read user-data, and scrub the user-data blob after first boot where the provider API supports it. The post-boot container-env exposure (`docker inspect`, root/docker-group-visible) is the same accepted class. *(The seed is inert after first boot — the on-disk identity wins; § Implementation status, step-1 nest-side.)* **A future redesign to post-boot seed delivery over the authenticated admin channel** (the rejected option (b)) **would remove the provider-metadata persistence** and is the natural hardening if a provider ever lands outside the trust boundary — captured here, not scheduled.

**Capture-path foreign-string transit of the seed — ACCEPTED while it existed, ENDED by the plane-era consumer cut.** *(The custody leg fetches and merges the seed inside Rust, and the claim reply's seed is no longer consumed, so no seed crosses into foreign code on the capture path and nothing below is re-accepted — § The plane-era recovery floor, (c). Kept as the record of why the transit was accepted while it existed; the deprecated UniFFI no-op wrappers that once remained for the apple glue are deleted, 2026-10-02.)* On the claim-capture path the seed transits foreign code as a plain hex string: web round-trips it WASM→JS→WASM (`capturedDeploymentSeed()` in `fauna-wasm-onboarding` → the onboarding glue → `fauna-wasm`'s `captureDeploymentSeed(secretHex, seedHex)` — the two cdylibs are separate wasm runtimes, so no Rust value can cross between them), and the three UniFFI apps (windows/apple/android) hand it across the binding twice (`captured_deployment_seed()` out, `capture_deployment_seed(owner_secret, seed_hex)` back in); linux and tui consume the machine getter in-Rust — no foreign transit. This is **accepted as-is**, not scheduled for redesign, on three grounds. **(1) Zero marginal exposure:** every such crossing already carries the admin's **identity secret** in the same call (`secretHex`/`owner_secret` — the foreign layer owns credential storage, so that parameter cannot be removed), web additionally persists that secret in script-reachable `localStorage` by architecture (`apps/web.md` § localStorage Keys), and `BackupKey` — derived from that secret (`owner-key-material.md` § Path A) — unseals the whole `__config`, custody map included. An attacker positioned to read the seed at this boundary therefore already holds the strictly stronger secret; the seed's confidentiality is bounded by the identity secret's wherever the transit exists. **(2) The redesign risks the property that matters:** the capture is the single-use claim hand-off whose failure is a *silent* loss of recovery. Keeping the write inside `fauna-wasm-onboarding` would force it to mint its own bearer (as the recovery reader does) — a new connect+auth failure surface on the one write the admin cannot retry, traded for a confidentiality gain of zero by (1). **(3) The read-side asymmetry is architectural, not an inconsistency:** the recovery-mode reader (`WasmRecoveryConfigReader`, § Mechanism notes) keeps the seed in-Rust because at recovery time there is no authed `fauna-wasm` session to reuse — its bearer mint was necessary, and in-Rust custody was free; at capture time the authed session exists, and reusing it is the durable choice. Same rule both ways: never add a connect+auth surface a path doesn't already need. **Revisit trigger:** if web's identity secret ever moves out of script-reachable storage (non-extractable key custody), ground (1) no longer holds for web and this acceptance must be revisited — captured here, not scheduled.

**Scope: one identity MAY administer many nests (BR-1 = YES, user decision 2026-06-29; IMPLEMENTED).** Custody is a **per-`nest_actor_id` map**, not a single scalar: one `DeploymentSeedEntry { nest_actor_id, seed, domain, superseded_by }` (`libs/fauna-core/src/data.rs`) per administered box, keyed by the box's `nest_actor_id` (= `ed25519(seed).public`), each resting as a row of the account-state plane kind `fauna.state.deployment-seeds` ([`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule → *The kinds*). The `domain: Option<String>` is the box's **own handle domain** (server_name / DNS zone) — the human label for the `recover-box-item` row and the cloud re-provision input (step-4 leg 3). It cannot be derived from the admin actor (in the multi-nest case the admin's *handle* domain need not equal a non-primary box's domain), so it is captured **from the box itself**: the custody leg best-effort resolves the connected box's `fauna.nest.info` `domain` (`resolve_box_domain`), `None` for a **domainless** box (nest.info `domain == "unknown"`/empty — the real home-relay case, which is why `domain` is `Option`, not `String`). The per-key union merge keeps a non-`None` domain from either device. The custody leg **custodies every nest** an admin identity administers (§ The plane-era recovery floor, (c)): a *different* box's seed is added to the map (`DeploymentSeedCustody::Captured`), not refused — so an admin running several nests backs up *all* of their recovery seeds; a box already custodied makes no round trip (`AlreadyCustodied`). Read via `DeploymentSeedEntry::seed_for` / `domain_for` over the folded map. *(History: until the rail retired on 2026-10-02 the map was the `deployment_seeds` field of the whole-record `UserConfig` in the `__config` blob, written by the claim-time `ConfigClient::capture_deployment_seed` — [`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6).)*

**⚠ Correction (2026-07-02) — the map is a data structure, but it is SILOED PER-NEST.** *(History: the per-nest `__config` silo and the fan-out that answered it both retired — the multi-box floor is the plane's own, § The plane-era recovery floor, (a); the rail retired 2026-10-02, [`../config-dissolution.md`](../config-dissolution.md) § The `__config` dissolution schedule → *The closure order*, step (6).)* The per-`nest_actor_id` map IS implemented, but each box's seed is captured only into *that box's own* `__config`: `capture_deployment_seed` is BR-2-gated to the **connected** nest, and `__config` is **per-nest with no inter-nest replication** (no `config` pairing capability — `reserved-folders.md` § UserConfig Sync; `private-mode.md`). So a *different reachable* box's config does **not** hold the dead box's seed, and the BR-1 promise "reach any surviving box, recover any dead one from the synced map that holds every box's seed" (§ Recovery UI step 4) is **not yet delivered by the capture path**. ## What this explicitly is not

No SSH, no shell, no `docker logs … fauna:secret:` "recovery command", no hand-saved value. The retired `setup-complete-recovery-command` UI element and the `installers/vps.md` Step-5 completion-screen recovery box (which described that SSH path — a path with no working restore consumer) are removed; recovery is wholly client-driven, consistent with the no-off-box-fix principle of `nest/common.md` § Client-state recoverability. *(Total box loss is itself a hardware/infrastructure disaster, not a **client-causable** state, so it sits outside the strict § Client-state recoverability invariant — but it inherits that invariant's principle: recovery is client-driven, never off-box.)*

### Single-identity unification (decision 2026-06-29; IMPLEMENTED in code)

✅ **The nest now has ONE Ed25519 identity — the deployment key.** Until this landed, the nest carried TWO independent identities and only one was custodied: the **deployment key** (`nest_deployment.key` ↔ DB `nest_keypair` → `nest_signing_key`) — the channel-binding `nest_actor_id` clients TOFU-pin + the claim hand-off seed this feature custodies — and a *separate*, independently-random **`nest_identity.key`** that `fauna.nest.info` returned (`discovery_core.rs`) and that served as the identity for federation, the backup-destination pubkey, multi-nest pairing, and the nest's own sync `device_id`/`service_id`. The two were minted a day apart in March 2026 for different features and never reconciled (historical accident, not design). So a recovered box kept the identity clients pin (they reconnect ✓) but would have presented a **new** identity to federation/backup/pairing/sync — those were **not custodied**.

**Decision (user, 2026-06-29): UNIFY to one nest identity (the deployment key).** Federation/backup/pairing are not live in alpha, so changing `fauna.nest.info`'s `nest_id` breaks no established relationship. **`nest_identity.key` is retired:** `NestIdentity` is now a *view* over the reconciled deployment key — `start_server` derives it from the loaded `nest_signing_key` via `NestIdentity::from_seed` (`bins/fauna-nest/src/nest_identity.rs`, `lib.rs`), so nest.info/federation/backup/pairing/sync all key off the single, custodied deployment seed → the one custodied seed restores the **whole** nest identity. Both boot paths reconcile the durable deployment key before `start_server` (standalone `main.rs`; embedded `desktop_serve.rs` now reconciles too), and `factory_reset` preserves the deployment identity via `nest_deployment.key` (the retired `nest_identity.key` is gone). **Safety (encryption root):** `nostr/key_crypto.rs` (via `nostr/bridge_provider.rs` and every other nostr call site — `bridge_leg.rs`, `store.rs`, `sync_worker.rs`, `mod.rs`, `relay_endpoint.rs`) is the one place a key is *encrypted* under the nest identity: `encrypt_nostr_privkey`/`decrypt_nostr_privkey` derive a symmetric AEAD key via `BLAKE3::derive_key(context = "fauna nostr key encryption 2026-03-19", key_material = nest_signing_key_bytes)` (`key-material-hierarchy.md` § Nest-internal key-encryption key). This is safe regardless of shipped status — it is the same domain-separated-KDF pattern the architecture already uses for the user's own primary root (`BackupKey`, Path A, itself `BLAKE3::derive_key` off the identity seed with its own distinct context string — `owner-key-material.md` § Path A; `key-material-hierarchy.md` § Architectural rules #3, § Don't do these), and it never signs, so it adds no context to the deployment key's signing surface (rule #8's six-context enumeration — the deployment-seed rotation statement (F) joined it 2026-08-12, this bullet's own § Deployment-seed rotation below — is unaffected — every nostr use of `nest_signing_key`/`nest_identity.signing_key` routes through this encrypt/decrypt pair, none calls `.sign(...)`). **`nostr` shipped to production 2026-07-16** (`--features bluesky,nostr`, user-approved — `../installers/docker.md` § Feature flags); the 2026-06-29 unification review (tracked internally) independently reached this "key-encryption, not signing, no cross-protocol signing surface" conclusion even before shipping, so no new review is owed by the flag flip. **`activitypub` shipped to production the same day** (`--features bluesky,nostr,activitypub` — `../installers/docker.md` § Feature flags), with zero enabled accounts at ship time.
