## The convention — convention 9 (== point 9)

9. **The harness is self-terminating (ratified 2026-07-14, after the 10 h wedge incident).** Nothing supervising the run is a safety net — a runner can be interrupted or killed at arbitrary times, so the harness itself bounds every wait and reaps every child; wedge states are made unrepresentable, not manually reapable (the [`nest/common.md`](nest/common.md) § Client-state recoverability spirit, applied to the harness). **A corollary with teeth, learned the hard way on iOS (2026-09-22): a bounded wait is only as good as the PRECONDITION it waits for, and a diagnosis printed in an error message is a load-bearing claim that ages like any other.** `IosInProcessDriver._ensure_booted` waited for `simctl list devices` to say `Booted` — which is the start of a simulator's boot, not the end of it: measured, `Booted` at **1.1 s** and `simctl bootstatus -b` finished at **513 s**, a 512-second window in which the device is up in name while installd and FrontBoard are not answering. Every bound downstream was correctly set and every one of them was then spent waiting on a device that had simply never been asked to finish (`terminate` 120 s + `uninstall` 120 s + `install` 300 s ≈ the whole 9-minute failure), and because the boot completed while the first test was failing, only ever the FIRST test of an invocation died — so the harness's own timeout message came to assert *"the simulator is wedged, not slow"* and to name the machine-wide `simctl shutdown all` as the cure. It was neither wedged nor slow, and that cure would have dropped another run's simulator, breaching this very point's process-safety rule to fix a problem that did not exist. Three rules follow. **(a)** Wait for the *completion* signal the platform actually offers (`bootstatus -b`), never a status word that a state machine passes through on its way up; where one spelling of "ready" exists, a second, weaker one beside it IS the defect. **(b)** Such a wait is a build-class cost, so convention 10's hoist applies to it: `conftest._get_ios_setup` starts the boot before the app build and collects it after, and `_prebuild_binaries` runs the whole thing at collection time, keeping a legitimately multi-minute boot out of a test's own 900 s budget. **(c)** When a failure's own message names a cause, verify it before building on it — a capture that inherits the message's diagnosis inherits its error. Pinned tier_1, with no simulator, by `tests/e2e-unified/tests/test_ios_boot_completion.py`. Six mechanisms, each with a red-on-regression proof — the first five in `tests/e2e-unified/tests/test_harness_self_termination.py`, the sixth beside its code:
   - **Every test is bounded — but HOW a wedge is reported is platform-split, and the split is load-bearing.** pytest-timeout enforces `timeout = 900` per test phase (`pytest.ini`), and conftest **refuses to run** when the plugin is missing rather than silently reverting to unbounded. On POSIX the `signal` method raises inside the hung test, so it dies as an ordinary failure and the session — summary and counts included — carries on. **Windows has no `SIGALRM`**, so the plugin falls to its `thread` method: it dumps every thread's stack and then `os._exit`s the process, ending the run at `+++ Timeout +++` with no summary, no counts, and **no traceback for any test that had already failed**. So "a wedged test dies as a normal failure" is a POSIX-only half of this bullet; on windows the diagnosis is carried instead by convention 7's live-reason line, which is exactly why that rider covers FAILEDs and not only ERRORs. Both halves are asserted rather than skipped (`tests/test_harness_self_termination.py` § 2) — the POSIX-only skip that used to hide the windows half was itself how two failures went permanently unattributable. Suites with a documented longer budget override with an explicit `@pytest.mark.timeout` (`tests/live/` 5400s; `tests/platform/docker/`, `version_skew`, `live_box` 3600s) — bounded always, unbounded never, and no *default* exceeds 15 min.
   - **The web browser is Playwright's bundled Chromium on every machine** (`drivers/browser.py`: explicit `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` → bundled → system fallback). Decision 2026-07-14: the snap Chromium and its machine-wide serialization flock (`drivers/chromium_lock.py`) are **retired** — the snap's per-machine ProcessSingleton was the root constraint behind the wedge class (silent flock queueing, same-process self-deadlock, an orphan browser wedging the next run), and the flock existed only because `playwright install chromium` was refused on ubuntu26.04-arm64, which an install-time `PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu24.04-arm64` resolves (the per-machine setup notes carry the exact command; verified: two concurrent bundled instances coexist). Concurrent browser runs — sibling sessions' web lanes, a tier_4 docker smoke beside a `--app web` run, a second same-process driver — are safe by construction, with nothing to serialize.
   - **Every harness child dies with its run.** Harness-spawned processes (web bridge, nest, mail bridge, xvfb + desktop app) are process-group leaders with Linux `PR_SET_PDEATHSIG` armed and their new process group registered with this run's pipe-EOF reaper — darwin's equivalent, since it has no parent-death signal at all (both inside `drivers/port_util.popen_group_kwargs`) and are torn down group-wide (`terminate_tree`: TERM → wait → KILL sweep); the web bridge forwards SIGTERM/SIGINT to its own group so the playwright node + Chromium subtree dies with it. Net guarantee: `kill -9` of pytest reaps the whole tree with **no cleanup code running** (kernel-delivered). Reapers only ever signal process groups this run created — never a pid discovered by name (process safety). **Windows has no process group to kill, so it gets the equivalent mechanism, not a weaker one** (2026-07-24): `port_util.reap_descendants_of(pid)` binds a launch **and every descendant it later spawns** to a `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` job object, which the kernel closes when the run dies for any reason — the same no-cleanup-code-required guarantee PDEATHSIG gives on Linux. `terminate_tree` reaches only the process it was handed, so before this a **grandchild** simply outlived the run: fauna-tui spawns `fauna-sync-agent`, a process *built* to outlive the app that started it (right in production, an orphan in a test), and the orphan then answered the next launch's pipe and held its own `.exe` against the next compile — found on the first windows run of the tui agent leg, 2026-07-24. Pinned by `test_job_object_reaps_a_grandchild_of_a_killed_spawner` (mutation-verified: disarming the flag turns it RED); the POSIX skip in that file is per-test rather than file-wide precisely so the platform whose orphans are hardest to see still runs its own proof. `drivers/tui.py` adopted it first (2026-07-24); **every remaining harness spawn site followed 2026-08-02** — the nest (`tests/common/nest.py::_spawn_and_wait`), the web bridge (`drivers/web.py`, whose playwright-node + Chromium subtree is precisely the grandchild case), and the mail bridge's three spawn/respawn sites in `conftest.py` (the respawn re-arms, because a job binds a *pid* and a rebind is a new process). The spawners still arming only `popen_group_kwargs()` are POSIX-only by construction — the linux app driver, `dbus-daemon`, the fake tray watcher — and are listed with their reasons in `test_every_spawn_site_arms_the_windows_half_too`, which fails on any new site that arms only the POSIX half **and** on a stale exemption. **The generalizable lesson, and the reason that structural test exists rather than just the four fixes: a mechanism armed by a SEPARATE call after the spawn will be forgotten.** The POSIX half rides *inside* `Popen(**popen_group_kwargs())` and so cannot be omitted; the Windows half is a second statement, and was in fact omitted at four of the five sites for the eight days after tui adopted it — invisible everywhere except a run on windows. What made the nest's instance expensive was blast radius, not the orphan itself: the leaked nest held its own pinned `fauna-nest-e2e-<hash>.exe` open, and because that name is deterministic per (features, profile), the NEXT run's `shutil.copy2` in `build_node` failed with `[WinError 32] … used by another process`, attributed to the `nest_binary` fixture — so a *failing* run silently armed the *following* run's failure, and the second failure presented as a build break in a tree that builds fine (cost a full ~13-minute run to identify, 2026-08-02). Pinned by `test_nest_spawn_dies_with_a_killed_run`, which drives the real `_spawn_and_wait` against a stub HTTP "nest" so the proof is a seconds-long process-lifetime question with no build in it. **The web bridge was leaking the same way**, and its fix is mutation-verified (disarming the call leaves the bridge alive after its run is `TerminateProcess`'d) and pinned end-to-end by `test_reap_drill_killed_pytest_leaves_no_orphans_win` — the Windows twin of the 3c reap drill, where a child pytest launches a real bridge + Chromium, is killed with no cleanup code, and the job must take the entire browser subtree; it also confirms that binding the bridge does not disturb Chromium's own sandbox job objects. Writing that twin **enabled the web lane on windows in this file** (2026-08-02): `test_second_web_driver_in_one_process_is_safe` had carried the blanket POSIX skip even though its subject is a *browser* singleton and the snap-Chromium constraint it replaced never existed off Linux — a stale skip which left the only test exercising the web-bridge spawn path unrun on the very platform whose orphans this section is about (point 7: a skip is not coverage). The file now runs 10 proofs on windows, up from 8. **A driver that hand-rolls its teardown silently opts out of all of this, and that is how the macOS seat orphaned `fauna-sync-agent` for months (found + fixed 2026-07-29).** `drivers/macos.py` and `drivers/tui.py` each open-coded "group TERM → wait → `proc.kill()`" instead of calling `terminate_tree`, which leaks the agent two ways: the `os.getpgid(pid)` call sat *inside* the `except ProcessLookupError` that was meant to tolerate an already-dead app, so once the app had exited and been reaped (the driver's own health-loop `poll()` does that) **no signal was sent at all**; and the escalation was a single-process `proc.kill()` rather than a group SIGKILL sweep, so a TERM-ignoring grandchild survived too. Two lessons generalize. **(a) Folklore about *why* a process survived is worth re-measuring:** this orphan was recorded for five days as "the agent ignores SIGTERM", which is false — the agent registers only `tokio::signal::ctrl_c` (SIGINT), so SIGTERM keeps its default disposition and kills it; it never *received* one. **(b) A backstop can hide a missing mechanism from the platform that has one.** `drivers/tui.py` had the identical hole yet reaped correctly, because a pty child is a session leader and the kernel SIGHUPs the foreground group when it exits — so the *pty*, not the teardown, was doing the work. macOS's plain-`Popen` launch has no such backstop and orphaned immediately. The tui gap is real but only observable with a grandchild that ignores SIGTERM **and** SIGHUP, which is ordinary `nohup`-style daemon behaviour and one disposition away for a process built to outlive its parent. Both drivers now call `terminate_tree`; pinned by `test_macos_teardown_reaps_the_agent_when_the_app_already_exited`, `test_macos_teardown_reaps_a_term_ignoring_agent`, and `test_tui_teardown_reaps_a_term_ignoring_agent`, all red-verified against the hand-rolled shape. The same file's `_pids_in_group` also read Linux `/proc` unconditionally, so **every proof in it errored on darwin** — the platform with no PDEATHSIG, i.e. the weakest reaping story, was the one never running its own proofs; it now falls back to `ps` off Linux. **The DETECTOR itself had the same shape of hole, closed 2026-08-14: `test_every_spawn_site_arms_the_windows_half_too` opens a file only if it already contains `popen_group_kwargs(`, so it catches "armed the POSIX half, forgot the Windows half" and is structurally blind to "armed NEITHER half".** A spawn site that never learned the convention was invisible; only one that half-learned it was caught — which is how `drivers/windows.py` sat unarmed indefinitely under a green pin (found 2026-08-05). The blindness was not only per-file: an AST census of all 115 spawn call sites found `conftest.py` holding three armed spawns **and one unarmed one** (the `just <recipe>` build spawn), so the pin opened that file, passed it on the armed sites, and never saw the other — the bug class hiding inside a file the detector considered covered. Seven infrastructure sites were unarmed (the AP nest, the windows sync agent and CalDAV nest, the android instrumentation client, that build spawn) and two more wore a **weaker shape that looks armed**: a bare `start_new_session=True` is the same setsid *without* `PR_SET_PDEATHSIG`, and `track_process()` only registers an atexit teardown a SIGKILL never runs, so `drivers/macos.py` and `drivers/posix_pty.py` had no guarantee at all when it mattered. All are now on the shared `popen_group_kwargs()` spelling. The second detector, `spawn-arming-ratchet-check` (a dedicated dev-fleet checker, cheap merge tier), is deliberately split by surface: **infrastructure** (`conftest.py`, `drivers/`, `helpers/`) is an **absolute** gate with no baseline, since its debt was measured to zero; **test files** are a **down-only ratchet** over 99 grandfathered sites, because most are genuinely short-lived children (18 of them are `test_build_slot.py`'s own tests of the slot mechanism) where a blanket widening would go loudly red for no safety gain. Red-verified by the discriminating mutant: disarming the AP nest spawn *including its import* — so the file contains no `popen_group_kwargs(` at all — leaves the original pin reporting **1 passed** while the new gate fails naming `helpers/ap_nest.py`. Also `bins/`-adjacent cleanup in the same pass: `tests/e2e-unified/bridges/process_manager.py` was an unarmed nest spawner with **zero consumers** since it was added four months earlier, deleted rather than armed — arming dead code would have made the exemption list lie. The generalizable lesson is one level up from the bullet above: **a detector keyed on the presence of a half-applied convention can only find half-adopters.** Key it on the *spawn*, which is the thing that actually exists, and let the exemption list carry the judgment. **And macOS had NEITHER half, for months and invisibly (found + closed 2026-08-22).** darwin has no `PR_SET_PDEATHSIG` and no job objects, so `popen_group_kwargs()` there was a bare `os.setsid()`: every mac harness child was held only by `terminate_tree`/atexit — cleanup code, which is precisely what a SIGKILLed pytest never runs. The cost was measured twice in one day on macOS: an e2e trio (the `FaunaMacOS` app, its `fauna-sync-agent` child, and a `fauna-nest-e2e` instance) outlived its pytest by 4h31m, and an independent recurrence hours later found **five** orphans from a single still-live checkout — two nests, two `fauna-mail-bridge` processes and an app — all reparented to PID 1, ages 4–7 h, holding two ports and ~375 MB while the session that spawned them kept adding more. **The rule the Windows case set applies unchanged: the platform without the primitive gets the equivalent mechanism, not a weaker one.** darwin's equivalent is **pipe EOF** — a pipe's last writer closing is kernel-delivered whether or not any cleanup code runs. `port_util._start_reaper()` starts ONE helper per run holding the read end of a pipe whose only writer is the pytest interpreter, and every child registers its own new pgid on that pipe **from inside `preexec_fn`** — so the arming rides within `Popen(**popen_group_kwargs())` and cannot be forgotten, the same property that makes the POSIX half unskippable and that the separate-call Windows half kept losing at four of five sites. On EOF the reaper sweeps every registered group TERM → wait → KILL; on a *clean* interpreter exit the atexit hook sends `BYE` first and the reaper exits **without signalling**, because a bare pgid number is indistinguishable from one the OS has since recycled, and firing on a recycled group could reach a sibling session's run (process safety). **It is armed on every POSIX platform, Linux included, deliberately:** this same section records darwin as "the platform with no PDEATHSIG, i.e. the weakest reaping story, [and] the one never running its own proofs" — a mechanism that executes only on the machine that needs it is a mechanism that rots, so the Linux dev machines' runs red-verify macOS's guarantee on every run. Pinned by `test_parent_reaper_kills_every_registered_group_when_the_spawner_is_sigkilled` (two armed groups, each holding a **SIGTERM-ignoring grandchild** — the shape that discriminates, since PDEATHSIG only ever signals the direct child and leaves such a grandchild alive on Linux too, and the shape the incident actually had: the sync agent is the *app's* child, the bridge's workers are the *bridge's*) and `test_parent_reaper_signals_nothing_after_a_clean_exit` (the recycled-pgid guard, asserted against the reaper's own **exit** as the causal barrier rather than a settle-sleep, point 14). Both are red-verified against discriminating mutants: dropping the registration write leaves both groups alive; suppressing `BYE` kills a group on a clean exit. The same change retired `test_nest_spawn_dies_with_a_killed_run`'s darwin skip, whose stated reason — "a declared platform gap there (testing.md § 9)" — **was never declared in any goal doc**: undeclared code drift wearing a citation, which is how a ratified guarantee goes unenforced on one platform without anyone reading a contradiction. That test now runs and passes on macOS unchanged. A **container** is the one child the kernel cannot reap with the group; the nest-mode axis's docker provider reaps those by label instead — owner [`testing.md`](testing.md) § Default app and nest mode, ruling (4) of the N-nests design.
   - **A machine-wide lock wait is loud and bounded.** Every machine-wide lock prints its holder(s) — pid + cwd (+ command) — immediately and once a minute, and fails the acquiring run with that diagnosis after a bound, so "slow sibling" and "wedged sibling" are distinguishable and nothing ever sleeps forever. Three locks exist: `helpers/live_box_lock.py` (serializing destructive tests against a shared live box; default bound 1800s, `FAUNA_E2E_LIVE_BOX_LOCK_TIMEOUT`) and the machine-wide **e2e slot pool** (a dedicated dev-fleet slot manager, acquired by conftest for any run selecting a tier_2/3/4 test, so N sessions' full e2e runs queue — 2 slots — instead of thrashing the shared machine; default bound 7200s, `FAUNA_SLOT_TIMEOUT`). Kernel flock in both — a crashed holder auto-releases. The third is the **windows physical-input mutex** (2026-08-01, `flaui-bridge/Actions.cs::_inputMutex`), and it is deliberately shaped differently from the other two: a named Win32 mutex held *inside the C# bridge* — not python — for a whole keyboard **ceremony**, session-scoped (`Local\`) because foreground ownership and `SendInput` are themselves per-session, so a `Global\` name would over-serialize sessions that cannot interfere. **The critical section is every operation that can move the foreground, not just the injection** (`Actions.cs::FocusThenInject`): UIA `SetFocus` *activates the containing window*, so focus, the focus-landing click and the keystrokes are one section. The mutex first shipped guarding only `ForegroundApp()`+`SendInput`, which does not work — a sibling still **blocked on the mutex** steals the foreground with an unlocked `el.Focus()` and collects the holder's keystrokes. That is measured, not reasoned: `tests/test_flaui_input_lock_windows.py` drives two bridges into a deterministic overlap (one holds the section open while the other is fired into it) and reads back each app's own text field; with the narrow boundary app A received nothing and app B received `'aaaaaaaaaabbbbbbbbbb'`, with the ceremony-wide boundary each app receives exactly its own text. The test stays honest by construction: `FAUNA_E2E_INPUT_LOCK=off` re-runs the same interleaving unserialized and is green only if the sibling's keystrokes really do land in the wrong app, so a lock that stopped working cannot present as a passing test. **Why it must exist:** `SendPhysicalInput`'s error-5 retry only covers a sibling stealing foreground from *us*; the damaging inverse is that when we *win* the foreground race, a sibling's in-flight `Keyboard.Type` lands in **our** app — a keystroke no process in this run sent, e.g. an ESC that closes a `ContentDialog` with its confirm handler never run, so the ceremony silently no-ops (modal closed, no RPC, no error) and is indistinguishable from a lost RPC without an app-side trace. Its wait is bounded at 30 s and then **degrades to running unlocked with a loud stderr warning** rather than failing the run — the one deliberate departure from "fails the acquiring run after a bound", because the critical section is milliseconds and converting a rare stall into a red would cost more than it catches; an abandoned mutex (bridge died mid-input) is caught and treated as acquired, which is the self-healing the other two get from kernel flock.
   - **A binary build — and the machine-wide `build`-slot wait in front of it — is never charged to a test's own clock (2026-07-29).** The session fixtures that build binaries (`nest_binary`, `mail_bridge_binary`, `seal_helper_binary`, the per-app build) delegate to memoized ensurers that `pytest_collection_finish` runs at collection time (`conftest.py::_prebuild_binaries`, beside `_prebuild_web_spa` and the `e2e` slot, which were always correctly placed there). Before this, the `just` recipes' unconditional `{{slot_build}}` acquisition (bounded 5400 s) landed inside the first requesting test's 900 s budget — a **bound inversion** that failed a healthy test as a bare `Timeout (>900.0s)` whenever concurrent builds elsewhere on the machine held both build slots, i.e. a verdict tracking machine load rather than the behavior under test: the harness-side violation of point 14's thesis, unfixable by pre-building (that removes the compile, never the slot wait). Laziness is exact (the collected items' fixture closures + app parametrization decide what builds); a collection-time build failure replays in the requesting fixture (correct attribution, no re-queue) while unrelated tests keep running. **The fixture-driven prebuild has a blind spot: a test that shells out to a `just` recipe directly, requesting no fixture, is invisible to `_prebuild_binaries`'s fixture-closure scan by construction** — measured 2026-08-16 when nine atproto e2e files did exactly that for `atproto-bridge-build`(`-e2e`), one dying as a bare `Timeout (>900.0s)` under fleet contention; closed by converting all nine onto `atproto_bridge_binary`/`atproto_bridge_e2e_binary` session fixtures. **The scope is EVERY build a run needs, and "small" is never a reason to build in-test (ruled 2026-10-30, advisory).** The in-test shape survived as *helper* builds — a helper function a test body calls, which builds a test-only binary on first use (`tests/api/conv_api.py::_ensure_keypkg_bin`, its `mls-group-gen` sibling, `test_plugin_install.py`'s `plugin-fixture-gen`), each slot-wrapped and each justified in its own comment by "the cold cost is one small bin, and the slot wait is the bounded, loud kind". The justification is false twice over, and the proof cost a windows run 3 h 31 m (2026-10-29/30: `test_contacts_accept_opens_conversation.py --app windows` died in pytest's `Timeout` inside `_ensure_keypkg_bin`, every `build` slot held by other sessions and a gate check, the assertions never reached; the same build took 159 s detached). First, the wait's bound is `FAUNA_SLOT_TIMEOUT` (5400 s), six times the 900 s test budget it is nested in — the bound inversion above exactly, and the crate's size has nothing to do with it: a one-crate no-op compile and a workspace build wait in the same queue. Second, the wait is spent holding the run's e2e lane, which the warm pass exists to keep out of the `build` queue. So the rule has no size carve-out: **a build, and any step whose wait is a machine-wide queue's, is reached at collection time or not at all.** Three shapes reach the prebuild — a session fixture's name (`_PREBUILD_BY_FIXTURE`), the helper-binary registry, a seam's table (`DEDICATED_NEST_BINARIES`). The registry is the one home of the helper case: **one helper-binary registry** (`helpers/helper_bins.py`: per test-only binary its crate, `--bin`/`--example`/`--lib`, features, declared disk, any crate of its own outside `libs/`, and the module names — reached transitively through this tree's own imports, `conftest` a leaf — and fixture names that reach it), from which `_prebuild_binaries` (and a tier_1-only run's warm step) adds a stamp-gated, slot-wrapped job for every entry a collected item reaches, the stamp the whole workspace's plus those crates and recording the binary's own mtime, so a binary another cargo run rebuilt under other features reads stale; and **an accessor that never builds** — `helper_bin("mls-keypackage-gen")` replays the collection-time memo (one memo with the fixture builds', a failure included, as `_memoized_build` does) and on a miss fails the test naming the registry gap and the reaching module, so an undeclared reach is a loud red at its first use rather than a silent build inside the clock. **A build that IS a test's subject stays in its test** — the installer an installer test packages, the archive an archive test exports, the image a tier_4 witness runs — under a declared `@pytest.mark.timeout` of at least 3600 s and a named exemption; its *prerequisites* (a bridge, an ffi, a release binary the packager consumes) are prebuilds like any other, run only for a run that will build the subject: a collected test that will skip, or a subject whose own cache will hit, needs none of them (the windows MSI's gate, `helper_bins.windows_msi_inputs_owed`). Enforcement is a cheap-tier ratchet in the app-gate shape (an in-test-build ratchet script beside `check_app_gate_ratchet.py`, minted by the ratchet row): an AST scan per call site under `tests/e2e-unified/tests/**` keyed on the INVOCATION — `_build_slot_cmd(`, `_cargo_cmd(`, `_run_build_recipe(`, a literal argv starting `just <recipe>` where the recipe compiles (`check_recipe_slots.py`'s classification, so `i18n-generate` is not a build), `cargo build|test|run`, `xcodebuild`, `MSBuild`/`dotnet build|publish`, `docker [buildx] build`, `go build`, `wasm-pack` — a per-file down-only ratchet over a committed baseline, with an exemption table naming each subject build and the trees whose subject is the build machinery itself (`test_build_slot.py`, the merge-gate and kache proofs); infrastructure (`conftest.py`'s ensurers, `tests/common/nest.py`, `fauna_ffi.py`, `helpers/prev_build.py`, the registry) is where builds live and is not scanned. What a run SAYS while it waits — the phase line a watching session reads — is the sibling design's; the prebuild's `[prebuild] [build-slot]` lines are today's form.
   - **A run that stops making progress ends itself, and a whole-suite run has a wall-clock ceiling (2026-09-30).** Bounding every test is not bounding the run: a bridge whose thread pegs and never frees turns EVERY later test into a full boot-class wait plus the death-confirm poll, each one correctly classified *alive* (`http_bridge._timeout_verdict` — silence with accepted connects is a stall, not a death), and the run never recovers — measured 2026-09-30, a web tier_2/3 measuring run paid ~490 s on nine tests in a row, sat at 59% after 13 h and held the one-wide `e2e_other` lane the whole time. Two bounds, both ending the run with `pytest.exit` (exit 3, the render preflight's fail-fast shape): **(a)** `http_bridge.BRIDGE_PEGGED_STREAK_ABORT` (3) pegged verdicts on one driver with no bridge answer between them — any HTTP answer, error codes included, or a clean `/health` restarts the count, so a slow boot that finishes is never cut short — abort the run naming the streak and the test it ended in; **(b)** `--max-run-secs` stops a run from STARTING another test once that long has passed since its first (collection and the slot queue hold no e2e lane, so they are not counted; the running test stays bounded by its own 900 s), naming how many of the selection ran — `just e2e-tier-23-check` passes the nightly gate's own `GATE_MAX_SECS` (8 h), so a measuring run launched on its own is bounded too and a run the gate abandons at that bound ends itself rather than holding the lane as an orphan. **(c) A single-threaded bridge frees its own thread before the streak forms (2026-10-19).** (a) and (b) end a run; a bridge must also never stay pegged, because one stuck page-bound call — `page.evaluate` takes no timeout — otherwise costs the whole remaining run, and the web bridge pegged twice this way, hours into whole tier_2/3 runs. The web bridge's watchdog thread (`web-bridge/server.py`, no Playwright calls) writes a `[bridge-watchdog]` line while one request has run past 60 s — the request, the server thread's stack, the Chromium tree's RSS and CPU per process kind — and `http_bridge`'s pegged verdict prints their tail (convention 6). Past `_STUCK_CALL_CEILING_S` (420 s: past the driver's 400 s boot ceiling, inside its 90 s `/health` confirm poll) it kills the bridge's Chromium browser, and does so at 60 s instead when a renderer has crashed under the call. The browser kill is the one Playwright answers: measured on Playwright 1.60, a renderer that crashes, or is killed, under a pending evaluate may leave it pending for ever. The stuck call fails, one test goes red, and the next page-bound request relaunches the browser with every page back at its URL (the pages' stores are gone). Proofs: `test_web_bridge_stuck_call.py` (a never-resolving promise, a spinning renderer, a renderer crashed under the call), `test_web_bridge_watchdog.py`. Proofs for (a) and (b): `test_bridge_death_classification.py::test_a_pegged_streak_aborts_the_run` / `::test_any_bridge_answer_between_pegged_verdicts_restarts_the_count`, and `test_run_ceiling.py`.
   - **A run names its phase while it runs, so a watcher tells a wait from a hang without reading the log (ruled 2026-10-30; BUILT 2026-10-30).** Bounding every wait (above) makes a run end; it does not make a run legible while it runs, and a session grading a detached run reads a bare `RUNNING` for hours. So conftest prints one `[e2e-phase] <phase> — <detail> @<ISO local time>` line, stdout, through the terminal reporter (on a line of its own and outside pytest's output capture), at every boundary of the run's front and body; `<phase>` is a word of a fixed vocabulary and `<detail>` its argument: `collect` (the items collected), `warm pass`, `prebuild` (one per prebuild job, `<detail>` the label `_prebuild_binaries` already prints), `lane wait` and `lane held` (`<detail>` the pool), `in-hold re-check` (whether builds are refused), `tests` (`N selected`), `test` (`<detail>` the node id; from `pytest_runtest_logstart`, before the item's setup and that phase's own clock — on windows the thread-method timeout's `os._exit` leaves this line as the run's last word on which test it was in), `teardown` and `done` (bracketing session finish, with the exit status); the prewarm-only and warm-only modes emit the lines for the boundaries they pass. The wait reason inside a phase is not restated: it is the `[build-slot]` waiting line that follows (*A machine-wide lock wait is loud and bounded*, above), and a phase with no open wait behind it is working, not queued. The existing `[prebuild]` and `[e2e-slot]` lines stay; the phase line is the one a reader parses. The reader is [`detached-run.md`](detached-run.md) § *A run names its phase, and the grade reads it*; the preflight that runs the front on its own first is [`e2e-warm-pass.md`](e2e-warm-pass.md) § *Build/e2e slot locks — the warm pass*, *The preflight*. Pinned by `test_e2e_binary_prebuild.py::test_a_prewarm_only_run_emits_its_boundaries_in_order` and `::test_a_warm_only_run_emits_its_boundaries_in_order`, and by `test_detached_run.py::test_a_run_names_its_phase_and_its_age_in_the_grade` (the grade names the newest phase and its age).
